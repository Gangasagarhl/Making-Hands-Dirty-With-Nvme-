S4. Root cause

Hidden root cause (official): SSD firmware R1.07 caches the HMB segment table internally when the HMB is first enabled after a controller enable (CC.EN 0→1) and does not reload it when the HMB is disabled (EHM = 0) and re-enabled (EHM = 1, MR = 0) with a new descriptor list while the controller remains enabled. After Set Features HMB EHM = 0 completes successfully, the firmware also continues to treat the old segments as valid on the next enable. Consequently, after resume the device accesses host memory that the host legitimately released after the disable completed. On this platform the IOMMU blocks those accesses (UR completions, dropped writes); the firmware then fails commands whose logical-to-physical map segments reside in the HMB (Internal Error, then stalls), and in the second incident hits an internal assertion leading to CSTS.CFS.

Why resets “fix” it: a controller reset clears the firmware’s cached table; the next HMB enable (D35, D39-reset) is the first after CC.EN 0→1 and is therefore honoured. The bug re-arms at the next suspend cycle where the driver chooses new memory.

Why some queues kept working (Likely): commands whose mapping segments were cached in device SRAM or whose LBAs were not mapped through HMB-resident segments did not need HMB reads. SQ 1, 2, 4 traffic in that window was a small working set (developer tools) — consistent but not proven.

Why the second failure looks different (Possible → needs vendor confirmation): in the second incident the first stale access was a write-back of a dirty map segment combined with reads; firmware error handling diverged into an assertion path. Same root cause, different symptom — a common pattern.

S6. Hypotheses eliminated

  • Signal integrity / L1.2 exit: eliminated as root cause — replay succeeded, no Bad TLP/Receiver Errors after, faults are address-specific.
  • Host driver freed HMB while still enabled: eliminated — free happened after EHM = 0 completed successfully (D28 → 600.0012); the specification expects the controller to stop using HMB memory once the disable completes derived (consult the HMB feature description in the Base specification for normative wording).
  • Bad PRPs from host: eliminated — faulting addresses do not match any SQE PRP (SQE H8 PRP1 differs) and match HMB lists exactly.
  • Power-state restore lost config (D3hot): eliminated — PMCSR No_Soft_Reset = 1; Command, Device Control, MSI-X unchanged; admin commands worked immediately (H5, H6).
  • APST: not involved in the failure window (device was in PS0 via explicit Set Features).

S7. Workaround and fix

  • Workaround (host): on resume for this device/firmware, either (a) re-enable HMB with the same memory and list and MR = 1 (keep HMB memory allocated across suspend), or (b) perform a controller reset before re-enabling HMB. Option (a) avoids the bug at the cost of 64 MiB reserved during suspend.
  • Permanent fix (device firmware): on every Set Features HMB with EHM = 0, quiesce and invalidate all HMB segment references before posting the completion; on every EHM = 1, (re)fetch the descriptor list and rebuild the segment table; if MR = 0 treat contents as undefined.
  • Hardening (host): optionally add an IOMMU-fault-to-device correlation in the driver to log “DMA to released HMB region” explicitly.

The decisive step was not decoding packets — it was building the address-attribution table (S3). Investigations often turn on a single join between two evidence sources (here: IOMMU fault addresses ⨝ HMB descriptor lists). Always ask “what other record contains this address/ID/tag?”
