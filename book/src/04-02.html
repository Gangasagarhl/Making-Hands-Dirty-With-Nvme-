27 I/O Queues

27.1 Why this chapter exists

The admin queue is for configuration; the I/O queues carry the actual reads and writes — millions per second on a modern SSD (Solid State Drive). Their number, depth, memory layout and interrupt binding decide whether a system scales across 128 CPUs or bottlenecks on one lock. This chapter teaches the two creation commands field by field, shows queue memory layouts (contiguous and PRP-described), explains the binding SQ→CQ→MSI-X vector→CPU, and treats the Command Identifier (CID) as the critical correlation key it is.

27.2 Learning objectives

  • Encode Create I/O Completion Queue (05h) and Create I/O Submission Queue (01h) in hex, including 0-based QSIZE.
  • Explain IV/IEN, PC and CQID/QPRIO fields and the errors returned when they are wrong.
  • Draw memory diagrams for a contiguous queue and for a non-contiguous queue described by a PRP list.
  • Explain CID uniqueness scope (per SQ) and how Linux encodes CIDs.
  • Choose queue count and depth with a quantitative argument (Little's law).

Prerequisites: Ch 25 ring model, Ch 26 admin queue. MSI-X (MSI-X, Message Signaled Interrupts – Extended) basics.

🧒 Kid analogy — opening checkouts

The manager opens new checkouts by writing two notes. The first note says "put a receipt belt here, 256 spots long, and when receipts arrive press buzzer number 3". The second note says "put a basket belt here, 256 spots long, and send its receipts to receipt belt number 3". You cannot connect a basket belt to a receipt belt that does not exist yet — so receipts belt first.

🧩 Where the analogy breaks

"Buzzer number 3" is an MSI-X table index, not a CPU. The OS decides which CPU each vector interrupts (affinity). One receipt belt can collect receipts from several basket belts, and polled queues have no buzzer at all.

27.6 Interrupt vectors and CPU binding

Each I/O CQ with IEN=1 names one interrupt vector. With MSI-X, the vector is an index into the MSI-X table in a BAR; each table entry holds a message address and data that the OS programmed (typically targeting one CPU's local APIC or equivalent). When the controller posts a CQE to that CQ and decides to interrupt, it issues a posted MWr with that address and data. verified (MSI-X mechanism per PCIe specification.)

 CPU0 ─┬─ SQ1 ─┐                                   MSI-X table (BAR)
       │       ├─► CQ1 ── IV=1 ─────────────────► entry 1: addr→CPU0, data→vec 0x41
 CPU1 ─┴─ SQ2 ─┘ (two SQs may share a CQ)
 CPU2 ─── SQ3 ───► CQ3 ── IV=3 ─────────────────► entry 3: addr→CPU2, data→vec 0x43
 poll ─── SQ9 ───► CQ9 ── IEN=0 (polled, no vector)
 admin─── SQ0 ───► CQ0 ── IV=0 ─────────────────► entry 0

Interrupt coalescing (Set Features FID 08h: aggregation threshold and time) lets the controller delay interrupts to batch completions; it improves throughput and CPU use at a latency cost verified. Whether and how precisely a controller honours it is impl. FID 09h (Interrupt Vector Configuration) can disable coalescing per vector.

27.7 Command Identifier (CID)

  • CID is 16 bits in CDW0[31:16], chosen by the host verified.
  • The pair (SQID, CID) must be unique among outstanding commands: a CID may be reused only after its CQE has been consumed verified. The same CID value may be in flight on two different SQs simultaneously.
  • The CQE echoes CID (DW3[15:0]) and SQID (DW2[31:16]); together they locate the original request.
  • Linux: the CID is derived from the blk-mq tag; newer kernels also place a small generation counter in the upper CID bits so a completion carrying a stale/bogus CID can be detected version (present since roughly the 5.15 era; verify in your kernel source).
🐞 Debugging connection

Kernel messages naming a CID and QID for a timeout are your bridge into an analyzer capture: find the SQE MRd on that queue whose CDW0[31:16] equals the CID, then look for the matching CQE MWr. If you find the SQE fetch but no CQE, the command is lost inside the controller; if you find neither, check the doorbell value.

27.8 Choosing queue count and depth

L = λ × W   (Little's law: outstanding = throughput × latency)
  • L — average number of commands in flight across the queues.
  • λ — target completion rate (IOPS).
  • W — average device latency per command (s).

Example: target 1,000,000 IOPS at 80 µs average 4 KiB read latency → L = 10⁶ × 80×10⁻⁶ = 80 commands in flight. Spread over 16 queues that is 5 per queue; a depth of 64–1024 per queue is ample. More depth than L does not raise throughput; it raises latency once the device saturates. derived

27.9 Deleting queues

Order matters: Delete I/O SQ (00h) first — the controller aborts outstanding commands on that SQ (status Command Aborted due to SQ Deletion, 08h) and posts their completions — then Delete I/O CQ (04h). Deleting a CQ that still has an SQ attached fails with Invalid Queue Deletion (command-specific 0Ch) verified.

27.12 Summary

I/O queues are created by the admin queue, CQ first; they carry QID, 0-based size, contiguity, CQ binding and interrupt vector. CIDs are per-SQ correlation keys. Next: Chapter 28 — doorbells.

28 Doorbells

📘 Source notes

Official specification: NVMe over PCIe Transport Specification (doorbell registers, stride) and NVMe Base Specification (CAP.DSTRD, queue semantics). Revision: PCIe Transport 1.4 / Base 2.4 baseline. Establishes: doorbell location formula, that doorbell values are queue indices. Does not establish: the controller's internal reaction time, fetch size or batching policy (impl).

28.1 Why this chapter exists

The doorbell is the only moment in the I/O fast path where the host CPU talks to the device. Everything before it (building the SQE) is ordinary memory writes; everything after it is device-initiated DMA. Doorbell mistakes — wrong offset, wrong value, missing memory barrier, rung too often — produce the most confusing failures in NVMe: silent hangs, replayed commands, and mysterious throughput ceilings.

28.2 Learning objectives

  • Compute any doorbell offset from QID and CAP.DSTRD, and invert an offset back to a queue.
  • State exactly what value is written and what it means (index, not count).
  • Describe the nine-step flow and the PCIe TLP for the doorbell, including ordering rules that make it correct.
  • Explain doorbell batching, shadow doorbells and their trade-offs.
  • Diagnose doorbell faults from a trace.

Prerequisites: Ch 25, Ch 27; TLP header basics (TLP).

🧒 Kid analogy

The doorbell is the bell on the cashier's desk. Ringing it does not carry any baskets — it only carries one number: "my last basket is just before spot 7". The cashier then walks along the belt and picks up everything up to spot 7. Each checkout has its own bell, and each receipt belt has its own bell you ring to say "I've collected receipts up to spot 3".

🧩 Where the analogy breaks

The "number" is the next empty slot (new tail), not the number of new baskets. And ringing twice with the same number does nothing new; ringing with a number that skips past baskets you never placed makes the cashier scan empty or stale spots — a real bell does not cause that damage.

28.3 The doorbell register map

SQyTDBL offset = 1000h + (2y) × (4 << CAP.DSTRD)
CQyHDBL offset = 1000h + (2y + 1) × (4 << CAP.DSTRD)
  • y — queue identifier (0 = admin).
  • CAP.DSTRD — Doorbell Stride, CAP bits 35:32; stride in bytes = 2^(2+DSTRD) = 4 << DSTRD.
  • SQyTDBL — Submission Queue y Tail Doorbell; bits 15:0 = SQT (new tail).
  • CQyHDBL — Completion Queue y Head Doorbell; bits 15:0 = CQH (new head).
  • Offsets are relative to the start of the controller register space (BAR0/BAR1 pair) verified.

Inverse: given offset O ≥ 1000h, index k = (O − 1000h) / stride; y = k ≫ 1; if k is even it is SQyTDBL, if odd CQyHDBL. Example DSTRD = 0, O = 1034h → k = 13 → y = 6, odd → CQ6HDBL. derived

Why a stride? A larger stride lets each doorbell sit in its own cache line or page — useful for virtualization (map one queue's doorbell page into a guest) or for hardware that wants doorbells in separate address decoding regions. Most physical SSDs report DSTRD = 0 impl.

BAR size consequence: the BAR must be large enough to contain 1000h + 2 × (max QID + 1) × stride bytes. With DSTRD=0 and 128 queue pairs that is 1000h + 256 × 4 = 1400h — under 8 KiB, hence the common 16 KiB BAR0. derived

28.5.1 Ordering — why the controller sees the new SQE, not the old one

  1. The SQE store (step 2) targets write-back cacheable DRAM; the doorbell store (step 4) targets uncacheable MMIO. The driver issues a write memory barrier between them (Linux: writel() includes the needed ordering on most architectures, plus explicit wmb()/dma_wmb() where required) so the SQE is globally visible before the doorbell leaves. impl (architecture-specific)
  2. When the controller's MRd for the SQE arrives at the Root Complex, coherent DMA reads observe the latest CPU store (snooped). On non-coherent platforms the driver must flush caches — a classic porting bug.
  3. In the other direction, PCIe ordering rules say a posted write may not pass an earlier posted write in the same direction (unless Relaxed Ordering is set). So data MWr → CQE MWr → MSI-X MWr arrive in that order, and when the interrupt fires the CQE and data are visible. verified (PCIe ordering rules); a controller using Relaxed Ordering for data must still guarantee data visibility before the CQE — how it does that is impl.

28.6 Doorbell economics: batching and shadow doorbells

  • Batching: writing SQEs for 8 requests then ringing once (tail += 8) costs one MMIO write instead of eight. Linux blk-mq passes a "last request in batch" hint so the NVMe driver can defer the doorbell (commit_rqs path) version. CQ head doorbells are likewise written once per batch of reaped CQEs.
  • Shadow doorbells (Doorbell Buffer Config, admin opcode 7Ch): optional feature for emulated/virtual controllers. The host writes tail/head values to a shadow buffer in memory and only performs the (expensive, VM-exit-causing) MMIO write when an "EventIdx" in another buffer says the controller needs one verified (optional; check OACS). It reduces VM exits for paravirtual NVMe.
  • Cost of an MMIO write: a posted write is cheap for the CPU (tens of ns to issue) but, in a VM without shadow doorbells, it traps to the hypervisor (µs). impl

28.7 Doorbell rules to remember

  • The value is an index in 0…N−1 — writing N or larger is an invalid doorbell write value verified.
  • The new SQ tail must not make the SQ appear to contain more than N−1 entries relative to the controller's head; the new CQ head must not move past the controller's tail (host would be "consuming" entries that do not exist) — both are invalid verified.
  • Writes to doorbells of queues that do not exist are invalid doorbell register writes; the controller may report them as an asynchronous error event verified.
  • Doorbell registers are write-oriented; reading them back is not a reliable way to learn queue state — do not design tools that depend on it uncertain (read behaviour is not something you should rely on across devices).
  • Bits 31:16 of a doorbell are reserved; write zero.

28.8 Code — doorbell calculator and decoder

#!/usr/bin/env python3
"""doorbell.py - compute and invert NVMe doorbell offsets (offline, no device access)."""
def sq_tdbl(qid, dstrd): return 0x1000 + (2 * qid) * (4 << dstrd)
def cq_hdbl(qid, dstrd): return 0x1000 + (2 * qid + 1) * (4 << dstrd)

def which(offset, dstrd):
    stride = 4 << dstrd
    if offset < 0x1000 or (offset - 0x1000) % stride:
        return "not a doorbell (or misaligned for this DSTRD)"
    k = (offset - 0x1000) // stride
    return f"{'CQ' if k & 1 else 'SQ'}{k >> 1}{'HDBL' if k & 1 else 'TDBL'}"

for d in (0, 2):
    print(f"DSTRD={d}: SQ3TDBL={sq_tdbl(3, d):#x} CQ3HDBL={cq_hdbl(3, d):#x}")
for off in (0x1000, 0x1034, 0x1060, 0x1006):
    print(f"offset {off:#x} @DSTRD0 -> {which(off, 0)}")

Solution

Tail went 0→3→6→1 (wrapped): 3+3+3 = 9 commands. CQ head went 0→2→3→7 = 7 consumed, matching 7 CQE writes, so no head write is beyond the tail. Outstanding = 9 − 7 = 2 commands (submitted, not completed). Was the SQ ever over-full? After the third ring, host-side used = (1 − SQ head) mod 8; the controller head is unknown without SQHD values — record "missing evidence: SQHD of last CQE". If SQHD of the 7th CQE was ≥ 2, the SQ never exceeded 7 entries.

Quiz

  1. DSTRD = 2. Offset of CQ5HDBL?

    Answer

    1000h + 11 × 16 = 1000h + B0h = 10B0h.

  2. Is the doorbell MWr acknowledged by a completion TLP?

    Answer

    No, memory writes are posted. Link-level Ack DLLPs confirm delivery across each link, but no end-to-end completion exists.

  3. Host submits 3 commands, SQ tail was 6, N = 8. Value written?

    Answer

    (6+3) mod 8 = 1.

💡 Senior insight

In a protocol trace, the doorbell writes are your skeleton: filter on host-originated MWr to BAR0 ≥ 1000h first, decode each to (queue, index), and only then add device MRd/MWr around them. A clean doorbell skeleton tells you in minutes whether the host or the device stopped first.

28.11 Summary

Doorbells are posted 4-byte MMIO writes of a queue index at 1000h + (2y or 2y+1) × (4 << DSTRD). They are the only host-to-device traffic in the I/O path; ordering barriers make them correct and batching makes them cheap.
