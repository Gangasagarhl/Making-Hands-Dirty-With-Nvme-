23 NVMe Controller

📘 Specification baseline

DOCUMENT: NVM Express Base Specification (architecture, controller model, resets, shutdown, Identify Controller); NVMe over PCIe Transport Specification (PCIe-specific reset interactions). REVISION: Base 2.4, PCIe Transport 1.4 version. STATUS: current baseline. OLDER VERSIONS THAT MAY DIFFER: controller types (I/O, administrative, discovery) are 2.0-era terminology; CRIME/ready-mode fields are 2.0+; Identify fields grow with every revision. SOURCE: nvmexpress.org.

23.1 Why this chapter exists

Most NVMe confusion in reviews and bug reports comes from mixing up two objects: the controller and the namespace. "The drive reset" — which object? "The namespace is read-only" — or is the controller in a degraded state? "Queue 3 belongs to namespace 1" — no, queues belong to controllers and can carry commands for any attached namespace. This chapter makes the controller a precise object with identity, properties, state and lifecycle, and separates it from the subsystem and namespace so cleanly that you will never mix them again.

23.2 Learning objectives

  • Beginner: define subsystem, controller, host and namespace and give one example of each on a real SSD.
  • Intermediate: explain controller properties, controller state (disabled, ready, shutdown, fatal) and how CC/CSTS express it.
  • Advanced: explain reset types (Controller Level Reset, NVM Subsystem Reset, PCIe Conventional Reset, Function Level Reset) and their scope; static vs dynamic controllers; primary/secondary controllers under SR-IOV.
  • Senior: predict the blast radius of an action (reset, format, namespace detach, firmware activation) by reasoning about which object owns which state.
  • Trace analysis: read a controller lifecycle from CC/CSTS accesses and admin commands in a trace.
  • Debugging/validation: design checks for controller identity, state transitions and reset scope.

23.4 Story

🧒 Kid analogy

The library (subsystem) has a front desk (controller). The desk has a light: off (disabled), blinking while it starts up, green (ready), orange while closing for the night (shutdown processing), and red (fatal — "something is badly wrong, call the manager"). The desk has its own in-tray and out-tray (queues). The books are in sections (namespaces) that belong to the library, not to the desk. If the desk closes and reopens, its trays are emptied — but no books are lost. If the whole library is reset, every desk closes at once.

🌍 Real-world analogy

A database server process (controller) serving connections (queues) to tables stored on disk (namespaces). Restarting the server process drops connections and in-flight transactions but not the tables. Two server processes can serve the same table (shared namespace) — and then you need locking (reservations).

🧩 Where the analogy breaks

NVMe does not guarantee what happens to commands in flight at reset time beyond what the spec says (commands may or may not have been executed; the host must treat them as having unknown status). And "the library" might physically be one chip — the subsystem/controller split is architectural, not necessarily physical.

📌 Remember

Queues and registers → controller. Data and format → namespace. Namespaces belong to the subsystem and are attached to controllers. A command names its namespace with the NSID field (CDW1); the queue it travels on names the controller.

23.6 Controller properties

The Base Specification defines the controller's configuration and status as properties with offsets in a property address space (CAP at 00h, VS at 08h, CC at 14h, CSTS at 1Ch, NSSR at 20h, AQA at 24h, ASQ at 28h, ACQ at 30h, …). The PCIe transport maps that property space into BAR0 as MMIO registers (and adds the doorbells at 1000h and above); fabrics transports access properties with Property Get / Property Set commands verified. Some properties are PCIe-only (e.g. INTMS/INTMC for pin-based/MSI interrupt masking, doorbells, CMB/PMR registers) verified.

Notes verified (confirm wording in your revision): on a Controller Level Reset initiated by CC.EN 1→0 the Admin Queue registers (AQA, ASQ, ACQ) are not reset, while other controller state is; drivers reprogram them anyway for robustness. Persistent features (saveable) and namespace data survive all of these resets; volatile features return to defaults. CSTS.NSSRO ("NVM Subsystem Reset Occurred") lets the host detect that an NVM Subsystem Reset happened.

⚠️ Safety

NSSR affects every controller in the subsystem — on a dual-port SSD, the other host loses its queues too. Never use it as a "stronger reset" casually; it is an EXPERT LAB action on dedicated hardware.

23.9 Shutdown

  1. Host stops submitting I/O, optionally deletes I/O queues (good practice: delete SQs then CQs).
  2. Host writes CC.SHN = 01b (normal) or 10b (abrupt).
  3. Controller sets CSTS.SHST = 01b while processing, then 10b when complete — at which point volatile data the controller is responsible for (e.g. write cache content, internal metadata) has been made non-volatile per the specification's shutdown semantics.
  4. Host may now remove power. Linux waits for SHST=10b with a timeout (module parameter shutdown_timeout) impl.

Unsafe shutdowns (power lost before SHST=10b) are counted in the SMART / Health Information log (Unsafe Shutdowns) — a frequently used validation signal verified. NVMe 2.x adds subsystem-level shutdown (NSSD register, CAP.NSSS) and shutdown-type reporting (CSTS.ST) version.

23.11 Deep dive: the subsystem

  • Ports — each PCIe port of a dual-port SSD is a separate PCIe function connected to a different host (or the same host for multipath). Each has its own BDF, BARs and controller.
  • Shared namespaces — the namespace's Identify data indicates whether it may be attached to multiple controllers (NMIC). Coordination is via reservations (Reservation Register/Acquire/Release/Report) verified.
  • Asymmetric Namespace Access (ANA) — reports per-controller access state for groups of namespaces (optimized, non-optimized, inaccessible, persistent loss, change) so multipath hosts pick paths verified.
  • Subsystem-wide actions — NVM Subsystem Reset, firmware activation (often), sanitize (affects all namespaces), subsystem shutdown (2.x).
  • Virtualization — with SR-IOV, a primary controller (on the PF) can manage secondary controllers (on VFs), assigning them queue and interrupt resources (Virtualization Management command) version.

23.12 Linux view

sudo nvme id-ctrl /dev/nvme0 -H | less      # -H decodes bit fields (OACS, ONCS, CMIC...)
sudo nvme list-subsys /dev/nvme0n1          # subsystem NQN, controllers, paths
cat /sys/class/nvme/nvme0/{cntlid,state,transport,address,model,serial,firmware_rev}
cat /sys/class/nvme/nvme0/subsysnqn
sudo nvme list-ctrl /dev/nvme0n1            # controllers that have this namespace attached (if supported)
sudo nvme list-ns /dev/nvme0 --all          # allocated namespace IDs (requires namespace mgmt support)

The sysfs state attribute reports the driver's controller state machine (e.g. live, resetting, connecting, deleting, dead) — this is Linux's state, related to but not identical with the NVMe CC/CSTS state impl.

23.13 Code: a controller object model

class Subsystem:
    nqn; namespaces: dict[nsid → Namespace]; controllers: dict[cntlid → Controller]
    def nvm_subsystem_reset():
        for c in controllers: c.reset(level="subsystem")       # every controller loses queues
        set CSTS.NSSRO on each controller

class Controller:
    cntlid; regs (CAP, VS, CC, CSTS, AQA, ASQ, ACQ, ...); queues; attached: set[nsid]
    def reset(level):
        abort/forget outstanding commands  # host must treat them as status unknown
        delete I/O SQs/CQs; reset admin queue; CSTS.RDY = 0
        features: volatile → defaults; saveable → saved values
    def submit(cmd):
        if cmd.nsid not in attached and cmd needs a namespace: return Invalid Namespace or Format
        ...

class Namespace:
    nsid; format (LBA size, metadata, PI); data
    # survives every controller reset; changed only by Format/Sanitize/Write/Delete

💡 Senior insight

Before any destructive or disruptive action, write down its scope: one command, one queue, one controller, one namespace, all namespaces, the whole subsystem, the PCIe function, or everything below a port. Most production incidents involving NVMe maintenance are scope surprises, not protocol bugs.

Expected reasoning

🧪 Lab 23.2 — Controller reset in a VM CAUTION

Setup: QEMU VM with an extra (non-root) NVMe device. Procedure: sudo nvme reset /dev/nvme1 while watching dmesg -w; then check that nvme id-ns data and file contents on the namespace are unchanged. Questions: what was lost, what persisted?

Expected reasoning

🧪 Lab 23.3 — Simulate scope SAFE

Implement the pseudocode model in 23.13 in Python with two controllers and a shared namespace; implement controller reset and NSSR; print which queues and outstanding commands are lost in each case.

Solution sketch

Controller reset clears only that controller's queue table; NSSR clears both and sets NSSRO on both; namespace dictionaries are untouched in both cases.

🧪 Lab 23.4 — Senior forensic: trace 23.D SAFE

Write the incident timeline and a prevention rule for maintenance on dual-port drives.

Model answer

Timeline: host A activated firmware with a reset that was subsystem-scoped; port 2 link reset; controller 2 lost queues; host B saw I/O errors, then recovered; NSSRO=1 on controller 2 and the firmware slot log confirm. Prevention: treat firmware activation and NSSR as subsystem-scope changes requiring coordination with every host attached to the subsystem (quiesce multipath, fail over, or schedule).

Quiz

  1. Does a Controller Level Reset erase namespace data?

    Answer

    No. It resets controller state and deletes queues; namespace data belongs to the subsystem.

  2. What value written to NSSR starts an NVM Subsystem Reset?

    Answer

    4E564D65h (ASCII "NVMe"), only if CAP.NSSRS = 1.

  3. Which register bits show shutdown progress?

    Answer

    CSTS.SHST: 00b normal operation, 01b processing, 10b complete.

  4. Is "maximum data transfer size" a namespace or controller property?

    Answer

    Controller (Identify Controller MDTS).

Interview questions

  1. Beginner Controller vs namespace?
    Model answer

    Controller = command-processing interface with registers and queues; namespace = formatted storage addressed by NSID, owned by the subsystem and attached to controllers.

  2. Intermediate Walk through CC/CSTS during enable and shutdown.
    Model answer

    Enable: EN=0 → wait RDY=0 → program AQA/ASQ/ACQ and CC → EN=1 → wait RDY=1 within TO. Shutdown: SHN=01b → wait SHST=10b → power off or EN=0 to reuse.

  3. Advanced Compare FLR, Controller Level Reset and NSSR.
    Model answer

    CLR: one controller via CC.EN, config space intact. FLR: PCIe function reset incl. config state; controller reset implied. NSSR: all controllers of the subsystem; may cause PCIe link reset; NSSRO reports it.

  4. Senior How would you design a validation plan for reset robustness?
    Model answer

    Matrix of reset types × controller states (idle, heavy I/O, mid-admin command, during shutdown, during firmware download) × host topologies (single/dual port); checks: data integrity of committed writes, no stale completions after reset, correct NSSRO/AEN behaviour, ready-time within TO, feature persistence rules, AER cleanliness, unsafe-shutdown counters.

23.18 Summary, further reading and next

The controller is the command-processing interface with properties (registers), queues and state; the namespace is formatted storage owned by the subsystem; the subsystem contains both and defines the scope of subsystem-wide actions. CC and CSTS express controller state; resets differ in scope.
