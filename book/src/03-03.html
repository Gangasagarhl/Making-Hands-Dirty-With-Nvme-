19.1 Why this chapter exists

The NVMe driver controls the SSD by reading and writing registers: CAP to learn limits, CC to enable, CSTS to see readiness, AQA/ASQ/ACQ to locate the admin queues, and doorbells to announce work. All of those registers live inside a Base Address Register (BAR) window — a range of physical addresses that, once assigned, the device decodes as its own. This chapter explains how that window is sized, placed, enabled and used, and how a single CPU store becomes a PCIe Memory Write TLP that rings an NVMe doorbell. It is the bridge between PCIe configuration (Chapter 18) and NVMe registers (Chapter 24).

19.2 Learning objectives

  • Beginner: explain a BAR as "a numbered doorway into the device" and distinguish memory BARs from I/O BARs.
  • Intermediate: perform the BAR sizing algorithm for 32-bit and 64-bit BARs and compute size and alignment.
  • Advanced: explain prefetchable vs non-prefetchable, bridge windows, and why NVMe BAR0 is non-prefetchable.
  • Senior: reason about MMIO ordering (posted writes, read-to-flush), access width and atomicity, write-combining, and their effect on doorbell correctness and performance.
  • Trace analysis: identify MMIO MRd/MWr TLPs to BAR0 and decode the register offset from the address.
  • Debugging: diagnose all-ones register reads, BAR assignment failures and doorbell writes that "vanish".
  • Validation: test BAR sizing behaviour, reserved-region behaviour and access-width handling of a controller.

19.4 Story: a numbered doorway

🧒 Kid analogy

A BAR is a numbered doorway into the device. The device was built with a doorway of a fixed width — say 16 rooms wide — but no street number. The town planner (firmware) asks: "How wide is your doorway?" The device can't say the number directly, so they play a game: the planner writes "all the rooms!" (all ones) on the doorway sign; the device rubs out the parts of the number it can't use; what's left tells the planner how wide the doorway is. Then the planner paints a real street number on the doorway. From then on, anyone walking to that street number — the CPU — is actually walking into the device's rooms: room 0 is "what can you do" (CAP), room 14h is "start working" (CC), room 1000h is the bell (doorbell).

🌍 Real-world analogy

A company rents a block of extension numbers on a switchboard. It says "we need 100 consecutive extensions, aligned to a hundred" but not which ones; the telephone exchange assigns 4300–4399. Calls to those numbers ring inside the company; extension 4314 is always the same desk regardless of which block the company got.

🧩 Where the analogy breaks

Walking into a room has no side effect, but reading some device registers can (e.g. a read can clear a status in some devices — not typical for NVMe registers, but legal for devices in general — which is exactly why "non-prefetchable" exists). Also, a doorway only works once the device is told "open for visitors" (Command.MSE = 1), and the street (bridge windows above the device) must route visitors there.

19.5 Beginner view: the BAR register format

3Prefetchable (RO)—
31:4Base address (RW above the size boundary, hard-wired 0 below it)—

The trick that makes sizing work: the device hard-wires to zero every address bit that lies inside its window. A 16 KiB window spans address bits 13:0, so bits 13:4 of the BAR always read 0 regardless of what is written; only bits 31:14 (and the upper BAR for 64-bit) are writable. All BAR sizes are powers of two and every BAR is naturally aligned to its size. verified

19.6 The BAR sizing algorithm

  1. Clear Command.MSE (and I/O Space Enable for I/O BARs) so that the transient all-ones address is not decoded. Otherwise, for a moment, the device claims an address range at the top of memory that might overlap real resources. verified
  2. Read and save the BAR's original value (and the upper BAR if 64-bit).
  3. Write FFFF_FFFFh to the BAR (and to the upper BAR if 64-bit).
  4. Read back. Mask off the low type bits (memory: lower 4 bits; I/O: lower 2 bits).
  5. Invert and add one: size = (~masked) + 1, computed across 64 bits for a 64-bit BAR.
  6. Restore the original value(s); restore Command.
size = (NOT (readback AND ~0xF)) + 1   (computed in the BAR's width: 32 or 64 bits)
  • readback — value read after writing all ones (for 64-bit: upper DWORD << 32 | lower DWORD).
  • 0xF — the four read-only type bits of a memory BAR (use 0x3 for an I/O BAR).
  • size — window size in bytes; also its required alignment.

The executable simulation below models a BAR register in software (hard-wiring the low bits exactly as hardware does) and runs the same algorithm for three BARs.

#!/usr/bin/env python3
"""BAR sizing SIMULATION. A fake BAR register models how hardware hard-wires the low
address bits to zero; the sizing code is the same algorithm firmware/OS use."""

class FakeBar:
    def __init__(self, size, is64, prefetch):
        assert size & (size - 1) == 0 and size >= 16       # power of two, >= 16 bytes
        self.size, self.is64, self.pf = size, is64, prefetch
        self.addr = 0                                     # full 64-bit address latch
    def _flags(self):
        return (0b10 << 1 if self.is64 else 0) | (self.pf << 3)   # bit0=0 -> memory
    def read(self, upper=False):
        if upper:
            return (self.addr >> 32) & 0xFFFF_FFFF
        return (self.addr & 0xFFFF_FFFF & ~(self.size - 1)) | self._flags()
    def write(self, value, upper=False):
        mask = ~(self.size - 1) & 0xFFFF_FFFF_FFFF_FFFF  # writable address bits only
        if not self.is64:
            mask &= 0xFFFF_FFFF
        if upper:
            new = (self.addr & 0xFFFF_FFFF) | (value << 32)
        else:
            new = (self.addr & ~0xFFFF_FFFF) | value
        self.addr = new & mask

def size_bar(bar):
    lo_orig = bar.read()
    if lo_orig & 1:
        raise ValueError("I/O BAR: mask with ~0x3 instead")
    is64 = ((lo_orig >> 1) & 0b11) == 0b10
    hi_orig = bar.read(upper=True) if is64 else 0
    # (Command.Memory Space Enable must be 0 while sizing -- see text.)
    bar.write(0xFFFF_FFFF)
    lo = bar.read()
    hi = 0xFFFF_FFFF
    if is64:
        bar.write(0xFFFF_FFFF, upper=True)
        hi = bar.read(upper=True)
    print(f"  read back lo={lo:#010x}" + (f" hi={hi:#010x}" if is64 else ""))
    mask = (hi << 32 | (lo & ~0xF)) & 0xFFFF_FFFF_FFFF_FFFF
    if not is64:
        mask |= 0xFFFF_FFFF_0000_0000      # treat a 32-bit BAR as having all-ones upper bits
    size = ((~mask) & 0xFFFF_FFFF_FFFF_FFFF) + 1
    bar.write(lo_orig & ~0xF)               # restore original address
    if is64:
        bar.write(hi_orig, upper=True)
    return size, is64, (lo_orig >> 3) & 1

for desc, bar in [("NVMe BAR0 (16 KiB, 64-bit, non-prefetchable)", FakeBar(16 * 1024, True, 0)),
                  ("32-bit 1 MiB non-prefetchable", FakeBar(1 << 20, False, 0)),
                  ("64-bit 8 GiB prefetchable (e.g. a GPU)", FakeBar(8 << 30, True, 1))]:
    print(desc)
    size, is64, pf = size_bar(bar)
    print(f"  size = {size:#x} ({size // 1024} KiB) 64-bit={int(is64)} prefetchable={pf}")

Note the 8 GiB case: the lower DWORD reads back 0000_000Ch — all its address bits are inside the window — and the upper DWORD FFFF_FFFEh carries the size information. A 32-bit-only sizing routine would conclude "size = 16 bytes"! This is why a 64-bit BAR must be sized as a pair. derived

In NVMe terms, the registers at BAR0 are named MLBAR (Memory Register Base Lower Address, at 10h) and MUBAR (Memory Register Base Upper Address, at 14h) in the transport specification. The NVMe specification also defines an optional Index/Data Pair register mechanism at BAR2 for legacy I/O-space access to the registers version; modern hosts use the memory BAR. Other BARs may hold MSI-X tables, the Controller Memory Buffer (CMB) or Persistent Memory Region (PMR) — located through MSI-X BIR fields and CMBLOC.BIR / PMRCAP.BIR impl.

19.8 Placing the window: resource assignment

After sizing all BARs, firmware (or the OS) solves a packing problem: assign every BAR an address naturally aligned to its size, inside its parent bridge's window, and size each bridge window (1 MiB granularity for memory windows) to cover all children. Bridges are then programmed bottom-up so that memory requests are routed:

  • A Downstream-going MWr/MRd is forwarded by a bridge if its address lies within the bridge's Memory or Prefetchable window.
  • An Upstream-going request (DMA from the SSD) is forwarded by a bridge if its address lies outside its windows (i.e. not destined for a sibling below it) — peer-to-peer within a switch is possible when the address falls inside a sibling's window and the switch permits it (ACS may redirect it upstream) verified.

19.9.1 What happens when the driver writes a doorbell

  1. The driver executes writel(tail, dbs + offset). dbs is a kernel virtual address produced by ioremap() of BAR0.
  2. The CPU's MMU translates the virtual address to the physical BAR address. The page is mapped uncacheable (UC) — no cache line is allocated, the store goes out as-is impl (architecture-specific memory types).
  3. The store reaches the Root Complex, which decodes the physical address as MMIO belonging to the Root Port's window and generates a MWr TLP: 1 DW payload, address = BAR0 + offset, Requester ID = the Root Complex.
  4. Bridges forward it downstream by address range. The SSD's BAR0 decoder claims it.
  5. Because MWr is posted, the CPU does not wait for any acknowledgement at the transaction level (the Data Link Layer still ACKs the TLP for reliability). The CPU continues immediately.
  6. The controller latches the new tail value and begins fetching submission queue entries by DMA (Chapter 20).
📡 Protocol: posted write ordering and the "read to flush" idiom

PCIe ordering rules let a later read not pass an earlier posted write in the same direction (with default attributes) verified. So if software must be sure a register write has arrived (for example before timing a delay), it reads any register of the same device: the read's completion cannot return before the earlier write was delivered. Linux drivers use this idiom (a read-back after write) in some reset and shutdown paths. Doorbell writes in the hot path deliberately avoid it — waiting a round-trip per I/O would cost microseconds.

⚠️ Access width

NVMe 64-bit registers (CAP, ASQ, ACQ, CMBMSC, …) may be accessed by hosts as two 32-bit accesses on platforms that lack atomic 64-bit MMIO; Linux uses lo_hi_readq/lo_hi_writeq helpers on such platforms. The NVMe specification defines the access rules for each register (for example which widths are required to be supported) — check the "register access" rules in your revision before relying on a particular behaviour version. Never use byte or word writes to doorbells; they are 32-bit registers.

19.11 Hardware view inside the SSD controller

Inside the controller, the PCIe endpoint core's BAR decoder compares the address of each incoming MRd/MWr against the BAR0 window and passes hits, with the offset, to a register block. The register block implements fixed registers (often in hardware), doorbell registers (often a small write-only RAM per queue whose writes trigger the queue manager), and possibly the MSI-X table. What happens after a doorbell write — how quickly the fetch engine reacts, whether doorbell writes are coalesced — is implementation-dependent and generally unobservable except through timing on a protocol analyzer.

📭 What the spec does not say

The NVMe specification defines what each register means and how the host shall use it; it does not specify how the controller implements decode, how long a register read takes, or how doorbell writes are internally queued. Latency numbers you see in a trace for MMIO reads are properties of a particular platform and controller.

Reading NVMe registers directly through resource0 is possible for root. The following is hardware-dependent and should be run only on a test machine:

#!/usr/bin/env python3
# CAUTION LAB: maps BAR0 of an NVMe device read-only and reads CAP, VS, CC, CSTS.
# Reading these registers has no side effects per the NVMe register definitions,
# but mapping device memory as root is a privileged operation. NEVER write here
# while the kernel nvme driver owns the device.
import mmap, os, struct, sys
bdf = sys.argv[1]                                   # e.g. 0000:01:00.0
fd = os.open(f"/sys/bus/pci/devices/{bdf}/resource0", os.O_RDONLY | os.O_SYNC)
m = mmap.mmap(fd, 4096, mmap.MAP_SHARED, mmap.PROT_READ)
rd32 = lambda off: struct.unpack_from("<I", m, off)[0]   # 32-bit accesses only
cap = rd32(0x00) | (rd32(0x04) << 32)
print(f"CAP={cap:#018x} VS={rd32(0x08):#010x} CC={rd32(0x14):#010x} CSTS={rd32(0x1C):#010x}")
⚠️ Safety note

Python's struct.unpack_from on an mmap is not guaranteed to perform a single 32-bit bus access on every platform/Python build impl. For reliable register work use a tool or a small C program with volatile 32-bit loads. Some kernels restrict resource mapping when lockdown is active. Writing any register (especially CC, NSSR or doorbells) behind the driver's back can corrupt queues and data.

# Inside a (simplified) controller model: decode an incoming memory request
on_memory_request(tlp):
    if not cfg.command.MSE:                 return  # not decoded → upstream sees UR
    if not (BAR0 <= tlp.addr < BAR0 + 16 KiB): return  # not ours
    off = tlp.addr - BAR0
    if tlp.is_write:
        if off >= 0x1000:
            q, is_cq = divmod((off - 0x1000) // (4 << CAP.DSTRD), 2)
            ring_doorbell(q, is_cq, tlp.data)      # tail for SQ, head for CQ
        else:
            write_register(off, tlp.data, tlp.byte_enables)
    else:
        send CplD(read_register(off, tlp.length))

19.15 Common mistakes

  • Sizing a 64-bit BAR with only its lower DWORD.
  • Leaving Command.MSE = 1 while writing all ones to a BAR.
  • Assuming BAR addresses are stable across boots or rescans.
  • Mapping register BARs write-combining or cacheable — reads might be served stale, writes merged or reordered.
  • Expecting a completion for an MMIO write.
  • Putting a CPU physical address into a PRP when an IOMMU is active (should be a DMA address).
  • Assuming MSI-X table placement — always read BIR/offset.

💡 Senior insight

All-ones is the universal "something is not there" signature for both configuration reads and MMIO reads. Make it a reflex: when a register reads all-ones, first prove the device is still reachable (Vendor ID, link state), then prove decode is on (MSE, BAR), and only then believe the value. NVMe registers do have fields that can legitimately be all-ones in part, but a whole 32-bit FFFF_FFFFh in CSTS or CAP is never a healthy value.

🧪 Lab 19.3 — Senior forensic: the vanishing doorbell SAFE

Scenario (synthetic): a custom user-space driver rings SQ1 tail at BAR0+1008h, but the controller never fetches. CAP high DWORD = 0000_0002h. Task: find the bug.

Model answer

CAP.DSTRD = bits 35:32 = 2 → stride 4<<2 = 16 bytes. SQ1TDBL = 1000h + (2×1)×16 = 1020h, not 1008h. 1008h falls in the gap between SQ0TDBL (1000h) and CQ0HDBL (1010h) — a write to an undefined location. Fix: compute offsets from DSTRD. Confidence high; verify with an analyzer showing MWr at 1008h with no subsequent MRd of SQ1 memory.

Quiz

  1. Read-back after all-ones: FFFF_8004h, upper FFFF_FFFFh. Size?

    Answer

    Mask FFFF_FFFF_FFFF_8000h → size 8000h = 32 KiB; 64-bit, non-prefetchable.

  2. Why are register BARs non-prefetchable?

    Answer

    Because reads may have side effects or must reflect current state; the system must not speculatively read or merge accesses.

  3. Is an MMIO write to a doorbell acknowledged by a completion TLP?

    Answer

    No. MWr is posted. Only link-level ACK DLLPs acknowledge delivery across each link.

  4. Where are NVMe doorbells located?

    Answer

    In BAR0 starting at offset 1000h; SQyTDBL at 1000h + (2y)×(4<<DSTRD) and CQyHDBL at 1000h + (2y+1)×(4<<DSTRD).

  5. Name two address kinds that may differ for the same DRAM page.

    Answer

    Physical address and DMA address/IOVA (when an IOMMU is used); also the kernel virtual address.

Interview questions

  1. Beginner What is a BAR?
    Model answer

    A configuration register that declares the type and size of an address window the device decodes, and holds the base address software assigns to it.

  2. Intermediate Walk me through BAR sizing for a 64-bit BAR.
    Model answer

    Disable decode, save both DWORDs, write all ones to both, read both, combine, mask the 4 type bits, invert, add one, restore both, re-enable decode.

  3. Intermediate MMIO vs config access?
    Model answer

    Config: ID-routed, non-posted CfgRd/CfgWr to configuration space; MMIO: address-routed MRd/MWr to BAR windows, writes posted. NVMe registers are MMIO.

  4. Advanced Why might a driver read back a register after writing it?
    Model answer

    To force earlier posted writes to complete before proceeding (ordering: the read completion cannot pass the earlier write), e.g. before a timed delay or before assuming a reset bit took effect.

  5. Senior Dozens of NVMe drives fail to get BARs in a dense server. What is your analysis?
    Model answer

    Non-prefetchable windows are 32-bit in Type 1 bridges; each drive's BAR0 (+ MSI-X, maybe CMB) needs space aligned within 1 MiB-granular bridge windows; with hot-plug reservation per port, 32-bit MMIO is exhausted. Options: firmware with larger MMIO hole, reducing per-port reservation, relying on 64-bit placement where the platform permits, or BIOS settings; verify with /proc/iomem and dmesg.

19.19 Summary, further reading and next

A BAR is a numbered doorway: the device fixes its size and type, software chooses its address. Sizing exploits hard-wired zero bits; 64-bit BARs are sized as pairs. NVMe registers are MMIO in BAR0 (non-prefetchable, 64-bit), with doorbells at 1000h. MMIO writes are posted; reads are non-posted and can be used to flush. Address kinds differ: VA, PA, IOVA, bus address, BAR address, controller-local.

Further reading: PCIe Base Specification sections on BARs and Type 1 windows; NVMe over PCIe Transport Specification (register mapping, MLBAR/MUBAR); Linux Documentation/driver-api/device-io.rst (MMIO accessors and ordering).
