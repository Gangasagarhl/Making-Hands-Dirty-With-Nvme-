PART IX

NVMe Architecture

Parts VII and VIII gave you a PCIe function with a mapped BAR0 and permission to DMA. Now we put NVMe on top of it. This Part builds the complete mental model — host, driver, subsystem, controller, namespace, media — then explains how the NVM Express specification family has been reorganized since 2.0 into a base specification, command-set specifications and transport specifications, and finally goes deep into the controller as an object (state, properties, types) and into its registers bit by bit, ending with a step-by-step controller initialization you can execute in simulation. 21 What Is NVMe?

📘 Specification baseline

DOCUMENT: NVM Express Base Specification. REVISION: 2.4 (released as part of the NVMe 2.4 specification set announced 4 August 2026 — confirm on nvmexpress.org) version. STATUS: current baseline for this course. OLDER VERSIONS THAT MAY DIFFER: NVMe 1.0 (2011) through 1.4 were single monolithic documents (with separate NVMe over Fabrics and NVMe-MI documents); 2.0 (2021) restructured the family (Chapter 22). SOURCE: https://nvmexpress.org/specifications/ ; https://nvmexpress.org/specification/nvm-express-base-specification/.

21.1 Why this chapter exists

Engineers who learn NVMe as "a faster SATA" or "a list of opcodes" get lost the moment a question involves two controllers, a shared namespace, a fabric transport, or a reset that affects more than one host. NVMe is an architecture — a set of objects (subsystem, controllers, namespaces, queues, ports) with defined relationships — plus a protocol carried by transports. This chapter builds the whole picture first, so that every later detail has a place to land.

21.2 Learning objectives

  • Beginner: state what NVMe is and name the chain Host → driver → subsystem → controller → namespace → media.
  • Intermediate: explain queue pairs, doorbells, admin vs I/O queues, and how NVMe differs from AHCI/SATA.
  • Advanced: distinguish protocol, command sets and transports; distinguish memory-based (PCIe) and message-based (fabrics) transport models.
  • Senior: reason about which object owns which state (queues belong to controllers; data belongs to namespaces; namespaces belong to the subsystem) and use that to predict the effects of resets and failures.
  • Trace analysis: place every NVMe-related transaction in a trace onto the object model.
  • Debugging / validation: know which Linux object (/dev/nvme0, /dev/nvme0n1, nvme-subsys0) corresponds to which NVMe object.

21.4 Story: the library, complete

🧒 Kid analogy

The school (host) has teachers (CPU cores). Each teacher has her own request box (Submission Queue) and answer box (Completion Queue) so teachers never fight over boxes. The giant library building is the NVM subsystem. Inside are one or more librarians at desks (controllers) — each desk serves visitors through its own doors. The library has sections (namespaces): "Section 1 — novels, numbered pages 0 to a billion". Behind the sections are the shelves and the warehouse (NAND media) that nobody visits directly. A librarian takes a slip from a box ("read pages 100–107 of section 1 into table 42"), fetches the books, puts them on the table, drops an answer slip, and taps the teacher.

🌍 Real-world analogy

A bank: the bank (subsystem) has several tellers (controllers), each with its own queues; customer accounts (namespaces) are held by the bank, not by a teller — any teller with access can serve an account; the vault (media) is behind everything. Closing one teller's window (controller reset) does not close the bank or delete accounts.

🧩 Where the analogy breaks

Controllers are not people with judgement — they process commands per the specification, in an order that is generally not guaranteed to match submission order. Namespaces are not just "sections": they have formats (LBA size, metadata), may be shared by controllers in different hosts, may be attached and detached, and may belong to different I/O command sets (block, zoned, key-value). The "warehouse" (flash translation layer, NAND) is entirely implementation-specific and outside the specification.

21.7 Protocol, command sets, transports

  • Protocol — the queueing model (SQ/CQ, doorbells or capsules), the 64-byte command and 16-byte completion formats, the admin command set, the controller state machine, features, log pages, asynchronous events, error reporting. Defined in the Base Specification.
  • I/O command sets — what I/O commands mean for a namespace of a given type: NVM Command Set (logical blocks: Read 02h, Write 01h, Flush 00h, Dataset Management 09h, Write Zeroes 08h, Verify 0Ch, Copy 19h…), Zoned Namespace (zones with sequential-write rules), Key Value, plus Computational Programs and Subsystem Local Memory command sets. Each namespace is associated with one I/O command set, identified by a Command Set Identifier (CSI) version.
  • Transports — how commands, data and completions move between host and controller: PCIe (memory-based: queues in host memory, DMA, MMIO doorbells), RDMA and TCP (message-based: commands and completions travel in capsules), and Fibre Channel (the FC mapping is defined by INCITS T11 as FC-NVMe, with NVMe-side requirements in NVMe documents) verified.
📡 Memory-based vs message-based

On PCIe, a "submission" is the host writing an SQE to its own memory and ringing a doorbell; the controller pulls the SQE. On fabrics, the host sends a command capsule (SQE plus optional in-capsule data) over the network; the controller sends back a response capsule containing the CQE. Same 64-byte command, same 16-byte completion, different delivery. Registers on PCIe correspond to properties on fabrics, accessed with Property Get/Set commands. verified

21.8 The command lifecycle in ten lines

  1. Application issues a read; the block layer picks the per-CPU hardware queue.
  2. Driver allocates a Command Identifier (CID), builds a 64-byte SQE (opcode 02h Read, NSID, SLBA in CDW10–11, NLB in CDW12, PRP1/PRP2 in DPTR bytes 24–39).
  3. Driver writes the SQE at SQ tail, advances tail, writes SQyTDBL.
  4. Controller fetches the SQE (MRd/CplD).
  5. Controller reads media (internal) and writes data (MWr) to PRP addresses.
  6. Controller writes a 16-byte CQE (DW2: SQ Head Pointer and SQ Identifier; DW3: CID, Phase Tag, Status) to the CQ.
  7. Controller sends MSI-X (unless coalesced/masked).
  8. Driver sees the new phase tag, matches CID to the request, checks status (SCT/SC, DNR, More).
  9. Driver writes CQyHDBL to release CQ entries; uses SQHD to know SQ slots are free.
  10. Block layer completes the request to the application.

21.9 Linux view

sudo nvme list                       # namespaces with their controller and model
sudo nvme list -v                    # subsystems → controllers → namespaces (newer nvme-cli)
sudo nvme list-subsys                # subsystem NQN, controllers, transport, address
ls /sys/class/nvme/ /sys/class/nvme-subsystem/ /sys/block/ | grep nvme
sudo nvme id-ctrl /dev/nvme0 | head -40   # controller identity (VID, SN, MN, FR, CNTLID, VER …)
sudo nvme id-ns /dev/nvme0n1 | head -30   # namespace size, capacity, LBA formats
cat /proc/interrupts | grep nvme          # per-queue vectors
⚠️ Naming trap

In Linux, nvme0n1 means "namespace 1 as seen through the subsystem/controller instance 0", but with native NVMe multipath the block device is attached to the subsystem and the controller numbers in the name may not match the controller actually used for I/O impl. Always confirm with nvme list -v or sysfs.

21.10 Common mistakes

  • "The SSD is the controller." The SSD is (usually) a subsystem containing one controller per PCIe function.
  • "Namespaces belong to controllers." They belong to the subsystem and are attached to controllers.
  • "NVMe means PCIe." NVMe is transport-independent; NVMe over PCIe is one transport.
  • "Commands complete in order." They need not; CID matching exists for this reason.
  • "VS in BAR0 tells me which features exist." It reports the specification version; individual features are discovered from CAP and Identify fields.

Quiz

  1. Name the six-link chain of the NVMe mental model.

    Answer

    Host → NVMe driver → NVM subsystem → controller → namespace → media.

  2. What is the difference between a command set and a transport?

    Answer

    A command set defines the meaning of I/O commands for a namespace type (blocks, zones, key-value…); a transport defines how commands/data/completions are delivered (PCIe, RDMA, TCP, FC).

  3. Why does NVMe avoid register reads in the I/O path?

    Answer

    MMIO reads are non-posted round trips costing on the order of a microsecond; NVMe puts completions in host memory with a phase tag instead.

  4. Which object does a controller reset destroy, and which does it not?

    Answer

    It destroys that controller's queues and volatile controller state; it does not delete namespaces or their data (which belong to the subsystem).

Interview questions

  1. Beginner What is NVMe?
    Model answer

    A host-controller interface and protocol for non-volatile storage, built around many paired submission/completion queues in host memory, with defined command sets and multiple transports.

  2. Intermediate Compare NVMe with AHCI.
    Model answer

    Many deep queues vs one 32-entry list; doorbell-only submission vs multiple register accesses; per-queue MSI-X vs per-port interrupts; designed for NVM vs rotating disks.

  3. Advanced How do registers on PCIe relate to properties on fabrics?
    Model answer

    The Base Specification defines controller properties; the PCIe transport maps them into BAR0 MMIO; fabrics access them with Property Get/Set commands.

  4. Senior Two hosts see the same namespace via different controllers. What can go wrong and what does NVMe provide?
    Model answer

    Concurrent writers can corrupt each other's data without coordination; NVMe provides reservations (and ANA for multipath access state), but correctness above blocks is the responsibility of a cluster-aware file system or application.

On PCIe, queues live in host memory, doorbells are MMIO, and the controller does all bulk movement by DMA. 22.4 Story

🧒 Kid analogy

The library rule book got so thick nobody could carry it. So the librarians split it: one main rule book for how every library works (how to queue, how to ask questions, how to open and close), one small book per kind of section (novels, maps, puzzle boxes), and one small book per way of getting to the library (by road, by train, by boat). Now when a new kind of section opens, they write a new small book and don't reprint the main one.

🧩 Where the analogy breaks

The books are released together as a set with coordinated revision numbers, and they cross-reference each other heavily; you often need two or three of them open to answer one question (e.g. PRP rules in Base + Read command in NVM Command Set + doorbell layout in PCIe Transport).

22.6 Why NVMe was modularized

  1. Size and navigability. By 1.4 the base document had grown very large, mixing PCIe-specific register details, block-storage command details and architecture. Readers needed only a fraction for any one task.
  2. Transport independence. NVMe over Fabrics was a separate document layered awkwardly on a PCIe-centric base. In 2.0 the fabrics architecture moved into the Base Specification and each transport got its own document — PCIe became "a transport" rather than "the" NVMe.
  3. Multiple I/O command sets. Zoned Namespaces and Key Value needed first-class status. Defining the block-storage commands in a separate NVM Command Set Specification made "an I/O command set" a pluggable concept, with discovery via I/O Command Set profiles and the Identify I/O Command Set data structure version.
  4. Independent evolution. A new command set (later: SLM, Computational Programs) or a transport change can be released without re-ratifying unrelated text; revisions of each document advance at their own pace (hence Base 2.4 alongside NVM 1.3 and ZNS 1.5).
  5. Cleaner compliance claims. A product can state exactly which documents and revisions it implements.
💡 Senior insight

The restructuring changed where things are written, not how a PCIe NVMe SSD works on the wire. A 1.4-era SSD and a 2.x SSD both use the same SQE/CQE formats, the same doorbells and the same admin queue registers. What changed for host software: new controller types, I/O Command Set selection in CC.CSS, new CAP/CC fields, new Identify CNS values, and the mental model that NVMe is transport-agnostic. When reading any statement, always ask: "Is this base, command-set, or transport?"

22.8 I/O Command Set discovery and selection

Since 2.0, a controller may support several I/O command sets. The host learns and selects them through a defined sequence version:

  1. Read CAP.CSS (bits 44:37). Bit 37 (in the CSS field: bit 0) = NVM Command Set supported; bit 43 (CSS bit 6) = one or more I/O Command Sets supported (I/O Command Set profiles); bit 44 (CSS bit 7) = no I/O command set supported (admin-only controller).
  2. Set CC.CSS (bits 6:4) before enabling: 000b = NVM Command Set; 110b = all supported I/O Command Sets (requires CAP.CSS bit 43); 111b = Admin Command Set only.
  3. If CC.CSS = 110b: issue Identify with the CNS value for the Identify I/O Command Set data structure to list supported command-set combinations, then select one with the I/O Command Set Profile feature (Set Features).
  4. For each namespace, discover its Command Set Identifier (CSI) via the Namespace Identification Descriptor list, and use I/O-command-set-specific Identify (CNS values that take a CSI) to read its type-specific structure. Commonly cited CSI values: 00h NVM, 01h Key Value, 02h Zoned Namespace; values for newer command sets: check the Base Specification.
📭 What must be checked in the specification

The exact CNS codes for "Identify I/O Command Set data structure" and the I/O-command-set-specific Identify variants, and the CSI values of SLM and Computational Programs command sets, must be taken from the current Base Specification — this course does not assert them.

Quiz

  1. Which document defines the Identify admin command?

    Answer

    The NVM Express Base Specification (Admin Command Set is in Base).

  2. Which document defines the Write command's fields?

    Answer

    The NVM Command Set Specification (with common SQE fields from Base).

  3. What does CC.CSS = 111b select?

    Answer

    Admin Command Set only (no I/O command set).

  4. Name three reasons for the 2.0 restructuring.

    Answer

    Navigability/size, transport independence (fabrics in base, per-transport docs), first-class multiple I/O command sets, independent evolution, cleaner compliance.

Interview questions

  1. Beginner What is in the NVMe Base Specification?
    Model answer

    Architecture, queueing model, command/completion formats, Admin Command Set, properties/registers semantics, initialization/reset/shutdown, features, logs, errors, security, fabrics architecture.

  2. Intermediate How does a host discover which I/O command sets a controller supports?
    Model answer

    CAP.CSS bits, then (if I/O command sets supported) select CC.CSS=110b, Identify the I/O Command Set data structure, choose a profile via Set Features, discover per-namespace CSI through the namespace descriptor list.

  3. Advanced Why are command sets versioned separately from Base?
    Model answer

    So they can evolve independently; a ZNS change need not reissue Base; products claim combinations of revisions.

  4. Senior A customer asks whether your drive "supports NVMe 2.4". How do you answer precisely?
    Model answer

    Break it down: which Base revision the controller reports (VS), which mandatory features of that revision are implemented, which optional features (listed with Identify evidence), which command-set and transport revisions are claimed, and any compliance test results (e.g. interoperability test suites). "Supports 2.4" without that breakdown is not an engineering statement.
