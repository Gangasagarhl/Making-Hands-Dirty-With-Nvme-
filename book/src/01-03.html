Chapter 1 introduced fifteen ideas one at a time. This deep-dive module joins them into one working machine and pushes each of them through the full ladder: hardware, specification, protocol, trace and debugging. If you only skimmed Chapter 1, go back — this module assumes every term there.

1A.2 A fresh story — the harbour office

🧒 Kid analogy — the harbour

A harbour master sits in an office (the CPU core) with a small notepad (registers) and a filing cabinet next to the desk (cache). Behind the office is a huge warehouse (DRAM) with numbered shelves. Out at sea are ships (devices), each with a captain (controller) and a radio.

The harbour master can do two things to the outside world: send a radio message (a store) or ask a question over the radio and wait for the answer (a load). Sending is quick — you speak and hang up. Asking means sitting by the radio, doing nothing, until the ship answers. A wise harbour master sends many messages and asks very few questions.

Ships with a crane (DMA) can unload cargo straight onto warehouse shelves without the harbour master touching any of it; the harbour office's switchboard (root complex) and its customs desk (IOMMU) decide which shelves each ship may use.

🧩 Where the analogy breaks
  • Represents: the asymmetry between posted writes and non-posted reads; the separation between CPU, memory and device; the gatekeeping role of the root complex and IOMMU.
  • Hides: caches coherence protocols; that many cores issue requests concurrently; that “radio messages” are packets with flow-control credits and can be retried at the link level.
  • Misleads: a radio message is heard instantly by everyone; a PCIe write travels one hop at a time and can sit in buffers. And unlike ships, a device that has “sunk” (been surprise-removed) still gets “answered” — the platform synthesises all-ones read data for the CPU.

1A.6 Specification discipline

📘 Specification — which documents govern this module

SPECIFICATION BASELINE — DOCUMENTS: PCI Express Base Specification (PCI-SIG; posted vs non-posted semantics, completion rules, Command register bits); NVMe Base Specification Rev. 2.4 and NVMe over PCIe Transport Specification Rev. 1.4 (controller register layout and doorbells). STATUS: current as of the August 4, 2026 NVMe release; PCIe revision per your platform. OLDER VERSIONS THAT MAY DIFFER: NVMe 1.x placed the register map and PCIe-specific behaviour in a single base document; NVMe 2.0 and later split PCIe-specific material into the PCIe transport specification version. SOURCE: nvmexpress.org specifications index; pcisig.com.

1A.7 Hardware view

  • Must participate: a core, the root complex, a root port, the link, the device's PCIe interface and register block.
  • May participate: PCIe switches, retimers, the IOMMU (for DMA, not MMIO), the inter-socket link on NUMA systems.
  • Observable: TLPs on the link (with an analyzer), register values (via the driver or debug tools), interrupt counts, kernel logs.
  • Internal and usually unobservable: cache states, store buffers, fabric queues, controller firmware state between register accesses.

1A.8 Protocol view

Software actionTLPPosted?ResponseTypical failure response
Register read (readl)MRd, 1 DWNoCplD with 4 bytesCompletion timeout, or Cpl with UR (Unsupported Request) / CA (Completer Abort); CPU usually sees all ones impl
Register write (writel)MWr, 1 DWYesNoneSilently dropped if device absent; error may be logged via AER at the receiver
64-bit register read (readq)MRd 2 DW, or two 1 DW readsNoCplDSplit 64-bit access may tear if the value changes between halves impl
Config read (lspci)CfgRd0 / CfgRd1NoCplDCpl with UR for a non-existent function (enumeration relies on this)

Ordering: posted writes from the CPU to one device arrive in order. A read following writes to the same device acts as a “flush” — the read's completion cannot overtake the writes, so reading any register after writing confirms the earlier writes reached the device. This is a common driver idiom.

⚠️ Warning

nvme show-regs only reads registers. Do not experiment with tools that write BAR registers (or setpci writes to config space) on a live system drive — a write to CC or to a doorbell can hang or corrupt the device.

1A.11 Labs

🧪 Lab 1A.1 (beginner) — Map the actors on your machine SAFE

Objective: identify cores, NUMA nodes, memory size and PCIe functions. Prerequisites: Chapter 1. Setup: any Linux machine.

Procedure:

lscpu | head -25
free -h
lspci -tv
lspci -nn | grep -i -e "non-volatile" -e 0108

Observations: record core count, NUMA nodes, memory, the tree path from root port to the NVMe function. Questions: how many bridges sit between the root complex and the SSD? Expected reasoning: each bridge in lspci -tv is a hop where the TLP is forwarded.

Solution

On a typical desktop the NVMe function hangs directly under a CPU root port (one hop); on chipset-attached M.2 slots it hangs under a chipset downstream port, behind the chipset's uplink — more latency and shared bandwidth. Lab answers are platform-specific impl.

Extension: identify which M.2 slot is CPU-attached on your motherboard from its manual and confirm with the tree.

🧪 Lab 1A.2 (intermediate) — Decode controller registers by hand SAFE

Objective: decode CAP, VS, CC, CSTS. Setup: root shell, nvme-cli, an NVMe device. Procedure: run sudo nvme show-regs /dev/nvme0 (raw hex) and, separately, with -H (human). Decode the raw CAP yourself: MQES = bits 15:0 (0's-based), TO = bits 31:24 (×500 ms), DSTRD = bits 35:32, MPSMIN = bits 51:48, MPSMAX = bits 55:52.

Questions: (1) Maximum I/O queue entries? (2) Worst-case ready timeout? (3) Doorbell stride in bytes? (4) Minimum memory page size?

Solution

(1) MQES+1. (2) TO × 500 ms. (3) 4 << DSTRD bytes (4 bytes when DSTRD=0). (4) 2^(12+MPSMIN) bytes — 4 KiB when MPSMIN=0. Compare your decode with -H; any mismatch reveals a bit-extraction error on your side.

Extension: compute the byte offset of SQ 3's tail doorbell and CQ 3's head doorbell for your device's DSTRD.

🧪 Lab 1A.3 (advanced) — Measure the cost of an MMIO read CAUTION

Objective: observe that register reads are expensive. Setup: a QEMU guest with an emulated NVMe device or a dedicated test box. Procedure: use perf trace or bpftrace to time nvme show-regs (each register read is an MMIO load via the kernel/driver or via sysfs resource mapping, depending on version impl). Compare against the time to read a file of the same size from page cache.

Observations: record total time and count of register reads. Questions: what is the per-read cost? Is it consistent?

Solution

Expect on the order of a microsecond per read on real hardware and very different numbers under emulation (where each access traps to the hypervisor). The lesson is the ratio: a fast path must avoid MMIO reads. NVMe's submission fast path performs no register reads.

Extension: explain why a virtualised guest's doorbell writes are expensive too, and how “shadow doorbell” buffers (Doorbell Buffer Config admin command) address that version.

Objective: localise a failure using only text evidence. Setup: the synthetic log below.

1A.13 Interview questions

Interview questions

  1. Beginner What is the difference between a CPU register and a device register?
    Model answer

    A CPU register is internal storage used by instructions and invisible outside the core. A device register is a control/status location in a device, reached through an address (MMIO or config space), and may have side effects when read or written.

  2. Beginner What does “memory-mapped I/O” mean?
    Model answer

    Device registers are assigned addresses in the physical address map, so ordinary load/store instructions to those addresses reach the device instead of DRAM.

  3. Beginner Why is memory called volatile?
    Model answer

    DRAM loses its contents without power; storage such as NAND retains them.

  4. Beginner What is a cache line?
    Model answer

    The unit in which caches hold and transfer memory, commonly 64 bytes; coherence is tracked per line.

  5. Beginner What is the role of the root complex?
    Model answer

    It bridges the CPU/memory system to the PCIe hierarchy: turns CPU accesses into TLPs and device memory requests into memory accesses.

  6. Intermediate Why is a register read more expensive than a write?
    Model answer

    Reads are non-posted: the core must wait for the round trip and completion. Writes are posted: the core continues once the store is handed off.

  7. Intermediate What is a read “flush” of posted writes?
    Model answer

    Because a read's completion cannot pass earlier posted writes in the same path, reading a device register after writes guarantees those writes have reached the device.

  8. Intermediate What does Bus Master Enable control?
    Model answer

    Whether the function may issue memory and I/O requests upstream — i.e. do DMA and send MSI/MSI-X.

  9. Intermediate Why must a barrier precede the doorbell write?
    Model answer

    So the SQE stores are visible in memory before the device is told to fetch; otherwise the device might read stale bytes.

  10. Intermediate Why is write-combining unsafe for control registers?
    Model answer

    WC can merge, reorder or delay stores, breaking side-effect semantics and ordering.

  11. Advanced How does a 64-bit register read appear on PCIe, and what risk exists?
    Model answer

    Either one 2-DW MRd or two 1-DW MRds depending on CPU/driver; split reads can tear if the register changes between them.

  12. Advanced What does an all-ones read tell you?
    Model answer

    Usually that the read failed (UR, CA, completion timeout, link down) and the platform returned all ones; check Vendor ID in config space to confirm.

  13. Advanced How do NUMA effects show up in NVMe performance?
    Model answer

    Higher latency and lower IOPS when queues, buffers or interrupt targets are on a different socket from the device's root port.

  14. Advanced What does CAP.TO govern?
    Model answer

    Worst-case time, in 500 ms units, for CSTS.RDY to transition after CC.EN changes.

  15. Advanced Why does NVMe use per-core queues?
    Model answer

    To avoid cross-core locking and cache-line bouncing on a shared queue, allowing linear scaling with cores.

  16. Senior A customer reports 50 µs latency spikes in the driver's interrupt handler. How do you proceed?
    Model answer

    Profile which instructions stall; look for MMIO reads in the handler; correlate with link power states and with analyzer capture of slow completions; test with ASPM disabled and with polling mode; form a hypothesis per evidence.

  17. Senior How would you prove a missing barrier caused corruption?
    Model answer

    Capture the fetched SQE bytes on an analyzer and compare with the driver's intended SQE logged after the fact; reproduce under stress on a weakly ordered platform; show the fix eliminates mismatches over a statistically meaningful run.

  18. Senior How would you design register-access validation for a new controller?
    Model answer

    Reset values, RO/RW/RW1C behaviour, access widths and alignment, reserved bits, side effects, behaviour during reset and when disabled, concurrency with DMA, error responses for unimplemented offsets.

  19. Senior What is the risk in a driver timeout shorter than CAP.TO?
    Model answer

    Spuriously declaring a healthy but slow controller dead, especially after unsafe shutdowns when initialisation is longer.

  20. Senior How do you tell a host hang from a device hang?
    Model answer

    Host hang: cores stuck (watchdog, NMI backtraces), possibly in an MMIO read waiting for a completion; device hang: link alive, device responds to config reads but not to commands. Analyzer or root-port completion-timeout logs discriminate.
