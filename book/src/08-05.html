PART XXXV

AI + NVMe Protocol Analysis

Large language models (LLMs) can read a page of normalized events and write a fluent paragraph about them in seconds. Fluency is exactly the danger: an LLM can also write a fluent paragraph about a packet that never existed, a status code that was never returned, or a specification requirement that is not in any specification. This Part teaches a responsible architecture — raw trace, deterministic parser, normalized events, and only then LLM reasoning — with retrieval, specification grounding, mandatory evidence citation, an explicit confidence model, a validator that rejects unsupported claims, and an evaluation discipline.

35 AI-Assisted Trace Analysis Without Hallucination

📘 Baseline and source notes

No NVM Express or PCI-SIG specification governs the use of AI in analysis; this chapter is engineering practice. All protocol facts it relies on come from the deterministic layer (Chapter 34) and from your own specification notes (Chapter 30). LLM capabilities, context sizes and behaviour vary by model and version impl version. Statements about how LLMs behave in general are labelled uncertain where they are empirical observations rather than guarantees.

35.1 Why this chapter exists

Teams are already pasting traces into chat assistants. Some get useful summaries; some get confident fiction. The difference is architecture and discipline, not luck. An LLM is a reasoning and writing aid that operates on text; it is not a packet decoder, not a clock, and not a specification. Used behind a deterministic parser and in front of a validator, it can speed up triage, report writing, hypothesis generation and teaching. Used in place of them, it produces unfalsifiable stories.

  • Beginner: state what an LLM must never do in trace analysis, and why the parser comes first.
  • Intermediate: design retrieval and grounding from your own specification notes, with chunk ids and revisions.
  • Advanced: implement a validator that checks citations, field values, spec references and confidence rules.
  • Senior: define a confidence model and an evaluation set; decide where human review is mandatory.
  • Trace-analysis: turn normalized events into a cited, structured finding.
  • Debugging: recognise hallucination, overconfidence, anchoring and prompt injection in AI output.
  • Validation: measure an AI-assisted pipeline with mutation tests and known-cause corpora.

Prerequisites: Chapter 34 (event model, summarizer); Projects 11–12.

🧒 Kid analogy — the clever helper who must show the page

Your class has a very clever helper who has read millions of books and talks beautifully. But the teacher has one rule: every time the helper says something, it must point to the exact line in the class notebook that proves it. If it cannot point, it must say "I don't know". The helper is not allowed to write in the notebook itself — only the class's careful note-taker writes there.

🌍 Engineering analogy — the expert witness

A court lets an expert witness interpret evidence, but the evidence itself is collected and logged by investigators with a chain of custody. The expert must cite exhibits, can be cross-examined, and is not allowed to introduce new "exhibits" from memory.

🧩 Where the analogy breaks

An expert witness knows when they are guessing; an LLM's fluent text does not reliably signal its own uncertainty uncertain. That is why uncertainty must be enforced structurally (labels, citations, validator) rather than trusted from the prose.

35.5 LLM guardrails

⚠️ The LLM must never invent
  • packets — no TLP, DLLP, ordered set, SQE or CQE that is not in the event store;
  • timestamps — no times, gaps or latencies not computed by the deterministic layer;
  • fields — no field value (tag, address, status, CID, opcode) that differs from the parsed value;
  • register values — no CAP/CC/CSTS/config-space value not captured;
  • specification requirements — no "the spec requires…" without a retrieved passage id; no section numbers;
  • root causes — no root cause without supporting evidence ids and a falsifier.

Direction of reasoning: EVIDENCE → CLAIM, never CLAIM → imagined evidence.

  1. Deterministic first: the LLM only sees normalized events and anomalies, never raw hex to decode.
  2. Structured output: JSON with claim, evidence ids, spec ids, confidence, falsifier, unknowns — prose is generated from validated JSON, not the reverse.
  3. Mandatory citations validated against the stores; unknown ids → reject.
  4. Field-value echo check: any quoted value must equal the stored value.
  5. Closed-book for normative claims: requirements may come only from retrieved passages; otherwise the claim must be labelled as general knowledge and confidence capped at LOW.
  6. Abstention is a valid answer: "UNKNOWN — evidence needed: …" is rewarded, not penalised, in evaluation.
  7. Data is not instructions: payload text, file names and log strings are quoted as data; instructions inside them are ignored (prompt-injection defence).
  8. Confidentiality: follow data-handling rules; strip payloads; do not send confidential captures or licensed specification text to services not approved for them.
  9. Reproducibility: log model id/version, prompt, context ids and output for every run; pin versions for regression.
  10. Human accountability: a named engineer signs every report; AI output is marked as assisted.
  11. Evaluation before trust: measured on a known-cause corpus with injected-hallucination tests (§35.10).
  12. Version awareness: passages carry document + revision; findings state which revision they rely on.

35.6 The validator (executable)

The validator below is model-agnostic: it checks any JSON finding against the deterministic event store and the set of retrieved passage ids. It is the component that makes the architecture safe; it is used in Project 12 (Chapter 33B).

#!/usr/bin/env python3
"""Part XXXV / Project 12 component - guardrail validator for LLM-written trace findings
(executable, stdlib only; the LLM call itself is NOT included - any model's JSON output
is checked the same way). Policy: EVIDENCE -> CLAIM. A finding is rejected if it cites
an event id that does not exist, quotes a field value that differs from the parsed
event, claims CONFIRMED without direct evidence, or cites a spec passage that was not
in the retrieved context."""
EVENTS = {   # produced by the deterministic parser (Project 10), SYNTHETIC
    "ev15": {"type": "Cpl", "status": "UR", "tag": 9, "req_id": "03:00.0"},
    "ev13": {"type": "MRd", "tag": 9, "addr": "0x2A500000", "len_dw": 32},
    "ev17": {"type": "MRd", "tag": 10, "addr": "0x2A600080"},
}
RETRIEVED_SPEC_CHUNKS = {"pcie-cpl-status", "nvme-prp-rules"}   # ids handed to the model
LEVELS = ["UNKNOWN", "LOW", "MEDIUM", "HIGH", "CONFIRMED"]

def check(finding, events=EVENTS, retrieved=RETRIEVED_SPEC_CHUNKS):
    errs = []
    for ref in finding.get("evidence", []):
        ev = events.get(ref["event"])
        if ev is None:
            errs.append(f"cites non-existent event {ref['event']}"); continue
        for field, val in ref.get("fields", {}).items():
            if str(ev.get(field)) != str(val):
                errs.append(f"{ref['event']}.{field}: claims {val!r}, parser says {ev.get(field)!r}")
    for s in finding.get("spec_refs", []):
        if s not in retrieved:
            errs.append(f"spec ref {s!r} not in retrieved context (possible fabrication)")
    lvl = finding.get("confidence", "UNKNOWN")
    if lvl not in LEVELS:
        errs.append(f"unknown confidence label {lvl!r}")
    if lvl == "CONFIRMED" and not finding.get("evidence"):
        errs.append("CONFIRMED with no evidence")
    if lvl in ("HIGH", "CONFIRMED") and not finding.get("falsifier"):
        errs.append("high confidence but no falsification test stated")
    return errs

if __name__ == "__main__":
    good = {"claim": "MRd tag 9 to 0x2A500000 was rejected with UR", "confidence": "CONFIRMED",
            "evidence": [{"event": "ev13", "fields": {"addr": "0x2A500000"}},
                         {"event": "ev15", "fields": {"status": "UR", "tag": 9}}],
            "spec_refs": ["pcie-cpl-status"], "falsifier": "ev15 tag/requester do not match ev13"}
    bad = {"claim": "Firmware bug caused CA on tag 9", "confidence": "HIGH",
           "evidence": [{"event": "ev15", "fields": {"status": "CA"}}, {"event": "ev99"}],
           "spec_refs": ["nvme-base-sec-9.9.9"]}
    for name, f in (("good", good), ("bad", bad)):
        e = check(f)
        print(f"{name}: {'ACCEPT' if not e else 'REJECT'}")
        for x in e: print("   -", x)
good: ACCEPT
bad: REJECT
   - ev15.status: claims 'CA', parser says 'UR'
   - cites non-existent event ev99
   - spec ref 'nvme-base-sec-9.9.9' not in retrieved context (possible fabrication)
   - high confidence but no falsification test stated

The "bad" finding illustrates four typical hallucinations at once: a status value contradicting the parser (CA vs UR), a citation to an event that does not exist, a specification reference that was never retrieved (with an invented section-like id), and high confidence without a falsification test.

35.7 The confidence model

LevelCriteriaExampleAllowed wording
CONFIRMEDDirectly observed in deterministic evidence, or reproduced and verified by a disambiguating experiment"MRd tag 9 was completed with UR" (events ev13, ev15)"Observed:", "Reproduced:"
HIGHMultiple independent evidence items support it; plausible alternatives eliminated by evidence; falsifier stated and not triggered"Invalid DMA address" after IOMMU fault log and PRP contents both match"Evidence strongly supports…"
MEDIUMSupported by evidence but at least one plausible alternative remains"Invalid DMA address" from the UR alone"Evidence supports…; alternative Y not excluded because…"
LOWConsistent with evidence but weakly supported; or based on general knowledge without retrieved source"Possibly a firmware race""Consistent with…; insufficient evidence"
UNKNOWNEvidence insufficient to rankRoot cause of a hang with no capture"Unknown; to decide we need…"
📌 Confidence is not probability

These levels are ordinal labels attached by defined criteria. They are not probabilities unless you have formally calculated them — for example from a calibrated model over a corpus where you measured how often HIGH findings were right. Writing "90% likely" without such a calculation is a fabricated number. If you want probabilities, measure calibration: across past cases, what fraction of HIGH findings were later confirmed?

🧪 Lab 35.1 — Write the report for a broken synthetic trace SAFE

Objective: produce the full §35.8 report, by hand or with an AI-assisted pipeline protected by the validator. Input (synthetic):

Questions: What is the first abnormal event? What should have happened? Which layer owns the behaviour? What are the hypotheses and what separates them?

Solution and grading rubric

Expected reasoning. ev1 writes SQ2 tail (1000h + 2×2×4 = 1010h) = 5, so one new entry at slot 4 (address 1F200000 + 4×64 = 1F200100 — matches ev2). Commands complete with successful CQEs (ev5, ev10) at CQ2 slots 4 and 5 (1F300000 + 4×16 = 1F300040; slot 5 = 1F300050). Expected after each CQE (if CQ2 has interrupts enabled with vector 2 and no coalescing): an MSI-X MWr to FEE00000. No MSI-X MWr appears after ev5. The first abnormal event is therefore the absence of the expected interrupt after ev5 — an anomaly defined by time window, anchored at ev5 (t=85.60 µs). The host timeout 30 s later is a consequence (symptom), not the cause. Layer: NVMe queue/interrupt path or host. Hypotheses: H1 interrupts suppressed by configuration (coalescing with a threshold/time not reached, IEN=0, vector masked) — MEDIUM; H2 controller failed to generate MSI-X — MEDIUM; H3 host-side interrupt handling fault (would show the MWr on the link) — LOW, because no MSI-X MWr is visible at all. Note: missing CQ head doorbell writes are consistent with the host never processing the CQEs. Separating evidence: Get Features Interrupt Coalescing and the CQ's creation parameters (IEN, IV); the MSI-X table entry and Pending Bit for vector 2 (pending bit set → masked); Linux /proc/interrupts counter for that vector. Regression test: per-queue interrupt delivery test across vectors with coalescing on/off.

Quiz

  1. Name the six things an LLM must never invent.

    Answer

    Packets, timestamps, fields, register values, specification requirements, root causes.

  2. Why is asking the model "are you sure?" not validation?

    Answer

    The same model re-generating text is not an independent check; validation must compare claims against the deterministic event store and retrieved sources.

  3. Is MEDIUM confidence the same as 50% probability?

    Answer

    No; it is an ordinal label with defined criteria. Probabilities require formal calculation and calibration data.

  4. In Lab 35.1, why is the host timeout not the first abnormal event?

    Answer

    It occurs 30 s later as a consequence; the earliest deviation is the missing interrupt after ev5.

  5. What is prompt injection in trace analysis?

    Answer

    Instructions embedded in data (payloads, logs, filenames) steering the model; defence: treat data as data, strip it, and validate outputs.

Interview questions

  1. Beginner Why should an LLM not decode raw TLP hex?
    Model answer

    Decoding must be exact and reproducible; a deterministic parser is tested and repeatable; language models can mis-split bits or produce plausible but wrong values.

  2. Beginner What does EVIDENCE → CLAIM mean?
    Model answer

    Start from observed events and derive claims that cite them; never start from a claim and imagine supporting evidence.

  3. Intermediate How do you ground an LLM in the current specification revision?
    Model answer

    Retrieve passages from your own revision-tagged notes or licensed documents into the context with ids; require citations; reject normative claims without them.

  4. Intermediate What checks does a validator perform?
    Model answer

    Existence of cited ids, equality of quoted fields, retrieved-only spec references, confidence rules (evidence and falsifier), schema conformance.

  5. Advanced How do you evaluate an AI-assisted analysis tool?
    Model answer

    Known-cause corpus, injected hallucinations, first-event agreement, root-cause top-k hit rate, calibration per confidence level, abstention on undecidable cases, version-pinned regressions.

  6. Advanced What are the confidentiality risks?
    Model answer

    Customer data in payloads, proprietary designs, licensed spec text; mitigate by stripping, approved services only, and access control on logs of prompts/outputs.

  7. Senior Your manager wants the AI to "find root causes automatically". Response?
    Model answer

    Propose an assisted workflow: deterministic detection, AI-drafted cited hypotheses, validator, human sign-off; show metrics; explain accountability and the cost of a confident wrong answer.

  8. Senior When would you forbid AI assistance entirely?
    Model answer

    When data cannot leave a controlled environment and no approved local model exists; when evaluation shows unacceptable error; for final safety/ship decisions.
