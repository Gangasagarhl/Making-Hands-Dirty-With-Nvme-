2026 NVMe 2.4 Updates

On August 4, 2026, NVM Express, Inc. announced the NVMe 2.4 specification set. This part is the course’s modern-update section. It is deliberately written as a reading and verification guide, not as a feature encyclopedia: for each highlighted capability it tells you what problem it addresses, which documents to open, what a validation engineer should look for, and — equally important — what you cannot conclude from a press release. Field layouts, opcodes and status codes of new 2.4 features are intentionally not reproduced here; you must read them in the normative text.

20.1 NVMe 2.4: What Changed in 2026, and How to Reason About It

📘 Specification baseline

SPECIFICATION BASELINE: NVMe 2.4 specification set. DOCUMENTS (per course brief): NVM Express Base Specification 2.4; NVM Command Set 1.3; Zoned Namespace Command Set 1.5; Key Value Command Set 1.4; Subsystem Local Memory Command Set 1.3; Computational Programs Command Set 1.3; NVMe over PCIe Transport 1.4; NVMe over RDMA Transport 1.3; NVMe over TCP Transport 1.3; NVMe Management Interface 2.2; NVMe Boot 1.4. SOURCE: NVM Express press release of August 4, 2026 (nvmexpress.org, News / Press Releases) and the specifications library at nvmexpress.org/specifications. version — individual sub-specification revision numbers are taken from the course brief; confirm each on nvmexpress.org before citing them in a report.

📭 Source notes — read this first
  • Official source: NVM Express announcement dated August 4, 2026; nvmexpress.org/specifications (each specification’s PDF and its revision history / list of incorporated ratified Technical Proposals (TPs) and Engineering Change Notices (ECNs)).
  • What the announcement establishes: that a 2.4 set was released; that it emphasises security, manageability, sustainability and support for AI, cloud, enterprise and client storage; and that it highlights Post-Quantum Cryptography, PCIe Exported NVM Subsystem Migration, Voltage Monitoring, Rate Limiting and Restore Manufacturing Default Settings.
  • What it does not establish: command opcodes, data structure layouts, log identifiers, feature identifiers, status codes, mandatory/optional status, which controller types must support a feature, or the exact algorithms used. None of these are stated in this course. Every one must be read in the normative specification.
  • Accessed/verified: the course baseline was fixed in August 2026. If you are reading this later, check for 2.4 errata/ECNs and later revisions.

20.1.1 Why this chapter exists

Every year, engineers receive a press release, skim five bullet points, and then — months later — confidently describe “how feature X works” in a design review, based on a guess. This chapter trains the opposite habit. You will learn a repeatable method for absorbing a new revision: read the announcement for intent, read the revision history for scope, read the normative sections for behaviour, then decide how it affects your product, your tests and your traces.

  • Beginner: name the five highlighted 2.4 capabilities and explain each one’s purpose in one sentence.
  • Intermediate: identify which specification documents you must open to study each capability.
  • Advanced: produce a “what is verified / what must be checked” sheet for each capability.
  • Senior: assess impact on a product roadmap, test plan and interoperability matrix without over-claiming.
  • Trace analysis: predict which capabilities can plausibly appear in a PCIe or NVMe command trace, and which have no necessary wire signature.
  • Debugging: recognise when a field anomaly may stem from a host and device implementing different revisions.
  • Validation: design validation thought experiments that do not depend on invented details.

Prerequisites: SR-IOV and NVMe virtualization (Ch 56), health monitoring (Ch 57), NVMe-MI (Ch 63), NVMe/TCP (Ch 66), and the spec-reading discipline of shall / should / may.

🧒 Kid story — the new rulebook for the football league

Every summer the football league publishes a new rulebook. The newspaper headline says: “New rules on safer helmets, team transfers, checking the stadium lights, limiting how fast players may run onto the pitch, and a reset button for the scoreboard.” A smart coach does not change tactics from the headline. She gets the rulebook, finds the exact pages, reads what is required and what is allowed, checks which rules apply to her league division, and only then trains the team.

🧩 Where the analogy breaks

A sports rulebook applies to everyone at once. NVMe features are mostly optional and are advertised by each device through capability fields, so two “NVMe 2.4” devices may support completely different subsets. A controller reporting a 2.4 version value is not a promise that it implements any particular new feature. Also, a single feature may be split across several documents (Base, a transport, NVMe-MI).

20.1.3 The method — twelve questions per feature

For every new capability we answer the same twelve questions. Where the honest answer is “read the spec”, we say so and tell you exactly what to look for.

  1. What existed before?
  2. What changed?
  3. Why was it needed?
  4. What problem does it solve?
  5. Which specification contains it?
  6. Which revision introduced or updated it?
  7. Is it mandatory or optional?
  8. What hardware/software is affected?
  9. How could it appear in traces?
  10. How would a validation engineer test it?
  11. What could go wrong?
  12. Why should a senior engineer care?

20.1.4 Post-Quantum Cryptography (PQC)

#QuestionAnswer (with evidence label)
1What existed before?NVMe already had security mechanisms that depend on public-key cryptography in some form: for example in-band authentication for fabrics (DH-HMAC-CHAP, which uses Diffie-Hellman groups), TLS for NVMe/TCP, and device security protocols reached through Security Send/Receive. verified that these mechanisms exist in recent revisions; derived that classical public-key algorithms are among their building blocks.
2What changed?The 2.4 announcement highlights Post-Quantum Cryptography. verified (announcement). Which mechanisms gained PQC options, and with which algorithms, must be read in the specification. uncertain
3Why was it needed?A sufficiently large quantum computer would break today’s widely used public-key schemes (RSA, elliptic-curve and finite-field Diffie-Hellman). Data recorded now could be decrypted later (“harvest now, decrypt later”), and storage devices have long service lives. NIST published its first PQC standards (FIPS 203 ML-KEM, FIPS 204 ML-DSA, FIPS 205 SLH-DSA) in August 2024. verified (NIST).
4What problem does it solve?Lets NVMe security mechanisms remain trustworthy against future quantum-capable adversaries; supports organisations with PQC migration mandates. derived
5Which specification?Open the NVMe Base Specification 2.4 first (security and authentication sections) and the NVMe over TCP Transport 1.3 (TLS-related content). Check NVMe-MI 2.2 if management-path security is in scope. Confirm against the revision history — do not assume which documents changed. uncertain
6Which revision?Highlighted with the 2.4 set (Aug 4 2026). Whether earlier TPs laid groundwork: check the revision history. version
7Mandatory or optional?Not stated in the announcement. Most new NVMe capabilities are optional and advertised by capability bits, but you must read the requirement language. uncertain
8Affected hardware/softwareController security firmware and crypto engines; host authentication stacks (e.g. Linux nvme-auth, nvme-cli, TLS libraries/keyrings), fabric targets, key-management systems. derived
9Trace appearanceNo necessary PCIe-level signature: PQC changes the content of security exchanges, not TLP types. Over fabrics, authentication/TLS handshakes may carry larger messages (PQC keys and signatures are generally larger than elliptic-curve ones — verified property of the NIST algorithms). Exact message formats: read the spec. Do not fabricate a trace.
10ValidationThought experiments: negotiate PQC vs classical between mixed-capability host/target; verify fallback policy matches the spec’s rules; measure handshake time and message sizes; negative tests with corrupted signatures; interop matrix across host stacks.
11What could go wrong?Downgrade to classical algorithms when policy forbids it; buffer sizes too small for larger keys; handshake timeouts tuned for classical crypto; interoperability gaps between early implementations. derived
12Why care (senior)?Crypto agility becomes a product requirement with a long tail: devices shipped in 2026 may still be in service when PQC is mandatory. Architecture must allow algorithm updates via firmware without breaking interop.

20.1.5 PCIe Exported NVM Subsystem Migration

#QuestionAnswer
1BeforeVirtualised hosts expose NVMe to guests through SR-IOV VFs (Ch 56) or software emulation. Direct-assigned devices are hard to live-migrate because state lives in the device. Recent NVMe revisions added infrastructure aimed at live migration of controllers version — identify which revision and which mechanisms in the revision history rather than relying on memory.
2What changedThe 2.4 announcement highlights “PCIe Exported NVM Subsystem Migration”. verified (name). Its mechanics are not described here. uncertain
3–4Why / problemCloud operators need to move running workloads (maintenance, load balancing) without stopping I/O for long, even when storage is presented over PCIe. The feature name indicates migration of an NVM subsystem that is exported over PCIe. derived from the name; confirm the definition of “exported NVM subsystem” in Base 2.4.
5SpecificationNVMe Base 2.4 (architecture, admin commands, data structures) and possibly NVMe over PCIe Transport 1.4 (PCIe-specific behaviour). Verify both. uncertain
6–7Revision / mandatoryHighlighted in 2.4; requirement level must be read. uncertain
8AffectedControllers supporting virtualization, hypervisors (VFIO-style passthrough, migration drivers), orchestration software, possibly DPUs/smart NICs that export storage. derived
9TracesAt NVMe command level, migration control would appear as admin commands and their data transfers on the managing function. At PCIe level, any state transfer is ordinary MRd/MWr traffic; there is no new TLP type to look for. A guest-visible pause may show as a gap in the guest’s I/O and a resumption on a different physical path. Do not invent command names.
10ValidationThought experiments: migrate under QD 128 mixed I/O; verify no lost, duplicated or reordered-in-violation completions; verify outstanding commands’ fate per spec; verify namespaces, reservations and AEN state after migration; abort migration mid-way; power loss during migration.
11What could go wrongLost in-flight commands; stale doorbell values; interrupt vector mismatch after resume; dirty-page tracking misses DMA writes; security boundary violations between tenants. derived
12SeniorMigration features move the hardest correctness problems (in-flight state, ordering, idempotency) into the boundary between hypervisor and device. Your test plan must cover the protocol’s failure states, not just the happy path.

20.1.6 Voltage Monitoring

#QuestionAnswer
1BeforeNVMe exposes temperatures (Composite Temperature, sensors), power states, and in recent revisions additional power-related reporting; supply voltage visibility typically came from platform/BMC sensors or vendor-specific logs. derived / impl
2What changedThe 2.4 announcement highlights Voltage Monitoring. verified (name). What is measured, granularity, units and reporting path: read the spec. uncertain
3–4Why / problemSupply-voltage excursions cause brown-out resets, unsafe shutdowns and latent reliability issues; correlating device events with voltage requires device-side visibility. Supports manageability and fleet reliability. derived
5SpecificationBase 2.4 (log pages/features/health reporting) and NVMe-MI 2.2 (out-of-band monitoring). Verify where it is defined and whether both paths expose it. uncertain
6–7Revision / mandatoryHighlighted in 2.4; requirement level must be read.
8AffectedController firmware and sensing hardware; host monitoring tools (nvme-cli plugins, telemetry pipelines); BMC firmware.
9TracesIf read via an admin command, it looks like any Get Log Page / Get Features exchange (Ch 57); out-of-band it appears as NVMe-MI messages over MCTP. No PCIe physical-layer signature is implied — the feature reports voltage, it does not change electrical behaviour.
10ValidationThought experiment: vary supply voltage with a programmable lab supply within the device’s rated range; check reported values track the reference meter within the device’s stated accuracy; check any threshold/event behaviour defined in the spec; compare in-band vs out-of-band values. EXPERT — voltage margining can damage hardware.
11What could go wrongUnit or scaling errors in host parsers; stale values; disagreement between BMC sensors and device reports due to measurement point differences. derived
12SeniorGives fleet teams a new correlation axis for “unexplained” resets and Unsafe Shutdown increments — if, and only if, sampling and reporting semantics are understood.

20.1.7 Rate Limiting

#QuestionAnswer
1BeforeNVMe offered building blocks for performance isolation (NVM Sets, Endurance Groups, I/O determinism, arbitration settings) but multi-tenant QoS was largely implementation-specific or host-enforced (e.g. Linux cgroups io controllers). derived
2What changedThe 2.4 announcement highlights Rate Limiting. verified (name). What is limited (commands, bandwidth, something else), at what scope (controller, namespace, host, other), and how limits are configured: read the spec. uncertain
3–4Why / problemNoisy neighbours in shared SSDs (see the SR-IOV noisy-neighbour trace in Ch 56) and predictable service levels for cloud and AI workloads. derived
5–7Spec / revision / mandatoryExpect Base 2.4; verify whether command-set or transport documents are involved; requirement level per spec.
8AffectedController schedulers; hypervisors/orchestrators that set limits; host drivers that must react to throttled behaviour.
9TracesConfiguration would appear as admin commands. Enforcement would appear as timing — longer command latency, spaced completions — not as a new packet type. A trace alone cannot distinguish rate limiting from thermal throttling or garbage collection; you need configuration state and device reporting.
10ValidationThought experiment: configure a limit, drive load above it, measure achieved rate and latency distribution; verify other tenants are unaffected; change limit under load; verify persistence across resets per spec.
11What could go wrongHost timeouts triggered by intentional throttling; unfairness at small time scales; interactions with host-side QoS producing double throttling. derived
12SeniorStandardised QoS changes how latency anomalies must be triaged: “the device is slow” may be policy, not fault. Make limit state part of every performance bug report.

20.1.8 Restore Manufacturing Default Settings

#QuestionAnswer
1BeforeConfiguration could be changed through many features (Set Features with Save, namespace management, power and thermal settings, MI configuration), while Sanitize (84h) and Format NVM (80h) address user data. Returning a repurposed drive to a known configuration often required vendor tools. derived
2What changedThe 2.4 announcement highlights Restore Manufacturing Default Settings. verified (name). Which settings are restored, whether namespaces or data are affected, and how it interacts with security state: read the spec. uncertain
3–4Why / problemDevice reuse and redeployment (sustainability, circular economy), consistent baselines for testing and support, recovery from misconfiguration. derived (the announcement emphasises sustainability).
5–7Spec / revision / mandatoryExpect Base 2.4; check NVMe-MI 2.2 for out-of-band invocation. Requirement level per spec.
8AffectedController firmware; provisioning and decommissioning tools; data-centre asset workflows.
9TracesInvocation appears as a command exchange; effects appear afterwards as changed Identify/Get Features values and possibly resets. No PCIe signature beyond ordinary traffic and any reset the spec requires.
10ValidationThought experiment: change every saveable setting; invoke the restore; verify each setting against documented defaults; verify user data handling exactly as specified (do not assume erase); verify behaviour with security locked; power loss during restore.
11What could go wrongOperators assuming it sanitises data (or that it doesn’t); host caches of feature values becoming stale; restoring settings that break the current platform (e.g. power limits). derived
12SeniorAny “reset to defaults” is a data-governance question. Write decommissioning procedures that cite exact spec behaviour, and keep Sanitize as the data-destruction step unless the spec says otherwise.

20.1.10 Reading section — “What changed from NVMe 2.3 to 2.4?”

🎯 Guided reading
  1. Collect sources. Download the 2.3 and 2.4 versions of the Base specification and every sub-specification you care about from nvmexpress.org/specifications. Save the August 4 2026 announcement.
  2. Read the revision histories first. Each specification lists changes and incorporated TPs/ECNs. Build a spreadsheet: document, TP/ECN identifier, title, one-line summary, sections touched.
  3. Map highlights to TPs. For each of the five highlighted features, find the TP(s) that introduced it and the sections they modified.
  4. Classify each change with the revision-diff method (Ch 20.3): added feature, changed field, changed behaviour, changed error handling, interoperability implication, validation requirement.
  5. Find requirement words. In each new section, highlight every “shall”, “should”, “may”. Note which controller types (I/O, administrative, discovery) each requirement applies to.
  6. Write the “cannot infer” list. For each feature, list three things you expected to find but did not — those are implementation-dependent and must not appear in your design docs as facts.

💡 Senior insight

The strongest engineers are not the ones who know the newest feature first; they are the ones who can say precisely which sentence of which revision supports their claim — and who label everything else as unknown. Make “source and revision” a mandatory field in your bug templates.

Quiz

  1. Name the five capabilities highlighted in the Aug 4 2026 announcement.

    Answer

    Post-Quantum Cryptography, PCIe Exported NVM Subsystem Migration, Voltage Monitoring, Rate Limiting, Restore Manufacturing Default Settings.

  2. A controller reports VS = 2.4. Does it support Rate Limiting?

    Answer

    Unknown. Check the capability fields defined by the specification for that feature.

  3. Should you expect a new TLP type for PCIe Exported NVM Subsystem Migration?

    Answer

    No basis for that. Control would use NVMe commands; any data movement is ordinary PCIe traffic. Confirm in the spec.

  4. Does Restore Manufacturing Default Settings erase user data?

    Answer

    Cannot be inferred from the name or the announcement. Read the normative description.

Interview questions

  1. Beginner What is post-quantum cryptography and why might storage care?
    Model answerPublic-key algorithms designed to resist quantum attacks; storage devices and their authentication/encryption key exchanges live for years, so long-lived data and trust anchors need protection against future attacks.
  2. Intermediate How would you find what changed between 2.3 and 2.4?
    Model answerRead each specification’s revision history and the incorporated TP/ECN list, map highlights to TPs, then read the affected normative sections and classify changes.
  3. Advanced How would you test a migration feature without knowing its internals in advance?
    Model answerDefine invariants independent of the mechanism (no lost/duplicated completions, consistent namespace and reservation state, bounded pause, security isolation), then read the spec to add mechanism-specific tests.
  4. Senior A product manager wants to claim “NVMe 2.4 compliant” on the datasheet. What do you say?
    Model answerSpecify which documents and revisions, which optional features are supported, and how compliance was tested (e.g. formal compliance programs); avoid implying support of all 2.4 features.
