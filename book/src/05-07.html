50 Power Management (Deep-Dive Module: Power Management)

50.1 Why this chapter exists

A laptop NVMe SSD may spend 99% of its life idle; a data-centre SSD may never be idle at all. Power management lets one design serve both — but it stacks three independent power-control systems on top of each other: NVMe power states (PS0…PSn, chosen by the host or autonomously via APST), PCIe link power states (ASPM L0s/L1 and L1 substates) and PCIe device power states (D0, D3hot, D3cold). Each saves power by adding wake-up latency, and each has failure modes: drives that never wake, links that throw errors on L1 exit, firmware that loses state in deep sleep. A large fraction of consumer NVMe bug reports on Linux are power-management quirks. This chapter makes the stack and its trade-offs explicit.

50.2 Learning objectives

  • Beginner: name the three power systems and their states.
  • Intermediate: read Power State Descriptors (MP, ENLAT, EXLAT, NOPS); configure/inspect Feature 02h and APST (0Ch); explain Linux nvme_core.default_ps_max_latency_us.
  • Advanced: explain ASPM L0s/L1, L1.1/L1.2, LTR, CLKREQ#, D3hot vs D3cold, PME and their latency budgets.
  • Senior: diagnose wake failures by separating power, link, controller and driver causes; tune for latency vs power.
  • Trace-analysis: recognise power transitions on the link (PM DLLPs, electrical idle, LTSSM L1 entry/exit, PME messages).
  • Debugging/validation: five failure patterns, power-state lab.

50.3 Kid story and analogy boundary

🧒 Kid analogy

The warehouse has three ways to save electricity. Inside, the manager can dim the lights in steps — bright, dim, very dim, off (NVMe power states); in the "off" steps nobody works, and it takes a while to switch lights back on. The road to your house can close one lane, or put up a barrier that takes a moment to lift (link L0s, L1). And the whole warehouse can go into night mode — doors locked except for the night bell (D3hot) — or be switched off at the mains (D3cold), which means a full morning start-up before anyone can help you.

🧩 Analogy boundary

Represents: three independent mechanisms, latency to wake. Hides: that the host and device must agree on some of these (ASPM must be enabled at both link ends, L1 substates need CLKREQ# and LTR), and that autonomous transitions (APST, ASPM) happen without host commands — there's no request on the wire you can point to. Misleading when: you assume a "dimmed" warehouse is also a closed road: NVMe PS and PCIe link states are independent; a drive in PS4 may have its link in L0 if ASPM is disabled, and a drive in PS0 may have its link in L1 between I/Os.

50.6.2 Host-controlled transitions — Feature 02h

Set Features 02h (Power Management) CDW11 bits 4:0 = PS, bits 7:5 = Workload Hint. Get Features 02h returns the current state. If the host submits I/O while the controller is in a non-operational state, the controller transitions to an operational state to process it (verified in substance — consult the Base spec "Power Management" section for exact rules).

50.6.3 APST — Feature 0Ch

Identify Controller APSTA bit indicates support. Set Features 0Ch: CDW11 bit 0 APSTE (enable) and a 256-byte data buffer of 32 entries (one per power state, 8 bytes each):

Entry bitsFieldMeaning
7:3ITPS — Idle Transition Power StateState to move to after the idle time, when in the state this entry describes
31:8ITPT — Idle Time Prior to TransitionMilliseconds of idle before transition (0 = disabled for this entry)

APST transitions go only to non-operational states. The device returns to the last operational state when work arrives, paying EXLAT.

50.6.4 Linux: nvme_core.default_ps_max_latency_us

Linux builds the APST table automatically: it considers non-operational states whose ENLAT + EXLAT ≤ the latency tolerance (nvme_core.default_ps_max_latency_us, commonly 100000 µs by default — version/kernel-dependent) and picks idle timeouts proportional to the state's latency (impl — the heuristic has changed across kernel versions). Setting the parameter to 0 disables APST. A per-device override exists via /sys/class/nvme/nvme0/power/pm_qos_latency_tolerance_us. Quirk tables (e.g. NVME_QUIRK_NO_DEEPEST_PS, NVME_QUIRK_NO_APST) disable states known to be broken on specific models.

sudo nvme id-ctrl /dev/nvme0 -H | sed -n '/^ps /,$p'      # power state descriptors
sudo nvme id-ctrl /dev/nvme0 | grep -E "npss|apsta"
sudo nvme get-feature /dev/nvme0 -f 0x02 -H              # current power state
sudo nvme get-feature /dev/nvme0 -f 0x0c -H              # APST table (read-only)
cat /sys/module/nvme_core/parameters/default_ps_max_latency_us
cat /sys/class/nvme/nvme0/power/pm_qos_latency_tolerance_us

ASPM is enabled per link end in Link Control bits 1:0 (01 L0s, 10 L1, 11 both). Endpoint Device Capabilities report acceptable L0s/L1 latencies; software should enable ASPM only where exit latencies along the path fit. Linux: /sys/module/pcie_aspm/parameters/policy (default, performance, powersave, powersupersave), boot option pcie_aspm=off, and per-link controls under /sys/bus/pci/devices/…/link/ on recent kernels (version).

🔧 Hardware

L1.2 requires the CLKREQ# sideband signal to be wired correctly on the board and supported at both ends, and correct T_POWER_ON / Common_Mode_Restore_Time programming. A board that advertises L1.2 but wires CLKREQ# incorrectly produces devices that "fall off the bus" after idle — the link cannot exit L1.2 cleanly and the root port logs Surprise Down or the device stops responding.

📘 Spec

verified PMCSR (Power Management Control/Status, in the PM capability, ID 01h) bits 1:0 PowerState (00 D0, 01 D1, 10 D2, 11 D3hot); bit 3 No_Soft_Reset; bit 8 PME_En; bit 15 PME_Status. 10 ms recovery time after D3hot → D0 before accessing the function. NVMe RTD3R / RTD3E in Identify Controller report the expected resume and entry latency for "runtime D3" (power removal) in µs — these are the NVMe-side numbers for D3cold-style power-off.

🏭 Implementation-dependent

How Linux handles system suspend for NVMe depends on platform: on many client platforms with s2idle, the driver keeps the controller in D0 and relies on an NVMe non-operational power state plus ASPM L1.2, instead of a full shutdown (because shutdown + power-off costs RTD3R on resume). Platform firmware (ACPI _DSD "StorageD3Enable" and similar) may request D3. The exact policy changes by kernel version and platform.

50.9 Latency trade-offs

added_latency_first_IO ≈ EXLAT(NVMe PS) + L1.x exit latency (+ D3hot→D0 10 ms + controller re-init, if applicable)
  • EXLAT — exit latency of the current NVMe non-operational state
  • L1.x exit — link exit latency (L1, L1.1 or L1.2)
  • D-state term — only if runtime PM put the function into D3

Example (synthetic): PS4 EXLAT 14 ms + L1.2 exit 70 µs → the first read after idle takes ~14 ms instead of ~80 µs. For a desktop, fine; for a database with a 5 ms SLO, unacceptable — disable deep APST states with default_ps_max_latency_us (e.g. 5000) on that system.

50.13 Labs

🧪 Lab 50.1 (beginner) — Inventory the power stack SAFE

Objective: record all three layers' configuration for your drive. Procedure: run the read-only commands in §50.6.4; sudo lspci -vvv -s <nvme> | grep -E "LnkCap|LnkCtl|L1SubCap|L1SubCtl1|PME|Status: D"; cat /sys/module/pcie_aspm/parameters/policy; cat /sys/bus/pci/devices/<bdf>/power/control. Observations: NPSS, PS table, APST enabled, ASPM enabled states, L1 substates enabled, D-state, runtime PM. Questions: what's the worst-case wake latency on your system?

Solution

Sum the EXLAT of the deepest APST-enabled state and the L1.x exit latency; add D3 resume if runtime PM puts the device in D3. Many laptops: ~10–20 ms; servers often have APST/ASPM disabled → microseconds.

🧪 Lab 50.2 (intermediate) — Measure first-I/O-after-idle latency CAUTION

Objective: observe APST exit latency in software. Setup: test system; read-only I/O. Procedure: run a 4 KiB O_DIRECT read, sleep N seconds (N = 0.05, 0.5, 2, 10), read again, record latency; repeat with nvme_core.default_ps_max_latency_us=0 (boot parameter; reboot required).

for s in 0.05 0.5 2 10; do
  sleep "$s"
  sudo fio --name=w --filename=/dev/nvme0n1 --rw=randread --bs=4k --direct=1 \
       --ioengine=psync --number_ios=1 --readonly --output-format=terse \
       | awk -F';' -v s="$s" '{print "idle", s, "s: clat_us", $16}'
done
⚠️ Safety

The fio job is read-only (--readonly). Changing kernel parameters affects power/battery and must be done on a test machine. The terse-output field index for completion latency varies by fio version — verify against fio --terse-version documentation before trusting the number.

Solution

Expect latency to jump once idle exceeds the APST ITPT for a non-operational state (e.g. ~100 ms → +EXLAT). With APST disabled, latency stays flat (but idle power rises).

Solution

(1) Controller (firmware) issue in leaving a non-operational power state — a power-management-triggered controller bug. (2) The absence of any device response after the doorbell at 10:05:00.000075 — phrased as "no upstream TLP visible in the captured interval" (capture covered both directions, link in L0, so coverage is good). (3) Link exited L1.2 to L0 promptly, DLLP Acks for the doorbell prove the device's data link layer received it; flow control continues — the link layer is alive. (4) The doorbell targeted SQ4's tail offset with a plausible value (verify), the admin Abort doorbell was also ignored (two different queues), and a controller reset fixed it without driver changes; CSTS shows no CFS — the controller wasn't "fatal", it was unresponsive. (5) Disable APST deep states (default_ps_max_latency_us below PS4's ENLAT+EXLAT) and run the same idle/wake pattern — failure should disappear; then re-enable only PS4 to confirm it's PS4-specific; check for firmware updates/errata. (6) Firmware update; until then, limit APST (kernel parameter or quirk). Confidence: medium-high.

Extension: rewrite the timeline so that the link fails to exit L1.2 instead, and list what evidence changes (Surprise Down, LTSSM Detect, CSTS all-ones).

50.14 Interview questions

Interview questions

  1. Beginner Name the three power-management layers of an NVMe SSD.
    Model answer

    NVMe power states, PCIe link states (ASPM), PCIe device states (D-states).

  2. Beginner What is APST?
    Model answer

    Autonomous Power State Transition: the controller moves to non-operational states after configured idle times.

  3. Beginner What does NOPS mean?
    Model answer

    Non-operational: I/O not processed in that state.

  4. Beginner D3hot vs D3cold?
    Model answer

    D3hot: powered, config accessible; D3cold: main power removed.

  5. Beginner What is ASPM?
    Model answer

    Hardware-autonomous link power saving (L0s, L1) during idle.

  6. Intermediate How does Linux choose APST states?
    Model answer

    Non-operational states with ENLAT+EXLAT ≤ default_ps_max_latency_us; timeouts by heuristic.

  7. Intermediate What's in a power state descriptor?
    Model answer

    MP, NOPS, ENLAT, EXLAT, relative throughput/latency, idle/active power.

  8. Intermediate What does L1.2 need on the board?
    Model answer

    CLKREQ# routing, LTR support, correct T_POWER_ON/common mode restore timing.

  9. Intermediate Why does a memory read to a D3hot device fail?
    Model answer

    In D3hot only configuration requests are supported; memory requests get UR.

  10. Intermediate What's RTD3R?
    Model answer

    RTD3 Resume Latency (Identify Controller): expected time to resume from power-off runtime D3.

  11. Advanced How do PM DLLPs negotiate L1?
    Model answer

    Downstream component requests (PM_Active_State_Request_L1), upstream acknowledges (PM_Request_Ack) after blocking new TLPs; both go to electrical idle.

  12. Advanced What's LTR used for?
    Model answer

    Device reports tolerable latency so platform can choose deeper states (e.g. L1.2 threshold, package C-states).

  13. Advanced Why might s2idle keep NVMe in D0?
    Model answer

    Faster resume and lower complexity using NVMe PS + L1.2 instead of full shutdown and RTD3R.

  14. Advanced How does the trace show an APST exit?
    Model answer

    Doorbell→fetch gap ≈ EXLAT; often preceded by link L1.x exit.

  15. Advanced Effect of No_Soft_Reset=0 on D3hot→D0?
    Model answer

    Function undergoes internal reset; config must be restored; NVMe sees a controller-level reset.

  16. Senior Tuning for a latency-SLO database server?
    Model answer

    Limit APST (latency budget), disable L1.2 or ASPM if exits exceed SLO, runtime PM off, measure p99.

  17. Senior How do you separate power vs link vs controller vs driver for a wake failure?
    Model answer

    Link state/AER/LTSSM for link; DLLP Acks + no device response for controller; config restore/timing for driver; ablation (APST off, ASPM off, runtime PM off) one at a time.

  18. Senior Why do Linux quirk tables exist for NVMe PS?
    Model answer

    Some firmware/boards fail in deep states; quirks disable them per model.

  19. Senior How does thermal throttling interact with power states?
    Model answer

    Device may lower performance autonomously (thermal management temperatures, HCTM) independent of host-selected PS; shows as throughput drop with SMART temperature evidence.

  20. Senior What evidence proves a device was in a deep state when it failed?
    Model answer

    Idle duration vs APST table, link L1.2 in trace, get-feature 02h before failure (if captured), doorbell→fetch gap patterns; otherwise only inferred — state confidence.

Child: dimming lights, closing road lanes, night mode and mains off. Junior: PS descriptors, APST table, ASPM states, D-states and the commands to inspect them. Senior: latency budget formula, platform/firmware/driver interactions, ablation-based diagnosis.

50A Capstone: One Incident, Every Layer

50A.1 Why this capstone exists

Parts XIII–XVI gave you the normal end-to-end sequence, interrupts, three floors of errors, resets and power states. Real incidents use all of them at once. This capstone presents a single synthetic incident and walks through a full investigation using the complete event model, timeline reconstruction, the first-abnormal-event rule and the negative-evidence rule.

50A.2 The incident (synthetic)

50A.3 Investigation

Step 1 — Build the expected timeline

Normal: I/O with clean link, rare correctable errors, no uncorrectable errors, link at Gen4 x4.

Step 2 — Observed timeline and first deviation

The background RxErr since 01:00 is a pre-existing deviation (low rate). The first sharp deviation is the burst of BadTLP/Replay Timeouts at 02:14:02.110. Working backwards: what preceded it? The BMC fan/temperature change at 02:13:50. Hypothesis: a marginal link (already showing RxErr) crossed a threshold with temperature change.

Step 3 — Layer assignment

EventLayerCause or symptom?
RxErr backgroundLink (PHY)Early cause indicator

Step 4 — Negative evidence check

"No media errors" is supported (SMART media_errors and error log show only transport status). "The drive's PHY is at fault" vs "the slot/riser/retimer is at fault" cannot be separated with this evidence — both ends of the link are candidates. Phrase it: "The evidence localises the fault to the physical link between root port 00:03.0 and device 02:00.0; it does not identify which side."

Step 5 — Disambiguating experiments

  • Swap the drive into a known-good slot and put a known-good drive in this slot (A/B swap): follow the errors.
  • Run at forced Gen3 to confirm margin-dependent behaviour (test window).
  • Check retimer/riser seating and firmware; check thermal profile.
  • If available, use lane margining (PCIe 4.0+ Lane Margining at the Receiver — version) to quantify eye margin per lane.

Step 6 — Conclusion

Do not RMA the drive on this evidence. The incident is a link-layer (signal integrity) fault, likely aggravated by temperature, that propagated up as PCIe completion timeouts, NVMe Data Transfer Errors, DPC containment and a controller reset. Confidence: medium-high for "link layer"; low for "which side". Next step: A/B swap.

💡 Senior insight

Notice how every layer told the truth from its own point of view: the NVMe controller correctly reported a Data Transfer Error, the driver correctly saw an unreachable controller, the AER driver correctly logged a completion timeout, and DPC correctly contained the link. The root cause lives where none of the error messages point directly — in the trend of corrected errors that nobody alerted on. Build monitoring on correctable-error rates.
