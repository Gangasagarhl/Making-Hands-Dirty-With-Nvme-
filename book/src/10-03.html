PART LV

Trace Correlation Exercise

Packet type alone never tells you what a packet means. This part starts with the six-line trace from the course brief, then gives a full synthetic multi-command trace with interleaved TLPs and DLLPs, and asks you to correlate every packet to its NVMe purpose — with an answer key that shows the evidence chain for each conclusion.

R7 Trace Correlation

R7.1 Why this chapter exists

Protocol analyzers show TLPs; engineers need NVMe meaning. The gap between them is filled by correlation: matching addresses against known structures (BARs, queue rings, PRP buffers, MSI-X table), matching tags between requests and completions, and matching CIDs between SQEs and CQEs. This chapter trains that skill and, equally important, the discipline of saying "unknown" when the evidence is missing.

  • Classify each TLP in a trace as doorbell, SQE fetch, PRP fetch, data DMA, CQE, interrupt, register access or unrelated.
  • State the evidence used for each classification and the evidence still missing.
  • Reconstruct per-command timelines from interleaved traffic of multiple commands.
  • Compute command latency components from timestamps.

Prerequisites: R1, R6, end-to-end flow (Part XIII), trace laboratory (Part XXIII).

🧒 Kid analogy

You watch a busy post office through a window. You see envelopes going in and out, but you can't read them. To know which envelope is a birthday card, you look at the address, the size, who sent it and when — and sometimes you just can't tell.

🧩 Where the analogy breaks

In a trace you can read the envelope contents (payload) — but the meaning of the contents depends on setup you may not have captured (which address is the CQ, which vector is which). Context capture is as important as packet capture.

3 — Why only B needs a PRP list

A spans exactly two 4 KiB pages: PRP1 + PRP2 (as a data pointer) suffice. B spans four pages: PRP1 covers page 0, so PRP2 must point to a list of the remaining three entries. The 24-byte list read confirms the controller fetched exactly three entries impl (some controllers read a whole list page).

4 — Row 10

No. It is the SSD answering the host's register read (row 7). Requester ID 0000h (host), Completer 0100h (SSD). It is a counterexample to "every CplD is DMA" and to "every completion belongs to a command".

5 — Completion order

B (submitted second, on SQ2) completes at 14.8 µs; A at 66.3 µs. Out-of-order completion across queues is normal; even within one queue it is allowed. A write can complete early when absorbed by a write cache impl; a read must wait for media (tR plus transfer).

6 — Latency arithmetic
  • A: doorbell t=0 → CQE t=66 300 ns ⇒ 66.3 µs device-side latency. Data transfer: 61 000 → 66 100 ns ≈ 5.1 µs for 8 KiB on the wire as seen here (the interval includes gaps; the link time for 8 KiB at ~7 GB/s effective would be ~1.2 µs derived, so the controller is pacing the transfer — e.g. from NAND buffers).
  • B: doorbell t=150 → CQE t=14 800 ns ⇒ 14.65 µs. Data fetch 2 600 → 9 300 ns ≈ 6.7 µs for 16 KiB. Fetch is round-trip bound: each MRd waits ~600–700 ns for its CplD; only 8 MRd per page in flight.
  • Host-side: MSI-X → CQ head doorbell 1.34 µs (B) and 1.54 µs (A) — ISR + completion processing time.
7 — SQHD consistency

Row 22 DW2 = 0002_0009h → SQID 2, SQHD 9: the controller has consumed SQ2 up to tail 9 — consistent with row 3. Row 27 DW2 = 0001_0004h → SQID 1, SQHD 4 — consistent with row 1. DW3 bit 16 (P) = 1 in both, matching expected phase 1.

8 — What cannot be concluded
  • Whether B's data reached NAND (write cache; durability unknown without FUA/Flush/VWC info).
  • Why the host read CSTS (row 7) — driver intent is not visible on the wire.
  • Whether the read data is correct — the trace shows bytes moved, not their correctness versus the stored data.
  • Which CPU handled each interrupt.
  • Anything about the other direction's Acks we did not list (the capture shows only some DLLPs).

Analysis

The first abnormal event is the UR completion at row 8 — but the first bad decision may be earlier: the PRP list entry 1_5000_7000h (row 5) is not mapped for the device in the IOMMU, or is wrong. Evidence chain: (1) row 7 address equals the second list entry; (2) row 8 UR from the root complex means the address was not accepted (IOMMU fault or unclaimed address impl); (3) the controller aborts the data transfer and reports a Data Transfer Error (Generic Command Status 04h) verified. Confidence: Strong evidence that the PRP entry was invalid for DMA; Likely an IOMMU mapping bug; to confirm, find the matching IOMMU fault message in the kernel log and the driver's mapping for that page.

🐞 Debugging connection

The first abnormal packet and the first wrong state are often different events. Here the wrong state (a bad list entry in memory) existed at row 5; the packet symptom appeared at row 8.

💡 Senior insight

Always capture enumeration and queue creation, or at least dump BARs, queue bases and the MSI-X table from the host before starting a mid-run capture. Correlation without context degrades every "confirmed" to "possible".

🧪 Lab R7.1 — Build a correlator SAFE

Objective: write a small program that ingests the trace table (CSV) plus setup context, and classifies each row.

ctx = { bar0: 0xFEA00000, dstrd: 0, ssd_rid: 0x0100,
        sq: {1: (0x12F402000, 64), 2: (0x12F406000, 64)},
        cq: {1: (0x12F404000, 64), 2: (0x12F408000, 64)},
        msix: {(0xFEE00000, 0x24): 1, (0xFEE02000, 0x25): 2} }
outstanding = {}               # (requester, tag) -> MRd row
def classify(r):
    if r.kind == "MWr" and r.dir == "down" and in_range(r.addr, ctx.bar0 + 0x1000, ctx.bar0 + 0x2000):
        idx = (r.addr - ctx.bar0 - 0x1000) // (4 << ctx.dstrd)
        return ("SQ%d tail doorbell" % (idx // 2)) if idx % 2 == 0 else ("CQ%d head doorbell" % (idx // 2))
    if r.kind == "MRd":
        outstanding[(r.req, r.tag)] = r
        for q,(base,n) in ctx.sq.items():
            if in_range(r.addr, base, base + 64*n): return "SQE fetch SQ%d slot %d" % (q, (r.addr-base)//64)
        return "DMA read (data or PRP list) - check PRP context"
    if r.kind in ("Cpl", "CplD"):
        req = outstanding.pop((r.req, r.tag), None)
        return "completion for row %s" % (req.row if req else "UNKNOWN - unexpected completion")
    if r.kind == "MWr" and r.dir == "up":
        if (r.addr, r.data) in ctx.msix: return "MSI-X vector %d" % ctx.msix[(r.addr, r.data)]
        for q,(base,n) in ctx.cq.items():
            if in_range(r.addr, base, base + 16*n): return "CQE CQ%d slot %d" % (q, (r.addr-base)//16)
        return "DMA write (read data) - check PRP context"
    return "other / link layer"

Questions: how does your correlator handle a CplD split into two (BC 512 then BC 256)? How should it treat an MRd whose tag is reused before its completion arrives?

Solution

Keep the outstanding entry until the completion with Byte Count equal to the remaining bytes arrives (BC counts remaining bytes, so the last completion has BC = its own length). A reused tag before completion is a protocol violation by the requester — flag it as an anomaly rather than overwriting the entry.

Extension: add PRP-awareness by decoding SQEs from CplD payloads and registering their PRP ranges.

Quiz

  1. Why do the read-data TLPs for A use 4-DW headers?

    Answer

    The target addresses are above 4 GiB (1_3A5C_xxxxh), requiring 64-bit addressing.

  2. What does BC 512 in the first CplD for a 512-byte MRd tell you?

    Answer

    512 bytes remain including this completion; since its payload is 256 B, another completion with BC 256 must follow.

Interview questions

  1. Senior An analyzer labels a TLP "NVMe Completion" but you see no CQ creation in your capture. What do you do?
    Model answer

    Treat the label as the tool's inference. Check the raw address against queue bases obtained from the host (driver debug output or a capture of queue creation). Until verified, downgrade the classification to "possible".

PART LVI

Evidence-Based Debugging

Every root-cause conclusion must carry a confidence label and must point to its evidence. This part defines the five confidence levels, the evidence hierarchy, the root-cause statement template, and walks through a complete investigation.

R8 Evidence-Based Debugging

R8.1 Why this chapter exists

Engineering organisations lose more time to confident wrong conclusions than to hard bugs. A conclusion with an honest "Likely" invites the next experiment; a wrong "Confirmed" shuts investigation down. This chapter standardises how certainty is expressed and earned.

  • Apply the labels Confirmed, Strong evidence, Likely, Possible, Unknown correctly.
  • Rank evidence by strength and independence.
  • Write root-cause statements that cite evidence and state what would falsify them.
  • Plan the cheapest experiment that raises confidence by one level.

Prerequisites: debugging methodology (Part XXVI), error handling (Part XV), R7.

🌍 Analogy

A court distinguishes "beyond reasonable doubt" from "balance of probabilities" and from "suspicion". Each verdict requires a different evidence standard, and the standard is stated openly.

🧩 Where the analogy breaks

In engineering you can usually re-run the crime: reproduce, instrument and experiment. Confidence should rise over time through experiments, not just through argument.

R8.3 Evidence hierarchy

  1. Direct protocol evidence captured at the right place: analyzer trace at the failing link, with context.
  2. Hardware-latched state: AER status and header log, CSTS, LnkSta, error logs read soon after the event.
  3. Controlled reproduction with on/off variable.
  4. Software logs: dmesg, tracepoints, driver debug messages (subject to timing and loss).
  5. Statistical correlation: fleet data, temperature/slot/firmware patterns.
  6. Expert intuition: hypothesis generator only — never evidence.
⚠️ Warning

Two pieces of evidence derived from the same source are not independent. A dmesg line and a dashboard alert both generated from the same AER interrupt count as one observation.

R8.4 The root-cause statement template

SYMPTOM:          what was observed, where, when, how often
LAYER (symptom):  physical | data link | transaction | NVMe | driver | block | app | media
FIRST BAD EVENT:  earliest observed deviation from expected behaviour (with evidence ref)
CAUSE:            mechanism, stated so it could be falsified
LAYER (cause):    ...
CONFIDENCE:       Confirmed | Strong evidence | Likely | Possible | Unknown
EVIDENCE:         numbered list, each with source + timestamp + what it shows
ALTERNATIVES:     other hypotheses + why they rank lower
FALSIFIER:        observation that would disprove the cause
NEXT EXPERIMENT:  cheapest step to raise confidence one level
SPEC REFERENCE:   document + revision (+ section title if verified), or "none needed"

R8.5 Worked investigation — intermittent I/O timeouts

Report: "nvme nvme0: I/O 123 QID 4 timeout, aborting" appears about once per day on one server; followed by a controller reset; workload resumes.

Notice the correlated "rising correctable errors" (step 2) was a red herring: true, but unrelated. Without step 5–6 the team might have replaced cables.

R8.6 Anti-patterns

  • Upgrade-as-diagnosis: "we updated firmware and it went away" — without a revert test, this is Likely at best (the trigger may simply be rarer).
  • Last-log fallacy: blaming the final error message; often a consequence (reset) of the first error.
  • Single-occurrence certainty: one capture is an anecdote.
  • Spec-as-evidence: "the spec requires the device to do X, so the device did X" — the spec states obligations, not observations.
💡 Senior insight

Separate the confidence in the trigger from the confidence in the mechanism. You can be Confirmed that disabling coalescing removes the symptom while only Likely about why. Both labels belong in the report.

🧪 Lab R8.1 — Label a real report SAFE

Objective: take a past bug from your own tracker (or the case above) and rewrite its conclusion with the template.

Checklist for a good answer

Every claim cites evidence; at least one alternative hypothesis is listed; a falsifier is specific (an observation, not "if it happens again"); the confidence label matches the hierarchy in R8.3.

Quiz

  1. You have an AER header log identifying the specific TLP that was rejected as Unsupported Request, but no reproduction. Label?

    Answer

    Strong evidence (for "this TLP was rejected at this port"); why it was sent remains Possible/Unknown until further evidence. Note that a Completion Timeout is not associated with a received TLP, so do not expect a header log for it — the evidence for timeouts comes from traces.

  2. Is "the vendor said it's a known firmware issue" evidence?

    Answer

    It is a hypothesis with some authority; raise confidence only when the vendor's described mechanism matches your observations and a fix passes an on/off test.

Interview questions

  1. Principal How do you stop a war-room converging on the wrong cause?
    Model answer

    Require confidence labels and evidence references on the whiteboard; keep an alternatives list alive; assign someone to try to falsify the leading hypothesis; prefer the cheapest discriminating experiment over debate.

PART LVII

Specification Safety

Never hallucinate a specification. This part teaches how to cite, how to separate normative text from interpretation, and how to handle revisions honestly.

R9 Specification Safety

R9.1 Why this chapter exists

Specifications are long, revised, and sometimes membership-restricted. It is tempting — for humans and for AI tools — to fill gaps with plausible text: an invented section number, a paraphrase presented as a quotation, a feature described as if it existed in an older revision. Each such fabrication can propagate into test plans and designs. This chapter defines the rules this book follows and that you should follow.

  • Cite specifications by document and revision, and by section only when verified.
  • Distinguish normative requirements, informative text, and interpretation.
  • Recognise version-dependent behaviour and say so.
  • Avoid claiming knowledge of proprietary documents not consulted.

Prerequisites: the specification-reading school (Part XXX).

🧒 Kid analogy

If you tell your friend "the rulebook says page 12 allows it", you had better have looked at page 12. Making up page numbers is how arguments — and games — go wrong.

🧩 Where the analogy breaks

Game rulebooks rarely change; specifications have revisions, errata, and Engineering Change Notices/Technical Proposals. "The rulebook" must always mean "which edition".

R9.2 The rules

  1. Consult the official document when exact normative behaviour matters.
  2. Cite document name + revision (+ section title/number only if you have it in front of you).
  3. Never invent quotations. Paraphrase and say "paraphrased".
  4. Never fabricate section numbers — section numbering changes between revisions (NVMe 2.0 reorganised the entire document set).
  5. Separate normative text ("shall", "shall not", "should", "may" carry defined meanings in the conventions sections of these specs) from informative notes and from your interpretation.
  6. State revision context for every feature introduced after 1.0.
  7. Do not pretend to have read a proprietary analyzer manual, a vendor datasheet under NDA, or a PCI-SIG member document you did not consult.
  8. Label implementation-dependent behaviour impl and unknowns uncertain.

R9.5 Reading normative language

NVMe and PCIe specifications define conventions for requirement keywords near their beginning. In both, "shall" denotes a mandatory requirement, "should" a recommendation, and "may" a permission verified. Optional features are discovered via capability fields (CAP, Identify, PCIe capability registers) — so a statement "the device supports X" must be checked against the reported capability, not assumed from the spec.

📭 What the spec does not say

Specifications rarely specify latency, internal firmware algorithms, NAND management, garbage-collection policy, or analyzer behaviour. Any statement about those is implementation-dependent by default.

🏭 Implementation-dependent

How a controller sizes SQE fetches, coalesces doorbells, orders data vs CQE writes within ordering rules, and allocates tags — all vendor choices.

R11.3 Narrative

An application asks for bytes. The filesystem translates "file, offset" into "device, LBA" — the last moment the request has any notion of a file. The block layer turns the bio into a request bound to the submitting CPU's hardware context, which in the NVMe driver corresponds to one SQ/CQ pair. The driver now speaks NVMe: it makes the buffer device-visible (an IOVA via the IOMMU), describes it with PRPs, fills a 64-byte SQE, and publishes it with a single tail-index write. That write is the only thing that crosses PCIe from host to device at submission time; the command itself stays in host memory until the controller pulls it across with a Memory Read — whose answer, a PCIe Completion with Data, is the moment the NVMe command first touches the link. The controller interprets the command, looks up its mapping table, wakes NAND dies, corrects bit errors, and moves the data using its own DMA engine, emitting Memory Writes towards host memory (for reads) or Memory Reads (for writes). When it has decided the outcome, it writes a 16-byte CQE whose phase bit announces "new", and then — ordered behind that write by PCIe's posted-write ordering — sends an MSI-X Memory Write that becomes a CPU interrupt. The driver reads the CQE, matches the CID, releases the CQ slot with a head-doorbell write, unmaps the buffer, and hands the status up. The application's read returns.

At no point is "the NVMe command" a packet; at no point is "the completion" a PCIe completion; at no point did the CPU copy the payload. If you can say why each of those three sentences is true, you hold the model.

🐞 Debugging connection

Place any symptom on the figure: an I/O timeout is "arrow 15 or 16 or 17 did not happen (or was not noticed)"; a Completion Timeout logged by the device is "arrow 11/13 MRd had no CplD"; a link down-train lives at arrow 10. Then use the evidence row for that arrow.

💡 Senior insight

The asymmetric paths explain most performance behaviour: submission is cheap (one posted write), the controller's pull of SQEs and write data is latency-sensitive (round trips), and completion is cheap again (posted writes). Optimisations target the round trips: CMB for SQEs, bigger MRRS, more tags, fewer PRP list fetches.
