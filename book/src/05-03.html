PART XIV

Interrupts

An NVMe controller can complete millions of commands per second across dozens of queues. Telling the host about those completions — quickly, to the right CPU, without drowning it — is the job of the interrupt architecture. This part follows the evolution from shared level-triggered wires (INTx) to Message Signalled Interrupts (MSI) to MSI-X, and then dissects MSI-X down to the bytes of its table and pending-bit array, the masking rules, the queue-to-vector mapping NVMe uses, and NVMe's interrupt coalescing feature. You will finish able to recognise an interrupt on a PCIe trace, explain why one is missing, and tune interrupt behaviour for latency or throughput.

42 Interrupt Architecture: INTx, MSI and MSI-X

42.1 Why this chapter exists

Every completed NVMe command must eventually reach software. Software can poll the CQ (burning CPU) or be interrupted. PCIe offers three interrupt mechanisms inherited from PCI history, each with very different scalability. NVMe allows all three — the NVMe over PCIe transport supports pin-based (INTx), single and multiple MSI, and MSI-X — but real high-performance systems use MSI-X almost exclusively. Understanding why requires knowing what each mechanism physically is.

42.2 Learning objectives

  • Describe INTx virtual wires, MSI and MSI-X and their PCIe representation (Assert/Deassert messages vs memory writes).
  • Explain why MSI-X suits NVMe's per-queue, per-CPU model.
  • Explain NVMe INTMS/INTMC and why they do not apply to MSI-X.
  • Identify interrupt TLPs in a trace.

Chapter 39's stage 15 (MSI-X in the end-to-end read); PCIe message TLPs and configuration space capabilities from earlier parts.

42.4 Story and analogy

🧒 Kid analogy

INTx is a single shared doorbell button for a whole apartment block: when it rings, the caretaker has to knock on every door to find who pressed it, and the bell keeps ringing until that person lets go. MSI is giving each flat a postcard with the caretaker's address printed on it — the flat drops the postcard in the post when it needs attention, and the postcard says which flat it is. MSI-X is giving each flat a whole book of differently addressed postcards — one for the plumber, one for the electrician, one for the caretaker — and a switch for each postcard to say "don't send this one right now".

🧩 Where the analogy breaks

INTx in PCIe is not a wire at all: it is emulated with Assert_INTx/Deassert_INTx message TLPs that the switch/root port aggregate into a virtual level. And MSI "postcards" are memory writes travelling the same posted path as data — which is precisely why they order correctly behind earlier data writes, something no physical wire could guarantee.

42.6 Why NVMe strongly benefits from MSI-X

  • One vector per CQ: Linux creates one I/O queue pair per CPU (or per CPU group) and one vector per CQ, each with affinity to that CPU. The completion is handled on the CPU that submitted the I/O — cache-hot, lock-free.
  • No source polling: the vector itself identifies the CQ; the ISR scans only one CQ.
  • Scale: NVMe allows up to 65,535 I/O queues; MSI caps at 32 vectors, MSI-X at 2048. Controllers commonly expose 32–256 vectors (impl).
  • Independent masking: a vector can be masked (e.g. while its CPU goes offline) without affecting others.
  • Ordering: the interrupt MWr follows the CQE MWr on the same posted path; when the interrupt arrives the CQE is in memory — no "flushing read" required (INTx needs one).
💡 Senior insight

When an NVMe drive gets fewer vectors than queues (e.g. MSI-X table size 9 on a 64-CPU host), Linux reduces the number of I/O queues to match vectors, and several CPUs share each queue — you'll see it in /sys/block/nvme0n1/mq/*/cpu_list. A "slow drive on big servers" complaint can be a vector-count limitation, not a media problem. Virtualised drives (SR-IOV VFs) are especially prone.

Quiz

  1. How is INTx carried on a PCIe link?

    Answer

    As Assert_INTx/Deassert_INTx message TLPs emulating a level-sensitive wire.

  2. Max vectors for MSI and MSI-X?

    Answer

    32 and 2048.

  3. Why does INTx need a flushing read?

    Answer

    The virtual-wire interrupt is turned into a CPU interrupt by the platform's interrupt controller on a path that is not guaranteed to be ordered with the device's earlier DMA writes reaching memory (and the line may be shared). A read of a device register cannot complete until earlier posted writes from the device ahead of the completion have been pushed through, so the ISR's MMIO read acts as a flush. MSI/MSI-X messages, being memory writes themselves, travel behind the data and need no such read.

  4. When should host software use INTMS/INTMC?

    Answer

    Only with pin-based or MSI interrupts — not MSI-X.

Interview questions

  1. Beginner What is MSI?
    Model answer

    An interrupt sent as a memory write of a data value to a special address, decoded by the platform as an interrupt.

  2. Intermediate Why does NVMe prefer MSI-X?
    Model answer

    Per-CQ vectors with independent address/data/mask allow per-CPU completion handling at scale.

  3. Advanced A server with 128 CPUs shows 16 NVMe queues. Why?
    Model answer

    Vector count or controller's Number of Queues (Feature 07h) limit; Linux maps several CPUs per queue.

43 MSI-X in Depth (Deep-Dive Module: MSI and MSI-X)

43.1 Why this chapter exists

"The interrupt didn't fire" is one of the most common NVMe bring-up and virtualisation complaints. Diagnosing it requires knowing exactly where MSI-X state lives (config space capability, a table in a BAR, a pending-bit array in a BAR), which bits gate delivery, how masking produces pending bits rather than lost interrupts, how NVMe binds CQs to vectors, and how coalescing deliberately delays interrupts.

43.2 Learning objectives

  • Beginner: name the three pieces of MSI-X (capability, table, PBA) and what a vector is.
  • Intermediate: decode Message Control, Table Offset/BIR, PBA Offset/BIR and a 16-byte table entry.
  • Advanced: explain masking semantics (Function Mask, per-vector mask, pending bits) and NVMe interrupt coalescing (Feature 08h) and Interrupt Vector Configuration (Feature 09h).
  • Senior: diagnose lost/late interrupts across device, platform (interrupt remapping) and virtualisation layers.
  • Trace-analysis: identify MSI-X MWrs and table-programming MWrs; map them to CQs.
  • Debugging: apply five failure patterns.
  • Validation: design tests for masking/pending behaviour.

43.3 Kid story and analogy boundary

🧒 Kid analogy

The SSD has a phone book (MSI-X table) kept in its own drawer. Each page (entry) has a phone number (Message Address), a short secret word to say (Message Data), and a little "do not call" sticker (mask bit). When a mailbox (CQ) has a new letter, the SSD looks up that mailbox's page and calls the number, saying the secret word. If the page has the "do not call" sticker, the SSD writes a tick on a sticky-note board (PBA) instead, and calls as soon as the sticker is removed. There's also a big "nobody calls anybody" switch for the whole phone book (Function Mask).

🧩 Analogy boundary

Represents: table entry fields, mask, pending. Hides: that the "call" is a posted memory write subject to PCIe ordering and flow control; that the platform decides what the "phone number" means (APIC address, interrupt remapping handle); that the host programs the phone book with MMIO writes. Misleading when: you think the tick on the board is a counter — it's one bit per vector, so multiple masked events collapse into one pending interrupt.

43.6 Mechanism step by step

The table below lists every actor. First, the same story as a picture: one I/O completion on queue 3 turning into an interrupt on CPU 3, plus what happens when a vector is masked.   1. Software programs MSI-X table entry 3

    At probe time the PCI core reads the MSI-X capability in config space (Table Size, Table BIR and Offset), sets MSI-X Enable with Function Mask, then writes each table entry it wants in the BAR: Message Address, Message Data, and finally Vector Control with Mask = 0.   2. Driver binds CQ 3 to vector 3 with Create I/O CQ

    The NVMe driver sends the admin command Create I/O Completion Queue (opcode 05h). Its CDW11 carries the Interrupt Vector (IV, bits 31:16) and Interrupts Enabled (IEN, bit 1).   3. Controller writes the completion entry to CQ 3

    An I/O on SQ 3 finishes. The controller writes its 16-byte completion entry into the next slot of CQ 3 in host memory, with the phase tag flipped to show it is new.

    Where: host memory, CQ 3 slot 2PCIe: Yes, device → host · MWr, 16 bytes
    CQE: CID = 0x0107 SQID = 3 SQHD = 3 Status = 0 P = 1
  4. Controller looks up vector 3 and decides whether to signal now

    Inside the SSD, the controller finds which vector CQ 3 uses (vector 3) and applies interrupt coalescing if the host enabled it: with Feature 08h it may wait until THR+1 completions have accumulated or TIME × 100 µs has passed. Then it checks MSI-X Enable = 1, Function Mask = 0 and entry 3's Mask = 0, and reads entry 3's address and data.

    Where: inside the SSD (vector state, coalescing counters, MSI-X table)PCIe: No. Nothing appears on the link while the controller decides.
    Coalescing off (Linux default): signal at once. With THR = 3, TIME = 1: signal after 4 CQEs or 100 µs, whichever first.
  5. Controller sends the interrupt: a memory write of Data to Address

    The interrupt is just a posted 4-byte memory write, sent upstream like any DMA write. Because it uses the same posted path, it cannot overtake the CQE write from step 3, so the CQE is already in RAM when the interrupt fires. Bus Master Enable must be set, or the device may not send it at all.

    Where: the Message Address from table entry 3 (an interrupt address, not RAM)PCIe: Yes, device → host · MWr, 1 DW, payload = Message Data
    MWr Requester ID = 02:00.0 Address = 0xFEE0_3000 Data = 0x0000_0024
  6. The platform turns the write into an interrupt on CPU 3

    The root complex recognises the interrupt address. If interrupt remapping (IOMMU) is on, it checks the requester ID and translates the message; the APIC then interrupts CPU 3. The NVMe handler for vector 3 reads CQ 3 only, processes entries while the phase tag matches, and writes the CQ 3 head doorbell.

    Where: host interrupt controller, then CPU 3PCIe: Only the final CQ head doorbell (MWr, host → device)
    /proc/interrupts: the count for the nvme0q3 line goes up on CPU 3
  7. If the vector is masked: the controller sets the pending bit instead

    Suppose vector 4 has Mask = 1 (for example while its CPU is going offline) when its CQ gets a new entry. The controller must not send the message. It sets bit 4 in the Pending Bit Array (PBA) and keeps the message waiting. The CQE itself is still written normally.

    Where: PBA in the BAR (read-only to software)PCIe: No message is sent while masked
    Entry 4: Mask = 1 → PBA bit 4 = 1
  8. When software unmasks, the pending message is sent

    When software later writes Mask = 0 for entry 4, the controller sees the pending bit, sends the MWr with entry 4's address and data, and clears the pending bit. Whether the controller re-checks that the CQ still has unprocessed entries first is implementation-dependent.

    Where: table entry 4 (unmask) → interrupt address of entry 4PCIe: Yes · host MWr to Vector Control, then device MWr 1 DW
    Host writes Vector Control[4] = 0 Device sends MWr 0x0025 → 0xFEE0_4000, PBA bit 4 = 0

Coalescing note: coalescing (Feature 08h) changes only when step 5 happens, never where the message goes. It trades fewer interrupts for added latency, and the admin CQ is never coalesced. A vector can be exempted with Feature 09h (Coalescing Disable).

43.8 Interrupt coalescing (NVMe Feature 08h)

CDW11 bitsFieldMeaning
15:08Aggregation Time (TIME)Maximum delay in 100 µs increments; 0 = no delay-based coalescing
07:00Aggregation Threshold (THR)Minimum number of CQEs to aggregate per vector, zero-based (0 → 1 entry)

The controller sends an interrupt when either the threshold of completions accumulates or the aggregation time elapses since the first unsignalled completion (spec describes the intent; exact timing impl). The setting applies to all I/O-queue vectors; Feature 09h (Interrupt Vector Configuration) CDW11 bits 15:0 select a vector and bit 16 Coalescing Disable (CD) exempts it. The admin CQ vector is not coalesced.

interrupts/s ≈ min(IOPS_per_vector / (THR+1), …) bounded below by 1 / (TIME × 100 µs) when traffic is light
  • THR — zero-based aggregation threshold
  • TIME — aggregation time in 100 µs units
  • IOPS_per_vector — completions per second on CQs mapped to this vector
⚠️ Latency trade-off

With TIME = 1 (100 µs) and QD1 workloads, a coalescing controller can add up to ~100 µs to every I/O — doubling the latency of a fast read. Linux does not enable NVMe coalescing by default. Tune only with measurement. nvme get-feature /dev/nvme0 -f 8 -H is read-only; set-feature changes device behaviour (caution).

    while t < dur_s:
        t += random.expovariate(iops); pending.append(t)
        if len(pending) >= thr or (tmax and t - pending[0] >= tmax):
            irqs += 1; added += [t - p for p in pending]; pending = []
    return irqs, sum(added)/max(1, len(added))
for thr0, tu in [(0,0),(3,1),(7,2),(15,4)]:
    print(thr0, tu, simulate(200_000, thr0, tu))

Questions: how does added latency scale with THR at high IOPS vs low IOPS?

Solution

At high IOPS the threshold triggers first: added latency ≈ (THR)/2 inter-arrival times (small). At low IOPS the timer dominates: added latency approaches TIME×100 µs. (This simple model only checks the timer on arrivals — a real controller has an independent timer; extend accordingly.)

🧪 Lab 43.4 (senior forensic) — The silent vector SAFE

Given (synthetic): timeouts on QID 7 only; /proc/interrupts for nvme0q7 stopped incrementing at 10:02:13; at 10:02:12 the kernel log shows CPU 6 offline then online; trace shows CQEs on CQ7 and no MWr to vector 7 address; PBA bit 7 = 1; Vector Control 7 = 1. Questions: What happened? Device or host? What fix?

Solution

The vector was masked during CPU offline (managed IRQ shutdown) and never unmasked when the CPU returned — host-side bug/race (high confidence: PBA proves the device latched the interrupt correctly). Fix: kernel update/patch for the affinity/hotplug path; workaround: avoid hotplug, reset controller.

43.13 Interview questions

Interview questions

  1. Beginner What is an MSI-X vector?
    Model answer

    An entry in the MSI-X table: address, data and mask; the device sends an MWr of the data to the address.

  2. Beginner Where is the MSI-X table?
    Model answer

    In a memory BAR, located by Table BIR and Offset from the capability.

  3. Beginner What does the PBA do?
    Model answer

    Records pending interrupts for masked vectors.

  4. Beginner How does an NVMe CQ choose its vector?
    Model answer

    IV field in Create I/O CQ CDW11, with IEN=1.

  5. Beginner Max MSI-X vectors?
    Model answer

    2048.

  6. Intermediate Decode Message Control 0xC01F.
    Model answer

    Enable=1, Function Mask=1, 32 vectors.

  7. Intermediate What does Feature 08h do?
    Model answer

    Configures interrupt aggregation threshold and time for I/O vectors.

  8. Intermediate Why must Bus Master Enable be set for MSI-X?
    Model answer

    Interrupt messages are memory writes the function initiates as a bus master.

  9. Intermediate What's the reset value of a vector's mask bit?
    Model answer

    1 (masked).

  10. Intermediate Can several CQs share a vector?
    Model answer

    Yes; the ISR must then scan all those CQs.

  11. Advanced Why does the CQE become visible before the ISR runs?
    Model answer

    Both are posted writes from the same requester; the interrupt cannot pass the CQE under default ordering.

  12. Advanced What happens to multiple events while a vector is masked?
    Model answer

    They collapse into one pending bit; one message on unmask.

  13. Advanced How does interrupt remapping change the meaning of Message Address/Data?
    Model answer

    Address/data become a handle into the IOMMU's remapping table, validated against the source ID.

  14. Advanced How would you test pending-bit behaviour?
    Model answer

    Mask vector, generate completions, read PBA (expect set), unmask, expect exactly one message and PBA clear.

  15. Advanced What is Coalescing Disable?
    Model answer

    Feature 09h bit 16 per vector, exempting it from Feature 08h.

  16. Senior A VM sees periodic 30 s timeouts after live migration. Approach?
    Model answer

    Check posted-interrupt/remapping state, table restore, PBA; correlate timestamp with migration; test with polling.

  17. Senior Design interrupt strategy for 2 M IOPS at low CPU.
    Model answer

    Per-CPU queues, MSI-X affinity, moderate coalescing for throughput queues, CD on latency queues, poll queues for hipri, NAPI-like hybrid polling.

  18. Senior Prove whether a missing interrupt is device or host.
    Model answer

    Analyzer at device link: MWr seen → host; not seen with PBA set → masked; not seen and PBA clear and CQE present → device bug (if coalescing excluded).

  19. Senior Why might vector count limit performance?
    Model answer

    Fewer queues than CPUs → shared queues, locking, cross-CPU completions, cache misses.

  20. Senior When is polling better than MSI-X?
    Model answer

    Ultra-low latency, high-IOPS dedicated cores where interrupt overhead dominates; costs CPU.
