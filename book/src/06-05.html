PART XIX

NVMe over Fabrics

NVMe was designed around shared memory: queues live in host RAM, the controller reads them by DMA, and a doorbell write across PCIe says “look now”. NVMe over Fabrics (NVMe-oF) keeps the command set, the queue-pair model, the namespaces and the status codes, and replaces the shared-memory transport with messages — capsules — carried by RDMA or TCP. This part teaches what stays the same, what changes, and how to debug the new layers. Baseline: NVMe Base 2.4 (which contains the fabrics architecture), NVMe over TCP Transport 1.3, NVMe over RDMA Transport 1.3, NVMe over PCIe Transport 1.4 (revision numbers per the August 2026 set — confirm on nvmexpress.org).

65 The NVMe-oF Mental Model

📘 Specification baseline

DOCUMENTS: NVMe Base Specification 2.4 (NVMe over Fabrics architecture, capsules, Fabrics commands, discovery, NQNs); transport binding specifications for PCIe (1.4), RDMA (1.3) and TCP (1.3). 65.1 Why this chapter exists

Engineers who know NVMe over PCIe often bring the wrong instincts to fabrics: they look for doorbells, PRPs and MSI-X, and find none. Engineers who know networking look for “a storage protocol inside TCP” and miss that it is still NVMe queue semantics. This chapter builds the bridge so the next three chapters make sense.

  • State precisely what is common to all NVMe transports and what each transport binds differently.
  • Explain capsules (command capsule = SQE + optional data/SGLs; response capsule = CQE).
  • Compare command delivery, data transfer, completion and notification across PCIe, RDMA and TCP.
  • Explain why fabrics need explicit Connect, NQNs and keep-alive.

Prerequisites: NVMe queues and SQE/CQE format (SQ, CQE), PRP and SGL; namespaces.

🧒 Kid analogy — same order form, different delivery

The library uses the same order form everywhere. In the school building (PCIe) you drop the form in a box on the librarian’s desk and ring a bell. For a library in another town you mail the form in an envelope (capsule) by express courier (RDMA) or by the regular postal service (TCP). The librarian fills orders the same way; only the delivery changes.

🧩 Where the analogy breaks

With PCIe, the librarian reaches into the school’s memory directly (DMA). With TCP, nobody reaches into anyone’s memory; every byte travels as a message. RDMA is in between: the remote librarian can read and write registered parts of the school’s memory, with permission keys.

65.2 What remains the same

  • Command set semantics: Read, Write, Flush, Identify, Get Log Page, and their status codes. verified
  • The SQE (64 bytes) and CQE (16 bytes) structures, with fabrics-specific use of some fields (e.g. SGLs are mandatory for data descriptions; PRPs are not used). verified
  • The subsystem → controller → namespace hierarchy, NSIDs, Asynchronous Events, reservations, ANA (Asymmetric Namespace Access) for multipath.
  • Queue-pair model: admin queue (QID 0) plus I/O queues.

💡 Senior insight

On PCIe, the transport is “invisible” and reliable: if a TLP is lost the link retries it. On fabrics, the transport has its own failure modes (packet loss, congestion, path failover, TLS errors) that surface to NVMe as timeouts and reconnects. Every NVMe-oF debug session starts by deciding: is this an NVMe problem or a transport problem?

Quiz

  1. Why are PRPs not used on fabrics?

    Answer

    PRPs are host physical page pointers meaningful only to a DMA engine with direct memory access; fabrics need descriptors meaningful to the transport (RDMA keys, TCP offsets), hence SGLs.

  2. How does a fabrics host read CSTS?

    Answer

    Property Get fabrics command on the admin queue.

Interview questions

  1. Intermediate What stays the same between NVMe/PCIe and NVMe/TCP?
    Model answerCommand sets, SQE/CQE structures, queue-pair model, subsystem/controller/namespace model, status codes, log pages.
  2. Senior Where does latency come from in NVMe/TCP vs PCIe?
    Model answerNetwork stack processing, copies, NIC interrupts, switch hops, R2T round trips for writes, and TCP congestion control — none of which exist in a PCIe doorbell/DMA path.

66 NVMe/TCP

📘 Specification baseline

DOCUMENT: NVMe over TCP Transport Specification, revision 1.3 per the August 2026 set (course brief — confirm). STATUS: transport binding. VERSION NOTES: NVMe/TCP was ratified in 2018 (TP 8000) and first published within NVMe-oF 1.1; TLS support and secure channel concatenation were added in later TPs version. PORTS: 4420 is the IANA-assigned port commonly used for NVMe-oF I/O; 8009 for the NVMe/TCP discovery service verified.

66.1 Why this chapter exists

NVMe/TCP runs on any Ethernet with an ordinary NIC and Linux kernel, which makes it the most widely deployed fabrics transport. Debugging it means reading a packet capture where NVMe commands are hidden inside a TCP byte stream as PDUs. This chapter teaches the PDU types, the command/data/completion paths, and the performance and failure patterns.

  • List the PDU types and their directions.
  • Decode the 8-byte common header (PDU-Type, FLAGS, HLEN, PDO, PLEN).
  • Trace read and write commands, including R2T and in-capsule data.
  • Explain header and data digests and when to enable them.
  • Diagnose connection, digest, R2T and timeout problems.

Prerequisites: Chapter 65; TCP fundamentals (stream, segments, retransmission).

🧒 Kid analogy — a phone call with forms

Two offices keep a phone line open (TCP connection). First they say hello and agree on rules (ICReq/ICResp). Then one reads out order forms (CapsuleCmd). For a delivery order, the other says “send me pages 1–4 now” (R2T) and the first reads them out (H2CData). For a fetch order, the other reads the pages back (C2HData) and then says “done, status OK” (CapsuleResp).

🧩 Where the analogy breaks

TCP is a byte stream: PDUs are not aligned to TCP segments, one segment can carry many PDUs, one PDU can span many segments. A capture tool must reassemble the stream to find PDU boundaries using PLEN.

Small writes can carry data in the CapsuleCmd itself (in-capsule data), avoiding the R2T round trip, if the controller’s in-capsule data size allows. verified The number of R2Ts and their sizes are controller choices bounded by MAXR2T and MAXH2CDATA impl.

66.4 Performance

T_write ≈ RTT (CapsuleCmd→R2T) + Σ(H2CData serialization) + t_media + RTT/2 (CapsuleResp)
  • RTT — network round-trip time
  • H2CData serialization — bytes / link rate per data PDU
  • t_media — controller processing and media time

Writes pay at least one extra half round trip for the R2T compared with reads unless in-capsule data is used. CPU cost per I/O (copies, checksums, interrupts) often limits IOPS before the network does; digests add CRC32C computation (offloaded by some NICs) impl.

💡 Senior insight

Map every NVMe/TCP I/O queue to its TCP connection (one connection per queue) and analyse them separately. An apparently random latency spike usually belongs to one connection that hit retransmission — averaged across queues it looks like a storage problem.

Quiz

  1. Which PDU solicits write data?

    Answer

    R2T (09h), sent by the controller.

  2. What do HLEN, PDO and PLEN tell you?

    Answer

    Header length, offset of data within the PDU, and total PDU length — enough to find the next PDU in the stream.

  3. Can a read finish without a CapsuleResp?

    Answer

    Yes, if the SUCCESS flag mechanism is enabled/used on the last C2HData PDU; otherwise a CapsuleResp follows.

67 NVMe/RDMA

📘 Specification baseline

DOCUMENT: NVMe over RDMA Transport Specification, revision 1.3 per the August 2026 set (course brief — confirm). RELATED: InfiniBand Architecture Specification and RoCE annexes (IBTA), iWARP RFCs (IETF). STATUS: transport binding. version

67.1 Why this chapter exists

RDMA (Remote Direct Memory Access) lets a NIC read and write registered memory on another machine without involving that machine’s CPU in the data path. NVMe/RDMA uses this to keep the “controller moves the data” spirit of PCIe NVMe across a network, giving the lowest-latency fabrics transport — at the cost of specialised networks and configuration.

  • Explain RDMA verbs at a conceptual level: SEND/RECEIVE, RDMA READ, RDMA WRITE.
  • Explain queue pairs and the mapping of NVMe queues to RDMA QPs.
  • Explain memory registration and keyed SGLs.
  • Trace NVMe reads and writes over RDMA.
  • Recognise RDMA transport failures (lossless network, PFC, retries).

Prerequisites: Chapter 65.

🧒 Kid analogy — the robot arm with a permission card

Before the library in the other town may take books from your shelf, you give it a permission card for one shelf (memory registration and key). Then its robot arm can reach over the network and take exactly those books (RDMA READ) or put books on that shelf (RDMA WRITE), without you lifting a finger. Messages like “please do this order” and “done!” are still mailed as letters (SEND).

🧩 Where the analogy breaks

The permission card is a 32-bit key plus address range checked by the NIC hardware; it can be invalidated, and stale keys are a security and correctness hazard. Also, RoCE networks usually need lossless Ethernet configuration (PFC/ECN) to perform well — the robot arm hates dropped packets.

67.2 Mechanism

Each NVMe queue pair (admin or I/O) maps to one RDMA queue pair (QP); connections are established with the RDMA connection manager, then the Fabrics Connect command is sent over that QP. verified concept; field and descriptor formats in the RDMA transport specification.

💡 Senior insight

In NVMe/RDMA the data path is driven by the target: it pulls write data and pushes read data. That mirrors PCIe NVMe (the controller does DMA) and is why RDMA latency approaches local NVMe. It also means a host-side memory lifecycle bug shows up as a remote error on the target’s operation — look at both sides.

Quiz

  1. Which RDMA operation moves data for an NVMe Write command (non-in-capsule)?

    Answer

    RDMA READ, issued by the target against the host’s registered buffer.

  2. What three things does a keyed SGL descriptor carry?

    Answer

    Address, length and key (remote access key).

68.1 The hierarchy

68.2 Discovery

A discovery controller is a special controller (in a discovery subsystem with the well-known NQN nqn.2014-08.org.nvmexpress.discovery, or a unique NQN for newer discovery models) that supports only what is needed to return the Discovery Log Page. Each log entry describes how to reach one subsystem port: transport type (TRTYPE), address family (ADRFAM), subsystem type, port ID, controller ID, transport address (TRADDR), transport service ID (TRSVCID, e.g. 4420), subsystem NQN and transport-specific attributes. verified

host:
  connect to discovery controller (e.g. TCP 192.0.2.10:8009, NQN = well-known discovery NQN)
  Get Log Page LID 70h  -> entries[]
  for e in entries matching policy:
      connect admin queue to e.TRADDR:e.TRSVCID, subnqn = e.SUBNQN
      Identify controller / namespaces; create I/O queues (one connection per queue)
  optionally keep discovery association (persistent) for change notifications

Centralized Discovery Controllers (CDC) aggregate many subsystems in large IP fabrics; hosts and subsystems register with them (Discovery Information Management) and mDNS-based automated discovery can locate discovery controllers version — confirm the current model and names in Base 2.4.

68.3 Multipath and ANA

A namespace can be reachable through several controllers/ports. Asymmetric Namespace Access (ANA) reports per-group states (optimized, non-optimized, inaccessible, persistent loss, change) via an ANA log page so hosts choose paths. Linux native NVMe multipath presents one block device per namespace across paths. verified

cat /sys/module/nvme_core/parameters/multipath
sudo nvme list-subsys -v
sudo nvme ana-log /dev/nvme1

💡 Senior insight

Interoperability bugs live in “optional” and “may”. When two compliant implementations fail together, list every optional feature and every “may” behaviour each one exercises, and test them pairwise. Then check which revision each side claims (VS register / Identify), because they may be reading different specifications.
