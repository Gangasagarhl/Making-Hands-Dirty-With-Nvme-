74 Protocol Trace Academy: Rules of Evidence

74.1 Why this chapter exists

Most wrong root causes are not caused by ignorance of the protocol; they come from over-trusting a trace: concluding "the completion never came" when the capture stopped too early, "the device never sent the interrupt" when the filter hid MSI-X writes, or "the link error caused the timeout" because one happened before the other. This chapter installs the habits that prevent those mistakes.

  • Beginner: read a trace table column by column and say what each row is.
  • Intermediate: state a trace's coverage and its limitations before analysing it.
  • Advanced: normalize traces into an event schema, group them into transactions and diff against a golden trace.
  • Senior: run the full ladder from packet reading to regression-test design; write evidence-graded bug reports.
  • Trace-analysis objective: find the first abnormal event, not the loudest one.
  • Validation objective: maintain versioned golden traces and automatic first-divergence detection.
🧒 Kid analogy

A trace is a security-camera recording of one hallway. It shows everyone who walked through that hallway while the camera was on. If the camera only records people wearing red (a filter), or was switched off at 3 o'clock (capture end), or faces only one way (one direction), then "nobody came" really means "nobody the camera could see came".

🧩 Where the analogy breaks

A camera records pixels; an analyzer records decoded symbols. If the analyzer cannot lock onto the signal (bad probing, unsupported speed, electrical idle exit it misses), it may silently miss or mis-decode packets — the recording itself can be wrong, not just incomplete.

74.3 Synthetic and real trace rules

⚠️ Synthetic trace rule

Every invented trace in this book is labelled SYNTHETIC TEACHING TRACE — NOT A REAL DEVICE CAPTURE and marked synthetic. Timings are plausible orders of magnitude chosen for teaching, not measurements of any product. Do not cite them as data.

Real trace rule. If you use a real trace (in training or a bug report), record: its source; the capture tool and its software/firmware version; whether it is public or confidential; known limitations (probe point, filters, buffer size); and redact confidential content: serial numbers, possibly vendor/device IDs, host names, file paths, proprietary payload bytes (user data can appear in data TLPs!), and customer identity. A trace of a Read command contains the data that was read — treat captures of production systems as potentially containing customer data.

74.6 Trace normalization: deterministic first, reasoning second

Raw captures come in proprietary formats, with analyzer-specific columns, and with traffic you do not care about. Before any human — or any AI assistant — reasons about a trace, convert it deterministically:

raw capture (vendor file)
   │  export with vendor software (CSV/text) — see Chapter 78
   ▼
normalized event schema   {t_ns, dir, layer, kind, req, cpl, addr, tag, len, status, payload?}
   │  classify addresses using configuration knowledge (BAR0, queue bases, MSI-X table)
   ▼
transaction groups        (Requester ID, Tag) pairs; NVMe commands keyed by (SQID, CID)
   │  order by time, compute phases
   ▼
timeline                  per command: doorbell, fetch, data, CQE, interrupt, head doorbell
   │  rules + golden-trace diff
   ▼
anomalies                 first divergence, missing stages, timeouts, protocol violations
💡 Senior insight — why deterministic normalization comes before LLM reasoning

A language model (or a tired human) reading 50,000 raw rows will pattern-match, skip, and occasionally invent a matching completion that is not there. A 100-line deterministic script never invents a row, produces the same answer every time, and can be reviewed and regression-tested. Use deterministic code for counting, matching and ordering; use human or AI reasoning for interpreting the reduced, verified anomaly list — and keep the reduced list as the citation for every claim.

74.7 Trace diffing and golden traces

A golden trace is a capture of a known-good transaction that is versioned (device firmware, host kernel, analyzer software), reproducible (scripted workload), labelled (what operation, what config), configuration-documented (Gen, width, MPS, MRRS, queue count, interrupt coalescing) and known-good (passed functional checks). Diffing a failing capture against the golden trace aligns: initialization, command submission, queue activity, TLP sequences, completions and interrupts — and highlights the first divergence.

The script below normalizes two synthetic traces and diffs them in two ways. Note how the raw-sequence diff is noisy because commands overlap, while the transaction-grouped diff pinpoints the missing stage:

#!/usr/bin/env python3
"""Trace normalization + good-vs-bad diff (OFFLINE / SIMULATION).
raw events -> normalized schema -> transaction-role tokens -> alignment -> first divergence.
Normalization removes things that legitimately differ between runs (timestamps,
absolute buffer addresses, tag values) so that only BEHAVIOUR is compared."""
import difflib
from trace_common import gen_trace, classify

def normalize(evs):
    toks = []
    for e in evs:
        role = classify(e)
        if role.startswith("data"):
            role = "data"                       # collapse addresses
        elif "slot" in role:
            role = role.rsplit(" ", 1)[0]       # drop ring slot index
        toks.append(f"{e.dir}:{e.kind}:{role}:{e.nbytes}")
    # collapse runs of identical data TLPs into one token with a count
    out = []
    for t in toks:
        if out and out[-1][0] == t:
            out[-1][1] += 1
        else:
            out.append([t, 1])
    return [f"{t} x{n}" if n > 1 else t for t, n in out]

def first_divergence(golden, test):
    sm = difflib.SequenceMatcher(a=golden, b=test, autojunk=False)
    for op, a0, a1, b0, b1 in sm.get_opcodes():
        if op != "equal":
            return op, a0, golden[a0:a1], test[b0:b1]
    return None

def transaction_diff(golden_evs, test_evs):
    """Group into per-command transactions FIRST, then compare stage sequences.
    Overlapping commands make raw-sequence diffs noisy; grouped diffs are not."""
    from lab06_timeline import build_timeline
    stages = ["doorbell", "fetch", "sqe", "data_first", "cqe", "irq"]
    g, _ = build_timeline(golden_evs)
    t, _ = build_timeline(test_evs)
    for key in sorted(g, key=lambda k: g[k].get("doorbell", 0)):
        gs = [s for s in stages if s in g[key]]
        ts = [s for s in stages if s in t.get(key, {})]
        if gs != ts:
            missing = [s for s in gs if s not in ts]
            return key, gs, ts, missing[0]
    return None

if __name__ == "__main__":
    golden = normalize(gen_trace(3))
    bad = normalize(gen_trace(3, faults=["nocqe:0x11"]))
    print(f"golden {len(golden)} tokens, test {len(bad)} tokens")
    d = first_divergence(golden, bad)
    if d:
        op, idx, g, b = d
        print(f"FIRST DIVERGENCE at golden token #{idx} ({op}):")
        print("   context :", golden[max(0, idx - 2):idx])
        print("   golden  :", g)
        print("   test    :", b)
    r = transaction_diff(gen_trace(3), gen_trace(3, faults=["nocqe:0x11"]))
    if r:
        key, gs, ts, first_missing = r
        print(f"TRANSACTION DIFF: SQ{key[0]} CID {key[1]:#x}: golden {gs}")
        print(f"                                test   {ts}")
        print(f"   first missing stage: {first_missing}")
golden 23 tokens, test 18 tokens
FIRST DIVERGENCE at golden token #14 (replace):
   context : ['UP:MWr:data:256 x4', 'DN:MWr:CQ1 head doorbell:4']
   golden  : ['UP:MWr:data:256 x12', 'UP:MWr:CQE post slot:16', 'UP:MWr:MSI-X interrupt:4', 'UP:MWr:data:256 x4', 'DN:MWr:CQ1 head doorbell:4', 'UP:MWr:data:256 x12']

🔍 Lesson

Normalization removed timestamps, tags and buffer addresses (which legitimately differ between runs) and collapsed runs of data TLPs. Even so, interleaving makes the sequence diff point at "data x12 vs data x28" — technically the first divergence, but not a useful one. Grouping by transaction first yields: CID 0x11 stopped after data; CQE missing. Always diff at the level of meaning you want to conclude about.

Quiz

  1. Name the six coverage items every trace analysis must state.

    Answer

    Capture start, capture end, timestamp completeness, filtering, decoder omissions, directions captured.

  2. Why can an SQE be absent from a trace even when the device executed the command?

    Answer

    The capture may have started after the fetch, a filter may hide CplDs, or the SQ may live in the Controller Memory Buffer (CMB), in which case the host writes it with MWr to the device and no fetch MRd occurs.

  3. What five properties make a trace "golden"?

    Answer

    Versioned, reproducible, labelled, configuration-documented, known-good.

✅ Mastery gate
  • I state coverage before analysis, every time.
  • I can describe the normalization pipeline and why it precedes interpretation.
  • I can explain why transaction-level diffs beat raw-sequence diffs.
  • I know what to redact before sharing a trace.

💡 Senior insight

Memorize the shape: tiny DN write, small UP read, small DN completion, long silence, burst of UP writes, one small UP write to the CQ, one tiny UP write to the interrupt address, tiny DN write. Abnormal traces are recognisable first as a shape violation — a missing burst, a silence in the wrong place.

(4) The root-port receiver (upstream direction); the SSD transmitter, the channel (connector, retimer, trace) or the root-port receiver equalization are candidates.

First abnormal event: row 2, the first TLP with bad LCRC — not the Nak (a consequence) and not the Recovery (an escalation).

Hypotheses: H1 marginal channel at 16 GT/s; H2 SSD transmitter equalization preset; H3 root-port receiver issue; H4 power/thermal noise.
