PART XVI

Power and Reset

Resets and power transitions are where state goes to die — and where many of the hardest bugs live. An NVMe SSD has state at several levels: NVMe controller registers and queues, the NVM subsystem shared by controllers, the PCIe function's configuration space, the link's training state, and the physical power rails. Each reset type and each power state wipes a different subset of that state, takes a different amount of time, and leaves different evidence. This part teaches you, for every reset and every power transition, exactly what is lost, what survives, what the host must rebuild, and how to recognise each one in a trace or a log.

48 NVMe Reset (Deep-Dive Module: Reset, NVMe Side)

48.1 Why this chapter exists

When an NVMe command times out, Linux's escalation ends in a controller reset. When firmware is updated, activation may need a reset. When the system shuts down, the controller must be told so that it can flush its caches and mark itself clean — otherwise the next boot may see an "unsafe shutdown" and spend time rebuilding mapping tables. Each of these is a different NVMe mechanism: Controller Reset (CC.EN 1→0), NVM Subsystem Reset (NSSR), and Shutdown (CC.SHN / CSTS.SHST). Confusing them causes lost data, hung reboots and "drive disappeared" incidents.

48.2 Learning objectives

  • Beginner: state what CC.EN, CSTS.RDY, CC.SHN, CSTS.SHST and NSSR do.
  • Intermediate: list the state destroyed and preserved by a controller reset; write the re-initialisation sequence.
  • Advanced: explain outstanding command handling, CAP.TO timing, NSSR scope and its PCIe side effects; distinguish normal vs abrupt shutdown.
  • Senior: design a robust reset/recovery ladder and reason about lost commands.
  • Trace-analysis: recognise reset and re-init sequences on the link.
  • Debugging/validation: five failure patterns; validate reset correctness.

48.3 Story and analogy

🧒 Kid analogy

A controller reset is the warehouse manager blowing a whistle: every worker drops what they're holding, all the trays except the main office tray are thrown away, and work starts again only when the manager says "ready". Shutdown is closing time: workers finish putting things on shelves, lock up, and hang a sign "closed properly". NVM subsystem reset is turning off the power to the whole warehouse complex, including the other managers' buildings next door.

🧩 Where the analogy breaks

Dropped work isn't reported: commands outstanding at a controller reset simply never get CQEs — the host has to know to treat them as aborted. And "closed properly" (SHST complete) does not by itself mean power is off; the host decides what happens next (power off, D3, keep running).

48.5 Controller Reset (CC.EN 1 → 0)

Effects (verified in substance; consult Base spec "Controller Reset" for normative text):

  • The controller stops processing commands; all I/O SQs and CQs are deleted; outstanding commands are not completed (the host treats them as aborted).
  • Controller registers return to their reset values except the admin queue registers (AQA, ASQ, ACQ), which are retained; CSTS.RDY goes to 0 within CAP.TO.
  • Internal controller state (Set Features values that are not saved, Asynchronous Event state, etc.) resets; persistent namespace data is unaffected; writes already completed remain subject to cache rules (a reset is not a power loss, but a host should Flush before a deliberate reset if durability matters).
  • The PCIe function, its configuration space, BARs, MSI-X configuration and the link are not reset by CC.EN alone.

Re-initialisation sequence:

// Controller reset + re-init (host side)
cc = mmio_read32(CC); cc &= ~CC_EN; mmio_write32(CC, cc);   // MWr to BAR0+14h
wait_until(mmio_read32(CSTS) & RDY == 0, CAP.TO * 500 ms);   // MRd/CplD polling
// all I/O queues are gone; outstanding CIDs -> fail/requeue in software
mmio_write32(AQA, (acqs-1) << 16 | (asqs-1));               // optional: retained, but reprogram
mmio_write64(ASQ, asq_iova); mmio_write64(ACQ, acq_iova);
mmio_write32(CC, CSS | MPS | AMS | IOSQES(6) | IOCQES(4) | EN);
wait_until(mmio_read32(CSTS) & RDY == 1, CAP.TO * 500 ms);
if (CSTS & CFS) escalate();                                    // PCIe-level reset
identify_controller();                                         // re-validate (FW may have changed)
set_features(NUM_QUEUES 07h);                                  // re-negotiate
for each queue: create_io_cq(qid, iv), create_io_sq(qid, cqid); // CQs first, then SQs
submit_async_event_requests(AERL+1 or fewer);
restore_features();   // e.g. APST (0Ch), coalescing (08h), VWC (06h), HMB (0Dh) if used
resubmit_or_fail(outstanding_requests);
⚠️ Host Memory Buffer

If the controller uses an HMB (Feature 0Dh), the host must keep the HMB memory intact and mapped until the controller is reset or the HMB disabled; after a controller reset the host re-enables it. Freeing HMB memory while the device may still access it is a classic use-after-free DMA hazard (derived).

48.6 Outstanding commands — the lost-command problem

At the moment of reset, a command can be in any of these states; the host cannot generally tell which:

State at resetHas data moved?Media effectHost treatment
In SQ, not fetchedNoNoneResubmit safe
Fetched, not startedNoNoneResubmit safe
Read in progressPartially into host bufferNoneResubmit (buffer contents undefined until success)
Write in progressPartially fetchedMay be partially written (atomicity rules — AWUN/AWUPF — define what's guaranteed)Resubmit; upper layers must tolerate torn writes beyond atomic size
Completed, CQE posted but not consumedYesDoneCQE is lost with CQ deletion; host may resubmit — idempotent for read/write, not for e.g. some admin commands
💡 Senior insight

The dangerous cases are non-idempotent commands (Firmware Commit, Format, Sanitize, Namespace Management, reservation commands) and writes whose completion was lost. Robust hosts poll the CQ one last time before resetting (Linux's timeout handler does check for a completed CQE), and upper layers must use FUA/Flush and journalling, not assumptions about which writes landed.

48.7 NVM Subsystem Reset (NSSR)

If CAP.NSSRS = 1, writing 4E564D65h to NSSR (20h) resets the whole NVM subsystem — every controller in it, on every port. After it, CSTS.NSSRO = 1 tells hosts it happened. Because the subsystem includes the PCIe port logic on many designs, the PCIe link may go down and retrain (impl) — the root port may log Surprise Down unless masked, and Linux must handle the device as if it had been reset at the PCIe level (re-restore config space). Linux exposes it as nvme subsystem-reset.

⚠️ Safety

nvme reset and nvme subsystem-reset interrupt all I/O on the device; on a boot or root device this can crash or hang the system. Use only on dedicated test devices.

48.8 Shutdown

TypeCC.SHNController doesHost waits forUse
Normal01bCompletes/flushes internal work, saves metadata, marks cleanCSTS.SHST = 10b (time guided by RTD3E in Identify Controller and host timeout; Linux nvme_core.shutdown_timeout)Power off, reboot, suspend-to-power-off

Recommended order (normal shutdown): stop new I/O → wait for or abort outstanding commands → delete I/O SQs, then I/O CQs → set CC.SHN = 01b → poll SHST until 10b → (optionally) clear EN, transition to D3hot/D3cold or power off. To restart after shutdown, the host performs a controller reset/enable sequence. Newer specification revisions also define NVM-subsystem-level shutdown — version.

🔍 Evidence

    The controller reports "shutdown processing occurring" in CSTS.SHST and starts its work: finishing anything in flight, writing its volatile cache and mapping tables to NAND, and recording a clean shutdown.

    Where: inside the SSD; CSTS at BAR0 + 1ChPCIe: No. Internal work; nothing is sent.

  4. The controller finishes: SHST = 10b

    When everything is safe, the controller sets SHST = 10b (shutdown processing complete). How long this takes is device-specific; Identify Controller RTD3E gives a hint, and the host also has its own timeout.

    Where: CSTS at BAR0 + 1ChPCIe: No
    CSTS: SHST = 10b, RDY = 1 (e.g. 180 ms after step 2, synthetic)
  5. The driver polls CSTS until SHST = 10b

    The driver reads CSTS in a loop. Each read is a full round trip over PCIe. If SHST does not reach 10b before the host's timeout, the host gives up; the next power-up will count an unsafe shutdown in the SMART log.

    Where: CSTS at BAR0 + 1ChPCIe: Yes · MRd (host → device), CplD with 4 bytes (device → host), repeated
    reads: 0x0000_0005 (SHST=01b, RDY=1) … 0x0000_0009 (SHST=10b, RDY=1)
  6. Controller reset: CC.EN = 0

    To use the device again (instead of powering it off), the host performs a controller reset by clearing CC.EN (and SHN). This is the same reset used for error recovery.

    Where: CC at BAR0 + 14hPCIe: Yes, host → device · MWr, 4 bytes
    CC: 0x0046_4001 → 0x0046_0000 (EN = 0, SHN = 00b)
  7. The controller resets: RDY → 0

    The controller drops all I/O queue state and any outstanding commands, returns its registers to reset values except AQA, ASQ and ACQ, and clears CSTS.RDY within CAP.TO. SHST returns to 00b. Config space, BARs, MSI-X and the PCIe link are not touched.

    Where: inside the SSD; CSTSPCIe: No
    CSTS: RDY = 0, SHST = 00b (CAP.TO = 0x28 → wait up to 20 s)
  8. Wait for RDY = 0, then enable again

    The driver polls CSTS until RDY = 0. It (re)writes AQA, ASQ and ACQ (they were kept, but drivers usually write them anyway), then writes CC with the queue entry sizes, memory page size and EN = 1.

    Where: AQA 24h, ASQ 28h, ACQ 30h, CC 14hPCIe: Yes · MRd/CplD polls, then MWr to each register
    AQA = 0x001F_001F (32-entry admin queues) CC = 0x0046_0001 (IOCQES=4, IOSQES=6, EN=1)
  9. The controller becomes ready: RDY = 1

    The controller initialises and sets CSTS.RDY = 1. The driver's polling sees it. If instead CSTS.CFS = 1, or RDY never comes within CAP.TO, the driver escalates to a PCIe-level reset (Chapter 49).

    Where: CSTSPCIe: MRd/CplD polls only
    CSTS: 0x0000_0001 (RDY = 1, CFS = 0, SHST = 00b)
  10. Rebuild: Identify, features, queues, async events

    The driver sends Identify Controller (firmware may have changed), Set Features Number of Queues (07h), creates each I/O CQ and then its SQ, submits Asynchronous Event Requests, restores other features (APST, coalescing, write cache) and resubmits or fails the requests that were stopped in step 1.

    Where: admin queue, then I/O queuesPCIe: Yes · normal admin-command traffic
    Create I/O CQ 1..8 (IV 1..8), then Create I/O SQ 1..8 (CQID 1..8)

An error-recovery reset skips steps 1–5: the driver goes straight to step 6, and any command that was outstanding is lost without a completion (see 48.6).

🧪 Lab 48.1 — Reset lab: which state must be rebuilt? SAFE

Objective: from a synthetic event log covering normal init, reset, teardown, re-init and a lost command, determine what the host must rebuild and which command was lost. Setup (synthetic log):

t=0.000  CC.EN=1, RDY=1; Identify; Set Features 07h -> 4 SQ / 4 CQ granted
t=0.010  Create I/O CQ 1..4 (IV 1..4); Create I/O SQ 1..4; 4x AER armed
t=0.020  Set Features 08h (THR=3, TIME=1); Set Features 0Ch APST enabled
t=5.000  SQ2: Write CID 0x0101 LBA 0x1000 NLB 7   (doorbell seen)
t=5.000  SQ2: Write CID 0x0102 LBA 0x2000 NLB 7   (doorbell seen)
t=5.001  CQ2: CQE CID 0x0101 status 0             (MWr seen; host has NOT processed CQ2 yet)
t=5.002  host: CC.EN=0  (timeout recovery on another queue)
t=5.015  CSTS.RDY=0
t=5.020  CC.EN=1 ... RDY=1
t=5.400  Identify; Set Features 07h; Create CQ1..4; Create SQ1..4; AER armed
t=5.410  (no Set Features 08h / 0Ch issued)

Procedure: list every piece of state destroyed by the reset; mark which the host rebuilt; identify missing rebuild steps; classify CID 0x0101 and 0x0102.

Questions: (1) What did the reset destroy? (2) What did the host forget? (3) What is the status of CIDs 0x0101 and 0x0102? (4) What changes in observed behaviour after the reset?

Solution

(1) All I/O SQs/CQs and their contents (including the unprocessed CQE for 0x0101), outstanding commands, queue doorbell state, AER commands, non-saved feature values (Interrupt Coalescing, APST, etc.), async event masks. Admin queue registers were retained; PCIe config/MSI-X were not touched. (2) Coalescing (08h) and APST (0Ch) were not restored — they reverted to defaults. (3) 0x0101: completed by the device, but its CQE was destroyed before the host consumed it → host sees it as outstanding → must resubmit (write is idempotent: same data to same LBA). 0x0102: unknown — may be partially written; must resubmit; durability only after Flush/FUA. (4) Interrupt rate changes (no coalescing → more interrupts, lower latency) and power behaviour changes (no APST → higher idle power): "performance changed after a reset" is a classic symptom of features not restored.

Extension: add an HMB and decide when the host may free it.

Quiz

  1. Which registers survive CC.EN 1→0?

    Answer

    AQA, ASQ, ACQ (admin queue attributes and bases).

  2. What value initiates NSSR?

    Answer

    4E564D65h ("NVMe") written to offset 20h, if CAP.NSSRS=1.

  3. Which SHST value means shutdown complete?

    Answer

    10b.

  4. How long may the host wait for RDY?

    Answer

    CAP.TO × 500 ms.

  5. Order to create queues after reset?

    Answer

    CQs before the SQs that reference them.

Interview questions

  1. Beginner What does a controller reset do?
    Model answer

    Stops the controller, deletes I/O queues, drops outstanding commands, resets registers except admin queue registers; host re-enables and rebuilds.

  2. Intermediate Difference between shutdown and reset?
    Model answer

    Shutdown prepares for power loss (flush, mark clean) and is reported via SHST; reset reinitialises the controller and discards in-flight work.

  3. Advanced Why might NSSR cause a Surprise Down?
    Model answer

    Subsystem reset can reset PCIe port logic, dropping the link.

  4. Senior Design a recovery ladder.
    Model answer

    Poll CQ → Abort → controller reset → FLR → hot reset (SBR) → slot power cycle → remove device; with feature restore and command replay rules at each step.

49 PCIe Reset

49.1 Why this chapter exists

When an NVMe controller reset is not enough — the controller is fatal, MMIO returns all-ones, or the link is broken — recovery moves down to PCIe-level resets. They are blunter: they reset configuration space (BARs, Command register, MSI-X enable, MPS/MRRS settings), may retrain the link and may take hundreds of milliseconds. Knowing which reset resets what is essential to recover a device without rebooting, and to avoid making things worse.

49.2 Learning objectives

  • Define Conventional Reset (Cold, Warm, Hot) and Function Level Reset, plus Link Disable and Secondary Bus Reset as triggers.
  • State what each reset affects (function state, link, sticky bits) and timing rules after reset.
  • Explain the relationship between PCIe resets and NVMe controller state.
  • Recognise resets in traces (LTSSM transitions, CRS completions, config re-programming).

49.3 Analogy

🌍 Analogy

A cold reset is unplugging the whole building. A warm reset is pressing the building's big red reset button with power still on (PERST#). A hot reset is a message sent down the road telling the next building to reset itself. An FLR resets just one office in a building that houses several companies, leaving the road open.

🧩 Where the analogy breaks

Hot reset is not addressed to one device: it propagates to everything below the port that issued it. And FLR does not reset the shared link or other functions, but an NVMe subsystem may still be shared with other functions or ports — FLR's scope is the function's controller only.

📘 Spec — timing rules

verified (substance; see PCIe Base for exact conditions): after a Conventional Reset, software must wait at least 100 ms before sending configuration requests to a device below a port supporting ≤ 5 GT/s; for ports supporting > 5 GT/s, wait 100 ms after link training completes (Data Link Layer Link Active). A device may answer configuration requests with Configuration Request Retry Status (CRS) while initialising, for up to 1 s after reset; software with CRS Software Visibility enabled sees a special value (Vendor ID 0001h) when reading. After FLR, software waits 100 ms before accessing the function (unless Readiness Notifications/Immediate Readiness say otherwise — version). After D3hot → D0, a 10 ms recovery time applies.

🐞 Debugging

After any PCIe-level reset, the OS must restore config space (BARs, Command register Memory Space + Bus Master enable, MSI-X, MPS/MRRS, ASPM, LTR, L1 substates) before the NVMe driver touches BAR0. If restore is skipped or partial, the first MMIO read of CAP returns all-ones (Memory Space disabled → UR) or the first DMA fails (Bus Master disabled → the device can't issue requests). Many "device dead after reset" bugs are restore bugs, not device bugs.

Quiz

  1. Which resets are Conventional Resets?

    Answer

    Cold, warm (Fundamental Resets) and hot reset.

  2. How is FLR initiated?

    Answer

    Device Control bit 15 (Initiate Function Level Reset), if FLR capable.

  3. Does FLR retrain the link?

    Answer

    No.

  4. What does CRS mean?

    Answer

    Configuration Request Retry Status — device not ready; retry the config request.

  5. Does a controller reset (CC.EN) reset MSI-X configuration?

    Answer

    No — PCIe config/MSI-X untouched; only NVMe controller state.

Interview questions

  1. Intermediate Compare FLR and SBR for recovering an NVMe SSD.
    Model answer

    FLR: function only, link stays up, no effect on siblings; SBR: everything below the port, link retrains, more thorough (resets PCIe logic) but broader impact.

  2. Advanced Why wait 100 ms after reset?
    Model answer

    Spec-mandated time for device initialisation before config requests; CRS covers longer init up to 1 s.

  3. Senior A device recovers only after a cold power cycle. What does that tell you?
    Model answer

    State survives warm/hot/FLR: sticky or always-powered logic, firmware stuck in a state not reset by PERST#, or PHY needing full power-on; escalate to vendor with that evidence.
