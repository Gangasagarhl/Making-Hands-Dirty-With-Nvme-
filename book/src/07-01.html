PART XXI

Linux Practicals

Everything so far has been theory, specification and synthetic traces. This Part puts your hands on a real Linux machine — safely. You will learn to read what the kernel and the device already expose: the PCIe configuration space through lspci and sysfs, the NVMe controller through nvme-cli, and the history of what went wrong through dmesg and journalctl. The rule for the whole Part is simple: read first, write never — unless you know exactly what the write does, on a machine you are allowed to break, with data you are willing to lose. Every command table in this Part has two columns that matter more than the command itself: what this proves and what this cannot prove.

69 Linux PCIe Inspection

69.1 Why this chapter exists

When an NVMe drive is "slow", "missing" or "flaky", the first question a senior engineer asks is not about NVMe at all. It is: did the PCIe link come up the way it should, and is the device configured the way the driver expects? On Linux, the answers already sit in the PCI Express configuration space of every device and every port above it. lspci, setpci and /sys/bus/pci are the three windows onto that space. Engineers who cannot read them waste days on analyzers and firmware logs to discover something that one lspci -vv line would have told them: the drive trained at x2 instead of x4, or at 8 GT/s instead of 16 GT/s.

  • Beginner: list PCIe devices, find your NVMe controller, and identify its Bus/Device/Function (BDF) and vendor/device IDs.
  • Intermediate: read Link Capabilities vs Link Status, Max Payload Size (MPS), Max Read Request Size (MRRS), MSI-X state, and Advanced Error Reporting (AER) status bits from lspci -vv.
  • Advanced: walk the topology with lspci -tv and sysfs to find the upstream port that limits the link, and decode raw config space with lspci -xxxx and the Lab 1 parser.
  • Senior: state precisely what config-space inspection proves and what it can never prove, and decide when to escalate to a protocol analyzer.
  • Validation: build a read-only "link health snapshot" that can be compared before and after a test run.

Prerequisites. Configuration space layout, capability lists, Base Address Registers (BAR), link training (LTSSM) and the PCIe Capability structure from the PCIe Parts of this book; the programming lab that parses config hex is Lab 1 in Chapter 72.

69.2 Story: the building inspector

🧒 Kid analogy

Imagine a huge apartment building. Every apartment has a little sign-board by its door: who lives there, how many rooms they have, how wide their front door is, and whether the door is currently stuck half-open. A building inspector walks the corridors reading every sign-board. She never goes inside and never moves the furniture — she only reads. lspci is that inspector. The sign-boards are each device's configuration space. The corridors are the PCIe bridges and switches. If a sign says "my door is 4 people wide" but "today only 2 people can pass", the inspector has found a problem without opening a single door.

🧩 Where the analogy breaks

Real sign-boards cannot lie or go stale, but config-space values are written by firmware, by the BIOS/UEFI, by the kernel and by the device itself, at different times. A "status" bit may be sticky (it records something that happened hours ago and stays set until cleared — many AER bits behave this way), and some registers change dynamically (link speed can change after a Recovery). Also, reading certain registers is not always side-effect free on broken hardware, and reading the extended space needs root. The inspector reads a snapshot, never a movie.

69.3 Beginner: the commands and what each one is for

The PCI utilities package (pciutils) provides lspci (list and decode) and setpci (read and write individual registers). Both read the same data the kernel exposes through /sys/bus/pci/devices/<domain:bus:dev.fn>/config. As an unprivileged user you typically see only the first 64 bytes (the standard header); the capability lists — where everything interesting lives — need root.

💡 Senior insight

The single most valuable two-line comparison in PCIe debugging is endpoint LnkCap/LnkSta vs root-port LnkCap/LnkSta. If the root port's LnkCap says 8 GT/s, your "Gen4 SSD at Gen3" is not a fault at all — it is the platform. If both say 16 GT/s and LnkSta says 8 GT/s, something during equalization or Recovery decided to fall back, and that is a signal-integrity investigation. Always read both ends before you write a bug report.

69.5 Topology: lspci -tv and sysfs paths

The tree view is how you find the port above your device. Illustrative shape (synthetic):

-[0000:00]-+-00.0  Host bridge
           +-01.0-[01]----00.0  NVMe controller (the SSD)
           +-01.1-[02-05]----00.0-[03-05]--+-00.0-[04]----00.0  NVMe controller
           |                               \-08.0-[05]----00.0  NVMe controller
           \-1f.0  ISA bridge

Read it as: root port 00:01.0 has secondary bus 01, and on that bus sits the SSD 01:00.0. Root port 00:01.1 leads to bus 02 where a switch upstream port 02:00.0 lives; its downstream ports 03:00.0 and 03:08.0 lead to buses 04 and 05. The switch matters for debugging because every TLP crosses an extra pair of links and an extra store-and-forward or cut-through stage, and because the switch can be a capture point itself (see Chapter 78).

sysfs encodes the same path in its directory names, which makes it scriptable:

# Full path from the root complex to the device
readlink -f /sys/bus/pci/devices/0000:01:00.0
#  -> /sys/devices/pci0000:00/0000:00:01.0/0000:01:00.0

# Upstream port of the device = parent directory
basename "$(dirname "$(readlink -f /sys/bus/pci/devices/0000:01:00.0)")"

# Link state, both ends, without root
for d in 0000:00:01.0 0000:01:00.0; do
  p=/sys/bus/pci/devices/$d
  echo "$d now=$(cat $p/current_link_speed) x$(cat $p/current_link_width)" \
       "max=$(cat $p/max_link_speed) x$(cat $p/max_link_width)"
done

69.7 setpci: reading single registers — and why writing is dangerous

setpci addresses registers by offset or by name, with a width suffix .b, .w or .l. Capability-relative names such as CAP_EXP (the PCI Express capability) and ECAP_AER let you avoid hard-coding offsets that differ between devices (check man setpci for the names your version supports version).

# READS ONLY. No "=" sign anywhere means no write.
sudo setpci -s 01:00.0 VENDOR_ID.w DEVICE_ID.w      # identity
sudo setpci -s 01:00.0 COMMAND.w                      # bit1 Mem, bit2 BusMaster
sudo setpci -s 01:00.0 CAP_EXP+0x08.w                 # Device Control (MPS bits 7:5, MRRS 14:12)
sudo setpci -s 01:00.0 CAP_EXP+0x0c.l                 # Link Capabilities
sudo setpci -s 01:00.0 CAP_EXP+0x12.w                 # Link Status (speed 3:0, width 9:4)
sudo setpci -s 01:00.0 ECAP_AER+0x04.l                # AER Uncorrectable Error Status
sudo setpci -s 01:00.0 ECAP_AER+0x10.l                # AER Correctable Error Status

Decoding CAP_EXP+0x12.w = 1043: bits 3:0 = 3 → 8 GT/s; bits 9:4 = 4 → x4; bit 12 = 1 → slot clock configuration. Compare with Link Capabilities bits 3:0 (max speed) and 9:4 (max width).

⚠️ Warning — setpci writes

Any setpci argument containing = is a write to live hardware. A single wrong write can: disable Memory Space or Bus Master (the device vanishes from the driver's view mid-I/O, causing timeouts and possible data loss), change MPS to a value the path does not support (Malformed TLPs, fatal errors), retrain or disable the link (the root filesystem disappears if it lives on that drive), or clear AER status that someone else needed as evidence. Rules: never write on a production system; never write to the device holding your OS; know the register's semantics from the specification, including RW1C ("write 1 to clear") bits; record the old value first; and prefer the kernel's own interfaces (sysfs, driver parameters) over raw writes. This book does not ask you to perform any setpci write.

69.8 Specification and hardware view

📘 Specification

The register layout lspci decodes is defined by the PCI Express Base Specification (Type 0/1 headers, capability structures, extended capabilities starting at offset 100h). verified Offsets used above inside the PCI Express Capability: Device Capabilities +04h, Device Control +08h, Device Status +0Ah, Link Capabilities +0Ch, Link Control +10h, Link Status +12h, Device Control 2 +28h, Link Capabilities 2 +2Ch, Link Control 2 +30h, Link Status 2 +32h. Inside AER: Uncorrectable Status +04h, Mask +08h, Severity +0Ch, Correctable Status +10h, Correctable Mask +14h. Always confirm against the specification revision your platform implements.

🔧 Hardware

Every config read by lspci becomes a configuration-read request (CfgRd0 to the endpoint, or ECAM memory reads that the root complex converts into configuration TLPs impl). That means an analyzer on the link will see your lspci — useful as a deliberate trigger marker, and a reason not to run monitoring loops of lspci during a sensitive capture. A device that has dropped off the link returns all-ones (ff) for every config read; lspci then shows !!! Unknown header type 7f or similar.

69.9 Debugging connection

🐞 Debugging

Config space is the first stop for: device missing (enumerated or not?), slow sequential throughput (width/speed downgrade, MPS 128), interrupts misbehaving (MSI-X disabled or masked), and error storms (AER status bits). It is the wrong tool for: intermittent link Recovery (you need counters or an analyzer), latency outliers (you need block-layer tracing), or "which command failed" (you need NVMe logs). See the decision tree in Chapter 80.

69.10 Common mistakes

  • Running lspci -vv without root and concluding "the device has no AER capability" — the output said Capabilities: <access denied>.
  • Reading only the endpoint's LnkSta and blaming the SSD for a speed the root port could never reach.
  • Treating one latched CorrErr+ as a fault. Correctable errors are designed to be corrected; their rate is the signal.
  • Copy-pasting a setpci line from a forum that contains =.
  • Assuming lspci names are authoritative: the pci.ids file maps IDs to names and may be outdated; IDs are the truth.
🧪 Lab 69.1 — H1/H2/H3: identify the device, read config space, identify BARs SAFE

Classification: non-destructive · read-only · production-safe (reads only; root needed for full decode).

Objective: produce a one-page "PCIe identity card" for one NVMe controller.

Setup: any Linux machine with an NVMe SSD; pciutils installed.

  1. H1 — lspci -nn -d ::0108; record BDF, vendor:device, revision.
  2. H2 — sudo lspci -s <BDF> -vv; record Command bits, MSI-X state, DevCap/DevCtl MPS, MRRS, LnkCap, LnkSta, AER status lines.
  3. H2b — sudo lspci -s <BDF> -xxxx > cfg.hex; run python3 lab01_cfgspace.py cfg.hex (Chapter 72) and check that its decode agrees with lspci.
  4. H3 — cat /sys/bus/pci/devices/0000:<BDF>/resource; identify BAR0 start/end; compute its size.
  5. Repeat steps 2 for the upstream port (find it with readlink -f).

Observations to record: device and port speeds/widths; programmed MPS on both; any AER bits set.

Questions: (1) Is the link at the maximum both ends support? (2) Is MPS identical on port and endpoint? (3) How large is BAR0 and why is it at least 0x1000 + doorbell space?

Solution / expected reasoning

(1) Compare min(port LnkCap, device LnkCap) with LnkSta; equality is healthy. (2) MPS must be configured consistently along a path; Linux commonly programs a common value per hierarchy (policy is configurable with the pci=pcie_bus_* kernel parameters version). (3) NVMe controller registers occupy offsets 00h–FFFh and doorbells begin at 1000h with stride 4 << CAP.DSTRD; with N queue pairs you need 1000h + 2·N·stride bytes; vendors round BAR0 up (16 KiB is common) and may place MSI-X tables in the same BAR impl.

Extension: write a shell script that prints a CSV row per NVMe device: BDF, port BDF, cur/max speed and width for both, MPS, MSI-X count. Run it before and after a stress test and diff.

Quiz

  1. Which flag shows extended capabilities such as AER in hex?

    Answer

    -xxxx (as root). -xxx stops at 256 bytes; extended capabilities start at offset 100h.

  2. LnkSta shows 16GT/s x2 on a x4-capable SSD whose root port is x4-capable. Name three plausible causes.

    Answer

    Lanes failing detect/training (damaged lane, bad connector, cable/riser), a slot physically wired x2 despite a x4 port configuration (bifurcation/BIOS setting), or a retimer/redriver issue. Confirm with port LnkCap, platform documentation, and if needed an analyzer capture of training.

  3. Why can lspci not tell you that the link went through Recovery 300 times last night?

    Answer

    Config space shows current state and some sticky status bits, not event counts. Recovery history needs AER counters, vendor-specific counters, platform telemetry or an analyzer.

  4. Which setpci commands in this chapter write to hardware?

    Answer

    None. A write always contains = (e.g. REG.w=VALUE).

Interview questions

  1. Beginner How do you find the PCIe address and IDs of an NVMe SSD on Linux?
    Model answer

    lspci -nn and look for class [0108], or nvme list plus /sys/class/nvme/nvme0/address. Report domain:bus:device.function and vendor:device.

  2. Intermediate What is the difference between DevCap MaxPayload and DevCtl MaxPayload?
    Model answer

    DevCap is what the function supports; DevCtl is what software programmed. Only the programmed value governs the maximum TLP payload the function may send.

  3. Advanced An SSD is fine on one server but shows (downgraded) on another identical server. Walk through your triage.
    Model answer

    Compare both ends' LnkCap/LnkSta/LnkCtl2 on both servers; check BIOS/firmware versions and slot configuration; check AER counters for RxErr/BadTLP; swap the drive between servers to see whether the problem follows the drive or the slot; if it follows the slot, capture link training with an analyzer or use lane-margining tools if supported.

  4. Senior What can config-space inspection never tell you, and how do you close that gap?
    Model answer

    Temporal behavior (event counts, Recovery frequency, latency), traffic contents, and anything inside the controller. Close it with AER/telemetry counters, NVMe logs, block-layer tracing, and a protocol analyzer with a well-defined trigger.

Summary. lspci/sysfs reveal identity, topology, negotiated link parameters, programmed payload sizes, interrupt mode and latched errors. They prove static state, not dynamic behavior. setpci reads are safe; writes are a lab-only, expert activity. Next: the NVMe controller itself, through nvme-cli.

70 Linux NVMe Inspection

70.1 Why this chapter exists

PCIe inspection tells you the road is open. NVMe inspection tells you what the controller says about itself: who it is, what it supports, how healthy it is, and what errors it has recorded. nvme-cli wraps the admin commands you studied earlier (Identify 06h, Get Log Page 02h, Get Features 0Ah) and sends them through the kernel driver's passthrough interface. Most of what you need is read-only; a small but dangerous subset of nvme-cli commands destroys data or changes firmware.

  • Beginner: list controllers and namespaces; map nvme0, nvme0n1, the PCIe BDF and the subsystem.
  • Intermediate: interpret the key Identify Controller and Identify Namespace fields (MDTS, SQES/CQES, NN, ONCS, LBA formats) and the SMART / Health log.
  • Advanced: read the Error Information log and correlate its SQID/CID entries with kernel timeouts; read features (Number of Queues, Interrupt Coalescing, APST).
  • Senior: classify every nvme-cli subcommand as read-only, state-changing, or destructive before running it.
  • Validation: snapshot NVMe health before/after a test and compute deltas.

Prerequisites: admin queue and admin opcodes; Identify; Get Log Page; Features; namespace concepts; Chapter 69.

70.2 Story

🧒 Kid analogy

The library (the SSD) has a front desk (the controller). You can ask the desk polite questions on special "office" forms: "What is your name? How many rooms do you have? How tired are you? What went wrong recently?" The desk answers on paper and nothing in the library changes. But some office forms say things like "throw away every book and repaint the shelves" — those forms (format, sanitize) are real, and the desk will obey them. Learn to read the form's title before you hand it over.

🧩 Where the analogy breaks

A real librarian might ask "are you sure?"; the controller does not. nvme-cli may print a warning or ask for confirmation for some destructive commands version, but you must not rely on that. Also, "polite questions" are not always free: an admin command still occupies the admin queue, and on a hung controller even an Identify can time out.

70.8 Interpreting the Error Information log

Each entry carries an error_count (a unique, incrementing number), sqid, cmdid, status_field, parm_err_location (byte/bit in the command that caused the error, if applicable), lba, nsid and vendor info. The log is a circular buffer of a device-specific depth (Identify Controller elpe = entries minus one). Entries with error_count 0 are empty.

🐞 Correlation recipe

The kernel's timeout message names the queue (QID) and tag/command id. The error log names sqid and cmdid. If they match and the status field is, for example, Unrecovered Read Error, you have tied a host-visible failure to a controller-reported media event. If the error log is empty, the controller did not consider the command errored — that pushes suspicion toward the transport (lost doorbell, lost completion, interrupt path). Note that the Linux driver's CID encoding may include a generation counter in upper bits on newer kernels version, so match on what the log line actually prints.

70.9 Commands that change state or destroy data

⚠️ DESTRUCTIVE — read before you type

nvme format (Format NVM, 80h) erases every LBA in the namespace — or, depending on the controller's format attributes, all namespaces. nvme sanitize (84h) irreversibly destroys all user data in the entire NVM subsystem and may run for a long time and continue after a reset. nvme write, write-zeroes, write-uncor, dsm --ad (deallocate/TRIM) overwrite or discard data. nvme delete-ns / create-ns destroy namespaces. nvme fw-download + fw-commit change firmware (a bad image or interrupted activation can brick the drive). nvme reset, subsystem-reset and set-feature change live controller state. Never run these on a production system or on a drive holding data you want, and never on a device addressed as nvmeX without verifying its serial number first.

    The failing command was on the admin queue — often a tool probing an unsupported log or feature, not your I/O workload.

71 Kernel Logs: dmesg and journalctl

71.1 Why this chapter exists

Config space and NVMe logs are snapshots. The kernel log is a timeline: enumeration, driver probe, link events, AER reports, NVMe timeouts, aborts, resets, removals. For most field failures it is the only evidence you will ever get, so you must learn to read it precisely — and to know which events it can never contain.

  • Beginner: retrieve kernel messages for the current and previous boot; filter for nvme, pcieport, AER.
  • Intermediate: recognize the message families for link errors, AER, NVMe timeouts, aborts, resets and controller failure.
  • Advanced: order events into a causal hypothesis chain without confusing correlation for causation.
  • Senior: know the blind spots: firmware-first error handling, rate-limited messages, lost logs on crash, timestamp caveats.
  • Validation: automatically extract a failure timeline (Lab 10) from a saved log.

Prerequisites: Chapter 69, Chapter 70, AER and the Linux NVMe driver's timeout path from earlier Parts.

🧒 Kid analogy

The kernel log is the ship's logbook. The captain writes "12:03 — heard a strange noise from engine 2", "12:05 — engine 2 restarted". The logbook only has what the crew noticed and bothered to write down. If the noise happened while everyone was asleep, or the page got wet, it is not in the book — but the noise still happened.

🧩 Where the analogy breaks

Some "crew members" (platform firmware in firmware-first error handling) may fix a problem and never tell the captain. Some messages are rate-limited, so the 1,000th identical noise is not written down. And the logbook itself lives in RAM: a hard hang can lose the last pages unless the journal is persistent or a serial/netconsole is attached.

71.3 Message families you must recognize

The excerpts below are illustrative and synthetic, written in the general shape of messages printed by recent Linux kernels. Exact wording varies by kernel version and driver version; never grep for an entire sentence in production tooling — match stable fragments.

A. Link bandwidth / training

nvme 0000:01:00.0: 15.752 Gb/s available PCIe bandwidth, limited by 8.0 GT/s PCIe x2 link at 0000:00:01.0 (capable of 63.012 Gb/s with 16.0 GT/s PCIe x4 link)

Meaning: at probe time the kernel compared the device's capability with the narrowest link on the path and found a limitation, naming the limiting port. Proves: a static bandwidth limit exists at probe time. Cannot prove: why (platform design vs failed lanes) or whether it changes later.

B. Link errors (AER correctable)

pcieport 0000:00:01.0: AER: Corrected error received: 0000:01:00.0
nvme 0000:01:00.0: PCIe Bus Error: severity=Corrected, type=Physical Layer, (Receiver ID)
nvme 0000:01:00.0:   device [abcd:0001] error status/mask=00000001/00002000
nvme 0000:01:00.0:    [ 0] RxErr

Meaning: the device's receiver saw a physical-layer error (e.g. framing/decode problems) that the link recovered from, typically via Data Link Layer replay. Status bit 0 = Receiver Error. BadTLP (bit 6) and BadDLLP (bit 7) point at LCRC failures; Rollover (8) and Timeout (12) at the replay mechanism. Proves: link-level errors occurred and were corrected. Cannot prove: data loss (there was none at the transaction level) or which side's transmitter is weak — the reporting side is the receiver.

C. AER uncorrectable

pcieport 0000:00:01.0: AER: Uncorrected (Non-Fatal) error received: 0000:01:00.0
nvme 0000:01:00.0: PCIe Bus Error: severity=Uncorrected (Non-Fatal), type=Transaction Layer, (Requester ID)
nvme 0000:01:00.0:   device [abcd:0001] error status/mask=00004000/00000000
nvme 0000:01:00.0:    [14] CmpltTO
nvme 0000:01:00.0: AER:   TLP Header: 20000010 01002aff 00000001 10010080

Meaning: bit 14, Completion Timeout, detected by the SSD acting as requester: a read it issued (here the logged header decodes — with Lab 2 — as a 64-byte MRd, tag 0x2a, to an address that may be an SQ slot) never completed. When a TLP header is logged, decode it: it is often the best single clue in the whole log. Non-fatal uncorrectable errors are typically followed by the driver's error-recovery callbacks; fatal ones by a link reset.

D. NVMe timeout, abort, reset

nvme nvme0: I/O tag 23 (1017) opcode 0x2 (Read) QID 3 timeout, aborting
nvme nvme0: I/O tag 23 (1017) opcode 0x2 (Read) QID 3 timeout, reset controller
nvme nvme0: Abort status: 0x0
nvme0n1: I/O Cmd(0x2) @ LBA 123456, 8 blocks, I/O Error (sct 0x3 / sc 0x71)
blk_update_request: I/O error, dev nvme0n1, sector 123456 op 0x0:(READ) flags 0x0 phys_seg 1 prio class 0

Meaning: the host's timer (io_timeout) expired for a read on hardware queue 3. The driver's escalation (abort the command, then reset the controller) is version-dependent version. The "I/O Error" line with SCT/SC is printed by newer kernels on error completions; SCT 3h is Path Related status; SC 71h in that type is "Command Aborted By Host", which the Linux driver assigns itself to requests it cancels during a controller reset verify against your kernel source — so this line may describe the host's cleanup, not something the device reported. Always check whether a status came from a real CQE or was synthesized by the driver. Proves: the host did not observe a completion in time. Cannot prove: whether the device never received the command, received it and stalled, posted a CQE that the host missed, or raised an interrupt that was lost. That is exactly the ambiguity Labs 6–8 and the analyzer resolve.

E. Controller failure / surprise removal

nvme nvme0: controller is down; will reset: CSTS=0xffffffff, PCI_STATUS=0xffff
nvme nvme0: Device not ready; aborting reset, CSTS=0x1
nvme nvme0: Removing after probe failure status: -19
nvme 0000:01:00.0: frozen state error detected, reset controller
pcieport 0000:00:01.0: pciehp: Slot(1): Link Down
pcieport 0000:00:01.0: DPC: containment event, status:0x1f01 source:0x0000
  • CSTS=0xffffffff, PCI_STATUS=0xffff: register reads returned all-ones — the device is not answering on the link at all (link down, device reset, power loss). This is a PCIe-layer observation, not an NVMe status.
  • CSTS=0x1 while trying to reset: RDY stuck at 1 — controller not responding to CC.EN=0 within CAP.TO; firmware hang suspicion.
  • CSTS bit 1 (CFS, Controller Fatal Status) set: the controller itself declared a fatal internal error.
  • frozen state error detected: the PCI error-recovery framework told the NVMe driver the channel is frozen (typically after a fatal AER or DPC event).
  • pciehp ... Link Down, DPC: containment event: hot-plug saw link loss; Downstream Port Containment isolated the port after an uncorrectable error.

💡 Senior insight — create a sync marker

To align a kernel log with an analyzer capture, generate a recognizable, harmless event on the link and log it at the same time: for example a setpci read of a specific register (appears as a configuration read on the analyzer) immediately followed by echo MARK-1 | sudo tee /dev/kmsg. The configuration read in the trace and the MARK-1 line in dmesg anchor both clocks to within the latency of the script.

Quiz

  1. Why prefer monotonic timestamps over dmesg -T when correlating?

    Answer

    -T converts using an assumed boot time and can drift across suspend/resume; monotonic seconds are what the kernel actually recorded.

  2. CSTS=0xffffffff. Is this an NVMe status?

    Answer

    No. It means MMIO reads returned all-ones: the device is not responding on PCIe (link down/reset/power). Investigate the PCIe layer first.

  3. Corrected RxErr is reported by device 01:00.0. Whose receiver saw the error?

    Answer

    01:00.0's own receiver (downstream direction traffic). The weak side could be the port's transmitter, the channel, or the device's receiver.

Interview questions

  1. Intermediate The log shows an NVMe timeout but no AER messages. What does that exclude?
    Model answer

    Very little. It excludes OS-reported AER errors — not firmware-first handled errors, masked errors, or non-PCIe causes (controller hang, lost interrupt, host software). It shifts but does not settle suspicion.

  2. Senior How do you preserve kernel evidence for a hang that requires a power cycle?
    Model answer

    Persistent journal, serial console or netconsole, pstore/ramoops where available, and an external analyzer or BMC log; also capture NVMe telemetry logs after reboot if supported.
