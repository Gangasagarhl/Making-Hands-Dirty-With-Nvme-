46 AER — Advanced Error Reporting (Deep-Dive Module: AER)

46.1 Why this chapter exists

Baseline PCIe error reporting (four bits in Device Status) tells you that a correctable, non-fatal, fatal or unsupported-request error happened. AER tells you which error, which was first, how it was classified, and — crucially — logs the header of the offending TLP, which turns an anonymous error into a forensic artefact: requester, tag, address, length, type. In NVMe debugging the AER header log is often the single piece of evidence that ties a PCIe error to a specific NVMe queue or buffer.

46.2 Learning objectives

  • Beginner: list the AER registers and what each holds.
  • Intermediate: decode Uncorrectable/Correctable Status and Mask values bit by bit; explain Severity.
  • Advanced: decode a 4-DW Header Log into a TLP and map it to an NVMe action; use First Error Pointer; read root port Root Error Status and Error Source Identification.
  • Senior: plan masking/severity policy; know when AER evidence is incomplete (masked, overflow, cleared by OS).
  • Trace-analysis: match an AER header log to a TLP in a capture.
  • Debugging: read AER from Linux logs/sysfs and lspci safely.
  • Validation: design error-injection validation (e.g. via platform error injection or aer-inject on test systems).

46.3 Kid story and analogy boundary

🧒 Kid analogy

Every room in the house has a logbook by the door. When something goes wrong, the room ticks a box on a checklist ("muddy letter", "letter for a person who doesn't live here", "nobody answered my question"). Some boxes are taped over (masked) so ticking them doesn't call anyone. Each box also says whether it's a "call the parent now" box or "just tell them later" (severity). The room photocopies the envelope of the bad letter (header log) and writes which box was ticked first. The parent's room (root port) keeps a master logbook: "I got a message from room 2:00.0 about a serious problem".

🧩 Analogy boundary

Represents: status, mask, severity, header log, root collection. Hides: that there's only room for one (or a few, if multiple-header recording is supported) envelope photocopies; that status bits are sticky (survive some resets) and RW1C (cleared by writing 1); that masking a bit still records status in many cases but suppresses signalling. Misleading when: you assume the logbook is complete — OS drivers clear AER status after reading it, so by the time you run lspci the evidence may be gone.

On many servers AER is firmware-first: the BIOS/UEFI owns the AER registers (OS not granted control via _OSC), handles errors, and reports to the OS through APEI/GHES records. 46.7 Decoding the Header Log

The Header Log holds the first 4 DW of the TLP header (for a 3DW header, DW3 is undefined/zero). Decode DW0 with the standard fields:

Requests DW1: Requester ID [31:16], Tag [15:8], Last DW BE [7:4], First DW BE [3:0]. DW2 (3DW) address [31:2]; for 4DW, DW2 = address [63:32], DW3 = address [31:2]. Completions DW1: Completer ID [31:16], Completion Status [15:13] (000 SC, 001 UR, 010 CRS, 100 CA), BCM [12], Byte Count [11:0]. DW2: Requester ID [31:16], Tag [15:8], Lower Address [6:0].

Worked decode 1 — Poisoned completion seen by the SSD

Device 02:00.0 AER Uncorrectable Status = 0x0000_1000   (bit 12 Poisoned TLP)
Header Log: 4A004010 00000040 02002A00 00000000

DW0 = 0x4A004010: byte 0 = 4Ah → CplD; bit 14 EP = 1 (poisoned); Length = 0x010 = 16 DW = 64 bytes. DW1 = 0x0000_0040: Completer ID 0000 (root complex), status 000 (SC), Byte Count 0x040 = 64. DW2 = 0x0200_2A00: Requester ID 0x0200 = 02:00.0 (the SSD itself), Tag 0x2A, Lower Address 0. Interpretation: a 64-byte read by the SSD came back poisoned — exactly an SQE fetch size (or a 64-byte PRP list/data chunk). Correlate tag 0x2A at that time in a trace, or the SQ base address, to identify which. Cause direction: host memory or RC (the poison was applied upstream). Next evidence: host MCE/EDAC logs.

Worked decode 2 — Malformed TLP at the root port

Root port 00:01.1 AER Uncorrectable Status = 0x0004_0000 (bit 18 Malformed TLP), severity fatal
Header Log: 60000040 020000FF 00000001 40000000

DW0: byte 0 = 60h → MWr 4DW; Length 0x040 = 64 DW = 256 bytes. DW1: Requester 0x0200 (the SSD), Tag 00 (writes may carry any tag), BEs FF. Address = 0x1_4000_0000 → data buffer region (read data DMA). Interpretation: 256-byte write rejected as malformed — check root port MPS: if 128, the SSD was misconfigured with MPS 256 (or ignored its setting). Next evidence: lspci -vvv DevCtl MaxPayload on both ends.

Worked decode 3 — Unsupported Request at the SSD

Device 02:00.0 AER Uncorrectable Status = 0x0010_0000 (bit 20 UR)
Header Log: 00000001 00000C0F F7A0001C 00000000

DW0: MRd 3DW, Length 1 DW. DW1: Requester 0x0000 (host RC), Tag 0x0C, First BE F. DW2: address 0xF7A0_001C = BAR0 + 1Ch = CSTS. Interpretation: the host read CSTS and the SSD answered UR — the SSD was not accepting memory requests (e.g. in D3hot, Memory Space Enable clear, or mid-reset). The host saw a UR completion → returned all-ones to the CPU → driver sees CSTS = 0xFFFFFFFF. Symptom or cause? Symptom of a power/reset state problem.

Worked decode 4 — Completion Timeout

Status bit 14 set; Header Log usually not meaningful for CTO (no received TLP). Newer components may advertise Completion Timeout Prefix/Header Log Capable and log the request header (version). Without it, correlate by time and by the device's outstanding request types — a trace is needed.

Reading the lines: "status/mask=00004000/00400000" → status bit 14 (Completion Timeout); mask bit 22 (Uncorrectable Internal Error masked by default). "00000001/0000e000" → Receiver Error; mask bits 13–15 default-masked. The "(Requester ID)" / "(Receiver ID)" annotation tells you whether the logging agent was acting as requester or receiver. Can prove: which error bits were set at the time the OS read them, source device. Cannot prove: errors that were masked, cleared by firmware-first handling, or that occurred on devices without AER; which NVMe command was affected (needs header/trace correlation).

⚠️ Safety

setpci can write AER mask/severity registers; doing so on a production system can hide real errors or turn a correctable condition into a system-wide fatal recovery. Use read-only lspci and sysfs. Tools like aer-inject require a kernel module and are for test systems only.

46.11 Labs

🧪 Lab 46.1 (beginner) — Read AER state safely SAFE

Objective: locate AER in lspci and sysfs. Procedure: run §46.8 commands for the NVMe device and its root port (lspci -tv to find it). Observations: is AER present? which bits set? counters? Questions: are any errors masked that you'd want unmasked?

Solution

Most systems show zeros. Default masks: Uncorrectable Internal Error; correctable Advisory Non-Fatal, Corrected Internal, Header Log Overflow. Counters in sysfs accumulate since boot even after status is cleared.

🧪 Lab 46.2 (intermediate) — Decode status/mask words SAFE

Given: UE status 0x0010_4000, CE status 0x0000_1041. Procedure: decode.

Solution

UE: bit 14 Completion Timeout, bit 20 Unsupported Request. CE: bit 0 Receiver Error, bit 6 Bad TLP, bit 12 Replay Timer Timeout. Interpretation: noisy link plus at least one transaction failure; ask whether the CTO followed a retrain.

🧪 Lab 46.3 (advanced) — Header log decoding drill SAFE

Given: (a) 4A000010 00000040 02001100 00000000 logged as Unexpected Completion at 02:00.0; (b) 40000001 0000000F F7A01018 00000000 logged as UR at 02:00.0.

Solution

(a) CplD, 16 DW, not poisoned; Completer 0000, BC 64; Requester 0200, tag 0x11. The SSD got a completion for tag 0x11 it no longer expected — typical after the device already timed out that request (late completion) → correlate with an earlier CmpltTO. (b) MWr 3DW, 1 DW, Requester 0000, tag 00, First BE F, address 0xF7A0_1018 = SQ3 tail doorbell. A doorbell write was rejected as UR: the device was not accepting memory writes (in reset/D3hot/MSE clear) → the doorbell was lost; expect an NVMe timeout later.

Questions: 1. What error occurred? 2. Which TLP is implicated? 3. Which requester? 4. Which completer? 5. Symptom or cause? 6. What additional evidence is needed?

Solution

1. SSD A reported a Completion Timeout; the switch downstream port 02:00.0 reported an Unexpected Completion. 2. The SQE-fetch MRd with tag 0x1F (16 DW) from 03:00.0. The header logged at 02:00.0 is a CplD with Requester ID 0x0300 and tag 0x1F, byte count 64 — the completion for that very request. 3. Requester: 03:00.0 (SSD A). 4. Completer: the root complex (Completer ID 0000). 5. The CTO is a symptom. The completion did come back but was rejected at the switch's downstream port as unexpected — so it never reached the SSD. Why would a switch port consider a completion for 03:00.0 unexpected? Possibilities: the completion arrived after the port considered the request expired (unlikely — switches don't time out), or more plausibly the completion was routed by ID to a bus number that doesn't match the port's secondary/subordinate bus range at that moment — e.g. bus numbers were reprogrammed (hot-plug rescan) or the completion carried a corrupted Requester ID. Given the logged Requester ID 0x0300 is correct, check the port's bus number registers and any recent re-enumeration. 6. Evidence needed: switch port config (secondary/subordinate bus), timeline of hot-plug/rescan events, a capture on the upstream side of the switch to see when the CplD arrived, root port AER (0x24 = ERR_FATAL/NONFATAL received + non-fatal messages), switch vendor counters. Confidence in "switch-side routing/state problem rather than SSD fault": medium.

Extension: rewrite the conclusion if the logged Requester ID had been 0x0400 (SSD B).

46.12 Interview questions

Interview questions

  1. Beginner What does AER add over baseline error reporting?
    Model answer

    Per-error status, masks, severity, first error pointer, header log, root error collection.

  2. Beginner What is the Header Log?
    Model answer

    The first 16 bytes of the header of the TLP associated with the first logged uncorrectable error.

  3. Beginner How do you clear an AER status bit?
    Model answer

    Write 1 to it (RW1C).

  4. Beginner Where are root-level AER registers?
    Model answer

    Root ports/RCECs: Root Error Command, Root Error Status, Error Source Identification.

  5. Beginner What's the difference between NVMe AER and PCIe AER?
    Model answer

    NVMe Asynchronous Event Request (command) vs PCIe Advanced Error Reporting (capability).

  6. Intermediate What does severity control?
    Model answer

    Whether an uncorrectable error is signalled as ERR_FATAL or ERR_NONFATAL.

  7. Intermediate Why might the header log be zero for a CTO?
    Model answer

    No TLP was received; CTO header logging is an optional newer capability.

  8. Intermediate What is First Error Pointer?
    Model answer

    Bit index of the first uncorrectable error recorded; ties the header log to that error.

  9. Intermediate What does "Multiple ERR_COR Received" mean?
    Model answer

    More correctable messages arrived after the first was logged; the source ID only identifies the first.

  10. Intermediate What is firmware-first?
    Model answer

    Platform firmware owns AER handling and reports through APEI/GHES.

  11. Advanced Decode header DW0 0x4A004010.
    Model answer

    CplD, EP=1, 16 DW.

  12. Advanced Why would masking Surprise Down be done?
    Model answer

    During intentional link-down operations (hot-plug, resets) to avoid fatal reporting of an expected event.

  13. Advanced What are Linux PCI error recovery callbacks?
    Model answer

    error_detected, mmio_enabled, slot_reset, resume (and reset_prepare/done for resets).

  14. Advanced How does DPC relate to AER?
    Model answer

    DPC uses uncorrectable error detection at a downstream port to disable the link and contain errors; AER still provides details.

  15. Advanced How do you map a header log to an NVMe command?
    Model answer

    Requester/tag/address → SQ/CQ/PRP region from address map → slot → CID via SQE or trace.

  16. Senior What's your policy for correctable error thresholds?
    Model answer

    Rate-based alerting per link, correlate with temperature/ASPM/speed, schedule maintenance before fatal; avoid per-event paging.

  17. Senior Why is AER evidence often incomplete?
    Model answer

    Masking, firmware-first, OS clears status, single header slot, first-source-only, devices without AER.

  18. Senior How do you validate AER handling?
    Model answer

    Error injection (platform EINJ, aer-inject, analyzer/exerciser injection) on test systems; verify logging and recovery paths.

  19. Senior Two devices report errors simultaneously. What do you suspect?
    Model answer

    Common upstream component (switch, root port, power, clock).

  20. Senior When would you change severity defaults?
    Model answer

    Rarely; e.g. to downgrade a known benign error on specific hardware after root-cause, with documented risk.

47 Error Correlation Across Layers

47.1 Why this chapter exists

A user says "the SSD is broken". The SSD vendor says "our drive is fine". The platform team says "PCIe is healthy". Everyone may be honest and wrong, because each looked at one floor. This chapter trains you to distinguish software issue vs driver issue vs NVMe issue vs PCIe transaction issue vs link issue vs firmware issue vs media issue with explicit decision trees, an error correlation matrix, a "what would you capture" ladder, multi-layer failure cases, and a safe error-injection lab.

47.2 Learning objectives

  • Assign any error observation to a layer with a stated confidence.
  • Use decision trees starting from the five common symptoms.
  • Know what each evidence source can and cannot prove.
  • Diagnose multi-layer failures where one layer looks healthy and another fails.
  • Run simulated error injection and diagnose the results.

47.3 Analogy

🌍 Analogy

A package didn't arrive. Was the order form wrong (software), did the clerk mistype it (driver), did the warehouse reject it (NVMe), did the courier lose the parcel at a depot (PCIe transaction), was the road flooded (link), did the warehouse robot crash (firmware), or was the item itself broken on the shelf (media)? Each has a different paper trail: order history, clerk's notes, warehouse rejection slip, courier tracking, road reports, robot logs, inventory quality reports.

🧩 Where the analogy breaks

In real systems the layers share timing and resources: a flooded road (link errors) can make the warehouse robot (firmware) hit an internal timeout and report "internal error" — so a firmware symptom can have a link cause. Layer boundaries are where causality crosses, not where it stops.

47.6 Decision trees

Tree A — "I/O timed out"

I/O timeout (driver)
├─ Read CSTS
│   ├─ 0xFFFFFFFF ──► device unreachable ─► check LnkSta, AER/DPC on root port, lspci presence
│   │                   ├─ link down / Surprise Down ─► LINK or POWER (or intentional reset)
│   │                   └─ link up, config reads OK, BAR reads all-ones ─► Memory Space disabled / D3 / reset ─► DRIVER/PM
│   ├─ CFS=1 ─► FIRMWARE (controller fatal) ─► reset, collect telemetry
│   └─ RDY=1, CFS=0 ─► controller alive
│        ├─ CQE present in memory with valid phase? (driver debug / timeout handler message)
│        │    └─ yes ─► INTERRUPT path ─► MSI-X mask/PBA, affinity, remapping (DRIVER/PLATFORM)
│        ├─ device AER CmpltTO? ─► PCIe TRANSACTION (host didn't answer device reads) ─► IOMMU, switch
│        ├─ async event on admin CQ (invalid doorbell)? ─► DRIVER (doorbell offset/value)
│        └─ nothing ─► FIRMWARE hang on command or MEDIA stall ─► vendor telemetry, retry same LBA

Tree B — "Command returned an error status"

Non-zero status
├─ SCT 0 (generic)
│   ├─ 01h/02h/0Bh/0Ch/13h ─► HOST (software/driver) ─► Error log PEL, Identify capabilities
│   ├─ 03h ─► DRIVER (CID reuse)
│   ├─ 04h ─► TRANSPORT ─► AER, IOMMU
│   ├─ 06h ─► FIRMWARE (± transport) ─► telemetry, AER internal errors
│   ├─ 07h/08h ─► HOST ACTION (abort/teardown) ─► why was it aborted? (timeout upstream)
│   └─ 80h–84h (NVM) ─► HOST/CONFIG (range, capacity, reservations, format state)
├─ SCT 1 ─► HOST misuse of a specific command (check command semantics)
├─ SCT 2 ─► MEDIA (81h/80h) or DATA INTEGRITY (82h–84h: host PI vs device)
├─ SCT 3 ─► PATH (multipath/ANA)
└─ SCT 7 ─► VENDOR ─► vendor docs

Tree C — "Wrong data, success status"

Corruption with success
├─ PI enabled and no E2E errors? ─► device path likely clean ─► HOST: buffer reuse, IOMMU lifetime, app bug
├─ Same LBA reads differently over time? ─► MEDIA/FIRMWARE (silent corruption) ─► rare; capture data MWr payloads
├─ Corruption pattern = stale previous contents? ─► CQE before data (ordering/RO), or ignored error status ─► check RO, check status handling
└─ Corruption = shifted/other LBA data? ─► wrong PRP/LBA ─► DRIVER/FIRMWARE ─► decode SQE from trace

47.9 Error-injection lab (simulated)

🧪 Lab 47.1 — Simulated error injection and diagnosis SAFE

Objective: inject faults into a model of the end-to-end read and practise diagnosing them from the resulting synthetic evidence — without touching hardware. Prerequisites: Python 3. Setup: the simulator below produces an event list (simplified event model) and evidence (AER, status, logs) for a single 4 KiB read under a chosen fault.

FAULTS = ["none", "missing_completion", "invalid_opcode", "invalid_prp",
          "unsupported_request", "completion_timeout", "malformed", "link_recovery"]

def simulate(fault):
    ev, aer, status, log = [], {}, None, []
    t = 0.0
    def e(dt, d, typ, info):
        nonlocal t; t += dt; ev.append((round(t, 2), d, typ, info))
    e(0, "dn", "MWr", "SQ3 tail doorbell")
    if fault == "unsupported_request":            # device not accepting memory requests
        aer["dev"] = "UnsupReq, header=MWr 3DW BAR0+1018h"
        log.append("t=30s nvme: I/O timeout QID3 (illustrative)")
        return ev, aer, status, log
    e(0.6, "up", "MRd", "SQE fetch tag 0x11")
    if fault in ("missing_completion", "completion_timeout"):
        aer["dev"] = "CmpltTO"
        if fault == "missing_completion":
            log.append("IOMMU fault: read 0x123401080 not mapped (illustrative)")
        log.append("t=30s nvme: I/O timeout QID3 (illustrative)")
        return ev, aer, status, log
    e(0.9, "dn", "CplD", "tag 0x11 SQE" + (" opcode 0xFF" if fault == "invalid_opcode" else ""))
    if fault == "invalid_opcode":
        status = "SCT0/SC01h DNR"
    elif fault == "invalid_prp":
        status = "SCT0/SC13h PRP Offset Invalid DNR"
    else:
        if fault == "link_recovery":
            e(10, "--", "LTSSM", "Recovery entered (REPLAY_NUM rollover)")
            aer["dev"] = "Rollover, BadTLP (correctable)"
        e(60, "up", "MWr x16", "data")
        if fault == "malformed":
            aer["rootport"] = "MalfTLP fatal, header=MWr 4DW len 64DW"
            log.append("AER fatal -> link reset, I/O error (illustrative)")
            return ev, aer, status, log
        status = "success"
    e(0.1, "up", "MWr", "CQE " + status)
    e(0.05, "up", "MWr", "MSI-X")
    e(3, "dn", "MWr", "CQ3 head doorbell")
    return ev, aer, status, log

f = random.choice(FAULTS)
ev, aer, status, log = simulate(f)

Observations: keep a table of your diagnoses vs the truth.

Questions: Which two faults produce nearly identical evidence? What extra evidence separates them? Why does "invalid_opcode" produce no data TLPs? Why does "link_recovery" still end with success?

Solution

"missing_completion" and "completion_timeout" both show an MRd without CplD and CmpltTO at the device; only the IOMMU fault log (or a capture at the RC side) separates "host refused" from "completion lost in fabric". "invalid_opcode": controller rejects at parse, posts CQE with SCT0/01h — no data phase; layer = host/driver (or a corrupted SQE — check the CplD payload against what the driver wrote). "invalid_prp": host/driver bug, DNR. "unsupported_request": the doorbell itself was rejected (device in D3hot/reset/MSE clear) — no fetch at all; first abnormal event is the UR logged against the doorbell; timeout is a symptom 30 s later. "malformed": data MWr exceeded root port MPS → fatal at root port → link reset; cause is configuration. "link_recovery": correctable; replays/retrain recovered transparently — I/O succeeded with added latency; layer = link; evidence is the correctable counters.

Extension: add faults "poisoned_cpld", "msix_masked" and "cqe_before_data (RO bug)"; generate an ambiguous variant where the capture misses the upstream direction, and practise negative-evidence phrasing.

47.10 Worked example: the 3 a.m. page

Observations (synthetic): database reports I/O errors at 03:12:44; dmesg shows "I/O … QID 7 timeout, aborting", then an abort attempt that itself times out, then a controller reset (exact message wording is impl/kernel-version dependent); after reset the drive works. AER: root port logged Receiver Errors (correctable) at a low rate for weeks; no uncorrectable errors were logged at or around 03:12:44. SMART clean. LnkSta Gen4 x4.

Analysis: timeline T0 (weeks of RxErr — background), T1 03:12:14 (30 s before timeout — the command was submitted), T2 timeout, T3 abort, T4 reset recovers. First abnormal event in the evidence: the command at 03:12:14 that never completed. Was it fetched? Unknown — no trace (negative evidence: we cannot say it wasn't). Hypotheses: (a) firmware hang on that command (reset fixes; no CFS though), (b) lost interrupt (CQE present? — the driver would have reported completion in the timeout handler; it didn't), (c) lost doorbell due to link error (RxErr on the downstream direction would cause replay, not loss — the DLL guarantees delivery unless the link fails). Conclusion: most likely firmware (medium confidence); background RxErr probably unrelated but should be fixed. Next evidence: vendor telemetry captured after the event (Telemetry Host-Initiated log), firmware version vs known errata, and enabling nvme tracepoints for the next occurrence.

Quiz

  1. CSTS reads 0xFFFFFFFF. Which layer first?

    Answer

    PCIe/link/power/reset state — the MMIO read itself failed.

  2. Status 04h Data Transfer Error — which evidence next?

    Answer

    AER on device and ports, IOMMU faults.

  3. Corruption with PI enabled and no E2E errors suggests?

    Answer

    Host-side problem (buffer lifetime, app), since device path is PI-protected.

  4. Can a link problem cause an NVMe Internal Error status?

    Answer

    Yes — e.g. firmware internal timeouts triggered by link stalls; correlate timing.

Interview questions

  1. Intermediate How do you tell a driver bug from a device bug on an invalid-field status?
    Model answer

    Error log Parameter Error Location + decode the SQE as fetched (trace CplD) vs what the driver intended; if the fetched SQE is valid per spec, device bug.

  2. Advanced Walk through the decision tree for timeouts.
    Model answer

    CSTS all-ones vs CFS vs alive; CQE present → interrupts; AER CTO → transport; async events → doorbell; else firmware/media.

  3. Senior Describe a case where every layer looked healthy yet data was lost.

  4. Senior How do you avoid blaming the first visible error?

    Build an expected vs observed timeline, look backwards for earlier deviations, state confidence, apply negative-evidence discipline.
