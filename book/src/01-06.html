PART III

Why NVMe Exists

Every interface is an answer to a problem. NVMe's problem was simple to state and hard to solve: flash had become parallel and fast, and the interfaces in front of it were single-file and slow. This Part tells the story from SATA and AHCI through the first proprietary PCIe SSDs to NVMe 1.0, the 2.0 refactor and the August 2026 release — and quantifies, with formulas you can check, exactly what changed.

3 From SATA/SAS to NVMe

Why this chapter exists

Engineers who know why a protocol is shaped the way it is can predict its behaviour and its failure modes. NVMe's queue pairs, doorbells, phase tags, fixed-size entries and per-queue interrupts are not arbitrary; each removes a specific cost that AHCI and SATA imposed. Knowing those costs also tells you what NVMe still cannot fix — media latency, host software overhead, and interrupt handling — which is where real performance work happens.

Learning objectives

  • Describe AHCI's architecture: one command list of 32 slots per port, PRD tables, FIS areas, port registers.
  • Explain command serialization, queue limits and CPU overhead in the SATA/AHCI path, with numbers.
  • State NVMe's queue limits precisely (up to 65,535 I/O queues; up to 65,536 entries each; admin queue up to 4,096 entries) and why a ring of N slots holds N−1 commands.
  • Compare per-command register-access cost of AHCI and NVMe and compute its CPU impact.
  • Compare SATA, SAS, NVMe/PCIe and NVMe-oF protocol stacks layer by layer.
  • Narrate the history SATA → AHCI → PCIe SSDs → NVMe → NVMe 1.x → NVMe 2.0 family → NVMe 2.4, labelling dates by confidence.
  • List NVMe's design goals and connect each to a mechanism you will study later.

Story

🧒 Kid analogy — the restaurant

An old restaurant has one order spike by the kitchen door that holds 32 tickets. Every waiter in the restaurant must queue at that spike, and only one waiter may touch it at a time. After pinning a ticket, the waiter must also lean into the kitchen and ask the cook a few questions (“Did you see my ticket? Which orders are ready?”) and wait for each answer. When food is ready, the cook rings one bell for the whole restaurant, and somebody has to go and find out whose food it is.

The new restaurant gives every waiter their own order rail and their own pickup shelf, each with room for thousands of tickets. A waiter clips tickets on their own rail, flips a little flag to say “new tickets up to here”, and walks away — no questions, no waiting. The cooks (dozens of them now) take tickets from all rails at once. When a dish is ready, the cook puts it on that waiter's shelf with the ticket number, and buzzes that waiter's own pager.

🧩 Where the analogy breaks

In NVMe the “cook” (controller) walks to the waiter's rail to fetch tickets — the tickets live in host memory, not in the kitchen. The “flag” is a doorbell register write. And dishes are delivered by the cook writing directly into the waiter's memory (DMA), not by handing a plate across a counter. The restaurant analogy also hides that cooks may finish orders out of order, which is why every ticket carries a command identifier.

Beginner explanation

SATA drives are controlled through a host-side chip called an AHCI controller. AHCI was designed in the era of hard disks, when a disk could handle a few hundred operations per second and nobody cared about a few microseconds of overhead. It offers one queue of 32 commands per drive, needs the CPU to read device registers to learn what finished, and funnels everything through a single shared structure. SSDs made the drive thousands of times faster, so the overhead that used to be invisible became the bottleneck. NVMe replaced the whole design with many deep queues in host memory, written without locks and signalled with a single register write.

3.2 AHCI — the Advanced Host Controller Interface

AHCI is a register-level interface specification (Intel, first released in 2004 version) for SATA host controllers. The AHCI HBA is itself a PCI function, class code 01h/06h/01h (mass storage, SATA, AHCI) verified. Its memory-mapped registers live in a BAR (ABAR). Per port it uses:

  • a command list of up to 32 command headers (“slots”) in host memory, each pointing to a command table containing the command FIS and a Physical Region Descriptor Table (PRDT) — AHCI's scatter-gather list;
  • a received-FIS area in host memory where the HBA deposits frames from the device;
  • port registers including PxCI (Command Issue — bit per slot), PxSACT (SATA Active — bit per NCQ tag), PxIS (Interrupt Status), PxIE (Interrupt Enable), and a global IS (Interrupt Status per port).

3.3 Command serialization and queue limitations

With AHCI, all CPU cores issuing I/O to one drive must allocate slots from the same 32-slot command list and update the same PxSACT/PxCI registers. The driver therefore serialises submission with a per-port lock. On a many-core server, cores contend on that lock and the cache lines holding the command list bounce between cores. The queue limit compounds the problem: at most 32 commands can be in flight per drive, and Little's law says

IOPSmax ≤ QDmax / Wmin
  • IOPSmax — upper bound on completions per second for one device
  • QDmax — maximum outstanding commands (32 for NCQ)
  • Wmin — minimum per-command latency (seconds)

With W = 80 µs: 32 / 80 µs = 400,000 IOPS as an absolute ceiling, before any overhead derived. A modern NVMe SSD can exceed 1,000,000 random-read IOPS, which at 80 µs requires at least 80 commands in flight — more than NCQ allows. (In practice SATA's 600 MB/s caps 4 KiB IOPS at ~146,000 anyway: 600×106 / 4096 derived.)

3.4 CPU overhead — the register-access cost

From §1.4: an uncached MMIO read stalls a core for a full round trip (~1 µs order impl); a write is posted. Compare the shape of a typical submit/complete cycle:

// AHCI-style (conceptual; real drivers differ in detail)
submit(cmd):
    lock(port)                          // serialise all cores
    slot = find_free_bit(issued_mask)   // shared 32-bit bookkeeping
    build command header + command table + PRDT in memory
    write PxSACT |= 1<<slot              // MMIO write (NCQ)
    write PxCI   |= 1<<slot              // MMIO write
    unlock(port)
irq():
    is   = read IS                      // MMIO READ  (which port?)
    pis  = read PxIS                    // MMIO READ  (why?)
    write PxIS = pis                    // MMIO write (ack, RW1C)
    sact = read PxSACT                  // MMIO READ  (which tags still active?)
    done = issued_mask & ~sact          // infer completions by difference
    write IS = is                       // MMIO write (ack)

// NVMe-style (conceptual)
submit(cmd):                            // per-CPU queue: no lock shared with other cores
    copy 64-byte SQE into sq[tail]; tail = (tail+1) % depth
    wmb(); write SQyTDBL = tail         // ONE posted MMIO write (can cover many commands)
irq():                                  // per-queue MSI-X vector, ideally on the submitting CPU
    while cq[head].phase == expected_phase:     // plain memory reads, cache-friendly
        complete(cq[head].cid, cq[head].status)
        advance head (flip expected_phase on wrap)
    write CQyHDBL = head                // ONE posted MMIO write per batch

NVM Express overview material from NVMe's introduction commonly summarised this as AHCI needing about four uncacheable register reads per command (on the order of 2,000 CPU cycles) versus none for NVMe uncertain — treat the exact counts as illustrative of a typical driver, not a protocol constant. The derived consequence is robust:

CPUstall = IOPS × R × tread
  • CPUstall — core-seconds per second spent stalled on MMIO reads (1.0 = one whole core)
  • IOPS — commands per second
  • R — MMIO reads per command
  • tread — stall per read (seconds)

1,000,000 IOPS × 4 reads × 0.7 µs = 2.8 cores doing nothing but waiting derived (synthetic tread). Interrupt batching reduces R per command, but the structure cannot reach zero. NVMe removes the term entirely from the fast path.

3.5 Latency

For HDDs, 10 µs of host-interface overhead was 0.1% of a 10 ms access. For a 70 µs flash read it is 14%; for low-latency media (SLC-class or storage-class memory with ~10 µs reads impl) it is half the total. NVMe shortens the path: no HBA, no SCSI/ATA translation layer, no register reads, interrupt delivered to the submitting core. What remains — the kernel block layer, the interrupt and context switch — is why polling modes and io_uring exist for the lowest-latency use cases.

📘 Specification — why a ring holds N−1

NVMe queues are circular. The queue is empty when head equals tail, and full when tail + 1 (modulo size) equals head. One slot always stays unused so that “full” and “empty” are distinguishable verified. A 1,024-entry queue holds at most 1,023 outstanding commands.

3.7 PCIe as the transport

PCIe was already the CPU's native high-speed I/O fabric, with lanes coming directly from the processor. Attaching flash directly to it removed the HBA and offered scalable bandwidth (x1 to x16, doubling per generation), full duplex, low latency, and a mature software model (enumeration, BARs, MSI-X) every OS already understood. The missing piece was a standard host interface, so one driver could run every PCIe SSD. Early PCIe SSDs (late 2000s) used proprietary interfaces and vendor drivers; competing standardisation paths included SATA Express (AHCI over PCIe) and SCSI Express (SCSI over PCIe, SOP/PQI). NVMe became the dominant one version.

3.10 Historical timeline

The story in one sentence: disks got an interface designed for disks; flash outgrew it; vendors bolted flash to PCIe with private drivers; the industry standardised one queue-based interface; then it grew features, transports and management until it needed to be split into a family of specifications.

The readable version of the story. In the disk era, AHCI was a sensible design: one drive could only do a few hundred operations per second, so a 32-slot queue and a few register reads per command cost nothing measurable. Flash broke every one of those assumptions within a few years. Vendors first attached flash directly to PCIe with their own interfaces — fast, but every product needed its own driver, and enterprises dislike unique drivers. A consortium of companies wrote a clean-sheet interface instead, designed around the costs we quantified above: never read a register on the fast path, give every core its own queues, make commands fixed-size, let completions arrive out of order. NVMe 1.0 shipped in 2011. Over the 1.x years it grew enterprise features (namespaces, reservations, multi-path, sanitize, power and thermal management), went beyond PCIe to fabrics, and gained a management interface. By 2021 the single document had become unwieldy and was refactored into a family. Each release since has added command sets, transports and management capabilities, up to the August 2026 set that this book uses as its baseline.

Hardware view

SATA SSD: chipset AHCI controller (a PCIe function), SATA PHY, cable or M.2 SATA, drive controller. NVMe SSD: CPU root port lanes (or chipset lanes), M.2/U.2/EDSFF connector, NVMe controller with PCIe endpoint, NVMe queue engine, DMA. One less controller and one less serial link in the data path. Note that an M.2 slot may be wired for SATA, PCIe, or both — the connector shape does not tell you the protocol.

Specification view

Worked example — sizing queue depth for a target

Target: 1.5 M random-read IOPS on one SSD whose loaded latency is 120 µs, from 16 cores.

  1. Little's law: required outstanding = 1.5×106 × 120×10−6 = 180 commands.
  2. Per core: 180 / 16 ≈ 12 outstanding per queue.
  3. With AHCI: impossible — 32 max total, and SATA bandwidth caps 4 KiB at ~146 K IOPS.
  4. With NVMe: 16 queues of depth ≥ 13 suffice (remember N−1); Linux defaults (e.g. 1,024-entry queues impl) give ample headroom.
  5. Bandwidth check: 1.5 M × 4 KiB = 6.1 GB/s → needs at least a Gen4 x4 link (~7.9 GB/s raw), and the TLP overhead must still fit derived.

Common mistakes

  • Saying “NVMe supports 64 K queues of 64 K commands” without the precise limits (65,535 I/O queues; up to 65,536 entries, N−1 usable; device-advertised maxima).
  • Assuming every NVMe device supports many queues — the controller grants a number via the Number of Queues feature.
  • Believing M.2 means NVMe.
  • Attributing NVMe's speed only to PCIe bandwidth; the protocol overhead reduction matters as much for small I/O.
  • Assuming NVMe removes all host overhead — interrupts, block layer and context switches remain.
  • Citing AHCI-vs-NVMe register-read counts as specification facts; they describe typical driver behaviour.

Debugging connection

Chapter 3's ideas become debugging tools: if a device advertises few queues, many cores share them — expect lock contention and lower IOPS; if completions arrive out of order, the host must match by CID — a driver that assumes order will corrupt request state; if one doorbell write covers several commands, a lost or mis-addressed doorbell stalls them all; if queue depth exceeds what the device can parallelise, latency rises with no errors.

💡 Senior insight

Interfaces carry their history. NVMe's admin/I/O split, its 64-byte command and its doorbell model come from 2011 assumptions about PCIe and host memory. When you see a newer feature that looks awkward — doorbell buffer configuration for virtualised guests, controller memory buffers, fabrics capsules — ask which original assumption it is compensating for. That question tells you its likely corner cases.

🧪 Lab 3.1 — SATA vs NVMe on the same machine SAFE

Objective: observe queue structure differences. Setup: a machine with an AHCI controller (most PCs) and an NVMe SSD; or a QEMU guest with both -device ahci/ide-hd and -device nvme. Solution

(1) SATA: one queue, depth ~32 (Linux often reports 32 or 31). NVMe: typically one hardware queue per CPU (or per group of CPUs) with large depth. (2) Each mq/N/cpu_list lists the CPUs mapped to hardware queue N. (3) Compare queue count with CPU count and with the Number of Queues feature value (+1 since 0's-based); the smaller one wins impl.

Extension: in QEMU, change the emulated NVMe device's maximum queue count (consult your QEMU version's documentation for the property name) and observe how Linux adapts.

🧪 Lab 3.2 — Register-access budget SAFE

Objective: quantify CPU cost. Assume tread = 0.8 µs, twrite (CPU-side) = 0.05 µs. Driver A (AHCI-like): per command 3 MMIO reads + 4 writes. Driver B (NVMe-like): per command 0 reads + 2 writes, with doorbells batched 8 commands per write.

Questions: CPU time per command and cores needed for 1 M IOPS, for each.

Solution

A: 3×0.8 + 4×0.05 = 2.6 µs/command → 2.6 cores at 1 M IOPS just for register access. B: (2×0.05)/8 = 0.0125 µs/command → 0.0125 cores. Ratio ≈ 200× derived (inputs synthetic). Real totals include block layer and interrupt costs, which dominate for NVMe.

Quiz — Chapter 3

  1. How many command slots does an AHCI port's command list have?

    Answer

    32.

  2. Maximum number of NVMe I/O submission queues?

    Answer

    65,535 (queue ID 0 is the admin queue).

  3. Maximum entries in an NVMe admin queue? an I/O queue?

    Answer

    Admin: 4,096. I/O: 65,536, limited by the device's CAP.MQES.

  4. Why can a 256-entry queue hold only 255 commands?

    Answer

    Full is defined as tail+1 = head; one slot stays empty to distinguish full from empty.

  5. What is the theoretical IOPS ceiling of NCQ at 100 µs latency?

    Answer

    32 / 100 µs = 320,000 IOPS.

  6. Which AHCI registers indicate issued and active NCQ commands?

    Answer

    PxCI (Command Issue) and PxSACT (SATA Active).

  7. How does an NVMe host learn which commands completed?

    Answer

    By reading CQEs in host memory, identified as new by the phase tag, each carrying the CID and SQ ID.

  8. What major structural change came with NVMe 2.0?

    Answer

    Refactoring into a family: base specification, separate command-set specifications and transport specifications.

  9. Name three highlights of the August 2026 NVMe release.

    Answer

    Any three of: Post-Quantum Cryptography, PCIe Exported NVM Subsystem Migration, Voltage Monitoring, Rate Limiting, Restore Manufacturing Default Settings.

  10. Why does NVMe avoid a lock shared across cores?

    Answer

    Each core gets its own SQ/CQ pair, so cores never contend on a common submission structure.

  11. What class code does an AHCI controller report?

    Answer

    01h/06h/01h.

  12. Why did proprietary PCIe SSDs not become the standard?

    Answer

    Each required its own driver and management tools; the industry wanted one standard interface with in-box OS drivers.

Interview questions — Chapter 3

  1. Beginner Why was NVMe created?
    Model answer

    SATA/AHCI, designed for HDDs, limited SSDs with one 32-deep queue, high per-command CPU overhead and a 600 MB/s link; NVMe offers many deep queues over PCIe with minimal overhead.

  2. Beginner What is AHCI?
    Model answer

    The register-level interface for SATA host controllers, using per-port command lists of 32 slots.

  3. Intermediate Explain why NVMe needs no register reads to submit or complete a command.
    Model answer

    Submission: host writes SQE to memory and the tail to a doorbell (posted). Completion: device writes CQE with phase tag to memory, host polls memory, then writes the head doorbell (posted). SQ head progress is reported inside CQEs.

  4. Intermediate How does out-of-order completion work in NVMe?
    Model answer

    Each command has a CID unique within its SQ; CQEs carry CID and SQ ID, so the host matches completions regardless of order.

  5. Advanced If NVMe allows billions of outstanding commands, why do devices advertise far fewer?
    Model answer

    Each queue/command costs controller resources (state, doorbells, interrupt vectors, fetch bandwidth); devices size limits to their parallelism and silicon budget.

  6. Advanced Compare the SATA and NVMe software stacks in Linux.
    Model answer

    SATA: blk-mq → SCSI mid-layer → libata translation → ahci → HBA → SATA. NVMe: blk-mq → nvme-core/nvme → PCIe → device. Fewer layers and no translation.

  7. Senior Where does NVMe over PCIe still spend host CPU per I/O, and how would you reduce it?
    Model answer

    Block layer, request allocation, DMA mapping/IOMMU, interrupts and context switches; reduce with batching, interrupt coalescing, polling queues, io_uring with registered buffers, user-space drivers, IOMMU passthrough where acceptable.

  8. Senior A team wants to keep SATA for a new low-latency product “because it's simpler”. Argue the trade-offs.
    Model answer

    SATA: cheap, mature, adequate for low-IOPS. But QD 32 cap, 600 MB/s, HBA latency and CPU overhead; NVMe offers lower latency, scalability, richer features (namespaces, telemetry, management) and is now the commodity interface. Quantify with Little's law and the target workload.

Chapter summary

  • SATA/AHCI suited disks: one 32-slot queue per port, shared locks, register reads on completion, 600 MB/s.
  • Flash needs concurrency (Little's law) and low overhead; AHCI could supply neither.
  • NVMe: up to 65,535 I/O queues, up to 65,536 entries each (N−1 usable), admin queue up to 4,096; fixed 64 B/16 B entries; doorbell writes; no fast-path reads; per-queue MSI-X; out-of-order completion.
  • History: SATA → AHCI → proprietary PCIe SSDs → NVMe 1.0 (2011) → 1.x features → 2.0 family (2021) → 2.4 set (August 4, 2026).
