12 Posted vs Non-Posted Transactions (and Completions)

12.1 Why this chapter exists

The posted/non-posted distinction explains three things every NVMe engineer must understand: why ringing a doorbell is cheap for the CPU but reading a register is expensive; why an SSD's write throughput depends on how many reads it can keep in flight; and why errors on writes are reported "somewhere else, later". It also hosts the deep dive on completions: status codes, splitting, timeouts and the configuration-retry mechanism used while a freshly reset SSD boots.

  • Beginner: define posted, non-posted, completion, and classify every TLP type.
  • Intermediate: connect doorbells (posted) and DMA reads (non-posted) to NVMe performance.
  • Advanced: explain completion status codes, split completions, RCB, Completion Timeout ranges, CRS/RRS.
  • Senior: reason about error visibility for posted writes and design flushes (read-after-write) correctly.
  • Trace/debug/validation: find missing or erroneous completions and decide whether a timeout is real.

Prerequisites: Chapter 10, Chapter 11.

12.2 Story and analogy

🧒 Kid analogy

A posted transaction is sending a postcard: you drop it in the box and walk away. You never hear back, and you don't wait. A non-posted transaction is asking a librarian a question: you hand over your question with your name and a ticket number, and you must wait (or do other things) until the librarian comes back with an answer slip carrying your name and ticket number. That answer slip is the completion.

🧩 Where the analogy breaks

Postcards can be lost silently; posted TLPs are delivered reliably link by link, and if the destination rejects one, an error message goes to the root complex (not to the sender as a reply). The librarian may answer in several slips (split completions), and if you wait too long, you declare a timeout — the librarian never says "I give up". Also, a non-posted write exists (config writes): a question whose answer is just "done".

12.4 Connection to NVMe: doorbells and DMA

Doorbells are posted

When the NVMe driver writes the SQ tail doorbell, the CPU store becomes a MWr. The CPU core does not wait for the SSD; the store retires once the write is accepted into the uncached write path. Consequences:

  • Doorbell writes are cheap for the CPU (tens to hundreds of ns of core time, platform-dependent impl), which is why NVMe's design of "one MMIO write per batch of commands" scales.
  • The driver gets no confirmation the doorbell arrived. If the SSD is gone, the write vanishes into a UR (or is dropped by a downstream port with link down) and the only symptom is a command timeout later.
  • Host-side ordering between writing the SQE into host memory and ringing the doorbell is a CPU memory-ordering problem (Linux uses write barriers before MMIO writes, e.g. writel() semantics include ordering against prior normal memory writes verified for Linux's documented MMIO accessor rules), not a PCIe ordering problem.

Register reads are non-posted

Reading CSTS, CAP or any BAR register stalls the CPU core for a full round trip: MRd down, CplD up. Polling CSTS in a hot path is expensive; NVMe uses CQ phase tags in host memory precisely so that the data path needs no MMIO reads at all. A read is also a flush: because a read request must not pass earlier posted writes in the same direction (Chapter 14), reading any register of a device after writing to it guarantees the earlier writes reached the device (on that path) before the read's completion returns.

DMA: reads are non-posted, writes are posted

  • NVMe Read command (data to host): the SSD issues posted MWr TLPs — throughput limited mainly by link bandwidth and posted credits.
  • NVMe Write command (data from host): the SSD issues non-posted MRd TLPs and waits for CplD — throughput limited by outstanding read bytes ÷ round-trip latency (Little's law), i.e. by tags, MRRS, completion buffering, and host memory latency.
  • SQE fetches, PRP list and SGL fetches are reads: on a long-latency path (remote NUMA, IOMMU miss) they add directly to command latency.
Throughputread-DMA ≤ (Noutstanding × Srequest) ÷ RTT
  • Noutstanding — number of MRd requests in flight (bounded by tags and completion buffer space)
  • Srequest — bytes per read request (≤ MRRS)
  • RTT — time from MRd transmission to the last CplD for it

Example derived: RTT = 1.2 µs, MRRS = 512 B, target 7 GB/s → N ≥ 7×109 × 1.2×10−6 / 512 ≈ 16.4 → at least 17 reads in flight. With 32 tags this is easy; at RTT = 4 µs it needs 55.

Completion status

CRS lets a device that has just been reset say "ask again". With CRS Software Visibility enabled in the root port, a config read of the Vendor ID returns a special value (0001h) to software so the OS can poll instead of the hardware retrying invisibly verified. After a conventional reset, devices are allowed a defined period (commonly cited 1 s) before they must answer config requests successfully version; SSDs whose firmware takes long to boot rely on this.

Split completions and RCB

A read may be answered by several completions. Rules (simplified verified): each CplD ≤ MPS; completions for a single request are returned in increasing address order; if split, each completion except the last must end on a naturally aligned Read Completion Boundary (64 or 128 bytes; root complexes report their RCB, endpoints are configured via Link Control); Byte Count and Lower Address let the requester place data (worked example in §11.11). Completions of different requests may interleave and arrive in any order relative to each other.

Completion Timeout

A requester must implement a timer for every non-posted request; if no (final) completion arrives in time, it reports a Completion Timeout (uncorrectable, non-fatal by default) and frees the tag. Device Control 2 selects the range when the device supports programmability; ranges are commonly listed as default 50 µs–50 ms, Range A 50 µs–10 ms, B 10 ms–250 ms, C 250 ms–4 s, D 4 s–64 s, and the timeout can be disabled if supported verified (confirm sub-range details in your revision). For an SSD, a Completion Timeout on its DMA read means the host never answered — rare, and usually a root-complex/IOMMU/link-reset event. For the root complex, a Completion Timeout on a CPU read of a BAR register means the SSD stopped answering — the classic "device hung" signature, after which Linux typically reads all-ones (FFFFFFFFh) from the device.

⚠️ All-ones is not data

Many root complexes synthesize FFFFFFFFh for a failed MMIO read (UR/CA/timeout) impl. The Linux NVMe driver treats CSTS = FFFFFFFFh as "controller gone" — the ffff pattern is evidence of a PCIe failure, not a valid NVMe status.

Unexpected Completion

A completion whose Requester ID/Tag matches no outstanding request at the receiver. Causes: a completion arriving after the requester already timed out and freed the tag; a completer corrupting the tag; a switch misrouting. Reported (often advisory) as Unexpected Completion; the completion is discarded.

12.6 Hardware and protocol view

🔧 Hardware

The requester's outstanding-request table (tag → buffer address, size, timer) and its completion reassembly buffer are internal and invisible. Completer side: the root complex has read queues toward memory; their depth and the IOMMU translation cache determine RTT. Observable: TLP timing on the link, AER logs, and indirect throughput effects.

    Answer

  2. Why does an MMIO read "flush" prior writes?

    Answer

    Read requests may not pass posted writes in the same direction, and the read's completion cannot pass them either, so the completion's arrival proves the writes ahead of it were delivered.

    Answer

    CRS (RRS).

  4. Why is NVMe write throughput sensitive to host memory latency?

    Answer

    The SSD pulls write data with non-posted reads; throughput ≤ outstanding bytes / RTT.

13 Tags and Outstanding Requests

13.1 Why this chapter exists

Tags are what make non-posted reads scalable: each outstanding request gets a unique ticket number so completions can come back in any order and still be matched. The number of tags caps how many reads a function can have in flight, which, with latency, caps its read bandwidth. At Gen5 and Gen6 speeds this cap is real — the reason 10-bit and 14-bit tags exist.

  • Explain the transaction ID (Requester ID + Tag) and why tags exist.
  • Describe 5-bit, 8-bit (Extended Tag), 10-bit and FLIT-mode 14-bit tag spaces and enabling rules.
  • Read a trace with many simultaneous reads and out-of-order completions.
  • Compute the number of outstanding requests needed to hide latency.
  • Recognize tag-related failures (reuse, exhaustion, mismatch).

Prerequisites: Chapter 12.

🧒 Kid analogy

At a busy bakery you get a numbered ticket. You can order five cakes and get tickets 1–5; cake 3 may be ready before cake 1. When "3!" is called, you know exactly which cake it is. If the bakery only has 32 tickets, the 33rd customer waits even if the ovens are free.

🧩 Where the analogy breaks

Tickets are per requester, not per bakery: tag 3 of the SSD and tag 3 of the NIC are different because the Requester ID differs. And a "cake" may be delivered in several boxes (split completions), all bearing the same ticket; the ticket is returned only after the last box (Byte Count says so).

13.2 The transaction ID

A non-posted request is uniquely identified by its Transaction ID = Requester ID (16 bits) + Tag verified. The completer copies both into every completion. The requester must not reuse a tag while a request with that tag is outstanding. Completers and switches do not interpret tags; they just copy them. Posted requests also carry a tag field but it has no matching role (some implementations put arbitrary values there).

13.6 Ordering and tags

Tags do not impose order; completions for different tags may return in any order. Within one tag, multiple completions return in increasing address order. With 10-bit tags, an analyzer decoding only 8 bits will show apparent duplicates (tag 107h and 007h both shown as "07"): a classic analyzer-configuration trap.

import random, heapq
def simulate(ntags, mrrs=512, rtt_us=2.0, jitter=0.5, total_reqs=20000, issue_ns=30):
    t, free, inflight, done, events = 0.0, list(range(ntags)), 0, 0, []
    issued = 0
    while done < total_reqs:
        while free and issued < total_reqs:
            tag = free.pop()
            rtt = (rtt_us + random.uniform(-jitter, jitter)) * 1000
            heapq.heappush(events, (t + rtt, tag)); issued += 1
            t += issue_ns                      # serialization of request TLPs
        t_done, tag = heapq.heappop(events)
        t = max(t, t_done); free.append(tag); done += 1
    return total_reqs * mrrs / t               # bytes per ns == GB/s
for n in (32, 64, 256, 768):
    print(n, "tags:", round(simulate(n), 2), "GB/s (ignores link cap)")

14 PCIe Ordering

14.1 Why this chapter exists

NVMe correctness relies on PCIe ordering: the host must never see a Completion Queue Entry before the data it describes is in memory, and must never take an interrupt before the CQE is visible. PCIe guarantees this — under specific conditions. Change attributes (Relaxed Ordering), traffic classes, or paths (peer-to-peer, multiple root ports) and the guarantees change. Ordering is also where oversimplification is most dangerous; this chapter keeps the rules precise and labels every simplification.

🧒 Kid analogy

A one-lane tunnel with a few passing bays. Delivery trucks (posted writes) must stay in line behind each other, so a "dinner's ready" sign truck can't get ahead of the food trucks. But delivery trucks are allowed to drive past cars waiting to ask questions (non-posted), so a stuck question can't block deliveries forever. Some trucks have a sticker "I don't mind being overtaken" (Relaxed Ordering).

🧩 Where the analogy breaks

There isn't one tunnel: ordering is defined per direction, per Traffic Class/Virtual Channel, and only for transactions that travel the same path. Two writes going to different root ports, or in different TCs, have no ordering relationship at all.

14.2 The producer–consumer model

PCIe ordering is designed so that the classic producer–consumer pattern works without any extra handshake verified: a producer writes data, then writes a flag; a consumer that sees the flag (by reading it, or by being interrupted) will see the data. NVMe completion is exactly this: data (MWr) → CQE with flipped phase (MWr, the flag) → MSI-X (MWr, the doorbell to the CPU).

14.4 Why each core rule exists

  • Posted must not pass posted (RO=0): producer–consumer — the flag must not overtake the data.
  • Read must not pass posted: a read of the flag/data after writes must return the written values; also makes MMIO reads usable as write flushes.
  • Completion must not pass posted: if a device writes data to memory then a CPU read of device status returns "done", the data must already be visible — the completion carrying "done" may not overtake the device's earlier writes in that direction.
  • Posted must be able to pass non-posted and completions-may-pass-non-posted: deadlock avoidance. Non-posted requests can be blocked for lack of NP credits or of completion resources; if posted writes and completions could be stuck behind them, circular waits could freeze the fabric.
  • No ordering between different TCs: each VC has independent queues and credits; TC mapping is the system's way of saying "these flows are independent".

14.5 Attributes: Relaxed Ordering, ID-based Ordering, No Snoop

Relaxed Ordering (RO, Attr[1]): a TLP with RO = 1 is permitted to pass earlier posted writes (row-side rule) verified. Note the asymmetry: a later TLP with RO = 0 still may not pass earlier writes, whatever their RO. So an NVMe controller may mark bulk data writes RO = 1 (letting the root complex commit them to memory in any order, which can help throughput on some platforms) and send the CQE with RO = 0; the CQE then still cannot pass any of the data writes. A device may set RO only if "Enable Relaxed Ordering" in its Device Control register is set verified. Some platforms have had problems with RO and Linux contains quirks that clear the enable for specific root ports impl.

ID-based Ordering (IDO, Attr[2]): permits TLPs from different Requester IDs (or different completers for completions) to pass each other where otherwise forbidden, since unrelated requesters rarely have producer–consumer relationships. Enabled per function in Device Control 2.

No Snoop (NS, Attr[0]): not an ordering attribute; it tells the root complex coherency snooping is not required. Misuse yields stale data, which can masquerade as an ordering bug.

Traffic Class (TC): TC 0–7 maps onto Virtual Channels. Ordering applies only within a TC (strictly, within the VC). NVMe devices almost universally use TC0 / VC0.

🧪 Lab 14.1 — Ordering checker on a synthetic trace SAFE

Objective: write a checker that flags a posted write with RO = 0 that appears before an earlier posted write in a "delivery order" list.

# each tuple: (issue_seq, kind, ro, tc)  kind in {'P','NP','CPL'}
issued = [(1,'P',1,0),(2,'P',1,0),(3,'P',0,0),(4,'P',0,0)]
delivered = [2,1,4,3]                      # order seen at destination
def check(issued, delivered):
    info = {s:(k,ro,tc) for s,k,ro,tc in issued}
    pos = {s:i for i,s in enumerate(delivered)}
    bad = []
    for later,(k,ro,tc) in info.items():
        if k not in ('P','CPL') or ro: continue
        for earlier,(k2,_,tc2) in info.items():
            if earlier < later and k2 == 'P' and tc2 == tc and pos[later] < pos[earlier]:
                bad.append((later, earlier))
    return bad
print(check(issued, delivered))            # [(4, 3)]: RO=0 write passed earlier write
Solution

2 passing 1 is allowed (2 has RO = 1). 4 passing 3 is a violation (4 has RO = 0). Extend the checker to completions (completion with RO = 0 must not pass earlier posted writes) and to TC separation.

Extension: add IDO handling (different Requester IDs may pass when IDO is set).

Quiz

  1. May a posted write pass a blocked read?

    Answer

    Yes — and it must be able to (deadlock avoidance).

  2. Data writes have RO = 1, CQE RO = 0. Can the CQE pass data?

    Answer

    No; the passing TLP's RO governs and it is 0.

  3. Are writes in TC0 and TC1 ordered relative to each other?

    Answer

    No.

Interview questions

  1. Beginner Why must a flag write not pass a data write?
    Model answerConsumer might read stale data after seeing the flag.
  2. Intermediate Why can posted writes pass non-posted requests?
    Model answerTo prevent deadlocks when non-posted requests are blocked.
  3. Advanced How does RO help performance?
    Model answerRoot complex can commit writes out of order (e.g. different memory channels, cache-line ownership), avoiding head-of-line blocking.
  4. Advanced What is IDO for?
    Model answerAllowing unrelated requesters' traffic to bypass each other in switches/RC.
  5. Senior Prove NVMe data integrity relies on PCIe ordering, then find a case it doesn't.
    Model answerData→CQE→MSI same path posted ordering; breaks with CQE RO, different TCs, P2P/CMB destinations, or multi-path systems.
