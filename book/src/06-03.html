PART XVIII

NVMe Advanced Features

The core of NVMe — queues, doorbells, PRPs, reads and writes — is only the skeleton. Real products are distinguished by the features layered on top: how they report health, how they carve capacity into namespaces, how they expose zones, key-value stores and on-drive compute, how they are managed by a baseboard management controller over a side channel, and how they are booted before any operating system exists. Each chapter in this part is anchored to the August 2026 NVMe 2.4 specification set (Base 2.4, NVM Command Set 1.3, ZNS 1.5, Key Value 1.4, Subsystem Local Memory 1.3, Computational Programs 1.3, NVMe-MI 2.2, Boot 1.4 — revision numbers per the course brief; confirm each on nvmexpress.org/specifications before relying on them).

57 SMART / Health Information

📘 Specification baseline

DOCUMENT: NVM Express Base Specification. REVISION: 2.4 (August 2026 set). RELEVANT TOPIC: Get Log Page (admin opcode 02h), SMART / Health Information log page (Log Identifier 02h), Error Information log page (Log Identifier 01h), Asynchronous Event Request (admin opcode 0Ch), Temperature Threshold feature. STATUS: the SMART / Health log is mandatory for controllers that support the NVM Command Set (confirm the mandatory/optional matrix for your controller type in 2.4). OLDER VERSIONS THAT MAY DIFFER: Critical Warning bits and Endurance Group fields were added over 1.x revisions; per-namespace SMART support is optional. SOURCE: nvmexpress.org/specifications. version

57.1 Why this chapter exists

Fleet operators decide whether to retire, migrate or keep a drive based almost entirely on one 512-byte log page. Validation engineers must prove that every counter in it moves correctly. Support engineers receive it as the first artefact in every escalation. Misreading it — confusing data units with bytes, treating Percentage Used as “percent until failure”, or ignoring Unsafe Shutdowns — leads to wrong conclusions with real money attached.

  • Beginner: name the key fields and what physical phenomenon each reflects.
  • Intermediate: convert data units to bytes, Kelvin to Celsius, and compute write amplification inputs.
  • Advanced: map Critical Warning bits to asynchronous events and thresholds.
  • Senior: design a fleet health policy that distinguishes wear, thermal, power and media problems.
  • Trace: recognise the Get Log Page command and its data transfer in a PCIe/NVMe trace.
  • Debug/validation: design tests that move each counter predictably.

Prerequisites: admin queue and Get Log Page basics, CQE status fields, NAND wear concepts, FTL.

🧒 Kid analogy — the car dashboard and the logbook

A car has a dashboard: temperature gauge, fuel (spare blocks), odometer (data written), engine-hours (power-on hours), and warning lights (critical warnings). It also has a logbook of times someone turned the key off without parking properly (unsafe shutdowns) and of times the engine misfired (media errors). The SMART log is the SSD’s dashboard plus logbook.

🧩 Where the analogy breaks

An odometer is exact; Percentage Used is a vendor estimate based on the device’s own endurance model. The “fuel gauge” (Available Spare) is not linear with remaining life. And warning lights in NVMe can trigger an asynchronous message to the host, which a car dashboard cannot.

57.3 Conversions

Bytes = DataUnits × 1000 × 512
  • DataUnits — Data Units Read or Written (128-bit integer)
  • 1000 × 512 — the fixed unit defined by the specification (512 000 bytes)
T(°C) = T(K) − 273     WAF ≈ NAND_bytes_written / (DataUnitsWritten × 512 000)
  • T(K) — Composite Temperature in Kelvin
  • WAF — write amplification factor
  • NAND_bytes_written — only available from vendor-specific logs impl

Worked example

A drive reports Data Units Written = 61 035 157 and Power On Hours = 8 760. Bytes written = 61 035 157 × 512 000 ≈ 31.25 × 1012 bytes ≈ 31.25 TB (decimal) over one year, i.e. ≈ 85.6 GB/day. If the drive is a 3.84 TB device rated 1 drive-write-per-day for 5 years (≈ 7 008 TB), this is ≈ 0.45% of rated endurance per year — but Percentage Used might still read 2% or 3% because it reflects NAND wear including write amplification. synthetic numbers. The lesson: never compute Percentage Used yourself from Data Units Written.

58 Namespaces — Carving the Subsystem

📘 Specification baseline

DOCUMENTS: NVMe Base Specification 2.4 (Namespace Management admin opcode 0Dh, Namespace Attachment admin opcode 15h, Identify CNS values, Changed Namespace List log) and NVM Command Set 1.3 (Identify Namespace data structure for NVM: NSZE, NCAP, NUSE, FLBAS, LBA Format list). STATUS: Namespace Management and Attachment are optional (Identify Controller OACS bit 3 reports support). VERSION NOTES: since NVMe 2.0 the Identify data is split between command-set-independent and command-set-specific structures, and the I/O Command Set (CSI) concept was introduced version.

58.1 Why this chapter exists

A namespace is the thing your OS calls /dev/nvme0n1. It is a range of logical blocks with a format, a size and a set of controllers allowed to access it. Multi-tenant arrays, SR-IOV (see Chapter 56), multipath, and every “why does my drive show 0 bytes” bug lead here.

  • Define NSID, NSZE, NCAP, NUSE and their ordering NSZE ≥ NCAP ≥ NUSE.
  • Read the LBA format list (LBADS, MS, RP) and FLBAS.
  • Explain thin provisioning and capacity accounting (TNVMCAP/UNVMCAP).
  • Execute and trace the create → attach → rescan → use → detach → delete flow.
  • Understand shared namespaces and the Namespace Attribute Changed event.

Prerequisites: Identify command (admin 06h), LBA, controller ID (CNTLID).

🧒 Kid analogy — the library sections

A huge library (NVM subsystem) can be divided into sections (namespaces): “Science, 2 shelves”, “Stories, 5 shelves”. Each section has its own shelf numbering starting at 0 (LBAs). The head librarian decides which reading rooms (controllers) get a key to each section (attachment). A section can be labelled “5 shelves” but only have books on 3 (thin provisioning).

🧩 Where the analogy breaks

Namespaces are logical; there is no fixed physical shelf behind them. The FTL places data anywhere on NAND. Also, a namespace can be attached to several controllers at once (shared), which needs reservations or a cluster file system to be safe.

59 Zoned Namespaces (ZNS)

📘 Specification baseline

DOCUMENT: NVMe Zoned Namespace Command Set Specification. REVISION: 1.5 per the August 2026 set (course brief — confirm on nvmexpress.org). STATUS: optional I/O command set (CSI for ZNS). OLDER VERSIONS THAT MAY DIFFER: ZNS 1.0 was published with NVMe 1.4-era TP 4053; later revisions refined zone attributes, limits and reporting version. SOURCE: nvmexpress.org/specifications. Linux: Documentation/block/zoned and kernel zoned block device docs.

59.1 Why this chapter exists

A conventional SSD hides NAND’s erase-before-write nature behind an FTL that remaps every write, which costs DRAM, over-provisioning and write amplification. ZNS exposes the truth: the namespace is divided into zones that must be written sequentially and reset as a whole. The host takes over data placement, and in return the device can be cheaper, more predictable and more durable. The price is a strict state machine that the host must respect — and that you must be able to debug.

  • Define zone, zone size, zone capacity, write pointer, ZSLBA.
  • Draw the zone state machine with all seven states and the transitions caused by writes and Zone Management Send actions.
  • Explain active and open resource limits.
  • Explain Zone Append and why it exists.
  • Diagnose invalid-write and resource-limit errors from traces.

Prerequisites: namespaces, FTL, NAND erase blocks, ZNS.

🧒 Kid analogy — the warehouse aisles

A warehouse has many long aisles (zones). Workers must fill each aisle from the front to the back, one box after another, never skipping a spot. A pointer on the floor (write pointer) shows where the next box goes. When an aisle is full, nobody can add more until the whole aisle is emptied at once (reset). Only a limited number of aisles may have their lights on and workers in them at the same time (open zones). If you are in a hurry, you can hand a box to the foreman and say “put it at the end of aisle 7 and tell me where it went” (zone append).

🧩 Where the analogy breaks

A zone’s writable capacity may be smaller than its address span (zone capacity < zone size), so the “aisle” has a painted-off end you can never use. Zones can also become read-only or offline because of media failure — the warehouse can lose an aisle by itself. And “open” is an accounting state, not necessarily a physical one.

59.5 Why Zone Append exists

With ordinary writes, the host must issue exactly one write per zone at a time at the WP, because NVMe does not guarantee command execution order: two queued writes to the same zone may be processed out of order and the second becomes a Zone Invalid Write. That forces queue depth 1 per zone. Zone Append lets many writes to the same zone be outstanding; the device serialises them and reports where each landed. derived from NVMe’s lack of inter-command ordering. Linux’s block layer historically used per-zone write locking (mq-deadline) for regular writes and zone append for file systems such as btrfs and zonefs. version (kernel behaviour changes; newer kernels add zone write plugging).

ZNS moves the FTL’s hardest problem — garbage collection — into host software. 🧪 Lab 59.1 (Extended Lab 48) — Warehouse model and invalid-write diagnosis SAFE

Objective: build a software model of zones, write pointers and states; then diagnose an invalid write. Prerequisites: Python 3. Setup: the simulation below.

class Zone:
    def __init__(s, zslba, size, cap):
        s.zslba, s.size, s.cap = zslba, size, cap
        s.wp, s.state = zslba, "EMPTY"
class ZNS:
    def __init__(s, nzones=8, size=0x1000, cap=0xC00, mar=4, mor=2):
        s.z = [Zone(i*size, size, cap) for i in range(nzones)]
        s.size, s.mar, s.mor = size, mar, mor
    def count(s, states): return sum(z.state in states for z in s.z)
    def write(s, slba, nlb, append=False):
        z = s.z[slba // s.size]
        if z.state in ("FULL", "READ_ONLY", "OFFLINE"): return "Zone Is " + z.state.title(), None
        if append and slba != z.zslba: return "Invalid Field", None
        start = z.wp if append else slba
        if start != z.wp: return "Zone Invalid Write", None
        if start + nlb > z.zslba + z.cap: return "Zone Boundary Error", None
        if z.state == "EMPTY" and s.count({"IMP_OPEN","EXP_OPEN","CLOSED"}) >= s.mar:
            return "Too Many Active Zones", None
        if z.state in ("EMPTY","CLOSED") and s.count({"IMP_OPEN","EXP_OPEN"}) >= s.mor:
            return "Too Many Open Zones", None   # simplified: real devices may implicitly close
        if z.state in ("EMPTY","CLOSED"): z.state = "IMP_OPEN"
        z.wp += nlb
        if z.wp == z.zslba + z.cap: z.state = "FULL"
        return "Success", start
    def reset(s, zslba):
        z = s.z[zslba // s.size]; z.wp, z.state = z.zslba, "EMPTY"

d = ZNS()
print(d.write(0x0, 8))            # Success, 0
print(d.write(0x10, 8))           # Zone Invalid Write (WP is 0x8)
print(d.write(0x0, 8, append=True))  # Success, 8
print(d.write(0x1000, 8), d.write(0x2000, 8))  # second hits open limit (MOR=2)

Solution

The decisive evidence is the zone’s write pointer at the time of the command (Report Zones immediately after, plus the history of successful writes). If WP = 0x8 and SLBA = 0x10, the host skipped LBAs — host bug (often reordering). If WP = 0x10 but the device rejected, the device is wrong. The real specification also lets the controller implicitly close an Implicitly Opened zone instead of failing with Too Many Open Zones; whether it does is part of normative rules plus implementation choice — check the ZNS spec and device documentation.

Quiz

  1. Name the seven zone states.

    Answer

    Empty, Implicitly Opened, Explicitly Opened, Closed, Full, Read Only, Offline.

  2. Does a Closed zone count against the active limit?

    Answer

    Yes. Active = IO + EO + Closed.

  3. Where does the host learn the LBA used by a Zone Append?

    Answer

    In the completion queue entry for that command.

  4. Why can zone capacity be smaller than zone size?

    Answer

    So zone size can be a convenient (e.g. power-of-two) address span while capacity matches the device’s physical erase unit structure.

Interview questions

  1. Beginner What is a write pointer?
    Model answerThe next LBA that may be written in a sequential-write-required zone.
  2. Intermediate Conventional namespace vs ZNS?
    Model answerConventional allows random writes and the device FTL remaps; ZNS requires sequential writes per zone and explicit resets, moving placement and GC to the host.
  3. Advanced Why does Linux need special handling for zoned writes?
    Model answerBecause the block layer and NVMe may reorder; it must serialise per-zone writes or use zone append.
  4. Senior How would you validate a ZNS device’s state machine?
    Model answerEnumerate every (state, action) pair from the spec’s transition table, including illegal ones expecting Invalid Zone State Transition; test resource limits at MAR/MOR boundaries; power-loss tests for WP consistency; concurrency tests with append.

📌 Summary

ZNS zones are written sequentially at the write pointer, tracked through seven states, limited by active/open resources, and recycled by reset. Zone Append removes the QD-1-per-zone limit. Most bugs are WP disagreements between host and device.
