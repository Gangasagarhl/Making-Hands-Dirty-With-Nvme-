64.1.2 Part A — PCIe architecture

Part A

  1. A1. Explain the three PCIe layers and give one error detected at each.

    Answer

    Transaction Layer: TLP creation/consumption, flow control accounting, ordering; errors: Unsupported Request, Completion Timeout, Malformed TLP, ECRC error, Poisoned TLP. Data Link Layer: sequence numbers, LCRC, Ack/Nak, replay, DLLPs; errors: Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover, Data Link Protocol Error. Physical Layer: encoding, framing, scrambling, LTSSM, equalization; errors: Receiver Error, link training failures, Surprise Down (reported via DLL state).

  2. A2. Why can a Gen3 link at 8 GT/s carry nearly as much data per lane as a Gen2 link at 10 GT/s would?

    Answer

    Gen2 uses 8b/10b (80% efficiency) so 5 GT/s → 4 Gb/s; Gen3 uses 128b/130b (~98.5%) so 8 GT/s → ~7.88 Gb/s. A hypothetical 10 GT/s 8b/10b link would give 8 Gb/s — similar to Gen3. The encoding change let Gen3 nearly double usable bandwidth without doubling the rate.

  3. A3. What is the purpose of the Configuration state of the LTSSM?

    Answer

    Establish link and lane numbering, negotiate width, handle lane reversal and polarity (polarity is handled in Polling), and verify both ends agree via TS1/TS2 ordered sets before entering L0.

  4. A4. A switch sits between root port and SSD. Which agent regenerates LCRC, and what protects data integrity across the switch’s internals?

    Answer

    Each link’s transmitter regenerates LCRC (the switch checks on ingress and regenerates on egress). Internal switch paths are protected by switch-internal mechanisms (implementation-dependent) and end-to-end by ECRC if enabled; NVMe PI provides end-to-end protection at the storage level.

64.1.3 Part B — NVMe architecture

Part B

  1. B1. Define NVM subsystem, controller, namespace, and NVM set / endurance group in one sentence each.

    Answer

    Subsystem: the collection of controllers, namespaces and media sharing one NQN. Controller: the host-facing interface that processes commands through queues. Namespace: a formatted quantity of NVM addressed by NSID and LBAs. Endurance group: a set of media with shared endurance management; NVM set: a partition of media within an endurance group for isolation (introduced around 1.4 version).

  2. B2. What does VS = 0002_0000h mean, and what must you still check to know the feature set?

    Answer

    Major 2, minor 0, tertiary 0 → NVMe Base 2.0. Features are mostly optional: check Identify Controller (OACS, ONCS, LPA, FRMW, SGLS, CTRATT, etc.), supported log pages, Commands Supported and Effects log, and the command set specs in use.

  3. B3. Explain why NVMe was split into Base, command set and transport specifications, and name the document you would read for doorbell register layout in NVMe over PCIe.

    Answer

    To evolve command sets and transports independently (2.0 family). Doorbell/register mapping for PCIe: the NVMe over PCIe Transport specification (plus Base for controller register definitions) — confirm the current revision on nvmexpress.org.

  4. B4. Explain the difference between Admin, I/O, and Fabrics command sets in terms of queues.

    Answer

    Admin commands go on the admin queue (QID 0); I/O commands on I/O queues for a selected I/O command set; Fabrics commands (Connect, Property Get/Set, Authentication) are used by NVMe over Fabrics transports to establish queues and access properties, since no PCIe BAR exists there.

64.1.4 Part C — TLP decoding

Part C

  1. C1. Decode: DW0 = 0x2000_0010, DW1 = 0x0200_2CFF, DW2 = 0x0000_0001, DW3 = 0x0230_1000.

    Answer

    Fmt 001 = 4-DW header, no data; Type 00000 → MRd 64-bit. Length 10h = 16 DW = 64 B. DW1: Requester ID 0200h = bus 02, dev 0, fn 0; Tag 2Ch; Last BE Fh, First BE Fh. Address = 0000_0001_0230_1000. Interpretation: device 02:00.0 reading 64 B at 1_0230_1000 — a likely SQE fetch (64 B, from a queue address).

  2. C2. Decode: DW0 = 0x4A00_0010, DW1 = 0x0000_0040, DW2 = 0x0200_2C00.

    Answer

    Fmt 010 (3-DW, with data), Type 01010 → CplD. Length 16 DW. DW1: Completer ID 0000h, status bits 15:13 = 000 (SC), BCM 0, Byte Count = 040h = 64. DW2: Requester ID 0200h, Tag 2Ch, Lower Address = 00h. This completes C1’s request with all 64 bytes.

  3. C3. A CplD has Byte Count = 0x100 and Length = 0x20 DW. What do you conclude?

    Answer

    This completion carries 128 B but 256 B remain including this one → at least one more completion for this tag will follow (128 B). Not an error.

  4. C4. A TLP has Fmt 011, Type 00000, Length 1, address FEE0_3000 with data 0000_0024. What is it likely to be and how do you confirm?

    Answer

    4-DW MWr with data — an MSI/MSI-X message on x86 (address in FEEx_xxxx range) impl. Confirm by reading the device’s MSI-X table entries (address/data) and matching data 0024h to a vector. Note a 4-DW header with an address below 4 GiB is unusual (hardware normally uses 3-DW for 32-bit addresses) — worth noting as possibly a decoder display convention or a device quirk.

  5. C5. What do First DW BE = 0h with Length = 1 indicate for an MRd?

    Answer

    A zero-length read: commonly used as a flush to ensure prior posted writes have reached the destination. The completion returns one DW of undefined data.

64.1.5 Part D — NVMe command decoding

SQE (little-endian dwords): CDW0 = 0x0123_0002, NSID = 0x0000_0001, CDW2–3 = 0, MPTR = 0, PRP1 = 0x0000_0001_3A41_7200, PRP2 = 0x0000_0001_3A42_0000, CDW10 = 0x0010_0000, CDW11 = 0x0000_0000, CDW12 = 0x4000_0003, CDW13 = 0, CDW14 = 0, CDW15 = 0.

Part D

  1. D1. Opcode, CID, FUSE, PSDT?

    Answer

    Opcode 02h (Read), FUSE 0, PSDT 0 (PRPs), CID = 0x0123.

  2. D2. SLBA, number of blocks, FUA?

    Answer

    SLBA = CDW11:CDW10 = 0x0000_0000_0010_0000. NLB = 3 → 4 blocks. CDW12 bit 30 = 1 → FUA set. (Bit 31 LR = 0.)

  3. D3. With 4 KiB LBA format and 4 KiB memory page size, is the PRP usage valid?

    Answer

    Transfer 16 KiB starting at offset 0x200 in page 1_3A41_7000: PRP1 covers 4096 − 512 = 3584 B; remaining 12800 B spans 4 more pages (3 full + 512 B), i.e. 4 more entries → PRP2 must point to a PRP list, not a data page. Here PRP2 = 1_3A42_0000; whether it is a list cannot be known from the SQE alone — the device will treat it as a list pointer because more than one page remains. If the host intended it as a single data page, it is a host bug. Check memory at PRP2.

  4. D4. The CQE for this command has DW3 = 0x0285_0123 (assume current phase 0). Decode.

    Answer

    CID 0x0123; upper 16 bits 0x0285 → P = bit 16 = 1. The host expects phase 0, so this entry is not new — it is a stale entry from the previous pass and must not be consumed at all. If it were new (expected phase 1): Status = 0x0285 >> 1 = 0x0142: SC = 42h, SCT = 1 (command specific) — interpret against the command-specific status table for Read in the NVM Command Set (do not guess). Trick: check phase before decoding anything.

  5. D5. Encode a Write Zeroes for NSID 1, SLBA 0x2000, 256 blocks, deallocate requested.

    Answer

    CDW0 opcode 08h + CID; NSID 1; CDW10 = 0x0000_2000; CDW11 = 0; CDW12 = NLB 0x00FF with DEAC bit (bit 25) = 1 → 0x0200_00FF; no data pointer. Confirm DEAC support via Identify Namespace DLFEAT / Identify Controller ONCS version.

64.1.6 Part E — Queue analysis

Part E

  1. E1. SQ size 64. Host tail history: 10, 20, 63, 5. Controller SQHD history in CQEs: 8, 19, 60. How many commands outstanding at the end?

    Answer

    Tail 5 after wrap; head 60 → (5 − 60) mod 64 = 9 outstanding (slots 60–63, 0–4).

  2. E2. A host writes tail = 64 to a 64-entry queue. What should happen?

    Answer

    Invalid doorbell value (must be 0–63). The controller may report an Invalid Doorbell Write Value asynchronous event (error type), and behaviour of the queue is undefined/ignored for that write. Host bug.

  3. E3. CQ size 256, head 255, expected phase 1. Next CQE slot and expected phase after consuming it?

    Answer

    Consume slot 255 with phase 1; head wraps to 0; expected phase becomes 0.

  4. E4. Why might a controller stop fetching from an SQ that has pending entries while other SQs proceed?

    Answer

    Its CQ is full (head doorbell not advanced), arbitration priorities (WRR with urgent queues starving low), controller per-queue limits, or the SQ was deleted/invalid. Check CQ head doorbells first.

64.1.7 Part F — DMA analysis

Part F

  1. F1. List every DMA operation the controller performs for a 64 KiB write using a PRP list, in order.

    Answer

    SQE fetch (MRd 64 B) → PRP list fetch (MRd; 15 entries × 8 B if PRP1 page-aligned → 120 B) → write-data fetch MRds (64 KiB / MRRS) → (media program, internal) → CQE write (MWr 16 B) → MSI-X (MWr). Order of list fetch vs data fetch may interleave impl.

  2. F2. Why is an IOMMU fault for a write-direction DMA (device → memory) harder to notice than for a read?

    Answer

    Posted writes get no completion; the device believes the write succeeded and completes the command with success. Only the IOMMU log shows it. A read fault produces an error completion or timeout the device must handle.

  3. F3. A device DMAs read data to PRP1 + 0x1000 although PRP1 has offset 0x200 and PRP2 is a list. Is it wrong?

    Answer

    Yes. After the first page portion (from PRP1 to the end of its page), subsequent data must go to the page addresses from the list. Writing to PRP1’s page + 0x1000 (the physically next page) assumes contiguity — a device PRP-walk bug, or the list entry happens to equal that address (check the list).

  4. F4. What host-side condition can make DMA correct on the wire but data still wrong in the application?

    Answer

    Non-coherent DMA without proper cache maintenance (on non-coherent platforms), the host reading the buffer before completion (race), buffer reuse after timeout/abort while DMA still in flight, or bounce-buffer (swiotlb) copy errors.

The host consumed both and advanced CQ head to 8. Observed: all TLPs; inferred (label derived): which command was the write and which the read — confirm by decoding the SQEs in row 3.

Part H

  1. H1. Decode the root port uncorrectable status and its severity.

    Answer

    0x4000 = bit 14 = Completion Timeout. Severity register 0006_2030: bits 4, 5, 13, 17, 18 set (DLP, Surprise Down, FC Protocol, Receiver Overflow, Malformed TLP = fatal); bit 14 clear → Completion Timeout is non-fatal.

  2. H2. Decode the correctable status.

    Answer

    0x41 = bit 0 Receiver Error + bit 6 Bad TLP.

  3. H3. The header log is shown. What request timed out, and who issued it?

    Answer

    DW0 0000_0001 → Fmt 000, Type 0 → MRd 3-DW, length 1. DW1 0000_00FF → Requester 0000 (root complex/CPU), tag 00, BE Fh/Fh… (FF = last BE F, first BE F). Address FC00_001C → BAR0 + 1Ch = CSTS. So a CPU read of the NVMe CSTS register got no completion. Note: header logging for Completion Timeout is not guaranteed on every implementation impl.

  4. H4. Combine: what is your leading hypothesis and next steps?

    Answer

    The device stopped responding to MMIO (hung, in reset, or link issue). Correctable Receiver Errors and Bad TLPs suggest link marginality preceding it — possibly the link went through Recovery or the device’s receiver is struggling; but the SSD’s own AER is clean (if it is accessible at all — reading it may itself be unreliable). Next: check LnkSta/DLL Link Active, look for Surprise Down, read device config space (all ones?), check correctable error rate history, NVMe driver logs for timeouts preceding the CSTS read (the CSTS read is usually part of timeout handling — so the original failure is earlier). Confidence: Likely device unresponsive; cause Unknown pending evidence.

64.1.10 Part I — Performance debugging

Part I

  1. I1. A Gen4 x4 drive delivers 3.3 GB/s sequential read at QD 32, 128 KiB. Spec sheet says 7 GB/s. LnkSta: 16 GT/s x4. MPS 128. What do you suspect and why?

    Answer

    MPS 128 reduces efficiency to roughly 128/(128+24) ≈ 84% → ~6.6 GB/s ceiling, not 3.3. So MPS alone does not explain halving. Look at host side: single-thread fio CPU-bound? IOMMU strict mode? Drive in thermal throttling? Spec sheet measured with different conditions? Also check if the drive has an x4 link but the root port shares bandwidth via a switch upstream at x2. Measure per-layer.

  2. I2. 4 KiB random read at QD1: 85 µs average; at QD 32: 380 K IOPS. Compute average latency at QD 32 and comment.

    Answer

    32 / 380 000 = 84 µs — same as QD1. Latency did not grow with QD, meaning the device scales well with parallelism up to QD 32 (not yet saturated). Push to higher QD to find the knee.

  3. I3. p99.9 latency spikes of 5 ms every ~10 s during sustained random writes. Hypotheses?

    Answer

    Device GC/metadata flush, write cache flush cycles, thermal throttling steps, host writeback bursts (if via filesystem), SLC cache exhaustion periods. Check SMART temperature over time, test with direct I/O, vary fill level, look at the device’s periodicity vs host timers.

  4. I4. Interrupt rate is 900 K/s at 1 M IOPS and CPU is saturated. Two fixes?

    Answer

    Enable interrupt coalescing (moderate threshold/time) or use polling queues for high-QD workloads; ensure affinity so interrupts land on submitting CPUs; batch CQ head doorbells. Measure p99 impact.

64.1.11 Part J — Architecture design

Part J

  1. J1. Design host-side queue/interrupt topology for a 2-socket server with 8 NVMe drives (4 per socket), 128 CPUs, latency-sensitive DB plus batch analytics.

    Answer

    NUMA-local placement: DB threads on the socket of their drives; per-CPU I/O queues limited by vectors; separate poll queues for DB latency-critical I/O; WRR priority if supported (DB high, analytics low) or cgroup I/O controls; coalescing tuned per queue; monitor cross-socket traffic. Trade-offs: memory/vectors vs isolation.

  2. J2. Specify the minimum observability a new SSD controller must expose for field debugging.

    Answer

    Accurate Error Information log (SQID, CID, LBA, parameter location), Persistent Event Log, telemetry (host- and controller-initiated) with versioned decoders, link event counters (Recovery entries, replays), timestamp synchronised to host, thermal/throttle history, firmware activation history. Justify each by a failure class it helps diagnose.

  3. J3. Should a JBOF use one x16 upstream for 24 x4 drives? Discuss.

    Answer

    Oversubscription 96 lanes → 16 (6:1). Acceptable if workloads are capacity/IOPS-bound with low aggregate bandwidth; unacceptable for sequential-heavy workloads. Also consider failure domain (one upstream link), DPC behaviour, and switch latency. Alternatives: dual upstreams, multiple switches, higher gen upstream.

  4. J4. Design a validation matrix for APST.

    Answer

    Dimensions: each power state entry/exit, idle-time thresholds around transitions, I/O arrival during transition, combined with ASPM L1/L1.2 enabled/disabled, D3hot cycles, temperature extremes, firmware activation, host latency tolerance settings. Measure first-I/O latency, errors, link events. Include negative tests (non-operational state + admin commands).

64.1.12 Part K — 2026 NVMe feature analysis

Part K

  1. K1. Name the five highlights announced with the NVMe 2.4 specification set (August 2026) and the purpose of each, labelling what you know vs what you would check.

    Answer

    Post-Quantum Cryptography (purpose: resistance of security protocols to future quantum attacks); PCIe Exported NVM Subsystem Migration (moving exported subsystems across hosts/contexts); Voltage Monitoring (visibility into supply voltage conditions); Rate Limiting (controlling resource/throughput consumption); Restore Manufacturing Default Settings (standard return to factory configuration). Known: names and announced purposes version. To check: which documents carry each (Base 2.4, transport 1.4, MI 2.2…), the exact commands/log pages/features, and optionality.

  2. K2. A vendor claims “NVMe 2.4 compliant”. What questions do you ask?

    Answer

    Which documents and revisions (Base, NVM CS, transport, MI); which optional features implemented; compliance testing evidence (e.g. interoperability/compliance programs); VS value reported; behaviour with hosts expecting earlier revisions.

  3. K3. How would you teach a 1.4-era engineer about the 2.x restructuring in two minutes?

    Answer

    See Teach-back 106: the monolith split into Base + command sets + transports; new command sets (ZNS, KV, later SLM/computational programs); features like FDP and live migration in 2.1-era; 2.4 adds the listed highlights. Always cite document + revision.

  4. K4. What is the risk of using a protocol analyzer decoder older than the device’s spec revision?

    Answer

    New opcodes, log pages, fields or reserved bits now defined may be decoded as reserved/invalid or mislabelled, leading to false anomalies or missed ones. Label such decodes uncertain and verify against the spec.

🧠 Incident brief

After a fleet kernel upgrade, 0.3% of servers with SSD model Q report a once-per-day I/O error “Data Transfer Error” on writes larger than 512 KiB. No AER errors. IOMMU logs show nothing. Old kernel: zero errors. Same drive firmware. Only servers with a specific CPU stepping are affected.

Part L

  1. L1. What is the first abnormal event and its layer?

    Answer

    Row 5: a CplD with the poisoned (EP) bit — Transaction Layer, originated by the completer (root complex/memory subsystem). The device correctly refuses poisoned data and fails the command.

  2. L2. Why no AER entries, and why might that be a configuration issue?

    Answer

    Poisoned TLP received may be masked in the device’s AER Uncorrectable Mask, or the platform handles errors firmware-first and logs elsewhere (BMC/SEL), or advisory non-fatal handling suppresses reporting impl. Check masks and platform logs — the absence of AER is not absence of error.

  3. L3. What does the kernel-upgrade correlation suggest, given the CPU stepping dependence?

    Answer

    The new kernel may change memory placement or DMA buffer allocation patterns (e.g. larger contiguous buffers, different NUMA placement, new use of a memory feature) that exercise a CPU-stepping-specific erratum or a marginal memory region, causing poisoned reads (memory ECC uncorrectable surfaced as poison). Or a kernel change in RO/ordering settings. Hypotheses: Possible until platform logs (machine check / memory error records) correlate.

  4. L4. Plan the investigation and write the first abnormal event section of your report.

    Answer

    Plan: gather platform error logs (machine checks, memory ECC, firmware-first records) at failure times; map the poisoned address (from the request with tag 0x119 → PRP entry → physical page) to DIMM/channel; check whether failing addresses cluster; bisect kernel changes on affected stepping; consult CPU errata with vendor; test the old kernel with forced large buffers. First abnormal event: “At t=…, the root complex returned a poisoned CplD (EP=1) for device MRd tag 0x119 (address …, part of PRP entry N of write CID …); the device completed the command with Data Transfer Error as expected. Layer: host memory subsystem/root complex (Transaction Layer origin). Confidence: Confirmed (trace row 5).”

65.1.6 Parser architecture

  • Source adapters (one per format) produce raw records with provenance; no interpretation.
  • Decoders are pure functions: decode_tlp(bytes) → fields, decode_sqe(64B), decode_cqe(16B), decode_aer(regs), decode_cap(u64). Each references spec tables with revision tags.
  • Context builder scans config writes (BARs, Command, MSI-X), admin commands (Create CQ/SQ, Set Features) and register writes (AQA/ASQ/ACQ, CC) to build a time-versioned context: “at time t, BAR0 = …, SQ3 base = …, HMB list = …”.
  • Classifier uses the context to label MMIO writes as doorbells/CC writes, device MRds as SQE/PRP-list/data/HMB fetches, MWrs as data/CQE/MSI-X.

  SUBMITTED ──(SQE fetch covering slot)──▶ FETCHED ──(data MRd/MWr in PRP ranges)──▶ DATA_MOVING
      │                                       │                                         │
      │ (timeout without fetch)               │ (timeout)                              ▼
      ▼                                       ▼                                 CQE_POSTED ──(MSI-X)──▶ SIGNALLED
  ANOMALY:not_fetched                 ANOMALY:not_completed                          │                     │

65.1.8 Correlation algorithm

def correlate(events, ctx):
    pending_fetch = {}            # (sqid, slot) -> CommandLife
    outstanding_reads = {}        # (requester_id, tag) -> MRd event
    for e in sorted(events, key=lambda e: e.t):
        c = ctx.at(e.t)
        if e.kind == "MWr" and c.is_doorbell(e.addr):
            q, kind = c.doorbell_target(e.addr)
            if kind == "sq_tail":
                for slot in c.sq[q].slots_between(c.sq[q].tail, e.data):
                    pending_fetch[(q, slot)] = CommandLife(sqid=q, submit_evt=e)
                c.sq[q].tail = e.data
            else:
                c.cq[q].host_head = e.data; mark_consumed(c, q, e)
        elif e.kind == "MRd":
            outstanding_reads[(e.req_id, e.tag)] = e
            for q, slots in c.sq_slots_covered(e.addr, e.length_bytes):
                for s in slots:
                    life = pending_fetch.pop((q, s), None)
                    if life: life.fetch_evt = e
        elif e.kind in ("CplD", "Cpl"):
            req = outstanding_reads.get((e.req_id, e.tag))
            if req is None: flag(e, "unexpected_completion")
            elif e.status != "SC": flag(e, f"completion_{e.status}", refs=[req])
            if e.fields.get("EP"): flag(e, "poisoned", refs=[req])
            if req and e.byte_count == e.length_bytes: outstanding_reads.pop((e.req_id, e.tag))
        elif e.kind == "MWr" and c.is_cq_slot(e.addr):
            cqe = decode_cqe(e.payload)
            life = find_life(cqe.sqid, cqe.cid)
            if not life: flag(e, "cqe_without_command")
            elif cqe.phase != c.cq_expected_phase(e.addr): flag(e, "phase_mismatch")
            else: life.cqe_evt = e
        elif e.kind == "MWr" and c.is_msix(e.addr, e.data):
            link_irq(e, c.vector_of(e.addr, e.data))
        elif e.kind == "MWr" or e.kind == "MRd":
            if not c.addr_in_known_region(e.addr):    # PRP ranges, queues, HMB lists
                flag(e, "dma_outside_known_regions")
        if e.kind == "iommu_fault":
            region = c.region_history(e.addr)          # e.g. "HMB list L1, freed at 600.0012"
            flag(e, "iommu_fault", note=region)
    for life in all_lives(): check_timeouts(life)
