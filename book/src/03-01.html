PART VII

PCIe Configuration

A PCIe link that has trained to L0 is a road with no addresses on it. Before a single NVMe command can travel, software must discover every device on that road, give every bridge a range of bus numbers, read every device's identity card (its configuration space), learn how big each device's register window is, carve those windows out of the physical address map, and finally switch on memory decoding and bus mastering. This Part walks that journey in three chapters: Chapter 17 — Enumeration (the depth-first walk and bus numbering), Chapter 18 — Configuration Space (decoding headers and capability lists by hand), and Chapter 19 — BARs and MMIO (sizing, assigning and using the doorway through which the NVMe driver reaches the controller's registers). By the end of the Part you will be able to read an lspci -vvv listing or a raw hex dump and say exactly what firmware and the OS did to the device — and what they forgot to do.

17.1 Why this chapter exists

Every NVMe bring-up failure that ends in "the drive is not detected" is, at its root, an enumeration story. Either the link never reached L0, or a configuration read returned all-ones, or the bridge above the device did not forward the right bus numbers, or the Base Address Register (BAR) could not be placed, or the OS refused the device's resources. If you cannot narrate enumeration step by step, you will guess at these failures instead of localizing them. This chapter gives you that narration — from power-on to the moment the NVMe driver's probe() function runs — and teaches you to find the first step that went wrong.

17.2 Learning objectives

  • Beginner: explain what a Bus/Device/Function (BDF) number is and why software must discover devices rather than having them pre-listed.
  • Intermediate: perform a depth-first enumeration by hand on a topology with a switch, assigning Primary, Secondary and Subordinate bus numbers correctly.
  • Advanced: explain Type 0 vs Type 1 configuration requests, how a bridge decides to forward, convert, or reject them, and how Configuration Request Retry Status (CRS) interacts with slow-to-initialize devices.
  • Senior: reason about resource reallocation, hot-plug bus-number padding, ACPI and firmware hand-off, and why the OS may re-enumerate differently from firmware.
  • Trace analysis: recognise the signature of an enumeration scan in a protocol capture (bursts of CfgRd0/CfgRd1 at offset 00h, Unsupported Request completions for empty slots) and spot the first anomaly.
  • Debugging: map "device missing" symptoms to a layer: physical link, configuration routing, resource assignment, or driver binding.
  • Validation: design tests for enumeration robustness (cold boot, warm reset, hot-plug, CRS behaviour, slow firmware readiness).

17.3 Prerequisites

You should already understand the PCIe layer model and the Transaction Layer Packet (TLP) — in particular that configuration requests (CfgRd0, CfgRd1, CfgWr0, CfgWr1) are non-posted and complete with a Cpl or CplD (Cpl/CplD). You should know that the Link Training and Status State Machine (LTSSM) must reach L0 before any TLP flows. If those are shaky, revisit the PCIe fundamentals Part first. Inside this Part, the next stops are Chapter 18 and Chapter 19.

17.4 Story: the new apartment building

🧒 Kid analogy

Imagine a postman who arrives at a brand-new town where nobody has house numbers yet. He starts at the post office (the Root Complex). He walks down the first street and knocks on every door: "Is anyone home?" If nobody answers, he moves on. If someone answers, he asks, "Who are you, and are you a gate to another street?" When he finds a gate, he walks through it, names the new street "Street 1", and keeps going deeper before returning. Each gate gets a little sign: "Streets 1 through 1 are behind me." When he has visited every street, he goes back and asks each household, "How big is your mailbox?" and then gives each one a real address in the town map. Only then can letters (memory reads and writes) be delivered.

🌍 Real-world analogy

A network administrator plugging in a new building of routers: she walks the cabling, assigns subnets to each router port (bus numbers to bridges), records which subnet range sits behind each router (Secondary..Subordinate), then hands out IP addresses to devices (BAR assignment). Routing then works by range checks — exactly how PCIe bridges forward configuration and memory requests.

🧩 Where the analogy breaks

(1) Doors in PCIe do not answer with "nobody home" politely: a configuration read to an absent function is completed with Unsupported Request status by the bridge or Root Port, and the CPU typically sees FFFFh/FFFFFFFFh — the "all-ones" response. (2) The postman can find a house that says "come back later" (CRS) — a real device may still be booting its firmware. (3) House numbers (bus numbers) are assigned by the postman, but device numbers on a PCIe link are fixed by topology: a device directly below a Root Port or switch Downstream Port is device 0 (unless ARI is in use). (4) Addresses for mailboxes (BARs) are not chosen by the household — the household only states the size and alignment, and software picks the address.

17.5 Beginner view: what enumeration is

Enumeration is the process by which system software (platform firmware first, then usually the OS again) discovers every PCI Express function in the hierarchy, gives every bridge its bus-number range, sizes and assigns every BAR, and enables the functions it wants to use. It exists because PCIe, like PCI before it, is self-describing: the motherboard does not contain a list of what is plugged in. A slot could hold an NVMe SSD today and a network card tomorrow, and a switch could fan out to 24 drives in a storage enclosure. Software therefore discovers the topology at run time by issuing configuration reads and observing who answers.

17.5.1 Bus / Device / Function (BDF)

Every function is addressed in configuration space by a 16-bit Routing ID (called Requester ID when the function initiates a request, Completer ID when it completes one) verified:

Bits 15:8Bits 7:3Bits 2:0
Bus number (0–255)Device number (0–31)Function number (0–7)

Linux prints it as DDDD:BB:DD.F, for example 0000:01:00.0: PCI segment (domain) 0000, bus 01, device 00, function 0. Segments let a large server have more than 256 buses by giving each Root Complex (or each ECAM region) its own 256-bus space; the segment number is not carried in the TLP — it is a host-side concept. verified

  • Bus number — assigned by software during enumeration. Not burned into hardware. Bus 0 is the Root Complex's internal bus in the common case.
  • Device number — on a point-to-point PCIe link, the device below a Root Port or switch Downstream Port is device 0. The Downstream Port only forwards Type 0 configuration requests that target device 0 on its secondary bus (unless ARI forwarding is enabled). Devices other than 0 appear on a Root Complex's internal bus (integrated endpoints and Root Ports themselves) and on the internal virtual bus of a switch (one device number per Downstream Port).
  • Function number — a single physical device can expose up to 8 functions (e.g. a multi-port NIC). Function 0 must exist; software checks the multi-function bit (Header Type bit 7) of function 0 before probing functions 1–7.
🚀 Advanced: ARI

Alternative Routing-ID Interpretation (ARI, an extended capability, ID 000Eh) reinterprets the 8 bits of Device+Function as one 8-bit function number for devices directly below an ARI-capable Downstream Port. This allows up to 256 functions — needed for Single Root I/O Virtualization (SR-IOV) devices that expose many Virtual Functions. With ARI, "device number" stops being meaningful for that device. verified

17.7 Hardware view: who answers a configuration request

A configuration request is born in the Root Complex. The CPU never issues "a config TLP" directly; it performs a load or store to the ECAM window (or, on legacy x86, to I/O ports CF8h/CFCh), and the Root Complex converts that access into a configuration TLP verified. The Root Complex's ECAM decoder takes the address apart:

ECAM address = ECAM_base + (Bus << 20) + (Device << 15) + (Function << 12) + Register
  • ECAM_base — physical base of the configuration window, reported to the OS in the ACPI MCFG table (per segment and bus range).
  • Bus — 8 bits (0–255). Each bus takes 1 MiB of window.
  • Device — 5 bits (0–31). Each device takes 32 KiB.
  • Function — 3 bits (0–7). Each function takes 4 KiB.
  • Register — 12-bit byte offset (0–FFFh) into the function's 4 KiB configuration space.

A full 256-bus segment therefore needs a 256 MiB window. Firmware may describe a smaller bus range to save address space. derived

#!/usr/bin/env python3
"""ECAM and legacy CF8h address calculators (pure arithmetic, no hardware access)."""

def ecam_addr(base, bus, dev, fn, reg):
    assert 0 <= bus < 256 and 0 <= dev < 32 and 0 <= fn < 8 and 0 <= reg < 4096
    return base + (bus << 20) + (dev << 15) + (fn << 12) + reg

def cf8_value(bus, dev, fn, reg):
    # Legacy mechanism reaches only the first 256 bytes, dword aligned.
    assert reg < 256 and reg % 4 == 0
    return (1 << 31) | (bus << 16) | (dev << 11) | (fn << 8) | (reg & 0xFC)

def bdf_from_rid(rid):
    return (rid >> 8) & 0xFF, (rid >> 3) & 0x1F, rid & 0x7

ECAM_BASE = 0xE000_0000          # synthetic: real base comes from the ACPI MCFG table
for bdf, reg in [((0x01, 0, 0), 0x000), ((0x01, 0, 0), 0x100), ((0x04, 0, 0), 0x034)]:
    b, d, f = bdf
    print(f"{b:02x}:{d:02x}.{f} reg {reg:03x}h -> ECAM {ecam_addr(ECAM_BASE, b, d, f, reg):#010x}")
print(f"CF8h value for 01:00.0 reg 10h = {cf8_value(1, 0, 0, 0x10):#010x}")
rid = (0x04 << 8) | (0 << 3) | 0
print(f"Requester ID {rid:#06x} -> bus {bdf_from_rid(rid)[0]:02x} dev {bdf_from_rid(rid)[1]:02x} fn {bdf_from_rid(rid)[2]}")
print(f"ECAM window for 256 buses = {256 * 32 * 8 * 4096 // (1 << 20)} MiB")

17.7.1 Type 0 vs Type 1 configuration requests

The Root Complex chooses a TLP type by comparing the target bus with the topology:

  • CfgRd0 / CfgWr0 (Type 0) — targets a function on the bus directly below the port issuing it. The receiving function consumes it.
  • CfgRd1 / CfgWr1 (Type 1) — targets a function on a bus further down. Each bridge (Root Port, switch port) compares the target bus with its own registers:
    • target bus == Secondary Bus Number → convert to Type 0 and send it down the link;
    • Secondary < target bus ≤ Subordinate Bus Number → forward downstream unchanged as Type 1;
    • otherwise → not for this bridge (it is not claimed by this branch).

This range check is why bus numbering must be contiguous and depth-first: every bridge must "own" exactly the range of bus numbers beneath it. verified

🔧 Hardware: what a switch looks like to software

A PCIe switch is not one device to software. It appears as a tree of PCI-to-PCI bridges: one Upstream Port (a Type 1 function on the bus below the Root Port) and an internal virtual bus with one Type 1 function per Downstream Port. A 1-upstream/3-downstream switch therefore consumes two levels of bus numbers before its endpoints: one for the internal bus, then one per Downstream Port. Engineers who forget the internal bus mis-predict BDFs every time.

17.8 The depth-first enumeration algorithm

next_bus = 0

scan_bus(bus):
    highest = bus
    for dev in 0..31:
        if read_cfg16(bus, dev, 0, 0x00) == 0xFFFF: continue       # no function 0 → no device
        nfuncs = 8 if (read_cfg8(bus, dev, 0, 0x0E) & 0x80) else 1   # multi-function bit
        for fn in 0..nfuncs-1:
            vid = read_cfg16(bus, dev, fn, 0x00)
            if vid == 0xFFFF: continue
            if vid == 0x0001: retry later                           # CRS software visibility (see 17.9)
            hdr = read_cfg8(bus, dev, fn, 0x0E) & 0x7F
            if hdr == 0x01:                                          # Type 1: a bridge
                next_bus += 1
                write_cfg8(bus, dev, fn, 0x18, bus)                  # Primary
                write_cfg8(bus, dev, fn, 0x19, next_bus)             # Secondary
                write_cfg8(bus, dev, fn, 0x1A, 0xFF)                 # Subordinate: temporarily "everything"
                sub = scan_bus(next_bus)                             # recurse first (depth-first)
                write_cfg8(bus, dev, fn, 0x1A, sub)                  # shrink to the real range
                highest = max(highest, sub)
            else:
                record endpoint; size its BARs later
    return highest

scan_bus(0)

Two details matter in real firmware impl: (1) hot-plug capable Downstream Ports often get extra bus numbers reserved ("bus padding") so a switch inserted later can be numbered without renumbering the whole tree; (2) Linux normally reads the bus numbers firmware programmed and only assigns new ones if they are missing or broken. Linux performs its own scan using the same principles (pci_scan_child_bus, pci_scan_bridge).

17.8.1 Worked walk with bus numbering

The following executable simulation applies the algorithm to a synthetic topology: a Root Complex with an integrated host bridge, Root Port A (an NVMe SSD directly attached) and Root Port B (a 3-port switch with two NVMe SSDs and one empty slot).

#!/usr/bin/env python3
"""Depth-first PCIe bus-numbering simulation (SYNTHETIC topology, no hardware access)."""

# Each node: ("bridge", name, [children]) or ("ep", name)
# Children of a bridge sit on the bridge's SECONDARY bus; device numbers are list positions.
TOPOLOGY = [  # devices on bus 0 (root complex internal bus)
    ("ep", "Host bridge"),                                   # 00:00.0
    ("bridge", "Root Port A", [("ep", "NVMe SSD #1")]),       # 00:01.0
    ("bridge", "Root Port B", [                               # 00:02.0
        ("bridge", "Switch Upstream Port", [
            ("bridge", "Switch Downstream Port 0", [("ep", "NVMe SSD #2")]),
            ("bridge", "Switch Downstream Port 1", [("ep", "NVMe SSD #3")]),
            ("bridge", "Switch Downstream Port 2", []),      # empty slot
        ]),
    ]),
]

next_bus = 0
rows = []

def scan_bus(bus, devices, depth):
    """Scan one bus; recurse into bridges depth-first. Returns highest bus number used."""
    global next_bus
    highest = bus
    for dev, node in enumerate(devices):
        bdf = f"{bus:02x}:{dev:02x}.0"
        if node[0] == "ep":
            rows.append((depth, bdf, node[1], "type 0", ""))
            continue
        _, name, children = node
        next_bus += 1
        secondary = next_bus
        # Real firmware temporarily programs subordinate = 0xFF so Type 1 config
        # requests for any deeper bus are forwarded while scanning below.
        idx = len(rows)
        rows.append([depth, bdf, name, "type 1", None])
        sub = scan_bus(secondary, children, depth + 1)
        rows[idx][4] = f"pri={bus:02x} sec={secondary:02x} sub={sub:02x}"
        highest = max(highest, sub)
    return highest

scan_bus(0, TOPOLOGY, 0)
print(f"{'BDF':8} {'header':7} {'bus registers':24} device")
for depth, bdf, name, hdr, regs in rows:
    print(f"{bdf:8} {hdr:7} {regs:24} {'  ' * depth}{name}")

Primary = the bus the bridge sits on. Secondary = the bus immediately below it. Subordinate = the highest-numbered bus anywhere below it. A Type 1 request is forwarded if Secondary ≤ target ≤ Subordinate, and converted to Type 0 at the bridge whose Secondary equals the target.

17.9 Readiness, CRS and the "device not ready yet" problem

An NVMe SSD contains a controller running firmware. After reset, that firmware may need time before it can answer configuration requests. PCIe provides Configuration Request Retry Status (CRS): the device may complete a configuration request with CRS status, meaning "try again" verified. What software sees depends on the Root Port's CRS Software Visibility enable (in the Root Control register of the PCI Express Capability):

  • Visibility disabled — the Root Complex re-issues the request itself (hardware retry); the CPU load may simply stall until the device answers or a platform timeout occurs impl.
  • Visibility enabled — for a read that includes the Vendor ID register, the Root Complex returns the special value 0001h in the Vendor ID field so software can poll without blocking verified. Linux uses this when available and waits up to a bounded time (on the order of a minute in current kernels) for the device to become ready impl.

Newer PCIe revisions add Readiness Notifications (Device Readiness Status and Function Readiness Status messages) and a Readiness Time Reporting capability so software need not guess version. Support is optional; capability discovery applies.

📭 What the spec does not say

The PCIe specification does not say how long a particular NVMe SSD's firmware takes to become ready, nor how long a given BIOS waits before giving up. A drive that is "missing only on cold boot" is frequently a readiness-timing interaction between a slow device and an impatient firmware — the evidence is the timestamp of the first CfgRd relative to link-up, and whether CRS completions were returned.

Configuration writes are non-posted: the writer waits for a completion.     dma_set_mask_and_coherent(&pdev->dev, DMA_BIT_MASK(64))
    pci_request_mem_regions(pdev, "nvme")   # claim BAR0 in /proc/iomem
    bar = ioremap(pci_resource_start(pdev, 0), size)   # kernel virtual mapping of BAR0
    cap = readq(bar + 0x00)              # NVMe CAP register (Chapter 24)
    pci_alloc_irq_vectors(pdev, 1, N, PCI_IRQ_ALL_TYPES)  # MSI-X preferred
    ... controller reset/enable, Identify, I/O queues ...

Notice the strict order: you cannot read CAP before MSE=1 (the device would not decode the address and the read returns all-ones or faults), and the device cannot fetch commands before BME=1 (its memory reads would be blocked by its own Command register). derived

17.14 Worked example: predicting BDFs before you boot

Problem. A server has one Root Port at 00:03.0 with a 1-upstream/4-downstream switch. Downstream Ports 0 and 2 have NVMe SSDs; ports 1 and 3 are empty. Firmware reserves no hot-plug padding. Bus numbers already used: 00 only. Predict every BDF and every bridge's (pri, sec, sub).

Solution. Root Port 00:03.0 gets sec = 1. Switch USP is 01:00.0 with sec = 2 (internal bus). DSPs are 02:00.0, 02:01.0, 02:02.0, 02:03.0. Depth-first: DSP0 sec = 3 → SSD at 03:00.0, sub = 3. DSP1 sec = 4, empty, sub = 4. DSP2 sec = 5 → SSD at 05:00.0, sub = 5. DSP3 sec = 6, sub = 6. USP sub = 6, Root Port sub = 6. Note that empty DSPs still consume a bus number — they are bridges and have a secondary bus whether or not anything is plugged in. derived

Twist. If firmware gives each hot-plug DSP 8 extra buses of padding, the second SSD moves from bus 05 to a much higher bus number. This is why BDFs are not stable identifiers across firmware settings — use serial numbers, NGUID/EUI-64, or physical slot numbers in automation.

17.15 Common mistakes

  • Assuming the device number on a PCIe link can be anything but 0 (without ARI).
  • Forgetting the switch internal bus when predicting BDFs.
  • Treating FFFFFFFFh as data. On PCIe, all-ones from a config read is almost always "no response".
  • Using BDF as a persistent drive identifier in test scripts.
  • Believing enumeration happens once. It can happen at boot, after hot-plug, after rescan, after a Secondary Bus Reset, and in VMs again inside the guest.
  • Issuing configuration requests immediately after a reset (no readiness wait) and interpreting failures as a dead device.

💡 Senior insight

When a device is "missing", resist starting in the driver. Ask, in order: Did the link train? (Root Port Link Status / analyzer) → Did a config read reach the device? (trace or Root Port AER UR counts) → Did it answer with data, UR, or CRS? → Did resource assignment succeed? (dmesg) → Did a driver match? (lspci -k). Each question has cheap, decisive evidence. Debugging by layer is ten times faster than debugging by intuition.

🏭 Implementation-dependent

Exact firmware scan order (some scan all functions of all devices; some stop early), bus padding policy, the readiness timeout, whether firmware leaves the NVMe controller enabled when handing off to the OS, and whether the OS reassigns resources are all implementation-dependent. Linux's behaviour also varies with kernel version and command-line options.

🧪 Lab 17.1 — Read your machine's PCIe tree SAFE

Objective: map every Root Port, switch and NVMe endpoint on a real or virtual machine, and reconstruct each bridge's (pri, sec, sub).

Prerequisites: Linux with pciutils; root for full output.

Setup: any Linux machine or VM. In QEMU, you can create an emulated NVMe device with -drive file=nvm.img,if=none,id=nvm -device nvme,serial=lab17,drive=nvm, optionally behind -device pcie-root-port,id=rp1 with bus=rp1 on the NVMe device (Q35 machine type).

Procedure: (1) Run lspci -tv. (2) For each bridge, run sudo lspci -vvv -s <bdf> and record the "Bus: primary=, secondary=, subordinate=" line. (3) Draw the tree with bus numbers. (4) Locate every device with class "Non-Volatile memory controller".

Observations: every endpoint's bus number must fall inside exactly one chain of nested bridge ranges.

Questions: Which bridges have empty secondary buses? Are any ranges padded (sub > sec although nothing is below)?

Solution / expected reasoning

Each bridge's range [sec, sub] must contain the ranges of all bridges below it. Padding appears as sub > sec with nothing below — usually on hot-plug capable ports (look for "HotPlug+" in the slot capabilities of that port). Empty Root Ports still have a secondary bus. In QEMU with a single root port you should see the NVMe device at 01:00.0 or similar depending on how many ports precede it.

Extension: write a script that parses lspci -vvv and validates the nesting automatically.

🧪 Lab 17.2 — Simulate depth-first numbering SAFE

Objective: modify the simulation in 17.8.1 to add hot-plug padding of N buses to every Downstream Port that is marked hot-plug capable.

Procedure: add a flag to bridge nodes; after recursing, set sub = max(sub, secondary + N) and bump next_bus accordingly. Rerun and compare BDFs.

Questions: Which endpoints change BDF? Does the Root Port's range grow?

Solution

Padding a port shifts the bus numbers of everything enumerated after it, not before it. The enclosing bridges' Subordinate values grow to include the padding. In the sample topology, padding DSP 0 by 4 moves SSD #3 from bus 05 to bus 09 and the Root Port's range from 2–6 to 2–10.

Extension: model a hot-plug event: insert a switch below a padded port and verify it can be numbered without touching other ranges.

Procedure: (1) sudo dmesg -w in one terminal. (2) echo 1 | sudo tee /sys/bus/pci/devices/0000:01:00.0/remove. (3) echo 1 | sudo tee /sys/bus/pci/rescan. (4) Compare the messages to the timeline in 17.6.

🧪 Lab 17.4 — Senior forensic lab: the missing drives SAFE

Objective: given synthetic trace 17.C plus this lspci fact — "switch USP 02:00.0: Bus: primary=02, secondary=03, subordinate=03" — produce a root-cause statement with evidence and confidence.

Model answer

Root cause: the switch Upstream Port's Subordinate Bus Number was programmed to 03h before the scan below it completed, so Type 1 requests for buses 4 and 5 were not forwarded and returned UR. 17.19 Exercises

🎯 Exercise
  1. Compute the ECAM address of register 104h of function 05:00.3 with ECAM base C000_0000h.
  2. A Root Port has sec=08h, sub=0Ch. For a CfgRd1 to bus 0Bh, what does it do? For bus 08h? For bus 0Dh?
  3. Decode Requester ID 3A11h into bus, device and function.
Answers

(1) C000_0000h + (05h<<20) + (0<<15) + (3<<12) + 104h = C050_3104h. (2) Bus 0Bh: forward as Type 1. Bus 08h: convert to Type 0. Bus 0Dh: not claimed — not forwarded downstream. (3) 3A11h = 0011_1010_0001_0001b: bus 3Ah, device 00010b = 2, function 001b = 1 → 3A:02.1.

Quiz

  1. Why does a Root Port normally only forward Type 0 configuration requests for device 0?

    Answer

    Because a PCIe link is point-to-point: only one device sits on the secondary bus of a Root Port or Downstream Port, and it is device 0. (ARI changes the interpretation of the device/function bits.)

  2. What value does software typically see when reading a configuration register of a non-existent function?

    Answer

    All ones (FFFFh for a 16-bit read, FFFFFFFFh for 32-bit), because the request completes with Unsupported Request and the Root Complex returns all-ones to the CPU.

  3. Why is Subordinate written as FFh during the descent?

    Answer

    So that the bridge forwards Type 1 requests for any deeper bus that will be numbered during the recursion; the final value is written once the deepest bus number is known.

  4. What does a Vendor ID read of 0001h mean when CRS Software Visibility is enabled?

    Answer

    The device answered with Configuration Request Retry Status — present but not ready. Software should retry later.

  5. Which two Command register bits must the NVMe driver set before it can talk to the controller and before the controller can fetch commands?

    Answer

    Memory Space Enable (bit 1) for MMIO register access, and Bus Master Enable (bit 2) so the device may issue memory requests (DMA).

Interview questions

  1. Beginner What is a BDF and who assigns each part?
    Model answer

    Bus (8 bits, assigned by software during enumeration), Device (5 bits, determined by topology — 0 on a PCIe link), Function (3 bits, fixed by the device design). Together they form the Routing ID used in configuration requests and as Requester ID in TLPs the device sends.

  2. Beginner Why does PCIe need enumeration at all?
    Model answer

    Because the hierarchy is not known at design time; devices are self-describing and software must discover them, assign bus numbers and addresses, and enable them.

  3. Intermediate Explain the forwarding decision a bridge makes for a Type 1 configuration request.
    Model answer

    If the target bus equals Secondary, convert to Type 0 and send downstream; if it is greater than Secondary and at most Subordinate, forward unchanged; otherwise do not claim it.

  4. Intermediate How many bus numbers does a 1×4 switch consume below its Root Port, with no padding and nothing plugged in?
    Model answer

    Six: the Root Port's secondary bus (on which the Upstream Port sits), the switch's internal virtual bus (on which the four Downstream Ports sit), and one secondary bus per Downstream Port (four). Empty Downstream Ports still consume their secondary bus number.

  5. Advanced Why might an NVMe SSD be missing only after cold boot?
    Model answer

    Device readiness after power-on is slower than after warm reset (firmware load from NAND/NOR, self-tests); if platform firmware scans before readiness and does not honour CRS long enough, the device is missed. Evidence: timing of first CfgRd, CRS completions, firmware logs.

  6. Senior Your automation identifies drives by BDF and breaks after a BIOS update. What do you change and why?
    Model answer

    Switch to stable identifiers (controller serial number, namespace NGUID/EUI-64/UUID, physical slot via Slot Capabilities/ACPI). BDFs depend on enumeration order and padding policy and are not stable across firmware versions or population changes.

17.20 Summary, further reading and next

Enumeration is a depth-first walk that assigns bus numbers to bridges and discovers functions using non-posted configuration reads. BDF = software-assigned bus + topology-determined device + design-determined function. Bridges route Type 1 requests by Secondary/Subordinate ranges. Readiness (CRS) and resource assignment are the two most common sources of "device missing" problems after the link itself. The NVMe driver can only begin once Memory Space and Bus Master are enabled and BAR0 is mapped.

Further reading: PCI Express Base Specification (PCI-SIG) chapters on configuration space and the configuration transaction model; Linux kernel documentation Documentation/PCI/ (especially the PCI driver guide) and source drivers/pci/probe.c; ACPI specification (MCFG table, _CRS).
