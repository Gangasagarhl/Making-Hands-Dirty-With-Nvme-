PART I

Foundations

Before PCIe, before NVMe, before any acronym: what a computer actually is, who in it moves information, and how they agree on where information lives. Every later chapter leans on the ideas in this Part — addresses, registers, buses, drivers, interrupts and DMA — so we take them slowly and carefully.

1 How Computers Move Data

A story before any acronyms

🧒 Kid analogy — the busy school

Imagine a school. In the middle sits a very fast teacher who can do sums in the blink of an eye — but the teacher can only work on what is on the desk right in front of them. Around the classroom are tables covered in numbered paper trays; anything the teacher needs must be fetched from a tray onto the desk, and anything the teacher finishes must be put back in a tray.

Far down the corridor is a giant library that holds every book the school has ever owned. Nothing there is lost when the lights go out at night — but walking to the library is slow, so the teacher never goes personally. Instead there is a librarian who runs the library, a corridor connecting the classroom to the library, and a rule book everybody agreed on about how to ask for things.

When the teacher wants a book, they write a request slip, drop it in a request box on a table, and ring a bell. The librarian hears the bell, walks to the box, reads the slip, finds the book, carries the pages straight to the tray named on the slip, writes a little “done” note in an answer box, and taps the teacher on the shoulder. The teacher never had to walk to the library, and never had to stand and wait.

A computer is a collection of workers moving information. Some are fast and forgetful, some are slow and remember forever, and most of the clever engineering is about how they hand information to each other without tripping over one another.

🧩 Where the analogy breaks

Real teachers walk; a CPU never moves. Real librarians understand books; an SSD controller has no idea what your bytes mean — it only knows block numbers. Real trays hold one thing; a memory location is overwritten instantly and silently. And in a computer there are often dozens of teachers (CPU cores) and dozens of request boxes (queues) at the same time — the reason NVMe exists at all.

Why this chapter exists

Every NVMe and PCIe concept is built from a small set of older ideas: an address, a register, a memory write, an interrupt, a DMA transfer. When an engineer says “the device wrote the CQE to the wrong address”, every word in that sentence comes from this chapter. If you are shaky here, every trace you read later will be a wall of hexadecimal. If you are solid here, traces become stories.

Learning objectives

  • Beginner: explain, without jargon, the roles of the CPU, memory, storage, controllers, buses and drivers.
  • Beginner: convert between binary, hexadecimal and decimal; distinguish KB from KiB.
  • Intermediate: distinguish virtual, physical and bus/IO-virtual addresses, and explain why a buffer contiguous in virtual memory may be scattered in physical memory.
  • Intermediate: explain programmed I/O, memory-mapped I/O and DMA, and when each is used.
  • Advanced: explain why reading a device register is far more expensive than writing one, and why that shaped NVMe's design.
  • Senior: given a hang or corruption, decide which actor (CPU, memory, IOMMU, device, interrupt path) to suspect first, and what evidence would discriminate.
  • Trace analysis: recognise that an MSI-X interrupt and a DMA data write look alike on the wire — both are memory writes.
  • Validation: list what must be tested for DMA correctness: addresses, lengths, alignment, ordering, IOMMU faults.

The big reveal — the path information takes

1.1 What is information?

🧒 Kid analogy

If I hold up one hand behind my back and you have to guess whether it is open or closed, my answer gives you one tiny piece of news. If I have two hands, there are four possible answers. Information is “news that tells you which of the possibilities is true.”

Simple explanation. Information is a choice among distinguishable possibilities. A computer stores information by keeping something physical in one of several distinguishable states — a voltage high or low, a magnet pointing north or south, a tiny charge trapped or not trapped inside a flash cell.

Engineering explanation. The amount of information needed to pick one of N equally likely possibilities is log2(N) bits. Engineering systems encode information in physical quantities, and every physical quantity is noisy, so every layer adds redundancy to detect or correct errors: parity and ECC (Error-Correcting Code) in DRAM, CRCs (Cyclic Redundancy Checks) on PCIe packets, powerful LDPC (Low-Density Parity-Check) style codes on NAND flash impl. A large part of storage and protocol engineering is the cost of keeping information correct while moving or holding it.

I = log2(N) bits
  • I — information needed to identify one outcome
  • N — number of equally likely, distinguishable outcomes

Practical example. A 4 KiB block has 32,768 bits and therefore 232768 possible contents. A 512-byte logical block has 4,096 bits. When an SSD stores a block, it actually stores more bits than that — the extra bits are ECC and metadata — because the raw media flips bits at a measurable rate.

Common misconception. “Information is the data.” Not quite: data is the encoding; information is what the encoding distinguishes. The same information can be encoded many ways (ASCII text, compressed, encrypted) with very different sizes.

🎯 Mini exercise

A queue identifier must distinguish 65,536 queues. How many bits does it need?

Answer

log2(65,536) = 16 bits. NVMe queue identifiers are 16-bit fields verified.

1.2 Bits and bytes

🧒 Kid analogy

A bit is one light switch: on or off. A byte is a row of eight switches. With eight switches you can make 256 different patterns — enough to give every letter, digit and punctuation mark its own pattern.

Simple explanation. A bit is a 0 or 1. A byte is 8 bits. Bigger units are built from bytes: a 16-bit “word”, a 32-bit “dword” (double word), a 64-bit “qword”. NVMe and PCIe documents talk constantly about dwords — an NVMe command is sixteen dwords (64 bytes), a completion is four dwords (16 bytes) verified.

Engineering explanation. Three skills matter:

  1. Hexadecimal. One hex digit = 4 bits. 0x1000 (often written 1000h in specifications) = 4096 decimal. You must read hex as fluently as decimal, because every register offset, address and field is in hex.
  2. Bit numbering and masks. Bit 0 is the least-significant bit. To extract bits 19:16 of a value v: (v >> 16) & 0xF. Fields such as CAP.DSTRD (Doorbell Stride, bits 35:32 of the 64-bit Controller Capabilities register) are extracted exactly this way verified.
  3. Endianness. A multi-byte value stored in memory can put its least-significant byte at the lowest address (little-endian — x86, most Arm systems, and NVMe data structures verified) or its most-significant byte first (big-endian). PCIe specifications draw packet headers byte by byte with the most-significant bit on the left, while payload bytes keep their memory address order. The same bytes can therefore “look different” in a register view, a memory dump and a packet view — a classic source of decode mistakes.
UnitDecimal (SI) meaningBinary (IEC) unitBinary meaningDifference
KB (kilobyte)1,000 BKiB (kibibyte)1,024 B2.4%
MB1,000,000 BMiB1,048,576 B4.9%
GB109 BGiB1,073,741,824 B7.4%
TB1012 BTiB1,099,511,627,776 B10.0%

Drive marketing uses decimal units; operating-system tools often show binary units (and sometimes mislabel them “GB”). Memory page sizes and logical block sizes are binary (4 KiB, 512 B). Network and link rates are decimal (8 GT/s, 1 Gb/s = 109 bits per second).

Practical example. A drive sold as “1 TB” holds about 1012 bytes, which an OS reporting in binary shows as about 931 GiB. Nothing is missing.

# Python: decode a little-endian dword from bytes, then pull out a bit field
raw = bytes([0xFF, 0x03, 0x01, 0x00])   # four bytes as they sit in memory, lowest address first
v = int.from_bytes(raw, "little")        # 0x000103FF
mqes = v & 0xFFFF                         # bits 15:0  -> 0x03FF = 1023
print(hex(v), mqes, mqes + 1)            # a 0's-based field: 1023 means 1024 entries

Common misconception. “0x3FF in a size field means 1023 entries.” In NVMe many count fields are 0's-based: the stored value is one less than the real count verified. Always check the field's definition.

🎯 Mini exercise

(a) Convert 0x1008 to decimal. (b) The bytes in memory are 00 10 00 00; what little-endian dword is that? (c) How many bytes is 16 dwords?

Answer

(a) 4104. (b) 0x00001000 = 4096. (c) 64 bytes — the size of an NVMe submission queue entry.

1.3 Memory

🧒 Kid analogy

Memory is the classroom's wall of numbered trays. Every tray has a number painted on it (its address) and holds exactly one byte. Anybody who knows the number can put something in or take something out. When the school closes for the night, the trays are emptied — memory forgets when the power goes off.

Simple explanation. Main memory (RAM, Random Access Memory, usually DRAM — Dynamic RAM) is a huge array of bytes, each with a numeric address. It is fast compared with storage but volatile: it loses its contents without power.

Engineering explanation. Memory is a hierarchy. Each level is bigger and slower than the one above:

LevelTypical sizeTypical access latencyNotes
CPU registersHundreds of bytes per core< 1 nsOperated on directly by instructions
L1 / L2 / L3 cachesKiB to hundreds of MiB~1 ns to tens of nsHardware-managed copies of memory in fixed-size lines (64 bytes is common)
DRAMGiB to TiB~80–150 nsVolatile; host-side home of NVMe queues and data buffers
NVMe SSD (NAND)TB~tens of µs read; writes often absorbed by device buffersNon-volatile
Hard diskTB~several msMechanical

All numbers in that table are orders of magnitude impl; your platform will differ. The pattern is what matters: each step down costs roughly 10× to 1000× more time. Storage engineering is largely about hiding the bottom of this table.

Caches create a subtle problem for devices. When the CPU writes a command into memory, the newest bytes may sit in a CPU cache, not yet in DRAM. When a device later reads that memory via DMA, it must see the newest bytes. Platforms solve this with cache coherence: on most x86 servers, device DMA reads snoop the CPU caches; on some Arm and embedded platforms, drivers must explicitly clean or invalidate caches impl. Linux hides this behind its DMA API.

Practical example. When Linux creates an NVMe I/O submission queue of 1,024 entries, it allocates 1,024 × 64 = 65,536 bytes of DRAM that the device is permitted to read. The queue lives in host memory, not on the SSD.

Common misconception. “The NVMe queues live inside the SSD.” For NVMe over PCIe, queues normally live in host memory. An optional Controller Memory Buffer (CMB) can let queues live in device memory instead version — but that is the exception, advertised through CMBLOC/CMBSZ registers at offsets 38h/3Ch verified.

🎯 Mini exercise

A completion queue has 256 entries of 16 bytes. How many bytes, and how many 4 KiB pages?

Answer

4,096 bytes = exactly one 4 KiB page.

1.4 CPU

🧒 Kid analogy

The CPU is the teacher who follows a recipe book one line at a time, very fast: “take tray 12, add tray 13, put the answer in tray 14.” Modern schools have many teachers (cores), each with their own recipe.

Simple explanation. The CPU (Central Processing Unit) runs programs. A program is a list of instructions. The CPU repeatedly fetches the next instruction, decodes it, executes it and moves on. Modern CPUs have many cores, each an independent instruction runner.

Engineering explanation. From an I/O engineer's viewpoint, the CPU does only two things to the outside world: load (read from an address) and store (write to an address). Whether that address is DRAM or a device register is decided by the platform's address decoding, not by the instruction. Several properties of modern CPUs matter for drivers:

  • Out-of-order execution and write buffering. CPUs may reorder memory operations for speed. Drivers use memory barriers (for example Linux wmb(), or the ordering built into writel()) so that the command bytes in memory are globally visible before the doorbell write that tells the device to fetch them. Get this wrong and the device may fetch a half-written command.
  • Uncached device accesses. Device registers are mapped uncached (or write-combining). A load from an uncached device register stalls the core until the answer travels to the device and back — often around a microsecond or more across PCIe impl, thousands of instruction slots. A store can be posted: the core hands it off and continues.
  • Per-core work. Because each core can submit I/O independently, an interface that forces all cores through one queue and one lock wastes them. This is a central motivation for NVMe's per-core queues (Chapter 3).

Practical example. A 3 GHz core executes about 3 billion cycles per second. If a device register read costs 1 µs, that is ~3,000 cycles of stall per read. If an old storage interface needed several register reads per command, at 1 million commands per second a single core would be saturated by stalls alone. derived

Common misconception. “The CPU moves the data from the SSD into memory.” In NVMe, the CPU never touches the data bytes during a transfer; the SSD's DMA engine writes them directly into memory (§1.15).

🎯 Mini exercise

Why does it matter whether a doorbell write is “posted”?

Answer

A posted write lets the CPU continue immediately instead of waiting for a round trip to the device, so ringing a doorbell costs the core very little time. PCIe Memory Writes are posted transactions — no completion is returned verified.

1.5 Registers

🧒 Kid analogy

The teacher's desk has a few slots where the work in progress sits — those are the CPU's registers. The librarian also has a small control panel on the library door with labelled switches and lights: “ON”, “READY”, “ERROR”. The teacher can flip switches and read lights from the classroom. Those switches and lights are device registers.

Simple explanation. “Register” means two different things, and you must never confuse them:

  • CPU registers — tiny, ultra-fast storage inside the core (for example rax on x86-64, x0 on Arm64), used by instructions.
  • Device (hardware) registers — control and status locations inside a device that software reads and writes through addresses. The NVMe controller registers (CAP, VS, CC, CSTS, AQA, ASQ, ACQ, doorbells) are of this kind.

Engineering explanation. Device registers look like memory but are not memory. Reading or writing them can have side effects:

Register behaviourMeaningExample
Read-only (RO)Reports capabilities or status; writes ignoredNVMe CAP at 00h, VS at 08h verified
Read/write (RW)Software sets configurationNVMe CC at 14h — e.g. CC.EN enables the controller
Write-only / triggerA write causes an actionNVMe doorbells from 1000h; NSSR at 20h triggers an NVM Subsystem Reset when a specific value is written
Write-1-to-clear (RW1C)Writing 1 to a bit clears it; writing 0 does nothingMany PCIe status bits (e.g. AER status registers)
Status reflecting internal stateChanges on its own as hardware progressesNVMe CSTS at 1Ch: CSTS.RDY, CSTS.CFS (Controller Fatal Status)

Because of side effects, compilers and CPUs must not cache, merge, or drop register accesses; drivers use special accessors (readl/writel in Linux) and the platform maps register regions as uncached.

// Enabling an NVMe controller — the shape of the handshake (details in Part IX)
regs = map(BAR0)                         // device registers appear at addresses
cap  = read64(regs + 0x00)               // CAP: what the controller supports
write32(regs + 0x24, aqa)                // AQA: admin queue sizes
write64(regs + 0x28, asq_bus_addr)       // ASQ: where the admin SQ lives in host memory
write64(regs + 0x30, acq_bus_addr)       // ACQ: where the admin CQ lives
write32(regs + 0x14, cc | EN)            // CC.EN = 1: "please start"
wait_until(read32(regs + 0x1C) & RDY)    // CSTS.RDY = 1: "I am ready" (bounded by CAP.TO)

Practical example. When a driver writes CC.EN = 1, it is not storing a number for later; it is asking the controller to begin initialising. The controller answers asynchronously by setting CSTS.RDY. A driver that writes CC.EN and immediately submits commands, without waiting for RDY, is buggy.

Common misconception. “If I write a value to a register, reading it back returns the same value.” Not for trigger, RW1C, or status registers. Read-back verification of device registers is a classic way to cause bugs.

🎯 Mini exercise

Which is the CPU register and which the device register: (a) the x86 instruction pointer, (b) NVMe CSTS? Which one can a PCIe analyzer observe being accessed?

Answer

(a) CPU register, invisible outside the core. (b) Device register; accesses appear on PCIe as Memory Read/Write TLPs to BAR0 + 1Ch, so an analyzer can see them.

1.6 Address spaces

🧒 Kid analogy

The school has several numbering systems. Classroom trays are numbered 1, 2, 3… The lockers in the gym are also numbered 1, 2, 3… “Number 5” means nothing until you know which numbering system you are in. An address space is a numbering system.

Simple explanation. An address only has meaning inside an address space. A computer has several.

Engineering explanation.

Address spaceWho uses itWhat it numbersRelevance to NVMe/PCIe
Virtual address spaceEach process; the kernelWhat programs see; translated by the MMUYour application's buffer address

The platform's physical address map decides which physical addresses go to DRAM and which go to devices. During PCI enumeration, firmware or the OS assigns each device's BARs a window in this map. A CPU store to an address inside that window becomes a PCIe Memory Write to the device. This is memory-mapped I/O (MMIO).

# Show the physical address map (needs root to see real addresses; read-only)
sudo cat /proc/iomem | head -40
# Show which physical window the NVMe controller's BAR0 occupies (read-only)
lspci -vv -d ::0108 | grep -i "Region 0"

Illustrative, abbreviated meaning of what you will find: ranges labelled “System RAM”, ranges labelled “PCI Bus …” and inside them a range labelled with the NVMe device's address and the driver name nvme. Exact ranges are impl per platform.

Common misconception. “An address is an address.” Most painful DMA bugs come from putting an address from the wrong space into a device structure — for example a kernel virtual address into a PRP entry.

🎯 Mini exercise

Which address space does each belong to: (a) 0x7ffd1234a000 printed by a user program; (b) the value in ASQ; (c) BAR0 as shown by lspci?

Answer

(a) user virtual; (b) device-visible DMA address (equal to physical address when no IOMMU translation is applied); (c) physical/system memory space (the CPU's view of the device window).

1.7 Virtual memory

🧒 Kid analogy

Each pupil gets a notebook with pages numbered 1 to 100 — their own private numbering. A secret index at the front says which real tray each notebook page is stored in. Two pupils can both write on “page 7” without clashing, because the index sends them to different trays.

Simple explanation. Each program sees its own private, contiguous range of addresses — virtual memory. The CPU's MMU (Memory Management Unit) translates each virtual address to a physical address using page tables maintained by the operating system. Translation works in fixed-size pages, commonly 4 KiB, with larger “huge pages” (2 MiB, 1 GiB on x86-64) available.

Engineering explanation. Page tables map virtual page numbers to physical frame numbers plus permission bits. A TLB (Translation Lookaside Buffer) caches recent translations. Key consequences for storage:

  1. Contiguous virtual ≠ contiguous physical. A 64 KiB user buffer is 16 pages that may be scattered anywhere in DRAM. A device cannot use virtual addresses (it has no access to the process's page tables), so the driver must describe each physical piece. NVMe's PRP (Physical Region Page) lists and SGLs (Scatter Gather Lists) exist precisely to describe such scattered buffers (Part XII).
  2. Pages can move. The OS may swap or migrate pages. Memory under DMA must be pinned so it stays put until the device is done.
  3. Offsets survive translation. The low 12 bits of an address (offset within a 4 KiB page) are identical in virtual and physical addresses. That is why NVMe's PRP rules talk about offsets within a memory page, whose size is set by CC.MPS.

Practical example. fio --direct=1 --bs=128k issues 128 KiB reads into a user buffer. Without huge pages, that buffer is 32 separate 4 KiB physical pages; the NVMe driver must build a PRP list or SGL with an entry per page (minus merges where pages happen to be adjacent).

Common misconception. “Giving the device my buffer pointer is enough.” The pointer is virtual. The device needs device-visible addresses of every physical piece.

🎯 Mini exercise

A virtual address is 0x7f00_0000_3a40. With 4 KiB pages, what is the page offset, and what will the low 12 bits of the physical address be?

Answer

Offset = 0xa40 (2,624). The physical address's low 12 bits are also 0xa40; only the page-number part changes.

1.8 Physical memory

🧒 Kid analogy

The physical trays are the real ones on the real tables. A big school may have two buildings, each with its own trays; fetching from the other building's trays is possible, but slower.

Simple explanation. Physical memory is the real DRAM, addressed by physical addresses after translation. Devices reach it through the platform's I/O path.

Engineering explanation. Three topics matter to storage engineers:

  • NUMA (Non-Uniform Memory Access). Multi-socket servers attach DRAM and PCIe root ports to each socket. A device attached to socket 0 writing into memory on socket 1 crosses the inter-socket link, adding latency and consuming shared bandwidth impl. Linux exposes a device's node in /sys/bus/pci/devices/<BDF>/numa_node.
  • IOMMU (Input–Output Memory Management Unit). Many platforms put a translation unit between devices and memory (Intel VT-d, AMD-Vi, Arm SMMU). The device then issues IO virtual addresses (IOVAs), translated by the IOMMU to physical addresses with permission checks. With an IOMMU, the address in a PRP entry is an IOVA, not a physical address. A wrong or unmapped IOVA causes an IOMMU fault (a DMA remapping fault), logged by the kernel.
  • DMA-able memory. Not all physical memory may be reachable by every device (older devices with 32-bit addressing limits). Linux uses bounce buffers (swiotlb) to copy data into reachable memory when needed — at a performance cost.
# Which NUMA node is the NVMe device attached to? (read-only)
cat /sys/bus/pci/devices/0000:01:00.0/numa_node     # replace with your BDF
# Is an IOMMU active, and which group is the device in? (read-only)
ls /sys/kernel/iommu_groups/ | head
readlink /sys/bus/pci/devices/0000:01:00.0/iommu_group
dmesg | grep -i -e DMAR -e IOMMU -e AMD-Vi -e SMMU | head

Common misconception. “The device writes to physical addresses.” Only if no IOMMU translation is applied. The safe mental model is: the device writes to device-visible addresses, which the platform may translate.

🎯 Mini exercise

An SSD on socket 1 is driven by an application pinned to socket 0, with buffers in socket-0 memory. Name two costs.

Answer

(1) DMA data and completion writes cross the inter-socket link, adding latency; (2) interrupts and doorbell writes may also cross sockets, and cache lines bounce between sockets — reducing IOPS and raising tail latency impl.

1.9 I/O

🧒 Kid analogy

I/O — input and output — is everything that crosses the classroom door: requests going out to the library, books coming back, notes from the playground. Inside the classroom is “computing”; through the door is “I/O”.

Simple explanation. Input/Output (I/O) is communication between the CPU-and-memory world and everything else: disks, SSDs, network cards, keyboards, GPUs.

Engineering explanation. There are three classic ways to move data between a CPU and a device:

MethodHowCPU costWhere you see it
Port I/O (PIO)Special instructions to a separate I/O address spaceHigh; CPU moves every byteLegacy x86 devices, old IDE PIO modes
Memory-mapped I/O (MMIO)Ordinary loads/stores to device-owned addressesLow for control; high if used for bulk dataDevice registers, NVMe doorbells
Direct Memory Access (DMA)The device itself reads/writes host memoryVery low per byte; CPU only sets up and completesAll bulk storage and network data; NVMe commands, data, completions

Modern high-performance I/O uses MMIO for small control signals (“the tail is now 17”) and DMA for everything bulky. I/O is also asynchronous: a program issues a request, the CPU does other work, and later is notified of completion. Linux's block layer (blk-mq) and interfaces such as io_uring exist to keep many requests in flight at once.

From the application's view, storage I/O is “read N bytes at offset X”. The file system translates offsets into logical block addresses (LBAs), the block layer queues requests, and the driver turns them into device commands.

Practical example. iostat -x 1 shows, per device, reads and writes per second, throughput and average queue size — the outward signs of I/O traffic.

Common misconception. “I/O is slow because the bus is slow.” Often it is slow because of waiting: for the media, for the queue, for an interrupt, for a lock. Bandwidth and latency are different problems.

🎯 Mini exercise

Classify: (a) the driver writes a doorbell; (b) the SSD writes 4 KiB of data into a buffer; (c) the SSD writes a 16-byte completion.

Answer

(a) MMIO store by the CPU; (b) DMA by the device; (c) DMA by the device (it is just a small memory write).

1.10 Devices

🧒 Kid analogy

Devices are the specialist rooms of the school: library, kitchen, gym, music room. Each does one kind of job very well and each has its own way of being asked.

Simple explanation. A device is any hardware unit the computer uses besides the CPU and memory: SSDs, network adapters, GPUs, USB controllers.

Engineering explanation. In PCIe terms, a device exposes one or more functions, each identified by a Bus/Device/Function number (BDF) and described by a configuration space header: Vendor ID, Device ID, Class Code, BARs and a list of capabilities. Software discovers devices by reading configuration space (enumeration) — it does not need to know in advance what is plugged in. The class code tells software what kind of function it is; an NVMe controller over PCIe identifies itself with class code 01 08 02 — base class 01h (mass storage), sub-class 08h (non-volatile memory controller), programming interface 02h (NVM Express) verified.

A modern SSD presents itself as at least one PCIe function containing one NVMe controller. Advanced drives may present multiple functions (for example with SR-IOV, Single Root I/O Virtualization) or multiple ports.

lspci -nn                 # every PCI function with [vendor:device] and class
lspci -d ::0108 -vv       # only NVMe-class functions, verbose (some fields need root)
ls /sys/bus/pci/devices/  # the same functions, as Linux sees them

Common misconception. “Device = drive.” One physical drive can expose several functions, several controllers and many namespaces. Part IX separates these carefully.

🎯 Mini exercise

You see a function with class 0108 and prog-if 02. What is it, and which Linux driver will normally claim it?

Answer

An NVM Express controller; the in-kernel nvme driver (built on nvme-core).

1.11 Controllers

🧒 Kid analogy

The library has thousands of shelves, but you never talk to the shelves. You talk to the librarian, who knows where everything is, which shelves are broken, and how to fetch several books at once. The librarian is the controller.

Simple explanation. A controller is the “brain” in front of a device that understands the interface language and manages the hardware behind it.

Engineering explanation. The word is used on both sides of a link:

  • Host controllers sit on the host side: an AHCI (Advanced Host Controller Interface) SATA controller in the chipset, or a SAS HBA (Host Bus Adapter). The SATA drive behind them has its own device controller.
  • The NVMe controller sits inside the SSD, directly on PCIe. There is no separate host storage controller: the CPU's PCIe root port connects straight to the SSD's controller. In the NVMe specification, “controller” is a precise term — the interface between a host and an NVM subsystem, exposing registers, queues and namespaces.
  • Internally, an SSD controller is a system-on-chip: several embedded CPU cores running firmware, a PCIe interface, DMA engines, a DRAM or host-memory-buffer interface, an ECC engine, encryption, and multiple NAND channel controllers impl.

Common misconception. “NVMe defines how the SSD stores data in NAND.” NVMe defines the host-visible interface. The FTL, garbage collection and NAND layout are the controller vendor's business (Chapter 2).

🎯 Mini exercise

For a SATA SSD and an NVMe SSD, list every “controller” between the CPU and the NAND.

Answer

SATA: CPU → PCIe/internal fabric → AHCI host controller (chipset) → SATA link → SSD's device controller → NAND. NVMe: CPU → PCIe root port → SSD's NVMe controller → NAND. One fewer hop and one fewer protocol translation.

1.12 Buses

🧒 Kid analogy

The old school had one shared corridor. Only one person could walk down it at a time, so everyone queued and shouted “my turn!”. The new school gives every room its own private, two-lane road straight to a central roundabout — people can travel both ways at once, and rooms do not wait for each other.

Simple explanation. A bus is a shared communication pathway. The word survives even though modern interconnects such as PCIe are point-to-point links joined by switches.

Engineering explanation. The evolution matters because it explains PCIe's design:

PropertyConventional PCI (parallel, shared)PCI Express (serial, point-to-point)
TopologyMany devices share one set of wiresEach link connects exactly two ports; switches fan out
SignallingWide parallel bus with a common clock (32/64 bits, 33/66 MHz)Differential serial lanes, embedded clocking; x1, x2, x4, x8, x16 lanes
DirectionOne transaction at a time, half duplexFull duplex: each lane has a transmit and a receive pair
TransactionsBus cycles with arbitrationPackets (TLPs) with headers, routing, flow control and link-level retry
Bandwidth sharingAll devices shareEach link has its own bandwidth (shared only upstream of a switch)
Software modelConfig space, BARsSame model preserved — PCIe is software-compatible with PCI enumeration

Two ideas carry forward. A device that starts transactions on its own is a bus master (in PCIe, any requester); a device must be allowed to do so by the Bus Master Enable bit in its Command register before it can DMA verified. And the bus's ordering rules decide whether a later write can overtake an earlier one — critical for “data before completion” correctness.

BWraw = rate × lanes × encoding efficiency ÷ 8
  • BWraw — raw bandwidth per direction in bytes/s, before packet overhead
  • rate — transfers per second per lane (e.g. 16 GT/s for Gen4)
  • lanes — link width (e.g. 4)
  • encoding efficiency — 8/10 for Gen1–2, 128/130 for Gen3–5

Example: Gen4 x4 = 16 × 109 × 4 × 128/130 ÷ 8 ≈ 7.88 GB/s per direction before TLP/DLLP overhead derived. Real NVMe throughput is lower because each TLP carries header, sequence number and CRC bytes, and the link also carries flow-control and acknowledgement packets.

Common misconception. “x16 is 16 times faster for an SSD.” A typical NVMe SSD links at x4. Width only helps if the device uses it.

Compute raw per-direction bandwidth for Gen3 x4 and Gen5 x4.

Answer

1.13 Drivers

🧒 Kid analogy

The teacher speaks “classroom”. The librarian speaks “library”. A translator who knows both languages — and the library's exact rule book — stands between them. That translator is the driver.

Simple explanation. A driver is software (usually part of the operating system kernel) that knows how to operate one kind of device and presents it to the rest of the system through a standard interface.

Engineering explanation. On Linux, the PCI core enumerates functions and matches each against drivers' ID tables (vendor/device IDs or class codes). For a match, it calls the driver's probe(). The NVMe driver's probe, in outline:

nvme_probe(pci_dev):
    pci_enable_device_mem(pci_dev)        // enable memory decoding
    pci_set_master(pci_dev)               // set Bus Master Enable: allow device DMA
    dma_set_mask(64-bit)                  // tell DMA API what the device can address
    regs = ioremap(BAR0)                  // map controller registers (MMIO)
    reset/disable controller, read CAP    // learn MQES, DSTRD, TO, MPSMIN/MAX…
    allocate admin SQ/CQ in DMA-able memory
    program AQA/ASQ/ACQ, set CC.EN, wait CSTS.RDY
    Identify Controller, Identify Namespace(s)   // admin commands
    Set Features (Number of Queues)              // how many I/O queues?
    allocate MSI-X vectors, Create I/O CQ/SQ pairs (often one per CPU)
    register block devices /dev/nvmeXnY with blk-mq

Because NVMe is a standard interface, one in-box driver works with SSDs from every vendor — a major reason for NVMe's success compared with the vendor-specific PCIe SSDs that preceded it (Chapter 3).

lspci -k -d ::0108                       # "Kernel driver in use: nvme"
ls -l /sys/bus/pci/drivers/nvme/          # functions bound to the nvme driver
cat /sys/class/nvme/nvme0/model /sys/class/nvme/nvme0/firmware_rev

Common misconception. “The driver is the firmware.” The driver runs on the host CPU; firmware runs on the SSD controller's CPUs. A bug can be in either — a central question in debugging.

🎯 Mini exercise

Why must the driver call pci_set_master() before creating queues?

Answer

Without Bus Master Enable, the device may not issue memory requests, so it could never fetch commands or write completions. Symptom: doorbells written, nothing ever completes.

1.14 Interrupts

🧒 Kid analogy

The teacher could walk to the answer box every few seconds to check for “done” notes — tiring and wasteful. Instead, the librarian taps the teacher on the shoulder when a note arrives. The tap is an interrupt. With many librarians, each one taps a different teacher, so nobody is overwhelmed.

Simple explanation. An interrupt is a signal from a device that makes the CPU pause what it is doing and run a small handler routine (an interrupt service routine, ISR). The alternative is polling — repeatedly checking for completion.

Engineering explanation. PCI-family devices have three interrupt mechanisms:

MechanismHow it is signalledVectorsNotes
INTx (legacy)Conventional PCI used physical wires; PCIe emulates them with Assert/Deassert INTx messages4 shared lines (INTA–INTD)Level-triggered, often shared, slow to service
MSI (Message Signaled Interrupts)Device performs a memory write of a data value to an address programmed by the OSUp to 32 per functionConfigured in an MSI capability in config space
MSI-XSame idea, with a table of independent address/data pairs located in a BARUp to 2048 per functionEach vector can target a different CPU; Linux NVMe typically uses one vector per I/O queue

NVMe relates interrupts to completion queues: when creating an I/O CQ, the host chooses an interrupt vector for it. Interrupts carry no completion data; the handler must read the CQ entries in memory and use the phase tag bit to know which entries are new. The controller may also coalesce interrupts — signal once for several completions — controlled by the Interrupt Coalescing feature. NVMe also offers interrupt mask registers INTMS (0Ch) and INTMC (10h) for pin-based and single-message MSI use verified.

grep nvme /proc/interrupts      # one line per vector; counts per CPU column
lspci -vv -d ::0108 | grep -A3 MSI-X     # "MSI-X: Enable+ Count=..." (root needed for detail)

Common misconception. “An interrupt means my command finished successfully.” It means something may be in the CQ. The CQE's status field tells you success or failure; and an interrupt can arrive for several completions, or (with coalescing) be delayed.

🎯 Mini exercise

On a PCIe analyzer, what does an MSI-X interrupt look like?

Answer

A Memory Write TLP from the device to the address in the vector's MSI-X table entry, carrying the 32-bit message data. It is posted, so there is no completion TLP for it.

1.15 DMA

🧒 Kid analogy

Without DMA, the teacher must personally walk to the library door, take each page from the librarian and carry it to the right tray — thousands of trips. With DMA, the teacher writes on the request slip “please put the pages in trays 400 to 407”, and the librarian carries them there directly while the teacher keeps teaching.

Simple explanation. Direct Memory Access lets a device read or write host memory itself, without the CPU copying each byte.

Engineering explanation. On PCIe, DMA is simply the device acting as a requester of memory transactions: Memory Read requests (answered by Completions with Data) to read host memory, and posted Memory Write requests to write it. Everything an NVMe controller does to host memory is DMA:

  • fetching SQ entries (memory reads),
  • fetching PRP lists or SGL segments (memory reads),
  • reading write-command data (memory reads) or writing read-command data (memory writes),
  • posting CQ entries (memory writes),
  • signalling MSI/MSI-X interrupts (memory writes).

DMA needs four things to be correct: the right address (device-visible, possibly IOMMU-translated), the right length, permission (Bus Master Enable; IOMMU mapping), and ordering (the CQE must not become visible before the data it reports). PCIe ordering rules ensure that posted writes from one requester are not reordered past each other under default ordering attributes, which is why a device can write data and then the CQE and the host sees them in that order verified — but relaxed ordering attributes and platform behaviours complicate this, a topic for Part V.

Practical example. A 128 KiB read with Max_Payload_Size of 256 bytes arrives in host memory as at least 512 Memory Write TLPs from the SSD — none of which the CPU executed an instruction for. derived

Common misconception. “DMA means the device can write anywhere.” With an IOMMU, the device can write only where the OS mapped it; without one, it can write to any address it can form — a security and robustness concern.

🎯 Mini exercise

List the DMA operations an NVMe controller performs for a single 4 KiB write command whose data pointer is PRP1 only, with MSI-X enabled.

Answer

(1) Memory Read of the 64-byte SQE (answered by CplD), (2) Memory Read(s) of the 4 KiB write data from the PRP1 page, (3) Memory Write of the 16-byte CQE, (4) Memory Write of the MSI-X message. Doorbell writes are host-initiated MMIO, not device DMA.

📌 Remember — the fifteen ideas in one paragraph

Information is encoded in bits and bytes held at addresses in memory. The CPU runs instructions that load and store addresses; some addresses are DRAM and some are device registers, depending on which address space and which window they fall in. Programs use virtual addresses; devices use device-visible addresses that may pass through an IOMMU. I/O crosses buses — today, PCIe links — to devices whose controllers speak a protocol. A driver configures the controller through registers, then the controller does the bulk work by DMA and reports progress with interrupts that are themselves memory writes.
