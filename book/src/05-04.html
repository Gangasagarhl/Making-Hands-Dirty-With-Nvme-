PART XV

Error Handling

Errors on an NVMe SSD live on at least three floors of the building. On the top floor, the NVMe controller reports command outcomes in the 15-bit status field of every CQE, keeps an Error Information log, raises asynchronous events, and — in the worst case — declares itself fatally broken through CSTS.CFS. On the middle floor, the PCIe transaction and data link layers detect malformed, poisoned, unexpected and missing packets and classify them as correctable, uncorrectable non-fatal or uncorrectable fatal. Underneath, the physical layer suffers receiver errors that the data link layer quietly repairs with replays. AER (Advanced Error Reporting) is the instrument panel for the PCIe floors. This part teaches each floor, then — the real skill — how to correlate them so you can tell a software bug from a driver bug, an NVMe protocol error, a PCIe transaction error, a link problem, a firmware bug or a failing NAND die.

44 NVMe Errors (Deep-Dive Module: NVMe Errors)

44.1 Why this chapter exists

Every NVMe command ends with a status. Most of the time it is zero. When it isn't, the exact Status Code Type (SCT) and Status Code (SC), plus the DNR (Do Not Retry) and More bits, tell the host whether the command was malformed, rejected for a state reason, failed by the media, aborted, or failed because of a path problem — and whether retrying could help. Misreading status (e.g. treating "Invalid Field" as a media failure, or retrying a DNR error forever) causes wrong RMAs, data loss and endless retry storms. Beyond per-command status, NVMe has controller-level mechanisms — asynchronous events, the Error Information log, SMART/Health critical warnings, and the Controller Fatal Status bit — that you must read alongside.

44.2 Learning objectives

  • Beginner: locate the status field in a CQE and decode SCT/SC for success, invalid opcode, invalid field, LBA out of range.
  • Intermediate: classify status codes into generic, command specific, media and data integrity, path related; interpret DNR, More, CRD.
  • Advanced: use the Error Information log, Asynchronous Event Requests and SMART critical warnings to build a controller-level error picture; understand abort and CFS handling.
  • Senior: design retry/escalation policy; separate host-induced from device-induced statuses.
  • Trace-analysis: decode status from a captured CQE MWr payload.
  • Debugging: apply the five failure patterns.
  • Validation: design negative tests that elicit specific statuses safely.

44.3 Kid story and analogy boundary

🧒 Kid analogy

Every receipt the warehouse gives you has a stamp. Green "OK". Blue stamps mean "you filled the card wrong" (no such book type, a box ticked that makes no sense, a card number you already used). Orange stamps are "that particular kind of request didn't work" (the shelf you asked to build is the wrong size). Red stamps mean "the book itself is damaged" (we couldn't read page 7). Purple means "the road to that warehouse is blocked". And there's a small "don't bother asking again" box that is ticked when retrying won't help. If the whole warehouse catches fire, it doesn't stamp anything — it hangs a big sign on the door (CSTS.CFS).

🧩 Analogy boundary

Represents: SCT categories, DNR. Hides: that status can only be delivered if the controller is healthy enough to write a CQE; that some failures produce no CQE (timeouts); that statuses are command-set specific (the same SC value means different things under different SCTs and command sets). Misleading when: you assume a "red stamp" always means the SSD's NAND is failing — some media/data-integrity codes (e.g. end-to-end guard check errors) may reflect host-supplied protection information mismatches.

44.4 The status field

CQE Dword 3: bits 15:0 CID, bit 16 Phase Tag, bits 31:17 Status Field (SF). Inside the 15-bit SF:

SF bitCQE DW3 bitFieldMeaning
7:024:17SC — Status CodeSpecific code within the type
10:827:25SCT — Status Code Type0 Generic, 1 Command Specific, 2 Media and Data Integrity, 3 Path Related, 4–6 reserved, 7 Vendor Specific
12:1129:28CRD — Command Retry DelaySelects one of CRDT1–3 from Identify Controller (in 100 ms units) if host supports it

🔍 Linux status notation

Linux prints NVMe status as the 15-bit SF value shifted down (i.e. (DW3 >> 17)), so 0x281 = SCT 2, SC 81h (Unrecovered Read Error), and 0x4002 = DNR set, SCT 0, SC 02h (Invalid Field in Command). On a trace, the raw DW3 of a CQE MWr is (SF << 17) | (P << 16) | CID: Unrecovered Read Error with P=1, CID 0x0042 → 0x0503_0042.

44.7 Error Information log (Log Identifier 01h)

Each entry is 64 bytes; the controller keeps up to ELPE+1 entries (Identify Controller Error Log Page Entries, zero-based). Entries record (verified field set; exact byte offsets — consult the Base spec):

  • Error Count — 64-bit unique, incrementing identifier (0 = invalid entry).
  • Submission Queue ID and Command ID — which command (FFFFh if not command-related).
  • Status Field — the status that was (or would have been) returned, including Phase Tag position conventions.
  • Parameter Error Location — byte and bit within the SQE that caused an Invalid Field — invaluable for host bugs.
  • LBA and Namespace — first LBA affected.
  • Vendor Specific Information Available, Transport Type, Command Specific Information, Transport Type Specific Information.
sudo nvme error-log /dev/nvme0 -e 16        # last 16 entries (read-only)
sudo nvme smart-log /dev/nvme0              # media_errors, num_err_log_entries, critical_warning
sudo nvme get-log /dev/nvme0 --log-id=0x01 --log-len=1024   # raw bytes
🏭 Implementation-dependent

Which errors a controller records in the Error log is partly implementation-defined: some log every non-zero status, some only selected ones. Many consumer drives log host-caused Invalid Field errors from probing commands (e.g. the OS querying an unsupported log page), producing large num_err_log_entries counts that are not health problems. Always read the entries before concluding.

44.8 Asynchronous events

The host keeps one or more Asynchronous Event Request commands (admin opcode 0Ch) outstanding; they have no timeout. When something happens, the controller completes one with DW0 describing the event:

DW0 bitsFieldValues
2:0Asynchronous Event Type0 Error status, 1 SMART/Health status, 2 Notice, 6 I/O Command specific status, 7 Vendor specific
15:8Asynchronous Event InformationType-specific (e.g. for Error: 00h write to invalid doorbell register, 01h invalid doorbell write value, 02h diagnostic failure, 03h persistent internal error, 04h transient internal error, 05h firmware image load error; for Notice: namespace attribute changed, firmware activation starting, …)
23:16Log Page IdentifierLog page to read to clear the event (e.g. 01h Error, 02h SMART, 04h Changed Namespace List)

Events of a type are masked until the host reads the indicated log page (with RAE clear). Async events are the only way a controller tells the host about errors that are not tied to a command — notably a bad doorbell write, which otherwise would just silently be ignored.

🐞 Debugging

When a doorbell write seems to "do nothing", look for an async event with type 0 / info 00h or 01h on the admin CQ. If your driver doesn't keep AERs outstanding (custom/bring-up drivers often don't), you've thrown away the controller's only way to tell you.

44.9 Abort and Controller Fatal Status

Abort (08h): CDW10 = SQID (15:0) and CID (31:16) of the target. Abort is best effort: completion DW0 bit 0 = 1 means the command was not aborted. The aborted command, if aborted, completes with SCT0/07h. Linux sends Abort on I/O timeout, then escalates to controller reset if the Abort itself times out.

CSTS.CFS (bit 1): the controller sets Controller Fatal Status when it cannot communicate through its normal mechanisms — no further CQEs are expected. Host response is a controller reset; if CSTS reads as 0xFFFFFFFF the issue is not CFS but that the device isn't answering MMIO at all (link down, surprise removal, reset in progress) — a PCIe-floor problem.

44.13 Labs

🧪 Lab 44.1 (beginner) — Decode CQE DW3 values SAFE

Objective: decode raw CQE status. Setup: values (synthetic): 0x0001_0010, 0x8005_0011, 0x0101_0012, 0x0503_0013, 0x8004_0014. Procedure: SF = DW3 >> 17; P = bit 16; CID = low 16 bits.

Solution

(1) CID 0x10, P=1, success. (2) DW3>>17 = 0x4002 → DNR=1, SCT0, SC 02h Invalid Field; P=1; CID 0x11. (3) 0x0101_0012 >> 17 = 0x80 → SCT0 SC80h → LBA Out of Range (NVM); P=1; CID 0x12. (4) 0x0503_0013 >> 17 = 0x281 → SCT2 SC81h Unrecovered Read Error; P=1. (5) 0x8004_0014 >> 17 = 0x4002 → DNR, Invalid Field; P=0 — phase 0 is legal after a wrap.

Extension: write a decoder that prints names for the codes in §44.5.

🧪 Lab 44.2 (intermediate) — Read error logs safely SAFE

Procedure: run the read-only commands in §44.7; correlate error entries' SQID/CID with any dmesg messages; classify each entry host vs device.

Solution

Entries with SQID 0 and status Invalid Field/Invalid Log Page are typically host probes (e.g. tools querying unsupported log pages). Entries on I/O queues with SCT 2 are media-related. Entries with SQID FFFFh are not command-related.

🧪 Lab 44.3 (advanced) — Elicit an Invalid Field error safely CAUTION

Objective: generate a known host error without risking data. Setup: test system. Procedure: issue a Get Log Page for an unsupported vendor log ID via nvme get-log /dev/nvme0 --log-id=0xC7 --log-len=512 (read-only admin command); observe the returned status and new Error log entry.

Solution

Expected: SCT1/09h Invalid Log Page or SCT0/02h Invalid Field (implementation may vary); Error count increments if the controller logs it. Demonstrates host-induced errors in the log.

Extension: compare behaviour across two drive models.

🧪 Lab 44.4 (senior forensic) — Is it the drive? SAFE

Given (synthetic): app reports checksum mismatch; NVMe statuses all success; namespace formatted with PI type 1; no E2E errors; error log empty; dmesg shows IOMMU faults from 02:00.0 at nearby times.

Solution

PI would have caught media/device corruption of the data with E2E check errors (82h/84h). Success with corruption plus IOMMU faults points to host-side DMA mapping problems (buffer reuse/unmapped) or app bugs. Confidence medium; next evidence: IOMMU strict mode reproduction, data capture of MWr payloads.

    Can't tell — the read failed (device unreachable); all-ones is a PCIe-level symptom.

  9. Intermediate How do E2E PI errors help localise corruption?
    Model answer

    Guard/ref tags verify data integrity and LBA association across the path.

  10. Intermediate What's the Parameter Error Location?
    Model answer

    Byte/bit in the SQE responsible for an invalid-field error.

  11. Advanced What's the Linux recovery ladder on timeout?
    Model answer

    Abort → controller reset → remove device if reset fails (impl-dependent details).

  12. Advanced When is an Abort considered successful?
    Model answer

    Completion DW0 bit 0 = 0 and the target completes with 07h; otherwise not aborted.

  13. Advanced Data Transfer Error: where to look?
    Model answer

    PCIe AER on device/root port, IOMMU faults, poisoned TLPs.

  14. Advanced How are async events re-armed?
    Model answer

    Read the indicated log page (RAE=0) and submit a new AER command.

  15. Advanced What's DLFEAT and its relation to 87h?

  16. Senior Design an error-handling policy for a storage array.
    Model answer

    Classify by SCT; retry transient (non-DNR) with backoff; rebuild from redundancy on 81h; quarantine on repeated; reset on CFS; correlate with AER and SMART.

  17. Senior How do you prove an RMA is justified?
    Model answer

    Model answer

45 PCIe Errors (Deep-Dive Module: PCIe Errors)

45.1 Why this chapter exists

PCIe was designed so that most physical-layer imperfections never reach software: LCRC (Link CRC) and the Ack/Nak replay protocol repair corrupted TLPs transparently. When errors do reach software, PCIe classifies them by who detected them and how bad they are. Understanding the classes — correctable, uncorrectable non-fatal, uncorrectable fatal — and the individual errors (Bad TLP, Bad DLLP, Replay Timer Timeout, Receiver Error, Completion Timeout, Unsupported Request, Completer Abort, Malformed TLP, Poisoned TLP, ECRC, Surprise Down…) lets you tell a marginal link from a broken driver from a dead device.

45.2 Learning objectives

  • Classify every major PCIe error into correctable / non-fatal / fatal and name the layer that detects it.
  • Explain which errors are "symptoms" (replays, completion timeouts) vs "causes".
  • Explain how errors are signalled (ERR_COR, ERR_NONFATAL, ERR_FATAL messages), and how baseline (Device Status) and advanced (AER) reporting differ.
  • Interpret error patterns in synthetic traces.
  • Apply five failure patterns.

45.3 Story and analogy

🧒 Kid analogy

Letters between two towns travel on a road with a postman. If rain smudges a letter, the receiving post office says "send that again please" and nobody else ever hears about it — that's a correctable error; the post office just keeps a tally. If a letter arrives addressed to a house that doesn't exist, the post office says "unsupported!" — the letter is lost but the road is fine: uncorrectable non-fatal. If the bridge collapses, no letters get through at all: uncorrectable fatal.

🧩 Where the analogy breaks

Severity of most uncorrectable errors is programmable (via the AER Severity register), not inherent; "non-fatal" refers to the link's reliability, not the impact on your application — a non-fatal Completion Timeout can still hang your NVMe command and crash a filesystem. And some correctable errors (Replay Timer Timeout, REPLAY_NUM Rollover) are the early warning of a bridge about to collapse.

45.6 Requester vs completer errors

For a non-posted request, errors split by role: the completer detects UR and CA and returns a completion with that status (and logs the error, possibly as advisory); the requester detects Completion Timeout and receives the UR/CA completion status, and logs Unexpected Completion if a completion matches nothing. For NVMe this matters because the device is the requester for all data-path reads (SQE fetch, write data, PRP lists). So a host-side problem servicing the device's reads appears in the device's AER registers as Completion Timeout — the SSD is reporting the host's failure.

📌 Remember

"The SSD logged a Completion Timeout" usually means "the SSD asked the host for something and the host never answered". Treat it as host/topology-side evidence first.

45.7 Signalling paths

Endpoint detects error
  ├─ updates Device Status (CED/NFED/FED/URD)         [baseline, always]
  ├─ updates AER status bits (if AER implemented)      [advanced]
  ├─ if not masked and reporting enabled (Device Control bits 0-3, SERR# for fatal/non-fatal on bridges):
  │     sends Msg ERR_COR / ERR_NONFATAL / ERR_FATAL upstream (Requester ID = itself)
  └─ root port receives message
        ├─ Root Error Status records (first/multiple, source ID)
        ├─ if Root Error Command enables → interrupt to OS (AER service driver)
        └─ (optional) DPC trigger on fatal/non-fatal → contain link

DPC (Downstream Port Containment): an optional capability on downstream ports that, on an uncorrectable error, disables the link to stop traffic (protecting data integrity), lets software recover the port, and makes subsequent requests to the device complete with UR/all-ones. Linux supports DPC and Error Disconnect Recover (EDR) — impl/platform-dependent.

45.10 Lab

🧪 Lab 45.1 — Classify errors from descriptions SAFE

Procedure: for each scenario, give error name, class, detecting component: (a) SSD sends 512 B MWr to a root port with MPS 256; (b) host's DRAM reports UE while serving an SSD read; (c) SSD replays a TLP 4 times; (d) host reads BAR0 while SSD is in D3hot; (e) switch internal SRAM bit flip on a forwarded TLP with ECRC.

Solution

(a) Malformed TLP, fatal (default), root port. (b) Poisoned TLP Received (CplD EP=1), non-fatal, SSD. (c) REPLAY_NUM Rollover, correctable, SSD transmitter (then Recovery). (d) Unsupported Request (memory requests in D3hot are not supported), non-fatal, SSD as completer; host sees UR completion → all-ones. (e) ECRC Error, non-fatal, final receiver (if ECRC check enabled).

Quiz

  1. Which errors are corrected by the data link layer replay?

    Answer

    Bad TLP (LCRC/sequence), with Replay Timer Timeout / REPLAY_NUM Rollover as related correctable events.

  2. Who detects a Completion Timeout?

    Answer

    The requester.

  3. What's the default severity of Malformed TLP?

    Answer

    Fatal.

  4. What does EP=1 mean?

    Answer

    Poisoned — the data payload is known to be corrupt.

  5. Why is ECRC useful if LCRC exists?

    Answer

    LCRC is per link and regenerated at every hop; ECRC covers end-to-end, detecting corruption inside switches.

Interview questions

  1. Beginner Three PCIe error classes?
    Model answer

    Correctable, uncorrectable non-fatal, uncorrectable fatal.

  2. Intermediate UR vs CA?
    Model answer

    UR: request not supported by completer; CA: supported but completer failed to complete it due to a violation/internal error.

  3. Advanced Why might a correctable error storm hurt performance?
    Model answer

    Replays consume bandwidth and add latency; interrupts per error cost CPU; may lead to retraining/downgrades.

  4. Senior Device reports CTO, root port reports nothing. Next steps?
    Model answer

    Check IOMMU, switch ports' AER, whether the request reached the RC (analyzer upstream of switch), completion routing (BDF changes), ACS.
