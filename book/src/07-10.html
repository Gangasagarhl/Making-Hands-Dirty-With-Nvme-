88 Benchmarking Discipline with fio

88.1 Why this chapter exists

Most published SSD comparisons are irreproducible because nobody recorded the preconditioning state, the queue depth, the CPU placement, or the temperature. A benchmark is an experiment; it needs a hypothesis, controlled variables, repetitions and an error bar. fio is the standard Linux tool; this chapter teaches safe, interpretable fio usage.

  • Write fio jobs that state block size, mix, QD, jobs, engine, direct I/O, runtime and ramp.
  • Run read-only jobs safely; know which jobs destroy data.
  • Interpret fio output: IOPS, BW, slat/clat/lat, percentiles, CPU, IO depth distribution, util.
  • Apply benchmarking discipline: warm-up, steady state, cache, thermal, power, repeatability.
⚠️ DESTRUCTIVE — fio writes destroy data

Any fio job with rw=write, randwrite, rw/readwrite, randrw, trim/randtrim/trimwrite pointed at a raw device (filename=/dev/nvme0n1) overwrites or discards data on that device including partition tables and filesystems. Run write jobs only on a dedicated scratch drive with nothing you want to keep, verified by serial number. For read jobs, add readonly=1 as a safety net: fio then refuses to run write or trim workloads. Even read-only benchmarks load production systems — run them in maintenance windows.

#!/usr/bin/env python3
"""fio_summary.py - summarize `fio --output-format=json` results (OFFLINE PARSING).
Also checks Little's law consistency: outstanding ~= IOPS x mean latency.
Usage: fio job.fio --output-format=json > out.json ; python3 fio_summary.py out.json"""
import json, sys

SAMPLE = {"jobs": [{"jobname": "randread-4k-qd32", "job options": {"iodepth": "32"},
           "read": {"iops": 395_000.0, "bw": 1_580_000,          # bw in KiB/s
                    "clat_ns": {"mean": 80_400.0, "percentile": {
                        "50.000000": 77_312, "99.000000": 140_288,
                        "99.900000": 610_304, "99.990000": 2_441_216}}}}]}
# SYNTHETIC numbers in the shape of fio JSON (field names as used by fio's JSON output)

def summarize(doc):
    for job in doc["jobs"]:
        for d in ("read", "write"):
            st = job.get(d)
            if not st or not st.get("iops"):
                continue
            iops, mean_s = st["iops"], st["clat_ns"]["mean"] / 1e9
            pct = st["clat_ns"].get("percentile", {})
            qd = int(job.get("job options", {}).get("iodepth", 1))
            L = iops * mean_s
            print(f"{job['jobname']} {d}: {iops:,.0f} IOPS, {st['bw'] * 1024 / 1e9:.2f} GB/s, "
                  f"mean {mean_s * 1e6:.1f} us")
            print("   percentiles (us): " + ", ".join(f"p{float(k):g}={v / 1000:.0f}"
                                                     for k, v in sorted(pct.items(), key=lambda kv: float(kv[0]))))
            print(f"   Little's law: IOPS x mean = {L:.1f} outstanding vs iodepth {qd} per job"
                  + ("  (consistent)" if abs(L - qd) / qd < 0.15 else "  (CHECK: submission-side gaps or extra queueing)"))

if __name__ == "__main__":
    summarize(json.load(open(sys.argv[1])) if len(sys.argv) > 1 else SAMPLE)

89.3 Causality rules for performance claims

  1. Temporal precision: the cause must precede the effect at the right time scale (µs events cannot explain second-long stalls without a mechanism).
  2. Magnitude: the cause must be large enough (a 1 µs replay cannot explain a 2 ms tail).
  3. Intervention: removing the cause removes the effect, everything else fixed.
  4. Dose-response: more cause → proportionally more effect.
  5. Alternative exclusion: common causes (temperature, background work) ruled out.
🏭 Device-specific limitations

Do not attribute a curve to "GC", "SLC cache exhaustion" or "die collisions" by shape alone. Those are plausible mechanisms for many SSDs, but firmware, NAND type, controller architecture, caches, scheduling and thermal policies differ, and the standard interface exposes none of them directly. Say "consistent with write-cache exhaustion; vendor confirmation or telemetry needed".

Interview questions — performance (module 53)

  1. Beginner Convert 250k IOPS at 8 KiB to GB/s.
    Model answer

    250,000 × 8192 = 2.05 GB/s.

  2. Beginner What is queue depth?
    Model answer

    Maximum outstanding I/Os per submitter; actual outstanding may be lower.

  3. Beginner Why report percentiles?
    Model answer

    Averages hide tails that dominate user-visible latency.

  4. Beginner Why use direct=1?
    Model answer

    Bypass the page cache so the device is measured, not RAM.

  5. Beginner What does fio's clat measure?
    Model answer

    Completion latency from submission to completion.

  6. Intermediate State Little's law and use it to check fio output.
    Model answer

    L = λW; IOPS × mean latency should ≈ total outstanding (iodepth × jobs).

  7. Intermediate Why does sequential need lower QD than random to saturate?
    Model answer

    Each large command already spans many dies/pages; random small I/Os need many independent commands for parallelism.

  8. Intermediate What is the effect of MPS 128 vs 256 on Gen4 x4 throughput?
    Model answer

    Efficiency ~84 % vs ~91 % → ~6.5 vs ~7.1 GB/s ceilings (Ch 90 model).

  9. Intermediate Why precondition before write tests?
    Model answer

    To measure steady state instead of fresh-drive behavior with empty caches and no GC debt.

  10. Intermediate %util is 100 %. Is the SSD saturated?
    Model answer

    Not necessarily; it only shows the device always had work. Check whether IOPS grows with QD.

  11. Advanced How many outstanding MRds sustain 14 GB/s writes at 2 µs RTT, MRRS 512?
    Model answer

    14e9 × 2e-6 / 512 ≈ 55.

  12. Advanced Distinguish device-bound from host-bound latency.
    Model answer

    blktrace D2C vs Q2D/total; CPU profiles; analyzer device response times.

  13. Advanced Why can interrupt coalescing raise throughput but hurt latency?
    Model answer

    Fewer interrupts reduce CPU overhead per I/O, but completions wait for the threshold or timer.

  14. Advanced How many samples for a trustworthy p99.99?
    Model answer

    On the order of 106 or more, and repeated runs to estimate variance.

  15. Advanced What does a QD sweep knee tell you?
    Model answer

    The concurrency where the bottleneck saturates; beyond it, latency grows with no IOPS gain.

  16. Senior A vendor claims 14 GB/s on Gen5 x4. Is it plausible?
    Model answer

    Yes, near the ~14.1–14.7 GB/s effective ceiling with MPS 256–512 — leaves almost no margin; verify MPS, platform and measurement units (GB vs GiB).

  17. Senior Latency spikes coincide with AER corrected errors. What do you do?
    Model answer

    Check temporal precision and magnitude, then intervene (lower speed or fix channel) to test causality; consider common causes.

  18. Senior Design a performance regression gate for firmware releases.
    Model answer

    Fixed hardware, preconditioning, matrix of workloads, ≥5 repetitions, percentile-based tolerances with statistical tests, thermal logging, golden traces for latency phases.

  19. Senior When is a faster PCIe generation pointless?
    Model answer

    When media/controller latency or CPU dominates (QD1 4 KiB, Ch 87) or when the device's internal bandwidth is below the old link's ceiling.

  20. Senior How do you explain tail latency to a product manager?
    Model answer

    The slowest 1 in 1,000 requests; a page load that needs 100 storage reads hits it ~10 % of the time.

90 PCIe Bandwidth Calculations

90.1 Why this chapter exists

"Gen5 x4 is 16 GB/s" is the most repeated half-truth in storage. The raw signaling rate is not what your application gets: line encoding, TLP framing and headers, DLLPs and ordered sets, NVMe's own traffic (SQE fetches, CQEs, interrupts) and the device's internal limits all take their share. This chapter does the arithmetic explicitly so you can tell a link limit from a device limit.

  • Separate raw signaling rate, encoding efficiency, protocol efficiency, effective payload bandwidth and device limitation.
  • Compute TLP efficiency for MPS 128/256/512 including framing and header overhead.
  • Work Gen3 x4, Gen4 x4, Gen5 x4, Gen5 x8 and Gen6 x4 end to end.
  • Compute per-I/O link bytes for NVMe reads, and the write-direction (completion) efficiency.
🧒 Kid analogy — moving boxes on a conveyor

A conveyor belt moves 16 slots per second. Every 130 slots, 2 are used for "start marker" labels (encoding). Every box needs a shipping label and a tape strip (header and framing) that also take belt space — a small box wastes more belt on labels than a big one. Now and then, the belt carries "got it!" notes going back (DLLPs). What arrives at the end is fewer useful kilograms than the belt's slot rate suggests.

🧩 Where the analogy breaks

PCIe is full duplex: two belts in opposite directions, each with its own budget; acknowledgements for one direction ride on the other. And the factory at the end (the SSD) may simply not be able to fill the belt.

90.2 The four layers of bandwidth

BWraw = (GT/s per lane) × lanes / 8 [GB/s, per direction]
  • GT/s — transfers per second per lane: 2.5, 5, 8, 16, 32, 64 for Gen1–6 verified (Gen7 128 GT/s version); for Gen1–5 one transfer = one bit; Gen6 PAM4 carries 2 bits per symbol at 32 GBaud = 64 GT/s
  • /8 — bits to bytes
BWencoded = BWraw × Eenc , Eenc = 8/10 (Gen1–2), 128/130 (Gen3–5), 236/256 TLP bytes per flit (Gen6 Flit mode)
  • Eenc — encoding efficiency. Gen6 Flit mode: each 256-byte flit carries 236 bytes of TLP space plus data-link payload, CRC and FEC bytes (commonly described as 6 DLP + 8 CRC + 6 FEC) version — verify against the PCIe 6.x specification
ETLP = MPS / (MPS + H + F)
  • MPS — payload bytes per TLP (Max Payload Size, when transfers are large and aligned)
  • H — TLP header bytes: 12 (3DW) or 16 (4DW, 64-bit address); NVMe data to host memory usually uses 64-bit addresses → 16
  • F — per-TLP framing and link protection: Gen3–5: 4-byte STP token (includes sequence number) + 4-byte LCRC = 8; Gen1–2: STP 1 + sequence 2 + LCRC 4 + END 1 = 8; optional ECRC adds 4. Gen6 Flit: no per-TLP LCRC/framing (protection is per flit), header format differs — approximated here as 16 B per TLP approximation
BWeff ≈ BWencoded × ETLP × (1 − d)
  • d — fraction of link time for DLLPs (Ack/Nak, UpdateFC) and ordered sets (SKP) in the data direction; modelled as 2 % for Gen3–5 and 0 for Gen6 Flit (DLLP information travels inside flits) — an assumption; real values depend on Ack/UpdateFC policies and traffic in the other direction impl
⚠️ Never present theoretical bandwidth as guaranteed

BWeff is a ceiling for payload on the link. Application throughput is further limited by the device (controller and NAND), the host (CPU, memory, root complex), NVMe protocol traffic, and the workload's concurrency. Use these numbers to find which limit you are hitting, not to promise results.

90.4 Worked example: Gen4 x4

  1. Raw: 16 GT/s × 4 lanes / 8 = 8.000 GB/s per direction.
  2. Encoding 128b/130b: 8.000 × 128/130 = 7.877 GB/s.
  3. TLP overhead at MPS 256: 7.877 × 256/280 = 7.202 GB/s.
  4. DLLP/ordered-set allowance 2 %: 7.202 × 0.98 = 7.058 GB/s effective payload.
  5. Same at MPS 128: 7.877 × 0.8421 × 0.98 = 6.501 GB/s; at MPS 512: 7.374 GB/s.

NVMe per-I/O overhead (4 KiB random read, device → host direction). Upstream bytes per I/O at MPS 256: data 16 TLPs × 280 B = 4480; CQE MWr 16 + 24 = 40; MSI-X MWr 4 + 24 = 28 (if not coalesced); the SQE-fetch MRd header also travels upstream: 24. Total 4572 B → efficiency 4096/4572 = 0.896. Link-only ceiling: 7.877 × 0.98 × 109 / 4572 ≈ 1.69 M IOPS (6.92 GB/s of 4 KiB payload) — above most devices' 4 KiB random-read capability, so random-read IOPS is usually device-limited, not link-limited, at Gen4 x4 derived.

90.5 Worked example: Gen5 x4

  1. Raw: 32 × 4 / 8 = 16.000 GB/s.
  2. Encoded: 16 × 128/130 = 15.754 GB/s.
  3. MPS 256: 15.754 × 0.9143 × 0.98 = 14.115 GB/s; MPS 128: 13.001; MPS 512: 14.747.
  4. 4 KiB read link-only ceiling (MPS 256): ≈ 3.38 M IOPS.

90.6 All requested configurations

#!/usr/bin/env python3
"""PCIe bandwidth estimator (DERIVED MODEL - teaching estimates, not guarantees).
Layers of loss, applied in order:
  1. line encoding        8b/10b (Gen1-2), 128b/130b (Gen3-5), Flit 236/256 TLP bytes (Gen6)
  2. TLP framing+header   per-TLP bytes around each payload chunk of <= MPS
  3. DLLP / ordered sets  modelled as a fixed fraction (assumption, see text)
Units: GB/s = 1e9 bytes/s, per direction."""
GEN = {  # GT/s per lane, encoding efficiency, per-TLP non-payload bytes (64-bit MWr, no ECRC)
    1: (2.5, 8 / 10, 2 + 1 + 16 + 4 + 1),     # STP + seq(2) + hdr16 + LCRC4 + END ~ 24 B
    2: (5.0, 8 / 10, 24),
    3: (8.0, 128 / 130, 4 + 16 + 4),            # STP token 4 B (incl. seq) + hdr 16 + LCRC 4
    4: (16.0, 128 / 130, 24),
    5: (32.0, 128 / 130, 24),
    6: (64.0, 236 / 256, 16),                   # flit: CRC/FEC/DLP live in the flit; ~16 B hdr (approx.)
}

def raw_GBps(gen, lanes):
    gt, enc, _ = GEN[gen]
    return gt * lanes / 8                     # 1 bit per transfer per lane (PAM4 Gen6: 64 GT/s still = 64 Gb/s)

def encoded_GBps(gen, lanes):
    gt, enc, _ = GEN[gen]
    return gt * enc * lanes / 8

def tlp_eff(gen, mps):
    return mps / (mps + GEN[gen][2])

def effective_GBps(gen, lanes, mps=256, dllp_os_frac=None):
    if dllp_os_frac is None:                  # Gen6 flit already carries DLLP info in-flit
        dllp_os_frac = 0.0 if gen >= 6 else 0.02
    return encoded_GBps(gen, lanes) * tlp_eff(gen, mps) * (1 - dllp_os_frac)

def per_io_bytes(io_bytes, mps, gen):
    """Upstream link bytes for one NVMe READ of io_bytes (device -> host)."""
    ovh = GEN[gen][2]
    n = -(-io_bytes // mps)
    data = io_bytes + n * ovh
    cqe = 16 + ovh                             # CQE MWr
    msix = 4 + ovh                             # MSI-X MWr (if not coalesced)
    sqe_req = ovh                              # MRd header for the SQE fetch travels upstream too
    return data + cqe + msix + sqe_req

90.7 The write direction: read requests and completions

Quiz

  1. Why is Gen5 x4 not "16 GB/s" for applications?

    Answer

    128b/130b encoding, TLP header/framing overhead (MPS-dependent), DLLPs/ordered sets, NVMe command traffic, and device limits reduce it to ~14 GB/s or less.

  2. Per-TLP overhead for a 64-bit MWr at Gen4?

    Answer

    4 B STP token + 16 B header + 4 B LCRC = 24 B (no ECRC).

  3. Does doubling MPS from 256 to 512 double bandwidth?

    Answer

    No: efficiency rises from ~91.4 % to ~95.5 % — about +4.5 %.

  4. Gen6 uses PAM4 at 64 GT/s. Raw x4 bandwidth?

    Answer

    64 × 4 / 8 = 32 GB/s per direction before flit overhead.

Interview questions

  1. Intermediate Walk me through the effective bandwidth of Gen4 x4 with MPS 256.
    Model answer

    8 GB/s raw → ×128/130 = 7.88 → ×256/280 = 7.20 → minus ~2 % DLLP/SKP ≈ 7.06 GB/s.

  2. Advanced Why can writes be slower than reads at the protocol level on the same link?
    Model answer

    Writes need Non-Posted MRds with round trips and enough outstanding tags; completions may be split into small RCB-sized pieces with 20 B overhead each.

  3. Senior When would you recommend Gen5 x8 for a single SSD?
    Model answer

    Only if the device's internal bandwidth exceeds the Gen5 x4 ceiling (~14 GB/s) for the target workload, or for multi-function/aggregated designs; otherwise lanes are wasted.
