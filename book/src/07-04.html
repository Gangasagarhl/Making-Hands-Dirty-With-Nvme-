🧪 Trace Lab TL-5 — Read fails with "Data Transfer Error" (Advanced) SAFE

Scenario. After a driver change, ~1 in 106 large reads fails with an I/O error. The kernel log shows an IOMMU fault near each failure.

Background. With an IOMMU, device DMA addresses are I/O virtual addresses (IOVAs). A DMA to an unmapped IOVA is blocked by the root complex; the requester typically receives an unsuccessful completion (for reads) or the write is dropped (for posted writes) impl.

Questions. (1) Why is row 4 the first abnormal event rather than row 5? (2) Who decided the read had failed and how did it report? (3) List hypotheses for why IOVA 0xFFF0_1000 was unmapped. (4) What does the 38-µs gap between rows 3 and 4 suggest?

Hints

Compare the PRP list pointer in the SQE with the IOMMU fault address. Think about the lifetime of the PRP list page in the driver.

Solution

(1) Row 4 is the first event touching an invalid address — the request itself was already wrong; row 5 is the platform's (correct) reaction. Strictly, the true "first abnormal" fact is in row 3: the SQE carried a bad pointer — the trace cannot tell when it became bad. (2) The root complex/IOMMU blocked the DMA and returned UR; the controller then completed the command with Generic status 04h (Data Transfer Error) — a reasonable, implementation-chosen status impl. (3) H1 driver freed/unmapped the PRP list page before the device fetched it (use-after-unmap race); H2 the list was allocated from a pool whose IOVA mapping was torn down (e.g. after a reset); H3 IOVA arithmetic bug for lists crossing a page boundary; H4 IOMMU invalidation race. (4) The controller fetched the PRP list late (only when it was ready to transfer data) — devices may fetch lists lazily impl, which widens any host race window.

Evidence: instrument the driver to log map/unmap of PRP list pages with timestamps; check whether the failing commands' lists cross a page boundary; run with IOMMU in strict vs lazy invalidation modes. Root cause (lab answer): driver change released the PRP-list DMA mapping on a timeout-path cleanup that raced with normal completion. Corrective action: tie the list's lifetime to the request's completion. Regression test: stress 64 KiB–1 MiB reads with forced random timeouts and IOMMU strict mode for 24 h; zero DMAR faults allowed.

💡 Senior insight

The link was healthy; the controller behaved correctly; the bug was in host memory management. PCIe traces are often the tool that exonerates the device by showing exactly what address it was told to use.

Follow-up. How would the same bug look without an IOMMU? (Hint: the device reads whatever is in that physical page — possibly garbage PRP entries — and may DMA data to random memory: silent corruption. The IOMMU converted silent corruption into a clean error.)

🧪 Trace Lab TL-6 — The completion that nobody heard (Advanced) SAFE

Scenario. A single queue occasionally stalls for exactly 30 s; then I/O resumes. Kernel log: nvme nvme0: I/O 17 QID 5 timeout, completion polled (illustrative).

Background. MSI-X vectors can be masked per vector (table entry Mask bit) or for the whole function (Function Mask). A masked vector sets its Pending bit instead of sending the message; unmasking later sends the pending message verified for MSI-X semantics.

Gen / widthGen4 x4Device01:00.0, 33 MSI-X vectors; QID 5 → vector 5
Expected opRead CID 0x0011 on QID 5Initial stateHost CPU affinity for vector 5 being changed by irqbalance at about the time of the stall
CoverageBoth directions; TLPs; 40 s segmented capture with filter = "everything to/from QID 5 ranges + MSI-X address range + BAR0 writes".

10.000000 sDNTLMWr00:00.0—FE60202C—4MSI-X table entry 2, Vector Control: Mask = 1

Questions. (1) The MSI-X table lives in BAR0 at offset 2000h with 16-byte entries. Decode rows 1, 5, 6. (2) Is the device at fault for not sending the interrupt? (3) Why is row 4's "absence" trustworthy here but would not be in a capture filtered differently?

Hints

Entry n is at 2000h + 16n: Message Address low +0, high +4, Data +8, Vector Control +0Ch. Rows 1 and 5 differ.

Solution

(1) Row 1: entry 2 (2000h + 20h + 0Ch = 202Ch) masked — irrelevant to QID 5, a distractor; real traces have many. Row 5: entry 5 (2000h + 50h + 0Ch = 205Ch) masked; row 6 reprograms entry 5's address/data — the host is moving the vector to another CPU. Row 7: no unmask of entry 5 follows within the capture.

(2) Look at the ordering: the CQE (row 3) and the missing interrupt (row 4) come before the mask write of row 5. Two explanations fit: (a) vector 5 was already masked before capture start (an earlier affinity change outside coverage; row 5 is a repeated mask), in which case the device correctly withheld the message and set its Pending bit; or (b) the device failed to send an interrupt for an unmasked vector. The trace alone cannot decide, because coverage starts at row 1. Disambiguating evidence: read the Pending Bit Array (PBA, BAR0+3000h here) after the stall — bit 5 set supports (a); extend the capture start earlier to catch the first mask write; check host tracing of the affinity-change path. A masked vector must not send its message, so under (a) the device is not at fault.

(3) The filter explicitly included the MSI-X address range and all BAR0 writes; with a filter that excluded the interrupt address range, absence would mean nothing.

Root cause (lab answer): explanation (a), confirmed by PBA bit 5 = 1 and an extended capture: the host interrupt-affinity update path masked the vector and an error path skipped the unmask. Corrective action: fix the unmask path; regression test: stress I/O while forcing affinity changes every 10 ms for 1 h; assert no I/O exceeds 1 s; check PBA bits clear at end.

💡 Senior insight

Exactly-30-second stalls are a fingerprint: something waited for the default io_timeout. "Completion polled" means the CQE was already there — the interrupt path, not the device's command execution, is the suspect. Distractor rows (entry 2) are normal in real traces; disciplined address decoding beats intuition.

Follow-up. Design an analyzer trigger that fires when a CQE MWr is not followed by an MSI-X MWr within 10 µs (a "sequence + timer" trigger, if your analyzer supports it version).

Solution

(1) The switch: it received (and Acked) the CplD on its upstream port but never transmitted it on the downstream port. (2) "The root complex never answered" — wrong owner. Single-probe captures localize to a link, not a component. (3) Completion routing by Requester ID mis-programmed (bus number ranges), internal buffer/credit accounting bug under mixed load, error containment (e.g. internal parity error dropping the packet), tag-tracking bug for 10-bit tags impl. (4) Probe coverage (did Probe A's analyzer drop packets? check its buffer/overflow indications), that 0x2a's CplD on B really has Requester ID 04:00.0 (not a different function), switch error counters/logs, switch firmware version, and whether the switch reported its own AER error.

Corrective action: escalate to switch vendor with both captures and configuration; workaround candidates (lower load, firmware update). Regression test: mixed-load soak on all downstream ports with completion-timeout counters per SSD; zero tolerated.

💡 Senior insight

Placing probes is a hypothesis test. Probe A answers "did the SSD receive it?"; Probe B answers "did the switch receive it?". Together they bracket a single component. Before purchase or setup, ask what question each probe point answers.

Follow-up. If a switch offers its own internal capture/trace feature (Chapter 78), what would you capture to confirm the drop inside the switch?

🧪 Trace Lab TL-8 — The doorbell that rang the wrong bell (Senior) SAFE

Scenario. A new user-space test harness (lab-only, device bound to vfio-pci) works on SSD model A but on model B no I/O command ever completes; the admin queue works.

Background. Doorbell address: SQy tail = 1000h + (2y)·(4 << CAP.DSTRD); CQy head = 1000h + (2y+1)·(4 << CAP.DSTRD). Model A has DSTRD = 0; model B has DSTRD = 1 (8-byte stride).

Gen / widthGen4 x4DeviceModel B, CAP.DSTRD = 1
Expected opRead on QID 1, CID 1Initial stateAdmin queue live; one Asynchronous Event Request (AER cmd, opcode 0Ch) outstanding with CID 0x7F
CoverageBoth directions; all TLPs; 1 s.
SYNTHETIC TEACHING TRACE — NOT A REAL DEVICE CAPTURE · TL-8 wrong doorbell stride
#Time µsDirLayerTypeRequesterCompleterAddressTagLenMeaning
10.0DNTLMWr00:00.0—FE601008—4value 0x00000001 — intended "SQ1 tail = 1"
23.5UPTLMWr01:00.0—(admin CQ slot 9)—16CQE: CID 0x7F (the AER command), SQID 0, DW0 = 0x00010000
33.6UPTLMWr01:00.0—FEE0_0000—4MSI-X vector 0 (admin)
4———(none)—————no SQE fetch from I/O SQ1 within 1 s

Questions. (1) With DSTRD = 1, which register is at 1008h? (2) Decode DW0 of the asynchronous event completion: event type in bits 2:0, event information in bits 15:8, log page identifier in bits 23:16. (3) Why does the admin queue still work?

Hints

Stride = 8 bytes: SQ0 tail 1000h, CQ0 head 1008h, SQ1 tail 1010h, CQ1 head 1018h.

Solution

(1) 1008h is the admin CQ (CQ0) head doorbell. The harness wrote "head = 1" to the admin CQ — an invalid value if the host had not consumed entries accordingly. (2) DW0 = 0x00010000: event type 0 (Error status), event information 00h, log page 01h (Error Information). Under the spec's asynchronous event information for error status, the values distinguish "write to invalid doorbell register" and "invalid doorbell write value" — check the exact encoding table in the base specification revision you use verify code-point. Whether and how a controller reports an invalid doorbell write is controller behavior governed by the spec and may vary impl. (3) Admin SQ0 tail is at 1000h for any stride; only queues y ≥ 1 or the CQ0 head move with DSTRD.

Root cause: harness hard-coded a 4-byte stride instead of computing 4 << CAP.DSTRD. Corrective action: derive all doorbell offsets from CAP. Regression test: run the harness against devices (or an emulator such as a configurable virtual NVMe device) with DSTRD = 0, 1 and 2; assert I/O completes and no asynchronous error events are logged.

💡 Senior insight

Absence of activity after a doorbell is a doorbell-addressing problem until proven otherwise. Always decode the doorbell address against this device's CAP, and keep an outstanding Asynchronous Event Request — the controller will often tell you what you did wrong.

Questions. (1) Find the first abnormal event and justify it. (2) Which layer owns the problem? (3) Why only 15 % of resumes? (4) Write the bug report skeleton. (5) Design the regression test.

Solution

(1) Row 5: CC.EN=1 written while AQA/ASQ/ACQ hold reset values (zero). The spec's initialization sequence requires configuring the admin queue registers before setting CC.EN to 1 verified (initialization order). Rows 1–4 are healthy: the link trained to full speed and config restore succeeded. (2) Host driver / platform resume path (NVMe register programming order), not PCIe. CSTS.CFS=1 (row 7) is the controller's reaction — how a controller reacts to enable-without-queues is implementation-dependent impl. (3) Hypothesis: the resume path assumes register state is preserved (true after D3hot without reset, false after D3cold); the platform chooses D3cold only sometimes (e.g. depending on how long it slept or on a platform policy) impl. Evidence: correlate failures with the platform's power-state decision (logs/ACPI tracing) and with sleep duration.

(4) Bug report skeleton: Title: NVMe controller fatal status after resume when device enters D3cold: CC.EN set before admin queue registers. Environment: platform/BIOS, kernel version, SSD model/FW (SN redacted), link Gen4 x4. Coverage: capture armed before suspend; both directions; TLP + link-state; no filters on BAR0 traffic. Observations: rows 1–8 with times. Inferences: link and config restore healthy; register order violated. Hypotheses ranked: H1 resume path skips full re-init after D3cold (high); H2 controller firmware loses AQA writes (low — disproved: writes are visible on the link after CC). Evidence requested: driver trace of resume path; ACPI power-state decisions. Impact: data unavailability, potential data loss for unflushed writes. Reproduction rate: 15 % over 200 cycles.

(5) Regression test: 1,000 suspend/resume cycles forcing D3cold, and 1,000 forcing D3hot; assert after each resume: device present, CSTS.RDY=1 with CFS=0 within CAP.TO, a read-verify of a known pattern succeeds; on failure, auto-save kernel log and analyzer trigger.

💡 Senior insight

In resume bugs, the loud events (removal, reset loop) arrive seconds after the decisive one. Read forward from the last known-good state (link up, config restored) rather than backward from the crash.
