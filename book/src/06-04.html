📘 Specification baseline

STATUS: optional I/O command set, selected by Command Set Identifier (CSI). 60.1 Why this chapter exists

Many applications do not want blocks at all; they want “store this value under this key” and “give me the value for that key”. Today they run a key-value engine (an LSM-tree such as RocksDB) on a file system on a block SSD that runs an FTL — three layers of mapping, each with its own write amplification. The KV command set lets the device expose keys and values directly, potentially collapsing those layers. Whether it helps is workload- and implementation-dependent; understanding the interface lets you evaluate it honestly.

  • Explain the KV namespace concept and how it differs from an LBA namespace.
  • Describe Store, Retrieve, Delete, Exist and List at the conceptual level.
  • Compare KV and block storage on mapping, atomicity, write amplification and tooling.
  • Identify what the KV specification defines and what is left to the device.

Prerequisites: namespaces and CSI; NVMe command/completion format.

🧒 Kid analogy — the coat check

A block SSD is a wall of numbered lockers: you must remember which locker numbers hold your coat. A key-value SSD is a coat check: you hand over your coat (value) and say a name (key). Later you say the name and get your coat back. You do not care which hook it hangs on.

🧩 Where the analogy breaks

Keys have a strict maximum length, values have device-reported limits, there is no built-in range query beyond the List command’s semantics, and the device still runs an internal index and garbage collection — the mapping did not disappear, it moved.

61 Computational Programs

📘 Specification baseline

DOCUMENT: NVMe Computational Programs Command Set Specification, used together with the Subsystem Local Memory Command Set Specification (Chapter 62). REVISION: Computational Programs 1.3 per the August 2026 set (course brief — confirm). STATUS: optional I/O command set. 61.1 Why this chapter exists

Moving a terabyte from SSD to host DRAM to filter out 1% of it wastes PCIe bandwidth, host memory bandwidth and CPU time. Computational storage runs the filter next to the data and sends back only the result. NVMe’s Computational Programs command set is the standard interface for that: programs live in a compute namespace, operate on data staged in subsystem local memory, and are managed and executed with NVMe commands.

  • Explain computational storage and the data-locality argument with a bandwidth calculation.
  • Distinguish device-defined (preloaded) and downloadable programs.
  • Describe the program lifecycle: load, activate, execute, results.
  • Explain the relationship between compute namespaces, memory namespaces (SLM) and NVM namespaces.

Prerequisites: namespaces, CSI; PCIe bandwidth (Chapter 53).

🧒 Kid analogy — the factory beside the mine

A mine (NVM namespace) produces tons of rock. Trucking all the rock to the city (host) to extract a few grams of gold is slow and expensive. So you build a small factory (compute engine) next to the mine, with its own loading yard (subsystem local memory). The factory has some machines that came installed (preloaded programs) and you can ship in new machines (downloaded programs). Only the gold goes to the city.

🧩 Where the analogy breaks

The factory is small: compute engines inside SSDs are much weaker than host CPUs, so offload helps only when data reduction is large or host resources are the bottleneck. Also, the “yard” must be explicitly filled and emptied with commands — the factory does not dig the mine by itself.

61.2 Data-locality arithmetic

T_host ≈ D / BW_link + D / R_host     T_offload ≈ D / BW_internal + D / R_dev + (s·D) / BW_link
  • D — bytes to scan
  • BW_link — effective PCIe bandwidth to host
  • R_host / R_dev — processing rate of host CPU / device compute engine
  • BW_internal — media-to-SLM bandwidth inside the device
  • s — selectivity (fraction of data returned)

Worked example synthetic: D = 1 TB, BW_link = 7 GB/s, R_host = 20 GB/s (several cores), BW_internal = 10 GB/s, R_dev = 4 GB/s, s = 0.01. Simplifying as pipelined (time = slowest stage): host path ≈ 1 TB / 7 GB/s ≈ 143 s; offload ≈ 1 TB / 4 GB/s ≈ 250 s. Offload is slower here — but it frees the host CPU and PCIe link for other work. With 8 such SSDs on a shared x16 uplink (≈ 28 GB/s), the host path needs 8 TB / 28 GB/s ≈ 286 s of uplink time and 8 TB / 20 GB/s ≈ 400 s of CPU time, so it takes ≈ 400 s, while the eight devices offload in parallel in ≈ 250 s and return only 80 GB. derived The value of computational storage is usually aggregate and system-level.

61.4 Lifecycle

  1. Discover: identify compute namespaces and their programs (device-defined programs are present from manufacture/firmware; downloadable program slots may exist).
  2. Load (downloadable programs): transfer a program image to a program slot. Program type/format is specified per program type; image contents are impl.
  3. Activate: make a program executable.
  4. Stage data: copy data from an NVM namespace into SLM ranges (SLM command set), or write host data into SLM.
  5. Define memory ranges: describe which SLM ranges a program may use (memory range sets).
  6. Execute: run the program with parameters; completion returns program status.
  7. Collect: read results from SLM to host.

verified lifecycle concepts; command names (e.g. Load Program, Program Activation Management, Execute Program, Memory Range Set Management) and their fields must be read from Computational Programs 1.3 — this course deliberately does not reproduce field layouts.

📭 What the spec does not say

The specification does not define what a program’s instruction set is (that depends on program type, e.g. a device-specific format or a standard such as eBPF if a vendor chooses it), how fast it runs, how it is sandboxed internally, or how compute and I/O share device resources. Security of downloaded code is a system design concern; check how the spec ties program loading to security mechanisms and access control.

💡 Senior insight

The NVMe rule that commands are unordered is the number-one correctness trap in computational storage: “copy, then execute, then read” is three independent commands. 62 Subsystem Local Memory (SLM)

📘 Specification baseline

DOCUMENT: NVMe Subsystem Local Memory Command Set Specification. REVISION: 1.3 per the August 2026 set (course brief — confirm). STATUS: optional I/O command set; memory namespaces. RELATIONSHIP: designed to be used with Computational Programs (Chapter 61), but it is a separate command set. version

62.1 What SLM is and why it exists

Subsystem Local Memory is memory inside the NVM subsystem (for example DRAM on the SSD) exposed as a memory namespace that is accessed with NVMe commands — byte-addressed rather than LBA-addressed. It exists to give computational programs a workspace and to let hosts move data between NVM namespaces and that workspace without crossing PCIe. verified concept.

🧒 Kid analogy

SLM is the factory’s loading yard from the previous chapter: a place right next to the mine where rock can be piled up for the machines, and from which the finished gold is loaded onto trucks.

🧩 Where the analogy breaks

SLM is not host memory, not mapped into the CPU’s address space by this command set, and (unless stated otherwise) volatile — contents may be lost on reset or power loss. Do not confuse it with the Controller Memory Buffer (CMB) or Persistent Memory Region (PMR), which are exposed through PCIe BARs.

In a data centre, a Baseboard Management Controller (BMC) must see drive temperature, health and inventory even when the host OS is crashed, not installed or not trusted. 🧒 Kid analogy — the janitor’s back door

The teacher (host CPU) talks to the library (SSD) through the main door (PCIe + NVMe queues). The building janitor (BMC) has a key to a small back door (SMBus) and can check the thermostat, read the logbook and even swap a light bulb (firmware), even when the classroom is locked or the teacher is asleep.

🧩 Where the analogy breaks

The “back door” can also be a logical path over the main PCIe link (MCTP over PCIe VDM), and the janitor and teacher can step on each other’s toes: concurrent configuration from BMC and host must be coordinated, which the spec addresses only partly.

64 NVMe Boot

📘 Specification baseline

DOCUMENTS: NVMe Boot Specification, revision 1.4 per the August 2026 set (course brief — confirm); UEFI Specification (NVM Express Pass Thru Protocol, device paths); ACPI. STATUS: optional. SCOPE NOTE: booting from a local NVMe-over-PCIe SSD is handled by platform firmware (UEFI NVMe driver) and has worked for years without the NVMe Boot Specification; the Boot Specification primarily addresses booting over NVMe over Fabrics, including how pre-OS firmware passes its fabric configuration to the operating system version.

64.1 Why this chapter exists

Diskless servers and cloud instances want to boot from a remote NVMe/TCP target. Before the OS runs, UEFI firmware must connect to the target, read the boot loader and kernel, and then hand over to an OS that must reconnect to the same namespace without losing its root file system. That handoff is what the NVMe Boot Specification standardises, through a firmware table the OS reads.

  • Explain the pre-OS environment and the UEFI role for local NVMe boot.
  • Explain NVMe-oF boot and the NVMe Boot Firmware Table (NBFT) handoff concept.
  • Trace the boot sequence and identify failure points.

Prerequisites: controller initialisation (CC.EN, CSTS.RDY), NVMe-oF mental model (forward link — read Chapter 65 first if new).

🧒 Kid analogy — the relay baton

The morning caretaker (UEFI) unlocks the school, fetches the timetable from the faraway library (remote target), and starts the day. When the teacher (OS) arrives, the caretaker hands over a note: “we are using library X, room Y, with this key” (NBFT). Without the note the teacher would not know where the timetable came from.

🧩 Where the analogy breaks

The OS does not continue the caretaker’s connection; it builds its own new connections using the information in the table. Any secrets (authentication keys) in the handoff require careful protection — what the spec allows in the table must be checked, not assumed.

64.2 Local NVMe (PCIe) boot

  1. Platform firmware enumerates PCIe, finds class code 01h/08h/02h (mass storage / NVM / NVMe).
  2. UEFI NVMe driver initialises the controller (admin queues, CC.EN = 1, wait CSTS.RDY), identifies namespaces, creates I/O queues.
  3. UEFI exposes block I/O and the NVM Express Pass Thru Protocol; device paths include an NVMe namespace node.
  4. Boot manager reads the EFI System Partition and loads the boot loader.
  5. OS loader calls ExitBootServices; the OS NVMe driver resets and re-initialises the controller.

verified class code 010802h for NVMe; UEFI protocol names per UEFI specification.
