THE NVMe + PCIe ENGINEERING JOURNEY

From “what is a byte?” to reading a PCIe protocol capture, finding the first bad event, and defending a root cause in a senior design review.

This book is a long road with a clear destination. On the first page you may not know what a register is. On the last page you should be able to take an unfamiliar failure — a timed-out NVMe command, a link that keeps dropping into Recovery, a throughput cliff at queue depth 64 — and investigate it with a disciplined method that starts from evidence and ends with a defensible conclusion.

The path is deliberately slow at the beginning. Most people who struggle with NVMe and PCIe do not struggle with NVMe or PCIe. They struggle because nobody ever made them comfortable with the boring ground floor: what memory addresses are, who is allowed to write where, what “the device read host memory” physically means, and why an interrupt is not the same thing as a completion. We build that ground floor first, and we build it properly.

📌 Remember — the single sentence this whole book unpacks

Software writes a 64-byte command into a queue in host memory, rings a doorbell register on the device, the device fetches the command over PCIe using DMA, moves the data with more DMA, writes a 16-byte completion entry back into host memory, and signals the host with an interrupt message. Everything else in this book is detail, history, failure modes and evidence for that one sentence.

0.2 Why NVMe matters

NVM Express (NVMe) — Non-Volatile Memory Express — is the dominant host interface for solid-state storage in laptops, workstations, servers, hyperscale data centres and increasingly in automotive and embedded systems. It exists because flash memory became so fast that the old storage interfaces, which were designed around spinning disks, became the bottleneck. NVMe was designed from a blank page for parallel, low-latency, non-volatile media:

  • Massive parallelism. Up to roughly 64 K I/O queues, each up to roughly 64 K entries deep verified, so every CPU core can own its own queue pair without locks.
  • Lean command path. Submitting a command needs one memory write by the host to a doorbell register; no register reads are required on the fast path verified.
  • Fixed-size, cache-friendly structures. A submission queue entry (SQE) is 64 bytes and a completion queue entry (CQE) is 16 bytes verified.
  • One architecture, many transports. The same command model runs over PCI Express, RDMA (Remote Direct Memory Access) fabrics and TCP (Transmission Control Protocol) networks.
  • Living ecosystem. The specification family is refactored into a base specification, command-set specifications and transport specifications, and is revised regularly. The current baseline for this book is the set released on August 4, 2026.

If you work on storage firmware, SSD validation, server platforms, Linux block layers, cloud infrastructure, hardware security or test equipment, you will meet NVMe every week.

0.3 Why PCIe matters

PCI Express (PCIe) — Peripheral Component Interconnect Express — is the high-speed, point-to-point, packet-based interconnect that attaches nearly every serious peripheral to a modern CPU: GPUs, network adapters, accelerators and NVMe SSDs. For a locally attached SSD, PCIe is the road every NVMe command, every byte of data and every completion travels on.

  • PCIe defines how a device is discovered (enumeration), described (configuration space), addressed (Base Address Registers, BARs), and talks (TLPs carried reliably by a data-link layer over physical lanes).
  • Generations double the per-lane signalling rate: 2.5, 5, 8, 16, 32 and 64 GT/s for Gen1 to Gen6 verified; PCIe 7.0 at 128 GT/s was released in 2025 version.
  • When an NVMe drive misbehaves, the evidence is often in PCIe: a completion that never came back, a link that retrained, an Advanced Error Reporting (AER) message, a malformed packet.

An NVMe engineer who cannot read PCIe is like a pilot who cannot read weather. You can fly on a clear day; you cannot diagnose a storm.

0.4 How the two connect — the end-to-end picture

Here is the whole journey of a single read command in one figure. Do not worry if most labels are unfamiliar — by the end of Part XIII every arrow will have a chapter behind it.

Notice three things that surprise almost every beginner:

  1. The host never “sends” the command to the SSD. The host writes it into its own memory and then tells the SSD where the tail of the queue is. The SSD goes and fetches it. The command crosses PCIe inside a completion that answers the SSD's own read request.
  2. The SSD writes the answer directly into host memory. No CPU instruction copies data in; the device is a bus master doing Direct Memory Access (DMA).
  3. An MSI-X interrupt is just another memory write. Message Signaled Interrupts – Extended are posted writes to a special address that the interrupt controller decodes. On a protocol analyzer, an interrupt looks like data.

⚠️ Warning — your first safety rule

Never run a write, format, sanitize, firmware or setpci write command against a device that holds data you care about, including the drive your operating system booted from. Read-only commands such as lspci -vvv and nvme id-ctrl are safe; anything that writes to a device or a register is not, regardless of how harmless it looks.

0.8 Specification-reading strategy

Specifications are not tutorials. They are contracts. They say what a conforming device shall do, not why, and not always how. Learn to read them like a lawyer reads a contract and an engineer reads a datasheet.

  1. Identify the document and revision first. NVMe is a family: the NVMe Base Specification, command-set specifications (NVM, ZNS, Key Value, Subsystem Local Memory, Computational Programs), transport specifications (PCIe, RDMA, TCP), the Management Interface specification and the Boot specification. A feature lives in exactly one of them; find which.
  2. Read the conventions and definitions sections before anything else. They define notation such as 0's-based values, bit numbering, reserved fields and the meaning of “shall”, “should” and “may”.
  3. Separate normative from informative. Requirements are normative; notes, examples and rationale are informative. An informative figure never overrides normative text.
  4. Read the field table, then the behaviour text. A field's bit position is in a figure; its meaning, defaults and corner cases are usually in the prose around it and in the command or feature description elsewhere.
  5. Track optionality. Many features are optional and advertised in Identify data or capability registers. Before assuming a feature, find the bit that says the device supports it.
  6. Check revision history. When behaviour differs between revisions, the change list on the NVM Express revision-changes page and the document's own history tell you when.
  7. Cite precisely, never from memory. Write down document, revision and the exact figure or section as printed in your copy. This book deliberately does not invent section numbers; you should not either.
📘 Specification — the three words that matter most

shall — a requirement; a conforming implementation must do it. should — a recommendation; there may be valid reasons not to, and you cannot treat it as guaranteed. may — a permission; the behaviour is optional and software must tolerate both choices. Many real-world interoperability bugs come from treating “should” as “shall” or “may” as “will”.

Code and trace labels

Every code block states its kind: executable (you can run it), pseudocode (illustrates logic), simulation (runs, but models hardware rather than touching it), read-only inspection (a command that only reads state) or hardware-dependent (needs specific equipment and may change state). Every trace states whether it is synthetic, reconstructed, conceptual or excerpted. Rows marked in a highlighted colour are abnormal; the first abnormal event is marked separately, because finding it is the most important skill in debugging.

💡 Senior insight — how to actually learn from this book

Do the labs. Draw the diagrams yourself before looking at ours. When you read a quiz question, answer it out loud or on paper before opening the answer. Engineers who become senior quickly are not the ones who read the most; they are the ones who repeatedly turn reading into prediction (“I expect the next packet to be a CplD of 64 bytes”) and then check the prediction against evidence.

0.12 Your first promise

Write this at the top of your lab notebook. It is the habit that separates protocol engineers from people who guess:

  1. What did I OBSERVE?        (raw evidence, with its source and timestamp)
  2. What do I INFER from it?   (labelled: verified / derived / guess)
  3. What would DISPROVE it?    (the experiment I will run next)
