PART XXIV

Protocol Analyzer Training (Teledyne LeCroy–class Workflows)

Teledyne LeCroy is one of the best-known makers of PCIe/NVMe protocol analyzers, and many teams say "the LeCroy" the way people say "the Xerox". This Part teaches the workflow and concepts shared by hardware protocol analyzers of that class — capture, trigger, filters, views, timestamps, link state, error views, traffic analysis — and the reasoning path from symptom to root-cause hypothesis. It deliberately does not reproduce any product's menus, button names or screen layouts: those differ between product generations and software versions. Whenever this Part says "most analyzers can…", treat it as version-dependent and verify against the documentation for the exact analyzer hardware, firmware and software version you use.

77 Protocol Analyzer Workflows: From Symptom to Hypothesis

77.1 Why this chapter exists

A protocol analyzer is the only instrument that shows what actually crossed the link, symbol by symbol, in both directions, with nanosecond timestamps. It is also expensive, intrusive (you must insert something into the channel), limited in memory, and only as useful as the trigger you set. Teams that own analyzers but lack the workflow fill buffers with gigabytes of irrelevant idle traffic and still miss the event. This chapter teaches the workflow.

77.2 Learning objectives (deep-dive module)

  • Beginner: explain what an analyzer captures, the difference between capture-time filtering and display filtering, and what a trigger is.
  • Intermediate: configure a capture conceptually: speed/width, probe, buffer, trigger position, trigger condition; navigate packet, transaction and NVMe-command views.
  • Advanced: design sequence/timer triggers for "A not followed by B" failures; reason about lock, de-skew, scrambling and training capture requirements.
  • Senior: choose probe points as hypothesis tests; state analyzer limitations in every report.
  • Trace-analysis: go from symptom → trace region → first abnormal event → reconstructed transaction → hypothesis.
  • Debugging: distinguish device fault, host fault, channel fault and analyzer artefact.
  • Validation: build repeatable capture recipes and golden traces for regression.

77.3 Story and analogy

🧒 Kid analogy — the wildlife camera

A nature photographer wants a picture of a shy fox. She cannot film the forest all year — her memory card is small. So she puts a camera on the fox's path (probe placement), tells it to start recording when something fox-sized moves (trigger), keeps the last 10 seconds before the movement too (pre-trigger buffer), and ignores leaves blowing (filter). Back home, she watches the clip frame by frame (packet view), groups frames into "fox enters, sniffs, leaves" (transaction view), and decides what the fox was doing (hypothesis).

🧩 Where the analogy breaks

Represents: limited memory, triggers, pre-trigger history, filters, placement. Hides: that the camera itself is part of the path — an interposer changes the electrical channel and can create or hide errors; that the analyzer must understand the scene (lock to the bit stream, de-skew lanes, descramble, know queue addresses) to decode anything; and that what you see is a decoded interpretation, not raw truth. Misleading when: you believe "the camera saw no fox, so no fox passed" — filters, lock loss, buffer overflow and decoder limitations all produce false absences.

💡 Senior insight — trigger on the earliest observable deviation

Host symptoms (timeouts) arrive seconds late. Instead of triggering on the symptom, trigger on the earliest link-visible precursor you can define: an unsuccessful completion, an ERR_* message, a Recovery entry, or a timer trigger on a missing response. Set pre-trigger large enough to contain the precursor's cause; if the buffer cannot hold that much, use capture filters to drop bulk data payload TLPs (keep headers if the tool supports header-only capture version).

77.8 Filters and the capture buffer

  • Capture filters drop traffic before storage: e.g. drop idle/skip ordered sets, drop data MWr payloads, keep only one device's traffic behind a switch. What you drop cannot be argued from later. Record filters in the coverage statement (§74.2).
  • Display filters only hide rows; they are safe, but exports and statistics might honor them — check before exporting.
  • Buffer arithmetic: a Gen4 x4 link carrying ~7 GB/s of read data in one direction fills a buffer quickly. Example: with a hypothetical 8 GB buffer and both directions at high load, the window is on the order of one second, less with storage overheads derived. A 30-second NVMe timeout cannot be fully captured unfiltered; use filters, segmented capture (many short captures around repeated triggers), or trigger on a precursor.
  • Segmented capture (if supported): many small trigger-centred windows — ideal for intermittent failures.

📭 What the analyzer does not see

Host CPU stores to memory (SQE writes), controller-internal activity (FTL, NAND, firmware scheduling), host software (interrupt handling, block layer), and — if PCIe Integrity and Data Encryption (IDE) is enabled — the contents of encrypted TLP data version. Behind a switch, an analyzer on one link sees only that link.

77.10 The four-step method (the heart of this chapter)

Step 1 — From symptom to trace region

Translate the symptom into a link-visible signature and a time relation. "I/O timeout on QID 3" → signature: a command on SQ3 whose CQE never appears; time relation: the doorbell is ~30 s before the host log line. Choose: trigger (unsuccessful completion? timer trigger on missing CQE?), pre-trigger depth, filters. If you already have a long capture: search for the doorbell writes to SQ3 in the window 30 s ± 1 s before the logged time (needs a sync marker — Chapter 71).

Step 2 — Identify the first abnormal event

Walk forward from the last known-good state and compare each stage with the golden shape (TL-1). The first abnormal event is the earliest observation that deviates from expected behavior within coverage. It is frequently quieter than the trigger: a malformed field, a missing Ack, a late completion.

Step 3 — Reconstruct the transaction

Group everything belonging to the affected command: doorbell, SQE fetch (and its CplD payload: opcode, CID, PRPs), PRP list fetches, data, CQE, MSI-X, head doorbell. For PCIe-level problems, group request ↔ completion pairs by Requester ID + Tag, including split completions. Write the reconstructed timeline down.

Step 4 — Formulate root-cause hypotheses

For the stage where the chain broke, list the components that own that stage (Chapter 80), rank them by evidence, and for each define the experiment that would falsify it. A hypothesis that no experiment could disprove is not yet useful.

77.12 Hardware view and safe practice

⚠️ Safe hardware practice

Inserting an interposer is lab-only, requires powering down the system (unless the setup is explicitly designed for hot-plug), ESD precautions, and mechanical care with high-speed connectors. It is non-destructive to data but not production-safe: the extra channel loss can cause link degradation, and removing a drive's host from service to probe it is an operational decision. Never probe a system whose drives hold the only copy of important data.

🏭 Implementation-dependent

Whether an analyzer requires capturing link training to decode (scrambler and lane state), supports lane reversal/polarity inversion, SRIS/SRNS clocking, Gen5/Gen6 rates, FLIT mode, 10/14-bit tags, IDE, or NVMe command decoding for a given spec revision depends on the analyzer model, licenses and software version. Check the release notes before the lab day, not during it.

77.14 Labs

🧪 Lab 77.1 — Paper capture plan (Beginner) SAFE

Objective: write a capture plan without touching hardware. Procedure: for the symptom "random-read p99.9 spikes to 5 ms every few seconds", write: probe point, speed/width, buffer, pre-trigger %, trigger, capture filters, display filters, metadata to record, coverage statement template. Questions: what is your trigger, and why not "every read"?

Solution

Example: interposer at the SSD slot; capture both directions; filter out data payloads (keep headers) if supported; trigger: timer trigger "SQE-fetch CplD for SQ n not followed by data MWr within 2 ms" or, if unsupported, segmented captures triggered on MSI-X with a host-side marker for slow I/Os; pre-trigger ≥ 5 ms. Triggering on every read fills the buffer with normal reads and gives no anchor.

🧪 Lab 77.2 — Coverage audit of an exported capture (Intermediate) SAFE

Objective: given the synthetic export in Chapter 78's normalizer, list what you can and cannot conclude. Solution sketch in Chapter 78's lab.

🧪 Lab 77.3 — Trigger design for a missing interrupt (Advanced) CAUTION

Classification: lab-only hardware (interposer), non-destructive to data, read workload only. Objective: catch TL-6-like failures. Procedure: define a sequence/timer trigger "MWr into CQ ring range, not followed by MWr to MSI-X address range within 20 µs"; run a read-only fio workload; force interrupt affinity changes from the host. Questions: what if your analyzer lacks "not followed by" triggers?

Solution

Fallbacks: external trigger from a host-side watchdog (bpftrace program that detects a request older than 100 ms and toggles a GPIO or writes a marker that produces a recognizable config read), with a deep pre-trigger; or segmented capture triggered on every CQ5 MWr with short windows and offline post-processing (Lab 8 detector).

🧪 Lab 77.4 — Senior forensic: is it the device, the host, the channel, or the analyzer? SAFE

Objective: for each of the five failure patterns above, write the one-paragraph argument you would send to a skeptical colleague, including coverage and confidence. Extension: turn the arguments into a checklist that gates every analyzer-based bug report in your team.

Interview questions

  1. Beginner Capture filter vs display filter?
    Model answer

    Capture filters drop data before storage (irrecoverable); display filters hide stored data.

  2. Beginner Why keep pre-trigger data?
    Model answer

    The cause precedes the trigger; the trigger is usually a consequence.

  3. Beginner Why must the analyzer see both directions?
    Model answer

    Requests and completions, data and Acks, travel in opposite directions; one direction cannot show a transaction.

  4. Intermediate Why might an NVMe command view be empty?
    Model answer

    The decoder lacks queue base addresses because queue creation happened before capture start.

  5. Intermediate How do you align analyzer time with dmesg?
    Model answer

    Sync marker: a recognizable link event generated by a host script that also logs to /dev/kmsg.

  6. Intermediate What does an interposer change?
    Model answer

    The electrical channel (loss, reflections), potentially link training results and error rates.

  7. Advanced How do you capture a failure whose host symptom appears 30 s later?
    Model answer

    Trigger on an earlier precursor, filter bulk payloads, segmented capture, or deep buffer with external trigger and large pre-trigger.

  8. Advanced Analyzer shows LCRC errors but no Naks follow. Interpretation?
    Model answer

    Likely analyzer-side decode error (lock/de-skew/probe), since the real receiver would Nak a bad TLP.

  9. Advanced What changes when IDE is enabled?
    Model answer

    TLP data is encrypted/integrity-protected; the analyzer can show headers and timing but not payload contents (unless provided keys in a supported workflow uncertain).

  10. Senior How do you choose probe points behind a switch?
    Model answer

    Each probe answers "did the packet reach this link?"; bracket the suspected component (TL-7).

  11. Senior What goes in an analyzer-based bug report?
    Model answer

    Capture recipe (probe, settings, trigger, filters), coverage statement, analyzer/software versions, first abnormal event, reconstructed transaction, ranked hypotheses, requested evidence, redactions.

  12. Senior When is an analyzer the wrong tool?
    Model answer

    When the problem is above the link (host scheduling, filesystem) or inside the controller, or when cheaper evidence (logs, counters) already localizes it.

PART XXV

PEX and Proprietary Capture-File Training

Captures outlive the lab bench: they are mailed to vendors, archived with bug reports, and reopened years later. This Part covers the file side — what a proprietary capture file is, how to identify and preserve it, what can be inspected without vendor software, how to export it into portable form, and what is lost in conversion. It also covers captures and diagnostics that come from PCIe switches (for example Broadcom PEX-family switches) rather than from external analyzers.

78 Capture Files, PEX, and Portable Trace Evidence

78.1 Why this chapter exists

"Can you look at this .pex file?" is a common request. The honest answer begins with questions: which tool and version produced it, what was captured, and do we have the software to decode it? Engineers who guess — or who trust a "converter" of unknown provenance — corrupt evidence. Engineers who know the difference between a file container and decoded protocol content handle captures like forensic evidence.

  • Beginner: distinguish a capture file from an export; record a capture's metadata.
  • Intermediate: identify the producing tool and version safely; preserve chain of custody.
  • Advanced: export to portable formats and normalize with a reviewed mapping; validate the conversion.
  • Senior: explain what is lost in conversion and how that limits conclusions; handle switch-generated captures.
  • Trace-analysis / Debugging / Validation: keep conversions deterministic, reproducible and documented.

🧒 Kid analogy — the sealed diary

A capture file is a diary written in a secret alphabet, inside a locked box. You can weigh the box, read the label on it, and photocopy it (safely, without opening). To read the diary you need the key and the alphabet book — the vendor's software. If someone gives you a typed copy (an export), it is easier to share, but the typist may have skipped pages or misread smudges.

🧩 Where the analogy breaks

A capture file is not just text in a secret alphabet: it may contain raw per-lane symbol data, analyzer state, decoder settings, bookmarks and annotations, and an index database built by the software. "Reading" it means re-running a decoder whose output depends on the software version and settings — two versions can produce different decoded views from the same file.

78.4 Why capture formats are proprietary

  • They encode hardware-specific raw data (lane mapping, per-lane timestamps, analyzer error flags) that only make sense with that hardware's design.
  • They evolve with every software release (new protocol generations, new decoders, new metadata).
  • They embody vendor intellectual property (decoding pipeline, indexing).
  • Consequence: there is generally no public, official parser for such files; this book does not point to any, and you should be skeptical of unofficial converters — they may silently misinterpret data. If your vendor offers an SDK, automation API or command-line export for your version, use that and record its version version.

78.5 Identifying the producing tool and version — safely

# Work on a COPY. Never open the only original in tools that might "upgrade" it.
cp -p capture_0612.pex /evidence/work/
sha256sum capture_0612.pex > capture_0612.pex.sha256     # chain of custody
ls -l --time-style=full-iso capture_0612.pex               # size, mtime
file capture_0612.pex                                       # usually just "data"
xxd capture_0612.pex | head -16                             # header bytes (do not guess meanings)
strings -n 8 capture_0612.pex | head -40                    # readable strings may name tool/version

What you may learn: readable product or version strings, sometimes the capture date or the analyzer model. What you must not do: infer field layouts from a few bytes and write a "parser". The reliable sources are: the vendor software's file/capture information dialog (generic description; names vary), the lab notebook of whoever captured it, and sidecar files saved alongside (settings, notes).

78.7 Exporting to a portable representation

  1. Open the capture (copy) in the vendor software version recorded in metadata (or a compatible later one — note any differences).
  2. Clear display filters, or deliberately set them and record them.
  3. Export packet-level rows with at least: timestamp (absolute or relative — record which), direction/link, packet type, requester ID, completer ID, address, tag, length, completion status, error flags, and header bytes if available. Exclude payload bytes unless needed and permitted.
  4. Export the vendor tool's own statistics (counts per packet type) for validation.
  5. Write a metadata JSON sidecar (§78.6).
  6. Normalize with a reviewed mapping (below) and compare counts.
#!/usr/bin/env python3
"""normalize_export.py - map an analyzer's TEXT/CSV EXPORT to the normalized schema.
OFFLINE PARSING of a file you exported with the vendor's own software.
It does NOT read proprietary capture files: decoding those requires the
vendor's tools. Column names differ between tools and versions, so the
mapping lives in a small dict you edit after looking at the export header."""
import csv, io, json, sys, hashlib

SCHEMA = ["t_ns", "dir", "layer", "kind", "req", "addr", "tag", "len", "status"]

# Edit this mapping for YOUR export (keys = your column names). Example only.
MAPPING = {"Time Stamp": "t_ns", "Link Dir": "dir", "Packet": "kind",
           "Req ID": "req", "Address": "addr", "Tag": "tag",
           "Length": "len", "Status": "status"}
TIME_UNIT_NS = {"ns": 1, "us": 1_000, "ms": 1_000_000, "s": 1_000_000_000}
DIR_MAP = {"Upstream": "UP", "Downstream": "DN", "UP": "UP", "DN": "DN"}
DLL_KINDS = {"Ack", "Nak", "UpdateFC", "InitFC1", "InitFC2", "PM"}

def parse_time(text, default_unit="ns"):
    text = text.strip().replace(",", "")          # beware locale decimal commas!
    for unit in ("ns", "us", "ms", "s"):
        if text.endswith(unit):
            return round(float(text[:-len(unit)]) * TIME_UNIT_NS[unit])
    return round(float(text) * TIME_UNIT_NS[default_unit])

def normalize(fh, mapping=MAPPING):
    rows, problems = [], []
    reader = csv.DictReader(fh)
    missing = [c for c in mapping if c not in (reader.fieldnames or [])]
    if missing:
        problems.append(f"export lacks expected columns {missing} - wrong mapping or tool version?")
    for n, raw in enumerate(reader, 2):
        ev = {mapping[k]: v.strip() for k, v in raw.items() if k in mapping and v is not None}
        try:
            ev["t_ns"] = parse_time(ev["t_ns"])
            ev["dir"] = DIR_MAP.get(ev.get("dir", ""), "?")
            ev["layer"] = "DLL" if ev.get("kind") in DLL_KINDS else "TL"
            ev["addr"] = int(ev["addr"], 16) if ev.get("addr") else None
            ev["tag"] = int(ev["tag"], 16) if ev.get("tag") else None
            ev["len"] = int(ev["len"]) if ev.get("len") else 0
        except (KeyError, ValueError) as e:
            problems.append(f"line {n}: cannot normalize ({e}) -> kept out, review by hand")
            continue
        rows.append({k: ev.get(k) for k in SCHEMA})
    rows.sort(key=lambda r: r["t_ns"])
    return rows, problems

if __name__ == "__main__":

⚠️ Conversion caveats
  • Dropped layers: exports often omit DLLPs, ordered sets and link-state events unless explicitly selected.
  • Timestamps: precision may be reduced; time base may be relative to trigger; per-direction or per-link clocks may be merged with unknown alignment.
  • Filters: active display filters may silently apply to exports.
  • Locale: decimal commas and thousands separators break naive parsers (the normalizer strips commas — check that this is correct for your locale!).
  • Truncation: payload columns may be truncated; long captures may be split into multiple files.
  • Version drift: column names and enumerations change across software versions — the mapping is versioned with the export.
  • Validation: per-type counts after normalization must equal the vendor tool's statistics for the same range; unparseable rows must be reported, never dropped silently (as the script does).

78.8 Captures and diagnostics from PCIe switches

Some PCIe switches — Broadcom PEX-family devices among them — provide diagnostic capabilities such as per-port error counters, performance/traffic counters, and in some families an internal packet-capture or trace facility, accessible through vendor management tools or in-band/out-of-band interfaces impl. The details (which families, buffer sizes, trigger options, file formats) are vendor documentation, frequently under NDA, so this book does not describe them. Conceptually:

💡 Senior insight

In TL-7 a switch-internal view would answer "was the completion received on the upstream port and was it ever queued for the downstream port?" — the exact gap between the two external probes. When a switch is in the path, ask its vendor early which diagnostic features exist for your part and firmware; they can save weeks.

78.9 Data safety and sharing

A capture of a production host may contain user data in TLP payloads, encryption keys in transit (if not IDE-protected), file contents, and identifiers. Before sharing: export headers only where possible; zero or remove payloads; redact serial numbers (Identify data, DSN capability), host names and paths; and keep the original under access control with its hash. Share the original proprietary file only with parties who need it and are permitted to see it (e.g. the vendor under NDA).

Quiz

  1. Name the five representations of "a trace".

    Answer

    Raw packets/symbols, file container, analyzer database, decoded protocol content, exported CSV/text/XML.

  2. Why compute a hash before anything else?

    Answer

    Chain of custody: proves later analyses used the unmodified original.

  3. What can a switch-internal capture show that an external analyzer on one link cannot?

    Answer

    Traffic at multiple ports/internal points simultaneously — e.g. whether a packet received upstream was queued for a downstream port.

    Model answer
