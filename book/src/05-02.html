40 End-to-End NVMe Write

40.1 Why this chapter exists

A Write looks like a Read with the arrows flipped, and that intuition is half right and half dangerous. The control path (SQE, doorbell, fetch, CQE, MSI-X, head doorbell) is identical. The data path is not: for a Write the device must pull the data from host memory with non-posted MRd requests, each of which needs tags, Non-Posted credits, CplD responses and completion-timeout supervision. Writes therefore exercise the host's memory-read path far harder than reads do, they expose MRRS and RCB behaviour, and they bring in the volatile write cache, FUA (Force Unit Access) and Flush semantics — the source of most "I lost data after power loss" investigations.

40.2 Learning objectives

  • List the stages of a 4 KiB NVMe Write (opcode 01h) and mark which cross the link and in which direction.
  • Compute the number of MRd requests and CplD completions for a given size, MRRS and RCB.
  • Explain when the controller is allowed to post the CQE (before NAND program, with volatile write cache) and how FUA/Flush change that.
  • Recognise in a synthetic trace the data-fetch phase, tag usage and completion splitting.
  • Diagnose write-specific failures: completion timeout on data fetch, poisoned data, IOMMU read fault, write fault status, power-loss data loss.

40.3 Prerequisites

40.4 Story and analogy

🧒 Kid analogy

This time you want the warehouse to store your drawing. You put the request card in the tray and ring the bell, just like before. But the worker can't take your drawing through the bell either: they must reach into your house again and ask "please hand me pieces 1, 2, 3 and 4 of the drawing", and you (your house's front door, the root complex) hand each piece back. When the worker has all the pieces safely in the warehouse's front desk tray (write cache), they can already give you a receipt — even if they haven't walked to the shelf yet.

🧩 Where the analogy breaks

The "front desk tray" (volatile write cache) loses its contents if power fails unless the drive has power-loss protection capacitors; the receipt (CQE) does not promise the drawing is on the shelf (NAND) unless you asked with FUA or later sent a Flush. Also, the worker's requests for pieces are numbered with tags, can be outstanding concurrently and can be answered out of order across different tags.

    The data to be written is already sitting in a host buffer. The driver fills slot 3 of Submission Queue 1 with a command that says where that buffer is and where on the namespace the data should go.

    The driver writes the new tail index into the SSD's SQ1 tail doorbell register: "there is new work, up to (not including) slot 4". Identical to the Read.

    Where: Device register at BAR0 + 0x1008PCIe: Yes, host → device. · MWr, 4 bytes (posted)
    Value written: 4 Neither the command nor the data has crossed PCIe yet.
  3. Device fetches the command from host memory

    The controller sees the tail move from 3 to 4 and reads slot 3: it sends a read request and the root complex answers with the 64 bytes.

    Where: Host memory, SQ1 slot 3PCIe: Yes, both ways. · MRd (device → host), then CplD with 64 bytes (host → device)
    The device now knows: "write 8 blocks at LBA 0x1000, take the data from 0x1_2345_6000, call it CID 0x002B"
  4. Device reads the 4 KiB of data from the host buffer

    This is the step that makes a Write different. The data must travel host → device, but the host never pushes it: the device's DMA engine sends read requests (MRd) for the buffer at PRP1, and the host's root complex answers each one with completions carrying the data (CplD). Each MRd is limited by Max_Read_Request_Size and holds a tag until all its CplDs have arrived.

    Where: Host memory, data buffer at 0x1_2345_6000PCIe: Yes, both ways. · MRd (device → host, no data) then CplD with the data (host → device)
    MRRS = 512 B → 8 MRd requests, tags 0x12–0x19 MPS = 256 B → 16 CplD × 256 B (two per request) The bytes in RAM are only read; the buffer is unchanged.
  5. Data lands in the controller's write cache

    The controller reassembles the 4 KiB in its buffer (the write cache, usually DRAM inside the SSD) and checks protection information if the namespace uses it. The NAND has not been touched yet.

    Where: Inside the SSDPCIe: No. Nothing appears on the PCIe link during this step.
    Volatile write cache present and enabled (VWC = 1, WCE = 1), FUA = 0 → the controller may complete the command now.
  6. Device writes the 16-byte completion entry

    The controller writes a completion entry into CQ1 slot 3. With a volatile write cache enabled and FUA = 0, this completion may be posted before the data is programmed into NAND: success means "accepted", not "durable". With FUA = 1, or with no volatile write cache, the controller posts it only after step 10 has finished for this data.

    Where: Host memory, CQ1 slot 3 (address = CQ base + 3 × 16)PCIe: Yes, device → host. · MWr, 16 bytes
    CID = 0x002B Status = 0 (success) Phase tag = 1 SQID = 1 SQHD = 4
  7. Device sends the MSI-X interrupt

    The controller writes the interrupt message from its MSI-X table entry; the CPU runs the driver's handler. PCIe ordering keeps this write behind the completion entry.

    Where: Interrupt address/data taken from the device's MSI-X tablePCIe: Yes, device → host. · MWr, 4 bytes, to the MSI-X address
    Same mechanism as for a Read: an interrupt is just a memory write.
  8. Software reads the completion entry

    The handler checks the phase tag, matches CID 0x002B to the Write it sent, sees status 0 and completes the request; the application's write call returns.

    Where: Host memory, CQ1 slot 3PCIe: No. The CPU reads its own RAM.
    Phase = 1 as expected → new entry CID 0x002B → our Write; status 0 → success The buffer may now be reused by the application.
  9. Software rings the CQ head doorbell

    The driver writes the new head index into the CQ1 head doorbell so the device may reuse the consumed completion slots.

    Where: Device register at BAR0 + 0x100CPCIe: Yes, host → device. · MWr, 4 bytes (posted)
    Value written: 4
  10. Later: the cached data is programmed into NAND

    In the background the FTL picks a fresh NAND page, programs the data and updates its logical-to-physical map. Programming takes hundreds of microseconds to milliseconds and is invisible on PCIe. Until it finishes, a power loss on a drive without power-loss protection can lose this data, even though the host already saw success. A Flush command (or FUA on the Write) is how software asks for durability.

    Where: Inside the SSD (write cache → NAND)PCIe: No.
    Order with volatile write cache: 5 → 6 → 7 → 8 → 9 … 10 Order with FUA = 1 or no cache: 5 → 10 → 6 → 7 → 8 → 9

As for the Read, software writes only three things: the command (step 1) and the two doorbells (steps 2 and 9). The data does travel host → device, but the device fetches it: every data byte arrives in a CplD answering one of the device's own MRd requests.

🔧 Hardware

The number of tags a controller can keep outstanding, multiplied by MRRS, bounds the bytes in flight on the read path. With 8-bit tags (256) and MRRS 512 that's 128 KiB in flight — enough for Gen4 x4 at ~1–2 µs round trip. Gen5/Gen6 links and longer latencies (switches, retimers) push designs toward 10-bit tags (1024) — version: 10-bit tag requester/completer support is optional from PCIe 4.0 and must be enabled in Device Control 2. Write bandwidth that tops out well below link rate, with a trace showing the device stalls waiting for tags, is a classic signature.

40.7 Sequence diagram

40.8 Stage notes — the five views for the write-specific stages

Data fetch (MRd) — device → host

Analogy: "please pass me piece 3 of the drawing". Technical: the controller walks PRP1/PRP2 (or the PRP list it fetched) and issues reads no larger than MRRS that do not cross 4 KiB boundaries. Hardware: each request occupies a tag and reserves completion buffer space at the device (a requester must not issue a non-posted request unless it can accept all completions — completion credits are typically advertised as infinite by endpoints, so the requester self-limits). Protocol: MRd, 4DW header if above 4 GiB, Length in DW, First/Last BE all ones for aligned transfers. Trace: a train of upstream MRds with incrementing addresses and distinct tags.

Data delivery (CplD) — host → device

Analogy: pieces handed through the door. Technical: the completer returns one or more CplDs per request; Byte Count indicates remaining bytes including this completion; Lower Address gives the starting byte address low bits. Hardware: completions for the same request arrive in address order; completions for different tags may interleave. Protocol: CplD with Status SC; EP=1 marks poisoned data. Trace: pairs (or groups) of CplD with the same tag and decreasing Byte Count: 512, 256 for a 512-byte request split into two 256-byte completions.

Completion point

Technical: If the Volatile Write Cache is present and enabled (Feature 06h) and FUA=0, the controller may post the CQE as soon as the data is in its buffer. With FUA=1 (CDW12 bit 30) it must not complete until data is in non-volatile media. Drives with power-loss protection may report VWC not present because their buffer is effectively non-volatile (impl). Trace: the gap between the last CplD and the CQE MWr is short (µs) for cached writes and long (hundreds of µs or more) for FUA writes.

💡 Senior insight

On the PCIe link, a FUA write and a normal write look identical except for one bit inside the SQE payload of the CplD and the timing gap before the CQE. If you're investigating data loss after power failure, decode the SQE CDW12 bit 30 in captured CplDs and check whether Flush commands (opcode 00h on an I/O queue) were present before the power event. The absence of Flushes (in a complete capture) is strong evidence of a host/filesystem durability problem rather than an SSD bug.

40.11 Common mistakes

  • Expecting MWr from host to device for write data. The host never pushes I/O data (except into a CMB/PMR when used as a data buffer).
  • Treating each CplD as one request — multiple completions per request are normal.
  • Misreading Byte Count as "bytes in this TLP" — it is bytes remaining, including this one.
  • Assuming the CQE means data is on NAND.
  • Mapping the buffer DMA_FROM_DEVICE for a write (IOMMU permission fault).
  • Unmapping/reusing the buffer before the CQE (use-after-free DMA: device reads changed data).

40.12 Lab

🧪 Lab 40.1 — Count TLPs for writes of varying size SAFE

Objective: build intuition for MRRS/RCB effects without hardware. Setup: paper or a Python REPL. Procedure: for transfer sizes 512 B, 4 KiB, 16 KiB, 128 KiB and MRRS ∈ {128, 512, 4096}, completer max payload 256, RCB 64, compute MRd and minimum CplD counts. Observations: fill a table. Questions: which parameter dominates request count? which dominates completion count?

import math
def counts(size, mrrs, cpl_max=256):
    n_mrd = math.ceil(size / mrrs)
    n_cpl = sum(math.ceil(min(mrrs, size - i*mrrs) / cpl_max) for i in range(n_mrd))
    return n_mrd, n_cpl
for size in (512, 4096, 16384, 131072):
    for mrrs in (128, 512, 4096):
        print(size, mrrs, counts(size, mrrs))
Solution

MRRS dominates request count (e.g. 128 KiB: 1024 / 256 / 32 requests). The completer's max payload dominates completion count (128 KiB: 512 completions at 256 B regardless of MRRS ≥ 256; at MRRS 128 it's 1024 completions). Larger MRRS reduces tag and NP credit pressure, at the cost of potentially larger latency for other devices (fairness).

Extension: add RCB-split modelling for an unaligned start address (e.g. 0x...0020).

Objective: observe latency difference between cached writes and FUA/flush writes. Setup: a scratch NVMe namespace with no valuable data. ⚠️ Safety

Write workloads destroy data on the target. Use only a dedicated test device or namespace. Do not change Feature 06h on a production system.

Solution

With PLP, the controller can treat its buffer as non-volatile and complete Flush/FUA quickly (or reports VWC not present). Without PLP, Flush forces NAND programming of cached data, adding hundreds of µs to ms.

Quiz

  1. Which TLP type carries write data across the link for an NVMe Write with host-memory buffers?

    Answer

    CplD (host → device), answering the controller's MRd requests.

  2. A 2 KiB MRd is answered by CplDs with Byte Count 2048, 1792, 1536… what is the payload of each?

    Answer

    256 bytes each (difference between successive Byte Counts).

  3. Which SQE bit requests FUA on a Write?

    Answer

    CDW12 bit 30.

  4. What PCIe error does the controller log if the host never answers a data MRd?

    Answer

    Completion Timeout (uncorrectable, default non-fatal) in its AER Uncorrectable Error Status.

  5. What does MRRS limit?

    Answer

    The maximum size of a single memory read request issued by that function.

Interview questions

  1. Beginner How does write data get from host to SSD?
    Model answer

    The SSD reads it: MRd requests to the PRP addresses, the root complex answers with CplD packets carrying the data.

  2. Intermediate Why might writes be slower than reads at the same queue depth on a deep PCIe topology?
    Model answer

    Non-posted reads need round trips; with limited tags/MRRS the device can't cover the bandwidth-delay product. Reads use posted writes, which stream without waiting.

  3. Advanced Explain how a write CQE can be correct while the data is lost after a power cut.
    Model answer

    VWC enabled, FUA=0, no Flush: CQE posted when data reached volatile buffer. Durability requires Flush or FUA, or PLP hardware.

  4. Senior You see a poisoned CplD on a write data fetch. Who is at fault and what do you capture next?
    Model answer

    Data was poisoned at or before the completer — host memory (uncorrectable ECC) or RC internal error. Capture machine-check/EDAC logs, root port AER, physical address; the SSD should fail the command (not write poisoned data) — check its status code.

  • I can draw the write sequence and point out every non-posted request.
  • I can compute MRd/CplD counts from MRRS, MPS and RCB.

41 Command-to-TLP Correlation

41.1 Why this chapter exists

A protocol analyzer capture of a busy SSD contains millions of TLPs from dozens of queues and hundreds of in-flight commands. Nothing in a TLP header says "this belongs to NVMe command CID 0x0042 on queue 3". Correlation is an act of reasoning: you link a doorbell to a queue by address, a queue slot to an SQE fetch by address, an SQE to its data by PRP addresses, data to a CQE by CID and queue, and a CQE to an interrupt by vector. This chapter teaches that reasoning formally, and introduces the investigative rules — complete event model, timeline reconstruction, first-abnormal-event, negative evidence — used in every forensic lab of the remaining parts.

41.2 Learning objectives

  • Distinguish crisply: NVMe command, PCIe TLP, NVMe CQE, PCIe Completion TLP.
  • Build an address map (BAR0 doorbells, SQ/CQ rings, PRP lists, data buffers, MSI-X addresses) from initialization traffic.
  • Correlate each NVMe event to TLP type, direction, requester/completer, address region and tag.
  • Represent events using the complete event model and reconstruct expected vs observed timelines.
  • Apply the first-abnormal-event and negative-evidence rules.

41.3 The four things that are NOT interchangeable

📌 Remember

"Completion" means two unrelated things in this stack. A PCIe Completion (Cpl/CplD) answers a PCIe non-posted request within microseconds and lives only on the link. An NVMe Completion Queue Entry answers an NVMe command, may take milliseconds, and is carried to host memory inside a PCIe Memory Write — never inside a PCIe Completion.

41.4 The correlation chain

NVMe command (SQID, CID)
   ↕  queue location        SQ base + slot×64  (from Create I/O SQ PRP1 + slot index)
   ↕  controller access     MRd by device (ReqID = device BDF) to that address
   ↕  PCIe requester/completer  requester = device, completer = RC
   ↕  tag                   Tag in MRd = Tag in CplD (+ ReqID)
   ↕  data addresses        PRP1/PRP2/PRP list from the SQE payload → MWr (read) / MRd (write)
   ↕  completion            CQE MWr to CQ base + slot×16, payload CID + SQID
   ↕  interrupt             CQ's IV → MSI-X table entry → MWr to Message Address

Each link of the chain is learned from earlier traffic. You cannot correlate a mid-run capture unless you can reconstruct the setup: BAR0 address (from config space or lspci), CAP.DSTRD (from a CAP register read or the driver), queue base addresses (from Create I/O SQ/CQ admin commands — their PRP1 field), and MSI-X table contents (from host MMIO writes to the table, or by reading the BAR region).

🔍 Clock domains

Kernel timestamps, analyzer timestamps and device-internal logs run on different clocks. Align them with an anchor event visible in two domains (e.g. a doorbell MWr that also appears as an MMIO write in a hypervisor trace, or a distinctive admin command). Never compare raw timestamps across domains without an anchor and an error bar.

41.8 The first-abnormal-event rule

The first visible failure is not necessarily the root cause. Work backward: SYMPTOM → FIRST DEVIATION → PRECEDING CAUSE.

SYMPTOM          : "nvme0: I/O 66 QID 3 timeout" at t = 30 s (illustrative)
      ↑ backward
FIRST DEVIATION  : SQE fetch MRd (t = 0.7 µs) has no visible CplD
      ↑ backward
PRECEDING CAUSE? : at t = −2 s the IOMMU domain was switched (VFIO rebind),
                   SQ3 IOVA no longer mapped  → RC returns UR / drops request

The timeout is a symptom 30 seconds later; the first deviation is 0.7 µs after the doorbell; the cause predates the command entirely. An engineer who stops at the timeout will "fix" it by raising io_timeout.

41.9 The negative-evidence rule

Absence of an event is evidence only if (1) the event was expected and (2) the capture was complete enough to observe it. Never write "the device did not send the CQE". Write "no MWr to the CQ3 region is visible in the captured interval", then qualify with coverage: was the analyzer on the right link segment? Was the buffer full or filtered? Were both directions captured? Was the trigger window long enough? Was the CQ actually in host memory?

ClaimAcceptable only if…
"No doorbell was rung"Downstream direction captured, no filter on MWr, BAR0 address known, capture began before submission
"The device never fetched the command"Upstream MRd captured unfiltered for the whole interval, SQ base known, CMB not used for SQ
"No interrupt was sent"Upstream MWr to MSI address range captured, vector address known, no interrupt remapping change
"No error occurred"AER enabled and unmasked for that error, reporting enabled up to the root port, logs read before being cleared

41.10 Correlation worked example

Given (synthetic) these three upstream packets in a mixed trace with SQ1 base 0x1_0000_0000, SQ2 base 0x1_0001_0000, CQ1 base 0x1_0010_0000, CQ2 base 0x1_0011_0000 (1024-entry queues):

A: MRd  addr 0x1_0001_0FC0  len 32 DW tag 0x05
B: MWr  addr 0x1_0011_00A0  len 4 DW  payload DW2=0x0002_0040 DW3=0x0001_7A3F
C: MWr  addr 0xFEE0_1000    len 1 DW  payload 0x0000_0042

A: address − SQ2 base = 0xFC0 = slot 63; length 32 DW = 128 bytes → fetching SQ2 slots 63 and 64 (two SQEs in one request). B: address − CQ2 base = 0xA0 → CQ2 slot 10. DW2 = 0x0002_0040 → SQID 2, SQHD 0x40 (64); DW3 = 0x0001_7A3F → CID 0x7A3F, bit 16 Phase = 1, status bits 31:17 = 0 → success. The SQHD of 64 is consistent with slot 63 having been consumed. C: an MSI-X write; to know which CQ it signals, consult the MSI-X table: if entry 2 has address 0xFEE0_1000 and data 0x42, it's vector 2, which CQ2 was created with. Note that several vectors may share an address and differ only in data.

41.11 Common mistakes

  • Matching completions to requests by tag only (ignoring Requester ID) on topologies with several requesters.
  • Assuming one SQE per fetch MRd.
  • Correlating CQEs to commands by order instead of CID.
  • Comparing timestamps across clock domains without anchors.
  • Declaring absence without coverage.
  • Assuming tags are unique for all time — they are reused as soon as the request completes.

Quiz

  1. Which carries an NVMe CQE: a PCIe Completion or a PCIe Memory Write?

    Answer

    A PCIe Memory Write (posted, device → host).

  2. An MRd of 32 DW to an SQ ring — how many SQEs?

    Answer

    Two (128 bytes / 64).

  3. Which field links a CplD to its MRd?

    Answer

    Requester ID + Tag (Completer ID identifies the responder).

  4. Phrase correctly: the analyzer shows no CQE.

    Answer

    "No MWr to the CQ region is visible in the captured interval" — plus a statement of capture coverage.

  5. What admin command reveals an I/O CQ's base address and vector?

    Answer

    Create I/O Completion Queue (05h): PRP1 = base, CDW11 IV = vector.

Interview questions

  1. Beginner What's the difference between an NVMe completion and a PCIe completion?
    Model answer

    NVMe CQE: 16-byte record reporting an NVMe command's outcome, written into host memory via MWr. PCIe Cpl/CplD: transaction-layer response to a non-posted request, matched by ReqID+Tag.

  2. Intermediate How do you find which NVMe queue a doorbell write targets?
    Model answer

    (offset − 1000h)/(4 << DSTRD) = index; even index → SQ (index/2), odd → CQ ((index−1)/2).

  3. Advanced Why can't you correlate a capture started mid-run, and how do you recover?
    Model answer

    Queue bases, vectors and BAR addresses were set up earlier. Recover from host side (driver debugfs/tracepoints, lspci, reading MSI-X table), or by inferring ring regions from repeating MRd/MWr address patterns, with lower confidence.

  4. Senior Explain the first-abnormal-event and negative-evidence rules with an example.
    Model answer

    As in §41.8–41.9: timeout symptom → missing CplD deviation → IOMMU remap cause; absence claims need coverage.
