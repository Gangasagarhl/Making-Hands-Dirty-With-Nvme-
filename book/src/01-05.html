PART II

Storage Fundamentals

We walk down the corridor and open the library door. Spinning disks, the interfaces built for them, flash memory and the hidden machinery — the Flash Translation Layer, garbage collection, wear leveling — that makes flash behave like a disk. By the end you will know exactly why a new interface was needed, and which parts of an SSD's behaviour no interface will ever show you.

2 What Is Storage?

Why this chapter exists

An NVMe trace tells you when the device answered. It never tells you why it took 80 µs one time and 9 ms the next. The why is inside the SSD: NAND page reads, program and erase operations, garbage collection, a full write buffer, a read retry on a weak cell. A protocol engineer who does not understand the media will misattribute media behaviour to the protocol — and spend weeks hunting a PCIe bug that is really garbage collection.

Learning objectives

  • Explain how HDDs and SSDs store data and why their performance profiles differ by orders of magnitude.
  • Compare SATA, SAS and NVMe at the level of link, command set and queueing.
  • Explain NAND pages, blocks, planes, dies and channels and why erase-before-write forces an FTL.
  • Compute write amplification, endurance (TBW/DWPD), over-provisioning, IOPS↔throughput and use Little's law.
  • Convert namespace sizes from logical blocks to bytes and handle KB/KiB/GB/GiB exactly.
  • Interpret NVMe SMART data-unit counters using their defined units.
  • Separate host-visible protocol behaviour from implementation-dependent media behaviour.

Prerequisites

Chapter 1, especially §1.2 bits and bytes (units), §1.3 memory (hierarchy) and §1.11 controllers.

Story

🧒 Kid analogy — two libraries

The old library keeps its books on a giant spinning record player. To read a page, a robot arm swings to the right ring and waits for the right spot to spin round. It is cheap and enormous, but every new page means waiting for the arm and the spin.

The new library keeps its words in millions of tiny jars of marbles. Reading a jar is quick. But there is a strange rule: you can only fill an empty jar, and you can only empty jars a whole shelf at a time. So when you want to change a word, the librarian writes the new word into a fresh jar somewhere else, crosses out the old jar in a big index book, and later — during quiet time — copies the still-good jars off a messy shelf so the whole shelf can be emptied. Also, each jar wears out after being emptied too many times, so the librarian spreads the work around evenly.

🌍 Real-world analogy

An SSD is like a hotel with a strict rule that rooms can only be cleaned floor by floor. Guests (data) who “change rooms” are simply given a new room; the front desk (FTL) updates its register; housekeeping (garbage collection) periodically moves the remaining guests off a mostly-empty floor so the whole floor can be cleaned (erased). A hotel that keeps spare floors (over-provisioning) never makes guests wait while housekeeping works.

🧩 Where the analogy breaks

Hotels do not have rooms that wear out after a few thousand cleanings, nor rooms whose contents slowly fade (NAND charge leakage/retention). And the front desk register in a real SSD is itself data that must survive sudden power loss — a hard engineering problem the analogy hides.

Beginner explanation

Storage is where data lives when the power is off. The host does not see platters or flash cells; it sees a numbered array of fixed-size logical blocks (typically 512 bytes or 4 KiB), addressed by Logical Block Address (LBA) 0, 1, 2, … The device's job is to make that simple array fast and durable, whatever the media underneath.

2.1 HDD — the hard disk drive

An HDD stores bits as magnetic orientation on spinning platters. A head on an actuator arm moves to a track (seek), waits for the sector to rotate under it (rotational latency) and then transfers data. Every random access pays mechanical time:

taccess ≈ tseek + trot + txfer, trot,avg = ½ × 60 / RPM
  • tseek — head movement time, several ms average impl
  • trot,avg — average rotational wait in seconds: half a revolution
  • RPM — spindle speed (5,400 / 7,200 / 10,000 / 15,000)
  • txfer — media transfer time, tiny for 4 KiB

For 7,200 RPM: trot,avg = 0.5 × 60/7200 = 4.17 ms. With ~8 ms seek, a random 4 KiB access takes ~12 ms → ~80 random IOPS per disk derived. Sequential transfer, by contrast, can reach a few hundred MB/s because no seeks are needed. HDDs therefore love sequential I/O and hate random I/O; an HDD with queue depth 32 helps a little because the drive can reorder commands to shorten head travel (that is what Native Command Queuing was for).

Misconception: “Interface speed limits an HDD.” A single HDD cannot saturate even a 3 Gb/s SATA link on random I/O; mechanics dominate.

2.2 SATA — Serial ATA

SATA (Serial AT Attachment) replaced parallel ATA in the early 2000s for consumer and many enterprise drives. Key facts:

  • Link rates 1.5, 3.0 and 6.0 Gb/s (SATA I/II/III), 8b/10b encoding → 6 Gb/s carries at most 600 MB/s of raw data, ~550 MB/s achievable after protocol overhead derived.
  • Half-duplex at the protocol level: one frame direction at a time per link.
  • Uses the ATA command set (READ FPDMA QUEUED, WRITE FPDMA QUEUED for NCQ).
  • NCQ (Native Command Queuing): up to 32 outstanding commands per device (tag 0–31) verified.
  • Host side normally uses an AHCI (Advanced Host Controller Interface) controller, a PCI device that bridges system memory to SATA ports (Chapter 3).

For HDDs, SATA was more than enough. For SSDs, the 600 MB/s ceiling was reached by mainstream SATA SSDs within a few years — the ceiling, not the flash, became the limit.

2.3 SAS — Serial Attached SCSI

SAS carries the SCSI command set over serial links and targets enterprise systems:

  • Link rates 3, 6, 12 Gb/s and “24G” SAS (22.5 Gbaud with a more efficient encoding) version.
  • Full-duplex; dual-port drives connect to two controllers for high availability.
  • Expanders allow hundreds of drives behind one HBA; SAS controllers can also attach SATA drives.
  • Rich SCSI features: deep command queues per device (depth is device- and HBA-dependent impl), task management, protection information (T10 PI), mature error recovery.

SAS SSDs exist and are fast, but each I/O still traverses an HBA, its firmware and a SCSI protocol stack. NVMe adopted several SAS-world ideas (dual-port, end-to-end protection information, reservations) while removing the HBA in the middle.

2.4 SSD — solid-state drive

An SSD has no moving parts: a controller system-on-chip (Figure 1.4), NAND flash packages, usually DRAM for the mapping table and buffers (or a Host Memory Buffer borrowed from host DRAM on DRAM-less designs), power-loss protection capacitors on enterprise drives, and a host interface. Form factors include 2.5-inch, M.2, U.2/U.3 and the EDSFF family (E1.S, E1.L, E3.S, E3.L).

The SSD's essential trick is parallelism. A single NAND die is not fast — one page read takes tens of microseconds — but an SSD contains dozens to hundreds of dies operating at once. The controller's job is to keep them all busy. Feeding that parallelism needs many commands in flight, which an interface with a single 32-deep queue cannot supply efficiently.

2.5 NAND flash

A NAND cell stores charge in a floating gate or charge-trap layer; the stored charge shifts the cell's threshold voltage, which the read circuitry senses against reference voltages. Storing more bits per cell means distinguishing more voltage levels:

TypeBits/cellVoltage statesRelative read/program speedTypical endurance (P/E cycles)
SLC12Fastest~tens of thousands to 100 K
MLC24Fast~3 K–10 K
TLC38Medium~1 K–3 K
QLC416Slower, especially program~hundreds to ~1 K+

Endurance and speed values are broad industry ranges impl; they vary by vendor, generation and how the controller manages the cells. Modern NAND is 3D: hundreds of layers of cells stacked vertically. Many SSDs also run part of their TLC/QLC NAND in SLC mode as a fast write cache — which is why a long sustained write can suddenly slow down when that cache fills.

🔧 Hardware — why bits fade

Charge leaks over time (retention), reading neighbours disturbs cells (read disturb), and each program/erase cycle damages the oxide (wear). The controller fights back with strong ECC, read-retry with shifted reference voltages, periodic refresh (rewriting data), and wear leveling. All of this is invisible to NVMe — except as latency outliers and, eventually, SMART statistics.

2.6 NAND pages

A page is the smallest unit NAND can program (write) and the usual unit it reads. Modern page sizes are commonly 16 KiB of data plus a spare area for ECC and metadata impl. Constraints: a page can be programmed only when erased; within a block, pages are typically programmed in order; a programmed page cannot be partially rewritten.

Consequence: when the host writes 4 KiB, the controller must buffer and combine writes to fill pages (and often multiple planes' pages at once), and a 4 KiB host overwrite cannot modify the old page in place.

2.7 NAND blocks

A block (erase block) is the smallest unit that can be erased, containing hundreds to thousands of pages — block sizes in modern 3D NAND are many MiB impl. Erase is slow (milliseconds) and each erase wears the block. This mismatch — write in pages, erase in blocks — is the single most important fact about flash. It is the reason the FTL, garbage collection, write amplification and over-provisioning exist.

2.8 Channels

A channel is an independent bus between the controller and a group of NAND packages, using a NAND interface standard (ONFI or Toggle) at a rate measured in MT/s. Controllers commonly have 4 to 16 channels impl. Data transfers on different channels proceed in parallel; on one channel, transfers to different dies are time-multiplexed.

2.9 Dies

A die (often called a LUN in NAND interface terminology — not to be confused with a SCSI LUN) is the unit that executes array operations independently. While die 0 is busy for tens of microseconds sensing a page, the channel can be used to send commands to or move data from die 1. This die interleaving is the main source of SSD parallelism.

2.10 Planes

A die is split into planes (commonly 2 to 6 impl), each with its own page buffer. Multi-plane operations read or program one page in each plane at once, multiplying a die's throughput — subject to addressing restrictions defined by the NAND vendor.

PNAND = channels × dies per channel × planes per die
  • PNAND — maximum number of page operations that can be in progress simultaneously (an upper bound)

Example: 8 channels × 4 dies × 4 planes = 128 page operations in flight. If a page read (tR) takes ~50 µs and a page is 16 KiB, the array-side read bound is 128 × 16 KiB / 50 µs ≈ 42 GB/s — far above a PCIe Gen4 x4 link (~7.9 GB/s), so the link, channel transfer rates, ECC throughput or firmware become the limit instead derived (numbers synthetic). The crucial engineering point: to keep 128 operations busy with 4 KiB random reads, the host must keep enough commands outstanding — a queue depth of 1 uses only one die at a time.

2.11 Flash Translation Layer (FTL)

The FTL is controller firmware (often with hardware assists) that makes NAND look like a rewritable block device. Its core is the logical-to-physical (L2P) map: for each logical unit (commonly 4 KiB), where its current copy lives (channel, die, plane, block, page, offset).

  • On write: data goes into an open (erased) page, the map entry is updated to the new location, the old location is marked invalid (stale).
  • On read: look up the map, read the physical page, run ECC, return data.
  • On deallocate/trim (NVMe Dataset Management with the Deallocate attribute): the map entry is removed, the old copy becomes invalid without new writes — making garbage collection cheaper.
DRAML2P ≈ (C / G) × E
  • DRAML2P — memory needed for a flat page-level map
  • C — capacity in bytes
  • G — mapping granularity (e.g. 4 KiB)
  • E — bytes per entry (e.g. 4)

For 4 TB at 4 KiB granularity with 4-byte entries: 4×1012 / 4096 × 4 ≈ 3.9 GB — the origin of the rule of thumb “about 1 GB of DRAM per 1 TB of flash” derived. DRAM-less SSDs cache part of the map in SRAM and/or use the NVMe Host Memory Buffer (HMB) feature, borrowing host DRAM over PCIe. Some high-capacity drives use larger indirection units (e.g. 16 KiB or more) to shrink the map — which then makes small random writes more expensive impl.

2.12 Garbage collection (GC)

As data is overwritten, blocks accumulate invalid pages. To reclaim space, GC picks a victim block, copies its still-valid pages to a new location (consuming NAND bandwidth and causing extra writes), then erases the victim. GC competes with host I/O; when free blocks run low, host writes must wait for GC — producing the famous SSD write cliff and read tail-latency spikes.

WAF = NAND bytes written / host bytes written
  • WAF — write amplification factor, ≥ 1 without compression
  • NAND bytes written — includes host data, GC relocation, metadata, refresh
  • host bytes written — bytes the host asked to write

A simplified steady-state model for greedy GC under uniformly random overwrite: if a victim block is on average a fraction u valid, reclaiming it to free (1−u) of a block costs u of a block in copies, so WAF ≈ 1/(1−u) derived conceptual. More spare space → emptier victims → lower u → lower WAF. Sequential writes invalidate whole blocks together, giving WAF ≈ 1.

2.13 Wear leveling

Each block survives a limited number of program/erase (P/E) cycles. Dynamic wear leveling steers new writes to the least-worn free blocks. Static wear leveling also moves cold (rarely changed) data off low-wear blocks so those blocks can share the burden — at the cost of extra writes. The goal is that all blocks wear out at about the same time rather than a hot few failing early. NVMe exposes the consequence, not the mechanism: the SMART Percentage Used estimate and Available Spare.

2.14 Over-provisioning (OP)

OP = (physical NAND capacity − user capacity) / user capacity
  • physical NAND capacity — raw flash available for data (excluding ECC spare area)
  • user capacity — capacity exposed to the host

Example: 512 GiB of raw NAND (549.8 GB) sold as 512 GB → OP ≈ 7.4%, the “free” OP from the GiB/GB difference. Enterprise drives often expose 3.84 TB from ~4.4 TB of NAND (higher OP, more endurance, steadier latency) impl. Hosts can add effective OP by leaving space unwritten and deallocated, or by creating smaller namespaces.

2.15 Endurance

TBW ≈ (C × PE) / WAF · DWPD = TBW / (C × 365 × Y)
  • TBW — terabytes written (host writes) the drive is rated for
  • C — user capacity in TB
  • PE — rated program/erase cycles of the NAND
  • WAF — expected write amplification for the rating workload
  • DWPD — drive writes per day over the warranty
  • Y — warranty years

Example: 3.84 TB, 1 DWPD, 5 years → TBW = 3.84 × 365 × 5 ≈ 7,008 TB ≈ 7 PB derived. Vendors rate endurance against specified workloads (for example JEDEC client/enterprise workloads); a different workload yields a different WAF and different real endurance impl.

2.16 Latency

Latency is the time from submission to completion of one I/O. For an NVMe 4 KiB random read it decomposes roughly as:

ComponentOrder of magnitudeVisible where
Application + kernel submission path1–5 µsperf, bpftrace
Doorbell, command fetch over PCIe~1 µsAnalyzer
Controller processing, FTL lookupa few µsNot visible (inferred)
NAND array read (tR) + channel transfer + ECC~40–100 µs TLC; less for SLC-class mediaNot visible (inferred)
Data DMA + CQE + interrupt~1–2 µs for 4 KiBAnalyzer
Interrupt handling + completion to app1–5 µsperf, bpftrace

All values are typical orders of magnitude impl. Writes often complete faster than reads because the controller acknowledges them once data is in a protected buffer — until the buffer fills. Tail latency (p99, p99.9, p99.99) matters more than the average in real systems: a read that lands on a die busy programming or erasing can wait milliseconds unless the controller supports program/erase suspend impl.

2.17 IOPS

IOPS — I/O operations per second — measures how many commands complete per second, usually for small random I/O (4 KiB). It depends on queue depth, parallelism and latency, linked by Little's law:

L = λ × W ⇒ IOPS = QD / latency
  • L — average number of I/Os in the system (outstanding = effective queue depth, QD)
  • λ — throughput in I/Os per second (IOPS)
  • W — average time each I/O spends in the system (latency, in seconds)

Example: QD 1, 80 µs latency → 12,500 IOPS. QD 32 at the same latency → 400,000 IOPS, if the device has the parallelism to keep latency flat. When parallelism saturates, latency rises instead of IOPS — the knee of the curve. Little's law holds for averages in steady state; it says nothing about tails. It is previewed here and used heavily in Part XXVIII.

2.18 Throughput

Throughput = IOPS × I/O size
  • Throughput — bytes per second (state decimal MB/s or binary MiB/s explicitly)
  • IOPS — completed operations per second
  • I/O size — bytes per operation

Examples: 1,000,000 IOPS × 4 KiB = 4.096 GB/s (3.81 GiB/s); 7 GB/s at 128 KiB = ~53,400 IOPS derived. Small I/O is usually IOPS-bound (controller, CPU, interrupt rate); large I/O is bandwidth-bound (PCIe link, NAND channels). A Gen4 x4 drive cannot exceed ~7.9 GB/s raw link bandwidth whatever its IOPS.

Engineering explanation — the whole SSD in one model

 host cmd ─▶ NVMe front end ─▶ FTL ─▶ scheduler ─▶ ch0: die0 die1 die2 die3
 (LBA, len)  (queues, DMA)    (L2P)  (per-die    ch1: die0 die1 die2 die3
                                       queues)    ...
                               ▲                  chN: die0 die1 die2 die3
                               └── GC / wear leveling / refresh compete for the same dies

Host commands and background work share dies. Everything the host sees as “latency variance” is the result of this shared scheduling, which is implementation-dependent and not specified by NVMe.

Storage media reality — what the protocol does not expose

📭 What the spec does not say

The NVMe protocol defines the host-visible contract: logical blocks, commands, status, log pages, features. It generally does not expose or mandate: where an LBA is physically placed in NAND; the FTL mapping scheme or granularity; the garbage-collection algorithm or when it runs; the wear-leveling policy; the size of the write cache or SLC cache; how read retries are performed. Some features let the host influence placement or observe aggregates (for example Zoned Namespaces, Flexible Data Placement, Endurance Group and SMART log pages, predictable-latency features) version, but the mechanisms remain the vendor's.

Host-visible protocol behaviourInternal flash behaviour (generally hidden)

SMART: Percentage Used, Available Spare, Data Units Read/Written, Media and Data Integrity ErrorsPer-block P/E counts, retry rates, ECC margins

🏭 Implementation-dependent

When you see a latency outlier in a trace, “the SSD was doing GC” is a hypothesis, not a finding. Support it with evidence: correlation with sustained writes, free-space level, deallocate history, vendor telemetry logs — or label it as uncertain.

Hardware view

Controller SoC with CPU cores, NVMe/PCIe front end, DMA, ECC engines, encryption, NAND channel controllers; DRAM (or HMB); NAND packages each holding several dies; power-loss-protection capacitors (enterprise); temperature sensors feeding thermal throttling. When temperature exceeds thresholds the controller slows itself — another non-protocol cause of performance changes, visible through SMART temperature fields and thermal-management features.

Specification view

NVMe Base 2.4 and NVM Command Set 1.3 define namespaces, logical block formats, the SMART / Health Information log page, Endurance Group information, and Dataset Management deallocate semantics version. Key well-established definitions you will use in this chapter's labs:

  • NSZE / NCAP / NUSE (Identify Namespace): namespace size, capacity and utilisation, all in logical blocks.
  • FLBAS selects the active LBA Format; each LBA format gives LBADS — the LBA data size as a power of two (9 → 512 B, 12 → 4096 B) — and the metadata size.
  • Data Units Read / Written (SMART log): reported in thousands of 512-byte units, i.e. a value of 1 = 1,000 × 512 bytes = 512,000 bytes, rounded up verified — confirm in your revision of the Base specification.

SPECIFICATION BASELINE: NVMe Base Specification 2.4; NVM Command Set 1.3. OLDER VERSIONS THAT MAY DIFFER: in NVMe 1.x the NVM command set and Identify Namespace fields were in the single base document; field names are stable but locations moved in the 2.0 refactor version.

Protocol view

From the link's perspective a 4 KiB read and a 4 KiB read that waited 5 ms behind an erase look identical except for the gap between command fetch and the first data write. The protocol transports the consequences of media behaviour as time. That is why latency histograms are the main window into the media.

Code — Little's law and WAF calculators

#!/usr/bin/env python3
def iops_from_littles_law(qd, latency_us):          # L = lambda * W
    return qd / (latency_us * 1e-6)

def throughput(iops, io_bytes):                    # returns (GB/s, GiB/s)
    b = iops * io_bytes
    return b / 1e9, b / 2**30

def waf_greedy(valid_fraction):                    # conceptual steady-state model
    return 1.0 / (1.0 - valid_fraction)

def dwpd(tbw_tb, cap_tb, years):
    return tbw_tb / (cap_tb * 365 * years)

print(iops_from_littles_law(32, 80))               # 400000.0
print(throughput(1_000_000, 4096))                 # (4.096, 3.81...)
print(waf_greedy(0.75))                            # 4.0
print(round(dwpd(7008, 3.84, 5), 2))               # 1.0

Worked example — a capacity, from identify data to bytes

Synthetic Identify Namespace values: NSZE = 0x1BF1F72B0, FLBAS selects LBA format 1, LBAF1: LBADS = 12, MS = 0. synthetic

  1. NSZE = 0x1BF1F72B0 = 7,501,476,528 logical blocks.
  2. Logical block size = 212 = 4,096 bytes.
  3. Capacity = 7,501,476,528 × 4,096 = 30,726,047,858,688 bytes.
  4. In decimal units: ≈ 30.73 TB. In binary units: ÷ 240 ≈ 27.94 TiB.
  5. In Linux /sys/block/.../size units (512 B): 7,501,476,528 × 8 = 60,011,812,224.

Had the same namespace been formatted with 512-byte blocks (LBADS = 9), NSZE would be 8× larger for the same capacity. Always multiply by the active format's size.

Common mistakes

  • Assuming an SSD overwrites data in place.
  • Treating SSD latency as a constant; ignoring tails.
  • Measuring a fresh-out-of-box drive and calling it steady state (no GC yet).
  • Comparing MB/s numbers computed with different units.
  • Reading Data Units Written as bytes or as 512-byte sectors (it is thousands of 512-byte units).
  • Blaming PCIe for latency spikes with no PCIe errors and no protocol anomaly.
  • Believing trim/deallocate guarantees the data is erased (it does not, by itself; sanitize does — Part XVIII).

Debugging connection

When performance changes without errors, ask in order: Did the workload change (size, mix, QD)? Did media state change (free space, preconditioning, SLC-cache exhaustion, temperature/throttling)? Did the host change (CPU, interrupts, NUMA)? Only then: did the link change (speed/width downgrade, retraining, errors)? The first two are invisible to the protocol and are the most common causes.

💡 Senior insight

Always precondition before measuring: fill the drive (sequentially, then randomly for random workloads) until performance stabilises, and report steady-state numbers with percentiles. A benchmark on an empty SSD measures the FTL's best case, not the product.

Labs

🧪 Lab 2.1 — Capacity and LBA lab SAFE

Objective: compute capacity exactly from Identify data and reconcile it with every tool. Setup: Linux, nvme-cli, any NVMe namespace (read-only commands only).

Steps:

  1. sudo nvme id-ns /dev/nvme0n1 -H — record NSZE, NCAP, NUSE, FLBAS and the LBA format marked “in use” (LBADS, MS).
  2. Compute bytes = NSZE × 2LBADS. Express in B, KB, KiB, MB, MiB, GB, GiB, TB, TiB.
  3. Compare with lsblk -b, /sys/block/nvme0n1/size × 512, and nvme list.
  4. Record tnvmcap from nvme id-ctrl (total NVM capacity, in bytes) if reported, and compare.

Questions: (1) Do all tools agree once units are normalised? (2) What does NUSE < NSZE mean? (3) Why might tnvmcap exceed the namespace size?

Solution

(1) They should agree exactly in bytes; disagreements are unit errors (decimal vs binary, 512 B sectors vs logical blocks). (2) Fewer blocks are currently allocated than the namespace size — e.g. after deallocate, or thin provisioning; NUSE semantics depend on features supported version. (3) Capacity may be reserved, unallocated to namespaces, or the controller may support multiple namespaces; tnvmcap counts the NVM capacity of the controller/subsystem as defined in the spec, not just this namespace.

Extension: list all supported LBA formats and their “relative performance” hints; explain why a 4 KiB format may perform better (no read-modify-write for 4 KiB-aligned I/O).

🧪 Lab 2.2 — Data unit lab SAFE

Objective: interpret SMART counters using their defined units. Setup: sudo nvme smart-log /dev/nvme0 and, separately, sudo nvme smart-log /dev/nvme0 -o json.

Steps: record data_units_read, data_units_written, host_read_commands, host_write_commands, percent_used, avail_spare, temperature. Note whether the human-readable output already converts units (nvme-cli versions differ impl).

Compute: bytes written = data_units_written × 512,000. Average write size = bytes written / host_write_commands. Daily write rate = bytes written / power-on days.

Questions: (1) What is the TB written? (2) What is the average write size and what does it tell you about the workload? (3) Is the drive on track for its rated DWPD?

Solution

Example (synthetic): data_units_written = 12,345,678 → 12,345,678 × 512,000 = 6.32 × 1012 B ≈ 6.32 TB. With 98,000,000 write commands, the average is ≈ 64.5 KB — a mixed workload. Dividing TB written by capacity and days gives observed DWPD; compare with the vendor rating. Note: “data units” count data transferred by the host, not NAND writes; WAF cannot be computed from the SMART log alone. Some devices expose media-written counters in the Endurance Group Information log page or in vendor-specific logs version impl.

Extension: take two readings an hour apart during a known fio write job; check that the delta matches the bytes fio reports (allowing for the rounding rule).

  fio --name=qd$qd --filename=/dev/nvme1n1 --readonly --direct=1 --ioengine=io_uring \
      --rw=randread --bs=4k --iodepth=$qd --runtime=20 --time_based --group_reporting \
      --output-format=terse | awk -F';' '{print "'$qd'", $8, $40}'   # field numbers vary by fio version
done
⚠️ Warning

Never point fio write workloads at a device holding data. --readonly protects against typos. Terse field positions vary by fio version — verify with --output-format=json if unsure.

Questions: (1) For each QD, does IOPS ≈ QD / mean latency? (2) Where is the knee? (3) What happens to p99 past the knee?

Solution

Little's law should hold within a few percent for steady runs (deviations come from host overhead counted differently). IOPS grows almost linearly at low QD (parallelism unused), then flattens; past the knee, mean and p99 latency grow roughly proportionally to QD because requests queue inside the device. The knee position reveals effective internal parallelism and controller limits impl.

Extension: repeat with --numjobs=4 --iodepth=qd/4 to spread load over more submission queues and compare.

🧪 Lab 2.4 — Write amplification thought experiment SAFE

A drive has 1,000 blocks; user data occupies the equivalent of 800 blocks; the rest is OP. Under uniformly random 4 KiB overwrites with greedy GC, assume victim blocks are on average 75% valid. (1) Estimate WAF. (2) If the NAND is rated at 3,000 P/E cycles and capacity is 1 TB, estimate host TBW. (3) How would sequential writes change the answer?

Solution

(1) WAF ≈ 1/(1−0.75) = 4. (2) Raw NAND writes available ≈ 1.25 TB × 3,000 = 3,750 TB of NAND writes (using total physical capacity 1,000 blocks for 800 blocks of user data → physical ≈ 1.25 TB); host TBW ≈ 3,750 / 4 ≈ 940 TB. (3) Sequential overwrite invalidates whole blocks → victims nearly empty → WAF ≈ 1, host TBW ≈ 3,750 TB. derived conceptual model.

Why NVMe was needed

Put the chapter together:

  1. NAND SSD performance comes from parallelism across channels, dies and planes — dozens to hundreds of concurrent operations.
  2. Exploiting it requires many outstanding commands (Little's law) — far more than one 32-deep queue comfortably supplies, and supplied from many CPU cores at once.
  3. SSD latency is tens of microseconds, so every microsecond of host-interface overhead (HBA firmware, register reads, locks) is now a large fraction of the total.
  4. Bandwidth outgrew SATA's 600 MB/s and SAS's per-port rates; PCIe lanes, already wired to the CPU, offered gigabytes per second.

The next chapter tells the story of how the industry got from AHCI to NVMe — and quantifies each of these points.

Quiz — Chapter 2

  1. Average rotational latency of a 15,000 RPM drive?

    Answer

    0.5 × 60/15000 = 2 ms.

  2. Smallest unit NAND can erase? program?

    Answer

    Erase: block. Program: page.

  3. Why can't an SSD overwrite a page in place?

    Answer

    NAND pages must be erased before reprogramming, and erase works only on whole blocks.

  4. Define WAF and give a value for purely sequential writes.

    Answer

    NAND bytes written / host bytes written; ≈ 1 for sequential.

  5. A drive does 600,000 IOPS of 4 KiB reads. Throughput in GB/s and GiB/s?

    Answer

    2.4576 GB/s; 2.29 GiB/s.

  6. Mean latency 100 µs at QD 16. Predicted IOPS?

    Answer

    160,000.

  7. Data Units Written = 2,000,000. Bytes?

    Answer

    2,000,000 × 512,000 = 1.024 × 1012 bytes ≈ 1.02 TB.

  8. NSZE = 1,000,000 with LBADS = 9. Capacity?

    Answer

    512,000,000 bytes (512 MB, ≈ 488.3 MiB).

  9. What is a NAND die and why does it matter for performance?

    Answer

    The independently operating unit; interleaving operations across dies provides SSD parallelism.

  10. Name two things NVMe does not expose about NAND.

    Answer

    Any two of: physical placement, FTL map, GC algorithm/timing, wear-leveling policy, cache sizes.

  11. What is NCQ's maximum queue depth?

    Answer

    32 commands.

  12. Why does a longer warranty at the same TBW reduce DWPD?

    Answer

    The same total writes are spread over more days.

Interview questions — Chapter 2

  1. Beginner Why are SSDs faster than HDDs for random I/O?
    Model answer

    No mechanical seek or rotation; flash reads take tens of µs and many dies work in parallel.

  2. Beginner What is TRIM/deallocate for?
    Model answer

    Telling the SSD that LBAs no longer hold useful data so GC need not copy them, reducing WAF.

  3. Intermediate Explain the SSD write cliff.
    Model answer

    When free blocks/SLC cache are exhausted, writes must wait for GC and native TLC/QLC programming, so throughput drops and latency rises sharply.

  4. Intermediate How does over-provisioning improve performance and endurance?
    Model answer

    More spare space means GC victims hold fewer valid pages, lowering WAF, which reduces both background work and NAND wear.

  5. Advanced Use Little's law to explain why QD 1 latency benchmarks do not predict QD 32 throughput.
    Model answer

    At QD 1 only one die works; IOPS = 1/latency. Higher QD exploits parallelism until internal resources saturate; the relation depends on how latency changes with load.

  6. Advanced How would you estimate an SSD's internal parallelism from the outside?
    Model answer

    Sweep QD for random reads; IOPS × latency gives the effective concurrency at the knee, an estimate of usable parallel units (with caveats about controller limits).

  7. Senior A customer reports p99.9 read latency spikes every few minutes with no errors. Approach?
    Model answer

    Correlate with write activity, free space, temperature and power-state transitions; check SMART and vendor telemetry; reproduce with controlled preconditioning; consider host causes (interrupt affinity, CPU frequency); only then inspect PCIe for retraining/errors. Report GC as a hypothesis with evidence.

  8. Senior How do you test for endurance-related behaviour changes without waiting years?
    Model answer

    Accelerated write workloads on test drives, monitoring percent used, spare, error counters and latency drift; vendor-assisted pre-aged samples; retention bake tests per vendor methodology impl.

Chapter summary

  • HDD performance is mechanical; SSD performance is parallel flash managed by firmware.
  • NAND programs pages and erases blocks; the FTL hides this with an L2P map, GC and wear leveling, at the cost of write amplification.
  • OP, WAF and P/E cycles determine endurance; TBW and DWPD express it.
  • IOPS, throughput and latency are linked: Throughput = IOPS × size; IOPS = QD / latency.
  • Units matter: logical blocks vs 512-byte sectors; KB vs KiB; SMART data units of 512,000 bytes.
  • The protocol exposes time and aggregates, not media mechanisms.
