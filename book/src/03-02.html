18 Configuration Space

📘 Specification baseline

DOCUMENT: PCI Express Base Specification (PCI-SIG); PCI Code and ID Assignment Specification (class codes, capability IDs); NVMe over PCIe Transport Specification (how an NVMe controller presents itself as a PCIe function). REVISION: header layouts are stable since PCI 2.x/PCIe 1.0; extended capabilities keep being added (e.g. physical-layer capabilities for 16/32/64 GT/s, Data Object Exchange, Integrity and Data Encryption) version. STATUS: current baseline for NVMe: NVMe over PCIe Transport Revision 1.4 within the NVMe 2.4 family (confirm on nvmexpress.org). OLDER VERSIONS THAT MAY DIFFER: before NVMe 2.0, PCIe register requirements lived inside the single NVMe specification; since 2.0 they moved to the PCIe Transport specification. SOURCE: PCI-SIG specifications; nvmexpress.org; Linux include/uapi/linux/pci_regs.h (openly readable register definitions).

18.1 Why this chapter exists

Configuration space is the device's identity card, control panel and feature catalogue in one 4 KiB structure. Every question you ask about a PCIe NVMe SSD — "what is it?", "is it allowed to DMA?", "what link speed did it negotiate?", "which interrupt vectors does it have?", "did it log an error?" — is answered by a field in configuration space. The master curriculum asks for something specific here: give hex dumps and teach the learner to decode them manually. By the end of this chapter you will decode a 256-byte dump by hand, walk a capability list, and cross-check your decoding against lspci -vvv.

18.2 Learning objectives

  • Beginner: name the fields of the common header (Vendor ID, Device ID, Command, Status, Revision ID, Class Code, Header Type) and say what each one is for.
  • Intermediate: decode a Type 0 and a Type 1 header from a raw little-endian hex dump.
  • Advanced: walk both the standard capability list (from offset 34h) and the extended capability list (from offset 100h), decoding PCI Express, MSI-X, Power Management and AER structures.
  • Senior: predict the consequences of wrong Command/Device Control settings (MPS/MRRS mismatch, Bus Master off, INTx disable with MSI-X off) and design validation checks for them.
  • Trace analysis: interpret CfgRd/CfgWr TLPs by register offset and byte enables.
  • Debugging: use Status and AER registers as first-line evidence for link and transaction errors.
  • Validation: verify that a device's configuration space conforms to required fields for an NVMe controller (class code, BAR0 type, MSI-X presence).

18.3 Prerequisites

Chapter 17 (BDF, ECAM, Type 0/1 configuration requests). Little-endian byte order: in a dump, the byte at the lowest address is the least significant byte of a multi-byte field. Hexadecimal and bit numbering (bit 0 = least significant).

18.4 Story and analogy

🧒 Kid analogy

Every device carries a passport. The first page always looks the same for everyone: country (Vendor ID), name (Device ID), what kind of traveller it is (Class Code: "I am a storage device that speaks NVMe"), and a few switches the border guard can flip ("you may enter the country" = Memory Space Enable, "you may drive your own truck" = Bus Master Enable). After the first page come optional stamp pages — each stamp says "I can do power saving", "I can send interrupts as messages", "I keep an error diary". Each stamp says where the next stamp is, so you read them as a chain.

🌍 Real-world analogy

A server's BMC sensor table: a fixed header with identity fields, followed by a linked list of optional records whose type you check before interpreting the content. You never assume record 3 is "temperature" — you check its type ID.

🧩 Where the analogy breaks

A passport is read-only. Configuration space is not: many fields are writable control bits, some are "write 1 to clear" status bits, and some (BARs) behave strangely when written (they ignore address bits below their size). Also, the order of stamps (capabilities) is chosen by the device designer — two devices with identical features can list them in different orders and at different offsets.

⚠️ Why BME matters for safety

Bus Master Enable is the gate that allows the device to originate DMA. Until BME = 1, an NVMe controller cannot fetch submission queue entries, read write-data, write read-data, post completion entries, or send MSI-X interrupt messages (which are memory writes). Clearing BME on a running controller stops all of that abruptly — Linux clears it on shutdown and in some error paths precisely to stop DMA. verified

RW1C means "read; write 1 to clear". Writing the value you just read back to Status clears every set error bit — a common debugging technique, but also a common way to destroy evidence before you recorded it. Record first, clear second.

18.6.3 Class Code: how the NVMe driver finds the device

The 24-bit Class Code is three bytes: Base Class at 0Bh, Sub-Class at 0Ah, Programming Interface at 09h verified. For an NVMe I/O controller on PCIe:

Byte 0Bh — Base ClassByte 0Ah — Sub-ClassByte 09h — Prog-IF
01h — Mass storage controller08h — Non-Volatile Memory controller02h — NVM Express

Linux's NVMe PCI driver includes a class match for PCI_CLASS_STORAGE_EXPRESS (= 010802h), so any compliant NVMe device binds to it even if its Vendor/Device IDs are unknown to the driver verified. Prog-IF 01h under the same sub-class corresponds to the older NVMHCI interface. Other Prog-IF values may be defined in newer PCI Code and ID Assignment revisions for other NVMe controller types — check that document rather than assuming version.

  • Memory Base/Limit (20h/22h): a 1 MiB-granular, 32-bit, non-prefetchable window. Bits 15:4 of each 16-bit register hold address bits 31:20. Memory requests whose address falls inside [Base, Limit+FFFFFh] are forwarded downstream. verified
  • Prefetchable Base/Limit (24h/26h plus upper 32 bits at 28h/2Ch): the 64-bit capable window where 64-bit prefetchable BARs of children are placed.
  • Bridge Control (3Eh): includes Secondary Bus Reset (bit 6) — writing it resets everything below the bridge (a "hot reset" of the link). Never toggle on a production system.
💡 Senior insight: NVMe BAR0 lives in the non-prefetchable window

Because NVMe register BARs are normally non-prefetchable (reads have side effects — e.g. reading a register must return current state, not a cached guess) and the classic non-prefetchable bridge window is only 32 bits wide, NVMe BAR0 is usually placed below 4 GiB even when it is a 64-bit BAR. A host with dozens of NVMe drives and small 32-bit MMIO space can run out of non-prefetchable window space. Firmware "Above 4G decoding" settings and newer approaches change what is possible impl. When dmesg says a BAR cannot be assigned, look at the bridge windows before blaming the device.

18.8 Capability lists

Both lists are singly linked. A standard capability starts with an 8-bit Capability ID and an 8-bit Next Pointer (00h ends the list). An extended capability starts with a 32-bit header: bits 15:0 Extended Capability ID, bits 19:16 Capability Version, bits 31:20 Next Capability Offset (000h ends the list). The extended list always starts at 100h; if 100h reads 0, there are no extended capabilities (and FFFFFFFFh there means the extended space is not accessible, e.g. no ECAM) verified.

Link speed encoding in Current Link Speed / Max Link Speed: the value is an index into the Supported Link Speeds Vector in Link Capabilities 2; in practice 1 = 2.5 GT/s, 2 = 5.0, 3 = 8.0, 4 = 16.0, 5 = 32.0, 6 = 64.0 GT/s verified.

Each MSI-X table entry is 16 bytes in memory space: Message Address (low 32), Message Upper Address, Message Data, Vector Control (bit 0 = Mask) verified. An interrupt is literally a posted Memory Write TLP, sent by the device to the address with the data from the entry. For NVMe this means each completion queue can be bound to its own vector (the Interrupt Vector field of Create I/O Completion Queue), and per-CPU queues can interrupt per-CPU vectors. The table is placed in a BAR — often BAR0 above the NVMe register and doorbell area, or a separate BAR impl.

18.8.3 Power Management Capability (ID 01h)

PMC (+02h) advertises supported D-states and PME support; PMCSR (+04h) holds PowerState (bits 1:0: 00b D0, 01b D1, 10b D2, 11b D3hot) and No_Soft_Reset (bit 3: if 1, D3hot→D0 does not reset the function's state) verified. These are PCI function power states, not NVMe power states (which are set with the Power Management feature via Set Features). Both exist, stack, and are frequently confused.

18.8.5 SR-IOV (extended ID 0010h) in one paragraph

Single Root I/O Virtualization lets one Physical Function (PF) expose many Virtual Functions (VFs), each a lightweight PCIe function with its own BDF (via ARI and the First VF Offset / VF Stride fields), its own BARs (described collectively by VF BAR registers in the SR-IOV capability) and its own MSI-X. For NVMe, each VF is typically an NVMe controller that a hypervisor assigns to a VM; the NVMe specification's virtualization enhancements govern how controller resources (queues, interrupts) are shared between primary and secondary controllers version. Key fields: Total VFs, Num VFs, VF Enable, First VF Offset, VF Stride, VF Device ID.

18.9.1 Manual decode, line by line

  1. 00h: bytes 36 1b → Vendor ID 1B36h (little-endian: low byte first). 10 00 → Device ID 0010h.
  2. 04h: 06 04 → Command 0406h = 0000_0100_0000_0110b: bit 1 MSE=1, bit 2 BME=1, bit 10 Interrupt Disable=1. 10 00 → Status 0010h: bit 4 Capabilities List=1, no error bits.
  3. 08h: 02 Revision 02h; 02 08 01 → Prog-IF 02h, Sub-Class 08h, Base Class 01h → Class Code 010802h = NVM Express.
  4. 0Ch: Header Type at 0Eh = 00h → Type 0, single-function.
  5. 10h: 04 00 a0 fe → BAR0 = FEA00004h. Bit 0 = 0 (memory), bits 2:1 = 10b (64-bit), bit 3 = 0 (non-prefetchable). Because it is 64-bit, BAR1 (14h) = 00000000h is the upper half. Address = 00000000_FEA00000h. The size is not visible here — sizing (Chapter 19) is required.
  6. 2Ch: Subsystem Vendor ID 1AF4h, Subsystem ID 1100h.
  7. 34h: Capabilities Pointer = 40h.
  8. 3Ch: Interrupt Line 0Bh (software scratch value), Interrupt Pin 01h = INTA#.
  9. 40h: 01 50 → Cap ID 01h (Power Management), next 50h. PMC = 0003h (version 3). PMCSR at 44h = 0008h: PowerState 00b = D0, No_Soft_Reset = 1.
  10. 50h: 11 60 → Cap ID 11h (MSI-X), next 60h. Message Control = 803Fh: bit 15 Enable = 1, bit 14 Function Mask = 0, Table Size = 3Fh → 64 vectors. Table = 00002000h → BIR 0, offset 2000h. PBA = 00003000h → BIR 0, offset 3000h.
  11. 60h: 10 00 → Cap ID 10h (PCI Express), next 00h (end of list). PCIe Capabilities register 0002h → version 2, Device/Port Type 0000b = PCI Express Endpoint.
  12. 64h: Device Capabilities 10008002h: MPS supported = 010b → 512 B; bit 15 Role-Based Error Reporting = 1; bit 28 FLR capable = 1.
  13. 68h: Device Control 283Fh = 0010_1000_0011_1111b: bits 3:0 = 1111b (all error reporting enabled), bit 4 Relaxed Ordering = 1, bits 7:5 = 001b → MPS 256 B, bit 11 No Snoop = 1, bits 14:12 = 010b → MRRS 512 B. Device Status at 6Ah = 0000h: no errors detected.
  14. 6Ch: Link Capabilities 00000C44h: bits 3:0 = 4 → max 16.0 GT/s, bits 9:4 = 04h → x4, bits 11:10 = 11b → L0s and L1 ASPM supported.
  15. 70h: Link Control 0040h: Common Clock Configuration = 1, ASPM Control = 00b (disabled). Link Status 1044h: Current Link Speed 4 (16.0 GT/s), Negotiated Width 4 (x4), bit 12 Slot Clock Configuration = 1, Link Training = 0.
  16. 100h: 01 00 02 00 → 00020001h: Extended Cap ID 0001h (AER), version 2, next 000h (end).

Now confirm with the executable decoder (it parses only the text above):

#!/usr/bin/env python3
"""Decode a SYNTHETIC PCIe Type 0 configuration-space dump and walk its capability lists.
Pure parsing: it reads only the text below, never real hardware."""
import struct

DUMP = """
00: 36 1b 10 00 06 04 10 00 02 02 08 01 00 00 00 00
10: 04 00 a0 fe 00 00 00 00 00 00 00 00 00 00 00 00
20: 00 00 00 00 00 00 00 00 00 00 00 00 f4 1a 00 11
30: 00 00 00 00 40 00 00 00 00 00 00 00 0b 01 00 00
40: 01 50 03 00 08 00 00 00 00 00 00 00 00 00 00 00
50: 11 60 3f 80 00 20 00 00 00 30 00 00 00 00 00 00
60: 10 00 02 00 02 80 00 10 3f 28 00 00 44 0c 00 00
70: 40 00 44 10 00 00 00 00 00 00 00 00 00 00 00 00
100: 01 00 02 00 00 00 00 00 00 00 00 00 00 00 00 00
"""

cfg = bytearray(4096)
for line in DUMP.strip().splitlines():
    off, data = line.split(":")
    for i, byte in enumerate(data.split()):
        cfg[int(off, 16) + i] = int(byte, 16)

u8 = lambda o: cfg[o]
u16 = lambda o: struct.unpack_from("<H", cfg, o)[0]
u32 = lambda o: struct.unpack_from("<I", cfg, o)[0]
bit = lambda v, n: (v >> n) & 1
field = lambda v, hi, lo: (v >> lo) & ((1 << (hi - lo + 1)) - 1)

print(f"Vendor ID {u16(0x00):04x}h  Device ID {u16(0x02):04x}h")
cmd, sts = u16(0x04), u16(0x06)
print(f"Command {cmd:04x}h: IO={bit(cmd,0)} MEM={bit(cmd,1)} BusMaster={bit(cmd,2)} "
      f"SERR={bit(cmd,8)} INTxDisable={bit(cmd,10)}")
print(f"Status  {sts:04x}h: CapList={bit(sts,4)} RxMasterAbort={bit(sts,13)} DetParity={bit(sts,15)}")
cc = (u8(0x0B) << 16) | (u8(0x0A) << 8) | u8(0x09)
print(f"Revision {u8(0x08):02x}h  Class Code {cc:06x}h"
      + ("  -> mass storage / NVM / NVM Express" if cc == 0x010802 else ""))
ht = u8(0x0E)
print(f"Header Type {ht:02x}h: layout={ht & 0x7f} multifunction={bit(ht,7)}")

# BARs (Type 0 has six dword BAR slots at 10h..24h)
i = 0
while i < 6:
    off = 0x10 + 4 * i
    v = u32(off)
    if v == 0:
        i += 1
        continue
    if v & 1:
        print(f"BAR{i}: I/O at {v & ~0x3:#x}")
        i += 1
        continue
    kind, pref = field(v, 2, 1), bit(v, 3)
    if kind == 0b10:   # 64-bit: next BAR slot holds the upper dword
        addr = ((u32(off + 4) << 32) | (v & ~0xF)) & 0xFFFF_FFFF_FFFF_FFFF
        print(f"BAR{i}/{i+1}: 64-bit memory at {addr:#x} prefetchable={pref}")
        i += 2
    else:
        print(f"BAR{i}: 32-bit memory at {v & ~0xF:#x} prefetchable={pref}")
        i += 1

18.10 Procedure: reading any register correctly

The master curriculum's register-reading discipline applies to configuration registers as much as to NVMe registers:

  1. Locate the register (which capability, which offset — found by walking the list, never by hard-coding offsets that vary by device).
  2. Identify the width (8/16/32 bits) and read with a matching access size where side effects could matter.
  3. Identify the reset value (from the specification) to know what "untouched" looks like.
  4. Decode the fields with the bit ranges from the specification.
  5. Classify access (RO, RW, RW1C, RsvdP, RsvdZ, HwInit, ROS/RWS sticky) only when verified in the specification.
  6. Identify side effects (e.g. writing Initiate FLR resets the function; writing 1s to RW1C clears evidence).
  7. Identify sequencing rules (e.g. MSE off during BAR sizing; MSI-X table programmed before Enable).
  8. Identify related registers (Device Status ↔ AER status; Link Status ↔ Link Control 2 target speed).
  9. Identify the software owner (firmware? PCI core? driver?) to know who might change it behind your back.
  10. Identify hardware behaviour (what the device does when the field changes).
  11. Identify trace implications (which TLPs appear when this register is accessed or changes behaviour).
📘 Reserved fields

"RsvdP" (reserved and preserved) bits must be written back with the value read; "RsvdZ" bits must be written as zero. Software doing read-modify-write must respect these. Never assign meaning to reserved bits even if a particular device returns non-zero there.

18.12 Protocol view: what configuration TLPs carry

A configuration request header carries the Requester ID, a Tag, the target Bus/Device/Function, the Extended Register Number (4 bits) and Register Number (6 bits) forming a 10-bit DWORD index (so offset = index × 4), and First DW Byte Enables selecting which bytes of the DWORD are accessed. Length is always 1 DW verified. A 16-bit read of the Command register at 04h is therefore a 1-DW CfgRd to register index 1 with byte enables 0011b; a read of Status (06h) uses byte enables 1100b.

⚠️ setpci writes

setpci with =value writes configuration space directly, bypassing the kernel's view. Writing the Command register can disable a live NVMe device (the root file system disappears); writing Bridge Control can reset everything below a port; writing Device Control can create MPS mismatches that cause fatal errors. Treat any setpci … = as an EXPERT LAB action on disposable hardware.

18.14 Code: reading configuration space safely from sysfs

#!/usr/bin/env python3
# READ-ONLY: reads /sys/bus/pci/devices/<bdf>/config. Root is needed to see past 64 bytes.
# Never open this file for writing on a live system.
import struct, sys
bdf = sys.argv[1] if len(sys.argv) > 1 else "0000:01:00.0"
with open(f"/sys/bus/pci/devices/{bdf}/config", "rb") as f:
    cfg = f.read()
vid, did = struct.unpack_from("<HH", cfg, 0)
cls = cfg[0x0B] << 16 | cfg[0x0A] << 8 | cfg[0x09]
print(f"{bdf}: {vid:04x}:{did:04x} class {cls:06x} config bytes visible: {len(cfg)}")
if cls == 0x010802:
    print("This function is an NVM Express controller")

18.15 Worked example: decoding a Type 1 header fragment

Synthetic bytes at offsets 18h–2Fh of Root Port 00:02.0:

18: 00 02 06 00 f0 00 00 00 a0 fe b0 fe f1 ff 01 00
28: 00 00 00 00 00 00 00 00
  • 18h = 00, 19h = 02, 1Ah = 06 → Primary 0, Secondary 2, Subordinate 6.
  • 1Ch = F0h, 1Dh = 00h → I/O Base > I/O Limit → I/O window disabled.
  • 20h = FEA0h → Memory Base bits 15:4 = FEAh → base FEA0_0000h; 22h = FEB0h → limit FEB0_0000h + F_FFFFh = FEBF_FFFFh. Non-prefetchable window FEA0_0000h–FEBF_FFFFh (2 MiB).
  • 24h = FFF1h, 26h = 0001h → Prefetchable Base (FFFh<<20) > Limit (000h<<20) → prefetchable window disabled. The low nibble 1h of both means "64-bit capable window".

Consequence: all downstream NVMe BAR0s must fit inside FEA0_0000h–FEBF_FFFFh. The SSD in 18.9 with BAR0 at FEA0_0000h, 16 KiB, fits. derived

18.16 Common mistakes

  • Looking for CC or CSTS in configuration space. They are in BAR0 memory space.
  • Hard-coding the offset of the PCI Express capability (e.g. "it's always at 70h"). Walk the list.
  • Reading a 64-bit BAR as two independent 32-bit BARs.
  • Forgetting little-endian order when reading a dump by eye.
  • Clearing RW1C status bits before recording them.
  • Confusing PCI D-states (PMCSR) with NVMe power states (Set Features), or PCIe Device Serial Number with the NVMe serial number.
  • Assuming Revision ID is the NVMe version (it is not; VS in BAR0 is).

🧪 Lab 18.1 — Decode a dump by hand, then verify SAFE

Objective: decode your own NVMe device's first 256 bytes by hand. Setup: sudo lspci -s <bdf> -xxx > dump.txt. Expected reasoning

MPS is normally lower than or equal to the supported maximum because the whole path must agree. lspci output headers like "00:" use the same offset convention.

🧪 Lab 18.2 — Compare an emulated NVMe with a real one SAFE

🧪 Lab 18.3 — Watch AER counters during a stress run CAUTION

Procedure: record lspci -vvv AER lines for the SSD and its Root Port; run a read-only fio workload against a scratch namespace; record again; compare. Expected reasoning

Receiver Errors/Bad TLPs are logged by the receiver: errors at the Root Port indicate problems on the device→host direction; errors at the SSD indicate host→device. A few correctable errors may be tolerable; a growing rate is a signal-integrity investigation.

🧪 Lab 18.4 — Senior forensic: Status = 2010h SAFE

Given synthetic trace 18.D, write the investigation plan with checkpoints and the evidence that would raise or lower your confidence that an IOMMU-unmapped DMA caused the bit.

Model answer

Record full state (Status, AER UESta at Root Port and device, dmesg IOMMU faults). Clear the RW1C bit. Reproduce the workload with IOMMU fault reporting visible. If the bit re-appears together with an IOMMU fault naming 01:00.0 and an address, confidence is high that a DMA to an unmapped IOVA occurred; then correlate the IOVA with the driver's mapping lifetime (Chapter 20). If the bit re-appears without IOMMU faults, consider a request to an address outside any host bridge window (UR from the Root Complex). If it never re-appears, the original event was probably during boot (e.g. firmware probing).

Quiz

  1. Where are the NVMe controller registers: in configuration space or memory space?

    Answer

    Memory space, behind BAR0 (MMIO). Configuration space only describes and controls the PCIe function.

  2. BAR0 reads 0000000Ch. What does it tell you?

    Answer

    Memory BAR (bit 0 = 0), 64-bit (bits 2:1 = 10b), prefetchable (bit 3 = 1), address not yet assigned (or assigned at 0 — unassigned in practice).

  3. Message Control = 001Fh in MSI-X. How many vectors, and is it enabled?

    Answer

    Table Size 1Fh → 32 vectors; Enable (bit 15) = 0 → not enabled.

  4. What does the extended capability header 14810001h mean?

    Answer

    ID 0001h (AER), version 1 (bits 19:16 = 1), next offset 148h (bits 31:20 = 148h).

  5. Why must you record Status before writing it back?

    Answer

    Error bits are RW1C; writing back the read value clears every set bit, erasing evidence.

Interview questions

  1. Beginner What is class code 010802h?
    Model answer

    Mass storage / Non-Volatile Memory controller / NVM Express — the class by which OSes bind a generic NVMe driver.

  2. Beginner Name three fields every PCI function has at the same offsets.
    Model answer

    Vendor ID (00h), Device ID (02h), Command (04h), Status (06h), Class Code (09h–0Bh), Header Type (0Eh).

  3. Intermediate How do you find the PCI Express capability?
    Model answer

    Check Status bit 4, read the Capabilities Pointer at 34h, follow Next pointers until Cap ID 10h, guarding against loops and malformed pointers.

  4. Intermediate What is the difference between MPS and MRRS?
    Model answer

    MPS bounds the payload of TLPs carrying data (writes and completions); MRRS bounds how much a single read request may ask for. MPS must be consistent along a path; MRRS is a per-requester choice affecting fairness and efficiency.

  5. Advanced What does the AER Header Log give you on a Completion Timeout?
    Model answer

    If logged for that error, the header of the request that timed out: address, length, tag, requester — letting you correlate with driver activity (e.g. which queue or PRP list fetch). Whether it is logged is error- and implementation-dependent; check the spec and device.

  6. Senior Design a configuration-space conformance check for an NVMe SSD.
    Model answer

    Class code 010802h; BAR0 memory, 64-bit, non-prefetchable as required by the transport spec (verify wording); capability list well-formed (no loops, all pointers DW-aligned, within range); PCI Express capability with Endpoint type; MSI-X present with table/PBA inside implemented BARs and non-overlapping with NVMe registers/doorbells; PM capability; AER present if claimed; FLR behaviour matches capability; all RW1C bits clear after reset; MPS/MRRS defaults within spec. Run across cold/warm/hot reset and after FLR.

18.20 Summary, further reading and next

Configuration space = 64-byte header + standard capability list (from 34h) + extended capability list (from 100h). For NVMe the essentials are: Class Code 010802h, Command MSE/BME, BAR0 (64-bit memory), MSI-X capability, PCI Express capability (MPS, MRRS, link), and AER. Decode by walking, not by hard-coded offsets, and preserve evidence before clearing RW1C bits.
