PART XXIX

Validation Engineering

Everything you have learned so far — enumeration, registers, queues, doorbells, Transaction Layer Packets, completions, interrupts, power and errors — becomes useful to a team only when someone turns it into evidence. Validation engineering is the discipline of converting a requirement into a stimulus, an expected behaviour, an observable piece of evidence and a pass/fail decision, and then doing that systematically, across a matrix of configurations, with negative, stress and recovery cases, and with regression protection after every fix. This Part teaches you to write a validation plan that a senior reviewer would sign, to design a test matrix that does not explode combinatorially, to reproduce intermittent failures deliberately, and to treat every fixed bug as a permanent test.

29.1 Why this chapter exists

Engineers who understand a protocol but cannot validate it produce opinions. Engineers who can validate it produce evidence. In an SSD program, the validation team is where the specification, the firmware, the host driver and the board meet: they decide whether a product ships, and their test logs and traces are the raw material of every root-cause investigation. The skills in this chapter — writing a requirement precisely, choosing the observable that proves it, designing a matrix, isolating intermittent failures — are the same skills you use when you debug. A debug session is simply a validation test whose result surprised you.

  • Beginner objective: explain the difference between a requirement, a test, an expected result and evidence, and write one complete test card for NVMe controller enable.
  • Intermediate objective: build test cards with negative, stress and recovery variants for queue creation, read/write integrity, flush, error handling and MSI-X (Message Signalled Interrupts – Extended).
  • Advanced objective: design a test matrix over PCIe generation × link width × Max_Payload_Size × queue depth × block size × power state, compute its full size and reduce it with pairwise and risk-based selection.
  • Senior objective: write a test plan that a program manager, a firmware lead and a PCIe architect can all sign, with explicit exit criteria and a regression strategy.
  • Trace-analysis objective: recognise normal, slow, failed and ambiguous outcomes of a validation test in a synthetic trace and identify the first abnormal event.
  • Debugging objective: convert an intermittent failure into a deterministic reproduction using stress, reset, power-cycle and workload-dependent methods, and record what each method proves.
  • Validation objective: close every fixed defect with a regression test that would have caught it, plus neighbouring cases.

Prerequisites. You should already be comfortable with the controller registers (CAP, CC, CSTS, AQA, ASQ, ACQ), the Submission Queue / Completion Queue model (SQ, CQ, CQE), memory requests and completions (MRd, MWr, CplD), Physical Region Page (PRP) data pointers, MSI-X, and PCIe Advanced Error Reporting (AER). If any of these is shaky, revisit the earlier Parts first; this chapter assumes them and uses them as building blocks. The automated tools you will later build in Chapter 34 consume the evidence formats introduced here.

29.2 Story, analogy and where it breaks

🧒 Kid analogy — the bridge inspector

Imagine a new footbridge in a park. The builder says "it is strong". The bridge inspector does not argue; she writes on a clipboard: "Requirement: the bridge holds 50 children at once. Setup: a calm day, the bridge dry. Stimulus: 50 children walk on and stand still. Expected: the middle sags less than 2 cm. Evidence: a laser ruler reading. Pass if under 2 cm." Then she does sneaky things: one heavy cart instead of children (negative test), children jumping for an hour (stress test), and checking the bridge springs back after they leave (recovery test). She tests on a hot day and a frosty day, with the bridge wet and dry (the test matrix). When a bolt breaks and is replaced, she reruns the exact test that broke it, and the tests nearby (regression).

🌍 Engineering analogy — the driving examiner

A driving examiner has a fixed checklist (requirements), a route (setup and stimulus), observable behaviours (mirror checks, stopping distance), a scoring rule (pass/fail) and deliberate surprises (the emergency stop is a negative/stress test). The examiner never writes "drove well"; she writes "stopped within the line at the junction on Elm Street". That specificity is what makes a validation result reproducible and arguable.

🧩 Where the analogy breaks

A bridge or a driver is observed directly. An SSD is observed through narrow windows: registers you can read, log pages the firmware chooses to populate, PCIe packets an analyzer can capture, and host-side timings. Much of the device (NAND management, internal queues, firmware scheduling) is generally unobservable. Also, a bridge does not change between inspections; firmware does, and so does the host kernel. Validation of an SSD is therefore always "evidence about a specific firmware, on a specific platform, with a specific driver, at a specific time" — and must record all four.

📌 Remember

A negative test passes only when the DUT fails correctly: the right status code type and status code, no corruption of unrelated state, no link-level side effects, and an unchanged ability to process the next valid command.

29.5 Architecture of a validation setup

Actors: the harness (decides what to run and judges results), the host (executes stimulus through a driver), the DUT, and optional observers (interposer + analyzer, thermal chamber, programmable power supply). State: DUT configuration (firmware, namespaces, features set), host configuration (kernel, driver parameters, IOMMU mode), link state (generation, width, ASPM). Interfaces: PCIe (packets), MMIO (registers), admin/I/O commands, log pages, OS logs. Dependencies: a test is only as good as its oracle; a performance test is only as good as its preconditioning; a trace is only as good as its trigger.

29.6 Hardware, protocol and specification views

🔧 Hardware view — what participates and what you can see
  • Must participate: Root Port (or switch downstream port), the link, the NVMe controller's PCIe function, its BAR0 register file, its DMA engine, host memory for queues and data.
  • May participate: PCIe switch, retimers, IOMMU, interposer, power-loss-protection capacitors, thermal sensors, out-of-band management (NVMe-MI over SMBus/I2C or VDM).
  • Observable: config space, BAR registers, CQE contents, log pages, Linux kernel messages, timings, and — with an analyzer — every TLP and DLLP on the link.
  • Generally unobservable: internal SRAM/DRAM caches, NAND program/erase scheduling, internal retry, firmware task scheduling. Vendor debug logs may expose some of it impl.
📡 Protocol view — the transactions a validation test produces

Every NVMe test reduces to a small vocabulary of PCIe transactions: host MWr to BAR0 (register writes and doorbells, posted — no completion), host MRd to BAR0 (register reads, answered by CplD from the device), device MRd to host memory (SQE fetch, PRP list fetch, write-data fetch, answered by CplD from the Root Complex), device MWr to host memory (read data, CQEs, MSI-X messages). Ordering matters: PCIe ordering rules keep a CQE MWr from passing the data MWrs issued before it in the same direction under default ordering attributes, which is why "data before completion" is visible in correct traces derived. Errors appear as completion status (UR, CA), poisoned TLPs (EP bit), AER messages, or NVMe status in the CQE.

📘 Specification discipline for validation
  • Normative behaviour ("shall") becomes a pass/fail requirement.
  • Recommended behaviour ("should") becomes a warning-level finding, not a failure, unless your product requirements upgrade it.
  • Optional behaviour ("may", or features gated by a capability bit) is tested only if the DUT advertises it — and then it must behave as specified. Your plan must read the capability first (CAP, Identify Controller, Identify Namespace) and select tests accordingly.
  • Implementation-dependent behaviour (latency, which internal error produces which vendor-specific log entry) is measured and characterised, never "failed" against the spec.
  • Version-dependent behaviour: record which revision your requirement came from; a 2.x-only feature on a device reporting an older Version register (VS, offset 08h) is not a defect.

📭 What the specification does not say

The NVMe and PCIe specifications define behaviour, formats and many timing limits, but they do not give you a validation plan, a performance target, an error-injection method, a minimum soak duration, or a pass threshold for correctable PCIe errors per hour. Those come from product requirements, customer specifications, compliance programs (for example plugfests and integrator lists) and your organisation's quality policy. Never write "spec requires 0 correctable errors" — write which document set that target.

29.8.3 Flush and the volatile write cache

First read Identify Controller's Volatile Write Cache (VWC) field: if no volatile cache is present, Flush is still a valid command but the power-loss experiment cannot distinguish behaviour. If a cache is present and enabled (Get Features, Volatile Write Cache feature), the experiment is: write a unique pattern (LBA number + generation counter in each block), issue Flush, wait for its CQE, cut power with a programmable supply, power on, read back. Every block whose write and subsequent Flush completed must contain the new pattern. Blocks written after the last Flush may contain old or new data — but never a torn mixture of unrelated data, unless the product's atomicity rules allow it (check Identify fields for atomic write unit sizes version).

⚠️ Safety

Power-cut testing is an EXPERT LAB activity: use a dedicated, non-production drive in a dedicated test host, with a controllable supply or a relay-switched riser. Never on a drive whose data you need, and never on a laptop's internal SSD.

29.8.4 MSI-X routing

Requirement: completions on CQ n are signalled with the vector given in that CQ's IV field (when IEN=1). Evidence ladder: (1) /proc/interrupts counters per nvme vector increase in proportion to I/O submitted on each CPU/queue; (2) analyzer shows an MWr to the MSI-X message address/data for that vector after each CQE MWr (or after a coalesced batch); (3) masking the vector in the MSI-X table sets its Pending Bit Array bit, and unmasking delivers the pending message. A failure where the CQE is written but no interrupt MWr follows points to the interrupt path; a failure where the interrupt arrives but the host does not reap points to the host (phase tag / CQ head handling).

29.9 Test matrix design and combinatorial explosion

Every dimension multiplies. With six dimensions of three values each, the full factorial has 36 = 729 configurations. Add firmware (3 builds), OS (2 kernels), temperature (3 points) and duration (2): 729 × 36 = 26 244 runs. At 30 minutes each that is about 1.5 years of a single station.

The executable script below computes the full factorial for a six-dimension example and greedily builds a pairwise (all-pairs) cover: every value of every dimension appears together with every value of every other dimension at least once.

#!/usr/bin/env python3
"""matrix.py - full-factorial size vs. greedy pairwise (all-pairs) reduction.
Executable, standard library only. Dimensions are a SYNTHETIC teaching example."""
import itertools

DIMS = {
    "gen":   ["Gen3", "Gen4", "Gen5"],
    "width": ["x1", "x2", "x4"],
    "mps":   [128, 256, 512],
    "qd":    [1, 32, 256],
    "bs":    ["4K", "128K", "1M"],
    "ps":    ["PS0", "PS3", "APST"],
}

def all_pairs(dims):
    names = list(dims)
    uncovered = set()
    for a, b in itertools.combinations(range(len(names)), 2):
        for va in dims[names[a]]:
            for vb in dims[names[b]]:
                uncovered.add((a, va, b, vb))
    tests = []
    candidates = list(itertools.product(*dims.values()))
    while uncovered:
        def gain(c):
            return sum((a, c[a], b, c[b]) in uncovered
                       for a, b in itertools.combinations(range(len(c)), 2))
        best = max(candidates, key=gain)
        tests.append(best)
        for a, b in itertools.combinations(range(len(best)), 2):
            uncovered.discard((a, best[a], b, best[b]))
    return names, tests

if __name__ == "__main__":
    full = 1
    for v in DIMS.values():
        full *= len(v)
    names, tests = all_pairs(DIMS)
    print(f"full factorial: {full} configurations")
    print(f"pairwise cover: {len(tests)} configurations")
    print(" | ".join(f"{n:>5}" for n in names))
    for t in tests[:6]:
        print(" | ".join(f"{str(x):>5}" for x in t))
    print("...")

How senior engineers choose high-value tests

  1. Risk first. Weight cells by (probability of a defect) × (impact). New firmware features, recently changed code, unusual hardware (x1, Gen5 retimers), and boundaries (QD=1, max QD, minimum and maximum transfer sizes, MPS edges) get more cells.
  2. Pairwise as a floor, not a ceiling. Most interaction defects involve one or two factors; pairwise gives broad coverage cheaply. Add 3-way coverage only for factors known to interact (MPS × transfer size × PRP alignment).
  3. Boundaries and equivalence classes. Instead of all block sizes, choose 512 B, 4 KiB, one size that is not a power of two (e.g. 12 KiB), MDTS, and MDTS + 1 (negative).
  4. Customer configurations are mandatory cells, regardless of what the reduction algorithm says.
  5. Duration is a dimension. Short runs find functional bugs; long runs find leaks, wear-related and thermal behaviour.
  6. Keep a golden baseline cell (M01) that runs on every build: it is your regression canary and your performance reference.

Worked example. Before the fix the failure occurred in 3 of 200 runs, so p ≈ 0.015. For α = 0.05: n ≥ ln(0.05)/ln(0.985) ≈ 2.996/0.01511 ≈ 198.2, so about 199 clean runs are needed before you can claim, at roughly 95% confidence, that the per-run failure rate dropped below the original derived. Fifteen clean runs prove almost nothing.

29.13 Regression engineering

  1. Reproduce the original failure on the unfixed build; record its rate and evidence.
  2. Capture a baseline: traces, logs, performance of the neighbouring cells.
  3. Apply the fix (one change at a time; record build ids).
  4. Rerun the original test for the number of iterations the statistics require.
  5. Run neighbouring cases: same feature at other matrix cells; same code path through other commands.
  6. Run stress on the fixed path.
  7. Compare traces: the fixed trace should differ from the failing trace exactly at the first abnormal event, and match the baseline elsewhere. Unexpected differences elsewhere are new findings.
  8. Record evidence and add the test permanently to the regression suite, tagged with the defect id.
💡 Senior insight

A fix without a test that failed before and passes after is an opinion. A fix with such a test but without neighbouring cases is a patch. A fix with both plus a trace diff that shows the first abnormal event disappeared — and nothing else changed — is engineering.

🏭 Implementation-dependent

Reset latency, enable-to-ready time, interrupt coalescing defaults, APST transition behaviour, which errors populate the Error Information log, and performance all vary by controller, firmware, driver, OS, platform and analyzer. To establish them for a specific system you need: the exact firmware and driver versions, the Identify data, repeated measurements with a stated distribution (not a single number), and — for timing claims at the link — analyzer timestamps rather than host timestamps.

29.17 Labs

🧪 Lab 29.1 — Capability-driven plan skeleton SAFE

Objective: produce a test plan section 5 (capability read) and select optional tests from real capability data. Prerequisites: a Linux host with any NVMe drive, or a QEMU VM with an emulated NVMe controller (see Chapter 32). Setup: install nvme-cli. Procedure: run nvme id-ctrl, nvme id-ns, lspci -vvv and save them as artifacts; build a table "feature → advertised? → field that told you → tests selected". Observations: note VWC, NPSS, SGLS, ONCS (optional NVM commands), FRMW, and link capability. Questions: Which optional commands will you not test, and why? Which fields did you have to look up in the spec to interpret?

Solution / expected reasoning

A good answer ties each selection to a field (e.g. "ONCS shows Write Zeroes supported → include WZ tests; SGLS indicates no SGL support → SGL tests out of scope, negative test: PSDT selecting SGL must be rejected with an appropriate status"). It also notes that the meaning of each bit must be read from the Identify Controller data structure table in the revision the device reports via VS.

Extension: write a script that diffs two id-ctrl outputs (two firmware builds) and flags capability changes that require plan updates.

🧪 Lab 29.2 — Negative-test suite on emulated NVMe SAFE

Objective: exercise queue-creation negative tests without risk. Setup: QEMU guest with an emulated NVMe device backed by a scratch image file. Procedure: using nvme admin-passthru inside the VM, send Create I/O SQ (opcode 01h) with a CQID that does not exist, and Delete I/O CQ (04h) for a queue the kernel driver is using (expect refusal while the SQ exists). Observations: CQE status printed by nvme-cli. Questions: Did the guest kernel's queues continue to work after each negative command?

Solution

Expected: Command Specific status for an invalid CQ and invalid deletion; existing I/O keeps working (run a short fio read afterwards). Recording that "existing I/O kept working" is what makes this a complete negative test. Note that emulated behaviour proves the test logic, not the behaviour of a physical controller.

Extension: wrap the commands in a script that emits a JSON verdict per card.

🧪 Lab 29.3 — Data-integrity soak on a spare drive CAUTION

Objective: run a verifying workload and interpret the evidence. Setup: a spare, non-production drive with no needed data. Procedure: fio --name=v --filename=/dev/nvme1n1 --rw=randwrite --bs=4k --iodepth=32 --size=8G --verify=crc32c --do_verify=1 --direct=1; capture SMART and error logs before and after. Observations: verify errors (should be zero), SMART deltas. Questions: What exactly does fio's verify prove, and what does it not prove about power-loss behaviour?

Solution

It proves read-back equals what was written within the run (no miscompare in the steady state). It does not prove persistence across power loss, nor behaviour of the volatile cache, nor correctness under other queue depths. Add the power-loss experiment (Expert) for that.

⚠️ Warning

Writing to a raw block device destroys its contents. Double-check the device name with nvme list and lsblk; never point fio at a mounted or system disk.

🧪 Lab 29.4 — Senior forensic lab: the marginal pass SAFE

Objective: write a validation finding from the "slow" synthetic trace in §29.11. Procedure: produce a one-page finding with the root-cause template headings (observed symptom, evidence, first abnormal event, expected vs actual, layer, candidates, eliminated, likely cause, confidence, additional evidence, recommendation, regression test). Question: is a 9.8 s ready time a defect?

Solution

Against the spec bound it is a pass; against product risk it is a finding. Expected reasoning: "Evidence: RDY at 9.8 s with CAP.TO=20 (10 s). Expected: ≤ 10 s (met). Risk: hosts with shorter internal timeouts (implementation-dependent) may fail; margin 2%. Additional evidence: distribution over 1 000 cycles, conditions (after clean vs unsafe shutdown). Recommendation: characterise; if the tail exceeds the bound, it becomes a defect. Regression: enable-time histogram as a tracked metric." Confidence about defect status: LOW until distribution is known.

Quiz

  1. Why does a negative test that returns an error not automatically pass?

    Answer

    It must return the correct status, leave unrelated state untouched, and leave the controller able to process subsequent valid commands. Any of those failing is a defect.

  2. Six dimensions with 3, 3, 3, 4, 3, 2 values: how many full-factorial configurations, and what is a lower bound on a pairwise suite?

    Answer

    3×3×3×4×3×2 = 648. Lower bound: product of the two largest = 4×3 = 12.

  3. Where does a performance target come from: the NVMe specification or elsewhere?

    Answer

    Elsewhere — product requirements or customer specifications. The NVMe specification defines behaviour, not product performance.

  4. Before a fix, a failure occurred in 1 of 100 runs. Roughly how many clean runs are needed for ~95% confidence the fix changed something?

    Answer

    n ≥ ln(0.05)/ln(0.99) ≈ 298.1, so about 299 runs.

  5. CSTS reads FFFFFFFFh. Name the first two checks.

    Answer

    Read Vendor ID via config space (is the function reachable?) and check the Root Port link status / kernel log for link-down or AER messages.

  6. Why must the plan read CAP and Identify data before selecting tests?

    Answer

    Optional features are tested only if advertised; selection based on a datasheet risks testing unsupported features (false failures) or skipping supported ones (coverage holes).

Interview questions

  1. Beginner What is the difference between verification and validation?
    Model answer

    Verification asks "did we build it to the specification?" (conformance to documented requirements); validation asks "did we build the right thing for its use?" (fitness for the customer's purpose). SSD teams often use "validation" for both; a good engineer says which one a test addresses.

  2. Beginner What are the nine fields of a test card?
    Model answer

    Requirement, setup, stimulus, expected behaviour, observable evidence, pass/fail, negative test, stress test, recovery test.

  3. Beginner Which Linux commands give you safe before/after evidence for an NVMe test?
    Model answer

    nvme smart-log, nvme error-log, nvme id-ctrl, lspci -vvv, kernel log via journalctl -k, and /proc/interrupts.

  4. Beginner What is a flaky test and why is "rerun until green" dangerous?
    Model answer

    A non-deterministic test; rerunning hides a real race in either the DUT or the harness. Measure its failure rate and investigate.

  5. Beginner Why record firmware revision with every result?
    Model answer

    Behaviour is a property of the firmware build as much as of the hardware; without it a result cannot be reproduced or compared.

  6. Intermediate Design negative tests for Create I/O SQ.
    Model answer

    Non-existent CQID, QID 0 or beyond granted queues, QSIZE 0 or larger than MQES+1 entries, non-contiguous when CAP.CQR requires contiguous, duplicate QID. For each: expected status, no side effects, existing queues keep working.

  7. Intermediate How would you test that Flush works?
    Model answer

    Only meaningful if a volatile write cache is present/enabled: unique patterns, Flush, wait for completion, controlled power cut, read back; blocks covered by the completed Flush must be durable.

  8. Intermediate What evidence separates an interrupt-path failure from a host reaping failure?
    Model answer

    Analyzer: CQE MWr present but no MSI-X MWr → interrupt path; MSI-X MWr present but host times out → host. Without an analyzer: /proc/interrupts counters and driver tracing.

  9. Intermediate Why does performance testing need preconditioning?
    Model answer

    A fresh-out-of-box drive performs differently (no garbage collection pressure); steady state after a defined fill workload gives reproducible numbers. The procedure is implementation-dependent and usually follows an industry test specification.

  10. Intermediate What does a test plan's "out of scope" section protect against?
    Model answer

    Implicit assumptions of coverage. Stating that, e.g., SR-IOV is out of scope makes the gap visible and reviewable.

  11. Advanced How do you reduce a 26 000-run matrix to something runnable without losing important coverage?
    Model answer

    Pairwise as baseline, 3-way for known interacting factors, mandatory customer cells, boundary/equivalence classes, risk weighting toward changed code, long-duration runs only on a few representative cells, golden baseline cell on every build.

  12. Advanced How do you prove an intermittent failure is fixed?
    Model answer

    Measure the pre-fix rate, compute the clean-run count for a chosen confidence, run it, and confirm with a trace diff that the first abnormal event is gone; run neighbouring cells and stress.

  13. Advanced What makes host timestamps unsuitable for link-level latency claims?
    Model answer

    They include CPU scheduling, interrupt latency, driver path and clock-source effects; analyzer timestamps are taken at the link.

  14. Advanced A test passes alone but fails in suite order. Approach?
    Model answer

    Treat it as state leakage; dump features/namespace/power state before each test; bisect the predecessor list; fix the harness or file the device defect if the state should have been reset.

  15. Advanced Which tests change when a new spec revision adds a field in a formerly reserved area?
    Model answer

    Tests that wrote/checked that reserved area (old hosts write 0 — check the new default meaning), new positive tests for the field, interoperability tests between old hosts and new devices and vice versa.

  16. Senior What exit criteria would you sign for a firmware release?
    Model answer

    All P0 cards pass on mandatory cells; no open severity-1; every waiver signed with rationale and risk; regression suite green on the final build id; performance within tolerance of the baseline; known issues documented for customers.

  17. Senior How do you decide where to spend analyzer time?
    Model answer

    On failures whose layer cannot be determined from host and device logs, on timing claims at the link, and on golden-trace baselines for regression diffing; not on tests that already have clear evidence.

  18. Senior A customer reports a failure you cannot reproduce. What do you ask for?
    Model answer

    Exact platform/BIOS/kernel/driver/firmware, workload and timing, logs from both host and drive (SMART, error, telemetry if supported), frequency, and conditions (temperature, power events); then build a reproduction ladder matching their configuration.

  19. Senior How do you prevent validation from becoming a test-count metric?
    Model answer

    Report requirement and risk coverage with evidence quality, defect escape rates, and time-to-root-cause; not raw test counts.

  20. Senior When is a marginal pass worse than a fail?
    Model answer

    When it hides a tail that will fail in the field (different hosts, temperatures, ageing). A fail gets fixed; a marginal pass gets shipped. Report margins, not just verdicts.
