PART XIII

End-to-End NVMe over PCIe

Up to now you have learned NVMe and PCIe as two separate machines: one that speaks in queues, commands and completion entries, and one that speaks in Transaction Layer Packets, credits and links. This part welds them together. You will follow a single 4 KiB read and a single 4 KiB write from the application's system call all the way through the doorbell, the command fetch, the data movement, the completion entry, the MSI-X interrupt and the final head-doorbell update — and you will learn to recognise every one of those steps as a specific packet, travelling in a specific direction, to a specific address region. This is the part that converts "I know NVMe" and "I know PCIe" into "I can read a trace of an SSD and tell you what it is doing and what went wrong".

39 The Most Important Chapter: An End-to-End NVMe Read

📌 Remember

If you only ever master one chapter of this book, master this one. Every debugging session on a PCIe-attached SSD — a hang, a timeout, a performance cliff, a corrupted buffer, a missing interrupt — is a deviation from the sequence you will memorise here. When you know the normal sequence cold, the abnormal one jumps off the screen.

39.1 Why this chapter exists

Most engineers learn NVMe (Non-Volatile Memory Express) from the command-set point of view: a Read command has opcode 02h, a starting LBA (Logical Block Address) in CDW10–11, a block count in CDW12, and the data lands in the buffer described by PRP1/PRP2. Most engineers learn PCIe (Peripheral Component Interconnect Express) from the packet point of view: there are Memory Read requests, Memory Write requests, Completions with Data, and they flow over a layered link. Very few engineers can explain, without hesitation, which PCIe packets a single NVMe Read produces, who sends each one, in which order, to which address, and what evidence each one leaves behind. That gap is exactly where real bugs hide: a driver that rings the doorbell before the SQE (Submission Queue Entry) is visible in memory, a device that writes the CQE (Completion Queue Entry) before the data, an IOMMU (I/O Memory Management Unit) that blocks the device's DMA (Direct Memory Access), an MSI-X (Message Signalled Interrupts – Extended) vector that is masked. This chapter closes the gap.

39.2 Learning objectives

  • Beginner: list the 17 stages of an NVMe Read from application to application completion, in order, without notes.
  • Intermediate: for each stage, state whether it crosses the PCIe link, and if so the TLP (Transaction Layer Packet) type, direction (upstream/downstream), requester, completer, and address region (host DRAM, BAR0 doorbell, MSI-X address).
  • Advanced: explain why the CQE write cannot overtake the data writes under default PCIe ordering, why the SQE fetch is a non-posted request but the data delivery is posted, and how MPS (Max Payload Size), MRRS (Max Read Request Size) and RCB (Read Completion Boundary) change the number of TLPs.
  • Senior: given a partial trace with a missing step, reason about which layer stopped, what the first abnormal event is, and what capture would prove it.
  • Trace-analysis: label every packet in a synthetic read trace with the NVMe event it belongs to.
  • Debugging: map five failure symptoms (timeout, wrong data, no interrupt, AER error, all-ones reads) to the stage where they originate.
  • Validation: describe what a test must observe to prove a read completed correctly at both the NVMe and PCIe layers.

39.3 Prerequisites

You need: the NVMe queue model (SQ/CQ pairs, doorbells, phase tag), the 64-byte SQE and 16-byte CQE layouts, PRP (Physical Region Page) data pointers, the PCIe transaction layer (posted vs non-posted requests, completions, tags), and the idea of BARs (Base Address Registers) and MMIO (Memory-Mapped I/O). If any of those feel shaky, revisit the earlier parts of the book before continuing. Within this part, the companion chapters are Chapter 40 (write) and Chapter 41 (correlation); interrupts are detailed in Chapter 43.

39.4 The story: a library with a pneumatic tube

🧒 Kid analogy

Imagine you live in a house (the host) next to a giant warehouse of books (the SSD). You want page 7 of a book. You write your request on a card and put it in your outbox tray in your own kitchen (the Submission Queue in host memory). Then you ring a little bell on the warehouse wall (the doorbell). The bell does not carry your card — it only says "there is new stuff in tray number 1, up to slot 5". The warehouse worker walks over, reaches into your kitchen and copies the card (command fetch). They go into the warehouse, find the book, copy the page and post the copy through your letterbox straight onto your table (data DMA). Then they drop a receipt into your inbox tray (Completion Queue) and ring your doorbell (MSI-X interrupt). You read the receipt, see "page 7 — done, OK", and tell the warehouse "I've read receipts up to slot 5" by ringing a second bell (CQ head doorbell).

🌍 Analogy

Engineering version: a restaurant where the waiter (driver) pins an order ticket to a rail inside the kitchen pass (SQ in host DRAM), taps a bell that tells the chef "the rail now has tickets up to position N" (doorbell MMIO write), the chef pulls the ticket (DMA read of SQE), cooks (media access), places the dish on the pass (DMA write of data), pins a "served" chit on a second rail (CQE write), then presses a buzzer in the dining room (MSI-X). The waiter clears chits and tells the chef which chits are cleared (CQ head doorbell).

🧩 Where the analogy breaks

(1) In the analogy the chef "walks over"; in reality the controller issues PCIe Memory Read requests and waits for Completion TLPs — the fetch has latency, credits and can time out. (2) The doorbell is a single 32-bit register write; there is no handshake and no reply — it is a posted write, so the host has no idea whether it arrived. (3) The receipt (CQE) and the dish (data) travel on the same PCIe ordering rules; in a restaurant nothing prevents the chit arriving before the dish, but in PCIe, default ordering guarantees posted writes from the same requester are not reordered relative to each other. (4) The "buzzer" is itself just another memory write to a magic address; there is no separate wire.

39.6 The 17 stages — overview diagram

39.7 Stage by stage — the five views

Each stage below is described through five lenses demanded by this book: analogy, technical, hardware, protocol and trace appearance. Example parameters used throughout (all synthetic): I/O queue pair QID 3, SQ size 1024 entries, CQ size 1024 entries, CAP.DSTRD = 0 (doorbell stride 4 bytes), BAR0 at host physical address 0xF7A0_0000, SQ3 base IOVA 0x1_2340_0000, CQ3 base IOVA 0x1_2350_0000, data buffer IOVA 0x1_4000_0000 (4 KiB, page aligned), device BDF (Bus:Device.Function) 02:00.0 → Requester ID 0x0200, MPS = 256 bytes, MRRS = 512 bytes, MSI-X vector 4 for CQ3 with message address 0xFEE0_2000 and data 0x0000_0045 (x86-style, impl).

Stage 1 — Application request

Analogy: you decide you want page 7. Technical: the application calls pread(fd, buf, 4096, 7*4096) on an O_DIRECT file descriptor (or io_uring / libaio submit). With O_DIRECT the page cache is bypassed and the user buffer itself becomes the DMA target after pinning. Hardware: only the CPU is involved; the buffer may not even be resident yet. Protocol: none — no PCIe traffic. Trace appearance: nothing on a PCIe analyzer. In software, strace shows the system call, and bpftrace on syscalls:sys_enter_pread64 can timestamp it.

Stage 2 — Block request

Analogy: the house's secretary writes your wish onto a standard form. Technical: the filesystem maps file offset to device LBA; a bio is built and turned into a struct request by blk-mq, which picks a hardware queue (normally the one mapped to the submitting CPU) and allocates a tag. Hardware: CPU only. Protocol: none. Trace appearance: blktrace events Q (queued), G (get request), D (issued to driver) — the D timestamp is the last software event before the driver.

Stage 3 — Driver command creation

Analogy: the request is copied onto the warehouse's own card format. Technical: the driver chooses the SQ for this hardware context (SQ3), fills a 64-byte SQE: CDW0 = opcode 02h (Read), FUSE=00b, PSDT=00b (PRPs), CID = command identifier (Linux derives it from the blk-mq tag plus a generation counter in recent kernels — impl); NSID = 1; PRP1 = 0x1_4000_0000; PRP2 = 0 (a single 4 KiB page fits PRP1 alone); CDW10/11 = starting LBA; CDW12 bits 15:0 = NLB (number of logical blocks, zero-based) = 0 for one 4 KiB block on a 4 KiB-formatted namespace, or 7 for eight 512-byte blocks. The buffer has been DMA-mapped through the IOMMU, yielding the IOVA. Hardware: CPU writes into cacheable DRAM. Protocol: none yet. Trace appearance: Linux tracepoint nvme:nvme_setup_cmd records qid, cid, opcode, nsid and CDW10–15.

Stage 4 — Command memory

Analogy: the card is placed in the tray. Technical: the SQE is stored at SQ3_base + tail × 64. If the SQ were placed in a CMB (Controller Memory Buffer) instead, this store itself would be a PCIe write into device memory — a different trace shape (see the trace variants below). Hardware: the CPU store sits in cache; on most modern x86 platforms device DMA reads are cache-coherent (snooped), so no explicit flush is required, but a write memory barrier is required to order the SQE store before the doorbell store. Protocol: none for host-memory SQ. Trace appearance: invisible on the link. This is the first important negative-evidence trap: you can never "see" the SQE being written on a PCIe analyzer when the SQ lives in host DRAM — you only see the device reading it later.

Stage 5 — Submission queue tail update

Analogy: you count how many cards are in the tray now. Technical: driver increments its private tail: tail = (tail + 1) % qsize. The SQ is full when (tail + 1) % qsize == head, where head is learned from the SQHD field of returned CQEs. Hardware/Protocol: none yet. Trace: none.

Stage 6 — Doorbell

Analogy: ringing the bell. Technical: the driver writes the new tail value to the SQ3 Tail Doorbell register. Offset = 1000h + (2 × 3) × (4 << DSTRD) = 1000h + 24 = 1018h. With CAP.DSTRD = 0, the register sits at BAR0 + 0x1018 = 0xF7A0_1018. Linux writes it with writel(), preceded by a barrier so the SQE store is globally visible first. Linux may batch several SQEs and ring once (the bd->last hint) — impl. Hardware: the CPU issues an uncached (UC) store to the MMIO range; the store leaves the core, is claimed by the root complex because the address falls inside the root port's memory window, and becomes a TLP. Protocol: see stage 7. Trace: on a CPU-side tool (e.g. MMIO tracing in a hypervisor) the write is visible; on the link it becomes stage 7.

Stage 7 — PCIe Memory Write (doorbell TLP)

Analogy: the bell's sound travelling along the wire. Technical/Protocol: a MWr (Memory Write) request, 3DW header if the address is below 4 GiB (here it is), Length = 1 DW, First DW BE = 1111b, Last DW BE = 0000b, Requester ID = root port (e.g. 00:01.0 → 0x0008 — impl: some root complexes use 00:00.0), payload = tail value. It is posted: no completion will ever come back. It travels downstream. It consumes Posted Header and Posted Data flow-control credits on the link. Hardware: the endpoint's transaction layer decodes the address against BAR0, the controller latches the new tail. Trace appearance: one downstream MWr, 1 DW payload, address in BAR0 doorbell region. The payload equals the new tail — if you see tail values that skip or go backwards, suspect a driver bug or a lost/merged write.

⚠️ Warning

A posted doorbell write can be silently dropped if the device is in reset, if Memory Space Enable is cleared in the Command register, or if the link is down. The host's writel() returns immediately regardless. The first symptom is a command timeout 30 seconds later (Linux default nvme_core.io_timeout), not an error at the doorbell. Always correlate a timeout backwards to the doorbell.

Stage 8 — Controller command fetch decision

Analogy: the worker hears the bell and notes "tray 3 has one new card". Technical: the controller compares the new tail with its internal SQ head; entries between head and tail are pending. Fetch policy (how many SQEs per read, arbitration among SQs — round robin, weighted round robin with urgent priority) is controller-specific within the arbitration mechanism selected by CC.AMS. Hardware: doorbell write lands in a register file; firmware or a hardware queue manager schedules the fetch. Protocol: internal. Trace: the time gap between the doorbell MWr and the first fetch MRd is the controller's doorbell-to-fetch latency, typically sub-microsecond to a few microseconds (impl).

Stage 9 — DMA request

Analogy: the worker grabs a trolley. Technical: the DMA engine is programmed with source = SQ3_base + head × 64, length = 64 bytes (or a multiple if it fetches several SQEs at once, bounded by MRRS and by the ring wrap). Hardware: a tag is allocated from the device's outstanding-request pool (8-bit tags by default, 10-bit if enabled on both ends). Protocol/Trace: appears as stage 10.

Stage 10 — Memory Read TLP (SQE fetch)

Analogy: the worker's hand reaching into your kitchen. Protocol: MRd (Memory Read) request, 4DW header because the IOVA is above 4 GiB, Length = 16 DW (64 bytes), Requester ID = 0x0200 (the SSD), Tag = e.g. 0x11, address = 0x1_2340_0000 + head × 64. It is non-posted: it consumes Non-Posted Header credits and the device must keep the tag reserved until all completions arrive, or until the completion timeout fires. Direction: upstream. Hardware: the RC forwards to the IOMMU, which translates the IOVA; if no mapping exists the access is blocked and the device typically receives a completion with UR (Unsupported Request) or CA (Completer Abort) status — or, on some platforms, nothing useful — while the host logs an IOMMU fault (impl). Trace appearance: first upstream packet after the doorbell; address inside the SQ region.

Stage 11 — Completion with Data (SQE delivery)

Analogy: the copy of the card arrives in the worker's hand. Protocol: CplD (Completion with Data), downstream, Completer ID = root complex, Requester ID = 0x0200, Tag = 0x11 (matching), Status = SC (Successful Completion), Byte Count = 64, Lower Address = low 7 bits of the request address, payload 16 DW = the SQE. Because the request is 64-byte aligned and 64 bytes long, a single CplD is the usual result; a completer may legally split a read into multiple completions at RCB boundaries (64 or 128 bytes) — the requester must reassemble using Byte Count and Lower Address. Hardware: data comes from DRAM (or from CPU cache via snoop). Trace appearance: a CplD whose tag matches the MRd. The interval MRd→CplD is the host's memory read latency seen by the device, typically on the order of 0.5–2 µs on a direct-attached root port, more through switches or under IOMMU miss (impl).

📘 Spec

The PCIe Base Specification defines the Completion header fields (Completer ID, Completion Status, BCM, Byte Count, Requester ID, Tag, Lower Address) and the rules that a requester match completions by Requester ID + Tag (plus Function if Phantom Functions / extended tags are in use). The NVMe over PCIe Transport specification defines that the controller fetches SQEs from the SQ and posts CQEs; it does not mandate how many SQEs the controller reads per request.

Stage 12 — Flash operation

Analogy: the worker walks the warehouse aisles. Technical: the controller decodes opcode 02h, validates NSID, LBA range (else status 80h LBA Out of Range), and field values (else 02h Invalid Field). The FTL (Flash Translation Layer) maps the LBA to a physical NAND page; a NAND read (tR, tens of microseconds for TLC, less for SLC, impl) moves data into the die's page register, then onto the NAND channel into controller SRAM/DRAM, through LDPC/BCH ECC decode. If the LBA was never written (deallocated), the controller may return zeroes or a pattern per the DLFEAT reporting, without touching NAND. Hardware: NAND dies, channel controllers, ECC engine, internal buffer. Protocol: none on the PCIe link. Trace appearance: a silent gap on the PCIe link — no TLPs for this command. Other commands may be active in that gap.

Stage 13 — Data transfer (MWr to host buffer)

Analogy: the copy pushed through your letterbox, in several envelopes. Protocol: the controller issues MWr requests upstream to the PRP1 address. Each MWr payload is ≤ MPS (256 bytes here) and must not cross a 4 KiB address boundary. 4096 / 256 = 16 MWr TLPs, each 64 DW of payload, 4DW header (address above 4 GiB), Requester ID 0x0200, posted (no completion), consuming Posted credits. Hardware: IOMMU translates; RC writes into DRAM and invalidates/updates cache lines. Trace appearance: a burst of 16 upstream MWr packets to consecutive addresses 0x1_4000_0000, …_0100, …_0200 … _0F00.

N_MWr = ceil(transfer_bytes / MPS) (when start is MPS-aligned and no 4 KiB crossing)
  • transfer_bytes — data length of the command (NLB+1 × LBA size)
  • MPS — Max_Payload_Size programmed in Device Control (128–4096 bytes)
  • N_MWr — number of data-bearing write TLPs; unaligned starts add one partial TLP

Stage 14 — Completion entry (CQE write)

Analogy: the receipt in your inbox. Technical: the controller builds a 16-byte CQE: DW0 command-specific (0 for Read), DW1 reserved, DW2 = SQHD (new SQ head) bits 15:0 and SQID = 3 bits 31:16, DW3 = CID bits 15:0, Phase Tag bit 16, Status Field bits 31:17 (SC=00h, SCT=0 for success). It writes it to CQ3_base + cq_tail × 16. Protocol: one MWr, 4 DW payload, upstream, posted. Under default ordering (Relaxed Ordering attribute clear) a posted write may not pass an earlier posted write in the same direction, so the CQE cannot overtake the 16 data MWrs. Hardware: the controller's internal CQ tail and phase state advance; the phase it writes inverts every time the CQ wraps. Trace appearance: a 16-byte upstream MWr into the CQ region, immediately after the last data MWr.

🚀 Advanced

If the device sets Relaxed Ordering on data writes (allowed only if the host enabled it in Device Control), it must still ensure the CQE does not become visible before the data. Typical implementations send the CQE with RO clear, which forces it behind all earlier posted writes, or rely on a flush mechanism. Never assume — check the RO bit in the TLP Attr field in traces. A host bridge that mishandles RO is a classic source of "data corruption on fast completion" bugs (impl).

Stage 15 — MSI-X

Analogy: the buzzer. Technical: CQ3 was created with interrupt vector (IV) = 4 and IEN = 1 in the Create I/O CQ command. Unless coalescing defers it, the controller reads MSI-X table entry 4 (Message Address, Message Data, Vector Control) from its internal copy and, if the entry and the function are unmasked, sends the interrupt. Protocol: a MWr upstream, 1 DW payload = Message Data (0x45), to Message Address (0xFEE0_2000). On x86 that address range is decoded by the RC as an interrupt, not as DRAM (impl: platform interrupt architecture). Because it is a posted write behind the CQE write, the CQE is visible before the interrupt is delivered. Hardware: the interrupt controller (e.g. local APIC or interrupt remapping unit) raises the vector on the target CPU. Trace appearance: a 1 DW upstream MWr to a fixed, recurring address outside DRAM regions — recognisable because it repeats with the same address/data for every completion on that queue.

Stage 16 — Driver

Analogy: you read the receipt and tell the warehouse. Technical: the ISR (or a polling loop with io_uring IOPOLL) reads CQE at its own head index; it is new iff the Phase Tag equals the driver's expected phase. The driver issues a read barrier so the rest of the CQE is read after the phase bit, extracts CID to find the request, checks the status, updates SQ head from SQHD, advances its CQ head (flipping expected phase on wrap), and finally writes the CQ3 Head Doorbell at offset 1000h + (2×3+1) × 4 = 101Ch. Linux may process several CQEs before writing the head doorbell once. Protocol: the CQE read is a CPU memory read from DRAM — no PCIe. The head doorbell is a downstream MWr 1 DW, posted. Trace appearance: a downstream MWr to BAR0+0x101C some microseconds after the MSI-X message. Note the asymmetry: the SQ head never needs a doorbell — it comes back inside CQEs.

Stage 17 — Application completion

Analogy: you open the envelope and read page 7. Technical: blk_mq_complete_request → bio end → wake the waiting task / post an io_uring CQE (an io_uring CQE — not an NVMe CQE, another naming trap). The IOMMU mapping is torn down, and the pages unpinned. Protocol: none. Trace: blktrace C event; syscall return.

💡 Senior insight

Count the PCIe transactions for one 4 KiB read at MPS 256: 1 doorbell MWr + 1 MRd + 1 CplD + 16 data MWr + 1 CQE MWr + 1 MSI-X MWr + 1 CQ head doorbell MWr = 22 TLPs, plus Ack and UpdateFC DLLPs. Only 2 of them are downstream "control" writes; the protocol is deliberately device-driven. This is why NVMe scales: the host does a handful of uncached writes, everything else is device DMA into cacheable memory. Also note that with interrupt coalescing and doorbell batching, the per-command MSI-X and doorbells amortise away, approaching 1 MRd + 1 CplD + data + 1 CQE per command.

The lesson: on the wire, a read is a tiny burst of control traffic, a long silence, and a data burst. If the silence is suspiciously long for a single command, the cause is almost always inside the device (media, firmware, garbage collection), not the link. If the gap between the doorbell and the fetch is long, suspect controller arbitration or a device stalled on something else. If the gap between the MSI-X and the head doorbell is long, suspect the host (interrupt affinity, CPU busy, softirq).

39.12 Specification discipline

Applicable sources: NVMe Base Specification (queue model, SQE/CQE formats, status codes; baseline revision 2.4 in this book), NVM Command Set Specification (Read/Write semantics), NVMe over PCIe Transport Specification (doorbells, register mapping, interrupts), PCIe Base Specification (TLP formats, ordering, completions, MSI-X). Confirm current revisions on nvmexpress.org and pcisig.com.

  • verified SQE is 64 bytes, CQE is 16 bytes (base sizes for NVMe over PCIe I/O queues); CQE DW3 holds CID, Phase Tag and Status; DW2 holds SQHD and SQID.
  • verified Doorbell offsets: SQ y Tail at 1000h + (2y)×(4 << CAP.DSTRD); CQ y Head at 1000h + (2y+1)×(4 << CAP.DSTRD).
  • verified MWr is posted, MRd is non-posted and answered by CplD; MSI-X is delivered as a memory write.
  • derived The CQE cannot become visible before the data under default ordering — derived from PCIe producer/consumer ordering rules for posted writes.
  • impl How many SQEs are fetched per MRd, fetch latency, use of Relaxed Ordering, interrupt address format.
  • version 10-bit tag support (PCIe 4.0+ optional), 14-bit tags in FLIT mode (PCIe 6.0), Gen6 FLIT framing change the low-level encoding but not the transaction sequence.
📭 What the spec does not say

The NVMe specification does not require the controller to process commands in submission order, to fetch SQEs one at a time, to post CQEs in command order, or to generate exactly one interrupt per CQE. Commands in the same SQ may complete out of order — that is why every CQE carries the CID. Anyone who builds a test that expects in-order completion is testing an implementation, not the protocol.

⚠️ Safety

The commands above are read-only. --readonly makes fio refuse to write. Enabling tracepoints on a busy production system generates high volume; disable them afterwards (echo 0). Never point a write workload at a device holding data you care about.

What these outputs can prove: tracepoints prove the driver built a command with given CID/opcode and that a CQE with given status was consumed. What they cannot prove: which TLPs crossed the link, whether a doorbell was delivered, whether data landed before the CQE. Only a protocol analyzer (or device-internal logging) proves link-level events. This distinction — software evidence vs wire evidence — is the backbone of Chapter 47.

39.15 Code: a minimal submit/complete loop

// Submission (driver side) — pseudocode, single-producer queue
void submit_read(struct q *sq, u16 cid, u32 nsid, u64 slba, u16 nlb0, u64 prp1, u64 prp2) {
    struct sqe *e = &sq->ring[sq->tail];
    memset(e, 0, 64);
    e->cdw0  = 0x02 | (cid << 16);       // opcode Read, FUSE=0, PSDT=0 (PRP)
    e->nsid  = nsid;
    e->prp1  = prp1;  e->prp2 = prp2;     // bytes 24..39
    e->cdw10 = (u32)slba; e->cdw11 = (u32)(slba >> 32);
    e->cdw12 = nlb0;                      // zero-based block count
    sq->tail = (sq->tail + 1) % sq->size;
    wmb();                                // SQE globally visible BEFORE doorbell
    writel(sq->tail, sq->db);             // -> posted MWr on the link
}

// Completion (ISR side)
void cq_drain(struct q *cq, struct q *sq) {
    bool any = false;
    for (;;) {
        struct cqe *c = &cq->ring[cq->head];
        if (((c->dw3 >> 16) & 1) != cq->phase) break;  // not new yet
        rmb();                            // read rest of CQE after the phase bit
        u16 cid    = c->dw3 & 0xFFFF;
        u16 status = c->dw3 >> 17;        // SC[7:0] SCT[10:8] CRD[12:11] M[13] DNR[14]
        sq->head   = c->dw2 & 0xFFFF;      // SQHD
        complete(cid, status);
        if (++cq->head == cq->size) { cq->head = 0; cq->phase ^= 1; }
        any = true;
    }
    if (any) writel(cq->head, cq->db);   // CQ head doorbell -> posted MWr
}

39.16 Worked example: counting and addressing

Problem: CAP.DSTRD = 2, QID 5, 16 KiB read into a buffer at IOVA 0x8000_0800 (not page aligned), MPS = 128 B, memory page size (CC.MPS=0) 4 KiB. Compute: doorbell offsets, PRP entries, number of data MWr TLPs, header size.

Solution: stride = 4 << 2 = 16 bytes. SQ5 tail = 1000h + (2×5)×16 = 1000h + A0h = 10A0h; CQ5 head = 1000h + 11×16 = 10B0h. The buffer starts 0x800 into a page, so it spans 0x8000_0800 → 0x8000_47FF: pages 0x8000_0000 (2 KiB used), 0x8000_1000, 0x8000_2000, 0x8000_3000 and 0x8000_4000 (2 KiB used) = 5 pages. PRP1 = 0x8000_0800; more than 2 pages → PRP2 points to a PRP list containing 4 entries (0x8000_1000 … 0x8000_4000) → one extra MRd (32 bytes) + CplD. Data MWr count: 16384 / 128 = 128 TLPs; the start is 128-aligned (0x800) so no extra partial TLP. Addresses are below 4 GiB → 3DW headers. Total link TLPs ≈ 1 doorbell + 1 SQE MRd + 1 CplD + 1 PRP-list MRd + 1 CplD + 128 data MWr + 1 CQE + 1 MSI-X + 1 head doorbell = 136. Header+framing overhead per 128-byte TLP is significant — this is why MPS 128 costs bandwidth compared with 256 or 512.

39.17 Common mistakes

  • Believing the doorbell "contains" the command. It carries only a 16-bit index (in a 32-bit register).
  • Looking for the host's write of the SQE on the analyzer — it never crosses the link (unless the SQ is in the CMB).
  • Calling the CplD for the SQE fetch "the completion". It is a PCIe completion of a PCIe read; the NVMe completion is the CQE written later by an MWr.
  • Expecting a PCIe completion for the data write or for the doorbell. Both are posted.
  • Assuming in-order completion within a queue.
  • Forgetting the barrier between the SQE store and the doorbell (works on x86 by accident of strong ordering, fails on weakly ordered CPUs).
  • Reading the CQE fields before checking the phase bit, or without a read barrier after it.
  • Assuming one interrupt per command.
  • Computing doorbell offsets with stride 4 when CAP.DSTRD ≠ 0.

39.19 Lab

🧪 Lab 39.1 — Observe one read end to end in software SAFE

Objective: correlate application, block, and NVMe driver events for a single read and identify the parts you cannot see without an analyzer.

Prerequisites: Linux with an NVMe drive, root, tracefs, fio, blktrace (optional).

Setup: enable nvme_setup_cmd and nvme_complete_rq tracepoints and block:block_rq_issue/block:block_rq_complete.

Procedure: (1) Start trace_pipe capture to a file. (2) Run the single-I/O fio read from §39.14. (3) Stop capture. (4) Find the issue, setup_cmd, complete_rq and rq_complete lines for your I/O. (5) Note qid and cid. (6) Look up which IRQ line in /proc/interrupts incremented.

Observations: timestamps of four software events; qid; cid; status 0; IRQ count change.

Questions: (a) Which of the 24 steps in §39.8 does each event correspond to? (b) What fraction of the measured latency lies between setup_cmd and complete_rq? (c) Which steps are invisible here?

Solution

(a) block_rq_issue ≈ step 2/3; nvme_setup_cmd ≈ step 4; nvme_complete_rq ≈ step 21–22; block_rq_complete ≈ step 24. (b) Typically the vast majority (often > 90%) — that interval contains the doorbell, fetch, media, data, CQE, interrupt. (c) Steps 7–20: all link traffic, controller-internal work and interrupt delivery are not individually visible; you see only their aggregate latency.

Extension: repeat with --hipri (polling) on a kernel with poll queues configured (nvme.poll_queues=N) and confirm that no IRQ counter increments.

🧪 Lab 39.2 — Decode a synthetic read trace SAFE

Objective: reconstruct the NVMe command from raw TLP fields.

Setup: given (synthetic) the CplD payload for tag 0x11, first 48 bytes in little-endian DWORDs: 00420002 00000001 00000000 00000000 00000000 00000000 40000000 00000001 00000000 00000000 00001000 00000000.

Procedure: decode CDW0, NSID, PRP1, PRP2, CDW10–11.

Solution

CDW0 = 0x00420002 → opcode 02h (Read), FUSE 0, PSDT 0, CID = 0x0042. NSID = 1. CDW2–3 = 0, MPTR (bytes 16–23) = 0. PRP1 (bytes 24–31) = low DW 0x40000000, high DW 0x00000001 → 0x1_4000_0000. PRP2 (bytes 32–39) = 0. CDW10 = 0x00001000, CDW11 = 0 → SLBA = 0x1000 (4096). CDW12 (not shown) would hold NLB. Data MWrs should target 0x1_4000_0000 — check that they do.

Extension: write a 30-line Python script that decodes any 64-byte SQE hex dump.

39.20 Exercise

🎯 Exercise

For a 128 KiB read at MPS 512, page size 4 KiB, page-aligned IOVA above 4 GiB, MRRS irrelevant: (1) how many PRP list entries? (2) how many data MWr TLPs? (3) how many TLPs total, assuming one MSI-X and one CQ head doorbell? (4) If coalescing aggregates 8 completions per interrupt, what is the amortised MSI-X count per command?

Answer

(1) 32 pages; PRP1 covers page 0, PRP2 → list of 31 entries (248 bytes, fetched by one MRd if within one page). (2) 131072/512 = 256 MWr. (3) 1 + 1 + 1 + 1 + 1 + 256 + 1 + 1 + 1 = 264 (doorbell, SQE MRd, CplD, list MRd, list CplD — possibly split into 2 at RCB 128/64 — data, CQE, MSI-X, head doorbell). (4) 1/8.

Quiz

  1. Which TLP carries the 64-byte SQE across the link for a host-memory SQ?

    Answer

    A CplD (Completion with Data) sent by the root complex in response to the controller's MRd.

  2. Is the data delivery of an NVMe Read posted or non-posted?

    Answer

    Posted — MWr from device to host; no PCIe completion is returned.

  3. Why doesn't the host need to write an SQ head doorbell?

    Answer

    Only the controller consumes SQ entries; it reports its SQ head in the SQHD field of each CQE. There is no SQ head doorbell register.

  4. What guarantees the CQE is not visible before the data?

    Answer

    PCIe ordering: posted writes from the same requester (without RO) cannot pass earlier posted writes; the controller issues data writes before the CQE write.

  5. Compute the CQ 2 head doorbell offset with DSTRD = 0.

    Answer

    1000h + (2×2+1)×4 = 1014h.

  6. How does the driver know a CQE slot holds a new entry?

    Answer

    Its Phase Tag matches the driver's current expected phase, which flips each time the head wraps.

  7. On the analyzer you see a 1 DW upstream MWr to 0xFEE0_xxxx. What is it?

    Answer

    On x86 platforms, an MSI/MSI-X interrupt message (impl: address window is platform-defined).

Interview questions

  1. Beginner Walk me through what happens when Linux issues a 4 KiB read to an NVMe SSD.
    Model answer

    Block layer builds a request; driver writes a 64 B SQE into the SQ in host memory and rings the SQ tail doorbell (MMIO MWr). Controller fetches the SQE (MRd/CplD), reads NAND, DMA-writes the data to the PRP buffer (MWr), writes a 16 B CQE to the CQ (MWr), sends MSI-X (MWr). Driver checks phase, completes the request, writes CQ head doorbell.

  2. Beginner What is a doorbell?
    Model answer

    A controller register in BAR0 (from 1000h) holding the SQ tail or CQ head index; writing it informs the controller of new submissions or freed completion slots.

  3. Intermediate Why does NVMe use device-side DMA fetch rather than MMIO pushes of commands?
    Model answer

    MMIO writes are uncached and slow for the CPU; DMA reads from cacheable memory let the CPU write commands at memory speed, batch submissions, and touch MMIO only once per batch. CMB is the exception that trades this for reduced latency.

  4. Intermediate How many TLPs does a 4 KiB read generate at MPS 256?
    Model answer

    About 22: doorbell MWr, MRd, CplD, 16 data MWr, CQE MWr, MSI-X MWr, head doorbell MWr — minus amortisation from batching/coalescing.

  5. Advanced What happens if the device uses Relaxed Ordering for the CQE write?
    Model answer

    The CQE could pass data writes, so the host could see the completion and read stale buffer contents. Devices must keep RO clear on the CQE (or otherwise guarantee ordering); RO is only usable if enabled in Device Control.

  6. Advanced A trace shows the doorbell and nothing else for 30 s. List hypotheses.
    Model answer

    Invalid doorbell value (async event), queue not created, controller hung/fatal (CSTS.CFS), doorbell to wrong offset (DSTRD), Memory Space disabled, capture filter/placement. Disambiguate with CSTS, admin CQ, trace config.

  7. Senior How would you prove whether a data corruption came from the SSD or the host?
    Model answer

    Capture the data MWr payload on the link and compare with the buffer contents and the known-good data; use end-to-end PI (protection information) if formatted; check IOMMU mapping lifetimes (use-after-unmap) and RO handling; check EP bits; reproduce with IOMMU strict mode.

  8. Senior Explain the tail-latency signature of a media stall vs a host interrupt stall.
    Model answer

    Media stall: long gap between CplD (SQE) and first data MWr; data/CQE/MSI-X then normal. Host stall: data, CQE, MSI-X on time, but long gap before head doorbell and software completion.

39.21 Summary

An NVMe Read is a choreography of software steps (invisible to the link), a few host-initiated posted writes (doorbells), one device-initiated non-posted read per SQE batch (with CplD replies), a media gap, a posted data burst, a posted CQE write and a posted MSI-X write. The NVMe completion (CQE) and the PCIe completion (CplD) are completely different things. Every debugging question starts with: which step is the first that deviates?
