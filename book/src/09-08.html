FINAL MASTERY

Master Rubric, Transformation and Teach-Back Capstones

The last stretch is about proof. A learner is not senior because they read this book or memorised 500 definitions. They are senior when they can demonstrate accurate mental models, specification literacy, version awareness, evidence-based debugging, trace reconstruction, cross-layer reasoning, performance reasoning, validation planning, clear communication and uncertainty management — on demand, in front of someone else. This part defines the master rubric, maps the kid-to-senior transformation, sets five teach-back capstones with layer-by-layer grading, and ends with the final certification checklist.

102. First teach-back — “Explain NVMe Read from application to NAND and back.”

Model answer (abridged script)

“The application calls read() on a file opened with O_DIRECT. The filesystem maps the file offset to LBAs and the block layer builds a request, splitting it to fit the device’s limits. The NVMe driver picks the submission queue owned by the current CPU, allocates a command identifier and fills a 64-byte SQE: opcode 02h Read, NSID 1, starting LBA, number of blocks minus one, and PRP entries pointing to the physical (IOMMU-mapped) pages of the user buffer — a PRP list if more than two pages. It places the SQE at the queue tail in host memory, issues a write barrier, and writes the new tail to the SQ tail doorbell in BAR0. That MMIO write travels as a posted Memory Write TLP down the PCIe link. The controller sees the doorbell, issues a Memory Read TLP for 64 bytes at the SQ slot; the root complex returns a Completion with Data carrying the SQE. The controller parses it, looks up the logical-to-physical mapping in its FTL, issues NAND page reads to the right dies, waits tR, moves data through ECC decoding, then DMAs the data into host memory as Memory Write TLPs to the PRP addresses, each up to Max Payload Size. Then it writes a 16-byte CQE — CID, SQ ID, SQ head, status success, current phase — into the CQ with another posted write, which PCIe ordering keeps behind the data. Then it sends the MSI-X message — a Memory Write to the vector’s address with its data — which becomes a CPU interrupt. The driver’s handler sees the phase bit flip, reads the CQE, matches the CID to the request, completes it, writes the CQ head doorbell, and the block layer wakes the application, whose buffer already contains the data.”

103. Second teach-back — “Explain why a PCIe Completion TLP is not the same thing as an NVMe Completion Queue Entry.”

DimensionPCIe Completion TLP (Cpl/CplD)NVMe CQE
LayerPCIe Transaction LayerNVMe (above the transport)
Answers whatA non-posted PCIe request (MRd, CfgRd/Wr, I/O)An NVMe command (SQE)
Who sends itThe completer of that request — can be host (root complex) or deviceAlways the NVMe controller
How it travelsIs itself a TLP type (Fmt/Type Cpl or CplD)Carried as payload of a posted Memory Write TLP into host memory
Matching keyRequester ID + TagSQID + CID
StatusSC, UR, CRS, CASCT/SC, DNR, More, CRD
Count per NVMe ReadSeveral (e.g. CplD for SQE fetch, PRP list)Exactly one
Model answer

“They live at different layers and answer different questions. A PCIe completion answers a single PCIe non-posted request; it is matched by requester ID and tag and its status is about the transaction (successful, unsupported request, completer abort). In an NVMe read, the host sends CplDs to the device — for example to return the SQE the device fetched. The NVMe CQE answers an entire NVMe command; it is a 16-byte data structure the controller writes into host memory, and on the wire it is the payload of a Memory Write, not a Completion TLP. So in a normal NVMe read you see CplDs flowing toward the device and exactly one CQE carried in an MWr toward the host. Confusing them leads to wrong conclusions — like thinking a UR completion means the NVMe command failed (it means a PCIe request failed, which may or may not later cause the command to fail).”

104. Third teach-back — “Explain how you would debug a missing NVMe completion.”

Model answer

“First, identify the exact command: SQID, CID, submit time. Second, check whether the system is alive: read CSTS — all ones means the device is off the bus; CFS means controller fatal. Third, check the host’s view: is the CQE already in CQ memory with the right phase (lost interrupt or host bug) — polling the CQ answers that cheaply. If not, walk the pipeline on the wire: doorbell written with the right offset and value; SQE fetched (MRd covering the slot and a successful CplD); PRP list fetched if needed; data moved; CQE written — if it was written elsewhere, compare with the CQ base from Create I/O CQ; MSI-X sent with the right address/data and not masked. The first missing or wrong step is the first abnormal event. Then look at the layer of that step: UR completions point to addressing or IOMMU; no fetch after doorbell points to Bus Master, controller state or credits; CQE present but ignored points to phase or CQ mapping. At each step I keep alternatives and look for the evidence that eliminates them — e.g. link Recovery events or AER around the time, async events, error log. Finally I label confidence and design one experiment to confirm.”

105. Fourth teach-back — “What would you look for first in a protocol-analyzer trace (e.g. a Teledyne LeCroy capture) when a system reports an NVMe timeout?”

📭 Tool-neutral note

This answer describes an investigative sequence that applies to any PCIe protocol analyzer, including Teledyne LeCroy tools. It deliberately does not reproduce any vendor’s screens, menu names or exact view formats; consult the analyzer’s own documentation for how to perform each step.

StepConcrete actionWhy first / what it rules out
0Validate the capture: both directions present, link speed/width as expected, no buffer overflow gaps, triggers and filters recorded, interposer did not change behaviourPrevents conclusions from missing data
1Get the timed-out command’s QID and CID and the host timestamp from the kernel log; align host time with trace time using a marker or a known event (e.g. controller reset CC write)Gives the search key
2Compute that queue’s SQ tail doorbell address (BAR0 from config writes + 1000h + 2y × stride); find doorbell writes in the window before the timeout start (30 s earlier by default in Linux impl)Did the submission reach the device?
3Find the device MRd covering the SQE slot; decode the returned SQE; confirm CID and opcodeDid the controller fetch it? Is the SQE what the host intended?
4Follow data movement: PRP list fetch, data MRds (write) or MWrs (read); check every completion status, EP bit, and outstanding tagsLocates DMA/IOMMU/completion problems
5Search for the CQE MWr with matching SQID/CID into the CQ range; check phase and addressDistinguishes “device never completed” from “host never noticed”
6Search for the MSI-X MWr for that CQ’s vector after the CQELost/masked interrupt
7In the same window check link health: LTSSM transitions (Recovery, L1 exits), Naks/replays, UpdateFC progress, ERR_COR/ERR_NONFATAL/ERR_FATAL message TLPsTransport-layer causes and context
8Look at the host’s reaction: Abort command, CSTS reads, CC.EN writes; make sure you do not mistake recovery traffic for the causeSeparates cause from consequence
9State the first abnormal event, its layer, and the next evidence neededOutput of the analysis
⚠️ Not accepted

“I would look for errors in the trace.” — generic, no search key, no ordering. Also not accepted: starting from the end (the reset) and working backwards without first locating the specific command.

Model answer (script)

“If you learned NVMe at 1.4, the fundamentals you know still hold: the queue pairs, 64-byte commands and 16-byte completions, phase tags, the controller registers and doorbells, and the core admin and NVM opcodes. What changed is mostly around them. First, the specification is now a family: since 2.0 there is a Base specification, separate I/O command set documents — NVM, Zoned Namespaces, Key Value and newer ones like Subsystem Local Memory and Computational Programs — and separate transport documents for PCIe, RDMA and TCP. When you cite behaviour, cite the right document and revision. Second, the 2.x line added capabilities in placement, virtualisation and security — Flexible Data Placement, live migration, per-I/O keys among them; I’d check the exact revision of each before quoting it. Third, the 2.4 set released in August 2026 highlights Post-Quantum Cryptography, PCIe Exported NVM Subsystem Migration, Voltage Monitoring, Rate Limiting and a standard way to Restore Manufacturing Default Settings. I can tell you their purposes; for mechanisms — new commands, log pages, feature identifiers — we should read the 2.4 documents rather than guess. Practically: update your tools’ decoders, never infer feature support from the version register alone, and always state which revision you are reasoning from.”
