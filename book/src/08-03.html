PART XXXII

Lab Environment

You learn protocols with your hands, but hands can destroy data. This Part builds a graded lab: zero-risk emulation in a virtual machine, read-only inspection of real hardware, cautious experiments on a spare drive in a dedicated test host, and expert-only destructive work. Every activity in this book carries one of three labels — SAFE, CAUTION, EXPERT — and this Part defines them precisely.

32 Building a Safe NVMe/PCIe Lab

📘 Baseline

Tools change faster than specifications. Commands below are real for current mainstream Linux distributions, QEMU, nvme-cli and fio, but option names and output formats are version- and impl-dependent: check --help and man pages for your installed versions. Output shown is illustrative and abbreviated, never authoritative.

32.1 Why this chapter exists

Engineers lose data in labs for three reasons: they run a destructive command on the wrong device, they run an experiment on a machine they also depend on, or they did not know a command was destructive. This chapter removes all three: a classification of every activity, a recommended set of environments and hardware, and setup recipes that let you do most of this book's labs with zero risk.

  • Classify any lab activity as SAFE, CAUTION or EXPERT and apply the matching precautions.
  • Build a QEMU virtual machine with emulated NVMe controllers and namespaces for zero-risk experiments.
  • Set up a dedicated physical test host with a spare SSD, adapters and (optionally) an analyzer.
  • Use Linux kernel tracing, nvme-cli, fio and offline trace files as evidence sources.

Prerequisites: basic Linux shell; the validation mindset from Chapter 29.

🧒 Kid analogy — the science classroom

In a science class, reading the thermometer is always allowed (SAFE). Heating water needs goggles and a teacher nearby (CAUTION). Mixing chemicals that could explode is done only by the teacher, behind a glass screen, with a fire extinguisher ready (EXPERT). And the very first experiments are done with pretend chemicals in a computer game — that is the virtual machine.

🧩 Where the analogy breaks

In a classroom you can see the danger. In a lab, /dev/nvme0n1 and /dev/nvme1n1 look identical, device numbering can change between boots, and a destructive command gives no warning. The danger is invisible; your procedure must make it visible.

32.4 Tier 1: QEMU with emulated NVMe (zero risk)

QEMU emulates an NVMe controller as a PCI device (on mainstream builds the device model is called nvme, with separate nvme-ns devices for additional namespaces) version. The guest kernel's real NVMe driver binds to it, so you exercise genuine driver code paths, nvme-cli and fio — while every "destructive" command only modifies an image file on the host.

# On the HOST (not inside the guest). Creates two scratch images; touches no real disk.
qemu-img create -f qcow2 guest-os.qcow2 20G        # or reuse a cloud image as the OS disk
qemu-img create -f raw   nvme-ns1.img   4G
qemu-img create -f raw   nvme-ns2.img   1G

qemu-system-x86_64 -enable-kvm -m 4G -smp 4 -cpu host \
  -drive file=guest-os.qcow2,if=virtio \
  -drive file=nvme-ns1.img,if=none,id=ns1,format=raw \
  -drive file=nvme-ns2.img,if=none,id=ns2,format=raw \
  -device nvme,id=nvme0,serial=LAB0001 \
  -device nvme-ns,drive=ns1,bus=nvme0,nsid=1 \
  -device nvme-ns,drive=ns2,bus=nvme0,nsid=2 \
  -nographic
# Options and sub-option names vary by QEMU version: check
#   qemu-system-x86_64 -device nvme,help    and    -device nvme-ns,help

Inside the guest (all SAFE, because the targets are image files):

lspci -nn | grep -i 0108          # emulated controller, class 0108
sudo nvme list                    # serial LAB0001, two namespaces
sudo nvme id-ctrl /dev/nvme0 -H   # human-readable decode of Identify Controller
sudo nvme id-ns /dev/nvme0n1 -H
sudo nvme show-regs /dev/nvme0 -H # CAP/VS/CC/CSTS/AQA... if supported by your nvme-cli
sudo nvme get-feature /dev/nvme0 -f 0x07 -H   # Number of Queues

Useful QEMU features for learning impl (availability depends on QEMU version): trace events for the NVMe device model (e.g. enabling events matching pci_nvme* with QEMU's -trace option) give you a host-side log of each command the emulated controller processes — a software "analyzer" for the NVMe layer; zoned namespaces can be enabled on nvme-ns devices in recent versions for ZNS labs; SR-IOV emulation exists in recent versions for virtualization labs.

📭 What emulation does not show

An emulated controller has no PCIe link: no LTSSM, no DLLPs, no flow-control credits, no real TLP timing. Its latency and error behaviour are those of a software model. Use it to learn command semantics and driver behaviour; never to characterise a product.

32.5 Tier 2: physical system, read-only

lspci -tv                              # topology: root ports, switches, endpoints
sudo lspci -vvv -s <BDF>               # capabilities, LnkCap/LnkSta, DevCtl MaxPayload/MaxReadReq, AER
ls /sys/bus/pci/devices/<domain:BDF>/  # current_link_speed, current_link_width, max_link_speed ...
cat /sys/bus/pci/devices/<domain:BDF>/current_link_speed
sudo nvme list
sudo nvme smart-log /dev/nvme0
sudo nvme error-log /dev/nvme0
journalctl -k -b | grep -iE "nvme|pcieport|aer"
cat /proc/interrupts | grep nvme
⚠️ setpci is not read-only by default

setpci can read (setpci -s BDF CAP_EXP+12.w) but also write configuration registers (anything with =value). A write can disable memory decoding, change link control, or hang the system. Treat any setpci write as EXPERT, on a test host only.

32.8 Offline trace files

Keep a library of trace files with provenance: who captured, which tool and version, DUT and firmware, platform, trigger, and a hash of the raw file. Export to a neutral format (CSV/JSON) for your own tools, but keep the original. Label every file as real, synthetic, excerpted or reconstructed; a synthetic file must never be renamed into the "real" folder. The analyzer's export format is impl — write a column mapping per tool version (Project 9).

32.9 Bench procedure (the pre-flight checklist)

  1. Confirm the activity's safety level.
  2. Confirm the host is the dedicated test host and the boot disk is not the DUT.
  3. Identify the DUT by serial number; record firmware revision.
  4. Capture "before" evidence: lspci -vvv, id-ctrl, smart-log, error-log.
  5. Start observers (kernel trace, analyzer trigger) before stimulus.
  6. Run; capture "after" evidence; store everything with a run id.
🧪 Lab 32.1 — Zero-risk NVMe in QEMU SAFE

Objective: create a VM with an emulated NVMe controller and two namespaces; practise "destructive" commands safely. Setup: §32.4. Steps: (1) inside the guest list controllers and namespaces; (2) run nvme id-ctrl -H and note OACS (optional admin commands) and ONCS; (3) sudo nvme format /dev/nvme0n2 — destructive on real hardware, harmless here; (4) re-read id-ns and smart-log. Observations: what changed after format? Questions: why is this command EXPERT on real hardware but SAFE here?

Solution

The format only rewrites the host-side image file backing namespace 2; nothing physical is touched. On real hardware it erases user data and can take long, change LBA format, and fail in ways that need vendor recovery. Expected observations: namespace data reads back as zeros/deallocated pattern impl; counters may change.

Extension: enable QEMU's NVMe trace events and correlate guest nvme-cli commands with the host-side trace lines.

🧪 Lab 32.2 — Inventory a real machine SAFE

Objective: read-only inventory. Steps: topology (lspci -tv), link (LnkCap vs LnkSta), MaxPayload/MaxReadReq, MSI-X count, NVMe identify, health. Question: is your drive running at its capable speed and width? If not, which component limits it?

Solution

Compare drive LnkCap with the Root Port's LnkCap and the LnkSta; the link trains to the lower common capability, and can be down-trained by signal-integrity problems or firmware settings. A chipset-attached slot may also share upstream bandwidth.

🧪 Lab 32.3 — First workload on a spare drive CAUTION

Objective: run a read-only-then-write fio sequence on a dedicated spare. Steps: verify serial; random read QD1 and QD32 (--rw=randread --readonly); then random write with verify on the raw device. Questions: how did latency percentiles change between QD1 and QD32, and why?

Solution

QD32 increases throughput and increases per-command latency due to queueing (Little's Law: outstanding = throughput × latency). Absolute values are implementation-dependent.

🧪 Lab 32.4 — Firmware-slot inspection and controlled reset EXPERT

Objective: observe reset effects on a spare drive in the test host. Steps: read nvme fw-log (SAFE); then trigger a controller reset with nvme reset /dev/nvmeX and a function reset via sysfs (echo 1 > /sys/bus/pci/devices/<BDF>/reset) while no workload runs; observe kernel log and re-read Identify. Questions: what did each reset clear? What would change if I/O were in flight?

Solution

Controller reset reinitialises the NVMe controller (queues recreated by the driver); a function-level reset also resets PCIe function state and the OS restores config space. With I/O in flight, commands are aborted and retried or failed by the driver — implementation-dependent. Firmware download/commit are deliberately not part of this lab: they need a vendor-approved image and recovery path.

⚠️ Warning

Resets of the wrong device can take a running system's disk offline. Triple-check the BDF and serial; never run on a host whose boot disk is NVMe on the same controller.

    Answer

    Answer

  3. What can QEMU's emulated NVMe not teach?

    Answer

33A.2 Project 1 — Build an NVMe mental model

Requirements: encode the NVMe-over-PCIe command lifecycle as an ordered list of steps, each with an actor and the evidence it leaves; check an observed sequence for order violations and missing steps. Architecture: one data table (the model) + one checker function. Milestones: M1 table of 8 steps; M2 ordering checker; M3 missing-step report; M4 extend to write commands (device MRd of data instead of MWr) and to interrupt coalescing (interrupt may cover several CQEs). Expected output: the step list and problems found in a synthetic out-of-order observation.

#!/usr/bin/env python3
"""Project 1 starter - command-lifecycle mental-model checker (simulation, stdlib only).
Each step names the ACTOR and the EVIDENCE it leaves. The checker rejects
lifecycles whose steps are out of order - the core of the mental model."""
LIFECYCLE = [
    ("host",       "build 64-byte SQE in host memory",        "none on the link (memory write by CPU)"),
    ("host",       "write SQ tail doorbell (MMIO)",           "posted MWr TLP, host -> BAR0 + 1000h + ..."),
    ("controller", "fetch SQE from host memory",              "MRd TLP device -> host, CplD back"),
    ("controller", "DMA data (read cmd: write to host)",      "MWr TLPs device -> host buffers (PRP/SGL)"),
    ("controller", "post 16-byte CQE with phase tag",         "MWr TLP device -> CQ memory"),
    ("controller", "signal interrupt (MSI-X)",                "MWr TLP to MSI-X address (e.g. 0xFEExxxxx on x86)"),
    ("host",       "consume CQE, check phase + status",       "none on the link"),
    ("host",       "write CQ head doorbell",                  "posted MWr TLP host -> BAR0 doorbell"),
]

def check(observed):
    """observed: list of step indexes as seen in a (synthetic) trace."""
    problems = []
    for prev, cur in zip(observed, observed[1:]):
        if cur < prev:
            problems.append(f"step '{LIFECYCLE[cur][1]}' seen after '{LIFECYCLE[prev][1]}'")
    missing = sorted(set(range(len(LIFECYCLE))) - set(observed))
    for m in missing:
        problems.append(f"missing: {LIFECYCLE[m][1]} (expected evidence: {LIFECYCLE[m][2]})")
    return problems

if __name__ == "__main__":
    for i, (actor, step, ev) in enumerate(LIFECYCLE):
        print(f"{i}. [{actor:<10}] {step:<40} evidence: {ev}")
    print("\nchecking synthetic observation [0,1,2,4,3,5,6]:")
    for p in check([0, 1, 2, 4, 3, 5, 6]):
        print("  PROBLEM:", p)
0. [host      ] build 64-byte SQE in host memory         evidence: none on the link (memory write by CPU)
1. [host      ] write SQ tail doorbell (MMIO)            evidence: posted MWr TLP, host -> BAR0 + 1000h + ...
2. [controller] fetch SQE from host memory               evidence: MRd TLP device -> host, CplD back
3. [controller] DMA data (read cmd: write to host)       evidence: MWr TLPs device -> host buffers (PRP/SGL)
4. [controller] post 16-byte CQE with phase tag          evidence: MWr TLP device -> CQ memory
5. [controller] signal interrupt (MSI-X)                 evidence: MWr TLP to MSI-X address (e.g. 0xFEExxxxx on x86)
6. [host      ] consume CQE, check phase + status        evidence: none on the link
7. [host      ] write CQ head doorbell                   evidence: posted MWr TLP host -> BAR0 doorbell

checking synthetic observation [0,1,2,4,3,5,6]:
  PROBLEM: step 'DMA data (read cmd: write to host)' seen after 'post 16-byte CQE with phase tag'
  PROBLEM: missing: write CQ head doorbell (expected evidence: posted MWr TLP host -> BAR0 doorbell)

Tests / acceptance criteria: (1) the canonical order [0..7] yields no problems; (2) any swap of data and CQE yields an ordering problem (under default PCIe ordering, data MWrs are not passed by the later CQE MWr — the model encodes that expectation derived); (3) omitting the CQ head doorbell yields a missing-step report. Failure cases: treating "no evidence on the link" steps as missing (host-memory activity is invisible to a PCIe analyzer); forgetting that interrupt coalescing or polling legitimately removes the interrupt step. Extensions: add per-step "what Linux shows" (tracepoints); add a write-command variant; add an "ambiguous" status for steps that could be absent legitimately.

33A.3 Project 2 — Decode PCIe configuration space

Requirements: decode a Type 0 configuration header: IDs, class code, Command/Status bits, header type, BARs (I/O vs memory, 32/64-bit, prefetchable), subsystem IDs, interrupt pin, capability pointer; then walk the capability list given a full 256-byte or 4 KiB dump. Architecture: byte buffer → field decoders → BAR decoder (consumes two slots for 64-bit BARs) → capability walker (ID, next pointer) → report. Milestones: M1 header fields; M2 BARs; M3 capability list (PM 01h, MSI 05h, PCIe 10h, MSI-X 11h); M4 extended capabilities from offset 100h (AER, etc.) with loop detection. Expected output on a synthetic header modelled on QEMU's emulated controller IDs:

#!/usr/bin/env python3
"""Project 2 starter - decode a Type 0 PCI configuration header (executable, stdlib only).
Input: hex bytes of the first 64 bytes (SYNTHETIC sample below, IDs modeled on QEMU's emulated NVMe; you may paste
the hex from `lspci -xxx` for YOUR device - reading is safe, writing is not)."""
import struct

SAMPLE = bytes.fromhex(
    "36 1b 10 00 06 04 10 00 00 02 08 01 00 00 00 00"
    "04 00 00 fe 00 00 00 00 00 00 00 00 00 00 00 00"
    "00 00 00 00 00 00 00 00 00 00 00 00 f4 1a 00 11"
    "00 00 00 00 40 00 00 00 00 00 00 00 0b 01 00 00".replace(" ", ""))

CAP_NAMES = {0x01: "Power Management", 0x05: "MSI", 0x10: "PCI Express", 0x11: "MSI-X"}

def decode_bars(cfg):
    out, i = [], 0
    while i < 6:
        raw = struct.unpack_from("<I", cfg, 0x10 + 4 * i)[0]
        if raw == 0:
            out.append((i, "unimplemented (reads 0)", 0)); i += 1; continue
        if raw & 1:
            out.append((i, "I/O", raw & ~0x3)); i += 1; continue
        kind = (raw >> 1) & 0x3
        pref = bool(raw & 0x8)
        if kind == 0x2:   # 64-bit BAR consumes two slots
            hi = struct.unpack_from("<I", cfg, 0x10 + 4 * (i + 1))[0]
            out.append((i, f"MEM64 pref={pref}", (hi << 32) | (raw & ~0xF))); i += 2
        else:
            out.append((i, f"MEM32 pref={pref}", raw & ~0xF)); i += 1
    return out

def decode(cfg):
    vid, did, cmd, sts = struct.unpack_from("<HHHH", cfg, 0)
    rev, pi, sub, base = cfg[8], cfg[9], cfg[0xA], cfg[0xB]
    print(f"Vendor {vid:04x} Device {did:04x} Rev {rev:02x}")
    print(f"Class {base:02x}:{sub:02x}:{pi:02x}"
          + ("  -> NVMe I/O controller (01h/08h/02h)" if (base, sub, pi) == (1, 8, 2) else ""))
    print(f"Command {cmd:04x}: MemSpace={cmd>>1&1} BusMaster={cmd>>2&1} INTxDisable={cmd>>10&1}")
    print(f"Status  {sts:04x}: CapList={sts>>4&1}")
    svid, sdid = struct.unpack_from("<HH", cfg, 0x2C)
    print(f"Subsystem {svid:04x}:{sdid:04x}  INTx pin {cfg[0x3D]}")
    print(f"Header type {cfg[0xE] & 0x7f} multi-function={cfg[0xE]>>7}")
    for idx, kind, addr in decode_bars(cfg):
        print(f"BAR{idx}: {kind} base=0x{addr:x}")
    ptr = cfg[0x34]
    print(f"Capabilities pointer {ptr:02x}h" + ("" if ptr < len(cfg) else " (beyond the 64 bytes given: need full dump)"))

if __name__ == "__main__":
    decode(SAMPLE)

33A.6 Project 5 — Simulate Submission/Completion Queues

Requirements: simulate one SQ/CQ pair: host submits (advances tail), controller consumes (advances head, reports SQHD in CQE), controller posts CQEs with a phase tag that inverts every wrap, host reaps by comparing the phase tag with its expected phase. Architecture: Ring (size, head, tail), Controller (CQ slots, phase), Host (expected phase, CID allocator). Milestones: M1 ring full/empty; M2 phase tag; M3 SQHD reporting; M4 CQ-full back-pressure; M5 multiple SQs sharing one CQ. Expected output (three rounds through a 4-entry ring, showing the phase flip each wrap):

#!/usr/bin/env python3
"""Project 5 starter - SQ/CQ ring simulation with phase tag (simulation, stdlib only).
Models: 0-based queue size, full = (tail+1)%N == head, CQ phase tag inverts on wrap."""
class Ring:
    def __init__(self, entries):
        self.n, self.head, self.tail = entries, 0, 0
    def full(self):  return (self.tail + 1) % self.n == self.head
    def empty(self): return self.head == self.tail

class Controller:
    def __init__(self, sq, cq):
        self.sq, self.cq, self.phase, self.slots = sq, cq, 1, [None] * cq.n
    def process_one(self, sqe_table):
        if self.sq.empty():
            return False
        cid = sqe_table[self.sq.head]
        self.sq.head = (self.sq.head + 1) % self.sq.n           # consumed -> reported as SQHD
        if self.cq.full():
            raise RuntimeError("CQ full: controller must not overwrite unconsumed CQEs")
        self.slots[self.cq.tail] = {"cid": cid, "sqhd": self.sq.head, "p": self.phase, "status": 0}
        self.cq.tail = (self.cq.tail + 1) % self.cq.n
        if self.cq.tail == 0:
            self.phase ^= 1                                     # wrap -> invert phase
        return True

class Host:
    def __init__(self, sq, cq, ctrl):
        self.sq, self.cq, self.ctrl, self.expect_p, self.table = sq, cq, ctrl, 1, {}
        self.next_cid = 0
    def submit(self):
        if self.sq.full():
            return None
        cid = self.next_cid; self.next_cid += 1
        self.table[self.sq.tail] = cid
        self.sq.tail = (self.sq.tail + 1) % self.sq.n           # == doorbell write value
        return cid
    def reap(self):
        done = []
        while True:
            e = self.ctrl.slots[self.cq.head]
            if e is None or e["p"] != self.expect_p:
                break                                           # phase mismatch => not new
            done.append(e["cid"])
            self.cq.head = (self.cq.head + 1) % self.cq.n
            if self.cq.head == 0:
                self.expect_p ^= 1
        return done

if __name__ == "__main__":
    sq, cq = Ring(4), Ring(4)                 # 4 slots => 3 usable entries each
    ctrl = Controller(sq, cq); host = Host(sq, cq, ctrl)
    for rnd in range(3):
        cids = [c for c in (host.submit() for _ in range(4)) if c is not None]
        while ctrl.process_one(host.table): pass
        print(f"round {rnd}: submitted {cids} reaped {host.reap()} "
              f"sq(h={sq.head},t={sq.tail}) cq(h={cq.head},t={cq.tail}) host_expects_P={host.expect_p}")

round 2: submitted [6, 7, 8] reaped [6, 7, 8] sq(h=1,t=1) cq(h=1,t=1) host_expects_P=1

#!/usr/bin/env python3
"""Project 6 starter - doorbell address map and doorbell-write validation (simulation).
SQyTDBL = 1000h + (2y)   * (4 << CAP.DSTRD)
CQyHDBL = 1000h + (2y+1) * (4 << CAP.DSTRD)"""
def sq_tail_db(qid, dstrd): return 0x1000 + (2 * qid) * (4 << dstrd)
def cq_head_db(qid, dstrd): return 0x1000 + (2 * qid + 1) * (4 << dstrd)

def classify(offset, dstrd, max_qid):
    if offset < 0x1000:
        return "controller register (not a doorbell)"
    stride = 4 << dstrd
    idx, rem = divmod(offset - 0x1000, stride)
    if rem:
        return "misaligned doorbell access"
    qid, is_cq = divmod(idx, 2)
    if qid > max_qid:
        return f"doorbell for non-existent queue {qid}"
    return f"{'CQ' if is_cq else 'SQ'}{qid} {'head' if is_cq else 'tail'} doorbell"

def validate_write(value, qsize):
    """A doorbell value is a slot index, so it must be < queue size (entries).
    Extension: also reject an SQ tail that would overrun the current head."""
    if value >= qsize:
        return "INVALID: value >= queue size (controller may post an async error, see spec)"
    return "ok"

💡 Senior insight

The value of these small tools is not the code; it is the tests. Each test is a specification rule you have turned into something executable. When a real trace violates one, your tool tells you before your intuition does.

Quiz

  1. Why can a ring of 64 entries hold at most 63 outstanding commands?

    Answer

    Head == tail means empty; to distinguish full from empty, full is defined as tail+1 == head, leaving one slot unused.

  2. A TLP has Length field 0. How many DWs?

    Answer

    1024.

  3. Opcode 02h: what command is it?

    Answer

    Depends on the queue: Get Log Page on the admin queue, Read on an I/O queue (NVM command set).

  4. With DSTRD=2, where is CQ3's head doorbell?

    Answer

    1000h + (2×3+1) × (4 << 2) = 1000h + 7 × 16 = 1000h + 70h = 1070h.

Interview questions

  1. Intermediate Explain the phase tag and what goes wrong without it.
    Model answer

    The controller writes CQEs with a phase bit that inverts every pass through the ring; the host identifies new entries by comparing it with its expected phase, avoiding a separate "valid" flag that would need clearing. Without correct phase tracking the host either re-consumes stale entries or misses new ones.

  2. Advanced How would you test your TLP decoder's correctness without an analyzer?
    Model answer

    Build headers from field values with an independent encoder, round-trip decode, cross-check with a second implementation or published examples in the PCIe specification, and add boundary cases (Length 0, Byte Count 0, 4DW addresses).
