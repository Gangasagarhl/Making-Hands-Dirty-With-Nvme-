PART LIX

12-Month Study Plan

A year-long plan for a working engineer studying 6–10 hours per week. Each month has four weekly goals, a deliverable you can show someone, and links to the parts of the book that carry the material. The plan assumes one evening lab session and one weekend block per week, following the weekly lab format.

59.1 Month-by-Month Plan

59.1.1 Why this chapter exists

Ambitious learners fail by sprinting through Parts I–X in three weeks and then stalling at traces. A paced plan with deliverables spreads load, builds artefacts (parsers, notes, reports) you will use later, and inserts the spaced checkpoints from Part XLVIII.

59.1.2 Learning objectives

  • Commit to a realistic schedule with measurable weekly goals.
  • Produce twelve deliverables that together form a portfolio.
  • Reach rubric level 7 (Senior) by month 12.
🧪 Equipment assumptions

A Linux machine with at least one NVMe SSD you can afford to wipe (for CAUTION/EXPERT labs only), nvme-cli, pciutils, fio, Python 3. An analyzer is not required — synthetic traces cover trace skills; real analyzer time is a bonus in months 7–11.

PART LXI

Weekly Lab Format

Every study week follows the same eight-step loop — Read, Understand, Draw, Implement, Observe, Analyze, Debug, Explain. The loop guarantees that each concept passes through text, diagram, code, real data, trace and speech.

61.1.1 Why this chapter exists

Without a fixed loop, learners default to reading. The loop forces production: a drawing, a program, an observation, a debugged trace and a spoken explanation every week.

PART LXII

Teach-Back Method

At the end of every major chapter, you explain the concept twice: as if to a 10-year-old, and as if to a senior hardware engineer. Both explanations are graded. Weak intuition and weak technical precision are flagged separately because they need different remedies.

62.1 Two Audiences, Two Grades

62.1.1 Why this chapter exists

Explaining to a child tests whether you have a mental model; explaining to an expert tests whether the model is precise and complete. Many engineers pass one and fail the other.

62.1.2 The prompts

🧒 Prompt 1

“Explain this concept as if you are teaching it to a 10-year-old.”

🔧 Prompt 2

“Explain it as if you are presenting to a senior hardware engineer.”

62.1.4 Worked example — the doorbell

🧒 Kid version (scores 3)

“Imagine a restaurant where you write your order on a slip and pin it on a board by the kitchen. The cook can’t watch the board all the time, so after pinning slips you ring a little bell. The bell doesn’t say what you ordered — it just says ‘new slips are up to here’. The cook then walks over and reads the slips. Where it breaks: in a real computer the cook reads slips really fast by itself (DMA), and the bell is a number — the position of the newest slip — not just a ring.”

🔧 Senior version (scores 3)

“The SQ tail doorbell is a 32-bit write-only register in BAR0 at 1000h + 2y × (4 << CAP.DSTRD). The host writes the new tail index after placing SQEs in host memory, with a write barrier before the MMIO so the SQE stores are visible first. On the wire it is a 1-DW posted MWr downstream. The controller then issues MRds for 64-byte SQEs from SQ base + index × 64, CplDs return them. A tail ≥ queue size or a write to a non-existent queue is an invalid doorbell write, which the controller may report as an asynchronous event. Shadow doorbells (Doorbell Buffer Config) can replace most MMIO in virtualised setups version. To verify: analyzer filter on BAR0+1000h range; correlate with the subsequent MRd address.”

⚠️ Weak example (Kid 1, Senior 1)

“The doorbell is how NVMe sends commands to the SSD over PCIe.” — Wrong: the doorbell does not carry the command; it carries an index. Precise and intuitive explanations both fix this misconception.
