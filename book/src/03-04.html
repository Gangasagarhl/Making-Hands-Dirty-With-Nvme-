PART VIII

DMA

Once the driver can reach the controller's registers (Part VII), the direction of most traffic reverses. In NVMe, the host CPU writes only a handful of registers per command — essentially one doorbell write to submit and one to acknowledge completions. Everything else — fetching the command, fetching the data pointer lists, moving the data, posting the completion, even raising the interrupt — is done by the controller as a bus master, reading and writing host memory with Direct Memory Access. This Part explains what DMA really is on PCIe, what addresses the device uses, how an IOMMU sits in the middle, and how to see and debug all of it.

20.1 Why this chapter exists

The master curriculum's DMA-safety rule is explicit: never describe DMA as "the SSD directly reads RAM" without qualification. Instead you must be able to say who initiates the transaction, which address is used, what translation may exist, what PCIe transaction represents it, how data returns, and what the controller may do internally. This chapter builds exactly that vocabulary, then follows one NVMe read command through every DMA it causes.

20.2 Learning objectives

  • Beginner: explain why DMA exists and contrast it with programmed I/O (CPU copying).
  • Intermediate: describe DMA in terms of source, destination, descriptors, scatter-gather lists and direction; map NVMe structures (SQ, CQ, PRP, SGL) onto those terms.
  • Advanced: explain IOMMU translation, IOVA, DMA masks, bounce buffering, cache coherency (snooping, No Snoop) and ATS.
  • Senior: diagnose DMA failures across layers: driver mapping lifetime, IOMMU faults, completion timeouts, poisoned data, ordering.
  • Trace analysis: identify device-initiated MRd/CplD and MWr TLPs and correlate them with an NVMe command.
  • Debugging: use IOMMU fault logs, AER and NVMe status to localize a DMA failure.
  • Validation: design tests for unaligned buffers, large transfers, PRP list boundaries and IOMMU on/off configurations.

20.4 Story and analogies

🧒 Kid analogy

The teacher (CPU) could carry every book from the library to the classroom herself — but then she can't teach. Instead she writes a request slip, puts it in the request box, and rings a bell. The librarian (NVMe controller) comes over, reads the slip, walks to the classroom tables (RAM) and puts the books exactly on the table numbers written on the slip. When finished, the librarian puts a note in the answer box and taps the teacher's shoulder (interrupt). The teacher never carried a book.

🌍 Real-world analogies

Courier with a delivery manifest: the warehouse (host) prepares a manifest (descriptor) listing pick-up and drop-off addresses, possibly several drop-off points for one order (scatter-gather). The courier (DMA engine) does the driving. Gated community with a guard (IOMMU): the courier carries a visitor pass listing which houses it may enter; the guard translates "House 7 on my pass" to the real street address and turns the courier away from houses not on the pass.

🧩 Where the analogy breaks

(1) The librarian does not "walk into" RAM — the controller requests memory transactions which the Root Complex performs against the memory system; the controller never sees DRAM directly. (2) For a read from host memory, data comes back as completions, possibly split into several CplD TLPs, and may arrive in a different order from requests with different tags. (3) The guard can also cache passes in the courier's pocket (ATS) — and then revoking a pass needs an explicit invalidation round-trip.

20.7 Protocol view: what DMA looks like on PCIe

  • Device reads host memory: the controller sends a non-posted MRd (Requester ID = the controller's BDF, Tag, Address = DMA address, Length ≤ MRRS). The Root Complex reads memory and returns one or more CplD TLPs with Completer ID, the same Tag, a Byte Count and Lower Address so the requester can reassemble. Completions may be split at Read Completion Boundary (RCB, 64 or 128 bytes) aligned points, and each completion's payload is limited by MPS. verified
  • Device writes host memory: the controller sends posted MWr TLPs, each with payload ≤ MPS and not crossing a 4 KiB address boundary. No completion. verified
  • Device raises an interrupt: MSI-X is also an MWr — to the message address from the table entry with the message data. On x86 the address is in the FEEx_xxxxh range the Root Complex interprets as an interrupt impl (architecture-specific).
  • Ordering: posted writes from the device are not passed by later posted writes (unless Relaxed Ordering is set and permitted), and a completion cannot pass a posted write in the same direction by default. This is why a controller can write data (MWr), then the CQE (MWr), then the MSI-X (MWr), and the host is guaranteed to see the data before it sees the CQE — if Relaxed Ordering is not applied to the CQE write verified. The NVMe controller is responsible for using attributes that preserve this guarantee.
TLPs_for_write_data ≈ ⌈ transfer_bytes / MPS ⌉ (plus extra splits at 4 KiB boundaries)   |   MRd_requests ≈ ⌈ transfer_bytes / MRRS ⌉
  • transfer_bytes — bytes the controller moves for one command.
  • MPS — Max_Payload_Size in Device Control (e.g. 256 B).
  • MRRS — Max_Read_Request_Size in Device Control (e.g. 512 B).

Example: a 128 KiB NVMe read with MPS 256 B produces about 512 MWr TLPs of read-data; a 128 KiB NVMe write with MRRS 512 B produces about 256 MRd requests, answered by roughly 512 CplD (if the RC returns 256-byte completions — RC completion sizing is implementation-dependent). derived

20.9 IOMMU, mapping and isolation

An Input-Output Memory Management Unit (IOMMU) sits between PCIe and the memory system in the Root Complex. For each incoming request it identifies the device (by Requester ID, optionally PASID), looks up that device's translation tables (a "domain"), translates the IOVA to a physical address and checks permissions. Untranslatable or forbidden requests are blocked and reported as faults; the device typically sees an error completion (for reads) or the write is dropped impl (exact behaviour is platform-specific).

  • Why: isolation (a buggy or malicious device cannot scribble over the kernel), virtualization (assign a device to a VM whose "physical" addresses are guest addresses), and addressing (devices with narrow DMA masks reach high memory).
  • Linux modes: translated DMA (default on many distributions), passthrough/identity (iommu=pt — DMA address equals physical address for host drivers), or IOMMU disabled. The NVMe driver code is identical in all modes because it uses the DMA API impl.
  • Cost: map/unmap per I/O and IOTLB misses add latency and CPU cost; IOTLB invalidation strategies (strict vs lazy/flush-queue) trade safety for speed.
#!/usr/bin/env python3
"""Toy IOMMU SIMULATION: one flat IOVA->physical page table per device (Requester ID).
Real IOMMUs (Intel VT-d, AMD-Vi, Arm SMMU) use multi-level tables, caches (IOTLB),
and permission bits; this keeps only the idea. All addresses are synthetic."""
PAGE = 4096

class ToyIommu:
    def __init__(self):
        self.domains = {}                       # requester_id -> {iova_page: (phys_page, perms)}
        self.faults = []
    def map(self, rid, iova, phys, length, perms):
        dom = self.domains.setdefault(rid, {})
        for off in range(0, length, PAGE):
            dom[(iova + off) // PAGE] = ((phys + off) // PAGE, perms)
    def unmap(self, rid, iova, length):
        for off in range(0, length, PAGE):
            self.domains.get(rid, {}).pop((iova + off) // PAGE, None)
    def translate(self, rid, iova, is_write):
        entry = self.domains.get(rid, {}).get(iova // PAGE)
        need = "w" if is_write else "r"
        if entry is None or need not in entry[1]:
            self.faults.append((rid, iova, "write" if is_write else "read"))
            return None                          # request is blocked; the device sees an error
        return entry[0] * PAGE + iova % PAGE

io = ToyIommu()
NVME_RID = 0x0100                                # 01:00.0
# Driver maps a 3-page buffer that is physically scattered (an sg list):
for i, phys in enumerate([0x7_3A21_5000, 0x1_0F00_2000, 0x4_4410_9000]):
    io.map(NVME_RID, 0xFFFF_0000 + i * PAGE, phys, PAGE, "rw")
for iova in (0xFFFF_0000, 0xFFFF_1010, 0xFFFF_2FFF):
    print(f"device MWr to IOVA {iova:#x} -> phys {io.translate(NVME_RID, iova, True):#x}")
io.unmap(NVME_RID, 0xFFFF_1000, PAGE)            # driver unmapped too early (bug)
print("after early unmap:", io.translate(NVME_RID, 0xFFFF_1010, True))
print("other device using NVMe's IOVA:", io.translate(0x0400, 0xFFFF_0000, False))
for rid, iova, kind in io.faults:
    print(f"FAULT rid={rid >> 8:02x}:{(rid >> 3) & 0x1f:02x}.{rid & 7} {kind} iova={iova:#x}")

Output:

device MWr to IOVA 0xffff0000 -> phys 0x73a215000
device MWr to IOVA 0xffff1010 -> phys 0x10f002010
device MWr to IOVA 0xffff2fff -> phys 0x444109fff
after early unmap: None
other device using NVMe's IOVA: None
FAULT rid=01:00.0 write iova=0xffff1010

The simulation demonstrates the two classic IOMMU faults: a use-after-unmap by the device that owns the mapping (driver unmapped a buffer before the device finished — a real and serious bug), and a different device presenting an address that was never mapped for it (isolation working as intended).

20.9.1 ATS, PRI and PASID

Address Translation Services (ATS), an optional PCIe extended capability (ID 000Fh), lets a device ask the IOMMU (the Translation Agent) for a translation in advance and cache it in a device-side Address Translation Cache (ATC). The device then issues requests marked as already translated, saving IOMMU lookup latency. Software must invalidate the ATC when it changes mappings — an Invalidate Request message to the device, answered by an Invalidate Completion verified. Page Request Interface (PRI) lets a device request that missing pages be made resident (for shared-virtual-memory style use), and Process Address Space ID (PASID) tags requests with an address-space identifier so one function can serve several address spaces. Whether a given NVMe SSD implements ATS/PRI/PASID is implementation-dependent; it is uncommon in mainstream SSDs but appears in some data-centre and virtualization-focused designs. Capability discovery applies — check for the extended capabilities before assuming.

⚠️ Security note

Translated requests bypass the IOMMU lookup on the trusted assumption that the device's ATC is honest and up to date. Platforms therefore treat enabling ATS as a trust decision; Linux can refuse ATS for devices marked untrusted (e.g. externally exposed ports) impl.

20.10 Hardware view: coherency and attributes

  • Snooping: on most x86 platforms DMA is cache-coherent: device writes invalidate/update CPU caches and device reads see the latest CPU-written data. Many Arm platforms are also coherent for PCIe, but not all — the DMA API inserts cache maintenance where needed impl.
  • No Snoop attribute (TLP attribute bit, enabled by Device Control "Enable No Snoop"): tells the Root Complex it may skip snooping for that request. Only safe when software guarantees the data is not in CPU caches. Platforms may ignore it.
  • Relaxed Ordering attribute: allows a write to pass earlier writes. Good for bulk data, dangerous for the CQE that signals the data is complete — hence controllers must not apply it where ordering matters.
  • DMA mask: the number of address bits the device can generate. NVMe controllers use 64-bit addresses; drivers set a 64-bit mask, and the platform may still restrict addresses (IOMMU aperture, bounce buffers).

💡 Senior insight

In a DMA failure, ask "whose address was it?" before "what went wrong?". Every DMA address in an NVMe trace was produced by host software and handed to the controller through a structure you can inspect (ASQ/ACQ registers, Create Queue commands, the SQE, PRP lists). Trace the address back to the structure that delivered it, then to the code that wrote that structure. The controller is usually just the messenger.

20.13 Worked example: how many TLPs?

Problem: NVMe write of 64 KiB, buffer 4 KiB-aligned, MPS 256 B, MRRS 512 B, RCB 64 B, Root Complex returns completions of up to 256 B on 256 B boundaries synthetic. Count PCIe TLPs for data, excluding SQE/CQE/interrupt.

Solution: MRd requests = 64 KiB / 512 B = 128. Each 512 B read returns as 2 × 256 B CplD → 256 CplD. Total data-related TLPs = 384 (128 upstream MRd + 256 downstream CplD). Plus 1 SQE MRd + 1 CplD, 1 PRP-list MRd + CplD(s) (16 pages → PRP2 points to a list of 15 entries = 120 bytes), 1 CQE MWr, 1 MSI-X MWr, 2 doorbell MWr. derived

20.14 Common mistakes

  • Saying "the SSD reads RAM" without naming the MRd/CplD, the Requester ID, and the IOVA.
  • Putting virt_to_phys() results in PRPs instead of DMA-API addresses.
  • Touching a streaming buffer from the CPU while the device owns it.
  • Assuming coherency on every platform.
  • Unmapping buffers in timeout paths before the controller is disabled or the command is known aborted.
  • Thinking NVMe "read" generates MRd from the device for data (it generates MWr).

🧪 Lab 20.3 — Advanced: extend the toy IOMMU SAFE

🧪 Lab 20.4 — Senior forensic: trace 20.D SAFE

Write a root-cause hypothesis ranking with the evidence needed to confirm each, and a fix-verification plan.

Model answer

Rank (a) IOMMU-blocked read highest given the matching fault address; confirm by mapping the IOVA back to the driver's command (CID → PRP) and checking whether it was mapped at that time; (b) RC stall — would affect other devices too; check other devices' latency; (c) link loss — rejected by absence of link errors. Fix verification: after correcting the mapping lifetime, run the same workload with strict IOTLB invalidation and DMA debugging; expect zero faults and zero completion timeouts over a long soak.

Quiz

  1. Which TLP carries data for an NVMe Read command?

    Answer

    MWr from the controller to host memory.

  2. What must be true in the Command register before the controller can DMA?

    Answer

    Bus Master Enable (bit 2) = 1.

  3. Why are SQ/CQ rings allocated coherent while data buffers are streaming?

    Answer

    Rings are shared concurrently for the queue's lifetime; data buffers are owned by the device for one transfer and handed back.

  4. What does ATS add, and what new obligation does it create?

    Answer

    Device-side caching of translations; software must invalidate the device's ATC when mappings change.

  5. Why does the host see read-data before the CQE?

    Answer

    PCIe ordering: posted writes in the same direction are not reordered by default, so data MWr arrive before the CQE MWr if the controller does not use Relaxed Ordering for the CQE.

Interview questions

  1. Beginner Why does DMA exist?
    Model answer

    To move bulk data without consuming CPU cycles on slow device accesses; the device's engine moves data while the CPU does other work.

  2. Beginner What is scatter-gather?
    Model answer

    Describing one transfer as multiple memory segments, because buffers are rarely physically contiguous; NVMe uses PRP lists or SGLs.

  3. Intermediate What is an IOVA?
    Model answer

    An I/O virtual address that the device uses and the IOMMU translates to a physical address, per device domain.

  4. Intermediate List every DMA for an NVMe 4 KiB read.
    Model answer

    SQE fetch (MRd/CplD), data MWr (4 KiB split by MPS), CQE MWr, MSI-X MWr. No PRP list (single page).

  5. Advanced How can an IOMMU reduce NVMe performance and what mitigations exist?
    Model answer

    Map/unmap CPU cost and IOTLB misses add latency; mitigations: passthrough for trusted host drivers, lazy invalidation (flush queues), larger pages, ATS where supported, batching.

  6. Senior A customer reports silent data corruption only with IOMMU disabled. How do you proceed?
    Model answer

    Hypothesis: a stray DMA (late write after unmap, wrong PRP) that the IOMMU normally blocks; enable the IOMMU in strict mode to convert silent corruption into faults with addresses; correlate fault IOVA with command history; check driver timeout/abort paths and PRP list construction; validate with DMA API debug; only then consider device firmware.

20.17 Summary, further reading and next

DMA moves data by device-initiated memory transactions: MRd/CplD to read host memory, MWr to write it, MWr for interrupts. NVMe makes the controller the bus master for commands, PRP lists, data, completions and interrupts; the host only rings doorbells. The addresses the controller uses are DMA addresses, possibly translated by an IOMMU, possibly cached by ATS. Buffer lifetime and ordering are where the hard bugs live.
