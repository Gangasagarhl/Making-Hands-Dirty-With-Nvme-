Specification Reading School

The NVMe Base Specification, the command-set and transport specifications, and the PCI Express Base Specification together run to thousands of pages. Nobody reads them like a novel. Senior engineers read them like lawyers read statutes and like detectives read evidence: they know which words are binding, which are explanation, which fields are reserved for the future, which behaviour is left to the implementer, and which revision a sentence came from. This Part teaches that skill explicitly — with a keyword guide, procedures for reading registers, commands and state machines, a revision-diff method, a cross-specification matrix and a reusable worksheet — so that you never again cite a forum post where a "shall" should be.

30.1 Why this chapter exists

Most protocol misunderstandings in industry are not caused by ignorance of a fact but by a misreading: a "should" treated as a "shall", a 0-based field read as 1-based, a reserved bit assumed to be zero on read, a sentence from an informative note quoted as a requirement, a field that changed meaning between revisions, or a behaviour assumed to be standard when it is explicitly implementation-specific. Each of these produces wrong drivers, wrong firmware, wrong tests and wrong root causes. Reading discipline is cheaper than any of them.

  • Beginner: distinguish normative from informative text and interpret shall / should / may, reserved, obsolete and vendor-specific.
  • Intermediate: decode a register table, a command format and an error table using a repeatable procedure; maintain a field dictionary.
  • Advanced: read a state machine and turn it into a diagnostic tree; map a concept across Base, command-set, transport and PCIe documents.
  • Senior: read revision changes and derive interoperability and validation consequences; write source notes that state what a source does and does not establish.
  • Trace-analysis: link every decoded trace field to the table that defines it (trace mapping).
  • Debugging: recognise when a debate is really about an ambiguous or version-dependent sentence, and resolve it with the primary source.
  • Validation: turn each normative sentence into a test card (Chapter 29).

Prerequisites: controller registers (CAP, CC, CSTS), the 64-byte Submission Queue Entry and 16-byte Completion Queue Entry (CQE), and the PCIe Transaction Layer (TLP). The validation chapter (29) motivates why precise reading matters.

30.2 Story, analogy, and where it breaks

🧒 Kid analogy — the board-game rule book

A new board game comes with a thick rule book. Some sentences are rules ("You must roll before moving"). Some are tips ("You should keep your gold hidden"). Some are choices ("You may trade with a neighbour"). Some boxes are greyed out: "Reserved for the expansion pack" — you must not put anything there, because the expansion will use it. Some pages are stories about how the game was invented; fun, but not rules. When friends argue, you settle it by pointing at the exact rule sentence — and checking it is the same edition of the rule book everyone is using.

🌍 Engineering analogy — building codes

A building code contains mandatory requirements, recommended practices, informative commentary and referenced standards. An inspector cites the clause and edition. A contractor who builds to the commentary instead of the clause, or to last decade's edition, fails inspection. A specification works the same way: it binds conformance claims, not opinions.

🧩 Where the analogy breaks

Game rules and building codes are written for humans in a single domain. Protocol specifications bind two or more independent implementers (host and device, requester and completer), and many sentences are written from one side's viewpoint ("the controller shall…", "host software should…"). A requirement on the controller does not automatically imply a requirement on the host, and vice versa. Also, a specification frequently delegates to another specification (NVMe to PCIe), so the answer may live in a document the first one only references.

30.7 Reading a register

  1. Locate the register (document, offset, which space: PCI config space, BAR0 MMIO, or a capability structure).
  2. Identify width (32/64-bit) and whether it must be accessed atomically or as two halves.
  3. Identify the reset value and which reset sets it.
  4. Decode each field: bits, name, meaning, units, 0-based or not.
  5. Classify access type (RO, RW, RW1C, RWS, HwInit, …) only as stated in the table legend — never by guess.
  6. Identify side effects of reads and writes (e.g. a doorbell write starts work; a write-1-to-clear clears status).
  7. Identify sequencing rules (must be written before/after another register, only while disabled).
  8. Identify related registers and capability gates.
  9. Identify the software owner (who writes it: driver, firmware, BIOS).
  10. Identify hardware behaviour (what the controller does on change).
  11. Identify trace implications (what TLP and timing you expect).

Worked example: Controller Configuration (CC, offset 14h)

Bits31:252423:2019:1615:1413:1110:76:43:10
FieldReservedCRIME versionIOCQESIOSQESSHNAMSMPSCSSReservedEN

Applying the procedure: (1) BAR0 offset 14h, 32-bit verified. (4) EN enables the controller; CSS selects the I/O command set(s); MPS gives memory page size 2^(12+MPS); AMS selects the arbitration mechanism; SHN requests shutdown (01b normal, 10b abrupt); IOSQES/IOCQES give I/O queue entry sizes as powers of two (6 → 64 bytes, 4 → 16 bytes). (5) Read the access legend for each field in your revision. (7) Sequencing: several fields are only to be changed while the controller is disabled — read the exact rule. Bit 24 is an example of version dependence: older revisions show it reserved; later revisions define it (Controller Ready Independent of Media Enable) — so a driver written to an older revision writes 0 there, which must remain a valid, backward-compatible choice. (11) Trace: a single 1-DW MWr to BAR0+14h; enabling is followed by CSTS polling reads.

⚠️ Do not invent access semantics

If a table legend says a field is RW, do not assume it is readable back with the same value under all conditions, and do not assume the write takes effect immediately. If you cannot find the statement, write "unknown" in your field dictionary.

30.8 Reading a command definition

  1. Identify the command set (Admin, NVM, ZNS, KV, …) and owning document.
  2. Identify the opcode.
  3. Identify the command format (common 64-byte SQE plus command-specific dwords).
  4. Identify mandatory fields.
  5. Identify optional fields and the capability that gates each.
  6. Identify data pointers (PRP or SGL per PSDT; metadata pointer) and direction.
  7. Identify namespace applicability (NSID used? broadcast value allowed?).
  8. Identify prerequisites (feature enabled, namespace attached, controller state).
  9. Identify completion content (DW0/DW1 command-specific results).
  10. Identify errors (generic and command-specific status codes).
  11. Identify side effects (log pages updated, asynchronous events, state changes).
  12. Identify trace consequences (SQE fetch, data direction, CQE, interrupt).

30.9 Reading a state machine

  1. List the states.
  2. Identify each state's entry condition.
  3. Identify each exit condition.
  4. Identify events that cause transitions.
  5. Identify timers.
  6. Identify error transitions.
  7. Identify recovery paths.
  8. Map each state/transition to trace evidence.
  9. Identify impossible transitions (they become assertions in your analyzer scripts).
  10. Build a diagnostic tree.

Worked example: controller shutdown handshake

30.10 Reading tables, bitfields, error tables and references

Tables: read the caption, every column header, every footnote, and the sentences immediately before and after; a table often defines structure while a nearby sentence defines a condition ("this field is valid only if…"). Bitfields: record bits, width, units, 0-based-ness, reset value, attribute; then write one positive and one boundary test. Error tables: NVMe status is a pair (Status Code Type, Status Code) plus flags (More, Do Not Retry); generic status codes (SCT 0h) apply to many commands; command-specific codes (SCT 1h) are only meaningful for the command that defines them; media and data-integrity errors are SCT 2h; path-related SCT 3h; vendor specific SCT 7h verified. Read the conditions under which each code is returned, not just the name. References: when the text says "see …" or refers to another document, follow it and record the chain in your cross-reference map — a requirement may only be complete after two hops.

📭 What the specification does not say

It does not tell you how long a particular controller takes to become ready (only the bound it reports), how firmware schedules internal work, how a protocol analyzer displays things, or how fast a product is. It also does not interpret itself: when two sentences seem to conflict, the specification's own errata and later revisions — or the standards body — resolve it, not a forum thread.

🏭 Implementation-dependent

"This behaviour may vary by controller, firmware, driver, OS, platform, or analyzer." To establish it for a given system you need: the exact versions of each, repeated measurements, the Identify data that bounds it, and preferably a link-level trace.

Objective: classify ten sentences from the Base specification's queue-management text as shall/should/may, identify who is bound and under which condition. Solution

Quiz

  1. A sentence says "the controller should complete the command within X". Is exceeding X a spec violation?

    Answer

    No — "should" is a recommendation; it is a finding, and may be a product-requirement failure if your PRD adopts X.

  2. NLB = 0 in a Read command means how many blocks?

    Answer

    One (0's based).

  3. Difference between RsvdP and RsvdZ?

    Answer

    RsvdP: preserve the read value when writing (read-modify-write). RsvdZ: write zero.

  4. Why is "obsolete" not the same as "reserved"?

    Answer

    Obsolete marks something that once had meaning; old implementations may still use it, so it is not freely reusable and new hosts must tolerate it.

  5. Which document defines the doorbell stride and doorbell register offsets for PCIe-attached controllers?

    Answer

    The NVMe register map (CAP.DSTRD and doorbell offsets) — in the 2.x library the PCIe-specific register mapping is in the NVMe over PCIe Transport specification, while doorbell semantics are in the Base specification; check how your revision splits it version.

  6. What does AER mean in the NVMe document vs the PCIe document?

    Answer

    NVMe: Asynchronous Event Request (admin opcode 0Ch). PCIe: Advanced Error Reporting capability.

Interview questions

  1. Beginner What is the difference between normative and informative text?
    Model answer

    Normative text defines conformance requirements; informative text (notes, examples, overviews, rationale) explains but does not bind.

  2. Beginner How should software treat reserved fields?
    Model answer

    Write them with the value the conventions require (typically 0), do not depend on their value when reading, and never store private meaning in them; check the document's conventions for the exact rule.

  3. Intermediate Walk me through reading a new admin command definition.
    Model answer

    The 12-step command procedure: set, opcode, format, mandatory/optional fields and gates, data pointers, namespace use, prerequisites, completion content, errors, side effects, trace consequences.

  4. Intermediate How do you avoid off-by-one bugs from specifications?
    Model answer

    Mark 0-based fields and units in the field dictionary; write boundary tests at 0 and max; review code with the dictionary.

  5. Advanced Two engineers disagree about whether a controller may return a status in a situation. How do you resolve it?
    Model answer

    Find the normative sentences (both sides), check revision, conventions, footnotes and referenced sections; record what the source establishes and does not; if still ambiguous, check errata/later revisions or escalate to the standards body; meanwhile make the host tolerant of both.

  6. Advanced How do you convert a state diagram into analyzer assertions?
    Model answer

    List impossible transitions and timer bounds; encode each as a rule over observed register reads or packets; flag violations as candidate first abnormal events.

  7. Senior How would you onboard a team to a new specification revision?
    Model answer

    Revision-diff workshop (added/changed fields, behaviour, errors, interoperability, validation impact), update field dictionaries and command matrices, flag driver/firmware code touching changed areas, add tests, and document "what we do not yet know".

  8. Senior What does a good source note contain?
    Model answer

    Document, revision, topic, verification date, what it establishes, and explicitly what it does not establish.

30B Cross-Specification Mapping, Revisions and the Limits of a Specification

📘 Specification baseline

DOCUMENTS: the NVM Express library (Base 2.4; NVM CS 1.3; ZNS 1.5; KV 1.4; SLM 1.3; Computational Programs 1.3; PCIe transport 1.4; RDMA 1.3; TCP 1.3; NVMe-MI 2.2; Boot 1.4) and the PCIe Base Specification version. STATUS: per the course brief (set released 4 August 2026); confirm each sub-revision on nvmexpress.org. SOURCE NOTES: the matrix below states which document covers each concept — derived from the published scope of each document — not specific section numbers.

30B.1 Why this chapter exists

No single document defines an NVMe read on a PCIe SSD. The Base specification defines the queue model and command processing; the NVM Command Set defines Read; the PCIe transport specification defines how the controller's registers and doorbells map onto a PCIe function; the PCIe Base specification defines the packets that actually carry everything; the operating system defines what software does. Engineers who confuse these owners cite the wrong document, test the wrong thing, and argue past each other.

  • Map any NVMe/PCIe concept to the documents that own it, and refuse to populate a cell no source covers.
  • Apply the six-point revision-diff method and derive validation consequences.
  • State what a specification does not guarantee, and what evidence would establish implementation-dependent behaviour.
  • Verify a new release's highlighted features without inventing details.

Prerequisites: Chapter 30.

🧒 Kid analogy — the school with many rule books

A school has a school rule book (how classes work), a maths department book (how maths tests are marked), a bus company book (how the bus to school runs) and a city traffic code (how every vehicle on every road behaves). "How do I get my maths test back?" touches all four. If you only read the maths book, you will never learn why the bus was late.

🧩 Where the analogy breaks

School rule books rarely conflict; protocol documents are layered so that the lower one (PCIe) knows nothing about the upper (NVMe). A PCIe completion timeout is a PCIe event; the NVMe command timeout that follows is a host-driver policy. Neither document defines the other.

30B.3 What the specification does not say, and implementation-dependent behaviour

📭 What the specification does not guarantee
  • Internal NAND management algorithms (garbage collection, wear levelling, read-retry).
  • Proprietary firmware scheduling and internal queue arbitration beyond the defined arbitration mechanisms.
  • Undocumented controller optimisations (prefetch, write coalescing).
  • Protocol-analyzer user-interface behaviour, decode naming, or timestamp methods.
  • Vendor-specific performance, latency, or power numbers beyond what the device reports.
  • How many TLPs a given transfer is split into (bounded by MPS, MRRS, page boundaries; the exact split is the device's choice).
  • Operating-system timeouts, retry policies, and recovery escalation.

30B.4 Version control rule and revision awareness

Never describe a modern feature as if it existed in an older revision; never use an old command layout as though it were necessarily current. The largest structural change to learn is the move from NVMe 1.x (one monolithic document including the PCIe register interface and NVM I/O commands) to the 2.0 library, which separated the Base specification from command-set specifications (NVM, ZNS, KV, …) and transport specifications (PCIe, RDMA, TCP) version. Older references to "the NVMe spec, section X" therefore often point to material that now lives in a different document.

The revision-diff method

  1. Added feature — what new capability exists, which capability bit or field advertises it, which document owns it.
  2. Changed field — new fields in formerly reserved space; widened fields; renamed fields; new encodings in existing fields.
  3. Changed behaviour — a "may" that became "shall", new conditions, new ordering rules.
  4. Changed error handling — new status codes, new conditions for existing codes, new log pages or events.
  5. Changed interoperability implication — what an old host does with a new device (writes 0 to the new field; ignores new events) and what a new host does with an old device (must check capability before using).
  6. Changed validation requirement — tests added, retired (obsolete), or modified.

The script below diffs two field dictionaries that you built from two revisions (sample content is synthetic and refers to an invented register, so nothing in it asserts real specification text):

#!/usr/bin/env python3
"""revdiff.py - diff two field dictionaries you built from two spec revisions
(executable, stdlib only). The dictionaries are YOUR notebook entries; the sample
content is SYNTHETIC (invented register 'XREG') so nothing here asserts real spec text."""
OLD = {  # "register.field": (bits, attribute, meaning)
    "XREG.EN":   ("0",     "RW", "enable"),
    "XREG.MODE": ("3:1",   "RW", "mode select; 000b/001b defined"),
    "XREG.RSV":  ("31:4",  "reserved", ""),
}
NEW = {
    "XREG.EN":   ("0",     "RW", "enable"),
    "XREG.MODE": ("3:1",   "RW", "mode select; 000b/001b/010b defined"),
    "XREG.LIM":  ("7:4",   "RW", "rate limit (new)"),
    "XREG.RSV":  ("31:8",  "reserved", ""),
}

def diff(old, new):
    rows = []
    for k in sorted(set(old) | set(new)):
        a, b = old.get(k), new.get(k)
        if a is None:
            rows.append(("ADDED", k, b, "new field: old hosts write 0 here (was reserved) -> check default behavior"))
        elif b is None:
            rows.append(("REMOVED", k, a, "field gone/obsolete: new devices may ignore it -> retire tests"))
        elif a != b:
            what = [n for n, x, y in zip(("bits", "attr", "meaning"), a, b) if x != y]
            rows.append(("CHANGED", k, (a, b), f"changed {what}: interoperability + new negative tests"))
    return rows

if __name__ == "__main__":
    for kind, key, val, impl in diff(OLD, NEW):
        print(f"{kind:<8} {key:<10} -> {impl}")

    Model answer
