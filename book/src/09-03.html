PART XXXVIII

Scenario Interviews

Scenario interviews hand you a symptom and watch how you think. There is no single correct answer; there is a correct method: establish facts, locate the first abnormal event, reason layer by layer (application → driver → NVMe queues → PCIe transaction → data link → physical → device internals), propose hypotheses ranked by likelihood and cost-to-test, and name the evidence that would confirm or eliminate each. Each scenario below gives the interviewer prompt, what a strong candidate does, red flags that sink candidates, and a model answer. All traces are synthetic teaching material.

38.1 Fourteen Layered-Reasoning Scenarios

38.1.1 Why this chapter exists

Isolated facts do not debug systems. Real failures cross layers: a signal-integrity problem appears as an NVMe timeout; a driver bug appears as a PCIe Unsupported Request; a power-state bug appears as a Completion Timeout. These scenarios train the habit of descending and ascending the stack deliberately.

38.1.2 Learning objectives

  • Apply the layered model to fourteen common symptom classes.
  • Write hypothesis tables with discriminating evidence.
  • Recognise red-flag behaviours in yourself: premature conclusions, single-layer thinking, unlabelled certainty.

Prerequisites: Part XIII (End-to-end NVMe over PCIe), Part XV (Error handling), Part XVI (Power & reset), and the Advanced/Senior interview banks (37.3, 37.4).

🧒 Kid analogy

When a letter never arrives, you don’t just blame the postman. You check: did you write the right address, did you post it, did the post office receive it, did the van leave, did it reach the town, did the neighbour take it by mistake? A good detective checks each step in order and asks for proof at each step.

🧩 Where the analogy breaks

Letters travel one way. NVMe I/O involves both directions many times (doorbell down, fetch up, completion down, data up, CQE up, interrupt up), and the “post office” (PCIe) retries corrupted packets automatically at the Data Link Layer, so some failures are silently repaired and leave only counters behind.

38.1.3 The layered reasoning ladder

38.1.4 Scenario 1 — Stable at Gen4, unstable at Gen5

🧠 Interviewer prompt

“An NVMe SSD works perfectly when the BIOS forces Gen4. At Gen5 it shows occasional I/O errors and once fell off the bus. What do you investigate?”

What a strong candidate does

  • Recognises the most probable domain: Physical/Data Link — doubling the rate halves the unit interval and shrinks eye margin; but does not stop there.
  • Asks for correctable AER counts at both ends at Gen4 vs Gen5 (Receiver Error, Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover).
  • Asks whether a retimer, riser, cable or backplane is in the path and checks its firmware and configuration.
  • Examines equalization: did Gen5 equalization phases complete, which presets were chosen, does the link frequently enter Recovery? (LTSSM capture.)
  • Uses lane margining at the receiver (where supported, PCIe 4.0+) to quantify margin per lane.
  • Correlates with temperature (thermal changes channel loss and device behaviour).
  • Keeps device-side Gen5 bugs in the list: the controller’s Gen5 PHY or the firmware’s handling of Recovery events.

Red flags: “Gen5 is just unstable, use Gen4” without data; blaming NVMe firmware without examining link errors; assuming no AER messages means no link problems (correctable errors may be masked or not reported to the OS).

Plan: (1) enable and read AER correctable counters at root port and device; (2) capture with an analyzer/interposer qualified for Gen5 — confirm the interposer itself does not change behaviour; (3) lane margining per lane; (4) swap the device to a known-good slot, swap a known-good device into this slot; (5) temperature sweep; (6) if margin is insufficient, the fix is in the platform channel or retimer tuning; if margin is fine and the controller hangs after Recovery, it is a device bug. Workaround while investigating: cap at Gen4 (Target Link Speed), with the bandwidth cost documented.

38.1.5 Scenario 2 — The controller receives the command, the host never receives completion

🧠 Interviewer prompt

“The analyzer shows the doorbell and the SQE fetch. The host never sees a completion and times out after 30 seconds. Where is the bug?”

What a strong candidate does: splits the remaining pipeline into checkpoints — (a) did the controller move data (MWr to PRP for read / MRd for write)? (b) was a CQE MWr written? to which address? with what phase and CID? (c) was an MSI-X MWr sent? to which address/data? (d) did the host process the vector? Identifies that each checkpoint’s presence or absence on the trace localises the fault.

Red flags: “The SSD firmware hung” without checking for the CQE; ignoring that the CQE might be present but wrong (phase, CQ address, CID); forgetting about MSI-X masking and interrupt routing.

Model answer

Data moved (row 4), CQE was written (row 5) and an interrupt was sent (row 6). The first abnormal event is row 5: the CQE address does not match the driver’s CQ 2 base. Two possibilities: the device used the wrong CQ (e.g. SQ 2 was created bound to CQ 1 — check the Create I/O SQ command’s CQID field in the admin trace) or the driver’s record of CQ base addresses is wrong (e.g. it reallocated CQ memory after a reset but the controller still holds the old base — impossible without recreation unless the reset path skipped queue recreation). The CQE at 0x1_0410_0290 = slot 41 of a CQ at 0x1_0410_0000 — which matches CQ 1’s base in the driver’s table synthetic. So Create I/O SQ for SQ 2 specified CQID 1 while the driver expects CQ 2 and armed vector 2. Row 6 is then consistent: the controller signalled the vector associated with CQ 1 (confirm by finding which MSI-X table entry holds message data 0x4023); the CQ 1 handler found an entry whose SQID (2) and CID it did not expect, or found nothing because it was not polling that CQ. Root cause class: host driver queue-mapping bug (Strong evidence pending confirmation of the Create I/O SQ CDW11). Fix: correct CQID assignment; regression test: verify every Create I/O SQ’s CQID against the intended map.

38.1.6 Scenario 3 — AER reports Completion Timeout

🧠 Interviewer prompt

“dmesg shows an AER Uncorrected (Non-Fatal) error, Completion Timeout. What does it mean and what do you do?”

What a strong candidate does: asks which device reported it (the requester) — root port or NVMe endpoint; explains that the requester is the one whose non-posted request did not get a completion; uses the AER header log if present; checks the configured completion-timeout range (Device Control 2) and whether timeout is even enabled; correlates time with NVMe events (resets, power-state changes, firmware activation).

Red flags: treating Completion Timeout as a cause; not knowing that the reporter is the requester; assuming the device is at fault when the device reported it.

Model answer
ReporterWhose request was lostNVMe meaningTop hypotheses
NVMe endpointDevice MRd to host memorySQE fetch, PRP list fetch, or write-data fetch never completedIOMMU block with no completion; root complex completion drop; host memory hang; switch bug; device tag reuse confusion
Root portCPU MMIO read to device (or config read)Driver read of CSTS/CAP or a BAR register unansweredDevice hung or in D3/reset; link went down (look for Surprise Down / DLL state change); device firmware busy beyond timeout during activation

Steps: decode AER (dmesg, journalctl -k; sysfs aer counters if available); identify the reporter BDF; get the header log; check LnkSta (link up?), CSTS (all ones?); check device logs after recovery; reproduce with analyzer triggered on the AER message (ERR_NONFATAL Msg) and look backwards for the request with the matching tag. Root cause is whatever prevented the completion — Completion Timeout is the observed symptom. Note: Linux AER recovery may reset the link, which then triggers NVMe controller reset — order of events matters.

38.1.7 Scenario 4 — Works at QD1, fails at QD128

🧠 Interviewer prompt

“The device passes every test at queue depth 1. At queue depth 128 we get timeouts within minutes.”

What a strong candidate does: lists everything that scales with concurrency — outstanding tags, flow-control credits, CQ occupancy, SQ wrap, CID space, controller internal resources, interrupt rate and coalescing, host CPU, PRP list memory pool, thermal load. Checks queue sizing first (QD128 on a 128-entry queue is impossible: max outstanding is size−1). Checks the CQ size relative to SQs sharing it.

Red flags: “the drive can’t handle load”; no attempt to find the threshold QD; ignoring host-side resources.

Model answer

First, bisect the QD to find the threshold (e.g. fails at ≥ 64). A threshold that is a power of two near a resource size is a strong clue: 32 → AHCI-like internal limit or 5-bit tag bug; 64 → CQ size; 256 → 8-bit tag wrap (10-bit tags enabled but completer mishandles?); 1024 → queue size. Then check: (1) queue configuration — SQ/CQ sizes, CQ shared by many SQs (CQ overflow stall); (2) CID allocation — duplicates across outstanding commands on the same SQ (host bug) cause the controller or host to mismatch completions; (3) analyzer: count outstanding device MRds without CplD (tag exhaustion/aliasing); (4) thermal — QD128 heats the drive; throttling should slow, not fail; (5) host — PRP pool exhaustion leading to allocation failure paths. A synthetic but classic finding: the driver allocates CIDs modulo 64 while allowing 127 outstanding, producing duplicate CIDs; the host completes the wrong request and the real one times out. Evidence: two outstanding SQEs with the same CID on the same SQ in the trace.

38.1.8 Scenario 5 — Only large I/O fails

🧠 Interviewer prompt

“4 KiB and 64 KiB transfers work. 1 MiB transfers fail with Data Transfer Error or time out.”

What a strong candidate does: identifies size-dependent mechanisms: PRP list usage (≥ 3 pages) and chained list pages (more than 512 entries for 4 KiB pages — 2 MiB+), MDTS limit (Identify Controller Maximum Data Transfer Size, in units of CAP.MPSMIN pages, 2^MDTS), SGL descriptor segments, MRRS splitting, DMA mapping limits, IOMMU segment boundaries, and controller buffer limits.

Red flags: not knowing MDTS; assuming bandwidth/timeout without checking size thresholds.

Model answer

Find the exact threshold by sweeping sizes (4 KiB steps near the boundary). Then: (1) compare with MDTS: if MDTS = 5 with 4 KiB MPSMIN, max transfer is 128 KiB; a 1 MiB command sent directly via passthrough exceeds it and should fail with Invalid Field — the Linux block layer splits normal I/O to respect MDTS, so a failure through the block layer suggests a different cause. (2) PRP list threshold: transfers needing a PRP list (more than two pages) — check list contents on the analyzer (device MRd of the list page and the returned entries). (3) Chained PRP lists: for > 512 entries the last entry of a list page points to the next list page — a classic host bug writes a data pointer there or the device mis-handles chaining. (4) IOMMU mapping: large buffers mapped as multiple segments; a bug in merging can produce a wrong address mid-transfer → DMAR fault → device sees UR/CA → Data Transfer Error. The first abnormal event is likely a CplD with non-success status or an IOMMU fault for an address in the middle of the buffer — correlate the address with PRP entries.

38.1.9 Scenario 6 — Reads work, writes time out

🧠 Interviewer prompt

“Read-only workloads run for days. Any write workload times out within an hour.”

What a strong candidate does: notes the PCIe asymmetry — writes make the device issue non-posted MRds for host data and depend on CplDs flowing downstream; reads make the device issue posted MWrs. Also notes device-side asymmetry: write cache, GC, program failures, write protection, thermal from programs, Flush handling.

Red flags: “writes are slower so they time out”; ignoring namespace write protection or read-only modes (SMART critical warning bit for read-only).

Model answer

Two branches. Transport branch: check device-side AER for Completion Timeout and analyzer for MRds lacking CplDs; examine MRRS, tag settings (try disabling 10-bit tags), IOMMU faults on write buffers, and root-complex completion handling. Device branch: SMART critical warning (read-only mode, spare below threshold), namespace write protection state, write-cache settings and Flush latency, GC stalls on a full drive (does the problem disappear after deallocating/sanitizing on a test unit?), firmware assertion on program failure (telemetry). Discriminating experiment: write with tiny transfers (512 B / 4 KiB) vs large; with and without volatile write cache; with fresh vs full drive; with reduced MRRS. If MRRS reduction fixes it, transport; if fill level matters, device.

38.1.10 Scenario 7 — Errors only after resume from a low-power state

🧠 Interviewer prompt

“After system suspend/resume, or after the drive idles for a few minutes, the first I/O times out and the controller resets. Otherwise it is stable.”

What a strong candidate does: distinguishes the power mechanisms involved — system S3/S0ix (driver suspend/resume path, possibly D3cold), PCIe D3hot, ASPM L1/L1.x, NVMe power states via APST — and designs experiments that toggle each independently. Checks restored state: BARs, MSI-X table, Command register, AER/ASPM/LTR config, NVMe features (APST, HMB re-enable, queue recreation).

Red flags: lumping all “sleep” into one concept; not knowing that D3hot→D0 may reset function state (No_Soft_Reset); ignoring HMB (Host Memory Buffer) that must be re-enabled correctly.

Capture the resume with an analyzer triggered on the PMCSR write or the LTSSM L1 exit; look for the first MMIO read after resume and its completion status. A typical root cause class: function state not restored after D3cold — the MSI-X table returns to defaults, so CQEs are posted but interrupts go nowhere (Strong evidence when the CQ has entries and /proc/interrupts shows no increment).

38.1.11 Scenario 8 — AER immediately before an NVMe controller reset

🧠 Interviewer prompt

“Logs show an AER error and, 2 ms later, the NVMe driver resets the controller. Which caused which?”

What a strong candidate does: refuses to infer causality from order alone; notes that AER recovery itself can initiate resets (link reset, slot reset callbacks to the driver), that an NVMe controller fatal condition can cause the device to stop responding (leading to root-port Completion Timeout AER), and that both may share a third cause (power event, link Recovery). Asks for timestamps with resolution, the AER type, the reporter, and whether the reset was AER-initiated (error recovery path) or timeout-initiated.

Red flags: “AER happened first, so AER caused the reset” or the reverse without evidence; not checking which code path performed the reset.

Model answer

Build a timeline with all clocks aligned: kernel log, AER messages, NVMe driver messages, analyzer capture (with a host marker). Classify: (a) AER-initiated recovery — kernel logs the AER, calls driver error_detected, resets link/slot, driver resets controller in slot_reset/resume: AER cause is upstream (the reset is a consequence). (b) NVMe timeout-initiated reset — driver logs a timeout first (the timeout started 30 s earlier!), and the AER is a Completion Timeout on the root port from the driver’s CSTS read to a hung device: the controller hang is the earlier event. (c) Common cause — link went into Recovery or down due to power/SI, producing both. The order in which messages print within 2 ms is not reliable evidence; look for the earliest abnormal event, which may be 30 s earlier (the I/O that later timed out).

38.1.12 Scenario 9 — Device disappears after firmware activation

🧠 Interviewer prompt

“We ran Firmware Commit with immediate activation. The drive vanished from lspci until a power cycle.”

Strong candidate: distinguishes activation without reset vs activation requiring Conventional/NVM Subsystem reset; checks commit action used, FRMW capabilities, MTFA; considers link retraining during activation (Surprise Down if hot-plug surprise not supported), the image itself (bad build, wrong slot), and host handling (driver removed the device after link down and did not rescan).

Red flags: “firmware bug” without checking whether rescanning the bus restores the device; not knowing about firmware slots and fallback.

Model answer

Check: did the root port see Surprise Down / DLL Link Active cleared? Try echo 1 > /sys/bus/pci/rescan on a test system (CAUTION) — if the device returns, the link re-trained but the OS did not re-enumerate: host/platform hot-plug handling issue. If the link never trains (no Detect), the device is not coming up: firmware image or activation bug — use firmware slot information after power cycle to see which image is active; test the same image with reset-based activation. Report the commit action, previous/new firmware, MTFA, and whether the platform supports hot-plug on that port.

38.1.13 Scenario 10 — Throughput halves after a BIOS update

🧠 Interviewer prompt

“After a BIOS update, sequential read throughput dropped from 6.8 GB/s to 3.4 GB/s on all drives.”

Strong candidate: exact halving suggests a link change — speed Gen4→Gen3 or width x4→x2; or MPS dropped (e.g. 512→128 changes efficiency but rarely exactly halves); or bifurcation changed; or NUMA/IOMMU settings changed. Checks LnkSta, DevCtl MPS/MRRS, IOMMU mode (strict vs lazy invalidation) and C-states.

Model answer

lspci -vvv LnkSta on device and root port; DevCtl MaxPayload/MaxReadReq; compare with pre-update saved output (always save baseline). Gen4 x4 practical ≈ 7 GB/s vs Gen3 x4 ≈ 3.5 GB/s derived — 3.4 GB/s matches a Gen3 link. Confirm LnkCtl2 Target Link Speed set by BIOS, or a changed equalization setting causing fallback. If link is unchanged, check IOMMU strict mode (map/unmap cost), interrupt routing, and CPU frequency policy. Report with before/after config dumps.

38.1.14 Scenario 11 — Silent data corruption, no errors anywhere

🧠 Interviewer prompt

“An application checksum detects corrupted 4 KiB blocks about once a day. No AER, no NVMe errors, SMART clean.”

Strong candidate: treats it as highest severity; looks for patterns in corrupted data (stale data, zeros, data from another LBA, shifted by an offset, data from a different buffer); considers ordering (CQE before data — Relaxed Ordering), buffer lifetime (host reused buffer before completion), PRP offset errors, cache coherency issues on non-coherent DMA platforms, device FTL mapping bugs, and memory errors on host.

Model answer

Classify the corrupt content: (a) stale old version of the same LBA → write lost (volatile cache + power events? FTL?) or read raced a write; (b) another LBA’s data → FTL mapping or host submitted wrong SLBA (check via block trace); (c) zeros/partial → DMA incomplete when host consumed (ordering/RO, or host consumed after timeout/abort); (d) data shifted by N bytes → PRP1 offset handling bug. Enable end-to-end PI if the format supports it to localise where corruption enters; add host-side tracing of buffer addresses and LBAs; test with RO disabled; run memory diagnostics. Without PI, the device cannot know data is wrong — so “no errors” is expected and is not exculpatory.

38.1.15 Scenario 12 — SR-IOV VF in a VM times out; PF on host is fine

🧠 Interviewer prompt

“The VM using a virtual function sees I/O timeouts; the host using the physical function is fine on the same drive.”

Strong candidate: checks secondary-controller resource assignment (flexible queue and interrupt resources, controller online state), the VF’s MSI-X with interrupt remapping (posted interrupts), IOMMU mappings for guest memory (DMAR faults with VF RID), VF FLR handling when VMs reboot, and noisy-neighbour arbitration.

Model answer

Host-side IOMMU fault logs filtered by the VF’s BDF are the first check — they distinguish DMA translation problems from device-side scheduling. Then interrupt delivery (guest’s /proc/interrupts, host interrupt remapping logs), then VF controller state (secondary controller list via Identify on the PF; VQ/VI resources assigned). Compare with the same guest using an emulated controller to isolate VF-specific behaviour. Typical root-cause classes: guest memory not pinned/mapped for a range used by PRP lists; MSI-X vectors exceeding VI resources; VF FLR not waiting long enough before re-init.

38.1.16 Scenario 13 — Failures only behind a PCIe switch

🧠 Interviewer prompt

“Drives directly attached are fine. Behind a switch in a JBOF, under heavy mixed load, several drives time out simultaneously.”

Strong candidate: simultaneous failures of several drives point to a shared component — switch upstream port, upstream link, switch firmware, power — rather than individual drives. Looks at switch port error counters, upstream link AER, DPC triggers, credit starvation upstream, oversubscription (sum of drive bandwidth vs upstream width).

Model answer

Timeline across all affected drives; switch logs and AER at each switch port; analyzer on the upstream link (where all traffic converges). If a DPC event or upstream link Recovery coincides, the shared path is implicated. Test reduced load, fewer drives, different upstream speed. Common fault classes: switch completion handling under P2P/ACS settings, upstream link SI, switch firmware credit bug. Report with “Strong evidence” only once a single shared abnormal event is located.

38.1.17 Scenario 14 — Namespace vanishes after namespace management

🧠 Interviewer prompt

“After creating a second namespace and attaching it, the first namespace’s block device disappeared on one host of a dual-host system.”

Strong candidate: reasons about controller vs namespace attachment, per-controller attachment lists, Namespace Attribute Changed asynchronous events, Changed Namespace List log, and host rescan behaviour; checks whether the NSID was reused or detached on the wrong controller ID.

Model answer

Check the Namespace Attachment command used (controller list contents) and Identify with CNS for attached controllers; read the Changed Namespace List log on both hosts; check the AER (asynchronous event) completion and whether the host rescanned. A common class: management tool detached NSID 1 from controller X instead of attaching NSID 2, due to wrong controller ID; or host rescan logic dropped a namespace whose Identify temporarily failed. Evidence: admin command log (nvme-cli history, device persistent event log if supported).

💡 Senior insight

Across all fourteen scenarios, the winning move is the same: name the checkpoint list, and look for the first one that fails. The interviewer is watching whether you localise before you explain.

Pick three scenarios. For each, write a one-page hypothesis table with at least five rows, each with supporting evidence, eliminating evidence, cost to test (minutes/hours/days) and confidence label. Then order the tests by information gained per hour.
