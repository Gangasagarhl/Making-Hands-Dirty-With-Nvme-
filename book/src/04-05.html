34 FLUSH

📘 Source notes

Official specification: NVM Command Set Specification (Flush command) and NVMe Base Specification (Identify Controller VWC, Volatile Write Cache feature FID 06h). Revision: NVM CS 1.3 / Base 2.4 baseline. Establishes: Flush opcode 00h; that Flush commits data and metadata held in a volatile write cache to non-volatile media; NSID usage including broadcast where supported. Does not establish: how long a Flush takes, how a controller schedules it relative to other I/O, or whether a power-loss-protected drive does any work at all — those are impl.

34.1 Why this chapter exists

Flush is the shortest NVMe command (no data, no fields beyond NSID) and the most misunderstood. Databases, filesystems and hypervisors build their crash-consistency on it. Misunderstanding what it guarantees leads to either lost data (trusting completions that were only cached) or terrible performance (flushing on every write on a drive that does not need it).

34.2 Learning objectives

  • Beginner: explain what a volatile write cache is and what Flush does to it.
  • Intermediate: state precisely which writes a Flush covers and which it does not.
  • Advanced: map Linux REQ_PREFLUSH/REQ_FUA to NVMe Flush and FUA; explain when the block layer drops flushes.
  • Senior: reason about durability across multiple queues, namespaces and controllers; design a power-loss test.
  • Trace/debug/validation: identify Flush in a trace, measure its cost, and test that durability claims hold.

Prerequisites: Ch 33 (completion semantics), Ch 31.

🧒 Kid analogy — the homework tray

The teacher has an "in-tray" on her desk. When you hand in homework, she says "got it!" and drops it in the tray — fast. Later she files it in the big locked cabinet. If the school catches fire before filing, the tray burns. "Flush" is when you say: "please file everything that's in your tray right now into the cabinet, and tell me when you're done".

🧩 Where the analogy breaks

(1) Homework handed in while she is filing may or may not be included — Flush only promises what was already completed when you asked. (2) Some teachers have a fireproof tray (power-loss protection): Flush then has nothing to do. (3) The cabinet is per-namespace; a Flush for one namespace says nothing about another, unless you use the broadcast NSID.

📭 What the spec does not say

How long a Flush may take, whether it blocks other I/O, whether the controller flushes the whole cache or only the namespace's dirty data, and how a PLP device implements it. These are why Flush cost differs by 1000× across drives.

34.5 Architecture — who acts

 Application   fsync()/fdatasync()/O_DSYNC
     │
 Filesystem    journal commit: write log blocks → REQ_PREFLUSH | REQ_FUA on commit block
     │
 Block layer   blk-flush state machine: if queue is "write back": issue PREFLUSH as separate
     │         flush request; FUA passed if device supports it, else emulated with POSTFLUSH;
     │         if "write through": flush/FUA flags dropped
 NVMe driver   REQ_OP_FLUSH → SQE opcode 00h, NSID;  REQ_FUA → Write CDW12 bit 30
     │
 Controller    drain volatile cache for namespace → NAND program → update mapping persistently
     │
 CQE           success → data safe

Linux behaviour verified in principle; function names and flag handling evolve across kernel versions version.

34.6 Performance consequences

  • On a consumer drive with a large volatile cache, a Flush may need to program megabytes of data: milliseconds. An fsync-heavy workload (databases with synchronous commit, VMs with cache=none and barriers) becomes flush-bound.
  • On a PLP enterprise drive (VWC=0), Linux marks the queue write through; no Flush is sent; fsync cost is just the write latency.
  • Flush cost is roughly proportional to dirty cache content impl; frequent small flushes may each be cheap; rare large flushes expensive.
  • Flushes do not stop other queues' reads in the specification, but some controllers deprioritise or stall other I/O while draining impl — visible as read latency spikes coinciding with fsync.

35 Dataset Management (Deallocate / TRIM)

📘 Source notes

Specification: NVM Command Set (Dataset Management command 09h, range format, DLFEAT in Identify Namespace; DSM limits in NVM-command-set-specific Identify Controller in newer revisions version). Establishes: command layout, range format, attributes (AD, IDW, IDR), read behaviour of deallocated blocks reported by DLFEAT. Does not establish: when the FTL actually reclaims space, the performance effect, or whether deallocation is immediate.

35.1 Why this chapter exists

An SSD cannot know a file was deleted — the filesystem just changes its own metadata. Without being told, the FTL keeps copying dead data during garbage collection, increasing write amplification, wearing NAND and slowing writes. Dataset Management with the Deallocate attribute (the NVMe equivalent of ATA TRIM / SCSI UNMAP) tells it. Misusing it causes performance stalls; misunderstanding its read-back semantics causes data-integrity bugs in software that assumed zeros.

35.2 Learning objectives

  • Beginner: explain why the SSD needs to know about deleted data.
  • Intermediate: encode a DSM command with N ranges and build the range list.
  • Advanced: explain DLFEAT, deallocated-read semantics and Write Zeroes vs DSM.
  • Senior: design a discard policy (online discard vs periodic fstrim) and diagnose discard-induced latency.
  • Trace/debug/validation: decode DSM in a trace including its 4 KiB payload fetch; test deallocate behaviour.

Prerequisites: Ch 31, Ch 33 (GC, WA).

🧒 Kid analogy — the moving company

A warehouse keeps your boxes. Every so often it must empty a room by moving every box that is still yours to another room. If you threw away half your toys but never told them, they carefully move broken toys forever. DSM-deallocate is a note: "boxes on shelves 100–355 are rubbish; don't bother moving them".

🧩 Where the analogy breaks

The note is advisory: the warehouse may throw the boxes out now, later, or partially. And if you later ask "what's on shelf 120?", the answer depends on the warehouse's stated policy (DLFEAT): maybe empty (zeros), maybe "unspecified" — not necessarily your old toy.

35.4 Code — build a DSM range list

#!/usr/bin/env python3
"""dsm_ranges.py - build and decode a Dataset Management range list (offline)."""
import struct

def build(ranges, ad=True):
    """ranges: list of (slba, nlb_count, context_attributes)."""
    assert 1 <= len(ranges) <= 256, "1..256 ranges per DSM command"
    buf = b"".join(struct.pack("<IIQ", ca, n, slba) for slba, n, ca in ranges)
    cdw10 = len(ranges) - 1                 # NR is 0-based
    cdw11 = (1 << 2) if ad else 0           # AD = Attribute - Deallocate
    return cdw10, cdw11, buf

def decode(buf):
    for i in range(len(buf) // 16):
        ca, n, slba = struct.unpack_from("<IIQ", buf, i * 16)
        print(f"  range {i}: SLBA={slba:#x} length={n} LBAs  CA={ca:#010x}")

if __name__ == "__main__":
    # free three extents of a deleted file (4 KiB LBAs)
    cdw10, cdw11, buf = build([(0x10000, 256, 0), (0x48000, 2048, 0), (0x90010, 16, 0)])
    print(f"CDW10={cdw10:#010x} (NR={cdw10 + 1} ranges)  CDW11={cdw11:#010x} (AD=1)")
    print(f"payload {len(buf)} bytes, pointed to by PRP1:")
    for off in range(0, len(buf), 16):
        print(f"  {off:04x}: " + " ".join(f"{b:02x}" for b in buf[off:off + 16]))
    decode(buf)

35.5 Semantics and the FTL

  • What deallocation does: the controller may mark the mapping entries for those LBAs as unmapped and the corresponding physical pages as invalid impl.
  • Reads afterwards: governed by DLFEAT in Identify Namespace: bits 2:0 report whether deallocated blocks read as not reported/unspecified, all zeros, or all ones; DLFEAT also indicates whether Write Zeroes with DEAC is supported and guard field behaviour verified. If the namespace enables Deallocated or Unwritten Logical Block Error (DULBE, a feature), reads return 2/87h instead.
  • Guarantee: DSM deallocate is a hint about data you no longer need. If you need zeros, use Write Zeroes (with DEAC) and check DLFEAT — or write zeros.
  • Impact on GC: invalid pages need not be copied; WA falls, especially on nearly full drives. Example: block with 256 pages, 200 valid → GC copies 200; after trimming 150 of them → copies 50. derived
  • Performance: deallocation is metadata work. Large or frequent DSM commands can delay concurrent I/O on some controllers; Linux therefore offers online discard mount option vs periodic fstrim (batched, scheduled) impl.
  • Limits: max 256 ranges per command; per-range and per-command size limits may be reported (DMRL, DMRSL, DMSL) in newer revisions version. Linux exposes discard_max_bytes, discard_granularity in sysfs.

35.6 Hardware and protocol view

On the wire a DSM looks like a small write: doorbell → SQE fetch → controller MRd of the range list (48 bytes for 3 ranges, up to 4 KiB) → CQE. No user data moves. Everything interesting is internal and invisible to the analyzer; only latency (and later GC behaviour) is observable.
