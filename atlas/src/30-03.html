III.3 Host Timers in Linux v7.2: Timeouts, Retries, Resets and Reconnects

The NVMe and PCIe specifications say what the device promises. The Linux host decides how long it will actually wait, and what to do afterwards. Every value in this chapter is impl Linux v7.2 behaviour, read from drivers/nvme/host/*.c, block/blk-mq.c and drivers/pci/pci.c; other operating systems and other kernel versions differ.

⚠️ Changing timeouts

Writing to these files is safe in the sense that it cannot damage the drive, but on a production system a shorter timeout turns slow-but-successful commands into resets, and a longer one turns a hung device into a hung application. Change them on test machines; record the original values first.

T-21Missed interrupt: completion found only by pollingDegradedLinux host / interrupts
In a PEX trace
Visible Interval = CQE MWr → MSI-X MWr (should be microseconds unless coalescing is set). A CQE MWr with no MSI-X MWr (or an MSI-X MWr to the wrong address/data) and a CQ head doorbell MWr only ~30 s later proves a missed interrupt. Host-side IRQ handling is not visible.
What happens
The controller posted the CQE and (maybe) sent the MSI-X message, but the host never ran the completion handler. The command sits "in flight" until the timeout handler polls the CQ and finds it.
How it shows up
Linux v7.2: I/O tag N (CID) QID Q timeout, completion polled. The command succeeds, but 30 s late. No reset.
Spec basis
NVMe over PCIe: MSI-X vector per CQ, interrupt coalescing (Feature 08h), INTMS/INTMC registers for pin/MSI. PCIe: MSI-X is a posted MWr to the address in the MSI-X table.
Typical causes
MSI-X table or address programmed wrong (e.g. after a VM migration or IOMMU remap); interrupt remapping fault; CPU hot-unplug with vector affinity; device bug that writes the CQE but skips the MSI-X write; interrupt coalescing that never fires because the threshold is not reached and the timer is broken.
How to detect / prove
Count "completion polled" lines in dmesg; check /proc/interrupts for the nvme queue vector not incrementing; IOMMU fault messages (DMAR: ... fault). On an analyzer, find the CQE MWr and check for the following MSI-X MWr to the APIC address range.
Linux v7.2 source
pci.c:nvme_timeout(): nvme_poll() for polled queues or nvme_poll_irqdisable(); if blk_mq_rq_state(req) != MQ_RQ_IN_FLIGHT afterwards, logs "completion polled" and returns BLK_EH_DONE.
Test to provoke it
Mask the queue's MSI-X vector through a debug interface, or use QEMU and drop interrupts in the model; with a short io_timeout the message appears. SAFE in a VM.
T-22I/O command timeout: poll, Abort, then resetTimer onlyLinux host / nvme-pci
In a PEX trace
Partly visible The ladder is visible packet by packet: doorbell MWr → (no CQE) → Abort SQE fetch at +io_timeout → CC.EN=0 MWr at +2×io_timeout. The host's CQ polling reads only host memory and is not on the link.
What happens
An I/O command passes its block-layer deadline (io_timeout, 30 s). Linux escalates: check for a dead or offline device, poll the CQ, send an NVMe Abort, and on the second expiry reset the controller.
How it shows up
I/O tag N (CID) opcode 0x.. (Name) QID Q timeout, aborting req_op:... size:..., then possibly ... timeout, reset controller. If PCI error recovery is in progress (pci_channel_offline()), the timer is simply re-armed. If CSTS.CFS=1 or NSSRO is set, the driver resets at once with controller is down; will reset: CSTS=0x..., PCI_STATUS=0x....
Spec basis
Host policy; NVMe Abort and controller reset are spec mechanisms used by the policy.
Typical causes
Any device stall (see T-01); a firmware bug affecting a specific opcode or LBA; Completion Timeouts on the device's DMA (T-33); a device that is in a long internal operation (GC, T-48) exceeding 30 s.
How to detect / prove
dmesg timeout lines (tag, CID, opcode, QID, size); nvme error-log; AER status of the device and Root Port for the same time window; tracepoints nvme:nvme_setup_cmd and nvme:nvme_complete_rq to measure per-command latency before the failure.
Linux v7.2 source
block/blk-mq.c:blk_mq_timeout_work() → blk_mq_rq_timed_out() → pci.c:nvme_timeout(); helpers nvme_should_reset(), nvme_warn_reset(), abort_endio(), nvme_dev_disable(), nvme_try_sched_reset(). Timeout value set by core.c:nvme_alloc_io_tag_set() (NVME_IO_TIMEOUT).
Test to provoke it
echo 2000 > /sys/class/nvme/nvme0/io_timeout on a test box, then generate long commands (e.g. very large Write Zeroes or Verify ranges on a slow device) to see the ladder quickly. CAUTION: resets interrupt other I/O.
T-23Admin command timeout: immediate controller resetTimer onlyLinux host / nvme-pci
In a PEX trace
Visible Admin doorbell MWr (SQ0 tail, BAR0+1000h) → no CQE → MWr CC EN=0 about admin_timeout later; no Abort in between distinguishes admin from I/O timeouts.
What happens
Any command on the admin queue (QID 0) that exceeds admin_timeout (60 s) causes a controller reset straight away; Linux never sends an Abort for an admin command.
How it shows up
I/O tag N (CID) opcode 0x.. (Name) QID 0 timeout, reset controller. Typical opcodes: Format NVM (0x80), Sanitize (0x84), Firmware Commit (0x10), Get Log Page of a large telemetry log (0x02), vendor-specific commands.
Spec basis
Host policy.
Typical causes
Long synchronous admin commands; controller stuck in an internal operation; a firmware path that blocks the admin queue while background work runs.
How to detect / prove
QID 0 in the timeout message. For tools: pass an explicit timeout (nvme ... --timeout=<ms>) for long operations.
Linux v7.2 source
pci.c:nvme_timeout(): if (!nvmeq->qid || (iod->flags & IOD_ABORTED)) → reset. Admin timeout configured in core.c:nvme_alloc_admin_tag_set() (NVME_ADMIN_TIMEOUT); changeable through sysfs admin_timeout (sysfs.c:nvme_admin_timeout_store()).
Test to provoke it
See T-11. EXPERT when the command is destructive.
T-24Retry budget exhausted (max_retries)ReportedLinux host / nvme-core
In a PEX trace
Visible The same command (same opcode/SLBA/NLB in the SQE payload) fetched repeatedly with new CIDs; CQE status DNR bit visible; count retries and spacing between them.
What happens
Retryable errors (DNR=0) and cancelled commands after a reset are retried. After max_retries (5) attempts, or immediately when DNR=1, the error reaches the block layer and the application.
How it shows up
An application I/O error; kernel NVMe error log line with the final status; sysfs command_retries_count and command_error_count per namespace increase.
Spec basis
NVMe Base: DNR bit, CRD field. Retry count is host policy.
Typical causes
Repeated resets (each reset cancels and retries all in-flight commands); a namespace that stays not-ready (T-18); transient transport errors on fabrics.
How to detect / prove
cat /sys/block/nvme0n1/device/../nvme0n1/command_retries_count (path varies; find with find /sys -name command_retries_count); tracepoint nvme:nvme_complete_rq prints retries.
Linux v7.2 source
core.c:nvme_decide_disposition() (retries >= nvme_max_retries), nvme_retry_req(), nvme_cancel_request() (sets NVME_SC_HOST_ABORTED_CMD on reset).
Test to provoke it
Inject errors with drivers/nvme/host/fault_inject.c (debugfs directory per disk with status and dont_retry files plus the standard fault-attr controls); clear dont_retry to watch retries. SAFE.
T-25Timeout while the controller is resetting or connectingTimer onlyLinux host / nvme-pci
In a PEX trace
Visible Reset sequence visible (CC EN=0/EN=1, AQA/ASQ/ACQ writes, Identify/Set Features/Create queue SQEs); the admin SQE that never gets a CQE, then CC writes stop and config/MMIO traffic ceases as the host disables the device.
What happens
A command (often an admin command issued during re-initialisation) times out while the controller is already in RESETTING or CONNECTING. The host cannot reset again, so it gives up on the controller.
How it shows up
I/O tag N (CID) QID Q timeout, disable controller (CONNECTING or DELETING); the controller is marked for deletion and the namespaces disappear. During RESETTING the timer is just re-armed.
Spec basis
Host policy.
Typical causes
Device fails during its own recovery: Identify or Create I/O Queue never completes after a reset; flaky link that drops again during re-init.
How to detect / prove
dmesg sequence: a reset, then "timeout, disable controller", then the device node vanishes (nvme list).
Linux v7.2 source
pci.c:nvme_timeout() state switch: NVME_CTRL_CONNECTING → change to DELETING, nvme_dev_disable(dev, true); NVME_CTRL_RESETTING → BLK_EH_RESET_TIMER. For fabrics, tcp.c:nvme_tcp_timeout() and rdma.c:nvme_rdma_timeout() complete the request immediately when not LIVE.
Test to provoke it
Make the device fail a second time during reset (vendor hook or QEMU model). CAUTION.
T-26Multipath failover delayed by the full timeoutDegradedLinux host / multipath
In a PEX trace
Not visible Path switch happens in the host; a PCIe trace of one path shows its I/O stopping and, if you probe the second path (dual-port drive or second drive), the same LBAs resuming. Measure the gap between the last CQE on path A and the first SQE fetch on path B.
What happens
With native NVMe multipath, a path-related status (SCT 3h) fails over immediately. A path that simply stops answering gives no status, so failover waits for the command timeout (and for fabrics, the transport's error recovery).
How it shows up
I/O pauses for about io_timeout (30 s) — or KATO / transport detection time on fabrics — then continues on the other path. multipath_failover_count in sysfs increases. No application error.
Spec basis
NVMe Base: path-related status codes (Host Path Error 370h, Host Aborted Command 371h, ANA statuses 301h–303h).
Typical causes
Hung path rather than failed path; long io_timeout chosen for single-path use left in place on multipath systems.
How to detect / prove
Latency log shows a gap equal to the timeout when one path is pulled; dmesg timeout on the failed path followed by successful I/O. Compare iopolicy (numa, round-robin, queue-depth) behaviour.
Linux v7.2 source
core.c:nvme_decide_disposition() returns FAILOVER for REQ_NVME_MPATH with nvme_is_path_error(); multipath.c:nvme_failover_req() moves the bios to the head's requeue list and kicks nvme_requeue_work(); cancelled requests carry NVME_SC_HOST_ABORTED_CMD (a path error) so they fail over after a reset.
Test to provoke it
Two-port NVMe-oF setup; block one path with iptables -j DROP (not REJECT) and measure the I/O gap. SAFE in a lab.
T-27All paths gone: I/O queued, then failed (or held forever)Timer onlyLinux host / multipath
In a PEX trace
Not visible Host queueing is not on the wire; the trace only shows silence. Use dmesg and sysfs counters.
What happens
When no path is usable, the multipath head either fails I/O immediately or queues it. Queued I/O waits for a path to return, for delayed_removal_secs, or for every controller to be deleted (ctrl_loss_tmo).
How it shows up
Applications block in D state; after the hold time, I/O errors. sysfs io_fail_no_available_path_count increases.
Spec basis
Host policy.
Typical causes
Network outage longer than expected; all controllers in CONNECTING with failfast not expired; misconfigured ctrl_loss_tmo=-1 (reconnect forever).
How to detect / prove
nvme list-subsys shows all paths connecting or missing; hung-task warnings in dmesg; sysfs counters above.
Linux v7.2 source
multipath.c:nvme_available_path() treats LIVE, RESETTING and CONNECTING controllers as available unless NVME_CTRL_FAILFAST_EXPIRED is set; otherwise nvme_mpath_queue_if_no_path() (driven by delayed_removal_secs) decides.
Test to provoke it
Disconnect all target ports and watch blocked tasks; vary fast_io_fail_tmo. SAFE in a lab.
T-28Fabrics controller lost: reconnect loop ends (ctrl_loss_tmo) or fails fastTimer onlyLinux host / NVMe-oF
In a PEX trace
Not visible Fabrics reconnects are network events; use a packet capture (TCP SYN/ICReq spacing = reconnect_delay).
What happens
After a transport error the host reconnects every reconnect_delay seconds. After ctrl_loss_tmo it gives up and deletes the controller. If fast_io_fail_tmo is set, queued I/O is failed after that time even while reconnects continue.
How it shows up
Reconnecting in 10 seconds... repeated; finally Removing controller (N).... With fast_io_fail_tmo: failfast expired and queued I/O fails with a host path error.
Spec basis
NVMe over Fabrics: association, Connect command. Timer values are host policy.
Typical causes
Target down longer than ctrl_loss_tmo (default 600 s); authentication failure (no retry); Connect rejected with DNR.
How to detect / prove
dmesg | grep -E "Reconnecting|Removing controller|failfast"; sysfs ctrl_loss_tmo, reconnect_delay, fast_io_fail_tmo for the controller.
Linux v7.2 source
fabrics.c:nvmf_parse_options(): max_reconnects = DIV_ROUND_UP(ctrl_loss_tmo, reconnect_delay), warns failfast tmo (N) larger than controller loss tmo (M); fabrics.c:nvmf_should_reconnect() (no reconnect on DNR or key rejection); tcp.c:nvme_tcp_reconnect_or_remove(); core.c:nvme_failfast_work(), nvme_fail_nonready_command(). Defaults in fabrics.h: NVMF_DEF_RECONNECT_DELAY 10, NVMF_DEF_CTRL_LOSS_TMO 600, NVMF_DEF_FAIL_FAST_TMO -1.
Test to provoke it
nvme connect -t tcp ... --ctrl-loss-tmo=30 --reconnect-delay=5 --fast_io_fail_tmo=10, then stop the target for 60 s. SAFE in a lab.
T-29NVMe/TCP or RDMA request timeout triggers error recoveryTimer onlyLinux host / NVMe-oF
In a PEX trace
Not visible NVMe/TCP or RDMA PDUs are on the network, not the PCIe link; use a packet capture (CapsuleCmd without CapsuleResp for io_timeout).
What happens
On fabrics there is no Abort escalation: a request timeout in LIVE state starts transport error recovery, which tears down all queues and reconnects.
How it shows up
I/O tag N (CID) type T opcode 0x.. (Name) QID Q timeout (TCP) followed by reconnect messages; all in-flight I/O is retried or failed over.
Spec basis
NVMe over Fabrics / NVMe/TCP transport; host policy.
Typical causes
Target stall; lost PDU; network partition shorter than KATO but longer than io_timeout.
How to detect / prove
dmesg; packet capture showing a command capsule without a response capsule.
Linux v7.2 source
tcp.c:nvme_tcp_timeout() → nvme_tcp_error_recovery() → nvme_tcp_error_recovery_work(); when not LIVE, nvme_tcp_complete_timed_out(). RDMA: rdma.c:nvme_rdma_timeout(), nvme_rdma_error_recovery(). FC: fc.c:nvme_fc_timeout().
Test to provoke it
Drop only response packets for one queue with a targeted firewall rule. SAFE in a lab.
T-30TLS handshake does not complete in time (NVMe/TCP)Timer onlyLinux host / NVMe-oF
In a PEX trace
Not visible TLS handshake is network traffic; use a packet capture.
What happens
With TLS-secured NVMe/TCP, the in-kernel handshake upcall must finish within tls_handshake_timeout. If not, the connect attempt fails and the reconnect loop continues.
How it shows up
Connect failure with a timeout error; repeated "Reconnecting in N seconds".
Spec basis
NVMe/TCP transport TLS support; timeout is host policy.
Typical causes
tlshd user-space daemon not running or slow; key lookup failing; network latency.
How to detect / prove
dmesg and tlshd logs; /sys/module/nvme_tcp/parameters/tls_handshake_timeout.
Linux v7.2 source
tcp.c: tls_handshake_timeout (default 10 s) used as tmo = tls_handshake_timeout * HZ and args.ta_timeout_ms.
Test to provoke it
Stop tlshd and attempt a TLS connect. SAFE.
T-31Device needs a delay before CSTS.RDY is checked (quirk)Timer onlyLinux host / quirks
In a PEX trace
Visible Interval = MWr CC EN=0 → first CSTS MRd: ~2.3 s of silence with the quirk, immediate polling without it; then the RDY transition as in T-04.
What happens
Some controllers misbehave if the host reads CSTS.RDY immediately after clearing CC.EN. Linux works around them with a fixed 2.3 s sleep. A new device with the same bug but without the quirk fails reset or initialisation.
How it shows up
Without the quirk: reset fails (Device not ready; aborting reset) or the controller hangs. With the quirk: every reset is 2.3 s slower.
Spec basis
Not a spec feature; a workaround for non-compliant behaviour.
Typical causes
Firmware that cannot handle register reads during reset.
How to detect / prove
Compare reset time with and without the quirk using the nvme.quirks=VID:DID:delay_before_chk_rdy module parameter (prefix the name with ^ to disable a built-in quirk), parsed in pci.c.
Linux v7.2 source
nvme.h: NVME_QUIRK_DELAY_BEFORE_CHK_RDY, NVME_QUIRK_DELAY_AMOUNT 2300 ("found empirically" for PCI_DEVICE(0x1c58, 0x0003)); used in core.c:nvme_disable_ctrl(). pci.c ID table applies it to e.g. HGST and WDC SN200 adapters, Memblaze Pblaze4, Samsung PM1725/PM1725a, Seagate Nytro; core.c applies it by model string to "Samsung Portable SSD X5".
Test to provoke it
On a device that needs it, load nvme with quirks=VID:DID:^delay_before_chk_rdy and run nvme reset. CAUTION.
T-32Host stall mistaken for device timeoutDegradedLinux host / platform
In a PEX trace
Partly visible The trace proves the device side: CQE MWr and MSI-X MWr on time, but the host's CQ head doorbell MWr (and the next SQ doorbells) arrive late. The cause in the host (lockup, VM pause) is not visible.
What happens
The device completed on time, but the host could not process the completion: CPU soft lockup, interrupts disabled for seconds, VM paused or migrated, NUMA memory pressure. The NVMe timeout fires anyway.
How it shows up
NVMe timeout messages, often with "completion polled" (T-21), accompanied by soft-lockup or RCU-stall warnings, or a VM pause in the hypervisor log. The device's own logs show nothing.
Spec basis
None; host behaviour.
Typical causes
Long critical sections in other drivers; hypervisor steal time; firmware SMI storms (System Management Interrupts) on x86 platforms.
How to detect / prove
Correlate timeouts with watchdog: BUG: soft lockup, rcu: INFO: rcu_sched detected stalls, hypervisor steal time (top "st"), perf sched. An analyzer shows the CQE and MSI-X were sent on time.
Linux v7.2 source
Same paths as T-21/T-22; the driver cannot tell host stalls from device stalls.
Test to provoke it
Pause a VM (virsh suspend) for longer than io_timeout during I/O and resume it. SAFE.

III.3.3 PCI core waits that NVMe depends on

Before the NVMe driver can read CAP, the PCI core must decide that the function is ready. Linux v7.2 implements these waits in drivers/pci/pci.c; their failure modes are cards in chapter III.4:

  • pci_dev_wait() polls with exponential back-off (1, 2, 4, ... ms). Past PCI_RESET_WAIT (1000 ms) it logs not ready Nms after FLR; waiting, may try pcie_failed_link_retrain() on the upstream bridge, and gives up after the caller's timeout — PCIE_RESET_READY_POLL_MS = 60000 ms for FLR and D3hot→D0 — with not ready Nms after ...; giving up.
  • pcie_flr() waits for pending transactions, sets Initiate FLR, sleeps 100 ms (unless Immediate Readiness is set), then calls pci_dev_wait().
  • pci_bridge_wait_for_secondary_bus() handles waits after a bus reset or D3cold: 100 ms for ports at or below 5 GT/s; for faster ports it first waits for the Data Link Layer Link Active bit (pcie_wait_for_link_delay()) and then 100 ms.
  • pci_dev_d3_sleep() sleeps d3hot_delay (10 ms by default) after D3hot→D0.
