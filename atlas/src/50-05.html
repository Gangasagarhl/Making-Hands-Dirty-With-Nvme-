24 Fabric Configuration, Interrupt and DMA-Translation Failures

24.1 Why this chapter exists

The failures in this chapter happen between the PCIe link and the NVMe controller logic. A payload-size setting or isolation policy can be inconsistent along the path. An interrupt can be routed to nowhere. A DMA address can be refused by the IOMMU. Or a power-saving link state may never wake up. On their own they rarely produce a clean error. Instead they cause timeouts, resets or silent loss of completions further up. Each card says which upstream symptom to look for.

L-32MPS / MRRS mismatch along the path ReportedPCIe config
What happens
Max_Payload_Size (MPS) must not exceed what each receiver on the path accepts. If the SSD's MPS is larger than the Root Port's or a switch's, its large MWr (read data to host) are Malformed at the receiver (L-18), which is fatal by default. Max_Read_Request_Size (MRRS) mismatches are legal but can hurt performance (too small) or fairness (too large). Some devices mishandle certain MRRS values, as the comment in pcie_write_mrrs() says: "issues with setting MRRS to 0 on a number of devices".
How it shows up
Fatal MalfTLP during the first large read, then a reset loop. Or, with consistent but small MPS/MRRS, a quiet bandwidth deficit (Degraded). Linux v7.2 messages: Max Payload Size set to %d (was %d, max %d), Upstream bridge's Max Payload Size set to %d ..., Max Payload Size %d, but upstream %s set to %d; if necessary, use "pci=pcie_bus_safe" and report a bug (with pci=pcie_bus_tune_off), can't set Max Payload Size to %d ..., Failed attempting to set the MPS, Failed attempting to set the MRRS, MRRS was unable to be configured with a safe value. If problems are experienced, try running with pci=pcie_bus_safe, and in non-default modes Max Payload Size set to %4d/%4d (was %4d), Max Read Rq %4d.
Spec basis
PCIe Base Specification: Device Capabilities Max_Payload_Size Supported, Device Control Max_Payload_Size and Max_Read_Request_Size, the rule that TLP payloads must not exceed the receiver's MPS.
Typical causes
Hot-plugged SSDs under a port configured for a different MPS. Firmware that programs the root ports differently from Linux's policy. P2P (pci=pcie_bus_peer2peer forces 128 B). Settings changed by user tools with setpci.
How to detect / prove
lspci -vvv | grep -E 'MaxPayload|MaxReadReq' on every device on the path. Each DevCtl line lists "MaxPayload N bytes, MaxReadReq M bytes". Each must be ≤ its partner's capability, and the payload size must be consistent across the path. Boot-option tests: pci=pcie_bus_safe, pcie_bus_perf, pcie_bus_tune_off, pcie_bus_peer2peer.
In a trace
MWr or CplD with a Length (DW) × 4 larger than the receiver's MPS. MRd sizes reflect the requester's MRRS. Completions are split per Read Completion Boundary.
Linux v7.2 source
drivers/pci/probe.c: pci_configure_mps, pcie_write_mps, pcie_write_mrrs, pcie_bus_configure_set, pcie_bus_configure_settings; drivers/pci/pci.c: pcie_bus_config and parsing of pcie_bus_*. Quirk: fixup_mpss_256 in quirks.c (limits MPSS to 256 for listed devices, including an ASMedia 0x0612 storage controller).
Test to provoke it
CAUTION/EXPERT: set mismatched MPS with setpci on a test machine and run a large read. Expect MalfTLP and a fatal reset.
L-33ACS misconfiguration — P2P blocked, redirected, or isolation silently missing SilentPCIe config
What happens
ACS has two failure directions. Too strict: P2P traffic (SSD ↔ GPU or NIC) is redirected upstream to the root complex, where it may be refused (UR or ACS Violation) or just run slowly through the IOMMU. Too loose: a switch without ACS lets an SSD DMA straight into a peer's BAR, bypassing the IOMMU. Isolation is broken with no error anywhere. A misprogrammed PRP that points at a peer BAR then corrupts that device silently.
How it shows up
Too strict: L-21 ACSViol, or P2P performance far below expectation. Too loose: nothing, apart from IOMMU groups that contain several devices (/sys/kernel/iommu_groups/*/devices).
Spec basis
PCIe Base Specification: ACS Source Validation, Translation Blocking, P2P Request Redirect, P2P Completion Redirect, Upstream Forwarding, P2P Egress Control, Direct Translated P2P.
Typical causes
Switches without an ACS capability. Firmware ACS settings that differ from what the OS expects. The pci=config_acs= override. VFIO setups.
How to detect / prove
lspci -vvv: ACSCap and ACSCtl on every downstream port. Linux logs Configured ACS to %#06x when it applies an override. Check IOMMU group membership.
In a trace
Too strict: P2P MWr going up to the root port and back down (doubling link traffic). Too loose: P2P TLPs turning around inside the switch without ever reaching the root.
Linux v7.2 source
drivers/pci/pci.c: pci_request_acs, pci_std_enable_acs, pci_enable_acs, pci_acs_enabled, pci_acs_path_enabled, pci_acs_init.
Test to provoke it
SAFE: inventory ACS capabilities and IOMMU groups. CAUTION: P2PDMA tests with ACS on and off.
L-34ATS / PRI errors — translated-address or page-request failures ReportedPCIe Transaction
What happens
With Address Translation Services (ATS) the device caches IOVA→physical translations (in its ATC) and sends "translated" requests that the IOMMU does not check again. Failure modes: a stale ATC entry after the host unmapped and invalidated, where the device misses or acknowledges the invalidation too late, so DMA goes to freed memory (silent corruption). An Invalidate Completion that never arrives, so the IOMMU invalidation times out. With Page Request Interface (PRI), a page request that is never answered or that fails, so DMA waits forever.
How it shows up
Invalidation timeouts and page-request failures are reported by the IOMMU driver (Intel VT-d / AMD-Vi / Arm SMMU), not by AER. Exact message wording is uncertain here because those drivers are not in the local source tree. Stale-ATC DMA is silent. Most NVMe SSDs do not implement ATS or PRI, so this matters mainly for SVA/PASID-capable or computational storage devices impl.
Spec basis
PCIe Base Specification: ATS (Translation Request/Completion, Invalidate Request/Completion), PRI (Page Request Message, PRG Response), PASID.
Typical causes
ATC invalidation bugs in device firmware. Invalidation queues saturated in the IOMMU. Page-request group bookkeeping bugs.
How to detect / prove
lspci -vvv: ATSCap/ATSCtl "Enable+", PRI capability, PASID capability. IOMMU fault logs. For stale-translation corruption: a read-back verify test (fio verify=crc32c) during heavy map/unmap churn (for example with the IOMMU in strict mode, iommu.strict=1).
In a trace
Translation Requests (MRd with AT=01b), translated requests (AT=10b), Invalidate Request messages, and missing or late Invalidate Completion messages.
Linux v7.2 source
ATS/PRI core (drivers/pci/ats.c) and IOMMU drivers are not in the local tree. Not verified here.
Test to provoke it
EXPERT: an exerciser that delays Invalidate Completions; IOMMU stress with frequent unmaps during DMA.
L-35MSI / MSI-X misconfiguration — lost or misrouted interrupts Timer onlyPCIe / host IRQ
What happens
The SSD posts a CQE, then sends its interrupt as an MWr to the MSI or MSI-X address. If the vector is masked, has the wrong address or data, is blocked by interrupt remapping, or is never sent (a device bug), the CPU never runs the completion handler. The CQE sits in host memory, already written.
How it shows up
After io_timeout, Linux v7.2's nvme_timeout() first polls the CQ ("Did we miss an interrupt?" in the source). If the request was in fact completed, it logs I/O tag %d (%04x) QID %d timeout, completion polled and finishes the request with no reset. A single occurrence means a lost interrupt. Many mean systematic interrupt failure. Other signs: /proc/interrupts counts for the nvme0qN vectors that stay flat while I/O is issued; the MSI core's arch assigned 64-bit MSI address %#llx above device MSI address mask %#llx.
Spec basis
PCI/PCIe: MSI and MSI-X capability, MSI-X Table and Pending Bit Array, Function Mask, per-vector Mask. NVMe: the INTMS/INTMC registers mask pin-based and single-message MSI only (not MSI-X). The Create I/O CQ "IV" field selects the vector.
Typical causes
Devices whose MSI (not MSI-X) does not work at all. Linux has NVME_QUIRK_BROKEN_MSI for two SanDisk models (Chapter 27). Controllers that require all queues on vector 0 (NVME_QUIRK_SINGLE_VECTOR, Apple). Interrupt-remapping table errors. CPU hot-unplug with affinity mistakes. A device that sends the MWr before its CQE write is visible (an ordering bug), so the handler finds nothing and the next interrupt never comes. Coalescing settings too aggressive (Set Features Interrupt Coalescing).
How to detect / prove
Search dmesg for "completion polled". Compare /proc/interrupts deltas with I/O counts. lspci -vvv "MSI-X: Enable+ Count=N Masked-". Boot with nvme.use_threaded_interrupts=1 or use poll queues (nvme.poll_queues=N, with io_uring hipri) to see whether the problem disappears when interrupts are bypassed.
In a trace
Normal: CQE MWr then MSI-X MWr (to the 0xFEExxxxx range on x86). Bug: CQE MWr with no MSI-X MWr afterwards, or an MSI-X MWr whose address or data does not match the table entry programmed by the host.
Linux v7.2 source
nvme/host/pci.c: nvme_timeout (poll then "completion polled"), nvme_irq, nvme_irq_check, nvme_poll_irqdisable, nvme_setup_irqs (BROKEN_MSI clears PCI_IRQ_MSI; SINGLE_VECTOR uses one vector), nvme_pci_enable; drivers/pci/msi/msi.c: msi_verify_entries.
Test to provoke it
CAUTION: mask an MSI-X vector through the table (with a debug tool) while I/O runs; expect "completion polled" after the timeout. SAFE: run with nvme.io_timeout lowered on a test box to shorten the experiment.
L-36IOMMU / DMAR fault — SSD DMA to an address the host did not map ReportedHost IOMMU
What happens
The SSD issues DMA (SQ fetch, PRP-list fetch, data read or write, CQE write, or the MSI address when not remapped) to an IOVA that has no valid mapping or no permission. The IOMMU blocks it. Blocked reads complete with an error (UR or CA, or a timeout at the device). Blocked writes are dropped. The NVMe command fails, or more often its CQE is lost and the host times out.
How it shows up
An IOMMU fault message naming the device's Requester ID and the faulting address. On Intel the message is commonly of the form DMAR: [DMA Read/Write] Request device [bb:dd.f] ... fault addr 0x... [fault reason 0xNN] ..., on AMD AMD-Vi: Event logged [IO_PAGE_FAULT device=... address=...]. These IOMMU driver strings were not verified against the local tree uncertain. The QEMU NVMe model shows what a careful device does when its own SQ or CQ DMA fails: nvme_process_sq() and nvme_post_cqes() trace pci_nvme_err_addr_read/_write and pci_nvme_err_cfs, then set CSTS to NVME_CSTS_FAILED. Real SSDs may instead set CFS, log an error, or carry on impl.
Spec basis
Platform IOMMU specifications (VT-d, AMD IOMMU, SMMU). NVMe: CSTS.CFS is the controller's way to say it can no longer operate. PCIe: completion statuses UR and CA.
Typical causes
Host driver bugs: use-after-unmap, wrong PRP list length, PRP offsets crossing into unmapped pages. Controller bugs: prefetching past the end of a PRP list, reading SQ entries beyond the queue size, DMA after a reset was requested (stale queue addresses). A device using the wrong Requester ID (see the DMA alias quirks in Chapter 27). NVME_QUIRK_DMA_ADDRESS_BITS_48: controllers that cannot DMA above 48 bits; Linux limits their DMA mask.
How to detect / prove
dmesg | grep -iE 'DMAR|AMD-Vi|iommu|smmu'. Match the fault address to an NVMe structure: run the nvme_setup_cmd tracepoint (/sys/kernel/tracing/events/nvme/) and look for the same IOVA in PRP1/PRP2. Rebooting with iommu=pt or the IOMMU off as a diagnostic can show whether faults turn into silent corruption, so verify the data.
In a trace
An SSD MRd or MWr to an address that does not match any PRP or queue base programmed in the preceding SQE or Create-queue commands.
Linux v7.2 source
nvme/host/pci.c: nvme_pci_alloc_dev sets dma_set_mask_and_coherent to 48 or 64 bits; drivers/pci/quirks.c: quirk_dma_func1_alias and related alias quirks; __pci_dev_specific_reset logs failed to stop IOMMU for a PCI reset: %d. QEMU: hw/nvme/ctrl.c nvme_process_sq, nvme_post_cqes.
Test to provoke it
EXPERT: a user-space NVMe driver (vfio-based) that submits a command with a PRP pointing outside its mapped buffer. The IOMMU must fault, and the SSD's response (CFS, error status, or hang) is the result of the test.
L-37ASPM-related link drop or stall (L0s / L1 / L1 substates) Timer onlyPCIe Physical / PM
What happens
When idle, the link goes into L0s, L1 or L1.1/L1.2. On the next transaction it must wake up. If exit latency exceeds what the endpoint tolerates, or the exit fails (CLKREQ# handshake, reference clock not restored, a PHY bug), the link either stalls (replay timeouts, Recovery) or goes down entirely. Often this happens only after minutes or hours of idle, which makes it look random.
How it shows up
Mild cases: correctable Replay Timer Timeout and Receiver Errors after idle periods. Severe cases: SSD drops off, and the first I/O after idle times out with CSTS=0xffffffff and the driver hint Try "nvme_core.default_ps_max_latency_us=0 pcie_aspm=off pcie_port_pm=off" and report a bug. NVMe APST (controller power states) often combines with ASPM, and the quirk table (Chapter 27) has many "drops off the PCIe bus" entries for APST. Linux ASPM messages: ASPM: current common clock configuration is inconsistent, reconfiguring, ASPM: Could not configure common clock, ASPM: Link Capabilities L0s/L1 treated as unsupported to avoid device defect (from pcie_aspm_remove_cap() via quirks), can't disable ASPM; OS doesn't have ASPM control.
Spec basis
PCIe Base Specification: ASPM L0s/L1, L1 PM Substates (L1.1, L1.2), LTR, exit latencies in Link Capabilities and Device Capabilities (acceptable latencies), Common Clock Configuration.
Typical causes
Platform firmware advertising L1.2 without proper CLKREQ# routing. Wrong T_POWER_ON or LTR values (Linux logs Invalid T_PwrOn scale). Device PHY bugs. Missing LTR restore after resume (no suspend buffer for LTR; ASPM issues possible after resume).
How to detect / prove
Diagnostic boots: pcie_aspm=off, or set /sys/module/pcie_aspm/parameters/policy to performance. Per-link control is under /sys/bus/pci/devices/<BDF>/link/ (for example l1_2_aspm; availability varies) version. lspci -vvv: LnkCtl "ASPM L1 Enabled", L1SubCtl1. An idle-then-burst test loop: sleep N seconds, issue a 4 KiB read, measure latency, raise N.
In a trace
PM_Active_State_Request_L1 DLLPs, electrical idle, then on wake an exit sequence (TS1s) that fails or takes too long. Analyzers need to handle electrical idle and CLKREQ# to capture this. Use a sideband probe on CLKREQ#.
Linux v7.2 source
drivers/pci/pcie/aspm.c: pcie_aspm_remove_cap, common-clock configuration, policy parameter; quirks.c: quirk_disable_aspm_l0s, quirk_disable_aspm_l0s_l1 (including ASMedia 0x1080); nvme/host/pci.c: nvme_warn_reset.
Test to provoke it
SAFE: idle-burst loop with ASPM policy powersupersave versus performance, counting timeouts. CAUTION: run for hours; a drop may need a power cycle to recover.
L-38Poisoned data accepted and committed — poison "handled" by writing it SilentPCIe / NVMe data path
What happens
The SSD receives a poisoned CplD carrying write data (L-12). AER logs it at the SSD, but the controller's data path ignores the poison, writes the bad data to NAND and completes the Write with success. Later reads return the corrupt data with good status.
How it shows up
One AER Poisoned TLP line (non-fatal, no reset, and possibly rate-limited). NVMe CQE status Success. Nothing else.
Spec basis
PCIe says a receiver of a poisoned TLP must not use the data as if it were good (Data Poisoning rules). How an NVMe controller then fails the command is implementation-defined impl.
Typical causes
Firmware that does not propagate the poison indication from the PCIe core to the command engine.
How to detect / prove
Inject a poisoned completion for a known write (exerciser), then read back the LBA and check that either the write failed or the data is intact. Correlate field AER poison events with later application checksum errors.
In a trace
A CplD with EP=1 for the SSD's MRd of write data, followed by a successful CQE for that Write command. This is the smoking gun.
Linux v7.2 source
aer.c: pcie_do_recovery(..., pci_channel_io_normal, ...) for non-fatal; nvme_error_detected returns CAN_RECOVER, so the NVMe layer does nothing.
Test to provoke it
EXPERT: exerciser or analyzer injection of EP on the CplD path; destructive to the target LBAs.
L-40Tag and ordering capability mismatch: Extended/10-bit tags, Relaxed Ordering errata DegradedPCIe config
What happens
Two related failures. (1) Tags: a requester using 8-bit (Extended) or 10-bit tags toward a completer or root that mishandles them gives wrong-tag completions (Unexpected Completion, Completion Timeout). Disabling them limits outstanding reads, so SSD read bandwidth drops at high queue depth. (2) Relaxed Ordering: some root complexes have errata with Relaxed Ordering (RO) TLPs. Linux disables RO for listed root ports and prints Disable Relaxed Ordering Attributes to avoid PCIe Completion erratum (the quirks.c comment cites a Flow Control credit issue on Broadwell/Haswell Xeon root complexes causing "performance problems").
How it shows up
probe.c messages enabling Extended Tags / disabling Extended Tags, Relaxed Ordering disabled because the Root Port didn't support it. Otherwise only lower bandwidth.
Spec basis
PCIe Base Specification: Extended Tag Field Enable, 10-Bit Tag Requester/Completer, Relaxed Ordering attribute, Enable Relaxed Ordering in Device Control.
Typical causes
Root complex errata; host-bridge flags (no_ext_tags); devices with limited completion buffers.
How to detect / prove
lspci -vvv DevCtl "ExtTag+ RlxdOrd+", DevCtl2 "10BitTagReq+". Compare fio random-read bandwidth at QD128 with and without those settings.
In a trace
Count of distinct outstanding MRd tags from the SSD. The RO bit in TLP Attr.
Linux v7.2 source
probe.c: pci_configure_extended_tags, Relaxed Ordering configuration; quirks.c: quirk_relaxedordering_disable.
Test to provoke it
SAFE: measure; CAUTION: toggle with setpci on a test system.
💡 Senior insight — the 30-second rule

Almost every card in this chapter ends in the same NVMe symptom: an I/O timeout 30 seconds later (Linux v7.2's default nvme_core.io_timeout). When you see an NVMe timeout, do not start with the SSD. Look backwards 30 seconds in the kernel log for AER, DPC, IOMMU, bwctrl or ASPM messages. If you find any, the timeout is a symptom. If you find none, check the "completion polled" message first (lost interrupt) before blaming the controller.

Interview questions

  1. Intermediate An SSD shows "completion polled" timeouts only after the system has been idle for an hour. Name two hypotheses and how to split them.
    Model answer

    (1) A lost MSI-X after a power-management transition (device bug, or vector masked across D3/L1.2 transitions). (2) ASPM or APST exit causing the device to post the CQE late or drop the interrupt. Split them by disabling APST (nvme_core.default_ps_max_latency_us=0) and ASPM (pcie_aspm=off) separately. Also check /proc/interrupts to see whether the vector fired at all.

  2. Senior Why might ECRC catch corruption that LCRC never sees?
    Model answer

    LCRC is per hop and regenerated by every switch. Corruption inside a switch's internal buffer happens after the ingress LCRC check and before the egress LCRC is computed, so the egress LCRC is valid over corrupt data. ECRC is computed end to end by the original requester and checked by the final receiver, so it covers the switch internals.
