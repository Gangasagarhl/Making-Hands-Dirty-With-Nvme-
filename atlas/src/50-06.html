PART VI

Controller and Host-Side Failures

These failures happen to the NVMe controller as a whole, not to one command. The controller declares itself dead (CSTS.CFS), refuses to become ready, never finishes shutting down, loses its admin queue, or falls asleep and never wakes up. The host driver then reacts with timers, aborts, resets and, as a last resort, by removing the controller. This part covers the controller-state failures, the Linux v7.2 recovery machinery with its real log messages, and the Linux quirk table, which is a public list of real device bugs that the kernel has to work around. Card ids use the prefix C-.

VI.1 Controller-State Failures

VI.1.1 The controller state machine in registers

The host sees the whole controller lifecycle through two registers. It writes CC (offset 14h): EN to enable or reset, SHN to request shutdown. It polls CSTS (offset 1Ch): RDY (bit 0), CFS Controller Fatal Status (bit 1), SHST Shutdown Status (bits 3:2: 00b normal, 01b processing, 10b complete), NSSRO NVM Subsystem Reset Occurred (bit 4), and PP Processing Paused (bit 5). Linux v7.2 names these NVME_CSTS_RDY, NVME_CSTS_CFS, NVME_CSTS_SHST_*, NVME_CSTS_NSSRO and NVME_CSTS_PP in include/linux/nvme.h verified. The time limits come from CAP.TO (worst-case time for RDY to change, in 500 ms units), CRTO (Controller Ready Timeouts, when CAP.CRMS says it is supported), and RTD3E / the host's own shutdown timeout for shutdown.

VI.1.2 What a PEX trace sees of controller state

Every CC write and every CSTS read the host makes is a TLP: a posted MWr to BAR0+14h, and an MRd to BAR0+1Ch answered by a CplD whose data is the CSTS value. A capture of an enable or reset sequence therefore contains the exact state history as the host polled it, with timestamps. The analyzer cannot see what happens between polls inside the controller, or why the controller set CFS. Linux polls CSTS every 1–2 ms (usleep_range(1000, 2000) in nvme_wait_ready()), so the trace resolves state changes to about 2 ms.

C-01Controller Fatal Status (CSTS.CFS) — controller declares itself failed ReportedNVMe controller
In a PEX trace
Visible The CplD for an MRd to BAR0+1Ch carries data with bit 1 set (for example 0x00000003), usually after a period with no CQE MWr from the controller. The CC write that follows (EN=0) and the recovery are visible too. Why the controller failed is internal and not visible.
What happens
The controller hit an error it cannot recover from by itself and set CFS. Outstanding commands will not complete. The host must reset it (CC.EN 1→0, or something stronger).
How it shows up
Linux v7.2 reads CSTS in nvme_timeout(). nvme_should_reset() returns true when CFS is set (or NSSRO on an NSSR-capable controller) and the controller is not already RESETTING or CONNECTING. nvme_warn_reset() logs controller is down; will reset: CSTS=0x%x, PCI_STATUS=0x%hx. If CSTS reads ~0, that means the device is gone rather than CFS, and two more lines follow: Does your device have a faulty power saving mode enabled? and Try "nvme_core.default_ps_max_latency_us=0 pcie_aspm=off pcie_port_pm=off" and report a bug. The driver then disables the controller and schedules a reset. CFS is noticed only when a command times out. Linux v7.2 does not poll CSTS periodically for PCIe controllers.
Spec basis
NVMe Base Specification: CSTS.CFS, controller reset, "Controller Fatal Status" handling (host should reset the controller).
Typical causes
Firmware assert or watchdog. DMA failure on queue memory (the QEMU model sets NVME_CSTS_FAILED when it cannot read an SQE or write a CQE: nvme_process_sq, nvme_post_cqes). Invalid CC values at enable (QEMU fails nvme_start_ctrl on misaligned ASQ/ACQ, unsupported CSS, page size out of range, or zero queue entry sizes, and sets CFS). Internal uncorrectable errors (L-22).
How to detect / prove
dmesg | grep 'controller is down' (the CSTS value is in the message: 0x3 = RDY+CFS, 0xffffffff = gone). nvme show-regs /dev/nvme0 (read-only register dump). After recovery, collect nvme error-log, the persistent event log, and vendor telemetry (nvme telemetry-log) before any further reset overwrites them.
Linux v7.2 source
drivers/nvme/host/pci.c: nvme_timeout, nvme_should_reset, nvme_warn_reset, nvme_pci_ctrl_is_dead (CFS or !RDY ⇒ dead, so nvme_dev_disable skips deleting queues on the device); QEMU hw/nvme/ctrl.c: nvme_start_ctrl failure paths (trace_pci_nvme_err_startfail_*).
Test to provoke it
CAUTION: on QEMU, enable the controller with a misaligned ASQ from a user-space test driver; the model sets CFS. EXPERT: vendor fault-injection commands on real SSDs.
C-02CSTS.RDY never sets after CC.EN=1 Timer onlyNVMe controller
In a PEX trace
Visible An MWr to BAR0+14h with EN=1, then a series of CSTS MRd/CplD pairs every 1–2 ms that all return RDY=0, lasting until about CAP.TO×500 ms (or the CRTO-derived value). After that the host stops polling. The timestamps prove the timeout.
What happens
The host enabled the controller, but it never reports ready within the advertised time. The admin queue cannot be used.
How it shows up
nvme_enable_ctrl() → nvme_wait_ready(ctrl, NVME_CSTS_RDY, NVME_CSTS_RDY, (timeout + 1) / 2, "initialisation") logs Device not ready; aborting initialisation, CSTS=0x%x and returns -ENODEV. Note the unit conversion: the wait is in seconds, and CAP.TO is in 500 ms units. If CAP.CRMS indicates CRTO support, the driver reads CRTO and uses the larger of CRTO.CRWMT and CAP.TO. When CRTO is smaller, it logs bad crto:%x cap:%llx once (C-13). The reset then fails with Disabling device after reset failure: -19.
Spec basis
NVMe Base Specification: CAP.TO ("worst-case time that host software should wait for CSTS.RDY to transition"), CRTO and CC.CRIME (Controller Ready Independent of Media Enable), controller initialization sequence.
Typical causes
Firmware boot slower than CAP.TO after an unsafe shutdown (mapping-table rebuild). Media not ready. Note that Linux v7.2 always clears CC.CRIME (ctrl->ctrl_config &= ~NVME_CC_CRIME, with the comment that the driver cannot yet handle "Admin Command Media Not Ready"), so the controller must wait for media before setting RDY. Invalid CC field values; the controller may instead set CFS (C-01).
How to detect / prove
The dmesg line gives the final CSTS. Compare the elapsed time with CAP.TO (nvme show-regs: "cap" field, TO bits 31:24). Repeat cold-boot and warm-reset tests, and especially after an unsafe power loss.
Linux v7.2 source
drivers/nvme/host/core.c: nvme_enable_ctrl, nvme_wait_ready; quirk NVME_QUIRK_DELAY_BEFORE_CHK_RDY (C-27).
Test to provoke it
CAUTION: power-cut during heavy writes (unsafe shutdown), then time the next enable. Repeat 100+ times and plot time-to-RDY against CAP.TO.
C-03CSTS.RDY never clears after CC.EN=0 (controller reset hangs) Timer onlyNVMe controller
In a PEX trace
Visible An MWr to CC with EN=0, then repeated CSTS reads with RDY=1 for the whole timeout. In Linux v7.2 that is followed by an FLR: a CfgWr to Device Control with the Initiate FLR bit set, the link quiet period, config-space restore CfgWrs, then a second CC EN=0 write and polling.
What happens
The host asked for a controller reset and the controller never acknowledged it by clearing RDY. Its internal state is stuck.
How it shows up
nvme_disable_ctrl(ctrl, false) → nvme_wait_ready(..., NVME_CSTS_RDY, 0, (CAP.TO + 1)/2, "reset") logs Device not ready; aborting reset, CSTS=0x%x. In nvme_pci_configure_admin_queue(), Linux v7.2 then escalates: the source comment says "The NVMe Controller Reset method did not get an expected CSTS.RDY transition... Use the lower level and bigger hammer PCIe Function Level Reset". It calls pcie_reset_flr(), restores state, retries the disable, and on success logs controller reset completed after pcie flr.
Spec basis
NVMe Base Specification: controller reset via CC.EN, CAP.TO. PCIe: Function Level Reset.
Typical causes
Firmware stuck on an outstanding internal operation (a long command that cannot be aborted, background media work). A controller left enabled by firmware or a previous OS (kexec, boot loader). Linux deliberately does not send a shutdown notification in that case, for fear the device "may cause the device to complete commands to the admin queue ... and we don't know what memory that might be pointing at!"
How to detect / prove
dmesg: "aborting reset" followed by "controller reset completed after pcie flr" means CC reset is broken and FLR works around it. Report it to the vendor even though the system recovered.
Linux v7.2 source
core.c: nvme_disable_ctrl, nvme_wait_ready; pci.c: nvme_pci_configure_admin_queue; drivers/pci/quirks.c: nvme_disable_and_flr (generic NVMe pre-FLR disable used for Samsung 0xa804, logging Timeout waiting for NVMe ready status to clear after disable).
Test to provoke it
CAUTION: issue a long-running admin command (for example a sanitize or self-test, where allowed) and immediately reset the controller (nvme reset /dev/nvme0) on a test drive; measure the time for RDY to clear.
C-04Shutdown never completes (SHST never reaches 10b) Timer onlyNVMe controller
In a PEX trace
Visible An MWr to CC with SHN=01b, then CSTS reads returning SHST=01b (processing) or 00b for the whole timeout, then the host giving up: on power-off, the link goes down or power is cut while SHST≠10b. Whether the controller flushed its cache is not visible.
What happens
The host notified the controller of shutdown, and the controller did not report completion in time. The host powers off anyway. Volatile write cache contents or FTL metadata may not be saved, which can cause data loss or a long recovery on the next boot.
How it shows up
nvme_disable_ctrl(ctrl, true) → nvme_wait_ready(ctrl, NVME_CSTS_SHST_MASK, NVME_CSTS_SHST_CMPLT, ctrl->shutdown_timeout, "shutdown") logs Device not ready; aborting shutdown, CSTS=0x%x. shutdown_timeout is a module parameter (default 5 s in Linux v7.2: nvme_core.shutdown_timeout). If the controller reports RTD3 Entry Latency (RTD3E, Identify Controller), Linux uses it clamped between shutdown_timeout and 60 s, and logs D3 entry latency set to %u seconds when that differs from the parameter. A controller that under-reports RTD3E gets only the default 5 s. On the next boot, SMART "Unsafe Shutdowns" goes up by one.
Spec basis
NVMe Base Specification: CC.SHN, CSTS.SHST, RTD3E, Unsafe Shutdowns in the SMART / Health Information log.
Typical causes
Large volatile caches that take longer than the host waits. Firmware that ignores SHN while busy. Host timeout lower than RTD3E.
How to detect / prove
Compare nvme smart-log unsafe_shutdowns before and after a clean reboot: it must not increase. Check nvme id-ctrl rtd3e against the effective host timeout. A data-integrity test: write with a known pattern, Flush, clean reboot, read back.
Linux v7.2 source
core.c: nvme_disable_ctrl, nvme_wait_ready, shutdown_timeout; pci.c: nvme_shutdown → nvme_disable_prepare_reset(dev, true), nvme_dev_disable.
Test to provoke it
SAFE: 500 reboot cycles while writing, checking unsafe_shutdowns each time. CAUTION: lower nvme_core.shutdown_timeout to 1 on a test system to expose slow shutdowns.
C-05NVM Subsystem Reset (NSSR) side effects — link drop and lost state ReportedNVMe subsystem / PCIe
In a PEX trace
Visible An MWr to BAR0+20h with data 0x4E564D65 ("NVMe"), then the link going down (electrical idle) and retraining, because an NVM subsystem reset resets the PCIe port too. The host's CSTS MRd right after it gets no completion, or all-ones. After re-link, a CSTS read shows NSSRO=1.
What happens
Writing "NVMe" to the NSSR register resets the entire NVM subsystem, including the PCIe link of every controller in it. Every in-flight command on every controller (all ports of a dual-port drive) is lost. The host sees what looks like a surprise link down (L-11 or L-27). After recovery, CSTS.NSSRO=1 tells the host what happened.
How it shows up
Linux v7.2 nvme_pci_subsystem_reset() moves the controller to RESETTING, writes NVME_SUBSYS_RESET to NVME_REG_NSSR, moves it through CONNECTING to LIVE, and then reads CSTS on purpose "to flush the previous write and trigger a pcie read error". Recovery comes from AER, DPC or the timeout path: nvme_should_reset() treats NSSRO as "loss of adapter communication". At init, nvme_pci_configure_admin_queue() clears a stale NSSRO (write-1-to-clear). Expect AER Surprise Down or DPC containment on the port, and "controller is down; will reset".
Spec basis
NVMe Base Specification: NSSR register (offset 20h), CAP.NSSRS, CSTS.NSSRO, NVM Subsystem Reset scope.
Typical causes
Deliberate test actions (nvme subsystem-reset). Firmware activation methods that need a subsystem reset. Unexpected NSSR from another host on a shared dual-port subsystem.
How to detect / prove
After the event, nvme show-regs shows NSSRO=1 (if not yet cleared). The QEMU model does not implement it: writing the magic value only traces pci_nvme_ub_mmiowr_ssreset_unsupported, and W1C of NSSRO traces ..._ssreset_w1c_unsupported. Do not validate NSSR handling on QEMU.
Linux v7.2 source
pci.c: nvme_pci_subsystem_reset, nvme_should_reset, nvme_pci_configure_admin_queue; nvme.h: nvme_reset_subsystem (requires ctrl->subsystem, which is set only if VS ≥ 1.1 and CAP.NSSRS).
Test to provoke it
EXPERT / destructive to in-flight I/O: nvme subsystem-reset /dev/nvme0 on a test system under load, while capturing the link and the AER/DPC logs.
C-06Controller reset loop ReportedNVMe controller / host
In a PEX trace
Visible A repeating macro-pattern: CC EN=0 → RDY=0 polls → AQA/ASQ/ACQ writes → CC EN=1 → RDY=1 → Identify, Set Features (Number of Queues), Create CQ/SQ commands → I/O → (timeout gap) → CC EN=0 again. The analyzer's NVMe-over-PCIe decode makes each cycle easy to spot, and the last command before each reset is the suspect.
What happens
Every reset succeeds, but the same trigger hits again soon after: a command that always times out, a fatal AER on the first large transfer (MPS mismatch), or an APST transition that drops the device. The system spends its time resetting, and the I/O that keeps failing after retries reaches applications as errors.
How it shows up
Repeated I/O tag ... timeout, reset controller or controller is down; will reset lines. The controller's reset counter (nr_reset, incremented in nvme_change_ctrl_state() on each transition to RESETTING) keeps rising. Linux has no generic "give up after N resets" for PCIe impl; per-request retries are limited by nvme_core.max_retries. The loop ends only when a reset itself fails (C-17).
Spec basis
Host behaviour; not defined by the NVMe spec.
Typical causes
A poisoned command that is retried after each reset (same LBA, same opcode). Fatal PCIe errors on a specific transfer pattern (L-18). Power-state bugs (C-07). Firmware asserts on a specific command.
How to detect / prove
Count resets per hour from dmesg. The NVMe tracepoints (nvme:nvme_setup_cmd, nvme:nvme_complete_rq) show the last command before each timeout. Find whether the same opcode and LBA appear every time.
Linux v7.2 source
core.c: nvme_change_ctrl_state (atomic_long_inc(&ctrl->nr_reset)), nvme_reset_ctrl, max_retries; pci.c: nvme_timeout, nvme_reset_work.
Test to provoke it
CAUTION: replay the suspected command in a loop with nvme io-passthru on a scratch namespace.
C-07Controller stuck in a low-power state / drops off the bus after APST or D3 Timer onlyNVMe power mgmt
In a PEX trace
Partly visible APST is configured with a Set Features (FID 0Ch) admin command whose table is a DMA'd payload, which is visible. Autonomous transitions are internal and invisible. A failed wake shows as the next doorbell MWr followed by no SQE-fetch MRd from the device, or as the link never leaving electrical idle (L-37). For D3hot, the CfgWr to PMCSR is visible.
What happens
The controller enters a non-operational power state (APST or host-requested) or the function goes to D3, and does not come back correctly. It either answers nothing (link down, CSTS all-ones) or wakes with lost state. The quirk table (Chapter VI.3) records this as the most common shipping-device bug class: NVME_QUIRK_NO_DEEPEST_PS (10 PCI IDs, plus DMI-matched Samsung cases) and NVME_QUIRK_NO_APST (core quirks for a Toshiba and a Kioxia model, plus DMI-matched cases), with comments such as "seem to drop off the PCIe bus randomly when APST is on and uses the deepest sleep state", and the Kioxia CD6 entry "times out and aborts I/O during any load, but more easily reproducible with discards".
How it shows up
An I/O timeout after an idle period, then controller is down; will reset: CSTS=0xffffffff and the power-saving hint lines. Configuration messages: NPSS is invalid; not using APST, failed to set APST feature (%d), forcibly allowing APST due to nvme_core.force_apst -- use at your own risk.
Spec basis
NVMe Base Specification: Power State Descriptors (ENLAT, EXLAT, NOPS), Autonomous Power State Transition feature (FID 0Ch), Power Management feature (FID 02h), Non-Operational Power States.
Typical causes
Firmware wake-up bugs. Interaction with platform L1.2 or CLKREQ#. Exit latency longer than advertised.
How to detect / prove
Diagnostic boot with nvme_core.default_ps_max_latency_us=0 (disables APST). nvme get-feature -f 0x0c -H /dev/nvme0 shows the APST table. nvme id-ctrl -H shows the power-state descriptors. Idle/burst loop tests with increasing idle time.
Linux v7.2 source
core.c: nvme_configure_apst (APST table construction; honours NVME_QUIRK_NO_DEEPEST_PS), default_ps_max_latency_us, force_apst, apst_primary_timeout_ms and related parameters, core_quirks[]; pci.c: check_vendor_combination_bug, nvme_suspend, nvme_set_power_state.
Test to provoke it
SAFE: idle soak (hours) with default APST, then a single read; repeat with APST off. CAUTION: suspend/resume cycling (s2idle) 500 times.
C-08Admin queue hang — admin command never completes Timer onlyNVMe admin
In a PEX trace
Visible An MWr to the SQ0 tail doorbell (BAR0+1000h), then the controller's MRd fetching the 64-byte admin SQE (visible with its opcode and CID), and then no CQE MWr to the admin CQ for that CID within the timeout. If the controller never even fetches the SQE, the hang is in its front end.
What happens
An admin command (Identify, Get Log Page, Format, Sanitize, Firmware Commit, Set Features) never completes. Linux does not abort admin commands. A timeout on QID 0 goes straight to a controller reset.
How it shows up
After admin_timeout (60 s default, nvme_core.admin_timeout): I/O tag %d (%04x) opcode %#x (%s) QID 0 timeout, reset controller. The nvme_timeout() branch is if (!nvmeq->qid || (iod->flags & IOD_ABORTED)). The submitting tool (nvme-cli) gets an error such as EINTR or ENODEV after the reset cancels it.
Spec basis
NVMe Base Specification: admin queue; some admin commands have long, implementation-defined durations (Format NVM, Sanitize runs in the background with its own log, Device Self-test).
Typical causes
Long Format NVM with a user timeout shorter than its duration (nvme-cli's --timeout). Firmware deadlocks between admin and I/O paths. Get Log Page of large telemetry. Identify CNS values the controller mishandles: Linux's NVME_QUIRK_IDENTIFY_CNS for QEMU's old model and an Apple controller means "doesn't handle Identify value others than 0 or 1 correctly".
How to detect / prove
Read the opcode from the dmesg line (the %s part is nvme_opcode_str()). Re-issue it alone with a long timeout to separate "slow" from "hung".
Linux v7.2 source
pci.c: nvme_timeout; core.c: admin_timeout, nvme_alloc_admin_tag_set (set->timeout = NVME_ADMIN_TIMEOUT).
Test to provoke it
CAUTION: nvme format with a deliberately short --timeout on a large scratch drive (destroys data on the namespace).
C-09Invalid Doorbell async event — host wrote a bad doorbell ReportedNVMe queue
In a PEX trace
Visible The bad doorbell MWr is visible: offset 1000h + (2y or 2y+1)×(4<<DSTRD) for a queue that was never created, or a value ≥ the queue size from its Create command. If an Async Event Request is outstanding, a CQE MWr on the admin CQ for that AER CID follows, with DW0 type 0 (Error) and info 0 (Invalid Doorbell Register) or 1 (Invalid Doorbell Write Value).
What happens
The host (driver bug, or a user-space driver) writes a doorbell for a non-existent queue or a value beyond the queue size. The controller ignores the write and, if an AER command is outstanding, posts an Error-type asynchronous event. Some controllers then also need a reset.
How it shows up
The AEN. Linux v7.2 nvme_complete_async_event() stores the result in ctrl->aen_result for Error-type events and re-arms. It sends a uevent (through nvme_aen_uevent, carrying NVME_AEN=%#08x) rather than logging a kernel message, so check udevadm monitor --kernel. QEMU's model posts NVME_AER_INFO_ERR_INVALID_DB_REGISTER / _VALUE with log page Error Information and traces pci_nvme_ub_db_wr_invalid_cq, ..._invalid_cqhead, ..._invalid_sq, ..._invalid_sqtail.
Spec basis
NVMe Base Specification: Asynchronous Event Information for Error Status (Invalid Doorbell Register, Invalid Doorbell Write Value), doorbell register rules. The QEMU source quotes NVMe 1.3d section 4.1 on this behaviour.
Typical causes
Host bugs in custom or user-space drivers (SPDK-style, test tools). Using the wrong CAP.DSTRD stride. Writing a doorbell after the queue was deleted. Shadow-doorbell (DBBUF) mismatches.
How to detect / prove
nvme error-log (error information entries, if the device logs them). udev events. The trace (above) is the definitive proof.
Linux v7.2 source
core.c: nvme_complete_async_event, nvme_aer_type, nvme_aer_subtype; QEMU hw/nvme/ctrl.c: doorbell write handling (around the NVME_AER_INFO_ERR_INVALID_DB_* sites).
Test to provoke it
SAFE on QEMU / CAUTION on hardware: from a user-space driver, write the SQ tail doorbell of QID 99 with an AER outstanding. Verify the event and that the controller keeps working.
C-10Keep-alive loss (fabrics / KATO-enabled controllers) Timer onlyNVMe admin
In a PEX trace
Partly visible For a PCIe controller that uses KATO, the Keep Alive admin commands (opcode 18h) and their CQEs are visible with timestamps, so gaps longer than KATO are provable. For NVMe over Fabrics the keep-alive travels on the network, not on PCIe, so it is not in a PEX trace.
What happens
The Keep Alive Timer expires on the controller because the host did not send a Keep Alive in time (or, with Traffic Based Keep Alive, no traffic was seen). The controller then treats the host as gone, which on fabrics means tearing down the association. On the host side, a keep-alive command that fails or times out leads to a reset.
How it shows up
Linux v7.2: long keepalive RTT (%u ms) when a keep-alive took longer than its period; failed nvme_keep_alive_end_io error=%d; keep-alive failed: %ld (allocation failure, followed by nvme_reset_ctrl()); keep alive interval updated from %u ms to %u ms. For fabrics, KATO is mandatory (keep-alive support is mandatory for fabrics). PCIe controllers usually run with KATO=0, so keep-alive is not started (nvme_start_keep_alive returns early when kato == 0).
Spec basis
NVMe Base Specification: Keep Alive Timer feature (FID 0Fh), Keep Alive command, Traffic Based Keep Alive (CTRATT.TBKAS).
Typical causes
Host CPU stalls (softlockups), admin-queue saturation, network partitions (fabrics), controllers that count time differently.
How to detect / prove
nvme get-feature -f 0x0f /dev/nvmeX; dmesg strings above; on fabrics, a network capture.
Linux v7.2 source
core.c: nvme_keep_alive_work, nvme_keep_alive_end_io, nvme_start_keep_alive, nvme_stop_keep_alive, nvme_update_keep_alive.
Test to provoke it
CAUTION (fabrics): block traffic with a firewall rule for longer than KATO and watch the reconnect.
C-11Persistent Internal Error async event ReportedNVMe controller
In a PEX trace
Visible A CQE MWr on the admin CQ completing the outstanding Async Event Request with DW0 type 0 (Error), info 03h. Then, from Linux, a controller reset sequence (CC EN=0 ...) without any timeout gap in between. The internal fault itself is not visible.
What happens
The controller reports a persistent internal error, one that will not go away without intervention.
How it shows up
Linux v7.2 handles this subtype specially in nvme_complete_async_event(): for NVME_AER_ERROR_PERSIST_INT_ERR it calls nvme_handle_aer_persistent_error(), which logs resetting controller due to persistent internal error and calls nvme_reset_ctrl() (without re-arming the AER; the reset does that).
Spec basis
NVMe Base Specification: Asynchronous Event Type Error Status, Persistent Internal Error (03h); QEMU defines the same value (NVME_AER_INFO_ERR_PERS_INTERNAL_ERR = 3).
Typical causes
Internal memory errors, firmware faults, media controller failures.
How to detect / prove
dmesg; nvme error-log; SMART critical warnings; telemetry captured immediately.
Linux v7.2 source
core.c: nvme_complete_async_event, nvme_handle_aer_persistent_error.
Test to provoke it
Vendor-specific injection; on QEMU it would require modifying the model.
C-12Firmware activation never finishes (CSTS.PP stays set) Timer onlyNVMe controller
In a PEX trace
Visible The Firmware Commit admin command, the AEN CQE (Notice, Firmware Activation Starting), then Linux polling CSTS every 100 ms with PP=1 in the CplD data. If PP never clears within MTFA×100 ms (or admin_timeout when MTFA=0), the host stops polling and a controller reset sequence follows.
What happens
On activation without reset, the controller pauses command processing (CSTS.PP=1) while it switches firmware. If it never resumes within its advertised Maximum Time for Firmware Activation (MTFA), the host must reset it.
How it shows up
Linux v7.2 nvme_handle_aen_notice() on NVME_AER_NOTICE_FW_ACT_STARTING moves the controller to RESETTING ("(ab)using the RESETTING state to prevent subsequent recovery actions from interfering") and runs nvme_fw_act_work(). That quiesces I/O and polls nvme_ctrl_pp_status(). On timeout it logs Fw activation timeout, reset controller. Related: Firmware is activated after next Controller Level Reset (from the firmware slot log handling) and Get FW SLOT INFO log error.
Spec basis
NVMe Base Specification: Firmware Commit actions, CSTS.PP, MTFA in Identify Controller, Firmware Activation Notices.
Typical causes
Firmware images whose activation exceeds MTFA. MTFA reported as 0 or too small.
How to detect / prove
Compare measured PP=1 time with nvme id-ctrl mtfa. Check that I/O resumes without a reset.
Linux v7.2 source
core.c: nvme_handle_aen_notice, nvme_fw_act_work, nvme_get_fw_slot_info.
Test to provoke it
CAUTION/EXPERT: firmware download and commit with action "activate immediately" on a test drive, under I/O, while capturing the trace. Risk of bricking with an incorrect image.
C-13CRTO smaller than CAP.TO — inconsistent ready-timeout advertisement ReportedNVMe registers
In a PEX trace
Visible The MRd of CAP (64-bit, read as two 32-bit reads) and of CRTO (BAR0+68h) and their CplD data show the inconsistent values directly.
What happens
The controller advertises a CRTO (Controller Ready With Media Timeout) smaller than CAP.TO. A host that trusts CRTO alone may give up too early.
How it shows up
Linux v7.2 logs bad crto:%x cap:%llx once and uses the larger value. The source comment says "CRTO should always be greater or equal to CAP.TO, but some devices are known to get this wrong."
Spec basis
NVMe Base Specification: CAP.CRMS, CRTO register (CRWMT/CRIMT).
Typical causes
Firmware filling the newer register incorrectly.
How to detect / prove
nvme show-regs; dmesg.
Linux v7.2 source
core.c: nvme_enable_ctrl.
Test to provoke it
Inspection only.
