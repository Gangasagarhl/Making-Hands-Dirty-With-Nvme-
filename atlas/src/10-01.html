PART I

How Failures Show Themselves

An error code is only one of four ways a failure can appear. Many of the most expensive NVMe and PCIe bugs never produce one: the command "succeeds", nothing is logged, and the trace looks normal. This part sets out the four classes, where the evidence for each lives, and how to use the rest of the atlas.

1 The Four Ways a Failure Shows Itself

1.1 Why error codes are not enough

The NVMe specification defines a status code for every command, and PCIe defines an Advanced Error Reporting (AER) bit for every error a link or transaction layer detects. It is tempting to think that if neither reports anything, nothing went wrong. That is false in three common ways:

  • Something took too long. A command that never completes has no status code at all, because there is no completion to carry one. Only a timer notices: the PCIe Completion Timeout in the device or root port, or the host driver's command timeout (30 seconds by default in Linux v7.2 for I/O).
  • Something "succeeded" without doing its job. A Flush that returns success while data is still only in a volatile cache, or a Deallocate (TRIM) that returns success while the blocks stay mapped. The command, the data and a clean completion are all on the wire, so a protocol analyzer shows nothing wrong. The failure happens inside the device, where no trace can see it.
  • Everything works, just worse. A Gen5 x4 link that trained at Gen3 x2, or a drive that throttles under heat. No error is raised anywhere; the only symptom is a number that is lower than it should be.

1.3 The user's example in one paragraph

📘 Write 10 GB, then trim the last 5 GB

When a file is truncated, the filesystem can ask Linux to discard the freed blocks. The NVMe driver sends a Dataset Management command with the Deallocate attribute (or Write Zeroes with the Deallocate bit), listing the LBA ranges. On the wire you see the command, the range list being fetched by the device, and a successful completion. Whether the controller actually unmapped those LBAs happens inside the SSD, so no analyzer can see it, and the specification treats deallocation as something the controller may or may not carry out in full (verify the exact wording for your revision). A failure here is Silent. It can only be proven indirectly: reading back the range and comparing against the drive's advertised read behaviour (DLFEAT), enabling the Deallocated or Unwritten Logical Block error, or watching the namespace utilization counter (NUSE) before and after. Part IV works through this example step by step.

1.5 How to use this atlas

  • Debugging a symptom: find the card whose "How it shows up" matches what you see, then follow "How to detect / prove".
  • Writing a test plan: walk the master catalog and make sure every Silent and Degraded card has a test, because nothing else will catch those.
  • Reading a trace: Part VII lists the rule violations a protocol checker, or a script over an exported PEX capture, can flag.
  • Working with an AI assistant: Part IX shows what to hand over (exports, logs, register dumps) and what an assistant can and cannot conclude.
⚠️ Sources and limits

The cards cite the Linux kernel v7.2 NVMe and PCI source, QEMU's NVMe controller model and libnvme's type definitions, which were read directly, plus public research where cited. The NVMe and PCIe specifications themselves could not be downloaded from this environment, so spec wording is paraphrased and anything not confirmed in those sources is tagged uncertain or "verify in spec". Kernel behaviour described here is Linux v7.2's and can differ in other versions or operating systems.
