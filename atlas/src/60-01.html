PART VII

Spec Violations You Can Only See in a Trace

Some failures never produce a status code, an AER bit or a log entry, yet they are plainly visible to anyone who looks at the wire: a doorbell value that points past the end of a queue, a completion that overtakes its own data, a command identifier used twice, a TLP bigger than the link allows. This part lists the rules that a protocol checker can enforce mechanically on a PEX trace — a PCIe protocol-analyzer capture file (such as a Teledyne LeCroy capture) viewed in the analyzer software, or a script over its CSV/text export. Every card starts with a verdict: Visible, Partly visible or Not visible in a PEX trace. Each card names the rule, shows what the violation looks like in a trace, and explains why it matters even when "nothing failed".

VII.1 How a Protocol Checker Thinks

A protocol checker is a state machine that replays a captured trace and asks, for every packet: was this event legal given everything that happened before it? It does not need to know whether the drive returned the right data; it only needs the rules of the protocol and enough state to apply them. This makes it the perfect tool for a class of bugs that are invisible to the operating system: the host and the device can both "work" while one of them breaks a rule that the other happens to tolerate today and will not tolerate on the next firmware, the next switch, or the next CPU.

🧒 Kid analogy

A referee does not care who wins the football match. The referee only checks: was that pass offside? Did that player touch the ball with a hand? A protocol checker is a referee for the bus. It can blow the whistle even when the goal still counts.

🧩 Where the analogy breaks

A referee sees the whole pitch. A checker sees only what the probe captured: if the analyzer sits on the link between the root port and the SSD, it sees TLPs and DLLPs on that link, but it does not see what the CPU wrote into host memory unless that data later crosses the link (for example, when the controller fetches a submission queue entry). Many NVMe rules can therefore only be checked indirectly, by watching the controller read the memory.

📭 What a PEX trace cannot show
  • Device internals: media, caches, FTL mapping, whether a deallocate really unmapped LBAs, power state inside the controller.
  • Host memory except as TLP payloads that cross the probed link: the host writing an SQE into DRAM is invisible; the controller fetching it (MRd + CplD) is visible.
  • Other links: traffic on a different port of a switch, or inside the root complex, is not in the capture.
  • Timeouts appear only as an absence plus timestamps (a request with no completion within N ms).
  • AER registers are visible only if software reads them with configuration reads over the probed link, or the device sends ERR_COR / ERR_NONFATAL / ERR_FATAL messages.
  • Host logs (dmesg, driver messages) are never in the trace — collect them separately and align the clocks.

VII.1.2 Three kinds of rule

  • Stateless rules look at one packet: TLP payload larger than MPS, read request larger than MRRS, request crossing a 4 KiB boundary, PRP2 with a non-zero offset, reserved bits set. Cheap, no false positives if the configuration (MPS, MRRS, page size) is known.
  • Stateful rules need history: CID reuse needs the set of outstanding commands; phase-tag checks need the CQ position and wrap count; Unexpected Completion needs the set of outstanding PCIe tags. The checker must start from a known state — ideally from controller enable (CC.EN 0→1) or queue creation — or it must "learn" state for a while and suppress findings until it is synchronised.
  • Ordering rules compare the timing of two related events: the CQE must not reach host memory before the data; the MSI-X must not arrive before the CQE it announces. These depend on where the probe sits: an analyzer on the SSD link sees the order in which the device sent the TLPs, which is what the PCIe ordering rules constrain; what the CPU observes also depends on the root complex.
💡 Senior insight

Most violations in this part are not reported by either side. The controller is allowed to ignore a bad doorbell; the host driver silently drops a CQE for an unknown CID with a log line; a PCIe receiver may or may not check the 4 KiB rule. "No error in dmesg" means only "nobody who checks was looking". The trace is the only witness — which is why a validation lab runs a checker on every capture, not only on failing ones.

VII.2 Queue and Doorbell Protocol Violations

The NVMe queue model is a pair of circular buffers per queue pair with strict producer/consumer ownership: the host produces SQ entries and advances the SQ tail doorbell; the controller consumes them and reports its consumer position in the CQE's SQ Head Pointer (SQHD); the controller produces CQ entries, marking each new pass with an inverted Phase Tag; the host consumes them and returns slots by writing the CQ head doorbell. A queue with N entries holds at most N−1 items: "full" is (tail + 1) mod N == head, "empty" is head == tail. Every card below is a violation of this ownership contract. verified

V-01SQ tail doorbell value beyond queue size ReportedNVMe queue
In a PEX trace
Visible Doorbell MWr (host→device, 4 B) to BAR0 + 1000h + 2y·(4<<DSTRD) whose data ≥ QSIZE+1 taken from the captured Create I/O SQ command; afterwards no SQE-fetch MRd from that SQ. A resulting async event is visible as a 16-byte CQE MWr to the admin CQ only if an AER command was outstanding.
What happens
The host writes an SQ y Tail Doorbell with a value ≥ the number of entries of that SQ (for example tail = 70 on a 64-entry queue). The value cannot be a slot index.
How it shows up
The controller ignores the write. If an Asynchronous Event Request is outstanding it may post an Error-type async event "Invalid Doorbell Write Value" and log an entry in the Error Information log. If no AER is outstanding, nothing is reported — commands placed in the SQ are simply never fetched and later time out.
Spec basis
NVMe Base: SQ Tail Doorbell register semantics; asynchronous event information "Invalid Doorbell Write Value" (Error event type). QEMU quotes the rule from NVMe 1.3d in nvme_process_db: "If host software writes an invalid value to the Submission Queue Tail Doorbell or Completion Queue Head Doorbell register and an Asynchronous Event Request command is outstanding, then an asynchronous event is posted…".
Typical causes
Host driver modulo bug (wrap at 2n instead of queue size); queue resized by a Create I/O SQ with a different QSIZE than the driver uses (QSIZE is 0's based); memory corruption of the driver's tail variable; a user-space driver (SPDK-style) with a stale queue configuration after reset.
How to detect / prove
Checker rule: for each doorbell MWr, decode queue id from offset and compare the value against the QSIZE+1 seen in the Create I/O SQ command (or AQA.ASQS+1 for the admin queue). On Linux, look for nvme_async_event trace events and nvme error-log entries; Linux v7.2 records the result in ctrl->aen_result.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_write_sq_db writes nvmeq->sq_tail, which nvme_sq_copy_cmd wraps at nvmeq->q_depth; drivers/nvme/host/core.c:nvme_complete_async_event handles NVME_AER_ERROR.
Test to provoke it
On QEMU (SAFE): use a user-space driver or nvme-cli is not enough — write the doorbell with a raw BAR mapping of an emulated device and watch the QEMU trace event pci_nvme_ub_db_wr_invalid_sqtail. On real hardware this is EXPERT: an unbound device, a vfio-based test harness, and an AER posted beforehand.
V-02CQ head doorbell value beyond queue size ReportedNVMe queue
In a PEX trace
Visible Doorbell MWr to BAR0 + 1000h + (2y+1)·(4<<DSTRD) with data ≥ CQ size; later SQE fetches continue but CQE MWr on that CQ stop after N−1 entries — the "device went quiet" pattern.
What happens
The host writes a CQ y Head Doorbell with a value ≥ the CQ size. The controller cannot interpret how many entries were released.
How it shows up
Write ignored; optional Error async event "Invalid Doorbell Write Value". Because the head is not advanced, the controller eventually sees the CQ as full and stops posting completions: all I/O on every SQ that shares that CQ stalls and then times out.
Spec basis
NVMe Base: CQ Head Doorbell semantics; same asynchronous event as V-01.
Typical causes
Host increments head past the end instead of wrapping; head computed in bytes instead of entries; CQ created with fewer entries than the driver assumes.
How to detect / prove
Same checker rule as V-01, against the CQ size from Create I/O CQ (QSIZE+1) or AQA.ACQS+1. Correlate: after the bad doorbell, CQE MWr count on that CQ stops at exactly size−1 outstanding entries.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_update_cq_head wraps cq_head at q_depth and flips cq_phase; nvme_ring_cq_doorbell writes it.
Test to provoke it
QEMU (SAFE): raw doorbell write of size+2 on an idle CQ; observe pci_nvme_ub_db_wr_invalid_cqhead and, with an AER outstanding, an async event on the admin CQ.
V-03Doorbell write for a queue that does not exist ReportedNVMe queue
In a PEX trace
Visible Doorbell MWr to an offset whose queue id was never created in the captured admin traffic, or written after the Delete I/O SQ/CQ completion; no fetch MRd follows. Requires the capture to include queue creation (start it before the driver loads, or decode CAP.DSTRD and Create commands from an earlier capture).
What happens
The host writes a doorbell offset belonging to a queue id that was never created, was already deleted, or exceeds the number of queues granted by Set Features Number of Queues.
How it shows up
Ignored by the controller; optional Error async event "Invalid Doorbell Register". QEMU's comment notes that the spec defines this code but "nowhere does it specify when to use it", and QEMU uses it for non-existent queues — so other controllers may report it differently or not at all. impl
Spec basis
NVMe Base: doorbell register layout (1000h + (2y)·(4<<CAP.DSTRD)); asynchronous event information "Invalid Doorbell Register".
Typical causes
Wrong CAP.DSTRD (doorbell stride) used by the host, so every doorbell lands on the wrong queue; queue deleted while another CPU still submits; use-after-teardown during reset; SR-IOV VF using PF queue numbering.
How to detect / prove
Checker keeps the set of live SQ/CQ ids from Create/Delete I/O SQ/CQ commands and their successful CQEs; any doorbell outside the set is flagged. A wrong stride shows as doorbells at offsets that are not multiples of 4<<DSTRD apart.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_create_queue sets up per-queue q_db pointers from dev->db_stride; teardown paths in nvme_dev_disable.
Test to provoke it
QEMU (SAFE): write SQ tail doorbell of queue id conf_ioqpairs+1; QEMU trace pci_nvme_ub_db_wr_invalid_sq. A synthetic example appears as rule DB-NOQ in 7.6.
V-04Misaligned or partial doorbell write SilentNVMe register
In a PEX trace
Visible MWr in the doorbell region with Length ≠ 1 DW, byte enables ≠ Fh, or a 2-DW write spanning SQ tail and CQ head of one pair.
What happens
A doorbell is written with a 1- or 2-byte access, or at an address that is not dword aligned, or a 64-bit write spans two doorbells (SQ tail and CQ head of the same pair).
How it shows up
Nothing is reported. QEMU logs a guest-error trace (pci_nvme_ub_db_wr_misaligned) and ignores the write; real controllers may ignore, latch only some bytes, or update both doorbells. impl
Spec basis
NVMe Base: controller registers are accessed with their natural width; doorbells are 32-bit registers. Accesses of other sizes are outside the defined behaviour.
Typical causes
Compiler merging two adjacent 32-bit stores into one 64-bit store on a write-combining mapping; a user-space driver using memcpy to MMIO; byte-wise BAR access tools.
How to detect / prove
Checker: doorbell MWr whose length ≠ 4 bytes, whose first/last byte enables are not 1111b, or whose address is not 4-byte aligned.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_write_sq_db and nvme_ring_cq_doorbell use writel (32-bit).
Test to provoke it
QEMU (SAFE): 16-bit write to a doorbell; check QEMU trace output.
V-05SQ tail moves backwards or overruns unfetched entries SilentNVMe queue
In a PEX trace
Visible Sequence of SQ tail doorbell values that implies more than N−1 unfetched entries (or a "backwards" move), compared with the SQE-fetch MRd/CplD count and SQHD in CQEs; re-fetched slots whose 64 bytes equal an already-completed SQE.
What happens
The new SQ tail value implies either a negative number of new entries (tail moved "backwards", i.e. the host withdrew entries) or so many new entries that the SQ would hold ≥ N items — the host has overwritten SQEs the controller had not yet fetched.
How it shows up
Nothing reported: the value is in range, so V-01 does not fire. Modulo arithmetic hides the problem — a backwards move looks like "N−k new commands". Consequences range from duplicated commands (the controller re-executes stale SQEs from a previous pass, e.g. a stale Write re-writes old data) to lost commands that time out.
Spec basis
NVMe Base queue model: the host shall not submit to a full SQ (full = tail+1 == head); entries between head and tail are owned by the controller and must not be modified by the host. The host learns the head from SQHD in CQEs.
Typical causes
Two CPUs submitting to one SQ without a lock; driver uses CQ depth for flow control while CQ is shared by several SQs; SQHD ignored and SQ larger than outstanding-request budget assumed; a reset path that zeroes the driver's tail but not the controller's.
How to detect / prove
Checker: keep host tail T, controller head H (from the most recent SQHD and from observed fetches); for a new tail T', new = (T'−T) mod N; flag if new > (N−1) − ((T−H) mod N). Also flag if the data of a re-fetched slot is identical to an already-completed SQE (stale replay).
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_sq_copy_cmd under nvmeq->sq_lock; nvme_commit_rqs rings only when sq_tail != last_sq_tail. Linux sizes SQ and CQ identically and limits outstanding requests via blk-mq tags, so it does not need SQHD for flow control (it only passes it to trace_nvme_sq).
Test to provoke it
QEMU (SAFE): QEMU does not check this (see 7.1.3) — write tail values out of order and observe re-executed commands; a good negative test for your checker.
V-06CQ head released past the controller's tail SilentNVMe queue
In a PEX trace
Visible CQ head doorbell value ahead of the number of 16-byte CQE MWr written to that CQ since the previous head.
What happens
The host writes a CQ head that releases more entries than the controller has posted. The controller now believes there is free space that actually contains its own future slots; its full/empty calculation is corrupted.
How it shows up
No status. Later the controller may overwrite CQEs the host has not yet consumed (because it thinks they were released), producing lost completions (timeouts) or, combined with phase-tag reuse, stale completions processed twice.
Spec basis
NVMe Base queue model: the host releases only entries it has consumed (entries with the current phase).
Typical causes
Host consumes entries by index without checking the phase tag (polling bug); host and controller disagree on CQ size; a missed wrap in the host.
How to detect / prove
Checker counts CQE MWr per CQ (device tail) and compares every CQ head doorbell: released = (H'−H) mod N must be ≤ (Tail−H) mod N. Rule CQDB-PAST-TAIL in 7.6.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_poll_cq consumes entries only while nvme_cqe_pending (phase match) and rings the head once, after the loop.
Test to provoke it
QEMU (SAFE) with a test harness: post one command, write CQ head = 3. QEMU will not complain; your checker should.
V-07CQ overflow: head not advancing, or controller posts into a full CQ Timer onlyNVMe queue
In a PEX trace
Visible (a) N−1 CQE MWr then no CQ head doorbell for a long time; (b) a CQE MWr to the slot just before the current head. Timeout is visible only as absence plus timestamps (a fetched command with no CQE within the host timeout).
What happens
Two variants. (a) The host stops advancing the CQ head (interrupt lost, CPU stuck, driver bug); the CQ fills to N−1 entries and the controller must stop posting — I/O stalls. (b) The controller posts while the CQ is full, overwriting an entry the host has not consumed.
How it shows up
(a) Only the host's I/O timeout, often with Linux "completion polled" if the CQE was actually there (see V-15). (b) Nothing; the overwritten completion is lost and its command times out; the overwriting entry may carry the "wrong" phase from the host's point of view.
Spec basis
NVMe Base: CQ full condition (head == tail+1); the controller does not post to a full CQ and the host is responsible for sizing CQs so that the commands that can be outstanding on its SQs fit. QEMU nvme_post_cqes breaks out of its loop when nvme_cq_full.
Typical causes
(a) Missing MSI-X (V-15), interrupt affinity to an offline CPU, softirq starvation. (b) Controller firmware not tracking the CQ head doorbell; several SQs mapped to one small CQ.
How to detect / prove
Checker: keep CQ tail (count of CQE writes) and head (doorbells); flag a CQE write when (tail+1) mod N == head. For (a), flag "CQ head unchanged for X ms while CQ non-empty".
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_timeout polls the CQ first and prints "I/O tag %d (%04x) QID %d timeout, completion polled" when the CQE was present.
Test to provoke it
QEMU (SAFE): issue N commands while never writing the CQ head; verify QEMU stops at N−1 CQEs. On hardware, the (b) variant needs an analyzer to prove.
V-08Command Identifier reused while still outstanding SilentNVMe command
In a PEX trace
Visible Two SQE-fetch CplDs on the same SQ carrying the same CID (DW0 bits 31:16) with no CQE MWr for that CID between them.
What happens
The host submits a command whose CID equals that of a command still outstanding on the same SQ. Completions become ambiguous: the host cannot tell which of the two finished, and Abort (which names SQID+CID) becomes ambiguous too.
How it shows up
Usually nothing. A controller may detect it and complete the new command with Generic status 03h "Command ID Conflict" (Linux NVME_SC_CMDID_CONFLICT); many controllers do not check. QEMU does not check (its nvme_abort would match the first request with that CID). impl
Spec basis
NVMe Base: the Command Identifier together with the SQ Identifier uniquely identifies a command outstanding at the controller; Generic Command Status "Command ID Conflict".
Typical causes
Host reusing a tag before its completion was processed; driver completing a request on timeout and reusing the tag while the controller still owns the original; user-space drivers with fixed CIDs.
How to detect / prove
Checker keeps the outstanding set per SQ: add (SQID,CID) on SQE fetch, remove on CQE. Flag duplicates (rule CID-REUSE in 7.6). Linux encodes a 4-bit generation counter into the top bits of the CID, so a reused tag normally has a different CID — a duplicate in a Linux trace is strong evidence of a real bug.
Linux v7.2 source
drivers/nvme/host/nvme.h:nvme_cid = nvme_cid_install_genctr(genctr) | rq->tag; nvme_find_rq checks the generation counter.
Test to provoke it
QEMU (SAFE) user-space harness: submit two long reads with the same CID; verify the checker flags it; on hardware, check whether the controller returns status 03h.
V-09CQE for an unknown or already-completed CID ReportedNVMe command
In a PEX trace
Visible A CQE MWr whose DW3 CID matches no earlier SQE fetch on that SQ, or matches a CID that already completed. The host's "invalid id" log line is NOT in the trace.
What happens
The controller writes a completion whose CID matches no outstanding command on that SQ — a duplicate completion, a corrupted CID, or a completion for a command the host already aborted/timed out.
How it shows up
Linux v7.2 logs "invalid id %d completed on queue %d" (or "request %#x genctr mismatch (got … expected …)") and drops the entry. Other drivers may complete the wrong request — a silent data-integrity hazard (the wrong buffer is declared ready).
Spec basis
NVMe Base: each command is completed exactly once by one CQE identifying it by SQID+CID.
Typical causes
Controller firmware posting a completion twice (retry path); CQE corrupted in flight (bit flip in DRAM or a poisoned TLP ignored); host timeout handling that freed the tag while the command was still executing.
How to detect / prove
Checker rule CQE-UNKNOWN. In Linux, grep dmesg for "invalid id" and "genctr mismatch". A trace distinguishes "duplicate" (CID seen in an earlier CQE) from "never submitted" (CID never fetched).
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_handle_cqe; drivers/nvme/host/nvme.h:nvme_find_rq.
Test to provoke it
QEMU fault injection is not built in; use a modified QEMU or an FPGA/emulator that duplicates a CQE (EXPERT). In the synthetic example, CID 0x99 triggers it.
V-10Wrong SQID or non-advancing SQHD in a CQE SilentNVMe command
In a PEX trace
Visible CQE MWr whose DW2 SQID differs from the queue the CID was fetched from, or whose SQHD sequence does not advance while SQE fetches proceed.
What happens
The CQE's SQ Identifier (DW2 bits 31:16) names a different SQ than the one the command came from, or SQ Head Pointer (DW2 bits 15:0) moves backwards, beyond the tail, or never advances although commands are being consumed.
How it shows up
With a shared CQ, a wrong SQID makes the host look up the CID in the wrong SQ — wrong request completed or "invalid id". A frozen SQHD makes a host that uses SQHD for flow control believe the SQ is full: throughput collapses to zero without any error. Linux, which does not use SQHD for flow control, is unaffected — so the same SSD "works on Linux, hangs on another OS".
Spec basis
NVMe Base: CQE DW2 SQID and SQHD semantics — SQHD indicates the current SQ head pointer for the SQ named by SQID.
Typical causes
Firmware filling SQHD from a stale variable; CQE template reused across queues; SQHD reported before the fetch actually advanced the head.
How to detect / prove
Checker: SQID must equal the SQ the CID was fetched from; SQHD must satisfy (SQHD − previous SQHD) mod N ≤ number of fetches since, and must never pass the host tail.
Linux v7.2 source

V-11Phase tag not inverted on CQ wrap Timer onlyNVMe queue
In a PEX trace
Visible CQE MWr to slot 0 after a wrap carrying the same phase bit as the previous pass (decode bit 16 of DW3 / bit 0 of the status half).
What happens
After the controller wraps from the last CQ slot to slot 0 it must invert the Phase Tag (P, bit 0 of the status half of DW3). If it keeps the old value, the host — which expects the new phase — sees the new entry as "old" and does not consume it; if it inverts too early, the host consumes stale entries.
How it shows up
Missing inversion: completions invisible to the host → I/O timeout (Linux may report "completion polled" only if the phase matches; here it does not, so a plain timeout and abort/reset follow). Early inversion: stale CQEs processed twice → "invalid id" messages or double completion.
Spec basis
NVMe Base: Phase Tag "identifies whether a completion queue entry is new"; it is inverted each pass through the CQ; host initialises the CQ memory to zero so the first pass uses P=1.
Typical causes
Firmware wrap logic off by one; CQ size mismatch between host and controller; controller reset without the host re-zeroing CQ memory.
How to detect / prove
Checker keeps tail and expected phase per CQ (start 1, invert at wrap) and compares every CQE (rule PHASE in 7.6). Note that a phase error is often the symptom of an earlier V-07(b) overflow; always report the first abnormal event.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_cqe_pending compares status & 1 with nvmeq->cq_phase; nvme_update_cq_head flips cq_phase at wrap.
Test to provoke it
Run enough I/O to wrap a small CQ many times (e.g. io_queue_depth=2 module parameter — the minimum Linux accepts — on a test system, SAFE) and verify no phase findings in the capture.
V-12Shadow doorbell buffer out of sync with the MMIO doorbell SilentNVMe queue
In a PEX trace
Partly visible Controller MRd of the shadow-doorbell buffer and the CplD values it returns are visible, as are MMIO doorbells; the host's own writes to the shadow buffer are CPU-to-DRAM and never cross the link. Only a mismatch between returned shadow values and later MMIO doorbells can be shown.
What happens
With the Doorbell Buffer Config admin command (used mainly by emulated/virtual controllers), the host writes doorbell values into a shadow buffer in host memory and only rings the real MMIO doorbell when the controller's EventIdx says so. If the host updates one but not the other, or ignores EventIdx, the controller works from a stale tail/head.
How it shows up
Stalls that recover when any later doorbell is rung; latency spikes; no error. QEMU's nvme_process_db comments that "various drivers including ones that run on Linux, are not updating Admin Queues" in the shadow buffer, so QEMU writes the admin values back itself. impl
Spec basis
NVMe Base: Doorbell Buffer Config command — Shadow Doorbell buffer and EventIdx buffer; QEMU quotes "the host shall also update the controller's corresponding doorbell property to match the value of that entry in the Shadow Doorbell buffer".
Typical causes
Missing memory barrier between the shadow write and the EventIdx read; admin queue excluded from shadowing in the driver; migration of a VM between hosts.
How to detect / prove
In a VM, the "trace" is QEMU's own tracing (pci_nvme_* events) or a vhost/vfio capture. Compare shadow value reads (DMA reads of the shadow buffer) with MMIO doorbells.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_dbbuf_update_and_check_event, called from nvme_write_sq_db and nvme_ring_cq_doorbell.
Test to provoke it
QEMU (SAFE): enable shadow doorbells (they are used automatically when the controller supports the command) and stress small-queue workloads while tracing pci_nvme_mmio_doorbell_sq.
