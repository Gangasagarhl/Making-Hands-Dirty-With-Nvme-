V-B.3 Flit Mode (PCIe 6.0 and Later): FEC, CRC and Flit Replay

V-B.3.1 What changes in Flit mode

At 64 GT/s PCIe uses PAM4 signalling, which has a much higher raw bit error rate than the earlier NRZ rates. To keep latency low, PCIe 6.0 does not add a heavy FEC. It packs everything into fixed 256-byte Flits. Public descriptions (Synopsys and Cadence verification blogs, an Intel talk at the OpenFabrics 2022 workshop) give this layout: 236 bytes of TLP space, 6 bytes of DLP (data-link payload carrying Ack/Nak and flow-control information), 8 bytes of CRC and 6 bytes of ECC. The ECC is a lightweight, three-way-interleaved code that corrects one byte per group, so a burst of up to 16 bits on one lane is correctable. The CRC then decides whether the Flit is accepted. A CRC failure leads to a Nak and a Flit replay. The Intel talk describes the design target as a pre-FEC first-bit error rate around 10−6, with a strong CRC so that undetected errors stay far below one per 109 hours uncertain (from search excerpts). In Flit mode, TLPs no longer carry their own LCRC and 12-bit sequence number: those checks move to the Flit level. Linux v7.2 reports Flit mode through PCI_EXP_LNKSTA2_FLIT and prints ", in Flit mode" in __pcie_print_link_status. Flit mode can also be negotiated at lower data rates when both ends support it version.

🔍 Trace

For a Flit-mode capture, the analyzer must know the link is in Flit mode, which it learns from training ordered sets or configuration. It then checks FEC and CRC itself. Expect three counts: Flits with errors corrected by FEC (normal at 64 GT/s, and a measure of margin), Flits with CRC failures (each must be followed by a Nak and replay), and replayed Flits. TLP-level LCRC checks from X-15 do not apply in this mode.

X-23Flit CRC failure / FEC-uncorrectable Flit DegradedPCIe Flit
In a PEX trace
Visible On a Flit-capable analyzer: Flits flagged as FEC-corrected (with the corrected byte positions) and Flits flagged as CRC-failed. A CRC-failed Flit should be followed by a Nak in the DLP bytes of the opposite direction, then a replay of that Flit (or of it and those after it).
What happens
When more errors hit a Flit than FEC can correct, the CRC fails and the receiver discards the Flit. Its TLPs and DLP content are recovered by replay. A rising FEC-corrected count is the early warning. A rising CRC-failure count costs bandwidth and latency.
How it shows up
Correctable errors in AER on the receiving device (the exact AER bits and any Flit-specific counters depend on the spec version and implementation uncertain). Linux v7.2 can log TLP headers captured in Flit format (PCI_ERR_CAP_TLP_LOG_FLIT). No NVMe-level effect unless replays escalate.
Spec basis
PCIe Base Specification 6.0 and later, Flit mode: FEC, CRC, Flit replay.
Typical causes
PAM4 channel margin, equalization, crosstalk, retimers; burst errors longer than the FEC can handle.
How to detect / prove
Track FEC-corrected and CRC-failed Flits per lane and per second, and compute the replay overhead. Compare FEC-corrected rates between slots or cables as a margin measure. Confirm CRC failures by the link partner's Nak.
Linux v7.2 source
drivers/pci/pcie/aer.c (Flit-format TLP log handling with PCI_ERR_CAP_TLP_LOG_FLIT); drivers/pci/pci.c: __pcie_print_link_status. See V-37.
Test to provoke it
EXPERT: Gen6 receiver margining or a lossy channel; error injection with a Gen6 exerciser.
X-24Flit sequence and replay anomalies (replay storms, wrong Nak target, missing Ack) DegradedPCIe Flit
In a PEX trace
Visible Flit sequence numbers and the Ack/Nak information in DLP bytes are decoded by Flit-aware analyzers. Look for replays without a preceding CRC failure, Naks naming a Flit that was received correctly, the same Flit replayed many times, or a gap in sequence numbers of new Flits.
What happens
Flit mode keeps an Ack/Nak replay protocol at Flit granularity. Public material mentions optimisations such as not replaying Flits that carry only NOP content and replaying only the failed Flit uncertain. Implementation bugs in this new protocol show as unnecessary replays or, in the worst case, lost TLPs.
How it shows up
Mostly bandwidth loss and latency. Errors that break the protocol are expected to be reported as Data Link Protocol errors or similar uncorrectable errors verify in spec.
Spec basis
PCIe Base Specification 6.0 and later, Flit sequence numbers, Ack/Nak in Flit mode, replay rules.
Typical causes
Early silicon and IP bugs, retimer handling of Flit replay, interaction with L0p (partial-width power state) transitions uncertain.
How to detect / prove
Per direction, list new Flit sequence numbers and replays. Pair each Nak with the CRC-failed Flit it refers to. A Nak with no CRC failure seen by the analyzer is either a receiver bug or an analyzer miss: check lane errors at that moment.
Linux v7.2 source
drivers/pci/pcie/aer.c ("DLP" for protocol errors).
Test to provoke it
EXPERT: Gen6 exerciser injecting CRC errors in chosen Flits and checking the DUT's replay choices.
X-25Flit mode or top speed not negotiated: link runs in non-Flit mode or below 64 GT/s DegradedPCIe Physical
In a PEX trace
Visible In training ordered sets, each side advertises its supported data rates and Flit-mode support. The trace shows who did not advertise it, or at which equalization step the attempt to reach 64 GT/s failed and the link fell back.
What happens
Both ends must support Flit mode for it to be used, and 64 GT/s requires it. A missing capability bit, a firmware setting or an equalization failure leaves a Gen6 SSD running at Gen5 or lower.
How it shows up
lspci -vvv LnkSta speed below LnkCap; Linux v7.2 prints available bandwidth and whether the link is in Flit mode; PCI_EXP_FLAGS_FLIT (Flit Mode Supported) and PCI_EXP_LNKSTA2_FLIT (Flit Mode Status).
Spec basis
PCIe Base Specification 6.0 and later, training ordered-set fields for Flit mode, PCI Express Capabilities register Flit Mode Supported, Link Status 2 Flit Mode Status.
Typical causes
One side lacks support, a disabled Flit mode in firmware or BIOS, a retimer in between that does not support it, equalization failure at 64 GT/s (X-13).
How to detect / prove
Capture training from reset and read both sides' advertisements. Compare with config-space capability bits read by software.
Linux v7.2 source
include/uapi/linux/pci_regs.h: PCI_EXP_FLAGS_FLIT, PCI_EXP_LNKSTA2_FLIT; drivers/pci/pci.c: __pcie_print_link_status.
Test to provoke it
SAFE: compare behaviour with and without a retimer/riser; record training each time.
X-26Error-message storm on the wire: ERR_COR / ERR_NONFATAL / ERR_FATAL messages ReportedPCIe Transaction
In a PEX trace
Visible Upstream Message TLPs from the SSD with error-message codes (ERR_COR 30h, ERR_NONFATAL 31h, ERR_FATAL 33h). Their rate and timing, relative to physical and link events just before them, show which event the SSD reported. If the host reads the SSD's AER registers during the capture, the config-read completions show which status bits were set.
What happens
An endpoint that detects an error and has reporting enabled sends an error message to the Root Port. A link with constant correctable errors produces a steady stream of ERR_COR messages and AER interrupts on the host.
How it shows up
On the host: AER interrupts, rate-limited dmesg lines, counters in sysfs. Sometimes a message storm costs measurable CPU time.
Spec basis
PCIe Base Specification, error signalling with messages; Device Control error-reporting enables; AER.
Typical causes
Any of the physical or link-layer problems in this part, or device-internal correctable errors (Corrected Internal Error).
How to detect / prove
Count error messages per second in the trace. For each, look back for the triggering event in the opposite direction (errors in TLPs the SSD received). If there is no visible trigger, the error is internal to the SSD or on its receive side below what the analyzer decoded.
Linux v7.2 source
drivers/pci/pcie/aer.c: aer_irq, aer_isr_one_error, aer_ratelimit. See Chapter 20.
Test to provoke it
SAFE: run a workload on a link with known correctable errors and correlate trace message counts with sysfs counters.

V-B.4 Analyzer-Induced Artifacts: When the Trace Is Wrong

V-B.4.1 Why this chapter exists

An analyzer is a receiver too, attached through extra hardware. It can report errors that the link partners never saw, and miss packets they exchanged. Vendors say their probes are designed to be transparent (Teledyne LeCroy describes high-impedance, non-intrusive probing; SerialTek says its SI-Fi interposers pass link training through without calibration) uncertain. Every analyzer still depends on correct setup, signal quality at the tap, and re-locking after idle and speed changes. A Teledyne LeCroy technical note on SuperSpeed (USB) analyzers also explains why analyzers that keep raw 10b symbols can show which invalid code arrived, while a PHY that reports only an error flag cannot. The same idea applies to PCIe raw-symbol views. These cards are about the trace itself. Their "rep" class describes what the system reports, which is usually nothing.

X-27Probe or interposer signal-integrity effects (errors caused or hidden by the tap) SilentAnalyzer
In a PEX trace
Partly visible Visible: errors flagged by the analyzer. Not visible: whether the link partners saw them. Tell-tale sign of an analyzer-only error: a TLP flagged with a bad LCRC that the receiver Acks with no replay, or symbol errors with no Nak, no Recovery and no AER counter change.
What happens
Two cases. (a) The interposer adds loss or reflections, so the real link gets worse: more errors, lower speed, extra Recovery, only while the probe is installed. (b) The analyzer's own receiver decodes worse than the link partners: the trace shows errors the link does not have.
How it shows up
Case (a): real AER counts and speed changes that disappear without the interposer. Case (b): nothing on the system.
Spec basis
None directly. The spec defines link-partner behaviour, not probes. Use the link-layer reaction rules (Nak on bad LCRC) as the test.
Typical causes
Gen4+ rates through an interposer without redriving; long or damaged probe cables; an interposer for a different form factor revision; analyzer equalization settings that do not match the link.
How to detect / prove
A/B test: the same workload with and without the interposer, comparing AER counters at both ends and LnkSta. In the trace, check the partner's reaction to every flagged error. Classify each error as "confirmed by partner" or "analyzer-only".
Linux v7.2 source
Counters for the A/B comparison: drivers/pci/pcie/aer.c sysfs attribute aer_dev_correctable.
Test to provoke it
SAFE: swap interposer cables or slots and repeat the capture; compare error counts.
X-28Analyzer re-lock after electrical idle or speed change: lost or garbled first packets SilentAnalyzer
In a PEX trace
Partly visible Bursts of symbol, disparity or sync-header errors on all lanes at once, immediately after an EIEOS/FTS sequence, an L1 exit or a speed change, followed by clean traffic. Or the first TLP after idle missing, while the partner Acks a sequence number the analyzer never saw.
What happens
After electrical idle, every receiver must regain bit, symbol or block lock. The link partners are given training sequences for this. The analyzer, tapping passively, may need longer, especially after a speed change where it must also follow the new rate and equalization. While it re-locks it either drops data or decodes garbage.
How it shows up
Nothing on the system.
Spec basis
None for the analyzer. Link partners follow the L0s/L1/Recovery rules.
Typical causes
Aggressive ASPM (frequent L1 entry/exit), short N_FTS for L0s, analyzer not set to follow speed changes, missing capture of the equalization phase.
How to detect / prove
Check sequence numbers across the idle exit: if the partner's Ack covers numbers that the trace never shows, the analyzer lost packets. Errors confined to the first few hundred nanoseconds after every exit, on all lanes, with no Nak, are re-lock artifacts. Disable ASPM and re-capture to confirm.
Linux v7.2 source
drivers/pci/pcie/aspm.c (ASPM policy that causes the idle transitions).
Test to provoke it
SAFE: capture a lightly loaded link with ASPM L1 enabled, then with it disabled, and compare error flags.
X-29Analyzer setup errors: wrong lane map, polarity, speed, clocking or descrambler state SilentAnalyzer
In a PEX trace
Partly visible Systematic nonsense: every packet flagged, impossible TLP headers, framing errors at the same lane boundary every time, ordered sets decoded correctly but data garbled (descrambler not synchronised), or a deskew failure the device clearly does not have (the link runs with no AER errors).
What happens
The analyzer must be told, or must learn, the link's width, lane order, polarity, data rate, clocking mode (common clock, SRNS, SRIS) and, for Gen3+, the scrambler and equalization state. If the capture starts after training, some state cannot be learned from the wire. Its deskew limits may also be tighter than the device's.
How it shows up
Nothing on the system.
Spec basis
None for the analyzer. Lane reversal, polarity and scrambling rules are in the PCIe Base Specification Physical Layer.
Typical causes
Interposer with reversed lanes not configured in the analyzer; capture started mid-traffic at Gen3+; wrong speed selected; spread-spectrum clocking not configured.
How to detect / prove
Re-capture from link training (reset or hot-plug) with automatic link-configuration detection enabled if the analyzer has it. If the errors disappear, they were setup artifacts. A real link with that many errors would not run without AER reports and retraining.
Linux v7.2 source
Not applicable. Use lspci -vvv LnkSta and AER counters to show the real link is healthy.
Test to provoke it
SAFE: deliberately set a wrong lane order in the analyzer on a known-good link to learn what the artifact looks like.
X-30Capture gaps, buffer wrap and hardware filters that fake a "missing" packet SilentAnalyzer
In a PEX trace
Partly visible A request with no completion, a CQE with no SQE fetch, no Ack/Nak at all, or no UpdateFC for a long time, where the real cause is that the analyzer did not store it. Signs: a gap in timestamps with no traffic in either direction, an Ack covering sequence numbers that never appear, a trace-start or wrap marker, filter settings that exclude DLLPs or completions.
What happens
Hardware filters drop items before storage. Ring buffers overwrite the oldest data until the trigger. Some analyzers pause storage while the buffer is uploaded or when the internal bandwidth is exceeded impl. The trace then shows an absence that did not happen on the wire.
How it shows up
Nothing on the system. The risk is a false report: "completion timeout", "missing interrupt", "credit starvation".
Spec basis
None for the analyzer. Before claiming any timing violation from an absence (for example a Completion Timeout, L-14), prove the window had no gaps.
Typical causes
Aggressive filtering to stretch capture time, too-small pre-trigger, buffer full at high link utilisation.
How to detect / prove
Use sequence numbers as a continuity check. In each direction, new TLP sequence numbers must be continuous (X-17). Ack numbers in the other direction must refer to TLPs present in the trace. A jump with no Nak and no error means the capture, not the link, lost data. Write the filter settings into every report.
Linux v7.2 source
Not applicable. Host-side logs (dmesg, NVMe timeouts from nvme_timeout in drivers/nvme/host/pci.c) show whether the host really saw a timeout.
Test to provoke it
SAFE: capture the same workload with and without DLLP filtering and compare what analysis rules report.

💡 Senior insight

When you report a physical or link-layer bug to an SSD or platform vendor, attach three things: the PEX trace window, the analyzer setup, and both ends' AER counters with and without the interposer. Vendors reject physical-layer bug reports that rest only on analyzer flags, and they are right to.

Interview questions

  1. Beginner Why does an LCRC error never show up as an NVMe error?
    Model answerThe Data Link Layer recovers it with a Nak and replay. The TLP arrives intact on the second try, so the NVMe command completes normally. Only AER (Bad TLP) and the trace record it, plus a small added latency.
  2. Intermediate The analyzer shows 2,000 disparity errors per second but the SSD's AER counters are zero. What do you do?
    Model answerCheck whether the link partners react (Naks, replays, Recovery). If they do not, suspect the analyzer: probe signal quality, wrong setup or re-lock (X-27 to X-29). Re-capture from link training, try another interposer cable, and compare counters with and without the interposer.
  3. Advanced How would you prove from a trace that a stall was caused by the host rather than the SSD?
    Model answerRebuild flow-control credits. If the SSD is at its posted-credit limit and the host's UpdateFC values stop advancing, the host side is not draining (X-22). Also check that the SSD's MRd requests for SQEs or data have outstanding completions from the host (completion latency at the probe). Each interval at the probe splits into "waiting for host" and "waiting for device".

Quiz

  1. Which of these is visible in a PEX trace on the SSD's link: (a) the Root Port's AER status, (b) the SSD's ERR_COR messages, (c) the SSD's internal ECC retries, (d) the host's NVMe timeout decision?

    Answer

    (b) only. (a) is read inside the host, not over this link. (c) is internal to the SSD. (d) is a CPU decision; the trace may show its consequences (Abort command, reset writes).

  2. In Flit mode, why doesn't the analyzer report LCRC errors?

    Answer

    TLPs in Flit mode do not carry a per-TLP LCRC. Integrity is checked per Flit with FEC and CRC, so the analyzer reports FEC-corrected and CRC-failed Flits instead.
