I-B.6 Setting Up a Capture So the Error Is Actually In It

I-B.6.1 Why this chapter exists

Most failed trace investigations fail before analysis starts. Typical reasons: the trace starts after queue creation, so NVMe cannot be decoded; DLLPs were filtered, so Ack/Nak cannot be checked; the buffer wrapped, so the cause is gone; or the probe made errors of its own. The checklist below is ordered the way you set up the bench. Menu names differ between analyzers and software versions, so the list says what to set, not where the setting is.

✅ Capture checklist
  • Write down the question first. Physical/link error? Protocol violation? Timing? NVMe command outcome? The answer decides filters and trigger.
  • Match the link. Set the analyzer to the expected maximum speed and width, with lane mapping and polarity matching the interposer. Enable Flit mode decode for Gen6 links. If the analyzer can follow speed changes, enable that, and capture link training so it learns equalization and scrambling state.
  • Prove the probe is neutral. Without the interposer, record link speed/width (lspci -vvv LnkSta) and AER correctable counters (/sys/bus/pci/devices/<BDF>/aer_dev_correctable) after a fixed workload. Repeat with the interposer installed. If counters rise only with the interposer, the probe is part of the problem (X-27).
  • Capture from before initialization when NVMe decode matters. Arm the analyzer, then cause re-initialization: power-cycle or hot-plug the SSD, rebind the driver (echo <BDF> > /sys/bus/pci/drivers/nvme/unbind then bind, CAUTION: the device disappears from the OS), or nvme reset /dev/nvmeX (CAUTION). The capture must include the CC/AQA/ASQ/ACQ writes and the Create I/O CQ/SQ commands.
  • For physical and link errors, do not filter DLLPs, ordered sets or SKPs. You need Ack/Nak, UpdateFC, TS1/TS2, EIOS/EIEOS and SKP OS. Filter data payloads instead if you need more capture time.
  • For data-integrity questions, keep payloads. Silent corruption is visible only by comparing payload bytes.
  • Choose the trigger at the cause side. Trigger on the first physical error, first Nak, first LTSSM Recovery entry, a UR/CA completion, an NVMe CQE with non-zero status, a specific opcode (for example DSM 09h) or an external trigger from a host script. Set the pre-trigger large enough (often 50–90 %) to include the cause.
  • Use the host to mark time. Before the interesting step, make the host send a recognisable TLP, such as a config read of an unusual register (setpci -s <BDF> 0x0.l, read-only) or an NVMe Get Features. Trigger on it, or search for it later. Record the host wall-clock time of each step to line up dmesg with the trace.
  • Capture the evidence the trace cannot hold. At the same time, save dmesg/journal, nvme error-log, nvme smart-log, AER counters at both ends, and LnkSta. Do this before and after.
  • Read registers over the probed link on purpose. If you want AER or NVMe register state in the trace, have software read them during the capture: lspci -vvv -s <BDF> (config reads of the SSD go over the probed link, but the Root Port's reads do not), nvme show-regs (MMIO reads of the BAR).
  • Check for gaps after capture. Before analysing, look for buffer-wrap markers, lost-lock events and long stretches with no traffic in either direction. Note any filters you applied.
  • Keep the raw file. Archive the .pex unmodified with its settings and the host logs. Exports are lossy.

⚠️ Safety

Unbinding a driver, resetting a controller, hot-plugging, power-cycling and margining are disruptive. Do them only on a test system with no data you need. Never run destructive NVMe commands (Format, Sanitize, Write Zeroes, DSM) on a namespace holding real data.

I-B.7 Exporting a PEX Capture for Scripts or an AI Assistant

I-B.7.1 What export can and cannot carry

The .pex file is a proprietary binary format. It is read by the vendor's software, which can open saved traces without the analyzer hardware attached. For scripts you export. Teledyne LeCroy release notes mention CSV and text export (with a time-delta field from version 7.15) and later a "legacy" export option uncertain (seen in search excerpts). Other vendors offer similar paths: Prodigy exports decoded data as CSV or TXT, and SerialTek advertises a REST API with JSON output for its BusXpert software uncertain. The details change between versions, so treat the following as a generic method.

  1. Choose the level. Export at the level your question needs. Use the packet level for link and timing rules, with one row per TLP/DLLP including direction, timestamp, sequence number, type, address, length, tag, requester ID, status and flagged errors. Use the NVMe level for command rules, with one row per command including SQID, CID, opcode, SLBA, NLB, submit time, completion time and status. The symbol level is rarely worth exporting: too large, little extra meaning.
  2. Export the whole window. Filtered views export only what is shown. If you hide DLLPs in the view, they will be missing from the CSV too.
  3. Keep raw columns. Keep raw header Dwords and the first bytes of payload as hex when possible. Decoded fields depend on the tool's interpretation, while raw values let a script check that interpretation.
  4. Normalize. Convert to a small neutral schema, one event per row: t_ns, dir, kind, seq, type, addr, len, tag, req_id, status, flags, nvme_sqid, nvme_cid, nvme_opc, raw. Chapter 7.6 has a rule checker that consumes this kind of schema (7.6).
  5. Attach the context. Include capture settings (speed, width, filters, trigger, buffer), the configured MPS/MRRS, CAP.DSTRD, queue map, and host logs with wall-clock offsets.

I-B.7.2 Giving a trace to an AI assistant

Language models handle tables of events well but cannot open a binary .pex file. A multi-gigabyte export will not fit in a prompt. A reliable workflow:

  • Cut to the window. Export about ±5 ms around the trigger, or the full lifetime of the commands in question, not the whole capture.
  • Summarise first with a script. Compute counts (TLPs by type, Naks, replays, Recovery entries, physical errors per lane), latency percentiles and the list of rule violations. Give the assistant the summary plus the raw rows around each violation.
  • State the limits explicitly. Tell the assistant: single link, which end is the SSD, which filters were active, whether init was captured, and that device internals are not visible. Otherwise it may "find" a missing completion that was filtered.
  • Ask for spec-anchored reasoning. Ask which rule each finding breaks and what other evidence would confirm it (AER counters, logs, read-back). Check its claims against the raw rows. A model can mis-pair tags just like a human.
  • Redact. Payloads may hold user data, keys or personal data. Truncate or hash payloads unless the question is about data content.
# Minimal normaliser for a generic packet-level CSV export (column names vary by tool: adjust MAP).
# Python 3, standard library only. Usage: python3 -I norm.py export.csv > events.csv
import csv, sys
MAP = {  # your export's column header  ->  neutral name
    "Time Stamp": "t", "Direction": "dir", "Packet": "kind", "Seq Num": "seq",
    "Type": "type", "Address": "addr", "Length": "len", "Tag": "tag",
    "Requester ID": "req_id", "Status": "status", "Error": "flags",
}
def to_ns(s):
    s = s.strip().lower()
    for unit, mul in (("ns", 1), ("us", 1e3), ("ms", 1e6), ("s", 1e9)):
        if s.endswith(unit):
            return int(float(s[: -len(unit)].replace(",", "")) * mul)
    return int(float(s))          # assume ns if there is no unit
rd = csv.DictReader(open(sys.argv[1], newline="", encoding="utf-8", errors="replace"))
out = csv.DictWriter(sys.stdout, fieldnames=list(MAP.values()))
out.writeheader()
for row in rd:
    ev = {MAP[k]: (row.get(k) or "").strip() for k in MAP}
    if ev["t"]:
        ev["t"] = to_ns(ev["t"])
    out.writerow(ev)

The column names in MAP are placeholders synthetic. Replace them with your export's header row. Once normalised, the checks in this atlas (sequence gaps, Ack latency, credit accounting, CQE pairing) become short loops over rows.

# Example rule over normalised events: Ack latency and replay counting (link-level, non-Flit mode).
# Expects rows with kind in {TLP, DLLP}, type 'Ack'/'Nak' for DLLPs, seq as hex or decimal.
import csv, sys
def num(x):
    x = (x or "").strip()
    return int(x, 16) if x.lower().startswith("0x") else (int(x) if x.isdigit() else None)
pending = {"Up": {}, "Down": {}}      # seq -> time of first transmission, per TLP direction
seen = {"Up": {}, "Down": {}}         # seq -> times transmitted
worst = []
for ev in csv.DictReader(open(sys.argv[1], newline="")):
    t, d, kind, seq = int(ev["t"]), ev["dir"], ev["kind"], num(ev["seq"])
    if kind == "TLP" and seq is not None:
        seen[d][seq] = seen[d].get(seq, 0) + 1
        pending[d].setdefault(seq, t)
    elif kind == "DLLP" and ev["type"] in ("Ack", "Nak") and seq is not None:
        tlp_dir = "Up" if d == "Down" else "Down"   # an Ack travels opposite to the TLPs it acknowledges
        # 12-bit sequence space: acknowledge everything up to seq (modulo 4096, window < 2048)
        for s in [s for s in pending[tlp_dir] if ((seq - s) & 0xFFF) < 2048]:
            # a Nak also acknowledges everything up to its sequence number (the last good TLP)
            worst.append((t - pending[tlp_dir].pop(s), tlp_dir, s))
replays = {d: {s: n for s, n in m.items() if n > 1} for d, m in seen.items()}
worst.sort(reverse=True)
print("slowest acknowledgements (ns, dir, seq):", worst[:10])
print("replayed sequence numbers:", {d: len(v) for d, v in replays.items()})
print("never acknowledged at end of capture:", {d: sorted(v)[:20] for d, v in pending.items()})

This script is a starting point, not a certified checker. It ignores sequence numbers that wrap during the capture window and treats every Ack as covering all earlier TLPs. A TLP still pending at the end of the capture is not a violation by itself: the window may have ended first.

Quiz

  1. Your CSV has no DLLP rows. Can you conclude there were no Naks?

    Answer

    No. Either DLLPs were filtered in hardware, hidden in the view before export, or the export level was NVMe or transaction rather than packet. Check the capture settings and re-export at packet level with all items shown.

  2. An AI assistant reports "the SSD did not perform the deallocate" from a trace that shows a DSM command with success status. Is that justified?

    Answer

    Not from the DSM command alone, since the effect is internal. It is justified only if the trace also contains evidence of the effect: for example a later read of those LBAs returning the old data on a namespace whose DLFEAT promises zeroes, or Identify Namespace data whose NUSE did not change. Even then it is an inference about internal state, supported by on-wire data.
