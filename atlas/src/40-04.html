IV.4 Erase, protection, identity, completion and firmware: more successes that aren't

The previous chapter was about user data. This one covers commands whose job is to destroy data (Sanitize, Format, crypto erase), to protect it (PI), to describe the device (Identify, SMART, firmware slots, zone state), and the queue mechanics that tell the host a command finished (CQE, CID, DMA). For each one the trace shows a well-formed exchange, and the problem is in what the content means. Many of these cards are partly visible in a PEX trace, because the misleading information (an Identify payload, a CQE with the wrong CID, a DMA to a strange address) does cross the link. You only need to know what to compare it with.

⚠️ Host-side false positive for every erase test

After a Sanitize or Format sent through passthrough (nvme sanitize, nvme format), the Linux page cache of /dev/nvme0n1 may still hold blocks read before the erase. A buffered dd or hexdump can then show "old data" that is not on the drive at all. The v7.2 driver marks Format and Sanitize with the LBCC (logical block content change) effect in core.c:nvme_init_known_nvm_effects(), and Format also with NCC (namespace capability change) so the namespace is rescanned. But verify with O_DIRECT reads or nvme read passthrough, and drop caches (echo 3 > /proc/sys/vm/drop_caches) before concluding anything.

IV.4.1 Erase and protection

D-18Sanitize reports success but user data remains SilentAdmin command
In a PEX trace
Partly visible The Sanitize SQE (admin OPC 84h, SANACT in CDW10), its quick Success CQE, the Get Log Page 81h polling and the Sanitize Status payload (SPROG, SSTAT) are visible. Read data payloads after the sanitize showing old patterns are visible proof that the logical view still has data. Remaining data in NAND blocks that are no longer mapped is not visible.
What happens
A Sanitize (Block Erase, Overwrite or Crypto Erase) runs to completion. The Sanitize Status log reports the most recent sanitize as completed successfully, but some user data can still be read: from LBAs (an incomplete pass), from areas outside the user LBA space (over-provisioning, retired blocks, caches), or by reading the raw NAND.
How it shows up
SSTAT says success (value 1, or 4 for the No-Deallocate variant), and no error is logged. Only a read-back audit or forensic analysis of the NAND finds the leftovers.
Spec basis
Base spec Sanitize command (84h) and Sanitize Status log (81h). libnvme defines SSTAT status values 0 never sanitized, 1 completed successfully, 2 in progress, 3 failed, 4 completed successfully with No-Deallocate, plus the Global Data Erased bit (bit 8) and completed-passes count. Identify Controller SANICAP (CES, BES, OWS, NDI, NODMMAS). Sanitize is meant to affect all user data, including caches and unallocated media verify exact scope wording in spec.
Typical causes
Firmware erasing only mapped blocks; skipping retired or bad blocks that still hold readable data; host-memory-buffer or controller cache not cleared; a power loss during sanitize followed by a wrong recovery. Wei, Grupp, Spada and Swanson (FAST '11) found that built-in sanitize commands worked on drives where they were implemented correctly, but some implementations were incorrect.
How to detect / prove
Fill the whole namespace with a recognizable, LBA-tagged pattern (including writes over the full capacity several times, so over-provisioned blocks also hold the pattern), sanitize, poll the log to completion, then read every LBA with O_DIRECT and search for the pattern. For the media-level claim, only a lab chip-off/raw-NAND read (as in Wei et al.) or a vendor-supported verification can prove it.
Linux v7.2 source
Linux never issues Sanitize itself. It arrives via the passthrough ioctls; core.c:nvme_init_known_nvm_effects() forces the LBCC and CSE effects for nvme_admin_sanitize_nvm, and core.c:nvme_passthru_end() unfreezes queues afterwards.
Test to provoke it
CAUTION (destroys all data): pattern-fill ×2, nvme sanitize /dev/nvme0 -a 2 (block erase; check nvme sanitize --help for your version), nvme sanitize-log /dev/nvme0 until done, full O_DIRECT read audit. Repeat for each SANACT the drive supports, and once with a power cut mid-sanitize (EXPERT): the drive must resume or report failure, never report success.
D-19Crypto erase leaves data readable SilentAdmin command
In a PEX trace
Partly visible The command (Sanitize SANACT=100b, or Format NVM with SES=010b) and its Success CQE are visible. A later Read whose data payload contains the old plaintext is visible proof. A key that was not really replaced (data still decryptable with the old key, but reads return garbage) is not visible.
What happens
The drive reports a successful cryptographic erase but did not change the media encryption key, or changed it for some ranges only, or kept a copy. Reads either return old plaintext (key unchanged) or random-looking data (key changed). The second case looks correct even if a copy of the old key remains.
How it shows up
Silent. The user's only check, "reads now return something other than my data", passes even when the erase is not cryptographically effective.
Spec basis
Sanitize Crypto Erase (SANICAP.CES) and Format NVM Secure Erase Setting 010b (cryptographic erase), supported when the Identify Controller FNA field says so verify FNA bit. NVMe defines the command, not the key management. TCG Opal/Ruby specs cover encryption ranges.
Typical causes
Drive not actually encrypting media (no self-encryption despite the claim); key wrapped by a constant; per-range keys with one range forgotten; firmware bug that rewrites the old key after power cycle.
How to detect / prove
Read-back immediately after the erase and after a power cycle: old plaintext anywhere = proof. Strong assurance needs vendor documentation, a certification report (for example FIPS 140 validation of the drive's crypto module), or raw-NAND analysis showing ciphertext that changes between two writes of the same plaintext.
Linux v7.2 source
Passthrough only; Format gets LBCC|NCC|CSE effects in core.c:nvme_init_known_nvm_effects(), so the namespace is rescanned after it.
Test to provoke it
CAUTION: write pattern, crypto erase, O_DIRECT read audit, power cycle, audit again. Compare against the DLFEAT read behaviour: many drives deallocate after crypto erase, so reads return zeroes. A drive returning ciphertext is fine, and one returning plaintext has failed.
D-20Format NVM leaves old data SilentAdmin command
In a PEX trace
Visible The Format SQE (admin OPC 80h) shows the SES field in CDW10, so the trace proves which erase was requested. If SES=001b or 010b was requested, a later Read data payload with old data is visible proof. With SES=000b the trace also shows that no secure erase was asked for.
What happens
After Format NVM completes, reads return the data written before. Two different situations: (a) SES = 000b (no secure erase) was used. Then the spec does not require the data to be destroyed, only the LBA format to change, and with DLFEAT 000b the old data may still read back. That is a misunderstanding, not a drive failure. (b) SES = 001b (user data erase) or 010b was requested and data remains. That is a real failure.
How it shows up
Silent. Format may complete in milliseconds in either case.
Spec basis
Format NVM CDW10: LBAF, MSET, PI, PIL, SES (000b none, 001b user data erase, 010b cryptographic erase). FNA in Identify Controller says whether Format applies to all namespaces and whether crypto erase is supported verify bit layout.
Typical causes
Tools defaulting to SES=0 (users assume "format = wipe"); firmware implementing SES=1 as "deallocate all" on a drive with DLFEAT 000b, so reads still return old content.
How to detect / prove
Check the SES actually sent (PEX trace, or nvme format … --ses=1 on the command line). Pattern-fill, format, O_DIRECT read audit. With SES ≥ 1, any old pattern = proof. Check the Format completion time against Identify Controller's estimate, if reported.
Linux v7.2 source
Passthrough. After the command, nvme_passthru_end() runs a namespace rescan (NCC effect), which also catches LBA-format changes.
Test to provoke it
CAUTION: run the same audit for SES=0, 1 and 2. Expect possible old data only for SES=0 with DLFEAT 000b.
D-21Metadata / protection information not checked SilentData integrity
In a PEX trace
Partly visible The PRINFO bits (PRACT, PRCHK guard/app/ref in CDW12 bits 29:26) of every Read/Write, and the reference/application tags in CDW14–15, are visible, so you can prove checking was not requested. With separate metadata (MPTR) or extended LBAs the PI bytes themselves cross the link and can be checked offline. Whether the controller really checked is not visible, unless a deliberately bad PI comes back with Success.
What happens
The namespace is formatted with PI, but corrupted data passes because: PI checking was not requested (PRCHK = 0); the host uses PRACT = 1 so the controller generates and strips PI and the host-to-controller path is not covered; the PI type is 0 (metadata only, never checked); application tag FFFFh disables checking for that block (an escape value verify per PI type); or the controller ignores PRCHK.
How it shows up
No Guard/App/Reference Tag Check Error (282h/283h/284h) even though data or LBA is wrong.
Spec basis
NVM Command Set End-to-end Data Protection: Identify Namespace DPC/DPS, FLBAS/LBA format MS, PRINFO in Read/Write. Status codes Guard Check Error 282h, Application Tag Check Error 283h, Reference Tag Check Error 284h (Linux NVME_SC_GUARD_CHECK etc.).
Typical causes
Kernel without CONFIG_BLK_DEV_INTEGRITY; integrity profile not registered; the user assuming "formatted with PI" means "protected end to end"; firmware skipping checks for performance.
How to detect / prove
Write with a deliberately wrong guard or reference tag via passthrough (nvme write … --prinfo with a wrong --ref-tag) and confirm the error. A Success here proves the check is not done. Check /sys/block/nvme0n1/integrity/ (format, read_verify, write_generate) to see what Linux does.
Linux v7.2 source
core.c:nvme_init_integrity() (returns PI-capable only if the namespace has PI when integrity support is missing); core.c:nvme_setup_rw() sets PRACT when no integrity payload exists, and PRCHK bits from BIP_CHECK_GUARD/REFTAG/APPTAG; core.c:nvme_set_ref_tag(); core.c:nvme_error_status() maps 282h–284h and Invalid PI to BLK_STS_PROTECTION.
Test to provoke it
CAUTION on a test namespace formatted with PI Type 1: wrong ref tag write; correct write then wrong expected ref tag on read; corrupt guard. Each must fail. Repeat with app tag FFFFh to see the documented escape.

IV.4.2 Identity, accounting and health reporting

D-22Bogus or duplicate namespace identifiers (NGUID / EUI64 / UUID) SilentIdentify
In a PEX trace
Visible The Identify payloads (Identify Namespace NGUID/EUI64, and the Namespace Identification Descriptor list for CNS 03h) cross the link as MWr data. All-zero, all-FFh, or identical values across namespaces or across drives of the same model can be read straight from the capture.
What happens
The drive reports identifiers that are not unique: the same NGUID for every unit of a model, garbage, or the same ID for two namespaces. Multipath software and /dev/disk/by-id links may then merge two different namespaces into one, or point to the wrong disk.
How it shows up
Silent unless Linux detects the duplicate. Linux v7.2 then prints "clearing duplicate IDs for nsid N" and "use of /dev/disk/by-id/ may cause data corruption" (or "ignoring nsid N because of duplicate IDs" for fabrics or shared multi-controller namespaces) and sets NVME_QUIRK_BOGUS_NID at runtime.
Spec basis
Identify Namespace NGUID/EUI64, Namespace Identification Descriptor list (CNS 03h), NSFEAT bit 3 (identifiers never reused).
Typical causes
Firmware with a constant ID from the reference design; manufacturing step that never programs a unique value. v7.2 pci.c:nvme_id_table has many NVME_QUIRK_BOGUS_NID entries, including Intel 0A54h (P4500/P4600) and both QEMU device IDs.
How to detect / prove
nvme id-ns /dev/nvme0n1 | grep -iE 'nguid|eui64' and nvme ns-descs /dev/nvme0n1 on several units and namespaces; compare. dmesg | grep -i "duplicate IDs\|bogus".
Linux v7.2 source
core.c:nvme_process_ns_desc() (ignores IDs under the quirk), core.c:nvme_identify_ns() ("Ignoring bogus Namespace Identifiers"), core.c:nvme_init_ns_head() (duplicate detection, runtime quirk), core.c:nvme_subsys_check_duplicate_ids().
Test to provoke it
SAFE: create two namespaces (or use two drives of one model), compare all identifiers, and check that by-id links resolve uniquely.
D-23Identify returns wrong data for a CNS value it does not really support SilentIdentify
In a PEX trace
Visible The Identify SQE shows CNS in CDW10 bits 7:0. The returned data payload is visible. A controller answering CNS 02h (active namespace list) with the Identify Controller structure, or returning Success with a zero-filled descriptor list, shows up when you compare the payload with what that CNS should contain.
What happens
The controller claims a spec version that includes a CNS value but handles it wrongly: it truncates CNS to one bit (NVMe 1.0 behaviour), so the request is answered as a different structure, or returns Success with an empty structure instead of Invalid Field.
How it shows up
Silent wrong values: missing namespaces, wrong namespace list, garbage descriptors. Sometimes Linux prints "ctrl returned bogus length" for descriptor list entries.
Spec basis
Identify CNS values. NVMe 1.1 widened CNS from one bit to two bits; later versions to a full byte. The Linux comment in nvme_id_cns_ok() explains this history.
Typical causes
Old command decoders kept after raising the reported version. Linux quirks: NVME_QUIRK_IDENTIFY_CNS (only CNS 0/1 handled, QEMU 5845h and Apple controllers in v7.2) and NVME_QUIRK_NO_NS_DESC_LIST (descriptor list not handled despite claiming 1.3).
How to detect / prove
Issue each CNS with nvme admin-passthru --opcode=0x06 --cdw10=<cns> --data-len=4096 -r and compare the structure with what the CNS defines. An unsupported CNS should fail with Invalid Field, not return Success with unrelated data.
Linux v7.2 source
core.c:nvme_id_cns_ok() (CNS ≤ 3 for ≥ 1.1 unless quirk, else ≤ 1), core.c:nvme_identify_ns_descs(), core.c:nvme_process_ns_desc() ("ctrl returned bogus length"), apple.c sets NVME_QUIRK_IDENTIFY_CNS.
Test to provoke it
SAFE (read-only admin commands): sweep CNS 00h–1Fh with NSID 0, 1 and FFFFFFFFh, log status and payload.
D-24Namespace capacity or format mis-reported SilentIdentify
In a PEX trace
Partly visible NSZE/NCAP/NUSE (bytes 0–23), FLBAS (byte 26) and the LBA format table are in the Identify Namespace payload, so inconsistent values (NUSE > NCAP, NCAP > NSZE without THIN, a format index beyond NLBAF) are visible. Whether the drive really has that much usable space is not: the failure shows later as writes beyond some LBA failing or wrapping.
What happens
The reported size is larger than the media really backs (counterfeit or mis-configured drives: writes past the real capacity wrap around and overwrite earlier data), or the LBA data size in the format table is wrong, or NCAP/NSZE disagree after namespace management.
How it shows up
Silent at first. Later: data at low LBAs is overwritten by writes to high LBAs (wraparound), or LBA Out of Range errors appear below the reported size.
Spec basis
Identify Namespace NSZE, NCAP, NUSE, NSFEAT THIN, FLBAS, LBAF[]; Identify Controller TNVMCAP/UNVMCAP for totals.
Typical causes
Fake-capacity firmware; namespace-management bugs; reporting the LBA count for 512-byte format while the namespace uses 4096.
How to detect / prove
Full-capacity write with LBA-tagged data (fio --verify=crc32c headers include offset, or f3-style tools), then full read-verify. Wraparound shows as blocks containing headers of other offsets. Cross-check blockdev --getsize64 with NSZE × LBA size.
Linux v7.2 source
core.c:nvme_update_ns_info_block() computes capacity and calls set_capacity_and_notify(); capacity is set to 0 if metadata cannot be handled (nvme_init_integrity() false).
Test to provoke it
CAUTION: full-drive tagged write and verify. Also create, resize and delete namespaces repeatedly and check the Identify values each time.
D-25SMART / health counters frozen or wrong; bogus temperature SilentLog page
In a PEX trace
Partly visible Each Get Log Page 02h returns 512 bytes of payload over the link, so values that do not change between two captures, or that are impossible (temperature 0 K, Percentage Used decreasing), are visible. Whether a counter is right needs a reference from the same trace: Host Write Commands must rise by the number of Write SQEs you saw in between.
What happens
Counters do not update (Data Units Written stuck), update at the wrong scale, wrap, or reset at power cycle. Composite Temperature is constant, 0, or far from reality. Critical Warning bits never set even when thresholds are crossed.
How it shows up
Monitoring sees a healthy drive. Wear-out or thermal trouble is missed, or alarms fire falsely.
Spec basis
SMART / Health Information log (02h): Critical Warning, Composite Temperature (Kelvin), Available Spare, Percentage Used, Data Units Read/Written (thousands of 512-byte units, rounded up), Host Read/Write Commands, Power Cycles, Power On Hours, Unsafe Shutdowns, Media and Data Integrity Errors, Number of Error Information Log Entries. Temperature thresholds via Feature 04h.
Typical causes
Counters kept in RAM and only saved occasionally; a broken sensor; firmware that reports a fixed value. Linux has quirks NVME_QUIRK_NO_TEMP_THRESH_CHANGE and NVME_QUIRK_NO_SECONDARY_TEMP_THRESH for drives that misbehave with temperature thresholds.
How to detect / prove
Snapshot nvme smart-log, write exactly N × 512,000 bytes with O_DIRECT, snapshot again: Data Units Written must grow by N (± rounding), Host Write Commands by the number of commands sent. Compare temperature with an external thermocouple and with the hwmon value (sensors, /sys/class/hwmon/*/temp1_input). Power cycle and check that counters persist and Power Cycles increments.
Linux v7.2 source
hwmon.c:nvme_hwmon_get_smart_log(), hwmon.c:nvme_hwmon_read(), hwmon.c:nvme_get_temp_thresh()/nvme_set_temp_thresh().
Test to provoke it
SAFE: counted-write test above; heat the drive with a sustained write and watch temperature and Warning Composite Temperature Time; cool it and check the reverse.
D-26Firmware update reports success but the old firmware is still running SilentAdmin command
In a PEX trace
Visible Firmware Image Download (11h) chunks, Firmware Commit (10h) with its Commit Action and slot in CDW10, the CQE status (Success, or 10Bh/110h/111h "activation requires … reset"), any AER notice for firmware activation, and the Firmware Slot log (03h) and Identify Controller FR payloads afterwards are all on the wire. Comparing FR before and after the reset shows whether activation happened.
What happens
The download and commit succeed, the tool says "updated", but the running firmware revision is unchanged: the commit action only stored the image (CA = 000b), activation was deferred to a reset that did not happen (status 10Bh/110h/111h treated as success by a tool), or activation silently failed and the drive fell back to the old slot.
How it shows up
Silent if the tool ignores the status or the slot log. Linux v7.2 logs "Firmware is activated after next Controller Level Reset" when the slot log's next-active slot differs from the current one.
Spec basis
Firmware Commit (CA values: replace, replace and activate at next reset, activate at next reset, replace and activate immediately), status codes Firmware Activation Requires Conventional Reset (10Bh), Requires NVM Subsystem Reset (110h), Requires Controller Level Reset (111h), Requires Maximum Time Violation (112h), Firmware Slot Information log (AFI: active slot bits 2:0, next slot bits 6:4; FRS1–FRS7), Identify Controller FR and FRMW.
Typical causes
Tool or script not checking the CQE status or not resetting; wrong slot; image verification failing in firmware after the commit returned; a read-only slot 1.
How to detect / prove
nvme fw-log /dev/nvme0 (AFI and slot revisions) and nvme id-ctrl /dev/nvme0 | grep -i '^fr ' before and after the activation reset; cat /sys/class/nvme/nvme0/firmware_rev. The running revision is FR after the reset, not what the tool printed.
Linux v7.2 source
core.c:nvme_get_fw_slot_info() (reads log 03h, compares afi & 0x7 with (afi & 0x70) >> 4, updates subsys->firmware_rev), core.c:nvme_handle_aen_notice() (NVME_AER_NOTICE_FW_ACT_STARTING), core.c:nvme_fw_act_work(); status codes NVME_SC_FW_NEEDS_* in include/linux/nvme.h.
Test to provoke it
CAUTION (vendor image required): commit with each supported CA, check status, slot log and FR before and after a controller reset, a subsystem reset and a power cycle. Also try a corrupted image: the drive must reject it, never report success and keep running old firmware silently.
D-27ZNS write pointer does not match the data SilentZNS
In a PEX trace
Partly visible Zone Append CQEs return the assigned LBA in DW0–DW1, and Zone Management Receive (Report Zones) payloads carry each zone's state and write pointer, so a WP that disagrees with the appends you saw complete is visible. Data persisted beyond or below the WP after a power cut is not, until you read it.
What happens
The reported write pointer is ahead of the data actually persisted (reads below the WP return old or unwritten content), or behind it (data written but the WP rolled back, so the host overwrites it with the next append). Usually after a power loss or a reset in the middle of writes.
How it shows up
Silent. Zoned filesystems and applications that rebuild state from the WP (for example to find the end of a log) lose or duplicate records.
Spec basis
Zoned Namespace Command Set: zone states, write pointer, Zone Append (returns the LBA written), Zone Management Send/Receive, errors such as Zone Invalid Write (1BCh) and Zone Boundary Error (1B8h) that Linux names in include/linux/nvme.h.
Typical causes
WP updated before the data is durable; WP recovery after power loss scanning the wrong way; zone state machine bugs on Finish/Reset.
How to detect / prove
Append records with sequence numbers and checksums, cut power or reset, then nvme zns report-zones and read each zone up to and past the WP. All records below the WP must verify; none above it may be valid new data (allowed values above WP per the read rules for unwritten blocks verify in spec).
Linux v7.2 source
zns.c:nvme_zone_parse_entry() (for zones reported FULL, Linux sets wp = start + len instead of the reported WP; non-sequential zone types fail with "invalid zone type"), zns.c:nvme_ns_report_zones(), zns.c:nvme_setup_zone_mgmt_send().
Test to provoke it
EXPERT: append workload across many open zones with power cuts; compare WP with the last acknowledged append per zone and with the data.

IV.4.3 Completion and DMA failures that hide themselves

D-28Completion posted with the wrong CID SilentNVMe queue
In a PEX trace
Visible Every SQE fetch (CplD with the CID) and every CQE MWr (DW3 CID, SQID) is captured, so an analyzer script can match them: a CQE whose CID was never submitted on that SQ, or a CID completed while its own command is still outstanding and another's is missing, is directly visible.
What happens
The controller completes command A but writes the CID of command B. If B is outstanding, the host completes B (with A's status) while B's data is not there yet, and A later times out. Buffers can be reused while the device still DMAs into them.
How it shows up
Partly reported. Linux v7.2 encodes a 4-bit generation counter in the CID upper bits (unless NVME_QUIRK_SKIP_CID_GEN), so a CID with a wrong generation produces "request 0x… genctr mismatch" and "invalid id N completed on queue M". A wrong CID that happens to match another outstanding request with the right generation is silent and completes the wrong request.
Spec basis
CQE DW3 Command Identifier and DW2 SQ Identifier; CID must be unique among outstanding commands on that SQ.
Typical causes
Firmware CQE-assembly bugs under high queue depth; controllers that store only some CID bits (the reason NVME_QUIRK_SKIP_CID_GEN exists: "requires the command_id value be limited").
How to detect / prove
dmesg | grep -E "genctr mismatch|invalid id". Data verification (fio verify) catches the reads that completed early. Analyzer script: build a map SQID/CID → outstanding from SQE fetches and check every CQE against it.
Linux v7.2 source
nvme.h:nvme_cid(), nvme.h:nvme_find_rq() (genctr check), nvme.h:nvme_try_complete_req() (increments genctr), pci.c:nvme_handle_cqe() ("invalid id %d completed on queue %d").
Test to provoke it
SAFE to observe: high-QD mixed fio with verify while capturing. On QEMU, a modified model that corrupts CIDs shows how Linux reacts.
D-29Duplicate completion for one command ReportedNVMe queue
In a PEX trace
Visible Two CQE MWr TLPs with the same SQID/CID and no SQE fetch of that CID in between are directly visible in the capture.
What happens
The controller posts two CQEs for the same command, for example after an internal retry or an Abort race. If the host has already reused the tag for a new command, the second CQE completes the new command early.
How it shows up
Usually reported, not silent, on Linux v7.2: nvme_try_complete_req() increments the request's generation counter on the first completion, so the duplicate CQE (carrying the old generation in CID bits 15:12) fails the check in nvme_find_rq(), is logged as "genctr mismatch" / "invalid id … completed on queue …" and ignored. It becomes silent with NVME_QUIRK_SKIP_CID_GEN, or if the duplicate arrives exactly 16 reuses later, and then it can complete an unrelated new I/O early.
Spec basis
Exactly one completion per command.
Typical causes
Abort handling races, error-recovery paths, CQ-wrap bugs (phase tag not flipped, so the host re-reads an old entry as new).
How to detect / prove
dmesg genctr messages; analyzer CID-pairing script; check CQ phase-tag handling at wrap (the duplicate appears exactly at the CQ wrap point if the phase tag is wrong).
Linux v7.2 source
nvme.h:nvme_find_rq(), pci.c:nvme_cqe_pending() (phase tag check), pci.c:nvme_update_cq_head() (phase flip on wrap).
Test to provoke it
CAUTION: Abort storms (nvme_core.io_timeout lowered on a test system) under load; small CQ sizes to force frequent wrap.
D-30Missing interrupt or completion hidden by timeout polling Timer onlyNVMe queue
In a PEX trace
Visible Two patterns: (a) the CQE MWr is there but no MSI-X MWr follows (missed interrupt), and about 30 s later (the I/O timeout) the host just resumes; (b) no CQE MWr at all for a fetched CID until the host sends Abort or resets. Timestamps between SQE fetch and CQE show the gap.
What happens
The device posts the CQE but the interrupt is lost (masked vector, wrong MSI-X entry, coalescing bug). After the I/O timeout, Linux polls the CQ, finds the completion and finishes the request normally. The application sees a 30-second stall but no error.
How it shows up
Only a warning: "I/O tag N (CID) QID M timeout, completion polled". No error is returned to the application, so monitoring based on I/O errors never sees it.
Spec basis
Interrupt generation for CQ entries (MSI-X table, Interrupt Vector in Create I/O CQ, interrupt coalescing Feature 08h).
Typical causes
Interrupt coalescing or aggregation firmware bugs; MSI-X table programming races; platform interrupt remapping problems. Linux quirks NVME_QUIRK_BROKEN_MSI and NVME_QUIRK_SINGLE_VECTOR exist for related device problems.
How to detect / prove
dmesg | grep "completion polled"; latency histograms with a long tail at exactly the timeout value; /proc/interrupts counts for the NVMe vectors not increasing while I/O completes.
Linux v7.2 source
pci.c:nvme_timeout(): polls the queue ("Did we miss an interrupt?") with nvme_poll() or nvme_poll_irqdisable(), then logs "completion polled" and returns BLK_EH_DONE; otherwise aborts ("timeout, aborting") or resets.
Test to provoke it
CAUTION: run with interrupt coalescing enabled at extreme settings (Feature 08h), CPU hotplug of the CPUs owning NVMe vectors, and watch for "completion polled".
D-31DMA writes outside the data buffer SilentPCIe / DMA
In a PEX trace
Visible Every device-to-host MWr carries its address and length. Comparing them with the PRP/SGL entries in the captured SQE (and PRP list CplDs) shows a write past the end of the buffer, to a page not in the list, or after the CQE. The analyzer sees it even when nothing in the host notices.
What happens
The device writes data beyond the PRP range, to a stale address from a previous command, or after it already posted the CQE (when the host may have freed the buffer). Without an IOMMU this silently corrupts unrelated kernel or application memory.
How it shows up
Without IOMMU: random crashes, corrupted unrelated data, nothing pointing at the SSD. With IOMMU (Intel VT-d, AMD-Vi, Arm SMMU) in translated mode: a DMA fault message naming the device's BDF and the faulting address (wording varies by IOMMU driver, for example "DMAR: [DMA Write] … fault addr …" or "AMD-Vi: Event logged [IO_PAGE_FAULT …]"; illustrative), and the write is blocked.
Spec basis
PRP/SGL data pointer rules (PRP entries and the transfer length NLB × LBA size); Linux also limits addresses for NVME_QUIRK_DMA_ADDRESS_BITS_48 devices.
Typical causes
Off-by-one in PRP list walking (page boundary at the end of a list page), metadata pointer misuse, firmware reusing a stale PRP after Abort, devices that cannot handle DMA addresses above 48 bits.
How to detect / prove
Boot with the IOMMU in translated (not passthrough) mode (intel_iommu=on iommu.passthrough=0 or the AMD equivalent) and watch dmesg for faults naming the NVMe BDF. In the analyzer, check every MWr address against the command's PRPs.
Linux v7.2 source
Driver builds PRP/SGL in drivers/nvme/host/pci.c; DMA mask reduced for NVME_QUIRK_DMA_ADDRESS_BITS_48. IOMMU fault reporting is in the IOMMU drivers (not in the local snapshot).
Test to provoke it
SAFE with IOMMU strict mode: run fio with odd buffer alignments (--iomem_align), transfer sizes that end exactly at PRP-list page boundaries, and Abort under load. Any IOMMU fault is a finding.
D-32DSM range list over-read: device ignores Number of Ranges SilentNVMe command / DMA
In a PEX trace
Visible The device's MRd for the range list asks for 4096 bytes (256 × 16) while the SQE's CDW10 NR is 0 (one range). The MRd length versus NR+1 is in the capture.
What happens
The controller DMA-reads the maximum range buffer instead of (NR+1) × 16 bytes. With a small host buffer this reads memory past the end, and with an IOMMU it faults and the DSM fails. Linux v7.2 hides it by always allocating a 4096-byte, zero-filled buffer, so on Linux the over-read is harmless and invisible. If the device then also processes the extra (zero) ranges, it should be harmless (NLB 0). If the buffer held stale ranges, it would deallocate the wrong LBAs (see D-06).
How it shows up
Silent on current Linux. Historically visible as failing trims: a 2020 Ubuntu kernel SRU ("Prevent fstrim failure so unused blocks can be discarded", Launchpad bug 1856603) restored the larger allocation after "nvme: rewrite discard support" reduced it, because discard requests failed on a non-compliant device with "FITRIM ioctl failed: Input/output error". Search results connected to that bug also mention IOMMU faults during the trim.
Spec basis
DSM CDW10 Number of Ranges (0's based); data length = (NR+1) × 16 bytes.
Typical causes
Firmware using a fixed-size DMA for the range list.
How to detect / prove
Analyzer: compare range-list MRd length with NR. On an OS that allocates exactly (NR+1)×16 bytes (or with a custom passthrough that places the range list at the end of an IOMMU-mapped page), an IOMMU fault proves it.
Linux v7.2 source
core.c:nvme_setup_discard(): alloc_size = sizeof(*range) * NVME_DSM_MAX_RANGES with the comment "Some devices do not consider the DSM 'Number of Ranges' field when determining how much data to DMA"; kzalloc zero-fills it.
Test to provoke it
CAUTION: nvme dsm --ad -s <slba> -b <nlb> with one range while capturing; check the MRd length.
D-33Verify or Compare returns Success without checking the media SilentNVMe command
In a PEX trace
Partly visible Verify (0Ch) moves no data, so the trace shows only SQE and CQE, and the completion time is the only clue (a 1 GiB Verify finishing in microseconds every time did not read the media). Compare (05h) is visible: the device fetches the host buffer (MRd/CplD), and a Success CQE for a buffer you know differs from the media is proof.
What happens
Verify is supposed to read and check the data (and PI) without transferring it. A shortcut implementation returns Success without reading, so "scrubbing" with Verify finds nothing. Compare returning Success when the data differs (or Compare Failure, 285h, when it matches) breaks fused compare-and-write users.
How it shows up
Silent: scrubs report clean drives that later return uncorrectable errors on normal reads.
Spec basis
NVM Command Set Verify (ONCS bit 7) and Compare (ONCS bit 0); Compare Failure status 285h; Unrecovered Read Error 281h expected from Verify on bad blocks.
Typical causes
Firmware treating Verify as a no-op; Compare checking only the first block.
How to detect / prove
Use Write Uncorrectable (04h, ONCS bit 1) on a test LBA, then Verify it: it must fail (with Unrecovered Read Error or similar). For Compare: compare a buffer that differs only in the last byte of the last block. Also time Verify of a large range against a Read of the same range.
Linux v7.2 source
Linux does not issue Verify or Compare for normal block I/O; use passthrough. core.c:nvme_init_known_nvm_effects() marks Write Uncorrectable as content-changing (LBCC).
Test to provoke it
CAUTION: nvme write-uncor on an LBA, then nvme verify and nvme read on it (both must fail), then rewrite the LBA to clear it.

Quiz

  1. A Format NVM with SES=000b leaves old data readable. Card D-20: failure or not?

    Answer

    Not a failure if DLFEAT read behaviour is 000b. SES=0 does not require erasure. The PEX trace shows SES in the Format SQE, so you can settle it from the capture.

  2. Why does Linux v7.2 rarely show D-28/D-29 silently?

    Answer

    The 4-bit generation counter in the CID upper bits makes stale or duplicate CQEs mismatch after the tag is reused, so they are logged ("genctr mismatch") and ignored, unless the controller needs NVME_QUIRK_SKIP_CID_GEN.

  3. Which card is "Timer only", and what log line gives it away?

    Answer

    D-30: "I/O tag … timeout, completion polled" from pci.c:nvme_timeout().
