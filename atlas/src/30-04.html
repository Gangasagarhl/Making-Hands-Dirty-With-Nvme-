III.4 PCIe Timers: Completion Timeout, Replay, Flow Control, Training, Readiness and Power

PCI Express (PCIe) has watchdogs at every layer. The Transaction Layer bounds how long a non-posted request may wait for its completion. The Data Link Layer bounds how long a transmitted TLP may wait for an acknowledgement, and how many replays are allowed. The Physical Layer bounds each state of the Link Training and Status State Machine (LTSSM). Above the link, the specification fixes how long software must wait after resets and power-state changes before it may talk to a function. Unlike most NVMe limits, many PCIe timer expiries are reported — through Advanced Error Reporting (AER) — but only if AER is implemented, enabled and not masked.

III.4.1 Completion Timeout encoding

Device Capabilities 2 tells software which ranges a function supports (Completion Timeout Ranges Supported, bits 3:0) and whether the timeout can be disabled (bit 4). Device Control 2 (offset 28h in the PCIe capability) selects the value (bits 3:0, PCI_EXP_DEVCTL2_COMP_TIMEOUT) and disables it (bit 4, PCI_EXP_DEVCTL2_COMP_TMOUT_DIS).

Read it without writing anything: lspci -vvv -s 01:00.0 | grep -E "DevCap2|DevCtl2" shows lines such as "Completion Timeout: Range ABCD, TimeoutDis+" and "Completion Timeout: 50us to 50ms, TimeoutDis-". The value applies to requests the function itself issues: for an NVMe drive, its DMA reads of SQ entries, PRP/SGL lists and write data. The Root Port's own value governs CPU MMIO reads and configuration reads to the drive.

T-33Completion Timeout: a non-posted request gets no completionReportedPCIe Transaction Layer
In a PEX trace
Visible Request with tag T (MRd or CfgRd) and no Cpl/CplD with tag T and the same Requester ID within the programmed range; measure MRd → CplD per tag. AER bits themselves are visible only if software reads them (CfgRd of the AER capability) or the device sends ERR_NONFATAL/ERR_FATAL messages.
What happens
A requester sends a non-posted request (memory read, configuration access, I/O) and no completion arrives within the Completion Timeout value. The request is abandoned.
How it shows up
AER Uncorrectable Error Status bit 14 (Completion Timeout, PCI_ERR_UNC_COMP_TIME) in the requester; Linux prints the error name "CmpltTO" and identifies the agent as Requester. If the Root Port is the requester (CPU MMIO read of a BAR, e.g. reading CSTS), the CPU receives all-ones data and some platforms escalate to a machine check. With DPC root-port PIO extensions the Root Port logs "Memory Request Completion Timeout" or "Configuration Request Completion Timeout".
Spec basis
PCIe Base: Completion Timeout mechanism; Device Capabilities 2 / Device Control 2 fields; AER uncorrectable bit 14 (default severity non-fatal verify). The header of the timed-out request is logged only if the function supports Completion Timeout prefix/header logging.
Typical causes
Completer hung (device firmware not answering an MMIO read); completion lost or routed wrongly (bad Requester ID/tag after a switch reset); link went down while requests were outstanding; completer much slower than the requester's range (common with long config accesses during device firmware boot); IOMMU blocked the DMA so the host never returned a completion (usually an Unsupported Request instead).
How to detect / prove
dmesg | grep -i -E "aer|CmpltTO"; sysfs /sys/bus/pci/devices/BDF/aer_dev_nonfatal counters; lspci -vvv UESta line shows "CmpltTO+". On an analyzer: find a MRd/CfgRd whose tag never receives a Cpl/CplD within the programmed range.
Linux v7.2 source
drivers/pci/pcie/aer.c (AER_AGENT_REQUESTER_MASK includes PCI_ERR_UNC_COMP_TIME; name string "CmpltTO"; header logged only with PCI_ERR_CAP_COMP_TIME_LOG); recovery via drivers/pci/pcie/err.c; DPC strings in drivers/pci/pcie/dpc.c. The NVMe driver's nvme_timeout() re-arms its timer while pci_channel_offline().
Test to provoke it
Hold a device in reset with an exerciser or a programmable switch while the host reads its BAR; or use an exerciser endpoint that withholds completions. On Linux, aer_inject (drivers/pci/pcie/aer_inject.c) can inject the error record without real traffic. CAUTION: real CTOs may hang the CPU core on some platforms.
T-34Completion Timeout disabled or set longer than upper-layer timersTimer onlyPCIe Transaction Layer / configuration
In a PEX trace
Partly visible The DevCtl2 value is visible if the capture includes the CfgRd/CfgWr of offset 28h of the PCIe capability; then any MRd → CplD gap longer than the upper-layer timeout with no ERR_* message shows the effect.
What happens
If the Completion Timeout is disabled, a lost completion never produces an error and the request (and its tag) is stuck forever. If it is set to Range D (seconds), it fires after the NVMe or application timeout, so the upper layer resets first and the real cause is never logged.
How it shows up
No AER entry; instead an NVMe I/O timeout (T-22), or a CPU stuck on an MMIO load (watchdog soft lockup) when the Root Port has no timeout. Tag exhaustion can stall all further DMA from the device.
Spec basis
PCIe Base: Completion Timeout Disable (Device Control 2 bit 4) is allowed only if Device Capabilities 2 bit 4 says it is supported.
Typical causes
BIOS or firmware sets long ranges to "hide" slow devices; driver for a storage controller disables CTO for long config accesses; test configuration left over.
How to detect / prove
lspci -vvv DevCtl2 for the drive and every port on the path: "TimeoutDis+" or a seconds-range value. Read-only check: setpci -s BDF CAP_EXP+28.w. Compare with /sys/class/nvme/nvme0/io_timeout.
Linux v7.2 source
Linux v7.2 PCI core does not normally reprogram the Completion Timeout for endpoints (no reference in the local drivers/pci/pci.c subset); values come from firmware or device defaults.
Test to provoke it
EXPERT: writing DevCtl2 with setpci changes live hardware behaviour and can hang the system; only on a lab machine with an exerciser.
T-35Replay Timer Timeout: TLP not acknowledged in timeReportedPCIe Data Link Layer
In a PEX trace
Visible TLP with sequence number N retransmitted with no Nak DLLP in between; interval = TLP end → retransmission start equals the replay timer; compare with the spec table for the negotiated width/rate/MPS.
What happens
Each transmitted TLP stays in the replay buffer until the link partner acknowledges it with an Ack DLLP. If the REPLAY_TIMER expires first, the transmitter resends all unacknowledged TLPs.
How it shows up
AER Correctable Error Status bit 12 (Replay Timer Timeout, PCI_ERR_COR_REP_TIMER, Linux name "Timeout", agent Transmitter). Usually masked or rate-limited by platforms; latency of the affected I/O rises by microseconds. Many of them mean the link is marginal.
Spec basis
PCIe Base, Data Link Layer: REPLAY_TIMER, its limit given by tables/formulas depending on maximum payload size, link width and data rate (plus internal delay and L0s adjustments); timer restarts on forward progress.
Typical causes
Ack DLLPs corrupted (bad DLLP at the receiver side) or lost; receiver too slow to send Ack (T-37); electrical problems causing LCRC errors (then usually Bad TLP and Nak first).
How to detect / prove
lspci -vvv CESta "Timeout+"; sysfs aer_dev_correctable counters (they include per-bit counts); analyzer: a TLP retransmitted with the same sequence number without an intervening Nak.
Linux v7.2 source
drivers/pci/pcie/aer.c: AER_AGENT_TRANSMITTER_MASK = PCI_ERR_COR_REP_ROLL | PCI_ERR_COR_REP_TIMER; correctable errors are logged and counted, no recovery action.
Test to provoke it
Signal-integrity stress: lower the transmitter swing or add attenuation on a riser; or an exerciser that drops Ack DLLPs. CAUTION.
T-36REPLAY_NUM rollover: four replays without progress force RecoveryReportedPCIe Data Link Layer
In a PEX trace
Visible Same sequence number transmitted four times without an Ack, followed by TS1/TS2 ordered sets (Recovery); count replays per sequence number.
What happens
REPLAY_NUM is a 2-bit counter of replays without forward progress. When it rolls over (the fourth replay attempt of the same TLP), the Data Link Layer tells the Physical Layer to retrain the link (LTSSM Recovery).
How it shows up
AER Correctable bit 8 (REPLAY_NUM Rollover, Linux name "Rollover"); link enters Recovery; if Recovery fails the link goes down (Surprise Down, T-44) and the NVMe device disappears. Bandwidth drops during each retrain.
Spec basis
PCIe Base, Data Link Layer: REPLAY_NUM counter, rollover action (initiate link retraining), correctable error reporting.
Typical causes
Persistent receiver errors in one direction; equalization not converged; a receiver that never acks (firmware or hardware bug).
How to detect / prove
lspci -vvv CESta "Rollover+"; the Root Port's LnkSta "Link Training" bit or speed/width change; Linux bandwidth notifications from drivers/pci/pcie/bwctrl.c; analyzer: repeated identical TLP retransmissions followed by TS1 ordered sets (Recovery).
Linux v7.2 source
Logged by drivers/pci/pcie/aer.c as a correctable error; no driver recovery. Link speed or width changes are tracked by bwctrl.c.
Test to provoke it
As T-35, with stronger impairment. CAUTION: may cause link down.
T-37Ack latency too long: unnecessary replays and lost bandwidthDegradedPCIe Data Link Layer
In a PEX trace
Visible Interval = end of TLP with sequence N → first Ack DLLP with AckNak_Seq_Num ≥ N; compare with the AckNak latency table; spurious replays follow when it exceeds the partner's replay time.
What happens
The receiver must return an Ack within its AckNak latency limit. A receiver that batches Acks for too long makes the transmitter's replay timer expire although nothing was corrupted.
How it shows up
Correctable Replay Timer Timeouts on the partner (T-35) with no Bad TLP / Bad DLLP on either side; throughput below expectation because the replay buffer fills and the transmitter stalls.
Spec basis
PCIe Base, Data Link Layer: AckNak_LATENCY_TIMER limits (tables by payload size, width, rate); it should be well below the partner's replay limit.
Typical causes
Device Data Link Layer implementation coalescing Acks too aggressively; receive-side backpressure inside the device; L0s entry delaying DLLPs.
How to detect / prove
Analyzer: measure time from TLP end to the covering Ack DLLP; compare with the spec table for the negotiated width, rate and MPS. Throughput test with fio sequential reads at high queue depth.
Linux v7.2 source
Not visible to Linux except via the correctable counters (aer.c).
Test to provoke it
Run maximum-bandwidth sequential I/O and inspect Ack spacing in an analyzer. SAFE.
T-38Flow-control credit starvation (no UpdateFC)Timer onlyPCIe Transaction / Data Link Layer
In a PEX trace
Visible Track UpdateFC DLLPs per type (P/NP/Cpl, header/data); interval between consecutive UpdateFC of a type should be ≤ ~30 µs while credits are finite; a credit counter stuck at zero with TLPs pending on the other side proves starvation.
What happens
A transmitter may send a TLP only when the receiver has advertised credits for it. If the receiver stops returning credits (no UpdateFC DLLPs), traffic of that type stops. No error is defined for "slow credits"; only upper-layer timers notice.
How it shows up
Nothing on the starved link itself, unless the optional flow-control update watchdog retrains the link or a Flow Control Protocol Error (AER uncorrectable bit 13, PCI_ERR_UNC_FCP) is detected for an illegal credit update. Upstream symptoms: Completion Timeouts (T-33), NVMe I/O timeouts (T-22).
Spec basis
PCIe Base: InitFC1/InitFC2/UpdateFC DLLPs per type (Posted, Non-Posted, Completion; header and data credits); UpdateFC sent when credits are freed and periodically (about every 30 µs) while credits are not infinite; an optional 200 µs update watchdog verify.
Typical causes
Device receive buffer stuck (firmware not draining posted writes, e.g. doorbells or CQE writes from the host side); deadlock between posted and non-posted queues violating ordering rules; switch buffer exhaustion.
How to detect / prove
Analyzer: credit tracking view (most analyzers compute available credits): the advertised credit counter stays at zero while the partner has TLPs waiting. lspci cannot show credits.
Linux v7.2 source
No direct visibility. Indirect: aer.c for FCP errors and Completion Timeouts, pci.c:nvme_timeout() for stalled commands.
Test to provoke it
Exerciser endpoint configured to withhold UpdateFC for posted credits while the host writes doorbells. EXPERT.
T-39LTSSM state timeout: training loops, falls back or downshiftsDegradedPCIe Physical Layer
In a PEX trace
Visible LTSSM state entries/exits (TS1/TS2, EIOS, electrical idle) with timestamps: interval = state entry → exit or fallback; e.g. Polling.Active → Detect after 24 ms. Negotiated width/rate visible in TS ordered sets. Requires an analyzer that records the training (start capture before reset).
What happens
Each LTSSM state has a timeout. If the expected ordered sets are not seen in time, the state machine moves on: Detect repeats every 12 ms while no receiver is detected; Polling and Configuration fall back to Detect; Recovery may fall back to Detect (link down). Repeated partial success shows up as a link trained at lower width or speed.
How it shows up
No AER error for a successful downshift. lspci -vvv LnkSta shows "Speed 8GT/s (downgraded), Width x2 (downgraded)" versus LnkCap. Root Port LnkSta2 equalization bits; Link Bandwidth Management Status. In the worst case the link never reaches L0 and the device is missing.
Spec basis
PCIe Base, LTSSM: Detect.Quiet 12 ms timeout verified; Polling.Active 24 ms, Polling.Configuration 48 ms, Configuration.Linkwidth.Start 24 ms, other Configuration substates 2 ms, Recovery.RcvrLock 24 ms, Recovery.RcvrCfg 48 ms, Recovery.Idle 2 ms verify in spec; equalization phase timeouts at 8 GT/s and above verify.
Typical causes
Signal integrity (lane failing receiver detect or symbol lock); lane reversal or polarity issues; equalization failure at 16/32 GT/s; reference clock problems; mis-wired lanes on risers.
How to detect / prove
Compare LnkCap and LnkSta for both ends; analyzer LTSSM view: state durations and which state times out; Linux bwctrl.c link speed change notifications; repeated link-up/down events in dmesg (pciehp: "Link Down"/"Link Up").
Linux v7.2 source
quirks.c:pcie_failed_link_retrain() handles one known case (link stuck in training; retrain at 2.5 GT/s then lift the limit) — "broken device, retraining non-functional downstream link at 2.5GT/s".
Test to provoke it
Disable lanes with a lane-disabling interposer, or force target speed (setpci on Link Control 2 — EXPERT, can drop the link) and retrain.
T-40Link does not come up in time after reset or power-onTimer onlyPCIe Physical / software wait
In a PEX trace
Visible Interval = PERST# deassertion (if the fixture records sideband) or electrical idle exit → first TS1 → L0 (first DLLP/InitFC); and L0 → first CfgRd from the host (must be ≥ 100 ms above 5 GT/s).
What happens
After a reset the downstream component must enter Detect within 20 ms, and software must not send configuration requests until the link is up and a further 100 ms have passed (above 5 GT/s, measured from Data Link Layer Link Active). If the link is not active within the host's wait, software declares the device missing.
How it shows up
Linux: the device does not enumerate, or not ready Nms after bus reset; giving up; for hot-plug ports, no "Link Up" event. Without Data Link Layer Link Active reporting Linux simply sleeps 1000 ms + delay and hopes.
Spec basis
PCIe Base reset and link-up timing rules (as quoted in drivers/pci/pci.c comments: enter Detect within 20 ms; 100 ms minimum before configuration requests; at least 1 s before declaring a non-responding device broken). Link Capabilities DLLLARC; Link Status DLLLA and LT bits.
Typical causes
Slow device PHY start; reference clock or PERST# sequencing errors; LTSSM failures (T-39).
How to detect / prove
dmesg with pci=... debug (dyndbg="file drivers/pci/* +p") shows "waiting N ms for downstream link"; analyzer timestamp of PERST# deassertion vs first TS1 and vs L0.
Linux v7.2 source
pci.c:pci_bridge_wait_for_secondary_bus(), pcie_wait_for_link_delay() (20 ms then poll DLLLA, timeout PCIE_LINK_RETRAIN_TIMEOUT_MS, then pcie_failed_link_retrain()), pcie_wait_for_link_status() polling every 1 ms.
Test to provoke it
Delay the device's PERST# release with a controllable fixture; secondary bus reset via /sys/bus/pci/devices/BDF/reset (CAUTION: resets the device).
T-41Device not ready after reset: RRS beyond 1 s or no response at allTimer onlyPCIe configuration / readiness
In a PEX trace
Visible CfgRd0 → Cpl with status RRS (Configuration Request Retry) repeated; interval = reset (or L0) → first CplD with a valid Vendor ID; compare with 1 s. DRS/FRS messages, if sent, are visible as Msg TLPs.
What happens
After a Conventional Reset or D3cold→D0, a function must accept configuration requests within 1 s, but may answer with Request Retry Status (RRS, formerly CRS) to ask for more time. A function that keeps answering RRS, or answers with all-ones, is "not ready".
How it shows up
Linux: pci BDF: not ready 1023ms after FLR; waiting, then ready Nms after ... or, after 60 s, not ready 65535ms after ...; giving up. During enumeration: not ready after Nms; giving up from pci_bus_wait_rrs(). NVMe probe never starts.
Spec basis
PCIe Base: device readiness 1 s after Conventional Reset; RRS completions; Root Control "Configuration RRS Software Visibility Enable" (with it, a Vendor ID read returns the special value 0001h); Readiness Time Reporting extended capability; Device Readiness Status (DRS) and Function Readiness Status (FRS) messages; Immediate Readiness bit in the Status register.
Typical causes
Firmware boot slower than 1 s (large drives loading internal tables); firmware stuck in a boot loop; failed link retrain.
How to detect / prove
dmesg lines above; lspci -s BDF -vvv returning "Unknown header type 7f" (all-ones); analyzer: CfgRd0 answered by Cpl with status RRS repeatedly.
Linux v7.2 source
pci.c:pci_dev_wait() (uses Vendor ID with RRS SV, otherwise the Command register; PCI_RESET_WAIT 1000 ms, caller timeout PCIE_RESET_READY_POLL_MS 60000 ms); probe.c:pci_enable_rrs_sv(), pci_bus_wait_rrs(), pci_bus_read_dev_vendor_id(..., 60*1000); probe.c:pci_imm_ready_init() reads Immediate Readiness. The local v7.2 subset showed no consumer of Readiness Time Reporting, DRS or FRS verify.
Test to provoke it
Trigger FLR via echo 1 > /sys/bus/pci/devices/BDF/reset (CAUTION: unbind the NVMe driver first, data in flight is lost) and time the "ready Nms" message.
T-42D3hot→D0 transition: access before the 10 ms recovery timeTimer onlyPCIe power management
In a PEX trace
Visible Interval = CfgWr to PMCSR setting D0 → next config/memory request to that function; must be ≥ 10 ms (or the device's value); its completion shows whether the device was ready.
What happens
After writing PowerState=D0 in the PM capability of a function that was in D3hot, software must wait 10 ms before accessing it (unless the function reports otherwise). Accessing earlier, or a function that needs longer, gives undefined results.
How it shows up
Config reads return garbage or all-ones; MMIO reads time out (T-33); the NVMe driver sees CSTS=0xffffffff on resume. Linux increases the delay for known-bad devices (quirks 20 ms or 120 ms).
Spec basis
PCI Power Management: D3hot→D0 recovery time 10 ms; "No Soft Reset" bit determines whether state is preserved.
Typical causes
Device firmware needs longer than 10 ms; platform-specific slowness; driver skipping the wait.
How to detect / prove
dmesg with PM debug; analyzer: CfgWr to PMCSR (D0) followed by CfgRd sooner than 10 ms, answered badly.
Linux v7.2 source
pci.c:pci_dev_d3_sleep() (max of dev->d3hot_delay and global pci_pm_d3hot_delay; default PCI_PM_D3HOT_WAIT = 10 ms, defined in drivers/pci/pci.h); then pci_dev_wait(dev, "power up D3hot->D0uninitialized", PCIE_RESET_READY_POLL_MS). quirks.c:quirk_d3hot_delay() raises it to 20 ms for some devices; quirk_intel_pcie_pm() sets the global delay to 120 ms; quirk_remove_d3hot_delay() sets 0 for some Intel chipset functions.
Test to provoke it
Runtime PM: echo auto > /sys/bus/pci/devices/BDF/power/control and idle the device; measure resume. SAFE.
T-43Function Level Reset not complete in 100 msTimer onlyPCIe reset
In a PEX trace
Visible Interval = CfgWr to Device Control with Initiate FLR (bit 15) → first CfgRd that completes successfully; must be ≥ 100 ms (unless Immediate Readiness); outstanding non-posted requests at FLR time are visible.
What happens
After Initiate FLR, a function must complete the reset within 100 ms; it may silently drop requests during that time. Software also should wait for outstanding transactions to drain before initiating FLR.
How it shows up
Linux: timed out waiting for pending transaction; performing function level reset anyway (Transaction Pending bit still set after about 700 ms of polling), then readiness messages from pci_dev_wait() (T-41).
Spec basis
PCIe Base: FLR (Device Capabilities FLR bit, Device Control Initiate FLR bit 15); 100 ms completion requirement; Device Status Transactions Pending bit.
Typical causes
DMA engine stuck (completions never returned); firmware slow to reinitialise after FLR.
How to detect / prove
dmesg; lspci -vvv DevSta "TransPend+" before reset; time between CfgWr setting Initiate FLR and the first successful CfgRd.
Linux v7.2 source
pci.c:pcie_flr(): pci_wait_for_pending_transaction() (polls 4 times with 0, 100, 200, 400 ms sleeps), sets PCI_EXP_DEVCTL_BCR_FLR, msleep(100) unless dev->imm_ready, then pci_dev_wait(dev, "FLR", PCIE_RESET_READY_POLL_MS).
Test to provoke it
echo flr > /sys/bus/pci/devices/BDF/reset_method then echo 1 > .../reset with the driver unbound. CAUTION.
T-44Surprise link down / hot removal while I/O is in flightReportedPCIe link / hot-plug
In a PEX trace
Partly visible The link drop is visible (traffic stops, electrical idle, Detect) and outstanding tags never complete; the Surprise Down AER bit and hot-plug slot events are in the port's registers, visible only if read by software over a probed link.
What happens
The link drops without warning (cable pull, power fault, failed Recovery). Outstanding requests can never complete; the port may report a Surprise Down error and hot-plug events.
How it shows up
Port AER uncorrectable bit 5 (Surprise Down, PCI_ERR_UNC_SURPDN) if the port supports Data Link Layer Link Active reporting; Slot Status Data Link Layer State Changed / Presence Detect Changed; DPC may contain the port. NVMe: reads of CSTS return all-ones, the controller is removed; I/O fails with a host path error and fails over if multipath.
Spec basis
PCIe Base: Surprise Down error, Data Link Layer State Changed, hot-plug slot registers, Downstream Port Containment (DPC).
Typical causes
Physical removal; power loss on the device; REPLAY_NUM rollover followed by failed Recovery (T-36); deep power state not exiting (T-15).
How to detect / prove
dmesg: pciehp "Link Down", AER "Surprise Down", DPC containment messages, NVMe "controller is down" or removal. lspci -vvv on the port: SltSta DLActive-.
Linux v7.2 source
pci.c:nvme_timeout() checks pci_dev_is_disconnected() and moves the controller to DELETING; pci.c:pci_dev_wait() returns early when disconnected; DPC in drivers/pci/pcie/dpc.c, recovery in err.c. (pciehp itself is not in this atlas's source subset.)
Test to provoke it
Hot-plug capable slot: echo 0 > /sys/bus/pci/slots/N/power during I/O (CAUTION), or pull a U.2 drive in a hot-plug backplane (EXPERT).
T-45ASPM exit latency larger than the endpoint can acceptDegradedPCIe power management
In a PEX trace
Visible Interval = electrical idle (EIOS) → first TLP after exit, i.e. the L0s/L1 exit time; compare with LnkCap exit latency and DevCap acceptable latency (both visible in config CplD payloads if captured).
What happens
Each port reports how long it needs to leave L0s and L1 (Link Capabilities exit latencies); each endpoint reports how much latency it can accept (Device Capabilities acceptable latencies). If exit latency (plus 1 µs per switch for L1) exceeds acceptable latency, enabling that ASPM state can starve the device.
How it shows up
If enabled anyway (by firmware or by forcing a policy): latency spikes, sometimes Completion Timeouts or replay errors after L1 exit. If Linux detects the mismatch it silently does not enable the state (higher power, no error).
Spec basis
PCIe Base: Link Capabilities L0s/L1 Exit Latency, Device Capabilities Endpoint L0s/L1 Acceptable Latency, Link Control ASPM Control.
Typical causes
Under-reported exit latencies; PLLs that take longer than declared; platform BIOS forcing ASPM.
How to detect / prove
lspci -vvv: LnkCap "ASPM L0s L1, Exit Latency L0s <1us, L1 <8us", DevCap "Latency L0s <64ns, L1 <1us", LnkCtl "ASPM L1 Enabled". Compare with /sys/module/pcie_aspm/parameters/policy. Measure fio latency with ASPM on and off (pcie_aspm=off).
Linux v7.2 source
drivers/pci/pcie/aspm.c:pcie_aspm_check_latency() converts encodings (calc_l0s_latency() = 64 ns « encoding, calc_l1_latency() = 1 µs « encoding; encoding 7 means "more than"), adds 1 µs per switch for L1 and clears aspm_capable bits that do not fit. It does not check L1 substates ("We assume that the L1 exit latencies advertised by a device include L1 substate latencies").
Test to provoke it
Compare tail latency with pcie_aspm.policy=performance vs powersupersave. SAFE.
T-46L1 substates / LTR misprogrammed: wake too slow or link lostDegradedPCIe power management
In a PEX trace
Partly visible L1 entry (PM DLLPs / EIOS) and exit timing visible; L1.2 itself turns the PHY off so the analyzer sees only electrical idle and the wake; CLKREQ# is sideband (visible only with a sideband probe). LTR Message TLPs carrying latency values are visible.
What happens
L1.1/L1.2 turn off more of the PHY. Entry depends on the device's Latency Tolerance Reporting (LTR) value versus the LTR_L1.2_THRESHOLD; exit timing depends on T_POWER_ON and Common_Mode_Restore_Time. Wrong values make exit slower than the device tolerates, or make exit fail.
How it shows up
Latency spikes after idle; in bad cases the link fails to retrain after L1.2 and the drive disappears (T-15, T-44). No error is reported for a slow exit.
Spec basis
PCIe Base: L1 PM Substates extended capability (capability ID 1Eh): L1SS capabilities, Control 1 (enables, Common_Mode_Restore_Time, LTR_L1.2_THRESHOLD value/scale), Control 2 (T_POWER_ON scale/value); LTR extended capability (18h): Max Snoop/No-Snoop Latency; Device Control 2 LTR Mechanism Enable.
Typical causes
Inconsistent values programmed on the two ends; T_POWER_ON shorter than the PHY needs; CLKREQ# routing problems; device reporting very large LTR values.
How to detect / prove
lspci -vvv: "L1SubCap", "L1SubCtl1: PCI-PM_L1.2+ ASPM_L1.2+ ... T_CommonMode=..us LTR1.2_Threshold=..ns", "L1SubCtl2: T_PwrOn=..us", "LTR+" in DevCtl2. Compare both ends of the link. Reproduce with L1.2 disabled.
Linux v7.2 source
aspm.c:aspm_calc_l12_info() computes T_POWER_ON, Common_Mode_Restore_Time and LTR threshold from both ends; pcie_encode_t_power_on(); pci_configure_aspm_l1ss(), pci_save_aspm_l1ss_state()/pci_restore_aspm_l1ss_state() across suspend.
Test to provoke it
Toggle L1.2 via the ASPM policy (powersupersave) on a laptop and run idle/burst fio patterns. SAFE.
📭 What the spec does not say

No PCIe timer bounds how long an endpoint may take to process a posted write (such as an NVMe doorbell) or to issue its next request. A drive that accepts a doorbell write and then does nothing for a minute violates no PCIe rule. The only watchdog for "the device forgot to do the work" is the host NVMe timeout.
