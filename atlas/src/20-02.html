4 Generic Command Status (SCT 0)

Generic status codes can be returned by any command. SC 0x00–0x7F apply to all commands. SC 0x80–0xBF are "generic for the I/O command set" codes such as LBA Out of Range. Linux writes them as 0x000–0x0FF. In practice, almost everything here comes from argument validation or from controller state (format, sanitize, reset). Only a few (0x04, 0x05, 0x06, 0x21, 0x22) point to a real hardware or transport problem.

How to read the cards: "Linux" values are the shifted layout from include/linux/nvme.h. "QEMU" names the function in hw/nvme/ctrl.c where the reference model returns the code. That is a good guide to typical cause, but it is implementation-specific impl. Unless a card says otherwise, Linux maps the code to BLK_STS_IOERR / -EIO (see §3.4.2) and retries it unless DNR is set.

S-01Invalid Command Opcode (SCT 0 / SC 0x01) ReportedNVMe command
What happens
The controller does not implement the opcode on that queue type (admin vs I/O), or the opcode is reserved. Nothing is executed.
How it shows up
CQE with SCT 0 / SC 0x01, normally DNR=1. Linux: NVME_SC_INVALID_OPCODE 0x001 → BLK_STS_NOTSUPP → -EOPNOTSUPP. dmesg "Invalid Command Opcode".
Spec basis
NVMe Base: Generic Command Status "Invalid Command Opcode". Commands Supported and Effects log (LID 05h) CSUPP bit says which opcodes the controller claims to support.
Typical causes
Optional command not supported (Compare, Write Zeroes, Copy, Verify, Write Uncorrectable); vendor tool sending a vendor opcode to a different model; I/O opcode sent on the admin queue; mismatch between Identify ONCS/OACS bits and actual support. QEMU: nvme_admin_cmd(), nvme_io_cmd_nvm(), nvme_io_cmd_zoned() reject opcodes whose effects entry lacks NVME_CMD_EFF_CSUPP.
How to detect / prove
Compare against nvme id-ctrl (OACS, ONCS) and nvme effects-log /dev/nvme0. If the effects log says CSUPP=1 but the command returns 0x01, the controller contradicts itself (conformance bug).
In a trace
SQE fetch, then an immediate CQE (a few µs) with no data TLPs.
Linux v7.2 source
core.c:nvme_error_status() (NOTSUPP); pr.c:nvme_status_to_pr_err() → -EINVAL for persistent reservations.
Test to provoke it
SAFE: nvme io-passthru /dev/nvme0n1 --opcode=0x7f --namespace-id=1 (a reserved I/O opcode) or nvme admin-passthru /dev/nvme0 --opcode=0x7f. Check that DNR=1.
S-02Invalid Field in Command (SCT 0 / SC 0x02) ReportedNVMe command
What happens
A field in the SQE (CDW10–15, flags, PSDT, NSID-dependent fields, data length) holds a reserved or unsupported value. This is the catch-all argument error.
How it shows up
SCT 0 / SC 0x02, normally DNR=1. If the controller supports it, the Error Information log entry's Parameter Error Location names the byte and bit that was wrong. Linux 0x002 → BLK_STS_NOTSUPP → -EOPNOTSUPP.
Spec basis
Generic "Invalid Field in Command". Error Information log field Parameter Error Location (libnvme parm_error_location).
Typical causes
Transfer larger than MDTS (QEMU nvme_check_mdts()); unsupported Feature ID or log page offset (QEMU nvme_get_log(), nvme_set_feature()); Identify CNS not supported; bad Abort SQID (nvme_abort()); reserved bits set; SGL requested when unsupported (nvme_map_dptr()); Flush to a bad NSID; DSM range count too large. QEMU returns this from about 86 sites, more than any other code.
How to detect / prove
nvme error-log /dev/nvme0 -e 16: match SQID/CID, then read parm_error_location. Re-check the command against Identify limits (MDTS, ONCS, SGLS, DMRL/DMRSL).
In a trace
Immediate CQE after the SQE fetch. For PRP-based commands the device may first fetch the PRP list before rejecting.
Linux v7.2 source
core.c:nvme_error_status(); core.c:nvme_scan_work() falls back to sequential namespace scanning when Identify NS List fails with DNR.
Test to provoke it
SAFE: Read with NLB larger than MDTS through nvme io-passthru; nvme get-feature -f 0x7e on an unsupported FID; nvme get-log -i 0x02 -l 4096 -o 0x10000 (offset beyond the log).
S-03Command ID Conflict (SCT 0 / SC 0x03) ReportedNVMe command
What happens
The host submitted a command whose CID is already outstanding on the same SQ. The controller may reject the new command.
How it shows up
SC 0x03. Many controllers do not check this and instead complete two commands with the same CID, which the host then confuses. Linux does not handle the code specially (→ -EIO).
Spec basis
Generic "Command ID Conflict". CIDs must be unique per SQ among outstanding commands.
Typical causes
Host driver bug (tag reuse before completion), a user-space driver (SPDK-style) with a broken tag allocator, or a duplicate completion making the host believe a tag is free. QEMU does not return it.
How to detect / prove
In an analyzer trace, list outstanding CIDs per SQ and flag a second SQE with the same CID before its CQE. Linux v7.2 adds a 4-bit generation counter to CID bits 15:12 (nvme_cid_install_genctr()) and warns on mismatching completions, which catches the host-side variant.
In a trace
Two SQEs on one SQ with the same CID and no CQE between them.
Linux v7.2 source
nvme.h:nvme_cid(), nvme_genctr_from_cid(); quirk NVME_QUIRK_SKIP_CID_GEN disables the generation counter for devices that mishandle it.
Test to provoke it
EXPERT: only from a user-space driver or a protocol exerciser that can submit duplicate CIDs.
S-04Data Transfer Error (SCT 0 / SC 0x04) ReportedNVMe command / PCIe DMA
What happens
Moving data or metadata between host memory and the controller failed: a DMA read returned an error completion, a write could not be posted, or a transport failed in the middle of a transfer.
How it shows up
SC 0x04, DNR varies (QEMU uses both). Often there is a companion PCIe-level error: Unsupported Request or Completer Abort completion for the device's MRd, or an IOMMU fault on the host. Linux → -EIO.
Spec basis
Generic "Data Transfer Error". PCIe completion status UR/CA for the device's memory reads.
Typical causes
IOMMU blocks a PRP/SGL address (stale mapping, use-after-unmap in the host driver); a bad PRP entry pointing to non-existent memory; host memory poisoned (ECC) during the DMA read; link errors that corrupt the transfer. QEMU: nvme_map_addr(), nvme_map_prp(), nvme_map_sgl(), nvme_tx() return it when pci_dma_rw() fails or the address cannot be mapped.
How to detect / prove
dmesg for IOMMU/DMAR faults with the device's BDF at the same time; AER logs; analyzer: the device's MRd to the PRP address gets a UR/CA completion. Check lspci -vvv DevSta "UnsupReq+" / "AuxPwr".
In a trace
MRd from device → Cpl with status UR or CA (or no completion → device completion timeout), followed by a CQE with SC 0x04.
Linux v7.2 source
No special handling. Mapped to BLK_STS_IOERR in core.c:nvme_error_status().
Test to provoke it
EXPERT: in a QEMU guest with a vIOMMU, unmap a buffer while a passthrough command is outstanding; or use a protocol exerciser to return UR to the device's data MRd.
S-05Commands Aborted due to Power Loss Notification (SCT 0 / SC 0x05) ReportedNVMe command
What happens
The controller saw a power-loss notification (e.g. a shutdown notification by CC.SHN, or a platform power-fail signal) and aborted outstanding commands instead of finishing them.
How it shows up
SC 0x05 on the commands that were outstanding. Retryable after power returns. Linux → -EIO if the request ends there; usually the controller is being shut down anyway.
Spec basis
Generic "Commands Aborted due to Power Loss Notification". Shutdown via CC.SHN / CSTS.SHST.
Typical causes
Host issued a shutdown while I/O was still queued (driver ordering bug); surprise power loss with a hold-up circuit giving the firmware time to post completions; hot-unplug.
How to detect / prove
Correlate with SMART "Unsafe Shutdowns" increasing, the Persistent Event log "Power-on or Reset" event, and CC.SHN writes in the trace. The data from writes aborted this way is not guaranteed. Verify it with read-back.
In a trace
MWr to CC (offset 14h) setting SHN, then a burst of CQEs with SC 0x05, then CSTS.SHST = 10b (shutdown complete).
Linux v7.2 source
Linux quiesces and drains queues before shutdown (pci.c:nvme_dev_disable()). Seeing 0x05 under Linux suggests an unexpected power event. No special case in nvme_error_status().
Test to provoke it
CAUTION: write CC.SHN through a user-space driver while I/O is queued (not with the kernel driver bound). EXPERT: a power-fail test fixture.
S-06Internal Error (SCT 0 / SC 0x06) ReportedNVMe command / device
What happens
The command failed because of something inside the controller that is not a media error and not the host's fault: a firmware exception, resource exhaustion, an internal bus or SRAM error.
How it shows up
SC 0x06; DNR=0 for transient problems, DNR=1 if the firmware knows it will repeat. Often comes with an Error-type AEN (Transient Internal Error 04h or Persistent Internal Error 03h) and a Persistent Event log "NVM Subsystem Hardware Error" event. Linux → -EIO after retries.
Spec basis
Generic "Internal Error". Asynchronous Event Information – Error Status values 03h/04h (see S-79).
Typical causes
Firmware bugs (assertion, corner-case state), DRAM ECC errors inside the SSD, thermal throttling edge cases, internal queue overflow. QEMU: returned when the backend block-status query fails (nvme_check_dulbe()), in zone-state checks for impossible states, and in nvme_map_addr() when too many SG entries are needed.
How to detect / prove
Read nvme error-log, nvme persistent-event-log and the vendor telemetry (nvme telemetry-log --output-file=...) right after the event. Repeat the same command: if it fails deterministically, record it as a firmware defect with the exact SQE.
In a trace
Normal SQE fetch, sometimes partial data transfer, then a CQE with SC 0x06. Latency is often abnormal (long internal retry before giving up).
Linux v7.2 source
Default branch of core.c:nvme_error_status(); persistent internal error AEN → core.c:nvme_handle_aer_persistent_error() resets the controller.
Test to provoke it
Not reliably possible from the host. Use vendor error-injection commands, or QEMU with a backend whose block-status call fails while DULBE is enabled.
S-07Command Abort Requested (SCT 0 / SC 0x07) ReportedNVMe command
What happens
The command was aborted because the host sent an Abort (admin opcode 08h) naming its SQID and CID.
How it shows up
The aborted command completes with SC 0x07. The Abort command itself completes with Dword 0 bit 0 = 0 if the command was aborted, 1 if not. Linux prints "Abort status: 0x%x" from pci.c:abort_endio().
Spec basis
Admin Abort command; Identify Controller ACL (Abort Command Limit, 0's based); Generic "Command Abort Requested".
Typical causes
Almost always a host timeout: Linux pci.c:nvme_timeout() sends Abort for an I/O command that exceeded nvme_core.io_timeout (default 30 s) the first time it times out. The real problem is whatever made the command slow or stuck.
How to detect / prove
dmesg "I/O tag N (cid) opcode ... QID q timeout, aborting" followed by "Abort status". If the command is not aborted and times out again, Linux resets the controller ("timeout, reset controller").
In a trace
Original SQE → long silence → admin SQE opcode 08h with CDW10 = SQID | CID<<16 → CQE for the target (SC 0x07) and a CQE for the Abort.
Linux v7.2 source
pci.c:nvme_timeout(), pci.c:abort_endio(); the limit ctrl->abort_limit is set to ACL+1 in core.c.
Test to provoke it
CAUTION: in QEMU, cause a stalled backend I/O (for example a blkdebug rule with a delay); lower io_timeout (writable module parameter) to see the abort sooner. QEMU's nvme_abort() cancels the backend AIO, which completes it with 0x07.
S-08Command Aborted due to SQ Deletion (SCT 0 / SC 0x08) ReportedNVMe command
What happens
The host deleted an I/O SQ (admin opcode 00h) while commands were still outstanding on it. The controller aborts them.
How it shows up
SC 0x08 on each outstanding command, posted to the associated CQ before the Delete SQ completes. If the CQ has already been reaped, these completions can be lost.
Spec basis
Delete I/O Submission Queue; Generic "Command Aborted due to SQ Deletion".
Typical causes
Controller reset path, CPU hot-unplug changing queue count, driver unload. QEMU: nvme_del_sq() and nvme_ctrl_reset() set this status on in-flight requests.
How to detect / prove
Analyzer: Delete SQ SQE followed by completions with SC 0x08. Linux normally cancels requests itself (0x371) before deleting queues, so seeing many 0x08 under Linux suggests a driver bypass or a non-Linux host.
In a trace
Admin SQE opcode 00h → CQEs on the I/O CQ with SC 0x08 → CQE for Delete SQ.
Linux v7.2 source
pci.c:adapter_delete_sq(); mapped to -EIO by default.
Test to provoke it
EXPERT: user-space driver deleting a busy SQ.
S-09Fused command aborted: Failed Fused (0x09) / Missing Fused (0x0A) ReportedNVMe command
What happens
A fused pair (e.g. Compare + Write = atomic compare-and-write) did not run as a pair. 0x09: the other half failed, so this half was aborted. 0x0A: the adjacent SQE was not the expected fused partner.
How it shows up
One half gets the real error (e.g. Compare Failure 0x285), and the other gets 0x09. A mis-built pair gets 0x0A.
Spec basis
Fused Operation (FUSE field in CDW0: first/second command); Identify FUSES. Generic codes 0x09, 0x0A.
Typical causes
Compare miscompare (expected for CAS semantics); host submitting the two halves non-adjacently (another thread rang the doorbell in between); controller not supporting fused operations.
How to detect / prove
Trace: both SQEs must be consecutive slots in the same SQ, and the tail doorbell must cover both in one write.
In a trace
SQE[n] FUSE=01b, SQE[n+1] FUSE=10b. On failure: CQE(n) Compare Failure, CQE(n+1) SC 0x09.
Linux v7.2 source
The kernel block path does not issue fused commands. They come only through passthrough (ioctl.c). Status → -EIO.
Test to provoke it
EXPERT: user-space (SPDK-style) compare-and-write with deliberately wrong compare data → 0x285 + 0x09.
S-10Invalid Namespace or Format (SCT 0 / SC 0x0B) ReportedNVMe command
What happens
The NSID is not valid for this command (not allocated, not attached, 0 where not allowed, or FFFFFFFFh where broadcast is not allowed), or the namespace's current format does not support the command.
How it shows up
SC 0x0B, normally DNR=1. Linux 0x00B → BLK_STS_NOTSUPP → -EOPNOTSUPP. During a namespace rescan, Linux treats an Identify Namespace failure with DNR as "namespace gone" and removes the block device.
Spec basis
Generic "Invalid Namespace or Format". Identify NN (number of namespaces), Active Namespace ID list (CNS 02h).
Typical causes
Namespace deleted or detached by another host or a management tool; stale NSID after reformatting; tools using NSID 1 on a drive where it does not exist. QEMU: nvme_io_cmd(), nvme_identify_ns(), nvme_get_feature(), nvme_smart_info() (per-namespace SMART not supported) and about 15 other sites.
How to detect / prove
nvme list-ns /dev/nvme0 --all versus nvme list-ns /dev/nvme0 (allocated vs attached); look for a Namespace Attribute Changed AEN and the Changed Namespace List log (LID 04h).
In a trace
Immediate CQE after the SQE fetch.
Linux v7.2 source
core.c:nvme_error_status(); core.c:nvme_validate_ns() starts with ret = NVME_SC_INVALID_NS | NVME_STATUS_DNR and calls nvme_ns_remove() on fatal (DNR) errors.
Test to provoke it
SAFE: nvme id-ns /dev/nvme0 -n 0xfffe (an unused NSID). CAUTION: detach a namespace (nvme detach-ns) with I/O running and watch the block device disappear.
S-11Command Sequence Error (SCT 0 / SC 0x0C) ReportedNVMe admin
What happens
The command is valid on its own but not allowed in the current state of a multi-command sequence or controller state.
How it shows up
SC 0x0C, usually DNR=1.
Spec basis
Generic "Command Sequence Error". Examples in the spec: Firmware Image Download sequencing, Set Features Number of Queues after queues exist, security protocol sequences.
Typical causes
Changing Number of Queues (FID 07h) after I/O queues were created (QEMU nvme_set_feature(): if (n->qs_created) return NVME_CMD_SEQ_ERROR); changing FDP mode while namespaces exist in the endurance group (QEMU); Firmware Commit without a complete downloaded image; TCG/OPAL protocol out of order.
How to detect / prove
Reconstruct the admin command order from a trace or from the nvme_setup_cmd/nvme_complete_rq tracepoints; check which preceding command changed the state.
In a trace
Immediate CQE. The interesting part is the earlier commands.
Linux v7.2 source
Linux sets Number of Queues once per reset (core.c:nvme_set_queue_count()) before creating queues, so it avoids this. A tool that sends the feature at runtime gets 0x0C.
Test to provoke it
SAFE on QEMU / CAUTION on hardware: nvme set-feature /dev/nvme0 -f 7 -v 0x00030003 while the driver has queues.
S-12Data pointer descriptor errors: SGL 0x0D–0x11, 0x16, 0x1E; PRP Offset 0x13 ReportedNVMe command / data pointer
What happens
The controller rejects the data pointer: an invalid SGL Segment/Last Segment descriptor (0x0D), a bad number of descriptors (0x0E), Data SGL length too short or too long (0x0F), Metadata SGL length invalid (0x10), unsupported SGL descriptor type (0x11), SGL offset invalid (0x16, mainly fabrics in-capsule data), SGL data block granularity invalid (0x1E), or PRP entry offset invalid (0x13).
How it shows up
One of these SCs, with DNR=1 in QEMU. Linux → -EIO. These almost always point to a host driver or IOMMU bug, not a drive problem.
Spec basis
PRP rules (PRP1 offset; PRP list entries must be page-aligned, Dword-aligned offsets); SGL descriptor types; Identify Controller SGLS field.
Typical causes
QEMU: nvme_map_sgl() → 0x0D for a misplaced segment descriptor; nvme_map_sgl_data() → 0x0E / 0x0F; nvme_map_mptr() → 0x10; 0x11 for unknown types (ctrl.c line ~1013); nvme_map_prp(), nvme_create_cq()/nvme_create_sq() → 0x13 for a non-page-aligned PRP. In real systems: a new driver (user-space or in-kernel) building PRP lists across page boundaries incorrectly, or MPS (CC.MPS) disagreeing with the host's assumed page size.
How to detect / prove
Decode the SQE's PSDT and DPTR in the trace and walk the PRP list or SGL by hand. Check that CC.MPS matches the host page size the driver uses.
In a trace
MRd of the PRP list or SGL segment (sometimes), then a CQE. No data TLPs.
Linux v7.2 source
Linux builds PRPs and SGLs in pci.c (e.g. nvme_pci_setup_data_prp() and the SGL counterpart). Errors are mapped to -EIO by nvme_error_status().
Test to provoke it
EXPERT: user-space driver with a deliberately misaligned PRP2; QEMU gives deterministic results.
S-13Controller Memory Buffer misuse: Invalid Use of CMB (0x12), Command Not Supported for Queue in CMB (0x1F) ReportedNVMe command / CMB
What happens
0x12: a data pointer mixes CMB (or PMR) addresses and host-memory addresses in a way the controller does not support, or uses the CMB for something not enabled in CMBSZ. 0x1F: the command is not allowed when its SQ/CQ lives in the CMB.
How it shows up
SC 0x12 / 0x1F, DNR=1 in QEMU.
Spec basis
CMBLOC (38h), CMBSZ (3Ch) register capabilities (SQS, CQS, WDS, RDS); CMBMSC in newer revisions.
Typical causes
QEMU nvme_map_addr(): a scatter list that has started with DMA addresses then hits a CMB/PMR address (or the reverse). Peer-to-peer DMA setups with partly mapped buffers.
How to detect / prove
Compare every PRP/SGL address with the CMB BAR range from lspci -vvv and the CMBLOC offset.
In a trace
Addresses inside the device's own BAR in the DPTR. There is no MRd to host memory for those parts.
Linux v7.2 source
pci.c CMB support (nvme_map_cmb(); SQs in CMB with the use_cmb_sqes module parameter). The status itself is mapped to -EIO.
Test to provoke it
EXPERT: QEMU -device nvme,cmb_size_mb=64 plus a user-space driver mixing CMB and host buffers.
S-14Atomic Write Unit Exceeded (SCT 0 / SC 0x14) ReportedNVMe command
What happens
The write is longer than the atomic write unit, and the controller is configured to reject such writes instead of executing them non-atomically.
How it shows up
SC 0x14. Linux → -EIO. Note that Linux's newer atomic-write support (RWF_ATOMIC) checks sizes before submission, so a drive returning this to the kernel path points to a mismatch between Identify limits and behaviour.
Spec basis
Identify Controller AWUN/AWUPF; Identify Namespace NAWUN/NAWUPF/NABSN; Write Atomicity Normal feature (FID 0Ah); QEMU nvme_set_feature_write_atomicity().
Typical causes
Database or filesystem relying on atomic writes larger than the advertised unit; writes crossing an atomic boundary (NABO/NABSN).
How to detect / prove
Compare the write's SLBA/NLB with NAWUPF/NABSN from nvme id-ns -H. QEMU's nvme_atomic_write_check() shows how a controller decides whether a write is atomic.
In a trace
SQE for Write with NLB > limit → CQE 0x14, no data MRd.
Linux v7.2 source
Atomic limits come from Identify (NAWUPF/AWUPF) into queue limits in core.c:nvme_configure_atomic_write(); core.c:nvme_valid_atomic_write() refuses, on the host side, REQ_ATOMIC writes that cross an atomic boundary before they reach the drive. The status itself → -EIO.
Test to provoke it
SAFE (data-destructive only for the target LBA range): enable the Write Atomicity Normal feature on QEMU and issue an oversized write with nvme write.
S-15Operation Denied (SCT 0 / SC 0x15) ReportedNVMe command / security
What happens
The command was denied for lack of access rights, as defined by a security specification (e.g. TCG Storage), or by a locking or lockdown rule.
How it shows up
SC 0x15. A read to a locked TCG range usually returns this or Access Denied 0x286, depending on the implementation impl.
Spec basis
Generic "Operation Denied"; Security Send/Receive; related Generic 0x23 "Command Prohibited by Command and Feature Lockdown" (libnvme NVME_SC_PROHIBITED_BY_CMD_AND_FEAT).
Typical causes
Self-encrypting drive locked after power cycle (no unlock in initramfs); management commands blocked by lockdown; vendor-unique commands needing a key.
How to detect / prove
sedutil-cli --query or nvme security-recv to check locking state; repeat after unlock.
In a trace
Immediate CQE; for SEDs, there are Security Send/Receive (81h/82h) exchanges earlier.
Linux v7.2 source
core.c OPAL hook (nvme_sec_submit()); the status itself → -EIO.
Test to provoke it
CAUTION: lock a TCG Opal range on a test drive and read it.
S-16Host Identifier Inconsistent Format (0x18), Keep Alive Timer Expired (0x19), Keep Alive Timeout Invalid (0x1A) ReportedNVMe admin / NVMe-oF
What happens
0x18: the subsystem saw both 64-bit and 128-bit Host Identifiers used across controllers. 0x19: the Keep Alive Timer expired and the controller tears down the association; outstanding commands may complete with this status. 0x1A: Set Features Keep Alive Timer (FID 0Fh) with an unacceptable value.
How it shows up
On fabrics: 0x19 together with the controller disappearing; the host sees the connection reset and reconnect attempts. On PCIe keep-alive is optional and rarely enabled.
Spec basis
Host Identifier feature (FID 81h); Keep Alive Timer feature (FID 0Fh), KAS in Identify Controller.
Typical causes
0x19: host stalled (CPU soft lockup, network partition), or a target too strict about KATO. 0x18: mixed host tooling on a shared subsystem. 0x1A: KATO outside the controller's range.
How to detect / prove
On the host: dmesg keep-alive messages from core.c:nvme_keep_alive_end_io(); on the target, its log; on the network, a gap in Keep Alive capsules longer than KATO.
In a trace
Missing Keep Alive (admin opcode 18h) commands for > KATO, then the association closes.
Linux v7.2 source
core.c:nvme_keep_alive_work(), nvme_keep_alive_end_io(); pr.c handles 0x18 (NVME_SC_HOST_ID_INCONSIST) for Reservation Report by retrying without the Extended Data Structure (128-bit Host ID) format.
Test to provoke it
CAUTION: NVMe/TCP loopback target, then tc qdisc add ... netem loss 100% for longer than KATO.
S-17Command Aborted due to Preempt and Abort (SCT 0 / SC 0x1B) ReportedNVMe command / reservations
What happens
Another host ran Reservation Acquire with the Preempt and Abort action. Commands from the preempted host that were in progress on the namespace are aborted.
How it shows up
SC 0x1B on in-flight commands of the preempted host. Later commands from that host get Reservation Conflict (0x83). A Reservation Notification log page (LID 80h) and an I/O Command Set–specific AEN (Reservation Log Page Available) may follow.
Spec basis
Reservations (Register/Acquire/Release/Report); Reservation Notification log.
Typical causes
Cluster fencing (pacemaker/STONITH with persistent reservations) evicting a node.
How to detect / prove
nvme resv-report /dev/nvme0n1 before and after; cluster logs; nvme get-log -i 0x80.
In a trace
On the other host's path: Reservation Acquire (opcode 11h) with RACQA=Preempt and Abort; on this host's path: CQEs with 0x1B.
Linux v7.2 source
pr.c implements the block pr_ops; status → -EIO in the I/O path.
Test to provoke it
CAUTION: two hosts (or two controllers) on a shared namespace; register both keys, acquire on A, then preempt-and-abort from B while A runs fio.
S-18Sanitize Failed (SCT 0 / SC 0x1C) ReportedNVMe admin / sanitize
What happens
The most recent sanitize operation failed and no recovery has completed yet. Until then, the controller rejects commands that would expose possibly un-sanitized data.
How it shows up
Media-access commands complete with SC 0x1C. Sanitize Status log (LID 81h) SSTAT status = 3h "completed with failure" (libnvme NVME_SANITIZE_SSTAT_STATUS_COMPLETED_FAILED). See S-89.
Spec basis
Sanitize command (84h), Sanitize Status log, "Exit Failure Mode" sanitize action.
Typical causes
Block erase failed on some dies; power lost during sanitize with an implementation that cannot resume; crypto erase key-store failure.
How to detect / prove
nvme sanitize-log /dev/nvme0: SSTAT and SPROG; Persistent Event log Sanitize Start/Completion events (types 09h/0Ah).
In a trace
Sanitize SQE earlier; reads now return 0x1C immediately.
Linux v7.2 source
No special handling (→ -EIO). The kernel does not issue Sanitize itself.
Test to provoke it
EXPERT/destructive: power-cycle during a sanitize on a sacrificial drive. Recovery: nvme sanitize -a 1 (Exit Failure Mode) or retry sanitize.
S-19Sanitize In Progress (SCT 0 / SC 0x1D) ReportedNVMe command / sanitize
What happens
A sanitize is running. Commands that are prohibited during sanitize (I/O, most admin commands that touch media) are rejected.
How it shows up
SC 0x1D, typically DNR=0 (it will work once sanitize is done). Linux retries up to max_retries, which is far shorter than a sanitize, so the I/O ends with -EIO. Boot-time partition scans fail and the disk may look empty.
Spec basis
Sanitize; Sanitize Status log SPROG (progress /65536) and SSTAT = 2h "in progress"; sanitize persists across resets and power cycles.
Typical causes
A sanitize started by someone else (or by a previous boot, because sanitize resumes after power cycle); estimated times (ETBE/ETCE/ETO fields in LID 81h) of hours on large drives.
How to detect / prove
nvme sanitize-log /dev/nvme0 shows SSTAT=2 and SPROG increasing. Get Log Page for LID 81h is allowed during sanitize.
In a trace
Every I/O SQE gets an immediate CQE 0x1D.
Linux v7.2 source
Generic retry in core.c:nvme_decide_disposition(); the delay depends only on CRD.
Test to provoke it
DESTRUCTIVE / EXPERT: nvme sanitize /dev/nvme0 -a 2 (block erase) on a scratch drive, then dd from it.
S-20Namespace is Write Protected (SCT 0 / SC 0x20) ReportedNVMe command
What happens
The namespace is in a write-protected state (Namespace Write Protection Config feature: Write Protect, Write Protect Until Power Cycle, Permanent Write Protect), so writes and other modifying commands are refused.
How it shows up
SC 0x20 on writes. Linux → -EIO for that write. Linux also reads the namespace write-protect state at scan time and marks the disk read-only if Identify NS NSATTR has the write-protected bit set.
Spec basis
Namespace Write Protection Config feature (FID 84h); NSATTR in Identify Namespace.
Typical causes
Admin set write protection (forensics, golden images); permanent protection after end-of-life policies; feature set without the host noticing (no AEN for it).
How to detect / prove
nvme get-feature /dev/nvme0 -n 1 -f 0x84; nvme id-ns -H NSATTR; blockdev --getro.
In a trace
Writes get immediate CQEs. Reads succeed.
Linux v7.2 source
core.c namespace update path sets the disk read-only from NSATTR (NVME_NS_ATTR_RO). The status itself → -EIO.
Test to provoke it
CAUTION: nvme set-feature /dev/nvme0 -n 1 -f 0x84 -v 1 (Write Protect, reversible), write, then set it back to 0. Never use the permanent value on a drive you want to keep.
S-21Command Interrupted (SCT 0 / SC 0x21) ReportedNVMe command
What happens
The controller stopped processing the command (internal event, ANA-related change, resource rebalance) and asks the host to retry, often with a Command Retry Delay.
How it shows up
SC 0x21 with DNR=0 by definition. If the retries run out, Linux maps it to BLK_STS_TARGET → -EREMOTEIO ("critical target error").
Spec basis
Generic "Command Interrupted": "the host should retry the command" (libnvme). CRD field + CRDT1–3 + ACRE.
Typical causes
Firmware busy with a background operation; controller-level events in dual-port arrays; QEMU returns it as an internal status for interrupted zone/atomic operations (defined as NVME_COMMAND_INTERRUPTED).
How to detect / prove
Trace with nvme:nvme_complete_rq (status 0x21 with retries > 0) and command_retries_count. Check CRD values against nvme id-ctrl crdt1..3.
In a trace
CQE 0x21 → host waits the CRD time → same command re-submitted.
Linux v7.2 source
core.c:nvme_error_status() → BLK_STS_TARGET; nvme_retry_req() CRD delay; nvme_configure_host_options() ACRE.
Test to provoke it
SAFE: fault-inject status 0x21 with dont_retry=0 (§3.5) to see the retry and errno behaviour.
S-22Transient Transport Error (SCT 0 / SC 0x22) ReportedNVMe-oF transport
What happens
A short-lived transport problem made the command fail. Retrying on the same controller should work. libnvme quotes the spec: after four or more failures with this status, treat it as a persistent transport error.
How it shows up
SC 0x22, DNR=0. Linux retries (up to 5) and then gives -EIO. It is not in SCT 3, so Linux multipath does not fail over on it directly.
Spec basis
Generic "Transient Transport Error"; transport bindings (TCP, RDMA, FC).
Typical causes
Packet loss or digest errors (NVMe/TCP HDGST/DDGST), RDMA retry exhaustion, FC link resets.
How to detect / prove
Network counters (ethtool -S, RDMA counters), NVMe/TCP digest error messages in dmesg; correlation with retries in the tracepoint.
In a trace
On the network capture: retransmissions or digest mismatches just before the response capsule.
Linux v7.2 source
Default retry/COMPLETE path in core.c; transport drivers in tcp.c/rdma.c.
Test to provoke it
CAUTION: NVMe/TCP with tc netem corrupt plus data digest enabled.
S-23Admin Command Media Not Ready (SCT 0 / SC 0x24) ReportedNVMe admin
What happens
The admin command needs the media, but the media is not ready yet. This can happen when the controller became ready early (CSTS.RDY) because the host set CC.CRIME (Controller Ready Independent of Media Enable).
How it shows up
SC 0x24 on admin commands such as Identify Namespace, Get Log Page of media-backed logs, Format.
Spec basis
CAP.CRMS (CRWMS/CRIMS), CC.CRIME, CRTO register (Controller Ready Timeouts).
Typical causes
Host using CRIME mode and sending media-dependent commands before media ready; large drives whose internal metadata load takes seconds.
How to detect / prove
Check CC.CRIME in a register dump or trace; compare time since CC.EN with CRTO.CRIMT.
In a trace
CC write with CRIME=1 → CSTS.RDY=1 quickly → admin command → CQE 0x24.
Linux v7.2 source
core.c:nvme_enable_ctrl() clears CRIME on purpose: "Setting CRIME results in CSTS.RDY before the media is ready. This makes it possible for media related commands to return the error NVME_SC_ADMIN_COMMAND_MEDIA_NOT_READY. Until the driver is restructured to handle retries, disable CC.CRIME." So Linux should never see this code.
Test to provoke it
EXPERT: user-space driver enabling with CRIME=1 on a CAP.CRMS-capable drive and sending Identify NS at once.
S-24I/O Command Set errors: Invalid I/O Command Set (0x2C) and the 0x29–0x2B group ReportedNVMe admin
What happens
A command references a Command Set Identifier (CSI) that the controller does not support, has not enabled, or cannot combine with the others.
How it shows up
Linux defines NVME_SC_INVALID_IO_CMD_SET = 0x2C in the Generic range. QEMU (NVME_INVALID_IOCS = 0x012c) and libnvme (NVME_SC_INVALID_IOCS = 0x2c under "Command Set Specific – Namespace Types") place it in SCT 1, along with 0x29 I/O Command Set Not Supported, 0x2A Not Enabled, 0x2B Combination Rejected. uncertain Verify the SCT in the spec. A Linux string lookup of a real SCT 1 / 0x2C status prints "Unknown" because 0x12C has no entry.
Spec basis
I/O Command Set Profile feature (FID 19h), Identify I/O Command Set data structure (CNS 1Ch), CC.CSS.
Typical causes
QEMU: nvme_identify_ns() returns INVALID_IOCS for a namespace whose CSI is not enabled; nvme_set_feature() returns IOCS_NOT_SUPPORTED / COMBINATION_REJECTED. Real: tools asking for ZNS/KV identify data on an NVM-only controller.
How to detect / prove
nvme id-iocs /dev/nvme0; nvme get-feature -f 0x19.
In a trace
Identify with CNS 05h/06h and a CSI value → immediate CQE.
Linux v7.2 source
Linux sets CC.CSS to NVME_CC_CSS_CSI when CAP.CSS allows it (core.c:nvme_enable_ctrl()) and ignores namespaces with unsupported CSI during scan.
Test to provoke it
SAFE: nvme admin-passthru /dev/nvme0 --opcode=0x06 --cdw10=0x05 --cdw11=0x05000000 -r -l 4096 --namespace-id=1 (Identify CNS 05h with an unsupported CSI value).
S-25LBA Out of Range (SCT 0 / SC 0x80) ReportedNVMe command
What happens
SLBA + NLB goes past the namespace size (NSZE), or the arithmetic overflows. Nothing is transferred.
How it shows up
SC 0x80, DNR=1 in QEMU. Linux maps it to BLK_STS_TARGET → -EREMOTEIO ("critical target error"), not EIO, which surprises people searching logs.
Spec basis
Generic (I/O command set) "LBA Out of Range"; Identify Namespace NSZE.
Typical causes
Namespace shrunk/recreated while the host kept the old size (no rescan); partition table from a larger drive copied to a smaller one; block-layer sector-to-LBA conversion bugs with mixed 512/4096 formats. QEMU: nvme_check_bounds(): if (UINT64_MAX - slba < nlb || slba + nlb > nsze).
How to detect / prove
dmesg error line shows "@ LBA x, n blocks". Compare with nvme id-ns NSZE and blockdev --getsize64. A mismatch means a stale capacity.
In a trace
SQE with SLBA near the end of the namespace → immediate CQE.
Linux v7.2 source
core.c:nvme_error_status() (BLK_STS_TARGET); capacity updates in nvme_update_ns_info() after rescans.
Test to provoke it
SAFE: nvme read /dev/nvme0n1 -s <NSZE> -c 0 -z 4096 (read the block just past the end).
S-26Capacity Exceeded (SCT 0 / SC 0x81) ReportedNVMe command
What happens
Running the command would make the namespace use more than its capacity (NCAP). This only matters for thin-provisioned namespaces, where NCAP < NSZE.
How it shows up
SC 0x81. Linux maps it to BLK_STS_NOSPC → -ENOSPC: the filesystem gets "no space" even though df shows free space.
Spec basis
Identify Namespace NSZE, NCAP, NUSE; thin provisioning (NSFEAT bit 0).
Typical causes
Over-subscribed thin namespace; host not sending Deallocate (discard), so NUSE never shrinks; deallocations the drive accepts but does not apply (see silent-failure part).
How to detect / prove
Watch NUSE vs NCAP with nvme id-ns over time; compare with filesystem usage. If NUSE stays high after fstrim, deallocation is not taking effect.
In a trace
Write SQE → CQE 0x81, possibly after data transfer.
Linux v7.2 source
core.c:nvme_error_status() → BLK_STS_NOSPC.
Test to provoke it
CAUTION: thin namespace (QEMU or array) filled past NCAP with fio.
S-27Namespace Not Ready (SCT 0 / SC 0x82) ReportedNVMe command
What happens
The namespace cannot be accessed right now, for a reason other than an ANA state (libnvme wording). Examples: still coming up after reset, a background operation, or a namespace that is being created.
How it shows up
SC 0x82. DNR=0 means "try again later", DNR=1 means "will not become ready". Linux → BLK_STS_TARGET → -EREMOTEIO once retries are used up.
Spec basis
Generic "Namespace Not Ready"; Identify Namespace / I/O Command Set Independent NS data "Namespace Ready" indications in newer revisions (verify in spec).
Typical causes
Command sent right after reset or namespace attach on a drive that rebuilds mapping tables; a drive in a vendor "failure" mode returning 0x82 to everything.
How to detect / prove
Time since CSTS.RDY; check whether it clears by itself (poll with nvme read each second). Persistent 0x82 with DNR=1 is a dead namespace.
In a trace
Immediate CQE 0x82 to I/O shortly after controller enable.
Linux v7.2 source
core.c:nvme_error_status() → BLK_STS_TARGET.
Test to provoke it
SAFE via fault injection (status 0x082).
S-28Reservation Conflict (SCT 0 / SC 0x83) ReportedNVMe command / reservations
What happens
Another host holds a reservation on the namespace that does not allow this host's access (for example, Write Exclusive held by another host, and this host writes).
How it shows up
SC 0x83, normally DNR=1. Linux maps it to BLK_STS_RESV_CONFLICT → -EBADE; the persistent-reservation API returns PR_STS_RESERVATION_CONFLICT.
Spec basis
Reservation types (Write Exclusive, Exclusive Access, Registrants Only, All Registrants); Reservation Report.
Typical causes
Cluster software fenced this node; stale reservation left by a crashed node; a host that has not registered its key after reboot.
How to detect / prove
nvme resv-report /dev/nvme0n1 -c 1 shows holder, type and registrants; compare with this host's Host ID (nvme get-feature -f 0x81).
In a trace
I/O SQE → immediate CQE 0x83.
Linux v7.2 source
core.c:nvme_error_status(); pr.c:nvme_status_to_pr_err().
Test to provoke it
CAUTION: nvme resv-register + resv-acquire -t 1 (Write Exclusive) from controller A, write from controller B.
S-29Format In Progress (SCT 0 / SC 0x84) ReportedNVMe command
What happens
A Format NVM is running on the namespace; I/O to it is rejected until it completes.
How it shows up
SC 0x84 on I/O, DNR typically 0. Linux retries a few times, then -EIO.
Spec basis
Format NVM (80h); Identify Controller FNA (Format NVM Attributes, e.g. whether a format applies to all namespaces). Some drives report progress in a vendor log.
Typical causes
Format issued by another tool or host on a shared namespace, or on a "format all namespaces" drive (FNA bit) where formatting one namespace blocks the others. QEMU: nvme_do_format() sets ns->status = NVME_FORMAT_IN_PROGRESS and I/O to that namespace returns it until done.
How to detect / prove
Look for an earlier Format SQE (opcode 80h) in the trace or in the admin nvme_setup_cmd tracepoint; Persistent Event log Format NVM Start/Completion events (07h/08h).
In a trace
Format SQE without its CQE yet; I/O CQEs with 0x84.
Linux v7.2 source
Default handling; the kernel itself never formats.
Test to provoke it
DESTRUCTIVE / CAUTION: on a scratch namespace in QEMU, nvme format /dev/nvme0n1 -s 1 (user-data erase; slower) and read from another shell.
💡 Senior insight

When a new drive fails qualification with "-EOPNOTSUPP" or "-EREMOTEIO" in an application, translate back with the table in §3.4.2 before blaming the application. EREMOTEIO always means LBA Out of Range, Namespace Not Ready or Command Interrupted. Those three have very different root causes, and the dmesg nvme_log_error line (if it printed) tells you which one. If it did not print, the request was RQF_QUIET or the error came from somewhere other than the NVMe driver.
