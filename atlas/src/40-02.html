IV.2 Deallocate, Write Zeroes and allocation accounting: the error cards

This chapter turns the worked case into cards you can look up. Each card says what the failure is, what is (and is not) reported, the spec basis, how to prove it, and how to provoke it. "Silent" means the command completes with Success and nothing appears in dmesg, nvme error-log or the SMART log. The cards share one rule: check the drive's promises first (DLFEAT, NSFEAT, ONCS, granularity), because they decide whether the observed behaviour is a spec violation or only a quality problem.

D-01Deallocate accepted but not performed SilentNVMe command
In a PEX trace
Partly visible The DSM SQE (OPC 09h, CDW11=4), the range-list fetch with SLBA/NLB, the Success CQE and MSI-X are all visible and look perfect. The failure itself is not. Partial clue: if the capture also holds the Identify Namespace data (DLFEAT RB=001b/010b) and a later Read of the range, a non-zero data payload in that Read proves it. Detail: Identical to a good deallocate: doorbell MWr, MRd of the 64-byte SQE (OPC 09h, CDW11 = 4), MRd of 16×(NR+1) bytes of ranges, MWr of a CQE with status 0, MSI-X. The DSM exchange itself never shows the failure; only the absence of a later effect does.
What happens
The host sends DSM with AD=1 for a range. The controller fetches the range list, completes with status 0, and leaves every LBA in the range mapped. Old data, space accounting and garbage-collection load stay as if nothing happened.
How it shows up
Nothing is reported: CQE status 0, no dmesg line, no Error Information log entry, no AER. blkdiscard/fstrim exit 0. Over time sustained write performance and endurance are worse than expected, because the drive keeps moving data the host no longer needs.
Spec basis
NVM Command Set: Dataset Management, Attribute – Deallocate. Identify Namespace DLFEAT (read behaviour bits 2:0), NSFEAT bit 2 (DULBE), NUSE; Feature 05h DULBE bit. Whether doing nothing is a violation depends on these promises. AD is widely described as advisory verify in spec.
Typical causes
Firmware treats AD as a hint and drops it under load or when the queue of unmap work is full. Ranges smaller than the internal mapping unit are ignored. Firmware feature disabled in a SKU. A bug where a multi-range DSM processes only range 0.
How to detect / prove

1) Confirm the DSM and its ranges on the wire or with blktrace (rule out D-04). 2) If DLFEAT RB = 001b/010b: read back sample LBAs; old data = proven. 3) If NSFEAT.DULBE: enable Feature 05h bit 16 and read; Success instead of status 287h = not deallocated (control: a never-written LBA must give 287h). 4) NUSE before/after (if the drive tracks it). 5) Performance A/B against a run without deallocate.

Linux v7.2 source
drivers/nvme/host/core.c:nvme_setup_discard() builds the command; nvme_update_disk_info() sets discard limits; nvme_cleanup_cmd() frees the range buffer. No code path verifies the effect.
Test to provoke it
Lab IV.1 CAUTION: write a pattern, deallocate an aligned range, read back per DLFEAT, DULBE probe, NUSE delta. Vary the range size (1 granule, 1 GiB, whole namespace), number of ranges (1, 2, 256), and queue depth of concurrent writes. In QEMU, a backend that ignores discards reproduces it on purpose.
D-02Deallocate partially performed: ranges or edges silently skipped SilentNVMe command
In a PEX trace
Partly visible The range descriptors and the length of the range-list MRd are visible, so a device that fetched fewer than 16×(NR+1) bytes is caught. Which ranges took effect is not visible, except through later Read payloads at range edges. Detail: Decode every range descriptor in the range-list CplD. Confirm that NR+1 descriptors were fetched (the MRd length). If the device fetched fewer bytes than 16×(NR+1), it cannot have processed the later ranges. That is the one case where the trace does show a partial deallocate.
What happens
Only part of the request takes effect: the first range of a multi-range DSM, only fully-aligned granules (the unaligned head and tail are kept), or every range except the ones larger than an internal limit. The CQE is still Success.
How it shows up
Silent. Read-back gives zeroes in the middle of the range and old data near the edges, or in whole sub-ranges. NUSE drops by less than NLB.
Spec basis
NPDG/NPDA and NPDGL/NPDAL are preferred granularity and alignment. Unaligned deallocates are allowed, and how much is deallocated is implementation-dependent unless DLFEAT promises a read value for each deallocated LBA. DMRL/DMRSL are limits the host should honour. What a controller must do when they are exceeded: verify in spec.
Typical causes
Internal mapping unit larger than the LBA size (for example 4 KiB map on 512-byte LBAs). Range-count or range-size limits handled with a silent "skip". The QEMU model does exactly this: hw/nvme/ctrl.c:nvme_dsm_cb() skips a range with nlb > dmrsl or out-of-bounds LBAs, emits only a trace event, and completes Success.
How to detect / prove
Read back the first and last LBA of every range, plus one LBA either side of each. With DLFEAT RB = 001b, any non-zero LBA inside a range is a violation, whatever the alignment. Check NUSE delta against Σ NLB. For multi-range, use distinct patterns per range so you can tell which range was skipped.
Linux v7.2 source
core.c:nvme_update_disk_info() (discard_granularity from NPDG/NPDA/NPDGL/NPDAL; max_discard_segments from DMRL or 256; max_hw_discard_sectors from DMRSL); core.c:nvme_init_non_mdts_limits() reads DMRL/DMRSL.
Test to provoke it
CAUTION With nvme dsm passthrough (bypasses the block layer's rounding): issue ranges that start or end off the NPDA boundary, 256-range DSMs, and a range just above DMRSL. Check every edge LBA. Run on QEMU first to see the skip behaviour in its trace events.
D-03Read after deallocate returns old data (DLFEAT promise broken) SilentData integrity
In a PEX trace
Visible If the capture includes the Identify Namespace payload (DLFEAT), the DSM, and the later Read, the Read data payload carrying the old pattern instead of the promised 00h/FFh is direct proof on the wire. Detail: The later Read's data MWr TLPs carry the old pattern. This is one of the few silent failures where the proof itself is visible on the wire, in the read data payload.
What happens
The namespace reports DLFEAT read behaviour 001b (zeroes) or 010b (FFh). After a successful deallocate, a Read returns the previous contents of the block. Either the FTL did not unmap it, or it unmapped and a cache (read buffer, write cache, read-ahead) still returns the old page.
How it shows up
Read completes Success with stale data. With PI enabled, the stale PI may still be valid for the old data, so even PI checks pass.
Spec basis
Identify Namespace DLFEAT bits 2:0. With 001b/010b the read result is defined. Returning old data is a conformance failure. Linux relies on this promise: nvme_update_ns_info_block() enables DEAC only when RB = 001b and DLFEAT bit 3 is set.
Typical causes
Deallocate not performed (D-01). Unmap applied to the map but not invalidated in an internal read cache. A race between a write still in the volatile cache and the deallocate (ordering bug). Unmap lost across a power cycle (the unmap journal was not persisted, so after power-on the old mapping comes back). The last case is the nastiest: data deleted for security reasons reappears.
How to detect / prove
Read-back right after the CQE, again after idle, and again after a clean power cycle (nvme subsystem-reset or a real power cycle). Any non-promised value at any point is proof. Collect: Identify Namespace (DLFEAT), trace of the DSM, and a hex dump of the read.
Linux v7.2 source
core.c:nvme_update_ns_info_block() (DEAC condition), core.c:nvme_setup_write_zeroes(); quirk NVME_QUIRK_DEALLOCATE_ZEROES in nvme.h and pci.c:nvme_id_table.
Test to provoke it
CAUTION Write pattern → deallocate → read immediately → idle 10 min → read → power cycle → read. Also overlap: issue a Write and a DSM to the same LBAs back to back at high queue depth, then read. The result must be either the new data or the promised value, consistent with the completion order.
D-04Discard never reaches the device (host-side silent drop) SilentHost / block layer
In a PEX trace
Visible Visible as an absence: no SQE with OPC 09h (or 08h) in a capture window long enough to cover the journal commit or fstrim. That proves the drive was never asked. Detail: Nothing: no OPC 09h SQE in the capture window. Note that discards may come long after the truncate (journal commit, periodic fstrim), so capture long enough.
What happens
The user believes the space was trimmed, but no DSM was ever sent. Common reasons: filesystem not mounted with -o discard and no fstrim run; dm-crypt without discard passthrough; LVM/MD layers or a virtual disk that do not forward discards; discard_max_bytes = 0 because ONCS.DSM is clear or the queue limit was changed; the discard was smaller than discard_granularity and rounded away.
How it shows up
Mostly silent. blkdiscard on a device without discard support does fail (EOPNOTSUPP), but filesystem truncate and many stacked layers just drop the request. The drive is blamed for keeping data it was never told about.
Spec basis
Not a device issue. Identify Controller ONCS bit 2 decides whether Linux enables discard at all.
Typical causes
Mount options, dm/LVM configuration, virtualization layers, misread fstrim output (its byte count is what it asked for), discards rounded away by granularity.
How to detect / prove
lsblk --discard on every layer of the stack (non-zero DISC-GRAN/DISC-MAX needed on each). blktrace -d /dev/nvme0n1 while truncating or trimming: look for discard requests (RWBS with D). Enable the nvme:nvme_setup_cmd tracepoint and look for DSM with attributes=4. Analyzer: no SQE with OPC 09h means nothing was sent.
Linux v7.2 source
core.c:nvme_update_disk_info(): max_hw_discard_sectors = 0 when ONCS.DSM is clear and DMRSL is 0. core.c:nvme_setup_cmd() is the single point where REQ_OP_DISCARD becomes a DSM, so a probe there catches every discard that leaves the block layer.
Test to provoke it
SAFE on a scratch filesystem: mount without discard, write and delete a file, trace for 2 minutes and observe no DSM. Remount with discard and repeat. Repeat on dm-crypt with and without discard passthrough.
D-05Write Zeroes completes but blocks are not zero SilentNVMe command
In a PEX trace
Visible The Write Zeroes SQE (OPC 08h, DEAC in CDW12 bit 25) and Success CQE, followed by a Read whose data payload is non-zero, are both on the wire, which proves the failure. Detail: SQE OPC 08h with SLBA/NLB in CDW10-12 and DEAC in CDW12 bit 25. No data transfer for the command itself. The later Read data TLPs show the non-zero content.
What happens
Write Zeroes (08h), with or without DEAC, returns Success, but later reads return old data, garbage, or zeroes for only part of the range. Filesystems and databases that rely on zero-out for allocation (for example, unwritten extents converted to written, or BLKZEROOUT used to clear metadata) then see stale structures.
How it shows up
Silent at the NVMe level. Upper layers may later report corruption (filesystem check errors, database page checksum failures) far away from the cause.
Spec basis
NVM Command Set Write Zeroes: after completion the LBAs read as zeroes (and PI per PRACT/PRINFO). DEAC allows the controller to deallocate instead, but the zero read result is still required. Linux's comment in nvme_update_ns_info_block() says DEAC "must be a no-op if reads from deallocated data do not return zeroes".
Typical causes
Firmware implementing DEAC as "deallocate" on a drive whose deallocated read value is not zero. Size-limit handling (WZSL, or WZDSL when ONCS bit 11 applies) silently truncating long commands. Bugs the Linux quirk NVME_QUIRK_DISABLE_WRITE_ZEROES ("Broken Write Zeroes") exists for: in v7.2 it is set for many device IDs in pci.c:nvme_id_table, including the Intel 600P/P3100 and the QEMU 5845h controller.
How to detect / prove
Write a non-zero pattern, Write Zeroes the range (both DEAC=0 and DEAC=1 via nvme write-zeroes … --deac), read every block back, compare with zeroes. Test sizes around WZSL/WZDSL and MDTS. Any non-zero byte is proof, independent of DLFEAT.
Linux v7.2 source
core.c:nvme_setup_write_zeroes(), core.c:nvme_init_non_mdts_limits() (WZSL, NVME_QUIRK_DISABLE_WRITE_ZEROES), core.c:nvme_update_disk_info() (max_write_zeroes_sectors, NVME_QUIRK_DEALLOCATE_ZEROES).
Test to provoke it
CAUTION On a spare namespace: pattern-fill 1 GiB; nvme write-zeroes in sizes 1 block, WZSL−1, WZSL, WZSL+1 (expect an error, not silent truncation), with and without --deac. Read back and compare. Also run blkdiscard -z and confirm with blktrace which command Linux actually used.
D-06Deallocate reaches too far: live data outside the range lost SilentData integrity
In a PEX trace
Partly visible The range descriptors in the range-list CplD show whether the host asked for the right LBAs. Lost guard blocks show up only if the capture also holds the guard writes and a later read of the guards. Detail: Range descriptor values in the CplD. If they are right and guards are still lost, the device is at fault. If they are already wrong, the host is.
What happens
Blocks outside the requested range read back as zeroes/FFh or fail with 287h. The drive rounded the range out to its internal unit, mis-parsed the descriptor (for example, read NLB as 0's based, which adds one block), or the host sent the wrong range.
How it shows up
Silent until the data is read. Filesystems see corrupted files or metadata long after the trim. Host-side cases have happened in practice: a 2019 dm-devel thread reports fstrim discarding too many or the wrong blocks on Linux 5.1 with dm-crypt/LVM, which led to data loss.
Spec basis
Range descriptor: Length in logical blocks (a 1's based count, unlike CDW12 NLB in Read/Write, which is 0's based). Deallocating LBAs not listed in any range is never permitted.
Typical causes
Firmware treating Length as 0's based; rounding unaligned ranges outward instead of inward; host stacking layers translating offsets wrongly; a DSM processed against the wrong namespace (NSID bug).
How to detect / prove
Guard pattern: write distinct "guard" blocks right before and after each range, deallocate, and verify the guards with a checksumming read (fio --verify=crc32c over the guard areas). Decode the range list in the trace to tell host error from device error.
Linux v7.2 source
core.c:nvme_setup_discard(): nlb = blk_rq_sectors(req) >> (lba_shift - 9) (single segment) or bi_size >> lba_shift per bio, written as a 1's based count.
Test to provoke it
CAUTION For N in {1, 7, 8, 9, 4095, 4096, 4097} blocks: guard–range–guard layout, deallocate the range via nvme dsm, verify guards. Repeat with 2- and 256-range DSMs and with ranges in a second namespace to catch NSID mix-ups.
D-07Allocation accounting wrong: NUSE frozen, DULBE not reported SilentIdentify / features
In a PEX trace
Visible The Identify Namespace data payload (NUSE at bytes 16–23) before and after, and the CQE status of a DULBE-enabled Read (287h expected, 0 observed) are on the wire, provided the test commands are captured. Detail: Identify Namespace data (4 KiB CplD/MWr to the host) shows NUSE at bytes 16–23. Compare captures before and after. The DULBE read's CQE carries SCT 2h / SC 87h when it works.
What happens
The namespace advertises thin provisioning (NSFEAT bit 0) or DULBE (NSFEAT bit 2), but NUSE never changes after writes or deallocates, or DULBE is enabled and reads of never-written/deallocated blocks still return Success. Management software that relies on NUSE for capacity planning or thin-provisioning alerts gets wrong numbers.
How it shows up
No error. NUSE stays equal to NCAP (or at its value from the factory), and Get Features 05h shows DULBE=1 while reads of unwritten LBAs succeed.
Spec basis
Identify Namespace NUSE ("current number of logical blocks allocated", ≤ NCAP), NSFEAT THIN/DULBE, Feature 05h DULBE bit 16. A drive without thin provisioning may legitimately report NUSE = NCAP. The QEMU model does so on purpose (hw/nvme/ns.c: "no thin provisioning").
Typical causes
NUSE computed once at format time; DULBE accepted by Set Features but not wired to the read path; DULBE checked for never-written blocks but not for deallocated ones (or the reverse).
How to detect / prove
After a Format (NUSE should drop to about 0 on a tracking drive), write N blocks (NUSE +N), deallocate them (NUSE −N). For DULBE: read a never-written LBA (expect 287h), write it (expect Success), deallocate it (expect 287h). The QEMU controller's nvme_check_dulbe() is a reference: it returns NVME_DULB when the block-status query says the range holds no data.
Linux v7.2 source
Linux does not use NUSE for block I/O. core.c:nvme_error_status() maps NVME_SC_UNWRITTEN_BLOCK (287h) to BLK_STS_MEDIUM; constants.c names it "Deallocated or Unwritten Logical Block".
Test to provoke it
CAUTION Format the test namespace, then run the NUSE/DULBE state table above: never-written → written → deallocated → written again, at both 1-block and 1 GiB scale. Disable DULBE afterwards.
🐞 Reading the cards together

D-01, D-02 and D-03 are the same mechanism seen at different strengths: nothing, part, or "something done but the read path not updated". D-04 is the false positive to rule out first. D-06 is the dangerous opposite of D-01: too much deallocated, which destroys data instead of wasting space. When a customer reports "trim doesn't work", check D-04 first, then D-01/D-02. When a customer reports "files corrupted after trim", check D-06 first.

Quiz

  1. A drive has DLFEAT = 00h and returns old data after a deallocate. Which card applies, and is it a spec violation?

    Answer

    Possibly D-01, but with RB = 000b old data is allowed, so the read-back is not proof and not a violation. Use DULBE (if NSFEAT bit 2) or NUSE, or a performance A/B, to decide.

  2. What is the one partial-deallocate case that a trace alone can prove?

    Answer

    The device fetched fewer than 16×(NR+1) bytes of range list, so it never saw the later ranges.

  3. Why is D-05 always provable by read-back but D-01 is not?

    Answer

    Write Zeroes defines the read result (zeroes) for every drive. DSM deallocate defines it only when DLFEAT says so.
