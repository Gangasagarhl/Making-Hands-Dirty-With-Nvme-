6 Media and Data Integrity (SCT 2) and Path Related (SCT 3)

SCT 2 codes are the ones operators fear. They mean the device could not store or return data correctly, or that a data-integrity check (Protection Information, Compare) failed. SCT 3 codes describe the route to the namespace, not the data. They exist so multipath hosts can pick another controller. Linux treats them very differently: most SCT 2 codes become -ENODATA ("critical medium error") or -EILSEQ, while on a multipath namespace every SCT 3 code triggers nvme_failover_req() and the application never sees it.

🌍 Analogy

An SCT 2 error is a library telling you "the book on that shelf is damaged". An SCT 3 error is "this branch can't reach that shelf right now, try the other branch". Retrying an SCT 2 read at the same library sometimes works, because the librarian tries harder. Retrying an SCT 3 error at the same branch rarely does.

Where the analogy breaks: a write fault is not like a damaged book. The library failed to shelve your book, and you may not know which copy, old or new, is now on the shelf.

6.1 Media and Data Integrity errors (SCT 2)

S-59Write Fault (SCT 2 / SC 0x80) ReportedNVMe command / media
In a PEX trace
Partly visible The status is in DW3 of the 16-byte CQE that the device writes with a device→host MWr to the CQ base address + head×16; the analyzer's NVMe decoder pairs it with the SQE by SQID/CID. The CQE and the full data transfer are visible; whether anything reached the media is not. Use read-back and SMART media_errors. Pattern: Write SQE → device MRd of all data (it was transferred) → after unusually long latency, CQE with SCT 2/SC 0x80.
What happens
The controller could not commit the write data to the media. The data was transferred from the host, but programming failed and the firmware could not place it elsewhere.
How it shows up
SCT 2 / SC 0x80 → Linux BLK_STS_MEDIUM → -ENODATA, dmesg "Write Fault" and "critical medium error ... op 0x1:(WRITE)". SMART "Media and Data Integrity Errors" increments. An Error Information log entry gives the LBA. Repeated faults usually come with Available Spare dropping and possibly critical warning bit 2 or 3 (S-74, S-75).
Spec basis
Media and Data Integrity Errors "Write Fault"; SMART/Health log Media and Data Integrity Errors counter; Error Information log LBA field.
Typical causes
Program failure with no spare blocks left; power-loss-protection capacitor failure making the drive refuse writes; drive entering read-only end-of-life mode in a vendor-specific way. QEMU: nvme_rw_complete_cb() maps any backend write error (Write, Write Zeroes, Zone Append) to NVME_WRITE_FAULT; nvme_flush_ns_cb() and nvme_copy_out_completed_cb() also return it.
How to detect / prove
nvme smart-log (media_errors, avail_spare, critical_warning); nvme error-log (LBA, NSID, status 0x280 in libnvme form is SCT 2/SC 0x80); read back the LBA. The old data, the new data or garbage can be returned. Record which.
Linux v7.2 source
core.c:nvme_error_status() → BLK_STS_MEDIUM; filesystems usually go read-only on a failed metadata write.
Test to provoke it
SAFE in QEMU: attach the namespace through a blkdebug drive with an injected write error (event write_aio, errno 5) to get a real 0x280 CQE on the emulated wire. On hardware only vendor error injection works.
S-60Unrecovered Read Error (SCT 2 / SC 0x81) ReportedNVMe command / media
In a PEX trace
Partly visible The status is in DW3 of the 16-byte CQE that the device writes with a device→host MWr to the CQ base address + head×16; the analyzer's NVMe decoder pairs it with the SQE by SQID/CID. The CQE and the missing data MWrs are visible; the media cause is not (use the Error log LBA and SMART). Pattern: Read SQE → long latency (milliseconds instead of ~100 µs, from internal retries) → no data MWr, or partial → CQE SCT 2/0x81. With TLER set, the latency is capped.
What happens
The data could not be recovered from the media even after the controller's full error correction (ECC, read retries, soft decoding, RAID-like die parity). The data at those LBAs is lost unless the host has another copy.
How it shows up
SCT 2 / SC 0x81 on Read, Verify, Compare or Copy. Linux → BLK_STS_MEDIUM → -ENODATA. SMART media_errors increases. The Error Information log has the first failing LBA. Since the controller has already done its internal retries, DNR=1 is common. If DNR=0, Linux retries up to 5 times.
Spec basis
"Unrecovered Read Error"; Error Recovery feature (FID 05h) TLER (Time Limited Error Recovery) limits how long the drive tries before reporting; Write Uncorrectable (04h) marks LBAs to return this error on purpose.
Typical causes
Retention loss (data at rest too long, especially on hot drives), read disturb, worn blocks, firmware mapping bugs that point to the wrong physical page. Field data: Schroeder et al. (FAST '16) found that roughly 20–63% of drives in Google's fleet saw at least one uncorrectable error over four years, and that raw bit error rate was a poor predictor. QEMU: nvme_rw_complete_cb(), nvme_verify_cb(), nvme_compare_*_cb() map backend read errors to NVME_UNRECOVERED_READ.
How to detect / prove
Read the LBA range with nvme read and compare with nvme error-log. Use nvme verify (if ONCS supports it) to scan without moving data. Rewrite the LBA (that usually remaps it), then re-read to confirm.
Linux v7.2 source
core.c:nvme_error_status(); nvme_log_error() prints "@ LBA x, n blocks" for the whole request (not the exact bad LBA).
Test to provoke it
CAUTION (destroys data in the range): nvme write-uncor /dev/nvme0n1 -s 0x1000 -c 7, then nvme read ... -s 0x1000 → 0x281. Then nvme write-zeroes or a normal write clears it. In QEMU, use blkdebug read_aio errors.
S-61End-to-end PI check errors: Guard (0x82), Application Tag (0x83), Reference Tag (0x84), Storage Tag (0x88) ReportedNVMe command / PI
In a PEX trace
Visible The status is in DW3 of the 16-byte CQE that the device writes with a device→host MWr to the CQ base address + head×16; the analyzer's NVMe decoder pairs it with the SQE by SQID/CID. If the metadata crosses the link (separate MPTR buffer or extended LBA), the PI tuple is in the payload and the guard can be recomputed offline from the trace. Pattern: Read with PRINFO bits in CDW12 → data and metadata MWr (on read checks the data is often transferred first) → CQE 0x82–0x84.
What happens
On a namespace formatted with Protection Information, a check enabled by PRCHK failed. Guard: CRC of the data does not match the guard field, so the data or metadata was corrupted. App Tag: the tag differs from the expected value (under the mask). Ref Tag: the block is not the LBA the host expected, for example a misdirected write or read. Storage Tag (0x88, libnvme/QEMU only; Linux nvme.h has no constant): the storage tag check failed.
How it shows up
0x282/0x283/0x284 → Linux BLK_STS_PROTECTION → -EILSEQ ("protection error"). 0x288 → "Unknown" → -EIO. The checks can run on writes (PRACT=0, the controller verifies host-supplied PI) or on reads.
Spec basis
End-to-end Data Protection (Type 1/2/3; 16-bit guard CRC-16 T10-DIF, and 32/64-bit guard formats in newer revisions); PRINFO = PRACT + PRCHK[2:0]; ELBAT/ELBATM/ILBRT fields.
Typical causes
Guard: DMA corruption, controller SRAM/DRAM bit flips, wrong PI generation by the host (bad CRC table, wrong byte order). Ref: host reused a buffer from a different LBA, firmware L2P mapping bug (misdirected write), Type 1 reference tag not incremented across blocks. App: application-tag misuse. QEMU dif.c:nvme_dif_prchk_crc16() shows the exact algorithm and the escape values. For Type 1/2 an app tag of FFFFh disables checking. For Type 3 the app tag FFFFh and ref tag FFFFFFFFh are needed.
How to detect / prove
Read the block with PRCHK cleared plus its metadata (nvme read ... -y 8 -M meta.bin), recompute CRC-16 T10-DIF over the data and compare the stored guard; the stored ref tag shows which LBA's data you got. This is one of the few ways to prove a misdirected write.
Linux v7.2 source
core.c:nvme_error_status() → BLK_STS_PROTECTION; PRINFO and reftag setup in core.c:nvme_setup_rw(); module parameter disable_pi_offsets in core.c changes how PI offsets are handled.
Test to provoke it
SAFE in QEMU (-device nvme-ns,ms=8,pi=1): write with correct PI, then read with PRCHK=ref and a wrong ILBRT (nvme read ... -p 1 -r 0x1234) → 0x284. Write data with a bad guard → 0x282.
S-62Compare Failure (SCT 2 / SC 0x85) ReportedNVMe command
In a PEX trace
Visible The status is in DW3 of the 16-byte CQE that the device writes with a device→host MWr to the CQ base address + head×16; the analyzer's NVMe decoder pairs it with the SQE by SQID/CID. Pattern: Compare SQE → device MRd of the host buffer → CQE 0x285.
What happens
A Compare (05h) found that the media data differs from the host buffer. This is an expected result, not a fault, for compare-and-write locking. As the first half of a fused pair it also aborts the second half (0x09).
How it shows up
0x285 → Linux BLK_STS_MEDIUM → -ENODATA, so it looks like a medium error in dmesg. Monitoring tools that count "critical medium error" lines over-count on systems using Compare (e.g. VMware-style ATS-like locking over NVMe-oF).
Spec basis
NVM Compare command; Fused Operation; ONCS Compare bit.
Typical causes
Lock contention (expected); stale data after a lost write (unexpected and worth investigating). QEMU: nvme_compare_data_cb(), nvme_compare_mdata_cb() (data and metadata compared separately).
How to detect / prove
Read the LBA and diff it against the compare buffer; check whether the differing data matches an older write (lost-write detection).
Linux v7.2 source
core.c:nvme_error_status() (BLK_STS_MEDIUM). Compare is not issued by the block layer; it comes from passthrough or targets.
Test to provoke it
SAFE: nvme compare /dev/nvme0n1 -s 0 -c 0 -z 4096 -d /dev/urandom (random data will not match).
S-63Access Denied (SCT 2 / SC 0x86) ReportedNVMe command / security
In a PEX trace
Visible The status is in DW3 of the 16-byte CQE that the device writes with a device→host MWr to the CQ base address + head×16; the analyzer's NVMe decoder pairs it with the SQE by SQID/CID. Pattern: Reads → immediate CQE 0x286 (no media latency).
What happens
Access to the namespace or LBA range is denied because of missing access rights, typically a locked range of a self-encrypting drive.
How it shows up
0x286 → Linux BLK_STS_MEDIUM → -ENODATA. On boot this looks like a dying disk ("critical medium error" on every read of the partition table) when the drive is simply locked.
Spec basis
Media and Data Integrity "Access Denied"; TCG Storage Opal/Enterprise locking ranges via Security Send/Receive.
Typical causes
Opal locking range locked after power cycle; S3 resume without re-unlock (Linux supports Opal unlock on resume through sed-opal).
How to detect / prove
sedutil-cli --query /dev/nvme0 shows Locked = Y; all failing LBAs fall inside one locking range.
Linux v7.2 source
core.c:nvme_error_status(); Opal through core.c:nvme_sec_submit() and block/sed-opal.c.
Test to provoke it
CAUTION: lock a range on a test SED and read it. Keep the admin password safe.
S-64Deallocated or Unwritten Logical Block (SCT 2 / SC 0x87) — DULBE ReportedNVMe command
In a PEX trace
Visible The status is in DW3 of the 16-byte CQE that the device writes with a device→host MWr to the CQ base address + head×16; the analyzer's NVMe decoder pairs it with the SQE by SQID/CID. This is one of the few ways a PEX trace can prove a deallocation took effect: with DULBE enabled, a read of the trimmed range returns SC 0x87 and no data MWr. Pattern: Read SQE → immediate CQE 0x287, no data.
What happens
A Read, Verify, Compare or Copy touched a deallocated or never-written LBA, and the host enabled DULBE (Deallocated or Unwritten Logical Block Error) in the Error Recovery feature. Without DULBE the drive returns the deallocated read pattern (often zeros; see DLFEAT) with success.
How it shows up
0x287 → Linux BLK_STS_MEDIUM → -ENODATA. It is a useful error. It is also the only way, other than LBA Status, to prove that a Deallocate actually took effect: after deallocating a range, reads with DULBE on must fail with 0x287.
Spec basis
Error Recovery feature (FID 05h) DULBE bit; Identify Namespace NSFEAT DAE bit (DULBE supported); DLFEAT (read behaviour of deallocated blocks).
Typical causes
Host enabled DULBE and then reads unwritten space (partition probing, filesystem scans). Linux never sets DULBE because it would break partition and filesystem probing (Christoph Hellwig, linux-nvme 2018). Arrays sometimes return it even when DULBE is off, which is a vendor bug (Hannes Reinecke in the same thread). QEMU: nvme_check_dulbe() uses the backend's block status (unallocated → NVME_DULB) when NVME_ERR_REC_DULBE(ns->features.err_rec) is set.
How to detect / prove
nvme get-feature /dev/nvme0 -n 1 -f 5 shows whether DULBE is on. As a deallocation proof: write a pattern, nvme dsm -d the range, enable DULBE, read → expect 0x287. If the read returns the old pattern with success, the deallocation was silently ignored.
Linux v7.2 source
core.c:nvme_error_status() (UNWRITTEN_BLOCK → BLK_STS_MEDIUM).
Test to provoke it
CAUTION (the DSM step destroys data): on a scratch namespace, nvme set-feature /dev/nvme0 -n 1 -f 5 -v 0x10000 (DULBE is bit 16 of the Error Recovery value), deallocate a range, read it, then set the feature back to its previous value.

6.2 Path Related Status (SCT 3)

The ANA codes 0x01–0x03 carry the Asymmetric Namespace Access state of the controller–namespace relationship. 0x00 is a controller-internal path error. 0x60 is a controller-detected pathing error, and 0x70/0x71 are host-detected. Linux's nvme_is_path_error() checks only (status & NVME_SCT_MASK) == NVME_SCT_PATH, so every SCT 3 code fails over on a multipath head. nvme_is_ana_error() additionally schedules an ANA log re-read for 0x301–0x303.

S-65Internal Path Error (SCT 3 / SC 0x00) ReportedNVMe command / path
In a PEX trace
Visible The status is in DW3 of the 16-byte CQE that the device writes with a device→host MWr to the CQ base address + head×16; the analyzer's NVMe decoder pairs it with the SQE by SQID/CID. Pattern: On path A: CQE 0x300; the same LBA then appears on path B.
What happens
The command failed because of an internal error specific to the controller processing it, so another controller (path) to the same namespace may succeed (libnvme wording).
How it shows up
0x300. Multipath: failover, multipath_failover_count increases, and the I/O succeeds on the other path. Single path: retry, then -EIO.
Spec basis
Path Related Status "Internal Path Error".
Typical causes
One controller of a dual-controller array failing its back-end link; one port of a dual-port SSD with an internal fault.
How to detect / prove
nvme list-subsys path states; failover counters per path; correlate with array logs.
Linux v7.2 source
nvme.h:nvme_is_path_error(), multipath.c:nvme_failover_req() (nvme_mpath_clear_current_path(), requeue on the head).
Test to provoke it
SAFE: fault-inject 0x300 on one path's namespace device (the hidden nvme0c0n1-style node) and watch I/O continue.
S-66ANA path errors: Persistent Loss (0x01), Inaccessible (0x02), Transition (0x03) ReportedNVMe command / ANA multipath
In a PEX trace
Visible The status is in DW3 of the 16-byte CQE that the device writes with a device→host MWr to the CQ base address + head×16; the analyzer's NVMe decoder pairs it with the SQE by SQID/CID. Pattern: CQEs with SCT 3 on one controller; Get Log Page LID 0Ch shortly after; I/O moves to the other controller.
What happens
The namespace's ANA group on this controller is in Inaccessible (0x02), Persistent Loss (0x01) or Change/Transition (0x03) state, so the command cannot be served on this path.
How it shows up
0x301/0x302/0x303. Linux multipath: nvme_failover_req() sets NVME_NS_ANA_PENDING and queues ana_work to re-read the ANA log (LID 0Ch), then resubmits the bios on another path. Usually an ANA Change AEN (S-83) arrives too. Without multipath (nvme_core.multipath=N), the code is retried on the same path and ends in -EIO.
Spec basis
Asymmetric Namespace Access: ANA log page (groups, states Optimized 01h, Non-Optimized 02h, Inaccessible 03h, Persistent Loss 04h, Change 0Fh — Linux enum nvme_ana_state), ANATT (ANA Transition Time, seconds), ANACAP, ANAGRPID.
Typical causes
Array controller failover or firmware upgrade (Transition); a path to a namespace owned by the peer controller (Inaccessible); controller permanently lost access (Persistent Loss).
How to detect / prove
nvme ana-log /dev/nvme0; cat /sys/block/nvme0c0n1/ana_state; failover counters; dmesg "ANATT timeout, resetting controller." if a transition outlasts ANATT.
Linux v7.2 source
multipath.c:nvme_failover_req(), nvme_update_ana_state(), nvme_anatt_timeout() (resets the controller after ANATT×2 seconds of Change state, via mod_timer(&ctrl->anatt_timer, ctrl->anatt * HZ * 2 + jiffies)); nvme.h:nvme_is_ana_error().
Test to provoke it
SAFE: Linux nvmet target with two ports; change a port's ANA state through configfs (ana_groups/<id>/ana_state) to "inaccessible" or "change" and run fio on the host.
S-67Controller Pathing Error (SCT 3 / SC 0x60) ReportedNVMe-oF / path
In a PEX trace
Partly visible On NVMe/PCIe the CQE with SCT 3/SC 0x60 is visible like any other; on fabrics (the usual case) it is not on PCIe. Pattern: Response capsule with SCT 3/SC 0x60.
What happens
The controller detected a pathing error, e.g. a fabrics transport problem between itself and the host, or within the subsystem.
How it shows up
0x360 → failover on multipath; default -EIO otherwise.
Spec basis
Path Related Status "Controller Pathing Error" (controller-detected range 60h–6Fh).
Typical causes
Target-side transport errors; fabric port reset.
How to detect / prove
Target logs; failover counters; network counters on the target side.
Linux v7.2 source
Same path as S-65.
Test to provoke it
SAFE via fault injection 0x360.
S-68Host Pathing Error (SCT 3 / SC 0x70) — host-generated ReportedHost driver / path
In a PEX trace
Not visible Host-generated: no CQE carries 0x370. At most you see that the command was never submitted (no SQ doorbell MWr) while the controller was being reset. Evidence: the nvme:nvme_complete_rq tracepoint and dmesg. Pattern: Nothing. The command was never submitted, or was submitted to a dead link.
What happens
The host detected that it cannot reach the controller. Linux sets this status itself when a request cannot be queued to a controller that is not live (e.g. during reconnect).
How it shows up
No CQE on the wire. Linux: status 0x370 → FAILOVER on multipath, otherwise BLK_STS_TRANSPORT → -ENOLINK ("recoverable transport error").
Spec basis
Path Related Status "Host Pathing Error" (host-detected range 70h–7Fh).
Typical causes
Fabrics connection lost; PCIe controller in RESETTING/DELETING; the driver's nvme_fail_nonready_command() path for non-ready controllers.
How to detect / prove
dmesg controller state changes ("resetting controller", reconnect attempts) right before; tracepoint status 0x370 with no matching CQE in an analyzer capture.
Linux v7.2 source
core.c:nvme_host_path_error(), core.c:nvme_fail_nonready_command(), core.c:nvme_error_status() → BLK_STS_TRANSPORT.
Test to provoke it
SAFE: NVMe/TCP loopback, take the target port down (ip link set ... down) with fast_io_fail_tmo set, run I/O.
S-69Host Aborted Command (SCT 3 / SC 0x71) — host-generated ReportedHost driver
In a PEX trace
Partly visible 0x371 itself is never on the wire (host-generated). What is visible is the cause and the reset: outstanding SQEs with no CQE, then CC.EN←0 (MWr to BAR0+14h) and re-initialisation. Pattern: No CQE with 0x371. You see the reset itself: CC.EN←0 (MWr to offset 14h), CSTS.RDY→0, re-enable.
What happens
The host cancelled the command because of a host action. Linux sets it on every in-flight request when it tears down a controller's queues (reset after timeout or CSTS.CFS, removal, transport error recovery).
How it shows up
dmesg nvme_log_error lines with "Host Aborted Command (sct 0x3 / sc 0x71)" for many requests at once, usually right after "I/O tag N ... timeout, reset controller" or "controller is down; will reset". Being SCT 3 it fails over on multipath; otherwise it is retried after the reset, or -EIO if the controller is removed.
Spec basis
Path Related Status "Command Aborted By Host" (libnvme NVME_SC_CMD_ABORTED_BY_HOST).
Typical causes
It is always a symptom. The cause is earlier: a command timeout, a fatal controller status, a PCIe error (AER/DPC), or surprise removal.
How to detect / prove
Read dmesg backwards from the first 0x371 to the first timeout, CFS or AER message. In an analyzer capture, find the last good CQE and what the device stopped doing.
Linux v7.2 source
core.c:nvme_cancel_request() (nvme_req(req)->status = NVME_SC_HOST_ABORTED_CMD), nvme_cancel_tagset(), nvme_cancel_admin_tagset().
Test to provoke it
CAUTION: nvme reset /dev/nvme0 during heavy fio; or echo 1 > /sys/bus/pci/devices/<bdf>/remove (EXPERT: device disappears until rescan).
S-70Vendor Specific status (SCT 7) and reserved SCT 4–6 ReportedNVMe command / vendor
In a PEX trace
Visible The status is in DW3 of the 16-byte CQE that the device writes with a device→host MWr to the CQ base address + head×16; the analyzer's NVMe decoder pairs it with the SQE by SQID/CID. Pattern: CQE DW3 bits 27:25 = 111b.
What happens
The controller reports a vendor-defined status (SCT 7). SCT 4–6 are reserved, and receiving one is a device bug.
How it shows up
Linux prints "Unknown (sct 0x7 / sc 0x..)" and maps it to BLK_STS_IOERR → -EIO; retried unless DNR.
Spec basis
Status Code Type 7h = Vendor Specific (libnvme NVME_SCT_VS).
Typical causes
Vendor commands; firmware debug builds; drives that use SCT 7 for internal faults that should have used Internal Error.
How to detect / prove
Ask the vendor for the code table; capture telemetry right after.
Linux v7.2 source
constants.c:nvme_get_error_status_str() → "Unknown".
Test to provoke it
SAFE via fault injection status 0x7xx.
