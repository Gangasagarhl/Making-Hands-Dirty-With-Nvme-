7.5 PCIe Transaction, Data Link and Flit Layer Violations

Below NVMe, every PCIe link has its own rulebook. The Transaction Layer constrains TLP sizes, address/length combinations, completion splitting and ordering; the Data Link Layer (DLL) guarantees delivery with sequence numbers, LCRC (Link CRC), Ack/Nak DLLPs and a replay buffer; in PCIe 6.0 Flit mode the unit of protection becomes a fixed-size FLIT with FEC (forward error correction) and CRC. Some of these violations are caught by the receiver and logged in the AER (Advanced Error Reporting) capability — Linux v7.2 names the bits in drivers/pci/pcie/aer.c (aer_correctable_error_string, aer_uncorrectable_error_string) — but many are "receiver may check" rules, so only an analyzer sees them reliably.

V-26TLP payload larger than Max_Payload_Size ReportedPCIe TL
What happens
A transmitter sends a TLP whose data payload exceeds the MPS programmed in its own Device Control register (for the SSD: data MWr for reads, or CplD for a host read of the CMB). A receiver with a smaller MPS setting cannot accept it.
How it shows up
The receiver treats it as a Malformed TLP: uncorrectable AER bit 18 "MalfTLP", fatal by default severity, which on Linux triggers AER recovery (reset of the link / device) or, with DPC, containment of the downstream port. The NVMe controller disappears briefly and I/O is retried or failed.
Spec basis
PCI Express Base: Max_Payload_Size — transmitters must not send TLPs with payload larger than MPS; receivers treat such TLPs as Malformed. All functions on a path must use an MPS no larger than what every element supports.
Typical causes
Firmware ignoring the programmed MPS and using its capability maximum; hot-plugged device behind a switch whose MPS was configured smaller after the device was enumerated; firmware/OS (pci=pcie_bus_perf) choices that set MPS per segment inconsistently.
How to detect / prove
Analyzer: compare each TLP's Length field with the configured MPS of the transmitter (capture config writes at enumeration or read lspci -vvv of every device on the path). Rule TLP-MPS in 7.6. Host: dmesg AER lines naming MalfTLP; /sys/bus/pci/devices/<bdf>/aer_dev_fatal.
In a trace
MWr with Length = 128 DW (512 B) while DevCtl MaxPayload = 256 B; immediately followed by an ERR_FATAL message from the receiving port.
Linux v7.2 source
drivers/pci/probe.c:pcie_write_mps, pcie_bus_configure_settings, pcie_bus_configure_set (MPS policy per pcie_bus_config); drivers/pci/pcie/aer.c string "MalfTLP".
Test to provoke it
EXPERT: lower MPS on the root port with setpci below the device's setting on a test box — this crashes I/O to the device; do it only with no mounted filesystems.
V-27Read request larger than Max_Read_Request_Size SilentPCIe TL
What happens
The SSD (as requester) issues a memory read (to fetch write data, SQEs or PRP lists) with a length greater than its programmed MRRS.
How it shows up
MRRS is a requester-side limit; whether the completer flags an oversized read is implementation-dependent (verify the receiver rules in the PCIe Base spec). Usually the host bridge just services it — so the violation is silent, but it breaks the fairness and buffer assumptions the OS made when it chose MRRS (e.g. for isochronous or peer devices).
Spec basis
PCI Express Base: Max_Read_Request_Size in Device Control — the requester must not generate read requests larger than this value.
Typical causes
Firmware using a fixed 4 KiB read size; MRRS changed by the OS after the device cached it at link-up.
How to detect / prove
Analyzer: MRd Length × 4 > MRRS of the requester.
In a trace
MRd with Length = 1024 DW (4096 B) while DevCtl MaxReadReq = 512 B.
Linux v7.2 source
drivers/pci/probe.c:pcie_write_mrrs (calls pcie_set_readrq in performance mode); register field PCI_EXP_DEVCTL_READRQ.
Test to provoke it
SAFE observation: capture a large sequential write and check MRd sizes against lspci -vvv MaxReadReq.
V-28Request crossing a 4 KiB address boundary SilentPCIe TL
What happens
A memory read or write request whose address + length spans a 4 KiB-aligned boundary (e.g. MWr of 256 B starting at …0F80h).
How it shows up
Receivers may optionally check this rule; if they do, the TLP is Malformed (AER MalfTLP). Many root complexes do not check, so the request is serviced — and the second part may land in a page that belongs to a different IOMMU mapping, causing an IOMMU fault for "half" a TLP or silent access to the wrong page. impl
Spec basis
PCI Express Base: requests must not specify an address/length combination that causes a memory space access to cross a 4 KB boundary.
Typical causes
DMA engine splitting at MPS multiples from the PRP1 offset instead of at page boundaries; PRP1 with an odd offset (V-17) combined with naive splitting.
How to detect / prove
Analyzer rule: (addr mod 4096) + len > 4096 for any MRd/MWr. Cheap and stateless — always enable it.
In a trace
MWr address 1000_0F80h, Length 64 DW (256 B): bytes 1000_0F80h–1000_107Fh.
Linux v7.2 source
Linux cannot see this; IOMMU fault logs are the only host-side hint. dma_set_min_align_mask in drivers/nvme/host/pci.c preserves page offsets, so a correct device never needs to cross.
Test to provoke it
SAFE: send reads with PRP1 offsets such as 0F80h via passthrough and inspect the device's MWr split pattern.
V-29Completions not respecting the Read Completion Boundary SilentPCIe TL
What happens
A completer answering one read request with several CplD TLPs must split only at RCB-aligned addresses (64 or 128 B): each partial completion except the last must end on an RCB boundary, and the data must be returned in increasing address order for a single request. A completer that splits at arbitrary points (e.g. 100 bytes) violates this.
How it shows up
A requester that relies on RCB-aligned splits (to size its completion buffers) may mis-assemble data; a strict requester flags a Malformed TLP. Often silent. impl
Spec basis
PCI Express Base: Read Completion Boundary (Link Control RCB; root ports 64 B or 128 B) and completion splitting rules for memory read requests.
Typical causes
Device-side CMB / PMR completion logic (when the host reads the SSD's Controller Memory Buffer) with an incorrect splitter; RCB register not programmed consistently with the root port.
How to detect / prove
Analyzer: for each request with multiple CplDs, check that each non-final CplD's end address (Lower Address + payload) is a multiple of RCB.
In a trace
Host MRd 512 B from CMB; device answers with CplDs of 100, 412 B rather than 64/128-aligned pieces.
Linux v7.2 source
include/uapi/linux/pci_regs.h:PCI_EXP_LNKCTL_RCB; CMB mapping in drivers/nvme/host/pci.c (nvme_map_cmb).
Test to provoke it
SAFE observation on devices with a CMB: read the CMB region with large reads (e.g. via a test harness or dd on a resource file — read-only) while capturing.
V-30Byte Count / Lower Address inconsistent in completions ReportedPCIe TL
What happens
In a completion, Byte Count must equal the number of bytes remaining to satisfy the request (including this completion's bytes), and Lower Address must be the low address bits of the first byte returned in this completion. A completer that reports the wrong values (e.g. Byte Count = payload length on every partial, or Lower Address not advancing) breaks the requester's reassembly.
How it shows up
The requester may treat the completion as malformed or unexpected, or may conclude the request is finished too early and later receive "unexpected" completions — AER "UnxCmplt" (bit 16) or "MalfTLP"; or the read silently returns partial data. impl
Spec basis
PCI Express Base: Completion header fields Byte Count and Lower Address and their rules for split completions.
Typical causes
Completer logic that does not track remaining bytes across splits; BCM (Byte Count Modified) misuse by PCI-X bridges in legacy topologies.
How to detect / prove
Analyzer: for each tag, track remaining bytes; every CplD must have Byte Count == remaining and Lower Address == (next expected address mod 128).
In a trace
Request 256 B; CplD #1 Byte Count 128, Lower Address 00h; CplD #2 Byte Count 128, Lower Address 00h — the first should have said 256, the second's Lower Address should be 80h.
Linux v7.2 source
Only the AER outcome is visible: drivers/pci/pcie/aer.c strings "UnxCmplt", "MalfTLP".
Test to provoke it
Device-side bug; validate with an exerciser that injects wrong Byte Count (EXPERT, lab equipment).
V-31Completion for an unknown tag (Unexpected Completion) ReportedPCIe TL
What happens
A completion arrives whose Transaction ID (Requester ID + Tag) matches no outstanding non-posted request of the receiver — because the request already completed, already timed out, was never sent, or the completer copied the wrong tag/requester ID.
How it shows up
The receiver logs Unexpected Completion: AER uncorrectable bit 16 "UnxCmplt" (non-fatal by default, often handled as an advisory non-fatal error and reported as correctable "NonFatalErr"). Frequently seen as the second half of a Completion Timeout ("CmpltTO", bit 14): the late completion for a request already timed out arrives and is unexpected.
Spec basis
PCI Express Base: Transaction ID matching of completions; Unexpected Completion error; Completion Timeout mechanism (range in Device Control 2).
Typical causes
Completion timeout set too short (PCI_EXP_DEVCTL2_COMP_TIMEOUT) on a slow path (e.g. through a switch to a busy root port or to a device in a low-power state); tag mismatch after enabling 10-bit tags on only one side; firmware returning completions after FLR.
How to detect / prove
Analyzer: maintain outstanding (Requester ID, Tag) per requester; flag CplD/Cpl without a match; measure request→completion latency to see if a timeout explains it.
In a trace
MRd tag 2Ah at t0; no completion for 50 ms (beyond the configured timeout); CplD tag 2Ah at t0+60 ms → unexpected at the requester.
Linux v7.2 source
drivers/pci/pcie/aer.c strings "UnxCmplt", "CmpltTO"; per-device counters in sysfs aer_dev_nonfatal, aer_dev_correctable.
Test to provoke it
EXPERT: shorten the completion timeout range in Device Control 2 with setpci on the requester while the completer is slow (e.g. deep power state), on a test system only.
V-32Tag reused while a request is outstanding SilentPCIe TL
What happens
A requester issues a new non-posted request with a Tag that is still in use by an outstanding request (same Requester ID). The completer cannot tell them apart; completions may be matched to the wrong request.
How it shows up
Silent data mix-up: the SSD receives data meant for a different read (e.g. PRP list bytes delivered as write data, or one write's data in another write). Possibly Unexpected Completion later when the "second" completion for the tag arrives.
Spec basis
PCI Express Base: Transaction ID (Requester ID + Tag) must be unique among a requester's outstanding non-posted requests; 8-bit, 10-bit (optional, Gen4+) and 14-bit (Flit mode) tag spaces.
Typical causes
Tag allocator bug after a completion timeout (tag freed while the completion may still arrive); 10-bit tag requester whose tags are truncated to 8 bits by a component that does not support 10-bit tags.
How to detect / prove
Analyzer: per requester, flag a non-posted request whose tag is in the outstanding set. This is the PCIe twin of V-08.
In a trace
MRd tag 05h at t0 (4 KiB), MRd tag 05h at t1 before all CplDs of the first have arrived.
Linux v7.2 source
Not visible to Linux: tags are allocated by the device's hardware. A grep of v7.2 include/uapi/linux/pci_regs.h and drivers/pci/ finds no 10-bit-tag enable logic, so check the Device Control 2 setting with lspci -vvv rather than assuming the kernel configured it. impl
Test to provoke it
Device-side; observe with analyzer under deep queue sequential writes (many concurrent MRd) — the scenario where tag exhaustion bugs appear.
V-33Posted-write ordering violation SilentPCIe TL
What happens
A component reorders TLPs in a way the ordering table forbids: a posted write passes an earlier posted write without RO; a completion passes a posted write in the same direction (which would let a read return before an earlier write is visible); a read passes a posted write. In NVMe terms: host doorbell write overtaking the host's earlier SQE write is impossible on PCIe (the SQE is in host memory, not sent to the device), but device-side reorderings of data/CQE/MSI-X (V-13, V-14) and switch reorderings are possible.
How it shows up
Stale reads, stale data, spurious interrupts; never a status code.
Spec basis
PCI Express Base: Transaction Ordering rules (the ordering table for Posted, Non-Posted, Completion), Relaxed Ordering and ID-Based Ordering attributes.
Typical causes
Device setting RO/IDO on TLPs that need strong ordering; a switch or root complex bug; host chipsets that are known to mishandle RO (Linux has quirks that clear RO enable for certain root ports).
How to detect / prove
Two probes (upstream and downstream of a switch) and compare TLP order; on a single link, check that no CQE or MSI-X TLP has RO=1 and that the ordering of device→host MWr matches the NVMe dependency (data → CQE → MSI-X).
In a trace
Upstream capture order: MWr(CQE) before MWr(data) although downstream order was data then CQE, with RO=0 on the CQE.
Linux v7.2 source
drivers/pci/quirks.c contains relaxed-ordering quirks for root ports (search for PCI_DEV_FLAGS_NO_RELAXED_ORDERING); enable bit PCI_EXP_DEVCTL_RELAX_EN.
Test to provoke it
Analyzer-only; run fio verify with RO enabled vs disabled on a test system and compare.
V-34ECRC mismatch ReportedPCIe TL
What happens
When end-to-end CRC is enabled, the transmitter appends a 32-bit TLP Digest (TD bit = 1). A receiver with ECRC checking enabled recomputes it; a mismatch means the TLP was corrupted inside a component (e.g. switch internal SRAM) after the link-level LCRC had already been checked and stripped.
How it shows up
AER uncorrectable bit 19 "ECRC"; Linux logs the TLP header from the AER Header Log. Without ECRC enabled (the common default), the same internal corruption is silent.
Spec basis
PCI Express Base: End-to-End CRC (ECRC), TLP Digest, AER ECRC Generation/Check Capable/Enable bits.
Typical causes
Switch or retimer internal memory errors; a component that modifies a TLP header field it is not allowed to modify (some fields are variant and excluded from ECRC); mismatched ECRC enable (TD set by a device whose partner miscomputes).
How to detect / prove
Analyzer recomputes ECRC on every TLP with TD=1 at both ends of a switch; host: lspci -vvv shows "ECRCGenCap/ECRCChkCap" and enables; dmesg AER messages with "ECRC".
In a trace
TLP with TD=1 whose digest does not match the recomputed value at the downstream side while LCRC was fine.
Linux v7.2 source
drivers/pci/pcie/aer.c (ECRC policy via kernel parameter pci=ecrc=on|off, string "ECRC"); PCI_ERR_CAP_ECRC_* in pci_regs.h.
Test to provoke it
SAFE: boot a lab host with pci=ecrc=on and capture; an exerciser can inject ECRC errors (EXPERT).
V-35LCRC errors and sequence-number errors DegradedPCIe DLL
What happens
In non-Flit mode, every TLP carries a 12-bit sequence number and a 32-bit LCRC. A receiver that sees a bad LCRC or an out-of-order sequence number (a gap) discards the TLP and sends a Nak; a duplicate (already acknowledged) sequence number is discarded and Acked. The transmitter replays from its replay buffer.
How it shows up
Correctable AER: bit 6 "BadTLP" (LCRC or sequence error), bit 7 "BadDLLP" (DLLP CRC), bit 0 "RxErr" (physical layer receive error). Throughput drops due to replays; latency spikes; no data loss as long as replays succeed.
Spec basis
PCI Express Base: Data Link Layer — sequence numbers, LCRC, Ack/Nak protocol, replay buffer, Bad TLP / Bad DLLP / Receiver Error correctable errors.
Typical causes
Marginal signal integrity (long traces, connectors, risers), wrong equalisation presets, temperature, retimer configuration.
How to detect / prove
Analyzer: count Nak DLLPs and replayed TLPs (same sequence number transmitted twice); host: AER correctable counters in /sys/bus/pci/devices/<bdf>/aer_dev_correctable; lspci -vvv "CESta" bits.
In a trace
TLP seq 0x3A0 with LCRC error → Nak 0x39F → replay of 0x3A0 onwards; periodic bursts under load.
Linux v7.2 source
drivers/pci/pcie/aer.c:aer_correctable_error_string ("RxErr", "BadTLP", "BadDLLP", "Rollover", "Timeout").
Test to provoke it
CAUTION: lower the link speed or swap a riser to compare counts; never "fix" by masking correctable errors without understanding them.
V-36Missing ACKs: replay timer timeout and REPLAY_NUM rollover DegradedPCIe DLL
What happens
The transmitter keeps each TLP until it is acknowledged. If no Ack/Nak arrives before the replay timer expires, it replays; after four consecutive replays of the same TLP (REPLAY_NUM rolls over) the link is retrained (Recovery).
How it shows up
Correctable AER: bit 12 "Timeout" (Replay Timer Timeout), bit 8 "Rollover" (REPLAY_NUM Rollover). Each rollover causes a retrain (link briefly down, hundreds of µs or more). Repeated failures escalate to "DLP" (Data Link Protocol error, uncorrectable bit 4) or "SDES" (Surprise Down, bit 5) if the link drops.
Spec basis
PCI Express Base: Ack/Nak latency limits, replay timer, REPLAY_NUM, link retraining on rollover; AER correctable errors Replay Timer Timeout and REPLAY_NUM Rollover.
Typical causes
Receiver not sending Ack DLLPs in time (firmware/PHY stall, power state transitions), DLLPs corrupted (Bad DLLP), Ack coalescing set too long.
How to detect / prove
Analyzer: measure the gap between a TLP and the Ack covering its sequence number; flag gaps above the spec's Ack latency limit for that link speed/width (look up the table in the spec); detect the same sequence number transmitted 4 times followed by training sets.
In a trace
TLP seq 0x120 sent at t0, t0+Δ, t0+2Δ, t0+3Δ with no Ack; then TS1/TS2 ordered sets (Recovery); then traffic resumes.
Linux v7.2 source
drivers/pci/pcie/aer.c strings "Timeout", "Rollover", "DLP", "SDES".
Test to provoke it
Analyzer-based; exercisers can drop Acks (EXPERT).
V-37FLIT errors in PCIe 6.0 Flit mode (FEC/CRC, replay, sequence) DegradedPCIe Flit
What happens
At 64 GT/s with PAM4 signalling, Flit mode carries traffic in fixed 256-byte FLITs (vendor overviews: 236 bytes of TLP, 6 of DLP, 8 of CRC, 6 of ECC). A lightweight FEC corrects small symbol errors in-line; a FLIT whose CRC still fails after FEC is retried at FLIT granularity, with flit sequence numbers and standard or selective NAK. Per-TLP LCRC and the classic per-TLP sequence/Ack scheme are replaced by this flit-level mechanism. version
How it shows up
A rising FEC-corrected count costs nothing yet (an early-warning signal); CRC-failed FLITs cause retries (bandwidth/latency loss); persistent failures cause Recovery or link-down. How these are surfaced to software (AER bits, vendor counters, new capability registers) depends on the implementation and spec version — verify in the PCIe 6.x spec and the device's documentation. uncertain
Spec basis
PCI Express Base 6.0 and later: Flit mode, FEC, flit CRC, flit sequence numbers and NAK/retry (names of the specific counters and capability structures: verify in spec).
Typical causes
PAM4 eye margin (reflections, crosstalk, temperature); equalisation; retimers; mixed Flit/non-Flit negotiation issues on links that fall back to lower speeds.
How to detect / prove
Gen6-capable analyzer with Flit decode: count FEC corrections per lane, flit CRC failures and NAKs; correlate with temperature and link speed. Host: lspci -vvv shows speed 64GT/s and Flit mode state when supported by your lspci version.
In a trace
Flit sequence N with CRC failure → NAK → retried flit N; bursts correlated with a particular lane's FEC correction count.
Linux v7.2 source
Generic AER handling in drivers/pci/pcie/aer.c; link speed decoding in drivers/pci/pci.c:__pcie_print_link_status. No NVMe-driver-specific handling.
Test to provoke it
Lab-only (EXPERT): margining tools / lane margining at the receiver, cable or channel stress, and compare FEC/CRC counters at different temperatures.
V-38Poisoned TLP data accepted as good SilentPCIe TL
What happens
A TLP carries the EP (Error Poisoned) bit, meaning its payload is known to be bad (e.g. a host memory read hit an uncorrectable ECC error). The receiving NVMe controller must not treat the data as valid — e.g. it must not write poisoned write-data to media as if it were good.
How it shows up
Correct behaviour: AER "Poisoned TLP" received (uncorrectable bit 12, shown by Linux as "TLP") and the NVMe command fails (typically Data Transfer Error 04h). Incorrect behaviour: success, and the corrupted bytes are now persistent on media — silent corruption.
Spec basis
PCI Express Base: Data Poisoning (EP bit) and Poisoned TLP Received error; NVMe Base: Data Transfer Error generic status.
Typical causes
Controller firmware ignoring EP on CplD; host DRAM UE during a write command; switch forwarding poisoned data.
How to detect / prove
Analyzer: any CplD/MWr with EP=1 must be followed by a failing CQE for the owning command (or by the device's documented poisoned-data handling). A success CQE after a poisoned CplD is a finding.
In a trace
CplD with EP=1 answering the device's write-data MRd for CID X; later CQE for CID X with status 0.
Linux v7.2 source
drivers/pci/pcie/aer.c:aer_uncorrectable_error_string bit 12 "TLP"; status 04h string in drivers/nvme/host/constants.c.
Test to provoke it
EXPERT: error-injection (EINJ on servers that support it) or a PCIe exerciser setting EP on completions.

7.6 An Executable Checker over an Exported Trace

Analyzers export traces as CSV or text. The schema differs per vendor, so the practical approach is: export, convert to a small neutral event schema (one decoded NVMe/PCIe event per row), and run rules over it. The script below is self-contained Python 3 (standard library only). It embeds a synthetic 26-event trace that deliberately contains violations, and it implements 15 rules from this part: DB-RANGE (V-01/V-02), DB-NOQ (V-03), CQDB-PAST-TAIL (V-06), CQ-OVERFLOW (V-07), CID-REUSE (V-08), CQE-UNKNOWN (V-09), SQID (V-10), PHASE (V-11), CQE-BEFORE-DATA (V-13), MSIX-NO-CQE (V-14), DMA-NOCMD (V-16), PRP1-ALIGN (V-17), PRP2-OFFSET (V-18), MDTS (V-20), TLP-MPS (V-26).

🧪 Lab

Save as trace_check.py, run python3 trace_check.py to see the synthetic findings, then convert your own export to the same columns and run python3 trace_check.py my_trace.csv --mps 256 --mdts-bytes 131072. The exit code is 1 when findings exist, so it can gate a CI job.

#!/usr/bin/env python3
"""trace_check.py - rule-based checker for an exported NVMe-over-PCIe trace (CSV).

SYNTHETIC example: the embedded CSV below is invented to exercise the rules.
Columns (one decoded event per row, time-ordered):
  t_ns   event     q  cid  opc  val  len   prp1        prp2        sqid sqhd ph  tlp_len
  event in: CFG_Q (queue created: val=entries), SQDB, CQDB (doorbell writes),
            SQE (device fetched a command), DATA_WR / DATA_RD (device DMA for cid),
            CQE (device wrote a completion), MSIX (interrupt for vector q),
            TLP (any MWr from device; tlp_len = payload bytes)
Usage:  python3 trace_check.py [trace.csv] [--mps 256] [--mdts-bytes 131072] [--page 4096]
"""
import csv, io, sys

SAMPLE = """t_ns,event,q,cid,opc,val,len,prp1,prp2,sqid,sqhd,ph,tlp_len
0,CFG_Q,1,,,4,,,,,,,
100,SQDB,1,,,1,,,,,,,
400,SQE,1,0x10,0x02,,4096,0x10000000,0,,,,
900,DATA_WR,1,0x10,,,4096,,,,,,
950,TLP,1,,,,,,,,,,256

1050,MSIX,1,,,,,,,,,,
1100,CQDB,1,,,1,,,,,,,
1200,SQDB,1,,,3,,,,,,,
1300,SQE,1,0x11,0x02,,8192,0x10001000,0x20000010,,,,
1350,SQE,1,0x12,0x01,,4096,0x10003000,0,,,,
1400,DATA_RD,1,0x12,,,4096,,,,,,
1500,MSIX,1,,,,,,,,,,
1600,CQE,1,0x11,,,,,,1,3,1,
1700,DATA_WR,1,0x11,,,8192,,,,,,
1750,TLP,1,,,,,,,,,,512
1800,CQE,1,0x12,,,,,,1,3,1,
1900,CQE,1,0x99,,,,,,2,3,1,
2000,SQDB,1,,,7,,,,,,,
2100,SQDB,1,,,1,,,,,,,
2200,SQE,1,0x13,0x01,,262144,0x10010000,0x30000000,,,,
2250,SQE,1,0x13,0x01,,4096,0x10050000,0,,,,
2300,CQE,1,0x13,,,,,,1,1,1,
2400,CQDB,1,,,6,,,,,,,
2450,CQDB,1,,,3,,,,,,,
2500,SQDB,5,,,1,,,,,,,
"""

def num(s):
    s = (s or "").strip()
    return int(s, 0) if s else None

def check(rows, mps=256, mdts_bytes=128 * 1024, page=4096):
    findings = []
    def flag(row, rule, msg):
        findings.append((row["_line"], row["t_ns"], rule, msg))

    qsize = {}                 # qid -> entries
    sq_tail, cq_head = {}, {}  # last doorbell values
    cq_tail, cq_phase = {}, {} # device-side CQ position and expected phase
    outstanding = {}           # (qid, cid) -> dict(opc, len, data_done)
    completed_since_irq = {}   # qid -> CQEs posted since last MSI-X

    for r in rows:
        ev, q = r["event"], num(r["q"])
        cid = num(r["cid"])
        if ev == "CFG_Q":
            qsize[q] = num(r["val"]); sq_tail[q] = 0; cq_head[q] = 0
            cq_tail[q] = 0; cq_phase[q] = 1; completed_since_irq[q] = 0
            continue
        if ev in ("SQDB", "CQDB"):
            v = num(r["val"])
            if q not in qsize:
                flag(r, "DB-NOQ", f"{ev} for queue {q} that was never created "
                     "(controller may post AEN 'Invalid Doorbell Register')")
                continue
            if v >= qsize[q]:
                flag(r, "DB-RANGE", f"{ev} value {v} >= queue size {qsize[q]} "
                     "(controller may post AEN 'Invalid Doorbell Write Value')")
                continue
            if ev == "CQDB":
                # host must not release CQ slots the device has not filled
                used = (cq_tail[q] - cq_head[q]) % qsize[q]
                adv = (v - cq_head[q]) % qsize[q]
                if adv > used:
                    flag(r, "CQDB-PAST-TAIL", f"CQ head {cq_head[q]}->{v} releases {adv} "
                         f"entries but only {used} were posted")
                cq_head[q] = v
            else:
                sq_tail[q] = v
            continue
        if ev == "SQE":
            key = (q, cid)
            if key in outstanding:
                flag(r, "CID-REUSE", f"CID {cid:#x} reused on SQ {q} while still outstanding")
            ln, p1, p2 = num(r["len"]) or 0, num(r["prp1"]) or 0, num(r["prp2"]) or 0
            if ln > mdts_bytes:
                flag(r, "MDTS", f"transfer {ln} B exceeds MDTS limit {mdts_bytes} B")
            first = page - (p1 % page)
            if ln > first:                          # PRP2 is used
                if p1 % 4:
                    flag(r, "PRP1-ALIGN", f"PRP1 {p1:#x} not dword aligned")
                if ln - first <= page and p2 % page:
                    flag(r, "PRP2-OFFSET", f"PRP2 {p2:#x} is a data pointer and must "
                         "have zero page offset (status: PRP Offset Invalid)")
            outstanding[key] = {"opc": num(r["opc"]), "len": ln, "data": 0}
            continue
        if ev in ("DATA_WR", "DATA_RD"):
            o = outstanding.get((q, cid))
            if o is None:
                flag(r, "DMA-NOCMD", f"{ev} for CID {cid:#x} that is not outstanding "
                     "(late DMA after completion?)")
            else:
                o["data"] += num(r["len"]) or 0
            continue
        if ev == "TLP":
            if (num(r["tlp_len"]) or 0) > mps:
                flag(r, "TLP-MPS", f"MWr payload {r['tlp_len']} B > MPS {mps} B (Malformed TLP)")
            continue
        if ev == "CQE":
            if q in qsize:
                if (cq_tail[q] + 1) % qsize[q] == cq_head[q]:
                    flag(r, "CQ-OVERFLOW", f"CQE posted into full CQ {q} "
                         f"(tail {cq_tail[q]}, host head {cq_head[q]})")
                exp = cq_phase[q]
                if num(r["ph"]) != exp:
                    flag(r, "PHASE", f"phase tag {r['ph']} at CQ slot {cq_tail[q]}, expected {exp}")
                cq_tail[q] += 1
                if cq_tail[q] == qsize[q]:
                    cq_tail[q] = 0; cq_phase[q] ^= 1
                completed_since_irq[q] += 1
            if num(r["sqid"]) != q:
                flag(r, "SQID", f"CQE SQID {r['sqid']} but command was on SQ {q}")
            key = (q, cid)
            o = outstanding.pop(key, None)
            if o is None:
                flag(r, "CQE-UNKNOWN", f"CQE for CID {cid:#x} with no outstanding command")
            elif o["opc"] == 0x02 and o["data"] < o["len"]:
                flag(r, "CQE-BEFORE-DATA", f"Read CID {cid:#x} completed after only "
                     f"{o['data']}/{o['len']} B of data were written to host")
            continue
        if ev == "MSIX":
            if completed_since_irq.get(q, 0) == 0:
                flag(r, "MSIX-NO-CQE", f"MSI-X for vector {q} with no new CQE posted")
            completed_since_irq[q] = 0
    return findings

def main(argv):
    mps, mdts, page, path = 256, 128 * 1024, 4096, None
    it = iter(argv)
    for a in it:
        if a == "--mps": mps = int(next(it))
        elif a == "--mdts-bytes": mdts = int(next(it))
        elif a == "--page": page = int(next(it))
        else: path = a
    text = open(path).read() if path else SAMPLE
    rows = []
    for i, r in enumerate(csv.DictReader(io.StringIO(text)), start=2):
        r["_line"] = i; rows.append(r)
    f = check(rows, mps, mdts, page)
    for line, t, rule, msg in f:
        print(f"line {line:>3}  t={t:>5} ns  {rule:<16} {msg}")
    if f:
        print(f"\n{len(f)} findings; first abnormal event: line {f[0][0]} ({f[0][2]})")
    else:
        print("no findings")
    return 1 if f else 0

if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))

💡 Senior insight

A checker that reports 15 findings is less useful than one that says "the first abnormal event is line 11; lines 16, 24-PHASE and 26 are consequences". When you extend this script, give each rule a suppression link ("if CQ-OVERFLOW fired on this CQ, downgrade later PHASE/CQDB findings on it to 'cascade'"). The same principle drives the AI workflow in Part IX.

7.6.2 Extending the checker to PCIe rules

The same structure handles the TLP-level rules if your export has the TLP header fields. Add columns type, req_id, tag, addr, len_dw, byte_count, lower_addr, ro, ep, td and implement:

on MRd/MWr:   if (addr % 4096) + len > 4096        -> V-28 4K-CROSS
on MRd:       if len > MRRS[requester]             -> V-27 MRRS
              if (req_id, tag) in outstanding      -> V-32 TAG-REUSE
              outstanding[(req_id, tag)] = len
on CplD:      o = outstanding.get((req_id, tag))   -> None: V-31 UNEXPECTED-CPL
              if byte_count != o.remaining         -> V-30 BYTECOUNT
              if lower_addr != o.next_addr % 128   -> V-30 LOWER-ADDR
              if not last and (o.next_addr + payload) % RCB != 0 -> V-29 RCB
              if ep                                -> V-38 (expect failing CQE later)
on CQE/MSI-X MWr: if ro                            -> V-13 / V-33 RO-ON-CQE
on DLLP Nak / replay of same seq 4x                -> V-35 / V-36
📭 What the spec does not say

The specifications define what is legal, not how an analyzer exports it. Column names, timestamp resolution, whether a CSV row is a TLP or a decoded transaction, and whether replayed TLPs appear twice all differ by tool. Always write a short converter and test it on a known-good capture before trusting findings.

Quiz

  1. The checker reports PHASE on a CQE. Why should you look at earlier lines before blaming the controller's phase logic?

    Answer

    Because a phase mismatch is the visible symptom of several earlier problems: a CQ overflow (the controller wrapped past the host's head), a CQ size mismatch, or a missed wrap in the checker's own state (it started mid-stream). Report the first abnormal event (here CQ-OVERFLOW on the same line) as the root.

  2. Why can a controller not detect V-05 (SQ tail overrun) from the doorbell value alone?

    Answer

    Because the value is a slot index modulo the queue size; any in-range value is a legal tail. Only the history (how many entries the controller has not yet fetched) reveals that the host has gone past the head. QEMU indeed does not check it.

  3. An 8 KiB read has PRP1 = …1000h. Is PRP2 a data pointer or a list pointer, and what must its low 12 bits be (4 KiB pages)?

    Answer

    PRP1's page provides 4096 bytes, the remaining 4096 fit in one page, so PRP2 is a data pointer and its low 12 bits must be zero.

  4. Which AER bit would you expect after V-26, and is it correctable?

    Answer

    Malformed TLP (uncorrectable status bit 18, "MalfTLP" in Linux), fatal by default severity.
