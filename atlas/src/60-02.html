7.3 Ordering and Interrupt Violations

NVMe over PCIe relies on one PCIe ordering guarantee above all others: a posted Memory Write must not pass an earlier posted Memory Write in the same direction unless the later TLP has the Relaxed Ordering (RO) attribute set (and the path honours it). Data MWr TLPs, the CQE MWr and the MSI-X MWr are all posted writes from the device to the host, so if the device sends them in the order data → CQE → MSI-X without RO on the CQE and MSI-X, the host is guaranteed to observe them in that order. The producer–consumer correctness of every NVMe read rests on this. verified

V-13Completion posted before the data writes (ordering) SilentNVMe / PCIe ordering
What happens
For a Read, the controller writes the CQE (or sets RO on data or CQE TLPs in a way that lets the CQE overtake) before all data MWr TLPs for that command have been sent. The host sees "success", hands the buffer to the application, and the application reads stale bytes; the real data arrives microseconds later, after the application has already used the buffer.
How it shows up
Nothing in any log. Symptoms are intermittent data corruption that disappears when tracing is enabled (timing changes) and checksum failures at the application level, typically on the last TLP(s) of a transfer.
Spec basis
PCI Express Base: ordering rules for posted requests (a posted request must not pass another posted request unless RO is set) and the Relaxed Ordering attribute; NVMe Base: a completion indicates the command's data transfer is complete.
Typical causes
Controller DMA engine with several parallel channels and the CQE sent from a different channel; RO set on the CQE write; a switch or root complex that reorders RO TLPs (legally) combined with the device setting RO where it must not.
How to detect / prove
Checker: map each data MWr to its CID (address ∈ the command's PRP/SGL ranges); at each CQE, require delivered bytes == transfer length (rule CQE-BEFORE-DATA in 7.6). Also flag RO=1 on any CQE or MSI-X TLP. Prove at the application level with fio --verify=crc32c --verify_fatal=1 on reads of data written earlier.
In a trace
CQE MWr for CID X timestamped before the last data MWr whose address lies in CID X's PRP list; or attribute field RO=1 in the CQE TLP header.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_poll_cq issues dma_rmb() between the phase check and reading the rest of the CQE — this protects against CPU reordering of the CQE fields, not against a device that wrote the CQE too early. Relaxed ordering enable bit: include/uapi/linux/pci_regs.h:PCI_EXP_DEVCTL_RELAX_EN.
Test to provoke it
CAUTION: toggle Device Control "Enable Relaxed Ordering" with setpci on an idle test device and run a verify workload with an analyzer attached; never on a system with data you care about.
V-14MSI-X sent before the CQE it announces DegradedNVMe interrupt
What happens
The interrupt MWr reaches the host before the CQE MWr (or there is no new CQE at all). The interrupt handler polls the CQ, finds nothing with the expected phase, and returns.
How it shows up
Spurious interrupts: Linux nvme_irq returns IRQ_NONE; if this happens very often the kernel's spurious-interrupt detector can disable the IRQ line ("nobody cared"), after which completions are found only by the timeout handler — then V-07(a) and "completion polled" messages. Before that point: extra latency, because the real CQE waits for the next interrupt.
Spec basis
NVMe Base: interrupts are generated for new CQ entries; PCI Express Base posted-write ordering ensures the MSI-X MWr cannot pass the earlier CQE MWr if the device sends them in order without RO.
Typical causes
Interrupt sent from a different internal engine than the CQE; interrupt coalescing logic counting submissions instead of completions; RO set on the MSI-X write.
How to detect / prove
Checker rule MSIX-NO-CQE: each MSI-X for vector v must be preceded by at least one new CQE on a CQ mapped to v since the previous MSI-X. On Linux, compare per-vector counts in /proc/interrupts with completions; spurious counts show in /proc/irq/<n>/spurious.
In a trace
MWr to the MSI-X address with no preceding CQE MWr; or CQE MWr timestamped after the MSI-X MWr.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_irq (returns IRQ_NONE when nvme_poll_cq finds nothing), nvme_irq_check for threaded interrupts.
Test to provoke it
Device-side bug; to validate the checker, use the synthetic trace in 7.6 (line with MSI-X at t=1500 ns).
V-15CQE posted but no MSI-X ever sent Timer onlyNVMe interrupt
What happens
The controller writes a CQE but never sends the interrupt (vector masked in the MSI-X table, wrong vector programmed in Create I/O CQ, function-mask bit set, or firmware bug).
How it shows up
Linux v7.2: the request times out; nvme_timeout polls the CQ, finds the completion and prints "I/O tag … QID … timeout, completion polled" — the signature of a lost interrupt. Latency equals the timeout (default 30 s for I/O).
Spec basis
NVMe Base: Create I/O Completion Queue Interrupt Vector (IV) and Interrupts Enabled (IEN) fields; PCI MSI-X table and Pending Bit Array semantics (a masked vector sets its pending bit instead of sending).
Typical causes
MSI-X vector masked during CPU hotplug or IRQ migration and never unmasked; IV out of range of the MSI-X table size; interrupt remapping (IOMMU) misconfiguration so the write is blocked.
How to detect / prove
Checker: CQE written, no MSI-X for the vector within a window (e.g. 1 ms) while IEN=1 for that CQ. Host-side: "completion polled" in dmesg; read the MSI-X PBA through the BAR (read-only inspection) to see pending bits.
In a trace
CQE MWr followed by silence; next activity is the host's Abort or controller reset seconds later.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_timeout; vector assignment in nvme_create_queue / queue_irq_offset.
Test to provoke it
EXPERT: mask a vector in the MSI-X table of a test device during I/O; expect "completion polled" and recovery.
V-16DMA to a command's buffer after its completion SilentNVMe / DMA
What happens
The controller writes to (or reads from) host memory belonging to a command after it has posted that command's CQE — for example the tail of the data for a read, or a retry of a data read for a write. By then the host may have freed or reused the buffer.
How it shows up
Random memory corruption elsewhere in the system (the page has been reallocated), IOMMU faults if the mapping was torn down (DMAR/AMD-Vi fault messages in dmesg naming the device), or nothing at all.
Spec basis
NVMe Base: posting the completion transfers ownership of the data buffers back to the host; PRP/SGL entries are valid only while the command is outstanding.
Typical causes
Same as V-13 (parallel DMA channels); Abort handling that completes the command while a DMA is still queued; firmware retry after timeout.
How to detect / prove
Checker rule DMA-NOCMD: any data MWr/MRd whose address belongs to a command that has already completed (and no newer command owns that address). With an IOMMU in strict mode, a late DMA produces a translation fault — strong host-side evidence.
In a trace
CQE for CID X followed by MWr TLPs into CID X's buffer range.
Linux v7.2 source
Unmapping on completion in drivers/nvme/host/pci.c:nvme_pci_complete_rq / nvme_pci_complete_batch.
Test to provoke it
Boot a test host with iommu.strict=1 (or the platform equivalent) and run high-QD mixed I/O; any IOMMU fault naming the SSD is a finding to correlate with a trace.

7.4 Command-Format Violations: PRP, SGL, MDTS, FUSE and Reserved Fields

V-17PRP1 not dword aligned, or PRP list entry with an offset ReportedNVMe command
What happens
PRP1 has bits 1:0 set, or an entry inside a PRP list (other than as allowed for the list pointer) has a non-zero page offset.
How it shows up
A checking controller completes the command with Generic status 13h "PRP Offset Invalid" (Linux NVME_SC_PRP_INVALID_OFFSET), usually with DNR. A non-checking controller DMAs to the wrong address — silent corruption of unrelated memory.
Spec basis
NVMe Base: PRP Entry format (offset field; dword alignment), PRP List rules; Generic Command Status "PRP Offset Invalid".
Typical causes
Host builds PRPs from CPU page size (e.g. 16 KiB or 64 KiB pages on arm64/ppc64) while the controller is configured with CC.MPS = 4 KiB, or vice versa; byte-granular user buffers passed through a passthrough interface.
How to detect / prove
Checker: decode DPTR, fetch the PRP list via the MRd/CplD that follows, and test each entry against the rules in the table above. Host-side: nvme error-log shows status 13h with the CID and SQID.
In a trace
SQE CplD with PRP1 low bits ≠ 0; or a PRP list read (MRd from the address in PRP2) returning entries with non-zero low 12 bits.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_pci_setup_data_prp builds PRP1 from the first segment's offset and list entries with NVME_CTRL_PAGE_SIZE stride; dma_set_min_align_mask(&pdev->dev, NVME_CTRL_PAGE_SIZE - 1) in probe keeps bounce buffers page-offset-preserving.
Test to provoke it
QEMU (SAFE): passthrough command with a crafted PRP list; expect status 13h and QEMU trace pci_nvme_err_invalid_prplist_ent.
V-18Offset in PRP2 when it is a data pointer ReportedNVMe command
What happens
The transfer needs exactly two pages (the remainder after PRP1's page fits in one page), so PRP2 is a data pointer; it must point at the start of a page but contains an offset.
How it shows up
Status 13h PRP Offset Invalid with DNR (QEMU and checking controllers). A lenient controller writes the second part of the data to PRP2 including the offset and then across the next page boundary — corrupting the neighbouring page.
Spec basis
NVMe Base: PRP Entry 2 semantics — data pointer vs PRP List pointer — and the zero-offset requirement for PRP entries other than PRP1 and the list pointer.
Typical causes
Host confusing "two-page transfer" with "list" case; off-by-one in computing whether the remainder fits in one page (e.g. using < instead of ≤).
How to detect / prove
Checker rule PRP2-OFFSET in 7.6: compute first = page − (PRP1 mod page); if first < len ≤ first + page then PRP2 mod page must be 0.
In a trace
8 KiB read with PRP1 = …1000h and PRP2 = …0010h; no PRP-list MRd follows; the controller either completes with 13h or writes data to …0010h onward.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_pci_setup_data_prp (the length <= NVME_CTRL_PAGE_SIZE branch places the second page directly in PRP2).
Test to provoke it
QEMU (SAFE): passthrough read of 8 KiB with PRP2 offset 10h; expect pci_nvme_err_invalid_prp2_align and status 13h.
V-19PRP list crossing or chaining rules broken ReportedNVMe command
What happens
The PRP list is laid out so that entries run past the end of the memory page that holds the list without using the last entry as a pointer to the next list page; or the last entry is used as a data pointer when more entries follow; or the list has fewer entries than the transfer needs.
How it shows up
The controller interprets a data page address as a list pointer (or vice versa): DMA to/from wrong memory, a Data Transfer Error (04h) if the access fails, or 13h when the misinterpreted entry happens to have an offset. Often silent.
Spec basis
NVMe Base: PRP List — a list occupies one memory page; when more entries are required, the last entry in the page is a pointer to the next PRP list.
Typical causes
List allocated from a pool not aligned to the controller page; driver computing entries per page from CPU page size; list allocated at an offset with the "entries per page" count not reduced accordingly (QEMU computes nents from the offset precisely because this is legal for the first list).
How to detect / prove
Checker walks the list exactly as nvme_map_prp does and compares the number of data bytes described with the command length (NLB+1 × LBA size, plus metadata if interleaved).
In a trace
MRd of the list spans a page boundary (e.g. starts at …FF8h with length 16 bytes); or a data MWr to an address that was read as a list entry pointing to the next list.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_pci_setup_data_prp chains when i == NVME_CTRL_PAGE_SIZE >> 3; NVME_MAX_NR_DESCRIPTORS (5) at the top of pci.c bounds the number of list pages per request.
Test to provoke it
QEMU (SAFE) user-space harness: 1 MiB transfer with a PRP list starting at offset FF0h of its page and no chaining; observe misbehaviour and whether status 13h is returned.
V-20Transfer longer than MDTS ReportedNVMe command
What happens
A command transfers more data than Maximum Data Transfer Size allows: MDTS (Identify Controller) is a power of two in units of the minimum memory page size (CAP.MPSMIN); 0 means no limit. MDTS = 5 with 4 KiB MPSMIN → 128 KiB.
How it shows up
QEMU and most controllers: Generic status 02h "Invalid Field in Command" with DNR. Some controllers transfer the data anyway (and may truncate silently).
Spec basis
NVMe Base: Identify Controller MDTS field; applies to the data transfer of a command (NVM Command Set defines how it applies to commands like Write Zeroes, which have no data transfer — they have separate limits such as WZSL in the NVM Command Set Identify Controller structure).
Typical causes
Passthrough tools ignoring MDTS; user-space drivers with hard-coded 1 MiB I/O; kernel limits overridden; MDTS reduced by a firmware update while the host cached the old value.
How to detect / prove
Checker rule MDTS in 7.6: (NLB+1)·LBA size (+ metadata if extended LBA) > 2MDTS·MPSMIN. Host: nvme id-ctrl /dev/nvme0 | grep mdts and cat /sys/block/nvme0n1/queue/max_hw_sectors_kb.
In a trace
SQE with NLB implying 256 KiB on a 128 KiB-MDTS controller; CQE status 02h, DNR=1; or, worse, 256 KiB of data MWr followed by success.
Linux v7.2 source
drivers/nvme/host/core.c:nvme_init_identify derives max_hw_sectors from id->mdts via nvme_mps_to_sectors; nvme_init_non_mdts_limits handles commands without data transfer.
Test to provoke it
QEMU (SAFE): -device nvme,mdts=5 then nvme io-passthru a 256 KiB read; expect status 02h and trace pci_nvme_err_mdts.
V-21Reserved fields non-zero SilentNVMe command
What happens
The host sets bits that are reserved in the SQE (for example CDW0 bits 13:10, CDW2–3 in commands that do not define them, reserved CDW10–15 bits) or in a data structure it passes (feature data, PRP list padding).
How it shows up
Today usually nothing — most controllers ignore reserved bits. Tomorrow, when a newer spec revision gives those bits a meaning, the same host software suddenly enables a feature it never intended (e.g. a bit that later became a "storage tag" or "directive" field). Some controllers return Invalid Field in Command. impl
Spec basis
NVMe Base conventions: reserved fields shall be cleared to 0 by the writer; receivers are generally not required to check. (Verify the exact wording for your revision in the spec.)
Typical causes
Uninitialised SQE memory (stack garbage) in user-space or firmware hosts; copying a command structure from a newer spec header to an older device.
How to detect / prove
Checker with a per-opcode mask of defined bits, generated from the spec revision the device claims in VS; flag any 1 outside the mask. Re-run the check against the masks of the next spec revision to spot "future meaning" hazards.
In a trace
SQE bytes 8–15 (CDW2–3) non-zero for an NVM Read on a namespace without end-to-end protection features that use them; CDW0 bits 13:10 ≠ 0.
Linux v7.2 source
Linux builds commands from a zeroed struct nvme_command (e.g. memset(&c, 0, sizeof(c)) in drivers/nvme/host/ioctl.c:nvme_user_cmd), so reserved fields are zero unless passthrough users set them via CDW fields.
Test to provoke it
SAFE on a scratch namespace: nvme io-passthru a read with a reserved CDW bit set; record whether the controller ignores it or returns 02h — a good conformance data point.
V-22FUSE field misuse (fused operations) ReportedNVMe command
What happens
FUSE (CDW0 bits 9:8): 01b = first command of a fused pair, 10b = second, 11b reserved. Violations: first without second; second without first; the two not in adjacent SQ slots; a non-fusable opcode (only Compare + Write is defined for the NVM Command Set); fused commands submitted to a controller that does not report support in Identify Controller FUSES; reserved value 11b.
How it shows up
Defined status codes: Generic 09h "Command Aborted due to Failed Fused Command" and 0Ah "Command Aborted due to Missing Fused Command" (Linux NVME_SC_FUSED_FAIL, NVME_SC_FUSED_MISSING), or 02h Invalid Field. QEMU returns Invalid Field (without DNR) for any FUSE value because it does not implement fused operations.
Spec basis
NVMe Base: Fused Operations; Identify Controller FUSES (Fused Operation Support); NVM Command Set: Compare and Write as the fused pair.
Typical causes
Host sets FUSE but the doorbell is rung between the two commands (so the controller fetches only the first); second command placed after a wrap without considering adjacency; garbage in CDW0.
How to detect / prove
Checker: for FUSE=01b at SQ slot k, require FUSE=10b at slot (k+1) mod N in the same doorbell batch; require FUSES bit 0 set; require opcodes 05h then 01h.
In a trace
SQ tail doorbell that makes slot k visible but not k+1; SQE with FUSE=01b followed by an unrelated opcode.
Linux v7.2 source
Linux does not issue fused commands (see the comment in drivers/nvme/host/fc.c: "Linux initiators don't send fused"); drivers/nvme/host/ioctl.c:nvme_user_cmd rejects passthrough commands with non-zero flags (-EINVAL), so FUSE/PSDT cannot be set from user space. Strings for 09h/0Ah are in drivers/nvme/host/constants.c.
Test to provoke it
Requires a user-space driver (SPDK-style, CAUTION on a scratch device): submit a lone FUSE=01b Compare; expect 0Ah or 02h.
V-23Admin command placed on an I/O queue (or vice versa) SilentNVMe command
What happens
Opcodes are interpreted per queue type: SQ 0 carries Admin opcodes; I/O SQs carry I/O command set opcodes. An admin opcode on an I/O queue is not an admin command — it is whatever I/O command shares that opcode value. Admin 01h Create I/O SQ becomes NVM Write; 02h Get Log Page becomes Read; 00h Delete I/O SQ becomes Flush; 09h Set Features becomes Dataset Management (possibly a deallocate!); 06h Identify, 0Ah Get Features, 10h Firmware Commit map to opcodes that are reserved or optional in the NVM set and normally return Invalid Command Opcode.
How it shows up
When the opcode collides with an implemented I/O command: nothing — the controller executes a real I/O with arguments taken from admin fields (CDW10 = PRP/feature data becomes SLBA/NLB…). Otherwise Generic status 01h "Invalid Command Opcode" with DNR.
Spec basis
NVMe Base: Admin command set vs I/O command sets; opcode tables per command set; Commands Supported and Effects log page.
Typical causes
Passthrough tool sending an admin opcode through the namespace I/O passthrough path (e.g. nvme io-passthru with an admin opcode); user-space driver queue-selection bug; test scripts copying opcode tables.
How to detect / prove
Checker: classify each SQE by queue id; for SQ ≠ 0 validate the opcode against the namespace's command set (Commands Supported and Effects log for that CSI); flag admin-only opcodes on I/O queues whose CDW layout looks like an admin command (e.g. NSID = 0 or FFFFFFFFh with opcode 09h). Then read back the affected LBAs.
In a trace
SQE on SQ 3 with opcode 09h and CDW10 = feature identifier-like value (e.g. 0000_0007h): the controller treats it as DSM with NR = 7 ranges and fetches a range list from PRP1.
Linux v7.2 source
QEMU dispatches by queue: nvme_process_sq calls sq->sqid ? nvme_io_cmd(n, req) : nvme_admin_cmd(n, req), and nvme_io_cmd_nvm rejects unsupported opcodes with NVME_INVALID_OPCODE | NVME_DNR. Linux: drivers/nvme/host/ioctl.c:nvme_cmd_allowed gates passthrough by opcode and capability.
Test to provoke it
CAUTION, scratch namespace only: nvme io-passthru /dev/nvme0n1 --opcode=0x06 … should return Invalid Command Opcode; never try opcodes 01h/09h on a namespace with data.
⚠️ Warning

Opcode collisions are the reason a mis-routed "harmless" admin command can destroy data. When a trace shows an admin-looking command on an I/O queue, treat it as a potential write or deallocate and verify the namespace contents.

V-24SGL descriptor rules broken ReportedNVMe command
What happens
Typical violations: PSDT selects SGL on an Admin command (not allowed for NVMe over PCIe); SGL used although Identify Controller SGLS reports no support; Segment / Last Segment descriptor length zero or not a multiple of 16; a Last Segment whose final descriptor is not a Data Block; a Segment descriptor inside a segment in a position other than last; total data block length smaller than the transfer, or larger without "excess length" support; reserved descriptor type; SGL Data Block with address + length overflowing 64 bits.
How it shows up
QEMU statuses (all with DNR): NVME_INVALID_SGL_SEG_DESCR (0Dh), NVME_INVALID_NUM_SGL_DESCRS (0Eh), NVME_DATA_SGL_LEN_INVALID (0Fh), NVME_SGL_DESCR_TYPE_INVALID (11h); metadata SGL length problems map to NVME_MD_SGL_LEN_INVALID; SGL on admin → Invalid Field. Linux names for the same generic codes: NVME_SC_SGL_INVALID_LAST 0Dh, _COUNT 0Eh, _DATA 0Fh, _METADATA 10h, _TYPE 11h, _OFFSET 16h, _GRANULARITY 1Eh.
Spec basis
NVMe Base: Scatter Gather List — descriptor types (Data Block, Bit Bucket, Segment, Last Segment, Keyed Data Block, Transport), SGLS field, PSDT; NVMe over PCIe transport: Admin commands use PRPs.
Typical causes
Host chaining segments like PRP lists; byte-granular buffers with SGLS "dword alignment required" bit ignored; descriptor arrays allocated without 16-byte alignment.
How to detect / prove
Checker walks SGL segments as QEMU's nvme_map_sgl does, including the "no forward progress" rule QEMU adds to stop pathological loops, and compares described length with the command length.
In a trace
SQE with PSDT=01b on SQ 0; MRd of a segment whose length field is 24 bytes; CQE status 0Dh/0Fh with DNR.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_pci_use_sgls uses SGLs only when nvmeq->qid ≠ 0 and the controller supports them (forced for page gaps, user commands, multiple integrity segments); nvme_pci_setup_data_sgl; module parameter sgl_threshold (default 32 KiB).
Test to provoke it
QEMU (SAFE): QEMU supports SGLs; a user-space harness can send a Last Segment ending with a Segment descriptor and observe 0Dh.
V-25Illegal queue creation parameters ReportedNVMe admin
What happens
Create I/O SQ/CQ with: QID 0 or beyond the granted number of queues, or already in use; SQ referencing a CQ that does not exist; QSIZE 0 or greater than CAP.MQES; non-contiguous queue (PC=0) on a controller with CAP.CQR=1; queue base not page aligned; interrupt vector beyond the MSI-X table.
How it shows up
Command Specific status: Completion Queue Invalid (00h), Invalid Queue Identifier (01h), Invalid Queue Size (02h), Invalid Interrupt Vector (08h); or Generic PRP Offset Invalid / Invalid Field. QEMU nvme_create_sq returns NVME_INVALID_CQID, NVME_INVALID_QID, NVME_MAX_QSIZE_EXCEEDED, NVME_INVALID_PRP_OFFSET, NVME_INVALID_FIELD (PC=0) — all with DNR.
Spec basis
NVMe Base: Create I/O Submission Queue and Create I/O Completion Queue commands; CAP.MQES (0's based), CAP.CQR.
Typical causes
QSIZE passed as 1's based; ignoring MQES on small embedded controllers; physically discontiguous queue memory on a controller without PRP-list queue support.
How to detect / prove
Checker validates Create commands against CAP (read during init — capture from controller enable) and the queue count granted in the Set Features Number of Queues CQE (DW0).
In a trace
Admin SQE opcode 01h/05h with CDW10 QSIZE > MQES; CQE with SCT=1 (Command Specific) and SC=02h.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_create_queue and the adapter helpers it calls; queue depth clamped against MQES during nvme_pci_enable.
Test to provoke it
QEMU (SAFE): nvme admin-passthru Create I/O SQ with QSIZE beyond MQES on an unused QID; expect status 0102h (SCT 1, SC 02h) in QEMU's encoding.
