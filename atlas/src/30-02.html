3.2 NVMe Time Limits: Ready, Shutdown, Keep Alive, Abort, Activation and Friends

The NVM Express (NVMe) specification bounds time in two ways. Some limits are registers or Identify fields the controller advertises (CAP.TO, CRTO, RTD3E, MTFA, EDSTT, ANATT, CRDT, power state latencies); the host is expected to wait at least that long and may declare the controller failed afterwards. Others are timers the controller runs on the host (the Keep Alive Timer). The cards below cover each one. For the controller-state cards it helps to keep the register handshake in mind:

  host writes CC.EN=1  ---------->  controller initialises  ----> CSTS.RDY=1     (bounded by CAP.TO or CRTO)
  host writes CC.EN=0  ---------->  controller resets       ----> CSTS.RDY=0     (bounded by CAP.TO)
  host writes CC.SHN=01b -------->  controller flushes      ----> CSTS.SHST=10b  (typical time RTD3E; host picks the limit)
  host stops sending Keep Alive -->  KATO expires           ----> controller treats host as gone
📘 Units cheat-sheet

CAP.TO and CRTO: 500 ms units. MTFA and CRDT: 100 ms units. KAS (keep-alive granularity): 100 ms units. KATO value: milliseconds. RTD3E, RTD3R, ENLAT, EXLAT: microseconds. EDSTT: minutes. ANATT and the Sanitize estimates: seconds. Timestamp: milliseconds since 1 January 1970 (48 bits). Getting the unit wrong is itself a common bug: a CAP.TO of 20 means 10 s, not 20 s.

T-02CSTS.RDY does not become 1 within CAP.TO after CC.EN=1Timer onlyNVMe controller register
What happens
The host enables the controller (CC.EN 0→1) and polls CSTS.RDY. The controller stays not-ready for longer than the worst-case time it advertised in CAP.TO.
How it shows up
No status at all; only a host timer. Linux v7.2 prints Device not ready; aborting initialisation, CSTS=0x0 and the probe or reset fails with -ENODEV. If CSTS reads 0xffffffff the loop exits immediately with -ENODEV (device gone from the bus).
Spec basis
NVMe Base: CAP.TO (bits 31:24) is the worst-case time, in 500 ms units, the host should wait for CSTS.RDY to change after CC.EN changes. Maximum 0xFF = 127.5 s.
Typical causes
Firmware boot slower than advertised (e.g. large mapping-table rebuild after unsafe shutdown); media or NAND not responding; CAP.TO set too small by firmware; controller waiting on a dependency (power, clocks, PERST# timing); host started polling before the device was out of reset.
How to detect / prove
Measure: dmesg -T timestamps of driver bind vs failure; with an analyzer, find the MWr to CC (offset 14h) and the last MRd of CSTS (offset 1Ch) and compare the gap with CAP.TO×500 ms. Read CAP with nvme show-regs /dev/nvme0 (read-only) and decode bits 31:24.
In a trace
A long string of MRd to BAR0+1Ch, each CplD returning RDY=0, starting just after the MWr to BAR0+14h with EN=1. Nothing else from the device. Gaps of 1–2 ms between polls (Linux sleeps 1–2 ms per loop).
Linux v7.2 source
drivers/nvme/host/core.c:nvme_enable_ctrl() computes the limit as (CAP.TO + 1) / 2 seconds and calls nvme_wait_ready(), which polls every 1–2 ms (usleep_range(1000, 2000)), aborts on fatal signal, and fails with -ENODEV on timeout or CSTS = ~0.
Test to provoke it
In QEMU, CAP.TO is 0Fh (7.5 s) in hw/nvme/ctrl.c; patch the model to delay setting RDY beyond that. On hardware, force an unsafe power cut during heavy writes (CAUTION: data-loss risk on that drive) and time the next initialisation against CAP.TO.
T-03CRTO inconsistent with CAP.TO, or media not ready in timeTimer onlyNVMe controller register
What happens
Controllers that support Controller Ready Modes (CAP.CRMS) report two timeouts in the CRTO register: CRWMT (ready with media) and CRIMT (ready independent of media). If CRWMT is smaller than CAP.TO, or the media is not ready within CRWMT, the host either waits too little or gives up.
How it shows up
Linux v7.2 logs once bad crto:<value> cap:<value> when CRWMT < CAP.TO and falls back to CAP.TO. If the controller then still misses the deadline, the T-02 message appears. When CC.CRIME=1 is used by a host, media commands issued too early complete with Admin Command Media Not Ready (generic 24h) or Namespace Not Ready (82h).
Spec basis
NVMe Base 2.x: CAP.CRMS (CRWMS bit 59, CRIMS bit 60), CC.CRIME (bit 24), CRTO register at offset 68h with CRWMT (bits 15:0) and CRIMT (bits 31:16), both in 500 ms units.
Typical causes
Firmware fills CRTO but forgets that CAP.TO must stay consistent; large-capacity drives whose media becomes ready much later than the controller.
How to detect / prove
nvme show-regs to read CAP and CRTO; compare CRWMT with CAP.TO. In dmesg, look for bad crto. Time the CC.EN→RDY gap on an analyzer.
In a trace
Same as T-02. With CRIME=1, an early Identify or Read completes quickly but with SC 24h or 82h; a correct device sets RDY late instead.
Linux v7.2 source
core.c:nvme_enable_ctrl() reads NVME_REG_CRTO if NVME_CAP_CRMS_CRWMS, uses the larger of CAP.TO and CRWMT, and always clears NVME_CC_CRIME ("Until the driver is restructured to handle retries, disable CC.CRIME").
Test to provoke it
QEMU or a device simulator: set CAP.CRMS and an inconsistent CRTO; check for the bad crto warning. SAFE.
T-04CSTS.RDY does not return to 0 after CC.EN=0 (reset hangs)Timer onlyNVMe controller register
What happens
To reset, the host clears CC.EN and waits for CSTS.RDY to go to 0. The controller keeps RDY=1 beyond CAP.TO, so the reset cannot proceed and the controller cannot be re-enabled.
How it shows up
Linux v7.2: Device not ready; aborting reset, CSTS=0x1; the controller is then marked dead and its namespaces are removed. Every outstanding I/O fails.
Spec basis
NVMe Base: after CC.EN 1→0 the controller shall bring CSTS.RDY to 0 within CAP.TO. Some devices need an extra delay before the host starts checking RDY (see NVME_QUIRK_DELAY_BEFORE_CHK_RDY).
Typical causes
Firmware stuck in the very operation that caused the reset (a hung command, a media operation that cannot be interrupted); internal deadlock; PCIe link lost (CSTS reads all-ones instead, a different failure).
How to detect / prove
dmesg shows the "aborting reset" line after a timeout or nvme reset. Analyzer: MWr CC with EN=0, then MRd CSTS returning RDY=1 for longer than CAP.TO×500 ms. Check whether the device sent any TLPs in between (DMA still running after EN=0 is itself a bug).
In a trace
MWr BAR0+14h (EN=0) → repeated MRd BAR0+1Ch, CplD RDY=1. A correct device may keep DMA quiet and drops RDY within milliseconds.
Linux v7.2 source
core.c:nvme_disable_ctrl(ctrl, false): optional msleep(NVME_QUIRK_DELAY_AMOUNT) (2300 ms), then nvme_wait_ready(ctrl, NVME_CSTS_RDY, 0, (NVME_CAP_TIMEOUT(cap)+1)/2, "reset"). Note: v7.2 uses CAP.TO, not CRTO, for the disable direction.
Test to provoke it
Issue nvme reset /dev/nvme0 while a vendor debug hook keeps the firmware busy, or during a long Format. CAUTION: may leave the drive needing a power cycle.
T-05Shutdown not complete (CSTS.SHST ≠ 10b) before power is removedTimer onlyNVMe controller register
What happens
At power-off, suspend or driver unload the host writes CC.SHN=01b (normal shutdown) and waits for CSTS.SHST=10b (shutdown processing complete). If the controller takes longer than the host waits, power may be removed while the write cache and mapping tables are still being saved.
How it shows up
Linux v7.2: Device not ready; aborting shutdown, CSTS=0x.... At the next boot the drive's SMART / Health log Unsafe Shutdowns counter has increased, and initialisation may be slower (rebuild), possibly exceeding CAP.TO (T-02).
Spec basis
NVMe Base: CC.SHN (01b normal, 10b abrupt), CSTS.SHST (00b normal operation, 01b processing, 10b complete). Identify Controller RTD3E gives the typical time in microseconds to enter Runtime D3 (shutdown); RTD3R the expected resume time.
Typical causes
Large volatile cache to flush; RTD3E under-reported; host value too small (Linux default 5 s); platform cuts power on a fixed timer regardless of SHST.
How to detect / prove
nvme smart-log /dev/nvme0 before and after a clean reboot: unsafe_shutdowns must not increase. nvme id-ctrl /dev/nvme0 | grep -i rtd3 for RTD3E. dmesg for D3 entry latency set to N seconds (Linux applied RTD3E) and for the aborting-shutdown line.
In a trace
MWr CC with SHN=01b; MRd CSTS polls with SHST=01b; the series ends (power removed or host gives up) without a CplD showing SHST=10b.
Linux v7.2 source
core.c:nvme_init_identify() sets ctrl->shutdown_timeout = clamp(RTD3E/1e6, shutdown_timeout, 60) seconds; module parameter nvme_core.shutdown_timeout (default 5). nvme_disable_ctrl(ctrl, true) sets NVME_CC_SHN_NORMAL and waits for NVME_CSTS_SHST_CMPLT.
Test to provoke it
Fill the write cache (sustained writes with volatile write cache on), then reboot and compare unsafe_shutdowns. Try nvme_core.shutdown_timeout=1 on a test machine to see how a too-short host limit shows up. CAUTION: risk of losing cached data on that drive.
T-06Resume from runtime D3 slower than RTD3RDegradedNVMe power management
What happens
After a runtime-D3 or system suspend, the controller takes much longer to resume than the RTD3R value it advertises. Nothing fails, but the first I/O after resume stalls.
How it shows up
No error. Applications see a multi-second stall after resume; if it exceeds CAP.TO the re-enable fails (T-02). dmesg timestamps between resume start and the controller becoming live show the gap.
Spec basis
NVMe Base: Identify Controller RTD3R (Runtime D3 Resume Latency, µs, expected) and RTD3E (entry latency). These are informational: the host uses them to decide whether runtime D3 is worth it.
Typical causes
Mapping table reload from NAND; firmware re-training of internal components; platform delays on the PCIe side (D3cold power ramp, link training, see T-40 and T-41).
How to detect / prove
Measure with dmesg -T or ftrace on the PM callbacks (pci_pm_resume, nvme_resume) and compare with nvme id-ctrl RTD3R. Run fio with latency logging across a suspend cycle.
In a trace
Power-up and link training, config reads (possibly RRS), then MWr CC EN=1 and a long CSTS polling series.
Linux v7.2 source
Linux v7.2 does not use RTD3R in the NVMe host driver (only RTD3E, for the shutdown timeout). Resume paths: pci.c:nvme_resume(), core.c:nvme_enable_ctrl().
Test to provoke it
rtcwake -m mem -s 10 on a laptop with a fio latency log running. SAFE.
T-07Keep Alive Timer expires in the controllerTimer onlyNVMe over Fabrics
What happens
The host sets a Keep Alive Timeout (KATO) at connect time or via Set Features (FID 0Fh). If the controller does not receive a Keep Alive command (or, with Traffic Based Keep Alive, any command) within KATO, it concludes the host is gone.
How it shows up
On the controller: the association is torn down, outstanding commands may complete with Keep Alive Timer Expired (generic status 19h) and the host's resources (reservations held by the host, queues) are released. On the host: the transport connection drops, the controller goes to RESETTING/CONNECTING and reconnects (T-28).
Spec basis
NVMe Base: Keep Alive command (admin opcode 18h); Keep Alive Timer feature (FID 0Fh), KATO in milliseconds; Identify Controller KAS = timer granularity in 100 ms units; CTRATT.TBKAS = Traffic Based Keep Alive support. The host should send Keep Alive at a rate that allows for round-trip time (Linux comment quotes "at half of the Keep Alive Timeout").
Typical causes
Host CPU starvation or a stalled admin queue (the Keep Alive itself is queued behind blocked admin commands); network congestion or packet loss; a target that processes admin commands slowly; KATO set close to the network RTT.
How to detect / prove
Host dmesg: reconnect messages, long keepalive RTT (N ms). Target-side logs (e.g. Linux nvmet prints keep-alive expiry). Packet capture: interval between Keep Alive capsules (admin opcode 18h) versus KATO.
In a trace
TCP/RDMA capture: Keep Alive command capsules every KATO/2 (or KATO/4 with TBKAS in Linux); before the failure the gap grows to ≥ KATO, then the target closes the connection (TCP FIN/RST or RDMA disconnect).
Linux v7.2 source
core.c:nvme_keep_alive_work_period() = KATO/2 (halved again if TBKAS); nvme_keep_alive_work() sends the command with rq->timeout = kato * HZ; fabrics.c:nvmf_parse_options() defaults KATO to NVME_DEFAULT_KATO (5 s) for I/O controllers; fabrics.c:nvmf_connect_cmd_prep() puts KATO×1000 into the Connect command.
Test to provoke it
nvme-tcp to a Linux nvmet target; add delay with tc qdisc add dev eth0 root netem delay 3000ms on the host (CAUTION: affects all traffic on that interface). Watch the target drop the association after KATO.
T-08Keep Alive command itself slow or failing (host side)Timer onlyNVMe over Fabrics
What happens
The host's Keep Alive command takes most of the keep-alive period to complete, or fails. The host cannot keep the controller's timer refreshed in time.
How it shows up
Linux v7.2 warns long keepalive RTT (N ms) when the round trip exceeds the work period, and failed nvme_keep_alive_end_io error=N on failure. If the request cannot even be allocated: keep-alive failed: N followed by a controller reset.
Spec basis
NVMe Base Keep Alive; the host-side scheduling is implementation policy.
Typical causes
Reserved admin tags exhausted; admin queue blocked by long commands (Format, Sanitize start, Firmware Commit); network latency; target overloaded.
How to detect / prove
dmesg | grep -i keepalive; trace with nvme_setup_cmd/nvme_complete_rq tracepoints (/sys/kernel/tracing/events/nvme) filtering admin opcode 0x18.
In a trace
Keep Alive capsule sent on time; the response capsule arrives late.
Linux v7.2 source
core.c:nvme_keep_alive_end_io() subtracts the measured RTT from the next delay and logs the warning; nvme_keep_alive_work() resets the controller if blk_mq_alloc_request() fails. A Set Features KATO passed through user space is applied by nvme_update_keep_alive() ("keep alive interval updated from ... ms to ... ms").
Test to provoke it
Same netem setup as T-07, with delays between KATO/2 and KATO. SAFE on a lab network.
T-09Abort does not abort (or cannot be sent)Timer onlyNVMe admin command
What happens
After an I/O timeout the host sends Abort (admin 08h) naming the SQID and CID. Abort is best-effort: the controller may complete it without aborting anything, or the host may have no Abort credits left.
How it shows up
Abort CQE Dword 0 bit 0 = 1 means "command not aborted". Linux v7.2 logs only Abort status: 0x0 and does not inspect Dword 0; it relies on the second timeout to reset. If more Aborts are outstanding than ACL+1, the controller returns Abort Command Limit Exceeded (103h); Linux avoids that by keeping its own budget and simply re-arming the timer.
Spec basis
NVMe Base: Abort command; Identify Controller ACL (0's based; the specification recommends 3, i.e. four concurrent Aborts); command-specific status 103h; an aborted command completes with Command Abort Requested (generic 07h).
Typical causes
Firmware cannot locate the command (already inside the media pipeline); controller ignores Abort entirely; Abort itself stuck behind the hung command on the admin queue.
How to detect / prove
Analyzer: Abort SQE fetched from the admin SQ, its CQE written with DW0 bit 0 = 1, and no CQE for the target CID. dmesg: "aborting" followed ~io_timeout later by "reset controller" for the same tag.
In a trace
CQE for Abort (SQID 0) with DW0=00000001h; no completion with SC 07h for the victim CID.
Linux v7.2 source
pci.c:nvme_timeout(): atomic_dec_return(&dev->ctrl.abort_limit) (initialised to ACL+1 in core.c:nvme_init_identify()), sets IOD_ABORTED, sends Abort with abort_endio(); a second timeout on an IOD_ABORTED request resets. QEMU hw/nvme/ctrl.c:nvme_abort() sets result=1 by default and only reports 0 when it aborts an AER.
Test to provoke it
QEMU with a stalled backend (e.g. a blkdebug or throttled image) and a low io_timeout; watch the Abort CQE result. SAFE.
T-10Firmware activation takes longer than MTFATimer onlyNVMe admin / firmware
What happens
Firmware Commit with activation without reset pauses command processing (CSTS.PP=1) while the new image starts. If the pause lasts longer than MTFA, every I/O on the host stalls for that time and the host may reset the controller.
How it shows up
Linux v7.2: Fw activation timeout, reset controller. Applications see an I/O pause of up to MTFA (or up to admin_timeout when MTFA=0). If the controller knows activation would exceed MTFA it should refuse up front with Firmware Activation Requires Maximum Time Violation (command-specific 112h).
Spec basis
NVMe Base: Identify Controller MTFA (100 ms units); CSTS.PP (Processing Paused, bit 5); Firmware Activation Notice asynchronous event; status 112h.
Typical causes
New firmware image with longer init; image upgrade that migrates internal data structures; MTFA left at an optimistic value.
How to detect / prove
nvme id-ctrl | grep -i mtfa; run fio with --write_lat_log during nvme fw-commit -a 3 and measure the pause; analyzer: CSTS MRd showing PP=1 and its duration.
In a trace
AER completion (Notice: Firmware Activation Starting), then CSTS reads with PP=1; device sends no CQEs until PP clears.
Linux v7.2 source
core.c:nvme_fw_act_work(): quiesces I/O queues, polls nvme_ctrl_pp_status() every 100 ms until mtfa * 100 ms (or admin_timeout seconds if MTFA=0), then nvme_try_sched_reset().
Test to provoke it
Activate a firmware image with commit action 3 (activate without reset) under load. EXPERT: firmware updates can brick a drive; use vendor-approved images only.
T-11Format NVM outlasts the host admin timeoutTimer onlyNVMe admin command
What happens
Format NVM (80h) runs synchronously: the CQE is posted when the format is done. On a large drive or with Secure Erase Settings = user data erase, that can take minutes. The host's admin timeout (60 s in Linux) fires first.
How it shows up
Linux v7.2 times out an admin command and goes straight to reset: I/O tag N (....) opcode 0x80 (Format NVM) QID 0 timeout, reset controller. The reset interrupts the format; afterwards the namespace may report Format In Progress (84h) or be unusable until a new format.
Spec basis
NVMe Base: Format NVM has no advertised duration. Commands to the affected namespace during the format complete with Format In Progress (84h). FNA in Identify Controller describes the scope of a format/secure erase.
Typical causes
Using the default admin timeout for a long operation; tools that do not pass a longer timeout.
How to detect / prove
dmesg line with opcode 0x80 on QID 0. Pass an explicit timeout: nvme format /dev/nvme0n1 --timeout=600000 (milliseconds; check your nvme-cli version's default).
In a trace
Format SQE fetched from the admin SQ; no CQE; 60 s later a CC.EN=0 write (reset).
Linux v7.2 source
pci.c:nvme_timeout(): if (!nvmeq->qid || ...) → reset for any admin-queue timeout, no Abort. Passthrough timeout: ioctl.c uses cmd.timeout_ms when non-zero.
Test to provoke it
Format a large namespace with SES=1 with --timeout=60000 on a lab drive. EXPERT/DESTRUCTIVE: erases all data on the namespace.
T-12Sanitize runs far longer than its estimate (or never finishes)DegradedNVMe admin / background
What happens
Sanitize (84h) completes immediately and the operation continues in the background. The controller publishes estimated durations in the Sanitize Status log. If the operation takes much longer than estimated, or SPROG stops moving, the drive is unusable for that time and no timer fires.
How it shows up
No error. Most I/O and many admin commands fail with Sanitize In Progress (generic 1Dh) for the whole duration. Sanitize Status log: SSTAT = in progress, SPROG (numerator over 65536) stuck. On failure SSTAT reports "failed" and later commands get Sanitize Failed (1Ch).
Spec basis
NVMe Base: Sanitize Status log (LID 81h) fields SPROG, SSTAT, SCDW10, ETO, ETBE, ETCE and the No-Deallocate variants ETOND, ETBEND, ETCEND (seconds; 0 = completes in the background when the command completes; FFFFFFFFh = not reported). A sanitize continues across resets and power cycles.
Typical causes
Block erase on a drive with many bad blocks; overwrite passes; firmware estimate based on a different capacity; firmware hang.
How to detect / prove
Poll nvme sanitize-log /dev/nvme0 and record SPROG versus time; compare the elapsed time with the relevant estimate. A tool should flag "elapsed > k × estimate" (pick k, e.g. 2).
In a trace
Sanitize SQE and an immediate success CQE; afterwards periodic Get Log Page (02h, LID 81h) from the host; I/O CQEs with SC 1Dh.
Linux v7.2 source
Linux v7.2 has no Sanitize timer; the CQE arrives quickly. The driver records failures in passthrough logs only.
Test to provoke it
nvme sanitize /dev/nvme0 -a 2 (block erase) and poll the log. EXPERT/DESTRUCTIVE: erases the whole NVM subsystem's user data.
T-13Device self-test exceeds EDSTT (or short test exceeds its limit)DegradedNVMe admin / background
What happens
Device Self-test (admin 14h) runs in the background. The extended test should finish in about EDSTT minutes; the short test has a fixed upper bound in the specification. A test that keeps running hides a slow or failing internal component.
How it shows up
No error while it runs; a second self-test request gets Device Self-test In Progress (command-specific 11Dh). The Device Self-test log shows Current Operation and Current Completion percentage. The final result entry records abort reasons or a failing segment.
Spec basis
NVMe Base: Identify Controller EDSTT (minutes, extended test in power state 0); short self-test time limit (two minutes in NVMe Base; verify in your spec revision); Device Self-test log (LID 06h).
Typical causes
Media with many weak blocks; self-test throttled by host I/O (allowed); thermal throttling (T-49).
How to detect / prove
Start nvme device-self-test /dev/nvme0 -s 2; poll nvme self-test-log /dev/nvme0 and compare elapsed time with nvme id-ctrl | grep edstt.
In a trace
Self-test SQE and fast CQE; periodic Get Log Page LID 06h.
Linux v7.2 source
Linux v7.2 does not time self-tests; the command completes immediately.
Test to provoke it
Run the extended test idle and again under full fio load; compare durations. SAFE (self-test is non-destructive by definition; still avoid on production drives).
T-14Power-state exit slower than EXLAT (latency spike after idle)DegradedNVMe power management
What happens
With Autonomous Power State Transition (APST) the controller drops into non-operational power states after an idle period. The first command after idle waits for the exit. If the real exit latency exceeds the advertised EXLAT, the host's latency budget is broken without any error.
How it shows up
No error. A periodic latency outlier on the first I/O after idle (often tens of milliseconds). Linux excludes states whose EXLAT > ps_max_latency_us, so a device that under-reports EXLAT defeats that protection.
Spec basis
NVMe Base: Power State Descriptor ENLAT/EXLAT (µs, 0 = not reported), NON-OP flag; Autonomous Power State Transition feature (FID 0Ch) entries with Idle Time Prior to Transition (ms) and Idle Transition Power State; Identify Controller APSTA, NPSS.
Typical causes
Firmware under-reports EXLAT; platform adds PCIe L1/L1.2 exit on top (T-45, T-46); host idle timeout too short (thrashing between states).
How to detect / prove
nvme id-ctrl -H /dev/nvme0 for power state table; nvme get-feature -f 0x0c -H /dev/nvme0 for the APST table Linux programmed; fio with --thinktime larger than the idle time, recording clat; compare outlier size with EXLAT. Disable APST (nvme_core.default_ps_max_latency_us=0) to confirm the outliers disappear.
In a trace
Idle period on the link (probably in L1), then doorbell MWr; the device's first SQE fetch MRd arrives late (exit time). An analyzer that shows link power states will show L1 exit first.
Linux v7.2 source
core.c:nvme_configure_apst() walks states from deepest up, skips states with exit_lat > ps_max_latency_us or quirked deepest, uses apst_primary_timeout_ms (100 ms) for states with total latency ≤ 15 ms and apst_secondary_timeout_ms (2000 ms) for ≤ 100 ms; without those parameters it uses (ENLAT+EXLAT)/20 ms ("50 × (enlat + exlat) microseconds"). Per-device limit via PM QoS (/sys/class/nvme/nvme0/power/pm_qos_latency_tolerance_us, nvme_set_latency_tolerance()).
Test to provoke it
Sweep fio --thinktime across the APST idle times and plot first-I/O latency. SAFE.
T-15Controller never wakes from a deep power state (falls off the bus)Timer onlyNVMe power / PCIe
What happens
After entering a deep non-operational state (often combined with PCIe ASPM L1 substates), the device fails to come back: config and MMIO reads return all-ones.
How it shows up
The next I/O times out (30 s). Linux v7.2 then reads CSTS = 0xffffffff and prints controller is down; will reset: CSTS=0xffffffff, PCI_STATUS=0x... followed by Does your device have a faulty power saving mode enabled? and Try "nvme_core.default_ps_max_latency_us=0 pcie_aspm=off pcie_port_pm=off" and report a bug. The reset usually fails and the namespace disappears.
Spec basis
NVMe Base APST and power states; PCIe ASPM and L1 PM substates. No timer in either spec catches this; only the host I/O timer does.
Typical causes
Firmware bugs in the deepest power state; platform BIOS/ACPI problems; L1.2 timing parameters wrong (T-46). Linux carries DMI-based quirks for specific laptop/board and SSD combinations (Samsung SM951/PM951 on Dell XPS 15 9550, Samsung 960 EVO on some ASUS boards, a Lenovo N60z board).
How to detect / prove
The all-ones CSTS line in dmesg. Reproduce with APST disabled (default_ps_max_latency_us=0) and with ASPM off; if the problem disappears, it is a power-state exit failure. lspci -vvv after the event: "Unknown header type 7f" or all-ones config space means the device is gone.
In a trace
Link enters L1/L1.2 during idle; on the next doorbell, the root port starts exit but the link never returns to L0 (LTSSM goes to Detect) or the endpoint does not respond; root port logs a Completion Timeout or Surprise Down.
Linux v7.2 source
pci.c:nvme_warn_reset() prints the hints; pci.c:check_vendor_combination_bug() returns NVME_QUIRK_NO_DEEPEST_PS or NVME_QUIRK_NO_APST by DMI; core.c quirk table entries for specific models.
Test to provoke it
Idle the system for long periods (hours) with APST and ASPM enabled, polling with a cron job that issues one read every N minutes. SAFE, but may require a power cycle to recover.
T-16Host Memory Buffer missing or disabled: DRAM-less drive becomes slowDegradedNVMe feature
What happens
DRAM-less SSDs ask the host for a Host Memory Buffer (HMB) to cache mapping tables. If the host gives less than requested, or disables the HMB (for example across suspend), the drive keeps working but random-access latency rises.
How it shows up
No error. Linux may log min host memory (N MiB) above limit (128 MiB). and run without HMB, or failed to allocate host memory buffer. ("controller must work without HMB"). Random 4 KiB reads get markedly slower; the effect is device-specific.
Spec basis
NVMe Base: Host Memory Buffer feature (FID 0Dh); Identify Controller HMPRE (preferred size) and HMMIN (minimum), both in 4 KiB units, HMMINDS, HMMAXD.
Typical causes
Host limit lower than HMMIN; memory fragmentation; host disables HMB on suspend and the drive has to rebuild its cache on resume.
How to detect / prove
dmesg | grep -i "host memory"; nvme get-feature -f 0x0d -H /dev/nvme0 shows whether HMB is enabled; sysfs /sys/class/nvme/nvme0/hmb (present when HMPRE ≠ 0). Compare fio random-read latency with and without HMB.
In a trace
With HMB the device issues MRd/MWr to host memory addresses inside the HMB descriptor list during I/O; without it those accesses disappear and NAND reads per I/O increase (not visible on PCIe).
Linux v7.2 source
pci.c:nvme_setup_host_mem() caps the size at max_host_mem_size_mb (module parameter, default 128); pci.c:nvme_suspend() calls nvme_set_host_mem(ndev, 0) before suspend ("Host memory access may not be successful in a system suspend state").
Test to provoke it
Load nvme with max_host_mem_size_mb=0 on a DRAM-less drive and compare 4 KiB random-read latency. SAFE.
T-17Command Retry Delay ignored, missing or too longReportedNVMe command status
What happens
A controller can ask the host to wait before retrying: it sets the CRD field in the CQE status (1–3) and the host waits CRDT1/2/3 × 100 ms. If CRDT is zero while CRD is used, the host retries instantly and burns its retry budget; if CRDT is very large, every retry adds seconds of latency.
How it shows up
Completions with DNR=0 and a non-zero CRD (e.g. Namespace Not Ready 82h, Command Interrupted 21h). With Linux, each retry increments command_retries_count in sysfs; after max_retries (5) the error reaches the application.
Spec basis
NVMe Base: CQE Status field CRD (bits 12:11 of the status word as Linux stores it, mask 0x1800); Identify Controller CRDT1–CRDT3 (100 ms units); Host Behavior Support feature (FID 16h) ACRE bit enables the mechanism.
Typical causes
Firmware returning CRD before the host enabled ACRE; CRDT left at 0; CRDT set to many seconds for a transient condition.
How to detect / prove
Tracepoint nvme:nvme_complete_rq shows status and retries; nvme id-ctrl | grep -i crdt; nvme get-feature -f 0x16 -H for ACRE.
In a trace
CQE with status CRD≠0, then (after the delay) the same command resubmitted with a new CID.
Linux v7.2 source
core.c:nvme_retry_req(): delay = ctrl->crdt[crd - 1] * 100 ms, then blk_mq_delay_kick_requeue_list(); nvme_configure_host_options() sets ACRE only when CRDT1 ≠ 0; nvme_decide_disposition() stops retrying on DNR or retries >= nvme_max_retries.
Test to provoke it
QEMU or a target with a hook returning 82h with CRD=1; vary CRDT1 and measure added latency. SAFE.
T-18Namespace stays "not ready" longer than the host retriesReportedNVMe command status
What happens
After a reset, resume or capacity change, the namespace answers with Namespace Not Ready (82h) or Admin Command Media Not Ready (24h) for longer than the host is willing to retry.
How it shows up
First a few retried commands, then I/O errors reported to the application (blk_update_request: I/O error-style messages, the NVMe status in nvme_log_error() output).
Spec basis
NVMe Base: generic status 82h (Namespace Not Ready, retry allowed when DNR=0) and 24h (Admin Command Media Not Ready, used with CC.CRIME=1).
Typical causes
Media initialisation slower than the controller ready time; controller sets RDY too early; host retry budget (5 × CRDT) shorter than the real wait.
How to detect / prove
dmesg NVMe error lines with status 0x82; /sys/block/nvme0n1/device/.../command_retries_count; correlate with time since controller enable.
In a trace
Repeated I/O CQEs with SC 82h shortly after CSTS.RDY=1, each resubmitted, last one returned to the host as error.
Linux v7.2 source
core.c:nvme_decide_disposition(), nvme_retry_req(), nvme_error_status() maps the status to a block error. CRIME is kept off in nvme_enable_ctrl(), which avoids most 24h cases.
Test to provoke it
Power-cycle a large drive after an unsafe shutdown and start I/O immediately when the block device appears. CAUTION.
T-19ANA transition exceeds ANATTTimer onlyNVMe multipath (ANA)
What happens
In Asymmetric Namespace Access (ANA), a group can report the "change" state while it moves between optimized, non-optimized and inaccessible. ANATT is the maximum time the controller promises to stay in that state. If it stays longer, the host cannot use the path.
How it shows up
Linux v7.2 arms a timer at 2 × ANATT when any group is in change state; on expiry: ANATT timeout, resetting controller. I/O on that path completes with ANA Transition (path-related status 303h) and is failed over.
Spec basis
NVMe Base: Identify Controller ANATT (seconds), ANACAP; ANA log page; path-related statuses ANA Persistent Loss 301h, ANA Inaccessible 302h, ANA Transition 303h.
Typical causes
Target failover taking longer than declared (storage array controller takeover); target bug that never leaves change state.
How to detect / prove
nvme ana-log /dev/nvme0 repeatedly; sysfs ana_state per namespace path; dmesg for the ANATT line; multipath_failover_count in sysfs.
In a trace
Fabrics capture: AEN for ANA change, Get Log Page ANA, groups in change state; I/O completions with 303h.
Linux v7.2 source
multipath.c:nvme_read_ana_log() (and nvme_mpath_update()): mod_timer(&ctrl->anatt_timer, ctrl->anatt * HZ * 2 + jiffies) ("double the ANATT value to provide some slack"); nvme_anatt_timeout() calls nvme_reset_ctrl().
Test to provoke it
Linux nvmet: set a port's ANA group to change (configfs ana_groups/N/ana_state) and leave it there. SAFE in a lab.
T-20Controller timestamp drifts or stopsSilentNVMe feature
What happens
The host sets the controller clock with the Timestamp feature; the controller keeps counting. Over long uptimes the device clock can drift, and in some power states it may stop. Device-side logs (Persistent Event Log, telemetry) then carry wrong times.
How it shows up
Nothing. Log entries cannot be correlated with host logs; a device event appears minutes away from the host symptom it caused.
Spec basis
NVMe Base: Timestamp feature (FID 0Eh): 48-bit milliseconds since midnight 1 January 1970 UTC, plus attribute bits giving the timestamp origin and a "Synch" indication that the count may have stopped (exact semantics: verify). ONCS bit indicates support.
Typical causes
Oscillator tolerance; clock not counting in non-operational power states; host sets it only at controller initialisation.
How to detect / prove
nvme get-feature -f 0x0e -H /dev/nvme0 and compare with date +%s%3N; repeat a day later to measure drift.
In a trace
Set Features 0Eh at init (host to device data 8 bytes); later Get Features 0Eh returns the controller's value.
Linux v7.2 source
core.c:nvme_configure_timestamp() is called from nvme_init_ctrl_finish(), i.e. on every controller (re)initialisation, with ktime_get_real() in ms; failure logs could not set timestamp. QEMU computes the value from its virtual clock (nvme_get_timestamp()).
Test to provoke it
Read the timestamp periodically over a week of uptime; plot device minus host. SAFE.
🐞 Debugging connection

When a controller-state timeout (T-02, T-04, T-05) happens, always read CSTS one more time by hand: nvme show-regs /dev/nvme0. CSTS = 0xffffffff means the problem is below NVMe (link or power, see chapter 3.4). CSTS.CFS = 1 means the controller declared a fatal error itself. RDY stuck with CFS = 0 means the firmware is alive enough to answer register reads but not progressing — collect a telemetry log (nvme telemetry-log) before resetting it.
