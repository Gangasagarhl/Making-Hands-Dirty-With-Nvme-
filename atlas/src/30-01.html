PART III

Errors of Time: When Something Takes Too Long

A command that never finishes has no status code, because there is no completion to carry one. A link that never trains raises no AER bit, because there is no link to send it on. In NVMe, PCIe and the Linux host these failures are caught by one thing only: a timer. This part lists every timer and time limit across the three layers — who sets it, in what units, what happens when it expires, how to see it, and what Linux v7.2 does — and treats each expiry as an error in its own right, with its own card.

III.1 Time Is an Error Signal

III.1.1 Why "too slow" is a failure, not a nuisance

Every protocol in the storage path is built on a promise: if I ask, you will answer. The NVMe specification never says how long a Read may take, but it does say how long the controller may take to become ready (CAP.TO), to shut down (reported through RTD3E), to activate firmware (MTFA), to finish a transition between Asymmetric Namespace Access (ANA) states (ANATT), and how often the host must prove it is alive (KATO). PCI Express (PCIe) bounds how long a requester waits for a completion (Completion Timeout), how long a transmitter waits for an acknowledgement (replay timer), and how long each Link Training and Status State Machine (LTSSM) state may last. The Linux host adds its own limits on top: 30 seconds for an I/O command, 60 seconds for an admin command, 5 seconds by default for a shutdown.

When one of these limits passes, the same thing has happened as when a device returns an error status: the system can no longer trust that the request did what it asked. Often it is worse than an error status, for three reasons:

  • No information. An error status says what went wrong. An expired timer only says that something did not arrive. The cause could be the device firmware, the link, a missed interrupt, the host's own scheduling, or a power state that never woke up.
  • Unknown state. After a timeout the host does not know whether the command ran, ran partly, or is still running. A Write that "timed out" may have reached the media; a Write that was aborted may still be in flight inside the drive. Recovery has to assume the worst, which is why Linux escalates to a controller reset.
  • Large blast radius. One stuck command can cost a reset of the whole controller, and every other in-flight command on every queue is cancelled and retried with it.
📌 Remember

A timer expiry is an error even when no status code exists. In this atlas every such failure is labelled Timer only. If the cause is a slowdown that never trips any timer — a p99.9 latency miss, a throttled drive — it is labelled Degraded.

🔍 Time failures on a PEX trace

On a PCIe protocol-analyzer (PEX) capture, a timer expiry never appears as a packet of its own. It appears as an absence plus timestamps: a doorbell write with no CQE for that command ID, a memory read with no completion for that tag, a CC write with no CSTS read showing the expected bit. Every card in this part therefore says which two packets bound the interval and what limit to compare it with; chapter III.6 collects these checks in one table. Anything that happens on another link, on a network, or inside the drive or host CPU is not on the trace.

III.1.3 Nested timers for one I/O: which fires first

Consider one 4 KiB Read submitted on an NVMe drive behind a Root Port. Several independent timers start running at almost the same moment. They are nested by orders of magnitude, and the order in which they fire decides what you see in the logs.

PCIe hardware timerHost / Linux timerNVMe protocol timer (fabrics)Recovery action

Read the figure from left to right:

  1. Replay timer (microseconds). If a Transaction Layer Packet (TLP) is corrupted on the wire, the Data Link Layer retransmits it long before anyone else notices. The I/O is merely a few microseconds late. AER may log a correctable error.
  2. Completion Timeout (default 50 µs to 50 ms). Either side can be the requester. The drive is the requester when it fetches the Submission Queue Entry (SQE) and reads write data from host memory; the host is the requester when the CPU reads a register such as CSTS. If a completion does not come back in time, the requester's Completion Timeout fires and is logged as an uncorrectable AER error. For an MMIO read, the CPU then gets all-ones data. For a device DMA read, the device firmware decides what to do: ideally it completes the NVMe command with an error status; a poor implementation simply never completes it.
  3. Linux command timeout (30 s). If no Completion Queue Entry (CQE) arrives, the block layer timer fires and nvme_timeout() in drivers/nvme/host/pci.c runs: it first checks for a missed interrupt by polling the queue, then sends an NVMe Abort and re-arms the timer.
  4. Second expiry (about 60 s). If the aborted command still has not returned, Linux v7.2 disables the controller and schedules a reset. Every command in flight is cancelled and requeued.

The gap between the levels is the point: the lower layer should always fire first, so that the upper layer sees a clean error rather than silence. When a lower timer is configured longer than an upper one (a Completion Timeout in Range D, for example), the order flips: the NVMe timer fires while the PCIe transaction is still officially outstanding, and the reset races with a link-level error that has not yet been reported.

💡 Senior insight

When you see I/O tag N ... timeout, aborting in dmesg, first look at the AER log of the drive and of its Root Port for the same few seconds. If there is a Completion Timeout, Replay Timer Timeout or Surprise Down there, the NVMe timeout is a symptom; the root cause is on the link. If AER is clean, the drive accepted the command and failed to complete it: a firmware or media problem.

III.1.4 The escalation ladder in Linux v7.2

Linux turns a silent stall into a series of increasingly heavy actions. The ladder for an NVMe over PCIe I/O, as implemented in drivers/nvme/host/pci.c:nvme_timeout() and block/blk-mq.c:blk_mq_timeout_work():

t = 0          submit; blk_add_timer() arms deadline = now + io_timeout (30 s)
t = 30 s       blk_mq_timeout_work() finds request past deadline
               -> blk_mq_rq_timed_out() -> nvme_timeout(req)
                  if PCI device disconnected      -> state DELETING, disable, done
                  if pci_channel_offline()        -> BLK_EH_RESET_TIMER (let AER/DPC recover)
                  if CSTS.CFS=1 or NSSRO          -> "controller is down; will reset", reset
                  poll the CQ                     -> found? "completion polled", done
                  if controller CONNECTING        -> disable controller
                  if admin queue or already aborted -> "reset controller", reset
                  if no Abort credits (ACL+1 used) -> BLK_EH_RESET_TIMER (wait again)
                  else send Abort(SQID, CID), mark IOD_ABORTED, BLK_EH_RESET_TIMER
t = 60 s       second expiry of the same request -> IOD_ABORTED set -> reset controller
reset          nvme_dev_disable(): CC.EN=0, wait CSTS.RDY=0 for up to CAP.TO;
               cancel all requests; re-enable: CC.EN=1, wait CSTS.RDY=1 for CAP.TO / CRTO
retry          each cancelled request is retried up to max_retries (5) unless DNR

Every step is a separate failure card in chapter III.3.

In a PEX trace
Partly visible Visible as an absence: measure from the SQ tail doorbell MWr (BAR0+1000h+...) to the CQE MWr carrying that CID. Missing CQE plus the Abort SQE fetch ~30 s later proves the stall; the first missing packet (SQE fetch MRd, data, CQE MWr or MSI-X MWr) locates it. Why firmware stopped is not visible.
What happens
The host writes an SQE and rings the doorbell; the controller fetches it (or not) but never posts a CQE. No status code exists because there is no completion.
How it shows up
Nothing until the host timer fires. Linux v7.2: nvme nvme0: I/O tag 17 (0011) opcode 0x2 (Read) QID 3 timeout, aborting req_op:READ(0) size:4096 after 30 s; if the abort also fails, ... timeout, reset controller.
Spec basis
NVMe Base: every command submitted shall be completed with a CQE (unless the controller is reset or the queue deleted). The spec gives no general per-command time limit; host timeouts are policy.
Typical causes
Firmware hang or deadlock on one command type; command lost in the controller after a malformed SQE; device DMA read of the SQE hit a Completion Timeout and firmware dropped the command; MSI-X interrupt lost (command completed but host never noticed); queue stuck behind a long-running background operation.
How to detect / prove
dmesg timeout lines carry tag, CID, opcode, QID. Compare with an analyzer trace: was the SQE fetched (device MRd to the SQ address)? Was a CQE written (device MWr to the CQ address)? Was the MSI-X MWr sent? The first missing packet locates the fault. nvme error-log may show an entry for the CID if firmware noticed.

III.1.6 Common mistakes when reasoning about time

  • Treating the timeout value as the latency of the failure. A "30 s timeout" means the command was missing for at least 30 s; it may have been lost at t=1 ms.
  • Raising the timeout to "fix" errors. It hides a stall rather than removing it, and every stalled command now blocks its queue slot for longer.
  • Forgetting that the host can be the slow party. A CPU stuck with interrupts off, a thread starved by the scheduler, or a hypervisor that paused the VM produces exactly the same symptom as a slow drive. The "completion polled" message (T-21) is the classic sign.
  • Ignoring nesting. If an upper timer is shorter than a lower one, the upper layer always "wins" and the true cause is never logged.
