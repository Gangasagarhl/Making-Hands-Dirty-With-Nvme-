PART I-B

What a PEX Trace Is and What It Can See

A PEX trace is the capture file written by a Teledyne LeCroy PCI Express protocol analyzer (the Summit / PETracer family, analysed in the vendor's PCIe Protocol Suite / PCIe Protocol Analysis software). It is a record of every symbol, packet and ordered set that crossed one PCIe link, in both directions, with a timestamp on each. That makes it the strongest evidence you can have for anything that happens on that wire, and no evidence at all for anything that happens anywhere else. This part explains how the analyzer gets the data, what each decoding layer shows, how the NVMe decoder rebuilds commands from raw memory reads and writes, what can never be in the file, how to set up a capture so the error you care about is actually in it, and how to export the trace for a script or an AI assistant. It ends with one large table: which error categories the analyzer flags by itself and which ones you have to find by reasoning over the trace. Every error card in this atlas starts with an "In a PEX trace" verdict that follows the rules set out here.

I-B.1 How an Analyzer Captures a Link

I-B.1.1 Why this chapter exists

Engineers often treat a protocol-analyzer trace as "the truth". It is the truth about one link during one time window, as seen through one probe. Before you trust a missing completion, a flagged CRC error or a 40 µs gap, you need to know how the data got into the file. Some "errors" were made by the probe, and some real errors were never captured because the trigger fired too late or a filter dropped them. This chapter covers the capture chain: probe, deskew and decode hardware, buffer, trigger, filter and file.

  • Describe where an analyzer sits on an NVMe link and what "both directions" means for an endpoint capture.
  • Explain what the timestamps in a PEX file measure and what they do not.
  • Explain how capture-buffer size, triggers, pre-trigger percentage and hardware filters decide what the file contains.
  • Name the probing methods (slot interposer, M.2/U.2/EDSFF interposer, midbus or solder-down probe) and their side effects.

I-B.1.2 The physical setup

A PCIe link is a set of differential pairs: for each lane, one pair carries data from the upstream port (Root Port or switch Downstream Port) to the downstream port (the SSD), and one pair carries data back. A protocol analyzer taps both pairs of every lane at once. On an NVMe SSD the usual tap is an interposer: a small board that plugs into the slot (CEM add-in card, M.2, U.2/U.3, EDSFF E1.S/E1.L/E3, MCIO cable) with the SSD plugged into the interposer. A cable runs from the interposer to the analyzer box, which connects to a PC over USB or Ethernet. Teledyne LeCroy has announced interposers for EDSFF and MCIO form factors, and says its PCIe analyzers use "high-impedance, non-intrusive probing" uncertain (vendor claim seen in search excerpts, not independently checked). Other vendors make the same kind of claim for their own interposers (SerialTek SI-Fi).

🔧 Hardware

"Non-intrusive" means the probe is designed not to change what the two link partners exchange. It does not mean the probe adds no loss. At 16, 32 and 64 GT/s, any extra connector, trace or tap changes the channel. Some links that train cleanly without the interposer will show receiver errors, a lower speed or extra Recovery entries with it. Card X-27 covers this. The opposite also happens: a marginal link can get better with an interposer that includes a redriver or retimer. The rule is simple. A physical-layer finding seen only with the probe installed is not proven until you see the same symptom (AER counters, link status) without the probe.

The analyzer is passive. It never sends Acks, credits or training sequences, so it is not a link partner. Inside the box, each lane goes through a receiver (clock recovery and equalization), then lane-to-lane deskew, then decoding (8b/10b or 128b/130b, descrambling, and in Flit mode FEC/CRC checking). The result is written into a large memory with a timestamp. Because the analyzer receives the same signal as the real receiver, it can disagree with that receiver. The analyzer's receiver may lock worse (it sees an error the SSD did not) or better (it misses an error the SSD saw). The PEX file shows what the analyzer's receiver decoded, which is close to, but not the same as, what each link partner decoded.

I-B.1.4 Timestamps: what they measure

Each captured item gets a timestamp from the analyzer's own clock, normally at the start of the packet as it passes the probe. Several timing questions follow directly:

  • Single-point measurement. The time between a host doorbell write (downstream) and the SSD's first SQE fetch (upstream read request) is measured at the probe, not inside the host or the SSD. Host-internal delays (CPU, root-complex queues) and device-internal delays are both hidden inside that interval.
  • Resolution and accuracy. These depend on the model impl. Treat sub-symbol-time differences as noise.
  • Exported deltas. Teledyne LeCroy release notes say exports to CSV or text have included a time-delta field since version 7.15 of the PCIe Protocol Suite uncertain (seen in a search excerpt of the release notes).
  • Gaps. If the buffer filled, a filter dropped traffic or the analyzer lost lock, there is no packet in the file even though traffic flowed on the wire. A long gap in a trace is a fact about the capture first. Only after you have ruled out capture problems is it a fact about the system.

I-B.1.5 Buffer, triggers and filters

A Gen5 x4 NVMe link at full load moves roughly 16 GB/s in each direction. Even a large capture memory fills in seconds unless you filter. Vendor pages list 256 GB of trace memory for the Summit T516 (a Gen5 x16 model). They also describe an "NVMe Enhanced Mode" on the Summit T34 that stretches recording to "up to several hours" depending on the device under test, presumably by storing NVMe-relevant traffic selectively uncertain. Three controls decide what lands in the file:

⚠️ Warning

Write the capture settings into your bug report: speed, width, lane mapping, trigger, pre-trigger %, hardware filters and buffer size. A reviewer who sees "no UpdateFC DLLPs in 2 ms" must be able to rule out "UpdateFC was filtered".

I-B.1.6 One link, both directions, one time window

The three limits that shape every verdict in this atlas:

  1. One link. If the SSD sits behind a PCIe switch and you probe the SSD's link, you see nothing on the switch's upstream link. A completion the switch dropped or poisoned on the way up is invisible. A peer-to-peer transfer between two other devices is invisible.
  2. Both directions. Every TLP the SSD sends (DMA reads of SQEs and PRP lists, DMA writes of data and CQEs, MSI-X writes) and every TLP the host sends (doorbells, register reads, completions carrying data) is visible. That is everything the SSD and host say to each other. It is not what either of them does.
  3. One time window. Anything before the first stored item, after the last one, or inside a gap is not in the file.
💡 Senior insight

Put each claim you make from a trace into one of three classes. (a) "This packet was on the wire": strong, assuming the probe decoded it correctly. (b) "This packet was not on the wire in this window": strong only if no filter, gap or lost lock covers that window. (c) "Therefore the device did or did not do X internally": an inference, never a direct observation. The silent-trim case (Part IV) lives entirely in class (c).

Quiz

  1. You probe an NVMe SSD behind a switch and see a host read request with no completion for 50 ms. Is that a completion timeout on the SSD?

    Answer

    Not necessarily. If the read was sent by the SSD (a DMA read toward host memory), the completion comes from the host through the switch. It may have been lost or delayed on the switch's upstream link, which you cannot see. If the read was sent to the SSD (an MMIO register read), a missing completion from the SSD on your link is direct evidence. Also check for a buffer gap or a filter that dropped completions.

  2. Why can a physical-layer error appear in the trace while the SSD's AER Receiver Error counter stays at 0?

    Answer

    The analyzer has its own receiver. A probe-induced loss or a weaker equalization setting in the analyzer can corrupt symbols that the SSD's receiver decoded correctly. The error is then an analyzer artifact (X-27). The reverse also happens. Check both ends' AER counters.

I-B.2 Decoding Layers: What Each View Shows

I-B.2.1 Why this chapter exists

The same PEX file can be viewed as raw symbols, as packets, as request/completion pairs or as NVMe commands. Each view answers different questions and hides different errors. A physical error is obvious in the symbol view and invisible in the NVMe command view. A missing CQE is obvious in the NVMe view and needs real work to spot in the packet view. The view levels named in Teledyne LeCroy spec sheets include symbol (or Dword), packet, link and split-transaction levels. Recent software adds NVMe-level views, queue-utilization graphs and a "Trace Expert" report on NVMe queues, commands, doorbells and control registers uncertain (names taken from vendor spec sheets and press releases seen in search excerpts; check your version's manual for current menu names).

The lower an error sits, the more likely the analyzer flags it automatically, because the rules are local: one symbol, one block, one packet. The higher it sits, the more the check depends on state (which queue, which CID, which outstanding tag). The analyzer must rebuild that state from the trace, and it can only do so if the trace contains the setup.

I-B.2.4 Reading a flagged item

Analyzers mark an error by colouring the item and naming the check that failed, usually per lane and per direction. When you see one, ask four questions:

  1. Which direction? Errors in packets sent by the SSD were decoded by the host's receiver, so check the Root Port's AER. Errors in packets sent by the host were decoded by the SSD's receiver, so check the SSD's AER.
  2. Did the link partner react? A real LCRC error must be followed by a Nak (or, if the receiver missed the whole packet, a replay timeout). If the analyzer flags an LCRC error and the next DLLP is an Ack covering that sequence number, the receiver accepted the packet. The analyzer's decode was wrong (X-27).
  3. Is it isolated or clustered? Errors right after electrical-idle exit, a speed change or an equalization phase are often analyzer re-lock artifacts.
  4. Is it one lane? Errors on one lane point to a channel or connector problem, or an analyzer lane-mapping mistake.

The Nak carries the sequence number of the last good TLP (0x2A1). That confirms the host's receiver also rejected 0x2A2. The transmitter replays everything after 0x2A1, including 0x2A3, which arrived intact but was discarded because it followed a bad TLP. This is normal recovery. It becomes an error pattern only when it repeats (X-18).

📭 What the spec does not say

The PCIe Base Specification defines what receivers must check and how they report it. It does not define what a protocol analyzer must check or how to label it. Analyzer error names and coverage are vendor-specific. Two analyzers can label the same event differently, and some check rules that are optional for devices. Treat analyzer labels as hints that point you to the spec rule, not as spec citations.

Quiz

  1. Which view would you open first to answer "why did this NVMe read take 900 µs"?

    Answer

    Start at the NVMe level to get the command timeline (doorbell → SQE fetch → data writes → CQE → MSI-X). Then drop to the split-transaction and link levels for the slowest interval to look for replays, Naks, credit stalls or slow host completions on SQE/PRP fetches. Go to the symbol level only if the link level shows errors.
