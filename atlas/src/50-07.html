26 The Linux v7.2 NVMe Error-Recovery Path

26.1 Why this chapter exists

When an NVMe SSD misbehaves on Linux, the kernel log is usually the first and sometimes the only evidence. Each message in this chapter comes from a specific branch of the driver, and the branch tells you what the driver concluded. One line can tell you whether the command was aborted, whether the interrupt was lost, whether the device is gone, or whether the controller is now dead. This chapter follows nvme_timeout() branch by branch, then covers the PCI error callbacks and the end state of a controller that cannot be recovered. All strings are copied from Linux v7.2 sources (drivers/nvme/host/pci.c, core.c, nvme.h). The example lines are illustrative.

26.2 Controller states in the driver

Linux tracks its own view of the controller in enum nvme_ctrl_state. The transitions allowed by nvme_change_ctrl_state() in v7.2 are listed below. Attempts not listed fail silently (the function returns false), which is why some recovery paths "do nothing".

26.3 nvme_timeout(): the decision tree

blk-mq calls nvme_timeout() when a request exceeds its deadline: nvme_core.io_timeout (default 30 s) for I/O, admin_timeout (default 60 s) for admin. The function reads CSTS once at entry, then decides in this order.

Driver decisionDevice / bus actionOutcome
  1. Device gone or controller already terminal

    If pci_dev_is_disconnected() is true, the state goes to DELETING. If the state is terminal (DELETING/DEAD), go to the disable path. The comment explains this breaks a deadlock where error recovery waits for a removed device.

    Where: pci.c nvme_timeoutPCIe: none
  2. PCI error recovery in progress

    If pci_channel_offline(pdev), return BLK_EH_RESET_TIMER, because "we cannot reset or the recovery mechanism will surely fail". AER/DPC owns the device for now.

    Where: nvme_timeoutPCIe: none
  3. Controller fatal (or NSSR happened)

    nvme_should_reset(dev, csts) is true if CSTS.CFS is set, or NSSRO is set on an NSSR-capable controller, and the state is not already RESETTING/CONNECTING. Log controller is down; will reset: CSTS=0x%x, PCI_STATUS=0x%hx (plus two hint lines if CSTS reads all-ones). Go to disable.

    Where: nvme_should_reset, nvme_warn_resetPCIe: MRd CSTS, CfgRd PCI_STATUS
    controller is down; will reset: CSTS=0xffffffff, PCI_STATUS=0xffff (illustrative)
  4. Missed interrupt?

    Poll the CQ (nvme_poll for polled queues, otherwise nvme_poll_irqdisable). If the request is no longer in flight, the CQE was there all along: log I/O tag %d (%04x) QID %d timeout, completion polled and return DONE. No reset happens.

    Where: nvme_timeoutPCIe: none (reads host memory)
  5. Timeout during (re)initialisation or deletion

    If the state is CONNECTING, move to DELETING. Then for CONNECTING or DELETING: log I/O tag %d (%04x) QID %d timeout, disable controller (rate-limited), mark the request cancelled, call nvme_dev_disable(dev, true) and return DONE. If the state is RESETTING, return RESET_TIMER.

    Where: nvme_timeoutPCIe: shutdown sequence
  6. Admin command, or second timeout of an aborted command

    If QID 0, or the request has IOD_ABORTED already: log I/O tag %d (%04x) opcode %#x (%s) QID %d timeout, reset controller, mark cancelled, go to disable.

    Where: nvme_timeoutPCIe: none yet
  7. Try an NVMe Abort

    If the Abort Command Limit allows (the counter abort_limit starts at Identify Controller ACL+1; if exhausted, return RESET_TIMER and try later), set IOD_ABORTED, build Abort (opcode 08h) with the CID and SQID, and log I/O tag %d (%04x) opcode %#x (%s) QID %d timeout, aborting req_op:%s(%u) size:%u. The Abort's completion logs Abort status: 0x%x. Return RESET_TIMER: "If hit twice, it'll cause a device reset".

    Where: nvme_timeout, abort_endioPCIe: Yes, admin SQ doorbell MWr, Abort SQE fetch, CQE
    I/O tag 17 (a011) opcode 0x2 (Read) QID 3 timeout, aborting req_op:READ(0) size:131072 (illustrative)
  8. The disable path

    Change the state to RESETTING. If that fails and the state is terminal, call nvme_dev_disable(dev, true); otherwise return DONE. If it succeeds, call nvme_dev_disable(dev, false) (freeze queues, delete I/O queues and disable the controller unless it is "dead", free IRQs, disable the PCI device, cancel all outstanding requests with host status Aborted), then nvme_try_sched_reset() queues nvme_reset_work.

    Where: nvme_dev_disable, nvme_try_sched_resetPCIe: Delete SQ/CQ, CC write, CSTS polls

⚠️ "Removing dead controller"

Older kernels had a dedicated remove-dead-controller step with its own message. In Linux v7.2 that string does not exist in drivers/nvme/host/pci.c. A failed reset ends in nvme_reset_work's "out" path: Disabling device after reset failure, state DELETING, nvme_dev_disable(dev, true), nvme_mark_namespaces_dead(), state DEAD. The PCI driver stays bound, and the block devices remain but fail all I/O. (The separate Apple SoC NVMe driver, apple.c, still has apple_nvme_remove_dead_ctrl_work(), which unbinds its driver with device_release_driver(). The PCIe driver has no equivalent.) Search logs for the v7.2 strings, not ones remembered from older kernels.

C-14I/O command timeout handled by Abort Timer onlyHost driver
In a PEX trace
Visible The original SQE (fetched by the device with its CID), no CQE for that CID for about 30 s, then an admin SQ doorbell, the device fetching an Abort SQE (opcode 08h, CDW10 = SQID | CID<<16), the Abort's CQE (DW0 bit 0 = 1 means "not aborted"), and ideally a CQE for the original CID with status Command Abort Requested (generic 07h). Measure the gap from the SQE fetch to the Abort.
What happens
An I/O command does not complete within io_timeout. The driver asks the controller to abort it. Abort is best effort, and the controller may decline.
How it shows up
The "aborting req_op" line, then Abort status: 0x0 (or an error). If the original command completes with "Command Abort Requested", blk-mq retries it up to nvme_core.max_retries (default 5) unless DNR is set. If it does not complete within another timeout, the second-timeout branch resets the controller.
Spec basis
NVMe Base Specification: Abort command, Abort Command Limit (ACL), status Command Abort Requested.
Typical causes
A slow internal operation (GC, read-retry ladders on worn NAND). A lost doorbell (L-20, L-27). A device that fetched the SQE and lost it.
How to detect / prove
dmesg. The trace (above) separates "never fetched" from "fetched but not completed" from "completed but CQE lost or misdirected".
Linux v7.2 source
pci.c: nvme_timeout, abort_endio; core.c: abort_limit from id->acl + 1, nvme_decide_disposition, nvme_retry_req.
Test to provoke it
SAFE: lower nvme_core.io_timeout on a test box and run a workload that triggers long internal operations. The NVMe fault-injection framework (CONFIG_FAULT_INJECTION_DEBUG_FS, drivers/nvme/host/fault_inject.c) injects status errors, not timeouts.
C-15Lost interrupt — "completion polled" Timer onlyHost / interrupt
In a PEX trace
Visible A CQE MWr to the CQ for the CID, and then no MSI-X MWr (or an MSI-X MWr to a vector the host did not expect). About 30 s later, the CQ head doorbell write from the host's poll. If the MSI-X MWr is present, the loss happened in the host (interrupt remapping or CPU), which a PEX trace cannot see.
What happens
The device completed the command, but the host never processed the CQE until the timeout handler polled the CQ.
How it shows up
I/O tag %d (%04x) QID %d timeout, completion polled, a 30-second latency for that I/O, and no reset.
Spec basis
NVMe: interrupts per CQ (Create I/O CQ IEN/IV). PCIe: MSI-X.
Typical causes
See L-35: broken MSI (quirked devices), vector affinity bugs, a CQE write after the interrupt (ordering bug), interrupt coalescing.
How to detect / prove
Count "completion polled" occurrences. Check /proc/interrupts. Bisect with poll queues.
Linux v7.2 source
pci.c: nvme_timeout, nvme_poll_irqdisable, nvme_poll.
Test to provoke it
CAUTION: mask a vector from a debug tool.
C-16Device gone: CSTS reads all-ones ReportedHost / PCIe
In a PEX trace
Partly visible On the Root Port side of the link, the CSTS MRd from the host and then either no CplD (Completion Timeout) or a Cpl with UR. The all-ones value is synthesised by the root complex and is never on the wire. On the SSD side you see the link down. The CfgRd of PCI_STATUS has the same pattern.
What happens
The driver reads 0xFFFFFFFF from CSTS. The PCIe read failed, so the device is not responding at all.
How it shows up
In nvme_timeout: controller is down; will reset: CSTS=0xffffffff, PCI_STATUS=0xffff plus the two power-saving hint lines. In nvme_wait_ready(), all-ones returns -ENODEV at once with no message. In nvme_pci_enable(): debug-level reading CSTS register failed and -ENODEV. The reset therefore fails (C-17).
Spec basis
PCIe: unsuccessful completions return all-ones on most platforms impl.
Typical causes
Surprise link down (L-11, L-27), DPC containment (L-28), power loss, firmware crash, power-state exit failure (C-07, L-37).
How to detect / prove
lspci -s <BDF> -vv shows "!!! Unknown header type 7f" or all-ff. Check the upstream port's LnkSta for DLActive.
Linux v7.2 source
pci.c: nvme_warn_reset, nvme_pci_enable, nvme_pci_ctrl_is_dead; core.c: nvme_wait_ready.
Test to provoke it
See L-11 and L-27.
C-17Reset fails — controller marked DEAD, namespaces fail all I/O ReportedHost driver
In a PEX trace
Partly visible The failed re-init is visible (CC EN=1 with RDY never set, or no completions at all, or an admin command that fails). The driver's decision to give up is host-side. Afterwards, no traffic reaches the device.
What happens
nvme_reset_work() fails at any step: PCI enable, admin queue setup, enable, Identify, HMB setup, I/O queue creation, or a state change. The controller is moved to DELETING, disabled with shutdown, its namespaces are marked dead (blk_mark_disk_dead) and its state becomes DEAD. Applications get I/O errors and the block devices stay present but unusable until the device is removed and rescanned.
How it shows up
Disabling device after reset failure: %d (-19 = ENODEV is typical for a missing device). This is often preceded by Device not ready; aborting initialisation, Identify Controller failed (%d), Could not set queue count (%d) or IO queues lost.
Spec basis
Host behaviour.
Typical causes
Device gone (C-16), a controller that cannot complete re-initialisation (firmware hung), repeated fatal PCIe errors.
How to detect / prove
cat /sys/class/nvme/nvme0/state shows dead (or deleting). dmesg. Recovery attempt: echo 1 > /sys/bus/pci/devices/<BDF>/remove then echo 1 > /sys/bus/pci/rescan (CAUTION: removes the device).
Linux v7.2 source
pci.c: nvme_reset_work (out: path), nvme_dev_disable; core.c: nvme_mark_namespaces_dead, nvme_change_ctrl_state.
Test to provoke it
CAUTION: power off the slot (sysfs slot power) without removing the driver, then trigger I/O.
C-18PCI error recovery of the NVMe function (error_detected / slot_reset / resume) ReportedHost / PCIe
In a PEX trace
Partly visible The cause (an ERR_FATAL message, a malformed TLP and so on) is visible if it crossed the probed link. Then the secondary bus reset (Hot Reset TS1s, or the link going down for DPC), link retraining, config-space restore CfgWrs, and a full NVMe init sequence. The callbacks themselves are software.
What happens
AER or DPC decides the channel is frozen. The NVMe driver shuts the controller down, the link is reset, and the driver re-initialises. In-flight requests are cancelled and retried.
How it shows up
frozen state error detected, reset controller → (port) Root Port link has been reset (0) or DPC messages → restart after slot reset → device recovery successful. On failure: failure state error detected, request disconnect, device recovery failed. Non-fatal errors: nvme_error_detected returns CAN_RECOVER, no NVMe log line, nothing is reset. Also reset_prepare/reset_done (nvme_reset_prepare, nvme_reset_done) for user-initiated resets via /sys/bus/pci/devices/<BDF>/reset.
Spec basis
Linux PCI error recovery (Documentation/PCI/pci-error-recovery.rst); PCIe secondary bus reset, DPC.
Typical causes
Any fatal AER (Chapter 22) or DPC trigger (L-28).
How to detect / prove
dmesg sequence; pci_uevent_ers uevents; AER counters.
Linux v7.2 source
pci.c: nvme_error_detected, nvme_slot_reset, nvme_error_resume, nvme_err_handler; drivers/pci/pcie/err.c: pcie_do_recovery, report_error_detected (logs can't recover (no error_detected callback) for drivers without one).
Test to provoke it
SAFE-ish: aer-inject (CONFIG_PCIEAER_INJECT) a fatal error at the SSD's BDF on a test system; this exercises the software path only.
C-19Completion for an unknown or stale command ID ReportedNVMe queue
In a PEX trace
Visible A CQE MWr whose CID (DW3 bits 15:0) does not match any outstanding SQE on that queue, or matches one that already completed (a duplicate CQE). Compare it with the SQE CIDs in the trace. Check the phase tag too: a stale phase means a CQE the host should have ignored.
What happens
The controller posts a CQE whose CID the host cannot match. Linux v7.2 encodes a 4-bit generation counter in the upper CID bits (unless NVME_QUIRK_SKIP_CID_GEN is set), so late or duplicate completions for a reused tag are caught instead of completing the wrong request.
How it shows up
request %#x genctr mismatch (got %#x expected %#x), could not locate request for tag %#x, then invalid id %d completed on queue %d. The CQE is dropped, and the real request (if any) later times out.
Spec basis
NVMe Base Specification: CID uniqueness per SQ for outstanding commands; CQE format (SQ ID, CID, phase).
Typical causes
Controller firmware bugs (duplicate completions, wrong CID after an abort). A controller limiting CID values (the Apple quirk). Memory corruption of the CQ.
How to detect / prove
dmesg; the trace.
Linux v7.2 source
nvme.h: nvme_find_rq, nvme_cid; pci.c: nvme_handle_cqe.
Test to provoke it
EXPERT: a modified QEMU model that posts a duplicate CQE.
C-20Controller comes back with no I/O queues ReportedNVMe admin
In a PEX trace
Visible After re-init, the Set Features Number of Queues (FID 07h) CQE reports 0 queues allocated, or Create I/O CQ/SQ commands complete with an error status. Both are admin CQEs on the wire.
What happens
After a reset, the controller accepts admin commands but grants no I/O queues, or queue creation fails. Linux keeps the controller for investigation ("If only admin queue live, keep it") but removes the namespaces.
How it shows up
IO queues lost (reset) or IO queues not created (probe); Could not set queue count (%d). nvme list shows the controller but no namespaces, and admin passthrough still works.
Spec basis
NVMe Base Specification: Number of Queues feature, Create I/O Submission/Completion Queue.
Typical causes
Firmware in a degraded or read-only "safe mode" (often after media failure). Controller resources leaked across resets.
How to detect / prove
nvme get-feature -f 7 /dev/nvme0; nvme smart-log critical warning; vendor logs.
Linux v7.2 source
pci.c: nvme_reset_work, nvme_setup_io_queues; core.c: nvme_set_queue_count.
Test to provoke it
Vendor-specific (force safe mode).
C-21Abort Command Limit exhausted — abort requests deferred Timer onlyHost driver
In a PEX trace
Partly visible You see up to ACL+1 outstanding Abort commands and further timed-out commands with no Abort issued for them. The driver's counter is host-side, and only the absence of Aborts is visible.
What happens
Many commands time out at once (typically when the controller has stalled). Linux v7.2 has only ACL+1 aborts available. When none are left, nvme_timeout just re-arms the timer (RESET_TIMER), so recovery for the rest is delayed by whole timeout periods until an abort finishes or a reset happens.
How it shows up
A few "aborting" lines followed by silence. Long multi-minute stalls before the eventual "reset controller".
Spec basis
NVMe Base Specification: Abort Command Limit (ACL, 0's based) in Identify Controller; "Abort Command Limit Exceeded" status.
Typical causes
Controller-wide stall with many commands outstanding. Very small ACL (e.g. 0, meaning one abort).
How to detect / prove
nvme id-ctrl /dev/nvme0 | grep acl; timestamps of timeouts versus resets.
Linux v7.2 source
pci.c: nvme_timeout (atomic_dec_return(&dev->ctrl.abort_limit)), abort_endio; core.c: atomic_set(&ctrl->abort_limit, id->acl + 1).
Test to provoke it
CAUTION: stall a QEMU controller (for example by pausing its I/O thread with a debugger) under QD128 load.
💡 Senior insight — reading a recovery from the log alone

Write down three facts from the first NVMe line: (1) which branch fired (polled / aborting / reset / disable / controller is down), (2) the CSTS value if printed, and (3) the opcode. "completion polled" points at interrupts. "aborting" followed by a successful completion points at a slow device. "controller is down" with CSTS=0x3 points at device firmware. With CSTS=0xffffffff, look at PCIe and power. "Disabling device after reset failure" means the controller is gone until the device is removed and re-probed or power-cycled.
