III.5 Performance-Time Failures: Slow but "Successful"

Some time failures never trip any timer. Every command completes successfully, well inside 30 seconds, yet the system misses its purpose: a database misses its p99.9 latency target, a stream stalls, throughput halves after an hour. These are Degraded failures. They are found only by measuring and comparing against a target that you define, because neither NVMe nor PCIe defines one.

latency(cmd) = t(CQE written) − t(SQ doorbell written)
  • t(SQ doorbell written) — timestamp of the host's MWr to the SQ tail doorbell that made the command visible to the controller (on a PEX trace) or the nvme_setup_cmd tracepoint (on the host).
  • t(CQE written) — timestamp of the device's MWr into the CQ slot holding that CID (trace) or nvme_complete_rq (host; includes interrupt and scheduling delay).

Measure both if you can. The difference between the device-side latency (trace) and the host-side latency (tracepoints, fio clat) is time spent in the host — the part a PEX trace cannot see.

III.6 Measuring Time on a PEX Trace

A PEX trace (a Teledyne LeCroy PCIe protocol-analyzer capture) records every TLP, DLLP and ordered set on the probed link with a timestamp. That makes it the best tool there is for time failures on that link — with three limits:

  • A timeout is visible only as an absence. The trace shows a request and then no completion; you prove the violation by measuring the time from the request to the end of the capture (or to the recovery action) and comparing it with the limit.
  • Only the probed link. A Completion Timeout on a different link, a network capsule for NVMe over Fabrics, or a host CPU stall are not on the trace.
  • Registers are visible only when read. CAP, CSTS, CRTO, AER status and Device Control 2 appear only as payloads of configuration or memory reads the host performs during the capture. Read them deliberately at the start and the end of a capture (e.g. nvme show-regs, lspci -vvv) so their values are in the trace.

Each NVMe interval is bounded by two packets that both cross the link: a host write (doorbell or register) and a device write (CQE, MSI-X) or a completion of a host read (CSTS). Each PCIe interval is bounded by a request and its completion, a TLP and its Ack, or two LTSSM state entries.

Objective: compare advertised limits with measured times on a test machine.

Setup: a non-production NVMe drive; root shell; optionally a PCIe analyzer on the drive's link.

  1. Record advertised values: nvme show-regs /dev/nvme0 (CAP.TO, CRTO), nvme id-ctrl /dev/nvme0 (rtd3e, rtd3r, mtfa, edstt, crdt1–3, kas, anatt, acl, power-state table).

  3. Measure enable time: unbind and rebind the driver (echo 0000:01:00.0 > /sys/bus/pci/drivers/nvme/unbind, then bind) — CAUTION: unmount first — and read the timestamps in dmesg -T, or on the analyzer the CC EN=1 → RDY=1 interval.
  4. Measure idle-exit latency: fio --rw=randread --bs=4k --iodepth=1 --thinktime=500ms --runtime=120 --time_based --lat_percentiles=1 --readonly with APST on and with default_ps_max_latency_us=0.
  5. Check PCIe settings: lspci -vvv -s 01:00.0 DevCtl2 (Completion Timeout), LnkCap/LnkCtl (ASPM), L1SubCtl1/2.

Observations: fill a table of advertised versus measured values.

Questions: Is CAP.TO generous or tight compared with your measurement? Does the first-I/O-after-idle latency exceed EXLAT of the deepest state Linux enabled?

Solution notes

Typical drives become ready in well under CAP.TO after a clean shutdown and closer to it after an unsafe one. If idle-exit latency exceeds the sum of EXLAT and the PCIe L1 exit latency, either the drive under-reports EXLAT or the platform adds latency (L1.2, clock request); repeat with pcie_aspm=off to separate them.

Extension: repeat step 3 after an unsafe power cut (CAUTION: risk to data on that drive) and compare.

Quiz

  1. CAP.TO reads 28h. How long should the host wait for CSTS.RDY, and how long does Linux v7.2 wait?

    Answer

    28h = 40 units × 500 ms = 20 s. Linux uses (CAP.TO + 1) / 2 seconds in integer arithmetic = 20 s (or the larger CRWMT if CRTO is supported).

  2. Why does Linux send no Abort for a timed-out admin command?

    Answer

    The Abort itself would be an admin command on the same queue that is apparently not progressing; v7.2 resets the controller directly when nvmeq->qid == 0.

  3. The drive's Completion Timeout is set to Range D. What do you expect to see when a host memory read is lost?

    Answer

    An NVMe I/O timeout at 30 s (and probably a reset) before any AER Completion Timeout is logged, because the PCIe timer (4–64 s) may be longer than the NVMe timer.

  4. Which interval on a PEX trace proves a missed interrupt?

    Answer

    A CQE MWr with no following MSI-X MWr (or one to the wrong address), followed only much later by the CQ head doorbell; dmesg shows "completion polled".

  5. CRD=2 and CRDT2=5. How long should Linux wait before resubmitting?

    Answer

    5 × 100 ms = 500 ms (nvme_retry_req()), provided ACRE was enabled.

Interview questions

  1. Beginner Why is a command timeout considered an error even though no status code is returned?
    Model answerBecause the host no longer knows the state of the request: it may or may not have executed. Recovery (abort, reset, retry) is required, exactly as for an error status, and often with a bigger impact.
  2. Intermediate Describe the Linux v7.2 escalation for an NVMe/PCIe I/O timeout.
    Model answerblk-mq timeout work calls nvme_timeout(): check disconnect/offline/CFS, poll the CQ, then send Abort (if Abort credits remain) and re-arm; on a second expiry, or for admin commands, disable and reset the controller; cancelled commands are retried up to max_retries.
  3. Senior How would you design timer values across PCIe, NVMe and the application?
    Model answerNest them: lower layers must fire first with margins of at least an order of magnitude (CTO in ms, NVMe command timeout in tens of seconds, application or cluster failover above that), and make sure device-advertised limits (CAP.TO, MTFA, RTD3E, ANATT) are below the corresponding host waits.
