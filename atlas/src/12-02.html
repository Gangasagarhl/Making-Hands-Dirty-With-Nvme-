I-B.3 The NVMe Decoder: Rebuilding Commands From Memory Traffic

I-B.3.1 Why this chapter exists

NVMe has no packet type of its own on PCIe. A "command" on the wire is a 4-byte memory write to a doorbell register, then a memory read from the SSD into host memory that fetches a 64-byte Submission Queue Entry (SQE), then more reads or writes for PRP lists and data, then a 16-byte memory write of a Completion Queue Entry (CQE) into host memory, then an MSI-X memory write. To label these TLPs as "Read command CID 0x0012 on SQ 3", the analyzer must know where every queue lives in host memory and where the doorbells live in the SSD's BAR. This chapter explains how the decoder learns that, and why a capture that starts too late shows only anonymous memory traffic.

  • List the facts an NVMe decoder needs: BAR0 base, doorbell stride, admin queue addresses and sizes, every I/O queue's base, size, ID and CQ association, PRP/SGL usage, MSI-X table.
  • Explain how each fact appears in the trace: config writes, MMIO writes to CC/AQA/ASQ/ACQ, Create I/O CQ/SQ SQEs.
  • Explain how the decoder pairs doorbell → SQE fetch → data → CQE → MSI-X, and where that pairing can go wrong.
  • Know the workarounds when initialization is missing: manual queue entry, re-initializing the device under capture, vendor "decode without boot trace" features.

I-B.3.3 How one command is paired

Host sends itSSD sends itDecoder bookkeeping (not on the wire)
  1. Doorbell write

    The host writes the new SQ tail to the SQ 3 tail doorbell. The decoder recognises the address as BAR0 + 1000h + (2·3)·(4<<DSTRD) and learns that new SQEs exist between the old and new tail.

    Where: host → SSDPCIe: Yes · MWr, 4 bytes
    MWr 0xF7E0_1018 data 0x0000_0006 (tail 5 → 6) (synthetic)
  2. SQE fetch

    The SSD reads the 64-byte SQE from host memory, and the host's completion returns it. The decoder matches the read address to SQ 3 slot 5 and parses the SQE: opcode 02h, CID, NSID, PRP1/PRP2, SLBA, NLB. SSDs often fetch several SQEs in one read, and the decoder must split them.

    Where: SSD → host, then host → SSDPCIe: Yes · MRd + CplD
    MRd 0x1_0000_0140 len 16 DW, tag 0x21 → CplD tag 0x21 (synthetic)
  3. Data transfer

    For a read command, the SSD writes data to the PRP addresses (MWr, upstream). For a write command, it reads them (MRd, then CplD from the host). The decoder links these to the command through the PRP addresses from the SQE and any PRP list it fetched.

    Where: SSD → hostPCIe: Yes · MWr, MPS-sized chunks
    MWr 0x2_3456_7000 len 64 DW ×16 for 4 KiB (MPS 256) (synthetic)
  4. CQE write

    The SSD writes a 16-byte CQE to CQ 3. The decoder reads CID, SQID, SQHD, phase tag and status, and closes the open command. A CQE whose CID is not open is flagged. An open command that never gets a CQE is flagged at the end of the trace (or not at all, depending on the tool).

    Where: SSD → hostPCIe: Yes · MWr, 16 bytes
    CQE DW2 SQHD=6 SQID=3, DW3 CID=0x0012 P=1 status=0 (synthetic)
  5. MSI-X interrupt

    The SSD writes the MSI-X message for the CQ's vector. The decoder links it to CQ 3 through the MSI-X table addresses it learned during setup.

    Where: SSD → hostPCIe: Yes · MWr, 4 bytes, to the APIC/ITS address
    MWr 0xFEE0_0000 data 0x0000_4023 (synthetic)
  6. CQ head doorbell (later)

    The host later writes the CQ 3 head doorbell. This is visible on the wire. The CPU's reading of the CQE from its own memory is not visible, because it never crosses the link. The decoder's open-command table is pure bookkeeping, built only from the TLPs above.

    Where: decoder state, then host → SSDPCIe: doorbell yes; CPU memory read no
    MWr 0xF7E0_101C data 0x0000_0006 (synthetic)

I-B.3.4 Where pairing goes wrong

  • Capture starts after initialization. No AQA/ASQ/ACQ writes, no Create I/O queue commands. The decoder shows MWr/MRd with no NVMe meaning, unless the tool lets you type in queue bases or has its own discovery heuristics impl.
  • Queues re-created during the capture. After a controller reset the driver may place queues at different addresses. A decoder that keeps old mappings will mislabel traffic.
  • Host memory buffer, CMB or SQ in device memory. If the SQ lives in the Controller Memory Buffer, the host writes SQEs into the SSD's BAR (downstream MWr) and the SSD never fetches them over the link. The decoder must know CMB is in use.
  • Shadow doorbells (Doorbell Buffer Config). With shadow doorbells the host updates a host-memory buffer instead of the BAR doorbell for most updates. The SSD reads it by DMA. Doorbell-based pairing then loses events.
  • Prefetching. SSDs fetch SQEs in batches and may fetch entries that are not yet valid. A decoder that treats every fetched 64 bytes as a command produces ghost commands.
  • Behind an IOMMU. The addresses on the wire are I/O virtual addresses. That is fine for pairing, but they will not match physical addresses in host logs.
  • Filtered payloads. If the capture truncated payloads, the SQE contents cannot be parsed, so the decoder cannot know opcode, CID or LBA.
🐞 Debugging connection

If you must analyse a late-start capture, recover the queue map yourself. Group upstream MRd requests whose addresses step by 64 bytes and wrap: these are SQs. Group upstream 16-byte MWr whose addresses step by 16 bytes: these are CQs. Pair each SQ with the doorbell address whose written values track its slot index. This works, but every conclusion is then derived, not decoded. Say so in the report. The easiest fix is to re-capture with the trigger before the driver loads: unbind and rebind the driver, or reset the controller with nvme reset /dev/nvme0 during the capture (CAUTION: aborts outstanding I/O).

I-B.4 What Is Fundamentally Invisible

I-B.4.1 The rule

A PEX trace contains only what crossed the probed link while the analyzer was recording and decoding correctly. Everything else must be proved with other evidence: logs, registers read by software, read-back tests, a second capture on another link, or vendor debug data. 📌 Remember

"Not in the trace" has three meanings. (1) The event happened somewhere else: inside the SSD, on the CPU, on another link. (2) It happened on this link but the capture missed it: window, filter, lost lock. (3) It did not happen. Only (3) is a finding about the system. A timeout is visible only as (3) plus timestamps: a request with no matching completion within N µs in a window with no gaps.
