PART V-B

Physical and Link-Layer Errors Only an Analyzer Sees

The AER registers in Part V tell you that a Receiver Error or a Bad TLP happened, and on which device. They do not tell you which lane, which symbol, which packet, how often, or what came just before. A protocol analyzer does. This part lists the physical-layer, data-link-layer and Flit-layer failures you can find in a PEX trace, plus the false errors the analyzer itself can create. Most cards here have the verdict Visible, because these failures live on the wire by definition. The hard part is telling a real link problem from a probe problem. Read Part I-B first for the capture model. Card ids use the prefix X-. Where Part V already has an AER card for the same event, the X- card links to it and covers only the trace side.

V-B.1 Physical Layer: Symbols, Blocks, Ordered Sets and Training

V-B.1.1 Why this chapter exists

Physical-layer faults are the most common cause of "the SSD sometimes vanishes" and "Gen4 drive runs at Gen3 speed". They are also the faults least visible to software: a correctable Receiver Error bit, perhaps a rate-limited line in dmesg, and nothing at all at the NVMe level. In a trace each one has a precise signature: a lane, a direction, a symbol or block, and what the link did next.

  • Recognise symbol, disparity, sync-header, ordered-set and framing errors in a trace and tie them to a lane and direction.
  • Tell legitimate nullified TLPs from real framing faults.
  • Read link training in the trace: speed and width changes, Recovery entries, equalization phases and presets, Polling.Compliance entry.
  • Know which physical findings need confirmation without the probe.

X-01Invalid 10b symbol (code violation) on a Gen1/Gen2 lane ReportedPCIe Physical
In a PEX trace
Visible The analyzer flags a symbol that is not a valid 10b code word on lane N in one direction. Look for the TLP or DLLP containing it, then a Nak (for a TLP) or a missing Ack and replay-timer replay, from the receiver in the opposite direction.
What happens
One or more bits flip on a lane, so the 10-bit group decodes to no valid 8-bit value. The receiver reports a Receiver Error and discards the packet containing the symbol. The transmitter replays it.
How it shows up
On the receiving device: AER Correctable Error Status Receiver Error (PCI_ERR_COR_RCVR, "RxErr"), ERR_COR message, often Bad TLP as well. Nothing at the NVMe level.
Spec basis
PCIe Base Specification, Physical Layer 8b/10b decode rules and Receiver Error reporting; AER Correctable Error Status.
Typical causes
Marginal channel (long trace, worn connector, riser), crosstalk, a reference-clock problem, a failing transmitter, or the analyzer's own probe (X-27).
How to detect / prove
Count flagged symbols per lane and direction over a fixed workload. Real errors on the link match: the receiver in the opposite direction sends a Nak and the device's AER RxErr counter rises (/sys/bus/pci/devices/<BDF>/aer_dev_correctable). Errors on one lane only point to that lane's channel. If the analyzer can show raw 10b codes, a single-bit difference from a valid code suggests noise, while a whole-symbol garble suggests a lock or alignment problem.
Linux v7.2 source
drivers/pci/pcie/aer.c: aer_irq, aer_isr_one_error, aer_print_error, pci_dev_aer_stats_incr, aer_ratelimit. See also L-01.
Test to provoke it
SAFE: run the same workload through different slots or extenders and compare counts. EXPERT: add a lossy fixture to the channel, or force Gen2 on a channel built for Gen1.
X-02Running-disparity error (Gen1/Gen2) ReportedPCIe Physical
In a PEX trace
Visible The analyzer flags a valid 10b code with the wrong disparity for the current running disparity on lane N. Often a symbol error on a nearby symbol accompanies it, because the actual bit error can be several symbols before the place disparity catches it.
What happens
8b/10b keeps the count of ones and zeros balanced. Each code word has a positive and a negative form, chosen by the running disparity. A bit error can produce a valid code word of the wrong form, which the receiver detects only as a disparity violation.
How it shows up
Receiver Error in AER on the receiving side, like X-01. The packet is discarded and replayed.
Spec basis
PCIe Base Specification 8b/10b rules (inherited from the IBM 8b/10b code); Receiver Error.
Typical causes
Same as X-01. A disparity error with no symbol error nearby is a strong hint of a single bit flip.
How to detect / prove
Because the error position is uncertain, look at the packet that the receiver Nak'd, not only the flagged symbol. A cluster of disparity errors right after electrical-idle exit, on every lane at once, is usually the analyzer regaining lock (X-28), not a link problem.
Linux v7.2 source
As X-01 (PCI_ERR_COR_RCVR in include/uapi/linux/pci_regs.h).
Test to provoke it
As X-01. Disparity errors cannot be injected from software on standard hardware. Use an exerciser that can send bad disparity on purpose (EXPERT).
X-03Invalid sync header in a 128b/130b block (Gen3–Gen5) ReportedPCIe Physical
In a PEX trace
Visible The analyzer flags a block on lane N whose 2-bit sync header is 00b or 11b. Then look for what the link does: Recovery (TS1 ordered sets in both directions) usually follows within microseconds, and TLPs in flight are Nak'd or replayed after Recovery.
What happens
Each 130-bit block starts with a sync header that says "data block" or "ordered-set block". Only two of the four values are valid. A bit error in the header means the receiver cannot tell how to interpret the next 128 bits, so the data stream is lost on that lane.
How it shows up
Receiver Error (RxErr) on the receiving device. The receiver typically treats it as a framing error and directs the LTSSM to Recovery verify in spec. Linux sees an RxErr burst and possibly a link-speed or width change notice.
Spec basis
PCIe Base Specification, 128b/130b encoding, sync header and data-stream framing rules. A vendor PHY register guide (Efinix) lists "00 and 11 are Invalid Sync Headers".
Typical causes
Gen3+ channel margin, bad equalization result (X-13), retimer problems, block-alignment loss after L0s/L1 exit.
How to detect / prove
Count invalid sync headers per lane. Check that each one is followed by a Recovery entry. If the analyzer reports invalid sync headers and the link stays in L0 without any Recovery, the analyzer lost block alignment (X-28). Use Lane Margining at the Receiver (Gen4+) to measure margin on the suspect lane.
Linux v7.2 source
drivers/pci/pcie/aer.c (RxErr), drivers/pci/pcie/bwctrl.c: pcie_bwnotif_irq (records speed/width changes after Recovery).
Test to provoke it
CAUTION: step receiver margining toward the eye edge on a Gen4+ platform that supports it. EXPERT: insert a lossy channel.
X-04Invalid or malformed ordered set (TS1/TS2, EIEOS, EIOS, SDS, SKP) DegradedPCIe Physical
In a PEX trace
Visible The analyzer shows an ordered set whose identifier symbols, length or fields are wrong. Examples: a TS1 with a lane number that differs from the other lanes' pattern, reserved bits set, an EIEOS with the wrong pattern, an ordered-set block in the middle of a data stream without a preceding EDS (Gen3+).
What happens
Ordered sets drive link training and maintenance. A malformed one is ignored by a robust receiver. If it is ignored too often, training takes longer, falls back to a lower speed or width, or times out.
How it shows up
Often nothing directly. Indirectly: longer link-up time, Recovery entries, LnkSta lower than LnkCap, or RxErr when the ordered set breaks framing rules (Gen3+).
Spec basis
PCIe Base Specification, ordered-set definitions (TS1/TS2 fields: Link Number, Lane Number, N_FTS, data-rate identifier, training control, equalization fields) and Gen3+ data-stream rules (EDS before an ordered set).
Typical causes
Firmware or PHY bugs in one link partner (often a new controller or retimer), wrong lane numbering on a board, bit errors in ordered sets.
How to detect / prove
Compare the same ordered set across lanes. All lanes of a link must agree on the link number and the training fields, and lane numbers must be consecutive. Repeated identical malformed ordered sets point to a design bug. Random ones point to bit errors. Use the analyzer's LTSSM view to see which state each one belongs to.
Linux v7.2 source
No direct visibility. Effects appear through drivers/pci/pci.c: pcie_wait_for_link / pcie_retrain_link and drivers/pci/probe.c: pcie_update_link_speed.
Test to provoke it
EXPERT: use an exerciser to send TS1/TS2 with bad fields and watch whether the DUT ignores them correctly.
X-05Framing error: bad STP/SDP/END/EDB placement or token (TLP or DLLP boundaries lost) ReportedPCIe Physical
In a PEX trace
Visible The analyzer flags a packet with no valid end, a start token in an illegal lane or position, an STP whose length field does not match the data that follows, an STP frame-CRC or parity mismatch (Gen3+), or an invalid token in a data block. The partial packet is shown truncated or as an error item. Look for Recovery (Gen3+) and a replay afterwards.
What happens
The receiver loses track of where packets start and end. In 8b/10b mode framing uses K symbols (STP…END for TLPs, SDP…END for DLLPs). In 128b/130b mode the STP token carries the TLP length, protected by a small CRC and a parity bit. Any inconsistency means the rest of the data stream on that link cannot be trusted.
How it shows up
Receiver Error on the receiving side. In 128b/130b mode the receiver must also enter Recovery to re-establish the data stream verify in spec. Packets in flight are replayed after Recovery.
Spec basis
PCIe Base Specification, packet-framing rules for 8b/10b and 128b/130b (framing tokens STP, SDP, END, EDB, EDS, IDL; Gen3+ framing-error rules).
Typical causes
Bit errors that hit a framing symbol or token; a transmitter bug (wrong STP length, packing tokens into illegal positions on wide links); lane-to-lane skew beyond the deskew buffer (X-07).
How to detect / prove
Separate random from systematic. A framing error that recurs with the same TLP type and length is a transmitter bug. Prove it with the exact bytes: STP length versus the actual number of Dwords up to the next token. A random framing error with a physical error on the same lane just before it is a channel problem.
Linux v7.2 source
drivers/pci/pcie/aer.c (RxErr, BadTLP). See L-01, L-02.
Test to provoke it
EXPERT: an exerciser sending a TLP with a mismatched STP length, or an END-less packet, then checking that the DUT recovers and replays.
X-06Nullified TLP (EDB end, inverted LCRC): legal by design, wrong when unexpected SilentPCIe Data Link
In a PEX trace
Visible A TLP ending with EDB (8b/10b) or followed by an EDB token (128b/130b) and carrying the bitwise inverse of the correct LCRC. Analyzers show it as "nullified" rather than as an LCRC error. Check that no Ack or Nak refers to it and that the next TLP reuses the same sequence number.
What happens
A switch or retimer that forwards a TLP before it has fully arrived (cut-through) may discover an error at the end. It then ends the packet with EDB and inverts the LCRC. The receiver silently drops it: no Nak, no error, and the sequence number is not consumed.
How it shows up
Normally nothing, by design. If the nullified TLP's LCRC is not exactly inverted, the receiver treats it as a Bad TLP (Receiver Error / Bad TLP in AER).
Spec basis
PCIe Base Specification, Data Link Layer rules for nullified TLPs; framing (EDB).
Typical causes
Legitimate: cut-through forwarding in a switch that saw an error upstream. Suspicious: an endpoint SSD nullifying its own TLPs (it has no upstream source to forward), or many nullified TLPs in a row.
How to detect / prove
Count nullified TLPs per source. On a direct Root-Port-to-SSD link with no switch, nullified TLPs from the SSD indicate an internal transmit-path problem. Nullified TLPs from a switch indicate errors on the switch's other link. Probe that link next.
Linux v7.2 source
None: nullified TLPs raise no AER bit when correctly formed.
Test to provoke it
EXPERT: inject errors on a switch's upstream link with cut-through enabled and capture the downstream link.
X-07Lane-to-lane skew beyond the receiver's deskew capability ReportedPCIe Physical
In a PEX trace
Visible The analyzer measures arrival skew between lanes on ordered sets (SKP, TS, EIEOS, SDS) and flags a deskew failure when the same ordered set does not arrive on all lanes within its window. Symptoms: packets with corrupted Dwords on one lane, framing errors (X-05), training that ends at a narrower width.
What happens
Lanes of one link travel through slightly different lengths of trace, cable and retimer. The receiver aligns them using a common marker (COM in SKP/TS ordered sets for 8b/10b; SKP, SDS or EIEOS block boundaries for 128b/130b). If skew is larger than the receiver's deskew buffer, bytes from different lanes are combined in the wrong order.
How it shows up
Receiver Errors and replays, or the link trains at a reduced width that leaves out the badly skewed lanes (L-25).
Spec basis
PCIe Base Specification, lane-to-lane skew limits for transmitter and receiver (per data rate). One patent summary quotes 20 ns receiver skew tolerance at Gen1 and 8 ns at Gen2 uncertain. Limits for Gen3 and later are tighter; check the spec table for your rate.
Typical causes
Mismatched cable lengths, retimers that add different numbers of SKP symbols per lane, board routing errors, separate-clock (SRIS/SRNS) configurations with dynamic skew.
How to detect / prove
Read the analyzer's per-lane skew report for the same capture at each speed. Skew that grows with speed changes or temperature points to the channel. A constant skew that the analyzer reports but the device tolerates (no RxErr) is within the device's capability. The analyzer's own limit may be tighter (X-29).
Linux v7.2 source
Effects only: drivers/pci/pci.c: __pcie_print_link_status reports reduced bandwidth; AER RxErr counters.
Test to provoke it
EXPERT: insert unequal-length cable pairs on a cabled link (MCIO, OCuLink) and record the width and errors.
X-08Lane reversal or polarity inversion not handled (wrong width, failed training) DegradedPCIe Physical
In a PEX trace
Visible In Polling and Configuration, TS1/TS2 lane numbers show whether lanes are reversed (lane 0 of one partner meets lane N−1 of the other). Inverted symbols in TS1/TS2 on a lane show uncorrected polarity. Failure appears as a link trained at x1 or a reduced width, or a loop in Configuration.
What happens
PCIe lets board designers reverse lane order and swap D+/D−. Every receiver must detect and undo polarity inversion on each lane during Polling. Lane reversal support is optional on one side, so it works only if at least one partner handles it. When neither handles it, or a device bug prevents it, the link trains narrow or not at all.
How it shows up
LnkSta width lower than LnkCap (lspci -vvv: "LnkSta: … Width x1 (downgraded)"), lower bandwidth, possibly no link at all.
Spec basis
PCIe Base Specification, Polling (polarity inversion detection from TS1/TS2 symbols) and Configuration (lane number negotiation, lane reversal).
Typical causes
Board layout reversed on a device that cannot reverse; adapter cards that swap pairs; a known device erratum (for example Intel's advisory that automatic polarity inversion is not guaranteed in one FPGA family under certain conditions).
How to detect / prove
Capture link training from power-on with the analyzer configured for the physical lane map. Compare lane numbers in TS1/TS2 from both ends. Note that the analyzer must also be told about any reversal on the interposer, otherwise it reports false errors (X-29).
Linux v7.2 source
drivers/pci/pci.c: __pcie_print_link_status (prints available bandwidth and the limiting link); PCI_EXP_LNKSTA_NLW in include/uapi/linux/pci_regs.h.
Test to provoke it
EXPERT: use an adapter or interposer that reverses lanes and check both training and analyzer decoding.
X-09Unexpected link width or speed renegotiation during operation DegradedPCIe Physical
In a PEX trace
Visible In the middle of traffic, both directions switch to TS1 ordered sets (Recovery), then TS2 with a changed data-rate field, a speed change (Recovery.Speed), or Configuration with fewer lanes. Traffic resumes at the new speed or width. The analyzer must follow the change; if it does not, the rest of the trace is undecodable.
What happens
A port can change speed or width autonomously (for example after repeated errors, or for power) or because software asked for it. A drop from Gen4 to Gen1, or from x4 to x1, keeps the SSD working at a fraction of its bandwidth.
How it shows up
Link Status bits Link Bandwidth Management Status (LBMS) or Link Autonomous Bandwidth Status (LABS) set on the downstream port. Linux v7.2's bandwidth controller handles that interrupt and updates the cached link speed. No NVMe error, only lower throughput.
Spec basis
PCIe Base Specification, LTSSM Recovery and Configuration; Link Status register (LBMS, LABS), Link Control 2 Target Link Speed.
Typical causes
Hardware autonomous fallback after errors; equalization failure at the higher rate; thermal or power policy; software writes to Target Link Speed followed by Retrain Link.
How to detect / prove
In the trace: find the first TS1 after L0 and look backwards for the physical errors or EIOS that triggered it. Note who started Recovery: the direction where TS1 appears first. On the host: lspci -vvv LnkSta and the sysfs current_link_speed / current_link_width attributes, sampled over time.
Linux v7.2 source
drivers/pci/pcie/bwctrl.c: pcie_bwnotif_irq (reads PCI_EXP_LNKSTA, records LBMS in PCI_LINK_LBMS_SEEN, calls pcie_update_link_speed); drivers/pci/quirks.c: pcie_failed_link_retrain (forces 2.5 GT/s when a link fails to come up and LBMS was seen, then tries to lift the restriction). See L-25.
Test to provoke it
CAUTION: on a test system, change the Target Link Speed and retrain through the kernel's bandwidth-control interface, or physically degrade one lane, and capture the transition.
X-10SKP ordered-set errors: missing, too frequent, malformed, or inside a packet ReportedPCIe Physical
In a PEX trace
Visible Only if SKP ordered sets are not filtered. Measure the interval between SKP OS per direction, check their length and format, and look for SKP symbols where they are not allowed (inside a TLP in 8b/10b). The analyzer flags format errors. Interval violations usually need a timing search.
What happens
SKP ordered sets let receivers compensate for small clock-frequency differences between the two ends. Retimers and receivers add or remove SKP symbols. At Gen1/2 a SKP OS is COM followed by SKP symbols. At Gen3+ it is a block of SKP bytes, an end marker and LFSR/parity bytes, and at Gen4+ it can carry margining commands. Too few SKPs over time overflow or underflow the receiver's elastic buffer.
How it shows up
Receiver Errors from elastic-buffer overflow or underflow; with separate reference clocks (SRIS) and wrong SKP interval settings, periodic error bursts.
Spec basis
PCIe Base Specification, clock tolerance compensation: SKP scheduling interval (different for common-clock, SRNS and SRIS modes), SKP OS format for 8b/10b and 128b/130b. The exact intervals depend on mode and rate verify in spec.
Typical causes
SRIS (separate reference clocks with spread spectrum) not enabled on both ends when it is required; retimer bugs; transmitter scheduling bugs under heavy back-to-back traffic.
How to detect / prove
Export SKP timestamps per direction and compute the distribution of intervals; compare with the spec maximum for the clocking mode. Check the platform clocking: whether the SSD uses the slot's reference clock or its own.
Linux v7.2 source
RxErr counters only (drivers/pci/pcie/aer.c).
Test to provoke it
EXPERT: run a link with separate spread-spectrum clocks and SRIS disabled, under heavy traffic.
X-11Recovery storm: the LTSSM keeps leaving L0 DegradedPCIe Physical
In a PEX trace
Visible Repeated bursts of TS1/TS2 between stretches of traffic: L0 → Recovery.RcvrLock → Recovery.RcvrCfg → Recovery.Idle → L0, many times per second. Each burst stalls all traffic for microseconds to milliseconds. Look at what precedes each entry: physical errors, replay timeouts, REPLAY_NUM rollover, or nothing (a partner's internal decision).
What happens
Recovery re-establishes bit, symbol or block lock and is how a link handles errors and speed changes. A healthy link enters it rarely. A link that enters it constantly works, but with large latency spikes and reduced bandwidth.
How it shows up
Correctable AER errors (RxErr, Replay Timer Timeout, REPLAY_NUM Rollover) on one or both ends, rate-limited in dmesg. NVMe I/O latency spikes, sometimes host timeouts.
Spec basis
PCIe Base Specification, LTSSM Recovery substates and entry conditions.
Typical causes
Marginal channel, equalization that converged to a poor preset, ASPM L1 exit problems, retimer firmware bugs.
How to detect / prove
Count Recovery entries per second from the LTSSM view, and plot them against workload and time. Classify each entry by its trigger (error, rollover, speed change request, idle exit). Confirm with both ends' AER counters over the same period.
Linux v7.2 source
drivers/pci/pcie/aer.c (correctable error handling and rate limiting through aer_ratelimit). See L-26.
Test to provoke it
CAUTION: enable ASPM L1 on a link with marginal timing, or use receiver margining to reduce margin, and capture.
X-12LTSSM stuck or looping in training (Polling.Compliance, Detect/Polling loop, Configuration loop) Timer onlyPCIe Physical
In a PEX trace
Visible Instead of TS1/TS2 progressing to L0, the trace shows the compliance pattern on some lanes (Polling.Compliance), TS1 exchanges that never advance to TS2, or the same Detect → Polling → Detect cycle repeating every few tens of milliseconds. No TLPs at all, or none after a certain point.
What happens
Polling.Compliance is a test mode. A port enters it when it detects a receiver on a lane but receives no TS1s there (or when told to by the Enter Compliance bit or a test signal). In normal operation this means one side sees a partner that is not training. Other loops come from mismatched link numbers, lanes that never achieve lock, or timeouts in Configuration.
How it shows up
The SSD never appears in lspci, or appears after a long delay. On the Root Port, Data Link Layer Link Active never sets. Linux waits and then gives up, or applies the 2.5 GT/s retrain quirk.
Spec basis
PCIe Base Specification, LTSSM Detect, Polling (Active, Compliance, Configuration) and Configuration states, including their timeouts.
Typical causes
Broken lane or missing termination on one side, wrong pin assignment, a test strap left asserted (an Altera knowledge-base entry lists a test input bit and PCB pin errors as causes), power sequencing or PERST# timing, an SSD firmware hang during boot.
How to detect / prove
Capture from PERST# deassertion with an analyzer that brings out PERST#. Measure time from PERST# to first TS1 from each side, and find which side stops progressing. Note which lanes show the compliance pattern.
Linux v7.2 source
drivers/pci/pci.c: pcie_wait_for_link, pcie_wait_for_link_status (polls PCI_EXP_LNKSTA_DLLLA or PCI_EXP_LNKSTA_LT); drivers/pci/quirks.c: pcie_failed_link_retrain. See L-39, T-02.
Test to provoke it
EXPERT: tape off or disconnect a lane's receive pair on an adapter, or hold the SSD in reset, and capture training from power-on.
X-13Equalization failure or poor preset (Gen3+): fallback to a lower speed, or high error rate DegradedPCIe Physical
In a PEX trace
Visible Equalization phases appear as TS1 ordered sets in Recovery.Equalization with preset and coefficient fields. A failure shows as phases that time out, repeated requests, lanes finishing on different presets, or a retrain back to the old speed. A Teledyne LeCroy blog notes that lanes ending on different presets (for example P6 on some, P10 on others) are a red flag, since P10 is meant for boost-limit testing.
What happens
At 8 GT/s and above, the two ends tune each other's transmitter equalization in phases 0–3. In phase 2 the upstream port asks the downstream port to adjust its transmitter, and in phase 3 the reverse happens. A bad result leaves a link that works with little margin, or makes the port give up the higher rate.
How it shows up
Link Status 2 equalization status bits (Equalization Complete, Phase 1/2/3 Successful) clear for the failing rate; link at a lower speed; or a link at full speed with steady RxErr counts.
Spec basis
PCIe Base Specification, Link Equalization Procedure, Lane Equalization Control registers (Linux: PCI_SECPCI_LE_CTRL, PCI_PL_16GT_LE_CTRL, PCI_PL_32GT_LE_CTRL, PCI_PL_64GT_LE_CTRL), Link Status 2 equalization bits.
Typical causes
Channel loss outside the budget, wrong preset hints from firmware, retimer equalization bugs, a PHY that does not evaluate requests in time.
How to detect / prove
Trigger on the first TS1 with the equalization bit set after a speed change, or on a speed change, and capture the whole procedure. Tabulate each lane's requested and final preset. Correlate with per-lane errors after equalization. For the analog view, Teledyne LeCroy describes CrossSync PHY, which time-aligns an oscilloscope capture with the protocol trace.
Linux v7.2 source
include/uapi/linux/pci_regs.h (Lane Equalization Control registers above); effects through drivers/pci/pcie/bwctrl.c: pcie_bwnotif_irq.
Test to provoke it
EXPERT: force a specific preset through platform firmware settings or the device's debug interface, then capture the next equalization and its error rate.
X-14Electrical-idle glitches and L0s/L1 entry or exit failures DegradedPCIe Physical
In a PEX trace
Partly visible Visible: EIOS before idle, the idle period, EIEOS/FTS/TS1 on exit, PM DLLPs (PM_Enter_L1, PM_Request_Ack) and the TLP that woke the link. Not reliable: the exact moment of a short glitch, because the analyzer itself must re-lock after idle and may lose the first symbols (X-28).
What happens
During L0s and L1 the transmitter stops driving the lane. On exit, the receiver must regain lock in a limited time (N_FTS fast training sequences for L0s; Recovery for L1). Problems: idle entered without EIOS, a lane drifting into idle on its own (inferred idle), too few FTS for the receiver to lock, or an exit that fails and falls into Recovery or Detect.
How it shows up
Latency spikes after idle, RxErr bursts at exit, sometimes a link drop. Disabling ASPM makes it go away.
Spec basis
PCIe Base Specification, Electrical Idle rules, EIOS/EIEOS, L0s (N_FTS) and L1 entry/exit, ASPM.
Typical causes
N_FTS advertised too small, CLKREQ# handling problems in L1 substates, reference-clock gating issues, PHY bugs at low-power exit.
How to detect / prove
Measure each exit: time from first EIEOS/FTS to the first good TLP, and count errors in that window. Compare with ASPM disabled (lspci -vvv LnkCtl ASPM field; the kernel parameter pcie_aspm=off). If errors appear only in the analyzer and not in either device's counters, suspect analyzer re-lock.
Linux v7.2 source
drivers/pci/pcie/aspm.c (ASPM policy). See L-37, T-14.
Test to provoke it
CAUTION: enable ASPM L0s/L1 (and L1 substates where supported) with a bursty, low-duty workload that makes the link enter and exit idle thousands of times.
