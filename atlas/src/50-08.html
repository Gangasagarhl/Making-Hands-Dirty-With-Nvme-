VI.3 The Linux Quirk Tables: A Catalogue of Real Field Bugs

VI.3.1 Why the quirk table is evidence

Most failure lists are built from specifications ("what could go wrong"). The Linux NVMe quirk table is different: every entry exists because a shipping device misbehaved for real users, and someone had to change the kernel to cope. Documentation/nvme/feature-and-quirk-policy.rst says so directly. Quirks exist because "implementations of open standards fail to correctly implement parts of the standards". They are meant for "widely available hardware, usually consumer", are "a last resort, if no firmware updates or other workarounds are available from the vendor", and "will not be added to the Linux kernel for hardware that isn't available on the mass market". So the table is biased toward consumer drives and does not show enterprise bugs that were fixed in firmware before release. Within that bias it is a public, versioned, reviewed record of what goes wrong in shipping SSDs.

In Linux v7.2 there are four places where quirks are applied to an NVMe PCIe controller:

  1. The PCI ID table nvme_id_table[] in drivers/nvme/host/pci.c: 81 entries, of which 79 carry at least one quirk flag. The last entry, PCI_DEVICE_CLASS(PCI_CLASS_STORAGE_EXPRESS, 0xffffff), is the generic class match, and Apple 0x2003 has none.
  2. Model/firmware-string quirks core_quirks[] in drivers/nvme/host/core.c, matched on Identify Controller VID, model number and firmware revision. Four entries.
  3. Board-specific (DMI) combinations in check_vendor_combination_bug() in pci.c: the drive is fine except in specific laptops or boards. Also the ACPI "StorageD3Enable" platform hint (acpi_storage_d3), logged as platform quirk: setting simple suspend.
  4. User override: new in this version, the nvme.quirks=VID:DID:name[,^name] module parameter (quirks_param_set, nvme_parse_quirk_names), which uses the names from nvme_quirk_name(). A ^ prefix disables a quirk. Unknown names fail with nvme: unrecognized quirk %s.

The PCI core adds device-specific reset and link quirks in drivers/pci/quirks.c (section VI.3.5).

💡 Senior insight

The table contains no "flush doesn't flush" or "trim doesn't trim" quirk, because the kernel cannot work around those. A quirk is only possible when the host can avoid the broken feature. Silent data bugs (Part on silent failures) therefore never show up here, which does not mean they are rare. The DISABLE_WRITE_ZEROES entries are the closest thing: devices where Write Zeroes did not reliably zero, discovered because users checked.

C-22Drive drops off the bus in its deepest power state (APST / deepest PS) Timer onlyNVMe power mgmt
In a PEX trace
Partly visible The Set Features APST command and its table payload are visible. The autonomous entry into the deepest state is not. A failed exit appears as link electrical idle that never ends, or as the first doorbell after idle getting no SQE fetch. See C-07 and L-37.
What happens
The kernel comments describe it: Samsung SM951/PM951/950 PRO on two Dell laptops "drop off the PCIe bus randomly when APST is on and uses the deepest sleep state"; Samsung 960 EVO "drops off the PCIe bus after system suspend" on two ASUS boards; the Toshiba THNSF5256GPUK "seems to die using any APST states"; "NVMe SSD drops off the PCIe bus after system idle for 10 hours on a Lenovo N60z board".
How it shows up
After idle: an I/O timeout, then controller is down; will reset: CSTS=0xffffffff ... and the power-saving hint. The reset fails, and the device is gone until power-cycled.
Spec basis
NVMe: APST, power state descriptors (non-operational states, ENLAT/EXLAT).
Typical causes
Firmware or PHY bugs in the deepest state, often only with particular platform clocking or power delivery. That is why several quirks are DMI-matched.
How to detect / prove
Reproduce with a long idle soak. Confirm the fix with nvme_core.default_ps_max_latency_us set to just below the deepest state's exit latency (Linux picks APST targets using this limit), or with nvme.quirks=VID:DID:no_deepest_ps.
Linux v7.2 source
pci.c: check_vendor_combination_bug; core.c: core_quirks[], nvme_configure_apst.
Test to provoke it
SAFE: idle soaks of 1, 4 and 12 hours, then I/O. CAUTION: 500× s2idle suspend/resume.
C-23Write Zeroes (or Deallocate-as-zero) reported successful but data not zeroed SilentNVMe command
In a PEX trace
Partly visible The Write Zeroes SQE (opcode 08h: SLBA, NLB, DEAC bit) or DSM Deallocate SQE (09h with the range list as a DMA payload) and its successful CQE are visible. Whether the media was zeroed is not. Only a later Read's CplD/MWr payload crossing the link (non-zero data where zeros were promised) proves it.
What happens
19 ID-table entries carry NVME_QUIRK_DISABLE_WRITE_ZEROES ("Broken Write Zeroes"): Linux stops issuing Write Zeroes to them. Two older Intel IDs carry NVME_QUIRK_DEALLOCATE_ZEROES ("deterministically returns 0's on reads to logical blocks that deallocate was called on"). For those, Linux v7.2 implements block-layer write-zeroes with a Deallocate (nvme_setup_write_zeroes calls nvme_setup_discard) and advertises unlimited write-zeroes size. If such a device stopped returning zeroes after deallocate (a firmware change, or a partial-block range), write-zeroes would be silently wrong. This is the user's "trim completes but nothing happens" scenario, with the kernel depending on it.
How it shows up
Nothing. Both commands return Success. On a quirked drive, /sys/block/nvme0n1/queue/write_zeroes_max_bytes is 0 (DISABLE) or very large (DEALLOCATE_ZEROES).
Spec basis
NVMe NVM Command Set: Write Zeroes (DEAC), Dataset Management Deallocate, deallocated logical block read behaviour (DLFEAT in Identify Namespace).
Typical causes
Firmware implementing Write Zeroes as a metadata-only operation with bugs at range boundaries. Deallocate granularity larger than the request.
How to detect / prove
Write a pattern, issue Write Zeroes (nvme write-zeroes) or blkdiscard -z, read back, compare. Vary alignment and length, including sub-granularity ranges. Do it across a power cycle too.
Linux v7.2 source
core.c: nvme_setup_write_zeroes, the NVME_QUIRK_DEALLOCATE_ZEROES check in queue-limit setup, NVME_QUIRK_DISABLE_WRITE_ZEROES checks around max_zeroes_sectors.
Test to provoke it
CAUTION (destroys data in range): fio verify pattern write, blkdiscard -z -o OFF -l LEN, read-back verify; repeat for 4 KiB-misaligned ranges.
C-24Bogus or duplicate namespace identifiers (EUI-64 / NGUID / UUID) ReportedNVMe identify
In a PEX trace
Visible The Identify Namespace (CNS 00h) and Namespace Identification Descriptor list (CNS 03h) data are DMA'd to the host as MWr payloads, so the duplicate or garbage EUI-64/NGUID/UUID bytes can be read directly. Compare captures from two drives of the same model.
What happens
The most-quirked bug in the table (30 IDs): drives report all-zero, constant or duplicated identifiers. Two drives of the same model then look like the same namespace, which breaks /dev/disk/by-id, multipath and RAID membership.
How it shows up
With the quirk: Ignoring bogus Namespace Identifiers. Without it, Linux v7.2 detects duplicates in the subsystem and, for non-shared PCIe namespaces, logs clearing duplicate IDs for nsid %d and use of /dev/disk/by-id/ may cause data corruption, then sets NVME_QUIRK_BOGUS_NID itself. For fabrics or shared namespaces it refuses the namespace: ignoring nsid %d because of duplicate IDs. Also: missing or invalid SUBNQN field. (IGNORE_DEV_SUBNQN cases).
Spec basis
NVMe Base Specification: namespace identifiers must be globally unique (EUI-64, NGUID, UUID), Namespace Identification Descriptors, SUBNQN.
Typical causes
Controller vendors' reference firmware shipping with placeholder IDs. OEMs not programming unique values.
How to detect / prove
nvme id-ns /dev/nvme0n1 | grep -E 'nguid|eui64' on two drives; nvme ns-descs; ls -l /dev/disk/by-id/.
Linux v7.2 source
core.c: nvme_identify_ns_descs paths (NVME_QUIRK_BOGUS_NID checks), nvme_global_check_duplicate_ids / namespace-head checks around "clearing duplicate IDs".
Test to provoke it
SAFE: install two identical drives and compare identifiers.
C-25MSI (not MSI-X) never fires Timer onlyPCIe / interrupt
In a PEX trace
Visible The CfgWr enabling MSI (MSI Control Enable=1, address/data programmed), then CQE MWrs with no following MSI MWr to the programmed address.
What happens
NVME_QUIRK_BROKEN_MSI: "MSI (but not MSI-X) interrupts are broken and never fire" (SanDisk SN530, SN550). If the platform falls back to MSI (for example a vector shortage, or MSI-X disabled), every completion relies on timeout polling.
How it shows up
Without the quirk: "completion polled" for every command, and probe takes minutes. With it, Linux clears PCI_IRQ_MSI so only MSI-X or INTx are used.
Spec basis
PCI: MSI capability is optional when MSI-X exists, but if advertised it must work.
Typical causes
Untested MSI path in firmware.
How to detect / prove
Force MSI (pci=nomsi forces INTx instead; to test MSI specifically, disable MSI-X on a test kernel or with the nvme.quirks parameter on another drive). Watch /proc/interrupts.
Linux v7.2 source
pci.c: nvme_pci_enable, nvme_setup_irqs.
Test to provoke it
CAUTION: test-kernel modification.
C-26DMA above 48 bits mishandled SilentPCIe DMA
In a PEX trace
Visible Compare the 64-bit addresses in PRP entries (in the SQE and PRP lists) with the addresses of the device's MRd/MWr. A device that truncates the upper bits issues TLPs to the wrong (lower) address.
What happens
NVME_QUIRK_DMA_ADDRESS_BITS_48: "does not properly handle DMA addresses over 48 bits" (six Amazon device IDs). Without the quirk, a buffer above 248 could be read from or written to a truncated address: silent corruption of unrelated memory, or an IOMMU fault if one is present.
How it shows up
With the quirk, Linux sets a 48-bit DMA mask (dma_set_mask_and_coherent(..., DMA_BIT_MASK(48))) and nothing is visible. Without it, corruption or IOMMU faults appear only on systems with very large IOVA/physical spaces.
Spec basis
NVMe PRP/SGL entries are 64-bit addresses. PCIe supports 64-bit addressing.
Typical causes
Hardware DMA engines with truncated address registers.
How to detect / prove
Force IOVAs above 248 (IOMMU with a large address width, or a test DMA allocator), then data-verify.
Linux v7.2 source
pci.c: nvme_pci_alloc_dev.
Test to provoke it
EXPERT: platform-specific.
C-27Controller needs a delay before CSTS.RDY can be checked Timer onlyNVMe registers
In a PEX trace
Visible The CC EN=0 MWr followed by a CSTS MRd within milliseconds. On an affected device that read misbehaves: it returns stale RDY=1 forever, gets no completion, or is followed by a failed enable. With the quirk the gap is about 2.3 s.
What happens
NVME_QUIRK_DELAY_BEFORE_CHK_RDY: "needs a delay before starts checking the device readiness" (Seagate Nytro, HGST and WDC SN200 adapters, Memblaze Pblaze4, Samsung PM1725/PM1725a, and the Samsung Portable SSD X5 by string). Linux sleeps NVME_QUIRK_DELAY_AMOUNT = 2300 ms after clearing CC.EN, before polling. The core quirk comment adds that the X5 "fails initialization without a delay ... and has a whole set of other problems" and shares a PCI ID with the internal 970 Evo Plus, which does not need the quirk. That is why it is matched by model string.
How it shows up
Without the quirk: Device not ready; aborting reset or initialisation failures at probe.
Spec basis
NVMe: CSTS must reflect state transitions within CAP.TO, and register reads should always be valid.
Typical causes
Controllers that reset their register block asynchronously after CC.EN=0.
How to detect / prove
Repeated resets (nvme reset) with dmesg monitoring; test with the quirk disabled through nvme.quirks=VID:DID:^delay_before_chk_rdy.
Linux v7.2 source
core.c: nvme_disable_ctrl; nvme.h: NVME_QUIRK_DELAY_AMOUNT; drivers/pci/quirks.c nvme_disable_and_flr notes these devices are not supported by its generic path.
Test to provoke it
SAFE: 1000 controller resets on a test drive.
C-28Device unusable after Function Level Reset Timer onlyPCIe / NVMe reset
In a PEX trace
Visible The CfgWr setting Initiate FLR in Device Control, then (for the failing case) every subsequent CfgRd returning Cpl with RRS or all-ones data, or an enable sequence with RDY never set. With Linux's workaround: a CC EN=0 MWr and RDY polls before the FLR (Samsung), or a 250 ms gap after it (Intel, Solidigm).
What happens
Two PCI-core quirks in drivers/pci/quirks.c. (1) "The Samsung SM961/PM961 controller can sometimes enter a fatal state after FLR where config space reads from the device return -1. We seem to be able to avoid this condition if we disable the NVMe controller prior to FLR." This is nvme_disable_and_flr(), registered for Samsung 0xa804, which logs Timeout waiting for NVMe ready status to clear after disable if RDY does not clear. (2) "Some NVMe controllers such as Intel DC P3700 and Solidigm P44 Pro will timeout waiting for ready status to change after NVMe enable if the driver starts interacting with the device too soon after FLR": delay_250ms_after_flr() for Intel 0x0953, 0x0a54 and Solidigm 0xf1ac.
How it shows up
Without the quirks: VFIO passthrough or /sys/bus/pci/devices/<BDF>/reset leaves the device dead (config reads all-ones) or the next enable fails with Device not ready; aborting initialisation.
Spec basis
PCIe: FLR, a function must be ready for config requests within the post-reset period (or use RRS). NVMe: controller state after FLR is equivalent to a controller reset.
Typical causes
Controllers whose FLR handling races with in-progress internal operations.
How to detect / prove
Loop echo 1 > /sys/bus/pci/devices/<BDF>/reset (CAUTION: unbinds traffic) followed by nvme id-ctrl; watch for "not ready ... after FLR" messages from pci_dev_wait.
Linux v7.2 source
drivers/pci/quirks.c: nvme_disable_and_flr, delay_250ms_after_flr, pci_dev_reset_methods[], __pci_dev_specific_reset.
Test to provoke it
CAUTION: 1000 FLR cycles with the device unbound from the nvme driver (or under VFIO), checking Identify after each.

🧪 Lab 27.1 — Find which quirks your drive gets, and test without them CAUTION

Objective: find out whether a drive in your fleet relies on a quirk, and whether a firmware update made the quirk unnecessary.

lspci -nn -d ::0108             # NVMe controllers with [VID:DID]
cat /sys/class/nvme/nvme0/quirks   # v7.2: quirks_show() in drivers/nvme/host/sysfs.c lists active quirk names
nvme id-ctrl /dev/nvme0 | grep -E '^(vid|mn|fr) '
# compare VID:DID against nvme_id_table[] in drivers/nvme/host/pci.c of your kernel

Steps: (1) Identify any matching ID-table, core-string or DMI quirk. (2) On a test system only, boot with nvme.quirks=VID:DID:^name to disable it. (3) Run the card's test (idle soak for NO_APST/NO_DEEPEST_PS, write-zeroes verify for DISABLE_WRITE_ZEROES, two-drive ID comparison for BOGUS_NID).

Solution

If the failure reproduces without the quirk, it is still needed with this firmware. If it does not reproduce after a long enough run, you have evidence (not proof) that the firmware fixed it. Report it upstream with the firmware revision, because quirks are keyed on IDs, not firmware, except in core_quirks[].

⚠️ Warning

Disabling DISABLE_WRITE_ZEROES or BOGUS_NID on a production system risks silent data corruption or wrong device identity. Use scratch drives only.
