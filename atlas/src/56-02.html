V-B.2 Data Link Layer: CRCs, Sequence Numbers, Ack/Nak and Credits

V-B.2.1 Why this chapter exists

The Data Link Layer is the part of PCIe that hides errors from you. A corrupted TLP is Nak'd and replayed, a lost Ack is covered by the next one, and a lost UpdateFC is covered by the next one. The NVMe command still completes successfully. The cost shows up as latency and lost bandwidth, plus a few correctable AER bits that most systems mask or never read. In a trace, the Data Link Layer is fully visible: every sequence number, every Ack and Nak, every credit update. That makes it the place to prove "the link is retrying a lot" or "the SSD stopped returning credits".

  • Follow sequence numbers, Ack/Nak and replays through a trace, and recognise legal duplicates versus real gaps.
  • Measure Ack latency and replay behaviour and compare them with spec limits.
  • Rebuild flow-control credit state from InitFC/UpdateFC DLLPs and TLP sizes, and detect violations and starvation.

X-15LCRC error on a TLP ReportedPCIe Data Link
In a PEX trace
Visible The analyzer flags a TLP whose LCRC does not match (and that does not end in EDB, so it is not nullified). Expected follow-up: a Nak in the opposite direction carrying the previous good sequence number, then replay of the bad TLP and everything after it.
What happens
A bit error inside a TLP that the physical layer did not catch (for example in a scrambled data byte, which has no code-level check) breaks the LCRC. The receiver discards the TLP, reports Bad TLP and sends a Nak.
How it shows up
AER Correctable Bad TLP (PCI_ERR_COR_BAD_TLP, "BadTLP") on the receiving device. Possibly RxErr as well. Nothing at the NVMe level.
Spec basis
PCIe Base Specification, Data Link Layer: LCRC, receive rules, Nak scheduling; AER Bad TLP.
Typical causes
Channel noise, equalization margin, retimer bugs; much less often a transmitter that computes LCRC incorrectly for some TLP format (that one repeats exactly).
How to detect / prove
For each flagged TLP, check the receiver's reaction. A Nak, or a replay of the same sequence number, proves the link partner also saw it. If the next Ack covers the flagged TLP with no replay, the receiver accepted it and the flag is an analyzer decode error (X-27). Compute the rate: LCRC errors per 109 TLPs by direction.
Linux v7.2 source
drivers/pci/pcie/aer.c: aer_print_error, pci_dev_aer_stats_incr ("BadTLP" counter). See L-02, V-35.
Test to provoke it
EXPERT: an exerciser or error-injecting retimer that corrupts LCRC on selected TLPs; or margin the receiver (CAUTION).
X-16DLLP CRC error (corrupted Ack, Nak or UpdateFC) ReportedPCIe Data Link
In a PEX trace
Visible The analyzer flags a DLLP whose 16-bit CRC fails. Follow-up depends on its type. A lost Ack is normally covered by a later Ack; if none comes in time, the transmitter's replay timer expires and it replays. A lost UpdateFC is covered by the next UpdateFC of the same type.
What happens
The receiver silently discards a DLLP with a bad CRC and reports Bad DLLP. Because Acks and UpdateFCs are cumulative, one loss is harmless. Many losses cause replays and credit stalls.
How it shows up
AER Correctable Bad DLLP (PCI_ERR_COR_BAD_DLLP). Sometimes Replay Timer Timeout on the other side.
Spec basis
PCIe Base Specification, DLLP CRC, Data Link Layer receive rules; AER Bad DLLP.
Typical causes
As X-15. DLLPs are short, so they are hit less often per packet than long TLPs.
How to detect / prove
Count bad DLLPs per direction. Check whether each was followed by a replay-timer replay (the Ack was really lost) or a later DLLP that covered it.
Linux v7.2 source
drivers/pci/pcie/aer.c ("BadDLLP"). See L-03.
Test to provoke it
EXPERT: exerciser that corrupts DLLP CRCs; watch the DUT's replay and credit behaviour.
X-17Sequence-number errors: gaps, out-of-order TLPs, Ack/Nak for a number never sent ReportedPCIe Data Link
In a PEX trace
Visible In one direction, list the sequence numbers of new (non-replayed) TLPs. They must increase by one, modulo 4096. Three patterns matter: (1) a number skipped in a new transmission, (2) a TLP with a number lower than expected that is not part of a replay (a duplicate), (3) an Ack or Nak whose number does not belong to any unacknowledged TLP.
What happens
The receiver accepts only the next expected number. A lower number (a duplicate) is discarded and an Ack is scheduled; this is legal after replays. A higher number means TLPs were lost, so the receiver discards it and sends a Nak (Bad TLP). An Ack/Nak whose number is not outstanding at the transmitter is a Data Link Protocol Error.
How it shows up
Pattern 2 (legal duplicate): nothing. Pattern 1: Bad TLP on the receiver plus a Nak. Pattern 3: uncorrectable Data Link Protocol Error (PCI_ERR_UNC_DLP, "DLP"), which is often set to Fatal severity and leads to link reset or DPC.
Spec basis
PCIe Base Specification, Data Link Layer: NEXT_RCV_SEQ, NEXT_TRANSMIT_SEQ, ACKD_SEQ rules; Data Link Protocol Error.
Typical causes
Transmitter bugs after Recovery (sequence state not kept), replay-buffer bugs, a DLLP with a corrupted but CRC-valid number (rare), or analyzer decode errors on a framing boundary.
How to detect / prove
Script it: per direction, keep the next expected number; mark replays (same number and same contents as an earlier TLP); flag new TLPs with unexpected numbers. For pattern 3, keep the set of unacknowledged numbers and check each Ack/Nak. A DLP error in AER right after the event confirms it.
Linux v7.2 source
drivers/pci/pcie/aer.c ("DLP"), recovery through drivers/pci/pcie/err.c. See L-10.
Test to provoke it
EXPERT: exerciser sending TLPs with skipped sequence numbers or Acks for unsent numbers; check that the DUT Naks or reports DLP.
X-18Nak storm: frequent Naks and replays on a link that never fails outright DegradedPCIe Data Link
In a PEX trace
Visible Many Naks per millisecond in one direction, each followed by a replay of several TLPs. Throughput drops. Look at what the Nak'd TLPs have in common: size, type, lane errors, time after idle exit, or high utilisation.
What happens
Every Nak costs a replay of all unacknowledged TLPs after the bad one. With large payloads and a deep replay buffer this can waste a large share of the bandwidth while still delivering correct data.
How it shows up
Bad TLP and RxErr correctable counters rising steadily on the receiving side; Linux prints rate-limited correctable error lines. Throughput below expectation; higher latency percentiles. No NVMe error.
Spec basis
PCIe Base Specification, Ack/Nak protocol. The spec sets no "maximum Nak rate". This is a quality problem, judged against the expected bit error rate.
Typical causes
Marginal channel, poor equalization, crosstalk under load, a receiver bug for a specific TLP pattern.
How to detect / prove
Compute replay overhead = replayed bytes ÷ total TLP bytes, per direction, per second. Plot it against workload. Errors that grow with traffic on neighbouring lanes or links suggest crosstalk or power-supply noise. Errors concentrated on one TLP type suggest a design bug.
Linux v7.2 source
drivers/pci/pcie/aer.c: aer_ratelimit (why dmesg understates the rate), pci_dev_aer_stats_incr (sysfs counters show the true count).
Test to provoke it
CAUTION: run a full-bandwidth sequential workload (for example fio with large blocks) through a marginal extender and capture.
X-19REPLAY_NUM rollover: four replays without progress force Recovery ReportedPCIe Data Link
In a PEX trace
Visible The same oldest unacknowledged sequence number is transmitted four times (the original plus replays), with no Ack advancing past it, then the transmitter enters Recovery (TS1s). After Recovery the replay continues. Count the replays per sequence number to see this pattern.
What happens
The transmitter keeps a 2-bit REPLAY_NUM. Each replay without forward progress increments it. When it rolls over, the transmitter assumes the link is in trouble and retrains. Any Ack that advances resets the counter.
How it shows up
AER Correctable REPLAY_NUM Rollover (PCI_ERR_COR_REP_ROLL, "Rollover") on the transmitter; Recovery; latency spike of the Recovery duration plus all replay time.
Spec basis
PCIe Base Specification, Data Link Layer replay mechanism; AER REPLAY_NUM Rollover.
Typical causes
The receiver cannot receive a specific TLP correctly (pattern-dependent error), a receiver that stopped sending Acks, or all Acks lost (DLLP errors in the other direction).
How to detect / prove
Look at the other direction during the replays. No DLLPs at all means the receiver is not sending Acks (a receiver bug or hang). Naks mean it receives the TLP but rejects it every time. Corrupted DLLPs mean the return path is bad.
Linux v7.2 source
drivers/pci/pcie/aer.c ("Rollover"). See L-04, T-36.
Test to provoke it
EXPERT: an exerciser that withholds Acks or Naks the same TLP repeatedly.
X-20Ack/Nak latency violation: Acks sent too late, causing replay-timer replays Timer onlyPCIe Data Link
In a PEX trace
Visible Measure, for each TLP, the time from its end to the first Ack or Nak in the opposite direction that covers it. Long tails show a slow receiver. The proof is a replay that happens with no Nak before it (a replay-timer expiry), followed by an Ack for the original that arrives just after the replay started.
What happens
The receiver must send an Ack within a latency limit that the spec gives as a table depending on link width, speed and maximum payload size. The transmitter's replay timer is set to a larger multiple of the same quantity. If the receiver delays Acks (for example because it prioritises sending its own TLPs or UpdateFCs), the transmitter times out and replays TLPs that had arrived fine.
How it shows up
AER Correctable Replay Timer Timeout (PCI_ERR_COR_REP_TIMER, "Timeout") on the transmitter, although the fault is in the receiver. Duplicate TLPs at the receiver (silently discarded). Wasted bandwidth.
Spec basis
PCIe Base Specification, Ack/Nak latency and replay-timer limit tables (depend on width, rate, Max_Payload_Size, and an internal-delay term) exact formula: verify in spec.
Typical causes
Receiver Ack scheduling bugs under heavy bidirectional traffic. An NXP/Mobiveil Linux patch (erratum A-011451) describes a controller that did not prioritise Acks behind many split completions and UpdateFCs, causing Ack-latency timeouts and replays at the link partner. Its workaround reduced the Ack latency timer.
How to detect / prove
Use the Ack-latency script in I-B.7. Report the distribution per direction and the replays with no preceding Nak. Repeat at different MPS settings: the allowed latency scales with MPS.
Linux v7.2 source
drivers/pci/pcie/aer.c ("Timeout" correctable). See L-05, T-37.
Test to provoke it
CAUTION: heavy simultaneous read and write traffic (mixed fio workload at high queue depth) so both directions are busy, then capture.
X-21Flow-control credit violation: TLP sent without credits, or credits over-advertised ReportedPCIe Data Link
In a PEX trace
Visible Rebuild credits per direction and type. Start from InitFC1/InitFC2 (this needs a capture that includes link-up), add UpdateFC values, subtract each TLP's header credit (1) and data credits (payload ÷ 16 bytes, rounded up). A TLP sent when the required credits exceed the limit is a transmitter violation. An UpdateFC that grants more outstanding credits than the field allows, or changes an infinite (0) advertisement, is a receiver violation.
What happens
Credits prevent buffer overflow at the receiver. A transmitter that ignores them overflows the receiver's buffer and TLPs are lost. A receiver that advertises nonsense credits breaks the transmitter's gating.
How it shows up
Receiver Overflow (PCI_ERR_UNC_RX_OVER, "RxOF") or Flow Control Protocol Error (PCI_ERR_UNC_FCP, "FCP"), both uncorrectable, often followed by link reset or DPC.
Spec basis
PCIe Base Specification, Flow Control: credit types, InitFC/UpdateFC, credit-limit arithmetic, infinite credits (endpoints must advertise infinite completion credits), Receiver Overflow and Flow Control Protocol Error. A vendor controller guide (Efinix) states the maximum outstanding unused credits without scaling as 2,047 data and 127 header credits and reports violations as FCPE.
Typical causes
Credit-counter bugs (wrap-around of 8-bit header or 12-bit data counters), mis-handled scaled flow control (Gen6), changes in credit accounting after Recovery.
How to detect / prove
Credit arithmetic is modular. Compare (credit limit − credits consumed) mod 2field size against the needed amount, as the spec describes. An analyzer with credit tracking can do this, or a script over an export with DLLPs and TLP lengths. Any trace starting after InitFC can only check changes, not absolute limits.
Linux v7.2 source
drivers/pci/pcie/aer.c ("RxOF", "FCP"). See L-13, L-17.
Test to provoke it
EXPERT: an exerciser that sends TLPs beyond advertised credits, or advertises out-of-range credits, and checks the DUT's error reporting.
X-22Missing or stuck UpdateFC: credit starvation stalls one traffic class Timer onlyPCIe Data Link
In a PEX trace
Visible One TLP type stops flowing in one direction (for example the SSD's posted writes of read data) while others continue. In the opposite direction, UpdateFC for that type has stopped, or keeps repeating the same credit value. Rebuilding credits (X-21) shows the transmitter is at its limit and correctly waiting.
What happens
The receiver returns credits only through UpdateFC. If it stops (because its buffers are full, or because of a bug), the transmitter must wait. Non-posted requests (reads) can then pile up behind it, and the whole device stalls. The spec defines an optional flow-control watchdog that retrains the link when no UpdateFC arrives for a while. One patent summary gives 200 µs for PCIe 2.0 uncertain, and notes that the watchdog cannot catch UpdateFCs that arrive with an unchanged value.
How it shows up
NVMe commands stall and time out with no AER error, unless the optional watchdog is implemented (then it shows as a correctable or uncorrectable error and a retrain, depending on the implementation). Linux shows I/O timeouts and an NVMe controller reset.
Spec basis
PCIe Base Specification, Flow Control update rules and recommended UpdateFC frequency; optional Flow Control Update timer.
Typical causes
Host-side buffers full (the root complex cannot drain posted writes to memory, for example because of a memory-subsystem or IOMMU stall); deadlocks from ordering rules; SSD firmware bugs that never release completion buffers.
How to detect / prove
Plot UpdateFC values per type over time, with TLP counts of that type. A flat UpdateFC with no TLPs of that type, and other types still flowing, identifies the starving type and which side holds the credits. Note the time of the last UpdateFC and compare it with the NVMe command timeout on the host.
Linux v7.2 source
drivers/nvme/host/pci.c: nvme_timeout (the visible consequence). See T-38.
Test to provoke it
EXPERT: an exerciser that withholds UpdateFC for one credit type and observes whether the DUT stalls, recovers or reports an error.

Quiz

  1. A TLP is transmitted twice with the same sequence number and there is no Nak between the two copies. What happened, and which side reports an AER error?

    Answer

    The transmitter's replay timer expired before an Ack arrived, so it replayed (X-20 if the Ack was simply late, X-16 if the Ack was corrupted). The transmitter logs Replay Timer Timeout. The receiver discards the second copy as a duplicate and logs nothing.

  2. Why can't you check absolute credit limits in a trace that starts after link training?

    Answer

    The initial limits are set by InitFC1/InitFC2 during Data Link Layer initialization. UpdateFC carries cumulative values modulo the field size, so without the starting point you can only check relative movement, not whether a TLP exceeded the limit.
