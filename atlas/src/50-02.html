21 Correctable AER Errors: The Link Is Telling You Something

21.1 Why correctable errors matter

A correctable error costs no data. The Data Link Layer replays the TLP and the command completes normally, so the NVMe driver never knows anything happened. But each replay costs link time, and a rate of correctable errors shows how much margin the link has. A Gen5 x4 SSD that logs a few Receiver Errors per day is healthy. One that logs a few hundred per second has lost real bandwidth and latency. It is also one temperature swing away from Replay Rollover, link Recovery and, eventually, a Surprise Down. This chapter covers the eight correctable bits and how to turn their counts into a verdict.

🧒 Kid analogy

You are passing notes in class. If a note gets smudged, your friend says "say again?" and you resend it. Nothing is lost, but if you have to resend every other note, the lesson is nearly over before your message gets through. Correctable errors are the "say again?" requests.

21.2 The replay mechanism in brief

Every TLP gets a 12-bit sequence number and a 32-bit Link CRC (LCRC) from the Data Link Layer. The receiver checks both. If they are good it returns an Ack DLLP. If they are bad it returns a Nak, discards the TLP and sets Bad TLP. The transmitter keeps every unacknowledged TLP in a replay buffer. On a Nak, or when its replay timer expires with no Ack/Nak (Replay Timer Timeout), it resends everything from the oldest unacknowledged TLP onward. A 2-bit REPLAY_NUM counter counts replays of the same TLP. When it rolls over (REPLAY_NUM Rollover) the transmitter sends the link into LTSSM Recovery to retrain. Physical-layer framing and symbol errors are counted as Receiver Error. In Gen6 Flit mode, Forward Error Correction (FEC) corrects most symbol errors before any of this happens, and the detailed rules differ version.

21.3 How to judge a correctable-error rate

The PCIe spec defines a target bit error rate (BER) for the electrical link, but it does not say "N correctable errors per hour is a failure". Your platform qualification has to set that threshold impl. A practical method:

  1. Snapshot aer_dev_correctable on the SSD and on its upstream port. Run a fixed workload, for example 10 minutes of 128 KiB sequential read at QD32 with fio. Snapshot again.
  2. Compute errors per second. Compare across identical slots or systems. A slot that is far worse than its siblings points to the platform (riser, cable, retimer). A drive that is bad in every slot points to the drive.
  3. Correlate with temperature (nvme smart-log) and with link state (lspci -vvv LnkSta). A rising rate together with a speed drop (Chapter 23) means the link is retraining down.
L-01Receiver Error (RxErr) — physical-layer symbol or framing errors ReportedPCIe Physical
What happens
The receiver sees a bad symbol, disparity or block-encoding error, a framing error, or a lane-to-lane deskew problem. The TLP or DLLP that contained it is dropped and normally replayed.
How it shows up
Correctable Status bit 0 (PCI_ERR_COR_RCVR), ERR_COR to the Root Port. Linux v7.2 prints PCIe Bus Error: severity=Correctable, type=Physical Layer, (Receiver ID) and [ 0] RxErr at KERN_WARNING, rate-limited. The RxErr counter in aer_dev_correctable increments. The NVMe layer reports nothing.
Spec basis
PCIe Base Specification, AER Correctable Error Status register, Receiver Error Status. Physical Layer receiver error rules.
Typical causes
Marginal channel: long traces, riser or cable adapters, U.2/U.3 backplanes, missing or misconfigured retimers, poor TX/RX equalization presets at Gen4/Gen5, reference-clock problems (SSC mismatch with separate clocks), contamination or wear on M.2 connectors, thermal drift.
How to detect / prove
Read counters at both ends (cat /sys/bus/pci/devices/<BDF>/aer_dev_correctable). lspci -vvv shows CESta: RxErr+ and DevSta: CorrErr+. For per-lane detail, use the Lane Error Status register of the Secondary PCIe Extended Capability (setpci read-only) or the platform's lane-margining tool (Gen4+ Lane Margining at the Receiver).
In a trace
An analyzer flags disparity, invalid symbols or invalid sync headers on a specific lane, followed by a Nak or a replay. Interposers can add their own errors, so confirm with the device's own counters.
Linux v7.2 source
drivers/pci/pcie/aer.c: aer_irq, aer_isr_one_error, aer_print_error, pci_dev_aer_stats_incr, pci_aer_handle_error (clears status and calls cor_error_detected if the driver has one; the NVMe driver does not).
Test to provoke it
SAFE: run the workload with the SSD in different slots, with and without an extender. CAUTION: use lane margining (time/voltage offset) to step toward the eye edge on Gen4+ platforms. EXPERT: insert a lossy channel or an attenuating fixture.
L-02Bad TLP — LCRC or sequence error, TLP replayed ReportedPCIe Data Link
What happens
A TLP arrives with a bad LCRC or an unexpected sequence number. The receiver Naks it and the transmitter replays it. The NVMe command is delayed by roughly one replay round trip.
How it shows up
Correctable bit 6 (PCI_ERR_COR_BAD_TLP), [ 6] BadTLP, reported by Linux as Data Link Layer / Receiver ID. Counter BadTLP.
Spec basis
PCIe Base Specification, Data Link Layer: LCRC, Sequence Number, Ack/Nak protocol; AER Bad TLP Status.
Typical causes
Same channel problems as L-01 when the error is not caught as a symbol error. Occasionally a controller bug that generates a wrong LCRC on certain payload sizes.
How to detect / prove
Counters at both ends. If BadTLP rises only during large DMA (writes to the SSD stress the RC→EP direction; reads stress EP→RC), the problem is direction-dependent: look at the transmitter on the far side.
In a trace
A Nak DLLP whose AckNak_Seq_Num is earlier than the TLP just sent, followed by a run of replayed TLPs with repeated sequence numbers. Analyzers mark these as "replayed".
Linux v7.2 source
aer.c: AER_DATA_LINK_LAYER_ERROR_MASK, aer_correctable_error_string ("BadTLP").
Test to provoke it
As L-01. An error-injecting interposer or jammer can corrupt the LCRC of chosen TLPs (EXPERT, needs lab equipment).
L-03Bad DLLP — corrupted Ack/Nak/flow-control DLLP ReportedPCIe Data Link
What happens
A DLLP (Ack, Nak, UpdateFC, PM) fails its 16-bit CRC and is discarded. A lost Ack is harmless because later Acks are cumulative, unless the next one is also late, in which case L-05 follows. A lost UpdateFC can briefly starve the transmitter of credits.
How it shows up
Correctable bit 7 (PCI_ERR_COR_BAD_DLLP), [ 7] BadDLLP, Data Link Layer.
Spec basis
PCIe Base Specification, DLLP CRC; AER Bad DLLP Status.
Typical causes
Channel quality, as L-01 and L-02. DLLPs are short, so a high BadDLLP count with little BadTLP points to burst errors.
How to detect / prove
Counters. Look for throughput dips that coincide with bursts of BadDLLP, which show credit starvation.
In a trace
A DLLP marked CRC-error by the analyzer, possibly followed by a replay timeout (L-05) on the far side.
Linux v7.2 source
aer.c: string "BadDLLP", data-link classification.
Test to provoke it
As L-01 and L-02.
L-04REPLAY_NUM Rollover — four replays failed, link forced into Recovery ReportedPCIe Data Link
What happens
The same TLP has been replayed until the 2-bit REPLAY_NUM counter rolls over. The transmitter starts LTSSM Recovery to retrain the link. No new TLPs move for the length of the retrain, typically microseconds but sometimes much longer. If retraining picks a lower speed, the link stays degraded (see L-25).
How it shows up
Correctable bit 8 (PCI_ERR_COR_REP_ROLL), [ 8] Rollover, Data Link / Transmitter ID. Because the agent is the transmitter, the device that logs it is the one whose packets were not getting through. If the port supports bandwidth notification, Link Status LBMS may also be set (Linux bwctrl tracks this).
Spec basis
PCIe Base Specification: REPLAY_NUM, Recovery entry; AER REPLAY_NUM Rollover Status.
Typical causes
Severe signal integrity problems, a receiver CDR losing lock, or a lane that stopped working.
How to detect / prove
Counter Rollover. Check LnkSta speed and width before and after. On the analyzer, look for TS1/TS2 ordered sets mid-traffic (Recovery). Repeated Rollovers are the "recovery storm" pattern of L-26.
In a trace
The same sequence number replayed several times, then electrical idle or TS1 ordered sets, then traffic resuming. NVMe commands in flight show a latency gap the same length as the Recovery.
Linux v7.2 source
aer.c: AER_AGENT_TRANSMITTER_MASK (Rollover, Timeout), string "Rollover". drivers/pci/pcie/bwctrl.c: pcie_bwnotif_irq records LBMS.
Test to provoke it
EXPERT: an interposer that Naks or corrupts every copy of one TLP; or margin the link until rollovers appear.
L-05Replay Timer Timeout — no Ack/Nak in time ReportedPCIe Data Link
What happens
The transmitter's replay timer expires before any Ack or Nak arrives for outstanding TLPs, so it replays them all. This is "timer only" at link level, but AER does report it.
How it shows up
Correctable bit 12 (PCI_ERR_COR_REP_TIMER), [12] Timeout, Data Link / Transmitter ID. Do not confuse it with Completion Timeout (uncorrectable bit 14, L-14).
Spec basis
PCIe Base Specification: REPLAY_TIMER, its limit formula (depends on link width, max payload, and L0s exit latency); AER Replay Timer Timeout Status.
Typical causes
Lost or corrupted Acks (L-03). Receiver Ack-coalescing that is too slow. Long ASPM L0s/L1 exit latency on the receiver side so Acks leave late. A link partner stalled internally.
How to detect / prove
Counter Timeout. If it correlates with ASPM being enabled (it disappears with pcie_aspm=off as a diagnostic boot), suspect power-management exit latency (see L-37).
In a trace
A gap with no Ack after TLPs, then a replay of the same sequence numbers without any preceding Nak.
Linux v7.2 source
aer.c: string "Timeout", transmitter agent mask.
Test to provoke it
CAUTION: enable aggressive ASPM (/sys/module/pcie_aspm/parameters/policy set to powersupersave) with bursty, low-QD I/O. Compare counts with ASPM off.
L-06Advisory Non-Fatal Error — an uncorrectable error handled as correctable ReportedPCIe Transaction
What happens
The PCIe spec allows certain uncorrectable non-fatal errors to be signalled as "advisory" when the detecting agent is not the one that has to act. A typical case is a completer that returns UR to a request and also logs the error: it signals ERR_COR instead of ERR_NONFATAL, because the requester will handle the failed completion. The uncorrectable status bit (for example UR) is still set as well.
How it shows up
Correctable bit 13 (PCI_ERR_COR_ADV_NFAT), [13] NonFatalErr, plus the underlying uncorrectable bit in the same device's uncorrectable status, which Linux does not print on this path. Masked by default per spec, so many systems never show it.
Spec basis
PCIe Base Specification: Advisory Non-Fatal Error cases; AER Advisory Non-Fatal Error Status and Mask.
Typical causes
Config reads of absent functions during enumeration (UR, advisory). An endpoint receiving a request it does not support, for example an MMIO read to an unimplemented register.
How to detect / prove
lspci -vvv: look for CESta: AdvNonFatalErr+ together with UESta: UnsupReq+ on the same device. Read both registers with setpci (read-only).
In a trace
A request answered with a completion that has status UR or CA, then an ERR_COR message from the completer.
Linux v7.2 source
aer.c: string "NonFatalErr". Handled like every correctable error: cleared, no recovery.
Test to provoke it
SAFE (if unmasked): lspci scans of absent functions. CAUTION: unmasking the bit with setpci changes platform configuration.
L-07Corrected Internal Error — controller fixed its own internal fault ReportedPCIe Transaction
What happens
The function detected and corrected an internal error, for example single-bit ECC in a buffer RAM of the PCIe or NVMe front end. What counts as an internal error is up to the device.
How it shows up
Correctable bit 14 (PCI_ERR_COR_INTERNAL), [14] CorrIntErr. Masked by default. Linux v7.2 unmasks internal errors only for CXL devices (pci_aer_unmask_internal_errors(), exported only to cxl_core; its comment says internal errors are "too device-specific to enable generally").
Spec basis
PCIe Base Specification: Corrected Internal Error Status/Mask (optional).
Typical causes
SRAM soft errors, aging, temperature. A rising rate can come before an uncorrectable internal error (L-22) or an NVMe-level Persistent Internal Error event.
How to detect / prove
Unmask it in a lab with setpci (CAUTION), then watch the counter. Correlate with the NVMe SMART "Media and Data Integrity Errors" field and with vendor telemetry.
In a trace
Only an ERR_COR message; nothing else is visible.
Linux v7.2 source
aer.c: pci_aer_unmask_internal_errors, is_aer_internal_error (CXL RAS only).
Test to provoke it
Vendor-specific error injection only.
L-08Header Log Overflow — more errors than the log can hold ReportedPCIe Transaction
What happens
With multiple-header recording enabled, the device's header log is full, so the next error's TLP header is lost. Diagnosis loses information exactly when errors are arriving fastest.
How it shows up
Correctable bit 15 (PCI_ERR_COR_LOG_OVER), [15] HeaderOF. Masked by default.
Spec basis
PCIe Base Specification: Multiple Header Recording, Header Log Overflow Status.
Typical causes
A burst of UR or CA from a misbehaving DMA engine. Software that does not clear status fast enough.
How to detect / prove
Treat it as a sign that the logged header is not necessarily representative. Look at the first error, not the last.
In a trace
Many erroneous transactions in a short window.
Linux v7.2 source
aer.c: string "HeaderOF".
Test to provoke it
EXPERT: error injection while multiple-header recording is enabled.
🐞 Debugging connection

None of the eight correctable bits ever produce an NVMe error, but all of them show up in NVMe latency. If p99.99 latency has spikes at the microsecond-to-millisecond scale with no NVMe errors, compare the spike timestamps with AER counter deltas sampled every second. A link Recovery after a Rollover stalls every queue at once, which is the giveaway: all queues spike together, not just one.

🧪 Lab 21.1 — Measure a correctable-error rate on both ends of the link SAFE

Objective: get an errors-per-second figure for the SSD link and decide which end is receiving the errors.

Setup: Linux with AER native control (check for AER: enabled with IRQ or that the aer_dev_* files exist), fio, an NVMe SSD at <BDF> and its upstream port <UP> (find it with lspci -tv or readlink /sys/bus/pci/devices/<BDF>/..).

for d in <BDF> <UP>; do echo "== $d"; cat /sys/bus/pci/devices/$d/aer_dev_correctable; done > before.txt
fio --name=r --filename=/dev/nvme0n1 --rw=read --bs=128k --iodepth=32 --direct=1 \
    --runtime=600 --time_based --readonly
for d in <BDF> <UP>; do echo "== $d"; cat /sys/bus/pci/devices/$d/aer_dev_correctable; done > after.txt
diff before.txt after.txt

Observations: which counters moved, and on which device. Repeat with a write workload. (Note: a write workload changes data; use a scratch namespace.)

Solution

Reads move data EP→RC, so a bad SSD transmitter shows up on <UP>. Writes move data RC→EP, so a bad host transmitter shows up on the SSD. Acks and flow-control DLLPs travel the other way, so BadDLLP is seen on the opposite side from BadTLP in each case.

Extension: repeat at 40 °C and 70 °C drive temperature and plot the rate against temperature.
