PART V

PCIe Link and Transaction Errors

Every NVMe command travels as PCIe Transaction Layer Packets (TLPs), and every one of them can be damaged, refused, dropped or delayed on the way. PCIe has its own error system, Advanced Error Reporting (AER). AER is separate from NVMe status codes, and the NVMe driver often never hears about it. This part covers every AER status bit that Linux v7.2 defines, then the many link and fabric failures that set no AER bit at all: a link that trained narrow or slow, a recovery storm, a surprise link-down, Downstream Port Containment (DPC), lost interrupts, Input/Output Memory Management Unit (IOMMU) faults and bad Base Address Register (BAR) assignment. Card ids use the prefix L-.

20 How AER Works, and What Linux v7.2 Does With It

20.1 Why this chapter exists

When an NVMe drive "disappears", the first evidence is usually a few lines from AER: or pcieport in the kernel log, not an NVMe status code. To read those lines you need four things: what each register holds, which layer of PCIe detected the problem, how severity is decided, and what Linux does next. Linux can do nothing, reset the link, or remove the device. This chapter explains all four and ends with a reference table of every AER status bit in include/uapi/linux/pci_regs.h. Chapters 21 and 22 give each bit its own card.

  • Name the AER registers (Uncorrectable Status/Mask/Severity, Correctable Status/Mask, Capabilities and Control, Header Log, Root Error Command/Status, Error Source ID) and their offsets inside the AER extended capability.
  • Explain correctable, non-fatal uncorrectable and fatal uncorrectable, and who decides which one applies.
  • Follow Linux v7.2 from the Root Port interrupt to pcie_do_recovery() to the NVMe driver's nvme_error_detected().
  • Find the per-device AER counters in sysfs and know why they can read zero on the device that caused the problem.

🌍 Analogy

Think of each PCIe device as a building with a fire panel. The status register is the panel of lamps, one per alarm type. The mask register is the set of lamps someone has taped over. The severity register decides whether a lamp calls the fire brigade (fatal) or only the caretaker (non-fatal). The Root Port is the central dispatch. It receives a short message ("building 03:00.0 has an alarm") and must then phone the building to find out which lamp is lit.

🧩 Where the analogy breaks

The message that reaches the Root Port (ERR_COR, ERR_NONFATAL, ERR_FATAL) carries only a Requester ID and a class, never the specific bit. Linux has to read the device's AER registers over the same link that may just have failed. On a fatal error Linux does not read the endpoint's uncorrectable registers at all. Section 20.5 shows the code.

20.3 Three classes of error, and who decides

  • Correctable. Hardware already fixed it. Examples are a bad Link CRC (LCRC) that a Data Link Layer replay fixed, or a receiver symbol error. The device sends ERR_COR. No data was lost, but each one costs bandwidth and latency. A rising rate is the most important early warning of a marginal link.
  • Uncorrectable, non-fatal. One transaction was lost or refused, but the link itself still works. The device sends ERR_NONFATAL. Examples are an Unsupported Request, a Completion Timeout, or a Poisoned TLP. The link is usable, so recovery may not need a reset.
  • Uncorrectable, fatal. The link or the device's protocol state can no longer be trusted. The device sends ERR_FATAL. Examples are a Data Link Protocol error, Surprise Down, a Malformed TLP or a Receiver Overflow. The link must be reset.

The Severity register decides fatal versus non-fatal for each uncorrectable bit. It has a spec-defined default, but firmware or the OS can change it. Before you reason from the log line, check the actual value with lspci -vvv ("UESvrt:"). The defaults are in the table in section 20.8.

📭 What the spec does not say

The PCIe Base Specification says when an error must be detected and signalled. It does not require the OS to do anything in particular. Whether a non-fatal Completion Timeout ends up as an NVMe I/O error, a controller reset or nothing visible depends entirely on the OS and the device. Everything in this part about "what happens next" describes Linux v7.2 behaviour impl.

20.4 Which layer detects what (as Linux reports it)

Every AER log line contains type=Physical Layer, Data Link Layer or Transaction Layer. Linux v7.2 does not read this from the hardware. It derives it from the status bits with the macro AER_GET_LAYER_ERROR in drivers/pci/pcie/aer.c verified:

/* drivers/pci/pcie/aer.c (v7.2), abbreviated */
#define AER_PHYSICAL_LAYER_ERROR_MASK(t) ((t == AER_CORRECTABLE) ? PCI_ERR_COR_RCVR : 0)
#define AER_DATA_LINK_LAYER_ERROR_MASK(t) ((t == AER_CORRECTABLE) ?  \
        (PCI_ERR_COR_BAD_TLP | PCI_ERR_COR_BAD_DLLP |                  \
         PCI_ERR_COR_REP_ROLL | PCI_ERR_COR_REP_TIMER) : PCI_ERR_UNC_DLP)
/* everything else is reported as "Transaction Layer" */

So Receiver Error is reported as Physical Layer. Bad TLP, Bad DLLP, REPLAY_NUM Rollover, Replay Timer Timeout and Data Link Protocol Error are reported as Data Link Layer. Every other bit is reported as Transaction Layer, including Surprise Down, even though the PCIe spec counts Surprise Down as a Data Link Layer error. When several bits are set, the line names only the first matching layer. The "agent" part of the line is derived the same way: Completer Abort gives Completer ID; Completion Timeout and Unsupported Request give Requester ID; Rollover and Replay Timer give Transmitter ID; everything else gives Receiver ID.

20.5 The Linux v7.2 AER path, step by step

The step-through below follows one error from the wire to the NVMe driver. The function names are the ones in drivers/pci/pcie/aer.c, err.c and drivers/nvme/host/pci.c.

Device / Root Port hardwarePCIe messageLinux PCI coreNVMe driver
  1. Device detects and signals

    The detecting device sets a bit in its AER status register. If the bit is unmasked it records the header of the offending TLP and sends an error message upstream. The detecting device can be the NVMe endpoint or the Root Port itself (for example, a Root Port that receives a bad TLP from the SSD). ERR_COR is used for correctable errors, and ERR_NONFATAL or ERR_FATAL for uncorrectable ones, chosen by the Severity register.

    Where: endpoint or port hardwarePCIe: Yes, device → Root Port · Message TLP
    e.g. endpoint 0000:03:00.0 sets UNCOR_STATUS bit 14 (Completion Timeout), severity 0 → ERR_NONFATAL (synthetic)
  2. Root Port interrupts the CPU

    The Root Port sets Root Error Status and Error Source ID, then raises its AER interrupt. In Linux v7.2 aer_irq() reads Root Error Status and Error Source ID, writes them back to clear them, and queues them in a kfifo. The threaded handler aer_isr() drains the fifo with aer_isr_one_error(), which handles the correctable part first and then the uncorrectable part.

    Where: drivers/pci/pcie/aer.cPCIe: MSI/MSI-X from Root Port
  3. Find the source and read its registers

    find_source_device() walks the hierarchy below the Root Port. aer_get_device_error_info() reads status and mask from each candidate. For correctable errors it reads the correctable registers. For uncorrectable errors it reads the uncorrectable registers only if the device is a Root Port, an RCEC or a Downstream Port, or the error is non-fatal. On a fatal error from an endpoint the link is assumed broken, so the endpoint's registers are not read. It then prints with aer_print_error(). All devices are printed before any is handled, "to not lose records by reset".

    Where: aer_process_err_devices()PCIe: CfgRd0/CfgRd1 to each candidate
  4. Broadcast error_detected()

    pci_aer_handle_error() clears a correctable error and calls the driver's optional cor_error_detected. For non-fatal errors it calls pcie_do_recovery(dev, pci_channel_io_normal, aer_root_reset), and for fatal errors the same with pci_channel_io_frozen. pcie_do_recovery() in err.c calls every driver below the bridge. The NVMe driver's nvme_error_detected() returns CAN_RECOVER for normal, disables the controller and returns NEED_RESET for frozen, and returns DISCONNECT for perm_failure.

    Where: drivers/pci/pcie/err.cPCIe: No (software)
  5. Reset the link if needed

    If the channel was frozen or any driver voted NEED_RESET, aer_root_reset() runs. It does a secondary bus reset of the Root or Downstream Port via pci_bus_error_reset(), or an FLR for an RCiEP, and logs "%s Port link has been reset (%d)". With DPC, dpc_reset_link() is used instead, because the hardware has already taken the link down.

    Where: aer_root_reset() / dpc_reset_link()PCIe: Yes, link goes down and retrains
  6. slot_reset and resume

    nvme_slot_reset() logs "restart after slot reset", restores config space and schedules the NVMe reset work. nvme_error_resume() waits for that work to finish. If everything voted RECOVERED, the PCI core logs "device recovery successful". Otherwise it calls error_detected again with perm_failure and logs "device recovery failed".

    Where: drivers/nvme/host/pci.cPCIe: Yes, config restore and controller re-init

20.6 What the log looks like

The format strings below are copied from aer.c v7.2. The bus type is "PCIe", or "CXL" for CXL devices. Linux adds the prefix AER: through dev_fmt. The example output is synthetic and abbreviated, built only from those format strings.

pcieport 0000:00:1d.0: AER: Uncorrectable (Non-Fatal) error message received from 0000:03:00.0
nvme 0000:03:00.0: AER: PCIe Bus Error: severity=Uncorrectable (Non-Fatal), type=Transaction Layer, (Requester ID)
nvme 0000:03:00.0: AER:   device [144d:a80a] error status/mask=00004000/00400000
nvme 0000:03:00.0: AER:    [14] CmpltTO                (First)
pcieport 0000:00:1d.0: AER: device recovery successful

Details to know when reading these lines:

  • error status/mask are the raw 32-bit values. The bit list that follows is status & ~mask. A set bit with no name in Linux's string table prints as Unknown Error Bit.
  • (First) marks the bit that the First Error Pointer (PCI_ERR_CAP_FEP) names. When several bits are set, this one caused the Header Log capture.
  • A TLP Header: line is printed only for the bits in AER_LOG_TLP_MASKS: Poisoned TLP, Poisoned TLP Egress Blocked, ECRC, UR, CA, Unexpected Completion, ACS Violation, MC Blocked, AtomicOp Egress Blocked, DMWr Blocked, TLP Translation Egress Blocked, TLP Prefix Blocked, Malformed TLP, IDE Check, Misrouted IDE and PCRC. It is also printed for Completion Timeout, but only if the device sets the "Completion Timeout Prefix/Header Log Capable" bit (PCI_ERR_CAP_COMP_TIME_LOG). See tlp_header_logged().
  • If the source cannot be found, the Root Port line ends with (no details found. If the status read returns zero, the line reads type=Inaccessible, (Unregistered Agent ID). Both mean "something sent an error message and Linux could not get the details". This is common when the device has already dropped off the bus.
  • Correctable errors are logged at KERN_WARNING and uncorrectable errors at KERN_ERR, so dmesg -l err hides every correctable error.

20.7 Rate limits, counters and the "it was the other end" trap

Linux v7.2 rate-limits AER printing per device. Correctable and non-fatal errors each get a ratelimit state initialised in pci_aer_init() with DEFAULT_RATELIMIT_INTERVAL and DEFAULT_RATELIMIT_BURST. Documentation/PCI/pcieaer-howto.rst gives these as 10 events per 5 seconds. Fatal errors are never rate-limited. The limits can be tuned in sysfs under /sys/bus/pci/devices/<BDF>/aer/: correctable_ratelimit_interval_ms, correctable_ratelimit_burst, nonfatal_ratelimit_interval_ms and nonfatal_ratelimit_burst. Counting is not rate-limited. pci_dev_aer_stats_incr() runs before the ratelimit check, so the counters are the reliable source.

# per-device counters (every AER-capable device)
cat /sys/bus/pci/devices/0000:03:00.0/aer_dev_correctable
cat /sys/bus/pci/devices/0000:03:00.0/aer_dev_nonfatal
cat /sys/bus/pci/devices/0000:03:00.0/aer_dev_fatal
# Root Port totals (messages received, including its own)
cat /sys/bus/pci/devices/0000:00:1d.0/aer_rootport_total_err_cor
cat /sys/bus/pci/devices/0000:00:1d.0/aer_rootport_total_err_nonfatal
cat /sys/bus/pci/devices/0000:00:1d.0/aer_rootport_total_err_fatal

Each aer_dev_* file prints one line per named bit (RxErr 0, BadTLP 3, ...) followed by TOTAL_ERR_COR, TOTAL_ERR_FATAL or TOTAL_ERR_NONFATAL. The correctable array has 16 entries (AER_MAX_TYPEOF_COR_ERRS).

⚠️ The "it was the other end" trap

The comment above struct aer_info in aer.c warns that counters show errors "as seen by this device". If the SSD's transmitter is bad, the Root Port's receiver sees the errors, so the Root Port's counters go up and the SSD's stay at 0. Always read both ends of the link: the SSD and its upstream port, which may be a switch Downstream Port rather than the Root Port.

🏭 Implementation-dependent: firmware-first

Linux handles AER only if firmware gives it control through ACPI _OSC (pcie_aer_is_native()). On many servers firmware keeps control ("firmware-first"). Errors then arrive as APEI/GHES records, go through aer_recover_queue() and are printed by pci_print_aer() in a different format (aer_status:, aer_mask:, aer_layer=, aer_agent=). Firmware may also hide, mask or count errors that Linux never sees. If dmesg shows no AER lines at all, first check that this is not the reason.

20.9 What a PEX trace shows of AER

A protocol analyzer capture (for example a Teledyne LeCroy .pex file) records the TLPs and DLLPs on one probed link. AER is mostly register state inside the devices, so an AER error can show up in a trace in only three ways:

  1. The error condition itself is a packet. A Nak DLLP and its replay (Bad TLP), a Cpl with status UR, CA or RRS, a TLP with the EP (poisoned) bit set, an oversize or 4 KB-crossing TLP (Malformed), or bad flow-control DLLPs. The analyzer decodes these directly.
  2. The error is an absence. A non-posted request with no completion within N microseconds or milliseconds (Completion Timeout), or no Ack within the replay window. You find these with timestamps and the analyzer's outstanding-request view.
  3. The device reports it. ERR_COR, ERR_NONFATAL and ERR_FATAL are Message TLPs (routed to the Root Complex) and are visible when they cross the probed link. They carry only the class and the sender's Requester ID, not the bit. The bit is visible only if software reads the AER capability over that link: Linux's aer_get_device_error_info() issues CfgRd to offsets 04h–1Ch of the AER capability after each event, and the completion data holds the status, mask and header log.

🔍 Trace tip

Set the analyzer trigger on "Message TLP, code ERR_COR / ERR_NONFATAL / ERR_FATAL" with a large pre-trigger buffer. The packets just before the message usually contain the cause (the Nak, the UR completion, the poisoned CplD). The CfgRd completions just after it, issued by Linux's AER handler, contain the status bits, so a single capture gives you both the cause and the AER verdict.

💡 Senior insight

The NVMe controller and the PCIe AER block are different pieces of logic, often from different IP vendors. AER errors usually do not appear in the NVMe Error Information log page (Log ID 01h), and NVMe status codes do not appear in AER. To diagnose a failure, line up three timelines: the AER lines in dmesg, the NVMe driver lines (nvme nvme0: ...), and the device's own logs (nvme error-log, telemetry). A Completion Timeout in AER that comes 50 ms before an NVMe "I/O timeout, aborting" is almost always the cause, not a coincidence.

Quiz

  1. The SSD logs nothing, but the Root Port's aer_dev_correctable shows thousands of BadTLP. Which side's transmitter is suspect?

    Answer

    The SSD's. The Root Port received bad TLPs, so the SSD's transmit path is the one to examine: its TX lanes, the connector, a retimer, or the Root Port's receiver equalization. Counters show what each device received.

  2. Why does Linux not read an endpoint's uncorrectable status after an ERR_FATAL?

    Answer

    aer_get_device_error_info() reads uncorrectable registers only for Root Ports, RCECs, Downstream Ports, or non-fatal errors. After a fatal error the link to the endpoint is assumed unreliable, so a config read could hang or return all-ones.

  3. You see [14] CmpltTO with no TLP Header line. Is the Header Log empty?

    Answer

    Not necessarily. Linux prints the header for Completion Timeout only if the device sets PCI_ERR_CAP_COMP_TIME_LOG. Otherwise it assumes no header was logged.
