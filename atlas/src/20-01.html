PART II

Errors That Come With a Code

This part covers the easy failures: the drive admits something went wrong. It gives a status code in the Completion Queue Entry (CQE), raises an Asynchronous Event, sets a bit in a log page, or sets the fatal bit in a controller register. Each failure gets an error card that says what the device means by it, why it usually happens (using the places where the QEMU NVMe model returns it), and what Linux v7.2 does with it. Most of the hard bugs are near these codes: a driver that ignores the More bit, a firmware that sets DNR when it should not, a retry loop that hides a dying drive. Reading the code correctly is step one. Chapter II.1 covers the status field and the Linux code path. Chapters 4–6 hold the per-code cards, Chapter II.5 is the complete code table, and Chapter II.6 covers failures reported through logs, events and registers instead of a CQE.

II.1 The Status Field: Anatomy and the Linux Path

📌 Four ways to show a failure (recap)

Part I describes them in detail. In short, an NVMe failure reaches the host in one of four ways: (1) a non-zero status in a completion (this part), (2) no completion at all, so only a host timer notices (Part on timing), (3) a successful completion with the wrong effect (silent data problems), or (4) correct results delivered slowly or over a degraded link. Category 1 also includes failures reported out of band: Asynchronous Event Request (AER) completions, log pages and the CSTS register. Chapter II.6 covers those.

II.1.1 Why this chapter exists

A failed command returns 15 bits of status, and engineers misread them all the time. Common mistakes: decoding SC without SCT (0x02 is "Invalid Field" under SCT 0 but "Invalid Queue Size" under SCT 1), treating DNR as a severity, ignoring the More bit and never reading the Error Information log, or forgetting that the host driver invents some status codes itself (0x370, 0x371) that never appeared on the PCIe link. The cards in the following chapters assume you can decode the field without hesitating and know which branch of the Linux completion path a code takes.

  • Decode a CQE status word into Phase, SC, SCT, CRD, More and DNR, both in raw CQE layout and in the Linux shifted layout.
  • Predict whether Linux v7.2 retries, fails over, re-authenticates or completes a failed request, and which errno user space sees.
  • Find the exact dmesg line, sysfs counter and tracepoint that record each failed command.
  • Use the kernel's NVMe fault injection to test the host's handling of any status code without a misbehaving drive.

II.1.2 Where the status lives

A CQE is 16 bytes verified. Dword 0 (and in newer specs Dword 1) holds the command-specific result, DW2 holds SQ Head Pointer (SQHD) and SQ Identifier (SQID), and DW3 holds the Command Identifier (CID, bits 15:0), the Phase Tag (bit 16) and the 15-bit Status Field (bits 31:17). Linux's struct nvme_completion in include/linux/nvme.h declares DW3 as __u16 command_id; __le16 status;. So the 16-bit status includes the phase tag in bit 0, and the driver shifts it off.

The shift happens in drivers/nvme/host/nvme.h:nvme_try_complete_req(): rq->status = le16_to_cpu(status) >> 1;. From that point on, every Linux constant (NVME_SC_*, NVME_SCT_*) is written in the shifted layout. The Generic codes are 0x000–0x0FF, Command Specific 0x100–0x1FF, Media 0x200–0x2FF and Path 0x300–0x3FF. This is why include/linux/nvme.h lists NVME_SC_WRITE_FAULT = 0x280: SCT 2, SC 0x80. libnvme's types.h instead lists the SC alone (NVME_SC_WRITE_FAULT = 0x80) and the SCT separately (NVME_SCT_MEDIA = 0x2, shift 8). Always check which convention a tool prints. nvme-cli and the Linux log line print SCT and SC as separate numbers. The QEMU trace and Linux's internal constants use the combined form.

⚠️ DNR is a prediction, not a severity

DNR=0 does not mean "minor", and DNR=1 does not mean "fatal". An Unrecovered Read Error with DNR=0 tells the host "try again, a re-read might succeed". The data is still at risk. An Invalid Field with DNR=1 tells the host "your command is wrong". Nothing is broken on the drive. Firmware that clears DNR on deterministic errors makes Linux resend the same bad command up to max_retries (default 5) times. Firmware that sets DNR on transient errors makes Linux fail I/O that would have succeeded on retry. Both are real conformance bugs. Check DNR on every error a drive under test returns.

II.1.4 What Linux v7.2 does with a non-zero status

All transports (PCIe, RDMA, TCP, FC, loop) reach the same core path. The diagram below follows a completion from the CQE to the errno.

II.1.4.1 nvme_decide_disposition() — the one function that decides

/* drivers/nvme/host/core.c (v7.2), abridged */
static inline enum nvme_disposition nvme_decide_disposition(struct request *req)
{
	if (likely(nvme_req(req)->status == 0))
		return COMPLETE;
	if (blk_noretry_request(req) ||
	    (nvme_req(req)->status & NVME_STATUS_DNR) ||
	    nvme_req(req)->retries >= nvme_max_retries)
		return COMPLETE;
	if ((nvme_req(req)->status & NVME_SCT_SC_MASK) == NVME_SC_AUTH_REQUIRED)
		return AUTHENTICATE;
	if (req->cmd_flags & REQ_NVME_MPATH) {
		if (nvme_is_path_error(nvme_req(req)->status) ||
		    blk_queue_dying(req->q))
			return FAILOVER;
	} else {
		if (blk_queue_dying(req->q))
			return COMPLETE;
	}
	return RETRY;
}

Consequences worth remembering verified:

  • Linux does not look at the code when deciding to retry. Any non-zero status without DNR is retried up to nvme_core.max_retries (module parameter, default 5), unless the request is marked no-retry (blk_noretry_request(), i.e. a REQ_FAILFAST_* flag). So for retries, the device's DNR choice is the policy.
  • Path errors (SCT 3) fail over to another path only on a multipath namespace head (REQ_NVME_MPATH). On a single-path device they are plain retries.
  • Older kernels had a helper named nvme_req_needs_retry(). It does not exist in v7.2. Its logic is now inside nvme_decide_disposition().
  • Admin and passthrough requests use the same function, but most are submitted with flags that make them no-retry. If you see an admin error, assume it was not retried.
  • nvme_retry_req() increments nvme_req(req)->retries and the per-namespace ns->retries (sysfs command_retries_count), then calls blk_mq_delay_kick_requeue_list() with the CRD-derived delay.

The text "Unrecovered Read Error" comes from nvme_get_error_status_str() in drivers/nvme/host/constants.c, which indexes nvme_statuses[] with status & NVME_SCT_SC_MASK and returns "Unknown" for gaps. The second line comes from the block layer (block/blk-mq.c:blk_print_req_error()). Note that it reports a 512-byte sector, not an LBA. Two quirks of the string table derived:

  • 0x104 (NVME_SC_ABORT_MISSING) is printed as "Reserved" (the source carries an /* XXX */ comment).
  • Fabrics Connect codes share the numbers 0x180–0x184 with NVM command-set codes. The table only has the NVM names, so a Fabrics status decoded by this function shows the NVM text (0x182 → "Attempted Write to Read Only Range"). Connect failures are logged separately by drivers/nvme/host/fabrics.c:nvmf_log_connect_error(), which uses its own wording.

The log line appears only when the request finally completes with an error. A command that failed twice and then succeeded on the third retry prints nothing. Only command_retries_count and the tracepoint record it. This is a common way intermittent drive errors stay invisible.

II.1.4.5 Passthrough and ioctl users see the raw status

For NVME_IOCTL_ADMIN_CMD / NVME_IOCTL_IO_CMD (what nvme-cli uses), the ioctl return value is the positive NVMe status (shifted layout) when the device fails the command, and a negative errno for host-side failures (drivers/nvme/host/ioctl.c). For io_uring passthrough, nvme_uring_cmd_end_io() places nvme_req(req)->status in the CQE result and only falls back to blk_status_to_errno() when the status is zero but the block layer reported an error. This is why nvme-cli can print "NVMe status: Invalid Field in Command(0x2)" while a filesystem would only see EOPNOTSUPP.

II.1.5 Host-generated statuses — codes that were never on the wire

Two path-related codes are mostly synthesised by the host driver. In a protocol-analyzer capture there is no CQE carrying them.

  • NVME_SC_HOST_PATH_ERROR (0x370): set by nvme_host_path_error() when a transport cannot even submit (e.g. the controller is not live). Mapped to BLK_STS_TRANSPORT / -ENOLINK.
  • NVME_SC_HOST_ABORTED_CMD (0x371): set by nvme_cancel_request() for every in-flight request when the driver tears down queues (reset, removal, timeout recovery). Not DNR, so it is retried or failed over. If the retry budget runs out or the queue is dying, the application sees -EIO.

Likewise NVMe fault injection (drivers/nvme/host/fault_inject.c, built with CONFIG_FAULT_INJECTION_DEBUG_FS) overwrites nvme_req(req)->status inside nvme_try_complete_req(). The drive really returned success, and the trace shows a good CQE.

🧪 Lab 3.1 — Make Linux see any status code you choose CAUTION

Objective: exercise the host's error handling for a specific status (e.g. 0x281 Unrecovered Read Error) without a faulty drive.

⚠️ Safety

Injected write failures make filesystems go read-only or remount, and can corrupt a mounted filesystem's view. Use a scratch namespace or a QEMU guest. The drive's media is never touched.

Setup: kernel with CONFIG_FAULT_INJECTION_DEBUG_FS=y, debugfs mounted. Per-namespace directory: /sys/kernel/debug/nvme0n1/fault_inject/ (the parent is named after the disk or controller device).

cd /sys/kernel/debug/nvme0n1/fault_inject
echo 0x281 > status        # SCT 2 / SC 0x81, shifted Linux layout
echo 1     > dont_retry    # ORs NVME_STATUS_DNR into the injected status
echo 100   > probability
echo 1     > times
dd if=/dev/nvme0n1 of=/dev/null bs=4k count=1 iflag=direct
dmesg | tail -3            # expect the nvme_log_error line + "critical medium error"
echo 0 > dont_retry; echo 3 > times   # now observe retries in command_retries_count

Observations: with dont_retry=1, dd fails at once with "No data available" (ENODATA). With dont_retry=0 and times < 6, the read succeeds after retries, nothing is printed, and command_retries_count goes up.

Solution / explanation

The injected status passes through nvme_decide_disposition() exactly like a real one. DNR → COMPLETE → nvme_error_status() maps 0x281 to BLK_STS_MEDIUM → -ENODATA. Without DNR, the request is requeued and the next attempt succeeds because times is used up. This is the "retry hides the error" pattern from §II.1.4.3.

Extension: inject 0x302 (ANA Inaccessible) on one path of a multipath namespace and watch multipath_failover_count.

II.1.6 How the device side decides — the QEMU reference model

The QEMU NVMe controller (hw/nvme/ctrl.c) is the most readable open model of when a controller returns each status. Its checks are a useful baseline for "typical cause" impl. Real firmware has many more error sources (media, power, thermal), but argument validation usually looks very similar. Status names in QEMU's include/block/nvme.h differ from Linux's (e.g. NVME_DATA_TRAS_ERROR, NVME_INTERNAL_DEV_ERROR, NVME_DULB), and its values use the same combined SCT/SC layout as Linux. A static scan of return sites in QEMU's ctrl.c shows how lopsided real error traffic is: NVME_INVALID_FIELD | NVME_DNR is returned from about 86 places, NVME_INVALID_NSID | NVME_DNR from about 15, and everything else from a handful derived from grep, approximate.

QEMU has a few useful behaviours for testers verified in source:

  • Backend I/O failure is turned into a media status in nvme_rw_complete_cb(): reads → NVME_UNRECOVERED_READ, writes / Write Zeroes / Zone Append → NVME_WRITE_FAULT. A host-side blkdebug rule therefore gives a real SCT 2 error on the emulated wire.
  • Its Error Information log (nvme_error_info()) always returns zeroed entries, so QEMU never sets More meaningfully.
  • Its Abort (nvme_abort()) only cancels outstanding AERs, plus queued backend AIO on a best-effort basis, and otherwise completes with result bit 0 = 1 ("not aborted").
  • SMART critical warnings can be injected at run time through the QOM property smart_critical_warning (nvme_set_smart_warning()), which raises the matching SMART AEN if the host enabled it.

II.1.8 Finding a status code in a PEX trace

Everything in this part that travels in a CQE can be seen in a PCIe protocol-analyzer capture (a Teledyne LeCroy .pex file or similar) of the link between the root port (or switch) and the SSD. The trace never shows a "status" packet, though. It shows memory writes, and you or the analyzer's NVMe decoder must know where the CQs live verified:

  1. Find the queues. The admin CQ base is the value the host writes to ACQ (BAR0 + 30h). That is an MWr from host to device, visible if the capture includes controller initialisation. I/O CQ bases are in PRP1 of each Create I/O Completion Queue SQE (admin opcode 05h). The device fetches that SQE with an MRd from the admin SQ, and the SQE is in the returned CplD. If the capture starts after initialisation, the decoder may not know the queue addresses. Re-trigger with a controller reset, or tell the decoder the addresses by hand.
  2. Find the CQE. A device→host MWr with a 16-byte payload to CQ base + head×16. DW3 holds CID (bits 15:0), Phase (bit 16) and status (bits 31:17). It is followed by an MSI-X MWr (to the address from the MSI-X table, typically FEExxxxxh on x86) and later by the host's CQ head doorbell MWr (BAR0 + 1000h + (2y+1)×(4<<DSTRD)).
  3. Match it to the command. Use SQID and CID from the CQE to find the SQE (the device's MRd of the SQ slot after the tail doorbell). Opcode, NSID, SLBA and NLB are in that CplD payload.
  4. Decode. Status = DW3[31:17]: SC = bits 24:17, SCT = 27:25, CRD = 29:28, More = 30, DNR = 31. A non-zero value is the error. For the full detail, the Error Information log must be read inside the capture window (Get Log Page LID 01h: admin SQE, then the device's MWr of the log data into host memory). Otherwise More=1 points to information the trace does not contain.
📭 What the trace cannot tell you

The trace shows that a status was returned, never why inside the drive (media, FTL, firmware). It does not show host-generated statuses (0x370, 0x371, fault injection), anything Linux did with the status (retry, failover, errno), or AEN causes beyond the AER completion's Dword 0. And it only shows what crosses the probed link: for NVMe-oF the statuses travel in network capsules, not NVMe CQEs on that PCIe link.

II.1.9 Common mistakes

  • Comparing a raw CQE status (phase still in bit 0) with a Linux NVME_SC_* constant: you are off by one bit and everything looks like a different code.
  • Assuming "sct 0x0 / sc 0x2" and "sct 0x1 / sc 0x2" are the same error.
  • Reading only dmesg: retried-then-successful errors never print. Read the tracepoint, the counters and the Error Information log.
  • Assuming a 0x371 in dmesg means the drive aborted a command: it means Linux cancelled it, usually during a reset that a timeout or CSTS.CFS triggered. Look for the root cause earlier in the log.
  • Expecting CRD to work without the host enabling ACRE. Linux v7.2 enables ACRE (nvme_configure_host_options()) only if crdt1 is non-zero in Identify Controller.

Quiz

  1. The raw 16-bit CQE status word is 0x8103. Decode it.

    Answer

    Bit 0 (P) = 1. Shifting right by one gives 0x4081: DNR=1 (0x4000), More=0, CRD=0, SCT=0 (bits 10:8 of 0x081 = 0), SC=0x81 → Generic "Capacity Exceeded". Linux maps it to BLK_STS_NOSPC → -ENOSPC and does not retry.

  2. A drive returns Internal Error (0x006) with DNR=0 on every attempt. How many times does Linux v7.2 send the command, and what does the application see?

    Answer

    With the default max_retries=5: the first attempt plus 5 retries = 6 submissions. Then retries >= nvme_max_retries → COMPLETE, one log line, and BLK_STS_IOERR → -EIO.

  3. Why can't you find status 0x371 in an analyzer trace that covers the failure?

    Answer

    Because the driver created it in nvme_cancel_request() while tearing down queues. No CQE carried it.
