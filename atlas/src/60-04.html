PART VIII

Performance Failures

A drive that returns correct data at a third of the speed it should is failing — just not in a way any status code describes. Performance failures are "Degraded" by nature: every command succeeds, every log is clean, and the only evidence is a number that is lower (or a latency that is higher) than it should be. This part gives the arithmetic for what "should be" means, then one card per anomaly with the tool that exposes it: fio, iostat, perf, nvme-cli SMART data and lspci link status.

8.1 Knowing the Ceiling: Link, Queue and Latency Arithmetic

You cannot call a result "slow" without a ceiling to compare it with. Three ceilings matter: the link (how many bytes per second PCIe can carry after encoding and packet overhead), the device (its datasheet sequential/random figures, measured under the vendor's stated conditions), and the queueing law that links IOPS, latency and queue depth.

8.1.1 Link ceiling

BW_raw = rate (GT/s) × lanes × encoding efficiency ÷ 8     BW_data ≈ BW_raw × MPS ÷ (MPS + overhead)
  • rate — 8 GT/s (Gen3), 16 (Gen4), 32 (Gen5), 64 (Gen6)
  • encoding efficiency — 128/130 for Gen3–Gen5; Gen6 Flit mode uses 1b/1b PAM4 encoding with the FLIT carrying 236 TLP bytes per 256 (vendor overviews) version
  • MPS — Max_Payload_Size of the data TLPs (128, 256, 512 B typical)
  • overhead — per-TLP bytes besides payload: ≈ 4 B framing token (carries length and sequence number in 128b/130b) + 16 B header (4 DW, 64-bit address) + 4 B LCRC = ≈ 24 B; +4 B if ECRC is enabled. DLLP traffic (Ack, UpdateFC) costs a few more percent and is ignored here. derived

8.1.2 Queueing ceiling: Little's Law

IOPS = outstanding I/Os ÷ mean latency     (QD 32, 80 µs → 400 000 IOPS; QD 32, 400 µs → 80 000 IOPS)
  • outstanding I/Os — the average number of commands actually in flight at the device (not the fio iodepth you asked for, if the host cannot keep up)
  • mean latency — device + host completion latency (fio clat + slat)

Little's Law holds for any stable system. Use it as a lie detector: if fio reports QD 32, 80 µs average latency and only 150 000 IOPS, then the device did not have 32 commands in flight — the host is the bottleneck (P-09).

8.1.3 The measurement discipline

  • State the drive's condition: fresh-out-of-box, after secure erase, or preconditioned (written sequentially twice its capacity, then the random workload until steady state). Performance numbers without condition are meaningless.
  • Run long enough: fio's steadystate option (e.g. ss=iops_slope:0.1% with ss_dur and ss_ramp) stops a job only once the metric has stabilised; use time_based with runtime.
  • Record time series, not only averages: --write_bw_log, --write_lat_log, --log_avg_msec=1000.
  • Record percentiles: --percentile_list=50:99:99.9:99.99.
  • Record the environment at the same time: nvme smart-log before/after, lspci -vvv link status, CPU frequency governor, IRQ affinity.
# Baseline evidence bundle (read-only; reads only, no writes to the device)
lspci -vvv -s 0000:01:00.0 | grep -E 'LnkCap|LnkSta|DevCtl|MaxPayload|MaxReadReq|ASPM'
cat /sys/bus/pci/devices/0000:01:00.0/{current_link_speed,current_link_width,max_link_speed,max_link_width,numa_node}
nvme smart-log /dev/nvme0
nvme id-ctrl /dev/nvme0 | grep -E '^(mdts|apsta|wctemp|cctemp|mntmt|mxtmt)'
nvme get-feature /dev/nvme0 -f 0x0c -H     # APST table
nvme get-feature /dev/nvme0 -f 0x08 -H     # interrupt coalescing
cat /sys/module/nvme_core/parameters/default_ps_max_latency_us
fio --name=rr --filename=/dev/nvme0n1 --readonly --rw=randread --bs=4k --iodepth=32 \
    --numjobs=4 --ioengine=io_uring --direct=1 --time_based --runtime=60 --group_reporting \
    --percentile_list=50:99:99.9:99.99
⚠️ Warning

Write workloads (--rw=write, randwrite, preconditioning) destroy the data on the target. Run them only on a scratch device or namespace. --readonly makes fio refuse to write.

8.2 Device-Side Performance Anomalies

P-01Throughput well below link capability DegradedSystem
What happens
Large sequential reads (128 KiB–1 MiB, QD ≥ 8) reach, say, 4.1 GB/s on a Gen4 x4 drive whose link ceiling at MPS 256 B is ≈7.2 GB/s and whose datasheet says 7.0 GB/s.
How it shows up
Only in the benchmark number. No error, no log.
Spec basis
PCI Express Base: link rate/width, MPS; NVMe Base: MDTS (limits per-command size), queue model. The ceiling is arithmetic, not a spec field.
Typical causes
Link trained below capability (P-11); MPS 128 B (P-12); I/O split into small commands by MDTS or max_sectors_kb; too few outstanding commands; CPU or single-thread submission limit (P-09); device thermal throttling (P-06); measuring through a filesystem with buffered I/O.
How to detect / prove
Compute the ceiling (8.1.1) from lspci LnkSta and DevCtl MaxPayload; run fio --rw=read --bs=1m --iodepth=32 --direct=1; check iostat -x 1 rareq-sz (average request size actually sent) and aqu-sz (average queue size). If rareq-sz is much smaller than bs, the block layer is splitting.
In a trace
Analyzer bandwidth view: gaps between bursts of data TLPs (device or host idle), TLP payloads of 128 B, or fewer outstanding SQEs than expected.
Linux v7.2 source
drivers/nvme/host/core.c:nvme_init_identify (MDTS → max_hw_sectors); drivers/pci/pci.c:__pcie_print_link_status reports "available PCIe bandwidth, limited by …".
Test to provoke it
SAFE: read-only fio sweep of bs (4k…1m) × iodepth (1…128); plot bandwidth; the plateau should approach the ceiling.
P-02IOPS collapse at high queue depth DegradedDevice / host
What happens
IOPS rise with queue depth until the device's internal parallelism is saturated; beyond that they should plateau while latency grows linearly (Little's Law). A collapse — IOPS falling as QD rises (e.g. 800k at QD 64, 450k at QD 256) — means something degrades under contention.
How it shows up
QD sweep curve with a peak and a decline; mean latency growing faster than QD/IOPS predicts.
Spec basis
None; queue depth limits come from CAP.MQES and the host driver's queue depth.
Typical causes
Device: firmware arbitration overhead, internal buffer thrashing, read disturb mitigation, too many concurrent streams for the FTL cache. Host: lock contention when many jobs share one hardware queue, nr_requests limits causing requeue storms, interrupts from all queues landing on one CPU.
How to detect / prove
Sweep --iodepth 1…256 at fixed numjobs; then repeat with jobs pinned to CPUs on the device's NUMA node. If host CPU (fio sys%, perf top) is saturated at the peak, it's the host; if the device-reported latency (or analyzer SQE→CQE time) rises disproportionately, it's the device.
In a trace
Analyzer: time from SQE fetch to CQE per command rises super-linearly with outstanding count; or the device stops fetching SQEs although many are available (internal back-pressure).
Linux v7.2 source
drivers/nvme/host/pci.c module parameter io_queue_depth (default 1024, "should >= 2 and < 4096"); q_depth clamped to CAP.MQES+1 in nvme_pci_enable.
Test to provoke it
SAFE (read-only): for qd in 1 2 4 8 16 32 64 128 256; do fio --readonly … --iodepth=$qd; done.
P-03Latency outliers at p99.9 / p99.99 DegradedDevice / host
What happens
Median read latency is 80 µs but one I/O in a thousand takes 5–50 ms. Averages hide it; databases and distributed storage feel it, because a request that touches many I/Os waits for the slowest.
How it shows up
fio clat percentiles; application tail latency; occasionally Linux timeouts if outliers exceed 30 s (then it becomes a timing failure, not a performance one).
Spec basis
NVMe defines no latency targets for ordinary I/O; some features exist to manage it (Predictable Latency Mode, Read Recovery Level, I/O Determinism concepts) — check Identify Controller for support.
Typical causes
Garbage collection (P-05), read retry / soft-decode on worn or long-retention NAND, internal firmware housekeeping (SMART update, table flush), power state exit (P-07), host: interrupt on a busy CPU, softirq delay, CPU frequency ramp-up, SMIs.
How to detect / prove
fio --percentile_list=99:99.9:99.99 --write_lat_log to get each slow I/O's timestamp; bpftrace/biolatency-style histograms; correlate outlier timestamps with SMART temperature samples, APST transitions, and other activity. An analyzer gives the device-only latency (SQE fetch → CQE), separating device from host.
In a trace
One SQE→CQE interval of 12 ms among thousands of 70 µs intervals; if many commands stall together, a device-wide pause (GC, table flush); if only one, a media retry.
Linux v7.2 source
Trace events nvme_setup_cmd and nvme_complete_rq in drivers/nvme/host/trace.h give per-command host-side latency (enable via /sys/kernel/tracing/events/nvme/).
Test to provoke it
SAFE: long (≥ 30 min) read-only random read at moderate QD on a drive that has been written full; compare a fresh drive.
P-04Write cliff after the SLC cache is exhausted DegradedDevice (FTL)
What happens
Many TLC/QLC drives write first into NAND operated in single-bit (pseudo-SLC) mode, which is fast. When that cache fills during a long sequential write, the drive must write to native TLC/QLC — and simultaneously fold the cache — so throughput drops sharply. Reviewers report drops such as from >2.5 GB/s to ≈0.8 GB/s after ≈150 GB on one TLC drive, and to ≈160 MB/s after ≈80 GB on a QLC SATA drive; the cache recovers during idle time.
How it shows up
A bandwidth-over-time plot with a step down; average numbers for short tests look perfect.
Spec basis
Not specified by NVMe; it is FTL design. (Endurance/space reporting fields in SMART do not expose the cache size.)
Typical causes
Dynamic SLC cache sized by free space (shrinks as the drive fills), no idle time to flush, drive nearly full.
How to detect / prove
CAUTION (destructive): sequential write of the full capacity on a scratch drive with --write_bw_log and 1 s averaging; plot GB written vs MB/s. Repeat at 50% and 90% fill to show the cache shrinking.
In a trace
Device MRd rate (write data fetch) drops; SQE→CQE time per write rises; host-side, the queue stays full (device-bound).
Linux v7.2 source
Not visible to the driver.
Test to provoke it
CAUTION: fio --name=fill --filename=/dev/nvme1n1 --rw=write --bs=1m --iodepth=32 --direct=1 --write_bw_log=fill --log_avg_msec=1000 on a scratch device.
P-05Garbage-collection stalls in steady state DegradedDevice (FTL)
What happens
After the drive has been fully written (no free blocks left), every new write needs garbage collection to reclaim space. Random write IOPS fall from the fresh-out-of-box value to a much lower steady-state value, with periodic stalls when GC falls behind.
How it shows up
IOPS-over-time plot: high, then decline, then a noisy plateau with dips; write latency p99.9 in the tens of ms.
Spec basis
Not specified by NVMe. Related features that help: Deallocate/TRIM (DSM), Write Zeroes, over-provisioning, Endurance Group / NVM Sets, Flexible Data Placement (reduces write amplification when supported).
Typical causes
No TRIM (filesystem mounted without discard and no periodic fstrim), low over-provisioning, mixed hot/cold data, and see the "deallocate completes but does nothing" silent failure elsewhere in this atlas.
How to detect / prove
CAUTION: precondition (2× capacity sequential, then random 4k writes) and use fio --steadystate=iops_slope:0.1%; record SMART "Data Units Written" before/after to compute host writes; if the vendor log exposes NAND writes, compute write amplification.
In a trace
Device stops fetching SQEs for milliseconds while queues are full; then bursts of CQEs.
Linux v7.2 source
Discard path drivers/nvme/host/core.c:nvme_setup_discard (DSM deallocate).
Test to provoke it
CAUTION: the SNIA-style preconditioning workflow on a scratch drive; compare with and without a full-drive deallocate beforehand.
P-06Thermal throttling DegradedDevice
What happens
As the composite temperature rises, the controller reduces performance to stay within limits — either its own internal throttling or Host Controlled Thermal Management (HCTM) levels TMT1/TMT2 set by the host.
How it shows up
Throughput saw-tooth that correlates with temperature. Evidence lives in the SMART / Health Information log: Composite Temperature, Warning Composite Temperature Time, Critical Composite Temperature Time, Temperature Sensor 1–8, Thermal Management Temperature 1/2 Transition Count and Total Time. Crossing a temperature threshold can also raise a SMART/Health async event (critical warning temperature bit).
Spec basis
NVMe Base: SMART / Health Information log page fields above; Identify Controller WCTEMP, CCTEMP, MNTMT, MXTMT; Set Features Temperature Threshold (04h) and Host Controlled Thermal Management (10h).
Typical causes
No heatsink or airflow (M.2 under a GPU), Gen5 drives with high controller power, sustained writes, HCTM thresholds set too low by platform software.
How to detect / prove
Sample nvme smart-log /dev/nvme0 every second during the workload (temperature, thm_temp1_trans_count, thm_temp1_total_time, warning_temp_time); the counters increasing during the dips is proof. Linux exposes temperatures through hwmon (sensors).
In a trace
Longer gaps between data bursts; possibly power-state changes if the device uses them to throttle.
Linux v7.2 source
SMART fields in include/linux/nvme.h struct nvme_smart_log: warning_temp_time, critical_comp_time, temp_sensor[8], thm_temp1_trans_count, thm_temp2_trans_count, thm_temp1_total_time, thm_temp2_total_time; feature ids NVME_FEAT_TEMP_THRESH (04h), NVME_FEAT_HCTM (10h); mntmt/mxtmt in Identify Controller.
Test to provoke it
CAUTION: sustained sequential write on a scratch drive with airflow blocked for a short, monitored period; stop at WCTEMP. Never exceed the drive's critical temperature.

8.3 Host, Power-Management and Link Anomalies

P-07APST / ASPM wake-latency spikes DegradedPower management
What happens
After idle, the drive enters a non-operational power state via Autonomous Power State Transition (APST), and/or the link enters L1 / L1 substates via ASPM. The first I/O after idle pays the exit latency (the power state descriptor's EXLAT, plus link L1 exit latency) — from tens of µs to tens of ms.
How it shows up
Latency outliers that occur only after idle periods (bursty workloads, interactive desktops); benchmarks with continuous load never see them. Some drive/platform combinations fail to wake at all (then it becomes a controller-fatal/timeout failure, which is why Linux has quirks).
Spec basis
NVMe Base: Power State Descriptors (ENLAT, EXLAT, non-operational flag), Autonomous Power State Transition feature (0Ch), Identify Controller APSTA, NPSS; PCI Express Base: ASPM L0s/L1, L1 PM Substates, exit latencies in Link Capabilities.
Typical causes
Linux v7.2 default default_ps_max_latency_us = 100000 (100 ms) allows deep states; platform ASPM policy "powersave"; drives with optimistic EXLAT values.
How to detect / prove
Read the APST table: nvme get-feature /dev/nvme0 -f 0x0c -H; the descriptor latencies: nvme id-ctrl /dev/nvme0 -H (power states); ASPM state: lspci -vvv "LnkCtl: ASPM …"; cat /sys/module/pcie_aspm/parameters/policy. Experiment: run fio --thinktime=2s --thinktime_blocks=1 (idle between I/Os) and compare p99 with APST disabled (nvme_core.default_ps_max_latency_us=0) — a clear difference is proof.
In a trace
Link: L1 entry/exit (electrical idle, then training to L0) before the first doorbell is serviced; device: long SQE-fetch delay after the doorbell for the first command after idle.
Linux v7.2 source
drivers/nvme/host/core.c:nvme_configure_apst, nvme_apst_get_transition_time, module parameter default_ps_max_latency_us (100000); quirks NVME_QUIRK_NO_APST, NVME_QUIRK_NO_DEEPEST_PS in drivers/nvme/host/nvme.h; per-device limit via PM QoS latency tolerance in sysfs.
Test to provoke it
SAFE: read-only fio with think time as above, with APST enabled vs disabled; plot first-I/O-after-idle latency.
P-08Interrupt storm or interrupt-coalescing misconfiguration DegradedHost / NVMe
What happens
One interrupt per completion at 1M+ IOPS costs a lot of CPU (storm); conversely, aggressive coalescing (Feature 08h aggregation threshold/time) saves CPU but adds latency up to the aggregation time to every I/O at low QD. Misrouted interrupts (all vectors on CPU 0) create a single-core bottleneck.
How it shows up
High %irq/%soft in mpstat; one CPU at 100%; or a constant added latency (e.g. +100 µs) at QD 1.
Spec basis
NVMe Base: Interrupt Coalescing feature (08h: Aggregation Time in 100 µs units, Aggregation Threshold), Interrupt Vector Configuration feature (09h: Coalescing Disable per vector).
Typical causes
Coalescing set by vendor tools or firmware defaults; irqbalance moving NVMe vectors away from their managed affinity; fewer MSI-X vectors than CPUs.
How to detect / prove
nvme get-feature /dev/nvme0 -f 0x08 -H; grep nvme /proc/interrupts (per-CPU counts per queue); mpstat -P ALL 1; compare IOPS/CPU with poll_queues + --hipri polling.
In a trace
Ratio of MSI-X MWr to CQE MWr: 1:1 means no coalescing; 1:N with a fixed delay between the first CQE and the MSI-X means coalescing by time.
Linux v7.2 source
Linux v7.2 does not program Feature 08h: NVME_FEAT_IRQ_COALESCE is only defined in include/linux/nvme.h, not used by drivers/nvme/host. Vector setup: drivers/nvme/host/pci.c:nvme_setup_irqs; polling queues via module parameter poll_queues.
Test to provoke it
CAUTION (changes device settings, revert afterwards): nvme set-feature /dev/nvme0 -f 0x08 -v <value> on a test system and measure QD 1 latency before/after.
P-09CPU-bound submission path DegradedHost
What happens
The host cannot generate I/O fast enough: one fio job on one core saturates at a few hundred thousand IOPS with libaio, so a drive rated for 1.5M IOPS appears "slow".
How it shows up
fio cpu: usr/sys near 100% per job; Little's Law mismatch (8.1.2); adding jobs increases IOPS linearly.
Spec basis
None (host software).
Typical causes
Single job; synchronous engine; buffered I/O; per-I/O syscalls; kernel debug options; security mitigations; IOMMU in strict mode (map/unmap per I/O); CPU in a low-frequency state.
How to detect / prove
perf top / perf record -g during the run to see where cycles go; try --ioengine=io_uring --fixedbufs --registerfiles --hipri, more numjobs, --iodepth_batch_submit; check cpupower frequency-info.
In a trace
Device idle gaps: doorbells arrive slowly; the SQ is rarely deep.
Linux v7.2 source
drivers/nvme/host/pci.c:nvme_queue_rq, nvme_commit_rqs (batched doorbells), nvme_poll_cq; block/blk-mq.c for the submission path.
Test to provoke it
SAFE: read-only 4k random read with numjobs=1 vs 8, libaio vs io_uring; record IOPS per CPU.
P-10NUMA misplacement DegradedHost
What happens
On a multi-socket (or multi-die) server, the SSD's root port belongs to one NUMA node. Threads and buffers on the other node make every DMA and every MMIO doorbell cross the inter-socket link, adding latency and consuming inter-socket bandwidth.
How it shows up
10–30% higher latency or lower IOPS depending on which CPUs run the benchmark; results that vary run to run as the scheduler moves threads. impl
Spec basis
None (platform topology).
Typical causes
Benchmark not pinned; application threads on the wrong socket; interrupt affinity crossing nodes; memory allocated on the remote node.
How to detect / prove
cat /sys/bus/pci/devices/<bdf>/numa_node and local_cpulist; run fio with --numa_cpu_nodes=N --numa_mem_policy=bind:N (or numactl --cpunodebind=N --membind=N fio …) for local and remote N and compare; perf stat uncore/inter-socket counters where available.
In a trace
Higher host-side completion latency on the analyzer (time from a host MRd/CplD to its completion) when buffers are remote.
Linux v7.2 source
drivers/nvme/host/pci.c allocates queues with dev_to_node()-based NUMA hints (e.g. the HMB/descriptor allocations pass numa_node).
Test to provoke it
SAFE: read-only fio pinned locally vs remotely.
P-11Link trained below capability (speed or width downgrade) DegradedPCIe PHY
What happens
A Gen4 x4 drive links at Gen3 or at x2 (or x1). Everything works, at half or a quarter of the bandwidth.
How it shows up
lspci -vvv: "LnkSta: Speed 8GT/s (downgraded), Width x2 (downgraded)" vs "LnkCap: Speed 16GT/s, Width x4"; Linux at enumeration prints "… available PCIe bandwidth, limited by … link at … (capable of …)". Bandwidth-management interrupts may log autonomous speed changes.
Spec basis
PCI Express Base: Link Capabilities (Max Link Speed/Width), Link Status (Current Link Speed, Negotiated Link Width), LTSSM training and Recovery speed changes.
Typical causes
Slot wired with fewer lanes (chipset slot, bifurcation settings), riser cables, BIOS forcing Gen3, signal-integrity problems causing the LTSSM to fall back, thermal or power policy (some laptops lower speed on battery).
How to detect / prove
cat /sys/bus/pci/devices/<bdf>/{current_link_speed,max_link_speed,current_link_width,max_link_width}; check the upstream port's LnkCap too (the link runs at the lower of the two); dmesg | grep 'limited by'. Bandwidth test: sequential read plateau ≈ the ceiling of the downgraded link.
In a trace
Training sets showing the negotiated rate/width; Recovery entries with speed change; per-lane activity on only 2 of 4 lanes.
Linux v7.2 source
drivers/pci/probe.c:pcie_report_downtraining → drivers/pci/pci.c:__pcie_print_link_status ("%u.%03u Gb/s available PCIe bandwidth, limited by %s x%d link at %s (capable of …)"); pcie_bandwidth_available; register fields PCI_EXP_LNKSTA_CLS, PCI_EXP_LNKSTA_NLW.
Test to provoke it
SAFE: move the drive between slots and record LnkSta; CAUTION: forcing the target link speed via Link Control 2 with setpci and retraining on a test system.
P-12Small MPS or MRRS limiting throughput DegradedPCIe TL
What happens
MPS = 128 B costs ≈8% of a Gen4 x4 link versus 256 B and ≈12% versus 512 B (8.1.1). A small MRRS (e.g. 128 B) forces the SSD to issue many more read requests to fetch write data, each needing a tag and a completion; with limited outstanding tags this caps write throughput.
How it shows up
Sequential read or write stuck at ~85–90% of the expected plateau; lspci -vvv "DevCtl: MaxPayload 128 bytes, MaxReadReq 128 bytes".
Spec basis
PCI Express Base: Max_Payload_Size, Max_Read_Request_Size (Device Control).
Typical causes
A device on the same hierarchy that supports only 128 B forcing the "safe" MPS for all; firmware defaults; kernel MPS policy (pci=pcie_bus_safe, pcie_bus_perf, pcie_bus_peer2peer, pcie_bus_tune_off).
How to detect / prove
lspci -vvv for every device from root port to SSD (DevCap MaxPayload vs DevCtl MaxPayload); compare sequential bandwidth; analyzer shows TLP payload sizes directly.
In a trace
All data MWr exactly 128 B; MRd requests of 128 B each with many tags outstanding.
Linux v7.2 source
drivers/pci/probe.c:pcie_bus_configure_settings, pcie_bus_configure_set, pcie_write_mps, pcie_write_mrrs; pcie_bus_config values PCIE_BUS_TUNE_OFF, PCIE_BUS_SAFE, PCIE_BUS_PERFORMANCE, PCIE_BUS_PEER2PEER.
Test to provoke it
CAUTION: boot with a different pci=pcie_bus_* policy on a lab machine and compare; never lower MPS on one end only (that is V-26).
P-13Misaligned or sub-sector writes causing read-modify-write DegradedHost / device
What happens
A namespace formatted with 512-byte LBAs on a drive whose internal mapping unit is 4 KiB (or larger) receives writes that are not 4 KiB aligned or not 4 KiB multiples. The FTL must read the rest of the unit, merge and rewrite: more latency, more NAND writes.
How it shows up
Small-write IOPS far below datasheet; higher write amplification; nothing in logs.
Spec basis
NVM Command Set: LBA formats (Identify Namespace LBAF, "Relative Performance" field), and optimal I/O hints: NPWG (Preferred Write Granularity), NPWA (Preferred Write Alignment), NOWS (Optimal Write Size) when reported.
Typical causes
Partitions not 1 MiB aligned; databases with 512 B or 2 KiB pages; namespace formatted with a non-preferred LBA format.
How to detect / prove
nvme id-ns /dev/nvme0n1 -H (LBA formats with "Relative Performance", npwg/npwa/nows); cat /sys/block/nvme0n1/queue/{physical_block_size,optimal_io_size,minimum_io_size}; fio with --bs=4k --offset=512 vs aligned on a scratch device.
In a trace
SLBA/NLB values not multiples of 8 (for 512 B LBAs and 4 KiB units).
Linux v7.2 source
drivers/nvme/host/core.c derives physical_block_size/io_opt from NPWG/NOWS when the namespace reports them (search for npwg in nvme_update_disk_info-related code).
Test to provoke it
CAUTION (writes): aligned vs misaligned 4k random write on a scratch namespace.
P-14Flush/FUA-heavy workload on a drive without (or with disabled) volatile write cache DegradedHost / device
What happens
Applications that call fsync after every write generate Flush commands (or FUA writes). On consumer drives with a volatile write cache, each Flush forces cached data to NAND — sync-write latency jumps from tens of µs to milliseconds. Enterprise drives with power-loss protection can acknowledge flushes quickly.
How it shows up
Database commit latency high; iostat shows low throughput but high w_await; nothing in logs.
Spec basis
NVMe Base / NVM Command Set: Flush command (00h), Force Unit Access bit in Write, Volatile Write Cache feature (06h) and Identify Controller VWC.
Typical causes
Workload design; drive class (no power-loss protection); volatile write cache disabled by a tool (each write then becomes write-through).
How to detect / prove
nvme id-ctrl /dev/nvme0 | grep vwc; nvme get-feature /dev/nvme0 -f 0x06; cat /sys/block/nvme0n1/queue/write_cache; fio with --fsync=1 vs none on a scratch device; count Flush commands with the nvme_setup_cmd trace event.
In a trace
SQE opcode 00h after every write; long SQE→CQE time for each Flush.
Linux v7.2 source
drivers/nvme/host/core.c:nvme_setup_cmd (flush and FUA paths); write-cache reporting set from VWC.
Test to provoke it
CAUTION (writes): fio --rw=randwrite --bs=4k --fsync=1 on a scratch namespace, compared with --fsync=0.
