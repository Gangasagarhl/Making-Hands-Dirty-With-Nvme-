IV.5 How to catch silent failures

A silent failure becomes visible only when something outside the failing component checks the result. The drive's own status is useless here, by definition. This chapter collects the techniques used in the cards above into one toolbox, says which failures each technique catches, and shows how to use a PEX trace as part of the proof instead of expecting it to show the failure by itself.

  • Pick the right end-to-end check for each class of silent failure (content, location, version, durability, erasure, reporting).
  • Use fio's verify modes correctly, including the ones for trim and for crash testing.
  • Design golden-data patterns that tell you what went wrong, not only that something did.
  • Plan an analyzer capture so the PEX trace contains the promise, the command and the broken result.

IV.5.2 fio verify: the workhorse

fio writes blocks with a verification header (a magic value, the block's offset and length, the verify type, and a checksum of the data) and later reads them back and checks them. Because the header contains the offset, fio catches misdirected writes as well as corruption. The options below exist in current fio. Check fio --cmdhelp=<option> for your version.

OptionUseCatches
--verify=crc32c (or sha256, xxhash, md5, …)Checksum type in the header. crc32c is fast; sha256 for "is this really my data" audits.D-16, D-14 (offset in header)
--verify=pattern --verify_pattern=0x…Fixed pattern, no header. Useful when you need a known byte value on the wire (easy to recognise in a PEX payload).D-03, D-05 read-backs. Does not catch D-14.
--do_verify=1 / --verify_onlyVerify after the write phase / only verify data written by an earlier run with the same job parameters (for example after a power cycle).D-10, D-13 after reboot
--verify_backlog=NVerify while writing, after every N blocks, so errors are found close to when they happen.D-13, D-15 timing
--verify_state_save / --verify_state_loadSave how far a write job got so a later verify_only run after a crash or power cut knows which blocks were completed.Power-cut testing (D-08 – D-12) when combined with a durability point
--verify_fatal=1, --verify_dump=1Stop at the first error and dump the expected and received buffers to files.Evidence for any card: the dump shows the bit pattern (flips vs other block's data)
--trim_percentage=P --trim_verify_zero=1 --trim_backlog=NTrim a percentage of the verified blocks and check that they read back as zero.D-01/D-03 when DLFEAT RB = 001b. On RB = 000b drives, expect false alarms.

⚠️ fio verify limits

fio verifies content and location. On its own it cannot tell an old version from a new one when both were valid fio blocks for that offset, and it cannot tell whether data is durable. For those you need a generation counter (custom tool) and the power-cut ledger of Lab IV.3. All verify runs that write are destructive to the target device.

IV.5.3 Golden-data patterns that explain the failure

A good pattern does not just say "mismatch". It says what the wrong data is. Put these fields in every logical block (512 B or 4 KiB) you write, at fixed offsets:

Bytes0–78–1516–2324–2728–3132 … end−4last 4
FieldMagic + test-run IDIntended LBAGeneration (write count for this LBA)Epoch / flush numberWriter ID (queue, thread)Pseudo-random fill seeded from (LBA, generation)CRC32C of bytes 0 … end−5
  • Bad CRC, right LBA/generation: content corruption (D-16). Compare with the regenerated fill to see whether it is a few bits or a chunk.
  • Good CRC, other LBA: misdirected write or read (D-14). The field tells you where the data was meant to go.
  • Good CRC, right LBA, older generation: lost write or stale read (D-13/D-15). The generation gap tells you how many writes were lost.
  • Good CRC, wrong run ID: data from a previous test run, so the device kept data across a Format, Sanitize or deallocate (D-03, D-18, D-20).
  • All zeroes / all FFh: deallocated or erased. Compare with DLFEAT, and with what should be there.
  • Mixed within one multi-block record: torn write (D-11). The epoch field tells you whether it was flushed.

The magic and LBA fields also make blocks easy to spot by eye in a PEX trace: the analyzer's payload view of a Read MWr shows the first bytes, so you can see "LBA 0x1E8480, generation 1, run 7" directly in the capture.

IV.5.4 Protection information (PI / DIF)

PI adds 8 or 16 bytes per block (guard CRC, application tag, reference tag) that travel with the data. When the host generates and checks them (Linux with CONFIG_BLK_DEV_INTEGRITY and a registered profile, see core.c:nvme_init_integrity()), corruption anywhere between host memory and NAND causes a Guard Check Error (282h) instead of silent bad data, and Type 1 reference tags catch misdirected blocks (284h). Limits: PI does not catch lost writes or stale versions (the old block has valid PI). With PRACT=1 (Linux's fallback when it has no integrity buffer), the controller generates and strips PI itself, so the host↔controller path is not covered (D-21). Check /sys/block/nvme0n1/integrity/ to see what is active.

IV.5.5 Power-cycle and reset testing

  • Orderly vs unexpected. Test both: orderly shutdown (Linux sets CC.SHN and waits for CSTS.SHST), and sudden power removal. Only the second tests PLP and Flush honesty. The SMART Unsafe Shutdowns counter must count exactly the sudden ones.
  • Randomize timing. Cut at random times relative to Flush completions, during idle (background GC), during Format/Sanitize, during firmware activation.
  • Enough cycles. Failure rates per cut can be low. Zheng et al. used thousands of fault-injection cycles across their drives. Hundreds per drive and workload is a practical minimum.
  • Resets are cheaper power cuts. Controller reset (nvme reset), NVM subsystem reset (nvme subsystem-reset, if NSSRS is supported), FLR, and hot reset exercise much of the same recovery code. Do them first. They also catch D-11 tears and D-27 WP problems.
  • Ledger off-box. The record of what was acknowledged must survive the cut, so send it to another machine.

IV.5.6 Read-back audits and accounting cross-checks

# After any erase-type command (Format, Sanitize, Write Zeroes, deallocate): audit with O_DIRECT.
# CAUTION: read-only, but run it only on the test namespace you just erased.
echo 3 > /proc/sys/vm/drop_caches                 # avoid page-cache false positives
dd if=/dev/nvme0n1 bs=1M iflag=direct status=progress | \
  python3 -c 'import sys
MAGIC=b"ATLAS-T7"     # magic + run ID used by the writer
off=0; hits=0
while True:
    b=sys.stdin.buffer.read(1<<20)
    if not b: break
    i=b.find(MAGIC)
    while i>=0:
        hits+=1
        if hits<=10: print("old data at byte", off+i)
        i=b.find(MAGIC,i+1)
    off+=len(b)
print("blocks with old magic:", hits)'

# Accounting cross-check: write a known amount, compare SMART deltas.
nvme smart-log /dev/nvme0 | grep -iE 'data_units_written|host_write_commands'
#   ... write exactly 1000 x 512,000 bytes with O_DIRECT ...
nvme smart-log /dev/nvme0 | grep -iE 'data_units_written|host_write_commands'
# Data Units Written should rise by about 1000 (units of 1000 x 512 bytes, rounded up).

IV.5.7 Using the PEX trace as part of the proof

For silent failures the analyzer almost never shows the failure on its own. It is still the best evidence you can give a vendor, because it proves the host side was correct and it can contain the broken result as a payload. Plan the capture so it contains all three parts of the story:

  1. The promise. Capture Identify Controller / Identify Namespace (and Get Features) at the start of the test, so DLFEAT, NSFEAT, VWC, ONCS, NAWUPF, FR are in the file.
  2. The command. Trigger on the SQE opcode of interest (DSM 09h, Write Zeroes 08h, Flush 00h, Format 80h, Sanitize 84h, Firmware Commit 10h) and keep its data fetches (range list, PRP lists).
  3. The broken result. Keep capturing through the read-back, the DULBE read, the Identify-after, or the log-page read, so the wrong payload or wrong status is in the same file.

💡 Senior insight

When someone says "the PEX trace shows no error, so the drive is fine", the right answer is: "the trace shows the drive accepted the command. For this command the job happens inside the drive, so we need a read-back or accounting check, and if we capture that too, the trace becomes the proof." In practice, most silent-failure bug reports that vendors take seriously are a capture plus a deterministic read-back script.

🧪 Lab IV.5 — Build a silent-failure regression suite CAUTION LAB
⚠️ Destroys data

Every step writes, trims or erases the test namespace. Use a spare drive or QEMU.

Objective. One script that runs the cheap checks from this part on every new drive or firmware.

  1. Record Identify Controller/Namespace, SMART, firmware log (the promises and baselines).
  2. Golden-pattern fill of 10 GiB; full verify (D-14, D-16).
  3. Deallocate last 5 GiB; read-back per DLFEAT; DULBE probe; NUSE delta (D-01 – D-03, D-07).
  4. Write Zeroes 1 GiB with and without DEAC; read-back (D-05). Guard blocks around each range (D-06).
  5. Overwrite hot set with generation counters from all CPUs; verify versions (D-13, D-15).
  6. Write Uncorrectable + Verify on one LBA (D-33).
  7. SMART counted-write delta (D-25).
  8. Controller reset in the middle of large writes; verify atomic records (D-11).
  9. Scan dmesg for "genctr mismatch", "invalid id", "completion polled", IOMMU faults (D-28 – D-31).
Solution notes

Keep every step's raw outputs (Identify dumps, hexdumps of failing blocks, dmesg) in a per-run directory, and run the suite once on a reference drive or QEMU to calibrate expected results. Mark steps whose interpretation depends on drive promises (step 3 with DLFEAT 000b) as "informational" instead of pass/fail. Add the power-cut ledger (Lab IV.3) as a separate nightly EXPERT job.

Interview questions

  1. Intermediate Why doesn't PI catch lost writes?
    Model answerThe old block still carries PI that is valid for its own data and LBA. Detection needs a version stored outside the block.
  2. Senior How do you convince a vendor that their drive ignores trims when their trace shows a perfect DSM exchange?
    Model answerOne capture containing Identify Namespace (DLFEAT 001b or NSFEAT DULBE), the DSM with the decoded range, the Success CQE, then a Read of an LBA inside the range returning the old golden pattern (with run ID and LBA visible in the payload), or a DULBE read returning Success while a never-written control LBA returns 287h. Add the script so they can reproduce it.
