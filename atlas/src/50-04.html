23 Link Failures That Are Not AER Errors

23.1 Why this chapter exists

The most common PCIe "failure" in the field sets no error bit at all. A link trains at Gen3 instead of Gen4, or at x2 instead of x4, and the SSD runs at half speed for years. Other failures are visible only as side effects: a link retraining hundreds of times a second, a device that disappeared, a Root Port that cut the link off on purpose (DPC), or a device that answers "retry" forever during enumeration. This chapter covers the link, enumeration and containment failures. Chapter 24 covers configuration, interrupt and DMA-translation failures.

23.2 Reading link state correctly

Three registers in the PCI Express Capability matter. Link Capabilities (LnkCap) holds the maximum speed and width this port supports. Link Status (LnkSta) holds the current negotiated speed and width, plus the DL_Active, Link Training, LBMS and LABS bits. Link Control 2 (LnkCtl2) holds the Target Link Speed, which can be lower than LnkCap. The negotiated link is limited by the lesser of the two ends and by every hop. Linux v7.2 computes this in pcie_bandwidth_available(), walking up from the device to find the slowest link on the path to the root.

lspci -vvv -s 0000:03:00.0 | grep -E 'LnkCap:|LnkSta:|LnkCtl2:'
cat /sys/bus/pci/devices/0000:03:00.0/max_link_speed      # from LnkCap
cat /sys/bus/pci/devices/0000:03:00.0/current_link_speed  # from LnkSta
cat /sys/bus/pci/devices/0000:03:00.0/max_link_width
cat /sys/bus/pci/devices/0000:03:00.0/current_link_width
# ...and the same for every upstream port up to the Root Port
⚠️ Power management can make LnkSta lie

Some devices drop to a lower speed when idle (autonomous speed change, or a platform policy) and go back up under load. Read LnkSta while a workload is running before you declare a link downtrained. Also note that LnkSta "downgraded" annotations in newer lspci versions only compare against LnkCap of the same device.

L-25Link trained at lower speed or narrower width than capable DegradedPCIe Physical
In a PEX trace
Visible The training sequence shows it: TS1/TS2 ordered sets advertise data rates and link/lane numbers, lanes that do not respond are marked PAD, and a failed speed change appears as Recovery.Speed reverting. In L0, the analyzer's link-status display shows the negotiated width and rate. The capture must include link-up, or a retrain, for the reason to be visible.
What happens
The LTSSM settled on a lower data rate (for example 8 GT/s instead of 16 GT/s) or fewer lanes (x2 instead of x4). Everything works and nothing is logged as an error, but sequential bandwidth is capped. A Gen4 x4 link carries roughly 7–7.5 GB/s of payload, while Gen3 x2 manages under 2 GB/s.
How it shows up
No AER bit and no NVMe status. Linux v7.2 prints an informational line once at enumeration, from pcie_report_downtraining() → __pcie_print_link_status(dev, false), only when available bandwidth is less than capable: "%u.%03u Gb/s available PCIe bandwidth, limited by %s x%d link at %s (capable of %u.%03u Gb/s with %s x%d link)". The at %s part names the limiting device, which may be an upstream switch port or Root Port and not the SSD. A downgrade after boot (retraining at runtime) does not print this line. bwctrl updates the cached speed in sysfs when the port supports Link Bandwidth Notification.
Spec basis
PCIe Base Specification: Link Capabilities (Max Link Speed, Maximum Link Width), Link Status (Current Link Speed, Negotiated Link Width), Link Control 2 (Target Link Speed), LTSSM Configuration and Recovery (speed change, equalization).
Typical causes
Width: a damaged lane or connector pin; M.2 slots wired x2 on the board; bifurcation set wrong in BIOS; a riser that carries only some lanes. Speed: equalization failure at Gen3+ that falls back to a lower rate; BIOS "Link Speed" set to GenN; a retimer or redriver not rated for the rate; a slot sharing lanes through a slower switch; Linux or firmware lowered Target Link Speed (a thermal cooling device through bwctrl, or the 2.5 GT/s retrain quirk, L-39).
How to detect / prove
Compare LnkCap with LnkSta at each hop under load. dmesg | grep 'limited by'. Prove the performance impact with fio sequential read at high queue depth (bandwidth close to the lower link's ceiling). Re-seat the drive or swap slots. Check LnkCtl2 Target Link Speed. Check BIOS settings.
Linux v7.2 source
drivers/pci/pci.c: __pcie_print_link_status, pcie_print_link_status (verbose variant, exported for drivers), pcie_bandwidth_available, pcie_bandwidth_capable; drivers/pci/probe.c: pcie_report_downtraining (only for Endpoints, Legacy Endpoints and Upstream Ports, function 0, not VFs); drivers/pci/pcie/bwctrl.c: pcie_bwnotif_irq, pcie_set_target_speed.
Test to provoke it
SAFE: limit speed in BIOS, then confirm the log line appears and fio bandwidth drops. CAUTION: write LnkCtl2 Target Link Speed with setpci on the Root Port and set Retrain Link. This changes the live link and may drop it.
Synthetic example — the "limited by" message for a Gen4 x4 SSD behind a Gen3 switch
DeviceLnkCapLnkStaNote
Root Port 0000:00:01.116 GT/s x168 GT/s x16link to switch
Switch USP 0000:01:00.08 GT/s x168 GT/s x16switch is Gen3
Switch DSP 0000:02:04.08 GT/s x48 GT/s x4limiting link
SSD 0000:03:00.016 GT/s x48 GT/s x4prints: 31.504 Gb/s available PCIe bandwidth, limited by 8.0 GT/s PCIe x4 link at 0000:02:04.0 (capable of 63.012 Gb/s with 16.0 GT/s PCIe x4 link)

The bandwidth values in this example come from the kernel's per-lane calculation for 128b/130b encoding (8 GT/s × 128/130 ≈ 7.877 Gb/s per lane). The exact string format is __pcie_print_link_status's. The device numbers are invented synthetic.

L-26Link flapping / recovery storm — only correctable errors, endless retraining DegradedPCIe Physical/Data Link
In a PEX trace
Visible Repeated TS1/TS2 bursts (Recovery) between TLPs, usually after Naks or replays. Count Recovery entries per second and correlate them with gaps in NVMe traffic. The underlying physical-layer errors are covered in the physical-layer part of this atlas.
What happens
The link keeps entering LTSSM Recovery: after Replay Rollover, after receiver errors, or after an electrical-idle glitch. Each retrain stalls all traffic for microseconds to milliseconds. Data is never lost, so no uncorrectable error appears. The only symptoms are correctable counts (RxErr, BadTLP, BadDLLP, Rollover, Timeout), periodic latency spikes, and sometimes a speed or width that changes over time.
How it shows up
Rate-limited severity=Correctable lines (10 per 5 s per device by default, so the log hides the true rate; the aer_dev_correctable counters show it). LnkSta LBMS (Link Bandwidth Management Status) set by hardware when it changes speed or width "to correct unreliable link operation". Linux bwctrl records it (PCI_LINK_LBMS_SEEN). The NVMe layer shows no errors, only p99.9 latency spikes and lower throughput.
Spec basis
PCIe Base Specification: Recovery state, Link Bandwidth Management Status / Link Autonomous Bandwidth Status, Link Bandwidth Management Interrupt Enable.
Typical causes
Marginal signal integrity near the eye limit (temperature dependent). Spread-spectrum clocking mismatch. Failing retimers. ASPM exit problems (L-37).
How to detect / prove
Sample aer_dev_correctable on both ends every second and plot the deltas. Sample LnkSta. Run fio --percentile_list=99:99.9:99.99 latency. A storm shows as all queues stalling together. An analyzer with a trigger on TS1 ordered sets in L0 shows each Recovery entry.
Linux v7.2 source
aer.c: aer_ratelimit, pci_dev_aer_stats_incr; bwctrl.c: pcie_bwnotif_irq, pcie_reset_lbms; Documentation/PCI/pcieaer-howto.rst "AER Ratelimits".
Test to provoke it
CAUTION: thermal cycling of the riser or SSD under load. EXPERT: lane-margining at an offset that produces occasional errors.
L-27Surprise link down without Surprise Down reporting Timer onlyPCIe Data Link
In a PEX trace
Partly visible On the SSD link: abrupt electrical idle with no PM or Hot Reset first. The host's later requests appear on the Root Port side, but the Root Port drops them once the link is down, so they are not on this link. The 30-second NVMe timeout and the CSTS read returning all-ones are host-side, and visible only if the probe is upstream.
What happens
The link drops (DL_Active goes to 0), but the Downstream Port does not support Surprise Down error reporting, or the error is masked, or there is no hot-plug or DPC service on that port. Nothing is signalled. The host finds out the next time it touches the device: MMIO reads return all-ones (after a Completion Timeout at the Root Port, if that is logged), doorbell writes vanish, and every outstanding NVMe command waits for its timer.
How it shows up
Up to io_timeout (30 s default in Linux v7.2) or admin_timeout (60 s) later: nvme_timeout() reads CSTS = 0xffffffff, nvme_should_reset() decides it must reset (CFS bit appears set in all-ones), and the driver logs controller is down; will reset: CSTS=0xffffffff, PCI_STATUS=0xffff plus Does your device have a faulty power saving mode enabled? and Try "nvme_core.default_ps_max_latency_us=0 pcie_aspm=off pcie_port_pm=off" and report a bug. The reset then fails (nvme_pci_enable sees CSTS == -1), and Disabling device after reset failure: -19 follows (C-17).
Spec basis
PCIe Base Specification: Data Link Layer Link Active Reporting Capable, Surprise Down Error Reporting Capable (both optional); a read to a non-responding device ends in a Completion Timeout at the requester.
Typical causes
SSD firmware hang or crash that takes down the PHY. Power-state exit failures (APST, L1.2). Power delivery dips. Connector problems.
How to detect / prove
Read the port's LnkSta (DLActive-) and LnkCap ("Surprise-" / "DLActive-" capability flags). Cross-check the time of the first NVMe timeout with the kernel timestamps of earlier traffic. An analyzer left armed on electrical idle catches the moment.
Linux v7.2 source
nvme/host/pci.c: nvme_timeout, nvme_should_reset, nvme_warn_reset, nvme_pci_enable, nvme_reset_work; core.c: admin_timeout, nvme_io_timeout.
Test to provoke it
EXPERT: cut SSD power with an interposer on a slot without Surprise Down reporting; or force a firmware crash with a vendor debug command.
L-28DPC containment event — the port cut the link on purpose ReportedPCIe Data Link
In a PEX trace
Partly visible On the SSD link: the port forces the link down (electrical idle, no TLPs), then after software clears DPC a fresh Detect, Polling, Configuration, L0 and the re-enumeration CfgRd/CfgWr sequence. The trigger reason is in the port's DPC registers. If the trigger was an ERR_FATAL from the SSD, that message is visible just before the link goes down.
What happens
A Downstream Port with Downstream Port Containment (DPC) enabled saw an uncorrectable error. Linux v7.2 configures DPC to trigger only on ERR_FATAL, as the dpc_handler comment says. The port immediately disables its link, so no possibly-corrupt TLPs travel further upstream, and it interrupts the OS. Every request to the SSD fails until software clears the trigger and the link retrains.
How it shows up
dpc_process_error() logs one of: containment event, status:%#06x: unmasked uncorrectable error detected (the port's own error, followed by the AER details); containment event, status:%#06x, ERR_FATAL received from DDDD:BB:DD.F (an error message from the SSD); or containment event, status:%#06x: RP PIO error detected / software trigger detected. With RP extensions, RP PIO details follow, for example [18] Memory Request Completion Timeout. Then pcie_do_recovery(pdev, pci_channel_io_frozen, dpc_reset_link): the NVMe driver logs frozen state error detected, reset controller then restart after slot reset. If the link does not come back: Data Link Layer Link Active not cleared in 1000 msec, root port still busy, or device recovery failed.
Spec basis
PCIe Base Specification: Downstream Port Containment, DPC Status Trigger Reason, RP PIO extensions.
Typical causes
Any fatal error from the SSD (L-10, L-13, L-17, L-18, L-11). Completion Timeouts of host MMIO reads when RP PIO is enabled. Software trigger by firmware (EDR).
How to detect / prove
dmesg | grep -E 'DPC|containment'. lspci -vvv -s <port> shows the DPC capability and DpcSta. On probe, Linux prints enabled with IRQ and an error containment capabilities: Int Msg #%d, RPExt%c PoisonedTLP%c SwTrigger%c RP PIO Log %d, DL_ActiveErr%c line, which tells you what is enabled.
Linux v7.2 source
drivers/pci/pcie/dpc.c: dpc_irq, dpc_handler, dpc_process_error, dpc_process_rp_pio_error, dpc_reset_link, dpc_wait_rp_inactive, pci_dpc_recovered; err.c: pcie_do_recovery.
Test to provoke it
CAUTION: software trigger via DPC Control (setpci) on a test port. EXPERT: inject a fatal error with an exerciser. The effect is a full SSD reset, and data in flight is lost.
L-29Hot-plug removal under I/O (surprise or orderly) ReportedPCIe / host
In a PEX trace
Partly visible For orderly removal: the CC write with SHN set, CSTS polling, then the link going down. For surprise removal: only the abrupt end of traffic. Presence-detect and slot events are sideband signals, not TLPs.
What happens
The SSD is removed or powered off in a hot-plug slot. In an orderly removal (attention button or echo 0 > /sys/bus/pci/slots/N/power) the OS unbinds the driver first. In a surprise removal the device is already gone when the driver is told. The PCI core marks it disconnected, and pending I/O must fail rather than hang.
How it shows up
The hot-plug driver (pciehp, not in the local source tree used here) logs slot link-down and presence-change events uncertain wording. Linux v7.2 NVMe: nvme_remove() sets the state to DELETING and, if !pci_device_is_present(), sets DEAD and calls nvme_dev_disable(dev, true) at once, so outstanding requests are cancelled and namespaces are marked dead (nvme_mark_namespaces_dead → blk_mark_disk_dead). Filesystems see I/O errors. In nvme_timeout(), if pci_dev_is_disconnected() is true, the controller goes straight to DELETING and is disabled. The source comment says this unblocks a deadlock between error recovery and removal.
Spec basis
PCIe Base Specification: Hot-Plug (Presence Detect, Data Link Layer State Changed, Attention Button); NVMe transport behaviour is up to the host.
Typical causes
Operator removal, drive failure that triggers presence-detect change, backplane faults.
How to detect / prove
dmesg around removal; lspci no longer lists the BDF; /sys/block/nvme* disappears. Check that no task is left in D state (ps -eo stat,pid,cmd | grep '^D'), which would mean an I/O path hang.
Linux v7.2 source
nvme/host/pci.c: nvme_remove, nvme_timeout, nvme_dev_disable, nvme_pci_ctrl_is_dead; core.c: nvme_mark_namespaces_dead, nvme_remove_namespaces.
Test to provoke it
CAUTION: orderly hot-remove through sysfs slot power with fio running on a scratch namespace, then check for hung tasks. EXPERT: physical surprise removal in a certified hot-plug bay.
L-30Configuration RRS (CRS) loop — device answers "retry" forever Timer onlyPCIe Transaction
In a PEX trace
Visible CfgRd0 to the Vendor ID register answered with a Cpl with Completion Status RRS (Configuration Request Retry Status), repeated with growing gaps (Linux doubles its delay). If the device never returns Successful Completion within the timeout, the loop is the evidence.
What happens
After reset or power-up, a function may return Configuration Request Retry Status (RRS, formerly CRS) completions while it initializes. If its firmware never finishes booting, it keeps answering RRS. Enumeration or post-reset restore waits and then gives up. The device is missing from lspci, or present but unusable.
How it shows up
With Configuration RRS Software Visibility enabled on the Root Port (Linux enables it if supported: PCI_EXP_RTCAP_RRS_SV → PCI_EXP_RTCTL_RRS_SVE), a Vendor ID read returns a special value, which Linux recognises with pci_bus_rrs_vendor_id(). During enumeration, pci_bus_wait_rrs() doubles its delay each time and logs pci DDDD:BB:DD.F: not ready after %dms; waiting once past 1000 ms, then ready after %dms or not ready after %dms; giving up. After resets, pci_dev_wait() logs not ready %dms after %s; waiting / giving up (the timeout for reset waits is PCIE_RESET_READY_POLL_MS = 60000 ms). Past PCI_RESET_WAIT (1000 ms) it tries one link retrain through pcie_failed_link_retrain(). Without RRS visibility, the hardware retries silently and eventually returns all-ones.
Spec basis
PCIe Base Specification: Configuration Request Retry Status, Configuration RRS Software Visibility, the rule that a device must be ready for configuration requests after reset within the specified time (with Readiness Notifications as an optional speed-up).
Typical causes
SSD firmware stuck in its boot ROM (corrupt firmware image, failed update). Very slow boot after unsafe shutdown with a large mapping-table rebuild. Power sequencing problems.
How to detect / prove
dmesg | grep -E 'not ready|ready after'. A long "ready after" (several seconds) on every boot is a latent problem even when it works. Time the SSD's boot after power-on with an analyzer: count the RRS completions.
Linux v7.2 source
drivers/pci/probe.c: pci_bus_wait_rrs, RRS SV enable around line 1304; drivers/pci/pci.c: pci_dev_wait, PCI_RESET_WAIT, PCIE_RESET_READY_POLL_MS; quirks.c: pcie_failed_link_retrain.
Test to provoke it
EXPERT: an exerciser as endpoint that answers RRS for N seconds; or a vendor command that holds the SSD in its boot loader.
L-31BAR not assigned / resource conflict — driver cannot map registers ReportedPCIe config / host
In a PEX trace
Partly visible The enumeration CfgWr sequence to BAR0/BAR1 and the readback show the sizing and the assigned address. Later MMIO TLPs are either missing or go to an address outside the SSD's BAR. The OS's decision not to assign the BAR is host-side.
What happens
The SSD's BAR0 (registers and doorbells) has no address assigned, or has one that conflicts with another device or lies outside the upstream bridge window. The NVMe driver's probe fails, or MMIO goes to the wrong place.
How it shows up
Enumeration messages from probe.c such as %s: can't handle BAR larger than 4GB, %s: can't handle BAR above 4GB, initial BAR value %#010llx invalid, device has non-compliant BARs; disabling IO/MEM decoding, or devices behind bridge are unusable because %pR cannot be assigned for them. Resource-assignment failure messages come from setup-res.c, which is not in the local tree, so treat their wording as uncertain. NVMe probe then fails in nvme_dev_map() / pci_request_mem_regions or reads all-ones; nvme_pci_enable logs reading CSTS register failed at debug level only, and probe ends with probe failed (dev_err_probe).
Spec basis
PCI/PCIe configuration space: BARs, bridge memory windows. NVMe: BAR0/BAR1 hold the controller registers (the 64-bit MLBAR/MUBAR pair).
Typical causes
Too little 32-bit MMIO space with many devices. BIOS not reserving hot-plug windows. Thunderbolt or USB4 enclosures. SR-IOV VF BARs exhausting space. "Above 4G decoding" disabled.
How to detect / prove
lspci -vv -s <BDF> showing "Region 0: Memory at <unassigned>" or "[disabled]"; cat /proc/iomem; dmesg | grep -i 'BAR\|bridge window'. Try pci=realloc as a diagnostic boot option.
Linux v7.2 source
drivers/pci/probe.c: BAR sizing messages (lines ~264–320), "devices behind bridge are unusable..."; nvme/host/pci.c: nvme_dev_map, nvme_remap_bar, nvme_pci_enable.
Test to provoke it
SAFE: boot with many devices and BIOS "above 4G decoding" off, then inspect. CAUTION: hot-plug into a slot whose bridge window is too small.
L-39Link never reaches DL_Active — training fails or oscillates between speeds Timer onlyPCIe Physical
In a PEX trace
Visible Repeated TS1/TS2 ordered sets alternating between data rates, the link never reaching L0 or dropping back to Recovery straight away, and no DLLPs or TLPs ever exchanged. A Linux retrain at 2.5 GT/s appears as a new training sequence advertising only 2.5 GT/s.
What happens
Training never completes. The LTSSM cycles between Detect, Polling, Configuration and Recovery, or keeps switching speed. The pcie_failed_link_retrain() comment in quirks.c describes a real case (ASMedia ASM2824 switches) where the link "continues switching between the two speeds indefinitely and the data link layer never reaches the active state, with link training reported repeatedly active ~84% of the time". The SSD never appears.
How it shows up
The SSD is not enumerated. Linux v7.2 may log broken device, retraining non-functional downstream link at 2.5GT/s, then removing 2.5GT/s downstream link speed restriction on success or retraining failed on failure. Also Data Link Layer Link Active not set in %d msec from pci_bridge_wait_for_secondary_bus() in pci.c (after pcie_wait_for_link_delay() fails).
Spec basis
PCIe Base Specification: LTSSM, Data Link Layer Link Active, Link Bandwidth Management Status, Target Link Speed.
Typical causes
Speed-negotiation interoperability bugs. Bad equalization. A broken lane 0. Missing reference clock. PERST# timing.
How to detect / prove
Port LnkSta shows Link Training set or toggling, DLActive-, and LBMS+. The quirk uses exactly this: DLLLA clear plus LBMS seen. Try forcing 2.5 GT/s Target Link Speed to see whether the link comes up.
Linux v7.2 source
drivers/pci/quirks.c: pcie_failed_link_retrain; bwctrl.c: pcie_set_target_speed; pci.c: pci_dev_wait.
Test to provoke it
EXPERT: an exerciser that refuses speed change, or a degraded channel at the target rate.
