8 Errors Reported Through Logs, Events and Registers

A CQE status reports the fate of one command. Everything else the controller wants to say arrives on four other channels:

  • Asynchronous Event Requests (AER): the host leaves admin commands (opcode 0Ch) outstanding, and the controller completes one when an event happens.
  • Log pages read with Get Log Page (02h): Error Information (01h), SMART/Health (02h), Firmware Slot (03h), Changed Namespace List (04h), Device Self-test (06h), Telemetry (07h/08h), ANA (0Ch), Persistent Event (0Dh), Sanitize Status (81h), and others (LIDs from libnvme NVME_LOG_LID_*).
  • Controller registers: above all CSTS (BAR0 + 1Ch): CFS (bit 1), NSSRO (bit 4), PP (bit 5), SHST (bits 3:2) (Linux NVME_CSTS_*).
  • Completion Dword 0 of specific commands (Abort result bit 0, Firmware Commit statuses, Set Features results).

This chapter's cards cover those channels. In a PEX capture they are visible in a specific way. An AER completion is an ordinary CQE on the admin CQ (Dword 0 carries the event). A log page is a device→host MWr of the log data into the host buffer, but only if someone reads it during the capture. A register is visible only when the host reads it: an MRd to BAR0 + offset and the CplD with the value. The controller never pushes register changes over the link.

Two rules decide whether you ever see an event verified in Linux and QEMU source:

  1. Configuration. SMART critical-warning events and notices are enabled per bit in the Asynchronous Event Configuration feature (FID 0Bh). Linux's nvme_enable_aen() writes only ctrl->oaes & (NVME_AEN_CFG_NS_ATTR | NVME_AEN_CFG_FW_ACT | NVME_AEN_CFG_ANA_CHANGE | NVME_AEN_CFG_DISC_CHANGE), i.e. bits 8, 9, 11 and 31. SMART bits 7:0 stay 0, so Linux does not ask for SMART AENs (QEMU's nvme_smart_event() checks NVME_AEC_SMART(n->features.async_config) & event and drops them).
  2. Masking until the log is read. After an event of a given type is reported, further events of that type are held back until the host reads the indicated log page (without the Retain Asynchronous Event bit). QEMU: n->aer_mask |= 1 << type on delivery, and nvme_clear_events() on the log read. Linux reads the log for notices it handles itself (Changed NS list, ANA, FW slot). For Error and SMART events it only sends a uevent. Unless user space reads the log, Error/SMART events of that type stop after the first one.

Linux posts exactly one AER (NVME_NR_AEN_COMMANDS = 1) with a fixed CID (NVME_AQ_BLK_MQ_DEPTH), so in a PEX trace the AER is easy to find: an admin SQE with opcode 0Ch, and much later a CQE on the admin CQ with that CID and the event in Dword 0.

# Watch events as they happen (Linux)
udevadm monitor --kernel --property | grep -E 'NVME_AEN|nvme'
echo 1 > /sys/kernel/tracing/events/nvme/nvme_async_event/enable
# Turn SMART critical-warning AENs on (bits 0-5 + keep the notice bits Linux set)
nvme get-feature /dev/nvme0 -f 0x0b -H
nvme set-feature /dev/nvme0 -f 0x0b -v 0x00000b3f   # example value; read OAES first (nvme id-ctrl | grep oaes)
⚠️ Example value

The value above is illustrative. It enables SMART bits 0–5 and notice bits 8, 9, 11. Only set notice bits the controller lists in OAES, or Set Features may fail with Invalid Field. Linux rewrites FID 0Bh on every reset (nvme_enable_aen()), so your SMART bits are lost after a controller reset.

8.2 Error Information log and the More bit

S-71Error Information log entry (LID 01h) — the detail behind More ReportedNVMe log
In a PEX trace
Partly visible The More bit (CQE DW3 bit 30) of the failed command is visible. The entry itself is visible only if a Get Log Page LID 01h is issued inside the capture window: admin SQE (02h, CDW10 LID=01h), then a device→host MWr of 64-byte entries into the host buffer. Decode error_count, SQID, CID, status_field and LBA from that payload.
What happens
For commands that complete with an error (and some errors not tied to a command), the controller records a 64-byte entry: Error Count (unique, increasing), SQID, CID, Status Field, Parameter Error Location, LBA, NSID, Vendor Specific info, Transport Type, Command Specific info, and in newer versions opcode, CSI and log page version (libnvme struct nvme_error_log_page).
How it shows up
Nothing is pushed unless an Error AEN is raised for errors not tied to a command. The SMART "Number of Error Information Log Entries" counter increases. The CQE's More bit says an entry exists for that command.
Spec basis
Error Information log; Identify Controller ELPE (Error Log Page Entries, 0's based); SMART num_err_log_entries.
Typical causes
Any failing command. The log is a ring of ELPE+1 entries, newest first, so heavy error traffic overwrites the evidence quickly. QEMU's nvme_error_info() returns all-zero entries.
How to detect / prove
nvme error-log /dev/nvme0 -e 64 right after the failure; match SQID/CID to the CQE (or to the nvme_complete_rq tracepoint); use Parameter Error Location (byte in bits 7:0, bit in bits 10:8) to find the offending SQE field.
Linux v7.2 source
The driver never reads LID 01h (no use of NVME_LOG_ERROR in drivers/nvme/host/). nvme_log_error() only prints "MORE". struct nvme_error_slot in include/linux/nvme.h defines the entry.
Test to provoke it
SAFE: send an Invalid Field command (e.g. nvme get-feature -f 0x7e) and read nvme error-log. Check that error_count increased and that SQID=0 and the CID match.

8.3 SMART / Health critical warnings (LID 02h, byte 0)

Critical Warning is a bit field (Linux NVME_SMART_CRIT_*, libnvme adds bit 5 PMR read-only). Each set bit is a condition the controller considers critical. If enabled, its rising edge raises a SMART/Health AEN. The bits stay set while the condition lasts. A drive with any bit set should be treated as failing until explained.

S-72SMART critical warning bit 0 — Available Spare below threshold ReportedNVMe log / AEN
In a PEX trace
Partly visible Only as (a) an AER CQE on the admin CQ with DW0 type 1 / info 02h / LID 02h, if enabled, or (b) the SMART log payload (byte 0 bit 0; byte 3 avail_spare; byte 4 spare_thresh) in a device→host MWr when the host reads LID 02h during the capture. The underlying wear is not visible.
What happens
Available Spare (percent of remaining spare blocks) fell below Available Spare Threshold. Spare is used when blocks retire. When it runs out the drive usually goes read-only (bit 3).
How it shows up
critical_warning bit 0 set; avail_spare < spare_thresh in nvme smart-log. Linux: no AEN by default (SMART AEN bits not enabled). If enabled, the AEN becomes a uevent NVME_AEN=0x020201 (type 1, info 02h, LID 02h; illustrative encoding) and nothing else.
Spec basis
SMART/Health Information log: Critical Warning, Available Spare, Available Spare Threshold, Percentage Used; Asynchronous Event Configuration bit 0.
Typical causes
End of life (Percentage Used near or over 100%); early block failures in a bad batch; firmware reporting spare wrongly.
How to detect / prove
Poll nvme smart-log /dev/nvme0 periodically (smartd / node exporter). Trend avail_spare together with percent_used and media_errors.
Linux v7.2 source
core.c:nvme_enable_aen() (SMART bits not requested), core.c:nvme_complete_async_event() (ctrl->aen_result), core.c:nvme_aen_uevent().
Test to provoke it
SAFE in QEMU: enable SMART AENs (FID 0Bh bit 0), then QMP qom-set /machine/peripheral/<nvme-id> smart_critical_warning 1 (nvme_set_smart_warning() raises the event only for newly set bits).
S-73SMART critical warning bit 1 — Temperature threshold ReportedNVMe log / AEN / hwmon
In a PEX trace
Partly visible AER CQE with type 1 / info 01h (if enabled), or the SMART log payload if read. The temperature itself is not on the wire. The thermal effect (throttling) shows up only as longer command latency between SQE fetch and CQE.
What happens
A temperature sensor crossed the over-temperature (or under-temperature) threshold set with the Temperature Threshold feature (FID 04h). Beyond WCTEMP/CCTEMP (Identify Controller) the drive throttles and counts Warning/Critical Composite Temperature Time.
How it shows up
critical_warning bit 1; SMART temperature (Kelvin), warning_temp_time and critical_comp_time increase, thermal management transition counters change. Linux exposes the bit as hwmon temp1_alarm.
Spec basis
Temperature Threshold feature (TMPTH, TMPSEL, THSEL); Identify WCTEMP/CCTEMP; Host Controlled Thermal Management (FID 10h).
Typical causes
Poor airflow, missing heatsink, sustained writes; a threshold set too low by a tool.
How to detect / prove
sensors / cat /sys/class/nvme/nvme0/hwmon*/temp1_alarm; nvme smart-log (temperature, warning_temp_time); correlate latency spikes with temperature.
Linux v7.2 source
hwmon.c: case hwmon_temp_alarm: *val = !!(log->critical_warning & NVME_SMART_CRIT_TEMPERATURE); hwmon reads LID 02h through nvme_get_log().
Test to provoke it
SAFE: lower the over-temperature threshold below the current temperature: nvme set-feature /dev/nvme0 -f 4 -v <kelvin>. QEMU raises the event at once (nvme_set_feature() → nvme_smart_event(n, NVME_SMART_TEMPERATURE)). Restore the default afterwards.
S-74SMART critical warning bit 2 — NVM subsystem reliability degraded ReportedNVMe log / AEN
In a PEX trace
Partly visible AER CQE type 1 / info 00h, or SMART log payload bit 2. The preceding SCT 2 CQEs (0x280/0x281) are visible if they happened during the capture. The internal cause is not.
What happens
The controller decided that reliability is degraded because of significant media-related errors or an internal error that degrades reliability.
How it shows up
critical_warning bit 2; usually media_errors rising; possibly endurance group critical warning summary (byte 6) set.
Spec basis
SMART Critical Warning bit 2; Endurance Group Information log (LID 09h) critical warnings.
Typical causes
Die failure, parity/RAIN rebuild exhausted, DRAM ECC problems, controller-internal faults.
How to detect / prove
nvme smart-log, nvme endurance-log, vendor telemetry; Persistent Event log NVM Subsystem Hardware Error events (05h).
Linux v7.2 source
Uevent only (nvme_aen_uevent()).
Test to provoke it
SAFE in QEMU: smart_critical_warning 4 via QMP.
S-75SMART critical warning bit 3 — media placed in read-only mode ReportedNVMe log / AEN
In a PEX trace
Partly visible Writes start completing with errors (CQE status visible; often Write Fault or a write-protect status, depending on the vendor impl). The bit itself is visible only in the SMART log payload or an AER CQE.
What happens
The drive has put all media into read-only mode to protect existing data, typically at end of life or after a critical internal failure.
How it shows up
critical_warning bit 3; writes fail; reads still work. Linux does not mark the block device read-only from this bit. Each write fails individually and filesystems remount read-only.
Spec basis
SMART Critical Warning bit 3.
Typical causes
Spare exhausted; power-loss capacitor failure (some vendors); firmware panic mode.
How to detect / prove
nvme smart-log; copy the data off immediately with read-only tools.
Linux v7.2 source
No handling beyond the uevent. Read-only state comes only from namespace write protection or NSATTR (core.c, NVME_NS_ATTR_RO).
Test to provoke it
SAFE in QEMU: smart_critical_warning 8 (QEMU sets the bit only; writes keep working, so this tests monitoring, not the write path).
S-76SMART critical warning bit 4 — volatile memory backup device failed ReportedNVMe log / AEN
In a PEX trace
Not visible as a failure: power-loss protection health is internal. Only the bit in a SMART log read or an AER CQE is visible. A host-side effect may follow: drives that lose PLP often enable a volatile write cache or slow down (Flush latency). Check Identify VWC and Get Features FID 06h.
What happens
The backup power (capacitors) that protects the volatile write cache has failed, so acknowledged writes may be lost on power failure.
How it shows up
critical_warning bit 4. Behaviour after that is vendor-specific impl: some go read-only, some switch to write-through.
Spec basis
SMART Critical Warning bit 4; Volatile Write Cache feature (FID 06h).
Typical causes
Capacitor ageing or failure; failed PLP self-test at power-on.
How to detect / prove
nvme smart-log; power-fail test with write verification (fio verify after a power cut) to prove loss of acknowledged data.
Linux v7.2 source
Uevent only. Linux learns cache state from Identify VWC at scan time, not from this bit.
Test to provoke it
SAFE in QEMU: smart_critical_warning 16.
S-77SMART critical warning bit 5 — Persistent Memory Region read-only/unreliable ReportedNVMe log / AEN
In a PEX trace
Partly visible PMR accesses are MWr/MRd to the PMR BAR and are visible, but a failure shows only as the SMART bit (log read) or AER CQE. PMRSTS register reads (MRd + CplD) show its status if the host reads it.
What happens
The PMR became read-only or unreliable.
How it shows up
critical_warning bit 5 (libnvme NVME_SMART_CRIT_PMR_RO; not in Linux nvme.h). QEMU only accepts this bit when CAP.PMRS is set.
Spec basis
SMART Critical Warning bit 5; PMRCAP/PMRCTL/PMRSTS registers.
Typical causes
Backing NVRAM failure.
How to detect / prove
nvme smart-log, nvme show-regs -H PMRSTS.
Linux v7.2 source
No PMR consumer in the NVMe host driver; uevent only.
Test to provoke it
SAFE in QEMU with pmrdev=: smart_critical_warning 32.

8.4 Asynchronous Event cards

S-78AEN Error: Invalid Doorbell Register (00h) / Invalid Doorbell Write Value (01h) ReportedNVMe AEN / registers
In a PEX trace
Visible This is one of the best PEX cases: the bad doorbell MWr (host→device to BAR0 + 1000h + …) with its value is in the trace, and so is the AER CQE (type 0, info 00h/01h, LID 01h) that follows. Check that the written value is less than the queue size and that the doorbell belongs to an existing queue.
What happens
The host wrote a doorbell for a queue that does not exist (00h), or wrote a value that is invalid, e.g. tail ≥ queue size, or a CQ head that moves past entries not yet posted (01h).
How it shows up
Error-type AEN; the Error Information log has an entry. The controller may ignore the write. The affected queue can stall, which the host then sees as I/O timeouts.
Spec basis
Doorbell registers (SQyTDBL, CQyHDBL; stride from CAP.DSTRD); Asynchronous Event Information – Error Status.
Typical causes
Driver bug in a new host or user-space driver; doorbell offsets computed with the wrong DSTRD; shadow doorbell (Doorbell Buffer Config) misuse. QEMU: nvme_process_db() enqueues NVME_AER_INFO_ERR_INVALID_DB_REGISTER for an invalid qid and NVME_AER_INFO_ERR_INVALID_DB_VALUE for new_tail >= sq->size / new_head >= cq->size (only if an AER is outstanding).
How to detect / prove
Analyzer filter on MWr to BAR0+1000h…; decode qid = (offset−1000h)/(4<<DSTRD)/2 and SQ vs CQ from parity; compare the value with the queue size from the Create command.
Linux v7.2 source
Not handled specially (uevent). The Linux PCIe driver computes doorbells from dev->db_stride in pci.c.
Test to provoke it
EXPERT: user-space driver writing a tail value of queue size. Or in QEMU, write to an unconfigured doorbell through /sys/bus/pci/devices/<bdf>/resource0 (CAUTION: only with the kernel driver unbound).
S-79AEN Error: Diagnostic Failure (02h), Persistent Internal Error (03h), Transient Internal Error (04h), Firmware Image Load Error (05h) ReportedNVMe AEN / device
In a PEX trace
Partly visible The AER CQE on the admin CQ (DW0 type 0 with info 02h–05h) is visible. For 03h under Linux, the reset that follows within milliseconds is visible: MWr CC.EN=0 to BAR0+14h, CSTS polling MRds, re-initialisation. The internal failure is not visible.
What happens
02h: a diagnostic (e.g. power-on self-test) failed. 03h: a persistent internal error, so the controller needs a reset (or is broken). 04h: an internal error that the controller recovered from. 05h: the firmware image could not be loaded at activation (the drive fell back to another image).
How it shows up
Linux, 03h: dmesg "resetting controller due to persistent internal error" and a full controller reset; I/O in flight completes with 0x371 and is retried. Other subtypes: uevent only. 05h: firmware_rev after reset is not the version you committed.
Spec basis
Asynchronous Event Information – Error Status (libnvme NVME_AER_ERROR_*).
Typical causes
Firmware asserts; failed internal memory test; corrupt firmware slot.
How to detect / prove
nvme error-log, nvme persistent-event-log (NVM Subsystem Hardware Error and Firmware Commit events), nvme fw-log; capture nvme telemetry-log right after (before a reset clears volatile state).
Linux v7.2 source
core.c:nvme_complete_async_event(): if (aer_subtype == NVME_AER_ERROR_PERSIST_INT_ERR) { nvme_handle_aer_persistent_error(ctrl); return; } (no AER resubmit; the reset re-arms it).
Test to provoke it
Not provokable from a standard host; vendor injection only.
S-80AEN Notice: Namespace Attribute Changed (00h) ReportedNVMe AEN
In a PEX trace
Visible AER CQE DW0 = type 2 / info 00h / LID 04h, then Linux's Get Log Page LID 04h (Changed Namespace List, data MWr) and a burst of Identify commands (CNS 00h/05h/…) as it rescans.
What happens
A namespace was attached, detached, resized, formatted or changed in an Identify-visible way (by this host, another host, or the device itself).
How it shows up
Linux rescans: block devices appear or disappear or change capacity; dmesg capacity-change messages. If identifiers changed: "identifiers changed for nsid N" and the namespace is removed.
Spec basis
Notice 00h; Changed Namespace List log (up to 1024 NSIDs; FFFFFFFFh in the first entry means "more than 1024 changed"); OAES bit 8.
Typical causes
Namespace management from another host; thin-provisioned growth; vendor tools reformatting.
How to detect / prove
udev events; nvme list before/after; nvme_async_event tracepoint.
Linux v7.2 source
core.c:nvme_handle_aen_notice() → set_bit(NVME_AER_NOTICE_NS_CHANGED, &ctrl->events), nvme_queue_scan(); nvme_scan_work() → nvme_clear_changed_ns_log(); nvme_validate_ns().
Test to provoke it
CAUTION: nvme detach-ns / attach-ns on a test namespace (QEMU nvme-subsys).
S-81AEN Notice: Firmware Activation Starting (01h) and CSTS.PP ReportedNVMe AEN / registers
In a PEX trace
Visible AER CQE type 2 / info 01h / LID 03h, then a run of host MRds of CSTS (BAR0+1Ch) every ~100 ms whose CplD has PP (bit 5) set, then no I/O SQ doorbells (queues quiesced) until PP clears, then Get Log Page LID 03h. The gap length versus MTFA is directly measurable.
What happens
The controller begins activating new firmware without a reset (Firmware Commit CA=3). It sets CSTS.PP (Processing Paused) and stops processing commands until activation finishes.
How it shows up
Linux: controller state goes to RESETTING (to block recovery actions), I/O queues are quiesced, CSTS.PP is polled every 100 ms until clear or until MTFA×100 ms (or admin_timeout if MTFA=0). On timeout: "Fw activation timeout, reset controller". Afterwards it reads the FW Slot log to update firmware_rev.
Spec basis
Notice 01h; CSTS.PP; Identify MTFA; OAES bit 9.
Typical causes
Planned online firmware update. Trouble comes when activation takes longer than MTFA (I/O latency spike or a reset) or the drive never clears PP.
How to detect / prove
dmesg; fio latency log during the update; PEX gap measurement.
Linux v7.2 source
core.c:nvme_handle_aen_notice() (NVME_AER_NOTICE_FW_ACT_STARTING), nvme_fw_act_work(), nvme_ctrl_pp_status(), nvme_get_fw_slot_info().
Test to provoke it
CAUTION: nvme fw-download + nvme fw-commit -a 3 with a vendor-approved image during a fio run; measure the I/O pause.
S-82AEN Notice: Telemetry Log Changed (02h) — controller-initiated telemetry available ReportedNVMe AEN / log
In a PEX trace
Partly visible AER CQE type 2 / info 02h / LID 08h is visible. The telemetry contents are vendor-encoded and visible as raw payload only if read (Get Log Page LID 08h, possibly many MiB of data MWrs).
What happens
The controller captured an internal snapshot (Controller-Initiated Telemetry), usually because it hit an internal error worth debugging. Header byte ctrlavail = 1 and ctrldgn (generation number) increments (libnvme struct nvme_telemetry_log).
How it shows up
Linux: dev_warn(ctrl->device, "async event result %08x\n", result) (default case of nvme_handle_aen_notice()). This is often the only sign of an internal firmware problem.
Spec basis
Telemetry Host-Initiated (07h) and Controller-Initiated (08h) logs; data areas 1–3 (4 with extended); reason identifier.
Typical causes
Firmware assertion recovered internally; vendor-defined triggers.
How to detect / prove
Save it for the vendor: nvme telemetry-log /dev/nvme0 --output-file=tele.bin (check your nvme-cli version for the controller-initiated option). Compare ctrldgn across time.
Linux v7.2 source
core.c:nvme_handle_aen_notice() default branch.
Test to provoke it
Host-initiated variant only: Get Log Page LID 07h with LSP Create (libnvme NVME_LOG_TELEM_HOST_LSP_CREATE) — SAFE.
S-83AEN Notice: Asymmetric Namespace Access Change (03h) ReportedNVMe AEN / multipath
In a PEX trace
Visible on NVMe/PCIe dual-port: AER CQE type 2 / info 03h / LID 0Ch, then Get Log Page LID 0Ch with group descriptors in the data MWr. Note that each port is a different link, so you need both links probed to follow the failover.
What happens
The ANA state of one or more ANA groups changed on this controller.
How it shows up
Linux (CONFIG_NVME_MULTIPATH): ana_work re-reads the ANA log and updates ana_state per path; I/O policy re-selects paths.
Spec basis
Notice 03h; ANA log; OAES bit 11; ANATT.
Typical causes
Array failover/failback, maintenance, path loss.
How to detect / prove
nvme ana-log; /sys/block/nvme*c*n*/ana_state; see the synthetic trace in Chapter 6.
Linux v7.2 source
core.c:nvme_handle_aen_notice() → queue_work(nvme_wq, &ctrl->ana_work); multipath.c:nvme_update_ana_state(), nvme_anatt_timeout().
Test to provoke it
SAFE: nvmet configfs ANA state change.
S-84AEN Notices Linux does not act on: Predictable Latency (04h), LBA Status Information Alert (05h), Endurance Group Event (06h); Discovery Log Change (F0h) ReportedNVMe AEN
In a PEX trace
Visible AER CQE type 2 with info 04h/05h/06h. Since Linux does not read the indicated log, the event type stays masked and no later events of that kind show up on the wire. Absence of later AENs is therefore not evidence of health.
What happens
04h: Predictable Latency per-NVM-set event (deterministic window violated). 05h: the controller found LBAs that are or may become unrecoverable (LBA Status Information log, LID 0Eh). This is a proactive media warning. 06h: an endurance group crossed a threshold. F0h: fabrics discovery log changed.
How it shows up
Linux: "async event result %08x" warning for 04h–06h; F0h → uevent for nvme-cli's autoconnect rules. Linux does not enable 04h–06h in FID 0Bh, so they arrive only if the controller has them enabled by default or user space enables them.
Spec basis
Notice event info values (libnvme NVME_AER_NOTICE_*); LBA Status Information log; Predictable Latency Event Aggregate log; Endurance Group Event Aggregate log.
Typical causes
05h: background media scan found weak blocks. 04h: garbage collection breaking the deterministic window.
How to detect / prove
nvme get-log -i 0x0e for LBA status, then rewrite or relocate the listed LBAs; nvme get-log -i 0x0b (Predictable Latency aggregate).
Linux v7.2 source
core.c:nvme_handle_aen_notice() default case; NVME_AEN_SUPPORTED mask.
Test to provoke it
Vendor-specific; not provokable from the host on most drives.
S-85AEN I/O Command Set specific: Reservation Log Page Available (00h), Sanitize Completed (01h), Sanitize Completed With Unexpected Deallocation (02h) ReportedNVMe AEN
In a PEX trace
Visible AER CQE DW0 type 6 with info 00h/01h/02h; the log page (80h or 81h) only if read.
What happens
00h: a reservation notification is queued (registration preempted, reservation released or preempted). 01h: a sanitize finished. 02h: a sanitize finished but the media was deallocated in a way the host did not request (e.g. No-Deallocate After Sanitize could not be honoured) verify exact semantics in spec.
How it shows up
Linux: uevent NVME_AEN=... only.
Spec basis
libnvme NVME_AER_CSS_NVM_*; Reservation Notification log (80h); Sanitize Status log (81h).
Typical causes
Cluster fencing (00h); decommission workflows (01h/02h).
How to detect / prove
nvme get-log -i 0x80, nvme sanitize-log.
Linux v7.2 source
core.c:nvme_complete_async_event() (NVME_AER_CSS → ctrl->aen_result).
Test to provoke it
CAUTION: reservation preempt from a second controller; DESTRUCTIVE: sanitize a scratch drive.

8.5 Persistent Event, Telemetry, Self-test, Sanitize and Firmware logs

S-86Persistent Event log (LID 0Dh) entries that indicate failure ReportedNVMe log
In a PEX trace
Partly visible Only when read during the capture: Get Log Page LID 0Dh with LSP establishing a reporting context, then data MWrs with event headers. Events from before the capture are visible this way, which makes the log a time machine for things the trace missed.
What happens
The controller keeps a timestamped, power-cycle-persistent history: SMART/Health snapshot (01h), Firmware Commit (02h), Timestamp Change (03h), Power-on or Reset (04h), NVM Subsystem Hardware Error (05h), Change Namespace (06h), Format Start/Completion (07h/08h), Sanitize Start/Completion (09h/0Ah), Set Feature (0Bh), Telemetry Log Create (0Ch), Thermal Excursion (0Dh), Sanitize Media Verification (0Eh), vendor (DEh), TCG (DFh) (libnvme NVME_PEL_*).
How it shows up
Nothing is pushed. You must read it. Header has total events (TNEV), log length (TLL), timestamp, power-on hours, power cycle count, reporting context (RCI).
Spec basis
Persistent Event log; LSP actions read/establish/release context; Identify PELS (log size).
Typical causes
Read it after any unexplained reset, power event, firmware change or data-loss report. "Power-on or Reset" events with unexpected reasons and "NVM Subsystem Hardware Error" events are the highest-value entries.
How to detect / prove
nvme persistent-event-log /dev/nvme0 (establish context, read, release; see nvme-cli help for the action option). Correlate timestamps with host logs. Set the Timestamp feature (FID 0Eh) so the drive's clock matches.
Linux v7.2 source
Not read by the driver. Linux sets the Timestamp feature at init (core.c:nvme_configure_timestamp()), which makes PEL timestamps meaningful.
Test to provoke it
SAFE: nvme reset /dev/nvme0, then read the log and find the new Power-on or Reset event.
S-87Telemetry logs (LID 07h host-initiated, 08h controller-initiated) — failure evidence for the vendor ReportedNVMe log
In a PEX trace
Partly visible The transfer is visible (large Get Log Page with offsets; many data MWrs). The content is vendor-opaque. Note that collecting telemetry during a capture inflates the trace and may disturb timing.
What happens
Host-initiated: the host asks the controller to capture internal state now (LSP Create). Controller-initiated: the controller saved state itself (see S-82).
How it shows up
Header fields: lpi, IEEE OUI, last block of data areas 1–4 (dalb1–dalb4), ctrlavail, ctrldgn, reason identifier (128 bytes).
Spec basis
Telemetry logs; LPA bit for telemetry; Identify MDTS limits transfer chunking.
Typical causes
Collect after any firmware-suspected failure, before resetting or power-cycling (volatile data may be lost).
How to detect / prove
nvme telemetry-log /dev/nvme0 --output-file=t.bin; send it to the vendor together with the trace and time of failure.
Linux v7.2 source
Not used by the driver (NVME_LOG_TELEMETRY_HOST/_CTRL are only defined).
Test to provoke it
SAFE: host-initiated capture with nvme-cli.
S-88Device Self-test log (LID 06h) failure results ReportedNVMe log
In a PEX trace
Partly visible The Device Self-test command (14h) and its immediate CQE are visible. The test runs internally for minutes. The result is visible only when LID 06h is read: a 564-byte payload, 20 result entries of 28 bytes.
What happens
A short or extended self-test finished with a failure. Result codes (low nibble of DSTS, libnvme NVME_ST_RESULT_*): 0 no error, 1 aborted by Device Self-test command, 2 aborted by Controller Level Reset, 3 aborted by namespace removal, 4 aborted by Format NVM, 5 fatal or unknown test error, 6 completed with a failed segment (segment unknown), 7 completed with failed segment(s), first failing segment in SEG, 8 aborted for unknown reason, 9 aborted by sanitize, F entry unused.
How it shows up
Entry fields: dsts (result + test code), seg, vdi (which of NSID/FLBA/SCT/SC are valid), poh, nsid, flba (failing LBA), sct, sc.
Spec basis
Device Self-test command and log; EDSTT; DSTO (one test at a time per subsystem or per controller).
Typical causes
Results 5–7 are hardware/media failures; 2/3/4/8/9 mean the test was interrupted and is not a health verdict.
How to detect / prove
nvme device-self-test /dev/nvme0 -s 2, wait EDSTT minutes, nvme self-test-log /dev/nvme0; read the FLBA it reports with nvme read.
Linux v7.2 source
Not used by the driver.
Test to provoke it
SAFE: start an extended test and abort it (-s 0xf) → result 1. Run a test then reset → result 2.
S-89Sanitize Status log (LID 81h): sanitize completed with failure / interrupted ReportedNVMe log
In a PEX trace
Partly visible The Sanitize SQE (84h) and its fast CQE (the operation runs in the background) are visible, and so are later 0x1D/0x1C CQEs on I/O. SSTAT/SPROG are visible only as payload of a LID 81h read. Whether the media was really erased is never visible (prove it by reading back).
What happens
SSTAT bits 2:0 (libnvme NVME_SANITIZE_SSTAT_STATUS_*): 0 never sanitized, 1 completed successfully, 2 in progress, 3 completed with failure, 4 completed successfully with No-Deallocate (ND). Bits 7:3 completed overwrite passes, bit 8 Global Data Erased, bit 9 media verification cancelled. SPROG = progress ×65536.
How it shows up
SSTAT=3 → commands fail with Sanitize Failed (0x1C, S-18) until recovery.
Spec basis
Sanitize command and Sanitize Status log (sprog, sstat, scdw10, eto, etbe, etce, etond, etbend, etcend, etpvds, ssi).
Typical causes
Power interruption with an implementation that fails rather than resumes; die failures during block erase.
How to detect / prove
nvme sanitize-log /dev/nvme0; after "success", read random LBAs and verify they contain the expected pattern (zeros, the overwrite pattern, or deallocated data per DLFEAT). A sanitize can report success without erasing everything, and only read-back proves it.
Linux v7.2 source
Not used by the driver.
Test to provoke it
DESTRUCTIVE / EXPERT: sanitize a sacrificial drive, cut power mid-way, read the log after power-up.
S-90Controller Fatal Status — CSTS.CFS = 1 ReportedNVMe register
In a PEX trace
Partly visible CFS is visible only in the CplD payload of a host MRd to BAR0+1Ch (bit 1 set). The controller sends nothing when it enters fatal state. What you see first is silence: SQ doorbells with no SQE fetch MRds and no CQEs. Then, 30 s later (io_timeout), Linux's CSTS read and the reset sequence. A CSTS read returning FFFFFFFFh means the device did not answer (the root complex synthesised all-ones for a UR/timeout), which is a link/device-gone case, not CFS.
What happens
The controller hit a fatal error it cannot report through a CQE and stopped processing. Only a controller reset (CC.EN 1→0→1) or a deeper reset recovers it.
How it shows up
Linux does not poll CSTS. It finds CFS when a command times out: nvme_timeout() reads CSTS, nvme_should_reset() returns true for CFS, and nvme_warn_reset() prints "controller is down; will reset: CSTS=0x%x, PCI_STATUS=0x%hx". If CSTS reads all-ones it adds "Does your device have a faulty power saving mode enabled?" and suggests nvme_core.default_ps_max_latency_us=0 pcie_aspm=off pcie_port_pm=off. All in-flight commands are cancelled (0x371) and retried after the reset.
Spec basis
CSTS.CFS (bit 1); controller reset (CC.EN); CAP.TO for ready timeouts.
Typical causes
Firmware crash/watchdog, internal hardware fault, power-state transition bugs (APST), thermal shutdown.
How to detect / prove
dmesg line above (CSTS value: 0x3 = RDY|CFS); PEX shows the stall start time precisely. Afterwards read nvme error-log, persistent-event-log and telemetry. Check /sys/class/nvme/nvme0/state transitions.
Linux v7.2 source
pci.c:nvme_timeout(), nvme_should_reset(), nvme_warn_reset(), nvme_pci_ctrl_is_dead() ((csts & NVME_CSTS_CFS) || !(csts & NVME_CSTS_RDY)).
Test to provoke it
Not host-provokable on real drives without vendor commands. Simulate the host side with fault injection plus io_timeout, or with an exerciser that answers CSTS reads with CFS set.
S-91NVM Subsystem Reset Occurred — CSTS.NSSRO = 1 ReportedNVMe register
In a PEX trace
Partly visible The NSSR write itself (host MWr of 4E564D65h to BAR0+20h) is visible if it came over this link, and so is the link going through Recovery/re-training afterwards. NSSRO is visible in a CSTS read CplD (bit 4), and its clearing as a host MWr of 1 to CSTS bit 4.
What happens
An NVM subsystem reset happened (host-initiated through NSSR, or by the subsystem itself). All controllers in the subsystem were reset, possibly including other ports or hosts.
How it shows up
Linux: when dev->subsystem is set, NSSRO counts as a reason to reset in nvme_should_reset() ("loss of adapter communication, possibly by a NVMe Subsystem reset"); the driver clears NSSRO during reset.
Spec basis
CAP.NSSRS (NSSR supported); NSSR register (20h); CSTS.NSSRO (write 1 to clear).
Typical causes
Firmware activation needing a subsystem reset (0x110); nvme subsystem-reset; the other host on a dual-port drive resetting the subsystem.
How to detect / prove
dmesg reset messages on both hosts; Persistent Event log Power-on or Reset event.
Linux v7.2 source
pci.c:nvme_should_reset(); NSSRO cleared in pci.c (writel(NVME_CSTS_NSSRO, dev->bar + NVME_REG_CSTS)); nvme_pci_subsystem_reset().
Test to provoke it
CAUTION: nvme subsystem-reset /dev/nvme0 on a drive with CAP.NSSRS=1 (the link drops; some platforms report it as a surprise-down error).
S-92Firmware Commit outcome hidden in the Firmware Slot log (LID 03h): activation pending or reverted ReportedNVMe log / firmware
In a PEX trace
Partly visible The Firmware Image Download chunks (opcode 11h; host buffers fetched by device MRd), the Commit SQE and its CQE status are visible. Which image is actually running after reset is visible only from a LID 03h read (AFI byte) or Identify Controller FR field (bytes 64–71) in a data MWr.
What happens
After a commit the running firmware may not be what you expect: activation pending until the next reset (AFI bits 6:4 ≠ bits 2:0), image rejected at boot and the old slot used (Firmware Image Load Error AEN), or a successful commit reported with a "requires reset" status (S-40).
How it shows up
Linux: "Firmware is activated after next Controller Level Reset" (nvme_get_fw_slot_info()), and /sys/class/nvme/nvme0/firmware_rev keeps the old revision until reset.
Spec basis
Firmware Slot Information log (AFI, FRS1–FRS7); Firmware Commit CA values; Identify FR.
Typical causes
Fleet tools reporting "updated" without resetting; images that fail secure-boot checks and roll back silently.
How to detect / prove
nvme fw-log /dev/nvme0 + nvme id-ctrl | grep '^fr ' after every update and after the reset; Persistent Event log Firmware Commit events (02h) with old/new revision.
Linux v7.2 source
core.c:nvme_get_fw_slot_info() (cur_fw_slot = log->afi & 0x7; next_fw_slot = (log->afi & 0x70) >> 4).
Test to provoke it
CAUTION: commit with CA=2 (activate at next reset) and read the slot log before and after nvme reset.
S-93SMART counters creeping up without a critical warning: media_errors, num_err_log_entries, unsafe_shutdowns, percent_used DegradedNVMe log
In a PEX trace
Not visible as a trend. A capture covers seconds; counters change over days. Two SMART reads inside a capture can be diffed from their payloads. Otherwise use periodic nvme smart-log collection (smartd, Prometheus exporters).
What happens
The drive is still "healthy" (critical_warning = 0) but the counters show trouble: media_errors (unrecovered data-integrity errors), num_err_log_entries (lifetime error log entries), unsafe_shutdowns (power lost without a shutdown notification, so data in a volatile cache may be gone), percent_used (wear estimate, may exceed 100), warning/critical temperature time.
How it shows up
Nothing is pushed. These counters never raise an AEN on their own.
Spec basis
SMART/Health log counters (128-bit fields; Linux struct nvme_smart_log).
Typical causes
Ageing media; host shutting down without CC.SHN (unsafe_shutdowns increasing on every reboot points to a platform or driver shutdown bug); thermal design problems. Field studies (Meza et al., SIGMETRICS 2015; Schroeder et al., FAST 2016) found that uncorrectable errors are common across fleets and that wear alone predicts them poorly, so trend counters per drive instead of trusting a single threshold.
How to detect / prove
Store nvme smart-log -o json daily and alert on deltas; after a clean reboot unsafe_shutdowns must not change (if it does, the shutdown path is broken; check that CC.SHN was written, which is visible in a PEX trace of the shutdown).
Linux v7.2 source
Linux uses the SMART log only for hwmon temperatures (hwmon.c). Shutdown notification is sent from core.c:nvme_disable_ctrl() with shutdown=true (CC.SHN) and polled with shutdown_timeout (default 5 s).
Test to provoke it
CAUTION: hard power-off a test machine and verify unsafe_shutdowns increments by exactly one. A clean poweroff must not increment it.
