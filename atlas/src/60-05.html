PART IX

Using AI (Claude) on a PEX Trace Export

An AI assistant cannot plug into an analyzer, cannot see the wire and cannot look inside an SSD. What it can do is read the text you export from a PEX capture — packet lists, transaction lists, decoded NVMe commands — together with logs and register dumps, apply every rule in this atlas to it, line up timelines, explain status codes, and write the checker scripts that make the conclusions reproducible. This part is a practical workflow: how to export, what to hand over, which prompts work, what the AI may conclude, and the guardrails that keep it honest.

IX.1 What an AI Can and Cannot Conclude from a PEX Export

🧒 Kid analogy

Imagine giving a very fast, very well-read detective a printed list of everything that went through a door: who, when, what they carried. The detective can spot that the same person came in twice without leaving, or that a parcel was delivered before it was ordered. The detective cannot tell you what happened inside the house — nobody wrote that down.

🧩 Where the analogy breaks

A human detective knows when they are guessing. A language model can produce a fluent, confident explanation for something the list does not show. The workflow in this part exists to force every conclusion back to a row in the export.

IX.1.1 Three levels of conclusion

ObservedDirectly in the export, a row or a set of rows"Row 1843: CQE for CID 0x0013 written at 12.004 ms, but the last data MWr for that command is row 1851 at 12.019 ms."Yes — with row citations; you can verify in seconds

💡 Senior insight

The single most valuable thing an AI does with a trace is not "finding the bug". It is finding the first abnormal event among hundreds of thousands of rows, and separating it from the cascade that follows. A human engineer then spends their time on one row instead of a million.

IX.2 Exporting from the Analyzer and Handing It Over

A PEX capture file is a binary, analyzer-specific format. An AI assistant should not be expected to parse it directly; the analyzer software decodes it, and you export the decoded view as text. The menu names and options below are deliberately generic — they vary across tool versions. uncertain Check your analyzer's manual for exact names.

IX.2.1 Which view to export

View (generic name)GranularityBest forWatch out for
Packet / TLP listone row per TLP or DLLP (optionally ordered sets)PCIe rules (V-26 … V-37): sizes, tags, Byte Count, EP/TD/RO bits, Nak/replayLarge; replayed TLPs appear twice; include both directions
Transaction / split-transactionone row per request with its completion(s)latency per read, Unexpected Completions, tag reuse, completion timeoutsHow unmatched completions are shown varies
NVMe command / queue decodeone row per SQE / CQE / doorbell, sometimes per command with bothPart VII queue and command rules (V-01 … V-25), status codes, per-command latencyNeeds the analyzer to know BAR0 and queue bases — usually learned from captured enumeration and queue creation; start the capture early
Link / LTSSM eventstraining, Recovery, power-state transitionsP-07, P-11, link context for Part VPhysical-layer analysis belongs to Part V

IX.2.2 Export settings that matter

  • Timestamps with their unit stated (ns, µs) and absolute or relative origin. Keep the analyzer's timestamp column unmodified.
  • Both directions (upstream and downstream) in one file, time-ordered, with a direction column.
  • Raw fields as well as decoded text: TLP type, length, address, requester ID, tag, attributes (RO, NS, IDO), TD, EP, Byte Count, Lower Address; for NVMe: opcode, CID, NSID, PRP1/PRP2 or SGL, CDW10–15, CQE DW0–DW3.
  • Payload bytes for SQE fetch completions, CQE writes, PRP-list reads and Identify/log-page data (these are where NVMe decoding comes from). Data payloads of bulk I/O can be truncated to save space.
  • Time window: from controller enable (or at least queue creation) to a few seconds after the failure. If the file is too big, export two pieces: the setup phase (enumeration, CAP/CC writes, Identify, Create I/O queues) and a window around the failure.
  • Filters: filtering out DLLPs and ordered sets is fine for NVMe questions; keep them for link questions. Say which filters you applied.

IX.2.3 Evidence checklist — what to hand over

✅ Evidence checklist
  • The export file(s) (CSV/text), with the analyzer tool name and version, the view exported, filters applied, and the timestamp unit.
  • Where the probe sat (root port ↔ SSD, switch downstream port ↔ SSD, …) and the link speed/width.
  • Configuration context: lspci -vvv of the SSD and every port above it (MPS, MRRS, RCB, ASPM, LnkCap/LnkSta, AER capability); nvme id-ctrl (MDTS, SGLS, FUSES, VWC, APSTA, power states); nvme id-ns; CAP/VS if a register dump is available.
  • Host logs for the same period: journalctl -k / dmesg -T, with a note on how host time maps to analyzer time (e.g. "the doorbell at analyzer t=12.000 ms corresponds to the nvme_setup_cmd trace event at 1739.512301 s").
  • Device logs after the event: nvme error-log, nvme smart-log, vendor logs if available.
  • The workload: exact fio job or application, start time, what was expected vs observed.
  • Known-good comparison: the same export from a passing run, if you have one.
  • A statement of what was redacted (serial numbers, host addresses) — so the AI does not "find" artefacts of redaction.
⚠️ Warning

Exports can contain real data payloads (file contents, keys in memory buffers) and system identifiers. Truncate data payloads you do not need, and follow your organisation's rules before uploading anything to any external service.

IX.2.4 Size strategy

A busy Gen5 link produces millions of TLPs per second; a full export will not fit in any conversation. Use this order: (1) give the AI the column header and the first 200 rows so it can write a parser for your format; (2) run that parser (or the checker from 7.6) locally on the whole file; (3) hand back only the findings and a few hundred rows around the first abnormal event. With an agentic tool such as Claude Code, step (2) can be done by the assistant itself on your machine — it reads the file and runs the script, and you see every command before it runs.

IX.3 A Concrete Workflow with Prompt Templates

IX.3.1 Template A — describe the export and get a parser

I captured a PCIe trace with a protocol analyzer (probe between the root port and an
NVMe SSD, Gen4 x4) and exported the <packet | transaction | NVMe command> view to CSV.
Tool and version: <...>. Timestamp unit: <ns>. Filters applied: <none | DLLPs removed>.
Here are the header and the first 200 rows: <paste>.
1. Explain what each column means; say "unknown" if you cannot tell - do not guess.
2. Write a Python 3 script (standard library only) that maps these rows to the event schema
   t_ns,event,q,cid,opc,val,len,prp1,prp2,sqid,sqhd,ph,tlp_len  (events: CFG_Q, SQDB, CQDB,
   SQE, DATA_WR, DATA_RD, CQE, MSIX, TLP).
3. List any rows you could not map and why.

IX.3.2 Template B — find the first abnormal event

Here is my CSV export (or: here are the findings of trace_check.py plus rows N-200..N+200).
Context: lspci -vvv <paste>; nvme id-ctrl <paste>; dmesg for the same period <paste>.
Expected behaviour: <e.g. fio 4k randread QD32 should run 60 s without errors>.
Task: find the FIRST abnormal event.
Rules for your answer:
- Cite every claim with row numbers from the export.
- Label each statement OBSERVED, RULE (name the rule; no spec section numbers), or HYPOTHESIS.
- Separate the root event from its cascade (what follows from it).
- If the export does not contain enough to decide, say exactly which extra evidence you need.

IX.3.3 Template C — explain a status code or async event

Row 5521 is a CQE: DW0=00000000 DW1=00000000 DW2=00010023 DW3=8027A00C (raw hex, little-endian
fields already decoded by the analyzer as shown).
Decode SQHD, SQID, CID, phase, SCT, SC, CRD, More, DNR. Name the status code and say which
command (by CID) it answers. Point to the SQE row for that CID. If the code name depends on the
command set or spec revision, say so.

IX.3.4 Template D — timeline correlation

Analyzer time 0 = <host timestamp> (anchor: the SQ1 doorbell at analyzer 12.000 ms is the
nvme_setup_cmd event at 1739.512301 s in the attached ftrace).
Merge the analyzer findings, the ftrace nvme_setup_cmd/nvme_complete_rq events and dmesg into one
timeline. For each dmesg line (timeouts, resets, AER messages) show the nearest preceding
abnormal trace row and the time difference. Do not assume causality from proximity alone.

IX.3.5 Template E — generate a new checker rule

Add a rule to trace_check.py: "every MRd with Length*4 > MRRS (given on the command line) is a
finding V-27". Write a unit test with two synthetic rows (one legal, one violating) and show the
test output after running it. Do not change existing rules.

IX.3.6 Template F — performance from a trace

From this NVMe command export compute: per-second read bandwidth, average payload size of data
MWr TLPs, mean and p99.9 of (SQE fetch -> CQE) per opcode, average outstanding commands, and the
ratio of MSI-X writes to CQEs. Compare bandwidth with the link ceiling for Gen4 x4 at MPS 256 B
using rate x lanes x 128/130 / 8 x MPS/(MPS+24). Show the arithmetic. Then list which Part VIII
anomalies are consistent with the numbers and which extra evidence would confirm each.

IX.3.7 Worked example (synthetic)

Synthetic exchange — Template B applied to the 7.6 sample
StepContent
InputThe 15 findings printed by trace_check.py in 7.6, rows 2–27 of the sample CSV, and "queue 1 was created with 4 entries; MPS 256 B; MDTS 128 KiB".
Answer, part 1OBSERVED: row 11 is the first abnormal event — SQE CID 0x11, 8 KiB, PRP1 0x10001000, PRP2 0x20000010. RULE: PRP2 is a data pointer here (the remainder after PRP1's page fits one page), so its offset must be zero (V-18). A checking controller would complete it with status 13h; the sample export has no status column, so whether it did is unknown — ask for the CQE status field (DW3) of row 15 before concluding. HYPOTHESIS: data for the second page landed at 0x20000010 and overran into the next page; verify with a read-back into a guarded buffer.
Answer, part 2OBSERVED: row 15 CQE for CID 0x11 precedes the 8 KiB DATA_WR at row 16. RULE: completion before data (V-13); row 16 is the same defect seen as DMA after completion (V-16) — a cascade, not a second bug.
Answer, part 3OBSERVED: row 24 CQE posted into slot 0 while host head is 1 → CQ overflow (V-07b). The PHASE finding on row 24 and CQDB-PAST-TAIL on row 26 follow from it.
Answer, part 4Independent host-side findings: rows 20, 25 (doorbell values ≥ 4), 22 (256 KiB > MDTS), 23 (CID 0x13 reused), 27 (doorbell for non-existent queue 5). Independent device-side: rows 14 (MSI-X without CQE), 17 (512 B TLP > MPS), 19 (CQE with SQID 2 and unknown CID 0x99).
NeedNot in the export: whether the host saw corrupted data (needs application checksums), and whether the device reported any of this in its Error Information log (needs nvme error-log).

Notice the shape of a good answer: every sentence starts from a row, rules are named, the cascade is separated, and the "Need" line lists exactly what the export cannot show.

IX.4 Guardrails: Where AI Help Ends

Language models can produce plausible but wrong root causes. Research on LLM-based log analysis reports exactly this: models invent root causes when evidence is ambiguous, and simply instructing a model to use only the supplied evidence does not reliably prevent it; grounding the model in structured, pre-computed evidence helps. Treat the AI as a fast junior analyst whose every claim must be checked against a row.

RiskWhat it looks likeGuardrail
Invented spec citations"Section 4.2.3.1 requires…"Ask for rule names and field names, not section numbers; verify wording in your copy of the spec
Status-code mix-upsWrong name for a code, or a command-specific code read as genericDecode SCT first; cross-check names against include/linux/nvme.h / drivers/nvme/host/constants.c or the spec
Claims about device internals"The FTL failed to unmap", "the SLC cache filled"Must be labelled HYPOTHESIS with an experiment (read-back, SMART deltas, long-run bandwidth log)
Proximity = causality"The AER at 12.3 ms caused the timeout"Require the mechanism (which rule) and a second occurrence, or a provoked reproduction
Parsing errorsMisread column, wrong endianness, hex vs decimalRun the AI-written parser on a known-good capture first; spot-check 10 rows by hand
Sampling biasLooking only at the rows you pastedRun checks on the full file with a script; paste only windows around findings
Missing stateCapture started mid-stream: "CQE for unknown CID" everywhereTell the AI where the capture started; let the checker learn state and suppress early findings
Destructive suggestions"Run nvme format / sanitize / setpci to test"Only on scratch hardware; an agentic tool must ask before running anything that writes; review every command
📭 What the AI cannot see
  • The wire itself — only what your export contains.
  • Anything on a link the probe was not on, or inside the root complex, switch or SSD.
  • Host memory contents that never crossed the probed link.
  • Whether a command did its job inside the device (deallocate, write to media, firmware activation) — the "completes but does nothing" class needs read-back evidence.
  • Analyzer-specific decode errors — if the analyzer mis-decoded a packet, the AI will faithfully reason about the wrong data.

IX.4.1 Acceptance test for an AI conclusion

✅ Before you put an AI conclusion in a bug report
  • Every observed claim points to row numbers, and you have looked at those rows yourself.
  • The rule is named, and you checked its wording in the spec or in this atlas's card.
  • The finding is reproduced by a script run over the full export, not only by reading pasted rows.
  • The first abnormal event is identified, and the later findings are explained as cascade or as independent.
  • Hypotheses about device internals are labelled and paired with an experiment.
  • Context the AI did not have (probe location, redactions, filters) has been considered.

Quiz

  1. An AI says "the trace proves the drive did not deallocate the last 5 GB". What is wrong with the claim?

    Answer

    The trace can prove only that a DSM command with the deallocate attribute and its range list crossed the link and completed with a given status. Whether the device unmapped those LBAs is device-internal (marked Not visible); proof needs read-back behaviour, Get LBA Status or capacity/utilisation counters.

  2. Why give the AI the setup phase of the capture (enumeration, CAP/CC writes, queue creation) even if the failure happens later?

    Answer

    Many rules are stateful: queue sizes, doorbell stride, BAR addresses, MPS/MRRS and the MSI-X table come from that phase. Without it the AI must guess state, which creates false findings (e.g. unknown CIDs) or missed ones (doorbell range).

  3. What is the minimum you should paste into a conversation for a multi-gigabyte export?

    Answer

    The header and a few hundred rows so the AI can write a parser; then run the parser/checker locally on the full file and paste only the findings and windows around the first abnormal event.

Interview questions

  1. Intermediate How would you use an AI assistant to triage a 2 GB analyzer export of an NVMe timeout?
    Model answerExport the NVMe-command and transaction views to CSV; give the AI the header plus sample rows and the configuration context; have it write a mapper and a rule checker; run them locally on the full file; give back the findings and a window around the first abnormal event; require row-cited, rule-named conclusions; verify the root event by hand and with a reproduction.
  2. Senior What can a PEX trace not tell you about a "successful" command that did nothing?
    Model answerIt shows the command, its data/range list and a success CQE; it cannot show media state. You need functional evidence: read-back, Get LBA Status, utilisation counters, or a device log — and only then can you call it a silent failure.
