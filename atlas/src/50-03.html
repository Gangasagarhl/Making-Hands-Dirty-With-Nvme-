V.3 Uncorrectable AER Errors: Lost, Refused and Malformed Transactions

V.3.1 How to read this chapter

Each uncorrectable bit means that at least one transaction did not complete as intended. In NVMe terms, that transaction can be any of four things:

  • Host → SSD MMIO. Doorbell writes (posted MWr) and register reads (MRd, which needs a completion). A lost doorbell write is silent. A failed register read returns all-ones to the CPU, which Linux treats as "device gone" (CSTS == ~0).
  • SSD → host DMA reads. The controller fetches SQ entries, PRP lists, SGL segments and write data with MRd and waits for CplD. A missing CplD gives a Completion Timeout in the SSD. The NVMe command is then usually aborted by the device or hangs until the host times it out.
  • SSD → host DMA writes. Read data, CQ entries and MSI-X messages are posted MWr, so the SSD never learns whether they arrived. If the root complex or IOMMU refuses one, the error is logged at the root, and the SSD believes it completed the command.
  • Configuration requests at enumeration and recovery time.

The default severities below follow section V.1.8. Always check the actual Severity register.

L-09Undefined (bit 0) set — legacy "Training Error" bit ReportedPCIe Transaction
In a PEX trace
Not visible Nothing on the wire identifies bit 0. You might see an ERR_* Message. To identify the bit, read UESta (CfgRd).
What happens
Bit 0 of Uncorrectable Status was "Training Error" in early PCIe revisions. It is now undefined. A device that sets it is either very old or buggy.
How it shows up
[ 0] Undefined in the AER log (PCI_ERR_UNC_UND).
Spec basis
PCIe Base Specification: Uncorrectable Error Status bit 0 is Undefined in current revisions.
Typical causes
Legacy IP, or firmware that writes the wrong bit.
How to detect / prove
Read UESta with lspci -vvv. Report it to the vendor as a compliance issue.
Linux v7.2 source
aer.c: aer_uncorrectable_error_string[0] = "Undefined".
L-10Data Link Protocol Error (DLP) ReportedPCIe Data Link
In a PEX trace
Visible An Ack or Nak DLLP whose AckNak_Seq_Num refers to a sequence number the transmitter never sent, or one already acknowledged. Then an ERR_FATAL Message (if the link still works) and, after Linux recovery, a link-down followed by retraining (secondary bus reset: Hot Reset TS1s).
What happens
The Data Link Layer received an Ack or Nak whose sequence number does not match any unacknowledged TLP, or another DL-protocol violation. The replay state can no longer be trusted. The default severity is Fatal.
How it shows up
[ 4] DLP, severity=Uncorrectable (Fatal), type=Data Link Layer. Linux v7.2 calls pcie_do_recovery(..., pci_channel_io_frozen, aer_root_reset), which brings the link down and up again. The NVMe driver logs frozen state error detected, reset controller then restart after slot reset, and in-flight I/O is retried or failed.
Spec basis
PCIe Base Specification: Data Link Protocol Error, AckNak_Seq_Num checks.
Typical causes
Data Link Layer bugs in the port or SSD IP. Retimer bugs. Interaction with link power-management entry and exit.
How to detect / prove
The AER log and the counter aer_dev_fatal DLP. An analyzer capture with a trigger on "Ack/Nak sequence out of range".
Linux v7.2 source
aer.c: AER_DATA_LINK_LAYER_ERROR_MASK (DLP); err.c: pcie_do_recovery; nvme/host/pci.c: nvme_error_detected, nvme_slot_reset, nvme_error_resume.
Test to provoke it
EXPERT: an exerciser or interposer that injects bad AckNak_Seq_Num values. Software injection: aer-inject with CONFIG_PCIEAER_INJECT exercises the recovery path only, not the hardware.
L-11Surprise Down Error (SDES) ReportedPCIe Data Link
In a PEX trace
Partly visible Visible only if the probe sits on the SSD's link: traffic stops, electrical idle with no PM_Enter DLLPs and no Hot Reset or Disabled TS first, then possibly Detect and Polling. The SDES bit is set in the Downstream Port's registers. The port's ERR_FATAL travels on the upstream link, which a probe on the SSD link cannot see.
What happens
A Downstream Port (Root Port or switch DSP) that supports Surprise Down reporting sees its link go from DL_Active to DL_Inactive without being told to. To the host, the SSD has vanished. Every MMIO read returns all-ones, posted writes are dropped, and DMA in flight is lost.
How it shows up
Uncorrectable bit 5 on the Downstream Port, not on the SSD. Default severity Fatal. Linux prints [ 5] SDES as "Transaction Layer" (see 20.4). If DPC is enabled and the port is a hot-plug bridge, dpc_is_surprise_removal() treats it as an expected removal and quietly cleans up (dpc_handle_surprise_removal()). Otherwise DPC or AER recovery runs. The NVMe driver then sees CSTS == ~0 on its next register read or in nvme_timeout(), and logs controller is down; will reset: CSTS=0xffffffff, PCI_STATUS=0xffff or PCI_STATUS read failed, followed by the hint lines about power saving (C-01).
Spec basis
PCIe Base Specification: Surprise Down Error, Data Link Layer Link Active reporting, Hot-Plug surprise.
Typical causes
Physical removal. Power loss to the slot or a brown-out. An SSD firmware crash or watchdog reset that drops the link. An ASPM L1 or L1-substate exit failure (see L-37). Thermal shutdown. A loose M.2 or U.2 connector.
How to detect / prove
On the port: lspci -vvv -s <port> shows UESta: SDES+ and LnkSta DLActive-. On the SSD, config reads return ff. Afterwards, check the drive's nvme smart-log "unsafe shutdowns" counter: if it went up by one, the drive lost power or reset without a shutdown notification.
Linux v7.2 source
drivers/pci/pcie/dpc.c: dpc_is_surprise_removal, dpc_handle_surprise_removal, pci_clear_surpdn_errors; nvme/host/pci.c: nvme_should_reset, nvme_warn_reset, nvme_timeout (checks pci_dev_is_disconnected), nvme_remove (checks pci_device_is_present).
Test to provoke it
CAUTION: surprise-remove a hot-plug-capable U.2/E3.S drive in a hot-plug bay under I/O. EXPERT: cut slot power with a controllable riser or power interposer. Never do this on a non-hot-plug M.2 slot.
L-12Poisoned TLP received ReportedPCIe Transaction
In a PEX trace
Visible A TLP with the EP (poisoned) bit set: usually a CplD toward the SSD carrying write data, or an MWr from the SSD carrying read data. An ERR_NONFATAL Message from the receiver follows. The CQE that follows for the affected command shows whether the controller failed it.
What happens
A TLP arrives with the EP (Error Poisoned) bit set. Its data payload is known to be bad. Most often the host memory controller found an uncorrectable ECC error while serving the SSD's DMA read of write data, and returned the CplD poisoned. The opposite case is the SSD sending poisoned read data because of an internal uncorrectable error.
How it shows up
Uncorrectable bit 12 at the receiver, default Non-fatal, with the TLP header logged. Linux prints [12] TLP and a TLP Header: line. Recovery runs with pci_channel_io_normal, and nvme_error_detected() returns CAN_RECOVER (no reset). What happens to the NVMe command is up to the controller. A well-behaved SSD fails the write with a data-transfer or internal-error status and does not commit poisoned data impl. A poor one may write it. When the host receives poisoned read data, platform RAS policy decides the outcome (machine check, data dropped, or poison propagated in memory) impl.
Spec basis
PCIe Base Specification: Data Poisoning, EP bit, Poisoned TLP Received Status. NVMe Base Specification: generic status codes such as Data Transfer Error and Internal Error are what a controller can return. Check which one your device uses.
Typical causes
Host DRAM uncorrectable errors. Errors in the SSD's internal SRAM or DRAM on the read path. Switch internal parity errors (some switches poison rather than drop).
How to detect / prove
The AER log with the header (decode it: a CplD toward the SSD means host memory; an MWr toward the host means SSD data). Correlate with EDAC or MCE logs (ras-mc-ctl --errors, journalctl -k | grep -i mce). Read back the affected LBA range and check it.
Linux v7.2 source
aer.c: AER_LOG_TLP_MASKS includes PCI_ERR_UNC_POISON_TLP; pci_aer_handle_error → pcie_do_recovery(..., pci_channel_io_normal, ...); dpc.c reports whether DPC can trigger on poisoned TLPs ("PoisonedTLP" in the capability line).
Test to provoke it
EXPERT: an exerciser that sends CplD with EP=1 to the SSD's MRd, or an analyzer with injection. On servers, ACPI EINJ memory error injection into a buffer the SSD then DMA-reads (CAUTION: may cause machine checks).
L-13Flow Control Protocol Error (FCP) ReportedPCIe Transaction
In a PEX trace
Visible InitFC1/InitFC2 or UpdateFC DLLPs with illegal credit values, or credit counters that jump beyond the allowed range. Then an ERR_FATAL and a link reset.
What happens
The flow-control credit protocol was violated, for example InitFC advertising illegal values or credits that overflow the counter field. Credit accounting is corrupt. The default severity is Fatal, and the link is reset.
How it shows up
[13] FCP, Fatal, frozen-channel recovery, NVMe controller reset (messages as in L-10).
Spec basis
PCIe Base Specification: Flow Control, Flow Control Protocol Error.
Typical causes
Port IP bugs. Very rare in shipping products. More likely on FPGA-based NVMe prototypes.
How to detect / prove
Analyzer capture of InitFC and UpdateFC DLLPs around link-up or the event.
Linux v7.2 source
aer.c: string "FCP".
Test to provoke it
EXPERT: an exerciser that injects bad UpdateFC.
L-14Completion Timeout — a read request was never answered Timer onlyPCIe Transaction
In a PEX trace
Partly visible Visible only as an absence. The analyzer shows an MRd (from the SSD for SQE, PRP or data fetch, or from the host to a register) with a given tag and no CplD with that tag within the timeout. The analyzer's 'outstanding request' or 'split transaction' view makes this easy to spot. Next comes an ERR_NONFATAL from the requester, and possibly a late CplD (L-16). If the request was dropped on another link (inside the root complex or IOMMU), the trace cannot show why.
What happens
A requester sent a non-posted request (MRd, CfgRd, ...) and no completion arrived within its Completion Timeout range. In NVMe there are two cases. (a) The SSD's DMA read of an SQE, PRP or SGL list, or write data is never answered by the host: an IOMMU silently dropping it, a root complex deadlock, or a switch problem. The SSD logs CmpltTO and usually ends the command with an error status, or hangs. (b) The host CPU's MMIO read of an SSD register is not answered because the controller's PCIe front end is hung. The root port logs CmpltTO, and the CPU receives all-ones (or, on some platforms, a machine check impl).
How it shows up
Uncorrectable bit 14 on the requester, default Non-fatal, agent "Requester ID". A header is logged only if the device advertises PCI_ERR_CAP_COMP_TIME_LOG. Downstream NVMe effects: case (a) gives a CQE error or an NVMe I/O timeout (I/O tag N (cid) opcode 0x.. (...) QID n timeout, aborting ...). Case (b) gives CSTS=0xffffffff → controller is down; will reset.
Spec basis
PCIe Base Specification: Completion Timeout mechanism, Device Control 2 "Completion Timeout Value" and "Completion Timeout Disable", Device Capabilities 2 "Completion Timeout Ranges Supported". The timeout value is configurable. A 50 µs–50 ms default range is commonly cited (verify in spec).
Typical causes
IOMMU faults where the platform drops the request (see L-36). DPC or containment upstream. Host memory power states that stall. P2P targets that never answer. A hung SSD front end.
How to detect / prove
See which device logged it: the SSD (case a) or the Root Port (case b). lspci -vvv DevCtl2 shows "Completion Timeout: 50us to 50ms" or similar, and whether it is disabled. Correlate with IOMMU fault logs and the NVMe timeout messages.
Linux v7.2 source
aer.c: AER_AGENT_REQUESTER_MASK (CmpltTO, UR), tlp_header_logged; nvme/host/pci.c: nvme_timeout, nvme_warn_reset.
Test to provoke it
EXPERT: an exerciser acting as host memory that withholds CplD for chosen tags. CAUTION: shorten the SSD's Completion Timeout Value through Device Control 2 with setpci on a test system to make marginal latency visible.
L-15Completer Abort (CA) ReportedPCIe Transaction
In a PEX trace
Visible A Cpl (no data) with Completion Status = CA (100b), matching the tag of a preceding request. The completer then sends an ERR_NONFATAL, or ERR_COR if advisory.
What happens
The completer understood the request but refused it because of an internal rule: an access violation, an unsupported access size to a register, or a device in a state where it cannot serve it. It returns a completion with status CA and logs bit 15. The requester sees an "unsuccessful completion".
How it shows up
[15] CmpltAbrt, agent "Completer ID", header logged, default Non-fatal. If the SSD aborts a host MMIO read, the CPU usually sees all-ones data. If the root complex aborts an SSD DMA read, the SSD's command fails.
Spec basis
PCIe Base Specification: Completion Status CA, Completer Abort Status.
Typical causes
Host side: MMIO accesses that cross register boundaries or use unsupported sizes (for example, 64-bit reads of registers some controllers accept only as 32-bit; Linux uses lo_hi_readq for CAP for this reason). Root complex: some platforms use CA for IOMMU-blocked requests impl.
How to detect / prove
Decode the logged header: address and requester. If the address is inside the SSD's BAR0, look at the access size and offset.
Linux v7.2 source
aer.c: AER_AGENT_COMPLETER_MASK; nvme/host/pci.c: nvme_pci_reg_read64 uses lo_hi_readq.
Test to provoke it
CAUTION: issue unusual-size MMIO reads to reserved BAR offsets from a test tool, on a disposable system only.
L-16Unexpected Completion — completion for a request nobody is waiting for ReportedPCIe Transaction
In a PEX trace
Visible A CplD or Cpl whose Requester ID and Tag do not match any outstanding request on the link. Typically it arrives after the analyzer already shows that request as timed out. An ERR_NONFATAL or ERR_COR follows.
What happens
A completion arrives whose Requester ID and Tag do not match any outstanding request. The usual case is a completion that arrives after the requester already gave up (Completion Timeout). Another is a completion routed to the wrong function. The receiver drops it.
How it shows up
[16] UnxCmplt, header logged, default Non-fatal. Often seen right after an L-14 on the same device. Can be handled as advisory (L-06).
Spec basis
PCIe Base Specification: Unexpected Completion Status, completion matching rules.
Typical causes
A late completion from slow host memory or a switch. Tag reuse bugs, especially with 10-bit tags when one side does not support them properly. A completer returning the wrong Requester ID (for example a function-alias DMA bug; see the Marvell quirk in Chapter VI.3).
How to detect / prove
Decode the header's Tag and Requester ID. Check whether 10-Bit Tag Requester Enable is set (lspci -vvv DevCtl2 "10BitTagReq") and whether every hop supports it.
Linux v7.2 source
aer.c: string "UnxCmplt"; probe.c "enabling Extended Tags" and "disabling Extended Tags" messages.
Test to provoke it
EXPERT: an exerciser that delays a completion past the SSD's completion timeout.
L-17Receiver Overflow (RxOF) ReportedPCIe Transaction
In a PEX trace
Visible Compare the credits advertised in UpdateFC DLLPs with the headers and data sent. The analyzer's flow-control tracking flags the TLP that overran the credit limit. ERR_FATAL follows.
What happens
The receiver got more TLPs or data than the credits it advertised, so its buffer overflowed. Data is lost and credit state is broken. Default Fatal.
How it shows up
[17] RxOF, Fatal, link reset, NVMe controller reset.
Spec basis
PCIe Base Specification: Receiver Overflow, flow-control rules (optional checking).
Typical causes
Transmitter credit-accounting bugs, often after a link Recovery or power-state transition.
How to detect / prove
Analyzer: compare the credits advertised with the TLPs sent.
Linux v7.2 source
aer.c: string "RxOF".
Test to provoke it
EXPERT: an exerciser that ignores credits.
L-18Malformed TLP ReportedPCIe Transaction
In a PEX trace
Visible The analyzer decodes and flags the offending TLP: a payload longer than the receiver's MPS (Length field × 4 bytes), a request crossing a 4 KB boundary, or a Length/payload mismatch. The receiver's MPS comes from a CfgWr to Device Control earlier in the capture, or from your notes. ERR_FATAL follows.
What happens
A TLP breaks format rules. Examples: payload longer than the receiver's Max_Payload_Size, Length field not matching the actual payload, a request crossing a 4 KB boundary, illegal byte enables, an undefined Type, or TC/VC mapping violations. Default Fatal.
How it shows up
[18] MalfTLP with the header logged, Fatal, frozen recovery, NVMe reset. If it repeats at every large transfer, Linux keeps resetting (a reset loop, C-06).
Spec basis
PCIe Base Specification: TLP formation rules, Malformed TLP, Max_Payload_Size rules.
Typical causes
MPS mismatch is the classic case: the SSD is configured for 512 B and sends 512-byte MWr to a Root Port set to 256 B (L-32). DMA engine bugs that cross 4 KB with an unaligned PRP offset. Firmware bugs in CQE or MSI-X write formation.
How to detect / prove
Decode the logged header. Compare its Length with the MPS of the receiving device (lspci -vvv DevCtl "MaxPayload"). Check that the whole path has a consistent MPS.
Linux v7.2 source
aer.c: AER_LOG_TLP_MASKS includes MALF_TLP; probe.c: MPS configuration (pcie_bus_configure_settings path; messages "Max Payload Size set to ...", "can't set Max Payload Size to ...").
Test to provoke it
CAUTION/EXPERT: on a test system, set the Root Port's MPS lower than the SSD's with setpci, then run large reads. This deliberately creates a fatal error, so use a disposable system with no valuable data.
L-19ECRC Error — end-to-end CRC mismatch ReportedPCIe Transaction
In a PEX trace
Visible A TLP with TD=1 whose digest the analyzer's own ECRC check also finds wrong. Corruption inside a switch shows up only on the egress link, so probe both sides of the switch to localise it. Without ECRC (TD=0) the same corruption is invisible as an error.
What happens
When ECRC generation and checking are enabled, the receiver found the 32-bit end-to-end CRC (TLP Digest) wrong. LCRC protects each hop, but a TLP can be corrupted inside a switch or retimer buffer between hops. ECRC catches that.
How it shows up
[19] ECRC with the header, default Non-fatal. Without ECRC enabled, the same corruption is silent: the switch regenerates a valid LCRC around corrupted data.
Spec basis
PCIe Base Specification: ECRC, TLP Digest (TD bit), AER ECRC Generation/Check Capable/Enable.
Typical causes
Switch or retimer internal memory errors.
How to detect / prove
Check whether ECRC is on at all. lspci -vvv AERCap shows "GenCap+ CGenEn- ChkCap+ ChkEn-". Linux v7.2 has an ecrc= boot policy, "bios" (default), "off" or "on" (ecrc_policy_str; pcie_set_ecrc_checking), passed as pci=ecrc=on.
Linux v7.2 source
aer.c: enable_ecrc_checking, disable_ecrc_checking, pcie_set_ecrc_checking, pcie_ecrc_get_policy.
Test to provoke it
SAFE to enable (pci=ecrc=on) on a test system. EXPERT: inject digest errors with an exerciser.
L-20Unsupported Request (UR) ReportedPCIe Transaction
In a PEX trace
Visible For non-posted requests: a Cpl with Completion Status UR (001b). For posted requests (the SSD's MWr of data or a CQE to an unmapped address): the MWr is visible, but its rejection happens inside the root complex, so only the root's ERR message on another link, or the missing host reaction, shows it. Check the MWr address against the PRPs and queue bases earlier in the trace.
What happens
The completer does not support the request at all: an address no BAR or window claims, a disabled Memory Space Enable, a message type it does not know, or a config request to a function that does not exist. Non-posted requests get a Cpl with UR status. Posted ones (DMA writes, doorbells) are dropped.
How it shows up
[20] UnsupReq, agent "Requester ID", header logged, default Non-fatal. The kernel documentation example is exactly this line: severity=Uncorrectable (Fatal), type=Transaction Layer, (Requester ID) ... [20] UnsupReq (First), on a platform where severity was set to fatal. NVMe consequences: an SSD DMA write of read data or a CQE to an unmapped host address is dropped, and the command "completes" from the SSD's view while the host never sees the CQE, so it times out. A doorbell write while Memory Space is disabled is dropped silently.
Spec basis
PCIe Base Specification: Unsupported Request, completion status UR, address decoding.
Typical causes
DMA to a stale or unmapped IOVA when the IOMMU is in a mode that returns UR impl. PRP entries pointing at garbage (a host driver bug or a corrupted PRP list). MMIO after the BAR was moved or disabled by hot-plug or reset. Enumeration probing absent functions (expected, normally masked or advisory).
How to detect / prove
Decode the header address. Look for a matching IOMMU fault (L-36). Check lspci -vvv Control: "Mem+ BusMaster+" on the SSD.
Linux v7.2 source
aer.c: AER_AGENT_REQUESTER_MASK; Documentation/PCI/pcieaer-howto.rst example output.
Test to provoke it
SAFE-ish: setpci read of a non-existent function (normally masked). EXPERT: a deliberately wrong PRP in a user-space NVMe test driver (SPDK/vfio) with the IOMMU on. The IOMMU should block it, which proves the protection works.
L-21ACS Violation ReportedPCIe Transaction
In a PEX trace
Partly visible Visible if the probe is on the link where the P2P TLP enters the switch: the TLP goes in and never comes out on the peer's link. The violation is detected inside the switch and logged in its registers. Its ERR_NONFATAL goes upstream.
What happens
A switch Downstream Port or root port with Access Control Services (ACS) enabled blocked a TLP that violated its policy. Typically this is peer-to-peer traffic (SSD → GPU or NIC BAR) that ACS Source Validation, P2P Request Redirect or Egress Control forbids, or a TLP with a spoofed Requester ID. See also the configuration-level card L-33.
How it shows up
[21] ACSViol with the header, logged at the port, default Non-fatal. The P2P DMA fails, and the NVMe command using a P2P buffer times out or returns an error.
Spec basis
PCIe Base Specification: Access Control Services, ACS Violation Status.
Typical causes
P2PDMA (NVMe CMB as a target, GPUDirect Storage) through a switch with ACS redirect enabled for IOMMU isolation. VFs using the wrong Requester ID.
How to detect / prove
lspci -vvv ACSCtl on each port. Linux logs Configured ACS to %#06x (pci_std_enable_acs path), and the pci=config_acs= parameter changes it.
Linux v7.2 source
drivers/pci/pci.c: pci_enable_acs, pci_acs_enabled, pci_acs_path_enabled, messages "Invalid ACS flags specified", "Configured ACS to %#06x".
Test to provoke it
CAUTION: attempt P2PDMA between two devices under one switch with ACS P2P redirect on.
L-22Uncorrectable Internal Error ReportedPCIe Transaction
In a PEX trace
Not visible The fault is internal to the device. At most an ERR_FATAL Message appears, and only if unmasked. Afterwards the device may stop responding (MRd with no completion). Use the AER registers, CSTS.CFS and vendor telemetry.
What happens
The function detected an internal error it could not correct: a parity or ECC error in internal SRAM or an internal bus fault inside the PCIe or NVMe front end. Default Fatal, but masked by default, so most systems never see it as AER. The NVMe controller may instead set CSTS.CFS (C-01) or post a Persistent Internal Error asynchronous event (C-11).
How it shows up
If unmasked: [22] UncorrIntErr, Fatal recovery. If masked: nothing in AER. Look at the NVMe-level symptoms.
Spec basis
PCIe Base Specification: Uncorrectable Internal Error Status/Mask/Severity (optional).
Typical causes
SRAM soft errors, silicon defects, overheating.
How to detect / prove
Check UEMsk in lspci -vvv. For a lab, unmask and watch (CAUTION). Correlate with NVMe telemetry and the error log.
Linux v7.2 source
aer.c: pci_aer_unmask_internal_errors (CXL only), string "UncorrIntErr".
Test to provoke it
Vendor-specific injection only.
L-23Egress-blocked family: MC Blocked, AtomicOp Egress Blocked, TLP Prefix Blocked, Poisoned TLP Egress Blocked, DMWr Request Egress Blocked, TLP Translation Egress Blocked ReportedPCIe Transaction
In a PEX trace
Partly visible The originating TLP (AtomicOp, prefixed TLP, poisoned TLP, DMWr) is visible on the ingress link. The blocking happens inside the port. On the requester's link, you then see a UR/CA completion or no completion.
What happens
A port refused to forward a TLP out of an egress port because the next hop cannot accept that TLP type, or because policy says to block it. Bit 23 is a multicast TLP blocked. Bit 24 is an AtomicOp toward a port without AtomicOp routing or support. Bit 25 is an End-End TLP Prefix (such as PASID in some forms) toward a port that does not support prefixes. Bit 26 is a poisoned TLP blocked by policy. Bit 27 is a Deferrable Memory Write blocked. Bit 31 is translation-related egress blocking.
How it shows up
Bits 23–27 and 31, all in AER_LOG_TLP_MASKS (header logged). Linux strings: "BlockedTLP", "AtomicOpBlocked", "TLPBlockedErr", "PoisonTLPBlocked", "DMWrReqBlocked", "TLPXlatBlocked". The originator's request fails, usually as a Completion Timeout or UR from its point of view.
Spec basis
PCIe Base Specification: AtomicOp routing/egress blocking, End-End TLP Prefix rules, Poisoned TLP Egress Blocking, Deferrable Memory Write. Default severity and mask values for bits 26, 27 and 31: verify in spec uncertain.
Typical causes
Rare for plain NVMe I/O. Possible with PASID or SVA-capable NVMe controllers, computational storage using AtomicOps toward host memory, and poisoned-TLP containment policies on server root ports.
How to detect / prove
Decode the logged header (prefix present? Fmt/Type = AtomicOp?). Check DevCap2 AtomicOpsCap and AtomicOp routing on each port, and End-End TLP Prefix support.
Linux v7.2 source
pci_regs.h: PCI_ERR_UNC_MCBTLP, _ATOMEG, _TLPPRE, _POISON_BLK, _DMWR_BLK, _XLAT_BLK; aer.c: strings and AER_LOG_TLP_MASKS.
Test to provoke it
EXPERT: an exerciser sending AtomicOps or prefixed TLPs through a port without support.
L-24IDE family: IDE Check Failed, Misrouted IDE TLP, PCRC Check Failed ReportedPCIe Transaction
In a PEX trace
Partly visible IDE TLPs are visible with their IDE prefix and stream ID, but their payload is encrypted. Integrity failures can be decoded only if the analyzer has the keys. Otherwise you see only the error message or the device stopping DMA.
What happens
With PCIe Integrity and Data Encryption (IDE) active, used for confidential computing and TDISP-style device assignment, a received TLP failed its integrity (MAC) check (bit 28), arrived on the wrong IDE stream or port (bit 29), or failed the optional plaintext CRC (PCRC) check (bit 30). IDE treats integrity failure as a security event. The spec defines how the IDE stream is affected (for example, the stream is torn down and must be re-keyed) uncertain — verify in spec.
How it shows up
"IDECheck", "MisIDETLP", "PCRC_CHECK", with the header logged. The NVMe device's DMA stops working until the stream is re-established.
Spec basis
PCIe Base Specification: IDE (introduced in 6.0-era ECNs). Severity defaults: verify in spec.
Typical causes
Key-programming mismatches, stream ID misconfiguration, real tampering, or (more likely) firmware bugs in early IDE implementations.
How to detect / prove
The AER log plus the platform security or TSM logs. IDE-capable analyzers need the keys to decode traffic.
Linux v7.2 source
pci_regs.h: PCI_ERR_UNC_IDE_CHECK, _MISR_IDE, _PCRC_CHECK; aer.c strings.
Test to provoke it
EXPERT: program mismatched keys on a test setup.
📌 Remember

Posted writes fail silently for the sender. When an SSD's MWr carrying a CQE or read data is dropped as UR or by the IOMMU, the SSD considers the command complete and the host waits forever. The only evidence is an error logged at the root complex (AER on the Root Port or an IOMMU fault), followed 30 seconds later by the NVMe timeout. Always check the root-side logs for an NVMe timeout that has no device-side explanation.

Quiz

  1. MalfTLP appears on the Root Port every time a large sequential read starts. What is the first register you compare?

    Answer

    Max_Payload_Size in Device Control on the SSD and on the Root Port (and any switch between them). The SSD is sending read data in MWr TLPs larger than the Root Port's MPS.

  2. Why can Completion Timeout be "timer only" even though AER reports it?

    Answer

    Nothing reported the missing completion. The requester infers the failure only because its own timer expired. AER records that inference, but the root cause (who dropped the request) has to be found elsewhere.
