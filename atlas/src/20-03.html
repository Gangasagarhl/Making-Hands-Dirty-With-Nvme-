5 Command Specific Status (SCT 1)

SCT 1 codes only make sense together with the opcode that got them. SC 0x00–0x7F are defined per admin command (queue management, firmware, namespace management, virtualization). SC 0x80–0xBF are defined per I/O command set: for the NVM command set (0x80–0x8x), for Fabrics commands (the same numbers, different meanings), and for Zoned Namespaces (0xB6–0xBF). In Linux's shifted layout they are 0x100–0x1FF. Always decode an SCT 1 status with the opcode next to it. 0x180 is "Conflicting Attributes" for a Dataset Management command but "Incompatible Format" for a Fabrics Connect.

💡 Linux ignores some of these on purpose

drivers/nvme/host/pci.c:nvme_create_io_queues() says: "Ignore failing Create SQ/CQ commands, we can continue with less than the desired amount of queues, and even a controller without I/O queues can still be used to issue admin commands." A drive that rejects queue creation with an SCT 1 code (0x100–0x102, 0x108) therefore does not fail probe. The result is a working but slower device with fewer queues. The error is reported, but in practice it shows up as a performance anomaly. Check ls /sys/block/nvme0n1/mq | wc -l against the CPU count.

What happens
Create I/O SQ named a CQID that does not exist (or is 0), or Delete I/O CQ named an invalid CQ.
How it shows up
Linux 0x100 "Completion Queue Invalid" on the admin command; queue setup continues with fewer queues (see callout above).
Spec basis
Create I/O Submission Queue (01h) CDW11 CQID; Delete I/O Completion Queue (04h).
Typical causes

Admin command order in the trace: Create CQ (05h) must complete successfully before Create SQ (01h) uses its ID.
In a trace
Create SQ with CQID=n where no earlier successful Create CQ n exists.
Linux v7.2 source
pci.c:nvme_create_queue() → adapter_alloc_cq() then adapter_alloc_sq().
Test to provoke it

S-31Invalid Queue Identifier (SCT 1 / SC 0x01) ReportedNVMe admin / queues
What happens
Create I/O SQ/CQ used a QID that is 0, already in use, or above the number of queues granted by Set Features Number of Queues. Also used by Delete I/O SQ for a bad SQID.
How it shows up
Linux 0x101; queue creation stops at that queue.
Spec basis
Number of Queues feature (FID 07h) result NSQA/NCQA (0's based); Create/Delete queue commands.

What happens
The queue size in Create I/O SQ/CQ is 0 or bigger than CAP.MQES+1, or (QEMU) the CC.IOSQES/IOCQES entry sizes are not 64/16 bytes.

S-33Abort Command Limit Exceeded (0x03) / 0x04 "Abort Command Is Missing" (reserved) ReportedNVMe admin
What happens
The host has more Abort commands outstanding than ACL+1 (Identify Controller ACL is 0's based). The extra Abort is rejected. 0x04 is listed by libnvme as "Abort command is missing". Linux names it NVME_SC_ABORT_MISSING but prints "Reserved" uncertain in current specs.
How it shows up
The Abort itself completes with 0x103. Linux logs "Abort status: 0x103" from pci.c:abort_endio().
Spec basis
Abort command (08h); ACL in Identify Controller (spec recommends at least 4, i.e. ACL ≥ 3).
Typical causes
Many simultaneous timeouts from a non-Linux host. Linux sets ctrl->abort_limit = id->acl + 1 and, in nvme_timeout(), does not send more aborts than that (it re-arms the timer instead). Linux therefore should not trigger this code unless ACL is reported wrongly.
How to detect / prove
Count outstanding Abort SQEs (opcode 08h) in the trace vs ACL from nvme id-ctrl.
In a trace
ACL+2 Abort SQEs without completions between them; the last one gets 0x103.
Linux v7.2 source
pci.c:nvme_timeout() (atomic_dec_return(&dev->ctrl.abort_limit) < 0 → BLK_EH_RESET_TIMER).
Test to provoke it
EXPERT: user-space driver issuing ACL+2 aborts for commands stuck in a slow backend (QEMU).
S-34Asynchronous Event Request Limit Exceeded (SCT 1 / SC 0x05) ReportedNVMe admin / AEN
What happens
More AER commands are outstanding than the controller supports (Identify Controller AERL, 0's based). The extra AER completes at once with this status.
How it shows up
0x105 on an AER (opcode 0Ch). Linux's nvme_complete_async_event() returns early for any non-success AER status (if (le16_to_cpu(status) >> 1 != NVME_SC_SUCCESS) return;) and does not resubmit, so the error is not logged.
Spec basis
Asynchronous Event Request command; AERL (spec recommends at least 4 supported).
Typical causes
A host or tool submitting AERs in a loop; a controller with AERL=0 meeting a host that posts several. Linux posts only one (NVME_NR_AEN_COMMANDS = 1). QEMU: nvme_aer(): if (n->outstanding_aers > n->params.aerl) return NVME_AER_LIMIT_EXCEEDED (no DNR).
How to detect / prove
Count outstanding opcode 0Ch commands in the trace; compare with AERL.
In a trace
AER SQEs normally stay outstanding for hours. One that completes within microseconds with 0x105 is this error.
Linux v7.2 source
core.c:nvme_complete_async_event(), pci.c:nvme_pci_submit_async_event() (fixed CID NVME_AQ_BLK_MQ_DEPTH).
Test to provoke it
SAFE in QEMU: -device nvme,aerl=0 plus a second AER sent with nvme admin-passthru --opcode=0x0c (it blocks until an event if accepted).

S-36Invalid Firmware Image (0x07) and Overlapping Range (0x14) ReportedNVMe admin / firmware
What happens
0x07: the downloaded image failed validation (signature, CRC, wrong model, incomplete) at commit time. 0x14: Firmware Image Download pieces overlapped (the same offset range sent twice in an incompatible way).
How it shows up
0x107 on Firmware Commit, or 0x114 on Firmware Image Download/Commit. The running firmware is unchanged. Some drives also raise an Error AEN "Firmware Image Load Error" (05h) at a later activation.

Firmware Image Download (11h) NUMD/OFST in Dwords; FWUG (Firmware Update Granularity) in Identify Controller; Firmware Commit.
Typical causes
Wrong image file for the SKU; chunk size not a multiple of FWUG; tool retrying a chunk with a different offset; image signed for a different security version (anti-rollback).
How to detect / prove
Log every Firmware Image Download (offset, length) and check contiguity; compare nvme id-ctrl FWUG with the transfer size (nvme fw-download --xfer).
In a trace
A series of opcode 11h SQEs with OFST increasing by NUMD+1; a gap or overlap is visible directly.
Linux v7.2 source
Passthrough only.
Test to provoke it
CAUTION: download a truncated or foreign image, then commit with CA=0 (replace, no activation). The drive must reject it without bricking. Run this as a robustness test.

S-40Firmware Activation Requires Reset: Conventional (0x0B), NVM Subsystem (0x10), Controller Level (0x11) ReportedNVMe admin / firmware
What happens
These are successes reported as errors. The commit worked and the image is in the slot, but it will only run after the given type of reset. Until then the old firmware keeps running.
How it shows up
0x10B / 0x110 / 0x111 on Firmware Commit. Firmware Slot log (LID 03h) AFI: the "next active" slot (bits 6:4) differs from the current slot (bits 2:0). Linux reports this at AEN time as "Firmware is activated after next Controller Level Reset".
Spec basis
Firmware Commit CA values (libnvme: 0 replace, 1 replace+activate at reset, 2 activate at reset, 3 replace+activate immediately, 6/7 boot partition); Firmware Slot Information log AFI; NSSR register (20h) for subsystem reset.
Typical causes
Image needs a full reset to load; CA=1/2 used (activation at next reset by design). Scripts that treat any non-zero status as failure roll back a successful update. Scripts that ignore it think the new firmware is running when it is not.
How to detect / prove
nvme fw-log /dev/nvme0 AFI before and after; cat /sys/class/nvme/nvme0/firmware_rev stays old until reset; after a reset, check the revision again.
In a trace
Firmware Commit CQE with SCT 1 SC 0x0B/0x10/0x11; later CC.EN 1→0→1 (controller reset), PCIe hot/conventional reset, or a write of "NVMe" (4E564D65h) to NSSR.
Linux v7.2 source
core.c:nvme_get_fw_slot_info(): if (!cur_fw_slot || (next_fw_slot && (cur_fw_slot != next_fw_slot))) → "Firmware is activated after next Controller Level Reset"; reset via nvme reset /dev/nvme0 (NVME_IOCTL_RESET) or subsystem reset (NVME_IOCTL_SUBSYS_RESET, pci.c:nvme_pci_subsystem_reset()).
Test to provoke it
CAUTION: nvme fw-download a valid image, nvme fw-commit -s 2 -a 1, read status, then nvme reset /dev/nvme0 and verify firmware_rev. Use a supported vendor image only.
S-41Firmware Activation Requires Maximum Time Violation (0x12) / Activation Prohibited (0x13) ReportedNVMe admin / firmware
What happens
0x12: activating now (CA=3, immediate) would take longer than MTFA (Maximum Time for Firmware Activation, Identify Controller, 100 ms units), so the controller refuses. 0x13: the controller refuses this image for vendor-specific reasons (e.g. anti-rollback, a downgrade not allowed).
How it shows up
0x112 / 0x113 on Firmware Commit; the running firmware is unchanged.
Spec basis
MTFA; FRMW bit 4 (activation without reset supported); Firmware Commit CA=3.
Typical causes
Immediate activation of an image that changes the media layout; downgrade blocked by security policy.
How to detect / prove
Retry with CA=1/2 and a reset. If it works, the immediate path was the problem. For 0x13, check the vendor's release notes for minimum versions.
In a trace
Commit CDW10[5:3]=3 → CQE 0x12.
Linux v7.2 source
MTFA is stored in ctrl->mtfa and used by core.c:nvme_fw_act_work() to bound the wait while CSTS.PP is set after a "Firmware Activation Starting" AEN (S-81).
Test to provoke it
CAUTION: commit with CA=3 an image the vendor says needs a reset.

LBA Range Type feature (attributes: read-only / hidden ranges). QEMU defines NVME_WRITE_TO_RO but never returns it.
Typical causes
OEM BIOS/firmware marked ranges read-only; old tools.
How to detect / prove
nvme get-feature /dev/nvme0 -n 1 -f 3 -H.
In a trace
Write → CQE 0x182 (may follow data transfer).
Linux v7.2 source
core.c:nvme_error_status() (BLK_STS_MEDIUM).
Test to provoke it
CAUTION: set an LBA Range Type entry with the read-only attribute on a test drive that supports FID 03h.
S-52Command Size Limits Exceeded (0x83) and Copy-related 0x85/0x86/0x87/0x89 ReportedNVMe command / Copy
What happens
A Copy (19h) or similar command exceeds MSSRL (max single source range length), MCL (max copy length) or MSRC (max source range count): 0x83. libnvme and QEMU add 0x85 Incompatible Namespace or Format, 0x86 Fast Copy Not Possible, 0x87 Overlapping I/O Range, 0x89 Insufficient Resources. These are not in Linux's nvme.h, so Linux prints them as "Unknown".
How it shows up
0x183 (Linux text "Command Size Limits Exceeded"); 0x185/0x187 from QEMU's nvme_do_copy().
Spec basis
NVM Command Set Copy command; Identify Namespace MSSRL/MCL/MSRC; ONCS Copy bit.
Typical causes
Copy offload with ranges built from filesystem extents larger than MSSRL; cross-namespace copy between different LBA formats (0x85); source overlapping destination (0x87). QEMU: nvme_check_copy_mcl(), nvme_copy().
How to detect / prove
nvme id-ns -H mssrl/mcl/msrc, then the Copy range list contents.
In a trace
Copy SQE → MRd of the source range descriptors → CQE.
Linux v7.2 source
Default mapping (-EIO); Linux v7.2 does not issue Copy from the block layer in the paths examined here uncertain, so Copy errors come from passthrough.
Test to provoke it
SAFE in QEMU: nvme copy with a range longer than MSSRL.
S-53Fabrics Connect/Discovery statuses: 0x80–0x84, 0x90 Discovery Restart, 0x91 Authentication Required ReportedNVMe-oF
What happens
Fabrics Connect rejected: Incompatible Format (0x180), Controller Busy (0x181), Connect Invalid Parameters (0x182), Connect Restart Discovery (0x183), Connect Invalid Host (0x184). Also Discovery Restart (0x190) and Authentication Required (0x191). libnvme also lists 0x85 Invalid Queue Type for Disconnect.
How it shows up
Connect fails; nvme connect reports the error. dmesg from fabrics.c:nvmf_log_connect_error(). For 0x182 it decodes which parameter failed using the Connect response's IATTR/IPO fields. 0x191 on I/O → Linux disposition AUTHENTICATE → re-authentication work, then retry.
Spec basis
NVMe over Fabrics: Connect command and response, Discovery log, DH-HMAC-CHAP in-band authentication.
Typical causes
Host NQN not on the target's allow list (0x184); wrong subsystem NQN or CNTLID (0x182); dynamic controller already associated (0x181); keys not configured (0x191).
How to detect / prove
dmesg "Connect Invalid Host"/"Connect command failed ..." lines; target-side logs; nvme discover output.
In a trace
Network capture: Fabrics command capsule (opcode 7Fh, fctype Connect) → response capsule with the status.
Linux v7.2 source
fabrics.c:nvmf_log_connect_error(), nvmf_should_reconnect() path stops reconnecting when status & NVME_STATUS_DNR; core.c:nvme_decide_disposition() AUTHENTICATE branch. Note the string-table collision with NVM codes (§3.4.3).
Test to provoke it
SAFE: Linux nvmet loopback target without the host NQN in allowed_hosts → 0x184.

5.2 Zoned Namespace command set (SCT 1, SC 0xB6–0xBF)

ZNS errors are mostly the host breaking the zone state machine (write pointer, open and active limits). QEMU's ZNS model (nvme_check_zone_write(), nvme_check_zone_state_for_write(), nvme_zns_check_resources(), nvme_zrm_*()) returns all of them, so it is an excellent test device. Linux zoned users (f2fs, btrfs, dm-zoned, zonefs) get -EIO for most of them, but -EOVERFLOW / -ETOOMANYREFS for the active and open limits. libnvme also lists 0xB6 Invalid Zone Operation Request and 0xB7 ZRWA Resources Unavailable, which Linux's nvme.h lacks.

S-54Zone Boundary Error (SCT 1 / SC 0xB8) ReportedNVMe command / ZNS
What happens
A command's LBA range spans more than one zone. For reads this is only an error if the namespace forbids cross-zone reads (Read Across Zone Boundaries, OZCS.RAZB=0).
How it shows up
0x1B8 → -EIO.
Spec basis
ZNS Command Set: zone size (ZSZE), OZCS RAZB.
Typical causes
Host splitting logic ignoring zone size (non-power-of-2 zone sizes are a classic trap). QEMU: nvme_check_zone_write(), nvme_check_zone_read().
How to detect / prove
nvme zns id-ns (zsze); compute slba / zsze and (slba+nlb-1) / zsze.
In a trace
Write SQE near a zone end → CQE 0x1B8.
Linux v7.2 source
Block layer splits at chunk_sectors (zone size) so in-kernel I/O should not cross; default mapping in nvme_error_status().
Test to provoke it
SAFE in QEMU ZNS: nvme read across a zone boundary.
S-55Zone Is Full (0xB9) / Zone Is Read Only (0xBA) / Zone Is Offline (0xBB) ReportedNVMe command / ZNS
What happens
A write to a zone in ZSF:Full (0xB9) or ZSRO:Read Only (0xBA), or any access to a zone in ZSO:Offline (0xBB). Read Only and Offline are device-initiated states: the drive moved the zone there because of media problems. That makes them media-health events disguised as state errors.
How it shows up
0x1B9/0x1BA/0x1BB → -EIO. A zone report shows the zone state. The drive may also raise a Zone Descriptor Changed notice (ZNS-specific AEN) verify in spec.
Spec basis
ZNS zone states ZSE/ZSIO/ZSEO/ZSC/ZSF/ZSRO/ZSO; Zone Management Receive (report zones).
Typical causes
Host lost track of the write pointer after a crash (Full); worn or failed dies (Read Only, Offline). QEMU: nvme_check_zone_state_for_write(), nvme_check_zone_state_for_read().
How to detect / prove
nvme zns report-zones /dev/nvme0n1 -d 10; blkzone report; count zones in RO/Offline over time as a health metric.
In a trace
Write SQE → immediate CQE.
Linux v7.2 source
zns.c (nvme_ns_report_zones()) converts zone states for the block layer; status → -EIO.
Test to provoke it
SAFE in QEMU: fill a zone, then write again (0xB9). QEMU's Offline send action works only from Read Only (nvme_offline_zone()). Read Only and Offline must be entered by the device, so test 0xBA/0xBB with vendor injection or fault injection on the host.
S-56Zone Invalid Write (SCT 1 / SC 0xBC) ReportedNVMe command / ZNS
What happens
A Write to a sequential-write-required zone did not start at the zone's write pointer.
How it shows up
0x1BC → -EIO. The most common ZNS error in the field.
Spec basis
ZNS sequential write requirement; Zone Append (opcode 7Dh) avoids it by letting the device choose the LBA.
Typical causes
Reordered writes (multiple queues, no zone write locking or plugging); retry of a write that actually succeeded (write pointer already advanced); host write-pointer cache stale after power loss. QEMU nvme_check_zone_write(): if (slba != zone->w_ptr) return NVME_ZONE_INVALID_WRITE.
How to detect / prove
Trace per-zone SLBA order and compare with the reported write pointer. A write that is reported failed but whose data is present means the earlier attempt succeeded.
In a trace
Two Writes to the same zone completing out of order, or a re-submission after a host timeout.
Linux v7.2 source
Block layer zone write plugging keeps order. The NVMe driver maps the status to -EIO. Note the danger of nvme_decide_disposition() retries for zoned writes when DNR is clear derived.
Test to provoke it
SAFE in QEMU: nvme write to zslba + 8 on an empty zone.
S-57Too Many Active Zones (0xBD) / Too Many Open Zones (0xBE) ReportedNVMe command / ZNS
What happens
Opening or writing a zone would exceed MAR (Maximum Active Resources) or MOR (Maximum Open Resources), both 0's based.
How it shows up
0x1BD → BLK_STS_ZONE_ACTIVE_RESOURCE → -EOVERFLOW; 0x1BE → BLK_STS_ZONE_OPEN_RESOURCE → -ETOOMANYREFS. These are the only zone codes with dedicated Linux errnos, so the filesystem can tell them apart and close zones.
Spec basis
ZNS Identify Namespace MAR/MOR; implicit vs explicit open.
Typical causes
Too many concurrent writers or log streams; not finishing zones. QEMU: nvme_zns_check_resources() (with DNR).
How to detect / prove
cat /sys/block/nvme0n1/queue/max_open_zones and max_active_zones; count zones in open/closed states from a zone report.
In a trace
A write to an empty zone → CQE 0x1BE.
Linux v7.2 source
core.c:nvme_error_status(); limits set in zns.c from MAR/MOR.
Test to provoke it
SAFE in QEMU: -device nvme-ns,zoned=true,zoned.max_open=2, then write to 3 empty zones.
S-58Invalid Zone State Transition (0xBF) and Invalid Zone Operation Request (0xB6) / ZRWA Resources Unavailable (0xB7) ReportedNVMe command / ZNS
What happens
Zone Management Send asked for a transition the state machine does not allow (e.g. Open a Full zone, Finish an Offline zone) → 0xBF. 0xB6: invalid zone operation (e.g. allocating a ZRWA on a non-empty zone). 0xB7: no Zone Random Write Area available.
How it shows up
0x1BF → -EIO (Linux has no constant for 0xB6/0xB7 and prints "Unknown").
Spec basis
ZNS Zone Send Actions (Close, Finish, Open, Reset, Offline, Set Zone Descriptor Extension, Flush Explicit ZRWA Range).
Typical causes
Host state cache out of sync; tools sending Open to Full zones. QEMU: nvme_zrm_open_flags(), nvme_zrm_finish(), nvme_zrm_close(), nvme_zrm_reset(), nvme_offline_zone() return NVME_ZONE_INVAL_TRANSITION (no DNR); nvme_open_zone() returns NVME_INVALID_ZONE_OP / NVME_NOZRWA.
How to detect / prove
Zone report before the command; ZNS state diagram.
In a trace
Zone Management Send (79h) → CQE.
Linux v7.2 source
Zone ops (REQ_OP_ZONE_*) built in zns.c:nvme_setup_zone_mgmt_send().
Test to provoke it
SAFE in QEMU: nvme zns open-zone on a full zone.
