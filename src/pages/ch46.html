Advanced Error Reporting (AER) is the PCI Express capability that records exactly which error happened, in which function, how serious software has declared it to be, and — for many uncorrectable errors — the header of the very packet that caused it. This chapter walks through every AER register a working engineer uses, shows how errors flow from a device to the root port to the operating system, and teaches you to read Linux AER reports line by line.

Why this chapter exists

Chapter 45 named the PCIe errors. Without AER, a function can only say "I saw a correctable / non-fatal / fatal / unsupported-request error" (four bits in Device Status). With AER it can say "Completion Timeout, first, here is the header", and the root port can say "the first fatal error message came from 01:00.0". That difference decides whether a PCIe investigation takes an hour or a month.

Learning objectives

  • Locate the AER Extended Capability and name its registers and offsets.
  • Decode Uncorrectable Error Status, Mask and Severity; Correctable Error Status and Mask; Advanced Error Capabilities and Control (First Error Pointer, ECRC enables).
  • Decode the Header Log back into a TLP header and use it to identify the offending transaction.
  • Explain the root port registers: Root Error Command, Root Error Status, Error Source Identification.
  • Explain how masks, severity and Device Control enables decide whether an error is logged, signalled and as what.
  • Read Linux AER kernel messages and the per-device counters, and know what they prove.
  • Understand AER's role in recovery (driver callbacks, link reset, Downstream Port Containment) at an introductory level.

You need PCIe Errors, the configuration space and extended capabilities from Configuration Space, and TLP header fields from TLP Header Anatomy. Interrupt delivery for the root port's AER interrupt uses the mechanisms from Interrupt Architecture.

The story

Every guardhouse on the road keeps a notebook. The notebook has a page of checkboxes for small problems ("smudged label — fixed") and a page for big problems ("parcel for a building that doesn't exist"). Next to each big problem is a little sign saying whether it's "worrying" or "emergency". There are also "don't tell me about this" stickers the head office can put over any box.

When something big goes wrong, the guard also photocopies the parcel's label and staples it into the notebook, so later everyone can see exactly which parcel it was.

At the big gate near the school there's a special guardhouse with an extra page: "Who called me? First caller: guardhouse 01:00.0". When anybody reports a problem, the gate rings a bell in the head teacher's office.

AER is like an aircraft's maintenance logbook plus its central warning panel. Each system has its own fault codes (status registers), the airline decides which faults are cabin chimes and which are master cautions (severity), maintenance can inhibit known nuisance warnings (masks), and the flight data recorder keeps a snapshot of the parameters at the first serious fault (header log, first error pointer). The cockpit panel (root port) shows which system raised the latest warning (error source identification).

Hides: each function keeps its own logbook, and the root port's panel only records the source of messages, not the details — the OS must go and read the reporting function's registers, which may be impossible if that function is now unreachable. Misleads: "first" error and header snapshot are kept only for one error at a time (unless multiple header recording is implemented); later errors overwrite nothing but also add no detail. And masking an error does not make it disappear: the status bit is still set — only the reporting is suppressed.

Beginner explanation

AER is an optional structure in a PCIe function's extended configuration space (beyond offset 100h). It contains:

  • Two sets of status bits — one for correctable, one for uncorrectable errors — one bit per error type.
  • Two mask registers — a 1 stops that error type from being reported (signalled), though it is still recorded.
  • A severity register — for each uncorrectable error, 1 = fatal, 0 = non-fatal.
  • A header log — a copy of the 16-byte header of the TLP that caused the first logged uncorrectable error (when applicable).
  • A control register — including the First Error Pointer (which status bit was first) and the end-to-end CRC (ECRC) enables.
  • In root ports only: Root Error Command (turn on interrupts for received error messages), Root Error Status (what kinds of messages arrived) and Error Source Identification (who sent them).

The operating system's AER driver gets an interrupt from the root port, reads the root registers to find which device reported, reads that device's AER registers to find what happened, prints it, clears the bits, and may start recovery.

  • First Error Pointer (4:0) — the bit number, in Uncorrectable Error Status, of the first uncorrectable error recorded. The Header Log belongs to that error. Valid only while that status bit is still set.
  • ECRC Generation/Check Capable and Enable (5–8) — end-to-end CRC support and enable. ECRC is off by default on most platforms (Linux's pci=ecrc= controls it).
  • Multiple Header Recording (9–10) — optional ability to log several headers; when the log fills, Header Log Overflow (correctable bit 15) is set.
  • Completion Timeout Prefix/Header Log Capable (12) — whether the function logs a header for Completion Timeouts. Many do not, in which case the Header Log is meaningless for a CmpltTO.

Header Log

The Header Log holds the first 4 DWORDs of the TLP header associated with the error indicated by the First Error Pointer, for errors where a TLP is identifiable (Poisoned TLP, ECRC, UR, CA, Unexpected Completion, Malformed TLP, Completion Timeout if capable, ACS violation, and others). Each DWORD is stored as it appeared on the wire, byte 0 most significant — Linux prints them as four hex words you can decode with the same rules as in TLP Header Anatomy.

Root port registers

+30h31…2423…1615…87…0
Root Error StatusAE Int Msg #Reserved / newer fieldsFatal MsgsNF MsgsFirst Unc FatalMult F/NFF/NF RcvdMult CORCOR Rcvd
  • Root Error Command (2Ch): bit 0 Correctable Error Reporting Enable, bit 1 Non-Fatal Error Reporting Enable, bit 2 Fatal Error Reporting Enable — when set, receiving that class of error message raises the root port's interrupt.
  • Root Error Status (30h): ERR_COR Received (0), Multiple ERR_COR Received (1), ERR_FATAL/NONFATAL Received (2), Multiple ERR_FATAL/NONFATAL Received (3), First Uncorrectable Fatal (4), Non-Fatal Error Messages Received (5), Fatal Error Messages Received (6); bits 31:27 Advanced Error Interrupt Message Number (which MSI/MSI-X vector the root port uses for AER).
  • Error Source Identification (34h): bits 15:0 = Requester ID of the function that sent the ERR_COR being recorded; bits 31:16 = Requester ID of the ERR_FATAL/NONFATAL source. Only the first (or latest, depending on "multiple" state) source is held; the "Multiple" bits tell you that others were lost.

When the root port itself detects an error (for example a Bad TLP on its receiver, or a Malformed TLP from the device), it logs in its own AER status registers and, for signalling purposes, behaves as if it had received a message from itself: Error Source Identification may then contain the root port's own Requester ID. Linux prints "error message received from 0000:00:01.1" for such cases — the root port names itself.

Recovery: what happens after logging

AER also drives recovery. In Linux, on an uncorrectable error the AER driver calls each affected driver's error_detected() callback; for non-fatal errors it may only need mmio_enabled() and resume(); for fatal errors it resets the link (secondary bus reset or DPC) and calls slot_reset() then resume(). The NVMe driver implements these: it quiesces queues, disables the controller, and after the reset re-initialises it. If a platform implements Downstream Port Containment, the downstream port blocks traffic on an uncorrectable error before software even runs, limiting damage (see Advanced Error Handling and PCIe Reset).

Many server platforms use firmware-first error handling: platform firmware owns AER, reads and clears the registers, and reports to the OS through ACPI APEI/GHES records. The OS then prints hardware-error records instead of native AER lines, and the registers may already be cleared when you look. Check your kernel log for APEI/GHES messages and the ACPI _OSC negotiation result.

The central concept on the ladder

Every guardhouse keeps a notebook with boxes for each kind of problem, stickers to silence some, a "worrying vs emergency" sign, and a photocopy of the first bad parcel's label.

AER is a capability with status, mask and severity registers per error class, a first-error pointer and header log; root ports add registers that record who reported.

Status bits are sticky flip-flops in each function's configuration space, set by detection logic. The header log is a 16-byte latch loaded from the offending TLP. Root ports have extra latches for message sources and an interrupt generator.

PCI Express Base Specification: Advanced Error Reporting Capability (ID 0001h) register definitions; Error Signaling and Logging rules; default mask and severity values.

Error messages (ERR_COR/ERR_NONFATAL/ERR_FATAL) flow to the root complex; software then uses configuration reads/writes (CfgRd/CfgWr) to read and clear AER registers.

An analyzer shows the offending TLP, then the Msg ERR_* from the detector (if the detector is downstream), then a burst of configuration reads from the root complex to that function's AER offsets, then RW1C configuration writes.

Decode the First Error Pointer and Header Log at the detecting function; reconstruct the TLP; match it to a transaction in the NVMe timeline (which command, which buffer); then decide cause vs victim.

Hardware view

AER registers are implemented in each function's configuration space logic; they are sticky across Hot Reset / FLR in most cases (RW1CS / ROS attributes), so evidence survives the recovery that the error causes — one of AER's most important design choices. Detection logic for each error lives in the layer that detects it (Chapter 45 hardware view), wired to these status bits.

  • Must participate: detecting function's AER logic; root port's root error logic and interrupt (MSI/MSI-X) for AER.
  • May participate: switches forwarding error messages; Root Complex Event Collectors for integrated endpoints; DPC logic in downstream ports; platform firmware (firmware-first).
  • Observable: all AER registers via configuration reads (if the function is reachable); error messages on the link.
  • Unobservable: errors in a function that has no AER (only Device Status), errors that were masked (status set but never signalled), and errors in a function you can no longer reach (link down).

AER is optional for endpoints. Many NVMe SSDs implement it; some implement only a subset of status bits. Root ports on server platforms almost always implement it. Header logging for Completion Timeout and multiple header recording are optional.

Specification view

  • PCI Express Base Specification, Revision 6.x/7.0 — Advanced Error Reporting Extended Capability; Error Signaling and Logging; Root Complex Event Collector Normative
  • PCI Firmware Specification and ACPI Specification — _OSC control of AER; APEI for firmware-first ownership (platform-level).

AER is Extended Capability ID 0001h with Uncorrectable Error Status/Mask/Severity at 04h/08h/0Ch, Correctable Error Status/Mask at 10h/14h, Advanced Error Capabilities and Control at 18h (First Error Pointer 4:0), Header Log at 1Ch–28h, and for root ports Root Error Command 2Ch, Root Error Status 30h, Error Source Identification 34h. Status bits are write-1-to-clear and sticky. Default severities: DLP, Surprise Down, FC Protocol, Receiver Overflow, Malformed TLP, Uncorrectable Internal Error fatal.

Decoding the header log with TLP header rules, and the reasoning that the header identifies "the offending transaction", are applications of the specification; whether the logged TLP is the cause or merely the first casualty is interpretation.

Which bits a function implements; optional header logging; multiple header recording; whether firmware or OS owns AER; how the root port's AER interrupt is configured; whether DPC is present and enabled.

The bit set and some control fields grew over revisions (e.g. newer internal-error and blocked-TLP bits, TLP prefix logging, FLIT-mode related logging). Linux's AER message format and the sysfs counters differ between kernel versions.

Check in the specification: exact attribute (sticky or not) of each field; precise rules for when the header log is updated if several errors occur; which errors have a meaningful header; Advisory Non-Fatal cases. The specification does not say how software should prioritise or recover from errors.

Never assume a header log belongs to the error you are looking at — check the First Error Pointer. Never assume masked means "did not happen". Never assume an absence of AER messages means no errors (firmware-first, masking, reporting disabled, no AER on endpoint).

Protocol view

Note the traffic AER handling itself generates: configuration reads and writes to the reporting function. On an analyzer, a burst of CfgRd to offsets in the AER capability right after an ERR_* message is the signature of the OS handling an error — useful when you are trying to align an analyzer capture with a kernel log.

Code / pseudocode

AER register and header decoder

Standard-library Python. Decodes Uncorrectable/Correctable status, mask and severity values, the First Error Pointer, and a 4-DW header log; flags errors that would be masked or fatal. With no arguments it runs on the synthetic values used in this chapter.

#!/usr/bin/env python3
"""Decode PCIe AER register values and a header log (teaching tool).
Usage: aer_decode.py UESTA UEMSK UESVRT CESTA CEMSK CAPCTL [HDR0 HDR1 HDR2 HDR3]
All values hex. With no arguments, decodes chapter 46's synthetic examples."""
import sys

UNC = {4: "DLP", 5: "SDES", 12: "PoisonedTLP", 13: "FCP", 14: "CmpltTO",
       15: "CmpltAbrt", 16: "UnxCmplt", 17: "RxOF", 18: "MalfTLP", 19: "ECRC",
       20: "UnsupReq", 21: "ACSViol", 22: "UncorrIntErr", 23: "MCBlockedTLP",
       24: "AtomicOpEgressBlocked", 25: "TLPPrefixBlocked",
       26: "PoisonedTLPEgressBlocked"}
COR = {0: "RxErr", 6: "BadTLP", 7: "BadDLLP", 8: "Rollover", 12: "ReplayTimerTimeout",
       13: "AdvNonFatalErr", 14: "CorrIntErr", 15: "HeaderLogOverflow"}
DEFAULT_SEVERITY = 0x00462030
FMT_TYPE = {(0b000, 0): "MRd32", (0b001, 0): "MRd64", (0b010, 0): "MWr32",
            (0b011, 0): "MWr64", (0b000, 0b01010): "Cpl", (0b010, 0b01010): "CplD",
            (0b000, 0b00100): "CfgRd0", (0b010, 0b00100): "CfgWr0"}

def bits(v, names):
    return [(b, names.get(b, f"bit{b}?")) for b in range(32) if v >> b & 1]

def decode_header(h):
    dw0, dw1, dw2, dw3 = h
    fmt, typ = dw0 >> 29 & 7, dw0 >> 24 & 0x1F
    length = dw0 & 0x3FF or 1024
    kind = FMT_TYPE.get((fmt, typ), f"Fmt={fmt:03b} Type={typ:05b}")
    if fmt >= 4:
        return "TLP prefix present: decode with the prefix rules"
    ep = dw0 >> 14 & 1
    out = f"{kind} Len={length} DW ({length * 4} B) EP={ep}"
    if kind.startswith(("MRd", "MWr")):
        req, tag = dw1 >> 16, dw1 >> 8 & 0xFF
        addr = (dw2 << 32 | (dw3 & ~3)) if fmt & 1 else (dw2 & ~3)
        out += f" Req={req:04X} ({req >> 8:02x}:{req >> 3 & 31:02x}.{req & 7}) Tag=0x{tag:02X} Addr=0x{addr:X}"
    elif kind.startswith("Cpl"):
        cpl, st = dw1 >> 16, dw1 >> 13 & 7
        req, tag = dw2 >> 16, dw2 >> 8 & 0xFF
        out += f" Completer={cpl:04X} Status={ {0:'SC',1:'UR',2:'CRS/RRS',4:'CA'}.get(st, st)} Req={req:04X} Tag=0x{tag:02X}"
    return out

def report(uesta, uemsk, uesvrt, cesta, cemsk, capctl, hdr=None):
    fep = capctl & 0x1F
    print(f"Uncorrectable status 0x{uesta:08X}  mask 0x{uemsk:08X}  severity 0x{uesvrt:08X}"
          + ("  (default severity)" if uesvrt == DEFAULT_SEVERITY else ""))
    for b, n in bits(uesta, UNC):
        sev = "FATAL" if uesvrt >> b & 1 else "non-fatal"
        msk = " MASKED (logged, not reported)" if uemsk >> b & 1 else ""
        first = " (First)" if b == fep else ""
        print(f"   [{b:2d}] {n:24s} {sev}{msk}{first}")
    print(f"Correctable status 0x{cesta:08X}  mask 0x{cemsk:08X}")
    for b, n in bits(cesta, COR):
        print(f"   [{b:2d}] {n:24s}" + (" MASKED" if cemsk >> b & 1 else ""))
    if hdr:
        if uesta >> fep & 1:
            print("Header log: " + decode_header(hdr))
        else:
            print("Header log: not valid (First Error Pointer bit not set in status)")

if __name__ == "__main__":

OS-first AER handling (pseudocode)

aer_irq(root_port rp) {
    rs  = cfg_read(rp, AER + 0x30);                 /* Root Error Status   */
    src = cfg_read(rp, AER + 0x34);                 /* Error Source ID     */
    cfg_write(rp, AER + 0x30, rs);                  /* RW1C clear          */
    if (rs & ERR_COR_RCVD)   handle(src & 0xFFFF, CORRECTABLE, rs & MULTI_COR);
    if (rs & ERR_FNF_RCVD)   handle(src >> 16, (rs & FIRST_UNC_FATAL) ? FATAL : NONFATAL,
                                    rs & MULTI_FNF);
}
handle(id, severity, multiple) {
    devs = multiple ? scan_below(rp, has_aer_status) : { dev(id) };
    for d in devs:
        log(d, read_status_mask_severity_fep_header(d));
        clear_status(d);
    if (severity != CORRECTABLE) recover(devs, severity);  /* callbacks, link reset */
}

Worked example

Given (synthetic): SSD AER registers read after an incident — UESta 0x0000_5000, UEMsk 0x0040_0000, UESvrt 0x0046_2030, CapCtl 0x0000_000E, Header Log 00000000 00000000 00000000 00000000; CESta 0x0000_0000. Root port: Root Error Status 0x0000_0024 (ERR_FATAL/NONFATAL Received + Non-Fatal Error Messages Received), Error Source ID 0x0100_0000.

  1. Uncorrectable status 0x5000 = bits 12 and 14: Poisoned TLP Received and Completion Timeout. Both non-fatal by the default severity.
  2. First Error Pointer = 0x0E = 14 → Completion Timeout came first. Header log is all zeros → this SSD does not log headers for Completion Timeouts (check CapCtl bit 12: 0x0E has bit 12 clear → not capable).
  3. Root port: non-fatal message received, source 31:16 = 0x0100 → the SSD. No "Multiple" bit, so likely a single report (the second error raised no new message because the OS had not yet cleared status — or reporting coalesced).
  4. Interpretation: the SSD waited too long for some completion from the host, and also received poisoned data. Both point upstream: the host side failed to complete one read in time and returned poisoned data for another (or for the same one, late). Prime suspect: host memory uncorrectable errors or a root complex internal problem. Check machine-check/EDAC logs at the same timestamp.
  5. NVMe side: expect one or two commands completed with Data Transfer Error, or a timeout if the SQE fetch itself was affected.

Common mistakes

  • Reading the header log without checking that the First Error Pointer's status bit is set.
  • Assuming Error Source ID names every reporter; check the "Multiple" bits.
  • Treating "(Requester ID)" in a Linux report as "the requester is guilty". It is a role label.
  • Changing severity to non-fatal to "fix" crashes: it hides the symptom and may let a broken link keep carrying traffic.
  • Masking correctable errors to silence logs and then losing the early warning of a degrading link.
  • Clearing status bits on a production system before capturing them.
  • Forgetting firmware-first: the OS shows GHES records, and registers may already be cleared.
  • Decoding the header with the wrong byte order (DWORDs are big-endian on the wire; Linux prints each DWORD as a 32-bit number in that order).

Senior engineer insight

  • Collect first, clear later. AER status is sticky so that it survives recovery. Your incident script should dump every AER register on the path (endpoint, switch ports, root port) before anything clears them.
  • Severity is policy. Changing it changes system behaviour (reset vs continue). Treat severity and mask changes as configuration under change control.
  • The header log is your free analyzer. A single 16-byte header often answers what a week of analyzer time would: who, what, where, how long.
  • Know who owns AER. On firmware-first platforms you must get logs from the BMC/firmware event log; asking the OS will get you an incomplete picture.
  • Correctable errors are a trend metric. Export them to monitoring as rates per device and per detecting end; alert on change, not on presence.

Are masks/severities at defaults? Any status bits set? Is the header valid?

Questions

Challenge

Write a script that dumps AER registers of every function under a root port into a timestamped JSON file, suitable for running from a udev rule or an incident hook.

Hint

Walk /sys/bus/pci/devices/*/ and use the config file (root) to read extended space; find capability 0001h from offset 0x100.

Solution

1. XOR with the default: set bits that are now 1 were promoted to fatal; bits now 0 that were 1 were demoted.

2. UR from enumeration probing; the SSD DMA-ing to an address the root complex rejected (as in this chapter's trace); a peer device's request routed through the root port. Check the header log.

3. Kernel log lines from _OSC negotiation (AER control granted or not), presence of GHES/APEI messages, and whether aer_dev_* counters ever move.

What a senior engineer notices

Non-default masks (someone silenced errors), AER absent on the endpoint (blind spot), and Multiple bits in Root Error Status (lost sources).

Failure variants

  • setpci reports "unknown capability": use the numeric extended capability offset from lspci (e.g. 0x100).
  • All reads 0xFFFFFFFF: function unreachable (link down or D3cold).

Exercises

  1. Decode UESta = 0x0010_4000 with default mask and severity.
  2. A root port's Root Error Status = 0x0000_005F. List every meaning.
  3. Decode header log 4A000001 01000004 00092000 00000000 (hint: a completion).
  4. Why would an OS set Severity bit 14 (Completion Timeout) to fatal on some platforms?
  5. Write the steps to determine whether a header log is stale.
Model answers

1. Bits 14 (Completion Timeout) and 20 (Unsupported Request), both non-fatal, both unmasked.

2. 0x5F = bits 0,1,2,3,4,6: ERR_COR received, multiple ERR_COR, ERR_FATAL/NONFATAL received, multiple F/NF, first uncorrectable was fatal, fatal messages received (bit 5, non-fatal messages, is 0).

3. DW0 0x4A00_0001: Fmt 010, Type 01010 → CplD, Length 1 DW. DW1 0x0100_0004: Completer ID 0x0100, Status bits 15:13 = 000 (SC), Byte Count 0x004. DW2: Requester ID 0x0009, Tag 0x20, lower address 0. A 4-byte completion from the SSD to the root complex — e.g. an Unexpected Completion logged at the root port for tag 0x20.

4. If the platform cannot tolerate the consequences of a timed-out read (e.g. a CPU read stall that the platform turns into data corruption risk), escalating to fatal forces containment/reset.

5. Read CapCtl FEP; check that bit is set in UESta; compare timestamps of the last kernel clear; if the bit was set long ago and never cleared, the header belongs to that older event.

Quiz

  1. AER's Extended Capability ID is

    • 0001h
    • 0011h
    • 0010h
    • 000Bh
    Answer and reasoning

    0001h. (11h is the MSI-X capability ID in the legacy list.)

  2. Which register determines whether an uncorrectable error is signalled as fatal?

    • Uncorrectable Error Mask
    • Root Error Command
    • Uncorrectable Error Severity
    • Device Status
    Answer and reasoning

    Severity bit = 1 → fatal.

  3. Setting a bit in the Uncorrectable Error Mask

    • Prevents the status bit from being set
    • Prevents reporting, but status is still logged
    • Changes it to correctable
    • Clears the header log
    Answer and reasoning

    Masked errors are recorded in status but not signalled (and do not update the header log).

  4. The First Error Pointer is found in

    • Root Error Status
    • Uncorrectable Error Status
    • Header Log DW0
    • Advanced Error Capabilities and Control
    Answer and reasoning

    Bits 4:0 of the register at +18h.

  5. Error Source Identification bits 31:16 hold

    • The ERR_COR source
    • The ERR_FATAL/NONFATAL source
    • The interrupt message number
    • The header DW0
    Answer and reasoning

    15:0 for ERR_COR, 31:16 for ERR_FATAL/NONFATAL.

  6. Default Correctable Error Mask is

    • 0x0000_0000
    • 0x0000_0041
    • 0x0000_E000
    • 0x0046_2030
    Answer and reasoning

    Advisory Non-Fatal, Corrected Internal and Header Log Overflow are masked by default.

  7. Why are AER status bits sticky?

    Model answer

    So that evidence survives the resets (hot reset, FLR) that error recovery performs, allowing post-mortem analysis.

  8. What does "Multiple ERR_FATAL/NONFATAL Received" tell you?

    Model answer

    More than one uncorrectable message arrived before software cleared the status; Error Source ID only records one; other sources must be found by scanning.

  9. What is firmware-first error handling and how does it change what you see?

    Model answer

    Platform firmware owns AER, handles and clears it, and reports to the OS via APEI/GHES; native AER messages may not appear and registers may be cleared already.

Interview questions

  1. Beginner: What does AER add over basic PCIe error reporting?

    Model answer

    Per-error status bits, masks, configurable severity, first error pointer, header log, and root port source identification.

  2. Intermediate: Walk through what happens from a device detecting a non-fatal error to the OS logging it.

    Model answer

    Device sets status, captures header if first; sends ERR_NONFATAL (if enabled/unmasked); root port records Root Error Status and Source ID and raises its AER interrupt; OS reads root and device registers, logs, clears (RW1C), and runs recovery callbacks.

  3. Intermediate: How do you decode a header log line from Linux?

    Model answer

    Treat the four words as DW0–DW3 of the TLP header: Fmt/Type/Length from DW0; Requester ID/Tag/BEs from DW1 for requests (Completer ID/status/byte count for completions); address from DW2/DW3.

  4. Advanced: A Linux report says "Uncorrected (Fatal) error message received from 0000:00:01.1" — the root port itself. What do you do?

    Model answer

    The root port detected the error (e.g. on its receiver). Decode its status and header: the header identifies the TLP and its requester (often the device below). Investigate that transaction and the link, not the root port silicon.

  5. Senior: Your fleet shows no AER errors at all for six months. Is that good news?

    Model answer

    Not necessarily. Verify AER ownership (firmware-first?), that endpoints implement AER, masks/severities, Device Control reporting enables, that the kernel AER driver is active, and that correctable-error messages aren't being suppressed. Then trust the silence.

Chapter summary

AER (Extended Capability 0001h) records uncorrectable errors (status 04h, mask 08h, severity 0Ch) and correctable errors (status 10h, mask 14h), with the First Error Pointer and ECRC controls at 18h and a four-DWORD Header Log at 1Ch. Root ports add Root Error Command (2Ch), Root Error Status (30h) and Error Source Identification (34h). Masks suppress reporting but not logging; severity decides fatal vs non-fatal; status bits are sticky and write-1-to-clear. Linux prints the source, class, layer, role, status/mask, decoded bits, "(First)" and the TLP header, and keeps per-device counters. The header log identifies the transaction; reasoning decides whether it was cause or victim.

  • use the First Error Pointer to validate a header log
  • decode a header log into a TLP and match it to an NVMe transaction
  • explain root port Root Error Status and Error Source ID, including "Multiple"
  • read a Linux AER report line by line and state what it cannot prove
  • determine whether the OS or firmware owns AER on a platform
