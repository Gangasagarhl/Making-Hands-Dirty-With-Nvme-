Chapter 14 taught that posted writes stay in order and that this is what makes a completion trustworthy. This advanced chapter takes the whole Peripheral Component Interconnect Express (PCIe) ordering rules matrix apart cell by cell, shows which cells exist for correctness and which for deadlock freedom, and then applies Relaxed Ordering and ID-Based Ordering to the specific write sequence an NVMe controller produces: data, then completion queue entry, then interrupt. It ends with the bug patterns that ordering mistakes actually produce in the field.

Why this chapter exists

An NVMe host never checks that data has arrived. It sees a completion queue entry (CQE) with the right phase tag and trusts that the data buffer is complete. That trust rests on PCIe ordering rules, on the Root Complex's implementation of them, on the device not setting the wrong attribute bits, and on the CPU-side memory barriers in the driver. When any link of that chain fails, the result is the most expensive kind of bug: silent data corruption that appears only under load, only on some platforms.

Ordering also has a second job that is easy to forget: preventing deadlock. Half of the ordering table says "this must be allowed to pass that", not "this must stay behind that". Engineers who only remember the "must not pass" entries design switches, bridges and endpoints that hang.

Learning objectives

  • Reconstruct the PCIe ordering rules summary (row passes column) for posted requests, non-posted requests and completions, and justify every entry as either a correctness rule, a deadlock-avoidance rule or a freedom.
  • Explain the producer–consumer guarantee and map it onto NVMe's data → CQE → MSI-X sequence and onto the host's SQE → doorbell sequence.
  • Explain exactly what Relaxed Ordering (RO) and ID-Based Ordering (IDO) relax, who may set them, and which NVMe transactions may safely carry them.
  • Explain the deadlock scenarios that the "must be able to pass" entries prevent.
  • Separate PCIe fabric ordering from Root Complex internal ordering and from CPU memory ordering, and know where each one is defined.
  • Identify ordering violations in a trace and recognize the main field bug patterns.

The story

The librarian sends three things down the same slide to the teacher's desk: first the books, then a note saying "your books are here", then she rings a little bell. Because they all go down the same slide, they land in that order, so when the teacher hears the bell, the note is already there, and when she reads the note, the books are already there. But imagine the librarian put the note in a special "express" envelope that is allowed to jump ahead on the slide. The teacher could read "your books are here" — and find an empty desk.

There is a second rule on the slide: if someone's big box gets stuck waiting for an answer, the small letters behind it must be allowed to slip past. Otherwise everybody waits for everybody and nothing ever moves.

A hospital pneumatic-tube system. The lab sends test results (data), then a "results posted" slip (CQE), then pages the doctor (interrupt). Doctors trust the page because the tube is first-in, first-out. Some tubes are marked "urgent — may overtake": fine for independent samples, disastrous for the "results posted" slip. Meanwhile, requests for new samples (non-posted reads) must never block the deliveries the lab is waiting on, or the whole system jams.

A tube system is one physical channel. PCIe has separate buffers and credits for posted, non-posted and completion traffic, multiple Virtual Channels with no ordering between them, switches that merge traffic from many sources, and a Root Complex that turns TLPs into memory-system operations under its own (CPU-architecture-specific) ordering rules. The analogy also hides that CPU stores to host memory are not PCIe transactions at all — they need CPU barriers, not PCIe rules.

Beginner explanation

Every Transaction Layer Packet (TLP) belongs to one of three ordering classes:

  • Posted requests — Memory Writes and Messages. No reply.
  • Non-posted requests — Memory Reads, I/O and Configuration requests, AtomicOps. They expect a completion.
  • Completions — replies to non-posted requests.

For traffic going the same direction through the same path, in the same Traffic Class, the PCIe specification gives a table: for each pair (a later TLP of class X, an earlier TLP of class Y), may X overtake Y? The answer is one of: No (must not pass — needed for correctness), Yes (must be allowed to pass — needed to avoid deadlock), or Y/N (may or may not; no requirement).

Two attribute bits in the TLP header can turn some "No" entries into "Y/N": Relaxed Ordering and ID-Based Ordering. They exist for performance. Used on the wrong TLP, they break correctness.

The single most important consequence for NVMe: a posted write must not pass an earlier posted write (unless relaxed). The controller writes data, then the CQE, then the MSI-X interrupt — all posted writes, in that order — so the host can trust the CQE once it sees it, and the interrupt once it arrives.

Engineering explanation

Scope: what the rules order, and what they do not

  • Rules apply to transactions in the same direction through the same path — for example, everything an endpoint sends upstream through the same ports. Requests going down and completions coming up are different streams.
  • Rules apply within a Traffic Class (TC). There is no ordering between different TCs, which may map to different Virtual Channels (VCs). An NVMe SSD normally uses TC0 for everything.
  • Rules are about what an observer downstream of a point can see. Inside the Root Complex, the PCIe rules hand over to the platform's memory-ordering model.
  • Rules say nothing about CPU loads and stores to cacheable host memory (the SQ entries the driver writes, the CQ entries the driver reads). That ordering belongs to the CPU architecture and is enforced with barriers.

Read the table as three groups.

Correctness entries ("No")

  • A2a — a write must not pass an earlier write. This is the producer–consumer rule: data then flag.
  • B2a / C2a — a read (or non-posted write) must not pass an earlier posted write. This makes "a read flushes earlier writes" true: when the completion of a read returns, all writes the requester sent earlier in the same direction have reached the completer. Drivers rely on this when they read a device register to make sure their MMIO writes landed.
  • D2a — a completion must not pass an earlier posted write. Consider a device that writes data to memory and then answers a host's read of a status register: the host must not see "done" in the completion before the data writes have been pushed ahead of it.
  • D5b — completions for the same request stay in increasing address order (see Chapter 52).

Deadlock-avoidance entries ("Yes")

  • A3 / A4 — posted writes must be able to pass non-posted requests.
  • D3 / D4 — completions must be able to pass non-posted requests.

The reasoning is about buffers. A non-posted request can be stuck because the completer has no room to accept it or because it is waiting for its own resources. If posted writes and completions were stuck behind it, and the thing the completer is waiting for is one of those writes or completions, nobody moves. Making posted and completion traffic always able to pass non-posted traffic breaks every such cycle. This is also why flow control keeps separate credits for posted, non-posted and completion traffic (Chapter 16, Chapter 53).

Freedoms ("Y/N")

  • B3/B4/C3/C4 — non-posted requests may be reordered among themselves; a completer may service reads out of order.
  • B5/C5 — requests may pass completions or not.
  • D5a — completions for different requests may return in any order. A requester must match completions by Tag and must not assume the order in which it issued reads.
  • A5a — writes may pass completions or not.

A "Y/N" entry is a freedom for the fabric and therefore an obligation for the receiver: any design that works only if a Y/N case happens to be ordered is relying on implementation luck. Many "works on platform A, fails on platform B" bugs are exactly that.

A deadlock, constructed

Imagine a (non-compliant) switch that keeps a single first-in-first-out queue per port for all TLP types.

  1. Endpoint E1 sends many Memory Read requests to E2 (peer-to-peer). They fill E2's non-posted receive buffer and back up into the switch queue toward E2.
  2. E2 cannot accept more reads until it has returned completions for the ones it has. Its completions go to E1.
  3. E1's receive path from the switch is also a single queue, now holding posted writes from the host that are ahead of E2's completions; E1 cannot drain those writes because its internal write path is blocked behind its own outgoing reads waiting in the full switch queue.
  4. Cycle: E1 waits for E2's completions, which wait behind posted writes to E1, which wait for E1's internal resources, which wait for E1's reads to drain, which wait for E2.

The PCIe rules make this impossible in a compliant fabric: separate per-class buffering and credits, plus "posted and completions may always pass non-posted", ensure that completions and posted writes keep flowing even when non-posted traffic is stalled. A related rule: requesters must have space for the completions they solicit (endpoints and Root Complexes typically advertise "infinite" completion credits, meaning they promise to accept them). Uncertain — check the exact completion-credit advertisement rules in "Flow Control" of your revision.

The producer–consumer model and NVMe

The ordering rules exist to support one programming model: a producer writes data, then writes a flag; a consumer that sees the flag must see the data. PCIe guarantees this when producer, data, flag and consumer are arranged according to the rules (the specification has an informative appendix discussing producer–consumer configurations). Relaxed Ordering precisely

Relaxed Ordering is TLP attribute bit Attr[1]. A requester may set it only if Enable Relaxed Ordering is set in its Device Control register. A completer copies the request's RO bit into its completions.

  • A posted request with RO = 1 may pass earlier posted requests (A2b). Important: RO describes the later TLP. A CQE write with RO = 0 cannot pass earlier data writes even if those data writes had RO = 1.
  • A completion with RO = 1 may pass earlier posted requests (D2b).
  • RO does not let anything pass a non-posted request in a way it couldn't already, and does not affect D5b.

Why use it? In the Root Complex, strictly ordered writes to memory can serialize behind cache-coherency operations; letting independent data writes complete out of order raises write bandwidth on some platforms. For an NVMe controller, the safe policy is:

ID-Based Ordering precisely

ID-Based Ordering is Attr[2]. It relaxes ordering between TLPs from different sources: a TLP with IDO = 1 may pass an earlier TLP with a different Requester ID (for requests) or different Completer ID (for completions), in the cells marked "with IDO" (A2b, B2b, C2b, D2b). Same-source traffic stays ordered. Enabling bits: IDO Request Enable and IDO Completion Enable in Device Control 2.

Why it exists: in a switch, traffic from SSD 1 should not have to wait behind traffic from SSD 2 — they are unrelated producers. IDO lets fabrics avoid this head-of-line blocking while keeping each source's own producer–consumer ordering intact.

IDO assumes that each producer–consumer relationship is contained within one source ID. With SR-IOV (Chapter 56), every Virtual Function has its own Requester ID. That is fine as long as each VF's data, CQE and MSI-X carry the same VF's Requester ID. A device that, for example, sends data with a VF's ID but a CQE or interrupt with the Physical Function's ID breaks IDO's assumption — the CQE could pass the data. Validate that the IDs on data, CQE and MSI-X match.

No Snoop is not an ordering attribute

Attr[0], No Snoop, tells the Root Complex the transaction need not be snooped against CPU caches. It does not change PCIe ordering rules, but it changes visibility: data written with No Snoop may not be coherent with CPU caches unless software manages them. NVMe drivers on coherent platforms generally rely on snooped DMA; a CQE written with No Snoop could be invisible to a CPU spinning on a cached copy. Treat No Snoop as "visibility risk", not "ordering risk".

Where PCIe ordering ends: the Root Complex and the CPU

On strongly ordered CPUs (x86 for normal loads), the CPU-side barrier is mostly a compiler barrier. On weakly ordered CPUs (Arm, POWER, RISC-V), the driver must order the phase-tag load before the loads of the CQE's command identifier and status, and before the application reads the data. Linux's NVMe driver uses a read barrier after detecting a valid phase tag for this reason.

In the other direction, the driver stores the SQE in normal memory and then writes the doorbell. On weakly ordered CPUs the MMIO write could otherwise become visible to the device before the SQE store is visible to the device's coherent read. Linux's writel() includes the barrier that orders prior normal-memory stores before the MMIO write; the relaxed variant (writel_relaxed()) does not.

Atomicity and granularity of a single write

A 16-byte CQE is one MWr TLP. The host's phase-tag check assumes the entire entry becomes visible no later than its phase-tag bit. PCIe has rules about update ordering and granularity, and Root Complexes typically commit a small aligned write as one unit, but this is a platform property. Uncertain — read the PCIe Base Specification's discussion of update ordering and granularity, and your platform's documentation, rather than assuming atomicity beyond what is stated.

The ladder for "CQE implies data"

The books, the note and the bell go down the same slide in order, so the bell means the note is there and the note means the books are there.

The controller writes data, then the CQE, then MSI-X; posted writes keep their order; the host trusts the CQE without checking the data.

The controller's DMA engines must emit TLPs in that order onto the link; switches keep per-class FIFO order; the Root Complex commits them to coherent memory in order; the CPU orders its loads after the phase check.

PCI Express Base Specification ordering rule A2a (posted must not pass posted unless RO/IDO conditions), Relaxed Ordering and IDO definitions, producer–consumer discussion; NVMe: completion queue entry posting semantics.

Sequence of MWr TLPs from Requester ID 0x0100: data (Attr RO may be 1), CQE (RO = 0), MSI-X (RO = 0), all TC0.

On an analyzer: check the CQE TLP's Attr field and that it follows the last data TLP for that command; check the MSI-X write follows the CQE; check Requester IDs match.

If the host sees stale data, find the first TLP whose ordering or attributes permit a reordering the host relies on; then check platform RO handling and the driver's barriers.

The sixteen questions, applied to Relaxed Ordering

1. What is it?
A TLP attribute (Attr[1]) that permits a posted request or completion to pass earlier posted requests.
2. Why was it created?
To let independent writes and completions avoid unnecessary serialization in fabrics and Root Complexes.
3. What problem does it solve?
Head-of-line blocking and memory-write throughput limits caused by strict ordering.
4. What existed before it?
PCI-X introduced Relaxed Ordering; conventional PCI had strict ordering for posted writes.
5. Why is the current design better?
It is per-TLP, chosen by the requester who knows which writes are independent, and gated by an enable bit software controls.
6. Who creates it?
The requester (device DMA engine or Root Complex) sets it; completers copy it into completions.
7. Who consumes it?
Switches, Root Complexes and completers that may reorder.
8. Where does it live?
In the TLP header Attr field; the enable is in Device Control.
9. What memory/registers are involved?
Device Control (Enable Relaxed Ordering), the TLP header, the host buffers being written.
10. What happens before it?
Software enables (or disables) RO for the function; the device decides per TLP.
11. What happens after it?
The fabric or Root Complex may commit RO TLPs out of order relative to earlier posted writes.
12. What happens if it is wrong?
On the flag (CQE, MSI-X): silent data corruption or spurious interrupts. On platforms with errata: corruption or slowdowns.
13. What does the protocol analyzer show?
The RO bit in each TLP's Attr field; the order of TLPs on the link (which does not reveal Root Complex internal reordering).
14. What does Linux show?
RlxdOrd+/- in DevCtl from lspci; quirk-related kernel messages on affected platforms.
15. What would a validation engineer test?
Attr bits per TLP class under all command types; data integrity with RO enabled on platforms known to reorder; RO disabled path performance.
16. What would a senior engineer suspect when it fails?
RO on the CQE/MSI-X, platform errata, or a driver barrier missing on a weakly ordered CPU masquerading as an RO problem.

Hardware view

Ordering is implemented by queues and by the rules that choose which queue head may go next.

  • Endpoints (the SSD): ordering must hold from the point where the controller's firmware decides "command done" to the link. Many controllers have several DMA engines (data, CQE, interrupt); they need an internal ordering point — often a single posted-write queue toward the PCIe core, or explicit fences — so the CQE TLP cannot leave before the last data TLP.
  • Switches merge traffic from many ports. IDO lets them reorder between different sources; without it, a slow destination for one source can stall unrelated sources' writes.
  • Root Complexes turn each MWr into coherent memory operations. Maintaining strict write ordering often means waiting for each write's coherency to resolve before making the next visible. RO lets the Root Complex pipeline these. That is where RO's performance benefit — and its risk — lives.
  • The Data Link Layer replays TLPs in sequence-number order after errors, so link errors do not reorder TLPs (Chapter 15).

Specification view

Documents: PCI Express Base Specification, Revision 6.x/7.0 — Transaction Ordering (Ordering Rules Summary; Relaxed Ordering and ID-Based Ordering usage; Update Ordering and Granularity); appendix discussion of producer–consumer ordering; NVM Express Base Specification 2.4 — Completion Queue Entry; Command completion; NVMe over PCIe Transport Specification 1.4.

Posted requests must not pass earlier posted requests unless relaxed by RO or IDO conditions; reads must not pass earlier posted requests; completions must not pass earlier posted requests unless relaxed; posted requests and completions must be allowed to pass non-posted requests; completions of the same request are returned in address order. RO is Attr[1] gated by Enable Relaxed Ordering in Device Control; IDO is Attr[2] gated by IDO enables in Device Control 2; No Snoop is Attr[0]. There is no ordering requirement between different Traffic Classes.

For NVMe: the controller must not set RO (or rely on IDO with mismatched IDs) on CQE and MSI-X writes; the host's correctness additionally depends on the Root Complex honoring ordering into memory and on driver barriers. Peer-to-peer DMA between NVMe devices and other endpoints inherits the same producer–consumer reasoning, with the added complexity of the path through switches and ACS redirection.

Whether a given switch or Root Complex actually reorders RO or IDO traffic, how a Root Complex commits writes to memory, whether a device's DMA engines are internally ordered, and which TLPs a device marks with RO are implementation-dependent. An analyzer on the link cannot see Root Complex internal reordering.

RO came from PCI-X and is present from PCIe 1.0. IDO was added in the 2.1 era. Flit Mode (6.0) changed the TLP header format (the attribute bits are carried differently), so decode attributes with the right header format for the link mode. Some sub-entries of the ordering table were refined across revisions.

The PCIe specification does not define how a CPU observes memory, or what barriers a driver needs. The NVMe specification does not say which TLP attributes a controller should use. Check in the specs: the current wording of each ordering-table sub-entry; MSI/MSI-X attribute requirements; the update-granularity rules for a single multi-DWORD write; and any NVMe over PCIe Transport statements about write ordering.

Never assume: that completions return in the order reads were issued; that TLPs in different Traffic Classes are ordered; that "the analyzer shows the CQE after the data" means the CPU saw them in that order (RO and Root Complex behaviour matter); that x86 behaviour proves a driver correct on Arm.

Linux view

# Relaxed Ordering and No Snoop enables (DevCtl), IDO enables (DevCtl2)
sudo lspci -vvv -s 01:00.0 | grep -E 'DevCtl:|RlxdOrd|NoSnoop|DevCtl2:|IDO'

# Same for the Root Port: platform policy is visible here too
sudo lspci -vvv -s 00:01.1 | grep -E 'DevCtl:|DevCtl2:'

# Kernel messages from relaxed-ordering quirks on affected platforms (wording varies)
sudo dmesg | grep -i 'relaxed ordering'

The PCI core has a per-device flag marking Root Ports whose Relaxed Ordering handling is problematic; during enumeration, devices below such a port get Enable Relaxed Ordering cleared in Device Control (see pci_configure_relaxed_ordering() and the related quirks in drivers/pci). Drivers that care can ask pcie_relaxed_ordering_enabled(). On the CPU side, the NVMe driver relies on writel() ordering for doorbells and uses a read barrier after detecting a valid phase tag when processing CQEs. Exact code is Version-dependent; read drivers/nvme/host/pci.c for your kernel.

What Linux output proves: whether the function is allowed to use RO/NS/IDO. It does not prove which TLPs the device actually marks — only an analyzer shows that.

Expert lab Clearing Enable Relaxed Ordering with setpci on a test machine is a valid experiment for the abnormal case above; it is reversible but bypasses the kernel's view of the device and must not be done on production systems.

Code / pseudocode

A Monte Carlo model of a Root Complex that may commit RO writes early. It counts how often a consumer sees the CQE before all data — with RO on the CQE and without.

#!/usr/bin/env python3
"""Model: posted writes arrive in order; an RO write may become visible before
earlier writes; a non-RO write becomes visible only after all earlier writes."""
import random

def run(cqe_ro, data_chunks=16, trials=20000, seed=7):
    rng = random.Random(seed)
    writes = [("data", True)] * data_chunks + [("cqe", cqe_ro), ("msix", False)]
    bad_cqe = 0
    for _ in range(trials):
        visible = [False] * len(writes)
        while not all(visible):
            eligible = [i for i, (_, ro) in enumerate(writes)
                        if not visible[i] and (ro or all(visible[:i]))]
            i = rng.choice(eligible)
            visible[i] = True
            if writes[i][0] == "cqe" and not all(visible[:data_chunks]):
                bad_cqe += 1          # consumer could read stale data now
                break
    return bad_cqe / trials

if __name__ == "__main__":
    print(f"CQE RO=0: stale-data window in {run(False):.2%} of commands")
    print(f"CQE RO=1: stale-data window in {run(True):.2%} of commands")

Expected result: 0.00% with RO = 0 on the CQE; a large percentage with RO = 1, because the model lets RO writes become visible at any time (a real Root Complex reorders far less often — which is why the real bug appears at one in a billion, not one in two).

The host-side half of the contract, as C pseudocode in Linux style:

void submit(struct queue *q, const struct sqe *cmd)
{
    memcpy(&q->sq[q->tail], cmd, 64);       /* normal cacheable stores */
    q->tail = (q->tail + 1) % q->depth;
    writel(q->tail, q->sq_doorbell);          /* writel orders prior stores before MMIO */
    /* writel_relaxed() here would be a bug on weakly ordered CPUs */
}

int poll_cq(struct queue *q)
{
    int n = 0;
    while ((READ_ONCE(q->cq[q->head].status) & 1) == q->phase) {
        dma_rmb();                            /* order phase load before other CQE loads */
        complete_cmd(q->cq[q->head].command_id, q->cq[q->head].status >> 1);
        if (++q->head == q->depth) { q->head = 0; q->phase ^= 1; }
        n++;
    }
    if (n)
        writel(q->head, q->cq_doorbell);      /* release CQ slots */
    return n;
}

Common mistakes

  • Reading only the "No" cells and treating "Yes" as "may".
  • Thinking RO on an earlier TLP lets a later non-RO TLP pass it. RO is a property of the TLP that wants to pass.
  • Assuming read completions come back in issue order.
  • Treating link order as memory-visibility order (RO and Root Complex internals).
  • Applying PCIe rules to CPU stores and loads (the SQE write, the CQE read). Those need CPU barriers.
  • Assuming ordering across Traffic Classes.
  • Confusing No Snoop with Relaxed Ordering.
  • Testing ordering-sensitive firmware only on platforms that never reorder.

Senior engineer insight

Ordering bugs are invisible to anyone who only checks TLP order. The decisive evidence is often an attribute bit, a Requester ID, a platform property, or a CPU barrier — none of which show up as "out of order" on the wire. A senior review of a controller's DMA design asks: where is the single ordering point before the link, which TLP classes carry RO/IDO, and how is that verified on an RO-exploiting platform?

  • RO is a performance feature whose benefit depends on the Root Complex; measure before enabling it in firmware, and never on flags.
  • Data integrity validation must include platforms that exploit RO and weakly ordered CPUs; x86-only validation hides whole classes of bugs.
  • When reviewing switch or bridge designs, ask how deadlock freedom is guaranteed — "we never saw a hang" is not evidence.
  • For SR-IOV and multi-function devices, verify that every producer–consumer pair uses one Requester ID if IDO is enabled.

Lab: ordering audit of an NVMe completion path

Objective

Determine, from configuration and (optionally) analyzer data, whether a device's completion path is safe with respect to RO and IDO, and quantify the hazard with the simulator.

Skills

Ordering-table reasoning, attribute decoding, separating fabric ordering from CPU ordering.

Safety

Steps 1–3 Safe lab. The optional RO-disable experiment is Expert lab and is not required.

Hardware required

Any Linux machine with an NVMe SSD. Optional: PCIe analyzer.

Software required

pciutils, Python 3.

Input

lspci output for the SSD and its Root Port; the simulator; the synthetic traces in this chapter.

Expected output

A one-page ordering audit: enables (RO, NS, IDO) on device and port, which NVMe TLP classes may carry them, the hazard if CQE/MSI-X carried RO, and a recommendation.

Background

Ordering table, RO/IDO sections, NVMe producer–consumer table.

Step 1

Record DevCtl RlxdOrd/NoSnoop and DevCtl2 IDO bits for the SSD and the Root Port. Check dmesg for relaxed-ordering quirk messages.

Step 2

Run ro_ordering_sim.py. Modify it so that RO writes become visible early only with probability 0.001 per opportunity, and estimate the failure rate per command.

Step 3

Using the abnormal trace, write the root-cause statement, corrective action and regression test in the root-cause template (Debugging Methodology).

Observation

How does the per-command failure rate scale with the number of data chunks per command?

Questions

  1. If RlxdOrd is "-" on your SSD, can the CQE RO bug occur?
  2. Why can't an analyzer on the SSD's link prove the Root Complex reordered writes?
  3. Which CPU-side mistakes would produce symptoms similar to RO misuse?

Challenge

Extend the simulator with two Requester IDs and IDO, and show the hazard when data uses one ID and the CQE another.

Hints

A requester may set RO only if enabled. Analyzers see link order, not memory visibility. Look at the barriers in submit/poll pseudocode.

Solution

Q1: A compliant device must not set RO when Enable Relaxed Ordering is clear, so no — unless the device is non-compliant (worth checking on an analyzer). Q2: the link shows TLP order before the Root Complex; reordering happens inside the Root Complex's commit to memory, which the analyzer cannot observe — only the effect (stale data) is visible. Q3: missing read barrier after the phase check (reading CQE fields or data early) and missing write barrier before the doorbell (stale SQE). Challenge: give each write a source ID; with IDO, a write may become visible early if all earlier writes it has not yet passed have a different ID; show that a CQE with a different ID from the data now behaves like RO = 1.

What a senior engineer notices

Whether RO is enabled on a platform with known RO issues, whether the device's documentation states which TLPs use RO, and whether validation includes a weakly ordered host.

Failure variants

  • RO enabled by BIOS on the device but disabled on the Root Port: the device may still emit RO TLPs; what the port does with them depends on the platform.
  • IDO enabled without SR-IOV: effectively harmless for one function with one ID.

Extension

Capture a real read workload on an analyzer and build a per-address-range histogram of Attr bits (data buffers vs CQ ring vs MSI-X window).

Exercises

  1. For each "Yes" entry in the table, describe a concrete deadlock that would occur without it.
  2. A device issues MRd tags 1, 2, 3 and receives CplDs 3, 1, 2. Which rule permits this, and what must the device do?
  3. A driver reads CSTS after writing a doorbell to "make sure the doorbell landed". Which rule makes this work, and what does it not guarantee?
  4. Why is RO on Write-command data fetches (MRd from the device) generally harmless for NVMe?
  5. Explain the difference between "the CQE must not pass the data" and "the CPU must not read the data before the CQE".
Answers

1. A3/A4: posted writes stuck behind a non-posted request whose completer waits for those writes (or for buffer space freed by them) — e.g. a bridge forwarding reads that cannot complete until its posted buffer drains. D3/D4: completions stuck behind non-posted requests at a port where the requester of those non-posted requests waits for the completions to free resources — the peer-to-peer example in the chapter.

2. D5a: completions for different Transaction IDs may pass each other. The device must match completions by Tag (and Requester ID) and place data by the request's address, not by arrival order.

3. B2a: the read cannot pass the earlier posted write, so by the time the controller produces the read completion, the doorbell has arrived. It does not guarantee the controller has processed the doorbell (fetched the SQE) — only that the write reached it.

4. RO on the read request is copied to its completions, allowing them to pass host→device posted writes (doorbells, register writes). NVMe does not use the relative order of a doorbell and a data completion to validate data; the data was produced by the CPU before the command was submitted, so no producer–consumer pair is broken.

5. The first is a fabric/Root Complex property (PCIe ordering, RO usage). The second is a CPU load-ordering property, enforced by the driver's read barrier after the phase check. Both are needed.

Quiz

  1. "May a later Memory Read pass an earlier posted Memory Write in the same direction?" (no IDO)

    • Yes, must be allowed
    • No

    • D5b
    • A3/A4 and D3/D4
    • B3/B4
    Answer and reasoning

    Posted and completions must be able to pass non-posted.

    • Yes
    • Only across different TCs
    • Only if No Snoop is set
    Answer and reasoning

    RO applies to the passing TLP; the CQE has RO = 0, so A2a forbids passing.

  4. Which attribute bit is ID-Based Ordering?

    • Attr[0]
    • Attr[1]
    • TH
    • Attr[2]
    Answer and reasoning

    Attr[2] is IDO; Attr[1] RO; Attr[0] No Snoop.

  5. Two completions for the same read request — may the second pass the first?

    • Yes
    • No
    • Y/N
    • Only with RO
    Answer and reasoning

    D5b: same Transaction ID completions stay in address order.

  6. Why can't an analyzer on the endpoint link alone prove a CQE was visible before its data in memory?

    Model answer

    The analyzer sees link order. Visibility in memory is decided by the Root Complex after the link, and RO allows it to reorder; the CPU's load order adds a third domain.

  7. What CPU-side mechanism orders the SQE store before the doorbell MMIO write in Linux?

    Model answer

    The ordering semantics of writel(), which includes the necessary write barrier on weakly ordered architectures; writel_relaxed() does not.

  8. Is ordering guaranteed between TC0 and TC1 traffic?

    Model answer

    No. Ordering rules apply within a Traffic Class; different TCs may map to different VCs with independent arbitration.

  9. Give the safe RO policy for an NVMe controller.

    Model answer

    RO may be set (if enabled) on read-data writes and on read requests for SQEs, PRP/SGL lists and write data; never on CQE writes or MSI-X writes.

Interview questions

  1. Beginner: What are the three ordering classes in PCIe?

    Model answer

    Posted requests, non-posted requests (reads and non-posted requests with data), and completions.

  2. Beginner: Why does an NVMe host trust the CQE?

    Model answer

    Because the controller writes data before the CQE, posted writes keep their order on PCIe, and the Root Complex makes them visible in order — so a visible CQE implies visible data, given correct driver barriers.

  3. Intermediate: What does Relaxed Ordering relax?

    Model answer

    It lets a posted request or completion carrying RO pass earlier posted requests (A2b, D2b). It requires Enable Relaxed Ordering; completers copy RO from the request.

  4. Intermediate: Why must completions be able to pass non-posted requests?

    Model answer

    Non-posted requests can block waiting for resources; if completions (which free those resources) were stuck behind them, the system could deadlock. Separate credit classes plus the passing rule prevent it.

  5. Advanced: Explain IDO and a scenario where it breaks NVMe correctness.

    Model answer

    IDO lets TLPs from different source IDs reorder. If a device sends data with a VF's Requester ID and the CQE with the PF's ID while IDO is enabled, the CQE may pass the data. Correct designs keep each producer–consumer pair within one ID.

  6. Advanced: A storage team sees corruption only on Arm servers. Ordering hypotheses?

    Model answer

    Missing CPU barriers: relaxed MMIO before doorbell (stale SQE fetch) or missing read barrier after phase check. Also platform RO handling differences. Check driver code paths, compare analyzer-captured SQE data with logged commands, and test with barriers added.

  7. Senior: Review a controller DMA design with three engines (data, CQE, MSI-X). What do you ask?

    Model answer

    Where is the ordering point before the PCIe core? Can a CQE be enqueued before the last data TLP has been handed to the core? Which TLPs carry RO/NS/IDO and under which enables? How do Requester IDs work with SR-IOV? How is this verified (analyzer checks on attributes and order, RO-exploiting platform stress, weakly ordered host)?

  8. Senior: Is it ever right to enable RO on a data-center NVMe fleet?

    Model answer

    Yes, if measurements show a throughput benefit on the target Root Complex, the device uses RO only on data, the platform has no RO errata (or the kernel quirk handles them), and validation proves data integrity under stress. Otherwise the benefit is not worth the risk; the default should be evidence-driven.

Chapter summary

The PCIe ordering table has correctness entries (posted must not pass posted; reads and completions must not pass posted; same-request completions stay ordered), deadlock-avoidance entries (posted and completions must be able to pass non-posted) and freedoms (non-posted among themselves; completions of different requests). NVMe relies on the producer–consumer guarantee for data → CQE → MSI-X, plus CPU barriers for SQE → doorbell and phase → payload. Relaxed Ordering (Attr[1]) and ID-Based Ordering (Attr[2]) relax specific "No" cells for performance; they are safe on data and fatal on flags. Most real ordering bugs are invisible in TLP order: they hide in attribute bits, Requester IDs, Root Complex behaviour and driver barriers.

Do not move on until you can:

  • reproduce the ordering table and classify every cell as correctness, deadlock-avoidance or freedom
  • construct a deadlock that the "Yes" cells prevent
  • state exactly which cells RO and IDO relax and who may set them
  • give the safe RO policy for NVMe controller traffic
  • separate fabric, Root Complex and CPU ordering domains
  • find an ordering bug in a trace where TLP order looks correct
  • cite the PCIe Base specification sections by name
