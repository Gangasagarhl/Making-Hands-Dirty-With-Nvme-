Admin commands are how a host discovers, builds, configures, watches and maintains an NVMe controller. This chapter gives you the admin opcode map, a deep tour of the commands every driver and every validation engineer uses — Identify, Get Log Page, Set and Get Features, Abort, Asynchronous Event Request, the firmware, namespace, format, sanitize and security commands — and the order in which a driver sends them to bring a controller to life.

Why this chapter exists

After a reset, an NVMe controller has exactly one pair of queues: the admin Submission Queue and admin Completion Queue whose addresses the host programmed into the ASQ and ACQ registers (Admin Queue). It has no I/O queues, the host knows nothing about its capabilities beyond the CAP register, and no namespace has been discovered. Everything that turns this blank controller into a working block device happens through admin commands.

Admin commands also carry most of what a validation, field-support or reliability engineer cares about after bring-up: health and error logs, firmware updates, namespace layout, secure erase and security protocols, self-tests and asynchronous notifications. When something goes wrong in the field, the evidence you will be given is usually the output of admin commands. Knowing exactly what each command asks and what it returns is how you tell a real device problem from a misread log.

Learning objectives

  • Recall the admin opcode table and know which values you can state with confidence and which to confirm in the specification.
  • Explain Identify and its Controller or Namespace Structure (CNS) selector, and name what CNS 00h, 01h, 02h and 03h return.
  • Build Get Log Page, Set Features and Get Features commands field by field, including the 0's based dword count, offset, select and save fields.
  • Explain how Abort and Asynchronous Event Request work, why both are "best effort" or "parked" commands, and how to read their completion Dword 0.
  • Describe the firmware update flow (Firmware Image Download then Firmware Commit), namespace management and attachment, Format NVM, Sanitize and Security Send/Receive at the level a validation engineer needs.
  • Write down the controller initialisation sequence from CC.EN = 0 to the first I/O command, and recognise it in a PCIe trace.
  • Diagnose common admin failures: queue creation order, wrong queue sizes, invalid log pages, unsupported features.

Prerequisites

You need the 64-byte SQE / 16-byte CQE layout and the Status Field from NVMe Command Structure; controller registers CAP, CC, CSTS, AQA, ASQ, ACQ from NVMe Registers; the admin queue from Admin Queue; I/O queue pairs from I/O Queues; and the idea of a namespace from NVMe 2.x Architecture.

The story

The library has two kinds of request slips. The ordinary ones ask the librarian for books. The special ones go into a separate box on the head librarian's desk and ask about the library itself: "Tell me about yourself." "Which sections are open?" "Please set up a new request box for my class." "Show me your diary of problems." "Here is a new rulebook, please learn it." "Wipe this section clean." "Call me if anything important happens."

That last slip is special: the head librarian keeps it in her pocket and only answers when something actually happens — maybe hours later.

An adult version: the facilities desk of a large office building. Tenants (I/O) use the lifts and rooms all day; the facilities desk handles the meta-work — issuing the building directory, assigning floors, setting thermostats, reading the incident log, upgrading the access-control firmware, deep-cleaning a vacated floor, and paging the tenant's on-call contact when an alarm goes off. There is one facilities desk per building, it is open before any tenant can move in, and some of its jobs (a deep clean) take hours.

What it hides. The admin queue is not slower or lower priority by nature; arbitration rules decide how it competes with I/O queues, and many admin commands are fast. The "directory" (Identify data) is a fixed binary structure at fixed offsets, not a document you browse. Where it misleads. The facilities desk can act on its own; an NVMe controller never sends an unsolicited message — even an alarm needs a pre-posted Asynchronous Event Request to answer. And unlike a building, "deep cleaning" (Sanitize, Format) can continue across resets and power cycles, and some of it cannot be undone.

Beginner explanation

There are two families of NVMe commands. Admin commands go only on the admin queue (queue identifier 0) and manage the controller. I/O commands go on I/O queues and move or manipulate data in a namespace (NVM Command Set). The same opcode number means different things in each family, which is why the queue a command was submitted on is part of its meaning.

Admin commands do five broad jobs:

  1. Discover — Identify: ask the controller and its namespaces to describe themselves.
  2. Build — Create and Delete I/O Submission/Completion Queues.
  3. Configure — Set Features and Get Features: number of queues, power state, interrupt coalescing, write cache, temperature thresholds and many more.
  4. Observe — Get Log Page and Asynchronous Event Request: errors, health (SMART), firmware slots, changed namespaces, telemetry.
  5. Maintain — firmware download and commit, namespace create/delete/attach, Format NVM, Sanitize, Device Self-test, Security Send/Receive, Abort.

Every admin command uses the same 64-byte format you learned in NVMe Command Structure. Only CDW10–15, the NSID and the data pointer usage change.

Set Features (09h) and Get Features (0Ah)

Features are named controller settings. Both commands carry the Feature Identifier (FID) in CDW10 bits 7:0. Set Features carries a Save bit (SV, CDW10 bit 31) asking the controller to make the value persist across power cycles, if the feature is saveable. Get Features carries a Select field (SEL, CDW10 bits 10:8): 000b current, 001b default, 010b saved, 011b supported capabilities. The value itself usually travels in CDW11 (and sometimes a data buffer); Get Features returns it in CQE DW0.

Abort (08h)

Abort asks the controller to abort one specific command: CDW10 bits 15:0 hold the SQID and bits 31:16 the CID of the target. The Abort itself completes on the admin CQ; Dword 0 of its CQE indicates whether the target was aborted (in long-standing revisions, bit 0 cleared to 0 means aborted; confirm the 2.x definition, which adds detail Uncertain). If the target is aborted, it also completes on its own CQ with Command Abort Requested (generic 07h).

Abort is best effort: the controller may already be past the point of no return, may have completed the command, or may simply not find it. The number of concurrent Aborts is limited by ACL; exceeding it returns Abort Command Limit Exceeded (command-specific 03h). Linux uses Abort as the first step of timeout handling and resets the controller if that fails.

Asynchronous Event Request (0Ch)

The controller cannot send unsolicited messages. Instead the host submits one or more Asynchronous Event Requests (AERs) (up to AERL + 1) that the controller keeps outstanding — "parked" — indefinitely. When an enabled event occurs, the controller completes one AER; DW0 of the CQE describes the event:

An AER that is never fetched, or not re-submitted after completing, means the host will miss future events.

Firmware Image Download (11h) and Firmware Commit (10h)

A firmware update is two steps. First the host sends the image in pieces with Firmware Image Download: CDW10 holds NUMD (0's based Dword count of this piece) and CDW11 the Dword offset of the piece within the image; data flows host → controller. The controller's preferred granularity and alignment are reported in Identify Controller (firmware update granularity). Then Firmware Commit (10h) tells the controller what to do with the image: CDW10 bits 2:0 select the Firmware Slot (FS) and bits 5:3 the Commit Action (CA):

Namespace Management (0Dh) and Namespace Attachment (15h)

Namespace Management creates (SEL = 0h in CDW10 bits 3:0) or deletes (SEL = 1h) a namespace. A create carries a host buffer describing size, capacity, format and options and returns the new NSID in CQE DW0. A new namespace is allocated but not attached: Namespace Attachment (SEL 0h attach, 1h detach) with a controller list buffer makes it visible to particular controllers, which then report it in the Active Namespace ID list and raise a Namespace Attribute Changed notice. These commands exist only on controllers that set the Namespace Management bit in OACS; consumer drives often have one fixed namespace. See Namespaces.

Format NVM (80h)

Format NVM low-level formats one namespace or all namespaces (NSID = FFFFFFFFh, where the controller supports it). CDW10 chooses the new LBA format index (LBAF, low bits), whether metadata is extended or separate (MSET), the protection information type (PI) and location (PIL), and a Secure Erase Setting (SES): 000b no secure erase, 001b user data erase, 010b cryptographic erase. Upper LBA format index bits were added in 2.x Version-dependent. The concepts behind LBA formats, metadata and protection information are in NVM Command Set. Format destroys data. Expert lab only, on a scratch device.

Sanitize (84h)

Sanitize alters all user data in the NVM subsystem so it cannot be recovered — including caches, spare blocks and controller memory buffers — using one of three methods selected by the Sanitize Action: Block Erase, Overwrite or Crypto Erase (and an Exit Failure Mode action). It runs in the background, survives resets and power cycles, restricts most other commands while running, and reports progress in the Sanitize Status log page. It differs from Format NVM in scope (subsystem, not namespace) and in its guarantees.

Security Send (81h) and Security Receive (82h)

These commands are envelopes: the Security Protocol field (CDW10) and protocol-specific fields select a protocol whose payload travels in the data buffer. They carry, for example, TCG storage protocols (Opal, Enterprise), IEEE 1667, and in recent revisions authentication/attestation protocols. The NVMe specification defines the envelope; the security protocol's own standard defines the content. 2.4's post-quantum cryptography updates touch key-exchange algorithms used in NVMe security features; treat their exact encoding as something to read in the Base 2.4 and the relevant protocol specifications. Version-dependent

Device Self-test (14h), Keep Alive (18h), Directives (19h/1Ah) and the rest

  • Device Self-test: CDW10 bits 3:0 Self-test Code — 1h short, 2h extended, Fh abort. Progress and results in log 06h.
  • Keep Alive: resets the Keep Alive timer; vital over fabrics where it is how the controller detects a lost host. Over PCIe it is optional.
  • Directive Send/Receive: configure and query directives such as Streams and, in 2.x, data placement (Flexible Data Placement).
  • Virtualization Management: move flexible queue and interrupt resources between a primary controller and its secondary controllers (SR-IOV virtual functions, see SR-IOV).
  • NVMe-MI Send/Receive: carry NVMe Management Interface commands in-band (see NVMe-MI).
  • Doorbell Buffer Config: hands an emulated (para-virtual) controller two host pages for shadow doorbells and event indices, so a guest can avoid trapping MMIO writes.
  • Get LBA Status: reports LBAs that may be unrecoverable so a host can repair them from redundancy.

Controller initialisation: the admin sequence

The NVM Express Base Specification describes controller initialisation as an ordered list of host actions. The sequence below follows that description for a PCIe controller supporting the NVM Command Set; optional steps are marked. Confirm the exact list for your revision in the Base Specification's controller initialisation section.

  1. Read CAP (timeouts, doorbell stride, supported page sizes, command sets). If CC.EN = 1, clear it and wait for CSTS.RDY = 0.
  2. Program AQA (admin queue sizes, 0's based), ASQ and ACQ (admin queue base addresses).
  3. Program CC: command set selection (CSS), memory page size (MPS), arbitration (AMS), and I/O entry sizes IOSQES = 6, IOCQES = 4. Then set CC.EN = 1.
  4. Wait for CSTS.RDY = 1 (bounded by CAP.TO, in 500 ms units). If CSTS.CFS = 1, stop: fatal status.
  5. Identify Controller (06h, CNS 01h). Read MDTS, OACS, AERL, SQES/CQES, NN, ONCS, VWC, SGLS, VER.
  6. (If multiple I/O command sets) Identify the I/O command set structures and select a profile with Set Features. Optional
  7. Set Features — Number of Queues (09h, FID 07h); read NSQA/NCQA from DW0.
  8. Allocate MSI-X vectors to match; Create I/O CQ (05h) for each queue pair, then Create I/O SQ (01h) bound to it.
  9. Identify Active NSID list (CNS 02h, or per-command-set lists), then Identify Namespace (CNS 00h, and 03h for identifiers) for each NSID.
  10. Set Features — Asynchronous Event Configuration (FID 0Bh) and submit Asynchronous Event Requests.
  11. Other configuration as needed: Timestamp, Volatile Write Cache, APST, Host Memory Buffer, Keep Alive. Implementation-dependent (which ones a host sends and in what order).
  12. Begin I/O.

The ladder for the central concept: Identify

"Tell me about yourself," and the librarian hands back a printed card of fixed boxes: her name, how many sections, how big a request she can carry, which special jobs she knows.

Identify (admin opcode 06h) returns a 4096-byte data structure chosen by CNS: the controller (01h), a namespace (00h), the list of active namespaces (02h), namespace identifiers (03h).

Firmware assembles the structure from fixed tables and current state (e.g. NUSE) into a buffer, and the DMA engine writes it to the host page addressed by PRP1.

Base Specification defines the command, the CNS table and the controller structures; the NVM Command Set specification defines the NVM-specific namespace structure (LBA formats, NSZE/NCAP/NUSE, protection capabilities).

Doorbell MWr to SQ0TDBL; MRd/CplD of the 64-byte SQE; 4096 bytes of MWr from controller to the PRP1 page (16 × 256-byte TLPs at MPS 256); CQE MWr to the admin CQ; MSI-X vector 0.

In a trace, the first admin SQE after CSTS.RDY = 1 is usually opcode 06h with CDW10 = 1; the data TLPs start with the PCI vendor ID in the first two bytes and an ASCII serial number from byte 4.

If the driver reports a nonsense model name or a zero MDTS, check the bytes on the wire before blaming the device: a wrong PRP1 (IOMMU mapping), a too-short buffer, or a CNS typo gives the same symptom as broken firmware.

The sixteen questions, answered for Identify

1. What is it?
An admin command that returns a fixed-format 4 KiB description of the controller, a namespace or a list, selected by CNS.
2. Why was it created?
So a generic driver can adapt to any controller without vendor knowledge.
3. What problem does it solve?
Capability discovery: limits (MDTS, queue entry sizes), optional features (OACS, ONCS, SGLS), identity (SN, MN, FR, NQN) and namespace geometry.
4. What existed before it?
ATA IDENTIFY DEVICE (512-byte words) and SCSI INQUIRY / READ CAPACITY / mode pages — the inspiration, with less structure for multi-namespace devices.
5. Why is the current design better?
One command family, fixed offsets, a CNS selector that scales to new structures without new opcodes.
6. Who creates it?
The host builds the command; the controller firmware builds the data.
7. Who consumes it?
The driver (limits, features), management tools (nvme id-ctrl), and upper layers (block device size, logical block size).
8. Where does it live?
Command in the admin SQ; data in a host buffer described by PRP1/PRP2.
9. What memory/registers are involved?
ASQ/ACQ, SQ0TDBL/CQ0HDBL doorbells, the 4 KiB host buffer, MSI-X vector 0.
10. What happens before it?
Controller enable and CSTS.RDY = 1.
11. What happens after it?
Queue sizing, queue creation, namespace discovery.
12. What happens if it is wrong?
Wrong limits → oversize commands rejected or split badly; wrong capacity → I/O beyond the end (LBA Out of Range); wrong feature bits → unsupported commands sent.
13. What does the protocol analyzer show?
Admin SQE with OPC 06h, 4 KiB of controller→host MWr to PRP1, admin CQE.
14. What does Linux show?
nvme id-ctrl, nvme id-ns, nvme list-ns, sysfs attributes (model, serial, firmware_rev), block queue limits.
15. What would a validation engineer test?
Every CNS (supported and unsupported → Invalid Field), invalid NSIDs, buffers crossing a page (PRP2), consistency between Identify fields and actual behaviour, changes after Format/namespace management.
16. What would a senior engineer suspect when it fails?
Host buffer mapping first, then version mismatch (a field the host reads did not exist in the device's revision), then firmware.

Hardware view

Inside a typical controller, admin commands take a different path from I/O commands. The I/O fast path (Read, Write) is often handled by hardware accelerators and a small, latency-optimised firmware loop. Admin commands are almost always handled by general-purpose firmware on a management core, because they touch configuration tables, persistent metadata and sometimes the whole flash array. Implementation-dependent

  • Identify data is assembled from fixed tables in firmware plus live values (NUSE, capacity) from the flash translation layer.
  • Create/Delete queue commands program the controller's queue context table: base address, size, head/tail pointers, CQ binding, interrupt vector, phase state.
  • Set Features updates registers or firmware variables; saveable features are written to non-volatile configuration storage.
  • Get Log Page copies counters and ring buffers; telemetry may trigger the controller to snapshot internal state.
  • Firmware download streams into a staging buffer; commit writes it to a firmware slot in flash or NOR, with signature verification; activation swaps the running image, sometimes without reset.
  • Format/Sanitize drive long background media operations: block erases across the array, key destruction for crypto erase, mapping table rebuilds.
  • AERs occupy a slot in an outstanding-command table, completed by an event dispatcher that watches thermal sensors, spare counters, namespace changes and errors.

Admin and I/O share the same PCIe link, DMA engines and completion logic. A long admin operation (sanitize, extended self-test, a large telemetry read) can therefore affect I/O latency even though it is "on a different queue". Some admin commands — format, sanitize, firmware activation — intentionally pause or fail I/O while they run; the Commands Supported and Effects log page tells the host which ones.

Specification view

Admin commands are defined in the NVM Express Base Specification, Revision 2.4 — Admin Command Set, together with the Identify data structures, log pages and feature definitions in the same document. Command-set-specific admin behaviour (for example the NVM Command Set's Identify Namespace structure, Get LBA Status, and format details) is in the NVM Express NVM Command Set Specification, Revision 1.3. The controller initialisation procedure is in the Base Specification's controller initialisation section; transport-specific parts for PCIe (registers, MSI-X, doorbells) are in the NVMe over PCIe Transport Specification, Revision 1.4. Management tunnelled through NVMe-MI Send/Receive is defined by the NVM Express Management Interface Specification, Revision 2.2.

Normative content: the command fields and their required behaviour ("shall"), mandatory vs optional command lists, status code assignments. Informative content: examples, flow descriptions marked informative, and notes.

Opcodes marked verified in the admin table above; CNS 00h/01h/02h/03h; Get Log Page LID in CDW10 7:0, RAE in bit 15, NUMDL in 31:16, NUMDU in CDW11 15:0, LPOL/LPOU in CDW12/13; log identifiers 01h–08h as listed; feature identifiers 01h–0Fh as listed; Number of Queues CDW11 and DW0 encoding; Create queue CDW10/CDW11 fields; Abort CDW10 SQID/CID; AER DW0 type/info/LID encoding and type values; Firmware Commit FS/CA and CA 000b–011b; Format SES values 000b–010b; Device Self-test codes 1h/2h/Fh.

The init sequence's step ordering beyond "enable before admin commands" and "CQ before SQ" is the specification's recommended procedure; drivers vary in the optional steps. That a long admin command can slow I/O is reasoned from shared hardware, not quoted.

How long Identify, Format, Sanitize, self-tests and firmware activation take; whether admin commands are executed in order; how many queues are granted; whether a feature is saveable; the content of vendor-specific logs and telemetry; and which optional admin commands exist are all implementation-dependent and discoverable through Identify, the Commands Supported and Effects log and Get Features with SEL = 011b.

Mandatory vs optional status of several admin commands, the width of LSP, CDW14 selectors, the CNS list, the log page list, the feature list, Abort's DW0 detail and many command-specific status codes changed across 1.3, 1.4, 2.0 and later revisions. NVMe 2.4 adds commands, features and logs for live migration, rate limiting, voltage monitoring, lockdown persistence and manufacturing reset; their identifiers are not given in this course and must be read from the 2.4 documents and the Revision Changes list.

Check in the specification before relying on:

  • Any opcode, CNS, LID or FID this page marks uncertain or does not list.
  • Which NSID values (0, specific, FFFFFFFFh) each log page and feature accepts.
  • Which features are per-namespace vs controller-wide, and which are saveable.
  • The exact command-specific status codes each admin command may return.

The specification does not say how a host should choose the number of queues, how many AERs to keep outstanding, how often to read the SMART log, or what order to send optional configuration commands.

Never assume Set Features took effect without reading the result (DW0 or a Get Features). Never assume a log page is supported because it appears in the specification — check LPA, the supported log pages log where available, or the status. Never send Format NVM, Sanitize, Namespace Management delete, Firmware Commit or Security Send to a device whose data you care about while "just testing".

Protocol view

Over PCIe every admin command follows the same transaction pattern as an I/O command, only on queue 0: a doorbell MWr to SQ0TDBL (BAR0 + 1000h), a controller MRd of the 64-byte SQE from the ASQ region with a CplD reply, optional data movement (controller → host MWr for Identify/Get Log Page/Get Features data; controller MRd + host CplD for Set Features data, Firmware Image Download, Namespace Management), a CQE MWr to the ACQ region, typically an MSI-X MWr on vector 0, and a CQ0HDBL doorbell write from the host.

Admin command data movement patterns
CommandPCIe traffic between SQE fetch and CQE
Identify4096 bytes controller → host, MWr (16 × 256 B at MPS 256)
Get Log Page(NUMD + 1) × 4 bytes controller → host, MWr
Set Features (Number of Queues)none; result in CQE DW0
Set Features (APST, HMB descriptors…)controller MRd of the host buffer, host CplD
Create I/O CQ / SQnone (controller only records PRP1); a non-contiguous queue may cause the controller to read the PRP list
Firmware Image Downloadcontroller MRd + host CplD for the image piece
Asynchronous Event Requestnone; CQE may come much later
Format NVM / Sanitize / Self-testnone; long internal activity (sanitize completes its command quickly and continues in background)

Ordering: the controller is not required to execute admin commands in submission order, and the host must not submit a command that depends on another until that one's CQE arrives (for example Create I/O SQ after Create I/O CQ). Linux serialises its initialisation steps for this reason.

Later: the driver submits I/O on SQ1; the SQ1 tail doorbell is written to a queue that does not exist. Controller behaviour for a doorbell write to a non-existent queue is an error condition defined by the specification (asynchronous error event); the driver hangs waiting for completions.

Reasoning. The visible failure is a CQE with status word 0x8201: (0x8201 >> 9) & 7 = 1 → Command Specific Status; (0x8201 >> 1) & 0xFF = 0x00 → for Create I/O SQ, Completion Queue Invalid; DNR = 1. A junior might conclude "the controller lost CQ 1", because a later CQE shows CQ 1 was created successfully. The decoded SQEs in row 3 show the real story: the driver placed both commands in the queue with one doorbell, SQ creation first. Even if the order had been correct, submitting them together would be unsafe, because the controller may process admin commands in any order. Root cause: host submitted a dependent command before its prerequisite completed. Fix: wait for the Create I/O CQ completion before submitting Create I/O SQ. Regression test: fuzz admin submission batching and assert no dependent pairs share a doorbell.

#!/usr/bin/env python3
"""Build the admin SQEs a driver sends during initialisation and print them
as little-endian hex, plus decode two admin completion results.
Simulation only: nothing is sent to a device. Standard library only."""
import struct

def sqe(opc, cid, nsid=0, prp1=0, prp2=0, cdw10=0, cdw11=0, cdw12=0):
    cdw0 = (opc & 0xFF) | (cid << 16)          # FUSE=0, PSDT=0 (admin uses PRP)
    return struct.pack("<IIIIQQQIIIIII", cdw0, nsid, 0, 0, 0, prp1, prp2,
                       cdw10, cdw11, cdw12, 0, 0, 0)

def show(name, raw):
    print(f"{name}")
    for off in range(0, 64, 16):
        print(f"  {off:02x}: {raw[off:off + 16].hex(' ')}")

Worked example

Reading the SMART / Health log by hand

Synthetic example for teaching. The host wants the controller-wide SMART / Health Information log (LID 02h, 512 bytes).

  • NSID = FFFFFFFFh (controller-wide).
  • NUMD = 512 / 4 − 1 = 127 = 7Fh; NUMDL = 007Fh, NUMDU = 0.
  • CDW10 = (NUMDL << 16) | (RAE 0 << 15) | LID 02h = 0x007F_0002. CDW11 = 0. CDW12/13 = 0 (offset 0).
  • CDW0 with CID 0x0010 = 0x0010_0002. PRP1 = a 4 KiB-aligned buffer.

Suppose the first bytes of the returned buffer are 00 36 01 64 0a 03 …. Using the long-established SMART log layout:

Decoding a Create I/O CQ command

Given SQE bytes 40–47 01 00 ff 03 03 00 01 00: CDW10 = 0x03FF_0001 → QID 1, QSIZE 1023 → 1024 entries; CDW11 = 0x0001_0003 → PC = 1, IEN = 1, IV = 1. PRP1 bytes 24–31 00 00 41 23 01 00 00 00 → 0x0000_0001_2341_0000, the CQ1 base. Required memory: 1024 × 16 = 16 KiB, matching the reference system.

Interpreting an AER completion

An AER CQE arrives with DW0 = 0x0004_0002: type = 010b (Notice), information = 00h, log page = 04h (Changed Namespace List). The host reads log 04h (with RAE = 0, which also re-arms the notice), learns which NSIDs changed, re-issues Identify for those NSIDs, and submits a new AER.

Common mistakes

  • Treating 0's based fields as counts. QSIZE, NUMD, NSQR/NCQR, AERL, ACL are all 0's based. Off-by-one errors here create queues one entry too small or read 4 bytes too much.
  • Creating an SQ before its CQ, or deleting a CQ before its SQs.
  • Ignoring the granted queue count in Set Features Number of Queues DW0.
  • Setting Number of Queues after queues exist — rejected.
  • Forgetting to re-submit AERs, or reading the event's log page with RAE = 1 and never clearing the event — future events of that type stay masked.
  • Interpreting the same opcode on the wrong queue — 02h on the admin queue is Get Log Page, on an I/O queue it is Read.
  • Assuming Abort succeeded. Always check DW0 of the Abort's CQE and wait for the target's own CQE.
  • Misreading the SMART temperature as Celsius (it is kelvin).
  • Assuming Format affects all namespaces (or only one): depends on NSID and the controller's format attributes.
  • Equating Format with Sanitize: different scope, different guarantees.

Senior engineer insight

Seniors read Identify and the Commands Supported and Effects log before anything else when handed a new device, because those two structures define the contract for every later observation. Half of "firmware bugs" filed by junior engineers are hosts using a feature the device never advertised.

Second, admin commands are where state lives. An I/O failure is usually local; an admin mistake (wrong number of queues, a feature saved with SV = 1, an AER never re-armed, a namespace detached) persists and shows up later, far from its cause. When debugging intermittent issues, reconstruct the admin history since the last reset: which features were set, saved, which namespaces changed, which firmware slot is active.

Third, treat long-running admin operations as concurrency problems. Sanitize, Format and firmware activation interact with I/O, resets and power loss. Validation plans that only test them in isolation miss the real bugs: a reset during sanitize, a hot-plug during firmware activation, an AER for a namespace change arriving while the host is mid-scan.

Finally, the 2.4 additions (migration, rate limiting, voltage monitoring, lockdown persistence, manufacturing reset) are almost all admin-side. For day-to-day PCIe trace analysis they look like any other admin command; their importance is in system design and fleet management. Learn them from the specification when your platform needs them.

Hints

Synthetic fallback data

MDTS byte = 05h, MPSMIN = 0 → 25 × 4 KiB = 128 KiB. VER = 00 04 02 00 → 0x00020400 → 2.4.0. OACS = 0x005F. NN = 1. Get Features 07h result 0x001F001F. SMART first bytes 00 3c 01 64 0a 01.

Hint for VER

VER is MJR in bits 31:16, MNR in 15:8, TER in 7:0 — read the four bytes little-endian.

Solution

Solution (for the synthetic data)

MDTS = 128 KiB; Linux would normally report max_hw_sectors_kb = 128 unless a driver or quirk limit is lower. VER 2.4.0. OACS 0x005F → bits 0 (Security Send/Receive), 1 (Format NVM), 2 (Firmware Download/Commit), 3 (Namespace Management), 4 (Device Self-test), 6 (NVMe-MI Send/Receive) set; bit 5 (Directives) clear. (Bit meanings for bits 0–4 are long-established; confirm higher bits in your revision.) NN = 1. Number of Queues 0x001F001F → 32 SQs and 32 CQs granted. SMART: critical warning 0; temperature 0x013C = 316 K ≈ 43 °C; available spare 100 %; threshold 10 %; percentage used 1 %.

Answers: (1) the driver may cap transfers further (e.g. DMA mapping or segment limits); (2) Linux normally creates up to one queue per CPU within the granted count; (3) compare OACS bits with the "ACS" entries of the effects log; (4) subtract 273.15 from kelvin.

What a senior engineer notices

Mismatches. MDTS that differs from the driver limit, OACS bits that disagree with the effects log, a granted queue count far below CPU count (the device may be a virtual function with few resources), a firmware slot log with a pending image (an activation waiting on a reset — a future surprise), an unsafe-shutdown counter that is rising.

Failure variants

  • Get Log Page for an unsupported LID: expect Invalid Log Page (command-specific 09h) or Invalid Field.
  • Get Features with SEL = 010b (saved) on a non-saveable feature: an error or the current value, depending on capabilities — read the spec's rules.
  • Identify with an unsupported CNS: Invalid Field in Command.

Exercises

  1. Build CDW10 and CDW11 for Get Log Page reading 64 KiB of telemetry starting at byte offset 1 MiB. Which other Dwords change?
  2. Build CDW10/CDW11 for Create I/O SQ 3 with 256 entries, contiguous, medium priority, bound to CQ 3.
  3. An AER completes with DW0 = 0x0002_0001. What happened and what does the host do next?
  4. A Set Features Number of Queues with CDW11 = 0x0007_0007 completes with DW0 = 0x0003_0007. How many SQs and CQs may the host create?
  5. Explain why Abort cannot guarantee abortion, and what the host must do afterwards.
  6. List three differences between Format NVM with SES = 010b and Sanitize with Crypto Erase.
Answers

1: 64 KiB = 16384 Dwords → NUMD = 16383 = 0x3FFF; NUMDL = 0x3FFF, NUMDU = 0. CDW10 = 0x3FFF_0007 (LID 07h, host-initiated telemetry; LSP options as needed). CDW11 = 0. Offset 1 MiB = 0x0010_0000 → CDW12 = 0x0010_0000, CDW13 = 0. PRP1/PRP2 must describe a 64 KiB buffer (PRP2 → PRP list).

2: CDW10 = (255 << 16) | 3 = 0x00FF_0003. CDW11 = (3 << 16) | (QPRIO medium = 10b << 1) | PC 1 = 0x0003_0005. (QPRIO encodings: 00b urgent, 01b high, 10b medium, 11b low; only meaningful with weighted round robin.)

3: Type 001b SMART/Health status, information 00h, log page 02h. Read the SMART log (RAE = 0) to find which warning, act on it, re-submit an AER.

4: NSQA = 7 + 1 = 8 SQs; NCQA = 3 + 1 = 4 CQs. The host can create 4 CQs and up to 8 SQs (some SQs sharing CQs).

5: The target may already be executing past a cancellation point, completed, or not yet fetched in a way the controller can find; the specification makes it best effort. The host must wait for the target's own CQE (or reset the controller) before freeing its resources or reusing its CID.

6: Scope (namespace vs whole NVM subsystem, including caches and over-provisioned areas); persistence (sanitize continues across resets/power cycles and restricts commands until complete); verification and reporting (Sanitize Status log); format may also change LBA format and protection information.

Quiz

  1. Which admin opcode is Identify?

    • 02h
    • 05h
    • 06h
    • 09h
    Answer and reasoning

    06h. 02h is Get Log Page, 05h Create I/O CQ, 09h Set Features.

  2. Identify with CNS 02h returns:

    • The controller data structure
    • A list of active namespace IDs
    • The namespace data structure
    • Namespace identification descriptors
    Answer and reasoning

    CNS 02h is the active NSID list (up to 1024 NSIDs above the NSID in the command). 01h controller, 00h namespace, 03h descriptors.

  3. Which must be created first?

    • The I/O Completion Queue
    • The I/O Submission Queue
    • Either; the controller reorders
    • Both in one command
    Answer and reasoning

    An SQ is bound to an existing CQ by CQID, so the CQ must exist; otherwise Completion Queue Invalid.

  4. Get Log Page NUMD counts:

    • Bytes, 1-based
    • Bytes, 0's based
    • Dwords, 1-based
    • Dwords, 0's based
    Answer and reasoning

    Dwords, 0's based, split across NUMDL (CDW10 31:16) and NUMDU (CDW11 15:0).

  5. Where does Set Features Number of Queues return the granted counts?

    • In a 4 KiB data buffer
    • In CQE Dword 0
    • In the CAP register
    • In an AER
    Answer and reasoning

    CQE DW0: NSQA in bits 15:0, NCQA in bits 31:16, both 0's based.

  6. Why might an AER have been outstanding for three hours in a trace?

    Model answer

    That is its normal behaviour: the controller holds it until an enabled event occurs. A long-outstanding AER is healthy; the absence of any outstanding AER is the problem.

  7. What two steps does a firmware update over NVMe consist of, and which one selects when the new image runs?

    Model answer

    Firmware Image Download (one or more pieces with NUMD/OFST) and Firmware Commit; the Commit Action decides whether to replace, activate at next reset, or activate immediately.

  8. Which log page should a host read when a CQE has the More bit set?

    Model answer

    The Error Information log, LID 01h, which holds entries with SQID, CID, status and further details such as the LBA and NSID involved.

  9. Name the two Identify Controller fields that tell a driver whether it may use SGLs and how large one command's transfer may be.

    Model answer

    SGLS (SGL Support) and MDTS (Maximum Data Transfer Size, in units of the minimum memory page size as a power of two).

Interview questions

  1. Beginner. What is the difference between an admin command and an I/O command?

    Model answer

    Admin commands go on the admin queue (QID 0) and manage the controller — discovery, queues, features, logs, maintenance. I/O commands go on I/O queues and operate on namespace data. Opcode numbers are interpreted per queue type.

  2. Beginner. What does Identify Controller tell a driver?

    Model answer

    Identity (vendor, serial, model, firmware), limits (MDTS, entry sizes, number of namespaces, AER and Abort limits), optional command support (OACS, ONCS), SGL support, version, write cache presence, power states, subsystem NQN.

  3. Intermediate. Describe the controller initialisation sequence.

    Model answer

    Disable and wait RDY=0; program AQA/ASQ/ACQ; program CC (CSS, MPS, entry sizes) and set EN; wait RDY=1 within CAP.TO; Identify Controller; Set Features Number of Queues; Create I/O CQs then SQs; discover namespaces via Identify 02h then 00h; configure async events and post AERs; optional features; start I/O.

  4. Intermediate. How does an Asynchronous Event Request avoid flooding the host?

    Model answer

    Only as many events can be reported as AERs are outstanding; and after an event is reported, further events of that type are masked until the host reads the indicated log page with RAE cleared.

  5. Advanced. Create I/O SQ fails with SCT 1h SC 01h. What do you check?

    Model answer

    Invalid Queue Identifier: QID 0, QID already in use, or QID beyond the number granted by Set Features Number of Queues (NSQA). Check the driver's queue numbering and the DW0 of the Number of Queues completion; also check whether the device is a VF with fewer resources.

  6. Advanced. How do you validate firmware activation robustly?

    Model answer

    Cover every commit action and supported reset type; activation with I/O in flight; power loss at every step (download, commit, activation); invalid images, wrong offsets and sizes; read-only slot handling; firmware slot log and Identify FR consistency; link re-training and PCIe config state after activation; AER notices around activation.

  7. Senior. A fleet shows intermittent "namespace disappeared" events. Which admin evidence do you collect?

    Model answer

    Changed Namespace List and Persistent Event log, AER history from the host, Identify active NSID lists over time, namespace attachment state per controller, ANA state if multipath, firmware slot and activation history, reset history. I would also check whether a management agent (NVMe-MI out-of-band) issued namespace commands without the host knowing.

  8. Senior. How would you design a driver's handling of 2.4 features it does not understand?

    Model answer

    Discover them only through advertised capabilities; never send unknown opcodes; treat unknown AER information values and log pages as opaque but logged; pass unrecognised status codes up with SCT/SC preserved; keep feature-specific code behind capability checks so older and newer devices both work.

Chapter summary

Admin commands discover (Identify with CNS), build (Create/Delete I/O queues, CQ first), configure (Set/Get Features with FID, SV, SEL), observe (Get Log Page with 0's based Dword counts; parked Asynchronous Event Requests) and maintain (firmware download/commit, namespace management and attachment, Format NVM, Sanitize, Security Send/Receive, self-test, Abort). Their opcodes are stable for the classic set; newer commands must be confirmed in the current specification and discovered through OACS and the Commands Supported and Effects log. The initialisation sequence is a strict chain of dependencies, and most bring-up bugs are violations of it.

Do not move on until you can:

  • write the admin opcodes 00h–0Ch and the main maintenance opcodes from memory
  • build Identify, Get Log Page, Set Features Number of Queues, Create I/O CQ and Create I/O SQ commands by hand
  • decode AER and Number of Queues results from CQE DW0
  • recite the initialisation sequence and explain each dependency
  • recognise each admin command's traffic pattern in a PCIe trace
  • say which admin commands are destructive and how you would test them safely
  • cite the Base Specification, NVM Command Set and NVMe-MI documents for each part
