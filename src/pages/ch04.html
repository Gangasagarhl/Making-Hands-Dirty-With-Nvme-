PCI Express (PCIe) is not a faster version of the old shared bus. It is a switched network of private, point-to-point links. This chapter builds the mental model you will use for the rest of the course: who sits where (Root Complex, Root Port, Switch, Endpoint, bridge), what a lane and a link are, and what "width" and "generation" mean, all before we touch a single electrical detail or packet field.

Why this chapter exists

Every NVMe command you will ever trace rides on Peripheral Component Interconnect Express (PCIe). When a Solid-State Drive (SSD) is slow, missing, or throwing errors, the first questions a senior engineer asks are PCIe questions: Where is the device in the tree? What is it connected to? What did the link negotiate? Who owns the path between the CPU and the controller? You cannot answer them without a picture of the topology in your head.

Beginners often carry an outdated picture: a single set of wires that every card shares, where the CPU shouts and whichever card recognises its address answers. That was the original Peripheral Component Interconnect (PCI) model. PCIe kept PCI's software model (configuration space, Base Address Registers, the same enumeration ideas) but threw away the shared electrical bus. If you keep the old picture, you will misread almost everything: bandwidth sharing, error isolation, why a switch matters, why "the bus" in a Bus:Device.Function address is not a bus at all in the electrical sense.

This chapter is deliberately conceptual. Chapter 5 adds the wires, Chapter 6 the speeds, Chapter 7 the layers, and Chapters 8 and 9 the training state machine that brings a link to life.

Learning objectives

  • Explain the difference between a shared parallel bus and a point-to-point serial link, and why the industry moved from one to the other.
  • Name and place every PCIe component in a topology: Root Complex, Root Port, Switch (upstream and downstream ports), Endpoint, Root Complex Integrated Endpoint, and PCIe-to-PCI bridge.
  • Define lane, link, width (x1 … x16) and generation precisely, and stop using them interchangeably.
  • Read a Linux PCI tree and say, for an NVMe SSD, which port it hangs from and what that implies.
  • Describe what travels on a link (packets) versus what describes a device (configuration space), at a high level.
  • Predict how a fault on one link affects (and does not affect) other devices.

Prerequisites

You should be comfortable with the CPU–memory–I/O picture from Chapter 1 (addresses, memory-mapped I/O, the idea of Direct Memory Access), with what an SSD is from Chapter 2, and with why NVMe moved storage directly onto PCIe from Chapter 3. No electrical knowledge is required yet.

The story

Imagine a town where every house is connected to the train station by its own private railway track. In the old town, there was just one big road, and every delivery truck had to share it. If one truck broke down, the whole road was blocked. If two trucks wanted to drive at the same time, one had to wait.

In the new town, the station (the Root Complex) has several platforms (Root Ports). Each platform has its own track leading to one house (a device). Some tracks lead to a junction building (a Switch) that splits one track into several smaller private tracks, each going to its own house.

A track can have one rail pair, or two, four, eight or sixteen side by side, like more lanes on a motorway, so more trains can travel at once. And newer tracks let trains drive faster. The number of rail pairs is the width; how fast the trains go is the generation.

The best part: if a tree falls on one house's private track, the other houses still get their deliveries.

A modern office building's network is a good adult analogy. In the 1990s, many offices used a shared coaxial Ethernet: one cable snaking past every desk, every computer hearing every frame, collisions slowing everyone down. Today each desk has its own cable to a switch port. Switches connect upward to a core router. Each cable has a negotiated speed (100 Mb/s, 1 Gb/s, 10 Gb/s) that depends on both ends and the cable quality. A bad cable at one desk only affects that desk.

PCIe is the same shape: the Root Complex is the core router, Root Ports are its ports, PCIe Switches are access switches, and Endpoints are the desks. Each link negotiates its own width and speed.

  • Direction of authority. An Ethernet network is a set of peers. PCIe is a tree with a privileged root: the host (through the Root Complex) discovers devices, assigns their addresses, and owns configuration. Devices do not configure each other.
  • Addressing. PCIe routes most traffic by memory address (and by Bus/Device/Function identifiers for configuration and completions), not by device names or MAC-style addresses. A device's memory window is assigned by software during enumeration.
  • Reliability. Ethernet may drop frames and expects upper layers to cope. A PCIe link retransmits corrupted packets itself at the Data Link Layer; a dropped packet is an error event, not normal behaviour.
  • Lanes are not separate trains. The railway story suggests each rail pair carries its own train. In PCIe, one packet is striped across all lanes of a link byte by byte. The lanes act together as one wider pipe, not as independent channels.
  • The junction is smarter than a junction. A PCIe Switch is not a passive splitter; it contains bridges, buffers, credits and its own configuration space, and it can report errors.

Beginner explanation

Inside your computer, the CPU needs to talk to many devices: a graphics card, a network card, and the NVMe SSD this course is about. PCIe is the system of connections that lets it do so.

There are four ideas to hold:

  1. Every connection is private. A PCIe link connects exactly two ports: one at each end. Nobody else is on that wire.
  2. The connections form a tree. At the top is the Root Complex, the part of the CPU/chipset that turns CPU memory reads and writes into PCIe traffic. It has one or more Root Ports. A device plugs into a Root Port either directly or through a Switch that fans one link out into several.
  3. A link has a width. A link is made of one or more lanes. A lane is a pair of one-way signal paths, one in each direction. A link with four lanes is called "x4" (say "by four"). Most NVMe SSDs use x4.
  4. A link has a speed. Each PCIe generation (Gen1, Gen2 … Gen7) roughly doubles how fast each lane signals. Both ends must agree, so the link runs at the fastest speed both support, and only if the wiring is good enough.

The devices at the leaves of the tree are Endpoints. Your NVMe SSD is an Endpoint. The host software finds every Endpoint by walking the tree at boot (this is called enumeration, taught in Chapter 17), gives each one an address range, and from then on the CPU can read and write the device's registers as if they were memory.

Read the picture from the top. The CPU never "puts a signal on a bus" for the SSD. It issues a memory write; the Root Complex decides which Root Port the address belongs to and sends a packet down that one link. If a Switch is in the way, the Switch looks at the address, decides which downstream port leads to the target, and forwards the packet down only that link.

From a shared bus to point-to-point links

What the old shared bus looked like

Conventional PCI (1990s) used a parallel, shared, multi-drop bus: 32 or 64 address/data lines, plus control lines, routed past every slot on the motherboard. Every card was electrically attached to the same wires. A transaction went like this:

  1. A would-be initiator requested the bus from a central arbiter and waited for a grant.
  2. The initiator drove an address onto the shared lines.
  3. Every device on the bus decoded the address; the one that matched claimed the cycle (asserted a select signal).
  4. Data moved across the shared lines in lock-step with a common clock (33 or 66 MHz).
  5. The bus was released and the next initiator could have a turn.

PCI-X pushed the same idea to 133 MHz and beyond, but the approach hit physical walls.

What PCIe kept

PCIe's designers made a crucial compatibility decision: keep the software-visible model of PCI. That is why:

  • devices are still identified by Bus, Device and Function numbers (BDF);
  • each Function still has a configuration space with a standard header, Vendor ID and Device ID;
  • memory windows are still described by Base Address Registers (BARs, Chapter 19);
  • a PCIe Switch looks to software like a set of PCI-to-PCI bridges.

An operating system written for PCI could enumerate a PCIe system without knowing anything about lanes. Everything new (link control, Advanced Error Reporting, power management states) was added as extended capabilities on top.

When you see the word "bus" in Linux output (0000:01:00.0 is domain 0, bus 1, device 0, function 0), it is a logical bus number inherited from PCI. In PCIe, "bus 1" is usually the single link below a Root Port. There is no shared electrical bus behind it. Mixing up the logical and electrical meanings leads to wrong conclusions such as "the SSD and the NIC on bus 1 share bandwidth".

Engineering explanation

We now name each component precisely. For each one: what it is, where it lives, what it does with packets, and how software sees it.

Point-to-point architecture

A PCIe port is one end of a link: a transmitter, a receiver, and the logic that runs the protocol. A link connects exactly two ports. There are no multi-drop PCIe links. Every packet on a link is either going "downstream" (away from the Root Complex) or "upstream" (towards it). That directional vocabulary is used throughout the specification and throughout this course:

  • Downstream port: a port that faces away from the root (a Root Port, a Switch downstream port).
  • Upstream port: a port that faces towards the root (the port on an Endpoint, a Switch's upstream port).

Every link has exactly one downstream port at the top and one upstream port at the bottom. This matters for link training (Chapter 8): the downstream port leads certain negotiations, for example proposing link and lane numbers.

Root Complex

The Root Complex (RC) is the boundary between the CPU/memory world and the PCIe world. The specification defines it functionally, not as a specific chip. On modern x86 and Arm servers it is integrated in the processor package. Its jobs:

  • Translating CPU accesses to PCIe address space into PCIe requests. A CPU store to an NVMe doorbell becomes a Memory Write Transaction Layer Packet (TLP).
  • Translating device accesses to host memory into memory-system accesses. When the SSD does Direct Memory Access (DMA) to read a command or write data, the Root Complex receives the TLP and turns it into a memory read or write, often through an I/O Memory Management Unit (IOMMU).
  • Generating configuration requests on behalf of software during enumeration.
  • Hosting one or more Root Ports, and sometimes integrated devices.
  • Collecting errors and interrupts: error messages from below arrive at the Root Port; Message Signalled Interrupts (MSI/MSI-X) are memory writes that the RC turns into CPU interrupts.

Software never "sees" the Root Complex as a single PCI function; it sees its Root Ports and any integrated endpoints.

Root Port

A Root Port (RP) is a downstream port of the Root Complex. Each Root Port begins its own hierarchy domain below it. To software, a Root Port appears as a PCI-to-PCI bridge function (a configuration header of Type 1) with a PCI Express Capability that reports the port type as Root Port. The bridge's secondary and subordinate bus number registers say which bus numbers live below it, and its memory base/limit registers say which address ranges are forwarded downward.

In the course's reference lab system (a synthetic example for teaching, used in every chapter), the Root Port is 0000:00:01.1 and the NVMe SSD is directly below it at 0000:01:00.0. The link between them is Gen4 x4.

Endpoint

An Endpoint (EP) is a function that is the requester or completer of PCIe transactions on its own behalf, rather than forwarding them. It has a Type 0 configuration header, BARs that expose its registers, and it can perform DMA. An NVMe SSD is a PCIe Endpoint whose class code says "mass storage controller, Non-Volatile Memory controller, NVM Express". Endpoints come in a few flavours:

  • PCI Express Endpoint: the normal modern kind; must support 64-bit memory addressing and MSI or MSI-X; must not require I/O space.
  • Legacy Endpoint: a PCIe device permitted to use older PCI features such as I/O space and locked transactions.
  • Root Complex Integrated Endpoint (RCiEP): an endpoint built into the Root Complex itself, with no PCIe link of its own (common for on-die controllers).

One physical device can contain multiple Functions (up to 8 per device in the classic numbering, or up to 256 with Alternative Routing-ID Interpretation), and with Single Root I/O Virtualization (SR-IOV, Chapter 56) many Virtual Functions.

Switch

A PCIe Switch fans one upstream link out into several downstream links. Internally, the specification models it as:

  • one upstream port, which looks to software like a PCI-to-PCI bridge (Type 1 header);
  • an internal virtual bus;
  • one PCI-to-PCI bridge per downstream port, each heading its own link.

A Switch routes each packet by examining its header: memory requests by address (compared against each downstream bridge's base/limit windows), completions and configuration requests by Bus/Device/Function ID, and messages by their routing type. It buffers packets, manages flow-control credits on every link, and may support peer-to-peer forwarding between downstream ports (subject to Access Control Services settings).

A Switch is the reason a server can host 24 NVMe SSDs on a CPU that has fewer free lanes than 24 × 4 = 96. A Switch with a x16 upstream link and six x4 downstream links lets six SSDs share 16 lanes' worth of bandwidth toward the CPU. This is called oversubscription: fine when not all drives are busy at once; a bottleneck when they are. Understanding where switches sit explains many "the drives are fast individually but slow together" reports.

Bridge

"Bridge" has two meanings in PCIe that you must keep apart:

  1. The logical PCI-to-PCI bridge that every Root Port and every Switch port presents to software. It is a Type 1 configuration header with bus-number and window registers. It is how the tree is described.
  2. A physical protocol bridge that converts between PCIe and another bus, such as a PCIe-to-PCI/PCI-X bridge that lets an old parallel PCI card sit behind a PCIe link. These are rare in modern NVMe systems but appear in older or embedded platforms.

When an engineer says "the bridge window is too small", they mean meaning 1: the memory base/limit of a Root Port or Switch port does not cover the BAR of the device below it.

Lanes

A lane is the smallest unit of a PCIe link: one transmit differential pair and one receive differential pair, so four wires. Each direction of a lane carries a serial bit stream at the generation's signalling rate. Chapter 5 takes the lane apart electrically.

Link

A link is the collection of one or more lanes between two ports that operate together. Packets are striped across all lanes of a link: on a x4 link, byte 0 goes on lane 0, byte 1 on lane 1, byte 2 on lane 2, byte 3 on lane 3, byte 4 back on lane 0, and so on. The receiver reassembles them after compensating for small arrival-time differences between lanes (deskew).

Width

Width is the number of lanes in a link, written x1, x2, x4, x8, x16 (and historically x12 and x32, which are rare). Width is negotiated during link training. A device designed for x4 placed in an x16 slot trains to x4; a x16 card in a slot wired for only x4 trains to x4. The width you design for (capability) and the width you get (negotiated) are different numbers, and Linux reports both.

Generation

Generation is shorthand for the per-lane signalling rate defined by a revision of the PCI Express Base Specification: Gen1 2.5 GT/s, Gen2 5.0 GT/s, Gen3 8.0 GT/s, Gen4 16.0 GT/s, Gen5 32.0 GT/s, Gen6 64.0 GT/s, Gen7 128.0 GT/s. GT/s is "gigatransfers per second", the rate of symbols on the wire, before encoding overhead. Like width, the speed is negotiated: a link starts at 2.5 GT/s and moves up to the highest rate both ends support and the channel can sustain. Chapter 6 works through the arithmetic.

Do not confuse PCIe generations with NVMe revisions. "Gen4" is a PCIe link speed. "NVMe 2.4" is a revision of the NVM Express Base Specification. A drive can implement NVMe 2.4 over a Gen3 link, or NVMe 1.4 over a Gen5 link. The two version numbers are independent, and NVMe over PCIe Transport (Revision 1.4 in the August 2026 set) is the specification that joins them.

The central concept on the ladder: the point-to-point link

Every house has its own private railway track to the station. A tree falling on one track only stops deliveries to that one house.

A PCIe link joins exactly two ports. Bandwidth on a link belongs to those two ports. A Switch creates more links; the Root Complex is the root of the tree.

Physically, a link is N lanes, each with a transmit pair and a receive pair, driven by a serialiser/deserialiser (SerDes) in each port. The Root Port's SerDes and the SSD controller's SerDes are wired to each other and nothing else.

The PCI Express Base Specification defines ports, links, lanes and the component types (Root Complex, Switch, Endpoint, Bridge). Each port exposes a PCI Express Capability whose Link Capabilities/Control/Status registers describe and control its side of the link.

All communication is packets: Transaction Layer Packets (TLPs) for reads, writes, completions and messages; Data Link Layer Packets (DLLPs) for acknowledgements and flow-control credits; ordered sets for physical-layer management. Packets are routed hop by hop.

A protocol analyzer is inserted on one link (an interposer between Root Port and SSD). It sees only that link's traffic, in both directions, with timestamps. It cannot see traffic on a sibling link under the same Switch.

A Receiver Error storm on the SSD's link points to that link's channel (slot, cable, retimer), not to the CPU. If several SSDs under the same Switch fail at once, suspect the shared element: the Switch, its upstream link, or its power and clock.

The sixteen questions for "a PCIe link"

The 16 questions applied to the central concept of this chapter
QuestionAnswer for a PCIe link
1. What is it?A dedicated, dual-simplex, serial connection of 1 to 16 (or more) lanes between exactly two PCIe ports.
2. Why was it created?Parallel shared buses could not scale in clock speed, slot count or bandwidth per device.
3. What problem does it solve?Gives each device its own bandwidth, avoids bus arbitration, removes clock-skew limits, isolates faults.
4. What existed before it?Conventional PCI and PCI-X shared parallel buses; AGP for graphics.
5. Why is the current design better?Bandwidth scales by adding lanes and raising per-lane speed; a fault is contained to one link; fewer pins per unit of bandwidth.
6. Who creates it?The board designer wires it; the two ports' physical layers bring it up through link training (LTSSM) after reset.
7. Who consumes it?The Data Link and Transaction Layers of both ports, and ultimately the software and DMA engines above them.
8. Where does it live?On the motherboard traces, connector, cable or backplane between a downstream port (Root Port or Switch downstream port) and an upstream port (Endpoint or Switch upstream port).
9. What memory/registers are involved?Each port's PCI Express Capability: Link Capabilities, Link Control, Link Status (and the "2" versions); Advanced Error Reporting registers for link errors.
10. What happens before it?Power stable, reference clock running, fundamental reset (PERST#) released; then receiver detection and training.
11. What happens after it?Data Link Layer initialises flow control; the link becomes "DL_Active"; software can enumerate the device below.
12. What happens if it is wrong?The device is missing, trains at reduced width or speed, or generates correctable/uncorrectable errors and link retraining.
13. What does the protocol analyzer show?Training ordered sets, then TLPs and DLLPs in both directions; replays, Recovery entries and errors are timestamped.
14. What does Linux show?lspci -tv for the tree; lspci -vvv LnkCap/LnkSta for capability and negotiated speed/width; AER messages in the kernel log.
15. What would a validation engineer test?Training to full width and speed across temperature, voltage and many resets; error injection; hot-plug; margining; interoperability with many root ports.
16. What would a senior engineer suspect when it fails?Channel quality (connector, retimer, cable), reference clock or reset sequencing, firmware power-state handling, then device or root-port bugs; always check negotiated vs capable first.

How many Root Ports a CPU has, whether ports can be bifurcated, and whether the chipset adds more ports is entirely platform-dependent. Read the platform's documentation; the PCIe specification only defines what a Root Port must do, not how many exist.

Retimers and redrivers

At Gen4 and above, the distance a signal can travel on a circuit board shrinks. Platforms insert retimers: devices that fully receive, re-clock and retransmit the signal and participate in link training. A retimer is not a Switch: it has no configuration space visible as a PCI function in the tree, does not route packets, and is meant to be transparent to software. It does, however, split the electrical channel into two segments, and it appears in training ordered sets. Simpler redrivers only amplify/equalise analog signals and do not participate in the protocol. Both are introduced here because they are part of "the link" from a debugging point of view; Chapter 5 returns to them.

Bifurcation

A single x16 group of lanes from the CPU may be configured by firmware as one x16 Root Port, two x8 ports, or four x4 ports. This is how a "quad M.2 carrier card" works without a Switch: the slot is bifurcated into four x4 Root Ports, one per SSD. If firmware does not enable bifurcation, only the first SSD on such a card appears. That symptom ("only one of my four drives shows up") is a topology problem, not a drive problem.

Specification view

The topology concepts in this chapter are defined in the PCI Express Base Specification, Revision 6.x/7.0 — Introduction and Architectural Overview, published by PCI-SIG. The Base Specification is a members' document; the overview chapter's terms (Root Complex, Root Port, Switch, Endpoint, Bridge, Link, Lane, Upstream/Downstream) are stable across revisions. The register-level description of each port's link lives in the PCI Express Base Specification — PCI Express Capability Structure.

NVMe does not define topology. The NVMe over PCIe Transport Specification, Revision 1.4 — PCI Express mapping describes how an NVMe controller is presented as a PCIe Function (class code, BAR usage, interrupts). The NVM Express Base Specification, Revision 2.4 describes the controller behaviour independent of transport.

Verified definitions you can rely on: a link connects exactly two ports; a lane is a set of differential signal pairs, one pair for transmission and one for reception; a Switch appears to configuration software as two or more logical PCI-to-PCI bridges; a Root Complex denotes the root of an I/O hierarchy that connects the CPU/memory subsystem to the I/O; Endpoints have Type 0 configuration headers; Root Ports and Switch ports have Type 1 headers.

Derived (reasoned, not quoted): because each link has its own credits, its own retry buffer and its own error reporting, a fault on one link is contained to the devices below it. Because a Switch shares its upstream link among all downstream links, aggregate bandwidth below a Switch can exceed what reaches the CPU.

Implementation-dependent: how many Root Ports exist; how the Root Complex is built internally; whether peer-to-peer traffic between Root Ports is supported; whether a Switch supports peer-to-peer between its downstream ports; how a platform numbers its buses; bifurcation options.

Version-dependent: available link speeds (Gen1 at Revision 1.x through 128 GT/s at Revision 7.0); Flit Mode (introduced with Revision 6.0); some port and device-type rules have been refined across revisions. Topology concepts are stable.

  • The specification does not say how many lanes a CPU must provide, or how they map to slots.
  • It does not say "bus 1 is the NVMe drive": bus numbers are assigned by enumeration software.
  • Confirm in the Base Specification: exact rules for each Device/Port Type value in the PCI Express Capabilities register, and the rules for Root Complex Integrated Endpoints and Root Complex Event Collectors.

Never assume: that two devices with nearby bus numbers share a link; that a Switch is "non-blocking"; that a slot's mechanical size equals its electrical width; that the PCIe generation of the platform tells you the NVMe revision of the drive (or vice versa).

Protocol view

We will not decode packets until Chapter 10, but the mental model needs to know what crosses a link and how it is routed.

What crosses a PCIe link (overview)
ThingLayerGoes beyond this link?Example in NVMe life
Transaction Layer Packet (TLP)TransactionYes, routed hop by hop through Switches to its destinationDoorbell write from CPU; SSD reading a command from host memory; completion data; MSI-X interrupt write
Data Link Layer Packet (DLLP)Data LinkNo; consumed by the port at the other end of the linkAck after receiving a TLP; UpdateFC returning flow-control credits
Ordered setPhysicalNo; consumed by the neighbour (and retimers)TS1/TS2 during training; SKP for clock compensation; Electrical Idle ordered sets

Three routing methods

  • Address routing for memory (and legacy I/O) requests: each Switch port forwards if the address falls in its bridge window.
  • ID routing for configuration requests and completions: forwarded by target Bus/Device/Function. A completion finds its way back to the requester using the Requester ID copied from the request.
  • Implicit routing for some messages: "to the Root Complex", "broadcast from the Root Complex", "local, terminate at receiver".

Notice the asymmetry. The doorbell write is a posted request (no completion comes back), whereas the SSD's memory read is non-posted and must receive a completion. Chapter 12 explains why. The Ack DLLP never leaves the link; if a Switch were in the middle, there would be one Ack on each link segment.

Reasoning

  1. Nothing on SSD A's link is wrong: no replays, no Recovery, no error completions. A fault on SSD B's link would not appear here, because each link is private.
  2. Row 4 is unusual but harmless: a configuration read during I/O. It suggests the operating system reacted to an event elsewhere (for example a Downstream Port Containment event or a hot-plug "link down" on SSD B's port) and re-scanned devices.
  3. The right next step is not to stare harder at this trace. Move the analyzer to SSD B's link, or read the kernel log and the Switch downstream port's Link Status and AER registers for SSD B's port.

Topology tells you where to put the probe. A trace proves only what happened on the link it was attached to. Many wasted debug days start with an analyzer on the wrong link.

Linux view

Linux exposes the PCIe tree directly. All of the following commands are read-only and safe on a running system.

# The tree: Root Ports, Switch ports and endpoints as bridges and children
lspci -tv

# One line per function, with numeric IDs and the kernel driver
lspci -nnk

# Port type and link fields for the NVMe SSD and its Root Port (more detail needs root)
sudo lspci -vv -s 01:00.0 | grep -E "Express|LnkCap|LnkSta"
sudo lspci -vv -s 00:01.1 | grep -E "Express|LnkCap|LnkSta"

# sysfs: the directory path itself encodes the topology
readlink -f /sys/bus/pci/devices/0000:01:00.0
cat /sys/bus/pci/devices/0000:01:00.0/current_link_speed /sys/bus/pci/devices/0000:01:00.0/current_link_width

What the output can tell you (shapes described; actual text differs by system and pciutils version):

  • lspci -tv draws the tree as -[0000:00]-+-01.1-[01]----00.0 <vendor> NVMe SSD: Root Port at device 01 function 1 on bus 00, with bus 01 below it containing the SSD.
  • In lspci -vv, the line Capabilities: [..] Express (v2) Root Port (Slot+) or Express (v2) Endpoint gives the port type from the PCI Express Capability. A Switch shows Upstream Port and Downstream Port entries.
  • The sysfs path, for example /sys/devices/pci0000:00/0000:00:01.1/0000:01:00.0, lists every bridge between the root and the device. Each extra path component is one more hop (a Switch adds two: its upstream and its downstream port).

What Linux output cannot prove: it shows configuration-space state at the moment you read it. It does not show traffic, does not show how many times the link retrained, and the negotiated speed it reports could change a millisecond later. It also cannot show a retimer, which is invisible to configuration software.

Code / pseudocode

The following script walks sysfs and prints, for every NVMe controller, the chain of ports from the root to the device, with each port's type and its negotiated link. It only reads files. If run on a machine without NVMe devices, it says so.

#!/usr/bin/env python3
"""Print the PCIe path from the root to every NVMe controller (read-only, Linux sysfs)."""
import os, re

SYS = "/sys/bus/pci/devices"
BDF = re.compile(r"^[0-9a-f]{4}:[0-9a-f]{2}:[0-9a-f]{2}\.[0-7]$")

def read(path, name, default="?"):
    try:
        with open(os.path.join(path, name)) as f:
            return f.read().strip()
    except OSError:
        return default

def chain(dev):
    """Return the list of BDFs from the topmost bridge down to dev."""
    real = os.path.realpath(os.path.join(SYS, dev))
    return [p for p in real.split("/") if BDF.match(p)]

def main():
    if not os.path.isdir(SYS):
        print("no PCI sysfs here (not Linux?)")
        return
    found = False
    for dev in sorted(os.listdir(SYS)):
        cls = read(os.path.join(SYS, dev), "class")
        if not cls.startswith("0x010802"):      # mass storage / NVM / NVM Express
            continue
        found = True
        print(f"NVMe controller {dev}")
        for depth, hop in enumerate(chain(dev)):
            p = os.path.join(SYS, hop)
            speed = read(p, "current_link_speed")
            width = read(p, "current_link_width")
            mx = read(p, "max_link_speed") + " x" + read(p, "max_link_width")
            print(f"  {'  ' * depth}{hop}  class={read(p, 'class')}  now={speed} x{width}  max={mx}")
    if not found:
        print("no NVMe controllers (class 0x010802) found")

if __name__ == "__main__":
    main()

Class code 0x010802 is base class 01h (mass storage), subclass 08h (non-volatile memory controller), programming interface 02h (NVM Express). Bridges show class 0x0604xx (PCI-to-PCI bridge). Note that for a bridge, the link attributes describe the link on its secondary (downstream) side for a Root Port or Switch downstream port.

Worked example

Scenario. A storage server has one CPU socket providing a x16 Root Port to a PCIe Switch. The Switch has eight x4 downstream ports, each with a Gen4 NVMe SSD. The Switch upstream link is Gen4 x16. Each SSD can read at about 7 GB/s on its own. The customer asks: "Why do I only get about 26 GB/s when reading from all eight at once, not 56 GB/s?"

  1. Draw the tree. CPU → RP (x16) → Switch upstream port → 8 downstream ports (x4 each) → 8 SSDs.
  2. Find the narrowest shared point. All read data flows up through the single Gen4 x16 link to the Root Port.
  3. Bound it. Gen4 provides roughly 1.97 GB/s per lane per direction after 128b/130b encoding (Chapter 6), so x16 ≈ 31.5 GB/s raw usable symbol bandwidth per direction. Packet header and framing overhead reduce that further: with 256-byte payloads the efficiency is roughly 85–90 %, giving about 27–28 GB/s of data. Derived
  4. Compare. 8 × 7 GB/s = 56 GB/s of demand versus ≈ 27 GB/s of supply. Oversubscription ratio ≈ 2:1. Observed 26 GB/s is consistent with the upstream link being the bottleneck.
  5. Confirm with Linux. Check that the Switch upstream link really trained at Gen4 x16 (lspci -vv on the Switch upstream port and on the Root Port). If it trained at x8, the ceiling halves; if it trained at Gen3, it drops to about 13–14 GB/s.

Conclusion: the drives are healthy; the topology sets the ceiling. Fixes are architectural (wider or additional upstream links, more Root Ports), not drive firmware.

Common mistakes

  • "PCIe is a bus, so devices share bandwidth." Devices share bandwidth only where their paths share a link (typically a Switch upstream link), not otherwise.
  • "Lane" and "link" used interchangeably. A lane is one transmit pair plus one receive pair; a link is one or more lanes between two ports.
  • "x16 slot means x16 link." Mechanical slot size, electrical wiring and negotiated width are three separate facts.
  • "Gen5 SSD means it is NVMe 2.x." PCIe generation and NVMe revision are independent.
  • "The Switch is invisible." A Switch adds two bridge functions per hop, its own latency, its own buffers and its own error reporting. Retimers are the components that are (nearly) invisible to software.
  • "Bus number tells me the physical slot." Bus numbers are assigned by enumeration and can change with BIOS settings or added devices. Use slot information or the sysfs path.
  • "A trace on one link shows the whole system." It shows exactly one link.

Debugging connection

Topology is the first filter in almost every PCIe investigation. Ask, in order:

  1. Where is the failing device? Find its path from the root (lspci -tv, sysfs).
  2. What else shares that path? Siblings under the same Switch, the Switch upstream link, the same Root Port.
  3. Do the symptoms follow the device or the position? Swap the SSD into a different slot. If the problem moves with the drive, suspect the drive; if it stays with the slot, suspect the path.
  4. Which link reports errors? Advanced Error Reporting messages name the port that detected the error; that identifies the link.
  5. Did the link train to what both sides can do? Compare LnkCap and LnkSta on both ends (Chapter 9).

Symptom pattern "all drives under one Switch disappear at once": suspect the Switch upstream link, Switch power, Switch reference clock, or a containment event at the Root Port. Symptom pattern "one drive disappears, siblings fine": suspect that drive's link or the drive itself. The tree shape turns symptoms into a search space.

Senior engineer insight

Seniors think about PCIe as a network with a privileged root. Three habits follow:

  • They name the link, not the device. "The 01:00.0 link trained at x2" is actionable. "The SSD is slow" is not.
  • They separate failure domains. Each link is a failure domain; each Switch is a shared failure domain; the Root Complex is the largest one. A good bug report says which domain is affected and why.
  • They look for the shared choke point first when performance falls short with many devices, and for the private link first when one device misbehaves.

They also distrust their own mental model when retimers, bifurcation and Switch peer-to-peer settings are involved, because those features change the physical picture without changing what lspci -tv shows.

Lab: Map the PCIe tree of a real machine

Objective

Produce an accurate topology diagram of a Linux machine's PCIe hierarchy, from Root Ports to each NVMe SSD, including negotiated width and speed for every link on the path.

Skills

Reading lspci -tv, interpreting port types, following sysfs paths, distinguishing capability from negotiated state.

Safety

Safe lab Read-only. No configuration writes, no driver unbinding. Some fields need root to read; reading them changes nothing.

Hardware required

Any Linux machine with at least one PCIe device; an NVMe SSD is ideal. A virtual machine works but shows an emulated topology (which is itself instructive).

Software required

pciutils (lspci), Python 3 for the script in the Code section.

Input

The live system.

Expected output

A hand-drawn or ASCII tree like the one in the Beginner explanation, with every link labelled "GenN xM (capable GenP xQ)".

Background

Root Ports and Switch ports are bridges (class 0604); endpoints are not. Each bridge's secondary bus is the link below it. The negotiated link state is reported by both ends.

Step 1 — Draw the tree

Run lspci -tv. Identify every bridge with children. Mark which are Root Ports (directly on the root bus, usually bus 00) and which are Switch ports (bridges below another bridge).

Step 2 — Classify ports

For each bridge, run sudo lspci -vv -s <BDF> | grep Express and record the port type (Root Port, Upstream Port, Downstream Port). For each NVMe device, confirm it reports Endpoint.

Step 3 — Annotate links

Run pcie_path.py or read current_link_speed/current_link_width and max_link_speed/max_link_width for the endpoint and its parent. Write them on each link.

Observation

Note any link whose current values are below its maximum. Note any Switch, and the width of its upstream link compared to the sum of downstream widths.

Questions

  1. Which Root Port does each NVMe SSD hang from?
  2. Do any two NVMe SSDs share a link anywhere on their path to the CPU?
  3. What is the oversubscription ratio of each Switch (sum of downstream lanes × speed / upstream lanes × speed)?
  4. Is any link running below its capability?

Challenge

On a multi-socket server, determine which CPU socket each SSD is attached to (hint: numa_node in sysfs) and explain why that matters for latency.

Hint

A Switch shows up as one bridge (upstream port) whose children are several bridges (downstream ports) on the next bus. Root Ports have no bridge above them other than the host bridge.

Solution

Example reasoning for the lab system: lspci -tv shows 00:01.1 with child bus [01] containing 00.0, an NVMe controller. 00:01.1 reports "Root Port"; 01:00.0 reports "Endpoint". Both ends report 16GT/s x4; the endpoint's maximum is 16GT/s x4. There is no Switch, so the SSD has a private Gen4 x4 path to the Root Complex and shares nothing with other devices below the Root Complex. On a system with a Switch, the upstream port's link is the shared resource; compute the ratio as described. Any link with current < max should be investigated with Chapter 9's method.

What a senior engineer notices

  • Whether drives that will be used together (for example in a RAID set) are spread across Root Ports or crammed behind one Switch.
  • Whether the NVMe SSD is on the same NUMA node as the application threads using it.
  • Any port with "Slot+" (a hot-plug capable slot) and whether hot-plug is relevant to failures seen.

Failure variants

  • A drive is missing from the tree entirely: the link never trained, or the bridge window/bus range was not assigned. Check the parent port's Link Status ("Data Link Layer Link Active").
  • A drive appears with "!!! Unknown header type 7f" or reads of all-ones: the device is not responding to configuration reads (link down or device dead).
  • In a VM, everything hangs off emulated root ports: the "link speed" shown is emulated and proves nothing about the physical link.

Extension

Repeat the lab after moving an SSD to a different slot and compare the tree. Which bus numbers changed? Which did not?

Exercises

  1. Draw the topology for: one CPU with three Root Ports; RP0 x16 to a GPU; RP1 x4 to an NVMe SSD; RP2 x8 to a Switch with four x4 downstream ports, three populated with NVMe SSDs. Label every port as upstream or downstream.
  2. In that system, list every pair of devices that share at least one link.
  3. A colleague says "the NIC and SSD are both on bus 3 so they compete". Under what topology could that statement be literally impossible? Under what topology could two functions share bus 3 and a link?
  4. Explain in one paragraph why PCIe kept PCI's configuration model even though it dropped the shared bus.
  5. Using the Switch model (bridges plus internal virtual bus), how many bus numbers does a Switch with five downstream ports consume, not counting the buses below the downstream ports?
Answers

1–2: The GPU and the RP1 SSD share nothing but the Root Complex. The three SSDs behind the Switch share the RP2 x8 link. 3: If the NIC and SSD are separate functions, "bus 3" being a single link below a downstream port means only one device sits there; two different devices on bus 3 below a PCIe port is not possible (a PCIe link has one device below it, though that device can have multiple functions). Two functions of one multi-function device share bus 3 and the link. 4: Software compatibility: existing OS enumeration, drivers and tools worked unchanged. 5: The upstream port's link uses the bus above it (assigned by the parent); the internal virtual bus consumes one bus number; each downstream link consumes one. So one internal bus plus five downstream-port secondary buses = six.

Quiz

  1. How many ports are attached to a single PCIe link?

    • One
    • Exactly two
    • Up to eight
    • As many as there are slots on the board
    Answer and reasoning

    Exactly two. PCIe links are point-to-point: one downstream port and one upstream port.

  2. Which component appears to configuration software as a set of PCI-to-PCI bridges?

    • An Endpoint
    • A retimer
    • A Switch
    • A lane
    Answer and reasoning

    A Switch is modelled as an upstream bridge and one bridge per downstream port. Retimers are not visible as PCI functions.

  3. An NVMe SSD is which kind of PCIe component?

    • Endpoint
    • Root Port
    • Switch downstream port
    • Root Complex
    Answer and reasoning

    An Endpoint with a Type 0 header and class code 010802h.

  4. A lane consists of:

    • One wire carrying data in both directions
    • One differential pair used in alternating directions
    • One transmit differential pair and one receive differential pair
    • Sixteen parallel data wires and a clock
    Answer and reasoning

    Four wires: a pair in each direction, both active simultaneously (dual-simplex).

  5. Which statement about "Gen4" and "NVMe 2.4" is true?

    • Gen4 links require NVMe 2.4
    • They are independent: one is a PCIe signalling rate, the other an NVMe specification revision
    • NVMe 2.4 defines the Gen4 signalling rate
    • They are two names for the same thing
    Answer and reasoning

    Independent. The NVMe over PCIe Transport specification connects NVMe to PCIe; it does not tie NVMe revisions to PCIe generations.

  6. How is a completion TLP routed back to the requester?

    • By memory address
    • By the Requester ID (Bus/Device/Function) copied from the request
    • It is broadcast to all devices
    • By lane number
    Answer and reasoning

    ID routing using the Requester ID; the Tag then matches it to the specific outstanding request.

  7. Why can a protocol analyzer on SSD A's link not show a failure on SSD B's link under the same Switch?

    Model answer

    Each link is private. The analyzer interposes on one link and captures only packets on that link. SSD B's link-level traffic (TLPs to B, DLLPs, training ordered sets) never crosses A's link. Only indirect effects (software reacting to B's failure) might appear.

  8. Give two reasons the parallel shared PCI bus could not keep scaling.

    Model answer

    Any two of: clock skew across parallel wires at high frequency; electrical loading and reflections of multi-drop slots; bandwidth shared by all devices; half-duplex turnaround; fault containment (one card can hang the bus); high pin counts.

  9. Eight Gen4 x4 SSDs sit behind a Switch whose upstream link is Gen4 x8. What is the lane oversubscription ratio, and what is the approximate ceiling for aggregate reads?

    Model answer

    Downstream lanes 32, upstream 8, so 4:1. Ceiling ≈ 8 × 1.97 GB/s ≈ 15.75 GB/s of encoded bandwidth, roughly 13–14 GB/s of data after packet overhead. Derived

Interview questions

  1. (Beginner) What is the difference between a PCIe lane and a PCIe link?

    Model answer

    A lane is one transmit differential pair plus one receive differential pair. A link is the set of lanes (1 to 16, or more) between two ports that operate together, with packets striped across all lanes.

  2. (Beginner) What does the Root Complex do?

    Model answer

    It connects the CPU and memory to the PCIe hierarchy: turns CPU accesses into PCIe requests, turns device DMA into memory accesses, generates configuration requests, hosts Root Ports and collects errors and interrupts.

  3. (Intermediate) How does software see a PCIe Switch, and why that way?

    Model answer

    As an upstream PCI-to-PCI bridge, an internal bus, and a PCI-to-PCI bridge per downstream port. This re-uses the PCI bridge software model, so existing enumeration code assigns bus numbers and memory windows to each port without new concepts.

  4. (Intermediate) A drive in a quad-M.2 carrier card shows only one of four SSDs. What do you check?

    Model answer

    Whether the carrier has a Switch or relies on slot bifurcation. If it relies on bifurcation, check the firmware setting for that slot (x4x4x4x4). Then confirm with lspci -tv how many Root Ports appear for that slot.

  5. (Senior) Many NVMe drives behind one Switch time out together. Walk through your fault-isolation approach.

    Model answer

    Treat the Switch and its upstream link as the shared failure domain. Check AER logs at the Root Port and Switch ports to find the first reporting port; check upstream link state (LnkSta, retraining, Recovery counts if available); check whether a containment event (Downstream Port Containment) fired; check Switch power/clock/reset; capture the upstream link. Only then look at individual drives. Distinguish cause from consequence by timestamps: the first error is usually upstream.

  6. (Senior) Why might a retimer complicate topology-based reasoning?

    Model answer

    It is invisible in the software tree but splits the electrical channel and participates in training, so one "link" in lspci is physically two segments with separate signal-integrity behaviour. Errors or training problems can originate in either segment or in the retimer, and analyzers placed on different segments see different things.

Teach-back challenge

  • To a child: Explain why a town with private railway tracks to every house works better than one shared road. Use the word "junction" for a Switch.
  • To a junior engineer: Explain Root Complex, Root Port, Switch and Endpoint using the lab system (Root Port 00:01.1, SSD 01:00.0), and why "bus 01" is one link.
  • To a senior engineer: Argue for or against placing all 24 drives of a storage node behind two Switches instead of using direct-attached Root Ports, in terms of failure domains, oversubscription and latency.
Model explanation (junior engineer)

The Root Complex is the CPU-side gateway into PCIe. Root Port 00:01.1 is one of its doors; the cable behind that door is a private Gen4 x4 link going to exactly one device, our SSD at 01:00.0. Bus 01 is just the number software gave to that link when it enumerated. If we put a Switch there instead, the Switch would take bus 01 for its upstream side, create an internal bus 02, and give each downstream port its own bus (03, 04, …), each a private link to one SSD. Every TLP travelling to the SSD is routed by address; completions coming back are routed by the requester's ID.

Chapter summary

  • PCIe replaced a shared parallel bus with private, serial, dual-simplex links between exactly two ports.
  • The topology is a tree: Root Complex → Root Ports → (optional Switches) → Endpoints. Switches look like bridges to software.
  • A lane is a transmit pair and a receive pair; a link is one or more lanes; width is the lane count; generation is the per-lane signalling rate. Width and speed are both negotiated.
  • PCIe kept PCI's software model (BDF, configuration space, BARs, bridges), so "bus" is a logical number, not a shared wire.
  • Topology defines failure domains and bandwidth choke points, and it tells you where to put an analyzer.
  • PCIe generations and NVMe revisions are independent version axes.

Do not move on until you can:

  • draw a PCIe tree with Root Complex, Root Ports, a Switch and Endpoints, labelling upstream and downstream ports;
  • define lane, link, width and generation without mixing them up;
  • explain address routing versus ID routing in one sentence each;
  • read lspci -tv and identify the port an NVMe SSD hangs from;
  • compute an oversubscription ratio for a Switch;
  • say which link an analyzer must be on to observe a given failure.
