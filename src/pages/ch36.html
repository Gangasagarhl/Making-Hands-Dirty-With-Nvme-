A command says what to read or write; the Physical Region Page (PRP) entries say where in host memory the bytes live. This chapter teaches you to build, read and audit PRP1, PRP2 and PRP lists by hand, to count the pages a buffer touches, and to predict exactly which PCIe packets the controller will send to move the data.

Why this chapter exists

Every NVM Express (NVMe) Read, Write, Identify, Get Log Page and dozens of other commands move data between the host's memory and the controller. The 64-byte Submission Queue Entry (SQE) cannot carry the data itself, and it cannot carry a long list of addresses either: it has exactly sixteen bytes of room for the Data Pointer (DPTR). The Physical Region Page mechanism is how NVMe over PCIe squeezes "a buffer of any size, scattered across memory pages" into those sixteen bytes.

When PRPs are wrong, the failure is rarely polite. A wrong PRP does not usually produce a clean error status. It produces a controller that writes 4 KiB of somebody else's data into the wrong page, a read that returns success with zeros, an Input/Output Memory Management Unit (IOMMU) fault in the kernel log that nobody connects to the storage stack, or a machine that crashes an hour later in unrelated code. Engineers who can decode a PRP set in their head find these bugs in minutes. Engineers who cannot spend weeks.

This chapter is also the first place where three separate technologies meet in one field: the NVMe Base Specification defines what a PRP entry means; the NVMe over PCIe Transport Specification says PRPs are how data pointers work over PCI Express (PCIe); and the PCIe Base Specification governs the Memory Read and Memory Write Transaction Layer Packets (TLPs) the controller generates when it follows those pointers. Keep the three apart in your head and the rest of the chapter becomes easy.

Learning objectives

  • State the format of a PRP entry and explain which bits are the page base and which are the offset, for any memory page size.
  • Derive the memory page size from CC.MPS and know why it must lie between CAP.MPSMIN and CAP.MPSMAX.
  • Decide, for any buffer address and length, whether PRP2 is unused, a second data page, or a PRP list pointer.
  • Build a PRP list, including chained list pages, and say where the chain pointer goes.
  • Count the pages a buffer touches and the list entries it needs.
  • Predict the number and size of Memory Write (MWr) or Memory Read (MRd) TLPs, given Max Payload Size (MPS), Max Read Request Size (MRRS) and the Read Completion Boundary (RCB).
  • Explain why "physical address" in the name is really "the address the device emits", which is an I/O virtual address (IOVA) when an IOMMU is on.
  • Recognize the trace signature of a malformed PRP set.

The story

Imagine a giant warehouse where every shelf is exactly the same size. A delivery robot comes to pick up your toys. Your toys do not fit on one shelf, so they are spread over several shelves, and the shelves are not next to each other: one is in aisle 7, the next in aisle 2, the next in aisle 31.

You give the robot an order card. The card only has two lines. On line one you write "start at aisle 7, shelf position 3" — you are allowed to start part-way along the first shelf. If your toys fill just one more shelf, line two simply says "then aisle 2". But if there are many shelves, line two says "go read the clipboard hanging at aisle 50". The clipboard is a list: "aisle 2, aisle 31, aisle 9…". Every shelf on the clipboard starts at its very beginning. If the clipboard is full and there are still more shelves, the very last line of the clipboard says "continue on the clipboard at aisle 51".

The robot never asks you anything. It reads the card, reads the clipboards, and carries toys to and from exactly those shelves. If you wrote the wrong aisle, it happily fills the wrong shelf.

In a real distribution center, a pick ticket for a large order does not list every bin on the paper slip handed to the forklift driver. The slip has a header and a reference to a pick list stored at a terminal. The warehouse is divided into identical bin sizes (the memory page size), the first bin may be partly used by an earlier order (the offset in PRP1), every other bin on the list is a full, whole bin used from its start, and a long pick list continues on a second sheet whose location is printed in the last line of the first. The forklift driver (the controller's direct memory access engine) works without phoning the office (the CPU) for each bin.

  • The robot cannot see the aisle numbers you see. Software thinks in virtual addresses. The controller only sees bus addresses, which an IOMMU may translate again. The warehouse story hides that there are two or three different "aisle numbering systems".
  • Only the first shelf may be partly used. In a real warehouse you could start mid-shelf anywhere. With PRPs, every entry after the first must start at the beginning of a page, and every page except the last must be used to its end. That rigidity is the whole reason Scatter Gather Lists (SGLs) exist (Chapter 37).
  • The clipboard is fetched over the same road as the toys. Reading a PRP list costs real PCIe Memory Read transactions and real latency; the story makes it look free.
  • The robot does not carry a shelf in one trip. Data moves in TLPs of at most Max Payload Size bytes (256 bytes on our lab system), so one 4 KiB page becomes many separate packets.
  • Nobody checks the card. Controllers are allowed to, and some do, detect a bad offset; many do not. The story's "happily fills the wrong shelf" is realistic, but it is implementation-dependent.

Beginner explanation

Host memory is managed in fixed-size pages. On most x86-64 Linux systems the operating system page is 4 KiB, and NVMe controllers are almost always configured to use a 4 KiB memory page size too. When an application asks to read 128 KiB, the kernel's buffer for those bytes is usually virtually contiguous — one unbroken range in the program's address space — but physically it is a collection of 32 separate 4 KiB pages that may be anywhere in RAM.

The NVMe controller moves data by itself using direct memory access (DMA). It needs to know, for every byte of the transfer, the address in host memory where that byte goes (for a Read) or comes from (for a Write). A PRP entry is simply a 64-bit address of a place inside one memory page. The controller treats each PRP entry as "the next chunk of the buffer begins here and runs to the end of this page, or until the transfer is finished".

The SQE has room for two PRP entries, called PRP Entry 1 (PRP1) and PRP Entry 2 (PRP2). Three cases cover every transfer:

The three ways PRP2 is used (memory page size = 4 KiB)

Notice the rule is about boundaries crossed, not about size. A 4 KiB transfer that starts in the middle of a page crosses one boundary and needs PRP2. A 512-byte transfer that starts 256 bytes before a page boundary also needs PRP2. Beginners who think "4 KiB fits in one page, so PRP2 is unused" write exactly the bug we dissect in Chapter 38.

The word "physical" in the name comes from the days before IOMMUs were common. Today, the address in a PRP entry is whatever address the device must put on the PCIe bus to reach that memory: a bus address or DMA address. With an IOMMU enabled (as on our lab system), it is an I/O virtual address (IOVA) that the IOMMU translates to a real physical address. We keep the specification's name and teach you what it really means.

PRP1 may start anywhere inside a page (on a 4-byte boundary). Every other data pointer starts at the beginning of a page. Every page except the first and last is used completely. If a buffer does not fit that shape, PRPs cannot describe it.

Engineering explanation

The PRP entry format

A PRP entry is a 64-bit (8-byte, "quadword") memory address. How its bits divide depends on the memory page size. If the page size is 2n bytes, bits 63:n hold the page base address and bits n−1:0 hold the offset within the page. Bits 1:0 are always required to be zero, so every PRP entry is at least dword (4-byte) aligned.

PRP entry layout for a 4 KiB memory page (n = 12). Bits 63:32 omitted; they are part of the page base.
Bits31…2423…1615…87…0

With an 8 KiB page (n = 13) the offset widens to bits 12:2; with a 64 KiB page (n = 16) it is bits 15:2. The format never changes; only the line between "which page" and "where in the page" moves.

In this chapter "MPS" appears twice. CC.MPS is the NVMe Memory Page Size. PCIe Max Payload Size (MPS) is the largest data payload a TLP may carry, set in the PCIe Device Control register. On our lab system memory page size is 4096 bytes and Max Payload Size is 256 bytes. They are unrelated settings in different specifications.

PRP1: the only entry that may have an offset

PRP1 points at the first byte of the transfer. It may carry any dword-aligned offset within its page. The amount of data it describes is the smaller of "the rest of that page" and "the whole transfer":

B1 = min(L, PS − (A mod PS))

PRP2: three meanings, chosen by arithmetic

The controller does not get a flag that says "PRP2 is a list". It works out the meaning from the transfer length, the offset in PRP1, and the page size, exactly as the host should have done when it built the command. Both sides must reach the same answer from the same arithmetic. That is why a host that computes the length wrongly (for example, forgets that the Number of Logical Blocks field is zero-based) produces a PRP set that the controller interprets differently from how it was built.

  1. L, A, PS known; compute pages N
  2. N = 1: PRP2 unused
  3. N = 2: PRP2 = second page
  4. N > 2: PRP2 = list pointer
  5. SQE with PRP1, PRP2, NLB
  6. same arithmetic from NLB, PRP1 offset, PS
  7. decides PRP2 meaning independently

The page count is:

N = ⌈ ((A mod PS) + L) / PS ⌉
N
number of memory pages the transfer touches, which equals the number of PRP data pointers needed
A mod PS

L

PS

When N > 2, the PRP list must hold N − 1 data entries (PRP1 covers the first page).

PRP lists and chaining

A PRP list is an array of 8-byte PRP entries in host memory. Every entry in a list is page aligned (offset zero). The list itself lives in a memory page and may start part-way into that page: PRP2, when it is a list pointer, must be quadword (8-byte) aligned, and the base specification permits it to have a non-zero offset Verified. Linux exploits this: for short lists it allocates list memory from a small pool of 256-byte blocks rather than wasting a whole 4 KiB page on 248 bytes Implementation-dependent.

A list never silently runs off the end of its page. The number of slots available in the current list page is:

S = (PS − (P mod PS)) / 8
S
number of 8-byte slots left in the list page that contains the list pointer
P
address of the first entry of this list (PRP2, or a chain pointer)
PS
memory page size

If the entries still to be listed are more than S, the last slot of that page is not a data page. It is a pointer to the next PRP list page, and the first S − 1 slots carry data pages. If the remaining entries are S or fewer, they all go in this page and there is no chain pointer. A page-aligned 4 KiB list page has 512 slots, so a single list page can describe up to 512 more data pages, i.e. 2 MiB beyond PRP1's page. Larger transfers chain.

The PRP mechanism carries no length field and no "this is a chain pointer" marker. The controller knows an entry is a chain pointer purely because it sits in the last slot of a list page while more than one page of data remains. If the host's idea of the length differs from the controller's by even one page, the two sides disagree about which slot is the chain pointer. Nothing in the format detects that.

What shape of buffer PRPs can describe

Put the rules together and you get a precise shape: one run of bytes that may start mid-page, continues through whole pages, and may end mid-page, where each page can live anywhere in memory. Physically scattered pages are fine. Holes inside the run are not. A buffer made of "2 KiB here, 2 KiB there", where each piece starts at offset zero, cannot be described with PRPs, because the second piece would need the first to end exactly at a page boundary. The block layer in Linux avoids ever building such a request for NVMe by declaring a virtual boundary equal to the controller page size; requests that would create a gap are split before they reach the driver Implementation-dependent.

Physical addresses, bus addresses and IOVAs

The address in a PRP entry is what the device emits on PCIe. Three cases exist:

  • No IOMMU, or IOMMU in pass-through mode: bus address equals CPU physical address (on common x86 platforms).
  • IOMMU in translated mode (our lab system): the driver obtains an IOVA from the kernel's DMA mapping layer. The device puts the IOVA in its TLPs, and the IOMMU translates it, checking permissions per device. An entry pointing at an unmapped IOVA triggers an IOMMU fault instead of corrupting memory.
  • Virtual machine with an assigned device: the guest writes guest-physical addresses or guest IOVAs, and a second level of translation maps them.

The PRP list itself is also fetched by DMA, so the list pointer and chain pointers are IOVAs too, and the list memory must be mapped for the device just like the data.

Where else PRPs appear

  • Admin command buffers such as Identify (opcode 06h) and Get Log Page (opcode 02h). Identify returns 4 KiB; if the host's buffer starts at an offset, it touches two pages and needs PRP2. Over PCIe, admin commands use PRPs.
  • Non-contiguous I/O queues. When a host creates an I/O Submission or Completion Queue with the Physically Contiguous bit cleared (only allowed if the controller does not require contiguous queues), PRP1 of the Create command points to a PRP list describing the queue pages. See Chapter 27.
  • Metadata. With PRPs selected (PSDT = 00b), the Metadata Pointer (MPTR, SQE Dwords 4–5) is a single address of a contiguous metadata buffer, not a PRP. Metadata that must be scattered needs SGLs.

How PRPs interact with MDTS and the block layer

The Maximum Data Transfer Size (MDTS) field in Identify Controller limits one command's transfer to 2MDTS × the minimum memory page size (zero means no limit is reported). A controller with MDTS = 5 and a 4 KiB minimum page accepts at most 128 KiB per command, which is 32 pages and a 31-entry list. The Linux block layer reads MDTS and caps max_hw_sectors_kb, so a 1 MiB application read may reach the device as eight 128 KiB commands. Whether you ever see a chained PRP list in a trace depends on MDTS and on the driver Implementation-dependent.

The teaching ladder for PRPs

The order card has two lines: where to start, and either the next shelf or the clipboard that lists all the other shelves.

The data pointer in each SQE has two 64-bit entries. PRP1 is the address of the first byte. PRP2 is unused, the second page, or the address of a PRP list of page addresses.

The driver writes PRP entries into the SQE and list pages in host DRAM. The controller's DMA engine fetches the SQE and list with PCIe reads, translates entries into a per-command page table in its own SRAM, and drives data TLPs to those addresses; the IOMMU checks each one.

The NVMe Base Specification defines the PRP entry, PRP list, offset and alignment rules and the PRP Offset Invalid status; CC.MPS sets the page size; PSDT = 00b selects PRPs; the NVMe over PCIe Transport Specification makes PRPs the PCIe data pointer.

Over PCIe: MRd for the SQE, MRd for each list region, then MWr (for an NVMe Read) or MRd + CplD (for an NVMe Write) per data chunk, cut by Max Payload Size, MRRS and the 4 KiB address-boundary rule.

In an analyzer: a 64-byte SQE read, a short read of 8 × (N−1) bytes from the list region, then a run of data TLPs whose addresses jump at every page boundary to the next listed page.

If data TLP addresses do not match the list you expect, or a "list read" goes to a data page, or an IOMMU fault names an address the driver never mapped, compare the host's length arithmetic with the controller's: a PRP bug is almost always a disagreement about length or offset.

Hardware view

Inside the controller, a command passes through a front end that fetches SQEs, a data-pointer engine that turns PRP entries into an internal scatter table, and one or more DMA engines that move data between host memory and the controller's buffers. The exact partitioning is private to each controller design Implementation-dependent.

What the controller does with a PRP set

  1. Decode. From the opcode, NLB and namespace format it computes the transfer length. From PRP1's offset and the page size it computes the page count, and so the meaning of PRP2.
  2. Fetch lists. If PRP2 is a list pointer, it issues PCIe MRd requests for the list. Many controllers fetch the whole list (up to the end of the list page) up front; others fetch it in chunks as data moves, a form of prefetching that trades latency for SRAM.
  3. Build a per-command scatter table. Page addresses go into on-chip memory so that the DMA engine can compute "host address for byte k of this command" as page[k / PS] + (k mod PS), adjusted for PRP1's offset. This random access is the reason PRP entries are page aligned: no sequential walk is needed.
  4. Move data. The DMA engine emits MWr (controller-to-host) or MRd (host-to-controller) TLPs, never crossing a 4 KiB address boundary in one request, never exceeding Max Payload Size for writes, never exceeding MRRS for reads.
  5. Release. After the Completion Queue Entry (CQE) is posted, the controller must not touch the buffer or list again. The host may then unmap and reuse them.

Who else touches the addresses

  • The root complex receives the TLPs and routes them to memory.
  • The IOMMU (Intel VT-d, AMD-Vi, Arm SMMU) translates each IOVA and checks that this Requester ID (0x0100 for our SSD) is allowed to access it, in that direction. A failed check produces a fault record in the IOMMU and a log line in the kernel; the TLP is blocked.
  • Caches. On x86, DMA is cache coherent; on some embedded platforms the driver must flush or invalidate caches for the list and data pages. A list written by the CPU but still in a write-back cache on a non-coherent system is a classic "the controller read stale list entries" bug Implementation-dependent.

Because the controller can compute the page for any byte directly, it is free to move data out of order — for example, finishing the third page of a Read before the first if that NAND die answered first. Analyzer traces of large Reads often show data TLP addresses that are not monotonic. That is legal and is not a PRP bug.

Specification view

Three documents are involved:

  • NVM Express Base Specification, Revision 2.4 — Physical Region Page Entry and List; Submission Queue Entry (Data Pointer, PSDT); Controller Configuration (MPS); Controller Capabilities (MPSMIN, MPSMAX); Identify Controller (MDTS); Generic Command Status values
  • NVM Express NVMe over PCIe Transport Specification, Revision 1.4 — how the data pointer and queues work when the transport is PCIe, including that PRPs are the data pointer mechanism for admin commands.
  • NVM Express NVM Command Set Specification, Revision 1.3 — Read and Write commands (Starting LBA, Number of Logical Blocks) — the source of the transfer length the PRPs must cover.
  • PCI Express Base Specification, Revision 6.x/7.0 — Transaction Layer: Memory Requests, Completions, Max Payload Size, Max Read Request Size, Read Completion Boundary — the rules for the TLPs that move the data.

The definitions of PRP entry and PRP list, the offset rules, and the meaning of PRP2 are Normative. Figures and examples that show lists are Informative. How a controller fetches, caches or validates lists is not specified.

  • A PRP entry is a 64-bit address; bits 1:0 are zero; the offset field width depends on the memory page size.
  • Memory page size is 212 + CC.MPS, constrained by CAP.MPSMIN and CAP.MPSMAX.
  • PRP1 may have an offset; a PRP2 used as a data pointer and every data entry in a PRP list have an offset of zero.
  • PRP2 is a list pointer when the transfer crosses more than one memory page boundary; the last entry of a full list page points to the next list page when more entries are needed.
  • PSDT = 00b in Command Dword 0 selects PRPs for the data pointer.
  • The page-count formula N and the slots-per-list-page formula S follow from the rules; they are not quoted text.
  • PRPs can only describe a buffer whose interior pages are fully used — a consequence of offset-zero entries without length fields.
  • The number of TLPs is a consequence of PCIe rules applied to the PRP-derived address ranges, not of the NVMe specification.
  • Whether a controller checks offsets and reports PRP Offset Invalid, or simply uses the address.
  • How and when list pages are fetched (all at once, on demand, with prefetch).
  • The order data TLPs are issued in, their exact sizes below the PCIe maximums, and how many requests are outstanding.
  • Driver choices: Linux's fixed 4 KiB controller page, its 256-byte small list pool, when it chooses SGLs instead.

PRPs have existed since NVMe 1.0 and their core rules have been stable through the 2.x series; the 2.0 restructuring moved transport-specific material into the separate NVMe over PCIe Transport Specification, so older documents describe the same rules in a single base specification. Field names and section titles differ between revisions; always cite the revision you read. In NVMe-oF transports PRPs are not used — data pointers there are SGLs (Chapter 37).

  • The specification does not say a controller must detect every malformed PRP set. Undetected cases lead to undefined data movement.
  • It does not define a length field in PRP entries or a marker for chain pointers.
  • Check in the specification: the exact wording on PRP list pointer offsets and on chain-pointer alignment; which commands forbid a PRP1 offset; the value of the PRP Offset Invalid status code in the Generic Command Status table (13h in the revisions this author has read Confirm); MDTS units.
  • Never assume PRP2 is unused because "the buffer is only 4 KiB" — offsets change the page count.
  • Never assume a PRP address is a CPU physical address when an IOMMU is present.
  • Never assume a controller that accepted a bad PRP set has validated it.
  • Never assume the data TLPs arrive in address order.

Ordering

The controller cannot send data to page 5 before it has read the list entry for page 5, so list reads precede the data that depends on them. The host must have finished writing the list and SQE before the doorbell; on x86 the doorbell MWr is ordered behind the earlier memory writes by the driver's write barrier. The CQE write must not overtake the data writes it reports: PCIe ordering rules keep posted MWr in order unless Relaxed Ordering is set, and controllers that set Relaxed Ordering on data must not set it on the CQE write. See Chapter 14 — PCIe Ordering.

The 4 KiB boundary and PRP pages

PCIe forbids a single memory request from crossing a 4 KiB address boundary. With a 4 KiB memory page size, every PRP page boundary is also a 4 KiB boundary, so a TLP never spans two PRP pages. With larger memory page sizes (for example 64 KiB) the device still has to cut TLPs at every 4 KiB address boundary inside a PRP page.

Code / pseudocode

The host-side algorithm, written the way a driver writes it. This is simplified from the shape of real drivers; it assumes one virtually contiguous buffer already mapped to a single IOVA range, which is the simplest case.

/* ps: memory page size (1 << (12 + CC.MPS)); iova: DMA address of byte 0; len: bytes */
int build_prps(struct sqe *cmd, u64 iova, u32 len, u32 ps)
{
    u32 off   = iova & (ps - 1);
    u32 first = min(len, ps - off);             /* bytes covered by PRP1         */
    u32 npages = (off + len + ps - 1) / ps;     /* pages touched (uses offset!)  */

    if (iova & 3) return -EINVAL;               /* PRP1 must be dword aligned    */
    cmd->prp1 = iova;
    if (npages == 1) { cmd->prp2 = 0; return 0; }
    u64 next = (iova - off) + ps;               /* page-aligned second page     */
    if (npages == 2) { cmd->prp2 = next; return 0; }

    u64 *list = alloc_list_page(&list_iova);    /* must be DMA-mapped too        */
    cmd->prp2 = list_iova;
    u32 slot = 0, slots = ps / 8;               /* page-aligned list: 512 slots  */
    for (u32 left = npages - 1; left; left--) {
        if (slot == slots - 1 && left > 1) {    /* last slot, more than 1 to go  */
            u64 *nl = alloc_list_page(&nl_iova);
            list[slot] = nl_iova;               /* chain pointer                 */
            list = nl; slot = 0;
        }
        list[slot++] = next;
        next += ps;
    }
    write_barrier();                            /* list visible before doorbell  */
    return 0;
}

Note the condition left > 1: if exactly one entry remains when we reach the last slot, it goes in that slot as data. The off-by-one variant left > 0 wastes a page and, worse, disagrees with the controller, which expects data in that slot. That bug is a case in Chapter 38.

A small executable calculator for the arithmetic. It prints, for each buffer, the page count, PRP2's role and the list layout. The full PRP walker with TLP prediction and a checker is in Chapter 38.

#!/usr/bin/env python3
"""Count pages and PRP list entries for NVMe buffers. Standard library only."""

def prp_shape(addr, length, ps=4096, list_ptr=None):
    off = addr % ps
    pages = (off + length + ps - 1) // ps
    if pages == 1:
        return pages, "PRP2 unused", []
    if pages == 2:
        return pages, "PRP2 = second page", []
    entries = pages - 1
    lp = list_ptr if list_ptr is not None else 0   # offset of list in its page
    layout, left = [], entries
    while left:
        slots = (ps - lp % ps) // 8
        if left > slots:
            layout.append((slots - 1, "chain"))
            left -= slots - 1
        else:
            layout.append((left, "end"))
            left = 0
        lp = 0                                        # chained pages start aligned
    return pages, "PRP2 = list pointer", layout

if __name__ == "__main__":
    for addr, n, lp in [(0x200000000, 4096, None), (0x200000800, 4096, None),
                        (0x200000800, 8192, None), (0x200000000, 131072, None),
                        (0x200000000, 1 << 20, 0xC00), (0x200000000, 4 << 20, 0)]:
        pages, role, layout = prp_shape(addr, n, list_ptr=lp)
        desc = ", ".join(f"{k} data + {t}" for k, t in layout) or "-"
        print(f"0x{addr:x} len {n:>8}: {pages:>4} pages, {role:<20} lists: {desc}")

Running it prints one line per buffer (the 1 MiB case with its list starting at offset 0xC00 shows 127 data + chain, 128 data + end; the 4 MiB case shows 511 data + chain, 512 data + end). Run it yourself rather than trusting this paragraph.

Worked example

Five buffers, all on the lab system (memory page size 4 KiB, PCIe Max Payload Size 256 bytes, MRRS 512 bytes, RCB 64 bytes, data buffers from 0x2_0000_0000, PRP list pages from 0x1_5000_0000, Namespace 1 with 512-byte logical blocks). Every value below is a synthetic example for teaching. For each buffer we compute the pages, write the PRP set, draw it, and predict the data TLPs. TLP counts assume a controller that cuts requests at naturally aligned Max Payload Size or MRRS boundaries; real devices may cut differently Implementation-dependent, but none may exceed the limits.

Example 1 — 4 KiB, page aligned

Read of 8 blocks: NLB = 7 (zero-based), L = 8 × 512 = 4,096 bytes, buffer at 0x2_0000_0000.

  • Offset = 0; N = ⌈(0 + 4096) / 4096⌉ = 1 page. No boundary crossed.
  • PRP1 = 0x0000_0002_0000_0000; PRP2 unused (the driver writes 0; the controller ignores it).

Example 2 — 8 KiB, page aligned

Read of 16 blocks: NLB = 15, L = 8,192 bytes, buffer at 0x2_0000_0000, physically two consecutive pages. (They need not be consecutive; the second could be anywhere.)

  • Offset = 0; N = 2. Exactly one boundary crossed.
  • PRP1 = 0x2_0000_0000, PRP2 = 0x2_0000_1000 (a data page, offset 0).

Read: 32 MWr of 256 B. Write: 16 MRd of 512 B, answered by 32 to 128 CplD. If page B had been 0x2_0009_3000 instead, the TLP addresses would jump from 0x2_0000_0F00 to 0x2_0009_3000 halfway through; nothing else would change.

Example 3 — 4 KiB with an offset, crossing a page

Read of 8 blocks into a buffer at 0x2_0000_0800 (offset 0x800 = 2,048). L = 4,096 bytes.

  • N = ⌈(2048 + 4096) / 4096⌉ = 2. One boundary crossed, so PRP2 is needed even though the buffer is "only 4 KiB".
  • B1 = min(4096, 4096 − 2048) = 2,048 bytes in the first page.
  • PRP1 = 0x2_0000_0800, PRP2 = 0x2_0000_1000.

Read: 16 MWr (8 + 8). Write: 8 MRd of 512 B (4 per page; 0x800 is 512-aligned). Now change the offset to 0x810: the controller's first MWr can only run to the next 256-byte boundary (0x900), so it carries 240 bytes; then 15 full 256-byte writes; then a final 16-byte write at 0x2_0000_1800. That is 17 MWr — one more packet, and two short ones, for the same 4 KiB. Unaligned buffers cost link efficiency, which is one reason drivers prefer aligned buffers.

Example 4 — 128 KiB, requiring a PRP list

Read of 256 blocks: NLB = 0xFF, L = 131,072 bytes, buffer at 0x2_0000_0000 (32 pages, here shown consecutive for readability).

  • N = 32; more than one boundary crossed → PRP2 is a list pointer.
  • List entries = N − 1 = 31, size 248 bytes; list at 0x1_5000_0000 has 512 slots, so no chaining.
  • PRP1 = 0x2_0000_0000, PRP2 = 0x1_5000_0000.

At roughly 7.9 GB/s of raw Gen4 x4 bandwidth per direction, 128 KiB of data takes about 18 µs on the link. The list fetch adds one dependent round trip (about 0.6–1 µs) but is hidden behind the NAND read time on a Read.

Example 5 — 1 MiB with chained lists

Read of 2,048 blocks: NLB = 0x7FF, L = 1,048,576 bytes, buffer at 0x2_0000_0000. This needs a controller whose MDTS allows 1 MiB (MDTS ≥ 8 with a 4 KiB minimum page). N = 256 pages, so 255 list entries are needed.

If the list started at the beginning of a list page, 255 entries would fit in its 512 slots and there would be no chain. To see chaining with 1 MiB, the list pointer in this example has an offset: the driver placed the list at 0x1_5000_0C00, three quarters of the way into its page (legal: PRP2 as a list pointer need only be quadword aligned).

  • Slots left in the first list page: S = (4096 − 0xC00) / 8 = 1024 / 8 = 128.
  • 255 > 128, so slots 0–126 carry data pages 1–127, and slot 127 (at 0x1_5000_0FF8) is a chain pointer to the next list page, 0x1_5000_1000.
  • Remaining entries: 255 − 127 = 128. The next list page has 512 slots, so all 128 fit (0x1_5000_1000 … 0x1_5000_13F8). No further chain.
  • PRP1 = 0x2_0000_0000, PRP2 = 0x1_5000_0C00.

Contrast: with a page-aligned 4 MiB buffer (1,024 pages, 1,023 entries) the first list page holds 511 data entries and a chain pointer, the second holds the remaining 512 entries exactly — no second chain, because when the remaining entries equal the slots available, the last slot is data. Few controllers accept 4 MiB in one command; check MDTS.

Before reading on, compute the PRP set for a 12 KiB Write at 0x2_0000_0FFC. (Answer: offset 0xFFC, N = ⌈(4092 + 12288) / 4096⌉ = 4 pages; PRP1 = 0x2_0000_0FFC covers 4 bytes; PRP2 points to a 3-entry list: 0x2_0000_1000, 0x2_0000_2000, 0x2_0000_3000, the last of which holds the final 4,092 bytes.)

Debugging connection

A PRP problem is a disagreement between two computations of the same thing: the host's idea of where the bytes live and the controller's. Debugging is the act of reproducing both computations from evidence and finding the first place they diverge.

  1. Get the command. From an analyzer, decode the SQE CplD: opcode, NSID, PRP1, PRP2, Starting LBA, NLB. From software, log them in the driver or user-space tool.
  2. Compute L from the namespace format, not from the application. L = (NLB + 1) × LBA data size (+ metadata if extended LBAs are used). An LBA format change from 512 B to 4 KiB multiplies L by eight for the same NLB.
  3. Compute N and PRP2's role from PRP1's offset and the page size from CC.MPS.
  4. Predict the list reads (address, length) and check they appear in the trace at exactly PRP2 and at each chain pointer.
  5. Predict data TLP addresses per page and compare. The first data TLP to an unexpected page is your first abnormal event.
  6. Correlate host-side evidence: IOMMU faults (address, direction, device), kernel warnings about DMA mapping, memory corruption reports.

The full set of broken cases, with traces, is Chapter 38 — PRP/SGL Debugging Lab. The correlation method for any command is Chapter 41 — Command-to-TLP Correlation.

Senior engineer insight

  • Treat the length as the primary suspect. In practice, malformed PRP structures are rarer than correct structures built for the wrong length. Format changes, zero-based fields, metadata sizes and protection information all change L without changing the buffer.
  • "Success" is not evidence that the data went where you think. Posted writes blocked by an IOMMU produce no error back to the device. A Read that completes with Success status can still have delivered nothing. Always pair storage results with the IOMMU log.
  • List lifetime is a protocol. The list must remain valid and mapped until the CQE is consumed. Abort and timeout paths that free resources early are where use-after-free DMA bugs come from.
  • Prefetching hides bugs. A controller that fetches the entire list page up front reads slots the host never wrote; one that fetches on demand does not. The same buggy driver can pass on one SSD and corrupt memory on another.
  • Page size is a system decision. On hosts with large pages, a 4 KiB controller page multiplies list size and fetches; a 64 KiB controller page (if CAP.MPSMAX allows) shrinks lists but forces all interior data pointers to be 64 KiB aligned. Most drivers choose 4 KiB for compatibility.
  • When PRPs hurt, use SGLs. Many small, unaligned fragments, or metadata that is scattered, are expressed naturally by SGLs — if the controller supports them (Chapter 37).

Challenge

Find the smallest transfer length that needs a chained list when the list pointer is page aligned and PRP1 has offset 0. Then find it when PRP1 has offset 4.

Hint

A page-aligned list page holds 511 data entries plus a chain, or 512 data entries without one. Chaining starts when the list needs 513 entries.

Solution
  • (a) L = 4,096; N = 1; PRP1 = 0x2_0010_0000; PRP2 unused; 16 MWr.
  • (b) L = 2,048; offset 0xE00 leaves 512 bytes in page 0; N = 2; PRP1 = 0x2_0010_0E00, PRP2 = 0x2_0010_1000 (data page, 1,536 bytes used); 8 MWr (2 + 6).
  • (c) L = 16,384; offset 0x200; N = ⌈(512 + 16384)/4096⌉ = 5; PRP2 = 0x1_5000_2000 list with 4 entries (32 B, 1 MRd); data: each page section is 512-aligned, so 32 MRd of 512 B.
  • (d) L = 131,072; N = 32; 31 entries; list at offset 0xF00 has S = 32 slots; 31 ≤ 32 so no chain; one MRd of 248 B; 256 MRd for data.
  • (e) L = 1,048,576; offset 4 → N = 257; 256 entries in a page-aligned list (512 slots) → no chain; PRP1 covers 4,092 bytes, the last page 4 bytes. Data MWr: the first page yields 16 TLPs (first is 252 B), pages 1–255 yield 16 each, the last page 1 → 4,097 MWr.
  • Challenge: page-aligned list, offset 0: 513 list entries means N = 514 pages → L > 513 × 4096 = 2,101,248 bytes, so the smallest is 2,101,249 bytes. With PRP1 offset 4 the first page holds 4 bytes less, so N ≥ 514 when 4 + L > 2,101,248, i.e. the smallest is 2,101,245 bytes. (Real I/O is in whole blocks: at offset 0, 4,104 blocks of 512 B fill exactly 513 pages and do not chain; the smallest chaining Read is 4,105 blocks.)

What a senior engineer notices

Row (e) is legal but wasteful: an odd offset adds a page, a list entry, and a short TLP at both ends. In a performance investigation, a stream of 252-byte and 4-byte MWr is the fingerprint of misaligned user buffers.

Failure variants

  • Row (b) built with PRP2 = 0: second chunk goes to address 0.
  • Row (d) built with a list pointer of 0x1_5000_2F80 (16 slots): the list must chain after 15 entries.
  • Row (a) with NLB set to 8 instead of 7: 4,608 bytes, N = 2, PRP2 required but unset.

Exercises

  1. A 64 KiB Read at 0x2_0020_0100 with 4 KiB pages: give N, PRP2 role, and the list length in bytes.
    Answer

    N = ⌈(256 + 65536)/4096⌉ = 17; PRP2 is a list pointer; 16 entries = 128 bytes.

  2. With CC.MPS = 1 (8 KiB pages), how many slots does a page-aligned list page have, and how much data can one list page describe?
    Answer

    8192 / 8 = 1,024 slots; without chaining up to 1,024 pages of 8 KiB = 8 MiB beyond PRP1's page.

  3. Explain why the controller cannot be told directly that PRP2 is a list pointer, and what that implies for debugging.
    Answer

    There is no flag; the role is derived from length and offset. Any disagreement about length (format, NLB, metadata) changes the role, so debugging starts by recomputing length from the controller's point of view.

  4. Write the PRP set for an Identify command whose 4 KiB buffer sits at 0x2_0000_0400.
    Answer

    PRP1 = 0x2_0000_0400 (3 KiB), PRP2 = 0x2_0000_1000 (1 KiB). Identify uses PRPs over PCIe like any admin command.

  5. A list pointer is 0x1_5000_0FF8. How many entries can the first list page hold, and what must the single slot contain if 5 pages remain?
    Answer

    One slot. With 5 entries remaining (> 1), the slot must be a chain pointer to the next list page, which then holds all 5 entries. Legal, but a wasted round trip.

  6. Count MWr TLPs for a 4 KiB Read at offset 0x10 with Max Payload Size 128 B.
    Answer

    First page: 0x010–0x07F (112 B) then 31 full 128 B TLPs to 0xFFF; second page: 16 B at 0x000. Total 33.

    • The address of byte 3,072 of the buffer
    Answer and reasoning

    The offset makes the transfer cross exactly one page boundary (3 KiB + 1 KiB), so PRP2 is the second data page, offset zero.

  2. Which PRP item may have a non-zero page offset?

    • Every list entry
    • PRP2 when it is a data pointer
    • PRP1
    • None of them
    Answer and reasoning

    Only PRP1 may carry an offset among data pointers. (PRP2 as a list pointer may also have one, but it then points to a list, not to data.)

  3. CC.MPS = 2. What is the memory page size?

    • 4 KiB
    • 8 KiB
    • 16 KiB
    • 256 bytes
    Answer and reasoning

    212+2 = 16,384 bytes.

  4. A page-aligned PRP list page with 4 KiB pages. Exactly 512 entries remain to be listed. What goes in slot 511?

    • The 512th data page
    • A chain pointer
    • Zero, as a terminator
    • The list length
    Answer and reasoning

    A chain pointer is only needed when more entries remain than slots. 512 fit exactly, so slot 511 is data. There is no terminator in a PRP list.

  5. An NVMe Write of 8 KiB, MRRS 512 bytes. How many data MRd TLPs does an aligned buffer need at minimum?

    • 8
    • 16
    • 32
    • 2
    Answer and reasoning

    8,192 / 512 = 16. Each is answered by one or more CplD.

  6. With the IOMMU enabled, a PRP entry contains:

    • A user-space virtual address
    • A CPU physical address
    • An I/O virtual address that the IOMMU translates
    • A namespace LBA
    Answer and reasoning

    The device emits IOVAs; the IOMMU translates and permission-checks them.

  7. Why are PRP list entries page aligned?

    Model answer

    So the controller can locate any byte by index arithmetic (page index = byte offset / page size) without carrying lengths, which keeps the entries 8 bytes and the hardware simple; the price is that only the first page can start mid-page.

  8. A Read completes with Success, yet the application buffer is unchanged and the kernel log shows an IOMMU fault for 01:00.0 at a page address. Explain how both can be true.

    Model answer

    Data MWr are posted: the device never learns that the IOMMU blocked them. The controller completes normally. The fault shows a PRP entry (or a list) pointed at an unmapped IOVA — a wrong, stale or freed entry.

  9. Name two pieces of information you need, besides the SQE, to know what PRP2 means.

    Model answer

    The memory page size (from CC.MPS) and the namespace's LBA data size (and metadata layout) to turn NLB into bytes. The offset comes from PRP1 itself.

  10. Why might you see two short MWr TLPs at the start and end of an otherwise 256-byte stream?

    Model answer

    The buffer starts at an offset that is not a multiple of 256; the first TLP runs only to the next 256-byte boundary and the last covers the remainder. Exact cut points are implementation-dependent.

Interview questions

  1. Beginner: What are PRP1 and PRP2?
    Model answer

    The two 64-bit entries of the data pointer in an NVMe SQE when PRPs are selected. PRP1 points to the first byte; PRP2 is unused, the second page, or a pointer to a PRP list, depending on how many page boundaries the transfer crosses.

  2. Beginner: What sets the page size PRPs use?
    Model answer

    CC.MPS, written by the host before enabling the controller, within CAP.MPSMIN–CAP.MPSMAX; page size = 212+MPS.

  3. Intermediate: Walk me through building PRPs for a 20 KiB buffer at offset 0x100.
    Model answer

    N = ⌈(256 + 20480)/4096⌉ = 6; PRP1 = buffer address; PRP2 = list pointer to 5 page-aligned entries; one list read of 40 bytes; data in 6 pages, first 3,840 bytes, then 4 full pages, last 256 bytes.

  4. Intermediate: Why does Linux set a virtual boundary for NVMe queues?
    Model answer

    So the block layer never merges segments into a request whose interior has gaps or sub-page starts, which PRPs cannot describe; such requests are split instead.

  5. Advanced: A driver works with one SSD and corrupts memory with another. PRP lists are suspected. What do you look for?
    Model answer

    Behaviour that depends on how much of the list the controller reads: entries beyond the computed count, stale entries, a list running off its page, list freed early. A controller that prefetches whole list pages will consume slots the driver did not intend; compare list fetch lengths in traces from both SSDs.

  6. Advanced: How do PRP boundaries relate to the PCIe 4 KiB rule?
    Model answer

    With 4 KiB memory pages every PRP page boundary is a 4 KiB address boundary, so TLPs never span pages. With larger pages, the device must additionally cut at 4 KiB boundaries inside a page.

  7. Senior: Design a validation plan for PRP handling in a new controller.
    Model answer

    Matrix of offsets (0, 4, 0x800, PS−4), lengths at and around 1, 2, list-page-full and chain thresholds, list pointers at page start, mid-page and last slot, chained lists of 2–3 pages, MDTS-sized commands, every supported CC.MPS; negative tests for invalid offsets with expected status; IOMMU-enabled runs with fault monitoring; data-integrity checks with patterns per page; analyzer checks that no TLP touches an address outside the PRP set.

  8. Senior: When would you prefer SGLs over PRPs on PCIe?
    Model answer

    When buffers are fragmented at sub-page granularity, when metadata is scattered, when a Bit Bucket is useful for reads, or for very large transfers where descriptor count beats page count; only if the controller advertises SGL support, and measured, because some controllers are faster with PRPs for small I/O.

Teach-back challenge

  • To a child: explain the order card with two lines and the clipboard, and why every shelf after the first starts at its beginning.
  • To a junior engineer: take a buffer address and length and derive PRP1, PRP2 and the list on a whiteboard, including the zero-based NLB.
  • To a senior engineer: argue why most PRP bugs are length bugs, and how you would prove it from an analyzer trace and an IOMMU log.
Model explanation (junior)

"Take the offset of the address within a 4 KiB page, add the length, divide by 4,096 and round up. That's the number of pages. One page: PRP1 only. Two: PRP2 is the second page's start. More: PRP2 points to a list with one 8-byte entry per remaining page. If the list would run off its page, the last slot points to another list page. And length is (NLB+1) × block size."

Chapter summary

  • PRP entries are 64-bit page-relative addresses; the memory page size comes from CC.MPS.
  • PRP1 may have an offset; all other data pointers are page aligned; interior pages are used fully.
  • PRP2's role — unused, second page, list pointer — is derived from the number of page boundaries crossed.
  • PRP lists hold one entry per page after the first; a full list page chains through its last slot.
  • The addresses are what the device emits: IOVAs when an IOMMU translates.
  • Data TLPs follow the pages, cut by Max Payload Size, MRRS and the 4 KiB rule; list fetches are extra dependent reads.
  • Most PRP bugs are disagreements about length or offset, and many fail silently.

Do not move on until you can:

  • derive page size from CC.MPS and state the PRP entry bit split
  • compute N and PRP2's role for any address and length, including offsets
  • build a chained PRP list and place the chain pointer correctly
  • predict list fetches and data TLP counts from MPS, MRRS and RCB
  • find the first abnormal event in a PRP trace and name the length disagreement behind it
  • explain why an IOVA appears in PRPs on an IOMMU system
