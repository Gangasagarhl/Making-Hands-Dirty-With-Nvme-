Non-Volatile Memory Express (NVMe) is a storage protocol: a precise agreement about how a host asks a storage device to do work and how the device answers. This chapter builds the complete mental model of that agreement, from the host and its driver down through the NVM subsystem, the controller and the namespace to the media, and it separates the three things learners most often blur together: the NVMe protocol, the command sets that give it meaning, and the transports that carry it.

Why this chapter exists

Up to this point the course has taught Peripheral Component Interconnect Express (PCIe) from the ground up: links, layers, Transaction Layer Packets (TLPs), configuration space, Base Address Registers (BARs) and Direct Memory Access (DMA). You can now describe how bytes move between a device and host memory. What you cannot yet describe is why a storage device moves those particular bytes, at that moment, to that address. That "why" is NVMe.

Many engineers learn NVMe as a list of registers and opcodes. They can recite that Read is opcode 02h and that the controller registers start at BAR0, yet they freeze when an analyzer shows a Memory Read TLP from the SSD to an address they do not recognize. The gap is the mental model: which actor owns which object, which object lives where, and which layer is speaking at each moment. This chapter installs that model before the next chapters fill it with detail.

It also prevents the single most expensive confusion in this field: treating "NVMe" and "PCIe" as one thing. They are two independent technologies. NVMe defines storage semantics; PCIe moves packets; the NVMe over PCIe Transport specification binds the two. The rest of the course depends on keeping those three apart.

The story

Imagine a school with a gigantic library in the basement. The teacher (the CPU) does not go down to the library for every book. Instead, the school agrees on a set of rules: the teacher writes requests on slips of paper of exactly one size, puts them in a numbered request box on the classroom wall, and rings a little bell that sounds in the library. The librarian hears the bell, walks up, reads the new slips, goes back down, and carries the books straight to the right tables in the classroom without bothering the teacher. When each job is done, the librarian drops a small answer card into an answer box and taps on the classroom window.

The rules — slip size, what can be written on a slip, how the boxes work, what the answer card says — are NVMe. The staircase and corridor the librarian uses are PCIe. The signs on the staircase that tell everyone "request boxes are on this wall, the bell is this button" are the NVMe over PCIe Transport rules. The library itself can have several librarians (controllers), and the books are kept in separate sections (namespaces), each with its own numbering.

An adult version: think of an international shipping contract. The contract defines what an order looks like, what each field means, how an order is acknowledged, and what "delivered damaged" means. It says nothing about whether goods move by ship, rail or air. Separately, each carrier has its own rules about containers, labels and routing. A third document, the "carriage annex", explains how to pack contract orders into that carrier's containers. NVMe is the contract, PCIe is one carrier (Remote Direct Memory Access (RDMA) fabrics and TCP/IP networks are others), and the NVMe over PCIe Transport specification is the carriage annex.

  • The librarian is not a person waiting at a desk. A real controller is hardware and firmware with many parallel engines; it can fetch dozens of slips from dozens of boxes at once.
  • There are many request boxes, not one. NVMe allows up to 65,535 I/O submission queues plus the admin queue; the analogy hides that parallelism, which is the whole point of NVMe.
  • The bell carries a number. A doorbell write carries the new tail index, not just "ding". The librarian learns how many new slips there are from that number.
  • The answer card does not say which table the books went to. A completion entry identifies the command and its status; the data location was already in the command.
  • The shipping analogy hides that the host owns the memory. In NVMe over PCIe, the request boxes, answer boxes and data buffers all live in host memory; the device reaches into host memory with DMA. Carriers in real life never reach into your warehouse.
  • "NVMe = the rules" is incomplete. NVMe also defines architecture objects (subsystem, controller, namespace) that exist even when no command is in flight.

Beginner explanation

A computer needs to keep data when the power is off. Solid-state drives (SSDs) do that with flash memory. The computer's processor and the SSD are separate chips, so they need a shared language to talk. NVMe is that language for modern SSDs.

The language has a small number of ideas:

  • Commands. Every request is a fixed-size 64-byte message. "Read 8 blocks starting at block 1000 into this memory buffer" is one command.
  • Queues. Commands are not handed over one at a time. The host writes them into a submission queue, a ring of command slots in the host's memory. The device writes answers into a completion queue, another ring in host memory. Each completion is a 16-byte message.
  • Doorbells. The host tells the device "there are new commands up to slot N" by writing the number N into a special device register called a doorbell.
  • Controller. The part of the SSD that understands NVMe: it reads commands, does the work and writes completions.
  • Namespace. A numbered collection of storage blocks that commands read and write. Most consumer SSDs have one namespace; enterprise SSDs can have many.
  • Subsystem. The whole NVMe "thing": all controllers, all namespaces, and the ports through which hosts reach them.

And one idea that belongs to a different technology: the transport. Something has to physically carry commands, data and completions. Inside a computer that is usually PCIe. Across a data-center network it can be TCP or RDMA. NVMe the language stays the same; the carrier changes.

When someone says "NVMe wrote to NAND page 4021" they are describing firmware internals, not NVMe.

Host and NVMe driver

The host side has two jobs. First, it owns memory: in NVMe over PCIe, the submission queues, completion queues and data buffers are allocated by the host in host memory, and the device reaches them with DMA. Second, it initiates: the controller never does work it was not asked to do through a queue (with a few exceptions, such as asynchronous events, which are themselves answers to an outstanding request).

The driver (in Linux, the nvme and nvme-core modules) does the following, in order, over the lifetime of a device:

  1. Maps the controller's registers (through BAR0 for PCIe).
  2. Resets and enables the controller, after describing the admin queue (NVMe Registers).
  3. Sends admin commands: Identify, Set Features (Number of Queues), Create I/O Completion Queue, Create I/O Submission Queue (Admin Queue).
  4. Discovers namespaces and presents each as a block device (/dev/nvme0n1).
  5. For each I/O request from the block layer, builds a 64-byte command, places it in an I/O submission queue, rings the doorbell, and later consumes the 16-byte completion.

The NVMe protocol

The NVMe protocol is the set of rules for that conversation. Strip away every transport detail and what remains is:

  • A command format. A 64-byte Submission Queue Entry (SQE): Command Dword 0 with the opcode and Command Identifier (CID), the NSID, data pointer fields, and six command-specific dwords.
  • A completion format. A 16-byte Completion Queue Entry (CQE): command-specific result, the SQ head pointer and SQ identifier, the CID being completed, a Phase Tag, and a Status field (Status Code Type, Status Code, Do Not Retry, More).
  • A queueing model. Paired circular queues with head and tail pointers; the producer owns the tail, the consumer owns the head.
  • An architecture. Subsystem, controllers, namespaces, ports, and how they relate.
  • A command vocabulary. Admin commands (Identify, Create I/O SQ, Get Log Page, Set Features…) and I/O commands defined per command set (Read, Write, Flush… for the NVM Command Set).
  • A state model. How a controller is enabled, becomes ready, shuts down, resets and reports fatal errors.

The protocol is asymmetrical on purpose. The host is always the one who submits; the controller is always the one who completes. The controller does not push commands to the host. That asymmetry is why every NVMe trace has a recognizable rhythm: host writes doorbell, device reads command, device moves data, device writes completion, device signals interrupt, host writes completion doorbell.

Command sets

A command set is a vocabulary of commands with defined meaning. NVMe has two layers of vocabulary:

  • The Admin Command Set, used on the admin queue to manage the controller: discover capabilities, create and delete I/O queues, read logs, set features, manage namespaces, update firmware. In the NVMe 2.x family it is defined in the NVMe Base Specification.
  • I/O command sets, used on I/O queues to act on namespaces. The most common is the NVM Command Set (block storage: Read, Write, Flush, Dataset Management, Write Zeroes, Compare…). Others include Zoned Namespaces (ZNS), Key Value (KV), Computational Programs, and Subsystem Local Memory (SLM). Each I/O command set has its own specification in the 2.x family (NVMe 2.x Architecture).

Every namespace is associated with exactly one I/O command set. A host reading a KV namespace uses KV commands (Store, Retrieve…); a host reading an NVM namespace uses Read and Write. The Command Set Identifier (CSI) tells the host which vocabulary a namespace speaks.

Opcode numbers are only meaningful within a command set and queue type. Admin opcode 02h is Get Log Page; NVM I/O opcode 02h is Read. A decoder that ignores which queue a command came from will mislabel commands. This is a classic analyzer-configuration mistake.

Transports

A transport is how NVMe objects are carried between host and controller. The NVMe 2.x family defines three transport specifications:

The memory-based transport (PCIe) and the message-based transports (RDMA, TCP; collectively "NVMe over Fabrics") differ in a deep way. In PCIe, the controller registers are physically addressable memory and queues are shared memory. In fabrics, registers become properties read and written with Property Get and Property Set commands, and queues are logical constructs carried as capsules. NVMe's Base Specification is written in terms general enough to cover both, which is why it talks about "properties" where older revisions said "registers". This course focuses on PCIe and visits fabrics in NVMe-oF Mental Model.

The controller model

A controller is defined by what it holds and what it does:

  • Properties (registers). Capabilities (CAP), Version (VS), Controller Configuration (CC), Controller Status (CSTS), Admin Queue Attributes (AQA), and the admin queue base addresses (ASQ, ACQ). In PCIe they live at the start of BAR0. NVMe Registers treats them field by field.
  • Queues. Exactly one admin queue pair and zero or more I/O queue pairs. Many submission queues may share one completion queue.
  • Doorbells. One tail doorbell per SQ and one head doorbell per CQ (in PCIe, starting at offset 1000h of BAR0).
  • Data structures it reports. Identify Controller data, log pages, features.
  • State. Disabled, enabling, ready, shutting down, shut down, fatal.
  • Attached namespaces. The set of namespaces this controller can access.

The subsystem model

The NVM subsystem is the outer box. A simple consumer SSD is an NVM subsystem with one controller, one namespace and one PCIe port. An enterprise dual-port SSD may be one subsystem with two PCIe ports, a controller behind each port, and namespaces shared by both controllers so two servers can reach the same data. A device using Single Root I/O Virtualization (SR-IOV) may expose a controller per virtual function (SR-IOV). An array reached over fabrics is a subsystem with many ports and controllers created on demand.

The key relationships:

  • A namespace belongs to the subsystem, not to a controller. Controllers get access to it by attachment.
  • An NSID refers to the same namespace from every controller in the subsystem that can see it (NSIDs are subsystem-wide).
  • A controller is associated with exactly one host at a time in the sense of its queues (a host owns the queues it created); multiple hosts reach shared data through multiple controllers.
  • Ports are the transport-facing doors. In PCIe a port is a PCIe port of the device.

Why NVMe looks the way it does

Earlier storage interfaces were designed around rotating disks whose seek times dwarfed interface overhead. The Advanced Host Controller Interface (AHCI) used with Serial ATA (SATA) had one command queue of 32 entries and needed multiple uncacheable register reads per command. Flash removed the mechanical delay, and suddenly the interface overhead and the single queue became the bottleneck (From SATA/SAS to NVMe).

The teaching ladder for NVMe

A rule book for asking a library for books: same-size request slips, a request box per classroom, a bell, an answer box, and a librarian who carries books straight to your table.

NVMe is a host-to-storage protocol built on paired submission and completion queues, fixed-size commands and completions, doorbells and interrupts, organised around an NVM subsystem that contains controllers and namespaces.

In a PCIe SSD, the controller is an ASIC with an embedded processor complex, a PCIe endpoint, DMA engines and a NAND interface. Its registers appear in BAR0; doorbells start at BAR0 + 1000h; queues and data buffers are in host DRAM and are reached by DMA.

The NVMe Base Specification (Revision 2.4 in the August 2026 set) defines the architecture, the Admin Command Set, the queueing model and the controller properties. I/O command set specifications (NVM Command Set 1.3 and others) define I/O commands. The NVMe over PCIe Transport Specification (1.4) defines the memory-mapped register layout, doorbells, PRP/SGL use over PCIe and interrupts.

On the PCIe link one NVMe I/O appears as: host MWr (doorbell) → device MRd (fetch SQE) → CplD → device MWr or MRd for data → device MWr (CQE) → device MWr (MSI-X) → host MWr (CQ head doorbell).

In an analyzer, you identify the doorbell by its address (BAR0 + 1000h + stride × index), the SQE fetch by a 64-byte read to the known SQ base, the CQE by a 16-byte write to the known CQ base, and the interrupt by a write to the MSI-X message address.

When a command "hangs", you walk the rhythm: was the doorbell written? did the device fetch? did data move? was a CQE written? did the interrupt fire? did the host ring the CQ head doorbell? The first missing step localises the fault to host, link or device.

The sixteen questions, answered for NVMe

1. What is it?
A storage protocol and architecture for accessing non-volatile memory through paired queues, defined by the NVM Express family of specifications.
2. Why was it created?
Because interfaces designed for rotating disks (AHCI/SATA, and to a lesser degree SAS) wasted the latency and parallelism of flash.
3. What problem does it solve?
Software overhead per I/O, lock contention across CPU cores, and serialisation through a single shallow queue.
4. What existed before it?
AHCI over SATA (one queue, 32 commands), SCSI over SAS, and vendor-specific PCIe SSD interfaces that each needed their own driver.
5. Why is the current design better?
Many deep queues, a register-read-free fast path, a standard driver, and a modular specification family that separates semantics from transport.
6. Who creates it?
The protocol is defined by NVM Express, Inc. In a running system the host driver creates queues and commands; the controller creates completions.
7. Who consumes it?
The controller consumes commands; the host consumes completions; management software consumes logs and Identify data.
8. Where does it live?
Queues and buffers in host memory (PCIe); registers in the device's BAR0; namespaces and media in the device.
9. What memory/registers are involved?
CAP, VS, CC, CSTS, AQA, ASQ, ACQ, doorbells; admin and I/O queue memory; PRP lists or SGL segments; data buffers; the MSI-X table.
10. What happens before it?
PCIe enumeration assigns BAR0 and enables memory space and bus mastering (PCIe Enumeration); the driver binds by class code.
11. What happens after it?
The block layer exposes namespaces as block devices; filesystems and applications use them.
12. What happens if it is wrong?
Commands fail with status codes, time out, or (worse) silently move data to the wrong address; the controller may set Controller Fatal Status.
13. What does the protocol analyzer show?
PCIe TLPs whose addresses and payloads, decoded with knowledge of BAR0 and queue bases, reveal doorbells, SQE fetches, data transfers, CQE writes and MSI-X messages.
14. What does Linux show?
Controllers under /sys/class/nvme, namespaces as /dev/nvmeXnY, Identify data and logs via nvme-cli, errors and timeouts in the kernel log.
15. What would a validation engineer test?
Initialisation and reset sequences, queue creation limits, every command and its error paths, doorbell edge cases (wrap, full queue), interrupt coalescing, namespace management, power states, and conformance to each specification revision claimed in VS.
16. What would a senior engineer suspect when it fails?
First, which layer: is the failure in NVMe semantics (status code), in the transport binding (wrong doorbell offset, PRP alignment), or in PCIe (completion timeout, unsupported request, link down)? Then: host memory mapping errors (IOMMU faults), reset races, and firmware state.
