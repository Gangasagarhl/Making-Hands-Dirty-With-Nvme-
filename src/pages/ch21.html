Non-Volatile Memory Express (NVMe) is a storage protocol: a precise agreement about how a host asks a storage device to do work and how the device answers. This chapter builds the complete mental model of that agreement, from the host and its driver down through the NVM subsystem, the controller and the namespace to the media, and it separates the three things learners most often blur together: the NVMe protocol, the command sets that give it meaning, and the transports that carry it.

Why this chapter exists

Up to this point the course has taught Peripheral Component Interconnect Express (PCIe) from the ground up: links, layers, Transaction Layer Packets (TLPs), configuration space, Base Address Registers (BARs) and Direct Memory Access (DMA). You can now describe how bytes move between a device and host memory. What you cannot yet describe is why a storage device moves those particular bytes, at that moment, to that address. That "why" is NVMe.

Many engineers learn NVMe as a list of registers and opcodes. They can recite that Read is opcode 02h and that the controller registers start at BAR0, yet they freeze when an analyzer shows a Memory Read TLP from the SSD to an address they do not recognize. The gap is the mental model: which actor owns which object, which object lives where, and which layer is speaking at each moment. This chapter installs that model before the next chapters fill it with detail.

It also prevents the single most expensive confusion in this field: treating "NVMe" and "PCIe" as one thing. They are two independent technologies. NVMe defines storage semantics; PCIe moves packets; the NVMe over PCIe Transport specification binds the two. The rest of the course depends on keeping those three apart.

The story

Imagine a school with a gigantic library in the basement. The teacher (the CPU) does not go down to the library for every book. Instead, the school agrees on a set of rules: the teacher writes requests on slips of paper of exactly one size, puts them in a numbered request box on the classroom wall, and rings a little bell that sounds in the library. The librarian hears the bell, walks up, reads the new slips, goes back down, and carries the books straight to the right tables in the classroom without bothering the teacher. When each job is done, the librarian drops a small answer card into an answer box and taps on the classroom window.

The rules — slip size, what can be written on a slip, how the boxes work, what the answer card says — are NVMe. The staircase and corridor the librarian uses are PCIe. The signs on the staircase that tell everyone "request boxes are on this wall, the bell is this button" are the NVMe over PCIe Transport rules. The library itself can have several librarians (controllers), and the books are kept in separate sections (namespaces), each with its own numbering.

An adult version: think of an international shipping contract. The contract defines what an order looks like, what each field means, how an order is acknowledged, and what "delivered damaged" means. It says nothing about whether goods move by ship, rail or air. Separately, each carrier has its own rules about containers, labels and routing. A third document, the "carriage annex", explains how to pack contract orders into that carrier's containers. NVMe is the contract, PCIe is one carrier (Remote Direct Memory Access (RDMA) fabrics and TCP/IP networks are others), and the NVMe over PCIe Transport specification is the carriage annex.

  • The librarian is not a person waiting at a desk. A real controller is hardware and firmware with many parallel engines; it can fetch dozens of slips from dozens of boxes at once.
  • There are many request boxes, not one. NVMe allows up to 65,535 I/O submission queues plus the admin queue; the analogy hides that parallelism, which is the whole point of NVMe.
  • The bell carries a number. A doorbell write carries the new tail index, not just "ding". The librarian learns how many new slips there are from that number.
  • The answer card does not say which table the books went to. A completion entry identifies the command and its status; the data location was already in the command.
  • The shipping analogy hides that the host owns the memory. In NVMe over PCIe, the request boxes, answer boxes and data buffers all live in host memory; the device reaches into host memory with DMA. Carriers in real life never reach into your warehouse.
  • "NVMe = the rules" is incomplete. NVMe also defines architecture objects (subsystem, controller, namespace) that exist even when no command is in flight.

Beginner explanation

A computer needs to keep data when the power is off. Solid-state drives (SSDs) do that with flash memory. The computer's processor and the SSD are separate chips, so they need a shared language to talk. NVMe is that language for modern SSDs.

The language has a small number of ideas:

  • Commands. Every request is a fixed-size 64-byte message. "Read 8 blocks starting at block 1000 into this memory buffer" is one command.
  • Queues. Commands are not handed over one at a time. The host writes them into a submission queue, a ring of command slots in the host's memory. The device writes answers into a completion queue, another ring in host memory. Each completion is a 16-byte message.
  • Doorbells. The host tells the device "there are new commands up to slot N" by writing the number N into a special device register called a doorbell.
  • Controller. The part of the SSD that understands NVMe: it reads commands, does the work and writes completions.
  • Namespace. A numbered collection of storage blocks that commands read and write. Most consumer SSDs have one namespace; enterprise SSDs can have many.
  • Subsystem. The whole NVMe "thing": all controllers, all namespaces, and the ports through which hosts reach them.

And one idea that belongs to a different technology: the transport. Something has to physically carry commands, data and completions. Inside a computer that is usually PCIe. Across a data-center network it can be TCP or RDMA. NVMe the language stays the same; the carrier changes.

When someone says "NVMe wrote to NAND page 4021" they are describing firmware internals, not NVMe.

Host and NVMe driver

The host side has two jobs. First, it owns memory: in NVMe over PCIe, the submission queues, completion queues and data buffers are allocated by the host in host memory, and the device reaches them with DMA. Second, it initiates: the controller never does work it was not asked to do through a queue (with a few exceptions, such as asynchronous events, which are themselves answers to an outstanding request).

The driver (in Linux, the nvme and nvme-core modules) does the following, in order, over the lifetime of a device:

  1. Maps the controller's registers (through BAR0 for PCIe).
  2. Resets and enables the controller, after describing the admin queue (NVMe Registers).
  3. Sends admin commands: Identify, Set Features (Number of Queues), Create I/O Completion Queue, Create I/O Submission Queue (Admin Queue).
  4. Discovers namespaces and presents each as a block device (/dev/nvme0n1).
  5. For each I/O request from the block layer, builds a 64-byte command, places it in an I/O submission queue, rings the doorbell, and later consumes the 16-byte completion.

The NVMe protocol

The NVMe protocol is the set of rules for that conversation. Strip away every transport detail and what remains is:

  • A command format. A 64-byte Submission Queue Entry (SQE): Command Dword 0 with the opcode and Command Identifier (CID), the NSID, data pointer fields, and six command-specific dwords.
  • A completion format. A 16-byte Completion Queue Entry (CQE): command-specific result, the SQ head pointer and SQ identifier, the CID being completed, a Phase Tag, and a Status field (Status Code Type, Status Code, Do Not Retry, More).
  • A queueing model. Paired circular queues with head and tail pointers; the producer owns the tail, the consumer owns the head.
  • An architecture. Subsystem, controllers, namespaces, ports, and how they relate.
  • A command vocabulary. Admin commands (Identify, Create I/O SQ, Get Log Page, Set Features…) and I/O commands defined per command set (Read, Write, Flush… for the NVM Command Set).
  • A state model. How a controller is enabled, becomes ready, shuts down, resets and reports fatal errors.

The protocol is asymmetrical on purpose. The host is always the one who submits; the controller is always the one who completes. The controller does not push commands to the host. That asymmetry is why every NVMe trace has a recognizable rhythm: host writes doorbell, device reads command, device moves data, device writes completion, device signals interrupt, host writes completion doorbell.

Command sets

A command set is a vocabulary of commands with defined meaning. NVMe has two layers of vocabulary:

  • The Admin Command Set, used on the admin queue to manage the controller: discover capabilities, create and delete I/O queues, read logs, set features, manage namespaces, update firmware. In the NVMe 2.x family it is defined in the NVMe Base Specification.
  • I/O command sets, used on I/O queues to act on namespaces. The most common is the NVM Command Set (block storage: Read, Write, Flush, Dataset Management, Write Zeroes, Compare…). Others include Zoned Namespaces (ZNS), Key Value (KV), Computational Programs, and Subsystem Local Memory (SLM). Each I/O command set has its own specification in the 2.x family (NVMe 2.x Architecture).

Every namespace is associated with exactly one I/O command set. A host reading a KV namespace uses KV commands (Store, Retrieve…); a host reading an NVM namespace uses Read and Write. The Command Set Identifier (CSI) tells the host which vocabulary a namespace speaks.

Opcode numbers are only meaningful within a command set and queue type. Admin opcode 02h is Get Log Page; NVM I/O opcode 02h is Read. A decoder that ignores which queue a command came from will mislabel commands. This is a classic analyzer-configuration mistake.

Transports

A transport is how NVMe objects are carried between host and controller. The NVMe 2.x family defines three transport specifications:

The memory-based transport (PCIe) and the message-based transports (RDMA, TCP; collectively "NVMe over Fabrics") differ in a deep way. In PCIe, the controller registers are physically addressable memory and queues are shared memory. In fabrics, registers become properties read and written with Property Get and Property Set commands, and queues are logical constructs carried as capsules. NVMe's Base Specification is written in terms general enough to cover both, which is why it talks about "properties" where older revisions said "registers". This course focuses on PCIe and visits fabrics in NVMe-oF Mental Model.

The controller model

A controller is defined by what it holds and what it does:

  • Properties (registers). Capabilities (CAP), Version (VS), Controller Configuration (CC), Controller Status (CSTS), Admin Queue Attributes (AQA), and the admin queue base addresses (ASQ, ACQ). In PCIe they live at the start of BAR0. NVMe Registers treats them field by field.
  • Queues. Exactly one admin queue pair and zero or more I/O queue pairs. Many submission queues may share one completion queue.
  • Doorbells. One tail doorbell per SQ and one head doorbell per CQ (in PCIe, starting at offset 1000h of BAR0).
  • Data structures it reports. Identify Controller data, log pages, features.
  • State. Disabled, enabling, ready, shutting down, shut down, fatal.
  • Attached namespaces. The set of namespaces this controller can access.

Chapter NVMe Controller goes deep on this.

The subsystem model

The NVM subsystem is the outer box. A simple consumer SSD is an NVM subsystem with one controller, one namespace and one PCIe port. An enterprise dual-port SSD may be one subsystem with two PCIe ports, a controller behind each port, and namespaces shared by both controllers so two servers can reach the same data. A device using Single Root I/O Virtualization (SR-IOV) may expose a controller per virtual function (SR-IOV). An array reached over fabrics is a subsystem with many ports and controllers created on demand.

The key relationships:

  • A namespace belongs to the subsystem, not to a controller. Controllers get access to it by attachment.
  • An NSID refers to the same namespace from every controller in the subsystem that can see it (NSIDs are subsystem-wide).
  • A controller is associated with exactly one host at a time in the sense of its queues (a host owns the queues it created); multiple hosts reach shared data through multiple controllers.
  • Ports are the transport-facing doors. In PCIe a port is a PCIe port of the device.

Why NVMe looks the way it does

Earlier storage interfaces were designed around rotating disks whose seek times dwarfed interface overhead. The Advanced Host Controller Interface (AHCI) used with Serial ATA (SATA) had one command queue of 32 entries and needed multiple uncacheable register reads per command. Flash removed the mechanical delay, and suddenly the interface overhead and the single queue became the bottleneck (From SATA/SAS to NVMe).

The teaching ladder for NVMe

A rule book for asking a library for books: same-size request slips, a request box per classroom, a bell, an answer box, and a librarian who carries books straight to your table.

NVMe is a host-to-storage protocol built on paired submission and completion queues, fixed-size commands and completions, doorbells and interrupts, organised around an NVM subsystem that contains controllers and namespaces.

In a PCIe SSD, the controller is an ASIC with an embedded processor complex, a PCIe endpoint, DMA engines and a NAND interface. Its registers appear in BAR0; doorbells start at BAR0 + 1000h; queues and data buffers are in host DRAM and are reached by DMA.

The NVMe Base Specification (Revision 2.4 in the August 2026 set) defines the architecture, the Admin Command Set, the queueing model and the controller properties. I/O command set specifications (NVM Command Set 1.3 and others) define I/O commands. The NVMe over PCIe Transport Specification (1.4) defines the memory-mapped register layout, doorbells, PRP/SGL use over PCIe and interrupts.

On the PCIe link one NVMe I/O appears as: host MWr (doorbell) → device MRd (fetch SQE) → CplD → device MWr or MRd for data → device MWr (CQE) → device MWr (MSI-X) → host MWr (CQ head doorbell).

In an analyzer, you identify the doorbell by its address (BAR0 + 1000h + stride × index), the SQE fetch by a 64-byte read to the known SQ base, the CQE by a 16-byte write to the known CQ base, and the interrupt by a write to the MSI-X message address.

When a command "hangs", you walk the rhythm: was the doorbell written? did the device fetch? did data move? was a CQE written? did the interrupt fire? did the host ring the CQ head doorbell? The first missing step localises the fault to host, link or device.

The sixteen questions, answered for NVMe

1. What is it?
A storage protocol and architecture for accessing non-volatile memory through paired queues, defined by the NVM Express family of specifications.
2. Why was it created?
Because interfaces designed for rotating disks (AHCI/SATA, and to a lesser degree SAS) wasted the latency and parallelism of flash.
3. What problem does it solve?
Software overhead per I/O, lock contention across CPU cores, and serialisation through a single shallow queue.
4. What existed before it?
AHCI over SATA (one queue, 32 commands), SCSI over SAS, and vendor-specific PCIe SSD interfaces that each needed their own driver.
5. Why is the current design better?
Many deep queues, a register-read-free fast path, a standard driver, and a modular specification family that separates semantics from transport.
6. Who creates it?
The protocol is defined by NVM Express, Inc. In a running system the host driver creates queues and commands; the controller creates completions.
7. Who consumes it?
The controller consumes commands; the host consumes completions; management software consumes logs and Identify data.
8. Where does it live?
Queues and buffers in host memory (PCIe); registers in the device's BAR0; namespaces and media in the device.
9. What memory/registers are involved?
CAP, VS, CC, CSTS, AQA, ASQ, ACQ, doorbells; admin and I/O queue memory; PRP lists or SGL segments; data buffers; the MSI-X table.
10. What happens before it?
PCIe enumeration assigns BAR0 and enables memory space and bus mastering (PCIe Enumeration); the driver binds by class code.
11. What happens after it?
The block layer exposes namespaces as block devices; filesystems and applications use them.
12. What happens if it is wrong?
Commands fail with status codes, time out, or (worse) silently move data to the wrong address; the controller may set Controller Fatal Status.
13. What does the protocol analyzer show?
PCIe TLPs whose addresses and payloads, decoded with knowledge of BAR0 and queue bases, reveal doorbells, SQE fetches, data transfers, CQE writes and MSI-X messages.
14. What does Linux show?
Controllers under /sys/class/nvme, namespaces as /dev/nvmeXnY, Identify data and logs via nvme-cli, errors and timeouts in the kernel log.
15. What would a validation engineer test?
Initialisation and reset sequences, queue creation limits, every command and its error paths, doorbell edge cases (wrap, full queue), interrupt coalescing, namespace management, power states, and conformance to each specification revision claimed in VS.
16. What would a senior engineer suspect when it fails?
First, which layer: is the failure in NVMe semantics (status code), in the transport binding (wrong doorbell offset, PRP alignment), or in PCIe (completion timeout, unsupported request, link down)? Then: host memory mapping errors (IOMMU faults), reset races, and firmware state.

Hardware view

Open a typical NVMe SSD and you find a controller chip, DRAM (on many designs), NAND flash packages, power-loss protection capacitors on enterprise parts, and an edge connector (M.2, U.2, E1.S, add-in card). Three hardware facts matter for every later chapter:

  1. The registers are real flip-flops (or firmware-emulated storage) behind BAR0. A CPU store to BAR0 + 14h lands in CC. Some fields trigger hardware actions immediately (CC.EN starts initialisation), some are only sampled at specific moments.
  2. The doorbells are write-only in practice. The host writes a new tail or head value; the hardware latches it and schedules work. Reading a doorbell is not meaningful.
  3. The device is a bus master. It issues its own Memory Read and Memory Write TLPs to fetch commands and move data. If the Bus Master Enable bit in the PCI Command register is clear, none of that can happen — a frequent cause of "the controller never becomes ready" or "the first admin command times out" during bring-up.

A PCIe protocol analyzer sees everything that crosses the link: doorbells, fetches, data, completions, interrupts. It cannot see the firmware's queue arbitration, the FTL lookup, or NAND timing. Those show up only indirectly, as the time gap between the SQE fetch and the first data TLP.

Specification view

NVMe is defined by a family of documents published by NVM Express, Inc. The course baseline is the August 2026 NVMe 2.4 specification set. The documents most relevant to this chapter are:

  • NVM Express Base Specification, Revision 2.4 — Theory of Operation; NVM Subsystem Entities; Controller Architecture — the architecture (subsystem, controller, namespace, queues), the Admin Command Set, controller properties and initialisation.
  • NVM Express NVM Command Set Specification, Revision 1.3 — the block I/O commands (Read, Write, Flush, Dataset Management…) and NVM-specific namespace data.
  • NVM Express NVMe over PCIe Transport Specification, Revision 1.4 — memory-mapped register layout, doorbells, PRPs and SGLs over PCIe, interrupts, and PCIe-specific behaviour.

Normative text uses "shall", "should" and "may" with defined meanings. Figures and tables of fields are normative unless marked otherwise. Explanatory "theory of operation" text and examples are informative: they help you understand but do not create requirements.

  • An NVM subsystem contains one or more controllers, zero or more namespaces and one or more ports.
  • Commands are 64 bytes; completion queue entries for I/O queues on PCIe are 16 bytes (the CQE size is configured through CC.IOCQES; 16 bytes is the size the NVM Command Set requires).
  • The admin queue has Queue Identifier 0; I/O queues are created with admin commands.
  • In the NVMe over PCIe transport, controller registers are mapped at the start of the memory region described by BAR0 (with BAR1 forming the upper half of the 64-bit address), and doorbells begin at offset 1000h.
  • The PCI class code for an NVMe I/O controller is base class 01h (mass storage), subclass 08h (non-volatile memory), programming interface 02h.
  • A healthy NVMe over PCIe I/O path contains no host-initiated register reads, because every value the host needs during I/O (new completions, queue heads) arrives in host memory. This follows from the queue and Phase Tag design; the specification does not phrase it as a rule.
  • Because NSIDs are subsystem-wide, the same NSID seen from two controllers of one subsystem refers to the same namespace.
  • How many I/O queues a controller supports, how deep they are (up to CAP.MQES + 1), and how it arbitrates among them beyond the required round robin.
  • The internal media mapping (FTL), caching, and when written data becomes durable on media (subject to Flush and Volatile Write Cache rules).
  • Latencies of every step: doorbell-to-fetch, fetch-to-data, data-to-completion.
  • Before NVMe 2.0 the base specification contained the NVM Command Set and PCIe-specific details in one document; from 2.0 they are separate documents (NVMe 2.x Architecture).
  • The term "property" for controller registers, used to cover fabrics, appears in later revisions; older material says "register".
  • Newer capabilities (for example features added in 2.4: Exported NVM Subsystems, rate limiting, voltage monitoring) only exist in devices that claim that revision and advertise them; see 2026 NVMe 2.4 Updates.
  • The specification does not say how fast anything must happen (beyond timeouts reported by the controller, such as CAP.TO).
  • It does not say which CPU core should own which queue; that is a host-software choice.
  • It does not describe NAND, pages, blocks or the FTL.
  • It does not define the PCIe link itself; that is the PCI Express Base Specification, a PCI-SIG document.

Confirm in the specification: the exact list of NVM subsystem entities in 2.4 (domains, endurance groups, NVM sets, Exported NVM Subsystems) and their definitions, in the Base Specification's theory-of-operation and definitions clauses.

  • Never assume NVMe implies PCIe. NVMe/TCP and NVMe/RDMA have no BARs, no doorbell registers and no TLPs.
  • Never assume one controller per device, or one namespace per controller.
  • Never assume a device implements the latest revision because the latest specification exists. The device's VS register says what it claims.
  • Never decode an opcode without knowing whether it came from the admin queue or an I/O queue, and which command set the namespace uses.

Protocol view

Rules worth memorising now (each is treated in its own chapter):

  • Commands in one SQ may complete in any order. The CID, unique among outstanding commands in that SQ, is how the host matches completions to commands.
  • A CQE also reports the controller's current SQ head pointer, which is how the host learns that SQ slots are free again.
  • The Phase Tag inverts each time the controller wraps around the CQ, which is how the host distinguishes new entries from old ones.
  • Interrupts are a notification, not the completion itself. The completion is the CQE in memory.

Reading it as NVMe: #1 is a doorbell (address in the doorbell range of BAR0, offset 1008h = SQ1 tail with stride 4). #2 is a 64-byte read to the SQ1 base region: a command fetch. #4–19 are writes to an address that matches the command's PRP1: read data. #20 is a 16-byte write to the CQ1 region: the completion. #21 is a write to the MSI-X address window: the interrupt. #22 is the host acknowledging the completion. Every TLP maps to exactly one NVMe object.

Abnormal: a read addressed to a namespace that does not exist

#DirTime (ns)TypeFieldsMeaning
1Host→Dev0MWr32Addr=0xFE60_1008 Len=1 Req=RC Data=0x0000_0007SQ1 tail doorbell: tail 6 → 7
2Dev→Host650MRd64Addr=0x1_2340_0180 Len=16 Req=0x0100 Tag=0x22Fetch SQE in slot 6
3Host→Dev1,400CplDReq=0x0100 Tag=0x22 Status=SC ByteCnt=64SQE: opcode 02h, CID 0x0042, NSID 33 (0x21)
4Dev→Host4,900MWr64Addr=0x1_2341_0060 Len=4 Data DW3=0x8017_0042CQE: CID 0x0042, P=1, Status Code Type 0, Status Code 0Bh (Invalid Namespace or Format), DNR=1. First abnormal event
5Dev→Host4,980MWr32Addr=0xFEE0_1000 Len=1 Data=0x0000_0041MSI-X vector 1
6Host→Dev7,300MWr32Addr=0xFE60_100C Len=1 Req=RC Data=0x0000_0007CQ1 head doorbell = 7

Walking the reasoning

  1. The PCIe layer is clean. Every TLP completed successfully; there is no Unsupported Request, no Completion Timeout, no poisoned data. A PCIe-only view would call this trace healthy.
  2. Something is missing. Compared with the normal trace, there are no data TLPs between the fetch and the completion, and the completion arrived after about 3.5 µs instead of about 58 µs. A completion that arrives too fast, with no data, is the signature of a command rejected before execution.
  3. Decode the CQE. DW3 = 0x8017_0042: bits 15:0 = 0x0042 (CID), bit 16 = 1 (Phase Tag), bits 31:17 = 0x400B → Status Code (bits 24:17 of the dword) = 0Bh, Status Code Type (bits 27:25) = 0 (Generic Command Status), Do Not Retry (bit 31) = 1.
  4. Correlate with the command. The fetched SQE (row #3) carries NSID 33. The controller reports NN = 32 in Identify Controller, so 33 is outside the valid NSID range: an invalid NSID. Generic status 0Bh, Invalid Namespace or Format, fits exactly. Uncertain For a valid but inactive NSID (say NSID 3 on this controller, which has only namespaces 1 and 2 attached) the status a controller returns should be confirmed in the Base Specification's namespace-state rules; do not assume it is the same code.
  5. Localise. The fault is in the host: something built a command for a namespace the controller does not have (for example a user-space passthrough tool invoked with the wrong --namespace-id, or a corrupted command). The device behaved correctly.

This trace is why the course insists on separating NVMe from PCIe. The error is entirely an NVMe semantic error carried perfectly by PCIe. An engineer who only looks for PCIe errors will never find it; an engineer who only reads the kernel log will see "Invalid Namespace or Format" but not know whether the device even fetched the command. The two views together give certainty.

Code / pseudocode

The following program models the subsystem/controller/namespace relationships and decodes the first dword of an SQE and the last dword of a CQE. It is executable with Python 3 and the standard library only.

"""A tiny model of the NVMe object hierarchy plus SQE/CQE dword decoders.
Synthetic example for teaching; not a driver."""
from dataclasses import dataclass, field

@dataclass
class Namespace:
    nsid: int
    csi: int            # Command Set Identifier: 0x00 NVM, 0x01 KV, 0x02 ZNS
    lba_bytes: int
    nlbas: int

@dataclass
class Controller:
    cntlid: int
    attached: set = field(default_factory=set)   # NSIDs attached to this controller

@dataclass
class Subsystem:
    nqn: str
    nn: int = 32        # Identify Controller NN: maximum valid NSID
    namespaces: dict = field(default_factory=dict)
    controllers: dict = field(default_factory=dict)

    def attach(self, nsid, cntlid):
        if nsid not in self.namespaces:
            raise ValueError(f"NSID {nsid} does not exist in subsystem")
        self.controllers[cntlid].attached.add(nsid)

    def check_io(self, cntlid, nsid):
        """Return the generic status code a controller would report."""
        if nsid in self.controllers[cntlid].attached:
            return 0x00, "Successful Completion"
        if not 1 <= nsid <= self.nn:
            return 0x0B, "Invalid Namespace or Format"
        return None, "inactive NSID: confirm status in the Base Specification"

def decode_cdw0(dw0):
    return {"opcode": dw0 & 0xFF, "fuse": (dw0 >> 8) & 0x3,
            "psdt": (dw0 >> 14) & 0x3, "cid": (dw0 >> 16) & 0xFFFF}

def decode_cqe_dw3(dw3):
    return {"cid": dw3 & 0xFFFF, "phase": (dw3 >> 16) & 1,
            "sc": (dw3 >> 17) & 0xFF, "sct": (dw3 >> 25) & 0x7,
            "crd": (dw3 >> 28) & 0x3, "more": (dw3 >> 30) & 1,
            "dnr": (dw3 >> 31) & 1}

if __name__ == "__main__":
    s = Subsystem("nqn.2026-01.example:lab-ssd")
    s.namespaces[1] = Namespace(1, 0x00, 512, 1_953_525_168)
    s.namespaces[2] = Namespace(2, 0x00, 4096, 244_190_646)
    s.controllers[1] = Controller(1)
    s.attach(1, 1)
    s.attach(2, 1)
    for nsid in (1, 33):
        print(f"Read to NSID {nsid}:", s.check_io(1, nsid))
    print("SQE CDW0 0x00410002 ->", decode_cdw0(0x0041_0002))
    print("CQE DW3  0x00010041 ->", decode_cqe_dw3(0x0001_0041))
    print("CQE DW3  0x80170042 ->", decode_cqe_dw3(0x8017_0042))

Expected output: NSID 1 succeeds; NSID 33 returns status 0x0B; CDW0 0x0041_0002 decodes to opcode 02h (Read in an I/O queue of an NVM namespace) with CID 0x0041; the second CQE decodes to SC 0x0B, SCT 0, DNR 1.

Worked example

Scenario. A colleague says: "Our server has one NVMe SSD, but nvme list-subsys shows nvme0 and nvme1 under the same NQN, and lsblk shows only one nvme0n1. Is the drive broken?"

Step 1 — Name the objects. Two controllers (nvme0, nvme1) belong to one NVM subsystem (same SUBNQN). That is a dual-port or multi-controller subsystem.

Step 2 — Where are the controllers? cat /sys/class/nvme/nvme{0,1}/address shows two PCI addresses, e.g. 0000:01:00.0 and 0000:02:00.0, so the drive is attached through two PCIe ports (a dual-port U.2 drive behind two root ports, for example).

Step 3 — Why only one block device? The namespace is shared (Namespace Multi-path I/O and Namespace Sharing Capabilities (NMIC) indicates sharing) and Linux native NVMe multipath is enabled, so the kernel presents one block device per namespace (nvme0n1) with two paths underneath (visible as nvme0c0n1 and nvme0c1n1 in sysfs).

Step 4 — Conclude. The drive is healthy and doing exactly what the subsystem model allows: one namespace, attached to two controllers, reached through two ports. Nothing in this reasoning involved NAND, and nothing involved TLPs. It was pure NVMe architecture.

If multipath were disabled, the same hardware would appear as two block devices (one per controller) pointing at the same data — dangerous if a filesystem is mounted on both. The architecture is identical; only the host's presentation differs.

Common mistakes

Mistakes learners make about NVMe, and the correction

Debugging connection

The object model is a debugging map. When something fails, place the failure on the chain Host → driver → subsystem → controller → namespace → media and ask what evidence each layer leaves:

Where a failure lives and what it leaves behind
LayerTypical failureEvidence
PCIe (below NVMe)Link down, completion timeout, Unsupported Request, malformed TLPAER messages in the kernel log, analyzer error flags, lspci status bits (PCIe Errors)
Transport bindingWrong doorbell offset, PRP misaligned, MSI-X not configuredDevice never fetches, fetches from wrong address, or completes with no interrupt
ControllerNever becomes ready, Controller Fatal Status, reset loopsCSTS.RDY stays 0, CSTS.CFS = 1, kernel "controller is down; will reset"
NamespaceInvalid namespace, LBA out of range, write protectedStatus codes in CQEs; kernel log decodes them
MediaUnrecovered read error, wear-outMedia and Data Integrity Errors status codes, SMART / Health log (SMART / Health)

The first question in every investigation is: which layer reported the first abnormal event? A status code in a CQE is an NVMe-layer report. An AER error is a PCIe-layer report. A timeout is the absence of a report, and you must find which expected event did not happen.

Senior engineer insight

Senior engineers rarely think "NVMe" as one word. They think in four independent axes: architecture (which subsystem, controller, namespace), command set (which vocabulary applies to this queue and namespace), transport (how the bytes travel), and revision (which specification version the device claims and the host assumes). Most hard bugs live where two axes disagree: a host that assumes a 2.x feature on a 1.4 device, a decoder that applies NVM opcodes to a ZNS namespace, a fabric target whose properties differ from a PCIe controller's registers.

A second habit: they treat every NVMe identifier as scoped. A CID is unique only within one SQ and only among outstanding commands. A QID is unique only within one controller. An NSID is unique within one subsystem. A CNTLID is unique within one subsystem. An NQN is meant to be globally unique. Mixing scopes is how correlation tools produce nonsense.

A third: they know which behaviours are specification-mandated and which are a vendor's choice, and they label them in bug reports. "The controller took 9 seconds to become ready" is not a bug if CAP.TO allows 10 seconds; it may still be a product issue worth raising, but not a conformance failure.

Without using nvme list-subsys, write a shell or Python script that rebuilds the subsystem → controller → namespace tree from /sys/class/nvme* alone.

Hints

Group controllers by subsysnqn. Namespaces of controller nvmeX appear as nvmeXnY (or as nvmeXcYnZ paths under multipath) in /sys/class/nvme/nvmeX/ or /sys/block. Interrupt names follow nvmeXqN.

Solution

For the synthetic Lab SSD the map is: one subsystem (NQN nqn.2026-01.example:lab-ssd) → one controller (CNTLID 1, PCIe 0000:01:00.0, transport pcie) → two active namespaces (NSID 1 at 512-byte LBAs, about 1 TB; NSID 2 at 4 KiB LBAs). Queues: admin queue (vector 0, nvme0q0) and 32 I/O queue pairs (nvme0q1…nvme0q32, vectors 1–32).

Answers: (1) Same SUBNQN means same subsystem; different PCI addresses only show different ports/functions. (2) A successful nvme id-ctrl proves the admin path; a successful read from /dev/nvme0n1 (for example sudo dd if=/dev/nvme0n1 of=/dev/null bs=4k count=1 iflag=direct, which is read-only) proves at least one I/O queue path. (3) Interrupts belong to completion queues, which belong to controllers; namespaces have no interrupts.

A script solution groups subsysnqn values in a dictionary, then lists entries matching nvme*n* under each controller directory.

What a senior engineer notices

  • Whether the number of I/O queues equals the number of CPUs (Linux's default intent) or was capped by the controller (Set Features Number of Queues result).
  • Whether the firmware revision of two controllers in the same subsystem differs (it should not).
  • Whether namespaces with 4 KiB LBAs are used with software that assumes 512-byte sectors.

Failure variants

  • A PCIe function with class 0108 but no /sys/class/nvme entry: driver not bound, or controller failed to become ready — check the kernel log.
  • A controller with zero namespaces: normal for a freshly provisioned enterprise drive or an administrative controller.
  • A namespace visible in nvme list-ns --all but not as a block device: allocated but not attached to this controller.

Solutions
  1. Host (Host Identifier / host NQN, global) → driver (none) → NVM subsystem (SUBNQN, global) → controller (CNTLID, subsystem scope) → queues (QID, controller scope; CID per SQ) → namespace (NSID, subsystem scope; NGUID/EUI64/UUID global) → media (not addressed by NVMe).

Quiz

  1. Which statement best describes NVMe?

    • A newer generation of the PCIe physical layer
    • A type of NAND flash memory
    • A storage protocol and architecture that can run over several transports
    • A Linux driver
    Answer and reasoning

    NVMe is a protocol and architecture defined by a specification family; PCIe is one of its transports. The Linux driver implements it; it is not the definition.

  2. On NVMe over PCIe, where does a Submission Queue normally live?

    • In the controller's registers
    • In host memory
    • In NAND flash
    • In PCIe configuration space
    Answer and reasoning

    The host allocates queues in host memory and the controller fetches entries with DMA. (A Controller Memory Buffer is an optional alternative, not the normal case.)

  3. A namespace belongs to:

    • The NVM subsystem, and is attached to zero or more controllers
    • Exactly one controller
    • The host driver
    • The PCIe port
    Answer and reasoning

    Namespaces are subsystem entities; attachment determines which controllers can access them. Shared namespaces are attached to several.

  4. Admin opcode 02h and NVM I/O opcode 02h are:

    • The same command on different queues
    • Both Read
    • Both Get Log Page
    • Different commands: Get Log Page (admin) and Read (NVM I/O)
    Answer and reasoning

    Opcodes are scoped by queue type and command set. Decoders must track which queue a command came from.

  5. In the abnormal trace, why does a PCIe-only analysis miss the problem?

    Model answer

    Every TLP completed successfully. The error is an NVMe status (Invalid Namespace or Format) carried inside a perfectly valid Memory Write payload. Only decoding the CQE, and correlating its CID with the fetched SQE, reveals it.

  6. Which is the completion of an NVMe command?

    • The MSI-X interrupt
    • The CQE written to the completion queue
    • The CQ head doorbell write
    • The last data TLP
    Answer and reasoning

    The CQE is the completion. The interrupt is a notification and may be coalesced or absent (polling). The CQ head doorbell is the host releasing the slot.

  7. Name the three kinds of NVMe specification in the 2.x family besides the Base Specification.

    Model answer

    I/O command set specifications (NVM, ZNS, KV, Computational Programs, SLM), transport specifications (PCIe, RDMA, TCP), and the management and boot specifications (NVMe-MI, NVMe Boot).

  8. What does the PCI class code 01 08 02 tell you, and what does it not tell you?

    Model answer

    It says the PCIe function presents itself as an NVMe I/O controller (mass storage, non-volatile memory controller, NVMe programming interface), which lets a generic driver bind. It does not say which NVMe revision the controller implements (read VS), how many namespaces exist, or whether the controller works.

  9. Why does NVMe use many queues instead of one?

    Model answer

    So each CPU core can submit and complete without locks shared with other cores, and so the device can work on many commands in parallel. A single shared queue would serialise submission and cause cache-line contention between cores.

  10. True or false: every NVMe controller has at least one namespace.

    Answer

    False. A controller may have zero attached namespaces (for example before provisioning, or an administrative or discovery controller).

Interview questions

  1. Beginner: What is the difference between NVMe and PCIe?

    Model answer

    NVMe is a storage protocol: commands, completions, queues, controllers, namespaces. PCIe is a general-purpose serial interconnect that moves packets between devices and memory. NVMe can run over PCIe, and the NVMe over PCIe Transport specification defines how (registers in BAR0, doorbells, DMA with PRPs/SGLs, MSI-X). NVMe also runs over TCP and RDMA, where there is no PCIe at all.

  2. Beginner: What is a namespace?

    Model answer

    A quantity of storage, formatted into logical blocks for the NVM Command Set, identified by an NSID within the subsystem. The host sees each attached namespace as a block device.

  3. Intermediate: Walk me through what crosses the PCIe link for one 4 KiB read.

    Model answer

    Host MWr to the SQ tail doorbell; device MRd of 64 bytes for the SQE and the host's CplD; device MWr TLPs carrying 4 KiB of data, split by Max Payload Size (16 TLPs at 256 bytes); device MWr of a 16-byte CQE; device MWr of the MSI-X message; host MWr to the CQ head doorbell. If the buffer needs a PRP list, there is an extra device MRd for the list.

  4. Intermediate: Why are there no register reads in NVMe's I/O path, and why does that matter?

    Model answer

    Uncached MMIO reads are non-posted and stall the CPU for a full round trip, often around a microsecond. NVMe puts all completion information (including SQ head) in the CQE in host memory and uses the Phase Tag to mark new entries, so the host never needs to read the device during I/O. This cuts latency and CPU cost per I/O.

  5. Advanced: How would you decide whether two controllers belong to the same NVM subsystem, and why does it matter?

    Model answer

    Compare the subsystem NQN from Identify Controller (SUBNQN); same NQN means same subsystem. It matters because NSIDs are subsystem-wide, so namespaces may be shared, which affects multipath, reservations and data-integrity reasoning (two hosts writing the same namespace).

  6. Senior: A customer reports intermittent "Invalid Namespace or Format" errors after a firmware update. How do you investigate?

    Model answer

    First establish layer: the status is NVMe-level, so PCIe is probably fine, but confirm no AER events. Capture which NSIDs failing commands carry (kernel log, or a trace correlating CQE CID to SQE NSID). Check whether the active namespace list changed across the update (Identify active NSID list, namespace attachment), whether the namespace format (LBA format, metadata) changed, and whether the host cached a stale namespace list (a Namespace Attribute Changed asynchronous event may have been missed). Distinguish: wrong NSID from the host (host bug) vs a correct NSID the controller now rejects (firmware regression). Reproduce with a single passthrough Read to the NSID and compare before/after firmware.

Model explanation for a senior engineer

"NVMe is an architecture plus a protocol. The architecture is a subsystem containing controllers and namespaces behind ports; namespaces are subsystem objects attached to controllers. The protocol is paired queues of 64-byte commands and 16-byte completions with a phase tag, driven by doorbells. Command semantics come from the admin set and per-namespace I/O command sets identified by CSI. The transport binds it to PCIe (BAR0 registers, doorbells at 1000h, PRP/SGL DMA, MSI-X) or to fabrics (capsules, properties). In a trace, PCIe errors show as TLP-level failures; NVMe errors show only inside CQE payloads, so I always decode CQEs and correlate CIDs with fetched SQEs."

Chapter summary

  • NVMe is a storage protocol and architecture. PCIe is an interconnect. The NVMe over PCIe Transport specification binds them. Keep all three separate.
  • The chain is host → NVMe driver → NVM subsystem → controller → namespace → media; NVMe stops at the namespace and leaves media mapping to the device.
  • Commands (64 bytes) go into submission queues; completions (16 bytes) come back in completion queues; doorbells announce new work; interrupts announce new completions.
  • Command sets give commands meaning: the Admin Command Set for controller management, I/O command sets (NVM, ZNS, KV, Computational Programs, SLM) for namespaces.
  • Transports carry the protocol: PCIe (memory-based), RDMA and TCP (message-based).
  • A subsystem has one or more controllers, zero or more namespaces and one or more ports; namespaces are attached to controllers.
  • In a PCIe trace every TLP of an I/O maps to one NVMe object; NVMe-level errors hide inside CQE payloads.

Do not move on until you can:

  • define NVMe in one sentence without mentioning PCIe
  • draw the host → driver → subsystem → controller → namespace → media chain and name each identifier with its scope
  • explain the difference between a command set and a transport
  • label every TLP of the normal trace with the NVMe object it touches
  • decode a CQE's DW3 into CID, phase and status by hand
  • explain why the abnormal trace is invisible to a PCIe-only analysis
  • list which Linux evidence proves the admin path works and which proves an I/O path works
