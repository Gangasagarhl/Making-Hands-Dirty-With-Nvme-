Chapter 26 built the Admin queue from three registers and walked through the first Identify. This module studies the Admin queue in service: how events reach the host, how long commands block it, how queue creation and deletion fail, how wrap and phase go wrong, and how to reason about an Admin timeout when every packet looks fine.

Orientation

After bring-up, the Admin queue carries everything that is not data: health monitoring, error reporting, namespace management, firmware updates, formats, sanitize, feature changes and queue creation. It is small (32 entries on the Lab SSD), it is shared by every tool on the host that talks to the controller, and on many controllers it is processed largely one command at a time. It is also where the controller's only "voice" lives — the Asynchronous Event Request — and where host bugs in wrap and phase handling are least often exercised, because the Admin queue wraps rarely.

This module goes beyond the bootstrap: an event-driven trace from notice to re-arm; a long-running command that delays monitoring; a queue-creation failure that the driver ignored; an Admin timeout that could be a host phase bug or a dropped DMA write. The labs decode event completions, build Get Log Page commands that respect transfer limits, and simulate the Admin queue with outstanding events, serial execution and a phase bug.

Kid story

A school office has one small in-tray for notes from parents. Notes go in one at a time and the secretary works through them in order. Some notes are quick ("please send the lunch menu"); one is huge ("please re-paint the gym"), and while she is on the phone about the gym, everything else waits in the tray.

The secretary is never allowed to phone a parent first. So clever parents leave a blank, signed card in the tray that says "call me when something happens". When the school has news, she fills in that card and sends it home — and the parent must put a new blank card in the tray straight away, or they will miss the next news. Every blank card waiting in the tray takes up a spot that a real note could have used.

The tray is the Admin Submission Queue; notes are Admin commands; the gym note is a Format NVM or Sanitize; the blank cards are Asynchronous Event Requests; "put a new card in" is re-arming after each event; the limited spots are the 31 usable Admin slots.

Analogy boundary

  • Represents. A small shared queue, mostly serial processing, long jobs blocking short ones, and events delivered only by completing a request the host left waiting.
  • Hides. The tray has two halves (submission and completion queues) with heads, tails and a phase bit that flips each lap. The secretary may read several notes before acting on any (fetch is not execution), and some controllers do run some Admin commands concurrently.
  • Misleads. A note that waits a long time is not lost; and a blank card that waits for months is not "stuck". Timeouts must know the difference.

Who shares the Admin queue

On Linux, every nvme command that a user runs against /dev/nvme0 becomes an Admin SQE on the same queue the driver uses for its own work. A monitoring agent polling SMART every second, an orchestration tool creating namespaces and an engineer running a self-test all compete for the same slots and the same (often serial) command processor. The driver's Admin timeout applies to all of them unless a tool passes its own.

32 entries give 31 usable outstanding commands. Subtract the AERs the driver keeps outstanding, and remember that one long command can hold everything behind it. Size monitoring frequency and orchestration concurrency against that budget, not against I/O-queue intuition.

Mechanism

The Admin mechanism that matters most in service is the event loop: the host keeps AERs outstanding; the controller completes one when an event occurs; the host reads the indicated log, clears the event and re-arms. Lab SSD values (synthetic): AERL = 3 (four AERs allowed), the driver keeps one outstanding; Admin vector 0 at 0xFEE0_0000 with data 0x40.

Three rules people miss

  • No AER, no notice. If none is outstanding, events are queued or lost (how many the controller retains is implementation-dependent). Every controller reset deletes outstanding AERs; the host must re-arm after every reset. (Namespaces, senior lab, shows the consequence.)
  • Reading clears; RAE keeps. With RAE = 0 the log read clears the event and unmasks the type. Tools that read logs with RAE = 0 behind the driver's back can "steal" events: the driver's later read finds nothing pending. Tools should read with RAE = 1 unless they own event handling.
  • Long commands and the queue. Many controllers process Admin commands in order, so a 40-second Format makes a 1-ms Identify wait 38 seconds. The Commands Supported and Effects log reports per-opcode restrictions (for example "no other command to this namespace" while it runs) and side effects (capability or namespace inventory changes) that tell the host what to rescan afterwards. Uncertain Confirm the effects field names and encodings in Base 2.4.

Creation and deletion order

Create I/O CQ before any SQ that names it; delete every SQ before the CQ they use. Each step is an Admin command with its own status: Create I/O CQ can fail with Invalid Queue Identifier, Invalid Queue Size or Invalid Interrupt Vector; Create I/O SQ with Completion Queue Invalid (the named CQ does not exist), Invalid Queue Identifier or Invalid Queue Size; Delete I/O CQ with Invalid Queue Deletion (SQs still attached). These are Status Code Type 1h (command specific) values. A driver that ignores one failure builds every later step on a missing queue.

Timeouts and Abort

Linux defaults to a 60-second Admin timeout (module parameter admin_timeout) and excludes AERs. On timeout a host may send Abort (08h) naming the SQID and CID — but Abort is itself an Admin command, needs a free slot and may complete with "not aborted"; on serial controllers it may wait behind the very command it targets. The usual escalation is a controller reset, which deletes every queue and every AER; the host then rebuilds and must re-arm events and rescan.

The ladder for the central concept: the Admin event loop

A school office that may not phone parents: parents leave blank "call me" cards, and must leave a new one each time news arrives.

The host submits AERs; the controller completes one per event with type, information and log ID; the host reads the log and re-arms.

Firmware keeps a pending-event list and mask per type, and holds AER commands without completing them; events are coalesced and masked until their log is read.

Base 2.4 defines the AER command, DW0 format, event types, AERL, RAE, Asynchronous Event Configuration and the log pages; event lists grow by revision.

An AER's CQE is a normal MWr64 to the Admin CQ plus an MSI-X MWr32 to 0xFEE0_0000; the follow-up Get Log Page is a fetch, a data write and another CQE.

In a capture: a CQE whose CID belongs to an old SQE with opcode 0Ch, a Get Log Page with the matching LID within microseconds, then a new 0Ch SQE.

Check that every reset is followed by re-arming, that log reads clear events, that no tool steals events with RAE = 0, and that timeouts exclude AERs.

The sixteen questions for the Admin event loop

1. What is it?
The mechanism by which the controller reports events through outstanding host requests.
2. Why was it created?
Queues only carry completions of host commands; the controller cannot initiate a message.
3. What problem does it solve?
Prompt notice of health, errors and configuration changes without polling.
4. What existed before?
Interrupt status registers that the host had to read and clear (as in AHCI).
5. Why is it better?
No register polling; the notice carries its log identifier; delivery uses the normal completion path.
6. Who creates it?
The host submits the AER; the controller fills it with an event.
7. Who consumes it?
The host driver, which forwards to user space or acts itself.
8. Where does it live?
The Admin queue pair, controller event state and log pages.
9. What memory/registers are involved?
Admin SQ/CQ, log data buffers, SQ0TDBL/CQ0HDBL, MSI-X vector 0.
10. What happens before?
Bring-up, Asynchronous Event Configuration, AER submission.
11. What happens after?
Log read, event clear, re-arm, host action.
12. What happens if it is wrong?
Silent loss of notices: stale namespaces, missed temperature or spare warnings, unnoticed firmware activation.
13. What does the analyzer show?
An old 0Ch SQE, a much later CQE with non-zero DW0, a Get Log Page, a new 0Ch SQE.
14. What does Linux show?
Kernel messages and udev events for some notices; nvme logs read by tools.
15. What would a validation engineer test?
AERL enforcement, delivery after re-arm, masking until log read, RAE behaviour, events with no AER outstanding, behaviour across reset.
16. What would a senior engineer suspect?
That nobody re-armed after the last reset, or that a tool cleared the event first.

"Outstanding commands ≤ entries − 1" follows from the CQ full condition: a host that allowed more could make the controller unable to post. "Tools that read logs with RAE = 0 can hide events from the driver" follows from the clearing rule.

  • The specification does not require serial Admin execution, nor promise concurrency.
  • It does not define how long any Admin command may take, or what timeout a host should use.
  • It does not say how many events a controller remembers when no AER is outstanding.
  • Check in the specification: the Commands Supported and Effects field encodings; the event information values for each notice type in Base 2.4; Abort completion DW0 meaning.

Never count outstanding AERs as hung commands; never ignore a queue-creation status; never read event logs with RAE = 0 from a tool that does not own event handling; never assume a reset preserved AERs.

Admin commands often run in firmware on a management processor separate from the I/O fast path. That is why Admin latency is measured in hundreds of microseconds to seconds, why one long command can delay others, and why Admin behaviour differs most between products. Firmware-assisted operations (Format, Sanitize, self-test, firmware activation) also compete with background media management.

A controller may fetch several Admin SQEs at once (SQHD in later CQEs shows how far it has read) but execute them one by one. In a trace, an early fetch followed by a late CQE does not mean the command was "running" for the whole interval.

Ordering: the CQE write follows the data writes on the same path, and PCIe ordering keeps posted writes in order, so a host that sees a CQE can trust the data before it. The MSI-X write follows the CQE write for the same reason. A dropped posted write — blocked by the IOMMU, for example — produces no error the device can see.

Why it is ambiguous. Everything the device can do, it did. The candidates: (a) a host phase bug on the Admin CQ — the host still expects P = 1 in slot 0, so it ignores the new CQE (Admin CQs wrap rarely, so such bugs survive testing); (b) the IOMMU dropped the CQE write (mapping for 0x1_0000_1000 changed or was revoked), so slot 0 still holds the old first-lap CQE; (c) the interrupt was lost or misrouted and the host's timeout path does not poll the CQ before giving up; (d) the CPU read a stale copy of slot 0 (a coherence problem on unusual platforms).

Disambiguating evidence. Dump Admin CQ slot 0 from host memory (debugger, or a driver debug hook) before the reset: new CQE with P = 0 and CID 0x0014 points to (a), (c) or (d); the old CQE points to (b), which an IOMMU fault in the kernel log confirms. Then: a phase bug would usually also produce bursts of "invalid CID" or stale completions at the wrap (the advanced lab shows why) and recur every 32 Admin completions after it; an interrupt problem would show in interrupt counters for vector 0 not incrementing. Confidence before evidence: low; prior favours (b) or (c) on mature drivers, (a) on new ones.

         6: "I/O command specific status", 7: "Vendor specific"}
INFO = {
    0: {0: "Write to invalid doorbell register", 1: "Invalid doorbell write value",
        2: "Diagnostic failure", 3: "Persistent internal error",
        4: "Transient internal error", 5: "Firmware image load error"},
    1: {0: "NVM subsystem reliability", 1: "Temperature threshold",
        2: "Spare below threshold"},
    2: {0: "Namespace Attribute Changed", 1: "Firmware Activation Starting",
        2: "Telemetry Log Changed", 3: "Asymmetric Namespace Access Change"},
}
LOGS = {0x01: "Error Information", 0x02: "SMART / Health Information",
        0x03: "Firmware Slot Information", 0x04: "Changed Namespace List",
        0x0C: "Asymmetric Namespace Access"}

def decode(dw0):
    etype, info, lid = dw0 & 0x7, (dw0 >> 8) & 0xFF, (dw0 >> 16) & 0xFF
    t = TYPES.get(etype, f"reserved type {etype}")
    i = INFO.get(etype, {}).get(info, f"info 0x{info:02X}")
    log = LOGS.get(lid, f"log 0x{lid:02X}")
    steps = [f"Get Log Page LID {lid:02X}h ({log})"]
    if etype == 2 and info == 0:
        steps.append("rescan: Identify the NSIDs in the list")
    if etype == 2 and info == 1:
        steps.append("expect CSTS.PP = 1; extend timeouts, do not reset")
    if etype == 0:
        steps.append("this is a host or device fault: check the Error Information entries")
    steps.append("submit a new Asynchronous Event Request")
    return f"0x{dw0:08X}: {t} / {i} -> " + "; ".join(steps)

if __name__ == "__main__":
    for dw0 in (0x0002_0101, 0x0004_0002, 0x0001_0100, 0x0003_0102, 0x000C_0302):
        print(decode(dw0))

Procedure

  1. Decode 0x0002_0101 and 0x0004_0002 by hand: bits 2:0, 15:8, 23:16.
  2. Run the program. Expected: five lines — temperature threshold (read log 02h), Namespace Attribute Changed (read 04h, rescan), invalid doorbell write value (read 01h), Firmware Activation Starting (read 03h, expect Processing Paused), Asymmetric Namespace Access change (read 0Ch); every line ends with "submit a new Asynchronous Event Request".
  3. Encode the DW0 for "spare below threshold".

Observations

Note that DW0 always names the log to read.

Questions

  1. What happens to a second temperature event if the host never reads log 02h?
  2. Why is the last action the same for every event?
  3. Which event in the list is reporting a host bug?

Expected reasoning

Events of a type are masked until their log is read; delivery needs an outstanding AER.

Solution

0x0002_0101: type 1 (SMART / Health), info 01h (temperature threshold), LID 02h. 0x0004_0002: type 2 (notice), info 00h (Namespace Attribute Changed), LID 04h. Spare below threshold: type 1, info 02h, LID 02h → 0x0002_0201.

(1) It is not reported: the type stays masked until the log is read with RAE = 0. (2) Each completion consumes one AER; without a replacement, the controller has fewer (eventually zero) ways to notify. (3) Invalid doorbell write value (0x0001_0100): the host wrote a doorbell value that is out of range — for example a tail beyond the queue size.

Intermediate lab — Build Get Log Page commands within MDTS

Objective

Encode Get Log Page dwords correctly and split a large log into reads that respect MDTS and RAE.

Prerequisites

Admin Queue (Get Log Page fields); MDTS from NVMe Controller.

Setup

#!/usr/bin/env python3
"""Build Get Log Page (02h) command dwords, splitting a large log into reads
that respect MDTS. Field positions as in Chapter 26; confirm in the spec."""

def glp(lid, nbytes, offset=0, rae=False, lsp=0, nsid=0xFFFF_FFFF):
    assert nbytes % 4 == 0 and nbytes > 0, "logs are read in whole dwords"
    numd = nbytes // 4 - 1                       # 0's based dword count
    cdw10 = lid | (lsp << 8) | (int(rae) << 15) | ((numd & 0xFFFF) << 16)
    cdw11 = numd >> 16                           # NUMDU
    return dict(nsid=nsid, cdw10=cdw10, cdw11=cdw11,
                cdw12=offset & 0xFFFF_FFFF, cdw13=offset >> 32)

def read_plan(lid, total, mdts=5, mpsmin=4096, rae=True):
    """Split a log of `total` bytes into commands of at most 2^MDTS * MPSMIN.
    RAE stays set until the last piece, so the event is cleared only then."""
    chunk = (1 << mdts) * mpsmin if mdts else total
    plan, off = [], 0
    while off < total:
        n = min(chunk, total - off)
        last = off + n >= total
        plan.append((off, n, glp(lid, n, off, rae=rae and not last)))
        off += n
    return plan

if __name__ == "__main__":
    c = glp(0x02, 512)
    print("SMART 512 B:  CDW10=0x%08X CDW11=0x%08X" % (c["cdw10"], c["cdw11"]))
    c = glp(0x01, 16 * 64, rae=True)
    print("Error log 16 entries, RAE: CDW10=0x%08X" % c["cdw10"])
    c = glp(0xC0, 400 * 1024)
    print("Vendor log 400 KiB in one command (needs no MDTS limit): CDW10=0x%08X CDW11=0x%08X"
          % (c["cdw10"], c["cdw11"]))
    print("Same log with MDTS=5 (128 KiB per command):")
    for off, n, c in read_plan(0xC0, 400 * 1024):
        print("  offset 0x%06X len %6d  CDW10=0x%08X CDW11=0x%08X CDW12=0x%08X"
              % (off, n, c["cdw10"], c["cdw11"], c["cdw12"]))

Procedure

  1. Predict CDW10 for the 512-byte SMART read, then run. Expected: CDW10 = 0x007F_0002; the 16-entry error log with RAE gives 0x00FF_8001; the 400 KiB single read needs NUMDU = 1 (CDW10 0x8FFF_00C0, CDW11 0x0000_0001); with MDTS = 5 the log becomes four reads at offsets 0, 0x20000, 0x40000 and 0x60000, the last one with RAE clear.
  2. Explain why the single 400 KiB command would be rejected by the Lab SSD.
  3. Change the program so a tool that does not own event handling keeps RAE set on every piece.

Observations

Note how NUMD crosses from NUMDL into NUMDU at 256 KiB.

Questions

  1. What is the largest log read in one command on the Lab SSD (MDTS = 5, 4 KiB pages)?
  2. Why clear RAE only on the last piece?
  3. What goes wrong if the host computes NUMD as bytes/4 without subtracting one?

Expected reasoning

MDTS bounds every data transfer, logs included; RAE decides when the event is consumed; counts are 0's based.

Solution

(1) 25 × 4 KiB = 128 KiB. A 400 KiB read exceeds it and fails (Invalid Field in Command is typical), so large logs must be read in pieces with offsets — which requires the log to support offsets (LPA in Identify Controller). (2) If the first piece cleared the event, the log could change before the remaining pieces were read, mixing two versions; keeping the event retained until the end keeps the event and its data consistent. (3) The host asks for 4 bytes more than its buffer; the controller writes past the buffer by one dword — memory corruption, or an IOMMU fault if the buffer ended at a page boundary.

Extension

Add the Index Offset Type / Log Specific Identifier fields for logs that need them, after confirming their positions in Base 2.4.

Advanced lab — Simulate the Admin queue in service

Objective

See capacity, serial execution and a phase bug interact, and learn the signature of each.

Prerequisites

The trace section; phase tag rules from Queue Architecture.

Setup

#!/usr/bin/env python3
"""Simulate an Admin queue pair: limited slots shared with outstanding AERs,
serial command execution, CQ wrap with phase tags, host timeouts.
A teaching model of one plausible controller, not of any product."""

def simulate(cmds, entries=32, aers=1, flip_phase=True, timeout_ms=60_000, end_ms=None):
    """cmds: (name, submit_ms, service_ms[, timeout_ms]) in submission order."""
    cap = entries - 1                      # never more outstanding than CQ slots - 1
    cq = [(0, None)] * entries             # (phase, cid); memory starts zeroed
    ctail, cphase, hhead, hphase = 0, 1, 0, 1
    outstanding = {cid: "AER" for cid in range(aers)}   # AERs never complete here
    waiting, running, fifo, log = list(cmds), None, [], []
    started, done, limit = {}, {}, {}
    end_ms = end_ms or sum(c[2] for c in cmds) + max(c[1] for c in cmds) + timeout_ms + 1000
    for now in range(end_ms):
        # host: submit commands whose time has come, if a CID/slot is free
        while waiting and waiting[0][1] <= now and len(outstanding) < cap:
            name, t, svc, *tmo = waiting.pop(0)
            limit[name] = tmo[0] if tmo else timeout_ms
            cid = min(c for c in range(cap + 1) if c not in outstanding)
            outstanding[cid] = name
            started[name] = t
            fifo.append((cid, name, svc))
        # controller: executes one admin command at a time, in fetch order
        if running is None and fifo:
            cid, name, svc = fifo.pop(0)
            running = (cid, name, now + svc)
        if running and running[2] <= now:
            cid, name, _ = running
            cq[ctail] = (cphase, cid)      # post CQE (and raise MSI-X vector 0)
            ctail = (ctail + 1) % entries
            cphase ^= ctail == 0
            running = None
            # host interrupt handler: consume entries whose phase matches
            budget = entries
            while cq[hhead][0] == hphase and budget:
                _, c = cq[hhead]
                budget -= 1
                hhead = (hhead + 1) % entries
                if flip_phase and hhead == 0:
                    hphase ^= 1
                who = outstanding.pop(c, None)
                if who is None:
                    log.append(f"{now:>6} ms  spurious CQE: CID {c} is not outstanding")
                elif who == "AER":
                    log.append(f"{now:>6} ms  AER CID {c} 'completed' by a stale CQE")
                elif who != name and who not in done:
                    done[who] = now
                    log.append(f"{now:>6} ms  WRONG: stale CQE completes {who} (CID {c}) before it ran")
                else:
                    done[who] = now
        for name, t in list(started.items()):
            if name not in done and now - t == limit[name]:
                log.append(f"{now:>6} ms  TIMEOUT {name} (submitted at {t} ms)")
    lat = {n: done[n] - started[n] for n in done}
    return lat, log

def show(title, cmds, **kw):
    lat, log = simulate(cmds, **kw)
    print(f"[{title}]")
    vals = sorted(lat.values())
    if vals:
        print(f"   completed {len(vals)}/{len(cmds)}; latency min {vals[0]} ms, max {vals[-1]} ms")
    for kind in ("WRONG", "spurious", "AER", "TIMEOUT"):
        hits = [l for l in log if kind in l]
        if hits:
            print(f"   {len(hits)} x {kind}; first: {hits[0].strip()}")

if __name__ == "__main__":
    burst = [(f"cmd{i}", i, 2) for i in range(40)]          # 40 commands, wraps the CQ
    show("healthy, 40 commands", burst, aers=1)
    long_fmt = [("FormatNVM", 0, 40_000, 600_000), ("Identify", 2_000, 1), ("GetLogPage", 3_000, 1)]
    show("Format holds the queue; tool timeout 30 s", long_fmt, timeout_ms=30_000)
    show("host never flips its phase", burst, aers=1, flip_phase=False, timeout_ms=5_000)

Procedure

  1. Run it. Expected: healthy run completes 40/40 (the CQ wraps; latency grows to 80 ms because commands arrive faster than they are served); the Format run completes all three, but Identify and Get Log Page time out at the 30 s tool limit (latencies about 37–38 s); the phase-bug run shows 3 WRONG completions, 29 spurious CQEs and 5 timeouts.
  2. Rerun the phase-bug case with aers=4. What changes?
  3. Change the Format scenario so the controller executes Admin commands concurrently (hint: let more than one command run at once) and compare.

Observations

Record, for each scenario, what a host log would show and what an analyzer would show.

Questions

  1. Why does the phase bug first produce stale completions rather than silence?
  2. Why are the WRONG completions the most dangerous output?
  3. In the Format case, what would an analyzer show that the tool's log does not?

Expected reasoning

After a wrap, a host that does not flip expects the old phase, and every slot still holds an old entry with exactly that phase.

Solution

(1) When the host's head returns to slot 0, slots 0–31 still contain first-lap CQEs with P = 1 — which is what the buggy host expects — so it consumes them as new: a burst of stale completions. Once the controller overwrites slots with P = 0, the host ignores them, so later commands time out. (2) A stale CQE whose CID has been reused by a live command completes that command before it ran: the host believes a Set Features or Namespace Attachment succeeded when it did not. No error is logged. (3) The early fetch of the Identify (SQHD advancing) and no CQE for 38 s, with I/O flowing normally on other queues — proof the controller was alive and serial, not hung. With aers=4 (step 2) the results barely change: only 27 slots remain for ordinary commands, but this workload never has more than about 20 outstanding, and the CIDs simply start at 4. A burstier workload would show host-side waiting for slots — the capacity cost of AERs. Concurrent execution (step 3) removes the delay, which is why the effects log and vendor documentation matter.

Extension

Add an event source that completes an AER at a chosen time, and a "reset" that clears outstanding AERs; show a notice lost because the host did not re-arm.

Senior forensic lab — Drives "missing" on the new server model

Objective

Find why a storage service fails to start on one server model only, using Admin evidence.

Prerequisites

Creation and deletion rules; I/O Queues; Number of Queues from Admin Queue.

Setup (synthetic incident record)

  • A storage service uses an in-house user-space driver that creates one I/O queue pair per CPU.
  • On 32-CPU servers it works. On the new 64-CPU model, every Lab SSD is reported "initialisation failed" and left unused.
  • Driver debug log (new model): Set Features Number of Queues requested 0x003F_003F; completion DW0 = 0x001F_001F; queues 1–32 created successfully; Create I/O CQ for QID 33 failed with SCT 1h SC 01h; "rolling back".
  • Rollback log: Delete I/O CQ 1 → SCT 1h SC 0Ch; Delete I/O CQ 2 → SCT 1h SC 0Ch … then "rollback failed, resetting controller".
  • After the reset, the Error Information log shows 33 entries for SQID 0; the service exits.

Procedure

  1. Decode the Set Features exchange.
  2. Decode both failure statuses.
  3. Write the causal chain and the two bugs.
  4. Propose fixes and a test that would have caught this.

Observations

Note what the controller told the driver before any queue was created.

Questions

  1. How many I/O queues did the driver ask for, and how many did it get?
  2. What do SC 01h and SC 0Ch mean here?
  3. Was anything wrong with the drive?
  4. What is the right behaviour on a 64-CPU host?

Expected reasoning

Number of Queues is a negotiation; allocated values bound creation; deletion order is the reverse of creation.

Solution

(1) Requested NSQR = NCQR = 63 (0's based) → 64 each. Allocated NSQA = NCQA = 31 → 32 each. (2) SC 01h, Invalid Queue Identifier: QID 33 is above the allocation. SC 0Ch, Invalid Queue Deletion: the rollback tried to delete CQs while their SQs still existed.

Chain: the driver ignored the allocated count (bug 1), so creation failed at QID 33. Its rollback deleted CQs in creation order instead of deleting SQs first (bug 2), so the rollback itself failed and escalated to a reset, and the service gave up. On 32-CPU servers the request never exceeded the allocation, so the bugs never showed. (3) No: the drive answered every command correctly and even reported its limit up front. (4) Create min(CPUs, allocated) queue pairs and map CPUs onto them (several CPUs per queue), as the Linux driver does; roll back by deleting SQs then CQs. Test: a fault-injection or emulated controller (QEMU) configured with fewer queues than host CPUs, plus a creation failure injected mid-way to exercise rollback. Confidence: high — the status codes are unambiguous.

Extension

Design a CPU-to-queue mapping for 64 CPUs on 32 queues that keeps NUMA locality, and state what you would measure to validate it.

Debugging

Pattern 1 — "Hung" Admin commands that are AERs

Symptom
A monitoring tool or a custom driver reports one to four Admin commands outstanding for hours and raises alerts or resets.
Possible causes
AERs counted as normal commands; the tool's timeout logic does not exclude opcode 0Ch.
Evidence
Opcode of the "hung" CIDs; AERL; number outstanding.
First check
Are all the "hung" commands opcode 0Ch?
Second check
Is their number ≤ AERL + 1?
Disambiguating experiment
Trigger an event (for example lower the temperature threshold on a test drive) and watch one complete.
Likely conclusion
Tool bug; no controller problem.
Confidence
High.

Pattern 2 — Admin latency spikes during maintenance

Symptom
Monitoring commands take tens of seconds or time out while I/O is healthy.
Possible causes
Format, Sanitize, Device Self-test or Firmware Commit running on a controller that serialises Admin commands; very large log reads; many tools sharing the queue.
Evidence
Admin command history (which opcode started just before); Commands Supported and Effects; analyzer fetches with late CQEs.
First check
Was a long-running Admin command outstanding at the time?
Second check
Did I/O latency stay normal?
Disambiguating experiment
Run the same long command on a test system and time an Identify issued during it.
Likely conclusion
Serial Admin execution; host timeouts and scheduling must account for it.
Confidence
High once reproduced.

Pattern 3 — I/O queue creation fails at bring-up

Symptom
Fewer I/O queues than expected, or none; driver falls back or aborts.
Possible causes
QID above Number of Queues allocation (01h); QSIZE above CAP.MQES or zero (02h); invalid interrupt vector (08h); CQ not created or creation failed (00h); PRP to non-contiguous memory when CAP.CQR = 1.
Evidence
CQE status of each creation command; Set Features 07h DW0; CAP.MQES and CQR; MSI-X table size.
First check
Find the first failed creation CQE, not the last.
Second check
Decode its CDW10/CDW11 against the controller's limits.
Disambiguating experiment
Re-issue the failing creation in an emulator with the same parameters.
Likely conclusion
Host parameter error; the status names it.
Confidence
High.

Pattern 4 — Shutdown or rollback fails with Invalid Queue Deletion

Symptom
Delete I/O CQ fails; the host escalates to a controller reset during shutdown or error recovery.
Possible causes
CQs deleted before their SQs; an SQ deletion failed and was ignored; bookkeeping lost track of an SQ.
Evidence
Order of 00h and 04h commands; their statuses.
First check
Is any SQ that names this CQ still present?
Second check
Did every Delete I/O SQ succeed?
Disambiguating experiment
Delete in correct order on an emulator and confirm success.
Likely conclusion
Host ordering bug.
Confidence
High.

Pattern 5 — Events never arrive

Symptom
Temperature or spare warnings visible in SMART but never reported; namespaces added but hosts do not see them; firmware activation unnoticed.
Possible causes
No AER outstanding (not re-armed after reset or after a completion); event class disabled in FID 0Bh; event masked because its log was never read, or read with RAE = 1 forever; another tool read the log with RAE = 0 and cleared the event.
Evidence
Outstanding Admin commands (AER count); FID 0Bh value; log read history from all tools.
First check
Is at least one AER outstanding now?
Second check
Is the event class enabled?
Disambiguating experiment
Trigger a harmless event on a test drive and watch for the AER completion.
Likely conclusion
Host event-handling gap, usually re-arming or RAE.
Confidence
Medium-high.

Pattern 6 — Admin completions found only by polling

Symptom
Admin commands complete only when the timeout handler polls the CQ; logs say the completion was "polled"; Admin operations take exactly the timeout.
Possible causes
MSI-X vector 0 masked, unrouted or misprogrammed; interrupt remapping fault; CQ created with IEN = 0 for the Admin vector in a custom driver.
Evidence
/proc/interrupts for nvme0q0; MSI-X table entry 0 and mask bits; analyzer shows MWr32 to 0xFEE0_0000.
First check
Does the interrupt count for vector 0 increase per Admin command?
Second check
Does the analyzer show the MSI-X write at all?
Disambiguating experiment
Issue one Identify and compare MSI-X writes on the link with interrupts counted by the host.
Likely conclusion
Interrupt delivery path, not the controller or the queue.
Confidence
High once the write is seen on the link but not counted.

Interview

Beginner

  1. How does the controller tell the host about an event?

    Model answer

    By completing an Asynchronous Event Request the host submitted earlier; DW0 gives event type, information and the log page to read.

  2. Why must the host submit a new AER after each event?

    Model answer

    Each AER is consumed by one event; without replacements there is nothing to complete for the next event.

  3. Which order are I/O queues created and deleted in?

    Model answer

    Create the CQ before its SQs; delete the SQs before the CQ.

  4. How many commands can be outstanding on a 32-entry Admin queue?

    Model answer

    At most 31, including any outstanding AERs.

  5. What does Get Log Page LID 02h return?

    Model answer

    The SMART / Health Information log (512 bytes).

Intermediate

  1. What does RAE do and why does it matter?

    Model answer

    Retain Asynchronous Event: when set, reading the log does not clear the pending event. Used for multi-part reads and by tools that do not own event handling.

  2. How do you read a 1 MiB log on a controller with MDTS = 5?

    Model answer

    Eight 128 KiB Get Log Page commands with increasing offsets (if the log supports offsets), RAE set on all but the last.

  3. Create I/O SQ fails with Completion Queue Invalid. What do you look for?

    Model answer

    The earlier Create I/O CQ for that CQID: did it fail or was it never sent?

  4. Why should Admin timeout logic exclude AERs?

    Model answer

    They are designed to stay outstanding until an event, possibly forever.

  5. What is the Commands Supported and Effects log for?

    Model answer

    It lists supported opcodes and their effects and restrictions, so hosts know what to rescan afterwards and what to serialise.

Advanced

  1. Why can an Identify wait 38 s?

    Model answer

    On a controller that executes Admin commands serially, it waits behind a long command such as Format; it was fetched but not executed.

  2. How does an Admin CQ phase bug manifest?

    Model answer

    At the first wrap, stale completions (spurious or wrong CIDs), then timeouts as new CQEs are ignored; it hides because the Admin CQ wraps rarely.

  3. Why is Abort a weak recovery tool on the Admin queue?

    Model answer

    It is best effort, needs a free Admin slot, is limited by ACL, and on a serial controller may wait behind the very command it targets.

  4. The link shows a CQE and an MSI-X write, yet the host times out. What do you check?

    Model answer

    Host memory at the CQ slot (did the write land?), IOMMU faults, interrupt counts for vector 0, and the host's phase state.

  5. How can a tool steal events from the driver?

    Model answer

    By reading the event's log with RAE = 0 first; the event is cleared and the driver finds nothing.

Senior

  1. Design an Admin timeout policy.

    Model answer

    Per-opcode timeouts (long for Format, Sanitize, self-test, firmware), exclude AERs, poll the CQ before declaring timeout, try Abort where useful, escalate to reset only with evidence, and re-arm events and rescan after any reset.

  2. How would you govern Admin access among many tools?

    Model answer

    One owner for event handling; tools read logs with RAE set; rate-limit monitoring; schedule maintenance; budget slots; prefer kernel-exported state over passthrough.

  3. What would you validate in a vendor's Admin implementation?

    Model answer

    AERL enforcement and delivery, masking and RAE, events with no AER outstanding, long-command concurrency, creation/deletion statuses, Admin wrap, Abort behaviour, effects log accuracy.

  4. A fleet sees creation failures only on one server model. Approach?

    Model answer

    Compare what differs (CPU count, vectors, IOMMU); decode the first failing creation status; check Number of Queues negotiation and rollback order.

  5. How do you prove a notice was lost and not never generated?

    Model answer

    Show the state change in logs (for example the Changed Namespace List or SMART) and the absence of an outstanding AER at that time (trace or driver state), or the event cleared by another reader.

To a senior engineer

Model explanation

"Admin failures are mostly host policy failures: tools that steal events or count AERs as hangs, timeouts that ignore serial execution, ignored creation statuses, and wrap/phase bugs that appear after weeks. Govern access to the queue, make timeouts per opcode, verify event delivery end to end, and treat an Admin timeout with a CQE on the wire as a host-memory or interrupt problem until proven otherwise."

Mastery gate

Do not consider this module mastered until you can:

  • explain the event loop, Admin capacity, serial execution and the creation/deletion rules;
  • diagram an AER from submission to re-arm and a queue creation sequence with its failure points;
  • identify in traces an event delivery, a long command blocking others, an ignored creation failure and an Admin timeout with a CQE on the wire;
  • debug the six failure patterns;
  • distinguish the Admin queue from I/O queues (I/O Queues), from registers (NVMe Registers), from controller resets (Reset), from doorbell flow (Doorbells) and from PCIe Advanced Error Reporting (AER);
  • cite the NVM Express Base Specification, Revision 2.4 (Admin Command Set, Asynchronous Event Request, Get Log Page, Commands Supported and Effects, queue creation and deletion, Abort) by section name.
