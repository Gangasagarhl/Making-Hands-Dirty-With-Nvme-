One large simulated investigation that covers the whole course. A server's NVM Express (NVMe) solid-state drive (SSD) goes quiet now and then. You get the boot trace, the configuration space, the NVMe initialisation, normal I/O, power transitions, a failure, a recovery, a second failure, and every log a real investigation would collect. The root cause is hidden. Find the first abnormal event, write a bug report, and only then open the official solution.

How the capstone works

This is the course's final practical. Nothing on this page tells you the answer before the solution section. The evidence is complete enough to solve the case. It also holds distractors: real anomalies that have nothing to do with the root cause, as real incidents always do.

Learning objectives

  • Read evidence from every layer (PCIe physical and link, Transaction Layer Packets (TLPs), configuration space, NVM Express (NVMe) registers, queues, commands, interrupts, power management, Linux logs, NVMe logs) and correlate it on one timeline.
  • Tell apart the first abnormal event, its consequences, and unrelated anomalies.
  • Form hypotheses, rank them, and design experiments that would separate them.
  • Write a bug report that another engineer could act on without talking to you.

Prerequisites

Everything up to Chapter 71, especially link training (Chapter 9), enumeration and BARs (Chapter 17, Chapter 19), NVMe registers and initialisation (Chapter 24, Chapter 26), queues and doorbells (Chapter 25–Chapter 28), the end-to-end flow (Chapter 39), interrupts (Chapter 42, Chapter 43), errors (Chapter 44–Chapter 47) and power (Chapter 50). Read Engineering Bug Report Training before you write your report.

Rules

  1. Timebox: four hours for the investigation, one hour for the report.
  2. Work only from the evidence on this page and the course material. Do not open the solution until your report is written.
  3. Hints are graded from gentle to strong. Each hint you open costs points in the grading rubric; note which ones you used.
  4. Your deliverable is a bug report in the format taught in Engineering Bug Report Training, plus a one-page timeline.

This is a paper investigation (Safe lab). If you reproduce parts of it on real hardware, power-management and reset experiments are Caution lab and must run on a lab machine with no data you need.

Every trace, log, register value and counter on this page is synthetic, written for teaching, built on the course's reference lab system (see the environment table). Kernel log lines are paraphrased. Vendor names, model names and identifiers are fictional. Nothing here describes a real product.

Analyzers see the link, not the inside of the controller. Whether the controller entered PS3 or PS4, and what it did internally on entry or exit, is invisible here. You can only infer it from configuration (the Autonomous Power State Transitions (APST) table), timing (exit latency in later traces) and vendor telemetry. Say so in your report when you rely on it.

Part 2 — Where the completions were, and why the stall is exactly 30 seconds

At 104 s every stuck command's CQE is in host memory with the expected phase (Evidence I, queue state), and the analyzer shows the controller writing it (H8). So the completion was produced and delivered, but never signalled. The driver relies on the interrupt to look at the CQ, so nothing reads it until the block layer's I/O timeout fires. That timeout defaults to 30 seconds in common kernels, which is why every stall is "exactly 30 s". On timeout the driver polls the CQ, finds the entry, completes it, and logs "completion polled". The worker continues, and the rest of the burst has normal interrupts.

Why only one command per queue? Each burst starts with one synchronous read per worker, so each queue has exactly one command outstanding. If more commands were outstanding, the next completion's interrupt would cause the driver to process the CQ and pick up the earlier entry as well, so a lost interrupt would only add microseconds. Harness v3's opening synchronous read is what turned a lost interrupt into a 30-second stall.

Part 4 — Root cause and confirming experiments

Root cause (confirmed with the vendor in this simulated case): SSD firmware LS2F104 enters an internal "deep power-gated idle" state after 30 s in PS4 when the link is also in L1.2 (reference clock off). On exit from that state, the controller's command-processing path is restored before its MSI-X message generator finishes re-initialising (about 400 µs). Interrupt requests raised in that window are discarded, not held. Completions posted in the window therefore produce no interrupt. Neither the NVMe interrupt rules (a Completion Queue with interrupts enabled must signal its vector when entries are posted, subject to coalescing settings) nor the PCIe MSI-X rules (a message for a masked vector is held as pending, not lost) allow a request to be silently dropped; confirm the exact wording in the NVM Express Base Specification's interrupt sections and the PCI Express Base Specification's MSI-X sections when you cite them.

Why it started now: two changes were both necessary. Harness v3 (day −30) added long pauses and the queue-depth-1 opening read. Platform firmware 1.12 (day −14) enabled ASPM L1.2, without which the SSD never enters its deep power-gated state. Between day −30 and day −14 there were long gaps but no L1.2, and no stalls.

Firmware: hold command processing (or queue interrupt requests) until the MSI-X generator is ready after deep idle exit; never discard an interrupt request; add a telemetry counter for late interrupt delivery.

Part 6 — The distractors, and what to do about them
  • Receiver Errors at L1.2 exit. Real but minor: an occasional framing error during Recovery after the reference clock restarts. Worth a separate low-priority ticket (check the L1 PM Substates timing parameters such as T_POWER_ON and the common-mode restore time on both ends). Not the cause of the stalls.
  • 212 Error Information log entries. The monitoring agent asks for a vendor-specific log page this SSD does not implement. Fix the agent to check the Supported Log Pages log (or the vendor's documentation) first. Noise that makes the error log useless for real errors.
  • The operator's reset "fixing" it. The reset had no effect on the mechanism. The quiet period afterwards had no idle gap over 27 s. A recovery action followed by a quiet period is not evidence that the action fixed anything.
  • MSI-X entries 1–4 programmed after CSTS.RDY. This is normal for this driver. It is a reasonable hypothesis (state saved at "ready" time could miss them), which the table read during the stall eliminates. Good investigators list it and kill it with evidence.
  • VS = 2.0 while the course baseline is 2.4. Irrelevant to this failure: devices report the revision they implement.
  • The 9.2 ms delay before the SQE fetch. Expected: PS4 exit latency (9 ms) plus scheduling. It is the same with and without the failure.
