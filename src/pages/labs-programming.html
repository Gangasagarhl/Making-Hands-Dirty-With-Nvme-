What a decoded field really is

Every lab turns bytes into meaning. It helps to climb the course ladder once for that act itself, because the rest of the page depends on it.

A parcel arrives with a label covered in numbers. A decoder is the friend who knows that the first three digits are the town, the next two the street, and the last one the floor. Without the friend, the label is just numbers.

A decoder applies a layout (which bits form which field) and an encoding (what each value means) to raw bytes. Both come from a specification. If either is wrong, the output looks confident and is wrong.

Hardware stores fields in registers and memory structures with fixed bit positions: the Command register at configuration offset 04h, the SQE's opcode in byte 0, a TLP's Length in the low ten bits of its first header DWORD. Hardware never "knows" the names; it just acts on the bits.

The PCI Express Base Specification and the NVMe Base, NVM Command Set and NVMe over PCIe Transport specifications define the layouts and encodings normatively. A decoder is only as good as its fidelity to the right revision.

On the link, fields cross as bytes inside TLPs. Little-endian NVMe structures ride inside PCIe payloads; PCIe headers are defined with their own byte order. Mixing the two conventions is the most common decoding error.

An analyzer shows a decoded row. That row is the analyzer's decoder applied to captured bytes, which is exactly what your Python does, with the same failure modes.

When a decode looks impossible (a 4 KiB boundary crossing, a CID that was never submitted), a senior engineer checks the decoder and the capture before blaming the device. Your own tools are evidence with scope, like any other.

Background

A Type 0 configuration header (an endpoint's header) occupies the first 64 bytes. The fields this lab uses sit at offsets you should eventually know by heart. The capability list is a singly linked list: the Capabilities Pointer at 34h gives the first entry; each entry starts with a one-byte Capability ID and a one-byte Next pointer. The list is only valid when bit 4 (Capabilities List) of the Status register is set.

Inside the PCI Express Capability (ID 10h), this lab reads Device Control at +08h (MPS in bits 7:5, MRRS in bits 14:12, both encoded as 128 × 2n bytes), Link Capabilities at +0Ch (maximum speed in bits 3:0, maximum width in bits 9:4) and Link Status at +12h (current speed in bits 3:0, negotiated width in bits 9:4). Speed values index the supported-speeds vector: 1 = 2.5 GT/s, 2 = 5.0, 3 = 8.0, 4 = 16.0, 5 = 32.0, 6 = 64.0 GT/s. In the MSI-X Capability (ID 11h), Message Control at +02h holds Table Size (N−1) in bits 10:0, Function Mask in bit 14 and Enable in bit 15; the Table and PBA Offset/BIR DWORDs at +04h and +08h say which BAR holds each structure (bits 2:0) and where.

CAP_NAMES = {0x01: "Power Management", 0x05: "MSI", 0x09: "Vendor Specific",
             0x10: "PCI Express", 0x11: "MSI-X"}
SPEEDS = {1: "2.5 GT/s", 2: "5.0 GT/s", 3: "8.0 GT/s", 4: "16.0 GT/s",
          5: "32.0 GT/s", 6: "64.0 GT/s"}


def parse_lspci_hex(text):
    """Return a bytearray built from 'offset: b0 b1 ...' lines."""
    cfg = bytearray()
    for raw in text.splitlines():
        line = raw.strip()
        if not line or ":" not in line:
            continue
        off_txt, data_txt = line.split(":", 1)
        try:
            off = int(off_txt, 16)
        except ValueError:
            continue                      # skip the "01:00.0 Non-Volatile ..." title line
        values = [int(b, 16) for b in data_txt.split()]
        if len(cfg) < off:
            cfg.extend(b"\x00" * (off - len(cfg)))
        cfg[off:off + len(values)] = bytes(values)
    return cfg


def u8(c, o):  return c[o]
def u16(c, o): return c[o] | c[o + 1] << 8
def u32(c, o): return u16(c, o) | u16(c, o + 2) << 16


def decode_bars(cfg, findings):
    print("BARs (Type 0 header, offsets 10h-24h):")
    off = 0x10
    while off <= 0x24:
        val = u32(cfg, off)
        idx = (off - 0x10) // 4
        if val & 1:
            print(f"  BAR{idx}: I/O space, base 0x{val & ~0x3:08x}")
            off += 4
            continue
        kind = (val >> 1) & 0x3
        pref = "prefetchable" if val & 0x8 else "non-prefetchable"
        if kind == 0x2:                   # 64-bit BAR consumes two slots
            addr = (val & ~0xF) | (u32(cfg, off + 4) << 32)
            print(f"  BAR{idx}/BAR{idx+1}: 64-bit memory, {pref}, base 0x{addr:016x}")
            if addr == 0:
                findings.append(f"BAR{idx} is 64-bit but unassigned (base 0)")
            off += 8
        else:
            addr = val & ~0xF
            if val:
                print(f"  BAR{idx}: 32-bit memory, {pref}, base 0x{addr:08x}")
            off += 4


def walk_caps(cfg, findings):
    caps = {}
    if not (u16(cfg, 0x06) & 0x0010):
        findings.append("Status.Capabilities List = 0: no capability chain")
        return caps
    ptr, seen = u8(cfg, 0x34) & 0xFC, set()
    while ptr:
        if ptr in seen or ptr < 0x40 or ptr + 2 > len(cfg):
            findings.append(f"capability chain broken or looping at 0x{ptr:02x}")
            break
        seen.add(ptr)
        cap_id, nxt = cfg[ptr], cfg[ptr + 1] & 0xFC
        print(f"  cap @0x{ptr:02x}: ID 0x{cap_id:02x} {CAP_NAMES.get(cap_id, '(other)')}, next 0x{nxt:02x}")
        caps[cap_id] = ptr
        ptr = nxt
    return caps


def decode_pcie(cfg, p, findings):
    capreg = u16(cfg, p + 0x02)
    devctl = u16(cfg, p + 0x08)
    linkcap = u32(cfg, p + 0x0C)
    linksta = u16(cfg, p + 0x12)
    mps = 128 << ((devctl >> 5) & 0x7)
    mrrs = 128 << ((devctl >> 12) & 0x7)
    max_s, max_w = linkcap & 0xF, (linkcap >> 4) & 0x3F
    cur_s, cur_w = linksta & 0xF, (linksta >> 4) & 0x3F
    print(f"PCI Express capability: version {capreg & 0xF}, device/port type {(capreg >> 4) & 0xF}")
    print(f"  Device Control: MPS={mps} B, MRRS={mrrs} B, "
          f"RO={'on' if devctl & 0x10 else 'off'}, NoSnoop={'on' if devctl & 0x800 else 'off'}")
    print(f"  Link Capabilities: up to {SPEEDS.get(max_s, '?')} x{max_w}")
    print(f"  Link Status:       now   {SPEEDS.get(cur_s, '?')} x{cur_w}")
    if cur_s < max_s or cur_w < max_w:
        findings.append("link trained below its capability (check the partner port too)")


def decode_msix(cfg, p):
    ctl = u16(cfg, p + 0x02)
    tbl, pba = u32(cfg, p + 0x04), u32(cfg, p + 0x08)
    print(f"MSI-X: {(ctl & 0x7FF) + 1} vectors, enable={ctl >> 15 & 1}, function mask={ctl >> 14 & 1}")
    print(f"  table in BAR{tbl & 7} at +0x{tbl & ~7:x}; PBA in BAR{pba & 7} at +0x{pba & ~7:x}")

Observation

BAR0 alone is not an address: its low four bits are type flags (bit 0 memory/I/O, bits 2:1 width, bit 3 prefetchable) and BAR1 supplies the upper 32 bits. The capability walk needs a loop guard because a corrupted or half-read dump can link back on itself. The Link Status value is a snapshot from the moment of the dump.

Questions

  1. Why does the program print "BAR0/BAR1" as one entry?

    Answer

    BAR0's bits 2:1 are 10b, which marks a 64-bit memory BAR. A 64-bit BAR consumes two consecutive BAR slots: the lower DWORD (with the type bits masked off) and the upper DWORD in the next slot. Reading BAR1 as an independent BAR would invent a second, bogus memory range.

  2. After you cleared Bus Master Enable, what NVMe behaviour would you expect if the driver rang a doorbell?

    Answer

    The doorbell write itself still arrives (it is a host-to-device memory write, governed by Memory Space Enable). But the controller may not issue memory requests, so it cannot fetch the SQE, read PRP lists, move data, post a CQE or send an MSI-X message (an MSI-X message is itself a memory write). The command hangs until the host times out. The analyzer shows the doorbell and then silence from the device.

  3. Why is the capability pointer masked with 0xFC?

    Answer

    Capability structures are DWORD aligned, and the low two bits of the pointer are reserved. Masking makes the walk robust against a device or dump that sets reserved bits.

  4. With Link Status changed to 43 10, the program reports a downtrained link. Is the device at fault?

    Answer

    Not necessarily. The value means 8.0 GT/s ×4 on a link capable of 16.0 GT/s. The link trains to the highest speed both ends support and that the channel sustains. You must also read the Root Port's Link Capabilities (and the Link Capabilities 2 supported-speeds vector on both ends), and check whether software limited the target speed. A slot, riser or retimer problem, or an interposer, can also cause it. See Link Training.

  5. The class code says "NVM Express I/O controller". Does that prove the nvme driver is bound?

    Answer

    No. Configuration space describes the function; binding is an operating-system fact. Check lspci -k ("Kernel driver in use") or the driver link under the device's sysfs directory.

Challenge

Extend the program to walk the PCI Express extended capabilities, which start at offset 100h and are only visible in a 4096-byte dump (lspci -xxxx, root required). Each extended capability header is one DWORD: Capability ID in bits 15:0, Capability Version in bits 19:16, Next Capability Offset in bits 31:20. Hint

Stop when the header is 0 or the next offset is 0; guard against loops exactly as in walk_caps. An ID of 0xFFFF or a header of 0xFFFFFFFF means the read failed.

Solution 
def walk_ext_caps(cfg, findings):
    off, seen = 0x100, set()
    while off and len(cfg) >= off + 4:
        hdr = u32(cfg, off)
        if hdr in (0, 0xFFFFFFFF):
            break
        if off in seen:
            findings.append(f"extended capability loop at 0x{off:03x}")
            break
        seen.add(off)
        cap_id, ver, nxt = hdr & 0xFFFF, (hdr >> 16) & 0xF, (hdr >> 20) & 0xFFC
        name = "Advanced Error Reporting" if cap_id == 0x0001 else "(other)"
        print(f"  ext cap @0x{off:03x}: ID 0x{cap_id:04x} v{ver} {name}, next 0x{nxt:03x}")
        off = nxt

Call it from main() when len(cfg) > 0x100. Identify other extended capability IDs from the PCI Express Base Specification's extended capability list rather than from memory.

What a senior engineer notices

  • A dump is a snapshot. Link Status, Device Status error bits and power state can change a microsecond later; a dump taken after a reset shows the reset's results, not the failure.
  • Vendor ID 0xFFFF and every byte 0xFF is not a "device with ID FFFF"; it is the signature of a configuration read that no function completed (device absent, in a deep power state, or behind a link that is down).
  • MPS in Device Control is what software programmed, not what the device supports (Device Capabilities holds that). The value that matters for the link is the one programmed on both ends; a mismatch is a classic source of Malformed TLP errors (see Trace Lab 6).
  • lspci's human-readable decode is itself a decoder with a version. When it and your parser disagree, the raw bytes decide.

Background

In the non-flit header format, DWORD 0 is common to every TLP. Fmt says how long the header is and whether data follows; Type says what kind of transaction it is. Together they distinguish, for example, a 32-bit Memory Read (Fmt 000b, Type 00000b) from a 64-bit Memory Write (Fmt 011b, Type 00000b) and a Completion with Data (Fmt 010b, Type 01010b).

TLP header DWORD 0 (non-flit format)
DW31…2423…1615…87…0
DW0FmtTypeT9TCT8Attr[2]LNTHTDEPAttr[1:0]ATLength

For memory requests, DWORD 1 holds the Requester ID (bits 31:16), Tag (15:8), Last DW Byte Enables (7:4) and First DW Byte Enables (3:0); DWORDs 2 (and 3, for 64-bit addressing) hold the address with bits 1:0 reserved. For completions, DWORD 1 holds the Completer ID, Completion Status (15:13), Byte Count Modified (12) and Byte Count (11:0); DWORD 2 holds the Requester ID, Tag and Lower Address (6:0). Length is in DWORDs, and the value 0 encodes 1024.

The T9 and T8 bits extend the tag to 10 bits; they were introduced with 10-bit tag support (PCIe 4.0 era) and are reserved in older layouts. Status value 010b was long called Configuration Request Retry Status (CRS); later revisions generalise and rename it. In PCIe 6.x and 7.0 flit mode, TLP headers use a different layout entirely; this lab's decoder does not apply to flit-mode captures. Confirm the layout against the revision your link actually runs.

def tlp_name(fmt, typ):
    if fmt == 4:
        return "Prefix"
    data = fmt in (2, 3)
    a64 = fmt in (1, 3)
    if typ == 0x00:
        return ("MWr" if data else "MRd") + ("64" if a64 else "32")
    if typ == 0x01:
        return "MRdLk" + ("64" if a64 else "32")
    if typ == 0x02:
        return "IOWr" if data else "IORd"
    if typ in (0x04, 0x05):
        return ("CfgWr" if data else "CfgRd") + str(typ - 4)
    if typ == 0x0A:
        return "CplD" if data else "Cpl"
    if typ == 0x0B:
        return "CplDLk" if data else "CplLk"
    if typ >> 3 == 0x2:
        return ("MsgD" if data else "Msg") + f" (routing {typ & 7:03b})"
    if typ in (0x0C, 0x0D, 0x0E):
        return {0x0C: "FetchAdd", 0x0D: "Swap", 0x0E: "CAS"}[typ]
    return f"unknown type {typ:05b}"


def byte_count(length_dw, first_be, last_be):
    """Bytes actually requested by a memory request (contiguous-BE case)."""
    if length_dw == 1:
        if first_be == 0:
            return 0                        # zero-length read/write
        lo = (first_be & -first_be).bit_length() - 1
        hi = first_be.bit_length() - 1
        return hi - lo + 1
    lo = (first_be & -first_be).bit_length() - 1
    hi = last_be.bit_length() - 1
    return length_dw * 4 - lo - (3 - hi)


def decode(words):
    dw = [int(w, 16) for w in words.split()]
    d0 = dw[0]
    fmt, typ = d0 >> 29, (d0 >> 24) & 0x1F
    tc, td, ep = (d0 >> 20) & 7, (d0 >> 15) & 1, (d0 >> 14) & 1
    attr = (d0 >> 12) & 3
    length = d0 & 0x3FF or 1024           # 0 encodes 1024 DW
    name = tlp_name(fmt, typ)
    out = [f"{name:8s} fmt={FMT.get(fmt, '?')} TC={tc} TD={td} EP={ep} "
           f"RO={attr >> 1} NS={attr & 1}"]
    problems = []
    hdr_dw = 4 if fmt in (1, 3) else 3
    if len(dw) < hdr_dw:
        problems.append(f"need {hdr_dw} header DWORDs, got {len(dw)}")
        return out, problems
    has_data = fmt in (2, 3)
    if typ in (0x00, 0x01):                # memory request
        rid, tag = dw[1] >> 16, (dw[1] >> 8) & 0xFF
        last_be, first_be = (dw[1] >> 4) & 0xF, dw[1] & 0xF
        addr = (dw[2] << 32 | dw[3]) & ~3 if hdr_dw == 4 else dw[2] & ~3
        nbytes = byte_count(length, first_be, last_be)
        out.append(f"  ReqID={rid >> 8:02x}:{rid >> 3 & 0x1F:02x}.{rid & 7} (0x{rid:04x}) Tag=0x{tag:02x} "
                   f"Addr=0x{addr:x} Len={length} DW FirstBE={first_be:04b} LastBE={last_be:04b} -> {nbytes} bytes")
        if length == 1 and last_be:
            problems.append("Length=1 but Last DW BE is non-zero (malformed)")
        if length > 1 and last_be == 0:
            problems.append("Length>1 but Last DW BE is zero (malformed)")
        if hdr_dw == 4 and dw[2] == 0:
            problems.append("4DW header used for an address below 4 GiB (not allowed)")
        if (addr & 0xFFF) + length * 4 > 4096:
            problems.append("request crosses a 4 KiB boundary (not allowed)")
        if has_data and len(dw) > hdr_dw:
            out.append("  payload: " + " ".join(f"{w:08x}" for w in dw[hdr_dw:]))
    elif typ in (0x0A, 0x0B):              # completion
        cid, status = dw[1] >> 16, (dw[1] >> 13) & 7
        bcm, bc = (dw[1] >> 12) & 1, dw[1] & 0xFFF or 4096
        rid, tag, low = dw[2] >> 16, (dw[2] >> 8) & 0xFF, dw[2] & 0x7F
        out.append(f"  CplID=0x{cid:04x} Status={CPL_STATUS.get(status, f'reserved {status:03b}')} "
                   f"BCM={bcm} ByteCount={bc} ReqID=0x{rid:04x} Tag=0x{tag:02x} LowerAddr=0x{low:02x}")
        if status != 0 and has_data:
            problems.append("data carried on a non-successful completion")
        if status == 0 and not has_data:
            problems.append("successful completion without data: fine for a write/I/O/config, odd for a memory read")
    elif typ >> 3 == 0x2:
        rid, tag, code = dw[1] >> 16, (dw[1] >> 8) & 0xFF, dw[1] & 0xFF
        out.append(f"  ReqID=0x{rid:04x} Tag=0x{tag:02x} MessageCode=0x{code:02x}")
    return out, problems

Questions

  1. Why does the decoder flag a 4DW header whose upper address DWORD is zero?

    Answer

    The PCI Express Base Specification requires memory requests addressing below 4 GiB to use the 32-bit (3DW) format. A 64-bit header with a zero upper address is therefore a formation error that a receiver may treat as malformed. It also often betrays a driver or device that computes the format from a variable width instead of from the address.

  2. The MRd64 for the SQE uses tag 0x21. Does the doorbell MWr's tag of 0x00 conflict with anything?

    Answer

    No. The doorbell is a posted request: nothing will answer it, so its tag is never used for matching. Tags only bind non-posted requests to their completions, and the namespace is per requester (0x0100's tag 0x21 is unrelated to anything 0x0009 sends).

  3. A 1-DWORD MWr has First BE 0011b. How many bytes are written, and at what address?

    Answer

    Two bytes, at the DWORD address +0 and +1. Byte enables select bytes within the DWORD; the address in the header is always DWORD aligned. The program's byte_count gives 2.

  4. Why is the UR completion "Cpl" and not "CplD"?

    Answer

    A completion with a non-successful status carries no data. Fmt 000b means a 3DW header with no payload; Type 01010b is a completion. A CplD with UR status would itself be a protocol error, which is why the decoder checks for it.

What a senior engineer notices

def parse(raw):
    d = struct.unpack("<16I", raw)        # 16 little-endian DWORDs: CDW0..CDW15
    return {
        "opc": d[0] & 0xFF, "fuse": (d[0] >> 8) & 3, "psdt": (d[0] >> 14) & 3,
        "cid": d[0] >> 16, "nsid": d[1], "mptr": d[4] | d[5] << 32,
        "prp1": d[6] | d[7] << 32, "prp2": d[8] | d[9] << 32, "cdw": d,
    }

             f"CID=0x{s['cid']:04x} NSID=0x{s['nsid']:x} FUSE={s['fuse']} PSDT={s['psdt']}"]
    warn = []
    if s["psdt"] == 0:
        lines.append(f"  DPTR as PRPs: PRP1=0x{s['prp1']:016x} PRP2=0x{s['prp2']:016x}")
        if s["prp1"] & 0x3:
            warn.append("PRP1 is not DWORD aligned")
    else:
        lines.append("  DPTR is an SGL descriptor (decode it with the SGL rules, Lab 5 extension)")
    if queue == "io" and s["opc"] in (0x01, 0x02):
        slba = d[10] | d[11] << 32
        nlb = (d[12] & 0xFFFF) + 1        # 0-based field
        fua, lr = (d[12] >> 30) & 1, d[12] >> 31
        nbytes = nlb * LBA_BYTES
        lines.append(f"  SLBA=0x{slba:x} NLB={nlb} blocks ({nbytes} bytes at {LBA_BYTES} B/LBA) FUA={fua} LR={lr}")
        if s["nsid"] == 1 and slba + nlb > NSZE_NS1:

    elif queue == "admin" and s["opc"] == 0x06:

Questions

  1. The Write sample has NLB field 0x000F. How many bytes does it transfer?

    Answer

    NLB is 0-based, so 16 blocks × 512 bytes = 8192 bytes. Forgetting the +1 is one of the most common decoding bugs; it makes every transfer look one block short.

  2. Which controller structure would you have to read to know the LBA size is 512 bytes instead of assuming it?

    The Identify Namespace data structure: the active LBA format (selected by FLBAS) and its LBA Data Size (LBADS, a power-of-two exponent; 9 means 512 bytes). The parser hard-codes 512 for the synthetic namespace 1; a real tool must read it.

"""Lab 4 - decode Completion Queue Entries and walk a CQ with the Phase Tag (simulation).

Input : a snapshot of an 8-entry I/O Completion Queue (16 bytes per entry) printed as
        four DWORD values per entry (DW0 DW1 DW2 DW3), plus the host's CQ head and the
        phase value the host currently expects.
Output: which entries are new, each decoded, and the CQ head doorbell value to write.

CQ_SNAPSHOT = """\

00000000 00000000 00000000 00000000
00000000 00000000 00010007 0000001f

HOST_HEAD = 2          # entries 0 and 1 were consumed earlier
EXPECTED_PHASE = 1     # first pass through the ring after creation: phase 1 means "new"

SCT = {0: "Generic Command Status", 1: "Command Specific Status",
       2: "Media and Data Integrity Errors", 3: "Path Related Status", 7: "Vendor Specific"}
GENERIC = {0x00: "Successful Completion", 0x01: "Invalid Command Opcode",
           0x02: "Invalid Field in Command", 0x04: "Data Transfer Error",
           0x06: "Internal Error", 0x07: "Command Abort Requested",
           0x08: "Command Aborted due to SQ Deletion", 0x80: "LBA Out of Range"}

def decode(dw):
    dw0, dw1, dw2, dw3 = dw
    status = dw3 >> 17
    sc, sct = status & 0xFF, (status >> 8) & 0x7
    crd, more, dnr = (status >> 11) & 0x3, (status >> 13) & 1, (status >> 14) & 1
    table = GENERIC if sct == 0 else MEDIA if sct == 2 else {}
    return {
        "dw0": dw0, "sqhd": dw2 & 0xFFFF, "sqid": dw2 >> 16,
        "cid": dw3 & 0xFFFF, "phase": (dw3 >> 16) & 1,
        "sc": sc, "sct": sct, "crd": crd, "more": more, "dnr": dnr,
        "text": table.get(sc, "(look this code up in the specification)"),
    }


def main():
    ring = [tuple(int(w, 16) for w in line.split()) for line in CQ_SNAPSHOT.splitlines()]
    size, head, phase = len(ring), HOST_HEAD, EXPECTED_PHASE
    consumed = 0
    while True:
        e = decode(ring[head])
        if e["phase"] != phase:
            print(f"slot {head}: phase {e['phase']} != expected {phase} -> stop (not yet written)")
            break
        ok = e["sc"] == 0 and e["sct"] == 0
        print(f"slot {head}: CID=0x{e['cid']:04x} SQID={e['sqid']} SQHD={e['sqhd']} "
              f"{'OK' if ok else 'ERROR'} SCT={e['sct']} ({SCT.get(e['sct'], '?')}) "
              f"SC=0x{e['sc']:02x} {e['text']} DNR={e['dnr']} M={e['more']} CRD={e['crd']}")

        consumed += 1
        if head == size:           # wrap: the meaning of "new" flips

/* cqe_decode.c - decode one 16-byte NVMe CQE given as four DWORDs (offline, no hardware).
 * Build: cc -std=c99 -Wall -o cqe_decode cqe_decode.c
 * Run:   ./cqe_decode 00000000 00000000 00010004 81010008
 */
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

struct cqe_fields {
    uint32_t dw0;      /* command specific                 */
    uint16_t sqhd;     /* DW2 bits 15:0  SQ Head Pointer   */
    uint16_t sqid;     /* DW2 bits 31:16 SQ Identifier     */
    uint16_t cid;      /* DW3 bits 15:0  Command Identifier */
    unsigned phase;    /* DW3 bit 16     Phase Tag         */
    unsigned sc, sct, crd, more, dnr;  /* DW3 bits 31:17 Status */
};

static struct cqe_fields decode(const uint32_t dw[4])
{
    struct cqe_fields f;
    uint32_t status = dw[3] >> 17;
    f.dw0 = dw[0];
    f.sqhd = (uint16_t)(dw[2] & 0xFFFF);
    f.sqid = (uint16_t)(dw[2] >> 16);
    f.cid = (uint16_t)(dw[3] & 0xFFFF);
    f.phase = (dw[3] >> 16) & 1;
    f.sc = status & 0xFF;
    f.sct = (status >> 8) & 0x7;
    f.crd = (status >> 11) & 0x3;
    f.more = (status >> 13) & 1;
    f.dnr = (status >> 14) & 1;
    return f;
}

int main(int argc, char **argv)
{
    uint32_t dw[4];
    if (argc != 5) {
        fprintf(stderr, "usage: %s DW0 DW1 DW2 DW3 (hex)\n", argv[0]);
        return 2;
    }
    for (int i = 0; i < 4; i++)
        dw[i] = (uint32_t)strtoul(argv[i + 1], NULL, 16);
    struct cqe_fields f = decode(dw);
    printf("CID=0x%04x SQID=%u SQHD=%u P=%u SCT=%u SC=0x%02x CRD=%u M=%u DNR=%u %s\n",
           f.cid, f.sqid, f.sqhd, f.phase, f.sct, f.sc, f.crd, f.more, f.dnr,
           (f.sc == 0 && f.sct == 0) ? "success" : "error");
    return 0;
}

Questions

  1. What CQ head doorbell value does the host write, and what does it tell the controller?

    Answer

    5. It tells the controller that slots up to 4 are consumed and may be reused. Until the host writes it, those slots still count as occupied; if the host never writes it, the queue eventually fills and the controller cannot post further completions.

  2. Slot 4 has M = 1. What should a careful driver or test tool do?

    Answer

    Read the Error Information log page (Get Log Page, LID 01h) for the entry that matches this SQID and CID; it can include the LBA and other details. Linux does not always fetch it automatically, which is one reason validation tools do.

  3. Why is SQHD in a completion useful to the host?

    Answer

    It reports how far the controller has consumed the Submission Queue, so the host knows which SQ slots it can reuse. It is flow control for the SQ, delivered on the CQ. It does not say which command completed; the CID does.

  4. Status SCT 2, SC 81h, DNR 0. Should the host retry?

    Answer

    It may: DNR = 0 says a retry might succeed. Unrecovered Read Error on a media read often does not succeed on retry, so the host's policy (and the CRD delay, if non-zero) matters. Linux's retry policy is version-dependent; check the driver source for your kernel.

Challenge

Make the walk refuse to consume more than size − 1 entries in one pass and report "CQ appears full" if it gets there. Explain why a CQ with all slots holding new entries is impossible by construction.

Hint

The controller considers a CQ full when advancing its tail would make it equal to the head. One slot always stays empty.

Solution

What a senior engineer notices

  • A wrong expected phase after queue re-creation (reset, queue deletion and re-creation) is a classic driver bug: the host either ignores real completions or consumes stale ones.
  • On an analyzer, the CQE is a 16-byte MWr to the CQ's address. The phase bit inside it is the controller's claim; the host's CQ head doorbell is the host's acknowledgement. You need both to know the completion was actually consumed.
  • Status codes are only meaningful with their type. "Status 0x81" means nothing without SCT.

Failure variants

  • Host never writes the CQ head doorbell → controller stops posting when the CQ fills.
  • CQE posted with the wrong phase → host waits forever (looks like a missing completion; see Lab 8).
  • CQE with a CID that is not outstanding → see Lab 7.

Background

A PRP entry is a 64-bit host address. PRP1 may start anywhere in a page (DWORD aligned); it covers from its offset to the end of that page. If the transfer ends within that page, PRP2 is unused. If exactly one more page is needed, PRP2 is the address of that page. If more pages are needed, PRP2 points to a PRP list: an array of 8-byte entries, each naming one further page with a zero offset. When a list page is not enough, its last entry points to the next list page instead of to data.

#!/usr/bin/env python3
"""Lab 5 - interpret PRP1/PRP2 and PRP lists (simulation over a fake host memory).

The controller's view: given PRP1, PRP2, the transfer length and the memory page size
(CC.MPS = 0 -> 4 KiB), which host memory ranges will it read or write?
PRP list pages live in a dictionary that stands in for host memory.
"""
import struct

PAGE = 4096                                  # CC.MPS = 0 -> 2^(12+0)

# Fake host memory: PRP list pages (IOVA -> bytes). Synthetic Lab SSD values.
MEMORY = {
    0x1_5000_0000: struct.pack("<2Q", 0x2_0000_5000, 0x2_0000_6000),
    0x1_5000_1000: struct.pack("<2Q", 0x2_0000_9000, 0x2_0000_A200),   # 2nd entry has an offset
}
# a 514-page buffer: PRP1 + 511 entries + chain pointer, then 2 more entries
MEMORY[0x1_5000_2000] = struct.pack("<512Q", *[0x2_0010_0000 + i * PAGE for i in range(1, 512)], 0x1_5000_3000)
MEMORY[0x1_5000_3000] = struct.pack("<512Q", *[0x2_0010_0000 + i * PAGE for i in range(512, 1024)])


def read_qword(addr):
    base = addr & ~(PAGE - 1)
    if base not in MEMORY:
        raise ValueError(f"PRP list read from unmapped page 0x{base:x} (would be a UR/blocked DMA)")
    return struct.unpack_from("<Q", MEMORY[base], addr - base)[0]


def walk(prp1, prp2, length):
    """Return [(address, bytes)] segments, raising ValueError on a rule violation."""
    if prp1 & 0x3:
        raise ValueError("PRP1 must be DWORD aligned (bits 1:0 = 0)")
    first = min(length, PAGE - (prp1 & (PAGE - 1)))
    segs, left = [(prp1, first)], length - first
    if left == 0:
        return segs                                         # PRP2 not used
    if left <= PAGE:
        if prp2 & (PAGE - 1):
            raise ValueError(f"PRP2 used as 2nd data page must have zero offset, got 0x{prp2:x}")
        return segs + [(prp2, left)]                        # PRP2 is the second page
    entry_addr = prp2                                       # PRP2 points to a PRP list
    if entry_addr & 0x7:
        raise ValueError("PRP list pointer must be QWORD aligned")
    while left:
        entry = read_qword(entry_addr)
        last_slot = (entry_addr & (PAGE - 1)) == PAGE - 8
        if last_slot and left > PAGE:                       # last slot chains to next list page
            entry_addr = entry
            continue
        if entry & (PAGE - 1):
            raise ValueError(f"list entry 0x{entry:x} has a non-zero offset")
        n = min(left, PAGE)
        segs.append((entry, n))
        left -= n
        entry_addr += 8
    return segs

def classify(row):
    t, addr = row["type"], row["addr"]
    if t in ("CplD", "Cpl"):
        return "completion"
    a = int(addr, 16)
    if BAR0 <= a < BAR0 + 0x4000:
        off = a - BAR0
        if off >= 0x1000:
            q, is_cq = divmod((off - 0x1000) // 4, 2)        # CAP.DSTRD = 0
            return f"{'CQ' if is_cq else 'SQ'}{q} {'head' if is_cq else 'tail'} doorbell"
        return f"controller register 0x{off:x}"
    if SQ1_BASE <= a < SQ1_BASE + SQ1_BYTES:
        return f"SQE fetch (SQ1 slot {(a - SQ1_BASE) // 64})"
    if CQ1_BASE <= a < CQ1_BASE + CQ1_BYTES:
        return f"CQE post (CQ1 slot {(a - CQ1_BASE) // 16})"
    if MSI_BASE <= a < MSI_BASE + 0x10_0000:
        return "MSI-X interrupt"
    return "data DMA"


def kv(text):
    return dict(p.split("=", 1) for p in text.split() if "=" in p)

Questions

  1. Why must the data MWrs for a Read reach host memory before the CQE that reports its completion, and what in PCIe guarantees it?

    Answer

    The host may reuse the buffer as soon as it sees the CQE. Both the data and the CQE are posted writes from the same requester, and PCIe ordering rules keep posted writes in order unless Relaxed Ordering permits passing. A controller that sets Relaxed Ordering on data writes must ensure the CQE write cannot pass them; how a controller handles this is implementation-dependent and is a known validation focus (see PCIe Ordering).

  2. Why is the MSI-X write classified by address rather than by type?

    Answer

    On the link, an MSI-X interrupt is just a memory write (MWr) of the vector's data value to the vector's address. Only the address window (programmed by the host into the MSI-X table) identifies it as an interrupt.

  3. The doorbell's Requester ID is 0x0009, the Root Port. Does that mean the Root Port decided to ring it?

    Answer

    No. The CPU's store to MMIO space is forwarded by the Root Complex, and the TLP carries the Root Complex/Root Port identity as requester. The decision came from the driver running on the CPU.

#!/usr/bin/env python3
"""Lab 7 - correlate command identifiers with completions (offline parser).

Input : NVMe-level events already extracted from a trace (by Lab 6, by an analyzer's
        NVMe decode, or from host-side tracing). One event per line:
          t_us SQE sqid cid opcode              (controller fetched this SQE)
          t_us CQE sqid cid status sqhd         (controller posted this CQE)
        CIDs are hex. Status 0 = success. Queue size of SQ1/SQ2 is 1024 entries.
Output: matched pairs with latency, plus every correlation rule that was broken.
Rule  : a command is identified by (SQ ID, CID). A CID is unique only among the
        commands outstanding on that one Submission Queue.
"""
QSIZE = 1024

EVENTS = """\
10.0  SQE 1 0005 02
10.0  SQE 1 0006 02
10.2  SQE 2 0005 01
74.1  CQE 1 0006 0 7
81.9  CQE 2 0005 0 1

95.0  SQE 1 0007 02
96.2  SQE 1 0008 01
160.4 CQE 1 0007 0 10
170.0 CQE 1 0042 0 10
175.5 CQE 1 0008 0 9
"""


def main():
    outstanding, last_sqhd, problems = {}, {}, []
    order = {}                      # per-SQ submission order of outstanding commands
    for line in EVENTS.splitlines():
        f = line.split()
        t, kind, sqid, cid = float(f[0]), f[1], int(f[2]), int(f[3], 16)
        key = (sqid, cid)
        if kind == "SQE":
            if key in outstanding:
                problems.append(f"{t:7.1f} us: SQ{sqid} CID 0x{cid:04x} submitted while still outstanding "
                                f"(host reused a CID; controller may report Command ID Conflict or confuse completions)")
                continue
            outstanding[key] = (t, f[4])
            order.setdefault(sqid, []).append(cid)
        else:
            status, sqhd = int(f[4], 16), int(f[5])
            prev = last_sqhd.get(sqid)
            if prev is not None and (sqhd - prev) % QSIZE > QSIZE // 2:
                problems.append(f"{t:7.1f} us: SQ{sqid} SQHD moved backwards {prev} -> {sqhd}")
            last_sqhd[sqid] = sqhd
            if key not in outstanding:
                problems.append(f"{t:7.1f} us: CQE for SQ{sqid} CID 0x{cid:04x} matches no outstanding command")
                continue
            t0, opc = outstanding.pop(key)
            nth = order[sqid].index(cid)
            note = "" if nth == 0 else f"  (completed ahead of {nth} older SQ{sqid} command(s): legal)"
            order[sqid].remove(cid)
            print(f"SQ{sqid} CID 0x{cid:04x} opc {opc}: {t - t0:6.1f} us, status 0x{status:x}{note}")
    for (sqid, cid), (t0, opc) in outstanding.items():
        problems.append(f"end of trace: SQ{sqid} CID 0x{cid:04x} (opc {opc}, fetched at {t0} us) never completed")
    print("\nRule violations / open items:")
    for p in problems or ["none"]:
        print("  - " + p)


if __name__ == "__main__":
    main()

Questions

  1. Give two explanations for the CQE with CID 0x0042, one that blames the device and one that blames the capture.

    Answer

    Device: the controller corrupted the CID or completed a command twice. Capture: the SQE fetch for CID 0x0042 happened before the capture started or was dropped by a filter or a capture gap. Check the capture start time and filters before writing a device bug.

  2. Why is the backward-SQHD test written as (sqhd - prev) % QSIZE > QSIZE // 2?

    Answer

    SQHD wraps. Moving from 1023 to 2 is forward motion of 3 slots, and modular subtraction gives 3. A genuine backward step of one slot gives QSIZE − 1, which is larger than half the queue. The half-queue threshold is a heuristic that assumes the controller never advances by more than half a queue between two completions on the same SQ.

  3. Is completion order across different SQs meaningful?

    Answer

    No. The specification makes no ordering promise between commands, and certainly none between queues. That is why the program tracks order per SQ only, and only to annotate, never to flag.

  • Writing verdicts that name the next experiment

Safe lab Offline parsing.

Challenge

The "doorbell covered its slot" test (tail > slot) breaks when the tail wraps. Rewrite it with modular arithmetic for a queue of 1024 entries, given the previous tail value.

Hint

A doorbell write moving the tail from old to new covers slot s when (s − old) mod Q < (new − old) mod Q.

Solution 
def covers(old_tail, new_tail, slot, q=1024):
    return (slot - old_tail) % q < (new_tail - old_tail) % q

assert covers(1022, 2, 1023)      # wrapped: slots 1022, 1023, 0, 1 are covered
assert not covers(1022, 2, 2)     # slot 2 is the new tail itself: not yet submitted
assert not covers(17, 18, 18)     # the Lab 8 case for CID 0x0012

Background

A requester that issues a non-posted request starts a completion timer. If the full set of completions does not arrive within the programmed window, it records a Completion Timeout (an uncorrectable error, reported through AER when the function implements it). Completions for a read may be split, at Read Completion Boundary multiples, into several CplDs; each carries the number of bytes still remaining (Byte Count), so the last one's Byte Count equals its own length. A completion that matches no outstanding request is an Unexpected Completion at the receiver.

The completion timeout ranges, the default range and whether software may change or disable the timeout are defined in the PCI Express Base Specification (Device Capabilities 2 and Device Control 2). They vary by function and platform. This lab's 50 ms threshold is a parameter of the offline check, not a claim about any device.

NVMe has its own, much longer timeouts (the host's command timeout, typically tens of seconds). A PCIe completion timeout is measured in microseconds to milliseconds and is detected by the requester (here, the SSD). When the SSD's DMA read times out, the host learns of it only through the device's AER report or the NVMe status of the affected command.

def decode_header(words):
    dw = [int(w, 16) for w in words.split()]
    fmt, typ, length = dw[0] >> 29, (dw[0] >> 24) & 0x1F, (dw[0] & 0x3FF) or 1024
    kind = {0: "MRd", 2: "MWr"}.get(fmt & 2, "?") if typ == 0 else f"type {typ:05b}"
    addr = (dw[2] << 32 | dw[3]) if fmt & 1 else dw[2]
    return (f"{kind}{'64' if fmt & 1 else '32'} from requester 0x{dw[1] >> 16:04x}, "
            f"addr 0x{addr & ~3:x}, length {length} DW = {length * 4} bytes")

Common mistakes across the labs

  • Forgetting that NLB, queue sizes and NUMD are 0-based.
  • Treating a CID as globally unique instead of unique per SQ among outstanding commands.
  • Treating content rather than phase as "new CQE".
  • Treating "not in the capture" as "did not happen".
  • Decoding flit-mode captures with a non-flit decoder.

Quiz

  1. Configuration offset 04h reads 0x0402. What can the device not do?

    • Respond to memory reads of its BAR
    • Issue DMA (memory requests) of its own
    • Signal INTx interrupts
    • Be enumerated
    Answer and reasoning

    0x0402 has bit 1 (Memory Space) and bit 10 (Interrupt Disable) set but bit 2 (Bus Master) clear. It decodes its BAR but cannot issue memory requests, so it cannot fetch SQEs, move data or send MSI-X messages. INTx is disabled by bit 10, but that was not the question about DMA; enumeration does not depend on the Command register.

  2. A TLP header begins 0x4A000010. What is it?

    • A 32-bit memory write of 16 DWORDs
    • A completion without data
    • A completion with 16 DWORDs of data
    • A message
    Answer and reasoning

    0x4A = 010 01010b: Fmt 010b (3DW, with data), Type 01010b (completion). Length 0x010 = 16 DWORDs = 64 bytes, exactly one SQE.

  3. An SQE's CDW12 is 0x0000001F on a 512-byte-LBA namespace. How many bytes move?

    • 15,872
    • 31
    • 512
    • 16,384
    Answer and reasoning

    NLB is 0-based: 0x1F + 1 = 32 blocks × 512 bytes = 16,384 bytes.

  4. A CQE's DW3 is 0x00010003 and the host expects phase 0. What should the host do?

    • Ignore it: the phase is 1, so it is not new on this pass
    • Complete CID 3 successfully
    • Complete CID 1
    • Report an error
    Answer and reasoning

    Bit 16 (phase) is 1. When the host expects phase 0, an entry with phase 1 was written on the previous pass and is stale.

  5. PRP1 = 0x2_0000_0F00, length 8 KiB, 4 KiB pages. How many pages are touched?

    • 1
    • 2
    • 3
    • 4
    Answer and reasoning

    ⌈(0xF00 + 0x2000) / 0x1000⌉ = ⌈0x2F00 / 0x1000⌉ = 3. PRP2 must therefore point to a PRP list with two entries.

  6. Which event is not evidence that a completion was consumed by the host?

    • A CQ head doorbell write covering the entry
    • An MSI-X write after the CQE
    • The host reusing the CID for a new command
    • The driver's completion tracepoint for that CID
    Answer and reasoning

    The MSI-X write is the controller telling the host; it says nothing about whether the host handled it (Lab 8, SQ3 CID 0x0030).

  7. A CplD arrives whose (Requester ID, Tag) matches no outstanding request in your trace. Name two explanations and the first check for each.

    Model answer

    (1) The request was not captured (capture started later, hardware filter, buffer gap): check capture start, filters and the analyzer's dropped-packet indicators. (2) A genuine Unexpected Completion (completer bug, misrouting, or a late completion after the requester timed out): check the requester's AER Unexpected Completion / Completion Timeout status bits.

  8. Why does Lab 10's parser decode the raw status register instead of the kernel's printed names?

    Model answer

    The register layout is defined by the PCI Express Base Specification and is stable; the kernel's message text varies by version and platform (and firmware-first handling may change it entirely). Decoding raw values makes the tool portable and lets you verify the kernel's decode.

  9. Explain why "the program found no problems" does not mean "the device is fine".

    Model answer

    The programs check only the rules they encode, against the input they receive. Missing input (filtered or dropped traffic), wrong decoding assumptions (wrong revision, flit mode, wrong queue addresses) and failures outside the encoded rules (performance, media errors without status) all pass silently.

  10. In Lab 6, the host wrote two CQ head doorbells for three completions. Is that a bug?

    Model answer

    No. The host may batch head updates; it only must update the head often enough that the controller does not find the CQ full. Writing fewer doorbells reduces MMIO traffic and is a common driver optimisation.

  1. Beginner. How do you find an NVMe controller's register base address from configuration space?

    Model answer

    Read BAR0 at offset 10h; check bits 2:1 for the BAR type. For a 64-bit memory BAR, mask the low four bits and combine with BAR1 as the upper 32 bits. That address plus 0 is the controller register block (CAP at 00h, VS at 08h, CC at 14h, CSTS at 1Ch, doorbells from 1000h). Confirm Memory Space Enable is set in the Command register.

  2. Beginner. What is the phase tag for?

    Model answer

    It lets the host distinguish new CQEs from old ones without the controller clearing anything. The controller writes entries with a phase value that inverts each pass through the queue; the host tracks which value means "new" and flips its expectation when its head wraps.

  3. Intermediate. How would you write a tool that associates data TLPs with NVMe commands?

    Model answer

    Decode SQE fetch completions to learn each command's PRPs (and fetch PRP lists the same way), build an address-range map per command, then attribute each data TLP by address while the command is outstanding. Caveats: buffer reuse, IOMMU remapping, SGLs, capture gaps; validate with byte totals per command.

  4. Intermediate. A trace shows a completion with UR status for the controller's PRP list read. Walk me through the next steps.

    Model answer

    Decode the request address; compare it with the PRP2 in the SQE; check whether that IOVA was mapped at the time (IOMMU fault logs); check the host's PRP list construction and lifetime; then check what NVMe status the controller returned for the command. UR on a DMA read usually indicts the address, not the link.

  5. Advanced. How do you distinguish a completion timeout from a capture gap?

    Model answer

    Look for corroborating evidence: the requester's AER Completion Timeout bit, NVMe command errors, analyzer statistics for dropped packets or buffer overrun, link state changes in the window, and whether other traffic in the same direction was captured continuously around the gap. Re-capture with a trigger on the request and no filters.

  6. Senior. Your team wants a script that writes NVMe doorbells from user space to reproduce a bug. What do you say?

    Model answer

    Only on a dedicated lab system with the kernel driver unbound (or a user-space driver framework that owns the device), with a disposable drive, a reviewed procedure, and a clear rollback (reset, power cycle). Writing doorbells under a running kernel driver corrupts its queue state and risks data loss. Prefer reproducing through the normal I/O path, an exerciser, or a simulator first.

Mastery gate and next steps

Do not move on until you can:

  • decode BAR0, MPS, MRRS, link speed and width and the MSI-X layout from a raw configuration dump by hand
  • decode a 3DW or 4DW TLP header by hand and say whether it is legal
  • decode an SQE and a CQE by hand, including 0-based fields and the status field
  • compute the PRP layout for any transfer length and offset
  • reconstruct a command's timeline from TLPs and say which stage dominated
  • locate the first missing stage of a lost command and name its owner
  • separate "timed out", "failed" and "not captured"
  • read an AER log by raw status values and decode its header log
  • state, for every tool you wrote, what its verdicts cannot prove
