Chapter 31 surveyed the NVM Command Set: what each command does and how it looks on PCIe. This module covers what a storage engineer must get right and what a validation engineer must prove: which command set a controller is actually speaking, which guarantees (atomicity, durability, deallocation, protection, reservations) the namespace really advertises, and how to tell a correct-but-surprising result from a bug.

Orientation

Every I/O command you will see in a trace belongs to an I/O command set, and on most SSDs that set is the NVM Command Set. Its commands are simple; its guarantees are subtle. "The write completed" does not mean "the write is durable". "The blocks were deallocated" does not mean "they read as zeros". "Protection information is enabled" does not mean "it was checked". "A reservation exists" does not mean "this host is blocked". Each of those gaps has an Identify field, a command bit or a status that settles it, and each is a classic source of incidents.

You need the opcode table, the Read/Write fields (SLBA, NLB, FUA, LR, PRINFO), Dataset Management, Write Zeroes, the PI concepts and the reservation types from Chapter 31 — NVM Command Set. The common command format and the Status Field are in Chapter 29 and Module 28.

Where it goes next: Module 30 — READ and Module 31 — WRITE follow single commands across the link in depth; Module 32 — FLUSH and Module 33 — Dataset Management deepen durability and deallocation; ZNS and Key Value show the other I/O command sets.

Kid story

Imagine a huge warehouse with numbered shelves, each holding exactly one box. You can ask the workers to bring you boxes from some shelves, put new boxes on some shelves, empty some shelves, or check that some boxes are still fine without bringing them to you.

Some rules are surprising. When a worker says "I put your box on the shelf", it might really be on a cart near the door, safe only if the lights don't go out. If you want it truly on the shelf, you ask "please put everything from the cart away", and you wait for the answer.

Every box can have a little label with a checksum, a tag and the shelf number written on it. If the shelf number on the label doesn't match the shelf, a careful worker shouts. And some shelves have a "reserved for Team Blue" sign; Team Red may look but not touch, or not even look, depending on the sign.

Analogy boundary

What it represents. Shelves are logical blocks (LBAs); bring, put, empty and check are Read, Write, Dataset Management/Write Zeroes and Verify; the cart by the door is a volatile write cache; "put everything away" is Flush; the label is the 8-byte protection information tuple (guard, application tag, reference tag); the signs are reservation types.

What it hides. There are no real shelves: an SSD's flash translation layer maps LBAs to changing physical locations, so "empty" (deallocate) may cost nothing and "put" may write anywhere. Many commands move no data over PCIe at all. Several workers operate at once, so two requests for the same shelf in flight together have no guaranteed order.

Where it misleads. An emptied shelf in the story is visibly empty; a deallocated LBA reads as whatever the namespace reports (zeros, ones, or "not reported"). A careful worker always checks labels in the story; in NVMe, checking happens only for fields the command's PRCHK bits select. And a sign in the story is visible to everyone; a reservation is visible only through a Reservation Report or a Reservation Conflict status.

Mechanism

A durable, protected write on a shared namespace, step by step. For this module's PI examples, namespace 2 has been reformatted (synthetic) to 4096-byte data with 8 bytes of separate metadata and PI Type 1; the Lab SSD reports VWC = 1 with the cache enabled.

  1. Discover. Who: driver at probe. What: reads ONCS, VWC, AWUPF from Identify Controller; FLBAS, DPS, DLFEAT, NAWUPF from Identify Namespace. Where: driver data. Evidence: Identify commands with 4 KiB device-to-host transfers.
  2. Register. Who: clustered application through the driver. What: Reservation Register with this host's key; Reservation Acquire (for example Write Exclusive – Registrants Only). Evidence: small MRd/CplD of the key structure for each command.
  3. Write with PI. Who: driver. What: Write (01h), CDW12 PRACT = 0, PRCHK = 111b, MPTR to eight bytes of PI per block computed by the host. Evidence: SQE fields; MRd of data and of metadata.
  4. Check. Who: controller. What: reservation check (conflict → 83h without data), then per-block PI check: guard CRC over data, reference tag against the LBA (Type 1), application tag unless the escape value is used. Evidence: only on failure (SCT 2h, SC 82h–84h).
  5. Accept into cache. Who: controller. What: data and PI land in volatile cache; CQE success. Evidence: CQE. Not yet durable.
  6. Make durable. Who: host. What: after the Write completed, submit Flush (00h) — or had set FUA on the Write. Evidence: Flush SQE and its (possibly slow) CQE.
  7. Read back later. Who: host. What: Read with PRCHK = 111b re-verifies the tuple end to end. Evidence: successful CQE, or an end-to-end check status naming the field.

The central concept on the ladder: guarantees are advertised, selected and proven

The warehouse promises only what is on its notice board, and only checks labels you ask it to check.

Each NVM guarantee — durability, atomicity, deallocated read value, PI checking, reservation access — is advertised in Identify, selected per feature or per command, and visible only through status, data or a follow-up command.

Durability: VWC + Flush/FUA. Atomicity: AWUN/AWUPF/NAWUPF and boundaries. Deallocation: DLFEAT and DULBE. PI: DPS + PRACT/PRCHK. Reservations: registrants, holder, type.

NVM Command Set 1.3 defines the commands, Identify Namespace fields and end-to-end protection; Base 2.4 defines command-set selection, features, logs, the reservation framework and generic status.

Data-moving commands produce MRd/CplD or MWr; map-only and cache commands produce only SQE fetch and CQE; failures show up as fast CQEs without data.

Classify by signature (data direction, size, latency), then decode the SQE to confirm, then check Identify to see what the success actually promised.

For any "data wrong / data lost" claim: was it durable (Flush or FUA after completion)? was it atomic (within AWUPF and boundaries)? was it deallocated (DLFEAT)? was PI checked (PRCHK)? was another host allowed to write (reservation type)?

PI checking in hardware is commonly done twice inside a good controller: at the host interface (protecting the PCIe and DMA path) and before the media write (protecting internal buffers). The NVMe status names the field that failed, not the point inside the controller where it failed, which is why vendor logs are needed to distinguish "bad on arrival" from "corrupted inside the drive".

Ordering: the NVM Command Set does not order commands in flight with respect to each other. Two overlapping Writes submitted together may complete in either order and the final content may be either; a Read overlapping an in-flight Write may return old data, new data or — beyond the atomic unit — a mixture. A host that needs ordering waits for completion before submitting the dependent command, or uses fused Compare-and-Write.

Errors specific to the set appear with SCT 0h (LBA Out of Range 80h, Reservation Conflict 83h) and SCT 2h (Unrecovered Read Error 81h, end-to-end check errors 82h–84h, Compare Failure 85h), plus deallocated-block and command-set-specific statuses named but not numbered here.

Analysis. The tuples in row 5 are big-endian: guard 0x5C3A, application tag 0x0000, reference tag 0x0001_0000. For Type 1 the reference tag must equal the low 32 bits of the block's LBA: 0x2000 and 0x2001. The host wrote 0x2000 × 8 = 0x1_0000 and 0x2001 × 8 = 0x1_0008: it computed the tag in 512-byte sectors (a block layer's native unit) instead of namespace logical blocks. Linux would print status 0x284. The guard may well be correct; it was never the problem. Whether the controller checks metadata before or after fetching data, and whether any block was written, is implementation-dependent — the status says the command failed, so the host must treat both blocks as not written. Fix: compute reference tags from namespace LBAs; regression test: the advanced lab's simulator.

Customer: "the drive cannot have written 32 MiB of zeros in 9 µs — it is lying about Write Zeroes."

Analysis. Candidates: (a) the controller implements Write Zeroes as a mapping update (mark the range as zero or deallocated) — compliant if subsequent reads return zeros; (b) the range was already deallocated and the namespace reads deallocated blocks as zeros; (c) a controller bug that completes without effect. Nothing on the link distinguishes them, because none of the candidates moves data. Evidence: Identify Namespace DLFEAT (read-back value and Write Zeroes deallocation behaviour), a read of a sample of the range (must be zeros in every compliant case), and, if PI were enabled, the guard behaviour for deallocated blocks. Only (c) is a defect, and only a read-back proves or disproves it. The DEAC bit position should be checked against your revision Check bit position.

Objective

  2. List an alternative for each.
  3. Say which SQE field would confirm it.

Your table.

  2. What is (E)'s durability state at completion?

Data direction and size first, latency second.

(A) DSM with one range (alternative: Reservation Register/Acquire with a 16-byte structure); opcode confirms. (B) Flush (alternatives: Write Zeroes done on media, Verify of a big range). Setup

# pi_sim.py - end-to-end protection (Type 1, 16-bit guard) on a 4096+8 format.
# Synthetic teaching model: it shows WHICH tuple field breaks and WHO computes it.

def crc16_t10dif(data, crc=0):
    for b in data:                       # polynomial 0x8BB7, init 0, no reflection
        crc ^= b << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x8BB7) & 0xFFFF if crc & 0x8000 else (crc << 1) & 0xFFFF
    return crc

assert crc16_t10dif(b"123456789") == 0xD0DB     # published check value

def tuple_for(block, lba, app=0x0000):
    """8-byte PI tuple: guard (2 B), application tag (2 B), reference tag (4 B), big-endian."""
    return (crc16_t10dif(block), app, lba & 0xFFFFFFFF)

def controller_write(blocks, slba, tuples, pract, prchk):
    """prchk = (guard, app, ref) booleans. Returns status name and stored tuples."""
    stored = []
    for i, blk in enumerate(blocks):
        lba = slba + i
        if pract:                        # controller generates PI, host sent none
            stored.append(tuple_for(blk, lba)); continue
        g, a, r = tuples[i]
        if a == 0xFFFF:                  # Type 1: app tag FFFFh disables checks for this block
            stored.append((g, a, r)); continue
        if prchk[0] and g != crc16_t10dif(blk):
            return "End-to-end Guard Check Error (SCT 2h, SC 82h) at LBA %#x" % lba, stored
        if prchk[2] and r != (lba & 0xFFFFFFFF):
            return "End-to-end Reference Tag Check Error (SCT 2h, SC 84h) at LBA %#x: got %#x" % (lba, r), stored
        stored.append((g, a, r))
    return "Successful Completion", stored

blocks = [bytes([i]) * 4096 for i in range(4)]
SLBA = 0x2000
ALL = (True, True, True)

cases = {
  "host PI correct":            dict(tuples=[tuple_for(b, SLBA + i) for i, b in enumerate(blocks)], pract=0, prchk=ALL),
  "PRACT=1 (controller makes)": dict(tuples=None, pract=1, prchk=ALL),
  "ref tag in 512 B units":     dict(tuples=[tuple_for(b, (SLBA + i) * 8) for i, b in enumerate(blocks)], pract=0, prchk=ALL),
  "block 2 changed after PI":   dict(tuples=[tuple_for(b if i != 2 else b"\x00" * 4096, SLBA + i) for i, b in enumerate(blocks)], pract=0, prchk=ALL),
  "same, PRCHK guard off":      dict(tuples=[tuple_for(b if i != 2 else b"\x00" * 4096, SLBA + i) for i, b in enumerate(blocks)], pract=0, prchk=(False, True, True)),
  "bad ref, app tag FFFFh":     dict(tuples=[(crc16_t10dif(b), 0xFFFF, 0) for b in blocks], pract=0, prchk=ALL),
}
for name, c in cases.items():
    status, stored = controller_write(blocks, SLBA, c["tuples"], c["pract"], c["prchk"])
    print("%-27s -> %s; tuples stored: %d" % (name, status, len(stored)))

  2. Add a read path: stored tuples are checked against PRCHK on Read, and PRACT = 1 strips them.

Questions

  1. Why does "PRCHK guard off" succeed with corrupted data, and what does that mean for a validation plan?
  2. The model stores two tuples before failing. What does a real controller guarantee about partially processed blocks?
  3. Why does the application-tag escape value hide the reference error?

Expected reasoning

PI checks are selected; escape values exist; a failed command's partial effects are not defined by the status.

Solution

(1) The guard is not checked when its PRCHK bit is clear, so corrupted data is accepted and stored with a mismatching guard; it will fail later only if a Read checks the guard. A plan must include commands with every PRCHK combination and confirm what each one catches. (2) Nothing useful: after an error the host must assume the range may hold old, new or mixed data and rewrite it. (3) For Type 1 and 2, an application tag of FFFFh disables checking for that block; hosts sometimes use it to mark "no PI yet", which also hides real errors.

Advanced lab — Reservation state machine

Safe lab Pure software.

Objective

Derive the access matrix and replay a fencing scenario.

Prerequisites

Reservation types in Chapter 31.

Setup

# resv.py - reservation access matrix and a small two-host scenario (synthetic model).
TYPES = {1: "Write Exclusive", 2: "Exclusive Access",
         3: "Write Exclusive - Registrants Only", 4: "Exclusive Access - Registrants Only",
         5: "Write Exclusive - All Registrants", 6: "Exclusive Access - All Registrants"}

def allowed(rtype, role, op):
    """role: 'holder' | 'registrant' | 'other'; op: 'read' | 'write'."""
    if rtype is None:
        return True                                   # no reservation held
    if role == "holder":
        return True
    write_excl = rtype in (1, 3, 5)
    regs_ok = rtype in (3, 4, 5, 6)                   # registrants share access
    if op == "read" and write_excl:
        return True                                   # write-exclusive types let anyone read
    return role == "registrant" and regs_ok

print("type                                  holder R/W  registrant R/W  other R/W")
for t, name in TYPES.items():
    cells = []
    for role in ("holder", "registrant", "other"):
        cells.append("".join("Y" if allowed(t, role, op) else "-" for op in ("read", "write")))
    print("%-38s  %-10s  %-14s  %s" % ("%dh %s" % (t, name), cells[0], cells[1], cells[2]))

class NS:
    def __init__(self):
        self.keys, self.holder, self.rtype, self.gen = {}, None, None, 0
    def role(self, host):
        if self.rtype in (5, 6) and host in self.keys:
            return "holder"                           # every registrant is a holder
        if host == self.holder:
            return "holder"
        return "registrant" if host in self.keys else "other"
    def register(self, host, key):
        self.keys[host] = key; self.gen += 1; return "OK"
    def acquire(self, host, key, rtype):
        if self.keys.get(host) != key:
            return "Reservation Conflict"
        if self.holder not in (None, host):
            return "Reservation Conflict"
        self.holder, self.rtype = host, rtype; return "OK"
    def preempt(self, host, key, victim_key):
        if self.keys.get(host) != key:
            return "Reservation Conflict"
        victims = [h for h, k in self.keys.items() if k == victim_key]
        for h in victims:
            del self.keys[h]
        if self.holder in victims:
            self.holder = host
        self.gen += 1; return "OK (removed %s)" % ",".join(victims)
    def io(self, host, op):
        return "OK" if allowed(self.rtype, self.role(host), op) else "Reservation Conflict"

ns = NS()
steps = [("A", "register", ("A", 0xAAAA)), ("B", "register", ("B", 0xBBBB)),
         ("A", "acquire", ("A", 0xAAAA, 1)), ("B", "io", ("B", "read")), ("B", "io", ("B", "write")),
         ("B", "preempt", ("B", 0xBBBB, 0xAAAA)), ("A", "io", ("A", "read")), ("A", "io", ("A", "write")),
         ("A", "acquire", ("A", 0xAAAA, 1))]
print()
for who, op, args in steps:
    r = getattr(ns, op)(*args)
    print("host %s %-8s %-15s -> %-22s holder=%s type=%s gen=%d" %
          (who, op, " ".join(hex(a) if isinstance(a, int) and a > 9 else str(a) for a in args[1:]), r, ns.holder, ns.rtype, ns.gen))

Procedure

  1. Run it and check the matrix against the NVMe Base 2.4 reservation tables.
  2. Add Release (holder only) and Clear (any registrant, removes everything).
  3. Model "preempt and abort", which also aborts the victim's in-flight commands.

Senior forensic lab — "Our database lost committed transactions"

Safe lab Reasoning over synthetic evidence.

Objective

Decide whether the drive, the platform or the software broke durability.

Prerequisites

This module; Chapter 31 durability rules.

Setup — evidence (synthetic)

  • After a power cut, the last 40 ms of committed transactions are missing; older data is intact.
  • Identify Controller: VWC = 1; Volatile Write Cache feature: enabled.
  • Database config: commit_method = O_DIRECT, no fsync; the commit record is written with a plain Write (FUA = 0).
  • /sys/block/nvme0n1/queue/write_cache: "write back"; fua: 1.
  • SMART: unsafe shutdowns incremented by 1. No media errors.
  • A vendor tool claims "power-loss protection: partial (mapping table only)".

Procedure

  1. Identify the first broken link in the durability chain.
  2. State whether the drive violated any guarantee.
  3. Design a confirming test and a fix.

Observations

Separate advertised guarantees, host requests, and observed loss.

Questions

  1. Does O_DIRECT imply durability?
  2. Why are older transactions intact?

Expected reasoning

Durability requires a request (Flush or FUA) that the drive honours; without it, VWC = 1 permits loss.

Solution

O_DIRECT bypasses the page cache but issues ordinary Writes; with VWC enabled, a completed Write may be in volatile cache. The database never asked for durability (no fsync → no Flush; no FUA). The drive violated nothing: it advertised a volatile cache and lost cache contents on unsafe shutdown. Older transactions were drained by normal cache eviction. Confirming test: a power-cut rig that writes sequence-numbered records with (a) plain writes, (b) FUA commit records, (c) write + fsync; only (a) should lose records. Fix: commit with fsync/fdatasync (Flush) or with FUA on the commit record; or choose drives with full power-loss protection and confirm VWC behaviour. Note the vendor claim of "partial" protection explains why mapping state survived.

Extension

Write the durability contract for this database in five lines, each with the NVMe field or command that supports it.

Debugging

Pattern 1 — End-to-end check errors after a host software change

Symptom
Writes or reads fail with SCT 2h, SC 82h/83h/84h (Linux 0x282–0x284).
Possible causes
Host tag computation (units, seed, endianness); data modified after PI generation; buffer reuse; genuine corruption in the path or the drive.
Evidence
Which field (status), metadata bytes on the wire, LBA format and PI type.
First check
Reference tag errors: compare tag values with LBAs — a constant factor means unit mismatch.
Second check
Guard errors: recompute the CRC over the captured data; mismatch on the wire means the host changed data after computing it.
Disambiguating experiment
Repeat with PRACT = 1 (controller generates); if errors vanish, the host's generation is at fault.
Likely conclusion
Host software, unless the wire data matches its tuple and the drive still fails.
Confidence
High.

Pattern 2 — "Deleted data came back" or "trimmed blocks are not zero"

Symptom
Reads of deallocated ranges return old data or non-zero values.
Possible causes
DLFEAT reports "not reported"; deallocation is advisory and the drive kept the mapping; host assumed discard zeroes data.
Evidence
DLFEAT; DSM attributes; Linux discard settings.
First check
What DLFEAT promises.
Second check
Whether the host used Write Zeroes (guaranteed zeros) or DSM (not guaranteed).
Disambiguating experiment
Write Zeroes the range and read back; zeros mean the host must use Write Zeroes for zeroing semantics.
Likely conclusion
Host assumption.
Confidence
High.

Pattern 3 — Torn writes after power loss

Symptom
Database pages half old, half new after a power cut.
Possible causes
Writes larger than AWUPF/NAWUPF; writes crossing an atomic boundary; partial power-loss protection.
Evidence
Atomicity fields; write sizes and alignment in traces.
First check
Compare page size with the atomic unit (0's based, in logical blocks).
Second check
Boundary fields (NABSPF, NABO) against page alignment.
Disambiguating experiment
Power-cut test with pages of exactly the atomic unit, aligned, versus larger.
Likely conclusion
Usually the host relied on atomicity not advertised.
Confidence
Medium–high.

Pattern 4 — Sudden Reservation Conflicts in a cluster

Symptom
One node's writes fail with 83h; reads may still work.
Possible causes
Legitimate fencing by another node; registration lost after a controller reset or host identifier change; different Host Identifiers on the controllers of one host.
Evidence
Reservation Report (holder, type, registrants, generation); cluster logs.
First check
Is this host still a registrant?
Second check
Did the generation change near the first conflict?
Disambiguating experiment
Compare Host Identifier configured on each controller path.
Likely conclusion
Fencing or host identity configuration.
Confidence
Medium.

Pattern 5 — Optional command fails with Invalid Command Opcode

Symptom
Verify, Copy, Write Zeroes or DSM fail immediately.
Possible causes
ONCS bit clear; namespace with a different command set (CSI); command placed in the other document's opcode space for your revision.
Evidence
ONCS, Commands Supported and Effects log for the namespace's CSI.
First check
ONCS bit for that command.
Second check
The namespace's command set.
Disambiguating experiment
Send the command to another namespace with a known-NVM CSI.
Likely conclusion
Host used an unsupported command; fall back (Linux does so for discard and write-zeroes).
Confidence
High.

Interview

Beginner

  1. Which NVM commands are mandatory?

    Model answer

    Read, Write and Flush.

  2. What does FUA do?

    Model answer

    Force Unit Access: the Write completes only after its data is non-volatile (and a Read with FUA reads from media).

  3. What is the difference between DSM deallocate and Write Zeroes?

    Model answer

    DSM deallocate is a hint whose read-back value depends on DLFEAT; Write Zeroes guarantees reads return zeros.

  4. What are the three parts of the PI tuple?

    Model answer

    Guard (CRC of the data), application tag, reference tag.

  5. What does Reservation Conflict mean?

    Model answer

    The command is not allowed for this host under the current reservation.

Intermediate

  1. When does Flush cover a write?

    Model answer

    When the write completed before the Flush was submitted; writes still in flight are not covered.

  2. What does PRACT = 1 do on a Write with an 8-byte metadata format?

    Model answer

    The controller generates PI; the host transfers no metadata for it.

  3. How do you know if a 16 KiB write is atomic on power failure?

    Model answer

    Check AWUPF (or NAWUPF if the namespace reports its own) converted from 0's based blocks, and the boundary fields for alignment.

  4. How do you find which optional commands a controller supports?

    Model answer

    ONCS in Identify Controller and the Commands Supported and Effects log.

  5. Why can a Write Zeroes of 32 MiB complete in microseconds?

    Model answer

    It may be implemented as a mapping change; correctness is that reads return zeros.

Advanced

  1. A reference tag error appears only on 4 KiB-formatted namespaces. Why?

    Model answer

    Host computes tags in 512-byte units; on 512-byte namespaces the units match.

  2. Why does Flush slow concurrent reads?

    Model answer

    Draining the cache occupies media program bandwidth, and reads to the same dies wait.

  3. Can two overlapping Writes in flight produce a mixture?

    Model answer

    Beyond the atomic unit, yes; the specification gives no ordering between commands in flight.

  4. How does a host choose between multiple I/O command sets?

    Model answer

    CAP.CSS reports support; CC.CSS selects all supported sets; the host reads the I/O Command Set data, selects a combination through the profile feature and learns each namespace's CSI.

  5. What do NPWG and NPWA tell a filesystem?

    Model answer

    Preferred write granularity and alignment; writes that respect them avoid internal read-modify-write.

Senior

  1. Write a durability contract for a log-structured store on NVMe.

    Model answer

    Data writes in cache; commit record with FUA (or Flush after data completes, then commit, then Flush); records sized and aligned within AWUPF; recovery verifies checksums; on VWC = 0 the Flush is cheap but still issued for portability.

  2. Design a validation plan for PI.

    Model answer

    Every PI type supported × every PRCHK combination × PRACT 0/1 × Read/Write/Compare/Verify; injected errors in each field; escape values; deallocated blocks; extended versus separate metadata; confirm status and that unchecked fields pass.

  3. How would you prove a drive violates atomicity?

    Model answer

    Power-cut tests with patterned writes of exactly the advertised unit, aligned within boundaries, thousands of cycles; any torn record within the unit is a violation; outside it, not.

  4. What host-identity mistakes break reservations?

    Model answer

    Different Host Identifiers on different controllers of the same host, identifiers that change across reboots, cloned images sharing an identifier.

  5. When is DULBE useful?

    Model answer

    When reading never-written or deallocated blocks should be an error rather than silent zeros — for example to detect logic bugs in thin provisioning or replication.

Quiz

  1. A Write completed with VWC = 1, no FUA, no Flush. The data is:

    • Durable
    • Lost
    • Accepted but possibly volatile
    • On media for sure after 1 s
    Answer and reasoning

    Completion means accepted; durability needs Flush or FUA.

  2. CDW12 = 0x1C00_0001 means:

    • FUA, 2 blocks
    • PRCHK all, PRACT 0, 2 blocks
    • PRACT 1, 1 block
    • LR, 2 blocks
    Answer and reasoning

    Bits 28:26 = 111b, bit 29 = 0, NLB = 1 (0's based).

  3. Status word 0x0509 decodes to:

    • SCT 0, SC 84h
    • SCT 5, SC 09h
    • SCT 2, SC 82h
    • SCT 2, SC 84h
    Answer and reasoning

    (0x509 >> 1) & 0xFF = 0x84; (0x509 >> 9) & 7 = 2.

  4. Under Write Exclusive, a non-registrant may:

    • Read only
    • Read and write
    • Nothing
    • Write only
    Answer and reasoning

    Write-exclusive types leave reads open to all.

  5. Which command guarantees reads of the range return zeros?

    • DSM deallocate
    • Write Zeroes
    • Flush
    • Verify
    Answer and reasoning

    DSM's read-back depends on DLFEAT.

  6. A command with no data transfer that takes 21 ms is most likely:

    • DSM
    • Read
    • Flush
    • Reservation Report
    Answer and reasoning

    Flush draining a cache (Verify or media Write Zeroes are alternatives).

  7. Why must a host wait for a Write's completion before issuing Flush for it?

    Model answer

    Flush covers only commands completed before it was submitted; in-flight writes may be processed after the Flush.

  8. Name four guarantees and the field or bit that advertises or selects each.

    Model answer

    Durability: VWC + Flush/FUA. Atomicity: AWUN/AWUPF/NAWUPF. Deallocated read: DLFEAT. PI checking: DPS + PRCHK. (Reservation access: type.)

Teach-back

  1. To a child: why "I put it on the shelf" might not be true yet.

    Model explanation

    "The worker might leave your box on a cart by the door to be quick. If the lights go out, carts are emptied. If you really need it safe, ask them to put everything away and wait until they say done."

  2. To a junior engineer: the five questions to ask when data looks wrong.

    Model explanation

    "Was it made durable — Flush or FUA after completion? Was the write within the atomic unit? Was the range deallocated, and what does DLFEAT say about reading it? Was PI checked for that command? Could another host write it under the reservation?"

  3. To a senior engineer: why NVM guarantees must be read, not assumed.

    Model explanation

    "Every one is advertised per controller or namespace and selected per feature or command: VWC, AWUPF/NAWUPF and boundaries, DLFEAT, DPS with PRACT/PRCHK, reservation type. Two compliant drives can differ on all of them. Our software must query them at runtime and degrade correctly, and our tests must prove the advertised value, not the one we hoped for."

Mastery gate

  • diagram the path of a protected, durable write on a shared namespace
