Chapter 17 walked enumeration from power-on to driver probe. This module goes into the parts that break in the field: how address space is divided among bridge windows, who owns the assignment (firmware or the operating system), how hot-plug and Single Root I/O Virtualization (SR-IOV) add functions after the first scan, how device readiness is signalled, and how to tell from evidence which stage failed.

Orientation

In Chapter 17 enumeration was a census: find every function, number every bus, size and place every Base Address Register (BAR), switch on decoding. The census is the easy half. The hard half is resource allocation: packing BARs of very different sizes and types into windows that must nest along each path, within apertures the platform firmware publishes, while leaving room for devices that do not exist yet. Most "the NVMe drive is detected but doesn't work" reports in servers come from that half.

Know Chapter 17 — PCIe Enumeration (BDF, ECAM, Type 0/1, depth-first numbering, CRS), Chapter 19 — BARs and MMIO (sizing), and the routing model of Module 03. SR-IOV is introduced in Chapter 56.

Next: Module 05 decodes the configuration registers enumeration reads and writes; Module 06 continues with BAR and MMIO from the driver's side; Module 52 takes SR-IOV further.

Kid story

A school is planning a sports day on one big field. Each class says how big a patch it needs: "we need a square 16 steps wide", "we need 256 steps". The rule is strict: every class's patch must start at a line that is a multiple of its own size, and every team of classes gets a roped-off rectangle that must start and end on the big marker posts placed every 1,000 steps. The organizer measures the smallest classes first, then ropes each team, then ropes the teams of teams, all the way up to the field gate.

Halfway through the day a new class arrives. If no one left spare space inside their team's rope, the new class has nowhere to stand — even though the field has plenty of empty grass outside the rope.

Analogy boundary

Represents. Patch sizes are BAR sizes; "start on a multiple of your size" is natural alignment; ropes are bridge windows; the 1,000-step posts are the 1 MiB window granularity; teams of teams are nested bridges; the field gate is the host bridge aperture; the late class is a hot-plugged device.

Hides. There are separate fields: 32-bit non-prefetchable memory, prefetchable memory (which may be 64-bit), I/O space and bus numbers — each with its own rules. Some classes can only stand on the near half of the field (non-prefetchable BARs must fit the 32-bit window). The organizer may be replaced at lunchtime: firmware does the first layout, the operating system may keep or redo it.

Misleads. The class does not "ask": the organizer discovers its size by writing all ones into the BAR and reading back which bits stick. And new classes can appear not only by arriving (hot-plug) but by splitting (enabling SR-IOV virtual functions multiplies one function's needs).

Window sizing

Aw = max(G, maxi ai),    Sw = align_up(Σi si + R, G)
Aw
required alignment of the bridge window
G
window granularity: 1 MiB for memory windows, 4 KiB for I/O windows
ai
alignment of child i (a BAR's alignment equals its size; a child window's is its own Aw)
Sw
window size, valid when children are placed largest-first so that no padding is needed between them
si
size of child i (BAR size, or child window size)
R
hot-plug reservation added for this bridge (0 if none)

Worked example (topology of Module 03): DSP 03:00.0 holds SSD B's 16 KiB non-prefetchable BAR → window 1 MiB (granularity dominates). DSP 03:02.0 holds the NIC's BARs (say 128 KiB) → 1 MiB. DSP 03:01.0 holds the accelerator's 256 MiB 64-bit prefetchable BAR → prefetchable window 256 MiB aligned to 256 MiB. The switch upstream port therefore needs 2 MiB non-prefetchable (below 4 GiB) and 256 MiB prefetchable (above 4 GiB if the platform allows; otherwise it must also fit below 4 GiB). Add 32 MiB of hot-plug reservation under each empty downstream port and the numbers grow quickly — that is why storage servers ship with explicit padding policies.

A 64-bit BAR that is not prefetchable — like the Lab SSD's BAR0 — can only be forwarded through a bridge's 32-bit non-prefetchable window, so it lands below 4 GiB. NVMe controller registers are non-prefetchable by nature (reads have side effects in principle, and doorbells must not be merged), so NVMe BARs compete for the scarce space under 4 GiB.

Example (synthetic): SSD B is a PF at 04:00.0 (RID 0x0400) with F = 1, D = 1 and 16 VFs → RIDs 0x0401–0x0410, i.e. 04:00.1 to 04:02.0. Device numbers above 0 on bus 04 are reachable only if the downstream port has ARI Forwarding enabled. With F = 0x100 instead, the VFs would sit on bus 05 — which must be inside DSP 03:00.0's subordinate range, already used by the accelerator in our topology. VF BAR space is also allocated in bulk: each VF BAR in the SR-IOV capability is multiplied by NumVFs, so a 16 KiB VF BAR0 × 16 VFs needs 256 KiB inside the PF's parent window.

Readiness

Before configuration, a function must be ready. Mechanisms, oldest first: the fixed post-reset wait (about 100 ms) described in Chapter 17; Configuration Request Retry Status, renamed Request Retry Status in recent revisions Version-dependent; and newer optional mechanisms that let a function report readiness sooner — an Immediate Readiness indication in the Status register, a Readiness Time Reporting capability, and Device Readiness Status / Function Readiness Status messages Optional. Exact rules, bit positions and timing are in the PCI Express Base Specification; confirm them there Uncertain rather than from this summary.

The ladder for "resource allocation"

Each class gets a patch of field inside its team's rope, measured first, placed later, with spare space for latecomers.

Software sizes every BAR, sums them into windows bottom-up, places windows top-down inside platform apertures, then enables decoding.

BARs and window registers in Type 0 and Type 1 headers; apertures inside the Root Complex; SR-IOV capability VF BARs.

PCIe defines BAR and window semantics, alignment and granularity; the PCI Firmware Specification and ACPI define how firmware hands apertures and control to the OS. The allocation algorithm is not specified.

Configuration writes to BARs and windows; Type 0 on a port's own link, Type 1 further up.

A trace shows sizing writes of FFFF_FFFFh, the read-back masks, assignment writes — or the absence of an assignment write.

"No space" or "can't assign" in the kernel log means allocation failed, not the device; compare required sizes with windows and apertures.

Well established: BAR size is found by writing all ones and reading back; BARs are naturally aligned; memory windows have 1 MiB granularity and I/O windows 4 KiB; the non-prefetchable window is 32-bit; VF Routing IDs follow First VF Offset and VF Stride.

Derived: because every window must contain its children and be contained by its parent, the hardest allocation is always at the top of the deepest, widest subtree — which is why hot-plug failures surface at the Root Port, not at the new device.

Implementation-dependent: firmware padding policy; whether firmware enables Above-4G decoding by default; how Linux sizes reservations and when it reallocates; whether the OS or firmware owns hot-plug (via _OSC).

Version-dependent: the CRS/RRS name change; readiness mechanisms added over revisions; Linux reassignment behaviour and parameter defaults across kernel releases.

Neither PCIe nor NVMe specifies how to pack BARs, how much to reserve for hot-plug, or whether the OS must keep firmware assignments.

Never assume a device listed by lspci has assigned resources; never assume BDFs survive firmware changes, hot-plug or VF enablement.

Labs

Beginner lab — Read the allocation story

Safe lab

Objective
Reconstruct, from the kernel log, which resources firmware assigned and which the OS assigned.
Prerequisites
Chapter 17.
Setup
Linux; sudo for dmesg.
Procedure
  1. Collect the apertures ("root bus resource").
  2. For your NVMe device, find its BAR lines and any "assigned" lines.
  3. Find the "bridge window" lines for each bridge above it.
  4. Check nesting in /proc/iomem.
Observations
Apertures, BAR, windows, and whether any "assigned" lines exist for your path.
Questions
(1) Did the OS keep firmware's layout? (2) Is your NVMe BAR below 4 GiB, and why? (3) How much free space is left in the window above it?
Expected reasoning
No "assigned" lines for a device usually means the firmware assignment was kept; a non-prefetchable BAR behind a bridge is below 4 GiB; free space = window size − sum of children.
Solution

On most systems Linux keeps firmware assignments and logs only the BAR values it read. If you see "assigned" lines for bridges, the kernel reallocated (perhaps due to hot-plug padding or pci=realloc). The NVMe BAR is below 4 GiB because the bridge's non-prefetchable window is 32-bit. Free space in a Root Port window is often small — firmware packs tightly unless the port is hot-plug capable.

Extension: boot a test machine with pci=realloc and diff the logs.

Prerequisites

Setup

#!/usr/bin/env python3
"""Bottom-up window sizing and top-down placement (simulation, prefetchable/non-pref split)."""
MiB, GiB = 1 << 20, 1 << 30

def align_up(x, a):
    return (x + a - 1) // a * a

# tree: name -> list of children; leaves are (bar_name, size, prefetchable64)
TREE = {
    "RP 00:02.0": ["USP 02:00.0"],
    "USP 02:00.0": ["DSP 03:00.0", "DSP 03:01.0", "DSP 03:02.0"],
    "DSP 03:00.0": [("SSD B BAR0", 16 * 1024, False)],
    "DSP 03:01.0": [("Accel BAR2", 256 * MiB, True)],
    "DSP 03:02.0": [("NIC BAR0", 128 * 1024, False)],
}
RESERVE = {"DSP 03:02.0": 0}          # add hot-plug padding here

def size(node, pref):
    """Return (size, alignment) of node's window of the given kind."""
    items = []
    for c in TREE[node]:
        if isinstance(c, tuple):
            if c[2] == pref:
                items.append((c[1], c[1]))
        else:
            items.append(size(c, pref))
    if not items and not RESERVE.get(node):
        return (0, MiB)
    align = max([MiB] + [a for _, a in items])
    total = sum(s for s, _ in sorted(items, key=lambda x: -x[1]))
    return (align_up(total + RESERVE.get(node, 0), MiB), align)

def place(free, need):
    """First-fit an aligned block of need=(size, align) in free list [(base, limit)]."""
    sz, al = need
    for i, (b, l) in enumerate(free):
        start = align_up(b, al)
        if start + sz - 1 <= l:
            return start
    return None

for pref in (False, True):
    s, a = size("RP 00:02.0", pref)
    print(f"{'pref' if pref else 'non-pref'} window for RP 00:02.0: {s // MiB} MiB, align {a // MiB} MiB")

# 32-bit aperture fragmented by other devices (synthetic): free holes below 4 GiB
free32 = [(0xC000_0000, 0xC7FF_FFFF), (0xD000_0000, 0xDBFF_FFFF), (0xFE40_0000, 0xFE5F_FFFF)]
free64 = [(0x60_0000_0000, 0x7F_FFFF_FFFF)]
for above4g in (False, True):
    need = size("RP 00:02.0", True)
    where = place(free64 if above4g else free32, need)
    status = f"placed at {where:#x}" if where is not None else "can't assign; no space"
    print(f"Above-4G={above4g}: prefetchable window {need[0] // MiB} MiB -> {status}")
Procedure
Run; set RESERVE["DSP 03:02.0"] = 32 * MiB; rerun.
Observations
Non-prefetchable window 2 MiB (two 1 MiB child windows; DSP 03:01.0 needs none); prefetchable 256 MiB aligned to 256 MiB; without Above-4G the 256 MiB-aligned block does not fit any 32-bit hole.
Questions
(1) Why does a 16 KiB BAR cost 1 MiB? (2) Why does the 128 MiB hole at 0xC000_0000 not help? (3) What does the reservation change?
Expected reasoning
Window granularity; the hole is smaller than 256 MiB (and an aligned 256 MiB block needs a 256 MiB boundary); padding inflates every ancestor's window.
Solution

Output: "non-pref window … 2 MiB", "pref window … 256 MiB, align 256 MiB", "Above-4G=False … can't assign; no space", "Above-4G=True … placed at 0x6000000000". With 32 MiB reservation on DSP 03:02.0 the non-prefetchable window grows to 34 MiB, which may itself stop fitting in a tight 32-bit layout — the trade-off every server firmware makes. The simulator ignores I/O windows and 32-bit prefetchable placement.

Extension: add a "resizable BAR" option that grows the accelerator BAR to 16 GiB and observe which apertures still fit.

Advanced lab — VF Routing IDs and reachability

Safe lab Calculation; optional read-only sysfs check on SR-IOV hardware.

Objective
Compute VF BDFs and decide what the topology must provide for them to be reachable.
Prerequisites
SR-IOV formula; Chapter 17 on ARI.
Setup
Paper, or a small script; optionally an SR-IOV-capable NVMe device on a test machine.
Procedure
  1. For PF 04:00.0 with F = 1, D = 1, N = 16, list VF BDFs.
  2. Repeat with F = 0x80, D = 2, N = 64.
  3. For each case, state the subordinate bus number and ARI setting needed on DSP 03:00.0, and the window space for VF BAR0 = 16 KiB each.
  4. Optional: read sriov_offset, sriov_stride, sriov_totalvfs on real hardware and repeat.
Observations
Two lists of BDFs, bus ranges, window needs.
Questions
Which case needs a second bus? Which needs ARI? Why might the second case break the Module 03 topology?
Expected reasoning
RID arithmetic is 16-bit, so offsets carry into the bus number.
Solution

Case 1: RIDs 0x0401–0x0410 → 04:00.1 … 04:02.0; all on bus 04; device numbers 1 and 2 used, so ARI Forwarding must be enabled on DSP 03:00.0; VF BAR0 space 16 × 16 KiB = 256 KiB (fits in the 1 MiB window). Case 2: first RID 0x0400 + 0x80 = 0x0480 (04:10.0), last 0x0480 + 63 × 2 = 0x04FE (04:1F.6) — still bus 04, ARI required; 64 × 16 KiB = 1 MiB, exactly filling a 1 MiB window with no room for the PF's own BAR → the window must grow to 2 MiB. Had the last RID exceeded 0x04FF, bus 05 would be needed, which already belongs to DSP 03:01.0 in our topology — the VFs could not be enabled without renumbering.

Extension: write a function that, given F, D, N and the port's bus range, reports every reachability problem.

Senior forensic lab — The hot-plugged drive with no BAR

Safe lab Paper exercise.

Objective
Diagnose a hot-plug failure in a storage server from logs and configuration dumps.
Prerequisites
All of this module.
Setup
Synthetic evidence: a 24-bay server boots with bays 0–19 populated. A drive inserted into bay 21 links up (LnkSta Gen4 x4), appears in lspci as 2a:00.0 class 0108, but the nvme driver logs "probe failed". Kernel log: "pci 0000:2a:00.0: BAR 0 [mem size 0x00004000 64bit]: can't assign; no space". Its Downstream Port 29:05.0 shows "Memory behind bridge: [disabled]"; neighbouring empty ports 29:04.0 and 29:06.0 also show disabled windows; populated ports show 1 MiB windows. The upstream port's window is exactly the sum of populated children. Firmware option "PCIe hot-plug resource padding" is set to 0.
Procedure
First abnormal event, hypotheses, evidence, fix, regression test.
Solution

First abnormal event: at boot, firmware gave empty hot-plug ports no window (padding 0) and sized the switch upstream window to exactly its populated children; that is the latent defect. At hot-plug time, the first observable failure is "can't assign; no space". Hypotheses: (a) no reserved window space; (b) OS cannot grow windows because siblings and parents are packed; (c) a device fault — rejected, since enumeration and sizing succeeded. Evidence: disabled windows on empty ports, upstream window equal to sum. Fix: set firmware padding (or boot with pci=hpmmiosize=/hpbussize= so Linux reserves space when it owns hot-plug and reallocates), or pci=realloc on platforms where the kernel may redo the layout at boot. Regression test: boot half-populated, hot-plug into every empty bay, verify probe and I/O; repeat with largest-BAR devices allowed in the chassis. Confidence: high.

Extension: compute the minimum padding per port for drives with up to 32 KiB BARs plus a Controller Memory Buffer BAR of 64 MiB.

Interview

Beginner

  1. How is a BAR's size discovered?

    Model answer

    Write all ones, read back; the writable address bits reveal the size, a power of two.

  2. Who assigns BAR addresses?

    Model answer

    Platform firmware first; the OS may keep or redo them.

  3. What is a bridge window?

    Model answer

    A base/limit range a bridge forwards downstream; every BAR below must be inside it.

  4. Why must Memory Space Enable be set?

    Model answer

    Without it the function ignores memory requests to its BARs.

  5. What is a VF?

    Model answer

    A lightweight function created by an SR-IOV Physical Function, with its own Routing ID and BAR space.

Intermediate

  1. Why does a 16 KiB BAR consume 1 MiB behind a bridge?

    Model answer

    Memory windows have 1 MiB granularity.

  2. Why are NVMe BARs below 4 GiB?

    Model answer

    They are non-prefetchable, and the non-prefetchable bridge window is 32-bit.

  3. What does Above-4G decoding enable?

    Model answer

    A 64-bit host-bridge aperture so 64-bit prefetchable BARs and windows can be placed above 4 GiB.

  4. What is CRS Software Visibility?

    Model answer

    A Root Port control that lets software see CRS (Vendor ID 0001h) instead of the Root Complex retrying silently.

  5. How do you compute VF Routing IDs?

    Model answer

    PF RID + First VF Offset + (n − 1) × VF Stride.

Advanced

  1. Why do hot-plug failures show up as "no space" rather than device errors?

    Model answer

    The device enumerates and sizes fine; its parent windows cannot grow because siblings and ancestors are packed.

  2. What does _OSC decide?

    Model answer

    Whether the OS or firmware controls native hot-plug, AER, PME, LTR and DPC.

  3. Why can enabling VFs require renumbering?

    Model answer

    VF RIDs may extend onto buses beyond the port's subordinate range.

  4. Read a trace with sizing but no assignment write. What do you conclude?

    Model answer

    Allocation failed in software; check logs for "can't assign" and the apertures.

  5. Why can a CPU appear hung during enumeration?

    Model answer

    Without CRS SV, the Root Complex may retry a configuration read while the device answers CRS, stalling the load.

Senior

  1. What firmware settings do you specify for a 24-bay NVMe server?

    Model answer

    Above-4G decoding, hot-plug bus and memory padding per port sized for the largest supported drive (including CMB BARs), native hot-plug/AER/DPC ownership via _OSC, and stable slot numbering.

  2. How would you validate enumeration robustness?

    Model answer

    Slow-ready devices, hot-plug into every bay, VF enable/disable cycles, firmware option matrix, repeated rescans, maximum-BAR devices, with log and trace oracles.

  3. A customer's VFs disappear after a BIOS update. Approach?

    Model answer

    Diff bus ranges, ARI settings and apertures before/after; compute VF RIDs; check kernel logs at enable; likely the new layout reserves fewer buses or less space.

  4. Should the OS always reallocate?

    Model answer

    No: firmware may rely on its layout (boot devices, platform devices); reallocating risks conflicts. Prefer correct firmware padding; use reallocation where validated.

  5. Why are BDFs bad identifiers?

    Model answer

    They are assigned by enumeration and change with topology, firmware and VF enablement; use serial numbers or NVMe identifiers.

Quiz

  1. A BAR reads back 0xFFFF_C004 after sizing. Size and type?

    • 4 KiB, 32-bit
    • 16 KiB, 32-bit, prefetchable
    • 16 KiB, 64-bit, non-prefetchable
    • 64 KiB, 64-bit
    Answer and reasoning

    Bits 2:1 = 10b (64-bit), bit 3 = 0 (non-prefetchable), lowest writable address bit is bit 14 → 16 KiB.

  2. The Memory Base/Limit DWORD 0xFE40_FE40 describes:

    • A disabled window
    • FE40_0000–FE4F_FFFF
    • FE40_0000–FE40_FFFF
    • A 64-bit window
    Answer and reasoning

    Base and limit both encode bits 31:20 = FE4; limit low bits are implied ones → 1 MiB.

  3. On the link between Root Port 00:02.0 (secondary 02) and the switch, a configuration read to 04:00.0 is:

    • Type 0
    • Type 1
    • A memory read
    • Not sent
    Answer and reasoning

    Bus 04 is beyond the Root Port's secondary bus.

  4. Compute the RID of VF 5 for PF 0x0400, F = 2, D = 2.

    Model answer

    0x0400 + 2 + 4 × 2 = 0x040A → 04:01.2.

  5. Why is the first abnormal event in Trace 3 an absence?

    Model answer

    Sizing succeeded; the expected assignment write never happened because allocation failed in software.

  6. What does "root bus resource" in the kernel log report?

    Model answer

    Host-bridge apertures provided by firmware.

  7. Which of these does the PCIe specification define?

    • Window granularity
    • Hot-plug padding size
    • The allocation algorithm
    • Kernel parameters
    Answer and reasoning

    Granularity is part of the Type 1 register definition; the rest is implementation.

  8. What is the non-prefetchable window size needed for three children of 16 KiB, 64 KiB and 128 KiB, each behind its own downstream port?

    Model answer

    Each child port needs 1 MiB → the upstream port needs 3 MiB.

  9. True or false: VFs are discovered by the initial depth-first scan.

    • True
    • False
    Answer and reasoning

    They appear only after software sets NumVFs and VF Enable.

Teach-back

To a child

Model explanation

"Each class measures its patch, then each team gets a rope around its classes. If nobody leaves extra room, a class that arrives late has nowhere to stand."

To a junior engineer

Model explanation

"Enumeration sizes BARs, sums them into bridge windows bottom-up with 1 MiB granularity, places them inside firmware apertures, then enables decoding. NVMe BARs are non-prefetchable, so they live below 4 GiB. Hot-plug and SR-IOV add functions later and can only use space reserved earlier. 'Can't assign; no space' is an allocation failure, not a dead drive."

To a senior engineer

Model explanation

"The spec defines registers and granularity, not policy. Failures cluster at the top of packed subtrees: hot-plug padding, Above-4G, VF bus coverage and ARI. Evidence is mostly in kernel logs and the absence of assignment writes; readiness problems look like hangs when CRS SV is off. Design firmware defaults for the largest device the chassis supports."
