Chapters 42 and 43 showed how an NVMe completion becomes a memory write to 0xFEE0_xxxx and how the MSI-X table is laid out. This module looks at interrupts as a system with timing, ownership and failure modes: the MSI capability in detail, coalescing as a latency trade, what happens when a reset silently switches a device back to legacy interrupts, and why an analyzer can prove an interrupt was sent but never that it was handled.

Orientation

Message Signaled Interrupts (MSI) and their extended form MSI-X replace interrupt wires with posted Memory Write (MWr) Transaction Layer Packets (TLPs) whose address and data software chose in advance. For an NVMe controller, they are the last step of every command: Completion Queue Entry (CQE) write, then interrupt write. When that last step goes wrong, a perfectly healthy drive looks hung.

You need Chapter 42 — Interrupts and Completion Signaling (INTx/MSI/MSI-X comparison, IV and IEN, coalescing, INTMS/INTMC) and Chapter 43 — MSI-X (capability, 16-byte table entries, Pending Bit Array, mask-before-modify, the torn-entry trace). Ordering comes from Chapter 14; posted credits from Module 17.

Kid story

Lena works in a sandwich shop. When an order is ready she puts it on the counter, then presses one of many buttons on a wall; each button lights a lamp at one particular table. The manager decides which button lights which table, and can put a cover over any button.

When the shop is busy, Lena waits until she has eight orders or until a minute passes, then presses once — fewer lamps, less running around. When only one customer is in the shop, that same rule makes him wait a whole minute for a sandwich that was ready in ten seconds.

One morning the wall of buttons is switched off for cleaning and nobody switches it back on. Lena falls back to the old bell over the door. Nobody is listening for the bell any more, so the sandwiches sit on the counter getting cold.

Analogy boundary

What it represents. Sandwiches on the counter are CQEs in host memory; buttons are MSI-X vectors; the manager's wiring is the MSI-X table programmed by the operating system; covers are mask bits; "eight or a minute" is NVMe Interrupt Coalescing; the bell is legacy INTx; switching the wall off is an MSI-X Enable bit cleared by a reset.

What it hides. Lena must put the sandwich down before pressing, and PCIe ordering guarantees the lamp cannot light before the sandwich is visible. A covered button remembers it was pressed (the Pending Bit Array). Between the button and the lamp sits a switchboard (interrupt remapping) that can reroute or block the signal.

Where it misleads. It suggests the lamp is a separate wire. An MSI-X interrupt is an ordinary memory write sharing the link, credits and ordering with data. It also suggests customers react instantly; a CPU may be busy, offline or in firmware when the lamp lights.

Mechanism

Follow one READ completion on CQ1 (IV 1) with coalescing THR = 7, TIME = 1.

  1. Post the CQE. Who: SSD completion engine. What changes: 16 bytes at the CQ1 tail with the current Phase Tag; tail advances. Where: host memory 0x1_2341_0000 + 16 × slot. Evidence: MWr64 of 4 DW.
  2. Count. Who: SSD interrupt engine. What changes: vector 1's pending count increments; if it was zero, the aggregation timer starts. Where: controller state. Evidence: none.
  3. Decide. Who: same. What changes: if count ≥ THR + 1, or the timer reached TIME × 100 µs, or vector 1 has CD = 1, signal; otherwise wait. Implementations may signal earlier. Evidence: timing of the MWr relative to CQEs.
  4. Check masks and mechanism. Who: PCIe function logic. What changes: if MSI-X Enable = 1 and neither Function Mask nor entry 1's mask is set, send; if masked, set PBA bit 1. Evidence: an MWr32 to 0xFEE0_1000 with data 0x41 — or none.
  5. Order. Who: SSD Transaction Layer and every hop. What changes: the interrupt MWr is posted after the CQE MWr and may not pass it. Evidence: CQE always precedes interrupt on the wire.
  6. Deliver. Who: Root Complex and IOMMU. What changes: the write is recognised as an interrupt; with remapping, its contents index a remapping entry that names the destination CPU and vector. Evidence: none on the link; IOMMU fault log if blocked.
  7. Handle. Who: target CPU, Linux, NVMe driver. What changes: handler reads CQ entries while the Phase Tag matches, completes requests, writes the CQ1 head doorbell. Evidence: MWr32 to 0xFE60_100C; /proc/interrupts count increments.

The ordering contract

The CQE write and the interrupt write are both posted requests from the same requester. Without Relaxed Ordering, a posted request may not pass an earlier posted request, so when the CPU takes the interrupt, the CQE is already visible. If a device set Relaxed Ordering on the interrupt write, the Root Complex could legally make it visible first, and a fast handler could read a stale Phase Tag, find nothing, and return — the CQE then waits for the next interrupt. Derived The specification's rules on attributes for MSI/MSI-X writes are listed in Chapter 43 as items to confirm; the design rule "never let the interrupt overtake its data" is universal.

The ladder

Put the sandwich down, then press the right button; covers and waiting rules decide whether the lamp lights now.

Each completion queue names a vector; after writing a CQE the controller sends that vector's message unless masked or coalescing says wait; the host's handler drains the queue.

Per-CQ counters and timers, per-vector table entries and mask/pending bits in BAR memory, a mechanism selector driven by capability enables, a Root Complex address decoder, remapping hardware and per-CPU interrupt controllers.

Specification discipline

Informative Implementation notes and examples in both specifications. The latency arithmetic, the ordering argument and the failure chains in this module are derived.

Optional / Implementation-dependent MSI per-vector masking; how many vectors a controller exposes (33 on the lab SSD); coalescing timer design and early signalling; whether a controller supports Feature 09h; the host's remapping format and vector allocation; Linux managed affinity policy.

Uncertain Confirm where each NVMe interrupt rule lives in your specification set.

The specifications do not say how quickly a host must handle an interrupt, which CPU should receive which vector, what coalescing values to use, or how the remapped x86 message format encodes its handle. Check in your revision: whether coalescing applies to admin and error completions, the exact list of reasons for Invalid Interrupt Vector, and attribute requirements for MSI-X writes.

Never assume a missing interrupt is a device bug before checking masks and enables, that a sent interrupt was delivered, that remapped messages can be decoded as APIC IDs, that configuration survives FLR, or that THR = 7 produces exactly one interrupt per eight completions.

Lab 1 (beginner) — Map vectors to queues and CPUs

Safe lab Read-only.

Objective. Build a table: NVMe queue → vector → Linux IRQ → CPU. Prerequisites. Chapter 42. Setup. Linux with an NVMe drive.

Procedure. Run the Linux view commands. Note the names (nvme0q0, nvme0q1…), counts per CPU, and affinities. Run a short read-only fio job pinned to one CPU and see which counter grows.

Observations. nvme0q0 is the admin queue on vector 0; I/O queues are usually one per CPU or per CPU group, with managed affinity.

Questions. How many vectors does your drive expose versus use? Why does the counter that grows belong to the CPU you pinned to?

Expected reasoning. The driver maps each CPU to a queue whose vector targets that CPU, so submission and completion stay local.

Solution

Table Size + 1 in lspci is the exposed count (33 on the lab SSD); the number of nvme0qN entries is the used count, limited by CPUs and the Number of Queues feature. The pinned CPU's queue posts its CQEs with that queue's IV, whose table entry targets the same CPU.

Extension. Compare with a machine that has fewer vectors than CPUs: which queues share vectors?

Lab 2 (intermediate) — MSI data bits and coalescing timing by hand

Safe lab Paper exercise.

Objective. Apply the MSI data formula and the coalescing rule. Prerequisites. Mechanism above. Setup. Paper.

Procedure. (1) MSI Message Control = 0x0185: decode it. (2) Software programs Message Data 0x0060 with MME = 011b: list the data for each vector. Would 0x0064 be acceptable? (3) THR = 3, TIME = 2; CQEs at 0, 30, 60, 400 µs: when are interrupts sent (ignoring early signalling)? (4) Same with CD = 1 on that vector.

Observations. MSI vector blocks must be aligned; coalescing can be "count first" or "time first" depending on load.

Questions. Why can MSI with 8 vectors not spread them over 8 CPUs on x86 without remapping?

Expected reasoning. One address, one destination; only the vector (data) varies.

Solution

(1) 0x0185: Enable = 1; MMC = 010b (4 vectors capable); MME = 000b (1 granted); 64-bit capable; per-vector masking capable. (2) 0x0060–0x0067. 0x0064 is not acceptable: the function replaces the low three bits, so it would still send 0x0060–0x0067, not the block 0x0064–0x006B the OS reserved — vectors 0–3 would land on CPU vectors belonging to someone else. (3) First CQE at 0 starts a 200 µs timer; count reaches 3 at 60 µs, below THR + 1 = 4; timer fires at 200 µs (one interrupt for three CQEs); CQE at 400 starts a new timer, interrupt at 600 µs. (4) An interrupt after every CQE.

Extension. Repeat (3) with a timer that starts at the previous interrupt instead of at the first un-signalled CQE; note how implementation choices change latency.

Lab 3 (advanced) — Model the coalescing trade-off

Safe lab Simulation.

Objective. Quantify interrupt rate against latency for queue depth and coalescing settings. Prerequisites. Traces 1 and 2. Setup. Python 3.

"""Closed-loop model of NVMe interrupt coalescing on one queue (teaching model).

qd commands are always outstanding. Each takes `dev_us` (+/- jitter) in the
device. The controller signals when pending CQEs >= THR+1 (THR is 0's based)
or when TIME*100 us has passed since the first unsignalled CQE. The host then
spends `host_us` handling and resubmits every completed command. Real
controllers may signal sooner, and this device has unlimited internal
parallelism; it is a model, not a measurement.
"""
import heapq, random

def run(qd, thr, time_units, dev_us=10.0, host_us=3.0, n=20000, seed=1):
    rnd = random.Random(seed)
    events = []                                # (time, kind)
    for _ in range(qd):
        heapq.heappush(events, (dev_us * rnd.uniform(0.8, 1.2), "cqe"))
    t = pending = done = irqs = 0
    first = None
    window = time_units * 100.0
    while done < n:
        t, kind = heapq.heappop(events)
        if kind == "cqe":
            pending += 1
            if first is None:
                first = t
                if window:
                    heapq.heappush(events, (t + window, "timer"))
        fire = pending and (pending >= thr + 1 or window == 0 or
                            (kind == "timer" and first is not None and t - first >= window - 1e-9))
        if fire:
            irqs += 1
            t_done = t + host_us
            for _ in range(pending):            # resubmit after handling
                heapq.heappush(events, (t_done + dev_us * rnd.uniform(0.8, 1.2), "cqe"))
            done += pending; pending = 0; first = None
            events = [e for e in events if e[1] != "timer"]; heapq.heapify(events)
    iops = done / t * 1e6
    return iops, irqs / t * 1e6, qd / iops * 1e6   # Little's law: latency = QD / IOPS

if __name__ == "__main__":

Procedure. Run it. Then add rows for QD 8 and 16 with THR = 7, TIME = 1, and for QD 1 with THR = 7, TIME = 0.

Observations. QD1 THR 0: ≈ 13 µs per I/O. QD1 THR 7 TIME 1: ≈ 113 µs, eight times fewer IOPS. QD32 THR 7: interrupts drop about ninefold while latency rises only ≈ 1.4 µs.

Questions. At which queue depth does THR = 7 stop hurting? Why does THR = 0 with TIME = 1 behave like no coalescing?

Expected reasoning. Once at least THR + 1 completions arrive within one TIME window, the threshold triggers before the timer; THR = 0 means "signal on the first entry".

Solution

The cliff is at QD 8 (THR + 1): QD 7 gives ≈ 111 µs per I/O, QD 8 ≈ 14.6 µs, because eight in-flight commands complete close together and reach the threshold, while seven never can and always wait for the timer. These figures come from the model, which has unlimited device parallelism and a fixed host cost; measure a real drive before choosing settings.

Lab 4 (senior forensic) — "Drive vanished after the validation script"

Safe lab Synthetic evidence. Reproducing an FLR on real hardware is an Expert lab: a test machine, no data at risk.

Objective. Reconstruct Trace 3 from host evidence alone. Prerequisites. This module; Module 41.

Setup (synthetic). Kernel log: "nvme nvme0: I/O 12 QID 3 timeout, aborting", then "controller reset", then "irq 16: nobody cared (try booting with the "irqpoll" option)", "Disabling IRQ #16", "Identify Controller timeout", "Removing after probe failure". The script log shows a setpci command 2 s before the first timeout. lspci afterwards: "MSI-X: Enable- Count=33 Masked-"; "Interrupt: pin A routed to IRQ 16".

Procedure. Write the causal chain; list alternatives and how the evidence rejects them; propose a fix and a test.

Questions. Why did the first timeout occur before the controller reset? Why does "nobody cared" point at the device's interrupt mechanism rather than at the CPU?

Solution

Chain: setpci FLR → function state reset (Bus Master off, so in-flight I/O stops: first timeout) → driver reset re-enables Memory Space and Bus Master but not MSI-X (it assumed state persisted) → controller completes Identify and signals INTx → no handler on IRQ 16 → kernel disables the line → Identify times out → removal. Rejected: SSD hang (CQEs are written, per a capture or the CQ memory); platform interrupt failure (other devices fine; the IRQ is the device's legacy line). Fix: never reset a bound function behind the kernel's back; use the sysfs reset or unbind first. Test: after every reset type, check MSI-X Enable and that the first admin completion arrives as an MWr to 0xFEEx_xxxx. Confidence: high.

Extension. What would change if the device had no INTx support (Interrupt Pin = 0)?

Interview

Beginner

  1. What is an MSI-X interrupt on the wire?

    Model answer

    A posted 1-DW memory write with the table entry's address and data.

  2. Where is the MSI-X table?

    Model answer

    In a BAR region named by Table BIR and offset; BAR0+0x2000 on the lab SSD.

  3. Which vector does the admin CQ use?

    Model answer

    Vector 0.

  4. What happens when a masked vector has an event?

    Model answer

    Its PBA bit sets; the message is sent when unmasked.

  5. Why do NVMe drives prefer MSI-X to INTx?

    Model answer

    Per-queue vectors targeting different CPUs; no shared line; no need to scan all queues.

Intermediate

  1. Why must a table entry be masked before it is modified?

    Model answer

    The device may sample a half-written entry and send a torn message.

  2. How does MSI deliver multiple vectors?

    Model answer

    By modifying the low bits of one Message Data value; one address for all.

  3. What does THR = 7, TIME = 1 do at QD1?

    Model answer

    Each completion waits for the 100 µs timer.

  4. When does an NVMe controller use INTMS/INTMC?

    Model answer

    Only with INTx or MSI; not with MSI-X.

  5. Why does the CQE always precede its interrupt on the wire?

    Model answer

    Both are posted from the same requester; a posted write may not pass an earlier one without Relaxed Ordering.

Advanced

  1. What does interrupt remapping change for an engineer reading traces?

    Model answer

    The address and data are a handle into a remapping table, not a direct CPU and vector; decode with the IOMMU state, not APIC rules.

  2. Why can an FLR leave a device on INTx?

    Model answer

    FLR clears MSI-X Enable; if software does not restore it and Interrupt Disable is clear, INTx is the active mechanism.

  3. How do SR-IOV Virtual Functions handle interrupts?

    Model answer

    Each VF has its own MSI-X capability and table in its own BAR space; the hypervisor or guest programs them, often with posted-interrupt hardware.

  4. What does a spurious interrupt with an empty CQ tell you?

    Model answer

    Either the handler already consumed entries from a later batch, or ordering/visibility failed; check timing and attributes.

  5. How do you prove an interrupt was lost in the host?

    Model answer

    Show the MWr on the wire with correct address/data, and the absence of a handler entry or a remapping fault at that time.

Senior

  1. Choose coalescing for a mixed latency/throughput workload.

    Model answer

    Coalesce throughput queues; set CD on latency-sensitive vectors or use poll queues; validate with p99 latency and interrupt rate measurements.

  2. Write a validation plan for interrupts across resets.

    Model answer

    For controller reset, FLR, hot reset, link down/up and firmware activation: verify capability state, table contents, first completion mechanism, and no lost or duplicate interrupts.

  3. A customer sees 4 ms completion stalls with a clean capture. Next steps?

    Model answer

    Host-side tracing: irq handler timestamps, SMI counts, remapping faults, affinity changes; the capture has exonerated the device.

  4. Would you allow Relaxed Ordering on CQE writes?

    Model answer

    Not unless the interrupt write is guaranteed to follow visibility; the safe rule is that CQE and interrupt must stay strongly ordered.

  5. How many vectors should an NVMe controller expose?

    Model answer

    At least as many as I/O queues it supports plus one, so per-CPU queues need not share; the cost is table space and validation effort.

Teach-back

To a child: Lena's buttons and why the one-customer shop is slow.

Model explanation

"Lena waits for eight sandwiches or a minute before pressing the button. In a busy shop that saves running. With one customer, he waits the whole minute for nothing."

To a junior engineer: how to tell who lost an interrupt.

Model explanation

"Find the CQE write. Is the interrupt write right after it? If not, the device didn't send — check IEN, masks, PBA, coalescing, MSI-X Enable. If yes, the host lost or delayed it — check remapping faults, affinity, and handler timestamps."

To a senior engineer: why interrupts are part of the data path, not a side channel.

Model explanation

"The interrupt is a posted write: it shares credits and ordering with data, depends on Bus Master Enable, passes through the IOMMU, and its configuration lives in function state that resets clear. Any of those can silently break completion signalling while the data path works."
