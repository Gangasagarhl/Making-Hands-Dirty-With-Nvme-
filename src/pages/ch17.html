Between pressing the power button and the NVMe driver writing its first register, something has to discover every PCIe function, give each bus a number, size and place every BAR, and switch on memory decoding and bus mastering. That process is enumeration. This chapter walks it step by step, as a timeline, on the course's lab machine.

Why this chapter exists

A PCI Express (PCIe) device does not announce itself. After reset it sits silently on its link, waiting for software to send it configuration requests. Until software has found it, given it a Bus/Device/Function (BDF) address on a numbered bus, sized and assigned its Base Address Registers (BARs) and enabled it, the device cannot do anything useful: it cannot be reached by memory reads and writes, and it is not allowed to start its own Direct Memory Access (DMA).

Many NVM Express (NVMe) failures that look like "the drive is dead" are enumeration failures: the device was not ready when firmware probed it, a bus-number range was too small after a hot-plug, a BAR could not be placed because the bridge window above it was too small, or bus mastering was never enabled. You cannot debug those without knowing what enumeration does and in what order.

Learning objectives

  • Describe the timeline from power-on to driver probe: firmware → Root Complex → link → device detection → BDF → configuration space → BAR sizing → BAR assignment → Command register → bus mastering → driver.
  • Explain Bus/Device/Function addressing (8/5/3 bits) and the Alternative Routing-ID Interpretation (ARI) exception.
  • Distinguish Type 0 and Type 1 configuration headers and Type 0 / Type 1 configuration requests.
  • Explain the Primary, Secondary and Subordinate Bus Number registers and how bridges use them to route configuration requests.
  • Perform depth-first bus numbering by hand on a topology with a switch.
  • Compute Enhanced Configuration Access Mechanism (ECAM) addresses.
  • Explain why an absent function reads as Vendor ID FFFFh, and what Configuration Request Retry Status (CRS) means and how CRS Software Visibility changes what software sees.
  • Use Linux tools to see the result of enumeration and know what they cannot show.

The story

A new school opens. On the first morning, the head teacher walks the corridors with a clipboard. At each door she knocks: "Is anyone in this room?" Silence means an empty room. If someone answers, she asks "Who are you, and how many desks do you need?" Some rooms have a staircase going down to more rooms; she goes all the way down that staircase, numbering each floor as she reaches it, before she comes back up and carries on along the corridor. When she has visited every room, she gives each class its desks and a room number, writes everything in her book, and finally tells each class: "You may now open your door, and you may go out and fetch your own books from the library."

A census of a new apartment complex with towers, floors and flats. The census taker starts in the lobby (bus 0), knocks on every flat door on that floor, and whenever she finds a lift (a bridge) she takes it down, gives the floor below the next unused floor number, surveys that floor completely — including any further lifts — and then writes on the lift's plaque "floors 3 to 6 are reached through me". Only when the whole complex is surveyed does the facilities office allocate electricity and water connections (address space) to each flat, wire the lift shafts to carry just the right ranges, and switch on the supply.

Where the analogy breaks. (1) A knock on an empty PCIe door is not met with silence — it is met with an "Unsupported Request" completion, which the Root Complex turns into all ones (FFFFh) for software. (2) Residents may answer "come back later" (CRS) if they are still waking up; census takers rarely get that. (3) The census taker in PCIe also measures each flat's needs by a strange ritual — writing all ones into a register and reading what sticks — rather than asking. (4) The numbering is not a permanent property of the flat: move a card to another slot, add a switch, or hot-plug a device, and bus numbers change. Never treat a BDF as a serial number. (5) In real buildings the floors exist before the census; in PCIe, bus numbers exist only because software writes them into bridges.

Beginner explanation

Every PCIe function has a small block of registers called configuration space — 256 bytes inherited from conventional PCI, extended to 4 KiB by PCIe. Software reads and writes it with special configuration requests. To send a configuration request, software needs the function's address: bus number (0–255), device number (0–31) and function number (0–7). That is the BDF, written like 01:00.0, often prefixed with a PCI segment (domain) number: 0000:01:00.0.

Bus numbers are not wired in. Bus 0 is inside the Root Complex. Every other bus number is assigned by software as it discovers bridges. Each bridge — a Root Port, or a switch port — has three registers that say which buses lie behind it:

  • Primary Bus Number — the bus the bridge itself is on (upstream side);
  • Secondary Bus Number — the bus directly below it;
  • Subordinate Bus Number — the highest-numbered bus anywhere below it.

Enumeration is the walk that fills these in. Software reads the Vendor ID of every possible device on bus 0. A function that does not exist returns FFFFh. For every bridge it finds, it assigns the next bus number to that bridge's secondary side and walks down — depth first — before continuing. Then it sizes every BAR, assigns addresses, programs bridge windows, and enables each device. Finally the operating system matches each device's IDs and class code against its drivers; for the Lab SSD, class code 010802h (mass storage, Non-Volatile Memory controller, NVM Express interface) brings in the NVMe driver.

Bus, Device, Function

A configuration address — the Routing ID or Requester ID — is 16 bits: bus number in bits 15:8, device number in bits 7:3, function number in bits 2:0. The Lab SSD at 01:00.0 has ID 0x0100; the Root Port at 00:01.1 has ID 0x0009 (device 1 → 0x08, function 1 → 0x01). These are the same IDs that appear as Requester ID and Completer ID in TLP headers (Chapter 11), which is why enumeration determines what you see in every later trace.

Root Port0000 000000001001

On a PCIe link, there is exactly one device below a Downstream Port, and it is device 0. A Downstream Port forwards Type 0 configuration requests only to device 0 on its secondary bus; requests to devices 1–31 on that bus are not delivered to the link. ARI (Alternative Routing-ID Interpretation, an optional extended capability) reinterprets the 8 bits of device + function as a single 8-bit function number, so one device can expose up to 256 functions — essential for SR-IOV devices with many Virtual Functions (Chapter 56). With ARI Forwarding enabled in the Downstream Port, the "device 0 only" rule is relaxed accordingly.

Configuration mechanisms: legacy I/O and ECAM

Conventional PCI on x86 used two I/O ports, CF8h (address) and CFCh (data), to reach the first 256 bytes of configuration space. PCIe adds the Enhanced Configuration Access Mechanism: a memory-mapped window in which every function's full 4 KiB configuration space has its own address.

addr = ECAM_base + (bus << 20) + (dev << 15) + (fn << 12) + offset
ECAM_base
the physical base address of the window for this PCI segment, reported to the OS (on ACPI systems) in the MCFG table
bus
bus number (8 bits): 1 MiB of window per bus
dev
device number (5 bits): 32 KiB per device
fn
function number (3 bits): 4 KiB per function
offset
register offset within the function's configuration space (0–FFFh)

A full 256-bus segment therefore needs 256 MiB of address space. With an illustrative ECAM base of 0xE000_0000, the Lab SSD's configuration space begins at 0xE010_0000 and its BAR0 register is at 0xE010_0010. The CPU's load or store to that address is converted by the Root Complex into a configuration request TLP; it is not a Memory Read or Memory Write on the link. Implementation-dependent The ECAM base and how the Root Complex converts accesses are platform-specific.

Type 0 and Type 1 — headers and requests

Two different things share the "Type 0/Type 1" names, and beginners mix them up:

Type 0 / Type 1: headers vs requests
Type 0Type 1
Configuration header layout (Header Type field at 0Eh, bits 6:0)Endpoints: six BARs, Subsystem IDs, Expansion ROM, Interrupt Pin/Line (Chapter 18)Bridges (Root Ports, switch ports): two BARs, Primary/Secondary/Subordinate bus numbers, I/O, memory and prefetchable memory windows, Bridge Control
Configuration request (TLP type CfgRd0/CfgWr0 vs CfgRd1/CfgWr1)Targets a function on the bus directly below the port that emits itTargets a function on a bus further down; bridges forward it

The routing rule each bridge applies to an arriving Type 1 configuration request with target bus B:

  • If B = Secondary Bus Number: convert it to a Type 0 request and send it out of the secondary side (to device 0 on a PCIe Downstream Port, unless ARI forwarding applies).
  • If Secondary < B ≤ Subordinate: forward it unchanged, still Type 1, downstream.
  • Otherwise: it is not for this bridge's subtree. (A Root Port receiving a request outside its range from the Root Complex simply does not claim it.)

Software never generates Type 1 requests explicitly: it accesses ECAM (or CF8h/CFCh) with a bus number, and the Root Complex emits Type 0 or Type 1 as appropriate.

Depth-first bus numbering

The standard algorithm, run by firmware and often redone by the OS:

  1. Start on bus 0 with next_bus = 1.
  2. For each device number 0–31 on the current bus, read function 0's Vendor ID. FFFFh → absent; skip.
  3. If function 0's Header Type has bit 7 set (multi-function), also probe functions 1–7.
  4. For each function that is a bridge (Header Type 01h): set Primary = current bus, Secondary = next_bus++, Subordinate = FFh temporarily (so Type 1 requests to any deeper bus reach this subtree while scanning), then scan the secondary bus recursively.
  5. When the recursion returns, set Subordinate = the highest bus number assigned inside the subtree.

Because the walk is depth first, every subtree gets a contiguous range of bus numbers — which is what makes the simple Secondary/Subordinate range test work. The cost: if a device is hot-plugged later behind a bridge whose range was closed tightly, there may be no bus numbers left for a new switch below it. Hot-plug-capable platforms reserve spare bus numbers (and address space) behind hot-plug ports; Linux has boot parameters for this (pci=hpbussize=, pci=hpmemsize=).

Note that a switch is two levels of bridges: the upstream port is a bridge from the link to an internal virtual bus, and each downstream port is a bridge from that internal bus to its own link. That is why a single switch consumes 1 + (number of downstream ports) bus numbers.

Detecting an absent function: Vendor ID FFFFh

When a configuration request reaches a place with no function (a device number other than 0 below a Downstream Port is filtered by the port; an absent function on a present device is answered by the device), the result is a completion with status Unsupported Request (UR) — or, with no link at all, the Root Port answers on behalf of the empty slot. The Root Complex completes the CPU's load with all ones. So the 16-bit Vendor ID reads as FFFFh. FFFFh is never a valid Vendor ID, which is what makes the test reliable.

"All ones" is also what software reads when a device that was present falls off the bus (surprise removal, link down, fatal error). A driver that reads FFFFFFFFh from a register it expects to hold something else should suspect that the device is gone, not that the register value really is all ones. The Linux NVMe driver checks for exactly this when CSTS reads as all ones.

Configuration Request Retry Status (CRS)

After reset, a function may need time to initialise (load firmware, train internal memories) before it can answer configuration requests properly. During that time it may complete them with status CRS: "not ready yet, try again". What software sees depends on the Root Port:

  • With CRS Software Visibility disabled (or not supported), the Root Complex re-issues the request itself; the CPU's load simply takes longer — possibly long enough to hit platform timeouts. Implementation-dependent
  • With CRS Software Visibility enabled (a bit in the Root Port's Root Control register, if the Root Capabilities register says it is supported), a configuration read of the Vendor ID (both bytes) that receives CRS returns the special value 0001h to software, so software can poll and do other work in between. Other registers' reads are retried by hardware.

The specification bounds how long a function may keep answering CRS after reset (the commonly cited figure is 1.0 s after Conventional Reset) and how long software must wait before the first configuration request (100 ms, measured from reset for ports at 5.0 GT/s and below, and from link-training completion for faster ports). Uncertain Confirm both figures and their exact reference points in the PCI Express Base Specification — Reset Rules for your revision. Later revisions added Readiness Notifications (a Device Readiness Status message and Function Readiness Status) and an Immediate Readiness capability bit, which let devices tell software they are ready sooner Version-dependent.

From enumeration to the NVMe driver

Once enumeration is done, the OS matches drivers. The Linux NVMe driver matches the class code 010802h (and some specific Vendor/Device IDs for quirks). Its probe routine, as pseudocode:

  1. Enable the device: make sure Memory Space Enable is set (and that BARs are assigned).
  2. Set Bus Master Enable so the controller may issue DMA (Chapter 20).
  3. Set the DMA mask (64-bit addressing).
  4. Map BAR0 into kernel virtual address space (Chapter 19).
  5. Read CAP and VS, disable the controller (CC.EN = 0), wait for CSTS.RDY = 0, program AQA/ASQ/ACQ, enable, wait for CSTS.RDY = 1 (Chapter 24).
  6. Set up MSI-X vectors, create I/O queues, identify namespaces.

The ladder

The head teacher knocks on every door, goes down every staircase first, numbers the floors, finds out how many desks each class needs, hands them out, and then lets each class open its doors and fetch its own books.

Software reads Vendor ID at every BDF, numbers buses depth-first by programming bridges' Secondary/Subordinate registers, sizes and assigns BARs, enables memory decoding and bus mastering, then binds drivers by class code.

Root Complex converts ECAM accesses into configuration TLPs; bridges hold bus-number registers and windows; each function's configuration space is a 4 KiB register file in its PCIe core, reset to defaults by Conventional Reset.

The PCI Express Base Specification defines the Type 0/Type 1 headers, configuration request routing, ECAM, the Vendor ID semantics, completion status CRS and CRS Software Visibility, reset timing rules, and ARI. The ACPI specification defines the MCFG table that publishes ECAM bases.

On the link: CfgRd0 to 01:00.0 offset 00h, completion SC with data ABCDh/0420h; or completion CRS; or UR when absent. CfgWr0 to bridge offsets 18h–1Ah. CfgWr0/CfgRd0 pairs on BARs. All non-posted, so all completed.

An analyzer shows a dense burst of configuration TLPs right after link-up; CRS completions repeating at a fixed interval while the device boots; then BAR sizing patterns (all-ones write, read, restore).

"Device not detected": check link status at the Root Port first (was the link even up?), then whether config reads returned UR (no device), CRS until timeout (device stuck in boot), or success but no driver (class code/IDs wrong or BAR assignment failed).

Hardware view

Enumeration touches three pieces of hardware:

  • The Root Complex decodes the ECAM window. A CPU access in that window becomes a configuration request. Bus 0 is internal to the Root Complex, so accesses to bus 0 are handled inside it; for any other bus, the request leaves through the Root Port whose [Secondary, Subordinate] range contains the target bus — as Type 0 if the target is that port's Secondary bus, otherwise as Type 1. The Root Complex also implements the "all ones on UR" behaviour and, optionally, CRS retry in hardware.
  • Bridges (Root Ports and switch ports) each implement a Type 1 configuration header with bus number registers and address windows; the routing comparisons are hardware comparators on every configuration request and every memory request.
  • Endpoints implement a Type 0 header. The configuration space is a register file in the PCIe core; some registers are read-only constants (IDs, class code), some are writable controls (Command, BARs), some are sticky status. BARs are implemented as registers whose low-order bits are hard-wired to zero to encode the size.

On an NVMe SSD, the PCIe core's configuration space is ready shortly after the link trains, but the NVMe controller behind it may need much longer to load firmware. Well-designed devices answer configuration requests (and so complete enumeration) early, and use the NVMe register CSTS.RDY to signal when the controller itself is ready. A device that holds CRS for a long time because its firmware is slow to boot risks being missed by platform firmware that gives up early.

The device captures its own bus and device number from the first Type 0 configuration write it receives (the specification requires functions to capture them from configuration writes) and uses them as its Requester ID in every TLP it later sends. Until it has been configured, it has no reliable ID — one more reason it must not issue requests before enumeration.

Specification view

Enumeration is governed by the PCI Express Base Specification, Revision 6.x/7.0 — Configuration Space chapter (headers, ECAM, routing), its Reset Rules section (readiness timing, CRS), the Transaction Layer — Configuration Request Routing Rules, and the ARI capability. On ACPI platforms the PCI Firmware Specification (PCI-SIG) and the ACPI Specification — MCFG table describe how firmware hands ECAM to the OS. The NVMe specifications assume enumeration is complete; NVMe over PCIe Transport Specification 1.4 specifies the class code and BAR usage of an NVMe controller.

BDF is 8/5/3 bits. Configuration space is 4 KiB per function in PCIe (256 bytes in conventional PCI). ECAM allocates 4 KiB per function, i.e. 1 MiB per bus. Type 0 headers are for Endpoints, Type 1 for bridges; Primary, Secondary and Subordinate Bus Numbers are at offsets 18h, 19h and 1Ah of a Type 1 header. FFFFh is not a valid Vendor ID. CRS is a completion status; with CRS Software Visibility enabled, a Vendor ID read that receives CRS returns 0001h. The NVMe class code is 01h/08h/02h.

The depth-first algorithm is the conventional approach used by firmware and operating systems; the specification defines the registers and routing, not the scanning algorithm. The claim that depth-first walking yields contiguous subtree ranges follows from the algorithm.

ECAM base and segment count; whether firmware or the OS assigns final resources; how the Root Complex handles CRS without software visibility; how long platform firmware waits for slow devices; bus-number and address reservations for hot-plug.

Readiness Notifications, Immediate Readiness and related reset-time reductions were added in later PCIe revisions. Flit Mode (PCIe 6.0+) changes TLP header formats but not the configuration model. Linux changed its log formats for BARs and bridge windows across kernel versions.

Check in the specification: the exact post-reset wait and its reference point for your link speed; the maximum CRS duration; which register reads are subject to CRS software visibility; the precise rules for capturing bus/device number. The specification does not mandate bus-number order, which Root Port gets which bus, or that BDFs are stable across boots.

Never assume that a BDF identifies a physical slot permanently (use slot numbers or serial numbers); that the OS kept the firmware's assignments; that a device present in firmware setup is present to the OS; or that FFFFh always means "never existed" rather than "just disappeared".

Protocol view

All configuration requests are non-posted and travel downstream only (from the Root Complex). Every one gets a completion: Successful Completion (SC) with data for reads, SC without data for writes, UR for absent functions, CRS for not-yet-ready functions. Endpoints never send configuration requests (peer configuration is not permitted).

What it cannot prove: whether firmware or the kernel assigned the resources (look for "assigned" messages); how long the device took to become ready; whether CRS was ever returned; anything about the link's history. An absent device in lspci could be a dead link, a device stuck in CRS at boot, a disabled slot, or a device the firmware hid.

echo 1 > /sys/bus/pci/rescan and echo 1 > /sys/bus/pci/devices/…/remove change system state. They are useful in a lab (Caution lab) but can take a disk away from a mounted filesystem. Never on a production machine.

Code / pseudocode

The simulation below performs depth-first bus numbering on the synthetic topology from the Engineering section, honouring multi-function devices, and prints ECAM addresses for every function. It is standard-library Python and runs as written; it does not touch real hardware.

"""Depth-first PCI bus numbering on a synthetic topology (simulation, standard library only).

Each bus is a dict mapping (device, function) -> node. A node with type 1 is a
bridge (Type 1 header) and has its own 'bus' dict below it. 'mf' marks function 0
of a multi-function device (Header Type bit 7). ECAM base 0xE000_0000 is illustrative."""

ECAM_BASE = 0xE000_0000

def ecam_addr(bus, dev, fn, offset=0):
    """ECAM: 1 MiB per bus, 32 KiB per device, 4 KiB per function."""
    return ECAM_BASE + (bus << 20) + (dev << 15) + (fn << 12) + offset

TOPOLOGY = {   # bus 0 = root bus inside the Root Complex
    (0, 0): {"name": "Host bridge", "type": 0},
    (1, 0): {"name": "Host bridge function", "type": 0, "mf": True},
    (1, 1): {"name": "Root Port 00:01.1", "type": 1, "bus": {
                (0, 0): {"name": "Lab SSD (NVMe)", "type": 0}}},
    (2, 0): {"name": "Root Port to switch", "type": 1, "bus": {
                (0, 0): {"name": "Switch upstream port", "type": 1, "bus": {
                    (0, 0): {"name": "Switch downstream port 0", "type": 1, "bus": {
                        (0, 0): {"name": "NVMe SSD #2", "type": 0}}},
                    (1, 0): {"name": "Switch downstream port 1", "type": 1, "bus": {}},
                    (2, 0): {"name": "Switch downstream port 2", "type": 1, "bus": {
                        (0, 0): {"name": "Network adapter", "type": 0}}}}}}},
}

next_bus = 1

def read_vendor_id(bus_devs, dev, fn):
    """A config read to an absent function completes with UR; software sees 0xFFFF."""
    return 0xABCD if (dev, fn) in bus_devs else 0xFFFF

def scan_bus(bus, bus_devs, depth=0):
    global next_bus
    for dev in range(32):
        if read_vendor_id(bus_devs, dev, 0) == 0xFFFF:
            continue                                  # no function 0: device absent
        multi = bus_devs[(dev, 0)].get("mf", False)   # Header Type bit 7 of function 0
        for fn in (range(8) if multi else [0]):
            if read_vendor_id(bus_devs, dev, fn) == 0xFFFF:
                continue
            node = bus_devs[(dev, fn)]
            pad = "  " * depth
            print(f"{pad}{bus:02x}:{dev:02x}.{fn}  {node['name']:<26} "
                  f"ECAM 0x{ecam_addr(bus, dev, fn):08X}  type {node['type']}")
            if node["type"] == 1:
                secondary = next_bus
                next_bus += 1
                # Primary/Secondary set now; Subordinate temporarily 0xFF so that
                # Type 1 config requests for any deeper bus are forwarded while scanning
                node["pri"], node["sec"], node["sub"] = bus, secondary, 0xFF
                scan_bus(secondary, node["bus"], depth + 1)
                node["sub"] = next_bus - 1            # highest bus number found below
                print(f"{pad}   bridge: primary={node['pri']:02x} "
                      f"secondary={node['sec']:02x} subordinate={node['sub']:02x}")

if __name__ == "__main__":
    scan_bus(0, TOPOLOGY)
    print(f"Lab SSD 01:00.0 config space base : 0x{ecam_addr(1, 0, 0):08X}")
    print(f"  Vendor ID (offset 00h)          : 0x{ecam_addr(1, 0, 0, 0x00):08X}")
    print(f"  BAR0      (offset 10h)          : 0x{ecam_addr(1, 0, 0, 0x10):08X}")
    print(f"  AER cap   (offset 100h)         : 0x{ecam_addr(1, 0, 0, 0x100):08X}")

Reading a real function's configuration space safely

#!/usr/bin/env python3
"""Read IDs and class code of a PCI function from sysfs (read-only).
Usage: python3 read_ids.py 0000:01:00.0   (unprivileged users see the first 64 bytes)"""
import struct, sys

bdf = sys.argv[1] if len(sys.argv) > 1 else "0000:01:00.0"
with open(f"/sys/bus/pci/devices/{bdf}/config", "rb") as f:
    cfg = f.read(64)
vendor, device, command, status = struct.unpack_from("<HHHH", cfg, 0x00)
rev = cfg[0x08]
prog_if, subclass, baseclass = cfg[0x09], cfg[0x0A], cfg[0x0B]
header_type = cfg[0x0E]
print(f"{bdf}: vendor={vendor:04x} device={device:04x} rev={rev:02x}")
print(f"  class={baseclass:02x}{subclass:02x}{prog_if:02x} "
      f"header type={header_type & 0x7f} multi-function={bool(header_type & 0x80)}")
print(f"  command={command:04x} (Mem={command >> 1 & 1} BusMaster={command >> 2 & 1})")
if vendor == 0xFFFF:
    print("  all ones: function absent or no longer responding")

Worked example

Problem. Using the synthetic topology, a Linux user reports NVMe SSD #2 at 04:00.0. (a) What ECAM address holds its Device ID? (b) Which bridges forward a configuration read to it, and is the request Type 0 or Type 1 on each link? (c) What Requester ID will its DMA TLPs carry?

(a) Device ID is at offset 02h. Address = 0xE000_0000 + (0x04 << 20) + (0 << 15) + (0 << 12) + 0x02 = 0xE040_0002. (A 16-bit read; or read the dword at 0xE040_0000 and take the upper half.)

(b) Root Complex: bus 04 is in Root Port 00:02.0's range [02, 06] and is not its secondary bus (02), so it leaves as Type 1 on the Root Port ↔ switch link. Switch upstream port 02:00.0: range [03, 06], secondary 03 ≠ 04 → forwarded still Type 1 onto internal bus 03. Downstream port 03:00.0: secondary = 04 → converted to Type 0, sent to device 0 on its link. So: Type 1, Type 1 (internal), Type 0.

(c) Bus 04, device 0, function 0 → 0x0400. The IOMMU uses exactly this ID to find the device's translation tables (Chapter 20) — which is why renumbering a bus after boot is so disruptive.

Common mistakes

  • Treating BDFs as permanent identifiers. Adding a card can renumber everything after it.
  • Confusing Type 0/Type 1 headers with Type 0/Type 1 requests.
  • Scanning functions 1–7 of a single-function device. Some devices respond to all function numbers with function 0's contents (aliasing); always check the multi-function bit.
  • Calling CRS an error. It is a legal completion status; overrunning the time limit is the error.
  • Assuming config writes are posted. They are non-posted and always completed.
  • Forgetting the readiness wait after resets in test scripts — leading to flaky "device not found" failures in automated validation.
  • Expecting configuration requests from Endpoints. Only the Root Complex originates them.
  • Assuming firmware assignments survive into the OS. The OS may reassign, especially with pci=realloc.

Debugging connection

A structured triage for "NVMe device missing":

  1. Is the link up? At the Root Port: LnkSta speed/width and "DLActive+" if reported. No link → Physical Layer problem (Chapter 8): power, reference clock, PERST#, seating.
  2. Is the function visible? lspci shows it? If not but link is up → CRS beyond limits, or firmware hid it, or bus-number routing is broken (Trace 4).
  3. Are resources assigned? "BAR 0: no space" / "failed to assign" in dmesg → bridge window too small (Chapter 19).
  4. Is a driver bound? lspci -k. No → class code or ID mismatch, driver not loaded, or probe failed (dmesg from the driver).
  5. Did the driver's probe fail? Typical NVMe messages: CSTS reads all ones (device dropped), controller ready timeout (CAP.TO exceeded), or DMA problems (IOMMU faults).

Always write down where the chain broke: link → visible → resources → driver → controller ready. Each stage has different owners (board, firmware, OS PCI core, driver, device firmware). Misplacing the stage sends the bug to the wrong team.

Senior engineer insight

Platform firmware, OS kernel and device firmware each assume something about the others: that the device is ready within the reset window, that firmware reserved enough bus numbers and address space for hot-plug, that the OS will not move BARs under a device already doing DMA. Most enumeration bugs in the field are violations of those unwritten assumptions rather than of the PCIe specification. In a design review, ask each owner what they assume about the other two.

Readiness timing is as much a part of the device's interface as its registers. Seniors measure time-to-first-successful-config-read and time-to-CSTS.RDY across cold boot, warm reset, hot reset and Function Level Reset, at temperature extremes, and treat any growth across firmware releases as a regression.

Lab 17 — Mapping the hierarchy

Safe lab Read-only commands and a simulation. Do not use rescan/remove in this lab.

Objective

Reconstruct the PCIe hierarchy above your NVMe device, verify the bus-number registers of every bridge on the path, and compute the ECAM address of the device's configuration space.

Skills

  • Reading bridge bus numbers.
  • Depth-first numbering by hand.
  • ECAM address calculation.

Hardware required

A Linux machine with an NVMe SSD; or none (use the synthetic topology).

Software required

pciutils, Python 3, enum_sim.py.

Input

Your device's BDF, or 0000:04:00.0 in the synthetic topology.

Expected output

A diagram of the path from bus 0 to the device, with Primary/Secondary/Subordinate for each bridge, and the device's ECAM base address.

Background

Each bridge forwards configuration requests for buses in (Secondary, Subordinate] as Type 1 and converts those for its Secondary bus to Type 0.

Step 1

Run readlink -f /sys/bus/pci/devices/<BDF>. Each path component of the form 0000:BB:DD.F is a bridge on the path.

Step 2

For each bridge, run sudo lspci -vv -s <bridge> | grep Bus: and record the three numbers.

Step 3

Find your ECAM base in dmesg (ECAM or MMCONFIG lines) and compute the address of offset 00h of your device.

Observation

Check that every bridge's [Secondary, Subordinate] range contains your device's bus number, and that the ranges nest.

Questions

  1. Which bridges on your path emit Type 1 requests to reach your device?
  2. Why does a switch consume more than one bus number?
  3. What would you see in lspci -tv if a Root Port had Secondary = 05 and Subordinate = 04?

Challenge

Add a second switch below "Switch downstream port 1" in enum_sim.py and predict the new bus numbers of every device before running it.

Hint

Depth first: everything below downstream port 1 gets numbered before downstream port 2, so the network adapter's bus number will increase.

Solution

For the synthetic 04:00.0: path 00:02.0 (pri 00, sec 02, sub 06) → 02:00.0 (pri 02, sec 03, sub 06) → 03:00.0 (pri 03, sec 04, sub 04). ECAM base 0xE040_0000 with the illustrative base. (1) 00:02.0 and 02:00.0 forward Type 1; 03:00.0 converts to Type 0. (2) One bus for the internal virtual bus behind the upstream port plus one per downstream port's link. (3) An invalid range: nothing below would be reachable; Linux would typically print a warning and try to renumber. Challenge: adding a switch with, say, two downstream ports under 03:01.0 makes 03:01.0 sec=05, the new switch upstream port 05:00.0 sec=06, its downstream ports 06:00.0 and 06:01.0 get buses 07 and 08; then 03:02.0 becomes sec=09 and the network adapter moves from 06:00.0 to 09:00.0; the Root Port's and the first switch's Subordinate become 09.

What a senior engineer notices

Whether the hot-plug-capable ports have spare bus numbers and address space reserved — the difference between a system that accepts a new device later and one that needs a reboot.

Failure variants

  • Two PCI segments (domains) on large servers: the BDF alone is ambiguous; always include the domain.
  • VMD or similar host-bridge remapping features place NVMe devices in a separate domain behind a special device; the topology looks different and the ECAM is not the platform's.

Extension

Extend enum_sim.py to reserve 4 spare bus numbers behind any bridge marked "hot-plug" and show the effect on all downstream numbering.

Exercises

  1. Convert Requester IDs 0x0100, 0x0009, 0x0418 to BDF form.
  2. Compute the ECAM offset (from base) for bus 0x3A, device 0x1F, function 7, register 0x100.
  3. A Root Port has pri=00 sec=10 sub=1F. Which of these configuration requests does it forward, and as which type: bus 0x10, 0x15, 0x20?
  4. Why does a Type 0 configuration request to device 5 on a Root Port's secondary bus never reach the link?
  5. Explain the difference in what software sees when a Vendor ID read receives UR versus CRS (with and without CRS Software Visibility).
Model answers

(1) 0x0100 → 01:00.0; 0x0009 → 00:01.1; 0x0418 → 04:03.0 (0x18 = 00011 000b → device 3, function 0). (2) (0x3A<<20) + (0x1F<<15) + (7<<12) + 0x100 = 0x03A0_0000 + 0x000F_8000 + 0x7000 + 0x100 = 0x03AF_F100. (3) 0x10 = secondary → converted to Type 0; 0x15 → forwarded as Type 1; 0x20 → outside range, not forwarded. (4) On a PCIe link only device 0 exists; the Downstream Port does not forward Type 0 requests for other device numbers (unless ARI forwarding applies), and software sees all ones. (5) UR: the Root Complex returns all ones (FFFFh) — absent. CRS with visibility: 0001h — present but not ready; without visibility: the Root Complex retries invisibly and the read takes longer or eventually fails per platform policy.

Quiz

  1. How many bits encode the device number in a BDF?

    • 3
    • 5
    • 8
    • 16
    Answer and reasoning

    Bus 8, device 5, function 3.

  2. Which register tells a bridge the highest bus number below it?

    • Primary Bus Number
    • Secondary Bus Number
    • Subordinate Bus Number
    • Header Type
    Answer and reasoning

    Subordinate, at Type 1 header offset 1Ah.

  3. Reading Vendor ID FFFFh most likely means:

    • No function responded (UR or no link)
    • The device is not ready
    • A valid vendor
    • CRS
    Answer and reasoning

    FFFFh is invalid as a Vendor ID; it is the all-ones result of an unsuccessful configuration read. With CRS visibility a not-ready device gives 0001h.

  4. How much ECAM address space does one bus occupy?

    • 4 KiB
    • 32 KiB
    • 256 KiB
    • 1 MiB
    Answer and reasoning

    32 devices × 8 functions × 4 KiB = 1 MiB.

  5. Which component converts a Type 1 configuration request to Type 0?

    • The Endpoint
    • The bridge whose Secondary Bus Number equals the target bus
    • The IOMMU
    • The Data Link Layer
    Answer and reasoning

    Routing rule of Type 1 bridges.

  6. Who usually sets Bus Master Enable for an NVMe SSD on Linux?

    • The SSD itself
    • The Root Port
    • The driver, through the PCI core during probe
    • The BIOS, permanently
    Answer and reasoning

    The NVMe driver calls the PCI core to enable bus mastering in probe. Firmware may also have enabled it while booting from the device; the OS typically resets control.

  7. Open: Why does depth-first numbering give each bridge a contiguous range?

    Model answer

    Because all buses below a bridge are assigned during the recursive call for that bridge, before any sibling bridge is visited, the numbers allocated in that call are consecutive; the bridge's Secondary is the first and its Subordinate the last.

  8. Open: List the enumeration steps from power-on to the NVMe driver probe.

    Model answer

    Firmware initialises Root Complex and ECAM; link training to L0; DL_Active; readiness wait; Vendor ID probe (with CRS retries); depth-first bus numbering; header/class/capability reads; BAR sizing; resource and window assignment; Command register Memory Space Enable; OS rescan and driver match by class 010802h; driver probe enables bus mastering, sets DMA mask, maps BAR0.

  9. Open: What is the risk of a device that keeps answering CRS for 1.5 s after a cold boot?

    Model answer

    It exceeds the readiness limit; platform firmware may conclude the slot is empty or broken, skip resource assignment, and the OS may not find it or not be able to assign BARs. Behaviour then varies by platform, producing "works on one server, missing on another" reports.

Interview questions

  1. Beginner: What is a BDF and where does it come from?

    Model answer

    Bus/Device/Function, the configuration address of a PCI function. The bus number is assigned by enumeration software via bridge registers; on PCIe the device number below a Downstream Port is 0; the function number is fixed by the device's design.

  2. Beginner: What is ECAM?

    Model answer

    The Enhanced Configuration Access Mechanism: a memory-mapped window where each function's 4 KiB configuration space is at base + bus<<20 + device<<15 + function<<12.

  3. Intermediate: Explain Primary, Secondary and Subordinate bus numbers and the routing of a configuration request.

    Model answer

    Primary is the bridge's own upstream bus, Secondary the bus directly below, Subordinate the highest below. A Type 1 request for bus = Secondary is converted to Type 0; for Secondary < bus ≤ Subordinate it is forwarded as Type 1; otherwise not claimed.

  4. Intermediate: What is CRS and why does it exist?

    Model answer

    Configuration Request Retry Status: a completion status meaning "not ready, retry". It lets devices that need time after reset avoid returning garbage or UR; with CRS Software Visibility software sees 0001h for Vendor ID reads and can poll.

  5. Advanced: An NVMe SSD enumerates after warm reboot but not after cold boot on one platform. How do you investigate?

    Model answer

    Capture link training and early config TLPs with an analyzer on cold boot; check time from PERST# deassertion to first successful config read; check power rail and reference-clock timing against the form-factor specification; compare the platform firmware's wait/CRS policy. Warm reboot works because the device is already powered and its firmware boots faster or was not reset.

  6. Senior: How would you design a platform to support hot-plugging NVMe drives behind switches?

    Model answer

    Reserve bus numbers and memory (including 64-bit prefetchable) windows behind each hot-plug port sized for the largest expected subtree; enable Data Link Layer Link Active reporting and hot-plug interrupts; set appropriate Completion Timeout and DPC/AER policies for surprise removal; ensure the IOMMU and driver handle removal; validate with repeated insertion/removal under load.

Chapter summary

Enumeration turns an anonymous tree of links into an addressed, configured system. After reset and link training, and a readiness wait, software reads the Vendor ID at each possible BDF; absent functions read FFFFh, not-ready functions may answer CRS. Bridges get Primary/Secondary/Subordinate bus numbers in a depth-first walk, which makes every subtree a contiguous range and lets bridges route Type 1 configuration requests and convert them to Type 0 at the last hop. ECAM maps each function's 4 KiB configuration space at base + bus<<20 + device<<15 + function<<12. Then BARs are sized and assigned, bridge windows programmed, memory decoding and bus mastering enabled, and drivers bound by class code — 010802h for NVMe. The BDF determined here becomes the Requester ID in every later TLP.

  • convert between BDF, Requester ID and ECAM address
  • number a topology with a switch depth-first by hand
  • explain Type 0/Type 1 headers versus requests
  • explain FFFFh, UR, CRS and 0001h
  • localise a "device missing" report to the correct stage
