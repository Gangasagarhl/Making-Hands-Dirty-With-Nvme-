Paste the header DWORDs of a Transaction Layer Packet (TLP) and this tool takes it apart field by field: what kind of packet it is, who sent it, where it goes, which bytes it touches, and which rules it breaks. Everything runs in your browser; nothing is sent anywhere.

What this tool does

A Peripheral Component Interconnect Express (PCIe) protocol analyzer, a kernel Advanced Error Reporting (AER) message and a bus-functional model in a simulation log all end up showing you the same thing: three or four 32-bit doublewords (DW) of header, sometimes followed by payload. Reading them by hand is a core skill, taught in Chapter 11 — TLP Header Anatomy. This tool is the practice partner for that chapter. It does four jobs:

  1. Classifies the packet from its Format (Fmt) and Type fields: Memory Read (MRd), Memory Write (MWr), I/O, Configuration (CfgRd0/CfgWr0/CfgRd1/CfgWr1), Completion (Cpl, CplD), Message (Msg/MsgD), AtomicOp and TLP Prefix.
  2. Decodes every field and shows it four ways — bit position, binary, hexadecimal and decimal — plus a plain-English meaning, exactly as master-prompt section 36 asks.
  3. Checks the rules that are easy to state and easy to break: byte-enable rules, the 4 KB boundary rule, configuration-request restrictions, Max Payload Size (MPS), completion length versus Byte Count, data on an unsuccessful completion.
  4. Connects layers using the course's synthetic lab system (BAR0 = 0xFE60_0000, doorbell stride 4 bytes): a write to 0xFE60_1008 is labelled "SQ1 Tail doorbell", a write into 0xFEEx_xxxx is labelled as a Message Signaled Interrupt, a configuration offset is named after the header register it hits.

You will get the most out of this page after Chapter 10 — TLPs (the kinds of packet) and Chapter 11 — TLP Header Anatomy (the fields). For the NVMe side of the annotations see Chapter 24 — NVMe Registers and Chapter 28 — Doorbells.

The tool decodes non-Flit headers — the formats used by PCIe 1.0 through 5.0 and by PCIe 6.x links that are not operating in Flit Mode. Flit Mode (mandatory at 64 GT/s and above) uses a different header layout with a single Type byte and Orthogonal Header Content; it is out of scope here. If your analyzer says "Flit", do not paste those headers into this tool.

The decoder

Choose a preset or paste your own header. Input can be DWORDs (40000001 0009000F FE601008), a byte stream in wire order (40 00 00 01 00 09 00 0F …) or one long hex string. 0x, underscores, commas and leading 0000: offsets are ignored. Any DWORDs after the header are treated as payload (and, when TD = 1, the last one as the ECRC digest). Press Ctrl+Enter in the text box to decode.

How to read the result

The output has four parts, in the order a senior engineer reads a packet:

  1. The one-line summary — kind, header size, payload size and address. If this line surprises you (a 4 DW header where you expected 3, a CplD where you expected a Cpl), stop and find out why before reading further.
  2. The verdict — "well-formed", "decodes with warnings" or a count of rule violations. Errors are rules the PCIe Base Specification states as requirements (a receiver would log a Malformed TLP or similar). Warnings are legal-but-suspicious or revision-dependent cases.
  3. Notes — derived facts: how many bytes a request really touches after byte enables, whether a completion is partial, what an address means on the lab system.
  4. The field table — one row per field: name, position as DWn[hi:lo], binary, hex, decimal and meaning.

Bit and byte numbering

The tool follows the specification's convention: each DW is written most-significant byte first, and byte 0 of the header is bits 31:24 of DW0. So in 40000001, the first byte on the wire is 40 (Fmt and Type) and the last is 01 (low bits of Length). Analyzers display headers the same way. Payload is different: it is a byte stream, and NVMe values in it are little-endian, so a doorbell value of 5 is the bytes 05 00 00 00, which this tool shows as the DW 05000000. Some analyzers swap payload bytes for display; check which convention yours uses before you trust a decoded doorbell value.

Requester and Completer IDs

A 16-bit ID is shown as Bus:Device.Function: bits 15:8 bus, 7:3 device, 2:0 function. On the lab system the SSD at 01:00.0 is 0x0100 and the root port at 00:01.1 is 0x0009. With Alternative Routing-ID Interpretation (ARI) enabled, the low eight bits are a single function number; the tool's B:D.F view is then misleading, and it says so.

Tags

The Tag of a non-posted request is echoed in its completion, together with the Requester ID. Pairing a CplD with its MRd is therefore a two-field match: Requester ID and Tag. Bits T9 and T8 in DW0 extend the tag to 10 bits on devices with 10-bit tags enabled (PCIe 4.0 and later); before that they were reserved, and a capture of an older device will always show them as 0.

Worked examples

Each example below is a preset in the tool. Load it, read the output, then check your reading against the reasoning here. All are synthetic, built from the course's lab system (Chapter 24, Chapter 28).

1. The doorbell: 40000001 0009000F FE601008 05000000

Byte 0 is 0x40 = 010 00000: Fmt 010 (3 DW, with data), Type 0 → MWr32. Length = 1 DW. DW1: Requester ID 0x0009 (00:01.1, the root port — CPU stores leave the root complex carrying its ID), Tag 0 (meaningless on a posted write), Last BE 0000 (required for a 1-DW request), First BE 1111 (all four bytes). Address 0xFE60_1008 = BAR0 + 0x1008. With CAP.DSTRD = 0 the doorbells are 4 bytes apart from 0x1000: SQ0 tail, CQ0 head, SQ1 tail … so 0x1008 is the SQ1 Tail doorbell. The payload bytes 05 00 00 00 are the little-endian value 5: the driver says "SQ1 tail is now slot 5".

The packet carries no NVMe meaning at all. "Doorbell" is an interpretation you add by knowing BAR0 and CAP.DSTRD. That is why the tool lets you set the BAR0 base: a wrong base turns every doorbell annotation into nonsense, exactly as a wrong mental model would in a real trace.

2. The SQE fetch and its completion

20000010 010010FF 00000001 23400440: Fmt 001 (4 DW, no data), Type 0 → MRd64, Length 0x10 = 16 DW = 64 bytes — one Submission Queue Entry. Requester 01:00.0 (the SSD), Tag 0x10, both BEs 1111. Address 0x1_2340_0440: SQ1 base 0x1_2340_0000 + 0x440 = slot 0x11 × 64 bytes.

Now load the CplD preset, 4A000010 00090040 01001040: Fmt 010, Type 0 1010 → CplD, Length 16 DW. Completer 0x0009, Status 000 (Successful Completion), Byte Count 0x040 = 64, Requester 0x0100, Tag 0x10, Lower Address 0x40. Requester ID and Tag match the MRd; Byte Count equals the length, so this is the only completion; Lower Address 0x40 equals the low seven bits of 0x…0440. Every cross-check passes.

  1. MWr32 0xFE601008 = 5 (SQ1 tail)
  2. MRd64 0x1_2340_0440 Len=16 Tag=0x10
  3. CplD Tag=0x10 BC=64 LA=0x40
  4. decode SQE, start command

3. A partial completion

4A000010 00090200 01003100 carries 16 DW, but Byte Count says 0x200 = 512 bytes remain. The tool reports "partial completion": more CplDs with Tag 0x31 must follow, each with a smaller Byte Count, the last having Byte Count equal to its own length. A 512-byte read answered in 64-byte pieces is normal (the completer may split at the Read Completion Boundary, 64 bytes on the lab system). A sequence whose Byte Counts do not go down by exactly the bytes delivered is a completer bug.

4. Unsupported Request

0A000000 00092100 01002300: a Cpl (no data) with Status 001 = UR, returning to the SSD for Tag 0x23. If the SSD's request was a data read for an NVMe Write command, the controller will fail that command (typically with a data-transfer error status in its CQE, Chapter 44) and the root port may log an AER Unsupported Request. A frequent root cause is a PRP entry pointing at an address that the IOMMU does not map (Chapter 36, Chapter 38).

5. Crossing a 4 KB boundary

20000040 010031FF 00000002 00000F80 asks for 256 bytes starting at 0x2_0000_0F80 — 128 bytes before a 4 KB boundary. The rule is absolute: no memory request may span a 4 KB-aligned address. A compliant DMA engine would have issued two requests (128 bytes at 0x…0F80, 128 bytes at 0x…1000). A receiver treats this one as a Malformed TLP, an uncorrectable error.

The tool does not know the state of the link: whether Relaxed Ordering, No Snoop, 10-bit tags or ID-Based Ordering were enabled in the requester's Device Control registers, whether the address is inside a BAR, or whether the tag is already outstanding. Those checks need the configuration space (Config Space Decoder) and the surrounding trace. A packet that is well-formed in isolation can still be wrong in context.

Limitations and truth labels

  • Non-Flit only. Flit Mode headers (PCIe 6.x and later in Flit Mode) are not decoded. Version-dependent
  • TLP Prefixes are recognised and skipped; their contents (PASID, vendor prefixes) are not decoded.
  • TLP Processing Hints. When TH = 1 the PH bits are shown; the Steering Tag, which reuses other fields depending on request type, is not decoded.
  • Messages. Common message codes are named (INTx, PM, error messages, LTR, OBFF, Set_Slot_Power_Limit, vendor-defined); vendor-defined message contents are not decoded.
  • ECRC is displayed, not verified. The tool does not compute the LCRC either: it never sees the Data Link Layer framing.
  • NVMe annotations assume the lab system: BAR0 at the address you enter, 64-bit BAR, CAP.DSTRD = 0, MSI-X table at BAR0 + 0x2000. A real device needs its own values. Implementation-dependent
  • CRS vs RRS. Completion Status 010b was called Configuration Request Retry Status in older revisions and Request Retry Status more recently; the tool shows both names.

A synthetic preset is a teaching example. Do not compare a real device's traffic against these exact values, only against the rules.

Practice

  1. Byte 0 of a header is 0x60. What is the TLP?

    • MRd64
    • CplD
    • MWr64
    • Msg
    Answer and reasoning

    0x60 = 011 00000: Fmt 011 (4 DW, with data), Type 0 → MWr with a 64-bit address.

  2. An MRd32 has Length = 1, First BE = 1111, Last BE = 1111. What is wrong?

    Answer

    For a 1-DW request Last DW BE must be 0000. Paste 00000001 0100000F FE601000 versus 00000001 010000FF FE601000 to see the difference.

  3. A CplD has Length = 2, Byte Count = 4, Lower Address = 0x02. Is it consistent?

    Answer

    Yes. The data starts at byte 2 of a DW, so 4 bytes span bytes 2–5, i.e. two DWs. Length 2 = ⌈(2 + 4)/4⌉.

  4. Encode by hand: the SSD (01:00.0) reads 16 bytes at 0x1_2341_0000 with Tag 0x05. Check your answer in the tool.

    Answer

    20000004 010005FF 00000001 23410000: MRd64, Length 4 DW, Requester 0x0100, Tag 0x05, BEs 1111/1111.

  5. Which field pair links a completion to its request?

    • Completer ID and Lower Address
    • Requester ID and Tag
    • Byte Count and Length
    Answer and reasoning

    The completion echoes the requester's ID and tag; together they are unique among that requester's outstanding non-posted requests.

  6. A CfgRd0 decodes with offset 0x100. What region is that?

    Answer

    The start of PCIe extended configuration space, where the first extended capability header (often AER) lives. Reaching it needs the Ext Register Number field, which is why legacy port-I/O config access (256 bytes only) cannot see it.

  7. An MWr64 to 0x0_FEE0_1000 decodes "with warnings". Why might a real device do this, and why does it matter?

    Answer

    A device with a 64-bit MSI-X address register may emit 4 DW headers regardless of the value. The rule says addresses below 4 GB use the 3 DW form; how strictly receivers enforce that has changed between revisions, so it is a compatibility risk worth noting, not an automatic fault.

  8. Why can the tool never tell you whether a posted MWr "succeeded"?

    Answer

    Posted requests have no completion. Success is only visible indirectly — the effect (a doorbell causing an SQE fetch) or the absence of an error message.
