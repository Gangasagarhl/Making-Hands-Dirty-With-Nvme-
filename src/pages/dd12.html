Chapter 52 taught the arithmetic of completions: how a read is split, what Byte Count and Lower Address must be, and how timeouts are configured. This module treats the completion as a protocol between two state machines — a completer that decides what to answer and a requester that decides whether to believe it — and follows completions into the places where NVMe failures actually hide: error statuses, retries during reset, poisoned data, latency tails and evidence gaps in captures.

Orientation

Every non-posted request is a promise that exactly one of three things will happen: all of its completions arrive with Successful Completion status, an error completion arrives, or the requester's timer expires. This module deepens each branch. It covers the completer side (who generates which status, and why), the requester side (the matching and acceptance machine), configuration-retry behaviour around resets, how an NVMe controller turns a failed completion into an NVMe status, and how to prove from a capture that a completion was really missing rather than missed by the analyzer.

Completion header fields, splitting rules, Read Completion Boundary (RCB), Byte Count/Lower Address arithmetic, timeout ranges and Unexpected Completions: Chapter 52 — Completion Rules. Header decoding: Chapter 11 and Module 11. This module does not repeat the arithmetic; it uses it.

Kid story

You order a big puzzle from a toy shop by post, and the shop always writes back. Sometimes the whole puzzle comes in one box. Sometimes it comes in several boxes, each with a sticker: "pieces still to come, counting this box" and "where on the board these pieces go". Sometimes a letter comes instead: "we don't sell that" (that is Unsupported Request) or "our machine broke while packing it" (Completer Abort). And sometimes, when the shop has just opened in the morning, the letter says "we're not open yet, ask again in a minute" — that is the retry status.

You keep a list on the fridge of every order you are waiting for. When a box arrives, you check it against the list. If a box comes for an order that is not on your list, you are puzzled — maybe you crossed it out because you gave up waiting. And if you wait too long, you cross the order out and tell your parents something went wrong.

Analogy boundary

What it represents. One request, one or more answers; the answers say how much is left and where they belong; error letters end the order; a retry letter is special; the fridge list is the requester's outstanding-request table.

What it hides. The shop does not know your address in full — completions carry only the requester's ID and the low 7 address bits, so the requester must remember the rest. Boxes for one order must arrive in order (address order); boxes for different orders may arrive in any order. And a PCIe completion travels hop by hop through switches, which route it by ID without looking inside.

Where it misleads. "We're not open yet" only applies to configuration requests; a memory read never gets a retry status. Real shops may send a partial order and an apology; in PCIe an error completion ends the request, and any data already received for it must be treated as failed. And you cannot phone the shop to ask where the box is: a PCIe requester has no query mechanism, only its timer.

Mechanism

Follow one 512-byte WRITE-data read (Lab SSD, Tag 0x40, IOVA 0x2_0001_0000) through both machines. Each step: who acts, what changes, where, evidence.

  1. Reserve and send. The SSD's read DMA allocates Tag 0x40, reserves 512 bytes of reassembly buffer, starts the timer, records BC_left = 512 and next_LA = 0x00. Evidence: MRd64 on the link, 20000080 010040ff 00000002 00010000.
  2. Decode at the completer. The Root Complex checks the address belongs to system memory and asks the IOMMU to translate the IOVA for Requester ID 0x0100. Evidence: none on the link; an IOMMU fault log if it fails.
  3. Choose the status. Translation succeeds → SC path. If it failed, the Root Complex would answer Cpl with UR or CA (platform-dependent choice) and no data. Implementation-dependent
  4. Fetch and split. The memory system returns cache lines; the completion builder emits CplDs of at most MPS = 256 bytes, cutting only at RCB = 64-byte boundaries. Evidence: CplD rows with BC 512 then 256 (or 512, 448, … for 64-byte pieces).
  5. Route back. Each CplD is ID-routed to bus 01 via the Root Port. Switches compare the Requester ID's bus with their secondary/subordinate ranges. Evidence: completion appears on each link segment.
  6. Accept or reject. The SSD's acceptance machine: Tag 0x40 outstanding? status SC? Length ≤ MPS? Lower Address = next_LA? Byte Count = BC_left? If all yes, copy data, BC_left −= bytes, next_LA advances. Evidence: no error; data in the buffer.
  7. Finish. When a completion's Byte Count equals the bytes it delivers, the request is complete: timer stops, Tag 0x40 is freed. Evidence: the tag may reappear in a later MRd.
  8. Report upward. The DMA engine tells the NVMe front-end the 512 bytes are ready; when all data for the command has arrived and been processed, the controller posts a CQE. On any failure branch, the front-end must fail the command (see the protocol view).

The ladder for "a completion"

Every order gets an answer — boxes, a "no" letter, a "try later" letter — or you stop waiting.

Non-posted requests end with SC completions carrying all bytes, one error completion, or a Completion Timeout; Unexpected Completions are answers to orders already crossed out.

Requester: tag table, timers, pre-reserved buffers, an acceptance machine. Completer: decode, translation, memory fetch, completion builder with status choice and split policy.

PCI Express Base Specification — Completion Rules, Completion Handling Rules, Completion Timeout Mechanism, Configuration Request Retry (Request Retry) Status, Root Control CRS Software Visibility, error classification in Error Signaling and Logging.

Completions are ID-routed in the opposite direction to their request, may interleave across tags, stay in address order within a tag, and must not pass earlier posted writes unless relaxed.

A trace shows each tag's request row and its completion rows; the latency between them; status columns; and gaps — the hardest thing to see.

Order the evidence in time: the first non-SC status, the first missing piece, or the first poisoned CplD is the cause; timeouts and unexpected completions after it are usually consequences.

The PCIe specification does not say what an NVMe controller must do with a failed DMA read beyond PCIe error reporting; the NVMe Base Specification defines status codes and leaves the mapping to the controller. Neither says how long a Root Complex may take to answer, how large its completions are, or which status it uses for translation faults. The time a function may keep answering CRS after reset, and how software must wait, are defined in the reset and configuration-readiness rules — read them there rather than relying on a remembered number.

Never assume: a completion's Completer ID is the addressed device; a UR came from the endpoint; partial data before an error completion is usable; a Vendor ID of 0x0001 is real.

Completion latency has components no analyzer separates: Root Complex queueing, IOMMU translation (an IOTLB miss can add a page walk of several memory accesses), DRAM access, and coherency (snooping CPU caches). An analyzer sees only the sum, request-to-completion at its tap point. Senior engineers compare latency distributions under controlled changes (IOMMU off in a lab, huge pages, local versus remote NUMA buffers) to attribute the parts. Derived

On the SSD side, the reassembly buffer and the acceptance checks are in the PCIe IP or DMA front-end. What happens on failure is a firmware design choice: abort only the affected command, quiesce the queue, or enter a controller fatal state (CSTS.CFS). Good designs fail the single command and keep going.

Configuration completions and resets

After a reset (Conventional reset, Function Level Reset), a function may answer configuration requests with CRS/RRS until it is ready. Without CRS Software Visibility, the Root Complex re-issues the request, and the CPU instruction that started it can stall for a long time. With it enabled, a configuration read of the Vendor ID returns 0x0001 and software polls. NVMe enters this picture during controller and function resets (Chapter 48, Chapter 49). Memory requests to a function that is not ready do not get CRS; they get UR or are not answered usefully, which is why drivers must wait for configuration readiness before touching BAR0.

Ordering of completions

Completions for different tags may pass each other; completions of the same tag may not. A completion must not pass an earlier posted write in the same direction unless relaxed (its RO bit, copied from the request, or IDO). That is why a CPU's read of CSTS returns after all writes the SSD issued earlier have gone ahead of it — see Module 14.

Beginner lab — who answers, and how?

Objective. Predict the completion (or its absence) for eight situations. Prerequisites. Chapter 12. Setup. The example system.

Expected reasoning. Request type first (posted or not), then completer state.

Solution

(a) CplD, SC, 0x0100. (b) Cpl, UR, 0x0100; CPU sees all ones. (c) If the function is not ready: Cpl CRS from 0x0100, re-issued by the Root Complex until success — software sees a slow read. Intermediate lab — an acceptance machine under fault injection

Objective. Implement a requester's acceptance machine and see which error each injected fault produces. Prerequisites. Chapter 52 arithmetic. Setup. Save as cpl_accept.py.

#!/usr/bin/env python3
"""Requester-side completion acceptance machine with fault injection.
Standard library only. Teaching model: real devices differ in which checks they do."""
MPS, RCB = 256, 64

class Requester:
    def __init__(self):
        self.out = {}          # tag -> dict(addr, bc_left, next_la)
        self.log = []

    def issue(self, tag, addr, nbytes):
        assert tag not in self.out, "tag already outstanding"
        self.out[tag] = dict(addr=addr, bc_left=nbytes, next=addr)

    def timeout(self, tag):
        if tag in self.out:
            self.log.append(f"Completion Timeout tag {tag:#x}")
            del self.out[tag]

    def cpl(self, tag, status="SC", length_dw=0, bc=0, la=0, ep=0):
        e = self.out.get(tag)
        if e is None:
            return self.log.append(f"Unexpected Completion tag {tag:#x}")
        if status != "SC":
            self.log.append(f"tag {tag:#x} failed with {status}")
            del self.out[tag]
            return
        if 4 * length_dw > MPS:
            return self.log.append(f"Malformed TLP (payload > MPS) tag {tag:#x}")
        if ep:
            self.log.append(f"Poisoned TLP Received tag {tag:#x}")
            del self.out[tag]
            return
        if bc != e["bc_left"] or la != e["next"] & 0x7F:
            return self.log.append(f"inconsistent BC/LA tag {tag:#x} "
                                   f"(got BC={bc} LA={la:#x}, want BC={e['bc_left']} "
                                   f"LA={e['next'] & 0x7F:#x})")
        got = min(4 * length_dw, e["bc_left"])
        e["bc_left"] -= got
        e["next"] += got
        if e["bc_left"] == 0:
            self.log.append(f"tag {tag:#x} complete")
            del self.out[tag]

def run(name, script):
    r = Requester()
    for step in script:
        getattr(r, step[0])(*step[1:])
    print(f"--- {name}")
    for line in r.log:
        print("   ", line)
    if r.out:
        print("    still outstanding:", ", ".join(hex(t) for t in r.out))

A = 0x2_0001_0000
run("normal", [("issue", 0x40, A, 512), ("cpl", 0x40, "SC", 64, 512, 0x00),
               ("cpl", 0x40, "SC", 64, 256, 0x00)])
run("error mid-request", [("issue", 0x40, A, 512), ("cpl", 0x40, "SC", 64, 512, 0x00),
                          ("cpl", 0x40, "UR")])
run("late after timeout", [("issue", 0x40, A, 512), ("timeout", 0x40),
                           ("cpl", 0x40, "SC", 64, 512, 0x00)])
run("wrong byte count", [("issue", 0x40, A, 512), ("cpl", 0x40, "SC", 64, 512, 0x00),
                         ("cpl", 0x40, "SC", 64, 192, 0x00), ("timeout", 0x40)])
run("oversized", [("issue", 0x40, A, 512), ("cpl", 0x40, "SC", 128, 512, 0x00),
                  ("timeout", 0x40)])
run("poisoned", [("issue", 0x40, A, 512), ("cpl", 0x40, "SC", 64, 512, 0x00, 1)])

Procedure. Run it. For each scenario, write down which error is the cause and which is a consequence. Then add a scenario: two completions for the same tag arrive out of address order.

Questions. (1) Why does "wrong byte count" end in a timeout? (2) Why is "late after timeout" reported as Unexpected Completion and not as a second timeout? (3) What should happen to the 256 bytes already received in "error mid-request"?

Solution

(1) The inconsistent completion is rejected, so the request never reaches BC_left = 0 and the timer fires: the real first event is the inconsistency, the timeout is a consequence. (2) The tag was freed at timeout; the late completion matches nothing. (3) Discarded: a non-SC completion terminates the whole request, so the controller must not use partial data for the command. Out-of-order pieces of one tag fail the LA check here; a real device would report Malformed TLP or Unexpected Completion depending on design.

Extension. Add a duplicate-completion scenario and decide whether your machine should report it as unexpected (after completion) or inconsistent (mid-request).

Advanced lab — completion latency from a trace

Objective. Compute per-tag latency (to first and to last completion) and connect it to throughput. Prerequisites. Chapter 12 Little's Law. Setup. The synthetic rows below (time ns, direction, type, tag, BC, bytes).

0     up   MRd  0x40 512
10    up   MRd  0x41 512
20    up   MRd  0x42 512
880   down CplD 0x40 512 256
900   down CplD 0x41 512 256
940   down CplD 0x40 256 256
990   down CplD 0x41 256 256
3410  down CplD 0x42 512 256
3460  down CplD 0x42 256 256

Procedure. Parse it (a few lines of Python or by hand). Compute latency to first and last completion per tag. Then compute how many outstanding 512-byte reads would be needed to sustain 6.8 GB/s if every read behaved like Tag 0x42.

Solution

Tag 0x40: 880 / 940 ns. 0x41: 890 / 980 ns. 0x42: 3,390 / 3,440 ns. Using last-completion latency for 0x42: 6.8 GB/s × 3.44 µs ≈ 23.4 KB ⇒ ≈ 46 reads of 512 B outstanding, versus ≈ 13 at 0.98 µs. The tail, not the average, sets the requirement when the slow reads cluster (as at page boundaries).

Extension. Generate a histogram for 10,000 synthetic reads with 5% at 3.4 µs and compute throughput for 16 and 48 outstanding reads.

Senior forensic lab — the reset that produced unexpected completions

Objective. Order evidence across layers to find the first abnormal event. Prerequisites. Chapter 49, Chapter 46.

Setup (synthetic evidence, times in ms from an NVMe I/O timeout):

  • t = 0: NVMe driver: I/O timeout on QID 3, aborting; then "resetting controller".
  • t = 2: driver issues a Function Level Reset (FLR) to 01:00.0.
  • t = 2.3: Lab SSD AER: Unexpected Completion; Header Log 4a000040 00090100 01005a40 00000000.
  • t = 104: configuration read of Vendor ID returns 0x0001 twice, then the real Vendor ID.
  • Earlier, t = −30,000 (30 s before): Lab SSD AER: Completion Timeout (no header logged).

Questions. (1) Decode the Header Log. (2) Is the Unexpected Completion a device bug? (3) What do the 0x0001 reads tell you? (4) What was the first abnormal event and what would you investigate?

Solution

(1) CplD, Length 64 DW, Completer 0x0009, SC, Byte Count 256, Requester 0x0100, Tag 0x5A, Lower Address 0x40 — the second half of a 512-byte read. (2) No: the FLR discarded the SSD's outstanding requests; a completion still in flight from the Root Complex arrived afterwards and matched nothing. (3) CRS Software Visibility is enabled and the function was initialising after FLR; software polled correctly. (4) The first abnormal event is the Completion Timeout 30 s earlier: a DMA read never completed, the controller could not finish the command, and the NVMe driver's own timeout (≈ 30 s) fired later. Investigate the host side of that read: IOMMU faults, Root Port errors, memory errors around t = −30 s, and capture with a trigger on the SSD's ERR_NONFATAL message. Everything after t = 0 is recovery behaving correctly.

Extension. Explain why a shorter Completion Timeout would not shorten the NVMe-level outage unless the controller fails the command immediately on timeout.

Debugging

Pattern 1 — WRITE latency tail with no errors

Symptomp99.9 WRITE latency high; READs fine; no AER errors.
Possible causesSlow completions for some DMA reads (IOTLB misses, remote NUMA memory, memory contention); too few outstanding reads.
EvidencePer-tag completion latency distribution; buffer page sizes and NUMA placement.
First checkIs the latency histogram bimodal, and do slow tags cluster at page boundaries?
Second checkOutstanding-read ceiling of the device versus Little's Law at tail latency.
Disambiguating experimentHuge-page buffers or IOMMU pass-through in a lab; NUMA-local buffers.
Likely conclusionTranslation or memory latency on the completer side.
ConfidenceMedium; high if the tail collapses in the experiment.

Pattern 2 — NVMe Data Transfer Errors on specific buffers

SymptomSome commands fail with a data-transfer-class status; others fine.
Possible causesUR/CA completions from IOMMU-blocked addresses; poisoned completions from memory errors; device bug.
EvidenceIOMMU fault logs, memory-error (EDAC/machine-check) logs, SSD AER bits.
First checkCorrelate IOMMU faults by time and address with the failed commands' PRPs/SGLs.
Second checkPoisoned TLP Received at the SSD plus host memory errors?
Disambiguating experimentReproduce with buffers kept mapped longer; with memory error injection disabled or on different DIMMs.
Likely conclusionHost buffer lifetime bug (unmap before completion) or host memory error.
ConfidenceHigh when addresses match.

Pattern 3 — Unexpected Completions after resets

SymptomUnxCmplt at the SSD right after FLR or controller reset.
Possible causesIn-flight completions for discarded requests (benign consequence); bus renumbering; device tag-table bug.
EvidenceHeader Log tag versus requests issued before the reset; timing relative to reset.
First checkDid the Unexpected Completion arrive within a few microseconds of the reset?
Second checkWas there an earlier timeout that triggered the reset (the real cause)?
Disambiguating experimentQuiesce I/O before reset in a lab; the errors should disappear.
Likely conclusionConsequence of reset; look earlier for the cause.
ConfidenceHigh.

Pattern 4 — CPU stalls during device recovery

SymptomLong CPU stalls or watchdog warnings while an NVMe device resets; sometimes machine checks.
Possible causesMMIO reads to a function that is not answering (Root Port waits its full timeout); configuration reads retried on CRS without software visibility.
EvidenceRoot Port Completion Timeout setting; RootCtl CRSVisible; timing of stalls versus reset.
First checkRoot Port DevCtl2 Completion Timeout range.
Second checkIs CRS Software Visibility enabled?
Disambiguating experimentLab comparison with CRS SV enabled and the driver waiting for readiness before MMIO.
Likely conclusionRecovery path touching MMIO too early, or long retry without visibility.
ConfidenceMedium.

Pattern 5 — "Missing completion" that is not missing

SymptomCapture shows a request without all its completions, but no timeout is reported.
Possible causesAnalyzer dropped TLPs; filter excluded them; capture on the wrong side of a switch.
EvidenceSequence numbers and Acks around the gap; analyzer buffer statistics.
First checkAre sequence numbers contiguous on that link direction?
Second checkDoes an Ack cover the missing sequence number?
Disambiguating experimentRe-capture with filters off and a deeper buffer.
Likely conclusionInstrument artefact.
ConfidenceHigh if an Ack covers the gap.

Interview

Beginner

  1. Which requests get a Cpl without data when successful?

    Model answer

    Configuration writes and I/O writes.

  2. How is a completion routed?

    Model answer

    By ID: the Requester ID copied from the request.

  3. Name the four defined completion statuses.

    Model answer

    SC, UR, CRS (RRS), CA.

  4. What ends a non-posted request?

    Model answer

    All completions with SC, one error completion, or a Completion Timeout.

  5. Does an MSI-X write get a completion?

    Model answer

    No; it is a posted memory write.

Intermediate

  1. When does a switch generate a completion itself?

    Model answer

    When a non-posted request it receives matches no downstream window or target: it answers UR with its own Completer ID.

  2. What is CRS Software Visibility?

    Model answer

    A Root Port option: when a Vendor ID configuration read gets CRS, software receives 0x0001 instead of the Root Complex silently re-issuing; software can poll without stalling.

  3. Why measure latency to the last completion?

    Model answer

    The tag and buffer are held until the last piece; outstanding-request sizing depends on that time.

  4. What happens to partial data before an error completion?

    Model answer

    The request has failed; the data must not be used as a successful result.

  5. Why do endpoints usually advertise infinite completion credits?

    Model answer

    They reserve space before issuing each read, so completions can always be accepted and never block the path.

Advanced

  1. Describe a requester's acceptance checks.

    Model answer

    Match Transaction ID; check status; check size ≤ MPS; check Byte Count and Lower Address continuity; place data; detect the final piece; free tag and stop timer.

  2. UR or CA for an IOMMU-blocked read — what decides?

    Model answer

    The Root Complex implementation; both mean failure to the requester. Confirm with the platform's documentation and IOMMU logs.

  3. Explain how you prove a gap in a capture is an instrument artefact.

    Model answer

    Sequence numbers on that direction skip, and the receiver's Ack covers the skipped number; a receiver never acknowledges past a gap.

  4. Why are memory requests never answered with CRS?

    Model answer

    CRS is defined for configuration requests (readiness after reset); memory semantics have no retry status, so readiness must be established before BAR access.

  5. How does a poisoned completion differ from an error completion?

    Model answer

    Poisoned: status SC with data marked bad (EP); the receiver reports Poisoned TLP Received. Error completion: no data, status UR/CA.

Senior

  1. How should an NVMe controller react to a UR completion on a data read?

    Model answer

    Fail only the affected command with an appropriate status, release its resources, keep other queues running, and report the PCIe event per its error enables; avoid a controller-fatal state for a host-side mapping problem.

  2. Design completion-path validation for a new Root Complex.

    Model answer

    Every split policy at every alignment and RCB; status generation for each fault (translation, unmapped, poisoned memory); latency under translation misses and contention; behaviour with many requesters; late completions after requester reset; CRS handling with and without visibility.

  3. A customer sees Completion Timeouts only under heavy load. Your hypothesis tree?

    Model answer

    Completer latency exceeding a short timeout range; lost completions in a switch under congestion; replay storms on a marginal link delaying TLPs; a Root Complex starving one requester. Check timeout range, link error counters, per-tag latency, and switch counters.

  4. Why is "Unexpected Completion" weak evidence on its own?

    Model answer

    It is commonly a consequence of the receiver's own earlier timeout or reset; the cause lies earlier in time.

  5. Who owns the decision of the Completion Timeout value for NVMe DMA?

    Model answer

    Platform firmware and OS policy, balancing detection speed against the platform's worst legitimate completer latency (virtualization, error recovery), and coordinated with NVMe command timeouts.

Quiz

  1. Completion DW1 = 0x01002000. What is the status?

    • SC
    • UR
    • CRS
    • CA
    Answer and reasoning

    Low 16 bits 0x2000 = 0010 0000 0000 0000b; bits 15:13 = 001b = UR.

  2. A Vendor ID read returns 0x0001. Most likely?

    • A real vendor
    • A UR completion
    • CRS with Software Visibility enabled
    • A Completion Timeout
    Answer and reasoning

    CRS Software Visibility returns 0x0001 for a Vendor ID read that received CRS.

  3. Which component typically answers UR for an IOMMU-blocked DMA read?

    • The Root Complex
    • The SSD
    • A retimer
    Answer and reasoning

    The completer for host memory is the Root Complex; it decides the status (UR or CA, platform-dependent).

  4. A request receives an SC CplD with BC 512, then a Cpl UR. What is the outcome?

    • 256 bytes usable
    • The whole request failed
    • A timeout will follow
    Answer and reasoning

    A non-SC completion terminates the request as failed.

  5. Which statuses can a memory read receive?

    • All four
    • SC and CRS
    • SC, UR and CA
    Answer and reasoning

    CRS/RRS applies to configuration requests.

  6. A gap in a capture's completion stream is covered by a later Ack. What does that prove?

    • The TLP crossed the link; the analyzer missed it
    • The completion was lost
    • The receiver ignored an error
    Answer and reasoning

    A receiver acknowledges only in-order, intact TLPs.

  7. Why can an Unexpected Completion appear right after an FLR?

    Model answer

    FLR discards outstanding requests; completions already in flight arrive and match nothing.

  8. Why does a 3.4 µs completion tail cut WRITE throughput but not READ throughput?

    Model answer

    WRITE data is fetched with non-posted reads whose latency must be covered by outstanding requests; READ data is pushed with posted writes.

  9. Name two reasons a CPU MMIO read can return all ones.

    Model answer

    A UR/CA completion (e.g. Memory Space Enable clear, D3hot) or a Completion Timeout at the Root Port (device gone, link down) — the Root Complex synthesises the value.

Teach-back

  1. To a child: why the toy shop sometimes says "ask again in a minute".

    Model explanation

    "The shop just opened and is still turning on the lights. It's not saying no — it's saying not yet. So you ask again a bit later, and then it can answer."

  2. To a junior engineer: the three endings of a non-posted request and what each looks like in a trace.

    Model explanation

    "Success: CplDs with the same Requester ID and Tag until Byte Count equals the bytes carried. Error: a Cpl with UR or CA and no data — done immediately. Timeout: nothing; the requester's timer fires, it logs Completion Timeout and sends an error message. A late answer after that shows up as an Unexpected Completion."

  3. To a senior engineer: why NVMe failures caused by completions usually start on the host side.

    Model explanation

    "The SSD's fast-path non-posted requests target host memory, so the completer is the Root Complex, its IOMMU and the memory system. UR/CA come from translation faults or buffer lifetime bugs, poison from memory errors, latency tails from page walks and NUMA. The SSD is the detector and should fail the command cleanly; the cause is upstream until evidence says otherwise."
