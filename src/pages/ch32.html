This chapter follows one READ from the moment an application calls read() to the moment it wakes up with data: through the filesystem, the block layer, the NVMe driver, the 64-byte command, the submission queue, the doorbell, the controller, the flash, the DMA writes into host memory, the completion queue entry and the interrupt. At every layer you will see who acts, what changes, and what evidence it leaves — including the exact PCIe TLPs and what they look like when the read fails.

Why this chapter exists

Read is the simplest NVMe command that moves data, and the one that appears most often in every trace you will ever analyse. It is also the best vehicle for understanding the whole stack, because a read crosses every layer twice: down as a request and back up as data plus a completion. Once you can narrate a read end to end — and point to the evidence for each step — you have a template for every other command. WRITE reverses the data direction; The Most Important Chapter puts both on one timeline.

The READ is also where the three technologies of this course meet most visibly. The NVM Command Set defines the Read command's fields; the NVMe Base Specification defines the queues, the CQE and the status; the NVMe over PCIe Transport Specification maps it onto memory transactions; and PCI Express defines the TLPs that physically carry the doorbell, the command, the data, the completion and the interrupt. Keeping those four layers apart in your head, while seeing how they connect, is the skill this chapter trains.

The story

You are in class and want page 100 of a book in the giant library. You tell the teacher. The teacher writes a request slip — "please bring pages 100 to 107 of section 1 to table 7" — puts it in the request box, and rings the little bell. The librarian hears the bell, walks over, reads the slip, and goes into the stacks. Finding the pages takes the longest part of the whole job. Then she carries them straight to table 7 and puts them down — she doesn't hand them to the teacher. Then she drops an answer card in the answer box saying "slip 7 done, all fine", and taps the teacher on the shoulder. The teacher checks the answer box, sees the card, and tells you your pages are on table 7.

An adult version: ordering a part from a warehouse with direct delivery. Your purchasing department (driver) fills in a standard order form (SQE) in a shared tray (SQ) and texts the warehouse "new order in the tray" (doorbell). The warehouse collects the form (SQE fetch), pulls the part from deep storage (NAND read — slow), drives it directly to your loading dock bay 7 (DMA to the buffer) in several van-loads (TLPs), then puts a delivery note in your inbox tray (CQE) and phones reception (interrupt). Reception checks the tray and tells the engineer who asked.

What it hides. The "walk" to the request box is a PCIe Memory Read, and the "carry" is many PCIe Memory Writes, each limited in size; the bell is a 4-byte write to a register, not a message containing the request. The pages are not taken from a single shelf: one 4 KiB read may assemble data from a NAND page shared with other data, after error correction. Where it misleads. The librarian does not walk back for each slip — the controller can have hundreds of reads in flight and complete them in any order; the teacher may never be "tapped" because interrupts can be coalesced or replaced by polling; and "all fine" in the answer box is only trustworthy because PCIe ordering guarantees the pages arrived on the table first.

Beginner explanation

When a program reads a file, the operating system works out which blocks of the SSD hold that part of the file. If the data is not already in memory, the NVMe driver builds a Read command: "namespace 1, starting at block number X, this many blocks, put the data in these memory pages". It places the command in a submission queue in memory and writes the queue's new tail index to a doorbell register on the SSD.

The SSD's controller then reads the command from memory, looks up where those blocks physically live in its flash chips, reads them (this is the slow part — tens of microseconds), corrects any bit errors, and writes the data directly into the memory pages the driver named. That direct writing by the device is Direct Memory Access (DMA). Finally the controller writes a 16-byte completion entry into the completion queue and sends an interrupt. The driver sees the completion, tells the operating system the data is ready, and the program continues.

Engineering explanation

We follow a 4 KiB read of file data on the reference lab system: namespace 1 with 512-byte LBAs, I/O queue pair 1 (SQ1/CQ1, 1024 entries), Gen4 x4 link, MPS 256 bytes, IOMMU on. Every number is a synthetic example for teaching.

Layer 1 — the application

The program calls read(fd, buf, 4096) or submits an io_uring read. With buffered I/O, the kernel first looks in the page cache; a hit never reaches NVMe. With O_DIRECT, the page cache is bypassed and the user buffer itself becomes the DMA target (it must be suitably aligned, usually to the logical block size). The application's thread blocks (synchronous read) or continues (asynchronous).

Evidence: strace shows the system call; /proc/<pid>/io counts bytes; the page-cache hit rate is visible with tools such as cachestat if installed.

Layer 2 — the filesystem

The filesystem (ext4, XFS, …) maps the file offset to a logical block on the block device using its extent tree or block map, possibly reading metadata first (which is itself more reads). It then issues a bio describing "read N sectors starting at sector S into these memory pages". Linux counts block-device sectors in 512-byte units regardless of the device's LBA size; the NVMe driver converts.

Evidence: filefrag -v shows a file's extents; blktrace shows the bio as it enters the block layer.

Layer 3 — the block layer

The multi-queue block layer (blk-mq) may merge adjacent bios, splits requests that exceed the device's limits (derived from MDTS and segment limits), applies an I/O scheduler if one is configured (often "none" for NVMe), and allocates a tag from the hardware queue mapped to the submitting CPU. That hardware queue corresponds to one NVMe I/O SQ. The tag becomes the basis of the NVMe Command Identifier.

Evidence: /sys/block/nvme0n1/mq/ lists hardware queues and their CPU mappings; blktrace/blkparse show queue, merge, dispatch (D) and complete (C) events.

Layer 4 — the NVMe driver

The driver turns the request into an NVMe command. It:

  1. sets OPC = 02h, CID from the tag, NSID of the namespace;
  2. converts the start sector to an SLBA (sector × 512 / LBA size) and the length to NLB − 1;
  3. maps the data pages for DMA: with the IOMMU on, it obtains I/O virtual addresses (IOVAs) for the pages, so the device sees addresses such as 0x2_0000_0000 that the IOMMU translates to physical pages;
  4. builds PRP1/PRP2 (and a PRP list if the buffer spans more than two pages) or an SGL;
  5. copies the 64-byte SQE into the SQ slot at the current tail and advances the tail;
  6. after a write barrier, writes the new tail to the SQ1 tail doorbell (possibly once for a batch of commands).

NLB is 0's based. NLB = 7 reads 8 blocks: 8 × 512 = 4096 bytes on namespace 1, but 8 × 4096 = 32 KiB on namespace 2. Always multiply by the LBA size of the format in use.

Layer 6 — the submission queue

SQ1 is a ring of 1024 × 64-byte entries at IOVA 0x1_2340_0000. The tail was 5, so the SQE is written at 0x1_2340_0000 + 5 × 64 = 0x1_2340_0140 and the tail becomes 6. Until the doorbell is written, the controller does not know the entry exists.

Layer 7 — the doorbell

The driver writes 6 to SQ1's tail doorbell at BAR0 + 0x1008 = 0xFE60_1008. The CPU's uncached store becomes a PCIe Memory Write TLP from the root complex with a 1-Dword payload. It is posted: the CPU does not wait for any acknowledgement at the NVMe level. See Doorbells.

Layer 8 — the controller

The doorbell updates the controller's copy of SQ1's tail. Its fetch engine sees head (5) ≠ tail (6) and issues a Memory Read for 64 bytes at 0x1_2340_0140. The root complex answers with a Completion with Data containing the SQE. The controller increments its internal SQ1 head to 6, parses CDW0 (Read), checks NSID 1 is active, checks SLBA + NLB + 1 ≤ NSZE and the transfer ≤ MDTS, and hands the command to its read path. Its flash translation layer translates LBAs 0x10_0000–0x10_0007 to a physical location: for example one 4 KiB slice of a 16 KiB NAND page on channel 3, die 1, plane 0. Implementation-dependent

Layer 9 — the flash

The NAND back-end issues a page read to the die. The die senses the cells into its page register — the array read time (often written tR), tens of microseconds for TLC NAND — then the data is clocked across the NAND interface into the controller. An LDPC or BCH error-correction engine corrects bit errors. If correction fails, the controller retries with different read voltages ("read retry"), soft-decision decoding, or RAID-like parity across dies; each step adds latency, potentially milliseconds. If everything fails, the read ends with an Unrecovered Read Error. Limited Retry asks the controller to stop early. If the LBAs were never written or were deallocated, there may be no NAND access at all.

Layer 10 — DMA

The controller's DMA engine writes the 4096 bytes to PRP1 = 0x2_0000_0000. A PCIe Memory Write may carry at most Max Payload Size (256 bytes here) and must not cross a 4 KiB address boundary, so the transfer becomes 16 MWr TLPs of 256 bytes (Length = 64 Dwords) at 0x2_0000_0000, 0x2_0000_0100, … 0x2_0000_0F00. Each carries the controller's Requester ID 0x0100. They are posted: no completion comes back.

If the buffer had spanned more than two pages, PRP2 would point to a PRP list and the controller would first read that list (MRd/CplD) to learn the remaining page addresses.

Layer 11 — host memory

The root complex receives each MWr, the IOMMU translates its IOVA to a physical address (using the mapping the driver created), and the data is written into memory — on many platforms snooping or updating CPU caches so the CPU sees fresh data. If the IOVA is not mapped, the IOMMU blocks the write and logs a fault; because MWr is posted, the controller is not told, which is one of the nastiest failure modes in this chapter.

Layer 12 — the completion queue

After the last data TLP, the controller writes the CQE — 16 bytes as one MWr — at CQ1 base + slot × 16. With the CQ's tail at slot 3, that is 0x1_2341_0030: DW0 = 0, DW1 = 0, DW2 = SQID 1 / SQHD 6 (0x0001_0006), DW3 = status 0 / P 1 / CID 7 (0x0001_0007). Because PCIe does not let a posted write pass an earlier posted write on the same path (without relaxed ordering), the CQE cannot become visible before the data.

Layer 13 — the interrupt

CQ1 was created with interrupts enabled on vector 1. Unless interrupt coalescing delays it, the controller sends the MSI-X message for vector 1: an MWr of a 32-bit data value to the address programmed in the MSI-X table entry (on x86, in the 0xFEE0_0000 range). The interrupt controller delivers it to a CPU.

Back up the stack

  1. The interrupt handler reads CQ1 at its head, sees P = 1 matching the expected phase, and reads the entry (after a barrier).
  2. It updates SQ1's head from SQHD (6), looks up CID 7 on SQ1 and finds the request.
  3. Status 0: it ends the request successfully, unmaps the DMA buffer (IOMMU mapping torn down or reused), and frees the tag.
  4. It advances the CQ head and writes CQ1's head doorbell (BAR0 + 0x100C), telling the controller slot 3 can be reused.
  5. The block layer completes the bio; the filesystem marks the page uptodate; the waiting thread is woken; read() returns 4096.

Polling replaces steps 13 and 1: with io_uring polled I/O, the CQ is created without interrupts and a CPU spins on the phase bit. The trace then shows no MSI-X MWr at all — not a bug.

For a slow or failed read, find which arrow is late or missing: no SQE fetch (doorbell/controller), no data (media or rejection), data but no CQE (controller hang), CQE but no interrupt (MSI-X/coalescing), interrupt but no progress (host).

The sixteen questions, answered for the READ

1. What is it?
The NVM Command Set I/O command (opcode 02h) that transfers logical blocks from a namespace to host memory.
2. Why was it created?
It is the fundamental data-retrieval operation of a block device.
3. What problem does it solve?
Moving data from non-volatile media to memory with minimal host CPU involvement (DMA) and high parallelism (many queues, many outstanding reads).
4. What existed before it?
SCSI READ(10/16) through a SAS HBA; ATA READ FPDMA QUEUED (NCQ) through AHCI with a single 32-deep queue.
5. Why is the current design better?
One 64-byte command fetched directly by the device, no HBA translation, per-CPU queues, 64-bit LBAs, and one interrupt (or none, with polling) per completion batch.
6. Who creates it?
The NVMe driver, on behalf of the block layer.
7. Who consumes it?
The controller's front-end and read path.
8. Where does it live?
SQE in SQ1 (host memory); data in the PRP-described buffer; completion in CQ1.
9. What memory/registers are involved?
SQ1/CQ1 rings, SQ1 tail and CQ1 head doorbells, data buffer and PRP list, IOMMU tables, MSI-X table entry for vector 1.
10. What happens before it?
Page-cache miss, filesystem mapping, block-layer splitting and tag allocation, DMA mapping.
11. What happens after it?
Completion handling, DMA unmap, request completion, page marked uptodate, task woken; possibly read-ahead of the next blocks.
12. What happens if it is wrong?
Wrong data in memory, overwrite of neighbouring memory, LBA Out of Range, IOMMU faults, PI errors, timeouts.
13. What does the protocol analyzer show?
The TLP sequence above, with timing gaps showing where the time went.
14. What does Linux show?
nvme tracepoints (setup and complete with SLBA/length/status), blktrace events, iostat latency and throughput, kernel log messages on errors and timeouts.
15. What would a validation engineer test?
All sizes up to MDTS, unaligned PRP offsets, PRP lists across page boundaries, boundary LBAs, FUA/LR, PI types, deallocated LBAs, media errors (via Write Uncorrectable), interrupt coalescing, queue wrap, many concurrent reads.
16. What would a senior engineer suspect when it fails?
Depends on which arrow is missing: host mapping (IOMMU) for silent data loss; media for Unrecovered Read Error; controller firmware for missing CQEs; interrupt routing for "completion written but not seen".

The single largest component of a 4 KiB read's latency on a TLC SSD is normally the NAND array read, not anything on PCIe. That is why a protocol trace of a healthy read has a long quiet gap between the SQE's CplD and the first data MWr. When the gap grows from tens of microseconds to milliseconds, the controller is doing error recovery — the trace shows the symptom; the controller's telemetry or SMART media-error counters may show the cause. Implementation-dependent (NAND type, controller design, caching).

Specification view

Four documents define a read over PCIe:

  • NVM Express NVM Command Set Specification, Revision 1.3 — Read command: CDW10–15 fields, FUA, LR, PRINFO, DSM, PI behaviour, command-specific status.
  • NVM Express Base Specification, Revision 2.4: queues, SQE/CQE, Status Field, generic and media status codes, CID rules, interrupt and arbitration models.
  • NVM Express NVMe over PCIe Transport Specification, Revision 1.4: doorbell registers, PRP rules for the PCIe transport, MSI-X usage, queue memory requirements.
  • PCI Express Base Specification, Revision 6.x/7.0 (PCI-SIG members' document): Memory Read/Write requests, completions, Max Payload Size and Max Read Request Size, the rule that requests do not cross a 4 KB address boundary, ordering rules, MSI-X capability.

Read opcode 02h; SLBA in CDW10–11; NLB 0's based in CDW12 15:0; PRINFO 29:26, FUA 30, LR 31; DSM hints in CDW13 7:0; PRP1/PRP2 semantics (PRP2 is a second page or a PRP list pointer); CQE fields and status values used in this chapter (Unrecovered Read Error = SCT 2h / SC 81h; LBA Out of Range = SCT 0h / SC 80h). MWr TLPs are posted and MRd are non-posted; payloads are bounded by MPS; requests may not cross a 4 KB boundary.

The TLP counts in this chapter (e.g. 16 MWr for 4 KiB at MPS 256) and the wire-time estimates are derived from MPS, the 4 KB rule and link parameters. That the data is visible to the host before the CQE is derived from PCIe ordering rules for posted writes in the same direction, assuming no relaxed ordering on the CQE path.

The size of data TLPs a controller emits (it may use payloads smaller than MPS), whether SQEs are fetched singly or in bursts, the order of data TLPs within a command, how FUA on a read interacts with the cache, read-retry strategies and timeouts, interrupt coalescing and the presence of a PRP-list prefetch are all implementation-dependent.

Extended protection information formats (2.0 and later) change how CDW2–3 and CDW14–15 are used for PI; storage tag checking adds CDW12 controls. The NVM Command Set's revision 1.3 accompanies Base 2.4; older readers will find the Read command in "NVM Express Revision 1.4" under I/O commands.

The specifications do not define: how long a read may take; whether reads to the same LBA from different queues return in submission order; whether read data TLPs arrive in address order; what the data buffer contains if a read fails (do not use it); how a host should choose between interrupts and polling. Check in the NVM Command Set specification what a read of a deallocated or never-written block returns for your namespace.

Never use buffer contents from a read whose CQE status is non-zero — partial data may have been written. Never assume data TLPs arrive in address order. Never assume a successful CQE proves the data reached memory if IOMMU faults were logged at the same time.

Code / pseudocode

The simulation below prints the TLP sequence of a READ on the reference lab system: it computes PRP1/PRP2 and a PRP list when needed, splits data into MWr TLPs at MPS and 4 KiB boundaries, and builds the CQE (success or Unrecovered Read Error). It models order, not time.

#!/usr/bin/env python3
"""Simulate the PCIe TLPs of one NVMe READ on the course's reference lab system.
Prints a synthetic trace: doorbell, SQE fetch, PRP-list fetch (if needed),
data Memory Writes split at Max Payload Size and 4 KiB boundaries, CQE,
MSI-X. Standard library only. Timing is NOT modelled; order is."""
PAGE, MPS = 4096, 256
BAR0, SQ1, CQ1 = 0xFE60_0000, 0x1_2340_0000, 0x1_2341_0000
PRP_LIST = 0x1_5000_0000
REQ_DEV = "0x0100"

def prps(pages, first_offset, length):
    """Return (prp1, prp2, list_entries) for a buffer made of 4 KiB pages."""
    span = first_offset + length
    npages = (span + PAGE - 1) // PAGE
    prp1 = pages[0] + first_offset
    if npages == 1:
        return prp1, 0, []
    if npages == 2:
        return prp1, pages[1], []
    return prp1, PRP_LIST, pages[1:npages]

def data_chunks(pages, first_offset, length):
    """Split the transfer into MWr payloads: <= MPS, never crossing 4 KiB."""
    out, page_i, off = [], 0, first_offset
    while length:
        room = min(MPS, PAGE - off, length)
        out.append((pages[page_i] + off, room))
        length -= room
        off += room
        if off == PAGE:
            page_i, off = page_i + 1, 0
    return out

def read_trace(slot, cid, slba, nlb_field, lba_size, pages, first_offset=0,
               cq_slot=0, phase=1, fail=False):
    length = (nlb_field + 1) * lba_size
    p1, p2, plist = prps(pages, first_offset, length)
    rows = [("Host->Dev", "MWr32", f"Addr=0x{BAR0 + 0x1008:X} Data=0x{slot + 1:08X}",
             "SQ1 tail doorbell")]
    rows.append(("Dev->Host", "MRd64", f"Req={REQ_DEV} Addr=0x{SQ1 + slot * 64:X} Len=16",
                 f"fetch SQE slot {slot}"))
    rows.append(("Host->Dev", "CplD", "ByteCnt=64",
                 f"SQE: OPC=02h CID=0x{cid:04X} SLBA={slba} NLB={nlb_field} "
                 f"PRP1=0x{p1:X} PRP2=0x{p2:X}"))
    if plist and not fail:
        rows.append(("Dev->Host", "MRd64",
                     f"Req={REQ_DEV} Addr=0x{p2:X} Len={2 * len(plist)}",
                     f"fetch PRP list ({len(plist)} entries)"))
        rows.append(("Host->Dev", "CplD", f"ByteCnt={8 * len(plist)}",
                     "PRP entries: " + ", ".join(f"0x{a:X}" for a in plist)))
    if not fail:
        for addr, n in data_chunks(pages, first_offset, length):
            rows.append(("Dev->Host", "MWr64", f"Req={REQ_DEV} Addr=0x{addr:X} Len={n // 4}",
                         f"{n} bytes of read data"))
    status = (1 << 15) | (2 << 9) | (0x81 << 1) if fail else 0   # DNR, SCT 2h, SC 81h
    dw3 = ((status | phase) << 16) | cid
    rows.append(("Dev->Host", "MWr64",
                 f"Req={REQ_DEV} Addr=0x{CQ1 + cq_slot * 16:X} Len=4 "
                 f"Data=00000000 00000000 {(1 << 16) | (slot + 1):08X} {dw3:08X}",
                 "CQE " + ("Unrecovered Read Error, DNR" if fail else "success")))
    rows.append(("Dev->Host", "MWr32", "Addr=0xFEE01000 Data=0x00000041", "MSI-X vector 1"))
    rows.append(("Host->Dev", "MWr32", f"Addr=0x{BAR0 + 0x100C:X} Data=0x{cq_slot + 1:08X}",
                 "CQ1 head doorbell"))
    for i, r in enumerate(rows, 1):
        print(f"{i:3d} {r[0]:9s} {r[1]:6s} {r[2]:<62s} {r[3]}")
    return rows

if __name__ == "__main__":

Worked example

Synthetic example for teaching. An application reads 8 KiB with O_DIRECT into a user buffer whose IOVA starts at 0x2_0000_0200 (offset 0x200 in its page; the next pages are 0x2_0000_1000 and 0x2_0000_2000). The file's data is at byte offset 0x3_0000_0000 on namespace 1 (512-byte LBAs).

  1. SLBA = 0x3_0000_0000 / 512 = 0x180_0000 (25,165,824). CDW10 = 0x0180_0000, CDW11 = 0.
  2. NLB = 8192 / 512 − 1 = 15. CDW12 = 0x0000_000F.
  3. Pages touched: bytes 0x200–0x21FF relative to page 0x2_0000_0000 → page 0 (0x200–0xFFF, 3584 B), page 1 (4096 B), page 2 (0x0–0x1FF, 512 B): three pages.
  4. PRPs: PRP1 = 0x2_0000_0200 (with offset). More than two pages, so PRP2 = address of a PRP list, say 0x1_5000_1000, holding 0x2_0000_1000 and 0x2_0000_2000. (PRP list entries other than the first PRP must have zero offset.)
  5. Data TLPs at MPS 256 without crossing 4 KiB: page 0 from 0x200 to 0x1000 = 3584 B = 14 TLPs; page 1 = 16 TLPs; page 2 = 512 B = 2 TLPs; total 32 MWr. (A controller may choose to align its first TLPs differently; the count depends on its choice of payload sizes.)
  6. Extra traffic: one MRd of 4 Dwords (two 8-byte entries) for the PRP list and its CplD.
  7. Wire time ≈ 32 × 280 B / 7.88 GB/s ≈ 1.1 µs.
  8. CQE for CID 0x0020 on SQ1 at slot 10 of CQ1 with SQHD 12: address 0x1_2341_00A0, DW2 = 0x0001_000C, DW3 = 0x0001_0020.

Variant: the same read on namespace 2 (4096-byte LBAs): SLBA = 0x30_0000, NLB = 1. Same PRPs, same data TLPs — the PCIe traffic does not depend on the LBA size, only the command fields do.

Common mistakes

  • Confusing Linux 512-byte sectors with device LBAs on 4 KiB namespaces — SLBA off by a factor of 8.
  • Forgetting NLB is 0's based, leading to one extra block DMA'd past the end of the buffer.
  • Putting an offset in PRP2 or PRP list entries — only PRP1 may carry an offset.
  • Expecting a completion TLP for data writes — data MWr are posted; there is none.
  • Reading the CQE before checking the phase, or reading data before the CQE.
  • Treating a missing MSI-X as a hang when the queue is polled or coalesced.
  • Blaming the SSD for a 30 s stall without checking whether the SQE was ever fetched (doorbell problem) or whether the CQE was written but not seen (phase/CQ problem).
  • Using the buffer after a failed read.

Senior engineer insight

A senior engineer reads a READ trace as a timeline of promises. The doorbell promises an SQE fetch within a microsecond or so; the fetch promises data within the device's media latency; the last data TLP promises a CQE immediately; the CQE promises an interrupt unless coalesced or polled; the interrupt promises a CQ head doorbell soon after. Knowing these expected gaps for the specific platform turns every capture into a quick check: which promise was broken first?

Second, separate the three owners of a read: host (everything up to the doorbell, plus IOMMU mappings and CQ handling), link (TLP integrity, ordering, flow control, errors visible in AER) and device (from SQE fetch to CQE). Most cross-team arguments end as soon as someone shows which owner's promise broke first, with a TLP number and a timestamp.

Third, tail latency lives in the media gap. Garbage collection, read-retry, read disturb handling and die contention all appear as a longer gap between SQE fetch and first data. If p99.99 latency matters, measure that gap distribution directly from traces or with polling, and correlate it with controller telemetry; driver tuning cannot remove it.

Solution

R. SLBA = 4,000,000 = 0x3D_0900 → CDW10 = 0x003D_0900, CDW11 = 0. NLB = 12288/512 − 1 = 23 = 0x17 → CDW12 = 0x0000_0017. Data: 16 MWr to 0x2_0003_0000–…F00, 16 to 0x2_0007_0000–…, 16 to 0x2_0004_0000–… = 48 TLPs, plus one 4-DW PRP-list MRd. SQE at 0x1_2340_0000 + 40 × 64 = 0x1_2340_0A00; CQE at 0x1_2341_0000 + 17 × 16 = 0x1_2341_0110 with DW2 = 0x0001_0029 (SQHD 41) and DW3 = 0x0001_0033.

T. Row 1: SQ1 tail → 42. Row 2: fetch slot 41 (0xA40 / 64 = 41). Row 3: Read (OPC 02h), CID 0x34, NSID 1, PRP1 0x2_0005_0000, PRP2 0x1_5000_2000 (PRP list pointer, since NLB 0x17 = 24 blocks = 12 KiB spans three pages), SLBA 0x3D_0908, 12 KiB — well formed. Row 4: controller reads the 2-entry PRP list (4 DW). Row 5: the root complex answers with a Completion with status Unsupported Request and no data — the address 0x1_5000_2000 was not accepted (typically: IOVA not mapped in the IOMMU, so the read is rejected). Row 6: CQE at CQ1 slot 18 (0x120 / 16), DW2 = SQHD 42, DW3 = 0x00090034 → CID 0x34, P = 1, status word 0x0009 → SC = 0x04, SCT 0: Data Transfer Error, DNR 0.

First abnormal event: row 5, the UR completion to the controller's PRP-list read. It points to the host side: the PRP list page's IOVA was unmapped or freed (e.g. the driver freed the PRP-list page from its pool too early, or the IOMMU mapping was torn down). Evidence: IOMMU fault logs at the same time naming 0000:01:00.0 and address 0x1_5000_2000; AER logs on the root port if UR is reported; driver PRP-pool allocation tracing. Confidence: high that the host mapping is at fault; the controller behaved correctly by failing the command with Data Transfer Error and no data writes.

What a senior engineer notices

In T, the device did nothing wrong — the first abnormal event is the host's answer to a device request. A generic "Data Transfer Error" status would have sent a junior engineer to the SSD vendor. Also notable: no data TLPs were emitted before the failure, so no partial data reached memory; had the PRP list failure occurred halfway through, part of the buffer would contain new data — another reason never to use a failed read's buffer.

Failure variants

  • PRP-list read returns Completer Abort instead of UR (a different host-side condition; same NVMe status is plausible).
  • PRP list readable but contains an entry with a non-zero offset: the controller may fail with an invalid PRP offset status — confirm the status code in the specification. Uncertain
  • Data MWr to an unmapped page: no UR (posted), CQE success, IOMMU fault only in the kernel log.

  4. Explain why the CQE can be trusted as an indication that data is in memory, and name one configuration that could break this.
  5. A trace shows the SQE fetch, then 16 data MWr, then nothing for 30 s. Which owner do you suspect and why?
  6. Using the time formula, estimate Tdata for 128 KiB on Gen5 x4 (32 GT/s) at MPS 256.
Answers

1: SLBA = 10 GiB / 4096 = 2,621,440 = 0x28_0000; NLB = 64 KiB / 4 KiB − 1 = 15.

2: 512, 256 and 128 TLPs respectively (64 KiB / MPS), assuming the controller uses full MPS payloads.

3: 0x800 + 4096 = 0x1800 → spans two pages; PRP2 = the second page's address (no list needed). Data: 2048 B in page 0 (8 TLPs) + 2048 B in page 1 (8 TLPs) = 16 TLPs.

4: The controller sends the CQE MWr after the data MWr; PCIe ordering does not let a posted write pass an earlier posted write in the same direction, so data reaches memory first. Relaxed Ordering set on the CQE write (or a non-compliant bridge, or a platform that reorders) could break it.

5: The device: it has transferred the data but not written the CQE — a controller firmware hang after DMA (or a CQE write that failed in the controller). Check whether other commands complete, and capture controller telemetry before reset.

6: R ≈ 32 × 4 × 128/130 / 8 ≈ 15.75 GB/s; 512 TLPs × 280 B = 143,360 B → ≈ 9.1 µs.

Quiz

  1. Which TLP carries the Read SQE to the controller?

    • The doorbell MWr
    • An MRd from the host
    • A CplD answering the controller's MRd
    • An MSI-X MWr
    Answer and reasoning

    The controller reads the SQE from host memory with an MRd; the root complex returns it in a CplD. The doorbell carries only the tail index.

  2. For a 4 KiB read on a 512-byte-LBA namespace, NLB is:

    • 8
    • 7
    • 4096
    • 0
    Answer and reasoning

    Eight blocks, 0's based → 7.

  3. Read data travels from controller to host as:

    • Posted Memory Writes
    • Completions with Data
    • Non-posted Memory Reads
    • Messages
    Answer and reasoning

    The controller is the requester for data movement in both directions; for a read it writes into host memory with posted MWr TLPs.

  4. When does the controller read a PRP list?

    • Always
    • When PSDT = 01b
    • When the buffer is in one page
    • When the transfer spans more than two memory pages
    Answer and reasoning

    One page: PRP1 only. Two pages: PRP2 is the second page. More: PRP2 points to a PRP list.

  5. Status SCT 2h, SC 81h with DNR = 1 means:

    • LBA Out of Range, retry
    • Invalid Field
    • Unrecovered Read Error, retry not expected to help
    • Data Transfer Error
    Answer and reasoning

    Media and Data Integrity Errors / Unrecovered Read Error; DNR set.

  6. What does Limited Retry do?

    Model answer

    Asks the controller to apply limited error-recovery effort so the command fails quickly instead of spending a long time on retries; useful when the host can recover the data from elsewhere.

  7. Why might a trace of a healthy read show no MSI-X write?

    Model answer

    The CQ is polled (created without interrupts, e.g. io_uring polled queues), or interrupt coalescing delayed and merged the interrupt with a later one outside the capture window.

  8. Where does most of a 4 KiB read's latency go on a typical TLC SSD?

    Model answer

    The media: FTL lookup, NAND array read and ECC — tens of microseconds — compared with well under a microsecond for the data on a Gen4 x4 link and about a microsecond for the SQE fetch.

  9. A successful read returns wrong data; the kernel log shows an IOMMU fault for the SSD at the time. Explain.

    Model answer

    The controller wrote data to an IOVA the IOMMU did not map (stale or wrong PRP). The posted MWr was dropped and logged by the IOMMU, the controller never learned of it, and it completed the command successfully. The buffer still holds old content. Root cause is on the host (mapping lifetime or PRP construction).

Interview questions

  1. Beginner. Walk me through what happens when Linux reads 4 KiB from an NVMe SSD.

    Model answer

    Page-cache miss → filesystem maps to blocks → block layer request on the CPU's hardware queue → driver builds a Read SQE (SLBA, NLB, PRPs), writes it to the SQ, rings the doorbell → controller fetches the SQE, reads NAND, DMA-writes data to the buffer, writes a CQE, sends MSI-X → driver consumes the CQE, rings the CQ head doorbell, completes the request → task wakes.

  2. Beginner. Which fields of the Read command say what to read?

    Model answer

    NSID (which namespace), SLBA in CDW10–11 (where), NLB in CDW12 (how many, 0's based), and PRP1/PRP2 or SGL (where to put it).

  3. Intermediate. List the TLPs of a 4 KiB read and say which are posted.

    Model answer

    Doorbell MWr (posted), SQE MRd (non-posted) + CplD, 16 data MWr at MPS 256 (posted), CQE MWr (posted), MSI-X MWr (posted), CQ head doorbell MWr (posted). Plus PRP-list MRd/CplD if more than two pages.

  4. Intermediate. How do FUA and LR change a read?

    Model answer

    FUA forces the data to come from non-volatile media (after committing any cached write data for those LBAs). LR limits error-recovery effort so failures are reported quickly.

  5. Advanced. A read returns Data Transfer Error. How do you find out why?

    Model answer

    Look in the trace for a non-successful PCIe completion (UR/CA) to one of the controller's own reads during that command — typically a PRP-list or SGL fetch — and for AER logs at the root port and IOMMU faults in the kernel log. Then check the PRP construction and mapping lifetime in the driver.

  6. Advanced. How would you measure the media portion of read latency without a protocol analyzer?

    Model answer

    Use polled I/O at queue depth 1 to remove interrupt latency, compare against the device's reported latency statistics if available, and subtract a measured baseline for a read of a deallocated/cached LBA (no NAND access). Tracepoint timestamps of setup and completion bracket the device time plus small host overheads.

  7. Senior. Design a forensic checklist for "intermittent wrong data on read".

    Model answer

    Reproduce with pattern-filled buffers; capture PCIe with the data MWr addresses; compare with PRPs in the fetched SQE; check IOMMU faults; check CID bookkeeping (duplicate CIDs, stale completions); verify ordering attributes (relaxed ordering on CQE vs data); enable PI with host checking to catch misplaced LBAs; check for concurrent writes to the same LBAs; correlate with resets and queue deletion. Report the first abnormal event with TLP evidence.

  8. Senior. When would you choose polling over interrupts for reads, and what does it cost?

    Model answer

    For latency-critical, high-IOPS workloads at low queue depth, where interrupt delivery and context switches are a large fraction of latency. It costs CPU cycles spinning, reduces efficiency at low load, and needs dedicated polled queues; it also removes MSI-X from traces, which changes how you debug.

Model explanation for the senior engineer

"I lay the capture against the expected timeline. If there's no SQE fetch after the doorbell, it's the doorbell path or a dead controller. If the fetch happened, I decode the SQE: if it's malformed, it's the host. If the controller made its own reads (PRP list) and got UR or CA, it's host mapping — confirm with IOMMU logs. If it's well formed and there's no data and no CQE while other commands progress, it's the device. If there's a CQE with an error status, the status plus the gap tells me media versus validation. If there's a good CQE but the host times out, it's the host CQ or interrupt path — phase, CQ address, MSI-X. Each verdict comes with a TLP number."

Chapter summary

A READ travels down through application, filesystem, block layer and driver to become a 64-byte SQE (OPC 02h, NSID, SLBA in CDW10–11, 0's based NLB in CDW12 with FUA, LR and PRINFO, PRP1/PRP2). A doorbell MWr tells the controller; it fetches the SQE with MRd/CplD, fetches a PRP list if the buffer spans more than two pages, reads NAND (the dominant latency), writes the data with posted MWr TLPs bounded by MPS and 4 KiB boundaries, writes the CQE, and signals MSI-X. PCIe ordering makes the CQE a commit point. Failures show as absences (no fetch, no data, no CQE) or as statuses (media, transfer, range), and the first abnormal event — often an absence — assigns the fault to host, link or device.
