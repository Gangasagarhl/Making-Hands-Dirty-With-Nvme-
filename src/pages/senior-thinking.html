The questions a senior NVM Express (NVMe) and PCI Express (PCIe) engineer asks automatically when something fails — what each one means, where its answer lives in the evidence, the trap it protects against — and the drills, worked cases and checklists that turn them from a list into a reflex.

Why this part exists

Put a junior and a senior engineer in front of the same failing trace. The junior scrolls to the error the test reported — usually a timeout in the kernel log — and starts theorizing. The senior scrolls backwards from it, looking for the first thing that was not as it should be, and before forming any theory asks a quiet series of questions: who sent this, who should have answered, which queue, which command, which buffer, which layer owns this behaviour, and what would prove me wrong?

The difference is not knowledge. Most of the facts are in the earlier chapters. The difference is a disciplined sequence of questions applied every time, so that the answers — or the absence of answers — drive the investigation instead of the loudest symptom. This part names the questions and trains them until they become automatic.

Learning objectives

  • Ask and answer, from evidence, the thirteen senior questions for any failure.
  • Find the first abnormal event and state what should have happened instead.
  • Assign behaviour to the layer and the agent that owns it, and identify requester and completer for any transaction.
  • Pin a failure to queue, command identifier, namespace, DMA buffer and PCIe address.
  • Separate transport problems from protocol problems, and symptoms from causes.
  • State, for every hypothesis, the evidence that would falsify it — and go and get it.

The story

A cake comes out of the oven flat. One child says "the oven is broken!" because the oven is the last thing that touched it. A grandmother who has baked for fifty years asks different questions: what did the batter look like before it went in? Who added the baking powder, and was it the right jar? What should the batter have looked like at each step? And then she says: "If it was the oven, the cookies we baked after it would be flat too. They weren't. So it wasn't the oven."

Senior debugging is like air-accident investigation. Investigators do not start from the crash; they reconstruct the timeline from the recorders and look for the first departure from normal operation — the first deviation from the checklist, the first abnormal parameter. They assign each event to a system and an owner (crew, aircraft system, air traffic control). They distinguish the event that made the outcome inevitable from the many alarms that followed it. And every theory is tested against evidence that could disprove it before it goes in the report.

Accident investigators usually have one event and months to study it; you have thousands of commands and a release deadline. They have recorders designed for investigation; your capture may be one direction, one link, a short window, and missing the host software's view entirely. And an aircraft's systems are mostly independent, while in NVMe over PCIe one layer's symptom is routinely another layer's cause — a PCIe completion problem surfaces as an NVMe status, which surfaces as a file-system error. The questions must therefore cross layers explicitly.

What is the first abnormal event?

Meaning. The first abnormal event is the earliest observable point where the evidence departs from what correct operation would produce. Not the first error message; not the event the test reported; the first departure.

Why it matters. Everything after a failure is contaminated: recovery actions, retries, timeouts and secondary errors pile up and look like problems themselves. The first abnormal event is the last moment the system was telling you the truth about the original fault.

How to answer. Build the timeline (by hand or with the automated pipeline), start from the reported failure, and walk backwards through every event related by identifier — the same command, tag, address, queue — until events look normal. Then check the window just before for unrelated abnormalities. Date absences ("no completion") at the moment they became overdue, not at the request.

Trap. Mistaking the loudest event for the first. A kernel "I/O timeout" 30 seconds after a quiet Unsupported Request (UR) completion is a consequence, not a beginning.

Also ask. Is the first abnormal event inside my capture? If the capture started late, the honest answer is "the first abnormal event in the window is X; earlier events are unknown".

What should have happened?

Meaning. The expected event or value at that point, stated precisely enough to compare: "a CplD with 512 bytes and status Successful Completion (SC) for tag 0x13 within the completion timeout", not "it should have worked".

Why it matters. "Abnormal" is only defined relative to an expectation. If you cannot state the expectation, you cannot be sure the event is abnormal, and you cannot design a test.

How to answer. From the specification (what is required), from a golden trace of the same operation on a known-good system (what is typical), and from the system context (what this configuration should produce: MPS, queue sizes, interrupt settings). Label which of the three each expectation comes from.

Trap. Expecting implementation-dependent behaviour as if it were required — for example, assuming the controller always fetches one Submission Queue Entry (SQE) per read, or completes commands in order.

Which layer owns this behaviour?

Meaning. Which specification and which part of the stack defines the behaviour that went wrong: physical layer, data link layer, transaction layer (PCIe Base); NVMe transport mapping (NVMe over PCIe Transport); NVMe queues, commands, status (NVMe Base and command sets); or host software (driver, IOMMU, block layer — implementation).

Why it matters. The owner determines which document you read, which team investigates, and which evidence is relevant. A Data Transfer Error status is reported by NVMe, but the behaviour that failed may be owned by the PCIe transaction layer or by the host IOMMU.

How to answer. Use the ownership table below. For the first abnormal event, name the layer that defines the expected behaviour you stated in question 2.

Trap. Assigning ownership to the layer that reported the error rather than the layer whose rule was violated.

Who is the requester?

Meaning. The requester is the agent that initiated the transaction: its Requester ID (Bus/Device/Function) for PCIe requests; for NVMe, the host (which submits commands) or the controller (which issues DMA).

Why it matters. Requests carry intent. A Memory Read from Requester ID 0x0100 is the SSD acting as a bus master; a Memory Write from the root complex to BAR0 is the CPU acting through the driver. Confusing the two inverts the whole analysis.

How to answer. Read the Requester ID and the direction. On the course lab system, 0x0100 is the SSD; requests marked RC come from the root port / CPU side.

Trap. Assuming the host initiates all reads. In NVMe, the controller initiates nearly all data movement: SQE fetches, PRP list fetches, Write data reads, Read data writes, CQE writes and MSI-X writes are all device-initiated.

Who is the completer?

Meaning. For a non-posted request, the completer is the agent that should answer it. For device DMA reads on the lab system, the completer is the root complex on behalf of host memory (through the IOMMU). For host MMIO reads, the completer is the SSD's Function.

Why it matters. The completer is the agent that decided the outcome: when a completion says UR or Completer Abort (CA), the completer is telling you it could not or would not service the request. When no completion arrives, the completer — or the path to it — is the first suspect.

How to answer. Completer ID in the completion; or the routing target of the request address (which BAR, which memory region).

Trap. Blaming the requester for an unsuccessful completion without asking why the completer refused. A UR to a DMA read is the host side refusing; the question is whether the address was legitimately mapped.

Which queue is involved?

Meaning. The Submission Queue and Completion Queue the failing command used, identified by SQ Identifier (SQID) and the queue's base address.

Why it matters. Queues partition work by CPU core and by priority; queue-specific problems (a misconfigured queue, an interrupt vector mapping error, a doorbell stride mistake) affect only some commands. Knowing the queue tells you whether the failure is global or local.

How to answer. From the doorbell offset (using CAP.DSTRD), from the SQE fetch address (which queue's range), or from the CQE's SQID field.

Trap. Assuming the queue from the doorbell offset without checking CAP.DSTRD (see Case 2).

Which command ID is involved?

Meaning. The Command Identifier (CID) in the SQE, unique per SQ among outstanding commands, returned in the CQE.

Why it matters. (SQID, CID) is the key that ties together everything about one command: its fetch, its data, its completion, its log entries (the Error Information log records SQID and CID), and the driver's timeout message.

How to answer. Decode the SQE from the fetch completion's payload; match the CQE by (SQID, CID).

Trap. CIDs are reused. A CID seen twice in a capture may be two different commands. Always pair the CID with a time window or generation.

Which namespace?

Meaning. The Namespace Identifier (NSID) in the SQE, and the namespace's properties (LBA size, protection settings, command set).

Why it matters. The same command means different byte counts on a 512-byte and a 4 KiB LBA namespace; protection information and zoned rules are per namespace; namespace attachment and state changes cause specific errors.

How to answer. NSID from the SQE; namespace properties from Identify Namespace (for the lab system: namespace 1 uses 512-byte LBAs, namespace 2 uses 4 KiB).

Trap. Computing transfer lengths with the wrong LBA size, then "finding" a data-length anomaly that is not there.

Which DMA buffer?

Meaning. The host memory region the command's data pointer describes: PRP1/PRP2 (and PRP list) or SGL, as I/O virtual addresses (IOVA) when an IOMMU is on.

Why it matters. Data errors, UR completions on DMA, and corruption are all buffer questions: was it mapped, was it the right size, was it reused too early, did two commands overlap?

How to answer. Decode the data pointer from the SQE; fetch the PRP list if used; compare data TLP addresses against the ranges.

Trap. Comparing IOVAs in the trace with physical addresses in a host log. They are different address spaces when the IOMMU is enabled.

Which PCIe address?

Meaning. The exact address in the TLP, and what that address is in the system's memory map: a register in BAR0, a doorbell, an SQ or CQ slot, a data buffer, a PRP list, the MSI-X window.

Why it matters. Addresses are how PCIe expresses meaning. A write to the wrong doorbell, a read beyond a queue, a DMA to an unmapped page — each is visible only as an address.

How to answer. Map the address using the BAR assignment (configuration space), CAP.DSTRD (controller registers), queue bases (driver setup), the PRP/SGL ranges, and the MSI-X table contents.

Trap. Decoding an address with an assumed map. Read the map from the system.

Is the issue transport or protocol?

Meaning. Is the failure in moving packets reliably (link training, signal integrity, replay, flow control — the PCIe physical and data link layers, plus transaction-layer delivery) or in the meaning of what was exchanged (wrong command, wrong field, wrong state, wrong ordering — NVMe semantics or transaction-layer rules)?

Why it matters. Transport problems are investigated with link status, Advanced Error Reporting (AER) correctable errors, DLLP traces and electrical tools; protocol problems with decoders, specifications and firmware or driver code. Sending a signal-integrity problem to the firmware team wastes weeks.

How to answer. Look for Nak DLLPs, replays, Link Training and Status State Machine (LTSSM) entries into Recovery, link speed or width changes, correctable error counts. If the link is clean and the packets are well-formed, the problem is in what they say.

Trap. Transport problems often present as protocol symptoms: latency spikes, timeouts, even completion timeouts. Check the link first; it is cheap.

Is the error a symptom or a cause?

Meaning. Is this event the origin of the failure, or a consequence of something earlier?

Why it matters. Fixing a symptom (raising a timeout, retrying) hides the cause, which returns in a worse form.

How to answer. An event is a symptom if an earlier abnormal event shares an identifier with it (same command, tag, address, queue) and a known mechanism connects them. Draw the chain: cause → mechanism → effect, with evidence for each link.

Trap. "Post hoc" reasoning — B followed A, so A caused B — without a shared identifier or mechanism.

What evidence would falsify my hypothesis?

Meaning. For your current best explanation, name a falsifying observation that would prove it wrong, and then try to obtain that observation.

Why it matters. Confirming evidence is easy to find for almost any theory. Falsification is what separates a tested conclusion from a story. It also gives you the next experiment.

How to answer. Ask: "If my hypothesis is true, what else must be true?" and "If it is false, what would I see instead?" Then design a capture, a log check or a controlled experiment that distinguishes the two.

Trap. Hypotheses that cannot be falsified ("intermittent firmware issue") are not hypotheses. Make them specific enough to fail.

The first abnormal event, climbed

The flat cake: look at what went wrong first, not what you noticed last.

The first abnormal event is the earliest observation that differs from correct operation. Later errors are usually consequences.

In hardware, a fault causes a cascade: a refused DMA read leaves a controller unable to complete a command; the driver's timer fires; the driver aborts and resets; the resets create link events. Each stage is real hardware behaviour, but only the first is the fault.

Specifications define expectations precisely: completion rules (PCIe Base, Transaction Layer), queue and status semantics (NVMe Base), doorbell mapping (NVMe over PCIe Transport). An event is abnormal when it violates a stated rule or a configuration-derived expectation.

On the wire, the first abnormal event may be a packet with an error field (Cpl with UR), a packet that should not exist (a write to an unexpected address), or a packet that never appears (a missing completion, dated at its deadline).

In a capture, you find it by walking back from the reported failure along shared identifiers, then scanning the preceding window for unrelated anomalies; you mark it and write the expected event beside it.

Debugging starts there: name the owning layer, requester and completer, the NVMe context, and the falsification test for your first hypothesis.

Designing falsification experiments

For each hypothesis, write two predictions: what you must see if it is true, and what you would see if it is false. Then choose the cheapest observation that separates them.

Falsification patterns
Hypothesis typeFalsifying experiment
"The link is marginal"Force a lower speed (lab only) or swap slot/cable; check AER correctable counters during the failure
"The buffer was unmapped"IOMMU fault log at the failure time; rerun with buffers pinned and logged
"The controller stalls on command X"Issue X alone, with nothing else outstanding; vary queue depth
"The driver writes the wrong doorbell"Compare the doorbell addresses in the trace with the formula using CAP.DSTRD read from the device
"Firmware bug in feature F"Disable F (if configurable) and rerun; try another firmware version on a lab unit
"The CQE was lost"Capture longer and both directions; check other CQs; check the CQ memory contents in a host dump
"Interrupts are lost"Poll the CQ without interrupts; compare MSI-X writes with CQE writes; read the MSI-X table and PBA

Experiments that change link speeds, firmware, IOMMU modes or inject faults are Caution lab or Expert lab activities. Run them only on lab systems, never on production drives or hosts.

Drills

  1. Daily five. Take any trace excerpt from this course (or your work) and fill questions 1, 4, 5 and 10 in five minutes.
  2. Reverse walk. Given only the last error, list the identifiers you would follow backwards and in what order.
  3. Falsify a colleague. Take a hypothesis from a bug report and write the observation that would refute it.
  4. Layer sort. Sort twenty error messages (AER, NVMe status, kernel log lines) by owning layer.
  5. Silent cards. For each worked case, write which questions the evidence could not answer.
Model answer for drill 2 (Case 1)

From the CQE error: (SQID 1, CID 0x0041) → the SQE fetch that decoded that CID (tag 0x11) → its data pointer (IOVA 0x2_0000_1000) → device requests to that address (MRd tag 0x13) → completions for (0x0100, 0x13) → the UR. Then scan earlier events for anything abnormal unrelated to this chain.

Quiz

  1. A kernel log reports an I/O timeout at 30.2 s. The capture shows a Cpl with UR at 0.004 ms for a DMA read of the same command's buffer. Which is the first abnormal event?

    • The kernel timeout
    • The UR completion
    • The doorbell write
    • Cannot be determined
    Answer and reasoning

    The UR is earlier and shares the command; the timeout is a later consequence.

  2. Who is the completer for an SQE fetch on the lab system?

    • The SSD
    • The NVMe driver
    • The root complex on behalf of host memory
    • The IOMMU driver
    Answer and reasoning

    The SSD requests the SQE from host memory; the root complex returns the CplD.

  3. Repeated Nak DLLPs followed by LTSSM Recovery point to which class of problem?

    • Transport
    • NVMe protocol
    • Host driver
    • Namespace configuration
    Answer and reasoning

    Naks and Recovery are Data Link and Physical Layer reliability events.

  4. Why is a doorbell write's failure not visible as an error completion?

    • Doorbells are configuration writes
    • The analyzer filters them
    • NVMe forbids error reporting
    • Memory Writes are posted: there is no completion
    Answer and reasoning

    Posted requests receive no completion; any error would be signalled by other mechanisms at the receiver.

  5. What makes an event a symptom of an earlier event rather than a coincidence?

    Model answer

    A shared identifier (command, tag, address, queue) plus causal order plus a known mechanism connecting them. Time order alone is insufficient.

  6. The CQE says CID 0x0041 failed. Why is "which namespace?" still worth asking?

    Model answer

    Namespace properties (LBA size, protection, state) change expected transfer sizes and possible errors; failures may be confined to one namespace; the Error Information log entry includes it.

  7. Give a falsification test for "the SSD's garbage collection causes the latency spikes".

    Model answer

    If GC is the cause, the delay appears before data transfer starts (between SQE fetch and first data TLP) and the link is clean. If spikes coincide with Naks/Recovery mid-transfer, or persist with the device idle-preconditioned, GC is not the cause.

  8. Why must you check CAP.DSTRD before answering "which queue?" from a doorbell address?

    Model answer

    The doorbell stride is 4 << CAP.DSTRD bytes; with a non-zero DSTRD, the same offset belongs to a different queue or to a CQ head instead of an SQ tail.

  9. Your capture starts after the failure began. What can you say about the first abnormal event?

    Model answer

    Only the first abnormal event within the window; the true first event may be earlier and is unknown. Say so and recapture with an earlier trigger.

  10. Why is "intermittent firmware issue" not a hypothesis?

    Model answer

    It predicts nothing specific and cannot be falsified. A hypothesis must say what will and will not be observed under defined conditions.

Interview questions

  1. Beginner: What is the first abnormal event, and why do we look for it?
    Model answer

    The earliest observed departure from expected behaviour. Later events are contaminated by recovery and secondary failures; the first one is closest to the fault.

  2. Intermediate: Walk me through how you'd decide whether a failure is in the SSD or the host.
    Model answer

    Find the first abnormal event; identify requester and completer; name the rule violated and its owner; check address maps (doorbells, buffers) against host configuration; confirm with a falsification test (e.g. IOMMU log, different host, different device).

  3. Intermediate: A Write fails with Data Transfer Error. What do you look at in a PCIe trace?
    Model answer

    The command's data reads: addresses vs its PRP/SGL ranges, their completions (UR/CA/poisoned/missing), and any PRP list fetch; then the order of those events relative to the CQE.

  4. Advanced: How do you tell transport problems from protocol problems quickly?
    Model answer

    Check link status (speed/width), AER correctable counters, Naks/replays and LTSSM Recovery around the failure. If clean, and packets are well-formed, the problem is semantic. Transport issues usually show as latency or timeouts without semantic errors.

  5. Senior: Tell me about a time a symptom was mistaken for a cause, and how you'd prevent it on a team.
    Model answer

    (Use a real story.) Structure: the symptom, the misattribution, the evidence that revealed the earlier event, the fix. Prevention: report templates that require first abnormal event, owning layer and falsification test; reviews that ask the thirteen questions.

  6. Senior: What evidence would make you change your mind about your current hypothesis in Case 1?
    Model answer

    No IOMMU fault and a valid mapping for 0x2_0000_1000 at the time; the same UR with translation bypassed; or a UR address outside the command's buffer (indicating a controller addressing bug rather than a host mapping problem).

Teach-back challenge

  • To a child: explain why the grandmother asked about the batter instead of blaming the oven.
  • To a junior engineer: explain requester and completer with the SQE fetch and the doorbell as examples.
  • To a senior engineer: argue that Case 2's first abnormal event is the doorbell write, not the missing fetch.
Model explanation for the senior engineer

"The missing fetch is an absence that becomes observable only after some waiting time. The doorbell write at #40 is observable immediately and is already wrong in context: with CAP.DSTRD = 1 its offset decodes to the Admin CQ head doorbell. It precedes the absence, shares the queue identity question, and explains it by a mechanism. So #40 is the first abnormal event; the missing fetch is its consequence."

Summary, mastery gate and next steps

Seniority in protocol debugging is a habit of questions: locate the first abnormal event and its expectation; assign it to a layer and to agents; pin it to queue, command, namespace, buffer and address; classify transport versus protocol and symptom versus cause; and always state what would prove you wrong.

Do not move on until you can:

  • recite the thirteen questions in order and say what each locates
  • find the first abnormal event in a trace and state the expected event with its source
  • name requester, completer and owning layer for any NVMe-over-PCIe transaction
  • map any TLP address to its meaning using the system's maps
  • separate transport from protocol problems with evidence
  • draw a symptom → cause chain with shared identifiers
  • write a falsification test for every hypothesis you hold
  • fill the question card for an unfamiliar failure in under fifteen minutes
