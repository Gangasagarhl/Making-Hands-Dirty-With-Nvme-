A Zoned Namespace (ZNS) divides its logical blocks into zones that must be written from start to end, in order, and erased only as a whole. This chapter teaches the zone model, its state machine, the write pointer, Zone Append, Zone Management Send and Receive, open and active zone limits, and how all of it looks in a trace, in Linux and when it fails.

Why this chapter exists

NAND flash cannot overwrite in place. It programs pages in order inside an erase block and can only erase whole blocks. A conventional SSD hides that from the host with a Flash Translation Layer (FTL) that remaps every logical block, keeps spare capacity (over-provisioning) and runs garbage collection. The price is a large mapping table in DRAM, 7–28% of the flash held back as spare, and write amplification that steals bandwidth and endurance — all of it invisible and unpredictable from the host's side.

The Zoned Namespace Command Set exposes a model much closer to how flash wants to be written. The host promises to write each zone sequentially and to reset a zone before rewriting it; in return the device can shrink its mapping table, its spare capacity and its garbage collection. Log-structured file systems (F2FS, Btrfs in zoned mode), key-value stores (RocksDB with ZenFS) and object stores already write mostly sequentially, so they can carry the responsibility the device gives up.

For an engineer the consequence is that a whole new class of errors appears: writes that are "valid" for a block device are rejected because they are not at the write pointer, because the zone is full, or because too many zones are open. Understanding the zone state machine is now required to read traces from cloud and hyperscale storage, and the ZNS model is the clearest example in NVMe of a command set that changes the meaning of a WRITE.

The story

Imagine a giant warehouse with long aisles. Each aisle is a zone. The warehouse has one strict rule: in each aisle, boxes must be put down one after another starting from the front, with no gaps and no jumping ahead. A little flag on the floor, the write pointer, shows where the next box must go. When an aisle is full, nothing more can go in. To use it again, the workers must empty the whole aisle — you cannot take out just one box and put a new one in its place.

The warehouse also has only a few forklifts. Each aisle someone is actively filling needs a forklift parked in it. If all the forklifts are busy, you cannot start a new aisle until you park one somewhere (close an aisle) or finish one.

Sometimes you don't care exactly where your box goes, you just want it in aisle 7. Then you hand it to the aisle-7 worker and say "put it wherever the flag is, and tell me the spot number." That is Zone Append.

A high-bay distribution warehouse with "drive-in" racking. Each lane is loaded from the front and filled to the back, pallet after pallet; you cannot pull out a pallet in the middle without unloading everything in front of it, so lanes are emptied and reassigned whole. Lanes in use need a dedicated loading crew (open resources), and every lane that holds partial stock needs an inventory record kept current (active resources). Receiving can ask the dock "slot this pallet anywhere in lane 12 and give me the slot number" — that lets ten trucks unload into the same lane in parallel without agreeing on order. A conventional SSD is, by contrast, a warehouse with a full-time re-shelving team that lets customers drop items anywhere and quietly reorganizes at night — convenient for customers, expensive for the warehouse.

What it hides. A zone is a range of logical blocks, not a physical aisle. The device maps a zone onto flash erase blocks however it likes, possibly striped across many dies. Zone size and zone capacity are separate numbers: the aisle may be painted 100 m long but only 80 m usable.

Where it misleads. "Emptying the aisle" (Reset Zone) is not a physical erase you can time; the device may erase later or lazily. The forklift limit is not physical either — it is a promise about how many zones the device can keep in fast, partially-written state, and it is reported as a number you must respect. And unlike a warehouse, reading is unrestricted: you may read any written block of any zone in any order.

Where it breaks. In a warehouse two workers putting boxes in the same aisle would see each other. In NVMe two WRITE commands to the same zone can be reordered anywhere between the application and the controller, and the second one to arrive fails. That is the problem Zone Append solves.

Beginner explanation

A ZNS namespace looks like a normal namespace — LBA 0 to NSZE−1, READ works everywhere — but its LBAs are cut into equal-sized zones. If the zone size is 65,536 blocks, zone 0 is LBAs 0–65,535, zone 1 is 65,536–131,071, and so on.

Each zone has a write pointer: the next LBA that may be written. A fresh (Empty) zone has its write pointer at its first LBA. Every WRITE to a zone must start exactly at the write pointer; the pointer then moves forward by the number of blocks written. When the pointer reaches the end of the zone's usable capacity, the zone is Full.

To reuse a zone you reset it: the data is discarded, the write pointer goes back to the start, and the zone is Empty again. There is no way to overwrite part of a zone.

Each zone is in a state — Empty, Opened (implicitly or explicitly), Closed, Full, Read Only or Offline. Only a limited number of zones may be Opened at once, and only a limited number may be "active" (Opened or Closed — partially written). The device tells you the limits.

Instead of WRITE, the host can use Zone Append: "write these blocks to zone N wherever the write pointer is, and tell me where they landed." Many appends to the same zone can be in flight at once.

Finally, the host asks the device for the state and write pointer of each zone with Zone Management Receive (a zone report), and changes zone states with Zone Management Send (open, close, finish, reset, offline).

Engineering explanation

Zone geometry: size, capacity, start LBA

A zoned namespace has CSI 02h. Its zone geometry is reported in the ZNS-specific Identify Namespace data structure (Identify CNS 05h with CSI 02h):

  • Zone Size (ZSZE) — in the LBA Format Extension entry that matches the namespace's LBA format: the number of logical blocks per zone, identical for every zone in the namespace.
  • Zone Capacity (ZCAP) — reported per zone in the zone descriptor: the number of writable blocks in that zone, ZCAP ≤ ZSZE. Blocks from ZSLBA + ZCAP to the next zone start are not writable. Capacity may differ between zones and may shrink over a device's life.
  • Zone Start LBA (ZSLBA) — the first LBA of the zone: zone n starts at n × ZSZE.

Why separate size from capacity? Zone size is chosen as a convenient power of two so hosts can compute zone numbers with a shift; capacity matches what the flash geometry really holds (for example, an integral number of erase-block stripes). The Linux block layer requires a power-of-two zone size, so a device with a natural 1,077 MiB stripe might expose a 2 GiB zone size and a 1,077 MiB capacity.

Synthetic example for teaching: in this chapter, namespace 2 of the lab SSD is zoned with 4 KiB blocks, ZSZE = 0x1_0000 (65,536 blocks = 256 MiB), ZCAP = 0xD800 (55,296 blocks = 216 MiB) for every zone, so zone 3 starts at LBA 0x3_0000 and its last writable LBA is 0x3_D7FF.

The write pointer and the sequential write requirement

Every zone in an NVMe ZNS namespace has zone type 2h, Sequential Write Required — unlike Shingled Magnetic Recording (SMR) hard drives, NVMe ZNS defines no "conventional" random-write zones. The rules, normative in the Zoned Namespace Command Set Specification 1.5 — Zoned Namespace Command Set model, are:

  • A WRITE (or another command that writes, such as Write Zeroes) to a zone must have its starting LBA equal to the zone's write pointer. Otherwise the command fails with Zone Invalid Write.
  • A write must not cross a zone boundary. A command whose range spans two zones fails with Zone Boundary Error.
  • A write to a zone in the Full state fails with Zone Is Full; Read Only with Zone Is Read Only; Offline with Zone Is Offline.
  • On success the write pointer advances by the number of blocks written. When it reaches ZSLBA + ZCAP the zone becomes Full.
  • Reads are not restricted by the write pointer. Reading across a zone boundary is allowed only if the namespace reports Read Across Zone Boundaries support in its Optional Zoned Command Support (OZCS) field; otherwise it fails with Zone Boundary Error.

Key transitions in words:

  • Empty → Implicitly Opened: the first write or Zone Append to the zone. The controller opens it for you.
  • Empty/Closed → Explicitly Opened: Zone Management Send with the Open Zone action. An explicitly opened zone stays open until the host closes, finishes or resets it.
  • Opened → Closed: Close Zone action. The controller may also close an implicitly opened zone on its own to free an open resource for another zone; it never does this to an explicitly opened zone. Closing a zone whose write pointer is still at ZSLBA returns it to Empty rather than Closed Uncertain — confirm in the Close Zone action description.
  • Closed → Implicitly Opened: a write to the closed zone.
  • Opened/Closed → Full: the write pointer reaches ZSLBA + ZCAP, or the host sends Finish Zone (which marks the rest of the zone unwritten but full). The controller can also finish a zone itself; the Zone Finished by Controller attribute in the descriptor says so.
  • Opened/Closed/Full → Empty: Reset Zone. All data in the zone becomes deallocated; WP = ZSLBA.
  • Any → Read Only → Offline: controller-initiated when media degrades; the host can move a Read Only zone to Offline with the Offline Zone action.

Across a controller reset or power cycle, zones in the opened states transition to Closed Uncertain — the host must re-learn states from a zone report after any reset.

Open and active resources

A device keeps partially written zones in a special internal state: write buffers, parity accumulators, open erase blocks. That state is finite, so ZNS defines two limits in the ZNS Identify Namespace data structure:

  • Maximum Open Resources (MOR) — the maximum number of zones that may be in ZSIO or ZSEO at once.
  • Maximum Active Resources (MAR) — the maximum number of zones in ZSIO, ZSEO or ZSC at once. Active ≥ open.

Both are 0's based values, and an all-ones value (FFFFFFFFh) means no limit. So MOR = 13 means 14 open zones. Uncertain on the exact encoding — confirm in the ZNS Identify Namespace field definitions; nvme-cli prints these raw.

What happens at the limit:

  • A write to an Empty or Closed zone when the open limit is reached: if any zone is implicitly opened, the controller closes one of those (its choice) and proceeds; if all open zones are explicitly opened, the write fails with Too Many Open Zones.
  • A write to an Empty zone (or Open Zone on an Empty zone) when the active limit is reached fails with Too Many Active Zones. The controller cannot fix this for you — only Finish or Reset releases an active resource.
  • Open Zone on a zone when the open limit is reached by explicitly opened zones fails with Too Many Open Zones.

Open-limit pressure is relieved silently by implicit closes. Active-limit pressure is not: every zone you touch and abandon stays active until you finish or reset it. File systems that leave half-filled zones around (for example, one per open file) hit Too Many Active Zones long after they stop seeing Too Many Open Zones. Track active zones in the host as a first-class resource.

Zone Append

Zone Append is I/O opcode 7Dh in the ZNS command set. The host specifies the zone with its ZSLBA (Command Dwords 10–11) instead of the target LBA, and the number of blocks in CDW12 bits 15:0 (0's based). The controller writes the data at the current write pointer, advances it, and returns the LBA of the first written block in completion Dwords 0 and 1 (a 64-bit value).

Why it exists: NVMe guarantees no ordering between commands, even in the same submission queue. Two WRITEs to the same zone submitted back-to-back can be fetched, processed or completed in either order, and over a fabric even the transport may reorder. With WRITE, the host must therefore keep at most one write per zone in flight (queue depth 1 per zone), which wastes the device's parallelism. With Zone Append, any number of appends to one zone can be in flight; each lands somewhere sequential, and the host learns where from the completion.

Constraints: ZSLBA must be the first LBA of a zone (otherwise Invalid Field in Command); the transfer size must not exceed the Zone Append Size Limit (ZASL), reported in the ZNS Identify Controller structure as a power of two in units of the minimum memory page size (CAP.MPSMIN), with 0 meaning "the Maximum Data Transfer Size (MDTS) applies"; the append must fit in the remaining zone capacity, otherwise Zone Is Full or a boundary error. Appends to a Full zone fail with Zone Is Full.

The consequence for host software: the data's address is known only after completion. File systems must record the returned LBA in their metadata, and the application-level order of appended records is the order of the returned LBAs, not the order of submission.

The Finish Zone Recommended and Reset Zone Recommended attributes are the device asking the host for help — typically because data in a long-open zone is aging or the device wants to reclaim. When zone attributes change, the device can raise a Zone Descriptor Changed asynchronous event and list affected zones in the Changed Zone List log page (libnvme: log identifier BFh).

Zone Random Write Area and descriptor extensions

Two optional features soften the sequential rule. A Zone Random Write Area (ZRWA) lets the host write randomly within a window just above the write pointer and commit it later with the Flush action (ZSA 11h) or by writing beyond the window; the window size and flush granularity are reported in the ZNS Identify Namespace (ZRWASZ, ZRWAFG). A Zone Descriptor Extension lets the host attach a small block of its own metadata to a zone. Both are Optional; many deployed devices support neither. Version-dependent ZRWA arrived in a ZNS revision after 1.0.

The central concept on the ladder

Warehouse aisles filled front to back, a flag marking the next spot, a limited number of forklifts, and "put it wherever the flag is and tell me" for parallel unloading.

A zoned namespace is a set of fixed-size LBA ranges, each with a write pointer and a state. Writes must land at the write pointer; zones are reset whole; at most MOR+1 zones may be open and MAR+1 active.

Inside the device each open zone owns write buffers, an open erase-block stripe and parity state; the mapping table points per zone (or per stripe) instead of per 4 KiB page. Reset marks the zone's blocks for erase; no GC copies are needed.

The ZNS Command Set 1.5 defines zone types and states, the write pointer rules, Zone Management Send (79h), Zone Management Receive (7Ah), Zone Append (7Dh), the ZNS Identify structures (MAR, MOR, ZASL, LBA Format Extension with ZSZE) and the B8h–BFh statuses.

Writes and appends are ordinary I/O SQEs on an I/O queue with NSID of the zoned namespace; data moves by device-issued Memory Reads; completions carry status or, for appends, the assigned LBA in DW0–DW1. Zone reports move by device-issued Memory Writes.

In a PCIe trace a ZNS failure looks perfect at the link level: SQE fetch, data fetch (or none), and a CQE whose Status Field holds SCT 1h with an SC between B8h and BFh. The data payload of a report shows descriptors with state nibbles 1, 2, 3, 4, D, E, F.

Debugging: Zone Invalid Write after a reorder, Too Many Active Zones from leaked partially written zones, stale write pointers after a reset, mis-sized appends against ZASL. The method: get a zone report, compare with the host's write-pointer cache, find which side is wrong.

The sixteen questions, answered for "zone"

1. What is it?
A fixed-size range of LBAs in a zoned namespace that is written sequentially through a write pointer and reset as a whole.
2. Why was it created?
To align the host interface with flash's program-in-order, erase-in-blocks physics and remove device-side GC cost.
3. What problem does it solve?
Write amplification, over-provisioning cost, large DRAM mapping tables and unpredictable latency from device garbage collection.
4. What existed before it?
Conventional FTL SSDs; Open-Channel SSD proposals (host-managed flash geometry); SMR hard disks with ZBC/ZAC zones.
5. Why is the current design better?
It abstracts away flash geometry (unlike Open-Channel) while keeping the sequential contract, and reuses the zoned block device model already in Linux for SMR.
6. Who creates it?
The device defines zones when the zoned namespace is created; zone size is fixed per LBA format.
7. Who consumes it?
Zone-aware host software: file systems, key-value stores, user-space storage engines.
8. Where does it live?
As logical ranges in a namespace; physically on flash stripes chosen by the device.
9. What memory/registers are involved?
No controller registers; ZNS Identify Namespace/Controller structures, zone descriptors in report buffers, the write pointer state in controller memory, open-zone write buffers.
10. What happens before it?
A zoned namespace is created (CSI 02h) and attached; the host selects a command set profile that enables ZNS; the host reads ZNS Identify data.
11. What happens after it?
Writes/appends fill zones; host GC copies live data out and resets zones; zones may become Read Only/Offline as media ages.
12. What happens if it is wrong?
Writes fail with zone statuses; data written by appends can be lost if the host ignores returned LBAs; resetting the wrong zone destroys data instantly.
13. What does the protocol analyzer show?
Opcodes 79h/7Ah/7Dh plus WRITE/READ to the zoned NSID; report payloads; CQE DW0–1 with appended LBAs; SCT 1h status codes B8h–BFh.
14. What does Linux show?
queue/zoned = host-managed, chunk_sectors, nr_zones, max_open_zones, max_active_zones, zone_append_max_bytes; blkzone report; nvme zns report-zones.
15. What would a validation engineer test?
Every state transition and every invalid one; limits MOR/MAR exactly at and beyond; append concurrency and returned LBAs; ZASL boundaries; reset/power loss with open zones; Read Only/Offline injection; report filters and partial reports.
16. What would a senior engineer suspect when it fails?
Host write-pointer cache out of sync; reordering of WRITEs at QD > 1 per zone; active-zone leaks; 0's-based off-by-one on MOR/MAR; zone capacity treated as zone size.

Hardware view

ZNS changes nothing on the PCIe link and nothing in the controller registers. What it changes is inside the SSD controller and its firmware:

Over-provisioningLargeSmall, for bad-block replacement and internal metadata

Zone capacity usually corresponds to a whole number of erase-block "superblocks" striped across dies, which is why it is not a power of two. A reset typically just marks those superblocks for erase; the erase happens later, so Reset Zone is fast but the zone's physical blocks are not immediately reusable — which is one reason a device can delay or refuse reuse under heavy reset churn.

Read Only and Offline states are how a ZNS device reports media wear-out: instead of silently remapping, it can shrink a zone's capacity (on reset) or take a zone read-only. A host must therefore read ZCAP from every zone report and never cache it forever.

Power-loss protection capacitors must cover the write buffers of every open zone. A device with more capacitance can afford a higher MOR. That is a concrete hardware cost behind an Identify field.

Zoned namespaces were first ratified as a technical proposal in 2020 and published as the ZNS Command Set Specification 1.0 with the NVMe 2.0 family in 2021; later revisions added features such as ZRWA and additional report filters and attributes. Revision 1.5 is current with the 2026 set. Check the revision history in the ZNS specification for when each optional feature arrived, and 2026 NVMe 2.4 Updates for 2026 changes.

Check in the specification before relying on:

  • the complete state transition table, including what Close, Open and Finish do from Empty, and which actions are no-ops versus errors;
  • the exact encoding of MAR/MOR (0's based, all-ones meaning unlimited) and ZASL units;
  • which status applies to a write extending beyond zone capacity but not beyond zone size;
  • what happens to opened zones across controller reset and power loss;
  • reporting filter values above 7h and Zone Attributes Information bits in 1.5.

The specification does not say how zones map to flash, how a controller chooses which implicitly opened zone to close, or what "Reset Recommended" means about data age.

Never assume zone capacity equals zone size, that WP is meaningful in Full or Read Only zones, that two WRITEs to a zone complete in submission order, that MOR/MAR are 1's based, or that a zone's capacity never changes.

Zone Management Receive7AhSLBA, NUMD (CDW12), ZRA (CDW13 7:0), filter (15:8), Partial (bit 16)Controller → hostStatus

Ordering. NVMe imposes no execution order among commands. For ZNS this means two WRITEs to one zone are only safe if the second is submitted after the first completes. Zone Append removes the requirement. Zone Management Send actions are also unordered with respect to in-flight I/O to the same zone: a Reset Zone racing a WRITE may make the WRITE fail with Zone Invalid Write (if the reset ran first and moved WP back to ZSLBA) or let it succeed only for its data to be discarded by the reset that follows. Hosts serialize management and I/O per zone.

Errors and layer. Every ZNS error is an NVMe command status. A ZNS problem never causes a PCIe error; a PCIe error (poisoned TLP, completion timeout) during a ZNS write is a transport problem that leaves the zone's write pointer in a state the host must re-read.

Code / pseudocode

The simulator below implements the zone state machine, the write-pointer rule, Zone Append, the open and active limits and the management actions, and runs a scenario that triggers most ZNS statuses. It is a simulation for learning: where the specification leaves a choice to the controller (which implicitly opened zone to close, the order of checks) it makes one simple choice.

#!/usr/bin/env python3
"""Zoned namespace state-machine simulator (teaching model, not a device model).
Statuses use the ZNS names; the hex values are the libnvme encodings."""

EMPTY, IOPEN, EOPEN, CLOSED, FULL, RONLY, OFFLINE = "ZSE", "ZSIO", "ZSEO", "ZSC", "ZSF", "ZSRO", "ZSO"

STATUS = {
    "BOUNDARY":      (1, 0xB8, "Zone Boundary Error"),
    "FULL":          (1, 0xB9, "Zone Is Full"),
    "READ_ONLY":     (1, 0xBA, "Zone Is Read Only"),
    "OFFLINE":       (1, 0xBB, "Zone Is Offline"),
    "INVALID_WRITE": (1, 0xBC, "Zone Invalid Write"),
    "TOO_MANY_ACT":  (1, 0xBD, "Too Many Active Zones"),
    "TOO_MANY_OPEN": (1, 0xBE, "Too Many Open Zones"),
    "BAD_TRANS":     (1, 0xBF, "Invalid Zone State Transition"),
    "INVALID_FIELD": (0, 0x02, "Invalid Field in Command"),
}

class ZoneError(Exception):
    def __init__(self, key):
        self.sct, self.sc, self.name = STATUS[key]
        super().__init__(f"SCT={self.sct}h SC={self.sc:02X}h {self.name}")

class Zone:
    def __init__(self, zslba, zcap):
        self.zslba, self.zcap, self.wp, self.state = zslba, zcap, zslba, EMPTY

class ZonedNamespace:
    def __init__(self, nzones, zsze, zcap, mor, mar):
        """mor/mar are 0's based, as reported in ZNS Identify Namespace."""
        self.zsze = zsze
        self.zones = [Zone(i * zsze, zcap) for i in range(nzones)]
        self.max_open, self.max_active = mor + 1, mar + 1

    def n_open(self):   return sum(z.state in (IOPEN, EOPEN) for z in self.zones)
    def n_active(self): return sum(z.state in (IOPEN, EOPEN, CLOSED) for z in self.zones)

    def zone(self, lba):
        return self.zones[lba // self.zsze]

    def _check_writable_state(self, z):
        if z.state == FULL:    raise ZoneError("FULL")
        if z.state == RONLY:   raise ZoneError("READ_ONLY")
        if z.state == OFFLINE: raise ZoneError("OFFLINE")

    def _acquire_open(self, z):
        """Make room for z to become open; z is EMPTY or CLOSED."""
        if z.state == EMPTY and self.n_active() >= self.max_active:
            raise ZoneError("TOO_MANY_ACT")
        if self.n_open() >= self.max_open:
            victims = [v for v in self.zones if v.state == IOPEN]
            if not victims:
                raise ZoneError("TOO_MANY_OPEN")
            v = victims[0]                     # controller's choice
            v.state = CLOSED
            print(f"    (controller implicitly closed zone at {v.zslba:#x})")

    def _do_write(self, z, nlb):
        if z.state in (EMPTY, CLOSED):
            self._acquire_open(z)
            z.state = IOPEN
        start = z.wp
        z.wp += nlb
        if z.wp == z.zslba + z.zcap:
            z.state = FULL
        return start

    def write(self, slba, nlb):
        z = self.zone(slba)
        if self.zone(slba + nlb - 1) is not z:
            raise ZoneError("BOUNDARY")
        self._check_writable_state(z)
        if slba != z.wp:
            raise ZoneError("INVALID_WRITE")
        if z.wp + nlb > z.zslba + z.zcap:      # past zone capacity (status: confirm in spec)
            raise ZoneError("BOUNDARY")
        return self._do_write(z, nlb)

    def append(self, zslba, nlb):
        if zslba % self.zsze:
            raise ZoneError("INVALID_FIELD")
        z = self.zone(zslba)
        self._check_writable_state(z)
        if z.wp + nlb > z.zslba + z.zcap:
            raise ZoneError("BOUNDARY")
        return self._do_write(z, nlb)          # the LBA returned in CQE DW0-DW1

    def open_zone(self, zslba):
        z = self.zone(zslba)
        if z.state in (EMPTY, CLOSED):
            self._acquire_open(z)
        elif z.state not in (IOPEN, EOPEN):
            raise ZoneError("BAD_TRANS")
        z.state = EOPEN

    def close_zone(self, zslba):
        z = self.zone(zslba)
        if z.state in (IOPEN, EOPEN):
            z.state = EMPTY if z.wp == z.zslba else CLOSED
        elif z.state != CLOSED:
            raise ZoneError("BAD_TRANS")

    def finish_zone(self, zslba):
        z = self.zone(zslba)
        if z.state in (RONLY, OFFLINE):
            raise ZoneError("BAD_TRANS")
        z.state = FULL

    def reset_zone(self, zslba):
        z = self.zone(zslba)
        if z.state in (RONLY, OFFLINE):
            raise ZoneError("BAD_TRANS")
        z.state, z.wp = EMPTY, z.zslba

    def report(self):
        print(f"  open={self.n_open()}/{self.max_open} active={self.n_active()}/{self.max_active}")
        for i, z in enumerate(self.zones):
            wp = f"{z.wp:#06x}" if z.state in (EMPTY, IOPEN, EOPEN, CLOSED) else "  n/a "
            print(f"  zone {i}: ZSLBA={z.zslba:#06x} ZCAP={z.zcap} WP={wp} {z.state}")

def run(label, fn, *args):
    try:
        r = fn(*args)
        print(f"{label:40s} -> OK" + (f", LBA {r:#x}" if isinstance(r, int) else ""))
    except ZoneError as e:
        print(f"{label:40s} -> {e}")

if __name__ == "__main__":
    ns = ZonedNamespace(nzones=6, zsze=0x10, zcap=12, mor=1, mar=2)  # 2 open, 3 active
    run("WRITE  slba=0x00 nlb=4", ns.write, 0x00, 4)
    run("WRITE  slba=0x06 nlb=2 (not at WP)", ns.write, 0x06, 2)
    run("APPEND zslba=0x00 nlb=2", ns.append, 0x00, 2)
    run("APPEND zslba=0x00 nlb=2", ns.append, 0x00, 2)
    run("APPEND zslba=0x03 nlb=1 (not zone start)", ns.append, 0x03, 1)
    run("WRITE  slba=0x10 nlb=2 (zone 1)", ns.write, 0x10, 2)
    run("WRITE  slba=0x20 nlb=1 (zone 2)", ns.write, 0x20, 1)
    run("WRITE  slba=0x30 nlb=1 (zone 3)", ns.write, 0x30, 1)
    run("FINISH zone 0", ns.finish_zone, 0x00)
    run("WRITE  slba=0x30 nlb=1 (zone 3, retry)", ns.write, 0x30, 1)
    run("WRITE  slba=0x12 nlb=20 (crosses zone)", ns.write, 0x12, 20)
    run("APPEND zslba=0x00 nlb=1 (zone 0 full)", ns.append, 0x00, 1)
    run("OPEN   zone 4 (explicit)", ns.open_zone, 0x40)
    run("RESET  zone 0", ns.reset_zone, 0x00)
    ns.report()

Worked example

Problem. A logging service writes 64 KiB records to the lab's zoned namespace 2 (4 KiB blocks, ZSZE = 0x1_0000 blocks = 256 MiB, ZCAP = 0xD800 blocks = 216 MiB). ZNS Identify reports MOR = 13, MAR = 13, ZASL = 5, and CAP.MPSMIN = 0 (4 KiB). The service runs 32 writer threads. Design the write path. Synthetic example for teaching.

  1. Limits. MOR = MAR = 13 (0's based) → at most 14 open and 14 active zones.
  2. Append size. ZASL = 5 → 25 × 4 KiB = 128 KiB maximum per Zone Append. A 64 KiB record = 16 blocks, NLB field = 15. Fits.
  3. WRITE vs Zone Append. With WRITE, each zone allows one write in flight; 14 zones → at most 14 writes in flight, and the 32 threads queue behind per-zone locks. With Zone Append, all 32 threads can target, say, 4 open zones with many appends each in flight.
  4. Records per zone. 216 MiB / 64 KiB = 3,456 records per zone exactly (0xD800 / 16 = 3,456). The last append fills the zone; it transitions to Full and further appends fail with Zone Is Full — the service must move to a new zone on that status or by tracking remaining capacity.
  5. Metadata. Each completion's DW0–DW1 gives the record's LBA; the service writes an index entry (record ID → LBA) to a separate conventional namespace.
  6. Garbage collection. When records expire, the service copies live records out of the oldest zone (Zone Append into a fresh zone), updates the index, then sends Reset Zone. Active-zone budget: 4 writing zones + 1 GC destination + spare = 6 of 14.
  7. Unused capacity per zone. 256 MiB − 216 MiB = 40 MiB of LBA space per zone is never written. Capacity math must use ZCAP, not ZSZE: a 1 TB-class namespace with N zones offers N × 216 MiB.

Common mistakes

  • Using zone size as capacity. Writes beyond ZCAP fail; free-space math is wrong by 15% or more.
  • Queue depth > 1 WRITEs per zone. Works in testing (same CPU, same queue, idle device) and fails in production.
  • Ignoring the Zone Append result. Data is written but nobody knows where.
  • Closing zones to fix Too Many Active Zones. Closed is still active; finish or reset instead.
  • Treating MOR/MAR as 1's based or as "0 means zero zones".
  • Trusting a cached write pointer after a reset, error or power loss. Always re-report.
  • Reading WP of Full/Read Only/Offline zones. It is not valid.
  • Sending Zone Append larger than ZASL. Fails with Invalid Field even though the same size works for WRITE (MDTS).
  • Assuming a ZNS namespace can be used by any file system. ext4 and XFS (as of this writing) need a zone-aware layer such as dm-zoned, which itself has requirements; check versions.
  • Racing Reset Zone against in-flight I/O to the same zone.

The general method from Error Correlation applies with one ZNS-specific step: always take a zone report at the moment of failure. Without the device's view of the write pointer, every hypothesis is a guess.

Senior engineer insight

On a conventional SSD the host owns nothing but addresses; all state is inside the device. On ZNS, half of each zone's state machine — the write pointer, the open/active budget, the decision to finish or reset — must be mirrored in the host. Every ZNS bug is a disagreement between the two mirrors. Senior engineers therefore design for resynchronization: on any unexpected status, any reset, any timeout, the host re-reads the zone report and rebuilds its view before retrying.

A second insight: the open/active limits are the device's real parallelism budget. A host that uses fewer zones than MOR leaves bandwidth unused; one that uses more thrashes implicit closes. Treat MOR as a tuning parameter you measure against, not merely a limit you avoid.

Third: ZNS is valuable when the host software is already log-structured. Forcing a random-write workload onto ZNS through a translation layer usually rebuilds a worse FTL on the host. Ask "who will do garbage collection, and do they already?" before recommending ZNS.

Lab 59 — Drive the zone state machine on an emulated ZNS namespace

Objective

Create an emulated zoned namespace, observe every zone state and the write pointer, trigger Zone Invalid Write, Too Many Active Zones and Zone Is Full on purpose, and use Zone Append to see the device choose LBAs.

Skills

Reading ZNS Identify data; zone reports; reasoning from WP and state; mapping errors to the state machine; relating Linux sysfs to Identify fields.

Safety

Caution lab Run entirely inside a QEMU virtual machine against an emulated ZNS namespace backed by a scratch image file. Every step that writes or resets zones destroys data on that namespace; never point these commands at a real device you care about.

Hardware required

Any x86-64 Linux host able to run QEMU with KVM (or without, slowly).

Software required

QEMU with NVMe ZNS emulation (the nvme-ns device's zoned options); a Linux guest with nvme-cli and util-linux (blkzone); Python 3 with zone_report_decode.py.

Input

A 2 GiB raw image file; QEMU options such as (names version-dependent — check QEMU's NVMe documentation):

qemu-img create -f raw zns.img 2G
qemu-system-x86_64 ... \
  -drive file=zns.img,id=zns0,format=raw,if=none \
  -device nvme,serial=znslab01,id=nvme0 \
  -device nvme-ns,drive=zns0,bus=nvme0,nsid=1,logical_block_size=4096,physical_block_size=4096,\
zoned=true,zoned.zone_size=64M,zoned.zone_capacity=48M,zoned.max_open=4,zoned.max_active=6

Expected output

A log of each step's command, status and the relevant zone descriptors before and after, plus a hand-drawn path through the state machine that every zone you touched followed.

Background

This chapter's engineering explanation and zns_sim.py. Note that QEMU's options take absolute counts, whereas Identify reports 0's based MOR/MAR — so expect nvme zns id-ns to print 3 and 5.

Step 1 — identify

In the guest: sudo nvme zns id-ctrl /dev/nvme0, sudo nvme zns id-ns /dev/nvme0n1 -H, and the sysfs attributes from the Linux view. Record ZSZE, ZCAP, MOR, MAR, ZASL, chunk_sectors, max_open_zones, max_active_zones. Reconcile: 64 MiB / 512 = 131,072 sectors.

Step 2 — sequential writes and the write pointer

sudo nvme zns report-zones /dev/nvme0n1 -d 4. Then write 4 blocks at zone 0's start: sudo nvme write /dev/nvme0n1 -s 0 -c 3 -z 16384 -d /dev/urandom (NLB 0's based). Report again: zone 0 should be Implicitly Opened with WP = 4. Now write at LBA 10 (-s 10) and record the status. Write at LBA 4 and confirm success.

Step 3 — Zone Append

Run sudo nvme zns zone-append /dev/nvme0n1 -s 0 -z 8192 -d /dev/urandom three times; record the LBA each returns. Then try an append with -s 3 (not a zone start) and record the status.

Step 4 — limits

Write one block at the start of zones 1, 2, 3, 4, 5 (zone n starts at n × 16,384 blocks for 64 MiB zones of 4 KiB). After each, report with filter for implicitly opened and closed zones. Observe the implicit closes when you exceed 4 open zones and the Too Many Active Zones status when you try a seventh zone. Finish zone 0 (nvme zns finish-zone -s 0) and retry.

Step 5 — full and reset

Append to zone 0 (now Full) and record the status. Reset zone 0 (nvme zns reset-zone -s 0) and confirm Empty with WP = ZSLBA. Finally nvme zns reset-zone -a to reset all.

Observation

Note the exact error strings nvme-cli prints and the matching SCT/SC; check dmesg for kernel messages (there may be none for passthrough commands).

Questions

  3. Why did Finish, not Close, cure Too Many Active Zones?

Hint

Solution

Solution

Step 2: the write at LBA 10 fails with Zone Invalid Write (SCT 1h / SC BCh); the write at 4 succeeds; WP becomes 8. Step 3: appends of 8 KiB (2 blocks) return 8, 10, 12; WP becomes 14 (the question's "4 + 3 × 2" omits the Step 2 write — 8 + 6 = 14). The append with -s 3 fails with Invalid Field in Command. Step 4: with max_open=4, writing a fifth zone causes QEMU to close one implicitly opened zone (QEMU's choice; the specification leaves it to the controller); with max_active=6, the seventh distinct zone fails with Too Many Active Zones. Close would leave the zone active; Finish moves it to Full, freeing an active resource. Step 5: append to a Full zone fails with Zone Is Full; reset returns Empty, WP = ZSLBA.

zone_append_max_bytes is the kernel's per-command limit for appends, derived from ZASL (2ZASL × minimum page size), capped by the controller's MDTS and the driver's own limits.

What a senior engineer notices

Whether implicit closes happen exactly at MOR+1; whether QEMU (or a real device) returns DNR on zone errors, which tells the host whether retry is pointless; whether ZCAP is reported per zone consistently; whether a report taken during in-flight appends shows a WP between two completions.

Failure variants

  • Set zoned.zone_size to a non-power-of-two value: the kernel refuses the block device; only /dev/ng* appears.
  • Set zoned.zasl small and append more than the limit: Invalid Field.
  • Explicitly open MOR+1 zones: Too Many Open Zones, because the controller may not close explicitly opened zones.

Exercises

  1. ZSZE = 0x8_0000, LBA = 0x2_3456_7890. Which zone, and what is its ZSLBA?
  2. A zone has ZSLBA 0x40_0000, ZCAP 0x3_0000, WP 0x42_FFF0. What is the largest WRITE (in blocks) that can succeed, and what state results?
  3. Decode a zone descriptor whose bytes 0–3 are 02 40 04 00, bytes 8–15 are 00 D8 00 00 00 00 00 00, bytes 16–23 are 00 00 03 00 00 00 00 00 and bytes 24–31 are 00 08 03 00 00 00 00 00. What state is the zone in, and what does attribute value 04h ask of the host?
  4. MOR = 7, MAR = 11. How many zones may be Closed while 8 are open?
  5. Write CDW13 for Zone Management Receive: Extended Report Zones, filter Full zones, partial report.
Answers

1. 0x2_3456_7890 / 0x8_0000 = 0x468A (zone 18,058; the LBA shifted right by 19); ZSLBA = 0x468A × 0x8_0000 = 0x2_3450_0000.

2. Writable end = 0x40_0000 + 0x3_0000 − 1 = 0x42_FFFF; remaining = 0x43_0000 − 0x42_FFF0 = 0x10 = 16 blocks (NLB field 15). The zone becomes Full.

3. ZT = 2 (sequential write required); ZS byte 0x40 → state 4h Closed; ZA = 04h → bit 2 Reset Zone Recommended; ZCAP = 0xD800, ZSLBA = 0x3_0000, WP = 0x3_0800 (all little-endian), so 0x800 blocks are written. The device recommends the host reset this zone (after moving any live data out).

4. MOR = 7 → 8 open; MAR = 11 → 12 active. Open zones count as active, so 12 − 8 = 4 zones may be Closed.

5. ZRA = 1h (bits 7:0), filter = 5h (bits 15:8), Partial = bit 16 → 0x0001_0501.

Quiz

  1. A WRITE starts two blocks past the write pointer of an Implicitly Opened zone. Status?

    • Zone Boundary Error
    • Zone Invalid Write
    • LBA Out of Range
    • Success; the gap is zero-filled
    Answer and reasoning

    Writes must start exactly at the write pointer; anything else is Zone Invalid Write (SCT 1h, SC BCh). Boundary errors are for crossing zones.

  2. Which states count against Maximum Active Resources?

    • Implicitly and Explicitly Opened only
    • All except Empty
    • Implicitly Opened, Explicitly Opened and Closed
    • Closed and Full
    Answer and reasoning

    Active means partially written and holding device resources: the opened states plus Closed. Full, Empty, Read Only and Offline do not count.

  3. Where does a successful Zone Append report where the data landed?

    • Completion Dwords 0 and 1
    • The Changed Zone List log
    • CDW10–11 of the SQE, overwritten by the controller
    • It does not; the host must issue a zone report
    Answer and reasoning

    The controller returns the 64-bit LBA of the first block written in DW0–DW1 of the CQE. The SQE is never modified by the controller.

  4. A host hits Too Many Active Zones. Which action frees a resource?

    • Close Zone on an open zone
    • Open Zone on an empty zone
    • Report Zones
    • Finish Zone on a closed zone
    Answer and reasoning

    Finish moves a zone to Full, which is not active. Close only converts open to closed; still active.

  5. Which of these can the controller do on its own, without a host command?

    • Move an explicitly opened zone to Closed
    • Move an implicitly opened zone to Closed
    • Reset a Full zone
    • Move a Closed zone to Empty
    Answer and reasoning

    To free an open resource the controller may close an implicitly opened zone. It must not close explicitly opened zones, and it never discards data by resetting.

  6. Zone size 2 GiB, zone capacity 1,077 MiB. Why might a device do this?

    • To reserve space for host metadata
    • Because the specification requires capacity ≤ half the size
    • So zone size is a power of two while capacity matches the flash stripe
    • To support conventional zones
    Answer and reasoning

    Hosts (and Linux) want power-of-two zone sizes for shift arithmetic; the physical stripe holds 1,077 MiB. The difference is unwritable LBA space.

  7. Why does Zone Append exist if WRITE already works on zones?

    Model answer

    Because NVMe does not order commands, two WRITEs to a zone can execute out of order and the second-to-arrive fails. Hosts must therefore keep one WRITE per zone in flight. Zone Append lets the controller pick the LBA at the write pointer and return it, so many appends to one zone can be in flight at once, restoring parallelism.

  8. A trace shows a WRITE to the zoned namespace failing with SC BCh, and the zone report afterwards shows WP equal to the failed command's SLBA. What happened?

    Model answer

    At the time the controller validated the WRITE, WP was different (behind, because an earlier write had not yet been processed, or ahead/behind because of a reset). By the time of the report, WP had moved to that SLBA — typically because a reordered earlier WRITE completed. Classic reordering; retry would now succeed, but the fix is per-zone serialization or Zone Append.

  9. Name three things a validation engineer must test that do not exist for conventional namespaces.

    Model answer

    Every legal and illegal zone state transition (including Select All); behaviour exactly at MOR+1 and MAR+1 with mixes of implicit and explicit opens; Zone Append concurrency with correct, unique, contiguous returned LBAs and ZASL limits; opened-zone handling across reset and power loss; Read Only/Offline transitions and ZCAP shrink; report filters and partial reports.

Interview questions

  1. Beginner. What is a zone and what is a write pointer?

    Model answer

    A zone is a fixed-size LBA range in a zoned namespace that must be written sequentially and reset as a whole. The write pointer is the next LBA that may be written in that zone; it starts at the zone's first LBA and advances with each write.

  2. Beginner. Why can't you overwrite a block in a zone?

    Model answer

    Because the model mirrors flash, which programs pages in order and erases whole blocks. The only way to make space reusable is to reset the whole zone, after which writing restarts at the beginning.

  3. Intermediate. Explain the difference between open and active zones and why both limits exist.

    Model answer

    Open zones (implicitly or explicitly opened) are being written and need write buffers and parity state; active zones additionally include Closed zones, which are partially written and need metadata and partially programmed erase blocks. The device has finite buffer memory and power-loss protection (open limit) and finite partially-written-block tracking (active limit).

  4. Intermediate. How would you find, from a PCIe trace alone, where a Zone Append's data was written?

    Model answer

    Find the SQE fetch (device MRd of 64 bytes) and decode opcode 7Dh and CID; then find the CQE MWr to the matching CQ with that CID; DW0–DW1 of the CQE hold the first LBA. The SQE alone only names the zone start.

  5. Advanced. A RocksDB-on-ZNS deployment sees throughput collapse after weeks. Where do you look?

    Model answer

    Zone reports: count of Closed (active) zones, Finish/Reset Recommended attributes, ZCAP shrinkage, Read Only zones. Host side: GC efficiency (live data per zone at reset), whether the allocator leaks partially written zones, whether it hits the active limit and serializes. Device side: SMART and endurance. A common root cause is active-zone exhaustion forcing premature finishes and GC of mostly live zones.

  6. Senior. Should a cloud provider expose ZNS namespaces to tenant VMs?

    Model answer

    Only to tenants with zone-aware software, and with careful resource partitioning: MOR/MAR are per namespace and a tenant can exhaust them; resets are instant data destruction; the tenant must handle ZNS statuses. Many providers instead use ZNS internally beneath a log-structured storage service and expose conventional block devices to tenants, capturing the cost benefit without exporting the complexity. FDP is a competing option that keeps the block interface.

  7. Senior. Compare ZNS with Flexible Data Placement.

    Model answer

    ZNS changes the write contract: sequential writes, host-driven reset, new statuses, host GC. FDP keeps random writes and the conventional block interface but lets the host tag writes with placement handles so the device can segregate data with similar lifetimes, reducing write amplification without host GC. ZNS gives more control and the smallest device resources; FDP is far easier to adopt and degrades gracefully when hints are wrong.

Model explanation for the junior engineer

A zone only accepts a write at its write pointer. If you send two WRITEs — one at WP and one right after it — nothing in NVMe guarantees the controller handles them in the order you sent them; they might be in different queues or the controller might fetch them in any order. If the second one is checked first, it is not at WP yet, so it fails. You can avoid this by never having more than one WRITE to a zone in flight, but that is slow. Zone Append says "write this at whatever WP is when you get to it and tell me where" — so order no longer matters and you can send many at once.

Chapter summary

A zoned namespace (CSI 02h, ZNS Command Set 1.5) groups LBAs into fixed-size zones with per-zone capacity, a write pointer and a state: Empty, Implicitly Opened, Explicitly Opened, Closed, Full, Read Only, Offline. Writes must begin at the write pointer and stay inside the zone; zones are rewritten only after Reset Zone. Open and active zone counts are limited by MOR and MAR. Zone Append (7Dh) writes at the write pointer and returns the LBA in completion DW0–DW1, enabling concurrency that WRITE cannot safely have. Zone Management Send (79h) opens, closes, finishes, resets and offlines zones; Zone Management Receive (7Ah) reports them. ZNS errors are command statuses (SCT 1h, B8h–BFh) and are almost always disagreements between the host's mirror of zone state and the device's.
