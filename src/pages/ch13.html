A PCI Express (PCIe) requester can have many reads in flight at once, and their answers can come back in pieces and out of order. Tags are what make that safe. This chapter explains tag spaces (5-bit, 8-bit, 10-bit and larger), how outstanding requests are limited, how reads are split by the Max Read Request Size and how completions are split at the Read Completion Boundary — with worked examples and traces of several simultaneous reads.

Why this chapter exists

Chapter 12 showed that a device fetching data must keep many non-posted reads outstanding to hide latency: about 14 reads of 512 bytes for a Gen4 x4 link at 1 µs round trip, more at higher speeds. That immediately raises questions this chapter answers:

  • When eight completions arrive, how does the device know which read each one answers? (The Tag.)
  • How many reads may be outstanding? (Tag width, completion buffer space, flow-control credits.)
  • Why does one 4 KiB read become eight requests, and one 512-byte request become two, four or eight completions? (MRRS, MPS and the Read Completion Boundary.)
  • Why do completions arrive out of order, and when is that a bug?

These are everyday questions when you read NVMe traces: SQE fetches, PRP list fetches and WRITE data fetches from one SSD interleave, and only Tags let you untangle them.

Learning objectives

  • Explain why tags exist and state the Transaction ID uniqueness rule.
  • Describe tag-space sizes: default 5-bit, 8-bit with Extended Tag Field Enable, Phantom Functions, 10-bit tags, and wider tags in Flit Mode, with the registers that control each.
  • List what limits outstanding requests besides tags.
  • Split a large DMA read into requests by MRRS and the 4 KiB rule.
  • Split a read into legal completions by MPS and RCB, and compute Byte Count and Lower Address for each.
  • Read a trace with several simultaneous reads, match completions to requests and spot tag misuse.
  • Compute how many tags a link generation and width require.

The story

At a busy theatre, you hand your coat to the cloakroom and get a numbered ticket. Lots of people hand in coats, and the cloakroom attendants bring them back in whatever order they find them — not in the order people arrived. That is fine, because everyone has a ticket number. You only need the number to get your coat.

The library does the same. When it asks the teacher's classroom for eight different pages at once, it writes a different number on each question. Answers come back in any order, sometimes one page in two halves, and the library matches each answer to its question by the number. The library has only so many numbers. If it runs out, it has to wait until some answers come back before it can ask more questions. And it must never give out a number that is still in use — otherwise two answers would have the same number and it would put a page in the wrong place.

A restaurant with buzzing pagers. Each table order gets a pager number; the kitchen finishes orders in whatever order the dishes are ready and buzzes the right pager. A large order may come out in several trays, each labelled with the pager number and "2 of 3 trays remaining". The number of pagers on the counter limits how many orders can be in progress, and handing out a pager that is already buzzing for someone else would cause a mix-up.

  • The tag is not unique on its own. Uniqueness is per requester: Tag 0x21 from the SSD and Tag 0x21 from a GPU are different transactions because their Requester IDs differ. The cloakroom analogy has only one cloakroom per requester.
  • Trays of one order come out in order. Multiple completions for the same request are returned in increasing address order; only completions for different requests may be reordered. Coats could come in any order.
  • Pagers are the only limit in a restaurant. In PCIe, completion buffer space, the receiver's non-posted credits and the device's internal DMA contexts also limit outstanding reads, often before tags run out.
  • "2 of 3 trays" counts trays. Byte Count counts bytes remaining, not completions remaining; the number of completions is not announced in advance.

Beginner explanation

Every non-posted request carries an 8-bit Tag field (plus up to two extra bits with 10-bit tags). The requester picks a Tag that is not currently in use, sends the request, and remembers "Tag 0x40 = read of 512 bytes for buffer X at offset 0". When completions arrive, they carry the same Requester ID and Tag, so the requester looks up Tag 0x40, places the data, and when the last byte has arrived, frees Tag 0x40 for reuse.

Two size limits shape the traffic:

  • Max Read Request Size (MRRS) caps how many bytes one read request may ask for. In our example system it is 512 bytes, so a 4 KiB read becomes eight requests.
  • Max Payload Size (MPS) caps how many bytes one TLP may carry, including a completion. With MPS 256 bytes, a 512-byte read must come back as at least two completions.

And one alignment rule shapes how completions may be cut: the completer may only cut at Read Completion Boundary (RCB) boundaries — multiples of 64 or 128 bytes in the address space.

Engineering explanation

Why tags exist

PCIe reads are split transactions: request and completion are separate TLPs with arbitrary traffic between them. Without an identifier, a requester could have only one read outstanding (any completion would be "the" answer). Tags allow:

  • Multiple outstanding reads — the precondition for latency hiding.
  • Out-of-order completion — a completer may serve requests in whatever order is efficient (different memory channels, cache hits vs misses) and the requester still places every byte correctly.
  • Multiple completions per request — partial completions carry the same Tag; Byte Count and Lower Address place each piece.
  • Error attribution — an error completion or a timeout is tied to one specific request.

The uniqueness rule

The Transaction ID (Requester ID + Tag) of each outstanding non-posted request must be unique among all outstanding non-posted requests from that requester. A Tag may be reused only after the request has been completed (all completions received) or has failed (error completion or Completion Timeout). Normative in substance; see PCI Express Base Specification — Transaction Descriptor: Transaction ID.

Posted requests (memory writes, messages) carry a Tag field too, but it is not used for matching; it may be any value, and with TLP Processing Hints it can carry steering information instead. Do not track posted-request tags for uniqueness.

Tag width must be agreed by both ends and every switch in between. A requester that sends 10-bit tags to a completer that only supports 8-bit tags will receive completions with Tag[9:8] lost, which it sees as Unexpected Completions, and its real requests then time out. That is why system software enables 10-Bit Tag Requester only when the whole path supports it.

What limits outstanding requests

The tag space is a ceiling, rarely the actual limit. A requester can issue a new read only when all of these allow it:

  1. A free Tag.
  2. Completion buffer space reserved for the whole read's data (and headers). This is usually the real limit in endpoints: a device with 16 KiB of completion buffer and MRRS 512 can have at most 32 reads in flight, whatever its tag space.
  3. Non-posted flow-control credits at the link partner (one NP header credit per read request; reads carry no data so no NP data credits). If the Root Port advertises few NP header credits and is slow to return them, the device stalls (Chapter 16).
  4. DMA engine contexts and firmware policy: how many reads per command, per queue, per function.

Analyzers make this visible: count outstanding MRds at each moment. A flat ceiling (always exactly 32, or 24) tells you an internal limit; a ceiling that varies with NP credits at the Root Port tells you a link-partner limit.

Matching completions, and what "ordering" means here

  • Different requests: completions with different Transaction IDs may pass each other. A completion for Tag 0x45 arriving before one for Tag 0x41 is normal.
  • Same request: completions with the same Transaction ID must not pass each other, so the pieces of one read arrive in increasing address order. A requester can therefore place data with a running offset, and use Lower Address as a check.
  • Relative to posted writes: completions must not pass posted writes in the same direction except where Relaxed Ordering or ID-Based Ordering permits it — that is the subject of Chapter 14.

A requester's matching logic for each arriving completion: look up (Requester ID is its own) Tag → if absent, Unexpected Completion; if status is not SC, fail the request; otherwise check Lower Address against the expected next byte, copy the data, and if Byte Count equals the bytes carried, the request is complete and the Tag is freed.

Splitting reads: MRRS and the 4 KiB rule

A requester must split a DMA read into requests that each:

  • ask for at most MRRS bytes (Device Control: Max_Read_Request_Size; 128 B to 4096 B in powers of two);
  • do not cross a 4 KiB address boundary;
  • are expressed in DWs with byte enables for unaligned starts or ends.

Nothing requires the requester to use the maximum; some devices use smaller requests deliberately (for example, to align to RCB or to their own buffer granularity). Implementation-dependent

MRRS is a fairness and buffering control set by software. A completer serving a 4 KiB read occupies the completion path for ~4 KiB of data; other devices' completions queue behind it. Smaller MRRS gives finer interleaving between requesters at the cost of more request TLPs and more tags in flight. Platforms often choose MRRS for fairness, not for peak throughput of one device.

Splitting completions: MPS and the Read Completion Boundary

A completer may return a read's data in one completion or several. The rules (non-Flit, memory reads):

  1. No completion's payload may exceed the completer's MPS.
  2. Completions for one request are returned in increasing address order, with no gaps or overlaps; each starts where the previous one ended.
  3. When a read is completed with more than one completion, each completion other than the last must end on a naturally aligned RCB boundary. (So the first completion may start unaligned but must end at an RCB boundary; intermediate completions span whole RCB-aligned blocks — one or several; the last ends where the request ends.)
  4. RCB values: a Root Complex has an RCB of 64 or 128 bytes; it is reported to software and mirrored by system software into the Read Completion Boundary bit of downstream devices' Link Control registers so the device knows what to expect. Other completers (endpoints, switches acting as completers) use 128 bytes. Confirm these in the PCI Express Base Specification — Read Completion Boundary section of your revision.
  5. Byte Count in each completion = bytes remaining including this one; Lower Address = low 7 bits of the address of this completion's first byte.

Notice in split B that the second and third completions both have Lower Address 0x40: address 0x0C0 & 0x7F = 0x40. Lower Address alone is ambiguous over a 128-byte window; the requester resolves it with Byte Count (and its own running offset).

The central concept on the ladder

Cloakroom tickets: each question gets a number not in use; answers come back in any order with the number on them; when your number's answer is complete, the number goes back in the bowl.

Tag + Requester ID = Transaction ID, unique among a requester's outstanding non-posted requests. Reads ≤ MRRS, no 4 KiB crossing; completions ≤ MPS, split only at RCB boundaries, in address order per request.

The device has a tag table (state per tag: buffer, offset, bytes remaining, timer), a completion buffer reserved per request, and NP credit counters for its link partner. The Root Complex has its own policy for splitting completions (often at cache-line or RCB granularity).

Tag width capability/enable bits live in Device Capabilities/Control and Device Capabilities 2/Control 2; MRRS and MPS in Device Control; RCB in Link Control. The specification defines the uniqueness, splitting and ordering rules.

MRd(Tag t) → one or more CplD(Tag t) with decreasing Byte Count; different tags' completions interleave freely.

In a trace, group rows by Tag: each group should be one MRd followed by CplDs whose bytes add up to the request and whose Byte Count steps down to the last piece. Count outstanding tags over time to see the device's concurrency.

Tag reuse before completion, missing pieces, an illegal split, or 10-bit tags through a non-supporting path produce unexpected completions, timeouts or silent corruption. A flat outstanding-tag ceiling explains a throughput cap.

Hardware view

  • Tag table size is a silicon cost (state per entry, timers), which is why devices do not simply implement 1024 entries.
  • Completion buffer must hold the data for every outstanding read; at 32 × 512 B that is 16 KiB of SRAM.
  • Root Complex splitting policy is often tied to its internal cache-line size (64 B) and memory interleaving; some return MPS-sized completions, others return many 64-byte completions. Both are legal; the latter costs more completion headers on the link. Implementation-dependent
  • Switches route completions by Requester ID and do not track Tags. They also do not merge or split completions.

Specification view

Tags, the Transaction ID and the request/completion splitting rules are in the PCI Express Base Specification, Revision 6.x/7.0 — Transaction Layer Specification (Transaction Descriptor; Memory Request rules; Completion Rules; Read Completion Boundary). Enables and capabilities are in the PCI Express Capability structure (Device Capabilities/Control, Device Capabilities 2/Control 2, Link Control).

  • Requester ID + Tag form the Transaction ID, unique among outstanding non-posted requests of a requester.
  • Default Tag usage is 5 bits; Extended Tag Field Enable allows 8 bits; Phantom Functions extend the space via unused Function Number bits; 10-bit tags are capability-negotiated (Revision 4.0+).
  • Read requests must not exceed MRRS and must not cross a 4 KiB boundary; completions must not exceed MPS.
  • Multiple completions for one request return in increasing address order; partial completions (other than the last) end on naturally aligned RCB boundaries; RCB is 64 or 128 bytes for a Root Complex.
  • Completions with different Transaction IDs may be reordered relative to each other.
  • All splitting examples, tag-requirement tables and the outstanding-request limits from buffer sizes are computed for the synthetic example system.
  • Tag allocation order (sequential, round-robin, lowest free), and how many tags a device actually uses.
  • Root Complex completion split policy and RCB choice (64 vs 128).
  • Device request sizes below MRRS.
  • 10-bit tags (Revision 4.0+), Flit Mode 14-bit tags (Revision 6.0+).
  • The default value of Extended Tag Field Enable changed over revisions.

Check in the specification: the precise 10-bit tag value restrictions and the rules for using 10-bit tags toward completers that do not support them; the exact RCB rule wording including the multiple-of-RCB case; whether RCB applies to completions from endpoints and switches and with which value; Phantom Function requirements. The NVMe specifications say nothing about tags; how an NVMe controller allocates them is its own design.

  • Never assume completions return in request order.
  • Never assume one completion per request.
  • Never infer the request address from Lower Address alone.

Protocol view

All three requests are outstanding at once; completions for different tags interleave; each tag's two pieces are in order with Byte Count 512 then 256.

Walk-through. Every TLP here is individually well-formed; the bug is only visible by tracking state per tag. Row 2's Byte Count (512) with 256 bytes carried says the request is not finished; row 3 reuses the tag 10 ns later. The host's Root Complex is not required to detect duplicate Transaction IDs, so it happily serves both. Symptoms downstream are a data-integrity failure on one of two unrelated commands, or an AER Unexpected Completion at the SSD followed by a failed command — symptoms that point nowhere near the cause unless you track tags. The likely root cause is a tag-free race (freeing on the first completion, or on Byte Count misread) in the device's DMA logic. Synthetic example for teaching.

Code / pseudocode

An executable model of MRRS request splitting, RCB completion splitting, and a completion-stream checker that catches illegal splits and tag misuse. Standard library only.

#!/usr/bin/env python3
"""Split DMA reads into requests (MRRS, 4 KiB) and requests into completions (MPS, RCB),
then check a completion stream against the rules. Synthetic teaching model."""

def split_requests(addr, nbytes, mrrs):
    out = []
    while nbytes > 0:
        n = min(nbytes, mrrs, 4096 - (addr % 4096))
        out.append((addr, n))
        addr, nbytes = addr + n, nbytes - n
    return out

def split_completions(addr, nbytes, mps, rcb, policy="max"):
    """policy 'max': largest legal pieces; 'rcb': cut at every RCB boundary."""
    out, remaining = [], nbytes
    while remaining > 0:
        if policy == "rcb":
            end = min(addr + remaining, (addr // rcb + 1) * rcb)
        else:
            end = addr + min(remaining, mps)
            if end < addr + remaining:          # not the last piece: cut back to an RCB boundary
                end = (end // rcb) * rcb
                if end <= addr:
                    end = min(addr + remaining, (addr // rcb + 1) * rcb)
        n = end - addr
        out.append(dict(addr=addr, nbytes=n, byte_count=remaining, lower=addr & 0x7F))
        addr, remaining = end, remaining - n
    return out

def check(requests, completions, mps, rcb):
    """requests: {tag: (addr, nbytes)}; completions: list of dicts with tag, addr, nbytes, byte_count."""
    state = {t: dict(next=a, left=n) for t, (a, n) in requests.items()}
    problems = []
    for i, c in enumerate(completions, 1):
        s = state.get(c["tag"])
        if s is None:
            problems.append(f"#{i}: Unexpected Completion, tag {c['tag']:#x} not outstanding")
            continue
        if c["nbytes"] > mps:
            problems.append(f"#{i}: payload {c['nbytes']} > MPS {mps}")
        if c["addr"] != s["next"]:
            problems.append(f"#{i}: tag {c['tag']:#x} starts at {c['addr']:#x}, expected {s['next']:#x}")
        if c["byte_count"] != s["left"]:
            problems.append(f"#{i}: tag {c['tag']:#x} Byte Count {c['byte_count']} != remaining {s['left']}")
        end = c["addr"] + c["nbytes"]
        last = c["nbytes"] == s["left"]
        if not last and end % rcb:
            problems.append(f"#{i}: tag {c['tag']:#x} partial completion ends at {end:#x}, not on {rcb}-byte RCB")
        s["next"], s["left"] = end, s["left"] - c["nbytes"]
        if s["left"] <= 0:
            del state[c["tag"]]                   # tag free for reuse
    for t, s in state.items():
        problems.append(f"tag {t:#x}: {s['left']} bytes never completed (timeout pending)")
    return problems

Worked example

Tag budget for a mixed workload

The Lab SSD (Gen4 x4, 8-bit tags enabled) runs a 70/30 read/write mix at 6 GB/s total. Reads (host perspective) need no device read tags except SQE fetches; writes need data reads. Assume read round trip 1.2 µs, MRRS 512 B, and one 64-byte SQE fetch per command with 4 KiB commands.

  1. Write data rate = 0.3 × 6 GB/s = 1.8 GB/s → outstanding bytes = 1.8 × 109 × 1.2 × 10−6 ≈ 2,160 B → ≈ 5 data reads outstanding on average.
  2. Command rate = 6 GB/s ÷ 4 KiB ≈ 1.46 M commands/s → SQE fetches outstanding ≈ 1.46 × 106 × 1.2 × 10−6 ≈ 1.8 (fewer if the device batches SQE fetches as in the normal trace).
  3. Average outstanding ≈ 7 tags. Bursts (a queue of large WRITEs arriving together) can momentarily want 14+ (the Gen4 saturation figure). 256 tags are ample; 32 would be too, here — but not for a pure-write workload at higher latency.

Lesson: average tag use is low; peak tag use during write bursts with high latency is what limits throughput. Measure outstanding-tag histograms in traces, not averages. Derived

Common mistakes

  • "Tag 0x21 means the same request everywhere." Only together with the Requester ID.
  • Freeing a tag on the first completion. The tag is busy until Byte Count equals the bytes carried in a completion (the last one).
  • Treating out-of-order completions across tags as an error. It is legal and common.
  • Expecting MRRS-sized completions. Completions are bounded by MPS and cut at RCB; MRRS bounds requests.
  • Forgetting the 4 KiB rule when predicting request sizes for unaligned buffers.
  • Assuming 10-bit tags are on because the device supports them. Check the requester enable and the whole path.
  • Assuming Lower Address increments per completion. It wraps every 128 bytes.

Senior engineer insight

Plot "outstanding non-posted requests vs time" for every capture you study. It is the single most informative performance graph for a PCIe requester: a sawtooth that hits a flat ceiling is a resource limit; a graph that drops to zero between bursts is a device that is not pipelining; a slowly rising floor is a tag leak.

If an error path forgets to free a tag (for example after a UR completion), the device loses one tag per error. Throughput degrades gradually over hours and recovers on reset. When a "performance problem" correlates with uptime and disappears after a controller reset, count usable tags in a late trace.

Hints

Hint 1

0x1000 − 0xE10 = 0x1F0.

Hint 2

0x0E10 + 48 = 0x0E40, which is a multiple of 64.

Solution

Solution

Step 1: R1 0x0E10, 496 B (stops at 4 KiB boundary 0x1000); R2 0x1000, 512; R3 0x1200, 512; R4 0x1400, 480 (total 496 + 512 + 512 + 480 = 2,000).

Step 2: "max": [0xE10+240 BC 496 LA 0x10] (0xE10 + 256 = 0xF10, cut back to RCB 0xF00 → 240 B), then [0xF00+256 BC 256 LA 0x00]. Check: 240 + 256 = 496 ✔. "rcb": [0xE10+48 BC 496 LA 0x10], then seven 64-byte pieces from 0xE40 to 0xFFF with BC 448, 384, 320, 256, 192, 128 and 64 (48 + 7 × 64 = 496 ✔).

Step 3: Completions 1–5 are legal: tag 0x60 gets 48 (ends on 0xE40), 256 (ends on 0xF40, RCB-aligned), 192 (last; 48 + 256 + 192 = 496, BC steps 496 → 448 → 192 ✔); tag 0x61 gets 256 + 256 with BC 512 → 256 ✔. Completion 6 repeats tag 0x61's last piece after the tag was freed → Unexpected Completion. Q1: the 4 KiB boundary. Q2: legal — a first piece ending on an RCB boundary; 48 B because 0xE40 is the first 64-byte boundary. Q3: duplicate/late completion for a retired tag. Observation: a requester reports completion 6 (Unexpected Completion) and would report a Malformed TLP for size/boundary violations if it checks them; a requester that does not track Byte Count could silently accept a duplicate into a newly reused tag's buffer — silent corruption.

What a senior engineer notices

The legal stream mixes a 48-byte, a 256-byte and a 192-byte completion for one tag. Variable-size completions are normal; checkers must validate rules, not expected sizes. A test bench that hard-codes "two 256-byte completions per 512-byte read" will reject legal Root Complexes.

Failure variants

  • Make completion 3 carry 272 bytes: MPS violation.
  • Make completion 3 end at 0x0F50: RCB violation.
  • Swap completions 3 and 5: same-tag reordering — forbidden.

Extension

Add a tag allocator and generate random legal streams with random interleaving across tags; feed them to the checker as a self-test (it must report nothing).

Exercises

  1. How many read requests (MRRS 256) does a 64 KiB transfer starting at 0x…0F00 need?
  2. A Root Complex with RCB 128 B answers a 512-byte read at 0x…1040 with MPS 256. Give the largest-piece legal split.
  3. Why might a device choose 256-byte requests even when MRRS is 512?
  4. Two functions of a multi-function SSD both use Tag 0x05 at the same time. Is that a problem?
  5. Estimate the tags needed for a Gen5 x8 accelerator with 3 µs read latency at full rate (MRRS 512).
Model answers
  1. First request 256 B (0xF00–0xFFF, fits before the 4 KiB boundary), then (65,536 − 256) / 256 = 255 more → 256 requests. Every request is 256 B because 0xF00 is 256-aligned.
  2. From 0x1040: first piece may be at most 256 B → would end at 0x1140; cut back to a 128 B boundary → 0x1100: 192 B (BC 512, LA 0x40). Next: 0x1100 + 256 = 0x1200: 256 B (BC 320, LA 0x00) — ends on a 128 B boundary ✔. Last: 0x1200–0x123F: 64 B (BC 64, LA 0x00). Total 192 + 256 + 64 = 512 ✔.
  3. To match completion buffer granularity, to keep more requests in flight for fairness across queues, to align with MPS so each request completes in one CplD (less reassembly state), or to reduce head-of-line blocking at the Root Complex.
  4. No. Their Requester IDs differ (different function numbers), so the Transaction IDs are distinct.
  5. Gen5 x8 ≈ 31.5 GB/s raw, ≈ 28.4 GB/s payload; × 3 µs ≈ 85 kB; / 512 ≈ 167 tags. 8-bit tags suffice on paper but leave little headroom; 10-bit tags (or larger MRRS) become attractive.

Quiz

  1. What makes a Transaction ID?

    • Tag alone
    • Requester ID + Tag
    • Completer ID + Tag
    • Address + Tag
    Answer and reasoning

    Requester ID + Tag; the completer copies both.

  2. Without Extended Tag Field Enable, how many tags may a function use by default?

    • 32
    • 256
    • 1024
    • 16
    Answer and reasoning

    The default uses 5 bits (32 values).

  3. Which limits the size of a single completion?

    • MRRS
    • RCB
    • MPS
    • The Tag width
    Answer and reasoning

    MPS bounds every TLP payload, completions included. RCB constrains where splits may occur, not size.

  4. Completions for tags 0x41 and 0x40 arrive in the order 0x41, 0x40. Is this legal?

    • Yes; different Transaction IDs may pass each other
    • No; completions must return in request order
    • Only with Relaxed Ordering
    Answer and reasoning

    Completions with different Transaction IDs may be reordered.

  5. A completion has Byte Count 192 and carries 64 bytes. What does the requester expect next for that tag?

    • Nothing
    • 128 more bytes in one or more completions
    • A new request
    Answer and reasoning

    192 remaining including this 64 → 128 to come.

  6. With RCB 64, which partial completion end address is legal for a request that continues beyond it?

    • 0x…1050
    • 0x…1070
    • 0x…1080
    • 0x…1090
    Answer and reasoning

    0x1080 is a multiple of 64; the others are not.

  7. Why do Byte Count and Lower Address together suffice to place completion data?

    Model answer

    The requester knows each tag's request address and size; Byte Count tells how far into the request this piece starts (size − Byte Count), and Lower Address cross-checks the low 7 bits. Same-tag completions arrive in order, so a running offset works.

  8. Name three resources besides tags that limit outstanding reads.

    Model answer

    Completion buffer space reserved per read; non-posted header credits at the link partner; DMA engine contexts/firmware policy (also MRRS indirectly through bytes per tag).

  9. What symptom would 10-bit tags through a non-supporting path produce?

    Model answer

    Completions with Tag[9:8] lost or not matching → Unexpected Completions at the requester, and the original requests time out (Completion Timeout).

Interview questions

  1. (Beginner) Why do PCIe reads need tags?

    Model answer

    Reads are split transactions; with many in flight and completions returning out of order and in pieces, the requester needs an identifier to match each completion to its request.

  2. (Beginner) What is MRRS, and how is it different from MPS?

    Model answer

    MRRS caps the bytes requested by one read request; MPS caps the payload of any TLP (writes and completions). A 512-byte request with MPS 256 needs at least two completions.

  3. (Intermediate) Explain the Read Completion Boundary.

    Model answer

    When a completer splits a read into several completions, non-final pieces must end on naturally aligned RCB boundaries (64 or 128 B for a Root Complex, 128 B for others). It keeps splits predictable and aligned to cache lines, simplifying reassembly.

  4. (Intermediate) How do you compute the number of tags needed?

    Model answer

    Little's Law: bytes outstanding = rate × round-trip latency; divide by bytes per request (MRRS or actual request size); add headroom for bursts and latency variance.

  5. (Advanced) A device shows throughput dropping slowly over days; reset fixes it. What is your theory?

    Model answer

    A tag (or completion buffer) leak on an error or timeout path. Verify by plotting maximum outstanding requests in traces early vs late; look for error events correlating with each step down.

  6. (Advanced) What does a Root Complex gain by returning 64-byte completions instead of MPS-sized ones?

    Model answer

    It can return each cache line as soon as it is available from memory/coherency logic, reducing latency to first data and buffering inside the Root Complex; the cost is more completion headers (lower link efficiency) and more reassembly work at the requester.

  7. (Senior) How would you verify a new SSD's DMA engine handles every legal completion split?

    Model answer

    Use an exerciser or a programmable Root Complex model to return completions with all legal split patterns (single, RCB-granular, mixed sizes, interleaved across tags, maximal reordering across tags), unaligned starts and 4 KiB-adjacent requests, plus illegal ones for error handling; check data integrity per byte and error reporting.

  8. (Senior) When would you recommend enabling 10-bit tags, and what would you check first?

    Model answer

    When Little's Law shows more than ~256 outstanding requests are needed (wide Gen5/Gen6 links, high latency, peer-to-peer through switches). First check 10-bit completer support at every completer, routing support in switches, and that the requester's enable is the only change; then validate with traces for Tag[9:8] integrity.

Child: "Each coat gets a ticket number. If two people had the same number at the same time, one might get the other's coat. So you only reuse a number after its coat has been collected."

Junior: "Requests are limited to 512 bytes and can't cross a 4 KiB boundary, so the first one stopped at 0x1000 after 128 bytes, then 512, 512 and the remaining 348. Completions are limited to 256 bytes, so each 512-byte request came back in two pieces, the 348-byte one in 256 + 92, and the 128-byte one in one piece: seven."

Senior: "Both raise outstanding bytes. Raising MRRS is a configuration change with fairness costs for other devices on the same Root Port and larger head-of-line blocking; 10-bit tags need end-to-end support and more device state but keep request granularity small. Measure: if tags are the ceiling and the platform supports 10-bit, prefer that; if completion buffer or NP credits are the ceiling, neither helps."

Chapter summary

Tags turn split transactions into a pipeline. The Transaction ID (Requester ID + Tag) must be unique among outstanding non-posted requests; tag space is 32 by default, 256 with Extended Tags, more with Phantom Functions, 10-bit tags and Flit Mode. Outstanding reads are also bounded by completion buffer space, NP credits and DMA contexts. Requests are split by MRRS and the 4 KiB rule; completions by MPS and at RCB boundaries, in address order per tag but freely interleaved across tags; Byte Count and Lower Address place each piece.

Do not move on until you can:

  • state the Transaction ID uniqueness rule and when a tag may be reused
  • name every tag-space mode and its enable register
  • split a buffer into requests and a request into legal completions with Byte Count and Lower Address
  • untangle several simultaneous reads in a trace by tag
  • spot tag reuse, illegal splits and unexpected completions
  • compute tags needed for a link and latency
