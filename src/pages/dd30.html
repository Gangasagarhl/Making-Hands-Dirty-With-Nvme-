This module pushes the Read to its limits: maximum-size transfers with PRP lists that chain, concurrent reads interleaving on the link, the arithmetic of link-limited throughput, latency tails decomposed stage by stage, and every way a Read can fail or succeed with the wrong data.

Orientation

A Read is the most frequent command in almost every NVMe trace, and the one whose failures hurt most: a failed Write can be retried from the host's copy, but a Read that returns wrong data, or returns late, goes straight to the application. The happy path is in Chapter 32. Here we cover the cases that appear in incident reviews: reads at MDTS, reads whose descriptor structures span pages, reads whose data arrives partially, reads that take milliseconds without an error, and reads that are "too fast to be true".

You need the Read SQE fields (SLBA, NLB, FUA, LR, PRINFO, DSM hints), the 4 KiB read trace and the latency budget from Chapter 32 — READ, and the end-to-end correlation method from Chapter 39 — The Most Important Chapter. PRP rules are in Chapter 36; MPS and TLP shaping in Module 11.

Kid story

You ask the library for a big set of books. You give them a card that says where your first shelf is at home and, because the set is big, a second card that is a list of all your other shelves. The library staff gather the books from many storerooms at once, and a van brings them in small boxes, each box labelled with which shelf it goes on. Boxes for your neighbour's order travel in the same van, mixed with yours.

When the last box for your order is delivered, the driver rings your doorbell to say "your order is complete". Usually that takes a few minutes. Sometimes one book is in a dusty corner and takes ages to find, even though nothing is wrong. Occasionally the shelf list sends the van to an address that doesn't exist, and the delivery stops halfway.

Analogy boundary

What it represents. The first card is PRP1; the list card is a PRP list reached through PRP2; storerooms are NAND dies read in parallel; small labelled boxes are MWr TLPs of at most MPS bytes with a target address; the neighbour's boxes are data TLPs of other Reads; the doorbell ring at the end is the CQE followed by the MSI-X interrupt; the dusty corner is read retry; the bad address is a PRP entry the IOMMU does not map.

What it hides. The van is not one-way: the device also reads the list card from host memory (MRd and CplD) before it can deliver. Boxes may be delivered in any order within an order; only the doorbell ring is ordered after them, and only under the default ordering rules. The library can also hand you an empty box without visiting any storeroom (deallocated blocks).

Where it misleads. A half-finished delivery in the story leaves you knowing which books arrived; in NVMe a failed Read leaves the buffer in an undefined state, and the host must treat all of it as invalid. And a van that "rings first, delivers later" sounds absurd — but with Relaxed Ordering on the wrong TLP, the platform can let the completion overtake the data.

Mechanism

A 128 KiB Read (NLB 255 on 512-byte LBAs) on SQ1, concurrent with a 4 KiB Read on SQ2. Reference lab system; synthetic.

  1. Map and describe. Who: driver. What: maps 32 buffer pages (IOVAs 0x2_0010_0000–0x2_0011_F000); PRP1 = first page; 31 entries in a list page at 0x1_5000_0000; PRP2 = list address. Evidence: SQE and list contents.
  2. Submit. Who: driver. What: SQE in slot 160, doorbell 161. Evidence: MWr32 to 0xFE60_1008.
  3. Fetch command and list. Who: controller. What: MRd for the SQE, then MRd of 248 bytes for the list. Evidence: two MRd/CplD pairs; a controller may fetch the list later or in pieces.
  4. Read media in parallel. Who: FTL and dies. What: 32 logical pages spread over several dies read concurrently; ECC corrects each. Evidence: only the gap before data.
  5. Deliver data. Who: DMA engine. What: 512 MWr of 256 bytes, in bursts as dies finish; the concurrent Read's TLPs interleave. Evidence: MWr addresses in two disjoint ranges.
  6. Complete. Who: controller. What: CQE after the last data TLP; MSI-X. Evidence: MWr to CQ1, MWr32 to 0xFEE0_1000.
  7. Finish. Who: driver. What: consume CQE, unmap pages and list, complete the request. Evidence: tracepoints; CQ head doorbell.

The central concept on the ladder: a Read is a contract that data precedes completion

All boxes are delivered before the doorbell rings; if the doorbell says "problem", treat everything as missing.

The device writes the data into host buffers, then writes a completion. Success means the whole range arrived; failure means none of it may be trusted.

Descriptors (PRP1, PRP2, lists) tell the DMA engine where each page goes; the engine emits MPS-bounded writes in any order, then the CQE, relying on posted-write ordering.

NVM Command Set 1.3 defines the Read; Base 2.4 the CQE and generic status; NVMe over PCIe 1.4 the PRP rules; PCIe Base the ordering rules (posted writes do not pass posted writes unless Relaxed Ordering is set).

MRd/CplD for SQE and lists, then MWr data, then MWr CQE, then MWr32 MSI-X, all with Requester ID 0x0100.

For each Read: data address range = union of PRP pages; count bytes; confirm the CQE follows the last data TLP; check RO attributes.

"Wrong data" → was all data written before the CQE (ordering, RO)? to the right addresses (PRP, IOMMU)? from the right LBAs (SQE)? with correct content (PI, media)?

Link-limited throughput on the reference link (derived): Gen4 is 16 GT/s per lane with 128b/130b encoding, so x4 carries about 7.88 GB/s. Each 256-byte data TLP costs about 280 bytes on the wire (4 bytes framing and sequence, 16-byte header for 64-bit addresses, 4-byte LCRC), so data efficiency is 256/280 ≈ 0.914 and the ceiling is about 7.2 GB/s before DLLP traffic (ACKs, flow-control updates), which takes a few percent more. With MPS 128 the efficiency drops to 128/152 ≈ 0.84.

Ordering: data MWrs and the CQE MWr travel in the same direction from the same requester; without Relaxed Ordering, the CQE cannot pass them, so a host that sees the CQE also sees the data. A controller may set Relaxed Ordering on data TLPs (when enabled in Device Control) to let the platform write them faster, but must not set it on the CQE. If it does, or if a platform bug reorders writes, the host may read the buffer before the data lands — the senior lab's scenario.

Interleaving: concurrent Reads produce data TLPs from the same Requester ID; attribute them by address range (each Read owns its PRP pages), not by position. Tags do not help: posted writes carry tags that the receiver does not use for matching.

Data errors in mid-transfer: if a list fetch or data write fails, the controller completes the Read with an error status after an unpredictable amount of data has been written. The status, not the data, is authoritative.

Objective

Setup

Buffer pages are consecutive from 0x2_0010_0000; list pages from 0x1_5000_0000. Cases: (1) 4 KiB, offset 0; (2) 8 KiB, offset 0; (3) 6 KiB, offset 0xC00; (4) 128 KiB, offset 0x80.

Procedure

  1. Count pages touched.
  2. Choose PRP2: zero, second page, or list pointer.
  3. Count list entries.
  4. Count data TLPs at MPS 256.

Observations

Your table.

Questions

  1. Why does a 6 KiB read need a list?
  2. Why does case (4) have 513 TLPs instead of 512?

Expected reasoning

Pages touched, not bytes, decide the PRP form; boundaries split TLPs.

Solution

(1) 1 page: PRP1 = 0x2_0010_0000, PRP2 unused; 16 TLPs. (2) 2 pages: PRP2 = 0x2_0010_1000; 32 TLPs. (3) 0xC00 + 6 KiB spans 3 pages (1 KiB + 4 KiB + 1 KiB): PRP1 = 0x2_0010_0C00, PRP2 = list with 2 entries; 24 TLPs. (4) 33 pages: PRP1 = 0x2_0010_0080, list of 32 entries; the first page holds 3,968 bytes: 15 TLPs of 256 then one of 128 to reach the boundary; 31 full pages × 16; last page 128 bytes in one TLP: 16 + 496 + 1 = 513. The intermediate lab's script prints the same results.

Extension

Redo case (4) with the list at 0x1_5000_0FC0 and draw the chain.

# read_tlps.py - PRP layout, data-TLP shaping and reassembly for one NVMe Read (synthetic model).
PAGE, MPS, ENTRY = 4096, 256, 8

def prp_layout(buf_pages, offset, length, list_addr):
    """buf_pages: page-aligned host pages. Returns PRP1, PRP2 and list pages {addr: [entries]}."""
    first = PAGE - offset
    npages = 1 + max(0, -(-(length - first) // PAGE))
    prp1 = buf_pages[0] + offset
    if npages == 1:
        return prp1, 0, {}
    if npages == 2:
        return prp1, buf_pages[1], {}
    rest, lists, addr = list(buf_pages[1:npages]), {}, list_addr
    while rest:
        room = (PAGE - addr % PAGE) // ENTRY          # entries left in this list page
        if len(rest) <= room:
            lists[addr] = rest; rest = []
        else:                                         # last slot chains to the next list page
            nxt = (addr // PAGE + 7) * PAGE           # illustrative: next list page 7 pages on
            lists[addr] = rest[:room - 1] + [nxt]; rest = rest[room - 1:]; addr = nxt
    return prp1, list_addr, lists

def data_tlps(buf_pages, offset, length):
    """Device-to-host MWr TLPs: at most MPS bytes, never crossing a 4 KiB boundary."""
    tlps, done, i, off = [], 0, 0, offset
    while done < length:
        n = min(MPS, PAGE - off, length - done)
        tlps.append((buf_pages[i] + off, n)); done += n; off += n
        if off == PAGE:
            i, off = i + 1, 0
    return tlps

def overhead_rate(tlps, raw_gbs=16 * 4 * 128 / 130 / 8):
    wire = sum(n + 24 for _, n in tlps)                # 4 B framing+seq, 16 B 4DW header, 4 B LCRC
    payload = sum(n for _, n in tlps)
    return payload / wire, raw_gbs * payload / wire

pages = [0x2_0010_0000 + k * PAGE for k in range(40)]
for name, off, ln, la in [("128 KiB aligned", 0, 128 * 1024, 0x1_5000_0000),
                          ("128 KiB, offset 0x80", 0x80, 128 * 1024, 0x1_5000_0000),
                          ("128 KiB, list at page end", 0, 128 * 1024, 0x1_5000_0FC0),
                          ("6 KiB, offset 0xC00", 0xC00, 6 * 1024, 0x1_5000_0000)]:
    prp1, prp2, lists = prp_layout(pages, off, ln, la)
    t = data_tlps(pages, off, ln)
    eff, rate = overhead_rate(t)
    print("%-26s PRP1=0x%s PRP2=0x%s" % (name, format(prp1, "_x"), format(prp2, "_x")))
    for a, e in lists.items():
        print("%28s list page 0x%s: %d entries, last=0x%s" % ("", format(a, "_x"), len(e), format(e[-1], "_x")))
    sizes = sorted(set(n for _, n in t))
    print("%28s %d MWr TLPs, sizes %s, efficiency %.3f, link-limited %.2f GB/s" % ("", len(t), sizes, eff, rate))

# Reassembly check: every byte written exactly once, in buffer order.
t = data_tlps(pages, 0x80, 128 * 1024)
cover = sum(n for _, n in t)
contig = all(t[k][0] + t[k][1] == t[k + 1][0] for k in range(len(t) - 1) if (t[k][0] + t[k][1]) % PAGE)
print("reassembly: %d bytes, contiguous within pages: %s" % (cover, contig))

Questions

  1. Why does efficiency not change with the offset?
  2. What is the theoretical 128 KiB transfer time at MPS 256?
  3. Why can measured throughput still be far below 7.2 GB/s?

Expected reasoning

Efficiency depends on TLP size distribution; throughput also depends on concurrency and media.

Solution

(1) It does change slightly (one 128-byte TLP adds overhead) but rounds to the same three digits. (2) 512 × 280 B / 7.88 GB/s ≈ 18.2 µs. (3) Not enough Reads in flight to keep dies busy, DLLP overhead, IOMMU translation misses, device pacing, root-complex write bandwidth, or MPS below 256. The link ceiling is reached only when media parallelism exceeds it.

Advanced lab — Decompose the latency tail

Safe lab Pure software.

Objective

Show which stage owns each percentile.

Prerequisites

Latency budget in Chapter 32.

Setup

# lat_decomp.py - split 4 KiB random-read latency into link-visible stages (synthetic data).
import random
random.seed(32)

def one_read():
    """Times in microseconds, as an analyzer plus a host tracepoint would see them."""
    t_fetch = 0.7 + random.expovariate(1 / 0.3)              # doorbell -> SQE MRd
    if random.random() < 0.85:
        media = random.gauss(62, 6)                          # normal NAND read
    else:
        media = 62 + random.expovariate(1 / 25)              # die busy (program/erase in progress)
    if random.random() < 0.004:
        media += random.choice([900, 1800, 2700])            # read-retry steps on a weak page
    xfer = 4096 / 7200 + random.expovariate(1 / 0.2)         # data MWrs at ~7.2 GB/s + gaps
    cqe = 0.3                                                # last data MWr -> CQE MWr
    irq = 0.1 + random.expovariate(1 / 0.05)                 # CQE -> MSI-X
    host = 2.5 + random.expovariate(1 / 1.5)                 # MSI-X -> request completed in kernel
    return dict(fetch=t_fetch, media=max(media, 40), xfer=xfer, cqe=cqe, irq=irq, host=host)

N = 200_000
samples = [one_read() for _ in range(N)]
for s in samples:
    s["total"] = sum(s.values())

def pct(vals, p):
    vals = sorted(vals); return vals[min(len(vals) - 1, int(p / 100 * len(vals)))]

stages = ["fetch", "media", "xfer", "cqe", "irq", "host", "total"]
print("%-6s" % "pct" + "".join("%9s" % s for s in stages))
for p in (50, 99, 99.9, 99.99):
    print("%-6s" % ("p%g" % p) + "".join("%9.1f" % pct([s[k] for s in samples], p) for k in stages))

slow = sorted(samples, key=lambda s: s["total"])[-int(N * 0.001):]
share = {k: sum(s[k] for s in slow) / sum(s["total"] for s in slow) for k in stages[:-1]}
print("share of time in slowest 0.1%: " + ", ".join("%s %.1f%%" % (k, 100 * v) for k, v in share.items()))

Procedure

  1. Run it.
  2. Set the retry probability to zero and rerun; compare p99.9.
  3. Raise host jitter (exponential mean 15 µs) and see when the host starts to matter.

Questions

  1. Why do percentiles of stages not add up to the total percentile?
  2. Which stage would an analyzer alone measure?
  3. Why is "average latency" a poor service-level metric here?

Expected reasoning

Tails are mixtures; stage percentiles are taken over different samples.

Solution

(1) Each stage's p99 comes from different requests; the slow requests are slow in one stage. Decompose the slowest requests themselves, as the last line does. (2) Fetch, media (fetch → first data), transfer, CQE and interrupt — everything except host software. (3) A 0.4 % retry population dominates p99.9 while barely moving the mean.

Senior forensic lab — "Reads return stale data, but only on the new server"

Safe lab Reasoning over synthetic evidence.

Objective

Find which layer lets the application see old buffer contents.

Prerequisites

This module's Protocol view; Module 14 — PCIe Ordering.

Setup — evidence (synthetic)

  • About 1 in 10⁸ Reads hands the application data from a previous use of the buffer; re-reading the same LBA returns correct data.
  • Same SSD model and firmware work on the old server.
  • lspci on the new server: DevCtl shows RlxdOrd+ for 01:00.0; on the old server RlxdOrd-.
  • Analyzer capture of one bad case: data MWrs have the Relaxed Ordering attribute set; the CQE MWr also has it set.
  • No status errors, no IOMMU faults, no PI configured.

Procedure

  1. Identify the first abnormal event.
  2. Explain the mechanism and why it is rare.
  3. Propose an immediate mitigation and a permanent fix, with owners.

Observations

Separate what the device did, what the platform allowed and what the host assumed.

Questions

  1. Is setting RO on data TLPs wrong?
  2. Why does the old server not show it?

Expected reasoning

The CQE must not overtake its data; RO on the CQE removes that guarantee.

Solution

First abnormal event: the CQE MWr carrying Relaxed Ordering. With RO, the root complex may commit the CQE to memory before earlier data writes; the CPU sees the CQE, completes the request, and the application reads the buffer before the last data lands. RO on data TLPs is legitimate; on the CQE it violates the producer–consumer pattern that ordering protects. The old server either has RO disabled (no attribute is emitted) or a root complex that does not exploit it. Rare because the race needs a reordering in the root complex and a very fast host consumer. Mitigation: disable Relaxed Ordering for this device (a platform or kernel quirk; a configuration change, not a read-only action — follow your change process). Permanent fix: firmware must clear RO on CQE writes (owner: SSD vendor); add a validation test that inspects attributes of CQE TLPs with RO enabled.

Extension

Write the validation test: which captures, which filters, which pass/fail rule.

Debugging

Pattern 1 — Millisecond Read tails without errors

Symptom
p99.9 Read latency in milliseconds; all statuses success.
Possible causes
Read retry on weak pages; contention with program/erase or garbage collection; thermal throttling; host scheduling (if not confirmed device-side).
Evidence
Analyzer gap fetch → first data; temperature; workload mix (writes in parallel?).
First check
Is the delay before the first data TLP? If not, it is host-side.
Second check
Re-read the slow LBAs: persistent slowness points at weak pages.
Disambiguating experiment
Repeat with writes paused; tails that vanish were contention.
Likely conclusion
Device-internal media behaviour; mitigation via workload shaping or vendor features.
Confidence
Medium.

Pattern 2 — Data Transfer Error

Symptom
Reads complete with generic status 04h; often bursts after a driver change.
Possible causes
Unmapped data or list pages (IOMMU), miscomputed PRP entries, platform memory errors (poisoned completions).
Evidence
IOMMU fault log addresses; PRP entries in the SQE and lists; completion statuses on list reads.
First check
Match the fault address to a PRP entry or list page of the failing CID.
Second check
Whether failures correlate with list pages starting near page ends (chaining).
Disambiguating experiment
Force list pages to start at offset 0; if errors stop, the chaining path is buggy.
Likely conclusion
Host mapping bug.
Confidence
High.

Pattern 3 — Unrecovered Read Errors

Symptom
Status SCT 2h / SC 81h (Linux 0x281) on some LBAs.
Possible causes
Degraded media; Write Uncorrectable injected by a test; firmware recovery bug; LR = 1 causing early failure.
Evidence
SMART media errors; Error Information log LBA; LR bit in SQE; time to failure.
First check
LR bit and time to failure: fast failure with LR = 1 is policy.
Second check
SMART counter increment.
Disambiguating experiment
Re-read with LR = 0 on a non-production copy; recovery means LR policy.
Likely conclusion
Media, unless the test harness injected it.
Confidence
Medium–high.

Pattern 4 — Stale or partial data with success status

Symptom
Application sees old buffer contents; re-reads are correct.
Possible causes
RO on CQE; host reads buffer before consuming the CQE (driver bug); buffer reused before completion; non-coherent DMA without cache maintenance (on platforms without coherent I/O).
Evidence
TLP attributes, DevCtl, driver code paths, platform coherency.
First check
RO attribute on CQE writes.
Second check
Buffer lifetime in the application or filesystem.
Disambiguating experiment
Disable RO; if errors persist, look at host buffer handling.
Likely conclusion
Ordering or host lifetime bug.
Confidence
Medium.

Pattern 5 — Sequential read throughput far below the link

Symptom
3 GB/s on a link good for about 7 GB/s.
Possible causes
Low queue depth; small I/O size; MPS 128; link trained at lower speed or width; IOMMU translation overhead; device limits.
Evidence
LnkSta, DevCtl, fio settings, TLP sizes in a capture.
First check
Negotiated speed and width.
Second check
Outstanding data in flight (queue depth × size) versus media parallelism.
Disambiguating experiment
Sweep queue depth with fixed size; a plateau below the link means the device or IOMMU limits.
Likely conclusion
Configuration or concurrency, more often than device defect.
Confidence
Medium–high.

Interview

Beginner

  1. Which direction do Read data TLPs travel, and what type are they?

    Model answer

    Device to host, as posted Memory Writes.

  2. How many 256-byte TLPs carry 4 KiB?

    Model answer

    16.

  3. What is MDTS on the Lab SSD?

    Model answer

    5, meaning 2⁵ × 4 KiB = 128 KiB.

  4. When is PRP2 a list pointer?

    Model answer

    When the transfer touches more than two memory pages.

  5. What does a success CQE promise for a Read?

    Model answer

    All requested data has been written to the host buffers.

Intermediate

  1. Why can two Reads' data TLPs interleave?

    Model answer

    The controller works on many commands at once; the link carries whatever its DMA engines emit.

  2. How do you attribute an MWr to a command?

    Model answer

    By its address falling inside that command's PRP pages.

  3. What is the link-limited rate of Gen4 x4 at MPS 256?

    Model answer

    About 7.88 GB/s × 256/280 ≈ 7.2 GB/s before DLLP overhead.

  4. What does LR trade?

    Model answer

    Less recovery time in exchange for more Unrecovered Read Errors.

  5. What is a chained PRP list?

    Model answer

    A list that does not fit in the remainder of its page; the last entry points to the next list page.

Advanced

  1. Why must the CQE not carry Relaxed Ordering?

    Model answer

    It could pass earlier data writes and let the host consume the completion before the data is visible.

  2. What happens to buffer contents when a Read fails mid-transfer?

    Model answer

    Undefined; some data may be written. The host must not use any of it.

  3. How do you tell a host-side delay from a device-side one?

    Model answer

    Link timestamps: doorbell → fetch → first data → CQE are device or link; CQE → request completion is host.

  4. Why can a Read complete in 8 µs?

    Model answer

    Deallocated blocks, controller cache hits, or a bug; only content checks distinguish them.

  5. A list fetch gets UR. What status should the Read get?

    Model answer

    Data Transfer Error (or a similar generic transfer status); not a media error.

Senior

  1. Design a Read validation matrix.

    Model answer

    Sizes from one block to MDTS; PRP1 offsets; lists at page starts and ends (chaining); interleaving at high queue depth; FUA and LR; PI types; deallocated and never-written LBAs with and without DULBE; injected uncorrectables; IOMMU fault injection; RO enabled and disabled with attribute checks; content verification for every case.

  2. How would you prove a firmware bug returns wrong data?

    Model answer

    Known pattern written with FUA or followed by Flush, read back with analyzer capture: the MWr payloads differ from the pattern while the SQE, PRP addresses and ordering are correct.

  3. What drives the latency tail on a mixed workload?

    Model answer

    Reads waiting behind programs and erases on the same die, garbage collection and retries; mitigations include program/erase suspend, workload isolation and read-priority features.

  4. How do you set an SLO for Read latency on NVMe?

    Model answer

    Percentiles (p99, p99.9) measured under the production mix, with decomposition showing the media share; averages hide retry populations.

  5. When would you set LR = 1?

    Model answer

    When a redundancy layer (RAID, replication, erasure coding) can rebuild the block faster than the drive's deep recovery.

Quiz

  1. A Read of 6 KiB at buffer offset 0xC00 uses:

    • PRP1 only
    • PRP1 + PRP2 as second page
    • PRP1 + a PRP list
    • An SGL
    Answer and reasoning

    It touches three pages.

  2. A data MWr may be at most:

    • MRRS bytes
    • MPS bytes, not crossing 4 KiB
    • 4 KiB
    • MDTS bytes
    Answer and reasoning

    MPS bounds payload; 4 KiB boundaries cannot be crossed.

  3. DW3 = 0x0009_0130 means:

    • CID 0x0130, Data Transfer Error
    • CID 0x0009, success
    • CID 0x0130, Invalid Field
    • CID 0x0130, Unrecovered Read Error
    Answer and reasoning

    Status word 0x0009 → SC 04h, SCT 0.

  4. A Read is slow; the gap is between CQE and request completion in the kernel. The cause is:

    • Media
    • Link
    • Controller firmware
    • Host side
    Answer and reasoning

    Everything after the CQE and interrupt is host software.

  5. Which TLP must never carry Relaxed Ordering in a Read?

    • Data MWr
    • SQE MRd
    • CQE MWr
    • PRP list MRd
    Answer and reasoning

    The CQE must stay ordered behind its data.

  6. How many 256-byte TLPs for 128 KiB, aligned?

    • 256
    • 512
    • 1024
    • 32
    Answer and reasoning

    131,072 / 256 = 512.

  7. Why is the 2.8 ms Read in the slow trace not an error?

    Model answer

    It completed with success; the controller spent the time recovering or waiting, which the specification allows.

  8. List the evidence that separates a deallocated read from a cache hit.

    Model answer

    Write history, DLFEAT, DULBE behaviour on a test system, and a write-pattern/read-back/power-cycle sequence.

Teach-back

  1. To a child: the library van.

    Model explanation

    "You give the library a list of your shelves. Their van brings books in small boxes, mixed with your neighbour's, and only rings the bell when your last box is in. If the list has a wrong address, the delivery stops and the bell says 'problem' — so you put everything back and ask again."

  2. To a junior engineer: how a 128 KiB Read looks on the link.

    Model explanation

    "Doorbell, SQE fetch, PRP list fetch, a media gap of about 60–70 µs, then 512 MWr of 256 bytes into 32 pages, maybe interleaved with other reads, then the CQE and MSI-X. Attribute data by address, check the CQE comes last."

  3. To a senior engineer: how you investigate a Read incident.

    Model explanation

    "Split the timeline at the link: before fetch and after CQE are host; fetch to first data is media; data to CQE is transfer. For wrong data I check ordering attributes, addresses against PRP and IOMMU, the SQE's LBAs, and content against a known pattern. The status is authoritative for failure; only content checks prove correct success."
