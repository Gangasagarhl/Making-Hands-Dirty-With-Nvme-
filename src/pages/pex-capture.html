What happens to a protocol capture after someone presses "save": what a PEX or other proprietary capture file actually contains, how to identify the analyzer and software that produced it, what you can and cannot safely parse without the vendor's software, which metadata makes a capture trustworthy, and how to export it into a portable, provenance-carrying representation your own tools can use. Two Python tools on this page are runnable as written and never attempt to parse a proprietary format.

Why this part exists

Captures travel. A validation engineer records one in the lab, a firmware team in another country opens it a week later, a customer sends one to a vendor, a script ingests an export into a dashboard. At every hop, information can be lost or invented: the analyzer model, the software version, the filters, the probe point, the decoder's queue configuration, whether payloads were truncated, even which link was probed. A capture without that context is a pile of rows that look like evidence.

This part is about the file and its journey. It complements Teledyne LeCroy Analyzer Training (how a capture is made) and the Trace Analysis Laboratory (how one is read). PEX/Proprietary Capture Analysis goes deeper.

Learning objectives

  • Explain what a capture file represents and why vendors use proprietary formats.
  • Distinguish the file container, the decoded protocol content, the analyzer database, an exported CSV/text/XML file, and raw packets.
  • Identify the producing analyzer and software version without modifying the file.
  • State what can be parsed safely, and what requires the vendor's software.
  • Record the metadata that makes a capture reviewable.
  • Export and normalise a capture into a portable representation with provenance, and state the limits of what can be inferred from it.

Prerequisites

Read Teledyne LeCroy Analyzer Training first, especially analyzer presentation versus protocol truth and analyzer limitations. The normaliser on this page produces input for the programs in Programming Labs.

The story

You recorded a song on your grandmother's old tape recorder. The tape holds the music, but only that recorder plays it properly. If you want to send the song to a friend, you play it and record it again on your phone. The new recording is easy to share, but it lost a little, and if you do not write "recorded from Grandma's tape, kitchen, Sunday" on it, your friend will not know where it came from or why it hisses.

A proprietary capture file is like a camera's raw image file. It holds more than any exported picture (sensor data, settings, lens information), and only the maker's software (or software that implements the maker's format) develops it faithfully. Exporting to a common format makes the image portable but bakes in the development choices, and drops much of the metadata unless you keep it deliberately.

An exported photo still looks like the scene; an exported trace can look complete while silently missing whole categories of events (filtered DLLPs, truncated payloads, ordered sets) and carrying decoding decisions that were wrong. Raw image formats are often documented or widely reverse-engineered; many capture formats are neither, and their licences may restrict reverse engineering. And unlike a photo, a capture's payloads may contain customer data.

For the rest of this page, "capture file" means any proprietary analyzer trace file, PEX or otherwise. The principles are the same.

What a capture file represents

A capture file is the analyzer's record of a capture session: the captured events with timestamps, the configuration under which they were captured, and usually information the software needs to display and search them quickly. Five different things are easily confused (the first is the container):

File container, decoded content, analyzer database, export, raw packets
ThingWhat it isWho can read itWhat it can lose or add
File containerThe file on disk: its bytes, structure, compression, embedded sectionsAnyone can hash and copy it; only software that implements the format can interpret itNothing, if kept unmodified; it is the original evidence
Raw packetsThe captured events as recorded: symbols/bytes per direction with timestamps, inside the containerThe vendor's software (or another tool implementing the format)Already limited by capture filters, truncation, gaps and lock loss at capture time
Decoded protocol contentTLP and DLLP fields, link states, pairings, NVMe commands, computed by the software from raw packetsThe vendor's software, at the version you runDecoder assumptions: revision, flit mode, queue addresses; may change when re-opened with a newer version
Analyzer databaseIndexes, caches, statistics, bookmarks and annotations the software creates to work with the trace; sometimes stored inside the file, sometimes beside itThe vendor's softwareAdds user annotations and derived values; may be stale if the decoder configuration changed
Exported CSV/text/XMLA chosen view of the decoded content, at a chosen level, with chosen fields, written in an open formatAnyoneLoses everything not selected; bakes in decoding; may truncate payloads; units and spellings vary by tool and version

The container is the evidence. Everything else is a derived product of a particular software version and particular choices. Keep the container unmodified, and make every derived product say where it came from.

Why capture formats are often proprietary

  • Performance. Line-rate capture produces very large recordings; formats are designed for fast writing from the instrument and fast random access in the software (indexes, compression, segment tables).
  • Instrument-specific content. Per-lane details, analyzer status, probe information and hardware configuration are specific to the instrument and its generation.
  • Evolution. Formats change as new PCIe generations, flit mode and decoder features arrive; keeping them private lets vendors change them without breaking a public standard.
  • Commercial reasons. The analysis software is part of the product.

Consequences you have to plan for: you need the vendor's software (and often a compatible version) to decode the file; you should check the licence before attempting to reverse engineer a format; newer files may not open in older software; and an organisation that wants long-term access should archive the software version alongside its captures. No public, vendor-independent parser should be assumed to exist for any particular proprietary format.

Identifying the analyzer and version

Before analysing a capture you received, establish its origin. Work from the least intrusive source to the most:

  1. Ask the producer for the analyzer model, firmware, software version, probe type and the capture settings. This is the best source and the one most often skipped.
  2. Read the accompanying files: a settings export, a project file, a README, an email. Many teams send only the trace; ask for the rest.
  3. Open it in the vendor's software and read the file or trace properties it offers (what is shown and where depends on the product; check its documentation). Note any compatibility or conversion message.
  4. Inspect the container read-only: size, hash, extension, and the first bytes. Printable strings near the start may name the producing software or version, or may be noise. Treat such strings as hints, never as facts.
# Read-only inspection of a capture you received. Never edit the original.
ls -l capture.pex
sha256sum capture.pex
file capture.pex                       # often just "data" for proprietary formats
head -c 256 capture.pex | xxd          # first bytes; a readable header string may or may not appear
chmod a-w capture.pex                  # protect your working copy from accidental change

The intake tool below does the same in Python and writes a JSON record next to the file. It reads the container only and never claims to parse it.

#!/usr/bin/env python3
"""capture_intake.py - read-only intake record for a capture file of ANY format.

It never parses the format. It records what can be known safely about the container:
size, timestamps, SHA-256, the first bytes as hex, and printable ASCII/UTF-16LE strings
found near the start (which MAY include a software name or version, or may not).
Output: a JSON intake record to keep next to the untouched original.

Usage: python3 capture_intake.py <capture-file> [more files ...]
       python3 capture_intake.py --demo      (creates and inspects a synthetic file)
"""
import datetime
import hashlib
import json
import os
import re
import sys

HEAD_BYTES = 64          # shown as hex
SCAN_BYTES = 64 * 1024   # scanned for strings
MIN_STRING = 6


def strings(blob):
    ascii_hits = re.findall(rb"[\x20-\x7e]{%d,}" % MIN_STRING, blob)
    utf16_hits = re.findall(rb"(?:[\x20-\x7e]\x00){%d,}" % MIN_STRING, blob)
    out = [s.decode("ascii") for s in ascii_hits]
    out += [s.decode("utf-16-le") for s in utf16_hits]
    return list(dict.fromkeys(out))[:20]     # unique, in order of appearance


def intake(path):
    st = os.stat(path)
    sha = hashlib.sha256()
    with open(path, "rb") as f:                 # read-only
        head = f.read(SCAN_BYTES)
        sha.update(head)
        for chunk in iter(lambda: f.read(1 << 20), b""):
            sha.update(chunk)
    return {
        "file": os.path.basename(path),
        "extension": os.path.splitext(path)[1].lower(),
        "size_bytes": st.st_size,
        "modified_utc": datetime.datetime.fromtimestamp(st.st_mtime, datetime.timezone.utc).isoformat(),
        "sha256": sha.hexdigest(),
        "first_bytes_hex": head[:HEAD_BYTES].hex(" "),
        "printable_strings_near_start": strings(head),
        "format_parsed": False,
        "note": "Container facts only. Decode with the producing vendor's software; record its version.",
        "intake_utc": datetime.datetime.now(datetime.timezone.utc).isoformat(timespec="seconds"),
    }


def demo():
    # A made-up container: magic bytes, a UTF-16 string, binary noise. Not any real format.
    path = "demo_capture.bin"
    with open(path, "wb") as f:
        f.write(b"\x89DEMO\r\n\x1a\n" + "Example Analyzer Suite 9.9".encode("utf-16-le")
                + bytes(range(256)) * 4)
    return [path]


def main():
    paths = demo() if sys.argv[1:] == ["--demo"] else sys.argv[1:]
    if not paths:
        sys.exit(__doc__)
    for p in paths:
        rec = intake(p)
        print(json.dumps(rec, indent=2))
        with open(p + ".intake.json", "w") as f:   # written NEXT to the file, original untouched
            json.dump(rec, f, indent=2)


if __name__ == "__main__":
    main()

What can be parsed safely, and what requires vendor software

Safe and unsafe operations on a proprietary capture
OperationSafe without vendor software?Why
Copy, hash, record size and timestampsYesContainer-level facts; read-only
Look at the first bytes and printable stringsYes, as hintsRead-only; interpretation is heuristic
Parse vendor exports (CSV/text/XML)YesOpen formats, produced by the vendor's decoder; know their limits
Decode packets, timestamps, link states from the containerNoRequires the format specification and the vendor's decoder; guessing produces confident nonsense
Re-run NVMe decoding with corrected queue addressesNoDecoder configuration lives in the vendor software
Reverse engineer the formatCheck firstLicence terms may forbid it; results are unverified; formats change between versions
Modify the file (trim, merge, anonymise in place)NoDestroys the evidence chain; do it on exports, never on the original

Data payloads in a storage capture are pieces of the drive's content: user files, database pages, keys. Before sending a capture or export outside the team, check what it contains, whether payloads can be truncated or redacted at export, and what agreements govern the data. Redact exports, not originals, and record that you did.

Exporting into a portable representation

Portable representations let you run your own checks (Programming Labs), diff captures, build golden traces and feed automated analysis (Automated Trace Analysis). The process has three parts.

1. Export from the vendor software

  • Choose the level: packets (to re-derive pairing yourself), or transactions (if latency is all you need).
  • Choose fields: timestamp, direction, layer, type, Requester ID, Completer ID, tag, address, length, byte enables, status, EP/TD bits, sequence numbers for DLLPs, and payloads only as far as needed.
  • Export the capture settings alongside.
  • Note the software version used for the export: two exports of the same file by different versions may differ.

2. Normalise

Different tools, versions and export options spell columns, units and directions differently ("Downstream" versus "Host→Dev", microseconds versus a mixture of units, bus:device.function versus a hexadecimal Requester ID). A normaliser maps all of them to one canonical schema and records what it did.

#!/usr/bin/env python3
"""normalize_export.py - turn an analyzer's text/CSV export into a portable JSON Lines trace.

The embedded SAMPLE uses column names, units and spellings INVENTED for this exercise to
look like a typical decoded export; it is not the format of any real product. Real exports
differ by vendor, software version and the export options chosen. Adapt COLUMN_ALIASES.

Payload columns in the sample are printed as DWORD values (little-endian already applied);
check which convention your exporter uses before decoding NVMe structures from them.
Output: line 1 = provenance record, then one canonical event per line:
  seq, t_ns, dir (H2D|D2H), layer, type, rid, tag, addr, len_bytes, status, payload, src_row
Checks : required fields, time monotonicity, direction values, request/completion pairing.
Usage  : python3 normalize_export.py [export.csv] [--redact] [--exporter "name version"]
"""
import csv
import hashlib
import io
import json
import re
import sys
import datetime

SAMPLE = """\
Packet #,Time Stamp,Link Dir,Layer,Packet Type,Req ID,Tag,Address,Length (DW),Status,Data
1,0.000 us,Downstream,TL,MWr(32),00:01.1,,FE60_1008,1,,0000000A
2,0.090 us,Upstream,DLL,ACK,,,,,,
3,0.620 us,Upstream,TL,MRd(64),01:00.0,30,1_2340_0240,16,,
4,1.410 us,Downstream,TL,CplD,00:01.1,30,,16,SC,00190002 00000001 00000000 00000000 00000000 00000000 00008000 00000002 00000000 00000000 00005000 00000000 00000007 00000000 00000000 00000000
5,71.2 us,Upstream,TL,MWr(64),01:00.0,,2_0000_8000,64,,3F2A9C11 ...(truncated by exporter)
6,0.0729 ms,Upstream,TL,MWr(64),01:00.0,,1_2341_0090,4,,00000000 00000000 0001000A 00010019
7,73.05 us,Upstream,TL,MWr(32),01:00.0,,FEE0_1000,1,,00000041
8,76.8 us,Downstream,TL,MWr(32),00:01.1,,FE60_100C,1,,0000000A
9,80.1 us,Upstream,TL,MRd(64),01:00.0,31,1_2340_0280,16,,
"""

COLUMN_ALIASES = {            # canonical name -> header spellings seen in exports
    "seq": ["packet #", "packet", "#", "index"],
    "time": ["time stamp", "timestamp", "time"],
    "dir": ["link dir", "direction", "dir"],
    "layer": ["layer"],
    "type": ["packet type", "type", "tlp type"],
    "rid": ["req id", "requester id", "requester"],
    "tag": ["tag"],
    "addr": ["address", "addr"],
    "len_dw": ["length (dw)", "length", "len"],
    "status": ["status", "cpl status"],
    "payload": ["data", "payload"],
}
DIRS = {"downstream": "H2D", "down": "H2D", "host->dev": "H2D", "rc->ep": "H2D",
        "upstream": "D2H", "up": "D2H", "dev->host": "D2H", "ep->rc": "D2H"}
UNITS = {"s": 1e9, "ms": 1e6, "us": 1e3, "µs": 1e3, "ns": 1.0, "ps": 1e-3}
NON_POSTED = {"MRd", "CfgRd", "CfgWr", "IORd", "IOWr"}


def map_columns(header):
    lower = [h.strip().lower() for h in header]
    mapping = {}
    for canon, names in COLUMN_ALIASES.items():
        for n in names:
            if n in lower:
                mapping[canon] = header[lower.index(n)]
                break
    return mapping


def to_ns(text):
    m = re.fullmatch(r"\s*([0-9.]+)\s*([a-zµ]+)\s*", text)
    if not m or m.group(2) not in UNITS:
        raise ValueError(f"unparseable time {text!r}")
    return round(float(m.group(1)) * UNITS[m.group(2)], 3)


def to_rid(text):
    text = text.strip()
    m = re.fullmatch(r"([0-9a-fA-F]{2}):([0-9a-fA-F]{2})\.([0-7])", text)
    if m:
        b, d, f = (int(x, 16) for x in m.groups())
        return f"0x{(b << 8) | (d << 3) | f:04x}"
    return f"0x{int(text, 16):04x}" if text else None


def to_hex(text):
    text = text.strip().replace("_", "")
    return f"0x{int(text, 16):x}" if text else None


def normalize(text, redact=False):
    rows = list(csv.reader(io.StringIO(text)))
    header, body = rows[0], rows[1:]
    cmap = map_columns(header)
    idx = {k: header.index(v) for k, v in cmap.items()}
    missing = [k for k in ("time", "dir", "type") if k not in idx]
    if missing:
        raise SystemExit(f"cannot map required columns {missing}; extend COLUMN_ALIASES")
    events, problems, last_t = [], [], None
    for n, r in enumerate(body, start=2):
        get = lambda k: r[idx[k]].strip() if k in idx and idx[k] < len(r) else ""
        try:
            t = to_ns(get("time"))
        except ValueError as e:
            problems.append(f"line {n}: {e}")
            continue
        if last_t is not None and t < last_t:
            problems.append(f"line {n}: time goes backwards ({t} ns after {last_t} ns)")
        last_t = t
        d = DIRS.get(get("dir").lower())
        if d is None:
            problems.append(f"line {n}: unknown direction {get('dir')!r}")
        typ = re.sub(r"\((\d+)\)", r"\1", get("type")).replace("ACK", "Ack")
        length = int(get("len_dw")) * 4 if get("len_dw") else None
        payload = get("payload") or None
        if payload and "truncated" in payload:
            problems.append(f"line {n}: payload truncated by the exporter")
        if redact and payload and length and length > 64:
            payload = "sha256:" + hashlib.sha256(payload.encode()).hexdigest()[:16]
        events.append({"seq": int(get("seq")) if get("seq") else None, "t_ns": t, "dir": d,
                       "layer": get("layer") or None, "type": typ, "rid": to_rid(get("rid")),
                       "tag": to_hex(get("tag")), "addr": to_hex(get("addr")),
                       "len_bytes": length, "status": get("status") or None,
                       "payload": payload, "src_row": n})
    open_req = {}
    for e in events:
        base = re.sub(r"\d+$", "", e["type"])
        if base in NON_POSTED:
            open_req[(e["rid"], e["tag"])] = e["src_row"]
        elif e["type"].startswith("Cpl"):
            # A completion travels the other way: its rid field names the COMPLETER in this
            # export, so match on tag only and report ambiguity.
            hits = [k for k in open_req if k[1] == e["tag"]]
            if len(hits) == 1:
                del open_req[hits[0]]
            else:
                problems.append(f"line {e['src_row']}: completion tag {e['tag']} matches {len(hits)} requests")
    for (rid, tag), row in open_req.items():
        problems.append(f"line {row}: request {rid}/tag {tag} has no completion in this export")
    return events, problems


def main():
    args = [a for a in sys.argv[1:] if not a.startswith("--")]
    redact = "--redact" in sys.argv
    exporter = "unknown (record it!)"
    if "--exporter" in sys.argv:
        exporter = sys.argv[sys.argv.index("--exporter") + 1]
        args = [a for a in args if a != exporter]
    text = open(args[0], encoding="utf-8").read() if args else SAMPLE
    events, problems = normalize(text, redact)
    prov = {"_provenance": {
        "source": args[0] if args else "embedded SAMPLE (synthetic)",
        "source_sha256": hashlib.sha256(text.encode()).hexdigest(),
        "exporter": exporter, "redacted": redact,
        "converted_utc": datetime.datetime.now(datetime.timezone.utc).isoformat(timespec="seconds"),
        "warnings": problems}}
    print(json.dumps(prov))
    for e in events:
        print(json.dumps(e))
    for p in problems:
        print("WARNING:", p, file=sys.stderr)


if __name__ == "__main__":
    main()

The limits of what can be inferred

A normalised export is the most convenient form of a capture and the furthest from the wire. Before drawing a conclusion from one, check what it cannot tell you:

  • Absence is weak. Missing events may have been filtered at capture, dropped by the analyzer, outside the exported range, or not selected for export.
  • Decoding is baked in. If the decoder used the wrong queue addresses, revision or format, the export carries the error with no trace of doubt.
  • Precision may be lost. Timestamps rounded by the export format, payloads truncated, fields omitted.
  • Lower layers may be gone. Ordered sets, DLLPs and link-state transitions are often left out of exports; replay and credit questions cannot be answered from such an export.
  • Byte order and units are conventions. Payload columns may be printed as bytes in wire order or as DWORD values; timestamps may mix units. The sample export prints DWORD values; check yours.
  • Nothing inside devices. As with any capture: no controller-internal state, no host memory contents beyond what crossed the link.

When a conclusion matters, verify it in the vendor software at the packet level on the original container, and say so in the report. Use exports for breadth (searching, statistics, automation) and the original for depth (proof).

Chain of custody and sharing

  1. Hash the original on receipt (this is the start of the evidence's provenance); store it read-only; never modify it.
  2. Write the intake record and the metadata record next to it.
  3. Do all trimming, redaction and conversion on exports, each with a provenance record naming the original's hash and the tool versions.
  4. When sharing with another organisation, send the original (if permitted) plus the metadata, or a redacted export plus provenance, and say which.
  5. Archive the vendor software version used for analysis with long-lived captures, or at least record it, so the decode can be reproduced.

Specification view

No PCIe or NVMe specification defines capture file formats, export formats or analyzer metadata. The specifications define what the captured events mean (the PCI Express Base Specification for TLPs, DLLPs and ordered sets; the NVMe Base 2.4, NVM Command Set 1.3 and NVMe over PCIe Transport 1.4 specifications for queue structures and registers). Everything about files is vendor-defined.

Verified: the meaning of the fields in a correctly decoded event, checkable against the specifications.

Derived: everything a normaliser produces (units, directions, canonical names), and every pairing or statistic computed from an export.

Implementation-dependent: container formats, extensions, export options and their spellings, what metadata the software stores, and whether files from one version open in another.

Version-dependent: decoders and export formats change with software releases; re-exporting an old file with new software can change its content.

What must be checked: the vendor's documentation for export fields and conventions; the specifications for any field meaning a conclusion depends on.

Never assume: that a public parser exists for a proprietary format; that an export is complete; that two exports of one file are identical across versions; that a capture contains no sensitive data.

Lab 1 — Intake a capture you did not make

Objective

Produce an intake record and a list of questions for the producer, without modifying or decoding the file.

Skills

  • Read-only inspection
  • Hashing and custody
  • Separating hints from facts

Safety

Safe lab Read-only operations on a copy.

Hardware required

None.

Software required

Python 3.8+, capture_intake.py; optionally xxd and sha256sum.

Input

Any capture file you are permitted to handle, or the synthetic demo container (--demo).

Expected output

An .intake.json file beside the original and a short list of open questions.

Background

See Identifying the analyzer and version.

Step 1

Copy the file to a working directory, make the copy read-only, and run the intake tool on it.

Step 2

Compare the hash with the one the producer sent (ask for it if they did not).

Step 3

Fill in the metadata table from Metadata that matters with what you know; mark every unknown and turn it into a question for the producer.

Observation

For a typical received capture, most of the metadata table is unknown until you ask. The file alone rarely tells you the probe point or the filters unless the software stores and displays them.

Questions

  1. The intake tool finds the string "Suite 9.9" near the start of a file. Can you write "captured with version 9.9" in your report?

    Answer

    No. Write "a string suggesting version 9.9 appears in the file header (unconfirmed)", and confirm with the producer or the vendor software's file information. The string might record the version that last saved the file, not the one that captured it, or be unrelated.

  2. Why hash the file before opening it in the vendor software?

    Answer

    To be able to prove later that the analysed file is the one received. Some software may offer to convert or update files; the hash shows whether the original was changed.

Challenge

Extend the intake tool to accept a directory and produce one combined manifest, flagging duplicate files by hash.

Hint

Use os.walk; collect records; group by sha256.

Solution 
import collections, os

def manifest(root):
    records = [intake(os.path.join(d, f)) for d, _, files in os.walk(root)
               for f in files if not f.endswith(".intake.json")]
    by_hash = collections.defaultdict(list)
    for r in records:
        by_hash[r["sha256"]].append(r["file"])
    dups = {h: names for h, names in by_hash.items() if len(names) > 1}
    return {"records": records, "duplicates": dups}

Add it to capture_intake.py (it reuses intake()) and dump the result as JSON.

What a senior engineer notices

The questions list is the real output. A capture whose producer cannot answer them is weak evidence, however clear it looks.

Failure variants

  • Hash mismatch with the producer's: transfer corruption or a different file.
  • The software converts the file on opening: analyse the converted copy, keep the original.

Extension

Make the intake record part of your team's bug template; see Engineering Bug Report Training.

Safety

Safe lab Offline parsing.

None.

Software required

Python 3.8+, normalize_export.py.

Input

The embedded synthetic export, then an export from your own analyzer software if you have one.

Expected output

A JSONL file whose first line is a provenance record listing warnings.

Background

See Exporting into a portable representation.

Step 1

Run the normaliser on the sample and read every warning. Explain each.

Step 2

Decode the CplD payload of packet 4 (an SQE, printed as DWORD values) with Programming Lab 3. Be careful: Lab 3 expects bytes in memory order.

Step 3

Pipe the JSONL into a small script that reproduces Programming Lab 6's classification, and compare its timeline with Trace Lab 1.

Observation

The sample mixes microseconds and milliseconds, names the Root Port by Bus:Device.Function, truncates a data payload, and ends with a request whose completion is outside the export. Each is a realistic export hazard.

Questions

  1. Convert packet 4's first DWORD value 0x00190002 into the bytes Lab 3 expects.

    Answer

    Little-endian bytes: 02 00 19 00. Opcode 02h, CID 0x0019. Each DWORD value must be converted to its four little-endian bytes before feeding a byte-oriented parser.

  2. Why does --redact leave the CQE and doorbell payloads readable?

    Answer

    The heuristic redacts only payloads longer than 64 bytes, on the assumption that queue entries and register writes are small and carry no user data while data transfers are large. It is a heuristic: a small data transfer would leak, so review it for your workload.

  3. The normaliser reports "request 0x0100/tag 0x31 has no completion in this export". Is that a completion timeout?

    Answer

    Not on this evidence. The request is the last packet in the export; its completion probably falls outside the exported range. Check the original capture.

Challenge

Add a --payload-bytes option that converts DWORD-value payloads into memory-order byte strings, so SQEs and CQEs can be passed directly to Programming Labs 3 and 4.

Hint

int(w, 16).to_bytes(4, "little").hex() for each word.

Solution 
def dwords_to_bytes(payload):
    words = [w for w in payload.split() if all(c in "0123456789abcdefABCDEF" for c in w)]
    return "".join(int(w, 16).to_bytes(4, "little").hex() for w in words)

assert dwords_to_bytes("00190002 00000001") == "0200190001000000"

Apply it in normalize() when the option is set, and record the conversion in the provenance record so nobody converts twice.

What a senior engineer notices

The provenance line is what makes the output usable by someone else. Without it, a JSONL file is just another unlabelled trace.

Failure variants

  • Unknown direction spelling: extend the mapping, never guess.
  • Times going backwards: merged exports or two clocks; do not sort silently.
  • Column missing: export again with the field selected.

Extension

Write a differ that compares two normalised traces of the same operation and reports the first differing event: the core of golden-trace comparison in Synthetic vs Real Traces.

Lab 3 — Decide what a capture can prove

Objective

Given a capture's metadata, decide which questions it can and cannot answer.

Skills

  • Reasoning about scope
  • Writing evidence statements

Safety

Safe lab Paper exercise.

Hardware required

None.

Software required

None.

Input

Metadata: Gen4 ×4; capture started after boot; DLLPs and ordered sets not stored; payloads truncated to 32 bytes; trigger on any completion with non-successful status at 50%; exported at transaction level to CSV.

Expected output

For each of five questions, "answerable", "partly" or "not answerable", with a reason.

Background

See The limits of what can be inferred.

Step 1

Questions: (a) Did any read complete with Unsupported Request? (b) Were there link replays? (c) What were the SQE contents? (d) What was the read completion latency distribution? (e) Did the NVMe decoder know the I/O queue addresses?

Step 2

For each, name the evidence needed and whether the capture kept it.

Step 3

Write one evidence statement per question in the form "This capture can/cannot show X because Y."

Observation

One configuration answers some questions well and others not at all; "is this capture good?" has no answer without a question.

Questions

  1. Is (c) answerable?

    Answer

    Partly at best: SQEs are 64 bytes and payloads were truncated to 32, so only CDW0–CDW7 (opcode, CID, NSID, metadata pointer, PRP1) survive; command-specific DWORDs (LBA, length) are lost.

  2. Is (e) answerable?

    Answer

    Not from the capture alone: it started after boot, so the decoder could not have learned the queues from initialization; it depends on manual configuration in the software, which must be checked there.

Challenge

Propose the smallest change to the configuration that makes all five answerable.

Hint

Which single setting removed the most evidence?

Solution

Store DLLPs (for b), keep at least 64 bytes of payload (for c), start capture before NVMe initialization or configure the decoder manually with recorded queue addresses (for e). (a) and (d) were already answerable from transaction-level data, assuming no capture gaps.

What a senior engineer notices

The cheapest fix is almost always at capture time; the most expensive is discovering the missing evidence after the reproduction window has closed.

Failure variants

  • Export level too high (transactions) for a packet-level question.
  • Metadata missing altogether: every answer becomes "unknown".

Extension

Apply the same exercise to the capture of Trace Lab 11.

Common mistakes

  • Analysing an export and calling it "the trace".
  • Editing, trimming or re-saving the original capture.
  • Assuming a public parser exists, or writing one by guesswork and trusting it.
  • Sending captures with customer data outside the organisation without checking.
  • Not recording the software version used for decoding and export.
  • Silently sorting events by time when an export's times go backwards (hiding a merge or clock problem).
  • Treating "not in the export" as "did not happen".

Senior engineer insight

Senior engineers treat a capture like a forensic exhibit: they know where it came from, who has handled it, what has been done to it, and what it can and cannot prove. They keep the original pristine, do their work on derived copies with provenance, and they verify conclusions at the packet level in the vendor's software before signing a report. Most importantly, they make the metadata habit cheap for everyone else: a template, a sidecar file, an intake script. The investigation you save will probably be someone else's.

Quiz

  1. Which of these is the original evidence?

    • The unmodified capture file container
    • The CSV export
    • The analyzer's statistics view
    • The normalised JSONL
    Answer and reasoning

    Everything else is derived from the container by a particular software version and particular choices.

  2. A colleague says "this is a PEX file". What should you ask first?

    • Its size
    • Whether it is compressed
    • Which tool, version and hardware produced it (and whether "PEX" refers to an analyzer file or a switch)
    • Nothing; PEX is a standard format
    Answer and reasoning

    "PEX" is ambiguous and the format is vendor-defined; origin determines how to read it.

  3. Which operation is safe on a proprietary capture without vendor software?

    • Decoding TLP fields from the binary
    • Computing its SHA-256 hash
    • Trimming it to the interesting region
    • Re-running NVMe decoding
    Answer and reasoning

    Hashing is a read-only container operation. The others need the format or modify the evidence.

  4. An export prints payload DWORD 0x00190002. In memory, the bytes are:

    • 00 19 00 02
    • 19 00 02 00
    • 00 02 00 19
    • 02 00 19 00
    Answer and reasoning

    Little-endian: least significant byte first, 02 00 19 00. That is why exports must state their payload convention.

  5. Name the five things this page distinguishes and one thing each can lose or add.

    Model answer

    Container (nothing, if unmodified); raw packets (limited at capture time by filters and gaps); decoded content (decoder assumptions); analyzer database (annotations, possibly stale derived values); export (fields not selected, truncation, unit conventions).

  6. Why should long-lived captures be archived with the analysis software version?

    Model answer

    Decoding is version-dependent and formats evolve; to reproduce a decode, or even open the file, years later, you may need that version (or at least to know which version produced the conclusions).

  7. Give two reasons a request can lack a completion in an export without any protocol error.

    Model answer

    The completion falls outside the exported range or capture window; completions were filtered at capture or not selected for export. (Also: capture gap or analyzer drop.)

  8. What must a normaliser record about itself, and why?

    Model answer

    Its source (with hash), the exporter software and version, conversions applied (units, directions, payload byte order), redaction, the time of conversion and warnings, so any consumer can judge and reproduce the output.

Interview questions

  1. Intermediate. A customer sends a trace file and a one-line description. What do you do before analysing it?

    Model answer

    Hash and store it read-only, write an intake record, identify the producing tool and version, and request the capture settings, probe point, DUT configuration and reproduction steps. Check data classification before sharing internally.

  2. Advanced. How would you build a pipeline that ingests analyzer captures for automated checks?

    Model answer

    Export from the vendor software at packet level with a fixed field set; normalise to a canonical schema with provenance; validate against vendor statistics; run checks (pairing, ordering, NVMe rules); keep links back to the original file and row so every automated finding can be verified in the vendor software.

  3. Senior. Someone proposes writing a parser for a proprietary capture format to avoid licensing the vendor software. Your view?

    Model answer

    Check the licence first; reverse engineering may be prohibited. Even if allowed, an unverified parser for an evolving format will produce confident errors, and every conclusion would need verification in the vendor software anyway. Prefer vendor exports plus open tooling for automation.
