This module takes the Direct Memory Access (DMA) that you met in the end-to-end chapters and opens it up: who is allowed to master the bus, how a host buffer becomes an address the SSD can use, how the controller shapes its reads and writes into Transaction Layer Packets (TLPs), what limits DMA throughput, and the failure patterns that only make sense once you see DMA as a contract between four parties: driver, IOMMU, root complex and controller.

Orientation

In The Most Important Chapter you watched a 4 KiB READ land in host memory as sixteen posted Memory Writes, and in End-to-End Write you watched a WRITE pull its data with sixteen non-posted Memory Reads and thirty-two Completions with Data. Those chapters treated DMA as a step in a story. This module treats it as a subsystem with its own rules, limits and failure modes. We will go deeper on four things the chapters only touched: the address an SSD actually emits (an I/O virtual address, or IOVA, translated by an input–output memory management unit, the IOMMU); the shaping of DMA into TLPs (Max Payload Size, Max Read Request Size, Read Completion Boundary, the 4 KiB rule, outstanding-request limits); the attributes that change ordering and coherence (Relaxed Ordering, No Snoop); and the DMA the controller performs for itself rather than for a command (PRP list fetches, SQE fetches, the Host Memory Buffer).

Before this module you should be comfortable with: the general idea of DMA and bus mastering (DMA); the full READ path (The Most Important Chapter); the full WRITE path and the data pull (End-to-End Write); Physical Region Page (PRP) entries and lists (Physical Region Pages); posted versus non-posted requests (Posted vs Non-Posted Transactions). The module on DMA and Address Translation covers the IOMMU in general; here we stay on what NVMe makes of it.

Where this goes next: NVMe over PCIe places DMA inside the transport binding, Trace Correlation uses DMA addresses as the strongest correlation key, and NVMe Errors and PCIe Errors show how a failed DMA surfaces at each layer.

Kid story

Imagine a big school with a kitchen at the far end of a long corridor. The class teacher does not carry trays. Instead she writes a note: "Lunch for table 4: put the soup in bowls on shelves 12, 13 and 14." She pins the note on a board and rings a little bell.

A kitchen helper with a trolley comes down the corridor on her own, reads the note, goes back, fills the bowls, and pushes the trolley down the corridor to put the soup straight onto shelves 12, 13 and 14. She never asks the teacher to carry anything. But the school has a hall monitor at the classroom door. The monitor has a list of which shelves the kitchen helper is allowed to touch today. If the helper tries shelf 15, the monitor stops her and writes the shelf number in a notebook.

When the helper is collecting dirty bowls instead (going the other way), she has to ask for each tray and wait for someone to hand it to her, and she can only carry a few trays at a time. So collecting is slower than delivering, unless she has lots of hands.

What it hides. Shelf numbers in the note are not the real shelf numbers: the driver writes I/O virtual addresses, and the monitor translates every one of them. The trolley also has a maximum load per trip (MPS) and a maximum request per ask (MRRS), and a rule that no single trip may cross a 4 KiB "corridor junction". The kitchen helper also fetches the note itself and, for long lists, a second sheet of shelf numbers (a PRP list): that is DMA too.

Where it misleads. The story suggests the monitor always reports to the teacher. In reality a blocked posted write is invisible to the SSD: it gets no reply, believes it delivered, and may then report success. The story also implies a single helper; a real controller has many DMA engines running for many commands at once, and their TLPs interleave on one link. Finally, "soup arrives, then the note saying done" is guaranteed only because PCIe posted writes stay in order unless Relaxed Ordering says otherwise; there is nothing magic about kitchens that enforces it.

The central concept on the ladder

The central concept of this module is the DMA contract: the controller may touch exactly the bytes the command described, in shapes the link allows, only while the host keeps them mapped, and must make the bytes visible before it announces completion.

The kitchen helper may fill only the shelves on the note, only while the hall monitor's list includes them, and must finish filling before she drops the "done" card.

The driver maps buffers and passes their device addresses in PRP or SGL form; the controller reads or writes exactly that memory by itself; the driver unmaps only after the completion arrives.

The controller's DMA engines generate Memory Read and Memory Write requests with Requester ID 0x0100; the root complex translates each address through the IOMMU, snoops caches and forwards to DRAM; read completions return through the root port with the same tag.

The NVMe Base Specification and NVM Command Set define the data pointer fields and their rules (PRP offsets, list chaining, SGL descriptors) and say the controller transfers data between host memory and the namespace. The NVMe over PCIe Transport Specification places queues and data in host memory accessed by the controller. The PCI Express Base Specification defines memory requests, MPS, MRRS, RCB, the 4 KiB rule, attributes and ordering. The IOMMU is a platform architecture, not part of either specification.

READ data: posted MWr, no completions. WRITE data: non-posted MRd, CplD split at RCB and bounded by MPS. CQE: posted MWr ordered after the data. Interrupt: posted MWr ordered after the CQE.

An analyzer shows device-originated requests with Requester ID 0x0100 at IOVAs inside the ranges named by the SQE and PRP list, in TLP sizes set by MPS/MRRS, never crossing a 4 KiB line, followed by one CQE write and one MSI-X write.

For any DMA failure ask: was the address the one the command described (driver or controller fault)? Was it mapped at that moment (driver lifetime or IOMMU)? Was the TLP legal (controller DMA engine)? Did the host answer (root complex, completion timeout)? Did the data arrive but go stale (coherence)?

Stated plainly by the specifications: a memory request must not cross a 4 KiB boundary; a TLP payload must not exceed MPS; a read request must not exceed MRRS; read completions may be split, at RCB-aligned addresses, and are returned in address order for one request; posted writes without Relaxed Ordering do not pass earlier posted writes; a function with Bus Master Enable clear must not issue memory requests. On the NVMe side: PRP entries carry a page base and an offset; only the first PRP entry of a command may have a non-zero offset within the memory page; PRP entries must be dword-aligned; the memory page size is set by CC.MPS.

Reasoned, not quoted: a controller must not post the CQE until the data of a READ is written (the host may reuse the buffer after completion), so it must not set Relaxed Ordering on the CQE write. The bandwidth bound from outstanding reads (see Protocol view) follows from Little's law, not from any specification text.

Implementation-dependent: when the controller fetches the PRP list; how many reads it keeps outstanding; whether it uses MRRS-sized or smaller reads; whether it sets Relaxed Ordering or No Snoop on data TLPs; how the root complex splits completions; IOMMU page sizes, IOTLB behaviour and fault reporting format; whether the host grants an HMB and how much.

Version-dependent: SGL support for NVMe over PCIe I/O commands was added in NVMe 1.1 and remains optional; the HMB arrived in NVMe 1.2; from NVMe 2.0 the PCIe-specific material moved from the Base Specification into the NVMe over PCIe Transport Specification, now at 1.4. On the PCIe side, 10-bit tags (PCIe 4.0) and 14-bit tags in FLIT mode (PCIe 6.0) change how many reads may be outstanding.

Neither NVMe nor PCIe says how a host must manage IOMMU mappings, when a driver may unmap, or what a controller must report when one of its posted writes is dropped by the host (it cannot know). NVMe does not specify how a controller orders its data TLPs within a command or across commands. Check in the specification: the exact PRP list chaining rule at the end of a list page; whether a particular command set permits SGLs for a given command; the Host Memory Buffer descriptor layout; the precise Relaxed Ordering passing table for your PCIe revision.

Never assume a successful CQE proves the data reached the buffer: posted writes can be dropped by the IOMMU without the controller knowing. Never assume the address in a trace is a physical address. Never assume the IOMMU page size equals 4 KiB, or that the 4 KiB split rule comes from the IOMMU.

A data read is a round trip: the MRd travels up the link, waits in the root complex for the IOMMU translation and the memory read (including snoops), and the CplD travels back, consuming the root port's transmit credits on the way. On the lab system we assume about 1.6 µs per round trip at the device. The controller can hide that latency only by keeping several reads in flight, which is why the number of DMA read engines or tag slots in an SSD controller is a key design parameter.

Protocol view

Shaping rules, applied

Given a buffer region [start, start + len), a DMA engine produces TLPs as follows. The rules are PCIe rules; the policy within them is the controller's.

  1. Cut the region at every 4 KiB address boundary (mandatory).
  2. For writes, cut each piece into chunks of at most MPS (mandatory); most engines also align chunks to MPS so that later chunks start on a natural boundary (policy).
  3. For reads, cut each piece into requests of at most MRRS (mandatory); engines may use smaller requests (policy).
  4. The completer returns each read in one or more CplDs of at most MPS, splitting only at RCB-aligned addresses (completer policy within the rules).

Request and response relationships

  • READ data is posted: there is no response, and therefore no way for the controller to learn of a failure at the host. The only end-to-end confirmation is the host's own check of the data.
  • WRITE data is non-posted: each MRd carries a tag; completions return with the same Requester ID and tag; Byte Count tells the controller how many bytes remain; a completion with Unsupported Request (UR) or Completer Abort (CA) status, or no completion within the completion timeout, tells the controller the read failed.
  • SQE and PRP list fetches are non-posted reads with the same properties as WRITE data.

Ordering and completion

The correctness of NVMe completion rests on one PCIe ordering property: a posted write without Relaxed Ordering does not pass an earlier posted write. The controller issues the last data MWr, then the CQE MWr, then the MSI-X MWr; if all three have RO clear, they reach memory in that order, so the driver that sees the CQE (or receives the interrupt) can safely read the data. If the controller sets RO on data writes, those data writes may pass each other, but the CQE (RO clear) still cannot pass them. That is the design: RO for bulk data, never for the completion.

For WRITE-direction commands the reasoning is different: the controller must have received all completions for its data reads, and committed the data internally (to cache or media, depending on FUA and cache state), before it posts the CQE. The ordering here is enforced by the controller's own logic, not by the link.

Intermediate lab — Measure the outstanding-read bound with a simulator

Safe lab Python 3, standard library only.

Objective
Show by simulation that WRITE-direction bandwidth is bounded by outstanding reads, request size and round-trip time, and find the knee where the link takes over.
Prerequisites
The formula in Protocol view; PCIe Flow Control for why the link has a ceiling.
Setup
Save the script below as pull_sim.py.
Procedure
  1. Run it as given and record the table.
  2. Change RTT_NS to 2400 (an IOMMU miss on every page) and rerun.
  3. Change REQ to 256 and rerun.
#!/usr/bin/env python3
"""Event-driven model of an NVMe controller pulling WRITE data over PCIe.
Synthetic teaching model: fixed round trip, a link that serialises completions."""
import heapq

TOTAL = 128 * 1024          # bytes to pull (one 128 KiB WRITE)
REQ = 512                   # bytes per MRd (<= MRRS)
MPS = 256                   # bytes per CplD payload
RTT_NS = 1600               # MRd out to first CplD back, excluding serialisation
LINK_GBPS = 7.88            # Gen4 x4 raw, GB/s per direction
OVERHEAD = 24               # framing + header + LCRC bytes per TLP (approximate)

def cpl_time_ns(payload):
    return (payload + OVERHEAD) / LINK_GBPS   # bytes / (GB/s) = ns

def simulate(n_outstanding):
    t, issued, done = 0.0, 0, 0
    link_free = 0.0                        # time the downstream link is next free
    events = []                            # (time the request's data has all arrived)
    in_flight = 0
    while done < TOTAL:
        while in_flight < n_outstanding and issued < TOTAL:
            ready = t + RTT_NS             # completer has the data at this time
            finish = max(ready, link_free)
            for _ in range(REQ // MPS):    # completions share the link in order
                finish += cpl_time_ns(MPS)
            link_free = finish
            heapq.heappush(events, finish)
            issued += REQ
            in_flight += 1
        t = heapq.heappop(events)          # next request retires, tag is free
        in_flight -= 1
        done += REQ
    return t

print(f"{'N':>4} {'time_us':>9} {'GB/s':>7}")
for n in (1, 2, 4, 8, 16, 24, 32, 64):
    ns = simulate(n)
    print(f"{n:>4} {ns / 1000:>9.1f} {TOTAL / ns:>7.2f}")
Observations
Record the time and GB/s for each N in each of the three runs.
Questions
  1. At which N does throughput stop rising in the baseline run? Why?
  2. What happens to that knee when RTT grows to 2.4 µs?
  3. Why does halving REQ reduce throughput at small N but barely change the plateau?
Expected reasoning
Below the knee, bandwidth ≈ N × REQ / RTT; above it, the link serialisation term dominates; a longer RTT moves the knee to higher N; smaller requests halve the bytes per round trip but leave the link ceiling unchanged (apart from slightly more per-TLP overhead on the request path, which this model ignores).
Solution

Baseline: N = 4 gives about 1.2–1.3 GB/s (≈ 103 µs for 128 KiB), N = 16 about 4.7 GB/s, and the curve flattens from about N = 24 upward, where 24 × 512 B / 1.6 µs ≈ 7.7 GB/s exceeds the link's effective rate. The plateau the script prints (about 6.6 GB/s) is below the steady-state 7.2 GB/s because a 128 KiB transfer lasts only about 20 µs and the first round trip (1.6 µs of empty link) is included in the total. With RTT 2.4 µs, the knee moves to about N = 34–36 (because N × 512 / 2.4 µs must exceed ≈ 7.2 GB/s); at N = 32 you are still slightly read-limited (about 6.0 GB/s versus 6.4 GB/s at N = 64). With REQ = 256, each round trip carries half the bytes, so small-N throughput halves, but the plateau is the same link ceiling. The real-world lesson: a controller needs enough outstanding reads to cover the platform's worst realistic round trip, and IOMMU or switch latency directly eats WRITE bandwidth when it does not have them. Exact numbers vary with Python's floating-point output but the shape is the point.

Procedure
  1. Establish what the controller did, using only the analyzer row.
  2. Establish what the host's translation state was at the time of each command's data writes.
  3. Form at least three hypotheses and assign evidence for and against each.
  4. Propose the disambiguating experiment and the fix.
Questions
  1. Where did CID 0x3042's data most plausibly land?
  2. Why did neither NVMe nor AER report anything?
  3. What is the risk to other data on the system?
Expected reasoning
The same IOVA was reused 11 µs after an unmap whose IOTLB flush was deferred; if the IOMMU (or the device, via ATS) still held the old translation, writes to IOVA 0x2_0C42_1000 would land at P1.
Solution

The controller behaved correctly: the analyzer shows the right IOVA, payload and ordering. The failure is in translation. CID 0x2041 used IOVA 0x2_0C42_1000 → P1; it was unmapped at 4210.003291 with a deferred IOTLB invalidation, and the same IOVA was immediately reallocated to CID 0x3042 → P2. In a correct lazy-invalidation design, an IOVA is not reused until the deferred flush completes; the evidence shows reuse within 11 µs, so either the IOVA allocator in this driver change bypassed the deferred-free queue, or an invalidation was lost. If a stale translation (IOVA → P1) was still cached, CID 0x3042's data went to P1, which may now belong to someone else: silent corruption of an unrelated page, which is the real risk. The application at P2 saw old contents because nothing was written there.

No NVMe or AER error appeared because every TLP was legal and every write was accepted; translation succeeded, just to the wrong place. Hypotheses: (1) IOVA reused before IOTLB invalidation (supported by the 11 µs reuse and the driver change; against: none yet); (2) controller wrote to a stale address (rejected: analyzer shows the correct IOVA); (3) application race (rejected: the checksum failed after completion and the content was the pre-read content, not partial); (4) device-side ATS cache stale (possible if ATS is enabled; check the ATS capability's Enable bit in lspci). Disambiguating experiment: switch the IOMMU to strict invalidation (for example the kernel's strict mode parameter, on a test system) and rerun; the failure should vanish if (1) is right; additionally, fill P1 with a canary pattern after unmap and check it for overwrites. Fix: restore deferred-free semantics for IOVAs in the driver change. Confidence: high for a translation-lifetime fault, medium for which mechanism (IOMMU IOTLB vs device ATS) until the experiment runs. Regression test: a stress test that maps, unmaps and remaps small IOVA ranges at maximum rate with canary checking, run in lazy mode.

Debugging

Five DMA failure patterns, each one something the chapters mentioned only in passing. (DMA with no command outstanding is usually Host Memory Buffer traffic; see the advanced interview questions.)

Pattern 1 — IOMMU fault on a device read, WRITE fails with Data Transfer Error

SymptomWrite I/O errors; kernel log shows an IOMMU fault naming 01:00.0 with a read access, and an NVMe error with status SCT 0h / SC 04h.
Possible causesBuffer unmapped before the command completed (use-after-unmap); PRP entry computed wrongly; stale PRP list page reused; IOMMU domain detached during a reset.
EvidenceFault address; the command's PRPs (tracepoint or analyzer); root-port AER UR with header log.
First checkIs the fault address inside the command's described ranges? Decode the header log or the SQE.
Second checkWas that IOVA mapped at the time? Compare IOMMU map/unmap events with the command's lifetime.
Disambiguating experimentRun with IOMMU strict mode and debug assertions in the driver that every PRP entry lies within a live mapping.
Likely conclusionInside the range but unmapped → driver lifetime bug. Outside every range → pointer construction bug (driver) or controller address arithmetic (check analyzer).
ConfidenceHigh once the address is matched to the SQE; the layer is determined by evidence, not by who logged.

Pattern 2 — Commands time out with no SQE fetch after a reset

SymptomAfter a Function Level Reset or a user-space driver handover, every command times out; CSTS reads look healthy.
Possible causesBus Master Enable left clear; IOMMU domain not re-attached; queue base addresses programmed with stale IOVAs.
Evidencelspci Control line (BusMaster−); analyzer shows doorbells but no MRd from 0x0100; IOMMU faults (if BME is set but mapping missing).
First checkBusMaster+ or −? Read the Command register.
Second checkIf BME is set: any IOMMU fault at the SQ base address?
Disambiguating experimentCapture the first 10 µs after a doorbell: no MRd at all → BME or controller; MRd answered with UR → mapping.
Likely conclusionBME clear: host software sequencing bug. UR on SQ fetch: missing mapping for the queue memory.
ConfidenceHigh; the two cases leave different evidence.

Pattern 3 — WRITE throughput far below expectations, READ fine

SymptomSequential write bandwidth plateaus at a fraction of the link while reads reach near link rate.
Possible causesToo few outstanding reads (controller design, tag enables), long round-trip time (IOMMU misses, switch latency, remote NUMA memory), small MRRS, bounce buffering.
EvidenceAnalyzer: maximum tags in flight, RTT per read, MRd size. Host: CPU time in memcpy (bounce), NUMA placement of buffers.
First checkMaxReadReq in DevCtl and the MRd lengths actually used.
Second checkOutstanding reads × size / RTT from a short capture; compare with measured bandwidth.
Disambiguating experimentRepeat with IOMMU passthrough and with buffers on the SSD's local NUMA node; RTT changes → platform; N unchanged and low → controller.
Likely conclusionThe bound N × S / R matches the measurement; the factor that is smallest relative to design is the cause.
ConfidenceHigh when the formula reproduces the measured rate within about 10 %.

Pattern 4 — Fatal Malformed TLP from the SSD under specific buffer layouts

SymptomOccasional link resets during I/O with particular applications; AER reports a fatal Malformed TLP at the root port with the SSD as requester.
Possible causesMPS mismatch along the path; DMA engine crossing 4 KiB; illegal Length/byte-enable combination for a short transfer.
EvidenceRoot port AER Header Log: Length, address, byte enables.
First checkHeader Length vs root port MPS (MPS case) and address + length vs the next 4 KiB line (boundary case).
Second checkCorrelate the address with the application's buffer offsets (unaligned buffers reveal boundary bugs).
Disambiguating experimentReproduce with buffers at offsets 0xF00–0xFFC within a page on a test system; force MPS consistent on the path.
Likely conclusionHeader shows a 4 KiB crossing → controller firmware; header Length > MPS with consistent settings → controller; inconsistent settings → configuration.
ConfidenceHigh; the header is direct evidence of the TLP.

Pattern 5 — "Successful" READs that return stale data

SymptomRare application data mismatches after successful reads; no errors anywhere.
Possible causesPosted writes dropped by the IOMMU (fault logged but ignored); IOVA reuse before invalidation; No Snoop coherence problem; CQE posted before data (controller); application reading before completion.
EvidenceIOMMU fault log; IOMMU map/unmap timing; DevCtl NoSnoop; analyzer ordering of CQE vs data and attribute bits.
First checkAny IOMMU fault for 01:00.0 with a write access around the failures.
Second checkAnalyzer: does every CQE follow all of its command's data, and does any CQE carry RO = 1?
Disambiguating experimentToggle one variable at a time on a test system: strict IOMMU; Enable No Snoop off; polling off. Watch which change removes the failure.
Likely conclusionDepends on which toggle cures it; the trace view's ambiguous case shows why the link alone cannot decide.
ConfidenceLow until an experiment isolates one variable; report it that way.

Interview

Beginner

  1. In an NVMe READ, which side issues the data TLPs, and what type are they?

    Model answer

    The controller issues them, as posted Memory Write requests to the host buffer addresses from the PRP or SGL. The host issues no data TLPs.

  2. Why does a WRITE need completions on the link but a READ's data does not?

    Model answer

    For a WRITE the controller must fetch data, which is a Memory Read, a non-posted request that is answered with Completions with Data. For a READ the controller pushes data with posted writes, which have no completions.

  3. What is Bus Master Enable and what happens if it is clear?

    Model answer

    A bit in the PCI Command register that permits the function to issue memory requests. If clear, the controller cannot fetch commands or move data, so doorbells are never followed by fetches and commands time out.

  4. What is an IOVA?

    Model answer

    An I/O virtual address: the address the device is given and puts in its TLPs. The IOMMU translates it to a physical address. Analyzer addresses are IOVAs when an IOMMU is in translated mode.

  5. How many 256-byte Memory Writes carry a 4 KiB READ on the lab system?

    Model answer

    Sixteen, since MPS is 256 bytes and an aligned 4 KiB page splits evenly.

Intermediate

  1. Explain MPS, MRRS and RCB and which TLPs each one limits.

    Model answer

    MPS limits the payload of any TLP with data (MWr and CplD). MRRS limits how many bytes one MRd may request. RCB defines the address alignment at which a completer may split a read's completions. Together they decide how a DMA transfer becomes TLPs.

  2. A buffer starts at offset 0xF80 in its page. What does the controller have to do differently?

    Model answer

    Transfer only 128 bytes from the first page (to 0x…FFF), then continue at the next PRP entry's page, and never issue a request that crosses the 4 KiB boundary. Reads and writes must be cut at 0x…1000 regardless of MPS/MRRS.

  3. Why are SQs and CQs usually allocated as coherent DMA memory and data buffers mapped as streaming?

    Model answer

    Queues are long-lived and shared continuously between CPU and device, so they need memory that is always coherent without explicit sync calls. Data buffers belong to one I/O, so they are mapped for that I/O's duration and, on non-coherent platforms, synced at map/unmap time.

  4. What is the PRP list fetch and when does it occur?

    Model answer

    When a transfer spans more than two memory pages, PRP2 points to a list of page addresses, and the controller reads that list with a Memory Read. When it does so is implementation-dependent: right after the SQE fetch or just before the data phase. It is DMA like any other and can fault like any other.

  5. How can an IOMMU-blocked DMA write produce a successful NVMe completion?

    Model answer

    Posted writes receive no completion, so the controller never learns that the root complex dropped it. It posts a success CQE; only the host's IOMMU fault log reveals the loss.

Advanced

  1. Derive the WRITE-direction bandwidth bound and use it on a Gen4 x4 link with 8 outstanding 512-byte reads and 2 µs round trip.

    Model answer

    B ≤ min(N × S / R, B_link) = min(8 × 512 / 2 µs, ≈ 7.2 GB/s) = min(2.05 GB/s, 7.2 GB/s) = 2.05 GB/s. The device is read-limited; it needs about 28 outstanding reads to reach the link.

  2. Where may an NVMe controller use Relaxed Ordering, and where must it not?

    Model answer

    It may set RO on bulk data writes, which may then pass each other. It must not set RO on the CQE write (or the MSI-X write), because those must not pass earlier data writes. RO also requires the Enable Relaxed Ordering bit in Device Control.

  3. What risks does No Snoop introduce and who controls it?

    Model answer

    No Snoop tells the root complex it need not snoop CPU caches, which can leave stale cached copies if software did not prepare. The device sets it per TLP only if Enable No Snoop is set in Device Control; whether the platform honours it is platform-dependent.

  4. Explain how an IOTLB invalidation policy can corrupt data without any error report.

    Model answer

    If an IOVA is unmapped with a deferred invalidation and reused before the flush, the cached translation may still point at the old physical page; the device's legal writes land there. Every protocol layer sees success.

  5. Why does the Host Memory Buffer complicate trace analysis?

    Model answer

    Because the controller accesses HMB at any time, independent of commands, producing DMA reads and writes that do not correlate with any SQE. You must exclude HMB ranges (from the HMB descriptor list) before calling DMA an orphan.

Senior

  1. A customer reports a "DMA bug in your SSD" with IOMMU faults. How do you determine whose bug it is?

    Model answer

    Get the fault address and access type, the command's PRPs (tracepoint or capture), and the map/unmap timeline. If the address is within the command's described ranges and was unmapped at the time, the host's mapping lifetime is wrong. If it is outside every described range, either the driver built the pointer wrongly (check the SQE as the controller fetched it) or the controller miscomputed (the fetched SQE is right but the TLP address differs). The analyzer comparison of SQE payload and TLP address is decisive.

  2. Design a validation matrix for an SSD's DMA engine.

    Model answer

    Axes: first-page offset (0, small, near end of page), transfer length (sub-page, page-exact, page plus one, MDTS), PRP vs SGL with odd descriptor sizes, MPS 128/256/512, MRRS 128 to 4096, RCB 64/128, IOMMU strict/lazy/passthrough, RO and NS enables, tag modes (8/10-bit), injected UR/CA/poisoned completions and completion drops, HMB on/off. Oracle: data pattern check, analyzer rule checker (4 KiB, MPS, MRRS, CQE after data), expected NVMe status for injected faults.

  3. How would you argue for more outstanding read engines in a next-generation controller?

    Model answer

    Quantify N = B_link × R / S for the target link (for example Gen5 x4 ≈ 14.5 GB/s effective) and the worst realistic round trip on target platforms (IOMMU misses, switches, remote NUMA): at 2.5 µs and 512-byte reads you need about 70 outstanding reads, which also requires 10-bit tags. Show measured R distributions from customer platforms.

  4. A trace shows perfect DMA but the application sees wrong data. What is your plan?

    Model answer

    State that the link proves only delivery to the root complex. Collect IOMMU events, check NS and RO attributes, check polling behaviour and the application's completion handling, and design single-variable toggles. Report confidence as low until one toggle isolates the cause.

  5. What changes in DMA analysis when the SQ lives in the Controller Memory Buffer?

    Model answer

    The SQE fetch disappears from the link because the controller reads its own memory; instead the host writes the SQE into the device BAR with MMIO writes (host→device MWr). Correlation must then key on host writes into the CMB range, and the data path may still be host memory. Peer-to-peer use of CMB further moves traffic through switches without the root complex.

Quiz

  1. Which TLP carries READ command data from the SSD to the host?

    • CplD from the root complex
    • Posted Memory Write from the SSD
    • Memory Read from the SSD
    • Message TLP
    Answer and reasoning

    The controller pushes READ data with posted Memory Writes. CplD carries data only in answer to a read request.

  2. On the lab system, how many MRd TLPs are needed at minimum to pull a page-aligned 8 KiB WRITE?

    • 2
    • 8
    • 16
    • 32
    Answer and reasoning

    8192 / 512 (MRRS) = 16 requests. Thirty-two is the minimum number of completions.

  3. Which statement about the 4 KiB rule is correct?

    • It is a PCIe rule that applies to every memory request regardless of IOMMU page size
    • It comes from NVMe's 4 KiB memory page size
    • It applies only to Memory Writes
    • It applies only when an IOMMU is present
    Answer and reasoning

    The PCI Express Base Specification forbids memory requests crossing a 4 KiB boundary, independent of NVMe settings or IOMMU.

  4. The SSD writes READ data to an IOVA the IOMMU has no mapping for. What does the SSD see?

    • A UR completion
    • An ERR_FATAL message
    • A NAK DLLP
    • Nothing
    Answer and reasoning

    Posted writes get no completion. The SSD sees nothing and will normally post a success CQE.

  5. Which TLP must not carry Relaxed Ordering for NVMe's completion semantics to hold?

    • A data MWr in the middle of a page
    • The SQE fetch MRd
    • The CQE MWr
    • A PRP list MRd
    Answer and reasoning

    The CQE must not pass the data writes, so it must have RO clear.

  6. A controller keeps 6 reads of 512 B outstanding and the round trip is 1.5 µs. What is the bound on pull bandwidth (ignoring the link)?

    • 1.0 GB/s
    • 2.05 GB/s
    • 3.4 GB/s
    • 7.2 GB/s
    Answer and reasoning

    6 × 512 / 1.5 µs = 3072 B / 1.5 µs ≈ 2.05 GB/s.

  7. Why can DMA appear on the link when no NVMe command is outstanding? Name the most common legitimate reason and how to confirm it.

    Model answer

    The Host Memory Buffer: the controller uses granted host memory for its own tables at any time. Confirm by matching addresses against the HMB descriptor list and checking the HMB feature and the controller's HMPRE/HMMIN in Identify Controller.

  8. Explain why the first abnormal event and the root cause may be different rows in a DMA failure trace. Give an example.

    Model answer

    The bad value often enters the trace earlier as a normal-looking payload, for example a wrong PRP2 inside a successful SQE fetch completion; the first abnormal event is later, when the controller acts on it and receives a UR. Trace the abnormal event back to the data it depended on.

  9. What does the analyzer prove, and fail to prove, when all DMA writes for a READ are present and correct?

    Model answer

    It proves the TLPs crossed this link with the right addresses, payloads, order and attributes. It does not prove translation to the right physical page, coherence with CPU caches, or that the application read after completion.

  10. What does a bounce buffer do to the DMA picture, and when is it used?

    Model answer

    The device DMAs to or from a separate reachable buffer and the CPU copies between it and the real buffer. It is used when the device cannot address the real memory (DMA mask too small) or in confidential-computing guests whose memory is not directly accessible. It costs CPU time and latency and makes the analyzer addresses refer to the bounce pool.

Teach-back

Explain DMA with NVMe three times, to three audiences. Write your version first, then compare with the model.

  1. To a child. Why does the kitchen helper not need the teacher to carry trays, and what does the hall monitor do?

    Model explanation

    The teacher writes on a note exactly which shelves to use and rings a bell. The helper comes, reads the note and carries everything herself, so the teacher can keep teaching. The hall monitor checks every shelf number the helper uses; if a number is not on today's list, the helper is stopped and the monitor writes it down. Delivering is quick because the helper just drops things off; collecting is slower because she has to ask for each tray and wait.

  2. To a junior engineer. How do the bytes of a 16 KiB read get into the application's buffer?

    Model explanation

    The driver maps the buffer through the DMA API, which gives it device addresses (IOVAs). It puts the first page address in PRP1 and, since there are four pages, a pointer to a PRP list in PRP2. After the doorbell, the controller fetches the SQE and the PRP list with Memory Reads, reads the media, then writes the data with posted Memory Writes of at most 256 bytes each, never crossing a 4 KiB boundary. The IOMMU translates each address. Only after the last data write does the controller post the CQE and the MSI-X, and PCIe ordering keeps them behind the data. The driver unmaps the buffer after it consumes the CQE.

  3. To a senior engineer. What are the invariants of NVMe DMA, and which ones can fail silently?

    Model explanation

    Invariants: (1) every TLP address lies within the command's described ranges or the controller's own structures (SQ, CQ, PRP lists, HMB); (2) every address is mapped for the device's whole use; (3) TLPs obey MPS, MRRS and the 4 KiB rule; (4) the CQE follows all of the command's data writes, with RO clear; (5) for WRITEs, all data completions arrive before the CQE. Violations of (3) are loud (Malformed TLP). Violations of (1) and (2) are loud for reads (UR completions, Data Transfer Error) and silent for writes (IOMMU fault only, success CQE). Translation-lifetime and coherence faults are silent on the link altogether. So the tools for silent cases are host-side: IOMMU tracing, strict mode, canaries, and data verification under polling.
