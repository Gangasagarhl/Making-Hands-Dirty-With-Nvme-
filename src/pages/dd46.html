This module takes the Computational Programs Command Set from "I know the four steps" to "I can prove what a program run did, when it did it, and why it failed". It goes past Chapter 61 into program and range-set lifecycles as state machines, concurrency between executions, the PCIe traffic of a program download, abort and cancel semantics, duplicate-execution forensics, and validation plans that try hard to break the containment model.

Orientation

Chapter 61 introduced computational storage in NVM Express (NVMe): compute namespaces that hold programs, memory range sets that confine what a program may touch, and the copy → execute → read job that keeps bulk data inside the subsystem. It gave you the bottleneck model and one hung-program trace. This module assumes all of that and asks harder questions. What states can a program index be in, and which commands move it between them? What happens when two executions share a range set, or when a range set is deleted while a program still runs? What does a 192 KiB program download look like on a PCI Express (PCIe) analyzer? When a host times out, aborts and retries an Execute Program, how do you prove whether the program ran once or twice?

Read Computational Programs first (entities, lifecycle, bottleneck model, the hung-program trace). You also need Subsystem Local Memory for memory namespaces and copy paths, NVMe Errors for status fields, NVMe Reset for what a controller reset discards, and Command-to-TLP Correlation for matching Submission Queue Entries (SQEs) to Transaction Layer Packets (TLPs). The companion module is Subsystem Local Memory; after this module, Validation Engineering and Senior Architecture use computational storage as a case study.

Kid story

Deep under a museum there is a sealed vault full of old treasures. Nobody is allowed inside — not even the museum director. Inside the vault lives a careful robot.

The robot already knows a few jobs, printed on numbered cards hanging on its wall: card 0 says "count the coins", card 1 says "find every blue vase". The director can also slide a new card through the letterbox, but the robot will not use a new card until the director sends a second note saying "card 2 is approved".

Before any job, the director tells the robot which trays it may use: "Today you may use tray A to look at things and tray B to put your answers on." The robot's arms simply cannot reach any other tray.

Then the director posts a job slip: "Do card 1, with trays A and B." The robot works quietly for a long time. Nobody outside can see it working. When it finishes, it posts back one slip: "Done — I found 7 blue vases, the list is on tray B." Only then does the director ask for tray B's list to be passed out through the letterbox.

The most dangerous gap: the robot can be trusted. A downloaded program is arbitrary code inside a device that may hold data for many tenants. Everything in this module about lockdown, verifiers and range-set attacks exists because the analogy's "careful robot" is an assumption, not a property.

Two state machines you must be able to draw

Illegal transitions are where validation finds bugs: executing an inactive program, loading into an active index, deactivating a program with executions in flight, deleting a range set that a running execution references, creating a range set that overlaps itself or exceeds a memory namespace. For each, the device should return a defined error status and change nothing. Derived The specification defines which of these are errors and with which status; this course does not state the status values.

The central concept on the ladder: a contained, asynchronous program run

The vault robot does a numbered, approved job on the trays it was given, and only says "done" when finished.

An execution is a command naming an active program and a range set; it runs asynchronously and completes with a status and a result. Everything it touches must be inside the range set.

The controller's dispatcher queues the run for a compute engine; the engine accesses SLM through a bounds checker or a memory-protection unit configured from the range set; DRAM bandwidth and engine clock (and thermal throttling) set the run time.

Computational Programs 1.3 defines programs, activation, range sets and Execute Program; SLM 1.3 defines the memory; Base 2.4 defines CSI, Abort, Cancel, lockdown and reset. What the spec leaves to the device: engine count, scheduling, sandboxing technique, abortability of running code.

One I/O SQE in, possibly one parameter-buffer read, one CQE out. No ordering against other commands. Errors are command statuses; hangs are absences.

A tiny burst, then silence measured in milliseconds to seconds, then a CQE. The silence length is the only external measurement of the run, so timestamps are evidence.

Classify by time-to-completion and status: immediate error = validation; error after compute time = program fault; success but late = throttling or contention; no completion = hang; success with wrong data = host ordering or range bug.

The sixteen questions, answered for a memory range set

1. What is it?
A named list of SLM ranges that bounds one or more program executions.
2. Why was it created?
To give the device a validated, compact description of what a program may access, so it can enforce containment cheaply.
3. What problem does it solve?
Untrusted or buggy code reading or corrupting other data in device memory, and the cost of per-access permission checks.
4. What existed before?
Vendor-specific buffer handles on proprietary computational storage drives; accelerator cards with their own driver-managed buffers.
5. Why is the current design better?
Standard, transport-independent, created once and reused across executions, and separable from the program itself.
6. Who creates it?
The host, with Memory Range Set Management.
7. Who consumes it?
The dispatcher and the compute engine's bounds enforcement.
8. Where does it live?
In a device-side table associated with the compute namespace.
9. What memory/registers are involved?
The descriptor buffer in host memory (read once by DMA) and the SLM ranges themselves.
10. What happens before it?
The memory namespace exists and is attached; the host has planned offsets that do not collide with other jobs.
11. What happens after it?
Executions reference it; the host deletes it when no execution needs it.
12. What happens if it is wrong?
Creation fails (bounds), the program faults (too small), or results are silently wrong (wrong offsets, overlapping sets used concurrently).
13. What does the analyzer show?
An admin SQE, one small device MRd for descriptors, and a CQE. Never the enforcement itself.
14. What does Linux show?
Nothing natively; a computational storage library's logs, or pass-through results.
15. What would a validation engineer test?
Off-by-one boundaries, overlapping ranges, maximum ranges per set, deletion during execution, reuse of a deleted set ID, cross-tenant visibility.
16. What would a senior engineer suspect when it fails?
Host-side lifetime bugs (set deleted or reused too early) and overlapping output ranges among concurrent executions — long before suspecting the device.

Identifiers as encoded in libnvme 1.16.2, which tracks the Base specification: CSI 04h for Computational Programs (and CSI 03h for SLM); admin opcodes Load Program 85h, Program Activation Management 88h, Memory Range Set Management 89h; Abort 08h; I/O Cancel 18h. Treat these as well-sourced and still confirm them in the Base 2.4 tables before shipping a decoder.

This module does not state, and you must read from Computational Programs 1.3: the Execute Program opcode; its parameter encoding and the size of any inline parameter area; which completion dwords carry the program result; the memory range descriptor layout and alignment; maximum ranges per set; status codes for inactive programs, invalid sets and program faults; whether Load Program supports partial (offset) transfers; whether an "unload" operation exists separately from activation management.

The specification does not say how long a program may run, how a device stops a runaway program, or what a device-defined program computes beyond its documentation. It does not define host timeouts — those are host policy.

Never assume: that Abort or Cancel stops a running program; that downloaded programs survive a controller reset, firmware activation or power cycle; that program indexes are stable across firmware versions; that a successful completion means the program ran exactly once.

Contention is the hardware fact most often missed. Compute engines, the flash translation layer (FTL) and the SLM share the controller's DRAM bandwidth. A heavy program can slow ordinary reads on namespace 1, and a heavy write workload can slow programs. A validation plan that measures programs only on an idle drive measures a device nobody deploys.

Unobservable internals that still matter: how the dispatcher assigns executions to engines (first-free, round-robin, per-queue affinity); whether an engine can be pre-empted; whether the bounds checker is hardware (cheap per access) or software (cost per access, which changes run time with access pattern); and whether engine-local scratch memory is cleared between runs (a confidentiality question for multi-tenant systems).
