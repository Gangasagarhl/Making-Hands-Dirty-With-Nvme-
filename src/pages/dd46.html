This module takes the Computational Programs Command Set from "I know the four steps" to "I can prove what a program run did, when it did it, and why it failed". It goes past Chapter 61 into program and range-set lifecycles as state machines, concurrency between executions, the PCIe traffic of a program download, abort and cancel semantics, duplicate-execution forensics, and validation plans that try hard to break the containment model.

Orientation

Chapter 61 introduced computational storage in NVM Express (NVMe): compute namespaces that hold programs, memory range sets that confine what a program may touch, and the copy → execute → read job that keeps bulk data inside the subsystem. It gave you the bottleneck model and one hung-program trace. This module assumes all of that and asks harder questions. What states can a program index be in, and which commands move it between them? What happens when two executions share a range set, or when a range set is deleted while a program still runs? What does a 192 KiB program download look like on a PCI Express (PCIe) analyzer? When a host times out, aborts and retries an Execute Program, how do you prove whether the program ran once or twice?

Read Computational Programs first (entities, lifecycle, bottleneck model, the hung-program trace). You also need Subsystem Local Memory for memory namespaces and copy paths, NVMe Errors for status fields, NVMe Reset for what a controller reset discards, and Command-to-TLP Correlation for matching Submission Queue Entries (SQEs) to Transaction Layer Packets (TLPs). The companion module is Subsystem Local Memory; after this module, Validation Engineering and Senior Architecture use computational storage as a case study.

Kid story

Deep under a museum there is a sealed vault full of old treasures. Nobody is allowed inside — not even the museum director. Inside the vault lives a careful robot.

The robot already knows a few jobs, printed on numbered cards hanging on its wall: card 0 says "count the coins", card 1 says "find every blue vase". The director can also slide a new card through the letterbox, but the robot will not use a new card until the director sends a second note saying "card 2 is approved".

Before any job, the director tells the robot which trays it may use: "Today you may use tray A to look at things and tray B to put your answers on." The robot's arms simply cannot reach any other tray.

Then the director posts a job slip: "Do card 1, with trays A and B." The robot works quietly for a long time. Nobody outside can see it working. When it finishes, it posts back one slip: "Done — I found 7 blue vases, the list is on tray B." Only then does the director ask for tray B's list to be passed out through the letterbox.

The most dangerous gap: the robot can be trusted. A downloaded program is arbitrary code inside a device that may hold data for many tenants. Everything in this module about lockdown, verifiers and range-set attacks exists because the analogy's "careful robot" is an assumption, not a property.

Two state machines you must be able to draw

Illegal transitions are where validation finds bugs: executing an inactive program, loading into an active index, deactivating a program with executions in flight, deleting a range set that a running execution references, creating a range set that overlaps itself or exceeds a memory namespace. For each, the device should return a defined error status and change nothing. Derived The specification defines which of these are errors and with which status; this course does not state the status values.

The central concept on the ladder: a contained, asynchronous program run

The vault robot does a numbered, approved job on the trays it was given, and only says "done" when finished.

An execution is a command naming an active program and a range set; it runs asynchronously and completes with a status and a result. Everything it touches must be inside the range set.

The controller's dispatcher queues the run for a compute engine; the engine accesses SLM through a bounds checker or a memory-protection unit configured from the range set; DRAM bandwidth and engine clock (and thermal throttling) set the run time.

Computational Programs 1.3 defines programs, activation, range sets and Execute Program; SLM 1.3 defines the memory; Base 2.4 defines CSI, Abort, Cancel, lockdown and reset. What the spec leaves to the device: engine count, scheduling, sandboxing technique, abortability of running code.

One I/O SQE in, possibly one parameter-buffer read, one CQE out. No ordering against other commands. Errors are command statuses; hangs are absences.

A tiny burst, then silence measured in milliseconds to seconds, then a CQE. The silence length is the only external measurement of the run, so timestamps are evidence.

Classify by time-to-completion and status: immediate error = validation; error after compute time = program fault; success but late = throttling or contention; no completion = hang; success with wrong data = host ordering or range bug.

Identifiers as encoded in libnvme 1.16.2, which tracks the Base specification: CSI 04h for Computational Programs (and CSI 03h for SLM); admin opcodes Load Program 85h, Program Activation Management 88h, Memory Range Set Management 89h; Abort 08h; I/O Cancel 18h. Treat these as well-sourced and still confirm them in the Base 2.4 tables before shipping a decoder.

This module does not state, and you must read from Computational Programs 1.3: the Execute Program opcode; its parameter encoding and the size of any inline parameter area; which completion dwords carry the program result; the memory range descriptor layout and alignment; maximum ranges per set; status codes for inactive programs, invalid sets and program faults; whether Load Program supports partial (offset) transfers; whether an "unload" operation exists separately from activation management.

The specification does not say how long a program may run, how a device stops a runaway program, or what a device-defined program computes beyond its documentation. It does not define host timeouts — those are host policy.

Never assume: that Abort or Cancel stops a running program; that downloaded programs survive a controller reset, firmware activation or power cycle; that program indexes are stable across firmware versions; that a successful completion means the program ran exactly once.

Contention is the hardware fact most often missed. Compute engines, the flash translation layer (FTL) and the SLM share the controller's DRAM bandwidth. A heavy program can slow ordinary reads on namespace 1, and a heavy write workload can slow programs. A validation plan that measures programs only on an idle drive measures a device nobody deploys.

Unobservable but important: how executions are assigned to engines, whether an engine can be pre-empted, whether bounds checking is hardware or software (software checks make run time depend on access pattern), and whether engine scratch is cleared between runs (a multi-tenant confidentiality question).

Request/response. Each NVMe command gets exactly one CQE; underneath, each DMA read is a non-posted PCIe request answered by Completions with Data (CplD), and each doorbell or DMA write is posted. Keep the layers apart: an Execute Program "response" may come seconds after its SQE fetch, while every TLP-level read inside it completes within microseconds.

Ordering. NVMe orders no commands, within or across queues Normative; copy → execute → read is a chain the host enforces by waiting for CQEs. On PCIe, result writes precede the posted CQE and cannot be passed by it (PCIe Ordering). Two executions on different queues may run concurrently in either order; overlapping output ranges then give undefined content Derived. Lifecycle commands racing an in-flight execution are the classic validation corner.

Labs

Safe lab All four labs are paper, simulation or analysis of synthetic evidence.

Beginner lab — predict lifecycle outcomes

Objective: predict accept or reject for each command. Prerequisites: the state machines above. Setup: index 0 device-defined and active, indexes 1–3 empty; 4 GiB memory namespace.

Procedure: (1) Execute index 1 on set 7. (2) Create set 7 = {0, 1 GiB}, {1 GiB, 64 MiB}. (3) Load index 1. (4) Execute index 1 on set 7. (5) Activate index 1. (6) Execute index 1 on set 7 (keeps running). (7) Delete set 7. (8) Deactivate index 1. (9) Load index 0. (10) Create set 8 = {0, 2 MiB}, {1 MiB, 1 MiB}.

Observations and questions: write accept/reject with a reason. Which rejections concern state and which arguments? Which steps might differ between implementations? Expected reasoning: track both state machines; an execution holds references to an index and a set.

Solution

1 reject (empty index); 2 accept; 3 accept; 4 reject (inactive); 5 accept; 6 accept; 7 reject (set referenced); 8 reject (execution in flight); 9 reject (device-defined); 10 reject (overlap within a set). State: 1, 4, 7, 8, 9; arguments: 10. Steps 7, 8 and 10 may legitimately differ (deferred deletion, deactivation for future runs only, whether in-set overlap is forbidden) — mark them "check CP 1.3".

Extension: add firmware activation as an event and list what you would test survives it.

Intermediate lab — add lifecycles and references to the Chapter 61 model

Objective: make the behavioural model of Chapter 61 (cp_sim.py) enforce the state machines. Prerequisites: beginner lab. Setup: a copy of cp_sim.py.

Procedure: (1) Split execute() into start(eid, index, rsid) and finish(eid) and keep a reference count per set and a running count per index. (2) Make delete_range_set() and deactivation refuse while referenced. (3) Reject ranges that overlap within one set. (4) Add a host-side helper overlaps(set_a, set_b). (5) Replay the beginner-lab sequence and compare.

Observations and questions: Why should the device accept a set that overlaps another set? What happens to SLM if finish() is never called? Expected reasoning: overlap across sets is a valid pipeline design; only concurrent writers make it unsafe, which only the host knows.

Solution 
def start(self, eid, index, rsid):
    p = self.programs.get(index)
    if p is None or not p["active"]: raise CPError("program missing or not active")
    if rsid not in self.range_sets:  raise CPError("no such range set")
    self.running[eid] = (index, rsid); self.refs[rsid] = self.refs.get(rsid, 0) + 1

def finish(self, eid):
    index, rsid = self.running.pop(eid); self.refs[rsid] -= 1

def delete_range_set(self, rsid):
    if self.refs.get(rsid): raise CPError("range set referenced by a running execution")
    del self.range_sets[rsid]

A never-finished execution pins its set forever: the SLM it covers cannot be reclaimed until abort, cancel or reset. Your replay should match the beginner solution.

Extension: add tenants and assert no tenant can execute on another tenant's set.

Advanced lab — pipeline makespan with limited SLM

Objective: quantify how buffer and engine counts change a chunked job. Prerequisites: Chapter 61 worked example. Setup: save and run python3 cp_pipeline.py.

#!/usr/bin/env python3
"""cp_pipeline.py - makespan of a chunked copy -> execute -> read job
with B SLM buffers (B=1: serial, B=2: double buffering, B=3: triple).
Rates are illustrative inputs, not device data. Resources: one internal
copy engine, E compute engines, one result-read path (PCIe)."""

def makespan(chunks, chunk_gib, copy_gbs, exec_gbs, read_mb, link_gbs, buffers, engines=1,
             cmd_us=20.0):
    gb = chunk_gib * 1.073741824                 # GiB -> GB
    t_copy = gb / copy_gbs + cmd_us * 1e-6
    t_exec = gb / exec_gbs + cmd_us * 1e-6
    t_read = (read_mb / 1000) / link_gbs + cmd_us * 1e-6
    copy_free, read_free = 0.0, 0.0
    eng_free = [0.0] * engines
    buf_free = [0.0] * buffers                   # time each SLM buffer becomes reusable
    end = 0.0
    for k in range(chunks):
        b = k % buffers
        c0 = max(copy_free, buf_free[b]); c1 = c0 + t_copy; copy_free = c1   # copy waits for buffer
        e = min(range(engines), key=lambda i: eng_free[i])
        x0 = max(c1, eng_free[e]); x1 = x0 + t_exec; eng_free[e] = x1         # execute waits for copy CQE
        r0 = max(x1, read_free); r1 = r0 + t_read; read_free = r1             # read waits for execute CQE
        buf_free[b] = r1                                                      # buffer reusable after read
        end = max(end, r1)
    return end, t_copy, t_exec, t_read

if __name__ == "__main__":
    base = dict(chunks=64, chunk_gib=1.0, copy_gbs=6.0, exec_gbs=4.0, read_mb=8.0, link_gbs=7.0)
    print("64 x 1 GiB chunks; copy 6 GB/s, execute 4 GB/s, 8 MB result per chunk (illustrative)")
    for buffers, engines in [(1, 1), (2, 1), (3, 1), (2, 2), (3, 2), (4, 2)]:
        t, tc, te, tr = makespan(buffers=buffers, engines=engines, **base)
        print(f"  buffers={buffers} engines={engines}: makespan {t:7.2f} s")
    _, tc, te, tr = makespan(buffers=1, **base)
    print(f"  per chunk: copy {tc:.3f} s, execute {te:.3f} s, read {tr*1000:.2f} ms")
    print(f"  lower bounds: copy-bound {64*tc:.2f} s, single-engine execute-bound {64*te:.2f} s")

Procedure: explain each line with a bottleneck argument; rerun with exec_gbs=12 and with read_mb=2000. Questions: why does a third buffer help two engines but not one? What is the minimum buffer count for full overlap? Expected reasoning: a buffer is held from the start of its copy to the end of its read.

Solution

Serial: 64 × (0.179 + 0.268 + 0.001) ≈ 28.7 s. Two buffers, one engine: execution-bound ≈ 17.2 s plus fill; a third buffer cannot help an engine already busy all the time. Two engines make execution effectively 0.134 s/chunk, faster than the copy, but with two buffers both are often held by executing chunks and the copy stalls (14.5 s); three buffers reach the copy bound (≈ 11.7 s). Rule: buffers ≥ engines + 1. With exec_gbs=12 the copy dominates already at two buffers. With 2 GB results the PCIe read (≈ 0.29 s/chunk) becomes the bottleneck — selectivity too high for offload to pay.

Senior forensic lab — did the program run twice?

Objective: write a root-cause report for Trace D with confidence levels. Prerequisites: Error Correlation; Root Cause, Ambiguity and Forensic Reporting.

Setup (synthetic evidence): Trace D; library log "05.000 timeout cid=0x0161 → abort; abort result=not-aborted → resubmit as 0x0162"; vendor log "00.000 engine0 start idx2 set9; 05.204 engine1 start idx2 set9; 06.410 engine0 done; 11.920 engine1 done"; the log range holds 2,400 entries, keys of 1–1,200 repeated in 1,201–2,400, with 37 partial records.

Procedure: merge timelines (align clocks on the two CQEs); state the first abnormal event and the causal chain; classify claims as proven, probable or unproven; propose fix and regression test. Questions: which Trace D reading is selected? Why partial records? Was the 5 s timeout the root cause? Expected reasoning: separate trigger, defect and permitted device behaviour.

Solution

Reading (b): run 2 started at 5.204 s on engine 1 while run 1 ran on engine 0. Partial records are interleaved appends by two writers. First abnormal event: no CQE at the 5 s deadline. Chain: idle-baseline timeout → Abort cannot stop running code (allowed) → library treated "not aborted" as failure → resubmitted to the same set → concurrent runs → corrupt log. Proven: two concurrent runs and duplicates. Probable: run 1 was slow because the drive was busy (no telemetry says why). Unproven: whether CP 1.3 requires serialising runs that share a set — check it, and do not rely on it. Fix: never resubmit while the CID is outstanding; one output set per attempt; idempotent program design. Regression: inject "not aborted" and assert the library waits; assert it refuses concurrent overlapping outputs. The timeout was the trigger, not the root cause.

Extension: turn the report into a bug report using Engineering Bug Report Training.

Interview

Beginner

  1. What is a compute namespace?

    Model answer

    A namespace of the Computational Programs command set (CSI 04h per libnvme) holding programs at indexes; target of Execute Program; no LBAs.

  2. Loading vs activating?

    Model answer

    Load Program places the image; Program Activation Management makes it executable and is where verification happens.

  3. Why a memory range set?

    Model answer

    It bounds the SLM a run may touch, validated once by the device.

  4. Admin or I/O?

    Model answer

    Execute Program is I/O; Load Program, activation and range-set management are admin (85h, 88h, 89h in libnvme).

  5. Why is the trace of a big job quiet?

    Model answer

    Copy and compute are internal; only commands, completions and results cross PCIe.

Intermediate

  1. TLPs of a 192 KiB download on the lab system?

    Model answer

    Doorbell MWr32; SQE MRd64/CplD; PRP-list read; 384 image MRd64 of 512 bytes; ≥ 768 CplD of 256 bytes; CQE MWr64; MSI-X MWr32.

  2. Validation error or program fault, without decoding status?

    Model answer

    Time to completion: microseconds means validation; compute-scale time means a fault during the run.

  3. Is overlap between two sets a bug?

    Model answer

    Only when concurrent executions write the overlap; sequential pipelines share ranges by design.

  4. Abort says "not aborted". Now what?

    Model answer

    The command is still running: wait or reset; never resubmit to the same output.

  5. How to choose Execute timeouts?

    Model answer

    From measured worst-case run time (throttled, contended) per program and input size, set per command.

Advanced

  1. Pipeline 64 GiB through 4 GiB SLM with two engines.

    Model answer

    At least three buffers, each with its own set; copy into a free buffer, execute on its copy CQE, read on its execute CQE, release on the read CQE. Bottleneck = max(copy, execute/2, read).

  2. Which events can destroy program and set state?

    Model answer

    Controller, subsystem and function resets; firmware activation; power loss; possibly format or sanitize. Rediscover after any of them.

  3. Validate range-set enforcement.

    Model answer

    Adversarial ±1-byte accesses at every boundary, gaps between ranges, neighbouring sets, delete-vs-execute races, reuse of freed SLM; every violation faults and checksums of other ranges stay unchanged.

  4. What does activation latency tell you?

    Model answer

    Roughly how much verification or compilation the device performs. Evidence, not proof.

  5. Prove a program ran exactly once.

    Model answer

    One success CQE cannot. Use per-attempt output sets or idempotent programs, one outstanding CID per job, output duplicate checks, and device telemetry.

Senior

  1. Allow downloadable programs in the fleet?

    Model answer

    Only for a need device-defined programs cannot meet, with signed images, verifiable types, lockdown per interface, attacked isolation, telemetry and a firmware-activation and migration plan. Otherwise lock Load Program down.

  2. Vendor claims "10× faster analytics". Questions?

    Model answer

    Engine throughput under heat and concurrent I/O, benchmark selectivity, overlap, host baseline, abortability, telemetry, program-type portability, reset behaviour.

  3. How does incident response change?

    Model answer

    Link captures weaken; per-command timestamps, library logs, telemetry and output integrity checks dominate; retries become idempotence-aware; timeouts become per-program.

  4. What can leak between tenants besides range-set bytes?

    Model answer

    Uncleared engine scratch, timing side channels, shared indexes, logs containing others' parameters, SLM not cleared on reassignment.

  5. Where should dependency enforcement live?

    Model answer

    In the host library that knows the job graph; NVMe orders nothing and the driver is generic.

Quiz

  1. Minimum device read requests for a 192 KiB image at MRRS 512 bytes?

    • 48
    • 192
    • 384
    • 768
    Answer and reasoning

    196,608 / 512 = 384. 768 is the minimum completions at MPS 256; 48 is the 4 KiB page count.

  2. An Execute error arrives 0.7 µs after the SQE fetch. Most likely class?

    • Program fault
    • Command validation failure
    • Thermal throttling
    • PCIe completion timeout
    Answer and reasoning

    No compute time elapsed; the program never ran.

  3. Abort returns "not aborted" for a running Execute. Correct host action?

    • Resubmit to the same set
    • Delete the set
    • Mark failed and move on
    • Wait for the original CQE or reset the controller
    Answer and reasoning

    The command is still outstanding; resubmitting creates Trace D.

  4. Which statement about range sets is correct?

    • Sets may overlap other sets; concurrent writers to the overlap are the host's problem
    • Sets describe host memory for DMA
    • A set is single-use
    • Sets are created with an I/O command
    Answer and reasoning

    Sets describe SLM, are created by an admin command and are reusable.

  5. Two engines, copy faster than per-engine execution: minimum buffers for full overlap?

    • 1
    • 2
    • 3
    • 8
    Answer and reasoning

    Engines + 1.

  6. Best evidence that a slow run was throttled rather than contended?

    • The CQE status
    • A controlled rerun where slowness follows temperature, not concurrent I/O
    • Link speed
    • The program result
    Answer and reasoning

    A SMART reading alone is correlation.

  7. Why does a success CQE not prove a single run?

    Model answer

    A retry creates a second run with its own CID and its own success CQE; only output inspection, idempotence or telemetry shows how many runs touched the data.

  8. What changes in the trace over NVMe/TCP?

    Model answer

    Commands become CapsuleCmd/CapsuleResp PDUs, the image becomes in-capsule data or R2T + H2CData, results become C2HData; internal copy and compute stay invisible (NVMe/TCP).

Teach-back

Explain this module to three audiences, then compare with the models.

To a child — model

"A robot in a locked room knows some jobs. A new job card needs an OK note before it uses it. We say which trays it may use, ask for a job, and wait — maybe a long time — for its 'done' slip before asking for the answers. If we get impatient and ask again, it may do the job twice and make a mess."

To a junior engineer — model

"An index goes empty → loaded → active via Load Program and Program Activation Management; a set lives from create to delete and is referenced while runs use it. A job is create set, copy and wait, execute and wait, read and wait, delete. Each wait is for a CQE because NVMe orders nothing. On the analyzer, the download is device reads; the copy and compute are silences."

To a senior engineer — model

"The protocol is simple; the system is not. Run time depends on data and temperature, so timeouts are per-program. Abort is best effort, so retries can create concurrent runs on one output — Trace D. Containment rests on device-enforced sets and host scheduling; validation attacks both. Evidence is completion timing and telemetry, so we design idempotent, self-reporting programs."
