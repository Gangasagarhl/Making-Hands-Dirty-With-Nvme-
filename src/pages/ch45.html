PCI Express (PCIe) has its own error model, entirely separate from NVMe's: bits flip on the wire, packets arrive corrupted or malformed, requests go to addresses nobody claims, completions never come back, and links drop without warning. This chapter teaches every major PCIe error by the layer that detects it, how it is classified (correctable, uncorrectable non-fatal, uncorrectable fatal), how it is signalled, and what it does to the NVMe traffic riding on top.

Why this chapter exists

Chapter 44 covered errors that NVMe reports inside successful PCIe writes. This chapter is about the transport underneath failing. When PCIe fails, NVMe sees the consequence — a Data Transfer Error, a command that never completes, a register read returning all ones, a controller that vanishes — but NVMe cannot tell you why. Only PCIe error reporting can.

PCIe errors are also where good engineers most often fool themselves: a log full of correctable errors that are harmless; a single uncorrectable error that explains everything; an error logged at the root port that was actually caused by the device; an error reported by a device that was actually caused by host software. This chapter builds the vocabulary to avoid those traps, and Chapter 46 shows the registers that record it all.

Learning objectives

  • Classify PCIe errors as correctable, uncorrectable non-fatal or uncorrectable fatal, and explain what each class means for data and for the link.
  • Explain each major error by detecting layer: Receiver Error (Physical); Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover, Data Link Protocol Error, Surprise Down (Data Link); Poisoned TLP, ECRC Error, Unsupported Request, Completer Abort, Unexpected Completion, Completion Timeout, Malformed TLP, Receiver Overflow, Flow Control Protocol Error (Transaction).
  • Describe how errors are signalled: error messages (ERR_COR, ERR_NONFATAL, ERR_FATAL), completion status (UR, CA), and status bits.
  • Predict what each PCIe error does to an in-flight NVMe command.
  • Read PCIe error indications in lspci and the Linux kernel log, and know what they prove.

The story

The road between the school and the library has trucks carrying parcels. Lots of things can go wrong.

  • A gust of wind smudges a label. The receiving guard can't read it, throws it away, and shouts "send that one again!" The truck driver resends it. Nobody else ever knows. (That's a correctable problem.)
  • A parcel arrives addressed to a building that doesn't exist. The guard sends back a note: "No such building." That parcel's job failed, but the road is fine. (Non-fatal.)
  • A parcel arrives with a sticker saying "contents spoiled". Someone opened it and found the food bad. They stamped it so nobody eats it. (Poisoned.)
  • The teacher sends for a book and waits… and waits… and the book never comes. (Completion timeout.)
  • A truck arrives that's twice the legal size, or shaped all wrong. The guard can't trust anything about the road any more and calls for help. (Malformed — usually fatal.)
  • The bridge collapses. (Surprise down.)

PCIe error handling resembles a railway's safety system. Track-level faults (a signal glitch) are caught by the signalling equipment and the train simply repeats its approach — passengers never notice. Train-level faults (a wagon sent to a station that has no siding for it) cancel that wagon's journey but the line keeps running. Line-level faults (a derailment, a broken bridge) close the line and call the emergency services. Every incident is written in a log at the nearest signal box, and serious ones are telegraphed to central control.

Hides: PCIe correctable errors are not free. Every replay costs bandwidth and latency; a link correcting thousands of errors per second is a slow, sick link heading for failure. Misleads: "fatal" in PCIe means "the link or device can no longer be trusted" — it does not necessarily mean data was lost, nor that the machine crashes; with proper recovery (Downstream Port Containment, link reset) the system often survives. And the signal box that logs the incident is not always where the fault was: a root port logs errors it detected, which may have been caused by the device at the other end.

When a device detects an error it may record it in its own registers and send an error message up to the root complex: ERR_COR for correctable, ERR_NONFATAL or ERR_FATAL for uncorrectable. The root complex then raises an interrupt so the operating system can log it and, if needed, recover.

Engineering explanation

Detection, logging, signalling, handling

Every PCIe error goes through up to four steps, and different components do each:

  1. Detection — by a receiver (Physical/Data Link) or by a requester/completer (Transaction).
  2. Logging — status bits in the detecting function: Device Status (Correctable/Non-Fatal/Fatal/Unsupported Request Detected), the legacy PCI Status register, and, if implemented, the Advanced Error Reporting (AER) capability with per-error bits and a header log (Chapter 46).
  3. Signalling — an error message to the root complex if enabled (Device Control's reporting enables, and AER masks), and/or a completion status for a non-posted request (UR, CA).
  4. Handling — the root port collects messages, logs the source, interrupts the OS; the OS reads registers, logs, and may run recovery (driver callbacks, link reset, Downstream Port Containment).

Physical Layer: Receiver Error

A Receiver Error (correctable) is logged when the receiver's physical layer sees something it cannot decode: a framing violation, an invalid symbol or block, a disparity or sync-header error, elastic buffer problems. The exact set of conditions depends on the encoding (8b/10b at Gen1–2; 128b/130b at Gen3–5; PAM4 with FLIT mode at Gen6 and later). A corrupted symbol inside a TLP usually also causes a Bad TLP (the LCRC fails), so Receiver Errors and Bad TLPs tend to appear together.

From PCIe 6.0, FLIT mode with forward error correction (FEC) changes where errors are caught: many bit errors are corrected by FEC before the Data Link Layer sees them, and retry operates on FLITs. The names of logged errors are largely retained but their frequency and meaning shift. Confirm details in the Physical Layer and FLIT mode material of the revision you work with.

Data Link Layer errors

The Data Link Layer protects each TLP with a 12-bit sequence number and a 32-bit Link CRC (LCRC), keeps a copy in its replay buffer until it receives an ACK, and resends on NAK or timeout. Its errors are therefore mostly about that machinery:

A single Bad TLP is noise. REPLAY_NUM Rollover means the link failed to make progress through several replays in a row and had to retrain. Frequent rollovers predict link failure, speed downgrades and width downgrades. Count them separately from Bad TLPs.

Completion status: how a completer says no

For a non-posted request (Memory Read, Configuration Read/Write, I/O, some AtomicOps), the completer must answer. The Completion Status field carries the verdict:

Completion Status values
CodeNameMeaning to the requester
000bSuccessful Completion (SC)Data (if any) follows
001bUnsupported Request (UR)Completer did not support or claim the request
010bConfiguration Request Retry Status (CRS) — renamed Request Retry Status (RRS) in recent revisionsFunction not ready yet (typically after reset); retry the configuration request
100bCompleter Abort (CA)Completer refused or failed the request

A posted request (Memory Write, Message) gets no completion, so a posted request to a bad address is reported only by the completer that detected it (error message, logged as UR) — the requester never learns. That is why a DMA write from the SSD into an unmapped address shows up as an error at the root port (or IOMMU), not at the SSD.

Completion timeout in depth

A requester tracks each outstanding non-posted request by its Tag. If the completion does not arrive in time, it logs a Completion Timeout, retires the tag, and must handle the failure itself. Timeout ranges are configured in the Device Control 2 register (Completion Timeout Value and Completion Timeout Disable), with the supported ranges advertised in Device Capabilities 2. The default range is 50 µs to 50 ms.

Two NVMe-relevant directions:

  • Host → device read times out (CPU reads an NVMe register, e.g. CSTS, and the SSD does not answer). The root complex logs the timeout and typically returns all ones to the CPU. The driver sees CSTS = 0xFFFF_FFFF. On some platforms this is a machine check rather than all-ones data — platform-dependent.
  • Device → host read times out (SSD fetches an SQE, PRP list or write data and the host does not answer). The SSD logs the timeout. The NVMe command typically completes with Data Transfer Error, or, if the SQE fetch itself failed, the command never starts and the host eventually times out.

Completion timeouts are the most misattributed PCIe error. The function that logs a completion timeout is the requester, and it is usually the victim. The cause is upstream or downstream: a completer that hung, a switch that dropped the completion, a link that went down, or an unexpected-completion pair (the completion arrived but with wrong ID/tag).

Poisoned data

Poisoning is the PCIe way to say "this data is known bad, do not use it" without stopping the system. If host memory reports an uncorrectable ECC error while servicing the SSD's DMA read of write data, the root complex can return the CplD with EP=1. The SSD logs Poisoned TLP Received, must not commit that data, and should complete the NVMe WRITE with an error (typically Data Transfer Error). In the opposite direction, if the SSD's internal data is bad it should not send it poisoned as a READ result unless it is designed to; it reports a media error instead.

Malformed TLP and the MPS trap

The most common Malformed TLP in the field is a Max Payload Size mismatch: one side is configured for 512 bytes, the other for 256; the first sends a 512-byte write; the receiver sees a payload larger than its MPS and declares the TLP malformed. Because Malformed TLP is fatal by default, the result is dramatic: the link is reset, the device disappears, and the NVMe controller times out. Linux normally configures MPS consistently along a path, but hot-plug, BIOS settings and kernel parameters (pci=pcie_bus_*) can produce mismatches.

Advisory Non-Fatal errors

Some uncorrectable errors are better handled by the agent at the other end. For example, a completer that detects an Unsupported Request for a non-posted request returns a UR completion, and the requester will handle it; signalling ERR_NONFATAL as well would make the OS think something more serious happened. AER-capable functions can therefore report certain non-fatal errors as Advisory Non-Fatal Errors: they set the uncorrectable status bit but signal ERR_COR and set the Advisory Non-Fatal bit in the correctable status. The exact cases are defined in the PCIe Base Specification's role-based error reporting rules — read them before deciding an error was "missed".

Legacy PCI status bits still matter

Even without AER, the PCI Status register records Received Master Abort (a request it sent got UR), Received Target Abort (got CA), Signaled Target Abort (it sent CA), Detected Parity Error (it received poisoned data) and Signaled System Error (it sent ERR_FATAL/ERR_NONFATAL). These bits appear in lspci as >TAbort, <TAbort, <MAbort, >SERR, <PERR on the Status line.

The central concept on the ladder

Smudged labels get resent quietly; parcels to nowhere come back with a note; a collapsed bridge stops everything.

PCIe errors are correctable (hardware fixed it), uncorrectable non-fatal (one transaction failed) or uncorrectable fatal (link/device untrustworthy), and each is detected by a specific layer.

Receivers check symbols and LCRCs, transmitters run replay timers and counters, requesters track tags against a completion timer, completers decode addresses against BARs. Each sets status bits in its own configuration space and may send an error message upstream.

PCI Express Base Specification: Error Signaling and Logging; Error classification; Data Link Layer retry rules; Completion Timeout mechanism; Poisoned TLP rules; Malformed TLP rules; AER capability; Device Control/Status error bits.

On the wire: NAK DLLPs and replayed TLPs; Cpl with UR/CA status; TLPs with EP=1; Msg ERR_COR/ERR_NONFATAL/ERR_FATAL routed to the root complex; LTSSM entering Recovery.

An analyzer shows NAKs and duplicate sequence numbers (replay), completions with non-SC status, error messages with the reporter's Requester ID, gaps where a completion should be, and electrical idle when a link drops.

Ask: which layer detected it, which function logged it, was it the requester or the completer, and is it the first abnormal event or a consequence? Then look for the cause one hop away.

The 16 questions for Completion Timeout

1. What is it?
An uncorrectable (default non-fatal) error logged by a requester when a non-posted request does not receive its completion(s) in time.
2. Why was it created?
Without it, a lost completion would hang the requester forever with a tag consumed.
3. What problem does it solve?
Bounded failure: the requester can retire the tag and report an error instead of hanging.
4. What existed before it?
Conventional PCI's Master Abort (no device claimed the cycle) and target retry/disconnect semantics on a shared bus.
5. Why is the current design better?
Split transactions let requests and completions be separated in time; a timeout is the only way to bound a split transaction.
6. Who creates it?
The requester's transaction layer.
7. Who consumes it?
The requester's own logic (fail the operation), and the OS via AER.
8. Where does it live?
Uncorrectable Error Status (Completion Timeout bit) of the requester; Device Status; timeout configuration in Device Control 2.
9. What memory/registers are involved?
Device Capabilities 2 (ranges supported, disable supported), Device Control 2 (value, disable), AER status/mask/severity.
10. What happens before it?
A non-posted request was sent with a tag; time passed with no (complete) completion.
11. What happens after it?
Tag retired; operation failed; ERR_NONFATAL (if enabled and not masked); a late completion would now be an Unexpected Completion.
12. What happens if it is wrong?
Too short: false timeouts under heavy load or on slow paths. Disabled: hangs forever on a lost completion.
13. What does the protocol analyzer show?
A request with tag T, no matching completion for longer than the timeout, then (maybe) an ERR_NONFATAL message from the requester.
14. What does Linux show?
AER message naming the device with "CmpltTO"; for host MMIO reads, all-ones values and driver "controller is down" messages.
15. What would a validation engineer test?
Each supported range; disable; behaviour when completions are dropped; late completions handled as Unexpected Completion; NVMe command status on SQE/PRP/data fetch timeouts.
16. What would a senior engineer suspect when it fails?
The completer or path, not the requester: a hung completer, a link in recovery, a switch dropping completions, a reset mid-flight, or an IOMMU stall.

Hardware view

  • Receiver PHY — clock and data recovery, decoders, elastic buffer; source of Receiver Errors. Marginal signal integrity (long traces, bad connectors, risers, retimers) shows up here first.
  • Data Link Layer — LCRC generation/check, sequence numbers, replay buffer, replay timer, REPLAY_NUM counter, ACK/NAK scheduling, DLLP CRC. Source of Bad TLP/Bad DLLP/Replay/Rollover/DLP errors.
  • Transaction Layer — header decode and format checks (Malformed), flow-control credit accounting (Receiver Overflow, FC Protocol), address decode against BARs (UR), tag tracking and completion timers (Completion Timeout, Unexpected Completion), ECRC.
  • Application / core logic — decides Completer Abort, poisons outgoing data when its internal memory reports uncorrectable errors, handles received poison.
  • Downstream ports (root ports, switch downstream ports) — detect Surprise Down, can implement Downstream Port Containment (DPC) to stop traffic after an uncorrectable error (see Advanced Error Handling).

Which errors a component can detect beyond the mandatory set, its replay timer values, its completion timeout ranges, whether it implements AER, ECRC and DPC, and how a root complex answers a failed CPU read (all-ones vs machine check) are implementation- or platform-dependent.

Specification view

  • PCI Express Base Specification, Revision 6.x/7.0 — Error Signaling and Logging (error classification, error messages, Advisory Non-Fatal cases, error pollution rules); Data Link Layer (LCRC, retry, replay timer, REPLAY_NUM); Transaction Layer (Completion Timeout, Poisoned TLP, Malformed TLP rules, ECRC); Advanced Error Reporting Capability. PCIe errors are classified as correctable, uncorrectable non-fatal and uncorrectable fatal, signalled with ERR_COR, ERR_NONFATAL and ERR_FATAL messages. Correctable errors include Receiver Error, Bad TLP, Bad DLLP, REPLAY_NUM Rollover, Replay Timer Timeout, Advisory Non-Fatal Error. Uncorrectable errors include Data Link Protocol Error, Surprise Down, Poisoned TLP Received, Flow Control Protocol Error, Completion Timeout, Completer Abort, Unexpected Completion, Receiver Overflow, Malformed TLP, ECRC Error, Unsupported Request. Default fatal: DLP Error, Surprise Down, FC Protocol Error, Receiver Overflow, Malformed TLP (and Uncorrectable Internal Error). Completion status UR = 001b, CA = 100b. Default completion timeout range is 50 µs–50 ms.

Statements about which component is "the victim" vs "the cause" are diagnostic reasoning, not specification text. The NVMe-effect table above is derived from how NVMe controllers and Linux typically map PCIe failures.

Replay timer values (within specified limits), completion timeout actual values within a range, optional error detection (ECRC, ACS violations), AER presence on endpoints, root complex behaviour on failed reads, and NVMe status chosen for a PCIe failure.

New errors and capabilities appear in newer revisions (for example, errors tied to TLP prefixes, AtomicOps egress, FLIT mode, and the CRS→RRS renaming). Older devices implement fewer error bits. Check the revision your components claim in their PCI Express Capability.

Check in the specification: the full list of Malformed TLP conditions; the precise Advisory Non-Fatal cases; the exact replay timer formula for your link speed and width; error pollution rules (which error is logged when several occur from one cause). The PCIe specification does not define how an operating system must recover, nor what an NVMe controller must report to its host when its DMA fails — the latter is NVMe's domain.

Never assume the logger is the culprit. Never assume correctable means harmless at high rates. Never assume a fatal error crashed the system or lost data. Never assume ERR_* messages arrive if reporting is disabled or masked — absence of AER logs is not proof of no errors.

Code / pseudocode

Replay and rollover simulator

A simplified Data Link Layer model: TLPs are corrupted with a given probability, NAKed and replayed; four consecutive replays of the same TLP without progress cause a rollover (retrain). It shows how quickly a healthy-looking error rate turns into retraining.

#!/usr/bin/env python3
"""Toy Data Link Layer retry model (simulation, not spec-exact).
p = probability one TLP transmission is corrupted (LCRC fail).
REPLAY_NUM is a 2-bit counter: it increments on each replay of the same
oldest TLP and resets on forward progress; wrapping past 3 => rollover."""
import random

def run(p, tlps=1_000_000, seed=7):
    rnd = random.Random(seed)
    bad = replays = rollovers = 0
    sent = 0
    for _ in range(tlps):
        replay_num = 0
        while True:
            sent += 1
            if rnd.random() >= p:
                break                      # ACKed: forward progress
            bad += 1
            replays += 1
            replay_num += 1
            if replay_num > 3:            # 2-bit counter wraps
                rollovers += 1
                replay_num = 0             # link retrains, then retries
    return bad, replays, rollovers, sent / tlps

if __name__ == "__main__":
    for p in (1e-6, 1e-4, 1e-2, 0.2, 0.5):
        bad, rep, roll, eff = run(p)
        print(f"p={p:<7g} badTLP={bad:8d} replays={rep:8d} "
              f"rollovers={roll:6d} transmissions/TLP={eff:6.3f}")

Expected pattern: at 1e-6 a handful of Bad TLPs per million and no rollovers; at 0.2–0.5 (a badly broken lane) rollovers appear and throughput collapses. Real links fail more abruptly because errors are bursty, not independent — the simplification is part of the lesson.

Classifying an error report (pseudocode)

for each error report:
    layer  = PHY if RxErr; DLL if BadTLP|BadDLLP|Replay*|DLP|SDES; else TL
    role   = requester if CmpltTO|UnxCmplt|received UR/CA completion
             completer if UR|CA detected; receiver otherwise
    victim_or_cause = "victim" if role == requester else "detector"
    look_for_cause_at = other_end_of(link) if layer in (PHY, DLL)
                        else completer_of(request) if role == requester
                        else requester_of(request)

Worked example

Scenario (synthetic). A fleet monitor flags a server whose SSD's aer_dev_correctable shows BadTLP 41 and RxErr 39, accumulated over 90 days. Another server shows BadTLP 1,800,000 over one day and Rollover 220. Both run fine. Which needs action?

  1. Normalise. 41 Bad TLPs in 90 days ≈ one every two days. On a Gen4 x4 link carrying billions of TLPs a day that is far below any concern; it is normal noise (and Receiver Errors accompany Bad TLPs as expected).
  2. Second server. 1.8 M per day ≈ 21 per second, with 220 rollovers ≈ one every 6–7 minutes. Each rollover is a retrain — a latency spike of microseconds to milliseconds. This link is degraded.
  3. Locate. Which side logged them? If the root port logs Bad TLP, the corrupted direction is device→host (the SSD's transmitter, the channel, or the root port's receiver). If the SSD logs them, host→device. Check LnkSta: has the link downtrained to Gen3 or x2?
  4. Correlate. Do NVMe latency outliers line up with rollovers? Use timestamps from kernel AER logs and the application's latency histogram.
  5. Act. Reseat or swap the drive/riser/cable; compare with another slot; check firmware for retimer settings; run lane margining if the platform supports it.

The thresholds here are engineering judgement. The PCIe specification defines the errors and their classes, not an acceptable rate. Your platform vendor may publish guidance.

Common mistakes

  • Blaming the device that logged a Completion Timeout. It is the requester; look at the completer and path.
  • Ignoring which end logged a Bad TLP. It tells you the direction of the corrupted traffic.
  • Treating UR during boot enumeration as a fault (probing unimplemented functions or registers produces URs).
  • Thinking a posted write to a bad address will be reported to the writer. It cannot be.
  • Confusing "Poisoned TLP" (data known bad, EP bit) with "Bad TLP" (LCRC failure on the link).
  • Treating "fatal" as "the server will crash". With DPC and AER recovery, the system often survives.
  • Reading sticky status bits without timestamps and assuming they are recent.
  • Forgetting MPS/MRRS configuration when a Malformed TLP appears after hot-plug or firmware changes.

Senior engineer insight

  • Logger ≠ culprit. Every PCIe error is logged by a detector. Your first job is to name the detector's role (receiver, requester, completer) and then look at the other party.
  • Rates beat counts. A cumulative counter is meaningless without time. Instrument rates and correlate with workload and temperature.
  • The first fatal error explains the rest. After a link goes down you will see Completion Timeouts, all-ones reads, NVMe timeouts and resets. Only the first is evidence of the cause.
  • Silence is not health. AER may be masked, disabled by firmware (firmware-first error handling), or not implemented on the endpoint. Before declaring "no PCIe errors", confirm that errors could have been reported.
  • Configuration bugs look like hardware bugs. MPS, MRRS, ASPM, completion timeout ranges and ACS settings produce errors that disappear when you swap the "faulty" hardware into a correctly configured system.

Challenge

Run replay_sim.py with your measured Bad TLP rate converted to a per-TLP probability (estimate TLPs per second from throughput / 256 B) and predict rollovers. Compare with the Rollover bit.

Hint

Kernel counters only count errors that were signalled and handled by the kernel's AER driver; firmware-first platforms may handle them elsewhere.

Solution

1. Device → host: the root port received the corrupted TLPs.

2. UR detection is logged even when reporting is disabled/masked or classified as advisory; or it happened during enumeration before the AER driver loaded; or firmware-first handling consumed the message.

3. Answers vary; a handful per day on a busy link is unremarkable, sustained per-second rates or any rollovers merit investigation.

What a senior engineer notices

Link speed/width below capability (silent downtraining), UR bits on root ports from enumeration noise, AER capability absent on the endpoint, and whether the platform uses firmware-first error handling (kernel log mentions of APEI/GHES).

Failure variants

  • No AER lines in lspci: the device lacks AER or lspci lacks privileges (run as root).
  • aer_dev_* files missing: older kernel or AER not enabled for the device.

Exercises

  1. For each of: Bad TLP, Completion Timeout, Unsupported Request, Malformed TLP — name the detecting role and the default class.
  2. Explain why a posted Memory Write to a non-existent address cannot produce a Completion Timeout.
  3. The SSD logs Unexpected Completion shortly after a Completion Timeout for the same tag. Reconstruct what happened.
  4. Why does a Malformed TLP default to fatal while Unsupported Request defaults to non-fatal?
  5. A Gen4 x4 link trains at Gen4 x2 after a reboot, with no errors logged. What can you conclude?
Model answers

1. Bad TLP: receiver, correctable. Completion Timeout: requester, non-fatal. UR: completer, non-fatal. Malformed: receiver, fatal.

2. Posted requests have no completion, so there is nothing to time out.

3. The completion was delayed beyond the timeout; the SSD retired the tag (Completion Timeout); the late completion then matched nothing (Unexpected Completion). Look for a slow completer or a congested path.

4. A malformed TLP means the receiver cannot trust the sender's framing or rules — the link's integrity is in doubt. A UR is a well-formed request the completer simply does not support; the link is fine.

5. Width negotiation chose x2 (lane failure or poor signal on two lanes, or a slot wired x2). No error logs is consistent: training does not log AER errors for lanes that failed to train. Check LnkCap vs LnkSta and the platform's slot wiring.

Quiz

  1. A Bad TLP is detected by

    • The transmitter's replay timer
    • The receiver's LCRC/sequence check
    • The completer's address decoder
    • The root complex only
    Answer and reasoning

    The receiving Data Link Layer checks LCRC and sequence numbers.

  2. REPLAY_NUM Rollover causes

    • A fatal error
    • A Completion Timeout
    • Link retraining (Recovery)
    • A poisoned TLP
    Answer and reasoning

    It is correctable; the transmitter forces the link into Recovery.

  3. Which is fatal by default?

    • Completion Timeout
    • Unsupported Request
    • Poisoned TLP
    • Malformed TLP
    Answer and reasoning

    Malformed TLP, DLP, Surprise Down, FC Protocol, Receiver Overflow are fatal by default.

  4. Completion Status 001b means

    • Unsupported Request
    • Completer Abort
    • Successful
    • Retry status
    Answer and reasoning

    000 SC, 001 UR, 010 CRS/RRS, 100 CA.

  5. Who logs a Completion Timeout?

    • The completer
    • The requester
    • The switch
    • The root port always
    Answer and reasoning

    The requester owns the tag and the timer.

  6. The EP bit in a TLP header indicates

    • ECRC present
    • End of packet
    • Poisoned data
    • Error message
    Answer and reasoning

    EP = Error Poisoned; TD indicates a digest (ECRC).

  7. Explain why a root port logging Bad TLP may indicate a problem with the SSD's transmitter.

    Model answer

    Bad TLP is logged by the receiver; the root port received corrupted TLPs that the SSD transmitted. The cause can be the SSD's transmitter, the channel, or the root port's receiver — the log tells you direction, not culprit.

  8. Give two NVMe-visible consequences of a Completion Timeout at the host for an MMIO read.

    Model answer

    The register read returns all ones (e.g. CSTS=0xFFFFFFFF); the NVMe driver concludes the controller is dead and resets or removes it; I/O fails.

  9. What is an Advisory Non-Fatal Error?

    Model answer

    An uncorrectable non-fatal error that the detecting function reports as correctable (ERR_COR, with the Advisory Non-Fatal bit) because another agent is expected to handle it — e.g. a completer that returned UR for a non-posted request.

Interview questions

  1. Beginner: Name the three PCIe error classes.

    Model answer

    Correctable, uncorrectable non-fatal, uncorrectable fatal.

  2. Beginner: What does the Data Link Layer do when a TLP arrives with a bad LCRC?

    Model answer

    Discards it, logs Bad TLP, sends a NAK; the transmitter replays from its replay buffer.

  3. Intermediate: Difference between Unsupported Request and Completer Abort?

    Model answer

    UR: request not supported or not claimed (e.g. address not in any BAR). CA: completer recognised the request but refused/failed it for its own reasons.

  4. Intermediate: What's a poisoned TLP and how should an NVMe controller react to receiving one for write data?

    Model answer

    A TLP whose data is marked bad by EP=1. The controller must not commit the data; log Poisoned TLP Received; complete the WRITE with an error status.

  5. Advanced: Explain the MPS mismatch failure.

    Model answer

    A sender configured for a larger MPS than the receiver sends a TLP whose payload exceeds the receiver's MPS; the receiver flags Malformed TLP (fatal by default) → link reset, device loss. Fix: consistent MPS along the path.

  6. Advanced: Why are completion timeouts often misattributed?

    Model answer

    They're logged by the requester, which is the victim; the cause is the completer or path. Engineers see the error on device X and blame X.

  7. Senior: Fleet data shows rising correctable errors on one server model after a BIOS update. How do you proceed?

    Model answer

    Normalise to rates; separate by detecting end and error type; compare BIOS versions (equalisation presets, retimer firmware, ASPM, speed); correlate with slot/riser; reproduce on a lab unit with A/B BIOS; use lane margining; engage the platform vendor with data.

Chapter summary

PCIe errors are detected by the Physical Layer (Receiver Error), the Data Link Layer (Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover, Data Link Protocol Error, Surprise Down) and the Transaction Layer (Poisoned TLP, ECRC, Unsupported Request, Completer Abort, Unexpected Completion, Completion Timeout, Malformed TLP, Receiver Overflow, Flow Control Protocol Error). They are classed as correctable, uncorrectable non-fatal or uncorrectable fatal, signalled by ERR_COR/ERR_NONFATAL/ERR_FATAL messages and completion status (UR, CA), and logged in status registers. To NVMe they appear as extra latency, Data Transfer Errors, timeouts, all-ones reads or a vanished device. The detecting function is rarely the culprit: always reason about role and look one hop away.

Do not move on until you can:

  • place every error named here in its layer, detector role and default class
  • explain ACK/NAK replay and why rollover matters
  • explain completion timeout from both directions and its NVMe effect
  • tell Poisoned TLP from Bad TLP from Malformed TLP
  • read DevSta/CESta/UESta in lspci and kernel AER counters
  • find NAKs, UR/CA completions, missing completions and error messages in a trace
  • argue from detector role to likely cause
