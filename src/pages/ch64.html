Before any operating system runs, something has to find an NVM Express (NVMe) device, bring its controller up, read a boot loader from it, and hand everything over cleanly. This chapter follows that pre-operating-system (pre-OS) journey: platform firmware and the Unified Extensible Firmware Interface (UEFI), option ROMs, local boot from an NVMe namespace, NVMe Boot Partitions, booting over NVMe over Fabrics (NVMe-oF) as defined by the NVMe Boot Specification 1.4, and the handoff to the OS driver.

Why this chapter exists

Every chapter so far assumed a Linux driver was in charge. At power-on there is no Linux, no driver and no file system — just platform firmware with a small, carefully written NVMe driver of its own. If that driver cannot initialise the controller, there is no boot. If it leaves the controller in a strange state, the OS driver inherits a mess. And in cloud and disaggregated designs, the boot disk may not be in the server at all: it is an NVMe namespace on a target across a Transmission Control Protocol (TCP) network, so the pre-OS environment must speak NVMe over TCP.

Boot problems are among the hardest to debug — no shell, little logging, and every failure looks like "no bootable device". Engineers who understand the sequence (firmware enumeration → controller enable → Identify → read the partition table → load loader → handoff) can localise them; engineers who do not, swap hardware until something works.

  • Explain NVMe Boot Partitions and the BPINFO, BPRSEL and BPMBL registers, and when they are used.
  • Explain transport-aware boot: what the NVMe Boot Specification adds for NVMe-oF (especially NVMe/TCP), including the NVMe Boot Firmware Table (NBFT).

The story

Early in the morning, before the teacher arrives, the school's night caretaker unlocks the building. The caretaker does not know how to teach, but knows exactly one thing: how to open the library, find the shelf with the teacher's first-day instructions, and put them on the teacher's desk. Then the caretaker goes home. The teacher arrives, reads the instructions, and from then on runs the school — including opening the library properly in their own way.

Sometimes the first-day instructions are not in this building at all; they are in a library across town. Then the caretaker must make a phone call, and leave the teacher a note saying exactly which library and which phone number, so the teacher can call back.

A relay race with a baton. The first runner (platform firmware) has a short leg, carries the baton (control of the NVMe controller and the loaded OS loader), and must hand it over inside the exchange zone (ExitBootServices). A dropped baton — a controller left half-initialised, a connection the second runner does not know about — loses the race even if both runners were fast.

  • Runners do not reset each other. The OS driver normally resets the controller and starts over; what is handed over is the boot loader and configuration information, not live queues.
  • Hidden: three different storage locations. The "instructions" may be in a file system on a namespace (normal UEFI boot), in an NVMe Boot Partition (small dedicated area read by register mechanism), or on a remote target (NVMe-oF boot).
  • Hidden: the note format. For fabric boot the note is a standard Advanced Configuration and Power Interface (ACPI) table (the NBFT), not an informal message.
  • Misleading: one caretaker. Several firmware drivers participate: PCIe bus driver, NVMe driver, partition and file-system drivers, network stack, boot manager.

Beginner explanation

When a computer powers on, the central processing unit (CPU) starts executing platform firmware (today almost always UEFI firmware; older systems used a legacy BIOS). The firmware:

  1. initialises memory and the PCIe hierarchy, assigning bus numbers and BAR addresses to devices;
  2. loads drivers for devices it wants to boot from — for NVMe, a UEFI NVMe driver built into the firmware or loaded from the device's option ROM;
  3. uses that driver to enable the NVMe controller, discover namespaces, and present each namespace as a block device to the rest of the firmware;
  4. finds the EFI System Partition (ESP) on a GUID Partition Table (GPT), reads the OS loader file (for example \EFI\BOOT\BOOTX64.EFI or a path stored in a boot variable), and runs it;
  5. the OS loader loads the kernel, calls ExitBootServices, and the OS takes over; the OS NVMe driver then re-initialises the controller.

Two variations matter for NVMe engineers:

  • Boot Partitions: an optional NVMe feature giving small, dedicated areas that a very simple host (for example an embedded system-on-chip boot ROM) can read with a register-level mechanism, without building admin queues.
  • NVMe-oF boot: the boot namespace is on a remote NVMe target. The firmware runs an NVMe/TCP initiator, connects, reads the loader over the network, and passes the connection details to the OS. The NVMe Boot Specification standardises this.

Engineering explanation

The pre-OS environment

UEFI firmware runs in phases (security, pre-EFI initialisation, driver execution environment, boot device selection, runtime). For storage, the important phase is the Driver Execution Environment (DXE) and Boot Device Selection (BDS): PCI bus drivers enumerate devices and expose PCI I/O protocols; device drivers bind to them; the boot manager walks boot options. Informative summary of the UEFI Platform Initialization model — read the UEFI specification for normative detail.

BIOS, UEFI and option ROMs

A PCIe device can carry an option ROM — firmware code the platform can load and run — exposed through the Expansion ROM Base Address Register in configuration space (offset 30h in a Type 0 header). Legacy BIOS option ROMs hooked the INT 13h disk interrupt; UEFI option ROMs contain UEFI driver images. Verified for the Expansion ROM BAR location (PCI header layout).

  • Most current UEFI platform firmware includes a built-in NVMe driver (the open-source EDK II implementation is commonly called NvmExpressDxe), so most NVMe solid-state drives (SSDs) do not need an option ROM to boot. Implementation-dependent
  • Legacy BIOS boot from NVMe generally needs an option ROM on the device or in the platform, which many NVMe drives never shipped; this is why early NVMe adoption pushed systems to UEFI.
  • Secure Boot validates option ROMs and OS loaders against signature databases; an unsigned option ROM is skipped on a Secure Boot platform.

The UEFI specification defines an NVM Express Pass Thru Protocol through which UEFI code sends raw NVMe commands to a controller, and an NVMe namespace device-path node (identifying namespace by namespace identifier (NSID) and 64-bit Extended Unique Identifier (EUI-64)) so boot variables can name a specific namespace. Verified that these exist in the UEFI specification; check field layouts there.

Boot from a local NVMe namespace

The firmware NVMe driver performs a compact version of the initialisation you learned in Chapter 24 and Chapter 26:

  1. Enable memory space and bus mastering in the PCI Command register.
  2. Read CAP (00h) for the timeout (CAP.TO, in 500 ms units), doorbell stride and supported page sizes; read VS (08h).
  3. If CSTS.RDY = 1, clear CC.EN and wait for CSTS.RDY = 0.
  4. Allocate small admin queues in firmware memory; program AQA (24h), ASQ (28h), ACQ (30h).
  5. Set CC (14h): EN = 1, page size, I/O queue entry sizes; wait for CSTS.RDY = 1 up to CAP.TO.
  6. Identify Controller, Identify active namespace list, Identify Namespace for each.
  7. Create one I/O completion queue (CQ) and submission queue (SQ) (often small, often polled rather than interrupt-driven).
  8. Read logical block address (LBA) 0 (the protective Master Boot Record, MBR) and LBA 1 (GPT header), the partition entries, then the ESP's file system and the loader file.

Firmware drivers are minimal: usually one I/O queue, polled completions, Physical Region Pages (PRPs) only, small transfers. A drive that performs perfectly under Linux can still fail in firmware if it mishandles a code path only firmware uses — for example a very small queue size, or an unusual order of Identify commands. Boot qualification must test with the real platform firmware.

NVMe Boot Partitions

Boot Partitions are an optional feature of the NVMe Base Specification: small storage areas, separate from namespaces, intended for boot code of systems that want to read their first stage without full NVMe initialisation. There are two Boot Partitions (identified 0 and 1), allowing one to be updated while the other remains active.

Support is indicated by a capability bit in CAP (Boot Partition Support). Uncertain — confirm offsets, field bit positions and units in the Base 2.4 "Controller Registers" section and the PCIe Transport 1.4 specification before writing code. The read mechanism, in outline:

  1. read BPINFO: size, active ID
  2. write BPMBL = buffer address
  3. write BPRSEL: ID, offset, size
  4. read status = in progress
  5. MWr: boot image data (DMA)
  6. poll BPINFO read status
  7. status = completed

The key property: this can be done without enabling the controller and without any admin queue. Uncertain on the precise CC.EN preconditions — the specification states when a Boot Partition read may be initiated; confirm it. Writing a Boot Partition uses ordinary admin commands: Firmware Image Download to transfer the image and Firmware Commit with Boot-Partition-specific commit actions to replace a partition or mark it active. Boot Partition write protection (controllable via a feature in the 2.x specifications) can lock partitions. Uncertain on commit action values and feature identifiers — check Base 2.4.

On ordinary PCs and servers, UEFI boots from a GPT/ESP on a namespace; Boot Partitions are mainly for embedded and specialised platforms. Do not assume a laptop uses them.

Transport-aware boot: NVMe over Fabrics

The NVM Express Boot Specification, Revision 1.4 standardises how pre-OS software boots from NVMe-oF namespaces, focusing on NVMe/TCP because TCP needs only ordinary network interfaces. Verified that NVMe Boot is a separate specification at Revision 1.4 in the August 2026 set. It covers, in outline:

  • Configuration of the pre-OS host: host NVMe Qualified Name (NQN) and Host Identifier, network interface parameters (static or Dynamic Host Configuration Protocol, DHCP), and target or discovery-controller addresses — through firmware setup, UEFI variables or similar platform means. Implementation-dependent mechanism.
  • Discovery and connection: the pre-OS NVMe/TCP initiator optionally queries a discovery controller, connects an admin queue and I/O queue to the subsystem, and presents the namespace as a boot block device.
  • Handoff: the firmware publishes the NVMe Boot Firmware Table (NBFT), an ACPI table describing the host identity, host fabric interfaces, subsystem namespaces and discovery information used for boot, so the OS can re-establish the same connections. Verified that NBFT is the handoff mechanism defined by NVMe Boot; table layout must be read from the specification.

Booting over NVMe/RDMA is conceptually similar but needs RDMA-capable firmware drivers; check whether Boot 1.4 covers transports beyond TCP. Uncertain

OS handoff

After ExitBootServices, firmware drivers must no longer touch devices. Two handoff facts follow:

  • Local NVMe: the controller is typically left enabled with firmware-created queues in memory the OS may reuse. The OS driver therefore disables the controller (CC.EN = 0, wait CSTS.RDY = 0), discarding firmware queues, and initialises from scratch. A firmware that leaves DMA in flight, or a controller that is slow to go not-ready, creates early-boot failures. Derived
  • NVMe/TCP: the firmware's TCP connections disappear with the firmware network stack. The OS reads the NBFT and creates new connections — ideally with the same host NQN/ID — before it can mount the root file system. If the OS cannot reconnect, the kernel boots but cannot find root.

The central concept on the ladder: from power-on to OS-owned NVMe

A night caretaker opens the library, fetches the first-day instructions, leaves a note, and goes home; the teacher takes over.

Firmware enumerates PCIe, runs an NVMe driver, reads the boot loader from a namespace (or a Boot Partition, or a remote target), and hands off to the OS, which re-initialises the controller.

Real registers change: Command register (bus master), CC, CSTS, AQA/ASQ/ACQ; firmware memory holds small queues; for Boot Partitions, BPMBL/BPRSEL/BPINFO; for fabric boot, a network interface controller (NIC) and a TCP/IP stack in firmware.

NVMe Base 2.4 (initialisation, Boot Partitions), NVMe over PCIe Transport 1.4, NVMe Boot 1.4 (pre-OS NVMe-oF, NBFT), NVMe/TCP Transport 1.3, UEFI and ACPI specifications.

Config reads/writes during enumeration; memory-mapped I/O (MMIO) writes to CC and admin doorbells; admin commands; reads of LBA 0/1 and the ESP; or TCP protocol data units (PDUs) for fabric boot; then a reset sequence by the OS.

In a PCIe trace: a burst of CfgRd/CfgWr, a BAR write, CC.EN write, CSTS polling reads, the first submission queue entry (SQE) fetch, small reads of LBAs 0 and 1 — then silence until the OS reset writes CC.EN = 0.

"No bootable device": did enumeration see the device? Did CSTS.RDY rise before the firmware's timeout? Did Identify succeed? Is there a GPT/ESP? For fabric boot: did TCP connect, did Fabrics Connect succeed, did the OS find the NBFT?

The sixteen questions for the boot handoff

What is it?
The transfer of control of an NVMe device and boot information from platform firmware to the OS.
Why was it created?
Firmware and OS have separate drivers; a defined handoff lets each initialise safely.
What problem does it solve?
Booting from devices that need complex initialisation (NVMe queues, fabric connections) without OS help.
What existed before?
BIOS INT 13h disk services via option ROMs; iSCSI Boot Firmware Table (iBFT) for network boot over iSCSI.
Why is the current design better?
UEFI drivers are modular and signed; NBFT carries NVMe-oF specifics (NQNs, host IDs, multiple paths) that iBFT could not.
Who creates it?
Firmware (driver state, NBFT, boot variables).
Who consumes it?
The OS loader and OS (initramfs, NVMe driver, nvme-cli tooling).
Where does it live?
UEFI variables, ACPI tables in memory, the controller's register state.
Memory/registers involved?
CC, CSTS, AQA/ASQ/ACQ, firmware queue memory, NBFT memory, Boot Partition registers if used.
What happens before?
Enumeration, controller init, reading the loader.
What happens after?
OS controller reset and re-initialisation, or fabric reconnection from NBFT.
What if it is wrong?
Hang at early boot, missing root device, DMA into memory the OS reused, duplicate host identities on the fabric.
Analyzer view?
Firmware init burst, idle gap, OS reset (CC.EN 1→0) and re-init.
Linux view?
dmesg controller reset messages, efibootmgr -v, /sys/firmware/acpi/tables/NBFT, nvme nbft show (version-dependent).
Validation tests?
Boot across firmware versions, cold/warm boot, Secure Boot, slow-ready drives, Boot Partition switching, fabric boot with path failures.
Senior suspicion on failure?
Firmware timeout shorter than CAP.TO; leftover DMA; mismatched host NQN; NBFT not consumed by initramfs.

Hardware view

By the time firmware code runs, PCIe link training has completed in hardware (Chapter 09). The firmware sees the device only after it assigns bus numbers. The NVMe controller itself may still be busy: after a power-on, the SSD's own firmware must load from flash, rebuild or validate mapping tables, and only then report ready. This is why CAP.TO exists — the device declares the worst-case time to become ready, in 500 ms units, and the host must wait at least that long before declaring failure.

NVMe Boot is a separate NVMe family specification, current revision 1.4 (August 2026). NVMe controller registers CAP (00h), VS (08h), CC (14h), CSTS (1Ch), AQA (24h), ASQ (28h), ACQ (30h). CAP.TO is expressed in 500 ms units. The Expansion ROM BAR sits at configuration offset 30h of a Type 0 header.

Because the OS driver re-initialises the controller, any firmware-created queues are abandoned; a correct firmware must stop DMA before handoff, and a correct OS must not assume the controller is disabled when it starts.

Firmware NVMe driver timeouts, queue sizes, polling vs interrupts, whether option ROMs are executed, how NVMe/TCP boot is configured in firmware setup, and how the OS initramfs consumes NBFT.

The NVMe Boot Specification first appeared in 2022 (Revision 1.0) and has been revised to 1.4 in the 2.4 set. Uncertain on what each minor revision added; consult the "NVM Express Revision Changes 2026.07.30" document for 1.4. Boot Partition features (for example write protection) also evolved in the Base specification across 1.3, 1.4 and 2.x.

  • Confirm BPINFO/BPRSEL/BPMBL offsets, field positions and units, and the CC.EN preconditions for a Boot Partition read.
  • Confirm Firmware Commit action values for Boot Partitions and the Boot Partition write-protection feature.
  • Confirm NBFT structure layout and the list of descriptors in NVMe Boot 1.4.
  • The NVMe specifications do not define how a platform's boot menu works or how long firmware waits; that belongs to UEFI and platform vendors.
  • Never assume the controller is disabled when the OS driver starts.
  • Never assume a firmware timeout honours CAP.TO.
  • Never assume a PC uses Boot Partitions.
  • Never assume the pre-OS and OS host NQN/host ID match unless NBFT is consumed correctly.

Code / pseudocode

/* Pseudocode: minimal firmware-style controller enable honouring CAP.TO. */
int fw_nvme_enable(volatile u8 *bar0, u64 asq, u64 acq)
{
    u64 cap = rd64(bar0 + 0x00);
    u32 to_ms = (u32)((cap >> 24) & 0xFF) * 500;      /* CAP.TO, 500 ms units */
    if (rd32(bar0 + 0x1C) & 1) {                         /* CSTS.RDY */
        wr32(bar0 + 0x14, rd32(bar0 + 0x14) & ~1u);      /* CC.EN = 0 */
        if (wait_bit(bar0 + 0x1C, 1, 0, to_ms)) return -ETIMEDOUT;
    }
    wr32(bar0 + 0x24, (31u << 16) | 31u);               /* AQA: 32/32 */
    wr64(bar0 + 0x28, asq);
    wr64(bar0 + 0x30, acq);
    wr32(bar0 + 0x14, (4u << 20) | (6u << 16) | 1u);   /* IOCQES=4, IOSQES=6, EN=1 */
    for (u32 t = 0; t < to_ms; t++) {
        u32 csts = rd32(bar0 + 0x1C);
        if (csts & 2) return -EIO;                       /* CSTS.CFS: fatal */
        if (csts & 1) return 0;                          /* RDY */
        delay_ms(1);
    }
    return -ETIMEDOUT;                                   /* only after the full CAP.TO */
}

The bit positions used (CAP.TO in bits 31:24 of CAP; CC.EN bit 0, IOSQES bits 19:16, IOCQES bits 23:20; CSTS.RDY bit 0, CFS bit 1) are the well-established ones from the Base specification's Controller Registers section. Boot Partition register access is left out deliberately: write it only from the verified layout.

    struct.pack_into("<8sIII", hdr, 0, b"EFI PART", 0x00010000, 92, 0)
    struct.pack_into("<QQQQ", hdr, 24, 1, 0, 34, 0)
    struct.pack_into("<I", hdr, 16, zlib.crc32(bytes(hdr)) & 0xFFFFFFFF)
    img[ss:ss + 92] = hdr
    open(path, "wb").write(img)

def check(path, ss=512):
    with open(path, "rb") as f:
        data = f.read(ss * 2)
    mbr_ok = data[510:512] == b"\x55\xAA" and data[446 + 4] == 0xEE
    hdr = bytearray(data[ss:ss + 92])
    sig, rev, size, crc = struct.unpack_from("<8sIII", hdr, 0)
    struct.pack_into("<I", hdr, 16, 0)
    crc_ok = 92 <= size <= ss and (zlib.crc32(bytes(hdr[:size])) & 0xFFFFFFFF) == crc
    print(f"protective MBR: {mbr_ok}; GPT signature: {sig == b'EFI PART'}; header CRC ok: {crc_ok}")

if __name__ == "__main__":
    if sys.argv[1] == "--make":
        make(sys.argv[2]); print("wrote", sys.argv[2])
    else:
        check(sys.argv[1], int(sys.argv[2]) if len(sys.argv) > 2 else 512)

Running python3 gpt_check.py --make test.img then python3 gpt_check.py test.img prints protective MBR: True; GPT signature: True; header CRC ok: True. On a 4 KiB-LBA namespace (namespace 2 in the lab system), pass 4096: the GPT header is at LBA 1 of the namespace's own LBA size — a classic cause of "firmware cannot find the ESP" after cloning a disk between LBA formats.

Worked example

Scenario (synthetic): a server must boot from an NVMe/TCP namespace on a storage target. In firmware setup the operator configures host NQN nqn.2014-08.org.nvmexpress:uuid:1b4e28ba-…, a static IP on NIC port 1, and the target's discovery address. Boot succeeds to the kernel, but the system drops to an emergency shell: "cannot find root device".

  1. Localise the phase. The kernel loaded, so firmware boot over NVMe/TCP worked: discovery, connect and reads all succeeded. The failure is in the OS reconnection.
  2. Was the handoff produced? In the emergency shell: ls /sys/firmware/acpi/tables/ shows NBFT. Yes.
  3. Was it consumed? nvme list-subsys shows no fabric subsystems: the initramfs did not connect. The initramfs was built without NVMe-oF/NBFT support (for example, the dracut module for NVMe-oF absent).
  4. Fix. Rebuild initramfs with NVMe-oF support and nvme-cli; regenerate; reboot.
  5. Second issue. After the fix, the target logs show two host NQNs from this server: the OS used /etc/nvme/hostnqn (a different value) for a second, manual connection. The target's access control allowed only the firmware's NQN, so some namespaces were missing. Fix: make the OS identity match NBFT, or update target access control lists (ACLs). Derived scenario; tooling details are distribution-dependent.

Common mistakes

  1. Assuming firmware honours CAP.TO.
  2. Assuming the OS starts with the controller disabled.
  3. Confusing Boot Partitions with the EFI System Partition.
  4. Cloning a disk image between 512-byte and 4 KiB LBA namespaces and expecting the GPT to be found.
  5. Building an initramfs without NVMe-oF/NBFT support for a fabric-booted system.
  6. Mismatched host NQN/host ID between firmware and OS.
  7. Testing boot only with warm reboots, never after unclean power-off.
  8. Assuming legacy BIOS can boot NVMe without an option ROM.

Senior engineer insight

  • The boot path is a different product. Firmware NVMe drivers, firmware TCP stacks and boot ROMs exercise code paths the OS never touches. Qualify them separately, with the exact platform firmware revision.
  • Handoffs are where bugs live. Firmware → OS (controller state, DMA quiescence), firmware → OS (NBFT identity). Write down what each side assumes and test the assumption directly.
  • Time is a contract. CAP.TO is the device's promise; the platform's timeout is the host's patience. When they disagree, the failure appears only under rare conditions (unclean shutdown, large drives), which is why it escapes testing.
  • Diskless fleets change the blast radius. With NVMe/TCP boot, a target or network problem can stop many servers from booting. Multipath descriptions in NBFT and redundant discovery are design requirements, not extras.

Lab

Lab — Reconstruct a boot and find the handoff

Objective

Reconstruct how your machine booted from NVMe using read-only tools, verify the GPT logic on an image, and diagnose the synthetic timeout trace.

Skills

Boot-path reconstruction, register reasoning, log correlation.

Safety

Safe lab: read-only commands and file images only. Do not modify boot variables or Boot Partitions.

Hardware required

Any Linux system booted from NVMe (optional); otherwise none.

Software required

Python 3, efibootmgr, nvme-cli.

Input

gpt_check.py, the abnormal trace.

Expected output

A one-page boot reconstruction: boot entry, device path, namespace, OS reset evidence; GPT check results; timeout diagnosis.

Background

Re-read the local boot steps and the OS handoff section.

Step 1

Run efibootmgr -v; identify BootCurrent and decode its device path down to the NVMe namespace node. Map it to /dev/nvme0n1 via NSID.

Step 2

Run dmesg | grep nvme and find evidence the OS driver re-initialised the controller (queue counts, any reset messages).

Step 3

Create a test image with gpt_check.py --make, verify it, then corrupt one byte in the GPT header (offset 512+40) and re-check. Then check the image with sector size 4096 and explain the result.

Observation

Record each check's result and the reason.

Questions

  1. Why does the 4096 check fail on a 512-byte image?
  2. In the abnormal trace, what single register value proves the device was not in a fatal state?

Challenge

Compute the CAP.TO value a drive would need to report if its worst-case recovery is 23 s, and the CAP register bits that hold it.

Hints

CAP.TO counts 500 ms units; round up.

Solution

Step 3: corruption → "header CRC ok: False"; with 4096 the tool looks for the header at byte 4096 where the 512-byte image has only zeros → signature False and CRC check False (header size field is 0).

Questions: firmware reads LBA 1 in the namespace's LBA size; CSTS = 0x00000000 shows CFS = 0 (no fatal status) and RDY = 0.

Challenge: 23 s / 0.5 s = 46 → CAP.TO = 46 (0x2E), in CAP bits 31:24.

What a senior engineer notices

Whether BootCurrent matches the expected entry (fallback paths hide real failures), and whether the system has ever been tested after an unclean power-off.

Failure variants

  • Boot entry points to a namespace by EUI-64 that changed after a drive swap.
  • Two ESPs on two drives; firmware picks the wrong one.
  • CSTS.CFS = 1 during boot — a genuine device fault.

Extension

In a virtual machine with UEFI firmware (for example OVMF) and an emulated NVMe device, enable firmware debug logging and compare the firmware NVMe driver's command sequence with the trace above.

Exercises

  1. List every register write a firmware NVMe driver makes from enumeration to the first Identify, in order.
  2. Explain why a Boot Partition read needs no admin queue, and what replaces the CQE.
  3. Describe what information the OS needs to reconnect after NVMe/TCP boot, and where it gets it.
  4. Compute the number of 256-byte MWr TLPs to deliver a 512 KiB Boot Partition read.
  5. Design a test that would catch a firmware timeout shorter than CAP.TO.
Model answers

1: Config: BAR0/BAR1, Command register. MMIO: (CC.EN=0 if needed), AQA, ASQ, ACQ, CC; then doorbell SQ0 tail.

2: The host names the data (partition, offset, size) and buffer through registers; completion is reported as read status in BPINFO.

3: Host NQN and host ID, interface addressing, subsystem NQN, transport address/port, namespace identity, discovery info — from the NBFT.

4: 524,288 / 256 = 2,048.

5: An emulated or instrumented drive that delays CSTS.RDY by a controlled time below CAP.TO; boot must succeed for every delay up to CAP.TO.

Quiz

  1. On a typical UEFI PC, where does the OS loader for an NVMe boot come from?

    • NVMe Boot Partition 0
    • A file on the EFI System Partition in a namespace
    • The Controller Memory Buffer
    • The option ROM
    Answer and reasoning

    UEFI reads the GPT, finds the ESP and loads the loader file. Boot Partitions are mainly for embedded hosts.

  2. In what units is CAP.TO expressed?

    • 1 ms
    • 100 ms
    • 500 ms
    • 1 s
    Answer and reasoning

    500 ms units; CAP.TO = 60 means 30 s.

  3. Which ACPI table hands NVMe-oF boot information to the OS?

    • iBFT
    • MCFG
    • DMAR
    • NBFT
    Answer and reasoning

    NBFT, defined by the NVMe Boot Specification. iBFT is for iSCSI; MCFG describes PCIe Enhanced Configuration Access Mechanism (ECAM) regions; DMAR describes DMA remapping hardware (the IOMMU).

  4. What does the OS NVMe driver usually do first with a controller that firmware enabled?

    • Disable it (CC.EN = 0), wait for CSTS.RDY = 0, then re-initialise
    • Reuse the firmware's queues
    • Issue a Boot Partition read
    • Nothing; it is already ready
    Answer and reasoning

    The OS cannot trust firmware queue memory; it resets and builds its own.

  5. Name the three Boot Partition registers and their roles.

    Model answer

    BPINFO (size, read status, active partition), BPRSEL (which partition, offset, size — starts the read), BPMBL (host buffer address). Offsets to be confirmed in the specification.

  6. Why might legacy BIOS fail to boot an NVMe drive that UEFI boots fine?

    Model answer

    Legacy BIOS needs an INT 13h option ROM for NVMe; many drives/platforms do not provide one, whereas UEFI firmware includes an NVMe driver.

  7. In the abnormal boot trace, why is the first abnormal event a host action?

    Model answer

    The device behaved within its declared contract (not ready, no fatal status, within CAP.TO); the host gave up early.

  8. What PCIe traffic does an NVMe/TCP boot generate between CPU and the boot namespace?

    Model answer

    None to an NVMe controller — the PCIe link carries NIC traffic; NVMe commands travel inside TCP PDUs on the network.

  9. Which configuration-space register exposes an option ROM?

    Model answer

    The Expansion ROM Base Address Register at offset 30h in a Type 0 header.

Interview questions

  1. Beginner: How does a UEFI system boot from an NVMe SSD?

    Model answer

    Firmware enumerates PCIe, its NVMe driver enables the controller and exposes namespaces as block devices, the boot manager finds the ESP on the GPT and runs the loader, which loads the OS.

  2. Intermediate: What are NVMe Boot Partitions for?

    Model answer

    Small dedicated areas readable through a register mechanism without full controller initialisation, for simple boot ROMs; two partitions allow safe updates.

  3. Intermediate: What happens to the controller at OS handoff?

    Model answer

    Firmware stops using it at ExitBootServices; the OS driver disables and re-initialises it with its own queues and interrupts.

  4. Advanced: Explain NVMe/TCP boot and the role of NBFT.

    Model answer

    A firmware NVMe/TCP initiator connects to the target (optionally via discovery), reads the loader, and records host identity, interfaces, and subsystem/namespace information in the NBFT so the OS can reconnect identically.

  5. Senior: Intermittent "no boot device" after power failures across 2% of a fleet. Approach?

    Model answer

    Correlate with unsafe-shutdown counts; capture boot with an analyzer or firmware log to measure time-to-ready; compare to CAP.TO and the firmware timeout; reproduce with power-cut cycles; fix the side violating the contract.

  6. Senior: What would you require in a design review of a diskless NVMe/TCP-booted fleet?

    Model answer

    Redundant discovery/targets and multipath in NBFT; consistent host identity; initramfs support tested; boot-storm capacity on targets; security of boot configuration; fallback/recovery boot path.

Model teach-back (senior)

Boot is a chain of contracts: the device promises readiness within CAP.TO, the firmware must wait that long and must quiesce DMA before ExitBootServices, the OS must assume nothing about controller state, and for fabric boot the NBFT is the contract that keeps host identity and paths consistent across the firmware/OS boundary.

Chapter summary

Booting from NVMe means a firmware NVMe driver performs a minimal controller initialisation, reads GPT and ESP from a namespace, and hands off to an OS that re-initialises the controller. Option ROMs matter for legacy and add-in scenarios; UEFI usually has a built-in NVMe driver. Boot Partitions offer a register-driven read path for simple hosts (BPINFO, BPRSEL, BPMBL — confirm their layouts). The NVMe Boot Specification 1.4 standardises pre-OS NVMe-oF boot and the NBFT handoff. Most boot failures are contract violations at a handoff: timeouts shorter than CAP.TO, DMA not quiesced, identity not carried across.

Do not move on until you can:

  • explain Boot Partitions and how a read completes without a CQE
  • draw the NVMe/TCP boot flow including NBFT
  • diagnose the early-timeout trace and name the first abnormal event
  • reconstruct your own system's boot path from efibootmgr and dmesg
  • state what to confirm in Base 2.4 and Boot 1.4
