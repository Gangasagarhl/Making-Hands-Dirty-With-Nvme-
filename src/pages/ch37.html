Scatter Gather Lists (SGLs) describe a data buffer as a chain of 16-byte descriptors, each with its own address, length and type. This chapter teaches the descriptor types and layout, how segments chain, how a host discovers and selects SGL support, where SGLs beat Physical Region Pages (PRPs) and where they do not, and what SGL traffic looks like on the PCI Express (PCIe) link.

Why this chapter exists

In Chapter 36 you learned that PRPs can describe only one shape of buffer: a run that may start mid-page, continues through whole pages and may end mid-page. Real software does not always produce that shape. A network stack hands the storage layer a 9 KiB message split into a 1,500-byte header region and a scattering of payload fragments. A database wants to read eight blocks but only keep the fifth. A virtual machine's guest buffer, after translation, is a list of small, unaligned pieces. NVMe over Fabrics (NVMe-oF) has no host-memory pages to point at at all — it has remote memory regions protected by keys, or data that travels inside the command capsule.

The NVM Express (NVMe) answer to all of these is the Scatter Gather List: a list of descriptors, where each descriptor says "this many bytes, at this address, and this is what kind of thing I am". It costs more bytes per entry than a PRP (16 instead of 8) and more work for the controller, and in exchange it removes the alignment rules, adds a way to discard data, describes metadata as flexibly as data, and works across transports.

Knowing SGLs matters for three practical reasons. First, every NVMe-oF trace you read (TCP or RDMA) is full of SGL descriptors. Second, on PCIe, Linux and user-space drivers switch between PRPs and SGLs depending on the request, so you will meet both in the same trace. Third, SGL errors have their own family of status codes; recognising them is the fastest way to localize a malformed request.

Learning objectives

  • Name the SGL descriptor types — Data Block, Bit Bucket, Segment, Last Segment, Keyed Data Block, Transport Data Block — and state what each describes.
  • Draw the 16-byte descriptor layout: Address, Length, reserved/Key bytes, and the SGL Identifier (type and sub type).
  • Build a multi-segment SGL and place Segment and Last Segment descriptors correctly.
  • Read the SGL Support (SGLS) field of Identify Controller and choose PRP or SGL with the PRP or SGL for Data Transfer (PSDT) field.
  • Compare PRP and SGL for alignment, size, controller cost and transport applicability.
  • Predict the PCIe traffic for an SGL command, including segment fetches.
  • Recognize SGL-specific error statuses and their likely causes.

The story

The warehouse robot from the last chapter is back. This time, instead of an order card with two lines and clipboards full of shelf numbers, you give it stickers. Every sticker is the same size and says three things: where to go, how many toys to take, and what kind of sticker it is.

A blue sticker says "take 7 toys from aisle 12, starting at spot 3" — you can start anywhere and take any number. A grey sticker says "throw away the next 5 toys, I don't want them". A yellow sticker says "the rest of my stickers are stuck on a board in aisle 40, and there are 12 of them". A red sticker says the same thing but also means "and that board is the last one".

The robot is a bit slower, because it has to read each sticker's count and type. But you can describe any messy pile of toys you like.

Think of a courier's multi-stop delivery manifest. Each line is a stop: an address and a number of parcels. The manifest does not care whether the stops are evenly spaced or whether a stop takes a whole truckload or a single envelope. Some lines are instructions rather than stops — "continue on manifest sheet 2, which has 30 lines" — and the final continuation is marked as the last sheet. A "return to sender, do not deliver" line tells the driver to drop parcels instead of delivering them. For international shipments, a stop may also carry a customs authorization code without which the receiving depot refuses the parcel: that is the key in a Keyed SGL Data Block.

  • Stickers are not free. Each descriptor is 16 bytes and every segment is fetched over PCIe. For a page-aligned buffer, an SGL can be larger than the equivalent PRP list.
  • The robot cannot jump around a manifest. With PRPs, the controller finds the page for any byte by arithmetic. With SGLs it must add up lengths in order to find where byte k lives. That changes how controllers implement out-of-order data movement.
  • "Throw away" only makes sense for deliveries to you. A Bit Bucket discards data the controller would have written to host memory (a read). It cannot invent data for a write.
  • Customs codes are not on every road. Keyed descriptors exist for RDMA fabrics; a PCIe controller does not use them.
  • Not every robot reads stickers. SGL support is optional on PCIe; a controller that does not support SGLs rejects them.

Beginner explanation

An SGL is a list of descriptors that together describe where a command's data lives. Each descriptor is exactly 16 bytes and has an address, a length in bytes, and a type. The most common type, the SGL Data Block, simply says "length bytes at address". A list of Data Blocks can describe any number of fragments of any size at any address — no page rules.

The SQE still has only 16 bytes of data pointer. With SGLs those 16 bytes hold exactly one descriptor, called SGL Entry 1 (SGL1). If the whole buffer is one contiguous run, SGL1 is a Data Block and the job is done. If the buffer has several pieces, SGL1 is a Segment or Last Segment descriptor: it points to an array of further descriptors in host memory, called an SGL segment. A segment can end with another Segment descriptor, so lists chain without limit.

The host chooses between PRPs and SGLs for each command with a two-bit field in Command Dword 0 called PSDT. The host may only choose SGLs if the controller says, in its Identify Controller data, that it supports them.

Engineering explanation

The 16-byte descriptor

Every SGL descriptor shares one rule: byte 15 is the SGL Identifier. Its upper four bits (7:4) are the SGL Descriptor Type and its lower four bits (3:0) are the SGL Descriptor Sub Type. The other fifteen bytes are interpreted according to the type. All multi-byte fields are little-endian.

Segments and chaining

An SGL segment is a contiguous array of descriptors in memory. The rules are few and strict:

  • SGL1 in the SQE is the only descriptor not in a segment. It may be a Data Block (whole buffer is contiguous), a Segment, a Last Segment, or a transport-appropriate Data Block on fabrics.
  • A Segment or Last Segment descriptor may appear in a segment only as the last descriptor of that segment. Its Length is the size in bytes of the segment it points to, so it is a multiple of 16.
  • The segment pointed to by a Last Segment descriptor is the last segment: it contains no Segment or Last Segment descriptors.
  • The data described is the concatenation of every Data Block and Bit Bucket, in order, across all segments.

Why both "Segment" and "Last Segment"? Because a controller that knows the next segment is the last can stop looking for further chaining and size its fetch exactly. It also lets the controller detect a malformed list: a Segment descriptor inside a last segment is an error it can report.

Selecting SGLs: PSDT and the metadata pointer

Command Dword 0 holds the opcode (bits 7:0), the fused-operation field (bits 9:8) and PSDT (bits 15:14). PSDT decides how DPTR and MPTR are read:

PSDT values
PSDTDPTR isMPTR is
00bPRP1 + PRP2address of a contiguous metadata buffer
01bSGL1address of a contiguous, byte-aligned metadata buffer (if supported)
10bSGL1address of an SGL segment describing the metadata (the specification restricts this to a single descriptor; confirm the exact wording)
11breserved

Over PCIe, admin commands use PRPs: a host sets PSDT to 00b for every admin command. SGL support for I/O is optional and advertised by SGLS. On fabrics, every command uses SGLs and PRPs are not used Normative.

Address, length and alignment

  • Address: any byte address when SGLS reports 01b; dword-aligned when it reports 10b. Segment addresses are typically required to be quadword aligned — confirm in the specification for your revision Uncertain.
  • Length: a 32-bit byte count (24-bit for Keyed). A Data Block of length zero is legal in some contexts and rejected in others; avoid it.
  • Total: the sum of Data Block and Bit Bucket lengths must equal the command's transfer length, or exceed it only if the controller reports support for SGLs longer than the data. Too short is an error.
  • Page boundaries: irrelevant to the descriptor. A Data Block may span any number of pages, as long as the address range is contiguous in the device's address space (IOVA space when an IOMMU is on).

Bit Bucket

A Bit Bucket descriptor tells the controller "the next length bytes of data for this read are not wanted". The controller still reads the media and accounts for the bytes; it simply does not write them to host memory. Typical uses: reading a whole block when only part is needed, skipping protection information, or read-modify sequences in storage stacks. Bit Buckets are for controller-to-host data; how a controller treats one in a host-to-controller transfer is specified as an error case — check the exact status in the specification Uncertain. Support is optional (SGLS bit 16).

Keyed and transport descriptors (fabrics)

In NVMe over RDMA, the host registers a memory region with its RDMA network interface and gets a remote key. It sends a Keyed SGL Data Block with the address, length and key; the target controller then performs RDMA Read or RDMA Write operations directly against that region, and the host's network interface checks the key. In NVMe over TCP, data either rides in the command capsule (in-capsule data, described with an offset-type Data Block) or is transferred in separate data PDUs described by a Transport SGL Data Block. See Chapter 66 — NVMe/TCP and Chapter 67 — NVMe/RDMA.

The teaching ladder for SGLs

Stickers that each say where, how many, and what kind — including "throw these away" and "more stickers on that board".

16-byte descriptors with address, length and type; SGL1 in the SQE; Segment/Last Segment descriptors chain arrays of descriptors in host memory.

The controller's data-pointer engine fetches segments, accumulates lengths into a running offset map, and feeds address/length pairs to the DMA engine; a Bit Bucket becomes "advance the offset without a bus transfer".

The NVMe Base Specification defines descriptor formats, types, segment rules, SGLS and PSDT, and SGL error statuses; transport specifications define which descriptors their transport uses.

Over PCIe: MRd for each segment, then data MRd/MWr per Data Block, cut by Max Payload Size, Max Read Request Size and 4 KiB boundaries; on fabrics: RDMA operations or TCP data PDUs per descriptor.

In an analyzer: a 64-byte SQE read whose last 16 bytes end in 0x30 or 0x20 (Last Segment / Segment) or 0x00 (Data Block), a read of exactly the Length in SGL1 from its Address, then data TLPs whose address ranges match each Data Block.

Status codes in the SGL family point at descriptor problems; data TLPs that skip expected ranges suggest Bit Buckets or wrong lengths; a segment read whose length is not a multiple of 16 is a host bug before the controller even acts.

Hardware view

An SGL engine is a small sequential machine: fetch a segment, read descriptors in order, keep a running byte offset, and hand (host address, length, command offset) tuples to the DMA engine. The internal design is private to each controller Implementation-dependent.

What changes compared with PRPs

  • Sequential walk. To find where command byte k lives the controller must sum descriptor lengths. Controllers that move data out of order (as NAND completes) usually expand the SGL into an internal table first, which costs on-chip memory and latency before data can move.
  • Unaligned DMA. Byte-aligned addresses mean TLPs with partial first/last byte enables. Controllers that report dword granularity (SGLS 10b) avoid that hardware complexity.
  • Fewer fetches for big contiguous runs. A 1 MiB buffer in one IOVA range is one Data Block, already in the SQE: no list fetch at all.
  • More fetches for small fragments. 32 fragments cost 512 bytes of descriptors versus 256 bytes of PRP list for 32 pages.
  • Bit Buckets are pure bookkeeping: the engine advances its offset and skips the bus transfer, saving link bandwidth.

The IOMMU makes SGLs more attractive

When an IOMMU is in translated mode, the kernel's DMA mapping layer can map a scattered set of physical pages into one contiguous IOVA range. A 128 KiB buffer that would need a 31-entry PRP list can then be described by a single SGL Data Block. Whether a given kernel merges mappings this way depends on the IOMMU driver and configuration Implementation-dependent.

  • It does not require hosts to use SGLs even when supported (on PCIe).

Protocol view

On PCIe, an SGL command produces the same kinds of TLPs as a PRP command; only the descriptor fetches differ. Follow a 8 KiB Write described by a Last Segment of three Data Blocks (the lab system: Gen4 x4, Max Payload Size 256 B, MRRS 512 B, Requester ID 0x0100):

Direction, ordering and dependencies

  • Segment fetches are controller-initiated MRd, like PRP list fetches. Each Segment descriptor creates a dependency: the controller cannot read segment n+1 before it has read the last descriptor of segment n.
  • Data for a Read is MWr (posted); for a Write it is MRd with CplD. A Bit Bucket produces no TLP.
  • A Data Block that crosses a 4 KiB address boundary is split there by the device, because no PCIe request may cross 4 KiB.
  • Byte-aligned Data Blocks produce TLPs with partial byte enables at the edges; length and First/Last DW Byte Enables in the TLP header reflect that.
  • Fabrics replace all of this with transport operations: RDMA Read/Write against keyed regions or TCP data PDUs; there are no TLPs between host and target.

Code / pseudocode

A driver-side sketch for building an SGL from fragments, with one segment page and chaining when needed:

struct sgl_desc { u64 addr; u32 len; u8 rsvd[3]; u8 id; };   /* 16 bytes */
#define SGL_ID(type, sub)  (((type) << 4) | (sub))
enum { DATA_BLOCK = 0x0, BIT_BUCKET = 0x1, SEGMENT = 0x2, LAST_SEGMENT = 0x3 };

int build_sgl(struct sqe *cmd, struct frag *f, int n, u32 seg_cap)  /* seg_cap: descriptors per segment page */
{
    cmd->cdw0 = (cmd->cdw0 & ~(3u << 14)) | (1u << 14);   /* PSDT = 01b */
    if (n == 1) {                                         /* contiguous: SGL1 is the data */
        cmd->sgl1 = (struct sgl_desc){ f[0].iova, f[0].len, {0}, SGL_ID(DATA_BLOCK, 0) };
        return 0;
    }
    struct sgl_desc *seg = alloc_seg(&seg_iova);
    int left = n, in_this;
    /* SGL1 points to the first segment; Last Segment if everything fits */
    in_this = (left <= seg_cap) ? left : seg_cap - 1;
    cmd->sgl1 = (struct sgl_desc){ seg_iova,
                  16 * (in_this + (left > seg_cap)), {0},
                  SGL_ID(left <= seg_cap ? LAST_SEGMENT : SEGMENT, 0) };
    for (;;) {
        for (int i = 0; i < in_this; i++, f++)
            seg[i] = (struct sgl_desc){ f->iova, f->len, {0}, SGL_ID(DATA_BLOCK, 0) };
        left -= in_this;
        if (!left) break;
        struct sgl_desc *next = alloc_seg(&next_iova);
        int next_count = (left <= seg_cap) ? left : seg_cap - 1;
        seg[in_this] = (struct sgl_desc){ next_iova,
                  16 * (next_count + (left > seg_cap)), {0},
                  SGL_ID(left <= seg_cap ? LAST_SEGMENT : SEGMENT, 0) };
        seg = next; in_this = next_count;
    }
    write_barrier();
    return 0;
}

An executable encoder, decoder and walker. It builds the descriptors used in this chapter's examples, walks them the way a controller would, and reports problems. Run it with python3 sgl_tool.py.

#!/usr/bin/env python3
"""sgl_tool.py - encode, decode and walk NVMe SGL descriptors (teaching tool).

Synthetic example for teaching. Standard library only.
Layout used (16 bytes, little-endian):
  bytes 7:0   Address (Bit Bucket: reserved)
  bytes 11:8  Length
  bytes 14:12 reserved (Keyed SGL Data Block: Length is bytes 10:8, Key is bytes 14:11)
  byte  15    SGL Identifier: bits 7:4 = Descriptor Type, bits 3:0 = Sub Type
Confirm the layout and code values in the NVMe Base Specification
("Scatter Gather List (SGL)" in the data-structures material) for your revision.
"""
import struct

TYPES = {0x0: "Data Block", 0x1: "Bit Bucket", 0x2: "Segment",
         0x3: "Last Segment", 0x4: "Keyed Data Block",
         0x5: "Transport Data Block", 0xF: "Vendor Specific"}


def encode(dtype, addr=0, length=0, subtype=0, key=None):
    ident = (dtype << 4) | subtype
    if dtype == 0x4:                       # keyed: 3-byte length + 4-byte key
        body = struct.pack("<Q", addr) + length.to_bytes(3, "little") + \
            struct.pack("<I", key or 0)
    else:
        body = struct.pack("<QI", addr, length) + bytes(3)
    return body + bytes([ident])


def decode(d):
    assert len(d) == 16, "an SGL descriptor is exactly 16 bytes"
    dtype, sub = d[15] >> 4, d[15] & 0xF
    addr = struct.unpack_from("<Q", d, 0)[0]
    if dtype == 0x4:
        length = int.from_bytes(d[8:11], "little")
        key = struct.unpack_from("<I", d, 11)[0]
        return dict(type=TYPES.get(dtype, f"reserved {dtype:x}h"), sub=sub,
                    addr=addr, length=length, key=key)
    length = struct.unpack_from("<I", d, 8)[0]
    return dict(type=TYPES.get(dtype, f"reserved {dtype:x}h"), sub=sub,
                addr=addr, length=length)


def walk(sgl1, memory, expected_len, is_write):
    """Follow SGL1 through segments the way a controller would.

    memory: dict {address: bytes} holding segments the host built.
    Returns (list of (addr, len) data runs, list of problems).
    """
    runs, problems, total = [], [], 0
    pending = [sgl1]
    seen_last = False
    while pending:
        desc = decode(pending.pop(0))
        t = desc["type"]
        if t == "Data Block":
            runs.append((desc["addr"], desc["length"]))
            total += desc["length"]
        elif t == "Bit Bucket":
            if is_write:
                problems.append("Bit Bucket in a Write: host-to-device data cannot be discarded")
            runs.append((None, desc["length"]))
            total += desc["length"]
        elif t in ("Segment", "Last Segment"):
            if pending:
                problems.append(f"{t} descriptor is not the last descriptor of its segment")
            if seen_last:
                problems.append(f"{t} descriptor found inside the Last Segment")
            if desc["length"] == 0 or desc["length"] % 16:
                problems.append(f"segment length {desc['length']} is not a non-zero multiple of 16")
                break
            seg = memory.get(desc["addr"])
            if seg is None or len(seg) < desc["length"]:
                problems.append(f"segment at 0x{desc['addr']:x} not present in host memory")
                break
            pending = [seg[i:i + 16] for i in range(0, desc["length"], 16)]
            seen_last = t == "Last Segment"
        else:
            problems.append(f"descriptor type {t} not handled by this walker")
    if total < expected_len:
        problems.append(f"SGL describes {total} bytes, command needs {expected_len}")
    elif total > expected_len:
        problems.append(f"SGL describes {total} bytes > {expected_len}: legal only if the "
                        "controller reports support for SGL length larger than the data")
    return runs, problems


def show(title, sgl1, memory, n, is_write=False):
    runs, problems = walk(sgl1, memory, n, is_write)
    print(title)
    print("  SGL1 =", sgl1.hex(" "), "->", decode(sgl1)["type"])
    for a, ln in runs:
        print("   ", "discard" if a is None else f"0x{a:x}", ln, "bytes")
    print("  result:", "; ".join(problems) if problems else "valid")
    print()


if __name__ == "__main__":
    # 1) One contiguous 8 KiB buffer: a single Data Block in the SQE.
    show("Single Data Block, 8 KiB", encode(0x0, 0x2_0000_0000, 8192), {}, 8192)

    # 2) Three fragments via a Last Segment of three Data Blocks at 0x1_5000_0000.
    seg = (encode(0x0, 0x2_0000_0400, 3072) +       # 3 KiB, starts mid-page
           encode(0x0, 0x2_0003_0000, 1024) +       # 1 KiB elsewhere
           encode(0x0, 0x2_0007_1000, 4096))        # 4 KiB
    mem = {0x1_5000_0000: seg}
    show("Last Segment, 3 Data Blocks (8 KiB)",
         encode(0x3, 0x1_5000_0000, len(seg)), mem, 8192)

    # 3) Read that keeps only the second 4 KiB: Bit Bucket + Data Block.
    seg2 = encode(0x1, 0, 4096) + encode(0x0, 0x2_0000_0000, 4096)
    mem2 = {0x1_5000_1000: seg2}
    show("Read with Bit Bucket (discard first 4 KiB)",
         encode(0x3, 0x1_5000_1000, 32), mem2, 8192)

    # 4) Broken: segment length 40 (not a multiple of 16).
    show("BROKEN: Last Segment length 40", encode(0x3, 0x1_5000_0000, 40), mem, 8192)

    # 5) Keyed Data Block as an RDMA host would send it (fabrics only).
    k = encode(0x4, 0x7F00_1234_0000, 8192, subtype=0x0, key=0x00C0FFEE)
    print("Keyed Data Block:", k.hex(" "), decode(k))

Expected behavior: the first three examples print "valid" with their data runs; the fourth reports the length-40 segment; the last prints the 16 bytes of a Keyed descriptor and decodes them back.

Worked example

All examples use the lab system: Namespace 1 with 512-byte blocks, buffers from 0x2_0000_0000, segments from 0x1_5000_0000, Max Payload Size 256 B, MRRS 512 B, and a controller reporting SGLS bits 1:0 = 01b with Bit Bucket support. Synthetic examples for teaching.

Example 1 — 8 KiB contiguous: one Data Block in the SQE

Read, NLB = 15, buffer 0x2_0000_0000 contiguous in IOVA space. SGL1 = Data Block, address 0x2_0000_0000, length 0x2000:

SQE bytes 24..39 (DPTR): 00 00 00 00 02 00 00 00 | 00 20 00 00 | 00 00 00 | 00
                         address (LE)              length (LE)   reserved   ID: type 0h, sub 0h

PCIe traffic: no descriptor fetch at all; 32 MWr of 256 B. Compare PRPs: PRP1 + PRP2, also no list. For 128 KiB contiguous in IOVA space the SGL is still one descriptor, while PRPs need a 31-entry list and a list fetch.

Example 2 — three unaligned fragments: Last Segment

Write, NLB = 15 (8,192 B), fragments 3,072 B at 0x2_0000_0400, 1,024 B at 0x2_0003_0000, 4,096 B at 0x2_0007_1000. PRPs cannot describe this: the first fragment ends at 0x2_0000_1000 (fine) but the second fragment ends mid-page at 0x2_0003_0400 and the next one starts on a different page — a gap inside the buffer.

PCIe traffic: 1 MRd of 48 B (segment), 16 data MRd, 32 or more CplD.

Example 3 — 300 fragments: chained segments

Suppose a gather Write of 300 fragments of 512 B each (NLB = 299, 153,600 B), and the driver allocates 4 KiB segment pages (256 descriptors each).

  • Segment A (0x1_5000_0000, 4,096 B): 255 Data Blocks + 1 Last Segment descriptor pointing to segment B.
  • Segment B (0x1_5000_1000, 45 × 16 = 720 B): 45 Data Blocks.
  • SGL1 = Segment (type 2h), not Last Segment, because segment A is not the last segment: 00 00 00 50 01 00 00 00 00 10 00 00 00 00 00 20.
  • The last descriptor of A = Last Segment (type 3h), address 0x1_5000_1000, length 720: 00 10 00 50 01 00 00 00 d0 02 00 00 00 00 00 30.

PCIe traffic: segment A is 4,096 B = 8 MRd of 512 B; segment B is 720 B = 2 MRd (512 + 208). The controller can only issue segment B's reads after it has seen A's last descriptor. Data: 300 MRd of 512 B. With PRPs, the same 300 fragments would be legal only if each 512 B fragment were the full content of a page — they are not — so SGLs are the only option.

Example 4 — read with a Bit Bucket

The application needs only blocks 8–15 of a 16-block region but the storage stack prefers one command. Read, NLB = 15, SGL1 = Last Segment (32 B) → [Bit Bucket, length 4096], [Data Block 0x2_0000_0000, length 4096].

 0x1_5000_1000: Bit Bucket   (addr reserved)   len 4096   -> no TLPs, bytes discarded
 0x1_5000_1010: Data Block   0x2_0000_0000     len 4096   -> 16 MWr x 256 B

PCIe traffic: 1 MRd of 32 B (segment), 16 data MWr. The link carries half the data a plain 8 KiB read would. The media work is the same.

Example 5 — Keyed Data Block over RDMA

A host on NVMe over RDMA wants to read 8 KiB into a registered region at remote address 0x7F00_1234_0000 with remote key 0x00C0FFEE. SGL1 = Keyed Data Block (type 4h): 00 00 34 12 00 7f 00 00 | 00 20 00 | ee ff c0 00 | 40 — address, 24-bit length 0x002000, key 0x00C0FFEE, identifier 0x40. The target controller moves the data with RDMA Write operations into that region; the host's RDMA adapter validates the key. No PCIe TLPs cross between host and target, although each side's adapter still does PCIe DMA to its own memory.

Example 6 — metadata by SGL (PSDT = 10b)

A namespace formatted with 8 bytes of separate metadata per block. Read, NLB = 15 needs 128 bytes of metadata. With PSDT = 10b, MPTR holds the address of an SGL segment that describes the metadata buffer, for example one Data Block of 128 B at an unaligned address that PRP-mode MPTR could not express if it were scattered. Confirm in the specification how many descriptors the metadata SGL may contain.

Debugging connection

  1. Decode byte 15 of DPTR: type and sub type of SGL1. Confirm PSDT in Command Dword 0 matches (PRP vs SGL).
  2. Check SGLS for this controller: supported? alignment mode? Bit Bucket? Keyed?
  3. Follow every segment: the read in the trace must be exactly the address and length of the pointing descriptor.
  4. Sum Data Block and Bit Bucket lengths and compare with (NLB + 1) × LBA size.
  5. Partition each Data Block into expected TLPs and compare addresses; a gap suggests a Bit Bucket or a wrong length.
  6. Read the CQE status: SGL-family codes localize the problem to the descriptor structure; a Data Transfer Error or an IOMMU fault points at the addresses instead.

Senior engineer insight

  • Choose by measurement, not by elegance. SGLs are more expressive; that does not make them faster. Many PCIe controllers are tuned for PRPs on small I/O. Linux's threshold policy reflects this.
  • The IOMMU changes the trade-off. If the IOVA allocator gives you contiguous ranges, a large I/O becomes one Data Block — the best case for SGLs.
  • Two code paths computing one length is a bug factory. Data SGL Length Invalid in the field nearly always means the SGL builder and the command builder disagree.
  • Fabrics debugging is SGL debugging. Every NVMe/RDMA and NVMe/TCP command carries an SGL; learn to read the descriptor bytes on sight.
  • Watch the edges of byte-aligned buffers. Partial byte enables and odd-length TLPs exercise root complex and controller paths that PRP traffic rarely touches; validation should cover them deliberately.

Lab 37 — Encode, decode and walk SGLs

Objective

Encode SGL descriptors by hand, decode raw SQE bytes, and walk multi-segment SGLs to predict data ranges and detect malformed lists.

Skills

  • Descriptor byte layout and endianness
  • Segment chaining rules
  • Length accounting and status prediction

Safety

Safe lab Paper and Python only; optional read-only Linux commands.

Hardware required

None.

Software required

Python 3; optionally nvme-cli.

Input

  1. DPTR bytes: 00 04 00 00 02 00 00 00 00 0c 00 00 00 00 00 00
  2. DPTR bytes: 40 00 00 50 01 00 00 00 40 00 00 00 00 00 00 30 with segment content of four Data Blocks of 2,048 B each, command NLB = 0x000F.
  3. DPTR bytes: 00 00 00 50 01 00 00 00 20 00 00 00 00 00 00 30 with segment content: [Segment → 0x1_5000_1000 len 16], [Data Block 0x2_0000_0000 len 4096].

Expected output

For each: descriptor type, address, length; valid or not; expected PCIe reads of descriptors; data TLPs; or the expected error.

Background

Byte 15 is the identifier; addresses and lengths are little-endian.

Step 1

Decode each 16-byte value by hand.

Step 2

Apply the segment rules and length sums.

Step 3

Encode the same structures with sgl_tool.py (encode() and walk()) and compare.

Step 4 (optional)

Run nvme id-ctrl -H on a real controller and record its SGL support.

Observation

Note how quickly the identifier byte tells you which world you are in.

Questions

  1. Which input needs no descriptor fetch?
  2. Which input is malformed, and which status family would you expect?
  3. In input 2, how many MRd TLPs fetch descriptors and data for a Write?

Challenge

Rewrite input 3 so that it is valid without changing the data it describes.

Hint

Look at where the Segment descriptor sits inside a Last Segment's target.

Solution
  1. Data Block, address 0x2_0000_0400, length 0x0C00 = 3,072 B. Valid if the command is 3,072 B (NLB = 5 with 512-byte blocks). No descriptor fetch.
  2. Last Segment at 0x1_5000_0040, length 64 = 4 descriptors; one MRd of 64 B; 4 × 2,048 = 8,192 B matches NLB = 15. For a Write: 1 descriptor MRd + 16 data MRd of 512 B (if each block is 512-aligned).
  3. Last Segment at 0x1_5000_0000, length 32; the last segment's first descriptor is a Segment descriptor — illegal twice over (segment descriptor inside the last segment, and not in the last position). Expect Invalid SGL Segment Descriptor. Valid rewrite: SGL1 = Data Block 0x2_0000_0000 length 4096 directly (if that is all the data), or SGL1 = Last Segment length 16 pointing to a segment holding just the Data Block.

What a senior engineer notices

Input 3 is the shape a buggy segment allocator produces when it inserts a chain descriptor at the wrong index. The fix belongs in the builder's loop bounds, not in a special case.

Failure variants

  • Segment length 40 (not a multiple of 16).
  • Bit Bucket in a Write.
  • Keyed descriptor sent to a PCIe controller.

Extension

Extend walk() to enforce dword alignment when SGLS reports 10b.

Exercises

  1. Encode a Data Block for 512 bytes at 0x2_0000_0123. Is it legal on a controller reporting SGLS 10b?
    Answer

    23 01 00 00 02 00 00 00 00 02 00 00 00 00 00 00. Not legal with 10b: the address is not dword aligned.

  2. How many 4 KiB segment pages, and how many Segment/Last Segment descriptors, are needed for 1,000 Data Blocks?
    Answer

    Each non-last page holds 255 data + 1 chain: 255 + 255 + 255 = 765 in three pages, 235 in a fourth (last). Four segments; SGL1 is a Segment; pages 1 and 2 end with Segment descriptors; page 3 ends with a Last Segment.

  3. Why is a Bit Bucket's Address field reserved?
    Answer

    No memory is accessed; only the byte count matters.

  4. A trace shows SQE byte 39 = 0x00 and Command Dword 0 bits 15:14 = 00b. What is DPTR?
    Answer

    PRPs (PSDT 00b). Byte 39 is then the top byte of PRP2, not an SGL identifier. Always check PSDT first.

  5. When would a 1 MiB read use fewer bus bytes for descriptors with SGLs than PRPs?
    Answer

    When the buffer is contiguous in IOVA space (one Data Block in the SQE) or in a handful of large runs; PRPs always need one entry per page.

Quiz

  1. How large is an SGL descriptor?

    • 8 bytes
    • 12 bytes
    • 16 bytes
    • 64 bytes
    Answer and reasoning

    16 bytes, the same size as the DPTR field, so exactly one descriptor fits in the SQE.

  2. Byte 15 of a descriptor is 0x30. What is it?

    • Data Block
    • Bit Bucket
    • Segment
    • Last Segment
    Answer and reasoning

    Type = upper nibble = 3h = Last Segment; sub type 0h.

  3. Which PSDT value selects PRPs?

    • 00b
    • 01b
    • 10b
    • 11b
    Answer and reasoning

    00b. 01b and 10b select SGLs (differing in how MPTR is interpreted); 11b is reserved.

  4. Where may a Segment descriptor appear?

    • Anywhere in a segment
    • Only as the last descriptor of a non-last segment (or as SGL1)
    • Only in the last segment
    • Only in MPTR
    Answer and reasoning

    Chaining descriptors close a segment; the last segment contains none.

  5. Which SGLS value means "supported, dword alignment required"?

    • 00b
    • 01b
    • 10b
    • 11b
    Answer and reasoning

    10b; 01b means no alignment requirement; 00b not supported.

  6. Which descriptor carries a remote key for RDMA?

    • Transport SGL Data Block
    • Keyed SGL Data Block
    • Bit Bucket
    • Segment
    Answer and reasoning

    Keyed SGL Data Block (type 4h), with a 24-bit length and 32-bit key.

  7. Why can a controller find byte k of a PRP buffer faster than of an SGL buffer?

    Model answer

    PRP entries are fixed-size pages, so page index = (k + offset) / page size; SGL lengths vary, so the controller must sum lengths up to k (or pre-expand the list).

  8. A Write's SGL sums to 6 KiB, NLB = 15 with 512-byte blocks. What do you expect?

    Model answer

    Data SGL Length Invalid (Generic status), likely with DNR set; whether any data moved first is implementation-dependent.

  9. Give two buffers PRPs cannot describe but SGLs can.

    Model answer

    Several sub-page fragments (gaps inside the buffer); a read that discards part of the data (Bit Bucket); scattered metadata; remote keyed memory.

Interview questions

  1. Beginner: What is an SGL descriptor made of?
    Model answer

    16 bytes: an 8-byte address, a 4-byte length (24-bit for Keyed), reserved or key bytes, and an identifier byte with type and sub type.

  2. Beginner: How does a host know it may use SGLs?
    Model answer

    Identify Controller SGLS bits 1:0 non-zero; then it sets PSDT per command.

  3. Intermediate: Explain Segment versus Last Segment.
    Model answer

    Both point to the next segment with its byte length; Last Segment additionally says that segment is the final one and contains no chaining descriptors, letting the controller validate and size the fetch.

  4. Intermediate: Why does Linux not always use SGLs when supported?
    Model answer

    For small or page-aligned I/O, PRPs are cheaper for many controllers; the driver uses a threshold on average segment size.

  5. Advanced: How does NVMe/TCP describe data?
    Model answer

    With SGLs: in-capsule data via a Data Block with an offset sub type; otherwise a Transport SGL Data Block, with data moved in separate PDUs. Exact sub types are in the TCP transport specification.

  6. Senior: A new controller passes all PRP tests and fails intermittently with SGLs on unaligned buffers. Where do you look?
    Model answer

    Whether it reports SGLS 10b and the driver ignored it; byte-enable handling for partial first/last DWs; Data Blocks crossing 4 KiB boundaries at odd addresses; analyzer captures of the edge TLPs; comparing data at fragment edges.

Teach-back challenge

  • Child: stickers that say where, how many and what kind.
  • Junior: decode a 16-byte descriptor from hex and walk a two-segment SGL.
  • Senior: argue PRP vs SGL for a specific workload, with IOMMU behavior and controller cost.
Model explanation (senior)

"For 4 KiB random reads PRPs are optimal: one entry, no fetch. For large sequential I/O with a contiguous IOVA, one SGL Data Block beats a PRP list. For fragmented, unaligned buffers SGLs are the only option short of bounce buffers. Measure the specific controller, because its SGL engine may add per-command latency."

Chapter summary

  • SGLs describe data with 16-byte descriptors carrying address, length and type.
  • Types: Data Block, Bit Bucket, Segment, Last Segment, Keyed Data Block, Transport Data Block, Vendor Specific.
  • SGL1 sits in the SQE; segments chain through a final Segment/Last Segment descriptor.
  • SGLS in Identify Controller advertises support and alignment; PSDT selects PRPs or SGLs per command.
  • On PCIe, SGLs are optional and for I/O; on fabrics they are required.
  • SGLs trade random-access simplicity for flexibility; neither is universally faster.

Do not move on until you can:

  • decode any 16-byte descriptor from hex by hand
  • build a chained SGL with correct Segment/Last Segment placement
  • read SGLS and set PSDT correctly
  • predict segment fetches and data TLPs for an SGL command
  • name the SGL error statuses and what causes each
  • compare PRP and SGL for a given buffer and justify the choice
