With Revision 2.0, Non-Volatile Memory Express (NVMe) stopped being one ever-growing document and became a family: a Base Specification, a set of I/O command set specifications, a set of transport specifications, and separate management and boot specifications. This chapter explains that structure, why it exists, what lives in each document in the August 2026 NVMe 2.4 set, and how the architecture it describes (the NVM subsystem, its controllers and namespaces, and command sets) fits together.

Why this chapter exists

Every investigation eventually reaches the sentence "let us check the specification". In the NVMe 2.x world that sentence is ambiguous: which specification? A question about the Read command's Force Unit Access bit lives in the NVM Command Set specification. A question about why the host wrote BAR0 + 1008h lives in the NVMe over PCIe Transport specification. A question about Get Log Page lives in the Base Specification. A question about a Baseboard Management Controller polling drive temperature over SMBus lives in the NVMe Management Interface specification. Engineers who do not know the map waste hours searching the wrong document, or worse, cite a 1.4-era section that no longer exists in that form.

The structure is also an architecture lesson. The documents were split along the same lines the protocol is layered: core semantics, vocabulary per kind of storage, and carriage per kind of interconnect. Understanding why the split happened teaches you which behaviours are universal and which depend on the transport or the command set.

Learning objectives

  • Name every document in the NVMe 2.4 specification set and its current revision, and say what each one defines.

  • Recognise a command-set mismatch in a synthetic trace.

The story

A family loved a board game so much that they kept writing new rules into the back of the rulebook: rules for a new kind of dice, rules for playing outside, rules for playing over video call. After ten years the rulebook was so thick that nobody could find anything, and the rules for video calls kept accidentally changing the rules for the dice.

So they split it. One core rulebook says how turns work, what the board is and who the players are. Each expansion box (the "zones" expansion, the "key and treasure" expansion) has its own small booklet of extra moves. Each way of playing (around the table, over the phone, over video) has its own short booklet about how moves are passed between players. A separate caretaker's guide explains how a grown-up checks that the game pieces are all there without interrupting the game, and a setup card explains how to start the game when the box is in another house.

That is NVMe 2.x: the core is the Base Specification, the expansions are command sets, the ways of playing are transports, the caretaker's guide is NVMe-MI, and the setup card is NVMe Boot.

A software engineer's version: NVMe 1.x was a monolith; NVMe 2.x is a core library with plug-in modules behind stable interfaces. The core defines the object model and the admin API. Command-set modules register their vocabularies under a Command Set Identifier. Transport modules implement the "deliver this command and return this completion" interface for a particular interconnect. Management and boot are separate services that consume the core API.

  • The modules are not independent in practice. A command set specification constantly refers back to the Base Specification (for status codes, Identify, log pages). You cannot read the NVM Command Set alone.
  • Transports are not pure carriers. The PCIe transport defines things that look like core features (the register memory map, doorbells, PRPs, interrupts). The "plug-in" analogy hides how much of the everyday experience of NVMe on a server lives in the transport document.
  • Revisions do not move in lock-step forever. The 2026 release revised all eleven documents together, but command set and transport specifications have their own revision numbers (NVM Command Set 1.3, PCIe Transport 1.4) and have been released on their own schedule in the past.
  • A device does not "install" modules. A controller supports a fixed set of command sets and one transport per port, decided by its design and firmware.

Beginner explanation

NVMe began in 2011 as a single specification describing how a computer talks to a PCI Express (PCIe) solid-state drive (SSD). Over the next decade it grew: more commands, more features, a way to run NVMe across networks (NVMe over Fabrics), a way to manage drives from a server's management controller (NVMe Management Interface), and new kinds of storage that are not simple numbered blocks (zoned storage, key-value storage).

Putting all of that into one document made it hard to read, hard to change safely, and hard to implement only the parts a product needed. In 2021 NVM Express, Inc. released NVMe 2.0, which reorganised everything into separate documents:

  • One Base Specification for what every NVMe device has in common.
  • Command set specifications, one per kind of storage (ordinary blocks, zones, key-value, and newer ones).
  • Transport specifications, one per kind of connection (PCIe, RDMA networks, TCP networks).
  • A management specification for monitoring and managing drives, including from outside the operating system.
  • A boot specification for starting an operating system from NVMe storage reached over a network.

A drive in your laptop uses the Base Specification, the NVM Command Set specification and the PCIe Transport specification. A drive in a cloud server might additionally use the management specification. A storage array reached over Ethernet uses the Base Specification, a command set specification and the TCP Transport specification, and never touches PCIe transport rules at the host.

Engineering explanation

Before 2.0: the 1.x era

Through the 1.x revisions (1.0 in 2011 through 1.4 in 2019, with lettered updates such as 1.4a–1.4c), the "NVM Express" specification was a single document that contained:

  • the PCIe register map and doorbells,
  • the admin command set,
  • the NVM command set (Read, Write, Flush, Dataset Management…),
  • PRP and SGL data pointers,
  • interrupts, initialisation, reset and shutdown,
  • features such as namespaces, reservations, power management, directives, NVM sets, endurance groups, Asymmetric Namespace Access (ANA).

Alongside it lived the separate NVMe over Fabrics specification (1.0 in 2016, 1.1 in 2019) and the NVMe Management Interface specification (NVMe-MI, 1.0 in 2015). Fabrics had to restate or override parts of the base document because the base assumed memory-mapped registers and PCIe.

Version-dependent Years given here are for orientation; the authoritative dates are on each document's title page and in the revision history at nvmexpress.org.

What the Base Specification owns

The Base Specification is the spine. Anything that is true for every NVMe controller regardless of command set or transport belongs here:

  • Architecture and theory of operation: NVM subsystem, controllers, namespaces, ports, hosts; domains and divisions; endurance groups and NVM sets; Asymmetric Namespace Access; Exported NVM Subsystems (2.4).
  • Controller properties (CAP, VS, CC, CSTS, AQA, ASQ, ACQ and others) and the initialisation, shutdown and reset rules that use them. How properties are accessed depends on the transport: memory-mapped on PCIe, Property Get/Set commands on fabrics.
  • Queueing model: submission and completion queues, head and tail, phase tag, arbitration.
  • Submission and completion entry formats, status code types and generic status codes.
  • The Admin Command Set: Identify, Get Log Page, Set/Get Features, Create/Delete I/O SQ and CQ, Abort, Asynchronous Event Request, Namespace Management and Attachment, Firmware Image Download and Commit, Format NVM, Sanitize, Security Send/Receive, Device Self-test, Directive Send/Receive, Virtualization Management, Keep Alive, NVMe-MI Send/Receive, and more.
  • I/O commands common to all I/O command sets: for example the reservation commands, so that every command set shares one reservation model. Uncertain Exactly which common I/O commands (Flush, Cancel, I/O Management) are defined in the Base Specification rather than per command set should be checked in the Base Specification's I/O commands clause for the revision you use.
  • Fabrics: capsules, the Connect command, discovery, authentication — the material that was a separate NVMe-oF document in 1.x.
  • Security, logs, features, power management, telemetry and the 2026 additions (post-quantum-ready key exchange, rate limiting, voltage monitoring, manufacturing reset, lockdown improvements). See 2026 NVMe 2.4 Updates.

I/O command sets

An I/O command set defines what an I/O namespace is and which commands act on it. Each namespace is associated with exactly one I/O command set, named by its CSI. The CSI values that are well established are:

NVM Command Set

The classic block-storage vocabulary: Flush (00h), Write (01h), Read (02h), Write Uncorrectable (04h), Compare (05h), Write Zeroes (08h), Dataset Management (09h), Verify (0Ch), Copy (19h). It defines LBA formats (data size and metadata size per logical block), end-to-end data protection (protection information), and NVM-specific Identify data. Almost every Linux block device /dev/nvmeXnY you have used is an NVM Command Set namespace. Chapters NVM Command Set through Dataset Management cover it.

Zoned Namespace (ZNS) Command Set

ZNS divides a namespace into zones that must be written sequentially from a write pointer and reset as a whole. It reuses NVM Command Set reads and writes and adds Zone Management Send (79h), Zone Management Receive (7Ah) and Zone Append (7Dh). It moves part of the data-placement responsibility to the host, reducing device-side garbage collection and over-provisioning. See ZNS.

Key Value (KV) Command Set

KV namespaces store values addressed by keys instead of LBAs. Commands store, retrieve, delete, list keys and test whether a key exists. It removes the host-side key-to-block mapping for workloads that are naturally key-value. See Key Value.

Subsystem Local Memory (SLM) Command Set

SLM defines memory namespaces: byte-addressable memory inside the NVM subsystem that can be read, written and copied to and from other namespaces. It exists mainly to give computational programs a place to stage data. See Subsystem Local Memory.

Computational Programs Command Set

Computational Programs defines compute namespaces that hold programs, and commands to load, activate and execute those programs on data staged in subsystem local memory, so data can be processed near storage instead of being moved to the host. See Computational Programs.

Transports

The NVMe 2.x Base Specification describes two transport models:

  • Memory-based transport (PCIe): commands, completions and data are transferred through shared memory; the host signals through memory-mapped doorbells; controller properties are memory-mapped registers.
  • Message-based transport (RDMA, TCP; also Fibre Channel via FC-NVMe): commands and responses are carried as capsules; properties are accessed with Property Get/Set; a Connect command creates the association and each queue; discovery controllers advertise subsystems.

The transport specification fills in the concrete details. For this course the PCIe Transport specification is central. It defines the register offsets you will meet in NVMe Registers, the doorbell formula, Physical Region Page (PRP) rules, interrupt modes, the Controller Memory Buffer (CMB) and Persistent Memory Region (PMR), and how PCIe resets and errors interact with the controller.

NVMe Management Interface (NVMe-MI)

NVMe-MI lets a management controller — typically a server's Baseboard Management Controller (BMC) — inventory, monitor and configure NVMe devices out of band, without involving the host operating system. Messages use the Management Component Transport Protocol (MCTP) over SMBus/I2C or over PCIe vendor-defined messages. NVMe-MI also defines an in-band path, where the host tunnels the same management commands through the admin queue using the NVMe-MI Send (1Dh) and NVMe-MI Receive (1Eh) admin commands, and it covers enclosure management. See NVMe-MI.

NVMe-MI traffic over PCIe appears as vendor-defined message TLPs, not as memory reads and writes to queues. If your analyzer shows Message TLPs to an SSD during idle periods, a BMC may be polling it. That is not the host driver, and it is not NVMe I/O.

NVMe Boot

Booting from a local PCIe NVMe SSD is handled by platform firmware (UEFI NVMe drivers) and is long solved. The hard case is booting from NVMe over Fabrics, especially NVMe/TCP: the pre-OS environment must discover and connect to a remote subsystem, and then hand the connection details to the operating system so it can reconnect. The NVMe Boot specification defines that flow, including the NVMe Boot Firmware Table (NBFT), an ACPI table that carries the connection information from firmware to the OS. See NVMe Boot.

The 2.x architecture: NVM subsystem, controllers, namespaces

The architecture described by the Base Specification is the same object model you met in What Is NVMe?, refined for a world of multiple command sets and transports.

NVM subsystem

An NVM subsystem is one or more controllers, zero or more namespaces, and one or more ports, plus the non-volatile storage media and an interface between controllers and media. It is named by an NVM Subsystem NVMe Qualified Name (SUBNQN). In 2.x it can additionally be organised into domains (independently failing or power-managed portions) and, in 2.4, can expose Exported NVM Subsystems — virtual NVM subsystems presented from within a physical one, used for virtual machines and live migration. Endurance groups and NVM sets (introduced in 1.4) describe how media is partitioned for wear and performance isolation.

On PCIe the class code programming interface also distinguishes I/O controllers (02h) from administrative controllers Uncertain (confirm the administrative controller's programming interface value in the PCIe Transport specification).

Namespaces and command sets

A namespace is a formatted quantity of non-volatile memory associated with exactly one I/O command set. The host learns the association from Identify data. NSIDs are subsystem-wide. Namespaces are created (Namespace Management), attached to controllers (Namespace Attachment), and may be private to one controller or shared by several. Under the 2.x model, Identify gained command-set-specific variants: one structure common to all command sets and another specific to the namespace's command set.

How a host discovers command sets

  1. Read CAP.CSS (Command Sets Supported). One bit says the NVM Command Set is supported; another says one or more I/O command sets are supported and are discoverable through Identify; another says only the Admin Command Set is supported (no I/O).
  2. Choose CC.CSS before enabling: 000b selects the NVM Command Set (the 1.x-compatible choice), 110b selects "all supported I/O command sets", 111b selects "Admin Command Set only".
  3. After enable, read the I/O Command Set data structure with Identify (CNS 1Ch), which lists combinations of command sets the controller supports, and select one with the I/O Command Set Profile feature.
  4. For each namespace, read the common Identify Namespace data and the command-set-specific Identify Namespace data selected by CSI, and learn which CSI the namespace uses (for example from the Namespace Identification Descriptor list, which includes a CSI descriptor).
  5. Read the Commands Supported and Effects log page to learn which opcodes the controller supports for each command set and what side effects they have.

Uncertain The CNS values for command-set-specific Identify structures, the feature identifier for I/O Command Set Profile, and the exact descriptor types should be confirmed in the Base Specification 2.4 Identify and Set Features clauses before you put them into a decoder. CNS 1Ch for the I/O Command Set data structure is widely used by Linux and nvme-cli.

How the family evolves: revisions, TPs and ECNs

  • Technical changes are developed as Technical Proposals (TPs) inside NVM Express working groups. A ratified TP is binding as an addition even before it is folded into the next revision of the document.
  • Engineering Change Notices (ECNs) make smaller corrections.
  • A new revision incorporates ratified TPs and ECNs. The Revision Changes document lists them; for the 2026 set it is "NVM Express Revision Changes 2026.07.30".
  • The controller's Version (VS) register reports the Base Specification revision the controller claims (major, minor, tertiary). There is no equivalent register for command set or transport revisions; a host infers support from capability bits, Identify fields and log pages.

A device reporting VS = 2.0 is not "out of date" or broken in a 2026 system. It conforms to the revision it claims. Hosts must check capability bits rather than assume that every feature in Base 2.4 is present.

The teaching ladder for the 2.x family

One core rulebook plus expansion booklets, ways-of-playing booklets, a caretaker's guide and a setup card.

The NVMe 2.x family is a Base Specification plus I/O command set specifications, transport specifications, NVMe-MI and NVMe Boot, each revised separately and cross-referencing the Base.

A PCIe SSD controller implements Base behaviour (queues, admin commands, properties), at least one I/O command set (usually NVM) in firmware, the PCIe transport in its front end and DMA engines, and often an NVMe-MI endpoint on SMBus for the BMC.

CAP.CSS and CC.CSS select command sets; Identify (common and CSI-specific) and the Commands Supported and Effects log describe them; VS reports the Base revision; the transport specification defines register mapping and doorbells.

On the wire, command sets change only the meaning of opcodes and command dwords inside the same 64-byte SQE; transports change how SQEs and CQEs travel (DMA from host memory vs capsules).

In a trace, you identify the command set from the namespace's CSI (seen in Identify data during initialisation) and decode subsequent I/O SQEs with that vocabulary.

When a command fails with Invalid Command Opcode or Invalid Field in Command, a senior engineer checks whether the command belongs to the namespace's command set and whether the controller enabled that command set (CC.CSS, I/O Command Set Profile).

The sixteen questions, answered for the modular specification family

1. What is it?
The organisation of NVMe into a Base Specification plus command set, transport, management and boot specifications.
2. Why was it created?
The monolithic 1.x specification could not cleanly absorb new storage models and transports.
3. What problem does it solve?
It separates universal semantics from storage-model vocabulary and from interconnect carriage, so each can evolve without breaking the others.
4. What existed before it?
One NVM Express specification (1.0–1.4c) plus separate NVMe-oF and NVMe-MI documents.
5. Why is the current design better?
Clear ownership of each feature, command-set-neutral core, fabrics folded into the base, implementers read only what they need.
6. Who creates it?
NVM Express, Inc. working groups, through TPs and ECNs ratified by members.
7. Who consumes it?
Controller and firmware designers, driver writers, validation engineers, analyzer and tool vendors, and you.
8. Where does it live?
As documents at nvmexpress.org; in a device, as the set of features its controller implements and advertises.
9. What memory/registers are involved?
VS (Base revision claimed), CAP.CSS and CC.CSS (command sets), Identify data and the Commands Supported and Effects log.
10. What happens before it?
Standards work: TPs drafted, reviewed, ratified.
11. What happens after it?
Devices and drivers adopt features; compliance test suites are updated; analyzers add decoders.
12. What happens if it is wrong?
If you consult the wrong document or revision, you will mis-decode fields, chase non-bugs, or miss real ones.
13. What does the protocol analyzer show?
Nothing directly; the analyzer shows commands whose decoding depends on knowing the command set and revision.
14. What does Linux show?
VS (nvme id-ctrl "ver"), CSI per namespace, zoned devices in /sys/block/*/queue/zoned, effects via the command effects log.
15. What would a validation engineer test?
That the device behaves per each document and revision it claims; that it rejects commands from command sets it did not enable; that CC.CSS combinations behave correctly.
16. What would a senior engineer suspect when it fails?
A revision mismatch between host assumptions and device claims, a command-set mismatch, or a transport-specific behaviour wrongly assumed to be universal.

Hardware view

The document split is a paper construct; silicon is not split the same way. Still, it is useful to map the blocks of a real PCIe SSD to the documents that govern them, because that tells you which document to open when a block misbehaves.

Command sets are almost entirely a firmware matter. Supporting ZNS or KV on an existing controller ASIC is usually a firmware project; supporting a new PCIe generation is a silicon project. That asymmetry is one reason the documents evolve at different speeds.

Specification view

This chapter's sources are the documents themselves, as listed on the NVM Express specifications page (checked 2026-10-04): NVM Express Base Specification, Revision 2.4, the five I/O command set specifications, the three transport specifications, NVM Express Management Interface Specification, Revision 2.2 and NVMe Boot Specification, Revision 1.4, plus NVM Express Revision Changes 2026.07.30.

Each document states its own scope and normative references in its introduction. Read those first: they tell you which other documents a requirement depends on. Normative content uses "shall/should/may"; theory-of-operation chapters and examples are informative.

  • The NVMe 2.4 set (released 4 August 2026) consists of eleven documents: Base 2.4, NVM Command Set 1.3, ZNS 1.5, KV 1.4, SLM 1.3, Computational Programs 1.3, PCIe Transport 1.4, RDMA Transport 1.3, TCP Transport 1.3, NVMe-MI 2.2, NVMe Boot 1.4.
  • NVMe 2.0 (2021) introduced the split into Base, command set and transport specifications and merged NVMe over Fabrics content into the Base Specification.
  • The Admin Command Set is defined in the Base Specification.
  • CSI 00h is the NVM Command Set, 01h Key Value, 02h Zoned Namespace.
  • The 2.x architecture defines I/O, administrative and discovery controllers.
  • Because opcodes are reused across command sets, the meaning of an I/O SQE cannot be determined from the SQE alone; it depends on the namespace's CSI. This follows from the per-command-set opcode tables.
  • Since VS reports only the Base revision, a host's knowledge of a device's command set and transport revision is indirect (capability bits, Identify, logs).
  • Which command sets a controller supports, and which combinations it offers (I/O Command Set Profiles).
  • Whether a device has an NVMe-MI endpoint and on which physical interface.
  • Which optional Base features (namespace management, ANA, directives, telemetry, 2.4 features) it implements.
  • Document set membership changed after 2.0 (SLM, Computational Programs and Boot added later).
  • Every document's revision number is independent; NVM Command Set 1.3 is current with Base 2.4.
  • Features attributed to "NVMe 2.4" in press coverage (Exported NVM Subsystem migration, rate limiting, voltage monitoring, manufacturing reset, post-quantum-ready key exchange) are defined in the 2.4-era documents; their field-level details must be read there, not inferred from summaries.
  • The specifications do not require a device to support more than the NVM Command Set (or any I/O command set, for administrative and discovery controllers).
  • They do not define how a host chooses among transports.
  • They do not include the FC-NVMe transport binding (INCITS T11).

Check in the specification: the Base 2.4 table of Command Set Identifiers (for SLM and Computational Programs values); the exact CNS values for command-set-specific Identify structures; the I/O Command Set Profile feature identifier; which common I/O commands moved into the Base Specification.

  • Never cite a 1.4 section number for a 2.x question; structure and numbering changed completely.
  • Never assume ZNS commands work on an NVM namespace or vice versa.
  • Never assume a VS of 2.x implies support for any particular optional feature.

Walking the reasoning

  1. PCIe is clean: every TLP succeeded. The device fetched the command, so doorbell, addressing and DMA are fine.
  2. No data was read from host memory even though the command had a data pointer: the controller rejected the command before execution.
  3. DW3 = 0x8003_0050 → bits 31:17 = 0x4001 → SC = 01h, SCT = 0 (generic), DNR = 1; CID 0x0050 matches the SQE in row 3.
  4. Opcode 7Dh is Zone Append in the ZNS Command Set. NSID 1's CSI is 00h (NVM), whose opcode table does not define 7Dh. "Invalid Command Opcode" is exactly what the controller should report.
  5. Root cause: host-side configuration (tool aimed at the wrong namespace). Corrective action: the tool should read the namespace's CSI (or check /sys/block/nvme0n1/queue/zoned) before issuing zone commands. Regression test: run the tool against an NVM namespace and assert it refuses to start.

An analyzer configured to decode every I/O SQE with the NVM Command Set table would label row 3 as an unknown opcode. One configured with "ZNS" for all namespaces would label it "Zone Append" and might lead you to suspect a firmware ZNS bug. The truth needs both pieces: the opcode and the namespace's CSI, learned from initialisation traffic or from Linux.

Code / pseudocode

This program decodes the VS register and the CAP.CSS field and answers "which document defines this?" for a handful of terms. It is executable with Python 3 and the standard library. The register values are the synthetic Lab SSD's (see NVMe Registers for the full dump).

"""Decode VS and CAP.CSS, and route terms to the right NVMe document.
Synthetic example for teaching."""

SPEC_SET_2026 = {
    "Base": "NVM Express Base Specification 2.4",
    "NVM": "NVM Command Set Specification 1.3",
    "ZNS": "Zoned Namespace Command Set Specification 1.5",
    "KV": "Key Value Command Set Specification 1.4",
    "SLM": "Subsystem Local Memory Command Set Specification 1.3",
    "CP": "Computational Programs Command Set Specification 1.3",
    "PCIe": "NVMe over PCIe Transport Specification 1.4",
    "RDMA": "NVMe over RDMA Transport Specification 1.3",
    "TCP": "NVMe over TCP Transport Specification 1.3",
    "MI": "NVM Express Management Interface Specification 2.2",
    "Boot": "NVMe Boot Specification 1.4",
}

WHERE = {
    "Identify": "Base", "Get Log Page": "Base", "CC.EN": "Base",
    "doorbell stride": "PCIe", "PRP list": "PCIe", "MSI-X use": "PCIe",
    "Read (opcode 02h, I/O)": "NVM", "Dataset Management": "NVM",
    "Zone Append": "ZNS", "Store / Retrieve": "KV",
    "Connect command": "Base", "TCP PDU header": "TCP",
    "SMBus out-of-band health poll": "MI", "NBFT table": "Boot",
}

def decode_vs(vs):
    return (vs >> 16) & 0xFFFF, (vs >> 8) & 0xFF, vs & 0xFF

def decode_cap_css(cap):
    css = (cap >> 37) & 0xFF          # CAP bits 44:37
    return {
        "NVM command set (bit 37)": bool(css & 0x01),
        "I/O command sets via Identify (bit 43)": bool(css & 0x40),
        "No I/O command set, admin only (bit 44)": bool(css & 0x80),
    }

if __name__ == "__main__":
    vs = 0x0002_0000
    cap = 0x0040_0830_1401_0FFF
    print("VS  -> %d.%d.%d" % decode_vs(vs))
    for k, v in decode_cap_css(cap).items():
        print(f"CAP.CSS {k}: {v}")
    for term, doc in WHERE.items():
        print(f"{term:32s} -> {SPEC_SET_2026[doc]}")

Expected output: VS decodes to 2.0.0; CAP.CSS reports the NVM command set and "I/O command sets via Identify" as supported and "admin only" as not; each term is routed to its document.

Worked example

Problem. A bug report reads: "On firmware 3.1 the SSD returns Invalid Field in Command for Copy commands with 16 source ranges. The NVMe spec says up to 128 ranges are allowed. Also, BAR0 + 1008h writes are sometimes ignored, and the BMC cannot read the composite temperature." Which documents do you open, and for what?

  1. Copy with 16 ranges. Copy is an NVM Command Set I/O command (opcode 19h). Its limits are reported by the device (in NVM-specific Identify Namespace/Controller fields such as the maximum number of source ranges), not fixed by the specification. Open the NVM Command Set Specification 1.3, Copy command and the Identify fields it references. The claim "the spec says up to 128" must be checked: the specification bounds the field; the device declares its own limit. If the device declares fewer than 16, Invalid Field in Command is correct behaviour.
  2. BAR0 + 1008h writes ignored. With CAP.DSTRD = 0, 1008h is the SQ1 tail doorbell. Doorbell layout is in the PCIe Transport Specification 1.4; the queue semantics (for example, what the controller does with an invalid tail value) are in the Base Specification. Then capture a PCIe trace to prove whether the write reached the device.
  3. BMC cannot read temperature. That is out-of-band management: NVMe-MI 2.2 (and the platform's MCTP/SMBus configuration). The in-band SMART / Health log the host reads is in the Base Specification; comparing both tells you whether the problem is the sensor or the management path.

One bug report, three issues, four documents, three teams. Splitting the report along document boundaries is often the fastest way to get each part to the right owner.

Common mistakes

Mistakes about the NVMe 2.x family
MistakeCorrection
"NVMe 2.0 is a faster NVMe."2.0 was primarily a restructuring of the documents, plus new features (ZNS and KV as command sets, rotational media support, and more). It did not change the wire speed, which PCIe determines.
"The register map is in the Base Specification."Property definitions are in the Base; the memory-mapped offsets and doorbells are in the PCIe Transport specification. Check both.
"There is an Admin Command Set specification."Admin commands are defined in the Base Specification.
"ZNS is a different protocol."ZNS is an I/O command set within NVMe, using the same queues, controllers and transports.
"VS 2.4 means the device supports rate limiting."VS reports the claimed Base revision; optional features must be discovered.
"NVMe-MI traffic goes through the I/O queues."Out-of-band NVMe-MI uses MCTP over SMBus/I2C or PCIe VDMs; only the in-band tunnel uses the admin queue.
"NVMe/FC is in the NVMe transport set."FC-NVMe is an INCITS T11 standard.

Debugging connection

When an NVMe-level failure appears, classify it by document before you analyse it:

  • Generic status (SCT 0) on an I/O command such as Invalid Command Opcode or Invalid Field in Command: check that the command belongs to the namespace's command set and that the fields respect device-reported limits (command set specification + Identify).
  • Command-specific status (SCT 1): the meaning is defined by the command's own clause; for admin commands that is the Base Specification, for I/O commands the command set specification.
  • Controller never ready, fatal status, odd register values: Base Specification (properties, initialisation) plus PCIe Transport (mapping, PCIe resets).
  • Interrupt, doorbell or PRP problems: PCIe Transport first.
  • Management path problems: NVMe-MI.
  • Fabrics boot problems: NVMe Boot, then the fabrics transport.

A useful first question on any interoperability bug: "Which revision does the device claim (VS), which revision does the host driver implement, and which document defines the failing behaviour?" Revision mismatches cause a large share of interoperability bugs: a host using a field that was reserved in the device's revision, or a device enforcing a rule the host's revision did not have.

Senior engineer insight

Seniors keep a personal "where is it defined" index for the dozen fields they use most, with document and revision, because the same feature can move between documents across revisions. They also read the Revision Changes document for every new set before reading the specifications themselves: it is the cheapest way to learn what moved, what was added, and which TPs were incorporated.

Seniors are also careful with the word "spec" in conversation. "The spec says" is replaced by "Base 2.4, Identify clause, says" or "the NVM Command Set 1.3 Copy command description says". That precision ends arguments quickly, and it exposes claims that came from a vendor datasheet or a blog post rather than from the normative text.

Finally, they remember that architecture moved faster than many hosts. Domains, Exported NVM Subsystems and controller types exist in the specification; a given Linux kernel, hypervisor or analyzer may not yet decode or use them. Part of the job is knowing where your tools' knowledge ends.

What a senior engineer notices

  • Whether Linux chose CC.CSS = 110b (it does so when CAP indicates I/O command set support), which changes the Identify sequence seen in traces.
  • Whether the device claims a Base revision older than features it appears to support (sometimes vendors implement ratified TPs before claiming the revision).

Failure variants

  • nvme id-iocs fails with Invalid Field: the controller does not support CNS 1Ch (likely a 1.4-era device) — expected, not a bug.
  • show-regs fails: the kernel may restrict BAR access; use id-ctrl instead.

Quiz

  1. Where is the Admin Command Set defined in the NVMe 2.x family?

    • In its own Admin Command Set Specification
    • In the NVM Express Base Specification
    • In the NVM Command Set Specification
    • In the PCIe Transport Specification
    Answer and reasoning

    Admin commands are universal to controllers, so they are part of the Base Specification.

  2. Which revision of the NVM Command Set Specification is current in the August 2026 set?

    • 2.4
    • 1.0
    • 1.3
    • 1.5
    Answer and reasoning

    NVM Command Set 1.3. Command set revisions are numbered independently of the Base (2.4). ZNS is 1.5.

  3. CSI 02h identifies:

    • Zoned Namespace Command Set
    • Key Value Command Set
    • NVM Command Set
    • Admin Command Set
    Answer and reasoning

    00h NVM, 01h KV, 02h ZNS.

  4. Which controller type has no I/O queues and exists to advertise subsystems on a fabric?

    • I/O controller
    • Administrative controller
    • Virtual controller
    • Discovery controller
    Answer and reasoning

    Discovery controllers return the Discovery Log Page. Administrative controllers also lack I/O queues but manage the subsystem.

  5. What does the VS register tell you, and what does it not?

    Model answer

    It tells you the Base Specification revision the controller claims (major.minor.tertiary). It does not tell you command set or transport revisions, nor which optional features are implemented.

  6. Which document defines NVMe out-of-band management over SMBus?

    • Base Specification
    • NVMe Management Interface Specification
    • NVMe Boot Specification
    • PCIe Transport Specification
    Answer and reasoning

    NVMe-MI (2.2 in the current set), using MCTP.

  7. Give two reasons NVMe was modularised at 2.0.

    Model answer

    To accommodate new storage models (zoned, key-value) without special-casing a block-centric core; to separate transport-specific (PCIe) material from universal semantics so fabrics fit naturally; also independent evolution and smaller, focused documents.

  8. A Zone Append to an NVM namespace returns which generic status, and why is it correct?

    Model answer

    Invalid Command Opcode (SCT 0, SC 01h): the NVM Command Set does not define opcode 7Dh, so for that namespace the opcode is invalid.

  9. True or false: the NVMe over Fibre Channel binding is one of the NVM Express transport specifications.

    Answer

    False. FC-NVMe is defined by INCITS T11.

  10. Which CC.CSS value selects "all supported I/O command sets"?

    • 000b
    • 001b
    • 110b
    • 111b
    Answer and reasoning

    110b. 000b is the NVM Command Set; 111b is Admin Command Set only.

Interview questions

  1. Beginner: What changed in NVMe 2.0?

    Model answer

    The specification was restructured into a Base Specification, separate I/O command set specifications (NVM, ZNS, KV at the time), and separate transport specifications (PCIe, RDMA, TCP); fabrics content merged into the Base. New features arrived too, such as ZNS and KV as command sets and support for rotational media.

  2. Beginner: What is an I/O command set?

    Model answer

    A vocabulary of I/O commands and a namespace model; each namespace uses exactly one, identified by its CSI.

  3. Intermediate: How does a host learn which command set a namespace uses?

    Model answer

    After enabling with an appropriate CC.CSS, it reads Identify structures — the I/O Command Set data structure for supported combinations and the namespace identification descriptors (which include CSI) — and then the CSI-specific Identify Namespace. The Commands Supported and Effects log shows supported opcodes per command set.

  4. Advanced: Why are controller properties defined in the Base Specification but mapped in the PCIe Transport Specification?

    Model answer

    Properties are universal (every controller has CAP, CC, CSTS), but how they are accessed differs: memory-mapped registers in BAR0 for PCIe, Property Get/Set capsules for fabrics. Defining semantics in the Base and mapping in the transport keeps one meaning with several access methods.

  5. Senior: You are writing an NVMe trace decoder. How does the 2.x structure affect its design?

    Model answer

    Decoding must be layered and stateful: a transport layer (PCIe TLPs → doorbells, SQE/CQE/data by address), a Base layer (SQE/CQE common fields, admin commands, status), and pluggable command-set decoders chosen per namespace from CSI learned during initialisation (or configured). It must also be revision-aware, treating fields as reserved or defined according to the VS the device reports, and must mark anything it cannot attribute as unknown rather than guessing.

  6. Senior: A customer insists their device is non-compliant because it lacks a 2.4 feature. How do you respond?

    Model answer

    Check what the device claims (VS) and whether the feature is mandatory or optional in that revision. If the device claims an older revision, or the feature is optional, absence is compliant. If it claims 2.4 and the feature is mandatory for that claim, gather evidence (capability bits, Identify, test results) and escalate. Cite the document and clause name, and the Revision Changes entry.

Model explanation for a junior engineer

"Think of NVMe as one core book and many add-on books. The Base Specification 2.4 is the core: architecture, admin commands, queues, properties, status, fabrics behaviour. Chapter summary

  • NVMe 2.0 (2021) split the monolithic specification into a Base Specification, I/O command set specifications and transport specifications, merging fabrics content into the Base; NVMe-MI and NVMe Boot sit alongside.
  • The August 2026 set: Base 2.4; NVM 1.3, ZNS 1.5, KV 1.4, SLM 1.3, Computational Programs 1.3; PCIe 1.4, RDMA 1.3, TCP 1.3; NVMe-MI 2.2; Boot 1.4.
  • The Admin Command Set lives in the Base Specification.
  • The architecture: NVM subsystem (controllers, namespaces, ports; domains; Exported NVM Subsystems in 2.4), controllers of three types (I/O, administrative, discovery), namespaces each tied to one command set by CSI.
  • Hosts discover command sets through CAP.CSS, CC.CSS, Identify and the Commands Supported and Effects log.
  • VS reports only the claimed Base revision; features must be discovered.
