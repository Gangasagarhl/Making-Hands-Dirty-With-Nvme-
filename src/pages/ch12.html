Every PCI Express (PCIe) request is either posted (sent and forgotten) or non-posted (sent and answered). This one distinction explains why NVMe doorbells are cheap, why NVMe WRITE commands need many reads in flight, why the CPU never reads device registers on the fast path, and what happens when an answer never comes back.

Why this chapter exists

In Chapter 10 you met the Transaction Layer Packet (TLP) kinds and in Chapter 11 their headers. Both mentioned, in passing, that some requests get completions and some do not. That passing remark is one of the most consequential design decisions in PCIe, and it shapes NVM Express (NVMe) at every level:

  • Performance: a posted write costs bandwidth only; a non-posted read costs bandwidth and a round trip of latency.
  • Correctness: a posted write gives the sender no confirmation; you cannot know it has landed without some other mechanism.
  • Error handling: a non-posted request that is never answered becomes a Completion Timeout, one of the most common and most misunderstood PCIe errors in storage systems.
  • Deadlock freedom: the three traffic classes (posted, non-posted, completion) are buffered and credited separately so that one can never block another into a cycle.

Learning objectives

  • Define posted and non-posted requests and classify every TLP kind: MWr, Msg/MsgD (posted); MRd, CfgRd, CfgWr, IORd, IOWr, AtomicOps (non-posted); Cpl/CplD (completions).
  • Explain why memory writes are posted but configuration and I/O writes are not.
  • Map every TLP of an NVMe READ and WRITE to posted/non-posted and explain the performance consequences.
  • Use Little's Law to compute how many outstanding reads a device needs to sustain a target bandwidth.
  • Explain the Completion Timeout mechanism, its configuration in Device Control 2, and what the requester and the CPU see when it fires.
  • Explain how software "flushes" posted writes, and why the NVMe driver rarely needs to.
  • Diagnose a missing completion in a synthetic trace.

The story

There are two ways to talk to the librarian across town.

Sending a postcard. You write "New request slips are in box 5!" on a postcard and drop it in the mailbox. You do not wait. You go back to your work right away. You never get a reply to a postcard — you trust the mail.

Asking a question. You call the librarian and ask, "What does slip number 4 say?" Now you must wait on the phone until the librarian reads it and answers. If the librarian never answers, you cannot wait forever: after a while you hang up and say "something is wrong".

PCIe works the same way. Memory writes are postcards: the doorbell is a postcard. Memory reads are questions: when the SSD wants to read a request slip from the computer's memory, it asks and waits for the answer.

A restaurant kitchen: waiters post orders on the rail (they clip the ticket and walk away — no answer needed). When a waiter needs to know "is table 7's steak ready?", they must ask the chef and wait — and while waiting, that waiter does nothing else useful. A good restaurant is designed so that waiters almost never have to ask; the kitchen posts plates to the pass and rings a bell. NVMe is designed the same way: the host posts doorbells, the device posts data, completion entries and interrupts, and nobody stands waiting on the fast path except the device fetching what it needs.

  • Postcards can get lost silently; posted writes are not "unreliable". Each hop's Data Link Layer guarantees delivery with ACK/NAK and replay. What a posted write lacks is an end-to-end confirmation, not reliability on each link.
  • Postcards can arrive in any order. Posted writes from one source to one destination are delivered in order unless Relaxed Ordering permits otherwise (Chapter 14), and that order is exactly what makes NVMe work.
  • Someone on the phone waits. A PCIe requester does not have to wait idle; it can issue many more questions (non-posted requests) before the first answer arrives, up to its tag and credit limits (Chapter 13). The CPU is the exception: a CPU load from MMIO does stall the instruction that needs the value.
  • Hanging up after silence is a choice in real life. In PCIe the timeout range is configured in a register and the consequence (an error, all-ones data to the CPU) is defined behaviour.
  • A question answered by "I don't know" is still an answer. A completion with status Unsupported Request or Completer Abort discharges the request; it is not a timeout.

Beginner explanation

A posted request is one the sender does not expect to hear back about. Once it is handed to the link, the sender considers it done. Memory writes and messages are posted.

A non-posted request is one that must be answered by a completion. The sender keeps a record of it (by its Tag) until the answer arrives. Memory reads, configuration reads and writes, I/O reads and writes, and atomic operations are non-posted.

Why the difference? A read obviously needs an answer: the data. A memory write does not need one for the system to work, and skipping the answer doubles the efficiency of writes and removes a round trip. Configuration and I/O writes are different: they change how hardware behaves (enable a device, set a BAR), and software must know they have taken effect before proceeding — so they get a completion even though it carries no data.

Engineering explanation

Posted requests: Memory Write and Messages

A posted request is complete, from the requester's point of view, when its Transaction Layer has transmitted it. The requester keeps no state about it (beyond the Data Link Layer's replay buffer, which is per-hop and released on ACK). Consequences:

  • No round-trip latency. A CPU store to an uncacheable MMIO address retires once the write is accepted into the CPU's/Root Complex's posting path; the core continues. This is why an NVMe doorbell write costs tens to hundreds of nanoseconds of CPU time rather than a microsecond-scale round trip.
  • No end-to-end success signal. If a posted write is dropped because it is malformed or unsupported at the target, the requester is not told by a completion. The detecting component reports through error messages to the Root Complex (AER), not to the requester.
  • Ordering does the work of acknowledgement. Because a later read from the same requester to the same destination cannot pass an earlier posted write (Chapter 14), reading back after writing proves the write has reached that point.

Messages are posted for the same reasons: error notifications, interrupt emulation, and power-management handshakes would be self-defeating if they needed answers (imagine an error message timing out). Where a handshake is needed, it is built from two messages (for example, PME_Turn_Off followed later by PME_TO_Ack).

Non-posted requests

A non-posted request allocates a Tag and a slot in the requester's outstanding-request tracking, and holds them until the final completion arrives or the request times out. Each kind has a reason to be non-posted:

  • Memory Read: needs the data.
  • Configuration Read/Write: configuration software must know the access took effect, and a function that is not ready can ask for a retry (Configuration Request Retry Status, CRS). Conventional PCI configuration writes were also not posted.
  • I/O Read/Write: legacy I/O semantics required I/O writes to complete before the CPU's I/O instruction retired; PCIe preserved that.
  • AtomicOps: return the original value — the whole point of an atomic read-modify-write.
  • Deferrable Memory Write (DMWr) Version-dependent: a write that the completer may refuse, so the requester needs an answer. Only in recent revisions; you will not normally see it with NVMe.

Completions

A completer answers each non-posted request with one or more completions, routed by Requester ID. Rules worth knowing now:

  • Successful reads (memory, configuration, I/O) and AtomicOps get CplD; successful configuration and I/O writes get Cpl.
  • Unsuccessful requests get Cpl with status UR, CA or (configuration only) CRS, and no data.
  • A memory read may be answered by several CplDs, in increasing address order, splitting only at permitted boundaries (Chapter 13).
  • If no component claims a non-posted request (no BAR or window matches), the component that determines this — often a switch port or the Root Complex — returns a UR completion itself. For a posted request in the same situation, it simply drops it and reports the error.

Separate classes, separate credits

Inside every PCIe port, the receive buffers are split into three classes — Posted (P), Non-Posted (NP) and Completion (Cpl) — each with separate header and data credits advertised to the link partner (Chapter 16). The transmitter may only send a TLP of a class when it holds enough credits of that class. This separation is not cosmetic: it is how PCIe avoids deadlock. If a full NP queue could block posted writes or completions, a device waiting for a completion to free its own buffers could wait forever. The ordering rules require that posted requests and completions must be able to pass blocked non-posted requests for exactly this reason (Chapter 14).

A well-behaved requester only issues a read if it has buffer space to receive all of that read's completion data. This is why endpoints and Root Complexes are generally expected to advertise unlimited ("infinite") completion credits: they have already reserved the space before asking. Confirm the exact rule for each component type in the flow-control section of your specification revision. The practical consequence for NVMe: the number of reads an SSD keeps in flight is bounded by its internal completion buffer as well as by its tags.

Completion Timeout

Every requester of non-posted requests must implement a Completion Timeout: if a request's completion(s) do not all arrive within the configured time, the request is considered failed. Key facts:

  • Configuration. The Device Capabilities 2 register advertises which timeout ranges the function supports and whether the timeout can be disabled; the Device Control 2 register selects the Completion Timeout Value and the Completion Timeout Disable bit. The default range is 50 µs to 50 ms. Optional larger ranges reach seconds (commonly labelled ranges A–D, up to tens of seconds). Exact encodings: PCI Express Base Specification — Device Control 2 Register.
  • It is an error, not a retry. On expiry the requester logs a Completion Timeout error (in AER, an uncorrectable error, non-fatal by default severity) and reports it. PCIe does not re-issue the request.
  • Late completions become unexpected. If the completion arrives after the requester has given up and freed the Tag, the requester sees an Unexpected Completion.
  • CPU-side behaviour. When a CPU MMIO read times out at the Root Complex, the load must still return something: on most platforms it returns all ones (0xFFFFFFFF) Implementation-dependent. This is why drivers treat a register read of all ones as "device may be gone". The Linux NVMe driver checks Controller Status (CSTS) for this value.

Connecting posted/non-posted to NVMe

NVMe's queue design is, at heart, an exercise in using posted writes for everything time-critical and putting non-posted reads only where they are unavoidable — and on the device side, where they can be pipelined.

Three design choices stand out:

  1. Doorbells are writes, not reads. The host tells the controller where the tail is; it never asks the controller anything per command.
  2. Completions live in host memory. The controller writes CQEs (posted) and the host polls its own memory using the phase tag. In AHCI-era designs, drivers commonly read device registers to discover completion status; NVMe removed that from the fast path.
  3. The device does the waiting. All non-posted reads on the fast path are issued by the SSD, which can keep dozens in flight and overlap them with other work. The CPU never stalls on the fast path.

Latency hiding and Little's Law

For an NVMe WRITE the device must read the data. Each read takes a round trip. To keep the link full, the device must have enough bytes requested-but-not-yet-returned at any moment.

Flushing posted writes

When software must know that its posted writes have reached a device (for example, before it times a hardware operation or before it assumes a disable has taken effect), the classic technique is to read back from the same device. Because a read request must not pass earlier posted writes from the same requester on the same path, the read's completion cannot be generated until the writes ahead of it have been delivered to the completer. A zero-length read (Length 1, both byte enables 0000b) serves the same purpose for memory.

writel(value, regs + CTRL);        /* posted MWr: may still be in flight      */
(void)readl(regs + STATUS);        /* non-posted MRd: its completion cannot   */
                                   /* return until the write above has reached */
                                   /* the device (same requester, same path)   */

The NVMe driver does not need this for doorbells: the device's reaction (fetching SQEs) is itself the evidence, and nothing on the host depends on the exact moment the doorbell lands. It does matter during controller enable/disable and reset sequences, where the driver polls CSTS (a read) after writing CC — which both waits for the controller and incidentally flushes the write.

The central concept on the ladder

Postcards (no answer) versus questions on the phone (wait for the answer, hang up if none comes).

Posted: MWr, Msg. Non-posted: MRd, CfgRd/Wr, IORd/Wr, AtomicOps — answered by Cpl/CplD matched by Requester ID + Tag; unanswered requests time out.

Ports keep separate P/NP/Cpl buffers and credits. Requesters keep a table of outstanding non-posted requests with timers. CPUs stall a load until its CplD returns; stores to MMIO are posted and retire early.

The PCIe Base Specification classifies each request type, defines completion rules, the Completion Timeout mechanism and its Device Control 2 controls, and the ordering rules that relate the three classes.

NVMe: doorbells, data-to-host, CQEs and MSI-X are posted; SQE/PRP/SGL fetches and data-from-host are non-posted reads issued by the controller.

In a trace, every MRd/Cfg/AtomicOp row should be followed (not necessarily immediately) by completion rows with the same Requester ID and Tag; MWr and Msg rows have no partners.

A non-posted request without a completion is a timeout in the making; a posted write that produced an error is visible only in AER at the detector. Ask "who is waiting on whom?" and "who would have been told?"

Hardware view

On the CPU side

  • MMIO stores to an uncacheable BAR mapping go into the CPU's store/posting path and on to the Root Complex, which issues MWr TLPs. The core does not wait for the device. (Write-combining mappings, used for some device memory, can additionally merge stores; NVMe register BARs are normally mapped uncacheable.) Implementation-dependent
  • MMIO loads become MRd TLPs; the core's load cannot complete until the CplD returns. Out-of-order cores can keep doing independent work for a while, but anything depending on the loaded value stalls, and uncacheable loads are typically strongly ordered, limiting overlap. A single MMIO read commonly costs on the order of a microsecond on a server.
  • On completion timeout the Root Complex synthesises a result for the load (commonly all ones) so the core can make progress; it may also raise a platform error.

On the device side

  • Outstanding-request table: one entry per Tag in use, recording destination buffer, expected byte count and a timer.
  • Completion reassembly buffer: space reserved for each outstanding read's data before the read is issued.
  • Separate transmit queues per class so that posted writes (data to host, CQEs) are never stuck behind non-posted reads waiting for NP credits.
  • Completion timer: granularity and accuracy are implementation-dependent within the configured range — a "50 µs to 50 ms" setting means the timeout must not expire before the lower bound and should expire by the upper bound, not that it fires at a precise time.

Specification view

The classification of requests, the completion rules and the Completion Timeout mechanism are defined in the PCI Express Base Specification, Revision 6.x/7.0 — Transaction Layer Specification (Transaction Ordering; Completion Rules; Completion Timeout Mechanism), with the controls in the PCI Express Capability — Device Capabilities 2 and Device Control 2 registers and error reporting in the Advanced Error Reporting Capability. The NVMe side — that doorbells are writes to controller registers and that completion queues live in host memory — is defined by the NVM Express Base Specification 2.4 and the NVMe over PCIe Transport Specification 1.4.

  • Memory Writes and Messages are posted; Memory Reads, I/O and Configuration requests and AtomicOps are non-posted.
  • Configuration writes and I/O writes receive a completion without data.
  • Requesters must implement a Completion Timeout for non-posted requests (with permitted exceptions such as when disabled where supported); the default range is 50 µs to 50 ms.
  • Completion Timeout is an uncorrectable error class reported through AER; a completion arriving for a request that is no longer outstanding is an Unexpected Completion.
  • P, NP and Cpl are separate flow-control classes with separate header and data credits.
  • The Little's Law sizing of outstanding reads and the Gen4/Gen5 numbers are computed, not quoted.
  • "The NVMe fast path has no host-side non-posted requests" follows from the NVMe register and queue design; neither specification states it as a rule.
  • What value a CPU load returns when its MMIO read fails or times out (commonly all ones).
  • Whether a platform escalates a completion timeout to a machine check or system error.
  • How many reads a device keeps outstanding; how an NVMe controller maps a PCIe error on a data transfer to an NVMe status code.
  • The actual completion timer accuracy within the configured range.
  • Deferrable Memory Write (a non-posted write) exists only in recent revisions.
  • The name of status 010b changed from Configuration Request Retry Status to Request Retry Status in recent revisions, with broader use.

Check in the specification: the exact Completion Timeout Value encodings and range definitions; which device types must support which ranges; the rules on infinite completion credits; which requests are exempt from timeout. The NVMe specifications do not say how long a controller should wait for PCIe completions or which NVMe status to use when a PCIe data transfer fails — read your controller's documentation and observe.

  • Never conclude a posted write succeeded because no error completion arrived — there never is one.
  • Never treat a Completion Timeout as proof the completer is broken; the request or completion may have been lost or stalled anywhere on the path.
  • Never read a register of all ones as data without first asking whether the device is still there.

Protocol view

Direction and ownership summary:

  • Downstream posted: doorbells and register writes (CPU → device).
  • Downstream non-posted: CPU register reads and configuration requests (rare on the fast path).
  • Upstream non-posted: the device's DMA reads (SQEs, PRP/SGL lists, WRITE data).
  • Upstream posted: the device's DMA writes (READ data, CQEs) and MSI-X; error messages.
  • Completions flow opposite to their requests: downstream for device reads, upstream for CPU reads.

Code / pseudocode

A small simulation of a device fetching WRITE data with a limited number of outstanding reads. It shows latency hiding (throughput grows with outstanding reads until the link saturates) and models completion timeouts.

#!/usr/bin/env python3
"""Simulation: throughput of non-posted reads vs outstanding-request limit.
Standard library only. All numbers are illustrative, not measurements."""
import heapq
import random

LINK_BPS = 7.1e9          # usable completion payload rate, bytes/s (Gen4 x4, MPS 256)
MRRS = 512                # bytes per read request
RTT_NS = 1000             # mean read round trip, ns
JITTER_NS = 200           # +/- uniform jitter
TIMEOUT_NS = 50_000_000   # 50 ms, upper end of the default range
LOSS_PROB = 0.0           # probability that a request is lost (never completed)

def simulate(outstanding, total_bytes=8 << 20, loss=LOSS_PROB, seed=1):
    rnd = random.Random(seed)
    t, sent, done, timeouts = 0.0, 0, 0, 0
    wire_free = 0.0                       # time the completion direction is next free
    inflight = []                         # heap of (arrival_time, tag)
    tags = list(range(outstanding))
    while done < total_bytes:
        while tags and sent < total_bytes:
            tag = tags.pop()
            sent += MRRS
            if rnd.random() < loss:
                heapq.heappush(inflight, (t + TIMEOUT_NS, tag, False))
            else:
                ready = t + RTT_NS + rnd.uniform(-JITTER_NS, JITTER_NS)
                start = max(ready, wire_free)          # serialise on the link
                wire_free = start + MRRS / LINK_BPS * 1e9
                heapq.heappush(inflight, (wire_free, tag, True))
        t, tag, ok = heapq.heappop(inflight)
        if ok:
            done += MRRS
        else:
            timeouts += 1
            sent -= MRRS                   # the data must be fetched again by a retry policy
        tags.append(tag)
    return total_bytes / (t * 1e-9) / 1e9, timeouts

Worked example

How many reads must a Gen5 x4 SSD keep in flight?

Gen5 variant of the example system: 32 GT/s × 4 lanes × 128/130 ÷ 8 ≈ 15.75 GB/s per direction. With MPS 256 B and ~91% TLP efficiency, usable completion payload ≈ 14.3 GB/s. Assume a platform read round trip of 1.5 µs and MRRS 512 B.

  1. Bout = 14.3 × 109 B/s × 1.5 × 10−6 s ≈ 21,450 B.
  2. N = ⌈21,450 / 512⌉ = 42 outstanding reads.
  3. With 5-bit tags (32 values) the device could not reach line rate on WRITEs: 32 × 512 B / 1.5 µs ≈ 10.9 GB/s. With 8-bit tags (Extended Tag Field enabled) the tag limit is no longer the bottleneck — Chapter 13.
  4. If MRRS were raised to 1024 B, N would halve to 21; but larger requests increase the granularity of completion splitting and can hurt fairness for other devices sharing the Root Port. Derived

What a driver pays for a register read

Suppose a driver polled CSTS once per I/O at 1 million I/Os per second, with each MMIO read costing ~1 µs of stall: that is a full second of core stall per second — an entire CPU core consumed by waiting. A doorbell write costs a small fraction of that. This is the arithmetic behind NVMe's "no reads on the fast path" design. Derived

Common mistakes

  • "Configuration writes are posted like memory writes." They are not; they get a Cpl.
  • "No completion means it worked" for a posted write — no completion was ever going to come.
  • "Completion Timeout means the completer is broken." It means the requester did not receive all completions in time; the cause can be anywhere on the path (or a completer that is slow but correct, e.g. during its own error recovery).
  • Confusing PCIe Completion Timeout with the NVMe driver's command timeout. One is microseconds-to-milliseconds at the PCIe requester; the other is typically tens of seconds in the host driver.
  • Assuming the CPU waits for doorbell writes. It does not; any timing measured around a doorbell store measures the store, not the delivery.
  • Interpreting an error completion (UR/CA) as a timeout. Error completions discharge the request immediately.

Senior engineer insight

Posted traffic tells you what was decided; non-posted traffic tells you who is waiting. When a system hangs, list every outstanding non-posted request in the trace at the moment of the hang. Usually the list is short, and one entry explains the whole hang.

A Completion Timeout is reported long after the fault (milliseconds later, an eternity in trace time). Always go back in time from the timeout report to the request that caused it; in a long capture, trigger on the AER message and look back by the configured timeout window.

Seniors also know the asymmetry of evidence: a non-posted failure produces evidence at the requester (status or timeout); a posted failure produces evidence only at the detector. When the symptom is "data never arrived" for a posted write, look for AER logs at every component on the path, not at the sender.

Hints

Hint

Before the knee, each outstanding slot delivers MRRS bytes per round trip; total rate = N × MRRS / RTT.

Solution

Solution

Step 1: the formula predicts the knee at 7.1 GB/s × 1 µs / 512 B ≈ 13.9 outstanding reads; the simulation reaches 95% between 16 and 24 (16 gives ≈ 6.7 GB/s) because jitter and link serialisation round the corner of the curve. Step 2: the formula predicts ≈ 28; expect the simulated knee a little above that. Q1: each read slot independently delivers 512 B per round trip until the link becomes the bottleneck. Q2: each loss blocks one tag for 50 ms; with ~2,000 requests per MiB at 0.1% loss about two losses per MiB are expected (the fixed seed gives one), and the simulated rate collapses to ≈ 0.02 GB/s, each costing 50 ms — the time is dominated by timeouts, not data. Q3: up to 50 ms per lost completion (the timer must not fire before 50 µs and should fire by 50 ms); for the NVMe command it is part of, the latency then includes error handling on top.

What a senior engineer notices

Rare losses are a throughput catastrophe and a latency-tail catastrophe long before they are a "visible error". A tail-latency spike of tens of milliseconds at the 99.99th percentile with occasional CmpltTO entries in AER is this pattern.

Failure variants

  • Completer returns UR instead of losing the request: immediate failure, no timeout stall.
  • Completer is slow (RTT 60 ms) but correct: completions arrive after timeout — Unexpected Completions follow the timeouts.

Exercises

  1. Classify: CfgWr1, MsgD (vendor-defined), Swap, IOWr, MRdLk, MWr64 with RO set.
  2. Explain why an MSI-X interrupt is posted and what would go wrong if it were non-posted.
  3. A device keeps 8 reads of 256 B outstanding with 1.2 µs round trip. What is its maximum data-fetch rate?
  4. Why does the NVMe driver poll CSTS after writing CC.EN, and what PCIe property makes the poll also a flush?
  5. Describe a scenario in which a posted write is dropped and nobody on the host ever learns of it.
Model answers
  1. CfgWr1 non-posted; MsgD posted; Swap non-posted; IOWr non-posted; MRdLk non-posted; MWr64 posted (RO does not change the category).
  2. An interrupt is a notification; if it needed a completion, the device would hold a tag and buffer per interrupt and could time out on the platform's interrupt path. Posting also lets ordering rules ensure it follows the CQE write.
  3. 8 × 256 B / 1.2 µs ≈ 1.71 GB/s.
  4. The controller takes time to become ready; CSTS.RDY reports it. The CSTS read is non-posted and cannot pass the earlier posted CC write from the same requester, so the read's completion also proves the write arrived.
  5. A write to an address that no BAR claims, inside a switch's forwarding window: the switch's downstream port finds no target, drops it and logs/reports an error (which may be masked). With error reporting masked or unmonitored, no host software notices.

Quiz

  1. Which request receives a completion without data when successful?

    • MWr
    • CfgWr
    • MRd
    • Msg
    Answer and reasoning

    CfgWr (and IOWr) are non-posted writes; success is a Cpl. MWr and Msg get nothing; MRd gets CplD.

  2. Which NVMe action produces a non-posted request?

    • CQ head doorbell
    • CQE write
    • Fetching WRITE data from host memory
    • MSI-X
    Answer and reasoning

    The controller must read the data: MRd → CplD.

  3. What is the default Completion Timeout range?

    • 50 µs to 50 ms
    • 1 ms to 10 s
    • Exactly 30 s
    • There is no default
    Answer and reasoning

    The default range is 50 µs–50 ms; longer optional ranges may be selected in Device Control 2 if supported.

  4. A requester receives a completion for a Tag it has already freed. What does it report?

    • Malformed TLP
    • Completion Timeout
    • Poisoned TLP
    • Unexpected Completion
    Answer and reasoning

    No matching outstanding request → Unexpected Completion.

  5. Why are posted, non-posted and completion traffic buffered separately?

    • For bandwidth fairness only
    • To prevent deadlock: blocked non-posted requests must not block posted requests or completions
    • Because they have different header sizes
    Answer and reasoning

    Deadlock freedom relies on posted requests and completions being able to make progress when non-posted requests are blocked.

  6. A CPU load from a BAR returns 0xFFFFFFFF. List three possible explanations.

    Model answer

    The device is gone or the link is down (the Root Complex synthesised all ones); the read timed out or got UR/CA (also synthesised); or the register genuinely contains all ones (rare, check the register definition).

  7. Why can an SSD reach full READ bandwidth with few outstanding non-posted requests but needs many for WRITE?

    Model answer

    READ data flows to the host as posted writes — no waiting. WRITE data must be fetched with non-posted reads, each costing a round trip; Little's Law demands rate × latency bytes outstanding.

  8. What does reading back a register after writing it guarantee, and what does it not?

    Model answer

    It guarantees the earlier posted write from the same requester on the same path has reached the device before the read completes (ordering). It does not guarantee the device has finished acting on the write (e.g. a reset in progress) — that requires a status bit defined by the device.

  9. Is an MSI-X write subject to Completion Timeout? Why or why not?

    Model answer

    No. It is a posted memory write; there is no completion to time out.

Interview questions

  1. (Beginner) Define posted and non-posted with an NVMe example of each.

    Model answer

    Posted: no completion (doorbell MWr, CQE MWr). Non-posted: completion required (SQE fetch MRd, configuration writes during enumeration).

  2. (Intermediate) Why is a configuration write non-posted?

    Model answer

    Software must know the configuration change took effect before continuing (e.g. before using a BAR it just programmed), and a function not ready can respond with CRS. It also mirrors conventional PCI behaviour.

  3. (Intermediate) How does NVMe avoid MMIO reads on the I/O path?

    Model answer

    Doorbells are writes; completions are written by the device into host-memory CQs with a phase tag; the host learns head/tail positions from CQEs (SQ head pointer in each CQE) instead of reading registers.

  4. (Advanced) Explain a Completion Timeout investigation end to end.

    Model answer

    Identify the requester from AER; capture or reproduce with an analyzer; find the request without completions; check whether the request reached the completer (capture on both sides of switches), whether the address was valid/mapped (IOMMU log), whether the completer produced a completion that was lost or misrouted (wrong Requester ID), and correlate with link events (retrains, replays) at that time.

  5. (Advanced) Would you ever disable Completion Timeout?

    Model answer

    Only in narrowly controlled cases (e.g. debugging a completer that is known to take very long, or certain platform-recommended configurations), never as a fix: it converts a reported error into a potential permanent hang of the requester.

  6. (Senior) A customer sees occasional 50 ms latency spikes on writes only. What is your hypothesis and how do you test it?

    Model answer

    Hypothesis: rare lost or late completions for the device's data reads causing timeouts (writes need reads; reads don't). Test: AER counters for CmpltTO/UnxCmplt correlated with spikes; analyzer trigger on AER message with look-back; check if spikes vanish with a different slot/switch/IOMMU setting.

  7. (Senior) How would you explain to a firmware team that "the MWr was ACKed" is not proof it reached memory?

    Model answer

    ACK is a per-link Data Link Layer acknowledgement from the immediate neighbour. A switch or Root Complex may still drop, block or fail the write after ACKing it; the only end-to-end evidence is a subsequent ordered read or a consumer observing the data.

Teach-back challenge

  • To a child: postcard versus phone question, and what "hanging up after silence" means.
  • To a junior engineer: why NVMe WRITEs stress the device's read machinery.
  • To a senior engineer: why Completion Timeout values are a trade-off between hang detection and false positives during error recovery.
Model explanations

Child: "When you send a postcard you don't wait. When you ask a question on the phone you wait for the answer. If nobody answers for a long time, you hang up and tell a grown-up something is wrong — that's the timeout."

Junior: "For a WRITE, the data is in host memory and the SSD has to ask for it with reads. Every read takes a round trip, so the SSD must keep many reads in flight — rate times latency worth of bytes. Too few tags, small MRRS or high latency caps write bandwidth."

Senior: "Short timeouts detect lost completions quickly and free resources, but a completer in a legitimate slow path (internal error recovery, a Root Complex servicing a memory error, a switch retraining) may answer late; that produces timeouts followed by unexpected completions. Long timeouts avoid that but stall requesters and inflate tail latency. The right value depends on the platform's worst legitimate latency."

Chapter summary

Posted requests (MWr, Msg) are fire-and-forget: cheap, unacknowledged end to end, ordered. Non-posted requests (MRd, CfgRd/CfgWr, IORd/IOWr, AtomicOps) hold a Tag until Cpl/CplD arrives or a Completion Timeout fires. NVMe puts all host-side fast-path actions on posted writes and lets the device do the waiting with pipelined reads. Little's Law tells you how many reads must be outstanding; Device Control 2 tells you how long a requester will wait; AER tells you when it gave up.

Do not move on until you can:

  • classify every TLP kind as posted, non-posted or completion
  • explain why configuration writes are non-posted
  • map each NVMe step to posted/non-posted and say who waits
  • compute outstanding reads needed for a target bandwidth
  • explain Completion Timeout configuration, reporting and consequences
  • find a missing completion in a trace and list where it could have been lost
