Everything an NVMe SSD does on PCI Express (PCIe) eventually becomes a Transaction Layer Packet (TLP). This chapter teaches what a TLP is, why it exists, what is inside it, and the small family of TLP kinds you will meet in every NVMe trace: memory reads and writes, configuration reads and writes, completions, messages and atomic operations.

Why this chapter exists

In the PCIe layer model you met three layers: the Transaction Layer, the Data Link Layer and the Physical Layer. This chapter zooms into the top one and into the unit it trades in: the Transaction Layer Packet (TLP).

Why does a storage engineer care about a packet format? Because when an NVM Express (NVMe) command goes wrong, the specification-level story ("the host submitted a READ and never got a completion") is almost never enough to find the bug. The evidence lives one level lower. A protocol analyzer does not show you "a READ command"; it shows you a memory write to an address inside Base Address Register 0 (BAR0), followed by a memory read from host memory, followed by a completion carrying 64 bytes, and so on. If you cannot read those packets you cannot reconstruct the story, and if you cannot reconstruct the story you are guessing.

This chapter is the bridge. After it, every later chapter will speak in TLPs: header anatomy, posted versus non-posted, tags, ordering, flow control, doorbells, command-to-TLP correlation.

Learning objectives

  • Define a TLP and explain why PCIe moves transactions as packets rather than as bus cycles.
  • Name the three parts of a TLP (header, optional data payload, optional digest) and what each is for.
  • Explain the request/completion relationship and the role of the Transaction ID (Requester ID + Tag).
  • Recognise the major TLP kinds: Memory Read (MRd), Memory Write (MWr), Configuration Read and Write (CfgRd/CfgWr), Completion (Cpl), Completion with Data (CplD), Messages (Msg/MsgD) and Atomic Operations (AtomicOps), plus the legacy I/O Read and Write.
  • Say which of those carry data, which expect a completion, and who usually sends them in an NVMe system.
  • Map an NVMe command (doorbell, command fetch, data movement, completion entry, interrupt) to the TLPs it produces.
  • Read a simple synthetic trace and spot the first abnormal TLP.

Prerequisites

You should be comfortable with: the idea that the CPU and devices share an address space (How Computers Move Data); PCIe as a point-to-point, packet-switched interconnect with a Root Complex, switches and endpoints (PCIe Mental Model); and the three-layer model (PCIe Layer Model). Link training (LTSSM, Link Training) must have finished — TLPs only flow on a link in the L0 state.

The story

Imagine the computer is a town. The teacher (the CPU) lives in the school, the giant library (the SSD) is across town, and they are connected by a very fast road (PCIe). Nobody walks along the road carrying loose books. Everything travels in delivery trucks.

Every truck has a big label stuck on the front. The label says what kind of trip it is ("I am bringing you something", "please send me something back", "here is what you asked for"), where it is going, who sent it, and a tracking number. Some trucks carry boxes of books in the back; some are empty and only carry the label. A few trucks also carry a sealed checksum card so the receiver can be sure nothing in the truck was swapped on the way.

When the library asks the teacher's classroom "please give me the request slip on table 4", it sends an empty truck with a label. The classroom answers by sending back a truck full of what was asked for, with the same tracking number on the label, so the library knows which question this answer belongs to.

That truck is a TLP.

Think of a freight network with standardised shipping containers. Every shipment carries a waybill in a fixed format: shipment type, destination, sender, reference number, number of pallets, and which pallets are only partly full. The network does not care what is inside the pallets. Depots read the waybill, route the container, and the receiver unpacks it. Request-for-goods waybills are answered by a delivery waybill that quotes the original reference number.

The waybill is the TLP header; the pallets are the data payload (counted in 4-byte "doublewords"); the optional tamper-seal is the end-to-end digest; the reference number is the Tag together with the sender's identity.

  • No depot "stores" a TLP for later the way a warehouse does. Switches forward TLPs within microseconds or less, and a link only accepts a TLP when the receiver has advertised buffer space (flow-control credits, Chapter 16). The analogy hides credits entirely.
  • The truck is not responsible for arriving safely. Reliable delivery across one link is the job of the Data Link Layer (sequence numbers, LCRC, ACK/NAK and replay — Chapter 15). The TLP itself only optionally carries an end-to-end check.
  • Trucks on a real road overtake each other freely. TLPs obey strict ordering rules (Chapter 14), and whether one may pass another is part of the protocol, not of traffic luck.
  • The "classroom" answering the library is not the teacher. When an NVMe controller reads host memory, the Root Complex answers; the CPU's software is not involved at all. That is the whole point of Direct Memory Access (DMA).
  • Waybills have variable size here. The TLP header is 3 or 4 doublewords depending on the address width and type, which a fixed-form waybill does not capture.

Beginner explanation

Older PC buses such as conventional PCI were shared wires. A device that wanted to read memory would win arbitration, drive an address on the bus, and then hold the bus while the data came back. Everyone else waited.

PCIe replaced the shared bus with point-to-point serial links and made every interaction a packet. A device that wants to read memory sends a small packet that says "I am device 01:00.0, this is my request number 0x21, please read 64 bytes at address X". The link is then immediately free for other packets. Some time later the Root Complex sends back a packet that says "for device 01:00.0, request 0x21: here are your 64 bytes". The two halves of the conversation are separate packets, and between them the link carries other traffic. This is called a split transaction.

There are only a handful of things a packet can ask for:

  • Read some memory (Memory Read, MRd) — and wait for an answer.
  • Write some memory (Memory Write, MWr) — and do not wait for any answer.
  • Read or write a configuration register (CfgRd, CfgWr) — used by system software to discover and set up devices. Both wait for an answer.
  • Answer a previous request (Completion, Cpl, or Completion with Data, CplD).
  • Send a notification (Message, Msg or MsgD) — for example "an error happened" or "interrupt line A is asserted".
  • Do an atomic read-modify-write on memory (AtomicOp: FetchAdd, Swap, Compare-and-Swap) — and wait for the old value.

Every packet has a header (the label). Packets that carry data also have a payload. Some also carry a 4-byte digest (an end-to-end checksum called ECRC). That is the whole shape.

Requests ask; completions answer. Writes to memory and messages are fire-and-forget ("posted"). Reads, configuration accesses, I/O accesses and atomics expect an answer ("non-posted"). Chapter 12 is entirely about this split.

Engineering explanation

What a TLP is

A TLP is the unit of information exchanged between the Transaction Layers of two PCIe components. The Transaction Layer of the sender builds it; the Data Link Layer wraps it with a sequence number and a Link CRC (LCRC); the Physical Layer frames it and serialises it onto the lanes. At each hop, the receiving Data Link Layer checks and strips its wrapper, and if the TLP is not for this component (for example, inside a switch), it is forwarded out of another port where a new Data Link Layer wrapper is applied. The TLP itself — header, payload, digest — is carried unchanged end to end, except for a few fields that a component is explicitly allowed to modify (for example, the poisoned bit EP may be set on the way when data is known bad).

Why TLPs exist

The packet model solves four problems that a shared parallel bus could not:

  1. Scalability of bandwidth. A serial differential lane can run at gigatransfers per second; a wide parallel bus suffers skew. Packets let the same protocol run over x1 to x16 links and over many speed generations.
  2. Split transactions and concurrency. Because a read request and its answer are separate packets, a requester can have many reads outstanding at once (Chapter 13), hiding memory latency. A Gen4 x4 NVMe SSD needs dozens of reads in flight to fill the link.
  3. Routing through a fabric. A header carries enough information (an address, or a Bus/Device/Function ID, or an implicit routing code) for switches to forward the packet without understanding its meaning.
  4. Software compatibility. The kinds of request — memory, I/O, configuration — are deliberately the same as those of conventional PCI, so an operating system that knew PCI could drive PCIe with the same model. Only the wire changed.

Counting in DWs keeps the header small (a 10-bit Length field covers 4 KiB) and keeps receivers simple. The cost is that unaligned transfers need extra information: byte enables for requests and Lower Address/Byte Count for completions. Almost every "off by a few bytes" bug in a trace is a misunderstanding of those fields — Chapter 11 covers them bit by bit.

Request/completion relationship

Requests come in two families:

  • Posted requests (Memory Write, Messages) never receive a completion. Once the TLP is accepted by the link, the sender is done.
  • Non-posted requests (Memory Read, I/O Read/Write, Configuration Read/Write, AtomicOps, and in newer revisions Deferrable Memory Write) each receive one or more completions.

A completion is matched to its request by the Transaction ID: the pair (Requester ID, Tag). The Requester ID is the Bus/Device/Function number of the requester (for our Lab SSD at 01:00.0, that is 0x0100). The Tag is a number the requester chooses so that it can tell its outstanding requests apart. The completer copies both into the completion; switches route the completion back by Requester ID (ID routing), not by address.

Three facts about completions are worth memorising now and will be justified in later chapters:

  1. A single read may be answered by several completions, each carrying part of the data in increasing address order (Chapter 13).
  2. A completion carries a status: Successful Completion (SC), Unsupported Request (UR), Completer Abort (CA), or Configuration Request Retry Status (CRS). Only successful completions of reads carry data (CplD); unsuccessful ones are Cpl without data.
  3. If a completion never arrives, the requester eventually declares a Completion Timeout — an error, not a retry (Chapter 12).

Memory Read (MRd)

A memory read asks the completer to return Length DWs starting at a DW-aligned address, with First/Last DW byte enables saying which bytes of the first and last DW are really wanted. It carries no data. A 3DW header (MRd32) is used for addresses below 4 GiB, a 4DW header (MRd64) for addresses at or above 4 GiB. A requester may not ask for more than its Max Read Request Size (MRRS) in one request, and the answer may come back in several pieces.

In NVMe, MRds from the SSD are how the controller pulls work out of host memory: Submission Queue Entries (SQEs), Physical Region Page (PRP) lists, Scatter Gather List (SGL) segments, and the data of WRITE commands. MRds from the CPU to BAR0 are how the driver reads controller registers such as Controller Status (CSTS).

Memory Write (MWr)

A memory write carries Length DWs of data to a DW-aligned address, again with byte enables for partial first/last DWs. It is posted: the sender receives nothing back, not even an acknowledgement at the transaction level. (The Data Link Layer still ACKs the TLP hop by hop, but that only proves the neighbour received it intact, not that it reached memory.)

In NVMe, the CPU's MWrs to BAR0 are doorbell writes and register writes; the SSD's MWrs to host memory deliver READ-command data, Completion Queue Entries (CQEs) and MSI-X interrupt messages (an MSI-X interrupt is a memory write to a special address — see Chapter 43).

Configuration Read and Write (CfgRd, CfgWr)

Configuration requests access the 4 KiB configuration space of a function (Chapter 18). They are routed by Bus/Device/Function rather than by address, they are always one DW long, and both reads and writes are non-posted — a configuration write gets a Cpl so that software knows the write took effect. Type 0 (CfgRd0/CfgWr0) targets a function on the bus directly below a bridge; Type 1 (CfgRd1/CfgWr1) is forwarded by bridges and converted to Type 0 when it reaches the target bus. Only the Root Complex originates configuration requests.

Completion (Cpl) and Completion with Data (CplD)

Completions answer non-posted requests. CplD carries data (read data, configuration read data, the original value for an AtomicOp). Cpl carries no data: it answers a configuration write or I/O write, or reports a non-successful status for any request. Every completion header carries the Completer ID, the status, a Byte Count of remaining bytes, the requester's ID and Tag, and the low address bits of the data it carries.

Messages (Msg, MsgD)

Messages are posted TLPs used for in-band signalling that conventional PCI did with side-band wires: legacy interrupt assertion and de-assertion (INTx emulation), error reporting from a device to the Root Complex (ERR_COR, ERR_NONFATAL, ERR_FATAL), power-management handshakes, Latency Tolerance Reporting (LTR), slot power limits and vendor-defined messages. They always use a 4DW header; the Type field encodes how the message is routed (to the Root Complex, by address, by ID, broadcast from the Root Complex, local, or gathered and routed to the Root Complex), and a Message Code byte says which message it is.

In an NVMe system you mostly see messages when something goes wrong (error messages that become AER entries, Chapter 46) or when MSI-X is disabled and the device falls back to INTx emulation.

Atomic operations (AtomicOps)

AtomicOps are non-posted requests that ask the completer to perform a read-modify-write on memory and return the original value: FetchAdd (add an operand, return the old value), Swap (unconditional exchange) and CAS (compare-and-swap; carries both a compare value and a swap value). FetchAdd and Swap support 32- and 64-bit operands; CAS supports 32-, 64- and 128-bit operands. Support is optional and advertised in the Device Capabilities 2 register (completer support per operand size, routing support in switches), and requesters must be enabled in Device Control 2. They matter for accelerators that share counters or queues with the CPU; NVMe controllers do not normally use them.

I/O requests and other kinds

I/O Read/Write exist for legacy compatibility; modern endpoints including NVMe controllers use memory space. You may also meet Memory Read Lock (MRdLk, legacy, only from the Root Complex), TLP prefixes, and in recent revisions Deferrable Memory Write (DMWr) Version-dependent, a non-posted write that the completer may decline. Treat any TLP kind you do not recognise in a capture as a question for the specification revision your analyzer decodes against.

The central concept on the ladder

Everything on the PCIe road travels in a labelled truck. The label says what kind of trip it is, where it goes, who sent it and its tracking number. Question trucks are answered by answer trucks with the same tracking number; delivery trucks need no answer.

A TLP is a packet with a 3- or 4-DW header, an optional payload of up to MPS bytes, and an optional 1-DW ECRC digest. Requests are posted (MWr, Msg) or non-posted (MRd, Cfg, IO, AtomicOps); non-posted requests are answered by Cpl/CplD matched by Requester ID + Tag.

Inside a PCIe component the Transaction Layer has transmit queues and receive buffers separated into Posted, Non-Posted and Completion classes, each with header and data credits. A DMA engine in the SSD turns "read 4 KiB at IOVA X" into several MRd TLPs and reassembles CplDs into an internal buffer; a completion-tracking table indexed by Tag remembers what each outstanding read was for.

The PCI Express Base Specification defines the TLP formats, the Fmt/Type encodings, the field rules (Length, byte enables, address formats), the routing mechanisms and the completion rules in its Transaction Layer chapter. Whether a component implements optional features (ECRC, AtomicOps, TLP Processing Hints) is advertised in configuration space and enabled by software.

For an NVMe READ: CPU MWr32 doorbell → SSD MRd64 for the SQE → RC CplD (64 B) → SSD MWr64 data to the host buffer (several TLPs ≤ MPS) → SSD MWr64 CQE (16 B) → SSD MWr MSI-X (4 B data) → later CPU MWr32 CQ head doorbell.

On an analyzer each of those is one row: direction, timestamp, TLP type, address or ID, Length, Tag, Requester ID, and for completions the status and byte count. A healthy trace shows every non-posted request answered by completions with the same Requester ID and Tag.

When an NVMe command times out, a senior engineer looks for the last TLP in the command's chain: was the doorbell write seen? Was the SQE fetched? Did the fetch's completion come back with status SC? Did data move? Was the CQE written? Was the MSI-X write sent? The first missing or abnormal TLP localises the failure to driver, platform, link or device.

How big is the overhead?

Each TLP pays a fixed cost on top of its payload. In non-Flit mode at Gen3 and above, a TLP with a 4DW header and no ECRC pays roughly: 4 bytes of framing token, 2 bytes of sequence number, 16 bytes of header, and 4 bytes of LCRC — about 26 bytes. With a 3DW header it is about 22 bytes. Derived

E = P / (P + O)
E
TLP-level efficiency: the fraction of transmitted bytes that are payload
P
payload bytes in the TLP (at most MPS)
O
per-TLP overhead in bytes: framing + sequence number + header + optional ECRC + LCRC (≈ 26 for a 4DW header without ECRC at Gen3–Gen5 non-Flit)

With MPS = 256 bytes, E ≈ 256 / 282 ≈ 0.91. With MPS = 128 bytes, ≈ 128 / 154 ≈ 0.83. This ignores Data Link Layer Packets (ACKs, flow-control updates), SKP ordered sets and the 128b/130b encoding, all of which reduce usable bandwidth further. It also explains why read requests (no payload, ~22–26 bytes each) are cheap on the upstream direction while their completions dominate the downstream direction.

Hardware view

Inside every PCIe component the Transaction Layer is real logic with real buffers. In a typical endpoint such as an NVMe controller you can picture:

Controller firmware / command enginedecides "fetch SQE", "read 4 KiB of write data", "post CQE"
DMA enginessplit work into TLP-sized requests, assign Tags, track outstanding reads
Transaction Layer TXseparate queues for Posted, Non-Posted and Completion TLPs; credit checks; header build; optional ECRC
Data Link Layersequence number, LCRC, replay buffer, ACK/NAK
Physical Layerframing, scrambling, encoding, lanes

On the receive side the mirror image exists: receive buffers per class (Posted, Non-Posted, Completion), each split into header and data credits; a decoder that checks Fmt/Type and field rules and drops malformed TLPs; a BAR decoder that turns MWr/MRd addresses into register accesses; and a completion matcher that looks up incoming CplDs by Tag.

  • Root Complex. Turns CPU loads/stores to MMIO addresses into MRd/MWr TLPs; turns device MRd/MWr TLPs into memory-controller accesses (through the IOMMU when enabled); generates CplDs for device reads; originates all configuration requests; receives messages and turns error messages into AER events.
  • Switch. Routes TLPs by address (memory/IO), by ID (configuration, completions, ID-routed messages) or implicitly (messages to Root Complex, broadcast). It does not create completions for forwarded requests; it does generate UR completions if no port claims a non-posted request.
  • Endpoint (the SSD). Claims MRd/MWr hitting its BARs and CfgRd0/CfgWr0 for its own functions; masters MRd/MWr for DMA; sends messages (errors, LTR).

An interposer or analyzer on the link sees TLPs exactly as transmitted, including retries. Nothing in software sees them: the CPU sees loads and stores, the driver sees register values and memory, and the SSD firmware sees what its hardware DMA engines report. This is why analyzers remain essential for protocol debugging.

Specification view

TLPs are defined by the PCI Express Base Specification, Revision 6.x/7.0 — Transaction Layer Specification, a PCI-SIG members' document. The formats in this chapter are the long-standing non-Flit formats, which have been stable in their essentials across revisions; Flit Mode (introduced with Revision 6.0) uses a different header encoding (see Chapter 11). NVMe does not define TLPs at all: the NVMe over PCIe Transport Specification 1.4 defines how NVMe's queues, doorbells and data pointers map onto PCIe memory space, and PCIe defines the packets that carry those accesses. Keep the three documents (NVMe Base, NVMe over PCIe Transport, PCIe Base) separate in your head.

  • TLP = optional prefixes + 3DW or 4DW header + optional data payload + optional 1-DW digest (ECRC, present when TD = 1).
  • Memory Writes and Messages are posted; Memory Reads, I/O requests, Configuration requests and AtomicOps are non-posted and are answered by completions.
  • Completions are routed by ID back to the requester and matched by Requester ID + Tag.
  • Configuration requests are one DW, routed by ID, and originate only from the Root Complex.
  • Messages use a 4DW header with an implicit routing code in the Type field and a Message Code.
  • The overhead figures above (≈22–26 bytes per TLP) are computed from field sizes, not quoted.
  • The NVMe-to-TLP mapping (doorbell = MWr to BAR0, SQE fetch = MRd, CQE = MWr, MSI-X = MWr) follows from NVMe's memory-mapped design and PCIe's TLP definitions; neither specification lists it as one table.
  • How many TLPs a DMA engine uses for a transfer (any size up to MPS for writes, up to MRRS for reads), and how many reads it keeps in flight.
  • Whether the Root Complex returns read data in one CplD or several (within the completion rules).
  • Whether ECRC is supported or enabled; whether optional features (AtomicOps, TLP Processing Hints) are used.
  • Which Requester ID the Root Complex uses for CPU-originated MMIO requests.
  • Flit Mode (Revision 6.0 onward) changes the header format and framing; the Data Link Layer wrapper changes too.
  • Tag width has grown over revisions (5-bit default with Extended Tag, 8-bit, 10-bit, and larger in Flit Mode) — Chapter 13.
  • New request types (for example Deferrable Memory Write) appear in newer revisions.

Check in the specification: the complete Fmt/Type encoding table for your revision; the Message Code table; AtomicOp operand and alignment rules; which fields a switch may modify; the rules for TLP prefixes. The PCIe specification also does not tell you how a particular SSD sizes its DMA requests — that is a design decision you observe in traces.

  • Never assume one NVMe command = one TLP. A 128 KiB READ can easily be hundreds of TLPs.
  • Never assume a posted write "has happened" because it was sent. Posted means no answer, not instantaneous.
  • Never assume an analyzer's TLP naming (e.g. "MWr(64)", "MemWr64", "MW") is standard — vendors differ.

Protocol view

From the protocol point of view, an NVMe command is a short conversation of TLPs flowing in both directions over the link between the Root Port and the SSD. Direction matters: "downstream" means away from the Root Complex (towards the SSD), "upstream" means towards it.

Notice the pattern:

  • Downstream, the host sends only posted MWr32 doorbells (and, during this command, the CplD for the SQE fetch).
  • Upstream, the SSD sends one non-posted MRd64 and then a stream of posted MWr64s: data, CQE, and the MSI-X write.
  • Only one request in this whole command needs a completion: the SQE fetch. For an NVMe WRITE the picture flips: the SSD must read the data, so there are many MRd/CplD pairs.

The fact that data, CQE and MSI-X are all posted writes travelling in the same direction is what lets PCIe ordering guarantee the driver sees the data before it sees the CQE — Chapter 14 explains why that holds and when it would not.

Code / pseudocode

The first program classifies a TLP from its first header byte (Fmt and Type) and computes per-TLP overhead. It uses only the Python standard library.

#!/usr/bin/env python3
"""Classify a non-Flit-mode TLP from header byte 0 and estimate link overhead.
Covers the common Fmt/Type encodings taught in Chapters 10-11."""

FMT = {0b000: ("3DW", False), 0b001: ("4DW", False),
       0b010: ("3DW", True),  0b011: ("4DW", True)}

def classify(byte0: int) -> str:
    fmt, typ = byte0 >> 5, byte0 & 0x1F
    if fmt == 0b100:
        return "TLP Prefix"
    if fmt not in FMT:
        return f"reserved Fmt {fmt:03b}"
    hdr, data = FMT[fmt]
    if typ == 0b00000:
        name, posted = ("MWr" if data else "MRd"), data
        name += "64" if hdr == "4DW" else "32"
    elif typ == 0b00001 and not data:
        name, posted = "MRdLk", False
    elif typ == 0b00010:
        name, posted = ("IOWr" if data else "IORd"), False
    elif typ in (0b00100, 0b00101):
        name = ("CfgWr" if data else "CfgRd") + str(typ & 1)
        posted = False
    elif typ >> 3 == 0b10:
        routing = ["to RC", "by address", "by ID", "broadcast from RC",
                   "local", "gathered to RC", "reserved", "reserved"][typ & 7]
        name, posted = ("MsgD" if data else "Msg") + f" ({routing})", True
    elif typ == 0b01010:
        name, posted = ("CplD" if data else "Cpl"), None
    elif typ == 0b01011:
        name, posted = ("CplDLk" if data else "CplLk"), None
    elif typ in (0b01100, 0b01101, 0b01110) and data:
        name = {0b01100: "FetchAdd", 0b01101: "Swap", 0b01110: "CAS"}[typ]
        posted = False
    else:
        return f"unknown/reserved Fmt={fmt:03b} Type={typ:05b}"
    kind = "completion" if posted is None else ("posted" if posted else "non-posted")
    return f"{name:22s} header={hdr} data={'yes' if data else 'no'} {kind}"

def overhead(header_dw: int, ecrc: bool = False) -> int:
    """Approximate bytes per TLP at Gen3-Gen5 non-Flit: STP token 4 + seq 2 + header + ECRC + LCRC 4."""
    return 4 + 2 + 4 * header_dw + (4 if ecrc else 0) + 4

if __name__ == "__main__":
    for b in (0x40, 0x20, 0x00, 0x60, 0x04, 0x44, 0x05, 0x0A, 0x4A, 0x30, 0x34, 0x6C, 0x4E, 0x02):
        print(f"0x{b:02X}  {classify(b)}")
    for mps in (128, 256, 512):
        o = overhead(4)
        print(f"MPS {mps:4d}: efficiency {mps / (mps + o):.3f} (overhead {o} B/TLP)")

Running it prints one line per byte-0 value, for example 0x40 MWr32 … posted and 0x4A CplD … completion, followed by the efficiency estimates (0.831, 0.908, 0.952). Try adding the 3DW case and ECRC and see how much each costs.

The second program is pseudocode for how a DMA engine might turn "read n bytes at address a" into requests. It is deliberately simple; real engines add credit checks, tag allocation and ordering logic.

function dma_read(addr, nbytes):
    while nbytes > 0:
        # never cross a 4 KiB boundary in one request; never exceed MRRS
        chunk = min(nbytes, MRRS, 4096 - (addr mod 4096))
        tag   = allocate_free_tag()          # blocks if none free (Chapter 13)
        fmt   = 4DW if addr >= 2^32 else 3DW
        send MRd(fmt, addr, length_dw = ceil_dw(addr, chunk),
                 first_be, last_be, requester_id = my_bdf, tag)
        remember(tag -> {addr, chunk, destination buffer})
        addr   += chunk
        nbytes -= chunk

on CplD(tag, byte_count, lower_addr, data):
    entry = lookup(tag)
    copy data to entry.destination at offset derived from lower_addr
    if byte_count == len(data_bytes): free_tag(tag)    # last completion for this request

Memory requests must not cross a 4 KiB address boundary. That is why DMA engines split at 4 KiB even when MRRS or MPS would allow more, and why a 4 KiB-aligned NVMe PRP page never needs a request that straddles it.

Worked example

Counting the TLPs of a 4 KiB NVMe WRITE

Setup (example system): Gen4 x4, MPS = 256 B, MRRS = 512 B, Read Completion Boundary (RCB) = 64 B. The driver submits one 4 KiB WRITE on SQ1 with PRP1 = 0x2_0000_0000 (page-aligned, so no PRP list is needed).

  1. Doorbell. CPU store to SQ1TDBL → one MWr32 downstream (3DW header, 1 DW of data).
  2. SQE fetch. One MRd64 upstream (64 bytes = 16 DW), answered by one CplD downstream (the 64-byte block is RCB-aligned and below MPS, so a single completion is natural, though the Root Complex could split it into 64-byte pieces only at RCB boundaries — here there is just one).
  3. Data fetch. 4096 B ÷ MRRS 512 B = 8 MRd64 upstream, each 128 DW, each with its own Tag.
  4. Data completions. Each 512 B request returns at least 2 CplDs (no CplD can exceed MPS = 256 B), so at least 16 CplDs downstream. A Root Complex that returns RCB-sized pieces could send 8 per request — 64 CplDs. Which one you see is implementation-dependent.
  5. Completion entry. One MWr64 upstream with 16 bytes (4 DW).
  6. Interrupt. One MWr32 upstream (MSI-X).
  7. CQ head doorbell. One MWr32 downstream (possibly later, possibly coalesced with other completions by the driver).
TLP count and approximate bytes on the link for one 4 KiB WRITE (derived; minimum-completion case)

Upstream (SSD → RC)1 MRd64 (SQE) + 8 MRd64 (data) + 1 MWr64 (CQE) + 1 MWr32 (MSI-X) = 1116 + 4 = 2010 × 26 + 22 = 282≈ 302
Downstream (RC → SSD)2 MWr32 (doorbells) + 1 CplD (SQE) + 16 CplD (data) = 198 + 64 + 4096 = 41682 × 22 + 17 × 22 = 418≈ 4586

(Completions use a 3DW header, so their overhead is ≈ 22 bytes.) The downstream direction carries the data for a WRITE; the upstream direction is nearly idle. For a READ the roles reverse. Common mistakes

  • "A write gets an ACK, so the writer knows it landed." The Data Link Layer ACK is per hop and proves only link-level delivery to the neighbour. Posted writes have no end-to-end acknowledgement. To know a write has reached its destination you need an ordering-based flush (for example, a read that must be ordered behind it) — Chapter 14.
  • Confusing Cpl and CplD. A read that fails returns Cpl (no data), not a CplD with zeros. Seeing a Cpl in answer to a MRd is itself a red flag.
  • Matching completions by address. Completions carry only the low 7 bits of an address (Lower Address). Matching is by Requester ID + Tag.
  • Believing the SSD "sends interrupts". With MSI-X, the SSD sends a memory write; the Root Complex/interrupt controller turns it into an interrupt.
  • Assuming 64-bit addresses always use 4DW headers. Addresses below 4 GiB must use the 3DW format, even when the device and BAR are 64-bit capable. Our BAR0 at 0xFE60_0000 is reached by MWr32/MRd32.
  • Treating configuration writes as posted. CfgWr is non-posted and gets a Cpl.
  • Forgetting the 4 KiB boundary rule when reasoning about how many requests a buffer needs.

Debugging connection

A TLP-literate debugging habit has three steps:

  1. Reconstruct the expected chain. For the command in question, write down the TLPs that must appear and their direction (as in the worked example).
  2. Find the first divergence. Walk the trace and find the first TLP that is missing, malformed, unexpected, or carries a non-SC status. Everything after it is consequence, not cause.
  3. Assign the divergence to an owner. A missing doorbell → driver/CPU/Root Complex. A missing SQE fetch after a good doorbell → device. A UR/CA completion to a device read → host side (IOMMU, address map). A completion that never comes → completer or the path (and eventually a Completion Timeout). Data written to the wrong address → device (or a driver that gave it wrong pointers).
Symptoms and the first TLP to look for

NVMe I/O timeoutDid the doorbell MWr reach the device? Did a MRd for the SQE follow?
Data corruption on readsDo the data MWr64 addresses match the PRP entries? Is any MWr marked poisoned (EP=1)?
AER "Unsupported Request" from the SSDWhich request did the SSD receive that it could not claim? Check the logged header.
AER "Completion Timeout" at the SSDWhich MRd Tag never got a CplD? Was the request even forwarded?

Senior engineer insight

Seniors read traces in terms of obligations. Every non-posted request creates an obligation (a completion must come back); every doorbell creates an obligation (the controller must fetch); every SQE creates obligations (data must move, a CQE must be posted). A trace is healthy when every obligation is discharged in the right order. A failure is the first undischarged or wrongly discharged obligation.

Posted-only traffic in one direction with no non-posted requests means nobody is waiting on the link. A requester with all its tags outstanding and no completions returning is waiting on the completer. Silence after a doorbell means the device is the one not acting. Learning to ask "who owes whom a TLP right now?" is worth more than memorising encodings.

A second insight: the cheapest TLP to send is often the most expensive to wait for. A 26-byte MRd costs little bandwidth but a full round trip through the Root Complex and memory — hundreds of nanoseconds to microseconds. That is why NVMe was designed so the host never has to read from the device on the fast path: the driver writes doorbells (posted) and polls CQEs in its own memory, never reading device registers per I/O.

Background

Step 2

Step 3

Pair completions with requests by (Requester ID, Tag). Mark any non-posted request without a completion and any completion with non-SC status.

What a senior engineer notices

Two SQE fetches after a doorbell that wrote tail = 5: the controller is fetching slots 4 and 5, so it believed the previous tail was 3 — or it prefetches. Quiz

  1. Which TLP kind does an NVMe controller use to deliver a Completion Queue Entry to host memory?

    • CplD
    • MWr
    • Msg
    • CfgWr
    Answer and reasoning

    MWr. A CQE is ordinary data written into host memory by DMA. CplD answers a request; it is never used to "push" data that nobody asked for.

  2. Which of these TLPs is posted?

    • CfgWr0
    • MRd64
    • Msg ERR_NONFATAL
    • FetchAdd
    Answer and reasoning

    Messages are posted. Configuration writes, memory reads and AtomicOps are non-posted.

  3. What two fields together identify which request a completion answers?

    • Requester ID and Tag
    • Address and Length
    • Completer ID and Byte Count
    • TC and Attr
    Answer and reasoning

    The Transaction ID is Requester ID + Tag; the completer copies both into the completion.

  4. When is the TLP digest (ECRC) present?

    • Always
    • When TD = 1 in the header
    • Only on completions
    • Only on Gen5 links
    Answer and reasoning

    The TD bit says a 1-DW digest follows the header/payload. Whether a component generates it depends on support and enabling in its AER capability.

  5. The Lab SSD reads 64 bytes from IOVA 0x1_2340_0100. Which header format must it use?

    • 3DW (MRd32)
    • 4DW (MRd64)
    • Either; the device chooses
    Answer and reasoning

    The address is above 4 GiB, so it needs the 64-bit format. Below 4 GiB the 32-bit format is required.

  6. A read request fails at the completer. What does the requester receive?

    • A CplD full of zeros
    • Nothing
    • A Cpl with a non-successful status
    • A Msg ERR_FATAL
    Answer and reasoning

    A completion without data carrying UR or CA (or CRS for configuration requests). "Nothing" would lead to a Completion Timeout instead, which is a different failure.

  7. Who originates configuration requests?

    • Only the Root Complex
    • Any endpoint
    • Switches
    • The NVMe controller during initialisation
    Answer and reasoning

    Configuration requests come only from the Root Complex (on behalf of software). Bridges and switches forward/convert them.

  8. Why does NVMe avoid having the host read device registers on the I/O fast path?

    Model answer

    MMIO reads are non-posted: the CPU must wait for a full round trip to the device and back. Writes (doorbells) are posted and cheap. NVMe puts completion status in host memory (CQEs with a phase tag) so the host polls its own memory instead of reading the device.

  9. Explain why an MSI-X interrupt is visible as a TLP in a trace while a legacy interrupt "line" is visible as a message TLP.

    Model answer

    MSI-X is defined as a memory write of a programmed data value to a programmed address; it is an ordinary MWr. PCIe has no interrupt wires, so legacy INTx is emulated by Assert_INTx/Deassert_INTx message TLPs routed to the Root Complex.

  10. Give one reason the per-hop ACK does not make a posted write "acknowledged" end to end.

    Model answer

    The ACK is a Data Link Layer DLLP between two neighbours, generated when the neighbour's receive logic accepts the TLP intact. A switch that ACKs a TLP has not yet forwarded it, and the final target has not yet executed it.

Interview questions

  1. (Beginner) What is a TLP and what are its parts?

    Model answer

    The PCIe Transaction Layer's packet: a 3- or 4-DW header, an optional payload up to MPS, and an optional 1-DW ECRC digest; optional prefixes may precede the header. The Data Link Layer adds a sequence number and LCRC; the Physical Layer frames it.

  2. (Beginner) What is the difference between Cpl and CplD?

    Model answer

    CplD carries data (successful read, configuration read, AtomicOp result); Cpl carries none (completion of a configuration/I/O write, or any non-successful status).

  3. (Intermediate) Walk me through the TLPs of an NVMe READ.

    Model answer

    Doorbell MWr down; SQE MRd up and CplD down; possibly PRP list MRd/CplD; data MWrs up (≤ MPS each, not crossing 4 KiB); CQE MWr up; MSI-X MWr up; CQ head doorbell MWr down later.

  4. (Intermediate) Why do completions use ID routing?

    Model answer

    A completion must return to the requester, which is identified by Bus/Device/Function. The requester's identity is in the Requester ID; the original address is irrelevant (and only its low bits are carried) because the data goes back to the requester, not to an address.

  5. (Advanced) When would you expect to see AtomicOps on a link with an NVMe SSD?

    Model answer

    Normally never from the SSD itself. You might see them from accelerators sharing the hierarchy, or in computational-storage designs where a device coordinates with host data structures; it needs completer and routing support and requester enable.

  6. (Advanced) An NVMe command times out. You have an analyzer trace. What is your procedure?

    Model answer

    Find the command's doorbell write, then the SQE fetch, check its completion status, check data movement against the PRPs, check the CQE write and MSI-X. The first missing or abnormal step assigns ownership; then corroborate with AER/IOMMU logs and controller status.

  7. (Senior) How do you explain to a firmware team that "the host never responded" may be the wrong conclusion?

    Model answer

    Show whether the request ever left the device (trace), whether it was forwarded by the switch, whether the Root Complex returned a UR/CA rather than nothing, and whether the device's completion-tracking matched the Tag. "Never responded" vs "responded with an error the device ignored" vs "device mis-matched the completion" are distinct root causes with different owners.

  8. (Senior) What would change in your trace reasoning on a Gen6 link in Flit Mode?

    Model answer

    The transaction semantics (posted/non-posted, completions, Transaction IDs, ordering) remain; the header encoding and link-level framing differ, tags can be wider, and analyzer displays decode differently. I would re-check decoding assumptions against the 6.x specification and the analyzer's decode version.

Model explanations

Child: "When you ask a question you send an empty truck with a label saying what you want and a tracking number. The answer truck comes back full, with the same number, so you know which question it answers. When you just deliver something, you do not need an answer truck."

Junior: "A doorbell is a memory write: the CPU tells the controller 'the tail moved' and needs nothing back, so it is posted and the CPU moves on immediately. An SQE fetch is a memory read: the controller needs the 64 bytes, so it is non-posted and waits for a CplD. The write costs about 22 bytes of overhead plus 4 of data and no waiting. The read costs about 26 bytes upstream, 22 plus 64 downstream, and a full memory round trip of latency."

Senior: "Against: the Tag identifies the request only together with the Requester ID; Status distinguishes success from UR/CA/CRS; Byte Count and Lower Address tell you whether this is a partial completion and where its data lands; a correct Tag with a wrong Byte Count is still a bug. The Tag is necessary, not sufficient."

Chapter summary

A TLP is PCIe's unit of transaction: a header (3 or 4 DW) saying what, where, who and which; an optional payload of whole DWs up to MPS; and an optional ECRC digest. Requests are posted (MWr, Msg) or non-posted (MRd, CfgRd/CfgWr, IORd/IOWr, AtomicOps). Non-posted requests are answered by Cpl or CplD matched by Requester ID + Tag. NVMe rides on memory reads and writes: doorbells and register accesses go down, SQE/PRP/data fetches and data/CQE/MSI-X writes go up. Linux shows the knobs that shape TLPs and the errors they cause, never the TLPs themselves.

Do not move on until you can:

  • draw the parts of a TLP and say which are optional
  • list the TLP kinds and say which are posted, non-posted or completions
  • explain how a completion finds its request
  • write the TLP sequence of an NVMe READ and an NVMe WRITE with directions
  • find the first abnormal TLP in a short trace and name its owner
  • say what Linux can and cannot show about TLPs
