One hundred and fifty intermediate interview questions on NVM Express (NVMe) over PCI Express (PCIe). Each has a model answer, what a strong answer includes, the weak answer interviewers hear most often, and the chapter that teaches it. Few of them are definitions. Most ask you to decode, calculate, read a trace, write a little code or choose what to check next.

Who this bank is for and how to use it

This bank is for engineers with roughly one to three years in storage, PCIe or firmware validation: people who have run lspci and nvme-cli, looked at an analyzer capture or two, and can explain a Submission Queue without notes. At this level an interviewer is no longer checking that you know the words. They want to see you use them: turn a hex dword into fields, turn a link speed into bytes per second, turn a log line into a next step.

What "intermediate" means here

  • Queues and commands: you can build a Submission Queue Entry (SQE) by hand and decode a Completion Queue Entry (CQE).
  • Physical Region Pages (PRP) and Scatter Gather Lists (SGL): you can fill the data pointer for any buffer layout and spot an illegal one.
  • Transaction Layer Packet (TLP) decoding: you can read a raw header and say what it is, who sent it and whether it is legal.
  • Linux tools: you know which file, command or tracepoint answers a question, and what its output does not prove.
  • Basic Advanced Error Reporting (AER): you can decode the status registers and say which layer detected an error.
  • Small coding tasks: twenty-line functions in C or Python, written carefully, with the edge cases named.

How to practise

  1. Read the question and answer it aloud or on paper before you open the model answer. Time yourself: two to four minutes per question is realistic in an interview.
  2. Open the model answer. Compare against Strong answer includes, not against the wording. If you landed on the Common weak answer, mark the question and revisit the linked chapter.
  3. For trace and coding questions, redo the arithmetic yourself. Every number in this bank can be checked from the facts given in the question.

PCIe link, physical layer and link training

Questions 1–14. Intermediate candidates are expected to turn generation and width into bandwidth, read lspci link fields without guessing, and know which Link Training and Status State Machine (LTSSM) states matter when a link misbehaves.

  1. [Calc] A server has a free PCIe Gen3 x8 slot and a free Gen4 x4 slot. Someone says "they are the same bandwidth, so it does not matter where the Gen4 x4 SSD goes." Are they right?

    Model answer

    The slots have the same raw bandwidth: Gen3 is 8 GT/s per lane and Gen4 is 16 GT/s, both with 128b/130b encoding, so 8 × 8 × 128/130 ÷ 8 ≈ 7.88 GB/s per direction for Gen3 x8 and 16 × 4 × 128/130 ÷ 8 ≈ 7.88 GB/s for Gen4 x4. But the link trains to the lower of each side's speed and the narrower of each side's width. An x4 SSD in the Gen3 x8 slot gets x4 at 8 GT/s, about 3.94 GB/s per direction: half. In the Gen4 x4 slot it gets the full 7.88 GB/s. So they are wrong. The extra lanes in the x8 slot cannot be used by an x4 device.

    Strong answer includes: the per-lane formula; the min(speed), min(width) rule; checking LnkSta afterwards to confirm what was negotiated.

    Common weak answer: "The same, 8 GB/s either way", treating slot bandwidth as something the device can use regardless of its own width.

    Learn it in: Chapter 6, Mathematics for Storage and Links.

  2. [Concept] Why did PCIe move from 8b/10b encoding (Gen1, Gen2) to 128b/130b (Gen3 to Gen5)? What did it gain and what did it cost?

    Model answer

    8b/10b sends 10 bits for every 8 data bits: 20% overhead, but it guarantees DC balance and frequent transitions for clock recovery. Going from 5 GT/s to 8 GT/s and keeping 8b/10b would have needed 10 GT/s for double the data rate, which was hard on channels. 128b/130b sends a 2-bit sync header per 128 bits (about 1.5% overhead) and relies on a scrambler for transitions and DC balance. The gain: nearly double usable bandwidth at only 1.6× the signalling rate. The costs: no special control symbols in the data stream, so framing uses tokens and ordered-set blocks; scrambling makes raw lane data unreadable without descrambling; and error detection on framing has to be designed in separately. Gen6 moved again, to PAM4 signalling with FLIT mode and forward error correction, which is a different framing model.

    Strong answer includes: the overhead numbers (80% vs about 98.5% efficiency); scrambling taking over the job of transitions; framing tokens; mentioning that Gen6 changes the model again.

    Common weak answer: "It is more efficient", with no reason why 8b/10b existed in the first place.

    Learn it in: Chapter 6, Module 07.

  3. [Trace] Here is part of lspci -vvv -s 01:00.0 for a Lab SSD (illustrative output). What do you conclude and what do you do next?

    LnkCap: Port #0, Speed 16GT/s, Width x4, ASPM L1, Exit Latency L1 <8us
LnkSta: Speed 16GT/s (ok), Width x2 (downgraded)
        TrErr- Train- SlotClk+ DLActive- BWMgmt- ABWMgmt-
    Model answer

    The device can do x4 but the link trained to x2 at full speed, so bandwidth is halved (about 3.94 GB/s). Width is negotiated in the Configuration state of the LTSSM: lanes that fail to train are dropped. Causes in rough order of likelihood: a bad contact or damaged trace on two lanes, a riser or cable that only wires x2, a slot bifurcation setting, or a lane with poor signal integrity. Next steps: check the root port's LnkCap and LnkSta too (both ends must agree on x2); check the root port's AER correctable counters for Receiver Errors; reseat or move the card to another slot to see whether the problem follows the card or the slot; check platform bifurcation settings. Note DLActive- on an endpoint is normal, because the Data Link Layer Link Active reporting bit is typically meaningful only on downstream ports.

    Strong answer includes: comparing LnkCap with LnkSta; looking at both ends; the swap test to split card from slot; not over-reading DLActive on an endpoint.

    Common weak answer: "The drive is faulty, replace it", without any test that separates drive from slot.

    Learn it in: Chapter 69, Chapter 9.

  4. [Troubleshoot] A Gen4-capable SSD in a Gen4-capable slot always comes up at 8 GT/s. List the places you would look, in order.

    Model answer

    1. LnkCap on both the root port and the SSD: if either advertises only 8 GT/s the link cannot go higher. 2. Link Control 2 Target Link Speed on the root port: firmware or a BIOS option may cap it. 3. Anything in between: a retimer, riser or cable rated for Gen3 only. 4. Equalization: a link reaches 16 GT/s only after equalization at that rate succeeds; if it fails, the ports fall back. Check the equalization-complete indications (for 8 GT/s in Link Status 2, for 16 GT/s in the Physical Layer 16.0 GT/s extended capability). 5. Kernel log messages about link speed or bandwidth notifications. Then test: move the drive to another Gen4 slot, and try a known-good Gen4 drive in this slot.

    Strong answer includes: both ends' capabilities; Target Link Speed; components in the channel; equalization as a reason to fall back; a swap experiment.

    Common weak answer: "Update the drive firmware", without first reading what each side advertises.

    Learn it in: Chapter 9, Chapter 54, Module 09.

  5. [Concept] Why does every PCIe link first reach L0 at 2.5 GT/s even when both sides support 16 GT/s? How does it then get to the higher rate?

    Model answer

    Before training, neither side knows what the other supports, and the only rate every PCIe device must support is 2.5 GT/s. So Detect, Polling and Configuration run at 2.5 GT/s, and the two ports advertise their supported rates in the training sets they exchange. Once in L0, a port initiates a speed change by entering Recovery; in Recovery the ports switch rate (and, for 8 GT/s and above, run equalization) and return to L0 at the new rate. Software can also request a retrain with a different target speed. In a capture you therefore see a short period of 2.5 GT/s traffic, then Recovery, then the higher rate.

    Strong answer includes: 2.5 GT/s as the common baseline; data rates advertised in TS1/TS2 ordered sets; speed change through Recovery; equalization at 8 GT/s and above.

    Common weak answer: "It trains directly to the highest speed."

    Learn it in: Chapter 8, Module 08.

  6. [Trace] Two LTSSM logs from the root port of the Lab SSD over the same 10 ms window. One is normal and one is worrying. Which is which?

    LogTime (µs)State sequence
    A0 → 9,800L0 → L1 → Recovery → L0 → L1 → Recovery → L0 (repeats about every 400 µs)
    B0 → 9,800L0 → Recovery → L0 → Recovery → L0 (repeats about every 300 µs; no L1)
    Model answer

    Log A is normal Active State Power Management: the link enters L1 when idle and, by design, exits L1 through Recovery back to L0. Recovery here is the wake-up path, not an error. Log B is worrying: the link goes from L0 straight into Recovery without any power-management reason. That happens when a port decides the link needs retraining, for example after repeated replays (REPLAY_NUM rollover), loss of block alignment, or receiver errors. Next steps for B: read the correctable AER status on both ends (Receiver Error, Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover), check whether the link speed or width changed after Recovery, and correlate with temperature or load. Also check whether a speed change was requested (also via Recovery), which would be benign.

    Strong answer includes: L1 exit goes through Recovery; Recovery straight from L0 needs a reason; the correctable error bits that explain it.

    Common weak answer: "Any Recovery is bad", which raises false alarms on every ASPM-enabled system.

    Learn it in: Chapter 8, Chapter 50, Trace Analysis Laboratory.

  7. [Concept] What is link equalization, why is it needed only at 8 GT/s and above, and what happens in its phases?

    Model answer

    At high rates the channel (board traces, connectors, vias) attenuates high frequencies so badly that the eye at the receiver closes. Equalization adjusts the transmitter's de-emphasis/pre-shoot (presets and coefficients) and the receiver's own equalizers to reopen it. At 2.5 and 5 GT/s a fixed de-emphasis is enough. From 8 GT/s the ports tune per link in phases: Phase 0 and Phase 1 get a working link using starting presets the downstream port communicates; in Phase 2 the upstream port tunes the downstream port's transmitter; in Phase 3 the downstream port tunes the upstream port's transmitter. Each rate (8, 16, 32 GT/s…) has its own equalization. Results are visible in Link Status 2 and the per-rate physical layer capabilities, and lane margining can show how much margin remains.

    Strong answer includes: channel loss as the reason; presets and coefficients; who tunes whom in Phases 2 and 3; per-rate equalization; margining as the follow-up tool.

    Common weak answer: "It makes the signal stronger", with no idea that each side tunes the other's transmitter.

    Learn it in: Chapter 54, Module 09.

  8. [Concept] A colleague says "an x4 link is like four separate cables, so four TLPs travel at the same time, one per lane." Correct them.

    Model answer

    A multi-lane link is one logical link. The physical layer stripes the bytes of the outgoing stream across all lanes: byte 0 on lane 0, byte 1 on lane 1, and so on, then reassembles them in order at the receiver after deskew. One TLP is therefore spread over all four lanes, and TLPs go one after another on the combined link. Adding lanes shortens each TLP's time on the wire; it does not create independent channels. This is why a link that loses a lane does not lose "one quarter of the commands", it becomes slower for everything, and why lane-to-lane skew must be corrected before any byte can be used.

    Strong answer includes: byte striping; deskew; one logical stream; consequence for bandwidth and for a lost lane.

    Common weak answer: agreeing, or saying "lanes are for redundancy".

    Learn it in: Chapter 5, Module 07.

  9. [Concept] What is the difference between a retimer and a redriver on a PCIe path to an SSD, and what does each mean for debugging?

    Model answer

    A redriver is an analog amplifier and equalizer. It is invisible to the protocol: it does not recover the clock or take part in training, and it amplifies noise along with signal. A retimer recovers the clock and data, retransmits a clean signal, and participates in link training and equalization on both of its sides, so the channel is split into two electrically separate segments. For debugging: with a retimer, a problem can be on either segment, and an analyzer placed on one side sees only that segment's electrical conditions; retimers also add a little latency. With a redriver, the channel is still electrically one piece, so settings on the redriver itself can make or break equalization.

    Strong answer includes: clock and data recovery; participation in LTSSM; two segments; where to place the analyzer.

    Common weak answer: "They both boost the signal."

    Learn it in: Chapter 5, Chapter 54.

  10. [Concept] What is the difference between a common reference clock and Separate Reference Clocks with Independent Spread Spectrum Clocking (SRIS)? Why might an SSD in an external enclosure care?

    Model answer

    With a common clock, both ends derive their bit clocks from the same 100 MHz reference, so their frequencies match exactly, even when spread spectrum clocking modulates it. With separate reference clocks, each end has its own oscillator; the receiver's elastic buffer absorbs the small frequency difference by adding or dropping SKP symbols in SKP ordered sets. With independent spread spectrum on both sides the difference can be large, so SRIS requires SKP ordered sets to be sent much more often. An SSD in an enclosure or on a cable often cannot receive the host's reference clock, so both ends must support and be configured for the same clocking mode; a mismatch shows up as receiver errors or a link that will not train reliably.

    Strong answer includes: elastic buffer and SKP ordered sets; why spread spectrum makes it harder; the configuration-must-match point.

    Common weak answer: "The clock is in the data, so it does not matter."

    Learn it in: Chapter 5, Module 07.

  11. [Concept] The root port's LTSSM stays in Detect even though an SSD is plugged in. What is Detect actually sensing, and what does staying there tell you?

    Model answer

    In Detect, the transmitter checks for a receiver termination on each lane by driving a common-mode step and measuring how fast the line charges: a terminated receiver loads the line differently from an open one. No termination detected on any lane means the port sees nothing to train with. Staying in Detect therefore points to the physical path or the device's power state, not to protocol: the SSD is not powered, its PERST# is held asserted, the connector or cable does not complete the lanes, or the device's receivers are not yet enabled. It says nothing about NVMe. Check slot power and PERST# timing, reseat, and try a known-good device.

    Strong answer includes: receiver detection by termination; Detect as a physical/power symptom; PERST#; ruling out protocol layers.

    Common weak answer: "The driver is not loaded."

    Learn it in: Chapter 8, Chapter 49.

  12. [Spec] You want to (a) retrain the link to the SSD, (b) take the link down and keep it down, and (c) send a Hot Reset to the SSD. Which register bit do you use for each, and on which device?

    Model answer

    All three are controlled from the downstream port above the SSD, here the root port 00:01.1, not from the SSD. (a) Retrain Link bit in the root port's Link Control register: the port goes through Recovery and the link returns to L0, possibly at a new speed if Target Link Speed was changed. (b) Link Disable bit in the same Link Control register: the LTSSM goes to Disabled until the bit is cleared. (c) Secondary Bus Reset bit in the root port's Bridge Control register: the port signals Hot Reset to the device below. Software should expect the device to need re-initialisation after (b) and (c), and the operating system should be told (for example via the kernel's reset interfaces) so the driver can save and restore state.

    Strong answer includes: the downstream port is the controller of all three; the three bit names; consequences for the driver.

    Common weak answer: writing these bits on the endpoint, where Retrain Link is not applicable.

    Learn it in: Chapter 49, Chapter 18.

  13. [Concept] A board designer swapped the P and N wires of one receive lane and routed the lanes to the SSD connector in reverse order. Will the link train? Where does PCIe handle each problem?

    Model answer

    Probably yes. Polarity inversion (P and N swapped) is detected by the receiver during the Polling state, when it sees inverted training sets, and corrected by inverting the received data on that lane. Support for polarity inversion is required. Lane reversal (lane 0 connected to lane 3 and so on) is handled in the Configuration state, when lane numbers are negotiated; support for it is optional on each component, so it works only if at least one side supports it. Neither fixes arbitrary lane scrambling (lanes in a random order). A designer should still document such choices, because an analyzer interposer must decode the lanes the same way.

    Strong answer includes: Polling for polarity, Configuration for lane numbers; polarity inversion required, lane reversal optional; random permutation is not supported.

    Common weak answer: "No, the board must be respun", or "yes, PCIe can fix any wiring".

    Learn it in: Chapter 8, Module 08.

  14. [Calc] On the Lab SSD's Gen4 x4 link, how long does one MWr TLP carrying 256 bytes of read data (4DW header) occupy the wire, and what fraction of that time is payload?

    Model answer

    Bytes on the link: 16-byte header + 256-byte payload + about 8 bytes of Data Link and framing overhead (in non-Flit 128b/130b mode, a 4-byte start-of-TLP token that carries the length and sequence number, plus the 4-byte LCRC) = about 280 bytes; add 4 more if ECRC is used. Link rate: 16 GT/s × 4 lanes × 128/130 ÷ 8 ≈ 7.88 GB/s. Time: 280 ÷ 7.88 GB/s ≈ 35.5 ns. Payload fraction 256 ÷ 280 ≈ 91%, so the payload ceiling is about 7.2 GB/s, before Data Link Layer Packets (DLLPs) such as ACKs and flow-control updates take their share. With MPS 512 the fraction would be about 95%. Derived

    Strong answer includes: header, framing and LCRC counted; the encoding factor; the payload efficiency; the effect of MPS; DLLPs as further overhead.

    Common weak answer: 256 ÷ 8 GB/s = 32 ns, ignoring every overhead.

    Learn it in: Mathematics for Storage and Links, Performance Engineering.

TLPs, completions, tags and ordering

Questions 15–32. Expect to be handed raw header dwords. Know the first-dword layout cold (Fmt, Type, Length), the second dword of a request (Requester ID, Tag, Last and First Byte Enables) and of a completion (Completer ID, Status, Byte Count), and the rules that make a TLP legal.

  1. [Trace] An analyzer shows these three header dwords and one data dword travelling host to device on the Lab SSD's link. Decode them.

    DW0 0x4000_0001   DW1 0x0000_000F   DW2 0xFE60_100C   Data 0x0000_0011
    Model answer

    DW0: Fmt = 010 (3DW header with data) and Type = 0_0000, so the first byte 0x40 is a 32-bit Memory Write (MWr32); Length = 1 DW. DW1: Requester ID 0x0000 (the root complex side; the exact value is platform-dependent), Tag 0x00 (tags carry no meaning for posted writes), Last BE = 0 (required for a 1-DW request) and First BE = 0xF (all four bytes). DW2: address 0xFE60_100C. With BAR0 at 0xFE60_0000 that is offset 0x100C, which with a 4-byte doorbell stride is the CQ1 head doorbell. Data 0x11 = 17: the host has consumed CQ1 entries up to index 16 and the next entry it expects is index 17. It is posted, so there is no completion to look for. A 3DW header is used because the address is below 4 GiB.

    Strong answer includes: Fmt/Type → MWr32; byte enables and the 1-DW rule; offset → CQ1 head doorbell via the stride; what the value means; no completion.

    Common weak answer: "It's a doorbell" without saying which one or what the value means.

    Learn it in: Chapter 11, Chapter 28, TLP Header Decoder.

  2. [Trace] Now device to host: DW0 0x2000_0010, DW1 0x0100_21FF, DW2 0x0000_0001, DW3 0x2340_0040. What is the Lab SSD doing?

    Model answer

    First byte 0x20: Fmt = 001 (4DW, no data), Type = 0_0000, a 64-bit Memory Read (MRd64). Length 0x010 = 16 DW = 64 bytes. DW1: Requester ID 0x0100 (01:00.0, the SSD), Tag 0x21, Last BE 0xF, First BE 0xF. Address = DW2:DW3 = 0x0000_0001_2340_0040. SQ1's base is 0x1_2340_0000, and each Submission Queue entry is 64 bytes, so offset 0x40 is slot 1. The controller is fetching one SQE from slot 1 of I/O SQ1, which means a doorbell moved the SQ1 tail past 1 shortly before. Expect a CplD with Requester ID 0x0100 and Tag 0x21 to come back carrying the 64 bytes.

    Strong answer includes: MRd64 because the address is above 4 GiB; length in bytes; tag matching for the completion; mapping address → queue → slot.

    Common weak answer: decoding the fields correctly but not connecting the address to SQ1 slot 1.

    Learn it in: Chapter 41, Module 11.

  3. [Trace] The answer to the previous read arrives: DW0 0x4A00_0010, DW1 0x0000_0040, DW2 0x0100_2140, followed by 64 bytes of data. Decode it and say how the SSD knows it belongs to its read.

    Model answer

    First byte 0x4A: Fmt = 010 (3DW with data), Type = 0_1010: Completion with Data (CplD). Completions always use a 3DW header. Length 16 DW. DW1: Completer ID 0x0000 (the root complex; platform-dependent), Completion Status = 000 (Successful Completion), BCM = 0, Byte Count = 0x040 = 64 bytes remaining including this one, so this single completion finishes the request. DW2: Requester ID 0x0100, Tag 0x21, Lower Address 0x40 (the low 7 bits of the starting byte address). The SSD matches it using Requester ID plus Tag: completions are routed by ID back to 01:00.0, and the controller looks up tag 0x21 in its table of outstanding reads. Lower Address and Byte Count let it place the bytes and know when the read is complete.

    Strong answer includes: CplD encoding; Byte Count meaning "remaining", not "in this TLP"; Lower Address; ID routing; tag lookup.

    Common weak answer: "Byte Count is the payload size", which breaks as soon as a read is split.

    Learn it in: Chapter 52, Module 12.

  4. [Calc] A requester must write exactly 6 bytes starting at byte address 0x2_0000_0102. What are the Length, First BE and Last BE fields?

    Model answer

    The TLP address is dword-aligned, so it is 0x2_0000_0100 and the first dword covers bytes 0x100–0x103. The write starts at 0x102, so in the first dword only bytes 2 and 3 are written: First BE = 1100b = 0xC. Two bytes are done, four remain: bytes 0x104–0x107, the whole second dword: Last BE = 1111b = 0xF. Length = 2 DW. The payload is 8 bytes on the wire, but the byte enables tell the completer that bytes 0x100 and 0x101 must not be modified. Byte enables are how PCIe expresses writes that are not dword-aligned in start or length.

    Strong answer includes: dword-aligned address; bit-per-byte meaning of the enables; Length counts dwords touched; Last BE non-zero for multi-dword requests.

    Common weak answer: Length = 6 bytes, or First BE = 0x3 (reversed bit order).

    Learn it in: Chapter 11, Module 11.

  5. [Spec] A controller emits MWr64 Addr=0x2_0000_0F80 Len=64 DW for read data. Is that legal? If not, what happens and what should it have done?

    Model answer

    Not legal. 64 DW is 256 bytes, so the write covers 0x2_0000_0F80 to 0x2_0000_107F, which crosses the 4 KiB boundary at 0x2_0000_1000. A memory request must not cross a 4 KiB address boundary. The receiver (the root port) should treat it as a Malformed TLP, an uncorrectable error that is fatal by default, and log it in AER with the header. The controller should split it at the boundary: 128 bytes at 0x2_0000_0F80 and 128 bytes at 0x2_0000_1000. With NVMe this situation arises when PRP1 has an offset (for example 0xF80) and the controller's data engine forgets to align its chunks to page and 4 KiB boundaries. Such a bug often passes tests that only use page-aligned buffers.

    Strong answer includes: the 4 KiB rule; the arithmetic; Malformed TLP and its default severity; the correct split; why aligned-buffer tests miss it.

    Common weak answer: "Fine, it is within MPS."

    Learn it in: Chapter 11, Chapter 45.

  6. [Spec] A device sends MRd64 with address 0x0000_0000_8000_1000 (upper dword zero). Is a 4DW header allowed here?

    Model answer

    No. For addresses below 4 GiB a requester must use the 32-bit (3DW) format; the 64-bit format with the upper address bits all zero is not permitted. What the receiver does with such a TLP is a separate question: the PCI Express Base Specification has long left receiver behaviour for this case undefined, and some receivers treat it as malformed while others accept it. Uncertain The exact wording has changed across revisions, so check the revision you are designing to. The practical rule is: never generate it, and do not depend on any particular receiver tolerating it. In a trace, 4DW headers for addresses below 4 GiB are a red flag for a requester bug even when nothing fails.

    Strong answer includes: the requester rule; separating requester rule from receiver behaviour; checking the revision; spotting it as a latent bug.

    Common weak answer: "It's fine, the upper bits are zero."

    Learn it in: Chapter 11, Specification Reading School.

  7. [Trace] The SSD reads 512 bytes of write data from host address 0x2_0000_0020 (RCB 64, MPS 256). The root complex answers with the completions below. Which one is illegal, and why?

    #DirTypeFieldsCovers
    1Dev→HostMRd64Addr=0x2_0000_0020 Len=128 DW Tag=0x30request, 512 bytes
    2Host→DevCplDLen=56 DW ByteCount=512 LowerAddr=0x20 Tag=0x300x020–0x0FF (224 B)
    3Host→DevCplDLen=60 DW ByteCount=288 LowerAddr=0x00 Tag=0x300x100–0x1EF (240 B)
    4Host→DevCplDLen=12 DW ByteCount=48 LowerAddr=0x70 Tag=0x300x1F0–0x21F (48 B)
    Model answer

    Completion 3 is the first abnormal event. When a completer splits a read into several completions, each completion except the last must end on a naturally aligned RCB boundary (64 bytes here). Completion 2 ends at 0x100, which is aligned; completion 3 ends at 0x1F0, which is not a multiple of 64 and is not the end of the request. A legal split would be 0x020–0x0FF (224 B, Byte Count 512, Lower Address 0x20), 0x100–0x1FF (256 B, Byte Count 288, Lower Address 0x00) and 0x200–0x21F (32 B, Byte Count 32, Lower Address 0x00). The Byte Count values in the trace are internally consistent (512, 288, 48), which is why a quick look misses the error. No completion may exceed MPS (256), so at least three completions are needed anyway.

    Strong answer includes: the RCB rule; the MPS limit on completion payload; recomputing Byte Count and Lower Address; marking the first abnormal row.

    Common weak answer: "All fine, the bytes add up to 512."

    Learn it in: Chapter 52, Module 12.

  8. [Concept] Why does reading any controller register after writing a doorbell guarantee that the doorbell write has reached the controller? Which ordering rule makes this work?

    Model answer

    The doorbell MWr is posted: the CPU does not wait for it. The register read is a non-posted MRd sent along the same path afterwards. PCIe ordering does not allow a non-posted request to pass a posted request in the same direction (with the default attributes), so the read cannot reach the controller before the write. The read's completion cannot come back until the read has arrived and been serviced, so when the CPU receives the completion, the earlier write has arrived too. This is the classic "read to flush posted writes" pattern. It costs a full round trip (around a microsecond or more), which is why NVMe drivers do not do it on every doorbell and rely on the controller simply acting on the doorbell when it arrives.

    Strong answer includes: posted vs non-posted; the "non-posted must not pass posted" rule; the round-trip cost; why the normal I/O path does not do this.

    Common weak answer: "Reads are slower, so the write gets there first."

    Learn it in: Chapter 14, Chapter 12.

  9. [Spec] The SSD has two reads outstanding, tags 0x10 and 0x11. Can the completions for 0x11 arrive before those for 0x10? Can the completions of one split read arrive out of address order?

    Model answer

    Completions for different requests can arrive in any order: the root complex may service tag 0x11 first, for example because its data was in cache. The requester must use the tag to match each completion and must not assume order between tags. Within one request that is split into several completions, the completions are returned in increasing address order, which is what lets the Byte Count count down monotonically. So 0x11 before 0x10 is legal; the second half of 0x10 before its first half is not. A controller whose data engine assumes in-order completions across tags works on a simple test platform and fails on servers with more parallel memory controllers.

    Strong answer includes: no ordering across tags; address order within a request; tag-based reassembly; the platform-dependence trap.

    Common weak answer: "PCIe is in order, so completions come back in the order requested."

    Learn it in: Chapter 52, Chapter 13.

  10. [Performance] A device can use only 32 outstanding read tags. MRRS is 512 bytes and the read round trip (MRd out to last CplD back) is 2 µs. What is the maximum read bandwidth it can sustain? What if MRRS were 128 bytes?

    Model answer

    Bytes in flight at most = tags × request size = 32 × 512 = 16 KiB. Bandwidth = bytes in flight ÷ round-trip time = 16,384 B ÷ 2 µs ≈ 8.2 GB/s. That is just above the Gen4 x4 payload ceiling (about 7.2 GB/s), so tags are barely sufficient and any increase in latency makes them the bottleneck. With MRRS 128: 32 × 128 = 4 KiB in flight, ≈ 2.0 GB/s, a hard ceiling far below the link. For an NVMe SSD this is the Write path, because the controller reads write data from host memory. The fix is more tags (8-bit or 10-bit tags where both sides support them) or larger MRRS, and verifying the read latency the platform actually delivers. Derived

    Model answer

  13. [Concept] What is a zero-length read, how is it encoded, and why would a device issue one?

    Model answer

A device can use it to make sure its earlier memory writes have arrived before it does something else, though for NVMe the normal guarantee (CQE written after data, posted writes kept in order) usually makes this unnecessary.

  16. [Spec] What does the Completion Timeout mechanism look like from the SSD's side? Where is the timeout range configured and what is the usual default?

    Model answer

    When the SSD (as requester) issues a non-posted request such as an MRd, it starts a timer; if not all completions arrive within the timeout, it logs a Completion Timeout as an uncorrectable error (non-fatal by default) and must handle the lost data, for example by failing the NVMe command. The range is controlled in the Device Control 2 register: a Completion Timeout Value field selects one of the ranges the device advertises in Device Capabilities 2, and a Completion Timeout Disable bit may be offered. The default range is 50 µs to 50 ms. A short setting on a platform with long memory latency under load gives false timeouts; a long setting delays recovery.

    Strong answer includes: requester-side detection; Device Control 2 and Device Capabilities 2; default range; the tradeoff.

    Common weak answer: "The host's NVMe driver times out after 30 seconds", which is a different timeout at a different layer.

  17. [Troubleshoot] On a new platform, the analyzer shows the SSD's DMA requests carrying Requester ID 0x0000 instead of 0x0100, and every one faults in the IOMMU. How can a device end up with the wrong Requester ID?

    Model answer

    An endpoint does not know its bus number from birth. It captures its Bus and Device Number from the Type 0 Configuration Write requests addressed to it, and uses them as its Requester ID. If, after a reset, the device sends DMA before it has received any configuration write, or firmware failed to latch the captured value (for example after a Function Level Reset or a firmware activation), it may use 0x0000. The IOMMU looks up translations by Requester ID, finds no context for 0x0000, and blocks every request. Evidence: capture the configuration writes after reset and the first DMA; compare the IDs; check whether the problem appears only after a particular reset type. Root cause is usually in device firmware, but the platform's reset sequence is part of the test.

    Strong answer includes: ID capture from Type 0 configuration writes; IOMMU lookup by Requester ID; the reset-sequence angle; the capture that proves it.

    Common weak answer: "The IOMMU is misconfigured", without asking why the ID is wrong.

  18. [Concept] PCIe ordering lets a posted write pass an earlier non-posted request that is stuck. Why is that permission required rather than merely allowed? Give a scenario involving an SSD.

    Model answer

    Without it, the fabric can deadlock. Suppose a switch or root port queue holds a non-posted MRd from the SSD that cannot make progress because the target's non-posted buffers are full, and the target cannot free them until it can send its own posted writes (for example data and completion-queue writes heading the same way). If posted writes were stuck behind the MRd, nothing would move. So the ordering rules require that posted requests be able to pass non-posted requests (and completions) when those are blocked, and flow control keeps separate credit pools for posted, non-posted and completion traffic to make this possible. What posted writes may not do (with default attributes) is pass other posted writes, which is what keeps NVMe data ahead of its CQE.

    Strong answer includes: deadlock avoidance as the reason; separate credit classes; contrast with posted-after-posted ordering that NVMe relies on.

    Common weak answer: "For performance."

    Learn it in: Chapter 14, Chapter 51, Module 14.

Data Link Layer, replay and flow control

Questions 33–44. The Data Link Layer is where intermittent link trouble hides: replays that nobody logged, credits that throttle throughput without any error. Intermediate candidates should know ACK/NAK sequence arithmetic, credit units and what is and is not retried.

  1. [Trace] The SSD's replay buffer holds TLPs with sequence numbers 0x100 to 0x10A. An ACK DLLP with sequence number 0x105 arrives. What happens?

    Model answer

    An ACK acknowledges every TLP up to and including the sequence number it carries. The transmitter purges 0x100–0x105 from its replay buffer and resets its replay timer (because unacknowledged TLPs remain). 0x106–0x10A stay buffered until a later ACK covers them. ACKs are cumulative, so a receiver does not have to send one per TLP; seeing one ACK for several TLPs in a capture is normal. If the ACK carried a number outside the range of TLPs actually sent (for example 0x0F0 or 0x150), that would be a Data Link Layer protocol violation.

    Strong answer includes: cumulative acknowledgement; buffer purge; replay timer reset; what an out-of-range ACK means.

    Common weak answer: "Only TLP 0x105 is acknowledged."

    Learn it in: Chapter 15, Module 16.

  2. [Trace] Same buffer (0x100–0x10A), but now a NAK with sequence number 0x103 arrives. What is replayed, and in what order? Did TLP 0x104 arrive?

    Model answer

    A NAK carries the sequence number of the last TLP received correctly. So 0x100–0x103 are acknowledged and purged, and the transmitter replays every TLP from 0x104 to 0x10A, in the original order, including any it had already sent after 0x104. TLP 0x104 either arrived corrupted (LCRC failure) or something before it in the stream failed; the receiver discards everything after the bad TLP until the replay brings 0x104 again, because it accepts TLPs only in sequence. In a capture you see the original 0x104–0x10A, the NAK, then 0x104–0x10A again. The analyzer marks the replays; the upper layers never see duplicates.

    Strong answer includes: NAK sequence = last good; replay from the next one; in-order replay of all later TLPs; why duplicates never reach the Transaction Layer.

    Common weak answer: "Only 0x103 is resent."

    Learn it in: Chapter 15, Module 16.

  3. [Concept] What do the Replay Timer and the REPLAY_NUM counter do, and what happens when REPLAY_NUM rolls over?

    Model answer

    The Replay Timer covers lost ACKs and NAKs: if the oldest unacknowledged TLP has waited too long, the transmitter replays the buffer as if it had received a NAK, and logs a Replay Timer Timeout correctable error. REPLAY_NUM is a small counter (two bits) of how many times the same buffer content has been replayed without forward progress. When it rolls over, the transmitter concludes the link itself is unhealthy, logs a REPLAY_NUM Rollover correctable error, and has the physical layer retrain the link by entering Recovery. Any ACK that makes progress resets REPLAY_NUM. So persistent link trouble escalates: replays, then a retrain, and if retraining fails, the link goes down (which software sees as a Surprise Down or a dead device).

    Strong answer includes: what each one detects; both are correctable; rollover triggers Recovery; the escalation path.

    Common weak answer: "Replay Timer is a completion timeout", confusing Data Link and Transaction Layers.

    Learn it in: Module 16, Chapter 55.

  6. [Performance] The root port advertises 64 Posted Data credits to the SSD and returns UpdateFC DLLPs about 500 ns after it frees buffer space. Ignoring headers, what is the most read-data bandwidth the SSD can push?

To keep the link busy, advertised credit must cover bandwidth × credit-loop time: 7.2 GB/s × 500 ns ≈ 3.6 KB, so about 225 PD credits or more.   7. [Spec] Endpoints advertise infinite completion credits. Then what stops a root complex from flooding an SSD with more completion data than it can buffer?

    Model answer

    The SSD itself. Completions only come back for reads the SSD asked for, so the SSD controls the total. Before issuing a read, it must reserve receive buffer space for the full completion data (and headers) that read can return. Advertising infinite completion credits means the link partner never has to wait for completion credits, which avoids a class of deadlock where completions cannot drain, but it moves the responsibility to the requester: never have more read data outstanding than you can absorb. A device that over-issues reads and then cannot accept the completions would see Receiver Overflow, an uncorrectable error. In a trace, the SSD's MRd issue pattern is effectively its own flow control.

    Strong answer includes: the requester reserves space before issuing; deadlock avoidance; Receiver Overflow as the failure; outstanding-read limits as self-throttling.

    Common weak answer: "Infinite credits means unlimited buffer."

  8. [Concept] The LTSSM reports L0, but no TLPs flow and the downstream port shows the Data Link Layer is not active. What is happening between L0 and DL_Active, and what could block it?

    Model answer

    L0 means the physical layer is trained. The Data Link Layer then runs flow-control initialisation: each side sends InitFC1 DLLPs for posted, non-posted and completion credits, then InitFC2 to confirm, and only when both sides have exchanged them does the link become DL_Active and TLPs are allowed. If that never finishes, likely causes are DLLPs being corrupted (Bad DLLP errors), a device whose firmware or Data Link Layer is not running yet, or a protocol error in the exchange. Evidence: capture the DLLPs after L0; look for InitFC1 from one side only, or repeated Bad DLLP. A link stuck here looks "up" in LTSSM terms but cannot carry configuration requests, so enumeration fails.

    Strong answer includes: InitFC1/InitFC2; DL_Init vs DL_Active; L0 not being sufficient; what to capture.

    Common weak answer: "If it's L0 the link works."

  9. [Calc] The root port typically returns an ACK about 1 µs after it receives a TLP. How big must the SSD's replay buffer be to keep transmitting read data at full Gen4 x4 rate without stalling?

    Model answer

    Every transmitted TLP must stay in the replay buffer until acknowledged. At full rate the SSD sends about 7.88 GB/s of link bytes (including headers and framing). In 1 µs of acknowledgement latency that is about 7.9 KB, so the buffer needs to hold at least roughly 8 KB, plus margin for ACK coalescing and the time for the ACK DLLP itself to travel: in practice designers size it noticeably larger. A smaller buffer makes the transmitter stall until ACKs arrive, which looks like throughput loss with gaps in the trace but no errors.   10. [Concept] Are DLLPs acknowledged and replayed like TLPs? What happens if an UpdateFC DLLP is corrupted?

    Model answer

    No. DLLPs are small (4 bytes of content plus a 16-bit CRC), are not given sequence numbers, are not stored in the replay buffer and are not acknowledged. A corrupted DLLP is simply discarded and counted as a Bad DLLP correctable error. The protocol is designed so that loss is harmless: UpdateFC carries the absolute credit limit, not an increment, so the next UpdateFC repairs any loss, and ports send UpdateFC periodically even without new credit. A lost ACK is covered by the next ACK (cumulative) or by the replay timer. This is why Bad DLLP errors cost a little performance but no data.

    Strong answer includes: no sequence numbers or replay for DLLPs; absolute credit values; periodic UpdateFC; cumulative ACKs.

    Common weak answer: "They are retransmitted with a NAK."

Configuration, enumeration, BARs and DMA

Questions 45–60. Before any NVMe command runs, the platform must find the SSD, give it addresses and allow it to master the bus; and every address the SSD later uses passes through the Input-Output Memory Management Unit (IOMMU). These questions check that you can do the arithmetic and read the evidence.

  1. [Calc] During enumeration, software writes all ones to the Lab SSD's BAR0 and BAR1 and reads back BAR0 = 0xFFFF_C004, BAR1 = 0xFFFF_FFFF. What kind of BAR is it and how big?

    Model answer

    Look at the low bits of BAR0 first. Bit 0 = 0: memory space. Bits 2:1 = 10b: 64-bit BAR, so BAR1 holds the upper 32 address bits and BAR0/BAR1 form one register pair. Bit 3 = 0: non-prefetchable. Mask the low four type bits: 0xFFFF_C000, combined with the upper dword 0xFFFF_FFFF gives 0xFFFF_FFFF_FFFF_C000. Size = two's complement = 0x4000 = 16 KiB. Software then writes a 16 KiB-aligned address (0xFE60_0000 on the lab system, with BAR1 = 0) and restores Memory Space Enable. Because the BAR is non-prefetchable, it must be placed in a bridge's non-prefetchable memory window, and the Type 1 header's non-prefetchable Memory Base/Limit registers describe only 32-bit addresses, so it lands below 4 GiB even though it is a 64-bit BAR.

    Strong answer includes: decoding the type bits before the size; combining the pair; two's complement; alignment; why it sits below 4 GiB.

    Common weak answer: treating 0xFFFF_C004 as the size, or forgetting BAR1.

    Learn it in: Chapter 19, Module 06.

  2. [Calc] The platform's Enhanced Configuration Access Mechanism (ECAM) region starts at 0xE000_0000 for bus 0. What memory address does the CPU read for (a) offset 0x10 of 01:00.0 and (b) offset 0x18 of 00:01.1?

    Model answer

    ECAM gives each function 4 KiB: address = base + (bus << 20) + (device << 15) + (function << 12) + offset. (a) 01:00.0 offset 0x10: 0xE000_0000 + 0x10_0000 + 0 + 0 + 0x10 = 0xE010_0010, which is BAR0 of the SSD. (b) 00:01.1 offset 0x18: 0xE000_0000 + 0 + (1 << 15 = 0x8000) + (1 << 12 = 0x1000) + 0x18 = 0xE000_9018, which in a Type 1 header holds the Primary, Secondary and Subordinate Bus Numbers of the root port. The CPU's read of that memory address is turned by the root complex into a configuration request; for the SSD, the root port sends it on as a Type 0 CfgRd because bus 1 is its secondary bus.

    Strong answer includes: the bit layout (8 bus, 5 device, 3 function, 12 offset); the arithmetic; what each offset holds; that the CPU access becomes a configuration TLP.

    Common weak answer: using 256 bytes per function (the legacy CF8/CFC layout), which cannot reach extended space.

    Learn it in: Chapter 18, Module 05.

In Linux a driver calls pci_set_master(); a user-space driver must set the bit itself (for example through VFIO or setpci). Check with lspci -vvv: the Control line shows BusMaster+ or BusMaster-.

    Strong answer includes: Memory Space Enable vs Bus Master Enable; which works proves which; where to see it.

    Common weak answer: "The doorbell offset is wrong", which is worth checking second.

  4. [Trace] Right after a reset of the SSD, a configuration read of its Vendor ID returns 0x0001. There is no vendor with that ID. What is going on?

    Model answer

    The SSD is not ready yet and is answering configuration requests with Configuration Request Retry Status (CRS). When CRS Software Visibility is enabled in the root port, a CRS completion for a read of the Vendor ID is reported to software as the special value 0x0001 instead of being retried in hardware, so software can poll and do other work meanwhile. Software should keep polling (within the timeouts the platform allows) until it reads the real Vendor ID. Seeing 0x0001 for a long time after reset means the SSD's firmware is slow to come up; it should be compared with the readiness timing the platform expects.

    Model answer

If there were a switch below with buses 2–4, Subordinate would be 4 and the port would forward bus-2 requests unchanged as Type 1, for the switch to convert.   11. [Concept] What is a DMA mask, and what would happen to NVMe performance on a system where the SSD's driver could only use a 32-bit mask?

    Model answer

    The DMA mask tells the kernel the range of addresses the device can generate. NVMe controllers handle 64-bit addresses, and the Linux driver requests a 64-bit mask. If only 32-bit were possible (a broken platform, a quirk, or some IOMMU configurations), buffers above 4 GiB could not be given to the device directly. Without an IOMMU to remap them, the kernel would use bounce buffering (swiotlb): copy data through a buffer below 4 GiB. That adds a memory copy per I/O, raises CPU use and latency, and caps throughput at memory-copy speed. With an IOMMU, the kernel can instead allocate IOVAs below 4 GiB and map them anywhere, at the cost of IOVA space pressure. A trace would show device addresses all below 4 GiB, so 3DW MRd/MWr headers for data.

    Strong answer includes: mask meaning; bounce buffers; IOMMU as the alternative; the observable trace change.

    Common weak answer: "The SSD would only see 4 GiB of capacity", confusing host memory with storage capacity.

  12. [Concept] Why does an NVMe driver allocate its queues with coherent DMA memory but map data buffers per I/O with streaming mappings? What would break on a platform without hardware cache coherency if it got this wrong?

    Model answer

    Queues are long-lived and shared continuously: the CPU writes SQEs and reads CQEs while the device does the opposite. Coherent (consistent) DMA memory guarantees both sides see each other's writes without explicit cache maintenance. Data buffers belong to one I/O for a short time, so they are mapped for that I/O (with a direction) and unmapped afterwards; on non-coherent platforms the map and unmap operations perform the cache clean or invalidate. If queues were in ordinary cached memory on a non-coherent system, the device might fetch a stale SQE from memory while the new one sat in the CPU cache, or the CPU might poll a stale cached CQE and never see the phase tag change: classic "the device wrote it but the driver never saw it" hangs. On x86, DMA is cache-coherent, so such bugs stay hidden until the code runs on another architecture.

    Strong answer includes: lifetime and sharing pattern; who does cache maintenance; the two failure modes; why x86 hides it.

    Common weak answer: "Coherent memory is faster."

    Learn it in: Chapter 20, Module 36.

  4. [Concept] List the controller initialisation steps from "driver loads" to "first I/O command can be issued", and say why the order matters.

    Model answer
    1. Map BAR0, read CAP and VS. If CC.EN is 1, clear it and wait for CSTS.RDY = 0 (up to CAP.TO).

    The driver does not invert its expected phase when its head index wraps. On the first pass the controller writes Phase = 1 into each entry (the queue memory starts zeroed).   12. [Troubleshoot] A test driver processes CQEs correctly but never writes the CQ head doorbell. What happens and after how long on CQ1?

    Model answer

    The controller only knows which CQ slots are free from the head doorbell. Without it, the controller thinks the host has consumed nothing. CQ1 has 1024 entries, and a queue is full when one slot remains, so after about 1023 completions the controller considers CQ1 full and must not post more completions into it: it will not overwrite unconsumed entries. Commands keep executing internally but their completions cannot be posted, so I/O stops and the host times out. Because SQs completing into that CQ can also stall, the effect spreads to every SQ sharing it. Some controllers may additionally report an error through an asynchronous event. A trace shows the last CQE MWr, then silence while doorbell tail writes continue. Implementation-dependent Exactly when internal execution stops is up to the controller.

    Strong answer includes: head doorbell frees slots; the N − 1 limit; no overwriting; the trace signature.

    Common weak answer: "Nothing, the head doorbell is optional."

  13. [Spec] A buggy driver writes the value 1500 to the SQ1 tail doorbell (SQ1 has 1024 entries), and another write goes to the doorbell of SQ 7, which was never created. How does an NVMe controller report these?

The host then reads the Error Information log page to clear the event. This only works if the host keeps an Asynchronous Event Request outstanding. Controller behaviour beyond reporting (ignore the write, or stop processing that queue) varies, so the exact consequences belong in the specification text and the controller's documentation. Implementation-dependent

  15. [Concept] What are round-robin and weighted round robin with urgent priority arbitration in NVMe? When would you use the second, and why do many hosts not bother?

    Model answer

    Arbitration decides which SQ the controller fetches from next. Round robin, which every controller supports, treats all I/O SQs equally (taking up to Arbitration Burst commands from each in turn); the admin SQ always has highest priority. Weighted round robin with urgent priority class, optional and advertised in CAP.AMS, adds an urgent class served strictly first, then high, medium and low classes served in proportion to weights set with the Arbitration feature. Each SQ's class is set by QPRIO at creation, and the host selects the mechanism with CC.AMS. You would use it to protect latency-critical traffic (a database log) from bulk traffic on the same drive. Many hosts skip it because it is optional, Linux maps queues per CPU rather than per priority, and arbitration only affects fetch order, not internal scheduling once a command is fetched.

    Strong answer includes: fetch-order scope; CAP.AMS/CC.AMS/QPRIO; urgent as strict priority; the limits of the mechanism.

    Common weak answer: "WRR makes urgent commands complete first", ignoring what happens inside the controller after fetch.

    Learn it in: Chapter 25, Module 26.

  16. [Troubleshoot] A reset path writes CC.EN = 0 and then, in the next instruction, writes CC.EN = 1 with new settings. On some drives the controller ends up in a strange state. Why?

    Model answer

    Clearing EN starts a controller reset, which is complete only when CSTS.RDY reads 0. The host must wait for that (up to CAP.TO) before writing EN = 1 again. Writing EN = 1 while RDY is still 1 means the host is enabling a controller that has not finished resetting: the specification does not define a good outcome for this, and controllers differ: some ignore the write, some finish the reset and then never enable, some latch the new settings at the wrong moment. Fast controllers make the bug invisible because RDY falls almost immediately. Fix: poll CSTS.RDY to 0 with a timeout derived from CAP.TO, and handle CSTS.CFS or an all-ones read (device gone) during the poll.

    Strong answer includes: the RDY-0 wait; CAP.TO; why timing differences hide it; handling all-ones.

    Common weak answer: "Add a sleep(1)", which is fragile on slow controllers and wasteful on fast ones.

  17. [Concept] Describe a normal NVMe shutdown, and what the SMART "Unsafe Shutdowns" counter tells you if it increments on every reboot.

    Model answer

    For a normal shutdown the host stops issuing I/O, optionally deletes I/O queues, writes CC.SHN = 01b (normal shutdown notification), then polls CSTS.SHST until it reads 10b (shutdown processing complete) before removing power. The time to allow is guided by RTD3 Entry Latency in Identify Controller (or a host default if it reports 0). During shutdown the controller flushes volatile caches and saves its internal metadata. If Unsafe Shutdowns increments on every reboot, the host is cutting power before shutdown completes: the OS is not sending the notification, is not waiting long enough (a timeout shorter than the drive's real requirement), or a platform power sequence removes power too early. Consequences: longer start-up (metadata rebuild), possible loss of cached data, and extra wear.

    Strong answer includes: SHN and SHST values; RTD3 Entry Latency; what the counter means; the three host-side causes.

    Common weak answer: "Unsafe shutdowns mean the drive is failing."

    Learn it in: Chapter 48, Chapter 57.

  18. [Trace] A user-space driver sets ASQ and ACQ to the same address by mistake. The first Identify completes, but the next command fails oddly. What does the trace show and why?

    Model answer

    The controller fetches admin SQE slot 0 from address X and later writes the 16-byte CQE for it to ACQ slot 0, which is also X. That overwrites the first 16 bytes of SQ slot 0. The first command already ran, so it "works". As the driver fills SQ slots 1, 2… the controller's CQE writes to X + 16, X + 32… land inside SQ slot 0, while the driver's SQEs at X + 64… may be overwritten by later CQEs (CQ slot 4 is at X + 64). Commands become a mix of SQE and CQE bytes: odd opcodes, wrong CIDs, Invalid Field or Invalid Command Opcode statuses. In a trace, the CQE MWr64 addresses overlap the SQE MRd64 addresses: compare them and it is obvious. The controller is not required to detect this. Always check that queue regions do not overlap.

    Strong answer includes: overlapping addresses in the trace; why the first command survives; that the controller cannot be expected to catch it.

    Common weak answer: "Firmware bug in Identify."

  19. [Performance] A driver rings the SQ tail doorbell once per command. A colleague proposes ringing it once per batch of 16. What do you gain and what do you risk?

    Model answer

    Gain: fewer MMIO writes (each is an uncached write the CPU must post, and each causes the controller to wake its fetch logic), and the controller can fetch several SQEs in one larger MRd. At high IOPS this saves noticeable CPU per I/O. Risk: latency for the first command of the batch, which waits until the batch is full or a flush point is reached; at low queue depth a batch might never fill, so a timer or "last request in this submission" flag is needed. Linux block layer does exactly this: the driver is told whether a request is the last of the current batch and rings the doorbell then. Correctness rule: the doorbell is written only after all SQEs it covers are fully written (with a write barrier between).

    Strong answer includes: MMIO cost; larger fetches; first-command latency; a flush condition; the barrier rule.

    Common weak answer: "Always better", ignoring the latency of an unfilled batch.

    Learn it in: Chapter 28, Performance Engineering.

  20. [Spec] May the controller fetch SQEs beyond the tail value the host last wrote? May the host change an SQE after ringing the doorbell?

    Model answer

    No and no. The tail doorbell is the host's statement that entries up to (but not including) the tail slot are valid. The controller may fetch any entries between its head and that tail, in batches, at a time of its choosing, but must not consume entries at or beyond the tail, because those may be half-written. On the host side, once a slot is published by the doorbell, the host must not modify it until the controller has consumed it, which the host learns from the SQ Head Pointer in a later CQE. The controller may fetch the entry at any moment, so a late change is a race that produces a mix of old and new bytes. Prefetching speculatively past the tail would be a controller bug that only shows when the host writes SQEs slowly.

    Strong answer includes: tail as the publication point; fetch timing freedom; SQ Head as the release signal; the race.

    Common weak answer: "The host can reuse the slot after the command completes", which is right but late; the SQ head says when the slot is reusable.

    Learn it in: Chapter 25, Module 27.

    Model answer

    NLB is the number of logical blocks minus one. (a) 4096 ÷ 512 = 8 blocks → NLB = 7. (b) 4096 ÷ 4096 = 1 block → NLB = 0. (c) 131,072 ÷ 512 = 256 blocks → NLB = 255 (0xFF). Mixing up the LBA size of two namespaces is a common cause of "wrong data" bugs in test tools: an NLB of 7 on Namespace 2 reads 32 KiB.

The SQE's SGL1 cannot hold three data descriptors, so it is a Last Segment descriptor: address of a 48-byte segment in host memory (for example at 0x1_5000_0000), length 48, type 3h. That segment holds three Data Block descriptors (type 0h): {0x2_0000_0000, 4096}, {0x2_0004_0000, 512}, {0x2_0008_0000, 3584}. PSDT in CDW0 is set to select SGLs (01b uses SGLs for data with the metadata pointer as a plain buffer address). With PRPs this layout is impossible: the 512-byte buffer does not end on a page boundary, so the next buffer cannot be described. The controller first reads the 48-byte segment, then writes data to the three buffers. The descriptors must cover NLB × LBA size: a list that describes less data fails with an SGL length error, and whether a list describing more is accepted depends on what the controller reports in its SGL Support field.

    Strong answer includes: Last Segment in the SQE; three Data Blocks; PSDT; why PRPs cannot express it; length consistency.

    Common weak answer: "Put the three descriptors in the SQE."

    Learn it in: Chapter 37, Module 35.

  17. [Concept] What is an SGL Bit Bucket descriptor good for, and why is it valid only for reads?

    Model answer

    A Bit Bucket descriptor tells the controller to discard the given number of bytes of data instead of transferring them to host memory. It lets a host read a range of logical blocks but keep only parts of it, for example reading a 4 KiB block on a 4 KiB-LBA namespace but keeping only the 512-byte record it needs, without allocating a buffer for the rest. On the link, the discarded bytes simply never appear as MWr TLPs. It makes no sense for writes, because the controller would have no data to write for those bytes; the specification restricts it to data the controller transfers to the host. Support is optional and reported in the SGL Support field.

    Strong answer includes: discard semantics; a use case; no TLPs for the discarded bytes; why not for writes; optionality.

    Common weak answer: "It skips LBAs on the media."

    Learn it in: Chapter 37.

  19. [Concept] When would a host use the Compare command (opcode 05h), and how does a failed compare show up?

    Model answer

    Compare sends data from the host and asks the controller to compare it with the stored logical blocks without changing anything. Uses: verifying that a write landed (a read-back check without moving data back to the host), and, most importantly, as the first half of a fused Compare and Write, where the write happens only if the compare matches: an atomic test-and-set used by clustered file systems and lock managers. A mismatch completes with the media-and-data-integrity status Compare Failure (SCT 2, SC 85h). It is not an I/O error in the usual sense: the host's logic must treat it as "the data was different", not as a device fault. Data direction is host to controller, so on the link it looks like a write (controller MRds of host data) followed by a CQE.

    Strong answer includes: no media change; fused Compare and Write; status name; not an error in the fault sense; link direction.

    Common weak answer: "It compares two LBA ranges on the drive."

  20. [Spec] A tool sets the Volatile Write Cache feature to disabled with Set Features; after a reboot it is enabled again. Why, and how do you check what will survive a reset?

    Model answer

    Set Features changes the current value. Whether it persists depends on the Save bit (SV) in the Set Features command and on whether the feature is saveable at all. Without SV, a controller reset or power cycle restores the saved or default value. Get Features has a Select field that shows each view: current (000b), default (001b), saved (010b) and supported capabilities (011b), which tells you whether the feature is saveable, namespace-specific and changeable. So: check capabilities, then set with SV = 1 if saveable, then read saved to confirm. If the feature is not saveable, the host (for example a boot-time script or udev rule) must re-apply it after every reset, including resets the kernel does during error recovery.

    Strong answer includes: current vs saved vs default; SV bit; Select values; reapplying after error-recovery resets.

Interrupts, errors, AER, reset and power

Questions 101–122. Two error worlds meet here: NVMe status codes and asynchronous events on one side, PCIe Advanced Error Reporting (AER) on the other. Intermediate candidates should decode both, know which layer detected what, and know the reset and power controls well enough not to destroy evidence by accident.

  1. [Trace] You dump 16 bytes of the Lab SSD's MSI-X table at BAR0 + 0x2010: 0xFEE0_1000 0x0000_0000 0x0000_0041 0x0000_0000. Which vector is it, what does each dword mean, and what TLP fires when it is used?

    Model answer

    Entries are 16 bytes from the table base (BAR0 + 0x2000), so offset 0x10 is entry 1, vector 1, the first I/O vector on the lab system. Dword 0: Message Address low = 0xFEE0_1000 (the x86 interrupt address window; the value encodes the target CPU). Dword 1: Message Address high = 0. Dword 2: Message Data = 0x41 (the interrupt vector the CPU will run). Dword 3: Vector Control = 0: bit 0 (Mask) clear, so the vector is enabled. When CQ1 posts a completion (and coalescing allows), the SSD sends MWr32 Addr=0xFEE0_1000 Len=1 Data=0x0000_0041 with Requester ID 0x0100. It is a 3DW MWr because the address is below 4 GiB. Nothing distinguishes it from any other memory write except its address.

    Strong answer includes: entry index from offset; the four dwords; Mask bit; the exact TLP; MSI-X being an ordinary memory write.

    Common weak answer: "It's vector 2" (counting from 1), or describing an interrupt message TLP.

    Learn it in: Chapter 43, Module 19.

  2. [Trace] The same entry later reads Vector Control = 0x0000_0001, and the PBA dword at BAR0 + 0x3000 reads 0x0000_0002. What state is the interrupt in and what happens next?

    Model answer

    Vector 1 is masked (Vector Control bit 0 = 1). Bit 1 of the Pending Bit Array is set, so the SSD wanted to send vector 1's message while it was masked: an interrupt is pending. No MWr to 0xFEE0_1000 will be sent while the mask is set. When software clears the mask, the device sends the pending message and clears the pending bit. This is normal during interrupt reprogramming (for example CPU affinity changes). If a vector stays masked because of a driver bug, completions accumulate in CQ1 and no interrupt arrives: I/O on that queue appears hung, while polling the CQ would show completed entries. That is how to tell a masked vector from a lost completion.

    Strong answer includes: mask and pending semantics; delivery on unmask; how to diagnose a stuck mask.

    Common weak answer: "The interrupt was lost."

    Learn it in: Chapter 43, Module 19.

  3. [Concept] The MSI-X capability's Message Control register has Table Size, Function Mask and MSI-X Enable. Why does a driver set Function Mask before programming the table and clear it afterwards?

    Model answer

    Table Size (bits 10:0, N − 1) says how many vectors exist. MSI-X Enable (bit 15) switches the function from INTx/MSI to MSI-X. Function Mask (bit 14) masks every vector at once, regardless of the per-vector masks. Programming an entry means writing several dwords (address low, high, data); if the device fired that vector halfway through, it could send a write to a half-updated address, which is a stray memory write the platform may treat as an error or deliver to the wrong CPU. Masking the function (or the individual vector) during updates prevents that, and pending bits make sure nothing is lost; when the mask is cleared, pending messages are sent. Enabling MSI-X before the table is valid has the same risk.

    Strong answer includes: the three fields; the torn-update hazard; pending bits preserving interrupts.

    Common weak answer: "To save power."

    Learn it in: Chapter 43, Chapter 42.

  4. [Spec] What are the NVMe INTMS and INTMC registers, and why does a Linux NVMe driver using MSI-X never touch them?

    Model answer

    INTMS (Interrupt Mask Set, offset 0Ch) and INTMC (Interrupt Mask Clear, offset 10h) let the host mask and unmask interrupt vectors when the controller is using pin-based (INTx) or MSI interrupts: writing a 1 to a bit sets or clears the mask for that vector, which avoids a read-modify-write race. With MSI-X, masking is done in the MSI-X table's per-vector Vector Control and in the Function Mask, so the NVMe specification says the host should not access INTMS/INTMC when MSI-X is in use. A driver that falls back to INTx or single-message MSI (for example on a platform with broken MSI-X) does use them, typically to mask while processing completions.

    Strong answer includes: set/clear semantics; INTx and MSI only; MSI-X uses its own mask; when a driver would use them.

    Common weak answer: "They enable interrupts for each queue."

    Learn it in: Chapter 24, Chapter 42.

  5. [Performance] With Set Features, Interrupt Coalescing, a host sets Aggregation Threshold = 7 and Aggregation Time = 1. What does that mean, and what happens to a queue-depth-1 latency test?

    Model answer

    The feature applies to I/O completion queues that have coalescing enabled (the per-vector Interrupt Vector Configuration feature can exempt vectors). Aggregation Threshold is 0's based: 7 → interrupt after 8 completions. Aggregation Time is in 100 µs units: 1 → 100 µs. The controller sends the interrupt when either condition is met. At high queue depth, eight completions arrive quickly, so you get one interrupt per eight completions and save CPU. At queue depth 1, the eighth completion never comes while one command is outstanding, so every completion waits for the 100 µs timer: a 12 µs read now looks like up to about 112 µs. Coalescing settings must match the workload; many hosts leave it off and rely on polling or adaptive approaches instead. Implementation-dependent Timer granularity and exact behaviour vary by controller.

    Strong answer includes: 0's-based threshold; 100 µs units; either-condition rule; the QD1 penalty.

    Common weak answer: "Seven completions and 1 µs."

    Learn it in: Chapter 42, Performance Engineering.

  6. [Trace] CQEs for CQ1 are written correctly, followed each time by MWr32 Addr=0xFEE0_2000 Data=0x42. The driver's CQ1 handler never runs and I/O on CPU 0 times out. Explain.

    Model answer

    On the lab system, vector k is address 0xFEE0_k000 with data 0x40 + k, so this is vector 2. CQ1 should interrupt on vector 1. The interrupt vector for a CQ is chosen by the host in Create I/O CQ (the IV field in CDW11), so most likely the driver created CQ1 with IV = 2 while registering its CQ1 handler on vector 1. The vector-2 handler (for CQ2) runs, finds no new entries in CQ2, and returns; CQ1's entries sit unprocessed until the I/O timeout fires. Confirm by reading back the Create I/O CQ command in a trace or log (CDW11 bits 31:16), and by checking /proc/interrupts: the nvme0q2 counter rises while nvme0q1 stays flat. The controller is behaving correctly.

    Strong answer includes: decoding the vector from address and data; IV in Create I/O CQ; the /proc/interrupts evidence; assigning the bug to the host.

    Common weak answer: "The SSD sent the wrong interrupt."

    Learn it in: Chapter 43, Chapter 27.

  7. [Concept] Why does the Linux NVMe driver create one CQ and one MSI-X vector per CPU (when the drive allows), and what do /proc/interrupts lines like nvme0q3 tell you?

    Model answer

    A per-CPU submission and completion path avoids locks and cache-line sharing: a CPU submits to its own SQ, the completion interrupt arrives on that same CPU (the vector's affinity is set to it), and the data and request structures stay in that CPU's cache. With fewer queues than CPUs, CPUs share queues and interrupts cross cores. In /proc/interrupts, nvme0q0 is the admin queue's vector and nvme0q1…nvme0qN are the I/O queues; the per-CPU columns show where each vector was actually handled. A healthy per-CPU setup shows each nvme0qK counting mostly in one column. A vector counting on a different CPU than expected suggests affinity was changed (for example by irqbalance) or that queues are shared. /sys/block/nvme0n1/mq/*/cpu_list shows the CPU-to-queue mapping.

    Strong answer includes: lock-free per-CPU path; interrupt affinity; reading the columns; the mq sysfs mapping.

    Common weak answer: "More queues means more parallelism inside the SSD."

    Learn it in: Chapter 42, Chapter 70.

  8. [Trace] The root port's AER registers read: Uncorrectable Error Status 0x0004_0000, Correctable Error Status 0x0000_0041. Decode both.

    Model answer

    Uncorrectable: bit 18 = Malformed TLP, fatal by default (check the Uncorrectable Error Severity register for this system's setting). The Header Log holds the offending TLP's header, which tells you who sent it and why it was malformed (for example payload larger than MPS, or a 4 KiB boundary crossing). Correctable 0x41: bit 0 = Receiver Error (physical layer) and bit 6 = Bad TLP (data link layer, LCRC or sequence failure). Useful other bit positions to know: uncorrectable 4 Data Link Protocol Error, 5 Surprise Down, 12 Poisoned TLP, 14 Completion Timeout, 15 Completer Abort, 16 Unexpected Completion, 20 Unsupported Request; correctable 7 Bad DLLP, 8 REPLAY_NUM Rollover, 12 Replay Timer Timeout, 13 Advisory Non-Fatal. Status bits are sticky and cleared by writing 1. The correctable bits suggest link noise; the malformed TLP is a separate, more serious event to investigate from the header log.

    Strong answer includes: correct bit decoding; checking severity rather than assuming; using the header log; separating the two findings.

    Common weak answer: assuming the correctable errors caused the malformed TLP.

    Learn it in: Chapter 46, Module 18.

  9. [Concept] The Uncorrectable Error Status register has two bits set. How do you know which error happened first, and which error the Header Log describes?

    Model answer

    The First Error Pointer field in the AER Capabilities and Control register holds the bit position of the first uncorrectable error recorded (the one whose status bit was set first while the field was not already holding a valid pointer). The Header Log is captured for that first error, if the error type logs a header. Later errors set their status bits, but by default the header log is not overwritten (unless the device implements multiple header recording and it is enabled). So with Completion Timeout and Unsupported Request both set and First Error Pointer = 14, the timeout came first and the header log describes it. This is why clearing status in the wrong order, or not clearing it after handling, can leave you reading a stale header for a new error.

    Strong answer includes: First Error Pointer; header log belongs to the first error; stale header risk; multiple header recording as an option.

    Common weak answer: "The lowest bit number happened first."

    Learn it in: Chapter 46, Module 18.

  10. [Coding] A diagnostic script reads the Correctable Error Status register, prints it, and "clears only the Receiver Error bit" by writing back the value it read with bit 0 cleared. What actually happens?

    Model answer

    AER status bits are RW1C: writing 1 clears a bit, writing 0 leaves it alone. Writing back the read value with bit 0 cleared therefore clears every other bit that was set and leaves Receiver Error set: the exact opposite of the intent. The correct way to clear only Receiver Error is to write 0x0000_0001. To clear everything, write back the value read. This is a classic register-semantics bug in scripts using setpci; it destroys evidence (the other error bits) silently. In code: write(status_reg, 1 << 0), never write(status_reg, read(status_reg) & ~1).

    Strong answer includes: RW1C semantics; the reversed effect; the correct write; evidence destruction.

    Common weak answer: "It works, read-modify-write is the standard way."

  12. [Concept] An operations team masks Receiver Error in every SSD's Correctable Error Mask "to stop log spam". What changes, and what do they lose?

    Model answer

    The mask stops the device from reporting that error (no ERR_COR message, so no kernel log line); the hardware event still happens, and the link still replays or retrains as before. Depending on the implementation the status bit may still be set and readable. They lose the early-warning signal: receiver errors are often the first sign of a degrading connector, a thermal problem or a marginal link at a new speed, long before replays turn into REPLAY_NUM rollovers, Recovery events and finally NVMe timeouts. Better options: rate-limit logging in software, aggregate counts into telemetry, and alert on trends, keeping the device-level reporting intact.

    Strong answer includes: masking affects reporting, not the event; the lost trend; the escalation chain; telemetry instead of masking.

    Common weak answer: "Masking fixes the errors."

  13. [Troubleshoot] A Read completes with Status Code Type 2, Status Code 81h. What is it, what information do you collect, and what should the host do?

    Model answer

    SCT 2 is Media and Data Integrity Errors; SC 81h is Unrecovered Read Error: the controller could not return correct data for at least one LBA in the range, even after its internal error correction and retries. Collect: the Error Information log page (the entry for this command gives the LBA and NSID), the SMART log's Media and Data Integrity Errors count, and whether DNR was set. There is no PCIe error here: the link delivered the CQE fine, so AER will be clean, and that is expected. Host actions: do not blindly retry many times (a limited retry is reasonable if DNR is 0); recover the data from redundancy (RAID, replica, backup); rewrite the LBA, which lets the drive remap it; and track whether errors grow, which indicates wear-out.

  14. [Concept] A Write command completes with the generic status Data Transfer Error (04h). Which PCIe-level events could lie behind it, and how would you tell them apart?

    Model answer

    For a write, the controller reads data from host memory, so the transfer that failed is its MRd. Candidates: (1) a Completion Timeout on the MRd (the root complex never answered): the SSD's AER shows Completion Timeout; (2) a completion with UR or CA status, for example an IOMMU-blocked address: the host IOMMU logs a fault naming 01:00.0; (3) a poisoned CplD (EP bit set) because the host memory had an uncorrectable error: the SSD logs Poisoned TLP and the host may log a memory error; (4) an internal controller problem with its data path. Evidence order: the SSD's AER status and header log, host IOMMU and memory-error logs, then an analyzer capture around the command. The NVMe status is the symptom; the PCIe or platform log tells you the mechanism.

    Strong answer includes: direction of data for a write; the three PCIe mechanisms; where each is logged; symptom vs cause.

    Common weak answer: "The NAND failed."

    Learn it in: Chapter 47, Module 39, Module 40.

  15. [Spec] How does a host trigger an NVM Subsystem Reset, when is it available, and what should the host expect afterwards?

    Model answer

    It is available only if CAP.NSSRS is 1 (it is on the Lab SSD). The host writes the value 0x4E56_4D65 (ASCII "NVMe") to the NSSR register at offset 20h; any other value has no effect, which protects against accidental resets. It resets the whole NVM subsystem, every controller in it, not just this one. On a PCIe SSD this typically also resets the PCIe link, so the host should expect the link to go down and retrain, configuration state to need restoring, and a Surprise Down or link-down event at the port unless it prepared for it. After the reset, CSTS.NSSRO (NVM Subsystem Reset Occurred) is set so the host can tell this from other resets. Use it for firmware testing and recovery of a hung subsystem, and coordinate with the operating system, which will otherwise treat the device as having vanished.

    Strong answer includes: CAP.NSSRS; the magic value and offset; subsystem scope; link impact; NSSRO.

    Common weak answer: "Same as CC.EN = 0."

    Learn it in: Chapter 48, Module 41.

  16. [Concept] On Linux you can write 1 to /sys/bus/pci/devices/0000:01:00.0/reset. What happens if the method used is a Function Level Reset, and what does the kernel do around it?

    Model answer

    The kernel picks a reset method the device supports (listed in the reset_method attribute); for FLR it sets the Initiate Function Level Reset bit in the PCI Express Device Control register. FLR resets that function's internal state and most of its configuration registers (except sticky and some link-related bits) without touching the link or other functions; the function must complete it within 100 ms. Around it, the kernel saves the configuration space (BARs, command register, MSI-X setup), waits the required time, and restores it, and it notifies the bound driver before and after so the driver can quiesce and rebuild its state. For the NVMe controller, FLR means CC.EN is 0 afterwards: the driver must re-initialise queues from scratch. Any I/O in flight is lost, so the driver fails or re-queues it.

    Strong answer includes: the Device Control bit; scope (function, not link); 100 ms; save/restore; driver notification; NVMe re-initialisation.

    Common weak answer: "It power-cycles the SSD."

    Learn it in: Chapter 49, Chapter 48.

  17. [Spec] After a conventional reset (PERST# deasserted), how long must software wait before sending configuration requests to the SSD, and why does the rule differ for links faster than 5 GT/s?

    Model answer

    The base rule is that software must wait 100 ms after the end of a conventional reset before sending configuration requests to the device. For downstream ports that support speeds above 5 GT/s, the 100 ms is counted from the completion of link training rather than from reset, because training to higher speeds (with equalization) can itself take significant time, and the device's 100 ms of readiness should start when it can actually be reached. After that, the device may still answer with CRS while its firmware finishes initialising, and software keeps retrying within the platform's limits. Readiness reporting mechanisms (such as Device Readiness Status) can shorten this when supported. Sending configuration requests too early yields Unsupported Requests or CRS, and an impatient enumerator may conclude there is no device.

    Strong answer includes: 100 ms; counting from link training for faster links; CRS after that; readiness reporting as an optimisation.

    Common weak answer: "As soon as the link is up."

    Learn it in: Chapter 49, Chapter 17.

  18. [Concept] An NVMe controller lists power states PS0–PS4 in Identify Controller; PS3 and PS4 are marked non-operational. What do the descriptors tell the host, and what happens if an I/O arrives while the controller is in PS4?

    Model answer

    Each power state descriptor gives the maximum power in that state, entry and exit latencies, relative read/write throughput and latency, and a Non-Operational State flag. In an operational state (PS0–PS2 here) the controller processes I/O, within that state's power limit. In a non-operational state it does not process I/O. If the host submits a command while the controller is in PS4, the controller autonomously transitions to an operational state (the last operational state the host selected) to process it, paying the exit latency; the host does not have to change the state first. The host selects states with Set Features, Power Management, and APST automates entry into non-operational states after idle time. The exit latency is what shows up as an occasional slow first I/O after idle.

    Strong answer includes: descriptor fields; operational vs non-operational; autonomous return; exit latency as the user-visible cost.

    Common weak answer: "The I/O fails until the host wakes the drive."

  19. [Linux] How do you check on Linux whether Autonomous Power State Transitions (APST) are enabled for nvme0, which transitions are configured, and how the kernel limits them?

  20. [Spec] lspci shows the SSD's LnkCap with "ASPM L1, Exit Latency L1 <8us" and its DevCap with "L1 <64us" acceptable latency, but the kernel left ASPM L1 disabled. Give a reason based on these fields.

    Model answer

    The device's Endpoint L1 Acceptable Latency (in Device Capabilities) is the most total L1 exit latency it can tolerate. The operating system compares it with the sum of L1 exit latencies of every link on the path between the device and the root complex (plus a small per-switch allowance). With a direct link, 8 µs is well under 64 µs, so on these numbers alone L1 would be allowed; but if the root port's own LnkCap reports a larger exit latency, or the path has switches whose latencies add up beyond 64 µs, or one end does not support L1 at all, the kernel leaves it disabled. Other reasons are policy (the pcie_aspm settings, firmware not granting the OS control of ASPM) and quirks. So the check is: read both ends' LnkCap, add up the path, and look at the ASPM policy and the boot log.

    Strong answer includes: acceptable latency vs summed exit latency; both ends of each link; policy and firmware control as non-numeric reasons.

    Common weak answer: "8 µs is less than 64 µs, so it is a kernel bug."

  22. [Trace] An Asynchronous Event Request completes, and the host then reads the SMART / Health log: Critical Warning = 0x02. What does that mean and what should happen next?

  6. [Performance] Explain the difference between iodepth=32, numjobs=1 and iodepth=4, numjobs=8 in fio, and why direct=1 matters for SSD testing.

    Model answer

    Both aim for about 32 outstanding I/Os, but differently. One job with iodepth 32 is a single thread keeping 32 asynchronous I/Os in flight (with an asynchronous engine such as io_uring or libaio); it uses one CPU and usually one NVMe queue, so it can become CPU-bound.   7. [Performance] A 4 KiB random write test starts at 600,000 IOPS and drops to 120,000 IOPS after several minutes, then stays there. Is the drive broken?

    Model answer

    Most likely not. Fresh or trimmed drives have plenty of erased blocks and often a fast write cache region (for example a portion of NAND used in SLC mode). As random writes fill the drive, the controller must run garbage collection: relocate valid data from partially valid blocks before erasing them. That internal work competes with host writes, so sustained random-write throughput settles at a "steady state" far below the fresh-out-of-box value; write amplification makes it worse. The correct method is to precondition (write the full capacity, then run the random workload until stable) and report steady state, as standard SSD performance-test methodologies do. Evidence: SMART data-units-written versus host writes over time if the drive exposes write amplification data, and latency percentiles, which typically get much spikier at steady state.

    Strong answer includes: garbage collection and write amplification; cache effects; preconditioning; steady state.

    Common weak answer: "Thermal throttling", without checking temperature or the shape of the curve.

  11. [Concept] nvme list-subsys shows one namespace reachable through two controllers, one path "optimized" and one "non-optimized". What is Asymmetric Namespace Access (ANA) and how should the host use the paths?

    Model answer

  12. [Fabrics] On NVMe over TCP (NVMe/TCP), how does the data for a 128 KiB write get from host to target? How does read data come back?

    Model answer

    The host sends the command in a CapsuleCmd Protocol Data Unit (PDU). For a small write, the data may travel inside the capsule (in-capsule data), up to the size the target allows. For a 128 KiB write that typically exceeds it, the target sends a Ready to Transfer (R2T) PDU naming an offset and length it is ready to receive, and the host answers with H2CData PDUs carrying that data; there may be several R2Ts for one command. For reads, the target sends C2HData PDUs with the data, then a CapsuleResp PDU carrying the completion (or the last C2HData can indicate success so the response is skipped, if both sides agreed). There are no PRPs, no doorbells and no DMA by the target into host memory: the TCP connection carries everything, and SGLs describe data in the command.

    Strong answer includes: in-capsule vs R2T/H2CData; C2HData and CapsuleResp; SGLs; no doorbells or DMA.

    Common weak answer: "The target reads host memory over TCP."

  14. [Fabrics] In NVMe over PCIe the doorbell tells the controller there is work, and MSI-X tells the host a completion is ready. What plays those two roles in NVMe/TCP?

    Model answer

    In NVMe/TCP the submission queue is not in host memory and the controller never fetches anything. Sending the CapsuleCmd PDU is both "writing the SQE" and "ringing the doorbell": the command itself arrives at the target. On the return path, the CapsuleResp PDU carries the CQE (or a success flag on the last data PDU replaces it), and its arrival on the host's socket, through the network stack's own receive notification (interrupt from the NIC, then softirq processing), is what wakes the NVMe/TCP host driver. Flow control is handled by the queue size negotiated at Connect plus TCP's own windowing, rather than by the host tracking a head pointer for a memory ring. This is why NVMe/TCP latency depends heavily on network-stack and CPU behaviour.

    Strong answer includes: capsule as SQE+doorbell; response PDU as CQE; NIC interrupts as the notification; flow-control differences.

  2. [Coding] Write a PRP builder: given a buffer IOVA, a length and the address of a free list page, return PRP1, PRP2 and the list entries for 4 KiB pages. Do not handle chaining, but detect when it would be needed. Check it against questions 90–94.

    Model answer 
    PAGE = 4096

def build_prps(addr, length, list_addr):
    """Return (prp1, prp2, prp_list) for one transfer; no list chaining."""
    assert addr % 4 == 0 and length > 0
    first = min(length, PAGE - addr % PAGE)          # bytes in the first page
    pages = [addr]
    nxt = (addr // PAGE + 1) * PAGE                  # next page boundary
    remaining = length - first
    while remaining > 0:
        pages.append(nxt)
        nxt += PAGE
        remaining -= PAGE
    if len(pages) == 1:
        return pages[0], 0, []
    if len(pages) == 2:
        return pages[0], pages[1], []                # PRP2 is a data pointer
    entries = pages[1:]
    assert list_addr % PAGE == 0 and len(entries) <= PAGE // 8, "needs chaining"
    return pages[0], list_addr, entries              # PRP2 points to the list

  3. [Coding] Write the completion-processing loop for one CQ in C: consume new entries using the phase tag, hand each completion to the upper layer, and update the head doorbell. Point out the memory-ordering detail.

    Model answer 
    struct cqe {
    uint32_t dw0, dw1;
    uint16_t sq_head, sq_id;
    uint16_t cid, status_phase;     /* bit 0 = phase, bits 15:1 = status field */
};

int process_cq(struct cq *cq)
{
    int n = 0;

    for (;;) {
        struct cqe *e = &cq->entries[cq->head];
        uint16_t sp = READ_ONCE(e->status_phase);

        if ((sp & 1) != cq->phase)
            break;                          /* not written on this pass yet */
        dma_rmb();                          /* read the rest only after seeing the phase */

        cq->sq_head_seen[e->sq_id] = e->sq_head;   /* frees SQ slots */
        complete_cmd(e->sq_id, e->cid, sp >> 1, e->dw0);

        if (++cq->head == cq->size) {      /* wrap: flip expected phase */
            cq->head = 0;
            cq->phase ^= 1;
        }
        n++;
    }
    if (n)
        writel(cq->head, cq->head_db);     /* one doorbell per batch */
    return n;
}

    The ordering detail: the device writes the whole 16-byte CQE, but the CPU may read other fields of the entry before it reads the phase bit, or speculatively. A read barrier after checking the phase (dma_rmb() in Linux) ensures the CID, status and SQ head are read after the phase was seen as new. Other details: the phase starts at 1 for a freshly zeroed queue; the head doorbell is written after processing, once per batch, which also frees CQ slots for the controller; and complete_cmd must look up the command by (SQ ID, CID), not by CID alone, if SQs share the CQ.

    Strong answer includes: phase comparison and flip; the read barrier; batching the doorbell; (SQ ID, CID) lookup.

    Common weak answer: checking status == 0 to detect a new entry, which cannot tell new successful entries from stale ones.

  6. [Coding] Write a BAR decoder: given the values read back after writing all ones to a BAR (and to the next BAR for a 64-bit one), return the BAR kind, prefetchability and size.

    Model answer 
    def decode_bar(lo_readback, hi_readback=None):
    """Decode a BAR from the values read back after writing all ones."""
    if lo_readback & 1:                                   # I/O BAR
        mask = lo_readback & ~0x3 & 0xFFFFFFFF
        return {"kind": "io", "size": (~mask & 0xFFFFFFFF) + 1}
    bar_type = (lo_readback >> 1) & 0x3
    prefetch = bool(lo_readback & 0x8)
    if bar_type == 0b10:                                  # 64-bit: pair with next BAR
        mask = (hi_readback << 32) | (lo_readback & ~0xF & 0xFFFFFFFF)
        size = (~mask & 0xFFFFFFFFFFFFFFFF) + 1
        return {"kind": "mem64", "prefetchable": prefetch, "size": size}
    mask = lo_readback & ~0xF & 0xFFFFFFFF
    return {"kind": "mem32", "prefetchable": prefetch, "size": (~mask & 0xFFFFFFFF) + 1}

print(decode_bar(0xFFFF_C004, 0xFFFF_FFFF))   # Lab SSD BAR0/BAR1
print(decode_bar(0xFFF0_0008))                # 1 MiB prefetchable 32-bit BAR

    Output: the Lab SSD's BAR is a 64-bit non-prefetchable memory BAR of 16,384 bytes; the second example is a 32-bit prefetchable 1 MiB BAR. Points: decode bit 0 (I/O vs memory) first, then bits 2:1 (32 vs 64-bit), then bit 3 (prefetchable); mask the type bits before computing size; for a 64-bit BAR combine both halves before inverting; size is the two's complement of the mask. In real enumeration, software must disable memory decoding (Command register) while sizing, save and restore the original values, and remember that a 64-bit BAR consumes two BAR slots, so the next BAR index is skipped.

    Strong answer includes: decode order; masking; 64-bit pairing; disabling decode while sizing; skipping the upper BAR slot.

    Common weak answer: inverting the raw value without masking the type bits, giving a size off by a few bytes.

  7. [Coding] Write a script that pairs nvme_setup_cmd and nvme_complete_rq trace lines into per-command latencies, and reports commands that never completed.

    Model answer 
    import re, statistics

SETUP = re.compile(r"\s([\d.]+): nvme_setup_cmd: (nvme\d+):.*?qid=(\d+), cmdid=(\d+)")
DONE = re.compile(r"\s([\d.]+): nvme_complete_rq: (nvme\d+):.*?qid=(\d+), cmdid=(\d+).*?status=(0x[0-9a-f]+)")

def latencies(lines):
    pending, out = {}, []
    for line in lines:
        m = SETUP.search(line)
        if m:
            ts, ctrl, qid, cid = m.groups()
            key = (ctrl, int(qid), int(cid))
            if key in pending:
                out.append((key, None, "setup without completion (CID reused?)"))
            pending[key] = float(ts)
            continue
        m = DONE.search(line)
        if m:
            ts, ctrl, qid, cid, status = m.groups()
            key = (ctrl, int(qid), int(cid))
            start = pending.pop(key, None)
            if start is None:
                out.append((key, None, "completion without setup"))
            else:
                out.append((key, (float(ts) - start) * 1e6, status))
    for key in pending:
        out.append((key, None, "no completion in capture"))
    return out

SAMPLE = """\
 fio-2201 [003] ..... 5001.000100: nvme_setup_cmd: nvme0: disk=nvme0n1, qid=4, cmdid=18, nsid=1, cmd=(nvme_cmd_read slba=1048576, len=7)
 fio-2201 [003] ..... 5001.000112: nvme_setup_cmd: nvme0: disk=nvme0n1, qid=4, cmdid=19, nsid=1, cmd=(nvme_cmd_read slba=2048, len=7)
 <idle>-0 [003] ..... 5001.000188: nvme_complete_rq: nvme0: disk=nvme0n1, qid=4, cmdid=18, res=0x0, retries=0, flags=0x0, status=0x0
 <idle>-0 [003] ..... 5001.000301: nvme_complete_rq: nvme0: disk=nvme0n1, qid=4, cmdid=19, res=0x0, retries=0, flags=0x0, status=0x0
 fio-2201 [003] ..... 5001.000305: nvme_setup_cmd: nvme0: disk=nvme0n1, qid=4, cmdid=18, nsid=1, cmd=(nvme_cmd_read slba=4096, len=7)
"""
results = latencies(SAMPLE.splitlines())
for key, us, note in results:
    print(key, f"{us:.0f} us" if us is not None else "-", note)
done = [us for _, us, _ in results if us is not None]
print(f"median {statistics.median(done):.0f} us")

    Output: CID 18 took 88 µs, CID 19 took 189 µs, and the second use of CID 18 has no completion in the capture; the median is 139 µs. The sample lines are synthetic and approximate the kernel's tracepoint format, which varies between kernel versions, so the regular expressions must be checked against your kernel's output. Design points: the key must include controller and queue as well as CID, because CIDs are only unique per queue; a CID is reused once its command completes, so a new setup for a pending key indicates a lost completion or a capture gap; commands still pending at the end are the interesting ones in a hang investigation; and percentiles (p99, p99.9) matter more than averages.

    Strong answer includes: the (controller, queue, CID) key; reuse handling; pending-at-end reporting; format caveat.

    Common weak answer: keying on CID alone, mixing up commands from different queues.

    import struct

def decode_msix(table_bytes, pba_bytes, nvec):
    """Decode MSI-X table entries (16 bytes each) and pending bits."""
    pba = int.from_bytes(pba_bytes, "little")
    for k in range(nvec):
        lo, hi, data, ctrl = struct.unpack_from("<4I", table_bytes, 16 * k)
        addr = hi << 32 | lo
        flags = []
        if ctrl & 1:
            flags.append("MASKED")
        if pba >> k & 1:
            flags.append("PENDING")
        if addr == 0:
            flags.append("UNPROGRAMMED")
        yield k, addr, data, flags

# Synthetic Lab SSD dump: vectors 0-3, vector 2 masked with an interrupt pending

                 for k in range(4))
pba = (1 << 2).to_bytes(8, "little")
for k, addr, data, flags in decode_msix(table, pba, 4):
    print(f"vector {k}: addr 0x{addr:08X} data 0x{data:02X} {' '.join(flags)}")

    Model answer 
    def split_io(slba, nbytes, lba_size, mdts, mpsmin=4096):
    """Split a transfer into commands no larger than MDTS. Yields (slba, nlb_field)."""
    if nbytes % lba_size:
        raise ValueError("transfer must be a whole number of logical blocks")
    max_bytes = (1 << mdts) * mpsmin if mdts else None  # MDTS 0 = no limit reported
    max_blocks = max_bytes // lba_size if max_bytes else 1 << 16
    max_blocks = min(max_blocks, 1 << 16)                # NLB field is 16 bits, 0's based
    blocks = nbytes // lba_size
    while blocks:
        n = min(blocks, max_blocks)
        yield slba, n - 1                               # NLB is 0's based
        slba += n
        blocks -= n

for cmd in split_io(slba=0x10_0000, nbytes=1 << 20, lba_size=512, mdts=5):
    print(f"SLBA=0x{cmd[0]:X} NLB={cmd[1]}")

    Output: eight commands, SLBA 0x100000, 0x100100 … 0x100700, each with NLB = 255 (256 blocks of 512 bytes = 128 KiB). Points: MDTS is in units of the minimum memory page size and 0 means the controller reports no limit; the NLB field is 16 bits and 0's based, so one command can never cover more than 65,536 blocks even without MDTS; the transfer must be a whole number of blocks. A real driver splits with the PRP or SGL layout in mind too: an unaligned buffer at exactly MDTS touches one extra page, which is allowed, but other limits (maximum segments, list pool sizes) also apply.

    Strong answer includes: MDTS units and the 0 case; the 16-bit NLB limit; block alignment; other limits a driver applies.

    Common weak answer: using MDTS as a byte or kilobyte count.

How intermediate candidates lose points

  • 0's-based fields. MQES, QSIZE, NLB, ASQS, Number of Queues, Table Size, NR, NUMDL. Say "0's based" out loud every time.
  • Bit 16 of CQE DW3. The phase tag sits between CID and status; shifting by 16 instead of 17 corrupts every status you decode.
  • Direction. For a Read the SSD writes host memory; for a Write it reads it. Many wrong answers come from this flip.
  • Detector vs culprit. The device that logs an error is often not the one that caused it.
  • Overheads. Raw link rate is never payload rate; state the overhead you assumed.
  • Unverified specifics. If you are not sure of a code or offset, say what it is called and that you would confirm it. Interviewers reward that more than a confident wrong number.
