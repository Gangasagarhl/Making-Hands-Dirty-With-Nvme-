Validation engineering turns specifications and product requirements into evidence that a device or system does what it must, fails safely when it cannot, and keeps doing so after every change. This page teaches how to write a validation plan, measure coverage, approach compliance, build test matrices, design negative tests and error injection, and run regression, then applies the method to fifteen NVMe and PCI Express (PCIe) features with a full test specification for each.

Why this part exists

Debugging finds why something failed. Validation decides, in advance, what "working" means and collects the evidence. A validation engineer's output is not "it seems fine": it is a plan that traces each requirement to tests, each test to an observable, unambiguous pass/fail criterion, and each result to a configuration someone else can reproduce.

NVMe over PCIe is a good teacher because it has three specifications with different owners (the PCI Express Base Specification from PCI-SIG; the NVMe Base and command set specifications and the NVMe over PCIe Transport Specification from NVM Express), a large optional feature space, and behaviour that is deliberately left to implementations. A plan must say which document each requirement comes from, whether it is mandatory or optional, and what the product claims to support.

Learning objectives

  • Write a validation plan whose tests trace to requirements and whose pass/fail criteria are observable.
  • For any feature, define requirement, setup, stimulus, expected behaviour, observable evidence, pass/fail, negative test, stress test and recovery test.
  • Measure coverage in several dimensions (requirements, normative statements, states, commands × fields, error paths, configurations) and explain what each misses.
  • Describe the role of compliance and interoperability programs and what passing them does and does not prove.
  • Build a test matrix and reduce it with pairwise combination without losing important interactions.
  • Design negative tests and error-injection campaigns, choosing safe and appropriate injection methods.
  • Run a regression strategy that catches re-introduced bugs and keeps flaky tests from eroding trust.

The story

Before a new playground opens, an inspector visits. She does not just look at it and say "nice". She has a list: every swing chain must hold a grown-up's weight; the slide must not be hotter than a certain temperature in the sun; the gate must close by itself. For each item she knows exactly how to check it and what counts as "pass".

She also does naughty things on purpose: she pulls the swing sideways, she jumps on the bridge, she leaves the gate half open. A good playground doesn't break when children do silly things. And after the playground is repaired, she checks the old problems again, not just the new repair.

Aircraft certification is the adult version. Every requirement (from regulations and from the airline's specification) is traced to a test or analysis; tests include normal operation, abnormal conditions (engine failure on take-off), stress (maximum load), and recovery (restart an engine in flight). Evidence is recorded so an independent authority can review it. After any modification, affected tests are rerun.

An aircraft is certified once against a stable rulebook; storage products face a moving one: specifications revise (NVMe 2.4 was ratified in July 2026), kernels and platforms change every few weeks, and firmware updates arrive in the field. Validation is therefore continuous, not a one-time gate. The playground inspector also has an advantage you do not: she can see the whole playground. Much of an SSD's behaviour is internal and unobservable; you can only validate what crosses an interface or what the device reports, so choosing observable evidence is a skill in itself.

Anatomy of a validation plan

The document

  1. Scope: product, firmware and hardware revisions; which specifications and revisions (for example NVMe Base 2.4, NVM Command Set 1.3, NVMe over PCIe Transport 1.4, PCI Express Base Specification at the revision the product claims); which optional features the product claims (from Identify Controller and capability registers).
  2. Requirements: extracted, uniquely identified, each with a source and a classification: Normative mandatory, normative-if-supported (optional feature), product requirement (customer or internal), and Implementation-dependent behaviour the product defines.
  3. Test environment: hosts, root ports, switches, analyzers, exercisers, power-cycling rigs, thermal chambers, software versions.
  4. Test cases: each with the nine fields below.
  5. Traceability matrix: requirement ↔ test ↔ result.
  6. Test matrix: configurations under which tests run.
  7. Entry and exit criteria: what must be true to start, and what results allow release (for example "all mandatory requirements pass; no open severity-1 defects; performance within 5% of targets").
  8. Risks and gaps: what cannot be observed or tested, and how it is mitigated (analysis, vendor evidence, field monitoring).

The central concept on the ladder: a test with an oracle

A spelling test only works if the teacher has the answer sheet. Without it, she can only say "you wrote something".

A test has three parts: a stimulus, an observation, and an oracle that decides pass or fail. The oracle is what turns activity into evidence.

For a storage device the oracle may be a data pattern (each block carries its LBA, a write sequence number and a checksum), a register value (CSTS.RDY = 1 within CAP.TO), a status code, a timing bound, or an invariant (no CQE for an unknown Command Identifier).

Oracles for mandatory behaviour come from normative statements; for optional features from the feature's definition plus the device's claimed support; for implementation-dependent behaviour from the product's own specification. Each oracle cites its source.

Protocol-level oracles check what crosses the interface: every non-posted request receives a completion; every SQ tail doorbell value is within the queue; every MWr payload ≤ MPS.

Trace-level oracles compare captures with golden traces or rule checkers, flagging the first deviation (see golden traces and diffing).

When a test fails, a good oracle tells you which expectation broke, which is the first step of the debugging chain. A test that only reports "fail" sends the engineer back to the start.

High coverage numbers can be meaningless if tests lack oracles. A suite that issues every opcode and checks only that the controller did not hang has 100% command coverage and almost no checking power.

Compliance and interoperability

Industry programs provide shared test suites and lists of products that passed them. Program details change; check the program owner's current documentation.

  • PCI-SIG Compliance Program: PCI-SIG runs compliance workshops and maintains an Integrators List of products that passed its electrical, configuration, link and transaction-layer tests for a given specification revision. Test specifications and tools are available to members.
  • NVMe conformance and interoperability: NVMe conformance and interoperability testing has historically been run with the University of New Hampshire InterOperability Laboratory (UNH-IOL), which publishes NVMe test suites and an Integrator's List Uncertain for the current arrangement: check nvmexpress.org and the UNH-IOL site.
  • Customer and ecosystem requirements: data-centre purchasers often publish SSD requirement documents (for example through the Open Compute Project) that add requirements beyond the NVMe specifications: telemetry, latency targets, error-handling behaviour.

Passing a compliance suite shows the product passed those tests on that configuration. It does not prove the absence of bugs, does not cover implementation-dependent behaviour, and does not test your platform's interaction with the device. Compliance is a floor, not a ceiling.

Reducing the matrix

  • Pairwise (all-pairs) testing: choose configurations so every pair of values from any two dimensions appears at least once. Many interaction bugs involve two factors; pairwise covers all of those with a few dozen configurations instead of tens of thousands.
  • Risk weighting: run the full suite on the most common customer configurations; pairwise elsewhere.
  • Known interactions: force specific combinations known to matter (for example MPS 128 with 64-byte completions; strict IOMMU with maximum queue count).
  • Rotation: nightly runs rotate through matrix cells so the whole matrix is covered over a week.

Negative testing

Negative tests check that the device detects violations and responds as required, without hanging, corrupting other data or losing its health. The oracle has two parts: the specific response (a status code, an error report, an ignored write) and health afterwards (other commands still work; no unexpected Controller Fatal Status).

Fuzzing

Systematic negative tests cover known classes; fuzzing generates large numbers of semi-random commands (valid structure, random field values) and checks the health oracle. It finds the combinations nobody thought of. Combine with firmware coverage measurement to steer it.

Expert lab Negative and fuzz testing can brick devices (for example, malformed firmware or format commands) and destroy data. Use dedicated hardware with a recovery path, never production drives.

Linux also provides higher-level controls (the device's reset attribute in sysfs, and the NVMe CLI's controller reset) that coordinate with the driver; prefer them unless you are specifically testing uncoordinated resets. Check your kernel's documentation for available reset methods.

Every injection campaign needs a detection oracle (was the error detected and reported where the specification says?) and a recovery oracle (did the system return to full function, and was no data corrupted?). Injecting without both is noise.

Golden traces and baselines

For protocol behaviour, store golden traces of key flows (initialisation, queue creation, a Read, a Write, a reset) and compare new captures with them, flagging differences for review rather than auto-failing: legal variations are common. For performance, store baseline distributions and fail on statistically significant regressions, not on single-run noise.

Flaky tests

A test that sometimes fails without a product change is either a real intermittent bug or a broken test. Both matter. Quarantine it from the release gate, but investigate it with the debugging chain; never just add retries. Track the flake rate; a suite where people expect red results stops protecting anything.

Bisection

When a regression appears, bisect firmware builds, kernel versions or configuration changes (see elimination techniques). Keep builds and configurations archived so bisection is possible.

Feature test specifications

For each feature below: requirement, setup, stimulus, expected behaviour, observable evidence, pass/fail, negative test, stress test and recovery test. Requirements paraphrase the governing document by name; confirm exact wording and conditions in the specification before using these as formal requirements. Safety levels: anything that resets, power-cycles, injects errors or writes raw namespaces is Expert lab on dedicated hardware.

Reset

Reset (Chapter 48, Chapter 49)
RequirementController reset (CC.EN 1 → 0) returns the controller to a disabled state, CSTS.RDY clears, queues are deleted; re-enable succeeds within CAP.TO. Function Level Reset, hot reset and conventional reset affect PCIe and NVMe state as the PCIe and NVMe specifications define; NVM Subsystem Reset (if supported) is triggered by writing the defined signature to the NSSR register (NVMe Base Specification).
SetupInitialised controller with I/O queues and outstanding I/O at several queue depths; analyzer armed.
StimulusEach reset type in turn, with I/O idle and with I/O outstanding.
Expected behaviourOutstanding commands are aborted or completed as defined; controller reaches ready within CAP.TO after re-enable; no data corruption for writes that completed before the reset.
Observable evidenceCSTS transitions (poll trace), CQEs for outstanding commands (or their absence), time to RDY, data-integrity checker results, kernel log.
Pass/failPass iff RDY within CAP.TO in every iteration, no unexpected CFS, data checker reports zero mismatches for acknowledged writes, I/O resumes.
Negative testEnable with CC values outside CAP (for example a memory page size above CAP.MPSMAX): controller does not become ready or reports an error as specified; host can recover with a correct CC.
Stress test10 000 controller resets under QD 128 mixed I/O; resets at random times relative to command phases.
Recovery testReset while a previous reset is still completing (rapid reset storms); reset after CFS; verify full function each time.

Queue creation (Chapter 26, Chapter 27)
RequirementThe controller grants I/O queues via the Number of Queues feature; Create I/O Completion Queue (05h) and Create I/O Submission Queue (01h) succeed for valid parameters (queue size up to CAP.MQES + 1, contiguous or PRP-list memory as CAP.CQR requires, valid interrupt vector, an existing CQ for each SQ); Delete commands require SQs deleted before their CQ (NVMe Base Specification).
SetupController enabled with admin queues only.
StimulusRequest maximum queues; create every granted queue pair at minimum, typical and maximum sizes; delete and re-create.

Observable evidenceAdmin CQE statuses; per-queue I/O test; analyzer showing SQE fetches from each SQ base address.

StimulusReads of every size from 1 LBA to MDTS, aligned and unaligned buffers, PRP and SGL, all queues, QD 1–256.

Write

Write (Chapter 33, module 31)
RequirementWrite (01h) stores data for the LBA range; subsequent Reads return it; Force Unit Access (FUA) writes are non-volatile on completion (NVM Command Set Specification).

StimulusWrites of all sizes and alignments, overlapping writes from different queues, FUA and non-FUA.

Flush

Error handling

NVMe error handling (Chapter 44, module 39)
RequirementErrors are reported through the CQE Status field (status code type, status code, Do Not Retry and More bits), the Error Information log, and asynchronous events where defined; Abort (08h) handles outstanding commands as specified (NVMe Base Specification).

StimulusThe negative tests of every feature; Abort of commands in each phase (not fetched, executing, completed).

Advanced Error Reporting

AER (Chapter 46, module 18)
RequirementThe device implements the AER capability as claimed: detects correctable and uncorrectable errors, sets status bits, honours mask and severity registers, captures the Header Log for errors that log headers, and sends ERR_COR / ERR_NONFATAL / ERR_FATAL messages as enabled (PCI Express Base Specification).
SetupExerciser/jammer on the link; OS AER handling enabled; analyzer.
StimulusInject LCRC errors (Bad TLP), corrupted DLLPs, malformed TLPs, poisoned TLPs, unsupported requests, completion timeouts (drop a completion).

Negative testInject with the error class masked: no message, status bit behaviour per specification.
Stress testSustained correctable error injection at high rate: device and OS remain responsive.
Recovery testAfter uncorrectable non-fatal and fatal injections, OS recovery (driver error handlers, link reset) restores I/O without reboot.

Code: a pairwise matrix generator

#!/usr/bin/env python3
"""Greedy all-pairs test matrix generator (standard library only).
Every pair of values from any two dimensions appears in at least one row."""
import itertools
import random

DIMS = {
    "link":   ["Gen5x4", "Gen4x4", "Gen3x4"],
    "mps":    ["128", "256", "512"],
    "kernel": ["LTS", "latest"],
    "fw":     ["N", "N+1"],
    "lba":    ["512", "4096"],
    "iommu":  ["off", "lazy", "strict"],
    "aspm":   ["off", "L1"],
}

names = list(DIMS)
uncovered = {(a, va, b, vb)
             for a, b in itertools.combinations(names, 2)
             for va in DIMS[a] for vb in DIMS[b]}

def pairs_of(row):
    return {(a, row[a], b, row[b]) for a, b in itertools.combinations(names, 2)}

rows = []
random.seed(1)                       # deterministic output
while uncovered:
    best_row, best_gain = None, -1
    for _ in range(50):              # build 50 candidate rows, keep the best
        a, va, b, vb = random.choice(sorted(uncovered))   # seed with an uncovered pair
        row = {a: va, b: vb}
        for n in random.sample(names, len(names)):
            if n in row:
                continue
            def gain(v):
                trial = dict(row, **{n: v})
                return sum(1 for (x, vx, y, vy) in uncovered
                           if n in (x, y) and x in trial and y in trial
                           and trial[x] == vx and trial[y] == vy)
            row[n] = max(DIMS[n], key=gain)
        g = len(pairs_of(row) & uncovered)
        if g > best_gain:
            best_row, best_gain = row, g
    uncovered -= pairs_of(best_row)
    rows.append(best_row)

full = 1
for v in DIMS.values():
    full *= len(v)
print(f"exhaustive: {full} configurations; pairwise: {len(rows)}")
for i, r in enumerate(rows, 1):
    print(f"{i:2d}: " + "  ".join(f"{k}={r[k]}" for k in names))

Running it prints an eleven-row matrix (with the fixed random seed) instead of the 432 exhaustive configurations. No pairwise matrix here can have fewer than nine rows, because the two three-valued dimensions link and MPS alone form nine pairs; greedy algorithms get close to, but do not guarantee, the minimum. Then add the specific combinations you know are risky; pairwise is a floor, not a replacement for judgement.

Worked example: from one requirement to a test campaign

Requirement (paraphrased from the Dataset Management command in the NVM Command Set Specification): a Dataset Management command with the Attribute – Deallocate bit set deallocates the specified ranges; subsequent reads of deallocated LBAs return data as described by the namespace's reported deallocation read behaviour.

  1. Classify: Dataset Management is optional; the test applies only if Identify Controller's Optional NVM Command Support indicates it. The read-back value after deallocation is reported by the namespace (all zeros, all ones, or not reported) Version-dependent in its exact field names: check the current Identify Namespace definition.
  2. Setup: write patterns to ranges; record the reported deallocation behaviour.
  3. Stimulus: deallocate single and multiple ranges, including the maximum number of ranges per command, unaligned to internal mapping units.
  4. Oracle: reads of deallocated LBAs equal the reported value (if reported); non-deallocated neighbours unchanged.
  5. Negative: range beyond namespace; number of ranges above the maximum.
  6. Stress: interleave deallocate with writes to the same LBAs from other queues; check final state is consistent with command ordering the host enforced.
  7. Recovery: power cut after deallocate completion; check deallocated ranges and neighbours.
  8. Traceability: each step gets a test ID linked to the requirement ID in the matrix.

See Chapter 35 — Dataset Management and module 33 for the command itself.

Common mistakes

  • Tests without oracles ("ran without hanging").
  • Treating implementation-dependent behaviour as mandatory, then failing compliant devices.
  • Testing only happy paths; no negative, stress or recovery tests.
  • Results without configuration capture.
  • Software-only error injection used as evidence of hardware error detection.
  • Retrying flaky tests until green.
  • Assuming compliance-program passes mean interoperability.
  • Writing requirements from memory instead of the current specification revision.

Senior engineer insight

Senior validation engineers spend disproportionate effort on recovery tests and oracles. Field failures concentrate where two unusual things happen together (a reset during a firmware activation, a power loss during namespace formatting), and on paths that run rarely. They also treat the test suite as a product: versioned, reviewed, with its own bugs tracked. Every customer escape gets two outputs: a fix, and an answer to "which test should have caught this, and why didn't it?".

Lab: write a validation plan for Write Zeroes

Objective

Produce a complete nine-field test specification, a negative-test list and a small test matrix for one optional command.

Skills

Requirement extraction; oracle design; negative and recovery testing; matrix reduction.

Safety

Safe lab as a paper exercise. Executing the plan writes to the namespace: Expert lab on a dedicated drive.

Hardware required

None for the plan; an NVMe drive supporting Write Zeroes to execute it.

Software required

The NVM Command Set Specification 1.3 (Write Zeroes command section); nvme-cli; pairwise.py.

Input

The product claims Write Zeroes support (Identify Controller optional command support) with the Deallocate bit supported.

Expected output

Nine-field table; at least four negative tests; one stress and one recovery test; a pairwise matrix over at least four dimensions; traceability IDs.

Background

Write Zeroes sets a range of LBAs to zero without transferring data; options can allow the controller to deallocate. Read the command definition; do not rely on this summary for field names.

Step 1

Extract requirements and classify each as mandatory, mandatory-if-supported, or implementation-dependent.

Step 2

Fill the nine fields.

Step 3

Generate the matrix and add any risky combinations by hand.

Observation

Note which outcomes are observable from the host and which are not (for example, whether the controller actually deallocated).

Questions

  1. What is the oracle for "the LBAs are zero"?
  2. How can you test the deallocation option when deallocation itself is internal?
  3. Which interactions with other features deserve explicit matrix rows?

Challenge

Add a test that would catch a controller that returns zeros on read-back from a cache but never persists the zeroing.

Hint

Think about power loss and about the namespace's protection information and metadata.

Solution

Requirement: Write Zeroes sets the specified LBAs to read as zero (data and, per the command's options and the namespace format, metadata/protection information as defined); completion indicates the operation is done as defined by the command set.

Setup: namespace with known patterns; formats with and without metadata. Stimulus: Write Zeroes over ranges from 1 LBA to the maximum allowed, aligned and unaligned; with and without the deallocate option. Expected: reads return zeros in range; neighbours unchanged. Evidence: pattern checker; CQE status; analyzer confirms no data phase (no MRd for data). Pass/fail: zero mismatches over 105 commands.

Negative: LBA out of range; NLB beyond the end; inactive NSID; Write Zeroes to a read-only namespace or zone; size limit above the controller's reported Write Zeroes limit if one is reported.

Stress: Write Zeroes interleaved with Writes and Reads to overlapping ranges across queues, with host-enforced ordering.

Recovery (the challenge): Write Zeroes, wait for completion, issue Flush, cut power; on recovery the range must still read zero. A cache-only implementation fails this.

Deallocation: not directly observable; indirect evidence includes capacity utilisation reporting (if provided), subsequent write performance, or vendor telemetry; record it as a limitation.

Matrix rows to force: LBA format with metadata × protection information enabled; deallocate option × namespace reporting deallocated-read behaviour; ZNS namespace if supported.

What a senior engineer notices

The absence of a data phase is itself an oracle: if the trace shows the controller fetching data for Write Zeroes, something is badly wrong even when read-back passes.

Failure variants

  • Metadata not zeroed when it should be; protection information checks then fail on read.
  • Zeroing applied to the wrong range when NLB is at its maximum (off-by-one with zero-based NLB).

Extension

Turn the plan into automated tests and add them to the nightly tier with traceability IDs.

Quiz

  1. Which field turns test activity into evidence?

    • Setup
    • Stimulus
    • Pass/fail (the oracle)
    • Stress test
    Answer and reasoning

    Without a pass/fail oracle, a test only shows that something happened.

  2. Which method validates the device's hardware detection of LCRC errors?

    • Linux aer-inject
    • A PCIe exerciser/jammer corrupting LCRC on the wire
    • NVMe fault injection in the driver
    • Reading the SMART log
    Answer and reasoning

    aer-inject simulates reports in software; only real corruption on the link exercises the receiver's detection.

  3. What does pairwise testing guarantee?

    • Every pair of values across any two dimensions appears in some configuration
    • Every combination is tested
    • All three-way interactions are covered
    • Tests run in pairs
    Answer and reasoning

    Pairwise covers all two-factor interactions only.

  4. A product passes a compliance suite. What can you conclude?

    Model answer

    That it passed those tests on that configuration. Not that it is bug-free, interoperable with every host, or correct in implementation-dependent behaviour.

  5. Difference between a negative test and a stress test?

    Model answer

    Negative tests apply invalid or out-of-contract stimulus and check correct rejection and health; stress tests apply legal stimulus at extremes of rate, duration, size or environment.

  6. Why should a test result include configuration capture and before/after counters?

    Model answer

    To make it reproducible and comparable, and so the result can show side effects (for example new correctable errors) that the primary oracle does not check.

  7. A test fails one run in fifty with no product change. What do you do?

    • Add automatic retries
    • Delete the test
    • Ignore it until it fails more
    • Quarantine it from the release gate and investigate it as a possible intermittent bug
    Answer and reasoning

    It is either a real intermittent bug or a broken test; both need fixing; retries hide both.

  8. Give the recovery test for Flush.

    Model answer

    Reset or power-cut during/after Flush; after recovery, all data acknowledged before a successfully completed Flush is intact.

  9. Why might a golden-trace difference not be a failure?

    Model answer

    Many differences are legal: timing, completion splitting, SQE fetch batching, interrupt coalescing. The diff flags; a requirement decides.

  10. Name the two oracles every error-injection campaign needs.

    Model answer

    A detection oracle (detected, logged and signalled correctly) and a recovery oracle (returns to full function with no corruption).

Interview questions

  1. Beginner: What makes a requirement testable?

    Model answer

    It names an observable outcome under stated conditions with an unambiguous criterion and a source.

  2. Intermediate: How would you test queue creation negatively?

    Model answer

    Invalid queue IDs, sizes above CAP.MQES + 1, SQ referencing nonexistent CQ, invalid interrupt vector, wrong deletion order; check each specific status and that existing queues keep working.

  3. Advanced: Design an AER validation campaign.

    Model answer

    Use an exerciser to inject each error class at each agent; verify status, severity, masking, Header Log contents and message type; verify OS reporting; for uncorrectable classes, verify OS recovery restores I/O; repeat across platforms because root-port handling differs.

  4. Senior: A customer escape: data loss after power loss during firmware activation. What changes in your validation?

    Model answer

    Root-cause it; add a regression test at the precise window; widen the recovery matrix to power loss × every long-running admin operation (activation, format, sanitize, namespace management); review why the original plan did not include the cross-product; add field telemetry if detection was late.

  5. Senior: How do you decide release readiness?

    Model answer

    Against pre-agreed exit criteria: mandatory requirements pass on the release matrix, no open high-severity defects, performance and latency within targets, regression suite green with known flakes investigated, residual risks documented and accepted by owners.

Summary

A validation plan traces sourced requirements to tests with observable evidence and unambiguous oracles, and adds negative, stress and recovery tests for every feature. Coverage has many dimensions and none is complete alone. Compliance is a floor. Matrices are reduced with pairwise selection plus judgement. Error injection must match the layer whose detection you are testing, with both detection and recovery oracles. Regression is continuous, tiered, and fed by every bug.

Do not move on until you can:

  • write the nine fields for any NVMe or PCIe feature, with a sourced requirement and an observable oracle
  • list five coverage dimensions and what each misses
  • explain what compliance proves and what it does not
  • generate a pairwise matrix and name combinations to force by hand
  • choose an error-injection method for a given layer and state its safety level
  • design a regression strategy with tiers, golden traces and flake handling
