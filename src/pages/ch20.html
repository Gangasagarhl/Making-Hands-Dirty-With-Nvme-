Direct Memory Access (DMA) is how an NVMe SSD moves data without the CPU touching every byte: the controller itself issues PCIe Memory Read and Memory Write requests into host memory. This chapter explains why DMA exists, how bus mastering is enabled, how an IOMMU turns the device's I/O virtual addresses into physical ones, why cache coherence matters, how the Linux DMA API prepares memory, and how it all appears on the link as MRd → host memory → Completion with Data.

Why this chapter exists

Almost every byte an NVM Express (NVMe) drive moves crosses the PCI Express (PCIe) link as a DMA transaction the drive itself started. The host never "sends" write data to an NVMe SSD: it puts the data in memory, describes where it is, and rings a doorbell; the SSD then reads it. The host never "receives" read data: the SSD writes it into memory and then writes a completion entry. Even the commands themselves are fetched by the SSD from host memory, and the completions and interrupts are DMA writes.

So the addresses in nearly every NVMe trace are DMA addresses, and the most confusing NVMe failures — data corruption, "Data Transfer Error" statuses, IOMMU faults, hangs after suspend — are DMA failures. You need a precise model of who emits which address, who translates it, and when the CPU's caches and the device's view of memory agree.

Learning objectives

  • Explain why DMA exists: Programmed I/O (PIO, the CPU copying every word) versus DMA, with costs.
  • Describe a DMA engine: source, destination, length, descriptors, scatter-gather lists — and recognise NVMe queues, PRPs and SGLs as descriptor structures.
  • Explain bus mastering: the Command register's Bus Master Enable bit and what a function may do with and without it.
  • Distinguish CPU virtual addresses, CPU physical addresses and I/O virtual addresses (IOVA), and explain what an IOMMU does with the Requester ID and the IOVA.
  • Explain cache coherence for DMA: snooping, the No Snoop attribute, and why non-coherent platforms need explicit cache maintenance.
  • Use the Linux DMA API correctly in pseudocode: dma_set_mask_and_coherent, dma_alloc_coherent, dma_map_single/dma_unmap_single, dma_map_sg, sync calls and directions.
  • Trace the NVMe controller → PCIe Memory Read → host memory → Completion with Data path, and the Memory Write path for read data, completions and MSI-X.
  • Diagnose IOMMU faults, Bus Master disabled, use-after-unmap and coherence bugs from traces and logs.

The story

A teacher wants 500 books moved from the library to the classroom shelves. She could carry them herself, one at a time — and do no teaching all day. Instead she writes a list: "shelf 3, books 1 to 20 → classroom table A; shelf 9, books 4 to 30 → table B…" and hands it to the librarian, who has a trolley. The librarian moves the books while the teacher teaches, and rings a bell when done. The school has a rule: the librarian may only enter rooms that appear on a special map the head teacher keeps — so a librarian with a wrong list cannot wander into the head's office and rearrange it.

A warehouse with forklift robots. The office (CPU) does not move pallets; it prints pick lists — "4 pallets from aisle 12 bay 3, 2 pallets from aisle 40 bay 1, deliver to dock 7" — and drops them in the robots' inbox. The robots (DMA engines) execute lists autonomously. Robots navigate with their own coordinate system, translated by a gatehouse (the IOMMU) that holds a map for each robot fleet; a robot asking for a bay not on its fleet's map is stopped at the gate and the incident logged. Because the office keeps a few pallets on its own desks (CPU caches), the gatehouse also checks the desks before a robot takes or replaces a pallet, so nobody works with a stale copy.

Where the analogy breaks. (1) Robots get the pick list by themselves reading it from the office's inbox — in NVMe, the device fetches its own commands by DMA, and even the "bell" back to the CPU (MSI-X) is a DMA write. (2) The gatehouse map is per device (Requester ID), and its "coordinates" (IOVA) can be anything the OS chooses, including addresses that do not exist as physical memory. (3) Checking the desks (snooping) is automatic on x86 but not on every architecture; there the office must tidy its desks explicitly before and after. (4) A real warehouse robot can drop a pallet; a PCIe read never "drops" data silently — it either completes or returns an error status, or times out.

Beginner explanation

Without DMA, the CPU would have to move data itself: read a word from the device's register, store it in memory, repeat — that is Programmed I/O. At 7 GB/s, PIO would consume entire CPU cores just copying, and each MMIO read costs about a microsecond of stall (Chapter 19). Instead, the device has a DMA engine: hardware that, given a source, a destination and a length, issues memory requests on the bus by itself.

For DMA to work:

  1. The device must be allowed to issue requests — the Bus Master Enable bit in its Command register must be 1.
  2. The memory must be prepared — the driver allocates or "maps" buffers so the device has an address it can use, and so the CPU's caches will not hide or overwrite the data.
  3. The device must be told where — via descriptors. In NVMe, the descriptors are the Submission Queue Entries, which contain Physical Region Page (PRP) entries or Scatter Gather List (SGL) descriptors pointing to the data buffers.
  4. Addresses must be translated — on most modern systems an IOMMU sits between the device and memory. The device uses I/O virtual addresses; the IOMMU translates them to physical addresses and blocks anything not mapped.

On the link, a device reading host memory sends a Memory Read request (MRd); the Root Complex fetches the data from memory and returns one or more Completions with Data (CplD). A device writing host memory sends Memory Write (MWr) requests, which are posted — no completion.

DMA engines, descriptors and scatter-gather

A DMA engine executes descriptors: records that say "move length bytes from source to destination", often with flags (interrupt on completion, next descriptor). Because operating systems allocate memory in pages that are rarely physically contiguous, a single logical buffer is usually a scatter-gather list: a list of (address, length) segments. Engines either walk a linked list of descriptors in memory or are handed a ring.

NVMe is built entirely on this idea:

  • Submission Queues are rings of 64-byte command descriptors in host memory; the controller fetches them by DMA (Chapter 25).
  • PRP entries and PRP lists describe data buffers as a list of page addresses (Chapter 36); SGLs describe them as (address, length) segments (Chapter 37).
  • Completion Queues are rings of 16-byte entries the controller writes by DMA.
  • MSI-X interrupts are 4-byte DMA writes to an address/data pair the driver programmed.

Source and destination depend on direction: for an NVMe Write command, the source is host memory (described by PRP/SGL) and the destination is the controller's internal buffer, then media; for a Read, the reverse.

Bus mastering

Bit 2 of the Command register, Bus Master Enable (BME), controls whether a function may issue memory and I/O requests. With BME = 0, an Endpoint must not issue them — no DMA, and no MSI/MSI-X (those are memory writes). On a bridge (Root Port, switch port), BME controls whether requests from below are forwarded upstream; with it clear, the bridge treats them as Unsupported Requests. Firmware leaves BME clear until a driver takes ownership; the Linux NVMe driver sets it in probe through the PCI core, and error-recovery and shutdown paths clear it to stop a misbehaving device.

BME is a safety switch, not a security boundary on its own: a malicious or buggy device can ignore it. Protection against devices writing where they should not comes from the IOMMU.

The value a driver writes into an SQE's PRP field, or into ASQ, is an IOVA — the Linux type is dma_addr_t. It is not the CPU's virtual address and, with an IOMMU in translating mode, not the physical address either. Every address you see in a device-initiated TLP in a trace is an IOVA.

The IOMMU

An IOMMU (Intel VT-d, AMD-Vi, the Arm System MMU and others) sits in the Root Complex between PCIe and the memory system. For each device-initiated request it:

  1. Takes the Requester ID (Bus/Device/Function, e.g. 0x0100 for the Lab SSD) and optionally a PASID, and looks up which translation tables belong to that device (a context or device table).
  2. Walks those page tables to translate the IOVA to a physical address, checking read/write permission. Translations are cached in an IOTLB.
  3. On success, forwards the request to memory. On failure (not mapped, no permission), blocks it, records a fault (logged by the OS as a DMAR/IOMMU fault), and completes a read with an error status. Implementation-dependent Whether the completion is Unsupported Request or Completer Abort, and how a blocked write is reported, varies by platform.

The IOMMU gives: isolation (a device can only reach memory mapped for it — essential for assigning devices to virtual machines and for protection against malicious devices); contiguity (scattered physical pages can appear contiguous in IOVA space); and addressing (a device limited to 32-bit addresses can reach memory above 4 GiB through low IOVAs). Its cost is translation latency on IOTLB misses and the CPU time to create and tear down mappings. Linux offers modes: strict or lazy invalidation, and passthrough (iommu=pt: identity mappings for kernel drivers, translation only for devices assigned to user space or VMs). Implementation-dependent

Devices can cache translations themselves using Address Translation Services (ATS), and request page faults using Page Request Interface (PRI) — optional PCIe capabilities used mostly by accelerators and shared-virtual-memory devices, rarely by NVMe SSDs today. Optional

Cache coherence

CPUs keep copies of memory in caches. If the device reads memory while the latest data sits only in a CPU cache, it would read stale data; if the device writes memory while the CPU holds an old copy in cache, the CPU would later read stale data. Two solutions:

  • Hardware coherence (snooping). On x86 servers and many Arm servers, the Root Complex snoops CPU caches for every DMA access: reads get the latest data, writes invalidate or update cached copies. Software need not flush caches.
  • Software coherence. On non-coherent platforms (many embedded SoCs), the driver must clean (write back) caches before the device reads a buffer and invalidate them before the CPU reads a buffer the device wrote. The Linux DMA API does this inside map/unmap/sync calls, which is why drivers must call them even on x86, where they are cheap.

The TLP attribute No Snoop lets a device tell the Root Complex that a particular access does not need snooping (because software guaranteed coherence), saving snoop bandwidth; it is enabled by the Enable No Snoop bit in Device Control (Chapter 18). Whether a Root Complex honours it is platform-specific. Relaxed Ordering lets a device's writes be reordered with respect to each other for performance — safe for bulk data, not for the completion-queue entry that must arrive after its data (Chapter 14). Implementation-dependent

Ownership rules for streaming mappings: after dma_map_*, the device owns the buffer — the CPU must not touch it; after dma_unmap_* (or sync_for_cpu), the CPU owns it again. Breaking these rules works by accident on coherent x86 and fails on non-coherent systems or with bounce buffers.

Bounce buffers (swiotlb). If a device cannot reach a buffer's physical address (DMA mask too small, no IOMMU) or memory must be shared through a special region (as in confidential-computing guests), the DMA API copies data through a "bounce" buffer the device can reach. Correct, but each transfer now costs a CPU copy — a classic hidden performance problem.

The ladder

The teacher writes a list; the librarian with the trolley moves the books and rings a bell; a map decides which rooms the librarian may enter.

The driver prepares buffers, writes descriptors (SQEs with PRPs), and rings the doorbell; the controller's DMA engine reads and writes host memory itself; the IOMMU translates and polices its addresses; the device signals completion with a CQE and an MSI-X write.

In the SSD: queue-fetch engine, PRP/SGL walker, data DMA engines with tag tables and completion reassembly buffers. In the host: Root Complex with IOMMU (context tables, page tables, IOTLB), cache-coherent interconnect, memory controller.

PCIe Base Specification: Bus Master Enable, Memory Read/Write semantics, 4 KiB boundary rule, MRRS/MPS, RCB, attributes (No Snoop, Relaxed Ordering), ATS/PRI. NVMe Base/PCIe Transport Specifications: PRP and SGL formats, queue memory requirements. The IOMMU and the Linux DMA API are platform and OS definitions, not PCIe or NVMe specifications.

Device → host MRd (non-posted, tagged) answered by CplD; device → host MWr (posted) for read data, CQEs and MSI-X. Requester ID 0x0100 on every device-initiated request.

Analyzer: after a doorbell MWr, an MRd for 64 bytes at the SQ slot, then MRd bursts at the PRP addresses (Write) or MWr bursts (Read), then a 16-byte MWr to the CQ and a 4-byte MWr to 0xFEE0_xxxx.

Completion with UR/CA to a data MRd + DMAR fault in dmesg → IOMMU mapping problem (unmapped too early, wrong address). No MRd after the doorbell → BME off, queue not created, or doorbell address wrong. Data mismatch with clean link → coherence or ownership bug in the driver.

Hardware view

Inside the Lab SSD, several DMA engines share the PCIe core:

  • Command fetch engine: on a doorbell, issues MRd for new SQEs (often several at once, up to the new tail).
  • PRP/SGL walker: parses the data pointers, fetches PRP lists or SGL segments (more MRds), and produces a list of (IOVA, length) segments.
  • Data movers: for Writes, issue MRds (≤ MRRS, not crossing 4 KiB) and reassemble CplDs by tag into the controller's DRAM or SRAM buffer; for Reads, emit MWrs (≤ MPS, not crossing 4 KiB).
  • Completion engine: writes the CQE with the right phase tag, then the MSI-X message — in that order, relying on PCIe ordering so the interrupt cannot overtake the CQE.
  • Tag and completion buffer management: as many outstanding reads as tags and completion buffer allow (Chapter 13, Chapter 16).

Inside the host, the Root Complex receives the TLP, extracts the Requester ID and address, consults the IOMMU (IOTLB hit: tens of ns; miss: a page walk of several memory reads), snoops CPU caches, and reads or writes DRAM through the memory controller. For a read, it then builds CplD TLPs, splitting at RCB boundaries and respecting the device's MPS.

IOTLB misses are a real performance factor for NVMe at high IOPS: every new 4 KiB page touched by DMA may need a translation. Large IOVA mappings (huge pages), passthrough mode, and IOVA caching in the OS reduce the cost. When a platform shows lower throughput with the IOMMU enabled, translation is the first suspect — and, as Chapter 16 showed, slower draining at the Root Complex shows up as posted-credit starvation, not as an error.

Specification view

PCIe defines the transaction rules: PCI Express Base Specification, Revision 6.x/7.0 — Transaction Layer (Memory Read/Write, completion rules, RCB, 4 KiB boundary, attributes), Configuration Space (Bus Master Enable, Device Control), and optional Address Translation Services and Page Request Interface. NVMe defines data-pointer formats and memory requirements: NVMe Base Specification 2.4 — Data Structures (PRP, SGL) and NVMe over PCIe Transport Specification 1.4 (queue memory, PRP use over PCIe). IOMMUs are defined by vendor architecture documents (for example the Intel Virtualization Technology for Directed I/O Architecture Specification and the AMD I/O Virtualization Technology (IOMMU) Specification); the DMA API by the Linux kernel documentation.

Command register bit 2 is Bus Master Enable. Memory Read requests must not cross a 4 KiB boundary; request size is limited by MRRS and write payload by MPS. Completions may be split at RCB boundaries. No Snoop and Relaxed Ordering are TLP attributes enabled through Device Control. NVMe queues and data buffers are in host memory and accessed by the controller via DMA, using addresses the host supplies.

The PIO vs DMA cost comparison, the 8-MRd breakdown of a 4 KiB Write, and the claim that IOMMU translation latency appears as credit starvation are reasoned from the rules and the lab system's parameters.

IOMMU behaviour on faults (completion status, logging), IOTLB size, page-walk cost; Root Complex completion sizes (64 B vs larger); whether No Snoop is honoured; controller DMA engine counts and policies; Linux IOMMU modes and swiotlb sizing.

ATS, PRI and PASID were added to PCIe in later revisions and evolve with each; 10-bit and 14-bit tags (PCIe 4.0 and 6.0) raise outstanding-read limits; NVMe SGL support and options grew across NVMe 1.x and 2.x; the Linux DMA API's internals (e.g. IOVA caching, DMA-API debugging) change between kernel versions.

Check in the specifications: exact RCB rules and completion splitting; which attributes a completer must preserve; ATS/PRI details; PRP alignment rules (Chapter 36). The PCIe and NVMe specifications do not define IOMMUs, IOVAs, cache coherence policy or the Linux DMA API — be careful not to cite them for those.

Never assume a TLP address is a physical address; never assume a DMA has finished because a doorbell was written; never touch a streaming-mapped buffer from the CPU while the device owns it; never assume x86 coherence semantics on other architectures.

Reasoning:

  1. The first three pages read fine; the fourth faults. A wrong PRP would usually fault on the first page or point outside the buffer; here the address is exactly where the buffer should continue, so the mapping was missing, not the pointer.
  2. Two classic causes: the driver unmapped (or the IOMMU invalidated) the last page before the device finished — a lifetime bug, often in an error or timeout path; or the mapping was created for 12 KiB instead of 16 KiB (length bug in the SG list).
  3. Evidence to collect: the IOMMU fault address and Requester ID (identifies device and page), the NVMe status and CID (identifies the command), the driver's mapping log (DMA-API debug facilities can catch unmap-while-active bugs in a lab).
  4. Without an IOMMU, the same bug would have read whatever physical memory that page now held — silent corruption on disk. The IOMMU turned a silent corruption into a loud error.

How an NVMe driver uses the DMA API (pseudocode)

/* probe */
pci_set_master(pdev);                                   /* Command.BME = 1 */
if (dma_set_mask_and_coherent(&pdev->dev, DMA_BIT_MASK(64)))
        fail("no usable DMA addressing");

/* queue creation: long-lived, shared, coherent memory */
sq_cpu = dma_alloc_coherent(&pdev->dev, depth * 64, &sq_dma, GFP_KERNEL);
cq_cpu = dma_alloc_coherent(&pdev->dev, depth * 16, &cq_dma, GFP_KERNEL);
/* sq_dma / cq_dma are IOVAs: they go into Create I/O SQ/CQ commands (or ASQ/ACQ) */

/* per I/O: streaming mapping of the request's pages */
nents = dma_map_sg(&pdev->dev, sgl, nr_segments,
                   is_write ? DMA_TO_DEVICE : DMA_FROM_DEVICE);
if (nents == 0) fail("mapping failed");
build PRP1/PRP2 (or SGL) from sg_dma_address(sg) / sg_dma_len(sg);
copy SQE into sq_cpu[tail]; tail = (tail + 1) % depth;
wmb();                                                  /* SQE visible before doorbell */
writel(tail, sq_tail_doorbell);                         /* MMIO, Chapter 19 */

/* completion (interrupt handler) */
while (cqe_phase_matches(cq_cpu[head])) {
        dma_rmb();                                      /* read CQE fields after phase */
        req = lookup(cqe.cid);
        dma_unmap_sg(&pdev->dev, req->sgl, req->nr_segments, req->dir);
        complete(req, cqe.status);                      /* CPU owns the buffer again */
        head = (head + 1) % depth;
}
writel(head, cq_head_doorbell);

/* teardown: only after the controller is disabled and no DMA can be in flight */
dma_free_coherent(&pdev->dev, depth * 64, sq_cpu, sq_dma);

Note the order in error paths: a command that timed out may still be executing in the device. Unmapping its buffers before the controller has been reset or the command aborted is exactly the bug in Trace 2.

Simulation: IOVA translation and MRd splitting

This standard-library simulation maps four scattered physical pages to a contiguous IOVA range, splits a 16 KiB device read into MRd requests (≤ MRRS, never crossing 4 KiB), translates each through a toy IOMMU, splits completions at 64-byte boundaries, and finally shows the fault when a page is unmapped too early.

"""From a driver's buffer to PCIe TLPs: IOMMU translation, scatter-gather and
Memory Read splitting (simulation, standard library only).

Models the Lab SSD fetching write data for a 16 KiB NVMe Write:
  - the buffer is 4 physically scattered 4 KiB pages,
  - the driver maps it to a contiguous IOVA range (as an IOMMU allows),
  - the device issues MRd requests no larger than MRRS that never cross 4 KiB,
  - the Root Complex returns completions in RCB-aligned pieces."""

PAGE = 4096
MRRS = 512            # Max Read Request Size (bytes)
CPL_CHUNK = 64        # Root Complex returns 64-byte completions (RCB = 64)

class Iommu:
    def __init__(self):
        self.ptes = {}                       # IOVA page number -> physical page number
    def map(self, iova, phys_pages):
        for i, ppn in enumerate(phys_pages):
            self.ptes[iova // PAGE + i] = ppn
    def unmap(self, iova, npages):
        for i in range(npages):
            self.ptes.pop(iova // PAGE + i, None)
    def translate(self, iova):
        ppn = self.ptes.get(iova // PAGE)
        if ppn is None:
            raise LookupError(f"IOMMU fault: IOVA {iova:#x} not mapped")
        return ppn * PAGE + iova % PAGE

def device_reads(iova, length, tag0=0x20):
    """Split a DMA read into MRd requests: <= MRRS, never crossing a 4 KiB boundary."""
    reqs, tag = [], tag0
    while length:
        to_boundary = PAGE - iova % PAGE
        n = min(length, MRRS, to_boundary)
        reqs.append((tag, iova, n))
        iova, length, tag = iova + n, length - n, tag + 1
    return reqs

def root_complex(iommu, tag, iova, n):
    """Translate, then return completions split at RCB-aligned boundaries."""
    pa = iommu.translate(iova)
    cpls, remaining, addr = [], n, iova
    while remaining:
        chunk = min(remaining, CPL_CHUNK - addr % CPL_CHUNK)
        remaining -= chunk
        cpls.append((tag, chunk, remaining + chunk))     # (tag, length, byte count)
        addr += chunk
    return pa, cpls

if __name__ == "__main__":
    iommu = Iommu()
    phys = [0x7A3C1, 0x11F02, 0x7A3C9, 0x3300A]          # scattered physical pages
    iova = 0x2_0000_0000                                  # contiguous IOVA (lab system)
    iommu.map(iova, phys)
    print("driver: dma_map_sg -> IOVA", hex(iova), "for pages",
          [hex(p * PAGE) for p in phys])
    reqs = device_reads(iova, 4 * PAGE)
    print(f"device: {len(reqs)} MRd requests (MRRS={MRRS})")
    for tag, a, n in reqs[:3]:
        pa, cpls = root_complex(iommu, tag, a, n)
        print(f"  MRd64 Tag={tag:#04x} Addr={a:#x} Len={n // 4}DW -> PA {pa:#x}, "
              f"{len(cpls)} CplD: first ByteCount={cpls[0][2]}, last ByteCount={cpls[-1][2]}")
    print("  ...")
    tag, a, n = reqs[8]
    pa, _ = root_complex(iommu, tag, a, n)
    print(f"  MRd64 Tag={tag:#04x} Addr={a:#x} -> PA {pa:#x} (second page, different frame)")
    # A buggy driver unmaps before the device has finished:
    iommu.unmap(iova + 3 * PAGE, 1)
    try:
        root_complex(iommu, 0x3F, iova + 3 * PAGE, 512)
    except LookupError as e:
        print("  ", e, "-> Root Complex completes the MRd with an error status (UR/CA)")

Worked example

Problem. A 12 KiB NVMe Read lands in a buffer starting at IOVA 0x2_0000_0F00 (not page-aligned). MPS = 256 B. How many MWr TLPs does the SSD send for the data, and what are the first three?

Step 1 — boundaries. The buffer spans 0x2_0000_0F00 to 0x2_0000_3EFF. Writes must not cross 4 KiB boundaries (0x…1000, 0x…2000, 0x…3000) and carry at most 256 bytes.

Step 2 — first segment. From 0x…0F00 to 0x…0FFF is 256 bytes: one MWr of 64 DW at 0x2_0000_0F00.

Step 3 — full pages. 0x…1000–0x…1FFF and 0x…2000–0x…2FFF: 4096 / 256 = 16 MWr each → 32.

Step 4 — tail. 0x…3000–0x…3EFF = 3840 bytes = 15 MWr.

Total 1 + 32 + 15 = 48 MWr TLPs (12 288 / 256 = 48 — the misalignment happened to fall on a 256-byte boundary, so no extra TLP). First three: MWr64 Addr=0x2_0000_0F00 Len=64DW; Addr=0x2_0000_1000 Len=64DW; Addr=0x2_0000_1100 Len=64DW. If the buffer had started at 0x2_0000_0F80, the first TLP would be only 128 bytes and the total 49 — misaligned buffers cost extra TLPs. Derived PRP rules about offsets are in Chapter 36.

Common mistakes

  • Putting a CPU virtual address (or a physical address with an IOMMU) in a PRP. Always use the dma_addr_t from the DMA API.
  • Unmapping before the device is done, especially in timeout and error paths.
  • Wrong direction flag: DMA_TO_DEVICE for a Read command buffer makes the IOMMU mapping read-only — the device's MWr faults.
  • Forgetting pci_set_master in custom or test drivers.
  • Assuming "it works on x86" proves correctness of cache handling.
  • Using coherent memory for bulk data: coherent mappings may be uncached on some platforms and slow for CPU access; use streaming mappings for data.
  • Ignoring swiotlb messages: bounce buffering silently halves throughput.
  • Confusing MMIO with DMA direction: doorbells are CPU→device MMIO; data is device-initiated DMA.

Senior engineer insight

Almost every serious DMA bug is a lifetime bug: memory reused, freed or unmapped while a device can still access it. The hardest cases involve resets and timeouts — the driver gives up on a command, but the device has not. A robust driver makes "the device can no longer touch this memory" an explicit, verified state (controller disabled, queues deleted, BME cleared, IOMMU domain detached) before freeing anything. Ask for that proof in every design review of an error path.

On test and validation systems, run with the IOMMU in strict, translated mode and DMA-API debugging enabled. Production may run in passthrough for performance, but validation should run in the mode that converts corruption into faults. The same principle — make the first abnormal event observable — runs through the whole course.

Challenge

Hint

0x2_0000_0800 + 16 KiB = 0x2_0000_4800: the transfer touches five 4 KiB pages (0x0…, 0x1…, 0x2…, 0x3…, 0x4…).

Solution

(Step 1) 0xFE60_xxxx addresses are MMIO in BAR0 (CPU physical, no IOMMU); 0x1_2340_xxxx (SQ), 0x1_5000_0000 (PRP list) and 0x2_00xx_xxxx (data) are IOVAs. (Step 2) 0x…0800–0x…0FFF: 2048 B = 8 MWr; three full pages = 48 MWr; 0x…4000–0x…47FF: 8 MWr; total 64 = 16 384 / 256 — again aligned to 256 B so no extra TLPs, but five pages touched, so potentially five IOTLB lookups instead of four. (Questions) (1) On x86, the 0xFEE0_xxxx range is the interrupt window; with interrupt remapping, the IOMMU treats these writes as interrupt requests and translates them through an interrupt remapping table rather than DMA page tables. (2) No fault; the device would read whatever physical memory corresponds to the identity-mapped IOVA — potentially stale or reused data, silently. (3) dma_alloc_coherent (its dma_handle output) when the queue was created.

What a senior engineer notices

That address classification is the fastest way to orient in any NVMe trace: MMIO addresses tell you what the host did; IOVA addresses tell you what the device did; Requester IDs tell you who.

Failure variants

  • Device limited to 32-bit DMA without an IOMMU: buffers above 4 GiB bounce through swiotlb.
  • Device assigned to a VM (VFIO): IOVAs are guest physical addresses; faults are reported against the host's view of the device.

Model answers

(1) 0x…0F00 len 256 B (stops at the 4 KiB boundary); 0x…1000 len 512; 0x…1200 len 512; 0x…1400 len 512; 0x…1600 len 256 — total 2048. Quiz

  1. Which Command register bit must be set for an NVMe controller to fetch SQEs?

    • Memory Space Enable (bit 1)
    • I/O Space Enable (bit 0)
    • Bus Master Enable (bit 2)
    • Interrupt Disable (bit 10)
    Answer and reasoning

    Fetching SQEs is a device-initiated MRd, which requires BME.

  2. An address in a device-initiated MRd on an IOMMU-enabled system is:

    • A CPU virtual address
    • An IOVA
    • Always a physical address
    • A BAR address
    Answer and reasoning

    The device uses the IOVA the driver obtained from the DMA API; the IOMMU translates it.

  3. Which Linux call is appropriate for an I/O Submission Queue?

    • dma_alloc_coherent
    • dma_map_single per command
    • kmalloc and virt_to_phys
    • ioremap
    Answer and reasoning

    Queues are long-lived, shared CPU/device memory: coherent allocation. ioremap is for MMIO.

  4. A Memory Read request may not:

    • Use a 64-bit address
    • Be split into several completions
    • Carry a tag
    • Cross a 4 KiB address boundary
    Answer and reasoning

    The 4 KiB boundary rule applies to requests.

  5. On a non-coherent platform, before the device reads a buffer the CPU wrote, the DMA API must:

    • Invalidate CPU caches
    • Clean (write back) CPU caches
    • Disable the IOMMU
    • Set No Snoop
    Answer and reasoning

    Dirty lines must reach memory before the device reads it. Invalidation is needed before the CPU reads device-written data.

  6. For an NVMe Read command, how does data travel?

    • CPU MMIO reads from BAR0
    • Device MRd, host CplD
    • Device MWr into host memory
    • CfgWr
    Answer and reasoning

    The device writes read data into host memory with posted MWrs.

  7. Open: Why does an IOMMU turn some silent corruptions into visible errors?

    Model answer

    Without an IOMMU, a device access to a wrong or stale address reaches whatever memory is there. With an IOMMU, only explicitly mapped IOVAs translate; other accesses are blocked and logged as faults, and reads complete with an error status that the device reports.

  8. Open: Describe the controller → MRd → host memory → CplD path, naming who translates what.

    Model answer

    The controller's DMA engine issues an MRd with its Requester ID and an IOVA from the PRP. The Root Complex's IOMMU uses the Requester ID to select tables and translates the IOVA to a physical address, checking permission; the coherent fabric snoops caches; the memory controller reads DRAM; the Root Complex returns CplD TLPs with the same tag, split at RCB boundaries, to the controller, which reassembles them.

  9. Open: An NVMe driver frees a buffer when a command times out, and occasional corruption appears in unrelated kernel data. Explain.

    Model answer

    The command was still active in the device. When it eventually performed its DMA (a Read writing data into the freed buffer), it overwrote memory that had been reallocated to someone else. Without an IOMMU (or with lazy invalidation), nothing blocked it. The fix is to ensure the device cannot access the buffer (abort/reset completed) before freeing.

Interview questions

  1. Beginner: Why do storage devices use DMA instead of letting the CPU copy data?

    Model answer

    CPU copying through MMIO is slow (non-posted reads stall the CPU, small transactions waste link bandwidth) and consumes CPU time; DMA lets the device move data in large, pipelined transactions while the CPU does other work.

  2. Beginner: What is bus mastering?

    Model answer

    A device's ability to initiate memory transactions on the bus, controlled by the Bus Master Enable bit in its Command register (and in the bridges above it).

  3. Intermediate: What is the difference between dma_alloc_coherent and dma_map_single?

    Model answer

    Coherent allocation creates long-lived memory that CPU and device can both access at any time without explicit syncs; streaming mapping maps existing memory for a transfer, transferring ownership to the device until unmap or sync, with cache maintenance done at those points.

  4. Intermediate: What does an IOMMU do and why does NVMe care?

    Model answer

    It translates device-issued IOVAs to physical addresses per device and blocks unmapped accesses. NVMe cares because every queue, PRP list and data buffer address is an IOVA, faults surface as Data Transfer Errors, and translation cost affects throughput.

  5. Advanced: How can Relaxed Ordering cause an NVMe correctness problem, and how is it avoided?

    Model answer

    If the CQE write were allowed to pass earlier data writes, software could see the completion before the data is in memory. Controllers set Relaxed Ordering only on data writes and not on the CQE (or rely on rules that RO does not let later writes pass earlier ones in a way that breaks this), and platforms that mishandle RO have it disabled via Device Control.

  6. Senior: Design a validation plan for DMA in a new NVMe controller.

    Model answer

    Cover every PRP/SGL alignment and length class, 4 KiB boundary crossings, MRRS/MPS combinations, completion splitting by the host (various RCB behaviours), tag exhaustion, error completions (UR/CA) at every point of a transfer and the resulting NVMe statuses, IOMMU strict mode with fault injection, No Snoop and Relaxed Ordering on/off, reset and timeout during active DMA with checks that no access occurs after abort, and data-integrity patterns across power cycles.

Chapter summary

DMA lets the NVMe controller move commands, data, completions and interrupts itself, using its own engines driven by descriptors in host memory (SQEs, PRPs/SGLs). It requires Bus Master Enable, prepared memory, and correct addresses. The device emits I/O virtual addresses; the IOMMU translates them per Requester ID and blocks anything unmapped, turning silent corruption into faults. Cache coherence is maintained by snooping on coherent platforms and by explicit cache maintenance (inside the DMA API) on others; No Snoop and Relaxed Ordering trade safety for performance. Linux drivers use dma_set_mask_and_coherent, dma_alloc_coherent for queues, and streaming mappings (dma_map_sg/dma_map_single) with strict ownership rules for data. On the link, a device read of host memory is MRd (≤ MRRS, not crossing 4 KiB) answered by CplDs split at RCB; a device write is a posted MWr (≤ MPS).
