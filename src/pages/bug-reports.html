A bug report is the product of an investigation. If it is vague, the investigation is wasted. This page teaches the seventeen-field report the course uses, field by field. It then shows two complete reports that a firmware or driver team could act on without a meeting, and two weak reports for you to critique before reading the critique.

Why bug reports deserve training

In NVM Express (NVMe) and PCI Express (PCIe) work, the person who finds a problem is rarely the person who fixes it. A validation engineer finds it; a firmware engineer in another time zone, a platform vendor, or a Linux maintainer fixes it. The report is the only thing that crosses that gap. A good report gets a fix in days. A bad one starts weeks of "can you send logs?", "which firmware?", "can't reproduce".

Learning objectives

  • Write each of the seventeen fields so that it answers the reader's question without follow-up.
  • Separate observation, inference and opinion, and state confidence.
  • Present the first abnormal event with enough evidence that the reader can check it independently.
  • Write a regression test that targets the mechanism, not just the original reproduction.
  • Critique a weak report and rewrite it.

Prerequisites

The evidence-handling method from Debugging Methodology and Evidence-Based Debugging and Spec Safety; forensic reporting in Root Cause, Ambiguity and Forensic Reporting; error correlation in Chapter 47.

Imagine leaving a note for the person who looks after your dog while you are away. "Dog weird, fix pls" is no help. "Since Tuesday, Rex limps on his front left leg after walks longer than 20 minutes, not after short ones; he ate normally; here's a video" lets them act straight away.

The dog note is written for one reader who already knows the dog. A bug report is read by people who have never seen your system, sometimes months later, sometimes by a tool. It must name every version, link every artefact, and make sense without you there.

Title

A title has three parts: component and version, condition, effect. "LS-2 FW LS2F104: Write commands with PRP lists longer than one page write a PRP list page to media instead of user data." A reader scanning a bug tracker should be able to tell from the title alone whether it is theirs and how bad it is. Avoid "!!!", "URGENT", and blame words ("broken", "stupid").

Environment, Hardware, Firmware, OS

These four fields make the bug reproducible. Write down every component that could plausibly matter, with exact identifiers:

  • Hardware: host model, CPU, slot or bay, risers, retimers or switches between root port and device, the SSD model and capacity, and any analyzer interposer (it changes the electrical channel).
  • Firmware: SSD firmware revision, platform firmware (BIOS/UEFI) revision, retimer or switch firmware, baseboard management controller (BMC) firmware if it touches the device.
  • OS: distribution, kernel version, driver (in-box or other), and non-default parameters (I/O timeout, power-state latency limits, ASPM policy, IOMMU mode).
  • Environment: the test tool and its version, the workload parameters, temperature if relevant, and whether the system was under other load.

Attach a single command's output that captures the environment automatically (for example a script that saves uname -a, lspci -vvv for the device and its upstream port, nvme id-ctrl, the kernel command line and the firmware revisions). People forget fields; scripts do not.

PCIe generation and link width

Report the negotiated values from Link Status, and the capability values from Link Capabilities on both ends if they differ. "Gen5 x4 capable, negotiated Gen4 x4 (root port LnkCap Gen4)" tells the reader something; "Gen5" does not. If the problem involves link training, include LTSSM state history.

NVMe revision

The value the controller reports in the Version register, plus the features relevant to the bug (for example "APST enabled, PS4 allowed", "SGLs supported but not used", "Volatile Write Cache enabled"). If your argument cites the specification, name the document and revision you read (for example NVM Express Base Specification 2.4) and the section by name.

Reproduction steps

Numbered, minimal, and runnable by someone else. Include the reproduction rate ("7 of 10 runs, each 30 minutes") and the smallest known trigger. If you can only reproduce it with a private script, attach the script or describe its I/O pattern precisely (sizes, alignment, queue depth, read/write mix, idle times).

Expected and actual result

Expected: what the specification or the design says should happen, with a reference. Actual: what you observed, in observable terms (status codes by name, timings, data mismatch offsets), not your interpretation. "Read returns Unrecovered Read Error status for LBA 0x1000" is actual; "media is bad" is an interpretation and belongs in Root cause.

Trace evidence

Point to the exact rows. Give file name, analyzer software version, the time or packet number, and a short excerpt in the report body. Label provenance: real capture, excerpt, or reconstruction. State the clock alignment if you merge sources. A reader should be able to confirm your claim in five minutes.

First abnormal event

One event, with time, source, and why it is abnormal (which rule or expectation it breaks). Also list earlier anomalies you excluded, with the reason. This field is where reports most often go wrong: see Debugging Methodology.

Root cause

The mechanism, at the level the fixing team can act on, plus a confidence level and what would raise it. Use the confidence vocabulary below. If the root cause is not known, say so and give ranked hypotheses with the evidence for each. A good report with an honest "unknown" is far more useful than a confident wrong answer.

Workaround

What a user can do now, what it costs (power, performance, features), and any risk. "Disable ASPM L1.2 on this port; idle power rises by about 1.3 W per drive" is complete.

Permanent fix

What change removes the mechanism, and in which component. If you are not on the fixing team, propose; do not dictate implementation details.

Regression test

A test that would have caught this bug and would catch a similar one. It targets the mechanism (all boundary cases of the condition), runs automatically, has a clear pass/fail criterion, and states where it will run (every firmware release, every kernel update, every platform qualification).

Writing discipline: facts, inferences, confidence

A report mixes three kinds of statement. Label them so the reader knows which they are reading.

Three kinds of statement
KindExampleHow to signal it
Observation"Packet 18,233: CQE written for CID 0x004A; no MSI-X write within the next 30 s."Past tense, with a source reference
Inference"Therefore the controller did not signal the interrupt.""Therefore", "this indicates", with the reasoning
Hypothesis or opinion"We believe the interrupt block is not ready after deep idle.""We believe", "likely", plus a confidence level

Confidence vocabulary

Use these words consistently
WordMeans
ConfirmedA discriminating experiment was predicted and observed, or the fixing team verified it in code
High confidenceAll evidence consistent; alternatives eliminated by evidence; not yet confirmed by fix
Medium confidenceEvidence consistent; at least one plausible alternative not yet eliminated
Low confidenceA plausible lead; evidence thin or indirect
UnknownNo supported hypothesis yet; the report documents symptoms and evidence

Style rules that save time

  • Use names and numbers, not adjectives: "30.02 s", not "very long".
  • Write hexadecimal consistently (0x prefix or h suffix, not both) and give units for every number.
  • Use the specification's names for fields and statuses (CSTS.CFS, "Invalid Field in Command"); do not invent bit positions or codes.
  • Quote log lines exactly, and say when you paraphrase or trim them.
  • No blame. "The controller does not answer register reads during activation" is better than "vendor firmware is broken".
  • Keep the body under two pages. Put everything else in labelled attachments.

Severity and priority

Severity describes impact; priority describes urgency for the business. Teams define their own scales, but impact classes are almost universal, in this order: data integrity (silent corruption, data loss) > data availability (device lost, I/O errors) > performance (latency, throughput) > cosmetic (wrong log text). Say which class the bug is in, and the population affected (all units, one firmware, one platform).

Logs and captures can contain user data (read and write payloads), host names, serial numbers and keys. Strip payloads you do not need, and follow your organisation's rules before sending captures outside it. If the bug involves a confidential specification draft or a supplier's confidential document, refer to it by name, not by quotation.

Excellent report 1 — a device firmware bug

This report is about a fictional SSD on the course's reference lab system. It shows the template at its best: short body, exact evidence, honest confidence, and a regression test aimed at the mechanism.

Title
LS-2 FW LS2F104: Writes needing a chained PRP list (more than 512 pages) write the second PRP list page to media in place of user data
Environment
Validation host "val-07"; fio 3.x with verify=crc32c plus a custom pattern checker; I/O sizes 1 MiB–4 MiB, sequential, queue depth 4; IOMMU in strict mode.
Hardware
Lab SSD LS-2, 1 TB, at 0000:01:00.0, direct slot (no riser) behind root port 0000:00:01.1. Analyzer interposer installed for the captures; reproduces without it.
Firmware
SSD LS2F104 (fails), LS2F102 (passes). Platform firmware 1.12.
OS
Linux 6.x, in-box NVMe driver; max_sectors_kb raised to 4096 so the block layer sends 4 MiB commands; otherwise defaults.
PCIe generation
Gen4 16.0 GT/s negotiated (both ends Gen4-capable).
Link width
x4 negotiated.
NVMe revision
VS 2.0. MDTS = 0Ah (210 × 4 KiB = 4 MiB). SGLs not supported for I/O; PRPs used.
Reproduction steps
  1. Format namespace 1 with 512-byte LBAs (any LBA format reproduces).
  2. Write 4 MiB at LBA 0 from a 4 KiB-aligned buffer with a per-512-byte self-describing pattern (LBA number and a run ID in each sector).
  3. Read back 4 MiB and compare.
  4. Repeat with sizes 2 MiB, 2 MiB + 4 KiB, 3 MiB.

Result: 2 MiB passes (100/100). 2 MiB + 4 KiB, 3 MiB and 4 MiB fail (100/100 each).

Expected result
Read-back data equals written data. A transfer of more than 512 pages with PRP1 at offset 0 needs PRP1 plus more than 511 list entries; per the PRP rules in NVM Express Base Specification — Physical Region Page entry and list, the last entry of a full PRP list page points to the next list page rather than to data.
Actual result
For a 4 MiB write, the 4 KiB at byte offset 0x1FF000 (the 512th page) read back as a table of 64-bit values 0x0000_0002_0020_0000, 0x0000_0002_0020_1000, … (the contents of the second PRP list page). Every later page is shifted by one page, and the last page of the buffer is never written. Command status: Successful Completion. No AER errors, no IOMMU faults.
Trace evidence
Capture ls2-prpchain-4m.cap (analyzer software version recorded in the file), packets 1,204–2,290. Excerpt:
PktDirTypeFieldsMeaning
1,204Dev→HostMRd64Addr=0x1_5000_0000 Len=128DWReads first PRP list page (first 512 bytes)
… 7 more 512-byte reads complete the 4 KiB list page …
1,290Dev→HostMRd64Addr=0x2_0000_1000 Len=128DWData page 2 (first list entry), as expected
2,210Dev→HostMRd64Addr=0x1_5000_1000 Len=128DWEntry 511 (the chain pointer) used as a data page: the device reads the second list page as write data
The device then fetches further list entries from the bytes that follow the first list page (0x1_5000_1000 onward, which here happens to be the second list page), so every later data page is one page late and the last page of the buffer is never read.
First abnormal event
Packet 2,210: memory read of 0x1_5000_1000 (the address in entry 511 of the first list page, which per the PRP rules is the next-list pointer) issued as a data read. No earlier anomaly in the capture.
Root cause
The controller's PRP walker does not treat the last entry of a full PRP list page as a chain pointer when more entries remain. Confidence: high (failure threshold exactly at 512 pages; trace shows the pointer used as data; passes on LS2F102). The vendor's code reference would confirm.
Workaround
Limit host I/O size to 2 MiB (for example max_sectors_kb=2048). Cost: none measurable for this workload; some large sequential workloads may lose a few percent.
Permanent fix
Firmware: in the PRP walker, when the current list page's last entry is reached and bytes remain, fetch that entry as the next list page. Re-check the related case where the first list starts at a non-zero offset within its page, if the specification allows it for PRP2.
Regression test
For every firmware release: write/read/verify with transfer sizes of 1, 2, 3, 511, 512, 513, 1,023, 1,024 pages and MDTS; PRP1 offsets 0, 512 and 4,092 bytes; list pages placed at the end and the start of a page; IOMMU strict; self-describing data patterns; pass = zero mismatches and zero IOMMU faults.
  • The title alone tells the firmware team the area of code.
  • The size threshold is measured precisely and connected to the mechanism (512 pages = one list page full).
  • The data mismatch is described in a way that proves the mechanism (the corrupted page contains addresses).
  • An earlier firmware passes, giving the fixing team a diff to look at.
  • Confidence is stated with reasons; the regression test covers the whole boundary, not just 4 MiB.

Excellent report 2 — a host driver bug

Reports are not only for device vendors. This one goes to a host driver team and shows that the reporter checked the device's side before blaming the host, and the host's side before blaming the device.

Title
Custom user-space NVMe driver v0.9 on arm64: SQ tail doorbell can reach the controller before the SQE is visible, causing the controller to fetch a zeroed entry (status Invalid Namespace or Format for CID 0) and the real command to time out
Environment
Storage appliance software 4.2 with its bundled user-space NVMe driver v0.9 (polled mode, no interrupts). Workload: 4 KiB random reads, 16 threads, queue depth 64 each.
Hardware
arm64 server (weakly ordered memory model), Lab SSD LS-2 at 0000:01:00.0. The same SSD and software on an x86-64 server do not reproduce (0 in 48 h).
Firmware
SSD LS2F104; platform firmware 2.3.
OS
Linux 6.x; device bound to VFIO; IOMMU on.
PCIe generation
Gen4 negotiated.
Link width
x4 negotiated.
NVMe revision
VS 2.0; standard 64-byte SQEs, 16-byte CQEs.
Reproduction steps
  1. Run the appliance's I/O benchmark mode for 4 hours on the arm64 server.
  2. Count driver warnings "completion for unknown CID 0" and command timeouts.

Rate: 3–9 events per 4 hours on arm64; 0 on x86-64.

Expected result
The controller fetches the SQE the driver wrote. The driver must make the 64-byte SQE visible in memory before the doorbell write reaches the device; the controller may fetch the entry as soon as it sees the doorbell.
Actual result
Occasionally the controller completes a command with CID 0x0000 and status Invalid Namespace or Format, a CID the driver never issued in that slot. The command the driver did place in that slot never completes and times out after 10 s.
Trace evidence
Capture arm64-zero-sqe.cap, packets 88,410–88,431:
PktDirTime (ns)TypeFieldsMeaning
88,410Host→Dev0MWr32Addr=0xFE60_1018 Data=0x0000_02C1SQ3 tail = 705 (slot 704 newly filled)
88,412Dev→Host790MRd64Addr=SQ3 base + 0xB000 Len=16DW Tag=0x3AFetch slot 704
88,414Host→Dev1,310CplDTag=0x3A, 64 bytes, all zeroThe fetched SQE is all zeros
88,431Dev→Host3,900MWr64CQE: SQID 3, CID 0x0000, status Invalid Namespace or FormatController rejects the zeroed command

A host memory dump of SQ3 slot 704 taken by the driver's timeout handler 10 s later shows a valid Read SQE (opcode 02h, CID 0x02C0). The driver zeroes slots after completion, which is why the stale content is zero.

First abnormal event
Packet 88,414: the completion to the controller's SQE fetch returns zeros for a slot the driver had already filled (according to its own submission log) before ringing the doorbell at packet 88,410.
Root cause
The driver writes the doorbell with a relaxed memory-mapped I/O store and no write barrier between the SQE stores (normal cacheable memory) and the doorbell store (device memory). On arm64 these stores may become visible out of order; the controller sees the doorbell and fetches the slot before the SQE stores are visible. Confidence: confirmed: adding a write barrier before the doorbell store (or using an ordered MMIO write accessor) removes the failure (0 events in 72 h on arm64); removing it brings it back.
Workaround
None safe without a code change. Running on x86-64 masks the bug because of its stronger store ordering; that is not a workaround to rely on.
Permanent fix
Use an ordered doorbell write (a barrier that orders prior normal-memory stores before the device store) in the submission path; review the completion path for the matching read-side rule (read the phase bit, then a read barrier, then the rest of the CQE).
Regression test
On every supported weakly ordered architecture: 24 h of high-rate submission with a firmware or analyzer check that every fetched SQE has a CID the driver issued for that slot; plus a code-level test that fails the build if the doorbell write uses a relaxed accessor without an explicit barrier.
  • It proves the device behaved correctly: it fetched what was in memory and rejected an invalid command.
  • It uses the architecture difference as evidence, not as a workaround.
  • It confirms the root cause with a reversible experiment (add the barrier, remove it).
  • The regression test includes a static check, so the mistake cannot come back in another code path.

Poor report 2 — long, detailed, and wrong

This one looks thorough. It is harder to critique because it contains real evidence. Find at least six problems before opening the critique.

Title: SSD firmware causes PCIe Completion Timeout and NVMe resets

Environment: Our production cluster, latest software.

Description: We are seeing lots of AER errors on many servers. The SSD obviously has a firmware problem with completions. Below is the dmesg from one server (2,140 lines). You can see the Completion Timeout and then the NVMe driver resets the controller, and sometimes we also see Receiver Errors and Bad TLP. We think the SSD sometimes doesn't send completions. This started recently. We tried a different SSD vendor on two servers and haven't seen it yet (one day of testing). We also changed the I/O scheduler, which made it a bit better. Please provide a firmware fix.

Attachments: dmesg.txt (2,140 lines, from one server, timestamps removed for privacy)

Critique
  1. The conclusion is in the title, without evidence. "SSD firmware causes…" presumes the root cause. Titles should describe the observable failure.
  2. Who detected the Completion Timeout? The report does not say whether the root port or the SSD logged it. If the root port logged it, the requester was the CPU, and the SSD failing to answer is one of several possibilities; if the SSD logged it, the SSD's own reads went unanswered, which points away from the SSD (see Chapter 46).
  3. Receiver Errors and Bad TLP are mentioned but not ordered. If they come first, the cascade probably starts in the physical layer and the Completion Timeout is a consequence. The report treats the loudest error as the cause.
  4. Timestamps removed. Without them, ordering — the most important evidence — is lost. Redact host names, not timestamps.
  5. "Lots", "many servers", "recently", "a bit better". No counts, no population, no date, no measurement.
  6. "Latest software". Kernel, driver, platform firmware and SSD firmware versions are all missing, as are link generation and width.
  7. The vendor swap is presented as evidence but is not. One day on two servers is too small a sample if the failure rate is low; the report does not state the base rate.
  8. Changing the I/O scheduler "made it better". A host software change that alters the failure rate is an important clue (timing, queue depth), and it is mentioned in passing.
  9. No first abnormal event, no trace, no reproduction steps.
  10. The request ("provide a firmware fix") assumes the answer. Better: "please help determine whether the SSD is answering requests, and send your debug logs".

How a strong engineer would rewrite it (outline): Title: "Root port 00:01.1 logs Receiver Errors, then Completion Timeout, then NVMe controller reset, on cluster nodes with platform firmware 1.12 (11 of 240 nodes, 1–3 events/day)". Then: full environment; a table of AER events with timestamps and detecting agent; the ordering showing Receiver Errors first; per-node link speed and width; a hypothesis list with physical layer first; a request for an analyzer capture on one affected node; and the open question about the I/O scheduler effect. That version gets the right team involved on day one, and may well turn out not to be an SSD problem at all.

Lab: rewrite a report from raw evidence

Safe lab Paper exercise.

Objective

Turn an engineer's raw notes into a complete seventeen-field report.

Skills

Ordering evidence, finding the first abnormal event, separating fact and inference, writing a regression test.

Safety

None: no hardware involved.

Hardware and software required

None. A text editor.

Input

- lab box val-12, LS-2 fw LS2F104, platform fw 1.12, kernel 6.x
- laptop-style suspend test (s2idle) x 200 loops; after loop 37 writes fail
- dmesg: AER fatal at 01:00.0 "Malformed TLP", then link reset, then nvme reset, then loops
- reads OK after resume, Identify OK
- lspci before suspend: both ends MaxPayload 256
- lspci after resume: 01:00.0 MaxPayload 128, root port still 256
- header log DW0 = 4A000040
- fio write 4k fails, 512B write (one LBA) also fails
- if I set the SSD MPS back to 256 with setpci after resume -> works (I know, expert only)
- platform fw 1.07: 200 loops, no failure

Expected output

A report with all seventeen fields and a one-paragraph explanation of the first abnormal event.

Background

Maximum Payload Size (MPS) and Malformed TLP rules: Chapter 18, Chapter 45. Resume and configuration restore: Chapter 50.

Step 1

Sort the notes into: environment facts, observations, experiments, and opinions.

Step 2

Decode the header log DW0 and explain why it is malformed at the SSD.

Step 3

Write the report. Decide who should receive it.

Observation

Note which facts in the raw notes are evidence for the root cause and which are evidence against alternatives.

Questions

  1. Why does a 512-byte write fail even though 512 bytes is not larger than 256? (Think about what the SSD receives, not what it sends.)
  2. Is the setpci experiment evidence, a workaround, or both? How should the report present it?
  3. Which team owns the fix?

Challenge

The notes say "after loop 37": the first 36 loops passed. Propose a hypothesis for why it is not every loop, and the evidence you would ask for.

Hints

DW0 0x4A000040: Fmt and Type in the top byte, Length in the low 10 bits. For writes, the SSD reads host memory, and the root port answers with completions; their size is limited by the root port's MPS and Read Completion Boundary, not by the write's size alone. And the root port's completions for a 512-byte read can be 256 bytes each.

Solution

DW0 0x4A000040 decodes to Fmt 010, Type 01010 (Completion with Data), Length 0x040 = 64 DW = 256 bytes. The SSD's MPS was 128 bytes after resume, so a 256-byte completion arriving at the SSD is a Malformed TLP (payload larger than the receiver's MPS). Any write makes the SSD read host memory; the root port returns completions of up to 256 bytes (its own MPS), so even a 512-byte write triggers it. Reads work because the SSD sends data in its own TLPs (now ≤128 bytes) and receives only small completions for SQE fetches.

Model report highlights. Title: "After s2idle resume on platform FW 1.12, LS-2 Device Control MPS is 128 B while root port MPS is 256 B; root port completions trigger Malformed TLP (fatal) at the SSD and a reset loop." First abnormal event: the MPS value of 128 at the SSD after resume (configuration state), observed before any I/O; the first error event is the Malformed TLP with header log CplD 256 B. Root cause: configuration restore after resume leaves MPS inconsistent along the path; which agent writes 128 is not yet known (medium confidence that platform firmware 1.12 is involved, given 1.07 passes). Next evidence: a configuration-write trace across resume to see who writes Device Control. Workaround: documented as an expert-only diagnostic (the setpci write), not a user workaround. Owner: platform firmware team first, with the OS team copied. Regression: 500 suspend/resume loops with a diff of every function's Device Control and Link Control before and after each resume, and a large-write probe after each resume.

Challenge: intermittency suggests a race between the OS restoring configuration and another agent writing it (for example platform firmware on a resume path that sometimes runs later). Ask for timestamps of configuration writes across several resumes, passing and failing.

What a senior engineer notices

The notes contain a version comparison (platform firmware 1.07 passes): the strongest single piece of evidence, buried at the bottom. They also notice the setpci write: it is evidence, but it changes the system and must be labelled as an expert diagnostic, not a recommendation.

Failure variants

  • MPS mismatch in the other direction (SSD 256, root port 128): the root port flags the SSD's 256-byte data writes for Reads as malformed; now reads fail.
  • Max Read Request Size reset after resume: no error, but different performance; a report must not call it a failure.

Extension

Write the regression test as a script outline that diffs configuration space before and after each resume and flags any change in Device Control, Link Control, L1 PM Substates control and LTR fields.

Reviewer's checklist

Before sending a report, or when reviewing someone else's, check every line.

  • The title names component and version, condition and effect.
  • Every firmware, kernel and tool version is exact.
  • Link generation and width are the negotiated values, on both ends.
  • Reproduction steps are minimal and runnable by someone else, with a rate.
  • Expected result cites the specification or design by name.
  • Actual result is observable, with no interpretation.
  • Trace evidence points to exact rows or packets, with provenance.
  • The first abnormal event is one event, with earlier anomalies explicitly excluded.
  • The root cause has a confidence level and the evidence for it.
  • The workaround states its cost.
  • The regression test targets the mechanism and has a pass criterion.
  • No blame words; no invented specification details.
  • Attachments are labelled, timestamps intact, private data removed.
