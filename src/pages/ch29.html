Every NVMe command, from a 4 KiB read to a firmware activation, is a 64-byte record the host writes into memory, and every answer is a 16-byte record the controller writes back. This chapter teaches you to read both records byte by byte, so that a hex dump of a Submission Queue Entry or a Completion Queue Entry stops being noise and becomes a sentence you can say out loud.

Why this chapter exists

In Queue Architecture you learned that the host and the controller talk through rings in host memory. In Doorbells you learned how the host announces new work. What you have not yet studied closely is the thing that sits in each slot of those rings. That thing is the command, and its reply is the completion.

The fixed layout of these two records is the most stable contract in NVMe. Opcodes are added, command sets come and go, transports change from PCI Express (PCIe) to TCP, but the 64-byte Submission Queue Entry (SQE) and the 16-byte Completion Queue Entry (CQE) have kept the same skeleton since NVMe 1.0. If you know the skeleton, you can decode commands you have never seen before, because you know where the opcode, the identifier, the namespace and the data pointers live even before you know what the command does.

For trace analysis this is the bridge between two worlds. A protocol analyzer shows you a PCIe Memory Read completion carrying 64 bytes. Only when you can split those 64 bytes into Command Dwords do you know that the controller just fetched a READ of eight blocks for namespace 1 with Command Identifier 7. Every later chapter on commands, PRP/SGL, errors and end-to-end correlation stands on this one.

Learning objectives

  • Draw the 64-byte SQE as sixteen Command Dwords (CDW0–CDW15) and name every field of the common command format.
  • Decode CDW0 into opcode, fused operation, PRP-or-SGL selector and Command Identifier, and explain who chooses each value.
  • Explain the role of the Namespace Identifier, the Metadata Pointer and the Data Pointer, and when each is ignored.
  • Draw the 16-byte CQE and decode SQ Head Pointer, SQ Identifier, Command Identifier, Phase Tag and the Status Field (Status Code, Status Code Type, Command Retry Delay, More, Do Not Retry).
  • Decode a complete synthetic READ SQE and its CQE from raw little-endian hex, by hand and with a script.
  • Recognise the common command formats (admin with no data, admin with data, NVM I/O with LBA range) and where their command-specific fields sit.
  • Identify in a PCIe trace the TLPs that carry an SQE and a CQE, and correlate them using SQID and CID.
  • List what goes wrong when each field is wrong, and how each failure shows up in a trace and in Linux.

The story

Imagine the school library has a box of request slips. Every slip is printed on exactly the same size of card, with boxes in exactly the same places. The top-left box says what kind of job it is ("bring me books", "put these books away", "tell me about yourself"). Next to it is a ticket number you write yourself, so you can recognise the answer later. Another box says which shelf section the job is about. Two boxes say which table in the classroom the books should go to or come from. And at the bottom there is a big space whose meaning depends on the kind of job: for "bring me books" it says which books and how many.

When the librarian finishes, she does not write a whole letter back. She drops a tiny answer card into the answer box. The card has your ticket number, a word that means "done" or "problem", a note saying "I have read slips up to number 6", and a little coloured dot that flips colour every time she goes round the box, so you can tell new cards from old ones.

An adult version: a standardised shipping manifest at a container port. Every manifest is the same size and has the same header boxes — a form code that says what kind of shipment it is, a reference number chosen by the shipper, a destination warehouse code, and two address fields for where the goods physically are. Below the header is a free-form "commodity details" area whose layout is defined by the form code. The port's answer is a short receipt stamped with the shipper's reference number, the number of the last manifest the port has processed, an outcome code from a published list, and a "do not resubmit" box.

What the analogy hides. The slip is not handed over; it sits in host memory and the controller fetches it with a PCIe Memory Read when it chooses. Nothing physically moves until the doorbell rings, and the slip can be fetched long after it was written. The "table addresses" are not single locations but pointers that may describe a list of scattered memory pages (PRP) or a linked list of descriptors (SGL).

Where it misleads. The ticket number (Command Identifier) is only unique among commands outstanding on the same Submission Queue; two queues can use the same number at the same time. The colour dot (Phase Tag) is not a status; it says "this card is new", not "this card is good". And the receipt's "slips read up to number 6" (SQ Head Pointer) tells the host which slots it may reuse — it does not mean commands 0–5 have completed; completions may arrive in any order.

Beginner explanation

A computer that wants an NVMe SSD to do something writes a small, fixed-size record into a ring of memory called a Submission Queue (SQ). That record is the command. It is always 64 bytes. The SSD's controller later reads the record, does the work, and writes a 16-byte reply into a different ring called a Completion Queue (CQ).

The 64 bytes are grouped into sixteen 32-bit words. NVMe calls each 32-bit word a Dword (double word), and the words of a command are called Command Dwords, numbered CDW0 to CDW15. Some words have the same meaning in every command: which operation, which ticket number, which namespace, where the data is in memory. The last six words (CDW10–CDW15) change meaning depending on the operation.

The reply has four Dwords. The first is a small result value whose meaning depends on the command (for example, how many queues the controller granted). The third says which queue the command came from and how far the controller has read in that queue. The fourth carries the ticket number, a flip-flopping "new entry" bit, and the status: success, or a coded reason for failure.

Engineering explanation

The NVM Express Base Specification defines a common command format that every admin and I/O command uses. Individual command definitions then say how they use the command-specific Dwords and whether they use the namespace or data pointer fields at all. The Base Specification also defines the completion queue entry layout and the status field encoding that every command returns.

CDW1 — Namespace Identifier (NSID)

The Namespace Identifier (NSID) names the namespace the command acts on. Valid active NSIDs start at 1; NSID 0 is not a valid namespace; FFFFFFFFh is the broadcast value meaning "all namespaces" where a command allows it (for example some Get Log Page, Format NVM or Set Features uses). Admin commands that do not concern a namespace — Create I/O SQ, Abort, Keep Alive — define NSID as reserved or unused and expect zero.

NSID is checked by the controller before it touches media. An I/O command with an inactive or invalid NSID completes with Invalid Namespace or Format (generic status 0Bh). That status appears before any data transfer, so in a trace you see the SQE fetch followed directly by a CQE write, with no data TLPs in between.

CDW2 and CDW3

In early revisions these Dwords were reserved. Later revisions allow commands to use them for command-specific purposes (for example, some command sets place extended fields here). Treat them as "zero unless the command definition you are reading says otherwise" and check the definition for the revision you target. Version-dependent

CDW4–5 — Metadata Pointer (MPTR)

Metadata is extra per-block information (for example end-to-end protection information) that can travel either interleaved with the data ("extended LBA") or in a separate buffer. MPTR is used only when the namespace is formatted with metadata in a separate buffer and the command transfers data. With PSDT = 00b or 01b it is the address of one contiguous metadata buffer; with PSDT = 10b it points to an SGL segment that describes the metadata buffer. For namespaces without separate metadata, MPTR is ignored and should be zero.

CDW6–9 — Data Pointer (DPTR)

The 16-byte Data Pointer (DPTR) tells the controller where the data buffer is in host memory. It has two interpretations selected by PSDT:

  • PRP mode (PSDT = 00b). PRP Entry 1 (PRP1) is the address of the first memory page of the buffer; it may carry an offset within that page. PRP Entry 2 (PRP2) is either the address of the second page (if the transfer spans exactly two pages) or the address of a PRP List (if it spans more), or unused if the transfer fits in the first page. Physical Region Pages are taught fully in Physical Region Pages.
  • SGL mode (PSDT = 01b or 10b). The 16 bytes are one SGL descriptor, SGL Entry 1: an 8-byte address, a 4-byte length and a descriptor type byte. It may describe the data directly or point to a segment of further descriptors. Scatter Gather Lists are taught in Scatter Gather Lists.

Admin commands sent over the PCIe transport must use PRPs; SGLs are an I/O-command option that the controller advertises in the Identify Controller SGL Support field. Verified (NVMe over PCIe: admin commands use PRP). Commands that transfer no data ignore DPTR.

CDW10–15 — command-specific Dwords

The final 24 bytes belong to the command. A READ places its starting LBA in CDW10–11 and its block count in CDW12; Identify places its Controller or Namespace Structure (CNS) value in CDW10; Create I/O CQ places the queue identifier and size in CDW10 and its interrupt settings in CDW11. When you decode an unfamiliar command, you know CDW0–9 already; you only need the command's own table for CDW10–15.

How SQID and CID make a command unique

The CID is chosen by the host and only needs to be unique among commands outstanding on one SQ. A CQ may serve several SQs, so the controller reports SQID with every completion. The pair (SQID, CID) is therefore the command's unique key at any instant. Once a completion is consumed, the CID may be reused immediately.

Linux, for example, derives the CID from the block-layer request tag, and recent kernels add a small generation counter in the upper bits so that a stale or duplicated completion for a re-used tag can be detected. Implementation-dependent — another host may allocate CIDs sequentially, randomly, or by slot index. Never assume a CID pattern from one host applies to another.

The ladder for the central concept: the command record

A request slip of a fixed size with boxes in fixed places, dropped in a request box; a tiny answer card comes back with your ticket number on it.

A 64-byte SQE in a Submission Queue; a 16-byte CQE in a Completion Queue; the CID ties them together; the Status Field says what happened.

The CPU stores 64 bytes into a cache-coherent DRAM ring; the controller's DMA engine fetches them over the PCIe link into its internal command buffer, parses CDW0 in hardware or firmware, and later DMA-writes 16 bytes into the CQ ring.

The NVM Express Base Specification defines the common command format, the completion queue entry, the Status Field and its tables; each command's definition (in the Base or an I/O command set specification) assigns CDW10–15 and the CQE DW0 meaning.

Over PCIe: the doorbell is a posted Memory Write (MWr) from the root complex; the SQE travels as the data of a Completion with Data (CplD) answering the controller's Memory Read (MRd); the CQE travels as a posted MWr from the controller to the CQ address.

In an analyzer: an MRd of 16 Dwords to SQ base + slot × 64, a CplD with 64 bytes whose first byte is the opcode, then later an MWr of 4 Dwords to CQ base + slot × 16 whose last Dword contains the CID and phase.

When a command "never completes", first find its SQE fetch (was it fetched at all?), then the CQE write for that SQID/CID (was it written, with which phase?), then the interrupt. The first missing or malformed record localises the fault to host, link or controller.

The sixteen questions, answered for the SQE/CQE pair

1. What is it?
A fixed 64-byte command record and a fixed 16-byte completion record exchanged through memory-resident queues.
2. Why was it created?
To give a high-performance, low-overhead, lock-friendly command interface between host software and a non-volatile memory controller.
3. What problem does it solve?
Fixed-size, cache-line-friendly entries allow the host to build a command with a few stores and the controller to fetch it with one read, with no register-by-register handshake; many commands may be in flight across many queues.
4. What existed before it?
AHCI command tables and FIS structures (SATA), SCSI Command Descriptor Blocks carried by SAS HBAs: variable formats, a single command queue of limited depth (32 for AHCI), and more register traffic. See From SATA/SAS to NVMe.
5. Why is the current design better?
Every field sits at a known offset, the opcode alone defines the meaning of the rest, a single 64-byte fetch carries everything the controller needs for most commands, and the 16-byte completion is small enough to write atomically and cheaply.
6. Who creates it?
The SQE: the host driver. The CQE: the controller.
7. Who consumes it?
The SQE: the controller's command fetch and parse logic. The CQE: the host driver's completion handler.
8. Where does it live?
In host memory in the SQ and CQ rings (an SQ may also live in a Controller Memory Buffer when supported).
9. What memory/registers are involved?
SQ/CQ base addresses (ASQ/ACQ registers for admin; Create I/O SQ/CQ PRP1 for I/O), CC.IOSQES/IOCQES entry sizes (26 = 64 and 24 = 16), SQ tail and CQ head doorbells.
10. What happens before it?
The driver allocates a CID, maps the data buffer (PRP/SGL), fills the 64 bytes, then writes the SQ tail doorbell.
11. What happens after it?
The controller executes, transfers data, writes the CQE, optionally signals an interrupt; the host consumes the CQE and writes the CQ head doorbell.
12. What happens if it is wrong?
Invalid opcode/field statuses, DMA to wrong addresses, completion of the wrong request, lost or duplicated completions, hangs.
13. What does the protocol analyzer show?
The SQE in a CplD payload, the CQE in an MWr payload; good analyzers decode both into fields.
14. What does Linux show?
The nvme tracepoints (nvme_setup_cmd, nvme_complete_rq) print opcode, CID, NSID, CDW10–15 and status; error messages print the status in SCT<<8|SC form.
15. What would a validation engineer test?
Reserved-bit handling, every opcode on the wrong queue type, CID reuse and duplicates, PSDT values, NSID 0 / inactive / broadcast, phase-tag wrap, SQHD correctness under reordering, every status path.
16. What would a senior engineer suspect when it fails?
A host-side ring or CID bookkeeping bug before a controller bug; then IOMMU mapping of the SQ/CQ; then entry-size configuration (IOSQES/IOCQES); then controller firmware.

Hardware view

On the host side, building an SQE is nothing more than 64 bytes of CPU stores into ordinary write-back DRAM. On x86 that is one cache line. Because the line is cache-coherent and the controller's later read is snooped, the driver does not need to flush caches; it does need a memory barrier so that the SQE stores are globally visible before the doorbell store (an uncached MMIO write) leaves the CPU. On architectures with weaker ordering, the barrier is explicit in the driver's code path. Implementation-dependent (barrier instruction differs by CPU architecture).

On the controller side, a typical design has:

  • A doorbell register file in BAR0 space (from offset 1000h) that latches the new tail for each SQ and raises an internal "work available" event.
  • A command fetch engine that computes SQ base + head × 64, issues PCIe Memory Read requests (one per entry, or one larger read covering several consecutive entries — an implementation choice), and places the returned bytes in an on-chip command buffer.
  • A parser / dispatcher — hardware for the hot path (Read/Write), firmware for the rest — that checks the opcode against the queue type, validates NSID, reserved bits and PSDT, and dispatches the command.
  • A DMA engine that walks PRP or SGL structures and moves data.
  • A completion engine that builds the 16-byte CQE, sets the phase tag for the current pass of the CQ, writes it with a PCIe Memory Write, and then decides whether to send an interrupt (MSI-X Memory Write), subject to interrupt coalescing.

Entry sizes are not hard-coded on the controller side: the host programs CC.IOSQES and CC.IOCQES (as powers of two) before enabling the controller, and the controller reports the required and maximum entry sizes in Identify Controller (SQES and CQES bytes). For the NVM Command Set over PCIe these are 64 and 16 bytes. The admin queue entries are always 64 and 16 bytes. If a driver programs a different I/O size than the controller expects, every I/O queue creation fails — a classic bring-up bug.

Specification view

The common command format, the completion queue entry and the status field are defined in the NVM Express Base Specification, Revision 2.4 — Submission Queue Entry; Completion Queue Entry; Status Field Definition. Command-specific Dwords for I/O commands of the NVM Command Set (Read, Write, Compare, …) are defined in the NVM Express NVM Command Set Specification, Revision 1.3 — I/O Commands for the NVM Command Set. How SQEs and CQEs are carried by PCIe memory transactions, doorbells and PRP rules for admin commands are in the NVM Express NVMe over PCIe Transport Specification, Revision 1.4. These three documents are separate on purpose: NVMe defines the record, the transport defines how it moves, and PCIe itself (the PCI Express Base Specification, Revision 6.x/7.0) defines the Memory Read/Write and Completion packets that do the moving.

The normative text is in the field tables and "shall" statements of those sections. Figures showing example commands, and informative notes, are explanatory only.

The SQE is 64 bytes and the CQE is 16 bytes for NVMe over PCIe. CDW0 holds the opcode (bits 7:0), FUSE (9:8), PSDT (15:14) and CID (31:16). NSID is in bytes 4–7, MPTR in bytes 16–23, DPTR in bytes 24–39, CDW10–15 in bytes 40–63. In the CQE, DW2 holds SQHD (15:0) and SQID (31:16); DW3 holds CID (15:0), the Phase Tag (16) and the Status Field (31:17) with SC, SCT, CRD, M and DNR as tabulated above. Status Code Type values 0h, 1h, 2h, 3h and 7h are as listed.

That the (SQID, CID) pair is the unique key of an outstanding command follows from two normative facts: CID must be unique among outstanding commands on its SQ, and every CQE reports SQID. That the opcode's low two bits predict data direction is a property of how the opcode tables were assigned, and is reasoned from them rather than quoted as a rule for every future command.

How the controller fetches SQEs (one 64-byte read per entry, or a burst covering several entries), the order in which it executes and completes commands, the CQE write coalescing, how a host assigns CIDs, and whether non-zero reserved bits are rejected or ignored are implementation choices.

The use of CDW2–3 and of CQE DW1 by specific commands, the list of status codes, the set of opcodes and the existence of Command Retry Delay (added in the 1.4 era) vary with revision. In the 2.x family, command definitions were split between the Base Specification and the I/O command set specifications; older 1.x documents put everything in one book. When you read an older datasheet or driver, check which revision it was written against.

What must be checked in the specification for any command you decode:

  • Which command-specific Dwords it uses, and their bit fields.
  • Whether NSID is used, required to be zero, or may be the broadcast value.
  • Whether it transfers data, in which direction, and whether SGLs are allowed.
  • What CQE DW0 (and DW1, if any) returns.
  • Which command-specific status values it may return.

The specification does not say how fast a command must complete, in what order commands from one SQ are executed, or that completions appear in submission order. It does not define how a host allocates CIDs.

Never assume completions arrive in submission order. Never assume a CID is unique across queues. Never assume a reserved field is ignored. Never assume a non-zero PRP1 means data will move. Never assume the Phase Tag starts at 0 — it starts at 1 for the first pass, because the host zeroes the CQ memory and looks for P = 1.

Code / pseudocode

The script below decodes an SQE and a CQE from raw bytes using only the Python standard library. It encodes exactly the field positions taught in this chapter, and the Read/Write command-specific fields from READ. Run it as is; then paste your own captured payloads in place of the examples.

#!/usr/bin/env python3
"""Decode a 64-byte NVMe Submission Queue Entry and a 16-byte Completion Queue Entry.
Standard library only. Teaching tool: field positions follow the NVMe Base
Specification common command format; command-specific fields are decoded
only for the NVM Command Set Read/Write layout."""
import struct

ADMIN = {0x00: "Delete I/O SQ", 0x01: "Create I/O SQ", 0x02: "Get Log Page",
         0x04: "Delete I/O CQ", 0x05: "Create I/O CQ", 0x06: "Identify",
         0x08: "Abort", 0x09: "Set Features", 0x0A: "Get Features",
         0x0C: "Asynchronous Event Request"}
NVM = {0x00: "Flush", 0x01: "Write", 0x02: "Read", 0x08: "Write Zeroes",
       0x09: "Dataset Management"}
SCT = {0: "Generic Command Status", 1: "Command Specific Status",
       2: "Media and Data Integrity Errors", 3: "Path Related Status",
       7: "Vendor Specific"}
GENERIC = {0x00: "Successful Completion", 0x01: "Invalid Command Opcode",
           0x02: "Invalid Field in Command", 0x04: "Data Transfer Error",
           0x0B: "Invalid Namespace or Format", 0x80: "LBA Out of Range"}
MEDIA = {0x81: "Unrecovered Read Error"}

def decode_sqe(raw, admin=False):
    assert len(raw) == 64, "an SQE is exactly 64 bytes"
    dw = struct.unpack("<16I", raw)          # 16 little-endian dwords
    opc = dw[0] & 0xFF
    fuse = (dw[0] >> 8) & 0x3
    psdt = (dw[0] >> 14) & 0x3
    cid = dw[0] >> 16
    table = ADMIN if admin else NVM
    print(f"CDW0  0x{dw[0]:08X}  OPC=0x{opc:02X} ({table.get(opc, 'not in this table')})"
          f"  FUSE={fuse:02b}  PSDT={psdt:02b}  CID=0x{cid:04X}")
    print(f"      data direction bits[1:0] = {opc & 3:02b}"
          " (00 none, 01 host->ctrl, 10 ctrl->host, 11 bidirectional)")
    print(f"NSID  0x{dw[1]:08X}")
    print(f"CDW2  0x{dw[2]:08X}  CDW3 0x{dw[3]:08X}")
    mptr = dw[4] | dw[5] << 32
    prp1 = dw[6] | dw[7] << 32
    prp2 = dw[8] | dw[9] << 32
    print(f"MPTR  0x{mptr:016X}")
    if psdt == 0:
        print(f"PRP1  0x{prp1:016X}  (offset in 4 KiB page = 0x{prp1 & 0xFFF:03X})")
        print(f"PRP2  0x{prp2:016X}")
    else:
        print(f"SGL1  {raw[24:40].hex(' ')}")
    for i in range(10, 16):
        print(f"CDW{i:<2d} 0x{dw[i]:08X}")
    if not admin and opc in (0x01, 0x02):
        slba = dw[10] | dw[11] << 32
        nlb = (dw[12] & 0xFFFF) + 1          # 0's based on the wire
        print(f"  SLBA={slba}  NLB(field)={nlb - 1} -> {nlb} blocks"
              f"  PRINFO=0x{(dw[12] >> 26) & 0xF:X}"
              f"  FUA={(dw[12] >> 30) & 1}  LR={(dw[12] >> 31) & 1}")
    return cid

def decode_cqe(raw):
    assert len(raw) == 16, "a CQE is exactly 16 bytes"
    dw0, dw1, dw2, dw3 = struct.unpack("<4I", raw)
    sqhd, sqid = dw2 & 0xFFFF, dw2 >> 16
    cid, p = dw3 & 0xFFFF, (dw3 >> 16) & 1
    sc, sct = (dw3 >> 17) & 0xFF, (dw3 >> 25) & 0x7
    crd, m, dnr = (dw3 >> 28) & 0x3, (dw3 >> 30) & 1, dw3 >> 31
    name = (GENERIC if sct == 0 else MEDIA if sct == 2 else {}).get(sc, "see spec")
    print(f"DW0 0x{dw0:08X}  DW1 0x{dw1:08X}")
    print(f"DW2 0x{dw2:08X}  SQHD={sqhd}  SQID={sqid}")
    print(f"DW3 0x{dw3:08X}  CID=0x{cid:04X}  P={p}")
    print(f"    SCT={sct} ({SCT.get(sct, 'reserved')})  SC=0x{sc:02X} ({name})"
          f"  CRD={crd}  M={m}  DNR={dnr}")
    return cid

        "00000000" "00000000"                         # MPTR
        "00000000" "02000000"                         # PRP1 = 0x2_0000_0000
        "00000000" "00000000"                         # PRP2

Step 3 — decode the CQE

The controller later writes these 16 bytes into CQ1 slot 3: 00 00 00 00 00 00 00 00 06 00 01 00 07 00 01 00.

  • DW0 = 0, DW1 = 0: Read returns no result value.
  • DW2 = 0x0001_0006: SQID = 1, SQHD = 6.
  • DW3 = 0x0001_0007: CID = 0x0007; bit 16 = 1 → P = 1; bits 31:17 = 0 → success.

The host's current CQ phase for this pass is 1 (first pass), so the entry is new. CID 7 on SQ1 is outstanding, so it is the READ we sent. Status 0 means the 4 KiB at 0x2_0000_0000 is valid.

Step 4 — the same CQE, but failed

If instead DW3 were 0x8503_0007: CID 0x0007, P = 1, status word 0x8503. SC = (0x8503 >> 1) & 0xFF = 0x81; SCT = (0x8503 >> 9) & 0x7 = 2; CRD = 0; M = 0; DNR = 1. That is Media and Data Integrity Errors / Unrecovered Read Error, do not retry. Linux would print it as status 0x281. The buffer contents must not be used.

Common mistakes

  • Reading the SQE big-endian. The opcode is the first byte in memory, not the fourth. Analyzer "Dword" views and memory "byte" views look different; always know which one you are reading.
  • Forgetting that NLB is 0's based. NLB = 0 means one block. A driver that writes the count instead of count − 1 reads one block too many — often into the next buffer.
  • Assuming CID is globally unique. It is unique per SQ. Correlating by CID alone across a multi-queue trace pairs the wrong commands.
  • Treating SQHD as "commands done". SQHD says what was fetched, not what completed.
  • Misplacing the phase bit. P is bit 16 of DW3, bit 0 of the status word. Shifting the status word by 1 before extracting SC is required; forgetting it doubles every status code you print (02h becomes 04h — which happens to be a real, different status: Data Transfer Error).
  • Leaving stale bytes in a reused slot. If the driver does not zero the entry, CDW13–15 from the previous command can carry hints or protection settings into the new one.
  • Expecting data TLPs for every non-zero PRP1. Create I/O SQ/CQ use PRP1 for queue memory.
  • Interpreting an admin opcode as an I/O opcode. 01h on the admin queue is Create I/O SQ; on an I/O queue it is Write.

Debugging connection

The SQE and CQE are the first place to look whenever a command misbehaves, because they are the only two records that both sides agree on. A debugging pass looks like this:

  1. Find the command. In the trace, locate the CplD carrying the SQE (match SQ base + slot × 64). If there is none, the controller never fetched it: look at the doorbell (Doorbells).
  2. Decode every field. Opcode valid for this queue type? NSID active? PSDT supported? Reserved bits zero? PRP alignment correct? CDW10–15 sensible for this opcode?
  3. Find the completion. MWr to CQ base + slot × 16 with the same SQID and CID. If there is none: controller hang, or the host is looking at the wrong CQ.
  4. Decode the status. SCT tells you which family; SC tells you the specific condition; DNR tells you whether retrying is pointless; M tells you to read the Error Information log.
  5. Check the phase. A CQE written with the wrong phase is invisible to the host and looks like a timeout.
  6. Correlate with time. Microseconds between SQE fetch and CQE suggests rejection in parsing; tens of microseconds suggests media access; seconds suggests error recovery or a stuck controller.

Senior engineer insight

Experienced engineers treat the SQE and the CQE as contracts with witnesses. The trace is the witness. When software and firmware teams argue about who broke a command, the bytes of the SQE as fetched (not as the driver thinks it wrote them) settle the question. That is why a senior engineer always asks for the payload of the CplD, not the driver's log of what it built: an IOMMU mapping error, a cache-coherency problem on a non-coherent platform, or a missing barrier can make the two differ.

Second insight: the status code describes the controller's view, not the root cause. "Data Transfer Error" may mean a PCIe Unsupported Request on a PRP fetch caused by a stale IOMMU entry — a host bug. "Invalid Field" may hide a host using a feature the controller does not advertise. Use the status as a pointer to which field and which phase of execution to examine, then go to the evidence one layer down.

Third: the CQE is the commit point. Because of PCIe posted-write ordering, everything the controller DMA-wrote for a command is in memory before the CQE that the controller sends after it. Designs that break this (for example, careless use of relaxed ordering on data writes, or a host bridge that reorders) produce the rarest and nastiest bugs: a successful completion with stale data. If you ever see "status 0 but data wrong", look at ordering attributes in the trace before anything else.

Solution

Solution

SQE-A: CDW0 = 0x002A0002 → Read (02h, on an I/O queue), CID 0x002A, FUSE 0, PSDT 0. NSID = 1. PRP1 = 0x0000_0002_0000_3000. Bytes 32–39 are all zero, so PRP2 = 0 (do not confuse it with the next four bytes); bytes 40–43 00 20 00 00 are CDW10 = 0x00002000 → SLBA = 0x2000 = 8192. CDW12 = 0x4000000F → NLB field 15 → 16 blocks (8 KiB with 512-byte LBAs), FUA = 1 (bit 30). Note: an 8 KiB transfer starting at a page-aligned PRP1 spans two pages, so PRP2 should hold the second page address. With PRP2 = 0 this command is malformed — a deliberate defect. A controller would typically fail it (often Invalid Field or a data transfer error, depending on implementation), or worse, DMA to address 0.

SQE-B: CDW0 = 0x002A0001 → Write (01h), CID 0x002A on SQ2. NSID 1. PRP1 = 0x2_0000_5000, PRP2 = 0; CDW10 = 0x00000080 → SLBA 128; CDW12 = 0 → 1 block (512 bytes), fits in one page, so PRP2 = 0 is correct.

SQE-C: CDW0 = 0x00030006 on the admin queue → Identify, CID 0x0003. NSID 0. PRP1 = 0x0000_0001_0001_0000 (bytes 24–31: 00 00 01 00 01 00 00 00). CDW10 = 1 → CNS 01h, Identify Controller (4096-byte data structure; NSID not used).

CQE-1: DW2 = 0x00020001 → SQID 2, SQHD 1; DW3 = 0x0001002A → CID 0x002A, P 1, success. Pairs with SQE-B (SQ2, CID 0x2A). SQHD 1 matches: slot 0 consumed.

CQE-2: DW2 = 0x0001000A → SQID 1, SQHD 10; DW3 = 0x0101002A → CID 0x002A, P 1, status word 0x0101 → SC = (0x0101 >> 1) & 0xFF = 0x80, SCT = 0h, DNR 0: LBA Out of Range. Pairs with SQE-A (SQ1, CID 0x2A). On the reference namespace LBA 8192 is in range, so a real controller would not return this for SQE-A — but a controller that read PRP2 = 0 might fail differently. The lesson is pairing, not plausibility; in a real investigation this mismatch between status and command would itself be a finding.

CQE-3: same SQID/CID as CQE-2 but P = 0. On the first pass of CQ1 the host expects P = 1, so CQE-3 is a stale (or not-yet-written) entry and must be ignored.

CQE-4: DW2 = 0x00000005 → SQID 0 (admin), SQHD 5; DW3 = 0x00010003 → CID 3, P 1, success. Pairs with SQE-C. Admin SQ head is now 5, so slot 4 is free.

Answers: (1) Yes — CIDs need only be unique per SQ. (2) By the phase tag relative to the host's expected phase for that pass. (3) The controller has consumed admin SQ entries up to slot 4. (4) None correctly: SQE-A needed PRP2 and omitted it.

What a senior engineer notices

The duplicate CID across SQ1 and SQ2 is a deliberate trap — legal but dangerous for any tool or person correlating by CID alone. The missing PRP2 in SQE-A is the real defect, and it would not be visible in a driver log that prints only opcode, LBA and length. The status in CQE-2 does not match the defect, which is a reminder that a status is the controller's interpretation, not a diagnosis.

Failure variants

  • Change SQE-C's CNS to 02h: the data becomes the Active Namespace ID list.
  • Set FUSE = 01b on SQE-B with no following fused command: expect an aborted-missing-fused status.
  • Make CQE-1's SQID 1 instead of 2: the host completes SQE-A's request with SQE-B's result.

Exercises

  2. A CQE's DW3 is 0xC0050011. Decode every sub-field.
  3. A trace shows MRd to 0x1_2340_FFC0 with Length 16. Given SQ1 is 1024 entries at 0x1_2340_0000, which slot is it, and what slot comes next?
  4. Explain in three sentences why Create I/O CQ uses PRP1 and yet no data moves.
  5. For a 12 KiB read into a buffer starting at offset 0x200 in a page, how many pages does the buffer touch, and is PRP2 a page address or a PRP List pointer?
  6. List every SQE field that a controller must check before it starts any DMA.
Answers

1: Identify = 0x0100_0006; Write with SGL = 0xFFFE_4001; Flush = 0x0000_0000.

2: CID 0x0011; P = 1 (bit 16); status word = 0xC005 → SC = (0xC005 >> 1) & 0xFF = 0x02, SCT = 0, CRD = 0, M = 1 (bit 14 of word = bit 30), DNR = 1. Invalid Field in Command, more information in the Error Information log, do not retry.

3: (0xFFC0) / 64 = 1023, the last slot. The next fetch wraps to slot 0 at 0x1_2340_0000.

4: The PRP1 of Create I/O CQ holds the base of the queue's memory, which the controller records. Data is not transferred by the command itself. The CQ memory is only written later, one CQE at a time, as commands complete.

5: 0x200 + 12288 = 0x3200 bytes from the page start → spans 4 pages (0x0000–0x0FFF, 0x1000–0x1FFF, 0x2000–0x2FFF, 0x3000–0x31FF). More than two pages, so PRP2 points to a PRP List (see Physical Region Pages).

6: Opcode validity for the queue type; FUSE; PSDT and SGL support; reserved bits (if it checks them); NSID validity; command-specific range checks (SLBA + NLB within namespace, NLB within MDTS); data pointer offset and alignment rules.

Quiz

  1. How large is an NVMe over PCIe Submission Queue Entry?

    • 16 bytes
    • 32 bytes
    • 64 bytes
    • 128 bytes
    Answer and reasoning

    64 bytes: sixteen Command Dwords, CDW0–CDW15. 16 bytes is the CQE.

  2. Where is the Command Identifier in an SQE?

    • CDW0 bits 15:0
    • CDW0 bits 31:16
    • CDW1
    • CDW10 bits 15:0
    Answer and reasoning

    CDW0 bits 31:16. Bits 7:0 are the opcode; CDW1 is the NSID.

  3. Which pair uniquely identifies an outstanding command?

    • CID alone
    • CID and NSID
    • CQID and CID
    • SQID and CID
    Answer and reasoning

    The CID is unique only per SQ; several SQs may share a CQ, so the CQE reports SQID. NSID is irrelevant to identity.

  4. A CQE has DW3 = 0x0001_0000. What does it mean?

    • CID 0, phase 1, success
    • CID 1, phase 0, success
    • CID 0, Invalid Command Opcode
    • CID 0, phase 1, DNR set
    Answer and reasoning

    Bit 16 is the phase tag; bits 15:0 (CID) are 0; bits 31:17 (status) are 0.

  5. PSDT = 00b means:

    • No data transfer
    • The Data Pointer contains PRP entries
    • The Data Pointer contains one SGL descriptor
    • Metadata is interleaved
    Answer and reasoning

    00b selects PRPs. 01b and 10b select SGLs (with two different MPTR interpretations). Whether data moves at all depends on the opcode.

  6. What does the SQ Head Pointer in a CQE tell the host?

    • Which commands have completed
    • Where the next CQE will be written
    • Which SQ slots the controller has consumed and may be reused
    • The doorbell value the host must write
    Answer and reasoning

    SQHD reports consumption (fetch) of SQ entries, letting the host free slots. Completion of a specific command is reported by its own CQE.

  7. Status word 0x0005 (as printed with P in bit 0) means:

    • SC 05h
    • SC 02h, P = 1
    • SC 0Ah
    • SCT 5
    Answer and reasoning

    Bit 0 is P = 1; (0x0005 >> 1) = 0x02 → SC 02h, Invalid Field in Command, SCT 0.

  8. Why can the host trust read data in its buffer as soon as it sees the CQE?

    Model answer

    Because the controller sends the data Memory Writes before the CQE Memory Write, and PCIe ordering rules do not let a later posted write pass an earlier posted write in the same direction (absent relaxed ordering). The data therefore reaches memory first. The host must still use a read barrier after seeing the phase bit before reading the rest of the CQE and the data.

  9. Name two commands that use PRP1 without transferring data.

    Model answer

    Create I/O Submission Queue and Create I/O Completion Queue: PRP1 is the base address of the queue (or of a PRP list describing a non-contiguous queue).

  10. What is the first thing you check if a trace shows a CQE written for a command but the host times out?

    Model answer

    The phase tag versus the host's expected phase, and that the CQE address is in the CQ the host is polling (correct CQ, correct slot). A wrong phase or wrong CQ makes a correctly written CQE invisible.

Interview questions

  1. Beginner. What are the sizes of an SQE and a CQE, and who writes each?

    Model answer

    64 and 16 bytes for NVMe over PCIe. The host writes SQEs into the submission queue; the controller writes CQEs into the completion queue. Each is read by the other side.

  2. Beginner. What is the Command Identifier for?

    Model answer

    It lets the host match a completion to the command that caused it. The host chooses it; the controller returns it unchanged in the CQE. It is unique per SQ while the command is outstanding.

  3. Intermediate. Walk me through the Status Field.

    Model answer

    Fifteen bits in DW3 above the phase tag: Status Code (8 bits) qualified by Status Code Type (3 bits: generic, command-specific, media/data integrity, path-related, vendor-specific), Command Retry Delay (2 bits) choosing a retry delay, More (1 bit) saying the Error Information log has details, Do Not Retry (1 bit). All zero is success.

  4. Intermediate. Why does a CQE carry SQID and SQHD?

    Model answer

    SQID because a CQ can be shared by multiple SQs, so the CID alone is ambiguous. SQHD because the host has no other way to learn how far the controller has consumed the SQ; it needs that to avoid overwriting unfetched entries and to know when the queue is full.

  5. Advanced. How would you prove whether a corrupted command came from the driver or from the path to the controller?

    Model answer

    Compare three things: the driver's view (tracepoint or a debug dump of the SQ slot after the doorbell), the bytes on the wire (CplD payload in a PCIe trace for the MRd of that slot) and the controller's view (its error log or debug interface, if any). If the driver view and wire bytes differ, look at memory ordering, cache coherency and IOMMU mapping; if wire and controller differ, look at the link (LCRC/replays) and controller internals; if all agree, the driver built it wrong.

  6. Advanced. A controller occasionally reports Command ID Conflict under heavy load. What do you suspect?

    Model answer

    The host reused a CID before consuming the previous command's completion — e.g. a timeout/abort path freed a tag while the command was still alive, or a race between completion and requeue. I would trace CID allocation and free events against CQE arrival and check the abort/timeout handling.

  7. Senior. Design a check in a protocol-analysis tool that catches host bugs in SQE construction.

    Model answer

    Decode every CplD that answers an SQ-region MRd into an SQE; validate opcode against queue type and the Commands Supported and Effects log; check reserved bits, PSDT against SGL support, FUSE pairing, NSID against the active list, SLBA + NLB against NSZE and NLB against MDTS, PRP alignment and PRP2 presence against transfer size; track (SQID, CID) for duplicates while outstanding; report the first violation with the SQE bytes. Keep rules versioned by the controller's VS register.

  8. Senior. When is "status 0 but wrong data" possible, and how do you investigate?

    Model answer

    Wrong PRPs (data landed elsewhere), CID mismatch (a different command's success), ordering violations (CQE observed before data), IOMMU mapping to the wrong page, or firmware mapping the wrong LBA. Investigate by correlating data MWr addresses with the PRPs in the fetched SQE, checking relaxed-ordering attributes and the order of data vs CQE TLPs, and verifying CID bookkeeping on the host.

Model explanation for the junior engineer

"CDW0 is four bytes: the low byte is the opcode, then two bits of fused-operation, four reserved bits, two bits saying PRP or SGL, and the top sixteen bits are the command ID. 0x00070002 is opcode 02h — Read on an I/O queue — no fuse, PRP mode, CID 7. On the completion side, DW3 is the CID in the low half, then the phase bit, then fifteen status bits. 0x85030007 is CID 7, phase 1, and the status word 0x8503 shifted right once gives SC 0x81 with SCT 2 — Unrecovered Read Error — and the top bit, DNR, is set, so don't retry."

Chapter summary

An NVMe command is a 64-byte SQE in sixteen Dwords. CDW0 carries the opcode, fused-operation bits, the PRP/SGL selector and the host-chosen Command Identifier. CDW1 is the namespace. CDW4–5 point to separate metadata, CDW6–9 to the data buffer as PRP1/PRP2 or one SGL descriptor, and CDW10–15 belong to the command. A completion is a 16-byte CQE: a command-specific result, the SQ head and SQ identifier, the CID, the phase tag and a Status Field made of SC, SCT, CRD, M and DNR. Over PCIe the SQE is fetched by a controller Memory Read and the CQE is posted with a controller Memory Write; ordering makes the CQE a commit point. Correlate with (SQID, CID), always decode the fetched bytes rather than the driver's intent, and treat the status as a pointer to evidence, not a diagnosis.
