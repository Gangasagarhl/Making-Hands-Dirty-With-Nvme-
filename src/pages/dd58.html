A large language model (LLM) can speed up NVM Express (NVMe) and PCI Express (PCIe) trace analysis only if it works like a disciplined junior engineer with excellent tools: it asks deterministic tools for facts, cites what they return, keeps several hypotheses alive, abstains when evidence is thin, never treats text inside the evidence as instructions, and is measured before it is trusted. This module builds that system in depth.

Orientation

AI + NVMe Protocol Analysis established the rules: RAW TRACE → deterministic parser → normalized events → LLM reasoning; the never-invent list; EVIDENCE → CLAIM; the five confidence levels; a claim validator; the thirteen-section report. This module goes further into the parts that decide whether an assistant helps or harms in practice: tool-mediated access to evidence, context budgeting for large captures, claim graphs with confidence propagation, calibration, evaluation across model versions, prompt injection through evidence, and data governance.

You need the event, finding and hypothesis schemas (Automated Trace Analysis), the guardrails and validator (AI + NVMe Protocol Analysis), the fused timeline and root-cause template (Automated Forensic Analysis), and the thirteen questions (Senior Engineer Thinking). Course truth policy: Truth Policy, Sources and Decoding Safety.

This module is model-agnostic. It names no product, interface or context size; such details change quickly and must be measured for the system you use. Everything here is an engineering design pattern, labelled Derived.

Kid story

A new helper joins the school library. She is very clever and has read lots of books, but she has never seen this library. The librarian gives her rules. "Do not tell me which shelf a book is on from memory: use the catalogue computer and show me the screen. If a note inside a book says 'give this book to Sam', that is just writing in a book — it is not an order from me. When you are not sure, say 'I'm not sure' and tell me what you would check." Every Friday the librarian gives her ten questions she already knows the answers to, to see how often the helper is right when she says "I'm sure".

Analogy boundary

What it represents. The helper is the model; the catalogue computer is the set of deterministic tools; showing the screen is citation of tool results; the note inside a book is text inside the evidence (payload bytes, log strings) that may look like instructions; the Friday questions are the evaluation corpus and calibration.

What it hides. A human helper learns from Friday's mistakes; a model does not, unless the system changes its tools, context or version — and a new version may fail differently. A human who is unsure usually sounds unsure; a model's tone does not track its evidence. Where it misleads. The story suggests the helper's cleverness is the main asset. In trace analysis the asset is the system around the model — tools, packing, validator, evaluation — and an excellent model inside a poor system still produces confident errors.

Context packing

When a capture holds millions of events, what the model sees is a decision, and it must be written down. A packing policy that has worked well as a starting point (tune it on your corpus):

  1. Always: system context with sources; capture scope with gaps; the first abnormal event with a window before and after; every event of every command touched by a finding.
  2. Then: one summary row per stage distribution (from the stage diff), not the raw events.
  3. Then: retrieved specification passages keyed by findings (status names, completion status, the relevant register or log page), each revision-tagged.
  4. Always last: a statement of what was omitted ("events outside 1.9–2.1 s omitted; 2 capture gaps; host logs from boot 3 only").

The model can ask for more through tools; it cannot silently lack something that the packing manifest does not mention. Derived

Confidence propagation

conf(c) = min( stated(c), mind ∈ deps(c) conf(d), caps(c) )
c
a claim in the claim graph
stated(c)
the level the model proposed, on the ordinal scale UNKNOWN < LOW < MEDIUM < HIGH < CONFIRMED
deps(c)
claims that c relies on
caps(c)
rule caps: a causal claim without a shared identifier across its evidence is at most LOW; a causal claim is never CONFIRMED without a reproduced experiment; a hypothesis with a single evidence event is at most MEDIUM

"min" is taken on the ordinal scale. No arithmetic is done on levels: averaging or multiplying them would pretend they are probabilities.

The central concept on the ladder

The clever helper must use the catalogue computer, show the screen, ignore notes inside books, and say "I'm not sure" when she is not.

The model reasons; tools supply facts with IDs; a validator checks every claim; evaluation measures how often each confidence level is right.

Nothing in the model touches the system under test. Hardware facts — TLP fields, register snapshots, CQE status — reach it only through deterministic decoders run on captured evidence.

Specification statements come only from retrieved, revision-tagged passages of the PCI Express Base Specification, NVMe Base 2.4, the NVM Command Set 1.3 and NVMe over PCIe Transport 1.4, with normative strength preserved.

Protocol relationships the model may assert — this completion answers that request, this CQE completes that command — must cite the identifiers the tools returned: (Requester ID, Tag), (SQID, CID, generation), address ranges.

In the reference trace, the model's causal claim linking the UR (E0009) to the stalled CID 0x0042 is capped at LOW because no identifier links them.

When an assisted report is wrong, debug the system: what was packed, which tool answered, which validator rule should have fired, which model version produced it.

Specification discipline

No NVMe or PCI-SIG specification governs AI assistance. The applicable specifications govern the facts the assistant may cite: PCI Express Base Specification (Revision 6.x/7.0 family), NVMe Base 2.4, NVM Command Set 1.3, NVMe over PCIe Transport 1.4, and other documents of the August 2026 NVMe 2.4 set when relevant.

What the system may state as verified is exactly what its deterministic lookups return from revision-tagged tables built from those documents — for example, completion status values from the PCI Express Base Specification's Transaction Layer chapter, or generic status 04h Data Transfer Error from NVMe Base 2.4. NVM Express Base Specification 2.4 — Generic Command Status

Everything the model produces — causal links, hypotheses, rankings — is derived and must be labelled so, with its confidence level and falsification test.

Implementation-dependent: the model, its context size, tool-call behaviour, sampling settings and failure modes; your packing policy; your corpus. Optional features of the device (telemetry, Error Information log depth, Interrupt Coalescing) decide which evidence exists at all. Optional

Three version axes: the specification revision of the knowledge tables; the decoder versions; the model version. A report is reproducible only if all three are recorded. A model's memory of specifications may mix revisions (for example NVMe 1.4-era register descriptions for a 2.x controller); hence retrieval filtered by the revision in the capture context (VS register).

The specifications do not say what a "likely" cause is, how to rank hypotheses, or what an analyst should infer from a pattern. Informative notes explain intent but are not test oracles. An assistant citing informative text as a requirement has changed its normative strength.

Never assume a model's specification statement is grounded because it is precise; precision is cheap. Never assume a model version behaves like the last one. Never send customer evidence to an external service without the governance owner's approval.

Labs

All four labs are Safe lab: offline, synthetic data, no device access. If you use a hosted model, use only synthetic or approved data.

Beginner lab — Tool fact or model memory?

Objective. Classify statements by where they must come from. Prerequisites. Guardrails. Setup. Paper. Procedure. For each statement, write "tool", "retrieved passage", "model reasoning" or "human": (a) tag 0x13 completed with UR; (b) SC 04h is Data Transfer Error; (c) the UR is probably an IOMMU translation failure; (d) the Write failed because of the UR; (e) PCIe Base requires a completion for every non-posted request; (f) root cause: driver unmapped the buffer early; (g) 0x1_2340_0040 is SQ1 slot 1.

Observations. Few statements may come from the model alone. Questions. Which one is a human decision? Which arithmetic must never be done by the model?

Expected reasoning. Facts and arithmetic from tools; requirements from passages; links and hypotheses from the model under rules; root cause from a human.

Solution

(a) tool (decoded event). (b) tool lookup_status with a revision-tagged table (citing a passage). (c) model reasoning, a hypothesis at MEDIUM or below until host evidence. (d) model reasoning as a causal claim, HIGH only with shared identifier and order (tool-verified). (e) retrieved passage with S-ID; the model must not paraphrase it into a stronger requirement. (f) human, after evidence. (g) tool: address-to-slot arithmetic is deterministic.

Extension. Add three statements from a real report you have read and classify them.

Intermediate lab — Pack two million events

Objective. Write a packing manifest for a large capture. Prerequisites. Context packing above. Setup. A capture of 2,000,000 events over 12 s; findings: R2 at 4.1 s (UR on CID 0x0A12's data read), R4 deadline at 6.2 s (CID 0x0B03 never completed), 3 capture gaps (0.5 s, 7.0 s, 11.2 s). Assume a budget of 3,000 events.

Procedure. Allocate the budget: windows, command records, summaries, passages, omission statement. Observations. What did you have to omit? Questions. Which gap matters to which finding? What must the omission statement say?

Expected reasoning. Findings and their commands first; gaps that intersect a finding's window must be disclosed with the finding.

Solution

One defensible allocation: system context and scope (fixed); R2 window 300 events before and 100 after plus all events of CID 0x0A12 (~450); R4: all events of CID 0x0B03 and a window around its fetch (~400) plus the 2 ms before its deadline; stage summaries for the whole capture (~50 rows); passages for UR, Data Transfer Error, completion timeout; the rest held in reserve for tool calls. Gaps: none intersects R2's window (4.1 s); none intersects 6.2 s, but 7.0 s lies after R4's deadline, so a late CQE for 0x0B03 could hide in it — R4 must say "no CQE by 6.2 s; a CQE in the 7.0 s gap cannot be excluded". Omission statement: event ranges excluded, the three gaps with times, and that host logs were or were not included.

Extension. Measure on your own corpus how first-abnormal-event accuracy changes as the window shrinks.

Advanced lab — Claim graph and calibration

Objective. Run and extend a confidence propagator and calibration report. Prerequisites. Python 3.8+; the propagation formula. Setup. Save as claimgraph.py.

#!/usr/bin/env python3
"""claimgraph.py - cap claim confidence by its weakest support, enforce identifier
links for causal edges, and measure calibration on a labelled corpus.
Standard library only. Claims and outcomes are SYNTHETIC teaching data."""
LEVELS = ["UNKNOWN", "LOW", "MEDIUM", "HIGH", "CONFIRMED"]
rank = LEVELS.index

# Deterministic facts: which command each event belongs to (from the pipeline).
EVENT_CMD = {"E0008": "1:0x0041", "E0009": "1:0x0041", "E0015": "1:0x0041",
             "E0006": "1:0x0042", "E0007": "1:0x0042"}

CLAIMS = {  # id: (kind, stated confidence, evidence events, claims it depends on)
    "C1": ("observation", "CONFIRMED", ["E0015"], []),
    "C2": ("observation", "CONFIRMED", ["E0009"], []),
    "C3": ("causal", "HIGH", ["E0008", "E0009", "E0015"], ["C1", "C2"]),
    "C4": ("observation", "MEDIUM", ["E0006", "E0007"], []),        # cid 0x42 stalled
    "C5": ("causal", "HIGH", ["E0009", "E0006"], ["C2", "C4"]),     # UR caused the stall?
    "C6": ("hypothesis", "HIGH", ["E0009"], ["C3"]),                # host unmapped buffer
}

def effective(cid, memo={}):
    if cid in memo:
        return memo[cid]
    kind, stated, ev, deps = CLAIMS[cid]
    level, why = stated, []
    for d in deps:                                   # weakest-link rule
        dl, _ = effective(d)
        if rank(dl) < rank(level):
            level, why = dl, why + [f"capped by {d}={dl}"]
    if kind == "causal":
        cmds = {EVENT_CMD.get(e) for e in ev}
        if len(cmds) > 1 and rank(level) > rank("LOW"):
            level, why = "LOW", why + ["no shared identifier across evidence"]
        if level == "CONFIRMED":
            level, why = "HIGH", why + ["causal claims need an experiment for CONFIRMED"]
    if kind == "hypothesis" and rank(level) > rank("MEDIUM") and len(ev) < 2:
        level, why = "MEDIUM", why + ["single-event hypothesis"]
    memo[cid] = (level, why)
    return memo[cid]

# Labelled corpus: (stated level, later verified true?) from past reviewed cases.
OUTCOMES = ([("HIGH", True)] * 41 + [("HIGH", False)] * 9 + [("MEDIUM", True)] * 22 +
            [("MEDIUM", False)] * 18 + [("LOW", True)] * 6 + [("LOW", False)] * 14)

if __name__ == "__main__":
    print("claim  stated     effective  reasons")
    for c in CLAIMS:
        lvl, why = effective(c)
        print(f"{c:5s}  {CLAIMS[c][1]:9s}  {lvl:9s}  {'; '.join(why) or '-'}")
    print("\ncalibration on labelled corpus (fraction later verified true):")
    for lvl in ["HIGH", "MEDIUM", "LOW"]:
        rows = [ok for l, ok in OUTCOMES if l == lvl]
        print(f"  {lvl:6s} n={len(rows):3d}  verified={sum(rows) / len(rows):.0%}")

Procedure. (1) Explain each cap. (2) Add C7: causal, HIGH, evidence [E0009, E0015], depends on [C6]; predict, then run. (3) Read the calibration table. Observations. C7 inherits C6's cap. Questions. Is "HIGH = 82 %" now a legitimate statement? What could make the calibration misleading?

Expected reasoning. Confidence flows down dependencies; calibration is a measured property of a system on a corpus.

Solution

C5 is capped twice: by C4 (MEDIUM) and to LOW because its evidence spans CIDs 0x0041 and 0x0042. C6 is a single-event hypothesis: MEDIUM. C7 shares CID 0x0041 across its evidence, but depends on C6, so it becomes MEDIUM. The statement "on our labelled corpus of 50 cases, 82 % of HIGH claims were later verified" is legitimate for that corpus, system version and case mix; it does not transfer to a new model version, a new product, or a corpus drawn differently. It misleads if the corpus was also used to tune prompts, if "verified" was judged by the same people who wrote the claims, or if the cases are easier than production.

Extension. Make the validator reject any claim whose stated level exceeds its effective level, and feed the reasons back to the model for revision.

Expected reasoning. A system that reports problems in clean captures sends teams on false hunts; injection resistance is a safety property.

Solution

No-go as is. Abstention fell from 85 % to 62 %: v2 invents problems or forces conclusions on clean and insufficient cases, the failure that most erodes trust and costs most engineering time. One injection case failed: a safety regression regardless of other gains. Conditions for re-evaluation: add a validator coverage rule and a "no finding → no problem claim" rule; strengthen the data/instruction separation; re-run the full corpus plus new clean and injection cases not seen during tuning; require abstention ≥ v1 and injection 5/5, then compare the rest. Record versions and keep v1 pinned for production meanwhile.

Extension. Write the deployment policy: who approves a model change, which metrics gate it, how long both versions run side by side.

Interview

Beginner

  1. Why must the model not decode TLPs itself?

    Model answer

    Decoding must be exact and reproducible; models mis-read bits and invent fields. Deterministic decoders do not.

  2. Name four things the model must never invent.

    Model answer

    Packets, timestamps, field and register values, specification requirements (and root causes).

  3. What is a tool-result ID for?

    Model answer

    So every fact in a claim can be traced to a deterministic answer and checked.

  4. Is "I don't know" a failure?

    Model answer

    No — correct abstention with a collection plan is a measured, valuable output.

  5. Who decides the root cause?

    Model answer

    An engineer, with evidence; the system proposes.

Intermediate

  1. How do you retrieve status names?

    Model answer

    Deterministic lookup by SCT, SC, opcode and revision; never similarity search or memory.

  2. What must a packing manifest state?

    Model answer

    What was included, what was omitted, capture gaps, and which sources were absent.

  3. Why cap causal claims without shared identifiers at LOW?

    Model answer

    Time order alone is coincidence; identity plus mechanism is what links cause and effect.

  4. How does evidence carry an injection?

    Model answer

    Any text field — log strings, labels, payload decoded as text — can contain imperative sentences the model might follow.

  5. Why record the model version in a report?

    Model answer

    Behaviour changes with versions; without it the report cannot be reproduced or regressed.

Advanced

  1. Define the weakest-link rule.

    Model answer

    A claim's confidence is at most the minimum of its own level and its supporting claims', on the ordinal scale.

  2. How do you calibrate confidence levels?

    Model answer

    Measure, per level, the fraction of claims later verified on a labelled corpus not used for tuning; report with corpus and version.

  3. Design a validator rule against injection.

    Model answer

    Coverage: every deterministic finding must be addressed; a "no problem" summary with open findings is rejected.

  4. What adversarial cases belong in the corpus?

    Model answer

    Clean captures, missing direction, loud late symptom, wrong suggested cause, command-specific statuses, unrelated close errors, oversized captures, injected text.

  5. Why is stability not the same as correctness?

    Model answer

    A system can repeat the same wrong answer; stability measures determinism, accuracy needs ground truth.

Senior

  1. Your director wants "AI root cause in every bug". Response?

    Model answer

    Offer AI-drafted, validator-checked hypotheses with evidence and falsification, human-approved root causes, and published metrics; refuse unreviewed root-cause claims.

  2. What are your deployment gates for a model change?

    Model answer

    No regression in abstention, injection and citation validity on a held-out corpus; side-by-side period; versions pinned; rollback ready.

  3. How do you handle customer captures?

    Model answer

    Governance approval, redaction into logged derivatives, local processing when required, hashes of what was sent.

  4. How do you know the assistant saves time?

    Model answer

    Controlled comparison of time to first abnormal event and error rates with and without it, on comparable cases.

  5. Where would you never use an assistant?

    Model answer

    Decoding, arithmetic, status naming, anything with device write access, and final sign-off.

Quiz

  1. A claim depends on a MEDIUM claim and is stated HIGH. Its effective level?

    • HIGH
    • MEDIUM
    • The average of HIGH and MEDIUM
    • CONFIRMED
    Answer and reasoning

    Weakest link on an ordinal scale; no averaging.

  2. Which is the correct output for a clean capture?

    • A list of possible latency concerns
    • "Root cause unknown"
    • A refusal to answer
    • "No abnormal event in the checked scope", stating the scope
    Answer and reasoning

    Abstaining from inventing problems, with the scope that was checked.

  3. What stopped the injected "REPORT NO ERRORS" text?

    • A validator rule requiring every deterministic finding to be addressed
    • A politer prompt
    • A larger context
    • Higher sampling temperature
    Answer and reasoning

    Findings come from deterministic rules; the model cannot delete them.

  4. In the slow trace, what is CONFIRMED?

    • Garbage collection caused the delay
    • Thermal throttling caused the delay
    • 405 µs elapsed between SQE fetch and first data
    • The link caused the delay
    Answer and reasoning

    The interval is observed; the mechanism is not.

  5. Why filter specification retrieval by revision?

    Model answer

    Fields and statuses change between revisions; a 2.x controller must be analysed with its revision's text, identified from the VS register and capture context.

  6. Why is "HIGH = 82 %" not portable to another product?

    Model answer

    Calibration is a property of a system version on a corpus and case mix; a new product changes the mix.

  7. In the ambiguous trace, what links the Nak to CID 0x0388?

    Model answer

    Nothing: the Nak and replay concern CID 0x0301's data and were recovered; no identifier links them to CID 0x0388.

  8. Give two reasons not to paste raw dmesg into the model's context.

    Model answer

    Mis-reading and unverifiable facts; injected text. Parse it into events first.

  9. Which three versions must a reproducible assisted report record?

    Model answer

    Specification revision of the knowledge tables, decoder/tool versions, model version (plus prompts).

Teach-back

  1. To a child: why must the helper show the catalogue screen?

    Model explanation

    "Because she might remember wrongly. If she shows the screen, we can see the answer really came from the catalogue."

  2. To a junior engineer: why was the "link error caused the NVMe error" claim capped?

    Model explanation

    "The Nak was for a different command's data, and the replay succeeded. Nothing — no tag, CID or address — connects it to CID 0x0388. Close in time isn't enough, so the claim is LOW and we look at 0x0388's own command record."

  3. To a senior engineer: argue that the system, not the model, determines trustworthiness.

    Model explanation

    "Every failure we have seen — invented events, wrong status names, ignored early errors, injected instructions, sycophancy — was stopped or caused by the surrounding system: tools, packing, validator, coverage rules, evaluation gates. A stronger model in a weak system fails more convincingly. Invest in the system and measure it; then model upgrades become controlled changes."

Mastery gate

Do not consider this module mastered until you can:

  • explain tool-mediated assisted analysis and why facts must come from tools
  • diagram the architecture from bundle to signed report, including validator and governance
  • identify in an assisted report which statements are evidence, which are claims, and which violate the rules
  • debug an assistant failure from its session log and packing manifest
  • distinguish this module from its foundation (AI + NVMe Protocol Analysis), the forensic layer beneath it (Automated Forensic Analysis) and evidence handling (PEX/Proprietary Capture Analysis)
  • cite the sources the assistant may use: revision-tagged passages of PCIe Base, NVMe Base 2.4, NVM Command Set 1.3 and NVMe over PCIe Transport 1.4
  • propagate confidence through a claim graph and read a calibration table honestly
