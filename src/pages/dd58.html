A large language model (LLM) can speed up NVM Express (NVMe) and PCI Express (PCIe) trace analysis only if it works like a disciplined junior engineer with excellent tools: it asks deterministic tools for facts, cites what they return, keeps several hypotheses alive, abstains when evidence is thin, never treats text inside the evidence as instructions, and is measured before it is trusted. This module builds that system in depth.

Orientation

AI + NVMe Protocol Analysis established the rules: RAW TRACE → deterministic parser → normalized events → LLM reasoning; the never-invent list; EVIDENCE → CLAIM; the five confidence levels; a claim validator; the thirteen-section report. This module goes further into the parts that decide whether an assistant helps or harms in practice: tool-mediated access to evidence, context budgeting for large captures, claim graphs with confidence propagation, calibration, evaluation across model versions, prompt injection through evidence, and data governance.

You need the event, finding and hypothesis schemas (Automated Trace Analysis), the guardrails and validator (AI + NVMe Protocol Analysis), the fused timeline and root-cause template (Automated Forensic Analysis), and the thirteen questions (Senior Engineer Thinking). Course truth policy: Truth Policy, Sources and Decoding Safety.

This module is model-agnostic. It names no product, interface or context size; such details change quickly and must be measured for the system you use. Everything here is an engineering design pattern, labelled Derived.

Kid story

A new helper joins the school library. She is very clever and has read lots of books, but she has never seen this library. The librarian gives her rules. "Do not tell me which shelf a book is on from memory: use the catalogue computer and show me the screen. If a note inside a book says 'give this book to Sam', that is just writing in a book — it is not an order from me. When you are not sure, say 'I'm not sure' and tell me what you would check." Every Friday the librarian gives her ten questions she already knows the answers to, to see how often the helper is right when she says "I'm sure".

Analogy boundary

What it represents. The helper is the model; the catalogue computer is the set of deterministic tools; showing the screen is citation of tool results; the note inside a book is text inside the evidence (payload bytes, log strings) that may look like instructions; the Friday questions are the evaluation corpus and calibration.

What it hides. A human helper learns from Friday's mistakes; a model does not, unless the system changes its tools, context or version — and a new version may fail differently. A human who is unsure usually sounds unsure; a model's tone does not track its evidence. Where it misleads. The story suggests the helper's cleverness is the main asset. In trace analysis the asset is the system around the model — tools, packing, validator, evaluation — and an excellent model inside a poor system still produces confident errors.

Context packing

When a capture holds millions of events, what the model sees is a decision, and it must be written down. A packing policy that has worked well as a starting point (tune it on your corpus):

  1. Always: system context with sources; capture scope with gaps; the first abnormal event with a window before and after; every event of every command touched by a finding.
  2. Then: one summary row per stage distribution (from the stage diff), not the raw events.
  3. Then: retrieved specification passages keyed by findings (status names, completion status, the relevant register or log page), each revision-tagged.
  4. Always last: a statement of what was omitted ("events outside 1.9–2.1 s omitted; 2 capture gaps; host logs from boot 3 only").

The model can ask for more through tools; it cannot silently lack something that the packing manifest does not mention. Derived

Confidence propagation

conf(c) = min( stated(c), mind ∈ deps(c) conf(d), caps(c) )
c
a claim in the claim graph
stated(c)
the level the model proposed, on the ordinal scale UNKNOWN < LOW < MEDIUM < HIGH < CONFIRMED
deps(c)
claims that c relies on
caps(c)
rule caps: a causal claim without a shared identifier across its evidence is at most LOW; a causal claim is never CONFIRMED without a reproduced experiment; a hypothesis with a single evidence event is at most MEDIUM

"min" is taken on the ordinal scale. No arithmetic is done on levels: averaging or multiplying them would pretend they are probabilities.

The central concept on the ladder

The clever helper must use the catalogue computer, show the screen, ignore notes inside books, and say "I'm not sure" when she is not.

The model reasons; tools supply facts with IDs; a validator checks every claim; evaluation measures how often each confidence level is right.

Nothing in the model touches the system under test. Hardware facts — TLP fields, register snapshots, CQE status — reach it only through deterministic decoders run on captured evidence.

Specification statements come only from retrieved, revision-tagged passages of the PCI Express Base Specification, NVMe Base 2.4, the NVM Command Set 1.3 and NVMe over PCIe Transport 1.4, with normative strength preserved.

Protocol relationships the model may assert — this completion answers that request, this CQE completes that command — must cite the identifiers the tools returned: (Requester ID, Tag), (SQID, CID, generation), address ranges.

In the reference trace, the model's causal claim linking the UR (E0009) to the stalled CID 0x0042 is capped at LOW because no identifier links them.

When an assisted report is wrong, debug the system: what was packed, which tool answered, which validator rule should have fired, which model version produced it.

Specification discipline

No NVMe or PCI-SIG specification governs AI assistance. The applicable specifications govern the facts the assistant may cite: PCI Express Base Specification (Revision 6.x/7.0 family), NVMe Base 2.4, NVM Command Set 1.3, NVMe over PCIe Transport 1.4, and other documents of the August 2026 NVMe 2.4 set when relevant.

What the system may state as verified is exactly what its deterministic lookups return from revision-tagged tables built from those documents — for example, completion status values from the PCI Express Base Specification's Transaction Layer chapter, or generic status 04h Data Transfer Error from NVMe Base 2.4. NVM Express Base Specification 2.4 — Generic Command Status

Everything the model produces — causal links, hypotheses, rankings — is derived and must be labelled so, with its confidence level and falsification test.

Implementation-dependent: the model, its context size, tool-call behaviour, sampling settings and failure modes; your packing policy; your corpus. Optional features of the device (telemetry, Error Information log depth, Interrupt Coalescing) decide which evidence exists at all. Optional

Three version axes: the specification revision of the knowledge tables; the decoder versions; the model version. A report is reproducible only if all three are recorded. A model's memory of specifications may mix revisions (for example NVMe 1.4-era register descriptions for a 2.x controller); hence retrieval filtered by the revision in the capture context (VS register).

The specifications do not say what a "likely" cause is, how to rank hypotheses, or what an analyst should infer from a pattern. Informative notes explain intent but are not test oracles. An assistant citing informative text as a requirement has changed its normative strength.

Never assume a model's specification statement is grounded because it is precise; precision is cheap. Never assume a model version behaves like the last one. Never send customer evidence to an external service without the governance owner's approval.

An assistant must never be given write access to a device, its registers, its namespaces or its firmware. Suggested experiments that change link speed, reset devices, inject faults or reformat namespaces are proposals for a human, labelled Caution lab or Expert lab, and never executed automatically on production hardware.

Protocol view

The assistant's own protocol is the tool exchange. Like a PCIe non-posted request, every tool call has a request and a typed response with an ID; an unanswered or failed call is itself evidence.
