A doorbell is a single 32-bit write from the CPU to a register in the SSD. It is the only thing the host must send across PCI Express (PCIe) to start a command, and the only thing it must send to free completion slots. This chapter follows one command through all nine steps, from building the command to the interrupt, shows each doorbell as the exact Transaction Layer Packet (TLP) an analyzer would capture, and then catalogues the doorbell bugs that hang real systems.

Why this chapter exists

Doorbells are tiny, and that is exactly why they are misunderstood. A doorbell carries no command and no data — only an index. It does not wait for an answer. It does not tell the controller "one more command" but "the tail is now here". Getting any of those wrong produces commands that are never fetched, commands fetched twice, stale commands re-executed, or completion queues the controller believes are full.

Doorbells are also the seam between three worlds: the CPU's memory ordering rules (is the command in memory before the doorbell leaves?), PCIe's posted-write semantics (the doorbell has no completion), and NVM Express (NVMe) queue semantics (what the value means). A senior engineer reads a doorbell write in a trace and immediately knows which queue, which side, how many new entries, and whether the value is even legal.

Learning objectives

  • Describe, step by step, the nine-step flow from building a command to the host being interrupted, naming the actor, the state change and the evidence for each step.
  • Compute the address of any SQ tail or CQ head doorbell from CAP.DSTRD and the queue identifier.
  • Decode a doorbell write at TLP level: format, type, length, byte enables, address, payload, posted semantics.
  • Explain why a write memory barrier is needed before the doorbell and what happens without it.
  • Explain the CQ head doorbell: when it is written, what it frees, and what happens if it is late or missing.
  • Explain shadow doorbells and the Doorbell Buffer Config command, including their version and optional status.
  • Diagnose doorbell bugs: stale tail, wrapping errors, invalid values (and the asynchronous event they cause), wrong stride, wide writes, missing barriers.

The story

Remember the spinning tray of order cards and the bell? Here's a secret about the bell: it doesn't just ding. Every time a child rings it, they hold up a big number card — "the next empty slot is 8". The shopkeeper doesn't count dings; she looks at the number. If two children ring at once, or a child rings twice by accident, nothing bad happens — the number is still 8.

But there's a rule: you must put the order card in the tray before you ring and hold up the number. If you ring first and are still writing the card, the shopkeeper might grab a half-written card!

And when the children have read answer cards, they ring a different bell with a number: "we've read up to answer slot 40" — so the shopkeeper knows those answer slots are free to use again.

At a busy deli, customers pull numbered tickets; the server looks at a display showing "now taking up to ticket 57". The display isn't "one more customer" — it is an absolute position. If the display updates twice to 57, the server isn't confused. If it jumps from 50 to 57, the server knows seven customers are waiting. The display is updated by the front desk after the customer has actually taken a ticket; if the desk updated the display before printing the ticket, the server would call a number nobody holds.

What it hides. The deli display is read by the server whenever she likes; an NVMe doorbell is a write that the controller hardware latches when it arrives — there is no "display" in host memory the controller polls (except with shadow doorbells, below). The deli's numbers keep growing; NVMe indices wrap around at the queue size, so "50 → 7" can be a legal move.

Where it misleads. The analogy suggests the display tells the server everything. In NVMe the doorbell carries only an index; the command itself is fetched separately by the controller using DMA (direct memory access) from host memory. The doorbell also has no acknowledgement: the front desk never hears "got it".

Beginner explanation

Each queue pair has two doorbell registers in the controller's BAR0 (Base Address Register 0) space, starting at offset 1000h:

  • the SQ y Tail Doorbell (SQyTDBL): the host writes the new Submission Queue tail here after adding commands;
  • the CQ y Head Doorbell (CQyHDBL): the host writes the new Completion Queue head here after consuming completions.

There are no doorbells for the SQ head or the CQ tail, because those indices belong to the controller (Chapter 25).

A doorbell write is a normal CPU store instruction to an uncached memory-mapped address. The CPU hands it to the PCIe root complex, which turns it into a Memory Write TLP and sends it down the link. The CPU does not wait for the device; the store is "posted" — fire and forget.

The nine steps

  1. The host creates a command (a 64-byte Submission Queue Entry, SQE).
  2. The host writes the command into the SQ slot at its current tail.
  3. The host updates its SQ tail variable (tail + 1, wrapping at the queue size).
  4. The host writes the new tail value to the SQ tail doorbell.
  5. The controller notices the doorbell write.
  6. The controller fetches the command from host memory.
  7. The controller executes the command (including any data transfer).
  8. The controller posts a completion (a 16-byte Completion Queue Entry, CQE) into the CQ.
  9. The controller interrupts the host, if interrupts are enabled for that CQ.

Then the host processes the completion and writes the CQ head doorbell. We will walk through every step in detail next.

Engineering explanation

Doorbell addresses

The doorbell as a TLP

BAR0 in the reference system is a 64-bit BAR assigned below 4 GiB (0xFE60_0000). PCIe requires that a Memory request to an address below 4 GiB use the 32-bit address format (3 DW header), so the doorbell is an MWr32: Fmt = 010b (3 DW header with data), Type = 0_0000b (memory request).

SQ1 tail doorbell = 6 as a Memory Write TLP (3 DW header + 1 DW payload). Synthetic example.

Things to notice:

  • Length = 1 DW, First DW Byte Enables = 1111b, Last DW BE = 0000b: a single, full 32-bit write. A doorbell write with partial byte enables would be a driver or compiler mistake (for example, a 16-bit store).
  • Posted: there is no completion TLP. The CPU learns nothing about whether the write arrived or was accepted.
  • The Requester ID is the root port's / root complex's, not the device's; MMIO writes originate at the host side of the link.
  • The Tag is not meaningful for matching: posted requests receive no completion, so nothing is matched against the tag.
  • Payload byte order: PCIe carries data bytes in address order. An analyzer may show the payload as bytes 06 00 00 00 or as the Dword 0x0000_0006, depending on its display mode.

Because the doorbell is posted, the CPU's store instruction completes in nanoseconds; the cost on the CPU is small. A read of a device register is non-posted and stalls the CPU until the completion returns — often around a microsecond. NVMe's design avoids every MMIO read on the I/O path; doorbells are writes only.

Why the barrier before the doorbell matters

Steps 2 and 4 are both CPU stores, but to different kinds of memory: the SQE goes to cacheable RAM, the doorbell to uncached MMIO. Without a barrier, a weakly ordered CPU may let the MMIO store overtake the SQE store. The controller would then fetch slot 5 before the SQE is there and execute whatever was in slot 5 last time round — an old command, re-executed. That is silent data corruption (a stale Write re-issued) or a mysterious duplicate completion.

In Linux, writel() includes the necessary ordering: it guarantees that prior writes to normal memory are visible to the device before the MMIO write. That is why the NVMe driver calls writel() rather than the relaxed variant for doorbells. On x86 the hardware already orders these stores; on Arm and other weakly ordered CPUs, the barrier is a real instruction. (The kernel's Documentation/memory-barriers.txt describes this under device I/O.)

The barrier must come after the SQE is completely written and before the doorbell. Placing it after the doorbell does nothing useful. And it must cover all SQEs in a batch: write slots 5, 6, 7, then one barrier, then one doorbell with tail = 8.

Batching: one doorbell, many commands

Because the doorbell carries the absolute tail, the host can add several SQEs and ring once. That saves PCIe bandwidth and, more importantly, controller work. Linux's block layer tells the driver when a request is the last of a batch, so the driver can defer the doorbell until then. The cost is a little latency for the first commands in the batch. If the "last" signal is lost — for example a batch is cut short by an error path that forgets to ring — commands sit in the SQ unfetched until the next doorbell arrives, sometimes much later: a classic intermittent latency spike or timeout.

How the controller notices (step 5)

The specification defines what the doorbell means, not how quickly a controller must act on it Implementation-dependent. Typical designs:

  • Hardware doorbell detection: the write sets a "pending" bit for the queue; a hardware arbiter or firmware loop picks pending queues according to the arbitration mechanism (round robin or weighted round robin, Chapter 25).
  • Firmware polling of a doorbell shadow inside the controller.
  • Prefetch: on seeing tail − head = 3, the fetch engine reads all three SQEs in one Memory Read request (192 bytes), subject to Max Read Request Size.

Doorbell-to-fetch latency in a trace is your measure of step 5. If it varies wildly or grows under load, the controller's front end (arbitration, firmware) is the bottleneck, not the media.

The CQ head doorbell

The CQ head doorbell tells the controller which CQ slots the host has consumed and may be reused. Without it, the controller eventually finds the CQ full and stops posting (Chapter 25, abnormal trace). Key points:

  • It can be written lazily — once per batch of reaped CQEs, not once per CQE.
  • It must never move past entries the host has not consumed: that would let the controller overwrite unread completions.
  • It does not acknowledge the interrupt. With MSI-X there is no interrupt acknowledgement register; each MSI-X message is an edge-like event. (The Interrupt Mask Set/Clear registers INTMS and INTMC at offsets 0Ch and 10h apply to pin-based and single/multiple-message MSI interrupts, not MSI-X.)
  • Controllers may use CQ head doorbell writes as a hint for interrupt coalescing or for posting more CQEs — behaviour that is Implementation-dependent.

Shadow doorbells and Doorbell Buffer Config

In a virtual machine with an emulated NVMe controller, every MMIO doorbell write traps to the hypervisor (a "VM exit"), costing microseconds. NVMe 1.3 added an Optional Admin command, Doorbell Buffer Config (opcode 7Ch), to reduce those traps NVMe 1.3 and later:

  • The host gives the controller two memory pages: a Shadow Doorbell buffer (PRP Entry 1) and an EventIdx buffer (PRP Entry 2). Each has one slot per doorbell, laid out with the same stride as the real doorbells.
  • The host writes new tail/head values into the shadow doorbell buffer in host memory, which costs no trap.
  • The controller (the hypervisor's emulation) writes into the EventIdx buffer the index at which it next wants a real MMIO doorbell write.
  • The host performs the real MMIO doorbell write only when its update crosses the EventIdx value — that is, when the controller has asked to be woken. Otherwise the controller, which is actively polling the shadow buffer, picks up the new value by itself.
/* Return true if moving the index from old_idx to new_idx passes event_idx,
 * i.e. the controller asked to be notified somewhere in (old_idx, new_idx]. */
static bool need_event(uint16_t event_idx, uint16_t new_idx, uint16_t old_idx) {
    return (uint16_t)(new_idx - event_idx - 1) < (uint16_t)(new_idx - old_idx);
}

void ring_sq(struct queue *q, uint16_t new_tail) {
    if (q->dbbuf_shadow) {
        uint16_t old = q->dbbuf_shadow[q->sq_db_index];
        q->dbbuf_shadow[q->sq_db_index] = new_tail;     /* memory write, no trap */
        mb();                                          /* shadow before EventIdx read */
        if (!need_event(q->dbbuf_eventidx[q->sq_db_index], new_tail, old))
            return;                                    /* controller is polling */
    }
    writel(new_tail, q->sq_db);                        /* real MMIO doorbell */
}

Support is advertised in Identify Controller's Optional Admin Command Support (OACS) field. The scheme mirrors the "event index" technique of virtio. It is aimed at emulated or paravirtualised controllers; physical SSDs rarely implement it, and it changes what you see on the link — far fewer doorbell TLPs than commands. The exact normative rules (buffer layout, when the controller must re-read shadows, behaviour across resets) are in the NVMe Base Specification's Doorbell Buffer Config description; check them there Check details.

Invalid doorbell values and asynchronous events

The specification defines how a controller reports two classes of doorbell misuse to the host, through the Asynchronous Event mechanism (Chapter 26) with Asynchronous Event Type "Error status":

Doorbell-related asynchronous error events (names as in the NVMe Base Specification)
Asynchronous Event Information (name)Cause
Write to Invalid Doorbell RegisterHost wrote a doorbell register for a queue that does not exist (or another invalid doorbell register)
Invalid Doorbell Write ValueHost wrote a value that is not valid for the queue: for example a tail or head ≥ the queue size, an SQ tail that would overfill the queue, or a CQ head that passes entries not yet posted

The event is reported only if an Asynchronous Event Request command is outstanding (and the event type is enabled where the specification makes that configurable). Completion Dword 0 of that request names the event type, the event information and the log page to read — the Error Information log (Log Page Identifier 01h). The host must then read that log page (with Get Log Page) before the controller will report further events of that type, unless it uses the Retain Asynchronous Event option. The numeric Asynchronous Event Information values and the precise list of invalid-value conditions are defined in the specification; verify them there Check values.

The specification defines the reporting; it does not promise what the controller does with the queue after an invalid doorbell write. Some controllers ignore the write, some stop processing that queue, some require a reset. Never write test cases that depend on post-error queue behaviour without the vendor's documentation.

The sixteen questions: the doorbell

1. What is it?
A 32-bit controller register the host writes to publish a new SQ tail or CQ head.
2. Why was it created?
To let the host notify the controller of new commands or freed completion slots with one cheap, posted write.
3. What problem does it solve?
Without it, the controller would have to poll host memory for new commands (wasting bandwidth and adding latency) or the host would have to perform slow handshakes.
4. What existed before it?
AHCI's Command Issue register (a bit per command slot), and similar "issue" registers in other controllers.
5. Why is the current design better?
One write covers any number of new commands; it carries an absolute index, so repeats are harmless; per-queue doorbells avoid cross-core contention.
6. Who creates it?
The host writes it (the register exists in the controller from enable; it is meaningful once the queue exists).
7. Who consumes it?
The controller's doorbell logic and arbiter.
8. Where does it live?
In BAR0 at 1000h + index × stride.
9. What memory/registers are involved?
SQyTDBL, CQyHDBL, CAP.DSTRD; the SQ memory being published; shadow and EventIdx buffers if Doorbell Buffer Config is used.
10. What happens before it?
SQE written to memory, tail updated, write barrier (SQ); CQEs consumed (CQ).
11. What happens after it?
SQ: arbitration and SQE fetch. CQ: those slots become available for new CQEs.
12. What happens if it is wrong?
Lost, duplicated, stale or corrupted commands; full-CQ stalls; asynchronous error events.
13. What does the protocol analyzer show?
Host→device MWr32 (or MWr64 if BAR0 is above 4 GiB), Length 1, to the doorbell address, with the index as payload.
14. What does Linux show?
Nothing directly; only indirect signs (timeouts, interrupt counts). Tracepoints and analyzers are needed to see doorbells.
15. What would a validation engineer test?
Every invalid value class, doorbells for nonexistent queues, wrap at every size, batching, repeated writes, wide/partial writes, doorbells during reset, shadow doorbell semantics if supported, doorbell-to-fetch latency under load.
16. What would a senior engineer suspect when it fails?
Memory ordering (barrier), stride, wrap arithmetic, lost batch-end doorbells, CQ head not published, a hypervisor trapping and mis-emulating doorbells.

Hardware view

On the host side, the doorbell page is mapped uncached (UC) so stores go straight to the device without being combined or reordered with each other. Write-combining (WC) mappings are not used for doorbells because combining two doorbell writes into one burst — or delaying them in a buffer — would break their meaning and timing.

In the controller, the doorbell block is typically a register file with one entry per supported doorbell. A write generates an event for that queue. The controller compares the new SQ tail with its internal head (or the new CQ head with its internal tail) and validates it. Valid SQ events go to the arbiter; valid CQ events update free-slot accounting.

Some controllers implement doorbells in hardware that directly triggers DMA fetch engines, giving doorbell-to-fetch times well under a microsecond; others hand doorbell events to firmware, where latency depends on firmware load. Both are compliant. Measure, don't assume Implementation-dependent.

The Controller Memory Buffer (CMB), when supported and used for SQs, changes the picture: the host writes SQEs directly into device memory with posted writes, so step 6 (fetch) becomes internal to the device. The doorbell is still required.

  • It does not require a controller to fetch all published entries at once.
  • It does not define post-error queue behaviour after an invalid doorbell value.
  • Check in the specification: read behaviour of doorbell registers (do not rely on reading them back), the exact invalid-value conditions, and the numeric Asynchronous Event Information values.
  • Never ring before the SQE is visible in memory.
  • Never write a count; write the absolute index.
  • Never hard-code the stride.
  • Never assume a doorbell was received because the store completed — posted writes give no acknowledgement.
  • Never use 64-bit or partial-width stores on doorbells.

Between the host and device the doorbell is a one-way message. The controller's "reply" is its next action: a Memory Read of SQEs. That gives a simple, powerful correlation rule for traces: every SQ tail doorbell that adds N entries should be followed by device reads that together cover exactly those N slots, starting at the previous tail.

Code / pseudocode

void submit_batch(struct queue_pair *q, const struct sqe *cmds, int n) {
    for (int i = 0; i < n; i++) {
        memcpy(&q->sq[q->sq_tail], &cmds[i], 64);           /* step 2 */
        if (++q->sq_tail == q->size)                       /* step 3: wrap at SIZE, */
            q->sq_tail = 0;                                /* never write size      */
    }
    /* step 4: writel() orders all prior normal-memory stores before the MMIO store */
    writel(q->sq_tail, q->sq_db);                          /* one doorbell for n commands */
}

void reap_and_release(struct queue_pair *q) {
    uint16_t start = q->cq_head;
    while (cqe_is_new(q)) {                                  /* phase tag check */
        handle(&q->cq[q->cq_head]);
        if (++q->cq_head == q->size) { q->cq_head = 0; q->phase ^= 1; }
    }
    if (q->cq_head != start)
        writel(q->cq_head, q->cq_db);                      /* free CQ slots */
}

The caller must ensure n does not exceed the free SQ slots (computed from the latest SQHD). Notice that writel is a 32-bit store; using writeq here would write two doorbells.

Worked example

Problem. An emulated controller reports CAP.DSTRD = 1. Its BAR0 is at 0x2_0000_0000 (above 4 GiB). (a) Give the SQ3 tail and CQ3 head doorbell addresses. (b) What TLP format carries the doorbell? (c) The analyzer shows a write of 0x0000_0010 to BAR0 + 0x1030. Decode it. (d) The previous value written there was 0x0000_000C, and SQ3 has 16 entries. What should follow on the link?

(a) Stride = 4 << 1 = 8 bytes. SQ3TDBL = 1000h + 2 × 3 × 8 = 1000h + 30h = 1030h → 0x2_0000_1030. CQ3HDBL = 1000h + 7 × 8 = 1038h → 0x2_0000_1038.

(b) The address is above 4 GiB, so a 4 DW header Memory Write (MWr64): Fmt = 011b, Type = 0_0000b, Length = 1, First BE 1111b.

(c) Offset 1030h = SQ3 tail doorbell (index (1030h − 1000h) / 8 = 6 → even → SQ of queue 3). Value 0x10 = 16. For a 16-entry queue, valid indices are 0–15: 16 is invalid — a wrap bug.

(d) Nothing useful: the controller should not fetch on an invalid value. If an Asynchronous Event Request is outstanding, expect an Admin CQE completing it with an Error status event (Invalid Doorbell Write Value), an interrupt on vector 0, and then the host's Get Log Page for the Error Information log. The intended value was 0, which would have added (0 − 12) mod 16 = 4 entries (slots 12–15) and triggered a fetch from SQ3 base + 12 × 64.

Common mistakes

Doorbell misconceptions
MisconceptionReality
"The doorbell carries the command."It carries only an index. The command is fetched by the controller with DMA.
"Each doorbell means one new command."It means "the tail is now here". The number of new commands is the difference from the previous tail, modulo size.
"The doorbell write is acknowledged."It is a posted write: no completion, no acknowledgement.
"The CQ head doorbell acknowledges the interrupt."It frees CQ slots. MSI-X needs no acknowledgement.
"There's an SQ head doorbell."No. SQ head is reported in CQEs (SQHD).
"The stride is always 4."Only when CAP.DSTRD = 0.
"The barrier is only needed on Arm."It is needed in the code everywhere; on x86 it compiles to a compiler barrier, but omitting it is still a bug that the compiler can expose.
"Counting doorbell TLPs counts commands."Batching and shadow doorbells break that; count fetched SQEs instead.

Debugging connection

A doorbell investigation follows the correlation rule: each SQ doorbell should be followed by fetches covering exactly the slots it published; each CQ doorbell should not pass the CQEs posted.

  1. Decode every doorbell: queue, side, value. Flag values ≥ size, offsets not on stride boundaries, Length ≠ 1, partial byte enables.
  2. Compute the published range for each SQ doorbell: from the previous tail to the new tail − 1, modulo size.
  3. Match fetches: device MRd addresses and lengths should cover the range. Missing fetch → controller-side issue or invalid value. Extra fetch → an earlier doorbell you missed, or the controller re-reading.
  4. Check payloads: SQE payloads in the root complex's CplDs must match what the driver logged. Mismatch → barrier/ordering bug or slot reuse.
  5. Track CQ head: compare each CQ doorbell value with the CQE addresses posted. Head past the last CQE → invalid value. Long gaps without a CQ doorbell while CQEs pile up → full-CQ risk.
  6. Look at the Admin CQ for Asynchronous Event Request completions — the controller may already have told you which doorbell was wrong.

Many analyzers can trigger on "Memory Write to address range X with data ≥ Y". Set a trigger on the doorbell range with data ≥ the smallest queue size: it catches wrap bugs at the moment they happen, with the preceding traffic in the buffer.

Senior engineer insight

  • The doorbell is the boundary between two memory models. Bugs here are rarely NVMe bugs; they are CPU memory-ordering bugs that NVMe exposes. Review doorbell code with the CPU architecture manual and the kernel's memory-barrier documentation open.
  • Doorbell-to-fetch latency is a first-class performance metric. It isolates controller front-end delay from media and transfer time. Plot it against queue depth: a knee shows where firmware becomes the bottleneck.
  • Doorbells are where virtualisation costs hide. Each trapped doorbell costs a VM exit. Shadow doorbells, polling modes and hardware virtualisation (SR-IOV, Chapter 56) exist largely to remove that cost.
  • Absence is evidence. A missing CQ head doorbell, a missing batch-end doorbell, a missing fetch after a doorbell — the most important events in a doorbell investigation are often the ones that never happened. Make sure your capture filter would have shown them.
  • Arm an Asynchronous Event Request in every test. Without it, the controller cannot tell you about invalid doorbell writes, and you lose the cheapest diagnostic you have.

Lab: Decode and lint a doorbell trace

Safe lab Pure software analysis of a synthetic trace.

Objective

Decode doorbell writes to queue and side, track queue state from doorbells and CQE posts, and detect the doorbell bugs catalogued in this chapter.

Skills

Doorbell address arithmetic; modulo index arithmetic; correlating host writes with device actions; bug classification.

None.

Software required

Python 3.8+.

Input

A synthetic event list: host MWr TLPs to BAR0 (address, length in DW, data) and device CQE posts (queue, SQHD). Queues 0, 1 and 2 exist with 32, 1024 and 16 entries.

One decoded line per event, with "!!" and an explanation for each violation.

The doorbell address formula, the bug catalogue, and the asynchronous error events.

Step 1 — Run the linter

#!/usr/bin/env python3
"""Doorbell decoder and linter for synthetic traces (teaching model).

Input: host->device MWr TLPs into BAR0 plus device CQE posts (with SQHD).
Output: one decoded line per event and any doorbell rule violations.
"""

BAR0 = 0xFE60_0000
DSTRD = 0                              # CAP.DSTRD; stride = 4 << DSTRD bytes
STRIDE = 4 << DSTRD
QUEUES = {0: 32, 1: 1024, 2: 16}       # existing queue pairs: qid -> entries

class Queue:
    def __init__(self, size):
        self.size = size
        self.sq_tail = 0     # last SQ tail doorbell value
        self.sq_head = 0     # last SQHD seen in a CQE
        self.cq_tail = 0     # controller's CQ tail (counted from CQE posts)
        self.cq_head = 0     # last CQ head doorbell value

def decode(addr):
    off = addr - BAR0
    if off < 0x1000:
        return None, None, f"controller register 0x{off:02X}"
    if (off - 0x1000) % STRIDE:
        return None, None, f"offset 0x{off:X} not on a doorbell stride boundary"
    idx = (off - 0x1000) // STRIDE
    return idx // 2, ("SQ tail" if idx % 2 == 0 else "CQ head"), None

def lint(events):
    qs = {q: Queue(n) for q, n in QUEUES.items()}
    for ev in events:
        t, kind = ev[0], ev[1]
        if kind == "CQE":                       # ("CQE", qid, sqhd)
            _, _, qid, sqhd = ev
            q = qs[qid]
            q.sq_head = sqhd
            q.cq_tail = (q.cq_tail + 1) % q.size
            print(f"{t:>7}  CQE posted on CQ{qid}, SQHD={sqhd}")
            continue
        _, _, addr, ndw, value = ev              # ("MWr", addr, length_dw, data)
        qid, which, note = decode(addr)
        if note:
            print(f"{t:>7}  MWr 0x{addr:08X}: {note}")
            continue
        problems = []
        if ndw != 1:
            problems.append(f"{ndw}-DW write spans {ndw} doorbell registers")
        if qid not in qs:
            print(f"{t:>7}  {which} doorbell for queue {qid} = {value}  !! "
                  "queue does not exist (Invalid Doorbell Register event)")
            continue
        q = qs[qid]
        if value & 0xFFFF0000:
            problems.append("reserved bits 31:16 set")
        v = value & 0xFFFF
        if v >= q.size:
            problems.append(f"value {v} >= queue size {q.size} (Invalid Doorbell Write Value)")
        elif which == "SQ tail":
            added = (v - q.sq_tail) % q.size
            in_use_before = (q.sq_tail - q.sq_head) % q.size
            if added == 0:
                problems.append("tail unchanged: redundant or stale doorbell")
            elif in_use_before + added > q.size - 1:
                problems.append(f"adds {added} entries but only {q.size - 1 - in_use_before} free: overfills SQ")
            q.sq_tail = v
        else:
            freed = (v - q.cq_head) % q.size
            pending = (q.cq_tail - q.cq_head) % q.size
            if freed > pending:
                problems.append(f"head moves {freed} but only {pending} CQEs were posted: passes CQ tail")
            q.cq_head = v
        flag = "  !! " + "; ".join(problems) if problems else ""
        print(f"{t:>7}  {which} doorbell Q{qid} = {v}{flag}")

TRACE = [
    (0,     "MWr", 0xFE60_1008, 1, 3),       # SQ1 tail = 3
    (900,   "CQE", 1, 3), (910, "CQE", 1, 3), (920, "CQE", 1, 3),
    (1500,  "MWr", 0xFE60_100C, 1, 3),       # CQ1 head = 3
    (2000,  "MWr", 0xFE60_1008, 1, 3),       # stale: same tail again
    (2500,  "MWr", 0xFE60_1008, 1, 1024),    # wrap bug: should be 0
    (3000,  "MWr", 0xFE60_100C, 1, 5),       # head past tail
    (3500,  "MWr", 0xFE60_1018, 1, 1),       # SQ3 tail: queue 3 not created
    (4000,  "MWr", 0xFE60_1008, 2, 4),       # 64-bit write to SQ1TDBL
    (4500,  "MWr", 0xFE60_1006, 1, 1),       # misaligned
]

    lint(TRACE)

Challenge

Extend the linter to support shadow doorbells: add a shadow buffer and an EventIdx buffer per doorbell, and flag any MMIO doorbell write that was not needed (the controller did not ask for it) and any update that crossed EventIdx without an MMIO write (a missed notification).

Hints

For Q3: index = (0x1008 − 0x1000) / 8 = 1 → odd → CQ head of queue 0. For the challenge, reuse need_event() from the shadow doorbell pseudocode.

Solution

Q1. t = 2500 (value 1024 ≥ size): Invalid Doorbell Write Value. t = 3000 (CQ head passes posted CQEs): Invalid Doorbell Write Value. t = 3500 (queue 3 does not exist): Write to Invalid Doorbell Register. The 2-DW write at t = 4000 writes SQ1TDBL = 4 (legal) and CQ1HDBL = the second Dword (whatever it holds; with data 0 that moves CQ head backwards — likely invalid). The misaligned write at t = 4500 is not a doorbell register at all; controller behaviour is implementation-dependent (likely an invalid doorbell register event or ignored).

Q2. Doorbells carry an absolute index; writing the same tail adds zero entries. It is harmless to the controller, but a redundant doorbell in a trace often reveals a host logic error (the host thought it added commands but its tail variable didn't move — a stale tail).

Q3. With stride 8, 0x1008 is CQ0HDBL — the Admin CQ head doorbell, not SQ1's tail. A driver that assumes stride 4 on such a controller rings the wrong doorbell.

Q4. A Length = 2 write covers 0x1008–0x100F: the second Dword lands on CQ1HDBL and moves the CQ head to an arbitrary value — corrupting the controller's free-slot accounting.

Step 3 sketch. Keep pending[qid] = set of slots published but not fetched; on a doorbell, add slots old_tail … new_tail − 1 (mod size); on FETCH remove them; before processing the next doorbell (or at the end) report any remaining slots as "published but never fetched".

What a senior engineer notices

The linter needs the queue sizes. In real investigations you get them from the Create I/O queue SQE payloads earlier in the same capture — which is why seniors start captures before driver load when they can, or decode the create commands from a separate capture of the same build.

Failure variants

  • Doorbell writes with First BE = 0011b (a 16-bit store): the upper half is not written; the controller's interpretation is implementation-dependent.
  • Doorbell writes during reset (between CC.EN = 0 and RDY = 1): ignored; commands lost.
  • A hypervisor coalescing or reordering trapped doorbell writes across queues: per-queue order still holds, cross-queue order does not.

Extension

Generate a 10,000-event random trace with occasional injected bugs (probability 0.1%) and measure how many the linter finds, then add the fetch check and measure again. This is the seed of an automated analyzer (Automated Trace Analysis).

Exercises

  1. CAP.DSTRD = 2. Give CQ5HDBL's offset.
    Answer

    Stride = 4 << 2 = 16. CQ5HDBL = 1000h + (2 × 5 + 1) × 16 = 1000h + 176 = 1000h + B0h = 10B0h.

  2. An SQ of 64 entries had tail 60; the host adds 7 commands. What value does it write, and which slots does the controller fetch?
    Answer

    (60 + 7) mod 64 = 3. Slots 60, 61, 62, 63, 0, 1, 2 — likely as two fetches (60–63 and 0–2) because they are not contiguous in memory.

  3. Why can't the controller fetch slots 60–2 in one Memory Read in Exercise 2?
    Answer

    Slot 63 is at the end of the queue memory and slot 0 at its start; they are not adjacent addresses, and a Memory Read covers one contiguous address range.

  4. Explain the difference between a missing CQ head doorbell and a missing SQ tail doorbell as seen in a trace.
    Answer

    Missing SQ tail doorbell: commands are never fetched — no MRd for those slots. Missing CQ head doorbell: commands are fetched and completed until the CQ is full; then CQE posts stop while fetched work is held inside the controller.

  5. With shadow doorbells, a trace shows 50 SQ tail MMIO writes for 10,000 commands. Is that a bug?
    Answer

    Not necessarily: with Doorbell Buffer Config, the host only performs MMIO writes when an update crosses EventIdx. A low count is expected while the controller is actively polling the shadow buffer.

Quiz

  1. What does the value written to an SQ tail doorbell represent?

    • The number of new commands
    • The new absolute tail index
    • The Command Identifier
    • The SQ head
    Answer and reasoning

    It is the index of the next free slot — the new tail. New commands = (new − old) mod size.

  2. With CAP.DSTRD = 0, where is the SQ2 tail doorbell?

    • 1008h
    • 100Ch
    • 1010h
    • 1014h
    Answer and reasoning

    1000h + 2 × 2 × 4 = 1010h. 1014h is CQ2's head doorbell.

  3. What PCIe transaction type is a doorbell write?

    • Posted Memory Write
    • Non-posted Memory Write
    • Configuration Write
    • Message
    Answer and reasoning

    An MMIO store becomes a Memory Write TLP, which is posted: no completion.

  4. What happens if the doorbell write reaches the device before the SQE is visible in memory?

    • The controller waits for the SQE
    • The doorbell is rejected
    • The controller may fetch and execute stale contents
    • PCIe reorders them back
    Answer and reasoning

    The controller trusts the doorbell; it fetches whatever is in memory at that moment.

  5. Which doorbell does not exist?

    • SQ0 tail
    • CQ0 head
    • SQ1 tail
    • CQ1 tail
    Answer and reasoning

    CQ tail is owned by the controller; there is no CQ tail doorbell.

  6. The host writes 32 to the tail doorbell of a 32-entry SQ. The controller:

    • Wraps it to 0 and continues
    • Treats it as an invalid doorbell write value and may report an asynchronous error event
    • Fetches 32 commands
    • Returns a PCIe Completer Abort
    Answer and reasoning

    Valid indices are 0–31. Posted writes get no PCIe completion, so the only report path is the NVMe asynchronous event.

  7. Which Admin command enables shadow doorbells, and since which revision?

    • Doorbell Buffer Config (7Ch), NVMe 1.3, optional
    • Set Features FID 07h, NVMe 1.0
    • Create I/O SQ, NVMe 1.0
    • Virtualization Management, NVMe 2.4
    Answer and reasoning

    Doorbell Buffer Config, opcode 7Ch, introduced in NVMe 1.3 and optional.

  8. Why does NVMe avoid register reads on the I/O path?

    Model answer

    MMIO reads are non-posted: the CPU stalls until the device returns a completion across the link, typically on the order of a microsecond. Doorbells are writes (posted, cheap), and the device reports its state through host memory (SQHD, phase tag), which the CPU reads from cache.

  9. Describe the correlation rule between SQ doorbells and fetches, and one situation where it appears violated without a bug.

    Model answer

    Each doorbell that advances the tail from T0 to T1 should be followed by fetches covering slots T0 … T1 − 1. It can appear violated when the capture started mid-stream (earlier doorbells missing), when the controller fetches a previously published range together with new slots, when shadow doorbells are in use, or when SQs live in a Controller Memory Buffer (no host fetch needed).

  10. What is the difference between an Invalid Doorbell Write Value event and a Write to Invalid Doorbell Register event?

    Model answer

    The first is a bad value written to a real doorbell of an existing queue (out of range, overfilling, passing the CQ tail). The second is a write to a doorbell register that is not valid at all (for example for a queue that does not exist).

Interview questions

  1. Beginner: What is an NVMe doorbell?
    Model answer

    A 32-bit controller register the host writes to publish a new SQ tail (new commands) or CQ head (consumed completions). Located at BAR0 + 1000h onward, spaced by the doorbell stride.

  2. Beginner: Does the doorbell contain the command?
    Model answer

    No — only the new index. The controller fetches the command from host memory by DMA.

  3. Intermediate: Walk me through the nine steps of a command and say which are visible on the PCIe link.
    Model answer

    Build SQE (no), write into SQ (no), update tail (no), ring doorbell (yes, MWr), controller notices (no), fetch (yes, MRd + CplD), execute (data MWr/MRd yes), post CQE (yes, MWr), interrupt (yes, MSI-X MWr). Then host reaps (no) and rings CQ head doorbell (yes, MWr).

  4. Intermediate: Why is a write barrier needed before the doorbell?
    Model answer

    The SQE store (cacheable memory) and doorbell store (uncached MMIO) may be reordered on weakly ordered CPUs; the controller could fetch before the SQE is visible and execute stale contents. writel() provides the ordering.

  5. Advanced: What are shadow doorbells and when would you use them?
    Model answer

    An optional mechanism (Doorbell Buffer Config, NVMe 1.3) where the host writes doorbell values to a memory buffer and only performs MMIO writes when the controller's EventIdx asks for one. It avoids VM exits for emulated controllers in virtual machines.

  6. Advanced: How does a controller report a bad doorbell write, given that posted writes have no completion?
    Model answer

    Through the NVMe Asynchronous Event mechanism: an outstanding Asynchronous Event Request completes with an Error status event (Invalid Doorbell Write Value or Write to Invalid Doorbell Register), pointing to the Error Information log. Without an outstanding AER it cannot report it immediately.

  7. Senior: I/O on an Arm server occasionally completes the wrong command; x86 never does. What do you suspect and how do you prove it?
    Model answer

    Missing ordering between SQE stores and the doorbell (relaxed MMIO write, or barrier misplaced), visible only on a weakly ordered CPU with a fast controller. Prove it with an analyzer: compare the SQE payload in the root complex's CplD with the driver's log for that slot; a stale payload proves it. Confirm by fixing the barrier and re-running.

  8. Senior: Design the doorbell portion of a controller validation plan.
    Model answer

    Address decode across DSTRD values; every invalid value class (≥ size, overfill, CQ head past tail, nonexistent queue, reserved bits, partial and wide writes) with and without AERs outstanding; wrap at all sizes; redundant writes; batching of up to size − 1 commands; doorbells during reset/disable; doorbell-to-fetch latency distributions under load per arbitration mode; shadow doorbell semantics including EventIdx crossing and wrap if supported.

Model explanation for the child

"The shop has a tray of order cards and a bell. You write your order card, put it in the tray, and only then ring the bell and show a number that says where the next empty spot is. The shopkeeper looks at the number and picks up every card up to that spot. If you ring before your card is in the tray, she'll pick up an old card by mistake! When you've read your answer cards, you ring another bell with a number, so she knows she can reuse those answer spots."

Chapter summary

Doorbells are 32-bit registers at BAR0 + 1000h onward, spaced by 4 << CAP.DSTRD: SQ y tail at 1000h + 2y × stride, CQ y head at 1000h + (2y + 1) × stride. The host writes absolute indices (bits 15:00) — new SQ tail after writing SQEs (with a write barrier first), new CQ head after consuming CQEs. On PCIe each doorbell is a posted Memory Write with 1 DW of payload and no completion. A command's life is: build, write SQE, update tail, ring, controller notices, fetch, execute, post CQE, interrupt; then the host reaps and rings the CQ head doorbell. Doorbell Buffer Config (7Ch, optional, NVMe 1.3+) adds shadow doorbells for emulated controllers. Doorbell bugs — stale tails, wrap errors, missing barriers, wrong stride, wide writes, invalid CQ heads, nonexistent queues — are diagnosed by correlating doorbells with fetches and CQE posts, and by reading the asynchronous error events the controller reports.

  • compute any doorbell address for any DSTRD
  • narrate the nine steps with actor, state change and evidence for each
  • decode a doorbell TLP and state why it has no completion
  • explain the barrier and recognise its absence in a trace
  • apply the doorbell-to-fetch correlation rule to a trace
  • name the doorbell bug from its trace signature and the asynchronous event it causes
  • explain shadow doorbells, their purpose, version and optional status
