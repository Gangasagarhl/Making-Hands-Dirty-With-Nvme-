A specification is not a book you read once from front to back. It is a contract you learn to navigate, interrogate and cite. This part teaches the reading skills that turn a 700-page NVM Express (NVMe) document or the PCI Express (PCIe) Base Specification from a wall of tables into a tool you can use under pressure, and it gives you a notebook system and a reusable worksheet to keep what you learn.

Why a specification reading school exists

Every senior storage engineer has a moment where a colleague says "the drive is violating the spec", and the senior quietly asks: which sentence? Very often the answer is that nobody has read the sentence. They have read a blog post, a driver comment, or a remembered conversation. The defect report then argues with a ghost.

Reading a specification is a separate skill from understanding the technology. You can understand queues perfectly and still misread a table because you did not notice the value is "0's based", or that a field is "Reserved" in your revision but defined in the next one, or that a sentence uses should rather than shall. These mistakes are not about intelligence. They come from reading in the wrong way.

This page is the method. The companion page Reading Commands, Registers and State Machines applies the method to specific structures, and Reading Plan tells you which documents to read in what order. Read this page first.

Learning objectives

  • Describe how the NVMe specification family and the PCIe Base Specification are organized, and find any topic in under two minutes using the table of contents, figure list and search.
  • Classify any sentence as normative, informative, optional, implementation-specific or version-dependent, and explain the consequence of each for a conformance argument.
  • Read bit-field tables, byte-offset tables, 0's based values and register attribute legends without arithmetic or ordering mistakes.
  • Read a state diagram and convert it into a transition table with triggers, guards and observable evidence.
  • Read a command format and its status table and connect them to the Completion Queue Entry (CQE) a trace would show.
  • Track revision changes, Technical Proposals (TPs) and Engineering Change Notices (ECNs), and state which revision a claim depends on.
  • Maintain a specification notebook with six artifacts: notebook, field dictionary, command matrix, state-machine notes, trace mapping and cross-reference map.
  • Use the reusable specification-reading worksheet on any unfamiliar section.

Prerequisites

You should have met the objects you will be reading about: registers (NVMe Registers), queues (Queue Architecture), command structure (NVMe Command Structure), TLP headers (TLP Header Anatomy), and the link state machine (PCIe LTSSM). You do not need to remember details; this page shows you how to find them.

The story

Imagine the rules for a giant board game, written by a committee of a hundred people so that every family in the world plays exactly the same way. Some rules say "you must roll before you move". Some say "you should keep the cards in a neat pile". Some say "you may trade cards on your turn". Some boxes on the board are painted grey and say "for a future version of this game — leave empty". When a fight breaks out at the table, the winner is not the loudest child. It is the child who opens the rule book, puts a finger on the exact line, and reads it out loud.

A specification is like a building code combined with an engineering drawing set. The code tells you what is required (handrails shall be 34 to 38 inches high), what is recommended, and what is left to the architect. The drawings give exact dimensions in a notation you must learn to read. An inspector does not ask whether the building "feels right": they cite clause and drawing. You read a protocol specification as an inspector reads a code — looking for the obligation, its scope, and its exceptions.

The analogy hides three things. First, a building code rarely changes the meaning of a dimension between editions; specifications do redefine reserved fields as features arrive. Second, a building is inspected once; a protocol is exercised billions of times per second, so rare corner cases in a sentence become real bugs. Third, a building code is written for one jurisdiction; NVMe is a family of documents that refer to each other, and PCIe is a separate standard from a separate organization, joined to NVMe by a third document, the NVMe over PCIe Transport Specification. An inspector with only one book would miss most of the rules.

How a specification is built

Before you read any sentence, learn the shape of the whole document. A specification has a predictable skeleton, and knowing it is what lets experienced engineers find answers quickly.

The NVMe document family

Since the 2.0 restructuring, NVMe is not one document. It is a family. The NVM Express Base Specification defines the architecture, the common command format, the Admin command set, queues, namespaces, logs, features and the controller properties every transport shares. Command set specifications define the I/O commands for one kind of namespace. Transport specifications map the abstract architecture onto a physical or network transport. The management interface and boot specifications sit beside them.

The practical consequence: a question like "what does the controller do when the host rings a doorbell with an invalid value?" may touch three documents. The concept of a Submission Queue (SQ) tail lives in the Base Specification; the doorbell register as a memory-mapped location lives in the PCIe Transport Specification; and the Memory Write Transaction Layer Packet (TLP) that carries it is defined by the PCIe Base Specification. Reading one and assuming the rest is the most common early mistake.

The PCIe Base Specification

The PCI Express Base Specification is a PCI-SIG members' document. It is organized by layer and by system concern. Its major chapters, by name, are: Introduction; Transaction Layer Specification; Data Link Layer Specification; Physical Layer Logical Block; the electrical sub-block chapter; Power Management; System Architecture (where error signaling and logging, reset and many system rules live); Software Initialization and Configuration (configuration space and capability structures); and chapters on Single Root I/O Virtualization and Address Translation Services. Chapter order and naming can shift between revisions, so refer to chapter names rather than numbers.

The PCIe Base Specification is published as revision families (for example 5.0, 6.x, 7.0). Each adds signaling rates and features and may move material. When you cite PCIe, write "PCI Express Base Specification, Revision 6.x, Transaction Layer Specification — Completion Rules" rather than a numbered section, and note which revision you actually read.

Terminology and abbreviations

Specifications define ordinary-looking words with precise meanings. In NVMe, "controller", "NVM subsystem", "namespace", "host", "port", "property" and "command set" are all defined terms. A sentence that says "the controller shall…" is not about the silicon chip in general: it is about the defined logical entity that one host interface presents. Mixing the everyday and the defined meaning creates false contradictions.

How to handle definitions

  1. Find the definitions clause. In NVMe documents it sits in the introductory material together with the conventions; in PCIe it is the terms and acronyms list near the start.
  2. Copy defined terms into your field dictionary (described below) with the exact wording and the revision.
  3. Watch for definitions that moved. When NVMe split into a family, some terms became defined in the Base Specification and referenced from command sets. A command set may refine a Base term ("an NVM namespace" versus "a namespace").
  4. Distinguish the same word in two standards. "Function" in PCIe is a configuration-space-addressable entity; "function" in ordinary English is not. "Port" in PCIe is a link endpoint on a component; "port" in NVMe is an NVM subsystem port, a different concept. "Reset" is defined differently in each layer (see NVMe Reset and PCIe Reset).

Normative language: shall, should, may

The single most important reading skill is classifying the force of a sentence — whether it is normative or informative. Standards bodies use a small set of keywords, defined in the conventions clause of each document, to separate requirements from recommendations from permissions. The words below are used in this sense across NVMe documents; PCIe defines its own equivalent set in its terminology material. Always confirm the definitions in the document you are reading.

Requirement keywords and what they mean for an engineer

The scope of a requirement

A normative sentence has four parts. Train yourself to extract all four every time:

  1. Actor — who is obliged? The host, the controller, the NVM subsystem, a requester, a completer, a port.
  2. Condition — when does it apply? "If the controller supports…", "while CC.EN is set to '1'", "for a Non-Posted Request".
  3. Obligation — what must happen or not happen.
  4. Observable — what evidence would show compliance or violation (a register value, a status code, a TLP, a timing).

Not every obligation has an observable you can capture. Some describe internal behaviour; you can only infer them. Write "not directly observable" in your notes when that is true; it prevents you later from claiming a trace "proves" something it cannot show.

Informative text

Notes, examples, "theory of operation" narrative and diagrams labelled informative explain intent. They are invaluable for understanding but they do not create requirements. When informative text and a normative table disagree — and occasionally they do — the normative text governs, and the disagreement is a candidate for an erratum. Mark both in your notebook.

"Must" rules decide who wins an argument at the game table. "Should" rules are good manners. "May" rules are choices.

A normative statement is a requirement on a named actor under a named condition. Recommendations and permissions are different kinds of statement, and the keyword tells you which.

Hardware is designed against shall statements; firmware teams often keep a traceability matrix from each shall to a design element and a test. May statements become configuration choices or capability bits.

The conventions clause defines the keywords. Requirement tables use mandatory/optional columns. Capability fields (for example in Identify data or the CAP register) advertise which optional behaviours a controller implements, which in turn activates conditional shall statements.

On the wire, a shall often appears as a required response: a specific completion status, a field value, an ordering. A may appears as two valid alternatives your decoder must accept.

In a trace, you can confirm or refute observable shall statements: "the controller shall post a completion…" either has a matching CQE write or it does not, within your capture window.

When debugging, a deviation from a shall is a defect candidate; a deviation from a should is a risk; a choice between may options is a host-robustness question. Classify before you escalate.

Reserved, obsolete, vendor specific and implementation specific

A large fraction of every field table is marked "Reserved". Beginners skip these cells. Professionals read the rule for them, because reserved space is where future features appear and where interoperability bugs hide.

Reserved

Reserved means "set aside for future definition by this standard". The conventions clause tells you what the writer and reader of a reserved field are expected to do. The usual pattern is that the writer clears reserved fields to zero and the reader does not depend on their value; but the exact wording differs between documents and determines, for example, whether a controller is permitted to reject a command that has a non-zero reserved field. Read the wording in your document and copy it into your notebook.

"Reserved" is revision-relative. A field that is reserved in NVMe Base 2.0 may be defined in 2.4. A decoder that prints "reserved, ignore" for every bit it does not know will silently hide new features — or, worse, a host that writes garbage into reserved bits may suddenly enable a feature on a newer device. Always record the revision next to the word "Reserved".

PCIe register attributes

The PCIe Base Specification labels every register bit with an attribute that tells software how to treat it. Learn this legend once: it changes how you read every configuration-space table.

NVMe controller registers (properties) also carry attribute descriptions — read-only, read/write, and write-to-clear or write-to-set styles. Their notation is defined in the NVMe documents themselves; do not assume it is identical to the PCIe legend.

Obsolete

An obsolete field was defined in an earlier revision and has been removed. It is not the same as reserved: old devices may still implement the old meaning. A decoder should show "obsolete (was X in revision N)" rather than "reserved".

Vendor specific and implementation specific

Vendor-specific ranges (opcodes, log pages, status codes, register space) are fenced areas where implementers may define their own meaning. Implementation-specific (or implementation-dependent) behaviour is different: it is behaviour the specification deliberately leaves to the implementer — timing, internal buffering, the order in which a controller fetches commands from multiple queues within the arbitration rules, how long a firmware activation takes. Your notes should label these clearly because they are where two compliant devices behave differently.

Examples you will meet constantly: how many SQEs a controller fetches per Memory Read, whether it coalesces completions, interrupt coalescing behaviour within the configured limits, internal command execution order. Never infer "the spec requires" from one device's behaviour.

Reading tables and bit fields

Most normative content is in tables. Reading them correctly is a matter of notation discipline.

Number notation

Queue sizes, the Number of Logical Blocks (NLB) in Read and Write commands, and several other count fields are 0's based. A Read with NLB = 7 transfers eight logical blocks: 4096 bytes with 512-byte blocks. A decoder or a test script that forgets this is off by one block on every command. When a field is 0's based, your field dictionary must say so in bold.

Byte and bit ordering

NVMe data structures are little-endian: the least significant byte of a multi-byte field is at the lowest address. Tables list fields by byte range ("Bytes 03:00") and then by bit range within a Dword. PCIe TLP headers, in contrast, are drawn big-endian in the PCIe Base Specification figures — byte 0 of the header is drawn at the left and transmitted first — while the payload carries memory bytes in address order. When you correlate an SQE seen in a TLP payload with the SQE layout table, you must convert between the two drawing conventions. TLP Header Anatomy and Command-to-TLP Correlation show this conversion in detail.

Here is Command Dword 0 (CDW0), common to every NVMe command, drawn as a bit table. Every row of every SQE table can be redrawn this way, and redrawing is the fastest way to notice overlapping or missing bits.

CDW0Command Identifier (CID) 31:16PSDT 15:14Reserved 13:10FUSE 9:8Opcode (OPC) 7:0

Fields: Opcode (OPC), Fused Operation (FUSE), PRP or SGL for Data Transfer (PSDT), Command Identifier (CID). The CID is chosen by the host and is unique per Submission Queue among outstanding commands; it comes back in the CQE so the host can match the completion.

Reading table footnotes and columns

  • Read every footnote. Requirements ("this field is only valid if…") often live there.
  • Read column headers literally. Requirement tables often have separate columns for different controller types (for example I/O controllers, administrative controllers, discovery controllers) or for different command sets.
  • Notice "see" references. A table may define a field as "see the X section" — follow the link and copy the rule into your dictionary entry, not just the pointer.
  • Notice conditional validity. A field "valid only if bit Y is set to '1'" contains garbage-by-specification otherwise. Decoders must suppress it.

Reading state diagrams

State machines are where timing bugs live. A state diagram is compact, which makes it easy to read too quickly. Convert every diagram you care about into a transition table with five columns: current state, trigger, guard (condition), next state, and observable evidence.

Example: controller enable and ready

The controller initialization handshake uses CC.EN (written by the host) and CSTS.RDY (reported by the controller). The Base Specification describes the sequence in its controller initialization material, and CAP.TO gives the worst-case time the host should wait for CSTS.RDY to change.

The value of the table is the last column. A state diagram tells you what should happen; the evidence column tells you how you would know it happened. Where the evidence column says "internal — not observable", you have found a place where a trace can only support inference.

Reading the LTSSM diagram

The PCIe Link Training and Status State Machine (LTSSM) diagram in the Physical Layer Logical Block chapter is famous for overwhelming readers. Read it in passes: first the main path (Detect → Polling → Configuration → L0), then the recovery loop (L0 → Recovery → L0), then the power states, then the exceptional exits (timeouts back to Detect). For each substate, note the exit conditions and their timeouts in your state-machine notes. PCIe LTSSM walks through the states; here the point is the reading technique.

Seniors read state machines backwards: start from the failure state you observed (for example, Detect after a link drop) and list every transition that leads into it. That list is your hypothesis set.

Reading command formats

Every NVMe command is a 64-byte Submission Queue Entry. The Base Specification defines the common layout; each command then defines its own use of the command-specific Dwords and its own status codes. Read a command definition in this fixed order:

  1. Command summary — which command set, Admin or I/O, opcode, whether it transfers data and in which direction, whether it uses a namespace identifier.
  2. Common fields used — CDW0, Namespace Identifier (NSID, Dword 1), Metadata Pointer (MPTR, Dwords 4–5), Data Pointer (DPTR, Dwords 6–9). Note which are reserved for this command.
  3. Command-specific Dwords — CDW10 to CDW15, each as a bit table. Mark 0's based fields.
  4. Data structure — if the command transfers a structure (Identify, Get Log Page), the structure's own table.
  5. Command completion — what the CQE Dword 0 (command specific) carries on success.
  6. Command-specific status values — the errors this command can return in addition to generic ones.
  7. Requirements and interactions — mandatory/optional, effects on other commands, behaviour during reset or with other features.

The CQE is 16 bytes: Dword 0 command specific, Dword 1 reserved or command specific, Dword 2 SQ Head Pointer and SQ Identifier, Dword 3 the CID, the Phase Tag (bit 16) and the Status Field (bits 31:17). NVMe Command Structure covers the details.

When you read a new command, immediately write down: "what would this look like on the wire?" — which Memory Reads fetch the SQE, which data TLPs move in which direction, which Memory Write posts the CQE. That habit links reading to tracing from day one.

Reading error tables

Errors in NVMe are reported in the Status Field of the CQE. The field is structured: a Status Code Type (SCT) selects a table, and the Status Code (SC) selects an entry in that table. Additional bits signal "More" information in the Error Information log, "Do Not Retry" (DNR), and a Command Retry Delay (CRD) selector.

Status Code Types (NVMe Base Specification — Status Field definition)
SCTTableReading note
0hGeneric Command StatusApplies to any command. Read this table completely once.
1hCommand Specific StatusThe same SC value means different things for different commands. Never decode without the opcode.

3hPath Related StatusMultipath and transport path conditions.
7hVendor SpecificMeaning defined by the vendor only.

A status of SCT=1h with a given SC value has no meaning on its own. It is a lookup into the status table of that command. A decoder that prints a name for SCT=1h without knowing the opcode is wrong for most commands. In your command matrix, every command row lists its command-specific status names.

Errors are layered

An NVMe status code and a PCIe error are reported by different mechanisms in different documents. A PCIe Unsupported Request (UR) completion is a Transaction Layer event defined in the PCIe Base Specification; Advanced Error Reporting (AER) logs it in configuration space. An NVMe Data Transfer Error is an NVMe status in a CQE. One may cause the other, but you will not find them in the same table. The error-correlation chapters (Error Correlation) build on this distinction.

When you read an error table, add three columns to your notes: who reports it, where it is visible (CQE, log page, AER register, kernel log) and which layer's condition triggers it.

References and cross-references

Specifications refer to themselves and to other standards constantly. There are two kinds of reference:

  • Normative references — other documents whose content is incorporated as requirements. The NVMe over PCIe Transport Specification depends normatively on the PCIe Base Specification; the NVMe Base Specification references cryptographic and other standards for security features.
  • Informative references — documents listed for background.

Inside a document, a sentence such as "as described in the Controller Initialization section" is a cross-reference. The fastest way to understand a topic is to follow every cross-reference out of one section and build a small graph: this is the cross-reference map described below.

A specification rarely restates rules it imports. The NVMe documents do not re-explain PCIe completion timeout rules, ordering rules or AER; they rely on the PCIe Base Specification. When you cannot find a rule in an NVMe document, the next question is "which referenced document owns it?", not "the spec does not say".

Revision changes

A specification is a moving target. Being explicit about revision is part of being correct.

How NVMe changes

NVM Express work groups develop changes as Technical Proposals (TPs), and corrections as Engineering Change Notices (ECNs) or errata. Ratified TPs are published and later integrated into the next revision of the affected documents. NVM Express also publishes a Revision Changes document that lists what changed between revisions; for the 2026 release this is the document titled "NVM Express Revision Changes" dated 2026-07-30, linked from the nvmexpress.org Revision Changes page. The NVMe Base Specification revision 2.4 was ratified on 2026-07-31 and published with the rest of the family on 2026-08-04.

The August 2026 release revised all eleven NVMe documents together. Features reported for 2.4 include post-quantum cryptography preparation, PCIe Exported NVM Subsystem Migration, rate limiting, voltage monitoring, idle I/O exit latency limits, lockdown improvements and restore manufacturing default settings. Field-level details (opcodes, log identifiers, offsets) for these must be taken from the documents themselves; see 2026 NVMe 2.4 Updates.

How PCIe changes

PCI-SIG publishes Base Specification revisions, Engineering Change Notices against them, and errata. A device certified against one revision may legitimately lack features of a later one. Always note the revision both your device and your analyzer decoder target.

Reading a revision change list

  1. Read the summary of changes once fully.
  2. For each change, ask: does it affect a structure I decode, a state machine I trace, or a requirement I test?
  3. Mark affected entries in your field dictionary and command matrix with the new revision.
  4. Check the "incompatible changes" or similar list if the document has one: these break older assumptions.
  5. Update your decoder's reserved-field handling.

Every claim in your notes carries a revision tag. "CSTS.RDY clears when EN is cleared [Base 2.4]" is a claim. "CSTS.RDY clears when EN is cleared" is a rumour.

Worked example: reading Create I/O Completion Queue

Question: "Our driver creates CQ1 with 1024 entries and interrupt vector 1. The controller returns an error. Which fields could be wrong, and what would the text let us claim?" We walk the worksheet.

A–B. Identify and check conventions

Document: NVM Express Base Specification 2.4, Admin Command Set — Create I/O Completion Queue command. Conventions: hexadecimal with h; queue size is 0's based; reserved fields per the conventions clause.

D–E. Statements and fields

Create I/O Completion Queue fields as read (verify bit positions in your copy)

CDW0Opcode7:005h05h
DPTR (PRP1)Queue base address—Physically contiguous queue uses PRP1 as base0x1_2341_0000 (IOVA)

G. Errors

The command's own status table lists command-specific errors including an invalid queue identifier, an invalid queue size and an invalid interrupt vector (names as given in the specification; read their SC values from the table rather than from memory). Generic errors such as Invalid Field in Command also apply.

H. Cross-references followed

  • CAP.MQES (Maximum Queue Entries Supported, 0's based) — the queue size limit lives in the Controller Capabilities register, not in the command.
  • CAP.CQR (Contiguous Queues Required) — whether PC=0 is allowed at all.
  • Number of Queues feature — how many I/O queues the controller allocated, which bounds QID.
  • MSI-X capability (PCIe Base, via the PCIe Transport) — the number of vectors, which bounds IV.

I. What the section does not say

It does not say which error a controller reports first when two fields are invalid. It does not say how quickly the command completes. It does not define the MSI-X table: that is PCIe.

K–L. Answer

Candidates: QSIZE exceeding CAP.MQES; QID beyond the allocated number of queues or already in use; IV beyond the vectors the controller supports; PC=0 when CAP.CQR requires contiguous queues; a PRP1 not aligned as required. The status code identifies which (verified by text, given the command's status table). The order of checking for multiple bad fields is implementation-dependent. Next action: read CAP, the Number of Queues feature result and the MSI-X Table Size from configuration space, and compare.

The conclusion "QSIZE=1023 is legal if CAP.MQES ≥ 1023" is derived: it combines the 0's based definitions of both fields. Write the derivation in your notebook.

Lab: build a field dictionary for the Completion Queue Entry

Objective

Produce a complete, cited field dictionary for the 16-byte NVMe Completion Queue Entry and a trace mapping for the CQE write, then use it to decode three synthetic CQEs.

Skills

Conventions checking, bit-table reading, status table lookup, trace mapping.

Safety

Safe lab Reading and paper work only. No device access.

Hardware required

None.

Software required

The NVM Express Base Specification 2.4 (free download from nvmexpress.org), a text editor or spreadsheet, Python 3 for the optional checker.

Input

Three synthetic CQEs captured as 16 bytes each, shown as four little-endian Dwords (Synthetic example for teaching):

#DirTime (ns)TypeFieldsMeaning
1Dev→Host49500MWr64Addr=0x1_2341_0000 Len=4 DW0=00000000 DW1=00000000 DW2=00010003 DW3=00010040CQE slot 0
2Dev→Host53000MWr64Addr=0x1_2341_0010 Len=4 DW0=00000000 DW1=00000000 DW2=00010003 DW3=80090041CQE slot 1
3Dev→Host61000MWr64Addr=0x1_2341_0020 Len=4 DW0=00000000 DW1=00000000 DW2=00010004 DW3=00000042CQE slot 2

Dword values are shown as 32-bit numbers after little-endian assembly from the payload bytes.

Expected output

A field dictionary with at least the fields DW0, DW1, SQ Head Pointer (SQHD), SQ Identifier (SQID), CID, Phase Tag (P), Status Code (SC), Status Code Type (SCT), CRD, More (M), DNR — each with bits, owner, encoding, revision and citation by section name. A decode of the three CQEs.

Background

The CQE is written by the controller into host memory with a posted Memory Write. The host detects new entries by the Phase Tag toggling, not by an interrupt alone. See Queue Architecture.

Step 1 — Conventions

Fill worksheet boxes A–C for the Completion Queue Entry section of the Base Specification. Write down the rule for reserved fields and the bit numbering convention.

Step 2 — Field dictionary

Fill one row per field. For the Status Field, follow the cross-reference to the Status Field definition and record the sub-fields.

Step 3 — Decode

Decode each CQE. Use this small checker to confirm your bit arithmetic (it encodes the layout you should have found; if your dictionary disagrees, re-read the text — the text wins).

def decode_cqe(dw2, dw3):
    """Decode CQE Dwords 2 and 3 (NVMe Base Specification: Completion Queue Entry)."""
    sf = dw3 >> 17                     # Status Field, bits 31:17 of DW3
    return {
        "sqhd": dw2 & 0xFFFF,          # SQ Head Pointer, DW2 15:0
        "sqid": dw2 >> 16,             # SQ Identifier, DW2 31:16
        "cid":  dw3 & 0xFFFF,          # Command Identifier, DW3 15:0
        "p":    (dw3 >> 16) & 1,       # Phase Tag, DW3 bit 16
        "sc":   sf & 0xFF,             # Status Code
        "sct":  (sf >> 8) & 0x7,       # Status Code Type
        "crd":  (sf >> 11) & 0x3,      # Command Retry Delay
        "m":    (sf >> 13) & 1,        # More
        "dnr":  (sf >> 14) & 1,        # Do Not Retry
    }

for dw2, dw3 in [(0x00010003, 0x00010040), (0x00010003, 0x80090041), (0x00010004, 0x00000042)]:
    print(hex(dw3), decode_cqe(dw2, dw3))

Observation

Record, for each CQE: which command it completes, whether it succeeded, and whether the host would consider it new.

Questions

  1. Which CQE reports an error, and which table do you look in to name it?
  2. CQE 3 has P=0 while CQEs 1 and 2 have P=1. What does that mean if this is the first pass through CQ1?
  3. What does DNR=1 tell the host driver to do?
  4. Which part of your answers is verified text, and which is derived?

Challenge

Extend your trace mapping to show the MSI-X Memory Write that would normally follow CQE 2 and the CQ head doorbell write that releases it. Give addresses from the course lab system.

Hint

Write the status field out in binary before splitting it. DW3 of CQE 2 is 0x80090041: the top 15 bits (31:17) form the status field.

Solution

CQE 1: SQID=1, SQHD=3, CID=0x0040, P=1, status 0 — success. CQE 2: SQID=1, SQHD=3, CID=0x0041, P=1; status field = 0x80090041 >> 17 = 0x4004, so SC=0x04, SCT=0, CRD=0, M=0, DNR=1. SCT=0 means the Generic Command Status table; SC 04h there is Data Transfer Error. DNR=1 tells the host that retrying the same command is not expected to succeed. CQE 3: SQID=1, SQHD=4, CID=0x0042, P=0. On the first pass through a CQ, the controller writes entries with P=1 (the host initialized the queue memory to zero), so an entry with P=0 at slot 2 is not new from the host's point of view: either it is stale memory or the controller wrote the wrong phase. The host would not consume it. That is an abnormal event worth investigating. Classification: the field layout and status table lookup are verified; the "stale versus wrong phase" interpretation is derived and needs more evidence (for example, a capture that shows whether this write actually happened).

Challenge: MSI-X write to 0xFEE0_xxxx with the data value programmed for vector 1, then a host MWr to the CQ1 head doorbell at BAR0+0x100C with the new head value (here 2 after consuming two entries).

What a senior engineer notices

That the error CQE carries SQHD=3, the same as the successful one: the controller had already consumed through slot 2 when it completed both. Completion order is not submission order, and SQHD is not a per-command field. Also that the third "CQE" might never have been a CQE at all — a senior asks whether the write appeared on the wire before naming a controller bug.

Failure variants

  • Decode SCT=1h with SC=02h for a Create I/O Completion Queue and for a Read: show that the names differ.
  • Forget the 17-bit shift and decode the phase tag as part of the status: observe the nonsense result.
  • Swap DW2 and DW3: observe how a CID becomes an SQ head pointer.

Quiz

  1. A sentence says "the controller should complete the command within X". The device takes longer. What is the correct classification?

    • Non-conformance: file a spec violation
    • A deviation from a recommendation: an interoperability or quality risk, not a conformance failure
    • Undefined behaviour
    • Vendor-specific behaviour
    Answer and reasoning

    Should is a recommendation. Deviating is permitted with reason; it is not non-conformance. You can still raise it as a quality issue.

  2. A Read command has NLB = 0. How many logical blocks does it transfer?

    • Zero
    • One
    • It is invalid
    • Depends on the namespace
    Answer and reasoning

    NLB is 0's based, so 0 means one block. The byte count depends on the LBA format, but the block count does not.

  3. Which PCIe register attribute means writing a 1 clears the bit?

    • RO
    • RsvdP
    • RW1C
    • HwInit
    Answer and reasoning

    RW1C: read, write 1 to clear. Status bits in AER registers and Device Status use it.

  4. A CQE has SCT = 1h. What else do you need to name the error?

    • The opcode (and command set) of the command it completes
    • The namespace identifier
    • The SQ head pointer
    • Nothing; SC is enough
    Answer and reasoning

    SCT 1h is Command Specific Status; each command defines its own SC values. Find the command via SQID + CID, then its opcode.

  5. Where do you find the rule for how to treat reserved fields in an NVMe document?

    • In each command's table
    • In the Linux driver
    • In the PCIe Base Specification
    • In the document's conventions clause
    Answer and reasoning

    Conventions define reserved handling globally for the document. Individual tables may add rules in footnotes.

  6. Why should you cite section names rather than section numbers?

    Model answer

    Numbers change between revisions as material is added or reorganized (NVMe's 2.0 family split moved much material), so a number is only meaningful with an exact revision; names survive reorganization better and let readers search. Always add the document and revision.

  7. What is the difference between "reserved" and "obsolete"?

    Model answer

    Reserved space is held for future definition and has no current meaning. Obsolete space had a defined meaning in an earlier revision that has been removed; older devices may still implement it, so a decoder should label it as obsolete-with-history rather than ignore it.

  8. An informative figure and a normative table disagree. Which governs, and what do you do?

    Model answer

    The normative table governs. Record the conflict in your notebook, check errata and later revisions, and if still unresolved, raise it through the appropriate channel (your company's member representative). Do not build on the figure.

  9. Name the four parts you extract from every normative statement.

    Model answer

    Actor, condition, obligation and observable. The observable tells you whether a trace can confirm or refute it.

  10. A colleague says "the NVMe spec doesn't define completion timeouts". Is that a complete answer?

    Model answer

    No. PCIe completion timeouts (for non-posted requests such as configuration and memory reads) are defined in the PCIe Base Specification, which the NVMe over PCIe Transport relies on. NVMe-level command timeouts are a host policy (implementation-dependent), informed by fields such as CAP.TO for enable/disable. The right answer names the owning document for each kind of timeout.

Interview questions

  1. Beginner: What does "0's based" mean, and name two fields that use it?
    Model answer

    The stored value is one less than the quantity. Queue size fields in Create I/O SQ/CQ and NLB in Read/Write are examples; CAP.MQES too.

  2. Beginner: What is the difference between normative and informative text?
    Model answer

    Normative text creates requirements; informative text explains. Only normative text supports a conformance claim.

  3. Intermediate: How do you determine which documents govern NVMe doorbell behaviour on PCIe?
    Model answer

    Base for queue semantics, PCIe Transport for the register location and stride, PCIe Base for the Memory Write transaction and ordering. I would build a cross-reference map and cite each.

  4. Intermediate: Your decoder prints "reserved" for a bit that a new device sets. What do you do?
    Model answer

    Check the device's claimed revision and the newer specification and revision-change list; the bit may now be defined. Update the decoder with revision-aware decoding and record it in the field dictionary.

  5. Advanced: A vendor claims behaviour X is "allowed by the spec". How do you check?
    Model answer

    Ask for the sentence; find it; check the keyword (may vs should), the condition and the actor; check whether another shall constrains it; check revision. Then decide whether the host must tolerate it.

  6. Senior: How would you organize a team's specification knowledge so that new engineers ramp quickly and decoders stay correct across revisions?
    Model answer

    A shared, versioned field dictionary and command matrix with revision tags and citations by section name, generated decoders from that dictionary, a trace mapping maintained alongside analyzer scripts, a review step for every new revision's change list, and a rule that every claim in a bug report cites document, revision and section name.

  7. Senior: Explain how a should can still be a release-blocking issue.
    Model answer

    Conformance is not the only criterion. If a major host relies on the recommended behaviour, deviation causes real failures. The bug is then an interoperability or customer issue, argued with evidence of impact, not a conformance violation.

Summary and mastery gate

Specifications are contracts written in a precise dialect. Read the conventions first; classify every sentence by keyword, actor, condition and observable; read tables with notation discipline; turn state diagrams into transition tables with evidence; decode errors with their owning table and layer; and tag everything with a revision. Keep six artifacts — notebook, field dictionary, command matrix, state-machine notes, trace mapping, cross-reference map — and use the worksheet whenever you read something new.

Do not move on until you can:

  • find the conventions clause of any NVMe document and state its reserved-field rule
  • classify a sentence as shall / should / may and extract actor, condition, obligation, observable
  • read a bit-range table and handle 0's based fields without error
  • convert a state diagram into a transition table with an evidence column
  • decode a CQE status field and name the error using the correct table
  • explain which document owns a rule that spans NVMe and PCIe
  • state the revision of every claim in your notes
  • fill the worksheet for an unfamiliar section in under thirty minutes
