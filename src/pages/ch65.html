NVMe over Fabrics (NVMe-oF) takes the NVMe command set you learned over PCIe and carries it across a network. This chapter builds the mental model that keeps the three transports straight. It covers what stays exactly the same (commands, completions, namespaces, status), what is replaced (doorbells, interrupts, register reads, PRPs and queue-creation commands), and why the unit of exchange becomes a capsule instead of a memory write.

Why this chapter exists

Up to this point, every command you have followed has lived in host memory. A driver wrote a 64-byte Submission Queue Entry (SQE) into a ring, rang a doorbell with a PCI Express (PCIe) Memory Write, and the controller reached back into host memory with Direct Memory Access (DMA) to fetch the command and move the data. That whole picture depends on one thing: the controller and the host share an address space over a PCIe link.

NVMe over Fabrics removes that assumption. The host and the NVM subsystem might sit in different racks, connected by Ethernet, InfiniBand or Fibre Channel. There is no shared memory and no Transaction Layer Packet (TLP) between them, and there is no doorbell register the host can write. Yet a Read is still opcode 02h, a completion still carries a Command Identifier and a status field, and a namespace is still a namespace.

Engineers who do not build a clean mental model here make two opposite mistakes. Some assume "it is just NVMe, nothing changes" and go looking for doorbell writes in a packet capture. Others assume "it is a totally different protocol" and miss that the familiar command and completion structures sit, byte for byte, inside every network message. This chapter gives you the dividing line.

The story

Imagine the school library is in the same building as your classroom. When the teacher wants a book, she puts a request slip in the request box by the door and rings a little bell. The librarian walks over, reads the slip, walks back, finds the book and places it directly on the teacher's table. Then she drops an answer slip in the answer box.

Now imagine the library moves across town. The librarian can no longer walk into the classroom, reach into the request box or put a book on the table. So the teacher does something new. She copies the request slip onto a card, puts the card in an envelope and mails it. If the teacher is sending a small thing, like a page of notes to be stored, she slips it into the same envelope. For a big box of books, the librarian mails back a note saying "send me the first part now", and the teacher mails it over. When the work is done, the librarian mails back an envelope with the answer slip inside.

The request slip is written exactly the same way in both cases. What changed is how it travels. Nobody rings a bell, because the arrival of the envelope is the bell.

Think of a restaurant kitchen with a pass, the counter where waiters clip order tickets onto a rail. In the in-house dining room (PCIe), the waiter clips a ticket to the rail and taps the bell, and the chef pulls tickets off the rail when ready. Plates go straight onto a shelf the waiter can reach.

Now the restaurant also takes delivery orders through a courier company (the fabric). The ticket is identical, with the same dish codes and table number field, but it now arrives inside a courier pouch. The kitchen cannot reach into the customer's house to drop the food, so the food goes back through the courier too. The kitchen also needs a new front-desk procedure: "Which restaurant are you trying to reach, who are you, and how many orders may you have in flight?" That procedure is the Connect command.

What the analogy hides. Couriers are slow and unreliable. NVMe-oF transports are reliable, in-order connections (a TCP stream, or an RDMA Reliable Connected queue pair) that deliver in microseconds. The analogy also hides that with RDMA the "kitchen" really can reach into the customer's house: the target's network adapter reads and writes host memory directly, but only memory the host has registered and named with a key.

Where it misleads. It suggests the envelope always carries the food. In-capsule data is limited by a size the controller advertises. Larger writes use a separate data phase: Ready to Transfer (R2T) plus host-to-controller data PDUs on TCP, or RDMA READ on RDMA. It also suggests there is one courier per restaurant. In practice, every NVMe queue pair gets its own connection.

Beginner explanation

NVMe is two things glued together. First, it is a language: a set of commands (Read, Write, Identify, Get Log Page…), a fixed command format, a fixed completion format and a set of status codes. Second, it needs a way of delivering that language between a host and a controller. The original delivery method is PCIe, where the host and controller share memory.

NVMe over Fabrics keeps the language and swaps the delivery method. The host builds the same 64-byte command. Instead of leaving it in host memory and ringing a doorbell, it packs it into a network message called a command capsule and sends it over a network connection. The controller runs the command and sends back a response capsule containing the same 16-byte completion entry you already know.

Three families of fabric are defined today:

  • RDMA (Remote Direct Memory Access): RoCE (RDMA over Converged Ethernet), iWARP (Internet Wide Area RDMA Protocol) or InfiniBand. The network adapter can read and write the other side's memory directly. See NVMe/RDMA.
  • TCP (Transmission Control Protocol): ordinary Ethernet and IP networks, with NVMe messages framed into Protocol Data Units (PDUs) on a TCP stream. See NVMe/TCP.
  • Fibre Channel (FC-NVMe): defined by the INCITS T11 committee rather than NVM Express. We mention it for completeness and do not cover it in depth.

Because there is no shared memory, three things you relied on over PCIe disappear:

  1. Doorbells. The arrival of a capsule tells the controller there is new work.
  2. Interrupts. The arrival of a response capsule tells the host the command finished.
  3. Physical Region Page (PRP) lists. Data locations are described with Scatter Gather List (SGL) descriptors that make sense to the transport: an offset inside the capsule, a transport-managed data transfer, or an RDMA memory key plus address.

Two new things appear:

  1. Connecting. Before any command flows, the host opens a network connection and sends a Connect command that names the subsystem it wants (by its NVMe Qualified Name (NQN)), names itself and sets up one queue pair.
  2. Discovery. The host needs a way to learn which subsystems exist and at which network addresses. It does this by talking to a discovery controller. That is the subject of Fabric Architecture.

The SQE and CQE do not change shape when they cross a network. If you can decode a Read command from a PCIe trace, you can decode it from a packet capture. It just sits inside a capsule, which sits inside a transport PDU or message.

The transport binding idea

The Base specification describes a controller, its queues and its commands in abstract terms. A transport binding answers the concrete questions:

  • How does a command get from the host to the controller?
  • How does a completion get back?
  • How does data move, and how are data buffers described?
  • How is a queue created, sized and torn down?
  • How does the host reach controller registers or properties?
  • How are transport errors detected and reported?

The PCIe transport answers with memory writes, DMA, PRP/SGL, admin queue-creation commands, MMIO registers and AER. A fabric transport answers with capsules, transport data transfers, SGL descriptors, the Connect command, Property Get/Set and transport-level error PDUs or connection teardown.

Over PCIe, the host and controller share memory and signal each other. Over fabrics, they send each other messages and share nothing. RDMA blurs this for data, but not for commands.

RDMA sits in an interesting middle position. Commands and completions are still messages (RDMA SEND operations carrying capsules), but data can move with memory semantics: the target's RDMA NIC issues RDMA READ and RDMA WRITE operations directly against host buffers the host has registered. This is why NVMe/RDMA feels closer to PCIe for data movement and closer to TCP for command delivery. Chapter 67 works through it.

Capsules

A capsule is the transport-independent unit of NVMe-oF communication. The Base specification defines two kinds:

  • A command capsule contains a 64-byte SQE and may also contain additional SGL descriptors and/or data (in-capsule data).
  • A response capsule contains a 16-byte CQE and, depending on the transport and controller, may contain additional data. NVMe/TCP and NVMe/RDMA response capsules in practice carry just the CQE.

The transport then wraps the capsule. NVMe/TCP puts a command capsule inside a CapsuleCmd PDU, with an 8-byte common header and optional digests. NVMe/RDMA sends it as the payload of an RDMA SEND. NVMe/FC puts it in an FC-NVMe information unit. The capsule is identical in each case. Only the envelope differs.

In-capsule data

In-capsule data is write data (or other host-to-controller data) placed directly after the SQE in the same command capsule. It saves a round trip. The controller does not need to ask for the data, because it already has it when the command arrives.

  • The controller advertises how large an I/O command capsule it accepts in the Identify Controller data structure, in the I/O Queue Command Capsule Supported Size (IOCCSZ) field, expressed in 16-byte units. Subtract the 64-byte SQE and you get the maximum in-capsule data for I/O queues.
  • A companion field, I/O Queue Response Capsule Supported Size (IORCSZ), gives the response capsule size, also in 16-byte units.
  • The In Capsule Data Offset (ICDOFF) field says where data starts relative to the end of the SQE, in 16-byte units. It is usually zero.
  • The admin queue has its own in-capsule rules, which the transport specification defines. For example, NVMe/TCP requires an admin queue in-capsule data size large enough for a Connect command's 1024-byte data. Confirm exact value The TCP transport specification states the admin queue capsule size, so check it there rather than relying on implementation constants.

The SQE's data pointer for in-capsule data is an SGL Data Block descriptor with the Offset subtype. Its "address" field holds an offset into the capsule's data area, not a memory address. For data that does not fit, the descriptor is either a Transport SGL Data Block descriptor (NVMe/TCP: data moves in separate data PDUs) or a Keyed SGL Data Block descriptor (NVMe/RDMA: an address in host memory plus a remote key).

Read data never travels as in-capsule data in a command capsule, because the command capsule goes from host to controller. Read data travels in C2HData PDUs on TCP or as RDMA WRITE operations on RDMA, before the response capsule.

What stays exactly the same

  • The command sets. NVM Command Set opcodes (Flush 00h, Write 01h, Read 02h, Dataset Management 09h), Zoned Namespace and Key Value commands are unchanged.
  • Most admin commands. Identify (06h), Get Log Page (02h), Set/Get Features, Asynchronous Event Request, Keep Alive (18h), Abort and Namespace Management all work. The exceptions are the queue-management commands that make no sense without shared memory (Create/Delete I/O SQ/CQ, Doorbell Buffer Config). Over fabrics, the Connect command replaces them.
  • The SQE format. 64 bytes: Command Dword 0 (opcode, fused, PSDT, Command Identifier), NSID, data pointer, command dwords 10–15.
  • The CQE format. 16 bytes: command-specific DW0/DW1, SQ Head Pointer, SQ Identifier, Command Identifier, Phase tag and Status field. The Phase tag has no meaning over fabrics, since there is no ring in host memory to poll.
  • Status codes. Generic, command-specific, media and path-related status types keep their meaning. Fabrics add command-specific status values for Connect and path-related status values for transport issues.
  • Namespaces, NSIDs, subsystems, controllers. Same objects, same identifiers.
  • Controller properties. CAP, VS, CC and CSTS keep the same offsets (00h, 08h, 14h, 1Ch) and meaning. They are reached by Property Get/Set instead of MMIO.

The Connect command in detail

Connect is the most important Fabrics command, because nothing works until it succeeds. It does three jobs at once:

  1. Creates a queue pair (SQ and CQ) of a requested size on the connection it was sent over. The Queue ID (QID) field says which: QID 0 is the admin queue, 1…n are I/O queues.
  2. Establishes or joins an association. The first Connect (QID 0) creates an association between a host and a controller. Later Connects for I/O queues name the same controller by its Controller ID (CNTLID), returned by the admin Connect.
  3. Identifies both ends. Its 1024-byte data portion carries the Host Identifier (a 128-bit value), the requested CNTLID, the subsystem NQN the host wants and the host's own NQN.

Controller models: dynamic and static

A fabric subsystem may use the dynamic controller model, where each admin Connect with CNTLID FFFFh makes the subsystem allocate a fresh controller for that association, or the static controller model, where controllers exist ahead of time and the host asks for a specific one. Discovery controllers are always dynamic. Most software targets, including Linux nvmet, use the dynamic model. The difference matters for anything that is per-controller state: feature settings, Asynchronous Event Requests and keep alive.

Bringing a controller up over a fabric

The initialization sequence mirrors the PCIe one you learned in NVMe Controller, with transport steps in front and Fabrics commands replacing MMIO:

  1. Transport connect for the admin queue (TCP three-way handshake + ICReq/ICResp, or RDMA_CM connection establishment).
  2. Connect command, QID 0 → response carries CNTLID.
  3. If required, authentication (Authentication Send/Receive exchanges) on the admin queue.
  4. Property Get CAP, Property Get VS.
  5. Property Set CC (with CC.EN = 1, I/O queue entry sizes) → Property Get CSTS until CSTS.RDY = 1.
  6. Identify Controller (admin opcode 06h): learn IOCCSZ, IORCSZ, MDTS, number of queues, SGL support, KAS…
  7. Set Features Number of Queues, Asynchronous Event Request, Keep Alive scheduling.
  8. For each I/O queue: transport connect, then Connect with QID = n and the CNTLID learned in step 2.
  9. Identify Namespace list / Identify Namespace → block devices appear.

Notice what is missing compared with PCIe. You will see no AQA/ASQ/ACQ programming, since the admin queue's size comes from the admin Connect. You will see no doorbell stride, no MSI-X table setup and no Create I/O CQ/SQ commands. If a fabric trace seems to be "missing steps", check this list before assuming something failed.

SQ flow control and SQHD

Over PCIe, the host learns how far the controller has consumed the SQ through the SQ Head Pointer (SQHD) in each CQE, and must not overrun the ring. Over fabrics the same mechanism exists, with the "ring" now a controller-side buffer of capsules. A host may ask, through the Connect command, to disable SQ flow control. In that case the host promises never to have more commands outstanding than the queue depth, and the controller does not need to report meaningful SQHD values. Linux typically requests this when the controller allows it. Implementation-dependent When SQ flow control is disabled, SQHD in captures may look frozen. That is expected, not a bug.

The central concept on the ladder: the capsule

A sealed envelope that carries the request slip, and sometimes a small parcel, to a library across town. The reply comes back in another envelope.

A command capsule is a 64-byte NVMe SQE plus optional SGL descriptors and in-capsule data. A response capsule is a 16-byte CQE. Sending a capsule submits a command. Receiving a response capsule completes it.

The host's NIC (or RDMA NIC) transmits the capsule from a host buffer. On the target, a NIC receives it into target memory, where target software or an offload engine parses the SQE and dispatches it to a backing device, often a PCIe NVMe SSD. No PCIe traffic crosses between host and target.

The NVM Express Base Specification defines command and response capsules, the Fabrics commands and the message-based queueing model. Transport specifications (TCP 1.3, RDMA 1.3) define how capsules are framed. Capsule size limits come from Identify Controller (IOCCSZ, IORCSZ) and transport rules for the admin queue.

On TCP: CapsuleCmd PDU (common header + SQE + optional data + optional digests) → optional R2T/H2CData or C2HData → CapsuleResp PDU. On RDMA: SEND (command capsule) → optional RDMA READ/WRITE → SEND (response capsule).

A packet capture shows TCP segments to port 4420 that a dissector decodes as "NVMe/TCP CapsuleCmd, Read, CID 0x0042". The CID ties the C2HData and CapsuleResp rows to that command. On PCIe the same CID would tie an SQE fetch to a CQE write.

A missing CapsuleResp after C2HData with full data, combined with a host timeout and abort, points to the target's completion path or to a lost PDU. Digest errors point to corruption in transit. A Connect response with Connect Invalid Host points to configuration, not the network. Always find the first capsule whose content or timing deviates.

Hardware view

Draw the boxes before you draw the arrows. A fabric deployment has two hardware domains joined by a network, and NVMe appears in both of them in different roles.

What must participate

  • Host network adapter. A standard Ethernet NIC for NVMe/TCP, or an RDMA-capable NIC (RNIC) for RoCE, iWARP or InfiniBand. The NIC talks to the host CPU and memory over PCIe, so a PCIe analyzer on the host side sees NIC descriptor fetches and packet buffer DMA, not NVMe commands.
  • The network. Links and switches. NVMe/TCP tolerates loss through TCP retransmission, with a latency cost. RoCEv2 performs best on a lossless or well-tuned Ethernet configuration using Priority Flow Control (PFC) and/or Explicit Congestion Notification (ECN). Implementation-dependent
  • Target network adapter and target software or hardware. This might be Linux nvmet, a storage array's firmware, a SmartNIC/DPU offload, or an all-in-one "Ethernet SSD" where the controller itself speaks the fabric.
  • Backing media. Often a PCIe NVMe SSD, but it can be anything: a RAID volume, a file, RAM, a remote volume.

What may participate

  • TCP offload features: TSO/GSO (segmentation offload), LRO/GRO (receive coalescing), checksum offload, and on some NICs, NVMe/TCP digest and data-placement offload. Implementation-dependent
  • Kernel TLS offload (kTLS) when NVMe/TCP uses TLS.
  • On the target, peer-to-peer DMA between RNIC and SSD (e.g., through the SSD's Controller Memory Buffer), which avoids target CPU memory. Implementation-dependent

  • A command capsule contains an SQE and optionally SGLs and data. A response capsule contains a CQE and optionally data.
  • NVMe over Fabrics uses SGLs, not PRPs, to describe data.
  • Over fabrics, each I/O SQ is paired with exactly one CQ, and queues are created by the Connect command.
  • Controller properties CAP (00h), VS (08h), CC (14h) and CSTS (1Ch) are accessed with Property Get/Set over fabrics.
  • Fabrics architecture moved into the Base specification with NVMe 2.0. Transports have separate specifications.

Because a capsule's arrival is the submission signal, the "doorbell write → SQE fetch" latency of PCIe is replaced by "transmit → receive" latency on the fabric. A fabric command therefore cannot be "submitted but not fetched" in the PCIe sense. A command that never produces a response capsule was either lost in transit, discarded by the target, or stuck in target processing. The capture tells you which.

  • Number of I/O queues per association, queue depth and in-capsule data size, as advertised by the target.
  • Whether SQ flow control is disabled.
  • Whether a target is a software target, a hardware offload, or a native fabric-attached drive.
  • How the target maps fabric namespaces to backing storage, and how it schedules work across CPUs.
  • Host reconnect timers (Linux ctrl_loss_tmo, reconnect_delay) are host policy, not specification.
  • The original NVMe over Fabrics 1.0 (2016) defined the RDMA and FC bindings. NVMe/TCP was added later as a ratified Technical Proposal and is now its own transport specification.
  • TLS 1.3 support and secure channel concatenation evolved across TCP transport revisions. Check TCP Transport 1.3 for current requirements.
  • The 2026 (2.4) release updated the asymmetric key-exchange options used by authentication to prepare for post-quantum cryptography. See 2026 NVMe 2.4 Updates. Algorithm identifiers are not reproduced here. Read them in the Base 2.4 specification.
  • The Disconnect Fabrics command and some Connect attributes appeared in later revisions than the original Fabrics specification.
  • The specification does not say what latency or throughput a fabric must achieve.
  • It does not mandate a backing device type. A namespace over fabrics need not be an SSD.
  • It does not specify Linux behaviour: kernel module parameters, reconnect policy and multipath I/O policy are implementation choices.
  • Exact field offsets of Connect data, Discovery Log entries and PDU headers must be read from the specifications themselves. This chapter names them and gives values only where we are confident. Before you build tools, check them against the specification's figures.
  • Never assume a fabric controller's CNTLID or CIDs relate to the backing SSD's.
  • Never assume Phase Tag or SQHD values in fabric CQEs carry the same diagnostic meaning they carry over PCIe.
  • Never assume the in-capsule data size of the admin queue equals that of the I/O queues.
  • Never assume the target honours every Connect attribute you request. Read the response.

  1. Layer by layer. TCP connected (frames 1–3), so routing, firewall and listener are fine. ICReq/ICResp succeeded (4–5), so NVMe/TCP transport parameters are compatible. The failure is inside NVMe, in the Connect command's response.

Code / pseudocode

The program below builds two NVMe/TCP CapsuleCmd PDUs from scratch: an admin Connect with in-capsule data and an I/O Read whose data will arrive in C2HData PDUs. It then decodes them back. It uses only the Python standard library and runs as written. It never touches a network or a device.

#!/usr/bin/env python3
"""capsule_build.py - build NVMe-oF capsules and NVMe/TCP PDUs (synthetic, teaching only)."""
import struct, uuid

OPC_FABRICS, OPC_READ, OPC_WRITE = 0x7F, 0x02, 0x01
FCTYPE_CONNECT = 0x01
PSDT_SGL = 0x40                       # CDW0 flags bits 7:6 = 01b -> SGL used
PDU_CAPSULE_CMD = 0x04

def sgl_offset_desc(offset, length):
    """Data Block descriptor, Offset subtype: data sits inside the capsule."""
    return struct.pack("<QI3xB", offset, length, (0x0 << 4) | 0x1)

def sgl_transport_desc(length):
    """Transport SGL Data Block descriptor (type 5h, subtype Ah, as Linux nvme-tcp uses)."""
    return struct.pack("<QI3xB", 0, length, (0x5 << 4) | 0xA)

def connect_sqe(cid, qid, sqsize, kato_ms, data_len=1024):
    sqe = bytearray(64)
    struct.pack_into("<BBH", sqe, 0, OPC_FABRICS, PSDT_SGL, cid)
    sqe[4] = FCTYPE_CONNECT
    sqe[24:40] = sgl_offset_desc(0, data_len)
    struct.pack_into("<HHHBxI", sqe, 40, 0, qid, sqsize - 1, 0, kato_ms)  # RECFMT, QID, SQSIZE(0's based), CATTR, KATO
    return bytes(sqe)

def connect_data(hostid, cntlid, subnqn, hostnqn):
    d = bytearray(1024)
    d[0:16] = hostid.bytes
    struct.pack_into("<H", d, 16, cntlid)
    d[256:256 + len(subnqn)] = subnqn.encode()
    d[512:512 + len(hostnqn)] = hostnqn.encode()
    return bytes(d)

def read_sqe(cid, nsid, slba, nlb, nbytes):
    sqe = bytearray(64)
    struct.pack_into("<BBHI", sqe, 0, OPC_READ, PSDT_SGL, cid, nsid)
    sqe[24:40] = sgl_transport_desc(nbytes)
    struct.pack_into("<QI", sqe, 40, slba, nlb - 1)    # CDW10-11 SLBA, CDW12 NLB (0's based)
    return bytes(sqe)

def tcp_capsule_cmd(sqe, data=b""):
    hlen = 8 + len(sqe)
    pdo = hlen if data else 0
    plen = hlen + len(data)
    return struct.pack("<BBBBI", PDU_CAPSULE_CMD, 0, hlen, pdo, plen) + sqe + data

def hexdump(b, limit=96):
    for off in range(0, min(len(b), limit), 16):
        chunk = b[off:off + 16]
        print(f"  {off:04x}: {chunk.hex(' ')}")
    if len(b) > limit:
        print(f"  ... ({len(b) - limit} more bytes)")

def decode_sqe(sqe):
    opc, flags, cid = struct.unpack_from("<BBH", sqe, 0)
    addr, length, _, _, _, sglid = struct.unpack_from("<QIBBBB", sqe, 24)
    kind = {0x01: "Data Block / Offset (in-capsule)", 0x5A: "Transport Data Block"}.get(sglid, "other")
    print(f"  opcode={opc:02X}h PSDT={(flags >> 6) & 3:02b}b CID=0x{cid:04X}"
          f" SGL1: id={sglid:02X}h ({kind}) addr/offset=0x{addr:X} len={length}")
    if opc == OPC_FABRICS:
        recfmt, qid, sqsize, cattr, kato = struct.unpack_from("<HHHBxI", sqe, 40)
        print(f"  Fabrics FCTYPE={sqe[4]:02X}h RECFMT={recfmt} QID={qid} SQSIZE={sqsize} (0's based) KATO={kato} ms")

if __name__ == "__main__":
    hostid = uuid.UUID("5f1c0a2e-0000-4000-8000-00000000c0de")   # synthetic
    hostnqn = "nqn.2014-08.org.nvmexpress:uuid:" + str(hostid)
    subnqn = "nqn.2026-10.org.example:lab-ssd"

    sqe = connect_sqe(cid=0x0000, qid=0, sqsize=32, kato_ms=5000)
    pdu = tcp_capsule_cmd(sqe, connect_data(hostid, 0xFFFF, subnqn, hostnqn))
    print(f"Admin Connect CapsuleCmd PDU: {len(pdu)} bytes (8 CH + 64 SQE + 1024 in-capsule data)")

What to notice

  • The common header's first byte is 04h (CapsuleCmd). HLEN is 48h (72 = 8 + 64). For the Connect PDU, PDO is also 48h, because in-capsule data starts right after the header, and PLEN is 0448h (1096).
  • The SQE starts at byte 8 and looks exactly like a PCIe SQE, except that byte 1 (flags) is 40h: PSDT = 01b, SGL in use.
  • The Connect's SGL1 identifier is 01h (Data Block, Offset subtype), so its "address" is an offset into the capsule. The Read's is 5Ah (Transport Data Block, transport-specific subtype), so its address is zero and the transport moves the data.
  • SQSIZE is 1Fh for 32 entries, because it is 0's based. NLB 7 means 8 blocks for the same reason.

on_capsule(queue, capsule):
    sqe = capsule[0:64]
    if not queue.connected and not (sqe.opcode == 7Fh and sqe.fctype == CONNECT):
        respond(queue, sqe.cid, status = COMMAND_SEQUENCE_ERROR)   # nothing before Connect
        return

        return
    sgl = sqe.dptr
    switch sgl.type:
        case DATA_BLOCK_OFFSET:   data = capsule[64 + icdoff + sgl.offset : ... + sgl.length]
        case TRANSPORT_DATA_BLOCK: data = transport.pull_from_host(sgl.length)   # TCP: R2T/H2CData
        case KEYED_DATA_BLOCK:     data = rdma_read(sgl.addr, sgl.length, sgl.key) if is_write
    result = execute(sqe, data)                                   # same command logic as local NVMe

Worked example

Problem. An application writes 8 KiB (16 × 512-byte LBAs) to namespace 1 over NVMe/TCP. The controller reports IOCCSZ = 260 (in 16-byte units) and ICDOFF = 0. Will the data travel in-capsule? How many PDUs cross the wire, and how many round trips does the write take before the completion?

Step 1: maximum in-capsule data

Dmax = IOCCSZ × 16 − 64

260 × 16 − 64 = 4160 − 64 = 4096 bytes. The 8 KiB write does not fit. (Linux nvmet commonly advertises a few kilobytes of in-capsule data on I/O queues. Implementation-dependent)

Step 2: the PDU sequence

  1. Host → target: CapsuleCmd (Write, CID 0x0051, SGL 5Ah length 8192). 1 PDU.
  2. Target → host: R2T (CCCID 0x0051, R2TO 0, R2TL 8192, TTAG 0x0003). The target has buffer space. 1 PDU.
  3. Host → target: H2CData (DATAO 0, DATAL 8192, LAST_PDU), assuming MAXH2CDATA ≥ 8192. 1 PDU (several TCP segments at a 1500-byte MTU).
  4. Target → host: CapsuleResp (CID 0x0051, Success). 1 PDU.

That is 4 NVMe/TCP PDUs and two host↔target round trips: command→R2T, then data→response. For a 4 KiB write the data would have fit in-capsule, giving 2 PDUs and one round trip. This explains why small-write latency over fabrics depends heavily on the in-capsule size.

Step 3: compare with PCIe

Over PCIe the same 8 KiB write is: doorbell MWr → SQE MRd/CplD → data MRd (16 × 512-byte MRRS requests) → CplDs → CQE MWr → MSI-X. The "R2T" step has a PCIe analogue: the controller issues the data reads when it is ready. That is the same pull model, with the transport doing the pulling.

R2T is to NVMe/TCP what the controller's data MRd is to NVMe over PCIe. Both let the controller pace incoming data to its own buffer availability.

Senior engineer insight

On PCIe, a controller exists as long as the device is enumerated. Over fabrics, a controller exists only as long as an association exists. It is created by an admin Connect, kept alive by keep alive traffic, and destroyed by disconnect, keep alive expiry or connection loss. When the association dies, every queue, every outstanding command, every Asynchronous Event Request and every per-controller feature setting goes with it. With the dynamic model, a reconnect creates a new controller, possibly with a new CNTLID. Senior engineers ask "what happened to the association?" before they ask "what happened to the drive?"

TCP gives you reach (any IP network), mature tooling and tolerance of loss, at the cost of CPU copies and stack latency. RDMA gives you lower latency and CPU offload, at the cost of more demanding networks and memory registration complexity. The NVMe layer is identical, so a principal engineer evaluates fabrics on operational properties: failure domains, congestion behaviour, observability, security, and CPU cost per I/O. The command set does not decide between them.

In-capsule data removes a full round trip for small writes. If a workload is dominated by 4–16 KiB writes and the target advertises only 4 KiB of in-capsule space, most writes pay an R2T (TCP) or RDMA READ round trip. That is visible in captures as a command→R2T gap. Raising the target's in-capsule size trades target memory per queue entry for latency.

Background

In-capsule data uses the Data Block/Offset descriptor. Transport-moved data uses the Transport Data Block descriptor. For an NVMe/TCP write that does not fit in the capsule, the target sends one or more R2T PDUs. The host answers each with H2CData PDUs no larger than MAXH2CDATA.

Step 1

Add a function write_sqe(cid, nsid, slba, nlb, nbytes, inline) to the program. It should set opcode 01h and choose the descriptor: sgl_offset_desc(0, nbytes) if inline, else sgl_transport_desc(nbytes).

Step 2

Build the 3 KiB write as an in-capsule PDU, filling the data with a repeating byte pattern. Print the header and confirm HLEN = 72, PDO = 72 and PLEN = 72 + 3072 = 3144 (0C48h).

Step 3

Build the 64 KiB write without in-capsule data. Then, on paper, write the PDU sequence assuming the target issues a single R2T for the whole 64 KiB.

Observation

Compare bytes 8–71 of your write PDU with a PCIe Write SQE you decoded in WRITE. Every field except byte 1 (PSDT) and bytes 24–39 (DPTR) should match.

Questions

  1. Why can the 3 KiB write go in-capsule while the 64 KiB cannot?
  2. How many H2CData PDUs does the 64 KiB write need, and what are their DATAO values?
  3. What would change if the target sent two R2Ts of 32 KiB each?

Challenge

Write a decoder that takes a CapsuleCmd PDU and prints a Wireshark-style "Info" string, e.g. CapsuleCmd, Write, CID 0x0060, NSID 1, SLBA 0x2000, NLB 5, SGL 01h len 3072.

Hint

Maximum in-capsule data = 260 × 16 − 64 = 4096. For the H2CData count, divide R2TL by MAXH2CDATA and round up.

Solution 
def write_sqe(cid, nsid, slba, nlb, nbytes, inline):
    sqe = bytearray(64)
    struct.pack_into("<BBHI", sqe, 0, OPC_WRITE, PSDT_SGL, cid, nsid)
    sqe[24:40] = sgl_offset_desc(0, nbytes) if inline else sgl_transport_desc(nbytes)
    struct.pack_into("<QI", sqe, 40, slba, nlb - 1)
    return bytes(sqe)

small = tcp_capsule_cmd(write_sqe(0x0060, 1, 0x2000, 6, 3072, True), bytes([0xA5]) * 3072)
big = tcp_capsule_cmd(write_sqe(0x0061, 1, 0x3000, 128, 65536, False))
for name, pdu in (("3 KiB", small), ("64 KiB", big)):
    t, f, hlen, pdo, plen = struct.unpack_from("<BBBBI", pdu, 0)
    print(f"{name}: type={t:02X}h hlen={hlen} pdo={pdo} plen={plen}")
    decode_sqe(pdu[8:72])

Expected: the 3 KiB PDU prints hlen=72 pdo=72 plen=3144 with SGL id 01h. The 64 KiB PDU prints hlen=72 pdo=0 plen=72 with SGL id 5Ah.

Answers: (1) 3072 ≤ 4096, but 65536 > 4096. (2) 65536 / 32768 = 2 H2CData PDUs with DATAO 0 and 32768, the second carrying LAST_PDU. (3) Two R2Ts, each with its own TTAG and R2TO (0 and 32768). Each R2T is answered by one 32 KiB H2CData PDU carrying that R2T's TTAG. The total PDU count is the same, but the target can pace them.

Sequence for the 64 KiB write: CapsuleCmd → R2T(R2TO 0, R2TL 65536) → H2CData(DATAO 0, 32768) → H2CData(DATAO 32768, 32768, LAST_PDU) → CapsuleResp.

What a senior engineer notices

The 64 KiB write is gated by the target's willingness to issue R2T. That depends on target buffer availability, which is a common source of write-latency spikes under load. The host's MAXR2T (sent in ICReq) bounds how many R2Ts may be outstanding per command.

Failure variants

  • A host that sends in-capsule data larger than IOCCSZ allows: expect an error status or a transport termination.
  • A host that uses descriptor 5Ah but also appends data to the capsule: the PLEN/PDO mismatch is a framing error.
  • An H2CData whose DATAO does not match the R2T's R2TO: the target should treat it as a transport error.

Extension

Extend the decoder to the CapsuleResp PDU (common header + 16-byte CQE) and to C2HData. You will need these in NVMe/TCP.

Answers

Quiz

  1. Over NVMe/TCP, what tells the controller that a new command is available?

    • A write to the SQ Tail doorbell property via Property Set
    • An MSI-X message from the host NIC
    • The arrival of a CapsuleCmd PDU
    • A Keep Alive command
    Answer and reasoning

    Fabric controllers have no doorbells. The capsule's arrival is the submission. Doorbells are not properties over fabrics.

  2. Which opcode do all Fabrics commands share?

    • 06h
    • 18h
    • 01h
    • 7Fh
    Answer and reasoning

    7Fh. The Fabrics Command Type field distinguishes Connect, Property Get/Set, Authentication Send/Receive and Disconnect. 06h is Identify, 18h is Keep Alive, 01h is Create I/O SQ (admin) or Write (NVM).

  3. Which data-pointer mechanism is used over fabrics?

    • PRP only
    • SGL only
    • Either PRP or SGL, chosen per command
    • Neither: data always travels in the capsule
    Answer and reasoning

    SGLs only. PRPs name host memory pages that a remote controller cannot address.

  4. What does a response capsule contain at minimum?

    • A 16-byte CQE
    • A 64-byte SQE
    • The read data
    • An R2T
    Answer and reasoning

    The completion queue entry. Read data travels separately before it, in C2HData PDUs or RDMA WRITEs.

  5. How is an I/O queue created over a fabric?

    • Create I/O CQ then Create I/O SQ on the admin queue
    • Property Set to the AQA property
    • A Connect command with a non-zero QID on a new transport connection
    • It exists automatically after the admin Connect
    Answer and reasoning

    Each I/O queue gets its own transport connection (TCP connection or RDMA QP) and its own Connect with the CNTLID returned by the admin Connect.

  6. A controller reports IOCCSZ = 516. What is the maximum in-capsule data on its I/O queues?

    • 516 bytes
    • 8192 bytes
    • 8256 bytes
    • 4096 bytes
    Answer and reasoning

    516 × 16 = 8256 bytes per capsule, minus 64 bytes for the SQE, leaves 8192 bytes.

  7. In which specification does the Connect command live in the 2.4 set?

    • NVM Express Base Specification 2.4
    • NVMe over TCP Transport 1.3
    • NVM Command Set 1.3
    • NVMe over PCIe Transport 1.4
    Answer and reasoning

    Fabrics commands are transport-independent and live in the Base specification. Transport specifications define framing.

  8. A capture shows TCP connected and ICReq/ICResp succeeded, then a CapsuleResp with Connect Invalid Host. Which layer failed?

    • Link/MTU
    • TCP
    • NVMe/TCP framing
    • NVMe-oF association (host authorization)
    Answer and reasoning

    Every lower layer demonstrably worked. The subsystem rejected the host identity.

  9. Open question: why is the Phase Tag in a fabric CQE not useful for diagnosing completions?

    Model answer

    Over PCIe the phase tag lets the host find new entries in a ring it polls in its own memory. Over fabrics there is no host-memory CQ ring. Each response capsule is a discrete message, delivered once, so the host never needs to tell new entries from old by phase.

  10. Open question: name two things a reconnect with the dynamic controller model does not preserve.

    Model answer

    Outstanding commands (they must be retried or failed), Asynchronous Event Requests, per-controller feature settings and possibly the CNTLID. The host must re-issue AERs and re-apply features. Namespace data persists, because it belongs to the subsystem.

Interview questions

  1. Beginner: What is NVMe over Fabrics and why does it exist?

    Model answer

    It carries the NVMe command set over networks such as TCP/IP, RDMA and Fibre Channel, so hosts can use remote NVMe storage with the same commands, queues and status model as local NVMe, without translating to SCSI. It exists to disaggregate storage from compute while keeping NVMe's low-overhead, multi-queue design.

  2. Beginner: What is a capsule?

    Model answer

    The NVMe-oF message unit. A command capsule is an SQE plus optional SGLs and data. A response capsule is a CQE plus optional data. Transports wrap capsules in their own framing.

  3. Intermediate: Compare queue creation over PCIe and over fabrics.

    Model answer

    Over PCIe the host allocates rings in its memory, programs AQA/ASQ/ACQ for the admin queue, and creates I/O queues with Create I/O CQ (05h) and Create I/O SQ (01h), passing ring addresses. Over fabrics each queue has its own transport connection. The host sends Connect with the QID and size. The admin Connect creates the association and returns the CNTLID, which I/O Connects then reference. There are no ring addresses, and SQ:CQ is strictly 1:1.

  4. Intermediate: Why are PRPs not used over fabrics?

    Model answer

    PRPs are lists of host memory page addresses that the controller DMAs to and from. A remote controller cannot address host memory, except under RDMA, and even then it needs a key, which PRPs have no field for. SGL descriptors can express in-capsule offsets, transport-managed transfers, and keyed remote memory.

  5. Advanced: A host's fabric reads show 150 µs latency while the same SSD locally shows 70 µs. How do you split the 80 µs?

    Model answer

    Capture on the host wire and, if possible, the target's PCIe side or target tracepoints. Measure host submit→capsule on wire (host stack), capsule→target submits to SSD (network + target receive + parse), SSD time (target PCIe trace), SSD completion→C2HData (target data path), and C2HData→CapsuleResp→host completion (network + host receive). Then compare with idle conditions to separate queueing from fixed cost. Check offloads, interrupt coalescing and CPU affinity on both sides.

  6. Advanced: What is the significance of disabling SQ flow control?

    Model answer

    The host promises never to exceed the queue depth, so the controller does not have to report SQ head progress in SQHD. This simplifies target implementation and saves bookkeeping. The cost is that SQHD in captures is meaningless, so analyzers and engineers must not read progress from it.

  7. Senior: How would you design an observability plan for an NVMe/TCP deployment?

    Model answer

    Layered: switch and NIC counters (drops, pauses, retransmissions), host and target per-queue latency histograms (block layer and nvme tracepoints), keep alive and reconnect events with timestamps, periodic capture samples with digests enabled in test environments, ANA state change logging, and target-side backing-device latency so fabric overhead can be separated from media latency. Correlate with a common clock (PTP) where possible.

  8. Senior: What failure modes exist over fabrics that do not exist over PCIe?

    Model answer

    Partial network failure (one path down, another up), split-brain path states, keep alive expiry under CPU starvation, authentication and authorization failures, congestion collapse, MTU mismatches, discovery inconsistencies, reconnect storms, and security attacks (spoofed NQNs, man-in-the-middle without TLS). PCIe failures tend to be local and hard. Fabric failures are often partial, transient and caused by configuration.

Teach-back challenge

  • To a child: explain why the librarian across town does not need a bell.
  • To a junior engineer: explain, using one diagram, what stays the same and what changes between NVMe/PCIe and NVMe/TCP for a single Read.

Model explanations

Child: "When the librarian lived next door, the teacher rang a bell so she'd come look in the box. Now the teacher mails letters. When the letter arrives at the library, the librarian already knows there's work, because the letter is right in her hands."

Junior: "The 64-byte command and 16-byte completion are identical. Over PCIe, the command sits in host memory, a doorbell write tells the SSD, the SSD fetches the command, writes the data and completion into host memory, and interrupts. Over TCP, the host sends the command in a CapsuleCmd PDU. The target sends the data in a C2HData PDU and the completion in a CapsuleResp PDU. There are no doorbells, no fetches and no interrupts, and the data pointer is an SGL that tells the transport to move the data."

Senior: "Message-based. Commands and completions are messages, and queue state is not shared memory. RDMA adds memory semantics only to the data phase, and only for host-registered regions named by keys in Keyed SGL descriptors. The controller cannot fetch commands or walk host-memory structures. The Base specification's model calls this message-based, and the debugging consequences follow from that."

Chapter summary

  • NVMe-oF keeps the NVMe language (commands, completions, status, namespaces, controllers, subsystems) and replaces the PCIe delivery mechanism with transport bindings for TCP, RDMA and FC.
  • The unit of exchange is the capsule: an SQE plus optional SGLs and data, or a CQE plus optional data.
  • PCIe is memory-based: shared rings, doorbells, DMA, interrupts. Fabrics are message-based: capsules push commands and completions. RDMA adds memory semantics for data only.
  • Fabrics have no doorbells, no interrupts from the target, no PRPs and no Create I/O SQ/CQ. Connect, Property Get/Set and authentication commands (opcode 7Fh) replace or extend them.
  • In-capsule data saves a round trip and is bounded by IOCCSZ. Larger data uses R2T/H2CData (TCP) or RDMA READ (RDMA).
  • A fabric controller lives inside an association. Think in associations when debugging.
