How to use the Interview Academy

An interview for a Non-Volatile Memory Express (NVMe) or Peripheral Component Interconnect Express (PCIe) role is not a vocabulary test. The interviewer is trying to find out whether you can take something you have never seen before (a trace, a log, an odd symptom) and reason about it out loud, layer by layer, without bluffing. This page trains that skill.

Learning objectives

  • Answer questions at each level in the shape interviewers reward: claim, mechanism, evidence, limits.
  • Move from "what is it" to "what would I see in a trace" to "what would I suspect when it fails" without being prompted.
  • Say clearly what the specification requires, what you are inferring, and what depends on the implementation.
  • Use the links in each answer to go back to the chapter that teaches the point when an answer exposes a gap.

The shape of a strong answer

Interviewers say over and over that the "Limits" step is what separates senior candidates from the rest. Someone who says "I would confirm the exact field in the NVM Express Base Specification before relying on it" is more trustworthy than someone who recites a bit position confidently and gets it wrong.

Think of an interview as a cooking show where the judges care less about the dish than about whether you can tell them why you added each ingredient, what would happen if you left it out, and how you would know if it had gone wrong.

In a cooking show, the judges can taste the result. In an engineering interview there is often no "result": the interviewer only hears your reasoning. That is why saying your evidence and your uncertainty out loud matters more here than in almost any other setting.

Beginner bank

Beginner questions check that the mental model is in place: what talks to what, in which direction, and why. A strong beginner answer is short, correct, and already mentions where you would see the thing.

  1. [Concept] What problem did NVMe solve that the Advanced Host Controller Interface (AHCI) with Serial ATA (SATA) could not?

    Model answer and what the interviewer listens for

    AHCI was designed for spinning disks: one command queue of 32 entries per port, several uncached register accesses per command, and a single interrupt path. With flash, the media became fast enough that the interface and software stack became the bottleneck. NVMe gives each central processing unit (CPU) core its own Submission/Completion Queue pairs (up to 65,535 I/O queues, each up to 65,536 entries, depending on what the controller supports), needs only one doorbell write per batch of commands, uses Message Signalled Interrupts Extended (MSI-X) so each queue can interrupt its own core, and sits directly on PCI Express (PCIe) without a protocol translation layer.

    Listening for: "the interface became the bottleneck once the media got fast"; queues per core; fewer register accesses; no translation layer. Knowing that the queue limits are maximums, not what every controller supports, is a plus.

    Learn it in: Chapter 3, Chapter 21.

  2. [Concept] Are NVMe and PCIe the same thing? Explain how they relate.

    Model answer and what the interviewer listens for

    No. PCIe is a general-purpose, packet-based, point-to-point interconnect: it moves memory reads, memory writes, configuration accesses and messages between a host and devices. NVMe is a storage interface: a register set, a queueing model and command sets. The NVMe over PCIe Transport specification says how NVMe maps onto PCIe: registers in a Base Address Register (BAR), queues in host memory, doorbells as memory writes, data moved by the controller's Direct Memory Access (DMA). NVMe also runs over other transports (TCP, RDMA, Fibre Channel), and PCIe carries many devices that are not storage.

    Listening for: three separate things (interconnect, storage interface, transport mapping), and at least one example of NVMe without PCIe or PCIe without NVMe.

    Learn it in: Chapter 4, Chapter 22, Chapter 65.

  3. [Concept] What is a PCIe lane, and what does "x4" mean on a link?

    Model answer and what the interviewer listens for

    A lane is one differential pair for transmit plus one differential pair for receive, so it carries data in both directions at the same time. A x4 link uses four lanes in parallel, and bytes are striped across them. Link width is negotiated during training. If a lane fails to train, the link can come up narrower (for example x2), which you would see in the Link Status register as a negotiated width lower than the Link Capabilities maximum.

    Listening for: full duplex; striping; negotiated rather than fixed; knowing where to check the result (Link Status versus Link Capabilities).

    Learn it in: Chapter 5, Chapter 9.

  4. [Concept] What is a Transaction Layer Packet (TLP)? Name three kinds an NVMe solid-state drive (SSD) produces or receives in normal operation.

    Model answer and what the interviewer listens for

    A TLP is the unit of work at the PCIe Transaction Layer: a header (3 or 4 doublewords) with type, length, requester ID, tag and address (or routing ID), an optional data payload and an optional end-to-end CRC (ECRC). For an NVMe SSD: Memory Write (MWr) from the host for doorbells; Memory Read (MRd) from the device to fetch Submission Queue Entries (SQEs) and write data; Completion with Data (CplD) from the host's root complex answering those reads; MWr from the device carrying read data, Completion Queue Entries (CQEs) and MSI-X interrupts. Configuration Read/Write TLPs appear during enumeration.

    Listening for: a request and its matching completion; correct direction for each; MSI-X recognised as a memory write.

    Learn it in: Chapter 10, Chapter 11, Chapter 39.

  5. [Concept] What is a Base Address Register (BAR), and why does an NVMe driver care about BAR0?

    Model answer and what the interviewer listens for

    A BAR is a configuration-space register where a function says how much address space it needs and of what type. Enumeration software sizes it (writes all ones, reads back the mask), assigns a base address and enables Memory Space in the Command register. For NVMe over PCIe, the controller registers (Controller Capabilities CAP, Version VS, Controller Configuration CC, Controller Status CSTS, Admin Queue Attributes AQA, Admin Submission and Completion Queue base addresses ASQ and ACQ, and the doorbells from offset 1000h) live in the memory space described by BAR0 (with BAR1 when it is a 64-bit BAR). Without a valid BAR0 assignment and Memory Space Enable, the driver cannot reach any NVMe register.

    Listening for: sizing then assignment; the Memory Space Enable bit; the controller registers living in BAR0; 64-bit BARs using two registers.

    Learn it in: Chapter 19, Chapter 24.

  6. [Concept] Describe a Submission Queue and a Completion Queue. Who produces into and who consumes from each?

    Model answer and what the interviewer listens for

    Both are circular buffers in host memory (for NVMe over PCIe). The host produces commands into the Submission Queue (SQ) and advances the tail; the controller consumes them and advances its head. The controller produces 16-byte entries into the Completion Queue (CQ) and the host consumes them, advancing the CQ head. The host tells the controller about a new SQ tail and a new CQ head through doorbell writes. The controller reports its SQ head in each Completion Queue Entry (CQE) so the host knows which SQ slots are free.

    Listening for: producer/consumer for both queues stated correctly; doorbells as the way the host tells the controller; SQ head carried back in the CQE.

    Learn it in: Chapter 25, Chapter 27.

  7. [Concept] What is a doorbell? Why is it a write that the controller receives rather than something the controller polls in host memory?

    Model answer and what the interviewer listens for

    A doorbell is a controller register in BAR0 that the host writes with a new SQ tail or CQ head. It is a posted PCIe memory write, so the CPU does not wait for a response. If the controller instead polled host memory for new commands, it would generate constant read traffic across the link and add latency. The doorbell turns "is there work?" into a single event. (Some later mechanisms, such as shadow doorbells used in virtualized environments, change this tradeoff; they are optional features.)

    Listening for: posted write; cost of polling across the link; the CPU not stalling. Mentioning that shadow doorbell buffers exist as an optional feature is a bonus, not required.

    Learn it in: Chapter 28, Chapter 12.

  8. [Concept] What is Direct Memory Access (DMA), and why does NVMe depend on it?

    Model answer and what the interviewer listens for

    DMA means the device itself issues memory reads and writes to host memory, instead of the CPU copying each byte. An NVMe controller uses DMA to fetch commands from the SQ, to read data for writes, to write data for reads, and to post CQEs. The CPU only writes the Submission Queue Entry (SQE) and rings the doorbell. With an Input/Output Memory Management Unit (IOMMU), the addresses the device uses are I/O virtual addresses that the IOMMU translates and checks.

    Listening for: the device is the bus master; all four DMA uses named; awareness of the IOMMU.

    Learn it in: Chapter 20, Module 02.

  9. [Concept] How large is an NVMe Submission Queue Entry and a Completion Queue Entry, and what is the most important field in each?

    Model answer and what the interviewer listens for

    An SQE is 64 bytes; a CQE is 16 bytes (for NVMe over PCIe I/O queues with the standard entry sizes). In the SQE, Command Dword 0 carries the opcode and the Command Identifier (CID); the data pointer (PRP or Scatter Gather List (SGL)) says where the data is. In the CQE, Dword 3 carries the CID, the Phase Tag and the Status Field, and Dword 2 carries the SQ Head Pointer and SQ Identifier. The CID plus the SQ identifier is what lets the host match a completion to its command.

    Listening for: 64/16; the CID being the matching key (together with the SQ ID); status in the CQE.

    Learn it in: Chapter 29, Module 28.

  10. [Concept] What does the Admin Queue do that I/O queues do not?

    Model answer and what the interviewer listens for

    The Admin Queue pair (queue ID 0) carries management commands: Identify, Create/Delete I/O Submission and Completion Queues, Get Log Page, Set/Get Features, Firmware Download/Commit, Format NVM, Asynchronous Event Request and others. Its location and size are programmed directly in the AQA, ASQ and ACQ registers before the controller is enabled; I/O queues are created later with admin commands. Read and Write commands go on I/O queues.

    Listening for: configured through registers, not commands; it must exist before anything else; examples of admin commands.

    Learn it in: Chapter 26, Chapter 30.

  11. [Concept] What is a namespace?

    Model answer and what the interviewer listens for

    A namespace is a quantity of non-volatile storage that the host addresses by Logical Block Address (LBA), identified by a Namespace ID (NSID). One controller can expose several namespaces, each with its own size and LBA format. Linux shows each as a block device such as /dev/nvme0n1. Namespaces can be created, deleted and attached to controllers through Namespace Management and Attachment commands when the controller supports them.

    Listening for: addressed by Namespace Identifier (NSID); separate from the controller; its own format; the Linux naming.

    Learn it in: Chapter 58, Module 23.

  12. [Concept] Why is Identify one of the first commands a driver sends?

    Model answer and what the interviewer listens for

    Identify (admin opcode 06h) returns 4 KiB data structures that describe the controller (for example the Maximum Data Transfer Size (MDTS), the number of namespaces, optional features, power-state descriptors) and each namespace (size, LBA formats). The driver needs that information to size transfers, pick queue counts and features, and create block devices. Sending I/O before knowing MDTS or the LBA size would be guessing.

    Listening for: it returns data by DMA into host memory; the driver adapts to the controller rather than assuming; at least two concrete fields.

    Learn it in: Chapter 30, Capacity, Status, Identify, Logs.

  13. [Concept] What is MSI-X, and why does NVMe benefit from one vector per queue?

    Model answer and what the interviewer listens for

    MSI-X is an interrupt mechanism in which the device signals an interrupt by writing a specific data value to a specific address, both taken from a table in device memory (located through the MSI-X capability). It supports up to 2,048 vectors, each with its own address, data and mask bit. With one vector per Completion Queue, each queue's completions can interrupt the CPU core that submitted the work, so there is no shared interrupt handler to fight over and no cross-core cache traffic.

    Listening for: an interrupt is a memory write; the per-vector table; locality to the CPU core.

    Learn it in: Chapter 43, Module 19.

  14. [Troubleshoot] lspci shows the SSD, but there is no /dev/nvme0n1. What do you check first?

    Model answer and what the interviewer listens for

    The device enumerated, so the link trained and configuration space is readable. Next: is a driver bound (lspci -k shows "Kernel driver in use")? Does the kernel log show the NVMe driver probing, timing out waiting for CSTS.RDY, or reporting a controller fatal status? Does /dev/nvme0 (the controller character device) exist without namespaces, which would point to zero active namespaces or a namespace not attached? Is Memory Space Enable set and is BAR0 assigned? All of these are read-only checks.

    Listening for: splitting the problem by layer (enumeration done, driver bind, controller enable, namespaces); controller device versus namespace device; read-only first.

    Learn it in: Chapter 69, Chapter 70, Chapter 71.

  15. [Concept] What does lspci -vvv tell you that nvme list does not, and the other way round?

    Model answer and what the interviewer listens for

    lspci -vvv decodes PCIe configuration space: vendor/device IDs, BARs, capabilities, Link Capabilities versus Link Status (speed and width), Max Payload Size, MSI-X, Active State Power Management (ASPM) and Advanced Error Reporting (AER) capability registers. It knows nothing about NVMe. nvme list (nvme-cli) uses NVMe admin commands to show controllers, namespaces, model, serial number, firmware revision and capacity. It knows nothing about the link. Debugging needs both views because a problem can sit in either layer.

    Listening for: PCIe view versus NVMe view, stated as two different layers.

    Learn it in: Chapter 69, Chapter 70.

  16. [Concept] Give one example each of a posted and a non-posted PCIe transaction in NVMe traffic.

    Model answer and what the interviewer listens for

    Posted (no completion returned): a doorbell MWr from the host; a data MWr from the device for a Read command; a CQE MWr; an MSI-X MWr. Non-posted (a completion must come back): the device's MRd to fetch an SQE or write data; a configuration read or write; a CPU read of CSTS. A non-posted request uses a tag so the completion can be matched, and if nothing comes back the requester eventually logs a Completion Timeout.

    Listening for: correct classification; "completion timeout exists only for non-posted requests".

    Learn it in: Chapter 12, Chapter 13.

  17. [Concept] What is the raw signalling rate of a PCIe 4.0 lane, and what encoding does it use?

    Model answer and what the interviewer listens for

    16.0 GT/s per lane with 128b/130b encoding, the same encoding as 3.0 (8.0 GT/s). 1.0 and 2.0 used 8b/10b. PCIe 5.0 doubles to 32.0 GT/s with 128b/130b; PCIe 6.0 moves to 64.0 GT/s using four-level Pulse Amplitude Modulation (PAM4) and fixed-size FLITs with forward error correction.

    Listening for: GT/s, not GB/s; the encoding; awareness that 6.0 changes the framing.

    Learn it in: Chapter 6, Module 07.

  18. [Performance] A Gen4 x4 link is "16 GT/s". Roughly how many bytes per second of NVMe data can it carry, and why less than the naive number?

    Model answer and what the interviewer listens for
    B = R × N × E ÷ 8
    B
    raw link bandwidth in bytes per second, per direction
    R
    signalling rate per lane, 16 × 109 transfers per second
    N
    number of lanes, 4
    E
    encoding efficiency, 128/130

    That gives about 7.88 GB/s per direction. Each TLP adds framing, a sequence number, a header and a Link CRC (LCRC), so with 256-byte payloads roughly 90% of that is payload: about 7 GB/s in practice, minus Data Link Layer Packets (DLLPs) for acknowledgement and flow control, and minus read-request traffic in the other direction. Real drives also hit media and controller limits.

    Listening for: the arithmetic done out loud; per direction; protocol overhead named; the result stated as approximate.

    Learn it in: Chapter 6, Mathematics for Storage and Links, Calculators.

  19. [Concept] What is the Phase Tag in a Completion Queue Entry, and why is it needed?

    Model answer and what the interviewer listens for

    The Phase Tag is a bit the controller writes in every CQE. It flips value each time the controller wraps around the CQ. The host knows the phase it expects for the current pass; an entry whose Phase Tag matches is new, and one that does not is stale from the previous pass. This lets the host find new completions by reading host memory, with no register read across the link.

    Listening for: it flips on each wrap; no memory-mapped I/O (MMIO) read needed; how the host knows what to expect (it starts at 1 after the queue memory is cleared to zero).

    Learn it in: Chapter 25, Chapter 27, Queue Simulator.

  20. [Concept] What is a Logical Block Address (LBA)? What changes when a namespace is formatted with 4 KiB LBAs instead of 512-byte LBAs?

    Model answer and what the interviewer listens for

    An LBA is the index of a block in a namespace. The LBA size is set by the namespace's LBA format (LBA Data Size, a power of two). With 4 KiB LBAs, the same byte offset maps to an LBA eight times smaller; the Number of Logical Blocks field in a Read or Write counts 4 KiB units; I/O smaller than or not aligned to 4 KiB must be handled by the host (read-modify-write); and capacity in LBAs is eight times smaller for the same bytes. Formatting destroys the data.

    Listening for: it changes the unit of every command; alignment consequences; formatting is destructive.

    Learn it in: Chapter 2, Chapter 58, Chapter 32.

  21. [Spec] What do "shall", "should" and "may" mean when you read a specification?

    Model answer and what the interviewer listens for

    "Shall" states a mandatory requirement: a conforming implementation must do it. "Should" is a recommendation: a strong preference with room for justified exceptions. "May" is permission: the behaviour is optional. Notes and examples are informative, not normative. Check the conventions section of the specification you are reading, because each specification defines its own conventions.

    Listening for: normative versus informative; knowing that each specification defines its own conventions.

    Learn it in: Specification Reading School, Truth Policy.

  22. [Concept] In one minute: what is Advanced Error Reporting (AER)?

    Model answer and what the interviewer listens for

    AER is an optional PCIe extended capability that records errors in more detail than the basic Device Status bits: separate status, mask and severity registers for uncorrectable and correctable errors, a header log that captures the TLP header of the failing transaction for some errors, and, at root ports, registers that collect error messages from below. Errors are classed as correctable, uncorrectable non-fatal or uncorrectable fatal. Linux's AER driver reads these and logs them.

    Listening for: correctable / non-fatal / fatal; the header log; error messages reported to the root port; that it is a capability, not something always present.

    Learn it in: Chapter 46, Module 18.

  23. [Trace] An analyzer shows MWr32 Addr=0xFE60_1008 Len=1 Data=0x00000005 going to the course's Lab SSD (BAR0 at 0xFE60_0000, CAP.DSTRD = 0). What is it?

    Model answer and what the interviewer listens for

    The offset from BAR0 is 0x1008. Doorbells start at 0x1000, and with a stride of 4 bytes the order is SQ0 tail (0x1000), CQ0 head (0x1004), SQ1 tail (0x1008). So this is the host telling the controller that I/O Submission Queue 1's tail is now 5. You expect the controller to respond by reading one or more SQEs from SQ1's base address.

    Listening for: the subtraction from BAR0; using the stride formula; predicting the next event (an SQE fetch).

    Learn it in: Chapter 28, Module 27.

Intermediate bank

Intermediate questions check that you can follow one command across the layers, do the arithmetic, and name the register or log that proves a claim. Expect follow-ups such as "and what would that look like on the analyzer?"

  1. [Trace] Walk through a 4 KiB NVMe Read on the course's Lab SSD (Gen4 x4, Max Payload Size (MPS) 256 bytes), naming every PCIe transaction in order and its direction.

    Model answer and what the interviewer listens for

    The host builds the SQE in memory and writes the SQ1 tail doorbell (posted MWr, host to device). The controller issues an MRd for the 64-byte SQE; the root complex returns a CplD. The controller reads the media, then writes 4 KiB of data into the buffer named by PRP1 as sixteen 256-byte MWr TLPs (limited by MPS). It writes the 16-byte CQE (MWr), then the MSI-X interrupt (MWr to the address and data in the MSI-X table entry). The driver processes the CQE and writes the CQ1 head doorbell. Every device-to-host write is posted; the only non-posted request is the SQE fetch.

    Listening for: correct directions; MPS splitting the data; the CQE before the interrupt; the CQ head doorbell at the end; knowing which transactions are posted.

    Learn it in: Chapter 39, Chapter 41, Module 37.

  2. [Concept] How does a controller tell an SQ is empty or full? What does the host do to avoid overflowing it?

    Model answer and what the interviewer listens for

    Empty when head equals tail. Full when (tail + 1) mod size equals head, so one slot is always left unused to tell full from empty. The host owns the tail; it learns the controller's head from the SQ Head Pointer field in each CQE. Before writing a new entry the host checks that advancing the tail would not make it equal to the last head it saw. A host that ignores this overwrites commands the controller has not fetched yet.

    Listening for: the one-empty-slot convention; where the host learns the head; the danger of overwriting.

    Learn it in: Chapter 25, Queue Simulator.

  3. [Concept] Why does each CQE carry an SQ Head Pointer and an SQ Identifier?

    Model answer and what the interviewer listens for

    The SQ Head Pointer tells the host how far the controller has consumed that SQ, so the host can reuse those slots; there is no other cheap way to learn it, because reading a register across the link is slow. The SQ Identifier is needed because several SQs may share one CQ; together with the CID it tells the host which command completed.

    Listening for: slot reclamation; shared CQs; the (SQ ID, CID) pair as the key.

    Learn it in: Chapter 25, Chapter 27.

  4. [Coding] A 12 KiB Read targets a buffer starting at host address 0x2_0000_0800 (4 KiB memory pages). How are PRP1 and PRP2 filled?

    Model answer and what the interviewer listens for

    The buffer covers 0x2_0000_0800 to 0x2_0000_37FF: 2 KiB in the first page, 4 KiB, 4 KiB, then 2 KiB in a fourth page. That is four pages. PRP1 = 0x2_0000_0800 (it may have an offset). Because more than two pages are touched, PRP2 is not a data pointer but a pointer to a Physical Region Page (PRP) list, and that list holds three entries with zero offsets: 0x2_0000_1000, 0x2_0000_2000, 0x2_0000_3000. If the transfer touched exactly two pages, PRP2 would point directly at the second page.

    PAGE = 4096
def prp_layout(addr, length):
    first_page_bytes = PAGE - (addr % PAGE)
    pages = [addr]
    nxt = (addr // PAGE + 1) * PAGE
    remaining = length - min(length, first_page_bytes)
    while remaining > 0:
        pages.append(nxt)
        nxt += PAGE
        remaining -= PAGE
    if len(pages) == 1:
        return {"PRP1": pages[0], "PRP2": 0}
    if len(pages) == 2:
        return {"PRP1": pages[0], "PRP2": pages[1]}
    return {"PRP1": pages[0], "PRP2": "-> list", "list": pages[1:]}

r = prp_layout(0x2_0000_0800, 12 * 1024)
print(hex(r["PRP1"]), r["PRP2"], [hex(p) for p in r["list"]])

    Listening for: counting pages, not dividing bytes by 4096; the list holding only the pages after the first; non-first entries with zero offset; the two-page special case.

    Learn it in: Chapter 36, PRP Visualizer, Module 34.

  5. [Architecture] When would a host prefer a Scatter Gather List (SGL) over Physical Region Pages (PRPs)?

    Model answer and what the interviewer listens for

    PRPs describe memory as page-sized pieces, which suits page-aligned kernel buffers and is simple for hardware. SGLs describe arbitrary-length segments with byte granularity, so they suit large, physically scattered or unaligned buffers, user-space buffers with odd alignment, and fabrics, where NVMe over Fabrics requires SGLs for data. SGL support for I/O commands is optional on PCIe controllers and is advertised in Identify Controller; the host must check it. SGLs also allow bit-bucket descriptors (discarding parts of a read) when supported.

    Listening for: granularity; optional and advertised; fabrics need SGLs; a reason grounded in the buffer's shape.

    Learn it in: Chapter 37, Module 35.

  6. [Concept] What do Max Payload Size (MPS) and Max Read Request Size (MRRS) limit, and where are they set?

    Model answer and what the interviewer listens for

    MPS limits the data payload of any TLP a function sends (writes and completions with data). MRRS limits how many bytes one memory read request may ask for. Both are fields in the Device Control register of the PCI Express capability, programmed by system software within what Device Capabilities supports. MPS must be consistent along the path (a TLP larger than the receiver's MPS is a Malformed TLP); MRRS only affects the requester. For an NVMe Write, MRRS sets how many MRds the controller issues; for an NVMe Read, MPS sets how many MWr TLPs carry the data.

    Listening for: writes versus read requests; path-wide consistency for MPS; the consequence of a mismatch (Malformed TLP).

    Learn it in: Chapter 18, Chapter 11, Module 10.

  7. [Performance] With MPS 256 and MRRS 512, how many TLPs carry the data for a 128 KiB NVMe Read, and for a 128 KiB NVMe Write?

    Model answer and what the interviewer listens for

    Read: the device writes 131,072 bytes in MWr TLPs of at most 256 bytes: 512 MWr TLPs (assuming aligned buffers). Write: the device reads 131,072 bytes with MRds of at most 512 bytes: 256 MRd TLPs. Each completion can carry at most MPS (256 bytes), and the completer may split further at Read Completion Boundary (RCB) multiples, so there are at least 512 CplD TLPs coming back, often more. The write therefore costs more TLPs and depends on read latency and the number of outstanding tags.

    Listening for: MPS for the read; MRRS for request count on the write; completions bounded by MPS and RCB; noticing the asymmetry.

    Learn it in: Chapter 41, Chapter 52, Calculators.

  8. [Concept] What is a Completion Timeout, and which agent detects it?

    Model answer and what the interviewer listens for

    A Completion Timeout is logged by a requester that sent a non-posted request (a memory read, configuration access or I/O request) and received no completion within its timeout window. The detecting agent is always the requester: if the SSD's SQE fetch is never answered, the SSD logs it; if the CPU's read of CSTS is never answered, the root port logs it. The completer may know nothing. The timeout range is configured in Device Control 2 within the ranges advertised in Device Capabilities 2. By default it is reported as an uncorrectable, non-fatal error, and its severity is programmable in AER.

    Listening for: "the requester detects it"; only non-posted requests; the timeout is configurable; the fault may be anywhere on the path.

    Learn it in: Chapter 45, Chapter 52, Module 12.

  9. [Concept] Distinguish correctable, uncorrectable non-fatal and uncorrectable fatal PCIe errors, with an example of each.

    Model answer and what the interviewer listens for

    Correctable: hardware recovered with no loss of information, for example a Receiver Error or a Bad TLP fixed by Data Link Layer replay. Uncorrectable non-fatal: a specific transaction failed, but the link is still reliable, for example Completion Timeout, Unsupported Request, or Poisoned TLP received. Uncorrectable fatal: the link or device can no longer be trusted, for example a Data Link Protocol Error, Surprise Down, or Malformed TLP by default. Severity of uncorrectable errors is programmable in the AER Uncorrectable Error Severity register, so "by default" matters.

    Listening for: transaction-level versus link-level trust; defaults versus programmed severity.

    Learn it in: Chapter 45, Chapter 46.

  10. [Concept] Explain the CC.EN / CSTS.RDY handshake and the role of CAP.TO.

    Model answer and what the interviewer listens for

    The host programs AQA, ASQ and ACQ and the CC fields (for example memory page size and queue entry sizes), then sets CC.EN to 1. The controller initialises and sets CSTS.RDY to 1 when it is ready to process admin commands. To disable, the host clears CC.EN and waits for CSTS.RDY to return to 0. CAP.TO is the worst-case time, in 500 ms units, the host should wait for CSTS.RDY to change. A host that gives up earlier can falsely declare the device dead. CSTS.CFS (Controller Fatal Status) set during this wait means the controller hit a fatal internal error.

    Listening for: order of operations; the units of CAP.TO; checking CFS while waiting.

    Learn it in: Chapter 24, Chapter 48, Module 24.

  11. [Concept] Compare an NVMe Controller Reset, a Function Level Reset (FLR), a Hot Reset and a Conventional Reset. What survives each?

    Model answer and what the interviewer listens for

    Controller Reset (CC.EN 1→0): resets NVMe controller state (queues deleted, outstanding commands aborted) but leaves PCIe configuration space alone; the link stays up. FLR: a PCIe function-level reset that resets the function's configuration and controller state except for link-related state; the link stays up. Hot Reset: signalled through the link (training sets), resets everything below the port except sticky bits; the link retrains. Conventional Reset (cold, warm, PERST#): the strongest; everything resets, the link retrains from Detect. NVMe Subsystem Reset (NSSR), when supported, resets the whole NVM subsystem and may cause link loss. After anything stronger than a Controller Reset, software must restore configuration space (BARs, Command register, MSI-X).

    Listening for: a ladder from weak to strong; link survival; who restores state; sticky bits.

    Learn it in: Chapter 48, Chapter 49, Module 41.

  13. [Trace] In a trace, the CQE MWr is immediately followed by the MSI-X MWr. Why does the order matter, and what makes it safe without a read?

    Model answer and what the interviewer listens for

    The interrupt handler will read the CQ in host memory. If the interrupt could arrive before the CQE is visible, the handler would find nothing new. PCIe ordering rules say a posted write may not pass an earlier posted write in the same direction (unless Relaxed Ordering allows it), and the MSI-X message is itself a posted write. So the device can send the CQE write and then the interrupt write, and the host sees them in order. This is why the controller must not set Relaxed Ordering on the CQE or interrupt write in a way that lets the interrupt overtake the CQE.

    Listening for: posted-after-posted ordering; MSI-X as a memory write; the Relaxed Ordering caveat.

    Learn it in: Chapter 14, Chapter 43, Module 14.

  14. [Concept] What is an Asynchronous Event Request (AER command), and why does a driver keep one outstanding? How is it different from PCIe AER?

    Model answer and what the interviewer listens for

    Asynchronous Event Request is an admin command (opcode 0Ch) that the controller does not complete until something happens: a Self-Monitoring, Analysis and Reporting Technology (SMART)/health threshold crossing, an error, a namespace change notice, firmware activation and similar. The host keeps one or more outstanding so the controller has a way to tell it things; the completion says which log page to read to clear the event. It is unrelated to PCIe Advanced Error Reporting, which is a PCIe capability for transport and link errors. Same acronym, different layers.

    Listening for: a command that waits; reading the indicated log page; not confusing it with PCIe AER.

    Learn it in: Chapter 30, Chapter 44.

  15. [Troubleshoot] What does Linux do when an NVMe I/O command does not complete in time?

    Model answer and what the interviewer listens for

    The block layer's timer fires after the I/O timeout (the nvme_core.io_timeout module parameter, 30 seconds by default in common kernels). The NVMe PCI driver first checks whether the completion is actually sitting in the CQ (a missed interrupt) and, if so, completes it and warns. Otherwise it typically sends an Abort admin command; if that also fails or times out, it disables and resets the controller and requeues the I/O. Repeated failures can end with the controller being removed. Exact behaviour and messages vary by kernel version.

    Listening for: an escalation ladder (poll, abort, reset, remove); the timeout as a parameter; version caveat.

    Learn it in: Chapter 71, Chapter 48, Module 41.

  16. [Troubleshoot] A Gen4 SSD benchmarks at half its expected throughput. Which link fields do you check and where?

    Model answer and what the interviewer listens for

    In lspci -vvv for the SSD and for its upstream port: Link Capabilities (maximum speed and width) versus Link Status (current speed and width). A x4 device running at x2, or a 16 GT/s device at 8 GT/s, halves bandwidth. Also look at Link Capabilities 2 and Link Control 2 (target link speed), at whether the slot itself is wired x4, and at the "downgraded" annotations newer lspci versions print. Then check MPS and MRRS, and only then look at NVMe-level causes such as thermal throttling.

    Listening for: both ends of the link; capability versus status; slot wiring; layer order.

  17. [Concept] Name the main Link Training and Status State Machine (LTSSM) states a link passes through from power-on to normal operation, and one state it visits when errors occur.

    Model answer and what the interviewer listens for

    Detect (find a receiver), Polling (bit lock and symbol or block alignment, exchange training sets), Configuration (agree link width and lane numbering), then L0 (normal operation). Speed changes and error recovery go through Recovery (retrain, including equalization at higher speeds), then back to L0. Power states L0s, L1 and L2 branch from L0; Hot Reset, Disabled and Loopback are other states.

    Listening for: the main path in order; Recovery as the place where speed changes and retraining happen; a trace that shows repeated Recovery entries is a warning sign.

  18. [Troubleshoot] After a suspend test, reads of the NVMe registers return 0xFFFFFFFF. Give two different explanations and how to tell them apart.

    Model answer and what the interviewer listens for

    (1) The device is not reachable: link down, or the device fell off the bus. Config reads also return all ones; the upstream port's Link Status shows the link not active; AER or Downstream Port Containment may have triggered. (2) The device is present but cannot answer memory requests: for example still in D3hot, or Memory Space Enable was cleared and not restored. Memory reads then complete with Unsupported Request, which many root complexes turn into all ones for the CPU. Config reads still work, and the Power Management Control/Status register shows the D-state. Reading configuration space separates the two.

  20. [Concept] How does the Error Information log page relate to a failed command's CQE?

    Model answer and what the interviewer listens for

    The CQE gives the immediate status (Status Code Type and Status Code, plus the Do Not Retry and More bits). When the controller has more detail, it can record an entry in the Error Information log (log page 01h) with an error count, the SQ ID and CID of the failing command, the status, and where available the parameter, LBA and namespace involved. The More bit in the CQE hints that more information is available in the log. The error log is a ring of entries, so it can wrap and lose old entries.

    Listening for: CQE for the immediate result, log for detail; matching by SQ ID and CID; the log can wrap.

    Learn it in: Chapter 44, Chapter 57, Module 39.

  21. [Spec] What does Maximum Data Transfer Size (MDTS) mean, and in what units is it expressed?

    Model answer and what the interviewer listens for

    MDTS, in Identify Controller, is the largest data transfer a single command may request. It is a power of two in units of the minimum memory page size (CAP.MPSMIN): the limit is 2MDTS × the minimum page size. A value of 0 means no limit is reported. For example, MDTS = 5 with a 4 KiB minimum page means 128 KiB. Linux splits larger requests to respect it. Exceeding it typically completes with Invalid Field in Command. Some command sets add their own limits for particular commands; check the specification for the command you use.

    Listening for: the units (not bytes, not LBAs); 0 means no limit; the host splits.

    Learn it in: Chapter 30, Chapter 36.

  22. [Concept] What are ACK and negative acknowledgement (NAK) Data Link Layer Packets (DLLPs), and what happens on a NAK?

    Model answer and what the interviewer listens for

    The Data Link Layer gives each TLP a sequence number and an LCRC. The receiver acknowledges good TLPs with ACK DLLPs (which can cover several TLPs) and reports a bad one with a NAK. The transmitter keeps sent TLPs in a replay buffer until acknowledged; on a NAK, or when the replay timer expires, it retransmits from the oldest unacknowledged TLP. Four replays of the same sequence trigger REPLAY_NUM Rollover and link retraining. These events are reported as correctable errors (Bad TLP, Replay Timer Timeout, REPLAY_NUM Rollover).

    Listening for: sequence number plus LCRC; the replay buffer; correctable reporting; rollover leading to Recovery.

    Learn it in: Chapter 15, Module 16.

Advanced bank

Advanced questions move from "how it works" to "how it breaks and how you prove it". Expect the interviewer to push on corner cases: ordering, splitting, credits, resets, virtualization, and the edges of what the specification guarantees.

  1. [Concept] Which PCIe ordering rules does an NVMe controller rely on so that the host never sees a CQE before the data it describes?

    Model answer and what the interviewer listens for

    For a Read, data and CQE are both posted MWr TLPs from the device; posted writes in the same direction stay in order (when Relaxed Ordering is not set on the later one), so the data is in host memory before the CQE. For a Write command, the controller must have received all the read completions for the data before it can report completion, so ordering is guaranteed by the controller's own logic, not by the link. In the host-to-device direction, a CPU read of a device register cannot pass earlier posted writes, which is why "write then read back" works as a flush of posted MMIO writes.

    Listening for: separating the Read and Write cases; the read-flushes-posted-writes rule; where Relaxed Ordering could be risky.

    Learn it in: Chapter 14, Chapter 51, Module 14.

  2. [Architecture] Should an NVMe controller set Relaxed Ordering on its data writes? On its CQE writes?

    Model answer and what the interviewer listens for

    On data writes, Relaxed Ordering can help on some platforms, because it lets the root complex commit writes to memory out of order and so increases throughput; the data writes do not need to stay in order among themselves. The CQE write must not overtake the data, and the MSI-X write must not overtake the CQE, so those writes must be sent without Relaxed Ordering. Software can stop a function from using Relaxed Ordering with the Enable Relaxed Ordering bit in Device Control, and some platforms clear it because of known root complex problems. Whether it helps depends on the implementation.

    Listening for: which writes can be relaxed and which cannot; the enable bit belongs to system software; platform dependence.

    Learn it in: Chapter 51, Module 14.

  3. [Trace] The SSD sends an MRd for 512 bytes. The root complex returns eight CplD TLPs of 64 bytes each, with decreasing Byte Count values. Is that legal? What fields prove the completions belong together?

    Model answer and what the interviewer listens for

    Yes. A completer may split a read completion into several completions at naturally aligned Read Completion Boundary (RCB) addresses (64 bytes here), as long as each fits in MPS and they return in increasing address order for that request. All eight carry the same Requester ID (0x0100) and Tag as the request. Byte Count gives the remaining bytes including this completion (512, 448, … 64), and Lower Address gives the low address bits of the first byte in each. Analyzers often group them; the tag ties them together.

    Listening for: RCB; Requester ID + Tag as the key; Byte Count meaning "remaining"; in-order return for one request.

    Learn it in: Chapter 52, Module 12, Chapter 13.

  4. [Troubleshoot] How would you tell flow-control credit starvation from a completion timeout in a trace?

    Model answer and what the interviewer listens for

    Credit starvation shows as a transmitter that has TLPs queued but sends nothing of that type because the receiver advertised no credits; UpdateFC DLLPs from the receiver are missing or not increasing, while other traffic types still move. The link is up and healthy, and no request is lost. A Completion Timeout shows as a non-posted request that was sent and ACKed at the Data Link Layer but never answered with a completion carrying that tag; the requester later logs the timeout. Starvation can cause timeouts (completions stuck behind exhausted credits), so the first abnormal event decides which came first.

    Listening for: UpdateFC as the evidence; ACK of the request proving delivery; causal order.

    Learn it in: Chapter 16, Chapter 53, Module 17.

  5. [Performance] When does a device need 10-bit tags? Show the reasoning.

    Model answer and what the interviewer listens for

    Each outstanding non-posted request needs a unique tag. Bytes in flight = bandwidth × round-trip read latency. At Gen5 x4 (about 15 GB/s) with 2 µs read latency, about 30 KB must be outstanding. With 512-byte reads that is about 60 requests, well within 256 8-bit tags. At Gen5 x16 with long latency (a switch, a remote socket) or with small read requests, the need passes 256 and 10-bit tags (up to 768 usable tag values in common descriptions) are needed. Both requester and completer must support it, and software enables it in Device Control 2.

    Listening for: bandwidth-delay product; request size matters; both ends must support and enable it. Confirm exact tag-space numbers in the PCI Express Base Specification.

    Learn it in: Chapter 13, Module 13.

  6. [Troubleshoot] A Gen5 link sometimes comes up at Gen4 after cold boot. Where in the LTSSM would you look and why?

    Model answer and what the interviewer listens for

    The link trains at 2.5 GT/s first and moves to higher speeds through Recovery, including the equalization phases needed at 8 GT/s and above. If equalization at 32 GT/s does not reach an acceptable bit error rate, the ports can fall back to a lower speed. Look at the Recovery.Equalization phases in an LTSSM capture, at the equalization status bits in the Physical Layer 32.0 GT/s extended capability on both ends, at preset requests in the training sets, and at whether the problem follows the slot, the riser or the drive. Temperature and retimers are common factors.

    Listening for: speed change through Recovery; equalization per speed; checking both link partners; swapping hardware to localize.

    Learn it in: Chapter 54, Chapter 9, Module 09.

  7. [Trace] The root port's AER Header Log holds a 4-doubleword header whose first doubleword is 0x2000_0080, from Requester ID 0x0100. The error is Unsupported Request. What failed?

    Model answer and what the interviewer listens for

    The top byte 0x20 gives Fmt = 001 and Type = 00000: a 4-DW Memory Read (MRd64). The Length field is 0x080 = 128 doublewords = 512 bytes. Requester 0x0100 is the SSD, so the SSD issued a 512-byte DMA read that the root complex could not route or did not allow, and the root complex answered with an Unsupported Request completion. Next, read the address in doublewords 2–3 of the header log: an address outside any valid mapping (a stale PRP, an IOMMU-unmapped buffer, a corrupted PRP list) is the usual cause.   8. [Concept] Compare LCRC, ECRC and a Poisoned TLP. Which layer detects each, and what does each protect against?

    Model answer and what the interviewer listens for

    LCRC is a per-link cyclic redundancy check (CRC) added by the Data Link Layer; it detects corruption on one link and is fixed by replay, so the error is correctable. ECRC is an optional end-to-end CRC in the TLP digest, generated by the original requester or completer and checked at the final receiver; it catches corruption inside switches or bridges, where LCRC is regenerated. A Poisoned TLP (EP bit set) is a deliberate marker that the payload is known bad, for example after an uncorrectable memory error upstream; the receiver must not use the data as good. ECRC errors and Poisoned TLPs are uncorrectable (non-fatal by default).

    Listening for: per-hop versus end-to-end; poison as a marker rather than a check; who reports what.

    Learn it in: Chapter 45, Chapter 15, Module 40.

  9. [Spec] Why is the NVMe Abort command called "best effort"?

    Model answer and what the interviewer listens for

    Abort (admin opcode 08h) asks the controller to abort a command identified by SQ ID and CID. The specification lets the controller complete the target command normally, abort it, or report that it could not abort it, and the Abort's own completion tells the host whether the command was aborted. The command may already be in a state (media programming, data transfer) where stopping is unsafe, and the number of concurrent Aborts is limited by the Abort Command Limit in Identify Controller. A host must therefore be ready for the original command to still complete. That is why drivers escalate to a controller reset.

    Listening for: no guarantee; the Abort's own completion; a limit on outstanding Aborts; the escalation that follows.

    Learn it in: Chapter 30, Chapter 44.

  10. [Architecture] Explain how NVMe Autonomous Power State Transitions (APST), PCIe ASPM L1 substates and Latency Tolerance Reporting (LTR) interact.

    Model answer and what the interviewer listens for

    They are three different mechanisms at different layers. APST is an NVMe feature: after a host-specified idle time, the controller moves itself to a lower NVMe power state (possibly non-operational) from a table the host programs; each state has entry and exit latencies in Identify Controller. ASPM puts the PCIe link into L0s or L1, and L1.1/L1.2 substates turn off more of the physical-layer circuitry (PHY) and reference clock; they are enabled by system software in config space. LTR lets the device tell the platform how much latency it can tolerate, which the platform uses (with the L1.2 threshold) to decide whether deep link states are allowed. An I/O arriving after deep idle can pay both the NVMe exit latency and the link exit latency, and bugs often live at their boundary.

    Listening for: three layers kept separate; who enables each; adding up exit latencies; the boundary as a place where bugs hide.

    Learn it in: Chapter 50, Module 42.

  11. [Troubleshoot] A device's DMA write fails. Distinguish an IOMMU fault, an Unsupported Request and a Completer Abort.

    Model answer and what the interviewer listens for

    A DMA write is posted, so no completion returns to the device whatever happens. An IOMMU translation fault is logged by the IOMMU (for example in the kernel log as a DMA remapping fault with the device's requester ID and the faulting address); the write is dropped. Unsupported Request means the receiver did not recognise or support the request (for example an address that decodes nowhere); for a posted request it is logged by the receiver, usually the root port, in AER. Completer Abort means the completer recognised the request but refused it because of an internal condition. For DMA reads, UR and CA come back to the device as completion status. Check the IOMMU log, root port AER, then device AER.

    Listening for: posted versus non-posted changes who sees the error; IOMMU evidence lives outside AER; the order to check.

    Learn it in: Chapter 20, Chapter 45, Module 02.

  12. [Architecture] With Single Root I/O Virtualization (SR-IOV), what does a Virtual Function own and what does it share with the Physical Function?

    Model answer and what the interviewer listens for

    A Virtual Function (VF) has its own Routing ID, its own BAR space (carved out by VF BARs in the PF's SR-IOV capability), its own MSI-X table and, in NVMe, its own controller with queues, doorbells and the namespaces attached to it. It shares the physical link, the Physical Function's (PF) link-level and many device-level resources, and the NVM subsystem behind it. In NVMe, VFs are usually secondary controllers whose queue and interrupt resources are assigned through Virtualization Management by the primary controller. An error in shared hardware can affect every VF; FLR of one VF must not.

    Listening for: separate Routing ID and BARs; shared link; primary/secondary controller resource assignment; isolation expectations.

    Learn it in: Chapter 56, Module 52.

  13. [Trace] A trace shows a Read command fetched, all data MWr TLPs delivered and acknowledged, but no CQE write. List hypotheses in the order you would test them.

  15. [Coding] Write a function that builds the PRP list for a transfer, handling a PRP list that itself crosses a page (chaining).

    Model answer and what the interviewer listens for 
    PAGE = 4096
ENTRIES = PAGE // 8          # 512 eight-byte entries per list page

def build_prps(buf, length, alloc_list_page):
    """Return (prp1, prp2, list_pages) for a PRP-described transfer.
    alloc_list_page() returns the address of a fresh, page-aligned list page."""
    pages = [buf]
    nxt = (buf // PAGE + 1) * PAGE
    remaining = length - min(length, PAGE - buf % PAGE)
    while remaining > 0:
        pages.append(nxt); nxt += PAGE; remaining -= PAGE
    if len(pages) <= 2:
        return pages[0], (pages[1] if len(pages) == 2 else 0), {}
    rest = pages[1:]
    lists = {}
    cur = alloc_list_page(); prp2 = cur; lists[cur] = []
    while rest:
        if len(rest) > ENTRIES:            # need to chain: last slot points on
            lists[cur] += rest[:ENTRIES - 1]
            rest = rest[ENTRIES - 1:]
            new = alloc_list_page()
            lists[cur].append(new)
            cur = new; lists[cur] = []
        else:
            lists[cur] += rest; rest = []
    return pages[0], prp2, lists

counter = iter(range(0x1_5000_0000, 0x1_6000_0000, PAGE))
p1, p2, lists = build_prps(0x2_0000_0000, 4 * 1024 * 1024, lambda: next(counter))
print(hex(p1), hex(p2), {hex(k): len(v) for k, v in lists.items()})

    A 4 MiB aligned transfer touches 1,024 pages: PRP1 plus 1,023 list entries, which need two list pages (511 data entries plus a chain pointer, then 512). Real code must also respect MDTS, use a list page whose start is the PRP2 address (PRP2 may carry an offset only under rules you must check in the specification), and map every page through the DMA API.

    Listening for: last entry used as a chain pointer only when more entries remain; zero offsets in list entries; MDTS; DMA mapping.

    Learn it in: Chapter 36, Chapter 38, Module 34.

  16. [Performance] A 64-core host and an SSD that supports 128 I/O queues. How many queues and interrupt vectors would you create, and what is the tradeoff with interrupt coalescing?

    Model answer and what the interviewer listens for

    Usually one I/O queue pair per CPU (64), each with its own MSI-X vector affined to that CPU, so submissions need no locks and completions arrive on the submitting core. More queues than CPUs only helps for separate classes (for example polled queues or read/write separation). Interrupt coalescing (the Interrupt Coalescing feature, aggregation threshold and time) cuts interrupt rate and CPU cost at high IOPS but adds latency at low queue depth. Linux leaves it off by default; enabling it is a workload decision, measured with latency percentiles, not averages.

    Listening for: per-core queues; vector affinity; coalescing as a latency-versus-CPU tradeoff; percentiles.

    Learn it in: Chapter 42, Chapter 27, Performance Engineering.

  17. [Concept] Compare Flush, Force Unit Access (FUA) and the Volatile Write Cache feature. What does an application get from each after power loss?

    Model answer and what the interviewer listens for

    With a volatile write cache enabled, a successful Write may mean data is only in the cache. Flush (opcode 00h) commits all data in the cache (for that namespace, or all namespaces depending on NSID) to non-volatile media before it completes. FUA on a Write makes that one write durable before it completes. With the cache disabled, or with a drive that has power-loss protection and reports no volatile write cache, completion already means durable. Linux turns fsync into Flush or FUA depending on what the device reports. The Volatile Write Cache field in Identify Controller says whether a cache is present.

    Listening for: completion does not equal durable when a cache is present; per-command FUA versus a global Flush; the host reads the cache capability.

    Learn it in: Chapter 34, Chapter 33, Module 32.

  18. [Spec] What can a host assume about the data read from LBAs after a Dataset Management deallocate?

    Model answer and what the interviewer listens for

    Only what the controller reports. The Dataset Management command (opcode 09h) with the Deallocate attribute is a hint unless the controller reports stronger behaviour. The namespace's reported deallocate behaviour says whether deallocated blocks read back as zeroes, as all ones, or as not reported. Some features (such as Write Zeroes with deallocate, or a guaranteed-zero read behaviour) give stronger guarantees. A file system that assumes zeroes without checking can expose stale data or report wrong checksums.

    Listening for: hint versus guarantee; checking the reported read behaviour; a real consequence of getting it wrong.

    Learn it in: Chapter 35, Module 33.

  19. [Concept] What is a fused operation, and how does Compare and Write work in NVMe?

    Model answer and what the interviewer listens for

    A fused operation joins two adjacent commands in the same SQ, marked by the FUSE field in Command Dword 0 (first and second command), so they execute as one atomic unit. Compare and Write is a Compare followed by a Write: if the compare matches, the write happens; if not, the write is aborted with a fused-operation status. It gives an atomic test-and-set on blocks, useful for clustered locking. Support is optional and advertised in Identify Controller; the two commands must be adjacent and the host must ring the doorbell so both are visible.

    Listening for: adjacency in one SQ; atomicity; optional support; what happens on mismatch.

    Learn it in: Chapter 29, Chapter 31.

  20. [Architecture] Why does the Zoned Namespace (ZNS) Command Set change host software, and what does Zone Append solve?

    Model answer and what the interviewer listens for

    In a zoned namespace, each zone must be written sequentially at its write pointer and reset before reuse. That moves data placement and garbage collection responsibility partly to the host, which reduces device write amplification and over-provisioning but means the host must track zone state and never write out of order. With many writers to one zone, ordinary Writes require the host to serialise so each write lands at the write pointer. Zone Append lets the host send writes to the zone and have the controller choose the LBA, returning it in the completion, so several appends can be in flight at once.

    Listening for: the sequential write rule; who now owns placement; the concurrency problem and how Zone Append fixes it.

    Learn it in: Chapter 59, Module 44.

  21. [Architecture] How does an NVMe over Fabrics (NVMe-oF) capsule differ from an SQE in host memory on PCIe?

    Model answer and what the interviewer listens for

    On PCIe, the SQE sits in host memory and the controller pulls it with DMA after a doorbell. On fabrics there is no shared memory, so the host sends a command capsule (the 64-byte SQE plus optional in-capsule data) as a message over the transport (TCP, RDMA, Fibre Channel), and the controller returns a response capsule containing the CQE. Doorbells and the controller register set are replaced by transport messages and Fabrics commands (Connect, Property Get/Set). Data uses SGLs that refer to transport-specific buffers or in-capsule data.

    Listening for: push versus pull; no doorbells; property commands replacing MMIO; SGL requirement.

    Learn it in: Chapter 65, Chapter 66, Chapter 67.

  22. [Spec] May an NVMe controller complete commands in a different order from the order they were submitted? What must the host do about it?

    Model answer and what the interviewer listens for

    Yes. Commands in an SQ are fetched in order, but there are no ordering guarantees between their completions unless a specific mechanism (such as fused operations) says otherwise; a short read may complete before a long write submitted earlier. The host must match completions by CID and SQ ID, not by position, and must enforce its own ordering for dependent operations (for example by waiting for one completion before submitting the next, or by using Flush or FUA for durability).

    Listening for: fetch order versus completion order; CID matching; the host's responsibility for dependencies.

    Learn it in: Chapter 25, Chapter 41.

Senior bank

Senior questions are open-ended on purpose. There is rarely one right answer; the interviewer is watching how you structure an investigation, how you rank hypotheses, which experiment you choose to separate them, and whether you say what you do not know. Give yourself five minutes per question.

  1. [Troubleshoot] A Gen5 SSD runs clean at room temperature but logs correctable Receiver Errors, then link Recovery events, and finally NVMe timeouts when the chassis is hot and under sustained writes. Plan the investigation.

    Model answer and what the interviewer listens for

    The sequence says the physical layer degrades first and the NVMe symptoms come last, so the NVMe timeouts are probably consequences. Plan:

    1. Establish the cascade with timestamps: AER correctable counts per port, LTSSM Recovery count (from an analyzer or a link monitor), NVMe timeouts. Confirm the order with an analyzer if possible.
    2. Separate temperature from load: heat the system with the drive idle; load it while cool. Use the drive's composite temperature and the platform's thermal sensors.
    3. Localise by swapping: another drive in the same slot, the same drive in another slot, with and without riser or retimer. The error follows whichever part is the cause.
    4. Compare margins: lane margining at the receiver, where supported, at cool and hot temperatures, on both link partners.
    5. Check equalization results and preset choices at 32 GT/s on both ends.
    6. Workaround to confirm the mechanism: force Gen4 and show the NVMe timeouts disappear under the same heat and load.

    Listening for: the cascade direction; separating variables; swapping to localise; a confirming experiment; not starting with firmware.

    Learn it in: Chapter 54, Chapter 47, Debugging Methodology, Failure Library.

  2. [Troubleshoot] The root port logs a Completion Timeout and then the NVMe driver times out I/O and resets the controller. The platform team says "the SSD stopped responding". How do you decide?

    Model answer and what the interviewer listens for

    A root port Completion Timeout means a CPU-initiated non-posted request to the SSD, typically an MMIO read of a controller register, got no completion. That can be because the SSD did not answer, the request never reached it, or the completion was lost on the way back. Evidence that separates them: a trace showing the MRd reaching the SSD (and ACKed by the SSD's Data Link Layer) with no CplD returned points at the SSD; no ACK points at the link; a link-down or Surprise Down event points at the link or power. Also check what the driver was reading at that moment: if the controller was mid-reset or in a power state transition, the read itself may have been inappropriate. Then check whether the I/O timeouts started before the CTO (in which case the CTO is a symptom of recovery).

    Listening for: the requester detects it; the request path and the completion path are separate; the order of events; challenging the framing politely.

    Learn it in: Chapter 46, Chapter 47, Scenario Interviews.

  3. [Troubleshoot] A customer reports silent data corruption: an application checksum mismatches once a week. No errors anywhere. How do you approach it?

    Model answer and what the interviewer listens for

    First characterise the corruption: which bytes, how many, aligned to what (512, 4 KiB, 64-byte RCB boundary, page), stale data versus garbage versus shifted data. The pattern points to a layer: stale whole blocks suggest ordering, caching or a lost write; a 4 KiB page from elsewhere suggests a wrong PRP entry or IOMMU mapping; small bit flips suggest memory or the data path. Then add detection closer to the source: end-to-end data protection (Protection Information) if the namespace supports it, a write-read-verify test with known patterns that records LBA and buffer address, and IOMMU strict mode. Rule out host memory (ECC logs) and the file system. Keep the corrupted block and the expected block; a diff is evidence.

    Listening for: characterise before hypothesising; mapping patterns to mechanisms; adding instrumentation; preserving evidence.

    Learn it in: Chapter 36, Chapter 20, Evidence-Based Debugging.

  4. [Trace] How do you prove a lost interrupt rather than a lost completion?

    Model answer and what the interviewer listens for

    Lost completion: no CQE MWr to the CQ for that CID, and host memory at that CQ slot still has the old phase. Lost interrupt: the CQE MWr is present (with the expected phase), but no MSI-X MWr follows, or one follows to an address or data that does not match the vector's current table entry, or the vector is masked so the device sets the Pending Bit Array (PBA) bit instead. Linux evidence: the driver's timeout handler finds the completion already in the CQ ("completion polled" style message); /proc/interrupts counts for that vector stop increasing. Device-side evidence: read the MSI-X table entry and PBA through BAR space.

    Listening for: using host memory and the analyzer together; the PBA; matching interrupt address/data to the table.

    Learn it in: Chapter 43, Module 19, Final Capstone.

  5. [Troubleshoot] After a firmware update and activation, the SSD sometimes does not come back. What do you investigate?

    Model answer and what the interviewer listens for

    Establish which activation path was used (the Commit Action of Firmware Commit, opcode 10h): activation at next reset, immediate activation without reset, or replace-and-activate. Each implies a different reset (Controller Reset, NVM Subsystem Reset, or a PCIe-level reset), and some cause a link down. Check: did the link retrain (LTSSM, upstream port Link Status)? Did the host restore config space? Did CSTS.RDY come back within CAP.TO, and was CSTS "Processing Paused" set during activation? What do the Firmware Slot Information log and the persistent event log say? Is the new firmware's maximum activation time longer than the host waits? A race between the host's reset path and the device's activation time is a common cause.

    Listening for: the reset type depends on commit action; link versus controller recovery; timing budgets; the logs that record activation.

    Learn it in: Chapter 48, Chapter 49, Chapter 30.

  6. [Architecture] Firmware had a bug where transfers whose PRP list crossed a page were corrupted. Design the regression test.

    Model answer and what the interviewer listens for

    Target the mechanism, not the original reproduction. Parameters: transfer sizes that need exactly 512, 513 and 1,024+ list entries (forcing chaining); PRP1 offsets of 0, 512, 4,092 bytes; Read and Write; buffers placed so list pages sit at the end of a page. Verify by writing unique per-sector patterns (LBA and generation stamped into each 512-byte block) and reading back into a buffer pre-filled with a poison pattern, so missing or misplaced data is visible. Run with the IOMMU in strict mode so out-of-bounds DMA faults. Include boundary cases near MDTS. Pass criteria: zero mismatches and zero IOMMU faults over N iterations; record controller firmware revision and the test's PRP layouts in the log.

    Listening for: coverage of the boundary; self-describing data patterns; poison-prefilled buffers; IOMMU as a detector; reproducible logs.

    Learn it in: Chapter 38, Validation Engineering, Bug Report Training.

  7. [Troubleshoot] The analyzer shows bursts of NAKs and replays, but the host's AER log is empty. Why might that be, and does it matter?

    Model answer and what the interviewer listens for

    Several explanations: correctable errors are masked in the AER Correctable Error Mask; AER is not enabled or is handled by platform firmware ("firmware-first"), so the OS never sees it; the kernel rate-limits correctable messages; the errors are detected by the device (on traffic the host sends) and the device does not report them or its error reporting enables are off; or the analyzer's interposer is causing them. It matters: replays add latency and can precede rollover and Recovery. Check the mask and control registers on both ends, the platform's error handling mode, and repeat without the interposer if possible.

    Listening for: masks, enables, firmware-first; which side detected the error; the analyzer as a possible cause.

    Learn it in: Chapter 46, Chapter 15, Analyzer Training.

  8. [Concept] How do you know the protocol analyzer is not changing the behaviour you are trying to observe?

    Model answer and what the interviewer listens for

    An interposer adds loss, reflections and sometimes retiming, which can change equalization results and error rates, especially at Gen5 and above. Checks: compare error counters and link speed and width with and without the interposer; check the analyzer's own error indications (lost sync, recording gaps); confirm the failure still reproduces without it (using only host-side evidence); use the analyzer's recommended calibration and cable lengths. If the bug disappears with the analyzer attached, that is a clue about timing or signal integrity, not proof that the bug is gone.

    Listening for: the observer effect named; an A/B comparison; using host-side evidence to cross-check.

    Learn it in: Analyzer Training, Synthetic vs Real Traces.

  9. [Performance] 4 KiB random reads plateau at 600,000 IOPS with eight jobs, and the drive is rated for 1.2 million. CPU use is high. Where do you look?

    Model answer and what the interviewer listens for

    High CPU suggests the host is the limit. Check: are eight jobs mapped to eight different CPUs and eight different queues (or contending on fewer)? Is queue depth per job enough (Little's Law with the measured latency)? Are interrupts landing on the submitting cores? Is the I/O engine efficient (io_uring with polling versus synchronous)? Are IOMMU translations costly (strict mode, invalidation per I/O)? Profile with perf. On the device side, check that the link is at full speed and width, that the rating assumed a different queue depth or preconditioned state, and that the drive is not thermally throttled. Then compare per-I/O latency at the device (analyzer: doorbell to CQE) with application latency: the gap is host overhead.

    Listening for: using the CPU clue; Little's Law; mapping jobs to queues and interrupts; separating device time from host time.

    Learn it in: Performance Engineering, Module 53, Chapter 42.

  11. [Coding] You review a driver patch that writes the SQE into the queue and then rings the doorbell. What memory-ordering question do you ask, and why?

    Model answer and what the interviewer listens for

    "Is the SQE guaranteed to be visible to a device DMA read before the doorbell write reaches the device?" The SQE store goes to cached host memory; the doorbell is an MMIO write. On some architectures the CPU can reorder them unless there is a write barrier. In Linux, writel() is defined to order earlier normal memory writes before the MMIO write, while writel_relaxed() does not; a patch that switches to the relaxed accessor or writes the doorbell through a different path needs an explicit barrier (such as dma_wmb() or wmb() as appropriate). Similarly, when reading a CQE, the driver must check the phase bit before reading the rest of the entry, with a read barrier in between.

    Listening for: CPU ordering, not PCIe ordering; knowing which accessor implies a barrier; the matching rule on the completion side.

    Learn it in: Chapter 28, Programming Labs, Module 27.

  12. [Architecture] When would you let several SQs share one CQ, and what does it cost?

    Model answer and what the interviewer listens for

    Sharing helps when you want separate submission paths (for example by priority with weighted round robin arbitration, or by command type) but one completion path on one CPU, or when the controller limits the number of CQs or interrupt vectors. Costs: the CQ must be sized for the sum of outstanding commands on all its SQs, or the controller stalls when it is full; completions from one SQ can delay processing of another's; the host must use the SQ ID in the CQE to route completions; and arbitration fairness becomes visible in latency.

    Listening for: sizing the CQ for the sum; routing by SQ ID; arbitration consequences.

    Learn it in: Chapter 27, Chapter 25.

  13. [Troubleshoot] CSTS.CFS is set. What do you collect before resetting, and why does the order matter?

    Model answer and what the interviewer listens for

    A reset can erase volatile evidence. Before resetting: snapshot the controller registers (CAP, CC, CSTS and so on); host-side queue state (SQ and CQ contents and pointers, outstanding CIDs, last doorbell values); kernel log with timestamps; PCIe config space and AER registers for the device and upstream port. If the admin queue still works, read the Error Information log, SMART/Health log, and the telemetry logs (host-initiated telemetry, with a controller-initiated telemetry indication if present) and the Persistent Event log if supported. Then reset. Note that a controller in fatal state may not process admin commands, in which case record that the attempt failed.

    Listening for: evidence before recovery; knowing which logs survive a reset; recording failed attempts as evidence.

    Learn it in: Chapter 44, Chapter 48, Root Cause and Forensic Reporting.

  14. [Architecture] What must a host handle for surprise removal of an NVMe SSD, and where does Downstream Port Containment (DPC) fit?

    Model answer and what the interviewer listens for

    On surprise removal, the link goes down, MMIO reads return all ones (or fault), and outstanding DMA stops. The driver must detect removal (all-ones reads, hot-plug events, link-down notifications), fail outstanding I/O without hanging, avoid touching freed queues, and tear down cleanly. DPC lets a downstream port contain an uncorrectable error by taking the link down so errors do not propagate upstream, and software then recovers the port. DPC turns a "fatal" error into a controlled removal and re-insertion. The host must also tolerate Completion Timeouts during removal, since in-flight reads may never complete.

    Listening for: all-ones handling; no hang; containment versus recovery; expected noise during removal.

    Learn it in: Chapter 55, Chapter 49, Module 40.

  15. [Architecture] A customer insists "the SSD caused the AER error" because the error names its address. How do you explain why that might not be true?

    Model answer and what the interviewer listens for

    The logged location tells you who detected or reported the error, not who caused it. A Receiver Error at the SSD means the SSD's receiver saw bad signal; the cause could be the host transmitter, the slot, a riser or the board. A Completion Timeout at the SSD means the SSD's request was not answered; the root complex or the IOMMU could be at fault. An Unsupported Request reported by the root port with the SSD as requester means the SSD sent a bad address, but that address may have come from a host driver bug (bad PRP). The way to settle it is the first abnormal event in a trace and an A/B swap.

    Listening for: "detector is not cause" stated plainly; examples in both directions; an experiment to settle it; a respectful tone.

    Learn it in: Chapter 47, Communication and Design Review.

  16. [Architecture] Write a validation plan outline for the NVMe 2.4 rate-limiting feature on a drive with several controllers.

    Model answer and what the interviewer listens for

    Start from the specification text (NVM Express Base Specification 2.4 and the Revision Changes document) to list the configurable limits, their units and which controller or entity they apply to; do not assume field layouts. Then: (1) functional: limits accepted and reported back, invalid values rejected with the documented status; (2) enforcement accuracy: measured bandwidth and IOPS per controller versus configured caps, over different I/O sizes and mixes, with tolerance stated; (3) isolation: one controller saturating does not push another below its guarantee; (4) dynamics: changing limits at runtime, during I/O; (5) persistence across resets and power cycles as specified; (6) interaction with power states, thermal throttling and SR-IOV; (7) negative: a host that ignores limits sees them enforced, not errors. Measure with external instruments (analyzer throughput) as well as host tools.

    Listening for: starting from the specification text; accuracy with tolerances; isolation and dynamics; independent measurement; honesty about unverified field details.

    Learn it in: 2026 NVMe 2.4 Updates, Validation Engineering, Module 60.

  17. [Trace] Two outstanding Read commands on the same SQ carry the same CID. One completes, and the host later times out. Whose bug is it and what does the controller do?

    Model answer and what the interviewer listens for

    The host's: the CID must be unique among outstanding commands in that SQ. The controller is not required to detect it in all cases. A controller that checks may fail the second command with Command ID Conflict; one that does not may execute both and post two completions with the same CID, and the host will match both to one request and lose the other. The trace shows two SQE fetches with identical CDW0 CID fields while the first is still outstanding. Fix the host's CID allocator (typically a CID reused after a timeout or abort before the original truly completed).

    Listening for: uniqueness per SQ among outstanding commands; the controller may or may not catch it; the classic reuse-after-timeout cause.

    Learn it in: Chapter 29, Chapter 41, Module 28.

  18. [Trace] In a capture, one 4 KiB Read takes 40 µs from doorbell to CQE while its neighbours take 12 µs. How do you tell whether the link or the device added the time?

    Model answer and what the interviewer listens for

    Break the 40 µs into segments: doorbell to SQE fetch MRd; MRd to CplD; CplD to first data MWr (device internal time, mostly media); first to last data MWr; last data to CQE; CQE to MSI-X. Then look for link events inside each segment: NAKs and replays, Recovery or electrical idle, missing UpdateFC. If the extra time sits between CplD and the first data MWr with a clean link, it is device-internal (media read retry, garbage collection, read disturb handling). If it sits in data transfer with replays, it is the link. Compare with neighbours to see which segment grew.

    Listening for: segmenting the timeline; link events as evidence; comparing with normal commands.

    Learn it in: Chapter 41, Trace Analysis Laboratory, Module 38.

  19. [Spec] You and a firmware engineer read the same paragraph of the NVMe specification differently. How do you resolve it?

    Model answer and what the interviewer listens for

    Quote the exact text and revision you are each reading; check definitions and conventions sections (a word like "shall" or "command completion" may be defined); look for related normative statements elsewhere (state diagrams, figure notes, status-code rules); check the Revision Changes document and published errata or Engineering Change Notices for clarifications; check what the reference behaviour (for example the Linux driver and other vendors' devices) does, labelled as practice, not specification.   20. [Troubleshoot] Describe Linux's NVMe recovery escalation and what evidence each step destroys.

    Model answer and what the interviewer listens for

    Timeout → check CQ for a missed completion → Abort (admin) → controller reset (CC.EN cleared; all queues deleted and recreated, outstanding commands requeued) → if the controller does not come back, the device may be removed; platform-level PCIe recovery (AER recovery, DPC, secondary bus reset) may also happen around it. Each step destroys evidence: the reset clears controller state and queue contents; a PCIe-level reset clears non-sticky AER registers and possibly device logs held in volatile memory. Capture register snapshots and logs at the first timeout if you can (tracing, debug hooks), and record which steps happened in what order from the kernel log.

  21. [Troubleshoot] What is the minimum evidence you require before assigning a bug to the SSD firmware team?

    Model answer and what the interviewer listens for

    A reproduction recipe with environment details; the first abnormal event and evidence that it is device-side (for example a correctly formed command and doorbell, received and acknowledged, followed by a wrong or missing device response); evidence that the link was healthy around that event; the device's own logs (error log, SMART, telemetry if available); and ideally an A/B result showing the failure follows the drive or the firmware revision, not the host.   22. [Performance] IOMMU passthrough versus translated (strict or lazy) mode for NVMe: what changes for performance and for debugging?

    Model answer and what the interviewer listens for

    Passthrough (identity mapping) has the least overhead, but the device can reach any host memory, so a bad PRP corrupts memory silently. Translated strict mode unmaps and invalidates on every I/O completion: most protective, catches out-of-bounds DMA immediately as an IOMMU fault, but costs CPU and invalidation latency at high IOPS. Lazy mode batches invalidations: cheaper, with a short window where stale mappings still work. For debugging data corruption or DMA bugs, strict mode turns silent corruption into a logged fault with an address and requester ID. In traces, addresses are I/O virtual addresses, not physical addresses.

    Listening for: the safety-versus-cost tradeoff; strict mode as a debugging tool; IOVA in traces.

Principal bank

Principal questions are about architecture, debugging strategy at fleet or program scale, and judgement under uncertainty. A principal answer names options, states what each one costs, picks one with a reason, and says what evidence would change the decision. Twenty minutes per question is normal in a real loop; practise with ten.

  1. [Architecture] Design the quality-of-service architecture for a multi-tenant SSD that serves eight virtual machines through SR-IOV. Use NVMe 2.4 capabilities where they help.

    Model answer and what the interviewer listens for

    Layers: (1) isolation of control: one secondary controller per tenant via SR-IOV VFs, each with its own queues, interrupts and namespaces; (2) isolation of capacity: namespaces sized per tenant, and possibly separate endurance groups or NVM sets where supported to separate media; (3) isolation of performance: controller-enforced rate limits (the 2.4 rate-limiting capability) for bandwidth and IOPS, plus device-internal scheduling; host-side throttling as a backstop, not the main mechanism; (4) noisy neighbour defence: write-heavy tenants drive garbage collection that hurts everyone, so include media-level separation or write-rate caps; (5) observability per tenant: per-controller statistics, latency histograms. Tradeoffs: hard caps waste idle capacity; work-conserving schedulers risk interference; media separation reduces flexibility. Validate isolation under adversarial workloads. Confirm what 2.4 rate limiting can express in the specification before relying on it.

    Listening for: control, capacity, performance and media separated; enforcement in the device; the work-conserving tradeoff; adversarial validation; honesty about the new feature's exact scope.

    Learn it in: Chapter 56, 2026 NVMe 2.4 Updates, Module 59.

  2. [Architecture] Walk through live migration of a PCIe Exported NVM Subsystem (NVMe 2.4). What state must move, and what can go wrong?

    Model answer and what the interviewer listens for

    As reported for 2.4: create an Exported NVM Subsystem on the destination; recreate the exported controller and namespaces with matching identifiers; apply the same configuration template (identified by a 128-bit universally unique identifier (UUID)) so features and behaviours match; capture the source's runtime state; transfer and apply it; migrate the virtual machine; clean up the source. State that matters: identifiers (so the guest driver sees "the same" device), feature settings, queue configuration and in-flight commands, asynchronous event state, and data, which must already be consistent (shared or replicated storage). Risks: identifier collisions; in-flight I/O lost or duplicated at cutover; differences between source and destination firmware; validating that the destination is really in the expected state (the TEE Device Interface Security Protocol (TDISP) information package can support this); timing of the blackout. The exact commands and structures must be read in the Base 2.4 specification.

    Listening for: identity, configuration, runtime state and data as separate concerns; in-flight I/O at cutover; validation of destination state; not inventing opcodes.

    Learn it in: 2026 NVMe 2.4 Updates, Module 60.

  3. [Architecture] Design the observability strategy for a fleet of 100,000 NVMe SSDs. What do you collect, how often, and how do you turn it into action?

    Model answer and what the interviewer listens for

    Signals: SMART/Health (temperature, percentage used, media errors, critical warnings), error log counts, AER correctable and uncorrectable counters per port, link speed and width changes, latency histograms per device (not averages), NVMe timeouts and resets from kernel logs, firmware revision, telemetry logs on demand. Cadence: cheap counters every few minutes; logs on events; heavy telemetry only when triggered. Action: baselines per model and firmware; anomaly detection on rates and changes (a jump in correctable errors after a firmware rollout); cohort analysis by slot, platform and firmware; automated ticket with an evidence bundle. Costs: storage, privacy (no user data), and the risk of alert fatigue. A good test: can you answer "did this firmware change the error rate?" within a day?

    Listening for: histograms over averages; cohort comparison; event-triggered heavy collection; an outcome-based test of the system.

    Learn it in: Chapter 57, Automated Trace Analysis, Final Project.

  4. [Architecture] What changes for trace analysis and debugging when links move to PCIe 6.x FLIT mode with PAM4 signalling?

    Model answer and what the interviewer listens for

    PAM4 raises the raw bit error rate, so lightweight forward error correction (FEC) and a CRC protect fixed-size FLITs; the Data Link Layer's acknowledgement and replay work at FLIT granularity. For analysis: errors you used to see as LCRC failures may now be corrected silently by FEC, so error counters and FEC statistics become key health signals; TLPs are packed into FLITs, so "one packet per row" views are reconstructed by the analyzer; latency includes FEC decode; and capturing at 64 GT/s stresses interposers. Higher-level NVMe analysis (commands, queues, completions) is unchanged. Treat details as revision-specific: read the PCI Express Base Specification 6.x/7.0 FLIT-mode sections.

    Listening for: FEC hiding errors; FLIT framing changing analyzer views; NVMe logic unchanged; version labelling.

    Learn it in: Chapter 6, Module 07.

  5. [Architecture] For a new storage tier, how do you choose between local NVMe over PCIe, NVMe/TCP and NVMe/RDMA?

    Model answer and what the interviewer listens for

    Criteria: latency budget (local PCIe lowest; RDMA adds a few microseconds; TCP more, with more CPU unless offloaded); sharing and disaggregation needs (fabrics allow pooling and independent scaling of compute and storage); network operations (RDMA needs a lossless or carefully configured network; TCP runs on any IP network); CPU cost per I/O; failure domains (a network partition versus a dead drive); security (in-band authentication and TLS for TCP); team skills and tooling. Typical outcome: local for latency-critical single-host workloads; TCP for broad disaggregation; RDMA where both low latency and disaggregation justify the network investment. State what measurement would change the choice.

    Listening for: multiple dimensions; operational cost, not just latency; a decision with a reversal condition.

    Learn it in: Chapter 65, Chapter 66, Chapter 67, Chapter 68.

  6. [Architecture] NVMe 2.4 updates asymmetric key exchange to prepare for post-quantum cryptography. Where does that sit architecturally and what are the consequences?

    Model answer and what the interviewer listens for

    It sits in the security and authentication framework (in-band authentication, secure channel establishment, and related security protocols), not in the I/O data path, so Read and Write traffic is unchanged. Consequences: larger keys and signatures (ML-KEM, ML-DSA, SLH-DSA per NIST FIPS 203/204/205) mean bigger messages and possibly more computation at connection or authentication time; firmware and host libraries need updates; interoperability during transition requires negotiation and fallback policy (hybrid schemes are common practice elsewhere, but check what the specification defines); validation must cover negotiation failure paths. Exact algorithm identifiers and message formats must be read in the 2.4 specifications.

    Listening for: control path, not data path; size and time cost; transition and negotiation; no invented field details.

    Learn it in: 2026 NVMe 2.4 Updates, Module 60.

  7. [Architecture] Should your organisation build or buy an automated forensic analysis tool for NVMe/PCIe traces? How would you decide whether to trust its root-cause output?

    Model answer and what the interviewer listens for

    Buy when commercial analyzer software already decodes and correlates what you need; build the layer that encodes your organisation's knowledge (failure signatures, platform quirks, report formats), usually on top of exported trace data. Trust comes from: every conclusion linked to the evidence rows that support it; a labelled corpus of past incidents used as a regression suite (measure precision and recall of its first-abnormal-event detection); explicit confidence levels; a human reviewer for anything that leaves the team. A tool that cannot show its evidence should not be trusted with a root cause.

    Listening for: decomposition into commodity and differentiating parts; evaluation with a labelled corpus; evidence links; human review.

    Learn it in: Automated Trace Analysis, AI + NVMe Protocol Analysis, Final Project.

  8. [Spec] Your driver must support controllers from NVMe 1.3 to 2.4. Do you branch on the Version register?

    Model answer and what the interviewer listens for

    Mostly no. Prefer capability discovery: Identify fields, supported log pages, feature support, CAP bits, Commands Supported and Effects log. The Version register tells you what the controller claims to comply with, which helps interpret fields whose meaning changed and decide whether a field is defined at all, but vendors implement optional features unevenly and sometimes report a version with gaps. Use the version as a guard ("this field is not defined before revision X, so ignore it"), and capability bits as the switch. Keep a quirks table for known broken devices, with evidence for each entry.

    Listening for: capability over version; version as a guard for field interpretation; quirks with evidence.

    Learn it in: Chapter 22, Chapter 24, Specification Reading School.

  9. [Architecture] A product team wants the deepest power states for battery life, but a cloud team has a tail-latency service-level objective. How do you set policy, and how do the NVMe 2.4 idle I/O exit latency limits help?

    Model answer and what the interviewer listens for

    Separate policies by deployment: laptops enable APST to non-operational states and ASPM L1.2; servers cap allowed exit latency. Mechanisms: Linux's maximum allowed power-state latency parameter filters which APST states are used; ASPM policy controls link states; LTR tells the platform the device's tolerance. The 2.4 idle I/O exit latency limits let the host state the latency thresholds that must be maintained, so the device can choose states within that budget instead of the host guessing from a static table. Validate by measuring P99.9 latency after idle gaps of increasing length and by measuring idle power: the policy is a curve, not a switch.

    Listening for: per-deployment policy; the mechanisms at each layer; the new feature's role stated without invented details; measuring both sides of the tradeoff.

    Learn it in: Chapter 50, 2026 NVMe 2.4 Updates, Module 42.

  10. [Architecture] Compare error-containment philosophies: reset quickly, contain with DPC, or fail the device. When is each right?

    Model answer and what the interviewer listens for

    Reset quickly: lowest disruption for transient problems; risk of hiding a growing fault and destroying evidence. Contain with DPC: stops error propagation (for example poisoned data or a misbehaving device flooding the fabric) and gives software a clean recovery point; costs a link down and needs software support for recovery. Fail the device: right when integrity is in doubt (repeated uncorrectable errors, data integrity failures), for redundant systems where losing one device is cheaper than risking corrupted data. A principal sets thresholds (rate of resets per hour, kinds of errors) and makes sure evidence is captured before each step.

    Listening for: blast radius; integrity versus availability; thresholds and evidence capture; dependence on redundancy.

    Learn it in: Chapter 55, Module 40, Module 41.

  11. [Architecture] You are asked to define "done" for validating a new NVMe controller. What does your coverage model look like?

    Model answer and what the interviewer listens for

    A matrix by layer and dimension. Layers: PCIe physical (speeds, widths, equalization, margins), link (replay, flow control), transaction (TLP types, sizes, alignment, ordering, tags), configuration (capabilities, BARs, MSI-X), NVMe registers and initialisation, queues (sizes, wrap, full, shared CQs), commands (every supported opcode, every field, invalid values), data pointers (PRP and SGL boundaries), errors (every reportable error path, injected), reset and power (every reset type, every power state transition, under I/O), features (each optional feature claimed in Identify), performance (with stated tolerances), interoperability (hosts, kernels, platforms). Done means: every cell has a test, every claimed capability is checked against behaviour, and all known bugs have regression tests. Measure functional coverage, not test count.

    Listening for: structured coverage; testing what the device claims; error and reset paths, not just happy paths; a measurable criterion.

    Learn it in: Validation Engineering, Module 54.

  12. [Architecture] Design the on-device debug and telemetry architecture for an enterprise SSD so field failures can be root-caused without a protocol analyzer.

    Model answer and what the interviewer listens for

    Use standard mechanisms first: Error Information log, SMART/Health, Persistent Event log (power cycles, resets, firmware changes, thermal events, with timestamps), and telemetry log pages (host-initiated and controller-initiated) for vendor-specific internal state. Inside: a ring buffer of recent command events (opcode, CID, SQ, timestamps per phase, status), link events (Recovery entries, speed changes, error counts), power state transitions, and reset causes, kept in memory that survives a controller reset and is dumped to non-volatile storage on fatal errors. Design for privacy (no user data), bounded size, versioned formats with a decoder, and a timestamp that can be aligned with host time (the Timestamp feature). Validate by injecting known failures and checking the telemetry explains them.

    Listening for: standard logs first; what survives resets; time alignment; privacy; validation of the telemetry itself.

    Learn it in: Chapter 57, Chapter 44, Module 43.

  13. [Troubleshoot] A fleet issue appears in 0.1% of drives after a firmware rollout. How do you decide between rolling back, pausing, or continuing?

    Model answer and what the interviewer listens for

    Assess impact (data integrity versus availability versus performance), rate trend (growing, flat), cohort comparison (same platform with old firmware: is it truly new?), and reversibility (can firmware be rolled back safely, and does rollback itself carry risk). Data integrity issues justify an immediate pause and rollback even at low rates; availability issues with redundancy may justify pausing while investigating; performance regressions may allow continuing with a fix in the next release. Communicate the decision with evidence and a re-evaluation date. Capture telemetry from affected drives before any rollback changes their state.

    Listening for: severity classes; cohort evidence; risk of the remedy; evidence capture; communication.

    Learn it in: Senior Engineer Thinking, Communication and Design Review.

  14. [Architecture] Where do the Subsystem Local Memory and Computational Programs command sets fit, and when would you not use them?

    Model answer and what the interviewer listens for

    Computational Programs lets the host run programs on compute resources inside the NVM subsystem, close to the data, to reduce data movement (filtering, compression, search). Subsystem Local Memory gives those programs addressable memory inside the subsystem, with commands to move data between namespaces and that memory. Use them when data reduction near storage pays for itself: large scans with high selectivity. Avoid them when the workload is compute-heavy relative to data movement, when the programs need frequent coordination with the host, when portability across vendors matters more than efficiency, or when the security model of running code on the device is not acceptable. Measure end-to-end, including program load and result transfer.

    Listening for: data movement as the reason; selectivity; security and portability costs; measuring end-to-end.

    Learn it in: Chapter 61, Chapter 62, Module 46, Module 47.

  15. [Architecture] A DRAM-less SSD uses the Host Memory Buffer (HMB). What failure modes and tradeoffs does that create?

    Model answer and what the interviewer listens for

    The host lends memory (Host Memory Buffer feature) that the controller uses, typically for mapping tables. Tradeoffs: lower cost and power versus extra PCIe reads for table lookups (latency and link traffic) and dependence on host memory. Failure modes: host disables or resizes the HMB (for example across suspend/resume) and the controller must handle the change; IOMMU mapping errors fault the controller's internal accesses; host memory corruption corrupts device metadata; performance drops sharply when the HMB is smaller than requested. Debug evidence: device MRd traffic to the HMB region in a trace, HMB feature settings, IOMMU faults on HMB addresses.

    Listening for: device depends on host memory; suspend/resume and IOMMU risks; how to see it in a trace.

    Learn it in: Chapter 30, Module 21.

  16. [Architecture] Design queue and interrupt allocation for a 256-core host with 24 NVMe drives, each supporting 128 I/O queues and 129 MSI-X vectors.

    Model answer and what the interviewer listens for

    One queue per core per drive would need 256 queues per drive, more than each supports, and 24 × 256 interrupt vectors, which can exhaust per-CPU interrupt vector space on some platforms. Options: map groups of cores to each queue (128 queues, two cores each, grouped by Non-Uniform Memory Access (NUMA) node); dedicate some queues to polling (fewer interrupts, more CPU); use interrupt coalescing for throughput-oriented drives. Place drives' interrupts on the NUMA node they attach to. Validate with per-queue utilisation and interrupt distribution. The tradeoff is lock contention when cores share a queue versus interrupt resources.

    Listening for: the arithmetic; platform interrupt limits; NUMA placement; sharing versus resources.

    Learn it in: Chapter 42, Chapter 43, Performance Engineering.

  17. [Architecture] A team proposes polling-only completion (no interrupts) for all NVMe I/O. Review the design.

    Model answer and what the interviewer listens for

    Polling removes interrupt latency and overhead, which helps at very low latency and high IOPS. Costs: CPU spent spinning even when idle; power; poor behaviour under light or bursty load; harder sharing of cores. Middle grounds: hybrid polling (sleep for an estimated time, then poll), dedicated poll queues alongside interrupt queues, and interrupt coalescing. Ask for measurements: CPU per I/O and P99 latency at several loads, power, and behaviour when the workload is idle. Also the error path: timeouts and asynchronous events still need a reliable path.

    Listening for: load-dependent tradeoff; hybrid options; measurements requested; error paths remembered.

    Learn it in: Chapter 42, Module 53.

  18. [Troubleshoot] How would you use the NVMe 2.4 voltage monitoring capability in fleet diagnosis, and how would you avoid false conclusions?

    Model answer and what the interviewer listens for

    It reports discrepancies between the voltage the platform supplies and what the device sees, with thresholds, alerts and history. Use: correlate voltage alerts with resets, link errors and media errors by slot and platform model to find power delivery problems that look like device failures. Avoid false conclusions: thresholds and measurement accuracy are implementation-dependent; a voltage alert during a load step may be expected; correlation by time needs clock alignment; and a power problem can be caused by another device on the same rail. Confirm with platform-side measurements. Field details must be read in the Base 2.4 specification.

    Listening for: correlation by cohort and time; measurement limits; independent confirmation.

    Learn it in: 2026 NVMe 2.4 Updates, Module 60.

  19. [Architecture] What security and operational questions does the NVMe 2.4 "restore manufacturing default settings" capability raise?

    Model answer and what the interviewer listens for

    It returns an NVM subsystem to its as-shipped state. Questions: who is authorised to trigger it (and how it interacts with lockdown and security protocols); whether user data is sanitized as part of it or must be sanitized separately (do not assume); what happens to firmware, keys, namespaces and settings; whether it is logged in the Persistent Event log; how it behaves in multi-tenant or virtualized deployments (lockdown controls for virtualized environments are also part of 2.4); and how hosts discover the device has been reset. Operationally: drive return and redeployment flows, and fleet tooling that must not trigger it by accident. Read the Base 2.4 text for the exact scope.

    Listening for: authorisation; sanitization not assumed; logging; multi-tenant consequences.

    Learn it in: 2026 NVMe 2.4 Updates.

  20. [Architecture] What parts of the NVMe queue protocol would you model formally, and what properties would you check?

    Model answer and what the interviewer listens for

    Model the host, the controller and the shared memory as processes: SQ and CQ rings with head and tail, phase tags, doorbell writes as messages that can be delayed, completions that can be reordered. Properties: safety (the host never overwrites an unfetched SQE; the controller never posts to a full CQ; every CQE the host consumes has the expected phase; CIDs are unique among outstanding commands) and liveness (every submitted command eventually completes if the controller is live; no deadlock between a full CQ and a host waiting for completions). Then add reset: outstanding commands are aborted and no stale completion is accepted after the queue is recreated. Tools: TLA+ or a model checker on a small configuration (queue size 2–4).

    Listening for: small models; safety versus liveness; reset as a source of subtle bugs.

    Learn it in: Communication, Design Review and Formal Models, Chapter 25.

  21. [Architecture] How do you teach a junior engineer to read a PCIe/NVMe trace? Describe the first month.

    Model answer and what the interviewer listens for

    Week 1: one clean 4 KiB Read, annotated by hand, every row explained (who, what, why, which field ties it to the next). Week 2: the same command in different conditions (large transfer, Write, shared CQ), predicting the trace before seeing it. Week 3: abnormal traces with one injected fault each; the task is to find the first abnormal event and justify it. Week 4: an unlabelled real-world-style capture, with a written report reviewed against a rubric. Throughout: teach-back sessions, pairing on real bugs, and insisting on evidence for every claim. Measure progress on the rubric levels, not on hours spent.

    Listening for: predict before you look; one variable at a time; first abnormal event; written reports; feedback with a rubric.

    Learn it in: Trace Analysis Laboratory, Testing, Spaced Review and Teach-Back.

Junior engineer loop (45 minutes)

Senior engineer loop (60 minutes)

  2. 30 min: one scenario from Scenario Interviews, handing out evidence as the candidate asks for it.
  3. 15 min: one senior design or review question (regression test design or driver patch review).

  2. 40 min: one ambiguous incident (a scenario with conflicting evidence) where the candidate must decide what to do with incomplete data.
  3. 20 min: a communication exercise: explain the incident's conclusion to an executive and to the engineer whose code caused it.

Common ways strong candidates lose points

  • The loudest error wins. Naming the fatal error in the log as the cause when an earlier correctable error started the cascade.
  • The detector is the culprit. Treating the device that logged an error as the device that caused it.
  • Confident numbers. Quoting a status code or bit position wrongly. Saying "I would confirm that in the specification" costs nothing.
  • No evidence. Describing a mechanism without saying what would prove it happened.
  • No next step. Ending with a hypothesis instead of an experiment.
