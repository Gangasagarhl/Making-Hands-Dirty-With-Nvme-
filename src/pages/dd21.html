This module opens the Non-Volatile Memory Express (NVMe) controller up. Chapter 23 taught what a controller is and how it differs from a namespace; here you follow a controller's internal engines, its arbitration, its command bookkeeping and its life-cycle edges through synthetic traces, harder labs and a library of failure patterns.

Orientation

The chapter gave you the controller as a black box with a state machine: disabled, enabling, ready, shutting down, fatal, paused. This module treats it as a machine with parts — a register front end, a doorbell decoder, a submission-queue arbiter, a fetch engine, a command dispatcher, firmware cores, data movers and a completion poster — and asks which part is responsible for each thing you see on the wire. That shift is what lets you say "the arbiter starved queue 3" or "the fetch engine is alive but the firmware is not" instead of "the drive hung". You will also study the edges of the controller's life more precisely than the chapter did: re-enable races, reset variants, the Abort command, and controller-wide pauses.

Kid story

Imagine a pizza kitchen with a single order window. Outside the window hang several clipboards — one for each table in the restaurant. When a waiter adds orders to a clipboard, they ring that table's little bell. Inside, a caller decides which clipboard to read next: usually she goes around in a circle, but the "birthday party" clipboard (urgent) always goes first. A runner fetches the order slips. The head cook reads each slip and hands it to a station: the oven, the salad bar, the drinks fridge. Orders finish in whatever order they are ready — a drink is faster than a pizza — and a bell-ringer puts a "done" ticket on the table's tray and rings a buzzer at the waiter's station.

The kitchen also has a big red light on the wall. If the head cook faints, the caller and runner may keep fetching slips for a while, but nothing gets cooked. The waiter only finds out by looking at the red light — or by noticing that no "done" tickets are coming back.

The kitchen is the controller. The clipboards are submission queues in host memory, the bells are doorbells, the caller is the arbiter, the runner is the fetch engine, the head cook is the firmware dispatcher, the stations are the media back end and data movers, the bell-ringer is the completion poster and interrupt logic, and the red light is CSTS.CFS.

Analogy boundary

  • What it represents. Separate engines with separate failure modes; arbitration among queues; out-of-order completion; a status light that is the only reliable signal when the "cook" is gone.
  • What it hides. The clipboards are not in the kitchen: submission and completion queues live in host memory, and the runner must cross the PCI Express (PCIe) link to read each slip. The kitchen also cannot read a slip it was not told about — it only knows how far each clipboard is filled because of the doorbell value, not by looking.
  • Where it misleads. A real controller can read several slips in one trip (a batched fetch), may start a slip before finishing the previous one, and may silently drop every slip on a clipboard when the manager flips the kitchen off (a controller reset aborts outstanding commands without posting completions). No restaurant throws away orders and expects waiters to resubmit them.
  • Also misleading. "The birthday party always goes first" describes the urgent class only under weighted round robin with urgent priority class. Under plain round robin, which every controller supports, there is no priority at all.

The register front end and the doorbell decoder usually run in hardware; CC.EN, CC.SHN, admin commands and error handling usually run in firmware. A firmware crash can therefore leave a controller that still accepts doorbells and even fetches SQEs, but never completes them. A hardware hang usually stops everything, including CSTS reads. Keeping these two clocks apart is the single most useful idea in controller debugging.

Arbitration in detail

Every controller supports round robin: non-empty SQs (the admin SQ included) take turns, and each turn may fetch up to the Arbitration Burst. Weighted round robin with urgent priority class, when CAP.AMS bit 17 advertises it and CC.AMS = 001b selects it, creates three tiers: the admin SQ (strict highest priority), the urgent class (strict priority over everything below it), and a weighted round robin among high, medium and low classes using the weights in the Arbitration feature. Each I/O SQ's class is the QPRIO field given in its Create I/O Submission Queue command.

Strict priority means starvation is legal. A saturated urgent SQ can starve every high, medium and low SQ indefinitely. The specification does not promise fairness across tiers; it only defines the order of selection. A host that uses the urgent class owns the consequences. See the slow trace below.

Outstanding commands and CIDs

The controller identifies a command by the pair (SQID, CID). The host must not reuse a CID on an SQ while a command with that CID is outstanding there; if it does, the controller may report Command ID Conflict (generic status 03h) or, worse, complete the wrong one in the host's eyes. Nothing stops two SQs from using the same CID at the same time, which is why every CQE carries the SQID as well. A Controller Level Reset empties the outstanding table without posting completions: from the host's perspective, every outstanding command must be treated as "status unknown".

The Abort command, honestly

Abort (admin opcode 08h) names a target SQID and CID in Command Dword 10. The specification makes Abort best effort: the controller may complete the targeted command normally, abort it (completing it with Command Abort Requested, generic status 07h), or find nothing to abort. Abort's own completion reports in Dword 0 whether the command was aborted Uncertain (confirm the bit meaning in the Base Specification's Abort command clause). The Abort Command Limit (ACL) field in Identify Controller is a 0's based count of Abort commands that may be outstanding; exceeding it returns the command-specific status Abort Command Limit Exceeded. Linux uses Abort only as the first step of timeout handling and falls back to a controller reset when it fails — which is why Abort is rarely the end of a story.

Re-enable timing

After CC.EN goes 1→0, the host shall wait for CSTS.RDY = 0 before setting CC.EN = 1 again. The controller's reset work (stopping engines, discarding contexts) runs in firmware and takes microseconds to milliseconds. A host that re-enables early has written EN = 1 while the controller still believes it is resetting; the outcome is undefined, and a common real result is that RDY goes to 0 and stays there. The ladder for the central concept: the controller as a set of engines

A pizza kitchen behind one window: a caller who picks the next clipboard, a runner, a head cook, cooking stations, and a bell-ringer — plus a red light for "the cook fainted".

A controller arbitrates among submission queues, fetches commands, dispatches them, moves data, posts completions and raises interrupts, and reports its own health through CSTS.

Hardware: register file and doorbell decoder in the front end, queue context SRAM, fetch and DMA engines, MSI-X logic; firmware cores run the dispatcher, admin handlers and error handling; a media back end runs the FTL.

Base Specification 2.4 defines the observable behaviour: properties, initialisation, arbitration mechanisms, command processing, Abort, resets, shutdown, CSTS semantics. It does not define internal blocks; those are implementation-dependent.

Doorbell MWr in; SQE MRd/CplD; data MWr or MRd/CplD; CQE MWr; MSI-X MWr. Register MRd/CplD only for status or life-cycle events.

In a capture, each engine leaves its own signature: the arbiter in the order of fetches across queues, the fetch engine in MRd sizes, the firmware in the gap between fetch and data, the poster in CQE addresses and phase, the interrupt logic in MSI-X timing.

Ask which engine stopped first. Doorbells with no fetch: front end, arbiter, Bus Master Enable. Fetches with no completion: firmware or media. Completions with no interrupt: interrupt path. Nothing at all including CSTS: PCIe or hardware.

The sixteen questions for the controller's engines

1. What is it?
The set of hardware and firmware functions that turn queued NVMe commands into media operations and completions.
2. Why was it created?
To let many CPU cores submit work in parallel through independent queues, without locks or register reads in the I/O path.
3. What problem does it solve?
Scaling: Advanced Host Controller Interface (AHCI) had one command list per port, 32 slots, and register accesses per command.
4. What existed before?
AHCI controllers and SCSI host bus adapters, where the host adapter and device were separate and command issue was register-heavy.
5. Why is the current design better?
Up to 65,535 I/O queues, one posted doorbell write per batch, completions in host memory, and parallel engines inside the device.
6. Who creates it?
The device designer; on fabrics with the dynamic controller model, the subsystem instantiates one per association.
7. Who consumes it?
One host at a time through its queues; management agents through the admin queue or NVMe-MI.
8. Where does it live?
In the SSD's controller chip, exposed as a PCIe function with BAR0.
9. What memory/registers are involved?
BAR0 properties and doorbells; queue contexts in device SRAM; queues and buffers in host memory; MSI-X table.
10. What happens before?
PCIe enumeration, BAR assignment, Memory Space and Bus Master Enable, MSI-X setup, controller enable.
11. What happens after?
Namespaces become block devices; the controller runs until reset, shutdown or failure.
12. What happens if it is wrong?
Starvation, lost commands, CID conflicts, hangs with CSTS still healthy, CFS, unsafe shutdowns.
13. What does the analyzer show?
Doorbells, fetches, data, CQEs and MSI-X in a characteristic rhythm; deviations localise the failing engine.
14. What does Linux show?
Controller state in sysfs, timeouts and resets in the kernel log, per-queue interrupt counts, nvme tracepoints.
15. What would a validation engineer test?
Enable/disable races, arbitration fairness and starvation, Abort semantics, reset under load, invalid doorbells, shutdown timing against RTD3E.
16. What would a senior engineer suspect?
Which engine stopped first, and whether the host violated a timing rule (early re-enable, short CAP.TO wait) before blaming the device.

"Hardware front end alive, firmware stalled" is a reasoned model of how controllers are built, not specification text. So is the per-engine signature mapping in the trace section. Treat them as strong hypotheses that device-side evidence (telemetry, vendor logs) must confirm.

  • The specification does not define how many SQEs the controller fetches per Memory Read, or in what order it starts commands from one SQ.
  • It does not guarantee fairness between WRR tiers, nor a maximum latency for any command.
  • It does not specify what a controller does internally when the host violates the re-enable rule.
  • It does not require that an Abort succeed, nor bound how long one takes.
  • Check in the specification: the Abort completion Dword 0 encoding; the Arbitration feature field positions and the burst encoding; which properties each reset type leaves unchanged.

Never assume completion order equals submission order, that the urgent class is fair, that RDY = 1 means media is ready (with CRIME it need not), or that a completed Abort aborted anything.

Errors split by layer. NVMe command errors are carried in CQE status fields and never generate PCIe errors. PCIe errors (Unsupported Request, Completer Abort, Completion Timeout, poisoned TLPs) are reported through PCIe completion status and Advanced Error Reporting (AER). A controller-fatal condition is reported only through CSTS.CFS — there is no message for it, which is why the host has to read the register.

When a Controller Reset discards outstanding commands, no CQE is posted for them. The protocol's only "message" is the absence of completions plus RDY going to 0. Every host recovery path must therefore be built on timeouts and on the reset event itself, never on waiting for a final status.

  2. Fill a table with columns: field · value · decoded meaning · engine constrained (front end, arbiter, fetch, dispatcher, data mover, poster, firmware life cycle).

Observations

Record which limits come from registers (known before enable) and which from Identify (known only after the admin queue works).

Questions

  1. Which engine does MDTS constrain, and why does the host need to know it before building I/O?
  2. What does ACL = 3 mean for the host's timeout handling?
  3. Why can the driver use DSTRD before Identify, but not MDTS?

Expected reasoning

Limits that affect how the host talks to the controller before any command (doorbell addresses, timeouts, page sizes) must be in registers; limits about command contents can wait for Identify.

Solution

Synthetic decode: MQES 4096 entries (fetch engine and queue contexts); CQR 1 (queue contexts: contiguous queues only); AMS 00b — only RR (arbiter); TO 10 s (firmware life cycle); DSTRD 0 → 4-byte stride (front end); CC.AMS 000b RR; MDTS 5 → 25 × 4 KiB = 128 KiB (data movers; the host must split larger I/O); ACL 3 → 4 Aborts outstanding (dispatcher); AERL 3 → 4 Asynchronous Event Requests outstanding (dispatcher / event logic); SQES 0x66 → required and maximum SQE 64 bytes; CQES 0x44 → 16 bytes (fetch engine and poster); RTD3E 2 s (firmware shutdown path); NN 32 (namespace lookup).

Answers: (1) The data movers and the dispatcher; a command exceeding MDTS is rejected, so the block layer must split I/O before building SQEs. (2) At most four Abort commands may be outstanding; a timeout storm affecting more commands must fall back to a reset rather than queueing more Aborts. (3) DSTRD is in CAP, readable before enable; MDTS lives in the Identify Controller data structure, which requires a working admin queue.

Intermediate lab — Reconstruct pipeline timing from a capture

Objective

Split each command's latency into doorbell→fetch, fetch→data, data→CQE and CQE→interrupt, handling a batched fetch and out-of-order completion.

Prerequisites

The normal trace in this module; Python 3 (standard library only).

Setup

Save the program as pipeline.py. Its input is the module's normal trace, already decoded into events.

#!/usr/bin/env python3
"""Reconstruct per-command pipeline timing from a synthetic capture.
Teaching tool (course reference system); events are pre-decoded rows."""
SQ1_BASE, CQ1_BASE, SQE, CQE = 0x1_2340_0000, 0x1_2341_0000, 64, 16

# (time_us, kind, fields) -- the normal trace from this module, pre-decoded
CAPTURE = [
    (0.00, "db_sq", {"qid": 1, "tail": 43}),
    (0.62, "mrd", {"addr": SQ1_BASE + 40 * SQE, "dw": 48}),
    (1.35, "cpld_sqe", {"cids": [0x0101, 0x0102, 0x0103]}),
    (6.80, "cqe", {"cid": 0x0103, "status": 0}),
    (6.90, "msix", {"vector": 1}),
    (61.2, "data", {"cid": 0x0101}),
    (64.9, "data", {"cid": 0x0102}),
    (66.0, "cqe", {"cid": 0x0101, "status": 0}),
    (66.1, "cqe", {"cid": 0x0102, "status": 0}),
    (66.2, "msix", {"vector": 1}),
]

def reconstruct(capture):
    cmds, pending_irq = {}, []
    doorbell_t = fetch_req_t = None
    for t, kind, f in capture:
        if kind == "db_sq":
            doorbell_t = t
        elif kind == "mrd":
            fetch_req_t = t
            first_slot = (f["addr"] - SQ1_BASE) // SQE
            n = f["dw"] * 4 // SQE
            print(f"fetch at {t} us: slots {first_slot}..{first_slot + n - 1} ({n} SQEs)")
        elif kind == "cpld_sqe":
            for cid in f["cids"]:
                cmds[cid] = {"doorbell": doorbell_t, "fetch_req": fetch_req_t, "fetched": t}
        elif kind == "data":
            cmds[f["cid"]].setdefault("data", t)
        elif kind == "cqe":
            cmds[f["cid"]]["cqe"] = t
            pending_irq.append(f["cid"])
        elif kind == "msix":
            for cid in pending_irq:
                cmds[cid]["irq"] = t
            pending_irq = []
    return cmds

if __name__ == "__main__":
    cmds = reconstruct(CAPTURE)
    order = sorted(cmds, key=lambda c: cmds[c]["cqe"])
    print("completion order:", ", ".join(f"0x{c:04X}" for c in order))
    print(f"{'CID':>6} {'db->fetch':>9} {'fetch->data':>11} {'data->cqe':>9} {'cqe->irq':>8} {'total':>7}")
    for cid in sorted(cmds):
        c = cmds[cid]
        data = c.get("data", c["cqe"])     # writes have no device->host data
        print(f"0x{cid:04X} {c['fetched'] - c['doorbell']:9.2f} {data - c['fetched']:11.2f} "
              f"{c['cqe'] - data:9.2f} {c['irq'] - c['cqe']:8.2f} {c['irq'] - c['doorbell']:7.2f}")

Procedure

  1. Run it. Expected output: one fetch of slots 40–42 (3 SQEs); completion order 0x0103, 0x0101, 0x0102; CID 0x0101 total 66.20 µs with about 59.85 µs between fetch and data; CID 0x0103 total 6.90 µs.
  2. Add a fourth command that is fetched in a second MRd at 70 µs and completes at 140 µs. Make sure the code attributes the right doorbell and fetch to it.
  3. Change the CQE for CID 0x0102 to arrive before its data. What should the tool report?

Observations

Note which phase dominates for reads and for the write. Note that the fetch phase is shared by all three commands.

Questions

  1. Why is the write's fetch→"data" interval the time to fetch write data, while the reads' is media time plus transfer?
  2. A CQE before its data: device bug, capture artefact, or decoding error? How would you tell?
  3. Why can CQE→interrupt differ between commands completed by the same interrupt?

Expected reasoning

Phases are defined by link events, so each phase mixes several engines. Ordering rules (posted writes from one requester stay in order) constrain what is physically possible.

Solution

(1) For a write, the device pulls data from host memory (MRd/CplD) and may complete as soon as data reaches its write cache; for a read, the device must read NAND before it can push data. In the script the write has no device→host data, so it uses the CQE time and data→CQE is 0. (2) Read data and the CQE are posted writes from the same requester and cannot pass each other on the way to memory, so a capture that shows the CQE first is either mis-ordered by the capture tool (multiple probe points or timestamp merge) or mis-decoded (the "data" belonged to another command). A genuine device that posts a CQE before writing the data has a severe bug: the host could read stale data. Check the analyzer's capture points and the data addresses against the PRPs. (3) The poster writes each CQE when that command finishes; the interrupt logic fires once for the batch, so earlier CQEs wait longer.

Step 2 sketch: add (70.0, "mrd", …) and a cpld_sqe with the new CID before its CQE; because the script remembers the latest doorbell and fetch, place a new db_sq event before the second fetch.

Extension

Advanced lab — Arbitration and starvation in a model controller

Objective

Demonstrate, with a simulation, that weighted round robin with urgent priority class permits starvation, and quantify how the Arbitration Burst and weights change service.

Prerequisites

The Arbitration section of this module; Python 3.

Setup

#!/usr/bin/env python3
"""Toy model of NVMe SQ arbitration: round robin vs weighted round robin
with urgent priority class. Teaching simulation, not a controller design."""
from collections import deque

def simulate(mode, queues, burst=8, weights=None, slots=2000, refill=None):
    """queues: {qid: {"prio": "urgent|high|medium|low", "pending": n}}
    Each slot the arbiter fetches up to `burst` commands from one SQ.
    refill(qid, slot) -> commands added to that SQ at this slot.
    Returns the first slot at which each SQ was served, and totals."""
    weights = weights or {"high": 4, "medium": 2, "low": 1}
    first, served = {}, {q: 0 for q in queues}
    rr = deque(sorted(queues))
    credits = {}
    for slot in range(slots):
        if refill:
            for q in queues:
                queues[q]["pending"] += refill(q, slot)
        busy = [q for q in rr if queues[q]["pending"] > 0]
        if not busy:
            continue
        if mode == "rr":
            pick = busy[0]
        else:
            urgent = [q for q in busy if queues[q]["prio"] == "urgent"]
            if urgent:
                pick = urgent[0]
            else:
                if not any(credits.get(q, 0) > 0 for q in busy):
                    credits = {q: weights[queues[q]["prio"]] for q in busy}
                pick = next(q for q in busy if credits.get(q, 0) > 0)
                credits[pick] -= 1
        n = min(burst, queues[pick]["pending"])
        queues[pick]["pending"] -= n
        served[pick] += n
        first.setdefault(pick, slot)
        rr.remove(pick)
        rr.append(pick)
    return first, served

def scenario(mode):
    qs = {1: {"prio": "urgent", "pending": 64},
          2: {"prio": "low", "pending": 1},
          3: {"prio": "high", "pending": 64}}
    # the benchmark keeps SQ1 non-empty for the first 1500 slots
    refill = lambda q, s: 8 if (q == 1 and s < 1500) else 0
    return simulate(mode, qs, refill=refill)

if __name__ == "__main__":
    for mode in ("rr", "wrr"):
        first, served = scenario(mode)
        print(f"{mode.upper():3}: first slot served {dict(sorted(first.items()))}"
              f"  commands served {served}")

Procedure

  1. Run it. Expected output: under RR, SQ2 is first served at slot 1 and SQ3 at slot 2; under WRR, SQ2 at slot 1508 and SQ3 at slot 1509 — both wait until the urgent SQ1 drains.
  2. Change SQ1's priority to "high" and rerun. Record when SQ2 and SQ3 are first served.
  3. Set burst=1 and compare total commands served per queue in the first 100 slots.
  4. Change the weights to high 16, medium 4, low 1 and give SQ2 a continuous refill too. Measure SQ2's share.

Observations

Tabulate first-service slot and share per queue for each configuration.

Questions

  1. Why does SQ3 (high) also starve under WRR, even though it is not low priority?
  2. What host-side policy prevents starvation while keeping the benefit of the urgent class?
  3. What would you look for in a capture to tell arbiter starvation from firmware slowness?

Expected reasoning

Urgent is a strict tier above the weighted tiers; weights only share bandwidth within the weighted tiers.

Solution

(1) The urgent class has strict priority over high, medium and low; as long as any urgent SQ is non-empty, no weighted SQ is selected. (2) Rate-limit what the host places in urgent SQs (only latency-critical, low-volume traffic), or use RR. (3) Starvation shows as a doorbell for the starved SQ followed by no fetch for a long time while other SQs are fetched; firmware slowness shows as a prompt fetch followed by a long gap before data or CQE. The position of the gap relative to the fetch localises it.

With SQ1 "high": SQ2 is first served at slot 1 or soon after, because all three are in weighted tiers and credits rotate. With burst 1, each turn moves one command, so service is finer-grained and the low queue's share per turn is more visible; total throughput in the model is unchanged because the model has no per-fetch cost — a real controller would pay one MRd per turn.

Extension

Debugging

Each pattern lists symptom, possible causes, evidence, first and second checks, a disambiguating experiment, the likely conclusion and a confidence level. Read CSTS through MMIO (nvme show-regs), not through admin commands, whenever the controller itself is in doubt.

Pattern 1 — RDY never becomes 1 after a Function Level Reset

Symptom
After a hypervisor or driver issues FLR, the driver's enable times out; CSTS reads 0x0000_0000.
Possible causes
Config space not restored (Bus Master Enable or Memory Space Enable clear, BAR not reprogrammed); enable attempted before the function finished its FLR; device needs longer than CAP.TO after FLR (device bug); AQA/ASQ/ACQ not rewritten (they may be reset by FLR).
Evidence
Config space Command register; register dump; capture of the enable sequence.
First check
lspci -vvv Command register: are "Mem+" and "BusMaster+" set?
Second check
Does nvme show-regs show AQA/ASQ/ACQ as the driver last wrote them, or as zero?
Disambiguating experiment
Repeat with a delay of 100 ms after FLR (PCIe requires the function to be given time after FLR before it must respond normally) and with an explicit config-space restore; observe which change makes RDY set.
Likely conclusion
Incomplete host restore after FLR.
Confidence
Medium-high when the Command register shows the bits cleared.

Pattern 2 — Reset loop: CFS returns after every enable

Symptom
Kernel log repeats "controller is down; will reset: CSTS=0x3" every few seconds; the device eventually is marked dead.
Possible causes
Firmware crashing during initialisation (corrupted metadata, failed NAND block holding firmware state); a specific admin command in the bring-up sequence triggering a firmware fault; thermal or power protection.
Evidence
Time between RDY = 1 and CFS = 1; which admin command was last fetched before CFS.
First check
Is CFS set before or after the first admin command? (Capture, or kernel log ordering.)
Second check
Temperature and power state from the last readable SMART / Health log; platform power telemetry.
Disambiguating experiment
Enable the controller with a minimal user-space or bootloader driver that sends only Identify Controller; if CFS still follows, the fault is in firmware initialisation, not in a later command.
Likely conclusion
Device firmware fault; collect telemetry if any window allows it; involve the vendor.
Confidence
High that it is device-side; low on the mechanism without vendor logs.

Pattern 3 — One submission queue stalls, others are fine

Symptom
Timeouts only on one hardware queue (one CPU's I/O); other queues keep completing; CSTS = 0x1.
Possible causes
Arbiter starvation (urgent class saturated); doorbell value beyond the queue size (Invalid Doorbell Write Value); doorbell written to the wrong address; the SQ's CQ binding or vector broken (completions posted but no interrupt); host CPU offline handling bug.
Evidence
Doorbell writes for that SQ; fetches from its base; CQEs on its CQ; MSI-X for its vector; outstanding Asynchronous Event Request completions with Error status.
First check
Are there fetches from that SQ's base after its doorbells? No → arbiter or doorbell problem. Yes → look downstream.
Second check
Read the Arbitration feature and the queues' QPRIO; check the admin CQ for an Error status asynchronous event.
Disambiguating experiment
Pause the other workloads; if the stalled SQ immediately drains, it was starvation; if not, decode its doorbell values against the queue size.
Likely conclusion
Usually host-side: priority policy or doorbell bookkeeping.
Confidence
Medium until the experiment is run.

Pattern 4 — Abort never helps

Symptom
Every timeout logs an Abort followed 30 s later by a reset; or Aborts fail with Abort Command Limit Exceeded.
Possible causes
Device implements Abort minimally (legal); commands stuck beyond the point where firmware can abort them; host issuing more than ACL + 1 concurrent Aborts.
Evidence
Abort completion Dword 0 and status; ACL in Identify Controller; count of concurrent timeouts.
First check
ACL value versus the number of Aborts the host sends at once.
Second check
Does the target command ever complete after an Abort reports success?
Disambiguating experiment
On a scratch device, submit a long-running but abortable command (for example a large Read behind a throttled queue) and Abort it; check whether the device ever aborts anything.
Likely conclusion
Abort is best effort; host recovery must not depend on it.
Confidence
High for the policy conclusion.

Pattern 5 — Unsafe shutdowns increase on clean reboots

Symptom
SMART / Health "unsafe shutdowns" grows by one per reboot even though the OS shuts down normally; next boot takes longer to reach RDY.
Possible causes
Host shutdown timeout shorter than the device's real shutdown time (RTD3E is only an estimate); platform cuts power before SHST = 10b; driver writes CC without read-modify-write and turns shutdown into reset; firmware does not count correctly.
Evidence
RTD3E; the host's shutdown timeout (Linux nvme_core.shutdown_timeout); kernel log "shutdown timeout" messages; a capture of the final CC write and CSTS polling.
First check
Compare RTD3E with the host shutdown timeout.
Second check
Capture the last CC write: is SHN = 01b with EN still 1 (e.g. 0x0046_4061)?
Disambiguating experiment
Raise the host timeout above RTD3E and repeat ten reboots; if the counter stops increasing, timing was the cause.
Likely conclusion
Host or platform cuts the shutdown short.
Confidence
Medium-high after the experiment.

Pattern 6 — Latency spikes with no errors and CSTS.PP = 1

Symptom
Hundreds of milliseconds of stalled completions on every queue at once, no errors, recurring at maintenance time.
Possible causes
Firmware activation without reset pausing processing; thermal throttling; internal maintenance.
Evidence
CSTS sampled during a spike; an admin CQE for an Asynchronous Event Request with a firmware-activation notice; Firmware Slot Information log.
First check
Read CSTS during a spike: PP = 1 (0x0000_0021)?
Second check
Correlate spikes with Firmware Commit commands in the admin history.
Disambiguating experiment
Repeat the maintenance procedure on a lab system with I/O running and a capture; look for PP and for the activation notice.
Likely conclusion
Expected pause during activation; schedule it, and size host timeouts above the device's maximum activation time.
Confidence
High if PP is observed during the spike.

Interview

Beginner

  1. What does an NVMe controller do with a submission queue entry?

    Model answer

    It fetches it from host memory after a doorbell, parses opcode, NSID and data pointer, validates it, executes it against the namespace, moves data by DMA, posts a 16-byte completion to the bound completion queue, and raises the queue's interrupt.

  2. Why does every completion entry carry an SQ identifier and a CID?

    Model answer

    Several SQs may share one CQ, and CIDs are only unique per SQ; the pair identifies the command. The SQ head pointer in the CQE also tells the host how far the controller has consumed that SQ.

  3. What is arbitration in NVMe?

    Model answer

    The controller's choice of which non-empty submission queue to fetch from next: round robin always, weighted round robin with urgent priority class optionally, or a vendor scheme.

  4. Do NVMe commands complete in the order they were submitted?

    Model answer

    No. Completion order is up to the controller; a write absorbed by cache can complete before an earlier read. Hosts match completions by CID.

  5. What happens to outstanding commands on a controller reset?

    Model answer

    They are aborted without completions; the queues are deleted. The host must treat them as not completed and retry or fail them after re-initialising.

Intermediate

  1. Explain WRR with urgent priority class.

    Model answer

    Three tiers: the admin SQ first; then urgent SQs with strict priority; then high, medium and low classes sharing bandwidth by configurable weights. QPRIO at SQ creation chooses the class; the Arbitration feature sets weights and burst; CC.AMS selects the mechanism if CAP.AMS supports it.

  2. Why must a host wait for RDY = 0 before re-enabling?

    Model answer

    The controller performs its reset asynchronously and signals completion by clearing RDY. Setting EN = 1 before that leaves the controller's view of the transition undefined; the enable may be lost or misprocessed.

  3. How does a batched SQE fetch appear in a trace?

    Model answer

    One MRd whose length is a multiple of 16 DW covering consecutive slots, with one or more CplDs. All commands in it share fetch latency, and CQEs show the advanced SQHD.

  4. What does Interrupt Coalescing trade?

    Model answer

    Fewer interrupts and less CPU overhead for added completion latency, set by an aggregation threshold and time; latency-sensitive vectors can opt out with Interrupt Vector Configuration.

  5. What is the difference between a Controller Reset and an FLR from the host's recovery perspective?

    Model answer

    Both reset NVMe controller state. FLR also resets the PCIe function's config space and MSI-X table, so the host must restore Command register bits, BARs and MSI-X before re-enabling; a Controller Reset leaves PCIe state intact.

Advanced

  1. A capture shows a doorbell, a fetch, and nothing else for that command for 30 seconds while other commands complete. What do you conclude and what don't you?

    Model answer

    The front end, PCIe path and interrupt path work; the command is stuck inside the device after the fetch (firmware or media). I cannot conclude which; I need CSTS (to rule out fatal or paused), telemetry, and whether the delay repeats for the same LBA.

  2. How would you distinguish arbiter starvation from firmware slowness in a capture?

    Model answer

    By where the gap sits. Starvation: doorbell then a long absence of fetches for that SQ while other SQs are fetched. Firmware slowness: prompt fetch, then a long gap before data or CQE.

  3. Why does a successful Abort completion not prove anything about the target command?

    Model answer

    Abort is best effort. Its completion reports whether the controller aborted the command; the target may complete normally, be aborted with status 07h, or stay outstanding. The host must still wait for the target's completion or reset.

  4. What breaks if a driver handles FLR recovery like a Controller Reset?

    Model answer

    Config space and MSI-X state are lost: Bus Master Enable may be clear (no fetches), MSI-X table entries unprogrammed (no interrupts), possibly BARs. RDY may even set, but the first admin command will never complete.

  5. With CC.CRIME = 1 the controller reports ready in 50 ms but the first Read fails. Explain.

    Model answer

    Ready independent of media lets the controller accept admin commands before namespaces are ready; I/O to a namespace that is not ready returns Namespace Not Ready (with a retry delay hint where supported). The host should wait or retry per CRTO and the namespace readiness reporting rather than treating it as failure.

Senior

  1. Design a host recovery policy for a stuck command that minimises data risk and outage time.

    Model answer

    On timeout: read CSTS via MMIO first (all-ones → PCIe path; CFS → reset; PP → wait up to the documented activation time). If healthy, capture telemetry if fast enough, send Abort (bounded by ACL), wait a short grace period, then Controller Reset (not FLR or NSSR, which have larger blast radius). Treat all outstanding commands as unknown; retry idempotent ones; surface non-idempotent failures upward. Escalate to FLR, then hot reset, only when the cheaper reset fails. Log every step with timestamps for later correlation.

  2. How would you validate arbitration on a new controller?

    Model answer

    Matrix of RR and WRR, all QPRIO classes, weight and burst settings, saturated and idle mixes; measure per-queue fetch order and service share against the configured weights; prove admin priority under saturation; confirm starvation of weighted tiers under urgent saturation behaves as specified, not worse (e.g. admin starved); check behaviour when settings change at run time.

  3. A vendor says "our controller never loses commands". What evidence would convince you?

    Model answer

    Long-duration mixed workloads with error injection (media retries, power and thermal events, resets of other controllers in the subsystem), with a host-side ledger that matches every submitted CID to exactly one completion or one reset event, plus captures of edge cases (queue wrap, deletion with commands outstanding). A claim without such a ledger is an opinion.

  4. Where would you put the boundary between hardware and firmware in a new controller, and how does it affect debuggability?

    Model answer

    Hardware for doorbells, fetch, PRP walking, data movement and CQE posting (performance); firmware for admin, error handling and life cycle (flexibility). Debuggability needs hardware-maintained counters and a firmware heartbeat visible to the host (e.g. reflected in CSTS or telemetry), so "hardware alive, firmware dead" can be detected without a reset destroying evidence.

  5. Explain to a product team why a 48 ms latency outlier can be "within specification" and still a bug.

    Model answer

    The specification bounds behaviour (ordering, status, timeouts), not latency, and strict-priority starvation is legal. Whether 48 ms is acceptable is a product requirement: latency SLOs, host configuration guidance, and default settings. The fix may be documentation and defaults (no urgent class by default) rather than firmware.

Quiz

  1. Under WRR with urgent priority class, which queue is always selected first when non-empty?

    • The urgent I/O SQ with the lowest QID
    • The high-priority SQ with the largest weight
    • The admin submission queue
    • Whichever SQ's doorbell was written last
    Answer and reasoning

    The admin SQ has strict highest priority; urgent I/O SQs come next.

  2. An MRd from the device to SQ1 base + 0xA00 with Len = 48 DW fetches:

    • One SQE from slot 10
    • Three SQEs from slots 40–42
    • Forty-eight SQEs
    • A PRP list
    Answer and reasoning

    0xA00 / 64 = 40; 48 DW = 192 bytes = 3 × 64-byte SQEs.

  3. Which statement about Abort is true?

    • A successful Abort completion guarantees the target was aborted
    • Abort is an I/O command
    • Abort can cancel a command that has not been fetched yet by deleting the SQE
    • Abort is best effort and limited by ACL
    Answer and reasoning

    Abort (admin 08h) is best effort; the number outstanding is bounded by ACL (0's based).

  4. CSTS reads 0x0000_0001 during a hang in which all queues have stopped completing. Which is the best next step?

    • Check the host side and the device's fetch/completion activity: interrupts, CQ head doorbells, IOMMU faults, and a capture
    • Replace the SSD: the controller is fatal
    • Issue NSSR
    • Conclude the PCIe link is down
    Answer and reasoning

    RDY = 1 and CFS = 0 is a real value: the link works and the controller claims health. The failure may be host-side (interrupts) or inside the device after fetch; gather evidence before any reset.

  5. Which reset requires the host to restore PCIe config space before re-enabling the controller?

    • Controller Reset (CC.EN 1→0)
    • Function Level Reset
    • A namespace detach
    • Writing CC.SHN = 01b
    Answer and reasoning

    FLR resets the function's config state and MSI-X table; a Controller Reset does not.

  6. Why is the first abnormal event in the "re-enable" trace the CC write, not the timeout 10 seconds later?

    Model answer

    The CC write with EN = 1 was issued while the last observed RDY was 1, violating the re-enable rule. Everything afterwards (RDY stuck at 0, timeout) is a consequence of that write.

  7. In the normal trace, all three CQEs carry SQHD = 43. What does that tell you?

    Model answer

    The controller had consumed (fetched) all three SQEs before posting the first completion, so the host may reuse slots 40–42 as soon as it sees any of those CQEs. SQHD reports consumption, not completion.

  8. Name two pieces of evidence that separate "firmware stalled, front end alive" from "controller hardware hung".

    Model answer

    Fetches still occurring after doorbells (front end alive) and CSTS reads completing with real values (register path alive) point to firmware. No fetches and CSTS reads failing or timing out point to hardware or PCIe.

  9. MDTS = 5 and CAP.MPSMIN = 0. Maximum data per command?

    • 32 KiB
    • 64 KiB
    • 128 KiB
    • 5 × 4 KiB
    Answer and reasoning

    25 × 4 KiB = 128 KiB.

  10. Why can an 8-second successful read be invisible in the Linux kernel log?

    Model answer

    It completes before the 30-second I/O timeout and with success status, so no timeout or error is logged. Only latency tooling (tracepoints, blktrace, application metrics) shows it.

Teach-back

Explain the controller as a set of engines three times, to three audiences. Write your version first, then compare with the model explanation.

To a child

Model explanation

"Inside the SSD there's a little kitchen. Your computer puts orders on clipboards and rings a bell. A caller picks which clipboard to read, a runner fetches the order, the cook decides what to do, the stations make it, and a bell-ringer puts a 'done' ticket back and buzzes. Fast things come back first. If the cook faints, a red light comes on, and the only fix is to switch the kitchen off and on — but then all the unfinished orders are thrown away and have to be ordered again."

To a junior engineer

Model explanation

"The controller front end decodes BAR0: registers and doorbells. A doorbell updates the SQ tail in a queue context. The arbiter — round robin, or weighted round robin with an urgent class — picks a non-empty SQ and the fetch engine reads one or more SQEs with an MRd. Firmware dispatches by (SQID, CID), checks the namespace, runs the media operation, and the data movers push or pull data. The poster writes a 16-byte CQE with SQHD, SQID, CID, status and phase, then MSI-X fires, maybe coalesced. Completions can be out of order. On a Controller Reset all of that internal state is dropped without completions, and you must wait for RDY = 0 before enabling again."

To a senior engineer

Model explanation

"Localise by engine. Doorbell without fetch: arbiter policy, doorbell addressing/value, or bus mastering. Fetch without completion: firmware or media — CSTS distinguishes paused, fatal and 'claims healthy'. Completion without interrupt: vector binding, MSI-X table, IOMMU interrupt remapping. Nothing including CSTS: PCIe or hardware. Recovery escalates by blast radius — Abort (best effort, ACL-bounded), Controller Reset, FLR with config restore, hot reset, NSSR — and evidence capture must precede each step because each destroys state. Strict-priority starvation and slow-but-successful commands are legal; whether they are bugs is a product question."
