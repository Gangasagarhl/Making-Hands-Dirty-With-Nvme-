Chapter 48 reset the NVMe controller from above, through its own registers. This chapter resets it from below: through the Peripheral Component Interconnect Express (PCIe) link, the slot's reset signal, and the function's configuration space. You will learn the reset taxonomy of the PCI Express Base Specification, what each reset does to the link and to configuration space, how long software must wait before the device is ready again, and how Linux chooses and performs these resets.

Why this chapter exists

When an NVMe controller stops obeying its own Controller Configuration enable bit (CC.EN), the only remaining tools are PCIe resets. They are also what every boot, every hot plug, every virtual machine device assignment, and every Downstream Port Containment recovery uses. Getting them wrong produces some of the most confusing symptoms in storage engineering: devices that read back all-ones, drives that "vanish" for exactly one second, virtual machines that get a device with stale state, and recovery code that works on one platform and hangs on another because of a 100 ms rule.

PCIe resets also differ from NVMe resets in a fundamental way: they reset transport state — link training, flow-control credits, configuration space, Base Address Registers (BARs), interrupt configuration — which the NVMe driver depends on but does not own.

Learning objectives

  • Classify PCIe resets: Conventional Reset (Fundamental Reset — cold and warm — and Hot Reset), Function Level Reset (FLR), and the link-down events that behave like resets.
  • Explain PERST#, how a Hot Reset propagates in-band in training ordered sets, and what Secondary Bus Reset and Link Disable do.
  • List what each reset clears: link state, configuration space, sticky bits, other functions, the NVMe controller.
  • Apply the readiness rules after reset (the 100 ms waits, Configuration Request Retry Status) and know which details must be checked in your specification revision.
  • Recognize hot plug and surprise removal on a trace and in Linux.
  • Use Linux safely to inspect reset capability and, on test hardware, perform resets.
  • Debug "the device came back wrong" by finding the first abnormal event after a reset.

The story

The library is in a building with a road leading to it. There are four ways to start the library over. You can switch off the whole town's electricity and switch it back on — everything restarts, even the clocks. You can keep the electricity on but press the big red "everyone restart" button at the building door. You can phone down the road and shout the secret word "RESTART!" — the road workers repeat it to every building on that road. Or you can walk into one room and tell just that one librarian to start over, while the road and the other rooms carry on.

After any of these, the librarian needs a moment to put her coat on. If you ask her a question too soon, she says "come back later" — and you are supposed to wait, not give up.

A ship's engine room has several levels of restart. A dead-ship recovery (cold start) brings up generators from nothing. A main switchboard reset (warm) restarts every system while generators keep running. The bridge can ring "finished with engines" down the telegraph, and each station along the chain relays it (hot reset, propagated hop by hop). Or a single machine can be isolated and restarted by its own breaker (FLR) while the rest of the ship keeps steaming. After every restart, the crew follows a minimum warm-up time before the officer may demand full power — and a station may answer "not yet" during warm-up.

Where it breaks: a PCIe Hot Reset is not a message a device can choose to ignore; it is a link-training state that forces reset. An FLR is not perfectly isolated: it is designed to leave the shared link alone, but a function that is mid-transaction can still leave completions in flight that the rest of the system must tolerate. And "come back later" (Configuration Request Retry Status) only applies to configuration requests: a memory read to a device that is not ready does not politely retry — it fails.

Beginner explanation

PCIe defines two big families of reset.

Conventional Reset resets a whole device (all its functions) and the link to it. It has three flavours:

  • Cold reset — main power is applied after being off. Everything starts from zero.
  • Warm reset — power stays on, but the platform asserts the reset signal PERST# (PCI Express Reset; the # means active-low) on the slot.
  • Hot reset — a reset sent in-band over the link itself, using special training patterns. Software triggers it by setting the Secondary Bus Reset bit in the bridge above the device.

Cold and warm are together called Fundamental Reset (hardware-driven). Hot reset is the non-fundamental member of the conventional family.

Function Level Reset (FLR) resets one function of a device — for an NVMe SSD, typically the function hosting the NVMe controller — without touching the link or other functions.

After a reset, the device needs time. Software must wait before it talks to the device, and even then the device may answer configuration reads with a "retry later" status for a while. Once it answers normally, software restores the configuration (BARs, enables, interrupts) and only then can the NVMe driver start its own initialization from Chapter 48.

Engineering explanation

The taxonomy, precisely

Fundamental Reset and PERST#

A Fundamental Reset is applied by hardware. On add-in cards and M.2/U.2 form factors the mechanism is the PERST# sideband signal defined by the form-factor (electromechanical) specification, such as the PCI Express Card Electromechanical (CEM) Specification. The platform holds PERST# asserted while power rails ramp and the reference clock (REFCLK) stabilizes, then deasserts it; the device's internal reset logic releases and the LTSSM starts in Detect.

  • Cold: power off → on. Everything including "sticky" register bits and auxiliary-power state is lost.
  • Warm: PERST# asserted with main power maintained. Sticky bits (registers marked as sticky, such as AER error status, which survive non-cold resets for post-mortem logging) are preserved if the device kept auxiliary power to them.

Timing between power-stable, REFCLK-stable and PERST# deassertion is specified in the form-factor specification (for CEM, a parameter commonly quoted as at least 100 ms from power stable to PERST# deassertion). Uncertain — confirm the exact parameter names and values in the CEM or M.2 specification for your form factor and revision; they are not in the NVMe specifications.

Hot Reset: an in-band command carried by link training

Training Sequence ordered sets (TS1 and TS2, from Chapter 9) carry a Training Control field with bits for Hot Reset, Disable Link, Loopback, Disable Scrambling and Compliance Receive. A Downstream Port triggers a Hot Reset by:

  1. Software sets Secondary Bus Reset (SBR) in the Bridge Control register of the Root Port or switch Downstream Port (the bridge above the device).
  2. The port's LTSSM goes through Recovery into the Hot Reset state and transmits TS1 ordered sets with the Hot Reset bit set.
  3. The device's Upstream Port receives two consecutive TS1s with Hot Reset set, enters its own Hot Reset state, and resets everything except sticky state. If it is a switch, it propagates Hot Reset out of all its Downstream Ports.
  4. When software clears SBR (after at least the minimum hold time, commonly cited as 1 ms — Uncertain, check "Reset Rules"), the link goes to Detect and retrains.

A Hot Reset reaches every function of every device below that bridge. For a single-function NVMe SSD directly under a Root Port, that is exactly the SSD; below a switch Downstream Port, it is the device on that port; on a switch Upstream Port, it is the switch and everything below it.

Link Disable and link down

Setting Link Disable in a Downstream Port's Link Control register drives the LTSSM to the Disabled state (TS1s with Disable Link set, then electrical idle). The link stays down until software clears the bit. Separately, whenever a link goes down — the Data Link Layer reports DL_Down — the component below it is reset as if by a Hot Reset. Derived from the specification's rule that a link-down condition resets downstream components; confirm the wording in "Reset Rules" and "Data Link Control and Management State Machine". Consequence for NVMe: any event that drops the link (a surprise removal, a link failure, a Downstream Port Containment trigger, an NVM Subsystem Reset that the device implements by dropping the link) is a controller-level reset for the NVMe controller.

Retrain Link is not a reset. Link Control's Retrain Link bit sends the LTSSM through Recovery and back to L0 (for example after changing the target speed). Configuration space, the Data Link Layer's active state and the device are not reset; Transaction Layer Packets (TLPs) in flight are protected by the replay mechanism. People confuse "retrain" with "hot reset" in bug reports constantly.

Function Level Reset

FLR was introduced so that software — especially a hypervisor assigning a function to a virtual machine — can reset one function to a clean state without disturbing the link or other functions.

  • Capability: Device Capabilities register, Function Level Reset Capability bit. If clear, the function does not support FLR.
  • Trigger: write 1 to Initiate Function Level Reset (bit 15) in the Device Control register of the PCI Express Capability. The bit always reads as 0.
  • Before: software should stop the driver and wait for outstanding non-posted requests issued by the function to finish — the Transactions Pending bit in Device Status shows whether any are outstanding. An FLR with requests outstanding may produce completions that arrive for a function that no longer expects them (Unexpected Completions, Chapter 52).
  • During: the function must complete the FLR within a time bound (commonly quoted as 100 ms) and software must not access it before then (unless readiness notification says otherwise).
  • Effect: function state returns to its post-reset defaults, except sticky bits, hardware-initialized fields, and fields that control the shared link (which belong to the port, not just this function). BARs, the Command register (Memory Space Enable, Bus Master Enable), MSI/MSI-X configuration and the NVMe controller state are reset.

The exact list of fields an FLR must preserve, and the exact behaviour for requests in flight during an FLR, are in the PCI Express Base Specification section on Function Level Reset. Read it once in full; this course summarizes rather than quotes it.

Single-root I/O virtualization (SR-IOV, Chapter 56) adds a twist: an FLR of a Physical Function also resets its Virtual Functions; an FLR of a Virtual Function affects only that VF. NVMe controllers exposed as VFs rely on VF FLR for safe reassignment between virtual machines.

Readiness after reset: the rules to check in your revision

After a reset, a device may be internally busy (loading firmware, initializing media controllers). PCIe gives it two tools: a mandatory waiting period during which software must not send it requests, and a retry status it may return for Configuration Requests while it is still initializing.

The retry status was historically called Configuration Request Retry Status (CRS). In the PCIe 6.0 era it was generalized and renamed Request Retry Status (RRS) Version-dependent. If the Root Port has CRS Software Visibility enabled (Root Control register), a configuration read of the Vendor ID that receives CRS returns the special value 0001h to software instead of being retried automatically by hardware, so software can poll without stalling the CPU.

CRS/RRS protects only configuration requests. After the device answers configuration reads, the NVMe controller may still not be ready — that is what CSTS.RDY and CAP.TO are for. The two readiness layers are independent: PCIe readiness (can I talk to the function?) then NVMe readiness (is the controller ready for commands?).

Hot plug and surprise removal

A hot-plug capable Downstream Port has a Slot Capabilities register (presence detect, power controller, attention button, Data Link Layer State Changed events). Two removal styles exist:

  • Orderly removal: an operator requests removal (attention button or software); the OS stops the driver, which shuts the NVMe controller down (CC.SHN), then the slot is powered off.
  • Surprise removal: the device disappears without warning (pulled out, power failure, link death). The Downstream Port sees the link go down; if it supports Surprise Down Error reporting it may log a Surprise Down error (an uncorrectable Data Link Layer error); presence-detect or link-state-change interrupts fire. All in-flight requests to the device fail: memory reads return Unsupported Request or time out, and software sees all-ones (0xFFFF_FFFF).

Downstream Port Containment (DPC) is a related mechanism: on a configured uncorrectable error, the Downstream Port deliberately takes the link down and blocks traffic to contain the error. To the NVMe controller below, DPC looks exactly like a surprise link-down followed (after software releases containment) by a Hot-Reset-equivalent retrain. See Chapter 55 — Advanced Error Handling.

The ladder for a Hot Reset (Secondary Bus Reset)

Someone shouts the secret word down the road; every building on it restarts, and the librarian needs time to put her coat on.

Software sets Secondary Bus Reset in the bridge above the SSD, waits, clears it, waits for the link and readiness, restores configuration space, then the NVMe driver reinitializes the controller.

The Root Port's LTSSM enters Hot Reset and transmits TS1s with the Hot Reset bit; the SSD's PHY recognizes them and drives its internal reset; everything except sticky state is reset; when the bit clears, both ends retrain from Detect.

PCI Express Base Specification: Hot Reset is a Conventional Reset that is not Fundamental; it is signalled in-band; after it, the readiness rules apply. NVMe Base / PCIe Transport: a PCIe Conventional Reset is a controller-level reset.

No TLPs flow during the reset. Ordered sets (TS1 with Hot Reset, then electrical idle, then TS1/TS2 training) carry the event. After training, the first TLPs are Configuration Requests from the Root Complex, possibly answered with CRS/RRS.

An analyzer shows L0 traffic stop, TS1 ordered sets with Hot Reset set, electrical idle, Detect/Polling/Configuration training, Data Link Layer initialization (InitFC DLLPs), then CfgRd0 to Vendor ID with CRS completions, then successful completions, then CfgWr0 to BARs and Command.

If the device never leaves CRS, the device firmware is stuck in early boot. If the link never trains, look at REFCLK, power and PHY. If config works but NVMe CSTS reads all-ones, Memory Space Enable or BARs were not restored — a host bug.

The sixteen questions, applied to Function Level Reset

1. What is it?
A reset of one PCIe function triggered through its Device Control register.
2. Why was it created?
To reset a single function, especially for virtualization, without disturbing the link or sibling functions.
3. What problem does it solve?
Clean hand-off of a device between owners (VMs, containers), and recovery without collateral damage.
4. What existed before it?
Bus-level resets (PCI RST#, PCIe Hot Reset) that reset everything below a bridge, and PM-based soft resets that many devices did not implement.
5. Why is the current design better?
Targeted, discoverable (capability bit), with a defined completion time and preserved link.
6. Who creates it?
System software (OS PCI core, hypervisor, VFIO).
7. Who consumes it?
The function's hardware/firmware.
8. Where does it live?
PCI Express Capability: Device Capabilities (FLR Capability) and Device Control (Initiate FLR).
9. What memory/registers are involved?
Device Control, Device Status (Transactions Pending), Command register, BARs, MSI-X capability and table, and every NVMe register behind the BAR.
10. What happens before it?
Driver unbinds or quiesces; software saves configuration state; waits for Transactions Pending to clear.
11. What happens after it?
Wait for readiness; restore configuration; driver reinitializes NVMe from CC.EN = 0.
12. What happens if it is wrong?
Accessing too early gives CRS/UR/all-ones; forgetting to restore gives no MMIO and no DMA; FLR with pending requests gives Unexpected Completions on the host side or lost data.
13. What does the protocol analyzer show?
A CfgWr0 to Device Control, a quiet period, then config reads (possibly CRS), then config writes restoring state, then NVMe register traffic. The link stays in L0 throughout.
14. What does Linux show?
FLReset+ in lspci -vv DevCap; flr in reset_method; log lines when a device is slow to become ready after reset (wording version-dependent).
15. What would a validation engineer test?
FLR completion time; FLR under maximum outstanding DMA; NVMe state fully reset; sticky bits preserved; no traffic from the function during FLR; sibling functions unaffected.
16. What would a senior engineer suspect when it fails?
Firmware that does not truly reset the NVMe back end, an FLR implemented as a PERST#-like full reset that drops the link (non-compliant), or host software that skipped the readiness wait.

Hardware view

  • PERST# is a wire; nothing the device does can ignore it. While it is asserted, the device's PCIe logic is held in reset.
  • REFCLK must be stable before PERST# deasserts, or PLLs may lock badly and link training fails intermittently — a classic board-bring-up bug.
  • Hot Reset needs a working link: it is carried by ordered sets. If the link is already dead, software must fall back to a slot power cycle or a platform-controlled PERST#.
  • FLR is implemented inside the device: firmware or hardware resets the function's register state and the NVMe controller logic, but must keep the PHY, the Data Link Layer and flow control running.
  • Firmware CPUs: on many SSDs a Fundamental Reset restarts the controller firmware from its boot ROM, which is why the device needs hundreds of milliseconds and uses CRS/RRS. An FLR may only reset the host-interface firmware tasks. That is why FLR is often faster.

U.2/U.3 and EDSFF drive bays add drive-presence and power-disable sideband signals (for example a power-disable pin that lets the platform cold-reset one drive without pulling it). Their exact names and timings are defined by the form-factor specifications (SFF-TA family), not PCIe Base — check those documents for your bay.

Specification view

Primary source: PCI Express Base Specification, Revision 6.x/7.0 — Reset Rules; Function Level Reset; Link Training and Status State Machine (Hot Reset, Disabled states); Configuration Request Retry Status / Request Retry Status; Readiness Notifications. This is a PCI-SIG members' document. Form-factor timing: PCI Express Card Electromechanical Specification (or M.2 / SFF-TA documents). NVMe mapping: NVM Express Base Specification 2.4 — Resets and NVMe over PCIe Transport Specification 1.4.

The family names (Conventional Reset, Fundamental Reset with cold and warm forms, Hot Reset, FLR), the Initiate Function Level Reset bit in Device Control (bit 15), the FLR Capability bit in Device Capabilities, the Secondary Bus Reset bit in Bridge Control, the Link Disable and Retrain Link bits in Link Control, and the use of TS1/TS2 ordered sets to signal Hot Reset are stable PCIe concepts. The NVMe Base specification lists PCIe conventional reset and FLR among the events that cause a controller-level reset.

Because every conventional reset retrains the link and every FLR resets the function's configuration, a host must restore configuration space after either; this is why Linux saves state before a reset and restores it afterward. Because CRS applies only to configuration requests, MMIO to an unready function cannot be "retried" by hardware.

How long a device actually takes to become ready, whether FLR also restarts firmware, whether NVMe-level state like the Host Memory Buffer is released cleanly, whether a device implements the PM reset (No_Soft_Reset = 0), and how a Root Port behaves while a link is down (completion timeout vs immediate UR for MMIO) are implementation-dependent — and platform-dependent on the Root Complex side.

CRS was generalized to RRS in the 6.0 era; Readiness Notifications, Readiness Time Reporting and Immediate Readiness were added in later 3.x/4.0-era revisions; Flit Mode (6.0) changed the ordered-set and TLP framing used on the link but not the reset concepts. When reading a trace or a spec quote, note which revision the device and analyzer software implement.

The specifications do not say which reset an operating system should choose, how long a driver should wait for NVMe readiness beyond CAP.TO, or how a hypervisor must sanitize a device between virtual machines. Things to check in the spec revision before relying on them: every timing value in the readiness table above; the precise list of registers preserved across FLR; the minimum Secondary Bus Reset assertion time; and the exact rule for when a device may first return CRS/RRS.

Never assume: that FLR is supported (check the capability); that a PM reset resets anything (check No_Soft_Reset); that a device is ready after the 100 ms wait (it may legally return CRS/RRS longer); that a link-up means the NVMe controller is ready; that Secondary Bus Reset affects only your device (it affects everything below the bridge, including other functions and devices behind a switch).

Configuration Request Retry Status in a completion

A CRS/RRS response is a Completion without data whose Completion Status field carries the retry encoding (010b in the classic encoding). It carries the Requester ID and Tag of the configuration read, like any completion. With CRS Software Visibility enabled and the request being a read of the Vendor ID register, the Root Complex returns 0001h as Vendor ID to software; otherwise the Root Complex re-issues the request itself, which can stall the CPU for a long time.

The Root Port answers requests on the device's behalf (here with UR; some platforms instead let requests time out, which takes milliseconds and may raise a Completion Timeout). Linux's NVMe driver detects the disconnected device, fails all I/O immediately rather than retrying, and removes the controller. In-flight read data (row 1) may have partially landed — the block layer reports errors for those requests.

lspci shows FLR support as FLReset+ in DevCap, Secondary Bus Reset as BusReset+/- in BridgeCtl, and Data Link Layer Link Active as DLActive+ in LnkSta on capable ports. The reset_method attribute lists methods such as flr, pm, bus and device_specific (exact names and availability are Version-dependent; the attribute appeared in Linux 5.15-era kernels).

What this proves: capabilities and current state. What it cannot prove: how long the device actually needs to become ready, or whether an FLR fully resets the NVMe back end.

How the kernel performs a reset

The PCI core's pci_reset_function() family saves configuration state, tries the device's reset methods in order (device-specific quirk, FLR, PM reset, bus/slot reset), waits for readiness, and restores state. Readiness waiting polls the Vendor ID and tolerates CRS for a long, bounded time (the PCI core has used a timeout on the order of a minute); the log reports when a device is slow, using wording that changes between versions. The NVMe driver's reset path (nvme_reset_work) runs on top of this when the PCI core or AER/DPC recovery resets the device, through the driver's PCI error-handler callbacks (error_detected, slot_reset, resume) and reset-prepare/done hooks.

Actions that change state

Caution lab echo 1 | sudo tee /sys/bus/pci/devices/0000:01:00.0/reset performs a function reset using the kernel's preferred method; the NVMe driver is notified and recovers. Never on a device holding mounted file systems you need. Caution lab echo 1 | sudo tee /sys/bus/pci/devices/0000:01:00.0/remove followed by echo 1 | sudo tee /sys/bus/pci/rescan simulates an orderly removal and re-enumeration. Expert lab Toggling Secondary Bus Reset by hand with setpci on a bridge bypasses the kernel's save/restore and resets every device below that bridge; on the wrong bridge it can hang the machine. Do not do it outside a dedicated test system with remote power control.

Code / pseudocode

int safe_function_reset(struct pcidev *d)
{
    if (!(cfg_read32(d, PCIE_CAP + DEVCAP) & DEVCAP_FLR))
        return try_other_methods(d);           /* PM reset if No_Soft_Reset == 0, else bus reset */

    driver_quiesce(d);                          /* NVMe: stop queues, CC.SHN or CC.EN=0 */
    save_config_space(d);                       /* BARs, Command, MSI-X, DevCtl, LnkCtl, ... */
    cfg_clear_bits16(d, COMMAND, BUS_MASTER);   /* stop new DMA */

    for (int t = 0; t < 4; t++) {               /* wait for Transactions Pending to clear */
        if (!(cfg_read16(d, PCIE_CAP + DEVSTA) & DEVSTA_TRPND)) break;
        sleep_ms(100 << t);
    }
    cfg_set_bits16(d, PCIE_CAP + DEVCTL, DEVCTL_BCR_FLR);   /* Initiate FLR */
    sleep_ms(100);                              /* readiness rule: check your spec revision */

    if (wait_config_ready(d, /*timeout_ms*/ 60000) != 0) /* tolerate CRS/RRS */
        return -ETIMEDOUT;
    restore_config_space(d);                    /* BEFORE any BAR access */
    return driver_reinit(d);                    /* NVMe: Chapter 48 sequence from CC.EN=0 */
}

A runnable simulation of readiness polling, so you can see why "wait 100 ms then give up" is wrong:

#!/usr/bin/env python3
"""Simulate post-reset readiness: CRS/RRS period, then config OK, then NVMe CSTS.RDY."""
import random

def simulate(seed, pcie_ready_ms, nvme_ready_ms, poll_ms=10, give_up_ms=None):
    random.seed(seed)
    t = 100                      # mandatory wait already done (check your spec revision)
    crs = 0
    while t < pcie_ready_ms:
        crs += 1
        if give_up_ms is not None and t >= give_up_ms:
            return f"gave up at {t} ms after {crs} CRS replies (device was fine!)"
        t += poll_ms
    t_cfg = t
    t += 2                       # restore BARs, Command, MSI-X
    t_rdy = t + nvme_ready_ms    # NVMe layer: CC.EN=1 -> CSTS.RDY=1 (bounded by CAP.TO)
    return (f"config ready at {t_cfg} ms after {crs} CRS replies; "
            f"NVMe RDY at {t_rdy} ms")

if __name__ == "__main__":
    print("robust host :", simulate(1, pcie_ready_ms=310, nvme_ready_ms=410))
    print("naive host  :", simulate(1, pcie_ready_ms=310, nvme_ready_ms=410, give_up_ms=200))
    print("fast device :", simulate(1, pcie_ready_ms=90, nvme_ready_ms=40))

Expected output: the robust host sees configuration ready at 310 ms after 21 CRS replies and NVMe ready at 722 ms; the naive host gives up at 200 ms although the device was healthy; the fast device needs no CRS polling at all because it was ready before the mandatory wait ended.

Worked example

Question (synthetic): A hypervisor resets the Lab SSD between two virtual machines. FLR is supported. The device needs 180 ms of internal time after FLR before answering configuration reads successfully, and CAP.TO = 20, with EN→RDY typically 410 ms. What is the minimum and maximum time from "start reset" until the new VM's driver can submit its first admin command, and what dominates?

  1. Quiesce the old owner's controller: normal shutdown takes up to RTD3E — but a hypervisor typically just disables (CC.EN = 0): ~40 ms typical, up to 10 s (CAP.TO).
  2. Transactions Pending check: usually immediate after the controller is disabled.
  3. FLR + mandatory wait: 100 ms. Then CRS polling until 180 ms: +80 ms.
  4. Restore configuration: ~1 ms.
  5. NVMe enable: typical 410 ms, worst case 10 s.
Thandoff = Tquiesce + max(Twait, Tflr) + Trestore + Ten→rdy
Thandoff
time from start of reset to the new owner's first admin command
Tquiesce
time to stop the old controller (CC.EN = 0 to RDY = 0)
Twait
mandatory post-FLR wait required by the specification (commonly 100 ms; check revision)
Tflr
time the device actually needs before answering configuration requests successfully
Trestore
configuration restore time
Ten→rdy
NVMe enable time, bounded by CAP.TO × 500 ms

Typical: 40 + 180 + 1 + 410 ≈ 631 ms. Worst case allowed by the device's own declarations: 10,000 + (bounded CRS period, commonly 1 s for conventional reset; check the FLR rule) + 1 + 10,000 ≈ 21 s. The NVMe layer, not PCIe, dominates. This is why virtualization stacks measure "time to ready" per drive model.

Common mistakes

  • Treating the completion of the FLR configuration write as "reset done". It only means the write was accepted.
  • Touching BARs before restoring configuration after FLR or conventional reset: UR, all-ones, misdiagnosed as a controller fatal error.
  • Giving up on CRS/RRS too early. Retry status is a legal, bounded "not yet", not a failure.
  • Using Secondary Bus Reset on a bridge that has several devices below it (a switch Upstream Port, or a multi-device slot). Everything below is reset, including devices owned by other drivers or other VMs.
  • Calling Retrain Link a reset. It isn't.
  • Assuming PM reset works. If No_Soft_Reset = 1, D3hot → D0 preserves state; nothing is reset.
  • Ignoring Transactions Pending before FLR, leading to Unexpected Completions or completions for a reset function.
  • Forgetting Device Control fields (MPS, MRRS, Relaxed Ordering enable, No Snoop enable) in restore code: the device works, but differently.
  • Equating PCIe readiness with NVMe readiness. Config reads succeeding says nothing about CSTS.RDY.

Senior engineer insight

Every reset is a contract between three parties: the platform (power, PERST#, Root Port behaviour while the link is down), the device (PCIe readiness, then NVMe readiness), and the OS (save, wait, restore, reinitialize). When a reset "doesn't work", find which party broke its part of the contract first — the first abnormal event — before blaming the device.

  • Root Port behaviour while a link is down is platform-specific: some return UR quickly, some let requests time out (Completion Timeout ranges in Chapter 52). That changes how long a CPU stalls on an MMIO read to a dead device — sometimes enough to trigger watchdogs.
  • Time-to-ready after each reset type is a product metric: VM hand-off latency, hot-plug service time, DPC recovery time. Measure it per firmware release.
  • Multi-function and SR-IOV devices make the scope of each reset an architecture decision. Document which resets the device supports per function and what each clears — your customers' hypervisors depend on it.
  • For security (device assignment), a reset must clear all tenant-visible state. Validation should prove it, not assume it.

Lab: map the reset options and readiness behaviour of your NVMe device

Objective

Determine which PCIe resets your NVMe device supports, what scope each would have on your topology, and — on a test system — measure FLR and NVMe readiness times.

Skills

Reading Device Capabilities/Control/Status, Bridge Control and slot registers; reasoning about reset scope; correlating PCI core and NVMe driver logs.

Safety

Steps 1–3 Safe lab (read-only and simulation). Step 4 Caution lab: non-boot test drive, nothing mounted, test machine. Manual SBR via setpci is excluded.

Hardware required

Linux machine with an NVMe SSD; a spare test SSD for step 4.

Software required

pciutils (lspci), nvme-cli, Python 3.

Input

The BDF of your SSD (from lspci -nn | grep -i 'non-volatile') and its upstream bridge (from lspci -tv).

Expected output

A table: FLR supported?, No_Soft_Reset value, reset_method list, devices sharing the upstream bridge, Data Link Layer Link Active reporting capable?, hot-plug capable slot?, and measured FLR-to-NVMe-ready time (step 4).

Background

The taxonomy table and readiness rules in this chapter.

Step 1

Run sudo lspci -vvv -s <BDF>. Find FLReset in DevCap, the PM capability's NoSoftRst, and DevSta TransPend.

Step 2

Find the upstream bridge and run sudo lspci -vvv on it. Record BridgeCtl BusReset, LnkCap (Surprise Down reporting, DLActive reporting), SltCap (hot-plug).

Step 3

Read reset_method. Predict which method /sys/bus/pci/devices/<BDF>/reset would use and which devices it would affect. Run readiness_sim.py with your guess of timings.

Step 4 (caution)

On the test drive: note the time, write 1 to the device's reset attribute, and collect dmesg -T. Read /sys/class/nvme/nvmeX/state until it is live again.

Observation

Did the link retrain (look for link down/up messages)? Did the NVMe driver log a reset? How long until "live"?

Questions

  1. If reset_method lists only bus, what is the risk on your topology?
  2. Why might the measured time be much longer than 100 ms even though nothing failed?
  3. Why is the BAR address usually the same after the reset?

Challenge

Write a Python script that parses lspci -vvv text for a given BDF and prints a reset-capability report (FLR, NoSoftRst, upstream bridge, siblings below that bridge).

Hints

The kernel restores the saved BAR values; it does not re-run resource assignment. Readiness includes both PCIe readiness and NVMe CC.EN→RDY. For the challenge, lspci -tv or /sys/bus/pci/devices/<BDF>/.. (the parent directory) gives the upstream bridge.

Solution

Q1: a bus reset resets every device below the upstream bridge; on a Root Port with only your SSD below, that is acceptable; below a switch port shared by functions of a multi-function device, or on a switch Upstream Port, it hits other devices. Q2: the device may return CRS/RRS for a while, the kernel polls with sleeps, the NVMe driver then waits for CSTS.RDY (bounded by CAP.TO), and runs Identify/queue setup — hundreds of milliseconds is normal. Q3: Linux saves configuration space before the reset and restores the same BAR values afterward; the resources were never released. Challenge: a model approach reads /sys/bus/pci/devices/<BDF> symlink target to get the parent bridge, lists other devices whose sysfs path shares that parent, and greps lspci output for FLReset+ and NoSoftRst+.

What a senior engineer notices

Whether the device supports FLR at all (consumer drives sometimes do not), whether NoSoftRst+ makes the PM method useless, whether the topology makes bus reset dangerous, and whether the NVMe ready time after FLR is suspiciously similar to the cold-boot time (suggesting FLR restarts all firmware).

Failure variants

  • The reset write returns an error: no usable method, or the device is bound to a driver that refuses.
  • The device never returns: firmware hang; capture logs and use a cold reset.
  • The device returns with a lower link speed or width: retraining produced a different result; check LnkSta and correctable errors (Ch 9).

Exercises

  1. Classify: (a) the platform BMC toggles PERST# with power on; (b) Linux sets Secondary Bus Reset; (c) the SSD is yanked; (d) DPC triggers on a Root Port; (e) a hypervisor writes Initiate FLR.
  2. For each reset in (1), state whether AER sticky status on the SSD survives.
  3. Explain why a Root Port's link going down acts as a reset for the device below, using the Data Link Layer state machine.
  4. An engineer says "after FLR wait 100 ms, then the controller is ready." List the two separate readiness checks they are missing.
  5. Why does CRS Software Visibility only work for reads of the Vendor ID register?
Answers

1. (a) Fundamental Reset — warm; (b) Conventional Reset — Hot Reset; (c) surprise link down → reset-equivalent when (if) it comes back, with a Surprise Down error; (d) link down by containment → reset-equivalent; (e) FLR.

2. Sticky bits survive warm reset (with aux power), hot reset, link down and FLR; they are lost only on cold reset (or if aux power was not maintained). For (c), the device lost power when removed, so its sticky bits are gone too.

3. When the Data Link Layer goes to DL_Inactive (DL_Down), the specification requires the component below to be reset as if by a Hot Reset, because flow-control state and in-flight transactions can no longer be trusted. Confirm the exact rule in the spec.

4. (i) PCIe readiness: configuration reads may still return CRS/RRS; poll until success. (ii) NVMe readiness: after restoring configuration, CC.EN = 1 and wait CSTS.RDY = 1 (CAP.TO). Plus restore configuration between the two.

5. The Vendor ID is never 0001h for a real device (it is a reserved value), so returning 0001h is an unambiguous in-band signal to software; other registers have no reserved value that could be used that way.

Quiz

  1. Which reset is signalled in-band with TS1 ordered sets?

    • Warm reset
    • Hot Reset
    • FLR
    • Cold reset
    Answer and reasoning

    Hot Reset uses the Hot Reset bit in TS1 Training Control. Warm and cold use sideband PERST#/power. FLR is a configuration write and the link stays in L0.

  2. Which reset keeps the link in L0?

    • Hot Reset
    • Link Disable
    • FLR
    • Warm reset
    Answer and reasoning

    FLR resets the function, not the link; DLLPs continue throughout.

  3. Which register bit triggers FLR?

    • Initiate Function Level Reset in Device Control
    • Secondary Bus Reset in Bridge Control
    • Retrain Link in Link Control
    • CC.EN in NVMe CC
    Answer and reasoning

    Device Control (bit 15) of the PCI Express Capability.

  4. A configuration read after reset receives a completion with retry status. What should software do?

    • Declare the device dead
    • Issue a Hot Reset
    • Switch to MMIO reads
    • Retry until success or a bounded timeout
    Answer and reasoning

    CRS/RRS is a legal "not yet". MMIO does not help — the function is not configured and memory requests are not retried.

  5. Which reset can unintentionally hit devices other than the target?

    • FLR of a single-function device
    • Secondary Bus Reset
    • NVMe CC.EN
    • Delete I/O SQ
    Answer and reasoning

    SBR resets everything below the bridge.

  6. Why does a completion from a just-reset device sometimes show Completer ID 0000h?

    Model answer

    Endpoints capture their bus and device numbers from the first Type 0 Configuration Write after reset. Before that, they may not know their own ID.

  7. Why can a PM-based reset be a no-op?

    Model answer

    If the PM Control/Status register's No_Soft_Reset bit is 1, the function keeps its state across D3hot → D0, so the transition resets nothing.

  8. Name two differences between Retrain Link and Hot Reset.

    Model answer

    Retrain Link goes through Recovery and back to L0 keeping Data Link Layer state, configuration and the device intact; Hot Reset goes through the Hot Reset state to Detect, resets the device and its configuration, and requires flow-control re-initialization and readiness waits.

  9. After an SBR, configuration reads succeed, BARs are restored, but CSTS.RDY stays 0 for 3 s. Is that a PCIe problem?

    Model answer

    No. PCIe readiness is complete; the NVMe controller is initializing. It is acceptable if 3 s is within CAP.TO (or the applicable CRTO value). It becomes a problem only if RDY stays 0 beyond that, or CFS is set.

  10. What is the first thing to check when CSTS reads 0xFFFF_FFFF after any PCIe reset?

    Model answer

    Whether the function is configured and reachable: link up, Command.Memory Space Enable set, BAR0 restored. All-ones is a PCIe-layer symptom (UR or timeout), not an NVMe register value.

Interview questions

  1. Beginner: What is PERST#?

    Model answer

    The active-low PCI Express Reset sideband signal from the platform to a device (defined in form-factor specifications) that applies Fundamental Reset; deasserting it after power and REFCLK are stable lets the device start link training.

  2. Beginner: Fundamental vs Hot Reset?

    Model answer

    Fundamental is hardware-applied (power cycle or PERST#); Hot Reset is in-band over a working link via training ordered sets, triggered by a bridge's Secondary Bus Reset. Both are Conventional Resets.

  3. Intermediate: What must Linux do around an FLR?

    Model answer

    Notify the driver (reset_prepare), save config, check Transactions Pending, initiate FLR, wait the required time, poll for readiness tolerating CRS/RRS, restore config, notify the driver (reset_done) which reinitializes the NVMe controller.

  4. Intermediate: Why does an NVMe driver see all-ones after surprise removal?

    Model answer

    MMIO reads no longer reach a completer; the Root Port returns UR or the request times out, and the Root Complex returns all-ones data to the CPU. Drivers treat all-ones from CSTS as "device gone or unreachable".

  5. Advanced: How does DPC interact with NVMe recovery?

    Model answer

    DPC takes the link down on an uncorrectable error to contain it. The NVMe controller below is effectively reset. The OS's error recovery calls the driver's error handlers, waits for the link to come back after releasing DPC, restores config, and the driver reinitializes. In-flight I/O fails or is retried depending on driver policy. See Ch 55.

  6. Advanced: Why did the specification introduce readiness notifications?

    Model answer

    Fixed worst-case waits (100 ms, up to 1 s of CRS) slow down VM hand-off, resume and hot plug. Devices that are ready earlier can say so, and software can avoid fixed delays.

  7. Senior: A customer's hypervisor sometimes leaks data between tenants via an NVMe VF. Where do you look?

    Model answer

    Whether VF FLR is issued between tenants; whether the device's FLR resets all tenant-visible state (queues, controller memory buffer, HMB references, namespaces attached to the VF, cached data in controller buffers); whether the hypervisor waits for FLR completion before reassigning; test with known patterns; check the device's documentation and, for 2.4 features such as exported NVM subsystems, what the spec requires on reset.

  8. Senior: Design a reset-validation plan for a new SSD.

    Model answer

    Matrix: reset type (cold, warm, hot, link disable, FLR, NSSR, CC.EN) × device state (idle, max QD read/write, every admin command in progress, low-power states, firmware activation, during Format/Sanitize) × platform (several Root Ports and switches). Checks: link retrains at the expected speed/width, readiness within declared bounds, CRS behaviour, config defaults, sticky bit preservation, NVMe ready within CAP.TO, no DMA after reset, data integrity of completed writes, unsafe-shutdown accounting, repeatability over thousands of cycles.

Chapter summary

PCIe resets are Conventional (Fundamental: cold and warm via power and PERST#; Hot: in-band via TS1, triggered by Secondary Bus Reset, with link-down events acting similarly) or Function Level. All of them reset configuration space and the NVMe controller; conventional resets also retrain the link and reset every function on the device. After a reset, software waits the specified time (check the 100 ms rules and the CRS/RRS bounds in your revision), polls configuration reads tolerating retry status, restores configuration, and only then runs the NVMe initialization from Chapter 48. Hot plug and surprise removal look like link-down resets with no warning, produce all-ones reads, and are handled by pciehp, AER and DPC.

  • explain CRS/RRS and why it applies only to configuration requests
