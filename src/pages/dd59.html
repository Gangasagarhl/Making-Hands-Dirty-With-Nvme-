Senior architecture work in NVM Express (NVMe) over PCI Express (PCIe) is the art of choosing — queue counts, depths, interrupt policy, payload sizes, address translation, virtualization, transport — and of proving the choice with models, traces and tests before it ships. This module teaches a repeatable design-review method, the tradeoff template, formal lifecycle models with their invariants, design for debuggability, and how to explain a decision to five different audiences.

Orientation

Senior Engineer Thinking trained the thirteen questions for investigating a failure. Communication, Design Review and Formal Models introduced design review, the tradeoff template, "why not?" training and the ten lifecycle models. This module turns those into architecture practice: you will review real design choices on the course lab system, quantify them, predict how each shows up on the wire, define the invariants that make failures detectable, and write the decision so others can challenge it.

Assumed: queues and doorbells (Queue Architecture, Doorbells), MSI-X (Message Signaled Interrupts Extended) and interrupt coalescing (MSI-X), payload and read request sizes (TLP Header Anatomy), bandwidth and Little's law (Performance Engineering), Single Root I/O Virtualization (SR-IOV) (SR-IOV), and the fabrics mental model (NVMe-oF Mental Model).

Kid story

The school wants lunch to go faster. One teacher says: open more serving counters. Another says: give each counter a longer line. The cook says: instead of shouting "next!" for every child, shout once for every five children. A parent says: let the children watch the counter themselves instead of waiting for a shout. Each idea helps something and hurts something: more counters need more cooks; longer lines make the last child wait; shouting once for five makes the first child wait for the other four; watching the counter keeps children busy staring instead of eating. The head teacher draws a table: for each idea, what gets faster, what gets slower, what costs more, and how we will check that it worked.

Analogy boundary

What it represents. Counters are I/O queue pairs; line length is queue depth; shouting "next!" is an interrupt; shouting once for five is interrupt coalescing; children watching the counter is polling; the head teacher's table is the tradeoff template.

What it hides. In NVMe, the controller does not serve queues strictly one at a time: it fetches from many, executes in parallel inside, and completes out of order, under an arbitration scheme the host can only partly configure. "Cooks" are also shared: the media behind the controller limits throughput regardless of how many queues exist. Where it misleads. The story suggests each idea is a simple dial. Real knobs interact: coalescing hurts at low queue depth but helps at high; polling burns a CPU core even when idle; more queues need more MSI-X vectors and memory; and the link, the controller and the host CPU each saturate at different points.

An invariant is a design decision that can be checked by a machine. Write it once in the review and it becomes a detector in the forensic pipeline, an assertion in the driver, a firmware self-check and a validation test. Undocumented invariants become surprises.

Debugging decision tree as a heuristic

The central concept on the ladder: interrupt policy

Shout "next!" for every child, shout once for five, or let children watch the counter.

Per-completion interrupts minimize latency; coalescing trades latency for fewer interrupts; polling removes interrupt delay but spends CPU.

The controller decides when to write the MSI-X message for a CQ's vector; the CPU's interrupt controller turns it into a handler call; in polling, a core repeatedly loads CQ memory looking for the expected Phase Tag.

NVMe Base defines CQ interrupt enablement, vector assignment and the Interrupt Coalescing feature (threshold and time, with an exception for selected vectors); PCIe Base defines MSI-X messages, masking and pending bits. Exact field encodings: read Base 2.4.

Per-completion: one MWr32 per CQE. Coalesced: one MWr32 per batch. Polled: no MWr32 at all; head doorbells continue.

A trace with CQEs and head doorbells but no MSI-X is either a polled design or a lost-interrupt defect; the Create I/O CQ command's interrupt-enable setting decides which.

A latency regression only at low queue depth with interrupts rarer than completions points at coalescing; a CPU-saturated host at high IOPS with one interrupt per CQE points at the absence of it.

Sixteen questions: interrupt coalescing as a design choice

The course's sixteen questions applied to interrupt coalescing
QuestionAnswer
What is it? Why created?Aggregation of completions before an interrupt; created because per-completion interrupts cost CPU at high IOPS.
Problem solved? Before?Interrupt overhead; before, one interrupt per completion (or legacy shared interrupts).
Why better?Bounded by threshold and time, so the cost in latency is configurable.
Who creates, who consumes?Host configures (Set Features); controller enforces; CPU consumes fewer interrupts.
Where does it live? Registers?A controller feature value; MSI-X table and PBA in BAR0 (0x2000/0x3000 on the lab system).
Before / after?Before: CQE posted. After: MSI-X, handler, CQ head doorbell.
If wrong?Low-QD latency inflated by up to T; or interrupt storms if disabled at high IOPS.
Analyzer?Fewer MWr32 to 0xFEE0_xxxx than CQEs; CQE→MSI-X gaps up to T.
Linux?Interrupt counts per vector in /proc/interrupts versus completions; Get Features value.
Validation?Latency at QD1 and high QD; interrupt rate; boundary values; behaviour after reset.
Senior suspicion?A tool or driver option set it silently; the golden run used a different value.

Specification discipline

Applicable: NVM Express Base Specification, Revision 2.4 (queues, Create I/O SQ/CQ, Number of Queues and Interrupt Coalescing features, controller reset, CAP/CC fields); NVMe over PCIe Transport, Revision 1.4 (doorbells, MSI-X use); PCI Express Base Specification (Revision 6.x/7.0 family) (MPS, MRRS, RCB, MSI-X, ordering, completions); NVMe over TCP 1.3 and RDMA 1.3 Transports when the transport is the decision.

Normative facts this module relies on: SQEs are 64 bytes and CQEs 16 bytes for the NVM command set; doorbells begin at offset 1000h with stride 4 << CAP.DSTRD; a queue is full when the tail is one entry behind the head; CAP.MQES bounds queue size; MPS and MRRS are programmed in the PCIe Device Control register; a masked MSI-X vector sets its pending bit instead of sending. NVM Express Base Specification 2.4 — Queue Management; Controller Registers PCI Express Base Specification — Device Control; MSI-X Capability

The tradeoff template, the efficiency and coalescing models, the lifecycle state names and the decision tree are derived teaching tools. The lifecycles in particular are not the controller's internal states.

Implementation-dependent: arbitration behaviour beyond the defined mechanisms; how many queues a controller serves efficiently; internal parallelism; coalescing granularity; how a driver maps queues to cores; IOMMU performance. Optional mechanisms to check before designing on them: SGL support, Interrupt Coalescing behaviour details, weighted round robin arbitration, Controller Memory Buffer, Host Memory Buffer, SR-IOV.

Feature availability and field definitions change across revisions; NVMe 2.4 adds rate limiting and idle exit-latency limits that interact with these knobs (2026 NVMe 2.4 Updates). A design record names the revision it relies on.

The specifications do not say how many queues to create, what queue depth to use, whether to poll, or what coalescing values are "good". They define mechanisms; policy is architecture.

Never assume a knob behaves the same on another controller, that an optional feature is present, or that a lab-optimal setting suits a multi-tenant deployment. Never change production device settings to "try" a design; use a lab system.

Memory cost is concrete: 32 queue pairs × 1024 entries × (64 + 16) bytes = 2.5 MiB of pinned, DMA-mapped host memory — before PRP lists. On a host with many drives and many cores, queue sizing is a memory decision as much as a performance one.
