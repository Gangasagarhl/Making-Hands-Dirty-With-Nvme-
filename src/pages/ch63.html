The NVM Express (NVMe) Management Interface (NVMe-MI) lets a platform's management controller — usually a Baseboard Management Controller (BMC) — discover, monitor, configure and update NVMe drives without depending on the host operating system, and lets host software reach the same management functions in-band. This chapter separates the paths (System Management Bus (SMBus) / Inter-Integrated Circuit (I2C), PCI Express (PCIe) vendor-defined messages, in-band tunnelling), the actors (management controller, management endpoint, controller), and the functions (health polling, VPD, configuration, firmware update, enclosure management), against the NVMe-MI 2.2 baseline.

Why this chapter exists

Everything so far has assumed the host operating system is running, the NVMe driver is loaded, and admin and I/O queues exist. Data-centre operators cannot rely on that. A server may be powered on but still in firmware; the operating system (OS) may have crashed; the drive may sit in a storage enclosure whose host belongs to a customer. Operators still need to know: is the drive present? Is it hot? Is it wearing out? What is its serial number? Can I update its firmware or blink its locate light-emitting diode (LED)?

The NVMe Management Interface (NVMe-MI) specification answers those needs with a standard command set that travels over the platform's management buses as well as in-band. Validation engineers meet it in every server qualification; firmware engineers implement it in every enterprise solid-state drive (SSD); debug engineers meet it when a BMC poll collides with a host reset and someone asks why the drive "disappeared".

Learning objectives

  • Explain the difference between in-band and out-of-band management and when each is used.
  • Name the actors: Management Controller (for example a BMC), Management Endpoint, NVMe controller, and their relationships.
  • Describe the transport stack: NVMe-MI messages over the Management Component Transport Protocol (MCTP), over SMBus/I2C or over PCIe Vendor Defined Messages (VDMs); and NVMe-MI Send/Receive in-band.
  • Describe discovery, health monitoring (subsystem and controller health status polls), Vital Product Data (VPD), configuration, firmware update and enclosure management.
  • Recognise MCTP-over-PCIe-VDM traffic in a synthetic PCIe trace and reason about a failed management exchange.
  • State which details must be confirmed in NVMe-MI 2.2 and in the Distributed Management Task Force (DMTF) MCTP binding specifications.

The story

The library has a front door where the teacher sends request slips — that is the normal way in. But the library also has a little side window for the building caretaker. The caretaker never borrows books. Through the side window the caretaker asks: "Is the heating working? How old are the shelves? What is the library's name plate? Please put a new rule book in the office. Please flash the light over shelf 7 so I can find it." The side window works even when the teacher is asleep and the front door is locked.

The caretaker is the BMC. The side window is NVMe-MI out-of-band. Sometimes the teacher also asks caretaker-style questions through the front door — that is in-band NVMe-MI.

A building's facilities-management system talks to each air-handling unit over a separate low-speed control network, not over the tenants' office local area network (LAN). It reads temperatures and fault codes, pushes firmware, and sets setpoints, whether or not any tenant is in the building. NVMe-MI is that control network for drives: a separate, slower, always-available path that reports health and accepts configuration.

  • "Separate network" is only partly true. One out-of-band path (MCTP over PCIe VDM) shares the very same PCIe link as data traffic; it is logically separate, not physically separate. If the link is down, that path is down.
  • The caretaker can do more than read gauges. NVMe-MI can tunnel NVMe admin commands, including commands that change data (e.g. format, sanitize) if the device permits. That is why management access is a security boundary.
  • The side window has rules about sharing. Management and host commands reach the same controller; concurrency, resets and locking create interactions the analogy hides.
  • There are several windows. A subsystem can have more than one management endpoint (for example one per port), each a separate conversation.

Beginner explanation

There are two ways to manage an NVMe drive:

  • In-band: through the same path the host uses for storage — the host OS, the NVMe driver, the admin queue. Tools like nvme smart-log are in-band. Fast and familiar, but only works when the host OS and driver are healthy.
  • Out-of-band (OOB): through a separate management path driven by a management controller on the motherboard or enclosure, independent of the host OS. The BMC in a server talks to drives over the platform's SMBus/I2C wiring or over PCIe management messages.

NVMe-MI defines one management language for both: a set of NVMe-MI commands (for example "give me the subsystem's health status", "read the VPD", "set this configuration") plus the ability to carry ordinary NVMe admin commands (like Get Log Page or Firmware Image Download) over the management path.

Out-of-band, NVMe-MI messages are carried inside Management Component Transport Protocol (MCTP) packets, a DMTF standard that runs over several physical buses. In-band, they are carried inside two NVMe admin commands, NVMe-MI Send and NVMe-MI Receive.

The message stack

  • MCTP (DMTF DSP0236) gives every participant an Endpoint ID (EID), packetises messages into small packets (the baseline transmission unit is 64 bytes of payload), and marks the first and last packet of a message (SOM, EOM), a 2-bit packet sequence number, and a message tag with a Tag Owner bit to match responses to requests. Verified as general MCTP behaviour; confirm exact header bit positions in DSP0236.
  • The NVMe-MI message carries a message type that distinguishes Control Primitives, NVMe-MI commands, tunnelled NVMe admin commands and PCIe commands; it ends with a Message Integrity Check (MIC), a 32-bit cyclic redundancy check (CRC-32C) over the message. Uncertain on field positions — check NVMe-MI 2.2's message format.
  • Command slots. A management endpoint processes requests in a small number of command slots (NVMe-MI defines two per endpoint) so that two requesters, or a requester and an abort, can coexist. Control Primitives (such as Pause, Resume, Abort, Get State, Replay) act on slots and are processed even while a command is busy. Uncertain on the full primitive list in 2.2.

The MCTP message type value assigned to NVMe-MI is commonly given as 04h in the DMTF MCTP IDs and Codes document (DSP0239). Uncertain — confirm in DSP0239 before you write a decoder filter.

Out-of-band over SMBus/I2C

The two-wire sideband is the oldest and most robust path: a few hundred kHz (SMBus 100 kHz/400 kHz, up to 1 MHz in some platforms), independent of the PCIe link, often powered from auxiliary power. MCTP over SMBus uses SMBus block writes in both directions (the responder becomes a master to send its response). Every packet carries a Packet Error Code (PEC). It is slow — a 4 KiB log transfer takes on the order of a hundred milliseconds or more — but it works when the PCIe link is down, during link training, or while the host is in reset. Derived timing from the bus rate; actual throughput is platform-dependent.

NVMe-MI also describes a much simpler Basic Management Command (an informative SMBus block read of a fixed data structure with composite status, temperature and drive life) that predates full MCTP support and many BMCs still poll. Uncertain on its status in 2.2 and on its SMBus address; confirm in the NVMe-MI 2.2 annexes.

Out-of-band over PCIe VDM

MCTP over PCIe carries MCTP packets in PCIe Vendor Defined Messages (VDMs): Message TLPs with data (MsgD), routed by ID (or to the root complex), using the DMTF's vendor ID in the header (commonly given as 1AB4h) and the Vendor_Defined Type 1 message code. Uncertain on exact header values — confirm in DMTF DSP0238. It is much faster than SMBus, but it requires a trained PCIe link and an enabled function, so it disappears during resets, link-down events and some low-power states.

This is the reason platforms keep SMBus wiring even after adding VDM support: the moments you most need to manage a drive — it is stuck, the link will not train, it is in recovery — are exactly the moments the PCIe path is unavailable.

In-band: NVMe-MI Send and NVMe-MI Receive

The NVMe Base Specification defines two admin commands, NVMe-MI Send and NVMe-MI Receive, that carry NVMe-MI commands through the admin queue. Host software can then use exactly the same management commands as the BMC (VPD read, health poll, configuration, enclosure management) without needing MCTP. Their opcodes are commonly listed as 1Dh (Send) and 1Eh (Receive). Uncertain — confirm in the Base 2.4 admin command table. Not every controller supports them; check the controller's Identify data (Optional Admin Command Support).

Verified for the layering; names of individual data structures should be confirmed in NVMe-MI 2.2.

Monitoring: health status polls

NVMe-MI provides polling commands designed for a BMC that checks drives every few seconds:

  • NVM Subsystem Health Status Poll — a compact subsystem-wide summary: a composite status (e.g. ready, failure/warning indications), composite temperature, percentage of drive life used, and changes since last poll. It is designed to be cheap so that it can run constantly.
  • Controller Health Status Poll — per-controller status, with filtering so the BMC can ask only about controllers whose status changed.
  • Tunnelled Get Log Page for the SMART / Health Information log when detail is needed (Chapter 57).

Health polls can clear change indications ("changed since last poll"). If two management controllers poll the same endpoint, one may consume change flags the other needed. Configure a single poller or understand the clear semantics in the specification.

Vital Product Data

Vital Product Data (VPD) is the drive's identity card: manufacturer, product name, part number, serial number, form factor and capability information, laid out in the Intelligent Platform Management Interface (IPMI) FRU Information format. A BMC can read it directly from the FRU information device on the two-wire bus — even with only auxiliary power — or through the NVMe-MI VPD Read command; VPD Write exists for manufacturing. Implementation-dependent whether VPD is writable in the field.

Configuration

Configuration Get and Configuration Set NVMe-MI commands read and change management-interface settings — examples include the SMBus/I2C frequency of a port, the MCTP transmission unit size, and health-status change behaviour. Uncertain on the full list of configuration identifiers in 2.2. Controller-level configuration (features, namespace management) is done with tunnelled admin commands (Set Features, Namespace Management), subject to the device's management-access policy.

Firmware update

Out-of-band firmware update tunnels the same admin commands used in-band: Firmware Image Download (opcode 11h) to transfer the image in pieces, and Firmware Commit (opcode 10h) to commit it to a slot and select activation. Over SMBus this is slow (minutes for a multi-megabyte image), so platforms prefer VDM or in-band paths when available. Activation may need a reset, which interrupts host I/O: coordinate with the host. Derived

Enclosure management

For drives that act as, or sit in, an enclosure, NVMe-MI carries Small Computer System Interface (SCSI) Enclosure Services (SES) pages through SES Send and SES Receive commands. The BMC or host can read slot status and drive indicators (locate/fault LEDs) and control power to slots. The pages themselves are defined by the SES standard, not by NVMe-MI. Verified that NVMe-MI reuses SES for enclosure management; confirm command names and supported pages in NVMe-MI 2.2 and the SES standard.

The central concept on the ladder

The caretaker's side window: health, name plate, new rule books, blinking shelf lights — open even when the teacher is asleep.

NVMe-MI is a management command set. Out-of-band, a BMC sends NVMe-MI messages over MCTP to a management endpoint; in-band, the host sends them in NVMe-MI Send/Receive admin commands.

The BMC drives SMBus/I2C wires or PCIe VDMs; the drive firmware runs an MCTP stack and an NVMe-MI command processor alongside the NVMe controller, sharing sensors, logs and firmware slots.

NVMe-MI 2.2 defines messages, commands, data structures, command slots and integrity checks; DMTF DSP0236/0237/0238/0239 define MCTP and its bindings; NVMe Base 2.4 defines the in-band commands and the admin commands that are tunnelled.

Request message → (packetised) → management endpoint → response message, matched by MCTP tag and command slot; out-of-band and in-band requests can be concurrent with host I/O.

On a PCIe analyzer: MsgD TLPs (Vendor Defined Type 1) between the RC/BMC path and the device, small, sporadic, interleaved with normal I/O. SMBus traffic needs a separate two-wire analyzer.

"Drive missing from BMC" → check which path: if VDM, did the link go down or the function reset? If SMBus, is the bus hung, address conflicting, or the EID unassigned after hot-plug? Correlate BMC timestamps with host resets.

Hardware view

On a U.2/U.3 or E1/E3 (Enterprise and Datacenter Standard Form Factor, EDSFF) drive, the connector carries SMBus clock and data pins and often auxiliary power alongside the PCIe lanes; on M.2 the sideband pins are optional and frequently unconnected in client systems. Implementation-dependent — check the form-factor specification and the platform schematic. Inside the drive, a small microcontroller core or a firmware task on the main controller implements the MCTP stack and the NVMe-MI command processor; it shares temperature sensors, the SMART counters and the firmware slots with the NVMe controller.

SMBus is a shared, open-drain bus. One misbehaving device that holds the data line low can hang management for every drive behind the same multiplexer channel. Bus-recovery (clocking out a stuck device, timeouts) is a platform responsibility and a frequent field issue.

  • NVM Express Base Specification, Revision 2.4 — NVMe-MI Send / NVMe-MI Receive; admin commands that may be tunnelled Normative

  • IPMI Platform Management FRU Information Storage Definition (VPD format) and the SCSI Enclosure Services standard (enclosure pages).

NVMe-MI is a separate specification in the NVMe family; the current revision is 2.2, released with the NVMe 2.4 set on 2026-08-04. NVMe-MI uses MCTP as its out-of-band transport.

Because MCTP over PCIe uses Message TLPs, management traffic consumes posted-header and posted-data flow-control credits on the same link as host writes and can be seen in any PCIe trace. Because it uses ID routing, it depends on correct bus numbers, so it cannot work before enumeration.

Which ports have management endpoints, whether VDM is supported, SMBus addresses, supported optional commands, field-writability of VPD, which tunnelled admin commands are permitted out-of-band, polling rate limits, and response times.

NVMe-MI 1.0 (2015) introduced the out-of-band interface; 1.1 added in-band tunnelling and enclosure management; 1.2 and 2.x added further capabilities, and the 2.x line aligned with the NVMe 2.0 refactoring. Uncertain on which features arrived in which minor revision; the 2.4-set "NVM Express Revision Changes 2026.07.30" document lists what NVMe-MI 2.2 changed. Press coverage of 2.4 mentions voltage monitoring and manageability topics, which may touch NVMe-MI; confirm before teaching any specific command.

  • MCTP header bits, the NVMe-MI MCTP message type value, VDM header values: read DSP0236/0238/0239.
  • Whether a given admin command may be tunnelled out-of-band, and security/lockdown interactions (NVMe 2.x has a Command and Feature Lockdown mechanism that can restrict management interfaces): read Base 2.4 and NVMe-MI 2.2.

  • Never assume a health poll is side-effect free (change flags).
  • Never assume management access is harmless: tunnelled admin commands can destroy data.
  • Never assume SMBus addresses or MCTP EIDs persist across hot-plug.

Protocol view

Request/response over MCTP

  1. NVMe-MI request (slot 0), MIC
  2. packets: SOM … EOM, tag=3, TO=1
  3. check MIC, process command
  4. response packets, tag=3, TO=0
  5. reassembled response + MIC
  • Direction: requester → responder → requester. The drive does not originate requests (asynchronous event messages, where supported, are a separate mechanism — confirm in 2.2).
  • Matching: MCTP message tag + Tag Owner bit + source EID; at NVMe-MI level, the command slot.
  • Integrity: SMBus PEC per packet; PCIe link CRC (LCRC) and end-to-end CRC (ECRC); MIC end-to-end for the NVMe-MI message.
  • Busy and long operations: a responder may answer "more processing required" and later complete; control primitives can query state or abort. Uncertain on exact status names.
  • Ordering: no ordering is implied between management commands and host I/O commands to the same controller; they are independent paths into the controller.

Tunnelled admin command

An NVMe Admin Command message carries the fields of an admin submission queue entry (SQE) (opcode, namespace identifier (NSID), command dwords) and, for data-in commands, the data returns in the response message — there are no Physical Region Pages (PRPs), because there is no host memory involved. The controller executes the command as if it had come from a queue, but its completion is returned in the NVMe-MI response, not posted to a host completion queue (CQ). Derived

Packet sizes over PCIe VDM

An MCTP packet carries up to the negotiated transmission unit (64 bytes baseline). A 4 KiB Get Log Page response over VDM is therefore about 64+ MsgD TLPs of ≈ 64 bytes of MCTP payload each, plus headers. Over SMBus at 100 kHz, the same transfer is several hundred milliseconds. Derived

Linux view

Two different Linux machines are involved: the host (in-band) and, often, the BMC itself, which in many servers runs Linux (for example OpenBMC). The kernel has an MCTP networking stack (AF_MCTP sockets, since about kernel 5.15) with SMBus/I2C and other bindings; user space uses the mctp utility and libraries such as libnvme's NVMe-MI support. Version-dependent — check your kernel and nvme-cli/libnvme versions.

# Host, in-band: does the controller support NVMe-MI Send/Receive? (Optional Admin Command Support field)
sudo nvme id-ctrl /dev/nvme0 -H | grep -i -E "mi|oacs" -A2

# Host, in-band: the same health data a BMC would poll, via the admin queue
sudo nvme smart-log /dev/nvme0

# BMC or management host running Linux with MCTP enabled:
mctp link            # MCTP-capable interfaces (e.g. an i2c binding)
mctp address         # local EIDs
mctp route           # routes to remote EIDs (e.g. the drive's management endpoint)

# Is the drive's FRU/VPD device visible on the bus? (read-only scan; check your bus number, and avoid
# probing unknown devices on production systems)
sudo i2cdetect -l

Safe lab for the read-only commands. Writing to SMBus devices, tunnelling admin commands out-of-band, or VPD writes are Expert lab: they can brick FRU contents or affect data. Do not run i2cdetect probing modes on production BMCs without understanding the devices on that segment.

Code / pseudocode

A runnable simulation of MCTP packetisation and reassembly, which is where most hand-written management tools go wrong. It uses a CRC-32C for the end-to-end integrity check, as NVMe-MI's MIC does; the header layout here is simplified and is not the wire format.

#!/usr/bin/env python3
"""Simplified MCTP packetiser/reassembler with an end-to-end CRC-32C check.
Teaching model only: field layout is NOT the DSP0236 wire format."""

def crc32c(data: bytes) -> int:
    crc = 0xFFFFFFFF
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ (0x82F63B78 if crc & 1 else 0)
    return crc ^ 0xFFFFFFFF

def packetise(msg: bytes, tag: int, to: int, unit: int = 64):
    body = msg + crc32c(msg).to_bytes(4, "little")
    chunks = [body[i:i + unit] for i in range(0, len(body), unit)] or [b""]
    return [dict(som=i == 0, eom=i == len(chunks) - 1, seq=i % 4, tag=tag, to=to, data=c)
            for i, c in enumerate(chunks)]

def reassemble(packets):
    buf, expect, tag = b"", None, None
    for p in packets:
        if p["som"]:
            buf, expect, tag = b"", p["seq"], p["tag"]
        if tag is None or p["tag"] != tag:
            return None, "packet without SOM or wrong tag"
        if p["seq"] != expect:
            return None, f"sequence gap: expected {expect}, got {p['seq']}"
        buf += p["data"]
        expect = (expect + 1) % 4
        if p["eom"]:
            msg, mic = buf[:-4], int.from_bytes(buf[-4:], "little")
            return (msg, "ok") if crc32c(msg) == mic else (None, "MIC mismatch")
    return None, "no EOM"

if __name__ == "__main__":
    assert crc32c(b"123456789") == 0xE3069283  # standard CRC-32C check value
    log = bytes(range(256)) * 2                 # 512-byte "log page"
    pkts = packetise(log, tag=5, to=0)
    print("packets:", len(pkts))
    print("clean:", reassemble(pkts)[1])
    lost = pkts[:3] + pkts[4:]
    print("one packet lost:", reassemble(lost)[1])
    bad = [dict(p) for p in pkts]; bad[2]["data"] = b"\x00" + bad[2]["data"][1:]
    print("one byte corrupted:", reassemble(bad)[1])

Expected output: packets: 9, clean: ok, one packet lost: sequence gap: expected 3, got 0, one byte corrupted: MIC mismatch. Note that losing exactly four consecutive packets would not be caught by a 2-bit sequence number — that is precisely why the end-to-end MIC exists.

Worked example

Scenario (synthetic): a BMC manages 24 drives behind SMBus multiplexers at 100 kHz and polls each every 5 seconds with a subsystem health status poll. It must also update firmware (a 4 MiB image) on one drive out-of-band.

Polling budget

U = N × tpoll / P
U
fraction of bus time spent polling
N
number of drives sharing the bus (24)
tpoll
bus time per poll exchange, seconds
P
polling period per drive (5 s)

At 100 kHz, one bit ≈ 10 µs; a byte with acknowledge ≈ 9 bits ≈ 90 µs. A request of ≈ 20 bytes and response of ≈ 40 bytes (with MCTP/SMBus overhead; illustrative) ≈ 60 bytes ≈ 5.4 ms, plus turnaround and firmware latency, call it 10 ms. U ≈ 24 × 0.010 / 5 ≈ 4.8 %. Comfortable.

Firmware over SMBus

4 MiB ≈ 4.19 × 10⁶ bytes ≈ 3.8 × 10⁸ µs of bus time at 90 µs per byte ≈ 377 s ≈ 6.3 minutes, before overheads — and polling of the other 23 drives on that segment is delayed throughout unless interleaved. Over PCIe VDM the same transfer takes well under a second of link time. Conclusion: poll over SMBus (robust), update over VDM or in-band (fast), and fall back to SMBus only for recovery. Derived; all numbers illustrative.

Common mistakes

  1. Treating "out-of-band" as "physically separate" — VDM shares the PCIe link.
  2. Polling from two management agents and losing change flags.
  3. Assuming EIDs are permanent; after hot-plug or some resets they must be re-discovered.
  4. Ignoring the MIC or sequence numbers in a home-grown MCTP tool.
  5. Allowing unrestricted tunnelled admin commands out-of-band (Format, Sanitize) — a security issue.
  6. Comparing BMC and host temperature readings without aligning timestamps and field definitions.
  7. Expecting the M.2 slot in a client laptop to have SMBus wired.
  8. Pushing a firmware image over SMBus while the host runs latency-sensitive I/O, then activating with a reset the host did not expect.

Senior engineer insight

  • Management is a second control plane into the same controller. Every concurrency question you ask about two host queues, ask again about host + BMC: who wins on Set Features? What does a Format mean while the BMC is reading a log?
  • Management is a security boundary. The BMC is often less hardened than the host. Lockdown mechanisms in the NVMe 2.x family (and the 2.4 improvements described in 2026 NVMe 2.4 Updates) exist to restrict which commands are allowed from which interface. A platform security review should list which admin commands are reachable out-of-band.
  • Fleet tooling lives above NVMe-MI. Operators see Redfish or vendor dashboards, not NVMe-MI messages. When a dashboard is wrong, the debugging chain is dashboard → BMC firmware → MCTP → endpoint → controller; each hop can lie.
  • Correlate clocks. BMC and host clocks are different; capture both with a common reference before debugging interactions.

Lab

Lab — Management-path forensics

Objective

Use the MCTP simulator and the synthetic traces to practise packet reassembly, tag matching and reset correlation; then compare in-band and out-of-band health data on real hardware if available.

Skills

MCTP reasoning, integrity checking, cross-source correlation.

Safety

Safe lab for simulation and in-band reads. Any OOB write is Expert lab and out of scope.

Hardware required

None; optional Linux host with an NVMe drive; optional BMC with shell access.

Software required

Python 3; nvme-cli; optionally mctp tools on a BMC.

Input

mctp_sim.py; the three traces above.

Expected output

A short report: packet counts, failure modes detected, correlation of the FLR trace, and an in-band health snapshot.

Background

Re-read the Protocol view on matching and integrity.

Step 1

Run mctp_sim.py. Change the transmission unit to 32 and 128 bytes; record the packet counts for a 512-byte and a 4096-byte message.

Step 2

Modify the loss test to drop exactly four consecutive packets. Observe that the sequence check passes and the MIC catches it. Then drop four packets and recompute the MIC over the shortened message (simulate a buggy sender) — what catches it now?

Step 3

For the FLR trace, write a timeline merging a BMC log ("poll timeout at T") and a host log ("nvme nvme0: resetting controller at T+0.02 ms"), and state the first abnormal event and confidence.

Observation

Record which integrity layer detected each injected fault.

Questions

  1. Why can a 2-bit sequence number never be enough by itself?
  2. In Step 2's buggy-sender case, which layer is responsible for detecting the error?

Challenge

Add interleaving: two requesters (tags 1 and 2) with packets interleaved. Extend reassemble to keep one buffer per (source EID, tag).

Hints

Use a dictionary keyed by tag; SOM resets that tag's buffer only.

Solution

Step 1: with unit 64, 512+4 bytes → 9 packets; 4096+4 → 65. Unit 32: 17 and 129. Unit 128: 5 and 33.

Step 2: a correct MIC over the shortened message makes reassembly "succeed" — nothing in the transport can know the sender meant a longer message. Detection must come from the NVMe-MI layer: the response's length fields or the expected data length of the command do not match. This is why responders and requesters must validate lengths, not just CRCs.

Step 3: first abnormal event = no response to tag 6 within the BMC timeout; it coincides with FLR; confidence medium-high that the FLR dropped the request, pending a specification check of reset behaviour.

Questions: a 2-bit counter wraps every four packets, so losses of multiples of four are invisible; the NVMe-MI layer (length validation) or the application.

What a senior engineer notices

That every integrity mechanism has a blind spot and the design layers them: PEC/LCRC per hop, sequence per packet, MIC per message, length per command.

Failure variants

  • Response arrives with the wrong tag owner bit.
  • EOM never arrives (sender firmware crash mid-message).
  • Two requesters use the same tag.

Extension

On a BMC running OpenBMC, inspect how its NVMe-MI daemon schedules polls and handles timeouts, and compare against the slot and reset rules you find in NVMe-MI 2.2.

Exercises

  1. Draw the three management paths for one drive and label which survive an FLR, a link-down, and an OS crash.
  2. Compute the SMBus time for a 4 KiB log read at 400 kHz using the per-byte estimate in the worked example.
  3. List the admin commands you would block from out-of-band access on a multi-tenant cloud server, and why.
  4. Find in NVMe-MI 2.2 the definition of the subsystem health status poll fields and write a one-line meaning for each.
  5. Explain how you would tell, from a PCIe trace alone, whether a MsgD is MCTP traffic.
Model answers

1: SMBus survives all three (if aux power and the endpoint are alive); VDM survives an OS crash only; in-band survives none.

2: 400 kHz → 2.5 µs/bit → ≈ 22.5 µs/byte; 4096 bytes + ≈ 15% overhead ≈ 4,700 bytes ≈ 106 ms, plus firmware latency.

3: Format NVM, Sanitize, Namespace Management/Attachment, Firmware Commit (unless the update process is OOB-owned), security send/receive — because they destroy data or change tenancy.

4: Answer from the specification; do not answer from memory.

5: Message TLP with data, Vendor_Defined Type 1 message code, DMTF vendor ID in the header (confirm values in DSP0238), MCTP header in the payload.

Quiz

  1. Which path survives a Function Level Reset of the NVMe function?

    • MCTP over SMBus/I2C
    • MCTP over PCIe VDM
    • NVMe-MI Send/Receive
    • All of them
    Answer and reasoning

    The sideband does not depend on the PCIe function; the other two do.

  2. Which DMTF protocol carries NVMe-MI messages out-of-band?

    • PLDM
    • SPDM
    • MCTP
    • Redfish
    Answer and reasoning

    MCTP is the transport; Platform Level Data Model (PLDM) and Security Protocol and Data Model (SPDM) are other message types carried by MCTP; Redfish is an HTTP API above the BMC.

  3. How does host software issue NVMe-MI commands in-band?

    • Memory-mapped I/O (MMIO) writes to a management register
    • NVMe-MI Send / NVMe-MI Receive admin commands
    • PCIe VDMs from the CPU
    • Set Features
    Answer and reasoning

    Two admin commands defined in the Base specification tunnel NVMe-MI.

  4. What protects an NVMe-MI message end-to-end?

    • SMBus PEC
    • PCIe LCRC
    • MCTP sequence numbers
    • The Message Integrity Check (CRC-32C)
    Answer and reasoning

    PEC and LCRC are per hop; sequence numbers detect some losses; the MIC covers the whole message.

  5. Why might two BMC agents polling the same drive miss events?

    Model answer

    Health polls can clear "changed" indications; whichever agent polls first consumes them.

  6. Where is VPD stored and in what format?

    Model answer

    In FRU storage on the drive, typically reachable on the two-wire bus, in IPMI FRU Information format; also readable through NVMe-MI VPD Read.

  7. When a tunnelled Get Log Page returns 512 bytes, where does the data go?

    Model answer

    Into the NVMe-MI response message to the management controller — not into host memory, and no PRP is used.

  8. What standard defines the enclosure pages NVMe-MI carries?

    Model answer

    SCSI Enclosure Services (SES); NVMe-MI only transports them via SES Send/Receive.

  9. Give one reason to keep SMBus wiring on a platform that supports VDM.

    Model answer

    Management during link-down, resets, link training failures and auxiliary-power-only states.

Interview questions

  1. Beginner: What is the difference between in-band and out-of-band management?

    Model answer

    In-band uses the host OS and the NVMe admin queue; out-of-band uses a separate management controller and path (SMBus/I2C or PCIe VDM via MCTP), independent of the host OS.

  2. Beginner: What is a BMC?

    Model answer

    A Baseboard Management Controller: a service processor on the motherboard that monitors and manages the server independently of the host CPU and OS.

  3. Intermediate: Explain the encapsulation of an NVMe-MI command over PCIe.

    Model answer

    NVMe-MI message (header, body, MIC) → MCTP message type for NVMe-MI → MCTP packets (SOM/EOM, seq, tag) → PCIe VDM Message TLPs routed by ID, with DMTF vendor ID.

  4. Intermediate: Why does NVMe-MI have command slots?

    Model answer

    To let a management endpoint hold more than one request context, so that requesters or control primitives (abort, get state) can be processed while a command is busy.

  5. Advanced: How would you validate NVMe-MI robustness against host resets?

    Model answer

    Continuous polling and long transfers on each path while injecting Controller Level Reset, FLR, NVM Subsystem Reset, hot reset and link disable at random times; check timeouts, recovery, EID persistence, no false alerts, and that tunnelled commands in flight complete or fail cleanly per specification.

  6. Senior: A fleet shows 0.1% of drives "missing" in the BMC but healthy in the OS. Approach?

    Model answer

    Group by platform, slot, firmware and BMC version; check whether the failure follows the slot (wiring/mux), the drive (firmware), or the BMC build; read FRU directly over SMBus to separate bus from MCTP problems; correlate with host reset events; reproduce on a lab system with an SMBus analyzer.

  7. Senior: What security concerns does NVMe-MI raise?

    Model answer

    Out-of-band access can tunnel destructive admin commands, bypassing host access control; BMCs are an attack surface; mitigations include command lockdown per interface, authentication (e.g. SPDM-based mechanisms where supported) and least-privilege BMC policy.

Model teach-back (junior)

NVMe-MI is one management command set with three ways in. SMBus/I2C is slow but always there; PCIe VDM is fast but shares the link and drops out on resets; in-band NVMe-MI Send/Receive needs a working host driver. Out-of-band uses MCTP packets matched by tag and protected end-to-end by a CRC-32C MIC.

Chapter summary

NVMe-MI 2.2 standardises drive management for management controllers and host software. Out-of-band, NVMe-MI messages ride MCTP over SMBus/I2C or PCIe VDMs to a management endpoint in the subsystem; in-band, they ride NVMe-MI Send/Receive admin commands. The functions are discovery, health monitoring with cheap status polls, VPD, configuration, tunnelled admin commands (including firmware update), and SES-based enclosure management. The paths differ sharply in availability during resets; management is a concurrent control plane and a security boundary.

Do not move on until you can:

  • draw the in-band and both out-of-band paths and say when each works
  • explain the encapsulation NVMe-MI → MCTP → binding
  • identify an MCTP VDM in a PCIe trace and match request to response
  • diagnose the poll-lost-across-FLR trace
  • list the management functions and where each is defined
  • name what must be confirmed in NVMe-MI 2.2 and the DMTF bindings
