Four things in an NVMe-over-PCIe system are casually called "a command", "a packet" or "a completion", and they are not interchangeable: the NVMe command, the PCIe Transaction Layer Packet, the NVMe Completion Queue Entry, and the PCIe Completion TLP. This page separates them for good, shows how each one rides on the others, and then trains the skill that depends on the distinction — correlating a raw packet trace with the NVMe commands inside it — through a short exercise and a full trace-correlation lab with a hidden solution.

Why this distinction matters

When an engineer says "the completion never came back", they might mean any of three things: the PCIe completion for a read request never arrived (a link or root-complex problem), the NVMe Completion Queue Entry was never written (a controller problem), or the interrupt that announces it never fired (an interrupt-routing problem). Each points to a different team, a different log and a different fix. Confusing them costs days.

The confusion is natural, because the words overlap and because the layers nest inside each other in a counter-intuitive way: the NVM Express (NVMe) command travels to the device inside a PCI Express (PCIe) completion, and the NVMe completion travels to the host inside a PCIe request. Once you see that crossing clearly, a large class of trace-reading mistakes disappears.

This page assumes: Transaction Layer Packets (TLPs) and their headers (Chapter 10, Chapter 11); posted versus non-posted requests (Chapter 12); tags (Chapter 13); the queue model, doorbells and the 64-byte command / 16-byte completion entries (Chapters 25–28); and Physical Region Pages (PRPs) (Chapter 36). The end-to-end flows are in Chapter 39 and Chapter 41.

What you will be able to do

  • Define each of the four objects by layer, creator, consumer, size, location and identifiers.
  • Draw the crossing: SQE inside a PCIe completion, CQE inside a PCIe memory write.

The story

Think of a post office. Your letter (what you want) is not the same as the delivery van that carries it. When the shop answers you, its reply letter is not the same as the "delivered" receipt the van driver gets when a parcel is handed over.

Here's the funny part. The shop doesn't wait for your letter to arrive — it sends its own van to your house to pick it up. So your letter rides home to the shop inside the van's pickup run, which counts as an answer to the shop's "please hand it over". And when the shop replies, it sends its reply letter in an ordinary delivery van to your mailbox.

A company's purchase order (NVMe command) and invoice (NVMe completion) are business documents. The shipments that move them — a courier pickup request and the courier's delivery of the picked-up envelope, or a plain delivery — are logistics (PCIe TLPs). The courier's tracking number (PCIe Tag) is not the purchase order number (NVMe Command Identifier). A courier's "delivered" notice (PCIe completion status) says the envelope arrived; it says nothing about whether the order was fulfilled (NVMe status). A courier can lose a parcel while the order was perfectly valid, and a parcel can be delivered perfectly containing an invoice that says "order rejected".

What the analogies hide. In PCIe, a "pickup" (a Memory Read request) is always answered by a Completion TLP routed by ID, not by address; a delivery (a Memory Write) gets no receipt at all. Data movement (DMA, direct memory access) for reads and writes is separate from both the command and its completion and can be far larger than either.

Where they mislead. They suggest one envelope per document. In practice one TLP may carry several SQEs (a 192-byte fetch carrying three commands), one SQE may arrive split over two Completion TLPs, and one Memory Write may carry two CQEs. The mapping between NVMe objects and TLPs is many-to-many.

The four objects

The NVMe command

An NVMe command is an NVMe-level request: "read 8 blocks from namespace 1 starting at LBA 0x100000 into this buffer". On the queue interface it is a 64-byte Submission Queue Entry (SQE).

  • Layer: NVMe (the NVMe Base Specification and an I/O command set specification such as the NVM Command Set).
  • Created by: the host driver, written by the CPU into a Submission Queue in host memory.
  • Consumed by: the NVMe controller, which fetches it.
  • Identity: SQ Identifier + Command Identifier (CID, 16 bits, host-chosen).
  • On the link: never as its own packet. Its bytes appear as the payload of a PCIe Completion with Data that answers the controller's Memory Read of the SQ (unless the SQ is in a Controller Memory Buffer, in which case the bytes cross the link in host Memory Writes).
  • What it is not: it is not the doorbell (that only carries an index), and it is not a TLP.

The PCIe TLP

A Transaction Layer Packet is the PCIe transport unit: a header (3 or 4 Dwords in non-flit mode) plus optional data payload, carrying one request or one completion between two PCIe functions.

  • Layer: PCIe Transaction Layer (PCI Express Base Specification).
  • Created by: whichever side initiates: the root complex (for CPU MMIO accesses) or the device (for its DMA).
  • Kinds relevant here: Memory Read (MRd, non-posted), Memory Write (MWr, posted), Completion (Cpl, no data) and Completion with Data (CplD).
  • Identity: requests carry a Requester ID and a Tag; completions carry the Completer ID, and the Requester ID and Tag of the request they answer.
  • What it is not: it has no idea what NVMe is. A TLP carrying a doorbell, an SQE, a CQE, user data or an interrupt looks the same apart from address, direction, length and payload.

The NVMe Completion Queue Entry

An NVMe completion is the NVMe-level record that a command finished: a 16-byte Completion Queue Entry (CQE) holding the CID, SQ Identifier, SQ Head Pointer, Phase Tag and NVMe Status (Status Code Type and Status Code), plus command-specific Dwords.

  • Layer: NVMe.
  • Created by: the controller.
  • Consumed by: the host driver, which reads it from host memory.
  • On the link: as the payload of a device-originated, posted Memory Write to the Completion Queue's address. It is a PCIe request.
  • What it is not: it is not a PCIe Completion, and it does not answer any PCIe request. It is also not the interrupt — the MSI-X message is a separate Memory Write.

The PCIe Completion TLP

A PCIe Completion is the transport-level response to a non-posted PCIe request — for our purposes, a Memory Read. Cpl carries no data; CplD carries data.

  • Layer: PCIe.
  • Created by: the completer of the request: the root complex when the device reads host memory; the device when the CPU reads a device register.
  • Routed by: ID (the Requester ID of the original request), matched by Tag.
  • Carries: Completion Status (Successful Completion, Unsupported Request, Completer Abort, or Request Retry Status for configuration requests), Byte Count, Lower Address, and data if CplD.
  • What it is not: an NVMe completion. A PCIe completion with Successful status for an SQE fetch only says "here are the 64 bytes"; the command may still fail at the NVMe level.

The name of the retry status for configuration requests changed across PCIe revisions (older documents say Configuration Request Retry Status, CRS; newer ones generalise it as Request Retry Status). Check the revision your analyzer decodes against Version-dependent.

For a 4 KiB Write, the data direction flips: the controller issues Memory Reads for the data (8 × 512 B at Max Read Request Size), and the root complex answers with Completions with Data — so a Write produces many PCIe completions, all carrying user data, none of them NVMe completions.

The MSI-X interrupt goes to an address below 4 GiB (0xFEE0_xxxx on x86) and is therefore a 3 DW header MWr32, even from a device that uses 64-bit addressing for everything else. Analyzers label it "MSI-X" by recognising the address window or by being told the MSI-X table contents — it is not a different TLP type.

The ladder for the distinction

A letter is not the van; a reply letter is not the van driver's receipt. The shop's van picks up your letter, and the shop's reply comes in an ordinary delivery.

NVMe command and NVMe completion are records in host memory. PCIe requests and completions are packets on the link. The command crosses inside a PCIe completion; the NVMe completion crosses inside a PCIe write.

The controller's fetch engine issues MRd and receives CplD into an SQE buffer; its posting engine issues MWr to the CQ. The root complex is the completer for device reads of host memory; the device is the completer for CPU reads of its registers.

NVMe Base Specification 2.4 defines SQE and CQE formats and statuses; the NVMe over PCIe Transport Specification 1.4 maps queues to host memory accessed through PCIe memory transactions; the PCI Express Base Specification defines MRd, MWr, Cpl/CplD, routing, tags and completion status.

Non-posted MRd → Completion routed by ID with matching Tag; posted MWr → nothing. Ordering: the device's data MWrs, CQE MWr and MSI-X MWr arrive in order.

In a capture: CplD from RC with Requester ID 0x0100 and a 64-byte payload whose first byte is an opcode → an NVMe command. MWr from 0x0100 into the CQ range with a 16-byte payload → an NVMe completion. CplD from 0x0100 to RC → a register read answer, not NVMe at all.

"Completion missing" → which one? No CplD for the SQE fetch: PCIe/root complex. No CQE MWr: controller. No MSI-X MWr: interrupt configuration. CQE present with error status: NVMe command failure. Each has a different owner.

Common confusions, corrected

"The host sends the NVMe command to the SSD."The host writes it to its own memory and rings a doorbell; the SSD pulls it with a Memory Read.
"The doorbell packet contains the command."The doorbell carries a 16-bit index only.
"The NVMe completion is a PCIe completion."It is a posted Memory Write. PCIe completions only answer non-posted requests.

"MSI-X is a special packet type."It is an ordinary MWr to an address the OS chose.
"One command, one TLP."One 4 KiB Read is about 20 TLPs; a fetch TLP can carry several commands; a CQE TLP can carry several completions.

Trace correlation exercise

Here is the deliberately minimal trace from the master curriculum. It gives only a time and a packet type — the way a careless summary of a capture often looks. It is conceptual: there are no addresses, directions or identifiers, on purpose.

#TimeType as summarised
AT=100Memory Write
BT=110Memory Write
CT=130Memory Read
DT=140Completion with Data
ET=150Memory Write
FT=160MSI-X Message

Answer each question before opening the answer. The goal is not to find "the" interpretation — it is to list every interpretation the evidence allows, and the evidence that would decide.

  1. Which events could be a doorbell?

    Answer and reasoning

    A, B and E — any Memory Write could be a doorbell if it travels host→device, targets the doorbell range in BAR0 (offset 1000h and up, on a stride boundary), has Length 1 DW and full byte enables, and carries a value smaller than the queue size. C, D and F cannot: a doorbell is never a read or a completion, and F is labelled as an interrupt. Without direction and address you cannot decide. Note A and B could be two doorbells (SQ tail of two queues, or SQ tail then CQ head) or none.

  2. Which could be DMA?

    Answer and reasoning

    A, B, E (device→host Memory Writes: read data, or the CQE, which is also DMA) and C (a device→host Memory Read: an SQE fetch, a PRP or SGL list fetch, or data for a Write command). D is the root complex's answer to a device read — part of a DMA read — if it travels host→device; if it travels device→host it answers a CPU register read (MMIO) and is not DMA at all.

  3. Which could be a CQ update?

    Answer and reasoning

    A device→host Memory Write into the Completion Queue's address range with a payload that is a multiple of 16 bytes and decodes as a CQE (plausible CID, SQID, phase bit). In this trace, E is the classic candidate because it precedes the interrupt F; but A or B could be too (for example a CQE for an earlier command). Also, "CQ update" could mean the host's CQ head doorbell — a host→device write, likewise a Memory Write. Ask which one is meant.

  4. Which could be the interrupt?

    Answer and reasoning

    F is labelled MSI-X, but that label is the analyzer's (or summariser's) inference from the address. Physically it is a Memory Write. It is only an interrupt if it is device→host, Length 1 DW, and targets an MSI-X message address the OS programmed into the device's MSI-X table (on x86, an address in the 0xFEE0_xxxx window), with the matching data value. Conversely, E could also be an MSI-X write mislabelled as a plain write if the analyzer was not told the address window.

  5. Is C → D a request and its answer?

    Answer and reasoning

    Only if D's Requester ID and Tag match C's, and D travels in the opposite direction. Completions can arrive out of order relative to other reads, so D could answer an earlier read (outside this window), and C's own completion could come later. If C is a device read of the SQ, D (with matching tag) carries one or more NVMe commands in its payload — and is therefore not an NVMe completion in any sense.

  6. What additional evidence is required?

    Model answer
    • Direction (upstream/downstream, or which side of the analyzer): separates doorbells and MMIO from DMA.
    • Requester ID and Completer ID: device (0x0100 in our system) versus root complex.
    • Addresses plus an address map: BAR0 range and its sub-ranges (registers, doorbells, MSI-X table), SQ and CQ bases and sizes (from Create I/O queue commands or the Admin registers), PRP list pages, data buffers (from SQE payloads), MSI-X message addresses (from the MSI-X table writes).
    • Length, byte enables and payload: 1 DW for doorbells/MSI-X; 16-byte multiples for CQEs; 64-byte multiples for SQE fetches; payload decode to confirm.
    • Tags: to pair reads with completions.
    • Completion status: SC versus UR/CA.
    • Ordering and timing: data before CQE before MSI-X; doorbell before fetch.
    • Configuration context: CAP.DSTRD (doorbell stride), Max Payload Size, Max Read Request Size, IOMMU (are addresses IOVAs?).

    Without at least direction, address and an address map, the six events support dozens of stories. Packet type alone proves almost nothing.

A packet's type tells you what PCIe did. Its role in NVMe comes from direction, address, size, payload and context. Senior engineers never say "that write is the CQE" until they have checked the address against the CQ range and decoded the payload.

Lab: full trace correlation

Trace Lab — Three commands, twenty-seven rows

Safe lab Paper-and-pencil analysis of a synthetic trace; an optional Python helper with no device access.

Objective

Classify every TLP in a multi-command trace into its NVMe role, attribute data movement to commands, identify which "completions" are PCIe completions and which are NVMe completions, reconstruct queue state, and state what remains unprovable.

Skills

Address-map reasoning; tag matching; SQE and CQE payload decoding; PRP reasoning; doorbell arithmetic; evidence discipline.

Scenario

A database issues three I/Os almost simultaneously on CPU 0, which uses I/O queue pair 1. The driver writes three SQEs into SQ1 slots 5, 6 and 7 and rings the doorbell once. An unrelated agent reads the controller status register during the I/O, and the operating system happens to unmask an MSI-X vector.

def region(addr):
    for lo, hi, name in REGIONS:
        if lo <= addr < hi:

    return "unmapped"

Q1. Rows #3 and #4 carry the three NVMe commands as payload of PCIe completions. No row is a "command packet" because NVMe over PCIe never sends a command as a request; the controller pulls it.

Q2. PCIe completions: #3, #4, #7, #10, #11, #12 (46 TLPs), #14 — 52 TLPs in all. NVMe completions: #15, #21, #25 — three CQEs, all carried by posted MWr requests. The SSD sent exactly one PCIe completion: #14, answering the CPU's CSTS read.

Q3. Its address 0xFE60_201C lies in the MSI-X table (BAR0 + 0x2000 to 0x2FFF), not in the doorbell range; it targets entry 1's Vector Control Dword. Same type, direction and length as a doorbell — different role. Only the address map distinguishes them.

Q4. 24 blocks × 512 B = 12 KiB spans three pages from a page-aligned PRP Entry 1, so PRP Entry 2 must point to a PRP list holding the second and third page addresses. #5 reads that list; #7's payload gives 0x2_0001_1000 and 0x2_0001_2000, which explains the addresses in #9. Without #7 you could not verify that the data reads went to the right pages.

Q5. The completer may return a 512-byte read in several completions, each ≤ the requester's Max Payload Size (256 B here) and split on Read Completion Boundary multiples. Byte Count is the number of bytes still to be returned including this TLP's payload: 512 in the first, 256 in the last.

Q6. PRP Entry 1 = 0x2_0002_0800 has an offset of 0x800 into its page, so only 2 KiB fit before the page boundary; the remaining 2 KiB go to PRP Entry 2's page 0x2_0003_0000. Each MWr stays within a page and within 256 bytes.

Q7. 0x0062 (Write) at 9.8 µs, then 0x0063 at 22.6 µs, then 0x0061 at 41.2 µs. Legal: NVMe does not require in-order completion. Plausible reasons: the Write completed once its data reached the controller's volatile write cache (no media access needed before completion); the two Reads hit different NAND dies or planes with different busy times. These are hypotheses — the trace cannot show the media.

Q8. CQ1 head moves 37 → 38 → 39 → 40: each doorbell frees exactly one CQ slot after each CQE was consumed. The host reaped one CQE per interrupt and rang once per interrupt.

Q9. The controller had fetched up through slot 7 (head = 8) by the time it posted the first CQE, so SQ1 slots 5–7 are free for reuse from the host's perspective from #15 onward. It does not tell you when each command executed or the order of execution — SQHD reflects fetch progress, not completion order.

Q10. From the doorbell at 0 ns: CID 0x0062 ≈ 9.8 µs, CID 0x0063 ≈ 22.6 µs, CID 0x0061 ≈ 41.2 µs (to the CQE write; add interrupt and host processing time for application-visible latency).

Q11. All data TLPs (#8–#12, #18–#20, #24) are attributable only through PRP addresses from the SQE payloads and the PRP list. Without them you would know "a Write-direction transfer of 12 KiB" and "two Read-direction transfers of 4 KiB" but not which CID owns which.

Q12. Examples: that the data written was correct (payloads not decoded); that the host actually processed each interrupt (only the head doorbells suggest it); what happened inside the SSD between fetch and data transfer; that the IOMMU translated the I/O virtual addresses to the intended physical pages; that the SQEs in memory matched what the driver intended (only the fetched copy is visible).

Challenge. Surviving conclusions: roles of every TLP class from the address map; that three SQEs were fetched; that one Write-direction transfer of 12 KiB (with a list fetch) and two Read-direction 4 KiB transfers occurred; the CQE CIDs and order. Becoming hypotheses: which CID belongs to which data transfer (you might guess the Write from the direction and the CQE timing, but 0x0061 versus 0x0063 cannot be told apart from addresses alone, since you don't know which buffer each command named).

What a senior engineer notices

  • There are 52 PCIe completions and 3 NVMe completions in a 27-row summary — and the only completion the SSD itself sent is unrelated to I/O. Anyone counting "completions" without saying which kind will be wrong by an order of magnitude.
  • Row #6 would be classified as a doorbell by a naive filter on "host→device MWr to BAR0". Good filters use the BAR sub-ranges.
  • The Write finished first. Engineers who assume FIFO completion would have mis-attributed the first CQE.
  • The CSTS read in the middle of I/O is a non-posted MMIO read that stalls a CPU for ~0.9 µs. If a monitoring agent did that in a tight loop, it would show up here.

Failure variants

  • Remove the decode panel: attribution degrades as in the Challenge.
  • Make the analyzer drop #7: the Write's data addresses in #9 can no longer be verified.
  • Give CID 0x0061 and 0x0063 the same buffer by mistake: the trace would show two Reads writing the same pages — data corruption invisible at the NVMe status level.

Solution

First abnormal event: row 12a, the first non-SC PCIe completion (UR for tag 0x52). First wrong value: row 7′ — the PRP list's second entry is 0x2_0009_2000 instead of the buffer page the application wrote (0x2_0001_2000 in Part A). The first abnormal event is where the problem becomes visible, not necessarily where it begins.

Layers: the PCIe layer reported first (UR completions, and the IOMMU fault on the host); the NVMe layer reported to the application through the CQE status Data Transfer Error. The NVMe completion arrives as a normal posted MWr — the NVMe failure travels in a perfectly healthy PCIe request.

Root cause (in this synthetic scenario): the driver built the PRP list from a scatter-gather table whose third entry referred to a page from a previous, already unmapped I/O (a stale entry left in a reused list page). Regression test: issue Writes and Reads of 3–64 pages with varied offsets, reusing PRP list pages under memory pressure, with an analyzer trigger on any completion with status other than SC from the root complex to the device, and a host-side check that every PRP entry is within the current mapping.

None of the four objects is directly visible in standard Linux tools; each leaves different traces.

sudo ls /sys/kernel/tracing/events/nvme/        # nvme_setup_cmd, nvme_complete_rq, …

# NVMe-level failures: error log entries and kernel messages
sudo nvme error-log /dev/nvme0
sudo dmesg | grep -iE 'nvme|iommu|dmar|aer'

# PCIe-level errors that involve completions (UR, Completer Abort, completion timeout)
sudo lspci -vvv -s 01:00.0 | grep -iA4 'UESta\|CESta'

# Interrupt counts per queue vector (the MSI-X writes, counted)
grep nvme0q /proc/interrupts

Quiz

  1. On the PCIe link, the NVMe command is carried by:

    • The doorbell Memory Write
    • A Memory Write from the host
    • The payload of a Completion with Data answering the controller's Memory Read
    • An MSI-X message
    Answer and reasoning

    With the SQ in host memory, the controller reads the SQE; the root complex returns it in a CplD.

  2. The NVMe completion (CQE) travels as:

    • A PCIe Completion TLP
    • A posted Memory Write from the device
    • A non-posted Memory Write
    • A Message TLP
    Answer and reasoning

    The controller writes the CQE into host memory with a posted MWr.

  3. A CplD travels device→host with Completer ID = the SSD. It is:

    • An NVMe completion
    • An SQE
    • Read data for an NVMe Read
    • The answer to a CPU read of a device register
    Answer and reasoning

    The SSD is the completer only when something reads its BAR — an MMIO read by the CPU.

  4. Which PCIe field matches a completion to its request?

    • Requester ID + Tag
    • Command Identifier
    • Address
    • SQ Identifier
    Answer and reasoning

    Completions are routed by ID and matched by tag.

  5. A CplD for an SQE fetch has status SC. What do you know about the command's NVMe status?

    • Success
    • Failure
    • Nothing yet
    • It will be Data Transfer Error
    Answer and reasoning

    PCIe success only means the bytes were delivered. The NVMe status is in the later CQE.

  6. How many PCIe completions does a 4 KiB NVMe Read (one SQE, page-aligned buffer, MPS 256) typically involve?

    • Zero
    • One or two (the SQE fetch)
    • Sixteen (one per data TLP)
    • Seventeen
    Answer and reasoning

    Read data travels device→host in posted writes; only the SQE fetch needs a completion (possibly split).

  7. And a 4 KiB NVMe Write (MRRS 512, MPS 256)?

    • One
    • Two
    • Eight
    • About seventeen: the SQE fetch plus about sixteen data completions
    Answer and reasoning

    Eight 512-byte reads, each answered by two 256-byte CplDs = 16, plus the SQE fetch completion(s).

  8. Why is an "MSI-X Message" label in a trace an inference rather than a fact?

    Model answer

    MSI-X is an ordinary Memory Write; the analyzer labels it because the address falls in the platform's interrupt window or matches the MSI-X table programming. A different platform, a wrong configuration, or an analyzer without that knowledge would label it a plain MWr.

  9. Give three pieces of evidence needed to call a host→device MWr a doorbell.

    Model answer

    Address inside BAR0's doorbell range on a stride boundary (needs the BAR and CAP.DSTRD); Length 1 DW with full byte enables; a value less than the target queue's size, followed by a fetch from that queue (or a CQ head consistent with posted CQEs).

  10. Explain the "crossing" in two sentences.

    Model answer

    The NVMe command, an NVMe request, reaches the device as the payload of a PCIe completion, because the device reads it. The NVMe completion reaches the host as the payload of a PCIe request (a posted write), because the device writes it.

Interview questions

  1. Beginner: What's the difference between an NVMe completion and a PCIe completion?
    Model answer

    An NVMe completion is a 16-byte CQE the controller writes to host memory to report a command's result. A PCIe completion is a TLP that answers a non-posted PCIe request, such as a memory read. The CQE travels inside a posted Memory Write, not inside a PCIe completion.

  2. Intermediate: How do you find the NVMe commands in a PCIe capture?
    Model answer

    Find device-originated Memory Reads to the SQ address ranges, match their completions by tag, and decode the CplD payloads as 64-byte SQEs. Doorbells only tell you how many slots were published.

  3. Intermediate: A colleague says "the SSD never returned the completion". What do you ask?
    Model answer

    Which completion: a PCIe completion for a read (and whose read), the NVMe CQE, or the interrupt? Then: is there a device MWr into the CQ range with that CID? An MSI-X write after it? Did the host see it? Each answer points to a different layer.

  4. Advanced: A Write fails with Data Transfer Error. What PCIe evidence do you look for?
    Model answer

    Non-SC completions (UR/CA) or completion timeouts for the controller's data reads, poisoned TLPs, IOMMU faults on the host, AER logs on both sides; then trace back to the PRP entries or list that produced the failing addresses.

  5. Senior: How would you design an automated correlator for NVMe over PCIe traces?
    Model answer

    Build an address map from enumeration (BARs, MSI-X table), Admin registers (ASQ/ACQ) and decoded create commands; track queue state from doorbells, fetches and CQEs; decode SQE payloads to obtain CIDs and PRP/SGL ranges, including list fetches; attribute data TLPs by range membership; pair requests and completions by Requester ID and tag; flag non-SC completions, ordering violations, invalid doorbells, and phase anomalies; and report confidence and missing evidence explicitly rather than guessing.
