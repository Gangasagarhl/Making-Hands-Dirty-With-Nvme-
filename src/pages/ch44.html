An NVMe command can fail in many ways while the PCIe link underneath stays perfectly healthy. This chapter teaches the NVMe error model: the Status Field in every completion, its status code types and the codes you will meet most, the Do Not Retry and More bits, the Error Information log, Asynchronous Event Requests, aborts, and the controller's last word — Controller Fatal Status.

Why this chapter exists

So far, every command in this course has completed with status zero. Real systems are not so kind. A READ hits an unreadable block, a driver sends a field the controller does not support, firmware hits an assertion, the host asks for LBA 2 billion on a 1 TB namespace. Each of these is reported in an NVMe-defined way that is completely independent of PCIe. A PCIe analyzer will show those failures as perfectly successful TLPs: the controller DMA-wrote a completion entry; the link did its job. The failure is inside the 16 bytes.

Separating "NVMe said no" from "PCIe could not deliver" is the most important layering skill in this part of the course. This chapter covers the NVMe side; Chapter 45 covers PCIe; Chapter 47 correlates them.

Learning objectives

  • Decode the Status Field of a Completion Queue Entry (CQE): Status Code (SC), Status Code Type (SCT), Command Retry Delay (CRD), More (M) and Do Not Retry (DNR).
  • Name the status code types (Generic, Command Specific, Media and Data Integrity, Path Related, Vendor Specific) and classify a failure into the right one.
  • Recognise the common generic codes: successful completion, invalid opcode, invalid field, command ID conflict, data transfer error, internal error, abort requested, invalid namespace or format, LBA out of range — and the media codes such as unrecovered read error.
  • Explain command aborts (the Abort command, SQ deletion, and what the aborted command's CQE looks like).
  • Use the Error Information log page and Asynchronous Event Requests to get context the CQE cannot carry.
  • Recognise controller fatal state (CSTS.CFS) and distinguish it from a device that has vanished from the bus (all-ones reads).
  • Read NVMe errors in Linux kernel logs and with nvme-cli, and reason about retry behaviour.

Prerequisites

You need the CQE format from Queue Architecture and NVMe Command Structure, the admin commands from Admin Commands (Get Log Page 02h, Identify 06h), the I/O commands from NVM Command Set, READ and WRITE, and the controller registers from NVMe Registers (CSTS at 1Ch).

The story

Back to the library. Every request slip comes back with an answer slip. Most say "Here's your book." But some say:

  • "I don't understand what you wrote" — you asked for something the library does not do.
  • "You asked for shelf 900 but the library only has 500 shelves."
  • "The book is there, but the pages are smudged and I can't read them."
  • "You told me to stop looking, so I stopped."
  • "Don't bother asking again — it won't work next time either." (a little red stamp on the slip)
  • "There's more to this story in the big notebook at the front desk." (a blue stamp)

And once in a while the librarian faints. She doesn't answer slips at all, but she has a sign on her desk that flips from "OK" to "I need help". Someone must wake her up and start again.

Think of a postal parcel service. Each parcel comes back with a delivery receipt carrying a reason code from a small set of families: "address problem", "this kind of parcel has its own rules", "parcel damaged", "route problem", "carrier-specific". A "do not resend" box can be ticked. A "see incident report" box points you to the depot's incident log. And if the depot itself catches fire, receipts stop and a status light on the depot turns red.

Hides: the receipt is written into your memory by the depot over PCIe; it is not a separate channel, so a receipt can only report what the controller knows. If PCIe itself fails, no receipt arrives at all. Misleads: "do not resend" (DNR) is a hint about the same command on the same controller, not a statement that the data is lost forever: a different path in a multipath setup, or a retry after a reset, may still succeed. And the incident log has limited pages: old entries are overwritten, so you must read it promptly.

Beginner explanation

Every NVMe command gets exactly one completion entry (16 bytes) in a completion queue. Inside it, a 15-bit Status Field says how the command ended. Zero means success. Anything else is an error, described by two numbers:

  • The Status Code Type (SCT) — which family of error (3 bits).
  • The Status Code (SC) — which specific error in that family (8 bits).

Two single-bit flags travel with them: Do Not Retry (DNR) and More (M). DNR=1 means "retrying the same command is expected to fail again". M=1 means "more information is in the Error Information log page".

The error is NVMe's own report. It does not mean PCIe failed. In fact, you only see an NVMe status because PCIe successfully delivered the completion.

The Status Field in the CQE

The CQE's Dword 3 holds the Command Identifier (CID), the Phase Tag (P) and the Status Field:

The other CQE Dwords still matter in an error: DW2 carries the SQ Identifier and SQ Head Pointer (so you know which queue the failed command came from and that the controller consumed it), and DW0 (sometimes DW1) carries command-specific result information.

The Linux NVMe driver stores status as a 16-bit value with the Phase Tag shifted out: (SCT << 8) | SC, plus CRD in bits 12:11, More = 0x2000, DNR = 0x4000. So an Unrecovered Read Error (SCT 2h, SC 81h) appears as 0x281 in driver code, and with DNR as 0x4281. Do not confuse that packing with the raw CQE DW3 value, which is shifted left by 17 bits relative to the SC.

"Media error" does not prove the NAND is bad. An Unrecovered Read Error could be genuine media wear, a firmware mapping bug, a power-loss corruption, or a read of an LBA that was never correctly written. End-to-end Reference Tag errors in particular often indicate the controller returned the wrong block, not a damaged one.

Path Related Status (SCT 3h)

Used with multipath and Asymmetric Namespace Access (ANA): Internal Path Error (00h), Asymmetric Access Persistent Loss (01h), Asymmetric Access Inaccessible (02h), Asymmetric Access Transition (03h), and controller- and host-pathing errors in higher values (confirm). The key property is that these say "try another path", which is why Linux native multipath treats them differently from other errors (failover rather than fail).

DNR, More and CRD in practice

  • DNR=0: the controller does not rule out success on retry. Linux retries such commands up to nvme_core.max_retries times (default 5), honouring CRD delays when the host has enabled Advanced Command Retry Enable through the Host Behavior Support feature.
  • DNR=1: fail immediately; retrying wastes time. An invalid field will be invalid next time too.
  • M=1: read the Error Information log page now — entries are a ring and can be overwritten.
  • CRD≠0: wait the selected delay (CRDT1/2/3 from Identify Controller, in units of 100 ms) before retrying.

CRD and the Advanced Command Retry mechanism were added in NVMe 1.4. Older controllers always return CRD=0. Kernel retry policy (max retries, multipath failover rules, verbose error strings) is kernel-version-dependent.

Command ID conflicts

The CID, together with the SQ Identifier, uniquely identifies an outstanding command. The host must not reuse a CID in the same SQ until the previous command with that CID has completed. If it does, the controller may return Command ID Conflict (03h). Controllers are not required to detect every conflict, and a conflict the controller misses can corrupt the host's bookkeeping (two completions with the same CID, or a completion matched to the wrong request). Linux mitigates this by encoding a generation counter in the upper CID bits so it can detect completions for stale requests and log them.

Namespace errors

Namespace errors come in two flavours: addressing (Invalid Namespace or Format 0Bh — the NSID is invalid, inactive or not attached; LBA Out of Range 80h — the address is beyond NSZE) and state (Namespace Not Ready 82h, Format In Progress 84h, Reservation Conflict 83h, Namespace is Write Protected). Addressing errors are almost always host bugs or stale host state (for example after a namespace was deleted and recreated with a smaller size). State errors are often transient and DNR tells you whether to wait.

Aborts

A command can end with an "aborted" status for several reasons:

  • Abort command (admin opcode 08h): the host names a command by SQ Identifier and CID. The controller makes a best effort; the Abort command's own completion (Dword 0, bit 0) says whether the target was aborted. If it was, the target completes with Command Abort Requested (07h). If not, the target eventually completes normally. Identify Controller's Abort Command Limit (ACL, 0's based) bounds concurrent aborts.
  • SQ deletion: deleting a submission queue aborts commands still in it (08h).
  • Reset: a Controller Level Reset (CC.EN 1→0) aborts every outstanding command without posting completions — the host must treat them as failed and resubmit. This is the important asymmetry: aborts post a CQE, resets do not.
  • Power loss: 05h when a power-loss notification forces a shutdown.

In Linux, the timeout handler historically sent an Abort first and escalated to a controller reset if the abort itself timed out. Current kernels often go straight to reset for I/O timeouts on PCIe, and some devices handle Abort poorly. Always look at which path your kernel took (see NVMe Reset).

The Error Information log page

The CQE has 15 bits of status. The Error Information log page (Log Identifier 01h, read with Get Log Page) adds context. It is a ring of 64-byte entries; Identify Controller's Error Log Page Entries (ELPE, 0's based) says how many the controller keeps. Each entry contains, by name:

  • Error Count — a 64-bit, monotonically increasing identifier; 0 marks an empty entry. A gap in counts between reads means entries were lost (overwritten).
  • Submission Queue ID and Command ID — which command (FFFFh when not tied to a command).
  • Status Field — the status that was (or would have been) posted.
  • Parameter Error Location — which byte and bit of the command caused the error, for invalid-field style errors. Extremely useful for driver developers.
  • LBA and Namespace — first LBA that experienced the error and the NSID.
  • Vendor Specific Information Available — points to a vendor log page with more detail.
  • Transport Type and Transport Type Specific Information; Command Specific Information.

The specification does not require a log entry for every failed command, and how many entries survive a controller reset or power cycle is implementation-dependent. Read the byte offsets of the entry fields from the Error Information log page table in the NVMe Base Specification rather than from memory.

Asynchronous Event Requests

Some errors are not tied to any command: a doorbell write to a non-existent queue, a persistent internal error, a temperature threshold crossed. NVMe reports these through Asynchronous Event Requests (admin opcode 0Ch). The host keeps one or more AER commands outstanding (up to Identify Controller's AERL + 1). They have no timeout. When an event occurs, the controller completes one with Dword 0 describing it:

In NVMe, AER means Asynchronous Event Request. In PCIe, AER means Advanced Error Reporting (Chapter 46). They are unrelated mechanisms at different layers. Always expand the acronym in bug reports.

Internal errors and controller fatal state

An internal error can be scoped to one command (Internal Error 06h in that command's CQE), to the controller but recoverable (Transient Internal Error asynchronous event), or terminal. The terminal case is Controller Fatal Status (CSTS.CFS): bit 1 of the Controller Status register at offset 1Ch. When the controller sets CFS it is telling the host "I can no longer process commands; reset me". Outstanding commands will not complete. The host must perform a reset (Controller Level Reset via CC.EN, or an NVM Subsystem Reset, or a PCIe-level reset) and reinitialise.

Reading CSTS during an error

A register value of all ones from an MMIO read almost always means the read never reached a functioning device. Many platforms synthesise all-ones data when a non-posted read fails. Linux prints CSTS together with the PCI Status register in its "controller is down" message precisely so you can tell CFS (NVMe) from all-ones (PCIe).

The central concept on the ladder

Every request slip comes back with an answer slip; the answer can say "no", and why, and whether asking again could help.

Each command completes with a CQE whose Status Field gives a type (SCT), a code (SC), and DNR/More/CRD hints.

The controller's command processor or media back-end detects the error, the completion engine writes the CQE with non-zero status into the host CQ, optionally logs an Error Information entry in controller memory, and raises the interrupt as usual.

NVMe Base Specification: Completion Queue Entry, Status Field definition, Status Code Type values, Generic/Command Specific/Media/Path status tables; Error Information log page; Asynchronous Event Request; Controller Status register. NVM Command Set: NVM-specific status values.

On the link, an error completion is a perfectly normal Device→Host MWr of 16 bytes plus the usual MSI-X write. No PCIe error is involved.

The analyzer's NVMe decoder shows the CQE with Status ≠ 0; a raw TLP view shows only data bytes where DW3 bits 31:17 are non-zero. You must decode the payload to see the error.

Classify: SCT 0/1 with DNR → host sent something wrong (driver/application). SCT 2 → media/data path (controller/firmware/NAND). Generic 04h → look below at PCIe. No CQE at all → not an NVMe status problem: timeout, CFS, or PCIe.

Hardware view

Errors are detected in different blocks of the controller, and where an error is detected determines what status it can produce:

  • Validation errors are found before any data moves; the CQE comes back quickly (microseconds).
  • Data transfer errors appear when the controller's own PCIe requests fail — for example, its Memory Read of a host data buffer returns a Completion with Unsupported Request status because the address is not mapped in the IOMMU. The controller cannot report a PCIe error to the host's NVMe driver directly, so it maps the failure to an NVMe status (often 04h). The PCIe side may also log an AER error at the device or root port.
  • Media errors come back after the media latency (tens of microseconds to many milliseconds, since the controller retries reads internally with different thresholds before giving up).
  • Fatal state is usually set by firmware when an internal consistency check or watchdog fails; the controller may stop responding to doorbells while still answering MMIO reads.

Which conditions a controller detects, how long it retries a weak read before returning 81h, which internal errors it logs, and what vendor-specific detail it keeps are all implementation-dependent.

The Status Field occupies CQE Dword 3 bits 31:17 with SC (8 bits), SCT (3 bits), CRD (2 bits), More and DNR. SCT values: 0h Generic, 1h Command Specific, 2h Media and Data Integrity, 3h Path Related, 7h Vendor Specific. Generic codes 00h Successful Completion, 01h Invalid Command Opcode, 02h Invalid Field in Command, 03h Command ID Conflict, 04h Data Transfer Error, 06h Internal Error, 07h Command Abort Requested, 08h Aborted due to SQ Deletion, 0Bh Invalid Namespace or Format; NVM 80h LBA Out of Range; Media 80h Write Fault, 81h Unrecovered Read Error. Error Information is Log Identifier 01h. Asynchronous Event Request is admin opcode 0Ch; Abort is 08h. CSTS is at offset 1Ch with RDY in bit 0 and CFS in bit 1.

Mapping a status to a "layer" (host, controller, media, PCIe) is interpretation. The specification defines what each code means, not whose bug it is.

Which status a controller chooses when several apply; whether it detects CID conflicts; how many Error Information entries it keeps and whether they survive reset; DNR choice for internal errors; how long before media errors are returned.

The set of status codes grows with every revision (for example, codes for newer features and fabrics). CRD arrived with NVMe 1.4. NVMe 2.0 split command-set-specific statuses into separate command set specifications. Always use the tables of the revision your device reports in the VS register and Identify Controller.

Check in the specification: exact values for the less common generic codes (SGL and PRP related, write protection, transient transport error); command-specific values per command; the complete list of Asynchronous Event Information values per type; Error Information log entry byte offsets. The specification does not say how a host must retry, how many times, or whether a media error should take a drive out of service.

Never assume a non-zero status implies a PCIe problem, or that a PCIe problem will always produce an NVMe status. Never assume DNR=0 means the retry will succeed. Never treat vendor-specific (SCT 7h) codes as portable.

Code / pseudocode

CQE status decoder

Standard-library Python. Decodes a raw CQE Dword 3 (or a Linux-style packed status) and names common codes. Codes not in its table are reported as "look up in the specification" rather than guessed.

#!/usr/bin/env python3
"""Decode NVMe completion status. Synthetic teaching tool; names only the
common codes taught in Chapter 44. Usage: nvme_status.py 0x81010051 [...]
   or: nvme_status.py --linux 0x4281   (Linux packed status)"""
import sys

SCT = {0: "Generic", 1: "Command Specific", 2: "Media and Data Integrity",
       3: "Path Related", 7: "Vendor Specific"}
GENERIC = {0x00: "Successful Completion", 0x01: "Invalid Command Opcode",
           0x02: "Invalid Field in Command", 0x03: "Command ID Conflict",
           0x04: "Data Transfer Error",
           0x05: "Commands Aborted due to Power Loss Notification",
           0x06: "Internal Error", 0x07: "Command Abort Requested",
           0x08: "Command Aborted due to SQ Deletion",
           0x0B: "Invalid Namespace or Format", 0x0C: "Command Sequence Error",
           0x80: "LBA Out of Range (NVM)", 0x81: "Capacity Exceeded (NVM)",
           0x82: "Namespace Not Ready (NVM)", 0x83: "Reservation Conflict (NVM)",
           0x84: "Format In Progress (NVM)"}
MEDIA = {0x80: "Write Fault", 0x81: "Unrecovered Read Error",
         0x82: "End-to-end Guard Check Error",
         0x83: "End-to-end Application Tag Check Error",
         0x84: "End-to-end Reference Tag Check Error", 0x85: "Compare Failure",
         0x86: "Access Denied", 0x87: "Deallocated or Unwritten Logical Block"}
LAYER = {0: "host request or controller state", 1: "host request (command-specific)",
         2: "controller media / data path", 3: "multipath / ANA path",
         7: "vendor-defined"}

def name(sct, sc):
    table = {0: GENERIC, 2: MEDIA}.get(sct, {})
    return table.get(sc, "not in this decoder's table: look it up in the specification")

def decode_fields(sc, sct, crd, more, dnr, cid=None, phase=None):
    out = [f"SCT {sct:X}h ({SCT.get(sct, 'Reserved')}), SC {sc:02X}h: {name(sct, sc)}"]
    out.append(f"CRD={crd} More={more} DNR={dnr}"
               + ("" if cid is None else f" P={phase} CID=0x{cid:04X}"))
    if sct == 0 and sc == 0:
        out.append("success")
    else:
        out.append(f"suggested first suspicion: {LAYER.get(sct, 'unknown')}")
        if sct == 0 and sc == 0x04:
            out.append("note: Data Transfer Error often hides a PCIe-level failure; check AER")
        out.append("retry: " + ("no (DNR)" if dnr else "permitted" + (f", after CRDT{crd}" if crd else "")))
        if more:
            out.append("read the Error Information log (LID 01h) now")
    return out

def from_dw3(dw3):
    status = dw3 >> 17
    return decode_fields(status & 0xFF, (status >> 8) & 7, (status >> 11) & 3,
                         (status >> 13) & 1, (status >> 14) & 1,
                         cid=dw3 & 0xFFFF, phase=(dw3 >> 16) & 1)

def from_linux(st):
    return decode_fields(st & 0xFF, (st >> 8) & 7, (st >> 11) & 3,
                         (st >> 13) & 1, (st >> 14) & 1)

if __name__ == "__main__":
    args = sys.argv[1:] or ["0x00010048", "0x81010051", "0x45030072", "--linux", "0x4281"]
    linux = False
    for a in args:
        if a == "--linux":
            linux = True
            continue
        v = int(a, 0)
        print(("Linux status " if linux else "CQE DW3 ") + f"0x{v:08X}")
        for line in (from_linux(v) if linux else from_dw3(v)):
            print("   " + line)
        linux = False

Host retry decision (pseudocode, modelled on common driver behaviour)

disposition decide(req, status) {
    if (status == SUCCESS)               return COMPLETE;
    if (is_path_error(status) && multipath) return FAILOVER;   /* SCT 3h */
    if (status.dnr || req->retries >= max_retries || req_is_failfast(req))
                                         return FAIL;
    delay = status.crd ? crdt[status.crd] * 100ms : 0;           /* if ACRE enabled */
    return RETRY_AFTER(delay);
}

Worked example

Scenario (synthetic). After installing a new kernel module that builds custom Dataset Management commands, the kernel log fills with lines like nvme0n1: I/O Cmd(0x9) … I/O Error (sct 0x0 / sc 0x2) DNR.

  1. Classify. Opcode 09h (Dataset Management), SCT 0h, SC 02h: Invalid Field in Command, DNR. The controller rejected a field. This is a host-side request problem until proven otherwise.
  2. Get the location. nvme error-log /dev/nvme0 shows the newest entry with the same CID and a Parameter Error Location pointing at byte 40 (Command Dword 10), bits 7:0 — the Number of Ranges field.
  3. Inspect the command. The module sets Number of Ranges to the count of ranges, but the field is 8 bits wide and 0's based. With 256 ranges the module writes 0x100 into Command Dword 10: the low 8 bits become 0 and bit 8 — a reserved bit — becomes 1. A non-zero reserved bit is an invalid field. (With fewer ranges the bug is quieter: the controller processes one range too many.)
  4. Fix and verify. Write nr_ranges - 1, cap at 256 ranges. Re-run: status 0.
  5. Lesson. Parameter Error Location turned a vague "invalid field" into an exact byte and bit. This is why the Error Information log exists.

The Number of Ranges field description (8 bits, 0's based) is from the NVM Command Set Dataset Management command; confirm in Dataset Management. The Parameter Error Location value here is synthetic.

Common mistakes

  • Reading SC without SCT. SC 80h is "LBA Out of Range" under SCT 0h and "Write Fault" under SCT 2h.
  • Decoding the Status Field from DW3 without shifting by 17 (the Phase Tag is bit 16).
  • Treating every error as PCIe: an NVMe status proves the PCIe path delivered a completion.
  • Treating every Data Transfer Error as NVMe: it is often the NVMe echo of a PCIe failure.
  • Ignoring the More bit and reading the Error Information log hours later after it has wrapped.
  • Retrying DNR=1 commands in user-space tools in a loop.
  • Confusing NVMe AER (Asynchronous Event Request) with PCIe AER (Advanced Error Reporting).
  • Reading CSTS=0xFFFF_FFFF as "CFS set". All ones means the read failed.
  • Assuming an aborted command will produce a CQE after a reset. Resets do not post completions.

Senior engineer insight

  • Status codes describe symptoms at the controller's boundary. A Data Transfer Error describes what the controller saw, not what went wrong. Always ask "what could have made the controller see this?"
  • The first error matters, not the loudest. A burst of I/O errors after a controller reset is usually fallout. Find the first failing command's status and the first abnormal event before it.
  • Firmware sometimes lies by generalising. Internal Error (06h) is a catch-all. If a device returns it frequently, ask the vendor for the vendor-specific log that maps it to a cause.
  • Read logs early. Error Information log entries and telemetry are volatile; a reset or a flood of new errors can destroy the evidence. Make collection automatic.
  • Watch DNR in validation. Wrong DNR is a subtle compliance bug: DNR=1 on a transient condition causes unnecessary application failures; DNR=0 on a permanent one causes long retry stalls.

Lab

Lab 44 — Provoke, capture and decode harmless NVMe errors

Objective

Generate three NVMe error completions with read-only commands, see each in the kernel log or nvme-cli output and in the Error Information log, and decode each by hand.

Skills

Status decoding, Error Information log reading, Linux NVMe error messages.

Safety

Caution lab All commands are reads or Get commands and do not modify data, but they deliberately cause errors. Use a test device: error counters in SMART will increase, and on shared systems monitoring may alert. Never use vendor-specific opcodes for "invalid opcode" tests — they may do something.

Hardware required

Linux host with a test NVMe SSD.

Software required

nvme-cli, Python 3, nvme_status.py.

Input

NSZE of namespace 1 (from nvme id-ns /dev/nvme0n1), LBA size.

Expected output

Three decoded statuses: Invalid Field in Command, LBA Out of Range, and (if the device logs them) matching Error Information entries.

Background

A Get Features with a reserved Feature Identifier is invalid; a READ whose range crosses NSZE is out of range.

Step 1 — Baseline

sudo nvme error-log /dev/nvme0 -e 4 > before.txt
sudo nvme id-ctrl /dev/nvme0 | grep -i elpe

Step 2 — Invalid field

sudo nvme get-feature /dev/nvme0 -f 0x00 ; echo "exit=$?"
# FID 00h is reserved; expect an error status reported by nvme-cli

Step 3 — LBA out of range

NSZE=$(sudo nvme id-ns /dev/nvme0n1 | awk '/^nsze/ {print $3}')
sudo nvme read /dev/nvme0n1 --start-block=$((NSZE - 4)) --block-count=7 \
     --data-size=4096 --data=/dev/null ; echo "exit=$?"
sudo dmesg | tail -5

Observation

Compare nvme error-log after each step with before.txt. Decode each status with nvme_status.py.

Questions

  1. Did the device log an entry for each error? If not, why might it not?
  2. Was DNR set in each case? Is that what you expected?
  3. How long did each error take to complete, roughly, and what does that say about where it was detected?

Challenge

Write a script that polls the Error Information log every minute and alerts when Error Count jumps by more than ELPE+1 (entries lost).

Hint

Block count in nvme-cli is 0's based on some versions (the NLB field is 0's based). Check whether 7 means 7 or 8 blocks on your build.

Solution

1. Logging is not mandatory for every error; many controllers log invalid-field errors with Parameter Error Location and LBA range errors with the LBA, but some only log media/internal errors.

2. Expected DNR=1 for both: neither will succeed on retry.

3. Both are detected at command validation, so completion takes microseconds — no media access. A media error would take far longer.

Challenge: store the last Error Count; if new_count − last_count > ELPE + 1, the ring overflowed between polls and entries were lost.

What a senior engineer notices

Whether the device's Parameter Error Location is populated (quality signal); whether the SMART error-log-entries counter matches the number of errors you caused; whether dmesg printed anything for admin errors issued via passthrough (it often does not).

Failure variants

  • nvme-cli refuses the out-of-range read before sending it (some versions validate) — use io-passthru to send the raw command.
  • Error log returns all-zero entries — device keeps few or none.

Extension

Enable the nvme_complete_rq tracepoint and catch each status as it completes, with timestamps.

Exercises

  1. Decode CQE DW3 = 0x0403_0011 and 0xC502_0099.
  2. Build DW3 for: CID 0x0200, Phase 0, SCT 1h, SC 02h, DNR 1.
  3. A Create I/O SQ fails with SCT 1h SC 00h. What did the host do wrong?
  4. List three reasons a READ might end with Generic 04h.
  5. Explain why a controller reset does not produce CQEs for outstanding commands and how the host learns their fate.
Model answers

1. 0x0403_0011 >> 17 = 0x201 → SC = 01h, SCT = (0x201 >> 8) & 7 = 2h, M=0, DNR=0; P=1; CID 0x0011. SCT 2h SC 01h is not a defined media code in the table taught here — look it up; suspect a vendor or version issue. 0xC502_0099: >>17 = 0x6281 → SC 81h, SCT 2h, More=1, DNR=1; P=0; CID 0x0099 → Unrecovered Read Error, no retry, see log.

2. Status = DNR(1<<14) | SCT 1<<8 | 0x02 = 0x4102; DW3 = 0x4102 << 17 | 0x0200 = 0x8204_0200.

3. Completion Queue Invalid: the CQID named in the Create I/O SQ does not exist (CQ not created, or created and deleted).

4. The controller's read of a PRP list or SGL failed (UR/CA completion, completion timeout); a poisoned completion from host memory; an internal DMA error.

5. A reset discards controller state including queues; there is nowhere valid to post. The host's timeout/reset path fails or requeues all outstanding requests itself.

Quiz

  1. Which bits of CQE Dword 3 hold the Status Field?

    • 15:0
    • 31:17
    • 31:16
    • 23:16
    Answer and reasoning

    Bit 16 is the Phase Tag; 15:0 is the CID.

  2. SCT 2h is

    • Generic
    • Command Specific
    • Media and Data Integrity Errors
    • Path Related
    Answer and reasoning

    0 Generic, 1 Command Specific, 2 Media, 3 Path, 7 Vendor.

  3. Generic status 0Bh means

    • Invalid Namespace or Format
    • LBA Out of Range
    • Internal Error
    • Command ID Conflict
    Answer and reasoning

    LBA Out of Range is 80h; Internal Error 06h; CID Conflict 03h.

  4. DNR=1 means

    • The data was not written
    • Resubmitting the same command is expected to fail
    • The controller is fatal
    • The host must reset
    Answer and reasoning

    It is retry guidance for that command.

  5. Which register bit indicates the controller has hit a fatal condition?

    • CC.EN
    • CSTS.RDY
    • CSTS.SHST
    • CSTS.CFS
    Answer and reasoning

    Controller Fatal Status, CSTS bit 1.

  6. The NVMe Error Information log page is Log Identifier

    • 01h
    • 02h
    • 03h
    • 0Ch
    Answer and reasoning

    02h is SMART/Health, 03h Firmware Slot; 0Ch is the AER opcode, not a log.

  7. Why can an NVMe error completion never by itself prove the PCIe link is faulty?

    Model answer

    Because the CQE reached host memory over PCIe; the link delivered it. A PCIe fault may be the cause (e.g. behind a Data Transfer Error), but you must find PCIe evidence (AER, analyzer) to say so.

  8. What happens to an Asynchronous Event type after it is reported, and how does the host re-arm it?

    Model answer

    Further events of that type are masked until the host reads the associated log page with Retain Asynchronous Event cleared; the host also resubmits an AER command.

  9. Linux prints CSTS=0xffffffff. What layer do you investigate first?

    Model answer

    PCIe: the MMIO read failed (device unreachable). Check link state, AER, removal, power — not NVMe firmware first.

  10. How does an Abort command's result differ from the aborted command's result?

    Model answer

    The Abort completes with its own status and Dword 0 indicating whether the target was aborted; the target, if aborted, completes separately with Command Abort Requested (07h).

Interview questions

  1. Beginner: Where does an NVMe command's error status appear?

    Model answer

    In the Status Field of its Completion Queue Entry (DW3 bits 31:17).

  2. Beginner: Name the status code types.

    Model answer

    Generic, Command Specific, Media and Data Integrity, Path Related, Vendor Specific.

  3. Intermediate: What are the More and DNR bits for?

    Model answer

    More: additional information in the Error Information log. DNR: retrying the same command is expected to fail.

  4. Intermediate: How do NVMe asynchronous events work?

    Model answer

    Host keeps AER commands outstanding; controller completes one when an event occurs with type, info and log page ID; that type is masked until the log is read; host resubmits.

  5. Advanced: A READ returns Data Transfer Error. Walk through your investigation.

    Model answer

    Check AER at device and root port for UR/CA/completion timeout/poisoned TLP around the time; IOMMU fault logs for the device; validate PRPs/SGL in the SQE (trace or tracepoints); check whether the errors cluster on particular buffers or CPUs; reproduce with IOMMU in passthrough to separate translation issues.

  6. Advanced: Distinguish CSTS=0x3 from CSTS=0xFFFFFFFF.

    Model answer

    0x3: RDY and CFS set — controller reachable but fatal (NVMe). All ones: read failed (PCIe/link/device gone).

  7. Senior: Design an error-handling validation plan for an NVMe controller.

    Model answer

    Matrix of invalid inputs per command (opcodes, reserved fields, NSIDs, LBA ranges, PRP offsets, SGL types) → expected SCT/SC/DNR and log entries; media fault injection (ECC failure, program failure, PI mismatch); abort races (abort before fetch, during data, after completion); SQ deletion with outstanding commands; AER limits and masking; CFS injection and host recovery; CID reuse detection; Error log ring wrap and Error Count monotonicity.

Chapter summary

NVMe reports command outcomes in the CQE Status Field: SC and SCT (Generic, Command Specific, Media and Data Integrity, Path Related, Vendor Specific), plus CRD, More and DNR. Common generic codes include 00h success, 01h invalid opcode, 02h invalid field, 03h CID conflict, 04h data transfer error, 06h internal error, 07h abort requested, 0Bh invalid namespace or format, and NVM 80h LBA out of range; key media codes are 80h write fault and 81h unrecovered read error. The Error Information log (01h) adds location and context; Asynchronous Event Requests (0Ch) report events not tied to a command; CSTS.CFS signals a fatal controller that needs reset, while all-ones reads point at PCIe. An NVMe error travels in a normal, successful PCIe write.

Do not move on until you can:

  • decode any CQE DW3 into CID, P, SC, SCT, CRD, M, DNR by hand
  • name the status code types and give an example of each
  • recite the common generic and media codes taught here and know where to look up the rest
  • explain aborts vs resets in terms of whether a CQE is posted
  • use the Error Information log and asynchronous events to get context
  • tell CSTS.CFS from an all-ones read and name the layer for each
  • find an error completion in a trace and decide its likely layer
