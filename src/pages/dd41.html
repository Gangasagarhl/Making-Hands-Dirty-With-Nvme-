This module turns the reset family from Chapter 48 — NVMe Reset and Chapter 49 — PCIe Reset into an engineering discipline: which reset a host should choose, how it escalates when one fails, what each reset destroys (including evidence), how resets collide with long-running admin operations and with other hosts, and how to prove from a trace which reset actually happened.

Orientation

The chapters taught each reset on its own: the Controller Configuration enable bit (CC.EN) handshake with Controller Status Ready (CSTS.RDY), the NVM Subsystem Reset (NSSR) magic value, shutdown, Function Level Reset (FLR), Hot Reset through Secondary Bus Reset (SBR), Fundamental Reset through PERST#, and the readiness rules after each. This module assumes all of that and asks the senior questions: which reset should recovery code try first, how long may each tier take before the next starts, what does each tier destroy, and how do you tell from a capture whether the device was reset from above (registers), from beside (configuration space) or from below (the link)?

Re-read Chapter 48 (CC.EN/CSTS.RDY, the Capabilities Timeout field CAP.TO, the "destroys / survives" table, NSSR, shutdown) and Chapter 49 (Conventional, Fundamental and Hot Reset, FLR, Configuration Request Retry Status — CRS, renamed Request Retry Status, RRS — and the readiness waits). Error vocabulary: NVMe Errors, AER, Advanced Error Handling.

Kid story

A puppet theatre has one puppeteer. Sometimes the strings tangle mid-show. The smallest fix is to untangle one puppet while the others keep dancing. A bigger fix is "put all the puppets down and show me your empty hands". Bigger still is closing the curtain on the whole stage, which also resets that stage's lights and music. Biggest of all is switching the theatre's power off and on.

The manager's rule: try the smallest fix that can work, wait the right time for it, and only then try the next one. And before any big fix, take a photo of the tangle — afterwards nobody can see how it happened.

Analogy boundary

What it represents. One puppet = deleting and re-creating one I/O queue pair; "empty hands" = CC.EN = 0 then polling until CSTS.RDY = 0; closing one stage = FLR; the stage's lights and music = a Hot Reset or link-down event; theatre power = cold Fundamental Reset; the photo = capturing logs and telemetry first.

What it hides. Puppets that stop mid-dance do not report it: after a controller-level reset no completion is ever posted for in-flight commands. And some puppets belong to another theatre: an NSSR resets controllers another host may own.

Where it misleads. A bigger fix is not always a superset of host work: a controller reset leaves configuration space alone, while FLR forces the host to restore Base Address Registers (BARs), Bus Master Enable and MSI-X before it may even read CSTS. And a bigger reset can be the wrong layer: Hot Reset travels over the link, so it cannot reach a device whose link is already dead.

Mechanism

The central mechanism is the reset escalation ladder, shown on the synthetic Lab SSD (Requester ID 0x0100 at 0000:01:00.0, Root Port 00:01.1, BAR0 = 0xFE60_0000, CAP = 0x0040_0830_1401_0FFF so CAP.TO = 20 → 10 s and NSSRS = 1). The policy is host behaviour modelled on Linux, not specification text.

  1. Detect. Who: block-layer timer. What changes: a request passes nvme_core.io_timeout (historically 30 s). Where: host only. Evidence: kernel log; no completion queue entry (CQE) for that command identifier on the wire.
  2. Triage. Who: timeout handler. What: reads CSTS (MRd32 to 0xFE60_001C), polls the completion queue. Where: BAR0, CQ memory. Evidence: CFS = 1 → reset now; 0xFFFF_FFFF → PCIe layer broken, skip NVMe tiers; CQE found → interrupt problem, not a hang.
  3. Abort. Who: driver. What: Abort (admin opcode 08h) naming SQ and command identifier. Where: admin SQ. Evidence: the Abort's CQE; Dword 0 bit 0 = 1 means "not aborted". Abort is best-effort.
  4. Controller reset. Who: driver. What: MWr32 0x0046_0060 to 0xFE60_0014 (EN = 0), RDY falls. Where: registers and all queue tables. Evidence: CSTS polls; no new SQE fetches.
  5. Account for outstanding commands. Who: driver. What: every tracked command is requeued or failed by the host. Where: host structures. Evidence: no CQEs ever appear for them.
  6. Rebuild. Who: driver. What: zero admin CQ, program AQA/ASQ/ACQ, CC = 0x0046_0061, Identify, Number of Queues, features, Create I/O CQ/SQ, Asynchronous Event Requests, namespace rescan. Evidence: the bring-up command sequence.
  7. FLR if RDY never falls within CAP.TO. Who: PCI core. What: save configuration, clear Bus Master Enable, wait for Transactions Pending = 0, Initiate FLR, wait readiness, restore. Evidence: CfgWr0 to Device Control, link stays in L0, CfgRd0 polls (CRS allowed), CfgWr0 restores.
  8. Bus or slot reset if FLR is unavailable or ineffective. Who: PCI core or platform. Where: everything below Root Port 00:01.1. Evidence: TS1 with Hot Reset, electrical idle, retraining, InitFC DLLPs, configuration requests.
  9. Give up safely. Controller marked dead, namespaces removed; multipath should already have failed over. Evidence: sysfs state "dead".

The ladder for reset escalation

Untangle one puppet; if the puppeteer will not show empty hands, close the curtain; if the curtain is stuck, switch off the stage; photograph first.

The host tries Abort, controller reset, function reset, bus or slot reset, then removal, waiting a bounded time at each and rebuilding what each destroyed.

Each tier reaches deeper hardware: the command engine (CC.EN), the function's register logic (FLR), the PHY and Data Link Layer (Hot Reset), the whole board including boot firmware (PERST#). Firmware wedged in a media operation may ignore CC.EN; nothing ignores PERST#.

The NVMe Base Specification defines controller-level resets and CAP.TO; the NVMe over PCIe Transport Specification maps PCIe resets onto them; the PCI Express Base Specification defines FLR, Conventional Reset and readiness. None defines the escalation order or budgets.

Signatures: an Abort SQE; an MWr to BAR0+14h; a configuration write to Device Control; TS1 ordered sets with Hot Reset; electrical idle with no ordered sets (power or PERST#).

The first abnormal event is usually the poll after a reset: RDY still 1 at CAP.TO, or an Unsupported Request (UR) completion because configuration was not restored.

The tier that finally recovered the device localizes the fault: FLR but not CC.EN → controller reset path in firmware; only slot power → PHY, power or boot firmware. Fleet metrics of "recovering tier" per firmware expose regressions.

Specification discipline

  • NVM Express Base Specification, Revision 2.4 — Controller Registers; Resets; Controller Initialization; Controller Shutdown; Abort; Set Features (Number of Queues)
  • NVMe over PCIe Transport Specification, Revision 1.4 — reset mapping and NVM Subsystem Reset on PCIe
  • PCI Express Base Specification, Revision 6.x/7.0 — Reset Rules; Function Level Reset; LTSSM Hot Reset and Disabled states (PCI-SIG members' document); form-factor specifications for PERST# timing.

Normative CC.EN 1→0 is a controller reset; EN must not be set again until RDY = 0; CAP.TO (bits 31:24, 500 ms units) bounds RDY transitions; outstanding commands are not completed; AQA/ASQ/ACQ survive; NSSR at offset 20h with 4E564D65h when CAP.NSSRS (bit 36) = 1; NSSRO is CSTS bit 4. PCIe: FLR via Device Control, advertised in Device Capabilities; Hot Reset via SBR.

Informative Initialization flow figures and FLR implementation notes. Optional NSSR, FLR, PCIe Readiness Notifications, NVMe 2.x controller ready modes and NVM Subsystem Shutdown — discover each before use.

Actual RDY times; whether FLR restarts firmware or only the host interface; whether NSSR drops the link; how long CRS lasts; whether Abort succeeds; whether a Root Port answers MMIO to a dead link with UR immediately or after a Completion Timeout (platform-dependent).

The Controller Ready Timeouts register (CRTO) and ready modes are NVMe 2.0-era; 1.4 hosts know only CAP.TO. CRS became RRS in the PCIe 6.0 era. Linux's reset_method attribute appeared around kernel 5.15. Confirm CRTO and CC.CRIME positions in Base 2.4 before decoding them.

No specification defines the escalation order, per-tier timeouts beyond declared bounds, reset budgets, whether to retry or fail a given command, or how hosts sharing a subsystem coordinate NSSR. NVMe does not say whether an in-flight Write reached media (atomicity parameters bound torn writes; see WRITE).

Never assume a tier worked because its trigger was accepted: a posted CC write has no completion, and an FLR write's completion means only "accepted". Never assume a bigger reset clears a host-side fault — it returns.

Labs

Beginner lab — read reset state from register snapshots

Safe lab Paper only. Objective: decode CSTS/CAP into reset state and choose the next action. Prerequisites: NVMe Registers, Chapter 48. Setup: CAP = 0x0040_0830_1401_0FFF and CSTS readings: (a) 0x0000_0001 one second after EN = 0; (b) 0x0000_0001 eleven seconds after; (c) 0x0000_0003; (d) 0xFFFF_FFFF; (e) 0x0000_0010 at first probe after boot; (f) 0x0000_0009 while a driver submits I/O.

Procedure: decode CAP.TO and NSSRS; decode each CSTS into RDY, CFS, SHST, NSSRO; write the next action. Observations: mark which readings are NVMe state at all. Questions: which reading justifies FLR? Which says nothing about the controller? What should the host do with (e) and (f)? Expected reasoning: compare elapsed time with CAP.TO, and separate all-ones from NVMe state.

Solution

CAP.TO = 0x14 = 20 → 10 s; high DWORD 0x0040_0830 bit 4 (CAP bit 36) = 1 → NSSR supported. (a) Still within 10 s: keep polling. (b) RDY = 1 after 11 s: the controller broke its bound — escalate to FLR. (c) RDY = 1, CFS = 1: fatal; capture telemetry in a lab, then reset. (d) All-ones: no NVMe meaning; check link and AER. (e) NSSRO = 1: an NSSR happened before this probe; record, clear by writing 1 to bit 4, find who issued it. (f) RDY = 1, SHST = 10b: a shutdown completed and the controller need not process commands; reset and reinitialize before I/O.

Extension: compute your own drive's worst-case escalation time from its CAP.TO and your kernel's io_timeout.

Intermediate lab — watch the reset state machine in a VM

Caution lab QEMU virtual machine with an emulated NVMe device on a scratch image. Objective: observe Linux state transitions for a controller reset and a PCI function reset, measure them, and confirm what each destroys. Prerequisites: beginner lab; Lab Environment. Setup: guest with nvme-cli and pciutils; optional QEMU NVMe trace events (names begin with pci_nvme_ in recent versions — check yours).

Procedure:

  1. Record state, show-regs, lspci -vvv, reset_method.
  2. Start a sampler: while :; do printf '%s %s\n' "$(date +%s.%N)" "$(cat /sys/class/nvme/nvme0/state)"; done | uniq -f1 > states.txt
  3. Run sudo nvme reset /dev/nvme0; stop the sampler.
  4. Repeat with echo 1 | sudo tee /sys/bus/pci/devices/<BDF>/reset.
  5. After each, compare lspci -vvv with the baseline and read nvme get-feature /dev/nvme0 -f 7.

Observations: state strings and durations. Questions: why does the function reset take longer? Did Number of Queues change, and why did the driver set it again anyway? What appears in the QEMU trace only for the function reset? Expected reasoning: the PCI core wraps the function reset in save, readiness wait and restore, then the NVMe bring-up runs as for nvme reset.

Solution

Both show live → resetting → connecting → live; the function reset is longer because the PCI core waits at least the mandatory post-reset delay (commonly 100 ms) and restores configuration first. Number of Queues reads back unchanged because the driver requested the same count, but the controller forgot it at reset and the driver set it again. Only the function reset shows configuration accesses (Device Control or a bus-level reset, depending on what the emulated device advertises); the controller reset shows only MMIO to CC and CSTS. Durations and event names are version-dependent.

Extension: run fio random reads during step 3 and confirm they pause but do not fail — the requeue path.

Advanced lab — design and tune an escalation policy

Safe lab Simulation. Objective: see how tier order, timeouts and a budget determine time-to-recovery and expose storms. Prerequisites: Mechanism section; Python 3.8+. Setup: save as reset_ladder_sim.py.

#!/usr/bin/env python3
"""reset_ladder_sim.py - teaching simulation of a host reset-escalation policy.

Each fault scenario says which recovery tier (if any) clears it and what each
tier costs in time. The policy walks the tiers in order, respects a reset
budget, and reports how long recovery took. All numbers are synthetic.
"""

TIERS = ["abort", "ctrl_reset", "flr", "sbr", "slot_power"]

# Time each tier costs when it "runs to completion" (ms), synthetic.
COST_MS = {
    "abort": 30_000,        # wait for one more io_timeout after sending Abort
    "ctrl_reset": 450,      # EN=0 -> RDY=0 (~40 ms) + EN=1 -> RDY=1 (~410 ms)
    "flr": 100 + 80 + 450,  # mandatory wait + CRS period + NVMe enable
    "sbr": 2 + 22 + 100 + 190 + 450,  # hold, train, wait, CRS, NVMe enable
    "slot_power": 1_500 + 450,
}
# Time a tier burns when it FAILS (ms): usually its timeout bound.
FAIL_MS = {
    "abort": 30_000,
    "ctrl_reset": 10_000,   # CAP.TO = 20 -> 10 s waiting for RDY=0
    "flr": 1_000 + 10_000,  # bounded CRS period, then CAP.TO on enable
    "sbr": 1_000 + 10_000,
    "slot_power": 1_000 + 10_000,
}

SCENARIOS = {
    # name: (lowest tier that clears the fault, does every reset re-trigger it?)
    "transient firmware hang": ("ctrl_reset", False),
    "controller ignores CC.EN": ("flr", False),
    "function wedged, FLR broken": ("sbr", False),
    "PHY/link dead": ("slot_power", False),
    "bad command re-sent after reset": ("ctrl_reset", True),
    "device truly dead": (None, False),
}


def run(scenario, budget=3, skip_abort=False):
    clears_at, retrigger = SCENARIOS[scenario]
    t, resets_used, log = 0, 0, []
    tiers = TIERS[1:] if skip_abort else TIERS
    i = 0
    while i < len(tiers):
        tier = tiers[i]
        if tier != "abort":
            if resets_used >= budget:
                log.append(f"{t/1000:8.1f} s  budget exhausted -> mark controller dead")
                return t, log
            resets_used += 1
        ok = clears_at is not None and TIERS.index(tier) >= TIERS.index(clears_at)
        if ok:
            t += COST_MS[tier]
            log.append(f"{t/1000:8.1f} s  {tier:<10} recovered")
            if retrigger:
                # the requeued command hangs again: one more io_timeout, start over
                t += 30_000
                log.append(f"{t/1000:8.1f} s  requeued command hung again (storm)")
                i = 0
                continue
            return t, log
        t += FAIL_MS[tier]
        log.append(f"{t/1000:8.1f} s  {tier:<10} did not help")
        i += 1
    log.append(f"{t/1000:8.1f} s  all tiers failed -> remove device, alert")
    return t, log


if __name__ == "__main__":
    for name in SCENARIOS:
        total, log = run(name)
        print(f"== {name}  (total {total/1000:.1f} s)")
        for line in log:
            print("   " + line)

Procedure: run unchanged; rerun "PHY/link dead" with budget=4; run "transient firmware hang" with skip_abort=True; add poison-command handling that fails, rather than requeues, a command that hung twice. Observations: recovering tier and time wasted in tiers that cannot help. Questions: why does link-dead never reach slot_power with budget 3? Where would you cut the 62 s of the dead case? What does the storm teach? What should multipath do in the first 30 s?

Expected reasoning: most time is spent in timeouts of tiers that cannot help; triage evidence lets the host skip them safely.

Solution

Totals: 30.4, 40.6, 51.8, 62.0 (dead, budget exhausted), 211.3 (storm, budget exhausted), 62.0 s. Budget 3 allows three resets, so slot_power is never tried — a policy choice; count resets per incident separately from per hour if the budget is meant only to stop storms. With budget 4 link-dead recovers at 64.0 s. skip_abort gives 0.45 s instead of 30.4 s, but Abort is the only tier that does not disturb the other outstanding commands, so skip it only when triage says it cannot help. An all-ones CSTS means NVMe tiers cannot help: jumping to a link-level tier saves 40 s in the dead cases. The storm shows every tier "working" while the fault returns: the trigger is what the host re-sends. Multipath should fail I/O over at the first timeout while the ladder restores the path in the background.

Extension: add an evidence-capture step before FLR that costs time, and decide when policy should pay for it.

Senior forensic lab — the disappearing paths

Safe lab Evidence analysis. Objective: reconstruct an incident in which one host's maintenance action took down another host's storage, and write a root-cause statement with confidence. Prerequisites: Error Correlation; Root Cause, Ambiguity and Forensic Reporting.

Setup — synthetic evidence:

  • A dual-ported SSD (one subsystem, controller IDs 1 and 2) shared by Host A (port 0) and Host B (port 1).
  • Host A, 02:12:40: I/O timeout, Abort, then nvme reset hangs 10 s (RDY stuck at 1).
  • Host A audit log, 02:13:06: an operator runs a vendor "recover drive" script containing nvme subsystem-reset /dev/nvme0, executed after another failed nvme reset.
  • 02:13:07: Host A logs a hot-plug link-down on its port; Host B logs an all-ones CSTS read and a reset of nvme1; Host B applications see I/O errors for 1.6 s.
  • After recovery CSTS = 0x0000_0010 on both controllers; SMART Power Cycles and Unsafe Shutdowns unchanged on both.

Procedure: build one timeline across hosts; find the first abnormal event; separate the original fault from collateral damage; propose corrective actions. Observations: label each fact direct or inferred. Questions: what is the incident's first abnormal event, and Host B's? Why do the power counters matter? What should the script have done? What still needs the vendor? Expected reasoning: NSSRO on both controllers plus unchanged power counters point to NSSR, and the audit log names the actor.

Solution

The incident starts at 02:12:40 with Host A's timeout and a controller that ignored CC.EN for 10 s. Host B's outage starts with the NSSR issued from Host A at ~02:13:06–07 (inferred from audit log plus NSSRO; the write itself was not captured). Unchanged power counters exclude power loss — confidence high. The script should have escalated within Host A's domain (FLR of its own function, then a bus reset of its own Root Port) and refused NSSR when nvme list-subsys shows other controllers. Still open: why controller 1 ignored CC.EN — no telemetry was captured before the resets, so reproduction is needed. Statement: "Host B's outage was caused by an NSSR issued by a recovery script on Host A (high confidence); the trigger was a controller on Host A that did not complete a controller reset within CAP.TO (cause unknown; vendor analysis required)."

Extension: write a fleet rule requiring a cluster lock for NSSR and disabling it in tooling for multi-controller subsystems.

Debugging

Pattern 1 — RDY never falls after CC.EN = 0
SymptomReset hangs for CAP.TO, then escalation or removal.
Possible causesFirmware stuck in a media operation or deadlocked; CC write went to a stale BAR; thermal or power event.
EvidenceValid CSTS reads of 0x0000_0001 for the full CAP.TO; device traffic stops after the CC write.
First checkRead back CC: EN = 0?
Second checkSMART temperature and Critical Warning; telemetry controller-initiated generation number.
Disambiguating experimentFLR (after capturing telemetry): recovery means the controller-reset path is defective but function reset works.
Likely conclusion / confidenceFirmware does not honour controller reset under that load — high when CC reads back EN = 0.
Pattern 2 — reset completes, first admin command times out
SymptomRDY = 1 observed; Identify never completes.
Possible causesBus Master Enable not restored; IOMMU mapping missing for the admin queue; MSI-X disabled or masked.
EvidenceAnalyzer: SQE fetch after the doorbell? CQE write? MSI-X write?
First checklspci -vvv: BusMaster+, MSI-X Enable+; IOMMU fault log.
Second checkIs a CQE sitting in admin CQ memory with the expected phase?
Disambiguating experimentNo fetch → Bus Master/IOMMU; fetch and CQE but no interrupt → MSI-X path.
Likely conclusion / confidenceHost restore bug — high with an analyzer, medium from logs.
Pattern 3 — reset storm
SymptomTimeout → reset cycles; the device never stays live.
Possible causesA requeued poison command; a feature re-applied at each bring-up that firmware mishandles; a marginal link under load.
EvidenceSame opcode, LBA range or feature just before each hang; rising AER correctable counts (link case).
First checkCorrelate the first commands after each bring-up with the next timeout.
Second checkDisable APST, HMB and interrupt coalescing; does the storm stop?
Disambiguating experimentFail the suspect command once instead of requeuing it.
Likely conclusion / confidenceFirmware bug triggered by one command, sustained by host requeue — medium until reproduced in isolation.
Pattern 4 — device unusable after FLR
SymptomAfter a VM hand-off or sysfs reset, MMIO returns all-ones or enable fails.
Possible causesBAR access before configuration restore; giving up during legal CRS; non-compliant FLR that skips the NVMe back end or drops the link.
EvidenceUR completions to MMIO; CRS still arriving when the host stopped; link changes during FLR.
First checkOrder of configuration restore and first MMIO.
Second checkLink state during FLR (lspci LnkSta, analyzer).
Disambiguating experimentUse the kernel's reset path; if it works the tool is wrong; if not, a bus reset that works points at the device's FLR.
Likely conclusion / confidenceUsually host sequencing; sometimes a device needing a kernel quirk — high once the order is known.
Pattern 5 — another host loses its paths
SymptomHost B reports a reset or link loss it did not start.
Possible causesNSSR from another host or management software; reset of a shared switch port; drive power event.
EvidenceNSSRO = 1 on every controller; power counters; audit logs.
First checkNSSRO on all controllers of the subsystem.
Second checkPower Cycles and Unsafe Shutdowns deltas.
Disambiguating experimentIf NSSRO is clear, check switch and BMC logs for resets and power actions.
Likely conclusion / confidenceAn operational action, not a device fault — high with NSSRO plus audit logs.

Interview

Beginner

  1. What does writing CC.EN = 0 do?

    Model answer

    Starts a controller reset: queues deleted, outstanding commands dropped without completions, RDY falls when done. Link and configuration space untouched.

  2. How long may RDY take to change?

    Model answer

    Up to CAP.TO × 500 ms per transition (plus CRTO for the selected ready mode on 2.x). 10 s for the Lab SSD.

  3. Name a reset that keeps the link up and one that drops it.

    Model answer

    Controller reset and FLR keep it; Hot Reset, Link Disable, Fundamental Reset (and on many devices NSSR) drop it.

  4. Why no completions for outstanding commands?

    Model answer

    The completion queues are deleted by the reset; the host must complete those commands itself.

  5. What does CSTS = 0xFFFF_FFFF mean?

    Model answer

    No NVMe meaning: the read got no successful completion. Look at the PCIe layer.

Intermediate

  1. List the bring-up after a controller reset.

    Model answer

    Wait RDY = 0; reset host queue state, zero admin CQ; AQA/ASQ/ACQ; EN = 1; wait RDY = 1; Identify; Number of Queues once; other features; I/O CQs then SQs; AERs; namespace rescan; release requeued I/O.

  2. How does FLR change recovery compared with CC.EN?

    Model answer

    Before: clear Bus Master Enable, drain Transactions Pending, save configuration. After: readiness wait tolerating CRS, restore BARs, Command, MSI-X, Device Control — then the NVMe bring-up.

  3. Why is Abort best-effort?

    Model answer

    The controller may decline, and the Abort is unordered with its target, which may complete first.

  4. Why keep memory mapped until RDY = 0?

    Model answer

    The controller may still DMA while stopping; early unmapping causes IOMMU faults or corruption.

  5. What is NSSRO for?

    Model answer

    Evidence that an NSSR occurred; record it and clear it by writing 1.

Advanced

  1. How do you prove no DMA after RDY = 0?

    Model answer

    Trigger on any TLP from Requester ID 0x0100 after the RDY = 0 completion and before the next EN = 1; unmap all buffers at RDY = 0 and watch for IOMMU faults; vary load, size, temperature, fill.

  2. A firmware commit "activate at next reset" was issued. What changes in recovery?

    Model answer

    Re-read Identify, the Firmware Slot log and every cached capability after the next qualifying reset; some activation types need a conventional reset or NSSR rather than CC.EN.

  3. Why can Hot Reset fail to recover a dead link?

    Model answer

    It is signalled in TS1 ordered sets over that link; only sideband PERST# or slot power can reach the device.

  4. How do you stop a reset storm?

    Model answer

    Per-device budget, back-off, and failing (not requeuing) a command that repeatedly precedes the hang.

  5. Which interrupted commands are unsafe to retry blindly?

    Model answer

    Namespace Management, Format NVM, Sanitize, firmware download/commit, and non-idempotent I/O such as Zone Append.

Senior

  1. Design reset policy for a dual-ported drive in a cluster.

    Model answer

    Each host uses only tiers inside its own domain (Abort, controller reset, its own FLR, its own port reset). Subsystem-wide actions need cluster coordination after failover. Multipath fails over before slow tiers; metrics record the recovering tier.

  2. How do you choose per-tier timeouts?

    Model answer

    Declared bounds (CAP.TO, CRTO, readiness reporting) plus the PCIe readiness rules plus margin, never less than the declared worst case, with triage to skip impossible tiers.

  3. VMs see stale behaviour after FLR hand-off with HMB enabled. What do you ask?

    Model answer

    Whether FLR resets HMB use and derived caches; whether the hypervisor recycled the old HMB memory only after reset completion; whether the new owner re-enabled HMB with fresh memory; then test for DMA to old HMB addresses after FLR.

  4. When would you deliberately not reset a misbehaving drive?

    Model answer

    When volatile state is the evidence (validation, failure analysis), during a persistent admin operation with unclear semantics, or when other hosts would be affected: fail over, capture, then reset.

  5. Which fleet metric reveals a reset regression?

    Model answer

    Recovering tier and RDY transition times per firmware revision: a shift from controller reset to FLR, or RDY times approaching CAP.TO.

Quiz

  1. Which reset requires restoring BARs and the Command register before touching NVMe registers?

    • Controller reset (CC.EN)
    • Function Level Reset
    • Delete I/O SQ
    • Abort
    Answer and reasoning

    FLR resets the function's configuration space; CC.EN does not.

  2. A tool reads CSTS = 0xFFFF_FFFF and reports "CFS = 1". Correct?

    • Yes, bit 1 is set
    • Only if RDY is 1
    • No — all-ones means the read did not complete successfully
    • No — CFS is bit 4
    Answer and reasoning

    All-ones is the PCIe "no data" pattern.

  3. In Trace 1, why do requeued commands use SQ slots 0–35?

    • SQ1 was re-created empty
    • The controller remembered old slots
    • Hosts must start at slot 0
    • CIDs restart at 0
    Answer and reasoning

    The reset deleted SQ1; the new queue starts with head = tail = 0.

  4. Which evidence best distinguishes NSSR from power loss?

    • The link went down
    • RDY = 0
    • A kernel reset message
    • NSSRO = 1 with Power Cycles unchanged
    Answer and reasoning

    The others occur in both cases.

  5. Trace 2's 7.6 s enable with CAP.TO = 20 is…

    • A violation
    • Compliant with thin margin
    • A host bug
    • Unremarkable
    Answer and reasoning

    Inside 10 s, but 76% of the bound deserves characterization.

  6. Which is true of Abort?

    • The target never completes
    • It resets the queue
    • The target may complete before or after the Abort
    • It is a PCIe message
    Answer and reasoning

    Abort is a best-effort, unordered admin command.

  7. Why is Trace 3's first abnormal event invisible on the link?

    Model answer

    It is a host-internal IOMMU unmap; only its consequences (UR completion, dropped CQE) reach the wire. IOMMU fault logs show the cause.

  8. Give two ways a reset can be accepted yet ineffective.

    Model answer

    A posted CC write that firmware ignores; an FLR that does not reset the back end; Hot Reset over a dead link; any reset against a host-side poison command.

Teach-back

  1. To a child: why does the theatre manager photograph the tangle and try the small fix first?

    Model explanation

    "Big fixes make everything fresh, so nobody can see what went wrong afterwards — the photo helps stop it happening again. Small fixes stop less of the show and don't bother other stages, and we only wait as long as the puppeteer promised."

  2. To a junior engineer: explain the escalation ladder and what to rebuild after each tier.

    Model explanation

    "Read CSTS first; all-ones means skip NVMe tiers. Abort; then EN = 0 and wait up to CAP.TO, keep memory mapped, complete outstanding commands yourself, rebuild admin queue, features, I/O queues and AERs. If RDY never falls, FLR: save config, drain, reset, wait and tolerate CRS, restore config, same NVMe rebuild. Then bus or slot reset; then fail cleanly. Re-read Identify every time."

  3. To a senior engineer: argue reset policy for shared and virtualized topologies.

    Model explanation

    "Reset scope must match ownership. Per-controller state can be reset by its owner; per-subsystem state (namespaces, media, NSSR, power) cannot be reset unilaterally, so each host's ladder stops at its own function or port and subsystem tiers need coordination after failover. VF FLR is the hand-off primitive and must be validated to reset the back end and HMB use. Timeouts come from declared bounds, budgets stop storms, evidence capture precedes destructive tiers, and the recovering tier is tracked per firmware."
