This module takes the reset family from Chapter 48 — NVMe Reset and Chapter 49 — PCIe Reset and turns it into an engineering discipline: how a host chooses which reset to use, how it escalates when one fails, what each reset does to evidence, how resets collide with long-running admin operations and with other hosts, and how to prove from a trace which reset actually happened.

Orientation

The two chapters taught each reset on its own: the Controller Configuration enable bit (CC.EN) handshake with Controller Status Ready (CSTS.RDY), the NVM Subsystem Reset (NSSR) magic value, shutdown notification, Function Level Reset (FLR), Hot Reset through Secondary Bus Reset (SBR), Fundamental Reset through PERST#, and the readiness rules after each. This module assumes all of that and asks the questions a senior engineer gets asked: which reset should recovery code try first, how long may each tier take before the next one starts, what does each tier destroy that you might need for root cause, and how do you tell from a capture whether the device was reset from above (registers), from beside (configuration space) or from below (the link)?

Read Chapter 48 — NVMe Reset for CC.EN/CSTS.RDY, the Capabilities Timeout field (CAP.TO), the "destroys / survives" table, NSSR and shutdown; and Chapter 49 — PCIe Reset for the Conventional/Fundamental/Hot Reset taxonomy, FLR, Configuration Request Retry Status (CRS, renamed Request Retry Status, RRS, in newer revisions) and the readiness waits. Error vocabulary comes from Chapter 44 — NVMe Errors, Chapter 46 — AER and Chapter 55 — Advanced Error Handling (Downstream Port Containment).

Where it goes next: Module 42 — Power Management reuses the same readiness reasoning for resume from D3cold; Module 43 — SMART and Health shows the logs you should capture before a reset destroys volatile evidence; Module 52 — SR-IOV extends FLR to Virtual Functions.

Kid story

A puppet theatre has one puppeteer behind the curtain. Sometimes a puppet's strings get tangled in the middle of the show.

The smallest fix is to untangle one puppet: the other puppets keep dancing. A bigger fix is to tell the puppeteer, "Put all the puppets down, hands in the air, wait until I see your hands empty." Bigger still is to close the curtain on the whole stage, which also means the lights and the music for that stage reset. And biggest of all is to switch off the power to the theatre and switch it back on.

The rule the theatre manager follows: always try the smallest fix that can work, wait the right amount of time for it, and only then try the next one. And before any big fix, take a photo of the tangle, because after the fix nobody can see how it got tangled.

Analogy boundary

What the analogy represents. Untangling one puppet is deleting and re-creating one I/O queue pair. "Hands in the air" is a controller reset through CC.EN, and "wait until I see your hands empty" is polling CSTS.RDY until it reads 0. Closing the curtain on one stage is an FLR (the function's configuration space resets, other functions continue). Resetting the whole stage's lights and music is a Hot Reset or link-down event. Switching off the theatre is a cold Fundamental Reset. The photo is capturing logs and telemetry before resetting.

What it hides. Puppets that were mid-dance do not report that they stopped: after a controller-level reset no completion is ever posted for in-flight commands, and the host alone must decide what happened to them. It also hides that some "puppets" are shared with another theatre: an NSSR resets controllers that another host may be using.

Where it misleads. In the theatre a bigger fix is always "stronger". In practice a bigger reset is not always a superset of a smaller one in what the host must do: a controller reset leaves configuration space alone, while an FLR forces the host to restore Base Address Registers (BARs), Bus Master Enable and MSI-X before it may even read CSTS. And a bigger reset can be less effective if it is the wrong layer: a Hot Reset cannot reach a device whose link is already dead, because Hot Reset is carried by the link itself.

Reset is not one mechanism; it is a set of nested reset domains, each owned by a different agent and each with its own trigger, wait rule and evidence. The architecture below is the map a recovery designer works from.

Mechanism

The central mechanism of this module is the reset escalation ladder: the ordered recovery procedure a host follows when a controller stops making progress. The steps below follow a Linux-like policy on the course's synthetic Lab SSD (Requester ID 0x0100 at 0000:01:00.0 below Root Port 00:01.1; BAR0 = 0xFE60_0000; CAP = 0x0040_0830_1401_0FFF so CAP.TO = 20 → 10 s and NSSRS = 1). The policy itself is host behaviour, not specification text.

  1. Detect. Who: the block layer's per-request timer. What changes: a request passes its timeout (nvme_core.io_timeout, historically 30 s). Where: host memory only. Evidence: a kernel log line naming the queue and command; on the analyzer, no completion queue entry (CQE) for that command identifier.
  2. Triage without touching state. Who: the timeout handler. What changes: nothing in the device; the host reads CSTS (an MRd32 to 0xFE60_001C) and polls the completion queue. Where: BAR0 and CQ memory. Evidence: CSTS value: CFS = 1 → go straight to reset; 0xFFFF_FFFF → the PCIe layer is broken, skip NVMe tiers; a CQE found by polling → interrupt problem, not a hang.
  3. Abort. Who: the driver. What changes: an Abort admin command (opcode 08h) naming the SQ identifier and command identifier is submitted. Where: the admin SQ. Evidence: the Abort's own CQE; Dword 0 bit 0 says whether the command was not aborted. The specification lets the controller decline; Abort is best-effort.
  4. Controller reset. Who: the driver. What changes: CC.EN 1→0 (MWr32 0x0046_0060 to 0xFE60_0014), then CSTS.RDY falls. Where: controller registers and every queue table. Evidence: CSTS polls changing bit 0; silence of device-initiated SQE fetches after the CC write lands.
  5. Account for outstanding commands. Who: the driver. What changes: every tracked command is completed by the host with a requeue or an error. Where: host data structures. Evidence: requeue counters, application-visible latency, no CQEs on the wire for those identifiers.
  6. Rebuild. Who: driver. What changes: admin CQ zeroed, AQA/ASQ/ACQ written, CC.EN = 1 (0x0046_0061), Identify Controller, Set Features Number of Queues, other features, Create I/O CQ/SQ, Asynchronous Event Requests, namespace rescan. Where: registers then admin queue. Evidence: the bring-up admin command sequence in the trace.
  7. Escalate to FLR if RDY never falls within CAP.TO or enable fails. Who: PCI core. What changes: configuration state saved, Bus Master Enable cleared, Transactions Pending waited out, Initiate FLR written, readiness waited for, configuration restored. Where: the function's configuration space and everything behind it. Evidence: CfgWr0 to Device Control; quiet link in L0; CfgRd0 polls (possibly CRS/RRS); CfgWr0 restoring BAR0 and Command.
  8. Escalate to a bus or slot reset if FLR is unsupported or ineffective. Who: PCI core or platform. What changes: SBR on the Root Port 00:01.1 (or slot power), the link retrains from Detect. Where: the link and every function below the bridge. Evidence: TS1 ordered sets with Hot Reset, electrical idle, training, InitFC Data Link Layer Packets, then configuration requests.
  9. Give up safely. Who: driver. What changes: controller marked dead, namespaces removed, I/O failed (multipath fails over first). Where: host. Evidence: sysfs state "dead", block devices disappear, an alert.

The ladder for reset escalation

When a puppet tangles, try untangling it; if the puppeteer will not put her hands up, close the curtain; if the curtain is stuck, switch off the stage; take a photo first.

A host recovers a stuck NVMe device by trying, in order, Abort, controller reset, function reset, bus or slot reset, and finally removal — waiting a bounded time at each step and rebuilding everything the step destroyed.

Each tier reaches a deeper hardware domain: the controller's command engine (CC.EN), the function's register and configuration logic (FLR), the PCIe Physical and Data Link Layers (Hot Reset), the whole board including the firmware boot ROM (Fundamental Reset). Firmware that is wedged in a media operation may ignore CC.EN but cannot ignore PERST#.

The NVMe Base Specification defines controller-level resets, their effects and CAP.TO; the NVMe over PCIe Transport Specification maps PCIe resets onto them; the PCI Express Base Specification defines Conventional Reset, FLR and the readiness rules. No specification defines the escalation order or the budgets — those are host policy.

On the wire each tier has a distinct signature: an Abort SQE; an MWr to BAR0+14h; a configuration write to Device Control; TS1 ordered sets with the Hot Reset bit; electrical idle with no preceding ordered sets (power or PERST#).

An analyzer shows the first tier that changed device behaviour. The first abnormal event is usually not the reset itself but the poll after it: RDY still 1 at CAP.TO, or an Unsupported Request completion because configuration was not restored.

A senior engineer asks which tier finally recovered the device: recovery by FLR but not by CC.EN points at firmware that does not honour controller reset; recovery only by slot power points at the PHY, power or boot firmware. Fleet metrics of "recovering tier" expose firmware regressions.

The sixteen questions, applied to the reset escalation policy

1. What is it?
A host-defined, ordered sequence of recovery actions of increasing scope, each with a bounded wait and a rebuild step.
2. Why was it created?
Because no single reset works in every failure: the cheapest reset that works preserves the most state and availability, and the most powerful reset must exist for when nothing else works.
3. What problem does it solve?
Turning "the disk hung" into either recovery within a predictable time or a clean failure that multipath and applications can handle.
4. What existed before it?
SCSI error handling's escalation (abort → device reset → target reset → bus reset → host reset) and ATA's soft reset then hard reset. NVMe stacks inherited the idea.
5. Why is the current design better?
Every tier is a standardized, discoverable mechanism (CAP.NSSRS, Device Capabilities FLR bit, bridge SBR) with published timeouts, so the policy can be computed rather than guessed.
6. Who creates it?
Driver and operating-system authors; in virtualization, the hypervisor; in appliances, the storage stack's health monitor.
7. Who consumes it?
The device (each reset), the block layer and file systems (requeued or failed I/O), multipath (failover), operators (alerts).
8. Where does it live?
In host software: the NVMe driver's timeout handler and reset work, the PCI core's reset functions, AER/DPC recovery callbacks.
9. What memory/registers are involved?
CSTS, CC, NSSR, CAP; Device Control and Status; Bridge Control; Link Control/Status; host tracking structures for outstanding commands and saved configuration.
10. What happens before it?
A timeout, a fatal status, an AER/DPC event, or an operator request; ideally, evidence capture.
11. What happens after it?
Rebuild of everything the successful tier destroyed, requeue of outstanding I/O, and a record of which tier worked.
12. What happens if it is wrong?
Hangs with no timeout; resets that destroy evidence for no gain; reset storms; collateral resets of other devices or other hosts; data corruption from DMA into freed memory.
13. What does the protocol analyzer show?
The tier signatures listed in rung E, in order, with the gaps between them equal to the policy's timeouts.
14. What does Linux show?
Kernel log lines for timeout, abort, reset and removal; controller state transitions in /sys/class/nvme/nvme0/state; PCI core messages for reset and readiness waits.
15. What would a validation engineer test?
That each tier works alone (inject faults that only that tier can clear), that bounds are honoured, that no DMA occurs after RDY = 0 or during FLR, and that a reset during each admin command leaves persistent state consistent.
16. What would a senior engineer suspect when it fails?
A tier that "succeeds" without really resetting (firmware back end not reset by FLR), a host that skipped a rebuild step, a policy whose timeouts are shorter than the device's declared worst case, and a poison command that re-triggers the fault.

For every admin command whose effect is persistent, the test matrix needs a cell "reset at random points during execution". The controller must leave the persistent state either fully old or fully new, or report clearly (via a log page or a namespace state) that the operation must be repeated. Torn namespace metadata after a reset during Namespace Management is the kind of bug that escapes into the field because nobody tested it.

Host Memory Buffer and other host memory the controller owns

If the host enabled a Host Memory Buffer (HMB, Set Features 0Dh), the controller may read and write that host memory at any time while enabled. A controller-level reset ends the controller's permission to use it, but the host can only rely on that once the controller has stopped (CSTS.RDY = 0, or the link is down). The host must keep the HMB allocated and mapped until then and re-enable it with Set Features after the rebuild Derived. The same reasoning applies to queue memory and to any buffers named by outstanding commands.

Specification discipline

Applicable documents and revisions in the 2026 baseline:

  • NVM Express Base Specification, Revision 2.4 — Controller Registers; Resets; Controller Initialization; Controller Shutdown; Abort command; Set Features (Number of Queues)
  • NVMe over PCIe Transport Specification, Revision 1.4 — PCIe-specific reset mapping and NVM Subsystem Reset behaviour
  • PCI Express Base Specification, Revision 6.x/7.0 — Reset Rules; Function Level Reset; Link Training and Status State Machine (Hot Reset and Disabled states); Readiness Notifications (a PCI-SIG members' document)
  • Form-factor specifications (for example the PCI Express Card Electromechanical Specification, M.2, SFF-TA documents) for PERST# and power-sequencing timing.

Normative CC.EN 1→0 is a controller reset; the host waits for CSTS.RDY = 0 before setting EN again; CAP.TO (CAP bits 31:24, 500 ms units) bounds RDY transitions; outstanding commands are not completed by a controller-level reset; AQA/ASQ/ACQ survive CC.EN 1→0; NSSR at offset 20h with value 4E564D65h when CAP.NSSRS (bit 36) is set; CSTS.NSSRO (bit 4) records it. PCIe: FLR through Device Control, capability in Device Capabilities; Hot Reset through SBR.

Initialization and shutdown flow diagrams and examples in the NVMe Base Specification are informative: they show one valid way, not the only one. The PCIe specification's implementation notes about FLR (for example on avoiding outstanding requests) are informative guidance around normative rules.

Optional NSSR (CAP.NSSRS), FLR (Device Capabilities), PCIe Readiness Notifications and Readiness Time Reporting, controller ready modes (NVMe 2.x), NVM Subsystem Shutdown (NVMe 2.x). A host must discover each before using it.

How long RDY actually takes, whether FLR restarts controller firmware or only the host interface, whether NSSR drops the PCIe link, whether internal debug state survives any reset, how long the device returns CRS/RRS, and whether a device honours Abort. Platform-dependent: whether the Root Port answers MMIO to a down link with Unsupported Request immediately or after a Completion Timeout.

Controller ready modes and the Controller Ready Timeouts register (CRTO) arrived with NVMe 2.0; a 1.4-era host knows only CAP.TO. CRS was generalized to RRS in the PCIe 6.0 era. Readiness Notifications and Readiness Time Reporting were added in later PCIe 3.x/4.0-era revisions. Linux's reset_method sysfs attribute appeared around kernel 5.15. Confirm field positions of CRTO and CC.CRIME in Base 2.4 before decoding them; this course does not state them.

No specification defines: the escalation order, the per-tier timeouts beyond the device's declared worst cases, a reset budget, whether to retry or fail a given outstanding command, or how to coordinate NSSR among hosts sharing a subsystem. The NVMe specification does not say whether data written by an in-flight Write reached media before a reset (atomicity parameters bound torn writes; see WRITE).

Never assume that a reset tier "worked" because its trigger was accepted (a posted CC write has no completion; an FLR configuration write's completion means only "accepted"). Never assume a bigger reset clears a fault a smaller one did not if the fault is on the host side (a poison command, a wrong IOMMU mapping) — it will come back.

NAND program operations cannot be interrupted mid-pulse, and a multi-plane program on TLC or QLC can take milliseconds. Firmware usually lets in-progress media operations finish, discards the host-facing contexts, then clears queue tables and drops RDY. Under a heavy write load with a deep internal queue, tens of milliseconds are normal; seconds suggest a stuck back end. The 10 s CAP.TO of the Lab SSD is the contract, not the expectation.

NVMe does not order commands, and the Abort travels through the admin queue while the target sits in an I/O queue. A controller that completes the target 1 µs before processing the Abort is correct; the Abort then completes with "not aborted". Host code must handle the target's late completion and the Abort's completion in either order — the cause of many use-after-free bugs in home-grown drivers.
