This page assembles everything into one picture you can carry in your head: an application's read or write travelling down through the filesystem, block layer, Non-Volatile Memory Express (NVMe) driver, queues, doorbell, Memory-Mapped I/O (MMIO), PCI Express (PCIe) transaction, Transaction Layer Packet (TLP) and link, into the NVMe controller, out to the media through Direct Memory Access (DMA), and all the way back up through completion queue, MSI-X interrupt, driver, block layer and application. It starts with the distinction that makes the picture readable — NVMe, PCIe and NVMe over PCIe are three different things — and then explains every arrow of the stack: who acts, what crosses, what evidence exists, and where the course teaches it.

Why this page exists

Individual chapters teach individual pieces. Engineers who are senior in this field are distinguished less by knowing more pieces than by knowing how the pieces connect: where one layer's output becomes the next layer's input, which agent acts at each step, and which tool can see each step. When something fails, they can point at the arrow where the expected evidence stops.

This page is the reference you return to before a debugging session, an interview or a design review. It deliberately repeats nothing at length; every arrow links to the chapter that teaches it in depth.

Learning objectives

  • State precisely what NVMe defines, what PCIe defines, and what the NVMe over PCIe Transport specification defines, and classify any observation into one of them.
  • Draw the full stack from application to media and back, from memory.
  • For each of the nineteen arrows, name who acts, what crosses, what evidence exists, and which tool can see it.
  • Follow one 4 KiB read through a synthetic end-to-end timeline and attribute every microsecond to an arrow.
  • Localise a failure to the first arrow whose evidence is missing or abnormal, and explain how the error propagates upward.

NVMe, PCIe and NVMe over PCIe: three things, not one

Think of a busy restaurant. The order ticket has a fixed format: table number, dish, how it should be cooked. The kitchen answers with a "ready" slip. That ticket language is NVMe. The restaurant also has a pneumatic tube system that shoots capsules between the dining room and the kitchen; it carries tickets, but it also carries cash to the office and messages to the bar. That tube system is PCIe. Finally, there is a house rule card that says: "tickets go in the blue tube; ring bell 3 for table section 3; the kitchen fetches dishes' ingredients from the pantry shelf named on the ticket". That rule card is NVMe over PCIe.

In networking terms: NVMe is an application protocol (like HTTP semantics), PCIe is a packet network with its own link, routing and flow control (like Ethernet plus IP), and the NVMe over PCIe Transport specification is the binding (like the document that says how HTTP messages map onto TCP connections and ports). You can carry HTTP over different transports; you can carry many protocols over Ethernet; the binding is a separate, small agreement.

  • The tube does not just carry tickets. In NVMe over PCIe the device reaches into host memory itself (DMA): the "kitchen" fetches tickets from the dining room. No restaurant works that way, and it is the single most important asymmetry of the real system.
  • The binding is not small in practice. Registers, doorbells, PRP/SGL usage over PCIe and interrupts are all binding material; much of what engineers experience as "NVMe" on a server is actually the binding.
  • The HTTP analogy suggests strict layering. Real NVMe over PCIe relies on PCIe properties (posted write ordering, memory semantics) in ways HTTP never relies on Ethernet.

How to classify an observation

  • If it would still be true over NVMe/TCP, it is NVMe (for example "Read returned LBA Out of Range").
  • If it would still be true for a network card on the same slot, it is PCIe (for example "link trained to x2", "Completion Timeout").
  • If it only makes sense for NVMe on PCIe, it is the binding (for example "doorbell at BAR0 + 1008h", "PRP2 points to a PRP list", "CQ1 uses MSI-X vector 1").

Never collapse the three. "NVMe error" in a bug title should mean an NVMe status or controller state. A Completion Timeout on a device DMA read is a PCIe event that may cause an NVMe error (Data Transfer Error) — two layers, two events, one causal arrow between them.

The stack is drawn as a straight line, but two arrows hide a direction change. For a read, the controller reads media first (arrow 13) and then DMA-writes data into host memory (arrow 12 in reverse). For a write, the controller DMA-reads data from host memory first and then programs media. And arrows 7–11 also happen in the opposite direction: every device-initiated TLP (fetches, data, CQEs, MSI-X) goes back down the device's own transaction, data link and physical layers and up the root port's.

Every arrow, explained

Each subsection answers four questions: who acts, what crosses, what evidence exists, and where it is taught, followed by what typically goes wrong at that arrow. Examples use the course's synthetic Lab SSD (BAR0 = 0xFE60_0000, CAP.DSTRD = 0, I/O SQ1 at IOVA 0x1_2340_0000, CQ1 at 0x1_2341_0000, data buffer at 0x2_0000_0000, Gen4 x4, Max Payload Size 256 bytes).

Arrow 1 — Application → Filesystem

Who acts
An application thread, by making a system call: read(fd, buf, 4096), pread, or an io_uring submission. The CPU switches to kernel mode.
What crosses
A file descriptor, a file offset, a length and a user-space buffer address. Nothing NVMe-specific exists yet; the application does not know the file lives on NVMe.
Evidence
strace -T shows the call and its duration; syscall tracepoints (syscalls:sys_enter_read) timestamp it. No device-side evidence.
Taught in
How Computers Move Data, The Most Important Chapter.
What goes wrong
Misaligned buffers with O_DIRECT (EINVAL before any I/O), reads satisfied from the page cache (no I/O at all — a common reason "the trace shows nothing").

Arrow 2 — Filesystem → Block layer

Who acts
The filesystem (ext4, XFS…), possibly via the page cache. It maps file offset to logical block addresses on the block device and builds a bio.
What crosses
A bio: target block device (nvme0n1), starting sector (in 512-byte units in Linux, regardless of the namespace's LBA size), and a list of memory pages.
Evidence
blktrace "Q" (queued) events; block:block_bio_queue tracepoint.
Taught in
The Most Important Chapter.
What goes wrong
Metadata reads you did not expect (extent lookups), read-ahead turning one 4 KiB read into a 128 KiB read, writes deferred by the page cache so the I/O you are tracing happens seconds later from a kernel thread.

Arrow 3 — Block layer → NVMe driver

Who acts
The multi-queue block layer (blk-mq) converts bios into requests, may merge them, and dispatches them to a hardware queue context that the NVMe driver mapped to one NVMe I/O queue pair (typically one per CPU or group of CPUs).
What crosses
A struct request with operation, sector, length, scatterlist of pages and a tag; the call is the driver's queue_rq callback.
Evidence
blktrace "D" (issued to driver), block:block_rq_issue. Which NVMe queue it lands on depends on the CPU that submitted.
Taught in
I/O Queues.
What goes wrong
Queue depth exhaustion (requests wait for tags), requests split because they exceed MDTS or segment limits, I/O scheduler delays.

Arrow 4 — NVMe driver → NVMe command

Who acts
The NVMe driver. It allocates a Command Identifier (CID), translates the request into an NVM Command Set command (Read 02h, Write 01h, Flush 00h, Dataset Management 09h…), converts the sector to an LBA for the namespace's LBA size, and DMA-maps the data pages through the IOMMU to obtain I/O virtual addresses for PRP entries or SGL descriptors.
What crosses
The 64-byte SQE contents: CDW0 (opcode, CID, PSDT), NSID, PRP1/PRP2 (or SGL), CDW10–11 Starting LBA, CDW12 Number of Logical Blocks (0's based) and flags.
Evidence
The nvme:nvme_setup_cmd tracepoint prints queue, CID, NSID, opcode and command dwords. On the link, nothing yet.
Taught in
NVMe Command Structure, READ, Physical Region Pages, Scatter Gather Lists.
What goes wrong
PRP list construction errors (offsets, page boundaries), wrong LBA conversion for 4 KiB-LBA namespaces, IOMMU mapping failures, CID reuse while a command is outstanding.

Arrow 5 — NVMe command → Submission queue

Who acts
The driver, using ordinary CPU stores into host memory at SQ base + tail × 64. For the Lab SSD, slot 5 of SQ1 is 0x1_2340_0140.
What crosses
64 bytes into DRAM (through the CPU caches; on cache-coherent platforms the device will later read the current value).
Evidence
None on the PCIe link — this is CPU-to-memory traffic. The analyzer sees the SQE only later, inside the CplD that answers the device's fetch.
Taught in
Queue Architecture.
What goes wrong
Writing the doorbell before the SQE is visible (missing memory barrier), overwriting a slot the controller has not consumed (queue full miscalculation).

Arrow 6 — Submission queue → Doorbell

Who acts
The driver, which advances its tail index (wrapping at the queue size) and decides to ring — immediately or after batching several commands.
What crosses
One number: the new tail. The controller infers "slots old_tail … new_tail − 1 contain new commands".
Evidence
The doorbell write's data value on the analyzer; the nvme:nvme_sq tracepoint in recent kernels. Batching shows up as one doorbell for several commands.
Taught in
Doorbells.
What goes wrong
Tail value beyond queue size, tail wrap errors, forgetting to ring after batching (commands sit in memory forever), ringing the wrong queue's doorbell.

Arrow 7 — Doorbell → MMIO

Who acts
The CPU executes a 32-bit store (writel) to BAR0 + 1000h + (2y × (4 << CAP.DSTRD)). The address is in an uncached (or write-combining-forbidden) MMIO mapping, so it bypasses the cache and goes to the root complex.
What crosses
A store to physical address 0xFE60_1008 with data 0x0000_0006 (SQ1, tail 6).
Evidence
Only the resulting TLP. Software cannot observe the store itself except through instrumentation.
Taught in
BARs and MMIO, NVMe Registers.
What goes wrong
Wrong stride, BAR not mapped or memory space disabled (store goes nowhere), store reordered before the SQE write without a barrier.

Arrow 8 — MMIO → PCIe transaction

Who acts
The root complex. It recognises the address as belonging to the Root Port's downstream memory window and turns the store into a posted Memory Write request (no completion will come back).
What crosses
A transaction: Memory Write, address 0xFE60_1008, length 1 DW, byte enables, the root complex's Requester ID, attributes and traffic class.
Evidence
The MWr TLP on the analyzer. On the CPU, the store "completes" immediately — the reason doorbells are cheap.
Taught in
Posted vs Non-Posted Transactions, PCIe Ordering.
What goes wrong
Address outside any bridge window (Unsupported Request at the root port), posted write ordering assumptions broken by relaxed ordering settings.

Arrow 9 — PCIe transaction → TLP

Who acts
The Root Port's transaction layer builds the TLP header (Fmt/Type for a 32-bit Memory Write, length, Requester ID, tag, byte enables, address) and payload; the data link layer adds a sequence number and LCRC and keeps a copy in its replay buffer.
What crosses
A 3-DW header (32-bit address, since BAR0 is below 4 GiB) plus 1 DW of data, framed for the physical layer.
Evidence
Analyzer packet view: header fields, sequence number, LCRC status.
Taught in
TLPs, TLP Header Anatomy, DLLP.
What goes wrong
Malformed TLPs (rare from root complexes), byte-enable mistakes on sub-dword writes.

Arrow 10 — TLP → PCIe link

Who acts
The physical layers of the Root Port and the SSD (128b/130b encoding at Gen4, striping over 4 lanes), and the data link layers (the SSD returns an ACK DLLP; both sides exchange flow-control update DLLPs to return credits).
What crosses
Symbols on the lanes; ACK/NAK and UpdateFC DLLPs in the reverse direction.
Evidence
Analyzer link layer view (ACK latency, replays, NAKs), AER correctable errors (Bad TLP, Bad DLLP, Replay Timer Timeout), LTSSM state changes.
Taught in
PCIe Physical Architecture, PCIe LTSSM, DLLP, PCIe Flow Control.
What goes wrong
Signal integrity errors causing replays (latency jitter), credit starvation, link retraining or downtraining, link down (everything above stops).

Arrow 11 — PCIe link → NVMe controller

Who acts
The SSD's endpoint transaction layer decodes the address as a BAR0 hit at offset 1008h and hands it to the NVMe front end, which updates SQ1's tail register and schedules a fetch. This is where PCIe ends and NVMe begins on the device side.
What crosses
A register write: SQ1 tail = 6.
Evidence
Indirect: the device's next action (an MRd to the SQ) proves the doorbell was received and understood. If no fetch follows, the doorbell was lost, ignored, or the controller is not processing.
Taught in
NVMe Controller, NVMe Registers, Doorbells.
What goes wrong
Controller not ready (RDY = 0), controller fatal (CFS = 1), invalid doorbell value, queue not created.

Arrow 12 — NVMe controller → DMA

Who acts
The controller's DMA engines, as PCIe requester (Requester ID 0x0100). First an MRd for the SQE (64 bytes at 0x1_2340_0140); the root complex returns a CplD. If PRP2 points to a PRP list, another MRd for the list. Then, for a read, MWr TLPs carrying data into the buffer; for a write, MRd TLPs fetching data from it.
What crosses
Device-initiated TLPs addressed with IOVAs; the IOMMU translates them to physical addresses.
Evidence
Analyzer: device MRd/MWr with addresses matching queue bases and PRP entries; tag usage; completion latencies. Host: IOMMU fault messages if translation fails.
Taught in
DMA, Physical Region Pages, Command-to-TLP Correlation, PCIe Tags.
What goes wrong
Bus Master Enable clear, IOMMU faults (unmapped or freed buffers), completion timeouts, Max Read Request Size and Read Completion Boundary splitting misunderstood, data landing at wrong offsets because of PRP errors.

Arrow 13 — DMA → NAND / storage media

Who acts
Controller firmware and the Flash Translation Layer (FTL): look up logical-to-physical mapping, schedule NAND reads or programs across channels and dies, run error correction (LDPC), manage caches.
What crosses
Logical blocks of namespace 1 ↔ physical NAND pages. Nothing NVMe or PCIe crosses here; it is entirely internal.
Evidence
Only the time gap between the SQE fetch and the first data TLP (for reads) or between the last data TLP and the CQE (for writes, depending on caching). Indirectly: SMART / Health counters, vendor telemetry.
Taught in
What Is Storage?, READ, WRITE, FLUSH.
What goes wrong
Uncorrectable read errors, read retries (long latency tails), garbage collection stalls, thermal throttling.

Arrow 14 — NAND → Completion

Who acts
Firmware decides the command's outcome: success, or an NVMe status (for example Unrecovered Read Error in the media and data integrity class, LBA Out of Range, Data Transfer Error if DMA failed).
What crosses
A status code type and status code, command-specific DW0, the current SQ head, and the CID.
Evidence
The CQE contents (next arrow); later the Error Information log page for errors.
Taught in
NVMe Errors, Completion Rules.
What goes wrong
Completing a read before all data TLPs are sent (the CQE must not overtake its data — the posted-write ordering of PCIe is what normally guarantees this), wrong status class reported.

Arrow 15 — Completion → Completion queue

Who acts
The controller DMA-writes the 16-byte CQE into CQ1 at the controller's CQ tail (Lab SSD: slot 5 = 0x1_2341_0050), with the Phase Tag set to the current phase.
What crosses
One MWr TLP of 4 DW: DW0 result, DW1, DW2 = SQ head and SQ ID, DW3 = CID, Phase Tag, Status.
Evidence
Analyzer: MWr to the CQ region; decoding DW3 gives CID and status. This is the only place NVMe status is visible on the link.
Taught in
Queue Architecture, I/O Queues.
What goes wrong
Phase tag errors (host misses or double-processes entries), CQ overflow because the host did not advance the head doorbell.

Arrow 16 — Completion queue → MSI-X

Who acts
The controller, unless the vector is masked or interrupt coalescing delays it. It writes the MSI-X table entry's message data to its message address (x86: the 0xFEE0_0000 window) — on the wire, just another MWr.
What crosses
One MWr TLP of 1 DW, e.g. address 0xFEE0_1000, data 0x0000_0041 for vector 1 (CQ1).
Evidence
Analyzer MWr to the message address; per-vector counts in /proc/interrupts (nvme0q1).
Taught in
MSI-X, Interrupt Architecture.
What goes wrong
Masked vectors, wrong table programming after a reset, interrupt remapping faults, coalescing settings that add latency, polled queues that legitimately have no interrupts.

Arrow 17 — MSI-X → NVMe driver

Who acts
The CPU's interrupt controller delivers the vector to a core; the NVMe driver's handler reads CQ entries in host memory while their Phase Tag matches the expected phase, completes each by CID, then writes the CQ1 head doorbell (BAR0 + 100Ch) once for the batch.
What crosses
Interrupt delivery inside the CPU; then a CQ head doorbell MWr back down arrows 7–11.
Evidence
nvme:nvme_complete_rq tracepoint (CID, status); analyzer shows the CQ head doorbell MWr.
Taught in
Interrupt Architecture, Doorbells.
What goes wrong
Handler on the wrong CPU (latency), missing CQ head doorbell (controller eventually sees a full CQ and stops posting), spurious interrupts.

Arrow 18 — NVMe driver → Block layer

Who acts
The driver translates the NVMe status into a block-layer status (success, or errors such as I/O error, medium error, target error), unmaps DMA, frees the CID and completes the request. Errors are logged with the NVMe status name.
What crosses
Completion status and residual byte count.
Evidence
block:block_rq_complete with error field; kernel log lines naming the NVMe status and CID; retries on retryable statuses (DNR = 0).
Taught in
NVMe Errors, Kernel Logs.
What goes wrong
Status mapping hides detail (many NVMe statuses become one generic I/O error), retries mask intermittent faults.

Arrow 19 — Block layer → Application

Who acts
The block layer completes the bio; the filesystem finishes its part; the waiting thread is woken by the scheduler; the system call returns.
What crosses
Bytes read (for reads, already in the user buffer for O_DIRECT, or copied from the page cache), or an errno such as EIO.
Evidence
The return value and duration in strace -T; application logs.
Taught in
The Most Important Chapter, Linux NVMe Inspection.
What goes wrong
Scheduler wake-up latency dominating fast devices; errors surfacing far from their cause (an application EIO whose first abnormal event was a PCIe completion status many layers below).

The whole stack on the teaching ladder

A diner writes an order ticket, the waiter puts it in the box, rings the kitchen bell, the tube carries the bell's message, the cook fetches the ticket and ingredients, cooks, sends the dish to the table, drops a "ready" slip and taps the window; the waiter tells the diner.

Application → filesystem → block layer → NVMe driver builds a command, queues it, rings a doorbell; PCIe carries the doorbell; the controller fetches the command and data by DMA, uses the media, posts a completion and raises MSI-X; the driver completes the request upward.

CPU cores, DRAM, IOMMU, root complex and Root Port, lanes, the SSD's PCIe endpoint, NVMe front end, DMA engines, firmware CPUs, NAND channels.

NVMe Base 2.4 + NVM Command Set 1.3 (commands, queues, status), NVMe over PCIe Transport 1.4 (registers, doorbells, PRP/SGL, MSI-X use), PCI Express Base Specification (TLPs, ordering, link), plus Linux kernel interfaces (not specifications).

Host MWr (doorbell) → device MRd/CplD (SQE) → device MWr (data, read case) → device MWr (CQE) → device MWr (MSI-X) → host MWr (CQ head doorbell).

An analyzer shows arrows 8–17 directly (as TLPs and DLLPs, decodable with BAR0 and queue bases); Linux tracepoints show arrows 1–4 and 17–19; nothing shows arrow 13 except timing and device logs.

Find the first arrow whose evidence is missing or abnormal; everything above it in the return path is a consequence.

Reasoning arrow by arrow

  1. Start at the top, look for the first missing or abnormal evidence going down. Arrows 1–4: tracepoints normal. Arrows 6–11: doorbell written and acted upon (a fetch followed). Arrow 12: the SQE fetch succeeded, but the data fetch received a Completion with Unsupported Request status — a PCIe-level abnormal event.
  2. Correlate across views. The host's IOMMU fault log names the same device, direction and address within a microsecond. Two independent sources agree.
  3. Follow the propagation upward. The controller turned a PCIe failure into an NVMe status (Data Transfer Error, generic status 04h) in the CQE; the driver turned that into a block error; the block layer into EIO. Each layer translated, and each translation lost detail.
  4. Classify. PCIe was working correctly (the UR was the correct response to an unmapped address); NVMe was working correctly (it reported the transfer failure). The fault is in host software: the buffer's mapping lifetime (arrow 4's DMA mapping was undone before arrow 12 used it).
  5. Root cause and regression test. Fix the mapping lifetime; add a test that writes under IOMMU strict mode with KASAN/IOMMU debugging enabled and asserts no faults.

The application-level symptom (EIO at arrow 19) is eighteen arrows away from the first abnormal event (arrow 12). Without the stack in your head you would start with the SSD's SMART log, find nothing, and blame "the drive". With it, you ask at each arrow "did the expected evidence appear?", and the investigation is short.

Lab — Trace one I/O through as many arrows as your tools allow

Objective

Observe a single 4 KiB read at every arrow your system can show, timestamp each, and label the arrows you cannot see and why.

Skills

  • Using syscall, block and NVMe tracepoints together.
  • Mapping trace events to arrows.
  • Computing per-arrow latency.

Safety

Safe lab Reads only, with O_DIRECT via dd. Tracing needs root. Do not write to the device. On a production system, keep tracing sessions short.

Hardware and software required

Linux with an NVMe SSD; trace-cmd (or perf), strace, Python 3. Without hardware, use the synthetic timeline and the script below.

Input

Your NVMe namespace (/dev/nvme0n1) or the synthetic timeline from this page.

Expected output

A table with one row per visible arrow, its timestamp and delta, and a list of invisible arrows with the tool that would see them.

Background

The arrow-at-a-glance table and the visibility table above.

Step 1 — Record

sudo trace-cmd record \
  -e syscalls:sys_enter_read -e syscalls:sys_exit_read \
  -e block:block_bio_queue -e block:block_rq_issue -e block:block_rq_complete \
  -e nvme:nvme_setup_cmd -e nvme:nvme_complete_rq \
  dd if=/dev/nvme0n1 of=/dev/null bs=4k count=1 skip=512 iflag=direct
sudo trace-cmd report | grep -E 'dd-|nvme|block_' | head -40

Step 2 — Map events to arrows

Label each event with its arrow number using the table on this page. Note the NVMe queue ID and CID in nvme_setup_cmd and match them in nvme_complete_rq.

Step 3 — Compute and compare

Use the script below (fill in your own timestamps, or run it as is on the synthetic timeline).

"""Attribute end-to-end latency to arrows of the final mental model.
Default data: the synthetic timeline on this page (illustrative values, µs)."""

EVENTS = [  # (arrow label, timestamp in microseconds)
    ("1  syscall enter",           0.0),
    ("2  bio queued",              0.9),
    ("3  request issued",          1.6),
    ("4  SQE built",               2.4),
    ("6-10 doorbell on link",      3.0),
    ("11-12 SQE fetched",          4.4),
    ("13 media done, data starts", 61.2),
    ("12 data transferred",        62.2),
    ("14-15 CQE written",          62.4),
    ("16 MSI-X sent",              62.5),
    ("17 driver completed",        64.1),
    ("18 block complete",          65.4),
    ("19 syscall exit",            67.8),
]

def report(events):
    total = events[-1][1] - events[0][1]
    print(f"{'step':32s} {'t (us)':>8s} {'delta':>8s} {'share':>6s}")
    prev = events[0][1]
    for label, t in events:
        d = t - prev
        print(f"{label:32s} {t:8.1f} {d:8.1f} {100 * d / total:5.1f}%")
        prev = t
    host_down = events[3][1] - events[0][1]
    media = events[6][1] - events[5][1]
    host_up = events[-1][1] - events[9][1]   # from MSI-X sent to syscall exit
    print(f"\nTotal {total:.1f} us | host down {host_down:.1f} | media {media:.1f} | host up {host_up:.1f}")

if __name__ == "__main__":
    report(EVENTS)

Challenge

Repeat with bs=1M. Explain how many NVMe commands and how many data TLPs you expect (consider MDTS and Max Payload Size), and which arrows multiply.

Hints

A 1 MiB request larger than MDTS is split by the block layer into several requests (arrow 3). Each command's data is carried in MPS-sized MWr TLPs (arrow 12): 4 KiB / 256 B = 16 TLPs per 4 KiB.

Solution

(1) Typically invisible: arrow 5 (SQE store), arrows 7–12 and 14–16 as individual TLPs (need an analyzer), arrow 13 (device-internal; only inferable as the gap between setup and completion). (2) nvme_setup_cmd prints the qid; compare with the CPU column of the trace and with /sys/block/nvme0n1/mq/*/cpu_list. (3) In the synthetic data, host software is roughly 2.4 µs down and 5.3 µs up plus small gaps; polling removes the MSI-X and interrupt-delivery part of arrows 16–17 but spends CPU spinning.

Challenge: with MDTS = 128 KiB (as in NVMe Controller's worked example), 1 MiB becomes 8 commands of 128 KiB; each 128 KiB read needs 512 data MWr TLPs at MPS 256 B, so 4096 data TLPs in total, plus 8 SQE fetches, PRP list fetches (each 128 KiB command spans 32 pages, so PRP2 points to a list), 8 CQEs and up to 8 interrupts (fewer with coalescing).

What a senior engineer notices

  • Whether the first read after idle is much slower (power state exit, PCIe ASPM L1 exit) — arrows 10 and 13.
  • Whether interrupts land on a different CPU from the submitter (affinity), adding cross-CPU wake-up latency at arrow 19.

Failure variants

  • No NVMe events recorded: the read was served from cache (missing iflag=direct), or the tracepoints are named differently in your kernel (trace-cmd list -e nvme).
  • nvme_complete_rq shows a non-zero status: you have found a real error — stop and investigate with NVMe Errors.

Quiz

  1. Which statement is correct?

    • NVMe is a layer of PCIe
    • NVMe defines storage semantics, PCIe is an interconnect, and NVMe over PCIe binds them
    • NVMe over PCIe is published by PCI-SIG
    • PCIe defines NVMe status codes
    Answer and reasoning

    Three separate things. The binding (NVMe over PCIe Transport) is published by NVM Express, Inc.; PCIe is PCI-SIG's.

  2. At which arrow does the 64-byte SQE first appear on the PCIe link?

    • Arrow 5, when the driver writes it
    • Arrow 7, inside the doorbell write
    • Arrow 12, inside the CplD answering the controller's fetch
    • Never
    Answer and reasoning

    The driver writes the SQE to host memory (not on the link). The doorbell carries only the tail value. The SQE crosses the link in the completion to the device's Memory Read.

  3. Who acts at arrow 8 (MMIO → PCIe transaction)?

    • The root complex
    • The NVMe driver
    • The NVMe controller
    • The IOMMU
    Answer and reasoning

    The root complex converts the CPU's store into a posted Memory Write request.

  4. Which arrow is invisible to a PCIe analyzer and to Linux tracepoints?

    • Arrow 6
    • Arrow 15
    • Arrow 17
    • Arrow 13
    Answer and reasoning

    Arrow 13 (media access) is internal to the device; it appears only as a time gap and in device logs.

  5. Classify: "Completion Timeout on the controller's data read".

    Model answer

    A PCIe event (arrow 12) that will likely cause an NVMe event (a CQE with a data transfer error, or controller recovery) and then a block-layer error. One cause, several layered effects.

  6. Why is the doorbell cheap for the CPU while reading CSTS is expensive?

    Model answer

    The doorbell is a posted write: the CPU does not wait for anything. A CSTS read is non-posted: the CPU waits for the completion to travel back from the device.

  7. In the failure scenario, what is the first abnormal event and which layer reported it?

    Model answer

    The Completion with Unsupported Request status for the controller's data read (arrow 12), reported by the root complex at the PCIe layer, matched by an IOMMU fault on the host.

  8. Name two arrows that also occur in the device-to-host direction even though the stack draws them only downward.

    Model answer

    Arrows 9 and 10 (TLP formation and link transmission) occur for every device-initiated TLP: SQE fetch requests, data writes, CQE writes and MSI-X writes all go down the device's layers and up the root port's.

  9. Over NVMe/TCP, which arrows disappear or change?

    Model answer

    Arrows 6–12 and 15–16 change completely: no doorbell registers, MMIO, TLPs, PCIe link or MSI-X; commands and completions travel as capsules in TCP PDUs over a network stack, and data travels in data PDUs. Arrows 1–4, 13–14 and 17–19 keep their meaning (the driver is the NVMe/TCP host driver).

  10. A trace shows the doorbell MWr but no MRd from the device afterwards. Which arrows are suspect?

    Model answer

    Arrow 11 (controller not ready, fatal, invalid doorbell offset/value, queue not created) and possibly arrow 12 (Bus Master Enable cleared). Read CSTS and the PCI Command register next.

Interview questions

  1. Beginner: Explain the difference between NVMe and PCIe in two sentences.

    Model answer

    NVMe is a storage protocol: it defines controllers, namespaces, queues, commands and completions. PCIe is a general interconnect that moves packets between devices and memory; NVMe can use it as a transport, and the NVMe over PCIe Transport specification defines how.

  2. Intermediate: Walk me from read() to the bytes arriving in the user buffer.

    Model answer

    Syscall into VFS/filesystem → bio → blk-mq request on the CPU's hardware queue → NVMe driver builds a Read SQE with PRPs (IOVAs), writes it into the SQ in host memory and writes the SQ tail doorbell → the root complex sends a posted MWr TLP over the link → the controller fetches the SQE with MRd → reads media → DMA-writes data with MWr TLPs into the buffer → writes a CQE → sends MSI-X → the driver's handler processes the CQE by phase, rings the CQ head doorbell, completes the request → block layer and filesystem complete → syscall returns.

  3. Advanced: Where can a completion overtake its data, and what prevents it?

    Model answer

    Both data and CQE are device-to-host posted writes. PCIe ordering rules keep posted writes in order unless Relaxed Ordering permits passing; the controller must not set Relaxed Ordering on the CQE write in a way that lets it pass data, and host fabrics must honour ordering. If the CQE overtook the data, the host could read stale data after seeing the completion.

  4. Senior: An application reports sporadic EIO. Design your investigation using the stack.

    Model answer

    Start at the top and work down by evidence: syscall traces confirm which I/O fails; block tracepoints and kernel logs give the NVMe status and CID; NVMe tracepoints give the command; the status class decides the layer (media errors → arrow 13; Data Transfer Error → arrow 12, check IOMMU and AER; timeouts → arrows 11–17, read CSTS). Correlate kernel timestamps with AER and IOMMU logs. If ambiguous, capture with a PCIe analyzer triggered on the CQE status or on UR/CTO completions. Report the first abnormal event, the layer, the evidence from at least two independent views, and the propagation path.

  5. Senior: Which arrows would you instrument in production, and how, without hurting performance?

    Model answer

    Arrows 1/19 via application latency histograms; 3/18 via block-layer latency histograms (BPF, sampled); 4/17 via NVMe tracepoints with sampling or only on error statuses; AER, IOMMU and NVMe error counters continuously; SMART and telemetry periodically. Avoid per-I/O tracing; trigger detailed capture on anomalies.
