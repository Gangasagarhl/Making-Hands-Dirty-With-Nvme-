PCI Express (PCIe) does not deliver packets in strict order, and it does not deliver them in random order either. It follows an ordering table that is just strong enough for producer/consumer software to be correct and just weak enough to avoid deadlock and allow performance. This chapter teaches that table, the attributes that relax it (Relaxed Ordering, ID-Based Ordering), the role of Traffic Class, and why an NVMe driver can trust that read data is in memory before the completion entry that announces it.

Why this chapter exists

Every NVMe command depends on ordering twice. On the way in, the controller must not fetch a Submission Queue Entry (SQE) before the driver has finished writing it. On the way out, the driver must not see the Completion Queue Entry (CQE) before the data it describes has landed in memory, and must not take the interrupt before the CQE. Nothing in NVMe checks these things at run time: they are true because of CPU memory ordering on one side and PCIe ordering rules on the other. When either is misconfigured — a Relaxed Ordering bit on the wrong write, a missing barrier, a Root Complex that mishandles an attribute — the result is not an error message but silently wrong data.

The master plan for this course says "do not oversimplify ordering". So this chapter is careful about what is guaranteed, what is permitted, what is required for deadlock freedom, and what depends on your specification revision.

Learning objectives

  • State what PCIe ordering rules govern: TLPs in the same direction, through the same path, in the same Traffic Class (TC).
  • Read the ordering table: which of Posted requests, Non-Posted requests and Completions may pass, must not pass, or must be able to pass each other — and why.
  • Explain Relaxed Ordering (RO) and ID-Based Ordering (IDO): what they permit, who enables them, and when they are dangerous.
  • Distinguish ordering from coherency (No Snoop) and from flow control.
  • Apply the producer/consumer model to the NVMe submission path and completion path.
  • Explain why posted writes must be able to pass non-posted requests (deadlock avoidance).
  • Find an ordering violation in a synthetic trace.

The story

The library sends the teacher's classroom a big box of books, and then a note that says "Your books are on table 3!" If the note arrived first, a child would run to table 3 and find nothing. So the rule on the road is: a note may not overtake the books it is talking about.

But some trucks are allowed to overtake. A truck with a "this one can go ahead" sticker may pass slower trucks — useful when the order does not matter, like the many boxes of one big delivery. The library is careful never to put that sticker on the note.

And there is one special rule: delivery trucks must always be able to get past a truck that is stuck waiting for an answer, otherwise everyone could end up stuck forever, each waiting for the other.

A courier company that promises: "Parcels from the same sender to the same address arrive in the order you sent them, unless you mark a parcel no rush order. Collection requests (where we must bring something back) never hold up deliveries. And the parcels we bring back for you don't overtake the deliveries you sent before asking." With these promises a business can ship goods and then mail the invoice, confident the invoice never arrives first.

  • "Same sender, same address." PCIe ordering applies along a path in one direction within one Traffic Class; it is not a per-destination-address promise. Two posted writes from the SSD to different host addresses are still ordered (unless relaxed).
  • The courier never reorders. PCIe components are permitted to reorder in many cases (marked "Y/N" in the table). Correct software must not depend on order the table does not guarantee — even if a particular platform happens to preserve it.
  • The invoice and goods travel together. In NVMe the "note" (CQE) and "books" (data) are both device writes to host memory, so PCIe ordering covers them. But on the submission side, the SQE goes into host memory via the CPU's cache and the doorbell goes to the device via MMIO: two different paths. That ordering is the CPU's job, not PCIe's.
  • Couriers have no deadlock. The "deliveries never wait behind collections" rule exists in PCIe for a structural reason — to break dependency cycles between buffers — which the analogy only hints at.

Beginner explanation

Inside a PCIe component, TLPs waiting to be sent sit in separate queues for posted requests, non-posted requests and completions. When the component picks the next TLP to send, may it pick a later one before an earlier one? The ordering rules answer that, for every pair of TLP categories.

The three most important rules:

  1. Posted writes stay in order. A memory write must not pass an earlier memory write (unless the later one has Relaxed Ordering set, or ID-Based Ordering applies). So data written first is visible first.
  2. Reads and completions do not overtake writes. A read request must not pass an earlier posted write; a completion must not pass an earlier posted write (again, unless relaxed). So "write, then read" really reads after the write, and the answer to a read cannot arrive ahead of writes sent before it.
  3. Writes and completions must be able to overtake stuck requests. If a non-posted request is blocked (for example, waiting for credits), posted writes and completions behind it must be able to go around it. Otherwise the system can deadlock.

Everything else is mostly "permitted but not required" — components may reorder or not, and software must not depend on either.

Engineering explanation

Scope: what the rules apply to

  • Same direction, same path. The rules govern TLPs that a component handles in the same direction (for example, everything a switch forwards upstream from one port). TLPs going in opposite directions have no ordering relationship at all.
  • Same Traffic Class. Ordering is defined only among TLPs with the same TC. TLPs with different TCs may be mapped to different Virtual Channels (VCs) and have no ordering relationship. Almost all NVMe traffic is TC0, so this is normally moot — but a misconfigured TC breaks every ordering assumption below.
  • At every component. Each component along the path (Root Complex, switch, endpoint) must follow the rules for what it forwards or generates. End-to-end ordering is the composition of per-hop ordering.
  • As observed at the destination. For writes into host memory, the Root Complex must make writes visible to CPUs in an order consistent with the rules. How it does so internally is implementation-specific.

The ordering table

The specification presents ordering as a table: each cell answers "may a TLP of the row type pass an earlier TLP of the column type?" Entries are:

  • Yes — the row TLP must be able to pass the column TLP (to avoid deadlock). It does not have to pass if nothing is blocked; it must not be prevented from passing.
  • No — the row TLP must not pass the column TLP.
  • Y/N — no requirement: passing is permitted but not required.

Reading the table row by row

  • Posted passes posted: No (by default). This is the backbone of producer/consumer correctness: data then flag stays data then flag.
  • Posted passes non-posted: Yes. If reads are stuck (no NP credits at the next hop, or a bridge waiting on completions), writes must flow around them. Otherwise a write that would free the resource the read is waiting for could be stuck behind the read: a deadlock.
  • Posted passes completion: Y/N. Generally permitted; certain bridge configurations require it.
  • Read passes posted: No. A read must see the effects of writes issued before it on the same path. This makes "write then read back" a flush, and lets a device read back its own earlier writes.
  • Read passes read / completion: Y/N. Reads can be serviced out of order; their completions sort themselves out by tag.
  • Completion passes posted: No (by default). When the CPU reads a device register, the completion travels upstream behind any data writes the device issued earlier. So when the CPU gets the register value, the earlier writes are already ahead of it — the classic "read the status register to flush DMA" pattern.
  • Completion passes non-posted: Yes. Completions must never wait behind requests (they free requesters' resources).
  • Completion passes completion: Y/N across different requests; No within one request. Split completions of one read stay in address order (Chapter 13).

Relaxed Ordering (RO, Attr[1])

Strict write ordering costs performance in some Root Complexes and fabrics: if one write is slow to commit (for example, it misses in a cache or needs an IOMMU walk), every later write waits behind it, even writes that have nothing to do with it. Relaxed Ordering lets a requester mark TLPs whose ordering does not matter.

  • Who may set it: a function, only when software has set Enable Relaxed Ordering in its Device Control register. Even then, the function chooses per TLP.
  • What it permits: a posted request with RO set may pass earlier posted requests; a completion with RO set may pass earlier posted requests. Read completions inherit RO from the read request, so a requester asking with RO lets the completer's answer pass earlier writes.
  • What it does not permit: anything for TLPs that do not have it set. A posted write with RO clear still must not pass any earlier posted write — including earlier writes that had RO set. This asymmetry is what makes RO safe for data and dangerous for flags.
  • Who honours it: components may, but need not, exploit the permission. Some Root Complexes historically mishandled RO; operating systems carry quirks that clear the enable for devices below such ports. Implementation-dependent

Set RO on bulk data writes; clear RO on the write that signals completion (the CQE) and on the interrupt write (MSI-X). Then data writes may reorder among themselves, but the CQE cannot pass any of them, and the MSI-X cannot pass the CQE. This is the pattern an NVMe controller should follow when Relaxed Ordering is enabled. Derived from the rules above.

ID-Based Ordering (IDO, Attr[2])

In a fabric shared by many functions (multi-function devices, SR-IOV virtual functions, many devices behind one switch), strict ordering couples unrelated traffic: a stalled write from function A blocks function B's writes. IDO declares that a TLP only needs ordering with respect to TLPs from the same source.

  • What it permits: a posted or non-posted request with IDO set may pass an earlier posted request with a different Requester ID; a completion with IDO set may pass an earlier posted request whose Requester ID differs from the completion's Completer ID.
  • Enables: Device Control 2 — IDO Request Enable and IDO Completion Enable.
  • Why it is safe: producer/consumer relationships normally exist within one source's traffic; unrelated sources have no ordering relationship that software relies on.

No Snoop is not an ordering attribute

No Snoop (NS, Attr[0]) says the access does not need hardware cache coherency. It changes what data a read returns or where a write lands relative to CPU caches, not the order of TLPs. It is mentioned here because it causes the same class of symptoms (stale data) and is often confused with RO. A device that reads an SQE with NS set could read a stale copy from DRAM if the CPU's newer copy is still in its cache. Whether and when NVMe controllers use NS, and how platforms honour it, is implementation-dependent; NVMe drivers on cache-coherent platforms normally rely on snooped accesses for queues. Implementation-dependent

The producer/consumer model

The specification describes ordering in terms of a producer/consumer model: a producer writes data, then writes a flag; a consumer sees the flag, then reads the data. The ordering rules guarantee the consumer sees the new data, for the placements of producer, consumer, data and flag that the model covers. Apply it to NVMe:

Completion path: device produces, CPU consumes

Data and CQE are both posted writes from the same requester on the same path in the same TC. The CQE must not pass the data (posted must not pass posted unless the later one has RO). The MSI-X must not pass the CQE. When the CPU observes the CQE's new phase tag, all the data is visible. On the CPU side the driver still needs a read barrier between "observe phase tag" and "read the rest of the CQE / the data" to stop the CPU itself from reordering its loads (the Linux NVMe PCI driver uses dma_rmb() for this). If the driver polls without interrupts, the same reasoning holds without the MSI-X step.

Submission path: CPU produces, device consumes

Here PCIe ordering alone is not what makes it work. The SQE is a CPU store to coherent memory; the doorbell is a CPU store to MMIO. The CPU's memory model plus the barrier implied by Linux's writel() guarantee the SQE store is globally visible before the doorbell write leaves the CPU. The device's MRd for the SQE arrives at the Root Complex after the doorbell was delivered, and a snooped read then returns the current SQE. PCIe ordering contributes only in a supporting way (for example, the device's own read of the SQE cannot pass its own earlier posted writes). Write barriers in the driver are therefore not optional decoration: on weakly ordered CPUs, removing them breaks NVMe.

Why the NVMe doorbell/data ordering works: submission — CPU memory ordering + barrier before the MMIO doorbell + snooped device read; completion — PCIe posted-write ordering (CQE and MSI-X with RO clear cannot pass data) + CPU read barrier after observing the phase tag. Break any link and data or commands can be seen stale, with no error reported anywhere.

Register read as a flush

Older device designs (and some NVMe error-handling paths) read a device register to make sure earlier DMA writes are visible: the register read's completion travels upstream and cannot pass the device's earlier posted writes (unless the completion has RO set). NVMe's normal path does not need this because the CQE itself is a posted write ordered behind the data.

Deadlock avoidance, concretely

Practical implications for NVMe engineers

  • Data before CQE before MSI-X is guaranteed by PCIe only if the CQE and MSI-X writes are not relaxed and all three use the same TC.
  • RO on data writes is safe and can help throughput on platforms that exploit it.
  • A CPU register read after a device write sees the write (completion cannot pass posted) — unless the read's completion is relaxed.
  • SQE visibility before the doorbell is a CPU-side guarantee; check barriers in custom drivers (user-space drivers such as SPDK must place them correctly too).
  • Peer-to-peer traffic (device to device through a switch) follows the same rules along its path, but paths through the Root Complex may have platform-specific ordering limitations. Implementation-dependent

The central concept on the ladder

A note must not overtake the books it describes; trucks marked "can go ahead" may overtake; delivery trucks must always be able to get past trucks stuck waiting.

Posted must not pass posted; reads and completions must not pass posted; posted and completions must be able to pass non-posted; everything else is permitted. RO and IDO relax specific "No" entries for TLPs that carry them.

Ports keep per-class queues with bypass paths so posted and completion TLPs can go around blocked non-posted ones; Root Complexes keep write-commit ordering into memory unless RO lets them commit out of order.

The Transaction Ordering section of the PCIe Base Specification defines the table, the producer/consumer model, RO and IDO semantics; Device Control/Device Control 2 hold the enables; TC/VC mapping limits the scope.

NVMe completion path: MWr data (RO ok) → MWr CQE (RO clear) → MWr MSI-X (RO clear). Submission path: CPU store SQE → barrier → MMIO doorbell → device MRd SQE.

In a trace: check the Attr bits of CQE and MSI-X writes; check that CQE timestamps follow all data writes of that command at the link; check TC is uniform.

Stale or partially stale data with no errors logged → suspect RO on a flag write, a missing CPU barrier, NS on a coherent buffer, a TC/VC split, or a Root Complex RO erratum.

Hardware view

  • Endpoints must emit their own TLPs in an order consistent with the rules (a DMA engine that issues the CQE write from a different internal queue than the data writes must still keep them ordered on the link).
  • Switches forward between ports per class and VC; they must not reorder in forbidden ways and must let P/Cpl bypass blocked NP.
  • Root Complexes are where RO actually pays off: a write that waits on a slow address translation or a cache conflict need not hold up unrelated relaxed writes. It is also where RO errata have historically lived. Implementation-dependent
  • CPUs have their own memory-ordering model; MMIO and DMA-coherent memory accesses interact with it through barriers. PCIe ordering ends at the Root Complex's commit to the memory system.

Specification view

Ordering is defined in the PCI Express Base Specification, Revision 6.x/7.0 — Transaction Ordering (Ordering Rules Summary; Relaxed Ordering and ID-Based Ordering; Update Ordering and Granularity; producer/consumer model). Enables are in the PCI Express Capability — Device Control and Device Control 2. NVMe's reliance on ordering is implicit in the queue model of the NVM Express Base Specification 2.4 and the PCIe mapping in the NVMe over PCIe Transport Specification 1.4.

  • Ordering applies among TLPs of the same TC; there is no ordering between different TCs.
  • By default a posted request must not pass an earlier posted request; read requests and completions must not pass earlier posted requests.
  • Posted requests and completions must be able to pass blocked non-posted requests (deadlock avoidance).
  • Completions with the same Transaction ID must not pass each other; with different Transaction IDs they may.
  • RO (Attr[1]) and IDO (Attr[2]) relax specific rules for the TLP carrying them; they may only be set when enabled.
  • The "RO on data, not on CQE/MSI-X" pattern and the NVMe completion-path proof are reasoning from the rules.
  • The statement that the NVMe submission path relies on CPU ordering rather than PCIe ordering is reasoning from where the SQE and doorbell travel.
  • The simplified ordering table above is a reconstruction for teaching.
  • Whether a component actually reorders when permitted (Y/N cells).
  • Whether a Root Complex honours RO correctly; OS quirks that disable RO.
  • Which TLPs an NVMe controller marks RO or NS when enabled.
  • Ordering guarantees for peer-to-peer traffic through a Root Complex.
  • Newer revisions add request types and rules (for example, Deferrable Memory Write) and Flit Mode-specific behaviour; the exact table evolves.
  • IDO was added after the first PCIe revisions; very old devices lack Device Control 2 IDO enables.

Check in the specification: the complete ordering table with all footnotes for your revision; the precise IDO conditions; the bridge-related "must pass" cases; update-ordering granularity (how much of a multi-byte write a reader may observe partially); whether MSI/MSI-X writes have any attribute restrictions. To our knowledge the NVMe specifications do not state which TLPs a controller must or must not mark with RO — confirm in the NVMe Base and PCIe Transport specifications rather than relying on this note.

  • Never assume total ordering because "the trace looked ordered": the analyzer shows link order, not commit order inside the Root Complex.
  • Never set RO on a write whose purpose is to signal that earlier writes are done.
  • Never assume PCIe ordering protects the SQE-before-doorbell relationship; that is the CPU's job.

Code / pseudocode

An ordering explorer: it encodes the simplified table, enumerates every order in which a small sequence of TLPs could become visible under the rules, and checks a producer/consumer invariant. Standard library only; small sequences only (it tries all permutations).

#!/usr/bin/env python3
"""Explore which visibility orders the (simplified) PCIe ordering rules permit,
and whether NVMe-style producer/consumer invariants survive. Teaching model only."""
from itertools import permutations
from dataclasses import dataclass

@dataclass
class TLP:
    name: str
    cls: str                 # "P" posted, "NPR" read, "NPD" non-posted with data, "CPL"
    ro: bool = False
    ido: bool = False
    rid: int = 0x0100        # Requester ID (for completions: the original requester)
    cid: int = 0             # Completer ID (completions only)
    txid: int = 0            # Transaction ID (completions only)
    cfg_io_wr_cpl: bool = False

def may_pass(later, earlier):
    """'No', 'Y/N' or 'Yes' for: may `later` pass `earlier`?"""
    if later.cls == "P":
        if earlier.cls == "P":
            if later.ro or (later.ido and later.rid != earlier.rid):
                return "Y/N"
            return "No"
        return "Yes" if earlier.cls in ("NPR", "NPD") else "Y/N"
    if later.cls in ("NPR", "NPD"):
        if earlier.cls == "P":
            return "Y/N" if (later.ido and later.rid != earlier.rid) else "No"
        return "Y/N"
    # completion
    if earlier.cls == "P":
        if later.ro or later.cfg_io_wr_cpl or (later.ido and later.cid != earlier.rid):
            return "Y/N"
        return "No"
    if earlier.cls in ("NPR", "NPD"):
        return "Yes"
    return "No" if later.txid == earlier.txid else "Y/N"

def permitted_orders(seq):
    n = len(seq)
    for perm in permutations(range(n)):
        pos = {i: k for k, i in enumerate(perm)}
        if all(not (pos[j] < pos[i] and may_pass(seq[j], seq[i]) == "No")
               for i in range(n) for j in range(i + 1, n)):
            yield [seq[i] for i in perm]

def check(title, seq, before):
    """before: list of (a, b) meaning a must be visible before b."""
    orders = list(permitted_orders(seq))
    bad = [o for o in orders
           if any([t.name for t in o].index(a) > [t.name for t in o].index(b) for a, b in before)]
    print(f"{title}: {len(orders)} permitted orders, {len(bad)} violate the invariant")
    if bad:
        print("   e.g.", " -> ".join(t.name for t in bad[0]))

The model ignores the "must be able to pass" nuance (it treats Yes as permission) and simplifies multi-hop behaviour; it is for reasoning, not compliance testing.

Worked example

Is this firmware change safe?

A controller firmware team proposes: "When Relaxed Ordering is enabled, set RO on every upstream write, including CQEs, because our measurements on platform X show 3% more IOPS." Evaluate it step by step.

  1. Identify the producer/consumer pair. Data (MWr) is the data; the CQE (MWr) is the flag; the MSI-X (MWr) is a second flag.
  2. Apply the table. A posted request may pass an earlier posted request if the later one has RO set. With RO on the CQE, the CQE may pass earlier data writes. The rule is satisfied by the hardware; the invariant is not.
  3. Ask whether the platform exploits the permission. On platform X it may never reorder, which is why tests pass. On a platform whose Root Complex commits relaxed writes as soon as translation finishes, a CQE can become visible before slow data.
  4. Consider the consumer. The driver reads the CQE (phase tag), applies a CPU read barrier, and returns the buffer to the application. No later check can detect stale data.
  5. Conclusion. Unsafe by specification, even if it passes on platform X. Keep RO on data writes; clear it on CQE and MSI-X writes. If 3% matters, investigate why the CQE write is slow (for example, CQ memory placement).

Does a register read flush the data?

A diagnostic tool reads a vendor-specific "DMA idle" register after a READ to decide that data has landed. The read's CplD travels upstream behind the data MWrs. Completions must not pass posted requests unless the completion has RO set (or the IDO conditions apply). A completion's RO comes from the request: the CPU's MRd is issued by the Root Complex, which normally does not set RO on its MMIO reads, so the completion has RO clear. So the completion is strictly ordered behind the data writes on the link. Derived — confirm that your Root Complex does not set RO on MMIO reads before relying on it.

Common mistakes

  • "PCIe is in order." Only for the cells marked No, within a TC, along a path.
  • "PCIe is out of order." Equally wrong; posted writes are ordered by default.
  • "RO on the earlier write lets the later write pass it." No: the permission belongs to the TLP that does the passing.
  • "The trace shows the right order, so ordering is fine." The link order is not the commit order inside the Root Complex.
  • Mixing up NS and RO. NS is coherency, RO is ordering.
  • Forgetting the CPU side. SQE-before-doorbell and phase-tag-before-data need CPU barriers.
  • Assuming different TCs keep relative order. They do not.

Senior engineer insight

Ordering bugs are invisible to every tool that reports errors. They show up as data-integrity failures with no logs. When a team says "no errors anywhere, but data is occasionally wrong", put ordering (attributes, barriers, TC) on the suspect list before media or firmware logic.

The most dangerous phrase in ordering discussions is "but it works on our platform". Y/N cells and RO permissions describe what a component may do. A design that depends on a component not using a permission is a latent bug that will surface on the next Root Complex generation.

A senior also keeps the two halves separate: PCIe ordering (attributes, classes, TC) and CPU ordering (barriers, MMIO semantics). Most real ordering incidents in NVMe stacks happen at the boundary — in user-space drivers, custom firmware, or new CPU architectures with weaker memory models.

What a senior engineer notices

The safe policy is a property of which TLP signals completion, not of the data. Any future feature that adds a new "flag" write (for example, a status update in host memory) needs the same treatment; reviewing attribute policy belongs in the design review of such features.

Failure variants

Exercises

  1. Fill in from memory: may a completion pass an earlier posted request? May a posted request pass an earlier read request? Give the reason for each.
  2. An accelerator writes results to host memory and then writes a "done" flag, both with RO set. Is that safe? What would you change?
  3. Why does the deadlock-avoidance rule apply to completions passing non-posted requests as well as posted ones?
  4. A device issues MRd to a host buffer it wrote 1 µs earlier with MWr (RO clear). Will the read see the written data? Why?
  5. Explain why the NVMe driver needs a write barrier before the doorbell even though PCIe orders posted writes.
Model answers
  1. Completion past posted: No by default (so read results do not overtake earlier writes), Y/N with RO, IDO-ID conditions, or for I/O/config write completions. Posted past read: Yes (must be able to), to avoid deadlock.
  2. Unsafe: the flag may pass results. Clear RO on the flag write (results may keep RO).
  3. Requesters free buffers and tags only when completions arrive; if completions could be blocked behind non-posted requests that themselves wait for those resources, a cycle forms.
  4. Yes: a read request must not pass an earlier posted write on the same path, and the Root Complex must preserve that when serving the read from memory.
  5. The SQE is written to host memory by CPU stores, which are not TLPs at all; the doorbell is an MMIO store. Only CPU ordering (enforced by the barrier) guarantees the SQE stores are visible before the doorbell reaches the device.

Quiz

  1. By default, may a posted write pass an earlier posted write in the same TC?

    • Yes, always
    • No
    • Only if the earlier one has RO set
    Answer and reasoning

    No. Only RO (or IDO with different IDs) on the later write permits passing.

  2. Which entry exists to prevent deadlock?

    • Read must not pass posted
    • Completions of one request stay in order
    • Posted must be able to pass non-posted
    • Posted must not pass posted
    Answer and reasoning

    Posted requests (and completions) must be able to bypass blocked non-posted requests.

  3. Where is Relaxed Ordering enabled for a function?

    • Device Control register
    • Link Control register
    • NVMe CC register
    • MSI-X table
    Answer and reasoning

    Enable Relaxed Ordering is a Device Control bit in the PCI Express Capability.

  4. Which TLP of an NVMe READ should never carry RO?

    • Data writes
    • CQE write
    • SQE fetch read
    Answer and reasoning

    The CQE (and MSI-X) signal completion; they must not pass the data.

  5. Are TLPs in TC0 and TC1 ordered relative to each other?

    • Yes
    • No
    • Only posted ones
    Answer and reasoning

    Ordering is defined only within the same TC.

  6. What does No Snoop affect?

    • Cache coherency of the access
    • Ordering relative to posted writes
    • Routing
    Answer and reasoning

    NS says hardware snooping is not required; it is not an ordering attribute.

  7. Why does a CPU register read after device DMA writes "flush" them?

    Model answer

    The read's completion travels upstream on the same path as the device's earlier posted writes and must not pass them (absent RO/IDO conditions), so by the time the CPU gets the value the writes are ahead of it and committed in order.

  8. Explain IDO in one sentence and give a scenario where it helps.

    Model answer

    IDO lets a TLP pass earlier posted requests from a different source ID, keeping ordering only within a source; it helps when many SR-IOV virtual functions share a link and one function's slow write should not stall others.

  9. Why does the NVMe submission path not rely on PCIe ordering?

    Model answer

    The SQE is stored to host memory by the CPU (not a TLP) while the doorbell is an MMIO TLP; their relative order is established by CPU memory ordering and the barrier before the MMIO write.

Interview questions

  1. (Beginner) What does it mean that posted writes are ordered?

    Model answer

    Without RO/IDO, a later memory write from a requester will not become visible before an earlier one along the same path and TC.

  2. (Intermediate) Why must reads not pass posted writes?

    Model answer

    So a read sees the effects of earlier writes on the same path (read-after-write consistency, flush semantics, producer/consumer correctness).

  3. (Intermediate) What is Relaxed Ordering and when is it safe?

    Model answer

    An attribute letting a TLP pass earlier posted requests (and completions with RO pass posted). Safe on writes whose relative order does not matter (bulk data), never on writes that signal completion.

  4. (Advanced) Walk through why an NVMe driver sees READ data before the CQE.

    Model answer

    Data and CQE are posted writes from the same requester in TC0; the CQE has RO clear so it cannot pass earlier data; the Root Complex commits in order; the driver reads the CQE's phase tag, issues a read barrier, then accesses data.

  5. (Advanced) Explain a deadlock that the "posted passes non-posted" rule prevents.

    Model answer

    Two agents each with NP requests blocked for lack of credits at the other; each agent's ability to drain its NP buffer depends on a posted write making progress; if posted were stuck behind NP, neither progresses. Allowing posted to bypass breaks the cycle.

  6. (Senior) Data corruption appears only on a new server platform; no errors are logged. What is your plan?

    Model answer

    Suspect ordering/coherency first: capture traces and inspect RO/NS/TC on CQE and MSI-X writes; toggle RO enable on a test system to see if symptoms follow; check OS quirks for this Root Complex; review driver barriers for the CPU architecture; check IOMMU translation stalls correlating with corruption.

  7. (Senior) How would you review a firmware proposal to set RO on more TLP types?

    Model answer

    Enumerate every producer/consumer pair the device participates in, identify the flag TLP for each, and require RO clear on every flag; require evidence on platforms that exploit RO aggressively, not just on one that does not; document the policy.

Chapter summary

PCIe ordering is defined per TC along a path. Posted writes stay in order; reads and completions do not pass posted writes; posted writes and completions must be able to pass blocked non-posted requests; completions of one request stay in order. Relaxed Ordering lets the TLP carrying it pass earlier posted writes; ID-Based Ordering limits ordering to the same source. No Snoop is about coherency, not order. NVMe's completion path is protected by PCIe ordering if the CQE and MSI-X writes are not relaxed; its submission path is protected by CPU ordering and barriers.
