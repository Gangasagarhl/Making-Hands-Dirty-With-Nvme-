One capture rarely holds the whole story. This module builds forensic analysis across sources — analyzer export, kernel log, NVM Express (NVMe) logs, Advanced Error Reporting (AER) registers, Input–Output Memory Management Unit (IOMMU) faults — on one aligned clock, compares failing runs with golden runs stage by stage, groups thousands of failures by signature, and fills the senior root-cause template automatically, with every sentence traceable to evidence.

Kid story

A lunchbox went missing at school. The teacher's diary says "lunchboxes on the shelf at 11:55" by the classroom clock. The bus driver's notebook says "school bus left 12:03" by his watch. The cook's list says "lunch served 12:00" by the kitchen clock. Each clock is a little wrong. So the detective finds things everyone wrote down — the fire bell rang at the same moment for all of them — and uses those to fix each clock. Now the notes line up, and the detective sees that the lunchbox was last seen after the bus left, so the bus did not take it. Then the detective looks at last week's diaries, when nothing went missing, and asks: "What is different today?"

Analogy boundary

What it represents. Diaries are evidence sources (analyzer export, kernel log, NVMe logs, register snapshots); each clock is a clock domain; the fire bell is an anchor event seen by several sources; correcting the clocks is alignment; last week's diaries are the golden run.

What it hides. Real clocks drift as well as being offset, so one anchor is not enough; two or more, spread over the window, are needed to estimate drift. Sources also differ in what they can see: the analyzer sees packets but not driver decisions; the kernel log sees driver decisions but not packets; some sources only record a snapshot (a register read) rather than a moment. Where it misleads. The story implies that after alignment everything can be put in order. It cannot: when two events from different sources are closer together than the alignment uncertainty, their order is unknown, and a forensic tool must say so instead of sorting them confidently.

Clock alignment

tan = a + b × thost,   u = maxi |ri|
tan
time on the analyzer timebase (the reference), ns
thost
time on the host's clock, ns
a
offset, ns, fitted by least squares over anchor pairs
b
rate ratio; (b − 1) × 106 is the relative drift in parts per million
ri
residual of anchor i: its analyzer time minus the fitted value
u
alignment uncertainty: events from different domains closer than u cannot be ordered

Anchors must be causal pairs with small, known lag: a host log line written just before a doorbell, an Abort or reset command, a marker I/O. The host log's timestamp is taken by software at some point near the doorbell, not at it; that lag is the main source of residual. Derived

The central concept on the ladder

Fix every diary's clock with the fire bell, line the notes up, and compare with a normal week.

Forensic analysis normalizes every source, aligns clocks with anchors, links events by shared identifiers, and compares with golden behaviour to find the first abnormal event and the owning layer.

Each source sits at a different place: the analyzer at the link, the kernel log in the driver, the Error Information log inside the controller, AER registers in each port's configuration space, the IOMMU log in the host platform. Each sees one layer and has its own clock.

The specifications define the meaning of what is recorded — AER registers (PCI Express Base), the Error Information log and CQE status (NVMe Base 2.4), doorbells and MSI-X mapping (NVMe over PCIe Transport 1.4) — but not how to fuse them. Fusion is engineering.

The links between sources are protocol identities: the Command Identifier (CID) in the driver's log and in the SQE; the Requester ID and Tag in the TLP and in the AER Header Log; the IOVA (I/O virtual address) in the TLP and in the IOMMU fault.

In the fused timeline, a CQE at 2,000,065,000 ns with no MSI-X afterwards, and a host timeout 30 s later, become one story connected by CID 0x0042.

The first abnormal event is the missing interrupt, dated at its deadline; candidates are a masked vector, a controller interrupt bug, coalescing settings, or capture filtering — each with a discriminating check.

Specification discipline

Applicable documents: PCI Express Base Specification (Revision 6.x/7.0 family) for TLP semantics, completion timeout, AER registers and error Messages; NVM Express Base Specification, Revision 2.4, for queues, CQE status, the Error Information log, SMART/health and asynchronous events; NVMe over PCIe Transport, Revision 1.4, for doorbells and interrupt mapping; NVM Command Set, Revision 1.3, for I/O command status.

Normative: a non-posted request is answered by completions carrying the requester's ID and Tag; posted requests receive none; CQEs carry SQID, CID, SQ Head Pointer, Phase Tag and Status; the Error Information log records errors with identifying fields including the submission queue and command identifiers. PCI Express Base Specification — Transaction Layer; Advanced Error Reporting NVM Express Base Specification 2.4 — Completion Queue Entry; Error Information log page

Clock alignment, evidence graphs, stage diffing, signatures, triage clustering and the root-cause template are engineering methods. Their outputs are interpretations of normative facts, and must be labelled as such. Derived

Implementation-dependent: host timeout values and recovery steps (driver policy); which errors a controller records in its Error Information log and when; telemetry content; interrupt coalescing behaviour within the configured limits; IOMMU fault logging format; kernel log wording. Optional: AER itself is an optional capability; Interrupt Coalescing and telemetry are optional NVMe features — check the device's capabilities before expecting evidence from them. Optional

Log page contents and status code tables grow across NVMe revisions; kernel log formats change across kernel versions. Record versions in the bundle; key status names by revision.

No specification defines a common timebase across host, analyzer and device, how long a host should wait before declaring a timeout, or how an interrupt should be "expected" when coalescing is enabled. Informative text in the specifications explains intent; it is not a test oracle.

Never assume a missing log entry means nothing happened (logs are finite and implementation-defined), that AER registers still hold the first error (later errors and clearing change them), or that a host timeout time equals the device's stall time.

The MSI-X table lives in device memory (BAR0 + 0x2000 on the lab system) and each entry has a mask bit in its Vector Control field. A masked vector means the device must not send that message and instead sets the pending bit (PBA, BAR0 + 0x3000). A snapshot of both is decisive evidence in "lost interrupt" cases — and reading them is a read-only MMIO access that a lab tool can perform; never write them.

Ordering rules help alignment. A CQE write (posted MWr64) followed by an MSI-X write (posted MWr32) from the same device travel in order on the link; the MSI-X cannot overtake the CQE under default ordering, which is why a host that takes the interrupt finds the CQE in memory. See PCIe Ordering. Errors appear at their own layer: completion status (Transaction Layer), AER (reporting), CQE status (NVMe), timeouts (driver policy).

Labs

Labs 1–3 are Safe lab: offline, synthetic data. Lab 4 is Safe lab as a paper exercise; its extension collecting evidence on hardware is a Caution lab on a lab system only (reading registers is safe; never write MSI-X or AER registers to "test").

Beginner lab — Map sources to layers and clocks

Objective. For each evidence source, name the layer it observes, its clock domain and one blind spot. Prerequisites. Vocabulary above; Kernel Logs. Setup. Paper. Procedure. Fill a table for: analyzer export, kernel log, nvme tracepoints, Error Information log, SMART/health log, AER status, IOMMU fault log, MSI-X table snapshot. Observations. Count sources with no timestamp at all. Questions. Which sources can serve as anchors? Which are snapshots?

Expected reasoning. Only events seen by two sources with known identity make anchors; snapshots have a collection time, not an event time.

Solution

Analyzer: PCIe link layers, analyzer timebase, blind to host software and device internals. Kernel log: driver decisions, host clock, blind to the link. Tracepoints: driver submissions and completions, host clock (fine resolution), blind to the device. Error Information log: controller-recorded errors, its own counters rather than a host timestamp, blind to errors it does not record. SMART/health: cumulative counters and warnings, no event times. AER status: PCIe error bits, snapshot only. IOMMU fault log: translation faults with host timestamps, blind to successful DMA. MSI-X table: configuration snapshot. Anchors: tracepoint or log lines for commands whose doorbells the analyzer sees; driver abort/reset messages. Snapshots: AER, CSTS, MSI-X table, SMART.

Extension. Add the BMC's out-of-band NVMe-MI health polls as a ninth source; what clock does it use?

Intermediate lab — Align, fuse, and find the order you cannot know

Objective. Run and modify the alignment program. Prerequisites. Python 3.8+; the formula above. Setup. Save as fuse.py.

def fit(pairs):
    """Least-squares t_analyzer = a + b * t_host over anchor pairs."""
    xs, ys = [p[0] for p in pairs], [p[1] for p in pairs]
    mx, my = statistics.fmean(xs), statistics.fmean(ys)
    b = sum((x - mx) * (y - my) for x, y in pairs) / sum((x - mx) ** 2 for x in xs)
    a = my - b * mx
    resid = [y - (a + b * x) for x, y in pairs]
    return a, b, max(abs(r) for r in resid)

if __name__ == "__main__":
    amap = {e[0]: e[1] for e in ANALYZER}
    pairs = [(h[1], amap[h[3]]) for h in HOST if h[3]]
    a, b, worst = fit(pairs)
    print(f"alignment: t_an = {a:,.0f} + {b:.9f} * t_host  (drift {1e6 * (b - 1):+.1f} ppm, "
          f"worst anchor residual {worst:,.0f} ns, {len(pairs)} anchors)")
    timeline = [(t, eid, "analyzer", txt) for eid, t, txt in ANALYZER]
    timeline += [(round(a + b * t), hid, "host", txt) for hid, t, txt, _ in HOST]
    print("\nfused timeline (analyzer clock, ns; host rows carry +/- residual uncertainty):")
    for t, eid, src, txt in sorted(timeline):

Observations. Drift and residual after each change. Questions. With two anchors, why does the residual become zero, and is the alignment better? What does step 3 change in the fused order?

Expected reasoning. Fit quality must be measured with more anchors than parameters.

Solution

With two anchors the line passes through both points exactly: residual 0, but no information about uncertainty — the fit is not better, only unverifiable. Use at least three anchors spread over the window, or hold one out to test. A constant shift of host times is absorbed by the offset a: the fused order does not change (a metamorphic test the pipeline should pass). H2 landing after A2 in the original output is not an inversion but a pair inside u.

Extension. Print each host row as an interval [t − u, t + u] and mark pairs of cross-source events whose intervals overlap as "unordered".

Objective. Localize a regression to one lifecycle stage. Prerequisites. Golden traces; command lifecycle (The Most Important Chapter). Setup. The slow trace's table. Procedure. (3) Write a finding with evidence and falsification. Observations. Only one stage changes. Questions. Why is end-to-end latency alone misleading? Which configuration events should a golden comparison check before any timing diff?

Expected reasoning. Owners are per stage; configuration must be equal before timing comparisons mean anything.

Solution

Owners: 1 controller front end (after the host's doorbell); 2 controller and media; 3 controller DMA and link; 4 controller; 5 controller interrupt generation as configured by the host; 6 host interrupt handling. Only stage 5 exceeds noise (+100.2 µs against 0.1 µs). Finding: "Stage CQE→MSI-X increased from 0.2 to 100.4 µs median (events: all CQE/MSI-X pairs); candidate run contains Set Features Interrupt Coalescing at initialization. HIGH: coalescing holds interrupts at QD1. Falsify: same firmware with the feature at default shows 0.2 µs." End-to-end latency mixes six owners. Before timing: firmware revision, Identify data, every Set Features, number of queues, MSI-X vector mapping, link speed and width, MPS/MRRS, power state settings.

Extension. Compare full distributions (99th percentile per stage), not only medians; a change that only moves the tail often points at a different owner.

Senior forensic lab — Triage a thousand failures

Objective. Design signatures and a triage flow for an overnight regression with 1,000 failing tests. Prerequisites. Everything above. Setup. Summary data (synthetic): 640 failures with signature "cqe_posted:status0 | msix_after_cqe:none | host:timeout | host:abort"; 300 with "cpl:UR on data read | cqe:SCT0/SC04h"; 55 with "no fetch after doorbell | doorbell offset decodes to CQ head"; 5 with no analyzer capture, only "host:timeout".

Procedure. (1) Decide whether the signature design is too coarse or too fine. (2) Rank clusters for investigation. (3) For the 5 unsupported failures, decide what to do. (4) Fill the root-cause template for the largest cluster from the failed trace above.

Observations. Clusters map to different owners. Questions. Could the 640 be two bugs? What would show it?

Expected reasoning. Signatures group by mechanism; each cluster still needs its own falsification.

Solution

Signatures built from layer-level facts are appropriately coarse; check fineness by sampling three members per cluster and confirming the same first abnormal event. Rank by size and by blast radius: 640 (lost interrupts; host interrupt management), 300 (DMA translation; host IOMMU/driver mapping, as in the reference case), 55 (doorbell stride; a custom driver path). The 5 go to an "insufficient evidence" bucket with a collection request; they are not assigned to the nearest cluster. The 640 could be two bugs if MSI-X table snapshots differ (some masked, some unmasked with no message): add "msix_mask" to the signature facts and re-cluster. Eliminated controller bug (masked vector explains silence; pending bit set), coalescing (none configured), filter (audit clean). Most likely host left vector 1 masked. Confidence HIGH. Interview

Beginner

  1. Why is one analyzer capture often not enough?

    Model answer

    It sees only the link; driver decisions, device-recorded errors, IOMMU faults and register states live elsewhere.

  2. What is an anchor event?

    Model answer

    An event recorded by two sources with known identity, used to align their clocks.

  3. What is a golden run?

    Model answer

    A versioned, configuration-documented capture of correct behaviour for the same workload.

  4. Why date an absence at its deadline?

    Model answer

    It becomes observable only then; dating it earlier distorts the first abnormal event.

  5. Name three NVMe-side sources of evidence.

    Model answer

    CQE status, Error Information log, SMART/health log, CSTS, telemetry if supported.

Intermediate

  1. How many anchors do you need, and why?

    Model answer

    At least three spread across the window: two fit offset and drift, the rest measure uncertainty.

  2. What makes a good failure signature?

    Model answer

    Layer-level facts (first abnormal event kind, layer, status class, absence pattern) without times, addresses or tags.

  3. Why diff by stage rather than end to end?

    Model answer

    Each stage has one owner; stage diffs localize a change to an owner.

  4. What links an AER error to a packet in the capture?

    Model answer

    The AER Header Log holds the failing TLP's header; match it to the captured TLP.

  5. What does a set PBA bit with a masked MSI-X vector mean?

    Model answer

    The device had an interrupt to send but was prohibited by the mask, so it recorded it as pending.

Advanced

  1. Two cross-source events are 20 µs apart; u = 45 µs. What do you report?

    Model answer

    Their order is unknown; any causal claim must rest on identity and mechanism, not order.

  2. How do you test the pipeline's alignment?

    Model answer

    Inject known skew and drift; shift host times metamorphically; hold out anchors; results must be stable or flagged.

  3. Separate "lost interrupt" from "controller stall" in one sentence of evidence.

    Model answer

    A posted CQE without an MSI-X is a lost or suppressed interrupt; no CQE at all is a stall or earlier failure.

  4. Why is a missing Error Information log entry weak evidence?

    Model answer

    What the controller records, and for how long, is implementation-dependent and the log is finite.

  5. What goes in a reproducibility bundle?

    Model answer

    Input hashes, pipeline and rule versions, alignment parameters, configuration, outputs and their hashes.

Senior

  1. Design the failure hook for a validation farm.

    Model answer

    On failure, before any reset: collect logs, registers, AER, IOMMU faults, tracepoints, capture export; hash; bundle; compute signature; route by cluster owner.

  2. A cluster of 640 failures is assigned to firmware. What do you check first?

    Model answer

    That sampled members share the first abnormal event and that its owning layer is firmware; lost-interrupt clusters often belong to host interrupt management.

  3. How do you keep golden runs trustworthy?

    Model answer

    Version them with full configuration, re-record on any config change, review their own absence of findings, and never compare across configurations.

  4. When is "root cause: UNKNOWN" the right report?

    Model answer

    When candidates remain that the evidence cannot separate; report the ranking and the collection plan that would.

  5. How do you stop the template becoming a box-filling exercise?

    Model answer

    Require evidence IDs per field, eliminated causes with their eliminating evidence, and a falsification test reviewed by someone outside the owning team.

Quiz

  1. The fitted line passes exactly through both anchors. What does that tell you about alignment quality?

    • It is perfect
    • Drift is zero
    • Nothing: two points always fit; uncertainty is unmeasured
    • The host clock is the analyzer clock
    Answer and reasoning

    Two parameters, two points: zero residual by construction. Add anchors.

  2. Which stage owns the slow trace's regression?

    • Doorbell → fetch
    • Fetch → first data
    • MSI-X → head doorbell
    • CQE → MSI-X
    Answer and reasoning

    Only stage 5 changed, by about 100 µs, matching a coalescing configuration.

  3. Which signature fact is a bad choice?

    • First abnormal event kind
    • The tag of the failing request
    • Owning layer
    • Absence pattern
    Answer and reasoning

    Tags vary run to run; including them makes every failure unique.

  4. In the failed trace, why is the controller not the first suspect?

    • It posted a successful CQE and its vector was masked with the pending bit set
    • Controllers never fail
    • The kernel said so
    • The CQE had status 04h
    Answer and reasoning

    The device behaved as PCIe requires for a masked vector.

  5. Why record host logs with monotonic rather than wall-clock timestamps?

    Model answer

    Wall-clock time can jump (synchronization, manual changes); monotonic time is continuous within a boot, so a linear fit is meaningful.

  6. Name the evidence that would decide the ambiguous trace.

    Model answer

    Device and root-port AER status (Completion Timeout), CSTS.CFS, Error Information log, IOMMU faults for the PRP-listed IOVAs, a capture extending past the host timeout.

  7. What is the metamorphic test for alignment?

    Model answer

    Shift all host times by a constant: offset absorbs it, fused order and findings are unchanged.

  8. Why must eliminated causes be listed with evidence?

    Model answer

    So reviewers can check the elimination; an unlisted alternative is unexamined, not excluded.

  9. Which document defines the AER registers whose snapshot you collect?

    Model answer

    The PCI Express Base Specification (Advanced Error Reporting capability).

Teach-back

  1. To a child: why did the detective need the fire bell?

    Model explanation

    "Everyone's clock was a bit wrong, but everyone heard the bell at the same moment. So the bell tells us how wrong each clock is, and then we can put all the notes in the right order."

  2. To a junior engineer: explain the failed trace without blaming the SSD.

    Model explanation

    "The SSD fetched the command, did it and wrote a good CQE. Then it should have sent MSI-X vector 1 and didn't. The MSI-X table shows vector 1 was masked by the host with a pending interrupt waiting — exactly what PCIe says a device must do. So the first abnormal event is the missing interrupt, and the question is why the host left the vector masked."

  3. To a senior engineer: argue for alignment uncertainty in every forensic report.

    Model explanation

    "Cross-source order is our most persuasive and most fragile claim. Without u, a 20 µs inversion inside a 45 µs band reads as causality and moves bugs between teams. With u, the report states which orders are known, which are not, and rests causation on shared identifiers and mechanism. It costs one fit per source and stops a class of escalations."
