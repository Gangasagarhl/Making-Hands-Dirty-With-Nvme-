Why this part exists

Reading about a feature and diagnosing it are different skills. You can recite that Advanced Error Reporting (AER) has a Header Log and still freeze when someone hands you sixteen bytes of hexadecimal and asks "which device sent this?". You can draw the Zoned Namespace (ZNS) state diagram and still not know which evidence proves that a failed write was the host's fault rather than the drive's.

This part closes that gap. It turns sections 43 to 50 of the course's master specification — the "feature labs" — into laboratories you actually work through. Each lab gives you inputs (synthetic traces, register snapshots, logs, topologies), asks diagnostic questions, and hides a worked solution that reasons from evidence rather than announcing an answer.

Learning objectives

  • Inject faults into a simulated NVM Express (NVMe) over Peripheral Component Interconnect Express (PCIe) event stream and find the first abnormal event for each fault class.
  • Decode an AER Header Log back into a Transaction Layer Packet (TLP) header and name the requester, the receiver and the implicated transaction.
  • Separate power, link, controller and driver causes of a failure that appears after a low-power period.
  • List every piece of state that a controller reset destroys and that the host must rebuild.
  • Draw a Physical Function / Virtual Function topology and label which behaviour is specification-defined and which is implementation-specific.
  • Diagnose an invalid zoned write from the write pointer, the zone state and the completion status.
  • Compare one NVMe Read over PCIe with the same Read over NVMe/TCP, layer by layer, including failure modes.
  • Study a 2026 feature without fabricating a trace signature it does not have.

The story

A fire brigade does not wait for a real fire to practise. They light a small, controlled fire in a training yard, with a hose ready and an instructor watching. They learn what smoke looks like when it comes from a kitchen and when it comes from wiring. Then, when the real alarm rings, they already know where to look first.

These labs are the training yard. We light small, safe "fires" in a pretend computer — a lost answer, a wrong request, a sleepy drive that will not wake up — and you practise finding where the smoke really started.

A flight simulator lets a pilot experience an engine failure on take-off without risking an aircraft. The simulator does not need to model every rivet; it needs to model the instruments faithfully, because the pilot's job is to reason from instruments. Our synthetic traces, register dumps and logs are the instruments.

A simulator only produces the failures its designer imagined. Real hardware fails in ways nobody scripted: an analog signal-integrity problem, a firmware race, a platform quirk. The labs teach the reasoning; they cannot teach you every failure. They also produce perfectly clean evidence — no capture gaps, no clock skew — unless the lab says otherwise, and real evidence is never that clean (see analyzer limitations).

Lab 1 — Safe simulated error injection

Safe lab Simulation only; no device is touched.

Objective

Inject seven classes of fault into a simulated NVMe-over-PCIe event stream — missing completion, invalid opcode, invalid Physical Region Page (PRP) pointer, Unsupported Request, completion timeout, malformed event and link recovery — and, for each, find the first abnormal event, name its layer, and say what a real system would show.

Skills

  • Reading an event stream as expected-versus-observed.
  • Distinguishing an error reported by a layer from an error caused in that layer.
  • Detecting absences (events that should have happened and did not).
  • Recognising that "abnormal" is not the same as "causal".

Hardware and software required

Any computer with Python 3.8 or later. Standard library only.

Background

Real error injection exists at several levels: PCIe analyzers and jammers can corrupt or drop packets on the wire, some platforms offer firmware-driven error injection, Linux has an AER software injector (aer-inject, a kernel module plus user tool) that fakes error reports without any hardware event, and NVMe controllers in development may expose vendor-specific injection hooks. Each method tests a different part of the chain: a software-injected AER report exercises the operating system's handler but not the device's detection logic. This is why Validation Engineering insists you name what an injection method really tests.

Here we inject at the cheapest level: a toy event generator. It models five 4 KiB Write commands on I/O Submission Queue 1 of the course's lab system (The Most Important Chapter walks the normal path). Each Write moves through: driver writes the 64-byte Submission Queue Entry (SQE) → doorbell Memory Write (MWr) → controller Memory Read (MRd) of the SQE → Completion with Data (CplD) → controller reads the data buffer → media work → 16-byte Completion Queue Entry (CQE) → Message Signalled Interrupt eXtended (MSI-X) write.

Input

"""errinj.py - inject faults into a toy NVMe-over-PCIe event stream (Synthetic, teaching only)."""
import sys

FAULTS = ["none", "missing_completion", "invalid_opcode", "invalid_prp",
          "unsupported_request", "completion_timeout", "malformed_event", "link_recovery"]

def generate(fault="none", victim=3, n=5):
    """Return a list of (time_us, layer, event, cid, detail) for n 4 KiB WRITE commands."""
    ev, t = [], 0.0
    for cid in range(1, n + 1):
        hit = (cid == victim)
        opc = 0x7F if (hit and fault == "invalid_opcode") else 0x01
        prp = 0x2_0000_0003 if (hit and fault == "invalid_prp") else 0x2_0000_0000 + cid * 0x1000
        ev.append((t, "driver", "SQE_WRITTEN", cid, f"opc={opc:02X}h prp1={prp:#x}"))
        if hit and fault == "link_recovery":
            ev.append((t + 0.2, "pcie-phy", "LTSSM", None, "L0->Recovery->L0 (2.1 us)"))
            t += 2.1
        ev.append((t + 0.3, "pcie-tl", "MWr_DOORBELL", None, f"SQ1 tail={cid}"))
        ev.append((t + 1.1, "pcie-tl", "MRd_SQE", cid, "64 B"))
        if hit and fault == "malformed_event":
            ev.append((t + 1.6, "pcie-tl", "CplD_SQE", cid, "len=12 B (expected 64)"))
        else:
            ev.append((t + 1.6, "pcie-tl", "CplD_SQE", cid, "64 B"))
        if hit and fault == "missing_completion":
            t += 10; continue
        if hit and fault == "invalid_opcode":
            ev.append((t + 2.0, "nvme", "CQE", cid, "SCT=0h SC=01h (Invalid Command Opcode)"))
            ev.append((t + 2.4, "pcie-tl", "MWr_MSIX", None, "vector 1")); t += 10; continue
        if hit and fault == "invalid_prp":
            ev.append((t + 2.0, "nvme", "CQE", cid, "SCT=0h SC=13h (PRP Offset Invalid)"))
            ev.append((t + 2.4, "pcie-tl", "MWr_MSIX", None, "vector 1")); t += 10; continue
        ev.append((t + 2.0, "pcie-tl", "MRd_DATA", cid, f"512 B from {prp:#x}"))
        if hit and fault == "unsupported_request":
            ev.append((t + 2.6, "pcie-tl", "Cpl_UR", cid, "Status=UR, no data"))
            ev.append((t + 9.0, "nvme", "CQE", cid, "SCT=0h SC=04h (Data Transfer Error)"))
            ev.append((t + 9.4, "pcie-tl", "MWr_MSIX", None, "vector 1")); t += 70; continue
        elif hit and fault == "completion_timeout":
            ev.append((t + 50002.0, "pcie-aer", "CTO", cid, "device logged Completion Timeout"))
            t += 50010; continue
        else:
            ev.append((t + 2.6, "pcie-tl", "CplD_DATA", cid, "512 B (1 of 8)"))
            ev.append((t + 60.0, "media", "PROGRAM_DONE", cid, "write buffered/programmed"))
            ev.append((t + 61.0, "nvme", "CQE", cid, "SCT=0h SC=00h (Success)"))
        ev.append((t + 61.4, "pcie-tl", "MWr_MSIX", None, "vector 1"))
        t += 70
    ev.sort(key=lambda e: e[0])
    return ev

if __name__ == "__main__":
    f = sys.argv[1] if len(sys.argv) > 1 else "none"
    if f not in FAULTS:

Step 3 — Automate the detection

"""detect.py - find the first abnormal event per command (Synthetic, teaching only)."""
import sys
from errinj import generate, FAULTS

EXPECTED = ["SQE_WRITTEN", "MRd_SQE", "CplD_SQE", "MRd_DATA", "CplD_DATA", "CQE"]

def first_abnormal(events):
    findings = []
    seen = {}
    for t, layer, name, cid, detail in events:
        if name in ("Cpl_UR", "CTO", "LTSSM"):
            findings.append((t, layer, name, detail))
        if cid is None:
            continue
        seen.setdefault(cid, []).append(name)
        if name == "CplD_SQE" and "64 B" not in detail:
            findings.append((t, layer, "MALFORMED_SQE_FETCH", detail))
        if name == "CQE" and "SC=00h" not in detail:
            findings.append((t, layer, "ERROR_STATUS", f"cid={cid} {detail}"))
    for cid, names in seen.items():
        if "CQE" not in names:
            last = names[-1]
            findings.append((float("inf"), "nvme", "NO_CQE", f"cid={cid} last seen={last}"))
    findings.sort(key=lambda f: f[0])
    return findings

if __name__ == "__main__":
    for f in FAULTS:
        res = first_abnormal(generate(f))
        first = res[0] if res else None
        print(f"{f:20s} -> {first}")

Observation

The detector reports, for each fault, its earliest finding. Notice three things: the missing completion is reported at time "infinity" (an absence has no timestamp of its own); the completion timeout is reported 50 ms after the real deviation; and link recovery is flagged even though every command succeeds.

Challenge

Extend detect.py so that it finds absences with a timestamp: if a MRd_DATA has no matching CplD_DATA or Cpl_UR within 10 µs, report "missing data completion" at the MRd time plus 10 µs. Then re-run the completion_timeout case.

Hint

Keep a dictionary of outstanding data reads keyed by CID with their issue time. On each later event, check whether any outstanding read has aged past the window. Real analyzers do the same with the PCIe Tag instead of the NVMe CID, because the Tag is what links a completion to its request on the wire.

Solution

Q1. The last known controller action is the CplD of the SQE fetch at 141.6 µs: the controller received the command. Nothing after it — no data read, no CQE. Evidence supports "command fetched, not progressed"; it weakens "driver never submitted" and "doorbell lost". The next place to look is inside the controller (firmware logs, vendor telemetry) or at a resource the command waits on. A host-side cause remains possible only if the host could block the controller (for example an interrupt-only failure is ruled out here, because no CQE was written at all).

Q2. The true first abnormal event is the absence of a completion for the data MRd issued at 142.0 µs. The completion timer in the device only fires much later (PCIe completion-timeout ranges are configurable through the Device Control 2 register and are in the microsecond-to-second range — check the exact ranges in the PCI Express Base Specification, Device Capabilities 2 / Device Control 2). The detector reports the timer, not the deviation. Always back-date an absence to the moment the expected event became overdue.

Q3. The PCIe transaction layer reports first: the Completion carries status UR. The NVMe layer reports to software, as a Data Transfer Error CQE. The NVMe status is a consequence: the controller could not obtain the write data, so it could not complete the command. A senior report says "Data Transfer Error caused by UR on DMA read of PRP1 buffer", not "NVMe error".

Q4. A link entering Recovery and returning to L0 is a normal mechanism (for example to retrain after errors or to change speed); it is abnormal against this golden run but every command succeeds. It becomes relevant if it correlates with replays, with error counters, with latency spikes, or if it repeats. One recovery is a note in the timeline; a recovery every second is a finding.

Q5. For an invalid opcode, check the Opcode byte in Command Dword 0 against the opcodes the controller reports as supported (the Commands Supported and Effects log is the authoritative source). For an invalid PRP, check PRP1's offset: PRP entries must be Dword aligned, so the two least-significant bits must be zero; 0x2_0000_0003 violates that. The status value 13h used in the simulator is the code the course believes is "PRP Offset Invalid" Uncertain — confirm it in the Generic Command Status table of the NVMe Base Specification revision you work with.

Q6. The host (here the host memory subsystem, through the root complex) is the completer of the controller's SQE read; it is responsible for returning 64 bytes. A short completion that is never followed by the rest leaves the controller with a partial command, which it must treat as a transport error. On a real link, a completion whose length disagrees with its Byte Count rules is detected by the receiver as a Malformed TLP or leads to a completion timeout; which one depends on exactly what is wrong — check the completion rules in the PCI Express Base Specification.

What a senior engineer notices

  • Four of the seven faults are first visible below the NVMe layer, yet software would report all of them as "NVMe I/O error" or "timeout". The layer that reports is rarely the layer that failed.
  • Absences dominate real debugging. Most "hangs" are an event that did not happen; you need the expected sequence to see them.
  • The simulator injects one fault at a time. Real failures cascade: a completion timeout often triggers a controller reset, whose own events bury the original deviation.

Lab 2 — AER forensics

Safe lab Decoding supplied data only.

Objective

Given an AER status snapshot, a Header Log, a short trace and the device topology, answer six forensic questions: what error occurred, which TLP is implicated, which requester, which completer or receiver, whether it is symptom or cause, and what additional evidence is needed.

Skills

  • Decoding a TLP header from four Dwords.
  • Placing an AER record in a topology.
  • Joining PCIe evidence with NVMe evidence.

Hardware and software required

Pencil, or the course's TLP Header Decoder.

Background

AER registers and severities are taught in AER and deepened in the AER module; the TLP header fields in TLP Header Anatomy. Review the DW0 field layout before starting.

The AER Extended Capability holds, among others, the Uncorrectable Error Status, Mask and Severity registers, the Correctable Error Status and Mask registers, the Advanced Error Capabilities and Control register (which contains the First Error Pointer) and a Header Log of four Dwords (16 bytes). For error types that log a header, the Header Log holds the header of the TLP that caused the error as received or sent by the function that detected it. That last clause is the whole lab: the function that logs is the detector, which is not necessarily the culprit.

Challenge

The note in the trace says rows 16–19 write past the 4 KiB buffer. Is that a second bug, or a misreading? Re-check the arithmetic before you open the solution.

Hint

Fmt 011 means a four-Dword header with data. Type 00000 with data is a Memory Write. A Memory Write is posted: there is no completer, only a receiver. For the challenge: count the TLPs. Sixteen 256-byte TLPs move 4 KiB; how many data TLPs would a 4 KiB read need, and which addresses would they cover?

Solution

1. What error occurred? The Root Port recorded Poisoned TLP Received. Evidence: its Uncorrectable Error Status shows only that bit and the First Error Pointer points to it. Confidence: CONFIRMED that the port detected a poisoned TLP.

2. Which TLP? The logged header decodes as a 64-bit Memory Write (Fmt 011, Type 00000) with EP = 1, Length 64 Dwords (256 bytes, equal to MPS), to address 0x2_0000_3000. The trace has exactly one such TLP: row 16. Two independent sources (register and trace) share address and requester, so the identification is CONFIRMED.

3. Which requester? Requester ID 0x0100 = bus 01, device 00, function 0: the Lab SSD.

4. Which completer? None: a Memory Write is posted and has no completion. The receiver that detected the poison is the Root Port 00:01.1. Writing "completer = root port" would be a category error a reviewer will catch.

5. Symptom or cause? A poisoned TLP is the device telling the truth about bad data: the endpoint knowingly forwarded data it had marked as corrupted. The PCIe link carried it correctly (no LCRC or replay evidence, no correctable errors). So the AER record is a symptom at the PCIe layer of a data-integrity problem inside the SSD. The NVMe CQE agrees: Unrecovered Read Error, at LBA 0x10_0008. The cause lies in the media or internal data path, below what PCIe can see.

Challenge. It is a misreading — and a planted one. Rows 4–19 are sixteen TLPs: 4 through 15 cover 0x2_0000_2000–0x2_0000_2BFF (twelve TLPs, 3 KiB), and rows 16–19 cover 0x2_0000_3000 onward. That leaves a gap at 0x2_0000_2C00–0x2_0000_2FFF and data beyond 0x2_0000_2FFF. Either the trace excerpt is mislabelled (the elided rows hide the real addresses) or the device wrote outside the buffer. Evidence supports "excerpt problem" only weakly: the note row hides exactly the region in question. Treat it as insufficient evidence and get the unfiltered capture. If the device truly wrote outside the 4 KiB PRP1 page, that is a second, more serious bug (and with the IOMMU enabled, a write outside a mapped page would normally produce an IOMMU fault in the host log — check for it). This challenge exists to teach that an annotation in a trace is a claim, not evidence.

6. Additional evidence needed. (a) The unfiltered capture of rows 7–19 to settle the address question. (b) The device's SMART / Health log and Error Information log over time: is this one LBA, or a growing number? (c) A re-read of LBA 0x10_0008 with the same and with a different transfer size: a repeatable failure points to media; an intermittent one to an internal buffer or path. (d) Vendor telemetry, if available, to see whether the error was detected by internal ECC on the media or on an internal memory. (e) Host OS log for the IOMMU and for the driver's reaction (did it retry? did it reset?).

Root-cause summary. Observed symptom: Read CID 0x0017 failed. First abnormal event: poisoned MWr64 at 59,280 ns, address 0x2_0000_3000. Affected layer reporting: PCIe transaction layer (poison) and NVMe (status). Most likely cause: uncorrectable data error inside the SSD for LBA 0x10_0008 — MEDIUM, pending (c) and (d). Eliminated: link corruption (poison is set deliberately by the sender; no LCRC errors). Fix/workaround: the data is lost from this copy; rely on redundancy above the drive; consider the drive's health trend. Regression test: none for the drive; for the host, verify that the driver surfaces the error to the application rather than returning poisoned data.

What a senior engineer notices

  • The detector, the sender and the root cause are three different things. AER answers "who noticed"; the header answers "who sent"; only further evidence answers "why".
  • Poison is a feature, not a failure, of PCIe: it lets bad data be contained instead of silently consumed. Whether the host consumes poisoned data or contains it is platform-dependent.
  • How the host is notified of a poisoned TLP (error message severity, whether it is an advisory non-fatal case) depends on severity settings and on rules in the PCI Express Base Specification's error-handling sections. Do not guess the message type; read the "Advisory Non-Fatal Error Cases" discussion for your revision.

Failure variants

  • Unsupported Request at the endpoint. The CPU reads BAR0 + 0x5000, beyond the 16 KiB BAR. The endpoint logs Unsupported Request with the header of an MRd32 from the root complex. Now the requester is the host, the completer is the device, and the root cause is host software (a bad offset), not the device that logged it.
  • Completion Timeout at the endpoint. The SSD's MRd for a PRP list receives no completion. Header logging for a request that timed out is not guaranteed in every revision and implementation Version-dependent; you may get the status bit with no header. Fall back to the analyzer's outstanding-tag view.
  • Bad TLP (correctable). A Correctable Error Status with Bad TLP and Replay Timer Timeout, no uncorrectable errors: the Data Link Layer recovered. Link quality is the subject, not data integrity — see DLLP.

"""zns_warehouse.py - a toy zoned namespace (Synthetic, teaching only; not the ZNS state machine in full)."""

ZONE_SIZE = 64          # LBAs per zone (toy value)
WRITABLE = {"Empty", "Implicitly Opened", "Explicitly Opened", "Closed"}

class Zone:
    def __init__(self, zslba):
        self.zslba, self.wp, self.state = zslba, zslba, "Empty"

    def write(self, slba, nlb):
        if self.state == "Full":
            return "Zone Is Full"
        if self.state not in WRITABLE:
            return f"Zone is {self.state}"
        if slba != self.wp:
            return f"Zone Invalid Write (SLBA {slba - self.zslba:+d}, WP {self.wp - self.zslba:+d})"
        if slba + nlb > self.zslba + ZONE_SIZE:
            return "Zone Boundary Error"
        self.wp += nlb
        if self.wp == self.zslba + ZONE_SIZE:
            self.state = "Full"
        elif self.state != "Explicitly Opened":
            self.state = "Implicitly Opened"
        return "Success"

    def reset(self):
        self.wp, self.state = self.zslba, "Empty"
        return "Success"

zones = [Zone(i * ZONE_SIZE) for i in range(4)]
z = zones[1]
ops = [("write", z.zslba + 0, 8), ("write", z.zslba + 8, 8),
       ("write", z.zslba + 24, 8),          # gap: WP is at +16
       ("write", z.zslba + 16, 48),         # fills the zone
       ("write", z.zslba + 64 - 8, 8),      # zone already full
       ("reset", None, None), ("write", z.zslba, 8)]
for op, slba, nlb in ops:
    result = z.reset() if op == "reset" else z.write(slba, nlb)
    where = "" if slba is None else f" SLBA=ZSLBA{slba - z.zslba:+d} NLB={nlb}"

Solution

Q1. The write pointer was at ZSLBA + 16; the write started at ZSLBA + 24, leaving a gap. ZNS requires a Write to start at the write pointer, so the controller rejects it with the status the ZNS specification names "Zone Invalid Write" (look up its value in the ZNS command set's status tables; the simulator only uses the name).

Q2. Host bug, with HIGH confidence: the zone descriptor (from Report Zones immediately before) shows the write pointer at +16, the SQE shows SLBA +24, and the zone state is a writable state. The device is doing exactly what the specification requires. A device bug would show a write pointer that disagrees with completed writes (for example, two successful 8-LBA writes yet a write pointer at +24).

Q3. Both target the same LBA. Whichever the controller executes first succeeds and advances the pointer; the other now starts behind the pointer and fails. Zone Append lets the controller choose the LBA, so many writers can append concurrently; each learns its LBA from the completion.

What a senior engineer notices

  • Most ZNS "device errors" in the field are host ordering errors. The write pointer is the oracle: always fetch zone descriptors into the evidence bundle.
  • Open and active zone limits are device-reported resources; exceeding them produces "Too Many Open Zones" / "Too Many Active Zones" status, which look like random failures under parallel load.

Failure variants

  • Zone goes Read Only or Offline after media wear: the state changes without host action. Health logs and the zone descriptor are the evidence.
  • Finish Zone issued, then a write: fails because the zone is Full.

  • There is no "PCIe trace" of NVMe/TCP. The equivalent evidence is a packet capture plus target-side logs.

Failure variants

  • Header digest mismatch: the receiver detects corruption above TCP (TCP's own checksum passed). Suspect a NIC offload or a middlebox.
  • Keep Alive timeout while I/O is flowing: a target that does not count I/O as liveness, or a host that stops sending Keep Alive under load.

Quiz

  1. A Root Port's AER Header Log contains a 64-bit Memory Write header with Requester ID 0x0100. Which statement is correct?

    • The Root Port sent the TLP and the endpoint completed it.
    • The endpoint 01:00.0 sent the TLP and the Root Port detected the error.
    • The endpoint detected the error in its own transmitter.
    • The header proves the endpoint's firmware is faulty.
    Answer and reasoning

    The Header Log records the header of the TLP that caused the error as seen by the detecting function. The Requester ID identifies the sender. Writes are posted, so nothing "completes" them, and the header says nothing about why the sender sent it.

  2. In the error-injection lab, why is the completion-timeout fault reported 50 ms after the real deviation?

    Answer

    The deviation is an absence (no completion to a data MRd). It becomes visible only when a timer expires. Back-date absences to when the expected event became overdue.

  3. Which reset leaves the MSI-X table and Bus Master Enable untouched?

    • Controller Level Reset via CC.EN 1→0
    • Function Level Reset
    • Conventional (fundamental) reset
    • Removing slot power
    Answer and reasoning

    CC.EN is an NVMe controller control; PCIe function state lives in configuration space and is reset only by PCIe-level resets.

  4. After a low-power period, the analyzer shows no doorbell write at all for the timed-out command. Which owner is most likely?

    • The link
    • The controller
    • The host driver or OS power management
    • The NAND
    Answer and reasoning

    If the host never rang the doorbell, the device could not know about the command. Evidence (absence of MWr) supports a host-side cause.

  5. VF Routing ID: PF at 0x0100, First VF Offset 1, VF Stride 1. What is VF 4's RID?

    Answer

    0x0100 + 1 + 3 × 1 = 0x0104.

  6. A ZNS Write fails with "Zone Invalid Write". The zone descriptor shows the write pointer at ZSLBA+32 and the Write's SLBA is ZSLBA+40. Whose fault is it, most likely?

    • The host's: it did not write at the write pointer
    • The device's: it lost eight LBAs
    • The link's
    • Undeterminable
    Answer and reasoning

    The device behaved as required. Only if completed writes disagree with the write pointer would the device be suspect.

  7. Why is there no doorbell in NVMe/TCP?

    Answer

    The host pushes the command in a capsule over the connection; its arrival is the notification. A doorbell exists in the PCIe transport because the controller must be told to pull commands from host memory.

  8. Which of the following can a PCIe analyzer show directly for NVMe 2.4 rate limiting?

    • The rate-limit enforcement decision per command
    • The admin command that configures it, with an opaque or decodable payload
    • The controller's internal token bucket
    • Nothing at all, ever
    Answer and reasoning

    Configuration travels as an admin command (class 2); enforcement is an effect over time (class 3). Internal mechanisms are invisible.

  9. Is a poisoned TLP evidence of a bad link?

    Answer

    No. Poison is set deliberately by the sender to mark data it knows is bad; link corruption is caught by LCRC and replay. A poisoned TLP points at the data source.

  10. What makes an "abnormal" event different from a "causal" one? Use link recovery as your example.

    Answer

    Abnormal means "differs from the golden run". Causal means "its removal prevents the failure". A single Recovery that leaves every command successful is abnormal but not causal; you prove causality by correlation with the failing command and by an experiment that removes it.

Interview questions

  1. (Beginner) What is the difference between a correctable and an uncorrectable PCIe error?

    Model answer

    A correctable error was detected and fixed by hardware without loss of information (for example a Bad TLP recovered by replay); it is logged for link-health monitoring. An uncorrectable error could not be fixed by the link protocol; it is classified fatal or non-fatal by severity settings and may require software recovery.

  2. (Intermediate) You see a Data Transfer Error CQE. What PCIe evidence would you look for?

    Model answer

    Completions with UR or CA status to the controller's DMA reads for that command, completion timeouts in the device's AER, IOMMU faults in the host log for the command's buffer addresses, and poisoned TLPs. I'd match by address range from the command's PRPs and by time.

  3. (Intermediate) What must a driver rebuild after a controller reset?

    Model answer

    Admin queue registers and CC, then the I/O queues via Create commands, any features that do not persist, its own head/tail/phase state; it must zero CQ memory and fail or requeue outstanding commands. PCIe state is untouched by CC.EN reset but must be restored after FLR.

  4. (Advanced) An SSD times out only after idle periods. How do you localise the problem?

    Model answer

    Separate the three mechanisms: ASPM (link), APST (NVMe power states), runtime PM (D-states). Toggle one axis at a time. On an analyzer, check whether the doorbell was sent (host), whether the link retrained (link), whether the controller fetched (controller). Add rail monitoring if the device drops off the bus.

  5. (Senior) A tenant on an SR-IOV VF reports another tenant's data. Walk through your investigation.

    Model answer

    Cheapest first: namespace attachment and controller mapping; then hypervisor buffer reuse with a sentinel-pattern test; then IOMMU logs and analyzer evidence of RIDs on DMA; only then device internals. I'd treat it as a security incident with data handling rules, and I'd state confidence at each step.

  6. (Senior) How would you validate a feature that has no wire signature, such as a rate cap?

    Model answer

    Define observable effects with a specification-derived oracle (throughput within cap over a window, convergence time, independence of other controllers), measure as time series under controlled workloads, and include negative tests (invalid settings rejected). I would not use a packet trace as proof of a rate.
