PCIe link, physical layer and data link layer

Questions 1–16. The interviewer wants to know whether you can picture the wires, do simple bandwidth arithmetic, and explain what the Data Link Layer does for every packet.

  1. [performance] Which link moves more data per second in one direction: PCIe Gen3 x4 or PCIe Gen4 x2? Show the arithmetic.

    Model answer

    They are the same, about 3.94 GB/s per direction before packet overhead. Gen3 signals at 8 GT/s per lane and Gen4 at 16 GT/s per lane, and both use 128b/130b encoding. Gen3 x4: 8 × 128/130 × 4 lanes ÷ 8 bits per byte ≈ 3.94 GB/s. Gen4 x2: 16 × 128/130 × 2 ÷ 8 ≈ 3.94 GB/s. Doubling the rate and halving the width cancel out. Real NVMe throughput is lower still, because every Transaction Layer Packet (TLP) carries header, sequence number and Link CRC (LCRC) bytes, and the link also carries Data Link Layer Packets (DLLPs).

    Strong answer includes: GT/s is transfers per lane, not bytes; encoding efficiency (128/130); per-direction figure because the link is full duplex; a note that protocol overhead lowers the usable figure further.

    Common weak answer: "Gen4 is newer, so Gen4 x2 is faster," or forgetting to divide by 8.

    Learn it in: Chapter 6, Mathematics for Storage and Links.

  2. [concept] PCIe Gen2 runs at 5 GT/s and Gen3 at 8 GT/s, yet Gen3 is described as roughly doubling Gen2's bandwidth. How is that possible?

    Model answer

    The encoding changed. Gen1 and Gen2 use 8b/10b encoding: every 8 data bits are sent as 10 line bits, a 20% overhead, so 5 GT/s gives 4 Gb/s of data per lane (500 MB/s). Gen3 switched to 128b/130b: 128 data bits travel in a 130-bit block, about 1.5% overhead, so 8 GT/s gives about 7.88 Gb/s (about 985 MB/s). The designers chose 8 GT/s instead of 10 GT/s because a lower signaling rate was easier on the channel (board traces, connectors), and the more efficient encoding made up the difference. The tradeoff: 128b/130b needs scrambling to keep enough transitions for clock recovery, rather than the guaranteed transitions of 8b/10b.

    Strong answer includes: the two encodings and their overheads; the numbers per lane; why the rate was kept lower (signal integrity).

    Common weak answer: "They made it more efficient," with no mention of encoding, or claiming Gen3 runs at 10 GT/s.

    Learn it in: Chapter 6, Module 07.

  3. [concept] A PCIe lane carries data on differential pairs and has no separate data clock wire. How does the receiver know when to sample each bit, and what is the 100 MHz reference clock for?

    Model answer

    The clock is embedded in the data. The receiver uses clock and data recovery (CDR) circuitry that locks onto the transitions in the incoming bit stream; the encoding (8b/10b) or scrambling (128b/130b) guarantees there are enough transitions to stay locked. The 100 MHz reference clock (REFCLK) is not used to sample data bits; each side multiplies it up in a phase-locked loop to generate its transmit clock. In the common-clock arrangement both ends share the same reference, so their frequencies match exactly; configurations with separate references also exist; small frequency differences are absorbed by SKP (clock compensation) ordered sets, which separate-reference modes send more often. Differential signaling (two wires carrying opposite polarities) rejects common noise and allows low voltage swings at high speed.

    Strong answer includes: embedded clock and CDR; transitions guaranteed by encoding or scrambling; REFCLK as a frequency reference, not a sampling clock; why differential pairs.

    Common weak answer: "The 100 MHz clock clocks the data," which cannot be true at 16 GT/s.

    Learn it in: Chapter 5, Module 07.

  4. [tool] On the Lab SSD you see the lines below (illustrative, abbreviated lspci -vvv output). What do they tell you, and what is the very next thing you check?

    LnkCap: Port #0, Speed 16GT/s, Width x4, ASPM L1, Exit Latency L1 <8us
LnkSta: Speed 8GT/s (downgraded), Width x4 (ok)
    Model answer

    Link Capabilities (LnkCap) says the SSD can do 16 GT/s (Gen4) at x4. Link Status (LnkSta) says the link actually trained at 8 GT/s (Gen3) at full width. The bandwidth is roughly halved. A link trains to the highest rate both ends support and can sustain, so the next check is the other end: run lspci -vvv -s 00:01.1 and read the root port's LnkCap and its Link Control 2 Target Link Speed. If the root port (or a platform firmware setting) is limited to Gen3, the link is behaving correctly. If both ends say 16 GT/s, suspect signal integrity: a riser, a poorly seated card or a long channel can make the link fall back to a lower speed, often accompanied by correctable errors in Advanced Error Reporting (AER).

    Strong answer includes: LnkCap versus LnkSta; checking the partner; "trained speed is a negotiation"; signal integrity as the second hypothesis, with evidence to look for.

    Common weak answer: "The SSD is broken," or reading only the SSD's side.

    Learn it in: Chapter 9, Chapter 69.

  5. [concept] Name the three PCIe layers and say what each one does to a single 4-byte doorbell write on its way from the root port to the SSD.

    Model answer

    Transaction Layer: builds the Memory Write TLP: a 3-doubleword header (Fmt/Type for a 32-bit address memory write, Length = 1, Requester ID, byte enables, address BAR0 + 0x1008) plus one doubleword of data. It also checks there are enough Posted flow-control credits at the receiver before sending. Data Link Layer: adds a 12-bit sequence number in front and a 32-bit LCRC behind, keeps a copy in the replay buffer until the SSD acknowledges it, and replays it if a NAK arrives or the replay timer expires. Physical Layer: frames the packet, scrambles and encodes it (128b/130b at Gen4), stripes the bytes across the four lanes and drives them onto the differential pairs. On the SSD the same layers run in reverse: Physical decodes, Data Link checks the LCRC and sequence and sends an ACK, Transaction delivers the write to the doorbell register.

    Strong answer includes: one concrete action per layer for this specific packet; the replay buffer; the receiver's symmetric path and the ACK.

    Common weak answer: reciting the Open Systems Interconnection (OSI) model, or putting the LCRC in the Transaction Layer.

    Learn it in: Chapter 7, Chapter 15.

  6. [trace] Read this Data Link Layer excerpt (synthetic). After row 4, which TLPs can the root port delete from its replay buffer?

    #DirTime (ns)TypeFieldsMeaning
    1RC→Dev0TLPSeq=0x10A MWr32 Addr=0xFE60_1008SQ1 tail doorbell
    2RC→Dev40TLPSeq=0x10B MWr32 Addr=0xFE60_100CCQ1 head doorbell
    3RC→Dev95TLPSeq=0x10C MWr32 Addr=0xFE60_1010SQ2 tail doorbell
    4Dev→RC310DLLPAck AckNak_Seq_Num=0x10B?
    Model answer

    TLPs 0x10A and 0x10B. An ACK carrying sequence number N acknowledges every TLP up to and including N, so one ACK can cover several TLPs (receivers coalesce ACKs to save link bandwidth). TLP 0x10C stays in the replay buffer until a later ACK with 0x10C or higher arrives, or until the replay timer expires and the root port retransmits it. Nothing here is abnormal: a 0x10C that is not yet acknowledged 215 ns after it was sent is normal.

    Strong answer includes: "up to and including"; ACK coalescing; why 0x10C is not yet a problem; the replay timer as the safety net.

    Common weak answer: "Only 0x10B is acknowledged," treating ACKs as one-per-TLP.

    Learn it in: Chapter 15, Module 16.

  7. [trace] The SSD has sent TLPs with sequence numbers 0x2E, 0x2F, 0x30 and 0x31. The root port answers with a NAK carrying AckNak_Seq_Num = 0x2F. What happens next, and what does the NAK tell you about the link?

    Model answer

    The NAK says: "everything up to and including 0x2F arrived correctly; something after that did not." The SSD purges 0x2E and 0x2F from its replay buffer and retransmits 0x30 and 0x31, in order. The receiver discards anything it receives out of sequence until the replay arrives. A NAK is normally caused by a TLP that failed its LCRC check or arrived with a bad sequence number, so it is evidence of a bit error on the link in the SSD-to-host direction. One NAK is harmless and invisible to software except as a correctable error (for example Bad TLP logged by the receiver). Many NAKs point at signal integrity and cost bandwidth.

    Strong answer includes: correct purge and replay set (0x30 onward); which direction had the error; correctable-error logging; that the Transaction Layer and NVMe never see the bad copy.

    Common weak answer: "It resends 0x2F," or "the data is lost."

    Learn it in: Chapter 15, Module 16.

  8. [concept] What is a Data Link Layer Packet (DLLP)? Give three things DLLPs are used for, and say whether a PCIe switch forwards them.

    Model answer

    A DLLP is a small, fixed-size packet (6 bytes in the classic non-Flit format: 4 bytes of content plus a 16-bit CRC) that the Data Link Layers of the two ends of one link exchange to manage that link. Uses: ACK and NAK to acknowledge TLPs; flow control (InitFC during link bring-up to advertise buffer space, UpdateFC to return credits); power management (for example the handshakes for entering L1); and vendor-specific uses. DLLPs are link-local: a switch does not forward them. Each link between the root port and the switch, and between the switch and the SSD, has its own DLLP conversation. That is why an analyzer placed on the SSD's link sees only that link's ACKs and credits.

    Strong answer includes: link-local; three distinct uses; not carrying NVMe data; consequence for analyzer placement.

    Common weak answer: "A smaller TLP," or saying DLLPs carry interrupts.

    Learn it in: Chapter 15, Module 15.

  9. [performance] PCIe flow control counts credits in Header and Data units. How many Posted Header and Posted Data credits does each of these consume at the receiver: (a) a 4-byte doorbell write, (b) a Memory Write carrying 256 bytes of read data, (c) a 64-byte Memory Read request?

    Model answer

    One data credit covers 4 doublewords (16 bytes), and each TLP header uses one header credit of its type. (a) Doorbell: 1 Posted Header credit and 1 Posted Data credit (4 bytes round up to one 16-byte unit). (b) 256-byte write: 1 Posted Header and 256 ÷ 16 = 16 Posted Data credits. (c) A Memory Read is non-posted and has no payload, so it uses no Posted credits at all: it consumes 1 Non-Posted Header credit and no data credits. The 64 bytes it asks for come back as a completion, which uses Completion credits at the SSD on the return path (an endpoint is required to advertise infinite completion credits, because it must always be able to accept completions for reads it issued).

    Strong answer includes: the 16-byte data unit; three credit types (Posted, Non-Posted, Completion), each with header and data; reads consume Non-Posted credits, not Posted.

    Common weak answer: counting credits in bytes, or charging a read for 64 bytes of data credit.

    Learn it in: Chapter 16, Module 17.

  10. [concept] Why does PCIe need credit-based flow control at all, when the Data Link Layer already retransmits damaged packets?

    Model answer

    They solve different problems. Replay recovers from corruption: a packet arrived damaged. Flow control prevents overflow: a packet arriving when the receiver has no buffer space for it. With credits, the transmitter knows in advance how much space the receiver has for each type of packet and simply does not send until it has enough credits. Without it, a full receiver would have to drop packets, and dropping a good packet would trigger replays that waste bandwidth and could repeat forever. Credits are kept per type (Posted, Non-Posted, Completion) so that, for example, a flood of reads cannot block writes from making progress, which the ordering rules depend on.

    Strong answer includes: corruption versus overflow; credits checked before sending; separate pools per type and why.

    Common weak answer: "To control the speed of the link."

    Learn it in: Chapter 16.

  11. [troubleshoot] A newly installed NVMe SSD does not appear in lspci at all. List the checks you would make, in order, from the physical layer up.

    Model answer
    1. Power and seating: is the slot powered, is the card fully seated, is an M.2 drive's key compatible and screwed down?
    2. Platform configuration: is the slot enabled in firmware setup, and does an x16 slot holding a multi-drive adapter need bifurcation enabled (see question 12)?
    3. Link training: does the root port above the slot show the link up? Read its Link Status: the Data Link Layer Link Active bit (if supported) and the negotiated width. Kernel logs from pcieport may show the link failing to train or a "link down" message.
    4. Reset and clock: on a custom board, check that PERST# is released and that the reference clock is present; without them the device never leaves the Detect state of the Link Training and Status State Machine (LTSSM).
    5. Enumeration: if the link is up but the device is missing, try a rescan (echo 1 > /sys/bus/pci/rescan) and check whether firmware assigned bus numbers to that root port.

    Only after the device is in lspci does it make sense to look at the NVMe driver.

    Strong answer includes: bottom-up order; reading the root port, since the missing device cannot be read; bifurcation as a common platform cause.

    Common weak answer: "Reinstall the NVMe driver." The driver plays no part in whether a device is enumerated.

    Learn it in: Chapter 8, Chapter 17, Chapter 69.

  12. [architecture] What is lane bifurcation, and why might a four-drive M.2 adapter card in an x16 slot show only one SSD?

    Model answer

    Bifurcation means configuring one wide root port (for example x16) as several narrower, independent root ports (for example four x4 ports). Each x4 port trains its own link and can enumerate its own device. A simple passive four-drive adapter just routes lanes 0–3, 4–7, 8–11 and 12–15 to the four drives; it has no switch. If the platform leaves the slot as a single x16 port, the port trains with the drive on lanes 0–3 as a x4 link and the other three drives have no root port to talk to. The fix is to set the slot to x4x4x4x4 in platform firmware, or to use an adapter with a PCIe switch on it, which does not need bifurcation. Bifurcation support is platform-dependent.

    Strong answer includes: one link per root port; passive adapter versus switch adapter; the firmware setting; platform dependence.

    Common weak answer: "Three of the drives are dead."

    Learn it in: Chapter 5, Module 03.

  13. [troubleshoot] The Lab SSD trains at 16 GT/s but only x2, although both ends report x4 in Link Capabilities. What could cause it and how would you narrow it down?

    Model answer

    During training, both ends exchange training sets on every lane and agree a width from the lanes that work. If two lanes fail (a damaged pin, contamination in the connector, a broken trace on a riser or cable, or a lane-mapping error on a custom board), the link can still come up at a narrower width rather than not at all. Narrowing it down: reseat the card; move it to a different slot or remove the riser and see whether the width follows the card or the slot; check AER correctable-error counters, which often climb on a marginal lane; compare with a known-good SSD in the same slot. On a custom board, check the lane routing and polarity in the schematic. Firmware settings that force a width are rare but worth ruling out.

    Strong answer includes: width negotiated per lane; "does it follow the card or the slot" as the discriminating experiment; related error counters.

    Common weak answer: "The SSD is a x2 device," which contradicts its Link Capabilities.

    Learn it in: Chapter 9, Module 09.

  14. [concept] What are lane reversal and polarity inversion, and why does the NVMe driver never need to know about them?

    Model answer

    Polarity inversion: the positive and negative wires of a differential pair are swapped on the board. The receiver detects it from the inverted training sets during link training and simply inverts the bits. Lane reversal: lane 0 on one end is wired to lane 3 (on a x4) of the other end, which makes board routing easier. The ends detect the reversed numbering during the Configuration phase of training and remap lanes. Both are handled entirely in the Physical Layer during LTSSM training, before any TLP flows, so the Transaction Layer, the NVMe controller and the driver see a normal link. Support for lane reversal is optional on some components, so a board designer must check the parts used.

    Strong answer includes: what each is; detected during training; invisible above the Physical Layer; optional support caveat.

    Common weak answer: confusing the two, or saying the driver must reorder data.

    Learn it in: Chapter 8, Module 08.

  15. [concept] What are the link power states L0, L0s and L1 under Active State Power Management (ASPM), and why do some latency-sensitive deployments disable ASPM?

    Model answer

    L0 is the normal operating state. L0s is a light standby that each direction of the link can enter on its own when idle, with a short exit latency. L1 puts both directions to sleep, saves more power and takes longer to exit; L1 substates save more still. Under ASPM, the hardware enters these states by itself when the link is idle, without software asking. The cost is the exit latency: the first doorbell after an idle period must wait for the link to return to L0, which adds microseconds to that I/O. For a latency-sensitive server workload with bursty traffic, that variability can show up in tail latency, so some deployments disable ASPM in firmware or with a kernel parameter. Laptops usually keep it enabled for battery life. The exit latencies a device reports are in its Link Capabilities register; actual behavior is platform-dependent.

    Strong answer includes: hardware-autonomous entry; the latency cost appears on the first access after idle; the power versus latency tradeoff; where the latencies are advertised.

    Common weak answer: "ASPM makes the link slower all the time."

    Learn it in: Chapter 8, Chapter 50.

  16. [architecture] What is the difference between a redriver and a retimer, and which one shows up as an extra participant in link training?

    Model answer

    A redriver is an analog amplifier and equalizer: it boosts and reshapes the signal but does not decode it, so it is invisible to the protocol; it also passes noise along. A retimer recovers the clock and data, then retransmits a clean signal. Because it must understand the bit stream, a retimer takes part in the LTSSM (it is defined in the PCIe Base Specification and must, for example, participate in equalization), although it is still not a PCIe device that software enumerates. Retimers are common at Gen4 and Gen5 on long channels such as riser cards and backplanes. For debugging, a retimer splits the channel into two electrical segments, which matters when deciding where to probe and how to interpret errors.

    Strong answer includes: analog versus protocol-aware; retimer in training but not enumerated; why they appear at higher speeds.

    Common weak answer: "A retimer is a switch."

    Learn it in: Chapter 5, Module 07.

TLPs and the transaction layer

Questions 17–34. Expect to decode header doublewords by hand. The first doubleword (DW0) of a non-Flit TLP header holds Fmt in bits 31:29, Type in bits 28:24 and Length (in doublewords) in bits 9:0.

  1. [hex] A captured TLP starts with DW0 = 0x4000_0001. Decode Fmt, Type and Length, name the TLP, and say how many header doublewords follow.

    Model answer

    0x40 in the top byte is 0100 0000 in binary. Bits 31:29 (Fmt) = 010: 3-doubleword header, with data. Bits 28:24 (Type) = 00000: memory request. Fmt 010 + Type 00000 = Memory Write with a 32-bit address (MWr32). Length (bits 9:0) = 1: one doubleword (4 bytes) of payload. The header is 3 DW in total, so DW1 (Requester ID, Tag, byte enables) and DW2 (address) follow, then one data DW. On the Lab SSD this is exactly the shape of a doorbell write or a register write from the CPU.

    Strong answer includes: correct bit slicing; Fmt telling both header size and presence of data; Length in DW, not bytes; a guess at what it is in context.

    Common weak answer: reading 0x40 as the Type, or Length as bytes.

    Learn it in: Chapter 11, TLP Header Decoder.

  2. [hex] The Lab SSD sends a TLP with DW0 = 0x6000_0040. What is it and how many bytes does it carry? Is MPS respected?

    Model answer

    Top byte 0x60 = 0110 0000: Fmt = 011 (4-DW header, with data), Type = 00000 (memory). That is a Memory Write with a 64-bit address (MWr64). Length = 0x040 = 64 doublewords = 256 bytes. MPS on the Lab SSD link is 256 bytes, so this is the largest legal write, which is what you expect for read data the SSD streams into a host buffer above 4 GiB (for example 0x2_0000_0000).

    Strong answer includes: 4-DW header because the address is above 4 GiB; 64 DW × 4 = 256 bytes; comparison with MPS.

    Common weak answer: "0x40 bytes = 64 bytes."

    Learn it in: Chapter 11, Module 11.

  3. [spec] A junior engineer's simulation model makes the Lab SSD fetch the Submission Queue Entry (SQE) at 0x1_2340_0000 with DW0 = 0x0000_0010. A colleague says the header should start 0x2000_0010. Who is right?

    Model answer

    The colleague. 0x0000_0010 is Fmt 000 (3-DW, no data), Type 00000: a Memory Read with a 32-bit address (MRd32), Length 16 DW = 64 bytes. A 3-DW header has only 32 address bits, so it cannot express 0x1_2340_0000, which is above 4 GiB. The fetch must use Fmt 001 (4-DW, no data): DW0 = 0x2000_0010, an MRd64 with the full 64-bit address in DW2–DW3. The reverse rule also applies: an address below 4 GiB must use the 3-DW form, which is why doorbell writes to 0xFE60_xxxx are MWr32. A 64-byte read is the right length for one SQE.

    Strong answer includes: both rules (above 4 GiB needs 4 DW; below 4 GiB must use 3 DW); 16 DW = one 64-byte SQE.

    Common weak answer: "Either works, the address is in the header somewhere."

    Learn it in: Chapter 11, Module 11.

  4. [hex] The root complex sends the Lab SSD a TLP whose DW0 is 0x4A00_0010. What kind of TLP is it, and what one other header value lets the SSD know which of its requests it answers?

    Model answer

    0x4A = 0100 1010: Fmt = 010 (3-DW header with data), Type = 01010 (completion). That is a Completion with Data (CplD) carrying 16 DW = 64 bytes, for example the 64-byte SQE the SSD asked for. Completions are routed by ID, not address. DW2 carries the Requester ID (0x0100, the SSD) and the Tag of the original read; the SSD matches the Tag against its table of outstanding reads. The completion also carries a Completion Status, a Byte Count (bytes still to come for this request, including this TLP) and a Lower Address, which let the requester place partial completions correctly.

    Strong answer includes: CplD decode; routing by ID; the Tag as the match key (Requester ID plus Tag form the transaction ID); a mention of Byte Count.

    Common weak answer: "It's matched by address," but completions do not carry the request's full address.

    Learn it in: Chapter 12, Chapter 13.

  5. [coding] Write a small, runnable Python function that takes DW0 of a non-Flit TLP header and returns a name such as "MWr32", "MRd64", "CplD" or "CfgRd0", plus the payload length in bytes.

    Model answer 
    def decode_dw0(dw0: int):
    fmt = (dw0 >> 29) & 0x7
    typ = (dw0 >> 24) & 0x1F
    length_dw = dw0 & 0x3FF
    has_data = fmt in (0b010, 0b011)
    four_dw = fmt in (0b001, 0b011)
    if fmt == 0b100:
        return ("TLP prefix", 0)
    if typ == 0b00000:
        name = ("MWr" if has_data else "MRd") + ("64" if four_dw else "32")
    elif typ == 0b00100:
        name = "CfgWr0" if has_data else "CfgRd0"
    elif typ == 0b00101:
        name = "CfgWr1" if has_data else "CfgRd1"
    elif typ == 0b01010:
        name = "CplD" if has_data else "Cpl"
    elif (typ >> 3) == 0b10:
        name = "MsgD" if has_data else "Msg"
    else:
        name = f"other(Fmt={fmt:03b}, Type={typ:05b})"
    # Length 0 means 1024 DW, but only when the TLP carries data
    nbytes = ((length_dw or 1024) * 4) if has_data else 0
    return (name, nbytes)

for v in (0x4000_0001, 0x6000_0040, 0x2000_0010, 0x4A00_0010, 0x0A00_0000):
    print(hex(v), decode_dw0(v))

    For a read (no data) the function reports 0 payload bytes; the Length field of a read is the amount requested, which you could return separately. The code handles only the common types; I/O requests, locked reads and the full message routing sub-types are left out on purpose, and a real decoder would also check reserved bits.

    Strong answer includes: shifts and masks right; Length 0 meaning 1024 DW for payload-carrying TLPs; separating "requested" from "carried"; stating what is not handled.

    Common weak answer: using Type alone to decide read versus write.

    Learn it in: Chapter 11, Programming Labs.

  6. [coding] Compute the 16-bit Requester ID for (a) the Lab SSD at 01:00.0, (b) the root port at 00:01.1, (c) a second function at 03:00.1. Show the formula.

    Model answer

    Requester ID = Bus (8 bits) in bits 15:8, Device (5 bits) in bits 7:3, Function (3 bits) in bits 2:0, so ID = (bus << 8) | (dev << 3) | fn. (a) 01:00.0 → (1 << 8) | 0 | 0 = 0x0100. (b) 00:01.1 → 0 | (1 << 3) | 1 = 0x0009. (c) 03:00.1 → 0x0300 | 0 | 1 = 0x0301. The PCI domain (segment) number is not part of the ID; on a multi-segment system two devices can share a Requester ID in different segments. With Alternative Routing-ID Interpretation (ARI) the device and function fields merge into an 8-bit function number.

    Strong answer includes: correct packing; the domain not included; ARI as a known exception.

    Common weak answer: concatenating decimal digits ("0x0001") or forgetting the shift of 3.

    Learn it in: Chapter 13, Chapter 17.

  7. [trace] Explain each row of this short excerpt and say what NVMe event it shows.

  9. [concept] Why is a configuration write non-posted when a memory write is posted?

    Model answer

    Configuration writes change how a device or bridge behaves: bus numbers, BAR addresses, Memory Space Enable, Bus Master Enable. Software needs to know a change has taken effect (or failed) before it relies on it, for example before sending memory traffic to a BAR it has just programmed. The completion gives that confirmation and can carry an error status (such as Unsupported Request for a function that does not exist). Memory writes, by contrast, are the high-volume data path; making the sender wait for each one would waste the link. Ordering rules make posted writes safe: a later read to the same device cannot pass an earlier posted write, so software can "flush" posted writes by reading back.

    Strong answer includes: confirmation and error reporting; performance for memory writes; read-back flushing.

    Common weak answer: "Because configuration space is slow."

    Learn it in: Chapter 12, Chapter 18.

  10. [spec] For the doorbell MWr32 with Length = 1, what should First DW Byte Enables and Last DW Byte Enables contain? What would a Length = 1 write with First DW BE = 0x3 mean?

    Model answer

    A full 4-byte doorbell write has First DW BE = 1111b (all four bytes valid) and Last DW BE = 0000b. For a 1-DW request the Last DW BE field must be 0000b, because the first doubleword is also the last. First DW BE = 0011b would write only the two lowest bytes of that doubleword. For an NVMe doorbell that would be a host bug: doorbells are 32-bit registers, and a controller's reaction to a partial write is not something to rely on. Byte enables are how PCIe expresses byte-granular writes even though addresses in the header are doubleword-aligned (the low two address bits are not used as part of the address).

    Strong answer includes: 1111b/0000b; the 1-DW rule for Last BE; byte enables as the byte-level mechanism.

    Common weak answer: "Both 0xF."

  11. [concept] An NVMe Read command makes the SSD send PCIe Memory Writes, and an NVMe Write command makes it send Memory Reads. Explain why this is not a contradiction.

    Model answer

    The two words describe different things. NVMe Read and Write are named from the application's point of view relative to the storage media: Read moves data from the media to the host; Write moves data from the host to the media. PCIe Memory Read and Memory Write are named from the point of view of the requester accessing memory: the SSD, acting as bus master, writes into host memory to deliver read data and reads host memory to collect write data. So an NVMe Read appears on the link as MWr TLPs from the SSD, and an NVMe Write appears as MRd TLPs from the SSD followed by CplD TLPs from the root complex. Keeping the layers' vocabularies apart is the first habit of correct trace reading.

    Strong answer includes: the two points of view; the SSD as requester; the CplD return path for Writes.

    Common weak answer: "The host does a PCIe read from the SSD."

    Learn it in: Chapter 39, Command vs Packet vs Completion.

  12. [concept] Name the four completion status values a beginner should know and give a situation that produces each.

    Model answer
    • Successful Completion (SC): the normal case, such as CplD returning SQE bytes.
    • Unsupported Request (UR): the completer does not support the request or the address does not decode to anything, such as a configuration read to a function number that does not exist, or a memory read to an address no BAR claims.
    • Completer Abort (CA): the completer understood the request but cannot complete it because of an internal error or a rule violation on its side.

    Strong answer includes: four statuses with an example each; CRS only for configuration; the requester's view.

    Common weak answer: listing NVMe status codes instead of PCIe completion statuses.

  14. [performance] The Lab SSD uses 8-bit tags (256 values) and the round trip from issuing a read to receiving its last completion is 2 µs. Each read requests 512 bytes. What is the maximum read bandwidth the SSD can sustain with tags alone, and is that a problem on Gen4 x4?

    Model answer

    At most 256 reads can be outstanding. Each carries 512 bytes, so 256 × 512 = 131,072 bytes can be in flight per 2 µs, giving 131,072 ÷ 2×10⁻⁶ ≈ 65.5 GB/s. A Gen4 x4 link carries about 7.9 GB/s per direction, so tags are not the bottleneck here. The calculation is an application of Little's law (in-flight = rate × latency). Tags become a limit when latency is much higher (for example through switches or remote memory), when request sizes are small, or at Gen5/Gen6 rates; that is why 10-bit tags exist. In practice the device's own outstanding-request limit is often well below 256.

    Strong answer includes: bytes in flight ÷ latency; comparison with link bandwidth; when tags would matter; the device's own limit.

    Common weak answer: "256 tags means 256 × 512 bytes per second."

    Learn it in: Chapter 13, Mathematics for Storage and Links.

  15. [performance] How many MRd requests does the Lab SSD issue to fetch the data for a 4 KiB NVMe Write from a page-aligned buffer, and how many CplD TLPs is the smallest number that can answer each of them?

    Model answer

    MRRS is 512 bytes, so the SSD needs at least 4096 ÷ 512 = 8 MRd64 requests (a device may choose smaller requests, but not larger). Each 512-byte request must be answered with completions no larger than MPS on that direction, 256 bytes, so at least 2 CplD TLPs per request, 16 in total. The root complex may split further, on Read Completion Boundary (RCB) multiples of 64 bytes, so seeing four or eight completions per request is also legal. Requests also must not cross a 4 KiB address boundary, which a page-aligned 4 KiB buffer satisfies. Plus, separately: one MRd for the 64-byte SQE, one MWr for the CQE and one for MSI-X.

    Strong answer includes: MRRS bounds requests, MPS bounds completions; RCB-aligned splitting is legal; the 4 KiB boundary rule.

    Common weak answer: "One read of 4 KiB," or "8 completions" (forgetting MPS).

    Learn it in: Chapter 12, Chapter 40.

  16. [spec] PCIe registers and header fields are often marked "Reserved", "RsvdP" or "RsvdZ". What must a sender write into such bits and what must a receiver do with them?

    Model answer

    For registers: RsvdP (reserved and preserved) means software must keep the value it read when writing back, by read-modify-write; RsvdZ (reserved and zero) means software must write zero. For packet header fields, the general rule is that a transmitter sets reserved bits to zero and a receiver ignores them (unless a later revision has given them a meaning and the receiver supports it). This is what makes forward compatibility work: a newer revision can assign meaning to bits that older devices set to zero and ignore. A practical consequence for decoder authors: do not flag a non-zero reserved bit as an error without checking whether a newer revision defines it.

    Strong answer includes: RsvdP versus RsvdZ; transmit zero, receive ignore; forward compatibility reasoning.

    Common weak answer: "Reserved bits do not matter."

  17. [concept] The CPU reads the NVMe Controller Status register (CSTS) at BAR0 + 0x1C. Describe the TLPs on the link and explain why drivers avoid register reads in the I/O fast path.

    Model answer

    The root complex sends an MRd32 with Length = 1 to 0xFE60_001C, with the root complex's Requester ID and a tag; the SSD returns a CplD with one doubleword of data and the same tag. The CPU core that issued the load stalls (or at least that load cannot retire) until the completion comes back, which takes on the order of a microsecond: a full round trip over the link plus the device's response time. Thousands of these per second would waste CPU time and add latency to every I/O. NVMe's design avoids them: the host only writes doorbells (posted) and learns about progress from CQEs the controller writes into host memory, which the CPU reads at cache speed.

    Strong answer includes: MRd32 + CplD pair; non-posted round trip blocks the core; NVMe's design of write-only fast path.

    Common weak answer: "Reads are just as fast as writes."

    Learn it in: Chapter 19, Chapter 28.

  18. [concept] What do the Traffic Class and the Relaxed Ordering and No Snoop attribute bits in a TLP header do, in one sentence each, and what values do you expect on an ordinary NVMe data write?

    Model answer

    Traffic Class (TC): a 3-bit label that lets a link with several virtual channels separate traffic classes; NVMe traffic normally uses TC0 and most systems map everything to one virtual channel. Relaxed Ordering (RO): tells the fabric this TLP may pass earlier posted writes, which can help performance but must not be set where ordering matters. No Snoop (NS): tells the root complex it need not snoop CPU caches for this access, because software manages coherency itself. On ordinary NVMe data writes you usually see TC0 and NS clear; RO may or may not be set, depending on the device and on whether the platform enables it in the Device Control register. Whether these bits are honored or even permitted is controlled by enable bits the system sets, and their use is implementation-dependent.

    Strong answer includes: one-sentence meanings; enable bits in Device Control; TC0 as the common case; caution that RO must not reorder a CQE ahead of its data.

    Common weak answer: "Traffic Class is the priority of the packet."

    Learn it in: Chapter 14, Chapter 11.

Questions 35–50. Configuration space is where software discovers a device and turns it on; DMA and the Input/Output Memory Management Unit (IOMMU) decide where the device is allowed to reach. Offsets below are from the standard Type 0 configuration header.

  1. [hex] After the NVMe driver loads, the Lab SSD's Command register (configuration offset 0x04) reads 0x0406. Decode it. Which bit would you expect a driver to set before the first admin command, and why?

    Model answer

    0x0406 = bits 1, 2 and 10. Bit 1 is Memory Space Enable: the function responds to memory requests that hit its BARs, so the driver can reach BAR0. Bit 2 is Bus Master Enable: the function may issue its own memory requests, which is what DMA is. Bit 10 is Interrupt Disable: legacy INTx interrupts are turned off, as Linux does when it uses MSI or MSI-X. Bit 0 (I/O Space) is clear, which is normal for an NVMe device. Bus Master Enable must be set before the first admin command: without it the controller is forbidden to fetch the SQE or write the CQE, so the command would simply time out.

    Strong answer includes: all three bits named correctly; Bus Master Enable linked to DMA; Interrupt Disable linked to MSI-X use.

    Common weak answer: "0x0406 means enabled."

  2. [hex] Software reads the 32-bit value at configuration offset 0x00 of 0000:02:00.0 and gets 0xFFFF_FFFF. What does it conclude? And what does 0x5A1E_ABC0 (synthetic) mean if returned instead?

  4. [coding] Firmware writes 0xFFFF_FFFF to BAR0 and BAR1 of the Lab SSD and reads back 0xFFFF_C004 and 0xFFFF_FFFF. Decode the type of BAR and its size, and write a short C function that computes the size of a 64-bit memory BAR from the two values.

    Model answer

    Low bits of BAR0: bit 0 = 0 (memory space), bits 2:1 = 10b (64-bit BAR, so BAR1 holds the upper half), bit 3 = 0 (non-prefetchable). Mask off the four low bits: 0xFFFF_C000. Combined with BAR1 the mask is 0xFFFF_FFFF_FFFF_C000; invert and add one: 0x4000 = 16 KiB, which matches the course's Lab SSD.

    #include <stdint.h>

/* lo, hi: values read back after writing all ones to BAR n and BAR n+1.
   Caller must have checked (lo & 0x1) == 0 and ((lo >> 1) & 0x3) == 0x2. */
uint64_t bar_size64(uint32_t lo, uint32_t hi)
{
    uint64_t mask = ((uint64_t)hi << 32) | (lo & ~0xFULL);
    if (mask == 0)
        return 0;              /* BAR not implemented */
    return ~mask + 1;          /* two's complement gives the size */
}

    Real firmware also disables memory decoding in the Command register while sizing, restores the original values afterwards, and then writes the assigned address (0xFE60_0000 for the Lab SSD).

  5. [coding] The platform's Enhanced Configuration Access Mechanism (ECAM) region starts at physical address 0xE000_0000. At what address does the CPU read the Lab SSD's BAR0 register (offset 0x10)? Write the formula.

    Model answer

    ECAM gives each function 4 KiB of configuration space at address = base + (bus << 20) + (device << 15) + (function << 12) + offset. For 01:00.0, offset 0x10: 0xE000_0000 + 0x0010_0000 + 0 + 0 + 0x10 = 0xE010_0010. The CPU performs an ordinary memory load at that address; the root complex recognizes the ECAM window and turns it into a Configuration Read TLP (CfgRd0 at the target, since the SSD sits directly below the root port). On a system with several PCI segments there is one ECAM region per segment, described by firmware tables.

    Strong answer includes: the shifts (20, 15, 12); the result; that the root complex converts the access into a configuration TLP; segments.

    Common weak answer: using shifts of 8, 3, 0 (that is the Requester ID packing).

  6. [hex] The root port 00:01.1 has a Type 1 header with Primary Bus = 0x00, Secondary Bus = 0x01 and Subordinate Bus = 0x01. What do these tell you, and how is a Type 1 header different from the SSD's Type 0 header?

    Model answer

    A Type 1 header belongs to a bridge (root ports and switch ports appear as PCI-to-PCI bridges). Primary Bus is the bus the bridge sits on (bus 0), Secondary Bus is the bus directly below it (bus 1, where the SSD lives), and Subordinate Bus is the highest bus number anywhere below it (also 1, so nothing is deeper). The bridge forwards configuration requests for buses 1 through 1 downstream. A Type 1 header also has memory and I/O windows (base/limit registers) that decide which addresses it forwards down; the SSD's BAR0 at 0xFE60_0000 must fall inside the root port's non-prefetchable memory window. A Type 0 header belongs to an endpoint such as the SSD and has up to six BARs instead of bus numbers and windows.

    Strong answer includes: meaning of all three bus numbers; bridge windows; the BAR having to fit inside the window.

  12. [concept] With the IOMMU enabled, the PRP entry in a Read command says 0x2_0000_0000. Is that the physical address of the buffer in DRAM? Explain who translates what.

    Model answer

    Not necessarily. With an IOMMU, the driver obtains an I/O virtual address (IOVA) when it maps the buffer for DMA, and it puts that IOVA in the PRP. The SSD emits a Memory Write TLP to 0x2_0000_0000; the IOMMU in the root complex looks up the translation tables for that device (identified by its Requester ID, 0x0100) and turns the IOVA into the real physical address, or blocks the access if no mapping exists or the permission is wrong. The CPU uses yet another address, a kernel virtual address, for the same buffer. So one buffer can have three addresses: virtual for the CPU, IOVA for the device, physical for the memory controller.

  14. [concept] The Linux NVMe driver allocates its queues with a coherent DMA mapping but maps each I/O buffer with a streaming mapping. Why the difference?

    Model answer

    A coherent (consistent) mapping, from dma_alloc_coherent(), is set up once and stays valid; the CPU and the device can both access it at any time and see each other's writes without explicit synchronization calls. That suits Submission and Completion Queues, which both sides touch continuously for the life of the controller. A streaming mapping, from dma_map_sg() or dma_map_page(), maps an existing buffer for one transfer in one direction and is unmapped when the I/O completes; on platforms without hardware cache coherence the map and unmap calls do the cache maintenance. That suits data buffers, which belong to whoever issued the I/O and are only shared with the device for the duration of one command. Using coherent memory for every buffer would be wasteful, and streaming mappings for queues would need a sync call on every access.

    Strong answer includes: lifetime and ownership; the cache maintenance role; which structure gets which mapping.

    Common weak answer: "Coherent is faster."

    Learn it in: Chapter 20, Module 36.

  15. [concept] Why does a Linux driver set a DMA mask, and what happens if a device that can only generate 32-bit addresses is given a buffer at 0x2_0000_0000?

    Model answer

    The DMA mask tells the kernel which addresses the device can generate. An NVMe controller handles 64-bit addresses, so the driver sets a 64-bit mask, and the DMA API can then hand it any IOVA. If a device declares only a 32-bit mask, the DMA API must give it addresses below 4 GiB. With an IOMMU that is easy: it picks an IOVA below 4 GiB and maps it to the real page. Without an IOMMU, the kernel uses a bounce buffer (swiotlb): it copies the data through a buffer below 4 GiB, which costs CPU time and memory bandwidth. If a driver set no correct mask and passed 0x2_0000_0000 to a 32-bit device anyway, the device would truncate the address and DMA into the wrong memory: silent corruption.

    Strong answer includes: mask as a capability statement; IOMMU remapping versus bounce buffering; the corruption risk.

    Common weak answer: "The mask protects memory from the device." That is the IOMMU's job, not the mask's.

    Learn it in: Chapter 20, Module 02.

  16. [troubleshoot] A custom test tool enables the Lab SSD (CC.EN = 1, CSTS.RDY becomes 1), submits Identify, and the command never completes. The Command register reads 0x0002. What is wrong, and what would an analyzer show?

    Model answer

    0x0002 has Memory Space Enable set but Bus Master Enable clear. The tool can reach the registers, so enabling works: CSTS.RDY going to 1 needs no DMA. But to execute Identify the controller must fetch the SQE from host memory (MRd), write 4 KiB of data and the CQE (MWr), and raise an interrupt (MWr). With Bus Master Enable clear the function must not issue any memory requests, so the analyzer would show the host's doorbell MWr32 to 0xFE60_1000 and then nothing from the SSD. Fix: set bit 2 in the Command register before the first command. A good habit is to check the Command register first whenever "doorbell, but no fetch" appears in a trace.

    Strong answer includes: why enable works but commands do not; the expected trace (doorbell, silence); the fix; the general "doorbell but no fetch" pattern.

    Common weak answer: "The SSD firmware hung."

    Learn it in: Chapter 18, Chapter 26, Module 27.

NVMe architecture, registers and initialization

Questions 51–66. The controller registers live in BAR0: Controller Capabilities (CAP) at 00h, Version (VS) at 08h, Controller Configuration (CC) at 14h, Controller Status (CSTS) at 1Ch, Admin Queue Attributes (AQA) at 24h, Admin Submission Queue Base Address (ASQ) at 28h and Admin Completion Queue Base Address (ACQ) at 30h. Expect to decode them.

  1. [hex] The Lab SSD's CAP register reads 0x0040_0830_1401_0FFF. Decode Maximum Queue Entries Supported (MQES), Timeout (TO), Doorbell Stride (DSTRD), and the minimum and maximum memory page sizes.

    Model answer
    • MQES, bits 15:0 = 0x0FFF = 4095. It is a 0's based value, so each I/O queue can have up to 4096 entries.
    • TO, bits 31:24 = 0x14 = 20, in units of 500 ms: the host should wait up to 10 seconds for CSTS.RDY to change after it changes CC.EN.
    • DSTRD, bits 35:32 = 0 (the low nibble of the upper doubleword 0x0040_0830): doorbell stride = 4 << 0 = 4 bytes.
    • MPSMIN, bits 51:48 = 0: 2^(12+0) = 4 KiB. MPSMAX, bits 55:52 = 4: 2^(12+4) = 64 KiB.

    Also visible: bit 16 (Contiguous Queues Required, CQR) = 1, so queues must be physically contiguous; bit 36 (NVM Subsystem Reset Supported) = 1; the Command Sets Supported field (bits 44:37) has bit 37 (NVM command set) and bit 43 set. CAP is a 64-bit register; read it as one 64-bit access or as two 32-bit reads, low half first.

    Strong answer includes: 0's based MQES; TO units; stride formula; page size formula 2^(12 + n).

    Common weak answer: "MQES = 4095 entries" or "TO = 20 seconds".

    Learn it in: Chapter 24, Config Space and NVMe Register Decoder.

  2. [hex] Decode these Version register values: 0x0002_0000, 0x0001_0400, 0x0002_0100. Why should a driver not rely on VS alone to decide which features to use?

    Model answer

    VS has Major in bits 31:16, Minor in bits 15:8 and Tertiary in bits 7:0. 0x0002_0000 = 2.0.0 (the Lab SSD). 0x0001_0400 = 1.4.0. 0x0002_0100 = 2.1.0. A version says which revision the controller claims to comply with, but most features are optional in every revision. A 2.0 controller need not support SGLs, namespace management or any particular log page. Drivers therefore check the specific capability fields (in CAP and in Identify Controller fields such as Optional Admin Command Support and Optional NVM Command Support) for each feature, and use VS mostly to know which fields are defined at all. A 2.4 feature is reported through 2.4-defined fields, not by VS = 2.4 alone.

    Strong answer includes: correct byte fields; "version is not a feature list"; capability fields as the real test.

    Common weak answer: "0x0001_0400 is version 1.04."

    Learn it in: Chapter 24, Chapter 22.

  3. [hex] The driver writes CC = 0x0046_0061. Decode Enable (EN), Command Set Selected (CSS), Memory Page Size (MPS), and the I/O Submission and Completion Queue Entry Sizes (IOSQES, IOCQES).

    Model answer
    • EN, bit 0 = 1: enable the controller.
    • CSS, bits 6:4 = 110b (0x61 = 0110 0001): "all supported I/O command sets", which is allowed because CAP advertises that capability (bit 43). 000b would select just the NVM command set.
    • MPS, bits 10:7 = 0: host memory page size 2^(12+0) = 4 KiB, which must lie between CAP.MPSMIN and CAP.MPSMAX.
    • IOSQES, bits 19:16 = 6: 2^6 = 64-byte SQ entries. IOCQES, bits 23:20 = 4: 2^4 = 16-byte CQ entries.

    Shutdown Notification (SHN, bits 15:14) = 0 and Arbitration Mechanism (AMS, bits 13:11) = 0 (round robin). IOSQES and IOCQES are only needed before I/O queues are created, but drivers usually set them together with EN.

    Strong answer includes: each field with its bits; entry sizes as powers of two; MPS checked against CAP.

    Common weak answer: "IOSQES = 6 bytes."

  4. [hex] What do these CSTS values mean: 0x0000_0000, 0x0000_0001, 0x0000_0003, 0x0000_0009? Which one should make you stop and collect evidence?

    Model answer
    • 0x0: RDY = 0. Controller not ready (disabled, or still becoming ready after EN was set).
    • 0x1: RDY = 1. Ready to accept commands. Normal operation.
    • 0x3: RDY = 1 and Controller Fatal Status (CFS, bit 1) = 1. The controller has hit a fatal internal error and needs a reset.
    • 0x9: RDY = 1 and Shutdown Status (SHST, bits 3:2) = 10b, shutdown processing complete, after the host requested a shutdown through CC.SHN.

    0x3 is the one to stop on: before any reset, save CSTS, the controller's logs if they can still be read (for example the Error Information and telemetry log pages) and the kernel log, because a reset may clear the evidence. A read of 0xFFFF_FFFF is different again: it means the device is not answering at all (for example the link went down), not a CSTS value.

    Strong answer includes: RDY, CFS and SHST bits; collecting evidence before reset; all ones as "no device".

    Common weak answer: treating 0x3 as "ready plus something optional".

  5. [hex] AQA = 0x001F_001F and ASQ = 0x0000_0001_0000_0000. How large are the admin queues, and what alignment rule must ASQ and ACQ obey?

    Model answer

    AQA holds the Admin Submission Queue Size (ASQS) in bits 11:0 and the Admin Completion Queue Size (ACQS) in bits 27:16, both 0's based. 0x01F = 31, so each admin queue has 32 entries: 32 × 64 bytes = 2 KiB for the admin SQ and 32 × 16 bytes = 512 bytes for the admin CQ. ASQ and ACQ hold the base addresses; their low 12 bits are reserved, so each base must be aligned to 4 KiB (the course uses 0x1_0000_0000 for the admin SQ and 0x1_0000_1000 for the admin CQ). The admin queues must be physically contiguous, and these registers must be programmed while the controller is disabled (CC.EN = 0).

    Strong answer includes: 0's based sizes; bytes per queue; 4 KiB alignment; programmed only while disabled.

    Common weak answer: "31 entries."

    Learn it in: Chapter 26, Chapter 24.

  6. [coding] Write pseudocode for bringing up an NVMe controller from power-on to "ready to accept admin commands". Include the timeout.

    Model answer 
    cap = read64(BAR0 + 0x00)

/* 1. Make sure the controller is disabled */
if (read32(BAR0 + 0x14) & 1) {                     /* CC.EN */
    write32(BAR0 + 0x14, read32(BAR0 + 0x14) & ~1)
}
wait_until((read32(BAR0 + 0x1C) & 1) == 0, timeout_ms)   /* CSTS.RDY == 0 */

/* 2. Admin queues: memory already zeroed, 4 KiB aligned */

write64(BAR0 + 0x30, acq_dma_addr)                  /* ACQ */

  8. [architecture] Explain the difference between an NVM subsystem, a controller, a namespace and a port, using a dual-port enterprise SSD as the example.

    Model answer

    The NVM subsystem is the whole product: its non-volatile media, one or more controllers and one or more namespaces, identified by an NVMe Qualified Name (NQN). A port is a physical connection to a host fabric; on a dual-port SSD there are two PCIe ports, typically each going to a different server or a different CPU. A controller is the interface a host talks to: it has its own registers, queues and a controller ID; each port exposes at least one controller. A namespace is a quantity of storage formatted into logical blocks, identified by a namespace ID (NSID), which can be attached to one controller or shared by several. With a shared namespace, both hosts see the same LBAs through different controllers, which is the basis of high availability and multipath (coordination is needed, for example with reservations). A simple consumer SSD collapses all of this into one port, one controller and one namespace, which is why the distinction is often missed.

    Strong answer includes: the four entities and their relationships; shared namespace example; that a simple SSD hides the distinction.

    Common weak answer: "A namespace is a partition."

    Learn it in: Chapter 22, Module 22, Chapter 58.

  9. [spec] Which namespace ID values are valid in an I/O command, and what is special about NSID 0 and NSID FFFFFFFFh?

    Model answer

    A namespace identifier is a 32-bit value. Valid NSIDs for a controller run from 1 to the Number of Namespaces (NN) value it reports in Identify Controller (NN = 32 on the Lab SSD), and an I/O command must name an active namespace attached to that controller. NSID 0 is not a valid namespace; it is used in commands that do not refer to any namespace (Identify Controller, for example, is sent with NSID cleared to 0). FFFFFFFFh is the broadcast value meaning "all namespaces", allowed only for certain commands (some log pages and features, Format NVM in some configurations). Using an inactive or invalid NSID in a Read produces an NVMe error status such as Invalid Namespace or Format; the exact status depends on whether the NSID is unallocated, inactive or out of range, so confirm it in the NVM Express Base Specification for the case you are testing.

    Common weak answer: "NSIDs start at 0 like array indexes."

  11. [hex] Namespace 1 has LBA Data Size (LBADS) = 9 and namespace 2 has LBADS = 12. A file system wants to read the 4 KiB at byte offset 1 MiB. What starting LBA and Number of Logical Blocks (NLB) value go in the Read command for each namespace?

  12. [performance] The Lab SSD reports Maximum Data Transfer Size (MDTS) = 5 and CAP.MPSMIN = 4 KiB. An application issues one 1 MiB read. How many NVMe commands reach the drive, and who splits the request?

    Model answer

    MDTS is a power of two in units of the minimum memory page size: 2^5 × 4 KiB = 128 KiB per command. 1 MiB ÷ 128 KiB = 8 commands. The split happens in the host: the Linux block layer limits each request to the queue's max_hw_sectors_kb (derived by the NVMe driver from MDTS) and the possibly smaller max_sectors_kb, so the driver never receives a request the controller cannot accept. A controller that receives a command larger than MDTS fails it with an NVMe error (Invalid Field in Command); it does not split it. MDTS = 0 would mean "no limit reported".

    Strong answer includes: units of MPSMIN; 128 KiB; host-side split and where to see the limit in sysfs; MDTS = 0 meaning.

Queues, doorbells, commands, PRPs and interrupts

Questions 67–86. A Submission Queue Entry (SQE) is 64 bytes and a Completion Queue Entry (CQE) is 16 bytes. Doorbells start at BAR0 + 1000h; with stride s = 4 << CAP.DSTRD, SQ y's tail doorbell is at 1000h + 2y × s and CQ y's head doorbell at 1000h + (2y + 1) × s.

  1. [hex] Which doorbell is at BAR0 + 0x1014 on the Lab SSD (DSTRD = 0)? Which doorbell would BAR0 + 0x1020 be on a controller with DSTRD = 2?

    Model answer

    Lab SSD: stride = 4 bytes. 0x1014 − 0x1000 = 0x14 = 20 bytes = doorbell index 5. Odd indexes are CQ head doorbells, and 5 = 2y + 1 gives y = 2: the CQ2 head doorbell. Second controller: stride = 4 << 2 = 16 bytes. 0x1020 − 0x1000 = 0x20 = 32 bytes = index 2. Even indexes are SQ tail doorbells, 2 = 2y gives y = 1: the SQ1 tail doorbell. A larger stride spreads doorbells across separate cache lines or pages, which some virtualized and emulated designs prefer. Software must always compute offsets from CAP.DSTRD rather than assume 4 bytes.

    Strong answer includes: index = offset ÷ stride; even = SQ tail, odd = CQ head; never hard-coding the stride.

  2. [coding] I/O SQ1 has 1024 entries. The controller's last reported head is 1020 and the host's tail is 3. Write a function that returns how many entries are waiting and how many free slots the host may still fill, and apply it.

    Model answer 
    def sq_space(head: int, tail: int, size: int):
    """Entries waiting for the controller, and slots the host may still fill.
    One slot is always left empty so that full and empty can be told apart."""
    used = (tail - head) % size
    free = size - 1 - used
    return used, free

print(sq_space(1020, 3, 1024))   # (7, 1016)
print(sq_space(5, 5, 1024))      # (0, 1023) empty
print(sq_space(6, 5, 1024))      # (1023, 0) full

    (3 − 1020) mod 1024 = 7: slots 1020, 1021, 1022, 1023, 0, 1, 2 are waiting. The host may add 1016 more. The queue is full when (tail + 1) mod size equals head, so at most size − 1 entries are ever outstanding; that is how the protocol tells "full" from "empty" (head equal to tail) without a separate counter. The head value the host uses must come from the SQ Head Pointer (SQHD) field of the most recent CQEs, so it can lag the controller's real head; that only makes the host more conservative, never wrong.

    Strong answer includes: modular arithmetic; the one-empty-slot rule; where the head comes from.

    Common weak answer: tail − head = −1017.

    Learn it in: Chapter 25, Submission/Completion Queue Simulator.

The write of 30 submits 2 commands, in slots 28 and 29. The write of 2 wraps around: slots 30, 31, 0 and 1, so 4 commands; (2 − 30) mod 32 = 4. The controller would typically fetch them as two reads, slots 30–31 at the end of the queue memory and slots 0–1 at the start, because they are not contiguous in memory. A doorbell value is the new tail (the next free slot), not a count of commands.

    Strong answer includes: doorbell = tail position; modular difference; wrap leads to two fetch ranges.

Bits 15:14 (PRP or SGL for Data Transfer, PSDT) = 0: the data pointer holds PRPs. Bits 31:16 = 0x0003: command identifier (CID) 3. CDW1 = 1: namespace ID 1. The same opcode means something different on the admin queue (02h is Get Log Page there), which is why a decoder must know which queue a command came from.   5. [hex] A Read to namespace 1 (512-byte LBAs) has CDW10 = 0x0000_1000, CDW11 = 0x0000_0000 and CDW12 = 0x0000_0007. What bytes of the namespace does it read?

    Model answer

    The Starting LBA (SLBA) is 64 bits: CDW11 holds the upper 32 bits and CDW10 the lower, so SLBA = 0x1000 = 4096. CDW12 bits 15:0 hold NLB = 7, which is 0's based, so 8 blocks. 8 × 512 = 4096 bytes. Byte range: 4096 × 512 = 2,097,152 (2 MiB) up to 2 MiB + 4 KiB − 1. The upper bits of CDW12 hold flags such as Force Unit Access (FUA) and Limited Retry; here they are all 0. Before sending it, the host should check that SLBA + 8 does not exceed NSZE, otherwise the command fails with LBA Out of Range.

    Strong answer includes: 64-bit SLBA across two dwords; 0's based NLB; the byte arithmetic; bounds check.

    Common weak answer: "It reads 7 blocks from LBA 0x1000 bytes."

    Learn it in: Chapter 32, Module 30.

  6. [hex] Decode this CQE from I/O CQ1: DW0 = 0, DW1 = 0, DW2 = 0x0001_0005, DW3 = 0x0001_0003.

    Model answer

    DW2 bits 15:0 = 5: SQ Head Pointer (SQHD) = 5, so the controller has consumed SQ entries up to slot 4 and the host may reuse them. DW2 bits 31:16 = 1: SQ Identifier = 1, the command came from SQ1. DW3 bits 15:0 = 3: CID 3, which is the Read from question 70. DW3 bit 16 = 1: Phase Tag = 1. DW3 bits 31:17 = 0: Status Field all zero, successful completion. DW0 is command-specific and unused for a Read. The host matches the completion to its request by the pair (SQ ID, CID), not by its position in the CQ.

    Strong answer includes: all five fields; SQHD's meaning for free slots; matching by SQ ID plus CID.

    Common weak answer: "0x0001_0003 is status 0x10003, an error."

    Learn it in: Chapter 25, Chapter 29.

  7. [hex] Another CQE has DW3 = 0x8005_0007. Decode the CID, phase, Status Code Type (SCT), Status Code (SC) and Do Not Retry (DNR) bit, and say what the host should do.

    Model answer

    Bits 15:0 = 0x0007: CID 7. Bit 16 = 1: phase tag 1. Status Field = bits 31:17 = 0x8005 >> 1 = 0x4002. Inside it: SC (bits 24:17 of DW3) = 0x02; SCT (bits 27:25) = 0, Generic Command Status; More (bit 30) = 0; DNR (bit 31) = 1. Generic status 02h is Invalid Field in Command. DNR = 1 means retrying the same command will fail again. The host should report the error upward, not retry, and investigate what it built wrongly: for example a reserved field set, a transfer larger than MDTS, or a feature or flag the controller does not support. The Error Information log page may give the parameter location.

    Strong answer includes: shifting by 17 (or by 1 after taking the top half); the four sub-fields; DNR meaning; this is a host-side bug most of the time.

    Common weak answer: reading SC = 0x05 by forgetting the phase bit.

    Learn it in: Chapter 44, Chapter 29.

  8. [trace] A toy CQ has 4 entries, zeroed at creation. The controller has written slots 0–3 with phase 1, and the host has consumed all four and wrapped to slot 0. Slot 0 still contains the old CQE with phase 1. Is it a new completion? What phase will the next real completion in slot 0 have?

    Model answer

    No. The host tracks an "expected phase" that starts at 1 and flips each time its head wraps. On the first pass it accepted entries with phase 1; after wrapping it expects phase 0. Slot 0 still showing phase 1 is the stale entry from the first pass, so the host stops and waits. When the controller writes its next completion into slot 0, it writes phase 0 (the controller also inverts its phase on each wrap), and the host recognizes it as new. This is how the host finds new entries without reading any controller register, and why CQ memory must be zeroed (phase 0) when the queue is created.

    Strong answer includes: expected phase flips on wrap; the stale entry rejected; zeroed memory requirement.

    Common weak answer: "Phase 1 means valid, so it's new."

    Learn it in: Chapter 25, Module 26.

  9. [troubleshoot] A buggy driver processes CQEs correctly but never writes the CQ1 head doorbell. What happens, and after how many commands at most?

    Model answer

    The controller does not know the host has consumed anything, so from its point of view CQ1 fills up. It must not overwrite entries the host might not have read, so once the CQ is full (at most size − 1 entries, 1023 for a 1024-entry CQ) it stops posting completions. Commands then stall: the controller may keep fetching and even executing commands but cannot complete them; the host sees timeouts after its I/O timeout (30 seconds by default in Linux) and resets the controller. On an analyzer you see CQE writes stop and no MWr32 to BAR0 + 0x100C ever appear. The fix is to write the CQ head doorbell after consuming completions (batched writes are fine).

    Strong answer includes: why the controller stops; how many commands; the trace signature (no CQ head doorbell); resulting timeouts.

    Common weak answer: "Nothing, the CQ head doorbell is optional."

    Learn it in: Chapter 28, Chapter 27.

  10. [coding] With 4 KiB memory pages, give PRP Entry 1 and PRP Entry 2 for: (a) 4 KiB at 0x2_0000_0000, (b) 4 KiB at 0x2_0000_0200, (c) 8 KiB at 0x2_0000_0000.

    Model answer

    (a) The buffer fits in one page: PRP1 = 0x2_0000_0000, PRP2 not used (set to 0). (b) It starts 0x200 into a page, so it touches two pages: 0xE00 bytes in the first and 0x200 in the second. PRP1 = 0x2_0000_0200 (only PRP1 may have an offset), PRP2 = 0x2_0000_1000, the second page itself. (c) Two whole pages: PRP1 = 0x2_0000_0000 and PRP2 = 0x2_0000_1000. When exactly two pages are touched, PRP2 is a data page pointer; only when more than two pages are touched does PRP2 become a pointer to a PRP list. Any PRP entry other than the first must be page-aligned.

    Strong answer includes: counting pages touched, not bytes; offset only in PRP1; PRP2 as page versus list pointer.

    Common weak answer: for (b), "4 KiB fits in one PRP".

  12. [trace] A 32 KiB Read uses a page-aligned buffer of eight non-contiguous pages. PRP2 = 0x1_5000_0000. What does the controller fetch from that address, how big is the fetch, and what follows it on the link?

    Model answer

    Eight pages are touched, so PRP1 points to the first data page and PRP2 points to a PRP list in host memory (the course's PRP list pages start at 0x1_5000_0000). The list holds the remaining 7 page addresses, 8 bytes each, so the controller issues an MRd64 for 56 bytes (14 DW) at 0x1_5000_0000, receives them in a CplD, and only then knows where to send data pages 2–8. The read data then flows as MWr64 TLPs of up to 256 bytes (MPS): 32 KiB ÷ 256 = 128 data writes, followed by the CQE write and the MSI-X write. A controller might fetch the list in pieces or ahead of time; how it does so is implementation-dependent, but the list must be read before data for those pages can be placed.

    Strong answer includes: 7 entries, 56 bytes; MRd for the list before data; data write count from MPS.

    Common weak answer: "PRP2 is the second data page."

    Learn it in: Chapter 36, Module 34.

  13. [spec] How does the host know whether it may use Scatter Gather Lists (SGLs) for I/O on a controller, and where in the command does it say it is using one?

    Model answer

    The controller reports SGL support in the SGL Support (SGLS) field of Identify Controller; if that says SGLs are not supported for the NVM command set, the host must use PRPs. Even if supported, SGL use may be limited (for example to certain descriptor types or alignments), which SGLS also reports. In each command, the PSDT field (bits 15:14 of CDW0) says whether the Data Pointer holds PRPs (00b) or an SGL descriptor; the non-zero encodings select SGL forms, which you should confirm in the Base Specification before using. Over PCIe, admin commands use PRPs. Linux's driver typically uses SGLs only for larger transfers when supported, because PRPs are cheaper for small ones.

  14. [trace] During driver probe, the admin SQEs carry these opcodes in order: 06h, 09h, 05h, 01h, 05h, 01h, 06h. Name each command and explain why 05h always comes before 01h.

    Model answer

    06h Identify (here Identify Controller); 09h Set Features (typically Number of Queues); 05h Create I/O Completion Queue; 01h Create I/O Submission Queue; again 05h and 01h for the second queue pair; 06h Identify again (for namespaces, for example the active namespace list or Identify Namespace). The order is required: Create I/O Submission Queue names the completion queue its completions go to (the CQ Identifier field), and that CQ must already exist, or the command fails. On teardown the order reverses: Delete I/O Submission Queue (00h) before Delete I/O Completion Queue (04h).

    Strong answer includes: correct names; the dependency; reverse order on teardown.

  15. [hex] A driver sends Set Features, Number of Queues (Feature Identifier 07h), asking for 32 submission and 32 completion queues with CDW11 = 0x001F_001F. The CQE's DW0 comes back as 0x0007_0007. How many I/O queues may the driver create?

    Model answer

    Both halves are 0's based. The request: bits 15:0 = 0x1F (32 submission queues), bits 31:16 = 0x1F (32 completion queues). The response in DW0: bits 15:0 = 7 and bits 31:16 = 7, so the controller allocated 8 I/O submission queues and 8 I/O completion queues. The number allocated may differ from the number requested; drivers such as Linux's use the smaller of the two, and should never create more than the controller allocated. The admin queue is not counted. The driver should create at most 8 I/O queue pairs, and typically maps them to CPUs, several CPUs sharing a queue.

    Strong answer includes: 0's based in both directions; response in CQE DW0; using the minimum of requested and allocated; admin queue not counted.

    Common weak answer: "7 queues", or assuming the request was granted.

  16. [hex] The Lab SSD's MSI-X table is at BAR0 + 0x2000. At what offset is the entry for vector 5, what are its four fields, and what values do you expect in it on the reference machine?

    Model answer

    Each MSI-X table entry is 16 bytes, so vector 5 is at 0x2000 + 5 × 16 = BAR0 + 0x2050 (0xFE60_2050).   17. [trace] The analyzer shows MWr32 Addr=0xFEE0_3000 Data=0x0000_0043 from Requester ID 0x0100. Which interrupt is this, and how do you find out which completion queue caused it?

    Model answer

    On the reference machine, address 0xFEE0_k000 with data 0x40 + k is vector k, so this is MSI-X vector 3, sent by the SSD (Requester ID 0x0100). NVMe does not put the queue number in the interrupt. The association is made when the host creates a completion queue: Create I/O Completion Queue carries an Interrupt Vector (IV) field and an Interrupts Enabled flag. So you look back in the capture (or in the driver's state) for the Create I/O CQ command whose IV = 3; with the usual Linux mapping that is CQ3, but several CQs could share a vector. The interrupt handler then checks the CQ(s) on that vector for new phase-tagged entries. In a capture you would expect a CQE write to that CQ just before the MSI-X write.

    Strong answer includes: vector decode; IV field at CQ creation; possibility of shared vectors; CQE write expected just before.

  19. [performance] What is interrupt coalescing, and what does it trade?

    Model answer

    Interrupt coalescing lets the controller wait until either a number of completions has accumulated (an aggregation threshold) or a time limit has passed before sending the interrupt, so one interrupt covers several CQEs. NVMe defines an Interrupt Coalescing feature that the host sets with Set Features; whether and how precisely a controller honors it is implementation-dependent. The trade is CPU efficiency versus latency: fewer interrupts mean less CPU spent in interrupt handling at high IOPS, but a completion may sit in the CQ until the threshold or timer fires, which adds latency, especially at low queue depth where there is nothing else to wait for. Hosts usually leave it off for latency-sensitive workloads; polling (checking the CQ without waiting for interrupts) is another way to reduce interrupt cost.

    Strong answer includes: threshold and time; it is a host-settable feature; the tradeoff; effect at low queue depth.

    Common weak answer: "It makes the drive faster."

    Learn it in: Chapter 42, Performance Engineering.

  20. [concept] A user runs fstrim on a file system on the Lab SSD. Which NVMe command reaches the drive, what does it carry, and what does it not guarantee?

    Model answer

    The file system tells the block layer which ranges are free (discard), and the NVMe driver turns each discard into a Dataset Management command (NVM opcode 09h) with the Deallocate attribute set. Its data buffer holds a list of ranges (each with a starting LBA and a length in LBAs), with the number of ranges in CDW10 as a 0's based value. The drive can then drop the mapping for those LBAs, which helps garbage collection and write amplification. It does not guarantee what a later read returns: depending on what the controller reports in Identify Namespace (deallocated-block read behavior), reads may return zeros, ones or be undefined, so software must not rely on trimmed data being zero unless the drive says so. Treat Deallocate as advisory rather than a guaranteed erase: how completely and how quickly a controller deallocates is implementation-dependent, and the exact obligations are worded in the NVM Command Set Specification, which you should check for the revision you are testing against.

    Strong answer includes: discard → DSM deallocate; ranges list; read-after-deallocate behavior is reported, not assumed; advisory nature.

    Common weak answer: "TRIM erases the data."

    Learn it in: Chapter 35, Module 33.

  1. [concept] A Read to an LBA beyond the end of namespace 1 fails. Will you see a PCIe error in AER or on the analyzer? Explain which layer reports the failure and how.

    Model answer

    No PCIe error. At the PCIe level everything works: the doorbell write is delivered, the SSD fetches the SQE with a successful completion, and it writes a CQE and sends MSI-X. The failure is an NVMe-level decision: the controller checks SLBA + NLB against the namespace size and completes the command with an error status in the CQE, LBA Out of Range (a status in the generic command status set), with no data transferred. PCIe errors (for example Unsupported Request, Completion Timeout, bad LCRC) are about moving packets; NVMe status codes are about whether the command made sense and succeeded. On the analyzer, the evidence is the CQE's status bits, which you decode from the payload of the CQE write. The inverse also happens: a PCIe error can make an NVMe command fail with a timeout or a data transfer error.

    Strong answer includes: PCIe transport succeeded; NVMe status in the CQE; where to see it in a trace; the two error domains kept apart.

    Common weak answer: "The SSD sends an Unsupported Request."

    Learn it in: Chapter 44, Chapter 47.

  2. [hex] The root port's AER Correctable Error Status register reads 0x0000_00C1. Which errors are logged, and what do they suggest together?

    Model answer

    0xC1 = bits 0, 6 and 7. Bit 0 = Receiver Error (the Physical Layer saw a bad symbol, framing or similar problem). Bit 6 = Bad TLP (a TLP failed its LCRC check or had a bad sequence number). Bit 7 = Bad DLLP (a DLLP failed its CRC). All three are detected by the root port's receiver, so the trouble is on the SSD-to-root-port direction of that link. Together they suggest a signal integrity problem rather than a protocol bug: noise or a marginal channel corrupts bits, and the Data Link Layer recovers through replay. They are correctable, so data is not lost, but rising counts cost bandwidth and can precede link retraining or speed drops. The bits are write-1-to-clear, so software clears them after logging; what matters is the rate.

    Strong answer includes: correct bits; detected at the receiver, so direction is known; signal integrity interpretation; RW1C and rate over count.

    Common weak answer: "Three fatal errors."

    Learn it in: Chapter 46, Module 18.

  4. [concept] What is PERST#, and how is a PCIe Fundamental Reset different from simply clearing CC.EN on the NVMe controller?

    Model answer

    PERST# (PCI Express Reset) is a sideband signal on the connector, driven by the platform. While it is asserted, the device is held in reset; the platform releases it after power and the reference clock are stable (the timing requirements are in the card electromechanical specification). Releasing it starts link training. A Fundamental Reset (a cold or warm reset, signaled to an add-in card through PERST#; together with Hot Reset these form the Conventional Reset family) resets the whole device: the link retrains, configuration space returns to defaults (BARs unassigned, Memory Space and Bus Master disabled), and the NVMe controller starts from scratch. Clearing CC.EN is an NVMe Controller Reset: the link stays up, configuration space and BARs are untouched, but the controller deletes all I/O queues, aborts outstanding commands and must be re-initialized from the admin queue registers. The first is a PCIe event, the second an NVMe event.

    Strong answer includes: PERST# as platform-driven sideband; what each reset clears; link stays up for CC.EN.

    Common weak answer: "They are the same, both reset the SSD."

    Learn it in: Chapter 49, Chapter 48.

  5. [concept] Why should the host perform an NVMe shutdown before cutting power, and how does it do it? What counter in the SMART / Health log reveals when it did not?

    Model answer

    The controller may hold data in a volatile write cache and has internal state (mapping tables, logs) that it wants to save. The host writes CC.SHN = 01b (normal shutdown), then polls CSTS.SHST until it reads 10b (shutdown processing complete), within a time the controller advertises (RTD3 Entry Latency in Identify Controller, when reported). Only then should power be removed. If power is lost without this, the drive counts an unsafe shutdown in the SMART / Health Information log page. Drives with power-loss protection can usually save their state anyway, but recovery at next power-on may take longer, and data that the host had not flushed may be lost on drives without protection. A rising unsafe-shutdown count on a server that is supposedly shut down cleanly points at a platform or operating system problem.

    Strong answer includes: SHN then SHST; timeout source; unsafe shutdowns counter; volatile cache risk.

    Common weak answer: "Just flush the file system."

  8. [performance] A single thread issues 4 KiB random reads one at a time (queue depth 1), and each takes 80 µs. What IOPS and throughput does it get, and why is that far below the drive's datasheet number?

    Model answer

    With one command outstanding, IOPS = 1 ÷ latency = 1 ÷ 80 µs = 12,500 IOPS, and throughput = 12,500 × 4096 bytes ≈ 51 MB/s. Datasheet numbers (hundreds of thousands or more IOPS) are measured with many commands outstanding across several queues, so that the drive's many flash dies work in parallel. Little's law says outstanding commands = IOPS × latency: to reach, say, 500,000 IOPS at 80 µs you need about 40 commands in flight. At queue depth 1 the drive is mostly idle, waiting for the next command. To improve the single thread: use asynchronous I/O (io_uring, libaio) to keep several commands outstanding, or use several threads.

    Strong answer includes: 1/latency; Little's law to explain the gap; parallelism inside the drive; how to raise queue depth.

    Common weak answer: "The drive is slow."

    Learn it in: Performance Engineering, Bandwidth, Latency and Little's Law Calculators.

  9. [performance] A Gen4 x4 SSD sustains 7.0 GB/s of 128 KiB sequential reads. How many commands per second is that, and how close is it to the link's limit?

    Model answer

    128 KiB = 131,072 bytes. 7.0 × 10^9 ÷ 131,072 ≈ 53,400 commands per second, a modest IOPS figure; at large transfer sizes bandwidth, not command rate, is the limit. The Gen4 x4 link carries about 7.88 GB/s per direction after 128b/130b encoding. Each 256-byte data payload also needs a TLP header, sequence number, LCRC and framing (roughly 20–30 bytes, depending on header size and options), plus DLLP traffic, so the practical ceiling for data is roughly 7.0–7.2 GB/s. This drive is therefore at the link's practical limit; buying a faster SSD for the same Gen4 x4 slot would not help, and checking that the link really trained at Gen4 x4 is the first thing to do if the number drops.

    Strong answer includes: bytes ÷ transfer size; per-TLP overhead estimate labeled approximate; link-bound conclusion.

  13. [coding] You have a list of decoded events: (time in ns, kind, sqid, cid) where kind is "submit" or "complete". Write a runnable Python function that pairs them and reports each command's latency, plus any command that never completed.

    Model answer 
    def pair(events):
    open_cmds = {}            # (sqid, cid) -> submit time
    done = []                 # (sqid, cid, latency_ns)
    problems = []
    for t, kind, sqid, cid in sorted(events):
        key = (sqid, cid)
        if kind == "submit":
            if key in open_cmds:
                problems.append(f"CID reuse while outstanding: {key} at {t}")
            open_cmds[key] = t
        elif kind == "complete":
            if key not in open_cmds:
                problems.append(f"completion with no matching submit: {key} at {t}")
                continue
            done.append((sqid, cid, t - open_cmds.pop(key)))
    for key, t in open_cmds.items():
        problems.append(f"never completed: {key} submitted at {t}")
    return done, problems

events = [(0, "submit", 1, 3), (500, "submit", 1, 4),
          (12_400, "complete", 1, 4), (13_100, "complete", 1, 3),
          (20_000, "submit", 1, 5)]
done, problems = pair(events)
for d in done:
    print("SQ%d CID %d: %.1f us" % (d[0], d[1], d[2] / 1000))
print(problems)

    The key is (SQ ID, CID), not CID alone, because CIDs are unique only per SQ; completions may arrive out of order (CID 4 finishes before CID 3 here, which is legal). The function also flags CID reuse and orphan completions, which are protocol violations worth reporting. Sorting by time assumes all timestamps come from one clock.

    Strong answer includes: correct key; out-of-order completion handled; anomalies reported rather than ignored; the single-clock assumption stated.

    Common weak answer: matching each completion to the oldest submission (FIFO), which is wrong for NVMe.

    Learn it in: Chapter 41, Automated Trace Analysis.

  14. [troubleshoot] Writes to an SSD suddenly fail, reads still work, and the file system remounts read-only. Which NVMe evidence do you collect first, and what would tell you the drive itself has entered a read-only state?

    Model answer

    First, separate host from device. The kernel log shows whether NVMe write commands are failing with a status (and which one) or whether the file system went read-only for its own reasons (for example after an I/O error or a detected inconsistency). Then read the SMART / Health Information log (nvme smart-log): the Critical Warning field has a bit that indicates the media has been placed in read-only mode, plus bits for spare capacity below threshold and reliability degraded; check available_spare against its threshold and percentage_used. If the read-only bit is set, the drive is protecting data at end of life or after an internal failure, and writes will keep failing with a status saying so; reads still work to let you copy data off. Also read the Error Information log for the failing commands. Do not run Format or Sanitize before data is copied and evidence saved.

    Strong answer includes: host versus device split; Critical Warning and spare fields; the drive's read-only mode as protective; preserve data and evidence first. Bit positions can be looked up; naming the fields is what matters.

    Common weak answer: "Remount the file system read-write."

    Learn it in: Chapter 57, Chapter 44.

How beginners lose points

  • Off-by-one on 0's based fields. MQES, AQA, NLB and the Number of Queues feature all store "count minus one".
  • Mixing the layers' vocabularies. An NVMe Read is carried by PCIe Memory Writes.
  • Skipping the other end of the link. Link speed, width and errors are properties of a link, not of one device.
  • Calling the last event the cause. A timeout is usually the end of a story that started earlier in the trace.
  • Inventing precision. If you do not remember a bit position or status value, name the field and say you would confirm it. That costs nothing.
