Behind the PCIe function you inspected in Chapter 69 sits an NVMe controller with its own identity, its own logs and its own queues. This chapter teaches you to interrogate it from Linux with nvme-cli, the NVMe sysfs tree, the block layer's queue settings and the kernel's NVMe tracepoints, and to know exactly which of those commands are harmless questions and which ones change the drive.

Why this chapter exists

The PCIe view tells you the road is open. It does not tell you whether the librarian is awake, how big the library is, whether the shelves are wearing out, or which requests failed last night. Those answers come from the NVMe layer: Identify data structures, log pages, features and controller registers, all defined by the NVM Express specifications and all reachable from Linux.

Unlike lspci, most nvme-cli commands are not passive reads of config space. They send real NVMe admin commands (Identify, Get Log Page, Get Features) through the driver onto the controller's Admin Submission Queue. They are safe because those particular commands are defined to have no effect on stored data, not because "reading is always safe". The same tool, one subcommand away, can format, sanitize or reflash a drive. Knowing the difference is the first professional skill this chapter builds.

The second skill is cross-layer correlation. The kernel's NVMe tracepoints print the queue identifier (QID) and command identifier (CID) of every command; an analyzer shows the same CID inside the 64-byte Submission Queue Entry (SQE) and the 16-byte Completion Queue Entry (CQE). That shared key lets you join a Linux trace to a PCIe trace, which is the core technique of Chapter 41 and the trace-analysis parts of this course.

Learning objectives

  • Map Linux device nodes (/dev/nvme0, /dev/nvme0n1, /dev/ng0n1) to NVMe controllers, namespaces and subsystems.
  • Run and interpret nvme list, id-ctrl, id-ns, smart-log, error-log, fw-log, get-log, get-feature, show-regs and list-subsys, naming the NVMe command each one sends.
  • Compute derived quantities: maximum data transfer size from MDTS, bytes from SMART data units, queue entry sizes from SQES/CQES, LBA size from the LBA Format.
  • Navigate /sys/class/nvme, /sys/class/nvme-subsystem and /sys/block/nvmeXnY/queue/*, and connect each value to the NVMe field it came from.
  • Trace commands with blktrace/blkparse and with the nvme_setup_cmd / nvme_complete_rq tracepoints via trace-cmd, ftrace and bpftrace.
  • Classify every nvme-cli subcommand into Safe, Caution or Expert, and practise all of it on a QEMU-emulated NVMe controller first.

The story

Chapter 69 let you read the name card on the library's door. Now you are allowed to talk to the librarian through a little window. You may ask polite questions: "Who are you? How many books do you hold? How tired are your shelves? What went wrong recently?" The librarian answers from her notebooks, and asking does not move a single book. But the same window also accepts orders such as "throw away every book" or "replace your brain with this new one". A good student only asks questions through the window unless the teacher is standing right there, with a spare library ready.

Adult version: nvme-cli is the diagnostic port of a modern car (the On-Board Diagnostics connector). A scan tool can read the vehicle identification, live sensors, fault codes and freeze-frame data without affecting how the car drives. The same port, with the right software, can also clear codes, recalibrate the engine or flash new firmware. Mechanics separate "read codes" from "program module" by procedure, not by plug.

Where the analogy breaks. (1) A car's diagnostic bus is separate from the driving controls; NVMe admin commands share the controller with I/O and consume admin queue slots, so a tight loop of queries can, in principle, compete with the driver's own admin work. (2) Reading a car's fault codes does not clear them; some NVMe log pages tied to asynchronous events are cleared or acknowledged when read without the Retain Asynchronous Event flag, and reading certain logs (for example a host-initiated telemetry log with "create") triggers new work inside the device. (3) The car has one controller; an NVMe subsystem can have several controllers and namespaces shared among hosts, so "the drive" is not always one thing.

Engineering explanation

How a nvme-cli query reaches the controller

This is a full NVMe command lifecycle, exactly like an I/O but on queue 0. Every nvme-cli query therefore appears on a PCIe analyzer as doorbell writes, an SQE fetch, a data transfer, a CQE write and an MSI-X write. The command identifier assigned by the driver is visible in the SQE on the wire and in the kernel's tracepoints.

Kernel side detail: the driver checks passthrough commands against the controller's Commands Supported and Effects log where available and may freeze I/O around commands flagged as changing the namespace inventory or capabilities (for example Format NVM), then rescan afterwards. That is driver policy, not something the NVMe specification requires of the host.

nvme error-log: Error Information (Log Page 01h)

Get Log Page with Log Identifier 01h. The controller keeps a ring of entries (elpe + 1 of them). Each entry contains:

  • error_count: a unique, incrementing identifier of the error (not a per-entry count). Zero means the entry is empty.
  • sqid, cmdid: the queue and command that failed. These are the join keys to tracepoints and analyzer traces.
  • status_field: the status of the failed command (Status Code Type, Status Code, More, Do Not Retry). nvme-cli shows the raw field; decode it with the status tables from Chapter 44.
  • parm_error_location: byte and bit in the command where a parameter error was found.
  • lba, nsid: first LBA and namespace involved, when relevant.
  • vs: vendor-specific information log page pointer; trtype, cs, trtype_spec_info: transport and command-specific information.

The error log is not a complete record of what Linux saw. Commands that timed out and were aborted or reset by the host may leave no entry, because from the controller's perspective they may never have completed with an error. Conversely, entries can exist for errors Linux handled silently (for example a retried command). And the ring overwrites old entries. Always cross-check with the kernel log (Chapter 71).

nvme fw-log: Firmware Slot Information (Log Page 03h)

Shows the active firmware slot (afi) and the revision in each slot (frs1 … frs7), including which slot will be activated at the next reset. Read-only and safe. The commands that change these slots (fw-download, fw-commit) are Expert.

nvme get-log: any log page by identifier

sudo nvme get-log /dev/nvme0 --log-id=0x02 --log-len=512     # SMART/Health, raw hex
sudo nvme get-log /dev/nvme0 --log-id=0x05 --log-len=4096    # Commands Supported and Effects
sudo nvme effects-log /dev/nvme0 -H                          # same log, decoded

Well-established identifiers: 01h Error Information, 02h SMART / Health Information, 03h Firmware Slot Information, 04h Changed Namespace List, 05h Commands Supported and Effects. Many more exist (device self-test, telemetry, endurance group, Asymmetric Namespace Access, persistent event log, feature-specific logs added in 2.x, including those for NVMe 2.4 features). For anything beyond the first five, look the identifier up in the NVMe Base Specification 2.4 log page table; do not guess. Check the specification

Some log pages are tied to Asynchronous Event Notifications: reading them without the Retain Asynchronous Event (RAE) bit can clear the event condition the driver is waiting on (the Changed Namespace List is the classic example). Host-initiated telemetry with "create" asks the controller to capture a new snapshot. The Persistent Event Log uses a read context that must be established and released. These are Caution lab operations on a production system even though they move no user data.

nvme show-regs: the controller registers

sudo nvme show-regs /dev/nvme0 -H maps BAR0 (through the PCI resource0 file) and reads the controller registers: CAP (00h), VS (08h), INTMS/INTMC (0Ch/10h), CC (14h), CSTS (1Ch), NSSR (20h), AQA (24h), ASQ (28h), ACQ (30h), and optional ones such as CMBLOC/CMBSZ and BPINFO. This is the only common nvme-cli command that is not an NVMe admin command: it is a set of PCIe memory reads (MRd) to BAR0. Fields to read:

  • CAP: MQES (maximum queue entries, 0's-based), CQR, TO (worst-case ready timeout in 500 ms units), DSTRD (doorbell stride), NSSRS, CSS, MPSMIN/MPSMAX, CMBS, PMRS.
  • VS: the version the controller implements.
  • CC: EN, CSS, MPS, AMS, SHN, IOSQES (6 → 64 bytes), IOCQES (4 → 16 bytes).
  • CSTS: RDY, CFS (Controller Fatal Status), SHST (shutdown status), NSSRO, PP.
  • AQA/ASQ/ACQ: admin queue sizes and base addresses (as I/O virtual addresses when an IOMMU is active).

show-regs needs root, and may fail on kernels that restrict mapping of BARs claimed by a driver (kernel lockdown, strict I/O memory policies) or on platforms where resource0 cannot be mapped. It also does not work for fabrics controllers in the same way. Reading NVMe registers is benign by specification (reads of NSSR return 0, doorbells are not read), but it is a live MMIO access to a device in use: treat it as Safe on lab systems and as a deliberate act on production ones.

Tracing NVMe commands from Linux

Identify and logs describe the controller. Tracing shows what it is doing. Linux offers two complementary layers.

Block layer: blktrace and blkparse

blktrace records block-layer events for a device; blkparse formats them. It observes requests above the NVMe driver, so it knows nothing of QIDs, CIDs or doorbells, but it shows queueing, merging, splitting and the time each request spent between issue to the driver (D) and completion (C).

sudo blktrace -d /dev/nvme0n1 -w 10 -o - | blkparse -i - > blk.txt   # 10-second capture
btt -i nvme0n1.blktrace.0      # (if saved to files) latency breakdown: Q2D, D2C, Q2C
259,0    3        1     0.000000000  4211  Q   R 2048 + 8 [fio]
259,0    3        2     0.000001210  4211  G   R 2048 + 8 [fio]
259,0    3        3     0.000002050  4211  D   R 2048 + 8 [fio]
259,0    3        4     0.000089400     0  C   R 2048 + 8 [0]

Columns: major,minor (259 is the extended block major used for NVMe namespaces), CPU, sequence, time in seconds, PID, action, RWBS flags, start sector + number of 512-byte sectors, process. Actions: Q queued, G request allocated, I inserted into a scheduler, D dispatched to the driver, C completed, X split, M/F merged. Here D→C = 87.35 µs: the device-plus-driver time. The sector numbers are always in 512-byte units even on a 4 KiB-LBA namespace.

NVMe driver tracepoints

The Linux NVMe driver defines tracepoints in the nvme event group. The two you will use constantly:

  • nvme:nvme_setup_cmd: fires when the driver builds an SQE. Records controller, QID, CID, NSID, flags and a decoded view of the command (opcode and key command dwords).
  • nvme:nvme_complete_rq: fires when the driver completes the request from a CQE. Records controller, QID, CID, the command-specific result, retries, flags and the status field.

Others in the group include nvme_async_event (an AEN arrived) and nvme_sq (SQ head updates seen in completions). List them on your kernel with ls /sys/kernel/tracing/events/nvme/ and read the exact field names in each event's format file. Field names and print format are kernel-version-dependent

# 1. trace-cmd (simplest)
sudo trace-cmd record -e nvme:nvme_setup_cmd -e nvme:nvme_complete_rq -- sleep 5
trace-cmd report > nvme-trace.txt

# 2. raw ftrace through tracefs
cd /sys/kernel/tracing
echo 1 | sudo tee events/nvme/nvme_setup_cmd/enable events/nvme/nvme_complete_rq/enable
sudo cat trace_pipe | head -50
echo 0 | sudo tee events/nvme/enable

# 3. bpftrace: per-queue latency histogram, and print any non-zero status
sudo bpftrace -e '
tracepoint:nvme:nvme_setup_cmd { @s[args->ctrl_id, args->qid, args->cid] = nsecs; }
tracepoint:nvme:nvme_complete_rq /@s[args->ctrl_id, args->qid, args->cid]/ {
  @lat_us[args->qid] = hist((nsecs - @s[args->ctrl_id, args->qid, args->cid]) / 1000);
  if (args->status) { printf("ctrl %d qid %d cid %d status 0x%x\n",
                             args->ctrl_id, args->qid, args->cid, args->status); }
  delete(@s[args->ctrl_id, args->qid, args->cid]);
}'

Newer bpftrace releases prefer args.qid over args->qid; both are accepted in many versions. If a field name is rejected, check the event's format file. Tracing has overhead: at millions of IOPS, enabling every NVMe event measurably changes the system you are measuring. Filter (by qid or ctrl_id) or sample when you can.

Read it like this: the read on QID 4 (the I/O queue mapped to CPU 3 on this synthetic system) has CID 37, starting LBA 2048 and len=7, which is the 0's-based Number of Logical Blocks field, so 8 blocks of 512 bytes = 4 KiB. It completed 87 µs later with status 0. The admin Identify on QID 0 completed in 88 µs. Note that the tracepoint timestamps are when the driver built the command and when it processed the completion, not when the doorbell write or the CQE crossed the link.

QID + CID identify an outstanding command uniquely on one controller at one moment. The same CID is in DWORD 0 of the SQE the controller fetches and in the CQE it writes back, so it is visible on a PCIe analyzer that decodes NVMe. That is how you line up a kernel trace with a link trace. Caveat: Linux encodes a small generation counter in the upper bits of the CID on recent kernels to catch stale completions, so CIDs look larger than the tag number and are reused across time; always join on (controller, QID, CID) within a time window. Driver-implementation-dependent

The central concept on the ladder: asking the controller about itself

You talk to the librarian through a window and ask polite questions. She reads answers from her notebooks. Some windows-requests could also make her throw books away, so you only use the question forms.

nvme-cli sends admin commands (Identify, Get Log Page, Get Features) through the kernel; the controller returns data structures that the tool decodes. sysfs and tracepoints add the kernel's own view.

Controller firmware serves admin commands, typically on a management path separate from the I/O fast path; it assembles Identify data from configuration tables and logs from counters kept in RAM and persisted to media. Registers (CAP, CC, CSTS) are hardware in the controller's PCIe front end.

The NVMe Base Specification 2.4 defines the Identify data structures, log pages and features, their fields and which are mandatory; the NVM Command Set Specification 1.3 defines the namespace fields for the NVM command set; the NVMe over PCIe Transport Specification 1.4 defines the register mapping and queue mechanics on PCIe.

Each query is an admin SQE (opcode 06h, 02h or 0Ah) placed in the Admin SQ, a doorbell write, a data transfer into a host buffer described by PRPs, a CQE and an MSI-X interrupt.

On an analyzer: MWr to BAR0+1000h, MRd of 64 bytes from the Admin SQ, MWr of the returned data (for Identify, 4096 bytes split into MPS-sized TLPs), MWr of 16 bytes to the Admin CQ, MWr to the MSI-X address, MWr to BAR0+1004h. In the kernel trace: nvme_setup_cmd qid=0 and nvme_complete_rq qid=0 with the same CID.

When a query fails or hangs, the failure is itself evidence: an Identify that times out says the admin path is stuck even if I/O appears fine; a SMART log with rising media_errors moves suspicion from the host to the media; an error-log entry's SQID/CID tells you exactly which command to find in the trace.

The sixteen questions for "inspecting an NVMe controller from Linux"

1. What is it?
Querying the controller's self-description (Identify), state (features, registers) and history (log pages), plus observing its commands in flight via tracing.
2. Why was it created?
So that one generic driver and tool can manage any vendor's controller and so that health and failures are reportable in a standard form.
3. What problem does it solve?
Identity, capability discovery, health monitoring and first-level failure diagnosis without vendor tools.
4. What existed before?
ATA IDENTIFY DEVICE and ATA SMART attributes (vendor-defined attribute tables), SCSI INQUIRY / mode pages / log sense, and vendor utilities.
5. Why is the current design better?
Fixed, specified structures (a single SMART/Health layout), log pages with identifiers, a command effects log to tell hosts which commands are dangerous, and namespace-scoped identity.
6. Who creates it?
Controller firmware (data), the specification (layout), the Linux driver (sysfs, tracepoints), nvme-cli (decoding).
7. Who consumes it?
The driver at probe time (Identify, Number of Queues), udev (identifiers), monitoring agents (SMART), engineers.
8. Where does it live?
In controller firmware and media; in registers in BAR0; in kernel memory (cached Identify); in sysfs and the trace ring buffer.
9. What memory/registers are involved?
Admin SQ/CQ in host memory, a data buffer, SQ0/CQ0 doorbells, MSI-X vector 0, CAP/VS/CC/CSTS for show-regs.
10. What happens before?
PCIe enumeration and BAR mapping (Chapter 69), controller enable (CC.EN=1, CSTS.RDY=1), admin queue creation.
11. What happens after?
You compare values with expectations, look for anomalies, and move to logs (Chapter 71) or traces.
12. What happens if it is wrong?
Wrong Identify data leads to wrong block-layer limits (oversized I/O rejected, missing discard); misreading SMART units misleads capacity planning; sending the wrong subcommand destroys data.
13. What does the analyzer show?
Admin command lifecycles on QID 0, with opcodes 06h, 02h, 0Ah and their data transfers.
14. What does Linux show?
nvme-cli output, sysfs attributes, block queue limits, tracepoints, kernel log messages.
15. What would a validation engineer test?
That Identify fields match the product specification and are consistent with each other (SQES/CQES, MDTS vs CAP), that log pages are well-formed and counters monotonic across power cycles, that features persist or not as specified, that error-log entries are produced for each injected error with correct SQID/CID/status.
16. What would a senior engineer suspect when it fails?
An admin path hang in firmware, a controller in a fatal state (CSTS.CFS=1), the wrong device node (multipath naming), a log read clearing an AEN, or an nvme-cli/kernel version mismatch decoding a newer structure.

Hardware view

Inside an SSD controller, admin commands are usually handled by firmware running on an embedded processor core that is separate from, or shares time with, the cores that drive the I/O pipeline and the flash translation layer. Identify data is a mostly static image built at boot from configuration tables; SMART counters live in controller RAM and are written to flash periodically and at shutdown; the error log is a RAM ring that may or may not persist across power cycles. Implementation-dependent

This has practical consequences. Admin commands are not on the fast path: a SMART query can take hundreds of microseconds to milliseconds, and some controllers pause internal work to service them. Monitoring agents that poll SMART every second across thousands of drives have, on some products, caused measurable latency outliers. The controller registers that show-regs reads, by contrast, are hardware in the PCIe/NVMe front end and answer in the time of a PCIe memory read.

The temperature in the SMART log is a "composite" chosen by firmware from several physical sensors. The thermal throttling behind Thermal Management T1/T2 counters is a firmware policy acting on clock and NAND parallelism, which is why a hot drive's throughput drops long before anything is logged as an error.

When the controller is in a fatal state (CSTS.CFS = 1) or hung, admin commands time out while register reads may still work, because registers are answered by hardware and commands need firmware. That asymmetry is a powerful diagnostic: "show-regs works, id-ctrl hangs" localizes the fault inside the controller.

Specification view

Sources: NVM Express Base Specification 2.4 — Identify command; Get Log Page command; Get Features and Set Features commands; Controller Registers; NVM Command Set Specification 1.3 — I/O Command Set specific Identify Namespace data structure; NVMe over PCIe Transport Specification 1.4 — register mapping and doorbells. nvme-cli and the Linux driver are implementations: their output names (mdts, num_err_log_entries) are their own labels for specification fields, close to but not always identical with the specification's field names.

Verified, well-established: admin opcodes Get Log Page 02h, Identify 06h, Abort 08h, Set Features 09h, Get Features 0Ah; CNS 00h Identify Namespace, 01h Identify Controller, 02h Active Namespace ID list, 03h Namespace Identification Descriptor list; log identifiers 01h Error Information, 02h SMART / Health Information, 03h Firmware Slot Information, 04h Changed Namespace List, 05h Commands Supported and Effects; feature identifiers 01h Arbitration, 02h Power Management, 04h Temperature Threshold, 05h Error Recovery, 06h Volatile Write Cache, 07h Number of Queues, 08h Interrupt Coalescing, 0Bh Asynchronous Event Configuration, 0Ch Autonomous Power State Transition; registers CAP 00h, VS 08h, CC 14h, CSTS 1Ch, AQA 24h, ASQ 28h, ACQ 30h; 64-byte SQE and 16-byte CQE for the NVM command set; SMART data units are thousands of 512-byte units.

Derived: the kernel's max_hw_sectors_kb is bounded by MDTS × minimum page size; write_cache follows VWC; discard_max_bytes is non-zero only when ONCS reports Dataset Management. Therefore a block-queue attribute that disagrees with Identify data indicates a driver quirk or policy, which is worth investigating.

Implementation-dependent: which optional fields and logs a controller fills; whether SMART is per namespace; error-log persistence; admin command latency; percentage_used estimation; composite temperature algorithm; the Linux CID encoding; the driver's queue count and depth.

Version-dependent: many Identify fields were added in NVMe 1.3, 1.4, 2.0 and later (the 2.0 restructuring moved command-set-specific fields into the NVM Command Set specification); NVMe 2.4 adds features such as rate limiting, voltage monitoring and manufacturing-default restore with their own fields and logs (see 2026 NVMe 2.4 Updates; identifiers must be checked in the 2.4 documents). nvme-cli decodes only what its version knows; older tools print unknown fields raw or not at all.

The specification does not define nvme-cli, its option names, its output layout, the Linux sysfs attributes or tracepoints, or the kernel's timeouts. It does not say how often a host may poll logs, or what latency an admin command must have. Check in the specification: the exact bit layout of critical_warning for your revision, the Get Log Page dword layout (Log Specific Field width changed across revisions), the CNS values for command-set-specific Identify structures, and the log identifiers of any 2.x log you need.

Never assume: that nvme0n1 belongs to nvme0; that an empty error log means no failures; that percentage_used < 100 means the drive is healthy; that SMART values update instantly; that QEMU's behaviour matches real hardware; that a "read-like" subcommand name (get-log) means no side effects.

"""Pair nvme_setup_cmd / nvme_complete_rq events from 'trace-cmd report' text.

def describe(status):
    sct, sc = (status >> 8) & 0x7, status & 0xFF
    dnr, more = bool(status >> 14 & 1), bool(status >> 13 & 1)
    name = GENERIC_SC.get(sc, "see status tables") if sct == 0 else "see status tables"
    return f"SCT={sct} SC=0x{sc:02x} ({name}){' DNR' if dnr else ''}{' MORE' if more else ''}"


def analyse(lines):
    pending, lat, errors, last_t = {}, {}, [], 0.0
    for line in lines:
        m = EVENT.search(line)
        if not m:
            continue
        t, ev, ctrl, qid, cid, rest = (float(m.group(1)), m.group(2), m.group(3),
                                       int(m.group(4)), int(m.group(5)), m.group(6))
        last_t = max(last_t, t)
        key = (ctrl, qid, cid)
        if ev == "nvme_setup_cmd":
            pending[key] = (t, rest.strip(", "))
        elif key in pending:
            t0, cmd = pending.pop(key)
            lat.setdefault((ctrl, qid), []).append((t - t0) * 1e6)
            s = STATUS.search(rest)
            status = int(s.group(1), 16) if s else 0
            if status:
                errors.append((t, ctrl, qid, cid, status, cmd))
    print("Per-queue completion latency (driver setup -> driver completion), microseconds")
    for (ctrl, qid), v in sorted(lat.items()):
        print(f"  {ctrl} qid {qid:3d}: n={len(v):5d} min={min(v):8.1f} "
              f"median={statistics.median(v):8.1f} max={max(v):8.1f}")
    print("Non-zero completion status:")
    for t, ctrl, qid, cid, st, cmd in errors or []:
        print(f"  t={t:.6f} {ctrl} qid {qid} cid {cid}: status=0x{st:x} -> {describe(st)}")
        print(f"      command: {cmd[:90]}")
    if not errors:
        print("  none")
    print("Submitted but not completed in this capture (age at end of capture):")
    for (ctrl, qid, cid), (t0, cmd) in sorted(pending.items(), key=lambda kv: kv[1][0]):

Worked example

Symptom

A storage application issues 1 MiB direct reads. blktrace shows each one split into eight pieces, and the team asks whether "the kernel is breaking our I/O".

Evidence

Synthetic example for teaching:

  • nvme id-ctrl /dev/nvme0 | grep mdts → mdts : 5
  • nvme show-regs /dev/nvme0 -H → CAP Memory Page Size Minimum = 4096 bytes (MPSMIN = 0)
  • cat /sys/block/nvme0n1/queue/max_hw_sectors_kb → 128
  • blkparse shows X (split) actions: R 2048 / 2304 … each piece 256 sectors.

Reasoning

MaxXfer = 25 × 4 KiB = 128 KiB. The kernel must not send a command larger than the controller's MDTS, so it caps max_hw_sectors_kb at 128 and splits a 1 MiB request into 8 × 128 KiB commands. Each piece appears in the NVMe tracepoint as its own command with len=255 (256 × 512-byte LBAs). Derived

Is it a problem?

Usually not: the eight commands are issued back to back on the same queue and complete in parallel inside the drive. Throughput is generally governed by the drive's internal parallelism, not by the command size beyond about 128 KiB. Measure before "fixing". If a larger MDTS is needed, it is a device property (firmware); the host cannot raise it.

What a careless engineer would do

Try to raise max_sectors_kb above max_hw_sectors_kb (the kernel refuses) or blame the I/O scheduler (NVMe usually runs with none). The Identify data answered the question in one line.

Common mistakes

  • Running a command against the wrong node because nvme1n1 is assumed to belong to nvme1.
  • Reading data_units_written as bytes or as LBAs. It is thousands of 512-byte units.
  • Forgetting 0's-based fields: len=7 is 8 blocks; Number of Queues result 0x1F is 32 queues; elpe 63 is 64 entries.
  • Treating error-log as the complete failure history.
  • Polling SMART aggressively in production and causing the latency outliers you are investigating.
  • Assuming get-log is always passive (RAE, telemetry create, persistent event log context).
  • Using tracepoint timestamps as wire timestamps. They are driver events.
  • Copy-pasting a "format" or "sanitize" command from a forum onto anything other than a spare or emulated drive.
  • Comparing outputs from different nvme-cli versions without noting that field names and decoding change.

Senior engineer insight

Seniors treat Identify data as claims to verify: is MDTS consistent with the largest transfer that actually works? Do SQES/CQES match what the driver programmed into CC? Does VWC match observed flush behaviour? Inconsistencies in Identify are among the cheapest firmware bugs to find and the most expensive to find late.

There are three timelines: the driver's (tracepoints, kernel log), the link's (analyzer), and the controller's (internal logs, telemetry, timestamp feature). They never agree exactly. Seniors align them on shared events (a CID, a doorbell value, a reset) and report offsets rather than pretending the clocks are one.

The Commands Supported and Effects log tells the host which commands change the logical block content, the namespace inventory or the controller capabilities. Reading it before running an unfamiliar admin or vendor command is the professional equivalent of reading a label before mixing chemicals.

Challenge

Without nvme-cli, find the namespace's LBA size and capacity using only sysfs, and explain which Identify fields the kernel used to compute them.

Hints

logical_block_size comes from the LBA Format's LBADS; size is NSZE × LBA size ÷ 512. For queue counts, remember both values may be 0's-based in one place and not in the other, and queue_count includes the admin queue.

Solution

1: MaxXfer = 2mdts × 2(12+MPSMIN); with the QEMU default mdts (commonly 7) and 4 KiB pages that is 512 KiB, and max_hw_sectors_kb should be at most that (the driver may impose a lower cap). Values depend on QEMU version and options. 2: SQES low nibble 6 = required 26 = 64 bytes, high nibble 6 = maximum 64; CQES 4/4 = 16 bytes; the driver programs CC.IOSQES = 6 and CC.IOCQES = 4. 3: size × 512 = NSZE × LBA size. 4: Get Features 07h returns NSQA and NCQA (0's-based) in completion DW0; queue_count = I/O queues created + 1 admin; the driver creates no more than min(granted, CPUs or module limits). 5: each 1 MiB read becomes ⌈1 MiB ÷ MaxXfer⌉ commands (2 with 512 KiB MaxXfer, 8 with 128 KiB), so 32 or 128 commands. 6: status 0x80 = SCT 0 (Generic Command Status), SC 80h LBA Out of Range; More and DNR bits are reported as the controller chose (a spec-compliant controller may set DNR since retrying cannot succeed).

What a senior engineer notices

Whether the emulated device's MDTS, queue count and VWC resemble production drives (if not, the lab's performance conclusions do not transfer); that tracepoint latencies include interrupt handling; that the failed command's CID can be found in three places (trace, kernel log, error log) and whether they agree.

Failure variants

  • show-regs fails with a mapping error: kernel lockdown or the region is busy; read CAP/CSTS via the kernel log or skip.
  • trace-cmd reports no nvme events: tracefs not mounted, events not compiled in, or wrong event names for your kernel.
  • The error log is empty after step 5: the emulated controller may not record entries; the trace and dmesg remain your evidence.

Extension

Run QEMU with --trace "pci_nvme_*" and align QEMU's device-side events with the guest's tracepoints using the CID. You now have a two-sided trace without an analyzer.

Answers

Quiz

  1. Which NVMe command does nvme id-ctrl send?

    • Get Log Page, LID 01h
    • Identify, CNS 01h
    • Identify, CNS 00h
    • Get Features, FID 07h
    Answer and reasoning

    Identify (opcode 06h) with CNS 01h returns the Identify Controller structure; CNS 00h is Identify Namespace.

  2. Which nvme-cli command does not send an NVMe admin command at all?

    • smart-log
    • get-feature
    • fw-log
    • show-regs
    Answer and reasoning

    show-regs reads the controller registers through a BAR0 mapping: PCIe memory reads, no SQE.

  3. In a tracepoint, cmd=(nvme_cmd_read slba=2048, len=15 …) on a 512-byte-LBA namespace transfers how much data?

    • 7.5 KiB
    • 15 KiB
    • 8 KiB
    • 16 KiB
    Answer and reasoning

    NLB is 0's-based: 16 blocks × 512 B = 8 KiB.

  4. Which statement about the Error Information log is correct?

    • It may not contain commands the host timed out and aborted
    • It records every failed I/O forever
    • It is maintained by the Linux driver
    • Its error_count field counts entries in the page
    Answer and reasoning

    The controller logs what it chooses; host-aborted commands may leave no entry; the ring overwrites; error_count is a unique incrementing identifier.

  5. Why can nvme0n1 belong to nvme1?

    Model answer

    With native multipath, namespace block devices are named after the subsystem instance, while nvmeN are controller instances; they are numbered independently. Use nvme list -v or list-subsys.

  6. MDTS = 6 and CAP.MPSMIN = 0. What is the maximum data transfer size?

    • 64 KiB
    • 128 KiB
    • 256 KiB
    • 6 × 4 KiB
    Answer and reasoning

    26 × 4 KiB = 256 KiB.

  7. Which source gives the time a command's SQE crossed the PCIe link?

    • nvme_setup_cmd
    • blktrace D action
    • nvme error-log
    • A PCIe analyzer (the MRd fetching the SQE)
    Answer and reasoning

    Kernel tracepoints and blktrace record driver/block-layer events; only the link view shows the fetch.

  8. Name two nvme-cli subcommands that read data but can still change device state, and why.

    Model answer

    get-log on AEN-tied logs without RAE (clears the event, e.g. Changed Namespace List); telemetry-log with host-initiated create (captures a new snapshot); persistent event log reads need a context. They change state without changing user data.

  9. Which file shows whether the kernel will issue Flush commands for durability?

    • queue/rotational
    • queue/write_cache
    • queue/scheduler
    • queue/nr_requests
    Answer and reasoning

    write back means a volatile write cache is present (Identify VWC), so the kernel sends Flush (or FUA) where durability is required.

  10. show-regs succeeds, but every nvme-cli admin query times out. What does this localize?

    Model answer

    The PCIe link and BAR decoding work (MMIO reads succeed). Admin command processing is stuck: firmware hang, controller fatal status (check CSTS.CFS), or an admin queue problem. The fault is inside the controller or in the admin queue setup, not the link.

Interview questions

  1. (Beginner) What is the difference between /dev/nvme0 and /dev/nvme0n1?

    Model answer

    The first is the controller's character device for admin commands; the second is a namespace exposed as a block device for I/O and filesystems.

  2. (Beginner) Which fields of the SMART log would you watch to predict a drive's end of life?

    Model answer

    percentage_used, available_spare versus its threshold, critical_warning, media_errors, and trend of data_units_written against rated endurance.

  3. (Intermediate) How does Linux derive max_hw_sectors_kb, and why does it matter?

    Model answer

    From MDTS × CAP.MPSMIN page size, capped by driver limits. It bounds request size; larger requests are split; sending larger would violate the controller's limit and fail with Invalid Field.

  4. (Intermediate) How would you measure per-command latency on a production server with minimal overhead?

    Model answer

    bpftrace or a BPF tool on nvme_setup_cmd/nvme_complete_rq keyed by (ctrl, qid, cid), aggregating into in-kernel histograms rather than printing per event; filter by queue or sample; keep the capture short; note the overhead in the report.

  5. (Advanced) A command appears in nvme_setup_cmd but never in nvme_complete_rq. List the possibilities in order of how you would test them.

    Model answer

    Still in flight (wait for timeout); the CQE was posted but the interrupt was lost (check /proc/interrupts, CQ contents, MSI-X masking); the controller never posted a CQE (firmware stuck on that command; check other commands on the same queue); the doorbell write never reached the device (link problem, analyzer); the capture ended or the trace buffer overflowed (check lost-event counts).

  6. (Advanced) Why might a SMART-polling agent cause latency spikes, and how would you prove it?

    Model answer

    Admin commands are served by firmware that may contend with I/O processing or trigger internal housekeeping. Prove it by correlating the agent's polling times (admin QID 0 tracepoints) with the I/O latency outliers, then disabling or slowing the agent and repeating.

  7. (Senior) How would you design a cross-layer trace correlation between Linux and a PCIe analyzer?

    Model answer

    Use (QID, CID) as the join key within time windows; anchor clocks with a distinctive event (an admin command with a unique CID or a doorbell value pattern); compute the offset and drift; handle CID reuse and the Linux generation bits; verify on a few hundred commands before trusting the join; report residual uncertainty.

  8. (Senior) A customer sends nvme-cli output from an old nvme-cli. What do you do before analysing it?

    Model answer

    Ask for the nvme-cli and kernel versions and, ideally, raw binary dumps (-b) or JSON. Old tools may mis-decode or omit fields added in newer specification revisions. Re-decode raw data with current tools and the 2.4 specification.

Chapter summary

nvme-cli queries the controller with real admin commands: Identify (06h) for identity and capabilities, Get Log Page (02h) for health, errors and firmware, Get Features (0Ah) for settings; show-regs reads the registers directly. Linux exposes its own view in /sys/class/nvme, /sys/class/nvme-subsystem and /sys/block/nvmeXnY/queue, whose values come from Identify fields. blktrace shows the block layer; the nvme_setup_cmd/nvme_complete_rq tracepoints show each NVMe command with QID and CID, the key to joining Linux traces with analyzer traces. Every subcommand belongs to a safety tier; practise on QEMU.
