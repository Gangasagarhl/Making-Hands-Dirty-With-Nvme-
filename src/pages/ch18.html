Every PCIe function carries a 4 KiB block of registers that tells software who it is, what it can do and how it is configured. This chapter teaches you to read that block byte by byte: the Type 0 header, the capability list, the PCI Express capability, MSI and MSI-X, power management, and the extended capabilities starting at 100h — finishing with a full manual decode of a synthetic dump of the course's Lab SSD.

Why this chapter exists

Configuration space is the one interface every PCI Express (PCIe) function must implement and every operating system can read. When a device misbehaves, its configuration space is the first evidence you collect: link speed and width, Max Payload Size, whether bus mastering is enabled, whether MSI-X is on, which errors have been logged. Tools like lspci -vvv decode it for you — but they decode it according to their own tables, they sometimes lag behind new capabilities, and when you look at a raw dump in a bug report, a firmware log or a protocol analyzer capture of configuration reads, there is no decoder at all. A senior engineer can read a hex dump of configuration space the way a mechanic reads a gauge cluster.

This chapter builds that skill. By the end, you will decode the Lab SSD's dump by hand and check your answers with a small Python decoder.

Learning objectives

  • Lay out the 64-byte Type 0 header from offset 00h (Vendor ID) to 3Fh (Max_Lat), stating the owner and purpose of every field.
  • Decode the Command and Status registers bit by bit, and explain which bits matter on PCIe.
  • Decode Class Code, Revision ID and Header Type; recognise NVMe's class code 01h/08h/02h.
  • Walk the capability list from the Capabilities Pointer (34h) and decode the Power Management, MSI, MSI-X and PCI Express capabilities.
  • Walk the extended capability list from 100h and decode the Advanced Error Reporting (AER) registers; recognise Device Serial Number, LTR, Secondary PCIe, L1 PM Substates and SR-IOV.
  • Read a raw lspci -xxxx-style dump, respecting little-endian byte order.
  • Know which fields Linux shows, and which a dump alone cannot tell you.

The story

Every new pupil arrives with a passport. The first page is the same for everybody: name, family, which class they belong to, which doors they use. After the first page, there is a chain of stickers: each sticker says what it is ("swimming certificate", "allergy card", "bus pass") and on which page the next sticker is. The teacher reads the first page, then follows the stickers from one to the next until a sticker says "no more". Later, the school glued a second, bigger book behind the passport for newer certificates, with its own chain starting on page 100.

A vehicle's registration document and service book. The first page has a fixed layout every inspector knows: manufacturer, model, vehicle category, engine number, registered owner's address. After that, the service book is a linked list of stamped entries, each with a type and a pointer to the next — brakes, emissions, tyre inspection — in no fixed order. Newer vehicles have an extended service book with longer entries and larger page numbers. An inspector who knows the first-page layout and the entry types can audit any vehicle without a manual.

Where the analogy breaks. (1) A passport is a passive record; configuration space is live: writing a bit can enable memory decoding, start DMA, change link speed or reset the function. (2) Some fields are not stored values at all — BARs return a different value depending on what you just wrote (sizing, Chapter 19). (3) Status bits are often "write 1 to clear": writing back what you read clears them, which a document never does. (4) The chain of stickers can be broken by a buggy device (pointing to itself, or into garbage), and software must defend against loops. (5) Different readers see different amounts: unprivileged Linux users see only the first 64 bytes through sysfs.

Beginner explanation

Configuration space is 4096 bytes per function. It has three regions:

  1. The header, 00h–3Fh (64 bytes). Fixed layout. Type 0 for Endpoints (like an NVMe SSD), Type 1 for bridges.
  2. The PCI-compatible capability area, 40h–FFh. A linked list of capability structures, each starting with a 1-byte ID and a 1-byte pointer to the next. The first one's location is in the header at 34h.
  3. The extended configuration space, 100h–FFFh. Only reachable through the Enhanced Configuration Access Mechanism (ECAM). Another linked list, of extended capabilities, starting at exactly 100h, each with a 4-byte header: 16-bit ID, 4-bit version, 12-bit next pointer.

Registers are little-endian: the byte at the lowest offset is the least significant. So when a dump shows 00: cd ab 20 04, the Vendor ID (offset 00h, 2 bytes) is ABCDh and the Device ID (02h) is 0420h.

Fields have owners. Read-only fields (IDs, class code, capability structures' "capability" registers) are set by the device's designer. Control fields (Command, BARs, Device Control, MSI-X Message Control) are written by firmware, the OS, or the driver. Status fields are set by hardware and cleared by software.

Class Code, Revision, Header Type

Class Code is three bytes: Base Class at 0Bh, Sub-Class at 0Ah, Programming Interface at 09h. For NVMe: 01h (mass storage controller), 08h (Non-Volatile Memory controller), 02h (NVM Express). The NVMe over PCIe Transport Specification 1.4 specifies this class code for NVMe I/O controllers; other programming-interface values in the 01h/08h family exist for other NVMe controller types — check the transport specification for the current list. The PCI-SIG's PCI Code and ID Assignment Specification is the master list of class codes and capability IDs.

SR-IOV (extended capability 0010h) — what to look for

An SR-IOV-capable NVMe controller (a Physical Function) has an SR-IOV extended capability containing: SR-IOV Capabilities and Control (VF Enable, VF Memory Space Enable, ARI Capable Hierarchy), InitialVFs and TotalVFs (how many Virtual Functions it can expose), NumVFs (how many software enabled), First VF Offset and VF Stride (which Routing IDs the VFs get), VF Device ID, supported and system page sizes, and six VF BARs — which describe one VF's BAR and are replicated for every VF. Uncertain Exact offsets of these fields: take them from the SR-IOV section of the PCI Express Base Specification. Our Lab SSD does not implement SR-IOV; Chapter 56 and Module 52 use a different synthetic device for it.

The ladder

A passport with a fixed first page and a chain of stickers, plus a newer, bigger book glued on behind.

Configuration space: a 64-byte fixed header, a linked list of capabilities from the pointer at 34h, and a linked list of extended capabilities from 100h.

A 4 KiB register file in each function's PCIe core. Some bits are constants, some are controls wired into the datapath (Memory Space Enable gates BAR decoding; Bus Master Enable gates the DMA engines' request path), some are sticky status set by error detectors.

Layouts are normative in the PCI Express Base Specification (Configuration Space chapter and each capability's section); IDs come from the PCI Code and ID Assignment Specification; NVMe's class code and BAR usage from the NVMe over PCIe Transport Specification.

Software reads and writes it with CfgRd0/CfgWr0 TLPs (1 DW, with byte enables) — always non-posted, always completed.

In a capture: configuration reads during enumeration and driver probe; a CfgWr0 to the Command register setting Bus Master; CfgWr0 to the MSI-X Message Control setting Enable. Each appears as a request/completion pair from the Root Complex.

Debugging: compare LnkCap with LnkSta (trained below capability?), DevCtl MPS with the Root Port's MPS (mismatch → Malformed TLPs), Command bits (BusMaster off → DMA impossible), AER status (which errors, on which end), MSI-X enable (interrupts not arriving).

Hardware view

Inside the device, configuration space is a set of flip-flops and small RAMs in the PCIe core, decoded on CfgRd0/CfgWr0 TLPs. Design details that leak into debugging:

  • Read-only values can be loaded at reset from on-chip fuses or an external EEPROM/flash ("config space initialisation"). If that load is slow, the device answers CRS (Chapter 17); if it fails, you may see default IDs from the IP vendor instead of the product's IDs.
  • Control bits are wired into the datapath. Memory Space Enable gates the BAR address comparators; Bus Master Enable gates the request path from the DMA engines; MSI-X Enable switches interrupt generation from INTx messages to memory writes.
  • Sticky bits (most AER status, some error logs) survive hot reset and FLR so errors that caused a reset are still visible afterwards — but not a power cycle.
  • Some registers are shadowed by firmware. In many SSDs, a microcontroller can modify configuration values (for example the Subsystem ID, or capability visibility) before link-up.

Configuration accesses are slow (each is a non-posted TLP with a completion; microseconds through ECAM) and serialised by the OS. Drivers read configuration space at probe and on errors, never in the I/O path. Everything performance-critical — doorbells, MSI-X table — lives in memory space behind a BAR.

Specification view

Normative sources: PCI Express Base Specification, Revision 6.x/7.0 — Configuration Space (header layouts, Command/Status, PCI Express Capability, extended capabilities including AER, SR-IOV, LTR, L1 PM Substates), PCI Code and ID Assignment Specification (class codes, capability and extended capability IDs), PCI Local Bus Specification 3.0 (legacy header fields and conventional-PCI meaning), PCI Bus Power Management Interface Specification (PM capability, now incorporated into the PCIe Base Specification), and for NVMe NVMe over PCIe Transport Specification 1.4 (class code, BAR0/BAR1 register mapping, required capabilities).

Type 0 header offsets from 00h Vendor ID to 3Fh Max_Lat as tabulated above; Capabilities Pointer at 34h; capability IDs 01h (PM), 05h (MSI), 10h (PCI Express), 11h (MSI-X); extended capabilities start at 100h with a 16/4/12-bit header; AER ID 0001h, Device Serial Number 0003h, SR-IOV 0010h; NVMe class code 01h/08h/02h; MPS/MRRS encoding 128 × 2n.

The "senior cross-checks" (LnkSta vs LnkCap, MPS vs Root Port, MSI vs MSI-X exclusivity, BusMaster consistency) are diagnostic practice derived from the rules, not specification text.

Capability order and offsets; which optional capabilities exist; vendor-specific capabilities; BAR count and size; MSI-X table location; whether Subsystem IDs are programmable; whether DLLLA reporting is implemented (optional for Endpoints).

New fields and capabilities appear in each PCIe revision (10-/14-bit tags, Flit Mode, higher speeds' physical-layer capabilities, Data Object Exchange, IDE for link encryption, TDISP-related structures). The PCI Express Capability version field reads 2 for all modern devices and does not tell you the revision. NVMe 2.4's TDISP information package relates to device security state, not to configuration-space layout itself.

Check in the specification: exact offsets inside newer extended capabilities; the full AER bit list for your revision; SR-IOV field offsets; which capabilities are required for which device types and speeds. The specification does not fix the order of capabilities or their offsets, and does not guarantee that a vendor-specific capability means the same thing across products from the same vendor.

Never assume a capability is at a fixed offset; never write back a whole Status register you just read (you will clear its RW1C bits); never trust a dump of FFh bytes as real data (the device may be gone); never decode new-revision bits with an old table.

Protocol view

Each configuration access is a 1-DWORD CfgRd0 or CfgWr0 with byte enables selecting which bytes of the DWORD are meant. Writing the 16-bit Command register at 04h is a CfgWr0 to register 01h (DWORD index; byte offset 04h) with First DW Byte Enables 0011b. The completion comes back from the device with its Completer ID.

def parse(text):
    cfg = bytearray(4096)
    for line in text.splitlines():
        if ":" not in line:
            continue
        off, _, rest = line.partition(":")
        try:
            base = int(off.strip(), 16)
            vals = [int(b, 16) for b in rest.split()]
        except ValueError:
            continue                      # skip lspci's own header line
        cfg[base:base + len(vals)] = bytes(vals)
    return cfg

def u8(c, o):  return c[o]
def u16(c, o): return struct.unpack_from("<H", c, o)[0]
def u32(c, o): return struct.unpack_from("<I", c, o)[0]

def decode(c):
    vid, did = u16(c, 0x00), u16(c, 0x02)
    if vid == 0xFFFF:
        print("Vendor ID FFFFh: no function (or it has gone away)"); return
    cmd, sts = u16(c, 0x04), u16(c, 0x06)
    print(f"00h Vendor ID {vid:04x}  02h Device ID {did:04x}")

Worked example

Problem. A bug report contains only these two lines from a different NVMe device's configuration space, and says "drive is slow":

70: 10 b0 02 00 22 80 00 10 1f 20 00 00 44 08 40 00
80: 40 00 21 10 00 00 00 00 00 00 00 00 00 00 00 00

The PCI Express capability is at 70h (ID 10h confirms). Decode what matters.

  1. DevCtl at 78h: bytes 1f 20 → 201Fh. MPS bits 7:5 = 000b → 128 B. MRRS bits 14:12 = 010b → 512 B. Relaxed Ordering (bit 4) on. Extended Tag (bit 8) off.
  2. LnkCap at 7Ch: 0040_0844h → 16.0 GT/s, x4.
  3. LnkSta at 82h: bytes 21 10 → 1021h. Current speed bits 3:0 = 1 → 2.5 GT/s. Width bits 9:4 = 02h → x2.

Conclusion. The link trained at 2.5 GT/s x2 instead of 16 GT/s x4: about 1/16 of the bandwidth. That alone explains "slow". MPS 128 B and Extended Tag off cost a little more but are secondary. Common mistakes

  • Reading bytes left to right as a big-endian number. cd ab is ABCDh.
  • Assuming fixed capability offsets ("PCIe cap is always at 70h").
  • Confusing the capability ID 10h (PCI Express) with extended ID 0010h (SR-IOV).
  • Decoding MSI-X Table Size as N instead of N − 1. 020h means 33 vectors.
  • Treating BAR contents as size. A BAR holds an address; size comes from sizing.
  • Thinking DLLLA = 0 on an Endpoint means the link is down. Reporting is optional and mainly for Downstream Ports.
  • Writing back the Status register and clearing evidence.
  • Trusting the PCI Express capability version (2) to tell the PCIe revision.

Debugging connection

A configuration-space checklist, in the order seniors run it on any NVMe incident:

  1. Vendor/Device ID valid (not FFFFh) — the device is reachable.
  2. Command: Mem+ and BusMaster+ — MMIO and DMA possible.
  3. Status error bits and AER status on the device and its upstream port.
  4. LnkSta versus LnkCap on both ends — speed and width.
  5. DevCtl MPS consistent along the path; MRRS sensible.
  6. MSI-X enabled, function not masked, vector count as expected.
  7. PMCSR in D0.
  8. Completion Timeout settings (DevCtl2) if Completion Timeouts are logged.

Capture configuration space early, before any reset or driver reload, and again after. Sticky AER bits plus Header Log are often the only record of the first error; a well-meaning recovery path that clears them destroys the evidence.

Senior engineer insight

Every bit has an owner. When a value is wrong, the first question is not "what does it mean?" but "who wrote it, and when?" — device reset defaults, device firmware, platform firmware, the OS PCI core, the driver, a hot-plug or error-recovery path, or a user with setpci. Many field incidents (MPS mismatch after hot reset, ASPM enabled by a BIOS update, MSI-X masked after a failed resume) are ownership bugs.

Store a full configuration dump of every device model at a known-good state, per platform. Diffing a failing system against the golden dump finds misconfigurations in seconds; the course's golden-trace methodology applies equally to configuration space.

Challenge

Modify one byte of the dump so the capability chain loops (e.g. MSI-X next → 40h). Confirm the decoder terminates. Then corrupt the extended chain to point at 0FFCh with a header of FFFF_FFFFh and check the behaviour.

Hint

DevCtl is the low half of the DWORD at 78h; DWORD index 78h ÷ 4 = 1Eh.

Solution

Answers are in the decode tables above. (1) 0x0100 (bus 01, device 0, function 0); it is not stored in configuration space as a field — the device captures bus and device numbers from configuration writes and the function number is its own. (2) Register 1Eh with First DW Byte Enables 0011b. (3) MSI is a simpler fallback for systems or drivers that do not use MSI-X; only one may be enabled at a time. Challenge: the seen set breaks the loop; the FFFF_FFFFh header stops the extended walk.

What a senior engineer notices

Whether the values are coherent as a system: MPS identical along the path, link at capability, error enables consistent with the platform's AER mode, MSI-X table inside BAR0's 16 KiB. Individually plausible values that contradict each other are the bug.

Failure variants

  • Dump taken without root: only 64 bytes — the capability list appears empty.
  • Dump from a device in D3hot: some registers may read differently; check PMCSR first.
  • Dump of a VF: many header fields read as zero by definition (Vendor ID of a VF reads FFFFh); interpret with the SR-IOV rules.

Model answers

(1) Command: I/O, Memory and Bus Master enabled. Status: Capabilities List, and bit 13 Received Master Abort — the function received an Unsupported Request completion for one of its requests. (2) 0x5050: bits 7:5 = 010b → MPS 512 B; bits 14:12 = 101b → MRRS 4096 B; bit 4 = 1 → Relaxed Ordering enabled. (3) ID 0010h (SR-IOV), version 1, next 2C0h. (4) Table Size 03Fh → 64 vectors; Enable (bit 15) = 0 → disabled. (5) Speed code 3 → 8.0 GT/s; width bits 9:4 = 08h → x8.

    • 32 vectors

  6. Which Command bit must be 1 before an NVMe controller may fetch commands from host memory?

    • bit 0
    • bit 1
    • bit 2
    • bit 10
    Answer and reasoning

    Bus Master Enable (bit 2) permits the function to issue memory requests.

  7. Open: Why can't you learn a BAR's size from a configuration dump?

    Model answer

    The BAR contains the assigned base address; its size is encoded by which low-order address bits are hard-wired to zero, which only shows when you write all ones and read back. A dump shows the current address, not the read-back after sizing.

  8. Open: Which two registers do you compare to detect a link trained below capability, and on which devices?

    Model answer

    Link Capabilities (Max Link Speed, Maximum Link Width) and Link Status (Current Link Speed, Negotiated Link Width), on both the device and its upstream port — the link runs at the lower of the two capabilities, so both must be checked.

  9. Open: AER Uncorrectable Error Severity reads 0x00462030. Name the fatal errors.

    Model answer

    Bits 4, 5, 13, 17, 18, 22: Data Link Protocol Error, Surprise Down, Flow Control Protocol Error, Receiver Overflow, Malformed TLP, Uncorrectable Internal Error.

Interview questions

  1. Beginner: What are the three regions of PCIe configuration space?

    Model answer

    The 64-byte header (00h–3Fh), the PCI-compatible capability area (40h–FFh) and the extended configuration space (100h–FFFh), reachable through ECAM.

  2. Beginner: How do you find the PCI Express capability?

    Model answer

    Read the Capabilities Pointer at 34h, then follow the linked list (ID byte, next byte) until you find ID 10h.

  3. Intermediate: What is the difference between MSI and MSI-X configuration?

    Model answer

    MSI keeps one address/data pair in configuration space and allows up to 32 contiguous vectors with a shared address; MSI-X keeps a table of independent address/data/mask entries (up to 2048) in a BAR, with the capability pointing to it via BIR and offset.

  4. Intermediate: Walk me through what you check in lspci -vvv for a slow NVMe drive.

    Model answer

    LnkSta vs LnkCap (both ends), MPS/MRRS, ASPM settings in LnkCtl, AER correctable status (replays), MSI-X enabled, D0 power state, Relaxed Ordering/No Snoop enables, then NUMA node and IOMMU.

  5. Advanced: After a firmware update, some hosts log Malformed TLPs from an SSD. What configuration evidence would you gather?

    Model answer

    DevCap MPS supported and DevCtl MPS on device and every port in the path; AER Header Log at the Root Port to see the offending TLP's length; whether the firmware update changed DevCap; the OS MPS policy; and whether the problem occurs after hot reset or resume (paths where MPS might be reset).

  6. Senior: How would you build a regression test for configuration space across device firmware releases?

    Model answer

    Capture full 4 KiB dumps after cold boot, warm reset, FLR and D3hot→D0 for each release; mask fields that legitimately vary (serial number, assigned BARs, status bits); diff against golden; additionally test read-only bits are read-only, RW1C semantics, capability chain integrity and reset defaults. Flag any added/removed capability for review.

Chapter summary

Configuration space is 4 KiB per function: a fixed 64-byte header, a capability list from the pointer at 34h, and an extended capability list from 100h. The Type 0 header identifies the function (Vendor/Device ID, Class Code 01h/08h/02h for NVMe, Revision), controls it (Command: Memory Space, Bus Master, Interrupt Disable), reports coarse status, and holds BARs, Subsystem IDs, the Capabilities Pointer and legacy interrupt fields. Capabilities — Power Management, MSI, PCI Express (device and link capabilities, control and status, MPS/MRRS, speed/width), MSI-X (table in a BAR) — are found by walking the list. Extended capabilities such as AER, Device Serial Number, LTR, Secondary PCIe, L1 PM Substates and SR-IOV are found by walking from 100h. Values are little-endian; every field has an owner; dumps show current values, not BAR sizes or history.

Do not move on until you can:

  • recite the Type 0 header offsets from 00h to 3Fh with each field's owner
  • decode Command and Status by bit
  • walk both capability lists by hand from a hex dump
  • decode MPS, MRRS, link speed and width from the PCI Express capability
  • decode MSI-X Message Control, Table and PBA registers
  • read AER status, mask and severity registers and name the bits
  • state what a dump cannot tell you
