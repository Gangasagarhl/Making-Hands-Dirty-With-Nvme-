Things engineers commonly get wrong about Non-Volatile Memory Express (NVMe) and PCI Express (PCIe) — forty-eight of them, each taken apart the same way: the wrong belief, why smart people hold it, the correct model, the evidence that settles it, and the chapter that teaches it properly. Use this page as a self-test before interviews, design reviews and debugging sessions.

How to use this page

A misconception is rarely ignorance. It is usually a model that was correct somewhere — in an older technology, in a simpler case, at a higher level of abstraction — and is now applied where it does not fit. That is why each entry below explains why people believe it: if you understand where the wrong model comes from, you will recognize its relatives.

Every entry has the same five parts:

The wrong belief
Stated the way people actually say it.
Why people believe it
The legitimate experience or simplification behind it.
The correct model
What is actually true, with the layer and the owner named.
Evidence that proves it
Something you can observe — a register, a trace, a command output, a specification structure — rather than an appeal to authority.
Where it is taught
The chapter that builds the full model.

Three technologies appear throughout, and keeping them apart is the first discipline of this course: PCI Express (PCIe), the interconnect, specified by PCI Special Interest Group (PCI-SIG); Non-Volatile Memory Express (NVMe), the storage interface and command sets, specified by the NVM Express consortium (NVM stands for non-volatile memory); and the NVMe over PCIe Transport specification, which joins them. Several misconceptions below are simply these three collapsed into one.

Before opening each entry, read only its heading and say out loud what the correct model is and what evidence you would collect. Then compare. Tick the entries you got fully right in the mastery gate at the bottom; revisit the others after reading the linked chapter. Evidence examples on this page that look like command output are illustrative; real output varies by tool version and device.

Where NVMe meets PCIe

These eight are the misconceptions the master curriculum names explicitly. They all come from blurring the boundary between the storage protocol and the interconnect.

NVMe is the same thing as PCIe

The wrong belief
"NVMe drives are PCIe drives; NVMe is just the name for storage over PCIe."
Why people believe it
Almost every NVMe device a person handles is a PCIe card or M.2 module, and marketing uses "PCIe solid-state drive (SSD)" and "NVMe SSD" interchangeably.
The correct model
PCIe is a general-purpose interconnect that carries memory reads and writes, configuration requests and messages for any kind of device (graphics processing units, network interface cards, accelerators). NVMe is a storage interface: queues, commands, completions, controller registers, namespaces. NVMe runs over PCIe through the NVMe over PCIe Transport specification, but it also runs over Remote Direct Memory Access (RDMA) and Transmission Control Protocol (TCP) (NVMe over Fabrics), where there is no PCIe between host and controller at all.
Evidence that proves it
The NVMe specification family lists separate transport specifications (PCIe, RDMA, TCP). A PCIe analyzer shows only generic Transaction Layer Packets (TLPs) — memory reads and writes — and needs to be told where the queues live to decode NVMe. An NVMe/TCP namespace (nvme list showing a fabrics transport) has no PCIe function behind it.
Where it is taught
Chapter 21 — What Is NVMe?, Chapter 22 — NVMe 2.x Architecture, Chapter 65 — NVMe-oF Mental Model.

PCIe is the NVMe protocol

The wrong belief
"The NVMe protocol is defined by PCIe packets; to understand NVMe I study TLPs."
Why people believe it
On a PCIe system every NVMe action does produce TLPs, and analyzers present "NVMe decode" views on top of PCIe captures.
The correct model
The NVMe protocol is defined in terms of memory-resident data structures (Submission and Completion Queues, Physical Region Page (PRP) lists, Scatter Gather Lists (SGLs)) and controller registers. PCIe only carries the memory accesses that read and write them. The protocol would be the same if the memory accesses traveled on a different interconnect; indeed NVMe over Fabrics carries the same commands as capsules.
Evidence that proves it
The NVMe Base Specification defines a 64-byte Submission Queue Entry and 16-byte Completion Queue Entry without reference to TLP formats. In a trace, the Submission Queue Entry (SQE) appears as the payload of a Completion with Data answering the controller's Memory Read — the NVMe structure is the cargo, not the packet.
Where it is taught
Chapter 22, Chapter 39 — The Most Important Chapter.

The NVMe command set is the transport

The wrong belief
"Read and Write are part of NVMe over PCIe."
Why people believe it
Before NVMe 2.0 everything lived in one document, so command definitions, register definitions and PCIe-specific details sat side by side.
The correct model
Since NVMe 2.0 the family is split: the Base specification (common architecture, Admin commands, queues, status), I/O command set specifications (NVM, Zoned Namespaces, Key Value, Subsystem Local Memory, Computational Programs) and transport specifications (PCIe, RDMA, TCP). Read and Write are defined in the NVM Command Set; doorbells and Message Signaled Interrupts – Extended (MSI-X) interrupts are in the PCIe Transport specification.
Evidence that proves it
The 2026 baseline lists NVM Command Set 1.3 and NVMe over PCIe Transport 1.4 as separate documents with separate revision numbers. Identify Controller reports which I/O command sets a controller supports independently of its transport.
Where it is taught
Chapter 22, Chapter 31 — NVM Command Set.

A TLP is the same as an NVMe command

The wrong belief
"The host sends the Read command to the SSD in a TLP."
Why people believe it
It is how network protocols usually work: the request travels in a packet to the server.
The correct model
The host writes the 64-byte command into a Submission Queue in host memory and then writes a 4-byte doorbell value to the controller. The controller fetches the command itself with a Memory Read request; the command arrives at the controller as the payload of a Completion with Data. One NVMe command therefore produces many TLPs (doorbell, SQE fetch and its completion, data movement, Completion Queue Entry (CQE) write, interrupt) and one TLP can carry parts of several commands (a 256-byte fetch can return four SQEs).
Evidence that proves it
In any PCIe capture of NVMe I/O, the only host-to-device TLP at submission time is a 4-byte Memory Write (MWr) to an address in BAR0 at offset 1000h or above (a doorbell). The SQE contents appear in a downstream Completion with Data (CplD) answering an upstream Memory Read (MRd).
Where it is taught
Chapter 41 — Command-to-TLP Correlation, Command vs Packet vs Completion.

A PCIe completion is the NVMe completion

The wrong belief
"When the SSD sends the completion TLP, the command is done."
Why people believe it
Both are called "completion", and both mean "your request has been answered".
The correct model
A PCIe Completion (Cpl or CplD) answers one non-posted PCIe request — a memory read, configuration access or I/O access — and travels from completer to requester. An NVMe completion is a 16-byte Completion Queue Entry that the controller writes into host memory with a posted Memory Write. During an NVMe Read, the host does not receive any PCIe completion from the device at all: the data and the CQE arrive as posted writes. The PCIe completions flow toward the device, answering its reads of the SQE and of write data.
Evidence that proves it
In a trace, CQEs appear as MWr TLPs to the Completion Queue address (16 bytes), while CplD TLPs carry the Requester ID of the device and the Tag of the device's own MRd. A Completion Timeout is a PCIe error about a missing Cpl; an NVMe command timeout is a host driver's timer on a missing CQE.
Where it is taught
Chapter 12 — Posted vs Non-Posted, Chapter 52 — Completion Rules, Command vs Packet vs Completion.

PCIe generation is NVMe revision

The wrong belief
"A Gen5 SSD supports NVMe 2.0 features" or "NVMe 2.4 needs PCIe 6.0".
Why people believe it
New drives tend to arrive with both a newer link and a newer NVMe revision, and product briefs list them together.
The correct model
PCIe generation (link speed: 2.5, 5, 8, 16, 32, 64, 128 gigatransfers per second, GT/s) is negotiated by the physical and data link layers and reported in PCIe capability registers. NVMe revision is reported by the controller's Version register (VS, offset 08h) and governs which NVMe features the controller may implement — most of which are optional anyway. A Gen3 device can implement NVMe 2.x; a Gen5 device can implement NVMe 1.4.
Evidence that proves it
lspci -vvv shows the Link Capabilities (LnkCap) and Link Status (LnkSta) registers, which report supported and negotiated link speed and width; nvme id-ctrl reports the version field and the optional-feature bits. They vary independently across products.
Where it is taught
Chapter 6 — PCIe Generations, Chapter 24 — NVMe Registers.

M.2 means NVMe

The wrong belief
"It's an M.2 drive, so it's NVMe."
Why people believe it
Most current M.2 SSDs are NVMe, and the M.2 form factor became popular at the same time as NVMe.
The correct model
M.2 is a mechanical and electrical form factor whose connector can carry Serial ATA (SATA), PCIe, Universal Serial Bus (USB) and other interfaces depending on the module and slot keying. An M.2 SATA SSD uses the AT Attachment (ATA) command set through an Advanced Host Controller Interface (AHCI) host controller. Likewise U.2, U.3, Enterprise and Data Center Standard Form Factor (EDSFF) (E1/E3) and add-in cards are form factors; NVMe is the storage interface spoken across them.
Evidence that proves it
An NVMe controller appears in PCIe configuration space with class code 01h (mass storage), subclass 08h (non-volatile memory), programming interface 02h (NVMe). An M.2 SATA drive appears behind a SATA/AHCI controller (subclass 06h) and is handled by the ahci driver, showing up as /dev/sdX, not /dev/nvme*.
Where it is taught
Chapter 3 — From SATA/SAS to NVMe, Chapter 5 — PCIe Physical Architecture.

SSD latency is the same as PCIe latency

The wrong belief
"Gen5 halves the SSD's latency" or "this 80 µs read must be a slow link".
Why people believe it
Faster links do reduce transfer time, and bandwidth and latency are often conflated.
The correct model
End-to-end read latency is the sum of host submission, doorbell propagation, SQE fetch round trip, controller firmware, NAND (Not-AND gate based) flash read (tens of microseconds for triple-level cell (TLC)), data transfer, CQE and interrupt delivery, and host completion processing. PCIe transfer of 4 KiB at Gen4 x4 is roughly one to two microseconds; the NAND read dominates. Link speed matters for large transfers and bandwidth, little for small-I/O latency.
Evidence that proves it
A trace of a 4 KiB read shows the gap between SQE fetch and the first data MWr is tens of microseconds — the media — while the data burst itself occupies around a microsecond. Running the same drive at a forced lower link speed changes 4 KiB latency only slightly but changes 128 KiB throughput a lot.
Where it is taught
Chapter 32 — READ, Performance Engineering.

PCIe misconceptions

A wider link makes every transaction faster in proportion

The wrong belief
"x8 is twice as fast as x4, so latency halves."
Why people believe it
Bandwidth does scale roughly with lane count, and bandwidth is what datasheets advertise.
The correct model
Width shortens the serialization time of each packet; it does not shorten fixed delays (propagation, switch and root complex processing, memory access, device firmware). For small packets the fixed parts dominate. Width also cannot help when the bottleneck is elsewhere (media, tags, credits).
Evidence that proves it
A Gen4 lane carries roughly 2 bytes per nanosecond, so a 256-byte payload TLP (about 280 bytes with framing and headers) takes about 35 ns to serialize at x4 and about 18 ns at x8, while an MRd round trip through a root complex is commonly hundreds of nanoseconds to a microsecond. Use the calculators to compare.
Where it is taught
Chapter 6, Mathematics for Storage and Links.

Link up means the device is healthy

The wrong belief
"Link Training and Status State Machine (LTSSM) reached L0, so the hardware is fine and the problem is software."
Why people believe it
Link training failure is the most visible hardware failure; once it passes, hardware seems "done".
The correct model
L0 means the physical and data link layers can exchange packets. The link may have trained at a lower speed or width than capable, may be running with a high replay rate, and the device's function may still fail enumeration, Base Address Register (BAR) sizing, or — for NVMe — controller enable (the Controller Status register's ready bit CSTS.RDY never set, or its Controller Fatal Status bit CSTS.CFS set).
Evidence that proves it
Compare LnkCap with LnkSta (speed and width); check correctable error counters; read CSTS after enable. All three can be bad on a link that is "up".
Where it is taught
Chapter 8 — PCIe LTSSM, Chapter 9 — Link Training, Chapter 24.

Every PCIe write is acknowledged by the receiver

The wrong belief
"The doorbell write was acknowledged, so the controller has seen it."
Why people believe it
Analyzers show ACK Data Link Layer Packets (DLLPs) after every TLP, and many bus protocols acknowledge writes end to end.
The correct model
Memory Writes are posted: they have no completion. The Acknowledgement (ACK) DLLP is a data-link-layer acknowledgement between the two ends of one link, saying "this TLP arrived intact on this link", not "the target processed it". Through a switch, the host's ACK comes from the switch, not the SSD. Software that needs to know a posted write has reached the device performs a read to the same device (the read cannot pass the earlier write).
Evidence that proves it
TLP type MWr has no corresponding Cpl in any trace. ACK DLLPs carry a sequence number, not a tag or requester ID.
Where it is taught
Chapter 12, Chapter 15 — DLLP, Chapter 14 — PCIe Ordering.

Configuration space and BAR space are the same kind of memory

The wrong belief
"NVMe registers like Controller Configuration (CC) and CSTS are in the PCIe configuration space."
Why people believe it
Both are "registers on the device", and Linux exposes both under /sys/bus/pci/devices/….
The correct model
Configuration space (256 bytes legacy, 4 KiB extended) holds PCI-defined headers and capabilities and is reached with Configuration Read/Write requests (generated by the root complex, often from Enhanced Configuration Access Mechanism (ECAM) memory accesses). NVMe controller registers live in memory space decoded by BAR0, reached with ordinary Memory Read/Write TLPs. The BAR register itself is in configuration space; what it points to is not.
Evidence that proves it
On a trace, accessing CC produces MRd/MWr TLPs to the BAR0 address (e.g. 0xFE60_0014 on the course's lab system), while reading the Device ID produces a CfgRd0 TLP with bus/device/function routing.
Where it is taught
Chapter 18 — Configuration Space, Chapter 19 — BARs and MMIO.

PCIe tags are NVMe command identifiers

The wrong belief
"Tag 0x21 in the trace is command 0x21."
Why people believe it
Both are small integers used to match responses to requests.
The correct model
A PCIe tag is chosen by a requester for each outstanding non-posted request and is unique only together with the Requester ID while the request is outstanding; the same tag is reused within microseconds. An NVMe Command Identifier (CID) is chosen by the host driver and is unique among outstanding commands on one Submission Queue. One NVMe command typically consumes several tags (SQE fetch, data reads); posted writes have tags that carry no matching meaning.
Evidence that proves it
Decode an SQE from a CplD: its CID (bytes 2–3) bears no relation to the tag of the CplD that carried it. The CQE's CID matches the SQE's, not any tag.
Where it is taught
Chapter 13 — PCIe Tags, Chapter 29 — NVMe Command Structure.

A bigger Max Payload Size is always better and can be set freely

The wrong belief
"The device supports 512-byte Max Payload Size (MPS), so set 512."
Why people believe it
Larger payloads reduce header overhead, and the capability register advertises the maximum.
The correct model
MPS must be configured consistently along the path: a TLP larger than a receiver's configured MPS is a Malformed TLP. System software normally sets MPS to the minimum supported along the hierarchy. The efficiency gain from 256 to 512 bytes is a few percent; larger packets also increase buffer needs and can add latency for other traffic. Max Read Request Size is a separate, per-function setting.
Evidence that proves it
The Device Capabilities register (DevCap) reports the maximum payload supported; the Device Control register (DevCtl) reports the configured value; they differ on most systems. A misconfigured MPS shows Malformed TLP errors in Advanced Error Reporting (AER).
Where it is taught
Chapter 11 — TLP Header Anatomy, Chapter 53 — Flow Control and Credits.

Any replay on the link is a failure

The wrong belief
"We saw a Negative Acknowledgement (NAK) and a replay — the link is broken."
Why people believe it
A NAK looks like an error, and analyzers highlight it in red.
The correct model
The data link layer's replay mechanism exists precisely to recover from occasional bit errors invisibly to the transaction layer. A low, stable rate of replays is normal at high data rates. What matters is the trend and the rate relative to traffic, and whether replays escalate (replay number rollover, retraining, recovery entries).
Evidence that proves it
AER correctable status bits (Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover) and their counts over time; LTSSM Recovery entries in the analyzer.
Where it is taught
Chapter 15, Deep-Dive Module 16 — DLLP and Replay.

Correctable errors can be ignored

The wrong belief
"They're correctable, the hardware fixed them, nothing to see."
Why people believe it
Individually they are harmless, and many systems log them at a low level or rate-limit the messages.
The correct model
Correctable errors are the early warning system. A rising rate signals marginal signal integrity (connector, retimer, equalization, temperature), and they cost bandwidth through replays. A link that throws thousands of correctable errors per hour is one bad day away from uncorrectable errors or downtraining.
Evidence that proves it
Linux exposes AER counters per device in sysfs (aer_dev_correctable); correlate their rate with temperature, workload and link speed. Forcing the link to a lower speed usually makes them vanish — a classic margin diagnosis.
Where it is taught
Chapter 45 — PCIe Errors, Chapter 54 — Equalization.

Moving to a newer PCIe generation doubles application performance

The wrong belief
"Gen5 SSD: twice as fast as Gen4."
Why people believe it
Each generation doubles the per-lane rate, and sequential benchmarks of top drives roughly track it.
The correct model
Only workloads limited by link bandwidth benefit proportionally. Small random I/O is limited by media latency, controller parallelism and host software; a database doing 4 KiB random reads at low queue depth may see almost no change. The device's back end (NAND channels, dies) must also be able to supply the extra bandwidth.
Evidence that proves it
Measure the same workload with the link forced to the lower generation (where the platform allows): sequential throughput changes, 4 KiB QD1 latency barely moves.
Where it is taught
Chapter 6, Performance Engineering.

NVMe misconceptions

The controller is the namespace

The wrong belief
"/dev/nvme0 is the drive, and the drive is the storage."
Why people believe it
Most client SSDs expose exactly one controller with exactly one namespace, so the distinction never shows.
The correct model
A controller is the interface that processes commands: registers, queues, the command engine. A namespace is a quantity of formatted storage, addressed by logical block address (LBA), identified by a Namespace Identifier (NSID). One controller can have many namespaces attached; a namespace can be shared by several controllers in an NVM subsystem (multipath, dual-port drives). Admin commands target the controller; I/O commands name a namespace.
Evidence that proves it
Identify with Controller or Namespace Structure (CNS) for the active namespace list returns several NSIDs on enterprise drives; Linux creates /dev/nvme0n1, /dev/nvme0n2 for them while /dev/nvme0 remains the controller character device. Every I/O SQE carries an NSID in Dword 1.
Where it is taught
Chapter 23 — NVMe Controller, Chapter 58 — Namespaces.

The queue is the doorbell

The wrong belief
"Submission Queue 1 is at BAR0 + 1008h."
Why people believe it
Doorbells are named after queues (SQ1 Tail Doorbell), and in traces the doorbell is the only visible host action.
The correct model
For NVMe over PCIe, the queue is a ring of entries in host memory (or in a Controller Memory Buffer). The doorbell is a 32-bit register in the controller's BAR that holds only an index: the new tail (for a Submission Queue (SQ)) or new head (for a Completion Queue (CQ)). The base address and size of the queue were given to the controller when the queue was created (ASQ/Admin Completion Queue Base Address (ACQ)/Admin Queue Attributes (AQA) registers for the Admin queues; Create I/O SQ/CQ commands for I/O queues).
Evidence that proves it
A doorbell MWr carries a 4-byte value such as 0x00000006; the controller then issues an MRd to an address in host memory (the queue slot), not to its own BAR.
Where it is taught
Chapter 25 — Queue Architecture, Chapter 28 — Doorbells.

The doorbell is the command

The wrong belief
"Writing the doorbell sends the command to the SSD."
Why people believe it
It is the moment the controller learns about the command, and in older register-based interfaces writing a command register did start the operation.
The correct model
The doorbell says "entries up to this index are valid". One doorbell write can announce one command or a hundred. The controller decides when to fetch, how many entries per fetch, and in what order across queues (arbitration). Writing the doorbell before the SQE is visible in memory is a classic bug: the controller can fetch a stale entry.
Evidence that proves it
In traces, a single doorbell often moves the tail by several entries and is followed by one larger MRd (e.g. 256 bytes for four SQEs). The driver code places a write memory barrier between filling the SQE and writing the doorbell.
Where it is taught
Chapter 28, Deep-Dive Module 27 — Doorbells.

DMA is a CPU copy

The wrong belief
"The driver copies the data to the SSD."
Why people believe it
At the application level, write() looks like copying, and buffered I/O really does copy into the page cache.
The correct model
With Direct Memory Access (DMA), the device is the bus master: the NVMe controller issues PCIe memory requests to read host memory (for writes) or write host memory (for reads). The central processing unit (CPU) only describes where the buffers are (PRP or SGL) and is free to do other work. With an input–output memory management unit (IOMMU), the device's addresses are I/O virtual addresses translated by the IOMMU.
Evidence that proves it
Data TLPs carry the device's Requester ID (0x0100 on the lab system), not the root complex's. CPU utilization for large direct I/O is low relative to bandwidth.
Where it is taught
Chapter 20 — DMA, Chapter 36 — Physical Region Pages.

Commands in a Submission Queue complete in order

The wrong belief
"SQ is a first-in, first-out (FIFO), so completions come back in submission order, and a later write to the same LBA wins."
Why people believe it
Queues are FIFOs for fetching, and at low load completions often do come back in order.
The correct model
The controller fetches entries in order from each SQ, but may execute and complete them in any order. NVMe defines no ordering between separate commands (fused Compare-and-Write is the narrow exception). The host must wait for completion before issuing a dependent command.
Evidence that proves it
CQE CIDs arrive out of order under mixed workloads (a 4 KiB read submitted after a 1 MiB read usually completes first). The CQE's SQ Head Pointer reflects fetching progress, not completion order.
Where it is taught
Chapter 25, Chapter 33 — WRITE.

A successful completion means the data is durable

The wrong belief
"The write completed successfully, so it will survive a power cut."
Why people believe it
"Complete" sounds final, and many enterprise drives (with power-loss protection) do behave that way.
The correct model
If the controller has an enabled volatile write cache, a successful Write completion guarantees that later reads see the data, not that it is on non-volatile media. Durability needs Force Unit Access (FUA) on that write, or a Flush submitted after the write completed, or a controller that reports no volatile write cache.
Evidence that proves it
Identify Controller's Volatile Write Cache (VWC) field bit 0; Get Features for the Volatile Write Cache feature (06h); power-cut tests showing completed but unflushed writes reverting to old data.
Where it is taught
Chapter 33 — WRITE, Chapter 34 — FLUSH.

Flush is a barrier that orders everything around it

The wrong belief
"Submit writes, Flush, then the commit write — the Flush keeps them in order."
Why people believe it
Operating systems once used "barrier" requests with ordering semantics, and the word flush suggests "everything before this, then everything after".
The correct model
Flush covers writes to the namespace that completed before the Flush was submitted. Writes still in flight are not covered, and commands submitted after the Flush may complete — even become durable — before it. Ordering comes only from the host waiting for completions.
Evidence that proves it
The Flush command's scope definition in the Base specification; traces where commands submitted after a long Flush complete before it.
Where it is taught
Chapter 34 — FLUSH.

Deallocate (TRIM) erases the data

The wrong belief
"I trimmed the drive, so the data is gone."
Why people believe it
Trimmed blocks often read back as zeros immediately.
The correct model
Dataset Management with Deallocate updates the flash translation layer (FTL)'s mapping. The NAND pages holding old data are only erased when garbage collection reclaims their block, which may be much later. What reads return is governed by Deallocate Logical Block Features (DLFEAT) (zeros, FFh or not reported) and only for blocks actually deallocated. Secure destruction requires Sanitize or a secure Format NVM.
Evidence that proves it
DLFEAT in Identify Namespace; the existence of separate Sanitize (Admin 84h) and Format NVM (Admin 80h) commands with explicit erase semantics; forensic recovery of trimmed data from raw NAND.
Where it is taught
Chapter 35 — Dataset Management.

NLB is the number of blocks

The wrong belief
"Number of Logical Blocks (NLB) = 8 reads 4 KiB on a 512-byte-LBA namespace."
Why people believe it
Field names suggest counts, and many application programming interfaces (APIs) use counts.
The correct model
Many NVMe count fields are 0's based: Read/Write NLB, Dataset Management Number of Ranges (NR), queue sizes in Create I/O Queue commands and AQA. NLB = 7 means 8 blocks. Some are not: the Length in a Dataset Management range is a plain count. Always check the "0's based" note in the field description.
Evidence that proves it
A Read with NLB = 7 on a 512-byte-LBA namespace produces 4,096 bytes of data MWrs in a trace; the Linux tracepoint shows the request length in bytes.
Where it is taught
Chapter 29, Chapter 31.

The Command Identifier is globally unique

The wrong belief
"CID 0x0045 identifies the command; search the log for it."
Why people believe it
It is called an identifier, and in single-queue tests it appears unique.
The correct model
The CID is unique only among commands outstanding on one Submission Queue at one time. The same CID appears on every queue and is reused as soon as the previous command with it completes. A command is identified by (controller, SQ ID, CID, time window).
Evidence that proves it
The CQE carries both SQ Identifier and CID because the CID alone is ambiguous; Linux encodes a generation counter into CIDs in recent kernels to detect stale completions.
Where it is taught
Chapter 29, Chapter 41.

Every completion raises an interrupt, and interrupts are required

The wrong belief
"One command, one MSI-X message."
Why people believe it
At low load with default settings, that is what traces show.
The correct model
A CQ may be created with interrupts disabled, in which case the host polls. With interrupts enabled, interrupt coalescing (Feature: Interrupt Coalescing) may let the controller send one interrupt for several completions, and the driver processes every new CQE it finds (by the Phase tag) in one handler run. Several CQs may share a vector.
Evidence that proves it
Trace counts: CQE MWrs outnumber MSI-X MWrs under load. Linux polled queues (nvme.poll_queues) generate no interrupts for their CQs.
Where it is taught
Chapter 42 — Interrupt Architecture, Chapter 43 — MSI-X.

Linux misconceptions

lspci's link speed proves the bandwidth

The wrong belief
"LnkSta says 16GT/s x4, so the drive gets 8 GB/s."
Why people believe it
It is the most prominent number in lspci -vvv.
The correct model
LnkSta reports negotiated speed and width — the ceiling. Achieved bandwidth is reduced by encoding, TLP and DLLP overhead, MPS and Max Read Request Size (MRRS) choices, credits, tags, the root complex and memory system, and the device back end. Also check that LnkSta matches LnkCap: a downtrained link is reported honestly there and often missed.
Evidence that proves it
Compute the theoretical payload rate with the calculators (Gen4 x4 ≈ 7.88 GB/s raw, roughly 7 GB/s of payload at MPS 256) and compare with measured throughput.
Where it is taught
Chapter 69 — Linux PCIe Inspection.

/dev/nvme0 and /dev/nvme0n1 are the same device

The wrong belief
"Run the Identify Namespace on /dev/nvme0 and fio on /dev/nvme0 too."
Why people believe it
Both appear when a drive is installed and many nvme-cli commands accept either.
The correct model
/dev/nvme0 is a character device for the controller (Admin commands, passthrough). /dev/nvme0n1 is a block device for namespace 1 (filesystems, block I/O). /dev/ng0n1 is a per-namespace character device for passthrough I/O. With native NVMe multipath, the block device may represent a namespace reachable through several controllers. Controller numbering is not guaranteed stable across boots; use /dev/disk/by-id/.
Evidence that proves it
ls -l /dev/nvme* shows c and b device types; /sys/class/nvme/nvme0/ lists the namespaces under it.
Where it is taught
Chapter 70 — Linux NVMe Inspection.

An NVMe timeout in dmesg means the SSD hung

The wrong belief
"The kernel says I/O timeout, aborting — the drive froze."
Why people believe it
The message names the NVMe device, and the obvious explanation is that it stopped responding.
The correct model
A timeout means the driver did not observe a completion in time. Causes include a device that never posted the CQE, but also a CQE that was posted but whose interrupt was lost or misrouted (MSI-X misconfiguration, IOMMU interrupt remapping, CPU offline), a CQ the driver is not polling, or an IOMMU fault that blocked the CQE write. The Linux driver checks the CQ before declaring a timeout and logs when it finds a completion "polled" — a strong hint the interrupt path is at fault.
Evidence that proves it
Kernel messages that mention completions found by polling; /proc/interrupts counts for the NVMe vectors; IOMMU fault messages; a PCIe trace showing the CQE MWr present but no MSI-X MWr.
Where it is taught
Chapter 71 — Kernel Logs, Chapter 43 — MSI-X.

"Percentage Used" at 100% means the drive is dead

The wrong belief
"Self-Monitoring, Analysis and Reporting Technology (SMART) says 100% used, replace it now; at 50% it has half its life left."
Why people believe it
It looks like a fuel gauge.
The correct model
Percentage Used is a vendor-specific estimate of life consumed relative to the rated endurance; it may exceed 100 and the drive may keep working. It is not linear in remaining capability, does not predict sudden failure, and says nothing about other failure modes. Use it together with Available Spare, critical warnings, media and data integrity errors, and the error log.
Evidence that proves it
The SMART / Health Information log definition describes the value as an estimate that can exceed 100 (capped in the field at 255). Fleet data shows drives running well past 100%.
Where it is taught
Chapter 57 — SMART / Health.

O_DIRECT means the data is on disk

The wrong belief
"We use O_DIRECT, so we don't need fsync."
Why people believe it
O_DIRECT bypasses the kernel page cache, which is the cache people know about.
The correct model
O_DIRECT avoids the page cache; the write still lands in the device's volatile write cache if one is enabled, and filesystem metadata may still be unwritten. Durability needs fsync/fdatasync or O_DSYNC, which make the kernel issue Flush or FUA.
Evidence that proves it
NVMe tracepoints show no nvme_cmd_flush and no FUA bit for plain O_DIRECT writes; they appear when fdatasync is called.
Where it is taught
Chapter 33, Chapter 34.

Writing "write through" to queue/write_cache makes the drive safe

The wrong belief
"I disabled the write cache through sysfs."
Why people believe it
The attribute is writable and its values sound like cache modes.
The correct model
The attribute records what the kernel believes about the device. Setting it to "write through" makes the kernel stop sending flushes and FUA. It does not send Set Features to the device. On a drive with an enabled volatile cache this removes the very commands that provide durability.
Evidence that proves it
nvme get-feature -f 0x06 still reports the cache enabled after the change; tracepoints show flushes disappearing.
Where it is taught
Chapter 34.

Trace and error-analysis misconceptions

A protocol analyzer shows everything that happened

The wrong belief
"It's not in the trace, so it didn't happen."
Why people believe it
Analyzers capture every symbol on the wire, and their timelines look complete.
The correct model
An analyzer sees one link. It cannot see CPU writes into host memory (the SQE being written), the controller's internal work (NAND, cache, FTL), traffic on other links in the hierarchy, or anything outside its trigger window and filters. Captures can also drop data when buffers fill, or when the analyzer loses lock during speed changes.
Evidence that proves it
The SQE appears in the trace only when the controller fetches it; a Flush's work appears only as a gap. Check capture settings, filters and sequence-number continuity before concluding absence.
Where it is taught
Trace Analysis Laboratory, Synthetic vs Real Traces.

The first error in the log is the first abnormal event

The wrong belief
"dmesg starts with a timeout, so the timeout is where it went wrong."
Why people believe it
Logs are chronological, and people read top to bottom.
The correct model
Logs record what software detected, when it detected it. The first abnormal event is the earliest deviation from expected behavior, which often produced no message at all: a missing completion, a slowly growing latency, an unexpected status bit, an IOMMU fault logged by a different subsystem. A 30-second NVMe timeout is logged 30 seconds after the event that matters.
Evidence that proves it
Correlate timestamps across kernel log, AER, NVMe error log and traces; subtract detection delays (timeouts, polling intervals). The first abnormal row in the course's traces is usually well before the first error status.
Where it is taught
Debugging Methodology, Chapter 47 — Error Correlation.

A TLP's timestamp is when the command executed

The wrong belief
"The doorbell at t = 0 is when the command ran; the CQE at t = 80 µs is when it finished on the media."
Why people believe it
Timestamps on wire events are precise, so they feel authoritative about everything.
The correct model
A timestamp says when a packet crossed the analyzer's probe point. The doorbell may be written long after the SQE was placed in memory; the controller may fetch late; the CQE may be posted long before the data reaches media (cache) or after (FUA). Different directions may also be captured with small skews.
Evidence that proves it
Compare host-side timestamps (tracepoints) with wire timestamps for the same command; the differences reveal queuing and coalescing delays.
Where it is taught
Chapter 41.

A missing completion in a trace proves a device bug

The wrong belief
"The device sent an MRd and the trace has no CplD; the root complex dropped it" — or the reverse.
Why people believe it
Absence looks like evidence.
The correct model
Before blaming any component, prove the capture was complete: filters, trigger window, lost-lock events, the possibility that the completion traveled on a different link (switch hierarchies) or was split into several completions you filtered out. Then check whether a Completion Timeout was logged by the requester: real missing completions produce one.
Evidence that proves it
AER Completion Timeout status at the requester; analyzer sequence numbers without gaps; the same tag reappearing in a new request (which would be illegal if the old one were still outstanding).
Where it is taught
Chapter 52 — Completion Rules, Trace Analysis Laboratory.

The analyzer's NVMe decode is authoritative

The wrong belief
"The analyzer labeled it as a Write command, so it was a Write."
Why people believe it
Decoders are polished and usually right.
The correct model
An NVMe decoder reconstructs queue locations by watching Admin queue setup and Create I/O Queue commands. If the capture started after initialization, or the queues were created before the trigger, or the decoder's revision predates fields the device uses, labels can be wrong or missing. Treat decodes as hypotheses and verify key bytes yourself.
Evidence that proves it
Decode the SQE bytes by hand from the CplD payload and compare; check the decoder's configured queue base addresses against the Create I/O SQ commands.
Where it is taught
Teledyne LeCroy Analyzer Training, Truth Policy, Sources and Decoding Safety.

AER identifies the root cause

The wrong belief
"AER says Completion Timeout at the root port, so the root port is broken."
Why people believe it
AER messages name a device and an error type, which reads like a diagnosis.
The correct model
AER reports which agent detected which error, and (for some errors) a header log of the offending TLP. The detector is often not the cause: a root port logs a Completion Timeout because an endpoint never answered; an endpoint logs a Malformed TLP because something upstream sent it. AER is evidence for the first abnormal event, not the conclusion.
Evidence that proves it
Decode the header log (requester, address, type) to find the transaction involved; correlate with link state, other devices' AER status and the NVMe-level symptoms.
Where it is taught
Chapter 46 — AER, Chapter 47.

An NVMe error status always means the device is faulty

The wrong belief
"The SSD returned an error, return merchandise authorization (RMA) it."
Why people believe it
The status comes from the device.
The correct model
Many statuses report host mistakes: Invalid Field in Command, Invalid Namespace or Format, LBA Out of Range, Invalid Opcode, Command ID Conflict. Data Transfer Error often reflects a host-side DMA problem (IOMMU, bad PRP). Media and Data Integrity errors (Status Code Type 2h) are the ones that point at the media. Read the Status Code Type first.
Evidence that proves it
The CQE's Status Code Type and Status Code; the Error Information log page entry with the failing parameter location; whether the command's SQE was well formed when decoded by hand.
Where it is taught
Chapter 44 — NVMe Errors.

One good trace proves the root cause

The wrong belief
"We captured the failure once and saw X; X is the cause."
Why people believe it
Captures are expensive, and a single striking observation is persuasive.
The correct model
A single trace shows correlation in one instance. Root cause requires a mechanism that explains every symptom, a disambiguating experiment that would have failed if the hypothesis were wrong, a fix that removes the failure, and a regression test. Several captures — including passing ones — separate the abnormal from the merely unusual.
Evidence that proves it
Compare against a golden trace of the same operation; reproduce with the suspected factor removed.
Where it is taught
Root Cause, Ambiguity and Forensic Reporting, Debugging Methodology.

Performance misconceptions

Higher queue depth is always better

The wrong belief
"Push queue depth (QD) to 256 for best performance."
Why people believe it
Throughput rises with queue depth at first, and benchmark headlines quote high-QD numbers.
The correct model
By Little's Law, outstanding commands = throughput × latency. Once the device saturates, extra depth only adds waiting time: latency rises linearly while I/O operations per second (IOPS) stays flat. The right depth is the smallest that reaches the throughput you need within your latency target.
Evidence that proves it
A QD sweep: IOPS plateau while mean and tail latency keep growing. Check with the Little's Law calculator.
Where it is taught
Performance Engineering, Mathematics for Storage and Links.

Fresh-drive benchmark numbers describe production behavior

The wrong belief
"It did 1 M write IOPS in our test, so production will be fine."
Why people believe it
Short benchmarks on new drives are convenient and repeatable.
The correct model
A fresh or freshly trimmed drive writes into empty blocks and a cache; there is no garbage collection. After the drive has been filled and overwritten (steady state), write throughput can fall several-fold and tail latency grows. Results also depend on temperature (throttling) and how much the host deallocates.
Evidence that proves it
Precondition the drive (fill it twice with the target workload) and plot IOPS over time until it flattens; compare to the first minutes.
Where it is taught
Chapter 35, Validation Engineering.

Sequential and random I/O cost the same on an SSD

The wrong belief
"No moving heads, so access pattern doesn't matter."
Why people believe it
SSDs eliminated seek time, the main reason random I/O was slow on disks.
The correct model
Random small writes scatter data across blocks, raising garbage-collection cost; random small reads cannot benefit from read-ahead and use more commands, interrupts and mapping-table lookups per byte. DRAM-less drives page their mapping table and suffer most on random access across a large span.
Evidence that proves it
Compare 4 KiB random vs 128 KiB sequential at equal bandwidth targets, at steady state; compare random reads over a small span versus the whole drive.
Where it is taught
Performance Engineering.

IOPS and bandwidth are interchangeable

The wrong belief
"1 M IOPS × 128 KiB = 128 GB/s, so this drive is fast for everything."
Why people believe it
Bandwidth = IOPS × size is a correct identity.
The correct model
The identity holds for one workload at a time. A drive's IOPS limit (command processing) and bandwidth limit (link, media) bind at different sizes; small I/O is IOPS-bound, large I/O bandwidth-bound. Gen4 x4 cannot exceed roughly 7 GB/s of payload whatever the IOPS rating.
Evidence that proves it
Sweep block size: IOPS stays flat for small sizes, then bandwidth flattens at the link or media limit.
Where it is taught
Mathematics for Storage and Links, Chapter 6.

100% utilization in iostat means the SSD is saturated

The wrong belief
"%util is 100, the device is maxed out."
Why people believe it
For a single-spindle disk that served one request at a time, it was true.
The correct model
%util measures the fraction of time at least one request was outstanding. An NVMe SSD serves many requests in parallel; it can show 100% at a small fraction of its capability.
Evidence that proves it
Increase load: %util stays at 100 while throughput keeps rising. Watch average queue size and latency instead.
Where it is taught
Chapter 70, Performance Engineering.

Writes and reads load the PCIe link the same way

The wrong belief
"A 7 GB/s link gives 7 GB/s of reads plus writes combined, using the same mechanism."
Why people believe it
Both move data, and benchmark tools report them side by side.
The correct model
PCIe is full duplex. Read data goes device→host as posted writes; write data goes host→device in completions answering the device's read requests. A mixed workload can exceed one direction's bandwidth in total. Write throughput additionally depends on the device keeping enough read requests outstanding to cover the host's read latency.
Evidence that proves it
A trace of a write shows upstream MRds and downstream CplDs; a 50/50 mix measured at the link shows both directions busy.
Where it is taught
Chapter 33 — WRITE, Chapter 32 — READ.

The patterns behind the misconceptions

Look back over the entries and you will see the same handful of mistakes in different clothes. Learning to name the pattern is more useful than memorizing the list.

Five root patterns
PatternWhat goes wrongExamples on this pageAntidote
Layer collapseTwo layers with similar words are treated as oneNVMe = PCIe; PCIe completion = CQE; tag = CID; generation = revisionFor every term, name its specification and its layer
Location confusionA thing is placed where its handle livesQueue = doorbell; NVMe registers in config space; controller = namespaceAsk "which memory, which address space, who owns it?"
Word trustAn everyday meaning of a word replaces its defined meaningComplete = durable; flush = barrier; trim = erase; "identifier" = uniqueRead the normative definition, including its scope
Observation as truthA tool's view is taken as realityThe analyzer sees all; the decoder is right; first log line is first event; LnkSta is bandwidthAsk what the tool cannot see, and corroborate
Linear extrapolationA local trend is assumed to continueGen5 doubles everything; more QD is better; fresh = steady state; %utilFind the bottleneck, then predict

In a design review or a war room, when someone states a conclusion, a senior engineer silently asks which of these five patterns the conclusion might be an instance of. "The SSD lost the write" invites the word-trust check (completed or durable?). "The trace shows no completion" invites the observation check (could the capture have missed it?). This habit catches most wrong conclusions before they cost a week.

Quiz

  1. During an NVMe Read over PCIe, which TLPs carry the read data to the host?

    • CplD TLPs from the device
    • Posted MWr TLPs from the device
    • MRd TLPs from the host
    • CplD TLPs from the root complex
    Answer and reasoning

    The controller writes the data into host memory with posted Memory Writes. No PCIe completion is involved for the data; this is why "PCIe completion = NVMe completion" is wrong.

  2. An engineer says "Submission Queue 2 lives at BAR0 + 1010h". What is the best correction?

    • It is at BAR0 + 1008h
    • It lives in configuration space
    • BAR0 + 1010h is SQ2's tail doorbell (with stride 4); the queue itself is a ring in host memory
    • Queues have no fixed location
    Answer and reasoning

    Doorbells hold indices; queues are memory rings whose base address was supplied by Create I/O Submission Queue.

  3. An M.2 SSD shows up as /dev/sda. What does that most likely tell you?

    • It is an M.2 SATA drive handled through AHCI, not NVMe
    • The NVMe driver is misconfigured
    • It is NVMe over TCP
    • The link trained at Gen1
    Answer and reasoning

    M.2 is a form factor; SATA devices appear as SCSI-disk block devices. Confirm with lspci class codes.

  4. Which statement about correctable PCIe errors is correct?

    • They indicate data corruption
    • They are always caused by software
    • They can be ignored because hardware recovered
    • Their rate is an early warning of link margin problems
    Answer and reasoning

    Individually harmless, but trends matter: rising rates predict worse failures and cost bandwidth.

  5. The kernel logs an NVMe I/O timeout and notes that the completion was found by polling. What should you suspect first?

    • NAND failure
    • The interrupt path (MSI-X configuration, remapping, affinity)
    • A PCIe Completion Timeout
    • An incorrect NLB
    Answer and reasoning

    The device did post the CQE; the host was not notified. That points at interrupts, not the device's command processing.

  6. AER at a root port reports a Completion Timeout. What does that establish?

    • The root port is defective
    • The endpoint's firmware crashed
    • A request issued by the root port side did not receive a completion in time; the cause is still to be found
    • The NVMe command timed out
    Answer and reasoning

    AER names the detector and error type. The cause could be the endpoint, a switch, the link, or a reset in progress.

  7. Explain why "the doorbell is the command" leads to a real bug class.

    Model answer

    If a developer thinks the doorbell carries the command, they may write the doorbell before the SQE is globally visible in memory (missing write barrier, or writing the SQE after the doorbell). The controller may then fetch a stale or partially written entry. Correct drivers write the SQE, issue a write barrier, then write the doorbell.

  8. A team reports "Gen5 gave us no improvement for our database". Using this page, explain why that can be correct.

    Model answer

    Small random I/O latency is dominated by media and controller processing, not link serialization; a doubling of link rate saves well under a microsecond per 4 KiB while NAND reads take tens of microseconds. Only bandwidth-bound workloads gain proportionally.

  9. Name the five root patterns behind the misconceptions and give one example of each.

    Model answer

    Layer collapse (PCIe completion = CQE); location confusion (queue = doorbell); word trust (complete = durable); observation as truth (analyzer sees everything); linear extrapolation (higher QD always better).

  10. A colleague says "trimmed data is gone, so we don't need Sanitize before returning leased drives". Respond.

    Model answer

    Deallocate only updates the FTL mapping; the NAND pages may hold the old data until garbage collection erases them, and forensic recovery is possible. Reads of deallocated blocks returning zeros reflect DLFEAT, not destruction. Use Sanitize (or a secure Format NVM) and verify completion via the Sanitize Status log.
