Things engineers commonly get wrong about NVMe and PCIe — forty-two of them, each taken apart the same way: the wrong belief, why smart people hold it, the correct model, the evidence that settles it, and the chapter that teaches it properly. Use this page as a self-test before interviews, design reviews and debugging sessions.

How to use this page

A misconception is rarely ignorance. It is usually a model that was correct somewhere — in an older technology, in a simpler case, at a higher level of abstraction — and is now applied where it does not fit. That is why each entry below explains why people believe it: if you understand where the wrong model comes from, you will recognise its relatives.

Every entry has the same five parts:

The wrong belief
Stated the way people actually say it.
Why people believe it
The legitimate experience or simplification behind it.
The correct model
What is actually true, with the layer and the owner named.
Evidence that proves it
Something you can observe — a register, a trace, a command output, a specification structure — rather than an appeal to authority.
Where it is taught
The chapter that builds the full model.

Three technologies appear throughout, and keeping them apart is the first discipline of this course: PCI Express (PCIe), the interconnect, specified by PCI-SIG; Non-Volatile Memory Express (NVMe), the storage interface and command sets, specified by NVM Express; and the NVMe over PCIe Transport specification, which joins them. Several misconceptions below are simply these three collapsed into one.

Before opening each entry, read only its heading and say out loud what the correct model is and what evidence you would collect. Then compare. Tick the entries you got fully right in the mastery gate at the bottom; revisit the others after reading the linked chapter. Evidence examples on this page that look like command output are illustrative; real output varies by tool version and device.

Where NVMe meets PCIe

These eight are the misconceptions the master curriculum names explicitly. They all come from blurring the boundary between the storage protocol and the interconnect.

NVMe is the same thing as PCIe

The wrong belief
"NVMe drives are PCIe drives; NVMe is just the name for storage over PCIe."
Why people believe it
Almost every NVMe device a person handles is a PCIe card or M.2 module, and marketing uses "PCIe SSD" and "NVMe SSD" interchangeably.
The correct model
PCIe is a general-purpose interconnect that carries memory reads and writes, configuration requests and messages for any kind of device (GPUs, NICs, accelerators). NVMe is a storage interface: queues, commands, completions, controller registers, namespaces. NVMe runs over PCIe through the NVMe over PCIe Transport specification, but it also runs over RDMA and TCP (NVMe over Fabrics), where there is no PCIe between host and controller at all.
Evidence that proves it
The NVMe specification family lists separate transport specifications (PCIe, RDMA, TCP). A PCIe analyzer shows only generic TLPs — memory reads and writes — and needs to be told where the queues live to decode NVMe. An NVMe/TCP namespace (nvme list showing a fabrics transport) has no PCIe function behind it.
Where it is taught
Chapter 21 — What Is NVMe?, Chapter 22 — NVMe 2.x Architecture, Chapter 65 — NVMe-oF Mental Model.

PCIe is the NVMe protocol

The wrong belief
"The NVMe protocol is defined by PCIe packets; to understand NVMe I study TLPs."
Why people believe it
On a PCIe system every NVMe action does produce TLPs, and analyzers present "NVMe decode" views on top of PCIe captures.
The correct model
The NVMe protocol is defined in terms of memory-resident data structures (Submission and Completion Queues, PRP lists, SGLs) and controller registers. PCIe only carries the memory accesses that read and write them. The protocol would be the same if the memory accesses travelled on a different interconnect; indeed NVMe over Fabrics carries the same commands as capsules.
Evidence that proves it
The NVMe Base Specification defines a 64-byte Submission Queue Entry and 16-byte Completion Queue Entry without reference to TLP formats. In a trace, the SQE appears as the payload of a Completion with Data answering the controller's Memory Read — the NVMe structure is the cargo, not the packet.
Where it is taught
Chapter 22, Chapter 39 — The Most Important Chapter.

The NVMe command set is the transport

The wrong belief
"Read and Write are part of NVMe over PCIe."
Why people believe it
Before NVMe 2.0 everything lived in one document, so command definitions, register definitions and PCIe-specific details sat side by side.
The correct model
Since NVMe 2.0 the family is split: the Base specification (common architecture, Admin commands, queues, status), I/O command set specifications (NVM, Zoned Namespaces, Key Value, Subsystem Local Memory, Computational Programs) and transport specifications (PCIe, RDMA, TCP). Read and Write are defined in the NVM Command Set; doorbells and MSI-X interrupts are in the PCIe Transport specification.
Evidence that proves it
The 2026 baseline lists NVM Command Set 1.3 and NVMe over PCIe Transport 1.4 as separate documents with separate revision numbers. Identify Controller reports which I/O command sets a controller supports independently of its transport.
Where it is taught
Chapter 22, Chapter 31 — NVM Command Set.

A TLP is the same as an NVMe command

The wrong belief
"The host sends the Read command to the SSD in a TLP."
Why people believe it
It is how network protocols usually work: the request travels in a packet to the server.
The correct model
The host writes the 64-byte command into a Submission Queue in host memory and then writes a 4-byte doorbell value to the controller. The controller fetches the command itself with a Memory Read request; the command arrives at the controller as the payload of a Completion with Data. One NVMe command therefore produces many TLPs (doorbell, SQE fetch and its completion, data movement, CQE write, interrupt) and one TLP can carry parts of several commands (a 256-byte fetch can return four SQEs).
Evidence that proves it
In any PCIe capture of NVMe I/O, the only host-to-device TLP at submission time is a 4-byte MWr to an address in BAR0 at offset 1000h or above (a doorbell). The SQE contents appear in a downstream CplD answering an upstream MRd.
Where it is taught
Chapter 41 — Command-to-TLP Correlation, Command vs Packet vs Completion.

A PCIe completion is the NVMe completion

The wrong belief
"When the SSD sends the completion TLP, the command is done."
Why people believe it
Both are called "completion", and both mean "your request has been answered".
The correct model
A PCIe Completion (Cpl or CplD) answers one non-posted PCIe request — a memory read, configuration access or I/O access — and travels from completer to requester. An NVMe completion is a 16-byte Completion Queue Entry that the controller writes into host memory with a posted Memory Write. During an NVMe Read, the host does not receive any PCIe completion from the device at all: the data and the CQE arrive as posted writes. The PCIe completions flow toward the device, answering its reads of the SQE and of write data.
Evidence that proves it
In a trace, CQEs appear as MWr TLPs to the Completion Queue address (16 bytes), while CplD TLPs carry the Requester ID of the device and the Tag of the device's own MRd. A Completion Timeout is a PCIe error about a missing Cpl; an NVMe command timeout is a host driver's timer on a missing CQE.
Where it is taught
Chapter 12 — Posted vs Non-Posted, Chapter 52 — Completion Rules, Command vs Packet vs Completion.

PCIe generation is NVMe revision

The wrong belief
"A Gen5 SSD supports NVMe 2.0 features" or "NVMe 2.4 needs PCIe 6.0".
Why people believe it
New drives tend to arrive with both a newer link and a newer NVMe revision, and product briefs list them together.
The correct model
PCIe generation (link speed: 2.5, 5, 8, 16, 32, 64, 128 GT/s) is negotiated by the physical and data link layers and reported in PCIe capability registers. NVMe revision is reported by the controller's Version register (VS, offset 08h) and governs which NVMe features the controller may implement — most of which are optional anyway. A Gen3 device can implement NVMe 2.x; a Gen5 device can implement NVMe 1.4.
Evidence that proves it
lspci -vvv LnkCap/LnkSta report link speed and width; nvme id-ctrl reports the version field and the optional-feature bits. They vary independently across products.
Where it is taught
Chapter 6 — PCIe Generations, Chapter 24 — NVMe Registers.

M.2 means NVMe

The wrong belief
"It's an M.2 drive, so it's NVMe."
Why people believe it
Most current M.2 SSDs are NVMe, and the M.2 form factor became popular at the same time as NVMe.
The correct model
M.2 is a mechanical and electrical form factor whose connector can carry SATA, PCIe, USB and other interfaces depending on the module and slot keying. An M.2 SATA SSD uses the ATA command set through an AHCI host controller. Likewise U.2, U.3, EDSFF (E1/E3) and add-in cards are form factors; NVMe is the storage interface spoken across them.
Evidence that proves it
An NVMe controller appears in PCIe configuration space with class code 01h (mass storage), subclass 08h (non-volatile memory), programming interface 02h (NVMe). An M.2 SATA drive appears behind a SATA/AHCI controller (subclass 06h) and is handled by the ahci driver, showing up as /dev/sdX, not /dev/nvme*.
Where it is taught
Chapter 3 — From SATA/SAS to NVMe, Chapter 5 — PCIe Physical Architecture.

SSD latency is the same as PCIe latency

The wrong belief
"Gen5 halves the SSD's latency" or "this 80 µs read must be a slow link".
Why people believe it
Faster links do reduce transfer time, and bandwidth and latency are often conflated.
The correct model
End-to-end read latency is the sum of host submission, doorbell propagation, SQE fetch round trip, controller firmware, NAND read (tens of microseconds for TLC), data transfer, CQE and interrupt delivery, and host completion processing. PCIe transfer of 4 KiB at Gen4 x4 is roughly one to two microseconds; the NAND read dominates. Link speed matters for large transfers and bandwidth, little for small-I/O latency.
Evidence that proves it
A trace of a 4 KiB read shows the gap between SQE fetch and the first data MWr is tens of microseconds — the media — while the data burst itself occupies around a microsecond. Running the same drive at a forced lower link speed changes 4 KiB latency only slightly but changes 128 KiB throughput a lot.
Where it is taught
Chapter 32 — READ, Performance Engineering.

PCIe misconceptions

A wider link makes every transaction faster in proportion

The wrong belief
"x8 is twice as fast as x4, so latency halves."
Why people believe it
Bandwidth does scale roughly with lane count, and bandwidth is what datasheets advertise.
The correct model
Width shortens the serialization time of each packet; it does not shorten fixed delays (propagation, switch and root complex processing, memory access, device firmware). For small packets the fixed parts dominate. Width also cannot help when the bottleneck is elsewhere (media, tags, credits).
Evidence that proves it
Serialization of a 256-byte payload TLP on Gen4 is about 0.5 ns per byte per lane-group divided by width — tens of nanoseconds at x4 — while an MRd round trip through a root complex is commonly hundreds of nanoseconds to a microsecond. Use the calculators to compare.
Where it is taught
Chapter 6, Mathematics for Storage and Links.

Link up means the device is healthy

The wrong belief
"LTSSM reached L0, so the hardware is fine and the problem is software."
Why people believe it
Link training failure is the most visible hardware failure; once it passes, hardware seems "done".
The correct model
L0 means the physical and data link layers can exchange packets. The link may have trained at a lower speed or width than capable, may be running with a high replay rate, and the device's function may still fail enumeration, BAR sizing, or — for NVMe — controller enable (CSTS.RDY never set, or CSTS.CFS fatal status).
Evidence that proves it
Compare LnkCap with LnkSta (speed and width); check correctable error counters; read CSTS after enable. All three can be bad on a link that is "up".
Where it is taught
Chapter 8 — PCIe LTSSM, Chapter 9 — Link Training, Chapter 24.

Every PCIe write is acknowledged by the receiver

The wrong belief
"The doorbell write was acknowledged, so the controller has seen it."
Why people believe it
Analyzers show ACK DLLPs after every TLP, and many bus protocols acknowledge writes end to end.
The correct model
Memory Writes are posted: they have no completion. The ACK DLLP is a data-link-layer acknowledgement between the two ends of one link, saying "this TLP arrived intact on this link", not "the target processed it". Through a switch, the host's ACK comes from the switch, not the SSD. Software that needs to know a posted write has reached the device performs a read to the same device (the read cannot pass the earlier write).
Evidence that proves it
TLP type MWr has no corresponding Cpl in any trace. ACK DLLPs carry a sequence number, not a tag or requester ID.
Where it is taught
Chapter 12, Chapter 15 — DLLP, Chapter 14 — PCIe Ordering.

Configuration space and BAR space are the same kind of memory

The wrong belief
"NVMe registers like CC and CSTS are in the PCIe configuration space."
Why people believe it
Both are "registers on the device", and Linux exposes both under /sys/bus/pci/devices/….
The correct model
Configuration space (256 bytes legacy, 4 KiB extended) holds PCI-defined headers and capabilities and is reached with Configuration Read/Write requests (generated by the root complex, often from ECAM memory accesses). NVMe controller registers live in memory space decoded by BAR0, reached with ordinary Memory Read/Write TLPs. The BAR register itself is in configuration space; what it points to is not.
Evidence that proves it
On a trace, accessing CC produces MRd/MWr TLPs to the BAR0 address (e.g. 0xFE60_0014 on the course's lab system), while reading the Device ID produces a CfgRd0 TLP with bus/device/function routing.
Where it is taught
Chapter 18 — Configuration Space, Chapter 19 — BARs and MMIO.

PCIe tags are NVMe command identifiers

The wrong belief
"Tag 0x21 in the trace is command 0x21."
Why people believe it
Both are small integers used to match responses to requests.
The correct model
A PCIe tag is chosen by a requester for each outstanding non-posted request and is unique only together with the Requester ID while the request is outstanding; the same tag is reused within microseconds. An NVMe Command Identifier (CID) is chosen by the host driver and is unique among outstanding commands on one Submission Queue. One NVMe command typically consumes several tags (SQE fetch, data reads); posted writes have tags that carry no matching meaning.
Evidence that proves it
Decode an SQE from a CplD: its CID (bytes 2–3) bears no relation to the tag of the CplD that carried it. The CQE's CID matches the SQE's, not any tag.
Where it is taught
Chapter 13 — PCIe Tags, Chapter 29 — NVMe Command Structure.

A bigger Max Payload Size is always better and can be set freely

The wrong belief
"The device supports 512-byte MPS, so set 512."
Why people believe it
Larger payloads reduce header overhead, and the capability register advertises the maximum.
The correct model
MPS must be configured consistently along the path: a TLP larger than a receiver's configured MPS is a Malformed TLP. System software normally sets MPS to the minimum supported along the hierarchy. The efficiency gain from 256 to 512 bytes is a few percent; larger packets also increase buffer needs and can add latency for other traffic. Max Read Request Size is a separate, per-function setting.
Evidence that proves it
DevCap reports MaxPayload supported; DevCtl reports the configured value; they differ on most systems. A misconfigured MPS shows Malformed TLP errors in AER.
Where it is taught
Chapter 11 — TLP Header Anatomy, Chapter 53 — Flow Control and Credits.

Any replay on the link is a failure

The wrong belief
"We saw a NAK and a replay — the link is broken."
Why people believe it
A NAK looks like an error, and analyzers highlight it in red.
The correct model
The data link layer's replay mechanism exists precisely to recover from occasional bit errors invisibly to the transaction layer. A low, stable rate of replays is normal at high data rates. What matters is the trend and the rate relative to traffic, and whether replays escalate (replay number rollover, retraining, recovery entries).
Evidence that proves it
AER correctable status bits (Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover) and their counts over time; LTSSM Recovery entries in the analyzer.
Where it is taught
Chapter 15, Deep-Dive Module 16 — DLLP and Replay.

Correctable errors can be ignored

The wrong belief
"They're correctable, the hardware fixed them, nothing to see."
Why people believe it
Individually they are harmless, and many systems log them at a low level or rate-limit the messages.
The correct model
Correctable errors are the early warning system. A rising rate signals marginal signal integrity (connector, retimer, equalization, temperature), and they cost bandwidth through replays. A link that throws thousands of correctable errors per hour is one bad day away from uncorrectable errors or downtraining.
Evidence that proves it
Linux exposes AER counters per device in sysfs (aer_dev_correctable); correlate their rate with temperature, workload and link speed. Forcing the link to a lower speed usually makes them vanish — a classic margin diagnosis.
Where it is taught
Chapter 45 — PCIe Errors, Chapter 54 — Equalization.

Moving to a newer PCIe generation doubles application performance

The wrong belief
"Gen5 SSD: twice as fast as Gen4."
Why people believe it
Each generation doubles the per-lane rate, and sequential benchmarks of top drives roughly track it.
The correct model
Only workloads limited by link bandwidth benefit proportionally. Small random I/O is limited by media latency, controller parallelism and host software; a database doing 4 KiB random reads at low queue depth may see almost no change. The device's back end (NAND channels, dies) must also be able to supply the extra bandwidth.
Evidence that proves it
Measure the same workload with the link forced to the lower generation (where the platform allows): sequential throughput changes, 4 KiB QD1 latency barely moves.
Where it is taught
Chapter 6, Performance Engineering.
