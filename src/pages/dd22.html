The NVM subsystem is the unit of identity, persistence and blast radius in Non-Volatile Memory Express (NVMe). This module goes beyond Chapter 22's architecture overview: it follows NVMe Qualified Names (NQNs), multiple controllers, shared namespaces, subsystem-scoped firmware and the NVM Subsystem Reset through traces in which one host's action reaches another host.

Orientation

Most engineers meet the subsystem as a sentence — "one or more controllers, zero or more namespaces, one or more ports" — and then forget it, because a client SSD has exactly one of each. The subsystem stops being abstract the first time a firmware update on one server pauses I/O on another, or a reset issued through one PCI Express (PCIe) port drops the link on a second port. This module teaches the subsystem as a scope: for every object and every action, which controllers, ports and hosts does it touch? It uses a dual-port variant of the course's Lab SSD so that two controllers, two links and two hosts can appear in one trace.

  • NVMe 2.x Architecture — subsystem, controller types, namespaces and command sets in the 2.x document family.
  • NVMe Controller — controller vs namespace, topologies, CMIC and NMIC, Controller Level Resets.
  • NVMe Registers — NSSR, CSTS.NSSRO, CAP.NSSRS.
  • NVMe Controller (deep dive) — reset variants and what each touches.

Where it goes next: Namespaces (the subsystem's storage objects in depth), SR-IOV and SR-IOV deep dive (virtual functions as secondary controllers), NVMe-oF Mental Model (subsystems reached over fabrics), and 2026 NVMe 2.4 Updates (Exported NVM Subsystems and their migration).

Kid story

Think of an apartment building with one big basement storeroom. The building has two front doors on two different streets, and each door has its own doorman. Families on Oak Street use the Oak door; families on Elm Street use the Elm door. Each doorman keeps his own notebook of requests, but both doormen fetch boxes from the same basement. Some storage cages belong to one family; one cage is shared by two families who agreed to share it.

The building has a name on a brass plate — that is how the post office knows both doors belong to the same building. And there is one main fuse box in the basement. If anyone flips the main fuse, both doors go dark at once, even though only the Oak family touched it. When the building's lift is being repaired, both doormen have to say "please wait" to their families at the same time.

The building is the NVM subsystem; the brass plate is the subsystem NQN; the doors are ports; the doormen are controllers; the cages are namespaces (private and shared); the main fuse is the NVM Subsystem Reset; the lift repair is firmware activation, which is subsystem-wide.

Analogy boundary

  • Represents. One identity, several entrances, shared storage, and actions whose effect is building-wide even when one person performs them.
  • Hides. A port and a controller are not always one-to-one: one PCIe port can expose many controllers (SR-IOV virtual functions), and on fabrics a controller can be created when a host connects. The brass plate can also be wrong — a non-unique NQN is a real firmware defect.
  • Misleads. Flipping the main fuse in a building cuts power; an NVM Subsystem Reset does not erase stored data. Namespaces and their contents survive it, just as the boxes survive a power cut. Also, families at different doors may see the same cage under the same number (NSID) — numbers are building-wide, not per door.

Architecture

This module's synthetic system is Lab SSD-D, a dual-port variant of the Lab SSD (synthetic example for teaching): SUBNQN nqn.2026-01.example:lab-ssd-d; port A exposes controller CNTLID 1, port B exposes CNTLID 2; CMIC bits 0 and 1 set; NSID 1 is shared (NMIC bit 0 = 1) and attached to both controllers; NSID 2 is private and attached to CNTLID 1 only. On host A the port-A function is 0000:01:00.0 (Requester ID 0x0100, BAR0 0xFE60_0000). In the single-host setup, port B appears as 0000:02:00.0 (Requester ID 0x0200, BAR0 0xFE40_0000) under a second root port; in the two-host setup, host B sees port B with the same numbers.

NVM Subsystem Reset, port by port

An NSSR (write 4E56_4D65h, ASCII "NVMe", to offset 20h of any controller with CAP.NSSRS = 1) resets the entire subsystem. On PCIe the subsystem's ports are reset, so every link drops and retrains Derived (confirm the exact PCIe-specific text in the NVMe over PCIe Transport Specification). Each host sees what looks like a surprise link-down: outstanding MMIO reads fail, outstanding NVMe commands never complete, and the PCIe hierarchy may report Data Link Layer state changes or Downstream Port Containment events. After retraining and re-enumeration, each controller reports CSTS.NSSRO = 1 so its host can tell this was a subsystem reset rather than a power failure. Data in namespaces survives; volatile write cache contents follow the device's power-loss rules.

Identity: how a host decides "same subsystem"

A host groups controllers into one subsystem by SUBNQN. Linux additionally checks that controllers grouped together have different CNTLIDs and consistent model and serial information (Implementation-dependent host policy). Namespaces seen through several controllers are matched by their global identifiers (NGUID, EUI-64, UUID) and NSID. A device that reports a non-unique SUBNQN (the same string on every unit of a product line) breaks this logic: the host may try to merge two independent drives. Linux carries per-device quirks for such firmware.

NQN format

An NQN is either nqn.yyyy-mm.reverse.domain:string, where the date is when the naming authority owned the domain, or the UUID form nqn.2014-08.org.nvmexpress:uuid: followed by a UUID in its 36-character textual form. The well-known discovery NQN is nqn.2014-08.org.nvmexpress.discovery. NQNs are at most 223 bytes of UTF-8. The course's nqn.2026-01.example:… names are synthetic and deliberately use a non-routable "example" authority.

The ladder for the central concept: the subsystem as a scope

One building, two doors, two doormen, one basement, one main fuse, one name plate.

An NVM subsystem groups controllers, namespaces and ports under one SUBNQN; some state is per controller, some is shared by all of them.

Hardware: two PCIe ports and functions (or one PF with many VFs) in front of one firmware image, one metadata store and one media pool; NSSR resets the shared part and the ports.

Base Specification 2.4 defines subsystem entities, NQNs, CMIC/NMIC, namespace attachment, firmware commit semantics, NSSR and NSSRO, domains and Exported NVM Subsystems; the PCIe Transport Specification maps NSSR to PCIe behaviour.

Subsystem actions travel as ordinary admin commands on one controller and appear as events, pauses or resets on the others; NSSR is a single MWr32 that takes down every port.

In traces, causality crosses captures: a command on link A, then an asynchronous event, PP or link-down on link B. One capture is never enough.

When a host is hit by something it did not do, ask which subsystem-scoped actions other hosts or management agents performed: firmware, sanitize, NSSR, namespace management, format of all namespaces.

The sixteen questions for the NVM subsystem

1. What is it?
The container of controllers, namespaces, ports and media that forms one NVMe storage entity.
2. Why was it created?
To let several hosts and paths reach the same storage with one identity.
3. What problem does it solve?
Multipath, high availability, virtualisation and fabric access without duplicating storage.
4. What existed before?
SCSI targets with multiple ports and logical units; dual-ported SAS drives.
5. Why is it better?
Explicit scopes, globally unique names, and per-controller queues that keep hosts independent for I/O.
6. Who creates it?
The device maker (physical); with 2.4, a physical device may create Exported NVM Subsystems.
7. Who consumes it?
Hosts, through controllers; management controllers through NVMe-MI.
8. Where does it live?
In the device's firmware, metadata and media; it has no register of its own except actions like NSSR exposed through each controller.
9. What memory/registers are involved?
SUBNQN and CMIC in Identify Controller; NSSR, CSTS.NSSRO, CAP.NSSRS; Identify CNS 12h/13h (controller lists), 14h/15h (SR-IOV).
10. What happens before?
Device power-on; each port's link training; each controller's enumeration.
11. What happens after?
Hosts group controllers by SUBNQN and build multipath namespace devices.
12. What happens if it is wrong?
Merged unrelated drives, duplicate block devices, cross-host outages, data corruption on shared namespaces.
13. What does the analyzer show?
Nothing subsystem-specific on one link; cross-link correlation shows propagation.
14. What does Linux show?
/sys/class/nvme-subsystem, nvme list-subsys, per-path nodes.
15. What would a validation engineer test?
Every subsystem-scoped action via each controller, observed on every other; NSSR recovery on all ports; identity uniqueness across units.
16. What would a senior engineer suspect?
An action by another host or agent, or a host that grouped controllers incorrectly.

NSSR at offset 20h with value 4E56_4D65h, CSTS.NSSRO, CAP.NSSRS, the CMIC field and its first bits (multiple ports, multiple controllers, SR-IOV, ANA reporting), the UUID-based NQN form and the discovery NQN are established across Base 1.4–2.4.

"NSSR drops every PCIe link of the subsystem" follows from the subsystem reset including its ports; the analyzer-level sequence shown in this module (link down, retrain, re-enumeration) is the expected consequence, but the exact timing and whether Downstream Port Containment triggers depend on the platform.

  • The specification does not tell a host how to group controllers or pick paths; Linux native multipath and other stacks are host policy.
  • It does not coordinate hosts sharing a namespace beyond reservations; cluster correctness is above NVMe.
  • It does not bound the pause during firmware activation beyond what the device reports (check the maximum time-for-activation field in Identify Controller and the commit statuses that refuse activation when it would be exceeded).
  • Check in the specification: the commit action encodings; the asynchronous event information value for "firmware activation starting"; the scope column for each log page and feature; NSSD layout; the field layouts for Exported NVM Subsystems and configuration templates (2.4 — do not infer from summaries).

Never assume one PCIe function is the whole subsystem, that an action through "your" controller stays on your controller, that two device nodes are two drives, or that SUBNQN is unique across units without checking serial numbers and namespace identifiers.

Hardware view

Hardware participation
CategoryHardware
Must participateAt least one port (PCIe core), at least one controller front end, shared firmware processor(s), shared metadata store, media
May participateA second PCIe port (dual-port U.2/U.3 or E3 form factors split a x4 link into two x2 links); SR-IOV logic exposing many virtual functions behind one port; a management endpoint for NVMe-MI over SMBus/I3C; hardware isolation between domains
ObservableEach port's link and TLPs (one analyzer per port); each controller's registers and Identify data; management traffic on the sideband bus with the right tool
Internal, unobservableThe shared firmware's scheduling between controllers, the attachment table, inter-controller locking, how a subsystem reset is sequenced internally

Dual-port drives connect each port to a different host or a different root port; the drive's two x2 links train independently. That independence is why a link problem on one port does not usually affect the other — and why an NSSR, which deliberately resets both, is so visible. With SR-IOV, all virtual functions share one physical link, so a link event affects every VF controller at once even though they are separate controllers.

Proving cross-port causality needs two captures on a common timebase: two analyzer ports synchronised by the analyzer, or two analyzers sharing a reference and trigger. Without that, you can only argue order from host logs, whose clocks may drift by milliseconds.

Ordering: nothing orders commands on controller 1 relative to commands on controller 2. Errors keep their layers: subsystem actions produce NVMe statuses and events; only NSSR produces PCIe-level events (link down, completion timeouts) — on every port.

Intermediate lab — Validate NQNs and identity pairs

Objective

Write and use a checker for NQN format and for "same subsystem?" decisions.

Prerequisites

The NQN format and identity sections of the Mechanism; Python 3.

Setup

#!/usr/bin/env python3
"""Check NVMe Qualified Names against the format rules taught in this module.
Teaching tool: confirm the normative rules in the Base Specification."""
import re, uuid

MAX_BYTES = 223
DISCOVERY = "nqn.2014-08.org.nvmexpress.discovery"
UUID_PREFIX = "nqn.2014-08.org.nvmexpress:uuid:"
DOMAIN_FORM = re.compile(r"^nqn\.(\d{4})-(\d{2})\.([a-z0-9-]+(\.[a-z0-9-]+)*):(.+)$")

def check(nqn):
    problems = []
    if len(nqn.encode("utf-8")) > MAX_BYTES:
        problems.append(f"longer than {MAX_BYTES} bytes")
    if nqn == DISCOVERY:
        return "discovery NQN", problems
    if nqn.startswith(UUID_PREFIX):
        u = nqn[len(UUID_PREFIX):]
        try:
            if str(uuid.UUID(u)) != u.lower() or len(u) != 36:
                problems.append("UUID not in 8-4-4-4-12 textual form")
        except ValueError:
            problems.append("invalid UUID")
        return "UUID form", problems
    m = DOMAIN_FORM.match(nqn)
    if not m:
        problems.append("not 'nqn.yyyy-mm.reverse.domain:string' and not the UUID form")
        return "unknown", problems
    year, month = int(m.group(1)), int(m.group(2))
    if not 1 <= month <= 12:
        problems.append("month out of range")
    if year < 1985:
        problems.append("implausible year for a domain registration date")
    if "." not in m.group(3):
        problems.append("authority has no dot: not a reverse domain name (fine for synthetic examples only)")
    return "domain form", problems

def same_subsystem(ids_a, ids_b):
    """ids: dict with subnqn, sn, cntlid. Returns a verdict string."""
    if ids_a["subnqn"] != ids_b["subnqn"]:
        return "different subsystems"
    if ids_a["cntlid"] == ids_b["cntlid"]:
        return "SUSPECT: same SUBNQN and same CNTLID - two devices sharing a name?"
    if ids_a["sn"] != ids_b["sn"]:
        return "AMBIGUOUS: same SUBNQN, different serials - verify with a marker write"
    return "consistent with one subsystem, two controllers"

if __name__ == "__main__":
    tests = [
        "nqn.2026-01.example:lab-ssd-d",
        "nqn.2014-08.org.nvmexpress:uuid:1b4e28ba-2fa1-11d2-883f-0016d3cca427",
        "nqn.2014-08.org.nvmexpress:uuid:1B4E28BA2FA111D2883F0016D3CCA427",
        "nqn.2014-08.org.nvmexpress.discovery",
        "nqn.2026-13.com.example:bad-month",
        "nvme.2026-01.com.example:wrong-prefix",
        "nqn.2026-01.com.example:" + "x" * 220,
    ]
    for t in tests:
        form, problems = check(t)
        shown = t if len(t) < 60 else t[:57] + "..."
        print(f"{shown:60} {form:13} {'OK' if not problems else '; '.join(problems)}")
    a = {"subnqn": "nqn.2026-01.example:lab-ssd-d", "sn": "LSD0000917", "cntlid": 1}
    for b in ({**a, "cntlid": 2}, {**a, "cntlid": 2, "sn": "LSD0000944"}, {**a}):
        print(same_subsystem(a, b))

Procedure

  1. Run it. Expected: the course's synthetic NQN is accepted but flagged (no dot in the authority — fine for examples only); the lowercase UUID form passes; the UUID without hyphens fails; the discovery NQN is recognised; month 13, the wrong prefix and the 244-byte name fail; the three identity comparisons print "consistent", "AMBIGUOUS" and "SUSPECT".
  2. Feed it your own drives' SUBNQNs from nvme id-ctrl.
  3. Add a rule that rejects uppercase hexadecimal in the UUID form only if your reading of the specification requires lowercase — and record what you found.

Observations

Record which real SUBNQNs use the UUID form and which use a vendor domain.

Questions

  1. Why does the checker count bytes, not characters?
  2. Why is "same SUBNQN and same CNTLID" more alarming than "different serials"?
  3. What should a host do with a device that reports an empty SUBNQN?

Expected reasoning

Format rules protect global uniqueness; identity checks protect the host from merging different media.

Solution

(1) The limit is 223 bytes of UTF-8; non-ASCII characters take several bytes. (2) CNTLIDs are unique within a subsystem, so two controllers with the same SUBNQN and the same CNTLID cannot be one subsystem: two devices are sharing a name, and merging them would be data-dangerous. Different serials with different CNTLIDs are odd but possibly legitimate. (3) Treat it as its own subsystem and synthesise a unique name from vendor ID, serial and model, as Linux does for devices that predate SUBNQN; never merge such devices by name. Uppercase handling: check the Base Specification's NQN text; this course does not assert a rule.

Extension

Extend same_subsystem to compare namespace NGUIDs and the CNS 13h controller lists, returning a confidence level.

Advanced lab — Blast-radius model

Objective

Predict, before acting, which controllers, hosts and namespaces an action touches; test the predictions against the module's traces.

Prerequisites

The scope table in Architecture; Python 3.

Setup

#!/usr/bin/env python3
"""Blast-radius model of an NVM subsystem: which controllers, hosts and
namespaces does an action touch? Synthetic Lab SSD-D; teaching simulation."""

SUBSYS = {
    "controllers": {1: {"port": "A", "host": "hostA"}, 2: {"port": "B", "host": "hostB"}},
    "namespaces": {1: {"attached": {1, 2}}, 2: {"attached": {1}}},
}

# scope of each action, and what it does to queues / data / links
ACTIONS = {
    "controller_reset": {"scope": "controller", "queues": True, "link": False, "data": False},
    "flr":              {"scope": "controller", "queues": True, "link": False, "data": False},
    "fw_activate_now":  {"scope": "subsystem",  "queues": False, "link": False, "data": False, "pause": True},
    "fw_activate_reset":{"scope": "subsystem",  "queues": True, "link": False, "data": False},
    "nssr":             {"scope": "subsystem",  "queues": True, "link": True, "data": False},
    "sanitize":         {"scope": "subsystem",  "queues": False, "link": False, "data": True},
    "format_ns":        {"scope": "namespace",  "queues": False, "link": False, "data": True},
    "detach_ns":        {"scope": "attachment", "queues": False, "link": False, "data": False},
}

def blast(action, via_cntlid, nsid=None):
    a, ctrls = ACTIONS[action], SUBSYS["controllers"]
    if a["scope"] == "controller":
        hit = {via_cntlid}
    elif a["scope"] == "subsystem":
        hit = set(ctrls)
    elif a["scope"] == "namespace":
        hit = set(SUBSYS["namespaces"][nsid]["attached"])
    else:                     # attachment: via_cntlid = controller named in the list
        hit = {via_cntlid}
    effects = []
    if a["queues"]: effects.append("queues deleted, outstanding I/O lost")
    if a.get("pause"): effects.append("processing paused")
    if a["link"]: effects.append("PCIe link down on port")
    if a["data"]: effects.append("user data destroyed")
    if action == "detach_ns": effects.append(f"NSID {nsid} inactive")
    hosts = sorted({ctrls[c]["host"] for c in hit})
    return sorted(hit), hosts, effects or ["no visible effect"]

if __name__ == "__main__":
    plan = [("controller_reset", 1, None), ("fw_activate_now", 1, None),
            ("nssr", 1, None), ("format_ns", 1, 1), ("format_ns", 1, 2),
            ("detach_ns", 2, 1), ("sanitize", 2, None)]
    for action, via, nsid in plan:
        hit, hosts, eff = blast(action, via, nsid)
        tag = f"{action}(via CNTLID {via}{', NSID ' + str(nsid) if nsid else ''})"
        cross = " <-- reaches a host that did not issue it" if len(hosts) > 1 else ""
        print(f"{tag:38} controllers {hit} hosts {hosts}: {'; '.join(eff)}{cross}")

Procedure

  1. Run it. Expected: controller reset and detach stay on one controller; firmware activation, NSSR, sanitize and formatting the shared NSID 1 reach both hosts.
  2. Add a third controller (an SR-IOV virtual function on port A, used by a VM) and rerun.
  3. Add the action "activate firmware at next reset" and model that it has no effect until some controller resets.
  4. Turn the output into a change-review checklist: for each action, the hosts that must be notified.

Observations

Note which actions are dangerous because of data and which because of availability.

Questions

  1. Why does formatting NSID 2 stay on host A while formatting NSID 1 does not?
  2. Which action in the list is the only one that produces PCIe-level errors?
  3. Why is "activate at next reset" not automatically safe in a two-host system?

Expected reasoning

Scope is a property of the object acted on, not of the controller used to act.

Solution

(1) NSID 2 is private to CNTLID 1; NSID 1 is shared, so its data loss reaches host B. (2) NSSR: it resets ports, so links drop and MMIO fails. (3) "Next reset" means the next Controller Level Reset that triggers activation — which might be a reset initiated by the other host for unrelated reasons, or an NSSR; the new firmware then appears at a time neither host planned. Confirm in the Firmware Commit text which reset types activate a pending image.

Extension

Model domains: split the subsystem into two domains and make some actions domain-scoped; discuss what a domain-scoped log or feature would mean for monitoring.

Senior forensic lab — The 02:00 firmware window

Objective

Determine why a planned firmware update on node A of a two-node database cluster caused node B to fence itself, and propose procedural and technical fixes.

Prerequisites

All traces in this module; Error Correlation.

Setup — evidence (synthetic)

  • Change ticket: "Update firmware on node A's SSD. Node B unaffected: separate server." Both nodes use Lab SSD-D through ports A and B; NSID 1 is the shared cluster volume.
  • Node A log: 02:00:04 Firmware Commit (activate without reset) succeeded.
  • Node B log: 02:00:04.2 asynchronous event logged (notice, firmware); 02:00:06.3 cluster heartbeat write to NSID 1 timed out (heartbeat timeout 2 s); 02:00:06.3 node B fences itself.
  • Identify Controller (both): FRMW indicates activation without reset supported; the maximum time for firmware activation field reports 2,500 ms (synthetic).
  • Port B capture: I/O completions stop at 02:00:04.15 and resume at 02:00:06.0; CSTS read at 02:00:05 returns 0x0000_0021.

Procedure

  1. Build the cross-node timeline.
  2. Find the first abnormal event from node B's perspective and the root cause.
  3. Decide whether the device violated anything.
  4. Write the corrective actions and a regression test.

Observations

Compare the pause length with the heartbeat timeout and with the device's advertised maximum.

Questions

  1. Was the ticket's statement "node B unaffected" correct?
  2. Did the device exceed its advertised activation time?
  3. What is the root cause?
  4. What would you change?

Expected reasoning

Firmware is subsystem-scoped; pauses are legal within the advertised bound; host timeouts must exceed device bounds.

Solution

Timeline: 02:00:04.0 commit on node A; 02:00:04.15 completions stop on port B (first abnormal event for node B, an absence); 02:00:04.2 node B receives the firmware notice; 02:00:05 CSTS shows PP = 1; 02:00:06.0 processing resumes (pause ≈ 1.85 s); 02:00:06.3 heartbeat times out (it was submitted just before the pause and its 2 s window expired shortly after resumption, before node B processed the late completion).

(1) No: firmware activation is subsystem-scoped. (2) No: about 1.85 s is within the 2,500 ms advertised maximum. (3) Root cause: a change process that treated a subsystem-scoped action as node-local, combined with a heartbeat timeout (2 s) shorter than the device's advertised activation bound (2.5 s). (4) Corrective actions: classify firmware updates on shared subsystems as cluster-wide changes; before activation, raise heartbeat timeouts above the advertised maximum or put the cluster in maintenance mode; or use "activate at next reset" and perform a coordinated reset. Regression test: in the lab cluster, activate firmware under heartbeat load and assert no fencing with the new procedure. Confidence: high.

Extension

Repeat the analysis for a sanitize issued from node A, and for an NSSR. Which of the three is recoverable without data loss?

Symptom
File system corruption on a dual-port drive; lsblk shows two NVMe disks with identical size.
Possible causes
Native multipath disabled; a third-party multipath stack misconfigured; the device reports identifiers the host cannot match.
Evidence
nvme list-subsys; wwid of both devices; multipath module parameter; mount history.
First check
Are both block devices under one subsystem with identical wwid?
Second check
Was each mounted independently (two file system instances on one namespace)?
Disambiguating experiment
On a scratch namespace, marker write through one node, read through the other.
Likely conclusion
Host configuration: one namespace mounted twice.
Confidence
High when the marker experiment confirms one namespace.

Pattern 2 — Host refuses a controller, or merges two drives

Symptom
Kernel message about a duplicate CNTLID or a rejected controller; or a "multipath" device whose paths return different data.
Possible causes
Non-unique SUBNQN across units (firmware defect); cloned identity in emulated or virtual devices; empty SUBNQN handled inconsistently.
Evidence
SUBNQN, SN, CNTLID, CMIC of each controller; namespace NGUID/EUI-64.
First check
Same SUBNQN with the same CNTLID? (Impossible in one real subsystem.)
Second check
Serial numbers and physical slots: are these two devices?

Remove or disable one device; does the "other path" disappear too?

Identity defect; apply a host quirk or firmware fix; quarantine until resolved.

High.

Pattern 3 — A host loses service after another host's maintenance

Symptom
Latency spike, timeouts or a reset on host B with nothing in host B's change log.
Possible causes
Firmware activation (pause or reset), NSSR, sanitize, format of a shared namespace, namespace detach — all issued through another controller or out of band through NVMe-MI.

Read CSTS on host B: PP = 1 now, or NSSRO = 1 since the event?

Replay the other host's maintenance step in a lab with I/O running on the second port and a two-port capture.

A subsystem-scoped action treated as local.

High once PP/NSSRO or an FR change is observed.

Interview

Beginner

  1. What is an NVM subsystem?

    Model answer

    The NVMe entity containing one or more controllers, zero or more namespaces, one or more ports and the media, identified by a subsystem NQN.

  2. What is an NQN used for?

    Model answer

    To give hosts and subsystems globally unique names, so a host can recognise that several controllers belong to one subsystem and, on fabrics, connect to the right one.

  3. Can two controllers access the same namespace?

    Model answer

    Yes, if the namespace is shareable (NMIC) and attached to both. The NSID is the same through both.

  4. What does NSSR do?

    Model answer

    Writing 4E56_4D65h to the NSSR register resets the entire subsystem — every controller on every port — and leaves NSSRO = 1 in CSTS.

  5. Why might one SSD appear as two controllers in Linux?

    Model answer

    It is dual-ported (two PCIe ports, one controller each), or it exposes SR-IOV virtual functions, each a controller.

Intermediate

  1. Name four subsystem-scoped actions.

    Model answer

    Firmware activation, sanitize, NVM Subsystem Reset, namespace management (create/delete, which draws on shared capacity). Formatting a shared namespace affects all controllers attached to it.

  2. Decode CMIC = 0x07.

    Model answer

    Bit 0: may have more than one port; bit 1: may have more than one controller; bit 2: the controller is associated with an SR-IOV virtual function. ANA reporting (bit 3) not supported.

  3. How does a host know an NSSR happened?

    Model answer

    CSTS.NSSRO = 1 after recovery. Without it, the event looks like a link failure.

  4. What are primary and secondary controllers?

    Model answer

    With SR-IOV, the physical function's primary controller manages flexible resources (queues, interrupts) of the secondary controllers in virtual functions using Virtualization Management, and brings them online or offline.

  5. What does the UUID form of an NQN look like?

    Model answer

    nqn.2014-08.org.nvmexpress:uuid: followed by a 36-character UUID string.

Advanced

  1. Why is firmware activation without reset still disruptive in a cluster?

    Model answer

    It pauses processing on every controller in the subsystem (CSTS.PP) for up to the advertised maximum; hosts whose timeouts or heartbeats are shorter fail even though no command is lost.

  2. How would you prove that host A's action caused host B's outage?

    Model answer

    Synchronised two-port capture or tightly synchronised logs showing A's command, then B's event (notice, PP, link-down), plus device-side evidence (NSSRO, FR change, firmware slot log). Correlation in time plus a mechanism.

  3. What breaks if a product line ships with the same SUBNQN on every unit?

    Model answer

    Hosts with several units group different drives into one subsystem; CNTLID collisions cause controllers to be rejected, or worse, namespaces with colliding identifiers are merged as multipath, mixing data from different media.

  4. Is sharing a namespace through two controllers safe?

    Model answer

    Safe for the device; not for the data unless the hosts coordinate through reservations, a cluster file system or an application protocol. NVMe sharing provides access, not consistency between hosts.

  5. What changes for the subsystem concept on fabrics?

    Model answer

    Controllers may be created dynamically on Connect; host NQNs and Host IDs are explicit; discovery controllers advertise subsystems; ports are fabric ports; properties are accessed by commands; NSSR semantics are transport-specific.

Senior

  1. Design a change-management rule for NVMe subsystems in a fleet.

    Model answer

    Classify every NVMe action by scope (controller, namespace, subsystem); subsystem-scoped and shared-namespace actions require notifying every host reaching the subsystem, compatible timeouts, and a maintenance state. Automate the scope lookup from CMIC, controller lists and attachment data rather than from inventory documents.

  2. What would you validate about NSSR on a dual-port device?

    Model answer

    Both links reset and retrain within a bound; NSSRO set on both controllers; namespaces, attachments and identifiers intact; volatile cache handling per specification; reservations' persistence per their settings; behaviour when NSSR arrives during firmware activation or sanitize; NSSR via out-of-band management.

  3. How do Exported NVM Subsystems change the identity problem?

    Model answer

    A physical device hosts virtual subsystems with their own identities, and in 2.4 they can be migrated to another device with matching identifiers through a configuration template. Identity must then be stable across physical devices, which makes uniqueness and duplication rules more important; field-level details must be read in Base 2.4.

  4. An architect proposes a single dual-port SSD as shared storage for a two-node cluster. Review it.

    Model answer

    Points: the drive is a single failure domain for both nodes (firmware, media, subsystem resets); maintenance actions are cluster-wide; requires reservations or a cluster file system; timeouts must exceed firmware activation; ANA/path behaviour on port failure; monitoring must read subsystem-level logs once, not per node. Acceptable for some availability goals, not as redundancy.

  5. Which evidence do you collect first when a host reports "the drive disappeared" on a shared subsystem?

    Model answer

    Before any reset: CSTS via MMIO on every controller (all-ones, NSSRO, PP, CFS), PCIe link status and AER on every port, the other hosts' and the BMC's recent actions, then device logs (firmware slots, error log, telemetry). Recovery on one port can destroy the evidence the other port needs.

Quiz

  1. Which identifier names the subsystem?

    • CNTLID
    • SUBNQN
    • NSID
    • Requester ID
    Answer and reasoning

    The subsystem NQN, reported by every controller in Identify Controller.

  2. Host A writes NSSR on a dual-port drive. What does host B see?

    • Nothing
    • A Namespace Attribute Changed notice only
    • Its link drops and outstanding commands are lost; NSSRO = 1 after recovery
    • CSTS.PP = 1
    Answer and reasoning

    NSSR resets the whole subsystem including its ports.

  3. Which action stays on one controller?

    • Controller Reset (CC.EN 1→0)
    • Firmware activation
    • Sanitize
    • NSSR
    Answer and reasoning

    A Controller Reset only touches that controller's state.

  4. CMIC bit 1 set means:

    • The namespace is shared
    • ANA is supported
    • The controller is a VF
    • The subsystem may contain more than one controller
    Answer and reasoning

    Bit 1 is multiple controllers; bit 0 multiple ports; bit 2 SR-IOV; bit 3 ANA reporting.

  5. Two controllers report the same SUBNQN and the same CNTLID. What do you conclude?

    Model answer

    They cannot be one subsystem (CNTLIDs are unique within a subsystem): two devices share a name. Do not merge them; investigate a firmware identity defect.

  6. Why is NMIC sharing not enough for two hosts to write one namespace safely?

    Model answer

    NMIC allows attachment to several controllers; it does not coordinate writes. Reservations or cluster software are needed.

  7. What is the maximum length of an NQN?

    • 64 bytes
    • 223 bytes
    • 256 characters
    • 4096 bytes
    Answer and reasoning

    223 bytes, UTF-8 encoded.

  8. In the slow trace, what tells host B the pause is legitimate?

    Model answer

    The firmware-activation notice completing its Asynchronous Event Request, and CSTS.PP = 1 during the stall; completions resume without errors.

  9. Which Identify CNS value lists all controllers in the subsystem?

    • 01h
    • 02h
    • 13h
    • 00h
    Answer and reasoning

    CNS 13h; 12h lists controllers attached to a given NSID.

Teach-back

To a child

Model explanation

"An SSD can be like an apartment building with two front doors. Each door has its own doorman, but they share one basement. The building has one name, so the post office knows both doors are the same building. If someone flips the main fuse, both doors go dark — even the door you were using."

To a junior engineer

Model explanation

"The subsystem is the container: controllers, namespaces, ports, media, one SUBNQN. Queues, CC/CSTS and most features are per controller; NSIDs, firmware, sanitize, capacity and NSSR are per subsystem. Dual-port drives give one controller per port; SR-IOV gives one controller per VF. Linux groups controllers by SUBNQN and merges shared namespaces into one multipath device. Before you run a firmware update or a subsystem reset, ask which other controllers and hosts it reaches."

To a senior engineer

Model explanation

"Treat the subsystem as the blast-radius and identity boundary. Cross-host causality only shows with two-port evidence: command on A, then notice, PP or link-down on B, confirmed by NSSRO or an FR change. Identity is a safety property — duplicate SUBNQNs or cloned namespace identifiers turn multipath into data corruption, so validate uniqueness and keep a marker-write test in the playbook. Operational rules follow: subsystem-scoped actions are cluster changes; host timeouts must exceed the device's advertised activation bound; NSSR is never routine on shared subsystems."

Mastery gate

Do not consider this module mastered until you can:

  • explain the subsystem as an identity, persistence and blast-radius scope;
  • diagram Lab SSD-D with ports, controllers, shared and private namespaces;
  • identify in traces a cross-port firmware pause, an NSSR from another host, and an identity mismatch;
  • debug the six failure patterns, including the marker-write experiment;
  • distinguish the subsystem from neighbouring concepts: the controller (NVMe Controller), the namespace (Namespaces), the PCIe device and its functions (SR-IOV), and the fabric target (Fabric Architecture);
  • cite NVM Express Base Specification, Revision 2.4 (subsystem entities, NQNs, firmware update, NVM Subsystem Reset, Exported NVM Subsystems) and NVMe over PCIe Transport Specification, Revision 1.4.
