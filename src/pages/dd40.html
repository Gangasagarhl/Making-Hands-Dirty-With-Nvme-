PCIe errors are reported by whichever function noticed them, which is often not the one that caused them. This module goes deeper than classifying errors: it follows errors through switches and root ports, through containment and recovery, through masking and firmware-first handling, and into their effects on an NVMe SSD, so that you can name the cause, the victim and the reporter separately.

Orientation

PCIe Errors classified errors by layer (Physical, Data Link, Transaction) and by severity (correctable, uncorrectable non-fatal, uncorrectable fatal), and showed what each one does to NVMe. AER opened the Advanced Error Reporting capability: status, mask and severity registers, First Error Pointer, Header Log, root port registers and the Linux report format. This module assumes both and adds what an engineer needs in real systems: who reports what in a hierarchy with switches; containment with Downstream Port Containment (DPC) and what it does to an NVMe controller; timeouts and late completions as a pair; rates and trends of correctable errors as a predictor; and evidence that disappears (masks, firmware-first handling, register clearing by recovery).

Needed first: PCIe Errors (classes, detection, completion status, NVMe effects), AER (registers and Linux reports), PCIe Flow Control and DLLP and Replay for the Data Link Layer machinery, and PCIe Reset for what recovery does.

Where this goes next: Advanced Error Handling and Reset continue into containment and recovery; NVMe Errors covers the layer above; AER goes deeper on the capability itself.

Kid story

A town has a postal system with sorting offices. Every office checks every parcel it receives. If a label is smudged, the office asks the previous office to send it again, and writes a tally mark in a little book. If a parcel is addressed to a house that doesn't exist, the office sends back a "no such address" card. If a parcel is torn and leaking, it is stamped "damaged" and delivered anyway, so the person knows not to use it. If a bridge between two offices collapses, a guard at the bridge closes the road at once so that no more parcels fall into the river.

The office that writes in its book is the office that noticed, not the one that made the mistake. And every office sends a short note to the town hall when something serious happens, but the town hall's in-tray only has room to remember one sender at a time, plus a sticker that says "others wrote too".

What it hides. Posted parcels (memory writes) to non-existent houses are not returned to the sender at all: only the office that noticed knows. And some offices can be told to stop writing in their book (masks) or to treat a serious problem as minor (severity), so an empty book does not prove nothing happened.

Where it misleads. The story suggests the "damaged" stamp means the post office broke it; in PCIe, poisoning usually means the sender's memory already held bad data. It also suggests the guard closes only one road; DPC disables the whole link below a port, taking down every function there, including a healthy NVMe controller with commands in flight.

Mechanism

We follow an uncorrectable non-fatal error end to end on the switch topology: the SSD's DMA read of a PRP list receives no completion because the host IOMMU stalled, the SSD logs a Completion Timeout, and recovery runs.

  1. Request. Who: SSD (RID 0x0300). What: MRd for a PRP list, tag 0x32, starts its completion timer. Where: SSD transaction layer. Evidence: MRd on links B and A.
  2. Silence. Who: host root complex (fails to complete). What: nothing returns. Where: host. Evidence: absence of a CplD with tag 0x32 for longer than the timeout range.
  3. Detect. Who: SSD. What: Completion Timeout status bit (Uncorrectable Error Status bit 14) set; tag retired; First Error Pointer = 14 if first; Header Log only if the function supports logging headers for completion timeouts. Where: SSD AER capability; Device Status Non-Fatal Error Detected. Evidence: configuration reads later.
  4. Signal. Who: SSD. What: ERR_NONFATAL message with Requester ID 0x0300 (if Non-Fatal Reporting Enable is set and the bit is unmasked). Where: link B, forwarded by the switch through link A. Evidence: Msg TLP on both links.
  5. Collect. Who: root port 00:01.1. What: Root Error Status: ERR_FATAL/NONFATAL Received; Error Source Identification bits 31:16 = 0x0300; interrupt if Root Error Command enables it. Where: root port AER. Evidence: OS interrupt.
  6. Diagnose. Who: OS AER driver (or firmware, if firmware-first). What: reads root port and source registers, prints a report, increments counters. Where: configuration reads to 00:01.1 and 03:00.0. Evidence: kernel log; sysfs counters.
  7. Consequence at NVMe. Who: SSD firmware. What: the command whose PRP list could not be read completes with Data Transfer Error. Where: host CQ. Evidence: CQE status SCT 0h SC 04h.
  8. Recover. Who: OS error recovery. What: calls the NVMe driver's error_detected callback; for a non-fatal error the device may continue (with MMIO checks), or recovery may reset the link. Where: host software. Evidence: kernel log lines from the AER and NVMe drivers.
  9. Clear. Who: OS. What: writes 1s to clear status bits (RW1C) in the SSD and root port. Evidence: CfgWr TLPs; status reads 0 afterwards. After this step, the register evidence is gone; only logs and counters remain.

Containment: what DPC does to an NVMe SSD

  1. An unmasked uncorrectable error of a class configured to trigger DPC is detected at, or reported to, a downstream port with DPC enabled.
  2. The port immediately takes its link down (the LTSSM goes to Disabled) and sets DPC Trigger Status. Requests in flight toward the device are completed by the port with error status or discarded, depending on the request type and configuration Uncertain: confirm the DPC completion-handling rules in the specification.
  3. The OS DPC driver is interrupted, tells drivers below the port that their devices are offline, and later clears DPC Trigger Status, which lets the link retrain.
  4. The NVMe controller has been reset by the link going down: all queues, outstanding commands and controller state are gone. The NVMe driver must reinitialise from configuration space up (BARs and MSI-X restored by the OS), and requeue or fail outstanding I/O.

The central concept on the ladder

The central concept is separating cause, detector, reporter and victim for every PCIe error, and knowing which evidence each one leaves.

The office that wrote in its book noticed the problem; it may not have made it; the person whose parcel was lost is someone else again.

Every PCIe error is detected by one function in a role (receiver, requester, completer), logged there, possibly signalled to the root complex, and causes harm elsewhere. Root cause is usually one hop away from the detector.

Receivers detect symbol and LCRC errors; transmitters detect replay timeouts and rollovers; requesters time out tags; completers check addresses and permissions; downstream ports detect link loss. Each sets sticky bits in its own AER capability; root ports collect messages and interrupt the OS; DPC hardware can disable a link in microseconds.

The PCI Express Base Specification defines error classes, default severities, role-based reporting, error pollution, messages, the AER and DPC capabilities, completion timeout ranges and Data Link Layer retry. It does not define OS recovery policy or what an NVMe controller reports.

On the wire: NAK DLLPs and replays; Cpl with UR or CA; TLPs with EP set; Msg ERR_*; missing completions; electrical idle and training sequences when links drop or recover.

In a capture, the error message's Requester ID names the reporter; the Header Log names the transaction; the first abnormal TLP (or absence) is the cause's footprint. Captures placed on one link do not see errors detected on another.

For every error, write four names: cause, detector, reporter, victim. Then check that the evidence is complete: masks, severities, firmware-first, and whether recovery cleared registers before you read them.

Well established: three severities with ERR_COR, ERR_NONFATAL, ERR_FATAL; default fatal errors are Data Link Protocol Error, Surprise Down, Flow Control Protocol Error, Receiver Overflow, Malformed TLP and Uncorrectable Internal Error; default correctable mask hides Advisory Non-Fatal, Corrected Internal Error and Header Log Overflow; status bits are sticky and write-1-to-clear; the root port records one source per class plus "Multiple" flags; the default completion timeout range is 50 µs to 50 ms; completion statuses are SC, UR, RRS (formerly CRS) and CA.

Derived: the cause/detector/reporter/victim table; rate thresholds for correctable errors; the inference that simultaneous errors from several functions behind one switch suggest a common upstream cause. These are engineering judgements built on the specification's rules.

Implementation-dependent: whether endpoints implement AER (most NVMe SSDs do) and DPC (ports only); whether a function logs headers for completion timeouts; actual timeout within the configured range; how a root complex answers a CPU read that failed (all ones or a machine check); firmware-first versus OS-first; Linux's choice to reset on non-fatal errors.

Version-dependent: DPC and eDPC arrived as ECNs and were folded into later base revisions; Configuration Request Retry Status was renamed Request Retry Status; FLIT mode (6.0) with forward error correction changes how often bit errors reach the Data Link Layer and how retries are performed; new error bits appear in the uncorrectable registers over revisions. Check the revision in each function's PCI Express Capability.

The PCI Express Base Specification does not say how an OS must recover, how many correctable errors are acceptable, or what an NVMe controller must report when its DMA fails. NVMe does not define PCIe error logging. Check in the specification: the full role-based reporting table (which role logs which error, and when Advisory Non-Fatal applies); the error pollution rules; the DPC trigger options and how in-flight requests are completed; the completion timeout value encodings in Device Control 2.

Never assume the reporter caused the error. Never treat zero AER counts as proof of a clean link without checking masks, severities, reporting enables and firmware-first. Never read AER registers after recovery and conclude "no error": recovery clears them.

Completion timeouts and late completions as a pair

When a completer is slow rather than dead, a requester whose timeout is short logs Completion Timeout and retires the tag; when the completion finally arrives, the requester logs Unexpected Completion (and discards it). The pair "CmpltTO, then UnxCmplt for the same tag" is evidence that the completer answered, late. The fix is either the completer's latency or the requester's timeout range, not the link.

Ordering of evidence in a cascade

For a fault that causes both PCIe and NVMe errors, the expected order is: wire-level footprint (missing completion, UR completion, poisoned TLP) → detector's status bits → error message → root port interrupt → NVMe status in a CQE (if the controller survives) → host timeouts and recovery. The NVMe status may appear before the OS prints the AER report, because the report is produced by software after an interrupt, while the CQE goes straight to memory.

Beginner lab — Four names for ten errors

Which events leave no evidence at the SSD at all?
Expected reasoning

Intermediate lab — Turn counters into rates and trends

Safe lab Python 3, standard library only.

Objective
Convert periodic snapshots of AER counters into rates, detect trends, and raise alerts that predict failure rather than react to it.
Prerequisites
The slow trace; Linux view counters.
Setup
Save as aer_trend.py. The snapshots are synthetic, in the format of the kernel's per-type counter files (type name and count).
#!/usr/bin/env python3
"""Rate and trend analysis of AER correctable-error counters (synthetic snapshots)."""

# (minute, device, {counter: cumulative count}, link speed GT/s, temperature C)
SNAPS = [
    (0,  "02:01.0", {"RxErr": 10,    "BadTLP": 12,    "Rollover": 0, "Timeout": 0}, 16, 52),
    (0,  "03:00.0", {"RxErr": 0,     "BadTLP": 0,     "Rollover": 0, "Timeout": 0}, 16, 52),
    (10, "02:01.0", {"RxErr": 2400,  "BadTLP": 2500,  "Rollover": 0, "Timeout": 0}, 16, 61),
    (10, "03:00.0", {"RxErr": 0,     "BadTLP": 0,     "Rollover": 0, "Timeout": 3}, 16, 61),
    (20, "02:01.0", {"RxErr": 21000, "BadTLP": 22000, "Rollover": 0, "Timeout": 0}, 16, 68),
    (20, "03:00.0", {"RxErr": 0,     "BadTLP": 0,     "Rollover": 2, "Timeout": 40}, 16, 68),
    (30, "02:01.0", {"RxErr": 23000, "BadTLP": 23500, "Rollover": 0, "Timeout": 0}, 8, 71),
    (30, "03:00.0", {"RxErr": 0,     "BadTLP": 0,     "Rollover": 5, "Timeout": 55}, 8, 71),
]
LIMIT_PER_MIN = {"RxErr": 60, "BadTLP": 60, "Rollover": 0, "Timeout": 10}

def analyse(snaps):
    last = {}
    for minute, dev, counts, speed, temp in snaps:
        if dev in last:
            m0, c0, s0 = last[dev]
            dt = minute - m0
            for k, v in counts.items():
                rate = (v - c0[k]) / dt
                if rate > LIMIT_PER_MIN[k]:
                    print(f"t={minute:>3} min {dev} {k:<8} {rate:>8.1f}/min  ALERT (temp {temp} C)")
            if speed < s0:
                print(f"t={minute:>3} min {dev} link speed {s0} -> {speed} GT/s  ALERT: downgrade")
        last[dev] = (minute, dict(counts), speed)

if __name__ == "__main__":
    analyse(SNAPS)
Procedure
  1. Run it.
  2. Identify the first alert and the first alert on each device.
  3. Set the Rollover limit to 1 and rerun: what changes?
Observations
Receiver-side errors appear at the switch DSP; transmitter-side errors (Replay Timer Timeout, Rollover) at the SSD.
Questions
  1. Why do the two ends of link B show different error types?
  2. When could an operator have acted, and with what?
  3. Why does the BadTLP rate drop in the last interval, and is that good news?
Expected reasoning
Receivers count what they receive badly; transmitters count retries they had to make; a downgrade lowers the error rate by lowering the speed.
Solution

At 10 minutes the switch DSP's RxErr and BadTLP rates (about 240/min each) already exceed limits at 61 °C, and the SSD shows Replay Timer Timeouts (0.3/min, below limit). At 20 minutes rates are about 1,860 (RxErr) and 1,950 (BadTLP) per minute at the DSP; the SSD's timeouts reach 3.7/min (still below its limit) and it logs two rollovers (0.2/min, an alert because the rollover limit is 0). At 30 minutes the DSP rates fall to 200 (RxErr) and 150 (BadTLP) per minute, and both ends report the downgrade to 8 GT/s: the drop is not good news; the link is slower and still erroring. The two ends differ because the SSD is the transmitter of the corrupted direction (it sees missing ACKs: Replay Timer Timeout and Rollover), while the switch DSP is its receiver (it sees bad TLPs). An operator could have acted at 10 minutes: correlate with temperature, schedule maintenance, check airflow, run lane margining. With a Rollover limit of 1, both rollover alerts disappear (0.2/min and 0.3/min), so the SSD's first alert is the downgrade itself; that is why any rollover deserves attention.

Extension

Advanced lab — Predict containment and recovery

Safe lab Read-only inspection plus paper. Do not inject errors on a system you care about.

Objective
From a port's DPC and AER configuration, predict what happens to an NVMe SSD for each class of error, then check the predictions against the configuration on your own machine.
Prerequisites
Mechanism (containment); PCIe Reset.
Setup
Run the read-only lspci commands from the Linux view against your NVMe SSD's root port (or downstream port). Record: DPC capability present and enabled? Trigger on fatal only or also non-fatal? AER severity register of the port and the SSD. Firmware-first or OS-first.
Procedure
For each of: Bad TLP storm, Completion Timeout at the SSD, Poisoned TLP at the SSD, Malformed TLP at the port, Surprise Down: write (a) whether DPC triggers, (b) what happens to in-flight NVMe commands, (c) what the NVMe driver must do, (d) where the evidence will be after recovery.
Questions
Which configuration would turn a non-fatal SSD error into a full link reset?
Expected reasoning
DPC triggers on uncorrectable errors of the configured classes at or reported to the port; severity settings decide fatal versus non-fatal.
Solution

With DPC enabled and triggering on fatal errors only (a common setting), and default severities: Bad TLP storm, no DPC (correctable), commands only delayed; Completion Timeout at the SSD, non-fatal, no DPC, the affected command fails with Data Transfer Error and the OS may run non-fatal recovery (which, depending on the kernel and driver, may still reset the device); Poisoned TLP at the SSD, the same; Malformed TLP at the port, fatal, DPC triggers, the link goes down, all in-flight commands are lost, the NVMe driver reinitialises after the OS releases containment; Surprise Down, fatal, the same, though the device may not come back. Evidence after recovery: the SSD's sticky status bits may survive (if it kept auxiliary power and the OS did not clear them), the port's DPC status records the trigger reason until cleared, kernel logs and counters hold the reports; with firmware-first, look in the platform's error records instead. A configuration that makes an SSD non-fatal error reset the link: DPC set to trigger on non-fatal errors as well, or the SSD's (or port's) severity register changed to make that error fatal. Your own machine's answers depend on its firmware; record them as observations, not as general truths.

Extension
On a disposable test system with a kernel built with the aer-inject facility, inject a correctable error at the SSD and confirm the counters move (Caution lab).

Senior forensic lab — One switch, many victims

Safe lab Evidence analysis.

Objective
Decide between independent device failures and a common upstream cause from fleet evidence, and write the root-cause report.
Prerequisites
The ambiguous trace in AER (Multiple ERR_FATAL/NONFATAL); this module's role table.
Setup
Evidence (synthetic): over a week, 14 servers of one model report NVMe I/O timeouts on SSDs behind the same switch model. Per incident: two or three SSDs behind the same switch log Completion Timeout within 10 µs of each other; the root port's Root Error Status shows Multiple ERR_FATAL/NONFATAL Received; Error Source ID names one SSD; switch USP AER shows no errors; SSDs in direct-attached slots on the same servers never fail; three incidents coincide with BMC logs of the switch's temperature above 85 °C; the switch firmware was updated fleet-wide two weeks earlier.
Procedure
Build hypotheses; weigh each piece of evidence; name the cause, detector, reporter and victims; propose a disambiguating experiment and interim mitigation.
Questions
  1. Why does the root port name only one SSD?
  2. Why might the switch's own AER be empty even if the switch is the cause?
  3. What would make you change your conclusion?
Expected reasoning
Simultaneous requesters timing out behind one switch implies the completions were lost in or above the switch.
Solution

Hypotheses: (a) independent SSD failures (rejected: simultaneity within 10 µs across different drives, and direct-attached drives never fail); (b) host completer (root complex or memory) stalls (possible, but direct-attached SSDs on the same root complex do not time out, which argues against a global host stall); (c) the switch drops or stalls completions toward its downstream ports (supported by locality, simultaneity, temperature correlation and the recent firmware change). The root port names one source because Error Source Identification holds one RID per class; the Multiple bit says others reported. The switch's AER may be empty because a switch that internally drops completions may not detect any error of its own (it is an intermediate, not a requester or completer), or because its uncorrectable internal error bit is masked by default. Conclusion: cause, the switch (firmware or thermal); detectors and reporters, the SSDs (requesters); victims, the NVMe commands on those SSDs. Confidence: medium-high. Disambiguating experiment: roll back switch firmware on a subset and compare incident rates; run thermal stress in the lab with a capture on both sides of the switch to see completions entering and not leaving. Interim mitigation: improve switch cooling, lengthen SSD completion timeout ranges only if supported and acceptable (it hides, not fixes), and alert on Multiple ERR bits. What would change the conclusion: incidents on direct-attached SSDs, or captures showing completions leaving the switch intact.

Extension
Write the bug report to the switch vendor using Engineering Bug Report Training.

Debugging

Pattern 1 — Correctable error storm and downgrade

SymptomLatency spikes, throughput loss, high correctable counts, LnkSta below LnkCap.
Possible causesSignal integrity (connector, cable, retimer, board), temperature, equalisation settings, a failing transmitter.
EvidenceCounters at both ends of each link; Rollover counts; link speed history; temperature; Lane Margining.
First checkWhich end logs receive errors and which logs replay errors? That identifies the direction.
Second checkDo rates correlate with temperature or load?
Disambiguating experimentSwap drive and slot; force a lower speed; margin each lane.
Likely conclusionA marginal link segment in one direction; the hardware at either end of that segment or the channel.
ConfidenceHigh after the swap experiment.

Pattern 2 — Completion Timeout at the SSD

SymptomAER CmpltTO at the SSD; NVMe Data Transfer Errors or I/O timeouts.
Possible causesHost completer stall (IOMMU, memory, root complex), switch dropping completions, link recovery during the request, short timeout range.
EvidenceRoot port and switch AER; IOMMU messages; Multiple bits; DevCtl2 of the SSD; capture showing the request and absence.
First checkIs the SSD the only device timing out, and only for some addresses?
Second checkAny link recovery or switch error at the same time?
Disambiguating experimentCapture on both sides of the switch; move the SSD to a direct-attached slot.
Likely conclusionThe completer side or path, not the SSD.
ConfidenceMedium until a capture shows where the completion was lost.

Pattern 3 — Unsupported Request: DMA or MMIO?

SymptomAER UnsupReq somewhere on the path.
Possible causesAt the root port with the SSD as requester: DMA to an unmapped IOVA (driver). At the SSD with the root complex as requester: MMIO to an unclaimed address or with Memory Space Enable clear (host). At a switch: an address no port claims.
EvidenceWhich function logged it; the Header Log (requester ID, address, type).
First checkDecode the Header Log: requester and address.
Second checkFor DMA: IOMMU fault at the same address. For MMIO: BAR assignment and MSE.
Disambiguating experimentReproduce with IOMMU strict mode and driver assertions (DMA) or with a BAR/MSE check before access (MMIO).
Likely conclusionHost software in both cases; the header says which part.
ConfidenceHigh with a valid header.

Pattern 4 — Fatal Malformed TLP after hot-plug or reconfiguration

SymptomLink reset and device loss shortly after hot-plug, firmware update or a kernel parameter change.
Possible causesMPS mismatch along the path; a device sending illegal TLPs (4 KiB crossing, see DMA with NVMe).
EvidenceHeader Log at the detecting port: Length versus MPS, address versus 4 KiB; MaxPayload settings of each function on the path.
First checkCompare DevCtl MaxPayload on every function from root port to SSD.
Second checkDecode the header's Length and address.
Disambiguating experimentForce consistent MPS; reproduce with a known-good device.
Likely conclusionConfiguration if MPS differs; device bug if settings are consistent and the header shows a rule violation.
ConfidenceHigh.

Pattern 5 — Surprise Down or DPC events

SymptomDevice disappears; DPC containment or Surprise Down reported by the port above it.
Possible causesPower loss to the device, connector or cable, device firmware crash that drops the link, deliberate removal without hot-plug notification.
EvidencePlatform power logs; SMART Unsafe Shutdowns; device telemetry after return; whether the device returns after link retrain.
First checkDid Unsafe Shutdowns increase (power) or not (firmware-initiated link drop more likely)?
Second checkDoes the event follow the drive or the slot?
Disambiguating experimentSwap drives and slots; monitor slot power rails.
Likely conclusionPower/slot if the event follows the slot; device if it follows the drive.
ConfidenceMedium until the swap result is in.

Pattern 6 — Errors that never appear in the OS

SymptomNVMe Data Transfer Errors or timeouts with clean OS AER logs.
Possible causesFirmware-first handling; masked errors; reporting enables off in Device Control; errors detected on a link the OS does not monitor (switch internal); recovery cleared registers.
Evidence_OSC negotiation and GHES messages; UEMsk/CEMsk; DevCtl reporting enable bits; platform error logs.
First checkWho owns AER on this platform?
Second checkMasks and enables on every function of the path.
Disambiguating experimentOn a test system, switch to OS-first (if the platform allows) and reproduce.
Likely conclusionEvidence suppressed or relocated, not absent.
ConfidenceHigh once ownership and masks are known.

Interview

Beginner

  1. Name the three PCIe error severities and their messages.

    Model answer

    Correctable (ERR_COR), uncorrectable non-fatal (ERR_NONFATAL), uncorrectable fatal (ERR_FATAL).

  2. Which function logs a Completion Timeout?

    Model answer

    The requester, whose request did not receive its completion in time.

  3. What is a NAK DLLP for?

    Model answer

    It tells the transmitter that a TLP failed its checks and that TLPs after the acknowledged sequence number must be replayed.

  4. Why does a DMA write to an unmapped address produce no error at the SSD?

    Model answer

    Memory writes are posted: no completion returns, so only the host side (IOMMU or root complex) knows it failed.

  5. Where does Linux keep per-device AER counts?

    Model answer

    In sysfs files such as aer_dev_correctable, aer_dev_nonfatal and aer_dev_fatal under the device, plus root port totals.

Intermediate

  1. Behind a switch, which RID appears in an ERR_COR caused by bit errors from the SSD toward the switch?

    Model answer

    The switch downstream port's, because it is the receiver that detected the bad TLPs.

  2. What does the pair Completion Timeout followed by Unexpected Completion for the same tag mean?

    Model answer

    The completer answered, but after the requester's timeout; the problem is completer latency or a too-short timeout, not a lost path.

  3. What does DPC do and what does it cost an NVMe SSD?

    Model answer

    It disables the link below a downstream port immediately on configured uncorrectable errors, preventing further corruption. The SSD loses all controller state and in-flight commands, and must be reinitialised after the OS releases containment.

  4. Why is REPLAY_NUM Rollover more important than a single Bad TLP?

    Model answer

    It means several replays in a row failed to make progress and the link had to retrain: a stall and a precursor to speed or width downgrade.

  5. What is firmware-first error handling and why does it matter for debugging?

    Model answer

    Platform firmware owns AER, reads and clears registers, and reports via ACPI records. OS AER logs may be empty or summarised; evidence must be collected from platform logs.

Advanced

  1. Explain the error pollution concept.

    Model answer

    When one event triggers several error conditions, the specification's rules have the function report the most significant one rather than all, to avoid misleading cascades. So missing secondary bits do not mean secondary conditions did not occur; read the rules for the exact precedence.

  2. How would you prove which direction of a link is marginal?

    Model answer

    Receiver-side errors (RxErr, BadTLP) at the receiving end and replay-side errors (Replay Timer Timeout, Rollover) at the transmitting end point to one direction; Lane Margining at each receiver quantifies it; an analyzer shows which direction carries NAKs.

  3. Why can a root port's Header Log mislead you?

    Model answer

    It belongs to the error named by the First Error Pointer, which may be an older error whose status was never cleared; some error types do not log headers; firmware or recovery may have cleared it.

  4. What happens to an outstanding NVMe MMIO read when DPC triggers?

    Model answer

    The port completes or discards it according to DPC rules; the CPU typically receives all ones. The NVMe driver must treat this as device loss, not a register value.

  5. Which completion timeout setting would you choose for an NVMe SSD and why?

    Model answer

    Long enough to exceed the worst legitimate completion latency on the path (including switches, IOMMU stalls and device firmware activities) with margin, but short enough to bound hangs; typically the default or range B, decided from measured latency distributions rather than guessed.

Senior

  1. Design fleet monitoring for PCIe errors on NVMe servers.

    Model answer

    Collect counters at both ends of every link and at switch ports, link speed and width, temperatures, DPC and Surprise Down events, Multiple-bit occurrences, and platform firmware records; compute rates and trends per link direction; alert on any Rollover, any downgrade, rising correctable rates, and correlated events across devices behind one switch.

  2. A vendor says "your platform's root port logged the error, so it's your problem". How do you respond?

    Model answer

    Separate roles: the root port may be the detector or reporter; decode the Header Log to identify the transaction and requester; check whether the requester's behaviour was legal; show evidence for the cause one hop away; agree on the experiment that separates the hypotheses.

  3. How do you validate an NVMe SSD's behaviour under PCIe errors?

    Model answer

    Use an exerciser or jammer to inject UR, CA and poisoned completions, drop completions, corrupt TLPs, and drop the link; check the SSD's AER status, header logs, error messages, NVMe status (Data Transfer Error for failed data, no silent success), recovery after link reset, and that no data is committed from poisoned completions.

  4. What are the risks of masking correctable errors to quiet logs?

    Model answer

    You lose the early warning of degrading links; the first visible event becomes a rollover, downgrade or fatal error. Rate-limit reporting and alert on trends instead.

  5. When is it right to change an error's severity?

    Model answer

    Rarely, and with documented reasons: for example making an error fatal to force containment in a system where corruption risk outweighs availability, or non-fatal to avoid resets for a known-benign condition. Changes must be recorded because they alter all later evidence.

Quiz

  1. Bit errors on the SSD→switch link are detected by:

    • The SSD's receiver
    • The switch downstream port's receiver
    • The root port
    • The IOMMU
    Answer and reasoning

    The receiver of the corrupted direction detects it: the switch downstream port.

  2. Which error is fatal by default?

    • Completion Timeout
    • Unsupported Request
    • Poisoned TLP Received
    • Surprise Down
    Answer and reasoning

    Surprise Down is fatal by default; the others are non-fatal.

  3. Root Error Status shows Multiple ERR_FATAL/NONFATAL Received. What do you know?

    • More than one uncorrectable message arrived before software handled the first; only one source is recorded
    • The same device reported twice
    • The link failed twice
    • Nothing useful
    Answer and reasoning

    The source register holds one RID; the Multiple bit signals others.

  4. The default completion timeout range is:

    • 1 µs to 10 µs
    • 10 ms to 250 ms
    • 50 µs to 50 ms
    • 4 s to 64 s
    Answer and reasoning

    50 µs to 50 ms when no other value is selected.

  5. After DPC contains a link to an NVMe SSD, what must the NVMe driver do?

    • Nothing; DPC preserves state
    • Reinitialise the controller after the OS releases containment
    • Clear CSTS.CFS
    • Send Abort for each command
    Answer and reasoning

    The link went down, so the controller is reset; all queues must be rebuilt.

  6. Which evidence best shows that a completer was slow rather than dead?

    • Completion Timeout alone
    • All-ones read data
    • Completion Timeout followed by Unexpected Completion for the same tag
    • ERR_COR from the requester
    Answer and reasoning

    The late completion proves an answer was sent.

  7. Give the four roles for an SSD Poisoned TLP Received error during a WRITE's data pull, caused by a host memory ECC error.

    Model answer

    Cause: host memory. Detector: the SSD (receiver of the poisoned CplD). Reporter: the SSD (ERR_NONFATAL, its RID). Victim: the WRITE command (Data Transfer Error).

  8. Why can AER counters be zero while PCIe errors are occurring?

    Model answer

    Firmware-first handling, masks, disabled reporting enables, errors detected only at functions the OS does not read, or counters reset by recovery or reboot.

  9. What do falling correctable error rates after a link downgrade mean?

    Model answer

    The link is running slower, which hides the margin problem; it is not a recovery. Investigate and restore the intended speed.

Teach-back

  1. To a child. Why isn't the office that wrote the complaint always the one to blame?

    Model explanation

    Each post office checks what it receives. If a parcel arrives smudged, the office that notices writes it down, even though the smudge happened on the road before. If a road collapses, the guard closes it so no more parcels are lost, and everyone has to start again once it's fixed.

  2. To a junior engineer. How do you read a PCIe error report on an NVMe system?

    Model explanation

    Find which function logged it and in what role: receiver (link errors), requester (timeouts, unexpected completions), completer (UR, CA). Decode the header log to find the transaction. The cause is usually one hop away from the detector. Check both ends of each link, the switch ports, masks and whether firmware handles errors. Then find the NVMe consequence: Data Transfer Error, timeout, or controller reset after containment.

  3. To a senior engineer. What makes PCIe error evidence trustworthy?

    Model explanation

    Completeness and provenance: who owns AER, masks and severities as configured at the time, registers read before recovery cleared them, counters from both ends of every link and from switches, and a capture where possible. With that, you separate cause, detector, reporter and victim, and you can treat simultaneous reports from several devices as one upstream cause instead of several failures.

Mastery gate

Do not consider this module mastered until you can:

  • explain cause, detector, reporter and victim for any PCIe error on a topology with a switch
  • diagram error signalling, collection, containment and recovery
  • identify NAK/replay, rollover and Recovery, UR/CA completions, poisoned TLPs, missing and late completions, and Surprise Down in a capture
  • debug a correctable storm, a completion timeout, a UR and a Surprise Down to the right owner
  • distinguish PCIe errors from neighbours: the AER capability itself (AER), Data Link Layer retry (DLLP and Replay), NVMe status (NVMe Errors), and resets (Reset)
  • cite the PCI Express Base Specification by name and revision family for every rule, and label OS and platform behaviour as implementation-dependent
