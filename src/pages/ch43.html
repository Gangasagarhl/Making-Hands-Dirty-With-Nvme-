MSI-X turns "the device needs attention" into an ordinary PCIe Memory Write whose address and data the operating system chose in advance, one entry per vector. This chapter opens the MSI-X capability, the vector table and the Pending Bit Array field by field, shows how NVMe binds completion queues to vectors, and teaches you to find every step in a trace and in Linux.

Why this chapter exists

Chapter 42 compared the three interrupt mechanisms and argued that NVMe needs Message Signaled Interrupts eXtended (MSI-X). This chapter is the mechanics: where the MSI-X structures live, who writes each field, what the controller does when a completion queue needs attention, and what an interrupt looks like as a Transaction Layer Packet (TLP). Engineers who can decode an MSI-X table entry by eye can answer "where did that interrupt go?" in minutes instead of days.

Learning objectives

  • Locate the MSI-X capability in configuration space and decode Message Control (Table Size, Function Mask, MSI-X Enable), Table Offset/BIR and PBA Offset/BIR.
  • Find the MSI-X table and Pending Bit Array (PBA) in a Base Address Register (BAR) region and decode a 16-byte table entry (Message Address, Message Upper Address, Message Data, Vector Control).
  • Explain the masking and pending rules: what the device does when a vector is masked, and what happens on unmask.
  • Explain how NVMe maps completion queues to vectors (Create I/O Completion Queue IV and IEN; admin CQ on vector 0) and how Linux chooses the mapping.
  • Identify the interrupt as a posted Memory Write (MWr) TLP in a trace, with its Requester ID, address, data and ordering position.
  • Read MSI-X state in Linux: lspci -vvv, /proc/interrupts, msi_irqs, IRQ affinity.
  • Debug masked, misrouted, stale and missing MSI-X interrupts.

Prerequisites

Read Interrupt Architecture first. You also need Configuration Space (capability lists), BARs and MMIO (how a BAR region is addressed), TLP Header Anatomy (MWr fields), Posted vs Non-Posted, and I/O Queues (Create I/O Completion Queue).

The story

The librarian has a clipboard. On it is a list with one line per "done basket". Each line has three things: a room number, a secret word, and a little red flag. When a book lands in basket 3, the librarian looks at line 3. If the red flag is down, she walks to that room and says the secret word — and the teacher there knows exactly what to do. If the red flag is up, she does not walk; she puts a tick next to line 3 on a second sheet called "waiting". When the teacher lowers the flag later, the librarian sees the tick and goes straight away.

The teachers write the clipboard, not the librarian. The librarian only reads it.

MSI-X is like a hotel's guest-paging system. Each guest (CPU) registers a pager number at the front desk; the desk keeps a ledger: "room service for floor 3 → pager 0x41 on desk 1". When an order is ready the kitchen does not shout; it dials the number from the ledger. A "do not disturb" flag on a ledger line makes the kitchen hold the call and mark it pending; when the flag is cleared, the held call goes out at once.

Hides: the "dial" is a 4-byte Memory Write that travels the same PCIe path as data, so it can be delayed by flow control, blocked by the Input-Output Memory Management Unit (IOMMU), or ordered behind earlier writes. Misleads: one held call per line, not one per order: the pending bit is a single bit, so ten events on a masked vector produce one interrupt on unmask, not ten. And the ledger lives inside the device's memory space (a BAR), not at the front desk (the CPU), even though the CPU writes it.

Beginner explanation

MSI-X has four parts:

  1. The capability — a small structure in the device's configuration space. It says "I support MSI-X", how many vectors, and where the table and pending bits are. It also holds the on/off switch (MSI-X Enable) and a master mute (Function Mask).
  2. The table — in the device's memory-mapped space (inside one of its BARs). One 16-byte row per vector: where to write (address), what to write (data), and a mute flag (mask bit).
  3. The Pending Bit Array — also in a BAR. One bit per vector, set by the device when it wanted to interrupt but that vector was muted.
  4. The message — when the device needs to interrupt on vector v, it writes table row v's data to table row v's address. That is the whole interrupt.

The operating system fills the table so that each address/data pair means "interrupt this particular CPU with this particular vector number". The NVMe driver then tells the NVMe controller "completion queue 3 uses vector 3". From then on, whenever the controller puts a completion into CQ3 it sends vector 3's message, and the CPU that owns CQ3 is interrupted.

Encoding example: a Table Size field of 0x020 (32) means 33 vectors (0–32). A Message Control value of 0x8020 means Enable=1, Function Mask=0, 33 vectors; 0xC020 means enabled but the whole function masked.

The table entry

Each entry is 16 bytes; entry v is at table base + 16 × v.

Entry DW31…2423…1615…87…0
DW0 (+0)Message Address [31:2]00
DW1 (+4)Message Upper Address [63:32]
DW2 (+8)Message Data
DW3 (+C)Reserved / optional extensions (version-dependent)ReservedM
  • Message Address / Upper Address — DWORD-aligned target address of the interrupt write. On x86 the low 32 bits are in the 0xFEEx_xxxx window and the upper address is 0.
  • Message Data — the 32-bit value the device writes. The device does not interpret it.
  • Vector Control, bit 0: Mask Bit — when 1, the device must not send this vector's message; it sets the vector's pending bit instead. The mask bit is set after reset, so software must clear it before a vector can fire.

Recent PCI Express Base Specification revisions allow the upper bits of Vector Control to carry a TLP Processing Hints (TPH) Steering Tag when the TPH Requester capability places its steering-tag table in the MSI-X table. Treat this as optional and version-dependent; on most NVMe drives today these bits are reserved. Confirm in the TPH Requester and MSI-X sections of the PCIe Base Specification.

The Pending Bit Array

The PBA is an array of QWORDs: bit v of the array is the pending bit for vector v. It is read-only to software. The device sets bit v when an interrupt condition for vector v occurs while that vector (or the function) is masked; it clears the bit when it sends the deferred message, or when the condition goes away (for example, the host already consumed the CQ entries) — the latter is implementation-specific in its details.

The delivery rule

Two further normative points matter in practice:

  • Do not change an unmasked entry. If software modifies an entry's address or data while the vector is unmasked, the result is undefined (the device may send a message with half-old, half-new contents). Correct software masks, rewrites, then unmasks.
  • Bus Master Enable. An MSI-X message is a memory write; if the Command register's Bus Master Enable is clear, the function cannot send it, just as it cannot DMA.

The interrupt as a TLP

The message is a posted Memory Write of one DWORD:

DW31…2423…1615…87…0
DW0Fmt 010Type 00000TC=0, attrs (RO should be 0)TD/EP/AT…Length = 1
DW1Requester ID = 0x0100TagLast BE 0000First BE 1111
DW2Address [31:2] = Message Address (e.g. 0xFEE0_1000)00
DataMessage Data (e.g. 0x0000_0041)

Fmt 010b with Type 00000b is a 3-DWORD-header Memory Write with data (MWr32), used because the x86 interrupt address is below 4 GiB. With a non-zero Message Upper Address the device uses a 4-DWORD header (MWr64). Simplified layout: real DW0/DW1 contain more fields; see TLP Header Anatomy.

Tag value in a posted write has no completion to match, so analyzers often show it but nothing depends on it. The Requester ID tells you which function (and, with SR-IOV, which virtual function) sent the interrupt — essential when several functions share a link.

What the address and data mean on x86 (platform view)

The device treats address and data as opaque. The platform gives them meaning. In the classic (non-remapped) x86 format, the address carries the destination Local APIC ID in bits 19:12 and the data carries the CPU vector in bits 7:0 plus delivery and trigger mode bits. With interrupt remapping enabled (Intel VT-d or AMD-Vi), the address instead carries a handle into an IOMMU-owned Interrupt Remapping Table, and the IOMMU validates the Requester ID before delivering. Consult the Intel Software Developer's Manual (MSI message format) and the Intel VT-d or AMD IOMMU specifications for exact bit layouts.

Queue mapping in NVMe

NVMe ties completion queues to MSI-X vectors with two fields in Create I/O Completion Queue (admin opcode 05h), Command Dword 11:

CDW1131…2423…1615…87…0
Create I/O CQInterrupt Vector (IV)ReservedIENPC
  • IV — the MSI-X table index (or MSI vector) to use for this CQ. Must be less than the number of vectors the function supports; otherwise the controller fails the command with the command-specific status Invalid Interrupt Vector (see NVMe Errors).
  • IEN (Interrupts Enabled) — 1: the controller interrupts for this CQ; 0: it never does (used for polled queues).
  • PC (Physically Contiguous) — unrelated to interrupts; included for completeness.
  • The admin CQ always uses vector 0.
  • Several CQs may share a vector. One CQ cannot use several vectors.

How many vectors to ask for is negotiated in two places: the MSI-X Table Size (what the function supports) and the NVMe Number of Queues feature (Feature Identifier 07h; what the controller will allow in queues). Linux typically requests one I/O vector per CPU plus one for admin, bounded by both, and uses managed affinity so each vector is pinned to the CPUs of its hardware queue.

The central concept on the ladder

Each basket has a line on the clipboard telling the librarian which room to walk to and what to say, plus a "do not disturb" flag.

Each MSI-X vector has a table entry with an address, a data value and a mask bit. The OS fills it; the device uses it to send a memory write that the platform turns into a CPU interrupt.

The table and PBA are MMIO structures inside a device BAR (lab system: BAR0+0x2000 and +0x3000). The controller's interrupt engine reads entry v when CQ y (with IV=v) has new entries and either emits an MWr or sets PBA bit v.

PCIe Base Specification: MSI-X capability (ID 11h), Message Control, Table/PBA Offset and BIR, table entry format, masking and pending rules. NVMe Base Specification: Create I/O CQ IV/IEN; admin CQ vector 0; Number of Queues. NVMe over PCIe Transport: interrupt modes.

Device→Host posted MWr, 1 DW, First BE 1111b, address from the entry, data from the entry, Requester ID of the function, ordered behind the CQE write.

In the capture: RC→device MWrs to BAR0+0x2000.. at init (table programming), then during I/O pairs of (16-byte MWr to CQ memory, 4-byte MWr to 0xFEEx_xxxx). A missing second half of the pair is the signature of a masked or broken vector.

For a missing interrupt: read Message Control (Enable, Function Mask), the entry's mask bit and the PBA bit. PBA=1 → device wanted to fire, host masked it. PBA=0 and unmasked → device never decided to fire (IEN, IV, coalescing, firmware). Interrupt write seen but no handler → platform (remapping table, affinity, CPU state).

Hardware view

Inside the controller the MSI-X table is usually a small SRAM or register file mapped into the BAR decoder. Host writes to the table region land there; the interrupt engine reads from it. Many designs cache entries or latch them at unmask time; the specification's rule that software must mask before changing an entry is what makes such caching safe.

  • Must participate: BAR decoder (host access to table/PBA), interrupt engine, PCIe transaction layer (to emit the MWr), configuration space (capability).
  • May participate: coalescing logic, TPH steering-tag logic, SR-IOV (each virtual function has its own MSI-X capability and table).
  • Observable: table contents and PBA (MMIO reads), capability (config reads), the MWr on the link, host interrupt counters.
  • Unobservable: the device's internal decision timing, coalescing counters, any internal copy of the entry.

Where the table lives is the device designer's choice: the lab SSD places it in BAR0 after the doorbells; other NVMe controllers use a separate BAR (some designs use the BAR pair at configuration offsets 20h/24h). Always follow Table BIR/Offset; never hard-code. The PCIe specification recommends that the table and PBA not share a naturally aligned 4 KiB page with other registers, so that hypervisors can map them separately — check the exact recommendation text in the MSI-X section.

On the host side, the root complex steers writes in the interrupt address window to the interrupt fabric rather than to DRAM. If the IOMMU performs interrupt remapping, it looks up the handle in its remapping table, checks the Requester ID, and delivers to the target CPU's local APIC. A blocked or invalid entry generates an IOMMU fault record instead.

Specification view

  • PCI Express Base Specification, Revision 6.x/7.0 — MSI-X Capability and Table Structures Normative for the capability, table, PBA, masking and pending rules.
  • NVM Express Base Specification, Revision 2.4 — Create I/O Completion Queue command; Number of Queues feature for IV, IEN, vector 0 for the admin CQ.
  • NVMe over PCIe Transport Specification, Revision 1.4 — Interrupts for how NVMe CQs use MSI-X on PCIe.

MSI-X Capability ID is 11h. Message Control holds Table Size (N−1, bits 10:0), Function Mask (bit 14) and MSI-X Enable (bit 15). Table and PBA are located by BIR (bits 2:0) and QWORD-aligned offset (bits 31:3). Each table entry is 16 bytes: Message Address, Message Upper Address, Message Data, Vector Control with Mask Bit in bit 0. Up to 2048 vectors. Create I/O Completion Queue CDW11 carries IV in bits 31:16 and IEN in bit 1; the admin CQ uses vector 0.

That a missing interrupt with PBA=1 points at host-side masking, and with PBA=0 points at the device's decision logic, is reasoning from the delivery rules, not a statement in the specification.

Table location; whether the device latches entries; when exactly a pending bit is cleared if the condition disappears while masked; how many vectors are implemented; Linux's vector-to-CPU assignment and whether vectors are shared.

Optional Vector Control extensions (TPH steering tags) depend on PCIe revision and capability presence. Linux interfaces for MSI-X (e.g. pci_alloc_irq_vectors_affinity, managed affinity, IRQ debugfs) have evolved across kernel versions.

Confirm in the specifications: the exact rule for header format choice when the Message Upper Address is zero; attribute (Relaxed Ordering, No Snoop) requirements for MSI-X writes; the complete list of reasons the NVMe controller returns Invalid Interrupt Vector; and the recommended placement of the table relative to other registers. The specifications do not say which CPU a vector should target or how many vectors an OS should request.

Never assume the table is at a fixed offset; never assume vector number equals CQ identifier; never edit an entry while it is unmasked; never interpret Message Data without knowing the platform's format and whether remapping is on.

Code / pseudocode

MSI-X capability and table decoder

Standard-library Python. With no arguments it decodes a built-in synthetic configuration-space image and table dump of the lab SSD. With a path to a config file from sysfs it decodes a real capability (root is needed to read beyond the first 64 bytes). It never touches the device's BAR.

#!/usr/bin/env python3
"""Decode the MSI-X capability from a PCI config-space image and,
optionally, MSI-X table entries from a table dump. Read-only.
Usage: msix_decode.py [path/to/config]"""
import struct, sys

def synthetic_config():
    cfg = bytearray(256)
    struct.pack_into("<HH", cfg, 0x00, 0xFFFF, 0x0000)    # placeholder IDs (synthetic)
    struct.pack_into("<H", cfg, 0x06, 0x0010)            # Status: Capabilities List
    cfg[0x34] = 0x40                                       # first capability
    cfg[0x40:0x42] = bytes([0x01, 0xB0])                   # PM cap -> next 0xB0
    # MSI-X cap at 0xB0: ID 11h, next 0, Message Control 0x8020
    struct.pack_into("<BBH", cfg, 0xB0, 0x11, 0x00, 0x8020)
    struct.pack_into("<I", cfg, 0xB4, 0x2000 | 0)        # Table: BAR0 + 0x2000
    struct.pack_into("<I", cfg, 0xB8, 0x3000 | 0)        # PBA:   BAR0 + 0x3000
    return bytes(cfg)

def synthetic_table(n=4):
    out = b""
    for v in range(n):
        addr = 0xFEE00000 | (v << 12)                      # APIC ID v (non-remapped format)
        out += struct.pack("<IIII", addr, 0, 0x40 + v, 1 if v == 3 else 0)
    return out

def find_cap(cfg, cap_id):
    if not (struct.unpack_from("<H", cfg, 0x06)[0] & 0x10):
        return None
    ptr, seen = cfg[0x34] & 0xFC, set()
    while ptr and ptr not in seen and ptr + 1 < len(cfg):
        seen.add(ptr)
        if cfg[ptr] == cap_id:
            return ptr
        ptr = cfg[ptr + 1] & 0xFC
    return None

def decode_cap(cfg):
    off = find_cap(cfg, 0x11)
    if off is None:
        print("no MSI-X capability found (or config image truncated)")
        return
    mc = struct.unpack_from("<H", cfg, off + 2)[0]
    tbl = struct.unpack_from("<I", cfg, off + 4)[0]
    pba = struct.unpack_from("<I", cfg, off + 8)[0]
    print(f"MSI-X capability at 0x{off:02X}")
    print(f"  Message Control 0x{mc:04X}: Enable={mc >> 15 & 1} "
          f"FunctionMask={mc >> 14 & 1} TableSize={(mc & 0x7FF) + 1} vectors")
    print(f"  Table: BIR {tbl & 7} (BAR at cfg 0x{0x10 + 4 * (tbl & 7):02X}) offset 0x{tbl & ~7 & 0xFFFFFFFF:X}")
    print(f"  PBA:   BIR {pba & 7} offset 0x{pba & ~7 & 0xFFFFFFFF:X}")

def decode_table(raw):
    for v in range(len(raw) // 16):
        lo, hi, data, ctl = struct.unpack_from("<IIII", raw, 16 * v)
        addr = hi << 32 | lo
        note = ""
        if hi == 0 and (lo >> 20) == 0xFEE:
            if lo & 0x10:
                note = "x86 remappable format (handle-based; decode with IOMMU spec)"
            else:
                note = f"x86 compat: dest APIC 0x{(lo >> 12) & 0xFF:02X}, CPU vector 0x{data & 0xFF:02X}"
        print(f"  entry {v:4d}: addr=0x{addr:016X} data=0x{data:08X} "
              f"mask={ctl & 1}  {note}")

if __name__ == "__main__":
    if len(sys.argv) > 1:
        with open(sys.argv[1], "rb") as f:
            decode_cap(f.read())
    else:
        print("[synthetic example for teaching]")
        decode_cap(synthetic_config())
        decode_table(synthetic_table())

Device-side delivery logic (pseudocode)

void on_cq_has_new_entries(cq_t *cq) {
    if (!cq->ien) return;                          /* polled queue */
    vec_t *v = &vectors[cq->iv];
    if (!coalesce_should_fire(v)) return;          /* threshold/timer, unless CD set */
    if (!msix.enable) { legacy_or_msi_path(cq); return; }
    if (msix.function_mask || v->entry.mask) { pba_set(cq->iv); return; }
    pcie_post_mwr(v->entry.addr, v->entry.data, /*len=*/1, /*ro=*/0);
    pba_clear(cq->iv);
}
void on_unmask(int iv) {                           /* host cleared mask or FnMask */
    if (pba_test(iv) && vector_still_has_work(iv)) {
        pcie_post_mwr(vectors[iv].entry.addr, vectors[iv].entry.data, 1, 0);
        pba_clear(iv);
    }
}

Worked example

Task. Given the lab SSD's capability bytes at 0xB0: 11 00 20 C0 00 20 00 00 00 30 00 00 and a table dump of entry 5 at BAR0+0x2050: 00 50 E0 FE 00 00 00 00 45 00 00 00 01 00 00 00, determine the device's interrupt state for vector 5.

  1. Byte 0 = 11h → MSI-X. Bytes 2–3 little-endian = 0xC020 → Enable=1 (bit 15), Function Mask=1 (bit 14), Table Size = 0x020 → 33 vectors.
  2. Bytes 4–7 = 0x0000_2000 → Table BIR 0, offset 0x2000. Bytes 8–11 = 0x0000_3000 → PBA BIR 0, offset 0x3000.
  3. Entry 5: address DW = 0xFEE0_5000, upper = 0, data = 0x45, vector control = 1 → masked.
  4. Conclusion: two masks are active — the whole function is masked and vector 5 is individually masked. No vector of this function can interrupt right now. If this is a running system (not mid-initialization), this is a bug; check the PBA: any set bit shows events waiting.
  5. Next step: work out from the driver's state machine why Function Mask was left set — for example, an error-recovery path that masked during reset and did not restore.

Common mistakes

  • Reading Table Size as the vector count (it is N−1).
  • Using the raw Table Offset DWORD without masking off the BIR bits.
  • Confusing lspci's Masked- (Function Mask) with per-vector masks.
  • Assuming the table is in BAR0. Many devices put it elsewhere; follow BIR.
  • Rewriting an entry while unmasked (torn messages).
  • Expecting one deferred interrupt per masked event: the PBA is one bit per vector.
  • Forgetting Bus Master Enable: with it clear, a device can send no MSI-X messages at all — a common side effect of error recovery.
  • Thinking NVMe's IV field is a CPU vector. It is an MSI-X table index.
  • Blaming the SSD for an IOMMU interrupt-remapping fault: the fault says the message was blocked; the cause is usually host-side table or remapping-entry state.

Senior engineer insight

  • The PBA is your witness. It is the only place the device records "I wanted to interrupt". Read it before arguing about whose bug it is.
  • Reset paths lose interrupts. Function Level Reset clears MSI-X Enable and leaves all vectors masked; Bus Master Enable is cleared too. Any recovery path that forgets to restore state yields a perfectly healthy controller that can never tell anyone it finished.
  • Virtualization changes ownership. With device passthrough the guest writes what it believes is the table; the hypervisor traps those writes and programs the real entries (and the IOMMU's posted-interrupt structures). "Guest sees no interrupts" bugs are frequently in that translation layer.
  • Vectors are a budget. 2048 per function is generous, but SR-IOV virtual functions each have their own table, and platforms have finite interrupt vectors per CPU. Large deployments run out of CPU vectors before they run out of MSI-X entries.

Lab

Lab 43 — Decode an MSI-X capability and prove a queue-to-vector binding

Objective

Decode your NVMe device's MSI-X capability from configuration space, locate the table and PBA, and connect each NVMe queue's Linux IRQ to its MSI-X index and CPU.

Skills

Capability-list walking, BIR/offset arithmetic, Linux IRQ inspection, reasoning from snapshots.

Safety

Safe lab for steps 1–3 (configuration-space reads and procfs). Step 4 (reading the table through resource0) is a Caution lab: it maps device MMIO; use a test machine, read only, and double-check offsets. Never write.

Hardware required

Linux host with an NVMe SSD.

Software required

pciutils, Python 3, msix_decode.py from this chapter.

Input

Device BDF.

Expected output

Decoded capability (Enable, Function Mask, vector count, table/PBA BIR and offset); a table: nvme0qN → IRQ → MSI-X index → CPU.

Background

The number before -edge in /proc/interrupts is the MSI-X index on most kernels; nvme0qN is the queue name; Linux's NVMe driver creates CQ N with IV N in the common case.

Step 1 — Decode the capability

sudo python3 msix_decode.py /sys/bus/pci/devices/0000:01:00.0/config
sudo lspci -vvv -s 01:00.0 | sed -n '/MSI-X/,/PBA/p'

Step 2 — Compute the table address

sudo lspci -vv -s 01:00.0 | grep -E 'Region [0-9]'
# table address = (address of the BAR named by Table BIR) + Table Offset

Step 3 — Map queues to IRQs and CPUs

grep nvme0q /proc/interrupts | awk '{print $1, $(NF-2), $(NF-1), $NF}'

Step 4 (caution, optional) — Snapshot the PBA

import mmap, os, struct, sys
path, pba_off = sys.argv[1], int(sys.argv[2], 0)   # resourceN file, PBA offset
fd = os.open(path, os.O_RDONLY | os.O_SYNC)
m = mmap.mmap(fd, pba_off + 8, mmap.MAP_SHARED, mmap.PROT_READ)
print(hex(struct.unpack_from("<Q", m, pba_off)[0]))

Observation

Record Function Mask, vector count, and which vectors are allocated by Linux compared with the device's Table Size.

Questions

  1. How many table entries are unused by Linux, and why?
  2. Is the PBA normally zero on an idle running system? Why?
  3. What would Function Mask=1 on a running system tell you?

Challenge

Using a protocol analyzer if you have one (or the synthetic trace in this chapter if not), confirm that the interrupt write for a queue carries exactly the address/data of its table entry.

Hint

Linux allocates at most one vector per CPU plus admin, bounded by the Number of Queues the controller grants.

Solution

1. Unused entries = Table Size + 1 − allocated vectors. Linux allocates min(CPUs, controller queue limit) I/O vectors + 1 admin; a 33-vector device on an 8-CPU host leaves 24 unused (they remain masked).

2. Yes: unmasked vectors fire immediately so pending bits are clear; unused vectors never get events. A non-zero PBA on a running system means a vector is masked while the device has work for it.

3. No vector of the function can interrupt. On a running system that is a stuck recovery or initialization path; expect timeouts.

What a senior engineer notices

Whether the table shares a 4 KiB page with doorbells (affects passthrough), whether the address format is remappable (interrupt remapping on), and whether the vector count limits queue count on large-core hosts.

Failure variants

  • Non-root read of config returns 64 bytes: the decoder reports no capability — run as root.
  • Device in D3hot: MMIO reads return all ones (0xFFFF_FFFF), which is not a valid PBA reading.

Extension

Compare a virtual function's MSI-X capability (if your device supports SR-IOV) with the physical function's.

Exercises

  1. Message Control reads 0x07FF. Decode it and comment.
  2. Table Offset/BIR reads 0x0000_4004. Where is the table?
  3. Compute the byte address of vector 17's Vector Control on the lab SSD.
  4. Write the host sequence to safely retarget vector 4 to a different CPU.
  5. A Create I/O CQ with IV=40 completes with an error on a device whose Table Size field is 31. Explain.
Model answers

1. Enable=0, Function Mask=0, 2048 vectors supported; MSI-X not in use.

2. BIR=4 → the BAR at configuration offset 20h; offset 0x4000 (low 3 bits are BIR).

3. 0xFE60_2000 + 17×16 + 12 = 0xFE60_211C.

4. Set Vector Control mask=1; write Message Address/Upper/Data; clear mask; (the device sends any pending message on unmask).

5. Table Size 31 → 32 vectors (0–31); IV=40 is out of range, so the controller returns Invalid Interrupt Vector.

Quiz

  1. The MSI-X Capability ID is

    • 01h
    • 05h
    • 11h
    • 10h
    Answer and reasoning

    05h is MSI, 01h Power Management, 10h PCI Express. MSI-X is 11h.

  2. Table Size field = 0x00F. How many vectors?

    • 15
    • 16
    • 14
    • 32
    Answer and reasoning

    N−1 encoding: 15 + 1 = 16.

  3. What does the device do when an event occurs for a masked vector?

    • Drops it
    • Sets the vector's pending bit in the PBA
    • Sends the message anyway
    • Falls back to INTx
    Answer and reasoning

    Masked → pending bit; on unmask with pending set the message is sent.

  4. Which field binds an NVMe completion queue to an MSI-X vector?

    • IV in Create I/O Completion Queue
    • CQID in Create I/O Submission Queue
    • INTMS
    • The Number of Queues feature
    Answer and reasoning

    IV (CDW11 bits 31:16) with IEN (bit 1).

  5. Size of one MSI-X table entry?

    • 4 bytes
    • 8 bytes
    • 16 bytes
    • 64 bytes
    Answer and reasoning

    Address, upper address, data, vector control: four DWORDs.

  6. In a trace, how is an MSI-X interrupt distinguished from a data write?

    • Its TLP type is Msg
    • It has a completion
    • It uses TC7
    • Only by its target address (the platform's interrupt window) and 1-DW length
    Answer and reasoning

    On the wire it is an ordinary posted MWr; the address identifies it.

  7. Why must software mask a vector before rewriting its entry?

    Model answer

    The device may read the entry at any time; changing it unmasked can produce a message with a mix of old and new fields. The specification leaves the result undefined.

  8. After Function Level Reset, what is the state of MSI-X?

    Model answer

    MSI-X Enable cleared, per-vector mask bits set (reset default), Bus Master Enable cleared. Software must re-enable and reprogram before interrupts can be delivered.

  9. What does a set PBA bit with an unmasked vector suggest?

    Model answer

    Either the snapshot raced an unmask (benign), or the device failed to send the deferred message on unmask (device bug). Re-read; if it stays set while unmasked, suspect the device.

Interview questions

  1. Beginner: What is in an MSI-X table entry?

    Model answer

    Message Address, Message Upper Address, Message Data and Vector Control (mask bit).

  2. Beginner: Where is the MSI-X table?

    Model answer

    In a memory BAR of the function, identified by Table BIR and Table Offset in the capability.

  3. Intermediate: How does Linux end up with one NVMe interrupt per CPU?

    Model answer

    The driver requests vectors with managed affinity (one per hardware queue), the PCI core programs each entry to target that queue's CPUs, and the driver creates CQ N with IV N.

  4. Advanced: Explain the PBA and when you'd read it.

    Model answer

    One bit per vector, set when an interrupt was needed while masked. Read it when interrupts are missing to decide between "host masked it" and "device never decided to fire".

  5. Advanced: What can go wrong with interrupts in a VM using device passthrough?

    Model answer

    Guest table writes must be trapped and translated; IOMMU interrupt remapping / posted-interrupt descriptors must be updated; mistakes yield lost interrupts or remapping faults. The table sharing a page with other registers complicates trapping.

  6. Senior: A vendor claims their SSD "sends the interrupt" but the host never sees it. Design the experiment that settles it.

    Model answer

    Capture on the link next to the device with a trigger on CQE writes to the queue in question. If an MWr with the entry's address/data follows, the device is right; then check the root port's AER for UR, IOMMU faults, and host vector state. If no MWr follows, read the entry mask, Function Mask and PBA at that moment; PBA=1 → host masked; PBA=0 and unmasked → device.

Chapter summary

MSI-X consists of a configuration-space capability (ID 11h: Table Size N−1, Function Mask, Enable; Table and PBA BIR/offset), a table of 16-byte entries in a BAR (address, upper address, data, vector control mask bit), and a Pending Bit Array. The device sends entry v's data to entry v's address as a posted 1-DW Memory Write; when masked it sets the pending bit and sends on unmask. NVMe binds each I/O CQ to a vector with IV and IEN at Create I/O CQ; the admin CQ uses vector 0. In a trace, the interrupt is the small MWr to the platform's interrupt window right after the CQE. In Linux, lspci shows capability state, /proc/interrupts shows deliveries per CPU, and IRQ affinity files show targets.

Do not move on until you can:

  • decode an MSI-X capability from raw bytes
  • compute the address of any table entry and PBA bit from BAR, BIR and offset
  • decode a table entry, including the x86 non-remapped address/data meaning
  • state the masking, pending and "mask before modify" rules
  • explain IV/IEN and admin vector 0
  • identify the interrupt TLP in a trace and verify it against the table
  • separate host-masked, device-never-fired and platform-blocked interrupts with evidence
