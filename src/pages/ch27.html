I/O queues carry the data commands — Read, Write, Flush and the rest. This chapter shows exactly how a driver creates them with two Admin commands, why the Completion Queue must exist before the Submission Queue that points at it, how interrupt vectors and Command Identifiers tie completions back to the right CPU and the right request, and what the queues look like in host memory, byte by byte.

Why this chapter exists

The Admin queue (Chapter 26) is the control plane. Everything that makes an NVM Express (NVMe) SSD fast happens on the I/O queues: many of them, deep, one per CPU core, each with its own interrupt. How they are created and configured decides whether a system gets the device's full performance, whether interrupts land on the right core, and whether a reset or hot-unplug tears them down cleanly.

I/O queue creation is also where several classic failures live: a Create I/O Submission Queue that names a Completion Queue that does not exist yet, a queue size written as a count instead of 0's based, an interrupt vector beyond the MSI-X table, or a Delete I/O Completion Queue sent while Submission Queues still point at it. Each produces a specific status code you should be able to predict.

Learning objectives

  • Encode and decode Create I/O Completion Queue (opcode 05h) and Create I/O Submission Queue (opcode 01h), field by field.
  • Explain the mandatory creation order (CQ before SQ) and deletion order (SQ before CQ), and the errors that enforce them.
  • Associate CQs with MSI-X (Message Signaled Interrupts eXtended) vectors, decide when to share vectors, and explain polled queues with interrupts disabled.
  • Choose queue depth with reference to CAP.MQES, Little's Law and the device's internal parallelism.
  • Explain Command Identifiers (CIDs): who assigns them, their uniqueness rule, and how Linux uses them to find the request.
  • Draw I/O queue memory — contiguous and Physical Region Page (PRP) list based — and compute the address of any slot.
  • Recognise queue creation, normal I/O and creation failures in a synthetic PCI Express (PCIe) trace.

The story

The school has finally set up the library properly. Now every class gets its own question tray and its own answer tray. But there's a rule: before a class can have a question tray, its answer tray must already be on the table — otherwise the librarian would have nowhere to put the answers! And each answer tray comes with a little bell wired to that class's room, so when an answer arrives, only that class hears it.

Every question card has a number written by the class, like "card 17". The answer card says "answer to card 17", so the class knows which question it belongs to, even if answers come back in a different order.

A restaurant with one manager's desk (the Admin queue) opens new dining sections as customers arrive. To open a section, the manager first installs the pass where finished plates come out (the CQ) and wires a buzzer to the section's waiter (the interrupt vector). Only then does she open the order rail for that section (the SQ), telling the kitchen "orders from this rail go out at that pass". Several order rails may share one pass. Closing up runs in reverse: close the rails first, then remove the pass. Every ticket carries a ticket number (CID) so plates can be matched to tables, whatever order the kitchen finishes them in.

What it hides. The kitchen (controller) does not watch the rail; it is told by a doorbell when tickets are added. Rails and passes are memory in the host — the restaurant owner's building — not the kitchen's. Ticket numbers are chosen by the waiters (host), not the kitchen, and must be unique only per rail, not across the whole restaurant.

Where it misleads. A real restaurant can open a section without a buzzer; in NVMe that is also possible (interrupts disabled, the host polls), so the buzzer is optional. A restaurant may move a rail to a different pass while open; an NVMe SQ's CQ is fixed at creation and changing it means deleting and recreating the SQ.

Beginner explanation

An I/O queue pair is created by sending two commands on the Admin queue:

  1. Create I/O Completion Queue (opcode 05h). It tells the controller: "here is a block of host memory for a new CQ with identifier n and this many entries; when you post completions into it, raise interrupt vector v".
  2. Create I/O Submission Queue (opcode 01h). It tells the controller: "here is a block of host memory for a new SQ with identifier n and this many entries; post its completions into CQ c; give it priority class p".

The SQ names its CQ, so the CQ must already exist. That is the whole reason for the order. Deleting is the mirror image: Delete I/O Submission Queue (00h) for every SQ that uses a CQ, then Delete I/O Completion Queue (04h).

Before creating any I/O queues, the driver asks how many it may have (Set Features — Number of Queues), and it sets up MSI-X vectors so each CQ can have its own interrupt. Then it typically creates one queue pair per CPU core, up to the number granted.

What a queue looks like in memory

Using the course's reference lab system (synthetic): I/O SQ1 has 1024 entries of 64 bytes (64 KiB) at I/O virtual address 0x1_2340_0000, and CQ1 has 1024 entries of 16 bytes (16 KiB) at 0x1_2341_0000.

Creation and deletion order

When an SQ is deleted, commands previously submitted to it that have not completed are either completed normally or aborted; aborted ones complete with the generic status Command Aborted due to SQ Deletion. Their CQEs go to the SQ's CQ — another reason the CQ must outlive the SQ. Many drivers wait for outstanding I/O to drain before deleting queues, so this path is rarely exercised outside validation.

A controller reset (CC.EN = 0) deletes every I/O queue at once, with no Delete commands. That is how most drivers handle shutdown after an error: rather than deleting queues one by one on a controller that may be misbehaving, they reset and recreate everything.

Interrupt vectors

Each I/O CQ is bound at creation to one interrupt vector (IV). On PCIe, with MSI-X, the vector number is an index into the device's MSI-X table, where the operating system has written a message address and data for each entry. When the controller posts CQEs into a CQ with IEN = 1, it signals the vector by sending a posted Memory Write of the entry's data to the entry's address (subject to interrupt coalescing and masking).

  • One vector per CQ is the common choice: completions for CPU n's queue interrupt CPU n.
  • Several CQs may share a vector: legal; the interrupt handler must then check every CQ on that vector.
  • Vector 0 belongs to the Admin CQ; an I/O CQ may also use vector 0 (for example when only one vector is available), but then Admin and I/O completions share an interrupt.
  • IEN = 0 creates a polled queue. The host must poll the CQ's phase tags. Linux uses this for its "poll queues", which serve io_uring and similar polled I/O with no interrupt overhead.

How many MSI-X vectors a device exposes is in its MSI-X capability (Table Size); how many the OS grants depends on platform limits; which CPU each vector targets is OS policy (IRQ affinity). Interrupt coalescing (Feature 08h) and per-vector coalescing control (Feature 09h) change when interrupts fire. None of these is fixed by the queue-creation command.

Queue depth: how deep is deep enough?

Queue size bounds how many commands can be outstanding on one SQ. How many you need follows from Little's Law:

L = λ × W
L
average number of commands outstanding (the queue depth actually in use)
λ
throughput, in commands per second (IOPS, I/O operations per second)
W
average time a command spends outstanding (from doorbell to completion consumed), in seconds

Worked: to sustain 1,000,000 IOPS of 4 KiB random reads with an average latency of 80 µs, you need on average 1,000,000 × 0.000080 = 80 commands in flight — across all queues. Spread over 16 queues, that is 5 per queue; a single-threaded application on one queue needs 80 in that one queue. Queue size limits L per queue; the device's internal parallelism limits how far raising L raises λ before W grows instead.

Beyond the device's saturation point, extra depth only increases latency: λ stays flat, so W = L / λ rises linearly with L. Deep queues are for throughput; shallow queues keep latency predictable. That trade-off is a host policy, not a specification rule.

Command Identifiers

The Command Identifier is a 16-bit value in SQE Dword 0, bits 31:16. The rules:

  • The host chooses it.
  • The combination of SQ Identifier and CID must be unique among commands outstanding in the controller: two outstanding commands on the same SQ must not share a CID; the same CID on two different SQs is fine.
  • The controller copies the CID into the CQE (Dword 3, bits 15:00) and the SQ Identifier into Dword 2, so the host can find the command, whatever order completions arrive in.
  • The value FFFFh has a special meaning in some places (for example the Error Information log uses it to mean "not associated with a specific command"); check the specification before using it as a normal CID Check.

Linux derives the CID from the block layer's request tag (the request's index in the hardware queue's tag set), so finding the request from a CQE is an array lookup. Recent kernels also place a small generation counter in the upper CID bits to detect completions for a request that has already been completed or reused — a defence against buggy devices that post duplicate or stale CQEs Version-dependent.

Reusing a CID while the previous command with that CID is still outstanding on the same SQ is a host bug with confusing symptoms: the controller may complete one command twice from the host's point of view, or the host may complete the wrong request. In a trace it shows up as two SQE fetches with the same CID on the same SQ with no CQE for that CID between them.

Queue pairs per CPU and how Linux maps them

Linux can split I/O queues into types: default queues for normal I/O, optional read queues (so reads and writes use separate queues, via the write_queues parameter), and poll queues (created with IEN = 0). The kernel log reports the split at probe time. All of this is driver policy layered on the same two create commands.

Non-contiguous (PRP-list) queues

If CAP.CQR = 0, the controller accepts PC = 0, and PRP Entry 1 points to a PRP list: a page of 8-byte entries, each the address of one memory page of the queue, in order.

This saves the host from finding 64 KiB of contiguous memory, but costs the controller an extra lookup (and possibly an extra DMA read of the PRP list) for queue accesses. Most current controllers set CQR = 1; with an IOMMU, the host can give the device a contiguous I/O virtual range anyway.

The ladder for the central concept: creating an I/O queue pair

Put the answer tray (with its bell) on the table first, then the question tray that says "answers go in that tray".

Create I/O CQ (05h) with QID, size, base, interrupt vector; then Create I/O SQ (01h) with QID, size, base and the CQID. Delete in the opposite order.

The controller fills an entry in its queue-context table for each queue: base or PRP list, size, head/tail, phase (CQ), vector (CQ), target CQ and priority (SQ). Doorbell registers for that QID become live.

NVMe over PCIe Transport 1.4 for PRP-based queue memory and MSI-X.

Each create is an Admin command: host MWr to SQ0TDBL; device MRd/CplD to fetch the 64-byte SQE; device MWr of a 16-byte CQE to the Admin CQ; MSI-X MWr for vector 0; host MWr to CQ0HDBL. No queue memory is touched until I/O starts.

Decode the fetched SQE payload: opcode 05h, CDW10 = 0x03FF_0001, CDW11 = 0x0001_0003 → CQ1, 1024 entries, vector 1, IEN, PC. Then opcode 01h, CDW11 = 0x0001_0001 → SQ1 into CQ1. The first I/O doorbell at BAR0+0x1008 follows.

"Create I/O SQ failed with Completion Queue Invalid": was the CQ created first, did its create succeed, does CQID match? "No interrupts on queue 3": what IV and IEN did Create I/O CQ carry; is that MSI-X entry masked; where does its address point?

The sixteen questions: the I/O queue pair

1. What is it?
An SQ and CQ with identifiers 1 or above that carry I/O command set commands.
2. Why was it created?
To give each CPU (or workload) its own lock-free path to the device, separate from management traffic.
3. What problem does it solve?
Scalability: many cores issuing millions of I/Os per second without contending on one queue, with interrupts delivered to the core that submitted.
4. What existed before it?
AHCI's single 32-entry command list per port; SCSI adapters with one or few hardware queues.
5. Why is the current design better?
Up to 65,535 queues, each up to 65,536 entries, created and sized at runtime, each with its own interrupt.
6. Who creates it?
The host driver via Create I/O CQ and Create I/O SQ on the Admin queue.
7. Who consumes it?
The controller consumes the SQ; the host consumes the CQ.
8. Where does it live?
Host memory (contiguous or PRP list), with doorbells in BAR0 at the queue's stride position.
9. What memory/registers are involved?
Queue memory, PRP list (if any), SQyTDBL/CQyHDBL, CAP.MQES/CQR/DSTRD, CC.IOSQES/IOCQES, the MSI-X table entry.
10. What happens before it?
Admin queue bring-up, Identify, Number of Queues, MSI-X configuration.
11. What happens after it?
The block layer starts submitting I/O; the first SQ tail doorbell for that queue.
12. What happens if it is wrong?
Create fails with a predictable status; or worse, it succeeds with a wrong base or vector and fails silently at first use.
13. What does the protocol analyzer show?
The Admin command exchange (with decodable SQE payloads), then doorbells at the new queue's offsets, fetches from the new SQ base, and CQE posts to the new CQ base.
14. What does Linux show?
nvme0q1…nvme0qN in /proc/interrupts; blk-mq contexts; the queue split in the kernel log; module parameters.
15. What would a validation engineer test?
Each error status; maximum queue count and size; many-to-one mapping; IEN = 0; vector sharing; deletion with outstanding I/O; create/delete churn; PRP-list queues if CQR = 0.
16. What would a senior engineer suspect when it fails?
Creation order, 0's based size, granted count versus created count, vector numbering versus MSI-X table, queue memory mapping in the IOMMU, CID reuse, CQ sizing for shared mapping.

Hardware view

A controller supports a fixed maximum number of queue contexts — the source of the limit it reports through Number of Queues. Each context is a few dozen bytes of state. When a create command arrives, firmware or hardware validates the fields, allocates a context, and records:

  • base address (or PRP list address, possibly cached),
  • size, and initial indices (SQ head 0; CQ tail 0, phase 1),
  • for a CQ: the vector and interrupt enable, plus coalescing state;
  • for an SQ: the target CQ and priority class, linked into the arbiter's list.

The doorbell decoder must map a write at BAR0 + 1000h + (2y × stride) to SQ y's tail, and + ((2y + 1) × stride) to CQ y's head. For a queue that does not exist, a doorbell write is an error the controller may report (see Chapter 28).

On the host side, NUMA (Non-Uniform Memory Access) placement matters: a queue pair used by CPU 12 should live in memory close to CPU 12's socket, and its MSI-X vector should target CPU 12, so the device's DMA and the CPU's accesses stay local. Linux allocates queue memory on the device's NUMA node or the CPU's — another implementation choice that shows up as latency differences between queues.

Specification view

  • NVM Express Base Specification, Revision 2.4 — Admin Command Set: Create I/O Completion Queue, Create I/O Submission Queue, Delete I/O Completion Queue, Delete I/O Submission Queue
  • NVM Express Base Specification, Revision 2.4 — Set Features: Number of Queues, Interrupt Coalescing, Interrupt Vector Configuration
  • NVM Express over PCIe Transport Specification, Revision 1.4 — queue memory (PRP-described queues) and interrupts
  • Opcodes: Delete I/O SQ 00h, Create I/O SQ 01h, Delete I/O CQ 04h, Create I/O CQ 05h.
  • CDW10: QSIZE (bits 31:16, 0's based) and QID (bits 15:00) for both create commands.
  • Create I/O CQ CDW11: IV (31:16), IEN (bit 1), PC (bit 0). Create I/O SQ CDW11: CQID (31:16), QPRIO (02:01), PC (bit 0).
  • A CQ must exist before an SQ that references it; a CQ may not be deleted while SQs reference it.
  • Multiple SQs may map to the same CQ.
  • The CID is assigned by the host and returned in the CQE together with the SQ Identifier.
  • A create command cannot detect an unmapped queue base; failures appear at first use.
  • Queue priority has no effect unless weighted round robin was selected in CC.AMS.
  • Memory per queue pair = entries × (64 + 16) bytes for 64-byte SQEs and 16-byte CQEs: 80 KiB for a 1024-entry pair.
  • Maximum queues and vectors; behaviour on unused/reserved field bits; whether PRP-list queues are supported (CQR).
  • Host policies: queue count, depth, CPU mapping, read/write/poll split, NUMA placement, CID encoding.
  • Whether outstanding commands are completed or aborted on Delete I/O SQ (either is permitted).

NVM Sets (NVMe 1.4) added the NVM Set Identifier in Create I/O SQ CDW12. Later revisions have continued to add queue-related optional capabilities; the 2.4 release's rate-limiting controls (reported as allocating PCIe bandwidth and IOPS among controllers) live above the queue layer and are configured through Admin mechanisms whose identifiers must be checked in the 2.4 documents.

  • The specification does not require one queue per CPU, nor any particular depth.
  • It does not define how a controller distributes back-end resources among queues.
  • It does not say the host must zero a new CQ in so many words in every revision; check the phase-tag initialisation wording for yours. Zeroing is universal practice.
  • Check in the specification: the numeric status codes for the queue errors, and the exact conditions for each.
  • Never create an SQ before its CQ.
  • Never assume the controller granted as many queues as you requested.
  • Never reuse a CID while its command is outstanding on that SQ.
  • Never assume QPRIO does anything unless WRR is enabled.

Protocol view

Queue creation is invisible as a "queue" event on the link; it is ordinary Admin command traffic. The queue's existence becomes visible only when it is used:

A host that sees the interrupt and then finds no new CQE has a problem elsewhere (wrong CQ checked, wrong phase expected, or a cache coherency issue on non-coherent platforms).

Code / pseudocode

int create_io_queue_pair(struct ctrl *c, uint16_t qid, uint16_t entries, uint16_t vector) {
    struct qp *q = &c->qp[qid];
    q->size = entries;
    q->cq = dma_alloc_zeroed(entries * 16, &q->cq_dma);    /* zero: phase tags = 0 */
    q->sq = dma_alloc(entries * 64, &q->sq_dma);

    struct sqe cmd = {0};
    cmd.opcode = 0x05;                                       /* Create I/O CQ */
    cmd.prp1   = q->cq_dma;
    cmd.cdw10  = ((uint32_t)(entries - 1) << 16) | qid;      /* 0's based QSIZE */
    cmd.cdw11  = ((uint32_t)vector << 16) | (1u << 1) | 1u;  /* IV, IEN, PC */
    if (admin_sync(c, &cmd)) goto free;                      /* WAIT for completion */

    memset(&cmd, 0, sizeof cmd);
    cmd.opcode = 0x01;                                       /* Create I/O SQ */
    cmd.prp1   = q->sq_dma;
    cmd.cdw10  = ((uint32_t)(entries - 1) << 16) | qid;
    cmd.cdw11  = ((uint32_t)qid << 16) | (0u << 1) | 1u;     /* CQID = qid, QPRIO urgent, PC */
    if (admin_sync(c, &cmd)) goto delete_cq;

    q->sq_db = c->bar + 0x1000 + (2 * qid)     * c->db_stride;
    q->cq_db = c->bar + 0x1000 + (2 * qid + 1) * c->db_stride;
    q->sq_tail = q->cq_head = 0; q->phase = 1;
    return 0;

delete_cq:
    memset(&cmd, 0, sizeof cmd);
    cmd.opcode = 0x04; cmd.cdw10 = qid;                      /* Delete I/O CQ */
    admin_sync(c, &cmd);
free:
    dma_free(q->sq); dma_free(q->cq);
    return -EIO;
}

Note the error path: if the SQ create fails, the CQ already exists and must be deleted to avoid leaking a queue context in the controller.

Worked example

Problem. A 24-CPU host, Lab SSD with CAP.MQES = 03FFh, CAP.CQR = 1, 33 MSI-X vectors. The driver requests 24 SQs/CQs and is granted NSQA = 0Fh, NCQA = 0Fh. It wants 2 poll queues and the rest interrupt-driven, depth 1024. Plan the queues, give the CDW10/CDW11 for the first interrupt queue and first poll queue, compute the memory needed, and give the doorbell addresses of queue 16.

Grant. 16 SQs and 16 CQs. Plan: queues 1–14 interrupt-driven (vectors 1–14), queues 15–16 polled (IEN = 0). The 24 CPUs share the 14 interrupt queues (some queues serve two CPUs).

Queue 1 (interrupt). Create I/O CQ: CDW10 = (1023 << 16) | 1 = 0x03FF_0001; CDW11 = (1 << 16) | IEN | PC = 0x0001_0003. Create I/O SQ: CDW10 = 0x03FF_0001; CDW11 = (1 << 16) | PC = 0x0001_0001.

Queue 15 (poll). Create I/O CQ: CDW10 = 0x03FF_000F; CDW11 = (0 << 16) | PC = 0x0000_0001 (IV is ignored when IEN = 0; 0 is a safe value). Create I/O SQ: CDW10 = 0x03FF_000F; CDW11 = 0x000F_0001.

Memory. 16 pairs × 1024 × (64 + 16) bytes = 16 × 80 KiB = 1.25 MiB, each SQ needing 64 KiB contiguous (CQR = 1) and each CQ 16 KiB contiguous.

Doorbells for queue 16 (DSTRD = 0, stride 4): SQ16TDBL = 1000h + 2 × 16 × 4 = 1000h + 80h = 1080h → 0xFE60_1080. CQ16HDBL = 1000h + 33 × 4 = 1084h → 0xFE60_1084. The BAR is 16 KiB, so doorbells up to 3FFCh are within it; 16 pairs need only up to 1084h.

Debugging connection

Queue-creation problems split into two classes:

  • Loud failures — the create command completes with an error. Read the CQE's status (Status Code Type and Status Code) and map it to the cause table above. The fetched SQE payload in the trace shows exactly what the driver asked for.
  • Silent failures — the create succeeds, but first use fails: no fetch after the first doorbell (wrong doorbell offset), fetch completes with Unsupported Request (base not mapped), CQEs posted to an unexpected address (base or size mismatch), or no interrupt (IV/IEN, MSI-X masking). These need the first-use trace: doorbell → fetch → CQE → interrupt for that QID.

When only some queues misbehave, list the per-queue facts in a table — QID, base, size, IV, IEN, CPU affinity — and look for the column where the bad queues differ. "Only queues above 8 fail" often means a vector or doorbell-stride arithmetic error that only shows past a boundary.

Senior engineer insight

  • Create commands are cheap to validate; first use is what proves a queue. A queue isn't "up" until you've seen a fetch from its SQ, a CQE in its CQ and an interrupt on its vector.
  • Queue count is a resource negotiation, not a request. Robust drivers handle any grant from 1 to the requested number, and handle a create that fails mid-way by running with fewer queues.
  • CIDs are the join key across layers. In a trace, the CID ties the SQE fetch (in a PCIe completion payload) to the CQE (in a device write payload). Without decoding payloads you cannot correlate NVMe commands — see Command vs Packet vs Completion.
  • Polling and interrupts are per CQ. Mixing them is normal and useful: latency-critical polled queues alongside interrupt-driven bulk queues.
  • Depth is not free. Each extra outstanding command costs host memory for buffers and costs latency once the device is saturated. Use Little's Law to pick depth from targets, not from the maximum.

Step 1 — Run it

#!/usr/bin/env python3
"""Plan, encode and check I/O queue creation (synthetic teaching model).

Builds Create I/O Completion Queue (05h) and Create I/O Submission Queue
(01h) SQEs, checks them against CAP and the Number of Queues grant, and
prints the creation and deletion order.
"""
import struct

CAP_MQES = 0x03FF        # 1024 entries (0's based)
CAP_CQR = 1              # contiguous queues required
NSQA, NCQA = 0x000F, 0x000F   # Number of Queues grant: 16 SQs, 16 CQs (0's based)
MSIX_VECTORS = 33        # vector 0 admin, 1..32 I/O

def sqe(opcode, cid, prp1, cdw10, cdw11, cdw12=0):
    dw = [opcode | (cid << 16), 0, 0, 0, 0, 0,
          prp1 & 0xFFFFFFFF, prp1 >> 32, 0, 0,
          cdw10, cdw11, cdw12, 0, 0, 0]
    return struct.pack("<16I", *dw)

def create_cq(cid, qid, entries, base, vector, ien=True):
    cdw10 = ((entries - 1) << 16) | qid          # QSIZE is 0's based
    cdw11 = (vector << 16) | (int(ien) << 1) | 1  # IV, IEN, PC=1
    return sqe(0x05, cid, base, cdw10, cdw11)

def create_sq(cid, qid, entries, base, cqid, qprio=0):
    cdw10 = ((entries - 1) << 16) | qid
    cdw11 = (cqid << 16) | (qprio << 1) | 1       # CQID, QPRIO, PC=1
    return sqe(0x01, cid, base, cdw10, cdw11)

def check(cmd, existing_cqs):
    dw = struct.unpack("<16I", cmd)
    op, qid, qsize = dw[0] & 0xFF, dw[10] & 0xFFFF, (dw[10] >> 16) + 1
    pc = dw[11] & 1
    errs = []
    if qid == 0:
        errs.append("Invalid Queue Identifier (0 is the Admin queue)")
    limit = (NCQA if op == 0x05 else NSQA) + 1
    if qid > limit:
        errs.append(f"Invalid Queue Identifier (only {limit} granted)")
    if qsize < 2 or qsize > CAP_MQES + 1:
        errs.append(f"Invalid Queue Size ({qsize} entries; max {CAP_MQES + 1})")
    if CAP_CQR and not pc:
        errs.append("PC=0 but CAP.CQR=1 (non-contiguous not supported)")
    if (dw[6] & 0xFFF) != 0:
        errs.append("queue base not 4 KiB page aligned")
    if op == 0x05:
        iv = dw[11] >> 16
        if iv >= MSIX_VECTORS:
            errs.append(f"Invalid Interrupt Vector ({iv})")
    if op == 0x01:
        cqid = dw[11] >> 16
        if cqid not in existing_cqs:
            errs.append(f"Completion Queue Invalid (CQ {cqid} does not exist)")
    return errs

if __name__ == "__main__":
    sq_base, cq_base = 0x1_2340_0000, 0x1_2341_0000
    plan = []
    cid = 0x0010
    for q in (1, 2):
        plan.append(("CQ", q, create_cq(cid, q, 1024, cq_base + (q - 1) * 0x2_0000, vector=q)))
        cid += 1
    for q in (1, 2):
        plan.append(("SQ", q, create_sq(cid, q, 1024, sq_base + (q - 1) * 0x2_0000, cqid=q)))
        cid += 1
    # deliberate mistakes
    plan.append(("SQ", 3, create_sq(cid, 3, 1024, 0x1_2360_0000, cqid=3)))
    plan.append(("CQ", 17, create_cq(cid + 1, 17, 2048, 0x1_2370_0800, vector=40)))
    cqs = set()
    for kind, q, cmd in plan:
        dw = struct.unpack("<16I", cmd)
        errs = check(cmd, cqs)
        status = "OK" if not errs else "; ".join(errs)
        print(f"{kind}{q:<3} CDW0={dw[0]:08X} PRP1={dw[7]:08X}_{dw[6]:08X} "
              f"CDW10={dw[10]:08X} CDW11={dw[11]:08X}  -> {status}")
        if kind == "CQ" and not errs:
            cqs.add(q)
    print("Creation order : CQ1, CQ2, then SQ1, SQ2")
    print("Deletion order : SQ1, SQ2 (Delete I/O SQ 00h), then CQ1, CQ2 (Delete I/O CQ 04h)")
    for n in (1024, 256, 2):
        print(f"{n:5} entries: SQ {n*64:>6} bytes, CQ {n*16:>6} bytes, holds {n-1} commands")

Hints

Keep a dictionary sq_to_cq; a CQ is deletable only when no value in it equals that CQ's ID. For IEN, test bit 1 of CDW11.

Solution

Q1. IV = 0001h (vector 1), bits 15:02 reserved = 0, IEN (bit 1) = 1, PC (bit 0) = 1.

Q2. Its CQID = 3, and CQ 3 was never created. Status: Completion Queue Invalid. Fix: create CQ 3 first, or point SQ3 at CQ 1 or 2 (many-to-one is legal).

Q3. It has four problems: QID 17 beyond the grant, 2048 entries beyond MQES, a base with offset 0x800, and vector 40 beyond the table. The specification does not define a priority among multiple errors, so which status a controller returns is implementation-dependent; many check fields in the order they appear (QID first), but don't rely on it. Fix: QID ≤ 16, 1024 entries, base 0x1_2370_0000, vector ≤ 32.

Q4. 16 × 1024 × 80 B = 1,310,720 bytes = 1.25 MiB.

Challenge sketch. On successful SQ create: sq_to_cq[qid] = cqid. On Delete SQ: remove it. On Delete CQ: if cqid in sq_to_cq.values() → "Invalid Queue Deletion". For IEN: if op == 0x05 and (dw[11] >> 1) & 1: check vector.

What a senior engineer notices

The checker treats IV ≥ 33 as invalid because the device has 33 vectors. In reality the limit is what the OS enabled — if only 9 vectors were allocated, IV 12 passes the controller's check (the table has 33 entries) but its MSI-X entry is masked or unprogrammed, and interrupts silently never arrive. The controller cannot know what the OS configured.

Failure variants

  • QSIZE = 0: a 1-entry queue is invalid (minimum 2 entries).
  • CQID = 0 in Create I/O SQ: I/O SQs may not complete into the Admin CQ.
  • PC = 0 with CQR = 1: Invalid Field in Command.

Exercises

  1. Encode CDW10/CDW11 for Create I/O CQ QID 5, 256 entries, vector 5, interrupts enabled, contiguous.
    Answer

    CDW10 = (255 << 16) | 5 = 0x00FF_0005. CDW11 = (5 << 16) | 2 | 1 = 0x0005_0003.

  2. Decode Create I/O SQ CDW10 = 0x007F_0003, CDW11 = 0x0001_0005.
    Answer

    QID 3, 128 entries; CQID 1; QPRIO = (5 >> 1) & 3 = 2 = 10b Medium; PC = 1. SQ3 shares CQ1.

  3. Using Little's Law, how many commands must be outstanding to sustain 400,000 IOPS at 150 µs average latency?
    Answer

    L = 400,000 × 0.000150 = 60 commands in flight on average.

  4. Why must a driver wait for the Create I/O CQ completion before submitting Create I/O SQ, even if it places them in the right order in the Admin SQ?
    Answer

    Because the specification does not require the controller to process Admin commands in submission order; the SQ create could be processed before the CQ create and fail with Completion Queue Invalid.

  5. What happens to commands outstanding on an SQ when it is deleted?
    Answer

    They are completed normally or aborted with status Command Aborted due to SQ Deletion; the CQEs go to the SQ's CQ before the Delete command completes.

Quiz

  1. Which opcode creates an I/O Completion Queue?

    • 01h
    • 04h
    • 05h
    • 06h
    Answer and reasoning

    05h. 01h creates an SQ, 04h deletes a CQ, 06h is Identify.

  2. Create I/O SQ with CQID = 4 fails with Completion Queue Invalid. Most likely cause?

    • QSIZE too large
    • CQ 4 does not exist (yet)
    • The interrupt vector is invalid
    • The SQ memory is unmapped
    Answer and reasoning

    The SQ references a CQ that does not exist. Unmapped memory is not detected at create time.

  3. What does IEN = 0 in Create I/O CQ produce?

    • A CQ whose completions are not signalled by interrupt; the host polls
    • An invalid command
    • A CQ that uses vector 0
    • A CQ without phase tags
    Answer and reasoning

    Interrupts disabled for that CQ; it is a polled queue.

  4. The correct deletion order is:

    • CQ then SQ
    • All SQs that use a CQ, then the CQ
    • Any order
    • Reset only; queues cannot be deleted
    Answer and reasoning

    Deleting a CQ still referenced by an SQ fails with Invalid Queue Deletion.

  5. The uniqueness rule for Command Identifiers is:

    • Unique across the controller forever
    • Unique across all SQs among outstanding commands
    • Unique per SQ among outstanding commands
    • Assigned by the controller
    Answer and reasoning

    SQID + CID must be unique among outstanding commands; the host assigns CIDs.

  6. QPRIO = 11b in Create I/O SQ means:

    • Urgent
    • High
    • Medium
    • Low
    Answer and reasoning

    00b Urgent, 01b High, 10b Medium, 11b Low — meaningful only under weighted round robin.

  7. A Create I/O CQ succeeds but the first CQE post for that queue gets an IOMMU fault. Why didn't creation fail?

    Model answer

    Creation moves no data; the controller records the base address without accessing it. The memory is first touched at the first CQE post.

  8. Why is it useful to have different MSI-X vectors for different CQs?

    Model answer

    Each vector can target a different CPU, so completions are processed on the CPU that submitted the I/O (cache locality, no cross-CPU wakeups), and interrupt handlers only scan their own CQ.

  9. How many bytes do a 512-entry SQ and a 512-entry CQ occupy together?

    Model answer

    512 × 64 + 512 × 16 = 32,768 + 8,192 = 40,960 bytes (40 KiB).

Interview questions

  1. Beginner: How is an I/O queue pair created?
    Model answer

    Two Admin commands: Create I/O CQ (05h) with QID, 0's based size, base address, interrupt vector and enable; then Create I/O SQ (01h) with QID, size, base, the CQID it completes into and its priority.

  2. Beginner: What is a Command Identifier?
    Model answer

    A 16-bit value the host puts in each command, unique per SQ among outstanding commands; the controller echoes it in the CQE so the host can match completions to commands.

  3. Intermediate: What errors can Create I/O SQ return and why?
    Model answer

    Completion Queue Invalid (CQ doesn't exist), Invalid Queue Identifier (0, in use, or beyond the grant), Invalid Queue Size (0 or above MQES), Invalid Field in Command (e.g. PC = 0 with CQR = 1).

  4. Intermediate: How does Linux decide how many I/O queues to create?
    Model answer

    It requests up to the number of CPUs (plus extra for read/poll queue types), uses the controller's grant from Number of Queues and the number of MSI-X vectors it could allocate, and maps CPUs to queues through blk-mq.

  5. Advanced: When would you map several SQs to one CQ?
    Model answer

    To provide different priority classes under WRR without multiplying CQs and vectors, or when the controller grants more SQs than CQs or vectors are scarce. The CQ must be sized for the sum of outstanding commands.

  6. Advanced: One I/O queue never generates interrupts but completes commands when polled. Diagnose.
    Model answer

    Check Create I/O CQ CDW11 for IEN and IV; check that the MSI-X table entry for IV is programmed and unmasked; check the analyzer for an MWr to that entry's address after CQE posts; check host IRQ affinity and handler registration. If the MWr is present, the problem is host-side interrupt routing; if absent, IEN/IV or MSI-X masking.

  7. Senior: Propose a validation plan for I/O queue management.
    Model answer

    Positive: max queues × max depth, many-to-one, mixed IEN, vector sharing, QPRIO under WRR. Negative: each error status, boundary QSIZE values, CQ deletion with mapped SQs, double create, delete nonexistent. Stress: create/delete churn under I/O, delete SQ with outstanding commands (verify aborts and CQEs), reset during creation. Observability: trace each queue's first use.

  8. Senior: A customer reports data corruption only at very high queue depths. What queue-level mechanism could be responsible?
    Model answer

    CID reuse or CID collisions (host tag encoding bug, or the controller mixing CIDs across SQs), SQ slot reuse before SQHD advanced, CQ overflow with a shared CQ, or a controller completing a command with the wrong CID. Correlate SQE fetch payloads with CQE CIDs in a trace and look for duplicates or mismatches.

Model explanation for the senior engineer

Create I/O CQ and SQ register a queue context in the controller; they validate identifiers, sizes, vectors and contiguity, but touch no queue memory. A queue is proven by its first use: the SQ tail doorbell at the right stride offset, a successful fetch from the SQ base, a CQE at the CQ base with P = 1 and the right SQID, and an MSI-X write for the right vector. Queue count is negotiated and may be less than requested; depth should be derived from Little's Law and latency targets. CIDs are host-chosen, unique per SQ, and are the key that joins the NVMe command to its completion across the trace.

Chapter summary

I/O queues are created with Create I/O Completion Queue (05h) — QID, 0's based QSIZE, base or PRP-list pointer, PC, IEN, IV — and Create I/O Submission Queue (01h) — QID, QSIZE, base, PC, CQID, QPRIO (and NVMSETID). The CQ must exist first; SQs must be deleted (00h) before their CQ (04h). Creation does not touch queue memory, so first use is what proves a queue. Each CQ binds to one interrupt vector or is polled; SQs may share CQs. Queue depth is chosen with Little's Law up to CAP.MQES + 1 entries. Command Identifiers are host-assigned, unique per SQ among outstanding commands, and returned in every CQE.
