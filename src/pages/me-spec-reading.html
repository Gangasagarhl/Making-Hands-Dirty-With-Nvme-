Ten reading methods that turn a specification from a document you consult into a tool you operate: a question generator, a cross-reference matrix, the "does not say" and "implementation-dependent" disciplines, version and revision-diff methods, a reading order, and step-by-step procedures for reading a command, a register and a state machine — each with a worked reading you can check.

Why this part exists

The Specification Reading School taught you how a specification is built: normative language, reserved fields, tables, state diagrams and cross-references. This part is the workshop that follows the school. It gives you procedures — repeatable sequences of steps — for the reading tasks a protocol engineer performs every week, and it shows each procedure applied to a real NVM Express (NVMe) or Peripheral Component Interconnect Express (PCIe) structure.

Why procedures? Because the most common reading error is not misunderstanding a sentence; it is not reading a sentence that was there. Engineers read the field table for a command and miss the paragraph two pages later that says the field is ignored unless a feature is enabled. A procedure forces you to visit every place the answer could live.

Learning objectives

  • Generate questions about any chapter in the five classes SOURCE-LOOKUP, SYNTHESIS, TRACE, DEBUG and DESIGN, and answer them from sources.
  • Build a cross-reference matrix that places a concept in the Base specification, a command set, a transport, PCIe, Linux and an analyzer — leaving cells empty when a source does not cover it.
  • Write "what the specification does not guarantee" and "implementation-dependent" boxes, and name the evidence that would settle the behaviour on a specific system.
  • Compare two revisions with a feature matrix and the six-axis revision-diff method.
  • Follow a sensible reading order through the official documents.
  • Read an NVMe command in twelve steps, a register in eleven and a state machine in ten.

The story

Imagine a huge recipe book for a castle kitchen. One page says how to bake bread. Another page, far away, says "on feast days, every bread must be twice as big". A third book, in a different room, says which ovens the castle has. If you only read the bread page, your bread is wrong on feast days, and you might try to use an oven that does not exist.

Reading a specification well means knowing where all the pages about bread are, which book each lives in, and what the books simply do not tell you — like what the baker is thinking.

A building inspector reading architectural drawings does not read them like a novel. They have a checklist: the structural drawings, then the electrical, then the fire code, then the local amendments, cross-checking each room against each sheet. The drawings are the specification; the checklist is the procedure; the building as built is the implementation.

An inspector can walk the building. You often cannot see inside the implementation at all: a controller's firmware is closed, and your only view is through registers, logs and traces. Specifications are also less redundant than drawings — one sentence may carry a requirement that appears nowhere else — and they evolve by revision, so "the drawings" are really a stack of versions.

The source-based question generator

A question you cannot answer exposes a gap; a question you can answer only from memory exposes a risk. The question generator is a habit: for every chapter you study, write questions in five classes, and answer each from a named source.

Rules for writing good questions

  • SOURCE-LOOKUP questions name the document. "In the NVMe Base Specification, which register holds the doorbell stride?" — not "what is the doorbell stride?".
  • SYNTHESIS questions cross a boundary: two sections, two documents (Base + transport), or spec + Linux.
  • TRACE questions use the course's lab system numbers (see Example Data Sets) so answers can be checked.
  • DEBUG questions have at least two plausible causes; a debug question with one obvious answer is a lookup in disguise.
  • DESIGN questions ask "why not the alternative?" (see "Why not?" training).
  • Every answer you write states whether it is Verified (you read it), Derived (you reasoned it) or Uncertain.

Worked example: a full question set for the Doorbells chapter

This is a complete set for Doorbells. Answers are short; the point is the shape. Values use the course's lab system (BAR0 = 0xFE60_0000, CAP.DSTRD = 0).

SOURCE-LOOKUP (10)

  1. Where does the doorbell register area begin, relative to the controller's register base?
    Answer

    Offset 1000h. Verified Source: the controller register map for the PCIe transport (NVMe Base / NVMe over PCIe Transport specifications — check which document holds the doorbell definitions in your revision set).

  2. Which register field defines the doorbell stride?
    Answer

    CAP.DSTRD (Doorbell Stride) in the Controller Capabilities register at offset 00h. The stride is 2(2 + DSTRD) bytes.

  3. Which agent writes an SQ Tail doorbell?
    Answer

    The host.

  4. Which agent writes a CQ Head doorbell?
    Answer

    Also the host: it tells the controller which CQ entries it has consumed.

  5. What is the width of a doorbell value field?
    Answer

    Look it up: the doorbell registers are 32-bit with a 16-bit value field, the upper bits reserved. Confirm the exact field width in your revision.

  6. What does the specification say about a doorbell write with an invalid value (for example a tail beyond the queue size)?
    Answer

    It defines an asynchronous error ("Invalid Doorbell Write Value" under the Asynchronous Event Request mechanism) when asynchronous events are enabled. Read the doorbell error conditions in the Base specification for your revision.

  7. Is the admin SQ's doorbell at a fixed offset?
    Answer

    Yes: queue 0's SQ tail doorbell is the first doorbell, at 1000h.

  8. Where is the shadow doorbell / doorbell buffer mechanism defined, and what is it for?
    Answer

    The Doorbell Buffer Config admin command, intended mainly for emulated controllers to reduce MMIO traps. Look up its applicability (it is optional) in the Base specification.

  9. Which register would show that the controller is ready to accept doorbell writes?
    Answer

    CSTS.RDY (Controller Status, offset 1Ch).

  10. Where is the queue size of an I/O SQ set?
    Answer

    In the Create I/O Submission Queue command (Queue Size field, zero-based), bounded by CAP.MQES.

SYNTHESIS (10)

  1. Compute the SQ 3 tail doorbell address on the lab system.
    Answer

    0x1000 + (2 × 3) × 4 = 0x1018 → 0xFE60_1018. Combines the formula and CAP.DSTRD = 0.

  2. Why does the host write a CQ head doorbell at all, if the controller writes the CQ?
    Answer

    So the controller knows which CQ slots are free; without it, the controller could overwrite unconsumed entries. Combines the queue full/empty rules with doorbell semantics.

  3. How does the host know the controller has consumed SQ entries?
    Answer

    The SQ Head Pointer field in each CQE. Combines CQE layout with SQ flow control.

  4. Why can a single doorbell write submit many commands?
    Answer

    The tail value is an index; all entries between old and new tail become available.

  5. What happens to doorbell state on a Controller Level Reset?
    Answer

    Queues are deleted and pointers reset; host must re-create queues. Combines reset and doorbell sections.

  6. Relate DSTRD to virtualization.
    Answer

    A larger stride can place doorbells on separate pages or cache lines, which helps hypervisors trap or map them per queue. Derived

  7. Why is a doorbell write a posted PCIe transaction, and what does that imply?
    Answer

    It is an MMIO Memory Write; the host gets no completion, so it cannot know when the controller saw it. Combines NVMe and PCIe ordering rules.

  8. How do PCIe ordering rules guarantee the SQE is in memory before the controller fetches it?
    Answer

    They do not on their own: the host must make the SQE write visible before the doorbell write (a write barrier in the driver). The controller's fetch after the doorbell then sees the SQE. Combines CPU memory ordering, PCIe ordering and NVMe.

  9. What limits how often a driver should ring doorbells?
    Answer

    Each is an MMIO write with CPU cost; batching submissions reduces cost at the expense of latency. Combines doorbell semantics with performance.

  10. How does Linux expose the queue sizes it chose?
    Answer

    Through driver parameters and sysfs/debug information; the doorbell itself is not exposed. Combines spec with Linux.

TRACE (5)

  1. An MWr32 to 0xFE60_100C with data 0x0000_0007: what is it?
    Answer

    CQ 1 head doorbell = 7: the host has consumed CQ1 entries up to slot 6.

  2. Two MWr32 to 0xFE60_1008 with data 5 then 9, 40 ns apart, then eight SQE fetches. Is anything wrong?
    Answer

    Not necessarily: this is batching. If the previous tail was 1, the two writes make slots 1–4 and then 5–8 available — eight new entries, matching eight fetches. If the previous tail was something else, the count of fetches should change to match. The question teaches you to track the previous doorbell value; a single doorbell write cannot be interpreted alone.

  3. A doorbell write is followed by no SQE fetch for 30 s. List what you check in the trace.
    Answer

    Ack DLLP for the MWr (link delivery), the address (right queue?), the value (valid index?), the controller's other activity (alive?).

  4. An SQE fetch MRd has Length 48 Dwords. What does it imply?
    Answer

    Three 64-byte SQEs fetched in one read (48 × 4 = 192 bytes) — controller fetch batching, implementation-dependent.

  5. A doorbell MWr appears to BAR0+0x1010 with value 0x400 on a 1024-entry SQ 2. What is wrong?
    Answer

    0x400 = 1024 is not a valid index for a 1024-entry queue (valid 0–1023): an invalid doorbell write value. See the worked case in Debugging Methodology.

DEBUG (5)

  1. Commands on SQ 3 never execute; SQ 1 and 2 work.
    Answer

    Candidates: wrong doorbell offset (stride bug), SQ 3 not created or created with wrong CQ, invalid value. Separate by checking the doorbell address in a trace and the Create I/O SQ completion.

  2. On a virtual machine, I/O works but is slow; doorbell writes are many.
    Answer

    Each MMIO write traps to the hypervisor; check whether shadow doorbells are supported and used. Evidence: exit counters in the hypervisor.

  3. After a reset, the first command completes twice.
    Answer

    Stale CQ memory with matching phase (driver did not clear CQ) vs controller posting a late CQE. See Reset lab.

  4. A queue hangs exactly when it fills.
    Answer

    Full-condition bug: host considers the queue full at the wrong point or never writes CQ head doorbells, so the controller cannot post more CQEs.

  5. Asynchronous event reports an invalid doorbell write.
    Answer

    Read the Error Information log for the queue; compare with the host's tail tracking; find the code path that wraps the index.

DESIGN (2)

  1. Why does NVMe use per-queue doorbells instead of one shared "new work" register?
    Answer

    Per-queue doorbells let many CPUs submit independently without locks or read-modify-write, and let the controller know which queue has work. Cost: more register space, scaled by stride.

  2. Would you design doorbells as writes of an index or of a count?
    Answer

    An index is idempotent (writing the same value twice is harmless) and self-correcting after a lost update; a count would double-count on replay. That idempotence is a strong argument for the index design. Derived

"What the specification does not say"

Every major specification topic you study should end with a box titled What the specification does not guarantee. Its job is to stop overgeneralisation: the habit of turning "my drive does X" into "NVMe does X".

  • Internal NAND algorithms — how data is placed, programmed, refreshed or read-retried.
  • Firmware scheduling — the order in which a controller executes fetched commands, beyond the few ordering rules the spec states (for example fused operations).
  • Undocumented optimisations — write coalescing, read caching, prefetching.
  • Analyzer behaviour — how a vendor tool decodes, colours, groups or timestamps events.
  • Performance — latency, IOPS and bandwidth numbers, except where a feature defines reporting (for example latency-related logs and features).
  • Command execution order — commands in one SQ are not required to complete in submission order.
  • Timing of an Autonomous Power State Transition beyond the configured rules.

How to write your own

  1. List every behaviour you observed or were told about the topic.
  2. For each, find the normative sentence ("shall", "should", "may") that covers it. If you cannot find one, it goes in the box.
  3. For each item in the box, write who decides it instead (controller vendor, firmware, OS, platform, analyzer vendor).

Write the box for (a) Dataset Management Deallocate, (b) MSI-X vector selection, (c) the SMART "Percentage Used" value.

Model answer

(a) Not guaranteed: when the media is actually erased; whether a later read returns zeros, a fixed pattern or old data (this is governed by reported deallocation behaviour fields — read them, do not assume); performance effect. Decided by: controller firmware within the reported behaviour. (b) Not guaranteed by NVMe: which CPU handles a vector — the OS decides via affinity; the spec defines that each CQ is associated with a vector at creation. (c) Not guaranteed: the exact algorithm that maps wear to the percentage; it is a vendor-specific estimate of life used, which the spec describes but whose computation is implementation-dependent. It may exceed 100.

The implementation-dependent behaviour box

The companion discipline: whenever you describe behaviour that is not fixed by a specification, say so in a box that begins with one sentence —

This behaviour may vary by controller, firmware, driver, OS, platform, or analyzer.

— and then, crucially, state exactly what evidence would establish the behaviour for a specific system. A box that only says "it depends" is useless; a box that says what to measure is a test plan.

Version-compatibility lab

Safe lab Reading and reasoning.

Objective

Given an older NVMe revision (1.4), the current one (2.4) and a feature matrix, decide what is common, what changed, what must be checked, and what cannot be assumed — for a host driver written against 1.4 meeting a 2.4 controller, and the reverse.

Skills

  • Reading revision history.
  • Capability discovery as the bridge between versions.

Hardware and software required

The NVMe 1.4 specification (archived on nvmexpress.org), the 2.4 set, and the Revision Changes document.

Background

The Version register (VS, offset 08h) reports the major, minor and tertiary version the controller complies with. But a version number is a coarse signal: most features are optional and reported individually, so capability fields, not version numbers, decide behaviour. See Capability discovery.

Questions

  1. What is common?
  2. What changed?
  3. What must be checked?
  4. What cannot be assumed?
  5. A 2.4 host meets a 1.4 controller. What must it avoid?
Solution

Common. Register-based bring-up (CAP, VS, CC, CSTS, AQA, ASQ, ACQ), the queue and doorbell model, 64-byte SQE / 16-byte CQE, PRP and SGL data pointers, core admin commands (Identify, Get Log Page, Create/Delete queues, Set/Get Features) and the NVM command set's Read, Write and Flush.

Changed. Namespaces may now belong to command sets other than NVM; Identify gained command-set-specific data structures; new status codes, log pages and features exist; the document set is reorganised so a definition may have moved document.

Must check. CAP.CSS (which command sets the controller supports), the I/O Command Set profile selected, each namespace's command set (from the namespace identification descriptors), the Commands Supported and Effects log for each command set, the optional-feature support bits for every optional feature used, and the log pages supported.

Cannot assume. That every namespace is an NVM namespace; that a feature present in 2.4 is supported by any particular 2.4 controller; that a field reserved in 1.4 is still reserved; that a status code value means the same thing to an older host's tables (it may print "unknown").

Reverse direction. A 2.4 host must not issue commands, features or log requests the 1.4 controller does not report; it must gracefully handle Invalid Field / Invalid Opcode statuses if it probes; it must not interpret reserved (zero) fields as meaningful 2.4 values.

What a senior engineer notices

  • Interoperability bugs at version boundaries are mostly hosts that skip capability checks because "every drive we tested had it".
  • The version register is useful for triage, never for feature decisions.

Extension

On any Linux machine with an NVMe drive, read (only) nvme id-ctrl /dev/nvme0 -H and locate the version field and the optional-command support fields. Record which optional admin commands your drive supports.

The revision-diff method

The NVM Express organisation publishes an authoritative change list with each release (for 2.4, "NVM Express Revision Changes 2026.07.30"). Reading it well means reading every entry along six axes:

  1. Added feature — what capability now exists?
  2. Changed field — which data structure, command or register field is new, redefined, or no longer reserved?
  3. Changed behaviour — what must a controller or host now do differently?
  4. Changed error handling — new status codes, new error conditions, new log entries?
  5. Interoperability implication — what happens when old meets new, in both directions?
  6. Validation requirement — what new tests are needed; which existing tests change?

How to read an NVMe command

Twelve steps. Do them in order, write a line for each, and you will not miss the paragraph two pages away.

  1. Identify the command set (admin, NVM, ZNS, KV, …) — determines which document and which opcode space.
  2. Identify the opcode — from that document's command table.
  3. Identify the command format — which Command Dwords (CDW10–15) carry which fields; which common fields (NSID, data pointer, metadata pointer) are used.
  4. Identify mandatory fields — that must be set correctly for every use.
  5. Identify optional fields — and the capability that makes each meaningful.
  6. Identify data pointers — PRP or SGL; direction; length; who allocates the buffer.
  7. Identify namespace applicability — does NSID matter? broadcast value allowed?
  8. Identify prerequisites — features, formats, states, prior commands.
  9. Identify completion — what the CQE returns (Dword 0 command-specific results?).
  10. Identify errors — generic statuses that commonly apply, plus command-specific ones.
  11. Identify side effects — on other commands, logs, asynchronous events, state.
  12. Identify trace consequences — which TLPs, in which direction, in which order.

Read Get Log Page (admin opcode 02h) with the twelve steps. Pay special attention to step 3 (how the length is encoded) and step 11 (some logs clear or change state when read).

Solution

1 Admin. 2 02h (the same number as Read: opcodes are per command set — a classic trap). 3 CDW10 carries the Log Page Identifier in bits 7:0, Log Specific Parameter, Retain Asynchronous Event, and the lower half of Number of Dwords (NUMDL, bits 31:16); CDW11 carries the upper half (NUMDU) and a Log Specific Identifier; CDW12–13 the 64-bit offset; CDW14 UUID index and CSI. The number of Dwords is zero-based. 4 LID, NUMD, data pointer. 5 Offset (only if the log supports offsets), LSP/LSI (log-specific), RAE, CSI. 6 Device-to-host; length (NUMD + 1) × 4 bytes. 7 Some logs are per-namespace, some controller-wide (NSID FFFFFFFFh or 0, per log's rules) — read each log's scope. 8 The log must be supported (Log Page Attributes, Supported Log Pages log). 9 Status only. 10 Invalid Log Page, Invalid Field in Command. 11 Reading certain logs can clear an outstanding asynchronous event unless RAE is set; some logs are "read and clear". 12 Doorbell, SQE fetch, data MWr with the log, CQE, interrupt.

How to read a register

Eleven steps. The fifth carries a warning: classify access types (read-only, read-write, write-1-to-clear, and others) only when you have read them in the specification. Never infer "it must be write-1-to-clear because it is a status bit".

  1. Locate the register (document, offset, which BAR or capability).
  2. Identify its width.
  3. Identify its reset value (and which reset).
  4. Decode its fields.
  5. Classify field access types — only when verified.
  6. Identify side effects of reads and writes.
  7. Identify sequencing rules (what must be written before, what to wait for after).
  8. Identify related registers.
  9. Identify the software owner.
  10. Identify hardware behaviour in response.
  11. Identify trace implications.

Decode a CC value of 0x0046_0001. Then decode 0x0046_4001 and say what the host has asked for.

Answer

0x0046_0001: IOCQES = 4 (16-byte CQEs), IOSQES = 6 (64-byte SQEs), SHN = 0, AMS = 0 (round robin), MPS = 0 (4 KiB), CSS = 0 (NVM command set), EN = 1. 0x0046_4001 adds bits 15:14 = 01b: SHN = normal shutdown notification. The host is shutting the controller down; it should now poll CSTS.SHST for "shutdown processing complete".

A second register for practice: CSTS

CSTS (offset 1Ch): RDY (bit 0), CFS — Controller Fatal Status (bit 1), SHST — shutdown status (bits 3:2), NSSRO — NVM Subsystem Reset Occurred (bit 4), PP — Processing Paused (bit 5). Apply the eleven steps yourself. Pay attention to step 5 for NSSRO: how is it cleared? Read the table; do not guess.

The PCIe side: reading an AER register

The same eleven steps apply to PCIe registers. For the Uncorrectable Error Status register: it is located in the AER Extended Capability (found by walking the extended capability list from offset 100h in configuration space); its width is 32 bits; its status bits are "sticky" (they survive certain resets — read which); its access types are given per bit in the PCI Express Base Specification. Writing the step-5 answer from memory is the most common source of wrong AER-clearing code.

How to read a state machine

Ten steps. Specifications present state machines as diagrams, tables or prose; the procedure works for all three.

  1. List the states.
  2. Identify each state's entry condition.
  3. Identify each state's exit conditions.
  4. Identify the events (register writes, received messages, internal conditions).
  5. Identify the timers and their limits.
  6. Identify the errors (what happens when an event arrives in the wrong state).
  7. Identify recovery paths.
  8. Map each state and transition to trace evidence.
  9. Identify impossible transitions.
  10. Build a diagnostic tree.

Worked reading: the NVMe controller enable/shutdown lifecycle

The Base specification does not draw this as a single named state machine; it is spread across CC, CSTS and the initialisation and shutdown sections. Turning prose into a state machine is itself a skill — label the result Derived.

Apply the ten steps to the Zoned Namespace zone state machine (ZNS Command Set 1.5) and to the PCIe LTSSM top-level states (Detect, Polling, Configuration, L0, Recovery, L0s, L1, L2, Disabled, Loopback, Hot Reset). For each, list two impossible transitions and the trace evidence that would expose one.

Model answer (abbreviated)

ZNS: impossible — Empty → Full by a write that does not fill the zone; Offline → any writable state by host command. Evidence: zone descriptors before/after, the write's NLB. LTSSM: impossible — Detect → L0 without Polling/Configuration; L1 → L0 without passing through Recovery. Evidence: analyzer LTSSM view or ordered-set sequence; an observed "direct" transition usually means the analyzer missed states (capture limitation), not that the device violated the protocol — another lesson in analyzer limitations.

Lab: a complete reading of Create I/O Submission Queue

Safe lab Reading only.

Objective

Combine all three procedures on one topic: read the Create I/O Submission Queue command (twelve steps), the registers it depends on (CAP.MQES, CC.IOSQES), and the queue lifecycle it starts (ten steps). Produce a one-page study note with every fact cited.

Skills

  • Procedure discipline.
  • Citations by document, revision and section name.

Hardware and software required

NVMe Base Specification 2.4 and NVMe over PCIe Transport 1.4.

Input

The specifications. Specification Reading School worked the companion Create I/O Completion Queue command; use it as a model but do not copy.

Expected output

A study note with: a twelve-row command table; two eleven-row register tables; a ten-row lifecycle table; a cross-reference matrix row; a "does not say" box; an implementation-dependent box.

Step 1

Command reading. Note especially the Physically Contiguous flag, the Completion Queue Identifier field, and the queue priority field (meaningful only with weighted round robin arbitration).

Step 2

Register readings for CAP (MQES, CQR) and CC (IOSQES).

Step 3

Lifecycle: does not exist → created → in use → deleted (Delete I/O SQ) or destroyed by reset. What happens to outstanding commands on delete?

Observation

Count how many separate sections you visited. Most learners find six or more.

Questions

  1. Why must the CQ exist before its SQ is created?
  2. What status applies if the Queue Size exceeds MQES?
  3. What happens to commands still in the SQ when it is deleted?

Challenge

Write two DEBUG questions and one DESIGN question about this command, with answers.

Hint

For Q3, look for the status that names "SQ deletion" among the generic statuses.

Solution

Q1: the SQ creation names its CQ; the controller must be able to post completions for it, so the CQ must exist (otherwise a Completion Queue Invalid status). Q2: Invalid Queue Size (a command-specific status of Create I/O SQ; confirm its name and value in the Base specification). Q3: they are aborted with the generic status "Command Aborted due to SQ Deletion" (as the course understands it; confirm), and the host must handle those CQEs. Challenge examples: DEBUG — "Create I/O SQ fails with Invalid Queue Size on one drive but not another, same driver" (MQES differs; driver ignores CAP); DESIGN — "why not let SQs and CQs be created in one command?" (flexibility: many SQs can share one CQ; separate creation keeps the model simple and composable).

What a senior engineer notices

  • The command's own table answers perhaps half of the questions; the rest are in the queue model, the registers and the status tables.
  • Zero-based fields (Queue Size, NLB, NUMD) are where most off-by-one bugs start.

Failure variants

  • Driver sets IOSQES after creating queues: undefined behaviour territory — find the sentence that forbids it.
  • CQR = 1 (contiguous queues required) and a driver that allocates non-contiguous memory.

Extension

Repeat for Delete I/O Submission Queue and compare the lifecycles.

Quiz

  1. Tag this question: "Compute the SQ 2 tail doorbell address given CAP.DSTRD = 1."

    • SOURCE-LOOKUP
    • SYNTHESIS
    • TRACE
    • DESIGN
    Answer and reasoning

    It combines the doorbell formula with a capability value: synthesis. (Answer: stride 8 bytes; 0x1000 + 2×2×8 = 0x1020.)

  2. In a cross-reference matrix, the "PCIe" cell for "Zone write pointer" should be…

    • "Carried in TLPs"
    • "See PCIe flow control"
    • Empty — PCIe does not cover the concept
    • "Implementation-dependent"
    Answer and reasoning

    The write pointer is a ZNS concept. Commands carrying it travel in TLPs, but PCIe does not define it. Only populate a cell when the source covers the concept.

  3. Admin opcode 02h and NVM opcode 02h are…

    Answer

    Get Log Page and Read respectively. Opcodes are scoped by command set (and by admin vs I/O queue); step 1 of the command procedure exists for this reason.

  4. Which step of the register procedure warns against inventing semantics?

    • Classify access types only when verified
    • Identify width
    • Identify related registers
    • Identify trace implications
    Answer

    Step 5.

  5. Why is the version register insufficient for deciding whether to use a feature?

    Answer

    Most features are optional within a revision and are reported by capability fields; a 2.4 controller need not implement any particular optional 2.4 feature.

  6. Decode CC = 0x0046_0081.

    Answer

    EN = 1, CSS = 0, MPS = bits 10:7 = 0001b → 8 KiB pages (213), AMS = 0, SHN = 0, IOSQES = 6, IOCQES = 4. Check MPS against CAP.MPSMIN/MPSMAX.

  7. Name the six axes of the revision-diff method.

    Answer

    Added feature; changed field; changed behaviour; changed error handling; interoperability implication; validation requirement.

  8. In the controller lifecycle, CSTS reads 0xFFFF_FFFF. Which layer do you go to first?

    • NVMe queues
    • Command status
    • PCIe: the device is not responding to the MMIO read
    • Firmware logs
    Answer and reasoning

    All ones is what a host typically sees when a read is not completed successfully by the device (unsupported, removed, link down). It is a PCIe-level symptom before it is an NVMe one.

  9. What makes an "implementation-dependent" box useful rather than an excuse?

    Answer

    It names the evidence that would establish the behaviour on a specific system — which measurement, log or capture.

Interview questions

  1. (Beginner) How do you find out what a field in an NVMe command means?

    Model answer

    Identify the command set and document, find the command's format table and field definitions in the current revision, then read related sections (status codes, prerequisites, capability bits) — and note the revision.

  2. (Intermediate) What is the difference between a normative and an informative statement?

    Model answer

    Normative statements are requirements (shall/should/may with defined meanings); informative text explains or illustrates and is not binding. Compliance is tested against normative statements.

  3. (Advanced) A colleague claims "NVMe guarantees in-order completion within a queue". How do you respond?

    Model answer

    Ask for the normative sentence. NVMe does not require in-order completion; commands may complete in any order, which is why each CQE carries the CID. The exceptions (for example fused operations) are explicit.

  4. (Senior) How do you assess the impact of a new specification revision on your product?

    Model answer

    Read the Revision Changes document with the six axes for each entry; mark which features we implement or depend on; for each, list interoperability effects in both directions and new validation; update decoders for changed fields; schedule regression for anything that used previously reserved bits.

  5. (Senior) How would you turn a prose description into a state machine safely?

    Model answer

    Apply the ten steps, label the result Derived, cite each state's source sentence, list impossible transitions, and have it reviewed against the prose; never present it as the specification's own diagram.
