One imaginary machine, documented in full, and the synthetic data sets the course derives from it: a configuration-space dump, a controller register dump, Identify excerpts, a SMART / Health log, an Error Information log entry, and normal and abnormal trace files. Everything here is a synthetic example for teaching — never output from a real device and never an official specification example.

Why a shared synthetic system

Learning to read evidence is easier when the evidence stays consistent. If every chapter invented its own addresses, a learner could never tell whether a number changed because the scenario changed or because the author did. So every trace, register dump and worked example in this course uses one imaginary machine unless a page says otherwise. Once you know its numbers — the SSD is at 01:00.0, BAR0 is 0xFE60_0000, SQ1 lives at IOVA 0x1_2340_0000 — you can follow a command from Chapter 24 to Chapter 39 to the Trace Analysis Laboratory and recognise every address on sight.

None of the values on this page come from a real product. The Vendor ID ABCDh and Device ID 0420h are placeholders, not identifiers of any real company or device. Where a value depends on a specification field, the field's meaning is described from the specification; the value itself is invented. Real devices differ in every implementation-dependent detail. Treat this page the way you would treat a well-built test fixture: realistic, internally consistent, and not evidence about any particular product.

Root port companion values

For cross-checks, the root port 00:01.1 in this system reports (synthetic): Link Capabilities max 16.0 GT/s x4 (it is a x4 port), Link Status 16.0 GT/s x4 with Data Link Layer Link Active = 1, Device Control MPS = 256 B, and AER root error status clear. A mismatch between the two ends — for example the device's MPS larger than the root port's — is a configuration error worth finding before any trace is taken.

Variants used by other pages

  • Downtrained link: Link Status 1024h → 16.0 GT/s, negotiated width x2 (width field 2 instead of 4); see Link Training. Expected behaviour: sequential throughput capped near half.
  • Device gone: every byte reads FFh (Vendor ID FFFFh). Expected behaviour: the driver reports the controller as dead; AER may show Surprise Down at the root port (Chapter 45).
  • Bus mastering off: Command = 0402h. Expected behaviour: the controller cannot fetch commands; the first admin command after enable times out (Chapter 20).

Derived checks

  • Write rate: 768 GB / 91.25 days ≈ 8.4 GB/day ≈ 0.008 drive writes per day on a 1 TB drive: a very light workload. Derived
  • Average transfer sizes: 1.408 × 1012 / 98 × 106 ≈ 14.4 KB per read. Data units are rounded up per thousand units, so these averages are approximate. Derived
  • Busy fraction: 1,250 minutes / (2,190 × 60) ≈ 1%: the drive is idle almost all the time, so latency complaints on this system are unlikely to be saturation. Derived
  • Using the formula in Mathematics, Percentage Used of 1 after 91 days projects many years of rated life; with a 1-percent resolution, take another snapshot later before concluding anything.

The address in row 4 equals PRP1 from the SQE, so the question becomes "why is 0x2_0040_0000 not mapped?" — a host-side DMA mapping bug, not a link or SSD fault. Supporting evidence to look for: an IOMMU fault message in the kernel log naming device 01:00.0 and that address, and possibly an AER entry at the device for the received UR (reporting is implementation- and configuration-dependent). The CQE's DW3 decodes as CID 0x0043, phase 1, status field 0x0004 → SCT 0, SC 04h (Data Transfer Error), DNR 0.

Loading and checking the data sets

CQ1_BASE, CQE_SIZE = 0x1_2341_0000, 16

def decode_cqe(words):
    dw2, dw3 = words[2], words[3]
    status = dw3 >> 17
    return {"sqhd": dw2 & 0xFFFF, "sqid": dw2 >> 16, "cid": dw3 & 0xFFFF,
            "phase": (dw3 >> 16) & 1, "sc": status & 0xFF, "sct": (status >> 8) & 0x7,
            "dnr": (status >> 14) & 1}

def analyse(name, text):
    rows = list(csv.DictReader(io.StringIO(text)))
    outstanding, first_abnormal = {}, None
    t_doorbell = int(rows[0]["time_ns"])
    for r in rows:
        t = int(r["time_ns"])
        if r["type"].startswith("MRd"):
            outstanding[r["tag"]] = t
        elif r["type"].startswith("Cpl"):
            start = outstanding.pop(r["tag"], None)
            if start is None and first_abnormal is None:
                first_abnormal = (r["idx"], "completion with no matching request")
            if r["cpl_status"] != "SC" and first_abnormal is None:
                first_abnormal = (r["idx"], f"completion status {r['cpl_status']} for tag {r['tag']}")
            if start is not None:
                print(f"  tag {r['tag']}: round trip {t - start} ns, status {r['cpl_status']}")
        elif r["type"].startswith("MWr") and r["addr"] and CQ1_BASE <= int(r["addr"], 16) < CQ1_BASE + 1024 * CQE_SIZE:
            cqe = decode_cqe([int(w, 16) for w in r["data"].split()])
            slot = (int(r["addr"], 16) - CQ1_BASE) // CQE_SIZE
            print(f"  CQE slot {slot}: {cqe}; doorbell-to-CQE {t - t_doorbell} ns")
            if (cqe["sc"] or cqe["sct"]) and first_abnormal is None:
                first_abnormal = (r["idx"], "NVMe error status in CQE")
    if outstanding:
        print("  requests never completed (tags):", list(outstanding))
    print(f"{name}: first abnormal event = {first_abnormal or 'none'}\n")

if __name__ == "__main__":
    analyse("Trace A", TRACE_A)
    analyse("Trace B", TRACE_B)

Expected output: for Trace A, tag 0x21 round trip 640 ns, CQE slot 5 with sqhd 6, sqid 1, cid 66 (0x42), phase 1, status zero, doorbell-to-CQE 64,210 ns, and "first abnormal event = none". For Trace B, tag 0x22 completes with SC; tags 0x23 and 0x24 complete with UR; CQE slot 6 with cid 67 (0x43) and sc 4; and "first abnormal event = ('6', 'completion status UR for tag 0x23')". Note that the script reports row 6, not the CQE in row 8: the NVMe error is a consequence.

Rules for creating new synthetic data

  1. Start from this system's addresses and parameters; if you change one (for example Gen5 instead of Gen4), say so at the top.
  2. Keep every derived value consistent: SQE addresses from slot indices, CQE phase from the pass number, doorbell values from tail indices, TLP counts from MPS and MRRS.
  3. Label provenance, source, assumptions and expected behaviour, and mark the first abnormal event in abnormal traces.
  4. Use placeholder identifiers (ABCDh, "Lab SSD") — never a real vendor's IDs, model names or serial formats.
  5. Do not invent field encodings for features you cannot verify; describe them by name instead (see Truth Policy).

Exercises

  1. In Trace A, the next Read uses SQ1 slot 6 and lands in CQ1 slot 6. Write its SQE fetch address, its CQE address and the two doorbell values.
    Answer

    SQE fetch at 0x1_2340_0000 + 6 × 64 = 0x1_2340_0180; CQE at 0x1_2341_0000 + 6 × 16 = 0x1_2341_0060; SQ1 tail doorbell value 7; CQ1 head doorbell value 7. (This is exactly what Trace B shows.)

  2. When CQ1 wraps after slot 1023, what phase tag will the controller write in slot 0, and what must the host expect?
    Answer

    The controller inverts the phase on each pass: the first pass wrote 1, so the second pass writes 0. The host must flip its expected phase when its head wraps; otherwise it will treat stale entries as new or new ones as stale.

  3. Using the SMART data set, how many host bytes would have to be written per day to reach 1 DWPD, and how does the current workload compare?
    Answer

    1 DWPD on a 1.0 TB drive is 1.0 TB/day. The current rate is about 8.4 GB/day: roughly 0.8% of 1 DWPD.

  4. In Trace B, list two independent pieces of evidence that would confirm the host-side mapping hypothesis, and one that would refute it.
    Answer

    Confirm: an IOMMU fault log entry for device 01:00.0 at IOVA 0x2_0040_0000; driver tracing showing that buffer was unmapped (or never mapped) before submission. Refute: the IOVA is shown mapped at the time of the request and the root complex still returned UR — then look at address decoding or the root complex itself.
