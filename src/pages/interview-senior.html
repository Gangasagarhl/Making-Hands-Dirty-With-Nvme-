Two hundred senior-level interview questions on Non-Volatile Memory Express (NVMe) over Peripheral Component Interconnect Express (PCIe). Almost every question hands you evidence (a trace excerpt, a register dump, a log line, a piece of code or a set of numbers) and asks you to reason from it. Each one has a hidden model answer, what a strong answer includes, the weak answer interviewers hear most often, and a link to the chapter that teaches it.

Who this bank is for and how to use it

This bank is for engineers preparing for a senior role: the person a team calls when a field failure crosses layers, when two vendors blame each other, when a validation plan needs an owner, or when a performance number does not add up. At this level the interviewer rarely asks "what is X?". They ask "here is what we saw; what happened, how sure are you, and what would you do next?"

What the senior level tests

  • Ambiguous field failures. Symptoms with several plausible causes, where the skill is ranking hypotheses and choosing the experiment that separates them.
  • Cross-layer root cause with evidence. Moving between the physical layer, the Data Link Layer, Transaction Layer Packets (TLPs), NVMe queues and commands, the Linux driver and the application, and saying which evidence belongs to which layer.
  • Validation strategy. Designing tests that target a mechanism, with an oracle that can actually fail.
  • Performance tuning. Doing the arithmetic (link efficiency, Little's law, tags and credits) before touching a knob.
  • Firmware and driver interaction. Who owns which state, and what happens at the boundaries: reset, power transitions, timeouts and aborts.
  • Specification judgement. Separating what the specification requires (Normative) from what you infer (Derived) and what an implementation chooses (Implementation-dependent).
  • Leading a debug effort. Organising people, evidence and communication when the answer is not yet known.

How to use the bank

  1. Pick a section. Read a question and its evidence. Cover the answer.
  2. Answer aloud or on paper in about five minutes. Use the shape claim → mechanism → evidence → limits → next step taught on the Interview Academy hub page.

PCIe link and physical layer

Senior physical-layer questions are about localisation and judgement: which side, which lane, which condition, and whether a number is actually a problem. Fifteen questions.

  1. [Trace] A Gen4-capable SSD in a Gen4 slot comes up at 8.0 GT/s. The analyzer's Link Training and Status State Machine (LTSSM) view shows this. What happened, and what do you check next?

    #TimeStateRateNotes
    10 msDetect → Polling2.5 GT/sReceivers detected on lanes 0–3
    20.4 msConfiguration → L02.5 GT/sx4 negotiated
    30.6 msRecovery.Speed → L08.0 GT/sEqualization phases 0–3 complete at 8.0 GT/s
    41.3 msRecovery.Equalization16.0 GT/sPhase 2 ends without a usable preset on lane 2
    53.1 msRecovery.Speed → L08.0 GT/sBack to 8.0 GT/s; no further speed-change attempts
    Model answer

    The link trained normally, changed speed to 8.0 GT/s, then attempted 16.0 GT/s. Equalization at 16.0 GT/s failed (row 4 is the first abnormal event: lane 2 could not reach an acceptable preset), so the ports fell back to the highest rate that worked. Nothing at the NVMe layer is wrong; the drive simply runs at half the link bandwidth (about 3.9 GB/s instead of about 7.9 GB/s per direction before protocol overhead). Next: read Link Capabilities and Link Status on both the root port and the SSD to confirm the speed; read the Physical Layer 16.0 GT/s extended capability status on both ends to see which equalization phases completed; check Link Control 2 Target Link Speed in case firmware capped it; check for a riser, retimer or cable; use lane margining at 8.0 GT/s to see whether lane 2 is already marginal; and swap slot and drive to see whether the failure follows the lane or the part.

    A strong answer includes: the first abnormal event (row 4, not row 5); a per-lane hypothesis; checking both link partners; the bandwidth consequence in numbers; a swap experiment.

    Common weak answer: "The SSD only supports Gen3" (contradicted by the speed-change attempt) or "update the SSD firmware" without evidence.

  2. [Troubleshoot] In a fleet, about 3% of boots bring a U.2 SSD up at x2 instead of x4. After a warm reboot it is usually back at x4. How do you investigate?

    Model answer

    Width is decided in Detect and Configuration: a lane that does not detect a receiver, or that fails to exchange training sets during Configuration, is dropped and the link forms on the lanes that work (x2 is the natural fallback for an x4 link). Intermittent loss of one or two lanes at power-up points to a lane that is marginal at a specific moment: connector or cable contact, reference clock arrival time, the device's PHY coming out of reset late, or receiver detection being sensitive to AC-coupling and temperature. Evidence: log Link Status (Negotiated Link Width) at every boot along with slot, drive serial, cable and temperature; capture the LTSSM in Detect and Configuration on a failing boot (trigger on width < x4) to see which lanes dropped out; check whether it is always the same lanes (a hardware path) or random (timing). Swap cable and slot, and compare cold boots with warm reboots, because a warm reboot may not cycle power to the drive.

    A strong answer includes: where width is decided in the LTSSM; per-lane identification; separating cold from warm boot; fleet data to find the common factor.

    Common weak answer: "Reseat the drive and close the ticket", which hides a recurring hardware defect.

    Learn it in: Chapter 8, Module 08, Failure Library.

  3. [Spec] A monitoring script alerts whenever Link Bandwidth Management Status or Link Autonomous Bandwidth Status gets set on the root port above an SSD. Which of the two is worth an alert, and why?

    Model answer

    The two bits record different reasons for a speed or width change. Link Autonomous Bandwidth Status says the hardware changed the link speed or width on its own for a reason other than reliability (for example power management). Link Bandwidth Management Status says that a link retraining requested by software completed, or that the hardware changed speed or width because of a reliability problem. So Link Bandwidth Management Status deserves the alert when software did not just request a retrain; Link Autonomous Bandwidth Status is usually informational. Both bits are write-1-to-clear in Link Status, so the script must clear them after reading or it will alert forever. Pair the alert with the current speed and width and with AER correctable counters, so the alert says what changed.

    A strong answer includes: the reliability versus autonomous distinction; that a software retrain also sets the management bit; clearing the bits; adding context.

    Common weak answer: treating both as errors, or not knowing that software retraining sets one of them.

    Learn it in: Chapter 18, Chapter 69.

  4. [Trace] A link monitor reports 4,000 entries into the Recovery state per hour on an SSD that has no errors and normal performance. A colleague wants to raise a hardware defect. What do you ask first?

    Model answer

    "Is Active State Power Management (ASPM) L1 enabled?" Exiting L1 goes through Recovery before the link returns to L0, so every idle-to-active transition counts as a Recovery entry. A drive that idles between bursts can enter and exit L1 thousands of times an hour with no fault. Distinguish the cases: compare Recovery entries with L1 entries (they should match one to one if L1 explains them); look at what precedes each Recovery: an electrical idle exit after L1 is normal, while Recovery entered from L0 after NAKs, a replay timeout or framing errors is not; and check AER correctable counters (Receiver Error, Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover). If correctable counters are zero and every Recovery follows an L1 exit, there is no defect. The cost to watch is latency on the first request after idle, not reliability.

    A strong answer includes: L1 exit through Recovery; classifying Recovery entries by what preceded them; using AER counters as a cross-check.

    Common weak answer: "Recovery means the link is bad."

    Learn it in: Chapter 50, Chapter 8, Module 42.

  5. [Concept] A platform adds a retimer between the root port and a Gen5 SSD. The firmware team asks whether the retimer is "transparent" and can be ignored when debugging. What do you tell them?

    Model answer

    A retimer is transparent to the Data Link and Transaction Layers: it does not ACK TLPs, hold a replay buffer or change sequence numbers, and software does not enumerate it as a function. It is not transparent at the physical layer: it recovers the clock and re-drives the signal, participates in link equalization (each segment is equalized separately), forwards ordered sets with adjustments, and adds latency in each direction. For debugging this means: a link problem may live on either segment; correctable errors reported by the root port do not tell you which segment caused them; analyzer placement matters (an interposer on the SSD side of the retimer sees a different electrical segment from one on the root-port side); and the Link Status 2 register can report that a retimer was detected, which is worth recording in every bug report. Some retimers expose their own diagnostics through vendor channels.

    A strong answer includes: transparent to DLL and TL but active in the physical layer; two equalized segments; analyzer placement; recording retimer presence.

    Common weak answer: "It's just a buffer, ignore it" (that describes a redriver more closely, and even a redriver changes signal integrity).

    Learn it in: Chapter 5, Chapter 54, Module 07.

  6. [Troubleshoot] Lane margining on a Gen4 x4 link gives this table at room temperature. The link shows a few correctable Receiver Errors per day. What do you conclude, and what do you not conclude?

    Lane  Timing margin (steps, left/right)   Voltage margin (steps, up/down)
 0        14 / 15                               12 / 13
 1        15 / 14                               13 / 12
 2         5 /  6                                4 /  5
 3        14 / 14                               12 / 12
    Model answer

    Lane 2 at the root port's receiver has roughly a third of the margin of its neighbours in both timing and voltage. That localises the weakness to one direction (SSD transmitter → root port receiver) and one lane, and it is the best candidate for the Receiver Errors. What I do not conclude yet: whether the SSD's transmitter, the board trace, the connector or the root port's receiver is at fault; and whether the margin is "out of spec", because margining reports steps whose size and meaning come from each receiver's advertised capabilities, so steps are not directly comparable between different devices. Next: margin the other direction (the SSD's receiver, if it supports margining); repeat at high temperature; swap the drive into another slot and another drive into this slot; and confirm the error counters by lane if the platform exposes them. If the weak lane follows the slot, it is the board or root port side; if it follows the drive, it is the drive or its connector.

    A strong answer includes: per-lane, per-direction localisation; caution about step units; repeating under temperature; a swap to separate board from drive.

    Common weak answer: "Lane 2 is bad, replace the SSD."

  7. [Concept] An SSD in an external enclosure works on one host but logs bursts of Receiver Errors on another. The enclosure gets its reference clock locally rather than from the host cable. What clocking question do you ask, and why does it matter?

    Model answer

    "Are both ends configured for separate reference clocks, and is spread-spectrum clocking enabled on either side?" With a common reference clock, both ends run at exactly the same frequency (spread together), so the elastic buffers only absorb small drift. With separate clocks, the frequency difference can be larger, especially if one side spreads its clock and the other does not; the architecture that allows separate clocks with spread spectrum (Separate Reference Clocks with Independent Spread, SRIS) requires SKP ordered sets to be sent more often so the receivers' elastic buffers can compensate. If one side assumes common clock and the other runs from an independent spread clock, the elastic buffer underflows or overflows periodically, which appears as Receiver Errors and replays in bursts that may follow the spread modulation. Evidence: SKP ordered set intervals in the analyzer, the SRIS configuration in platform firmware, and whether the errors stop when spread spectrum is disabled on the enclosure.

    A strong answer includes: common clock versus separate clock; spread spectrum as the aggravating factor; SKP insertion rate as the compensation; an experiment (disable spread spectrum).

    Common weak answer: blaming the cable without asking about clocking.

    Learn it in: Chapter 5, Module 07.

  8. [Troubleshoot] On one server model, an SSD is missing from lspci after roughly 1 in 50 cold boots. When it is missing, the root port's Link Status shows Data Link Layer Link Active = 0. A rescan does not bring it back; a full power cycle does. Which timing relationships do you investigate?

    Model answer

    The device never reached a working link, so this is a power-up sequencing problem, not enumeration. Investigate: (1) power rails versus PERST# deassertion: is PERST# released only after the drive's supplies are stable for the required time? (2) reference clock versus PERST#: is REFCLK stable before PERST# is released? (3) the drive's own readiness: does its PHY start link training within the window the base specification allows after PERST# deassertion, and does the root port give up on Detect before the drive appears? (4) platform firmware: does it retrain or hot-reset a link that failed, or simply leave it down? Measure with a scope or logic analyzer on PERST#, REFCLK enable and the rails on failing and passing boots, and capture the LTSSM from the root port side. A rescan cannot help because software only probes devices behind a link that is up; a link retrain (or Secondary Bus Reset) from the root port is the software-side experiment to try. Confirm the exact timing parameters in the PCI Express Card Electromechanical (CEM) specification and the base specification's reset rules rather than from memory.

    A strong answer includes: link never up versus not enumerated; PERST#, REFCLK and rail timing; measuring failing versus passing boots; why rescan cannot help; citing the specifications by name for exact numbers.

    Common weak answer: "Add pci=realloc" (a resource fix for a link problem).

    Learn it in: Chapter 49, Chapter 17, Module 08.

  9. [Trace] An analyzer on a newly built backplane shows one port stuck cycling between Polling.Active and Polling.Compliance. What does that signature usually mean, and how do you narrow it down?

    Model answer

    Polling.Compliance is entered when the LTSSM detected a receiver on a lane during Detect but then does not see the expected training sets on all detected lanes during Polling (or when compliance is forced by the Enter Compliance setting). In a new board that usually means a lane that is electrically present (it detects the termination) but cannot carry data: a broken or mis-routed differential pair, swapped P/N handled badly, a missing AC-coupling capacitor, or a lane that is wired to the wrong partner lane. Narrow it down by looking at which lanes send training sets and which only send the compliance pattern, checking that Enter Compliance is not set in Link Control 2 by firmware, testing with a known-good card, and checking the board's lane routing against the schematic. Polarity inversion and lane reversal are normal and handled by training; they do not cause this signature by themselves.

    A strong answer includes: detected but not training; per-lane inspection; ruling out the configuration bit; separating legal polarity/lane reversal from wiring faults.

    Common weak answer: "The device is in test mode", without asking why.

    Learn it in: Chapter 8, Module 08.

  10. [Performance] A customer measures 6.2 GB/s of 128 KiB sequential reads on a Gen4 x4 SSD and asks whether the link is the limit. Do the arithmetic.

    Model answer

    Raw: 16 GT/s × 4 lanes × 128/130 ÷ 8 ≈ 7.88 GB/s per direction. Read data travels device → host as Memory Write TLPs; with MPS = 256 bytes and 64-bit addresses, each TLP carries 256 bytes of payload plus a 16-byte header and about 8 bytes of framing, sequence number and Link CRC (LCRC), so about 256/280 ≈ 91% efficiency → ≈ 7.2 GB/s. Subtract a few percent for ACK and flow-control DLLPs and SKP ordered sets: a practical ceiling around 6.8–7.0 GB/s. 6.2 GB/s is about 90% of that ceiling: close, but there is some headroom. Next checks: confirm the negotiated speed and width and that MPS really is 256 on both ends (MPS 128 would drop the ceiling to roughly 128/152 ≈ 84%, about 6.6 GB/s before DLLPs); check queue depth and job count (enough commands in flight to cover latency); and compare with the drive's datasheet figure, which may itself be below the link ceiling.

    A strong answer includes: the raw rate with encoding; per-TLP overhead with the actual MPS; DLLP and SKP overhead; checking MPS on both ends; checking concurrency.

    Common weak answer: "Gen4 x4 is 8 GB/s, so there's 2 GB/s missing."

    Learn it in: Performance Engineering, Mathematics for Storage and Links, Calculators.

  11. [Performance] The commonly cited bit error ratio target for a PCIe receiver is 10−12. On a fully loaded Gen4 x4 link, how many bit errors per hour would sit exactly at that target, and how does that number change how you read correctable error counters?

    Model answer

    One direction carries 16 × 109 bits/s per lane × 4 lanes = 6.4 × 1010 bits/s, or about 2.3 × 1014 bits per hour. At 10−12 that is about 230 bit errors per hour per direction. So a handful of correctable errors per day is far better than the target and is not, by itself, a defect. What matters is: the trend (rising over weeks, or with temperature); clustering (bursts that cause Recovery or REPLAY_NUM Rollover); lane concentration; and whether errors appear when the link is idle (then traffic volume does not explain them). Note also that each detected error usually costs a NAK and a replay, so a high rate shows up as latency before it shows up as failures. Health of a link is better judged with margining and trends than with a single counter value.

    A strong answer includes: the arithmetic; the conclusion that small counts are normal; trend, clustering and lane as the real signals; the latency cost of replays.

    Common weak answer: "Any correctable error is a bad link" or "correctable errors never matter."

    Learn it in: Chapter 45, Mathematics for Storage and Links.

  12. [Troubleshoot] A field team has "fixed" intermittent Gen4 link degradation by running a script every night that sets Retrain Link on the root port. The customer is happy. Do you accept the fix?

    Model answer

    No, not as a root-cause fix. Retrain Link sends the link through Recovery and lets it renegotiate; it can restore a link that has fallen back to a lower speed, but it does not explain why the link degraded, and it may not redo a full equalization. Risks: the retrain happens while I/O is running (latency spikes, and if the retrain fails the link may go down and the SSD may be reset under load); the underlying margin problem keeps getting worse unseen; and the next platform without the script fails. Accept it only as a documented, temporary workaround while collecting evidence: log Link Bandwidth Management Status, speed and width before each retrain, AER correctable counters and temperature, so the script itself becomes the data source for the real investigation.

    A strong answer includes: workaround versus root cause; the operational risk of retraining under I/O; turning the workaround into instrumentation.

    Common weak answer: "If the customer is happy, close it."

    Learn it in: Debugging Methodology, Chapter 9.

  13. [Troubleshoot] Several SSDs in a storage server go link-down at the same moment, but only during heavy write bursts. Afterwards each drive's SMART log shows its Unsafe Shutdowns counter incremented by one. Build the cross-layer hypothesis and the evidence plan.

    Model answer

    Several drives failing together points to something shared, and an Unsafe Shutdowns increment means each drive lost power (or saw a reset) without a normal shutdown notification. Combined with the write-burst trigger, the leading hypothesis is a power delivery problem: a shared rail or backplane supply sagging under the peak current of many drives writing at once, causing brown-out resets. Evidence plan: correlate the timestamps of the link-down events (pciehp or Data Link Layer Link Active changes, AER Surprise Down if the ports support reporting it) across drives; check the backplane's power telemetry and the baseboard management controller's event log; scope the rail during a reproduction; check whether the drives' power state descriptors allow a lower-power state to cap peak current. If the drives support NVMe 2.4 voltage monitoring, its alerts and history could directly show an under-voltage at the device; confirm the drive implements it and how to read it in the NVMe Base Specification 2.4. Competing hypotheses to rule out: a shared PCIe switch reset, a thermal trip, a host-side reset initiated by error recovery on one port.

    A strong answer includes: "shared cause" reasoning; Unsafe Shutdowns as evidence of power loss; timestamp correlation across drives; power measurement; alternatives ruled out.

    Common weak answer: treating each drive's failure as a separate drive defect.

    Learn it in: Chapter 57, Chapter 47, 2026 NVMe 2.4 Updates.

  14. [Troubleshoot] An SSD model trains at Gen4 on every motherboard except one vendor's, where it trains at Gen4 but logs thousands of correctable errors per hour. The motherboard vendor says their board passed compliance. How do you proceed?

    Model answer

    Compliance testing shows each component meets the specification against reference channels; it does not guarantee that a particular transmitter, channel and receiver combination has margin. Treat it as an interoperability margin problem. Steps: capture the equalization exchange on both boards (which presets were requested and chosen at 16.0 GT/s, and whether the SSD's preset hints or the root port's requests differ); margin both directions on the failing board; check whether the channel on that board is longer or has more connectors; try another SSD model on the same board and the same SSD on a different board from the same vendor; check for platform firmware equalization overrides. Bring both vendors data, not blame: "on board X, lane 1 SSD→host has 30% of the margin seen on board Y, with preset P chosen".

    A strong answer includes: compliance versus interoperability; equalization presets as the likely mechanism; margining both directions; a neutral, evidence-based report to both vendors.

    Common weak answer: "It passed compliance, so it's the SSD."

    Learn it in: Chapter 54, Validation Engineering.

  15. [Trace] A new engineer flags an analyzer capture: "lanes are reversed and lane 3 has inverted polarity, the board is miswired." Is it a defect?

    Model answer

    Probably not. Polarity inversion (P and N swapped within a lane) is detected and corrected by the receiver during Polling, and lane reversal (lane 0 on one side connected to the highest lane on the other) is handled during Configuration; both exist precisely to make board routing easier, and support for them is part of normal training (lane reversal support has some optionality, so confirm both ends support it if the link width is reduced). The analyzer must be told about them (or detect them) to decode the traffic correctly; otherwise it will show garbage. The real questions are whether the link reached L0 at full width and speed, and whether errors appear. If yes, the board is fine and the capture setup needs adjusting.

    A strong answer includes: where in training each is handled; that both are legal routing choices; the analyzer configuration consequence.

    Common weak answer: opening a board defect.

    Learn it in: Chapter 8, Analyzer Training.

Transaction layer: TLPs, completions, tags and ordering

Seventeen questions on the packets themselves: legality, splitting, tags, ordering and what each rule protects. Most give you header fields to reason over.

  1. [Trace] While fetching data for a host Write command whose PRP1 is 0x2_0000_0F00, the SSD sends the request below. The root port logs an uncorrectable error and the command later fails. Find every problem.

    #DirTypeFieldsMeaning
    1Dev→HostMRd64Addr=0x2_0000_0F00 Len=0x080 (512 B) Tag=0x14 RID=0x0100Read 512 bytes of write data
    No completion for tag 0x14 is ever seen. The root port's AER Uncorrectable Error Status shows Malformed TLP.
    Model answer

    Two problems, at two layers. PCIe: 0x0F00 + 0x200 = 0x1100, so the request crosses a 4 KiB address boundary. Memory requests must not cross a 4 KiB boundary; a receiver that checks for this treats the TLP as Malformed (the check is optional for receivers, which is why some platforms tolerate it and others do not). A Malformed TLP is dropped, so no completion returns and the SSD will eventually see a Completion Timeout. NVMe: even if the platform accepted it, the read is wrong: PRP1 only describes the bytes from 0x0F00 to the end of that 4 KiB page; the next bytes of the buffer live at the address in PRP2 (or the PRP list), not at 0x2_0000_1000. So the request would have fetched someone else's memory. The fix in the controller's DMA engine is to split every transfer at PRP page boundaries, which also guarantees no request crosses 4 KiB.

    A strong answer includes: the boundary arithmetic; why no completion returns; the NVMe-level data-integrity bug hidden behind the PCIe error; why it might "work" on another platform.

    Common weak answer: spotting only the PCIe rule and missing that the data would have been wrong anyway.

    Learn it in: Chapter 11, Chapter 36, Module 34.

  2. [Trace] The SSD reads 512 bytes at 0x2_0000_1020 (Tag 0x12). The root complex returns three completions. Is the set legal? What single change to one row would make it illegal?

    #DirTypeFields
    1Dev→HostMRd64Addr=0x2_0000_1020 Len=0x080 Tag=0x12 RID=0x0100
    2Host→DevCplDLen=0x008 (32 B) ByteCount=0x200 LowerAddr=0x20 Tag=0x12 Status=SC
    3Host→DevCplDLen=0x040 (256 B) ByteCount=0x1E0 LowerAddr=0x40 Tag=0x12 Status=SC
    4Host→DevCplDLen=0x038 (224 B) ByteCount=0x0E0 LowerAddr=0x40 Tag=0x12 Status=SC
    Model answer

    Legal. Check each rule: (1) Byte Count is the number of bytes remaining including this completion: 512, then 512 − 32 = 480 (0x1E0), then 480 − 256 = 224 (0xE0). (2) Lower Address is the low 7 bits of the address of the first byte in each completion: 0x1020 → 0x20; 0x1040 → 0x40; 0x1140 → 0x40. (3) When a completer splits a read, every completion except the last must end on a naturally aligned Read Completion Boundary (64 bytes here): the first ends at 0x1040 and the second at 0x1140, both multiples of 64. (4) No completion carries more than the Max Payload Size (256 bytes). (5) The lengths add to 512. Ways to make it illegal: give row 3 a Byte Count of 0x200 (inconsistent with row 2); make row 2 carry 40 bytes (it would end at 0x1048, not on a 64-byte boundary); or make row 3 carry 288 bytes (above MPS). A requester that detects such inconsistencies typically treats the completion as Malformed or Unexpected.

    A strong answer includes: checking Byte Count, Lower Address, RCB alignment, MPS and the total in turn, with arithmetic.

    Common weak answer: "Completions must be 64 bytes each" (RCB constrains where splits fall, not the size of each completion).

    Learn it in: Chapter 52, Module 12, TLP Header Decoder.

  3. [Trace] The SSD reads the PRP list of a large Read command and gets this. Explain the cross-layer story and where you would look on the host.

    #DirTime (µs)TypeFieldsMeaning
    1Dev→Host0.0MRd64Addr=0x1_5000_0000 Len=0x010 Tag=0x05Read first 8 PRP list entries
    2Host→Dev0.9CplStatus=UR Tag=0x05 Completer=RCNo data; Unsupported Request
    3Dev→Host1.6MWr64Addr=0x1_2341_0230 Len=4CQE: Status = Data Transfer Error
    Model answer

    The first abnormal event is the UR completion: the root complex refused the device's read of 0x1_5000_0000. With the IOMMU enabled this address is an I/O virtual address (IOVA), and the most common reason for this outcome is that the IOMMU has no valid read mapping for it; on many platforms a translation fault on an untranslated request is answered with UR (the exact status is implementation-dependent). The SSD then behaved well: rather than hanging, it completed the command with Data Transfer Error. On the host look for the IOMMU fault record in the kernel log (it names the device 01:00.0, the faulting address and read versus write), then ask why the list page was not mapped: the driver never mapped it, unmapped it early (for example after a timeout and abort while the device still held the command), or wrote the wrong PRP2 into the SQE. Compare the faulting IOVA with the SQE's PRP2, which you can capture from the SQE fetch in the same trace.

    A strong answer includes: IOVA versus physical address; the IOMMU as the likely refuser; matching the faulting address to PRP2 in the SQE; the driver lifecycle questions.

    Common weak answer: "The SSD returned an error, so the SSD is broken."

    Learn it in: Chapter 20, Module 02, Chapter 47.

  4. [Troubleshoot] On an Arm server, a polling-mode NVMe driver occasionally completes a command with the wrong Command Identifier (CID). The analyzer shows every Completion Queue Entry (CQE) written as a single 16-byte MWr with correct contents. Where is the bug most likely, and why?

    Model answer

    On the host, in the order of the CPU's loads. The driver checks the phase tag in CQE dword 3 and then reads the CID (also dword 3) and SQ Head and SQ Identifier (dword 2). On a weakly ordered CPU those loads can be satisfied out of order: the CPU may read dword 2 or a stale cached copy before the load of the phase tag that "proved" the entry was new, giving a mix of old and new fields. The device side is cleared by the analyzer (one TLP, correct order). The fix is a read barrier for DMA memory (in Linux, dma_rmb()) between reading the phase tag and reading the rest of the entry, and reading the entry's fields only after the phase check. x86's stronger load ordering hides this bug, which is why it surfaces first on Arm.

    A strong answer includes: using the analyzer to exonerate the device; CPU load reordering; the specific barrier and where it goes; why x86 hides it.

    Common weak answer: "PCIe reordered the bytes" (contradicted by the single TLP).

  7. [Spec] A firmware engineer wants the SSD to issue a zero-length read to the host after the last data write of every Read command, "to be safe", before writing the CQE. What is a zero-length read, what does it guarantee, and is it needed here?

    Model answer

    A zero-length read is a Memory Read with Length = 1 dword and both byte enables zero; the completer returns one dword of undefined data. Because a read request may not pass earlier posted writes from the same requester in the same direction, and its completion comes back only after the request reached the completer, the returning completion tells the requester that its earlier posted writes have reached the completer's ordering point (useful, for example, to confirm delivery before signalling through a path that is not ordered with those writes). For an NVMe Read it is not needed: data MWrs and the CQE MWr are all posted writes from the same device on the same path, and PCIe ordering already prevents the CQE (sent without Relaxed Ordering) from passing the data, so the host cannot see the CQE before the data. The extra read would add a full round trip (on the order of a microsecond) to every command. It could be justified only for a path outside PCIe ordering, such as notifying the host through a separate agent.

    A strong answer includes: the definition (Length 1, byte enables zero); the ordering rule that makes it a flush; why NVMe completion ordering already covers the case; the latency cost.

    Common weak answer: "It reads nothing so it's free" or "it makes the data persistent" (it confirms delivery to the completer, not persistence in memory, unless the platform says so).

  8. [Performance] A tuning guide recommends raising the SSD's Max Read Request Size (MRRS) from 512 bytes to 4,096 bytes to speed up sequential writes. Will it help? Give the numbers and the side effects.

    Model answer

    For host Write commands, the SSD reads data from host memory, so MRRS sets how many read requests it needs. A 128 KiB write needs 256 MRds at 512 bytes or 32 at 4,096 bytes. The completions coming back are limited by the root complex's split behaviour and MPS (256 bytes), so the downstream data TLP count barely changes (about 512 CplDs either way). Upstream, 224 fewer request headers (24 bytes each with framing) is about 5 KB saved per 128 KiB: noise on the request direction, which is mostly idle during writes anyway. What matters is outstanding data: bandwidth × latency ≈ 7.9 GB/s × 1 µs ≈ 7.9 KB must be in flight, which is 16 requests at 512 bytes, well within 256 tags. So the gain is usually small unless the device is tag-limited or has a per-request overhead. Side effects: larger reads can hog completion bandwidth and increase latency for other devices sharing the root port; some platforms deliberately keep MRRS small for fairness (Linux's "performance" bus-tuning mode, for example, limits MRRS for this reason; check your kernel's documentation). Measure before and after.

    A strong answer includes: MRRS affects requests, not completion size; the count arithmetic; the bandwidth-delay product; the fairness side effect; measuring.

    Common weak answer: "8× bigger requests, 8× faster."

  9. [Troubleshoot] The SSD logs Completion Timeouts on its own read requests (in its AER status), but only when a memory-bandwidth benchmark runs on the other CPU socket. Host Writes then fail with Data Transfer Error. Explain and propose fixes.

    Model answer

    The SSD is the requester here: its MRds for write data go to host memory, and the completer is the root complex plus the memory system. If the write buffers live on the other socket's memory, each read crosses the inter-socket link to a memory controller that the benchmark is saturating, so completion latency stretches from about a microsecond to far longer. If it exceeds the SSD's Completion Timeout value, the SSD declares the request lost, fails the command with Data Transfer Error, and may later receive the late completion as an Unexpected Completion. Evidence: the gap between MRd and CplD in a trace during the benchmark; the buffer's NUMA node; the Completion Timeout range the SSD uses (Device Control 2, against the ranges it advertises in Device Capabilities 2; the default range allows tens of milliseconds, but a device may select a shorter one). Fixes: allocate I/O buffers on the SSD's local node and run the submitting threads there; use a longer timeout range if the device supports it; on the platform, memory bandwidth quality-of-service features if available. The root cause is an unbounded memory latency path, not the SSD.

    A strong answer includes: the SSD as requester; NUMA placement of buffers; the timeout configuration registers; the late completion becoming an Unexpected Completion; fixes on both host and device.

    Common weak answer: "Completion timeout means the SSD is hung."

  10. [Concept] A firmware optimisation posts the CQE of a host Write command as soon as the last MRd for its data has been sent, before all the CplDs have arrived. Why is this a data-integrity bug, even though PCIe ordering is respected?

    Model answer

    The CQE tells the host that the controller is done with the command's buffers. Once the host sees it, the application may free or overwrite the buffer. For a Write, the data travels host → device as completions to the device's reads; sending the MRd does not mean the data has been read yet. If the host reuses the buffer before the read reaches memory, the device fetches the new contents and writes them to the LBA: silent corruption. PCIe ordering does not help, because the CQE is a posted write going upstream while the completions come downstream; there is no ordering relationship between a device's posted write and the completions of its own earlier reads that would protect the buffer. The rule is simple: complete a Write only after all of its data has been received (and, if the data is to be protected by a power-loss mechanism, after it is safe). For Reads the situation is different, because data and CQE are both posted writes from the device in the same direction and ordering covers them.

    A strong answer includes: the CQE as buffer ownership transfer; direction of data for Writes; why ordering rules do not apply across the two directions; contrast with Reads.

    Common weak answer: "Posted writes can't pass reads, so it's fine."

  12. [Performance] A future SSD design uses a Gen5 x16 link and reads host memory through a path with about 4 µs of completion latency. With MRRS = 512 bytes, are 8-bit tags enough? What else must the designer size besides tags?

    Model answer

    Gen5 x16 raw bandwidth is 32 GT/s × 16 × 128/130 ÷ 8 ≈ 63 GB/s per direction. To keep it busy the device needs bandwidth × latency ≈ 63 × 109 × 4 × 10−6 ≈ 252 KB of reads in flight, which is about 490 requests of 512 bytes. 8-bit tags allow 256 outstanding requests, so the link would be capped at roughly half its rate. Options: enable 10-bit tags (1,024 outstanding; both the device and every component in the path must support them), or use larger requests if the platform allows a larger MRRS. Just as important: an endpoint must accept all the completions it asked for (endpoints advertise infinite completion credits), so it needs about 252 KB of completion buffering, or it must cap outstanding reads to what its buffer holds. The tag count and the completion buffer must be sized together.

    A strong answer includes: the bandwidth-delay product; the 256 versus 1,024 limit; end-to-end support for 10-bit tags; completion buffer sizing.

  13. [Spec] An SSD sends its MSI-X writes as MWr64 with address 0x0000_0000_FEE0_1000. They work on platform A; on platform B interrupts are lost. Who is wrong according to the specification?

    Model answer

    The SSD. Platform A happens to accept it; platform B may drop it or log it as an error, and neither is a platform defect. In the course's example system, MSI-X writes and BAR accesses are always MWr32, and host memory above 4 GiB uses MWr64.

  14. [Architecture] A team wants a network card to write received data directly into an SSD's Controller Memory Buffer (CMB) using peer-to-peer DMA. Both devices sit under the same PCIe switch, and Access Control Services (ACS) is enabled. What determines whether the traffic goes through the switch or up to the root complex, and what are the consequences?

    Model answer

    With ACS P2P Request Redirect enabled on the switch's downstream ports, peer requests are redirected upstream to the root complex so the IOMMU can check them, instead of being routed directly across the switch. Consequences: (1) bandwidth: the traffic crosses the switch's uplink twice, competing with all host traffic; (2) latency: more hops; (3) support: whether a root complex forwards peer-to-peer traffic between its ports is implementation-dependent, and some do not; (4) addressing: the network card must target an address the IOMMU translates to the SSD's BAR. Without redirect, the switch routes by address directly (fast), but the IOMMU no longer sees or controls the traffic, which matters for isolation between tenants. Linux's peer-to-peer DMA support computes whether a path is usable and refuses unknown root complexes by default. The decision is a security-versus-performance tradeoff, and it must be made explicitly.

    A strong answer includes: ACS redirect behaviour; double uplink crossing; implementation-dependent root complex support; the isolation tradeoff.

    Common weak answer: "Same switch, so it's direct" without asking about ACS.

  16. [Troubleshoot] After the platform enables End-to-End CRC (ECRC) checking, the root port logs ECRC errors for a small fraction of the SSD's TLPs. Without ECRC everything appears fine. How do you find out whether the errors are real corruption or an ECRC generation bug?

    Model answer

    ECRC covers the header and payload end to end, with the "variant" header bits that intermediate components may legally change treated as fixed values. A link corruption would almost always be caught first by the Link CRC (LCRC) and replayed, so ECRC errors with a clean link point either to corruption inside a component (switch or retimer buffers) or to the sender computing ECRC wrongly. Evidence: use the AER Header Log for each error to find what the failing TLPs have in common (type, attributes, length, the poisoned bit, an address range); if they share a header property, suspect generation logic (for example mishandling of a variant bit or a particular TLP type). Check whether a switch is in the path. Experiment: turn off ECRC generation on the SSD (in its AER capability) while keeping checking enabled, and see whether the errors vanish; compare the same SSD directly on a root port. Then verify data: write-read-compare runs will show whether payloads were ever really corrupted.

    A strong answer includes: LCRC catches link errors first; header-log pattern analysis; variant bits; isolating generation from checking; a data-integrity cross-check.

    Common weak answer: "Turn ECRC off since everything worked before."

  17. [Spec] BAR0 is 16 KiB at 0xFE60_0000. A diagnostic tool reads 0xFE60_3F00 and then 0xFE60_4000. What should happen for each, and what would you see?

    Model answer

    0xFE60_3F00 is inside the BAR: the SSD claims it, and it must complete the read successfully. In the example system this is beyond the MSI-X Pending Bit Array (at BAR0 + 0x3000) in space with no defined register; what a device returns there is its choice (typically zeros), and reserved NVMe register space reads as zero. 0xFE60_4000 is outside every BAR of the SSD. Fifteen questions on the layer that hides most link errors from software, and on credits, the quiet source of many throughput mysteries.

  1. [Trace] Which TLP was corrupted, which were retransmitted, and how many copies of each reached the root complex's Transaction Layer?

    #DirTime (ns)PacketFields
    1Dev→Host0TLPSeq=0x041 MWr64 data
    2Dev→Host36TLPSeq=0x042 MWr64 data
    3Dev→Host72TLPSeq=0x043 MWr64 CQE
    4Host→Dev180DLLPNAK Seq=0x041
    5Dev→Host230TLPSeq=0x042 (replay)
    6Dev→Host266TLPSeq=0x043 (replay)

    A NAK carries the sequence number of the last TLP received correctly, so NAK 0x041 acknowledges 0x041 and says 0x042 arrived corrupted (failed LCRC) or was otherwise bad. The transmitter replays every unacknowledged TLP in order from 0x042: rows 5 and 6. The original 0x043 (row 3) was discarded by the receiver because, after detecting a bad TLP, it only accepts the next expected sequence number (0x042). So the Transaction Layer received exactly one copy of each: 0x041 once, 0x042 once (row 5), 0x043 once (row 6). The analyzer shows two copies of 0x043 on the wire; a trace tool that does not de-duplicate replays will report a phantom duplicate CQE. Important ordering consequence: the CQE (0x043) still reached the host after the data (0x042), because replay preserves order.

    A strong answer includes: NAK semantics (last good); replay of all unacknowledged TLPs; receiver discarding out-of-sequence TLPs; analyzer de-duplication; ordering preserved.

    Common weak answer: "0x041 was corrupted because the NAK names it."

  2. [Trace] The analyzer shows the same SQ1 tail doorbell MWr (same address, same data 0x0000_0007) twice, 1.2 µs apart. A colleague says the driver rings the doorbell twice. What single field settles it, and what does each answer mean?

    Model answer

    The Data Link Layer sequence number. If both copies carry the same sequence number, the second is a replay: the transmitter (the root port) did not get an ACK in time, its replay timer expired, and it resent the TLP. The receiver recognises a duplicate sequence number, discards it and acknowledges it, so the controller sees one doorbell. Look for the missing or late ACK and for a Replay Timer Timeout correctable error at the root port. If the sequence numbers differ, these are two separate TLPs: software really wrote the doorbell twice with the same value. That is harmless to the controller (no new commands) but wasteful, and worth a look in the driver. Either way, a trace tool that counts doorbells must de-duplicate by sequence number first.

    A strong answer includes: sequence number as the discriminator; replay timer as the mechanism; receiver duplicate handling; the AER correlate.

    Common weak answer: "The controller will see 0 new commands either way, so it doesn't matter" (true for the controller, but it misses a link-health signal).

  3. [Troubleshoot] Under heavy read load only, the SSD's AER log shows REPLAY_NUM Rollover correctable errors, and the link occasionally enters Recovery. Which direction of the link is suspect, and what evidence confirms it?

    Model answer

Logged by the SSD, it means the SSD's transmissions (device → host: read data and CQEs, which is exactly the heavy direction during reads) are repeatedly not being acknowledged. Two mechanisms: the root port's receiver keeps rejecting them (look for Receiver Error and Bad TLP counts at the root port), or the ACKs coming back (host → device) are being corrupted or are late (look for Bad DLLP at the SSD and for long ACK latency at the root port). The first is the common case and localises to SSD transmitter → channel → root port receiver. Confirm with margining on the root port receiver lanes and with an analyzer capture showing NAKs from the root port.

    Common weak answer: "The SSD's receiver is bad" (the error is about its transmissions).

  4. [Performance] The root port advertises 32 posted header credits and 512 posted data credits (one data credit is 16 bytes). The credit-return loop (TLP sent → UpdateFC received) takes about 600 ns. With MPS = 256 bytes on Gen4 x4, can the SSD stream read data at full rate? What if the posted data credits were only 64?

    Model answer

    A 256-byte MWr64 occupies about 280 bytes on the wire, about 36 ns at ≈ 7.88 GB/s. To keep streaming, credits must cover everything sent during one credit-return loop: 600 ns ÷ 36 ns ≈ 17 TLPs, which is 17 headers and 17 × 16 = 272 data credits. 32 header and 512 data credits (8 KiB, or 32 full TLPs) are enough. With 64 data credits (1 KiB), only 4 full TLPs can be outstanding, so the SSD sends 4 TLPs and waits for credit: about 4 × 256 bytes per 600 ns ≈ 1.7 GB/s, a quarter of the link. In a trace you would see bursts of four TLPs followed by idle gaps that end right after each UpdateFC from the root port. Header and data credits must be balanced against MPS: 32 headers with 64 data credits would be data-limited, while 4 headers with 512 data credits would be header-limited.

    A strong answer includes: the credit-loop arithmetic; data credits in 16-byte units; the trace signature (bursts gated by UpdateFC); header/data balance.

    Common weak answer: "Credits just prevent overflow; they don't affect throughput."

  5. [Trace] The SSD's InitFC1 DLLPs advertise: Posted Header 0x40, Posted Data 0x400, Non-Posted Header 0x20, Non-Posted Data 0x20, Completion Header 0, Completion Data 0. A reviewer says the SSD "has no completion buffer". Respond.

    Model answer

    A value of zero in an initial flow-control advertisement means infinite credits for that type, not none. Endpoints are required to advertise infinite completion credits: since an endpoint only receives completions for requests it issued, it must reserve buffer before issuing each read instead of relying on credits. So the advertisement is normal. The real question the reviewer should ask is the one it implies: does the SSD limit its outstanding reads to the completion buffer it actually has? If the firmware issues more reads than it can buffer, it will overflow internally (the root port is entitled to send completions at full speed).     A strong answer includes: 0 = infinite; endpoints advertise infinite completion credits; the obligation that comes with it.

    Common weak answer: agreeing with the reviewer.

  6. [Spec] During a burst of I/O, the link to the SSD goes down for 40 ms and comes back. What happens to the posted doorbell writes and the outstanding MMIO reads that were in flight, and what state is the NVMe controller in afterwards?

    Model answer

    When the Data Link Layer reports DL_Down, TLPs not yet acknowledged are discarded rather than delivered later, so in-flight doorbell writes may or may not have reached the controller, and nobody is told which. Outstanding CPU reads to BAR0 get no real completion; the root port or root complex completes them with an error, which software usually sees as all ones (0xFFFF_FFFF), possibly with a Completion Timeout or Surprise Down logged. At the device, a link going down at its upstream port resets it (the base specification treats this like a conventional reset of the device; confirm the exact wording in its reset rules), so after the link returns, NVMe registers are at reset values: CC.EN = 0, CSTS.RDY = 0, all queues gone. Outstanding commands have an unknown outcome: a Write may or may not have reached media. The driver must reinitialise the controller, restore PCI state (BARs, MSI-X), and treat every outstanding command as indeterminate (retry if safe, else report).

    A strong answer includes: discard on DL_Down; all-ones reads; device reset; indeterminate commands; the full reinitialisation including PCI state.

  7. [Performance] Adding two retimers to a long Gen5 backplane drops sequential read throughput by 8% with zero errors. What Data Link Layer resource might be the limit, and how do you test the idea?

    Model answer

    The replay buffer and the flow-control credit loop. A transmitter must keep every TLP in its replay buffer until it is acknowledged, so it can only have "replay buffer size" bytes unacknowledged. The ACK round trip includes wire and retimer latency in both directions plus the receiver's ACK scheduling. At about 15.75 GB/s (Gen5 x4), each extra 100 ns of round trip needs about 1.6 KB more replay buffer to keep streaming; the same is true for posted credits at the receiver. If either was sized for a short channel, throughput drops with no errors. Test: measure ACK latency (time from TLP to the ACK that covers it) and UpdateFC timing in an analyzer with and without the retimers; look for transmitter idle gaps that end exactly when an ACK or UpdateFC arrives; compare with a short-channel setup. The fix is in buffer sizing (device or root port), not in the retimers.

    A strong answer includes: replay buffer as a bandwidth-delay limit; credits as a second candidate; quantifying per 100 ns; the trace signature; the experiment.

    Common weak answer: "Retimers add latency, so throughput falls" (latency alone doesn't cut throughput unless a window is too small).

  8. [Troubleshoot] The root port's AER shows hundreds of Bad TLP and Receiver Error events per hour; the SSD's AER shows none. Which direction is failing, and which component do you suspect first?

    Model answer

    Receiver-side errors are logged by the component whose receiver saw them. Errors at the root port mean traffic from the SSD to the host (upstream) is arriving damaged; the SSD's clean receiver means downstream traffic is fine. Suspects, in order: the SSD's transmitter equalization at its current preset, the channel in that direction (connector, specific pair), and the root port's receiver settings. A clean SSD log does not prove the SSD is innocent; it only clears the other direction. Two cautions: check that the SSD actually reports correctable errors (masks and enables), and that the root port's counters are not inflated by L1 exits. Then margin the root port's receiver per lane and swap drives and slots. Note the impact: each Bad TLP costs a replay, so read latency (upstream heavy) suffers more than write latency.

    A strong answer includes: receiver logs reflect the incoming direction; suspects in that direction; verifying the clean side's reporting is enabled; impact on reads versus writes.

    Common weak answer: "The root port is reporting errors, so the root port is bad."

  9. [Spec] A device architect proposes a replay buffer that can hold 4,096 small TLPs "to never stall on ACKs". What limit in the sequence-number scheme makes part of that buffer useless?

    Model answer

    Data Link Layer sequence numbers are 12 bits (0–4,095) and wrap. To keep acknowledgements unambiguous, a transmitter must stop sending new TLPs when the number of unacknowledged TLPs reaches half the sequence space, 2,048. So no more than 2,048 TLPs can ever be outstanding, and any capacity beyond that (counted in TLPs) is never used. In practice the byte size matters more than the TLP count: 2,048 TLPs of 280 bytes is about 570 KB, far more than any realistic ACK round trip needs. The right sizing argument is bandwidth × ACK round-trip time plus margin, as in the previous question. Also, the receiver's ACK behaviour (it may coalesce ACKs, within the spec's timing limits) affects how long TLPs sit in the buffer.

    A strong answer includes: 12-bit sequence numbers; the 2,048 outstanding limit; sizing by bandwidth-delay product instead.

    Common weak answer: "Bigger is always better."

    Learn it in: Chapter 15, Module 15.

  10. [Troubleshoot] After an SSD firmware update, the root port occasionally logs a Receiver Overflow; on another platform, the SSD logs a Flow Control Protocol Error. Explain the difference and what each implies about who is at fault.

    Model answer

    Receiver Overflow is logged by a receiver that got more TLPs (or data) than the credits it had advertised: the other side sent beyond its credit limit. At the root port, that implicates the SSD's transmitter credit accounting (for example, the new firmware miscounting data credits for TLPs of a certain size) or, less likely, a root port that advertised more credits than it can hold. A Flow Control Protocol Error is logged when the flow-control DLLPs received violate the rules (for example, an update that would leave more unused credits than the counter width allows, or inconsistent initialisation values). At the SSD, that implicates the root port's FC DLLPs or the SSD's checker. Both are uncorrectable errors that usually lead to a reset. Evidence: an analyzer with credit tracking will show the exact TLP that exceeded available credits, or the exact UpdateFC that broke the rules. Given the timing (after an SSD firmware update), the SSD's credit accounting is the first suspect for the overflow.

    A strong answer includes: who logs each error; which side each implicates; analyzer credit tracking; using the change history.

    Common weak answer: treating the two names as the same thing.

  11. [Troubleshoot] A prototype SSD's LTSSM reaches L0 at Gen4 x4, yet the root port's Data Link Layer Link Active bit stays 0 and configuration reads time out. What is the analyzer likely to show?

    Model answer

    L0 is a physical-layer state; the Data Link Layer still has to initialise flow control before it reports DL_Active. Initialisation is the exchange of InitFC1 and then InitFC2 DLLPs for posted, non-posted and completion credits in both directions. If the SSD never sends InitFC DLLPs (its Data Link Layer firmware or hardware is not started), or sends malformed ones, the root port's Data Link Layer stays in its initialisation state, no TLPs can flow, and configuration requests cannot be delivered. The analyzer would show L0 with only the root port's InitFC1 DLLPs repeating (and SKP ordered sets), and no InitFC from the SSD, or bad-CRC DLLPs from it. This localises the bug to the SSD's Data Link Layer bring-up, not to signal integrity.

    A strong answer includes: L0 versus DL_Active; the InitFC1/InitFC2 exchange; the expected trace; the localisation.

  12. [Concept] In a dispute, the SSD vendor says "our analyzer shows the doorbell was ACKed by the SSD at t = 0, so the 9 ms latency is the host's fault." What is wrong with the argument?

    Model answer

    An ACK DLLP means the SSD's Data Link Layer received the TLP intact and will pass it to its Transaction Layer. It says nothing about when the NVMe controller noticed the new tail value, fetched the commands, executed them or posted completions. The 9 ms must be broken into stages, each with its own evidence: doorbell → SQE fetch MRd (controller noticed the doorbell; device side), fetch → data movement (device internal), data → CQE (device), CQE → MSI-X (device), MSI-X → host CQ head doorbell (host). Only the last interval is clearly the host's. If the SQE fetch is the delayed interval, the device is responsible even though it ACKed the doorbell promptly.

    A strong answer includes: ACK meaning delivery at the Data Link Layer only; stage latencies; which party owns each stage.

    Common weak answer: accepting the ACK as proof of processing.

  13. [Performance] An analyzer shows one NAK per 10,000 upstream TLPs during 4 KiB random reads. Estimate the throughput and latency impact. Would you fix it?

    Model answer

    Each NAK causes the bad TLP and everything sent after it to be retransmitted. If around 16 TLPs are unacknowledged at the time (a realistic window), that is about 16 × 280 bytes ≈ 4.5 KB resent, plus a NAK turnaround of a few hundred nanoseconds. Throughput cost ≈ 16/10,000 ≈ 0.16% of the bandwidth: negligible. Latency: the commands whose TLPs were replayed are delayed by roughly 0.5–1 µs each; with 4 KiB reads (about 18 upstream TLPs per command) about 1 command in 500 is touched, so the effect appears around the 99.8th percentile as a sub-microsecond shift, invisible next to tens of microseconds of NAND time. Would I fix it? I would not treat it as a performance bug, but I would treat it as a margin signal: track whether the rate rises with temperature or age, because a link with no margin left fails suddenly. That is the senior distinction between "harmless now" and "healthy".

    A strong answer includes: replay window arithmetic; throughput versus tail latency; scale relative to NAND latency; the margin argument.

    Common weak answer: "Any NAK must be eliminated" or "NAKs don't matter."

  14. [Troubleshoot] Bad TLP and Receiver Errors appear only when ASPM L1 with L1 substates is enabled, and they cluster in the first microseconds after the link leaves L1. What is the likely mechanism, and which configuration values do you check?

    Model answer

    In the deeper L1 substates (L1.2) the link's common-mode voltages and possibly the reference clock (via CLKREQ#) are turned off. On exit, the receivers need time for the clock to return and the common mode to settle before traffic is reliable. That time is set by values the host programs in the L1 PM Substates capability on both ends (power-on time and common-mode restore time), derived from what each port advertises. If the host programmed a value shorter than one side needs, or the platform's CLKREQ# and clock-enable timing is slow, the first symbols after exit are received badly, producing exactly this cluster. Check: the advertised and programmed L1 substates timing values on both ends (lspci shows them); the platform's CLKREQ# routing; whether errors stop when only L1.2 is disabled (keeping L1.1). Also check Latency Tolerance Reporting (LTR) values, which control whether L1.2 is entered at all.

    A strong answer includes: what L1.2 turns off; exit timing parameters on both ends; the targeted experiment (disable L1.2 only); LTR.

    Common weak answer: "Disable ASPM" as the fix, with no mechanism (it costs idle power).

  15. [Trace] In an upstream capture you notice that the SSD sends an ACK only after every eight TLPs from the root port, and the root port occasionally logs Replay Timer Timeout. Is ACK coalescing legal, and how could it cause these timeouts?

    Model answer

    ACK coalescing is legal: one ACK acknowledges every TLP up to its sequence number, and receivers are allowed to schedule ACKs, within limits set by the specification's ACK latency rules (which depend on link speed, width and payload size; check the base specification's Data Link Layer tables). Coalescing becomes a problem when the receiver waits too long: if the root port sends only a few TLPs and then pauses, the SSD may hold its ACK waiting for "eight", and the root port's replay timer, which assumes the receiver follows the ACK latency limits, expires and triggers an unnecessary replay. The symptom is Replay Timer Timeouts without Bad TLP or NAKs, mostly at low traffic. Evidence: time from the last TLP of a short burst to the covering ACK compared with the replay timer; the fix is in the SSD's ACK scheduling (send an ACK when the link goes quiet, not only every N TLPs).

    A strong answer includes: legality of coalescing within latency limits; the low-traffic failure mode; Replay Timer Timeout without NAKs as the signature; the timing measurement.

    Common weak answer: "Every TLP must be ACKed individually."

  3. [Spec] During BAR sizing you write all ones to BAR0 and BAR1 and read back 0xFFFF_C004 and 0xFFFF_FFFF. Decode the BAR, and name two mistakes that make BAR sizing dangerous on a live system.

    Model answer

    Low dword 0xFFFF_C004: bit 0 = 0 → memory BAR; bits 2:1 = 10b → 64-bit, so BAR1 holds the upper half; bit 3 = 0 → non-prefetchable. Masking the four type bits gives 0xFFFF_C000; combined with the upper 0xFFFF_FFFF the size is the two's complement: 0x4000 = 16 KiB. That matches the example system. Dangers: (1) sizing while Memory Space Enable is set: for a moment the BAR decodes an all-ones address and can capture or answer accesses meant for something else, so disable memory decode first; (2) forgetting to restore the original value (or restoring only one half of a 64-bit BAR), which moves the registers under a running driver. A third: sizing while the device is doing DMA or while another agent (a hypervisor, firmware) is using the BAR. Tools like setpci make all of these easy to do by accident.

    A strong answer includes: the decode bit by bit; the size arithmetic across both dwords; disabling decode; restoring both halves.

    Common weak answer: reading the size as 0xC000 bytes, or ignoring the upper dword.

  4. [Trace] After a Function Level Reset, configuration reads of the SSD return Configuration Request Retry Status (CRS) for 600 ms before succeeding. A platform team files a bug saying the SSD "violates the 100 ms rule". Do you agree?

    Model answer

    Not as stated. The 100 ms figure is how long software must wait after a reset before it may send configuration requests (after a Function Level Reset, the wait before the function is expected to be usable is also on the order of 100 ms). It is not a deadline for the device to be fully ready.   6. [Trace] A 16 KiB Read (namespace 1, 512-byte LBAs) fails with Data Transfer Error and an IOMMU write fault at IOVA 0x2_0000_5000. From the evidence below, who is wrong: the driver or the controller?

    SQE:  Opcode=02h (Read)  NSID=1  SLBA=0x1000  NLB=0x001F (32 blocks = 16 KiB)
      PRP1=0x2_0000_0200      PRP2=0x1_5000_0000 (PRP list)
PRP list page at 0x1_5000_0000:
      [0] 0x2_0000_1000   [1] 0x2_0000_2000   [2] 0x2_0000_3000   [3] 0x2_0000_5000  (stale)
IOMMU mappings for this I/O: 0x2_0000_0000 - 0x2_0000_3FFF (4 pages)
IOMMU fault: DMA write, device 01:00.0, IOVA 0x2_0000_5000
    Model answer

    The driver. PRP1 has an offset of 0x200, so the first page holds only 4,096 − 512 = 3,584 bytes. The remaining 16,384 − 3,584 = 12,800 bytes need three full pages (12,288) plus 512 bytes of a fourth: five pages in total, so the list needs four entries. The driver built only three valid entries and mapped only four pages, as if the buffer started on a page boundary (it computed 16 KiB ÷ 4 KiB = 4 pages and forgot the offset). The controller correctly used entry [3] for the final 512 bytes; that slot held a stale address from an earlier command, which was not mapped, so the IOMMU blocked the write and the controller reported Data Transfer Error. Without an IOMMU this would have silently overwritten memory at 0x2_0000_5000. The fix: count pages as ceil((offset + length) / page size), and fill and map every entry.

  7. [Troubleshoot] After moving a database to confidential virtual machines, NVMe throughput drops by 40% and perf shows much of the CPU time in a function that copies bounce buffers. What is happening, and what are the options?

    Model answer

    In confidential computing, guest memory is encrypted and private to the guest; a device cannot DMA into it directly. The guest therefore routes DMA through shared (unencrypted) bounce buffers using the kernel's software I/O translation layer (swiotlb): every read is DMAed into the bounce buffer and then copied into private memory by the CPU, and every write is copied out first. That doubles memory traffic and burns CPU, which matches the profile. The same symptom appears outside confidential computing when a device's DMA mask is too small or the IOMMU is off on a system with memory above the device's reach. Options: confirm the cause (the guest's swiotlb use, the DMA mask); size the bounce pool so it never runs out (running out causes I/O failures); use larger I/Os to amortise per-I/O overhead; and evaluate trusted device assignment based on the TEE Device Interface Security Protocol (TDISP), where a device that is admitted into the trust boundary can DMA into private memory without bouncing (platform and device support required).

    A strong answer includes: why bounce buffers exist; the cost mechanism; the non-confidential causes; the TDISP direction.

  8. [Spec] An SSD supports Address Translation Services (ATS) and caches translations. The host unmaps a buffer after an I/O completes and immediately reuses the page for another process. What protocol makes this safe, and what device bug would make it unsafe?

    Model answer

    When the IOMMU changes a mapping, it sends an Invalidation Request message to the device; the device must remove the matching entries from its Address Translation Cache, make sure no requests using the old translation are still in flight, and then send an Invalidation Completion. The host must wait for that completion before reusing the page. The dangerous device bug is to send the Invalidation Completion as soon as the cache entry is dropped, while DMA that already used the old translated address is still queued inside the device or on the link. That DMA then lands in the reused page, which now belongs to another process: corruption and a security breach, with no IOMMU fault (translated requests bypass the IOMMU's page walk). Validation must test invalidation under load, with DMA in flight to the page being invalidated, and check the new owner's data.

    A strong answer includes: the invalidation handshake; the host waiting for completion; in-flight DMA as the hazard; why the IOMMU cannot catch it; a targeted test.

  9. [Troubleshoot] A custom driver's unbind path clears Bus Master Enable first and then sets CC.SHN for a normal shutdown. Some drives report an unsafe shutdown at next power-up, and one hangs. Explain.

    Model answer

    The order is backwards. Clearing Bus Master Enable forbids the device from issuing any memory requests, including the posted writes it needs to finish outstanding commands (data and CQEs) and anything it does as part of shutdown processing. The controller may then be unable to complete in-flight I/O, so it cannot cleanly finish the shutdown; CSTS.SHST never reaches "shutdown complete", the driver gives up, and power is removed with the drive in an inconsistent state, so it counts an unsafe shutdown. Some firmware stalls waiting on DMA that can never be issued. The correct order: stop submitting I/O and drain or abort outstanding commands; delete I/O queues (optional but tidy); set CC.SHN to normal shutdown and wait for SHST to show complete (bounded by the controller's advertised entry latency); only then disable interrupts, clear Bus Master Enable and release resources.

  12. [Architecture] A team wants to pass an NVMe SSD through to a virtual machine with VFIO, but VFIO refuses because the SSD's IOMMU group also contains a network card. Explain why the group exists and what the options are.

    Model answer

    An IOMMU group is the smallest set of devices the kernel can isolate from each other. If two devices sit under a switch or root port that lacks Access Control Services (ACS), one can send peer-to-peer requests to the other without passing through the IOMMU, so they cannot be safely given to different owners and are grouped together. Assigning only the SSD would let the VM's SSD DMA reach the host's network card. Options: move the SSD to a slot whose path has ACS (or a different root port); assign the whole group to the VM; use platform firmware that enables ACS on the switch; or use a kernel ACS override, which is unsafe because it lies to the kernel about isolation and should never be used where tenants are untrusted.   13. [Coding] Write a function that walks the standard capability list of a configuration space image and returns (offset, capability ID) pairs. It must not hang on a corrupted list. Show test data.

    Model answer 
    def walk_capabilities(cfg: bytes) -> list:
    """Return [(offset, cap_id)] for the standard capability list in a
    256-byte (or larger) configuration space image."""
    if len(cfg) < 64:
        raise ValueError("need at least the 64-byte header")
    status = cfg[0x06] | (cfg[0x07] << 8)
    if not status & 0x0010:                 # Capabilities List bit
        return []
    caps, seen = [], set()
    ptr = cfg[0x34] & 0xFC                  # low two bits are reserved
    while ptr:
        if ptr < 0x40 or ptr + 1 >= min(len(cfg), 256):
            raise ValueError(f"pointer 0x{ptr:02x} outside capability area")
        if ptr in seen:
            raise ValueError(f"loop detected at 0x{ptr:02x}")
        seen.add(ptr)
        caps.append((ptr, cfg[ptr]))
        ptr = cfg[ptr + 1] & 0xFC
    return caps

if __name__ == "__main__":
    cfg = bytearray(256)
    cfg[0x06] = 0x10                        # Status: capabilities present
    cfg[0x34] = 0x40

    cfg[0x50:0x52] = bytes([0x05, 0x70])    # MSI -> 0x70
    cfg[0x70:0x72] = bytes([0x10, 0xB0])    # PCI Express -> 0xB0

  14. [Architecture] An SSD exposes a Controller Memory Buffer in a 64-bit prefetchable BAR, and the driver places submission queues there, mapped write-combining. What ordering problem must the driver solve, and is "prefetchable" appropriate for the CMB?

    Model answer

    Prefetchable is appropriate if reads of the CMB have no side effects and writes can be merged, which is how CMB memory is meant to behave (it is memory, unlike the register BAR). Write-combining lets the CPU send a 64-byte SQE as a few large writes instead of many small ones, which is the point of putting SQs in the CMB. The ordering problem: write-combined stores sit in CPU buffers and may be emitted late or in a different order relative to the uncached doorbell write. If the doorbell reaches the controller before the SQE bytes, the controller fetches an incomplete SQE from its own memory. The driver must flush or fence the write-combining buffers (on x86, a store fence; in Linux, the appropriate write barrier for I/O memory) after writing the SQE and before ringing the doorbell. Also check the CMB's advertised supported uses (submission queues, completion queues, data) and its size and location fields before using it, and remember the CMB lives behind the device's BAR, so it disappears on reset.

    A strong answer includes: why prefetchable fits memory but not registers; what write-combining buys; the fence before the doorbell; checking CMB capabilities; reset behaviour.

    Common weak answer: "PCIe orders posted writes, so no fence is needed" (the reordering happens in the CPU before PCIe).

  16. [Architecture] A user-space storage engine maps all I/O buffers once at startup into the IOMMU, while the kernel driver maps and unmaps each I/O. Compare the two for performance, safety and debuggability.

    Model answer

    Per-I/O mapping (kernel default with a translating IOMMU): every I/O creates IOMMU page-table entries and later invalidates them. Invalidation of the IOMMU's translation cache is costly, so kernels batch it ("lazy" mode), trading a window in which a device could still reach freed memory for speed; "strict" mode closes the window at more CPU cost. Safety is good: the device can only reach buffers of in-flight I/O. Debuggability is good: stray DMA faults immediately with an address. Persistent mapping (typical of user-space drivers using pinned huge pages): no per-I/O IOMMU cost and very low CPU per I/O, but the device can reach the whole pool at any time, so a stale PRP entry or a late DMA after an abort corrupts another buffer in the pool silently. Mitigations for the persistent model: per-buffer ownership tracking in software, poison patterns in free buffers, and checks that completions refer to buffers still owned by the command.

    A strong answer includes: invalidation cost; lazy versus strict; the protection window; silent corruption risk with persistent maps; compensating checks.

    Common weak answer: "Persistent mapping is faster, so it is better."

  3. [Spec] The driver clears CC.EN while 200 Write commands are outstanding. Afterwards it re-enables the controller. What can it assume about those writes?

    Model answer

    Almost nothing. Clearing CC.EN is a Controller Reset: the controller stops processing commands, deletes all I/O queues and does not post completions for commands that were outstanding. For each Write, any outcome is possible: not started, partially written (some LBAs new, some old, within the limits of the namespace's atomicity guarantees), or completely written. The host must treat every outstanding command as indeterminate. Safe recovery: re-issue Writes that are idempotent (rewriting the same data to the same LBAs is safe); for anything else, the upper layer (file system journal, database log) must reconcile. Also note: data already acknowledged with a successful completion before the reset is subject to the volatile write cache rules; a Controller Reset does not by itself lose cached data on a well-behaved controller, but only a Flush or FUA gives the guarantee. A normal shutdown (CC.SHN) before disabling is how an orderly host avoids this situation.

    A strong answer includes: indeterminate outcome; partial writes bounded by atomicity; idempotent retry; distinguishing acknowledged-and-cached from outstanding.

The fix is to zero the CQ memory (at least the phase bits) before Create I/O Completion Queue (or before enabling the controller, for the admin CQ), and to reset the driver's expected phase to 1 and head to 0 whenever a queue is created.   10. [Performance] At 1.5 million IOPS, a trace shows one SQ tail doorbell write per command. Quantify the cost on the link and on the CPU, and say when batching helps and when it hurts.

    Model answer

    Link: a doorbell is an MWr32 with a 12-byte header, 4 bytes of data and about 8 bytes of framing, roughly 24 bytes, so 1.5 M/s × 24 B ≈ 36 MB/s downstream, under 1% of Gen4 x4. The link is not the issue. It hurts latency when the driver waits to accumulate a batch: at low queue depth a delayed doorbell adds directly to latency.   11. [Spec] A virtualisation-focused controller reports CAP.DSTRD = 2. Compute the offsets of the SQ3 tail and CQ3 head doorbells, and explain why a controller would choose a stride larger than 4 bytes.

    Model answer

  12. [Troubleshoot] In a cloud VM whose NVMe controller is emulated and uses shadow doorbells (the Doorbell Buffer Config command), a command occasionally sits unprocessed until the next command is submitted on the same queue. Explain the race and the fix.

    Model answer

    With shadow doorbells, the driver writes the new tail into a shadow buffer in host memory and performs a real MMIO doorbell write only if the new value crosses the "event index" the controller published (the controller polls the shadow buffer while it is active and updates the event index to say when it wants to be notified). The race: the driver writes the shadow tail, then reads the event index to decide whether to ring. If those two operations are reordered (no full memory barrier between the store and the load), the driver can read an old event index, conclude no MMIO is needed, while the controller, having just gone idle, does not see the new shadow value. The command sits until the next submission rings the doorbell. The same pattern applies to the CQ head. The fix is a full barrier between updating the shadow value and reading the event index (store–load ordering, which even x86 does not guarantee without a fence), on both sides of the protocol.

  13. [Architecture] When would you put I/O submission queues in the Controller Memory Buffer rather than host memory, and what do you give up?

  15. [Concept] A team configures weighted round robin with an urgent priority class for their latency-sensitive SQ, but its tail latency is unchanged under a heavy background load on other SQs. Why might arbitration not help?

  16. [Coding] Write helpers for a trace checker: the BAR0 offset of SQ y tail and CQ y head doorbells for any DSTRD, the number of used entries in a ring, and a validator that says how many commands a tail write publishes or rejects it.

    Model answer 
    def sq_tail_db(qid: int, dstrd: int) -> int:
    """BAR0 offset of the Submission Queue y Tail Doorbell."""
    return 0x1000 + (2 * qid) * (4 << dstrd)

def cq_head_db(qid: int, dstrd: int) -> int:
    """BAR0 offset of the Completion Queue y Head Doorbell."""
    return 0x1000 + (2 * qid + 1) * (4 << dstrd)

def used(head: int, tail: int, size: int) -> int:
    """Entries published but not yet consumed (0 .. size-1)."""
    return (tail - head) % size

def check_tail_write(old_tail: int, new_tail: int, head: int, size: int) -> int:
    """Return how many new SQEs a tail write publishes, or raise."""
    if not 0 <= new_tail < size:
        raise ValueError(f"tail {new_tail} outside a {size}-entry queue")
    added = (new_tail - old_tail) % size
    if used(head, old_tail, size) + added > size - 1:
        raise ValueError("write would overrun the head: queue holds at most size-1")
    return added

            print("rejected:", e)

    Design points: all ring arithmetic is modulo the queue size; the "at most size − 1 entries" rule distinguishes full from empty; a tail equal to or beyond the size is invalid; and the validator needs the head, which a trace checker reconstructs from the SQ Head Pointer field of CQEs (it lags the true controller head, so a checker should allow for that by treating a violation as "suspect" until confirmed).

    A strong answer includes: correct offsets for any stride; modulo arithmetic; the full/empty rule; the head-lag caveat for traces.

    Common weak answer: new_tail - old_tail without modulo.

  17. [Spec] A 30 TB SSD takes 25 seconds after power-up before its media is usable. The vendor says the controller supports reporting ready "independently of media". What does that change for the host, and what must the driver handle?

    Model answer

    NVMe 2.x defines controller ready modes: in the traditional mode, CSTS.RDY = 1 means the controller and its attached namespaces are ready; in the "ready independent of media" mode (enabled by the host through a CC bit when CAP says it is supported), RDY can become 1 before the media is ready, so the host can bring up admin queues, read Identify data, set features and collect logs early. Separate timeouts for the two modes are reported in the Controller Ready Timeouts register (check the NVMe Base Specification for the exact fields and units). The driver must then handle I/O to namespaces that are not ready yet: such commands complete with Namespace Not Ready status, typically with Do Not Retry clear and possibly a Command Retry Delay, and the host should wait for the namespace to report ready (the base specification describes how readiness is indicated per namespace) rather than failing the device. A driver unaware of this mode may misread early Namespace Not Ready errors as a dead drive.

    A strong answer includes: the two modes; host opt-in; separate timeouts with a pointer to confirm fields; Namespace Not Ready handling; the risk for older drivers.

    Common weak answer: "Set a longer CAP.TO wait."

  18. [Troubleshoot] After a controller reset during error recovery, a system never again receives asynchronous event notifications (no temperature warnings, no namespace change notices), although the drive later overheats. What did the driver forget, and what second mechanism also suppresses events?

    Model answer

    Asynchronous events are delivered by completing an outstanding Asynchronous Event Request command. A controller reset aborts all outstanding commands, including the AERs, and the controller cannot report anything until the host submits new ones. The driver forgot to resubmit its AER commands (up to the limit in Identify Controller) after re-initialising the admin queue, and to re-apply the Asynchronous Event Configuration feature if needed. The second mechanism: after reporting an event of a given type, the controller masks further events of that type until the host reads the associated log page (without the Retain Asynchronous Event bit). If an earlier event's log page was never read, that event type stays masked even with AERs outstanding. Evidence: count outstanding AER commands in the admin queue after recovery, check the feature configuration, read the logs.

    A strong answer includes: AER as an outstanding command; reset aborting it; resubmission; masking until the log page is read; checking configuration.

    Common weak answer: "The drive stopped reporting events."

    Learn it in: Chapter 44, Chapter 26, Module 39.
