Two hundred senior-level interview questions on Non-Volatile Memory Express (NVMe) over Peripheral Component Interconnect Express (PCIe). Almost every question hands you evidence (a trace excerpt, a register dump, a log line, a piece of code or a set of numbers) and asks you to reason from it. Each one has a hidden model answer, what a strong answer includes, the weak answer interviewers hear most often, and a link to the chapter that teaches it.

Who this bank is for and how to use it

This bank is for engineers preparing for a senior role: the person a team calls when a field failure crosses layers, when two vendors blame each other, when a validation plan needs an owner, or when a performance number does not add up. At this level the interviewer rarely asks "what is X?". They ask "here is what we saw; what happened, how sure are you, and what would you do next?"

What the senior level tests

  • Ambiguous field failures. Symptoms with several plausible causes, where the skill is ranking hypotheses and choosing the experiment that separates them.
  • Cross-layer root cause with evidence. Moving between the physical layer, the Data Link Layer, Transaction Layer Packets (TLPs), NVMe queues and commands, the Linux driver and the application, and saying which evidence belongs to which layer.
  • Validation strategy. Designing tests that target a mechanism, with an oracle that can actually fail.
  • Performance tuning. Doing the arithmetic (link efficiency, Little's law, tags and credits) before touching a knob.
  • Firmware and driver interaction. Who owns which state, and what happens at the boundaries: reset, power transitions, timeouts and aborts.
  • Specification judgement. Separating what the specification requires (Normative) from what you infer (Derived) and what an implementation chooses (Implementation-dependent).
  • Leading a debug effort. Organising people, evidence and communication when the answer is not yet known.

How to use the bank

  1. Pick a section. Read a question and its evidence. Cover the answer.
  2. Answer aloud or on paper in about five minutes. Use the shape claim → mechanism → evidence → limits → next step taught on the Interview Academy hub page.
  3. Open the model answer. Compare the shape first, then the facts. Did you name the first abnormal event? Did you say how you would confirm it?
  4. Score yourself with the scoring guide near the end. Anything below 3 sends you to the linked chapter before you retry in a few days.
  5. Work through all twelve sections before the mastery gate. A real loop picks one or two questions per section.

PCIe link and physical layer

Senior physical-layer questions are about localisation and judgement: which side, which lane, which condition, and whether a number is actually a problem. Fifteen questions.

  1. [Trace] A Gen4-capable SSD in a Gen4 slot comes up at 8.0 GT/s. The analyzer's Link Training and Status State Machine (LTSSM) view shows this. What happened, and what do you check next?

    #TimeStateRateNotes
    10 msDetect → Polling2.5 GT/sReceivers detected on lanes 0–3
    20.4 msConfiguration → L02.5 GT/sx4 negotiated
    30.6 msRecovery.Speed → L08.0 GT/sEqualization phases 0–3 complete at 8.0 GT/s
    41.3 msRecovery.Equalization16.0 GT/sPhase 2 ends without a usable preset on lane 2
    53.1 msRecovery.Speed → L08.0 GT/sBack to 8.0 GT/s; no further speed-change attempts
    Model answer

    The link trained normally, changed speed to 8.0 GT/s, then attempted 16.0 GT/s. Equalization at 16.0 GT/s failed (row 4 is the first abnormal event: lane 2 could not reach an acceptable preset), so the ports fell back to the highest rate that worked. Nothing at the NVMe layer is wrong; the drive simply runs at half the link bandwidth (about 3.9 GB/s instead of about 7.9 GB/s per direction before protocol overhead). Next: read Link Capabilities and Link Status on both the root port and the SSD to confirm the speed; read the Physical Layer 16.0 GT/s extended capability status on both ends to see which equalization phases completed; check Link Control 2 Target Link Speed in case firmware capped it; check for a riser, retimer or cable; use lane margining at 8.0 GT/s to see whether lane 2 is already marginal; and swap slot and drive to see whether the failure follows the lane or the part.

    A strong answer includes: the first abnormal event (row 4, not row 5); a per-lane hypothesis; checking both link partners; the bandwidth consequence in numbers; a swap experiment.

    Common weak answer: "The SSD only supports Gen3" (contradicted by the speed-change attempt) or "update the SSD firmware" without evidence.

    Learn it in: Chapter 9, Chapter 54, Module 09.

  2. [Troubleshoot] In a fleet, about 3% of boots bring a U.2 SSD up at x2 instead of x4. After a warm reboot it is usually back at x4. How do you investigate?

    Model answer

    Width is decided in Detect and Configuration: a lane that does not detect a receiver, or that fails to exchange training sets during Configuration, is dropped and the link forms on the lanes that work (x2 is the natural fallback for an x4 link). Intermittent loss of one or two lanes at power-up points to a lane that is marginal at a specific moment: connector or cable contact, reference clock arrival time, the device's PHY coming out of reset late, or receiver detection being sensitive to AC-coupling and temperature. Evidence: log Link Status (Negotiated Link Width) at every boot along with slot, drive serial, cable and temperature; capture the LTSSM in Detect and Configuration on a failing boot (trigger on width < x4) to see which lanes dropped out; check whether it is always the same lanes (a hardware path) or random (timing). Swap cable and slot, and compare cold boots with warm reboots, because a warm reboot may not cycle power to the drive.

    A strong answer includes: where width is decided in the LTSSM; per-lane identification; separating cold from warm boot; fleet data to find the common factor.

    Common weak answer: "Reseat the drive and close the ticket", which hides a recurring hardware defect.

    Learn it in: Chapter 8, Module 08, Failure Library.

  3. [Spec] A monitoring script alerts whenever Link Bandwidth Management Status or Link Autonomous Bandwidth Status gets set on the root port above an SSD. Which of the two is worth an alert, and why?

    Model answer

    The two bits record different reasons for a speed or width change. Link Autonomous Bandwidth Status says the hardware changed the link speed or width on its own for a reason other than reliability (for example power management). Link Bandwidth Management Status says that a link retraining requested by software completed, or that the hardware changed speed or width because of a reliability problem. So Link Bandwidth Management Status deserves the alert when software did not just request a retrain; Link Autonomous Bandwidth Status is usually informational. Both bits are write-1-to-clear in Link Status, so the script must clear them after reading or it will alert forever. Pair the alert with the current speed and width and with AER correctable counters, so the alert says what changed.

    A strong answer includes: the reliability versus autonomous distinction; that a software retrain also sets the management bit; clearing the bits; adding context.

    Common weak answer: treating both as errors, or not knowing that software retraining sets one of them.

    Learn it in: Chapter 18, Chapter 69.

  4. [Trace] A link monitor reports 4,000 entries into the Recovery state per hour on an SSD that has no errors and normal performance. A colleague wants to raise a hardware defect. What do you ask first?

    Model answer

    "Is Active State Power Management (ASPM) L1 enabled?" Exiting L1 goes through Recovery before the link returns to L0, so every idle-to-active transition counts as a Recovery entry. A drive that idles between bursts can enter and exit L1 thousands of times an hour with no fault. Distinguish the cases: compare Recovery entries with L1 entries (they should match one to one if L1 explains them); look at what precedes each Recovery: an electrical idle exit after L1 is normal, while Recovery entered from L0 after NAKs, a replay timeout or framing errors is not; and check AER correctable counters (Receiver Error, Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover). If correctable counters are zero and every Recovery follows an L1 exit, there is no defect. The cost to watch is latency on the first request after idle, not reliability.

    A strong answer includes: L1 exit through Recovery; classifying Recovery entries by what preceded them; using AER counters as a cross-check.

    Common weak answer: "Recovery means the link is bad."

    Learn it in: Chapter 50, Chapter 8, Module 42.

  5. [Concept] A platform adds a retimer between the root port and a Gen5 SSD. The firmware team asks whether the retimer is "transparent" and can be ignored when debugging. What do you tell them?

    Model answer

    A retimer is transparent to the Data Link and Transaction Layers: it does not ACK TLPs, hold a replay buffer or change sequence numbers, and software does not enumerate it as a function. It is not transparent at the physical layer: it recovers the clock and re-drives the signal, participates in link equalization (each segment is equalized separately), forwards ordered sets with adjustments, and adds latency in each direction. For debugging this means: a link problem may live on either segment; correctable errors reported by the root port do not tell you which segment caused them; analyzer placement matters (an interposer on the SSD side of the retimer sees a different electrical segment from one on the root-port side); and the Link Status 2 register can report that a retimer was detected, which is worth recording in every bug report. Some retimers expose their own diagnostics through vendor channels.

    A strong answer includes: transparent to DLL and TL but active in the physical layer; two equalized segments; analyzer placement; recording retimer presence.

    Common weak answer: "It's just a buffer, ignore it" (that describes a redriver more closely, and even a redriver changes signal integrity).

    Learn it in: Chapter 5, Chapter 54, Module 07.

  6. [Troubleshoot] Lane margining on a Gen4 x4 link gives this table at room temperature. The link shows a few correctable Receiver Errors per day. What do you conclude, and what do you not conclude?

    Lane  Timing margin (steps, left/right)   Voltage margin (steps, up/down)
 0        14 / 15                               12 / 13
 1        15 / 14                               13 / 12
 2         5 /  6                                4 /  5
 3        14 / 14                               12 / 12
    Model answer

    Lane 2 at the root port's receiver has roughly a third of the margin of its neighbours in both timing and voltage. That localises the weakness to one direction (SSD transmitter → root port receiver) and one lane, and it is the best candidate for the Receiver Errors. What I do not conclude yet: whether the SSD's transmitter, the board trace, the connector or the root port's receiver is at fault; and whether the margin is "out of spec", because margining reports steps whose size and meaning come from each receiver's advertised capabilities, so steps are not directly comparable between different devices. Next: margin the other direction (the SSD's receiver, if it supports margining); repeat at high temperature; swap the drive into another slot and another drive into this slot; and confirm the error counters by lane if the platform exposes them. If the weak lane follows the slot, it is the board or root port side; if it follows the drive, it is the drive or its connector.

    A strong answer includes: per-lane, per-direction localisation; caution about step units; repeating under temperature; a swap to separate board from drive.

    Common weak answer: "Lane 2 is bad, replace the SSD."

    Learn it in: Chapter 54, Module 07, Module 09.

  7. [Concept] An SSD in an external enclosure works on one host but logs bursts of Receiver Errors on another. The enclosure gets its reference clock locally rather than from the host cable. What clocking question do you ask, and why does it matter?

    Model answer

    "Are both ends configured for separate reference clocks, and is spread-spectrum clocking enabled on either side?" With a common reference clock, both ends run at exactly the same frequency (spread together), so the elastic buffers only absorb small drift. With separate clocks, the frequency difference can be larger, especially if one side spreads its clock and the other does not; the architecture that allows separate clocks with spread spectrum (Separate Reference Clocks with Independent Spread, SRIS) requires SKP ordered sets to be sent more often so the receivers' elastic buffers can compensate. If one side assumes common clock and the other runs from an independent spread clock, the elastic buffer underflows or overflows periodically, which appears as Receiver Errors and replays in bursts that may follow the spread modulation. Evidence: SKP ordered set intervals in the analyzer, the SRIS configuration in platform firmware, and whether the errors stop when spread spectrum is disabled on the enclosure.

    A strong answer includes: common clock versus separate clock; spread spectrum as the aggravating factor; SKP insertion rate as the compensation; an experiment (disable spread spectrum).

    Common weak answer: blaming the cable without asking about clocking.

    Learn it in: Chapter 5, Module 07.

  8. [Troubleshoot] On one server model, an SSD is missing from lspci after roughly 1 in 50 cold boots. When it is missing, the root port's Link Status shows Data Link Layer Link Active = 0. A rescan does not bring it back; a full power cycle does. Which timing relationships do you investigate?

    Model answer

    The device never reached a working link, so this is a power-up sequencing problem, not enumeration. Investigate: (1) power rails versus PERST# deassertion: is PERST# released only after the drive's supplies are stable for the required time? (2) reference clock versus PERST#: is REFCLK stable before PERST# is released? (3) the drive's own readiness: does its PHY start link training within the window the base specification allows after PERST# deassertion, and does the root port give up on Detect before the drive appears? (4) platform firmware: does it retrain or hot-reset a link that failed, or simply leave it down? Measure with a scope or logic analyzer on PERST#, REFCLK enable and the rails on failing and passing boots, and capture the LTSSM from the root port side. A rescan cannot help because software only probes devices behind a link that is up; a link retrain (or Secondary Bus Reset) from the root port is the software-side experiment to try. Confirm the exact timing parameters in the PCI Express Card Electromechanical (CEM) specification and the base specification's reset rules rather than from memory.

    A strong answer includes: link never up versus not enumerated; PERST#, REFCLK and rail timing; measuring failing versus passing boots; why rescan cannot help; citing the specifications by name for exact numbers.

    Common weak answer: "Add pci=realloc" (a resource fix for a link problem).

    Learn it in: Chapter 49, Chapter 17, Module 08.

  9. [Trace] An analyzer on a newly built backplane shows one port stuck cycling between Polling.Active and Polling.Compliance. What does that signature usually mean, and how do you narrow it down?

    Model answer

    Polling.Compliance is entered when the LTSSM detected a receiver on a lane during Detect but then does not see the expected training sets on all detected lanes during Polling (or when compliance is forced by the Enter Compliance setting). In a new board that usually means a lane that is electrically present (it detects the termination) but cannot carry data: a broken or mis-routed differential pair, swapped P/N handled badly, a missing AC-coupling capacitor, or a lane that is wired to the wrong partner lane. Narrow it down by looking at which lanes send training sets and which only send the compliance pattern, checking that Enter Compliance is not set in Link Control 2 by firmware, testing with a known-good card, and checking the board's lane routing against the schematic. Polarity inversion and lane reversal are normal and handled by training; they do not cause this signature by themselves.

    A strong answer includes: detected but not training; per-lane inspection; ruling out the configuration bit; separating legal polarity/lane reversal from wiring faults.

    Common weak answer: "The device is in test mode", without asking why.

    Learn it in: Chapter 8, Module 08.

  10. [Performance] A customer measures 6.2 GB/s of 128 KiB sequential reads on a Gen4 x4 SSD and asks whether the link is the limit. Do the arithmetic.

    Model answer

    Raw: 16 GT/s × 4 lanes × 128/130 ÷ 8 ≈ 7.88 GB/s per direction. Read data travels device → host as Memory Write TLPs; with MPS = 256 bytes and 64-bit addresses, each TLP carries 256 bytes of payload plus a 16-byte header and about 8 bytes of framing, sequence number and Link CRC (LCRC), so about 256/280 ≈ 91% efficiency → ≈ 7.2 GB/s. Subtract a few percent for ACK and flow-control DLLPs and SKP ordered sets: a practical ceiling around 6.8–7.0 GB/s. 6.2 GB/s is about 90% of that ceiling: close, but there is some headroom. Next checks: confirm the negotiated speed and width and that MPS really is 256 on both ends (MPS 128 would drop the ceiling to roughly 128/152 ≈ 84%, about 6.6 GB/s before DLLPs); check queue depth and job count (enough commands in flight to cover latency); and compare with the drive's datasheet figure, which may itself be below the link ceiling.

    A strong answer includes: the raw rate with encoding; per-TLP overhead with the actual MPS; DLLP and SKP overhead; checking MPS on both ends; checking concurrency.

    Common weak answer: "Gen4 x4 is 8 GB/s, so there's 2 GB/s missing."

    Learn it in: Performance Engineering, Mathematics for Storage and Links, Calculators.

  11. [Performance] The commonly cited bit error ratio target for a PCIe receiver is 10−12. On a fully loaded Gen4 x4 link, how many bit errors per hour would sit exactly at that target, and how does that number change how you read correctable error counters?

    Model answer

    One direction carries 16 × 109 bits/s per lane × 4 lanes = 6.4 × 1010 bits/s, or about 2.3 × 1014 bits per hour. At 10−12 that is about 230 bit errors per hour per direction. So a handful of correctable errors per day is far better than the target and is not, by itself, a defect. What matters is: the trend (rising over weeks, or with temperature); clustering (bursts that cause Recovery or REPLAY_NUM Rollover); lane concentration; and whether errors appear when the link is idle (then traffic volume does not explain them). Note also that each detected error usually costs a NAK and a replay, so a high rate shows up as latency before it shows up as failures. Health of a link is better judged with margining and trends than with a single counter value.

    A strong answer includes: the arithmetic; the conclusion that small counts are normal; trend, clustering and lane as the real signals; the latency cost of replays.

    Common weak answer: "Any correctable error is a bad link" or "correctable errors never matter."

    Learn it in: Chapter 45, Mathematics for Storage and Links.

  12. [Troubleshoot] A field team has "fixed" intermittent Gen4 link degradation by running a script every night that sets Retrain Link on the root port. The customer is happy. Do you accept the fix?

    Model answer

    No, not as a root-cause fix. Retrain Link sends the link through Recovery and lets it renegotiate; it can restore a link that has fallen back to a lower speed, but it does not explain why the link degraded, and it may not redo a full equalization. Risks: the retrain happens while I/O is running (latency spikes, and if the retrain fails the link may go down and the SSD may be reset under load); the underlying margin problem keeps getting worse unseen; and the next platform without the script fails. Accept it only as a documented, temporary workaround while collecting evidence: log Link Bandwidth Management Status, speed and width before each retrain, AER correctable counters and temperature, so the script itself becomes the data source for the real investigation.

    A strong answer includes: workaround versus root cause; the operational risk of retraining under I/O; turning the workaround into instrumentation.

    Common weak answer: "If the customer is happy, close it."

    Learn it in: Debugging Methodology, Chapter 9.

  13. [Troubleshoot] Several SSDs in a storage server go link-down at the same moment, but only during heavy write bursts. Afterwards each drive's SMART log shows its Unsafe Shutdowns counter incremented by one. Build the cross-layer hypothesis and the evidence plan.

    Model answer

    Several drives failing together points to something shared, and an Unsafe Shutdowns increment means each drive lost power (or saw a reset) without a normal shutdown notification. Combined with the write-burst trigger, the leading hypothesis is a power delivery problem: a shared rail or backplane supply sagging under the peak current of many drives writing at once, causing brown-out resets. Evidence plan: correlate the timestamps of the link-down events (pciehp or Data Link Layer Link Active changes, AER Surprise Down if the ports support reporting it) across drives; check the backplane's power telemetry and the baseboard management controller's event log; scope the rail during a reproduction; check whether the drives' power state descriptors allow a lower-power state to cap peak current. If the drives support NVMe 2.4 voltage monitoring, its alerts and history could directly show an under-voltage at the device; confirm the drive implements it and how to read it in the NVMe Base Specification 2.4. Competing hypotheses to rule out: a shared PCIe switch reset, a thermal trip, a host-side reset initiated by error recovery on one port.

    A strong answer includes: "shared cause" reasoning; Unsafe Shutdowns as evidence of power loss; timestamp correlation across drives; power measurement; alternatives ruled out.

    Common weak answer: treating each drive's failure as a separate drive defect.

    Learn it in: Chapter 57, Chapter 47, 2026 NVMe 2.4 Updates.

  14. [Troubleshoot] An SSD model trains at Gen4 on every motherboard except one vendor's, where it trains at Gen4 but logs thousands of correctable errors per hour. The motherboard vendor says their board passed compliance. How do you proceed?

    Model answer

    Compliance testing shows each component meets the specification against reference channels; it does not guarantee that a particular transmitter, channel and receiver combination has margin. Treat it as an interoperability margin problem. Steps: capture the equalization exchange on both boards (which presets were requested and chosen at 16.0 GT/s, and whether the SSD's preset hints or the root port's requests differ); margin both directions on the failing board; check whether the channel on that board is longer or has more connectors; try another SSD model on the same board and the same SSD on a different board from the same vendor; check for platform firmware equalization overrides. Bring both vendors data, not blame: "on board X, lane 1 SSD→host has 30% of the margin seen on board Y, with preset P chosen".

    A strong answer includes: compliance versus interoperability; equalization presets as the likely mechanism; margining both directions; a neutral, evidence-based report to both vendors.

    Common weak answer: "It passed compliance, so it's the SSD."

    Learn it in: Chapter 54, Validation Engineering.

  15. [Trace] A new engineer flags an analyzer capture: "lanes are reversed and lane 3 has inverted polarity, the board is miswired." Is it a defect?

    Model answer

    Probably not. Polarity inversion (P and N swapped within a lane) is detected and corrected by the receiver during Polling, and lane reversal (lane 0 on one side connected to the highest lane on the other) is handled during Configuration; both exist precisely to make board routing easier, and support for them is part of normal training (lane reversal support has some optionality, so confirm both ends support it if the link width is reduced). The analyzer must be told about them (or detect them) to decode the traffic correctly; otherwise it will show garbage. The real questions are whether the link reached L0 at full width and speed, and whether errors appear. If yes, the board is fine and the capture setup needs adjusting.

    A strong answer includes: where in training each is handled; that both are legal routing choices; the analyzer configuration consequence.

    Common weak answer: opening a board defect.

    Learn it in: Chapter 8, Analyzer Training.
