A WRITE runs the end-to-end journey with the data flowing the other way. That one change rearranges the whole trace: the controller must pull the data with Memory Read requests and Completions, the flash work moves to after the completion, and a new question appears that a read never asks: when the drive says "done", is the data actually safe? This chapter follows an 8 KiB direct write on the lab system and then answers that question with write caching, Force Unit Access and Flush.

Why this chapter exists

In The Most Important Chapter you followed a READ through seventeen stages. A WRITE shares the first eight stages almost exactly, so it is tempting to think of it as "a read in reverse." It is not. Three things change in ways that matter for trace analysis and for correctness:

  • The data path flips from posted to non-posted. For a read, the controller pushes data with posted Memory Write (MWr) Transaction Layer Packets (TLPs) on the Peripheral Component Interconnect Express (PCIe) link. For a write, it must ask for the data with non-posted Memory Read (MRd) requests, and the root complex answers with Completions with Data (CplD). Tags, Maximum Read Request Size (MRRS), Read Completion Boundary (RCB) and completion splitting suddenly matter.
  • The flash work moves. A read must touch NAND before it can complete. A write usually completes as soon as the data is in the controller's write cache; the NAND program happens later, invisibly, and may take a thousand times longer than the command did.
  • Durability becomes a protocol question. With a volatile write cache, a successful completion does not mean the data survives a power loss. Force Unit Access (FUA) and the Flush command are how the host closes that gap, and file systems depend on them for crash consistency.

Engineers who understand reads but not these three differences misread write traces ("why are there so many completions?"), misjudge write latency ("why is a write faster than a read?") and miss a whole class of data-loss bugs. This chapter fixes that.

The story

This time Mia has drawn two pages of a comic and wants the library to keep them forever. The teacher writes a slip ("please file these two pages in shelf 1, starting at page 80; they are on table 6") and rings the buzzer.

The runner comes and takes the slip. But the pages are still on table 6 in the classroom, so the runner has to come back and ask for them. Because the runner's bag only fits a few sheets per trip-ticket, he writes sixteen little tickets ("give me sheets 1 and 2", "sheets 3 and 4"…) and the teacher's helpers hand the sheets over, sometimes in two handfuls per ticket.

Back at the library, the runner drops the pages into the "to be filed" tray right next to the front desk and immediately sends a "done!" card and flicks the lights. The librarian files them in the basement later, when there is a big stack to carry down. If the teacher says "file it in the basement before you say done," it takes much longer. And if the teacher says "please file everything in your tray right now," the librarian empties the whole tray before answering.

Sending documents to a bank's archive. You fill in a deposit form (the command) and put it in the outgoing tray; you call the bank (doorbell). The bank's courier collects the form, sees "documents are on desk 6," and makes several collection runs, each with a numbered receipt, to bring the documents back (Memory Reads with tags, answered by Completions). At the branch, a clerk puts them in the branch safe (the volatile write cache) and phones you: "received" (completion and interrupt). Overnight, the branch sends everything to the central vault (the NAND program). If the branch catches fire before the overnight run, documents only in the branch safe are lost, unless the branch has a fire-proof safe with its own generator (power-loss protection). "Store this directly in the vault before you call me" is FUA; "send everything in your safe to the vault now and call me when done" is Flush.

  • Collection runs overlap. The controller has many read requests outstanding at once, and completions for different tags can come back in any order. A courier making sequential trips hides this.
  • The receipts are not the deposit number. PCIe tags identify read requests and are reused within microseconds; the NVMe Command Identifier identifies the command. The analogy tempts you to merge them.
  • The "branch safe" is not one thing. Some drives have no volatile cache at all, some have cache backed by capacitors, some have a volatile cache that the host can disable. The specification lets the drive report which; the analogy suggests every bank works the same way.
  • Nothing tells you when the overnight run happens. NVMe exposes no event for "data is now on NAND" except FUA and Flush completions.
  • The customer must not touch the documents. Until the completion, the host buffer belongs to the controller, which may read it at any time, more than once. A real customer could rewrite the papers on the desk after the courier left; a host that changes the buffer mid-command gets a mixture on media.

Beginner explanation

To write, the driver again places a 64-byte command in a submission queue and rings a doorbell. The command says "write 16 logical blocks starting at this logical block address (LBA), and the data is in host memory at these addresses." The controller fetches the command exactly as for a read.

Now the difference: the data is in host memory, and only the controller can move it. So the controller sends read requests to host memory ("give me 512 bytes from this address"), and host memory answers with completion packets that carry the bytes. When all the bytes have arrived inside the drive, the drive puts them in its fast internal memory (the write cache), writes a completion entry, and raises an interrupt (an MSI-X message: Message Signaled Interrupts eXtended). The driver tells the application the write succeeded.

The slow part, programming the flash, has not happened yet. The drive does it later, in the background, usually after collecting enough data to fill a large flash page. That is why a write can finish in about 11 µs on our lab system while a read took 65 µs. It is also why there are special ways to say "really make it permanent before you answer": the FUA bit on a write, or a separate Flush command.

The central concept on the ladder

The central concept is the controller-pulled write and its durability point: the data reaches the drive only because the drive asks for it, and "complete" means "accepted," not necessarily "permanent."

The runner has to come back to the classroom to collect the drawings, ticket by ticket, puts them in the library's front tray, says "done," and files them in the basement later. "File it in the basement first" is a special request.

The controller fetches the Write command, reads the data from host memory with DMA, stores it in its write cache and posts a completion. NAND programming is deferred. FUA forces this command's data to non-volatile media before completion; Flush forces everything previously completed.

The controller's DMA engine issues read requests sized by MRRS and tracks them with tags in a completion reassembly buffer. The data lands in dynamic or static RAM (DRAM or SRAM) inside the solid-state drive (SSD). A drive with power-loss protection has capacitors that can finish programming that buffer after power fails; a drive without it can lose the cache contents.

NVM Command Set Specification: Write opcode 01h, SLBA, NLB, FUA bit in CDW12. NVMe Base Specification: Flush opcode 00h, Volatile Write Cache field in Identify Controller and the Volatile Write Cache feature. PCI Express Base Specification: Memory Read requests, completions, MRRS, MPS, RCB, Byte Count and Lower Address.

Doorbell MWr down; SQE MRd up and CplD down; 16 data MRd up, 32 data CplD down; CQE MWr and MSI-X MWr up; CQ head doorbell MWr down. Seventeen non-posted requests (one SQE fetch, sixteen data reads) instead of the read's one.

An analyzer shows a tight cluster: fetch at 0.7 µs, data reads issued at 2.2 µs, completions streaming from 2.9 to 4.0 µs, CQE at 4.4 µs. No 50 µs silent gap as in the read. With FUA, a long gap appears between the last data completion and the CQE.

Lost data after power failure with no errors: check whether the file system or application issued Flush/FUA and whether the drive honored them. Write errors with Data Transfer Error status: look for a failed completion (Unsupported Request, UR, or Completer Abort, CA) on a data-pull read and the IOMMU log. Slow writes: check whether FUA is set on every write, or whether the cache is disabled.

The sixteen questions, applied to the pulled write and its durability point

The controller-pulled write through the course's sixteen questions
QuestionAnswer
What is it?A write in which the controller reads data from host memory, acknowledges it once it is in the drive's cache (or media), and programs NAND at a time of its choosing.
Why was it created?Making the device the bus master keeps central processing unit (CPU) memory-mapped I/O (MMIO) out of the data path; caching hides NAND program time, which is far longer than read time.
What problem does it solve?Low write latency and high write throughput despite program times of hundreds of microseconds or more.
What existed before?Disk drives with volatile write caches and the same durability problem; the ATA and SCSI worlds had FUA and cache-flush commands, which NVMe carried over in its own form.
Why is the current design better?Explicit, per-command durability control (FUA) and an explicit barrier (Flush), with the drive reporting whether a volatile cache exists at all.
Who creates it?Application and file system decide the durability need; the driver encodes FUA or issues Flush; the controller performs the pull and the program.
Who consumes it?The controller consumes the data; the host consumes the completion, and crash-recovery code later relies on what was durable.
Where does it live?Host buffer until the pull completes; controller cache until programmed; NAND afterwards.
What memory/registers are involved?Buffer pages at IOVA 0x2_0000_8000 and 0x2_0000_9000, SQ1 slot 6, CQ1 slot 0x0C, doorbells, the controller's cache and its Volatile Write Cache setting.
What happens before it?The buffer is filled and pinned; for an allocating write, the file system may need to allocate blocks and journal metadata first.
What happens after it?Background programming, garbage collection; the host may later issue Flush (for example from fsync()).
What happens if it is wrong?Silent data loss on power failure (missing Flush/FUA), torn or mixed data (buffer modified before completion), Data Transfer Error (bad PRP), or data written to the wrong LBA.
What does the protocol analyzer show?MRd/CplD pairs for the data, tags, Byte Count sequences, and the time from last data completion to CQE (short when cached, long with FUA).
What does Linux show?Write tracepoints with the FUA flag, Flush commands, write_cache and fua queue attributes, error messages with status.
What would a validation engineer test?Power-loss tests with and without FUA/Flush, completion splitting with various MRRS/MPS/RCB, unaligned PRP1 offsets, UR/CA injection on data reads, cache enable/disable.
What would a senior engineer suspect when it fails?The durability contract between application, file system and drive; IOMMU mappings of the second page; completion reassembly in the controller; buffer reuse before completion.

The journey, stage by stage

The stages use the same template as the READ's. Where a stage is identical, the entry says so and gives only the values that change, so you can spend your attention on the differences. Note one deliberate reordering: in the read, the flash operation sits in the middle (stage 12); in a cached write, the flash program is the last stage and happens after the application has already been told the write succeeded.

Application request

Who acts / what changes
The application calls pwrite(fd, buf, 8192, 0x80000). The kernel pins the two buffer pages for the duration of the I/O. t = 0.
Analogy
Mia hands over two drawn pages and says where they should be filed.
Technical
As for the read, O_DIRECT bypasses the page cache. If the file had been opened with O_DSYNC (or O_SYNC), the write would also have to be durable before returning; the file system then requests FUA on the data write if the overwrite needs no metadata update and the device supports FUA, or issues a cache flush afterwards Implementation-dependent (file system and kernel version).
Hardware / protocol
CPU only; no protocol yet.
Trace appearance
Nothing on the link; syscalls:sys_enter_pwrite64 on the host.
Evidence
strace shows flags at open() time, which decide whether FUA or Flush will follow.
What goes wrong
The application modifies the buffer from another thread before pwrite() returns: the controller may read some sheets before and some after the change, so the media gets a mixture. With buffered I/O, the kernel's "stable pages" mechanism prevents this for page-cache pages on devices that need it; with direct I/O the application owns the problem.

Block request

Who acts / what changes
File system and blk-mq: offset 0x80000 maps to sector 0x0020_4000; a bio with two segments (the two pages) becomes a request with tag 0x31, operation REQ_OP_WRITE, plus REQ_FUA or REQ_PREFLUSH if durability was requested. t ≈ 0.40–0.85 µs.
Analogy
The teacher writes "shelf 1, page 80" on the slip.
Technical
If the device reports no volatile write cache, the block layer strips FUA and pre-flush flags because they would be meaningless; if the cache exists but the device does not support FUA, the block layer emulates FUA with a Flush after the write. This flag handling lives in the block layer's flush machinery.
Trace appearance
block:block_rq_issue with W (or WFS-style flag letters when FUA/sync are set; exact letters are version-dependent), sector 2113536 (0x204000), 16 sectors.
What goes wrong
An allocating write (to a hole or past end of file) is not a pure overwrite: the file system must journal metadata, so the trace shows extra writes and Flushes around the data write. Engineers expecting one command see five and suspect the drive.

Driver command creation

Who acts / what changes
The NVMe driver builds a Write command and maps two pages through the IOMMU: IOVA 0x2_0000_8000 and 0x2_0000_9000. t ≈ 0.85–1.10 µs.
Analogy
The slip now says "two sheets, on table 6, sheet 1 here and sheet 2 there."
Technical
Opcode 01h (Write), Namespace Identifier (NSID) 1, SLBA 0x0020_4000, NLB 15. For a two-page transfer the driver sets PRP1 to the first page and PRP2 to the second page directly; with more than two pages PRP2 would point to a PRP list. With REQ_FUA, the driver sets the FUA bit (bit 30 of CDW12).
Hardware / protocol
IOMMU page-table update for two pages; NVM Command Set Write format.
Trace appearance
nvme:nvme_setup_cmd: qid=1, cmdid=4145 (0x1031), cmd=(nvme_cmd_write slba=2113536, len=15, ctrl=0x0, …); ctrl=0x4000 would indicate FUA (the tracepoint prints the upper 16 bits of CDW12) Version-dependent.
What goes wrong
PRP2 pointing at a page that was not mapped (or is off by one page) is accepted by the controller without complaint until it tries to read it (the abnormal trace below). NLB off by one writes one block too many, silently corrupting the next block on media.

DMA request

Who acts / what changes
The controller's data DMA engine plans the pull: it walks PRP1 and PRP2, allocates 8 KiB of write-cache buffer, splits the transfer into read requests and allocates tags 0x30 to 0x3F. Analyzer t ≈ 1,350–2,200 ns.
Analogy
The runner writes sixteen numbered tickets, one per handful of sheets, and makes room in his bag.
Technical
Each request may ask for at most MRRS = 512 bytes and must not cross a 4 KiB boundary: 8192 / 512 = 16 requests, eight per page. Before issuing a request, the device must have buffer space for its completion data (it advertised infinite completion credits), so the size of the reassembly buffer limits how many requests can be outstanding. Many controllers also start the pull only when cache space is available, which is where back-pressure from a full write cache shows up.
Hardware
Tag allocator, completion reassembly buffer, cache allocator. With 10-bit tags disabled the device has at most 256 tags; deep write workloads on fast links can be tag-limited (see PCIe Tags).
Protocol
PCIe: MRRS (Device Control register) caps request size; the PRP rules (NVMe over PCIe Transport) define which addresses may be read.
Trace appearance
The gap between the SQE CplD and the first data MRd (about 850 ns here) is the controller's command-processing time for a write.
What goes wrong
A write cache that is full (sustained writes outrunning NAND) delays the pull by milliseconds; the trace shows the SQE fetched but no data MRd for a long time. This is normal steady-state behaviour, not a bug, but it is often reported as one.

Memory Read TLPs

Who acts / what changes
The device sends 16 MRd64 requests upstream, 512 bytes each, at 0x2_0000_8000, 0x2_0000_8200, … 0x2_0000_9E00. Analyzer t = 2,200–2,350 ns.
Analogy
The runner hands all sixteen tickets to the classroom helpers at once.
Technical
Each request: Fmt 001 (4-DW header, 64-bit address), Type 00000, Length 128 DW, First and Last BE 1111, Requester ID 0x0100, a distinct tag. The root complex translates each address through the IOMMU (two I/O translation lookaside buffer (IOTLB) entries, one per page) and reads memory coherently.
Hardware
Each request uses one non-posted header credit at the root port's receiver (no data credits: a read request carries no payload).
Protocol
Non-posted: each must be answered by one or more completions with the same Requester ID and tag, or by an error completion; otherwise the device times it out.
Trace appearance
Sixteen short TLPs about 10 ns apart, tags incrementing. On a real controller they may be interleaved with requests for other commands.
Evidence
Address ranges tie each request to this command's PRP pages; nothing else in the TLP refers to the command.
What goes wrong
A request larger than MRRS is a malformed request; a request crossing a 4 KiB boundary is also malformed. Both are rejected by the root port and reported through Advanced Error Reporting (AER).

Completions with Data

Who acts / what changes
The root complex returns the data in 32 CplD TLPs of 256 bytes, two per tag; the device places each payload into the cache buffer at the right offset. Analyzer t = 2,900–4,016 ns.
Analogy
The helpers hand back the sheets, sometimes two handfuls per ticket, each handful labelled with its ticket number and "how many sheets are still coming for this ticket."
Technical
A completion's payload may not exceed the MPS of the receiving device (256 B), so a 512-byte request is answered by at least two completions. When a completer splits, each split must end on an RCB-aligned address (64 B here), and completions for one request must be returned in increasing address order. Each completion carries Byte Count, the number of bytes still to be returned for the request including this completion (512 for the first, 256 for the second), and Lower Address, the low seven bits of the address of its first byte. Completions for different tags may arrive in any order. How a root complex chooses to split is implementation-dependent; the 2 × 256 pattern is common but not required Implementation-dependent.
Hardware
The device's reassembly logic uses (tag, Byte Count, Lower Address) to place each payload; the request is finished when a completion arrives whose Byte Count equals its own payload length.
Protocol
PCIe completion rules; see Completion Rules and Deep dive: PCIe Completions.
Trace appearance
CplD Host→Dev Tag=0x30 Len=64 BC=512 LowAddr=0x00, then CplD Tag=0x30 Len=64 BC=256 LowAddr=0x00, and so on for each tag.
Evidence
Sum of payloads per tag must equal the request length; any tag with a missing final completion means a Completion Timeout is coming.
What goes wrong
Unsupported Request completion (IOMMU fault, wrong PRP); Completer Abort; poisoned data (Error Poisoned, EP, bit) from a host memory error, which a careful controller must not write to media as good data; Completion Timeout if the root complex never answers.

Write cache

Who acts / what changes
The controller's cache manager. 8 KiB now sits in the drive's DRAM write cache, tagged with LBAs 0x0020_4000–0x0020_400F; the flash translation layer (FTL) marks these LBAs as "newest copy in cache" so a read would be served from cache. Analyzer t ≈ 4,016–4,400 ns.
Analogy
The drawings go into the "to be filed" tray at the front desk.
Technical
If the Volatile Write Cache is enabled and FUA is not set, the controller may complete the command now. If FUA is set, it must first make this command's data non-volatile (program it, or place it in a power-protected buffer). A controller that reports no volatile write cache (VWC field clear in Identify Controller) must already treat completed writes as non-volatile; drives with power-loss protection usually report it this way.
Hardware
DRAM or SRAM, often with internal error-correcting code (ECC); on enterprise drives, hold-up capacitors and firmware that dumps cache to NAND on power loss.
Protocol
NVM Command Set: FUA semantics. NVMe Base: Volatile Write Cache feature (the host can enable or disable the cache through Set Features when the drive supports changing it).
Trace appearance
A short gap (about 0.4 µs here) between the last data CplD and the CQE. A long gap (hundreds of microseconds) is the signature of FUA or of a disabled cache.
Evidence
nvme id-ctrl (VWC field) and nvme get-feature -f 6 (Volatile Write Cache feature) tell you which behaviour to expect.
What goes wrong
A drive that acknowledges FUA writes or Flush before data is non-volatile (firmware bug or misconfiguration): the trace looks fast and correct, and data is lost only on power failure. Only power-loss testing finds it.

Completion entry

Who acts / what changes
The controller writes the CQE into CQ1 slot 0x0C at 0x1_2341_00C0: DW2 = 0x0001_0007 (SQ Identifier (SQID) 1, SQ Head Pointer (SQHD) 7), DW3 = 0x0001_1031 (status 0, phase 1, CID 0x1031). Analyzer t = 4,400 ns.
Analogy
The "done" card in the answer box.
Technical
Same format as the read's. For a write, the ordering concern is reversed: the host already owns the data, so the controller must not post the CQE until it has received all data it needs from the buffer, because the host may reuse the buffer as soon as it sees the CQE.
Trace appearance
MWr(64) Dev→Host Addr=0x1_2341_00C0 Len=4 payload 00000000 00000000 00010007 00011031.
What goes wrong
A controller that posts the CQE while data reads are still outstanding: the host frees and reuses the buffer, and the late completions deliver new contents. On the analyzer this is unmistakable: a data CplD for this command's addresses after its CQE.

Flash program (after completion)

Who acts / what changes
The controller's back end, at a time of its choosing: the 8 KiB is combined with other cached data into a full programming unit (for example several 16 KiB pages across planes and, for triple-level-cell (TLC) NAND, a whole word line), written to a free location, and the FTL map is updated to point the LBAs at it. The old physical copy becomes stale and will be reclaimed by garbage collection.
Analogy
The librarian carries a full stack from the tray to the basement and updates the catalog cards.
Technical
NAND cannot overwrite in place: every write goes to a fresh page (out-of-place update), which is why an FTL and garbage collection exist. Program time (tPROG) is typically hundreds of microseconds to a few milliseconds per programming unit Implementation-dependent. Many drives first write to a single-level-cell (SLC) mode region (faster) and fold into TLC/QLC later.
Hardware
NAND channel controller, dies, the FTL's mapping table, and (on enterprise drives) the power-loss protection circuit that guarantees this stage completes even if power fails.
Protocol
Invisible to NVMe and PCIe. Only FUA and Flush give the host a protocol-level event tied to it.
Trace appearance
Nothing for this command. Indirectly: when the cache is full, later writes' data pulls are delayed (stage DMA request), and reads to busy dies take longer.
Evidence
Self-Monitoring, Analysis and Reporting Technology (SMART) / Health log data-units-written counters (SMART / Health) and vendor logs; write-amplification estimates from host versus NAND write counters where the vendor exposes them.
What goes wrong
Program failure: the controller retries elsewhere transparently; repeated failures retire blocks and consume spare capacity (visible in SMART as reduced available spare). Power loss with no protection and no Flush: the cached 8 KiB is lost although the host saw success.

Durability: write cache, FUA and Flush

A read has one completion point. A write has two: accepted (the CQE) and durable (data on non-volatile media). NVMe gives the host three tools to relate them.

The principle is stable: Flush covers data from commands that completed before it; it is not an ordering barrier for commands still in flight.

Same write with FUA

With O_DSYNC on a cached drive, the driver sets FUA (CDW12 = 0x4000_000F). Everything on the link up to the last data completion is identical. Then the controller must program (often into SLC-mode blocks) before posting the CQE. In our synthetic drive the CQE arrives about 240 µs later instead of 0.4 µs, and the write's end-to-end time becomes about 250 µs instead of 10.8 µs.

Flush after the write

With fsync() instead, the write completes in 10.8 µs and a separate Flush follows: one more SQE (opcode 00h, no data pointer, no data TLPs), and a CQE that arrives when the controller has made all previously completed writes durable. With a lot of dirty cache, that can take milliseconds; with little, much less.

FUA cost depends on one command's data. Flush cost depends on everything other applications wrote before it. That is why one process calling fsync() can be slowed down by another process's bulk writes, and why drives with power-loss protection (no volatile cache, so Flush is nearly free) are preferred for databases.

Flush broadcast-NSID support and its reporting, and the Linux block layer's FUA and flush handling, have changed over revisions and kernel versions. Older NVMe revisions placed PCIe-specific material in the Base Specification.

  • NVMe does not say when cached data is programmed, or give the host any event for it.
  • NVMe does not order the execution of commands in a queue: a Write submitted before a Read of the same LBA may complete after it. Hosts that need ordering wait for completions.
  • PCIe does not require completions for different tags to come back in request order.
  • Check in the specification: the precise scope of Flush, and the controller's obligations for a Write with FUA when the namespace has no volatile cache.
  • Never assume a successful Write completion means power-safe data unless the drive reports no volatile write cache, the cache is disabled, FUA was set, or a later Flush completed.
  • Never assume completions arrive in request order.
  • Never assume the data reads come immediately after the SQE fetch: a full cache can delay them for a long time.

Modelling the data pull

This script reproduces the data-pull half of the normal trace and the unaligned example in the figure. Run it with no arguments for the chapter's 8 KiB write, or with 0x830 4096 for a 4 KiB write whose buffer starts at offset 0x830 in its page.

#!/usr/bin/env python3
"""Synthetic model of how a controller pulls WRITE data on the lab system.
Walks the PRP entries, splits the pull into Memory Read requests (MRRS, no
4 KiB crossing), and models how the root complex answers each one with
Completions (payload <= MPS, split only at RCB-aligned addresses).
Standard library only. Splitting policy of the completer is an assumption.
Usage: python3 e2e_write_pull.py [PRP1_OFFSET] [LENGTH]   e.g. 0x830 4096"""
import sys

MPS, MRRS, RCB, PAGE = 256, 512, 64, 4096

def prp_ranges(prp1, prp2, length):
    """PRP1 may carry an offset; PRP2 is the second page (no list for <= 2 pages)."""
    first = min(length, PAGE - (prp1 % PAGE))
    out = [(prp1, first)]
    if length > first:
        if length - first > PAGE:
            raise ValueError("needs a PRP list; not modelled here")
        out.append((prp2, length - first))
    return out

def read_requests(ranges, first_tag=0x30):
    tag = first_tag
    for addr, n in ranges:
        while n:
            size = min(MRRS, n, PAGE - addr % PAGE)
            yield tag, addr, size
            tag, addr, n = tag + 1, addr + size, n - size

def completions(addr, size, chunk=MPS):
    """One assumed completer policy: MPS-sized pieces, cut at RCB-aligned addresses."""
    remaining = size
    while remaining:
        n = min(chunk, remaining)
        end = addr + n
        if n < remaining and end % RCB:          # cut must land on an RCB boundary
            n -= end % RCB
        yield addr, n, remaining                 # byte count = bytes still to come
        addr, remaining = addr + n, remaining - n

def main():
    offset = int(sys.argv[1], 0) if len(sys.argv) > 1 else 0
    length = int(sys.argv[2], 0) if len(sys.argv) > 2 else 8192
    prp1, prp2 = 0x2_0000_8000 + offset, 0x2_0000_9000
    reqs = list(read_requests(prp_ranges(prp1, prp2, length)))
    cpls = 0
    for tag, addr, size in reqs:
        print(f"MRd64  tag={tag:#04x} addr={addr:#x} len={size // 4:3d} DW")

Observations:

Common mistakes

  • Looking for MWr data in a write trace. Write data arrives at the device as Completions with Data, answering the device's own Memory Reads.
  • Treating 32 completions as an error. Split completions are normal; check Byte Count sequences instead of counting TLPs per tag.
  • Assuming completion order equals request order. Tags 0x34/0x35 in the normal trace show otherwise.
  • Equating "write completed" with "data durable". Only true with no volatile cache, cache disabled, FUA, or a later Flush.
  • Believing a Flush orders in-flight commands. It covers data from commands that already completed.
  • Reusing the buffer early. The controller can read the buffer at any time until the CQE; it may even read it twice (for example after an internal retry).
  • Blaming the drive for write-latency spikes caused by a full cache. Sustained writes eventually run at NAND speed; the spikes are the cache draining.
  • Forgetting the file system. Allocating writes and journal commits add metadata writes and Flushes around your data write.

Senior engineer insight

  • Reads are latency-bound by media; cached writes are latency-bound by the host. Tuning advice for one is often wrong for the other.
  • The durability contract is a chain. Application flags → file system → block layer flags → NVMe FUA/Flush → controller firmware → power-loss hardware. A break at any link loses data silently. When asked "is this durable?", walk the chain out loud.
  • Read-request sizing is a controller design lever. Larger reads (up to MRRS) reduce header overhead; smaller reads reduce reassembly buffering and head-of-line blocking. Many controllers use 256 B or 512 B regardless of MRRS. Do not assume MRRS-sized requests.
  • Tags can be the bottleneck for writes, never for reads. Read data uses posted writes and needs no tags; write data needs a tag per outstanding request. At Gen5 and beyond with long root-complex latencies, 8-bit tags can limit write throughput; this is a motivation for 10-bit and 14-bit tags.
  • "First abnormal event" and "root cause" are different rows. In the unmapped-PRP2 trace the evidence was in the SQE long before the UR.

Challenge

Predict the TLP count on the lab system for one 8 KiB write with FUA followed by nothing, and for one 8 KiB write followed by a Flush.

Hints

If write_cache says "write through", the block layer strips FUA and flushes. File-system journaling may add metadata writes in the fdatasync run if the file was extended.

Solution

Q1: the cached run, because completion does not wait for media. Q2: on a drive with a volatile cache and FUA support, ctrl=0x4000 on the writes (overwrites of allocated blocks); if FUA is unsupported, a Flush after each write; if the drive reports no volatile cache, neither, and the latencies match the cached run. Q3: typically two (Write, then Flush), more if metadata changed. Q4: the drive has no volatile write cache (typical of power-loss-protected drives) or the cache is disabled; every completion is already durable.

Challenge: FUA write: the same 54 TLPs as the normal trace (the only difference is timing and CDW12). Write + Flush: 54 + 6 = 60 TLPs (Flush doorbell, SQE MRd, CplD, CQE, MSI-X, head doorbell), assuming one interrupt and one head doorbell per command.

The 99th percentile, not the mean: Flush latency depends on the cache state, so its tail is long. Also whether the file was preallocated: if not, the first pass measures file-system allocation as much as the drive.

Exercises

  1. Redo the data-pull plan for MRRS = 256 and MPS = 256. How many reads and completions?

    Answer

    8192 / 256 = 32 reads; each fits in one completion (256 ≤ MPS), so at least 32 completions. Same completion count, twice the request count and tags.

  2. A 12 KiB write starts at a page-aligned buffer. What are PRP1 and PRP2?

    Answer

    Three pages: PRP1 is the first page; PRP2 is the address of a PRP list containing the second and third page addresses. The controller will first issue an MRd for the PRP list (at 0x1_5000_xxxx on the lab system) before or while pulling data.

  3. Decode CQE DW3 = 0x0009_1031.

    Answer

    CID 0x1031 (bits 15:0); phase 1 (bit 16); status field 0x0009_1031 >> 17 = 0x4: Status Code 04h with Status Code Type 0 (generic), More 0, Do Not Retry 0: Data Transfer Error.

  4. In the normal trace, which completion finishes tag 0x35, and how do you know without counting bytes?

    Answer

    Row 29: its Byte Count (256) equals its payload length (64 DW = 256 B), which marks the last completion of the request.

  5. Why does a write need tags for its data while a read does not?

    Answer

    Write data is fetched by non-posted Memory Reads, whose completions must be matched by Requester ID and tag. Read data is pushed with posted Memory Writes, which need no completion and therefore no tag matching.

  6. A drive reports VWC = 0. An application uses O_DSYNC. What NVMe commands do you expect, and what is the write latency compared with no O_DSYNC?

    Answer

    Plain Writes without FUA and no Flushes (the block layer strips them because there is no volatile cache). Latency is the same as without O_DSYNC, apart from any file-system metadata work.

Quiz

  1. How does WRITE data travel from host memory to the SSD?

    • The CPU writes it to the SSD's Base Address Register (BAR) window with Memory Writes
    • The SSD receives posted Memory Writes from the root complex
    • The SSD issues Memory Reads and the root complex returns Completions with Data
    • The data is inside the SQE
    Answer and reasoning

    The controller is the bus master for data in both directions. For a write it reads the PRP pages, and the data comes back as completions.

  2. With MRRS 512 and MPS 256, what is the minimum number of completions for 8 KiB?

    • 8
    • 16
    • 32
    • 64
    Answer and reasoning

    Each completion carries at most MPS = 256 bytes; 8192 / 256 = 32, regardless of how many requests there are.

  3. What does Byte Count = 256 on a 256-byte completion tell you?

    Answer

    It is the last completion for that request: the remaining byte count equals this completion's own payload.

  4. Which bit makes a Write durable before completion?

    • Limited Retry, CDW12 bit 31
    • Force Unit Access, CDW12 bit 30
    • PSDT in CDW0
    • The phase tag
    Answer and reasoning

    FUA (bit 30 of CDW12) requires the data to be on non-volatile media before the command completes.

  5. Why is a cached write faster than a read on the lab system?

    Answer

    The write completes once data is in the controller's cache; NAND programming is deferred. The read must wait for the NAND array read (tR) before any data can be returned.

  6. What does a Flush command guarantee?

    Answer

    That data from write commands completed before the Flush was submitted is on non-volatile media when the Flush completes (scope per the specification: the namespace, or all namespaces when broadcast). It does not order or cover commands still in flight.

  7. In the abnormal trace, what is the first abnormal event and where is the root-cause evidence?

    Answer

    First abnormal event: the UR completion for tag 0x38 (row 36). Root-cause evidence: the PRP2 value 0x2_0000_A000 in the SQE payload (row 3).

  8. Can completions for tag 0x35 arrive before those for tag 0x34?

    • Yes
    • No
    Answer and reasoning

    Yes. Ordering between completions for different requests is not guaranteed; only completions of a single request come in address order.

  9. Why must the controller not post the CQE before the last data completion arrives?

    Answer

    The host may reuse or free the buffer as soon as it sees the CQE; late reads would then fetch new contents, writing wrong data to media. The PCIe link cannot enforce this, so the controller must.

Interview questions

  1. (Beginner) What is the main difference on the PCIe link between an NVMe read and write?

    Model answer

    Read data goes device-to-host as posted Memory Writes. Write data goes host-to-device as Completions to the device's Memory Read requests.

  2. (Beginner) What is a volatile write cache, and why can it lose data?

    Model answer

    DRAM in the SSD where accepted write data waits before being programmed into NAND. DRAM loses contents on power loss, so without power-loss protection, acknowledged data not yet programmed is lost.

  3. (Intermediate) Explain Byte Count and Lower Address in a split completion.

    Model answer

    Byte Count is the number of bytes remaining to be returned for the request, including this completion. Lower Address gives the low bits of the address of this completion's first byte, so the requester can place the payload and check alignment. The last completion has Byte Count equal to its payload size.

  4. (Intermediate) How does Linux turn fsync() into NVMe commands?

    Model answer

    The file system writes dirty data and metadata (possibly journal commits with pre-flush and FUA flags), then issues a cache flush; the block layer turns the flush into an NVMe Flush command if the device has a volatile write cache, and strips it otherwise.

  5. (Advanced) A write workload shows good average latency but 5 ms spikes every few seconds. What do you investigate?

    Model answer

    Flush commands from journal commits or fsync; write-cache saturation and SLC-cache folding; garbage collection; thermal throttling. Correlate spikes with Flush tracepoints and write volume; on an analyzer, check whether the delay is between SQE fetch and data pull (cache full) or between data and CQE (FUA/program).

  6. (Advanced) Why can write throughput be tag-limited when read throughput is not?

    Model answer

    Each outstanding write data read needs a tag until all its completions arrive. Throughput ≤ tags × request size ÷ round-trip latency. With 256 tags, 512-byte requests and a 2 µs round trip, that is about 65 GB/s, but with smaller requests or longer latency (switches, remote memory) the limit can fall below link bandwidth. Reads use posted writes and need no tags.

  7. (Senior) How would you validate that a drive honours FUA and Flush?

    Model answer

    Automated power-loss testing: write known patterns with sequence numbers, with FUA and with write+Flush, cut power at random points after completions, then verify that every write acknowledged durable is present and correct. Combine with analyzer captures to time power cuts relative to CQEs. Test with the cache enabled and disabled, and with near-full cache.

  8. (Senior) A customer's database loses its last committed transactions after power failure on a new drive model. Walk through your investigation.

    Model answer

    Walk the durability chain: database settings (fsync/O_DSYNC usage), file system mount options (barriers), block-layer write_cache/fua, NVMe tracepoints to confirm Flush/FUA are issued, the drive's VWC report and firmware version, then reproduce with controlled power-loss tests. A drive that reports VWC = 0 but has a volatile cache, or completes Flush early, is the classic firmware culprit.

Model answer for the senior-engineer version

O_DSYNC makes the file system request durability; for a pure overwrite it marks the bio REQ_FUA, otherwise it journals metadata and issues flushes. The block layer keeps FUA only if the queue has a volatile cache and FUA support, otherwise it emulates with a post-flush or strips it. The NVMe driver sets CDW12 bit 30 or issues a Flush (opcode 00h). The controller must program the data (or protect it) before completion. To prove CQE-after-data on the analyzer, for each Write CQE find the command's PRP ranges from its SQE fetch completion, collect all data-read requests in those ranges and their completions, and assert every final completion (BC equal to payload) precedes the CQE. Chapter summary

An NVMe WRITE shares its submission half with the READ, then reverses the data direction: the controller pulls data with Memory Read requests (MRRS-sized, one tag each) and the root complex answers with Completions (MPS-sized, split at RCB boundaries, identified by tag, Byte Count and Lower Address). With a volatile write cache, the controller posts the CQE once the data is in cache, so a write completes much faster than a read, and the NAND program happens later. Durability then needs FUA (this command), Flush (everything already completed), or a drive with no volatile cache. Correctness on the link rests on the controller holding the CQE until all data has arrived, not on PCIe ordering.
