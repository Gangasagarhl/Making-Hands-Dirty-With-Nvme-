This module builds on Chapter 57 — SMART / Health, which decoded every field of the SMART / Health Information log. Here the subject is health monitoring as a system: how asynchronous events are armed, delivered, masked and lost; how to capture telemetry so that it is consistent and useful; how counters behave across resets, power loss and firmware updates; how health monitoring itself disturbs the drive; and how to turn fleet-wide snapshots into early, defensible conclusions.

Kid story

A lighthouse keeper writes everything in a logbook: how strong the wind was, how much oil is left, how many bulbs have burned out. Once a day a boat comes to read the logbook. But if a storm is coming, the keeper does not wait for the boat — she fires a flare.

The rule about flares is strict: she has only as many flares as the boat left her, and after she fires one for "storm", she will not fire another "storm" flare until someone comes and reads the storm page. If the boat never comes back with new flares, or reads the page without saying "got it", the next storm passes in silence — and the logbook is the only place it was written down.

Analogy boundary

What it represents. The logbook is the set of log pages; the daily boat is periodic polling with Get Log Page; flares are completions of Asynchronous Event Request (AER) commands; the number of flares left is the number of AER commands the host keeps outstanding (bounded by the Asynchronous Event Request Limit); "no more storm flares until the page is read" is the masking of an event type until the log is read with Retain Asynchronous Event (RAE) cleared; "saying got it" is RAE = 0.

What it hides. The keeper's notes are partly guesses: Percentage Used and the composite temperature are vendor estimates. It hides the bulky diagnostic dump (telemetry) the keeper can produce on request, whose contents only the lighthouse company understands. And it hides that reading the logbook is not free: each visit (an admin command) can wake a sleeping drive.

Where it misleads. A missed flare in the story is lost forever. In NVMe the condition stays reported in the log page — the Critical Warning byte still shows it — so a host that polls catches what events missed. Conversely a flare does not mean "the lighthouse is failing": several warnings mean "I protected myself" (read-only mode, throttling).

NVMe's Asynchronous Event Request is not PCIe Advanced Error Reporting, although both are abbreviated AER; on this page AER means the NVMe command unless stated otherwise.

Mechanism

The central mechanism is the event-delivery state machine for SMART / Health events, from configuration to re-arm. Synthetic example for teaching on the Lab SSD.

  1. Configure. Who: host. What: Set Features 0Bh enabling SMART critical-warning events (bits for spare, temperature, reliability, read-only, volatile backup). Where: controller feature state. Evidence: Set Features SQE; Get Features 0Bh reads it back.
  2. Arm. Who: host. What: submits up to AERL + 1 AER commands. Where: admin SQ; they occupy command identifiers with no completion. Evidence: AER SQE fetches and no CQEs.
  3. Condition occurs. Who: firmware. What: e.g. Available Spare drops below threshold; Critical Warning bit 0 is set in the SMART log. Where: drive state. Evidence: none on the link yet.
  4. Deliver. Who: controller. What: if the type is enabled, unmasked and an AER is outstanding, it completes one AER: Dword 0 carries Asynchronous Event Type (bits 2:0 = 1h, SMART/Health), Asynchronous Event Information (bits 15:8, e.g. 02h spare below threshold) and Log Page Identifier (bits 23:16 = 02h). The type is now masked. Evidence: CQE MWr64 to the admin CQ, MSI-X vector 0.
  5. Notify. Who: kernel. What: Linux converts it into a user-space event (a uevent carrying the result) rather than reading the log itself Version-dependent. Evidence: udev monitor output.
  6. Read and re-arm. Who: daemon. What: Get Log Page LID 02h with RAE = 0 (CDW10 = 0x007F_0002). Where: admin SQ, host buffer. Evidence: the SQE's CDW10; 512 bytes DMA; CQE. The event type is unmasked.
  7. Replenish. Who: driver. What: submits a new AER to replace the completed one. Evidence: AER SQE fetch.
  8. Persist and act. Who: daemon and fleet. What: store the snapshot with identity (serial, firmware, NSID), compute deltas, alert, maybe capture telemetry. Evidence: monitoring records.

The ladder for event delivery

The keeper fires a flare for a storm, then waits for someone to read the storm page and bring a new flare.

The host leaves AER commands outstanding; the drive completes one when an enabled condition occurs; the host reads the log to acknowledge and sends a replacement.

Firmware maintains a per-type mask and a queue of outstanding AER contexts; sensors and the FTL raise conditions; a CQE is posted like any other completion.

NVMe Base 2.4: Asynchronous Event Request command, Asynchronous Event Configuration feature, Get Log Page with RAE, SMART / Health Information log.

The AER SQE is fetched long before its completion; the completion arrives unprompted on the admin CQ; Get Log Page moves 512 bytes by device MWr.

In a capture: an admin CQE whose CID matches an old AER SQE, Dword 0 with type/info/log fields, then a Get Log Page with CDW10 bit 15 clear.

Missing events: count outstanding AERs, check Feature 0Bh, look for RAE = 1 reads; the log still shows the condition even when the event was lost.

Telemetry capture discipline

Telemetry logs are large — data areas can reach megabytes — so they are read in chunks with Get Log Page's offset fields (Log Page Offset Lower/Upper in CDW12/CDW13) and a transfer size bounded by the Maximum Data Transfer Size (MDTS; 128 KiB on the Lab SSD). A consistent host-initiated capture is Derived:

  1. Get Log Page 07h with the Log Specific Parameter's "Create Telemetry Host-Initiated Data" bit set, reading only the 512-byte header. The controller snapshots its internal state now.
  2. From the header, take the last block of the data area you want (Data Area 1, 2, 3, or 4 where extended telemetry is supported) and the generation number.
  3. Read the data in MDTS-sized chunks at increasing offsets without the create bit (setting it again would start a new snapshot).
  4. Re-read the header; if the generation number changed, the chunks may mix two snapshots — repeat.
  5. Store the file with serial number, firmware revision, timestamp and the reason for capture.

Confirm offset alignment requirements (multiples of 512 bytes are expected for telemetry) and header field positions in the Telemetry sections of NVMe Base 2.4 Uncertain.

Specification discipline

  • NVM Express Base Specification, Revision 2.4 — Asynchronous Event Request; Get Log Page; Log Page Identifiers (SMART / Health Information, Error Information, Telemetry Host-Initiated and Controller-Initiated, Endurance Group Information, Persistent Event); Features (Asynchronous Event Configuration, Temperature Threshold, Host Controlled Thermal Management); Device Self-test
  • NVM Command Set Specification, Revision 1.3 — which I/O commands count toward data units and command counts.
  • NVM Express Management Interface Specification, Revision 2.2 — out-of-band health status.

Normative AER is admin opcode 0Ch; Get Log Page 02h with LID in CDW10 bits 7:0 and RAE in bit 15; SMART log 02h is mandatory with the layout of Chapter 57; log identifiers 01h, 03h, 06h, 07h, 08h, 09h, 0Dh; features 04h and 0Bh; Device Self-test 14h. An event type is not reported again until the host reads the associated log with RAE cleared.

Informative Descriptions of how hosts may use telemetry and Percentage Used. Optional Telemetry, Endurance Group log, Persistent Event log, per-namespace SMART, Host Controlled Thermal Management, Device Self-test, 2.4 voltage monitoring — check Identify before use.

Percentage Used and composite temperature formulas; what counts as a media error; counter persistence interval; telemetry contents and size; self-test coverage; Linux's handling of AER completions.

The Log Specific Parameter field widened across revisions; NUMD split into upper and lower parts in 1.2.1-era revisions; extended telemetry (Data Area 4), Persistent Event log and Endurance Group features arrived in 1.3/1.4; NVMe 2.4 adds voltage monitoring with alerts and historical logs (identifiers not verified; see 2026 NVMe 2.4 Updates).

The specification does not say when to replace a drive, how often to poll, how to weigh spare against Percentage Used, or what telemetry contains. Check in the text: the Asynchronous Event Information values for each type, the Persistent Event log context actions (establish, read, release), telemetry header field offsets and offset alignment, and Feature 0Bh bit assignments in 2.4.

Never assume a missed event means no condition (read the log), that RAE = 1 is harmless, that telemetry captured across a generation change is consistent, or that counters from different firmware revisions are comparable.

Labs

Beginner lab — decode events and log commands

Safe lab Paper. Objective: decode AER completions and Get Log Page CDW10 values. Prerequisites: Chapter 57. Setup: AER Dword 0 values 0x0002_0101, 0x0002_0001, 0x0002_0201; CDW10 values 0x007F_0002, 0x007F_8002, 0x0000_0001.

Procedure: decode type, information and log page for each Dword 0; decode LID, RAE and NUMDL for each CDW10. Observations: which reads re-arm events. Questions: which CDW10 returns only 4 bytes of the Error Information log? Which read would leave the SMART/Health type masked? What should follow each AER completion? Expected reasoning: bit-field extraction with the positions in the Mechanism section.

Solution

0x0002_0101: type 1h SMART/Health, info 01h temperature threshold, log 02h. 0x0002_0001: info 00h NVM subsystem reliability. 0x0002_0201: info 02h spare below threshold. 0x007F_0002: LID 02h, RAE 0, NUMDL 0x7F → 128 dwords (512 bytes): re-arms. 0x007F_8002: same but RAE = 1: leaves the type masked. 0x0000_0001: LID 01h, NUMDL 0 → 1 dword (4 bytes). After each AER completion: read the indicated log with RAE = 0 and submit a new AER. (Information values per the Asynchronous Event Request definition; confirm in Base 2.4.)

Extension: encode the Get Log Page CDW10 for the first 4 KiB of Telemetry Host-Initiated with the create bit set, leaving the LSP bit position to be confirmed in the spec.

Intermediate lab — inject a critical warning in a VM

Caution lab QEMU virtual machine with an emulated NVMe controller. Objective: watch an event travel from injection to user space and see the effect of event configuration and RAE. Prerequisites: beginner lab; Lab Environment. Setup: QEMU started with a QMP socket and -device nvme,id=nvme0,serial=hlth01,drive=…. Recent QEMU versions expose a smart_critical_warning property on the NVMe device that injects Critical Warning bits Version-dependent — check your QEMU's NVMe documentation.

Procedure:

  1. In the guest: nvme get-feature /dev/nvme0 -f 0x0b -H. If the SMART warning bits are disabled, enable them in the VM only: nvme set-feature /dev/nvme0 -f 0x0b -v 0x1f.
  2. Start udevadm monitor --kernel --property --subsystem-match=nvme.
  3. From the QMP monitor: qom-set /machine/peripheral/nvme0 smart_critical_warning 1.
  4. Read the SMART log with RAE clear; set the property to 0, then to 1 again; observe a second event.
  5. Repeat step 4 reading with RAE set (if your nvme-cli exposes it) and observe that the second event does not arrive.

Observations: the uevent fields, the Critical Warning byte, and which injections produced events. Questions: what did step 1 reveal about the default configuration? Why does the second injection need a prior RAE = 0 read? Is the condition visible in the log even when no event was sent? Expected reasoning: event delivery requires enablement, an outstanding AER and an unmasked type.

Solution

Many configurations do not enable SMART critical-warning events by default — the driver enables the notice events it handles — so step 1 often shows them off, and without step 1's change the injection produces no uevent although the log shows the bit. With events enabled, the first injection produces a uevent whose AEN value decodes to type 1h, information 00h–02h depending on emulation, log 02h. The second injection arrives only after a read with RAE = 0; with RAE = 1 the type stays masked. The Critical Warning byte reflects the condition regardless. Exact emulation behaviour is version-dependent.

Extension: inject a temperature event by lowering the Temperature Threshold feature (04h) below the emulated temperature, inside the VM.

Safe lab Simulation. Objective: show how host behaviour determines which events are delivered. Setup: save as aen_rearm_sim.py.

#!/usr/bin/env python3
"""aen_rearm_sim.py - model of NVMe SMART/Health asynchronous event delivery.

Controller rules modelled (simplified from the NVMe Base Specification):
  * an event is reported only if enabled in Asynchronous Event Configuration (0Bh)
    and an Asynchronous Event Request (AER) command is outstanding;
  * after reporting, that event type is masked until the host reads the
    associated log page with Retain Asynchronous Event (RAE) = 0;
  * an event that occurs while masked or with no AER outstanding stays pending.
"""

EVENTS = [  # (time_s, event) - synthetic sequence for one drive
    (100, "temperature"), (160, "temperature"), (900, "spare"), (950, "reliability"),
]


def run(host):
    enabled = host.get("enabled", {"temperature", "spare", "reliability"})
    aers = host["aers"]                     # outstanding AER commands
    masked, pending, delivered = False, [], []
    for t, ev in EVENTS:
        if ev not in enabled:
            continue
        pending.append((t, ev))
        while pending and aers > 0 and not masked:
            te, e = pending.pop(0)
            aers -= 1
            masked = True                    # SMART/Health type now masked
            delivered.append(f"{e}@{te}s")
            # host reaction
            if host["resubmit"]:
                aers += 1
            if host["rae"] == 0:
                masked = False               # log read with RAE=0 re-arms
    return delivered, [f"{e}@{t}s" for t, e in pending]


HOSTS = {
    "correct daemon":            {"aers": 4, "resubmit": True,  "rae": 0},
    "reads log with RAE=1":      {"aers": 4, "resubmit": True,  "rae": 1},
    "never resubmits AERs":      {"aers": 1, "resubmit": False, "rae": 0},
    "spare warning not enabled": {"aers": 4, "resubmit": True,  "rae": 0,
                                  "enabled": {"temperature", "reliability"}},
}

if __name__ == "__main__":
    for name, h in HOSTS.items():
        got, stuck = run(h)
        print(f"{name:<26} delivered: {', '.join(got) or '-':<52} never seen: {', '.join(stuck) or '-'}")

Procedure: run it; add a host that reads with RAE = 0 but only after a 600 s delay; add a controller reset at 500 s after which the host forgets to resubmit AERs. Questions: why does the "never resubmits" host see exactly one event? Why does the "not enabled" host still have a correct log? What single host check would catch all three bugs? Expected reasoning: each bug breaks one of the three delivery conditions.

Solution

Correct daemon: all four events. RAE = 1: only the first; the type stays masked. Never resubmits: the only AER is consumed by the first event. Spare not enabled: the spare event is not reported, but Critical Warning bit 0 is set in the log. A single safety net catches all three: periodic polling that compares the Critical Warning byte with the last event received — any bit set without a matching event means delivery is broken. With a reset at 500 s and no resubmission, the spare and reliability events are lost; drivers must resubmit AERs and re-apply Feature 0Bh after every controller-level reset.

Extension: add the Error Information and notice event types, which are masked independently.

Senior forensic lab — fleet failures: drive, firmware or bay?

Safe lab Synthetic data analysis. Objective: attribute failures in a fleet and quantify the value of delta alerting. Prerequisites: this module; Root Cause, Ambiguity and Forensic Reporting. Setup: save as fleet_health.py (it generates a deterministic synthetic fleet).

#!/usr/bin/env python3
"""fleet_health.py - synthetic fleet SMART snapshots: thresholds versus deltas.

Generates a deterministic synthetic fleet (no real data), then compares two
alerting rules and groups failures by firmware revision and drive bay.
"""
import random
from collections import Counter

rnd = random.Random(2026)
DAYS = 120


def make_drive(i):
    fw = "FW-B" if i % 3 == 0 else "FW-A"
    bay = i % 8                                   # bays 6 and 7 sit behind the PSU
    hot = bay in (6, 7)
    fails = rnd.random() < (0.12 if hot else 0.02)
    start = rnd.randint(30, 90) if fails else None
    snaps, spare, media, tmt2 = [], 100, 0, 0
    for d in range(DAYS):
        tmt2 += rnd.randint(2, 6) if hot else rnd.randint(0, 1)
        if fails and d >= start:
            media += rnd.randint(0, 3)
            if d >= start + 6:
                spare = max(0, spare - rnd.randint(2, 9))
        cw = (1 if spare < 10 else 0) | (4 if media > 40 else 0)
        snaps.append((d, spare, media, tmt2, cw))
    return {"id": i, "fw": fw, "bay": bay, "fails": fails, "snaps": snaps}


def first_day(drive, rule):
    for d, spare, media, tmt2, cw in drive["snaps"]:
        if rule == "critical warning" and cw:
            return d
        if rule == "deltas" and (media >= 3 or spare < 100):
            return d
    return None


if __name__ == "__main__":
    fleet = [make_drive(i) for i in range(800)]
    failing = [x for x in fleet if x["fails"]]
    print(f"drives {len(fleet)}, failing {len(failing)}")
    for rule in ("critical warning", "deltas"):
        days = [first_day(x, rule) for x in failing]
        seen = [d for d in days if d is not None]
        lead = [cw - dl for cw, dl in zip([first_day(x, "critical warning") for x in failing], days)
                if cw is not None and dl is not None]
        false_pos = sum(1 for x in fleet if not x["fails"] and first_day(x, rule) is not None)
        print(f"rule {rule:<16}: detected {len(seen)}/{len(failing)}, false alarms {false_pos}"
              + (f", median lead over critical warning {sorted(lead)[len(lead)//2]} days" if rule == "deltas" else ""))
    print("failures by firmware:", dict(Counter(x["fw"] for x in failing)),
          " population:", dict(Counter(x["fw"] for x in fleet)))
    print("failures by bay     :", dict(sorted(Counter(x["bay"] for x in failing).items())))
    hot = [x["snaps"][-1][3] for x in fleet if x["bay"] in (6, 7)]
    cool = [x["snaps"][-1][3] for x in fleet if x["bay"] not in (6, 7)]
    print(f"mean TMT2 transitions after {DAYS} days: bays 6-7 {sum(hot)/len(hot):.0f}, others {sum(cool)/len(cool):.0f}")

Procedure: run it; compute failure rates per firmware and per bay group; compare alert rules. Questions: is FW-B worse? What explains the bay pattern, and what evidence supports it? How much warning do deltas give over Critical Warning? What does the model omit that would create false alarms in a real fleet? Expected reasoning: rates, not counts; environment evidence (thermal counters) alongside failures.

Solution

Output: 41 failing of 800; both rules detect all 41 with no false alarms; deltas lead Critical Warning by a median of 20 days. FW-B: 18/267 ≈ 6.7%; FW-A: 23/533 ≈ 4.3% — a difference of a few drives, easily chance, and not a basis for a firmware rollback. Bays 6–7: 31 failures of 200 (15.5%); other bays: 10 of 600 (1.7%) — a ninefold difference. Thermal management transition counts (mean ~480 versus ~60) show bays 6–7 run hot; heat is a plausible accelerator. Report: "failure rate correlates with bays 6–7 (high confidence), which show far more thermal throttling; firmware difference not significant at this sample size". The model omits benign media errors, counter resets from drive swaps, and firmware-dependent counter changes — all of which create false deltas and require identity tracking (serial, firmware) per snapshot.

Extension: compute a simple significance test for the firmware difference with the standard library.

Debugging

Pattern 1 — health events never arrive
SymptomCritical Warning bits are set in polled logs, but no event was ever received.
Possible causesType masked by an RAE = 1 read; no AER outstanding (not resubmitted, especially after reset); warnings not enabled in Feature 0Bh; user space ignores the uevent.
EvidenceFeature 0Bh value; CDW10 of log reads; AER submissions after resets.
First checkget-feature 0x0b.
Second checkMonitoring tool's RAE setting.
Disambiguating experimentIn a VM or lab, inject two events of one type and observe which step fails.
Likely conclusion / confidenceHost configuration — high once 0Bh and RAE are known.
Pattern 2 — telemetry the vendor rejects as inconsistent
SymptomVendor tools fail to parse a capture or report mixed snapshots.
Possible causesCreate bit set on every chunk; generation changed during reading; wrong offsets or truncated length; capture after a reset discarded the state.
EvidenceCapture script's commands; header generation before and after; file size versus header data area size.
First checkHeader generation numbers at start and end.
Second checkOffsets advance by exactly the chunk size; final size matches the header.
Disambiguating experimentRepeat with nvme-cli's telemetry-log command and compare sizes and headers.
Likely conclusion / confidenceCapture-script bug — high if the reference tool's capture parses.
Pattern 3 — counters jump or go backwards
SymptomPercentage Used steps by 10, or Power On Hours decreases.
Possible causesFirmware update changed formulas; drive replaced; snapshot from a different device or NSID; decoder bug; unsafe power loss dropped unpersisted increments.
EvidenceSerial and firmware revision of each snapshot; Persistent Event log firmware-commit entries; NSID used.
First checkIdentity fields of both snapshots.
Second checkFirmware Slot log and Persistent Event log between them.
Disambiguating experimentRe-read with NSID FFFFFFFFh and decode raw bytes with a known-good decoder.
Likely conclusion / confidenceIdentity or firmware change — high once identity is verified.
Pattern 4 — media errors with no host-visible failure
SymptomMedia and Data Integrity Errors increments; applications report nothing.
Possible causesRedundancy above the drive masked it; a background read (scrub, self-test) hit it; Protection Information mismatch from a bypassing write path.
EvidenceError Information entries (SQID, status, LBA); kernel logs; write history.
First checkMatch each increment to an Error log entry.
Second checkSQID 0 or a background source versus an I/O queue.
Disambiguating experimentCompare the LBA's data (PI checks off) with a redundant copy.
Likely conclusion / confidenceDepends on the experiment — low until done.
Pattern 5 — monitoring hurts the workload
SymptomPeriodic latency spikes, or a laptop drive that never reaches deep power states.
Possible causesScheduled telemetry captures; frequent SMART polls waking the drive; several agents polling independently.
EvidenceAdmin command timestamps; spikes aligned with the monitoring schedule; APST residency.
First checkList every agent that issues admin commands and its interval.
Second checkLatency spike period versus polling period.
Disambiguating experimentPause monitoring for an hour.
Likely conclusion / confidenceMonitoring side effect — high if the spikes vanish.

Interview

Beginner

  1. Polling versus events: what is the difference?

    Model answer

    Polling reads log pages on a schedule; events are AER completions the drive sends when an enabled condition occurs.

  2. What is an Asynchronous Event Request?

    Model answer

    An admin command (0Ch) the host leaves outstanding so the controller can complete it when an event occurs.

  3. Which log explains a media error count increase?

    Model answer

    The Error Information log (01h): it lists the command, status and LBA.

  4. What is telemetry, and who reads it?

    Model answer

    A vendor-defined diagnostic dump in a standard container (logs 07h/08h); the vendor's tools decode it.

  5. Does a Critical Warning of 0 mean the drive is healthy?

    Model answer

    No — only that no defined critical condition is reported now; trends and other logs matter.

Intermediate

  1. What does RAE do?

    Model answer

    With RAE = 1 the log read does not clear the associated event; with RAE = 0 it does, unmasking the event type.

  2. Decode AER Dword 0 = 0x0002_0101.

    Model answer

    Type 1h SMART/Health, information 01h temperature threshold, log page 02h.

  3. Why must AERs be resubmitted after a controller reset?

    Model answer

    Outstanding commands, including AERs, are discarded by a controller-level reset.

  4. How do you read a 24 MiB telemetry log on a drive with 128 KiB MDTS?

    Model answer

    Create and read the header, then read 192 chunks with increasing offsets without the create bit, then verify the generation number.

  5. Why might Data Units Written increase by 1 for a single 4 KiB write?

    Model answer

    The counter rounds up per thousand 512-byte units.

Advanced

  1. A guard check error appears with no application error. What are the two families of cause?

    Model answer

    Media corruption caught by PI, or a host write path that stored data without valid PI; separate them by comparing data with a redundant copy.

  2. How do you prove a telemetry capture is consistent?

    Model answer

    Same generation number before and after, offsets contiguous, final size equal to the header's data area size.

  3. How can monitoring change the result it measures?

    Model answer

    Admin commands wake drives and reset idle timers; telemetry capture adds latency; polling frequency alters power and latency.

  4. What does the Persistent Event log add to SMART?

    Model answer

    Timestamps and ordering for power, reset, firmware and thermal events, which turn counters into a timeline.

  5. Why is a missed event not a lost condition?

    Model answer

    The log still reflects it; polling Critical Warning against received events detects delivery failures.

Senior

  1. Design fleet health alerting.

    Model answer

    Events for immediacy; daily polling with identity-stamped snapshots; alerts on any Critical Warning bit and on deltas (spare, media errors, thermal counters, unsafe shutdowns per boot); cohort analysis by firmware, bay and platform; telemetry on demand.

  2. Firmware B shows more failures. How do you decide whether to roll back?

    Model answer

    Compare rates with confidence intervals, control for environment and age, check for counter-formula changes, and look for a mechanism in telemetry before acting.

  3. When is it right to capture telemetry before replacing a drive?

    Model answer

    Whenever root cause matters (fleet-level patterns, warranty, vendor escalation), and always before resets or firmware updates.

  4. What will 2.4 voltage monitoring change in field investigations?

    Model answer

    It gives device-side evidence of supply discrepancies, turning "drive versus platform power" arguments into data; identifiers must be confirmed in Base 2.4.

  5. How do you keep monitoring from hurting latency-sensitive tenants?

    Model answer

    One agent per host, bounded polling rates, telemetry only on demand, and out-of-band NVMe-MI where the platform supports it.

Quiz

  1. Which CDW10 reads the full SMART log and re-arms SMART/Health events?

    • 0x007F_8002
    • 0x007F_0002
    • 0x0000_0002
    • 0x00FF_0002
    Answer and reasoning

    LID 02h, RAE (bit 15) clear, NUMDL 7Fh = 128 dwords.

  2. AER Dword 0 = 0x0002_0201 means…

    • Temperature threshold
    • Reliability degraded
    • Spare below threshold
    • Error log changed
    Answer and reasoning

    Information byte (15:8) = 02h.

  3. After a controller reset, what must the host do for health events?

    • Resubmit AERs and re-apply Feature 0Bh
    • Nothing
    • Read every log with RAE = 1
    • Run a self-test
    Answer and reasoning

    Outstanding AERs and non-saved features are lost at reset.

  4. A telemetry header's generation number changed between start and end of a capture. The capture is…

    • Fine
    • Truncated
    • Encrypted
    • Possibly mixed from two snapshots
    Answer and reasoning

    New data was captured during reading; repeat the capture.

  5. In Trace 3, what single change fixes event delivery?

    • More AERs
    • Read with RAE = 0 after handling the event
    • Disable Feature 0Bh
    • Shorter polling interval
    Answer and reasoning

    The type stayed masked because the event was retained.

  6. Why does an AER not hit the driver's command timeout?

    Model answer

    It is expected to stay outstanding indefinitely; drivers exclude it from timeout handling.

  7. FW-B fails 6.7% and FW-A 4.3% with tens of failures each. What do you conclude?

    Model answer

    Not enough on its own: the difference could be chance; control for bay and age and look for a mechanism.

  8. Name three items to store with every SMART snapshot.

    Model answer

    Serial number, firmware revision, timestamp (also NSID and tool version).

Teach-back

  1. To a child: why might the lighthouse keeper's second storm flare never be seen?

    Model explanation

    "She only fires another storm flare after someone reads the storm page and says 'got it', and only if she still has flares. If the boat reads without saying 'got it', or never brings new flares, the next storm is only in the logbook."

  2. To a junior engineer: how do you handle a SMART/Health event correctly?

    Model explanation

    "Decode Dword 0 for type, information and log page; read that log with RAE = 0; submit a new AER; store the snapshot with identity; act on the warning; and make sure your setup re-applies Feature 0Bh and AERs after any reset."

  3. To a senior engineer: what makes fleet health data trustworthy?

    Model explanation

    "Identity on every snapshot, deltas rather than levels, rates rather than counts, environment evidence alongside failures, a cross-check that events match polled warnings, consistent telemetry captured before resets, and monitoring whose own cost is bounded and measured."
