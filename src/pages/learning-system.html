Reading builds familiarity. Testing, spacing and teaching build skill. This page defines the six question types every chapter uses, gives you review checkpoints after every Part (with hidden answers), lays out the weekly lab rhythm, and explains how to run and grade a teach-back.

Why a learning system

Most people who "studied NVMe" can recognize the words Submission Queue, doorbell and Transaction Layer Packet (TLP). Far fewer can predict what a protocol analyzer will show when a doorbell is written. Recognizing something you read and producing it yourself are different skills, and only the second one helps at 2 a.m. in a debug session.

Three well-established learning effects shape everything on this page:

  • Retrieval practice. Pulling an answer out of memory strengthens it far more than reading it again. That is why every chapter ends with questions and hides the answers.
  • Spacing. Reviewing just as you are about to forget works better than reviewing right away. That is why there are checkpoints after each Part and a review schedule, not a single exam at the end.
  • Generation and explanation. Explaining something in your own words, to a specific audience, exposes gaps that reading hides. That is why teach-back is mandatory.

If you want to remember where you hid your treasure, drawing the map once is not enough. You go back the next day and try to find it without the map. Then again next week. Every time you find it from memory, the path gets clearer.

Pilots do not stay current by rereading the manual. They fly simulator checkrides at intervals, with failures injected, and they brief the plan aloud before every flight. The checkride is the test, the interval is the spacing, and the briefing is the teach-back.

Pilot checkrides are graded by an examiner. Here you will mostly grade yourself, which is much easier to fool. The rubrics on this page exist to make self-grading honest. Also, a simulator models reality closely; the synthetic traces in this course are simplified and labeled as such, so passing a checkpoint is not the same as being ready for a real capture.

Answer first, then open the answer. Write your answer down, even a few words. A question you "would have got" without committing to an answer does not count.

A. Recall

Recall questions check that the vocabulary and key values are in your head, not just on the page. They are the least interesting type and the most necessary: you cannot reason about a doorbell if you have to look up where doorbells live.

Writing them: one fact per question; no trick wording; prefer values you will need in later reasoning (offsets, sizes, directions) over trivia (the year something was ratified, unless revision context matters).

  1. At what offset in BAR0 does the NVMe doorbell region start?

    Answer

    1000h. Individual doorbells are spaced by the stride given by CAP.DSTRD (4 << DSTRD bytes).

  2. Which PCIe layer adds the sequence number and Link CRC (LCRC)?

    Answer

    The Data Link Layer.

B. Understanding

Understanding questions ask why. They are where the 16 questions of the course method (what is it, why was it created, who creates it, who consumes it, what if it is wrong…) turn into test items.

Writing them: ask for a reason, a contrast or a consequence. Avoid "explain X" with no angle, which invites copying a paragraph.

  1. Why does the host need a Phase Tag in each CQE instead of reading a "completion count" register from the controller?

    Model answer

    Reading a device register is an uncached, non-posted MMIO read, which is slow (a full PCIe round trip) and stalls the CPU. The phase bit lets the host detect new entries by reading host memory only. The controller writes the CQE and its phase together, so a matching phase means the whole entry is valid.

  2. Why is a PCIe Memory Write "posted"? What would be lost if it needed a completion?

    Model answer

    Posting lets the sender move on immediately and lets writes stream without round trips, which matters for data and for doorbells and interrupts. Requiring completions would add a round trip per write, use tags and completion bandwidth, and slow every DMA write. Reliability is handled hop-by-hop by the Data Link Layer instead.

C. Application

Application questions give new numbers or a new situation. They test whether you can use the model, which is the first point at which most learners discover gaps.

Writing them: change one parameter from the chapter's example (a different DSTRD, offset, MPS, LBA size) and ask for the result. Always ask for the working.

  1. CAP.DSTRD = 1. What is the address of the CQ3 head doorbell if BAR0 = 0xFE60_0000?

    Model answer

    Stride = 4 << 1 = 8 bytes. CQ y head = 1000h + (2y + 1) × stride = 0x1000 + 7 × 8 = 0x1038. Address = 0xFE60_1038.

  2. A device with MRRS = 512 must fetch 6 KiB of write data. How many Memory Read requests does it issue at minimum, assuming 4 KiB-aligned buffers in two pages (4 KiB + 2 KiB)?

    Model answer

    Requests cannot cross a 4 KiB boundary and cannot exceed 512 bytes. 4096 / 512 = 8 for the first page and 2048 / 512 = 4 for the second: 12 requests.

D. Debugging

Debugging questions give evidence (a trace excerpt, a log, a register dump) and ask what it means and what to do next. A good answer separates what is observed from what is inferred, names the first abnormal event, and proposes a check that tells hypotheses apart.

  1. A trace shows the SQ1 tail doorbell written with value 4. No Memory Read from the device follows within 10 ms. CSTS was last read as 0x00000001. List two hypotheses and one check that tells them apart.

    Model answer

    Observed: doorbell write; no visible SQE fetch in the captured interval; CSTS.RDY = 1 at last read. H1: the doorbell went to the wrong offset (for example SQ1 is not where the driver thinks because DSTRD was misread, or SQ1 was never created), so the controller ignored it. H2: the device cannot master the bus (Bus Master Enable cleared, for example after a reset that did not restore config space). Check: read the Command register in config space (BME bit) and the driver's computed doorbell address against CAP.DSTRD. Also confirm that the capture includes upstream traffic (direction filters), because "no fetch visible" is only evidence if the capture would have shown it.

E. Senior thinking

Senior questions have no single right answer. They test judgment: weighing cost against risk, deciding under uncertainty, explaining to people with different needs.

  1. A rare data-corruption bug has a probable but unconfirmed cause: a missing write barrier before the doorbell on one architecture. Adding the barrier costs about 1% IOPS on all platforms. Release is in two weeks. What do you recommend?

    Model answer

    Corruption outranks 1% performance, so ship the barrier, but scope and label it: apply it on the affected architecture (or everywhere if the code path is shared and the cost is acceptable), record it as a mitigation with "Likely" confidence rather than a confirmed root cause, and keep the investigation open with a stress test that should reproduce the corruption without the barrier. State what would change the decision: if the stress test shows corruption with the barrier, the hypothesis is wrong and the release needs re-evaluation.

F. Lab

The lab item is one concrete hands-on task with an artifact at the end. Labs carry a safety level: Safe lab (simulation or read-only commands), Caution lab (writes to a test device, can lose data on it), Expert lab (register writes, resets, error injection; dedicated hardware only).

Example lab item Safe lab: run the queue simulator in the weekly lab section with a 4-entry CQ, post seven completions, and record head, tail and phase after each step. Then set buggy_host=True and explain, using your table, why the host stops seeing completions.

A complete chapter test: Doorbells

This is what a full end-of-chapter test looks like, built for Chapter 28, Doorbells. Use it as a model when you write tests for yourself or for others. The numbers come from the course's synthetic lab system.

A. Recall (5)

  1. Which register field determines the spacing between doorbell registers?

    Answer

    CAP.DSTRD (Doorbell Stride): stride = 4 << DSTRD bytes.

  2. What value does the host write to a submission queue tail doorbell?

    Answer

    The new tail index: the slot after the last entry it has written.

  3. Which doorbell does the host write after consuming completions?

    Answer

    The completion queue head doorbell for that CQ.

  4. What PCIe transaction carries a doorbell write?

    Answer

    A posted Memory Write TLP with a 1-DW payload, from the root complex to the device's BAR0 range.

  5. In the lab system, what is the address of the SQ1 tail doorbell?

    Answer

    0xFE60_1008 (BAR0 0xFE60_0000 + 0x1008, DSTRD = 0).

B. Understanding (5)

  1. Why must the SQE memory writes be visible before the doorbell write reaches the device?

    Model answer

    The controller fetches entries as soon as it sees the new tail. If the entry is still in a CPU write buffer or cache path, the controller reads stale data and executes a garbage or old command. Drivers use a write barrier between the SQE store and the MMIO doorbell store.

  2. Why is one doorbell write enough for several new commands?

    Model answer

    The value is an index; everything between the controller's head and the new tail is new. Batching amortizes the cost of the MMIO write.

  3. What happens if the host never writes the CQ head doorbell?

    Model answer

    The controller believes the CQ slots are still occupied. When the CQ is full it cannot post more completions, so commands appear to hang even though the device finished them.

  4. Why is the doorbell in device memory (BAR) while the queue is in host memory?

    Model answer

    The device needs a cheap, immediate notification (a posted write to its own register), while the bulk data (64-byte entries) is better fetched by DMA in batches. Host-memory queues scale to many large queues without device SRAM.

  5. How does a doorbell differ from an interrupt?

    Model answer

    Direction (host→device vs device→host), content (queue index vs vector message data), and mechanism (MMIO write to a BAR vs MSI-X memory write to the platform's interrupt address range).

C. Application (5)

  1. DSTRD = 0. Give the addresses (offsets) of SQ4 tail and CQ4 head.

    Answer

    SQ4 tail = 0x1000 + 8 × 4 = 0x1020; CQ4 head = 0x1024.

  2. SQ1 has 1024 entries. Tail is 1022. The host writes three commands. What doorbell value does it write?

    Answer

    Slots 1022, 1023, 0 are filled; the new tail is 1. The host writes 1.

  3. SQ size 16, controller head 14, host wants to write 3 more entries with tail at 12. Is there room?

    Answer

    Entries in use = (12 − 14 + 16) mod 16 = 14. Maximum usable is size − 1 = 15. Only one more entry fits; the third command must wait.

  4. How many doorbell TLPs does a driver produce for 64 commands if it batches 8 per doorbell?

    Answer

    8 SQ tail doorbell writes, plus CQ head doorbell writes depending on how it reaps completions.

  5. Write the trace row you expect for the doorbell in question 2.

    Answer

    Host→Dev, MWr, Addr = 0xFE60_1008, Len = 1, Data = 0x00000001, Requester = RC.

D. Debugging (3)

  1. The device fetches SQE slot 7 after a doorbell of 8, but the decoded SQE has opcode 0 and all-zero fields. What is the most likely class of bug?

    Model answer

    Ordering: the doorbell overtook the SQE store (missing barrier), or the driver wrote the entry to a different slot than it published. Check the driver's barrier and slot arithmetic; compare host memory contents after the fact with the fetched bytes.

  2. The analyzer shows a doorbell value of 1024 to a 1024-entry SQ. What will the controller do, and what will the host see?

    Model answer

    1024 is not a valid index (0–1023). The Base specification defines an asynchronous error event for invalid doorbell write values; the controller should not treat it as normal. The host sees an Asynchronous Event Request completion, if one is outstanding, and its commands do not run. Confirm the exact event in the specification.

  3. Doorbells reach the device but nothing happens; CSTS.CFS = 1. What does that tell you?

    Model answer

    The controller reports a fatal status and is not processing commands. The doorbell is not the problem. Collect logs (telemetry if available), then reset the controller. The first abnormal event is whatever led to CFS, earlier in the timeline.

E. Senior thinking (2)

  1. In a virtual machine, every doorbell write traps to the hypervisor. What design options exist, and what does each cost?

    Model answer

    Batch more per doorbell (latency at low queue depth); shadow doorbells via Doorbell Buffer Config (the emulated controller polls host memory, which costs CPU in the host); device assignment with SR-IOV so writes go to real hardware (needs SR-IOV-capable device, loses some flexibility such as live migration unless supported — NVMe 2.4's migration features target this).

  2. A junior engineer proposes reading back each doorbell register after writing it, "to make sure it arrived." Respond.

    Model answer

    It adds a full non-posted round trip per command and gives no useful information: doorbell registers are not meant to be read back as a confirmation mechanism. Delivery of posted writes is ensured by the link layer. The read does force earlier posted writes to complete (a read cannot pass them), but if that ordering is what is wanted, it should be done deliberately and documented, not as a check.

F. Lab (1)

Safe lab Extend the queue simulator below so that the host batches submissions and writes one doorbell per batch of N. Measure how many doorbell writes are needed for 1000 commands for N = 1, 4, 16, and plot or tabulate the result. Then add a "missing barrier" fault: with probability p, the controller sees the doorbell before the last entry is written. Show how batching changes the impact of the fault.

Grading your own answers

Self-grading is honest only if the rules are fixed before you look. Use these.

Self-grading scale
MarkMeaningAction
2 — RightCorrect and complete, with the reason or workingSchedule the next review at the next interval
1 — PartlyCorrect core, missing a condition, owner, direction or unitWrite the missing piece in your own words; review again in 3 days
0 — Wrong or blankIncorrect, or correct only by guessingRe-read the linked section, then answer again tomorrow from memory

Some answers look right but deserve a 1:

  • A number without units or working ("0x1038" without stride shown).
  • A mechanism without its owner ("the phase bit flips" — who flips it, and when?).
  • A debugging answer that gives a conclusion but no evidence or check.
  • Any answer that confuses the layers (calling a CQE a "completion TLP").

A score of 85% tells you little. The list of questions you got 0 on tells you exactly what to study. Keep that list; it is the most valuable study document you will produce.

A spaced-review scheduler

A small Leitner-box scheduler: each card moves up a box when answered correctly and back to box 0 when missed, and each box has a longer interval. It uses only the Python standard library.

#!/usr/bin/env python3
"""Leitner-style spaced review scheduler (standard library only)."""
import datetime as dt

INTERVALS = [1, 3, 7, 21, 60]          # days until next review, per box

class Card:
    def __init__(self, question, chapter):
        self.question = question
        self.chapter = chapter
        self.box = 0
        self.due = dt.date.today()

    def review(self, mark, today):
        """mark: 2 = right, 1 = partly, 0 = wrong (see grading scale)."""
        if mark == 2:
            self.box = min(self.box + 1, len(INTERVALS) - 1)
        elif mark == 1:
            self.box = max(self.box - 1, 0)
        else:
            self.box = 0
        self.due = today + dt.timedelta(days=INTERVALS[self.box])

def due_cards(cards, today):
    return [c for c in cards if c.due <= today]

if __name__ == "__main__":
    today = dt.date(2026, 10, 4)
    cards = [Card("Offset of the doorbell region in BAR0?", "ch28"),
             Card("Who flips the CQ phase tag, and when?", "ch25"),
             Card("Direction of data TLPs in an NVMe Read?", "ch32")]
    for c in cards:
        c.due = today
    # Simulated session: right, partly, wrong
    for card, mark in zip(due_cards(cards, today), [2, 1, 0]):
        card.review(mark, today)
    for c in cards:
        print(f"{c.chapter}  box={c.box}  next={c.due}  {c.question}")

Running it prints each card's box and next review date: the first card moves to box 1 (due in 3 days), the second stays at box 0 (due tomorrow), the third returns to box 0 (due tomorrow). Replace the sample cards with your zeros list.

Review checkpoints after each Part

One checkpoint per Part of the course. Parts I–III and Parts VII–VIII are short and are reviewed together. Do each checkpoint about a week after finishing the Part, not the same day.

Checkpoint: Parts I–III — Foundations, storage, why NVMe

Pages: ch01, ch02, ch03.

  1. What happens differently when a CPU load instruction targets an address mapped to RAM versus one mapped to a device?
  2. Why does a computer need storage in addition to RAM?
  3. Put these in order of typical access latency: NVMe SSD read, DRAM read, hard-disk read, L1 cache hit.
  4. What is a logical block, and what are the two common sizes?
  5. What queueing limitation of AHCI (Advanced Host Controller Interface) did NVMe remove?
  6. Why could a faster SATA link alone not deliver NVMe-class performance?
  7. A workload achieves 100,000 IOPS (input/output operations per second) at 50 µs average latency. How many commands are outstanding on average?
  8. A program writes a file and power fails one second later. Name two places the data could still have been volatile.
  9. In a capture you see the CPU write to a device address, and later the device write to RAM. Which is likely signaling and which is data movement?
  10. Why did NVMe put command queues in host memory rather than in device registers?
Answers: Parts I–III
  1. RAM: the memory controller returns cached or DRAM data. Device: the platform routes the access as a memory-mapped I/O (MMIO) transaction to the device, typically uncached, which can have side effects.
  2. RAM is volatile and relatively small and expensive; storage is non-volatile and large.
  3. L1 cache (~1 ns) < DRAM (~100 ns) < NVMe SSD (tens of µs) < hard disk (milliseconds). Values illustrative.
  4. The fixed-size unit the host addresses by logical block address (LBA); 512 bytes and 4 KiB.
  5. AHCI has one command queue of up to 32 commands per port; NVMe allows up to about 64K I/O queues of up to 64K entries each, with no shared lock needed between cores.
  6. The AHCI model needs several uncached register accesses per command and one shared queue; the protocol overhead and serialization remain even with a faster link.
  7. L = λW = 100,000 × 50 × 10⁻⁶ = 5 commands.
  8. The OS page cache (not yet written back) and the drive's volatile write cache (not yet flushed).
  9. CPU→device write: command signaling (for example a doorbell). Device→RAM write: DMA data movement (or a completion record).
  10. Host-memory queues scale to many deep queues without device SRAM, need only one small MMIO write per batch, and let each CPU core own its queue.

Checkpoint: Part IV — PCIe from zero

Pages: ch04–ch09.

  1. Name the three PCIe layers in order from software to wire.
  2. What physically is a lane?
  3. What are the per-lane transfer rates of Gen3, Gen4 and Gen5, and their encoding?
  4. What happens if a x4 device trains as x2?
  5. Name the LTSSM (Link Training and Status State Machine) states a link passes through from power-on to L0.
  6. Name three reasons a link enters Recovery.
  7. Compute the raw bandwidth per direction of a Gen5 x4 link after encoding.
  8. lspci -vvv shows LnkCap 16GT/s x4 and LnkSta 8GT/s x4. What do you check next?
  9. An LTSSM capture shows L0 → Recovery → L0 every few seconds. Name two very different explanations and how to tell them apart.
  10. Why did PCIe replace a shared parallel bus with point-to-point serial links?
Answers: Part IV
  1. Transaction Layer, Data Link Layer, Physical Layer.
  2. One differential pair for transmit and one for receive: four wires, full duplex.
  3. Gen3 8.0 GT/s, Gen4 16.0 GT/s, Gen5 32.0 GT/s; all three use 128b/130b encoding.
  4. It works at half the lanes, so about half the bandwidth. It usually indicates a lane fault, connector or routing issue, or a slot that only wires two lanes.
  5. Detect, Polling, Configuration, L0 (with substates within each).
  6. Speed change, error recovery (for example after replay rollover), and exit from L1 or L0s power states back to L0.
  7. 32 GT/s × 4 × 128/130 ÷ 8 ≈ 15.75 GB/s per direction before packet overhead.
  8. Whether the slot or upstream port supports 16 GT/s; whether the link trained at 8 GT/s due to equalization failure (AER correctable errors, equalization status bits); whether a retrain reaches 16 GT/s.
  9. Power management (L1 entry and exit go through Recovery) vs signal problems. Check whether L1 entry precedes each Recovery, whether the errors and replay counters increase, and whether disabling ASPM stops it.
  10. Parallel buses suffer clock skew at high speed, share bandwidth among devices and need arbitration; serial links with embedded clocking scale in speed and width and give each device dedicated bandwidth.

  3. Which request types are posted and which are non-posted?

Answers: Part V
  1. The transaction layer packet carrying one request, completion or message between PCIe components.
  2. 3 DW for 32-bit addressed memory requests, completions and config requests; 4 DW for 64-bit addressed memory requests (and some messages).
  3. Posted: memory writes, messages. Non-posted: memory reads, I/O reads/writes, configuration reads/writes, and atomic operations.
  4. Payload size in DW (for requests with data), or requested size in DW (for reads).
  5. Together with the Requester ID it identifies an outstanding non-posted request, so completions can be matched to it.
  6. Bus number, Device number, Function number.
  7. 8 requests. Each 512-byte request needs at least 2 completions, because no completion may carry more than 256 bytes.
  8. The host may read the data as soon as it sees the CQE. The default rule that posted writes do not pass earlier posted writes ensures the data is in memory first.
  9. One 512-byte read answered in two 256-byte pieces. Byte Count is the remaining bytes including this completion: 512 for the first, 256 for the second (last).
  10. Relaxed Ordering lets data writes be reordered for performance; the CQE must not pass the data, so it is sent with strict ordering to act as a fence.

  2. What does an ACK acknowledge?

Answers: Part VI
  1. A small link-local packet used for acknowledgements, flow control and power management; it never leaves the link.
  2. Successful receipt of all TLPs up to and including the given sequence number (ACKs are cumulative).
  3. The sender's copy of transmitted TLPs not yet acknowledged, kept for retransmission.
  4. A NAK from the receiver, or expiry of the replay timer with no ACK.
  5. Posted, Non-Posted and Completion, each with separate header and data credits.
  6. Returns credits to the transmitter as receive buffers are freed.
  7. Data is intact (replays fixed it), but every replay costs bandwidth and latency and indicates low signal margin. Check correctable error counters (Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover) and trends.
  8. Posted traffic: memory writes, including DMA data writes, doorbells and MSI-X interrupts. Reads can still be issued.
  9. All of 0x100–0x10F are acknowledged and purged from the replay buffer.
  10. Errors are detected and corrected quickly on the hop where they occur, without involving software or distant endpoints. ECRC exists as an optional end-to-end check.

3. Draw

4. Implement

The simulator below models one CQ with a controller that posts entries and a host that reaps them. Run it, then run it with buggy_host=True, which models a host that never flips its expected phase.

#!/usr/bin/env python3
"""Completion Queue phase-tag simulator (standard library only)."""

class CompletionQueue:
    def __init__(self, size, buggy_host=False):
        self.size = size
        self.slots = [{"cid": None, "phase": 0} for _ in range(size)]  # memory starts zeroed
        self.tail, self.ctrl_phase = 0, 1      # controller side
        self.head, self.host_phase = 0, 1      # host side
        self.buggy_host = buggy_host

    def is_full(self):
        return (self.tail + 1) % self.size == self.head

    def post(self, cid):
        """Controller writes a CQE (a PCIe Memory Write in a real system)."""
        if self.is_full():
            return False                       # controller must wait for a head doorbell
        self.slots[self.tail] = {"cid": cid, "phase": self.ctrl_phase}
        self.tail = (self.tail + 1) % self.size
        if self.tail == 0:
            self.ctrl_phase ^= 1               # invert phase on wrap
        return True

    def reap(self):
        """Host consumes every entry whose phase matches; then rings the CQ head doorbell."""
        done = []
        while self.slots[self.head]["phase"] == self.host_phase:
            done.append(self.slots[self.head]["cid"])
            self.head = (self.head + 1) % self.size
            if self.head == 0 and not self.buggy_host:
                self.host_phase ^= 1
        return done                            # new head value = doorbell write

def run(buggy):
    cq = CompletionQueue(4, buggy_host=buggy)
    log = []
    for batch in ([1, 2, 3], [4, 5, 6], [7, 8]):
        posted = [cid for cid in batch if cq.post(cid)]
        reaped = cq.reap()
        log.append(f"posted={posted} reaped={reaped} head={cq.head} tail={cq.tail} "
                   f"ctrl_phase={cq.ctrl_phase} host_phase={cq.host_phase}")
    return log

if __name__ == "__main__":
    for buggy in (False, True):
        print("buggy_host =", buggy)
        for line in run(buggy):
            print("  ", line)

With the correct host, every posted CID is reaped: [1, 2, 3], then [4, 5, 6], then [7, 8]. With the buggy host, the second reap returns only [4]. After the host's head wraps to 0, it still expects phase 1, but slot 0 now holds CID 5 with phase 0, so the host stops. CIDs 5 and 6 are in memory but invisible. In the third round the controller posts CID 7 into the last free slot and then refuses CID 8, because the queue looks full to it (tail + 1 = head). The host reaps nothing. To an application, that looks exactly like a device that stopped completing commands.

The teach-back method

At the end of every major chapter, explain the chapter's central concept twice:

  1. "Explain this concept as if you are teaching it to a ten-year-old."
  2. "Explain it as if you are presenting to a senior hardware engineer."

The two audiences test different things. The child test checks intuition: do you know what the thing is for and how it behaves, without hiding behind vocabulary? The senior test checks precision: can you name owners, directions, fields, layers, specifications and failure modes without being vague? Most learners are strong on one and weak on the other, and the method is designed to show which.

How to run it

  1. Close all pages and notes.
  2. Record yourself speaking, or write the explanation in one go without editing. Recording is better: hesitation is information.
  3. Wait at least an hour, then grade with the rubric below while reading the chapter's summary and specification section.
  4. Write one sentence on what to improve for each audience.
  5. On the day-21 review, do the teach-back again without looking at the first attempt, and compare.

Worked evaluations: MSI-X

Three learners explained MSI-X (Chapter 43). Here is how each was graded.

Learner 1 — to a ten-year-old

"When the SSD finishes your job, it needs to tell the computer. Each classroom has its own buzzer, and the SSD presses exactly the buzzer of the class that asked. Pressing a buzzer is really just writing a note to a special mailbox that the school office watches. If the office has switched a buzzer off, the SSD makes a mark in a book instead, and buzzes later when it's switched back on. The buzzers aren't real wires — if the SSD writes to the wrong mailbox, nobody hears anything."

Intuition 3: purpose, targeting, masking and pending all predictable from the story; limit stated. Technical 2: correct mechanism, but nothing about the table or about NVMe binding vectors to completion queues. Not required at this level, though, so this is a strong child explanation.

Learner 2 — to a senior engineer

"MSI-X is the PCIe interrupt mechanism used by NVMe. The device has a table of vectors. When a command completes, the controller sends an MSI-X interrupt to the CPU, which runs the handler. Linux allocates one vector per CPU. If interrupts are missing, check /proc/interrupts."

Intuition 1: nothing explains why it is a memory write or what masking does. Technical 1: true but vague ("sends an interrupt"), no direction or TLP type, no location of the table, no relationship to the CQE write, and only one shallow failure mode. Mark: not yet at senior level. Improvement: say what crosses the link (posted MWr, 1 DW, to the vector's address), where the table lives (BAR region via BIR/offset), how NVMe binds vectors (Create I/O CQ), and two failure modes (masked vector with pending bit set; CQ bound to the wrong vector).

Learner 3 — to a senior engineer

"MSI-X, defined in the PCI Express Base Specification's MSI-X capability, expresses an interrupt as a posted Memory Write from the function: one DW of message data to the message address in the selected table entry. The table and Pending Bit Array live in a BAR, located through the capability's BIR and offset fields; each entry has a per-vector mask, and there is a function-wide mask. NVMe binds each I/O completion queue to a vector in Create I/O Completion Queue; the admin CQ uses vector 0. Because the interrupt is a posted write on the same path as the CQE write, default ordering ensures the CQE is visible before the handler runs. Failure modes: a masked vector sets its pending bit and nothing is sent — in a trace you see the CQE MWr and no write to the interrupt window; and a wrong address or data programmed by the OS — the write appears but no handler runs, which needs the platform's interrupt remapping logs. Coalescing settings can delay interrupts by design, so check them before calling a delay a bug."

Technical 3. Intuition 2: precise, but a listener new to the topic would not know why interrupts are writes. One sentence would fix it ("PCIe has no interrupt wires, so the interrupt travels as data on the same road"). Mark: technical good, intuition slightly weak. This is the most common profile among experienced engineers.

Teaching others: the peer protocol

Teach-back works best with a listener. If you study with others, use this protocol.

  1. The explainer gets 2 minutes without interruption.
  2. The listener asks exactly three questions: one "why", one "what if it is wrong", one "how would I see it in a trace or log".
  3. The listener scores both scales and names the single most important missing piece.
  4. Swap roles. Rotate topics so nobody always explains their strongest area.

Experienced engineers teach-back without calling it that: before a design review they explain the design to a colleague from another team, and every question they cannot answer goes into the document. The method in this course is the same habit, made explicit.
