Single Root I/O Virtualization (SR-IOV) lets one PCI Express device appear as many, so that each virtual machine can own a slice of it directly. For an NVMe SSD, that means two layers of virtualization working together: PCIe Physical and Virtual Functions, and NVMe primary and secondary controllers with flexible queue and interrupt resources. This chapter teaches both, how they connect, and where the 2026 NVMe 2.4 work on exported subsystems and live migration fits.

Why this chapter exists

A cloud server may host dozens of virtual machines (VMs) that all want fast storage. Emulating an NVMe device in the hypervisor costs CPU time on every I/O and adds latency. Giving each VM a whole SSD wastes capacity and slots. SR-IOV offers a third way: the SSD itself presents many independent PCIe functions, the hypervisor assigns one to each VM, and the VM's own NVMe driver talks to its function directly, with DMA protected by the IOMMU.

Making that work correctly touches nearly everything earlier in this course: enumeration and Routing IDs (Chapter 17), configuration space and BARs (Chapter 18, Chapter 19), DMA and the IOMMU (Chapter 20), NVMe controllers and queues (Chapter 23, Chapter 25), MSI-X (Chapter 43), reset (Chapter 48, Chapter 49) and isolation (Chapter 55). If you can explain SR-IOV for NVMe end to end, you understand the whole stack.

Learning objectives

  • Define Physical Function (PF) and Virtual Function (VF), and explain what a VF shares with and does not share with its PF.
  • Read the SR-IOV Extended Capability: TotalVFs, NumVFs, First VF Offset, VF Stride, VF Device ID, VF BARs, page sizes, VF Enable and VF MSE.
  • Compute VF Routing IDs and VF BAR addresses, and explain when Alternative Routing-ID Interpretation (ARI) is needed.
  • Explain NVMe virtualization: primary and secondary controllers, private and flexible resources (VQ and VI), and the Virtualization Management command's actions.
  • Walk through bringing up a secondary controller and assigning it to a VM, and identify which steps are PCIe and which are NVMe.
  • Explain isolation (IOMMU, ACS, FLR) and resource sharing (bandwidth, IOPS) between VFs, including NVMe 2.4 rate limiting.
  • Place the NVMe 2.4 PCIe Exported NVM Subsystem Migration feature in this architecture.

The story

Imagine a big school library with one head librarian. The school grows, and now many classes want to borrow books at the same time. Instead of building more libraries, the head librarian sets up several small help desks, each with its own assistant, its own in-tray and its own bell. Each class gets its own desk and never has to queue behind another class.

All the assistants share the same shelves behind them. The head librarian decides how many trays and bells each desk gets, opens and closes desks, and decides which shelves each desk may use. A class at desk 3 cannot see or touch desk 5's requests.

A large office building is leased floor by floor. Each tenant gets its own entrance code, mailbox and phone extension, and sees what looks like a private office. The building's management office (which the tenants never see) owns the lifts, the power and the plumbing, decides how many parking spaces each tenant gets, and can reassign them. Tenants share the building's lifts and corridors, so a very busy tenant can still slow others down unless management sets limits.

What it hides: in SR-IOV, the "management office" (the PF) is itself also a tenant-capable function with its own controller, and the boundaries are enforced by several different mechanisms in different places: the IOMMU in the host (memory isolation), ACS in the fabric (routing isolation), the device's internal design (resource isolation), and NVMe namespace attachment (data isolation).

Where it misleads: a leased floor is physically separate. VFs share one device's internal resources — NAND channels, controller CPUs, DRAM, the PCIe link — so their isolation is only as good as the device's implementation. The specification defines the interfaces, not the quality of internal isolation.

Beginner explanation

A PCIe function is what software sees as "a device": it has a Routing ID (bus, device, function), a configuration space, BARs and interrupts. A normal NVMe SSD has one function. SR-IOV adds two kinds:

  • A Physical Function (PF) is a full PCIe function with an SR-IOV capability. It is discovered at enumeration like any function and is normally managed by the host (hypervisor) driver.
  • A Virtual Function (VF) is a lightweight function created when software enables SR-IOV in the PF. It has its own Routing ID, its own BAR space and its own MSI-X vectors, but a much smaller configuration space; many of its properties are inherited from the PF.

Software chooses how many VFs to enable (up to the TotalVFs the device supports). Each VF can then be assigned to a VM: the hypervisor maps the VF's BAR into the VM and configures the IOMMU so the VF's DMA can only reach that VM's memory. The VM's ordinary NVMe driver runs on the VF as if it were a whole SSD.

For NVMe, a VF is not useful on its own: there must be an NVMe controller behind it. NVMe's virtualization features define a primary controller (behind the PF) and secondary controllers (typically one behind each VF). The primary controller lends queue resources and interrupt resources to secondary controllers and brings them online, using the Virtualization Management admin command. Namespaces are then attached to secondary controllers to give each VM its storage.

SR-IOV is a PCIe feature: it creates functions. NVMe virtualization is an NVMe feature: it creates usable controllers behind those functions and moves resources between them. You need both, configured in the right order.

VF Routing IDs can exceed the 8 functions a device normally has, and can even spill into higher bus numbers, which the enumeration software must then reserve. That is why SR-IOV devices are almost always used with Alternative Routing-ID Interpretation (ARI): with ARI, the device and function fields merge into one 8-bit function number, so a single device on a bus can have up to 256 functions. The downstream port above must have ARI Forwarding Enable set, because without ARI a downstream port only forwards configuration requests for device 0 on its secondary bus.

Linux always prints the 8-bit device/function byte as dd.f, even with ARI. ARI function 8 therefore appears as 01:01.0, which looks like "device 1" but is really function 8 of device 0. Do not conclude that a second physical device exists.

VF BARs and MMIO

A VF has no BARs in its own configuration space (they read as zero). Instead, each VF BARk in the PF's SR-IOV capability is sized exactly like a normal BAR (write all ones, read back the size mask), giving the per-VF size; software then assigns a base address for a region of NumVFs consecutive copies:

Base(VFn, BARk) = VFBARk.base + (n − 1) × VFBARk.size
VFBARk.base
address software assigned to the PF's VF BARk
VFBARk.size
per-VF size from BAR sizing (aligned to System Page Size)
n
VF number, 1 to NumVFs

For an NVMe VF, the per-VF BAR holds that secondary controller's registers (CAP, CC, CSTS, AQA, ASQ, ACQ…), its doorbells from offset 1000h, and usually its MSI-X table and PBA. The page-size alignment matters because the hypervisor maps each VF's BAR into a VM with page-granular second-level translation; two VFs sharing a page would let one VM touch another's doorbells.

NVMe virtualization: primary and secondary controllers

NVMe's virtualization enhancements (added in NVMe 1.4 and carried forward in the NVMe Base Specification 2.x) define how an NVM subsystem that supports SR-IOV manages its controllers:

  • The primary controller is associated with a PF. It reports the subsystem's virtualization resources and executes Virtualization Management commands.
  • A secondary controller is typically associated with a VF. It is a full NVMe controller from the VM's point of view, but it depends on the primary controller for its resources and its online/offline state.
  • Each secondary controller has a Controller Identifier (CNTLID) and is associated with a VF number.

Two resource types are managed:

NVMe controller resources
TypeMeaningConsumed by
VQ resource (Virtual Queue)One submission/completion queue pair's worth of controller resourcesThe admin queue pair and each I/O queue pair the secondary controller's driver creates
VI resource (Virtual Interrupt)One interrupt vector's worth of controller resourcesMSI-X vectors used by the secondary controller

Resources are either private (permanently belonging to the primary controller) or flexible (a pool the primary controller can keep for itself or assign to secondary controllers). The Primary Controller Capabilities data structure, returned by Identify, reports totals and limits, including (by name): VQ Flexible Resources Total, VQ Resources Flexible Allocated to Primary, VQ Private Resources Total, VQ Flexible Resources Secondary Maximum, VQ Flexible Resource Preferred Granularity, and the corresponding VI fields. The Secondary Controller List, also returned by Identify, lists each secondary controller with its Secondary Controller Identifier, its primary controller, its state (online/offline), its Virtual Function Number, and the number of VQ and VI flexible resources assigned.

The Virtualization Management admin command (opcode 1Ch) changes allocations and states. Its actions, by name:

A secondary controller must be offline to receive resources, and must be online before a driver can enable it. If the VF appears (VF Enable) and a driver binds to it before the secondary is online, the driver's controller enable will not succeed. Linux deployments typically disable automatic VF driver probing, enable the VFs, configure and online each secondary controller, and only then bind drivers or assign VFs to VMs.

Namespaces and data isolation

Resources make a secondary controller work; namespaces give it storage. The host uses Namespace Management to create namespaces and Namespace Attachment to attach each namespace to one or more controllers by CNTLID (see Chapter 58). Attaching namespace 5 only to secondary controller 3 makes it visible only through VF 3. Data isolation between VMs is therefore an NVMe-layer property, complementing the IOMMU's memory isolation and ACS's routing isolation.

Resource sharing and noisy neighbours

All VFs share the link and the device's internals. A VM saturating its VF with writes can raise latency for every other VF. Historically, QoS between VFs was entirely vendor-specific. NVMe 2.4 adds rate limiting: controls for allocating PCIe bandwidth and IOPS among multiple controllers, enforced by the controller. Version-dependent (NVMe 2.4). Field-level details are defined in the NVMe Base Specification 2.4 and are not reproduced here because we have not verified them; see 2026 NVMe 2.4 Updates.

Live migration and NVMe 2.4 Exported NVM Subsystems

SR-IOV assignment gives VMs speed but makes live migration hard: a VM directly driving a VF holds state inside the device (queue pointers, outstanding commands, controller registers, namespace identity) that the hypervisor cannot see or copy. The NVMe 2.4 release adds PCIe Exported NVM Subsystem Migration for this. As reported for the 2.4 release (see also 2026 NVMe 2.4 Updates):

  • An SSD can expose Exported NVM Subsystems — virtual SSDs within the physical SSD — to VMs.
  • A configuration template ("blueprint"), identified by a 128-bit UUID, defines the features, identifiers and behaviours an Exported NVM Subsystem presents, so the source and destination can present an identical device.
  • The reported flow: create the Exported NVM Subsystem on the destination; recreate the exported controller and namespace with matching identifiers; apply the same configuration template; capture the source's runtime state; transfer and apply it; migrate the VM; clean up the source.
  • Related 2.4 additions: a TDISP information package through which controllers report detailed state (useful when validating controller state, for example during migration), and lockdown controls for virtualized environments.

Exported NVM Subsystem migration, its configuration templates, the TDISP information package, virtualization lockdown controls and rate limiting are NVMe 2.4 (2026) features. Our sources for them are the release announcement and press coverage; treat this section as architectural orientation and read the NVMe Base Specification 2.4 and the NVM Express Revision Changes (2026.07.30) document for the normative definitions. Do not assume an SSD supports them because it supports SR-IOV.

How a given exported subsystem maps onto PCIe functions (PF, VF, or another mechanism) is an architecture and implementation question we have not verified for 2.4; do not equate "Exported NVM Subsystem" with "VF" without checking the specification.

Alternatives and neighbours

  • Hypervisor emulation (virtio-blk, virtio-scsi, emulated NVMe): flexible, migratable, slower.
  • Whole-device passthrough: one SSD per VM; simplest isolation, poor sharing.
  • Mediated or software-defined sharing (for example vfio-user or vendor-specific schemes): device-specific trade-offs.
  • Scalable I/O Virtualization (SIOV) uses Process Address Space IDs (PASIDs) instead of Routing IDs to isolate lightweight interfaces. Informative — outside this chapter's scope.
  • TDISP (TEE Device Interface Security Protocol) adds a security model for assigning device interfaces to confidential VMs; its relationship to NVMe 2.4's TDISP information package should be studied in the respective specifications.

The central concept on the ladder

One library, many help desks: each class gets its own desk, tray and bell; the head librarian hands out trays and bells and opens or closes desks.

One SSD presents many PCIe functions (VFs); each VM drives one directly. Behind each VF is an NVMe secondary controller that borrows queue and interrupt resources from the primary.

The device implements per-VF register sets, doorbells and MSI-X tables in VF BAR regions; per-VF DMA tagged with the VF's RID; internal queue/interrupt resources partitioned by the primary controller.

PCIe: SR-IOV Extended Capability (VF Enable, NumVFs, offsets, VF BARs), ARI, FLR. NVMe: Primary Controller Capabilities, Secondary Controller List, Virtualization Management (opcode 1Ch) actions, Namespace Attachment.

Configuration writes to the PF to enable VFs; admin commands to the primary controller to assign/online; VM driver MMIO to VF BAR; VF DMA with VF RID; MSI-X writes from VF vectors.

Analyzer shows TLPs with Requester IDs 0x0101, 0x0102…; doorbell writes to distinct VF BAR addresses; IOMMU faults show up as UR completions to VF requests.

"VF does not come ready" → secondary offline or no resources; "VF DMA faults" → IOMMU mapping or wrong RID; "VM slow when neighbour busy" → shared internal resources, rate limits.

Hardware view

  • Per-VF hardware: register file, doorbell array, MSI-X table and pending-bit array, DMA context tagged with the VF's RID. Often implemented as a large shared register file indexed by function.
  • Queue engines: an SSD has a finite number of hardware queue contexts; VQ resources are the specification's view of them.
  • Interrupt engine: a finite set of MSI-X vectors across all functions; VI resources reflect it.
  • Back end: NAND, flash translation layer and DRAM are shared; isolation of performance is the device's design problem.
  • Reset domains: VF FLR must reset only that VF's controller state; PF reset or link reset affects all VFs.

VF DMA carries the VF's Requester ID. The IOMMU uses that RID to select the VM's translation tables. If a device mistakenly issues a VF's DMA with the PF's RID, the IOMMU will translate it with the host's tables — a serious isolation bug that only a protocol analyzer or IOMMU fault log will reveal.

Specification view

PCIe side: PCI Express Base Specification, Revision 6.x/7.0 — Single Root I/O Virtualization and Sharing (formerly the standalone PCI-SIG SR-IOV specification, revision 1.1), plus Alternative Routing-ID Interpretation, Function Level Reset and Access Control Services. NVMe side: NVMe Base Specification 2.4 — Virtualization Enhancements; Identify (Primary Controller Capabilities, Secondary Controller List); Virtualization Management command; Namespace Attachment and the NVMe over PCIe Transport Specification 1.4 for how controllers map to PCIe functions. 2026 features: NVMe Base Specification 2.4 and NVM Express Revision Changes 2026.07.30.

What is verified? PF/VF model; SR-IOV capability fields; VF RID formula; VF BAR layout; VFs use MSI/MSI-X not INTx; ARI permits up to 256 functions; NVMe primary/secondary controllers; VQ and VI flexible and private resources; Virtualization Management (opcode 1Ch) with Primary Flexible Allocation, Secondary Offline, Secondary Assign and Secondary Online actions; NVMe 2.4 includes Exported NVM Subsystem migration, rate limiting, virtualization lockdown controls and a TDISP information package (per the release announcement).

What is derived? The configuration order recommendation; the resource planning arithmetic; the isolation layering (IOMMU / ACS / namespace attachment / device internals).

What is implementation-dependent? TotalVFs, VF BAR sizes, First VF Offset/VF Stride values, VQ/VI totals and granularity, internal QoS and isolation quality, how a device behaves when a VF driver enables an offline secondary controller, VF-to-secondary association policy, and hypervisor/VFIO behaviour.

What is version-dependent? NVMe virtualization enhancements first appeared in NVMe 1.4; the 2.x restructuring moved them into the Base Specification; 2.4 adds exported subsystems, migration, rate limiting and virtualization lockdown. SR-IOV moved from a standalone PCI-SIG specification into the PCIe Base Specification.

What must be checked in the specification? Identify CNS values and data structure layouts; Virtualization Management field positions; minimum resources for a secondary to go online; whether a Primary Flexible Allocation requires a reset to take effect; the VF configuration register table; System Page Size rules; all NVMe 2.4 identifiers for migration, templates and rate limiting (we have not verified them).

What the specification does not say: how much performance isolation VFs must have; how a hypervisor should schedule VFs; which VM gets which VF.

What should never be assumed? That a VF is usable as soon as it appears; that VF FLR resets namespace contents (it resets controller state); that VFs are isolated in performance; that "SR-IOV supported" implies NVMe 2.4 migration support; that the PF driver and the VF driver are the same component.

Protocol view

  • Configuration requests (CfgRd/CfgWr) to the PF set up SR-IOV. VF configuration space is reached at the VF's own RID.
  • Admin commands on the primary controller's admin queue manage secondary controllers. They are ordinary 64-byte SQEs (opcode 1Ch for Virtualization Management, 06h for Identify) and complete with CQEs and status codes as in Chapter 30.
  • Guest I/O uses the VF's BAR (doorbells at VF BAR0 + 1000h onward) and generates DMA with the VF's RID. The IOMMU translates guest IOVAs.
  • Interrupts: MSI-X writes from the VF's vectors are remapped by the interrupt remapping unit to the right VM's virtual CPU.
  • Reset: FLR on the VF (configuration write to its Device Control's Initiate FLR bit) resets that function; resetting the PF or the link affects every VF.

Code / pseudocode

VF RID, BAR and resource planner (runnable)

This script is executable with the standard library. It uses synthetic capability values; change them to match your device's SR-IOV capability and Primary Controller Capabilities.

#!/usr/bin/env python3
"""sriov_plan.py - compute VF Routing IDs, VF BAR placement and an NVMe
flexible-resource plan for a SYNTHETIC SR-IOV NVMe SSD (teaching example).

PCIe facts used (SR-IOV capability):
  RID(VF n) = PF RID + First VF Offset + (n - 1) * VF Stride   (n = 1..NumVFs)
  VF BAR k of VF n = VF BARk base + (n - 1) * VF BARk size
NVMe facts used (virtualization enhancements): flexible VQ/VI resources move
from the primary controller's pool to secondary controllers with the
Virtualization Management command; each secondary needs enough VQ resources
for its admin queue pair plus I/O queue pairs, and VI resources for vectors.
"""

PF_RID = 0x0100            # Lab SSD 01:00.0
FIRST_VF_OFFSET = 1
VF_STRIDE = 1
NUM_VFS = 10
VF_BAR0_BASE = 0x3_8000_0000   # assigned by the OS to the PF's VF BAR0 (synthetic)
VF_BAR0_SIZE = 16 * 1024       # per-VF size, found by BAR sizing

# Synthetic Identify Primary Controller Capabilities values
VQFRT, VIFRT = 64, 64      # flexible VQ / VI resources total
VQFRSM, VIFRSM = 16, 16    # max flexible resources per secondary
VQGRAN, VIGRAN = 1, 1      # preferred granularity

def linux_name(rid):
    """Linux always prints the 8-bit devfn as device.function, even with ARI."""
    bus, devfn = rid >> 8, rid & 0xFF
    return f"{bus:02x}:{devfn >> 3:02x}.{devfn & 7}"

def main():
    print("VF  RID     Linux name  ARI fn  needs ARI  VF BAR0 range")
    for n in range(1, NUM_VFS + 1):
        rid = PF_RID + FIRST_VF_OFFSET + (n - 1) * VF_STRIDE
        base = VF_BAR0_BASE + (n - 1) * VF_BAR0_SIZE
        needs_ari = (rid & 0xFF) >> 3 != 0      # non-ARI view: device number != 0
        print(f"{n:<3} 0x{rid:04x}  {linux_name(rid):<11} {rid & 0xFF:>6}  "
              f"{'yes' if needs_ari else 'no':<9}  0x{base:x}-0x{base + VF_BAR0_SIZE - 1:x}")
    print(f"Total VF BAR0 aperture: {NUM_VFS} x {VF_BAR0_SIZE // 1024} KiB = "
          f"{NUM_VFS * VF_BAR0_SIZE // 1024} KiB (contiguous)")
    print("needs ARI = yes: read without ARI, the RID's device number is not 0, and a")
    print("downstream port without ARI Forwarding only reaches device 0 below it")

    # Plan: keep 16 VQ/VI flexible for the primary, share the rest equally.
    keep_primary = 16
    per_vf_vq = min(VQFRSM, (VQFRT - keep_primary) // NUM_VFS // VQGRAN * VQGRAN)
    per_vf_vi = min(VIFRSM, (VIFRT - keep_primary) // NUM_VFS // VIGRAN * VIGRAN)
    print(f"\nFlexible plan: primary keeps {keep_primary} VQ / {keep_primary} VI; "
          f"each secondary gets {per_vf_vq} VQ / {per_vf_vi} VI")
    print(f"Each secondary: 1 admin queue pair + up to {per_vf_vq - 1} I/O queue pairs, "
          f"{per_vf_vi} interrupt vectors")
    print("Order per secondary: Offline -> Assign VQ -> Assign VI -> Online")
    used = keep_primary + NUM_VFS * per_vf_vq
    assert used <= VQFRT, "over-allocated VQ resources"
    print(f"VQ used {used}/{VQFRT}; VI used {keep_primary + NUM_VFS * per_vf_vi}/{VIFRT}")

if __name__ == "__main__":
    main()

Building a Virtualization Management command (pseudocode)

/* Field placement in CDW10/CDW11 must be taken from the NVMe Base Specification;
   the names below are the specification's field names. */
struct nvme_sqe sqe = {0};
sqe.opcode = 0x1C;                 /* Virtualization Management */
sqe.nsid   = 0;                    /* not namespace-specific */
set_field(&sqe, ACT,  0x8);         /* Secondary Controller Assign */
set_field(&sqe, RT,   RT_VQ);       /* resource type: VQ or VI */
set_field(&sqe, CNTLID, 2);        /* target secondary controller */
set_field(&sqe, NR,   4);           /* number of resources */
submit_admin(primary_ctrl, &sqe);
/* On success, re-read the Secondary Controller List to confirm NVQ = 4. */

Worked example

Plan ten VMs on one SSD

Synthetic example: the Lab SSD reports TotalVFs = 16, VQ Flexible Resources Total = 64, VI Flexible Resources Total = 64, VQ/VI Flexible Resources Secondary Maximum = 16, granularity 1. Ten VMs each need one VF.

  1. Routing IDs. First VF Offset 1, VF Stride 1 → RIDs 0x0101–0x010A. VFs 8–10 have device-number bits ≠ 0 when read without ARI, so the root port must have ARI Forwarding enabled (the planner's "needs ARI" column).
  2. BAR aperture. 10 × 16 KiB = 160 KiB of VF BAR0 space, which firmware or the OS must reserve in the root port's memory window. If the platform reserved only enough for the PF, VF Enable will work but VF BARs cannot be assigned — a common bring-up failure.
  3. Resources. Keep 16 VQ / 16 VI for the host's own use of the primary controller; 48 remain → 4 VQ and 4 VI per secondary: one admin queue pair plus 3 I/O queue pairs, and 4 interrupt vectors per VM.
  4. Is 3 I/O queues enough? A VM with 8 vCPUs would like 8 queues (one per CPU, Chapter 27). With 3, its driver shares queues among CPUs — acceptable for most VMs; for high-performance VMs, give fewer VMs more resources (up to 16 each).
  5. Namespaces. Create 10 namespaces and attach each to exactly one secondary controller.
  6. Isolation. Confirm each VF is in its own IOMMU group. Because all VFs are functions of one device, this depends on the device's ACS support for multi-function isolation (or on the kernel's handling of SR-IOV devices); check the groups, do not assume.

Common mistakes

  • Binding a driver to a VF before its secondary controller is online.
  • Reading VF Vendor ID = FFFFh as "no device." VFs report IDs through the PF's SR-IOV capability.
  • Forgetting ARI when VF RIDs exceed function 7, or forgetting to reserve bus numbers when VFs spill over buses.
  • Not reserving MMIO for VF BARs in platform firmware.
  • Resetting the PF to "fix" one VF, which disrupts every VM on the device. Use VF FLR.
  • Confusing the SR-IOV capability's legacy "VF Migration" fields with NVMe live migration.
  • Assuming VF performance isolation. Measure under contention; use rate limiting where supported.
  • Attaching one namespace to several secondary controllers unintentionally, exposing data across VMs.

Senior engineer insight

  • Two virtualization layers, two owners. PCIe SR-IOV is configured by the PF driver and platform; NVMe secondary controllers by the storage management stack. Bugs hide in the hand-off between them.
  • The RID is the security boundary. Validate on an analyzer that every DMA during VF I/O carries the VF's RID.
  • Reset scope is a product requirement. A VF FLR must not disturb other VFs; test it under load on every VF simultaneously.
  • Plan resources from workloads, not from equal division. Queues and vectors are scarce.
  • Migration changes what "state" means. With NVMe 2.4 exported subsystems, controller and namespace identity, configuration templates and runtime state become things you must be able to capture, transfer and verify — a new validation dimension.
  • Read the device's virtualization limits early (Primary Controller Capabilities) during platform selection, not after deployment.

Challenge

Extend sriov_plan.py to accept a list of per-VM requirements and produce a validated assignment, rejecting plans that exceed totals or per-secondary maxima.

Hints

Large VM: 8 I/O queue pairs + 1 admin pair = 9 VQ; small: 2 + 1 = 3 VQ. Vectors: 8 and 3 (one may be shared between admin and an I/O queue, depending on the driver).

Solution

Q1: 9 VQ for large, 3 VQ for small (each I/O queue pair plus the admin pair).

Q2: VQ total = 2 × 9 + 4 × 3 = 30; VI total = 2 × 8 + 4 × 3 = 28. Both fit in 64 with room for the primary, and 9 ≤ 16 per secondary. It fits.

Q3: VF FLR resets the VF's function and its controller state (registers, queues, outstanding commands, MSI-X configuration); the guest must reinitialize. SR-IOV enable, secondary resource assignment and online state, and namespace attachment are managed through the PF/primary and survive (confirm device-specific behaviour for secondary state across VF FLR in the specification and device documentation).

Q4: the hypervisor maps each VF's BAR into a VM's address space with page granularity; if two VFs shared a page, one VM could reach another VF's registers.

Spec vs implementation: spec — SR-IOV fields, RID formula, VF BAR layout, VQ/VI concept, Virtualization Management actions, namespace attachment; implementation — TotalVFs, BAR sizes, resource totals, offline-enable behaviour details, performance isolation, VF/secondary association.

What a senior engineer notices

That the plan's weakest point is not resources but reset and contention behaviour, which no capability field describes; and that the platform's MMIO and bus-number reservations must be part of the plan.

Failure variants

  • Request 16 VQ for a secondary with granularity 4: allowed. With secondary maximum 12: rejected.
  • NumVFs larger than the platform can map: VF Enable succeeds but VF BAR assignment fails.
  • Namespace attached to the primary only: guests see no storage.

Exercises

  1. A PF at RID 0x3A00 has First VF Offset 0x80 and VF Stride 2. What are the RIDs of VF1 and VF5?
  2. VF BAR0 is sized at 32 KiB and NumVFs is 8. How much MMIO is needed, and where is VF6's BAR0 if VF BAR0 base is 0x60_0000_0000?
  3. Why can a VF not use INTx?
  4. List the four Virtualization Management actions in the order you would use them to give a secondary controller more queues.
  5. Explain why NVMe live migration needs more than copying namespace data.
Answers

1. VF1 = 0x3A00 + 0x80 = 0x3A80. VF5 = 0x3A80 + 4 × 2 = 0x3A88.

2. 8 × 32 KiB = 256 KiB. VF6 = 0x60_0000_0000 + 5 × 0x8000 = 0x60_0002_8000.

3. INTx is a shared, level-triggered legacy mechanism tied to a function's Interrupt Pin; VFs are defined without it so each can have independent, remappable message-signalled interrupts.

4. Secondary Controller Offline → Secondary Controller Assign (VQ, and VI if needed) → Secondary Controller Online. (Primary Controller Flexible Allocation is used first if the primary is holding the flexible resources you need.)

5. The VM's driver holds live controller state — queues, doorbell values, outstanding commands, features, identifiers — and expects the same controller identity after migration. That state must be captured, transferred and applied, and the destination must present identical identifiers and behaviour (the 2.4 configuration template), not just identical data.

Quiz

  1. Where are a VF's BARs described?

    • In the VF's own Base Address Registers
    • In the VF BAR fields of the PF's SR-IOV capability
    • In the NVMe CAP register
    Answer and reasoning

    VF BARs live in the PF's SR-IOV capability; each describes per-VF size and a region of NumVFs copies.

  2. VF n's Routing ID is:

    • PF RID + First VF Offset + (n − 1) × VF Stride
    • PF RID + n
    • Assigned by the NVMe primary controller
    Answer and reasoning

    The SR-IOV formula; offset and stride come from the capability.

  3. What does a VQ resource represent in NVMe virtualization?

    • A namespace
    • An MSI-X vector
    • Controller resources for one submission/completion queue pair
    • A PCIe virtual channel
    Answer and reasoning

    VQ = virtual queue resource; VI = virtual interrupt resource.

  4. What state must a secondary controller be in to receive resources via Secondary Controller Assign?

    • Online
    • Offline
    • Either
    Answer and reasoning

    Offline; it is then brought online.

  5. Why is ARI usually required for SR-IOV devices with more than a few VFs?

    Model answer

    Without ARI, a device has device number 0 and up to 8 functions below a downstream port; VF RIDs beyond function 7 would need other device numbers, which a non-ARI downstream port does not reach. ARI makes the 8 bits one function number (256 functions).

  6. An IOMMU fault names device 01:00.2. What does this tell you?

    Model answer

    The faulting DMA carried RID 0x0102 — VF2 (with the lab numbering). Look at the VM assigned VF2 and its mappings. If VF2 was idle, suspect the device using the wrong RID.

  7. Which reset affects only one VM's VF?

    • Function Level Reset of the VF
    • PF Function Level Reset
    • Secondary bus reset of the root port
    • NVM Subsystem Reset
    Answer and reasoning

    VF FLR is scoped to that function; the others affect every function of the device (or the whole subsystem).

  8. Which NVMe 2.4 feature addresses VM live migration with SR-IOV-style direct assignment?

    • Voltage monitoring
    • Restore manufacturing default settings
    • PCIe Exported NVM Subsystem Migration
    • Idle I/O exit latency limits
    Answer and reasoning

    Exported NVM Subsystem Migration, with configuration templates identified by 128-bit UUIDs and state capture/transfer.

  9. Name two things that are specification-defined and two that are implementation-specific in an SR-IOV NVMe SSD.

    Model answer

    Spec-defined: SR-IOV capability fields and RID formula; Virtualization Management actions; VQ/VI resource concept; namespace attachment. Implementation: TotalVFs and resource totals; performance isolation; internal scheduling; VF BAR sizes.

Interview questions

  1. Beginner: What is the difference between a PF and a VF?

    Model answer

    A PF is a full PCIe function with an SR-IOV capability that manages VFs. A VF is a lightweight function created by the PF's VF Enable, with its own RID, BAR region and MSI-X, but reduced configuration space and many properties controlled by the PF.

  2. Beginner: Why does SR-IOV need an IOMMU?

    Model answer

    A VM's driver programs the VF with guest addresses; the IOMMU translates them per RID and blocks DMA outside the VM's memory. Without it, a VF could read or write any host memory.

  3. Intermediate: Walk through bringing an NVMe VF into service.

    Model answer

    Disable VF autoprobe; set NumVFs and VF Enable (VF BARs assigned); for its secondary controller: offline, assign VQ and VI, online; create/attach a namespace to that CNTLID; bind the VF to VFIO and assign to a VM; the guest driver enables the controller, creates queues and issues I/O.

  4. Intermediate: What are private and flexible resources?

    Model answer

    Private resources belong permanently to the primary controller; flexible resources form a pool that the primary can keep or assign to secondary controllers via Virtualization Management, subject to totals, per-secondary maxima and granularity.

  5. Advanced: How would you validate isolation between VFs?

    Model answer

    Analyzer checks that each VF's DMA uses its own RID; IOMMU fault injection (unmapped IOVAs) per VF; namespace attachment checks; FLR of one VF under load on all others; error injection on one VF and observation of others; MMIO page separation; performance contention tests with and without rate limits.

  6. Advanced: Why is live migration hard with direct-assigned VFs?

    Model answer

    The device holds guest-visible state the hypervisor cannot see — queues, doorbells, in-flight commands, controller configuration — and the guest expects identical identity after migration. NVMe 2.4's Exported NVM Subsystem Migration standardizes identical presentation (configuration templates) and state capture/transfer.

  7. Senior: A customer complains that VMs on one SSD all stall for 2 s occasionally. What do you suspect?

    Model answer

    A shared-scope event: PF reset by the host driver (e.g. after an admin timeout), a link event with DPC recovery, a firmware activation, or a device-internal stall (garbage collection, thermal throttling). Correlate host AER/DPC/nvme logs on the PF with guest timeouts; check NVMe telemetry and SMART on the PF; check firmware logs.

  8. Senior: What would you require from an SSD vendor for a multi-tenant SR-IOV deployment?

    Model answer

    TotalVFs and resource totals sufficient for the plan; documented and tested VF FLR isolation; correct per-VF RIDs; per-VF error containment; QoS or NVMe 2.4 rate limiting; virtualization lockdown controls where relevant; telemetry per controller; a roadmap for 2.4 exported subsystem migration if live migration is required; interoperability with the target hypervisor and kernel versions.

Chapter summary

SR-IOV creates VFs from a PF: each VF has its own RID (PF RID + First VF Offset + (n − 1) × VF Stride), its own BAR region carved from the PF's VF BARs, and its own MSI-X, while sharing the link and the device. ARI makes room for many functions. NVMe virtualization puts a primary controller behind the PF and secondary controllers behind VFs; flexible VQ and VI resources move to secondaries with Virtualization Management (Offline → Assign → Online), and namespace attachment gives each its storage. Isolation is layered: IOMMU (by RID), ACS, namespace attachment and device internals. VF FLR resets one VF; PF or link resets affect all. NVMe 2.4 adds rate limiting, virtualization lockdown, a TDISP information package and PCIe Exported NVM Subsystem Migration for live migration.

Do not move on until you can:

  • compute VF RIDs and VF BAR addresses from the SR-IOV capability
  • explain when ARI is required and how Linux names ARI functions
  • describe primary/secondary controllers, VQ/VI, private/flexible resources
