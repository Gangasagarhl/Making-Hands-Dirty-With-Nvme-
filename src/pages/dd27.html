Chapter 28 showed what a doorbell is and how to decode one. This module studies doorbells as a concurrent, cross-domain event: CPU memory ordering on one side, posted PCIe writes in the middle, a controller front end on the other, and in virtual machines a hypervisor in between. It adds the races, the latency measurements, the shadow-doorbell mechanics and the lifecycle edge cases that the chapter left out.

Orientation

A doorbell carries one 16-bit index. Everything difficult about it comes from when and by whom it is written and what state the controller is in when it arrives. This module deepens Chapter 28 in five directions: (1) concurrency — what happens when two CPUs share one Submission Queue (SQ) and ring its doorbell; (2) the doorbell as a performance signal — doorbell-to-fetch latency and its three very different causes; (3) shadow doorbells and EventIdx in depth, including when they save nothing; (4) lifecycle — doorbells written while the controller is resetting, disabled, or in a low-power state, and while Memory Space or Bus Master Enable is off; (5) trace ambiguity — telling a host double-write from a Data Link Layer replay.

You need the doorbell address formula, the nine steps and the write barrier from Chapter 28 — Doorbells; head/tail ownership from Chapter 25 — Queue Architecture; posted writes from Chapter 12; PCIe ordering from Chapter 14; and replay from Chapter 15 — DLLP. Queue topology is in Module 26.

Where it goes next: Module 28 examines the 64 bytes each doorbell publishes, and Module 38 — Trace Correlation builds the doorbell-to-fetch rule into a general correlation engine.

Kid story

A house at the end of a country lane has a big mailbox. Inside is a row of numbered slots for letters. On the side of the box is a dial, like a clock hand pointing at numbers. When you put letters in, you turn the dial to "my letters go up to slot 8". The mail carrier drives by, looks at the dial, and takes everything up to slot 8. The dial never says "two letters"; it always says "up to here".

Now two brothers post letters at the same time. Sam puts his letter in slot 5, Ali in slot 6. Ali is faster: he turns the dial to 7. Then Sam, who did not see, turns it back to 6. The carrier sees the dial go backwards and is confused — did someone take letters back? So the family makes a rule: only one person at a time may post a letter and turn the dial.

On busy days the carrier parks in the driveway and peeks into the box every minute anyway. Then nobody needs to turn the dial at all; they just write the number on a sticky note inside the box. When the carrier leaves, she pins a note saying "turn the dial if you post after letter 12", so the family knows when to call her back.

Analogy boundary

What it represents. The slots are SQ entries in host memory; the dial is the SQ tail doorbell; "up to here" is the absolute index; the brothers are two CPUs sharing a queue; the parked carrier peeking is a controller polling a shadow doorbell buffer; the pinned note is EventIdx.

What it hides. A real NVM Express (NVMe) doorbell is a register inside the controller, not a dial the carrier reads at leisure: each write is a Memory Write packet that travels over PCI Express (PCIe) and is latched on arrival. The letter must be fully written and visible before the dial moves — a CPU memory-ordering property with no counterpart in the story. And there is also a second dial on the other side of the box (the Completion Queue head doorbell) for "I have read your replies up to here".

Where it misleads. The carrier in the story notices a backwards dial and asks. A controller cannot ask: at best it reports an Invalid Doorbell Write Value through an Asynchronous Event, and only if the host left an Asynchronous Event Request outstanding. Otherwise the backwards value is silently interpreted or ignored. The story also suggests the sticky note is always cheaper; in fact shadow doorbells save nothing when the controller is idle, because it is asleep and must be woken by a real doorbell.

Mechanism

One submission on an SQ shared by two CPUs, done correctly. Reference lab system, SQ2 (1024 entries, base 0x1_2342_0000), synthetic example for teaching.

  1. Acquire the queue lock. Who: CPU 4. What: exclusive right to reserve a slot, write it and ring. Where: host lock variable. Evidence: none on the link; lock statistics on the host.
  2. Reserve the slot at the tail. Who: CPU 4. What: slot 5 chosen; host tail 5 → 6. Where: driver variable. Evidence: none.
  3. Write the 64-byte SQE. Who: CPU 4. What: slot 5 at 0x1_2342_0140 filled. Where: cache/DRAM. Evidence: only later, as the fetched payload.
  4. Order, then ring. Who: CPU 4. What: barrier, then a 32-bit uncached store of 6 to 0xFE60_1010. Where: CPU store path → root complex. Evidence: MWr32, Length 1, First DW BE 1111b, Requester ID of the root complex.
  5. Release the lock. Only now may CPU 6 reserve slot 6. Because the lock covers reserve, write and ring, the doorbell values on the link are strictly increasing (modulo wrap) for this queue.
  6. Latch and validate. Who: controller. What: new tail 6; checks 6 < size and that (6 − head) does not overfill. Where: doorbell register file. Evidence: none, unless invalid — then an Asynchronous Event completion on the Admin CQ.
  7. Arbitrate and fetch. Who: controller. What: SQ2 becomes eligible; when chosen and when internal command slots are free, MRd at 0x1_2342_0140. Evidence: the MRd; the time from step 4 to here is doorbell-to-fetch latency.
  8. Free completion slots later. Who: the CPU handling the CQ's vector. What: after reaping, a CQ head doorbell. Evidence: MWr32 to CQ2HDBL (or the shared CQ's head doorbell).

The central concept on the ladder: a doorbell under concurrency

One person at a time posts a letter and turns the dial, so the dial only ever moves forward.

Every SQ has exactly one logical producer. If several CPUs share it, a lock must cover reserving the slot, writing the SQE and writing the doorbell.

The doorbell is a register latch in the controller; each MWr overwrites it. The controller computes new entries as (new − old) mod size, so a late, smaller value looks like a very large forward move.

NVMe Base 2.4 defines the doorbell registers, the full rule, and Asynchronous Event reporting of Invalid Doorbell Write Value. It does not specify host locking — that is derived from the single-producer model.

Doorbells are posted MWrs; PCIe keeps posted writes from the same requester in order on one path, so the order in which CPUs' stores leave the root complex is the order the controller sees.

Per SQ, doorbell values must be monotonic modulo wrap. A value smaller than its predecessor, without an intervening full wrap, is the trace signature of a race.

Asynchronous Event "Invalid Doorbell Write Value" under multi-threaded load, never single-threaded → suspect a lock that covers the slot but not the doorbell.

The specification does not define host locking, batching policy or how often to write the CQ head doorbell. It does not bound doorbell-to-fetch latency or require the controller to fetch everything published at once. It does not define what a read of a doorbell register returns in a way you should rely on. For shadow doorbells, the exact rules for when the controller must re-read shadow values, the buffer layout details and the behaviour across resets must be read in the Doorbell Buffer Config description Check details. What a function in a low-power device state (D3hot) does with memory requests is governed by the PCI power-management rules, not by NVMe; check those rules rather than assuming a doorbell is buffered.

A controller only fetches when it has room to hold the command. If its internal command table is full (all slots holding fetched-but-not-completed commands), a newly published SQE waits in host memory. That back-pressure looks exactly like a slow front end in a trace: a long doorbell-to-fetch gap. Count fetched-but-not-completed commands at the moment of the doorbell before concluding the front end is slow.

The fourth row is a standard technique: drivers that must know a posted write has landed (for example before timing a measurement or before powering something down) follow it with a read of a register on the same device, such as CSTS. Because a read completion cannot pass posted writes in the same direction, its return proves the earlier writes arrived. It costs a full non-posted round trip, which is why it is never used on the I/O fast path Derived.

At the PCIe level a doorbell to a function with Memory Space Enable cleared is not delivered to the NVMe logic at all; it is an Unsupported Request at the PCIe layer, with no completion because it is posted. A doorbell to a function with Bus Master Enable cleared is delivered and latched, but the controller cannot issue the fetch. Both look like "doorbell present, no fetch" in a trace; the PCI Command register tells them apart.

Analysis. Three causes produce a long doorbell-to-fetch gap, and the trace can separate them. Arbitration: other SQs are fetched during the gap — not the case here, only SQ1 is busy. Back-pressure: the controller holds as many fetched-but-not-completed commands as its internal table allows, and fetches only when a completion frees a slot — supported here: the count was at 128 (a plausible internal limit) and every fetch in phase B follows a CQE by a fraction of a microsecond. Front-end saturation: firmware is too busy to service doorbells, so fetches lag even when slots are free — would show fetch delays without a matching CQE just before each fetch. Conclusion: back-pressure, which is normal behaviour; the extra queue depth beyond the device's internal limit only adds waiting in host memory. That is Little's Law in action, not a defect. Confidence medium: the internal limit is inferred, not reported Implementation-dependent.

Labs

Beginner lab — Doorbell address map for a physical and a virtual function

Safe lab Calculation only.

Objective

Produce the complete doorbell map and the correct TLP format for two functions with different strides and BAR locations.

Prerequisites

Doorbell formula (Chapter 28); 3-DW vs 4-DW headers (Chapter 11).

Setup

Physical function: BAR0 0xFE60_0000, DSTRD 0, queues 0–4. A virtual function of an SR-IOV capable SSD (synthetic): BAR0 0x38_0000_4000, DSTRD 1, queues 0–2.

Procedure

  1. List SQ tail and CQ head doorbell addresses for each queue of each function.
  2. State MWr32 or MWr64 for each function.
  3. Decode these writes: (a) PF write to 0xFE60_101C value 0x40; (b) VF write to 0x38_0000_5018 value 3.

Observations

A table with function, queue, side, offset, absolute address, TLP format.

Questions

  1. What does the VF write in (b) touch?
  2. Why must a driver never assume the PF's stride for the VF?

Expected reasoning

Index = (offset − 1000h) / stride; even index → SQ tail of queue index/2; odd → CQ head.

Solution

PF (stride 4): SQ0 1000h, CQ0 1004h, SQ1 1008h, CQ1 100Ch, SQ2 1010h, CQ2 1014h, SQ3 1018h, CQ3 101Ch, SQ4 1020h, CQ4 1024h; absolute 0xFE60_1000… — MWr32 (below 4 GiB). VF (stride 8): SQ0 1000h, CQ0 1008h, SQ1 1010h, CQ1 1018h, SQ2 1020h, CQ2 1028h; absolute 0x38_0000_5000… — MWr64 (above 4 GiB). (a) offset 101Ch → index 7 → CQ3 head = 64. (b) offset 0x5018 − 0x4000 = 1018h → index 3 → CQ1 head = 3 — not SQ3's tail, which a stride-4 assumption would have claimed. (2) Stride is per controller (CAP of that function); emulated and virtual controllers often use larger strides.

Extension

For DSTRD = 2, compute how many queue pairs fit in a 16 KiB BAR0 if the MSI-X table occupies 0x2000–0x2FFF and doorbells may not overlap it.

Intermediate lab — Enumerate the shared-SQ race

Safe lab Pure simulation.

Objective

Show, by enumerating every interleaving, that only a lock covering reserve + SQE + doorbell is correct when two CPUs share an SQ.

Prerequisites

The Failed trace above; Python 3.8+.

Setup

#!/usr/bin/env python3
"""Two CPUs submit to ONE shared SQ. Enumerate every interleaving of their
steps and classify what the controller would see. Synthetic teaching model,
standard library only. Assumption: the controller fetches up to the new tail
as soon as each doorbell arrives (a fast controller), so any slot it fetches
must already hold its SQE.
"""
from itertools import combinations

SIZE = 8          # queue entries
START = 5         # shared tail before both CPUs submit

def run(order, steps):
    """order: tuple of thread ids, e.g. (0, 1, 1, 0, ...). steps: per-thread op list."""
    shared = {"tail": START}
    local = [{}, {}]
    written = set()                      # slots that hold a fresh SQE
    last_db = START
    verdicts = []
    pc = [0, 0]
    for t in order:
        op = steps[pc[t]]; pc[t] += 1
        L = local[t]
        if op == "read":                 # racy: load the tail
            L["slot"] = shared["tail"]
        elif op == "store":              # racy: store tail + 1
            shared["tail"] = (L["slot"] + 1) % SIZE
        elif op == "reserve":            # atomic fetch-and-add
            L["slot"] = shared["tail"]
            shared["tail"] = (shared["tail"] + 1) % SIZE
        elif op == "sqe":
            if L["slot"] in written:
                verdicts.append("same slot used twice")
            written.add(L["slot"])
        elif op == "doorbell":
            new = (L["slot"] + 1) % SIZE
            added = (new - last_db) % SIZE
            if added == 0:
                verdicts.append("redundant doorbell")
            elif (new - START) % SIZE < (last_db - START) % SIZE:
                verdicts.append("tail moved backwards")
            else:
                for k in range(added):
                    if (last_db + k) % SIZE not in written:
                        verdicts.append("stale SQE fetched")
                        break
                last_db = new
    if (last_db - START) % SIZE != 2:
        verdicts.append("a command never published")
    return sorted(set(verdicts)) or ["correct"]

def explore(name, steps, atomic_block=False):
    n = len(steps)
    results = {}
    if atomic_block:                     # each CPU's whole sequence runs under a lock
        orders = [(0,) * n + (1,) * n, (1,) * n + (0,) * n]
    else:
        orders = []
        for pos in combinations(range(2 * n), n):
            o = [1] * (2 * n)
            for p in pos:
                o[p] = 0
            orders.append(tuple(o))
    for o in orders:
        key = ", ".join(run(o, steps))
        results[key] = results.get(key, 0) + 1
    print(f"{name}: {len(orders)} interleavings")
    for k, v in sorted(results.items(), key=lambda kv: -kv[1]):
        print(f"   {v:3d}  {k}")

if __name__ == "__main__":
    explore("A. racy load/store of tail", ["read", "store", "sqe", "doorbell"])
    explore("B. atomic slot reservation, no lock", ["reserve", "sqe", "doorbell"])
    explore("C. lock around reserve+SQE+doorbell", ["reserve", "sqe", "doorbell"], atomic_block=True)

Procedure

  1. Run it.
  2. Add a variant D: atomic reservation, and each CPU rings only after waiting until every lower slot it did not reserve has been written ("ring in order").
  3. Count correct interleavings for D.

Observations

    20  correct

     2  stale SQE fetched, tail moved backwards

Questions

  1. Why does atomic reservation (B) still fail 8 of 20 interleavings?
  2. Which outcome in A is invisible to the controller but loses a command?
  3. What does the controller do with a tail that moved backwards on a 1024-entry queue?

Expected reasoning

The doorbell publishes every slot up to its value; it is only safe if every such slot is already written, and if no later value has already been rung.

Solution

(1) Atomic reservation fixes slot ownership, but the two doorbells can still be written in the wrong order (backwards tail), and the higher one can publish the lower slot before it is written (stale fetch). (2) The lost update: both CPUs read tail 5, both write slot 5, both ring 6 — one command overwritten, the second doorbell redundant, nothing for the controller to complain about. (3) It computes (new − old) mod 1024 = 1023 entries, which would overfill the queue: an Invalid Doorbell Write Value event if a request is outstanding; otherwise implementation-dependent behaviour. Variant D is correct in all interleavings but makes one CPU wait for the other — which is why drivers simply use a per-queue lock or per-CPU queues.

Extension

Raise to three CPUs (SIZE = 8, START = 5) and compare counts; then argue why per-CPU queues remove the problem entirely.

Advanced lab — When do shadow doorbells save anything?

Safe lab Pure simulation.

Objective

Measure how many MMIO doorbells EventIdx avoids for dense and sparse workloads, and understand the re-check that prevents lost wakeups.

Prerequisites

Shadow doorbells in Chapter 28.

Setup

#!/usr/bin/env python3
"""Shadow doorbell / EventIdx simulation (Doorbell Buffer Config style).
Synthetic teaching model, standard library only.
The host writes each new SQ tail into a shadow slot in memory, and performs a
real MMIO doorbell write only when need_event() says the controller asked for
one. An emulated controller polls the shadow while busy; when it has been idle
for IDLE_US it publishes EventIdx = last tail it consumed, re-checks the
shadow once (to close the lost-wakeup window), and sleeps until an MMIO write.
"""
import random

def need_event(event_idx, new_idx, old_idx):
    """True if event_idx lies in (old_idx, new_idx], all 16-bit wrapping."""
    return ((new_idx - event_idx - 1) & 0xFFFF) < ((new_idx - old_idx) & 0xFFFF)

def simulate(gaps_us, poll_us=2, idle_us=20, shadow=True):
    shadow_tail = 0          # host-written shadow doorbell slot
    event_idx = 0            # controller-written EventIdx slot
    consumed = 0             # controller's view of the tail it has processed
    awake, idle_for, mmio, worst_notice = False, 0, 0, 0
    pending_since = {}       # tail value -> time it was published
    t, arrivals = 0, []
    for g in gaps_us:
        t += g
        arrivals.append(t)
    end = arrivals[-1] + 200
    nxt = 0
    for now in range(end + 1):
        while nxt < len(arrivals) and arrivals[nxt] == now:       # host submits one command
            old, new = shadow_tail, (shadow_tail + 1) & 0xFFFF
            shadow_tail = new
            pending_since[new] = now
            if not shadow or need_event(event_idx, new, old):
                mmio += 1
                awake, idle_for = True, 0                        # MMIO wakes the controller
            nxt += 1
        if awake and now % poll_us == 0:                         # controller polls the shadow
            if shadow_tail != consumed:
                worst_notice = max(worst_notice, now - pending_since[(consumed + 1) & 0xFFFF])
                consumed, idle_for = shadow_tail, 0
            else:
                idle_for += poll_us
                if idle_for >= idle_us:
                    event_idx = consumed                         # "wake me after this"
                    if shadow_tail != consumed:                  # re-check closes the race
                        idle_for = 0
                    else:
                        awake = False
    lost = consumed != shadow_tail
    return mmio, worst_notice, lost

if __name__ == "__main__":
    rng = random.Random(1)
    busy = [rng.randint(1, 4) for _ in range(2000)]      # dense: one I/O every 1-4 us
    sparse = [rng.randint(50, 300) for _ in range(200)]   # sparse: one I/O every 50-300 us
    for label, gaps in (("dense ", busy), ("sparse", sparse)):
        for sh in (False, True):
            mmio, notice, lost = simulate(gaps, shadow=sh)
            print(f"{label} {len(gaps):5d} cmds  shadow={'on ' if sh else 'off'}  "
                  f"MMIO doorbells={mmio:5d}  worst notice delay={notice:2d} us  lost={lost}")

Procedure

  1. Run it.
  2. Change IDLE_US (the idle_us argument) to 2 and rerun.
  3. Delete the re-check (the if shadow_tail != consumed inside the idle branch, always sleeping) and construct, by reasoning, a timeline that loses a wakeup when the host's EventIdx read and the controller's EventIdx write cross.

Observations

dense   2000 cmds  shadow=off  MMIO doorbells= 2000  worst notice delay= 1 us  lost=False
dense   2000 cmds  shadow=on   MMIO doorbells=    1  worst notice delay= 1 us  lost=False
sparse   200 cmds  shadow=off  MMIO doorbells=  200  worst notice delay= 1 us  lost=False
sparse   200 cmds  shadow=on   MMIO doorbells=  200  worst notice delay= 1 us  lost=False

Questions

  1. Why does the sparse workload save nothing?
  2. What does the controller pay for the dense-case savings?
  3. Why must the host place a full barrier between writing the shadow value and reading EventIdx?

Expected reasoning

Savings exist only while the controller is awake and polling; the cost is polling (CPU time in an emulator, memory reads in hardware).

Solution

(1) Between sparse commands the controller goes idle and publishes EventIdx = its last consumed tail; the very next update crosses it, so every command needs an MMIO write. (2) Continuous polling of the shadow buffer: an emulator burns a host CPU thread; a physical device would issue memory reads. (3) Without it, the host could read an old EventIdx (no MMIO needed) while the controller, having already decided to sleep, published a new EventIdx and stopped polling — the classic lost wakeup. The controller's re-check after publishing EventIdx and the host's barrier together close the window from both sides.

Extension

Add a CQ head shadow and EventIdx and measure how many CQ head MMIO writes are avoided when the host reaps in batches.

Senior forensic lab — "Our VMs got slower after the platform upgrade"

Safe lab Reasoning over supplied synthetic evidence.

Objective

Attribute a virtual-machine storage regression to the doorbell path with evidence, and propose a fix and a regression test.

Prerequisites

This module; Chapter 56 — SR-IOV for the alternative of assigning a virtual function.

Setup — evidence (synthetic)

  • Guests use an emulated NVMe controller. After a hypervisor and guest-kernel upgrade, 4 KiB random-read IOPS per VM fell 35% at queue depth 32; queue depth 1 latency unchanged.
  • Hypervisor statistics: MMIO exits per second rose from about 3,000 to about 210,000 at the same IOPS (roughly one exit per command).
  • Guest: Identify Controller OACS still reports Doorbell Buffer Config support. Guest kernel log has no Doorbell Buffer Config related messages.
  • Emulator trace (counts only): before the upgrade, "shadow doorbell update" events about equal to commands, "MMIO doorbell" events tiny; after, no shadow events.

Procedure

  1. State the first abnormal event.
  2. Rank hypotheses.
  3. Propose the disambiguating experiment.
  4. Corrective action and regression test.

Observations

Separate guest, hypervisor and emulated-device facts.

Questions

  1. Why is queue-depth-1 latency unchanged?
  2. Why does the drop appear only at high queue depth?

Expected reasoning

One VM exit per doorbell is the signature of shadow doorbells not being in use.

Solution

First abnormal event: during guest controller initialisation after the upgrade, no Doorbell Buffer Config command is issued (or it is issued and fails) — confirm with the emulator's Admin command trace. Hypotheses: (H1) the new guest kernel's NVMe driver does not enable shadow doorbells for this controller (configuration, quirk list or code path changed) — fits the missing shadow events and unchanged OACS; (H2) the emulator rejects Doorbell Buffer Config after its upgrade — would show the command with an error status; (H3) shadow doorbells are on but the emulator stopped polling, so EventIdx always requests MMIO — would show shadow events plus MMIO per command. Why QD1 is unchanged: at queue depth 1 the emulator is idle between commands, so every command needed an MMIO write even before (see the sparse case in the advanced lab). Why only high QD: savings only exist while the emulator polls continuously. Experiment: boot the old guest kernel on the new hypervisor and vice versa. Fix: restore Doorbell Buffer Config use in the guest driver (or fix the emulator). Regression test: per-release check of MMIO exits per I/O at QD 32 with an alarm threshold, plus a functional test that Doorbell Buffer Config completes successfully during init.

Extension

Estimate the per-exit cost from the numbers given (IOPS drop vs added exits) and compare with the gain from assigning an SR-IOV virtual function instead.

Debugging

Pattern 1 — Doorbell present, no fetch, ever

Symptom
Analyzer shows correct-looking doorbells; no MRd follows; commands time out.
Possible causes
Bus Master Enable cleared; Memory Space Enable cleared (doorbell is an Unsupported Request); controller not ready or fatal (CSTS.RDY = 0, CSTS.CFS = 1); queue not created; invalid value with no Asynchronous Event Request outstanding; wrong address that happens to decode inside BAR0.
Evidence
PCI Command register; CSTS; Admin create completions; AER Unsupported Request status for the device.
First check
lspci -vv Control line: Mem+ and BusMaster+.
Second check
CSTS (read through nvme show-regs): RDY and CFS.
Disambiguating experiment
Ring the Admin SQ doorbell with a harmless Identify. If it is fetched, the controller can fetch; the I/O queue itself or its doorbell value is the problem.
Likely conclusion
Enables or controller state (host/platform) far more often than doorbell logic.
Confidence
High once both registers are read.

Pattern 2 — Invalid Doorbell Write Value only under multi-threaded load

Symptom
Asynchronous event notices and occasional completions for inactive command IDs, never with one thread.
Possible causes
Shared SQ without a lock that covers the doorbell; per-CPU queue assumption broken by CPU hotplug or migration; two driver instances (for example a user-space driver and the kernel) touching the same queue.
Evidence
Non-monotonic doorbell values per SQ; Error Information log entry naming the queue.
First check
Read the Error Information log (Get Log Page 01h) for the queue identifier.
Second check
Review the submission path for the lock's scope.
Disambiguating experiment
Pin the workload to one CPU per queue; if the events vanish, it is a producer race.
Likely conclusion
Host concurrency bug.
Confidence
High.

Pattern 3 — Doorbell-to-fetch latency spikes

Symptom
Tail latency grows; the gap is before the fetch.
Possible causes
Arbitration (other SQs fetched in the gap); internal back-pressure (fetch follows a CQE); firmware front-end saturation (neither).
Evidence
What the link carries during the gap.
First check
Are other SQs fetched during the gap?
Second check
Does each delayed fetch follow a CQE closely?
Disambiguating experiment
Reduce queue depth to below the suspected internal limit; back-pressure delays vanish, front-end saturation does not.
Likely conclusion
Usually back-pressure (benign) or arbitration (policy); front-end saturation is a device performance defect.
Confidence
Medium.

Pattern 4 — Admin queue misbehaves after I/O doorbell writes

Symptom
Admin commands stall or Admin CQ entries are overwritten while I/O runs.
Possible causes
Stride assumed 4 on a DSTRD ≥ 1 controller, so an "SQ1 tail" write lands on CQ0's head; 64-bit store spanning two doorbells.
Evidence
Doorbell addresses vs DSTRD; MWr Length = 2.
First check
DSTRD in CAP.
Second check
Length and byte enables of every doorbell MWr.
Disambiguating experiment
Disable I/O and run Admin only; if the problem vanishes, I/O doorbells are corrupting Admin state.
Likely conclusion
Host address arithmetic or access width.
Confidence
High.

Pattern 5 — Commands hang after resume or reset

Symptom
Submissions made just before or during a reset or power transition never complete.
Possible causes
Doorbells written between CC.EN = 0 and CSTS.RDY = 1 (queues do not exist); doorbells to a function in a low-power state or with Memory Space disabled during the transition; host tail not reset after recreation.
Evidence
Timeline of CC/CSTS accesses and doorbells; AER Unsupported Request logging; first doorbell values after recreation.
First check
Are any doorbells in the reset window?
Second check
Is the first post-reset doorbell value consistent with a tail reset to 0?
Disambiguating experiment
Quiesce submissions before reset and resubmit after queues are recreated; the hang should disappear.
Likely conclusion
Host lifecycle ordering.
Confidence
High with a timeline.

Interview

Beginner

  1. What does an SQ tail doorbell value mean?

    Model answer

    The index of the next free slot: every slot before it (since the previous value) holds a new command.

  2. Why is writing the same doorbell value twice harmless?

    Model answer

    Because it is an absolute position; the second write adds zero new entries.

  3. Is there an SQ head doorbell?

    Model answer

    No. The controller owns the SQ head and reports it in each CQE's SQ Head Pointer.

  4. Does the CPU wait for a doorbell write to complete?

    Model answer

    No. It becomes a posted Memory Write; there is no completion.

  5. Where is the CQ1 head doorbell with stride 4?

    Model answer

    BAR0 + 100Ch.

Intermediate

  1. A VF's BAR0 is above 4 GiB. Which TLP carries its doorbells?

    Model answer

    MWr64 (4-DW header), Length 1, First DW BE 1111b.

  2. Why does an SQ wrap often produce two fetches for one doorbell?

    Model answer

    The last slot and slot 0 are not adjacent in memory; one Memory Read covers one contiguous range.

  3. Name two reasons for "doorbell, but no fetch".

    Model answer

    Bus Master Enable off; controller not ready; queue not created; invalid value; Memory Space Enable off (then the doorbell is not even accepted).

  4. How can a driver prove a posted doorbell reached the device?

    Model answer

    Follow it with a read of a register on the same device; the read completion cannot pass earlier posted writes on that path. Too expensive for the fast path.

  5. What does EventIdx tell the host?

    Model answer

    The index after which the controller wants a real MMIO doorbell; updates that do not cross it can stay in the shadow buffer.

Advanced

  1. Why is atomic slot reservation insufficient for a shared SQ?

    Model answer

    Doorbells can be written out of reservation order (tail regression) and a higher doorbell can publish a lower slot not yet written (stale fetch). The lock must cover reserve, write and ring.

  2. Three causes of long doorbell-to-fetch latency and how to tell them apart?

    Model answer

    Arbitration (other SQs fetched in the gap), back-pressure (fetch follows a CQE), front-end saturation (neither). Lower queue depth below the internal limit to separate back-pressure.

  3. How does a CMB-resident SQ change doorbell ordering?

    Model answer

    SQE writes become posted writes to the device on the same path as the doorbell, so PCIe ordering keeps them in order — provided the CMB mapping does not delay the SQE bytes (write-combining) and Relaxed Ordering is not used.

  4. Why do shadow doorbells not help at queue depth 1?

    Model answer

    The controller is idle between commands and has published an EventIdx that the next update crosses, so every command needs an MMIO write.

  5. Two identical doorbell TLPs in a capture: what do you check?

    Model answer

    Sequence numbers and DLLPs: same sequence with a NAK is a replay; different sequence numbers is a genuine double write. Either way the NVMe effect is the same.

Senior

  1. Review checklist for a new driver's doorbell code?

    Model answer

    Stride from CAP; 32-bit ordered MMIO accessor; barrier placement; lock scope per queue; wrap at size; never ring before SQEs complete; batch-end doorbell on every path including error paths; no doorbells across reset windows; tail/head reset on recreation; Asynchronous Event Request always outstanding; shadow-doorbell barrier and EventIdx comparison with 16-bit wrap.

  2. Validation plan for doorbells?

    Model answer

    Address decode for every DSTRD; values ≥ size, overfill, CQ head past tail, nonexistent queue, reserved bits, Length 2, partial byte enables; with and without outstanding Asynchronous Event Requests; doorbells during reset, disable and power transitions; multi-producer stress; shadow semantics and lost-wakeup tests; doorbell-to-fetch latency distribution under load.

  3. A hypervisor vendor wants to drop shadow-doorbell support. What do you tell them?

    Model answer

    Quantify: at high queue depth shadow doorbells remove nearly all MMIO exits; at low depth they save nothing. Without them, high-IOPS guests pay one exit per doorbell. Offer data, and the alternative of device assignment.

  4. Why is "absence of a doorbell" often the key evidence?

    Model answer

    Missing batch-end doorbells, missing CQ head doorbells and doorbells never sent after reset are host bugs that look like device hangs; only a capture that includes host-to-device writes to the doorbell range can show them.

  5. How would you design a controller's response to a backwards tail?

    Model answer

    Reject it as an invalid value (do not treat as a massive forward move), report through the asynchronous event and error log with queue and value, keep the queue's previous tail so already-published commands still execute, and document the behaviour for host developers.

Quiz

  1. DSTRD = 1. Address offset 1018h is:

    • SQ3 tail
    • CQ1 head
    • SQ1 tail
    • CQ3 head
    Answer and reasoning

    (1018h − 1000h) / 8 = 3 → odd → CQ head of queue 1.

  2. A 256-entry SQ: previous tail 254, new tail 1. How many new entries?

    • 253
    • 1
    • 3
    • Invalid
    Answer and reasoning

    (1 − 254) mod 256 = 3: slots 254, 255, 0.

  3. A doorbell to a function with Memory Space Enable = 0 results in:

    • An Unsupported Request at the PCIe level, no completion
    • An NVMe Invalid Doorbell event
    • A Completer Abort completion to the CPU
    • A normal fetch
    Answer and reasoning

    The function does not accept memory requests; the posted request is an Unsupported Request with no completion.

  4. Which mechanism lets a controller report a bad doorbell value?

    • A PCIe completion status
    • CSTS.CFS
    • An MSI-X write with special data
    • An Asynchronous Event Request completion
    Answer and reasoning

    Posted writes have no completion; NVMe uses Error status asynchronous events.

  5. Atomic slot reservation without a lock around the doorbell can cause:

    • Nothing
    • Tail regression and stale fetches
    • Only redundant doorbells
    • PCIe ordering violations
    Answer and reasoning

    See the race lab: 8 of 20 interleavings fail.

  6. Shadow doorbells save the most when:

    • The workload is sparse
    • The device is physical
    • The controller is continuously busy polling
    • The stride is large
    Answer and reasoning

    Only an awake, polling controller picks updates from the shadow buffer without an MMIO write.

  7. Explain why a long doorbell-to-fetch gap that ends just after a CQE is usually benign.

    Model answer

    It indicates the controller's internal command table was full; a completion freed a slot and the controller fetched the next command. The extra depth is waiting in host memory rather than inside the device — expected when the host queue depth exceeds the device's internal concurrency.

  8. How do you distinguish a replayed doorbell from a duplicated one?

    Model answer

    Replay: same Data Link Layer sequence number, usually preceded by a NAK or replay timeout. Duplicate: different sequence numbers. Only the former suggests a link-quality issue.

Teach-back

  1. To a child: the mailbox dial, why it only says "up to here", and why only one brother may turn it at a time.

    Model explanation

    "You put your letter in the box first, then turn the dial to the last slot that has a letter. The carrier takes everything up to the dial. If two people turn it at once, it can go backwards and the carrier gets confused — so one person at a time. On busy days the carrier peeks anyway, so you just leave a note."

  2. To a junior engineer: how to write a correct multi-producer submission path.

    Model explanation

    "Prefer one SQ per CPU. If CPUs share an SQ, take the queue lock, reserve the tail slot, write the full SQE, advance the tail, call writel with the new tail (it includes the barrier), then unlock. Never ring outside the lock, never ring a value you did not just compute under the lock, and wrap at size, not size − 1."

  3. To a senior engineer: how you attribute doorbell-to-fetch latency and when shadow doorbells pay off.

    Model explanation

    "I classify each delayed fetch by what happened in the gap: other SQs fetched means arbitration; a CQE just before the fetch means internal back-pressure; neither means front-end saturation. Shadow doorbells pay off only while the controller polls — high queue depth on emulated controllers — and depend on a full barrier on the host and an EventIdx re-check on the controller to avoid lost wakeups."
