The Validation Engineering part taught plans, coverage, matrices, negative testing, error injection and regression. This module goes into the part that decides whether any of it means something: the oracle and the strength of the evidence it produces. You will design data-integrity oracles that catch lost, misdirected, stale and torn writes; write protocol invariants that run over trace exports; compute what a run of passes actually proves; and analyse why bugs escape validation.

Orientation

Validation Engineering defined the nine fields of a test, the test oracle, coverage dimensions, compliance, pairwise matrices, negative testing, error-injection methods, regression tiers, golden traces and feature test specifications. This module assumes all of that. Its central concept is the oracle as a measuring instrument: what it can detect, what it is blind to, how often it lies (false passes and false failures), and how many trials it needs before a pass becomes a claim. That is the difference between a test suite that runs and one that protects customers.

  • Validation Engineering: test anatomy, coverage, negative testing, error injection, regression.
  • FLUSH and WRITE: what a completed Write and a completed Flush promise.
  • NVMe Reset: CC.EN, CSTS.RDY and CAP.TO.
  • Trace Analysis Laboratory: the first abnormal event.
  • Performance Engineering module: distributions and run-to-run variance.

Kid story

A class sends 100 letters through a new post office to see if it works. Each letter has a secret mark inside: who it is for, which letter number it is, and a little sum of all the words. When letters come back, the teacher checks each mark. Letter 37 went to the wrong house: the "who it is for" mark shows it. Letter 52 is an old copy from last week: the number is too small. Letter 80 has half its page missing: the sum does not add up.

Then a child asks: "We sent 100 letters and they all arrived. Does that mean the post office never loses letters?" The teacher smiles: "It means it probably loses fewer than about 3 in every 100. If you want to know it loses fewer than 3 in 1 000, we must send 1 000 letters."

Analogy boundary

What it represents. The secret marks are the oracle fields written into every block (target LBA, write sequence number, checksum). Wrong house, old copy and missing half are misdirected, stale and torn writes. "Fewer than about 3 in 100" is the zero-failure bound from statistics.

What it hides. A storage oracle must also know what the right answer is after events that legitimately change it: a power loss before a Flush may lawfully lose recent writes, and a Write still in flight when Flush was submitted is not covered by that Flush. The teacher's answer sheet is simple; a storage oracle's is a model of the specification.

Where it misleads. Letters are independent. Storage failures are not: a firmware bug may fail only under one queue depth, one temperature or one power state, so 3 000 passes in the wrong conditions prove nothing about the right ones. The bound applies to the conditions tested, not to the product.

A pattern header that catches five failure classes

Per-block oracle header (this course's format; place it at the start of every logical block)
BytesFieldCatches
0–7Target LBAMisdirected writes (wrong LBA), misdirected reads
8–11Write sequence number (per LBA, monotonic)Lost writes, stale reads
12–15Write command ID within the test (unique per Write command)Torn multi-block writes (blocks of one command disagree)
16–19Test run identifierLeftover data from earlier runs or other tenants
20–23CRC-32 of bytes 24 to end of blockCorruption inside the block, torn sectors
24–endPseudo-random fill seeded by (LBA, sequence)Pattern-sensitive corruption; regenerable without storing data

The model on the host stores, per LBA, the last sequence number written, the last sequence number known durable (covered by a completed Flush, or written with Force Unit Access, or written with the volatile write cache disabled), and any writes in flight. After a power loss, any read-back sequence between "durable" and "written" is legal; anything below "durable" is a failure. Derived from the durability semantics of Write, FUA and Flush; confirm the exact wording in the NVM Command Set Specification 1.3.

The central concept on the ladder: the oracle as an instrument

Secret marks in every letter, and a teacher who knows what each mark should say, even after the post office had a bad day.

An oracle compares observations with a model of what is allowed. It has a detection range (what it can catch) and an error rate (false passes and false failures).

Pattern headers live in host buffers and travel by DMA into the device; protocol invariants watch TLPs and registers; health oracles read log pages and AER status registers.

Each oracle rule must trace to a normative statement (for example the Flush command's durability promise, the CAP.TO bound on readiness) or to a stated product requirement. Rules from observed behaviour are Implementation-dependent and belong in product specifications, not in conformance oracles.

On the link, oracle fields are visible inside write-data completions and read-data writes; invariants pair requests and completions by tag, and commands and CQEs by CID.

In a capture you can read the header of any block in flight, so the trace itself says whether wrong data left the device or arrived wrong in host memory.

When a test fails, first ask whether the oracle was right: does the specification actually promise what the oracle expected? Then ask what the first violated rule was.

Specification discipline

Sources for the oracles in this module: NVM Command Set Specification, Revision 1.3 — Write, Read, Flush; Force Unit Access; atomicity parameters; NVM Express Base Specification, Revision 2.4 — Controller Registers (CAP.TO, CSTS), Volatile Write Cache feature, SMART / Health Information log, Error Information log, Persistent Event Log; NVMe over PCIe Transport Specification, Revision 1.4; PCI Express Base Specification, Revision 6.x/7.0 — completion and tag rules for protocol invariants.

Where oracle rules come from

  • The specifications do not say how many trials prove compliance, or what failure rate is acceptable.
  • They do not promise which data survives power loss for Writes not covered by Flush, FUA or a disabled cache; an oracle must accept any version between "durable" and "written".
  • They do not define test patterns or verification tools.

Never write an oracle from one device's behaviour. Never treat a pass count as a claim without stating conditions. Never "fix" a flaky test by adding retries.

Confidence high that the device violated its Flush guarantee; root cause inside the device needs vendor debug. Report it as a data-integrity defect with the trial count and rate.

Why it is ambiguous. The test says "device lost flushed data". But the Write was not complete when the Flush was submitted (row 2 precedes row 5). If the Flush guarantee covers only Writes completed before the Flush's submission, as the NVM Command Set's Flush description is commonly read, sequence 4 is a legal result and the oracle is wrong. If the product specification promises more (for example, ordering across a queue), the device is wrong. Resolution. Read the exact Flush wording in NVM Command Set 1.3 and the product's own requirements; then fix whichever is wrong. In this scenario the test harness submitted Flush without waiting for Write CQEs at high queue depth: the model must track "completed before Flush submission", not "completed before Flush completion". Conclusion: false failure, oracle bug (high confidence once the specification text is checked). Corrective action: fix the model, then re-run the campaign, because the same bug may also have hidden false passes.

Labs

Beginner lab: match failures to oracle fields

Objective. For each failure class, choose the header field that detects it and describe a failure the header cannot detect. Safe lab (paper).

Prerequisites. The pattern header table above.

Setup. Failures: (1) block for LBA 0x1000 written to 0x1008; (2) read returns last week's data from another test run; (3) one 4 KiB write of 8 blocks: blocks 0–3 new, 4–7 old; (4) a bit flip in byte 300; (5) read returns all zeros for a block never written.

Procedure. Fill a table: failure · detecting field · what the oracle prints.

Observations. One case needs the model, not just the header.

Questions. Which failure can a header never detect on its own?

Expected reasoning. Headers detect wrong content; the model knows expected content.

Solution

(1) LBA field mismatch at 0x1008 (and the 0x1000 block stale). (2) Run identifier. (3) Write command ID differs between blocks 0–3 and 4–7 (and sequence numbers). (4) CRC-32. (5) Zeros have no header: the model must know whether the block was ever written and what the device returns for unwritten or deallocated blocks (which depends on reported deallocation behaviour). A header alone never detects a write that was silently dropped and left the old valid block: only the model's sequence number does.

Extension. Add a field that detects reordering of writes across different LBAs, and explain when ordering across LBAs is promised at all.

Intermediate lab: protocol invariants over a trace export

Objective. Run invariants over a normalised event list and report the first violation. Safe lab

Prerequisites. PCIe Tags; Python 3.8+.

Setup. Hand-written events stand in for an analyzer export (Module 55 shows how real exports are normalised).

#!/usr/bin/env python3
"""rule_check.py - run protocol invariants over a (synthetic) normalised trace export.
Simulation: events are hand-written dicts standing in for an analyzer export."""

QSIZE = {"SQ1": 1024, "CQ1": 1024}

def check(events):
    open_reads, outstanding_cids, issues = {}, set(), []
    for n, e in enumerate(events, 1):
        k = e["kind"]
        if k == "sq_doorbell":
            if e["tail"] >= QSIZE["SQ1"]:
                issues.append((n, f"SQ1 tail {e['tail']} >= queue size {QSIZE['SQ1']}"))
        elif k == "sqe":
            outstanding_cids.add(e["cid"])
        elif k == "mrd":
            if e["tag"] in open_reads:
                issues.append((n, f"tag 0x{e['tag']:02X} reused while still outstanding"))
            open_reads[e["tag"]] = e["len"]
        elif k == "cpld":
            if e["tag"] not in open_reads:
                issues.append((n, f"completion for unknown tag 0x{e['tag']:02X}"))
                continue
            open_reads[e["tag"]] -= e["len"]
            if open_reads[e["tag"]] < 0:
                issues.append((n, f"tag 0x{e['tag']:02X} returned more bytes than requested"))
            if open_reads[e["tag"]] <= 0:
                del open_reads[e["tag"]]
        elif k == "cqe":
            if e["cid"] not in outstanding_cids:
                issues.append((n, f"CQE for CID 0x{e['cid']:04X} that is not outstanding"))
            outstanding_cids.discard(e["cid"])
        elif k == "msix" and e.get("after_cqe") is False:
            issues.append((n, "MSI-X with no new CQE"))
    for tag, left in open_reads.items():
        issues.append((len(events), f"tag 0x{tag:02X} never completed ({left} bytes missing)"))
    for cid in sorted(outstanding_cids):
        issues.append((len(events), f"CID 0x{cid:04X} never completed"))
    return issues

GOOD = [dict(kind="sq_doorbell", tail=0x105), dict(kind="mrd", tag=0x10, len=64),
        dict(kind="cpld", tag=0x10, len=64), dict(kind="sqe", cid=0x0044),
        dict(kind="mrd", tag=0x11, len=512), dict(kind="cpld", tag=0x11, len=256),
        dict(kind="cpld", tag=0x11, len=256), dict(kind="cqe", cid=0x0044), dict(kind="msix")]
BAD = [dict(kind="sq_doorbell", tail=0x105), dict(kind="mrd", tag=0x10, len=64),
       dict(kind="cpld", tag=0x10, len=64), dict(kind="sqe", cid=0x0045),
       dict(kind="mrd", tag=0x12, len=512), dict(kind="cpld", tag=0x12, len=256),
       dict(kind="mrd", tag=0x12, len=512), dict(kind="cqe", cid=0x0045),
       dict(kind="cqe", cid=0x0045), dict(kind="msix", after_cqe=False)]

if __name__ == "__main__":
    for name, ev in (("good", GOOD), ("bad", BAD)):
        found = check(ev)
        print(f"{name}: {len(found)} violation(s)")
        for i, (n, msg) in enumerate(found):
            print(f"  {'FIRST ' if i == 0 else ''}event {n}: {msg}")

Procedure. Run it; then add an invariant "CQE CID must have been fetched in an SQE on this queue before" (already partly there) and one for "doorbell values must advance modulo queue size".

Observations. Expected output:

good: 0 violation(s)
bad: 4 violation(s)
  FIRST event 7: tag 0x12 reused while still outstanding
  event 9: CQE for CID 0x0045 that is not outstanding
  event 10: MSI-X with no new CQE
  event 10: tag 0x12 never completed (512 bytes missing)

Questions. (a) Which violation is the root and which are consequences? (b) Why must the checker distrust a capture with filters before reporting "never completed"? (c) Which invariant would give false failures with interrupt coalescing?

Expected reasoning. The first violation in event order is the starting point, not necessarily the cause.

Solution

(a) Tag reuse at event 7 is first; the duplicate CQE and the stray MSI-X may be separate bugs or consequences of confused bookkeeping; "never completed" follows from the overwrite. (b) A capture filter that removed completions creates false "never completed" violations; the checker must read capture settings first (LeCroy training). (c) "MSI-X after every CQE": with coalescing, several CQEs share one message, so the rule must be "every MSI-X follows at least one new CQE".

Extension. Mutation-test the checker: inject ten known bugs into GOOD and measure how many it catches.

Advanced lab: what does a campaign prove?

Objective. Compute confidence bounds for campaign results and size campaigns. Safe lab

Prerequisites. Basic probability; Python 3.8+.

Setup. The program uses an exact binomial bound found by bisection.

#!/usr/bin/env python3
"""zero_fail.py - how much does a run of passes prove? (executable, standard library only)"""
import math

def upper_bound(n, k, conf=0.95):
    """Exact (Clopper-Pearson style) upper bound on the failure probability after k failures in n trials."""
    def tail(p):                                  # P(X <= k | n, p)
        return sum(math.comb(n, i) * p**i * (1 - p)**(n - i) for i in range(k + 1))
    lo, hi = 0.0, 1.0
    for _ in range(60):                           # bisection: find p with tail(p) = 1 - conf
        mid = (lo + hi) / 2
        lo, hi = (mid, hi) if tail(mid) > 1 - conf else (lo, mid)
    return hi

def trials_needed(p_max, conf=0.95):
    """Zero-failure trials needed to claim failure probability < p_max."""
    return math.ceil(math.log(1 - conf) / math.log(1 - p_max))

if __name__ == "__main__":
    for n, k in ((300, 0), (3000, 0), (3000, 1), (3000, 3)):
        print(f"{k} failures in {n:>5} trials -> failure rate < {upper_bound(n, k):.5f} (95%)")
    for p in (1e-2, 1e-3, 1e-4):
        print(f"to claim rate < {p:g} with zero failures: {trials_needed(p):>6} trials")
    flake, tests = 0.01, 500
    print(f"suite of {tests} tests, each flaking 1%: P(at least one flake per run) = {1 - (1 - flake)**tests:.3f}")

Questions. (a) A power-loss trial takes 90 s. How long to claim < 10−3 with no failures? (b) One failure appears at trial 2 900. What changes? (c) Why does the 500-test flake result matter more than any single test's flake rate?

Expected reasoning. Bounds scale with 1/p; one failure is a bug to investigate, not a statistic to absorb.

Solution

(a) 2 995 × 90 s ≈ 75 hours on one rig; parallel rigs divide it. (b) Statistically, the bound weakens (about 1.6 × 10−3 at 3 000 trials); in practice, the failure is a data-integrity bug with a reproducing condition to find, and the claim is suspended until it is root-caused. (c) With 500 tests each flaking 1%, 99.3% of suite runs contain at least one false failure, so engineers learn to ignore red results, and real failures hide among them.

Extension. Trials are not independent if the rig always cuts power at the same firmware phase. Add a random cut-time distribution and argue why it matters.

Senior forensic lab: escape analysis of a field data-loss bug

Objective. Classify why a bug escaped and propose process changes with measurable effect. Safe lab (paper exercise on synthetic evidence).

Prerequisites. This module; Validation Engineering regression and coverage sections.

Setup: evidence (synthetic).

  • Field report: after power loss during a firmware update's activation window, a few drives returned data older than the last completed Flush.
  • Validation records: 12 000 power-loss trials per release, zero failures; firmware download and commit tests: 400 per release, all passed, none with power loss.
  • Coverage model's state dimension: controller states (disabled, ready, shutting down) and power states; no "firmware activation in progress" state.
  • Pairwise matrix: "power cut" × "firmware commit" pair never generated, because firmware commit was modelled as a separate test, not a configuration dimension.
  • Oracle: correct; would have detected the bug.

Procedure. Classify the escape as requirement gap, coverage gap, oracle gap, environment gap or analysis gap. Propose changes and a metric to show they worked.

Questions. (a) Was the oracle at fault? (b) What does "12 000 trials, zero failures" prove about this bug? (c) What would you change?

Expected reasoning. A strong oracle is useless in unvisited states.

Solution

(a) No: it would have failed the trial. (b) Nothing: the bound applies to the tested conditions, which never included activation in progress. (c) Coverage gap (state model missing a state) plus a matrix-design gap (a stimulus modelled as a test instead of a dimension). Changes: add firmware download, commit and activation phases to the state model; make "background operation in progress" a matrix dimension crossed with power loss and reset; add a campaign with cuts at random times through activation; track a metric "state × fault pairs covered". Effect: the new campaign reproduces the field bug (proof the gap is closed), and the metric rises from its current value. Senior note: write the escape analysis blamelessly and share it; escapes are the cheapest source of new tests.

Extension. Apply the same analysis to an NVMe 2.4 feature your product adds (for example manufacturing reset): which states does it introduce, and which fault pairs must be crossed with them?

Interview

Beginner

  1. What is a test oracle?

    Model answer

    The rule and model that decide pass or fail for an observation, with a source for each rule.

  2. What is a false pass, and why is it worse than a false failure?

    Model answer

    A pass on a broken product; it ships bugs silently, whereas a false failure costs time but is visible.

  3. Why put the LBA inside each block's data?

    Model answer

    To detect misdirected writes and reads: data found at the wrong LBA identifies itself.

  4. What does Flush promise, informally?

    Model answer

    Data from Writes completed before the Flush was submitted is committed to non-volatile media when the Flush completes (check the exact wording in the NVM Command Set).

  5. Why record margins, not just pass/fail?

    Model answer

    A pass close to a limit predicts a future failure; trends reveal regressions before they fail.

Intermediate

  1. After a power loss, which data versions may an LBA legally return?

    Model answer

    Any version between the last durable one (covered by Flush, FUA or a disabled cache) and the last written one, subject to atomicity rules for torn data.

  2. How do you detect a torn multi-block write?

    Model answer

    Per-block command IDs or sequence numbers disagree across the blocks of one write; compare with the device's reported atomic write unit.

  3. How do you validate an oracle?

    Model answer

    Mutation testing: inject known faults (simulated or real) and confirm detection; review each rule against the specification.

  4. Name three protocol invariants you can check from a trace export.

    Model answer

    Every read completes with the right byte count; no tag reuse while outstanding; one CQE per command; data writes before the CQE.

  5. Why is "add retries" the wrong fix for a flaky test?

    Model answer

    It hides intermittent product bugs and test defects alike; the flake must be root-caused.

Advanced

  1. How many clean trials support "< 0.1% failure at 95%"?

    Model answer

    About 3 000 (2 995 exactly by the formula), under the tested conditions only.

  2. Why do trials need randomised conditions?

    Model answer

    Fixed cut times or orders sample the same internal state repeatedly; independence assumptions fail and rare windows are never hit.

  3. A test fails only with the analyzer attached. Next step?

    Model answer

    Compare link speed, width and correctable errors with and without the probe; if the probe causes errors, the failure is a setup artefact.

  4. How do you turn an ambiguous failure into a decision?

    Model answer

    Find the normative text for the expectation; if it does not promise the behaviour, fix the oracle; if it does, file the device defect with the trace.

  5. Why make background operations a matrix dimension?

    Model answer

    Faults during background work (firmware activation, sanitize, format) hit states that foreground tests never visit.

Senior

  1. How do you measure the quality of a validation organisation?

    Model answer

    Escape rate and severity, time to root cause, mutation scores of oracles, coverage across state × fault pairs, flake rate, and margin trends.

  2. How do you report a campaign to a release board?

    Model answer

    Claims with conditions and bounds, open defects with severity, margins and trends, and explicit untested areas with risk statements.

  3. What is your process after a field escape?

    Model answer

    Reproduce, classify the escape, add the missing coverage or oracle, prove the new test catches the bug, scan for siblings, and publish a blameless analysis.

  4. How do NVMe 2.4 additions change your plan?

    Model answer

    Each new feature adds requirements, states and fault pairs; read Base 2.4 and Revision Changes, extract normative statements, and extend the state model and matrix before writing tests.

  5. When would you block a release on a single failure in 10 000 trials?

    Model answer

    When it is a data-integrity or security failure; rate is irrelevant until the mechanism is understood.

Quiz

  1. A block contains another LBA's header. Failure class:

    • Stale read
    • Misdirected write or read
    • Torn write
    • Bit flip
    Answer and reasoning

    The embedded LBA identifies where the data was meant to be.

  2. Zero failures in 300 trials bounds the failure rate (95%) at about:

    • 0.1%
    • 0.3%
    • 1%
    • 3%
    Answer and reasoning

    About 3/N = 1%.

  3. A Write completes after a Flush that was submitted before it completed. After power loss, old data returns. Most likely:

    • Legal result; check the oracle
    • Device Flush bug
    • Link error
    • Namespace corruption
    Answer and reasoning

    Flush covers Writes completed before its submission; confirm the wording in the NVM Command Set.

  4. RDY after 96% of CAP.TO is:

    • A failure
    • Irrelevant
    • A link issue
    • A pass with dangerous margin
    Answer and reasoning

    The normative rule passes; the trend predicts failure.

  5. Which technique validates the oracle itself?

    • Pairwise testing
    • Mutation testing
    • Bisection
    • Golden-trace diff
    Answer and reasoning

    Seed known faults and check they are caught.

  6. A test passes alone and fails in the suite. Suspect first:

    • Thermal throttling
    • Link width
    • Leftover state from earlier tests
    • Firmware bug
    Answer and reasoning

    Order dependence points at test isolation.

  7. Invariant "MSI-X after every CQE" produces false failures when:

    • Interrupt coalescing is enabled
    • MPS is 256
    • The queue is full
    • ASPM is off
    Answer and reasoning

    Several CQEs share one message.

  8. Open: why can't 12 000 clean power-loss trials clear a bug that occurs during firmware activation?

    Model answer

    The trials never visited that state; statistical bounds apply only to tested conditions.

  9. Open: name the two halves of every error-injection oracle.

    Model answer

    Detection (reported where required) and recovery (full function restored, no data corruption).

Teach-back

  1. To a child: explain secret marks and why 100 good letters do not prove the post office is perfect.

    Model explanation

    "The marks tell us if a letter went to the wrong house, is old, or is torn. If 100 letters all arrive, the post office probably loses fewer than 3 in 100, but to be sure about rarer mistakes we need to send many more."

  2. To a junior engineer: explain the durable/written model for power-loss testing.

    Model explanation

    "For each LBA track the last written sequence and the last durable one: covered by a Flush submitted after the write completed, or by FUA, or with the cache off. After power loss, anything between durable and written is legal; below durable is a bug."

  3. To a senior engineer: argue for investing in oracle quality over test count.

    Model explanation

    "Test count without detection power produces confidence, not evidence. Mutation scores, normative sourcing of rules and state × fault coverage predict escapes; raw counts do not. A smaller suite with strong oracles in the right states finds the bugs customers would."
