Chapter 21 drew the NVMe object model and Chapter 22 mapped the specification family that defines it. This module puts the model under load: two controllers of one subsystem reached through two PCIe ports, namespaces that are shared or private, paths that change state, and identifiers that may or may not mean what the host assumes. Architecture stops being a diagram here and becomes the first thing you check when a drive "disappears", "duplicates" or "fails over badly".

Orientation

NVM Express (NVMe) architecture is a set of scoped objects — NVM subsystem, ports, controllers, namespaces, and the groupings around them — each with identifiers and relationships the host discovers through Identify data and log pages. Getting the model right decides whether the host sees one disk or two, one path or several, and whether data written through one controller is the same data read through another.

You need Chapter 21 — NVMe Architecture (subsystem, controller, namespace, port, host; the dual-controller example; the Invalid Namespace or Format trace) and Chapter 22 — NVMe 2.x Specification Family (Base versus command set and transport specifications, CSI values, controller types, Identify CNS 1Ch). Status decoding is in Chapter 21's trace view.

Next: the controller in depth in Module 21 — NVMe Controller; the subsystem in Module 22 — NVMe Subsystem; namespaces in Module 23 — Namespaces; the same model over networks in Module 50 — NVMe/TCP.

Kid story

Aunt Priya runs a library in a building with two front doors. Each door has its own librarian at a desk. Behind them is one big room of shelves. Some bookshelves can be reached from both desks; some only from one.

The library has one name painted over both doors. Each librarian wears a badge with a number, 1 and 2. Every bookshelf has a shelf number and, painted on its side, a long unique code.

A visitor who knows the rules can use either door to borrow from a shared shelf. When the left door is being repaired, the left librarian says "try again soon" for a while, and the visitor walks round to the right door. But if a new shelf was set up and only the left librarian was told about it, closing the left door makes that shelf vanish.

Analogy boundary

What it represents. The library is the NVM subsystem; the painted name is the NVM Subsystem NVMe Qualified Name (SUBNQN); doors are ports; librarians are controllers with Controller Identifiers (CNTLIDs); shelves are namespaces with Namespace IDs (NSIDs); the long code is the globally unique namespace identifier (NGUID, EUI-64 or UUID); telling a librarian about a shelf is namespace attachment; "try again soon" is an ANA transition.

What it hides. Shelves are grouped into larger units (endurance groups, NVM sets, domains) that share wear and capacity; a librarian may be a different kind (I/O, administrative, discovery) with different duties; the visitor (host) has its own identity (Host NQN, Host Identifier) that matters for reservations and fabrics.

Where it misleads. It suggests the visitor sees the building. A host sees only what Identify data tells it; if two different libraries paint the same name over their doors, the visitor will believe they are one library. And the doors are not independent: two controllers of one subsystem share media and firmware, so one failure can affect both.

Architecture

This module uses a dual-port variant of the lab system, as in Chapter 21's worked example: controller 1 is the usual Lab SSD function at 01:00.0 behind Root Port 00:01.1 (BAR0 0xFE60_0000); controller 2 is at 02:00.0 behind a second Root Port, 00:01.2 (Requester ID 0x0200, BAR0 0xFE40_0000). Both are reached through separate PCIe ports of one subsystem.

Mechanism

Follow a host discovering the dual-port subsystem and creating a shared namespace.

  1. Enumerate. Who: PCIe enumeration and the NVMe driver. What changes: two PCIe functions, two controllers enabled, two admin queues. Where: 01:00.0 and 02:00.0. Evidence: two CC.EN writes, two CSTS.RDY polls.
  2. Identify each controller. Who: driver. What changes: it learns SUBNQN, CNTLID, CMIC, controller type and ANA support from each. Where: 4 KiB Identify Controller data written into host memory. Evidence: MWr64 data TLPs, decodable at known offsets.
  3. Group. Who: host. What changes: controllers with the same SUBNQN are treated as one subsystem. Where: host data structures. Evidence: Linux shows one nvme-subsys entry with two controllers.
  4. List and identify namespaces. Who: driver, per controller. What changes: active NSID list (CNS 02h) and Identify Namespace for each; NMIC and unique identifiers recorded. Evidence: Identify data; one block device per namespace when identifiers match across paths.
  5. Create. Who: administrator via one controller. What changes: Namespace Management (0Dh) create allocates NSID 3 with NMIC = 1; it is not yet active anywhere. Evidence: CQE with Dword 0 = new NSID.
  6. Attach. Who: administrator. What changes: Namespace Attachment (15h) with a controller list — here only CNTLID 1. Where: subsystem metadata. Evidence: the controller-list data buffer fetched by the SSD; Namespace Attribute Changed asynchronous events on affected controllers.
  7. Report path state. Who: each controller. What changes: ANA group states per controller; transitions announced by asynchronous events, detailed in the ANA log. Evidence: Get Log Page for the ANA log; path-related status on I/O during transitions.

ANA states and what the host does

Namespaces are placed in ANA groups; each controller reports a state per group: optimized, non-optimized, inaccessible, persistent loss, or change (transition). I/O through an inaccessible or changing path fails with a path-related status (Status Code Type 3h), and the host retries on another path or waits within the ANA Transition Time the controller advertises. The commonly cited codes are 01h Asymmetric Access Persistent Loss, 02h Asymmetric Access Inaccessible and 03h Asymmetric Access Transition. Uncertain Confirm the path-related status values and the ANA log page identifier (commonly 0Ch) in the Base Specification of your revision.

The ladder

One library, two doors, two librarians; shelves reachable from one or both; a name over the doors and a code on each shelf.

An NVM subsystem has ports, controllers and namespaces; namespaces must be attached to a controller before it serves them; hosts recognise sameness by NQN and namespace identifiers.

Shared firmware and media behind several controller front ends, each with its own queues and registers; metadata tables for allocation, attachment, groups and path states.

NVM Express Base Specification: theory of operation (subsystem, controllers, namespaces, ports, domains), Identify data structures, Namespace Management and Attachment, ANA, asynchronous events; command set specifications for namespace formats; transport specifications for ports.

Admin SQEs and Identify data on each controller's PCIe function; asynchronous event CQEs; path-related status codes on I/O.

The same SUBNQN in two Identify Controller buffers; NMIC and identifiers in Identify Namespace; an attachment controller list; SCT 3h statuses clustering at failover.

"Disk vanished on failover", "two disks appeared", "only one path": reconstruct the object model from Identify data before touching link or media.

Specification discipline

Applicable specifications. NVM Express Base Specification, Revision 2.x — Theory of Operation (NVM subsystem, controllers, namespaces); NVM Express Base Specification — Identify, Namespace Management, Namespace Attachment, Asymmetric Namespace Access; NVM Express NVM Command Set Specification for namespace formats; NVM Express NVMe over PCIe Transport Specification for PCIe ports. The 2.4 set is described in Chapter 22.

Normative The subsystem/controller/namespace/port model; CNTLID unique within a subsystem; NSID scope; SUBNQN in Identify Controller; NMIC in Identify Namespace; namespace management and attachment as admin commands (0Dh, 15h); controller types (I/O, administrative, discovery); CSI values 00h NVM, 01h Key Value, 02h Zoned; CAP.CSS/CC.CSS selecting command sets; ANA as an optional capability with per-group states.

Informative Theory-of-operation figures and examples. The identifier-scope table, the host-behaviour consequences and the failure chains here are derived.

Optional / Implementation-dependent Multiple ports and controllers; namespace management; ANA; how many namespaces and ANA groups a product supports; transition times; whether identifiers are factory-unique; host multipath policy (Linux native multipath versus device-mapper).

Version-dependent Domains and divisions, endurance group and NVM set details, rotational media support, Exported NVM Subsystems and configuration templates (2.4), new controller and namespace types. Uncertain This module does not give 2.4 field layouts; confirm them in the 2.4 Base Specification.

The specification does not say how a host should merge paths, how long it should wait during ANA transitions, or how a manufacturer guarantees identifier uniqueness. Check in your revision: CMIC and NMIC bit assignments, the rule on serial numbers across controllers of one subsystem, the status returned for I/O to an allocated but inactive NSID, and the asynchronous event information values for namespace and ANA changes.

Never assume one PCIe function is one drive, that CNTLID or NSID identify anything outside their subsystem, that NMIC = 1 means the namespace is attached to more than one controller, that a shared SUBNQN proves a shared subsystem, or that Linux shows the device's architecture rather than its own presentation of it.

Linux view

All commands are read-only (Safe lab). Output differs between kernel and nvme-cli versions.

# Subsystems, their NQNs and controllers (paths)

Lab 3 (advanced) — Automate topology checks

Safe lab Pure computation on synthetic records.

Objective. Write checks that catch Traces 3 and 4 automatically. Prerequisites. Traces 3 and 4. Setup. Python 3.

"""Check NVMe architecture facts gathered per controller (teaching tool).

Each record is what Identify Controller / Identify Namespace / the active
namespace list returned on one path. Inputs are synthetic; nothing here
talks to a device. NGUIDs are shortened to labels.
"""
from collections import defaultdict

PATHS = [  # pci address, SUBNQN, CNTLID, serial, CMIC, {nsid: (NGUID, NMIC)}
    ("0000:01:00.0", "nqn.2026-01.example:lab-ssd", 1, "LAB0001", 0b0011,
     {1: ("A1", 1), 2: ("B2", 0), 3: ("C3", 1)}),
    ("0000:02:00.0", "nqn.2026-01.example:lab-ssd", 2, "LAB0001", 0b0011,
     {1: ("A1", 1)}),
    ("0000:05:00.0", "nqn.2014-08.org.nvmexpress:uuid:00000000-0000-0000-0000-000000000000",
     1, "XB777", 0b0000, {1: ("E5", 0)}),
    ("0000:06:00.0", "nqn.2014-08.org.nvmexpress:uuid:00000000-0000-0000-0000-000000000000",
     1, "XB778", 0b0000, {1: ("F6", 0)}),
]

def check(paths):
    by_nqn = defaultdict(list)
    for p in paths:
        by_nqn[p[1]].append(p)
    for nqn, ctrls in by_nqn.items():
        print("SUBNQN", nqn)
        ids = [c[2] for c in ctrls]
        serials = {c[3] for c in ctrls}
        if len(ids) != len(set(ids)):
            print("  !! duplicate CNTLID", ids, "- not one subsystem, or a firmware fault")
        if len(ctrls) > 1 and len(serials) > 1:
            print("  !! different serial numbers", sorted(serials), "under one NQN (verify the SN rule in your revision)")
        if len(ctrls) > 1 and not all(c[4] & 0b0010 for c in ctrls):
            print("  !! several controllers but CMIC multi-controller bit clear")
        paths_of = defaultdict(list)
        for addr, _, cntlid, _, _, nss in ctrls:
            for nsid, (nguid, nmic) in nss.items():
                paths_of[(nsid, nguid)].append((cntlid, addr, nmic))
        for (nsid, nguid), seen in sorted(paths_of.items()):
            note = ""
            if len(seen) == 1 and seen[0][2] == 1 and len(ctrls) > 1:
                note = "  <- shareable but reachable on one path only"
            print("  NSID %d NGUID %s via CNTLID %s%s" % (nsid, nguid, [s[0] for s in seen], note))

if __name__ == "__main__":
    check(PATHS)

Procedure. Run it. Add a check that flags the same NGUID on two different SUBNQNs, and one that flags NMIC = 0 namespaces active on two controllers.

Observations. The lab subsystem reports NSID 3 as shareable but single-path; the zero-UUID pair triggers duplicate-CNTLID, different-serial and CMIC warnings.

Questions. Which check would have prevented the data-corruption risk in Trace 4?

Expected reasoning. Merging paths needs both the same SUBNQN and the same namespace identifier; checking only one is unsafe.

Solution

The NGUID comparison: in Trace 4 the NGUIDs differ, so merging must be refused even though the NQNs match. The NMIC = 0 check catches a device attaching a private namespace to two controllers, which contradicts its own report. Serial number rules across controllers should be confirmed in your revision before treating a difference as an error.

Lab 4 (senior forensic) — "The database volume disappeared during maintenance"

Safe lab Synthetic evidence.

Objective. Build the case for Trace 3 from operational evidence. Prerequisites. This module.

Setup (synthetic). Change log: day 0, "created namespace 3 for DB, shared, attached". Monitoring: nvme list-subsys on day 0 showed two controllers; lsblk showed nvme0n3 with one path. Day 40: Port A cable pulled; nvme0n3 removed; no device errors logged; controller 2 healthy.

Procedure. Explain the outage, identify the first abnormal event, and propose fixes in the tool, the runbook and monitoring.

Questions. Why did "shared" in the change log not protect the volume?

Solution

"Shared" was set as NMIC (capability), but the attachment list held one controller, so the namespace had one path — visible on day 0 as a single path under nvme0n3. Removing that path removed the namespace. Fixes: the tool attaches to every controller listed in the subsystem by default for shared namespaces; the runbook checks path count before maintenance; monitoring alerts when a namespace with NMIC = 1 has fewer paths than the subsystem has controllers. Confidence: high — every step is in Identify data.

Extension. Add ANA: what if NSID 3 had been attached to both but its group were inaccessible on controller 2?

Interview

Beginner

  1. What does an NVM subsystem contain?

    Model answer

    One or more controllers, zero or more namespaces and one or more ports.

  2. Is CNTLID globally unique?

    Model answer

    No, only within a subsystem.

  3. What is the difference between allocated and active namespaces?

    Model answer

    Allocated exists in the subsystem; active is attached to a given controller.

  4. What does NMIC bit 0 mean?

    Model answer

    The namespace may be attached to more than one controller.

  5. Name the three controller types.

    Model answer

    I/O, administrative, discovery.

Intermediate

  1. How does Linux decide two controllers belong to one subsystem?

    Model answer

    Matching SUBNQN (plus checks); it then merges namespaces by unique identifiers.

  2. What does SCT 3h indicate?

    Model answer

    A path-related status: retrying on another path may succeed.

  3. Why can opcode 02h not be decoded without context?

    Model answer

    Opcodes are per queue type and command set; admin 02h is Get Log Page, NVM I/O 02h is Read.

  4. What does Namespace Attachment change?

    Model answer

    Which controllers have the NSID active.

  5. Why do dual-port drives often run x2 per port?

    Model answer

    The connector's lanes are split between two ports.

Advanced

  1. Explain ANA states and host behaviour.

    Model answer

    Per-group states per controller: optimized, non-optimized, inaccessible, persistent loss, change; hosts prefer optimized, use non-optimized when needed, avoid inaccessible, wait during change.

  2. What risk does a placeholder SUBNQN create?

    Model answer

    Hosts may group different drives as one subsystem and, with cloned namespace identifiers, merge different data as paths.

  3. How do endurance groups differ from ANA groups?

    Model answer

    Endurance groups share media wear and capacity; ANA groups share path state.

  4. What does a discovery controller do?

    Model answer

    On fabrics, it lists subsystems and ports; it performs no I/O.

  5. Why compare active NSID lists across controllers?

    Model answer

    Attachment is per controller; one-controller attachment silently creates single-path namespaces.

Senior

  1. What would you require of a dual-port SSD's identifiers?

    Model answer

    Unique, stable SUBNQN and namespace identifiers; distinct CNTLIDs; consistent CMIC/NMIC; documented behaviour of serial number across controllers.

  2. Design a validation for namespace attachment.

    Model answer

    Attach/detach to every combination of controllers; verify active lists, events and I/O on each; check error cases (already attached, invalid list); reset one controller and verify the other.

  3. A customer reports slow failover. Questions?

    Model answer

    ANA states during the event, transition time, host policy, status codes seen, whether the other path was non-optimized or inaccessible.

  4. How do Exported NVM Subsystems change architecture thinking?

    Model answer

    They let a subsystem present derived subsystems built from its resources; identifiers and failure domains must be reasoned about at both levels. Details are 2.4-specific and should be read in the specification.

  5. Where does architecture debugging stop and PCIe debugging start?

    Model answer

    When Identify data on every path is consistent and correct, and the failure persists, move down to the transport.

Teach-back

To a child: the library with two doors.

Model explanation

"Two doors, two librarians, one room of shelves. If only one librarian knows about a shelf, closing her door hides it."

To a junior engineer: how to tell one dual-port drive from two drives.

Model explanation

"Same SUBNQN, different CNTLIDs, CMIC multi-controller, and the same namespace identifiers on both paths: one drive. Same name but same CNTLID or different namespace identifiers: two drives with a bad name."

To a senior engineer: why architecture is checked before the link.

Model explanation

"Most 'disappearing' and 'duplicate' drive incidents are configuration or identity faults visible in Identify data. Ruling them out takes minutes; a capture takes hours and shows nothing about subsystem membership."
