This module goes below the "read, write, copy" summary of Chapter 62 to the places where Subsystem Local Memory (SLM) actually bites engineers: byte-granular transfers and what they do to Physical Region Page (PRP) pointers and PCI Express (PCIe) byte enables, consistency between queues, reset behaviour you must look up rather than assume, host-side planning of offsets, contention with the drive's own DRAM users, and a forensic case where the evidence genuinely points two ways.

Orientation

Chapter 62 established what SLM is (byte-addressable working memory inside the NVM subsystem, exposed as memory namespaces), how it differs from the Controller Memory Buffer (CMB), Persistent Memory Region (PMR) and Host Memory Buffer (HMB), and which side performs the Direct Memory Access (DMA) for each operation. This module assumes that and deepens four things: the exact Transaction Layer Packets (TLPs) a byte-granular transfer produces, the consistency rules a host must impose, how to plan and reclaim SLM space, and how to test and debug reset and contention behaviour.

Read Subsystem Local Memory first. You also need Physical Region Pages (PRP1 offset rules), TLP Header Anatomy (Length, First/Last DW Byte Enables), Posted vs Non-Posted Transactions, Completion Rules (Read Completion Boundary, RCB) and NVMe Reset. The program side is in Computational Programs; next comes NVMe-MI.

Kid story

A post office has a huge sorting table in the back room. The table is painted with tiny numbered squares, one for every letter-sized spot: square 0, square 1, square 2, all the way to square one million.

Customers never walk into the back room. If you want something put on the table, you fill in a ticket: "Put my 600 letters starting at square 4,000." A clerk comes to your counter, collects the letters in bundles, and lays them out. If you want something back, your ticket says "Bring me squares 4,000 to 4,599," and the clerk carries them out in bundles.

Sorting workers can also wheel sacks straight in from the warehouse next door and tip them onto the table, without ever passing the counter. At night the table is wiped clean. And if two customers' tickets both say "square 4,000", whoever's clerk gets there last wins — the table does not care who asked first.

A real table is shared by everyone who can reach the counter. SLM is reachable only by controllers the memory namespace is attached to, and by programs only through memory range sets. The story also hides that the host, not the device, decides which squares each job uses — SLM in this model has no allocator of its own.

Mechanism

Worked mechanism: the host reads a 601-byte program result from memory namespace 3, offset 0x10_0000, into a host buffer at IOVA 0x2_0000_0F82 — deliberately unaligned, as happens when results land inside a larger application structure. PRP entries must be DW-aligned (bits 1:0 = 00b), so this buffer cannot be named by PRP1; the library describes it with a Scatter Gather List (SGL) Data Block descriptor, which needs a controller that reports SGL support without an alignment restriction (whether SLM commands accept SGLs is a question for SLM 1.3).

The central concept on the ladder: a byte-granular transfer

The clerk carries 601 letters in three bundles because bundles have a maximum size and never cross a fence.

An SLM command names bytes, not blocks; the host buffer may start anywhere; the device must move exactly those bytes.

The DMA engine segments by MPS (256 bytes) and 4 KiB boundaries, and marks partial DWs with byte enables; for host → SLM it issues reads up to MRRS (512 bytes) and accepts completions split at RCB (64 bytes).

SLM 1.3 defines offset/length semantics and limits; Base 2.4 and PCIe Transport 1.4 define PRP rules (PRP1 may carry an offset; later entries page-aligned); the PCI Express Base Specification defines the 4 KiB rule, MPS, MRRS, RCB and byte enables.

Posted MWr for SLM → host; non-posted MRd answered by CplD for host → SLM; nothing for internal copies; one CQE per command.

Look for data TLPs whose sizes are not multiples of 512 or 4,096 and whose byte enables are not 1111b: the signature of a byte-granular command.

Wrong bytes at the start or end of a buffer point at PRP1 offset or byte-enable handling; wrong bytes in the middle point at offsets or ordering.

From well-established sources: PCIe requests must not cross a 4 KiB address boundary; memory write payload ≤ MPS; read request size ≤ MRRS; partial read completions end on RCB boundaries; a one-DW request carries its enables in First DW BE with Last DW BE = 0000b. NVMe: PRP1 may contain a page offset; PRP2 and PRP list entries are page-aligned (4 KiB with CC.MPS = 0 on the lab system). libnvme encodes the SLM CSI as 03h.

Read from SLM 1.3, not from this page: SLM command names and opcodes; which command dwords carry offset and length, and their units; granularity, alignment and maximum-transfer fields and their Identify locations; whether SGLs are supported for SLM commands; status codes for misaligned or out-of-range accesses; SLM content behaviour on each reset type; whether memory namespaces are created by namespace management.

The specification does not say how a device segments a transfer within the PCIe rules, how fast internal copies run, or how SLM traffic is prioritised against normal I/O inside the drive.

Never assume: that offsets need only DW alignment; that SLM maximum transfer equals MDTS; that commands on one queue execute in order; that SLM is cleared (or preserved) by a given reset; that a byte-exact read cannot touch bytes outside its range in the host buffer — it must not, and byte enables are how a device guarantees that.

Device DRAM bandwidth is shared. A drive with, say, a 32-bit LPDDR4 interface has a few tens of GB/s of raw bandwidth (illustrative) serving the FTL, write buffering, internal copies into SLM, program loads and stores, and host transfers. Heavy SLM use therefore shows up as higher latency on namespace 1 — evidence you can measure from the host without any device telemetry.

Internal and unobservable: whether SLM is a fixed DRAM carve-out or dynamically shared; ECC protection of SLM (a reliability question to ask the vendor); whether the copy engine bypasses the FTL cache; and how many copies run in parallel.

Consistency rules the host must impose

  • Read-after-write: a read of range R may be submitted only after the CQE of every earlier writer of R (host write, copy, program) has been consumed.
  • Write-after-write: two writers of overlapping bytes must be serialised by CQE; otherwise the final content is undefined.
  • Write-after-read: a buffer whose content is still being read out must not be overwritten (by a new copy) until that read's CQE.
  • Same queue is not enough. NVMe does not execute commands in submission order even on one queue; only completions order work. Normative

Errors. Invalid offset, length, alignment or NSID returns a status in the CQE (generic statuses such as Invalid Field in Command, SCT 0h SC 02h, or SLM-specific values — check SLM 1.3 for which applies). A PCIe-level failure during a host transfer (completion timeout on a CplD, Unsupported Request because a PRP points at unmapped memory and the IOMMU blocks it) surfaces as a data transfer error status and, on the host, as IOMMU or AER log entries.

Labs

Safe lab Labs 1–4 use paper, simulation and synthetic evidence. Extending them to real hardware with pass-through SLM commands is a Caution lab: double-check NSIDs and never target an NVM namespace holding data.

Beginner lab — predict PRPs and TLP counts

Objective: derive PRP1/PRP2 and the number of data TLPs by hand. Prerequisites: Physical Region Pages. Setup: lab system, MPS 256, MRRS 512, 4 KiB host pages.

Procedure: for each transfer give PRP1, PRP2 and the data TLPs: (a) SLM read of 600 bytes into 0x2_0000_0000; (b) SLM read of 601 bytes into 0x2_0000_0F84; (c) SLM write of 1,500 bytes from 0x2_0000_0200; (d) SLM read of 9,000 bytes into 0x2_0000_0800.

Questions: which transfers need PRP2? Which need a PRP list? Expected reasoning: count pages touched first, then split by MPS or MRRS and 4 KiB.

Solution

(a) one page: PRP1 = 0x2_0000_0000, PRP2 unused; MWr 256 + 256 + 88. (b) two pages: PRP1 = 0x2_0000_0F84 (DW-aligned, so legal as a PRP), PRP2 = 0x2_0000_1000; MWr 124 + 256 + 221. (The 0xF82 buffer of the Mechanism section cannot use PRPs at all: it needs an SGL.) (c) one page: PRP1 = 0x2_0000_0200; MRd 512 + 512 + 476, each answered by two CplDs at MPS 256 (the last 256 + 220). (d) 0x800 + 9,000 = 0x2B28, so pages 0x0000, 0x1000 and 0x2000 are touched — three pages, so PRP2 points to a PRP list with entries 0x2_0000_1000 and 0x2_0000_2000; MWr: 8 × 256 to finish page 1 (2,048 bytes), 16 × 256 for page 2, then 2,856 bytes in page 3 = 11 × 256 + 40, so 36 MWr in total.

Extension: repeat (d) with MPS 128 and count again.

Intermediate lab — a TLP predictor for byte-granular transfers

Objective: automate the beginner lab, including byte enables and completion splitting. Prerequisites: beginner lab; Completion Rules. Setup: save as slm_tlp.py; run python3 slm_tlp.py.

#!/usr/bin/env python3
"""slm_tlp.py - predict the device-initiated TLPs for one SLM host transfer.
SLM read  (SLM -> host): device issues MWr, each <= MPS, never crossing 4 KiB.
SLM write (host -> SLM): device issues MRd, each <= MRRS, never crossing 4 KiB;
the completer returns CplDs <= MPS that end on RCB boundaries (except the last).
Splitting at MPS/MRRS-aligned addresses is a common device policy, not a rule.
Addresses >= 4 GiB use 4-DW headers (MWr64/MRd64)."""

def be(addr, length):
    """First and Last DW Byte Enables (4-bit masks) and length in DW."""
    first_dw, end = addr & ~3, addr + length
    dws = (((end + 3) & ~3) - first_dw) // 4
    fbe = (0xF << (addr & 3)) & 0xF
    lbe = 0xF >> ((4 - (end & 3)) & 3)
    if dws == 1:                       # single DW: First BE covers both ends, Last BE = 0
        return dws, fbe & lbe, 0
    return dws, fbe, lbe

def split(addr, length, unit):
    out = []
    while length:
        n = min(length, unit - addr % unit, 4096 - addr % 4096)
        out.append((addr, n)); addr += n; length -= n
    return out

def fmt(a):
    h = f"{a:X}"
    return "0x" + (h[:-8] + "_" if len(h) > 8 else "") + h[-8:-4].rjust(4, "0") + "_" + h[-4:]

def kind(op, addr):
    return op + ("64" if addr >= 1 << 32 else "32")

def slm_read(host_addr, length, mps=256):
    for a, n in split(host_addr, length, mps):
        dws, fbe, lbe = be(a, n)
        print(f"  {kind('MWr', a)} Addr={fmt(a & ~3)} Len={dws}DW FirstBE={fbe:04b} LastBE={lbe:04b} ({n} bytes)")

def slm_write(host_addr, length, mrrs=512, mps=256, rcb=64):
    for a, n in split(host_addr, length, mrrs):
        dws, fbe, lbe = be(a, n)
        print(f"  {kind('MRd', a)} Addr={fmt(a & ~3)} Len={dws}DW FirstBE={fbe:04b} LastBE={lbe:04b} ({n} bytes)")
        ca, left = a, n
        while left:                    # completions: <= MPS, ending on an RCB boundary unless last
            c = min(left, mps)
            if c < left:
                c -= (ca + c) % rcb        # a partial completion must end on an RCB boundary
            print(f"      CplD {c:3d} bytes for {fmt(ca)}")
            ca += c; left -= c

Advanced lab — planning SLM offsets and measuring fragmentation

Objective: see why the host library's offset plan decides how much SLM is usable. Prerequisites: Computational Programs labs. Setup: save as slm_alloc.py; run it.

#!/usr/bin/env python3
"""slm_alloc.py - host-side planning of offsets in one memory namespace.
SLM has no allocator of its own in this model: the host library decides which
byte ranges each job uses. Granularity and capacity are parameters, not
specification values. Compares first-fit and best-fit under a job mix."""
import random

class Allocator:
    def __init__(self, capacity, gran, policy):
        self.cap, self.gran, self.policy = capacity, gran, policy
        self.free = [(0, capacity)]                     # sorted (offset, length) holes
    def alloc(self, size):
        size = -(-size // self.gran) * self.gran        # round up to granularity
        fits = [h for h in self.free if h[1] >= size]
        if not fits:
            return None
        off, ln = fits[0] if self.policy == "first" else min(fits, key=lambda h: h[1])
        self.free.remove((off, ln))
        if ln > size:
            self.free.append((off + size, ln - size)); self.free.sort()
        return (off, size)
    def release(self, rng):
        self.free.append(rng); self.free.sort()
        merged = []
        for off, ln in self.free:                       # coalesce neighbours
            if merged and merged[-1][0] + merged[-1][1] == off:
                merged[-1] = (merged[-1][0], merged[-1][1] + ln)
            else:
                merged.append((off, ln))
        self.free = merged
    def largest_hole(self):
        return max((ln for _, ln in self.free), default=0)

def run(policy, seed=11, steps=4000):
    MiB = 1 << 20
    rng = random.Random(seed)
    a = Allocator(capacity=1024 * MiB, gran=4096, policy=policy)
    live, refused = [], 0
    for _ in range(steps):
        if live and rng.random() < 0.48:
            a.release(live.pop(rng.randrange(len(live))))
        else:
            size = rng.choice([1, 2, 4, 8, 16, 64, 128]) * MiB + rng.randrange(0, 4096)
            r = a.alloc(size)
            if r is None:
                refused += 1
            else:
                live.append(r)
    used = sum(n for _, n in live)
    free = a.cap - used
    frag = 1 - a.largest_hole() / free if free else 0.0
    return refused, used // MiB, len(a.free), a.largest_hole() // MiB, frag

if __name__ == "__main__":
    print("1 GiB memory namespace, 4 KiB granularity, 4000 random alloc/free steps")
    for policy in ("first", "best"):
        refused, used, holes, largest, frag = run(policy)
        print(f"  {policy + '-fit':9s}: refused {refused:4d}, in use {used:4d} MiB, "
              f"holes {holes:3d}, largest hole {largest:4d} MiB, fragmentation {frag:.2f}")

Expected output (deterministic, fixed seed):

1 GiB memory namespace, 4 KiB granularity, 4000 random alloc/free steps
  first-fit: refused   87, in use  784 MiB, holes  17, largest hole   64 MiB, fragmentation 0.73
  best-fit : refused  101, in use  756 MiB, holes  17, largest hole  128 MiB, fragmentation 0.52

Procedure: (1) explain "fragmentation" as computed; (2) change the job mix to only 64 MiB and 128 MiB jobs and rerun; (3) replace the allocator with fixed 128 MiB slabs and compare refusals. Questions: why can a job of 100 MiB be refused when 240 MiB is free? Why can a real library not simply compact SLM? Expected reasoning: free space is useful only if contiguous for one range; moving data needs copies and must wait for every referencing execution.

Solution

Fragmentation = 1 − largest hole / total free: 0.73 means the largest hole is only 27% of free space. With uniform large jobs, holes match job sizes and refusals fall. Slabs waste space inside each slab but never fragment externally; for a few known job sizes they are usually the better design. Compaction requires moving bytes (SLM-to-SLM copies, if supported) while no execution or read references them and updating every range set — expensive and race-prone; libraries prefer slabs or per-job namespaces if the device supports several memory namespaces.

Extension: add range-set lifetimes: a region cannot be freed until its last execution completes; measure how long-running programs increase refusals.

Senior forensic lab — did the FLR leak data?

Objective: decide between readings (a) and (b) of Trace D and write the conclusion with confidence. Prerequisites: PCIe Reset; Root Cause, Ambiguity and Forensic Reporting.

Setup (synthetic evidence): Trace D; host log "reset_method=flr; FLR issued; config restored"; vendor data sheet: "SLM contents are retained across Controller Level Reset and Function Level Reset and are cleared on NVM Subsystem Reset and power loss"; your excerpt of the SLM 1.3 text on reset behaviour (you must look it up — the solution shows how to use it, not what it says); the platform is a single-tenant server.

Procedure: (1) state what the trace proves; (2) compare device behaviour with the data sheet and with the specification text; (3) decide whether it is a defect, and for whom; (4) design the follow-up tests.

Questions: if the specification leaves FLR behaviour implementation-dependent, is retention a defect? Would your answer change on a multi-tenant system that reassigns the function after reset?

Solution

Proven: an FLR happened, the controller was re-initialised, and the device returned pre-reset content. If the SLM 1.3 text you found requires clearing on FLR, this is a specification non-compliance regardless of the data sheet — confidence high. If the text leaves it implementation-dependent or says content is preserved, the device matches its data sheet and is compliant — but on a multi-tenant platform where a function is handed to a new tenant after FLR, retention is a security finding for the platform, whose reassignment procedure must clear SLM explicitly (or use a reset that clears it). Follow-up tests: each reset type alone with a fresh pattern; NVM Subsystem Reset and power cycle (expect cleared per the data sheet); verify that a "clear" really writes or invalidates the content (read back after reset must not return the old pattern). Record which specification sentence each expectation comes from.

Extension: write the platform requirement that closes the multi-tenant gap.

Interview

Beginner

  1. How is SLM addressed?

    Model answer

    By memory namespace NSID, byte offset and length, through SLM I/O commands.

  2. Which TLPs does an SLM read produce?

    Model answer

    Device-issued MWr to host memory (MWr64 above 4 GiB), then the CQE write and MSI-X.

  3. And an SLM write?

    Model answer

    Device MRd requests to host memory answered by CplDs.

  4. Why is a 600-byte transfer a clue?

    Model answer

    Block namespaces move LBA multiples; byte-granular sizes suggest SLM (or metadata/log data).

  5. Is SLM persistent?

    Model answer

    Treat it as volatile unless SLM 1.3 and the device say otherwise.

Intermediate

  1. Give PRP1/PRP2 for 601 bytes into 0x2_0000_0F84.

    Model answer

    PRP1 = 0x2_0000_0F84, PRP2 = 0x2_0000_1000. (At 0x2_0000_0F82 no PRP pair is legal: PRP entries must be DW-aligned, so that buffer needs an SGL.)

  2. Why does a transfer start with First BE = 1100b?

    Model answer

    It begins at byte 2 of a DW; only bytes 2 and 3 are valid.

  3. Why might the same 1,500-byte write produce different CplD counts on two platforms?

    Model answer

    The completer (root complex) chooses how to split within MPS and RCB rules.

  4. Does same-queue submission order guarantee a read sees an earlier write?

    Model answer

    No. Only waiting for the write's CQE does.

  5. What does an immediate error with no data TLPs tell you?

    Model answer

    The device validated and rejected the command before DMA: an argument problem, not a transfer problem.

Advanced

  1. Design boundary tests for SLM writes.

    Model answer

    Length 0, 1, granule − 1, granule, granule + 1, maximum, maximum + 1; offsets at 0, capacity − granule, capacity; host starts at every DW phase and straddling pages; guard bytes on both sides; SLM content checked after every rejection.

  2. Why do copies slow under writes?

    Model answer

    They share flash channels and DRAM with programs and garbage collection; the bottleneck is internal and shows only as latency.

  3. How should a library plan SLM offsets?

    Model answer

    Slabs sized to job classes, per-tenant partitions, lifetimes tied to range sets and outstanding commands, no reuse until all CQEs are consumed.

  4. An IOMMU fault names the SSD during an SLM read. Next step?

    Model answer

    Decode the SQE's PRPs and compare with the faulting IOVA; usually the host built a PRP list for an unmapped page.

  5. What makes a reset-axis test trustworthy?

    Model answer

    One reset type per run, a fresh pattern per run, proof from the trace that the reset happened, and expected values quoted from the specification.

Senior

  1. What SLM questions go into a supplier qualification?

    Model answer

    Revision; capacity, granularity, maximum transfer; reset behaviour per type; ECC on SLM; internal bandwidth under load; QoS interaction; telemetry; multi-namespace support.

  2. Is data retained across FLR a defect?

    Model answer

    Depends on the specification text and on the platform: compliant retention can still be a multi-tenant security issue that the platform must close.

  3. Where should consistency rules be enforced?

    Model answer

    In the host library's dependency tracker, keyed by byte range.

  4. SLM vs CMB for staging data — which and why?

    Model answer

    CMB for host-visible, MMIO-reachable buffers and peer-to-peer; SLM for device-internal processing and copies. Different access models, different failure modes.

  5. What observability would you demand?

    Model answer

    Per-command timestamps, SLM occupancy, copy throughput counters, reset event logs and error counters for SLM accesses.

Quiz

  1. 601 bytes into 0x2_0000_0F82 at MPS 256 needs how many MWr TLPs (minimum)?

    • 2
    • 3
    • 4
    • 5
    Answer and reasoning

    126 to the page end, then 256 + 219: three.

  2. A one-DW write of 3 bytes at byte offset 1 carries:

    • FirstBE 0111, LastBE 0000
    • FirstBE 1111, LastBE 1110
    • FirstBE 0000, LastBE 1110
    • FirstBE 1110, LastBE 0000
    Answer and reasoning

    Bytes 1–3 valid → 1110b; single-DW requests set Last BE to 0000b.

  3. Which PRP entry may carry a non-zero page offset?

    • PRP1 only
    • PRP2 only
    • Every PRP list entry
    • None
    Answer and reasoning

    PRP1 may point inside a page; PRP2 and list entries are page-aligned.

  4. An SLM write fails 0.55 µs after its SQE fetch with no data MRd. Most likely?

    • PCIe completion timeout
    • Flash error
    • Argument validation (offset, length, NSID)
    • IOMMU fault
    Answer and reasoning

    No DMA started; the command was rejected on its fields.

  5. Copies slow down and namespace 1 latency rises at the same time. Best first hypothesis?

    • Link errors
    • Shared internal resources (flash channels, DRAM)
    • Wrong MPS
    • Host CPU starvation
    Answer and reasoning

    Two workloads degrading together with no link anomaly point inside the drive.

  6. Which value most limits how many SLM bytes one command may move?

    • MPS
    • MRRS
    • The SLM maximum transfer reported for the namespace (and MDTS)
    • RCB
    Answer and reasoning

    MPS, MRRS and RCB shape TLPs, not command size.

  7. Why can free SLM be useless for a new job?

    Model answer

    It may be fragmented into holes smaller than the job's contiguous range; compaction is expensive and must wait for every reference to drain.

  8. What does Trace D prove, and what does it not?

    Model answer

    It proves an FLR and re-initialisation occurred and the device returned pre-reset content; it does not prove whether retention is required, allowed or forbidden — that comes from SLM 1.3.

Teach-back

Explain to three audiences, then compare.

To a child — model

"There's a big table with numbered squares in the back of the post office. You write a ticket saying which squares, and a clerk carries your letters in bundles. Bundles can't be too big or cross a line on the table, so odd amounts need extra bundles. If two people ask for the same squares, the clerk who comes last wins — so you wait until your first job is done before asking for the next."

To a junior engineer — model

"SLM commands name an NSID, a byte offset and a length; the host buffer is described with PRPs, and PRP1 can start mid-page. The device turns a read into MWr TLPs no bigger than MPS that never cross 4 KiB, with byte enables for partial DWs; a write becomes MRds of up to MRRS answered by CplDs split at RCB. Internal copies show nothing. Always wait for the producer's CQE before reading."

To a senior engineer — model

"Byte granularity moves correctness risk into host buffer handling and offset planning; NVMe's lack of ordering moves it into the library's dependency tracker; shared DRAM and flash make SLM performance a whole-drive property; and reset semantics are a specification lookup plus a platform security decision. A qualification plan needs boundary, concurrency, contention and reset axes with spec-traceable expectations."
