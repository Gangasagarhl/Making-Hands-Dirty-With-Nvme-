Every other command in this part tells the solid-state drive (SSD) to do something with data. Dataset Management, with its Deallocate attribute, tells the SSD which data it may forget. That single piece of information changes how much work the drive's garbage collector must do, how fast it writes when it is full, and how long it lives. This chapter teaches the command byte by byte and the flash physics that make it matter.

Why this chapter exists

A hard disk does not care whether a sector holds live data or leftovers from a deleted file: overwriting is free. A NAND (Not-AND gate based) flash SSD cares enormously. Flash cannot be overwritten in place; it must be erased in large blocks, so the drive constantly relocates still-valid data to reclaim space. If the drive does not know that a file was deleted, it keeps copying that dead data around forever, burning bandwidth and endurance.

The Dataset Management (DSM) command with the Deallocate attribute is Non-Volatile Memory Express (NVMe)'s way for the host to pass that knowledge down. In the Linux world it is called discard; in the AT Attachment (ATA) world TRIM; in Small Computer System Interface (SCSI) UNMAP. Engineers who understand it can explain write cliffs, latency spikes during fstrim, why a "deleted" file can still be physically on the NAND, and why a read of a freshly trimmed block might return zeros on one drive and old data on another.

It is also a command with a data buffer that most people never look at: a list of up to 256 ranges the controller reads from host memory. Decoding it in a trace is a small but very practical skill.

Learning objectives

  • Encode and decode a Dataset Management command: opcode 09h, Number of Ranges (NR, 0's based), the attribute bits Deallocate (AD), Integral Dataset for Write (IDW) and Integral Dataset for Read (IDR), and the 16-byte range entries.
  • Explain what deallocation means to the flash translation layer (FTL) and to garbage collection, and quantify its effect on write amplification.
  • State what reads of deallocated logical blocks return, using the Deallocate Logical Block Features (DLFEAT) field, and what the specification leaves to the device.
  • Distinguish deallocate from Write Zeroes, Sanitize and Format NVM (the Admin command that reformats a namespace; NVM stands for non-volatile memory).
  • Recognize DSM in a Peripheral Component Interconnect Express (PCIe) trace and debug discard-related performance and correctness problems.
  • Inspect and use discard safely on Linux.

The story

The library vault has shelves that can only be cleaned a whole shelf at a time. Books are never rubbed out; when a book changes, the librarian puts the new copy on an empty shelf and crosses the old copy off her list. When the vault gets full, she picks a shelf with lots of crossed-off books, moves the few good books to a new shelf, and wipes the whole old shelf clean.

Now imagine the teacher throws away some old worksheets but never tells the librarian. The librarian still thinks those books are good, and every time she cleans a shelf she carefully carries them to a new shelf. What a waste! So the teacher sends a note: "Books 100 to 199 and 5,000 to 5,099 — I don't need them any more." That note is DATASET MANAGEMENT with DEALLOCATE. The librarian crosses them off, and cleaning gets much easier.

A self-storage company that packs customers' boxes densely into shipping containers and can only empty a whole container at once. To free a container it must repack the boxes still wanted into another container. When you call and say "boxes 12, 17 and 40 can go to the dump", the company stops repacking them. Your call costs you nothing in boxes, but it saves the company work and keeps your storage fees (latency) down when space gets tight.

What it hides. Telling the company "you may dump these" does not mean they are destroyed today; they sit in the container until it is next emptied. Deallocate does not erase anything immediately, and the old data may physically remain on NAND for a long time — it is not a security mechanism.

Where it misleads. The storage company must obey your call. An SSD may, in some cases, not deallocate what you asked (for example ranges smaller than its internal mapping granularity); and what you get back if you later ask for those boxes — empty boxes, boxes full of 0xFF, or the old contents — is a matter of the device's reported features, not of your call.

What it gets right. The host's information has no value to the host's own data, but it has large value to the device's housekeeping cost.

Beginner explanation

An SSD stores data in NAND flash. Flash has two awkward rules:

  1. You can only write (program) a flash page that has been erased.
  2. You can only erase a whole block, which contains hundreds of pages.

So when you overwrite logical block 42, the SSD writes the new data to a fresh page somewhere else and updates its internal map (the flash translation layer) to say "logical block address (LBA) 42 now lives here". The old page becomes invalid but still occupies space. Eventually the SSD runs out of fresh pages and must perform garbage collection: choose a block, copy its still-valid pages elsewhere, erase it.

The SSD only learns that a page is invalid when the same LBA is written again. If the filesystem deletes a file, the SSD has no idea: those pages look valid, and garbage collection copies them around for nothing.

The Dataset Management command with the Deallocate attribute solves this. The host sends a list of LBA ranges it no longer needs. The SSD marks them as unused in its map. Garbage collection no longer copies them, and the SSD has more free space to work with. Linux calls this discard; you will also hear TRIM.

After deallocation, reading those LBAs does not return an error by default; it returns whatever the SSD says it returns for deallocated blocks — often all zeros. The SSD tells the host which behavior to expect in a field called DLFEAT.

Engineering explanation

The command

Dataset Management is opcode 09h in the NVM Command Set. Its low two opcode bits are 01b: data flows host-to-controller, because the controller reads a buffer of range descriptors from host memory. Support is optional and reported in Identify Controller's Optional NVM Command Support (ONCS) field, bit 2.

As for every command, the 64 bytes are sixteen 32-bit Command Dwords, CDW0 to CDW15.

Ranges and the data buffer

The buffer is an array of NR+1 range entries of 16 bytes each, so between 16 and 4,096 bytes. Each entry:

One Dataset Management range entry (16 bytes, little-endian)
Bytes31…2423…1615…87…0
03:00Context Attributes (access frequency, access latency, sequential read/write hints, write prepare, command access size)
07:04Length in logical blocks (a count — not 0's based)

NR in CDW10 is 0's based; the Length in each range is a plain count. A range of Length 8 covers 8 LBAs. Mixing these up is a classic off-by-one: either you deallocate one LBA too many (data loss in a neighboring file) or you miss one.

Context Attributes are per-range hints (expected access frequency, latency, whether the range will be read or written sequentially, a "write prepare" hint, and a command access size). For deallocation they are normally zero. Few hosts use them, and a controller may ignore them. Optional

Limits on what one command may carry were made explicit in NVMe 2.0: the I/O Command Set specific Identify Controller data structure for the NVM Command Set reports the Dataset Management Ranges Limit (DMRL), Dataset Management Range Size Limit (DMRSL) and Dataset Management Size Limit (DMSL). A zero value generally means "no limit reported". Version-dependent — confirm the fields and their units in the NVM Command Set specification for your revision.

Deallocate semantics

With AD set, the host declares that the data in the ranges is no longer needed. The controller may deallocate the logical blocks. Afterwards, for each logical block, one of two things is true:

  • It was deallocated. A read returns the value DLFEAT describes (below), or, if the host enabled the Deallocated or Unwritten Logical Block Error (DULBE) behavior, an error status.
  • It was not deallocated. A read returns the data last written. This can happen when a range does not cover a whole unit of the controller's internal mapping granularity.

The specification's precise wording about whether deallocation is mandatory or advisory, and about which blocks a controller may decline to deallocate, has evolved; read the Dataset Management and "Deallocated or Unwritten Logical Blocks" descriptions in your revision before relying on either behavior. Uncertain in this course's summary; Version-dependent in the specification.

Identify Namespace reports a preferred deallocation granularity and alignment (Namespace Preferred Deallocate Granularity, NPDG, and Namespace Preferred Deallocate Alignment, NPDA, introduced in NVMe 1.4). Deallocating in multiples of NPDG, aligned to NPDA, is the way to maximize the chance the controller actually frees the space. Linux uses these values (when present) to set the block device's discard granularity.

What reads of deallocated LBAs return — DLFEAT

Identify Namespace contains DLFEAT (Deallocate Logical Block Features). Bits 2:0 report the read behavior for deallocated logical blocks:

DLFEAT bits 2:0 — read value of a deallocated logical block
ValueMeaning for the host
000bNot reported. The host must not assume anything about the data returned.
001bAll bytes read as 00h.
010bAll bytes read as FFh.
011b–111bReserved.

Other DLFEAT bits report whether Write Zeroes can deallocate (the Deallocate bit in Write Zeroes) and how the protection-information Guard field behaves for deallocated blocks. Confirm their exact positions in the NVM Command Set specification. Uncertain

Many client drives report 000b. On those, a filesystem must not rely on a discarded block reading as zeros — for example to skip zeroing a new file's blocks. Linux no longer uses discard to provide guaranteed zeroing (the old discard_zeroes_data attribute now always reads 0); when it needs zeros it uses Write Zeroes, which is defined to return zeros.

Note a historical difference: SATA's original TRIM was a non-queued command that drained the drive's command queue — expensive. Queued TRIM came later. NVMe DSM is always an ordinary queued I/O command.

Impact on the FTL

Inside a page-mapped FTL, deallocation is mostly a mapping-table update: the LBA's entry is set to "unmapped", and the physical page it pointed at is decremented from its block's valid count. No NAND program or erase is needed, so a DSM command can complete quickly — but:

  • The mapping change must itself be made durable (or reconstructable) or the deallocation may be undone by a power loss. Whether a completed deallocation survives power loss without a Flush is tied to the same volatile-cache rules as writes; treat it like a write. Derived
  • Large ranges touch many map entries. Deallocating a terabyte may update hundreds of millions of entries; controllers often record a range-level "trim" in a journal and apply it lazily, but some do the work synchronously and stall.
  • Coarse-grained FTLs (mapping units of 16 KiB or more, or hybrid maps) can only free whole units; sub-unit ranges may be ignored, partially honored or recorded for later.

Impact on garbage collection and performance

Garbage collection cost is driven by how many valid pages must be relocated per block reclaimed. Write amplification factor (WAF) is the standard measure:

WAF = WNAND ÷ Whost
WAF
write amplification factor (1.0 means no extra writes)
WNAND
bytes programmed to NAND, including GC relocations and metadata
Whost
bytes the host asked to write

For a greedy collector that reclaims blocks whose valid fraction is u, each reclaimed block yields (1 − u) of a block of free space at the cost of copying u of a block:

WAF ≈ 1 ÷ (1 − u)
u
average fraction of pages still valid in the blocks the garbage collector chooses to reclaim (0 ≤ u < 1)

Deallocation lowers u by turning dead-but-mapped pages into invalid pages. It also acts like extra over-provisioning: an SSD whose filesystem is 50% full and diligently trimmed behaves, for GC purposes, like a drive with far more spare area than its specification sheet lists. Derived — a simplified model ignoring hot/cold separation, metadata writes and wear leveling.

The practical consequences:

  • Higher sustained write throughput and fewer latency spikes once the drive reaches steady state.
  • Longer life because fewer NAND program/erase cycles are spent on relocation.
  • A cost at discard time. DSM commands occupy the controller; a burst of large discards (for example deleting a huge directory with continuous discard enabled) can raise latency of concurrent I/O. Linux offers both continuous discard (mount option) and periodic batched discard (fstrim, often run weekly by a timer) for this reason.

The central concept on the ladder: deallocation

A note to the librarian: "I don't need these books any more" — so she stops carrying them from shelf to shelf when she cleans.

The host sends DSM with AD and a list of LBA ranges; the controller unmaps them; garbage collection stops relocating their old pages; reads return what DLFEAT promises.

The FTL's logical-to-physical table entries for the LBAs are cleared; per-block valid counts drop; GC victim selection finds cheaper blocks; no NAND program is needed for the deallocation itself.

NVM Command Set: Dataset Management (09h), NR 0's based (CDW10 bits 7:0), AD/IDW/IDR (CDW11 bits 2/1/0), 16-byte ranges; DLFEAT, NPDG/NPDA in Identify Namespace; ONCS bit 2; DMRL/DMRSL/DMSL limits (2.0+).

Doorbell Memory Write (MWr) down; Submission Queue Entry (SQE) Memory Read (MRd) up, Completion with Data (CplD) down; MRd(s) up for the 16–4,096 byte range list, CplD(s) down; Completion Queue Entry (CQE) MWr up; Message Signaled Interrupts – Extended (MSI-X) up.

An SQE with opcode byte 09h and CDW11 = 4; a small MRd (NR+1 × 16 bytes) to the PRP address; CplD payload decodes as (context, length, SLBA) triples.

Write cliff on a nearly empty filesystem? Check discard is reaching the device. Data vanished? Decode the range list for an NR/length off-by-one. Latency spikes every Sunday? Correlate with the fstrim timer.

A controller with a 4 KiB mapping unit can free any 4 KiB-aligned 4 KiB. A namespace formatted with 512-byte LBAs can still ask to deallocate a single 512-byte LBA; the controller cannot free the physical page while seven sibling LBAs in it are still mapped. It may track sub-unit validity, ignore the request, or remember it until the rest of the unit is deallocated. NPDG/NPDA exist so the controller can tell the host its preferred unit. Implementation-dependent

Some controllers keep the mapping table partially in host memory (Host Memory Buffer, HMB) on DRAM-less designs. Large deallocations on such drives touch host memory through device DMA as the FTL updates its map — traffic you may see in a trace that has nothing to do with the range list.

Specification view

Dataset Management is defined in the NVM Express NVM Command Set Specification, Revision 1.3 — Dataset Management command, together with the deallocation behavior and the namespace fields (DLFEAT, NPDG, NPDA) in the NVM Command Set's Identify Namespace data structure and the limits (DMRL, DMRSL, DMSL) in its I/O Command Set specific Identify Controller structure. Common elements — ONCS in Identify Controller, the SQE and CQE, PRP/SGL, generic status codes, the Error Recovery feature used for DULBE — are in the NVM Express Base Specification, Revision 2.4.

Opcode 09h; NR in CDW10 bits 7:0, 0's based, up to 256 ranges; attributes AD (bit 2), IDW (bit 1), IDR (bit 0) in CDW11; 16-byte range entries with Context Attributes (bytes 3:0), Length in logical blocks (bytes 7:4) and Starting LBA (bytes 15:8). DLFEAT bits 2:0: 000b not reported, 001b reads return 00h bytes, 010b reads return FFh bytes. ONCS bit 2 reports Dataset Management support.

WAF ≈ 1/(1 − u), the "effective over-provisioning" view, and the advice to treat deallocation like a write for power-loss purposes are reasoned from SSD architecture and the volatile cache rules, not quoted from the specification.

NPDG/NPDA and several DLFEAT refinements arrived in NVMe 1.4; DMRL/DMRSL/DMSL came with the NVMe 2.0 restructuring into command-set-specific Identify structures; status codes and the precise deallocation wording have been refined across revisions. The baseline for this course is NVM Command Set 1.3 with Base 2.4.

  • The specification does not require a deallocate to physically erase data.
  • It does not bound how long a Dataset Management command may take.
  • It does not define ordering between a DSM and concurrent Reads or Writes to the same LBAs — the host must not issue them concurrently if the outcome matters.
  • Check in the specification: whether deallocation of each block is mandatory or permitted; the exact positions of the other DLFEAT bits; the status for DULBE errors; whether a failing range means other ranges were not processed; the units of DMRSL and DMSL.

Never assume that a discarded LBA reads as zeros unless DLFEAT says 001b (and then only for blocks actually deallocated); that deallocate destroys data; that every layer between the filesystem and the drive passes discards through; or that the range Length is 0's based like NR.

Protocol view

  • Direction. Like a Write: the controller pulls a buffer from host memory with non-posted MRds. A 4,096-byte list (256 ranges) needs at least eight 512-byte MRds on our lab system.
  • Request/response. One CQE for the whole command. There is no per-range status; on error, the host does not know which ranges were processed unless the specification for your revision says so.
  • Ordering. As with all NVMe commands, none between commands. A Read submitted while a DSM to the same LBA is outstanding can return the old data or the deallocated value. A Write submitted concurrently with a DSM to the same LBA can be lost if the deallocation is applied after it. The host must serialize.
  • Buffer ownership. The range buffer belongs to the controller until the CQE arrives, exactly like a Write's data buffer.

In the driver, the discard path builds the range array from the request's segments (up to 256), allocates the buffer, and sets NR and AD. Code / pseudocode

Driver-side construction of a DSM, modeled on what Linux does (simplified pseudocode; not the kernel source):

struct dsm_range { le32 cattr; le32 nlb; le64 slba; };   /* 16 bytes */

/* nvme_setup_discard(): one block request may carry several discard segments */
n = 0;
for each discard segment s in rq:
    if (n == 256) return ERROR;                  /* NVMe limit */
    range[n].cattr = 0;
    range[n].nlb   = cpu_to_le32(bytes_to_lbas(s.len));    /* a COUNT, not 0's based */
    range[n].slba  = cpu_to_le64(sector_to_lba(s.sector));
    n++;

sqe.opcode = 0x09;                                /* Dataset Management */
sqe.nsid   = ns->nsid;
sqe.cdw10  = n - 1;                               /* NR is 0's based */
sqe.cdw11  = 1u << 2;                             /* AD: deallocate */
map_buffer(range, n * 16, &sqe.dptr);             /* one PRP: n*16 <= 4096 */

And a runnable script that builds and parses a range list, then runs a toy page-mapped FTL with greedy garbage collection twice — once ignoring deletions, once deallocating them — to show the effect on write amplification. The FTL has 4,096 physical pages for 3,600 user LBAs (about 14% over-provisioning) and the workload keeps roughly 45% of the LBA space free by deleting data.

#!/usr/bin/env python3
"""dsm_ftl_sim.py - build a Dataset Management range buffer, then show why deallocate
helps a flash translation layer (FTL). Simulation only, standard library, no hardware.
"""
import random
import struct

RANGE_FMT = "<IIQ"            # context attributes (4 B), length in LBAs (4 B), starting LBA (8 B)
RANGE_SIZE = struct.calcsize(RANGE_FMT)
assert RANGE_SIZE == 16
MAX_RANGES = 256


def build_dsm(ranges, deallocate=True):
    """ranges: list of (slba, nlb). Returns (cdw10, cdw11, buffer)."""
    if not 1 <= len(ranges) <= MAX_RANGES:
        raise ValueError("Dataset Management carries 1..256 ranges")
    buf = b"".join(struct.pack(RANGE_FMT, 0, nlb, slba) for slba, nlb in ranges)
    cdw10 = (len(ranges) - 1) & 0xFF          # NR is 0's based
    cdw11 = (1 << 2) if deallocate else 0     # AD = Attribute - Deallocate
    return cdw10, cdw11, buf


def parse_dsm(cdw10, cdw11, buf):
    nr = (cdw10 & 0xFF) + 1
    out = []
    for i in range(nr):
        ctx, nlb, slba = struct.unpack_from(RANGE_FMT, buf, i * RANGE_SIZE)
        out.append((slba, nlb, ctx))
    return nr, bool(cdw11 & 4), out


class ToyFTL:
    """Page-mapped FTL: BLOCKS erase blocks x PAGES pages; one LBA per page."""

    def __init__(self, blocks=64, pages=64, user_lbas=3600, seed=7):
        self.B, self.P, self.N = blocks, pages, user_lbas
        self.map = {}                                  # lba -> (block, page)
        self.valid = [set() for _ in range(blocks)]    # valid pages per block
        self.free = list(range(blocks))
        self.open, self.ptr = self.free.pop(0), 0
        self.host_writes = self.nand_writes = 0
        self.rng = random.Random(seed)

    def _program(self, lba):
        if self.ptr == self.P:
            self._new_block()
        old = self.map.get(lba)
        if old:
            self.valid[old[0]].discard(old[1])
        self.map[lba] = (self.open, self.ptr)
        self.valid[self.open].add(self.ptr)
        self.ptr += 1
        self.nand_writes += 1

    def _new_block(self):
        while len(self.free) < 2:
            self._gc()
        self.open, self.ptr = self.free.pop(0), 0

    def _gc(self):
        candidates = [b for b in range(self.B) if b != self.open and b not in self.free]
        victim = min(candidates, key=lambda b: len(self.valid[b]))   # greedy: fewest valid pages
        movers = [lba for lba, (b, _p) in self.map.items() if b == victim]
        self.free.append(victim)                                     # erased after copying
        self.valid[victim] = set()
        for lba in movers:
            del self.map[lba]
            self._program(lba)                                       # relocation = extra NAND write

    def host_write(self, lba):
        self.host_writes += 1
        self._program(lba)

    def deallocate(self, lba):
        loc = self.map.pop(lba, None)
        if loc:
            self.valid[loc[0]].discard(loc[1])

    def waf(self):
        return self.nand_writes / self.host_writes


def workload(use_trim):
    ftl = ToyFTL()
    rng = random.Random(42)
    live = set()
    for _ in range(60000):
        lba = rng.randrange(ftl.N)
        ftl.host_write(lba)
        live.add(lba)
        # the filesystem deletes files: about 45% of the LBA space is free at any moment
        if len(live) > ftl.N * 0.55:
            dead = rng.sample(sorted(live), len(live) // 10)
            for d in dead:
                live.discard(d)
                if use_trim:
                    ftl.deallocate(d)
    return ftl.waf()


if __name__ == "__main__":
    cdw10, cdw11, buf = build_dsm([(0x1000, 8), (0x9000, 2048), (0x7470_0000, 16)])
    print(f"CDW10={cdw10:#010x} CDW11={cdw11:#010x} buffer={len(buf)} bytes")
    print("range 0 bytes:", buf[:16].hex(" "))
    nr, ad, rngs = parse_dsm(cdw10, cdw11, buf)
    print(f"parsed: NR={nr} AD={ad}", [(hex(s), n) for s, n, _ in rngs])
    print(f"\nwrite amplification without deallocate: {workload(False):.2f}")
    print(f"write amplification with deallocate   : {workload(True):.2f}")

Worked example

Scenario (synthetic). On the lab system (namespace 1, 512-byte LBAs), a filesystem with 4 KiB blocks deletes a fragmented 10 MiB file stored in three extents: 2 MiB at filesystem block 262,144; 6 MiB at block 1,048,576; and 2 MiB at block 4,194,304. The partition starts at LBA 2,048. Continuous discard is enabled.

Step 1 — Convert to LBAs

One filesystem block = 4,096 / 512 = 8 LBAs. Extent start LBA = 2,048 + block × 8; length in LBAs = bytes / 512.

Extents converted to Dataset Management ranges
ExtentStarting LBAHexLength (LBAs)Hex
A (2 MiB)2,048 + 2,097,152 = 2,099,2000x0020_08004,0960x1000
B (6 MiB)2,048 + 8,388,608 = 8,390,6560x0080_080012,2880x3000
C (2 MiB)2,048 + 33,554,432 = 33,556,4800x0200_08004,0960x1000

Step 2 — Build the command

Three ranges → NR = 2 → CDW10 = 0x0000_0002. AD → CDW11 = 0x0000_0004. Buffer of 48 bytes; first range bytes: 00 00 00 00 | 00 10 00 00 | 00 08 20 00 00 00 00 00.

If the block layer merged discards from several files in one request, it could pack up to 256 ranges in one command. (Linux may also split the request according to discard_max_bytes.)

Step 3 — Check alignment against NPDG

Suppose Identify Namespace reports a preferred deallocate granularity and alignment of 8 LBAs = 4 KiB (whether NPDG/NPDA are encoded 0's based is a detail to confirm in the specification Uncertain). All three ranges start at multiples of 8 and have lengths that are multiples of 8: the controller can free every mapping unit. Had the partition started at LBA 63 (an old DOS layout), every range would start mid-unit and the first and last partial units of each range might not be freed. Derived

Step 4 — Predict the read-back

DLFEAT reported as 001b: subsequent reads of these 20,480 LBAs return zeros, provided they were deallocated. If DLFEAT were 000b, the filesystem must not assume anything — it would not anyway, because it no longer references these blocks.

Step 5 — Predict the effect

10 MiB of mapping entries are cleared. If those pages sat in blocks with, say, 70% valid data, and the garbage collector later reclaims those blocks, it now copies less — 10 MiB less in total. On a drive running near full, that is the difference between a 4× and a 2× write amplification in the affected region.

Debugging connection

Failure pattern 1 — Write performance cliff on a "mostly empty" drive

Symptom: sustained write throughput drops sharply after weeks of use although the filesystem is only 40% full. Likely cause: discards never reach the device, so it believes it is nearly 100% full. Evidence: no nvme_cmd_dsm in tracepoints during deletes or fstrim; discard limits of zero on an upper layer (lsblk -D on the dm device). Experiment: run fstrim -v, then repeat the write test; throughput should recover after the device has had time to garbage-collect.

Failure pattern 2 — Live data replaced by zeros

Symptom: a file reads back zeros in a 4 KiB-aligned region after another file was deleted. Likely cause: a host bug deallocating wrong ranges — NR or Length off-by-one, a stale range buffer, a wrong partition offset, or a filesystem bug freeing blocks still in use. Evidence: an analyzer capture of the DSM range list (CplD payload) matched against the file's extents. Experiment: reproduce with discard disabled; if corruption vanishes, the discard path is implicated. The device is almost never the first suspect: zeros are exactly what DLFEAT 001b promises.

Failure pattern 3 — Latency spikes at a fixed weekly time

Symptom: p99 latency spikes for minutes every Sunday 00:00. Evidence: systemctl list-timers shows fstrim.timer; tracepoints show large DSM commands at that time; the trace looks like Trace 35-B. Fix: reschedule, limit discard size, or switch to continuous discard with a device that handles small DSMs well.

Failure pattern 4 — DSM returns an error

Symptom: fstrim reports an I/O error. Evidence: status code (LBA Out of Range points at a partition that extends past NSZE; Invalid Field points at an unsupported attribute or too many ranges against DMRL). First check: partition table versus nvme id-ns NSZE. Second check: DMRL/DMRSL/DMSL versus the kernel's discard limits.

Failure pattern 5 — Old data reappears after power loss

Symptom: after a power cut, deallocated LBAs return old data instead of zeros. Likely cause: the deallocation's map update had not been made durable; the device reverted to the previous map. Interpretation: not necessarily a violation if no Flush followed the DSM on a drive with a volatile cache. Experiment: repeat with a Flush after the DSM completes; if old data still reappears, investigate the device.

The general method is in Debugging Methodology; status codes in Chapter 44.

Senior engineer insight

Senior storage engineers think of the free space a drive knows about as a performance resource. A drive's steady-state write performance and endurance are set by its effective over-provisioning, and the host controls a large share of that through deallocation. That is why database and cloud teams sometimes leave part of an SSD unpartitioned and deallocated: it is cheaper than buying a faster drive.

The second insight is that DSM is a write to the device's metadata. It has a cost, it occupies firmware resources, and on some drives it is processed synchronously. Batching discards into larger, aligned ranges at quiet times is often better than continuous trickle-discard — but for other drives the opposite is true. Measure both on your hardware.

The third: in a layered stack every layer must translate discards correctly — filesystem block to partition LBA, dm-crypt (which by default drops discards because they leak information about free space), thin provisioning, virtual disks. A senior engineer verifies at the bottom of the stack, with tracepoints or an analyzer, before trusting anything above.

Finally, remember Zoned Namespaces (Chapter 59): with zones, the host resets whole zones instead of deallocating arbitrary ranges, and garbage collection moves from the device to the host. Understanding DSM's cost model is the best preparation for understanding why Zoned Namespaces (ZNS) exists.

Answers

1. 1 GiB / 4 KiB = 262,144 = 0x4_0000 LBAs. CDW10 = 0x0000_0000 (one range), CDW11 = 0x0000_0004. Range: ctx 00000000, length 00040000, SLBA low 00100000, SLBA high 00000000; bytes: 00 00 00 00 00 00 04 00 00 00 10 00 00 00 00 00.

2. The Length field is zero (bytes 7:4 = 0) for a range at SLBA 0x2000. A zero-length range describes nothing; how the controller treats it (ignore, or error) is something to confirm in the specification. It most likely indicates a host bug — NR larger than the number of populated ranges, or a 0's based length for a single-block range.

3. With DULBE enabled (and supported), the read completes with an error status indicating a deallocated or unwritten logical block instead of returning zeros. Without DULBE it returns zeros per DLFEAT 001b.

4. DLFEAT may be 000b; the controller may decline to deallocate some blocks (granularity); and the result is not guaranteed across power loss without a flush. Write Zeroes is defined to make subsequent reads return zeros.

5. 1/(1 − 0.8) = 5; 1/(1 − 0.5) = 2.

Quiz

  1. A DSM command has CDW10 = 0x0000_00FF. How many ranges does the controller read, and how many bytes?

    • An error

    • Host MWr to the device Base Address Register (BAR)
    • Inside the SQE's CDW12–15
    • Through the Admin queue
    Answer and reasoning

    DSM is host-to-controller data (opcode low bits 01b); the controller pulls it exactly like Write data.

  6. Which statement about deallocate and security is correct?

    • Deallocate immediately erases the NAND pages
    • Old data may remain on NAND until garbage collection erases the block
    • Deallocate encrypts the data
    • Deallocate is equivalent to Sanitize for the ranges
    Answer and reasoning

    Deallocation updates the map; physical erasure happens later, if at all before reuse.

  7. Explain, using the WAF formula, why deallocation improves sustained write performance on a nearly full drive.

    Model answer

    WAF ≈ 1/(1 − u), where u is the valid fraction of GC victims. Without deallocation, deleted data counts as valid, so u is high and every host write costs several NAND writes. Deallocation lowers u, reducing relocation work and freeing NAND bandwidth for host writes.

  8. Why might a large DSM slow down unrelated reads?

    Model answer

    Some controllers process large deallocations synchronously, updating many map entries and holding FTL resources (locks, firmware cores, DRAM bandwidth, map pages on HMB designs) that reads also need. The effect is implementation-dependent; the trace shows read latency rising while the DSM is outstanding.

  9. A DSM with four ranges fails with LBA Out of Range. What can the host conclude about the three valid ranges?

    Model answer

    Nothing reliable from the status alone; whether they were processed before the error is not reported per range. The host should resubmit the valid ranges (deallocation is idempotent) after fixing the bad one.

  10. Name two fields that help the host choose discard sizes and alignment, and where they live.

    Model answer

    NPDG and NPDA in Identify Namespace (preferred deallocate granularity and alignment); also DMRL/DMRSL/DMSL in the NVM Command Set's I/O Command Set specific Identify Controller structure for limits on ranges and sizes.

Interview questions

  1. Beginner. What is TRIM and what is its NVMe equivalent?

    Model answer

    TRIM is the ATA mechanism for telling an SSD which LBAs no longer hold useful data. NVMe's equivalent is the Dataset Management command (opcode 09h) with the Deallocate attribute (CDW11 bit 2), carrying up to 256 ranges.

  2. Beginner. Why does an SSD need to be told about deleted data when a hard disk does not?

    Model answer

    Flash cannot be overwritten in place and is erased in large blocks, so the SSD must relocate valid data during garbage collection. Without being told, it treats deleted data as valid and relocates it needlessly. A hard disk overwrites sectors in place at no extra cost.

  3. Intermediate. Describe the DSM range format and its two counting conventions.

    Model answer

    16 bytes per range: Context Attributes (bytes 3:0), Length in logical blocks (bytes 7:4, a count), Starting LBA (bytes 15:8). The number of ranges in CDW10 bits 7:0 is 0's based, the range Length is not.

  4. Intermediate. What does DLFEAT tell the host, and how should Linux use it?

    Model answer

    Bits 2:0 report what reads of deallocated blocks return (not reported, zeros, or FFh). Other bits report Write Zeroes deallocation support and guard behavior. Linux does not treat discard as a zeroing operation; it uses Write Zeroes when zeros are required, possibly with deallocation if the device supports it.

  5. Advanced. Continuous discard or periodic fstrim? How do you decide?

    Model answer

    Measure. Continuous discard keeps the device informed promptly but sends many small DSMs during deletes, which some devices handle poorly. Periodic fstrim sends large batches that some devices process synchronously, causing latency spikes. Consider workload (large deletes vs small), latency service-level objectives (SLOs), device behavior (trace DSM latency vs size), and intermediate layers. Many distributions default to weekly fstrim.

  6. Advanced. A customer finds zeros in a database file after deleting an unrelated table. Investigate.

    Model answer

    Suspect the discard path first: capture DSM range lists (analyzer payload or instrumented driver) and compare with the database file's extents (filefrag). Check NR/Length off-by-ones in any custom user-space driver, partition offsets, and filesystem bugs. Reproduce with discard disabled. Check whether DLFEAT is 001b (zeros consistent with deallocation). The device is a later suspect.

  7. Senior. How would you validate an SSD's Dataset Management implementation?

    Model answer

    Functional: NR 0 and FFh; ranges at LBA 0, NSZE−1, crossing NSZE; zero-length; overlapping and duplicate ranges; misaligned vs NPDG; attributes combinations; DMRL/DMRSL/DMSL limits; DLFEAT read-back for deallocated blocks; DULBE enabled/disabled; protection information formats. Concurrency: DSM with reads/writes to other LBAs (latency) and verifying the host-side serialization assumptions. Durability: power loss after DSM with and without Flush. Performance: DSM latency vs size, effect on concurrent I/O, steady-state WAF/throughput with and without deallocation at several fill levels.

  8. Senior. Explain the relationship between deallocation, over-provisioning and ZNS.

    Model answer

    Deallocation increases the free space the FTL can use, acting as dynamic over-provisioning, which lowers GC write amplification. ZNS removes device-side GC for zoned data: the host writes zones sequentially and resets them whole, so instead of deallocating arbitrary ranges it manages placement and reclamation itself, trading host complexity for predictable device behavior.

Model explanations

Child: "If she thinks every book is important, she carries all of them each time she cleans a shelf. If you tell her which ones you threw away, she carries fewer and cleans faster."

Junior: "Make three 16-byte entries — context zero, length as a count, starting LBA as 64 bits little-endian — in a zeroed buffer. Set NR to 2, AD (bit 2 of CDW11), point PRP1 at the buffer. Check every range is inside the namespace and aligned to NPDG/NPDA, and don't issue writes to those LBAs until the DSM completes."

Senior: "Effective over-provisioning, and therefore steady-state WAF, latency and endurance, depend on what the FTL knows is free. Discards can be dropped by encryption layers, thin provisioning, virtual disks or misconfigured mounts; verify at the NVMe driver. Batch and align discards to the device's preferences and measure DSM cost on the actual device."

Chapter summary

Dataset Management (opcode 09h) carries up to 256 sixteen-byte ranges in a host buffer the controller pulls with PCIe Memory Reads; NR in CDW10 is 0's based, the range Length is a plain count. With the Deallocate attribute (CDW11 bit 2), the host tells the FTL which LBAs are dead. The FTL unmaps them, garbage collection stops relocating them, write amplification falls and sustained write performance and endurance improve. Reads of deallocated blocks return what DLFEAT reports (zeros, FFh, or unspecified), or an error with DULBE. Deallocation is not erasure, may be limited by mapping granularity (NPDG/NPDA), carries its own processing cost, and must be serialized with other I/O to the same LBAs by the host.
