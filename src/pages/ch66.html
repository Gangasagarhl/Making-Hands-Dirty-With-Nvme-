NVMe over TCP (NVMe/TCP) carries NVM Express (NVMe) capsules and data over ordinary Transmission Control Protocol / Internet Protocol (TCP/IP) networks. This chapter goes byte by byte through the Protocol Data Units (PDUs) that frame capsules on a TCP stream. It traces the command, data and completion paths for reads and writes, explains header and data digests and Transport Layer Security (TLS) 1.3, and builds a working method for performance analysis and debugging from packet captures.

Why this chapter exists

NVMe/TCP is the most widely deployable NVMe-oF transport. It needs no special NICs, no lossless Ethernet configuration and no subnet manager, just IP connectivity. That accessibility means you will meet it everywhere: in cloud block storage, in disaggregated flash arrays, in Kubernetes storage, and in your own lab with nothing but two Linux machines or one VM.

It is also the transport you can see most clearly. Every capsule, every byte of data and every digest crosses a TCP stream that tcpdump can record and Wireshark can decode. Once you can read an NVMe/TCP capture as fluently as a PCIe trace, you can debug remote storage problems that otherwise look like "the network is slow".

Chapter 65 gave you the model: capsules, the message-based transport, Fabrics commands. This chapter makes it concrete for one transport.

The story

Imagine a very long pipe between two houses. You can pour marbles into one end and they come out the other end in exactly the same order. None get lost (if one falls out, the pipe puts it back). But the pipe has no idea where one message ends and the next begins. It is just a stream of marbles.

So the two families agree on a rule. Every message starts with eight special marbles that say "this is a letter, and it is 72 marbles long", or "this is a parcel of 4,096 marbles for request number 66". The family at the other end counts marbles and always knows where the next message starts.

Sometimes the sender wants to send a huge parcel, but the receiver's shelf is not ready. So the receiver sends a little note back: "Ready for parcel 66, send me marbles 0 to 8,191." That note is called "Ready to Transfer".

Think of a freight railway between a factory and a warehouse, with one dedicated track per loading dock. Every wagon has a standard placard on the front: wagon type, how long the placard is, where the cargo starts, and the total wagon length. Order wagons (capsules) carry a work order. Cargo wagons carry goods and say which order and which part of it they belong to. When the warehouse is ready to accept a big inbound shipment, it sends back a "ready to receive" wagon with a dock ticket number. Optional seals (digests) on the placard and the cargo let inspectors detect tampering or damage. A locked, armoured train (TLS) hides everything except the fact that wagons are moving.

What it hides. TCP does not deliver "wagons". It delivers bytes, and one PDU may be cut across many TCP segments, or many PDUs may share one segment. The receiver must reassemble PDUs from the byte stream using the length in the header. Trains also do not run in reverse on the same track. A TCP connection is full duplex, and PDUs flow both ways at once.

Where it misleads. The railway suggests a "ready to receive" wagon is needed for every delivery. In NVMe/TCP, read data (controller to host) is sent without asking: the host already allocated the buffer when it sent the command. R2T is used only for host-to-controller data that does not travel in-capsule.

Beginner explanation

TCP gives NVMe/TCP a reliable, in-order, full-duplex byte stream between a host and a target. NVMe needs to send discrete things over it: a command, a block of data, a completion. So NVMe/TCP defines a small set of message types called PDUs. Every PDU begins with the same 8-byte common header that states its type and total length.

Each NVMe queue pair, the admin queue and every I/O queue, gets its own TCP connection. When a connection opens, the two sides exchange an Initialize Connection Request (ICReq) and Initialize Connection Response (ICResp) to agree on options such as digests. Then the host sends the Fabrics Connect command in a CapsuleCmd PDU, and the queue is ready.

After that, NVMe I/O follows three paths:

  • Command path: the host sends a CapsuleCmd PDU containing the SQE (and small write data, if it fits in-capsule).
  • Data path: read data comes back in C2HData (controller-to-host data) PDUs. Write data that did not fit in the capsule goes in H2CData (host-to-controller data) PDUs, but only after the controller asks for it with an R2T (Ready to Transfer) PDU.
  • Completion path: the controller sends a CapsuleResp PDU containing the CQE.

Two optional features protect and hide the data. A header digest and a data digest add CRC32C checksums. TLS 1.3 encrypts and authenticates the whole stream.

Default port: 4420 for NVMe/TCP I/O controllers, and 8009 for the NVMe/TCP discovery service. Both are IANA-registered for NVMe-oF use. Targets may listen on any port they choose. Discovery tells the host which.

Engineering explanation

Why framing is needed on a byte stream

TCP preserves byte order but not message boundaries. A sender writes a 4,120-byte C2HData PDU. With Generic Segmentation Offload, the NIC may cut it into three 1,448-byte segments on a 1,500-byte MTU network. The receiver's Generic Receive Offload may merge those with the following CapsuleResp into one large buffer. NVMe/TCP must therefore be self-delimiting. Every PDU announces its own total length (PLEN) in a fixed position, so a receiver can always find the next PDU boundary. If a single length field is corrupted and undetected, every later PDU on the connection is misparsed. This is why the header digest exists and why framing errors are fatal to the connection.

One TCP connection per queue pair

NVMe/TCP maps each NVMe queue pair to one TCP connection. A host with 16 I/O queues to a controller holds 17 TCP connections: 1 admin + 16 I/O. This preserves NVMe's lock-free, per-CPU queue design. Each host CPU can own one connection, and the target can steer each connection to one of its CPUs (via RSS, Receive Side Scaling, or aRFS, accelerated Receive Flow Steering). The I/O queue count is negotiated through Set Features Number of Queues and Linux's nr_io_queues option. Implementation-dependent

The write data path: in-capsule, or R2T and H2CData

If the write fits in the capsule (≤ IOCCSZ × 16 − 64 bytes, see Chapter 65), the data rides in the CapsuleCmd and there is one round trip. Otherwise:

  1. The host sends a CapsuleCmd with a Transport SGL Data Block descriptor (5Ah) and the total length.
  2. When the controller has buffer space, it sends an R2T naming CCCID, a TTAG it chose, the offset R2TO and length R2TL it wants now.
  3. The host answers with one or more H2CData PDUs covering exactly [R2TO, R2TO + R2TL), each no larger than MAXH2CDATA, echoing TTAG. The last one for that R2T carries LAST_PDU.
  4. The controller may issue further R2Ts for the rest of the data, with at most MAXR2T + 1 outstanding per command.
  5. When all data has arrived and the write completes, the controller sends a CapsuleResp.

The controller never receives write data it did not ask for, except in-capsule data whose maximum size it advertised. This protects target memory. A target under memory pressure simply delays R2Ts, and that delay shows up in captures as a gap between CapsuleCmd and R2T. When you see write latency, measure that gap first.

The completion path: CapsuleResp

A CapsuleResp is CH (8) + CQE (16) = HLEN 24. The CQE's CID matches the command's CID. Its Status field is the ordinary NVMe status. A transport-level problem that affects one command but not the connection, such as a data digest error, is reported through NVMe status values for transport errors. A problem that destroys framing is reported with a TermReq PDU and the connection closes.

Termination PDUs: H2CTermReq and C2HTermReq

When either side detects a fatal transport error, it sends a TermReq PDU and closes the TCP connection. The PDU carries a Fatal Error Status (FES) and Fatal Error Information, plus a copy of the offending PDU header (up to a limit). FES values the specification defines include, by name: Invalid PDU Header Field, PDU Sequence Error, Header Digest Error, Data Transfer Out of Range, Data Transfer Limit Exceeded (R2T limit), and Unsupported Parameter. Confirm values Read the numeric FES encodings from the TermReq PDU figures in TCP Transport 1.3. Linux decodes them in drivers/nvme/host/tcp.c.

When a connection terminates, its queue pair is gone. If it was the admin queue, the association is gone. The host's error recovery then tears down and reconnects the controller: state goes to resetting, then connecting.

Digests: what they protect

TCP has a 16-bit ones'-complement checksum, and Ethernet has a 32-bit FCS. Why add more? The Ethernet FCS protects only one link hop, and is recomputed by every switch and router. The TCP checksum is weak, and is frequently computed by NIC offload hardware that never sees memory corruption, which can occur in host memory, in a NIC, or in a middlebox. NVMe/TCP's optional digests are CRC32C (the Castagnoli polynomial, also used by iSCSI). They give end-to-end protection between the NVMe/TCP layers on each side.

  • Header digest (HDGST): 4 bytes immediately after the PDU header, covering CH + PDU-specific header. A mismatch means the framing itself is untrustworthy, so it is fatal to the connection.
  • Data digest (DDGST): 4 bytes after the PDU data, covering the data only (not padding). A mismatch means this command's data is bad, but framing is intact, so the command fails and the connection may survive.

Digests cost CPU unless the NIC offloads them. Modern CPUs compute CRC32C with dedicated instructions (SSE4.2 crc32 on x86, CRC extensions on Arm), so the cost is real but small. Some NICs offer NVMe/TCP digest offload. Implementation-dependent Linux disables digests by default.

TLS 1.3 for NVMe/TCP

Transport Layer Security (TLS) encrypts and integrity-protects the whole TCP stream. Current NVMe/TCP specifications require TLS 1.3 when TLS is used. NVMe/TCP TLS is based on pre-shared keys (PSKs) rather than certificates:

  • Configured PSK: an administrator provisions a key on host and target, in an interchange format that nvme-cli can generate (nvme gen-tls-key). From it, both sides derive a retained PSK and a TLS PSK identity that names the host NQN, subsystem NQN and hash.
  • Generated PSK (secure channel concatenation): the host first authenticates in-band with DH-HMAC-CHAP (Authentication Send/Receive) on an unencrypted admin queue. The exchange produces a key, and the queues are then reconnected over TLS using a PSK derived from it. Version-dependent This was introduced in later TCP transport and Base revisions. Linux support arrived in 2024–2025 kernels.

The discovery log page entry for a port says whether TLS is required, not required or supported, using its Transport Requirements (TREQ) and transport-specific (TSAS) fields. See Fabric Architecture.

On Linux, the kernel does not perform the TLS handshake itself. The tlshd daemon (from ktls-utils) performs the handshake in user space, using PSKs stored in a kernel keyring (.nvme), then hands the session keys to kernel TLS (kTLS) for the data path.

With TLS on, a capture shows a TLS 1.3 handshake (ClientHello with a PSK identity, ServerHello) right after the TCP handshake, and then only "Application Data" records. ICReq, every capsule and every digest are inside the encryption. To debug at the NVMe layer you need either the session keys (exported by the endpoint for a lab capture) or host/target tracing. In production, TLS is the reason "just take a capture" stops being enough. Plan observability before you enable it.

The 2026 NVMe 2.4 set updated the asymmetric key-exchange options in authentication to prepare for post-quantum cryptography. That affects how keys for secure channel concatenation can be derived. The framing in this chapter is unchanged. See 2026 NVMe 2.4 Updates and read algorithm identifiers only from the Base 2.4 specification.

Keep alive over TCP

A TCP connection can stay "up" while the far end is dead, for example a crashed target behind a switch that never sends a reset. NVMe's Keep Alive mechanism (admin command 18h, timeout KATO set in the admin Connect) detects this at the NVMe layer. If the controller sees no Keep Alive (or, with Traffic Based Keep Alive, no commands) within KATO, it tears down the association. If the host's Keep Alive commands are not completed, the host resets and reconnects. Linux sends Keep Alive at a fraction of KATO. Implementation-dependent Chapter 68 covers keep alive and reconnection policy in depth.

The central concept on the ladder: the NVMe/TCP PDU

Every parcel on the marble pipe starts with eight special marbles saying what kind of parcel it is and how long it is.

A PDU is a self-delimiting message on a TCP stream: an 8-byte common header (type, flags, header length, data offset, total length), a type-specific header, optional digests and padding, and optional data.

Host and target NVMe/TCP drivers build PDUs in socket buffers. NICs segment them into TCP/IP packets and may offload checksums and segmentation. On receive, the stack reassembles the byte stream and the driver walks it PDU by PDU, copying data into request buffers (or placing it directly, with DDP offload).

The NVMe over TCP Transport Specification, Revision 1.3 defines PDU types, header layouts, ICReq/ICResp negotiation, digests, R2T rules, termination and TLS use. The Base 2.4 specification defines the capsules carried inside.

Read: CapsuleCmd → C2HData… → CapsuleResp. Write (large): CapsuleCmd → R2T → H2CData… → CapsuleResp. Write (small): CapsuleCmd with in-capsule data → CapsuleResp. Fatal error: TermReq, then FIN/RST.

Wireshark shows "NVMe/TCP" frames with the PDU type, CCCID, DATAO/DATAL and the decoded SQE/CQE. Several PDUs may share one frame, and one PDU may span several frames.

A TermReq names the fatal error and quotes the bad header. A gap before R2T means target buffer pressure. Retransmissions mean network loss. A command with C2HData but no CapsuleResp, followed by a host abort, means the target's completion path. Classify each anomaly by layer before forming a hypothesis.

Where the bytes get copied. Without offload, a 4 KiB read on the host typically goes: NIC DMA → kernel socket buffer → copy into the block request's pages. On the target: backing device DMA into target memory → (possibly) copy into socket buffer → NIC DMA. Each copy costs memory bandwidth and CPU. This is the fundamental performance gap between NVMe/TCP and NVMe/RDMA, where the RNIC moves data directly between registered buffers. Implementation-dependent Zero-copy transmit paths and DDP offloads narrow the gap.

MTU and segmentation

With a 1,500-byte MTU and TCP timestamps, each segment carries up to 1,448 bytes of payload. A 128 KiB C2HData PDU becomes about 91 segments. With a 9,000-byte (jumbo) MTU it becomes about 15. Fewer segments mean fewer per-packet costs, but jumbo frames must be configured end to end. A single 1,500-byte hop causes fragmentation or, with Path MTU Discovery blocked, black-holed large packets. This is a classic NVMe/TCP failure: small commands work, large I/O hangs.

Specification view

NVMe/TCP framing is defined normatively by the NVMe over TCP Transport Specification, Revision 1.3. The capsule contents, Fabrics commands, authentication protocols and status codes come from the NVM Express Base Specification, Revision 2.4. TCP itself is defined by the IETF (RFC 9293), and TLS 1.3 by RFC 8446. NVMe documents reference them rather than redefine them.

  • Every PDU starts with an 8-byte common header: PDU-Type, FLAGS, HLEN, PDO, PLEN.
  • PDU types 00h–07h and 09h are ICReq, ICResp, H2CTermReq, C2HTermReq, CapsuleCmd, CapsuleResp, H2CData, C2HData and R2T.
  • ICReq/ICResp are exchanged once per connection before any capsule, and negotiate PFV, data alignment, digests, MAXR2T and MAXH2CDATA.
  • Header and data digests are CRC32C and optional, and are enabled by negotiation.
  • Each NVMe queue pair maps to one TCP connection.
  • Port 4420 is registered for NVMe-oF and port 8009 for NVMe/TCP discovery.
  • Because HLEN is fixed per PDU type, a receiver can validate it immediately. Any mismatch indicates corruption or a peer bug, never a negotiable difference.
  • Because header digests cover only headers, data corruption with digests disabled goes undetected by NVMe/TCP. Only the TCP checksum, which is often offloaded, stands in the way.
  • Because R2T is the only way large write data is solicited, write throughput per command is bounded by MAXR2T × R2TL per round trip.
  • Target in-capsule data size, MAXH2CDATA and how many R2Ts a target issues per command.
  • Whether data digests are verified in software or hardware, and whether the C2H SUCCESS optimization is used.
  • Linux options: nr_io_queues, queue_size, hdr_digest, data_digest, tls, keep_alive_tmo, ctrl_loss_tmo, reconnect_delay.
  • CPU steering of connections (RSS, aRFS, XPS) and busy polling.
  • NVMe/TCP was ratified as a Technical Proposal against NVMe-oF 1.1 (2018–2019) and became its own transport specification with the NVMe 2.0 restructuring.
  • TLS support moved from optional/early forms to TLS 1.3 requirements, with configured and generated PSKs, across TCP transport revisions. Secure channel concatenation came later.
  • The 2.4 set (August 2026) revised all transport specifications together. Check the Revision Changes document for TCP 1.3 specifics before claiming a behaviour is new or old.
  • The specification does not require digests. "Digests off" is fully compliant.
  • It does not specify TCP tuning: congestion control algorithm, Nagle (Linux nvme-tcp disables it), buffer sizes, or MTU.
  • It does not define performance targets or how many connections a host should open.
  • Exact FES numeric values, TLS PSK identity format details and any 1.3-specific PDU fields must be read from the TCP Transport 1.3 document. This chapter names them without numbers.
  • Never assume one TCP segment equals one PDU.
  • Never assume every read ends with a CapsuleResp (the SUCCESS flag may replace it).
  • Never assume digests are on because the admin queue showed them.
  • Never assume a TCP retransmission is an NVMe error. It is a latency event.

Ordering and concurrency

  • Within one connection, PDUs arrive in the order sent. Across connections, no order exists. Commands on different queues are independent, exactly as on PCIe.
  • Many commands are interleaved on one connection. C2HData for CID 0x0052 may be followed by C2HData for 0x0053 and then more for 0x0052. The target chooses the interleaving at PDU granularity. A PDU itself is never split by another PDU.
  • Completions may be out of order. CID matching is mandatory.
  • The host may send new CapsuleCmds while H2CData for earlier commands is in flight. Writes do not block the queue.

Code / pseudocode

A receiver's hardest job is reassembling PDUs from arbitrary TCP segments and checking digests. The program below builds a C2HData + CapsuleResp stream with both digests, feeds it to a receiver in random-sized chunks, and shows what happens when a data bit or a header bit is corrupted. It is a standard-library-only simulation and runs as written.

#!/usr/bin/env python3
"""nvme_tcp_stream.py - reassemble and check NVMe/TCP PDUs from a byte stream.
Synthetic teaching tool: builds its own stream, splits it into arbitrary TCP
segments, then parses it back the way a receiver must."""
import struct, random

# CRC32C (Castagnoli), reflected polynomial 0x82F63B78, as used by NVMe/TCP digests
_T = []
for i in range(256):
    c = i
    for _ in range(8):
        c = (c >> 1) ^ 0x82F63B78 if c & 1 else c >> 1
    _T.append(c)

def crc32c(data, crc=0):
    crc ^= 0xFFFFFFFF
    for b in data:
        crc = _T[(crc ^ b) & 0xFF] ^ (crc >> 8)
    return crc ^ 0xFFFFFFFF

assert crc32c(b"123456789") == 0xE3069283        # standard CRC32C check value

NAMES = {0x00: "ICReq", 0x01: "ICResp", 0x02: "H2CTermReq", 0x03: "C2HTermReq",
         0x04: "CapsuleCmd", 0x05: "CapsuleResp", 0x06: "H2CData", 0x07: "C2HData", 0x09: "R2T"}
HDGSTF, DDGSTF, LAST_PDU, SUCCESS = 0x01, 0x02, 0x04, 0x08

def pdu(ptype, flags, psh, data=b"", hdgst=False, ddgst=False):
    """Build one PDU: 8-byte common header + PDU-specific header [+HDGST] [+DATA] [+DDGST]."""
    hlen = 8 + len(psh)
    flags |= (HDGSTF if hdgst else 0) | (DDGSTF if ddgst and data else 0)
    pdo = (hlen + (4 if hdgst else 0)) if data else 0
    plen = hlen + (4 if hdgst else 0) + len(data) + (4 if ddgst and data else 0)
    ch = struct.pack("<BBBBI", ptype, flags, hlen, pdo, plen)
    out = ch + psh
    if hdgst:
        out += struct.pack("<I", crc32c(out))
    out += data
    if ddgst and data:
        out += struct.pack("<I", crc32c(data))
    return out

def c2h_data(cccid, datao, data, last=True, **kw):
    psh = struct.pack("<HHII4x", cccid, 0, datao, len(data))
    return pdu(0x07, LAST_PDU if last else 0, psh, data, **kw)

def capsule_resp(cid, status=0, **kw):
    cqe = struct.pack("<IIHHHH", 0, 0, 0, 1, cid, status << 1)   # DW0, DW1, SQHD, SQID, CID, P+Status
    return pdu(0x05, 0, cqe, **kw)

class Receiver:
    def __init__(self, hdgst, ddgst):
        self.buf, self.hdgst, self.ddgst = bytearray(), hdgst, ddgst

    def feed(self, segment):
        self.buf += segment
        while len(self.buf) >= 8:
            ptype, flags, hlen, pdo, plen = struct.unpack_from("<BBBBI", self.buf, 0)
            if len(self.buf) < plen:
                return                                   # wait for more bytes: PDUs span segments
            raw, self.buf = bytes(self.buf[:plen]), self.buf[plen:]
            self.check(ptype, flags, hlen, pdo, plen, raw)

    def check(self, ptype, flags, hlen, pdo, plen, raw):
        name = NAMES.get(ptype, f"unknown {ptype:02X}h")
        verdict = "ok"
        if self.hdgst:
            (got,) = struct.unpack_from("<I", raw, hlen)
            if got != crc32c(raw[:hlen]):
                verdict = "HEADER DIGEST ERROR -> fatal: terminate the connection (host sends H2CTermReq)"
        if verdict == "ok" and pdo and self.ddgst:
            data = raw[pdo:plen - 4]
            (got,) = struct.unpack_from("<I", raw, plen - 4)
            if got != crc32c(data):
                verdict = "DATA DIGEST ERROR -> fail this command; framing still intact"
        info = ""
        if ptype in (0x06, 0x07):
            cccid, _, datao, datal = struct.unpack_from("<HHII", raw, 8)
            info = f"CCCID 0x{cccid:04X} DATAO {datao} DATAL {datal}" + (" LAST_PDU" if flags & LAST_PDU else "")
        elif ptype == 0x05:
            cid, sf = struct.unpack_from("<HH", raw, 8 + 12)
            info = f"CID 0x{cid:04X} status 0x{sf >> 1:04X}"
        print(f"  {name:<11} hlen={hlen:<3} pdo={pdo:<3} plen={plen:<5} {info}  [{verdict}]")

if __name__ == "__main__":
    random.seed(7)
    data = bytes(range(256)) * 16                                     # 4 KiB of read data
    stream = c2h_data(0x0042, 0, data, hdgst=True, ddgst=True) + capsule_resp(0x0042, hdgst=True, ddgst=True)

    def deliver(stream, title):
        print(title)
        rx, pos = Receiver(hdgst=True, ddgst=True), 0
        while pos < len(stream):                                     # random segment sizes, like TCP
            n = random.randint(1, 1448)
            rx.feed(stream[pos:pos + n]); pos += n

    deliver(stream, "Clean stream (digests on), random TCP segmentation:")
    bad = bytearray(stream); bad[24 + 4 + 1000] ^= 0x10             # flip one bit in the data
    deliver(bytes(bad), "Same stream with one data bit flipped in transit:")
    bad = bytearray(stream); bad[12] ^= 0x01                         # flip a bit in DATAO
    deliver(bytes(bad), "Same stream with one header bit flipped in transit:")

What to notice

  • The receiver never assumes segment boundaries. It waits until PLEN bytes are buffered.
  • A flipped data bit is caught by the data digest. The framing is still intact, so the following CapsuleResp parses fine. The host would fail this command with a transport error status and keep the connection.
  • A flipped header bit changes DATAO from 0 to 1. The header digest catches it, and the only safe reaction is to terminate the connection. Without a header digest, the receiver would silently place data one byte off.

Worked example

Problem. On the lab network (25 Gb/s Ethernet, MTU 1,500, TCP timestamps on), what fraction of link bandwidth carries NVMe data for 128 KiB reads with digests on? And what is the minimum time just to serialize one such read onto the wire?

Step 1: bytes per read on the wire

The read produces one C2HData PDU of 24 + 4 (HDGST) + 131,072 + 4 (DDGST) = 131,104 bytes (assuming the target sends it as one PDU), plus a CapsuleResp of 28 bytes. Total NVMe/TCP stream bytes: 131,132.

Segments: ⌈131,132 / 1,448⌉ = 91. Per-segment overhead on the wire: 66 bytes of headers + 24 bytes of Ethernet preamble, start delimiter, FCS and inter-frame gap = 90 bytes.

E = D / (S + N × O)

E = 131,072 / (131,132 + 91 × 90) = 131,072 / 139,322 ≈ 94.1%. With jumbo frames (8,948 bytes of payload per segment, 15 segments): 131,072 / (131,132 + 1,350) ≈ 98.9%. The NVMe/TCP framing itself costs under 0.05%. The per-packet overhead is what matters.

Step 2: serialization time

139,322 bytes × 8 = 1,114,576 bits. At 25 × 109 b/s that is ≈ 44.6 µs. A Lab SSD read of 128 KiB takes tens of µs of NAND time plus about 8 µs of PCIe Gen4 x4 transfer. So for large reads on 25 GbE, wire serialization is comparable to media time. That is why 100 GbE and multiple connections matter for throughput.

25 Gb/s × 0.941 ≈ 23.5 Gb/s ≈ 2.94 GB/s of NVMe data, at most, for one port, before any CPU limits. The Lab SSD at Gen4 x4 can deliver around 7 GB/s locally, so one 25 GbE port cannot expose its full sequential bandwidth. Derived

Senior engineer insight

On modern networks, NVMe/TCP's protocol overhead is trivial. The 24-byte headers are noise next to 1,448-byte segments. What costs time is per-I/O CPU work on both ends (system calls, copies, digests, interrupts, context switches) and queueing: head-of-line blocking within a connection, and contention when several queues share a CPU. Senior engineers profile CPU per I/O and latency per connection before touching network settings.

More I/O queues mean more TCP connections. That improves parallelism and reduces head-of-line blocking, but costs target memory (buffers per queue entry × depth × queues) and connection-setup time on reconnect. A host with 64 CPUs connecting to 20 targets with 64 queues each holds 1,280+ connections, and reconnect storms after a switch failure become a real operational risk.

Production may run without digests for CPU reasons. Test and validation environments should run with them, because they turn silent corruption into a loud, attributable error. The bugs they catch, such as NIC offload defects, memory corruption and middlebox interference, are exactly the ones that otherwise take months to find.

Solution
  1. Two connections: admin (QID 0) and one I/O queue (QID 1). The admin Connect is on the first connection opened. If you see extra short-lived connections, check whether your nvme-cli version probed a discovery controller first.
  2. Typically Property Get CAP (00h), Property Get VS (08h), Property Set CC (14h) with EN = 1, then Property Get CSTS (1Ch) until RDY = 1. At disconnect, Property Set CC for shutdown, then Property Get CSTS. Order and repetition are implementation-dependent.
  3. On typical nvmet configurations, 4 KiB fits in-capsule. You will see a CapsuleCmd whose PLEN is 72 + 4096 = 4168 and SGL identifier 01h. If not, your target advertises a smaller in-capsule size.
  4. Usually one R2T for the full 128 KiB (or several, if the target limits R2TL), and as many H2CData PDUs as needed to respect MAXH2CDATA. Count them and divide 131,072 by the observed DATAL.
  5. Loopback has a large MTU and no NIC segmentation, so each PDU is usually one frame.

What a senior engineer notices

The time between CapsuleCmd and CapsuleResp on loopback is almost all software: two TCP stacks, nvmet, and file I/O on the page cache. It sets a floor for this machine's NVMe/TCP software cost. Real networks add serialization and propagation on top of it, but never subtract from it.

Failure variants

  • nvme connect reports that it failed to write to /dev/nvme-fabrics: the nvme-tcp module is not loaded, or the target is not listening. Check ss -ltn for port 4420.
  • No new block device appears: the namespace is not enabled, or the backing path is wrong. Check dmesg for nvmet messages.
  • Wireshark shows plain TCP: you captured on the wrong interface or the port differs. Use Decode As.

Extension

Add tc qdisc add dev lo root netem delay 200us loss 0.5% (Caution: affects all loopback traffic in the VM), repeat the read workload with fio, and observe retransmissions and head-of-line blocking in the capture. Remove it with tc qdisc del dev lo root.

Exercises

  1. Write out, byte by byte, the common header of a CapsuleResp PDU with header digest on and data digest negotiated.
  2. A C2HData PDU has HLEN 24, PDO 32, PLEN 4132, and both digest flags set. Is it consistent? If so, what is HPDA?
  3. Explain why a data digest error fails one command while a header digest error kills the connection.
  4. A host's ICReq sets MAXR2T = 3. What does that permit the controller to do?
  5. Design a validation test that proves a target honours MAXH2CDATA.
  6. Explain the difference between port 8009 and port 4420 to a new team member.
Answers
  1. Bytes 05 01 18 00 1C 00 00 00: type 05h, FLAGS 01h (HDGSTF only, since a CapsuleResp carries no data and so no DDGST), HLEN 24, PDO 0, PLEN 28 (24 + 4).
  2. 24 header + 4 HDGST = 28, padded to 32, so PDO = 32 means data aligned to 32 bytes. HPDA is 0's based in 4-byte units: 32 / 4 − 1 = 7. Data = 4132 − 32 − 4 (DDGST) = 4096 bytes. Consistent.
  3. A header digest error means fields such as PLEN, DATAO and CCCID cannot be trusted, so the receiver cannot find the next PDU boundary safely. A data digest error leaves framing intact. Only the data of one command is bad.
  4. MAXR2T is 0's based, so 3 means up to 4 R2Ts may be outstanding for a single command.
  5. Connect with a known MAXH2CDATA from ICResp. Issue large writes and verify (from the capture or target trace) that every H2CData PDU has DATAL ≤ MAXH2CDATA. Then use a custom initiator to send an oversized H2CData and expect a C2HTermReq for a data transfer limit violation.
  6. 8009 is where the discovery controller usually listens. You fetch the Discovery Log Page there to learn which subsystems exist and where. 4420 is where I/O controllers usually listen. You connect there to read and write namespaces. Both are conventions that discovery entries can override.

Quiz

  1. What is the size of the NVMe/TCP common header?

    • 4 bytes
    • 8 bytes
    • 24 bytes
    • 72 bytes
    Answer and reasoning

    8 bytes: PDU-Type, FLAGS, HLEN, PDO (one byte each) and PLEN (4 bytes). 24 and 72 are full HLENs for some PDU types.

  2. Which PDU carries read data?

    • H2CData
    • R2T
    • C2HData
    • CapsuleResp
    Answer and reasoning

    Controller-to-host data PDU. H2CData carries write data. R2T requests write data.

  3. When is R2T used?

    • For host-to-controller data not sent in-capsule
    • For every read
    • Before every command
    • Only on the admin queue
    Answer and reasoning

    The controller solicits write data it did not receive in-capsule.

  4. A header digest mismatch is detected. What is the correct reaction?

    • Ignore it, TCP already checksummed the data
    • Fail the command and continue
    • Request retransmission with a new R2T
    • Treat it as fatal: send a TermReq and close the connection
    Answer and reasoning

    Framing fields are untrustworthy, so the stream cannot be parsed safely beyond this point.

  5. What does MAXH2CDATA limit?

    • The size of in-capsule data
    • The data length of a single H2CData PDU
    • The number of outstanding R2Ts
    • The size of C2HData PDUs
    Answer and reasoning

    The controller advertises it in ICResp. In-capsule size comes from IOCCSZ, and outstanding R2Ts from MAXR2T.

  6. Which algorithm do NVMe/TCP digests use?

    • CRC-16
    • Adler-32
    • CRC32C
    • SHA-256
    Answer and reasoning

    CRC32C (Castagnoli), the same CRC used by iSCSI digests. TLS provides cryptographic integrity if needed.

  7. How many TCP connections does a host with 8 I/O queues to one controller use?

    • 1
    • 8
    • 9
    • 16
    Answer and reasoning

    One per queue pair: 8 I/O + 1 admin.

  8. A capture shows a lost segment and a 200 µs fast retransmission before a CapsuleResp. Where is the problem?

    • Network/TCP layer: NVMe only sees latency
    • Target firmware
    • NVMe/TCP framing
    • The host's Connect parameters
    Answer and reasoning

    TCP recovered the loss transparently. Head-of-line blocking delayed the response.

  9. Open: why can a target drop the CapsuleResp for a successful read, and what must the host still handle?

    Model answer

    The SUCCESS flag on the last C2HData PDU can signal successful completion, which saves a PDU. The TCP Transport specification limits when this may be used (for example around SQ flow control). The host must still accept a normal CapsuleResp, and must handle errors, which always need a CapsuleResp to carry status.

  10. Open: what does TLS change for a debugging engineer, and how would you prepare?

    Model answer

    All NVMe/TCP PDUs become opaque Application Data. Prepare by enabling session key export in labs (so Wireshark can decrypt), relying on host and target tracing in production, keeping TCP-level visibility (retransmissions and timing are still visible), and logging TLS handshake outcomes from tlshd.

Interview questions

  1. Beginner: Why does NVMe/TCP need PDUs when TCP already delivers bytes reliably?

    Model answer

    TCP is a byte stream with no message boundaries. NVMe needs discrete commands, data blocks and completions. PDUs give each message a type and length so the receiver can find boundaries and parse the content.

  2. Beginner: Walk me through a 4 KiB read over NVMe/TCP.

    Model answer

    Host sends CapsuleCmd (SQE with Read, SGL Transport Data Block, 4096 bytes). Target reads the data and sends a C2HData PDU (CCCID, DATAO 0, DATAL 4096, LAST_PDU), then a CapsuleResp with the CQE. The host copies the data into the request buffer and completes the request on the CapsuleResp.

  3. Intermediate: What do ICReq and ICResp negotiate?

    Model answer

    PDU format version, data alignment in each direction (HPDA/CPDA), header and data digest enablement, the host's maximum outstanding R2Ts (MAXR2T) and the controller's maximum H2CData size (MAXH2CDATA). They happen once per connection, before Connect.

  4. Intermediate: How does in-capsule data change write latency?

    Model answer

    It removes the R2T round trip. Writes that fit in IOCCSZ × 16 − 64 bytes complete in one round trip. Larger writes need CapsuleCmd → R2T → H2CData → CapsuleResp, which adds at least one RTT plus any target buffer-allocation delay.

  5. Advanced: A customer sees periodic 10 ms latency spikes on NVMe/TCP reads. How do you investigate?

    Model answer

    Capture at both ends and correlate. Check for TCP retransmissions (an RTO-scale gap suggests tail loss with no dup-ACKs), zero-window events (receiver stalls), and target-side backend latency (target trace or iostat). Check CPU scheduling: softirq starvation and interrupt coalescing. Check network: switch buffer drops and microbursts. Separate per-connection effects (head-of-line) from per-target ones by checking whether all queues spike together.

  6. Advanced: Compare NVMe/TCP digests with TLS.

    Model answer

    Digests are CRC32C: they detect accidental corruption but not deliberate tampering, and provide no confidentiality. TLS 1.3 provides confidentiality and cryptographic integrity and authenticates peers via PSKs. With TLS, digests are largely redundant for integrity, though the specification governs whether both may be negotiated. TLS also hides the PDUs from passive capture.

  7. Senior: How would you design an NVMe/TCP target for predictable write latency under load?

    Model answer

    Advertise an in-capsule size matched to the dominant small-write size. Pre-allocate per-queue buffer pools so R2T issuance never waits on allocation. Bound per-connection outstanding R2T bytes, steer each connection to a dedicated CPU, use zero-copy or DDP where available, apply admission control so backend saturation surfaces as queueing rather than R2T starvation, and instrument CapsuleCmd→R2T and R2T→data-complete latencies.

  8. Senior: When would you choose NVMe/TCP over NVMe/RDMA?

    Model answer

    When reach and operational simplicity matter: routed IP networks, mixed NICs, cloud and VM environments, no lossless Ethernet. Also when CPU headroom exists, and when tooling and team skills favour TCP. RDMA is the choice when the lowest latency and CPU efficiency justify the network engineering and RNIC requirements.

Teach-back challenge

  • To a child: explain why the marbles need a "label" at the start of every parcel.
  • To a junior engineer: explain R2T and why reads do not need it.
  • To a senior engineer: argue for or against enabling data digests in production for a specific workload.
Model explanations

Child: "The pipe gives you marbles one after another, but it does not tell you where one parcel stops. The label says how many marbles belong to this parcel, so you know when the next one starts."

Junior: "For a write too big for the command capsule, the target says 'I have room now, send bytes X to Y' with an R2T, and the host sends exactly those bytes in H2CData PDUs. For a read, the host already set aside room for the data when it sent the command, so the target just sends C2HData without asking."

Senior: "For a database on a routed network crossing middleboxes and NICs with aggressive offloads, enable data digests: CRC32C costs a few percent of CPU with hardware instructions, and it turns silent corruption into attributable errors. For a single-hop, TLS-protected deployment where TLS already supplies integrity, digests add little."

Chapter summary

  • NVMe/TCP frames capsules and data into self-delimiting PDUs, each starting with an 8-byte common header, on one TCP connection per queue pair.
  • ICReq/ICResp negotiate format version, alignment, digests, MAXR2T and MAXH2CDATA before Connect.
  • Read: CapsuleCmd → C2HData… → CapsuleResp. Write: in-capsule (one round trip) or CapsuleCmd → R2T → H2CData… → CapsuleResp.
  • Header digest errors are fatal to the connection, and data digest errors fail one command. TermReq PDUs report fatal errors.
  • TLS 1.3 with PSKs secures NVMe/TCP and hides PDUs from captures.
  • Performance is dominated by CPU cost, copies, segmentation and head-of-line blocking, not by PDU overhead.

Do not move on until you can:

  • decode any NVMe/TCP common header from hex
  • list all PDU types with direction and purpose
  • draw the read, small-write and large-write sequences
  • explain what each digest covers and the consequence of each failing
  • reassemble a PDU from TCP segments by PLEN
  • classify a capture anomaly as TCP, NVMe/TCP framing or NVMe status
  • set up, capture and tear down a loopback nvmet target safely
