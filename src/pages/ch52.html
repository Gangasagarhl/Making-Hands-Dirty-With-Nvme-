Every Memory Read an NVMe controller issues — for a submission queue entry, a PRP list, or the data of a Write command — comes back as one or more completions. This advanced chapter teaches the rules completers must follow when they split a read, the Read Completion Boundary, the exact Byte Count and Lower Address arithmetic (with worked examples you can check in code), the completion timeout mechanism and its ranges, and what happens to completions that arrive when nobody is waiting for them.

Why this chapter exists

Completions are half of all non-posted traffic and most of the bytes for NVMe Write commands. Analyzer users see dozens of Completion with Data (CplD) packets for one request and must decide whether the sequence is legal. Firmware engineers must reassemble those packets correctly, whatever order and size the Root Complex chooses. Validation engineers must know which fields a requester is entitled to check. And when a completion never arrives, the Completion Timeout mechanism decides how long a device waits — a value that ranges from microseconds to over a minute and is often left at a default nobody chose.

Getting completions wrong produces data corruption inside a single transfer, malformed-packet errors that take a link down, and "Unexpected Completion" and "Completion Timeout" errors in Advanced Error Reporting (AER) that are easy to misattribute.

Learning objectives

  • Decode every field of a completion header and state its owner and purpose.
  • Apply the completion-splitting rules: Max Payload Size (MPS), Read Completion Boundary (RCB), address order.
  • Compute Byte Count and Lower Address for every completion of a read, including unaligned and single-byte reads.
  • Validate a completion sequence as a requester would, and spot a broken one in a trace.
  • Explain the Completion Timeout mechanism, the timeout range encodings, and the Completion Timeout Disable control, and choose values with reasons.
  • Explain Unexpected Completions: causes, how they are logged, and how to tell a late completion from a misrouted one.
  • Relate completion behaviour to NVMe performance and NVMe error status.

The story

The librarian orders 200 pages of photocopies from the copy room. The copy room is allowed to send them back in several envelopes, but with rules. No envelope may be heavier than the mail carrier can carry. Every envelope except the last must end at the end of a "chapter" (a fixed number of pages). The envelopes must arrive in page order. And every envelope has two numbers on it: "how many pages are still coming, counting this envelope" and "which page on the shelf the first page in this envelope goes to". The librarian uses the numbers to know when she has everything — and if an envelope shows up for an order she has already given up on, she knows something has gone wrong.

A warehouse fulfilling a large order ships it as multiple parcels. Each parcel is limited by the courier's weight limit (MPS). For efficient pallet handling, every parcel but the last must end at a pallet boundary (RCB). Each label says "items remaining including this parcel" (Byte Count) and "shelf position of the first item" (Lower Address). The customer cancels an order if nothing arrives within a deadline (Completion Timeout); a parcel that arrives after cancellation, or carries someone else's order number, is an "unexpected delivery" (Unexpected Completion).

Parcels can arrive in any order; completions for one request may not (they must stay in address order). A warehouse label carries a full shelf address; a completion carries only the low 7 bits of the address — the requester must remember the rest from its own request, matched by Tag. And a customer can phone to ask; a PCIe requester has no way to ask about a missing completion — it can only time out.

Beginner explanation

When a device asks for data with a Memory Read (MRd), the answer comes back in one or more completions with data. Each completion carries a 3-DWORD header plus a payload.

  • Requester ID and Tag say which request this completion belongs to.
  • Completer ID says who answered.
  • Completion Status says whether it worked (Successful Completion) or not (Unsupported Request, Completer Abort, or a retry status for configuration requests).
  • Byte Count says how many bytes are still needed to finish the request, including this completion's bytes.
  • Lower Address gives the low 7 bits of the byte address of the first byte in this completion.

A completer may split one read into several completions, but each must fit within the maximum payload, all but the last must end at a Read Completion Boundary (64 or 128 bytes), and they must arrive in address order. The requester knows it has everything when a completion's Byte Count equals the bytes it carries.

If a requester gets no answer for too long, it declares a Completion Timeout. If it gets an answer it was not waiting for, it records an Unexpected Completion.

A completion with a status other than SC terminates the request: no further completions for it will arrive. For a memory read, the requester must treat the whole request as failed even if some data already arrived in earlier SC completions.

Who completes what

  • Memory Read: one or more CplD (or a single Cpl with an error status).
  • I/O and Configuration Read: exactly one CplD with one DWORD (or Cpl with error).
  • I/O and Configuration Write: exactly one Cpl without data.
  • AtomicOps: one CplD carrying the original value.
  • Posted requests: no completion, ever.

Splitting rules

A completer may return a memory read in a single completion or split it. The rules (paraphrased from the PCI Express Base Specification's completion rules; confirm the full set in your revision):

  1. MPS: no completion's payload may exceed the Max Payload Size configured for the completer's link direction (from the Lab SSD's point of view, the host's completions to it are limited to MPS = 256 bytes).
  2. RCB: when a request is split, each completion except the last must end on a naturally aligned RCB boundary. A completion may contain several RCB blocks.
  3. Address order: completions for one request are returned in increasing address order (ordering rule D5b).
  4. Exactness: together the completions return exactly the requested bytes (with whole DWORDs, padding disabled bytes at the start and end).
  5. One completion is always legal if the whole request fits within MPS.

The Read Completion Boundary is 64 or 128 bytes. A Root Port reports its RCB in its Link Control register (RCB field, read-only for Root Ports); software writes the same value into each endpoint's Link Control RCB field so the endpoint knows what to expect. An endpoint acting as a completer (for peer-to-peer or for host reads of its BAR) uses its own RCB setting. Switches do not split or merge completions.

Why have an RCB at all? A Root Complex fetches from memory in cache-line-sized chunks. Allowing it to return each chunk as soon as it is available, without waiting to build a full MPS-sized completion, lowers latency. The RCB rule constrains where splits may occur so requesters can size their reassembly buffers and checks predictably.

Byte Count arithmetic

For memory read completions, Byte Count is the number of bytes still to be returned, including the bytes in this completion. For the first completion it equals the total number of bytes requested, computed from Length and the byte enables.

Special cases, which you should confirm against the Byte Count table in the specification:

  • Length = 1: only First DW BE is used (Last DW BE must be 0000b). Byte Count is the span from the lowest to the highest enabled byte; for non-contiguous enables such as 1001b, the span is 4.
  • Zero-length read (Length = 1, First DW BE = 0000b): Byte Count is 1, and the completion carries one DWORD whose contents the requester ignores. Zero-length reads are used to flush posted writes (rule B2a) without reading data.
  • Non-memory completions (I/O and configuration): Byte Count is 4 and Lower Address is 0 Uncertain — check the completion rules of your revision, which also define the values for AtomicOp completions.
  • Error completions for memory reads: check the specification for the Byte Count value required in UR/CA completions; requesters should not depend on it.

Lower Address arithmetic

For memory read completions, Lower Address is bits 6:0 of the byte address of the first enabled byte of data returned in this completion.

  • First completion: (request address bits 6:2) combined with the byte offset implied by First DW BE (00b for xxx1b, 01b for xx10b, 10b for x100b, 11b for 1000b; 00b for 0000b).
  • Later completions: they start on an RCB boundary, so their Lower Address is a multiple of the RCB within 7 bits — with RCB = 64, either 00h or 40h; with RCB = 128, always 00h.

Because Lower Address has only 7 bits, the requester reconstructs the full address from its own record of the request (matched by Tag) plus the running Byte Count. Lower Address is a check and a position hint, not a full address.

Requester-side checks

A requester matches each completion to an outstanding request by Requester ID and Tag (with 10-bit tags, all 10 bits). It may check, and in some cases must check (see the specification's list of completion-receive rules, many of which are "permitted" rather than "required"):

  • the Tag is outstanding — otherwise Unexpected Completion;
  • the payload does not exceed MPS — otherwise Malformed TLP;
  • Byte Count and Lower Address are consistent with the request and with previous completions;
  • the completion does not return more data than requested;
  • the Completion Status is a defined value.

Which consistency checks a requester performs, and which error it reports when a check fails, is partly implementation-dependent. Two devices can react differently to the same malformed sequence: one logs Malformed TLP, the other Unexpected Completion, a third silently corrupts. Know your device's documented behaviour.

Completion Timeout

A requester that issues a non-posted request starts a timer. If the request has not been completed — all completions received, or an error completion received — when the timer expires, the requester reports a Completion Timeout (an uncorrectable error, non-fatal by default severity, logged in AER's Uncorrectable Error Status) and abandons the request. A partially completed read still times out.

Control lives in the PCI Express Capability:

  • Device Capabilities 2: Completion Timeout Ranges Supported (which ranges A–D the function implements) and Completion Timeout Disable Supported.
  • Device Control 2: Completion Timeout Value (a 4-bit encoding selecting a range) and Completion Timeout Disable.

A window means the timer must not fire before the lower bound and must fire before the upper bound. The specification also recommends that the default not expire in less than about 10 ms; check the exact wording.

Choosing a value for an NVMe controller's DMA reads: host memory reads normally complete in a microsecond or two, but can take far longer under IOMMU page-table walks, memory contention, virtualization (nested translation), remote NUMA memory, or a Root Complex recovering from errors. A timeout in the low milliseconds risks spurious timeouts under stress; a timeout of tens of seconds means a dead path takes tens of seconds to detect — longer than NVMe's own command timeouts in some stacks. Platform firmware, not the NVMe driver, usually programs this.

The Root Port's timeout governs CPU reads of the SSD's BAR (for example, reading CSTS). If the SSD is gone and the Root Port waits for the full timeout, the CPU core stalls for that long on a single load; some platforms convert this into a machine check. That is one reason surprise-removal handling prefers to detect link-down before touching MMIO.

Completion Timeout Disable exists for functions that cannot tolerate abandoning requests. Disabling the timeout means a lost completion waits forever: the request's tag is never reused and the function may hang. Use only with a strong reason and an independent watchdog.

Unexpected Completions

A completion that matches no outstanding request at the receiver is an Unexpected Completion, logged in AER's Uncorrectable Error Status (default severity non-fatal; in some roles it is handled as an advisory non-fatal error, see the role-based error reporting rules). Causes, from most to least common in practice:

  1. Late completion after a timeout: the requester gave up, freed the tag, and the completion arrives anyway.
  2. Completion after a reset: FLR or a controller reset discarded outstanding requests; completions still in flight arrive (Ch 49).
  3. Misrouting: wrong Requester ID copied by a buggy completer, or bus numbers changed (re-enumeration) while requests were outstanding.
  4. Duplicate completions: completer bug sends a completion twice, or splits incorrectly.
  5. Tag aliasing: requester reuses a tag before all completions of the previous use arrived, or mixes 8-bit and 10-bit tag handling between ends.

Telling them apart: a late completion carries a tag that was outstanding recently (correlate with a Completion Timeout logged just before); a misrouted completion carries a Requester ID that is not the receiver's; a duplicate repeats an earlier completion exactly.

The ladder for completion splitting

The copy room sends 200 pages in envelopes; each envelope says how many pages are still coming and where its first page goes; envelopes end at chapter boundaries and arrive in page order.

A memory read may be answered by several CplDs; each ≤ MPS; all but the last end on an RCB boundary; address order; Byte Count counts down; Lower Address gives the start offset.

The Root Complex reads host memory in cache-line chunks and returns completions as chunks become ready; the SSD's completion reassembly logic places payloads using its tag table entry plus Byte Count and Lower Address.

PCI Express Base Specification: completion rules (splitting, RCB, Byte Count and Lower Address definitions), ordering rule for same-request completions, Completion Timeout mechanism, Unexpected Completion error.

One MRd from the SSD (Requester ID 0x0100) followed by N CplDs from the Root Complex carrying the same Requester ID and Tag, decreasing Byte Count and RCB-aligned Lower Addresses.

An analyzer groups the CplDs under the MRd by tag; check MPS, RCB alignment, Byte Count sequence, address order and the final Byte Count ≤ payload.

A Byte Count that does not decrease by the delivered bytes, a Lower Address that does not match, or a payload above MPS is the first abnormal event; identify the completer (Completer ID) and whether the requester flagged it.

The sixteen questions, applied to Completion Timeout

1. What is it?
A requester-side timer per outstanding non-posted request, and the error raised when it expires.
2. Why was it created?
Non-posted requests otherwise wait forever if a completion is lost (link failure, completer bug, misrouting).
3. What problem does it solve?
Recovering tags and buffers and surfacing failures instead of hanging.
4. What existed before it?
Conventional PCI used retries and master-abort/target-abort on the bus with bus-level timers; PCI-X added split transactions with split completion timeouts.
5. Why is the current design better?
Configurable ranges, optional disable, standardized AER reporting.
6. Who creates it?
The requester's transaction layer.
7. Who consumes it?
The requester's error handling, AER, the OS error-recovery path.
8. Where does it live?
Device Capabilities 2 / Device Control 2 in the requester's PCI Express Capability; AER registers.
9. What memory/registers are involved?
The tag table, Device Control 2, Uncorrectable Error Status/Mask/Severity, the header log.
10. What happens before it?
A non-posted request is sent and its completions do not (fully) arrive.
11. What happens after it?
The request is abandoned; error logged and signalled; for an NVMe controller, the command that needed the data fails (e.g. a data transfer error status) or the controller enters a fatal state, depending on design.
12. What happens if it is wrong?
Too short: spurious failures under load. Too long: slow detection, long CPU stalls. Disabled: hangs.
13. What does the protocol analyzer show?
An MRd with no matching CplD (or partial CplDs) within the window; sometimes a later CplD that becomes an Unexpected Completion.
14. What does Linux show?
AER messages naming Completion Timeout for the device or port, with the TLP header log if supported; lspci -vv DevCap2/DevCtl2 timeout settings.
15. What would a validation engineer test?
Timer accuracy per encoding; behaviour with dropped completions (via an exerciser); recovery and tag reuse; interaction with resets.
16. What would a senior engineer suspect when it fails?
Host memory latency spikes (IOMMU, virtualization), a hung completer (Root Complex error recovery), link problems causing lost TLPs beyond replay, or an address that should have produced UR but was silently dropped.
