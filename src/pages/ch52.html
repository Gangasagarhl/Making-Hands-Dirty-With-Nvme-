Every Memory Read an NVMe controller issues — for a submission queue entry, a PRP list, or the data of a Write command — comes back as one or more completions. This advanced chapter teaches the rules completers must follow when they split a read, the Read Completion Boundary, the exact Byte Count and Lower Address arithmetic (with worked examples you can check in code), the completion timeout mechanism and its ranges, and what happens to completions that arrive when nobody is waiting for them.

Why this chapter exists

Completions are half of all non-posted traffic and most of the bytes for NVMe Write commands. Analyzer users see dozens of Completion with Data (CplD) packets for one request and must decide whether the sequence is legal. Firmware engineers must reassemble those packets correctly, whatever order and size the Root Complex chooses. Validation engineers must know which fields a requester is entitled to check. And when a completion never arrives, the Completion Timeout mechanism decides how long a device waits — a value that ranges from microseconds to over a minute and is often left at a default nobody chose.

Getting completions wrong produces data corruption inside a single transfer, malformed-packet errors that take a link down, and "Unexpected Completion" and "Completion Timeout" errors in Advanced Error Reporting (AER) that are easy to misattribute.

Learning objectives

  • Decode every field of a completion header and state its owner and purpose.
  • Apply the completion-splitting rules: Max Payload Size (MPS), Read Completion Boundary (RCB), address order.
  • Compute Byte Count and Lower Address for every completion of a read, including unaligned and single-byte reads.
  • Validate a completion sequence as a requester would, and spot a broken one in a trace.
  • Explain the Completion Timeout mechanism, the timeout range encodings, and the Completion Timeout Disable control, and choose values with reasons.
  • Explain Unexpected Completions: causes, how they are logged, and how to tell a late completion from a misrouted one.
  • Relate completion behaviour to NVMe performance and NVMe error status.

The story

The librarian orders 200 pages of photocopies from the copy room. The copy room is allowed to send them back in several envelopes, but with rules. No envelope may be heavier than the mail carrier can carry. Every envelope except the last must end at the end of a "chapter" (a fixed number of pages). The envelopes must arrive in page order. And every envelope has two numbers on it: "how many pages are still coming, counting this envelope" and "which page on the shelf the first page in this envelope goes to". The librarian uses the numbers to know when she has everything — and if an envelope shows up for an order she has already given up on, she knows something has gone wrong.

A warehouse fulfilling a large order ships it as multiple parcels. Each parcel is limited by the courier's weight limit (MPS). For efficient pallet handling, every parcel but the last must end at a pallet boundary (RCB). Each label says "items remaining including this parcel" (Byte Count) and "shelf position of the first item" (Lower Address). The customer cancels an order if nothing arrives within a deadline (Completion Timeout); a parcel that arrives after cancellation, or carries someone else's order number, is an "unexpected delivery" (Unexpected Completion).

Parcels can arrive in any order; completions for one request may not (they must stay in address order). A warehouse label carries a full shelf address; a completion carries only the low 7 bits of the address — the requester must remember the rest from its own request, matched by Tag. And a customer can phone to ask; a PCIe requester has no way to ask about a missing completion — it can only time out.

Beginner explanation

When a device asks for data with a Memory Read (MRd), the answer comes back in one or more completions with data. Each completion carries a 3-DWORD header plus a payload.

  • Requester ID and Tag say which request this completion belongs to.
  • Completer ID says who answered.
  • Completion Status says whether it worked (Successful Completion) or not (Unsupported Request, Completer Abort, or a retry status for configuration requests).
  • Byte Count says how many bytes are still needed to finish the request, including this completion's bytes.
  • Lower Address gives the low 7 bits of the byte address of the first byte in this completion.

A completer may split one read into several completions, but each must fit within the maximum payload, all but the last must end at a Read Completion Boundary (64 or 128 bytes), and they must arrive in address order. The requester knows it has everything when a completion's Byte Count equals the bytes it carries.

If a requester gets no answer for too long, it declares a Completion Timeout. If it gets an answer it was not waiting for, it records an Unexpected Completion.

Who completes what

  • Memory Read: one or more CplD (or a single Cpl with an error status).
  • I/O and Configuration Read: exactly one CplD with one DWORD (or Cpl with error).
  • I/O and Configuration Write: exactly one Cpl without data.
  • AtomicOps: one CplD carrying the original value.
  • Posted requests: no completion, ever.

Splitting rules

A completer may return a memory read in a single completion or split it. The rules (paraphrased from the PCI Express Base Specification's completion rules; confirm the full set in your revision):

  1. MPS: no completion's payload may exceed the Max Payload Size configured for the completer's link direction (from the Lab SSD's point of view, the host's completions to it are limited to MPS = 256 bytes).
  2. RCB: when a request is split, each completion except the last must end on a naturally aligned RCB boundary. A completion may contain several RCB blocks.
  3. Address order: completions for one request are returned in increasing address order (ordering rule D5b).
  4. Exactness: together the completions return exactly the requested bytes (with whole DWORDs, padding disabled bytes at the start and end).
  5. One completion is always legal if the whole request fits within MPS.

The Read Completion Boundary is 64 or 128 bytes. A Root Port reports its RCB in its Link Control register (RCB field, read-only for Root Ports); software writes the same value into each endpoint's Link Control RCB field so the endpoint knows what to expect. An endpoint acting as a completer (for peer-to-peer or for host reads of its BAR) uses its own RCB setting. Switches do not split or merge completions.

Why have an RCB at all? A Root Complex fetches from memory in cache-line-sized chunks. Allowing it to return each chunk as soon as it is available, without waiting to build a full MPS-sized completion, lowers latency. The RCB rule constrains where splits may occur so requesters can size their reassembly buffers and checks predictably.

Byte Count arithmetic

For memory read completions, Byte Count is the number of bytes still to be returned, including the bytes in this completion. For the first completion it equals the total number of bytes requested, computed from Length and the byte enables.

Special cases, which you should confirm against the Byte Count table in the specification:

  • Length = 1: only First DW BE is used (Last DW BE must be 0000b). Byte Count is the span from the lowest to the highest enabled byte; for non-contiguous enables such as 1001b, the span is 4.
  • Zero-length read (Length = 1, First DW BE = 0000b): Byte Count is 1, and the completion carries one DWORD whose contents the requester ignores. Zero-length reads are used to flush posted writes (rule B2a) without reading data.
  • Non-memory completions (I/O and configuration): Byte Count is 4 and Lower Address is 0 Uncertain — check the completion rules of your revision, which also define the values for AtomicOp completions.
  • Error completions for memory reads: check the specification for the Byte Count value required in UR/CA completions; requesters should not depend on it.

Lower Address arithmetic

For memory read completions, Lower Address is bits 6:0 of the byte address of the first enabled byte of data returned in this completion.

  • First completion: (request address bits 6:2) combined with the byte offset implied by First DW BE (00b for xxx1b, 01b for xx10b, 10b for x100b, 11b for 1000b; 00b for 0000b).
  • Later completions: they start on an RCB boundary, so their Lower Address is a multiple of the RCB within 7 bits — with RCB = 64, either 00h or 40h; with RCB = 128, always 00h.

Because Lower Address has only 7 bits, the requester reconstructs the full address from its own record of the request (matched by Tag) plus the running Byte Count. Lower Address is a check and a position hint, not a full address.

Requester-side checks

A requester matches each completion to an outstanding request by Requester ID and Tag (with 10-bit tags, all 10 bits). It may check, and in some cases must check (see the specification's list of completion-receive rules, many of which are "permitted" rather than "required"):

  • the Tag is outstanding — otherwise Unexpected Completion;
  • the payload does not exceed MPS — otherwise Malformed TLP;
  • Byte Count and Lower Address are consistent with the request and with previous completions;
  • the completion does not return more data than requested;
  • the Completion Status is a defined value.

Which consistency checks a requester performs, and which error it reports when a check fails, is partly implementation-dependent. Two devices can react differently to the same malformed sequence: one logs Malformed TLP, the other Unexpected Completion, a third silently corrupts. Know your device's documented behaviour.

Completion Timeout

A requester that issues a non-posted request starts a timer. If the request has not been completed — all completions received, or an error completion received — when the timer expires, the requester reports a Completion Timeout (an uncorrectable error, non-fatal by default severity, logged in AER's Uncorrectable Error Status) and abandons the request. A partially completed read still times out.

Control lives in the PCI Express Capability:

  • Device Capabilities 2: Completion Timeout Ranges Supported (which ranges A–D the function implements) and Completion Timeout Disable Supported.
  • Device Control 2: Completion Timeout Value (a 4-bit encoding selecting a range) and Completion Timeout Disable.

A window means the timer must not fire before the lower bound and must fire before the upper bound. The specification also recommends that the default not expire in less than about 10 ms; check the exact wording.

Choosing a value for an NVMe controller's DMA reads: host memory reads normally complete in a microsecond or two, but can take far longer under IOMMU page-table walks, memory contention, virtualization (nested translation), remote NUMA memory, or a Root Complex recovering from errors. A timeout in the low milliseconds risks spurious timeouts under stress; a timeout of tens of seconds means a dead path takes tens of seconds to detect — longer than NVMe's own command timeouts in some stacks. Platform firmware, not the NVMe driver, usually programs this.

The Root Port's timeout governs CPU reads of the SSD's BAR (for example, reading CSTS). If the SSD is gone and the Root Port waits for the full timeout, the CPU core stalls for that long on a single load; some platforms convert this into a machine check. That is one reason surprise-removal handling prefers to detect link-down before touching MMIO.

Completion Timeout Disable exists for functions that cannot tolerate abandoning requests. Disabling the timeout means a lost completion waits forever: the request's tag is never reused and the function may hang. Use only with a strong reason and an independent watchdog.

Unexpected Completions

A completion that matches no outstanding request at the receiver is an Unexpected Completion, logged in AER's Uncorrectable Error Status (default severity non-fatal; in some roles it is handled as an advisory non-fatal error, see the role-based error reporting rules). Causes, from most to least common in practice:

  1. Late completion after a timeout: the requester gave up, freed the tag, and the completion arrives anyway.
  2. Completion after a reset: FLR or a controller reset discarded outstanding requests; completions still in flight arrive (Ch 49).
  3. Misrouting: wrong Requester ID copied by a buggy completer, or bus numbers changed (re-enumeration) while requests were outstanding.
  4. Duplicate completions: completer bug sends a completion twice, or splits incorrectly.
  5. Tag aliasing: requester reuses a tag before all completions of the previous use arrived, or mixes 8-bit and 10-bit tag handling between ends.

Telling them apart: a late completion carries a tag that was outstanding recently (correlate with a Completion Timeout logged just before); a misrouted completion carries a Requester ID that is not the receiver's; a duplicate repeats an earlier completion exactly.

The ladder for completion splitting

The copy room sends 200 pages in envelopes; each envelope says how many pages are still coming and where its first page goes; envelopes end at chapter boundaries and arrive in page order.

A memory read may be answered by several CplDs; each ≤ MPS; all but the last end on an RCB boundary; address order; Byte Count counts down; Lower Address gives the start offset.

The Root Complex reads host memory in cache-line chunks and returns completions as chunks become ready; the SSD's completion reassembly logic places payloads using its tag table entry plus Byte Count and Lower Address.

PCI Express Base Specification: completion rules (splitting, RCB, Byte Count and Lower Address definitions), ordering rule for same-request completions, Completion Timeout mechanism, Unexpected Completion error.

One MRd from the SSD (Requester ID 0x0100) followed by N CplDs from the Root Complex carrying the same Requester ID and Tag, decreasing Byte Count and RCB-aligned Lower Addresses.

An analyzer groups the CplDs under the MRd by tag; check MPS, RCB alignment, Byte Count sequence, address order and the final Byte Count ≤ payload.

A Byte Count that does not decrease by the delivered bytes, a Lower Address that does not match, or a payload above MPS is the first abnormal event; identify the completer (Completer ID) and whether the requester flagged it.

The sixteen questions, applied to Completion Timeout

1. What is it?
A requester-side timer per outstanding non-posted request, and the error raised when it expires.
2. Why was it created?
Non-posted requests otherwise wait forever if a completion is lost (link failure, completer bug, misrouting).
3. What problem does it solve?
Recovering tags and buffers and surfacing failures instead of hanging.
4. What existed before it?
Conventional PCI used retries and master-abort/target-abort on the bus with bus-level timers; PCI-X added split transactions with split completion timeouts.
5. Why is the current design better?
Configurable ranges, optional disable, standardized AER reporting.
6. Who creates it?
The requester's transaction layer.
7. Who consumes it?
The requester's error handling, AER, the OS error-recovery path.
8. Where does it live?
Device Capabilities 2 / Device Control 2 in the requester's PCI Express Capability; AER registers.
9. What memory/registers are involved?
The tag table, Device Control 2, Uncorrectable Error Status/Mask/Severity, the header log.
10. What happens before it?
A non-posted request is sent and its completions do not (fully) arrive.
11. What happens after it?
The request is abandoned; error logged and signalled; for an NVMe controller, the command that needed the data fails (e.g. a data transfer error status) or the controller enters a fatal state, depending on design.
12. What happens if it is wrong?
Too short: spurious failures under load. Too long: slow detection, long CPU stalls. Disabled: hangs.
13. What does the protocol analyzer show?
An MRd with no matching CplD (or partial CplDs) within the window; sometimes a later CplD that becomes an Unexpected Completion.
14. What does Linux show?
AER messages naming Completion Timeout for the device or port, with the TLP header log if supported; lspci -vv DevCap2/DevCtl2 timeout settings.
15. What would a validation engineer test?
Timer accuracy per encoding; behaviour with dropped completions (via an exerciser); recovery and tag reuse; interaction with resets.
16. What would a senior engineer suspect when it fails?
Host memory latency spikes (IOMMU, virtualization), a hung completer (Root Complex error recovery), link problems causing lost TLPs beyond replay, or an address that should have produced UR but was silently dropped.

Hardware view

  • Requester tag table: for each outstanding tag, the device stores the request's full address, length, byte enables, a destination buffer pointer, a running Byte Count, and a timer. Completion handling is a lookup on (Requester ID, Tag) and a write of the payload at (buffer + offset), where offset is derived from Lower Address and progress so far.
  • Reassembly buffers: because completions for different tags may arrive in any order (rule D5a), a device fetching write data must buffer out-of-order completions or issue only as many reads as it can buffer. This, together with tag count and MRRS, bounds read throughput (Chapter 13).
  • Completion credits: a requester must have buffer space for the completions it solicits; endpoints typically advertise infinite completion credits and therefore must only issue reads they can absorb (Chapter 53).
  • Root Complex completion generation: memory controllers return cache lines (commonly 64 bytes). Many Root Complexes return completions in RCB-sized or cache-line-sized pieces; others coalesce up to MPS. The choice is platform-specific and affects link efficiency.

Specification view

Documents: PCI Express Base Specification, Revision 6.x/7.0 — Completion Rules; Completion Handling Rules; Read Completion Boundary; Completion Timeout Mechanism; Unexpected Completion; Device Capabilities 2 and Device Control 2 registers; Link Control (RCB); Advanced Error Reporting. NVMe uses completions only through the transport; the NVMe over PCIe Transport Specification 1.4 and the NVMe Base 2.4 status definitions (data transfer errors) describe how a failed DMA surfaces to the host.

Completion header fields (Completer ID, Completion Status, BCM, Byte Count, Requester ID, Tag, Lower Address); status values SC 000b, UR 001b, CRS 010b, CA 100b; completions are routed by ID; a memory read may be completed by multiple completions that must respect MPS and the RCB and be returned in address order; Completion Timeout and Unexpected Completion are uncorrectable errors reported through AER; RCB is 64 or 128 bytes.

The Byte Count/Lower Address recurrence and the final-completion test (Byte Count ≤ payload bytes after removing leading disabled bytes) follow from the field definitions; the efficiency figures follow from header sizes. The executable model in this chapter encodes these derivations and validates the worked examples.

Completion sizes chosen by a Root Complex; which receive checks a requester performs; how an NVMe controller maps a UR/CA/timeout on a DMA read to an NVMe status or to a controller fatal status; platform default Completion Timeout values.

CRS was generalized to RRS in the 6.0 era; 10-bit tags (4.0) and 14-bit tags in Flit Mode (6.0) change the matching key width; Flit Mode changes header layout. The Completion Timeout ranges have been stable for many revisions, but verify the encodings.

The specification does not tell you which Completion Timeout value to choose, how large completions a Root Complex will send, or what an NVMe controller must do on a DMA completion error beyond reporting. Check in the spec: the exact Byte Count table for single-DWORD and zero-length reads, the Byte Count and Lower Address rules for non-memory and AtomicOp completions, the list of required versus permitted receive checks, and the default-timeout recommendation.

Never assume: completions arrive in the order reads were issued; a read arrives in one completion; the first completion is MPS-sized; Byte Count equals the payload; a Completion Timeout means the completer is dead (it may just be slow); an Unexpected Completion means the completer is buggy (it may be your own timeout or reset).

The order and the tag tie them together: the Unexpected Completion is the late answer to the timed-out read, not a misrouting. Root cause: a timeout window (1–10 ms) shorter than worst-case host memory latency under virtualization. Corrective action: raise the Completion Timeout Value to a range B or C setting through platform policy, and investigate the latency spike (IOMMU configuration, huge pages). Regression test: memory-pressure stress with IOMMU enabled while monitoring AER counters.

Code / pseudocode

The executable model used for every worked example in this chapter. It builds a Memory Read from a byte range, splits it into completions under two policies, and validates a completion sequence as a careful requester would.

#!/usr/bin/env python3
"""Split a PCIe Memory Read into completions and compute Length, Byte Count and
Lower Address for each completion (teaching model of the completion rules)."""

def request_from_bytes(addr, nbytes):
    """MRd fields (DW-aligned address, Length in DW, First/Last DW BE) for a byte range."""
    first, last = addr, addr + nbytes - 1
    if first // 4096 != last // 4096:
        raise ValueError("a Memory Read request must not cross a 4 KiB boundary")
    dw_first, dw_last = first & ~3, last & ~3
    length = (dw_last - dw_first) // 4 + 1
    fbe = (0xF << (first & 3)) & 0xF
    lbe = 0xF >> (3 - (last & 3))
    if length == 1:                 # single DW: one BE field, Last DW BE must be 0000b
        fbe, lbe = fbe & lbe, 0
    return dw_first, length, fbe, lbe

def total_byte_count(length, fbe, lbe):
    """Byte Count of the first completion, for contiguous byte enables."""
    if length == 1:
        if fbe == 0:
            return 1                # zero-length read (confirm in the spec's Byte Count table)
        return fbe.bit_length() - ((fbe & -fbe).bit_length() - 1)
    lead = (fbe & -fbe).bit_length() - 1
    trail = 4 - lbe.bit_length()
    return 4 * length - lead - trail

def split(addr_dw, length, fbe, lbe, mps=256, rcb=64, policy="max"):
    """policy 'max': largest legal completions; 'rcb': one RCB-aligned block each."""
    lead = (fbe & -fbe).bit_length() - 1 if fbe else 0
    total = total_byte_count(length, fbe, lbe)
    first_byte = addr_dw + lead
    last_byte = first_byte + total - 1
    cur, end, remaining, out = addr_dw, addr_dw + 4 * length, total, []
    while cur < end:
        if policy == "rcb":
            stop = min(end, (cur // rcb + 1) * rcb)
        else:
            stop = end
            if stop - cur > mps:    # not the last one: must end on an RCB boundary
                stop = (cur + mps) // rcb * rcb
        lo, hi = max(cur, first_byte), min(stop, last_byte + 1)
        out.append((cur, (stop - cur) // 4, remaining, lo & 0x7F))
        remaining -= hi - lo
        cur = stop
    return out

def validate(cpls, total, mps=256, rcb=64):
    """Requester-side checks on the completions of one request (address order)."""
    expected = total
    for i, (start, ln, bc, la) in enumerate(cpls):
        n, end = i + 1, start + 4 * ln
        if 4 * ln > mps:
            return f"CplD {n}: payload {4 * ln} B exceeds MPS {mps}"
        if bc != expected:
            return f"CplD {n}: Byte Count {bc}, expected {expected}"
        if i and la != start & 0x7F:
            return f"CplD {n}: Lower Address 0x{la:02X} does not match its data"
        last = n == len(cpls)
        if not last and end % rcb:
            return f"CplD {n}: not last, yet does not end on an RCB boundary"
        delivered = end - (start + (la & 3) if i == 0 else start)
        if last:
            return "ok" if 0 <= delivered - bc <= 3 else f"CplD {n}: length/Byte Count mismatch"
        expected -= delivered
    return "incomplete: Byte Count never reached zero"

def show(title, addr, nbytes, mps=256, rcb=64, policy="max"):
    a, l, f, b = request_from_bytes(addr, nbytes)
    print(f"{title}: MRd Addr=0x{a:X} Length={l} DW FirstBE={f:04b} LastBE={b:04b}")
    cpls = split(a, l, f, b, mps, rcb, policy)
    for i, (start, ln, bc, la) in enumerate(cpls, 1):
        print(f"  CplD {i}: from 0x{start:X} Length={ln:3d} DW ByteCount={bc:4d} LowerAddr=0x{la:02X}")

if __name__ == "__main__":
    show("A  aligned 512 B, largest completions", 0x2_0000_0040, 512)
    show("A' aligned 512 B, RCB-sized", 0x2_0000_0040, 512, policy="rcb")
    show("B  unaligned 200 B, largest", 0x2_0000_1006, 200)
    show("B' unaligned 200 B, RCB-sized", 0x2_0000_1006, 200, policy="rcb")
    show("C  PRP list tail 24 B", 0x1_5000_0FE8, 24)
    show("D  single byte", 0x1_0000_0003, 1)
    show("E  512 B at offset 0x20, RCB 128", 0x2_0003_0020, 512, rcb=128)
    a, l, f, b = request_from_bytes(0x2_0000_1006, 200)
    good = split(a, l, f, b, policy="rcb")
    print("validate B':", validate(good, 200))
    bad = [good[0], (good[1][0], good[1][1], 144, good[1][3])] + good[2:]
    print("validate B' with a wrong Byte Count:", validate(bad, 200))

Expected output: the sequences shown in the worked examples (A: Byte Counts 512, 256; B': 200, 142, 78, 14 with Lower Addresses 06h, 40h, 00h, 40h; C: one completion with Lower Address 68h; D: Byte Count 1, Lower Address 03h; E: 512, 288, 32), followed by validate B': ok and validate B' with a wrong Byte Count: CplD 2: Byte Count 144, expected 142.

Requester-side handling in firmware pseudocode:

void on_completion(const struct cpl *c)
{
    struct tag_entry *t = tag_lookup(c->requester_id, c->tag);
    if (!t || !t->outstanding) { aer_report(UNEXPECTED_COMPLETION, c); return; }
    if (c->status != CPL_SC)   { fail_request(t, c->status); tag_free(t); return; }
    if (c->len_dw * 4 > mps_bytes) { aer_report(MALFORMED_TLP, c); return; }
    if (c->byte_count != t->remaining ||
        c->lower_addr != expected_lower_addr(t)) {
        aer_report(MALFORMED_OR_UNEXPECTED, c);      /* which one is design-specific */
        fail_request(t, CPL_CA); tag_free(t); return;
    }
    size_t skip = t->first ? (t->addr & 3) : 0;      /* leading disabled bytes */
    size_t n = MIN(c->len_dw * 4 - skip, t->remaining);
    memcpy(t->buf + t->done, c->payload + skip, n);
    t->done += n; t->remaining -= n; t->first = false;
    if (t->remaining == 0) { complete_request(t); tag_free(t); }
    else restart_timer_if_policy(t);                  /* timer semantics: check spec */
}

Worked example

Question: The Lab SSD executes a 128 KiB NVMe Write from a contiguous, page-aligned buffer (PRP list describes 32 pages). With MRRS = 512 bytes and MPS = 256 bytes, how many read requests and completions cross the link for the data, how many tags are needed for full overlap, and how does the Root Complex's completion size change the link time?

  1. Read requests: 128 KiB / 512 B = 256 MRds (no read may cross a 4 KiB boundary; 512-byte reads aligned to the pages never do).
  2. Completions: if the Root Complex returns 256-byte completions, 2 per read → 512 CplDs; if it returns 64-byte (RCB) completions, 8 per read → 2,048 CplDs.
  3. Tags for overlap (Little's Law, Chapter 13): with ~1 µs round-trip and ~7 GB/s target, bytes in flight ≈ 7,000 B, i.e. ≈ 14 reads of 512 B outstanding. 8-bit tags (256) are ample; the limit is buffer space, not tags.
  4. Link time for data: 131,072 bytes at η = 93% of 7.88 GB/s ≈ 17.9 µs with 256-byte completions; at η = 76% ≈ 21.9 µs with 64-byte completions — a 22% difference caused only by the Root Complex's completion size.
  5. Byte Count spot check: the 37th read (bytes 18,432–18,943 of the buffer) with 64-byte completions has Byte Counts 512, 448, …, 64 and Lower Address alternating 00h and 40h, because 18,432 = 0x4800 is 128-byte aligned.

When an NVMe vendor and a platform vendor disagree about write throughput, completion size is one of the first things to look at on an analyzer. It is set by the platform, not the SSD.

Common mistakes

  • Treating Byte Count as "bytes in this completion" instead of "bytes remaining including this one".
  • Forgetting leading disabled bytes in the first completion (the off-by-two in the abnormal trace).
  • Expecting Lower Address to be a full address, or forgetting it is a byte address (not DWORD).
  • Assuming completions for different tags arrive in issue order.
  • Treating an Unexpected Completion as an independent fault without checking for a preceding Completion Timeout or reset.
  • Choosing a very short Completion Timeout for "fast failure" without considering IOMMU and virtualization latency.
  • Disabling Completion Timeout to "fix" spurious timeouts, converting them into hangs.
  • Ignoring RCB when building a completer (e.g. an FPGA peer device) — splits at arbitrary points are illegal.

Senior engineer insight

Error names describe what the requester noticed, not what went wrong. One bad Byte Count can surface as Malformed TLP, Unexpected Completion or Completion Timeout depending on which check fires first. One slow memory read can surface as Completion Timeout plus Unexpected Completion. Always reconstruct the request's life: issue, completions, checks, timer — then name the root cause.

  • Completion Timeout values are a system-level contract between platform firmware, OS error recovery and NVMe command timeouts. They should be chosen together: PCIe timeout ≪ NVMe command timeout ≪ application timeout.
  • When validating a completer (any device exposing memory — CMB, PMR, peer-to-peer targets), test unaligned reads with every byte-enable combination, reads ending exactly on RCB boundaries, and reads of 1 to MPS+1 bytes. Byte Count bugs hide at edges.
  • A requester that does not validate Byte Count and Lower Address is fragile; a requester that validates too strictly (beyond the spec) is incompatible. Validate against the specification's rules, not against one Root Complex's behaviour.

Observation

Questions

  1. Why is the 300-byte read at 0x…0F01 illegal as a single request?
  2. Why does the final completion's Byte Count sometimes differ from its payload size?
  3. Your Root Port's timeout is 17–64 s. What happens if the SSD dies during a CSTS read?

Challenge

Extend the model to 10-bit tags and multiple outstanding requests with randomized interleaving of completions (legal under D5a), and make the validator group by tag.

Hints

0x0F01 + 300 − 1 = 0x102C, which crosses 0x1000. Trailing disabled bytes are included in the payload but not in Byte Count. A CPU load waiting for a completion cannot retire until the Root Port gives up.

Solution

Step 1: 100 bytes at 0x…0FB0 end at 0x…1013, so the request crosses a 4 KiB boundary and is illegal as given; a correct requester issues two reads, 80 bytes (0xFB0–0xFFF) and 20 bytes (0x1000–0x1013). The 80-byte read gives completions BC 80 (LA 30h, 4 DW) and BC 64 (LA 40h, 16 DW). Q1: it crosses a 4 KiB boundary; requesters must split such reads. Q2: the final completion includes whole DWORDs, so trailing disabled bytes are in the payload but not counted in Byte Count. Q3: the CPU core issuing the load stalls until the Root Port's timer expires (up to tens of seconds), then the load returns all-ones or the platform raises a machine check; watchdogs may fire first. Step 3: e.g. range C (260–900 ms) — long enough to ride out transient memory stalls, far below NVMe's command timeout so the controller can fail the command cleanly.

What a senior engineer notices

That both step-1 examples cross a 4 KiB boundary. Edge cases hide in innocent-looking numbers — always check the 4 KiB rule before computing completions.

Failure variants

  • RCB mismatch between Root Port and endpoint setting: a requester that checks RCB strictly may reject legal 128-byte-aligned splits or accept illegal 64-byte ones.
  • MPS mismatch: completions larger than the receiver's MPS → Malformed TLP.

Extension

On an analyzer, export completions for one NVMe Write and run them through the validator.

Exercises

  1. Compute all fields for a single CplD answering a read of 6 bytes at 0x…1002.
  2. A CplD shows Length = 16, Byte Count = 10, Lower Address = 40h. What can you conclude?
  3. Which Completion Timeout encoding would you choose for a requester that must detect a dead path within 100 ms but tolerate 50 ms stalls? Explain.
  4. List three distinct root causes that all produce an Unexpected Completion at the SSD.
  5. Explain why a zero-length read returns one DWORD of data and Byte Count 1.
Answers

1. Bytes 0x1002–0x1007: DWORD address 0x1000, Length 2, First DW BE 1100b, Last DW BE 1111b; CplD Length 2, Byte Count 6, Lower Address = 0x…1002 & 0x7F = 02h.

2. It is the final completion of its request (Byte Count ≤ payload), it starts at a 64-byte boundary with address bits 6:0 = 40h, and the last 6 bytes of its 64-byte payload are disabled (not requested).

3. 0110b (65–210 ms) could fire later than 100 ms; 0101b (16–55 ms) could fire during a 50 ms stall. Neither satisfies both constraints strictly; choose 0110b if stall tolerance matters more, or redesign the detection (e.g. a heartbeat). The exercise shows that timeout windows are coarse.

4. Late completion after the SSD's own timeout; completion arriving after an FLR/controller reset discarded the request; misrouted completion with the SSD's Requester ID belonging to another requester's request (completer bug), or duplicates.

5. The completion must still be a well-formed CplD for a 1-DWORD request; the specification defines Byte Count = 1 for that case so the requester sees "final completion" semantics; the data is ignored. The purpose is ordering (flushing earlier posted writes), not data.

Quiz

  1. Byte Count in a memory read completion means…

    • bytes in this completion
    • bytes remaining including this completion
    • total bytes of the request, in every completion
    • bytes already delivered
    Answer and reasoning

    Remaining including this one; it equals the total only in the first completion.

    • 0x…130

    • 0x…140
    • 0x…0A4

    0x140 is 64-byte aligned (0x140 = 320 = 5 × 64).

    • bits 6:0 of the byte address of the first returned enabled byte
    • bits 11:0 of the DWORD address
    • the tag
    • the full 64-bit address
    Answer and reasoning

    7 bits of byte address.

    • UR
    • CA
    • SC
    • CRS/RRS
    Answer and reasoning

    Configuration Request Retry Status (Request Retry Status in newer revisions), 010b.

  5. Completions for two different reads arrive interleaved. This is…

    • a violation
    • legal
    • legal only with RO
    • legal only in Flit Mode
    Answer and reasoning

    D5a allows completions with different Transaction IDs to pass each other.

  6. What is the default Completion Timeout window (encoding 0000b) as commonly documented?

    Model answer

    50 µs to 50 ms — verify in your revision; the spec also recommends a minimum of roughly 10 ms for the default.

  7. Why does an Unexpected Completion often follow a Completion Timeout for the same tag?

    Model answer

    The requester abandoned the request and freed the tag when its timer expired; the slow completion arrives later and matches nothing outstanding.

  8. Give the completion sequence (Length, Byte Count, Lower Address) for 512 bytes at 0x…040 with MPS 256, RCB 64, largest completions.

    Model answer

    (64 DW, 512, 40h), (64 DW, 256, 40h).

  9. Why can a Byte Count bug appear as three different AER errors?

    Model answer

    Depending on which check fires: a requester validating Byte Count may log Malformed TLP; one that treats the sequence as ended may later see extra completions as Unexpected; one that keeps waiting for missing bytes times out.

Interview questions

  1. Beginner: What fields does a requester use to match a completion?

    Model answer

    Requester ID and Tag (the Transaction ID); with 10-bit tags, all tag bits.

  2. Beginner: Can a 512-byte read be completed with one completion if MPS is 256?

    Model answer

    No; each completion's payload must not exceed MPS, so at least two completions are needed.

  3. Intermediate: Explain RCB and why it exists.

    Model answer

    The Read Completion Boundary (64 or 128 bytes) constrains where a split may occur: non-final completions end on naturally aligned RCB boundaries. It lets Root Complexes return cache-line-sized chunks early while keeping requester reassembly predictable.

  4. Intermediate: Compute Byte Count and Lower Address for the second completion of a 200-byte read at 0x…1006 split at 0x…1040.

    Model answer

    First completion delivered 0x1040 − 0x1006 = 58 bytes; Byte Count 142; Lower Address 40h.

  5. Advanced: How should an NVMe controller react to a Completion Timeout on a write-data fetch?

    Model answer

    Abandon the transfer, complete the NVMe command with an appropriate error status (a data transfer error class), report the PCIe error through AER, ensure no partial data is committed as if complete, and recover the tag. Escalation to controller fatal status is design-dependent.

  6. Advanced: Why do write throughputs differ between platforms with the same SSD?

    Model answer

    Root Complex completion sizes (RCB-sized vs MPS-sized), latency to memory, MPS/MRRS configuration, and tag/buffer limits all change efficiency and overlap.

  7. Senior: Propose a Completion Timeout policy for a cloud fleet.

    Model answer

    Pick ranges that exceed worst-case measured host memory latency under virtualization and IOMMU stress with margin (often range B/C), keep them well below NVMe command timeouts, avoid disabling, monitor AER counters for timeouts and unexpected completions per device, and correlate with host memory events.

  8. Senior: Review a peer-to-peer design where an FPGA exposes a buffer read by NVMe SSDs.

    Model answer

    Verify the FPGA completer: MPS/RCB compliance, Byte Count/Lower Address for all alignments and byte enables, address order, correct Completer ID after enumeration, timeout behaviour of the SSDs when the FPGA stalls, ACS/routing through switches, and ordering (data vs flags) for any producer–consumer protocol.

Chapter summary

Completions carry Completer ID, status, Byte Count, Requester ID, Tag and Lower Address. Memory reads may be split into completions that respect MPS, end on RCB boundaries (except the last), and arrive in address order; different requests' completions may interleave. Byte Count counts down the remaining bytes including the current completion; Lower Address is the low 7 bits of the first returned byte's address. Completion Timeout bounds how long a requester waits, with ranges from tens of microseconds to tens of seconds selected in Device Control 2; Unexpected Completions are often late answers to timed-out requests. Completion size chosen by the Root Complex materially affects NVMe write throughput.

Do not move on until you can:

  • decode a completion header and name each field's owner
  • split any read into legal completions by hand under MPS and RCB
  • compute Byte Count and Lower Address for unaligned and single-byte reads
  • validate a completion sequence and find the first bad completion
  • explain the Completion Timeout ranges, the disable control, and a reasoned policy
  • distinguish late, misrouted and duplicate completions
  • estimate the throughput cost of small completions
