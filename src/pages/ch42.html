A completion that nobody notices is as useless as a completion that never happened. This chapter teaches how an NVMe controller tells the host "your command is done": the three Peripheral Component Interconnect Express (PCIe) interrupt mechanisms — legacy INTx, Message Signaled Interrupts (MSI) and MSI-X — plus interrupt coalescing and polling, and why NVMe was designed around MSI-X from the start.

Why this chapter exists

Up to now the course has followed a command from the application down to the media and back up as far as the Completion Queue: the controller writes a 16-byte Completion Queue Entry (CQE) into host memory, flips the Phase Tag, and stops. But the CPU is not watching that memory. Something has to wake it. That "something" is the interrupt, and it is the last hop of every I/O you will ever trace.

Interrupts matter to an engineer for three reasons:

  • Correctness. A lost or misrouted interrupt looks exactly like a hung device: the command completed, the CQE is sitting in memory, but Linux times out after 30 seconds and resets the controller. Many "the SSD hung" bug reports are actually interrupt bugs.
  • Performance. At a million I/O operations per second (IOPS), one interrupt per command means a million interrupts per second. How interrupts are spread across CPUs, batched (coalesced) or avoided altogether (polling) decides tail latency and CPU cost.
  • Debuggability. The interrupt is the one event that crosses from the device back into the CPU's world. In a protocol analyzer it is a single tiny Memory Write; in Linux it is a counter in /proc/interrupts. Learning to connect the two is a core trace skill.

Learning objectives

  • Explain what an interrupt is and why a device needs one, in plain words and in PCIe terms.
  • Describe legacy INTx (a virtual wire signalled by Assert/Deassert messages), MSI (a memory write with a small set of vectors) and MSI-X (a memory write with a per-vector table), and compare them on vector count, sharing, masking and CPU steering.
  • Explain why NVMe's many-queue design strongly benefits from MSI-X: one vector per completion queue, one completion queue per CPU.
  • Describe NVMe interrupt coalescing (aggregation threshold and aggregation time) and the per-vector coalescing disable.
  • Explain polling (Linux poll queues, io_uring with I/O polling, RWF_HIPRI) and when it beats interrupts.
  • Know that the NVMe Interrupt Mask Set (INTMS) and Interrupt Mask Clear (INTMC) registers apply only to pin-based and MSI interrupts, never to MSI-X.
  • Recognise an interrupt in a synthetic trace and in Linux, and reason about a "completion arrived but no interrupt" failure.

Prerequisites

You should be comfortable with: posted vs non-posted transactions (an interrupt message is a posted write), PCIe ordering (why the interrupt cannot overtake the CQE), configuration space and capabilities, BARs and MMIO, queue architecture and doorbells, and the full command life cycle in The Most Important Chapter.

The story

Imagine a classroom where the teacher has sent twenty children to the library to fetch books. The librarian finds each book and puts it in the "done" basket by the classroom door. But the teacher is busy teaching and does not look at the basket.

In the oldest school, there is one bell rope shared by the whole library. When any book is ready, the librarian pulls the rope and keeps holding it. The teacher hears "ding" but has no idea whose book is ready, so she walks over and checks every basket. If two librarians pull the same rope, it still only rings once.

In a newer school, the librarian can send a note to the classroom instead. The note says a number, like "note 3". There can be up to 32 different note numbers, but they all go to the same teacher.

In the newest school, there is a list on the wall with one line per basket: "basket 1 → send a note to Mr. Ahmed in room 1", "basket 2 → send a note to Ms. Chen in room 2", and so on, for up to two thousand baskets. Each teacher only gets notes about their own children's books, and any line can be paused with a little "do not disturb" sticker.

Sometimes a teacher says "do not send me a note for every single book — wait until five are ready or until one minute has passed." That is coalescing. And sometimes a teacher is so impatient she just stands at the basket and keeps looking. That is polling.

Think of a large restaurant kitchen. Plates come out of the kitchen (completions) and must reach the right table. INTx is a single dinner gong in the dining room: every waiter hears it, all of them walk to the pass to see if the plate is theirs. MSI is a small pager system with a handful of buzzer codes, all routed to one head waiter's belt. MSI-X is a pager per waiter, with the kitchen holding a wall chart that says which waiter's pager number to buzz for each section of tables. Coalescing is the expediter saying "buzz me when four plates are up or after 30 seconds, whichever comes first." Polling is a waiter who never leaves the pass.

What the analogy hides: an MSI or MSI-X "page" is not a separate wire or radio: it is an ordinary PCIe Memory Write to a special address that the CPU's interrupt hardware watches. That is why it obeys PCIe ordering rules, can be blocked by an Input-Output Memory Management Unit (IOMMU) or interrupt remapping table, and shows up in a protocol analyzer exactly like a data write. Where it misleads: the gong suggests INTx is a physical wire; on PCIe it is a pair of in-band messages (Assert_INTx and Deassert_INTx) emulating a level-triggered wire. And the "wall chart" for MSI-X is written by the host, not the kitchen: the operating system decides which CPU each vector goes to, and the device merely obeys the table.

Beginner explanation

A CPU runs software. A device works on its own. When a device has finished something the CPU asked for, there are only two ways the CPU can find out:

  1. The CPU checks. Software keeps looking at a memory location or a register to see whether something changed. This is called polling.
  2. The device tells the CPU. The device sends a signal that makes the CPU stop what it is doing for a moment, run a small piece of code called an interrupt handler, and then go back. This is an interrupt.

Polling wastes CPU time when nothing is happening but reacts very quickly. Interrupts cost nothing while idle but each one has overhead: saving the CPU's state, running the handler, returning. Good systems use interrupts most of the time and polling when latency matters more than CPU efficiency.

An NVMe controller can have up to 65,535 I/O queues. Linux typically creates one queue pair per CPU. With MSI-X, each CPU's completion queue gets its own interrupt vector aimed at that same CPU, so the CPU that submitted a command is the CPU that gets told it finished. No sharing, no cross-CPU traffic, no checking queues that belong to someone else. That is the whole reason NVMe "strongly benefits from MSI-X".

An interrupt is just a notification. The actual result of the command is in the CQE in host memory. The interrupt carries no status, no command identifier, no data — only "look at queue(s) behind this vector".

Engineering explanation

What an interrupt is, precisely

An interrupt is an asynchronous event that diverts a CPU's instruction stream to a handler. On x86-64, the Local Advanced Programmable Interrupt Controller (LAPIC) of each core receives interrupt messages and delivers them as an 8-bit interrupt vector number that indexes the Interrupt Descriptor Table. On Arm, the Generic Interrupt Controller (GIC) with its Interrupt Translation Service (ITS) plays the same role for message-signalled interrupts. The details differ, but the device-side picture is the same: the device produces a signal; platform interrupt hardware turns it into "run handler X on CPU Y".

Note the two meanings of vector: the CPU vector (the IDT index on x86) and the MSI-X vector (an index into the device's MSI-X table, 0…N−1). NVMe uses the second meaning. Linux maps each device vector to a Linux IRQ number, and the platform maps that to a CPU vector. Keep the three numbering spaces apart in your head; mixing them is a classic source of confusion in bug reports.

Legacy INTx

Conventional PCI had four physical interrupt pins per slot (INTA#–INTD#), active-low and level-triggered, wired-OR so several devices could share one line. PCIe has no sideband interrupt wires. To stay software-compatible, PCIe emulates the wire with message TLPs (Transaction Layer Packets): the device sends an Assert_INTx message when its interrupt condition becomes true and a Deassert_INTx message when it becomes false. Switches and root ports collapse these into a virtual wire state per INTx line (and remap INTA–INTD across switch ports — the "swizzle"), and the root complex presents it to the platform interrupt controller (an I/O APIC on x86).

  • Level semantics. The virtual wire stays asserted until the device deasserts it. The handler must clear the cause in the device, otherwise the interrupt fires again forever (an "interrupt storm").
  • Sharing. Several functions can be behind the same INTx line. Every handler on that line runs and must ask "was it me?" by reading a device register — a non-posted MMIO read costing on the order of a microsecond.
  • Control bits. The PCI Command register's Interrupt Disable bit stops the function from sending INTx messages; the Status register's Interrupt Status bit reflects whether the function's INTx condition is pending. The Interrupt Pin register (read-only) says which INTx the function uses; Interrupt Line is just a scratch byte software fills in.
  • Exclusion. When MSI or MSI-X is enabled, the function must not use INTx.

For NVMe, INTx means one interrupt for the whole controller: on every interrupt the driver must scan all completion queues (or rely on INTMS/INTMC masking, see below). It works, and the NVMe specification allows it, but it throws away the per-queue parallelism NVMe was designed for.

MSI

Message Signaled Interrupts replace the wire with a posted Memory Write. Software programs a Message Address and a Message Data value into the function's MSI capability (Capability ID 05h in configuration space). To interrupt, the function writes the data value to the address. The platform's interrupt hardware decodes writes to that address range (on x86, the 0xFEEx_xxxx window) as interrupt messages rather than memory.

  • Vectors. A function advertises how many vectors it can use (Multiple Message Capable: 1, 2, 4, 8, 16 or 32) and software grants some (Multiple Message Enable). With several vectors, the function modifies the low bits of the data value to select the vector. All vectors share one address, so on most platforms they all target the same CPU (or the same set).
  • Masking. Per-vector masking is optional (Per-Vector Masking Capable); when present there is a Mask Bits and Pending Bits register in the capability.
  • Edge semantics. One write = one interrupt. There is no "deassert". If the device writes while the CPU is masked, the platform latches it; nothing is lost but nothing is repeated either.

MSI-X

MSI-X (Capability ID 11h) keeps the "interrupt is a memory write" idea but moves the address/data pairs into a table in a BAR (Base Address Register region), one 16-byte entry per vector, each with its own address, data and mask bit. A separate Pending Bit Array (PBA) records vectors that wanted to fire while masked. Up to 2048 vectors per function. Because every vector has its own address, each can be steered to a different CPU. Chapter 43 is entirely about MSI-X; here we only need the comparison.

Why NVMe strongly benefits from MSI-X

NVMe's performance story is "no shared locks between CPUs". Each CPU has its own Submission Queue (SQ) and Completion Queue (CQ). The submission path needs no lock because only one CPU writes that SQ. If the completion notification then went to a single CPU (INTx or MSI), that one CPU would have to process completions for every other CPU and wake them up with inter-processor interrupts — re-creating exactly the bottleneck NVMe removed. MSI-X closes the loop:

  1. At Create I/O Completion Queue time, the driver gives each CQ an Interrupt Vector (IV) number and sets Interrupts Enabled (IEN).
  2. The driver programs MSI-X table entry IV with an address/data that targets the CPU (or CPUs) that own that queue.
  3. When the controller posts a CQE to that CQ it writes table entry IV's data to table entry IV's address. Only that CPU is interrupted. Its handler reads only its own CQ.

The NVMe specification permits several CQs to share one vector (the driver gives them the same IV), and it permits fewer vectors than queues. Linux sometimes does this when the device offers fewer vectors than CPUs. The cost is that the handler must check several CQs on each interrupt.

NVMe interrupt rules that matter

  • Interrupt mode selection. The controller uses whichever mechanism the host has enabled in PCI configuration space: MSI-X if MSI-X Enable is set, else MSI if MSI Enable is set, else INTx. The NVMe over PCIe Transport specification describes how NVMe completion queues map onto each mode.
  • Admin CQ. The Admin Completion Queue always uses interrupt vector 0 (it has no Create command; interrupts for it are always enabled once the controller is enabled).
  • Pin-based and MSI masking. NVMe defines Interrupt Mask Set (INTMS, offset 0Ch) and Interrupt Mask Clear (INTMC, offset 10h). Writing a 1 to a bit in INTMS masks that vector; writing a 1 to INTMC unmasks it; reads of either return the current mask. These registers exist so a driver can stop interrupts from an INTx or multi-message MSI controller while it drains queues, without touching configuration space. When MSI-X is configured the host must not access INTMS/INTMC; MSI-X has its own per-vector mask bit in the table.
  • When the controller interrupts. For a CQ with IEN set, the controller generates an interrupt when it has posted entries the host has not yet consumed (the CQ head doorbell tells it how far the host got). Coalescing may delay it (below). The exact "when" — after one CQE, after several, how it treats a CQ that is still non-empty after the host updates the head — is partly defined by the transport specification and partly implementation-dependent. Read the "Interrupts" material in the NVMe over PCIe Transport specification before relying on fine detail.

Interrupt coalescing

Each interrupt costs CPU time: entering the handler, reading the CQ, ringing the CQ head doorbell, returning. At very high IOPS, servicing one completion per interrupt wastes cycles. Interrupt coalescing lets the controller wait and deliver one interrupt for several completions.

NVMe exposes this as the Interrupt Coalescing feature (Feature Identifier 08h, set with Set Features, read with Get Features). Command Dword 11 carries two fields:

CDW1131…2423…1615…87…0
Interrupt CoalescingReservedAggregation Time (TIME)Aggregation Threshold (THR)
  • Aggregation Threshold (THR) — the minimum number of completion entries to aggregate per vector before signalling an interrupt. It is a 0's based value: 0 means 1 entry (effectively no coalescing by count), 7 means 8 entries.
  • Aggregation Time (TIME) — the maximum time the controller may delay an interrupt because of coalescing, in 100-microsecond increments. 0 means no delay.
  • The interrupt fires when either condition is met: threshold reached or time expired. The default is typically 0/0 (coalescing off).
  • The companion Interrupt Vector Configuration feature (Feature Identifier 09h) has, per vector, a Coalescing Disable (CD) bit: set it and that vector ignores coalescing. Useful for a latency-sensitive queue next to throughput queues.

100 µs granularity is coarse compared with a ~10 µs flash read. A TIME of 1 can add up to 100 µs to the completion latency of a lightly loaded queue — ten times the device latency. Coalescing is a throughput tool; it is almost never a latency tool. Linux's NVMe driver does not enable it by default.

How a controller implements the timer (per vector, per CQ, started at the first un-signalled CQE or free-running) is implementation-dependent within what the specification requires. The specification also says the controller is not required to coalesce in every circumstance (for example, it may signal sooner). Measure your device; do not assume THR=7 always produces exactly one interrupt per eight completions. Confirm the current wording on admin-queue and error-completion behaviour in the Interrupt Coalescing feature description of the NVMe Base Specification.

Polling: no interrupt at all

At high queue depth, by the time the handler runs there are already more CQEs waiting; interrupts are cheap per I/O. At queue depth 1 on a fast drive, the interrupt path (MSI-X write → LAPIC → context switch to the woken thread) can be several microseconds out of a ~10 µs total. Polling removes it: the submitting thread spins reading the CQ's next entry, looking for the Phase Tag to flip.

  • Linux poll queues. The nvme driver's poll_queues module parameter creates extra I/O queue pairs whose CQs are created with IEN cleared: the controller never interrupts for them. They are used only for I/O submitted with the high-priority/polled flag.
  • io_uring. A ring set up with IORING_SETUP_IOPOLL polls for completions of O_DIRECT I/O instead of sleeping. fio exposes it as --hipri with ioengine=io_uring.
  • preadv2/pwritev2. The RWF_HIPRI flag requests polled completion for a single direct I/O.
  • Hybrid polling. Linux block layer can sleep for an estimated fraction of the expected latency before starting to spin, trading a little latency for much less CPU.

Linux block-layer polling has changed several times across kernel versions (classic polling, hybrid polling tunables in /sys/block/<dev>/queue/io_poll and io_poll_delay, the move to dedicated poll queues). Treat specific sysfs knobs as kernel-version-dependent and check your kernel's documentation.

The central concept on the ladder

When the librarian finishes your book, she sends a note to your teacher, not to the whole school.

When the controller posts a completion into a CQ, it signals the interrupt vector assigned to that CQ, which the operating system has aimed at the CPU that owns the queue.

The controller's completion engine writes the 16-byte CQE through its DMA engine, then its interrupt logic looks up the MSI-X table entry for the CQ's IV, checks the per-vector and function mask, and if unmasked emits a 4-byte write of the entry's Message Data to its Message Address. The CPU's LAPIC (or GIC ITS) receives it and raises the vector.

NVMe Base Specification: Create I/O Completion Queue carries IV and IEN; Interrupt Coalescing (FID 08h) and Interrupt Vector Configuration (FID 09h) features; INTMS/INTMC registers for pin-based and MSI only. NVMe over PCIe Transport: how CQ interrupts map to INTx, MSI, MSI-X. PCI Express Base Specification: MSI and MSI-X capabilities, INTx message emulation.

On the link: Device→Host posted MWr (CQE, 16 bytes) followed by Device→Host posted MWr (MSI-X, 4 bytes, to 0xFEEx_xxxx). PCIe ordering forbids the second posted write from passing the first (unless the interrupt write has Relaxed Ordering set, which it should not), so the CQE is in memory before the CPU can be interrupted.

In an analyzer: a 16-byte MWr to the CQ base region with Requester ID 0x0100, then within a few hundred nanoseconds a 1-DW MWr to 0xFEE0_xxxx with the same Requester ID. No completion follows — posted. Later, an RC→device MWr to the CQ head doorbell.

Command timed out but the CQE is in memory with the correct Phase Tag? Look for the interrupt MWr after it. Missing → controller didn't fire (IEN, mask, coalescing, firmware). Present → host side lost it (IOMMU interrupt remapping fault, wrong table entry, CPU offline, driver bug). That single question splits the search space in half.

The 16 questions for the MSI-X completion interrupt

1. What is it?
A posted PCIe Memory Write, generated by the NVMe controller after posting one or more CQEs, whose address and data come from the MSI-X table entry selected by the CQ's interrupt vector.
2. Why was it created?
To let a device notify a specific CPU of a specific event without shared wires, polling, or "was it me?" reads.
3. What problem does it solve?
Interrupt sharing, single-CPU bottlenecks, and the ordering hazard of sideband interrupts racing data.
4. What existed before it?
INTx (shared level-triggered pins, emulated by messages on PCIe) and MSI (up to 32 vectors with one address).
5. Why is the current design better?
Per-vector address/data/mask, up to 2048 vectors, table in MMIO space that is fast to update, natural ordering behind data.
6. Who creates it?
The table entries are created by host software (the OS interrupt subsystem); the interrupt write itself is created by the controller.
7. Who consumes it?
The platform interrupt hardware (IOMMU interrupt remapping, LAPIC/GIC), which raises a CPU vector; then the NVMe driver's handler.
8. Where does it live?
Capability in configuration space; table and PBA in a BAR (on the lab system BAR0+0x2000 and BAR0+0x3000); the write itself travels upstream on the link.
9. What memory/registers are involved?
MSI-X Message Control (Enable, Function Mask, Table Size), Table Offset/BIR, PBA Offset/BIR, table entries, PBA bits; NVMe CQ IV/IEN; Interrupt Coalescing and Interrupt Vector Configuration features; CQ head doorbell.
10. What happens before it?
The controller DMA-writes the CQE (with Phase Tag) into the CQ in host memory.
11. What happens after it?
The handler reads CQEs while the Phase Tag matches, completes requests, then writes the CQ head doorbell.
12. What happens if it is wrong?
Wrong address → write lands elsewhere or is blocked by the IOMMU (interrupt remapping fault); wrong data → wrong CPU vector, spurious or unhandled interrupt; masked → pending bit set, no interrupt; missing → I/O timeout and controller reset.
13. What does the protocol analyzer show?
A 1-DW MWr from the device's Requester ID to an address in the interrupt window, right after the CQE write.
14. What does Linux show?
Per-CPU counts in /proc/interrupts on lines named nvme0q0, nvme0q1…; affinity in /proc/irq/<n>/; lspci -vvv MSI-X Enable+ and Count.
15. What would a validation engineer test?
Every vector fires to its configured target; masked vectors set PBA bits and fire on unmask; coalescing thresholds and timers; IEN=0 produces no writes; interrupts never overtake CQEs; behaviour across reset and vector reprogramming.
16. What would a senior engineer suspect when it fails?
First: is the CQE there? Then: did the write go out (analyzer)? Then: was it masked, coalesced, remapped, or aimed at an offline CPU? Also: did firmware fire for the wrong CQ (IV mix-up), or fire before the CQE was visible (Relaxed Ordering misuse)?

Hardware view

Inside the controller, a completion engine and an interrupt engine cooperate. The completion engine owns, per CQ: the base address, size, tail pointer, current Phase Tag, the host-reported head (from the CQ head doorbell), the IV and IEN. The interrupt engine owns, per vector: a copy (or a read path) of the MSI-X table entry, its mask bit, its pending bit, and coalescing state (count of unsignalled CQEs, a timer).

On the host side the interrupt write reaches the root complex like any other upstream memory write. The root complex recognises the address range as interrupt space. With an IOMMU that does interrupt remapping (Intel VT-d IR, AMD-Vi), the address/data the device sends is not a raw "CPU + vector" but an index into an interrupt remapping table the IOMMU owns; the IOMMU validates the source Requester ID and translates. This is why a device that writes a stale MSI-X entry after the OS has reprogrammed things can produce an IOMMU fault message instead of an interrupt.

INTx hardware

For INTx, the device keeps a single "interrupt pending" condition. Rising edge of the condition → send Assert_INTA (or whichever pin); falling edge → send Deassert_INTA. A switch ORs the virtual wires from all downstream ports per line and forwards a single Assert/Deassert upstream when the OR changes. The root complex feeds the virtual wire into an I/O APIC pin. Because these are messages, they can be lost in exotic failures (for example a link reset between Assert and Deassert) and the virtual wire state must be cleaned up by the hardware on link down.

What is internal and unobservable

The coalescing counter, the timer and the decision "fire now" are inside the controller. You see only their result: an MWr or no MWr. A missing interrupt cannot be distinguished, from the link alone, between "masked", "coalesced and waiting", "IEN was 0" and "firmware bug" — you need register state (table mask bits, PBA, Get Features) to separate them.

Specification view

Three documents share this topic. Keep them separate:

  • PCI Express Base Specification, Revision 6.x/7.0 — MSI and MSI-X Capability structures; INTx emulation (virtual wire messages): defines the mechanisms themselves. A PCI-SIG members' document; cite by name, not by section number.
  • NVM Express Base Specification, Revision 2.4 — Controller Registers (INTMS, INTMC); Create I/O Completion Queue; Features: Interrupt Coalescing, Interrupt Vector Configuration: defines how NVMe uses vectors and coalescing.
  • NVMe over PCIe Transport Specification, Revision 1.4 — Interrupts: defines how completion queues map onto INTx, MSI (single and multiple message) and MSI-X on PCIe.

The PCIe-level definitions are Normative in the PCIe Base Specification. NVMe's coalescing semantics are normative but give the controller latitude. Linux behaviour is neither: it is implementation.

INTx on PCIe is signalled by Assert_INTx/Deassert_INTx messages. MSI (Capability ID 05h) supports 1–32 vectors in powers of two; MSI-X (Capability ID 11h) supports up to 2048 vectors with a table and PBA located via BIR/offset. NVMe INTMS is at offset 0Ch and INTMC at 10h, and are not used when MSI-X is configured. Create I/O Completion Queue carries Interrupt Vector and Interrupts Enabled. Interrupt Coalescing is Feature Identifier 08h with Aggregation Time in 100 µs units and a 0's based Aggregation Threshold; Interrupt Vector Configuration is Feature Identifier 09h with a Coalescing Disable bit.

That MSI-X "strongly benefits" NVMe is a design inference: one vector per CQ, each steerable to the owning CPU, preserves the lock-free per-CPU queue model end to end. That the interrupt cannot overtake the CQE follows from PCIe posted-write ordering when neither the interrupt write has Relaxed Ordering set nor the platform reorders.

Which CPU a vector targets, how many vectors the OS asks for, whether queues share vectors, whether coalescing is enabled, the controller's coalescing timer implementation, and the exact moment within a burst at which the controller fires are implementation-dependent.

Field names and the presence of some interrupt-related fields have evolved across NVMe revisions (for example, the restructuring of NVMe 2.0 moved PCIe-specific interrupt material into the NVMe over PCIe Transport specification). Older drives may report against NVMe 1.x, where the same material lived in a single base specification. Linux polling interfaces are kernel-version-dependent.

Check in the specifications: the exact conditions under which a controller must (not merely may) signal an interrupt for a CQ that still contains unconsumed entries after the host updates its head doorbell; whether coalescing applies to the Admin Completion Queue in your target revision; and the multiple-message MSI rules for how NVMe CQs map onto fewer MSI vectors. The NVMe specifications do not say which CPU an interrupt should target — that is entirely an operating-system choice.

Never assume one interrupt per completion; never assume interrupt vector number equals queue number (it usually does in Linux, but the specification does not require it); never assume an interrupt carries status; never assume INTMS/INTMC do anything useful under MSI-X.

Ordering is the hidden protocol requirement

Because the CQE write and the MSI-X write are both posted Memory Writes from the same function on the same traffic class, the PCIe ordering rules forbid the later one from passing the earlier one unless the later one carries Relaxed Ordering. So when the CPU receives the interrupt, the CQE is already globally visible. Old PCI with sideband pins had no such guarantee, which is why INTx handlers traditionally performed a read of the device ("flush posted writes") first. See PCIe Ordering.

Code / pseudocode

Driver interrupt handler (conceptual)

irqreturn nvme_irq(int irq, struct nvme_queue *cq) {
    bool found = false;
    while (cqe_phase(cq->entries[cq->head]) == cq->phase) {
        rmb();                       /* read CQE body only after phase is seen */
        complete_request(cq->entries[cq->head].cid,
                         cq->entries[cq->head].status);
        if (++cq->head == cq->depth) { cq->head = 0; cq->phase ^= 1; }
        found = true;
    }
    if (found)
        writel(cq->head, cq->head_doorbell);   /* tell controller entries are free */
    return found ? IRQ_HANDLED : IRQ_NONE;    /* IRQ_NONE = spurious */
}

Note the handler never asks the device "why did you interrupt?". The CQ itself is the answer.

Coalescing simulator

This standard-library Python program simulates THR/TIME coalescing for a stream of completions and reports interrupts per completion and added latency. Run it as written.

#!/usr/bin/env python3
"""Simulate NVMe-style interrupt coalescing (synthetic model, not a device model).

THR is 0's based (0 => 1 entry). TIME is in 100 us units (0 => no delay).
An interrupt fires when pending >= THR+1, or when the oldest pending
completion has waited TIME*100 us. Times are in microseconds."""
import random

def simulate(arrivals_us, thr, time_units):
    need = thr + 1
    limit = time_units * 100.0
    pending, interrupts, added = [], 0, []
    def fire(t):
        nonlocal pending, interrupts
        interrupts += 1
        added.extend(t - a for a in pending)
        pending = []
    for t in arrivals_us:
        if pending and limit > 0 and t - pending[0] >= limit:
            fire(pending[0] + limit)          # timer expired before this arrival
        pending.append(t)
        if len(pending) >= need or limit == 0:
            fire(t)
    if pending:
        fire(pending[0] + limit if limit else pending[-1])
    n = len(arrivals_us)
    return interrupts, interrupts / n, sum(added) / n, max(added)

def stream(rate_per_us, n, seed=1):
    rnd, t, out = random.Random(seed), 0.0, []
    for _ in range(n):
        t += rnd.expovariate(rate_per_us)
        out.append(t)
    return out

if __name__ == "__main__":
    for label, rate in (("light load  10k IOPS", 0.01), ("heavy load 800k IOPS", 0.8)):
        arr = stream(rate, 20000)
        print(label)
        for thr, tm in ((0, 0), (3, 1), (7, 1), (31, 2)):
            i, per, avg, worst = simulate(arr, thr, tm)
            print(f"  THR={thr:2d} TIME={tm} -> interrupts={i:6d} "
                  f"per-cmd={per:5.3f} added avg={avg:7.1f}us worst={worst:6.1f}us")

What you should see: under heavy load coalescing cuts interrupts per command several-fold for a few microseconds of added latency; under light load the threshold is rarely reached, so almost every completion waits for the timer and gains tens of microseconds. That is the coalescing trade-off in one table.

Mapping NVMe queues to CPUs from /proc/interrupts

#!/usr/bin/env python3
"""Summarise which CPU services each NVMe queue vector. Read-only.
Uses /proc/interrupts if present, otherwise a built-in synthetic sample."""
import os, re

SAMPLE = """            CPU0       CPU1
 120:         31          0  IR-PCI-MSIX-0000:01:00.0    0-edge      nvme0q0
 121:     184210          2  IR-PCI-MSIX-0000:01:00.0    1-edge      nvme0q1
 122:          0     179554  IR-PCI-MSIX-0000:01:00.0    2-edge      nvme0q2
"""

def load():
    if os.path.exists("/proc/interrupts"):
        with open("/proc/interrupts") as f:
            return f.read(), "live /proc/interrupts"
    return SAMPLE, "synthetic sample"

def main():
    text, src = load()
    lines = text.splitlines()
    cpus = lines[0].split()
    print(f"source: {src}")
    for line in lines[1:]:
        m = re.search(r"(nvme\d+q\d+)\s*$", line)
        if not m:
            continue
        parts = line.split()
        irq = parts[0].rstrip(":")
        counts = [int(x) for x in parts[1:1 + len(cpus)]]
        total = sum(counts)
        top = max(range(len(counts)), key=counts.__getitem__) if counts else 0
        share = (counts[top] / total * 100) if total else 0.0
        print(f"{m.group(1):10s} irq {irq:>4s}  total {total:10d}  "
              f"mostly {cpus[top]} ({share:5.1f}%)")

if __name__ == "__main__":
    main()

Worked example

Scenario (synthetic). A database team reports that after a platform firmware update, p99 READ latency on the lab SSD jumped from 95 µs to 190 µs at low load, while throughput at high load improved slightly. Nothing else changed in the application.

  1. Frame the question. Latency doubled at low load but not at high load. That pattern smells like something that waits for a batch: coalescing, or interrupt moderation in the platform.
  2. Check NVMe coalescing. nvme get-feature /dev/nvme0 -f 0x08 -H reports Aggregation Time = 1 (100 µs) and Aggregation Threshold = 7 (8 entries). Previously both were 0. Something now sets the feature at boot (a vendor tool in the new image).
  3. Predict. At low load the threshold of 8 is rarely reached; each completion waits up to 100 µs for the timer. Average added latency ≈ up to 100 µs, p99 near the full 100 µs. 95 + ~95 ≈ 190 µs: matches.
  4. Confirm with evidence, not just arithmetic. In a trace (or with the nvme:nvme_complete_rq tracepoint and IRQ timestamps) the CQE write and the MSI-X write are now separated by up to ~100 µs at low load, but back-to-back at high load.
  5. Fix. Set coalescing back to 0, or keep it and set Coalescing Disable on the vectors that serve latency-sensitive queues using feature 09h. Re-measure both loads.
  6. Regression test. Boot-time check that Get Features 08h matches the platform policy; latency SLO test at queue depth 1.

The arithmetic in step 3 is a model, not a measurement. The point is that the hypothesis made a quantitative prediction that the trace could then confirm or refute.

Common mistakes

  • "The interrupt tells the driver which command finished." It does not. The CQE does (CID + SQ Identifier).
  • Using INTMS/INTMC with MSI-X. They are defined for pin-based and MSI interrupts only. Under MSI-X, mask through the table's Vector Control bit or the Function Mask.
  • Assuming vector n = queue n. Linux usually does that; the specification does not require it. Always read IV from the Create I/O CQ command.
  • Reading the coalescing threshold as 1's based. THR=0 means one entry, THR=7 means eight.
  • Reading TIME as microseconds. It is in 100 µs units.
  • Forgetting the CQ head doorbell. If the host never updates the head, the controller eventually sees the CQ as full and stops posting — and, depending on implementation, may stop interrupting or keep re-interrupting.
  • Counting interrupts as completions. With coalescing or with several CQEs arriving before the handler runs, interrupts < completions. Use completion counts, not IRQ counts, for IOPS.
  • Blaming the SSD for a host-side interrupt loss. Prove the interrupt write was missing on the link before blaming the device.
  • Setting Relaxed Ordering on everything in device design. An interrupt write with Relaxed Ordering could pass the CQE write.

Senior engineer insight

  • Every interrupt is a contract between three owners. The OS owns the table contents and affinity, the device owns the decision to fire, the platform owns delivery. When an interrupt goes missing, get all three to show evidence before anyone claims innocence.
  • Interrupt latency belongs to the host. The time from the MSI-X write on the link to the CQ head doorbell is host time. Teams routinely send "slow SSD" bugs to the vendor when the trace shows the device finished in 12 µs and the host took 40 µs to notice.
  • Polling is a CPU purchase. It buys microseconds with whole cores. Use it for the latency tail you can name, not by default.
  • Coalescing is a policy, not a tuning. It should be set deliberately per workload class, documented, and checked at boot.
  • Interrupt affinity follows CPU hot-plug. When a CPU goes offline, its vectors must move or its queues must go quiet. Bugs here show up as timeouts that only occur during CPU hot-plug or power-management transitions.

Lab

Lab 42 — Who gets told? Mapping NVMe completions to CPUs

Objective

Determine which interrupt mechanism your NVMe device uses, map each queue's vector to a CPU, and prove experimentally that I/O submitted from a given CPU is completed via that CPU's vector.

Skills

Reading lspci capabilities, /proc/interrupts, IRQ affinity, NVMe Get Features; designing a disambiguating experiment.

Safety

Safe lab Read-only inspection plus reads with fio against a raw device using --readonly. Do not run write workloads against a device holding data. The optional challenge that changes coalescing is a Caution lab: it alters device behaviour until reset; use a test device.

Hardware required

Any Linux machine with an NVMe SSD. A spare test SSD for the challenge.

Software required

pciutils (lspci), nvme-cli, fio, util-linux (taskset), Python 3.

Input

The device's BDF (e.g. 0000:01:00.0) and its block device (e.g. /dev/nvme0n1).

Expected output

A table: queue name → Linux IRQ → MSI-X index → CPU(s) → observed counter delta during a pinned read workload.

Background

Linux allocates one I/O queue pair per CPU (or per CPU group) and assigns MSI-X vectors with managed affinity. The admin queue uses vector 0.

Step 1 — Identify the mechanism

Record MSI-X Count and Enable state, MSI Enable state, and whether DisINTx is set.

Step 2 — Snapshot the vector map

Step 3 — Pinned experiment

grep nvme0q /proc/interrupts > before.txt

Observation

Which vector's counter moved, and in which CPU column? Roughly how many interrupts per completed I/O (fio reports I/O count)?

Questions

  1. Why did only one vector's counter move significantly?
  2. If interrupts per I/O is noticeably below 1.0 at iodepth=1, what could explain it?
  3. What would you expect if the device were running in MSI mode with a single vector?

Challenge

On a test device only: read Feature 08h, set Aggregation Threshold 7 and Time 1, repeat step 3 at iodepth=1 and iodepth=32, and compare interrupt counts and fio latency percentiles. Restore the original value afterwards (or reset the controller).

Hint

Use the coalescing simulator above to predict the result before you measure. If your device ignores the setting, Get Features may still echo it back.

Solution

1. Linux's block layer maps CPU 2 to the hardware queue whose vector is affined to CPU 2, so submissions from CPU 2 go to that SQ and completions arrive on that CQ's vector, delivered to CPU 2. Other CPUs' counters move only from background I/O.

2. At iodepth=1 every completion is alone, so without coalescing expect ≈1.0. Below 1.0 suggests coalescing is active, or the I/O was completed by polling (io_uring with IOPOLL, poll queues), or some completions were harvested during another interrupt on a shared vector.

3. A single vector would show all I/O completions on one IRQ line and (usually) one CPU, with the driver checking every CQ on each interrupt.

Challenge: at iodepth=1 with THR=7, TIME=1, interrupts per I/O stay near 1.0 but latency rises by up to ~100 µs, because the timer, not the threshold, triggers each interrupt. At iodepth=32 interrupts per I/O fall well below 1.0 with little latency change. Restore the feature to its original value.

What a senior engineer notices

Whether vector 0 (admin) shares a CPU with a busy I/O vector; whether the number of I/O vectors is lower than the number of CPUs (meaning queue sharing); whether the IR- prefix is present (interrupt remapping in the path, which adds a failure point); whether effective affinity differs from requested affinity.

Failure variants

  • All counters frozen while I/O completes: device using polled queues, or interrupts lost and the driver recovering by polling — check dmesg.
  • Counter moves on the wrong CPU: affinity changed by irqbalance on a non-managed vector, or CPU hot-plug moved it.
  • Only INTx in use: MSI-X disabled by a kernel parameter (pci=nomsi) or a platform quirk.

Extension

Repeat with --hipri (io_uring IOPOLL) on a kernel with poll queues configured. Confirm the counter for the polled queue does not move while fio completes I/O.

Model answers

1. Both are posted MWr from the same function; a posted request without RO may not pass an earlier posted request, so the CQE is visible before the interrupt is. With RO on the MSI-X write, the interrupt could pass the CQE, and the handler might read the old Phase Tag, find nothing, and return IRQ_NONE — with the CQE then sitting unnoticed until another interrupt or a timeout.

2. Vector 0 for admin; 8 I/O vectors each shared by two CQs, ideally CQs belonging to sibling CPUs. Each interrupt handler must check both CQs bound to the vector.

3. 3 × 100 µs = 300 µs. Timer granularity, when the timer starts, and firmware scheduling can shift the actual delay.

4. Controller: IEN=0, coalescing, MSI-X Function Mask, per-vector mask (or INTMS for pin/MSI; Interrupt Disable for INTx); PCIe: MSI-X Enable cleared, Bus Master Enable cleared (no memory writes at all); platform: IOMMU interrupt remapping entry invalid; CPU: interrupts disabled, vector masked in LAPIC/GIC, CPU offline.

5. Write INTMS bit 0 (mask); read CQs while phase matches; write CQ head doorbells; write INTMC bit 0 (unmask). If entries arrived during the drain, the controller re-asserts after unmask.

Quiz

  1. How is a legacy INTx interrupt signalled on a PCIe link?

    • A dedicated sideband wire per slot
    • Assert_INTx and Deassert_INTx message TLPs
    • A posted Memory Write to 0xFEE0_0000
    • A DLLP
    Answer and reasoning

    PCIe emulates the level-triggered pins with in-band message TLPs; there are no interrupt wires in a PCIe link.

  2. What is the maximum number of MSI vectors a single function can be granted?

    • 1
    • 8
    • 32
    • 2048
    Answer and reasoning

    MSI allows 1, 2, 4, 8, 16 or 32. 2048 is the MSI-X limit.

  3. Under MSI-X, how should an NVMe driver mask a vector?

    • Write INTMS
    • Write INTMC
    • Set the Vector Control mask bit of that MSI-X table entry
    • Clear CC.EN
    Answer and reasoning

    INTMS/INTMC are for pin-based and MSI only; the host must not use them with MSI-X.

  4. Interrupt Coalescing is set with THR=3, TIME=2. What does that mean?

    • Interrupt after 4 completions or 200 µs, whichever first
    • Interrupt after 3 completions or 2 µs
    • Interrupt after 3 completions and 200 µs
    • Interrupt every 3rd completion only
    Answer and reasoning

    THR is 0's based (3 → 4 entries); TIME is in 100 µs units; either condition triggers.

  5. Which interrupt vector does the Admin Completion Queue use?

    • Vector 0
    • The vector given in Create I/O CQ
    • The last vector
    • Whatever INTMS selects
    Answer and reasoning

    The admin CQ has no create command; it always uses vector 0.

  6. Why does the CPU always see the CQE when the MSI-X interrupt arrives?

    • The interrupt carries the CQE
    • Posted writes from the device without Relaxed Ordering cannot pass earlier posted writes
    • The driver reads CSTS first
    • The controller waits for a completion TLP
    Answer and reasoning

    PCIe ordering rules keep the CQE write ahead of the interrupt write.

  7. Explain why an INTx handler for NVMe is more expensive than an MSI-X handler.

    Model answer

    The INTx line may be shared, so the handler must determine whether its device interrupted (often an MMIO read, a non-posted round trip); it must check every CQ, because one line serves all queues; the level-triggered line must be deasserted by the device before return; and all work lands on one CPU.

  8. A CQ was created with IEN=0. What happens when the controller posts to it, and why would a driver do that?

    Model answer

    The controller posts CQEs but generates no interrupt. Linux uses this for poll queues: a thread spinning on the CQ harvests completions, avoiding interrupt latency.

  9. In a capture you see the CQE write but no interrupt write, yet Linux's counter for that vector increments. What does that tell you?

    Model answer

    Something is inconsistent: either the capture missed the interrupt (analyzer filter, wrong link, trigger window), or another source is incrementing the counter (shared vector, a different device mapped to that IRQ). Verify the capture covers the right link and filter before drawing conclusions.

  10. When does polling beat interrupts, and what does it cost?

    Model answer

    At low queue depth on fast devices where interrupt delivery and wake-up is a large fraction of total latency. It costs CPU: the polling core spins instead of doing other work or sleeping.

Interview questions

  1. Beginner: What is the difference between polling and interrupts?

    Model answer

    Polling: the CPU repeatedly checks for completion, fast reaction, constant CPU cost. Interrupts: the device notifies the CPU, near-zero idle cost, per-event overhead and latency.

  2. Beginner: Name the three PCIe interrupt mechanisms.

    Model answer

    INTx (legacy, emulated via messages), MSI (memory write, up to 32 vectors), MSI-X (memory write, table of up to 2048 vectors).

  3. Intermediate: Why does NVMe benefit from MSI-X more than, say, a SATA AHCI controller?

    Model answer

    AHCI has one command list per port and typically one interrupt; NVMe has many independent queue pairs designed to be per-CPU. MSI-X lets each CQ interrupt its own CPU, keeping the lock-free per-CPU model intact from submission to completion.

  4. Intermediate: What are INTMS and INTMC and when must you not use them?

    Model answer

    NVMe controller registers at 0Ch and 10h that mask/unmask interrupt vectors for pin-based and MSI interrupts. Not to be used when MSI-X is configured.

  5. Advanced: Describe the trade-offs of interrupt coalescing and how NVMe exposes it.

    Model answer

    Fewer interrupts and better CPU efficiency at high load versus added latency at low load. Feature 08h: Aggregation Threshold (0's based count) and Aggregation Time (100 µs units); either triggers. Feature 09h per-vector Coalescing Disable lets latency-sensitive vectors opt out.

  6. Advanced: How could Relaxed Ordering break interrupt delivery semantics?

    Model answer

    If the interrupt write had RO set it could pass the CQE (or data) write, so the handler might see no new CQE; the completion would be stranded until another interrupt or timeout. Devices keep RO off the interrupt write; whether data writes may use RO depends on the CQE write ordering too.

  7. Senior: A customer sees sporadic 30-second NVMe timeouts only during CPU hot-plug tests. Walk through your investigation.

    Model answer

    Hypothesis: interrupts for queues whose CPU went offline are not being re-targeted or queues not quiesced. Senior: "Coalescing (FID 08h) trades latency for interrupt rate with 100 µs timer granularity, which is huge relative to flash latency. On a mixed server I'd leave it off globally, or enable it only on vectors serving throughput queues and set Coalescing Disable (FID 09h) on latency queues — if the driver maps workloads to queues at all, which Linux generally does not. I'd show interrupt rate and p99 at QD1 and QD32 before and after."

Chapter summary

A device tells the CPU that work is done either by being polled or by interrupting. PCIe offers INTx (virtual wire messages, shared, level-triggered), MSI (a memory write with up to 32 vectors) and MSI-X (a memory write with a per-vector table of up to 2048 entries). NVMe binds each completion queue to an interrupt vector at creation time (IV, IEN), uses vector 0 for the admin CQ, and benefits strongly from MSI-X because each per-CPU CQ can notify its own CPU. Coalescing (Feature 08h, threshold and 100 µs time) reduces interrupt rate at the cost of latency, and can be disabled per vector (Feature 09h). Polling avoids interrupts entirely for latency-critical I/O. INTMS/INTMC exist only for pin-based and MSI modes. The interrupt write is posted and ordered behind the CQE, and in a trace it is the small MWr to the interrupt window right after the CQE.
