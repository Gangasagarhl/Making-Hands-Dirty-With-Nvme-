Chapters 14 and 51 taught the ordering table, Relaxed Ordering, ID-Based Ordering and the NVMe completion-path proof. This module pushes ordering to where real systems break it: multiple paths, queues placed in device memory, write-combining CPU mappings, peer-to-peer transfers, Root Complex commit order and validation methods that can see reordering an analyzer cannot.

Orientation

PCI Express (PCIe) ordering is a promise about TLPs that travel the same path, in the same direction, in the same Traffic Class. Everything interesting in this module happens at the edges of that promise: when the data and the flag take different paths, when the CPU reorders before PCIe ever sees the stores, when a Root Complex exploits Relaxed Ordering (RO) internally, or when the producer and the consumer are both devices. You will learn to state, for any producer/consumer pair, which ordering domain carries the guarantee — CPU, PCIe fabric, Root Complex, or nobody — and to design tests that observe the result in memory rather than on the wire.

The ordering table (rows A–D, columns 2–5), the "No / Yes / Y/N" meaning, RO and IDO semantics, No Snoop and the NVMe submission and completion paths are in Chapter 14 — PCIe Ordering and Chapter 51 — PCIe Ordering (advanced), including the A2a, B2a, D2a and D5b cell names this module uses. Posted versus non-posted: Chapter 12. Do not continue until "a CQE with RO = 0 cannot pass data written with RO = 1" is obvious to you.

Where this goes next: flow control and the buffer dependencies behind deadlock in Module 17; MSI-X delivery in Module 19 — MSI and MSI-X; the Controller Memory Buffer in the NVMe architecture chapters (Chapter 23).

Kid story

Two friends send you things. Mia sends a parcel by the green road, and then a postcard by the same green road saying "your parcel has arrived". On the green road, things never overtake each other, so when the postcard comes, the parcel is already there.

But one day Mia sends the parcel by the green road and the postcard by the blue road. The blue road is sometimes faster. Now the postcard can arrive first, and you run to the door and find nothing. Nobody broke a rule: each road kept its own order. The mistake was using two roads and expecting them to keep order between them.

And sometimes the post office is allowed to sort parcels marked "no hurry" in any order — that is fine for parcels, but never put that sticker on the postcard.

Analogy boundary

What it represents. Ordering is per path; two paths give no mutual guarantee; a relaxation sticker is safe on data and unsafe on the notice.

What it hides. In PCIe the "road" is the sequence of components and the direction and Traffic Class together. It also hides that ordering is defined among categories (posted, non-posted, completion) with deliberate exceptions that keep the fabric deadlock-free, and that the last step — the Root Complex making writes visible in memory — is a platform mechanism, not a link rule.

Where it misleads. Roads suggest that the problem is speed. In PCIe the problem is permission: a component that is allowed to reorder may do so only rarely, under load, on one platform. Tests that pass on one machine prove nothing about the permission. And the friend in the story is one sender; in real systems the CPU itself may reorder stores before they reach any road.

Mechanism

The mechanism of ordering is the sum of the domains. Follow a WRITE-path proof for an NVMe submission queue placed in the SSD's Controller Memory Buffer (CMB), a case Chapter 14 did not cover.

  1. Driver writes the SQE into the CMB. The CPU (who) stores 64 bytes to a CMB address inside BAR2 (what), mapped write-combining (where). Evidence: on the link, one or more MWr TLPs from the Root Complex to the SSD, possibly merged, possibly in a different order than the program stores.
  2. Driver issues a write barrier. The CPU drains its write-combining buffers before later stores (what), inside the core (where). Evidence: none on the link; its absence shows as reordering in step 4.
  3. Driver writes the SQ tail doorbell. The CPU stores to BAR0 + 0x1008 (uncacheable). Evidence: MWr32 on the link.
  4. The fabric keeps the order. All of these are posted writes from the Root Complex to the SSD on one path in TC0 with RO clear: rule A2a forbids the doorbell passing the SQE writes. Evidence: link order SQE MWr(s) then doorbell MWr.
  5. The SSD consumes. The controller reads the SQE from its own memory — no PCIe read at all. Its internal design must not let the doorbell's effect overtake the CMB write it received earlier. Evidence: none on the link; a stale SQE shows as a command error.

Compare with the host-memory SQ of Chapter 14: there the SQE and doorbell take different paths (coherent memory and MMIO), so the CPU domain plus a snooped device read carries the guarantee. With a CMB, both writes go down the same PCIe path, so the fabric carries it — but write-combining puts the CPU domain back in play. Moving a data structure changes which domain you rely on. Derived

The ladder for "ordering domains"

Each road keeps its own order; two roads keep none between them; "no hurry" stickers go on parcels, never on postcards.

PCIe orders TLPs on one path, direction and TC; the CPU orders its own stores only with barriers; the Root Complex decides memory visibility; devices must emit in a rule-consistent order.

Per-port class queues with bypass; Root Complex write tracking (where RO lets independent writes commit out of order); CPU store and WC buffers; device DMA engines.

The PCIe specification does not describe CPU memory models, write-combining, or how a CPU's MMIO stores are ordered before they become TLPs. It does not guarantee any order between TLPs on different paths, from different Root Ports, or in different TCs. It does not say how an NVMe controller must order a CMB write against a later doorbell internally (that follows from the NVMe queue model and good design). Check in the specification: the full ordering table with footnotes for your revision, the update ordering and granularity rules (how large a write is guaranteed to become visible as a unit), and any new request types with their own ordering rules.

Never assume: that a passing test on one platform validates RO; that link order equals memory order; that two devices behind different Root Ports are ordered; that a WC mapping preserves program order.

Why RO helps at all: a Root Complex that must commit writes in order stalls every later write behind one that misses in the IOTLB or conflicts in a cache. With RO on independent data writes it can commit each as soon as its translation is ready. The benefit therefore appears mostly with the IOMMU on and buffers spread over many pages; on a platform without that bottleneck RO may change nothing measurable. Implementation-dependent

MSI-X is a posted write to the interrupt address window, but it ends in the interrupt controller, not in DRAM. PCIe orders it behind earlier writes on the link; the platform must ensure the interrupt is not delivered before those writes are visible. That is a Root Complex responsibility outside the PCIe ordering table. Implementation-dependent

Completion and error interactions: ordering violations produce no PCIe error. The only errors in this area come from deadlock-avoidance failures (which appear as hangs, timeouts and eventually Completion Timeout or link recovery) and from attributes set without enable (which a receiver may not detect at all). Ordering bugs are found by their effects in memory.

Happens about once per million interrupts; only on one platform; never with polling.

Analysis. The link order is right and the attributes are right, so the PCIe fabric is not at fault. Hypotheses: (a) a polling thread (or another CPU servicing a shared vector) consumed slot 12 between delivery and the handler's read, so the CQ legitimately looked empty — check whether the driver uses polled queues alongside interrupts; (b) the platform delivered the interrupt before the CQE write was visible (an interrupt-ordering erratum in the Root Complex); (c) the handler read a cached stale copy (No Snoop misuse or a missing read barrier on a weakly ordered CPU). Disambiguate: count consumed CQEs per vector and per poller (a); run with all queues interrupt-only and pin the vector to one CPU (a disappears if it was the cause); check the CQE's NS attribute and the driver's barrier (c); a memory-side timestamp test with an exerciser writing a counter then interrupting (b). Without that, confidence in any single hypothesis is low — and saying so is the senior answer.

Beginner lab — name the domain

Objective. For six scenarios, state whether the order is guaranteed and by which domain. Prerequisites. Chapter 14. Setup. Example system.

Procedure. (a) SSD writes data then CQE, both RO = 0. (b) Same, CQE RO = 1. (c) CPU writes SQE to host memory then doorbell with writel. (d) CPU writes SQE to a WC CMB then doorbell, no fence. (e) SSD writes data to a GPU BAR, then a flag to host memory. (f) SSD (TC0) writes data; a second function of the SSD writes a flag in TC1.

Solution

(a) Guaranteed: PCIe A2a + Root Complex commit + CPU read barrier. (b) Not guaranteed: RO on the flag permits passing. (c) Guaranteed by the CPU domain (barrier in writel) plus snooped read. (d) Not guaranteed: WC may reorder before PCIe. (e) Not guaranteed: two paths. (f) Not guaranteed: different TCs have no ordering relationship.

Observations / questions. Which cases would an analyzer on the SSD's link flag? Expected reasoning. Only (b) shows an attribute problem on the link; (d) shows wrong order on the link; (e) and (f) look fine on any single link. Extension. Re-do (e) with the flag written to GPU memory as well; what changes?

Intermediate lab — a Root Complex that exploits RO

Objective. Simulate commit order and count stale reads for different attribute policies. Setup. Save as ro_commit.py.

#!/usr/bin/env python3
"""Toy Root Complex commit model. Writes arrive in link order; each needs a
translation delay; RO writes may commit as soon as translated, non-RO writes wait
for every earlier write. A consumer polls the flag (CQE) and checks the data.
Standard library only; a teaching model, not a real Root Complex."""
import random

def run(cqe_ro, data_ro=True, trials=20000, chunks=16, seed=3):
    rnd = random.Random(seed)
    stale = 0
    for _ in range(trials):
        t, commits = 0.0, []
        writes = [("data", data_ro)] * chunks + [("cqe", cqe_ro)]
        prev_commit = 0.0
        for kind, ro in writes:
            t += 36                                   # link arrival spacing (ns)
            delay = 2000 if rnd.random() < 0.02 else 50   # rare IOTLB miss
            ready = t + delay
            commit = ready if ro else max(ready, prev_commit)
            prev_commit = max(prev_commit, commit)
            commits.append((kind, commit))
        cqe_time = commits[-1][1]
        if any(k == "data" and c > cqe_time for k, c in commits):
            stale += 1                               # CPU sees CQE before all data
    return stale / trials

if __name__ == "__main__":
    print(f"data RO, CQE strict : stale fraction {run(cqe_ro=False):.4f}")
    print(f"data RO, CQE relaxed: stale fraction {run(cqe_ro=True):.4f}")
    print(f"all strict          : stale fraction {run(cqe_ro=False, data_ro=False):.4f}")

Procedure. Run it; change the miss probability and the number of chunks. Questions. (1) Why is the strict-CQE case always zero even though data is relaxed? (2) Why does the relaxed-CQE stale fraction grow with chunks? (3) What does this model leave out?

Solution

(1) A non-RO write commits no earlier than every earlier write (the max over prev_commit), so the CQE is visible only after all data. (2) More data writes means more chances that one of them suffers a miss and commits after the relaxed CQE. (3) Real Root Complexes have bounded buffers (credit back-pressure), CPU-side reordering and caches, and their actual RO policy is unknown; the model shows the permission, not any platform's behaviour.

Extension. Add a strict MSI-X after the CQE and a consumer that reads the CQE only on interrupt; show the interrupt is never early when MSI-X is strict.

Advanced lab — design an ordering torture test

Objective. Design a test that detects reordering in memory. Prerequisites. The intermediate lab. Setup. A PCIe exerciser or an FPGA endpoint able to write patterns with chosen attributes (or an NVMe controller under test with debug hooks), host software that checks memory.

Procedure. (1) Device writes N data blocks, each stamped with a generation number, then a flag holding the generation. (2) Host spins on the flag; on change, reads all blocks and checks every stamp equals the flag's generation. (3) Repeat millions of times under IOMMU on/off, scattered/huge pages, RO on/off on data, RO on/off on the flag, local/remote NUMA. (4) Record failures per configuration.

Questions. Which configurations must show zero failures for a compliant platform? Which may show failures without any rule being broken?

Solution

Zero failures required whenever the flag write has RO = 0 and is on the same path and TC as the data, and the host uses a read barrier between flag and data reads. Failures are permitted (not a platform bug) when the flag has RO = 1. A failure in a required-zero configuration is a platform or device defect; capture the link to show the attribute and order were correct, which moves the fault to the Root Complex. Include a CPU-architecture variable (x86 versus Arm) to exercise the host barrier.

Extension. Add a second device writing to the same memory region to test IDO behaviour on a platform where IDO is enabled.

Senior forensic lab — peer-to-peer stale data

Objective. Diagnose a cross-path ordering assumption. Prerequisites. All previous labs.

Setup (synthetic evidence). A storage-to-accelerator pipeline: the Lab SSD reads data from flash and DMA-writes it directly into an accelerator's BAR (peer-to-peer through a switch). The NVMe CQE lands in host memory. A host thread sees the CQE and tells the accelerator to start. About 1 in 105 jobs compute on partially old data. Captures: on the switch's downstream port to the accelerator, all data MWrs precede, in time, the CQE MWr seen on the switch's upstream port. RO is disabled everywhere.

Questions. (1) Is a PCIe rule broken? (2) Where can the data still be in flight when the accelerator starts? (3) Propose two fixes.

Solution

(1) No. Data (SSD → switch → accelerator) and CQE (SSD → switch → Root Port → memory) share only the first hop. A2a orders them on that hop; after the switch they diverge, and nothing orders "data visible in the accelerator's memory" against "CQE visible to the CPU" plus "CPU's doorbell to the accelerator". The timestamps on two different links do not prove visibility inside the accelerator. (2) In the accelerator's ingress buffers or internal write path when its own start command (a later MMIO write from the CPU via a different path) arrives. (3) Have the accelerator flush: before starting, it performs a read of its own memory or a defined internal fence; or have the host issue a read to the accelerator that is ordered behind the SSD's writes on the accelerator's ingress port (only valid if the topology makes them the same path); or have the SSD write the "done" flag into the accelerator's memory itself, after the data, on the same path (A2a then applies end to end). Confidence: high on mechanism; the specific fix depends on the accelerator's documented ordering model.

Extension. Draw the topology and mark, for each hop, which TLPs share it.

Debugging

Pattern 1 — Stale data on one platform only

SymptomRare checksum failures on one server model; none elsewhere.
Possible causesRO on CQE/MSI-X exploited by that Root Complex; Root Complex erratum; NS on a coherent buffer.
EvidenceAttr bits on CQE and MSI-X writes; RlxdOrd/NoSnoop enables; kernel quirks for that Root Port.
First checkCapture: RO/NS on the CQ address range.
Second checkDoes disabling RO (lab) remove the failures?
Disambiguating experimentTorture test with RO on data only versus on flag.
Likely conclusionDevice sets RO on the flag, or a platform defect if attributes are correct.
ConfidenceHigh once the attribute is seen.

Pattern 2 — Invalid or garbage commands with a CMB

SymptomSporadic Invalid Opcode / Invalid Field statuses only when SQs are in the CMB.
Possible causesMissing store fence after WC writes; controller letting doorbell overtake CMB write internally.
EvidenceLink order of SQE MWrs versus doorbell.
First checkDoes any doorbell precede the last SQE write on the link?
Second checkDriver code between SQE copy and doorbell.
Disambiguating experimentMap the CMB UC instead of WC; if errors stop, it is the CPU domain.
Likely conclusionDriver fence bug if the link order is wrong; controller bug if link order is right.
ConfidenceHigh.

Pattern 3 — Throughput drop after a kernel update, no errors

SymptomREAD throughput down 10–20% after a kernel or firmware update.
Possible causesNew quirk clearing RO; changed IOMMU defaults; MPS change.
EvidenceRlxdOrd before and after; Posted credit gaps; IOMMU mode.
First checkDiff lspci -vvv before/after.
Second checkCredit-return gaps aligned with page changes.
Disambiguating experimentHuge pages or IOMMU pass-through in a lab.
Likely conclusionRO disabled under IOMMU translation pressure.
ConfidenceMedium.

Pattern 4 — "Spurious" interrupts

SymptomInterrupt handler finds no new CQE.
Possible causesMSI-X before CQE on the link; RO on MSI-X; concurrent poller; shared vector; platform interrupt ordering issue.
EvidenceLink order and attributes; driver queue configuration.
First checkLink order and RO bits of CQE and MSI-X.
Second checkAre polled queues or shared vectors in use?
Disambiguating experimentInterrupt-only queues, one vector per queue, pinned.
Likely conclusionDevice emission order bug if the link shows MSI-X first; otherwise software or platform.
ConfidenceMedium.

Pattern 5 — Hang under heavy mixed traffic

SymptomSystem hangs with many outstanding reads; Completion Timeouts follow.
Possible causesA component that does not let posted writes or completions pass blocked non-posted requests (deadlock-avoidance violation); credit misconfiguration.
EvidenceLink: posted traffic stops while NP is blocked; credit DLLPs absent.
First checkWhich class stopped first on which link?
Second checkIs a P2P or bridge path involved?
Disambiguating experimentRemove the switch or the P2P flow; reproduce with an exerciser holding NP credits at zero.
Likely conclusionComponent violating A3/A4/D3/D4 "must be able to pass".
ConfidenceMedium; needs multi-point capture.

Interview

Beginner

  1. What is the scope of PCIe ordering?

    Model answer

    TLPs on the same path, same direction, same Traffic Class.

  2. Can a CQE pass the data before it?

    Model answer

    Not if the CQE has RO clear (A2a) and both are on the same path and TC.

  3. Are an upstream and a downstream TLP ordered?

    Model answer

    No; opposite directions have no ordering relationship.

  4. Does No Snoop change ordering?

    Model answer

    No; it changes coherence/visibility, not the ordering rules.

  5. Why can a register read act as a flush?

    Model answer

    The read cannot pass earlier posted writes on the path (B2a), so its completion implies they arrived.

Intermediate

  1. How does a CMB SQ change the submission-path proof?

    Model answer

    SQE and doorbell both become posted MMIO writes on one PCIe path, so A2a orders them — provided the CPU emits them in order (WC needs a fence).

  2. Why is RO "safe for data, dangerous for flags"?

    Model answer

    RO lets the TLP carrying it pass earlier writes; data blocks are independent, but a flag must follow the data.

  3. What does IDO assume?

    Model answer

    That producer/consumer relationships are within one source ID; data, flag and interrupt must carry the same ID.

  4. Why do different TCs break ordering?

    Model answer

    They may map to different VCs with independent queues; the rules apply within a TC only.

  5. Why can an analyzer not prove memory order?

    Model answer

    It sees link order; the Root Complex's commit order and the CPU's view happen after the link.

Advanced

  1. Explain why posted writes must be able to pass blocked reads.

    Model answer

    To break buffer-dependency cycles: a write that would free resources must not wait behind a read that waits for those resources.

  2. Where does RO pay off and why?

    Model answer

    In Root Complexes where writes have variable commit latency (IOMMU misses, cache conflicts): independent writes need not wait behind a slow one.

  3. Is MSI-X delivery ordered after the CQE by PCIe alone?

    Model answer

    PCIe orders the TLPs on the link; the platform must not deliver the interrupt before earlier writes are visible — a Root Complex responsibility.

  4. Give an ordering hazard in P2P NVMe.

    Model answer

    Data to a peer BAR and a completion flag to host memory diverge after a switch; no guarantee the peer sees data before the host acts on the flag.

  5. What does a zero-length read do?

    Model answer

    Its completion cannot be returned before earlier posted writes on that path reached the completer, so it flushes them without reading data.

Senior

  1. When would you approve enabling RO for an NVMe controller?

    Model answer

    When captures prove RO is never set on CQE or MSI-X writes, the platform is not under an RO quirk, memory-side torture tests pass across target platforms, and the throughput benefit is measured.

  2. How do you validate ordering on a new Root Complex?

    Model answer

    Exerciser-driven memory-side tests with all attribute combinations, IOMMU modes, page sizes, NUMA placement, multiple requesters and interrupts; deadlock tests with NP credits held at zero.

  3. A team plans CMB queues with a user-space driver. Review points?

    Model answer

    Memory type of the mapping, fences after SQE copy, doorbell mapping, controller internal ordering, and behaviour across CPU architectures.

  4. Why is "it works on our server" weak evidence for ordering?

    Model answer

    Reordering is a permission; a platform may never exercise it. Only proof from the rules plus multi-platform testing is meaningful.

  5. How would you explain the four domains to a firmware team?

    Model answer

    CPU ordering ends at the Root Complex; PCIe ordering applies per path; the Root Complex decides visibility; the device must emit in order. A bug lives where a guarantee is assumed but no domain provides it.

Quiz

  1. Data and flag are written by the SSD to two different peer devices through one switch. Ordered?

    • Yes, same requester
    • No, the paths diverge
    • Only with RO
    Answer and reasoning

    Ordering holds along a path; after divergence there is no relationship.

  2. A CQE has RO = 0 and the data before it RO = 1. May the CQE pass the data?

    • No
    • Yes
    • Only with IDO
    Answer and reasoning

    RO describes the later TLP; the CQE is not relaxed.

  3. Which domain orders an SQE in host memory before the doorbell?

    • PCIe A2a
    • Root Complex commit
    • The CPU (barrier before MMIO)
    Answer and reasoning

    The SQE is a coherent memory store and the doorbell an MMIO store: different paths; the CPU barrier orders them.

  4. On the link, the doorbell appears before the last SQE write into a WC-mapped CMB. Who is at fault?

    • The switch
    • The CPU-side code (missing fence)
    • The controller
    Answer and reasoning

    The link carries TLPs in the order received from the CPU; the order was already wrong.

  5. TLPs in TC0 and TC1 from the same device:

    • Ordered by A2a
    • Ordered only if RO = 0
    • Have no ordering relationship
    Answer and reasoning

    Ordering applies within a Traffic Class.

  6. Why may RO increase throughput only with the IOMMU on?

    Model answer

    Translation misses create variable per-write commit latency; strict ordering makes later writes wait; RO removes the wait for independent writes.

  7. Give two causes of "interrupt but no CQE" that are not PCIe ordering violations.

    Model answer

    A concurrent poller or shared-vector handler consumed the entry; a CPU-side stale read (missing barrier or non-snooped CQE).

  8. What must a torture test observe that an analyzer cannot?

    Model answer

    The order in which writes become visible in memory to the consumer.

  9. Why does IDO break if the CQE carries the PF's ID and the data a VF's ID?

    Model answer

    With IDO, a TLP may pass earlier posted TLPs with a different ID; the CQE could pass the VF's data.

Teach-back

  1. To a child: why the postcard must use the same road as the parcel.

    Model explanation

    "On one road nothing overtakes, so the postcard always arrives after the parcel. On two roads, the postcard might be faster, and you'd go to the door too early."

  2. To a junior engineer: how moving the SQ into the CMB changes who guarantees ordering.

    Model explanation

    "With the SQ in host memory, the SQE and doorbell take different paths, so the CPU barrier in writel is what orders them. With the SQ in the CMB, both are posted writes down the same PCIe path, so PCIe keeps their order — but only if the CPU sent them in order, which with a write-combining mapping needs a fence."

  3. To a senior engineer: how you would decide whether a stale-data bug is a PCIe ordering bug.

    Model explanation

    "Write down producer, consumer, data, flag and the path of each. If the data and flag share a path and TC and the flag is not relaxed, PCIe guarantees the order on the link; check a capture for attribute and order. If those are right, the fault is in the Root Complex commit or the CPU side, and only a memory-side test will show it. If they don't share a path, it was never an ordering guarantee — it's a design assumption."

Mastery gate

Do not consider this module mastered until you can:

  • explain the four ordering domains and the scope of the PCIe rules
  • diagram the CMB submission path and the completion path with the domain that orders each step
  • identify in a trace: relaxed flags, wrong link order from the CPU, and cases where correct link order proves nothing
  • debug stale data, garbage commands and spurious interrupts to a domain
  • distinguish ordering from tag matching, from coherency (No Snoop), and from flow-control stalls
  • cite the PCI Express Base Specification — Transaction Ordering — and the NVMe Base Specification 2.4 Controller Memory Buffer definition
