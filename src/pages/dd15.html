Chapter 15 took the Data Link Layer apart packet by packet: sequence numbers, LCRC, Ack/Nak, replay, DLLP types. This module looks at the layer as a whole service: what it promises the Transaction Layer, how it comes up and goes down, how it reports its state to software, where its responsibility ends at switches and retimers, how it shapes throughput without ever logging an error, and how its evidence separates a physical fault from a logic fault.

Orientation

The Data Link Layer (DLL) turns one physical link into a reliable, in-order pipe for Transaction Layer Packets (TLPs) and carries its own small control packets, Data Link Layer Packets (DLLPs), for acknowledgement, flow control and power management. Seen from above, it offers exactly two things: "DL_Up — you may send, and what you send will arrive intact and in order at the neighbour", or "DL_Down — nothing gets through". Everything this module covers is about those two states, the transitions between them, and the quiet costs of keeping the promise.

Sequence numbers, LCRC, the replay buffer, Ack/Nak rules, REPLAY_NUM, DLLP formats and type encodings, the DL_Inactive/DL_Init/DL_Active states, and four traces are in Chapter 15 — DLLP. The layer model: Chapter 7. Link training and Recovery: Chapter 8 and Chapter 9. Errors and AER: Chapter 45, Chapter 46.

Where this goes next: the replay machine in full detail in Module 16 — DLLP and Replay; credits in Module 17 — PCIe Flow Control; error reporting in Module 18 — AER; equalization when the root cause is physical in Chapter 54.

Kid story

Two castles are joined by a rope bridge, and a porter stands at each end. The porters' only job is to get every basket across safely and in the right order. Before any baskets cross in the morning, the porters wave flags to each other: "Are you there?" "Yes! I can take this many baskets." Only then does the bridge open.

Each basket gets a number and a seal. The far porter shouts back "got up to 12!" and the near porter throws away his spare copies. If a seal is broken, he shouts "send again after 11!" The kings in the castles never hear any of this — they only see baskets arriving.

If the bridge snaps, the porters stop. Everything still on the near side waits; anything the king was expecting back across the bridge will never come. The king only finds out because he waited too long.

Analogy boundary

What it represents. A per-bridge (per-link) reliability service; a start-up handshake before traffic (flow-control initialisation); cumulative acknowledgements; that the kings (software and the Transaction Layer) see only results; and that link loss is discovered by the layers above through missing answers.

What it hides. A journey across several bridges has a separate pair of porters on each bridge (each switch port has its own DLL). Some helpers on a bridge — retimers — only re-carry the rope's vibrations and are not porters at all. The porters also carry messages about how much room is left in the castle store (flow-control credits) and about going to sleep (power management).

Where it misleads. A snapped bridge sounds rare and obvious; in PCIe "DL_Down" also happens on purpose (resets, hot-plug, disable) and the layers above must tell expected from surprise. And the porters are not allowed to fix a broken basket; they only resend. If the near porter's own copy is wrong, nobody below the Transaction Layer will notice — that is what end-to-end checks are for.

Mechanism

The lifecycle of one DLL hop, from power-on to a surprise loss. Each step: who acts, what changes, where, evidence.

  1. DL_Inactive. After reset, both DLLs (who) hold no state and discard the replay buffer (what), inside each port (where). Evidence: Link Status Data Link Layer Link Active = 0; nothing on the link but training ordered sets.
  2. LinkUp. The LTSSM reaches L0 and reports LinkUp = 1. Evidence: analyzer shows the end of training, then the first DLLPs.
  3. Feature exchange (optional, 4.0+). Ports that support it exchange Data Link Feature DLLPs announcing optional features (for example Scaled Flow Control). Evidence: feature DLLPs; Data Link Feature capability registers record the remote side's features. Version-dependent
  4. Flow-control initialisation. DL_Init: InitFC1 then InitFC2 for Posted, Non-Posted and Completion of VC0. Evidence: InitFC DLLPs; credit values visible on the analyzer only.
  5. DL_Active. Initialisation completes; the DLL reports DL_Up. Evidence: Data Link Layer Link Active = 1 (if reporting capable); hot-plug ports set Data Link Layer State Changed; the first TLP (typically a configuration request from the Root Port).
  6. Steady state. Every TLP gets a sequence number and LCRC, waits in the replay buffer until Acked; UpdateFC returns credits; PM DLLPs negotiate low-power states. Evidence: Acks march forward; Naks and replays when errors occur; correctable AER bits.
  7. Unrecoverable link problem. If the Physical Layer loses the link (LinkUp = 0), the DLL goes to DL_Inactive and reports DL_Down. Replay buffer contents are discarded. Evidence: Link Active = 0; the Downstream Port logs Surprise Down if the loss was not directed.
  8. Consequences above. Non-posted requests that crossed (or were waiting for) this link never complete: requesters log Completion Timeouts; CPU reads return synthesised values; the NVMe driver resets. Evidence: AER messages and kernel logs, in that order.

The specification does not say how big a replay buffer must be, how many replays per second are acceptable, how long a link may stay in Recovery before software should care, or how an NVMe driver should react to DL_Down. It does define timer formulas and limits that you must read rather than remember (replay timer, AckNak latency), the exact point at which DL_Up is signalled during initialisation, which ports must support Link Active and Surprise Down reporting, and the Flit Mode retry rules.

Never assume: that a quiet AER means a quiet link (masked bits, the other end's registers, or the counter being on a switch port); that L0 implies DL_Up; that a retimer logs errors; that Flit Mode behaves like non-Flit with larger numbers.

The replay buffer turns latency into a throughput limit. The transmitter may only have as many bytes unacknowledged as its buffer holds; if the Ack round trip grows (a retimer adds tens of nanoseconds each way, long channels add more, the receiver coalesces Acks), the buffer fills before Acks return and the transmitter idles — with no error anywhere.

Tmax = min( BWlink , Breplay / RTTack )
Tmax
maximum sustainable TLP throughput in one direction, bytes per second
BWlink
usable link bandwidth after encoding, bytes per second (≈ 7.88 GB/s for Gen4 x4 before TLP overhead)
Breplay
replay buffer capacity in bytes of TLP traffic
RTTack
time from a TLP's transmission to the processing of the Ack that covers it, in seconds

Derived With a 4 KB replay buffer and a 400 ns Ack round trip: 4,096 / 400 ns ≈ 10.2 GB/s → not limiting at Gen4 x4. Add two retimers and a receiver that coalesces Acks to 700 ns: 4,096 / 700 ns ≈ 5.9 GB/s → now the DLL caps throughput below the link rate. The same SSD and host, with a longer channel, get slower and log nothing.

Ordering: the DLL delivers TLPs to the peer's Transaction Layer in transmission order; a replay re-sends in the same order. The Transaction Layer's ordering rules operate on top of that in-order pipe. Completion: an Ack is not a completion; a posted write has an Ack and nothing else.

Link loss and transactions: at DL_Down, every non-posted request whose completion would have crossed this link becomes a future Completion Timeout at its requester; posted writes still in the replay buffer are lost silently. That is why the first abnormal event in an NVMe "device disappeared" incident is usually at the DLL or Physical Layer of one hop, milliseconds before the first Completion Timeout.

Beginner lab — which side logs what

Intermediate lab — Ack latency, replay buffer and bit errors

Objective. Quantify DLL-imposed throughput limits. Setup. Save as dll_window.py.

#!/usr/bin/env python3
"""DLL throughput model: replay-buffer window, Ack round trip, and replays caused
by TLP errors. Standard library only; illustrative numbers, not a link simulator."""

LINK_BPS = 7.88e9           # Gen4 x4, bytes/s after 128b/130b
TLP_BYTES = 282             # 256 B MWr64 + header + seq + LCRC + framing

def throughput(replay_buf, ack_rtt_ns, tlp_error_rate=0.0, nak_rtt_ns=None):
    """Return sustained bytes/s of TLP traffic in one direction."""
    window = replay_buf / (ack_rtt_ns * 1e-9)        # bytes/s the window allows
    base = min(LINK_BPS, window)
    if tlp_error_rate:
        nak_rtt = (nak_rtt_ns or ack_rtt_ns) * 1e-9
        # each error costs a Nak round trip plus re-sending the unacknowledged window
        resend = min(replay_buf, base * nak_rtt)
        cost_s = nak_rtt + resend / LINK_BPS
        errors_per_s = base / TLP_BYTES * tlp_error_rate
        busy = errors_per_s * cost_s
        base *= max(0.0, 1 - busy)
    return base

if __name__ == "__main__":
    print("buffer  ackRTT   errors    throughput")
    for buf, rtt, err in [(4096, 400, 0), (4096, 700, 0), (8192, 700, 0),
                          (4096, 400, 1e-4), (4096, 400, 1e-3), (4096, 700, 1e-3)]:
        gbs = throughput(buf, rtt, err) / 1e9
        print(f"{buf:6d} {rtt:6d}ns {err:8.0e}  {gbs:6.2f} GB/s")

Procedure. Run it. Find the Ack round trip at which a 4 KB buffer starts limiting Gen4 x4. Then the TLP error rate at which throughput loses 5%.

Questions. (1) Why does doubling the buffer fix the 700 ns case? (2) Why do errors hurt more when the Ack round trip is long? (3) Which of these effects produce AER errors?

Solution

The knee is where 4,096 B / RTT = 7.88 GB/s, i.e. RTT ≈ 520 ns. (1) The window doubles, 8,192 / 700 ns ≈ 11.7 GB/s, above the link rate. (2) Each error costs a Nak round trip and a re-send of everything unacknowledged, both proportional to RTT. (3) Only the error-driven replays (Bad TLP at the receiver, possibly Bad DLLP and timeouts); the window limit produces none. The 5% loss point depends on parameters; with 4 KB and 400 ns this model loses about 2% at a 10−3 TLP error rate and 5% at roughly 2×10−3 — far above what a healthy link shows, which is why healthy links lose nothing measurable.

Extension. Add Ack coalescing: the receiver sends one Ack per N TLPs; express RTT as a function of N and find the N that starts limiting throughput.

t=-120.0s   pcieport 0000:00:01.1: AER: Corrected error: Receiver Error (x2)

Procedure. Sort by time; label each line with its layer (Physical, DLL, Transaction/AER, NVMe); mark the first abnormal event; explain the I/O timeout at +31 s.

Solution

Order: −120 s Receiver Errors (Physical, early warning) → 0 s burst of Receiver Errors (Physical) → +3 ms Link Active 0 (DLL: DL_Down) → +4 ms Surprise Down (DLL/AER) → +90 ms link reset by recovery → +95 ms NVMe reset (CSTS all ones) → +0.6 s queues recreated → +31 s an I/O timeout. The first abnormal event visible is the Receiver Error trend at −120 s; the decisive one is the burst at 0 s. The +31 s timeout is a consequence: a command outstanding at the link loss that the driver's own timer (≈ 30 s) eventually aborted, or a request lost across the reset. Investigate the channel (slot, riser, retimer, power) using the Receiver Error history.

Extension. Rewrite the timeline as the kernel would if the Root Port did not support Surprise Down reporting. What evidence disappears?

Senior forensic lab — physical or logic, which segment?

Objective. Localise a fault using both ends of two hops. Setup (synthetic evidence). Root Port 00:01.1 → switch upstream port 02:00.0; switch downstream port 03:00.0 → Lab SSD 04:00.0. A retimer sits between 03:00.0 and the SSD. Over 24 hours:

  • 00:01.1: CESta clean. 02:00.0: CESta clean.
  • 03:00.0: CESta Bad DLLP (many), Replay Timer Timeout (some).
  • 04:00.0: CESta Bad TLP (none), Receiver Error (none).
  • Once: 03:00.0 UESta Data Link Protocol Error, link reset.

Questions. (1) Which hop and direction? (2) Physical or logic? (3) What do you do next?

Solution

(1) The 03:00.0 ↔ 04:00.0 hop. 03:00.0 receives bad DLLPs (Bad DLLP is receiver-side) and times out waiting for Acks: the SSD→switch direction is corrupting DLLPs. Yet the SSD's TLPs in that same direction would also be hit by noise, and the switch logs no Bad TLP. (2) Corruption that hits DLLPs but never TLPs on the same lanes is not what random noise does — TLPs are much longer and would be hit more. Combined with one Data Link Protocol Error (CRC good, impossible content), this points to the SSD's DLLP generation logic (or the retimer mishandling DLLP framing) rather than the channel. Confidence: medium. (3) Capture on both sides of the retimer: if DLLPs are already bad at the SSD's pins, it is the SSD; if good at the SSD and bad at the switch, suspect the retimer. Check SSD firmware/PCIe IP errata. Avoid "replace the cable" until the capture says physical.

Extension. Explain why the Root Port's clean registers do not clear the SSD of suspicion, and why 02:00.0's clean registers are irrelevant to this hop.

Debugging

Pattern 1 — Slower after a hardware change, no errors

SymptomThroughput drops after adding a riser, retimer or longer cable; AER clean.
Possible causesReplay-buffer starvation from longer Ack round trip; lower negotiated speed/width; credit return delay.
EvidenceLnkSta speed/width; idle gaps resuming on Acks versus on UpdateFC.
First checkNegotiated speed and width unchanged?
Second checkDo transmit gaps end at Acks?
Disambiguating experimentRemove the retimer/riser; compare Ack RTT.
Likely conclusionDLL window limit.
ConfidenceMedium-high with a capture.

Pattern 2 — Correctable error storms at one end

SymptomRising Bad TLP / Receiver Error counts at one port.
Possible causesMarginal channel in the direction toward the logging receiver; equalization; connector; temperature.
EvidenceWhich side logs receiver bits; per-lane margining; temperature correlation.
First checkRead AER on both ends to fix the direction.
Second checkLane margining or equalization results (Chapter 54).
Disambiguating experimentSwap slot or cable; force a lower speed in a lab.
Likely conclusionPhysical channel in one direction.
ConfidenceHigh if errors follow the slot.

Pattern 3 — Data Link Protocol Error

SymptomUncorrectable DLP, link reset, NVMe controller reset.
Possible causesPeer DLL logic bug (Ack for unsent sequence number), retimer or interposer fault.
EvidenceCapture of the offending DLLP with a valid CRC.
First checkWhich port logged it (the receiver of the bad DLLP)?
Second checkFirmware/IP versions on the peer; recent changes.
Disambiguating experimentCapture without interposer/retimer; exerciser compliance tests on the peer.
Likely conclusionLogic bug in the peer DLL.
ConfidenceHigh once captured.

Pattern 4 — Device "disappears" and returns

SymptomNVMe resets with CSTS all ones; sometimes the device does not come back.
Possible causesLink loss (power, PERST#, connector), firmware hang causing link down, thermal shutdown.
EvidenceSurprise Down, Link Active transitions, Receiver Error history, slot power events.
First checkDid Link Active go to 0 before the NVMe symptoms?
Second checkCorrectable error trend before the loss.
Disambiguating experimentMonitor slot power and temperature; capture with a trigger on link loss.
Likely conclusionPhysical or power cause if errors trend up first; device-internal if the link drops cleanly with no precursor.
ConfidenceMedium.

Pattern 5 — Errors only around power-state transitions

SymptomCorrectable errors only with ASPM L1 or L1 substates enabled.
Possible causesReceiver settling after exit; reference clock gating issues; DLL/PHY transition logic.
EvidenceErrors timed at L1 exit; which direction.
First checkError timing relative to PM DLLPs and Recovery.
Second checkBehaviour with L1 substates off but L1 on.
Disambiguating experimentSwap device and platform independently.
Likely conclusionExit-path margin issue on the side the errors follow.
ConfidenceLow-medium; needs swaps.

Interview

Beginner

  1. What does the Data Link Layer guarantee?

    Model answer

    That TLPs cross one link intact, once, in order — or that the link is reported down.

  2. Are DLLPs forwarded by switches?

    Model answer

    No; each link has its own DLLPs.

  3. Is an Ack a completion?

    Model answer

    No; it confirms link-level receipt only.

  4. What must happen before the first TLP after link-up?

    Model answer

    Flow-control initialisation (InitFC1/InitFC2) bringing the DLL to DL_Active.

  5. Which AER errors belong to the DLL?

    Model answer

    Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover (correctable); Data Link Protocol Error, Surprise Down (uncorrectable).

Intermediate

  1. Walk the DLCMSM.

    Model answer

    DL_Inactive (link down) → optional DL_Feature (4.0+) → DL_Init (FC_INIT1, FC_INIT2) → DL_Active; back to DL_Inactive when LinkUp drops.

  2. What is Data Link Layer Link Active used for?

    Model answer

    Software (hot-plug, error recovery) learns whether the DLL is active on a Downstream Port, not just whether training finished.

  3. Why does a retimer not log DLL errors?

    Model answer

    It has no DLL: it does not check LCRC, Ack or replay; errors are seen at the DLL endpoints of the hop.

  4. How does a receiver-side bit tell you direction?

    Model answer

    Bad TLP/Bad DLLP/Receiver Error at a port mean the traffic arriving at that port was damaged: the opposite port's transmit direction.

  5. What does Surprise Down mean?

    Model answer

    A Downstream Port saw its link leave DL_Active without being directed to; reported as an uncorrectable error.

Advanced

  1. How can the DLL limit throughput without errors?

    Model answer

    The replay buffer caps unacknowledged bytes; if the Ack round trip grows, buffer/RTT falls below link bandwidth and the transmitter idles.

  2. Why can't LCRC catch corruption inside a switch?

    Model answer

    The switch checks incoming LCRC and generates new LCRC on egress; internal corruption is covered by a fresh, valid LCRC. Only ECRC or poisoning catch it.

  3. What happens to TLPs in the replay buffer at DL_Down?

    Model answer

    They are discarded; posted writes are lost and non-posted requests will time out at their requesters.

  4. Why do correctable DLL errors matter if data is safe?

    Model answer

    They cost latency and throughput, and trending counts predict link loss.

  5. What changes in Flit Mode for the DLL?

    Model answer

    Retry, sequence numbering and CRC move to the flit level with FEC; per-TLP sequence numbers and LCRC no longer apply; DLLP information is carried in flits. Details come from the 6.x specification.

Senior

  1. How do you tell a physical fault from a DLL logic fault?

    Model answer

    Noise hits long TLPs more than short DLLPs and produces CRC errors; logic faults produce well-formed impossible content (Data Link Protocol Error), deterministic patterns, or errors on one packet type only. Confirm with captures on both sides of retimers and with swaps.

  2. Design DLL validation for a new SSD.

    Model answer

    Bring-up across speeds and widths with and without feature exchange; injected LCRC/DLLP CRC errors, dropped Acks, Naks, and illegal sequence numbers; replay-buffer stress at maximum Ack latency; REPLAY_NUM rollover; surprise link loss and recovery; ASPM transitions; correct AER reporting on both sides.

  3. What fleet signal predicts link loss?

    Model answer

    A rising trend of Receiver Error/Bad TLP/Bad DLLP at a port, especially temperature-correlated, before any uncorrectable event.

  4. A vendor says "our Root Port logged nothing, so the SSD is at fault". Reply?

    Model answer

    Receiver-side errors appear where damaged traffic arrives; check the SSD's registers too, check masks, and identify the hop and direction before assigning fault.

  5. Why should NVMe engineers care about Data Link Layer Link Active?

    Model answer

    It lets recovery code avoid MMIO to a link that is down (avoiding long CPU stalls) and correctly sequence reset and hot-plug handling.

Quiz

  1. The SSD logs Bad DLLP. Which direction is suspect?

    • SSD → Root Port
    • Root Port → SSD
    • Both
    Answer and reasoning

    The SSD received damaged DLLPs, which travel Root Port → SSD.

  2. Which component does not terminate a DLL hop?

    • Switch downstream port
    • Root Port
    • Retimer
    Answer and reasoning

    A retimer is a Physical Layer device.

  3. Link Active reads 0 while LTSSM training completed. Possible?

    • Yes, during flow-control initialisation or if it failed
    • No, L0 implies DL_Active
    Answer and reasoning

    DL_Active follows flow-control initialisation after LinkUp.

  4. Which error is uncorrectable?

    • Bad TLP
    • Replay Timer Timeout
    • REPLAY_NUM Rollover
    • Data Link Protocol Error
    Answer and reasoning

    DLP is uncorrectable (fatal by default).

  5. 4 KB replay buffer, 800 ns Ack round trip, Gen4 x4. Limiting?

    • Yes, ≈ 5.1 GB/s
    • No
    Answer and reasoning

    4,096 B / 800 ns ≈ 5.1 GB/s < 7.88 GB/s.

  6. What happens to a posted write in the replay buffer when the link goes down?

    • Replayed after link-up
    • Lost
    • Converted to an error completion
    Answer and reasoning

    DL_Inactive discards the replay buffer.

  7. Why is Surprise Down logged at the Downstream Port rather than the endpoint?

    Model answer

    The Downstream Port observes the loss and remains reachable by software; the endpoint is on the far side of the lost link.

  8. Name two DLL conversations other than Ack/Nak.

    Model answer

    Flow control (InitFC/UpdateFC), power management (PM DLLPs), and Data Link Feature exchange.

  9. Why can a gap in captured sequence numbers be checked against Acks?

    Model answer

    A receiver Acks only in order; an Ack covering the gap proves the missing TLP crossed the link.

Teach-back

  1. To a child: why the porters wave flags before the bridge opens.

    Model explanation

    "So each porter knows the other one is there and how many baskets the other side can store. If they started throwing baskets before that, some would fall on the floor."

  2. To a junior engineer: how to read AER from both ends of a link.

    Model explanation

    "Receiver-side bits — Receiver Error, Bad TLP, Bad DLLP — say the traffic coming into that port was damaged, so suspect the other side's transmit lanes. Transmitter-side bits — Replay Timer Timeout, Rollover — say this port's TLPs were not acknowledged in time. Always read both ends, and check masks."

  3. To a senior engineer: why "no AER errors" does not mean "the DLL is not the bottleneck".

    Model explanation

    "The replay buffer bounds unacknowledged bytes. When Ack latency grows — retimers, long channels, aggressive Ack coalescing — buffer over round trip can fall below link bandwidth, and the transmitter idles with no error. You find it by timing transmit gaps against Acks in a capture, not in AER."

Mastery gate

Do not consider this module mastered until you can:

  • explain the DLL's service, its states and what the Transaction Layer may do in each
  • diagram a DLL hop with a retimer and a switch, marking where sequence numbers and LCRC start and end

  • debug a correctable-error storm and a link loss to a hop, a direction and a layer
  • distinguish the DLL from the replay mechanism in detail, from flow control, from the LTSSM (Chapter 8), and from end-to-end ECRC
