Chapter 13 explained what a Tag is and how many a link needs. This module treats tags as a managed resource inside a device: how allocators work, how tag pools reveal a controller's internal engines in a trace, how tag width is negotiated end to end, and how tags leak, alias and — in the worst case — deliver a late completion into the wrong buffer without any error at all.

Orientation

A Tag is eight (or ten, or fourteen) bits in a header, but behind it sits a hardware allocator, a table of per-request state, a reassembly buffer and a timer. Most tag bugs are not header bugs; they are lifecycle bugs: a tag freed too early, freed never, or allowed to mean two things at once. This module follows the full lifecycle of a tag, shows how to measure tag occupancy from a capture, separates the tag limit from the other limits on outstanding requests, and gives you the forensic method for the most dangerous tag failure: reuse after a Completion Timeout.

Tag spaces (5-bit default, 8-bit Extended Tag, Phantom Functions, 10-bit, 14-bit in Flit Mode), the Transaction ID uniqueness rule, Max Read Request Size (MRRS) splitting and how many tags a link needs: Chapter 13 — PCIe Tags and Outstanding Requests. Completion matching and timeouts: Chapter 52 and Module 12. Where T9/T8 sit in DW0: Chapter 11.

Where this goes next: credits as the other limit on outstanding requests in Chapter 16 and Module 17 — PCIe Flow Control; ordering of completions across tags in Module 14; SR-IOV, where every Virtual Function has its own tag space, in Chapter 56.

Kid story

At the swimming pool there is a basket of coloured wristbands with numbers. When you want a locker, you take a wristband; when you leave, you give it back. There are only so many wristbands, so on busy days people wait at the entrance.

One day a wristband falls into the pool and nobody gives it back. Now there is one fewer, forever — the pool gets a little more crowded every day this happens. Another day, the lifeguard decides a wristband has been "gone too long", puts a new copy of the same number in the basket, and gives it to someone else. Then the first swimmer comes back and opens locker 17 — and finds someone else's clothes. Nobody shouted. Nobody noticed. That is the worst kind of mistake.

Analogy boundary

What it represents. A finite pool of numbers, allocation and return, the cost of a lost number (leak), and the danger of handing out a number whose previous holder may still return (reuse after timeout).

What it hides. Wristbands are unique within one pool only; PCIe tags are unique per Requester ID, so two functions can use the same tag value at once. The pool does not track partial returns; a PCIe tag is held until all completions of a request have arrived. And the size of the basket is negotiated: a requester may use wider tags only if the completer and every hop in between handle them.

Where it misleads. The lifeguard's decision sounds careless. In PCIe, freeing a tag after a Completion Timeout is what the rules expect — the request has failed. What makes it dangerous is a late completion that arrives after the tag has been reused, whose fields happen to pass the new request's checks. The danger is a race in time, not negligence; protection comes from allocator design (do not reuse recently timed-out tags quickly) and from strict completion checks.

Mechanism

The full lifecycle of Tag 0x45 for a 512-byte WRITE-data read, including the error branches.

  1. Gate. The data engine (who) needs 512 bytes. The allocator checks a free tag, 512 bytes of buffer, and a non-posted header credit (what), inside the SSD's DMA block (where). Evidence: none until the MRd appears; if a gate is closed, a gap in MRd issue.
  2. Allocate. The allocator removes 0x45 from the free set and writes the tag-table entry (buffer, offset, BC = 512, next LA, timer start). Evidence: Tag=0x45 in the next MRd.
  3. Send. Header builder emits MRd64 with Tag 0x45 (T9/T8 = 0 since 10-bit tags are disabled). Evidence: analyzer row.
  4. Copy. The Root Complex (completer) copies Requester ID and Tag into each completion. Evidence: CplD rows with Tag 0x45.
  5. Match. Each CplD is looked up by tag; checks pass; data placed; BC decremented. Evidence: none externally.
  6. Free. On the completion whose Byte Count equals its bytes, the entry is cleared and 0x45 returns to the free set. Evidence: 0x45 may appear in a later MRd.
  7. Error branch — error completion. UR/CA: entry cleared, engine told "failed", tag freed. Evidence: Cpl with status.
  8. Error branch — timeout. Timer fires: the request fails, AER Completion Timeout is logged, the entry moves to a timed-out state; when the tag becomes reusable is an allocator decision. Evidence: ERR_NONFATAL message; later possibly an Unexpected Completion with Tag 0x45.

The specification does not say how a requester allocates tags, how quickly a timed-out tag may be reused, whether a requester must check Byte Count and Lower Address strictly enough to reject a late completion that lands on a reused tag, or how many tags a device must actually use. It does define when a tag is no longer outstanding. Check in your revision: exact 10-bit tag value restrictions, how 10-bit tags interact with peer-to-peer and with Virtual Functions, and the rules on completers that do not support the requester's width.

Never assume a tag value tells you request order, that tags are allocated sequentially, or that "no AER errors" means no tag aliasing happened.

A tag-table entry holds tens of bytes of state plus a timer, and the reassembly buffer holds MRRS bytes per entry. At 256 entries and 512-byte MRRS that is 128 KiB of buffer — far more than most SSD controllers dedicate — so devices use fewer tags than the space allows. Timers are often one coarse clock with per-entry timestamps rather than 256 independent counters. Implementation-dependent

Allocation order leaves fingerprints. A lowest-free allocator reuses small values constantly; a round-robin allocator walks the space, which spreads reuse in time (a natural defence against late completions); partitioned pools show distinct value ranges per engine. Reading these patterns lets you attribute requests to engines without vendor documentation.

Protocol view

  • Messages and transactions. Tags matter only on non-posted requests (MRd, configuration, I/O, AtomicOps) and their completions. Posted requests carry a tag field with no matching role (with TLP Processing Hints it may carry steering information).
  • Request/response. One tag per request; one or more completions per tag.
  • Ordering. Completions for different tags may pass each other; completions of the same tag stay in address order. A requester must never infer request order from completion order across tags.
  • Completion. The tag is released on the final piece, an error completion, or timeout.
  • Errors. Unexpected Completion (no matching tag), Completion Timeout (tag never satisfied), Malformed TLP if a completion's fields are inconsistent and the requester checks them. Tag aliasing may produce none of these.

Whether the late completion is caught depends on the requester's checks. If A and B have the same size and the same address bits [6:0], Byte Count and Lower Address of A's first completion match B's expectations exactly. The completion is accepted. B's real completion then arrives and is rejected as inconsistent or unexpected — or, with lax checks, overwrites. Either way B's buffer may hold A's data. Derived

SSD AER: Unexpected Completion at 11.6 ms. Command 0x0512 completed successfully. Weeks later, a checksum mismatch is found in the data written by 0x0512.

Analysis. Rows 4–5 and 6 cannot both belong to B: a request has exactly one completion stream. Both A and B are 512 bytes with address bits [6:0] = 0x40, so A's late completion (rows 4–5) passes every check for B; B's real completion (row 6) then arrives for a tag already freed and is logged as unexpected. The capture alone cannot prove which payload is whose — but a two-sided capture (at the Root Complex's memory side, or by comparing payload bytes against the known contents of A's and B's host buffers) can. If rows 4–5 carry A's buffer contents, command 0x0512 wrote A's data to media: silent corruption caused by reuse after timeout. Confidence: medium from the header pattern, high once payloads are compared. Fix direction: quarantine timed-out tags for longer than the worst completer latency, and treat any Unexpected Completion shortly after a reuse as grounds to fail the reusing command.

Intermediate lab — allocator simulation: leaks and reuse races

Objective. See how allocation policy affects leak impact and reuse-race exposure. Prerequisites. Python 3. Setup. Save as tag_sim.py.

#!/usr/bin/env python3
"""Tag allocator simulation: lowest-free vs round-robin, with timeouts, late
completions, quarantine and a leak bug. Standard library only; numbers illustrative."""
import random
from collections import deque

def simulate(policy, ntags=64, n_req=100_000, load=0.5, p_late=1e-3,
             timeout_ns=50e3, late_ns=200e3, rtt_ns=1000.0,
             quarantine_ns=0.0, leak_on_timeout=False, seed=7):
    rnd = random.Random(seed)
    busy_until = [0.0] * ntags      # tag outstanding until this time
    usable_from = [0.0] * ntags     # quarantine end for timed-out tags
    leaked = [False] * ntags
    late = deque()                  # (arrival time, tag) of late completions
    step = rtt_ns / (ntags * load)  # request arrival spacing for the given load
    now, rr = 0.0, 0
    aliased = unexpected = stalls = 0
    for _ in range(n_req):
        now += step
        while late and late[0][0] <= now:
            _, t = late.popleft()
            if busy_until[t] > now and not leaked[t]:
                aliased += 1        # lands on a NEW request using the same tag
            else:
                unexpected += 1     # tag idle: reported as Unexpected Completion
        free = [t for t in range(ntags)
                if busy_until[t] <= now and usable_from[t] <= now and not leaked[t]]
        if not free:
            stalls += 1
            continue
        if policy == "lowest":
            t = free[0]
        else:
            t = min(free, key=lambda x: (x - rr) % ntags)
            rr = (t + 1) % ntags
        if rnd.random() < p_late:   # completion will arrive after the timeout
            late.append((now + timeout_ns + late_ns, t))
            if leak_on_timeout:
                leaked[t] = True    # bug: timeout path never returns the tag
            else:
                busy_until[t] = now + timeout_ns
                usable_from[t] = now + timeout_ns + quarantine_ns
        else:
            busy_until[t] = now + rtt_ns * rnd.uniform(0.8, 1.2)
    return dict(aliased=aliased, unexpected=unexpected, stalls=stalls,
                usable=ntags - sum(leaked))

if __name__ == "__main__":
    for pol in ("lowest", "round-robin"):
        print(f"{pol:12s}", simulate(pol))
    print("round-robin + 300 us quarantine", simulate("round-robin", quarantine_ns=300e3))
    print("leak bug (p_late 2e-4)        ", simulate("round-robin", p_late=2e-4,
                                                     leak_on_timeout=True))

Procedure. Run it. Vary load, p_late, late_ns and ntags. Note which policy produces more aliasing and what the quarantine does.

Questions. (1) Why does lowest-free alias more? (2) Why does quarantine reduce aliasing to zero here, and what does it cost? (3) Why is the leak bug invisible in a short test?

Solution

(1) At 50% load, lowest-free keeps reusing the same low values, so a timed-out tag is almost always busy again when its late completion arrives (87 aliased versus 7 unexpected in the default run); round-robin spreads use, so the tag is busy only about as often as the load (45 versus 49). Raise load towards 1.0 and the two policies converge: at full load every tag is busy all the time. (2) If no tag is reused within the quarantine window and late completions arrive within it, they find the tag free and are reported as Unexpected Completions instead of being misdelivered; the cost is fewer usable tags immediately after timeouts. (3) Each leak removes one tag; with rare timeouts it takes hours or days to lose enough tags to affect throughput — the symptom is a slow, monotonic decline that resets at controller reset.

Extension. Add a strict check: a completion arriving within 1 µs of a tag's reuse with Byte Count equal to the full request is flagged as suspicious. Count how many aliasing events it would catch.

Advanced lab — outstanding-tag occupancy from a capture

Objective. Turn a trace into an occupancy curve and identify the limit. Prerequisites. The beginner lab. Setup. Use the trace in the slow example above, or generate one with the Chapter 12 simulation that logs (time, tag, event).

Procedure. (1) For each MRd, add +1 at its time; for each final completion (Byte Count = bytes carried), add −1. (2) Plot or tabulate the running sum. (3) Measure the gap between a final completion and the next MRd. (4) Correlate MRd resumption with UpdateFC-NP DLLPs if present.

Expected reasoning. A flat ceiling with zero-gap resumption on tag free means a tag limit; resumption aligned with UpdateFC-NP means credits.

Solution

On the slow trace: occupancy rises to 32 in 320 ns and stays flat; each free is followed by an MRd within ≈ 10 ns using the same tag value. No UpdateFC-NP correlation. Conclusion: tag limit (5-bit tags). The ≈ 10 ns reaction also tells you the allocator is fast; the limit is width, not logic.

Extension. Compute average occupancy and, with Little's Law, the implied average latency; compare with the measured per-tag latency.

Senior forensic lab — the slow decline

Objective. Diagnose a tag leak from fleet evidence. Prerequisites. All previous labs.

Setup (synthetic evidence). A fleet of servers: SSD WRITE throughput declines by about 3% per day after each reboot and recovers at reboot or NVMe controller reset. READ throughput is unaffected. AER logs show a few Completion Timeouts per day per server, each preceded by a Root Port correctable error burst. A capture on a degraded server shows the SSD never exceeds 41 outstanding data reads (fresh servers: 64), and data tags 0x40–0x7F are used except 23 specific values that never appear.

Questions. (1) What is the mechanism? (2) Why only WRITE? (3) What evidence would confirm it and what is the fix and the regression test?

Solution

(1) A tag leak: each Completion Timeout takes a tag out of the data pool permanently (the timeout path does not return it). 64 − 23 = 41 matches the observed ceiling. (2) WRITE data uses non-posted reads; READ uses posted writes and needs no tags. (3) Confirm by matching the 23 missing tag values with tags in Completion Timeout events (if logged) or by injecting completion drops with an exerciser in the lab and watching the pool shrink. Fix: return tags on timeout (after a quarantine), and reset the pool on controller reset. Regression test: inject N timeouts and assert the outstanding ceiling returns to 64 after the quarantine. Separately, investigate the Root Port error bursts that cause the timeouts in the first place.

Extension. Write a monitoring query that would have caught this from fleet metrics without a capture.

Debugging

Pattern 1 — Gradual WRITE slowdown that resets on reset

SymptomMonotonic WRITE throughput decline over hours/days; restored by controller reset.
Possible causesTag leak on an error path; buffer leak; firmware queue leak.
EvidenceOutstanding ceiling over time; missing tag values; timeout history.
First checkCeiling now versus after reset.
Second checkDo missing values coincide with timed-out tags?
Disambiguating experimentInject completion drops in a lab and count lost tags.
Likely conclusionLeak in the timeout path.
ConfidenceHigh if counts match.

Pattern 2 — Unexpected Completions after enabling a feature

SymptomUnxCmplt and CmpltTO appear after a firmware/BIOS change.
Possible causes10-bit tags without completer support; Phantom Functions mis-enabled.
EvidenceLogged completion tags equal to low 8 bits of issued tags; DevCap2/DevCtl2.
First checkRequester enable versus completer support.
Second checkDo only tags ≥ 0x100 fail?
Disambiguating experimentRestrict to 8-bit tags in a lab.
Likely conclusionWidth mismatch.
ConfidenceHigh.

Pattern 3 — Rare silent corruption correlated with timeouts

SymptomApplication checksum failures, each within milliseconds of an AER Completion Timeout and a later Unexpected Completion.
Possible causesReuse-after-timeout race; completer duplicating completions.
EvidenceTwo completion streams for one tag; equal sizes and low address bits for the two requests.
First checkWas the timed-out tag reused before the Unexpected Completion?
Second checkCompare payloads against both buffers.
Disambiguating experimentLengthen quarantine (device setting, if available) or use a device with round-robin allocation; corruption should vanish.
Likely conclusionAllocator reuse race exposed by slow completer.
ConfidenceMedium until payloads compared.

Pattern 4 — Throughput cap at exactly 32 outstanding

SymptomWRITE bandwidth far below link; outstanding reads flat at 32.
Possible causesExtended Tag disabled; 32-entry buffer; firmware cap.
EvidenceDevCtl ExtTag; tag values used (all < 0x20?).
First checklspci ExtTag.
Second checkTag value range in a capture.
Disambiguating experimentSame SSD in a platform with ExtTag enabled.
Likely conclusionPlatform tag policy.
ConfidenceHigh if values stay below 0x20.

Pattern 5 — Duplicate tag in flight

SymptomCapture shows a tag reissued while its earlier request still has bytes outstanding.
Possible causesAllocator race (free on first completion instead of last), multi-engine shared pool without locking.
EvidenceByte Count of the last completion before reuse > bytes carried.
First checkDoes reuse follow a non-final completion?
Second checkDo the two requests come from different engines (different address regions)?
Disambiguating experimentForce single-completion reads (smaller MRRS ≤ MPS) — the race should disappear if it is "free on first piece".
Likely conclusionRequester tag-table bug.
ConfidenceHigh.

Interview

Beginner

  1. When may a tag be reused?

    Model answer

    After the request it identified has completed (final completion) or failed (error completion or timeout).

  2. Is a tag unique system-wide?

    Model answer

    No; unique among one requester's outstanding non-posted requests. Requester ID + Tag is the Transaction ID.

  3. Do posted writes need unique tags?

    Model answer

    No; they have no completions to match.

  4. Which enable allows 8-bit tags?

    Model answer

    Extended Tag Field Enable in Device Control.

  5. Why does a device need many tags for WRITEs?

    Model answer

    It fetches WRITE data with reads, and must keep rate × round-trip bytes outstanding.

Intermediate

  1. What must be true before using 10-bit tags?

    Model answer

    Requester supports and is enabled; the completer supports 10-bit completion; the path forwards T9/T8 intact.

  2. Name four limits on outstanding reads.

    Model answer

    Free tags, completion buffer space, non-posted credits, engine/firmware contexts.

  3. How do you tell a tag ceiling from a credit ceiling in a trace?

    Model answer

    Tag: flat at a fixed count, resume on tag free. Credit: varying ceiling, resume after UpdateFC-NP.

  4. What are Phantom Functions?

    Model answer

    Using unused Function Number bits as extra tag bits; requests appear with several Requester IDs.

  5. Why do traces sometimes show distinct tag ranges?

    Model answer

    Internal pools per engine — a design choice that isolates latency-critical fetches from bulk data.

Advanced

  1. Explain the reuse-after-timeout race.

    Model answer

    A timed-out tag is freed and reused; the original's late completion arrives, matches the new request and may pass its checks if sizes and low address bits match, placing old data in the new buffer.

  2. How does allocation policy change that risk?

    Model answer

    Lowest-free reuses immediately (high risk); round-robin delays reuse; quarantine forbids reuse for a window.

  3. Why are 10-bit tag mismatches intermittent?

    Model answer

    Only tags ≥ 0x100 lose bits; whether they are used depends on allocation and load.

  4. Why is a tag leak hard to catch in qualification?

    Model answer

    It needs the error path (timeouts) to run many times; short tests rarely hit it and throughput loss is gradual.

  5. Why does freeing a tag on the first completion cause problems only for some sizes?

    Model answer

    Only multi-completion reads (larger than MPS or split at RCB) have later pieces arriving after the premature free.

Senior

  1. Specify a tag-management validation plan.

    Model answer

    Full-space use and wrap; every split pattern; reuse protection; injected drops, delays, duplicates with an exerciser; timeouts with late completions at varying delays; width negotiation with completers lacking support; behaviour across FLR and controller reset; long soak with periodic timeouts to detect leaks.

  2. Would you require a quarantine in a controller design? How long?

    Model answer

    Yes, longer than the worst plausible late-completion delay (platform error recovery), within buffer limits; combine with strict checks and failing commands on suspicious completions.

  3. How do tags and SR-IOV interact?

    Model answer

    Each Virtual Function has its own Requester ID and so its own Transaction ID space, but often shares physical allocator and buffer resources; fairness and leaks per VF must be validated; width settings for VFs come from SR-IOV controls.

  4. A customer asks whether enabling 10-bit tags will speed up their Gen4 x4 SSD.

    Model answer

    Probably not: 8-bit tags cover x4 links at typical latencies; the device's buffer is usually the limit. 10-bit matters for wide/fast links and high-latency paths, and adds compatibility risk.

  5. What fleet metric would detect tag problems early?

    Model answer

    Per-device Completion Timeout and Unexpected Completion counts correlated with WRITE throughput and with uptime; a monotonic throughput decline that resets at reset is the leak signature.

Quiz

  1. A device issues at most 32 reads and every value is below 0x20. Most likely limit?

    • Non-posted credits
    • 5-bit tags (Extended Tag disabled)
    • MPS
    Answer and reasoning

    Values confined to 0x00–0x1F with a flat 32 ceiling is the default 5-bit tag space.

  2. Completions return Tag 0x0C5 for a request sent with 0x2C5. Which field was lost?

    • Tag[7:0]
    • Requester ID
    • T9 (Tag[9])
    • Lower Address
    Answer and reasoning

    0x2C5 − 0x0C5 = 0x200: bit 9, carried as T9 in DW0.

  3. Which allocation policy minimises reuse-after-timeout exposure (without quarantine)?

    • Round-robin
    • Lowest-free
    • Highest-free
    Answer and reasoning

    Round-robin maximises time between reuses of one value.

  4. Who copies the tag into completions?

    • Each switch
    • The completer
    • The Data Link Layer
    Answer and reasoning

    The completer copies Requester ID and tag; switches route by ID only.

  5. Tags 0x00–0x07, 0x20–0x27 and 0x40–0xBF are used by one SSD. Required by the specification?

    • Yes
    • No, it is an internal pool design
    Answer and reasoning

    Allocation policy is implementation-dependent.

  6. Which error is a tag leak likely to produce by itself?

    • Unexpected Completion
    • Malformed TLP
    • None — only reduced throughput
    Answer and reasoning

    A leaked tag is simply never reused; no error is reported.

  7. Why can't the completer detect duplicate tags from one requester?

    Model answer

    It is not required to track outstanding Transaction IDs; it serves each request independently.

  8. Two requests of 512 B, both at address offset 0x40 in their pages, share a reused tag. Why is that the worst case?

    Model answer

    The late completion's Byte Count and Lower Address match the new request's expectations, so checks pass and the data is accepted.

  9. Why do READ commands not depend on the SSD's tag supply for data?

    Model answer

    READ data goes to the host as posted writes; only SQE and list fetches need tags.

Teach-back

  1. To a child: why a lost wristband makes the pool more crowded every day.

    Model explanation

    "There's a fixed number of wristbands. Each lost one means one fewer person can swim at the same time, and nobody makes a new one until the pool closes for the night."

  2. To a junior engineer: how to read tag occupancy from a trace.

    Model explanation

    "Count +1 at every read request and −1 at each tag's final completion — the one where Byte Count equals the bytes it carries. Plot it. A flat top tells you there's a limit; what happens right after a tag frees tells you which limit."

  3. To a senior engineer: why tag reuse after timeout deserves a design rule.

    Model explanation

    "The specification frees the tag at timeout, which is right for liveness, but completers can answer late during their own recovery. If the allocator reuses the value immediately and the new request has the same size and low address bits, a late completion passes every check. That turns a reported, recoverable error into silent corruption. Quarantine and strict checks cost little and close the window."
