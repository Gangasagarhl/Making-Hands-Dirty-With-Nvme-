A Base Address Register (BAR) is a numbered doorway into a device: software decides where in the address map the doorway opens, and from then on ordinary CPU loads and stores through it become PCIe Memory Read and Memory Write packets that land on device registers. This chapter teaches BAR sizing, 32-bit and 64-bit BARs, prefetchable and non-prefetchable regions, memory-mapped I/O (MMIO), and how BAR0 of an NVMe controller becomes its register file and doorbells.

Why this chapter exists

Every NVM Express (NVMe) command the host submits ends with one 4-byte write: the doorbell. That write is a CPU store instruction to an address inside BAR0, which the Root Complex turns into a posted Memory Write Transaction Layer Packet (TLP) to the controller. The controller's register file — CAP, VS, CC, CSTS, AQA, ASQ, ACQ — is reached the same way. If the BAR is not assigned, is assigned to an address the bridges above do not forward, or is mapped with the wrong memory type in the CPU, the driver cannot even reset the controller.

BARs are also where the "address" concept splits into several meanings: CPU virtual addresses, CPU physical addresses, PCIe bus addresses and, for DMA in the other direction, I/O virtual addresses. Getting this straight is a prerequisite for Chapter 20 (DMA) and for reading any trace that contains an address.

Learning objectives

  • Decode a BAR's type bits: memory vs I/O, 32-bit vs 64-bit, prefetchable vs non-prefetchable.
  • Perform the BAR sizing algorithm (write all ones, read back, mask, invert, add one) by hand for 32-bit, 64-bit and I/O BARs.
  • Explain natural alignment and why BAR sizes are powers of two.
  • Explain how bridge memory windows (non-prefetchable and prefetchable) constrain where BARs can be placed — and why the Lab SSD's 64-bit BAR sits below 4 GiB.
  • Trace a CPU load/store to BAR0 + offset through page tables, memory type, Root Complex, bridges and device decode, and say which TLP results.
  • Map BAR0 offsets to NVMe controller registers and compute doorbell addresses from CAP.DSTRD.
  • Use Linux to see BAR assignments and, carefully, read NVMe registers through BAR0.

The story

A big building has a long corridor of numbered doors. A new toy shop moves in, and the caretaker asks: "How many rooms do you need?" The shop can't just say a number; instead the caretaker writes "all the rooms!" on the shop's sign, and the sign magically erases everything except how many rooms the shop really has — "4 rooms". The caretaker finds a spot in the corridor where 4 rooms fit and start at a nice round number, and paints the shop's door number on the sign. From then on, anyone who walks into door 4000 is in the shop's first room, and a note slipped under door 4008 lands on the shop's counter as a bell ring.

A postal system for a new business park. Each tenant tells the post office how many consecutive mailbox numbers it needs (always a power of two, and its block must start at a multiple of its size). The post office assigns ranges and tells each district sorting office which ranges to forward toward which street. After that, a letter addressed to box 0xFE60_1008 is routed street by street to the tenant, whose internal mail room knows that box 1008 is "the order desk's in-tray". Senders never need to know where the tenant physically is — only the box number.

Where the analogy breaks. (1) A BAR does not "move" the device; it only sets which addresses the device answers to. (2) Writing to a doorway is not storing something for later — writing to a doorbell does something immediately, and reading a register can have side effects (for non-prefetchable regions). (3) Letters can be read back from mailboxes; many device registers are write-only or return different values than written. (4) Postal routing is by street; PCIe routing is by address windows in every bridge, and the CPU additionally decides how to cache, combine or order accesses before they leave the chip. (5) In the analogy the tenant asks for space; in PCIe the device states its size by which bits it refuses to store.

Beginner explanation

A PCIe device that has registers or memory for the host to access exposes them as one or more regions. Each region is described by a BAR in the device's configuration header: up to six 32-bit BARs at offsets 10h, 14h, 18h, 1Ch, 20h and 24h for an Endpoint.

A BAR does two jobs:

  1. It tells software how big the region is and what kind it is. Software finds the size by writing all ones and reading back: bits the device cannot store read as zero, and those zero bits reveal the size.
  2. It holds the address software assigns. Software writes the chosen base address; from then on the device claims any memory request whose address falls inside [base, base + size).

Once a memory BAR is assigned and Memory Space Enable is set in the Command register, the CPU can access the device with normal load and store instructions. That is memory-mapped I/O (MMIO): device registers that look like memory addresses. A store becomes a posted Memory Write (MWr) TLP; a load becomes a non-posted Memory Read (MRd) TLP whose Completion with Data (CplD) brings the value back.

For an NVMe SSD, the controller's register file is at BAR0 offset 0: CAP at 00h, VS at 08h, CC at 14h, CSTS at 1Ch, and so on; doorbells start at 1000h. On the lab machine BAR0 = 0xFE60_0000, so SQ1's tail doorbell is at 0xFE60_1008.

The sizing algorithm

The device designer makes the BAR's low-order address bits read-only zero, up to the region size. Writing all ones and reading back exposes them:

  1. Clear Memory Space Enable (and I/O Space Enable) in the Command register, so the device does not decode a half-written address.
  2. Save the BAR's current value.
  3. Write FFFF_FFFFh to the BAR.
  4. Read it back.
  5. Mask off the type bits: bits 3:0 for memory BARs, bits 1:0 for I/O BARs.
  6. Invert and add one: size = (~masked) + 1 (in 32 bits; for I/O, consider only the implemented upper limit, typically 16 bits on x86).
  7. For a 64-bit BAR, repeat steps 2–4 for the upper BAR and combine: size = ~(upper:lower masked) + 1 in 64 bits.
  8. Restore the saved values, then restore the Command register.
size = (¬(R ∧ M)) + 1

Alignment and placement

Because the low bits are hard-wired to zero, a BAR's base is always naturally aligned to its size: a 16 KiB BAR starts on a 16 KiB boundary; a 256 MiB BAR on a 256 MiB boundary. Large BARs therefore fragment the address map, and resource allocators place the largest BARs first. Implementation-dependent Operating systems often round small BARs up to page size so each can be mapped independently.

Prefetchable vs non-prefetchable

A memory region is prefetchable if reads have no side effects (reading twice returns the same data and changes nothing) and writes can be merged (byte writes combined into larger writes) without changing behaviour. Device RAM — a frame buffer, an NVMe Controller Memory Buffer — is typically prefetchable. Registers with side effects — a status register that clears on read, a doorbell, a FIFO — are not.

Why it matters:

  • Bridges may prefetch (read ahead) and merge writes only in prefetchable windows.
  • The CPU mapping: the OS can map a prefetchable region as write-combining (WC), letting the CPU merge many stores into large MWr TLPs; non-prefetchable regions are mapped uncached (UC), every access a separate transaction in program order.
  • 64-bit placement: in a Type 1 bridge header, the non-prefetchable memory window (Memory Base/Limit at 20h/22h) is 32-bit only, while the prefetchable window (24h/26h plus upper halves at 28h/2Ch) can be 64-bit. So a non-prefetchable BAR must be placed below 4 GiB if it sits behind any bridge — even if the BAR itself is 64-bit capable. That is why the Lab SSD's 64-bit, non-prefetchable BAR0 has the address 0x0000_0000_FE60_0000.

Normative The PCI Express Base Specification expects Endpoints to mark memory as prefetchable unless it has read side effects or cannot tolerate write merging, and requires 64-bit addressing for prefetchable BARs of PCIe Endpoints. Confirm the current wording in the BAR section of your revision.

MMIO: from a CPU store to a device register

Points to notice:

  • No IOMMU in this direction. CPU-to-device MMIO uses CPU physical addresses, translated only by the CPU's MMU. The IOMMU translates addresses the device emits (Chapter 20).
  • Bus address = physical address on typical x86 systems. On some architectures a host bridge translates between CPU physical and PCIe bus addresses; Linux tracks the difference. Implementation-dependent
  • Writes are posted: the CPU instruction completes long before the TLP reaches the device. Reads are non-posted: the CPU stalls for the full round trip — typically around a microsecond — which is why drivers avoid MMIO reads in hot paths. A read also flushes earlier posted writes to the same device (PCIe ordering, Chapter 14), the classic way to make sure a write has arrived.
  • Access size: a 32-bit store becomes a 1-DW MWr with all byte enables set. A 64-bit access may become a single 2-DW TLP or two 1-DW TLPs depending on the CPU and Root Complex. Implementation-dependent NVMe registers are defined so that 32-bit accesses work; Linux reads the 64-bit CAP as two 32-bit reads, low half first.

BAR0 and the NVMe register file

The NVMe over PCIe Transport Specification 1.4 maps the controller properties (registers) defined by the NVMe Base Specification 2.4 into memory space through BAR0/BAR1, which together form a 64-bit, non-prefetchable memory BAR (the NVMe specifications name them MLBAR and MUBAR). Other BARs are optional: the MSI-X table and PBA may live in BAR0 or in another BAR (the MSI-X capability's BIR fields say which); the Controller Memory Buffer and Persistent Memory Region, when present, are located through their own registers' BAR indicator fields; older revisions defined an optional I/O-space index/data pair in BAR2 Uncertain — check the transport specification of your revision.

Resizable BAR

Some devices implement the Resizable BAR extended capability, which lets software choose among several supported sizes for a BAR (useful for GPUs with large memories, and for some devices with large Controller Memory Buffers). Software selects the size in the capability, then re-sizes and re-assigns the BAR. Optional Uncertain Take the extended capability ID and register layout from the PCI Express Base Specification; it is uncommon on NVMe SSDs.

The ladder

The shop's sign erases everything except how many rooms it has; the caretaker paints a door number on it; notes slipped under the door land on the counter.

A BAR reports its size through hard-wired zero bits and stores the base address software assigns; memory requests inside [base, base+size) reach the device's registers.

Address comparators in the device's PCIe core match incoming MRd/MWr addresses against each BAR (gated by Memory Space Enable) and route the offset to a register block, an SRAM (MSI-X table, CMB) or a doorbell FIFO. Bridges have window comparators; the CPU has page-table memory types.

The PCI Express Base Specification defines BAR formats, sizing semantics, prefetchability rules and bridge windows. The NVMe over PCIe Transport Specification binds the NVMe controller properties to BAR0/BAR1; the NVMe Base Specification defines each register.

CPU store → MWr TLP (posted), CPU load → MRd TLP + CplD; address = BAR base + register offset; Requester ID = Root Complex.

In a capture: "MWr32 Addr=0xFE60_1008 Len=1 Data=0x00000005" is a doorbell; "MRd32 Addr=0xFE60_001C" followed by "CplD Data=0x00000001" is the driver polling CSTS.RDY.

MMIO reads returning FFFF_FFFFh → device unreachable (link down, Memory Space Enable cleared, BAR moved). MWr with no effect → wrong offset (DSTRD ignored), wrong BAR, or device in reset. UR completions to MRd → address outside every BAR.

Hardware view

Inside the Lab SSD, the PCIe core compares each incoming memory request's address with BAR0's value (only the bits above 16 KiB), checks Memory Space Enable, and forwards the 14-bit offset to the controller front end. The front end decodes the offset further:

Doorbell writes are the hottest path in an NVMe device: millions per second under load. Controllers implement them as write-only registers that update a queue tail pointer and wake the fetch engine; some coalesce several doorbell writes before acting. Reading a doorbell returns an implementation-dependent value (often zero) — never use reads to "check" a doorbell.

On the CPU side, the Root Complex keeps a map of which physical address ranges are DRAM and which belong to each Root Port's windows. Accesses to MMIO ranges bypass caches (UC) or go through write-combining buffers (WC), and are subject to the CPU's ordering rules for those memory types. Drivers use I/O accessors (on Linux readl/writel and their relaxed variants) that include the necessary barriers.

Specification view

BARs and bridge windows: PCI Express Base Specification, Revision 6.x/7.0 — Configuration Space (Base Address Registers; Type 1 header windows). Resizable BAR: its extended capability section in the same document. NVMe binding: NVMe over PCIe Transport Specification 1.4 — PCI Express register mapping (MLBAR/MUBAR). Register definitions: NVMe Base Specification 2.4 — Controller Properties / Controller Registers.

BAR type bits: bit 0 memory/I/O; bits 2:1 = 00b (32-bit) or 10b (64-bit); bit 3 prefetchable. Sizing by writing all ones and reading back. Sizes are powers of two and regions are naturally aligned. Bridge non-prefetchable window is 32-bit; prefetchable window can be 64-bit. NVMe registers: CAP 00h, VS 08h, INTMS 0Ch, INTMC 10h, CC 14h, CSTS 1Ch, NSSR 20h, AQA 24h, ASQ 28h, ACQ 30h, CMBLOC 38h, CMBSZ 3Ch; doorbells from 1000h with stride 4 << CAP.DSTRD.

The consequence that a 64-bit non-prefetchable BAR behind bridges lands below 4 GiB follows from the 32-bit non-prefetchable window; the latency claims for MMIO reads and the hot-path advice are engineering practice.

BAR sizes and how many BARs a device implements; placement of MSI-X table/PBA; whether 64-bit MMIO accesses become one TLP or two; CPU memory types for MMIO; host bridge address translation; whether reads of write-only registers return 0.

Resizable BAR and its variants were added in later PCIe revisions. NVMe added the Controller Memory Buffer and Persistent Memory Region over successive 1.x revisions and adjusted CMB controls in later revisions; NVMe 2.x reorganised the specification into the Base + transport documents, so register definitions now live in the Base specification and their PCIe mapping in the PCIe Transport specification.

Check in the specification: the exact prefetchable/64-bit requirements for Endpoints; minimum BAR sizes; the full NVMe controller-property table for offsets above 3Ch; whether optional BARs (I/O index/data pair) still exist in your NVMe revision. The specifications do not say where a BAR will be placed, whether the OS maps it UC or WC, or how a CPU splits 64-bit MMIO.

Never assume BAR addresses are stable across boots; never compute doorbell addresses without CAP.DSTRD; never map non-prefetchable registers write-combining; never write to BAR0 from user space while a kernel driver owns the device.

Protocol view

MMIO traffic is always initiated by the Root Complex on behalf of the CPU (Requester ID = Root Complex), routed by address, and terminated at the device's BAR decoder.

Reading NVMe registers through BAR0 from user space

Caution lab Mapping resource0 gives raw access to the controller. The script below only reads CAP, VS, CC and CSTS, which are side-effect-free in NVMe. Any write could disable the controller under a mounted filesystem. Use a lab machine; never run modified versions that write. Requires root.

#!/usr/bin/env python3
"""Read-only dump of NVMe CAP/VS/CC/CSTS through BAR0 (needs root; lab machines only)."""
import mmap, os, sys

bdf = sys.argv[1] if len(sys.argv) > 1 else "0000:01:00.0"
fd = os.open(f"/sys/bus/pci/devices/{bdf}/resource0", os.O_RDONLY | os.O_SYNC)
mm = mmap.mmap(fd, 4096, mmap.MAP_SHARED, mmap.PROT_READ)
regs = memoryview(mm).cast("I")          # 32-bit aligned loads, one per register

def r32(off):
    return regs[off // 4]

cap = r32(0x00) | (r32(0x04) << 32)       # low half first, as Linux does
vs, cc, csts = r32(0x08), r32(0x14), r32(0x1C)
print(f"CAP  {cap:016x}: MQES={(cap & 0xFFFF) + 1} entries, CQR={cap >> 16 & 1}, "
      f"TO={(cap >> 24 & 0xFF) * 500} ms, DSTRD={cap >> 32 & 0xF} "

Code / pseudocode

A simulation of BAR sizing against a model function whose BARs have hard-wired low bits, plus NVMe doorbell address calculation. Standard library only; it touches no hardware.

"""BAR sizing against a simulated Type 0 function (simulation, standard library only).

Each simulated BAR has hard-wired low-order bits: the address bits below the region
size read back as 0, and the type bits (0..3) are read-only. That is exactly what
the sizing algorithm relies on."""

class SimFunction:
    def __init__(self, bars):
        # bars: list of 6 (size_bytes, kind) where kind is 'mem32', 'mem64', 'mem64pf',
        # 'io', or None. A 'mem64*' entry consumes the next BAR slot (upper half).
        self.regs = [0] * 6
        self.mask = [0] * 6        # writable bits of each 32-bit BAR register
        self.ro = [0] * 6          # read-only type bits
        i = 0
        while i < 6:
            size, kind = bars[i]
            if kind is None:
                i += 1
                continue
            if kind == "io":
                self.ro[i] = 0x1
                self.mask[i] = (~(size - 1)) & 0xFFFFFFFC
                i += 1
            elif kind == "mem32":
                self.mask[i] = (~(size - 1)) & 0xFFFFFFF0
                i += 1
            else:                                   # 64-bit memory BAR pair
                pf = 0x8 if kind == "mem64pf" else 0
                self.ro[i] = 0x4 | pf               # bits 2:1 = 10b, bit 3 = prefetchable
                full = (~(size - 1)) & 0xFFFFFFFF_FFFFFFF0
                self.mask[i] = full & 0xFFFFFFF0
                self.mask[i + 1] = full >> 32
                i += 2

    def cfg_write(self, idx, value):
        self.regs[idx] = (value & self.mask[idx]) | self.ro[idx]

    def cfg_read(self, idx):
        return (self.regs[idx] & self.mask[idx]) | self.ro[idx]

def human(n):
    for unit, div in (("GiB", 1 << 30), ("MiB", 1 << 20), ("KiB", 1 << 10)):
        if n >= div:
            return f"{n // div} {unit}"
    return f"{n} bytes"

def size_bars(fn):
    """The classic sizing algorithm. Real software clears Command bits 0-1 first
    so the device does not decode a half-written BAR, and restores them after."""
    i = 0
    while i < 6:
        orig = fn.cfg_read(i)
        fn.cfg_write(i, 0xFFFFFFFF)
        rb = fn.cfg_read(i)
        fn.cfg_write(i, orig)                       # restore
        if rb == 0:
            print(f"BAR{i}: unimplemented")
            i += 1
            continue
        if rb & 1:                                  # I/O BAR
            size = ((~(rb & 0xFFFFFFFC)) & 0xFFFF) + 1   # I/O space is 16 bits on x86
            print(f"BAR{i}: I/O, readback {rb:#010x}, size {size} bytes")
            i += 1
            continue
        kind, pf = (rb >> 1) & 3, (rb >> 3) & 1
        if kind == 2:                               # 64-bit: size the upper half too
            orig_hi = fn.cfg_read(i + 1)
            fn.cfg_write(i + 1, 0xFFFFFFFF)
            rb_hi = fn.cfg_read(i + 1)
            fn.cfg_write(i + 1, orig_hi)
            mask = (rb_hi << 32) | (rb & 0xFFFFFFF0)
            size = ((~mask) & 0xFFFFFFFF_FFFFFFFF) + 1
            print(f"BAR{i}/{i+1}: 64-bit memory, prefetchable={pf}, readback "
                  f"{rb_hi:#010x}:{rb:#010x}, size {size:#x} ({human(size)})")
            i += 2
        else:
            size = ((~(rb & 0xFFFFFFF0)) & 0xFFFFFFFF) + 1
            print(f"BAR{i}: 32-bit memory, prefetchable={pf}, readback {rb:#010x}, "
                  f"size {size:#x} ({human(size)})")
            i += 1

def nvme_doorbells(bar0, dstrd, queues):
    stride = 4 << dstrd
    for y in range(queues):
        sq = bar0 + 0x1000 + (2 * y) * stride
        cq = bar0 + 0x1000 + (2 * y + 1) * stride
        print(f"  SQ{y}TDBL {sq:#x}   CQ{y}HDBL {cq:#x}")

if __name__ == "__main__":
    print("Lab SSD (synthetic): 16 KiB 64-bit non-prefetchable BAR0/BAR1")
    lab = SimFunction([(16 * 1024, "mem64"), (0, None), (0, None),
                       (0, None), (0, None), (0, None)])
    lab.cfg_write(0, 0xFE60_0000)                   # address assigned by firmware
    lab.cfg_write(1, 0x0000_0000)
    size_bars(lab)
    print(f"BAR0 after sizing (restored): {lab.cfg_read(0):#010x}")
    print("A different synthetic device: 32-bit BAR0, 64-bit prefetchable BAR2/3, I/O BAR4")
    other = SimFunction([(64 * 1024, "mem32"), (0, None), (256 * 1024 * 1024, "mem64pf"),
                         (0, None), (256, "io"), (0, None)])

Worked example

Problem. A device has: BAR0 reads back FFFF_F000h after all-ones; BAR2 reads back FFFF_FF0Ch and BAR3 reads back FFFF_FFFFh; BAR4 reads back FFFF_FF81h. Decode every BAR, checking the low bits first.

BAR0 = FFFF_F000h. Bit 0 = 0 → memory. Bits 2:1 = 00b → 32-bit. Bit 3 = 0 → non-prefetchable. Mask FFFF_F000h → invert 0000_0FFFh → +1 = 1000h = 4 KiB.

BAR2/3 = FFFF_FFFF:FFFF_FF0Ch. Low byte 0Ch = 1100b: bit 0 = 0 memory, bits 2:1 = 10b 64-bit, bit 3 = 1 prefetchable. Mask the 64-bit value to FFFF_FFFF_FFFF_FF00h → invert FFh → +1 = 100h = 256 bytes. A 256-byte prefetchable 64-bit region (unusual, but legal).

BAR4 = FFFF_FF81h. Bit 0 = 1 → I/O BAR. Mask with …FFFCh → FFFF_FF80h; considering 16-bit I/O space, FF80h → invert 007Fh → +1 = 80h = 128 bytes of I/O space.

Placement. BAR0 must be 4 KiB aligned and below 4 GiB, in the bridge's non-prefetchable window. BAR2/3 may go above 4 GiB, in the prefetchable window, aligned to 256 B (the OS will likely round to a page). BAR4 needs an I/O window in every bridge above it — increasingly unavailable on modern platforms. Derived

Common mistakes

  • Forgetting to mask the type bits before inverting (FFFF_C004h → wrong size).
  • Sizing only the lower half of a 64-bit BAR.
  • Sizing with decode enabled: for a moment the device claims addresses up to 4 GiB.
  • Treating BAR1 of an NVMe device as a separate region. It is the upper half of BAR0.
  • Expecting 64-bit non-prefetchable BARs above 4 GiB behind bridges.
  • Using MMIO reads in the I/O path (each one stalls the CPU for a round trip).
  • Reading doorbells to see the current tail.
  • Assuming the IOMMU translates MMIO. It translates device-initiated DMA only.
  • Ignoring CAP.DSTRD.

Senior engineer insight

BARs are where the CPU's physical address space and the device's internal register space meet; DMA (next chapter) is where the device's view of host memory and the CPU's meet. Keeping "who emits this address, and who translates it" explicit for every address in a trace is the single most valuable habit for reading NVMe traces. A doorbell address is a CPU physical address inside a BAR. An SQ base address in ASQ is an I/O virtual address in host memory.

Is the BAR size fixed regardless of device state and firmware version? Are performance-critical structures (doorbells) separated from side-effect registers so the platform can use relaxed accessors? Is the MSI-X table in its own page so it can be protected separately when the device is assigned to a virtual machine? Is the CMB in a prefetchable BAR so it can be mapped WC and placed above 4 GiB?

Challenge

Add a 128 MiB prefetchable 64-bit BAR to the simulated device and compute where an allocator could place it in a window 0x40_0000_0000–0x40_3FFF_FFFF alongside the existing 256 MiB one.

Hint

(b): mask the low 4 bits of the lower word; the 64-bit value is FFFF_FFF0_0000_0000h. Natural alignment: each BAR's base is a multiple of its size.

Solution

(a) FFE0_0000h: 32-bit non-prefetchable memory, size 0x20_0000 = 2 MiB. (b) Lower 0000_000Ch: 64-bit prefetchable; 64-bit mask FFFF_FFF0_0000_0000h → size 0x10_0000_0000 = 64 GiB. (c) FFFF_FFF1h: I/O, mask FFF0h (16-bit) → size 16 bytes. Questions: (1) bridge windows have 1 MiB granularity. (2) Writes to registers could be merged or delayed/reordered relative to each other — a doorbell might be combined with another write or arrive after a later register write, breaking the programming model; and reads might be speculated. (3) Convention used by Linux's lo_hi_readq for NVMe; CAP is constant so order matters little here, but for changing 64-bit registers a defined order avoids torn reads being misinterpreted. Challenge: 256 MiB at 0x40_0000_0000; 128 MiB at 0x40_1000_0000 (128 MiB aligned); both fit within the 1 GiB window.

What a senior engineer notices

Whether BAR0 is shared with the MSI-X table (impacts virtualisation and protection), whether the CMB (if any) is in a prefetchable BAR, and whether the BAR size covers all doorbells for the maximum number of queues at the advertised stride.

Failure variants

  • resource0 mmap fails with "Operation not permitted": kernel lockdown or secure boot policies block it — use nvme show-regs.
  • Reads return all ones: wrong BDF, device in D3, or link down.
  • Values differ between two reads of CSTS: normal if the controller is changing state.

Model answers

(1) Memory, bits 2:1 = 00b → 32-bit, bit 3 = 1 → prefetchable; mask FFFF_8000h → size 8000h = 32 KiB. (2) DSTRD 0: SQ3 = 0xFE60_1000 + 6×4 = 0xFE60_1018, CQ3 = 0xFE60_101C. DSTRD 1 (stride 8): SQ3 = 0xFE60_1000 + 6×8 = 0xFE60_1030, CQ3 = 0xFE60_1038. (3) PCIe ordering: a read request (non-posted) may not pass earlier posted writes in the same direction, so the read's completion implies the writes reached the device. (4) Below 4 GiB (32-bit non-prefetchable window), 32 MiB-aligned, inside a window the firmware made large enough (1 MiB granularity). (5) BAR0 + 0x28 is the MMIO address of the ASQ register (CPU physical, inside the BAR); the value stored there is the I/O virtual address of the Admin Submission Queue in host memory, which the controller will use for DMA.

    • The IOMMU
    • The CPU's MMU (virtual → physical)
    • The NVMe controller
    • The Data Link Layer
    Answer and reasoning

    The IOMMU translates device-initiated accesses; CPU accesses use the MMU.

    • BAR0 + 1000h
    • BAR0 + 1004h
    • BAR0 + 1008h
    • BAR0 + 1010h
    Answer and reasoning

    1000h + 2×1×4 = 1008h.

  7. Open: Why does a 64-bit non-prefetchable BAR end up below 4 GiB on most systems?

    Model answer

    Bridges forward non-prefetchable memory only through the Memory Base/Limit window, which holds 32-bit addresses; any non-prefetchable BAR behind a bridge must therefore be placed in the lower 4 GiB regardless of its own 64-bit capability.

  8. Open: Describe the sizing algorithm including what software must do with the Command register.

    Model answer

    Clear Memory/I/O Space Enable; save BAR; write all ones; read back; mask type bits; invert and add one (combining both halves for 64-bit); restore BAR; restore Command.

  9. Open: An NVMe driver sees CSTS = FFFF_FFFFh. List three causes.

    Model answer

    Link down / surprise removal; Memory Space Enable cleared (e.g. by error recovery) so MRd gets UR; BAR reassigned after the driver mapped it. Also: device held in reset or in a power state where it cannot respond.

Interview questions

  1. Beginner: What is a BAR?

    Model answer

    A register in a function's configuration header that describes a region (memory or I/O, size, 32/64-bit, prefetchable) and holds the base address software assigns; requests to addresses inside the region are claimed by the device.

  2. Beginner: What is MMIO?

    Model answer

    Memory-mapped I/O: device registers and memory exposed at physical addresses, accessed by ordinary CPU loads and stores, which the Root Complex turns into Memory Read/Write TLPs.

  3. Intermediate: Why are MMIO reads expensive and how do NVMe drivers avoid them?

    Model answer

    They are non-posted; the CPU waits for the full PCIe round trip. NVMe drivers learn about completions by reading the Completion Queue in host memory (phase tag), not by reading device registers, and only write doorbells in the I/O path.

  4. Intermediate: How do you compute NVMe doorbell addresses?

    Model answer

    SQ y tail: BAR0 + 1000h + (2y × (4 << CAP.DSTRD)); CQ y head: BAR0 + 1000h + ((2y + 1) × (4 << CAP.DSTRD)).

  5. Advanced: After hot-plugging an SSD with a large CMB, Linux reports "BAR 2: no space". Explain and fix.

    Model answer

    The prefetchable window behind the hot-plug port was sized at boot without the new device; the CMB BAR does not fit. Fix by reserving larger windows for hot-plug ports (firmware settings or pci=hpmmioprefsize=), using pci=realloc, or rebooting so firmware sizes windows with the device present.

  6. Senior: What are the risks of exposing BAR0 to a virtual machine, and how are they mitigated?

    Model answer

    The guest could reprogram the MSI-X table to target arbitrary addresses or interfere with controller registers. Hypervisors trap/emulate the MSI-X table page (hence the value of placing it on its own page), use interrupt remapping in the IOMMU, and use SR-IOV VFs or mediated devices so each guest gets its own register set; IOMMU protection prevents DMA outside the guest's memory.

Chapter summary

BARs describe and place a device's address regions. Bits 0–3 encode memory/I/O, 32/64-bit and prefetchability; the remaining bits hold the base, with the low-order bits hard-wired to zero to encode a power-of-two size, found by writing all ones and reading back. 64-bit BARs use two slots. Non-prefetchable regions behind bridges must sit below 4 GiB because the non-prefetchable bridge window is 32-bit. Once assigned and enabled, CPU loads and stores to the region become MRd and MWr TLPs — MMIO, translated by the CPU's MMU, not the IOMMU. NVMe maps its controller registers at BAR0 offset 0 (CAP 00h, VS 08h, CC 14h, CSTS 1Ch, AQA 24h, ASQ 28h, ACQ 30h …) and doorbells from 1000h with stride 4 << CAP.DSTRD; on the lab system SQ1TDBL is 0xFE60_1008.

Do not move on until you can:

  • decode any BAR's type bits
  • size 32-bit, 64-bit and I/O BARs by hand
  • explain prefetchable vs non-prefetchable and its consequences
  • trace a CPU store to a doorbell all the way to the device register
  • compute NVMe doorbell addresses for any DSTRD
  • diagnose "no space", UR and all-ones symptoms
