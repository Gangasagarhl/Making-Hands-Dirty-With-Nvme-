Subsystem Local Memory (SLM) gives an NVM Express (NVMe) subsystem a pool of byte-addressable working memory that the host can read, write and fill through ordinary NVMe commands, and that computational programs can use as their scratchpad. This chapter teaches what it is, why it exists, how it is reached, how data moves in and out of it, and how to reason about it in a trace without inventing details the specification does not give you.

Why this chapter exists

In Chapter 61 you met Computational Programs: code that runs inside the non-volatile memory (NVM) subsystem, next to the data. A program needs somewhere to put its input, its intermediate results and its output. It cannot conveniently work directly on NAND flash pages (too slow, too coarse, wear-sensitive), and it should not reach across PCI Express (PCIe) into host memory for every byte (that defeats the purpose of moving compute to the data). The answer the NVM Express (NVMe) family gives is Subsystem Local Memory (SLM), defined in its own command-set specification.

SLM matters even if you never write a computational program. It is the first NVMe command set whose namespaces are memory rather than storage: bytes, not logical blocks; volatile working space, not a persistent medium. That changes how you read Identify data, how you interpret a namespace list, what Linux does with the namespace, and how you decode a trace. A validation engineer who assumes every namespace is a block device will mis-test it; a driver writer who assumes every namespace holds data across power cycles will lose data.

Learning objectives

  • Explain in one paragraph what SLM is and why the NVMe family added it.
  • Distinguish SLM from the Controller Memory Buffer (CMB), the Persistent Memory Region (PMR) and the Host Memory Buffer (HMB).
  • Describe how a host discovers and addresses SLM through memory namespaces and the SLM command set.
  • Describe the read, write and copy paths into and out of SLM, and which side performs the Direct Memory Access (DMA).
  • Explain how SLM and Computational Programs fit together (memory range sets, program inputs and outputs).
  • Recognise an SLM data transfer in a synthetic PCIe trace and reason about an abnormal one.
  • State clearly which SLM details you must confirm in the SLM Command Set Specification, Revision 1.3, rather than assume.

The story

Imagine the giant library from earlier chapters has opened a workshop in its basement. Workers in the workshop (the computational programs) do jobs like "count every book that mentions dragons". They do not carry the books upstairs to your classroom one at a time. Instead they copy the pages they need onto a big workbench in the basement, do the counting there, and leave a small note with the answer on the bench.

The workbench is not a bookshelf. When the lights go out at night, the bench is cleared. It holds working papers, not the library's collection. You, the teacher, can also send a helper to put papers on the bench or read the note off it. That workbench is Subsystem Local Memory.

Think of a commercial kitchen. The walk-in freezer is the NVM namespace: big, durable, slow to get things out of. The stainless-steel prep counter is SLM: limited space, fast, cleaned at the end of the shift. The cooks are compute engines running programs. The front-of-house staff (the host) can put a tray on the counter or take a finished plate from it, but they place orders through tickets (commands), not by walking into the kitchen. A good kitchen moves ingredients from freezer to counter inside the kitchen, without carrying them through the dining room first.

  • Hidden: addressing. A counter has no addresses. SLM is addressed as a memory namespace with byte offsets, and every access is a command with a namespace identifier, an offset and a length.
  • Hidden: the PCIe hop. When the host "takes a plate", the controller's DMA engine writes the bytes into host memory using PCIe Memory Write Transaction Layer Packets (TLPs). The host central processing unit (CPU) never loads from SLM directly in the way it loads from a CMB mapped through a Base Address Register (BAR).
  • Misleading: "cleaned every shift". Whether SLM content survives a reset, and which resets clear it, is defined by the specification and may be implementation-dependent; do not assume it is wiped or preserved on any particular reset without checking.
  • Misleading: one counter. A subsystem may expose several memory namespaces, and how they map onto physical dynamic RAM (DRAM) or static RAM (SRAM) inside the device is invisible and implementation-dependent.

Beginner explanation

An ordinary NVMe namespace is a numbered list of logical blocks (LBAs). You read block 1000, you write block 2000, and the device remembers what you wrote even after power is removed.

A memory namespace from the SLM command set is different in three ways:

  1. It is byte-addressed. You talk about "offset 0x4000, 256 bytes", not "LBA 32, 1 block".
  2. It is working memory. It exists to hold data that is being processed, not data you want to keep. Treat it as volatile unless the specification and the device tell you otherwise.
  3. It lives inside the NVM subsystem. Programs that run in the subsystem can reach it without crossing PCIe. The host reaches it with NVMe commands that move bytes between host memory and SLM.

The host does three basic things with SLM:

  • Write: copy bytes from host memory into SLM (for example, a list of search keys a program will use).
  • Read: copy bytes from SLM into host memory (for example, the result a program produced).
  • Copy inside the subsystem: move data from an NVM namespace into SLM (or between memory regions) without the data ever going to the host.

That third operation is the whole point. If a program needs to scan 100 GiB of logs to produce a 4 KiB answer, the 100 GiB should go from flash to SLM inside the device, and only the 4 KiB answer should cross PCIe.

Engineering explanation

What SLM is

SLM is memory within an NVM subsystem that is accessed through the SLM I/O command set. The SLM Command Set Specification defines a namespace type — commonly called a memory namespace — whose contents are addressed in bytes. A controller that supports the command set reports it through the usual command-set discovery mechanism of the NVMe Base Specification (the I/O Command Set profile and the per-namespace Command Set Identifier, CSI), and the host identifies each memory namespace with the command-set-specific Identify data structures the SLM specification defines. Verified that SLM is a separate command-set specification in the NVMe 2.4 family, at Revision 1.3 NVM Express specifications index, 2026-08 release. The open-source libnvme library encodes the SLM Command Set Identifier as 03h (and Computational Programs as 04h), as used in Chapter 61; confirm it in the Base 2.4 CSI definition. Uncertain the names of the SLM Identify structures — read them from the SLM specification rather than from this page.

Why it exists

Computational storage has three ingredients: something to run (programs), somewhere to run it (compute engines), and something to run it on (data in working memory). NVMe standardised them as two cooperating command sets: Computational Programs for the first two, and SLM for the third. Splitting memory into its own command set has a clear benefit: SLM can be used, tested and managed independently, and it can in principle serve consumers other than computational programs. Derived

Before SLM, vendors who built computational storage drives exposed working memory through vendor-specific commands, through a CMB repurposed as a scratchpad, or through a separate accelerator function with its own driver. Every product looked different, so host software could not be portable. SLM replaces those private mechanisms with a standard namespace type and standard commands.

How SLM differs from CMB, PMR and HMB

NVMe already had three "memory" features before SLM. Mixing them up is the single most common mistake in this area, so compare them carefully.

CMB and PMR are reached by address; SLM is reached by command. If you see the CPU issuing MMIO reads to a BAR window to fetch data, that is CMB or PMR. If you see a submission queue entry followed by controller-initiated DMA, that is a command — possibly to SLM.

Access: memory namespaces, offsets and lengths

The host addresses SLM with three things: a namespace identifier (NSID) that names the memory namespace, a byte offset within it, and a length. The host-memory side of a transfer is described with the familiar data pointer in the submission queue entry (SQE) — PRPs or SGLs, as allowed by the controller. Derived from the fact that SLM commands are NVMe I/O commands carried in 64-byte SQEs. Uncertain which command dwords carry the offset and length, their units, and any alignment or granularity rules: these are SLM-specific and must be read from the command definitions.

Because SLM is byte-addressed, alignment questions that never arise with block namespaces appear immediately: may an access start at an odd byte offset? May it cross an internal boundary? Is there a maximum transfer size distinct from the controller's Maximum Data Transfer Size (MDTS)? The specification answers these, or declares them implementation-reported; the host discovers the answers from Identify data. Write your test plan around whatever the device reports, never around a guess.

Read, write and copy

The SLM command set provides commands to:

  • read a byte range of a memory namespace into host memory (Memory Read);
  • write a byte range of a memory namespace from host memory (Memory Write);
  • fill or initialise a range, and copy data into SLM from other namespaces in the same subsystem.

Uncertain The command names above are given as the specification's concepts. Confirm the exact command names, opcodes and which copy variants (NVM namespace → memory namespace, memory → memory, memory → NVM namespace) exist in SLM 1.3 and in the NVM Command Set 1.3 Copy command, which gained cross-namespace capabilities in the 2.x era. Do not hard-code opcodes from this page.

An SLM write command makes the controller issue PCIe reads (it fetches the bytes from host memory). An SLM read command makes the controller issue PCIe writes. This inversion is the same as for NVM READ and WRITE, and new engineers trip on it every time they look at a trace.

Relationship to computational storage

The Computational Programs command set (Chapter 61) introduces compute namespaces, programs, and a way to describe the memory a program may use: a memory range set, a list of ranges within one or more memory namespaces. When the host executes a program, it names the memory range set; the program reads its input from those ranges and writes its output into them. SLM is therefore the data plane of computational storage, while Computational Programs is the control plane.

The central concept on the ladder

The library basement has a workbench. Workers copy pages onto it, do their job there, and leave a small answer. The teacher can put papers on the bench or read the answer by sending a helper with a ticket.

SLM is byte-addressable working memory inside the NVM subsystem, exposed as memory namespaces. The host moves data in and out with SLM I/O commands; programs and internal copies use it without crossing PCIe.

Physically it is DRAM or SRAM attached to the controller application-specific integrated circuit (ASIC) or to a compute complex inside the drive. The controller's DMA engine moves bytes between it and host memory; internal data-path hardware moves bytes between flash and SLM. Capacity, bandwidth and volatility are product decisions.

The SLM Command Set Specification 1.3 defines the memory namespace, its Identify data, and the SLM I/O commands; the Base Specification 2.4 defines command-set discovery and namespace management; Computational Programs 1.3 defines memory range sets that reference SLM.

Across the interface: SQ tail doorbell (MWr from the root complex), SQE fetch (MRd from the device), data movement (device MRd for host→SLM, device MWr for SLM→host, none for internal copies), CQE post (device MWr), Message Signaled Interrupts Extended (MSI-X) write (device MWr).

In an analyzer the SLM command looks like any I/O command until you decode the SQE: the NSID points at a memory namespace and the opcode is from the SLM set. Byte-granular lengths may produce data TLPs whose sizes are not multiples of 512 or 4096.

If a result read returns stale data, check ordering (was the read submitted before the program's completion was observed?), check the range set, then check whether a reset cleared SLM. If a copy is slow, the problem is internal and invisible to PCIe — use completion timing and vendor telemetry, not the link trace.

The sixteen questions for SLM

1. What is it?
Byte-addressable working memory inside an NVM subsystem, exposed as memory namespaces and accessed with the SLM command set.
2. Why was it created?
To give computational programs (and the host) a standard place to stage and process data inside the subsystem.
3. What problem does it solve?
Moving bulk data across PCIe just to process it; vendor-specific scratchpad mechanisms that made software non-portable.
4. What existed before it?
CMB repurposed as scratch space, vendor-unique commands, separate accelerator functions with private drivers.
5. Why is the current design better?
It reuses the NVMe namespace, queue, data-pointer and status machinery, so discovery, error handling and tooling are shared and standard.
6. Who creates it?
The device provides the memory; memory namespaces are reported by the controller and, depending on the device and specification rules, may be created or attached with namespace management. Implementation-dependent
7. Who consumes it?
Computational programs (via memory range sets), the host (via read/write), and internal copy operations.
8. Where does it live?
Inside the NVM subsystem; physically in device DRAM/SRAM. Not in host memory, not in a BAR window.
9. What memory/registers are involved?
No dedicated controller registers for data access; the SQ/CQ in host memory, host data buffers described by PRP/SGL, Identify data structures, and the memory namespace itself.
10. What happens before it?
Controller initialisation, command-set selection, Identify of the memory namespace, often creation of a memory range set.
11. What happens after it?
A program executes on the data, or the host reads the result; the range set may be deleted and the memory reused.
12. What happens if it is wrong?
Out-of-range accesses fail with an error status; wrong ordering gives stale results; assuming persistence loses data after reset.
13. What does the protocol analyzer show?
Doorbell, SQE fetch, data TLPs for host transfers only, CQE, MSI-X. Internal copies show only command and completion.
14. What does Linux show?
Typically a generic character device (/dev/ngXnY) for a namespace whose command set the kernel block layer does not support; no block device.
15. What would a validation engineer test?
Boundaries, byte-granular lengths, alignment, data integrity round trips, concurrent access from several queues, behaviour across each kind of reset, error statuses for invalid ranges.
16. What would a senior engineer suspect when it fails?
Host-side ordering assumptions, misreported capacity/granularity, reset semantics, range-set lifetime, and confusion between SLM and CMB.

Hardware view

Inside a computational storage drive, SLM is usually a slice of the drive's DRAM — the same DRAM that, in an ordinary solid-state drive (SSD), holds the flash translation layer (FTL) mapping table and write buffers — or a dedicated memory attached to the compute complex. Implementation-dependent The specification does not say which; it defines behaviour at the command interface.

DRAM inside an SSD is shared. An SSD that dedicates a large slice of DRAM to SLM has less for FTL caching and write buffering, which can change ordinary I/O performance. If you benchmark NVM I/O while programs use SLM heavily, expect interaction. Derived

Volatility is a hardware property with specification consequences. DRAM loses its content on power loss; a device may or may not have power-loss protection that covers SLM. Treat SLM content as lost on power loss unless the SLM specification and the device's reported capabilities guarantee otherwise.

Because SLM commands are NVMe I/O commands, they use 64-byte SQEs, 16-byte CQEs, normal queue and doorbell mechanics, and the controller's DMA for host transfers. Therefore, on NVMe over PCIe, host transfers produce ordinary MRd/CplD/MWr traffic, and internal copies produce no data TLPs.

For the reverse direction (SLM→host Memory Read), row 4–5 become device-issued MWr TLPs of at most 256 bytes (the MPS), and the ordering rule that matters is PCIe's: posted writes are not passed by the later posted CQE write, so when the host sees the CQE, the data writes ahead of it have been delivered (see Chapter 14 and Chapter 52).

Ordering inside the subsystem is a different matter. If the host submits "execute program" on one queue and "read result" on another without waiting for the program's completion, NVMe gives no ordering guarantee between the two commands. PCIe ordering cannot rescue a host that never waited. Derived from NVMe's general rule that commands are not ordered across or within queues unless a specific mechanism says so.

Errors

SLM commands complete with a status in the CQE like any NVMe command: generic status values (for example Invalid Field in Command, or a namespace/range error) and command-set-specific values defined in SLM 1.3. Treat any error mapping you see in vendor documentation as a claim to verify against the specification.

Linux view

The Linux NVMe driver creates a block device (/dev/nvme0n1) only for namespaces whose command set the block layer understands (the NVM command set, and Zoned Namespaces (ZNS) for zoned block devices). Since around kernel 5.13, it also creates a generic character device (/dev/ng0n1, /dev/ng0n2, …) for every namespace, including namespaces of command sets the kernel does not otherwise support. That generic device is how user space reaches a memory namespace today: through passthrough ioctls or io_uring passthrough. Version-dependent — check your kernel; native SLM support in Linux, if any is added, may change this.

# Which namespaces exist and which devices did the kernel create for them?
ls -l /dev/nvme0n* /dev/ng0n* 2>/dev/null
sudo nvme list -v

# Which I/O command sets does the controller support? (look for the command-set vector / profile)
sudo nvme id-ctrl /dev/nvme0 -H | less

# Namespace list per command set (the --csi value comes from the SLM spec; do not guess it)
sudo nvme list-ns /dev/nvme0 --all

# Independent, command-set-agnostic namespace identification
sudo nvme cmdset-ind-id-ns /dev/nvme0 -n 3   # subcommand name varies by nvme-cli version; check nvme help

# Kernel messages about unsupported command sets
sudo dmesg | grep -i nvme

Code / pseudocode

The first block is pseudocode for a host library that uses SLM safely. The second is a runnable simulation (standard-library Python) of a memory namespace that enforces the rules a validation engineer checks: bounds, granularity, and volatility across a reset. Granularity and capacity in the simulation are parameters, not specification values.

/* Pseudocode: run a filter program on 32 MiB of NVM data and fetch a small result. */
int run_filter(ctrl_t *c, u32 nvm_nsid, u64 slba, u32 nlb, u32 mem_nsid)
{
    /* 1. Discover: confirm the controller supports SLM and CP, and read memory-namespace limits */
    slm_limits_t lim = slm_identify(c, mem_nsid);          /* capacity, granularity, max xfer */
    if (!lim.valid) return -ENODEV;

    /* 2. Stage input inside the subsystem (no host transfer) */
    status_t s = submit_and_wait(c, copy_nvm_to_mem(nvm_nsid, slba, nlb, mem_nsid, /*off*/0));
    if (s != SUCCESS) return map_status(s);

    /* 3. Execute the program on a memory range set that covers input and output */
    rs_t rs = create_range_set(c, mem_nsid, /*in*/0, nlb_bytes(nlb), /*out*/OUT_OFF, OUT_LEN);
    s = submit_and_wait(c, exec_program(PROG_FILTER, rs));   /* MUST wait: no cross-command ordering */
    if (s != SUCCESS) { delete_range_set(c, rs); return map_status(s); }

    /* 4. Read only the result across PCIe */
    s = submit_and_wait(c, mem_read(mem_nsid, OUT_OFF, OUT_LEN, host_buf));
    delete_range_set(c, rs);
    return s == SUCCESS ? 0 : map_status(s);
}
#!/usr/bin/env python3
"""Toy model of a memory namespace for validation thinking. Not the SLM specification:
granularity, capacity and status names here are illustrative parameters."""
import os

class MemoryNamespace:
    def __init__(self, nsid, capacity, granularity=1, max_xfer=128 * 1024):
        self.nsid, self.capacity = nsid, capacity
        self.gran, self.max_xfer = granularity, max_xfer
        self.mem = bytearray(os.urandom(capacity))  # undefined content after power-on

    def _check(self, off, length):
        if length == 0 or length > self.max_xfer:
            return "INVALID_FIELD"
        if off % self.gran or length % self.gran:
            return "INVALID_FIELD"
        if off + length > self.capacity:
            return "OUT_OF_RANGE"
        return "SUCCESS"

    def write(self, off, data):
        st = self._check(off, len(data))
        if st == "SUCCESS":
            self.mem[off:off + len(data)] = data
        return st

    def read(self, off, length):
        st = self._check(off, length)
        return st, (bytes(self.mem[off:off + length]) if st == "SUCCESS" else b"")

    def power_cycle(self):
        self.mem = bytearray(os.urandom(self.capacity))  # volatile: content lost

def test():
    ns = MemoryNamespace(nsid=3, capacity=1 << 20, granularity=4)
    pattern = bytes((i * 7) & 0xFF for i in range(600))
    assert ns.write(0x4000, pattern) == "SUCCESS"
    st, back = ns.read(0x4000, 600)
    assert st == "SUCCESS" and back == pattern, "round trip failed"
    assert ns.write(0x4001, b"abcd") == "INVALID_FIELD", "misaligned offset accepted"
    assert ns.read((1 << 20) - 8, 16)[0] == "OUT_OF_RANGE", "overrun accepted"
    ns.power_cycle()
    st, after = ns.read(0x4000, 600)
    print("round trip ok; bounds ok; after power cycle data preserved?", after == pattern)

if __name__ == "__main__":
    test()

Worked example

Scenario (synthetic): a log-analytics service wants to count error lines in 64 GiB of logs stored in namespace 1 of the lab SSD (Gen4 x4). The drive offers a 1 GiB memory namespace (NSID 3) and a filter program. Compare moving the data to the host versus processing in the subsystem.

Step 1 — host-side processing cost

Tlink = D / Beff
Tlink
time to move the data across PCIe, seconds
D
bytes to move (64 GiB ≈ 68.7 × 10⁹ bytes)
Beff
effective payload bandwidth; Gen4 x4 raw ≈ 7.88 GB/s after 128b/130b encoding; assume ≈ 6.8 GB/s after TLP and flow-control overheads (illustrative)

Tlink ≈ 68.7 / 6.8 ≈ 10.1 s, and the host CPU must also scan 64 GiB. In practice flash read bandwidth may be the real limit, so the link is not always the bottleneck — but every byte also costs host memory bandwidth and CPU cycles.

Step 2 — in-subsystem processing

SLM is 1 GiB, so the job runs in 64 chunks: copy 1 GiB NVM → SLM (internal), execute the filter on the chunk, read an 8-byte counter. Link traffic per chunk ≈ three commands × (64-byte SQE + 16-byte CQE + MSI-X) + 8 bytes of result ≈ a few hundred bytes. For 64 chunks: tens of kilobytes instead of 64 GiB.

Step 3 — what limits it now

The internal flash read bandwidth and the compute engine's throughput. If internal bandwidth is, say, 6 GB/s, the copy phase alone takes ≈ 11 s — about the same as the host path. The win is not raw speed here; it is freeing the link, host memory bandwidth and CPU for other work, and scaling when many drives run in parallel. Derived All numbers are illustrative.

Step 4 — pipelining

With two halves of SLM (two 512 MiB buffers), the host can copy chunk n+1 while the program processes chunk n. Each step must wait on the right completion: the program on buffer A may start only after A's copy completes; the copy into A again may start only after the program on A completes and its result has been read. Writing that dependency graph down is the senior skill here.

Common mistakes

  1. Calling SLM "the CMB". CMB is BAR-mapped; SLM is command-accessed. The tools, traces and failure modes are different.
  2. Assuming persistence. Storing anything in SLM you cannot regenerate.
  3. Assuming ordering between commands. Reading a result before observing the program's completion (see the abnormal trace).
  4. Using block-device thinking. Expecting LBA formats, 512-byte multiples, or a /dev/nvme0nX block device.
  5. Hard-coding opcodes or CSI values from blog posts instead of the SLM 1.3 specification.
  6. Ignoring granularity and maximum transfer limits that the memory namespace reports.
  7. Forgetting range-set lifetime. Deleting or reusing a memory range set while a program still references it.
  8. Diagnosing internal copies with a PCIe analyzer. The link is silent by design; the evidence is completion latency and device telemetry.

For any "wrong data" report, separate three questions: did the bytes on the link match what the device intended to send (trace)? Did the device intend the right bytes (correct offset and ordering)? Senior engineer insight

SLM is a quiet but important architectural shift: NVMe is no longer only a block-storage protocol; it is becoming a general command-and-data transport between a host and an intelligent subsystem. Seniors notice three consequences.

  • Correctness moves into host software. NVMe has always left inter-command ordering to the host; with computational storage, the dependency graph (copy → execute → read) is application-specific and easy to get wrong. Good host libraries encode the graph so applications cannot violate it.
  • Observability gets worse. The interesting work happens inside the subsystem, where a PCIe analyzer cannot see. Validation plans must rely on completion timing, status values, logs, and vendor telemetry. Ask suppliers early what they expose.
  • Resource contention is a design question. SLM, FTL caches and write buffers share device DRAM and internal bandwidth. Quality-of-service promises for normal I/O must be re-validated with SLM in use.

When someone says "it's just memory", ask: who owns it, who clears it, who orders access to it, and what proves its content is the content you think it is. Those four questions find most SLM bugs.

Questions

  2. Why can the abnormal trace not be detected by a protocol-compliance checker?

Challenge

Add two submission queues to the simulator with a random execution order between them, run the "execute then read" sequence 1,000 times without waiting, and count stale results.

Hints

Model "program execution" as a function that writes the output range after a random delay; model the read as returning whatever is there when it runs. Use random.random() to choose which queue the device services first.

Solution

Step 1 boundary cases: zero length → reject; max length → accept; max+1 → reject; last valid byte (offset = capacity − granularity, length = granularity) → accept; offset = capacity → reject; misaligned offset/length → reject when granularity > 1.

Step 2: the reset table should be data-driven, e.g. CLEARS = {"controller": ?, "function": ?, "subsystem": ?, "power": True}, with question marks filled only from the specification; power loss clearing volatile DRAM is the only safe default.

Step 3: rows 1, 3, 7 belong to CID 0x0050; rows 2, 4, 5, 6 to CID 0x0051. All rows are protocol-legal. The missing dependency is "SQE for 0x0051 must not be submitted until the CQE for 0x0050 is consumed".

Questions: host↔SLM reads/writes produce data TLPs; NVM→SLM copies and resets do not. A compliance checker validates each transaction against PCIe and NVMe rules; the error is a violation of an application-level dependency NVMe deliberately does not enforce.

Challenge: with a 50/50 service order, roughly half the runs return stale data; with waiting, zero.

What a senior engineer notices

That the test plan has an explicit reset axis and an explicit concurrency axis, and that every "expected" value for reset behaviour is traceable to a specification statement rather than to the simulator author's assumption.

Failure variants

  • Device reports granularity 64 but silently accepts misaligned accesses (rounding down) — data lands at the wrong offset.
  • Maximum transfer for SLM smaller than MDTS — the host library splits by MDTS and fails.
  • Range set deleted while a program still runs.

Extension

On real hardware that supports SLM: use nvme-cli's io-passthru against the ng device to perform a write/read round trip, filling opcodes and dwords strictly from SLM 1.3. Capture with an analyzer if available and compare the data TLP sizes to your prediction.

Exercises

  1. Draw the four memories (CMB, PMR, HMB, SLM) on one diagram of host + device, with an arrow for who initiates each access.
  2. For a 1,500-byte SLM Memory Write in the lab system (MRRS 512, RCB 64), list the minimum number of device read requests and explain why the number of completions may be larger.
  3. Write the dependency graph for a two-buffer pipeline of copy → execute → read over eight chunks.
  4. List five SLM-related questions you would put to a drive vendor before qualification.
  5. Find in the SLM 1.3 specification the statement that defines what happens to SLM content on a Controller Level Reset, and paraphrase it.
Model answers

1: CMB/PMR — host CPU initiates via MMIO into the device BAR; HMB — device initiates DMA into host DRAM; SLM — host submits a command, device initiates DMA (host transfers) or internal moves.

2: ceil(1500/512) = 3 read requests (512, 512, 476 if aligned); each may be completed in several CplDs at 64-byte RCB boundaries, so completions ≥ 3.

3: For chunk i on buffer b = i mod 2: copy(i) depends on read(i−2) completing; exec(i) depends on copy(i); read(i) depends on exec(i).

4: Capacity and granularity; volatility per reset type; internal bandwidth; contention with normal I/O; telemetry exposed for programs and copies; revision of SLM/CP supported.

5: Answer depends on your reading — record the statement name and quote briefly; do not answer from memory.

Quiz

  1. How does a host access SLM?

    • By MMIO loads and stores through a BAR window
    • By NVMe I/O commands addressed to a memory namespace
    • By the controller using a Host Memory Buffer
    • Through PCIe configuration space
    Answer and reasoning

    SLM is command-accessed. BAR windows are CMB/PMR; HMB is host memory used by the device; configuration space holds capabilities, not data.

  2. An SLM Memory Write (host → SLM) of 1 KiB produces which data TLPs?

    • Host-issued MWr to the device BAR
    • Device-issued MWr to host memory
    • Device-issued MRd to host memory, answered by CplD
    • No data TLPs
    Answer and reasoning

    The controller must fetch the bytes from host memory, so it issues read requests and receives completions with data.

  3. An NVM-namespace → SLM copy of 32 MiB produces how many data TLPs on the link?

    • None; only command, completion and interrupt traffic
    • About 131,072 MWr of 256 bytes
    • About 65,536 MRd of 512 bytes
    • It depends on MPS only
    Answer and reasoning

    Both source and destination are inside the subsystem.

  4. Which specification defines memory range sets?

    • PCIe Base Specification
    • NVMe Base Specification only
    • NVMe-MI 2.2
    • Computational Programs Command Set 1.3
    Answer and reasoning

    Range sets describe the SLM a program may use; they belong to the Computational Programs command set, which references SLM.

  5. Why does Linux typically show /dev/ng0n3 but no /dev/nvme0n3 for a memory namespace?

    Model answer

    The block layer creates block devices only for command sets it supports (NVM, ZNS). The generic character device is created for every namespace so user space can use passthrough.

  6. A result read returns stale data with status Success. Name the first piece of evidence you check.

    Model answer

    Whether the program's completion (CQE) was observed by the host before the read was submitted — correlate CIDs and timestamps.

  7. True or false: SLM content is guaranteed to survive a Controller Level Reset.

    Model answer

    Not something to assume. The behaviour is defined (or left implementation-dependent) by the SLM specification; check it. Never assume either way.

  8. Why is a 600-byte data transfer a useful clue in a trace?

    Model answer

    Block namespaces transfer multiples of the LBA size (512 B or 4 KiB). A byte-granular size suggests a memory namespace (or a metadata/other structure), prompting you to decode the SQE's NSID and opcode.

  9. Name two reasons in-subsystem processing can help even when it is not faster end-to-end.

    Model answer

    It frees PCIe bandwidth, host memory bandwidth and CPU cycles for other work; it scales across many drives in parallel; it reduces data exposure outside the device.

Interview questions

  1. Beginner: What is Subsystem Local Memory?

    Model answer

    Byte-addressable working memory inside an NVMe subsystem, exposed as memory namespaces and accessed through the SLM command set, mainly to support computational programs.

  2. Beginner: How is SLM different from the CMB?

    Model answer

    The CMB is mapped into a BAR and accessed by address (MMIO); SLM is accessed by NVMe commands with the controller performing DMA.

  3. Intermediate: Describe the PCIe traffic for an SLM read of 600 bytes on a link with MPS 256.

    Model answer

    Doorbell MWr from RC; device MRd for the SQE and CplD back; three device MWr of 256, 256, 88 bytes to the host buffer; MWr CQE; MSI-X MWr; host CQ head doorbell.

  4. Intermediate: Why must the host wait for a program's completion before reading its output?

    Model answer

    NVMe does not order separate commands; the controller may execute the read first. Only the program's CQE tells the host the output is final.

  5. Advanced: How would you validate SLM reset behaviour?

    Model answer

    Write known patterns, apply each reset type in isolation (Controller Level Reset via CC.EN, Function Level Reset, NVM Subsystem Reset, power cycle), read back, and compare with the specification's statements; also test that commands outstanding at reset complete or abort correctly.

  6. Senior: A customer reports computational storage results are wrong 1% of the time. How do you approach it?

    Model answer

    Separate host logic from device behaviour: capture CID/timestamp logs to check dependency ordering; reproduce with explicit serialisation; check range-set lifetime and offsets; then, if host logic is clean, write known patterns to SLM with no program and read back under load to isolate SLM integrity; finally involve vendor telemetry for program execution. Report confidence at each step.

  7. Senior: What would you ask before committing a product to SLM-based offload?

    Model answer

    Supported revisions of SLM/CP; capacity and granularity; volatility and reset semantics; QoS interaction with normal I/O; telemetry and debug access; operating-system/driver support (likely passthrough only); multi-vendor portability.

Model teach-back (senior)

SLM turns the drive into a place where work happens, so the host must express dependencies NVMe never orders for it, and the evidence of correctness moves from the link to completion semantics and device telemetry. Validation therefore needs a concurrency axis, a reset axis, boundary tests derived from Identify-reported limits, and an agreement with the vendor on internal observability.

Chapter summary

SLM is byte-addressable working memory inside an NVM subsystem, exposed as memory namespaces and defined by the SLM Command Set Specification, Revision 1.3. It exists so that computational programs, and the host, have a standard place to stage and process data next to storage. The host reaches it with NVMe I/O commands: a write makes the device read host memory; a read makes the device write host memory; an internal copy moves data without touching the link. Computational Programs refer to SLM through memory range sets. SLM is not the CMB, not the PMR and not the HMB. Treat it as volatile, never assume ordering between commands, and read all field-level details from the specification.

Do not move on until you can:

  • explain SLM in one paragraph and contrast it with CMB, PMR and HMB
  • draw the copy → execute → read flow with the completions the host must wait for
  • predict the TLPs for an SLM read and an SLM write of a given size in the lab system
  • explain why an internal copy is silent on the link
  • diagnose the stale-result trace and name the first abnormal event
  • list what you must confirm in SLM 1.3 rather than assume
