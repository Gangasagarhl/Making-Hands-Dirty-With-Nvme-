An NVMe controller reports trouble through five different channels, each with its own lifetime and blind spots: the completion status of a command, the Error Information log, asynchronous events, the controller fatal bit, and silence. This module goes beyond decoding a status code: it follows errors through retry policy, log rings, event masking and abort races, and teaches you to decide what the controller is really telling you and whose problem it is.

Orientation

NVMe Errors gave you the Status Field layout (Status Code, Status Code Type, Command Retry Delay, More, Do Not Retry), the common status tables, the Error Information log, Asynchronous Event Requests, aborts and Controller Fatal Status. Error Correlation showed how to merge evidence and find the first abnormal event. This module assumes both and goes deeper in four directions: the life cycle of an error report (how long each channel keeps its evidence and what overwrites or masks it), the host's response (retry, delay, abort, reset, fail) and how it can make things worse, the races between those responses and the controller, and the evidence gaps where NVMe says nothing even though something went wrong.

Needed first: NVMe Errors (status layout and tables), Error Correlation (timeline discipline), Admin Commands (Get Log Page, Abort, Asynchronous Event Request), NVMe Reset, and SMART / Health for the health log fields.

Where this goes next: PCIe Errors covers the layer below, which often hides behind an NVMe Data Transfer Error; Reset covers recovery; SMART and Health covers the long-term health channel.

Kid story

A school has a homework tray. Every homework sheet that goes in comes back with a sticker. A green sticker means "done". A red sticker has a word on it, like "smudged" or "wrong page", and sometimes a little note: "don't send this again, it will never work", or "try again after lunch", or "there's more in the teacher's notebook".

The teacher's notebook only has room for a few pages. When it fills up, she rubs out the oldest notes. So if you want to know more about a red sticker, you had better look soon.

There is also a bell on the wall. The class leaves a "ring me if anything happens" card with the teacher. When something happens that isn't about any one homework, like the room getting too hot, she rings the bell once and uses up the card. She won't ring again for the same kind of problem until somebody comes and reads what she wrote, and gives her a fresh card.

And if the teacher faints, there are no stickers at all. The tray just stops coming back.

What it hides. The sticker's word is two-level (Status Code Type and Status Code), and the same Status Code means different things under different types and for different commands. The notebook entry links back to the sheet only by queue and command identifier, which are reused. The story also hides that the host, not the teacher, decides whether to resend, and that the host can make the "teacher" faint less often or more often through its own behaviour (aborts, resets, retry storms).

Where it misleads. A red sticker sounds like "the school made a mistake"; in NVMe, most error statuses mean the request was wrong (host bug) or the data path below failed (PCIe), not that the controller is broken. And the story implies one bell: a host can keep several AER commands outstanding, and events of different types are masked independently.

Mechanism

We follow one error from detection to final outcome on the lab system: a READ of LBA 0x0010_2403 that the media cannot recover, with M = 1 and DNR = 0, on a host that retries.

  1. Detect. Who: controller media back end. What: error correction fails after internal retries. Where: inside the SSD. Evidence: a long gap with no data TLPs for the command.
  2. Log. Who: controller. What: new Error Information entry with Error Count n + 1, SQID 1, CID, status, LBA 0x0010_2403, NSID 1. Where: controller-internal ring. Evidence: visible only when the host reads the log.
  3. Complete. Who: controller. What: CQE with SCT 2h, SC 81h (Unrecovered Read Error), M = 1, DNR = 0. Where: host CQ. Evidence: MWr64 of the CQE; DW3 = 0x4503_xxxx with phase 1.
  4. Notify. Who: controller. What: MSI-X. Evidence: MWr32 to the vector address.
  5. Decide. Who: host driver. What: DNR = 0 and retries remaining → requeue; CRD = 0 → no delay. Where: host memory (request retry count). Evidence: nvme_complete_rq tracepoint with non-zero status and retries; later a new nvme_setup_cmd for the same LBA.
  6. Retry. Who: host, then controller. What: same command resubmitted (often with a new CID). Evidence: doorbell, fetch, long gap, same error.
  7. Give up. Who: host after max retries. What: block layer receives an I/O error; the application sees EIO. Evidence: kernel log naming the command, LBA and status; block-layer I/O error line.
  8. Collect. Who: operator or a tool. What: Error Information log and SMART log read. Evidence: entries for each attempt (if the ring kept them); SMART media error count incremented.

Asynchronous events: arm, fire, mask, read, re-arm

  1. The host submits one or more Asynchronous Event Request commands at initialisation. They stay outstanding indefinitely.
  2. The host enables the event types it wants through the Asynchronous Event Configuration feature and thresholds (for example the Temperature Threshold feature).
  3. An event occurs. The controller completes one outstanding AER with Dword 0 holding the event type, event information and log page identifier.
  4. Further events of that type are masked.
  5. The host reads the indicated log page with RAE cleared; the event type is unmasked.
  6. The host submits a new AER command to replace the one consumed.

If step 5 or step 6 is skipped, the controller has fewer ways (or no way) to tell the host about the next event. That gap is behind several of the debugging patterns below.

The central concept on the ladder

The central concept is the error report life cycle: every NVMe error report has a channel, a scope, a reader and a lifetime, and the host's response changes what evidence survives.

Red stickers come back on each sheet; the notebook forgets old notes; the bell rings once per kind of problem until someone reads; a fainted teacher returns nothing.

Each command's CQE carries a status with retry hints; the Error Information log holds recent detail; asynchronous events report conditions not tied to a command and stay masked until read; CFS means the controller needs a reset; a missing completion is detected only by host timeout.

The controller's completion engine writes the status into the CQE; firmware maintains the log ring and event masks in controller memory; the CSTS register exposes CFS; the host's timers and retry counters live in driver memory.

NVMe Base 2.4 defines the Status Field, status code types and generic and command-specific codes, the Error Information log, the Asynchronous Event Request command and event types, Get Log Page with RAE, Abort, and CSTS; the NVM Command Set adds I/O-specific codes such as LBA Out of Range. Host retry policy is not specified.

Error completions are ordinary CQE writes followed by ordinary interrupts. Log reads are ordinary admin commands with data transfers. Asynchronous events are completions of long-outstanding admin commands. No PCIe error is involved in any of them.

In a trace, an error is visible only after decoding CQE DW3 (bits 31:17 non-zero) or AER completion DW0. Admin queue activity (Get Log Page, new AER submissions, Abort) right after an I/O error is the host's response.

Ask: which channel reported it, is the report still current, is it the first abnormal event or a consequence (of a lower layer or of the host's own retries), and did the host's response destroy or mask evidence?

Stated in the specification: Status Field bit positions (SC 24:17, SCT 27:25, CRD 29:28, M 30, DNR 31 of DW3); SCT 0h generic, 1h command specific, 2h media and data integrity, 3h path related, 7h vendor specific; Error Information is Log Identifier 01h and SMART / Health Information is 02h; Asynchronous Event Request is admin opcode 0Ch and Abort is 08h; an event type, once reported, is masked until the host reads the associated log page with RAE cleared; AER commands have no timeout; CFS is CSTS bit 1.

Reasoned from the specification: mapping status families to likely owners (host, controller, media, lower layer); the retry-storm latency arithmetic; the conclusion that a host which never re-arms AERs cannot learn of later events. These are engineering interpretations; label them as such in reports.

Implementation-dependent: which status a controller returns when several apply; whether it detects CID conflicts; ring size (ELPE), whether entries survive reset; DNR choice for internal and transient errors; how long internal media retries last before an error is returned; which events are supported; whether Abort ever succeeds on a given controller.

Version-dependent: CRD and Advanced Command Retry arrived in NVMe 1.4; NVMe 2.0 moved I/O-specific statuses into command set specifications; newer revisions add status codes and event information values for new features (for example those in the 2.4 set, whose values must be read there; see 2026 NVMe 2.4 Updates). Linux retry and multipath behaviour changes with kernel version.

The specification does not say how many times a host should retry, how long it should wait without CRD, when to abort versus reset, how to map status to application errors, or whether a media error should take a drive out of service. It does not require an Error Information entry for every error. Check in the specification: the Asynchronous Event Information values per event type; the Error Information log entry layout (byte offsets); the exact Abort completion encoding; which statuses carry command-specific information in DW0.

Never treat "no NVMe error" as "no error": posted DMA failures and some firmware faults complete with success or not at all. Never read a log page with RAE set in production tooling unless you know the driver will read it again with RAE cleared. Never assume an Abort's success means no data was transferred.

The delay between SQE fetch and an error completion tells you which hardware decided. A few microseconds: the command validator (host-caused errors). Exactly the length of a host timeout: the controller never answered and the "error" is the host's own abort or reset.

Ordering and races

  • Abort race. An Abort and its target are processed independently. Possible outcomes: target completes normally before the Abort is examined (Abort reports not aborted); target is aborted (target completes with Command Abort Requested, Abort reports aborted); target is past the point of no return (not aborted, completes later). In every case the target command still produces exactly one completion unless a reset intervenes. A host that frees the target's CID when it sends the Abort, rather than when the target's completion arrives, is wrong.
  • Error log versus CQE. The log entry may be written before or after the CQE; a host that reads the log immediately on M = 1 normally finds it, but the specification does not fix the ordering between the log update and the CQE write Uncertain: confirm in the Error Information log description.
  • Event versus log. An event is reported once per type until the log is read; several underlying occurrences can collapse into one event. The log page tells you the current state, not the history.
  • Reset versus completions. CQEs posted before CC.EN = 0 may be in host memory but unprocessed; after the reset the host must not treat them as completions of reissued commands with the same CIDs.

Failed: events masked forever by a monitoring tool

The host system, as a whole, never cleared the mask: the driver re-armed the AER command (necessary) but did not read the log (also necessary), and the agent read the log in a way that deliberately left events masked. The first abnormal event is therefore an absence (no RAE = 0 read after the first event), and it happened two days before the visible symptom. Fix: exactly one component owns the event cycle and reads with RAE = 0 after each event; monitoring tools read with RAE = 1 only if that owner exists. Intermediate lab — Reading the Error Information ring correctly

Safe lab Python 3, standard library only.

Objective

Prerequisites

Setup

#!/usr/bin/env python3
"""Simulate an NVMe Error Information log ring and a host that reads it.
Entry fields follow the log by name (Error Count, SQID, CID, Status, LBA, NSID); layout is not modelled."""
from collections import deque

STATUS = {(0, 0x02): "Invalid Field in Command", (0, 0x04): "Data Transfer Error",
          (0, 0x80): "LBA Out of Range", (2, 0x81): "Unrecovered Read Error"}

class Controller:
    def __init__(self, elpe):
        self.ring = deque(maxlen=elpe + 1)   # ELPE is zero-based
        self.count = 0
    def log(self, sqid, cid, sct, sc, lba, nsid=1):
        self.count += 1
        self.ring.append({"count": self.count, "sqid": sqid, "cid": cid,
                          "sct": sct, "sc": sc, "lba": lba, "nsid": nsid})
    def get_log_page(self):                  # newest entry first, as hosts usually display it
        return sorted(self.ring, key=lambda e: -e["count"])

def read_and_check(entries, last_seen):
    new = [e for e in entries if e["count"] > last_seen]
    if new:
        oldest_new = min(e["count"] for e in new)
        lost = oldest_new - last_seen - 1
        if lost > 0:
            print(f"  WARNING: {lost} entries overwritten between reads "
                  f"(counts {last_seen + 1}..{oldest_new - 1})")
    for e in sorted(new, key=lambda e: e["count"]):
        name = STATUS.get((e["sct"], e["sc"]), "other")
        print(f"  #{e['count']:>3} SQ{e['sqid']} CID 0x{e['cid']:04X} "
              f"SCT {e['sct']}h SC {e['sc']:02X}h {name:<26} LBA 0x{e['lba']:X}")
    return max([e["count"] for e in entries] + [last_seen])

if __name__ == "__main__":
    c = Controller(elpe=7)                   # 8 entries
    last = 0
    c.log(1, 0x0051, 0, 0x80, 0x74706DA8)    # host sent LBA beyond NSZE
    c.log(1, 0x0072, 2, 0x81, 0x102403)      # media
    print("Read 1:")
    last = read_and_check(c.get_log_page(), last)
    for i in range(6):                       # a retry storm on the same LBA
        c.log(1, 0x1072 + (i << 12), 2, 0x81, 0x102403)
    c.log(2, 0x2190, 0, 0x04, 0x0)           # data transfer error on another queue
    for i in range(4):                       # tool probing unsupported features
        c.log(0, 0x0030 + i, 0, 0x02, 0x0)
    print("Read 2:")
    last = read_and_check(c.get_log_page(), last)
Procedure
  1. Run it and read both outputs.
  2. Change elpe to 63 and rerun.
  3. Move the second read to directly after the Data Transfer Error and rerun.
Observations
With 8 entries, read 2 reports 3 lost entries: the first three retries are gone. With 64 entries, nothing is lost.
Questions
  1. Which interesting entry nearly got overwritten, and by what?
  2. Why can the host not reconstruct timing from the log?
  3. What host behaviour minimises loss?
Expected reasoning
Low-value errors (probing, retry storms) evict high-value ones; read promptly on M = 1; compare Error Count with the last read.
Solution

With ELPE = 7 the ring keeps 8 entries; read 2 sees counts 6–13 and warns that counts 3–5 were overwritten. The Data Transfer Error (count 9) survived, but four harmless Invalid Field entries from a tool probing features came after it; four more such entries would have evicted it. The log has no timestamps per entry, so ordering comes only from Error Count, and timing must come from host-side records (tracepoints, kernel log). The best host behaviour: read the log promptly when M = 1, keep the last Error Count seen and alert on gaps, avoid retry storms (honour DNR, use CRD), and avoid noisy probing in production. Moving the second read earlier shows no loss, because the probes had not happened yet.

Advanced lab — Design and evaluate a retry policy

Safe lab Paper and arithmetic.

Objective
Quantify how retry policy turns NVMe status into application latency and load, and propose a better policy.
Prerequisites
Mechanism; the slow trace.
Setup
Four scenarios on a host with max_retries = 5 and no delay unless CRD is honoured: (A) Unrecovered Read Error, DNR 0, each attempt takes 38 ms; (B) Namespace Not Ready for 250 ms, controller returns CRD 01b (CRDT1 = 100 ms), host honours CRD; (C) the same as B but the host has not enabled Advanced Command Retry, so CRD = 0 and each attempt takes 3 µs; (D) Invalid Field in Command, DNR 1.
Procedure
For each, compute the time until the application sees success or failure, the number of commands sent, and the outcome.
Questions
  1. Which scenario has the worst latency, and which the worst outcome?
  2. What policy change improves each?
Expected reasoning
Retries multiply attempt time; immediate retries are useless for time-based conditions; DNR stops retries.
Solution

(A) 1 + 5 = 6 attempts × 38 ms = 228 ms, then EIO; 6 commands; likely futile because the same LBA fails each time (the drive has already run its own recovery). (B) attempts at 0, 100, 200 ms fail, at 300 ms succeed: about 300 ms, 4 commands, success. (C) 6 attempts within about 20–30 µs (including submission overhead), then failure with Namespace Not Ready: fast failure of an operation that would have succeeded in 250 ms; worst outcome. (D) 1 command, immediate failure: correct. Worst latency: A. Worst outcome: C. Improvements: for A, fewer retries for media errors on reads (or one retry), and surface the LBA to a higher layer (RAID, application redundancy) quickly; for B/C, enable Advanced Command Retry so CRD is honoured, or apply a host-side backoff for state-type statuses (Namespace Not Ready, Format In Progress) when CRD is 0; for D, keep as is. The general principle: retry only what time can fix, and let the controller's CRD tell you how long.

Solution

The first abnormal event is at 130.000140: the driver released tag 0x31 (and so CID 0x0A31) when it submitted the Abort, not when the target completed. At 130.000150 it reused CID 0x0A31 for a WRITE while the READ was still outstanding at the controller: a CID-uniqueness violation by the host. The controller was right: Abort is best effort, it reported "not aborted", and it completed the READ normally. The host then matched the READ's success CQE to the WRITE (reporting a write that never happened as successful: silent data loss for LBA 0x9A0000), and the WRITE itself was rejected with Command ID Conflict, which the host could not match to anything. The original 30-second READ delay is a separate question (media, firmware or a stall; look at what happened between 100 s and 130 s), not the same bug; report it separately. Regression test: inject a delay on a READ long enough to trigger the timeout, let the Abort fail, and verify the CID is not reused until the READ completes.

Debugging

Pattern 1 — Retry storm on media errors

SymptomSome reads take hundreds of milliseconds before failing; the kernel log shows the same LBA repeated several times.
Possible causesGenuine weak media with DNR = 0 and host retries; firmware returning retryable media errors for a mapping problem; host retry count too high.
EvidenceRepeated status SCT 2h SC 81h for the same LBA; Error Information entries; SMART media error count; per-attempt latency.
First checkDo all attempts fail identically and take the same long time?
Second checkDo other LBAs nearby fail; does the error persist after a rewrite of test data (on a test system)?
Disambiguating experimentReduce max_retries on a test system; read the LBA with a single command and compare; rewrite and re-read.
Likely conclusionMedia defect amplified by host policy; tune retries and rely on redundancy above.
ConfidenceHigh when attempts are identical and the rewrite cures it.

Pattern 2 — Health events stop arriving

SymptomA drive overheats or loses spare capacity without any asynchronous event, though the first occurrence was reported.
Possible causesEvent type masked (log never read with RAE = 0); no AER commands outstanding (host did not re-arm, or a reset dropped them and the driver did not resubmit); event disabled in Asynchronous Event Configuration.
EvidenceGet Log Page CDW10 values (RAE bit); count of outstanding AER commands; feature 0Bh value.
First checkIs any AER command outstanding? (Driver debug state, or the last AER submission in a capture.)
Second checkWho reads the health log, and with which RAE value?
Disambiguating experimentLower the temperature threshold on a test system to force an event, then watch for the AER completion and the log read.
Likely conclusionHost-side event cycle broken (masking or re-arm).
ConfidenceHigh once the forced event behaves as predicted.

Pattern 3 — LBA Out of Range after a namespace change

SymptomErrors with SC 80h and DNR 1 at the end of a device after namespace management or a firmware update.

Second checkWas a Namespace Attribute Changed notice delivered and processed (rescan)?

Pattern 4 — Data Transfer Errors without lower-layer evidence

SymptomOccasional SC 04h completions; AER and IOMMU logs clean.

Interview

Beginner

  1. Where does an NVMe command's error status appear?

    Model answer

    In the Status Field of its Completion Queue Entry, Dword 3 bits 31:17.

  2. What does DNR mean?

    Model answer

    Do Not Retry: if the same command is resubmitted it is expected to fail, so the host should not retry.

  3. What does the More bit tell the host?

    Model answer

    That additional information is available in the Error Information log page (Log Identifier 01h).

  4. Which NVMe mechanism reports problems not tied to any command?

    Model answer

    Asynchronous events, delivered by completing an outstanding Asynchronous Event Request command.

  5. What should a host do when CSTS.CFS is set?

    Model answer

    Reset the controller and reinitialise; outstanding commands will not complete.

Intermediate

  1. Decode DW3 = 0x8101_0051.

    Model answer

    DNR 1, M 0, CRD 0, SCT 0, SC 80h (LBA Out of Range), P 1, CID 0x0051.

  2. Why must the host read the log page after an asynchronous event?

    Model answer

    Because the event type stays masked until the indicated log page is read with RAE cleared; until then the controller cannot report further events of that type.

  3. What is CRD and when does a controller use it?

    Model answer

    Command Retry Delay selects one of three delays from Identify Controller (CRDT1–3, in 100 ms units). It is used only if the host enabled Advanced Command Retry; otherwise the controller returns CRD = 0.

  4. Why can the Error Information log miss errors?

    Model answer

    It is a ring of limited size (ELPE + 1 entries) that overwrites the oldest entries; not every error must be logged; reset behaviour is implementation-dependent.

  5. What are the possible outcomes of an Abort?

    Model answer

    The target is aborted (it completes with Command Abort Requested) or not (it completes normally, earlier or later). The Abort's own completion reports which. Either way the target produces its own completion unless a reset intervenes.

Advanced

  1. How do you tell a host-caused error from a media error by timing alone?

    Model answer

    Host-caused errors (invalid fields, LBA out of range) are returned within microseconds of the fetch, by the validator. Media errors come after long internal recovery, often tens of milliseconds, with no data transferred.

  2. Why can a monitoring tool break event delivery?

    Model answer

    If it reads log pages with RAE set (or if nobody reads them with RAE cleared), event types stay masked; and if it consumes events without the driver knowing, the driver's state can diverge.

  3. When is an NVMe Data Transfer Error the cause and when a symptom?

    Model answer

    Usually a symptom of a lower-layer DMA failure (UR, completion timeout, poisoned data); occasionally the cause lies inside the controller. Evidence at the PCIe layer (AER, IOMMU, capture) decides.

  4. Describe a retry storm and how to prevent it.

    Model answer

    Repeated immediate retries of failing commands (DNR 0) that multiply latency and load. Prevent with sensible max retries by status type, honouring CRD (enable Advanced Command Retry), backoff for state-type statuses, and fast escalation to redundancy for media errors.

  5. What evidence would distinguish controller fatal from a dead PCIe link during a timeout?

    Model answer

    A CSTS read: valid data with CFS = 1 is a controller fatal; all ones (or a failed read) means the read never reached a functioning device, so PCIe. Configuration reads confirm the link.

Senior

  1. Design host error-handling policy for a storage product.

    Model answer

    Classify by SCT/SC and DNR: fail fast on host-caused errors; retry with backoff or CRD for state errors; limited retries and redundancy for media errors; failover for path errors; investigate Data Transfer Errors with PCIe evidence; own the asynchronous event cycle in one component; read the error log on M = 1 and track Error Count gaps; never free CIDs on abort; collect telemetry after CFS before reset where possible.

  2. A customer says "the SSD returned success for a write that never happened". How do you investigate?

    Model answer

    Check for host CID reuse (abort or reset paths), duplicate CIDs, posted-write loss (IOMMU faults on READs is the opposite direction, but check DMA), and controller cache behaviour (power loss without Flush/FUA). Correlate the CQE payload with the command that the host attributed it to.

  3. What should validation test for asynchronous events?

    Model answer

    Each supported event fires under its condition; DW0 fields are correct; masking after report; unmasking only after a read with RAE = 0; behaviour with zero, one and AERL + 1 outstanding AERs; AER Limit Exceeded beyond the limit; events across resets; no timeouts applied by the controller.

  4. How do the NVMe 2.4 additions, such as voltage monitoring, affect error handling?

    Model answer

    They add new conditions and logs that may surface as events or log entries; the host's event cycle must handle new types without breaking. Their identifiers and values must be read in the 2.4 documents; do not assume them.

  5. How do you write a root-cause report for an NVMe error that turned out to be a symptom?

    Model answer

    State the first abnormal event at the lower layer, the mechanism by which it produced the NVMe status, evidence for and against, confidence, fix and regression test; list the NVMe error as a consequence, not the root cause.

Quiz

  1. DW3 = 0x4503_0072. Which statement is right?

    • Generic Internal Error, DNR set
    • LBA Out of Range, M set
    • Media Unrecovered Read Error, M set, DNR clear
    • Command ID Conflict
    Answer and reasoning

    Bits 31:17 = 0x2281: M (bit 30) = 1, SCT 2, SC 81h; DNR 0.

  2. After a SMART / Health event is reported, what unmasks that event type?

    • Submitting a new AER command
    • Reading the indicated log page with RAE cleared
    • A controller reset only
    • Nothing; it stays masked
    Answer and reasoning

    The log read with RAE = 0 unmasks; submitting a new AER command re-arms delivery but does not unmask.

  3. A host has not enabled Advanced Command Retry. What CRD value will a controller return?

    • 0
    • 1
    • Whatever the condition needs
    • 3
    Answer and reasoning

    Without the host enabling it, CRD is 0.

  4. Which channel has no timeout on the controller side?

    • Get Log Page
    • Abort
    • I/O READ
    • Asynchronous Event Request
    Answer and reasoning

    AER commands stay outstanding until an event occurs; hosts must not time them out.

  5. An error completion arrives 4 µs after the SQE fetch with DNR = 1. The most likely owner is:

    • NAND media
    • The host (the command was invalid)
    • The PCIe link
    • The interrupt controller
    Answer and reasoning

    Fast rejection with DNR set is validator behaviour for invalid input.

  6. Error Count jumps from 0x41 at the last read to a newest entry of 0x52 with 8 entries visible (0x4B–0x52). How many entries were lost?

    • 0
    • 8
    • 9
    • 17
    Answer and reasoning

    Unseen counts 0x42–0x4A = 9 entries were overwritten.

  7. Explain why freeing a command's CID when sending an Abort is a bug.

    Model answer

    Abort is best effort; the target may still complete. Until its completion arrives (or a reset), its CID is in use; reusing it violates CID uniqueness and lets the late completion be matched to the wrong command.

  8. List the five NVMe error channels and the one that carries no cause at all.

    Model answer

    CQE status, Error Information log, asynchronous events, CSTS.CFS, and silence (no completion, detected by host timeout). Silence carries no cause.

  9. Why can a retry policy turn a recoverable condition into a failure?

    Model answer

    Immediate retries exhaust the retry budget in microseconds when the condition needs time (for example Namespace Not Ready). Honouring CRD or backing off allows the condition to clear.

Teach-back

  1. To a child. How does the SSD tell the computer something went wrong?

    Model explanation

    Every job comes back with a sticker: green for done, red with a word for a problem, and sometimes "don't try again" or "try after lunch". The SSD keeps a small notebook with more details, but it rubs out old notes, so you should look quickly. For problems that aren't about a job, like getting too hot, it rings a bell once, and won't ring again for the same thing until someone reads its note. If it faints, nothing comes back at all, and the computer notices only because it waited too long.

  2. To a junior engineer. What should your driver do with an error completion?

    Model explanation

    Decode SC, SCT, CRD, M and DNR from DW3 (shift by 17 for SC). If DNR is set, fail it. If not, decide by type: retry state errors after the CRD delay or a backoff; retry media errors sparingly; fail over path errors. If M is set, read the Error Information log soon and track Error Count gaps. For Data Transfer Error, look below at PCIe. Keep the CID allocated until the command's own completion arrives, even after an Abort.

  3. To a senior engineer. What is the most common way NVMe error handling goes wrong in systems?

    Model explanation

    Not the controller's reporting but the host's handling of the life cycle: events masked because nobody reads with RAE cleared, error logs overwritten by noise or retries before anyone reads them, retry policies that are wrong for the status type, and abort or reset paths that break CID uniqueness. Plus misattribution: treating a Data Transfer Error or an abort status as the cause when the first abnormal event was lower or earlier.

Mastery gate

Do not consider this module mastered until you can:

  • explain the five error channels and their lifetimes
  • diagram the asynchronous event cycle (arm, fire, mask, read with RAE cleared, re-arm)
  • decode raw CQE DW3, AER completion DW0 and Get Log Page CDW10 in a trace
  • debug a retry storm, masked events, an abort race and a Data Transfer Error without PCIe evidence
  • distinguish NVMe errors from neighbouring concepts: PCIe errors (PCIe Errors), PCIe Advanced Error Reporting (AER), resets (Reset), health monitoring (SMART and Health)
  • cite NVMe Base 2.4 and the NVM Command Set 1.3 for each status and log, and label host policy as implementation-dependent
