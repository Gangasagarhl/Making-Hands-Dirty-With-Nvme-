A protocol analyzer's native trace file is not a list of packets. It is a container of decoded content, analyzer state and metadata written by one product at one version. This module teaches you to treat such a file as evidence: identify what wrote it, separate the container from the content, export a portable view without losing meaning, prove that the export is faithful, and keep a chain of custody that holds up when the vendor, the customer and your own team argue about one capture.

Orientation

PEX / Capture File Training introduced the vocabulary: file container, decoded protocol content, analyzer database, exported CSV/text/XML (Extensible Markup Language) and raw packets. Teledyne LeCroy Analyzer Training showed how a capture is made and which fields an export should carry. This module goes one level deeper. It treats the proprietary file as forensic evidence and asks harder questions. What exactly is lost when you export? How do two exports of the same capture disagree? How do you prove a "missing completion" is in the device and not in the export? How do you hand a trace to someone who has different software, without handing them a different truth?

Before this module you should be able to read a Transaction Layer Packet (TLP) table (TLPs, TLP Header Anatomy), pair requests and completions by Requester ID and Tag (PCIe Tags and Outstanding Requests), follow one NVM Express (NVMe) command from doorbell to interrupt (Command-to-TLP Correlation), and explain analyzer views and triggers (Teledyne LeCroy Analyzer Training). The deep-dive Teledyne LeCroy Trace Analysis is the companion module on working inside the vendor software.

It will not describe the internal byte layout of any vendor's trace file, name a public parser for one, or tell you where to download one. Such formats are proprietary; their internals are not published as a specification, and anything written about them from the outside would be guesswork. Everything here works through the vendor's own software and its documented export features, plus tools you control.

Where it goes next: Automated Forensic Analysis takes the portable export this module produces and runs it through a forensic pipeline; Synthetic vs Real Traces, Diffing and Golden Traces uses the same discipline to build golden traces.

Kid story

Grandpa filmed the school play on an old video camera. The tape only plays in that one camera. Inside the camera there is the tape (the pictures), the little screen that adds the date and the subtitles, and a memory that remembers where you paused. To show the play to cousins far away, you hold your phone up to the camera's screen and record it. The phone video is easy to share. But it only shows what was on the screen when you pressed record: if the subtitles were switched on, the cousins see subtitles; if you fast-forwarded through the boring part, the cousins never see it; and if Grandpa's screen showed the wrong date, the phone video shows the wrong date too. So you write a note to go with it: "Recorded from Grandpa's camera, subtitles on, skipped the interval, the date on screen is wrong." And you keep the tape safe, because it is the only thing that has everything.

What it hides. A trace file is not a passive recording: the analyzer has already made choices before anything was saved (what to trigger on, what to filter, how to timestamp, where segments start), and those choices are invisible in the "pictures". A real export is also not a lossy picture of pixels: it can be exact for the fields it includes, and lossy only in what it omits. Where it misleads. The story suggests the tape is the raw truth. It is not: if the probe missed traffic or the buffer overflowed, the original file is incomplete too, and no amount of careful exporting will restore what was never captured. And the "wrong date" is worse in practice: a decoder can be wrong in a way that looks perfectly plausible — an NVMe "Read" that is really a Physical Region Page (PRP) list because the software assumed the wrong queue base.

Mechanism

The forensic handling of one capture, from the moment it is saved to the moment someone else reproduces your finding. Each step names who acts, what changes, where, and what evidence the step leaves behind.

  1. Seal the original. Who: capture operator. What changes: nothing in the file; a hash and a metadata record are created. Where: custody log beside the file. Evidence: SHA-256 of the native file, file size, time saved, analyzer serial and software version as displayed by the vendor software.
  2. Record the capture context. Who: operator. What changes: a context record is written. Where: the manifest. Evidence: probe point and type, link speed and width at capture, directions captured, trigger condition and position, filters, buffer size, segment count, timestamp resolution, and system context (lspci -vvv, register dump, queue map, kernel and firmware versions).
  3. Open in the vendor software and fix the decoder settings. Who: analyst. What changes: the software's database (queue map, decoder options). Where: the analyzer database, possibly saved with the file or beside it. Evidence: a written list of every setting entered by hand, and its source (for example, "SQ1 base from driver debug log").
  4. Choose the view and level for export. Who: analyst. What changes: nothing yet. Where: the recipe. Evidence: recipe line: view, level (packet, link transaction, split transaction, NVMe), columns, range, number and time formats.
  5. Export. Who: vendor software. What changes: a new file is created. Where: export file. Evidence: export file hash; row count reported by the software if available.
  6. Audit the export. Who: your audit tool. What changes: an audit report is written. Where: manifest. Evidence: schema check, monotonic time, direction coverage, pairing completeness, gap markers, a sampled hand decode against raw header bytes if exported.
  7. Normalize. Who: your parser. What changes: events in the course schema are created, keeping the raw row. Where: event store. Evidence: event IDs that map back to export row numbers.
  8. Redact for sharing (if needed). Who: analyst under a data-handling policy. What changes: a redacted derivative. Where: new file with its own hash. Evidence: redaction log naming each field class removed.
  9. Hand over. Who: analyst to reviewer, vendor or customer. What changes: custody. Where: custody log. Evidence: recipient, date, hashes, what was sent.
  10. Reproduce. Who: reviewer. What changes: nothing in the evidence. Where: reviewer's machine. Evidence: the reviewer's export, made from the original by the recipe, has the same hash or a documented, explained difference.

The central concept on the ladder

The tape plays only in Grandpa's camera; you share a phone recording of the screen, with a note saying exactly how it was recorded, and you keep the tape.

A native capture holds raw packets, decoded content and analyzer state. An export is one rendered view of it. Analysis runs on exports, but its credibility rests on the original plus a reproducible recipe.

The probe recovers symbols at one point on the link; the analyzer timestamps them with its own clock and stores them in a finite buffer. Buffer size, trigger position, and whether both directions were probed determine what exists in the file at all.

No NVMe or PCI-SIG specification defines analyzer file formats or exports. The specifications define what the packets mean: TLP fields in the PCI Express Base Specification, doorbells and queue mapping in the NVMe over PCIe Transport Specification, commands and completions in the NVMe Base Specification. An export is trustworthy only where its decoded fields can be checked against those definitions.

The protocol facts that survive export must include every field that pairs or orders transactions: direction, timestamp, TLP type, Requester ID, Tag, address, length, completion status, Byte Count, and for NVMe, the SQE and CQE payload fields.

In an export, a missing column or a filtered row looks exactly like a missing packet. The audit — row counts by direction and type, pairing completeness by (Requester ID, Tag) — is how you see the difference.

Before any device hypothesis, a senior asks: is this finding stable across views, export recipes and software versions, and is it inside a captured segment? If not, it is a question about the evidence, not about the device.

Specification discipline

Applicable specifications. None governs the file. The content is governed by the PCI Express Base Specification (Revision 6.x/7.0 family; TLP formats, completion rules, Data Link Layer), the NVMe over PCIe Transport Specification, Revision 1.4 (register map, doorbells, interrupts), the NVM Express Base Specification, Revision 2.4, and the NVM Command Set Specification, Revision 1.3 (commands, CQE status). The file format and the export formats are defined by the vendor's documentation for a given product and software version.

The meaning of every field you export — Fmt/Type, Requester ID, Tag, completion status, Byte Count, Lower Address — is defined by the PCI Express Base Specification's Transaction Layer chapter. The SQE and CQE layouts (64-byte and 16-byte entries) and the doorbell offsets from 1000h are defined by the NVMe Base and NVMe over PCIe Transport specifications. PCI Express Base Specification — Transaction Layer NVM Express Base Specification 2.4 — Submission Queue Entry; Completion Queue Entry

The five-representation model, the export recipe, the audit checks and the custody process are engineering practice derived from the requirement that evidence be reproducible. They are not normative anywhere. Derived

Implementation-dependent (vendor- and version-dependent): file container structure; which views exist; export formats and column sets; how segments and overflow are marked; timestamp resolution and format; whether raw header bytes can be exported; how NVMe decoders find queues; file compatibility between software versions. Read the vendor's manual for your version; do not generalize from one product.

Version-dependent on two axes at once. The software version changes decoders and export behaviour. The specification revision known to the decoder changes names: a decoder built before NVMe 2.4 may show newer admin opcodes, log pages or status values as unknown or vendor-specific. Record both versions with every export.

No specification says how an analyzer must timestamp (at the start of a packet, at its end, or at some symbol), what "transaction" means in a vendor view, how long completions may be paired before the software gives up, or how a decoder should behave on a field reserved in its revision. Those are product behaviours to confirm in vendor documentation.

Never assume that a vendor's "error" highlight is a specification violation, that an export contains all rows, that two software versions decode identically, or that an NVMe-level view found the queues correctly. Never reverse-engineer a vendor file format to "parse it yourself": besides the licensing question, your parser would carry undocumented assumptions into evidence.

Probe placement is part of provenance. An interposer in the slot, a mid-bus probe on a riser, and a probe on the far side of a retimer produce three different "truths" about the same transaction: different timestamps and potentially different error visibility. Write the probe point into the manifest in words, and photograph the setup if your policy allows it.

Caution lab Installing or moving a probe or interposer is a hardware operation on a powered-down system only, and it changes the electrical channel. Verify after installation that link speed and width match the unprobed configuration (lspci -vvv Link Status), as shown in Teledyne LeCroy Analyzer Training. Never probe a production host.

Posted requests (memory writes, messages) have no completion. An export that drops a posted write leaves no dangling request to warn you; only an audit against expectations (for example "every CQE is followed by an MSI-X unless coalesced") can notice it. Non-posted requests leave a dangling half when their completion is lost — which is why pairing completeness is the single most useful audit check.
