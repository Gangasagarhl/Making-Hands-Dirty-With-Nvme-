A protocol analyzer's native trace file is a container of captured traffic, decoded content, analyzer state and metadata, written by one product at one version. This module teaches you to treat it as evidence: separate container from content, export a portable view, prove the export faithful, and keep a chain of custody that survives a dispute between teams.

Orientation

PEX / Capture File Training introduced the vocabulary: file container, decoded protocol content, analyzer database, exported CSV/text/XML (Extensible Markup Language) and raw packets. Teledyne LeCroy Analyzer Training showed how a capture is made and which fields an export should carry. This module treats the proprietary file as forensic evidence: what is lost when you export, why two exports of one capture disagree, and how to prove a "missing completion" is in the device and not in the export.

Before this module you should be able to read a Transaction Layer Packet (TLP) table (TLPs, TLP Header Anatomy), pair requests and completions by Requester ID and Tag (PCIe Tags and Outstanding Requests), follow one NVM Express (NVMe) command from doorbell to interrupt (Command-to-TLP Correlation), and explain analyzer views and triggers (Teledyne LeCroy Analyzer Training). The deep-dive Teledyne LeCroy Trace Analysis is the companion module on working inside the vendor software.

It will not describe any vendor file's internal layout, name a public parser, or point to a download. The formats are proprietary and unpublished; everything here works through the vendor's software and documented exports, plus tools you control.

Where it goes next: Automated Forensic Analysis takes the portable export this module produces and runs it through a forensic pipeline; Synthetic vs Real Traces, Diffing and Golden Traces uses the same discipline to build golden traces.

Kid story

Grandpa filmed the school play on an old camera, and the tape plays only in that camera. Its little screen adds the date and subtitles. To share the play with cousins, you film the camera's screen with your phone. The phone video is easy to send, but it shows only what was on the screen: subtitles if they were on, nothing of the part you fast-forwarded, and the wrong date if the camera's date was wrong. So you send a note with it — "subtitles on, skipped the interval, date is wrong" — and you keep the tape safe, because only the tape has everything.

Analogy boundary

What it represents. The tape is the native trace file; the camera is the vendor software at a compatible version; the on-screen date and subtitles are decoded fields and groupings; the phone video is an export of one view; the note is the export metadata and custody record.

What it hides. The analyzer made choices before anything was saved — trigger, filters, timestamping, segments — that are invisible in the "pictures". And an export is not a blurry copy: it is exact for the fields it includes and lossy only in what it omits. Where it misleads. The tape is not raw truth: if the probe missed traffic or the buffer overflowed, the original is incomplete too. And a decoder can be wrong plausibly — an NVMe "Read" that is really a Physical Region Page (PRP) list because the software assumed the wrong queue base.

The central concept on the ladder

The tape plays only in Grandpa's camera; you share a phone recording of the screen, with a note saying exactly how it was recorded, and you keep the tape.

A native capture holds raw packets, decoded content and analyzer state. An export is one rendered view of it. Analysis runs on exports, but its credibility rests on the original plus a reproducible recipe.

The probe recovers symbols at one point on the link; the analyzer timestamps them with its own clock and stores them in a finite buffer. Buffer size, trigger position, and whether both directions were probed determine what exists in the file at all.

No NVMe or PCI-SIG specification defines analyzer file formats or exports. The specifications define what the packets mean: TLP fields in the PCI Express Base Specification, doorbells and queue mapping in the NVMe over PCIe Transport Specification, commands and completions in the NVMe Base Specification. An export is trustworthy only where its decoded fields can be checked against those definitions.

The protocol facts that survive export must include every field that pairs or orders transactions: direction, timestamp, TLP type, Requester ID, Tag, address, length, completion status, Byte Count, and for NVMe, the SQE and CQE payload fields.

In an export, a missing column or a filtered row looks exactly like a missing packet. The audit — row counts by direction and type, pairing completeness by (Requester ID, Tag) — is how you see the difference.

Before any device hypothesis, a senior asks: is this finding stable across views, export recipes and software versions, and is it inside a captured segment? If not, it is a question about the evidence, not about the device.

Specification discipline

Applicable specifications. None governs the file. The content is governed by the PCI Express Base Specification (Revision 6.x/7.0 family; TLP formats, completion rules, Data Link Layer), the NVMe over PCIe Transport Specification, Revision 1.4 (register map, doorbells, interrupts), the NVM Express Base Specification, Revision 2.4, and the NVM Command Set Specification, Revision 1.3 (commands, CQE status). The file format and the export formats are defined by the vendor's documentation for a given product and software version.

Every exported field's meaning — Fmt/Type, Requester ID, Tag, completion status, Byte Count, Lower Address — is defined by the PCI Express Base Specification; 64-byte SQEs, 16-byte CQEs and doorbells from 1000h by NVMe Base and the PCIe Transport. PCI Express Base Specification — Transaction Layer NVM Express Base Specification 2.4 — Submission Queue Entry; Completion Queue Entry

The five-representation model, the export recipe, the audit checks and the custody process are engineering practice derived from the requirement that evidence be reproducible. They are not normative anywhere. Derived

Vendor- and version-dependent: container structure, views, export formats and columns, segment and overflow marking, timestamp resolution, raw-byte export, how NVMe decoders find queues, file compatibility across versions. Read the manual for your version.

Two axes: the software version changes decoders and exports; the specification revision known to the decoder changes names — a pre-2.4 decoder may show newer opcodes, logs or statuses as unknown. Record both.

No specification says how an analyzer must timestamp (at the start of a packet, at its end, or at some symbol), what "transaction" means in a vendor view, how long completions may be paired before the software gives up, or how a decoder should behave on a field reserved in its revision. Those are product behaviours to confirm in vendor documentation.

Never assume a vendor "error" highlight is a specification violation, that an export holds all rows, that two versions decode alike, or that an NVMe view found the queues. Never reverse-engineer a vendor format: your parser would put undocumented assumptions into evidence.

In short: field semantics are Normative (PCIe Base, NVMe Base, PCIe Transport); NVMe and management decoders are Optional product features; transaction naming and error colouring are Implementation-dependent; decoder names for newer structures are Version-dependent; vendor manuals are Informative for protocol questions.

Any finding that changes when you change the view, the recipe, the software version or the queue map is a finding about your evidence. Only findings that are stable across those changes are findings about the device.

Linux view

Linux cannot read a proprietary trace's content. It can seal the evidence, record the context decoding needs, and check exports. These commands are read-only on the device.

# Hash the original and the export; store hashes in the custody log
sha256sum run42.pex run42_pkt.csv
stat run42.pex                 # size, timestamps of the file itself
file run42.pex                 # a generic type guess only; it says nothing about content
head -n 3 run42_pkt.csv        # the export's header row: which columns were included?
wc -l run42_pkt.csv            # row count, to compare with the software's own count
cut -d, -f3 run42_pkt.csv | sort | uniq -c   # rows per direction (column 3 here)
sudo lspci -vvv -s 01:00.0 > ctx_lspci_ssd.txt      # BAR0, MSI-X capability, link status
sudo lspci -vvv -s 00:01.1 > ctx_lspci_rp.txt       # root port link status, AER capability
sudo nvme id-ctrl /dev/nvme0 > ctx_idctrl.txt       # firmware revision, version, MDTS
sudo nvme show-regs /dev/nvme0 -H > ctx_regs.txt    # CAP (DSTRD), VS, CC, AQA, ASQ, ACQ
uname -r > ctx_kernel.txt

Labs

Labs 1–3 are Safe lab: synthetic data and file handling only. Lab 4 is Safe lab as written; its optional extension using a real analyzer is a Caution lab (probe installation on a lab machine only).

Beginner lab — Name the representation

Objective. Classify artefacts into container, decoded content, analyzer database, export and raw packets. Prerequisites. This module's vocabulary. Setup. The list below, no tools.

Procedure. For each item, write its representation and one thing it can hide: (a) a bookmark named "BUG HERE" at row 4413; (b) a CSV with columns time, type, address; (c) the analyzer's colour highlighting of a Cpl with UR; (d) a 1.9 GB file with the vendor's extension; (e) "Tag=0x22" shown in a packet view; (f) the 16 header bytes of a TLP shown in hex in the software; (g) an NVMe-level row reading "Write CID 0x0041 Data Transfer Error".

Observations. Notice how many items are interpretations. Questions. Which items would survive if you sent only the CSV? Which could differ between two software versions?

Expected reasoning. Raw is rarer than it looks; most of what you read is decoded or database content.

Solution

(a) Database (an annotation — opinion, not evidence). (b) Export — no direction, Tag or Requester ID, so no pairing. (c) Decoded content plus presentation — the colour is a product choice. (d) Container — hides its version and settings until opened. (e) Decoded content — right if the decoder is. (f) The closest to raw a user sees. (g) NVMe-level decode, dependent on the queue map and the decoder's revision tables. Only (b)'s columns survive in the CSV; (c), (e) and (g) can change between versions.

Extension. Pin the five representations beside your analyzer.

Intermediate lab — Write an export recipe and a manifest

Objective. Produce a reproducible recipe and a manifest for a capture. Prerequisites. Exporting; the Protocol view table above. Setup. A text editor. Use the normal trace above as the capture.

Procedure. (1) List every column you need to check pairing, ordering, doorbell values, CQE contents and interrupts. (2) Write the recipe: software version (as displayed), view, level, columns, range, filters (ideally none), time format, number format. (3) Write a manifest JSON with: original file name and hash, capture context (probe point, link, directions, trigger, buffer, segments, timestamp resolution), system context files with hashes, recipe, export file hash, auditor and date.

Observations. How many fields could you fill from the trace itself, and how many needed the operator? Questions. Which single missing column would make pairing impossible? Which missing context would make doorbell decoding impossible?

Expected reasoning. Most of the manifest is about things not visible in packets.

Solution

Columns: row, timestamp (ns or finer), direction, TLP type with header size, address, length, Requester ID, Tag, Completer ID, status, Byte Count, Lower Address, payload, EP (poisoned) bit; plus DLLP and analyzer-status rows. Without Tag, pairing is impossible; without BAR0 and CAP.DSTRD, doorbells cannot be decoded; without queue bases, SQE fetches cannot be told from data reads. The manifest holds the original's name, size and hash; capture context; system context files with hashes and the queue-map source; the recipe; the export hash and row count; the audit verdict, auditor and date.

Extension. Add an honest "known limitations" field, e.g. "times are at the probe point".

#!/usr/bin/env python3
"""export_audit.py - audit an analyzer export (CSV) before trusting it.
Standard library only. The embedded export is SYNTHETIC (course lab system)."""
import csv, hashlib, io, json

REQUIRED = ["row", "time_ns", "dir", "type", "addr", "len_dw", "req_id", "tag", "status", "byte_count"]
NON_POSTED = {"MRd32", "MRd64", "CfgRd0", "CfgWr0"}
COMPLETIONS = {"Cpl", "CplD"}

# Recipe recorded with the export (what the analyst asked the vendor software for).
RECIPE = {"software": "AnalyzerSW (version recorded from its About box)",
          "view": "packet", "columns": "as REQUIRED", "filter": "TLP types: MRd*, MWr*, CplD",
          "range": "full capture", "time": "ns from trigger"}

EXPORT = """\
row,time_ns,dir,type,addr,len_dw,req_id,tag,status,byte_count
1,0,down,MWr32,0xFE601008,1,RC,,,
2,820,up,MRd64,0x123400000,16,0100,0x20,,
3,1450,down,CplD,,16,0100,0x20,SC,64
4,1500,up,MRd64,0x123400040,16,0100,0x21,,
5,2140,down,CplD,,16,0100,0x21,SC,64
6,3300,up,MRd64,0x200001000,128,0100,0x22,,
7,64100,up,MWr64,0x200000000,64,0100,,,
8,64300,up,MWr64,0x200000100,64,0100,,,
9,66900,up,MWr64,0x123410000,4,0100,,,
10,67100,up,MWr32,0xFEE01000,1,0100,,,
11,70200,up,MWr64,0x123410010,4,0100,,,
12,70400,up,MWr32,0xFEE01000,1,0100,,,
"""

def audit(text, recipe):
    out = {"sha256": hashlib.sha256(text.encode()).hexdigest(), "recipe": recipe,
           "problems": [], "warnings": []}
    rows = list(csv.DictReader(io.StringIO(text)))
    missing = [c for c in REQUIRED if c not in rows[0]]
    if missing:
        out["problems"].append(f"missing columns {missing}: pairing/ordering cannot be checked")
    out["rows"] = len(rows)
    # 1. row numbering and time order (a sort or a dropped range shows here)
    last_t, last_row = -1, 0
    for r in rows:
        n, t = int(r["row"]), int(r["time_ns"])
        if n != last_row + 1:
            out["problems"].append(f"row numbers jump {last_row} -> {n}: rows removed?")
        if t < last_t:
            out["problems"].append(f"row {n}: time goes backwards ({t} < {last_t})")
        last_t, last_row = t, n
    # 2. direction and type coverage
    cover = {}
    for r in rows:
        cover.setdefault(r["dir"], {}).setdefault(r["type"], 0)
        cover[r["dir"]][r["type"]] += 1
    out["coverage"] = cover
    for d in ("up", "down"):
        if d not in cover:
            out["problems"].append(f"no rows in direction '{d}': absences there are UNKNOWN")
    # 3. pairing completeness: every non-posted request needs completion(s)
    open_np, unexpected = {}, []
    for r in rows:
        key = (r["req_id"], r["tag"])
        if r["type"] in NON_POSTED:
            open_np[key] = r
        elif r["type"] in COMPLETIONS:
            if key not in open_np:
                unexpected.append(r["row"])
            elif r["type"] == "Cpl" or int(r["byte_count"] or 0) <= 4 * int(r["len_dw"]):
                open_np.pop(key)          # last (or only) completion for this request
    for (rid, tag), r in open_np.items():
        out["problems"].append(f"row {r['row']}: {r['type']} tag {tag} from {rid} has no completion in export")
    if unexpected:
        out["problems"].append(f"completions with no request in export: rows {unexpected}")
    # 4. recipe-level lossiness: a type filter that drops completions without data
    f = recipe["filter"]
    if "all" not in f and "Cpl" not in f.replace("CplD", ""):
        out["warnings"].append("recipe filter excludes Cpl (completions WITHOUT data): "
                               "UR/CA completions to reads are invisible in this export")
    out["verdict"] = "REJECT" if out["problems"] else ("ACCEPT WITH WARNINGS" if out["warnings"] else "ACCEPT")
    return out

if __name__ == "__main__":
    a = audit(EXPORT, RECIPE)
    print(f"export sha256 {a['sha256'][:16]}...  rows={a['rows']}  verdict={a['verdict']}")
    print("coverage", json.dumps(a["coverage"], sort_keys=True))
    for p in a["problems"]:
        print("PROBLEM:", p)
    for w in a["warnings"]:
        print("WARNING:", w)

(4) Add a check that every CQE write (MWr64 into the CQ1 range) is followed by an MSI-X write (MWr32 into 0xFEE0_0000–0xFEEF_FFFF) within 10 µs, as a warning, not a problem.

Observations. Which checks fire before and after the fix? Questions. Why is the MSI-X rule a warning? Why does the pairing check use Byte Count rather than counting completions?

Expected reasoning. A finding should become a device finding only after the audit is clean.

Solution

Before: one problem (tag 0x22 unanswered) and one warning (Cpl filtered) → REJECT. After adding the Cpl UR row and fixing the filter: pairing complete, no warning → ACCEPT; the UR is now visible as the first abnormal event. The MSI-X rule is a warning because interrupt coalescing (Interrupt Coalescing feature) and polling legitimately produce CQEs without an immediate interrupt; the rule is a heuristic, not a specification requirement. Byte Count tells you how many bytes remain including this completion, so the last completion of a split read is the one whose Byte Count fits in its own payload; counting completions would fail when a completer splits at the 64-byte Read Completion Boundary differently from your expectation.

Extension. Add a check that a request crossing a 4 KiB address boundary, or a payload above MPS (256 B on the lab system), is flagged: these are PCIe Base Transaction Layer rules that an export lets you verify.

Senior forensic lab — The disputed capture

Objective. Resolve a dispute between two teams about one capture without new hardware access. Prerequisites. All of the above; Debugging Methodology. Setup. The facts below (synthetic).

Scenario. The platform team says the SSD dropped a completion: their export shows an SQE fetch at row 2,201,553 with no CplD, and the next fetch 4 ms later. The SSD vendor's firmware log says the command completed in 80 µs, and the vendor, opening the same file (same hash) in newer software, sees a CplD for that fetch. The platform export has 3,912,004 rows; the software reports 3,912,011 packets in that range.

Procedure. (1) List every explanation for the disagreement. (2) For each, write the evidence that would distinguish it. (3) Decide what to request from each team. (4) Write the conclusion you can defend today, with a confidence level from the course scale (CONFIRMED, HIGH, MEDIUM, LOW, UNKNOWN).

Observations. Seven packets are missing from the export. Questions. Is the missing CplD a device fact, a capture fact or an export fact? What one check would settle it?

Expected reasoning. The same original file, two exports, a seven-row discrepancy: the dispute is about the export pipeline until proven otherwise.

Solution

Explanations: (a) the older version's export dropped rows; (b) the newer version decodes or pairs differently; (c) different ranges or filters; (d) the CplD is really absent and the newer version mislabels something. Evidence: export the same range at packet level with both versions by one recipe, diff row by row, find the seven rows, and hand-decode the disputed packet's header bytes (type, Requester ID, Tag). Request the recipe and version from the platform team and an export by the same recipe from the vendor. Defensible today: "A completion for row 2,201,553 is present in the native capture per the newer software and absent from an older export that is seven rows short. 'Dropped completion' is LOW until a row-level diff says otherwise; the 4 ms gap before the next fetch is a separate open question." The settling check is the row diff plus hand decode.

Extension. On a lab system with a real analyzer (Caution lab), export the same capture with two recipes and two software versions if available, and diff them; record every difference class you find in your team's export guide.

Interview

Beginner

  1. Trace file versus export?

    Model answer

    The trace file is the native container with traffic, decodes and analyzer state; an export renders one view with chosen columns and range.

  2. Why keep the original after exporting?

    Model answer

    It alone holds everything captured; exports can be lossy and must be reproducible from it.

  3. Why hash a capture?

    Model answer

    To prove the analysed file is bit-identical to the one captured and handed over.

  4. Which columns pair requests with completions?

    Model answer

    Requester ID, Tag, type and direction; Byte Count for split completions.

  5. Can Linux tools read packets inside a proprietary trace?

    Model answer

    No: only hash, size and a generic type guess. Content comes via the vendor software.

Intermediate

  1. An MRd64 has no completion in an export. Explanations, cheapest check first?

    Model answer

    Filter or recipe; missing direction; range end; segment gap; tag width; then a real lost completion (confirm with AER).

  2. How can a transaction-level export hide a problem?

    Model answer

    Its grouping and derived latency hide split or short completions, segment boundaries and intermediate errors.

  3. What context does an NVMe-level decode need?

    Model answer

    BAR0, CAP.DSTRD, queue bases and sizes, which queue is Admin, command set, LBA size, decoder revision.

  4. What is an export recipe?

    Model answer

    Software version, view, level, columns, range, filters, formats — written so anyone can reproduce the export.

  5. What do you redact before sending a capture out?

    Model answer

    Per policy: serials, host names, paths, customer payloads — into a derivative with a redaction log and its own hash.

Advanced

  1. How do you show an export is faithful?

    Model answer

    Row count matches the software's count; monotonic time; both directions; pairing complete; hand-decoded header samples match; re-export gives the same hash.

  2. Two software versions decode one packet differently. Now what?

    Model answer

    Hand-decode the raw header bytes against PCIe Base or NVMe Base; note which tables cover the revision; log it as a tooling finding.

  3. Why is a Cpl-excluding filter dangerous for NVMe?

    Model answer

    UR and CA completions to reads carry no data; excluding Cpl hides the first abnormal event of most DMA-read failures.

  4. How do you export for an automated pipeline?

    Model answer

    Packet level, all types, raw header and payload, analyzer status rows, stable row numbers kept as source references.

  5. Provenance in one sentence?

    Model answer

    The recorded chain from system to analysed file; without it a finding cannot be reproduced or defended.

Senior

  1. Your team's capture policy in five rules?

    Model answer

    Hash originals at save; manifest every capture; export by named recipes and audit; redact only into logged derivatives; cite original hash, recipe and row numbers in findings.

  2. A customer sends a screenshot only. Response?

    Model answer

    Treat it as a pointer; ask for the native file or an export by our recipe plus capture context.

  3. How do you survive an analyzer software upgrade?

    Model answer

    Re-export a golden capture set, diff old and new, document differences, update recipe and pipeline before switching.

  4. When may you conclude "the device dropped a completion"?

    Model answer

    Clean audit, continuous segment, both directions, no filters, deadline inside the capture, independent AER or host-recovery evidence — ideally reproduced.

  5. A colleague wants to write a parser for the native format. View?

    Model answer

    No: undocumented format, unverifiable assumptions in evidence, possible licence issues. Invest in recipes, raw-byte exports and an auditor.

Quiz

  1. Which representation is closest to what crossed the wire?

    • The NVMe-level view
    • A transaction-level CSV export
    • Header bytes of each packet as recovered by the probe
    • The analyzer's bookmarks
    Answer and reasoning

    Raw packets (as the probe recovered them) are closest; everything else is decoded or derived.

  2. An export lacks any downstream rows. A fetch has no completion. What is the right classification?

    • Completion timeout in the root complex
    • UNKNOWN: completions travel downstream and were not exported or captured
    • Device bug
    • Driver bug
    Answer and reasoning

    Completions for device reads travel host→device. Without that direction, the absence proves nothing.

  3. Which filter would hide an Unsupported Request completion to a DMA read?

    • Keep only CplD (completions with data)
    • Keep only completions
    • Exclude DLLPs
    • Exclude MWr32
    Answer and reasoning

    A UR completion carries no data: it is a Cpl, not a CplD.

  4. Which statement about native trace formats is correct?

    • They are defined by the PCI Express Base Specification
    • They are defined by the NVMe over PCIe Transport Specification
    • They are identical across vendors
    • They are vendor-defined and version-dependent
    Answer and reasoning

    No protocol specification defines analyzer file formats.

  5. Why must the export use 64-bit vs 32-bit TLP type names (MWr32/MWr64) correctly for the lab system?

    Model answer

    Addresses below 4 GiB (doorbells at 0xFE60_xxxx, MSI-X at 0xFEE0_xxxx) use 3-DW headers; host memory above 4 GiB uses 4-DW. A mismatch means a decode or export error, or a real malformed TLP.

  6. What is the single most useful mechanical audit check, and why?

    Model answer

    Pairing completeness by (Requester ID, Tag) with Byte Count: lost non-posted rows leave a visible dangling half.

  7. In the ambiguous trace, why does the payload look like a PRP list?

    Model answer

    Read as little-endian 64-bit values it gives page-aligned addresses 0x2_0000_1000, 0x2_0000_2000 in the data-buffer region, which is what PRP entries are; read as an SQE it gives an implausible Flush with CID 0.

  8. Two exports of one hashed file differ by seven rows. What do you do first?

    Model answer

    Compare recipes and versions, then diff row by row to find the seven rows; hand-decode any that matter.

  9. What can file run42.pex tell you?

    Model answer

    Only a generic guess at the file type. Nothing about the analyzer, version or packets.

  10. Why record the decoder's specification revision with an export?

    Model answer

    Names for opcodes, log pages and status values depend on revision; a decoder that predates NVMe 2.4 may label newer structures unknown, and that must not be mistaken for device behaviour.

Teach-back

  1. To a child: explain why we keep Grandpa's tape even after we have the phone video.

    Model explanation

    "The phone video only shows what was on the little screen when we recorded it. If we skipped a part or the subtitles were wrong, the video has those mistakes too. The tape has everything, so if someone asks 'what really happened?', we can look again."

  2. To a junior engineer: explain why a Cpl filter turned a host-side UR into an apparent device failure.

    Model explanation

    "The controller read Write data from host memory with an MRd. The host refused with a UR completion that carries no data — a Cpl. Our export kept only CplD, so the refusal vanished, leaving an unanswered request and a later Data Transfer Error CQE that looks like a controller fault. Re-exported without the filter, the host's refusal is the first abnormal event."

  3. To a senior engineer: argue for making export audits mandatory in your validation pipeline.

    Model explanation

    "Every automated verdict inherits the faithfulness of its export. Unaudited exports produce phantom timeouts, false latency outliers and wrong first-abnormal-event calls that look exactly like device bugs, and they cost us cross-team escalations. An audit is cheap, mechanical and versionable: pairing completeness, coverage, monotonic time, recipe checks and a hand-decode sample. With it, each finding cites an original hash, a recipe and row numbers, so anyone — including the vendor — can reproduce it."

Mastery gate

Do not consider this module mastered until you can:

  • explain the five representations of a capture and what each can hide
  • diagram the capture-to-analysis pipeline and mark where assumptions enter
  • identify, in an export, a dangling request, a segment boundary and a lossy filter
  • debug a disputed finding by separating capture, export, database, software version and device
  • distinguish this topic from analyzer operation (Teledyne LeCroy Trace Analysis), from the forensic pipeline (Automated Forensic Analysis) and from golden-trace work (Synthetic vs Real Traces, Diffing and Golden Traces)
  • cite the applicable sources: the PCI Express Base Specification (Transaction Layer) and NVMe Base 2.4 / NVMe over PCIe Transport 1.4 for field meanings; the vendor's documentation for file and export behaviour
  • write an export recipe and manifest, and run an export audit
