A reset is the most violent thing a host can do to a working Non-Volatile Memory Express (NVMe) controller, and also the most common recovery tool in every driver. This chapter teaches exactly what each NVMe reset destroys, what it keeps, how long the host must wait, how shutdown differs from reset, and how a driver rebuilds queues and recovers outstanding commands afterwards.

Why this chapter exists

Every production NVMe stack eventually resets a controller: after a command timeout, after a fatal controller status, after a firmware activation, during suspend and resume, during hot plug, and every time the machine boots. Engineers who treat reset as "turn it off and on again" are surprised when commands vanish without completions, when the controller takes eleven seconds to come back, when a namespace's settings revert, or when the Peripheral Component Interconnect Express (PCIe) link drops because someone wrote the wrong register.

The NVM Express Base Specification describes a whole family of resets that differ in scope: a queue-level reset touches one queue, a controller-level reset touches one controller, an NVM subsystem reset touches every controller in the subsystem, and transport resets (PCIe resets, taught in Chapter 49) reach the controller from underneath. Shutdown is a separate mechanism with a different purpose: it is about making data durable before power goes away, not about recovering from a fault.

This chapter turns those words into register writes, timeouts, Transaction Layer Packet (TLP) traces and Linux behaviour you can reason about.

Learning objectives

  • Explain how the Linux NVMe driver escalates from a timeout to an abort to a controller reset.

The story

Imagine the school library has a librarian who takes request slips from a box and puts answers into another box. One day the librarian freezes and stops answering. The teacher can't fix the librarian's brain, so she says: "Stop. Put down everything. Empty both boxes. Stand by the door until you're ready to start fresh." The librarian drops every slip she was holding — those slips are simply gone, nobody gets an answer for them. When she is standing by the door with the green "ready" light off, the teacher sets up two brand-new, empty boxes and says "start". The green light comes on, and the teacher writes all the lost requests again.

At the end of the school day there is a different instruction: "We're turning off the lights soon. Put every book back on its shelf properly and tell me when you're done." That is not starting over — it is tidying up so nothing is lost when the lights go out.

Think of an air-traffic control tower that loses its picture of the sky. The supervisor orders a ground stop: every flight plan that was being worked is cancelled from the tower's point of view, the strip boards are cleared, and the tower reports "not ready". Only when the tower reports "ready" again do airlines re-file their flight plans, one by one, starting with the most important (the admin channel), then the bulk traffic (I/O). A planned end-of-day closure is different: the tower lands everything in the air, writes up its logs and only then reports "closed" — the equivalent of a shutdown notification.

The analogy hides three things. First, a controller does not "cancel" commands by telling anyone: after a controller reset no completion queue entry is posted for commands that were in flight, so the host itself must decide those commands failed. Second, the "re-file" step is entirely the host's job; the controller has no memory of the queues it had. Third, data the controller had already written to media is not undone — a reset is not a transaction rollback. A write that was outstanding may be fully written, partially written or not written at all, and the host cannot tell which from the reset alone.

Beginner explanation

An NVMe controller has an on/off switch inside its registers: the Enable bit in the Controller Configuration register (CC.EN). It also has a status light: the Ready bit in the Controller Status register (CSTS.RDY).

  • When the host writes CC.EN = 1, the controller starts up and eventually sets CSTS.RDY = 1. Now it will fetch commands.
  • When the host writes CC.EN = 0, the controller stops, throws away all its queues and all the commands it was working on, and eventually sets CSTS.RDY = 0.

The second step is a controller reset. "Eventually" matters: the controller may take time, and the host must wait for the light to change before doing anything else. The controller tells the host how long it might take, in the Timeout field of the Capabilities register (CAP.TO), counted in units of 500 milliseconds.

A bigger hammer is the NVM Subsystem Reset. An NVM subsystem can contain several controllers (for example, a dual-port SSD or a device using virtualization). Writing a special value — the ASCII letters "NVMe" — into the NVM Subsystem Reset register resets all of them together.

Separate from reset is shutdown. Before power is removed, the host writes the Shutdown Notification field (CC.SHN) and waits until the Shutdown Status field (CSTS.SHST) reports "complete". That gives the controller a chance to save its internal tables to non-volatile media so the next power-on is clean and fast.

After any reset, the host must build everything again: admin queue, Identify, features, I/O queues, interrupts. Commands that were in flight have no answers and must be retried or failed by the host.

The important engineering idea: every reset at or above the controller level has the same effect on NVMe state (queues gone, outstanding commands gone, CC.EN = 0, CSTS.RDY = 0) — they differ in what else they reset (PCIe configuration space, link state, other controllers, sticky error status).

Controller reset through CC.EN

The Controller Configuration register (CC, offset 14h) bit 0 is Enable (EN). The Controller Status register (CSTS, offset 1Ch) bit 0 is Ready (RDY). The handshake is asymmetric in time: the host's write is instant, the controller's response is not.

Rules the host must follow (wording paraphrased; confirm in the NVMe Base Specification, "Controller Registers" and "Resets" sections):

  • Normative After writing CC.EN = 0, the host waits for CSTS.RDY = 0 before writing CC.EN = 1. Writing EN = 1 while RDY is still 1 produces undefined results.
  • Normative CAP.TO (bits 31:24 of CAP) is the worst-case time the host should wait for CSTS.RDY to change in either direction, in 500 ms units. A value of 20 (14h) means 10 seconds.
  • Normative The admin queue registers AQA, ASQ and ACQ must be programmed while CC.EN = 0; changing them while enabled is not allowed.
  • Derived The host should treat a timeout waiting for RDY to fall as an escalation trigger: try a transport reset (FLR or PCIe reset) next, because the controller is not obeying its own register interface.

CAP.TO, CRTO and why "timeout" became two numbers

CAP.TO is 8 bits of 500 ms units, so it can express up to 127.5 seconds. NVMe 2.0 introduced controller ready modes: a controller may report that it can become ready before its attached namespaces are ready to process I/O ("ready independent of media"). For this, NVMe 2.0 added the Controller Ready Timeouts register (CRTO) with two values — a wait time for "ready with media" and a wait time for "ready independent of media" — and a CC field (Controller Ready Independent of Media Enable, CC.CRIME) that selects the mode. CAP reports which modes are supported (Controller Ready Modes Supported, CAP.CRMS).

CRTO, CC.CRIME and CAP.CRMS are NVMe 2.0-era additions. A 1.4-era driver knows only CAP.TO. When both exist, the specification describes how CAP.TO relates to the CRTO values (in short, CAP.TO is kept for older hosts). Confirm the field positions and the CRTO register offset in NVM Express Base Specification 2.4 — Controller Registers before decoding them; this course does not state them as verified.

Outstanding commands at reset time

The defining property of an NVMe reset is that it is completion-less. The controller does not post "aborted" entries; it cannot, because the completion queues themselves are deleted. The host is the only party that knows which command identifiers were outstanding, so the host must walk its own tracking structures and complete every one of them.

  • Reads: safe to retry. The data buffer may have been partially written by the controller's Direct Memory Access (DMA) before the reset, so the host must not hand that buffer to the application until a retry succeeds.
  • Writes: retry is usually safe because writing the same data to the same Logical Block Addresses (LBAs) is idempotent, but ordering with other writes matters for file systems and databases; most stacks retry in the order the block layer re-queues them.
  • Non-idempotent commands: Compare and Write-style fused operations, Zone Append in Zoned Namespaces (ZNS), Reservation commands, Format NVM, Sanitize, firmware commit. A blind retry may do something twice or something different. These need command-specific recovery.
  • DMA after reset: Normative intent — once CSTS.RDY = 0 after a reset, the controller is no longer processing commands. Derived — the safe host practice is still to keep data buffers and queue memory mapped until RDY reads 0, because a controller that is slow to stop may still be issuing DMA. Freeing memory as soon as you write CC.EN = 0 is a classic use-after-free with an IOMMU fault (or worse, silent corruption without an IOMMU).

Queue-level reset: deleting and recreating one queue

The smallest reset is deleting an I/O queue pair. The rules:

  1. Delete I/O Submission Queue (admin opcode 00h) first. Normative On deletion, commands that were submitted to that SQ and not yet completed are aborted by the controller; the specification describes them as being completed with an aborted status ("Command Aborted due to SQ Deletion") — unlike a controller reset, a queue delete does produce completions, because the associated CQ still exists.
  2. Then Delete I/O Completion Queue (admin opcode 04h). A CQ cannot be deleted while any SQ still maps to it (the controller returns an invalid-queue-deletion error).
  3. Re-create with Create I/O Completion Queue (05h) then Create I/O Submission Queue (01h).

Linux uses queue deletion during orderly shutdown (to let in-flight I/O complete) but uses a full controller reset for error recovery, because a misbehaving controller cannot be trusted to process admin commands correctly.

Reinitialization: the rebuild sequence

  1. Wait for CSTS.RDY = 0 (bounded by CAP.TO, or the CRTO value for the selected mode).
  2. Optionally check CSTS.CFS (Controller Fatal Status, bit 1) and CSTS.NSSRO (NVM Subsystem Reset Occurred, bit 4) — they explain why you are here. NSSRO is cleared by writing 1 to it.
  3. Zero admin CQ memory; program AQA (sizes, 0's based), ASQ, ACQ.
  4. Write CC with CSS, MPS, AMS, IOSQES = 6 (64-byte entries), IOCQES = 4 (16-byte entries) and EN = 1.
  5. Wait for CSTS.RDY = 1. If CSTS.CFS = 1 instead, the controller failed to initialize.
  6. Identify Controller (Identify, opcode 06h, CNS 01h) — firmware may have changed (e.g. after a firmware commit that activates on reset).
  7. Set Features: Number of Queues; then re-apply other features (Interrupt Coalescing, Power Management, APST, Host Memory Buffer, Keep Alive Timer if used, Asynchronous Event Configuration).
  8. Create I/O CQs, then I/O SQs, binding each CQ to its MSI-X vector.
  9. Submit Asynchronous Event Requests.
  10. Re-scan namespaces (Identify active namespace list): the set of namespaces may have changed.
  11. Release the requeued I/O.

Step 6 is easy to skip and expensive to forget. A firmware image committed with the "activate at next reset" action becomes active at a controller-level reset. Any cached Identify data — maximum data transfer size, supported features, power state table — may now be stale.

NVM Subsystem Reset

The NVM Subsystem Reset register (NSSR, offset 20h) exists if CAP.NSSRS = 1. Writing the value 4E564D65h — the bytes of the ASCII string "NVMe" — initiates an NVM Subsystem Reset. Any other value has no effect. The magic value is a guard against stray writes: resetting a whole subsystem by accident (for example from a buggy tool writing zeros across BAR0) would take every controller, possibly every host path, offline.

  • Scope: every controller in the NVM subsystem, including controllers seen by other hosts on other ports.
  • Evidence afterwards: CSTS.NSSRO = 1 in each controller (set by the NSSR, cleared by host write-1-to-clear). A host that finds NSSRO set on initialization knows a subsystem reset happened, possibly initiated by someone else.
  • PCIe consequence: Implementation-dependent / transport-defined. The NVMe over PCIe Transport specification describes the NSSR effect for PCIe. In practice an NSSR on a PCIe SSD commonly causes the PCIe link to go down and retrain, so the host sees a Surprise Down or a hot-plug event and must restore configuration space as well as reinitialize the controller. Confirm in NVMe over PCIe Transport Specification 1.4 — NVM Subsystem Reset.

NVMe 2.0 also added an NVM Subsystem Shutdown capability (a register-level way to shut down all controllers in the subsystem) and a Shutdown Type field in CSTS. Their presence is advertised in CAP. Treat these as 2.x features and confirm their offsets and capability bits in the 2.4 Base specification before using them.

Shutdown notification: normal and abrupt

CC.SHN (bits 15:14) tells the controller power is about to be removed. CSTS.SHST (bits 3:2) reports progress.

Normal shutdown is the polite path. The recommended host procedure: stop submitting new I/O, let outstanding commands complete, delete I/O SQs then I/O CQs, then write CC.SHN = 01b and poll CSTS.SHST until 10b. The controller flushes its volatile write cache, writes its mapping tables and metadata, and marks the shutdown clean.

Abrupt shutdown (10b) is for when power is going away soon and the host cannot wait: the controller does the minimum needed to protect data integrity. The host does not first drain I/O.

How long to wait: Identify Controller reports RTD3 Entry Latency (RTD3E, in microseconds) — the typical time to reach shutdown-complete from a normal shutdown notification — and RTD3 Resume Latency (RTD3R). RTD3 stands for Runtime D3, the PCIe low-power device state in which main power is removed (see Chapter 50). If RTD3E is 0 the controller does not report it, and the host falls back to its own default.

Shutdown is not reset. After SHST = 10b, the controller may not process new commands. To use it again without a power cycle, the host should perform a controller reset (CC.EN 1→0, wait RDY = 0) and reinitialize. A host that sets CC.SHN and then keeps submitting I/O will see commands that never complete.

What happens if the host never sends a shutdown notification and power simply disappears? The controller treats the next power-on as recovery from an unexpected power loss: SMART / Health "Unsafe Shutdowns" count increments, start-up can take much longer (rebuilding mapping tables from media), and data in a volatile write cache that was not protected by power-loss capacitors may be lost. That counter is one of the most useful pieces of field evidence in this whole chapter.

Transport resets reaching the controller

On PCIe, a conventional reset (cold, warm or hot) and an FLR are both controller-level resets for the NVMe controller(s) they reach. Two extra consequences compared with CC.EN:

  • PCIe configuration space is reset (BARs, Command register Memory Space Enable and Bus Master Enable, MSI-X enable). Until the host restores it, the controller's registers are not even reachable by Memory Read/Write TLPs, and the controller cannot DMA.
  • For conventional reset, the link itself goes down; Data Link Layer and Physical Layer state is lost.

The details, including readiness timing after a PCIe reset, are in Chapter 49 — PCIe Reset.

The ladder for controller reset

The teacher tells the frozen librarian to drop everything, empty both boxes and wait at the door until the light turns off; then new empty boxes are set up and lost requests are written again.

The host writes CC.EN = 0, waits for CSTS.RDY = 0, reprograms admin queue registers, writes CC.EN = 1, waits for RDY = 1, then rebuilds features and I/O queues and resubmits outstanding commands.

Inside the controller, firmware stops the SQ fetch engines, quiesces the DMA engines and media back-end, discards command contexts, clears queue tables, and only then drops RDY. The register block and the PCIe endpoint stay alive throughout; BARs and MSI-X are untouched.

NVMe Base Specification: CC.EN transition 1→0 is a Controller Reset (a controller-level reset). CAP.TO bounds RDY transitions. AQA/ASQ/ACQ are not reset. Outstanding commands are not completed. NVMe 2.x adds CRTO and ready modes.

On the wire: one Memory Write (MWr) TLP from the Root Complex to BAR0+0x14, a train of Memory Read (MRd) TLPs to BAR0+0x1C with Completion with Data (CplD) replies, and silence from the device — no SQE fetches, no CQE writes, no MSI-X — between EN = 0 and the new doorbells.

In an analyzer you see the CC write, the polling reads whose CplD data changes from ...01h to ...00h in bit 0, the AQA/ASQ/ACQ writes, the CC write with EN = 1, polls until RDY = 1, then the first admin SQ tail doorbell (BAR0+0x1000) and the controller's first SQE fetch from the admin SQ base.

If RDY never falls, the first abnormal event is the poll that is still 1 after CAP.TO. If RDY rises but no SQE fetch follows the admin doorbell, suspect Bus Master Enable or IOMMU mappings, not the controller. If DMA writes appear after RDY = 0, the controller violated reset semantics.

The sixteen questions, applied to controller reset

1. What is it?
A controller-level reset initiated by clearing CC.EN, which returns the controller to its idle, unconfigured state.
2. Why was it created?
To give software a guaranteed way to bring a controller back to a known state without a power cycle or a transport reset.
3. What problem does it solve?
Recovery from hung commands, inconsistent queue state, firmware activation, and orderly re-configuration (e.g. changing queue entry sizes or memory page size).
4. What existed before it?
Advanced Host Controller Interface (AHCI) used a similar enable bit plus port-level resets; legacy storage relied on bus resets and device-specific reset commands (e.g. ATA soft reset via the device control register).
5. Why is the current design better?
One register bit, a published timeout, and precisely defined state effects; no in-band command is needed, so it works even when the queues are broken.
6. Who creates it?
The host driver (or the platform, indirectly, through transport resets).
7. Who consumes it?
The controller's firmware and hardware state machines.
8. Where does it live?
In controller registers in BAR0: CC at 14h, CSTS at 1Ch, CAP at 00h.
9. What memory/registers are involved?
CC.EN, CSTS.RDY, CSTS.CFS, CAP.TO, CRTO (2.x), AQA/ASQ/ACQ, and the host memory of all queues and data buffers.
10. What happens before it?
Usually a fault detection: command timeout, CSTS.CFS = 1, an AER event, a user request, a firmware commit, a resume.
11. What happens after it?
Reinitialization and resubmission of host-tracked outstanding commands.
12. What happens if it is wrong?
EN = 1 before RDY = 0 gives undefined behaviour; freeing memory early causes stray DMA; forgetting to zero the CQ gives phantom completions; forgetting AERs loses events.
13. What does the protocol analyzer show?
An MWr to CC, MRd polls of CSTS with changing data, a gap of device-initiated traffic, then the bring-up pattern.
14. What does Linux show?
Controller state "resetting" then "connecting" then "live" in sysfs; kernel log lines from the nvme driver about timeouts or resets (exact strings are version-dependent).
15. What would a validation engineer test?
RDY timing versus CAP.TO across temperatures and fill levels; reset under maximum queue depth; reset during each admin command; reset during firmware download; reset storms; no DMA after RDY = 0.
16. What would a senior engineer suspect when it fails?
Firmware stuck in a media operation, a power or thermal problem, the link not actually delivering the CC write (check AER and link status), or a host that polled the wrong BAR after a re-enumeration.

Hardware view

Inside an SSD controller, "reset" is not one wire. Different blocks are reset by different events, and the art of controller design is choosing which blocks a given reset touches.

What the hardware must do when CC.EN falls:

  • Stop the front end: the SQ fetch arbiter stops issuing Memory Read requests for SQEs. Doorbell writes may still arrive (the BAR is alive) but must be ignored.
  • Quiesce DMA: in-flight PCIe reads for write data must either complete or be abandoned; completions arriving for abandoned tags must be dropped without being treated as errors. In-flight posted writes (read data, CQEs) that already left are gone — the host may still receive them a few hundred nanoseconds after its CC write.
  • Drain or abandon the back end: NAND program operations in progress cannot be aborted mid-pulse; firmware typically lets them finish while discarding the host-facing context. This is a major reason RDY takes time to fall.
  • Clear queue tables: all SQ/CQ descriptors, head/tail pointers and phase state.
  • Keep the register block and PCIe endpoint alive: the host must be able to read CSTS throughout.

For a shutdown, the hardware path is different: the front end keeps running until the host stops it, and the back end must write out the volatile write cache and FTL metadata. Drives with power-loss protection capacitors can make abrupt shutdown nearly as safe as normal shutdown; consumer drives without them rely heavily on the host sending a normal shutdown.

Why can RDY take seconds to rise? On power-up or after a reset, firmware may need to load its mapping tables from NAND, replay a journal, or check for an unclean shutdown. A drive that was not shut down cleanly can take many seconds longer — exactly what CAP.TO (and, in 2.x, the "ready with media" CRTO value) must cover. The "ready independent of media" mode exists so the admin queue can come up quickly while media initialization continues.

Specification view

Documents: NVM Express Base Specification 2.4 — Controller Registers; Resets; Controller Initialization; Controller Shutdown (the section names are stable across 2.x; numbers change between revisions, so search by name). Transport-specific reset mapping: NVMe over PCIe Transport Specification 1.4. PCIe resets themselves: PCI Express Base Specification, Revision 6.x/7.0 — Reset Rules.

The register definitions and the reset effects are Normative. Host procedures such as "delete I/O queues before a normal shutdown" are mostly written as recommendations ("should"), which the specification treats as normative recommendations rather than absolute requirements. Diagrams and examples in the specification are Informative.

CC is at offset 14h and CC.EN is bit 0; CSTS is at 1Ch with RDY bit 0, CFS bit 1, SHST bits 3:2, NSSRO bit 4; CC.SHN is bits 15:14 with 01b normal and 10b abrupt; CAP.TO is CAP bits 31:24 in 500 ms units; CAP.NSSRS is CAP bit 36; NSSR is at offset 20h and the reset value is 4E564D65h ("NVMe"). AQA, ASQ and ACQ are not reset by a CC.EN 1→0 controller reset. Outstanding commands are not completed by a controller-level reset.

Because completion queues are deleted by the reset, the absence of completions for outstanding commands is a logical consequence, not just a rule. Because PCIe posted writes already in the fabric cannot be recalled, a host may observe a small number of device writes after its CC write but before RDY falls; host memory must remain valid until RDY = 0.

How long RDY takes to change (within CAP.TO), whether NSSR drops the PCIe link, how much metadata is flushed on abrupt shutdown, how long start-up takes after an unsafe shutdown, and whether the controller preserves internal debug state across reset — all implementation-dependent.

Controller ready modes (CRTO register, CC.CRIME, CAP.CRMS), NVM Subsystem Shutdown and the CSTS Shutdown Type field are NVMe 2.0-era. Feature persistence rules across reset were clarified over several revisions. Older (1.x) drivers ignore all of these; a 2.4 controller must still work with them.

The specification does not say how long a controller reset typically takes, how a host should choose between retrying and failing an outstanding command, whether data from an in-flight write reached media, or which reset a driver should escalate to next. Those are host policy. It also does not define Linux's timeout values. Confirm in the 2.4 text: the full list of events that constitute a controller-level reset for PCIe, the per-feature persistence across reset, and the exact CRTO field layout.

Never assume: that RDY falls immediately; that a controller reset also resets PCIe configuration space (it does not) or that FLR does not reset the controller (it does); that an aborted command produced a completion entry; that NSSR is harmless to other hosts; that a controller which reached SHST = 10b will accept commands.

Shutdown looks similar: an MWr to CC with SHN set, then polling reads of CSTS whose SHST field goes 00b → 01b → 10b. Before that, an orderly host shows Delete I/O SQ and Delete I/O CQ admin commands on the admin queue.

NSSR is one MWr of 4E564D65h to BAR0+20h. If the implementation drops the link, the next thing a PCIe analyzer shows is electrical idle followed by link training (ordered sets, no TLPs) and then configuration requests from the host — and possibly completions with Configuration Request Retry Status while the device is still initializing (Chapter 49).

Ordering detail that matters: if the host writes CC.EN = 0 and then immediately rings a doorbell (a bug), both are posted writes and arrive in order; the controller sees the doorbell after EN = 0 and ignores it. If the host instead reads CSTS before releasing memory, PCIe ordering guarantees the read reaches the controller after the CC write — but it does not guarantee device-to-host writes already in flight have landed. Those are in the opposite direction and are unordered with respect to the host's read request.

The Linux NVMe PCIe driver (drivers/nvme/host/pci.c with common code in drivers/nvme/host/core.c) implements reset and shutdown with a small number of well-named functions. Names below are stable across recent kernels but the details are Version-dependent; read the source of the kernel you are running.

The timeout escalation ladder

  1. A request exceeds its timeout. The handler first reads CSTS: if CFS = 1, it logs that the controller is down and schedules a reset immediately.
  2. It checks whether the completion is actually sitting in the CQ (a lost interrupt); if so it completes it and logs that the completion was polled — evidence of an interrupt problem, not a controller problem (see Chapter 43).
  3. Otherwise, for an I/O command, it sends an Abort admin command (opcode 08h) for that command identifier and re-arms the timer.
  4. If the request times out again (or the Abort itself times out, or it was an admin command), it resets the controller.
  5. If the reset fails (RDY never changes, CFS on enable, Identify fails), the controller is marked dead and its namespaces are removed — the "disk vanished" symptom.

Kernel log wording for these steps differs between kernel versions (some print the queue ID and command ID, newer ones print the opcode and tag). Search the log for "timeout", "reset", "controller is down" and "CSTS=" rather than for an exact sentence. Do not trust a blog's exact string; trust your kernel's source.

Actions that change state

Caution lab nvme reset /dev/nvme0 (or writing 1 to /sys/class/nvme/nvme0/reset_controller) performs a controller reset. In-flight I/O is requeued, so it is normally non-destructive, but never do it on the disk holding your root file system or swap on a machine you care about. Expert lab nvme subsystem-reset /dev/nvme0 writes NSSR: it affects every controller in the subsystem and commonly drops the PCIe link; the device may not return without a rescan or reboot. First, the host-side reset and rebuild as pseudocode. It deliberately shows the bookkeeping most toy drivers skip.

int nvme_controller_reset(struct ctrl *c)
{
    quiesce_submission_paths(c);              /* no new doorbells from any CPU */
    uint64_t cap = mmio_read64(c->bar0 + 0x00);
    uint32_t to_ms = ((cap >> 24) & 0xff) * 500;   /* CAP.TO */

    uint32_t cc = mmio_read32(c->bar0 + 0x14);
    mmio_write32(c->bar0 + 0x14, cc & ~1u);   /* CC.EN = 0 */
    if (wait_csts(c, /*mask*/0x1, /*want*/0x0, to_ms) != 0)
        return escalate_to_transport_reset(c); /* FLR, then hot reset */

    /* Only now is it safe to forget DMA mappings of the old queues. */
    fail_or_requeue_all_outstanding(c);       /* no CQEs will ever arrive for these */
    reset_host_queue_state(c);                /* heads, tails, phase = 1 */
    memset(c->admin_cq_mem, 0, c->admin_cq_bytes);

    uint32_t csts = mmio_read32(c->bar0 + 0x1C);
    if (csts & (1u << 4))                     /* NSSRO: someone did an NSSR */
        mmio_write32(c->bar0 + 0x1C, 1u << 4); /* write 1 to clear */

    mmio_write32(c->bar0 + 0x24, ((ACQ_ENTRIES-1) << 16) | (ASQ_ENTRIES-1));
    mmio_write64(c->bar0 + 0x28, c->asq_iova);
    mmio_write64(c->bar0 + 0x30, c->acq_iova);
    cc = (4u << 20) | (6u << 16) | (0u << 7) | 1u; /* IOCQES, IOSQES, MPS=4KiB, EN */
    mmio_write32(c->bar0 + 0x14, cc);
    if (wait_csts(c, 0x3, 0x1, to_ms) != 0)   /* RDY=1 and CFS=0 */
        return mark_dead(c);

    identify_controller(c);                   /* firmware may have changed */
    set_number_of_queues(c);                  /* allowed once per reset */
    reapply_features(c);                      /* coalescing, APST, HMB, AEN config */
    create_io_queues(c);                      /* CQs first, then SQs */
    submit_async_event_requests(c);
    rescan_namespaces(c);
    unquiesce_and_resubmit(c);
    return 0;
}

Second, a runnable model of the CC/CSTS state machine. It is a simulation, not a driver: it lets you see what happens if the host violates the rules.

#!/usr/bin/env python3
"""Toy model of NVMe controller reset and shutdown handshakes (teaching only)."""

class ToyController:
    def __init__(self, cap_to=20, stop_ms=38, start_ms=410, shut_ms=120):
        self.cap_to = cap_to          # CAP.TO in 500 ms units
        self.stop_ms, self.start_ms, self.shut_ms = stop_ms, start_ms, shut_ms
        self.en = 0; self.rdy = 0; self.cfs = 0; self.shst = 0
        self.pending = None           # (deadline_ms, action)
        self.now = 0
        self.queues = {}
        self.outstanding = set()

    def tick(self, ms):
        self.now += ms
        if self.pending and self.now >= self.pending[0]:
            _, action = self.pending
            self.pending = None
            action()

    def write_cc(self, en, shn=0):
        if shn and self.rdy:
            self.shst = 1
            self.pending = (self.now + self.shut_ms, self._shutdown_done)
            return
        if self.en == 1 and en == 0:
            self.en = 0
            self.pending = (self.now + self.stop_ms, self._stopped)
        elif self.en == 0 and en == 1:
            if self.rdy == 1:
                self.cfs = 1          # model "undefined results" as a fatal status
                print(f"[{self.now} ms] EN=1 written while RDY=1 -> undefined, model sets CFS")
                return
            self.en = 1
            self.pending = (self.now + self.start_ms, self._started)

    def _stopped(self):
        lost = sorted(self.outstanding)
        self.queues.clear(); self.outstanding.clear()
        self.rdy = 0; self.shst = 0
        print(f"[{self.now} ms] RDY=0; queues deleted; {len(lost)} commands dropped without CQEs: {lost}")

    def _started(self):
        self.rdy = 1
        self.queues["admin"] = True
        print(f"[{self.now} ms] RDY=1; admin queue live")

    def _shutdown_done(self):
        self.shst = 2
        print(f"[{self.now} ms] SHST=10b (shutdown complete)")

    def csts(self):
        return self.rdy | (self.cfs << 1) | (self.shst << 2)


def wait_for(c, mask, want, poll_ms=1):
    limit = c.cap_to * 500
    waited = 0
    while (c.csts() & mask) != want:
        if waited >= limit:
            return False
        c.tick(poll_ms); waited += poll_ms
    return True


def main():
    c = ToyController()
    c.write_cc(1); assert wait_for(c, 1, 1)
    c.queues.update({"sq1": True, "cq1": True})
    c.outstanding.update({0x01A0, 0x01A1, 0x01A2})

    print("--- correct controller reset ---")
    c.write_cc(0); ok = wait_for(c, 1, 0)
    print("RDY fell within CAP.TO:", ok)
    c.write_cc(1); wait_for(c, 1, 1)
    print("queues after reset:", sorted(c.queues))

    print("--- buggy host: re-enable without waiting ---")
    c.write_cc(0)
    c.write_cc(1)                      # RDY is still 1 here
    print(f"CSTS=0x{c.csts():02x} CFS={c.cfs}")

    print("--- normal shutdown ---")
    d = ToyController(); d.write_cc(1); wait_for(d, 1, 1)
    d.write_cc(1, shn=1)
    wait_for(d, 0b1100, 0b1000)
    print(f"CSTS=0x{d.csts():02x} (RDY may stay 1; SHST=10b)")


if __name__ == "__main__":
    main()

Expected output (deterministic, because the model has fixed delays): a line reporting RDY = 0 after 38 ms with three commands dropped, "RDY fell within CAP.TO: True", the admin queue only after re-enable, a CFS line for the buggy host, and a final CSTS of 0x09 for the shutdown case (RDY = 1, SHST = 10b).

Worked example

Scenario (synthetic): the Lab SSD reports CAP.TO = 20 and RTD3E = 8,000,000 µs (8 s). Linux runs with io_timeout = 30 s and shutdown_timeout = 5 s. An application issues a 1 MiB write that the drive never completes because of a firmware hang. How long until the application sees an error, and what happens at the next system shutdown?

  1. First timeout: 30 s after submission. CSTS shows CFS = 0, the CQ has no entry, so the driver sends an Abort and re-arms the timer.
  2. Second timeout: another 30 s (the Abort is answered with "not aborted" or not at all). Now the driver resets: CC.EN = 0, waits up to CAP.TO = 20 × 500 ms = 10 s.
  3. Case A — reset succeeds in 40 ms; re-enable takes 0.4 s; the request is requeued and retried. If the hang was transient, the retry succeeds and the application never sees an error, only ~60.5 s of latency. If the retry hangs too, the cycle repeats until the block layer's retry limit is exhausted, then the application gets an I/O error.
  4. Case B — reset fails (RDY stuck at 1 for 10 s): the controller is removed. Total ≈ 30 + 30 + 10 = 70 s, then the application gets an I/O error and the namespace block device disappears.
  5. Shutdown: the driver chooses its shutdown wait as the larger of RTD3E (8 s) and the module default (5 s), subject to the kernel's cap — so about 8 s. Version-dependent If an older kernel ignored RTD3E and waited only 5 s, it would cut power while SHST was still 01b on a slow drive, and the drive would count an unsafe shutdown even though the host "did shut it down".
Terr ≈ Nto × Tio + Treset
Terr
time from submission until the application receives an error (single attempt, failed reset)
Nto
number of command timeouts before the driver resets (2 here: one before Abort, one after)
Tio
per-command timeout (nvme_core.io_timeout)
Treset
time the reset attempt takes before being declared failed (bounded by CAP.TO × 500 ms)

This arithmetic is why storage teams tune io_timeout differently for boot disks, database disks, and disks behind multipath: the default is designed to tolerate slow drives, not to fail over fast.

Common mistakes

  • Writing CC.EN = 1 immediately after CC.EN = 0. Undefined behaviour; some controllers happen to tolerate it, so the bug survives until a slower drive arrives.
  • Polling with no timeout, or with a hard-coded 500 ms. Use CAP.TO (and CRTO on 2.x).
  • Freeing queue memory or unmapping IOMMU entries before RDY = 0. Produces IOMMU faults or corrupts reused memory.
  • Not zeroing the admin CQ before re-enable: old entries with phase tag 1 look like new completions.
  • Waiting for completions of commands that were outstanding at reset. They will never come.
  • Forgetting Asynchronous Event Requests after reset: the host silently stops learning about namespace changes, firmware events and health warnings.
  • Assuming features survive reset, especially interrupt coalescing, APST and Host Memory Buffer.
  • Calling Set Features Number of Queues twice after one reset.
  • Treating shutdown as reset: submitting I/O after SHST = 10b, or never resetting before reuse.
  • Using NSSR to "fix" one controller on a multi-controller subsystem shared with other hosts.
  • Confusing "controller reset" with FLR in bug reports. They reset different things; say which one happened.

Senior engineer insight

A reset destroys evidence. Before resetting a misbehaving controller in a lab, capture what you can: CSTS, the Error Information log, the SMART log, the telemetry log (Telemetry Host-Initiated, if supported) and an analyzer trigger. Production drivers reset first because availability matters; validation engineers configure the driver or analyzer to preserve state first.

  • Reset time is a product requirement. Data-center buyers specify maximum time-to-ready after reset and after unsafe power loss; CAP.TO is the contract, not the typical value.
  • Reset during every admin command is a mandatory validation matrix entry. The interesting bugs are resets during Format NVM, Sanitize, firmware download/commit, and namespace management, where the controller must leave persistent state consistent.
  • Reset storms (a reset that triggers the condition that caused it) are a host-side failure as much as a device one. Back-off and a reset budget belong in the driver.
  • On multi-path systems, a controller reset on one path must not corrupt reservations or in-flight writes on another path. Know which state is per-controller and which is per-subsystem.
  • When a report says "the SSD reset", ask: which reset, initiated by whom, and what did CSTS say before and after?

Challenge

Extend the simulator so a configurable set of outstanding commands are writes with a random "fraction written to media" at reset time. Have the host retry them and assert the final media state is correct regardless of the fraction.

Hints

CAP.TO is bits 31:24 of the low 32 bits of CAP. A controller reset is a register operation inside the function; the link and config space are a different reset domain. For the challenge, idempotent writes make the final state independent of partial progress — that is the property you are testing.

Solution

Q1: CC.EN is a controller-level reset that does not reach the PCIe function's configuration space or the Physical/Data Link layers, so the link stays in L0 and BARs/MSI-X are untouched. Q2: the platform removes power before shutdown completes (shutdown timeout shorter than the drive needs, or firmware/BIOS cuts power), or the system crashes/loses power often (watchdog resets, power events). Some drives also count abrupt-shutdown notifications as unsafe. Q3: escalate to a transport reset — FLR if supported, otherwise a secondary bus reset of the upstream port — then restore configuration space and retry initialization; if that fails, mark the controller dead and report. Challenge: the retry of an idempotent write overwrites any partially written blocks with the full payload; non-idempotent commands (e.g. Zone Append) would break this assertion, which is the lesson.

What a senior engineer notices

Whether the reset time in the log is close to CAP.TO (a drive that routinely uses most of its timeout is one bad day away from being declared dead), whether the drive's RTD3E is honoured by the kernel, and whether unsafe shutdowns correlate with kernel versions or platform firmware updates.

Failure variants

  • Reset hangs and the device is removed: capture the log, then try echo 1 > /sys/bus/pci/devices/0000:01:00.0/reset only on a test machine (Chapter 49).
  • After reset, fewer I/O queues are created than before: the controller now reports a different Number of Queues allocation (firmware change, or a different interrupt allocation).
  • Reset succeeds but namespaces change: an Asynchronous Event or a namespace attach happened in between.

  1. CAP reads 0x0000_0020_3C01_0FFF. Decode MQES, CQR, TO and NSSRS. How long may RDY take to change?
  2. Write the exact CC value to enable a controller with 4 KiB pages, NVM command set, round-robin arbitration, 64-byte SQEs and 16-byte CQEs. Then the value to request a normal shutdown while keeping the rest.
  3. List, in order, every admin command Linux-style bring-up sends after a controller reset, up to and including the first I/O queue pair.
  4. A colleague says "FLR is lighter than a controller reset". Correct the statement precisely.
  5. Design a validation test that proves a controller performs no DMA after CSTS.RDY = 0.
  6. Explain why NSSR requires a 32-bit magic value but CC.EN is a single bit.
Answers

1. Low DWORD 0x3C01_0FFF: MQES = 0x0FFF (4096 entries), CQR = 1, AMS = 00b, TO = 0x3C = 60 → 30 s. High DWORD 0x20: DSTRD = 0, NSSRS (bit 36 = high-DWORD bit 4) = 0, and bit 5 (CSS bit 0, NVM command set) = 1. So NSSR is not supported. RDY may take up to 30 s.

2. EN: (4 << 20) | (6 << 16) | 1 = 0x0046_0001. Normal shutdown: set SHN = 01b in bits 15:14 → 0x0046_4001.

3. Identify Controller (06h, CNS 01h); Set Features Number of Queues (09h); possibly Identify for namespaces / command-set specific data; Set Features for other features; Create I/O Completion Queue (05h); Create I/O Submission Queue (01h); Asynchronous Event Request (0Ch). Exact order and extra commands are driver-dependent.

4. FLR resets the whole PCIe function including its configuration space (BARs, Bus Master Enable, MSI-X enable) and the NVMe controller inside it; a CC.EN reset touches only the controller. FLR is lighter than a conventional reset (the link stays up), not lighter than a controller reset.

5. Under load, write CC.EN = 0; poll until RDY = 0; record the timestamp; then use an analyzer trigger on any device-initiated TLP (MRd/MWr from Requester ID 0x0100) after that timestamp and before the next CC.EN = 1. Also repeat with the IOMMU unmapping all buffers right after RDY = 0 and check for IOMMU faults. Vary load, transfer size and temperature.

6. CC.EN affects only the controller the host owns; a stray clear is recoverable. NSSR affects every controller in the subsystem, possibly owned by other hosts, and on PCIe may drop the link; a 32-bit pattern makes accidental triggering from a wild write astronomically unlikely.

Quiz

  1. After the host writes CC.EN = 0, when may it write CC.EN = 1?

    • Immediately
    • After 500 ms
    • After CSTS.RDY reads 0
    • After CSTS.SHST reads 10b
    Answer and reasoning

    The host must observe RDY = 0 first; writing EN = 1 while RDY = 1 has undefined results. 500 ms is one CAP.TO unit, not a rule. SHST relates to shutdown, not reset.

  2. CAP.TO = 0x28. What is the worst-case wait?

    • 40 ms
    • 20 s
    • 40 s
    • 2.8 s
    Answer and reasoning

    0x28 = 40 units × 500 ms = 20 s.

  3. Which register values survive a CC.EN 1→0 controller reset?

    • AQA, ASQ and ACQ
    • All I/O queue head and tail pointers
    • The Number of Queues allocation
    • Outstanding Asynchronous Event Requests
    Answer and reasoning

    The admin queue attribute and base address registers are not reset; everything about I/O queues and outstanding commands (including AERs) is gone, and Number of Queues must be set again.

  4. What value written to NSSR initiates an NVM Subsystem Reset?

    • 0x0000_0001
    • 0xFFFF_FFFF
    • 0x6D65_564E
    • 0x4E56_4D65
    Answer and reasoning

    4E564D65h is "NVMe" in ASCII read as N=4Eh, V=56h, M=4Dh, e=65h from most to least significant byte. Option 3 is the byte-reversed value — a classic endianness mistake when building the value from a string.

  5. During a controller reset, what happens to commands that were outstanding?

    • They receive completions with an "aborted" status
    • They are dropped with no completion; the host must account for them
    • They are completed after the controller becomes ready again
    • They are moved to the admin queue
    Answer and reasoning

    The CQs are deleted by the reset, so no completion can be posted. Contrast with Delete I/O SQ, which does produce "aborted due to SQ deletion" completions in the still-existing CQ.

  6. The host wrote CC.SHN = 01b and SHST now reads 10b. The host wants to submit more I/O without power cycling. What must it do?

    Model answer

    Perform a controller reset (CC.EN = 0, wait RDY = 0, clearing SHN in the process) and reinitialize the controller fully. A shut-down controller is not required to process commands.

  7. CSTS reads 0xFFFF_FFFF during a reset. What does this tell you?

    Model answer

    Nothing about NVMe state. All-ones is what the host sees when a memory read gets no successful completion (link down, device removed, Unsupported Request, completion timeout). The problem is at the PCIe layer; check link status and AER before anything else.

  8. Why must host memory for queues and data buffers stay mapped until RDY = 0, not merely until the CC write?

    Model answer

    The CC write is posted and takes time to arrive; the controller needs time to stop; and device-to-host writes already in flight are not ordered against the host's later reads. Until RDY = 0 the controller may still DMA. Unmapping early causes IOMMU faults or, without an IOMMU, writes into memory that has been reused.

  9. Which reset will most likely cause the Linux PCI hot-plug or AER code to see a link-down event?

    • Controller reset (CC.EN)
    • Delete I/O SQ
    • NVM Subsystem Reset on a typical PCIe SSD
    • Set Features Power Management
    Answer and reasoning

    NSSR on PCIe implementations commonly takes the link down (transport-defined, implementation-dependent detail). The others do not touch the link.

  10. Explain why the Unsafe Shutdowns counter is useful evidence in a field investigation.

    Model answer

    It increments when the controller starts after power was lost without a completed shutdown. Rising counts that correlate with crashes, power events, or a kernel/firmware update point to the platform cutting power early or the host not waiting long enough, which explains slow starts and possible loss of volatile cache contents — without needing an analyzer.

Interview questions

  1. Beginner: What does CSTS.RDY mean?

    Model answer

    Controller Status Ready: 1 means the controller is enabled and ready to process admin (and, once created, I/O) submission queue entries; 0 means it is disabled or still transitioning. It is the controller's answer to CC.EN.

  2. Beginner: What is the difference between shutdown and reset?

    Model answer

    Shutdown (CC.SHN) prepares for power removal by making data and metadata durable and reports progress in CSTS.SHST. Reset (CC.EN 1→0 and friends) returns the controller to an idle unconfigured state for recovery or reconfiguration. A shutdown controller needs a reset before reuse.

  3. Intermediate: Walk me through recovering from an I/O timeout on Linux.

    Model answer

    Check CSTS for fatal status; check for a missed completion (poll the CQ); send Abort for the command; on a second timeout reset the controller: quiesce, disable, cancel outstanding requests for requeue, re-enable, Identify, Number of Queues, features, create queues, AERs, rescan namespaces, unquiesce. If reset fails, remove the controller.

  4. Intermediate: Why can a CQ not be deleted before its SQs?

    Model answer

    The SQ's commands complete into that CQ. Deleting the CQ first would leave an SQ with nowhere to post completions, including the aborted completions produced by the SQ deletion itself. The controller rejects it with an invalid queue deletion status.

  5. Advanced: What changed with controller ready modes in NVMe 2.0, and why?

    Model answer

    Large drives can need a long time to make media ready. 2.0 lets a controller become ready "independent of media", so the admin queue is usable quickly while namespaces finish initializing, with separate timeouts reported in CRTO and the mode chosen through CC. CAP.TO remains for legacy hosts. Field positions should be checked in the 2.4 text.

  6. Advanced: You see device-initiated MWr TLPs 200 µs after the host wrote CC.EN = 0. Bug?

    Model answer

    Not necessarily. Until CSTS.RDY = 0, the controller is still stopping, and writes already in flight must drain. It is a bug if they appear after RDY = 0 was reported, or if they are new SQE fetches after EN = 0 arrived (fetches indicate the front end ignored EN).

  7. Senior: Design the reset escalation policy for a hyperscale fleet.

    Model answer

    Tiered: abort → controller reset → FLR → secondary bus reset/slot power cycle → remove and alert. Each tier has a bounded time from the device's declared limits (CAP.TO/CRTO, readiness rules) plus margin; a per-device reset budget prevents storms; evidence capture (CSTS, error log, telemetry, AER) happens before destructive tiers when policy allows; multipath fails over first so availability doesn't depend on the slow tiers; metrics record which tier recovered each event so firmware regressions are visible fleet-wide.

  8. Senior: A customer reports data corruption after a power event despite a clean OS shutdown. How do you investigate?

    Model answer

    Check the Unsafe Shutdowns counter before and after; check the OS log for the shutdown wait and whether SHST reached complete; compare RTD3E with the host's timeout; check whether the platform removes power before the OS finishes (firmware/BMC sequencing); verify the volatile write cache setting and Flush usage by the application; check power-loss-protection capability; reproduce with an analyzer on CC/CSTS and a power-rail monitor.

Chapter summary

NVMe resets come in scopes: queue, controller, NVM subsystem, plus transport resets that reach the controller from below. A controller reset is CC.EN 1→0 followed by waiting for CSTS.RDY = 0 within CAP.TO; it deletes all I/O queues, drops outstanding commands without completions, and keeps AQA/ASQ/ACQ. The host rebuilds everything and accounts for every outstanding command itself. NSSR writes "NVMe" to offset 20h and resets all controllers in the subsystem, often with link consequences on PCIe. Shutdown (CC.SHN, CSTS.SHST) is about durability before power loss, has its own latency (RTD3E), and must be followed by a reset before reuse. Linux escalates from timeout to abort to reset to removal.
