The Computational Programs Command Set lets a host run programs inside an NVMe subsystem, next to the data, instead of dragging every byte across PCI Express to the CPU. This chapter explains computational storage, compute namespaces, device-defined and downloaded programs, memory range sets, the role of Subsystem Local Memory, how execution works, and when moving compute toward data actually helps.

Why this chapter exists

Every chapter so far has assumed the same division of labour: the storage device stores and moves bytes, the host CPU computes. For a scan that keeps 1% of 1 TB, that means moving 1 TB across the PCI Express (PCIe) link, through the root complex and memory controller, into host DRAM, through CPU caches — and then throwing 99% of it away. Link bandwidth, host memory bandwidth, CPU cycles and energy are all spent on data that never mattered.

Computational storage moves some of the compute to the device. The NVM Express (NVMe) organisation standardised it as two command sets released together: Subsystem Local Memory (SLM), which gives the subsystem byte-addressable memory the host can manage, and Computational Programs, which runs programs that read and write that memory. Together they let a host say: "copy these blocks into device memory, run the filter program over them, and give me only the matches."

As an engineer you need this chapter for three reasons. First, it introduces a new class of namespace — the compute namespace — and a new class of long-running, data-dependent commands whose latency has nothing to do with media. Second, it changes trace analysis: large amounts of data can move inside the device with almost no PCIe traffic, so "the trace is quiet" no longer means "nothing is happening". Third, it raises new architectural and security questions — who may load code into a storage device, what memory may it touch, and how is a runaway program stopped.

Learning objectives

  • Define computational storage and explain the data-locality argument with a quantitative model.
  • Describe compute namespaces, compute engines, programs and program indexes.
  • Distinguish device-defined (preloaded) programs from downloadable programs, and explain loading and activation.
  • Explain memory namespaces, memory ranges and memory range sets, and how they bound what a program can access.
  • Walk through an Execute Program flow end to end, including the SLM copy steps.
  • Explain the relationship between Computational Programs and Subsystem Local Memory, and map the NVMe terms to the SNIA Computational Storage architecture.
  • Identify computational-storage activity — and its near-absence — in a synthetic PCIe trace, and find the first abnormal event in a hung program.
  • State what must be checked in the Computational Programs 1.3 specification before writing code.

The story

Imagine a toy factory with a huge warehouse of parts. Every morning, a lorry drives all the parts from the warehouse to a workshop in town, where workers pick out the red pieces and throw the rest away. Then the lorry drives the rubbish back. Most of what the lorry carries is useless.

Someone has an idea: put a small workbench inside the warehouse. Now a worker at the warehouse picks out the red pieces right there, and the lorry only carries the red pieces to town. The workbench needs a table to lay parts on (that is the memory), a list of jobs the worker knows how to do (the programs), and rules about which tables the worker is allowed to use (the memory range set).

Some jobs the worker already knows from the factory (built-in programs). For new jobs, the town office can post instructions to the warehouse (downloading a program) and then say "this one is approved, you may use it" (activation).

A modern factory with an on-site quality-control cell. Raw castings arrive in the factory's own stores (the NVM namespace). Instead of shipping every casting to the head-office lab, the factory moves a pallet onto a staging bench (copy into Subsystem Local Memory), and a robot cell (the compute engine) runs an inspection routine (a program) — either one the robot shipped with or one head office uploaded and certified. The cell may only reach the benches it has been assigned (the memory range set). It writes a short report onto an output bench, and head office collects only the report. If an uploaded routine loops forever, a supervisor must be able to stop the cell without shutting the whole factory.

What it hides. The "workbench" is a small embedded processor or accelerator inside the SSD controller, typically much less powerful than a host CPU. If the job is compute-heavy rather than data-heavy, the warehouse bench is slower than town. The analogy also hides that data must still be copied from storage into device memory before the program can see it; programs do not usually read the NVM namespace directly.

Where it misleads. A factory robot cannot corrupt head-office records. A buggy or malicious program in a storage device sits inside the trust boundary of every host using that device. Program loading, activation and memory range sets exist precisely to keep that risk contained, and administrators will often lock program download down entirely.

Where it breaks. The lorry in the story is the bottleneck; in reality the bottleneck may be the device's internal flash bandwidth, its compute engine, or the host's CPU. Whether computational storage helps is an arithmetic question, not a slogan.

Beginner explanation

Computational storage means a storage device that can run computations on data it holds. In NVMe, this is organised with three kinds of namespace working together:

  • an ordinary NVM namespace holding the data (blocks);
  • a memory namespace — Subsystem Local Memory, byte-addressable memory inside the subsystem;
  • a compute namespace — the namespace through which programs are managed and executed.

A program is a piece of code the device can run. Some programs come with the device (device-defined or preloaded); others the host can download into an empty program slot (downloadable). Programs are identified by a program index. Before a program can run, it must be active.

A program cannot touch arbitrary device memory. The host first creates a memory range set: a list of memory ranges (offset and length inside memory namespaces) that a program run may use. When the host executes a program, it names the program index, the memory range set and some parameters.

A typical job looks like this:

  1. Copy data from the NVM namespace into a memory namespace (inside the device).
  2. Execute the program on that memory range set.
  3. The program writes its results into another range.
  4. Read just the results back to host memory.

Only step 4 (and the small commands themselves) crosses PCIe. That is the whole point.

Engineering explanation

Computational storage and data locality

Data locality means doing work where the data already is. Its benefit depends on the data reduction a computation achieves (selectivity of a filter, compression ratio, aggregation) and on where the bottleneck lies. A streaming scan through a pipeline runs at the speed of its slowest stage:

Thost = D / min(Blink, Bmedia, Chost)     Tdev = max( D/Bmedia, D/Cdev, s·D/Blink )
D
bytes of input data to process
Blink
usable host–device link bandwidth in bytes per second (for example, about 7 GB/s for PCIe Gen4 x4 after protocol overhead — illustrative)
Bmedia
bandwidth at which the device can read its own media internally, bytes per second
Chost
rate at which the host CPU can process the data, bytes per second
Cdev
rate at which the device's compute engine can process the data, bytes per second
s
selectivity: fraction of input bytes that must be returned to the host (0 to 1)
Thost, Tdev
time for the host-side path and the in-device path, in seconds

The model is deliberately simple (it ignores setup, copy and command overheads) but it already shows the rules: computational storage helps when s is small and Cdev is not the bottleneck and the device's internal media bandwidth exceeds the link. It does nothing when the host's link is not the bottleneck, and it hurts when the device's compute engine is slower than the link. Aggregated across many drives the argument strengthens: 24 drives behind a host have 24 internal media paths but share one CPU socket's memory bandwidth.

Other benefits beyond throughput: lower host CPU utilisation (cycles freed for other work), lower energy per byte processed (no long-distance data movement), and lower latency for small result sets. Costs: programming model complexity, portability, debuggability and security.

Programs: device-defined and downloadable

Device-defined programs (often called preloaded or fixed programs) ship with the device: compression, decompression, encryption, checksum, filter or search functions the vendor implemented and validated. They occupy program indexes the host cannot overwrite. Their behaviour is described by vendor documentation or by a standardised program identifier; their implementation may be hardware.

Downloadable programs are loaded by the host into a program index with the Load Program command. The program has a program type that the device must support — the device reports which types it accepts. Extended Berkeley Packet Filter (eBPF) bytecode is the most widely discussed portable type for computational storage, because it has a verifier, a well-defined instruction set and existing toolchains; vendor-specific native binaries are another. Uncertain which program types Computational Programs 1.3 standardises versus leaves vendor-specific; read the program type definitions.

Program lifecycle:

  1. Discover — the host reads Identify and log data to learn the compute namespace's program slots, which hold device-defined programs, and which program types are downloadable.
  2. Load (downloadable only) — Load Program transfers the program image from host memory into a program index. Large images may be transferred in pieces.
  3. Activate — Program Activation Management activates (or deactivates) the program at an index. Only active programs can execute. Activation is where a device can verify, compile or install the program.
  4. Execute — Execute Program runs it.
  5. Deactivate / unload — when no longer needed.

libnvme encodes Load Program as admin opcode 85h, Program Activation Management as 88h and Memory Range Set Management as 89h; it does not list Execute Program, which is an I/O command sent to the compute namespace. This course does not state the Execute Program opcode — read it from the Computational Programs 1.3 command table.

Memory ranges and memory range sets

A program's view of the world is deliberately narrow. Before execution, the host uses Memory Range Set Management to create a memory range set: an identifier plus a list of memory ranges, each naming a memory namespace, a starting byte offset and a length. When the host executes a program, it names one memory range set; the program may access those ranges and nothing else.

This is the containment boundary of computational storage. It means:

  • a program cannot read another tenant's data unless the host placed it in one of the program's ranges;
  • a program cannot write outside its output ranges, protecting other data in SLM;
  • the same program can be run concurrently on different range sets, like a function called with different buffers;
  • the device can validate ranges once at creation, not on every memory access.

The convention of "range 0 is input, range 1 is output" is not a specification rule; it is an interface the program defines, the way a C function defines its arguments. Implementation-dependent — the program's documentation (or, for downloaded programs, your own code) defines the meaning of each range and each parameter.

Executing a program

Execute Program is an I/O command submitted to the compute namespace. It identifies the program (by index), the memory range set, and parameters for the program, passed in command dwords and/or a parameter data buffer. The controller dispatches the program to a compute engine; when the program finishes, the controller posts a completion. The completion reports success or failure of the execution and can carry a program-defined result value. Uncertain on how parameters are encoded, the size of the inline parameter area and which completion dwords carry the program result — check the Execute Program command definition.

Execution time depends on the program and the data, not on the media. A filter over 4 GiB of SLM may take a second; a bad program may never finish. Hosts must set timeouts appropriate to the program (often far longer than the default I/O timeout) and must be able to abort. Execution failures inside a program (for example, a divide-by-zero in eBPF, or an access outside the range set) are reported as command statuses defined by the command set.

The relationship with Subsystem Local Memory

Computational Programs does not define where data lives during computation; Subsystem Local Memory does. SLM provides memory namespaces and commands to read and write them from the host and to copy data between NVM namespaces and memory namespaces inside the subsystem (taught in Subsystem Local Memory). The two specifications were designed together and are meant to be used together:

Division of responsibilities
NeedSpecification
Byte-addressable working memory in the deviceSLM (memory namespaces)
Move data NVM namespace ↔ memory namespace without crossing PCIeSLM (and the NVM Command Set's copy facilities — check which)
Host reads/writes memory namespace contentsSLM read/write commands
Define which memory a program may accessComputational Programs (memory range sets)
Load, activate and execute programsComputational Programs

SLM is useful without computation (for example, as device-side staging memory), but Computational Programs is not useful without SLM: programs need somewhere to read and write.

Security and control

  • Who may load code. Load Program and Program Activation Management are administrative operations. The Base specification's Command and Feature Lockdown mechanism lets an administrator prohibit specific commands, which is how a platform can forbid program download entirely.
  • What code may touch. Memory range sets bound memory access; a device must enforce them. Programs should not have direct access to NVM namespaces or to other tenants' SLM.
  • What code may do. A portable, verifiable program type (such as eBPF with a verifier) lets a device reject unsafe programs at activation.
  • Stopping code. Hosts need Abort, and as a last resort controller reset, to recover from a runaway execution.

A storage device that runs downloaded code is a new execution environment inside the server. Treat program download like loading a kernel module: privileged, audited, and disabled unless needed.

The central concept on the ladder

Put a workbench in the warehouse, give the worker a list of jobs and a set of tables they may use, and send only the finished results to town.

A compute namespace holds programs; a memory namespace holds working data; a memory range set says which memory a program run may use; Execute Program runs a program on that memory with parameters, returning a result.

Inside the controller: embedded cores or accelerators (compute engines), device DRAM partitioned into SLM, a program store, a loader/verifier, a dispatcher, and internal data paths from flash to SLM that never touch PCIe.

Computational Programs 1.3 defines compute namespaces, programs, program types, Load Program, Program Activation Management, Memory Range Set Management and Execute Program; SLM 1.3 defines memory namespaces and their data movement; Base 2.4 defines CSI, queues and lockdown.

Admin commands to set up ranges and programs; SLM I/O commands to copy data in (no data over PCIe) and read results out (device MWr); an Execute Program I/O command whose completion may arrive seconds later with a program result.

In a trace: a burst of small setup traffic, a long quiet period with outstanding commands and no data TLPs, then a small result transfer. The quiet period is the work.

Debugging: is the program active, is the range set valid and large enough, did the copy finish before execution, is the host timeout long enough, is the program looping? Distinguish a slow program from a hung one by device-side status and timing, not by link silence.

The sixteen questions, answered for "Execute Program"

1. What is it?
An I/O command to a compute namespace that runs an active program against a memory range set with parameters.
2. Why was it created?
To give a standard, transport-independent way to invoke computation inside NVMe subsystems.
3. What problem does it solve?
Moving and processing data that could be reduced at the source; host CPU and link saturation for data-heavy, compute-light work.
4. What existed before it?
Vendor-specific computational storage devices with proprietary commands, FPGA cards with their own drivers, and host-side processing.
5. Why is the current design better?
It reuses NVMe queues, transports, namespaces and management, separates memory (SLM) from compute, and provides a containment model via range sets.
6. Who creates it?
Host software — an application through a computational storage library and the driver's pass-through path.
7. Who consumes it?
The controller's program dispatcher and a compute engine.
8. Where does it live?
An SQE in an I/O submission queue associated with the compute namespace; program code in the device; data in SLM.
9. What memory/registers are involved?
SQ tail doorbell, SQE, optional parameter buffer in host memory, SLM ranges, CQE.
10. What happens before it?
Program loaded (if downloadable) and activated; memory range set created; input copied into SLM.
11. What happens after it?
Host reads results from SLM output ranges; may chain another program; eventually deletes the range set.
12. What happens if it is wrong?
Status errors (inactive program, invalid range set, program fault), wrong results from wrong ranges or parameters, or a hang requiring abort or reset.
13. What does the protocol analyzer show?
One SQE fetch, possibly a parameter buffer read, a long gap, and a CQE — with any bulk data movement invisible because it is internal.
14. What does Linux show?
A generic character device for the compute namespace (/dev/ngXnY), its CSI in the descriptor list, and the result of pass-through commands; no block device.
15. What would a validation engineer test?
Program lifecycle transitions; range enforcement (every out-of-range access must fault, not corrupt); concurrency of executions; abort and reset during execution; lockdown of Load Program; behaviour under SLM exhaustion; result correctness against a host reference implementation.
16. What would a senior engineer suspect when it fails?
Ordering between the SLM copy and Execute Program, timeouts sized for media rather than computation, range-set lifetime bugs, and the device compute engine being the actual bottleneck.

Hardware view

On PCIe, a computational storage device is still a single NVMe function with the same BARs, doorbells and MSI-X vectors. The new hardware is behind the controller front end:

Hardware that participates in a program execution (implementation-dependent)
ElementTypical realisationObservable from host?
Compute engineEmbedded Arm or RISC-V cores, a fixed-function accelerator (compression, crypto, regex), or FPGA fabricOnly through Identify/log reports and timing
Subsystem Local MemoryA partition of the controller's DRAM, sometimes dedicated DRAMThrough memory namespace commands
Internal data moversDMA engines from the flash back end to DRAMNo — internal copies generate no PCIe traffic
Program storeFirmware-managed region holding device-defined and downloaded programsThrough program lists
Loader / verifier / runtimeFirmware: eBPF verifier and JIT or interpreter, or a native loader with sandboxingIndirectly, through activation success or failure
Range checkerMMU/MPU or software bounds checks enforcing memory range setsOnly when it faults

Two hardware facts dominate performance. First, internal flash bandwidth across all channels often exceeds the PCIe link: a 16-channel controller may read flash internally faster than a Gen4 x4 link can carry. That surplus is what computational storage harvests. Second, embedded compute is modest: a few low-power cores may process data at a few GB/s or less for general code, while a fixed-function accelerator may run at line rate for its one job. The Cdev term in the model is therefore highly program-dependent.

Power and thermal limits matter too. A device running its cores flat out draws more power; it may throttle (see Power Management), and a throttled compute engine changes a program's execution time without any protocol-visible event.

Because the bulk data path is internal, a PCIe analyzer on the link sees almost nothing during a large computation. Hardware debug of computational storage therefore leans on device telemetry and vendor logs rather than link traces.

Check in the specifications before relying on:

  • the Execute Program opcode, parameter encoding and the completion fields carrying a program result;
  • whether Load Program, Program Activation Management and Memory Range Set Management are admin commands in every case and which NSID they take;
  • the memory range descriptor format, alignment rules and maximum number of ranges per set;
  • the standardised program types and program identifiers, if any, in revision 1.3;
  • the status codes for inactive programs, invalid range sets and program faults;
  • the exact SLM commands for copying between NVM namespaces and memory namespaces (see Subsystem Local Memory).

The specifications do not say how fast programs run, how a device sandboxes code, or what a device-defined program computes beyond what the vendor documents.

Never assume a program can read an NVM namespace directly, that execution time resembles I/O latency, that Abort can stop a running program, that a downloaded program survives a reset or firmware activation, or that two devices support the same program types.

Protocol view

Ordering. NVMe does not order commands. The host must wait for the copy's completion before submitting Execute Program, and for Execute Program's completion before reading results. Submitting them together and hoping is a correctness bug that will pass in testing (when the copy is fast) and fail in production.

Direction and size. Setup commands move small descriptor buffers host → device. The copy moves nothing over PCIe. Execute Program may read a small parameter buffer. The result read moves result bytes device → host. Everything else is internal.

Errors and layer. Program faults, invalid ranges and inactive programs are NVMe command statuses on the relevant command. A hung program produces no status at all — the first abnormal event is the absence of a completion, detected by a host timeout. PCIe errors during the small transfers are ordinary transport faults.

Reasoning: the controller rejected the command 700 ns after fetching it, with no compute time, which points at validation rather than execution. The management workflow skipped activation. The fix is procedural; the lesson is that Load and Activate are separate steps for a reason — activation is where a device can verify and install code.

Linux view

Linux does not drive compute or memory namespaces as block devices. As with KV, each active namespace still gets a generic character device /dev/ng<ctrl>n<ns> (kernel 5.13 and later), and user space issues commands through pass-through ioctls or io_uring pass-through, usually via a computational storage library. Code / pseudocode

A behavioural model of the computational storage entities — memory namespace, memory range sets, device-defined and downloadable programs, activation and execution with access confined to the range set — plus the bottleneck cost model from the Engineering explanation. It deliberately contains no opcodes or status values.

#!/usr/bin/env python3
"""Computational Programs teaching model: a compute namespace, a memory
namespace (Subsystem Local Memory), memory range sets and programs.
Names follow the NVMe concepts; there are no opcodes or status values here
on purpose -- read those from the Computational Programs 1.3 and SLM 1.3
specifications. Also prints a simple data-movement cost model."""
import struct

class CPError(Exception):
    pass

class MemoryNamespace:                       # SLM: byte-addressable device memory
    def __init__(self, size):
        self.mem = bytearray(size)

class MemoryRangeSet:
    def __init__(self, ranges):              # list of (memory namespace, offset, length)
        self.ranges = ranges

    def view(self, i):
        ns, off, length = self.ranges[i]
        return memoryview(ns.mem)[off:off + length]

class ComputeNamespace:
    def __init__(self):
        self.programs = {}                   # program index -> dict
        self.range_sets = {}                 # range set id -> MemoryRangeSet

    # --- device-defined (preloaded) and downloadable programs ---
    def preload(self, index, fn, name):
        self.programs[index] = {"fn": fn, "name": name, "active": True, "downloaded": False}

    def load_program(self, index, fn, name):          # models "Load Program"
        if index in self.programs and not self.programs[index]["downloaded"]:
            raise CPError(f"program index {index} holds a device-defined program")
        self.programs[index] = {"fn": fn, "name": name, "active": False, "downloaded": True}

    def activate(self, index, on=True):               # models "Program Activation Management"
        if index not in self.programs:
            raise CPError(f"no program at index {index}")
        self.programs[index]["active"] = on

    def create_range_set(self, rsid, ranges):         # models "Memory Range Set Management"
        for ns, off, length in ranges:
            if off + length > len(ns.mem):
                raise CPError("range exceeds memory namespace")
        self.range_sets[rsid] = MemoryRangeSet(ranges)

    def execute(self, index, rsid, params):           # models "Execute Program"
        p = self.programs.get(index)
        if p is None:          raise CPError(f"no program at index {index}")
        if not p["active"]:    raise CPError(f"program {index} ({p['name']}) is not active")
        rs = self.range_sets.get(rsid)
        if rs is None:         raise CPError(f"memory range set {rsid} does not exist")
        return p["fn"](rs, params)                    # program sees ONLY its range set

def filter_gt(rs, params):
    """Range 0: input array of uint32; range 1: output array; params: threshold.
    Returns the number of matches (a small result for the completion)."""
    src, dst = rs.view(0), rs.view(1)
    n_in = len(src) // 4
    out = 0
    for i in range(n_in):
        (v,) = struct.unpack_from("<I", src, 4 * i)
        if v > params["threshold"]:
            if 4 * (out + 1) > len(dst):
                raise CPError("output range too small")
            struct.pack_into("<I", dst, 4 * out, v)
            out += 1
    return out

def sum_u32(rs, params):
    src = rs.view(0)
    return sum(struct.unpack_from(f"<{len(src)//4}I", src, 0))

def cost_model(data_bytes, selectivity, link_gbs, media_gbs, host_gbs, dev_gbs):
    """Seconds for a streaming scan, each path limited by its slowest stage
    (stages overlap, so time = data / bottleneck bandwidth)."""
    host = data_bytes / (min(link_gbs, media_gbs, host_gbs) * 1e9)
    dev = max(data_bytes / (media_gbs * 1e9),               # internal media read
              data_bytes / (dev_gbs * 1e9),                 # compute engine
              data_bytes * selectivity / (link_gbs * 1e9))  # results over the link
    return host, dev

if __name__ == "__main__":
    slm = MemoryNamespace(64 * 1024)
    cns = ComputeNamespace()
    cns.preload(0, filter_gt, "filter_gt (device-defined)")

    # Host would use an SLM copy from an NVM namespace; here we fill the input directly.
    values = [(i * 2654435761) % 1000 for i in range(4096)]
    struct.pack_into(f"<{len(values)}I", slm.mem, 0, *values)        # input at 0..16 KiB
    cns.create_range_set(7, [(slm, 0, 16384), (slm, 16384, 16384)])  # input, output

    for label, call in [
        ("Execute program 0, range set 7", lambda: cns.execute(0, 7, {"threshold": 990})),
        ("Execute program 1 (not loaded)", lambda: cns.execute(1, 7, {})),
        ("Load program 1 (sum_u32)",       lambda: cns.load_program(1, sum_u32, "sum_u32 (downloaded)")),
        ("Execute program 1 (inactive)",   lambda: cns.execute(1, 7, {})),
        ("Activate program 1",             lambda: cns.activate(1)),
        ("Execute program 1, range set 7", lambda: cns.execute(1, 7, {})),
        ("Execute program 0, range set 9", lambda: cns.execute(0, 9, {"threshold": 1})),
        ("Create range set 8 beyond SLM",  lambda: cns.create_range_set(8, [(slm, 60000, 8192)])),
    ]:
        try:
            r = call()
            print(f"{label:34s} -> ok" + (f", result={r}" if r is not None else ""))
        except CPError as e:
            print(f"{label:34s} -> ERROR: {e}")

    n = cns.execute(0, 7, {"threshold": 990})
    out = struct.unpack_from(f"<{n}I", slm.mem, 16384)
    print(f"host reads back {4*n} bytes of results (first 5: {list(out[:5])}) instead of 16384 bytes of input")

    print("\nScan of 1 TB, bottleneck model (illustrative numbers, not measurements):")
    print("  link 7 GB/s, internal media 24 GB/s, host compute 20 GB/s")
    for dev in (4.0, 10.0, 30.0):
        for sel in (1.0, 0.01):
            h, d = cost_model(1e12, sel, link_gbs=7.0, media_gbs=24.0, host_gbs=20.0, dev_gbs=dev)
            print(f"  device compute {dev:4.0f} GB/s, selectivity {sel:4.2f}: "
                  f"host path {h:6.1f} s, in-device path {d:6.1f} s")

Pseudocode for a host-side job runner, showing the dependencies the host must enforce:

int run_filter_job(dev, nvm_nsid, mem_nsid, cmp_nsid, slba, nlb, threshold, out_buf)
{
    /* 1. Discover: program index of the device-defined filter, SLM size, limits */
    idx = find_program(dev, cmp_nsid, "filter_gt");            /* from program list */
    if (idx < 0) return -ENOTSUP;

    /* 2. Memory range set: input + output in the memory namespace */
    in_len  = nlb * lba_size(dev, nvm_nsid);
    out_len = in_len / 8;                                       /* sized from expected selectivity */
    rs = mrs_create(dev, cmp_nsid, { {mem_nsid, 0, in_len}, {mem_nsid, in_len, out_len} });
    if (rs < 0) return rs;

    /* 3. Copy NVM -> SLM inside the device; WAIT for completion */
    st = slm_copy_from_nvm(dev, mem_nsid, /*dst*/0, nvm_nsid, slba, nlb);
    if (st) goto out;

    /* 4. Execute; timeout sized for computation, not for I/O */
    st = execute_program(dev, cmp_nsid, idx, rs, params(threshold),
                         &result, timeout = estimate(in_len) * 4);
    if (st == -ETIMEDOUT) { abort_or_reset(dev); goto out; }
    if (st) goto out;

    /* 5. Read back only the results the program reported */
    n_bytes = result * 4;
    if (n_bytes > out_len) { st = -EOVERFLOW; goto out; }      /* never trust blindly */
    st = slm_read(dev, mem_nsid, in_len, n_bytes, out_buf);
out:
    mrs_delete(dev, cmp_nsid, rs);                              /* do not leak range sets */
    return st;
}

Worked example

Problem. A log-analytics service scans 2 TB of compressed logs per hour on one server with 8 lab SSDs (Gen4 x4 each). Each device advertises a device-defined decompress-and-grep program; vendor data says it processes 3 GB/s per device; internal media bandwidth is 10 GB/s per device; selectivity is 0.5%. The host CPU can decompress-and-grep at 12 GB/s total across its cores. Should the service use the device program? Synthetic example for teaching; numbers illustrative.

  1. Host path. Link: 8 × 7 GB/s = 56 GB/s; media is not the bottleneck at 8 × 10 GB/s; host compute 12 GB/s is. Thost = 2 × 1012 / 12 × 109 ≈ 167 s.
  2. Device path. Each device holds 250 GB. Per device: media 250 GB / 10 GB/s = 25 s; compute 250 GB / 3 GB/s ≈ 83 s; results 0.005 × 250 GB / 7 GB/s ≈ 0.18 s. Bottleneck: compute, 83 s. All eight run in parallel: Tdev ≈ 83 s.
  3. Overheads. The copy into SLM is part of the media stage if pipelined; if not pipelined (copy all, then execute), per-device time ≈ 25 + 83 = 108 s, still faster than the host path. SLM capacity limits chunk size: with 4 GiB of SLM, the job is a pipeline of ~60 chunks per device, so copy and execute should overlap using two range sets (double buffering).
  4. Host CPU freed. The host path consumes the CPU fully for 167 s; the device path consumes almost none.
  5. Verdict. Use the device program, with double buffering, explicit timeouts and a host-side reference check on a sample of chunks. Revisit if the host gains accelerators or if the device's compute engine throttles under sustained load (measure!).

Common mistakes

  • Assuming computational storage is always faster. Run the bottleneck model; a slow compute engine loses.
  • Submitting copy, execute and read together without waiting for completions.
  • Default I/O timeouts on Execute Program, causing spurious controller resets.
  • Forgetting activation after Load Program.
  • Leaking memory range sets and running out of SLM or range-set slots.
  • Trusting the program result as a length without bounds-checking against the output range.
  • Leaving program download enabled in production without a security review.
  • Using link traces to measure computational work. The work is invisible on the link.
  • Assuming programs read NVM namespaces directly. Data is staged in SLM.

Senior engineer insight

Computational storage succeeds in narrow, well-measured cases: high data reduction, a compute engine (often fixed-function) that keeps up, many drives per host, and a software stack willing to manage SLM staging. It fails when chosen as an architectural fashion. Senior engineers insist on the bottleneck model with measured numbers before any design review.

They also treat downloadable programs as a security architecture topic, not a feature: who signs programs, which program types are allowed, whether lockdown is on, how program state behaves across firmware activation and migration, and what telemetry exists to prove a program did only what it should. In a multi-tenant system, memory range sets are the isolation boundary — validation must try hard to break them.

Finally, debugging moves off the link. A senior engineer asks for device-side telemetry and per-command timestamps early, because a PCIe trace of a computational job is mostly silence.

Hints

Hint

For Question 2, set Cdev = Blink in the formulas: the device path is never faster than D/Cdev = D/Blink, which equals the host path when the link is the host bottleneck — regardless of selectivity.

Solution

Solution

Step 1: create range set ↔ Memory Range Set Management; load ↔ Load Program; activate ↔ Program Activation Management; execute ↔ Execute Program; errors would be command statuses defined in CP 1.3 (not stated here).

Step 2: in the unmodified model, indexing past a memoryview raises IndexError (Python enforces the bound), but a program that receives a MemoryRangeSet can reach rs.ranges[i][0].mem — the whole namespace. Passing only views closes that hole, mirroring a device that maps only the range set into the program's address space.

Step 3: with link 7 GB/s, media 24 GB/s and host compute 20 GB/s, the host path is always D/7. Device compute 4 GB/s: the device path is at least D/4, so it never wins. Device compute 10 GB/s: the device path is D/10 while s ≤ 0.7 and s·D/7 above that, so it wins for every s < 1 by up to 30%, and ties at s = 1. Device compute 30 GB/s: the device path is media-bound at D/24 for s ≤ 7/24 ≈ 0.29 (3.4× faster than the host), then limited by result transfer above that.

Step 4: link data ≈ 307,456 bytes vs 4,294,967,296 input bytes — about 1:14,000. Implied copy rate: 4 GiB / 0.36 s ≈ 11.9 GB/s; execute rate: 4 GiB / 0.54 s ≈ 8 GB/s.

Questions: 1 — NVMe does not order commands; Execute could run on partially copied data. 2 — none: with Cdev = Blink, the device path is never faster than the link-bound host path. 3 — device telemetry or progress counters, behaviour on a tiny input, and whether Abort succeeds; the link trace alone cannot distinguish them.

What a senior engineer notices

That the model's containment was only as strong as its interfaces — exactly the property to probe in a real device — and that the business case rests on Cdev, the least documented number.

  • Execute before activate → immediate error.
  • Range set larger than SLM → creation fails.
  • Output range too small → program fault.
  • Execute with no copy → program runs on stale or zero data and "succeeds".

Answers

1. Device-defined: shipped and validated by the vendor, can be hardware-accelerated, no download risk. Downloadable: flexible, application-specific, portable if the program type is standard (e.g. eBPF).

2. Thost = 500 / min(14, 20, 30) = 500 / 14 ≈ 35.7 s. Tdev = max(500/20 = 25, 500/16 = 31.25, 0.02 × 500 / 14 ≈ 0.71) = 31.25 s. Modest gain, compute-bound.

3. Two sets, each with an input range and an output range sized for the decompressed data: set A {in 0–1 GiB, out 1–4 GiB}, set B {in 4–5 GiB, out 5–8 GiB}. Ranges must not overlap between sets that run concurrently.

4. Load Program → Program Activation Management (activate) → Memory Range Set Management (create) → SLM copy in → Execute Program → SLM read out → Memory Range Set Management (delete) → Program Activation Management (deactivate) → (optionally unload, per CP 1.3).

5. The copy happens entirely inside the subsystem, from the NVM namespace's media into SLM; nothing crosses the PCIe link until the completion.

    Data is staged in Subsystem Local Memory, usually by an internal copy from an NVM namespace.

    • A controller reset
    • A Format NVM of the compute namespace

    Only active programs execute; activation is a separate step where the device can verify and install the program.

    • It always helps because PCIe is slow
    • It only helps on Gen3 links
    • It never helps if selectivity is below 1%

    Answer and reasoning

    The bottleneck model shows both conditions are required; a slow compute engine can make offload slower than the host path.

  5. What is the first abnormal event when a program hangs?

    • A PCIe completion timeout
    • The absence of the Execute Program completion by the host's deadline
    • An AER uncorrectable error
    • An MSI-X with no CQE
    Answer and reasoning

    A hung program produces no event at all; the host detects a missing completion at its timeout.

    • 01h and 02h
    • 02h and 03h
    • 03h and 04h
    • 04h and 05h
    Answer and reasoning

    NVM 00h, KV 01h, ZNS 02h, SLM 03h, Computational Programs 04h (confirm in Base 2.4).

  7. Explain why a PCIe trace of a large computational job is mostly silent, and what you use instead.

    Model answer

    The bulk data movement (NVM → SLM copy) and the computation happen inside the device. Only small commands, completions and results cross the link. Instead, use per-command submission/completion timestamps, device telemetry, program progress indicators and host-side logs.

  8. Why should program download be treated like kernel module loading?

    Model answer

    Because downloaded code executes inside a device that holds data for possibly many hosts and tenants; a malicious or buggy program could leak or corrupt data or deny service. It should be privileged, audited, restricted to verifiable program types, and disabled via lockdown when not needed.

  9. What does SLM provide that Computational Programs needs?

    Model answer

    Byte-addressable device memory organised as memory namespaces, plus commands to move data into and out of it (from NVM namespaces internally and from/to the host). Programs read and write only that memory, through memory range sets.

Interview questions

  1. Beginner. What is computational storage?

    Model answer

    Running computation inside or next to a storage device so that data is processed where it lives and only results travel to the host.

  2. Beginner. What is a compute namespace?

    Model answer

    A namespace using the Computational Programs command set; it holds programs at program indexes and is the target of Execute Program.

  3. Intermediate. Walk through running a filter on 10 GB of blocks with NVMe computational storage.

    Model answer

    Find the program (device-defined or load and activate a downloaded one); create a memory range set with input and output ranges in a memory namespace; copy the blocks from the NVM namespace into the input range (SLM, internal); wait; Execute Program with the range set and parameters; wait with an appropriate timeout; read the output range back by the reported length; delete the range set. Chunk if SLM is smaller than 10 GB, ideally double-buffered.

  4. Intermediate. How do Computational Programs and SLM relate?

    Model answer

    SLM provides the memory (memory namespaces) and data movement; Computational Programs provides programs, range sets and execution. Programs operate on SLM through range sets. SLM is usable alone; Computational Programs depends on SLM.

  5. Advanced. Execute Program commands occasionally time out and the Linux driver resets the controller, failing unrelated I/O. What do you do?

    Model answer

    Separate the cases: if executions are legitimately long, set explicit per-command pass-through timeouts sized to the program and input; if programs hang, find why (parameters, input size, throttling) with device telemetry and small-input reproductions. Mitigate blast radius: dedicated queues for compute commands, Abort before reset, and admission control on input size. Validate whether the device can abort running programs.

  6. Senior. Should your platform enable downloadable programs?

    Model answer

    Only with a clear use case that device-defined programs cannot serve, and with controls: signed programs, a verifiable program type, lockdown policy, tenant isolation via range sets that validation has tried to break, telemetry and incident response. Otherwise keep download locked and use device-defined programs.

  7. Senior. How would you validate range-set isolation?

    Model answer

    Adversarial programs that read/write one byte beyond each range, use overlapping and adjacent ranges, race range-set deletion against execution, reuse freed SLM, run concurrently on neighbouring sets, and attempt to observe other tenants' data; plus reset and firmware activation during execution. Every violation must fault deterministically without corrupting other ranges.

Model explanation for the child

Instead of bringing every toy part from the big warehouse to town just to throw most away, we put a little workbench in the warehouse. The worker there only knows certain jobs, and new jobs need the boss's OK. The worker may only use the tables we give him. He sorts the parts there, and we only bring the good ones to town. It's quicker if the worker is fast — but if he is very slow, it might be quicker to bring everything to town after all.

Chapter summary

The Computational Programs Command Set (revision 1.3, CSI 04h in libnvme) adds compute namespaces holding programs — device-defined or downloaded with Load Program and enabled with Program Activation Management — and executes them with Execute Program against memory range sets created with Memory Range Set Management. Programs operate on Subsystem Local Memory (SLM 1.3, CSI 03h), into which data is copied from NVM namespaces inside the device. Moving compute toward data helps when data reduction is high and the device's compute engine and internal media bandwidth outpace the link and host; it hurts when the compute engine is slow. Most of the work is invisible on PCIe, so debugging relies on completion timing and device telemetry. Downloadable programs are a security boundary and should be locked down unless needed.
