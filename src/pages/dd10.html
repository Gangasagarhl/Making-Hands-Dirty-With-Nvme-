This module studies the PCI Express (PCIe) Transaction Layer as a machine with six jobs — build and parse Transaction Layer Packets (TLPs), route them, order them, gate them with flow-control credits, track and complete non-posted requests, and detect and report end-to-end errors — and shows how an NVM Express (NVMe) controller's traffic exercises every one of them. It goes past Chapters 7, 10 and 12 with full header decoding, completion splitting, credit and tag arithmetic, ordering hazards, and the error classes a senior engineer must tell apart.

Orientation

Chapter 7 placed the Transaction Layer in the three-layer model; Chapter 10 introduced the TLP family and counted the TLPs of an NVMe command; Chapter 12 separated posted, non-posted and completion traffic and their latency consequences. This module integrates those into one working model of the layer and adds the parts the chapters only touched: header fields bit by bit, the routing rules, the ordering table and why it exists, the credit gate, completion splitting with Byte Count and Lower Address, tag budgets, attributes (Relaxed Ordering, No Snoop, ID-Based Ordering), traffic classes, prefixes, and Transaction Layer errors. Narrower deep dives follow: Module 11 (TLP Formats), Module 12 (Completions), Module 13 (Tags), Module 14 (Ordering), Module 17 (Flow Control).

Read first: Chapter 7 (PCIe Layer Model), Chapter 10 (TLPs), Chapter 12 (Posted vs Non-Posted). Helpful: Chapter 11 (TLP Header Anatomy), Module 06 (BAR and MMIO) for host-initiated traffic, Chapter 20 (DMA) for device-initiated traffic.

Kid story

A school sends notes between classrooms through a team of messengers. Every note has a label on the front: what kind of note it is, who it's for (a room number or a person's name), who sent it, and a ticket number.

Some notes are "do this" notes — "put these drawings on the wall" — and nobody answers them. Some are "please tell me" notes — "how many pencils are in the cupboard?" — and the answer comes back on a separate note with the same ticket number, so the asker knows which question it answers. A big answer might come back on several smaller notes, in order.

The messengers have rules. A "please tell me" note must never overtake a "do this" note sent before it, or the answer could describe the old wall instead of the new one. Each classroom has only a few in-trays, so a messenger may not deliver a note unless the room has said "I have space for two more". And if a note is nonsense — a ticket number nobody asked for, or a drawing bigger than the wall — the receiving room complains to the head teacher.

Mechanism

Follow one NVMe WRITE of 4 KiB on the lab system (MPS 256 bytes, MRRS 512 bytes, RCB 64 bytes, IOMMU on). The controller must read the data from host memory. Each step: who acts, what changes, where, what evidence.

  1. Doorbell arrives. Who: root complex as requester. What: posted MWr to BAR0 + 1008h. Where: SSD Transaction Layer RX: format checked, BAR claim, delivered to doorbell logic; Posted header and data credits consumed then returned by UpdateFC. Evidence: MWr in trace; UpdateFC-P DLLP afterwards.
  2. SQE fetch request. Who: SSD as requester. What: allocate Tag, build MRd 4 DW (IOVA above 4 GiB) Length 16 DW, start completion timer; wait for one Non-Posted header credit at the root port's receiver. Evidence: MRd with Tag; NPH credit consumption (visible only by modelling UpdateFC).
  3. Completion. Who: root complex as completer. What: reads memory (through the IOMMU translation), returns CplD with Status = Successful Completion, Byte Count 64, Lower Address = low 7 bits of the SQE address. Where: SSD RX matches Requester ID + Tag, stops the timer, frees the tag. Evidence: CplD with matching Tag.
  4. Data fetch requests. Who: SSD. What: 4 KiB at PRP1 split by MRRS 512 into 8 MRd, each with its own tag, issued as credits and tags allow. Evidence: 8 MRd, consecutive addresses, distinct tags.
  5. Split completions. Who: root complex. What: each 512-byte request answered by two CplD of 256 bytes (MPS bound; cut at RCB-aligned points), Byte Count 512 then 256. Completions for different tags may interleave; completions for one tag arrive in address order. Evidence: 16 CplD; Byte Count sequence per tag.
  6. Reassembly. Who: SSD RX. What: places each completion using Tag + Lower Address + Byte Count; when Byte Count of the last piece equals its payload, the request is complete. Evidence: none externally; internal errors would show as Unexpected Completion or Malformed TLP.
  7. Completion entry and interrupt. Who: SSD. What: MWr 16 bytes to CQ1, then MWr to the MSI-X address. Both posted, same requester, same TC: the interrupt write cannot pass the CQE write unless the interrupt TLP itself carries Relaxed Ordering. Evidence: two MWr in order.

Why NVMe cares: data writes (READ command results) followed by the CQE write followed by the MSI-X write form a producer–consumer chain. The driver must never see the CQE (or the interrupt) before the data is visible. Default ordering guarantees it; Relaxed Ordering on the data writes is safe (later CQE without RO cannot pass them), but RO on the CQE write would allow it to pass the data. Derived

Credits and tags: two independent budgets

BWread ≤ min( Ntags × Sreq / RTT , BWlink )
BWread
sustainable DMA read bandwidth of one requester (bytes per second)
Ntags
outstanding non-posted requests the requester can track (tag space, also limited by its own tracking table)
Sreq
bytes per read request (bounded by MRRS)
RTT
average time from issuing a read request to receiving its last completion
BWlink
effective link bandwidth for completion data in that direction

Example: 32 usable tags (Extended Tag disabled on a device that then uses 5-bit tags), MRRS 128 bytes, RTT 1.5 µs → 32 × 128 / 1.5 µs ≈ 2.7 GB/s, well below Gen4 x4's ≈ 7 GB/s. With 256 tags and MRRS 512: 256 × 512 / 1.5 µs ≈ 87 GB/s → the link is the limit. Derived (Little's law, Chapter 12).

Credits gate each hop: a TLP may be transmitted only if the receiver has advertised enough header credits (1 per TLP) and data credits (payload ÷ 16 bytes, rounded up) of that type. Root complexes and endpoints advertise infinite completion credits because a requester must have reserved room for the completions it asked for. Verified as the rule for endpoints and root complexes; switches differ. A credit stall looks like a gap in which TLPs of one type stop while others continue.

The ladder for the Transaction Layer

Labelled notes, some answered with ticket numbers, with overtaking rules, in-tray limits and complaints for nonsense notes.

The Transaction Layer turns reads, writes, messages and interrupts into TLPs, sends them where they belong, keeps them in a safe order, waits for buffer space, matches answers to questions, and reports problems.

Header builders/parsers, tag allocators with per-tag timers, per-type queues and credit counters, ordering logic, reassembly buffers, error logging registers in every port and function.

The Transaction Layer chapter of the PCI Express Base Specification: TLP formats, routing, ordering table, flow control, completion rules, error classes; the configuration registers that control them.

MRd/MWr/Cfg/Msg/AtomicOp requests and Cpl/CplD completions with Requester ID, Tag, Byte Count, Lower Address; credit updates in DLLPs.

A trace pairs each completion with its request by Requester ID and Tag, shows splitting and interleaving, shows ordering of writes, and shows gaps where credits or tags ran out.

UR, CA, Malformed, Unexpected Completion, Completion Timeout, Poisoned and ECRC errors each point at a specific originator and layer; throughput ceilings point at tags, MRRS or credits.

Specification discipline

Applicable documents: PCI Express Base Specification, Revision 6.x/7.0 — Transaction Layer Specification (TLP formats, routing, ordering, flow control, completion rules, error handling), PCI Express Base Specification — PCI Express Capability Structure and Advanced Error Reporting Capability, and, for how NVMe uses them, NVMe over PCIe Transport Specification 1.4 (which leaves the Transaction Layer to PCIe and defines the controller's memory-mapped interface and queue usage).

Memory writes and messages are posted; reads, configuration, I/O and AtomicOps are non-posted. Completions are routed by Requester ID and matched by Tag. Completion status values: Successful Completion (000b), Unsupported Request (001b), Configuration/Request Retry Status (010b), Completer Abort (100b). A request must not cross a 4 KiB boundary. Payload must not exceed MPS.

Throughput ceilings from tags and MRRS (formula above); the safety of RO on NVMe data writes but not on CQE writes; that a UR completion to the SSD's DMA read implicates the address (mapping) before the root complex.

Whether the root complex returns UR or CA for a DMA read that the IOMMU blocks; how many outstanding reads a given SSD issues; completion split patterns of a given root complex; credit advertisement sizes; whether a device sets RO on any of its writes when enabled.

Flit Mode (6.0+) changes the header format and adds an orthogonal header content mechanism; 10-bit tags appeared in 4.0; DMWr (Deferrable Memory Write) and other newer request types exist only in recent revisions. Uncertain on the exact revision that introduced each; check the revision history of the Base Specification.

The specification does not say how many tags a device should use, how long a completer may take within the timeout, which completion-timeout range to choose, or what an operating system must do with an uncorrectable error. NVMe does not require or forbid Relaxed Ordering on particular writes; it requires the controller to make data visible before the completion entry, and the controller must choose attributes that preserve that on PCIe.

Never assume: that completions return in request order; that a Malformed TLP report means the reporter is broken (it usually means the sender is); that MPS capability equals programmed MPS; that RO is harmless; that a link-level replay or Ack means the transaction completed end to end.

Completion rules worth memorising

  • A completer may split a read into several completions, each ending at an RCB-aligned address (except the last), each no larger than MPS; completions of the same request are returned in increasing address order. Verified
  • Byte Count in each completion is the number of bytes remaining including that completion; Lower Address gives the low 7 bits of the first byte's address. Verified
  • A completion with a non-successful status has no data and ends the request. Verified
  • A completion that matches no outstanding request is an Unexpected Completion at the receiver. Verified

Analysis. On the wire, data precede the CQE. But with RO set on the CQE write, the root complex is permitted to make the CQE visible in memory before earlier data writes, so the driver can observe a new completion entry (its phase tag) while data are still in flight inside the root complex. Is the device wrong (RO on a write that publishes completion), or the root complex (reordering more than the platform documentation claims)? The PCIe rules allow the reordering once RO is set, so the device's use of RO on the CQE is the defect from a specification standpoint; but the decisive experiment must separate it from a driver bug (reading the buffer before checking the phase tag, or a missing read barrier after the phase check): reproduce with RO disabled only on CQE writes (if the device allows per-type control), and with a driver build that adds a barrier after the phase check. If disabling RO on CQEs alone fixes it, the attribute choice is the root cause (confidence: medium-high).

Beginner lab: decode TLP headers from hex

Safe lab

  • Objective: decode memory-request and completion headers (non-Flit Mode) from DWORDs, including the AER header log format the kernel prints.
  • Prerequisites: the header tables above; Chapter 11.
  • Setup: Python 3.
#!/usr/bin/env python3
"""Decode non-Flit TLP headers given as hex DWORDs (executable). Usage: python3 tlp_hdr.py 60000080 010000ff 00000002 00000000"""
import sys

TYPES = {(0b000, 0b00000): "MRd32", (0b001, 0b00000): "MRd64", (0b010, 0b00000): "MWr32",
         (0b011, 0b00000): "MWr64", (0b000, 0b00100): "CfgRd0", (0b010, 0b00100): "CfgWr0",
         (0b000, 0b01010): "Cpl", (0b010, 0b01010): "CplD"}
STATUS = {0: "SC", 1: "UR", 2: "RRS/CRS", 4: "CA"}

def bdf(x):
    return f"{x >> 8:02x}:{(x >> 3) & 0x1f:02x}.{x & 7}"

def decode(dws):
    d0 = dws[0]
    fmt, typ = d0 >> 29, (d0 >> 24) & 0x1f
    length = d0 & 0x3ff or 1024
    name = TYPES.get((fmt, typ), f"Fmt={fmt:03b} Type={typ:05b}")
    out = [f"{name}: TC={(d0 >> 20) & 7} TD={(d0 >> 15) & 1} EP={(d0 >> 14) & 1} "
           f"RO={(d0 >> 13) & 1} NS={(d0 >> 12) & 1} AT={(d0 >> 10) & 3} Length={length} DW"]
    d1 = dws[1]
    if name in ("Cpl", "CplD"):
        d2 = dws[2]
        out.append(f"  Completer={bdf(d1 >> 16)} Status={STATUS.get((d1 >> 13) & 7, 'reserved')} "
                   f"BCM={(d1 >> 12) & 1} ByteCount={d1 & 0xfff or 4096}")
        out.append(f"  Requester={bdf(d2 >> 16)} Tag=0x{(d2 >> 8) & 0xff:02x} LowerAddr=0x{d2 & 0x7f:02x}")
    else:
        out.append(f"  Requester={bdf(d1 >> 16)} Tag=0x{(d1 >> 8) & 0xff:02x} "
                   f"LastBE={(d1 >> 4) & 0xf:04b} FirstBE={d1 & 0xf:04b}")
        if fmt & 1:
            addr = (dws[2] << 32) | (dws[3] & ~3 & 0xffffffff)
        else:
            addr = dws[2] & ~3 & 0xffffffff
        out.append(f"  Address=0x{addr:x}")
        if fmt & 1 and addr < (1 << 32):
            out.append("  WARNING: 4 DW header used for an address below 4 GiB (Malformed)")
        if ((addr & 0xfff) + length * 4) > 0x1000:
            out.append("  WARNING: request crosses a 4 KiB boundary (Malformed)")
    return "\n".join(out)

samples = [sys.argv[1:]] if len(sys.argv) > 1 else [
    ["60000080", "010000ff", "00000002", "00000000"],      # MWr64 512 B from 01:00.0
    ["4a000040", "00090200", "01004100"],                  # CplD from 00:01.1, BC=512, tag 0x41
    ["20000010", "01004aff", "00000000", "fe600040"],      # MRd64 to a 32-bit address
]
for s in samples:
    print(decode([int(x, 16) for x in s]))
    print()

Intermediate lab: TLP, credit and tag budget for NVMe transfers

"""TLP/credit/tag budget for one NVMe READ or WRITE (executable). Ignores PRP-list fetches for simplicity."""
import math

def budget(op, size, mps=256, mrrs=512, rcb=64, tags=256, rtt_us=1.5, link_gbs=7.0):
    out = {"op": op, "size": size}
    if op == "READ":                                   # controller writes data to host
        out["dev_to_host_MWr_data"] = math.ceil(size / mps)
        out["posted_data_credits"] = math.ceil(size / 16)
        out["host_to_dev"] = "doorbells only"
    else:                                              # WRITE: controller reads data from host
        reqs = math.ceil(size / mrrs)
        cpls_per_req = math.ceil(mrrs / min(mps, mrrs))
        out["dev_to_host_MRd"] = reqs
        out["host_to_dev_CplD"] = reqs * cpls_per_req
        out["np_header_credits_used"] = reqs
        ceiling = tags * mrrs / (rtt_us * 1e-6) / 1e9
        out["tag_ceiling_GBps"] = round(ceiling, 1)
        out["bottleneck"] = "tags/MRRS" if ceiling < link_gbs else "link"
    out["plus"] = "1 SQE MRd + 1 CplD, 1 CQE MWr, 1 MSI-X MWr, 2 doorbell MWr"
    return out

for args in (("READ", 4096, 256, 512), ("WRITE", 4096, 256, 512),
             ("WRITE", 131072, 256, 512), ("WRITE", 131072, 256, 128)):
    print(budget(*args))
print(budget("WRITE", 131072, 256, 128, tags=32))

4 KiB READ: 16 MWr of 256 bytes, 256 posted data credits. 4 KiB WRITE: 8 MRd, 16 CplD. 128 KiB WRITE with MRRS 512: 256 MRd, 512 CplD, tag ceiling ≈ 87 GB/s → link-bound. Advanced lab: a completion checker

Safe lab Simulation on synthetic TLP streams.

  • Objective: implement the requester-side completion rules: match by Requester ID and Tag, track bytes remaining, check Byte Count, Lower Address and ordering within a tag, detect unexpected completions and timeouts.
  • Prerequisites: completion rules above; Module 12 if available.
  • Setup: Python 3.
"""Requester-side completion checker (executable). Events: (t_ns, kind, fields). Memory reads only."""

TIMEOUT_NS = 50_000_000      # use your configured range; this is illustrative

def check(events, rid=0x0100):
    out, pending = [], {}
    for t, kind, f in events:
        if kind == "MRd":
            pending[f["tag"]] = {"addr": f["addr"], "left": f["len"], "next": f["addr"], "t": t}
        elif kind in ("CplD", "Cpl"):
            if f["rid"] != rid or f["tag"] not in pending:
                out.append((t, "Unexpected Completion", f))
                continue
            p = pending[f["tag"]]
            if f.get("status", "SC") != "SC":
                out.append((t, f"error completion {f['status']} for tag 0x{f['tag']:02x}", f))
                del pending[f["tag"]]
                continue
            if f["bc"] != p["left"]:
                out.append((t, f"Byte Count {f['bc']} != remaining {p['left']} (tag 0x{f['tag']:02x})", f))
            if f["la"] != (p["next"] & 0x7f):
                out.append((t, f"Lower Address 0x{f['la']:02x} != expected 0x{p['next'] & 0x7f:02x}", f))
            p["left"] -= f["len"]
            p["next"] += f["len"]
            if p["left"] == 0:
                del pending[f["tag"]]
        elif kind == "now":
            for tag, p in list(pending.items()):
                if t - p["t"] > TIMEOUT_NS:
                    out.append((t, f"Completion Timeout tag 0x{tag:02x}", p))
                    del pending[tag]
    return out or [("ok", "all completions consistent")]

Symptom

Second check

High with matching IOMMU and TLP addresses.

High.

Interview

Beginner

  1. What are the Transaction Layer's main jobs?

    Model answer

    Build and parse TLPs, route them, enforce ordering, gate them with flow-control credits, track and complete non-posted requests, and detect/report end-to-end errors.

  2. Which TLPs does an NVMe READ command cause from the SSD?

    Model answer

    An MRd for the SQE (plus PRP list reads if needed), MWr TLPs carrying data to host memory, an MWr for the CQE and an MWr for the MSI-X interrupt.

  3. What links a completion to its request?

    Model answer

    Requester ID and Tag (the Transaction ID).

  4. What is MPS?

    Model answer

    Max Payload Size: the largest data payload a function may send in one TLP, as programmed in Device Control.

  5. Is a memory write acknowledged end to end?

    Model answer

    No. It is posted; only hop-by-hop Data Link Layer Acks exist.

Intermediate

  1. How is a 4 KiB DMA read with MRRS 512 and MPS 256 carried?

    Model answer

    8 MRd of 512 bytes, each answered by (at least) two 256-byte CplD, completions possibly interleaved across tags but in address order within a tag.

  2. What do Byte Count and Lower Address tell the requester?

    Model answer

    Bytes remaining including this completion, and the low 7 address bits of its first byte, so it can place data and know when the request is done.

  3. Why must posted writes be able to pass non-posted requests?

    Model answer

    To avoid deadlock: if posted writes could be blocked behind reads that cannot complete until those writes drain, the fabric could lock up.

  4. What are header and data credits?

    Model answer

    Receiver buffer space advertised per type: one header credit per TLP, one data credit per 16 bytes of payload.

  5. Why do endpoints advertise infinite completion credits?

    Model answer

    A requester must have room for the completions of requests it issued; finite completion credits could deadlock.

Advanced

  1. Is RO safe on NVMe data writes? On CQE writes?

    Model answer

    On data writes, yes: a later CQE write without RO cannot pass them. On CQE writes, no: the CQE could become visible before the data.

  2. Which port reports a Malformed TLP and what does that imply?

    Model answer

    The receiver that detects the violation; the transmitter is usually at fault. Decode the header log to identify the sender.

  3. How do tags limit bandwidth?

    Model answer

    Outstanding reads ≤ tags; bandwidth ≤ tags × request size ÷ round-trip time.

  4. What happens to a completion that arrives after the requester timed out?

    Model answer

    The tag is retired, so it matches nothing and is reported as an Unexpected Completion.

  5. Why can a perfect wire order still produce out-of-order memory visibility?

    Model answer

    Relaxed Ordering lets the root complex commit writes to memory in a different order; the analyzer sees only wire order.

Senior

  1. Review an SSD's Transaction Layer defaults: what do you check?

    Model answer

    Tag usage and support (Extended Tag, 10-bit), outstanding read depth, MRRS handling, MPS capability, attribute use (RO only on safe writes; NS policy), completion timeout ranges supported, AER implementation and header logging, behaviour on UR/CA completions, and handling of poisoned data.

  2. Design a Transaction Layer validation plan for a new SSD.

    Model answer

    Exerciser-driven inbound requests of every size, alignment and BE pattern to BARs; outbound DMA against completers that split differently and reorder across tags; MPS/MRRS sweeps; tag exhaustion; credit starvation; error injection (UR, CA, poison, ECRC, timeout, unexpected completions); ordering checks for data/CQE/MSI chains with and without RO.

  3. A customer sees Completion Timeouts only in one server model. Plan.

    Model answer

    Compare timeout ranges and root-complex latency under load across models; check IOMMU and memory configuration; capture to see whether completions are late or missing; correlate with link errors; adjust range or firmware; engage platform vendor if completions vanish.

  4. When would you enable ECRC?

    Model answer

    When switches or other intermediate components sit on the path and end-to-end data integrity beyond LCRC is needed; only if every relevant component supports generation and checking; weigh the small bandwidth cost and the operational handling of ECRC errors.

  5. Explain to a firmware team why "the root port reported it" does not mean "the root port broke it".

    Model answer

    Many Transaction Layer errors are reported by the receiver of a bad TLP or by the requester that waited in vain. The header log identifies the TLP's source; the error type identifies the rule broken. Attribution follows the evidence, not the reporter.

Quiz

  1. A CplD with Byte Count 256 and Length 64 DW for a 512-byte request is:

    • the first completion
    • the last completion
    • malformed
    • unexpected
    Answer and reasoning

    Byte Count equals this completion's payload (256 bytes), so it is the last.

  2. Which error is reported by the requester rather than the completer?

    • Unsupported Request
    • Malformed TLP
    • Completion Timeout
    • Completer Abort
    Answer and reasoning

    Only the requester knows it waited too long.

  3. Fmt 011, Type 00000 identifies:

    • MRd32
    • CplD
    • CfgWr0
    • MWr64
    Answer and reasoning

    4 DW header with data, memory request.

  4. Which attribute, if set on the CQE write, can let it become visible before the data?

    • Relaxed Ordering
    • No Snoop
    • TC=1
    • TD
    Answer and reasoning

    RO permits passing earlier posted writes.

  5. Compute the read bandwidth ceiling for 64 tags, 256-byte requests, 2 µs round trip.

    Model answer

    64 × 256 / 2 µs = 8.19 GB/s.

  6. Why can completions for tags 0x41 and 0x42 interleave, but not two completions of tag 0x41 swap order?

    Model answer

    Different transactions have no mutual ordering requirement; completions of the same request must be returned in address order so the requester can track Byte Count and placement.

  7. An MRd64 carries address 0x0000_0000_FE60_0040. What is wrong?

    Model answer

    A 4 DW header must not be used for an address below 4 GiB; the TLP is malformed.

  8. Name three NVMe-relevant causes of a UR completion to the SSD's DMA read.

    Model answer

    IOVA not mapped in the IOMMU; address outside root-complex decode; platform blocking (ACS or security policy) — exact status (UR or CA) is platform-dependent.

  9. Which register fields would you check first for a throughput plateau on writes?

    Model answer

    Device Control MRRS and Extended Tag, Device Control 2 10-bit Tag Requester Enable; then measure round-trip time.

Teach-back

  1. To a child: explain ticket numbers and the overtaking rule.

    Model explanation

    "When you ask a question by note, you put a ticket number on it, and the answer comes back with the same number, so you know which question it answers even if answers come back mixed up. And a question must never overtake an earlier 'do this' note, or the answer might be about the old wall, not the new one."

  2. To a junior engineer: walk through a 4 KiB NVMe WRITE at the Transaction Layer.

    Model explanation

    "Host rings the doorbell with a posted MWr. The SSD fetches the SQE with an MRd and gets a CplD matched by tag. It reads the 4 KiB with eight 512-byte MRds (MRRS), each answered by two 256-byte CplDs (MPS), interleaved across tags. When Byte Count hits zero for each tag, the data are in. Then it posts the CQE and the MSI-X write, in that order."

  3. To a senior engineer: argue how you would attribute a fatal Malformed TLP in a switched topology.

    Model explanation

    "Decode the AER header log: Fmt/Type, Length, Requester ID tell me who sent what. Compare the violated rule (MPS, boundary, header size) with each port's configuration along the path. The reporting port is the first one whose rule was violated, not necessarily the culprit. Then I find the configuration step that allowed the mismatch — usually hot-plug MPS — and fix it with a regression test."

Mastery gate

Do not consider this module mastered until you can:

  • explain the Transaction Layer's six jobs and how NVMe traffic uses each;
  • diagram a 4 KiB NVMe READ and WRITE at TLP level with tags, splits, credits and ordering;
  • identify requests, completions, splitting, tag exhaustion, credit stalls and attribute use in a trace, and mark the first abnormal TLP;
  • debug UR/CA, Malformed, Completion Timeout, Unexpected Completion and RO-related corruption to their originators;
  • distinguish Transaction Layer behaviour from the Data Link Layer (Chapter 7, Module 15), from header-format detail (Module 11), from completion and tag deep dives (Module 12, Module 13), from ordering (Module 14) and flow control (Module 17), and from NVMe queue semantics (Chapter 25);
  • cite the PCI Express Base Specification's Transaction Layer chapter and capability structures, and the NVMe over PCIe Transport Specification 1.4, for each claim.
