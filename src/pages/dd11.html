Chapter 11 taught you to read the three or four header doublewords of an ordinary Transaction Layer Packet (TLP). This module looks at the whole packet as a format family: prefixes in front of the header, the optional digest behind the payload, the less common headers (AtomicOps, messages, configuration), the rules a receiver applies before it accepts any of them, and how to tell a format bug from a display bug when all you have is a log.

Orientation

A TLP is more than a header. On a non-Flit link it can be up to four parts: zero or more TLP prefixes, the header (3 or 4 doublewords), an optional data payload, and an optional TLP digest carrying the End-to-end Cyclic Redundancy Check (ECRC). Each part has its own rules, its own enable bits in configuration space and its own error when it is wrong. This module deepens that picture. It assumes you can already decode DW0, memory request headers and completion headers by hand; it goes on to format families, receiver-side format checking, the formats NVMe engineers meet only occasionally (but then urgently), and forensic decoding when the evidence is a log rather than a capture.

Field-by-field decoding of DW0, memory request, configuration and completion headers is in Chapter 11 — TLP Header Anatomy. TLP kinds and routing are in Chapter 10 — TLPs. Posted versus non-posted is in Chapter 12. If "0x4A means CplD" is not yet automatic for you, go back first. The browser decoder on the TLP Header Decoder tool page is useful throughout.

Where this goes next: completions as a protocol in Module 12 — PCIe Completions, the Tag field as a resource in Module 13 — PCIe Tags, the attribute bits as ordering policy in Module 14 — PCIe Ordering, and the sequence number and LCRC that wrap every TLP on the wire in Module 15 — PCIe Data Link Layer.

Kid story

Think of a train. The engine at the front says where the train goes and how many wagons it pulls — that is the header. Some trains have little flag cars in front of the engine ("this train belongs to the blue company") — prefixes. Behind the engine come the wagons — the payload. Some trains end with a caboose holding a check number that adds up everything on board, so the last station can tell if anything was swapped — the digest.

The station master checks every train. Does the engine say three wagons and are there three? Is there a caboose if the engine promised one? A flag car he does not understand? If anything is wrong, the whole train goes to a siding and he writes the engine's number in a notebook — the AER Header Log.

Analogy boundary

What it represents. The fixed order of TLP parts (prefixes, header, payload, digest), the idea that the header announces what follows, and that the receiver checks the announcement against reality before accepting the packet.

What it hides. The Data Link Layer wrapper (sequence number, LCRC) and Physical Layer framing are added and removed at every link and are not part of the TLP (see Module 15). Switches read only the routing parts of the train.

Where it misleads. Flag cars sound decorative; an End-End prefix changes how the destination must handle the packet, and a component that does not support it must not ignore it. Not every station checks the caboose: only receivers with ECRC checking enabled do. And a receiver never accepts part of a malformed TLP; it is discarded whole.

Architecture

The format of a TLP is produced by one Transaction Layer and checked by another. Between them, switches look at as little of it as they can. The architecture of "format" is therefore the set of places where fields are created, inspected and recorded.

Mechanism

Follow one TLP's format from creation to acceptance. The example is the Lab SSD returning 256 bytes of READ data to host memory with ECRC enabled on the path (an optional configuration; it is off in the base example system).

  1. Configuration gates the options. Firmware/OS (who) set MPS = 256 B in Device Control, ECRC Generation Enable on the SSD and ECRC Check Enable on the Root Port (what), in configuration space (where). Evidence: lspci -vvv.
  2. The DMA engine chooses the format. The SSD's write DMA engine picks 4DW (address above 4 GiB) with data: Fmt 011b, byte 0 = 0x60, in its header builder. Evidence: analyzer label "MWr(64)".
  3. Length and byte enables are set. The DMA splitter writes Length 64 and BEs 1111b/1111b into DW0 [9:0] and DW1 [7:0]. Evidence: header 60008040 010000ff 00000002 00000000.
  4. The digest is appended. The ECRC generator sets TD (byte 2 = 0x80) and appends one DW computed over prefixes, header (variant bits fixed) and payload. Evidence: 16 + 256 + 4 = 276 bytes; analyzer "ECRC OK".
  5. Credits are consumed. The SSD's Transaction Layer spends one Posted header credit and 16 Posted data credits. Evidence: later UpdateFC-P DLLPs (Chapter 16).
  6. The link carries it. The Data Link and Physical Layers add and strip sequence number, LCRC and framing per hop. Evidence: Seq/LCRC columns — not TLP fields.
  7. The receiver checks the format. The Root Port checks Fmt/Type, Length ≤ MPS and = payload, BEs, 4 KiB, digest presence and ECRC. Evidence: nothing on success; on failure, discard plus AER status and Header Log.
  8. The TLP is executed. The Root Complex translates the IOVA and commits the write. Evidence: data visible to the CPU only.

The ladder for "a TLP format"

A train: flag cars in front, an engine that announces everything, wagons, and sometimes a caboose with a check number. The station master counts before letting it in.

A TLP is prefixes (Fmt 100b, optional), a 3/4-DW header, a payload whose size the header's Length announces, and a digest whose presence TD announces. Receivers verify every announcement.

Header builders take fields from DMA descriptors and configuration registers; receivers have a parser that checks Fmt/Type, Length against the actual byte count and MPS, byte enables, and digest; failures go to AER with the header captured into the Header Log.

The PCI Express Base Specification — Transaction Layer Specification defines the TLP formats, the prefix rules, ECRC rules, and the list of conditions that make a TLP malformed; the AER capability defines how they are logged.

Every TLP kind is a variation of the same skeleton: memory requests, I/O and configuration requests, messages (with routing in Type), completions, AtomicOps, each possibly prefixed and digested.

An analyzer shows the parts as separate decoded blocks ("Prefix: PASID", "Header", "Data", "ECRC"). An AER log shows only the header (and prefixes in a separate log), as big-endian DWs.

Format bugs are the most deterministic PCIe bugs: one specific transfer shape produces them every time. Find the shape (size, alignment, address width, option enabled) and you have both the trigger and the fix.

Format families beyond memory requests

Messages

Messages always use a 4DW header (Fmt 001b without data, 011b with data). Type is 10rrr, where rrr selects routing. Length is reserved (zero) for messages without data. DW1 carries Requester ID, Tag and the 8-bit Message Code. DW2–DW3 hold an address (address-routed), a target ID (ID-routed), or message-specific content.

AtomicOps

FetchAdd, Swap and Compare-and-Swap (CAS) are non-posted requests with data. FetchAdd and Swap carry one operand of 32 or 64 bits (Length 1 or 2); CAS carries a compare value and a swap value, each 32, 64 or 128 bits (Length 2, 4 or 8). The target address must be naturally aligned to the operand size. The completer returns the original value in a CplD (Length 1, 2 or 4). Support is advertised in Device Capabilities 2 (AtomicOp completer support per size, and AtomicOp routing for switch and Root Ports) and a requester may issue them only when AtomicOp Requester Enable in Device Control 2 is set. Verified for the existence of these controls; exact byte-enable and Lower Address rules for AtomicOps Uncertain — read the AtomicOp sections of the Transaction Layer chapter.

NVMe controllers do not normally issue AtomicOps; accelerators sharing the host do, so you meet them in mixed captures and in Root Port logs ("AtomicOp Egress Blocked").

TLP prefixes

A DW whose Fmt field is 100b is not a header; it is a prefix, and the header follows it. Bit 4 of the prefix's Type field distinguishes Local (0) from End-End (1). Local prefixes are consumed on the link where they are sent. End-End prefixes travel with the TLP to its destination; support is advertised by End-End TLP Prefix Supported and a Max End-End TLP Prefixes count in Device Capabilities 2, and Device Control 2 has an End-End TLP Prefix Blocking control on ports. Named prefixes include PASID (End-End), extended TLP Processing Hints (End-End), Multi-Root I/O Virtualization (Local) and vendor-defined local and End-End prefixes. Uncertain Exact prefix Type encodings (for example a PASID prefix first byte of 0x91) are commonly quoted; verify them in the TLP Prefix tables before you write a decoder.

The digest (ECRC)

TD = 1 means one DW of ECRC follows the payload (or the header if there is no payload). ECRC is computed by the original requester or completer and checked by the final receiver if ECRC Check is enabled there. Switches forward it. Because a few header bits may legitimately change in flight, the ECRC calculation treats them as fixed values: the EP bit and bit 0 of the Type field (which a bridge changes when it converts a Type 1 configuration request into Type 0) are the commonly cited variant bits. Uncertain on the complete list — confirm in the ECRC Rules of your revision. Consequence: a switch that poisons a TLP (sets EP) does not cause an ECRC error, which is exactly what you want.

Inside an NVMe controller, the PCIe IP block builds headers from an internal request interface (address, length, attributes, tag). Format bugs come in two flavours that look identical on the wire: the NVMe front-end asks for something illegal (a 4 KiB crossing, a stale MPS) and the IP sends it; or the IP mis-encodes something legal. Front-end bugs follow NVMe structures (PRP boundaries, SGL segment ends); IP bugs follow arithmetic edges (Length 1024, last-DW byte enables). Linux view

Linux never sees TLPs in normal operation. It sees configuration space (which options are supported and enabled) and AER logs (the header, and on capable hardware the prefix log, of the first error). All commands below are read-only and safe.

# Options that change TLP format: AtomicOps, End-End prefixes, 10-bit tags, ECRC
sudo lspci -vvv -s 01:00.0 | grep -E 'DevCap2|DevCtl2|AtomicOps|EETLPPrefix|10BitTag'
sudo lspci -vvv -s 01:00.0 | grep -A8 'Advanced Error Reporting' | grep -iE 'ECRC|HeaderLog|AERCap'

# The same on the Root Port: what it accepts and checks
sudo lspci -vvv -s 00:01.1 | grep -E 'DevCap2|DevCtl2|AtomicOps|EETLPPrefix'

# AER messages with logged headers (and prefixes when logged)

Labs

All four labs are Safe lab: offline decoding, simulation, and read-only inspection. None writes configuration space.

Beginner lab — encode the families by hand

Objective. Produce correct header DWs for five format families from the example system. Prerequisites. Chapter 11. Setup. Paper, the Fmt/Type table from Chapter 11, the message table above.

Procedure.

  1. Encode the CQ1 head doorbell write = 9 from the Root Complex (Tag 0).
  2. Encode the Lab SSD's MSI-X write for vector 1 to address 0xFEE0_1000.
  3. Encode ERR_NONFATAL from the Lab SSD.
  4. Encode a CfgWr0 from the Root Port to 01:00.0 offset 0x004 (Command register) with Tag 0x12.
  5. Encode Deassert_INTA from the Lab SSD.

Observations. Count which ones are 3DW and which 4DW and why. Questions. Which of the five has a Length of 0 that is legal? Which needs a payload?

Expected reasoning. Address width decides 3DW/4DW for memory; messages are always 4DW; configuration is always 3DW with Length 1.

Solution

(1) 40000001 0009000f fe60100c, payload 09 00 00 00. (2) 40000001 0100000f fee01000, payload = the Message Data from the MSI-X table entry (0x0000_0041 for vector 1 in the example system: bytes 41 00 00 00). (3) 30000000 01000031 00000000 00000000. (4) 44000001 0009120f 01000004, payload = new Command value; the completion will be a Cpl (no data). (5) 34000000 01000024 00000000 00000000. Messages (3, 5) have Length 0 legally; (1), (2), (4) carry one DW of data.

Extension. Encode a 64-bit FetchAdd to 0x2_0000_8000 (Tag 0x30) and state the completion Length.

Intermediate lab — a format builder and round-trip checker

Objective. Build TLP headers from fields in code, compute their on-wire size, and verify against a decoder. Prerequisites. Python 3, the decoder from Chapter 11. Setup. Save the program below as tlp_build.py.

#!/usr/bin/env python3
"""Build non-Flit TLP headers from fields; compute on-wire size; self-check.
Standard library only. Synthetic examples for teaching."""

FMT = {"3dw": 0b000, "4dw": 0b001, "3dw_d": 0b010, "4dw_d": 0b011, "prefix": 0b100}
TYPE = {"mem": 0b00000, "cfg0": 0b00100, "cfg1": 0b00101, "cpl": 0b01010,
        "fetchadd": 0b01100, "swap": 0b01101, "cas": 0b01110}
MSG_ROUTE = {"to_rc": 0, "addr": 1, "id": 2, "bcast": 3, "local": 4, "gather": 5}

def dw0(fmt, typ, length=0, tc=0, ro=0, ns=0, ido=0, td=0, ep=0, at=0):
    return ((fmt << 29) | (typ << 24) | (tc << 20) | (ido << 18) | (td << 15) |
            (ep << 14) | (ro << 13) | (ns << 12) | (at << 10) | (length & 0x3FF))

def mem(write, addr, nbytes, rid, tag, td=0, ro=0):
    if addr & 3 or nbytes % 4:
        raise ValueError("this builder handles DW-aligned transfers only")
    if (addr & 0xFFF) + nbytes > 4096:
        raise ValueError("request would cross a 4 KiB boundary")
    length = nbytes // 4
    wide = addr >= 1 << 32
    fmt = (0b010 if write else 0b000) | (1 if wide else 0)
    lbe = 0 if length == 1 else 0xF
    hdr = [dw0(fmt, TYPE["mem"], length, td=td, ro=ro),
           (rid << 16) | (tag << 8) | (lbe << 4) | 0xF]
    hdr += [addr >> 32, addr & 0xFFFFFFFC] if wide else [addr & 0xFFFFFFFC]
    return hdr, (length if write else 0), td

def msg(code, rid, route="to_rc"):
    hdr = [dw0(0b001, 0b10000 | MSG_ROUTE[route]), (rid << 16) | code, 0, 0]
    return hdr, 0, 0

def wire_bytes(hdr, data_dw, td, prefixes=0, framing=4):
    """Prefix + header + data + digest + 6 DLL bytes + framing (128b/130b STP = 4)."""
    return 4 * prefixes + 4 * len(hdr) + 4 * data_dw + 4 * td + 6 + framing

def show(name, built, payload_bytes):
    hdr, data_dw, td = built
    size = wire_bytes(hdr, data_dw, td)
    eff = payload_bytes / size if size else 0
    print(f"{name:28s} {' '.join(f'{d:08x}' for d in hdr):40s} "
          f"{size:4d} B on wire, efficiency {eff:5.1%}")
    return hdr

if __name__ == "__main__":
    RC, SSD = 0x0009, 0x0100
    a = show("SQ1 doorbell MWr32", mem(True, 0xFE601008, 4, RC, 0), 4)
    assert a == [0x40000001, 0x0009000F, 0xFE601008]
    b = show("SQE fetch MRd64", mem(False, 0x1_2340_0100, 64, SSD, 0x21), 0)
    assert b == [0x20000010, 0x010021FF, 0x00000001, 0x23400100]
    show("READ data MWr64 256 B", mem(True, 0x2_0000_0000, 256, SSD, 0), 256)
    show("READ data MWr64 256 B ECRC", mem(True, 0x2_0000_0000, 256, SSD, 0, td=1), 256)
    show("READ data MWr64 64 B", mem(True, 0x2_0010_0000, 64, SSD, 0), 64)
    show("CQE MWr64 16 B", mem(True, 0x1_2341_0040, 16, SSD, 0), 16)
    e = show("ERR_COR message", msg(0x30, SSD), 0)
    assert e == [0x30000000, 0x01000030, 0, 0]
    try:
        mem(True, 0x2_0000_0F80, 256, SSD, 0)
    except ValueError as err:
        print("rejected as expected:", err)
    print("all self-checks passed")

Procedure. Run it. Then feed each printed header into the Chapter 11 decoder and confirm the decode. Add a builder for configuration requests and Assert/Deassert messages.

Observations. Record the efficiency column. Questions. (1) Why is the CQE's efficiency so low and why does that not matter much? (2) What does ECRC cost on a 256-byte write in percent? (3) What would the 4 KiB check have to change if you supported byte-granular SGL addresses?

Expected reasoning. Small TLPs are dominated by fixed overhead; their count, not their bytes, is what costs. ECRC adds 4 bytes per TLP.

Solution

(1) 16 bytes in a 42-byte TLP (≈ 38%), but one per command: at 1 M IOPS ≈ 42 MB/s of link time, negligible. (2) 286 vs 282 bytes, ≈ 1.4%. (3) Compute BEs from the true start and end byte offsets and use the true end address for the 4 KiB check — exactly where real DMA engines grow bugs.

Extension. Add a "prefix" argument and count one header credit per TLP regardless of prefixes; estimate how many header credits per microsecond a 64-byte-write stream consumes at Gen4 x4.

Advanced lab — a receiver format checker over a synthetic capture

Objective. Write the receive-side checks and run them over a capture to find every format violation. Prerequisites. The intermediate lab. Setup. The capture below (one TLP per line: direction, header DWs, actual payload DWs, digest present).

up   60000040 010000ff 00000002 00000000   payload=64 digest=0
up   60008040 010000ff 00000002 00000100   payload=64 digest=0
up   60000080 010000ff 00000002 00000200   payload=128 digest=0
up   20000080 010030ff 00000002 00000f80   payload=0 digest=0
down 4a000002 01000008 00090700            payload=1 digest=0
up   40000001 0100000f fee01000            payload=1 digest=0

Procedure. For each line check: payload equals Length (for TLPs with data); digest present iff TD = 1; Length ≤ MPS (256 B) for data TLPs; read Length ≤ MRRS (512 B); no 4 KiB crossing; BE rules; 3DW used for addresses below 4 GiB and 4DW only above. Print the first violation of each line and its error name.

Questions. Which lines are illegal and why? Which are legal but suspicious?

Expected reasoning. Apply checks in a fixed order and name the rule, not just "bad".

Solution

Line 1: legal. Line 2: TD = 1 (byte 2 = 0x80) but no digest → malformed. Line 3: Length 128 DW = 512 B > MPS 256 → malformed. Line 4: MRd64 of 512 B at 0x2_0000_0F80 crosses the 4 KiB boundary at 0x2_0000_1000 → malformed (it is legal for MRRS). Line 5: CplD Length 2 with 1 DW of payload → malformed (the failed trace above). Line 6: legal MSI-X write. Line 7: CQE write with Length 4 but Last DW BE = 0000b → malformed (Length > 1 requires non-zero Last DW BE). Line 8: MRd32 of 64 bytes at 0x2340_0100, a 3DW address below 4 GiB; legal in format, but suspicious: the SQ is at IOVA 0x1_2340_0100, so the high address DW was lost — the device dropped the upper 32 bits. Senior forensic lab — author versus detector

Objective. From logs alone, decide who authored a bad TLP and which part of it was bad. Prerequisites. All previous labs; Chapter 46 — AER.

Setup (synthetic evidence). A server has Root Port 00:01.1 → switch upstream port 02:00.0 → switch downstream port 03:01.0 → Lab SSD now at 04:00.0 (Requester ID 0x0400). ECRC generation is enabled on the SSD; ECRC checking is enabled on the Root Port only.

  • Root Port 00:01.1: Uncorrectable Error Status: ECRC Error; Header Log 60000040 040000ff 00000002 00340000.
  • Switch downstream port 03:01.0: Correctable Error Status: Bad TLP (receiver side), several occurrences in the hour before.
  • SSD 04:00.0: no errors.
  • Application: one checksum failure in a file read at the same time.

Procedure. Decode the header. Reason about each component's role (author, forwarder, detector). Decide whether the payload was corrupted inside the switch, on a link, or at the source.

Questions. (1) Why did the switch's Bad TLP errors not corrupt data? (2) Why did ECRC catch something LCRC did not? (3) Which component do you suspect, and what experiment confirms it?

Expected reasoning. LCRC protects each link and causes replay on mismatch, so link noise alone never delivers bad data. ECRC protects the whole path, including the inside of switches. An ECRC error with LCRC-clean delivery on the last link means corruption happened where only ECRC looks: inside a component that re-generated LCRC.

Solution

MWr64 from 0x0400 (the SSD), 256 bytes to 0x2_0034_0000: READ data. (1) Bad TLP at the switch downstream port is an LCRC failure on the SSD→switch link; the TLPs were replayed and delivered intact. (2) The Root Port received bytes that differ from those the SSD computed ECRC over, yet the last link's LCRC was clean: corruption happened after the switch checked incoming LCRC and before it generated outgoing LCRC — inside the switch — unless the SSD computed a wrong ECRC. (3) Suspect the switch, since the SSD's other writes pass; confirm with a two-sided capture comparing payloads, or by attaching the SSD directly to a Root Port. Confidence: medium-high, high after the capture.

Extension. Explain why enabling ECRC checking only at the Root Port is enough for this diagnosis, and what you would lose if ECRC were disabled entirely (the application checksum would be the only detector).

Debugging

Five recurring classes of format failure. Confidence is how sure the conclusion usually is once both checks agree.

Pattern 1 — Malformed TLP only for one transfer size

SymptomRoot Port logs Malformed TLP, link and controller reset, only with certain I/O sizes or buffer offsets.
Possible causesDMA splitter mishandles the last chunk (Last DW BE 0000b, Length off by one, 4 KiB crossing); MPS-sized chunk edge.
EvidenceHeader Log with the SSD's Requester ID; Length, BEs, address offset.
First checkDecode the Header Log; name the broken rule.
Second checkCompute the last chunk of the failing I/O and compare with the header.
Disambiguating experimentSweep sizes and alignments with fio; failures follow a precise arithmetic rule.
Likely conclusionDevice DMA splitter boundary bug.
ConfidenceHigh once the sweep reproduces it.

Pattern 2 — ECRC errors only behind a switch

SymptomECRC Error at the Root Port for devices behind one switch only.
Possible causesSwitch internal corruption or header modification; device ECRC generator bug for some TLP kinds.
EvidenceHeader Log TLP kinds; bytes on both sides of the switch.
First checkDo failing TLPs share a kind (completions, prefixed, poisoned)?
Second checkTwo-sided capture across the switch.
Disambiguating experimentAttach the device directly to a Root Port.
Likely conclusionSwitch datapath bug if bytes differ; device generator bug if they match.
ConfidenceMedium, high after the capture.

Pattern 3 — Failures right after enabling a feature on one end

SymptomAfter a BIOS or kernel change, Malformed TLP or UR storms at first I/O.
Possible causesA format-changing option (10-bit tags, End-End prefixes, AtomicOps, TPH) enabled without path-wide support.
EvidenceDevCap2/DevCtl2 on every port; T9/T8, TH, Fmt 100b or AtomicOp Type in the Header Log.
First checkDiff lspci -vvv before and after for every function on the path.
Second checkFind the new field in the logged header.
Disambiguating experimentRevert that single enable on a lab system.
Likely conclusionEnable applied without a path capability check.
ConfidenceHigh.

Pattern 4 — Malformed TLP with a legal header in the log

SymptomThe Header Log decodes to a legal TLP.
Possible causesViolation in an unlogged part (payload length, missing digest, prefix); tool byte order; the log belongs to an earlier error.
EvidenceFirst Error Pointer, Header and Prefix Logs, TD, tool convention.
First checkDecode a known-good header with the same tool.
Second checkCheck TD and the Prefix Log.
Disambiguating experimentCapture with a trigger on format violations.
Likely conclusionUnlogged-part violation or display convention.
ConfidenceMedium; usually needs a capture.

Pattern 5 — UR for a well-formed message or AtomicOp

SymptomUR logged for a received message, UR completions to AtomicOps, or AtomicOp Egress Blocked.
Possible causesUnsupported Vendor-Defined Type 0; AtomicOp size unsupported at the completer; no AtomicOp routing on a port.
EvidenceType, Message Code, Length in the Header Log; DevCap2 along the path.
First checkDecode Type/Message Code; identify the sender.
Second checkCapability bits for that feature and size on every port.
Disambiguating experimentRetry with a supported size or a Type 1 vendor message.
Likely conclusionFeature used beyond path support.
ConfidenceHigh.

Interview

Beginner

  1. What are the parts of a non-Flit TLP?

    Model answer

    Optional prefixes, a 3- or 4-DW header, an optional payload, and an optional 1-DW ECRC digest. The sequence number and LCRC are Data Link Layer wrappers, not TLP parts.

  2. How do you know a TLP has a payload?

    Model answer

    Fmt bit 30 (the "with data" bit): Fmt 010b or 011b. Length then gives the payload in DWs.

  3. Why are messages always 4DW?

    Model answer

    The message header reserves DW2–DW3 for an address, a target ID or message-specific content regardless of routing type, so the format is uniform.

  4. What does TD mean?

    Model answer

    TLP Digest present: a 1-DW ECRC follows the payload (or header). It must agree with what is actually present.

  5. Which header does the Lab SSD use to write to 0xFEE0_1000, and why?

    Model answer

    3DW (MWr32), because the address is below 4 GiB; the 32-bit format is required there.

Intermediate

  1. How do you recognise a TLP prefix in raw DWs?

    Model answer

    Its Fmt field is 100b, so byte 0 is 0x80–0x9F. One Type bit says Local or End-End. The header follows the last prefix.

  2. Contrast LCRC and ECRC.

    Model answer

    LCRC: per link, always present in non-Flit mode, failures replayed. ECRC: optional, end to end through switches, checked only where enabled, failures reported and never retried.

  3. What are variant bits and why do they exist?

    Model answer

    Header bits that may legally change in flight (commonly cited: EP and Type bit 0) are treated as fixed for the ECRC computation so legitimate modification does not create false ECRC errors.

  4. How large is the payload of a 128-bit CAS request and its completion?

    Model answer

    Request: two 128-bit operands = 32 bytes = Length 8. Completion: original 128-bit value = Length 4.

  5. Is Length 0 always 1024 DW?

    Model answer

    Only for TLPs whose Length is meaningful (with data, and reads). For messages without data Length is reserved and 0; for Cpl without data it is not a payload length.

Advanced

  1. A non-posted request is malformed. What does the requester see?

    Model answer

    Nothing immediately: the receiver discards it and reports Malformed TLP to the Root Complex through error messages; no completion is returned, so the requester eventually logs a Completion Timeout.

  2. Give three format violations a Header Log can show and three it cannot.

    Model answer

    Can: Length > MPS, illegal BEs, 4DW below 4 GiB, undefined Fmt/Type. Cannot: payload/Length mismatch, a missing digest, corrupted payload, prefix problems (separate log).

  3. How does a Vendor-Defined Type 0 message differ from Type 1 at a receiver that does not support it?

    Model answer

    Type 0 must be treated as an Unsupported Request; Type 1 must be silently discarded. That lets vendors send advisory messages safely with Type 1.

  4. What changes in Flit Mode, conceptually, for a decoder?

    Model answer

    A different header encoding (a Type byte instead of Fmt/Type), optional fields in Orthogonal Header Content, larger tags, flit-level CRC/FEC instead of per-TLP sequence numbers and LCRC; the same transaction model. Bit details come from the 6.x specification.

  5. Why do small TLPs pressure header credits rather than data credits?

    Model answer

    Each TLP consumes one header credit regardless of size, while data credits are 16-byte units. A stream of 4- or 16-byte writes uses many headers and few data units, so header buffers fill first.

Senior

  1. Design a format conformance suite for a new SSD controller.

    Model answer

    A matrix over address width (around 4 GiB), start offsets (within a DW, around RCB and 4 KiB), sizes around MPS/MRRS, every MPS/MRRS setting and enable (RO, NS, ECRC, 10-bit tags), with every emitted header checked automatically; plus exerciser-injected illegal inbound TLPs (bad Length, TD without digest, unsupported prefix, Vendor Type 0) to verify the right error and no hang.

  2. A customer reports corrupted data with no PCIe errors. ECRC is off. What do you propose?

    Model answer

    In a lab reproduction, enable ECRC generation at the device and checking at the Root Port to expose corruption inside switches and Root Complex datapaths, and NVMe protection information to separate media from transport.

  3. How do you decide who to blame for a Malformed TLP?

    Model answer

    The detector logged it; the author is named by the header (Requester ID for requests, Completer ID for completions). Confirm with a capture at the detector's ingress, then find the triggering transfer shape.

  4. A team wants End-End prefixes (PASID) with an NVMe device. What risks do you raise?

    Model answer

    Path-wide prefix support and count, port blocking settings, IOMMU PASID support, tooling that decodes prefixes, error evidence split across Header and Prefix Logs, and a fallback for paths without support.

  5. Teach a junior how to avoid misreading a header log.

    Model answer

    Establish link mode, the tool's byte order (decode a known doorbell) and whether prefixes exist; decode; then sanity-check against bus numbers, BARs and IOVAs. An implausible decode usually means a convention problem.

Quiz

  1. Byte 0 of a DW is 0x91. What is it?

    • An MRd with a 4DW header
    • A message routed by ID
    • A TLP prefix (End-End), with the header still to come
    • A completion with data
    Answer and reasoning

    0x91 = 100 1 0001b: Fmt 100b is a prefix; the next bit marks End-End. Keep reading for the header.

  2. Which message is silently discarded by a receiver that does not support it?

    • Vendor-Defined Type 0
    • Vendor-Defined Type 1
    • ERR_FATAL
    • PME_Turn_Off
    Answer and reasoning

    Type 1 vendor messages are discarded without error; Type 0 is handled as Unsupported Request.

  3. A 256-byte MWr64 with ECRC on a 128b/130b link occupies how many bytes of link time?

    • 256
    • 272
    • 282
    • 286
    Answer and reasoning

    16 header + 256 data + 4 ECRC + 6 Data Link Layer + 4 framing = 286.

  4. A switch sets EP on a TLP it forwards. Does the final receiver see an ECRC error?

    • No, because EP is a variant bit excluded from the ECRC computation
    • Yes, always
    • Only if TD = 0
    Answer and reasoning

    Variant bits are treated as fixed for ECRC so legitimate poisoning does not cause ECRC errors; the receiver reports Poisoned TLP Received instead.

  5. Which header family must have Length = 1 and TC = 0?

    • Memory read
    • Message
    • Configuration request
    • Completion
    Answer and reasoning

    Configuration requests always access one DW with TC0 and Last DW BE 0000b.

  6. A non-posted request arrives malformed. What happens next?

    • The receiver returns a UR completion
    • The receiver discards it and reports an error; the requester eventually times out
    • The receiver Naks it and it is replayed
    Answer and reasoning

    Malformed TLPs are discarded; no completion is produced. Nak/replay belongs to LCRC errors at the Data Link Layer.

  7. Why can a Malformed TLP log show a perfectly legal header?

    Model answer

    Because the violation may be in the payload length, the digest, or a prefix — none of which are in the Header Log — or because the tool printed the bytes in a different order.

  8. Why does the device's MSI-X write use a 3DW header while its data writes use 4DW?

    Model answer

    Header size follows the address: the MSI-X address is in the 0xFEE0_xxxx window below 4 GiB, while data IOVAs are above 4 GiB.

  9. What two capabilities must you check before trusting that a device's AtomicOps reach host memory?

    Model answer

    The completer's AtomicOp completer support for that operand size (Root Complex/Root Port) and AtomicOp routing support on every switch port in between; plus the requester's AtomicOp Requester Enable.

Teach-back

  1. To a child: explain why the station master writes down the engine's number when he turns a train away.

    Model explanation

    "So that later someone can find out which train was wrong and who sent it. He can't keep the whole train, so he writes down the engine — it says where it came from and what it was."

  2. To a junior engineer: walk through deciding the header size and Length for the Lab SSD's CQE write and its MSI-X write.

    Model explanation

    "The CQE goes to IOVA 0x1_2341_0040, above 4 GiB, so MWr64, 4DW, byte 0 0x60, 16 bytes → Length 4, both BEs 1111. The MSI-X goes to 0xFEE0_1000, below 4 GiB, so MWr32, 3DW, byte 0 0x40, one DW → Length 1, Last BE 0000, First BE 1111. Same device, two header sizes, because the address decides."

  3. To a senior engineer: argue why ECRC is worth enabling in validation even though LCRC exists.

    Model explanation

    "LCRC proves each hop's bytes arrived as sent by the previous hop. It says nothing about what happens inside switches, retimed paths that terminate the Data Link Layer, or Root Complex datapaths, where bytes are buffered and LCRC regenerated. ECRC is computed once by the source and checked at the destination, so it detects internal corruption that would otherwise surface only as application checksum failures. The cost is 4 bytes per TLP and some gate logic; the benefit is turning silent corruption into a logged, attributable error."
