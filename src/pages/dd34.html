Physical Region Pages look like arithmetic you do once and forget. Then a platform with a different page size, a list that starts eight bytes before a page end, or a controller that fetches its list one entry at a time turns that arithmetic into corruption or lost throughput. This module goes into how controllers walk PRPs, where host and controller can disagree, and how to prove which side was wrong.

Orientation

Chapter 36 (Physical Region Pages) taught the entry format, the memory page size from CC.MPS, the three meanings of PRP2, lists and chaining, the alignment rules, IOVAs and the Maximum Data Transfer Size (MDTS). Chapter 38 (PRP/SGL Debugging Lab) worked eight broken cases. This module goes beneath both: the controller's PRP engine (how and when it fetches lists, and what that costs a write), chaining in practice under the lab system's 128 KiB MDTS, page-size disagreement between host, driver and controller (CC.MPS and 64 KiB host pages), PRPs outside the I/O data path (queues, admin buffers, the Controller Memory Buffer), and a validation approach that finds disagreement before customers do.

Kid story

A treasure hunt in a book of identical pages. Your first clue card says "start on page 40, halfway down". Every other clue just says a page number, and you always start at the top of that page and read to the bottom. If there are only two pages of treasure, the second line of your card says the second page. If there are more, the second line says "look at the clue list on page 900, line 12".

The clue list on page 900 starts at line 12, so there are only a few lines left on that page. When the lines run out, the very last line says "the list continues on page 731". The treasure hunter never asks questions: she counts how many pages of treasure there should be, and uses that count to decide what every line means. If you counted pages of a different size — or if she reads the clue list one line per trip — the hunt goes wrong or takes forever.

Analogy boundary

What it represents. The card is the SQE's PRP1/PRP2; "halfway down" is PRP1's offset; book pages are memory pages of size 212+CC.MPS; the clue list is a PRP list; "starts at line 12" is a list pointer with an offset; the last-line redirection is a chain pointer; the hunter's page count is the controller's own computation from length, offset and page size.

What it hides. Every visit to the clue list is a PCIe Memory Read round trip; reading it one line at a time costs a round trip per page. The book's page numbers are I/O virtual addresses that an IOMMU translates, and the book has a second, different page size (the host's) that may not match the hunt's.

Where it becomes misleading. A real hunter could notice "this page has no treasure, it's a list". A controller cannot: a PRP entry carries no type, length or checksum, so a data page read as a list produces addresses from whatever bytes were there. Also, the hunter visits pages in order; a controller may move data for later pages first.

Mechanism

A 128 KiB Write (CID 0x0D00) whose PRP list pointer sits at 0x1_5000_0F80, 128 bytes before a page end — a legal layout that forces a chain even below MDTS.

  1. Driver maps the buffer. Who: driver and IOMMU. What: 32 controller pages get IOVAs (here scattered, 64 KiB apart from 0x2_00A0_0000). Where: IOMMU page tables. Evidence: none on the link; IOMMU fault logs only if wrong.
  2. Driver builds PRPs. Who: driver. What: PRP1 = 0x2_00A0_0000; N = 32 so PRP2 is a list pointer 0x1_5000_0F80; slots there S = (4096 − 0xF80)/8 = 16; since 31 entries remain, slots 0–14 hold pages 1–15 and slot 15 holds a chain pointer 0x1_5000_3000, where 16 more entries follow. Where: list memory. Evidence: SQE and list bytes in a capture.
  3. Submit. Who: driver. What: SQE in SQ1 slot 0x70, doorbell 0x71. Where: 0x1_2340_1C00, BAR0 + 0x1008. Evidence: doorbell Memory Write (MWr).
  4. Decode. Who: controller. What: L = 256 × 512 = 131,072; N = 32; PRP2 is a list. Where: controller. Evidence: the next request goes to PRP2.
  5. Fetch first list segment. Who: PRP engine. What: Memory Read (MRd) of 128 bytes at 0x1_5000_0F80 (16 slots). Where: link. Evidence: MRd Len = 32 DW.
  6. Recognise the chain. Who: PRP engine. What: slot 15 is in the last position of its page and more than one entry remains, so it is a chain pointer. Where: controller. Evidence: the next list MRd goes to 0x1_5000_3000.
  7. Fetch second segment. Who: PRP engine. What: MRd of 128 bytes (16 entries; no further chain needed). Evidence: a second, dependent list read.
  8. Pull data. Who: DMA engine. What: 8 MRds per page, 256 in total, addresses per the scatter table. Evidence: data MRds whose page addresses match list entries.
  9. Complete and release. Who: controller then driver. What: CQE; driver frees both list blocks and unmaps. Evidence: CQE MWr; later reuse of the list memory by other commands.

The central concept on the ladder: two computations that must agree

The hunter and the card-writer must count the same number of pages of the same size, or every line on the card means something different to each of them.

The driver and the controller each compute the page count N from length, PRP1 offset and page size; PRP2's role and the position of chain pointers follow from N. Any difference in inputs makes them disagree silently.

Inputs live in different places: length in NLB and the namespace format (Identify), page size in CC.MPS (set at enable) and in the driver's constants, offsets in the buffer addresses. The controller's engine has no way to ask the host which reading was meant.

NVM Express Base Specification, Revision 2.4 — Physical Region Page Entry and List; Controller Configuration (MPS); Controller Capabilities define the rules; NVMe over PCIe Transport Specification, Revision 1.4 makes PRPs the PCIe data pointer.

The controller's first request after the SQE reveals its N: a list MRd at PRP2 (N > 2), a data request at PRP2 (N = 2), or nothing at PRP2 (N = 1).

Predict the request at PRP2 from the SQE before reading further in the capture. A mismatch is the first abnormal event, usually long before any error appears.

When the prediction fails, ask which input differs: page size (CC.MPS versus driver), length (LBA size, 0's-based NLB, metadata), or offset (PRP1). Fix the side that deviates from the registers and Identify data.

The specification does not require a controller to detect every malformed PRP set, does not mark chain pointers, does not say when lists are fetched or how often, and does not require data to move in address order. Check in the specification: whether a chain pointer may carry an offset; the exact list of commands that prohibit a PRP1 offset; the PRP Offset Invalid value; which Controller Memory Buffer capability bits permit lists and data there.

Never assume the host page size is the controller page size; never derive length from a cached LBA size after a Format; never place a list at an offset without recomputing slots; never treat "no error" as "the controller agreed with you".

With page-aligned entries, the address of command byte k is table[(k + off) / PS] + (k + off) mod PS — a shift and a mask. A controller can therefore start NAND reads for any page and send data for whichever finishes first. The price is the list fetch: a dependent round trip before any page past the second can move, which a controller hides only if it fetches early enough.

Ordering, completion and errors

  • Dependency, not ordering rule. A data request for page k cannot precede the list read that reveals page k; chain reads are strictly sequential. PCIe ordering rules add nothing here; it is causality inside the controller.
  • Completion. List MRds are answered by Completions with Data (CplD) like any read; a list fetch that fails (Unsupported Request, Completer Abort, poisoned) should end the command with an error, typically Data Transfer Error.
  • Errors the controller may report. PRP Offset Invalid (if checked), Invalid Field in Command, Data Transfer Error. Errors it cannot report: a valid-looking address that is simply not the one the host meant.
  • After the CQE. The controller must not touch the list or data again; the host may free the list block immediately, so a controller that re-reads a list after completion reads someone else's list.

Chains below MDTS are rare with Linux, whose 256-byte list blocks always leave ≥ 32 slots, but they appear with other drivers, and firmware that only ever saw page-aligned lists may mishandle them. Analysis. With 8 KiB pages the controller computes N = ⌈16384 / 8192⌉ = 2, so PRP2 must be a page-aligned data pointer; 0x1_5000_0100 has offset 0x100 and is rejected. The host meant PRP2 as a list pointer for 4 pages. The status is the symptom; the missing list fetch is the first abnormal event, and it already tells you the controller's N differs from the host's. Fix: derive the PRP page size from CC.MPS in one place. prp_disagree.py in the Labs reproduces this case.

Beginner lab — PRP sets for awkward buffers

Safe lab Paper or the PRP tool.

Objective
Apply N and S without shortcuts.
Prerequisites
Chapter 36 formulas.
Setup
PS = 4 KiB unless stated. Cases: (a) 512 B at 0x2_0000_0F00; (b) 4 KiB at 0x2_0000_0FFC; (c) 12 KiB at 0x2_0000_0000; (d) 128 KiB, list pointer 0x1_5000_0F00; (e) 128 KiB, list pointer 0x1_5000_0FF8; (f) 16 KiB at 0x2_0000_0000 with PS = 8 KiB.
Procedure
For each: N, PRP2's role, list entries, chain position if any, list bytes fetched.
Observations
Which cases contradict intuition?
Questions
(1) Why does (a) need PRP2? (2) In (e), how many data entries fit before the chain? (3) In (f), what is PRP2?
Expected reasoning
Boundaries crossed, not size, decide N; slots depend on the list pointer's offset.
Solution

(a) 0xF00 + 512 = 0x1100 → N = 2; PRP2 = next page. (b) 0xFFC + 4096 → N = 2 (4 bytes in the first page, 4092 in the second); PRP2 = next page. (c) N = 3 → list of 2 entries, 16 bytes. (d) N = 32; S = (4096 − 0xF00)/8 = 32 ≥ 31 → no chain; one 248-byte list read. (e) S = 1: the only slot is the last slot of the page and 31 entries remain, so it is a chain pointer with zero data entries before it; the whole list (31 entries) is in the next page — legal but wasteful, and a classic firmware corner case. (f) N = 2 at 8 KiB; PRP2 = second 8 KiB page (8 KiB aligned). (2) Zero.

Extension. Recompute (d) and (e) for a 1 MiB transfer on a controller with MDTS = 8.

Intermediate lab — when host and controller disagree

Safe lab Python 3, standard library.

Objective
Build PRP sets with the host's assumptions, walk them with the controller's, and find the first byte whose destination differs.
Prerequisites
Beginner lab.
Setup
Save as prp_disagree.py.
#!/usr/bin/env python3
"""prp_disagree.py - build PRPs with the host's assumptions, walk them with the controller's.

Synthetic teaching model (standard library only). Memory is a dict {address: 8-byte value}
for PRP list pages. The host builder and the controller walker can be given different page
sizes or different transfer lengths, the two disagreements behind most PRP bugs. The walker
prints each (host address, bytes) chunk the controller would use and every rule it would
flag; a careful controller might report PRP Offset Invalid, a careless one would not.
"""
LIST_BASE = 0x1_5000_0000

def build(buf_pages, offset, length, ps, list_ptr=LIST_BASE, forget_offset=False):
    """Host side: buf_pages are the IOVAs of the buffer's pages (each ps-aligned)."""
    mem = {}
    n = -(-((0 if forget_offset else offset) + length) // ps)
    prp1 = buf_pages[0] + offset
    if n == 1:
        return prp1, 0, mem
    if n == 2:
        return prp1, buf_pages[1], mem
    slot, entries = list_ptr, buf_pages[1:n]
    while entries:
        room = (ps - slot % ps) // 8
        if len(entries) > room:                     # last slot becomes a chain pointer
            for e in entries[:room - 1]:
                mem[slot] = e; slot += 8
            nxt = (slot // ps + 1) * ps + 0x2000     # next list page, somewhere else
            mem[slot] = nxt; slot = nxt
            entries = entries[room - 1:]
        else:
            for e in entries:
                mem[slot] = e; slot += 8
            entries = []
    return prp1, list_ptr, mem

def walk(prp1, prp2, length, ps, mem):
    """Controller side: derive PRP2's role from length, PRP1 offset and ps."""
    notes, chunks = [], []
    if prp1 & 3:
        notes.append("PRP1 not dword aligned")
    first = min(length, ps - prp1 % ps)
    chunks.append((prp1, first))
    left = length - first
    n = -(-((prp1 % ps) + length) // ps)
    if n == 2:
        if prp2 % ps:
            notes.append(f"PRP2 0x{prp2:X} has offset 0x{prp2 % ps:X}: PRP Offset Invalid")
        chunks.append((prp2, left))
    elif n > 2:
        slot = prp2
        while left:
            room = (ps - slot % ps) // 8
            remaining = -(-left // ps)
            if remaining > room and slot % ps == ps - 8:
                slot = mem.get(slot, 0)              # chain pointer
                continue
            entry = mem.get(slot)
            if entry is None:
                notes.append(f"slot 0x{slot:X} read but never written by host (stale/garbage)")
                break
            if entry % ps:
                notes.append(f"list entry 0x{entry:X} has offset: PRP Offset Invalid")
            take = min(ps, left)
            chunks.append((entry, take))
            left -= take
            slot += 8
    return chunks, notes, n

def addr_at(chunks, off):
    for a, b in chunks:
        if off < b:
            return a + off
        off -= b
    return None

def first_mismatch(intended, actual):
    """First command byte offset at which host and controller use different addresses."""
    marks, off = set(), 0
    for chunks in (intended, actual):
        off = 0
        for _, b in chunks:
            marks.add(off); off += b
    for o in sorted(marks):
        a, b = addr_at(intended, o), addr_at(actual, o)
        if a != b:
            mine = "nothing" if b is None else f"0x{b:X}"
            return f"command byte {o} goes to {mine}, host meant 0x{a:X}"
    return None

def show(title, host_ps, ctrl_ps, offset, length, list_ptr=LIST_BASE, forget_offset=False):
    pages = [0x2_00A0_0000 + i * 0x1_0000 for i in range(40)]   # scattered, 64 KiB apart
    prp1, prp2, mem = build(pages, offset, length, host_ps, list_ptr, forget_offset)
    intended, left = [], length                    # what the host meant, page by page
    for i, p in enumerate(pages):
        start = p + (offset if i == 0 else 0)
        take = min(left, host_ps - (start % host_ps))
        intended.append((start, take)); left -= take
        if not left:
            break
    chunks, notes, n = walk(prp1, prp2, length, ctrl_ps, mem)
    print(f"--- {title}: controller sees {n} pages")
    print("    PRP1=0x%X PRP2=0x%X, %d list slots written" % (prp1, prp2, len(mem)))
    for a, b in chunks[:3]:
        print(f"    0x{a:X} +{b}")
    if len(chunks) > 3:
        print(f"    ... {len(chunks)} chunks in total")
    mism = first_mismatch(intended, chunks)
    if mism:
        notes.append("host and controller disagree: " + mism)
    for x in notes or ["no rule violations; host and controller agree"]:
        print("    ! " + x)

if __name__ == "__main__":
    show("agreeing 4 KiB pages, 128 KiB", 4096, 4096, 0x0, 128 * 1024)

Advanced lab — list-fetch strategy and write latency

Safe lab Python 3, standard library.

Objective
Quantify eager, lazy and windowed list fetching (Trace M34-S).
Prerequisites
Deep dive: WRITE pipeline lab.
Setup
Save as prp_fetch.py.
#!/usr/bin/env python3
"""prp_fetch.py - what does the PRP list fetch strategy cost a WRITE's data pull?

Synthetic teaching model (standard library only). Time 0 is when the SQE has been parsed.
Page 0's address is PRP1 (known at once). With more than two pages, the controller must
read page k's address from the PRP list before requesting page k's data. Strategies:
  eager   - one list read for all entries, issued at time 0
  lazy    - read entry k only when page k-1's data request is issued
  window  - read W entries at a time, prefetching the next window when a window starts
Data requests for a page take RTT_NS to answer; the link then needs PAGE_NS per 4 KiB.
"""
PAGE_NS = 585                       # 4 KiB at ~7 GB/s (illustrative)

def pull(pages, strategy, RTT_NS, w=2):
    issue = [0.0] * pages            # time each page's data request can be issued
    link_free = 0.0
    for k in range(pages):
        known = 0.0                  # time page k's address is known
        if k >= 1 and pages > 2:     # page k's address lives in the PRP list
            if strategy == "eager":
                known = RTT_NS
            elif strategy == "lazy":
                known = issue[k - 1] + RTT_NS
            else:                    # window: fetched when the previous window started
                win = (k - 1) // w
                known = RTT_NS if win == 0 else issue[1 + (win - 1) * w] + RTT_NS
        issue[k] = max(known, issue[k - 1] if k else 0.0)
        link_free = max(issue[k] + RTT_NS, link_free) + PAGE_NS
    return link_free

if __name__ == "__main__":
    for rtt in (800, 3000):
        print(f"host round trip {rtt} ns: time to pull all data (ns)")
        print(f"{'pages':>7} {'eager':>8} {'lazy':>8} {'window 2':>9}")
        for p in (2, 4, 8, 32):
            row = [pull(p, s, rtt) for s in ("eager", "lazy", "window")]
            print(f"{p:>7} {row[0]:>8.0f} {row[1]:>8.0f} {row[2]:>9.0f}")
Procedure
(1) Run it. (2) Find the smallest window w that matches eager at a 3,000 ns round trip. (3) Express the rule as an inequality.
Observations
Compare penalties at 800 and 3,000 ns.
Questions
(a) Why do 2-page transfers show no difference? (b) Why does a windowed fetch suffice at 800 ns but not at 3,000 ns with w = 2? (c) What should a validation bench vary to expose lazy fetching?
Expected reasoning
The window must cover the round trip: w × page time ≥ RTT.
Solution

Output at 800 ns: 32 pages take ≈19.7 µs eager, ≈26.2 µs lazy, ≈19.7 µs with w = 2. At 3,000 ns: ≈24.1, ≈96.6 and ≈51.6 µs. (a) N = 2 uses no list. (b) Two pages take ≈1.2 µs on the link, enough to hide 0.8 µs but not 3 µs. (2) w = 6 (6 × 585 ns ≈ 3.5 µs ≥ 3 µs) matches eager exactly (≈24.1 µs); w = 5 is within 0.5 µs. (3) w ≥ RTT / page time. (c) Host round-trip time: add memory load or IOMMU pressure; a bench with idle memory hides the defect.

Extension. Add a cap on outstanding data requests (as in the WRITE module) and see which limit binds first.

Senior forensic lab — corruption only on 64 KiB-page servers

Safe lab Evidence analysis.

Objective
Localise a platform-specific PRP bug from mixed evidence.
Prerequisites
This module.
Setup (evidence pack, synthetic)
  • A storage appliance's user-space NVMe driver passes all tests on x86-64. On Arm servers running a 64 KiB-page kernel, writes larger than 8 KiB sometimes fail with Data Transfer Error and IOMMU faults at addresses such as 0x6F6F_6F6F_6F6F_0000; smaller writes are fine.
  • CC.MPS = 0 (4 KiB) on both platforms.
  • The driver's PRP builder emits one entry per host page: on x86 that is one per 4 KiB; on Arm one per 64 KiB.
  • A capture on Arm for a 16 KiB write shows PRP1 = 0x2_0300_0000, PRP2 = 0x2_0301_0000 (no list), and the controller's next request is an MRd of 24 bytes at 0x2_0301_0000.
Procedure
Explain every observation, name the first abnormal event, root cause, owner, fix and test.
Observations
What N does the host compute, and what N does the controller compute?
Questions
(1) Why only above 8 KiB? (2) Where do the strange fault addresses come from? (3) Why does x86 hide the bug?
Expected reasoning
Controller page size, not host page size, defines PRP entries.
Solution

Host: the 16 KiB buffer lies in one 64 KiB host page, so the builder thinks one page (PRP1) — here even supplying a second host page as PRP2. Controller (4 KiB pages): N = 4, so PRP2 is a list pointer; it reads 3 × 8 = 24 bytes at 0x2_0301_0000 — the first abnormal event — and interprets the user data there (bytes 0x6F…) as page addresses, producing IOMMU faults at 0x6F6F…0000. Up to 8 KiB, N ≤ 2 and PRP2's role as a data page coincides with the host's if the buffer is contiguous, so it passes. On x86, host page = controller page, so the logic coincides. Root cause: PRP builder uses host page size. Owner: driver team. Fix: generate one entry per controller page (split each host page into 212+MPS-byte pieces). Test: run the full PRP matrix with the host page size as a parameter (4, 16, 64 KiB), with a byte-destination oracle. Confidence: high.

Extension. Could the driver instead set CC.MPS to match 64 KiB host pages? Discuss CAP.MPSMAX, IOMMU granularity and the effect on PRP list sizes.

Debugging

Six patterns, complementing the eight cases in Chapter 38.

IOMMU faults at data-looking addresses after a reformat

Symptom
After Format NVM changed namespace 1 to 4 KiB LBAs, a user-space tool's reads fault at addresses resembling file content.
Possible causes
Tool caches the old LBA size; controller length is 8× the host's; PRP2 reinterpreted.
Evidence
Identify Namespace current LBA format; tool's length computation; first request after the SQE.
First check
Recompute L from NLB and the current LBA size.
Second check
Does the controller read a list at PRP2 where the host put a data page?
Disambiguating experiment
Restart the tool (re-reading Identify) and repeat.
Likely conclusion
Stale length assumption.
Confidence
High.

PRP Offset Invalid on one platform only

Symptom
Trace M34-F behaviour on systems configured by one driver variant.
Possible causes
CC.MPS differs from the builder's page size; list pool alignment changed.
Evidence
CC register; builder constants; PRP2 values.
First check
Read CC.MPS.
Second check
Is the missing request the expected list fetch?
Disambiguating experiment
Run the same command with CC.MPS = 0 on a test system.
Likely conclusion
Page-size disagreement.
Confidence
High.

Large writes slow only on busy hosts

Symptom
128 KiB write throughput halves when the host runs memory-heavy jobs; reads unaffected.
Possible causes
Lazy or small-window list fetching; generic round-trip sensitivity of the pull (WRITE module).
Evidence
Size and timing of list MRds; outstanding data requests.
First check
Are list reads 8 bytes each, spread through the command?
Second check
Does a contiguous-IOVA SGL single Data Block (no list) remove the gap?
Disambiguating experiment
Compare 8 KiB (no list) and 128 KiB writes under the same load: only the latter degrades if the list is the cause.
Likely conclusion
Controller list-fetch strategy.
Confidence
Medium to high.

Tail corruption on MDTS-sized transfers from one driver

Symptom
The last pages of 128 KiB writes are wrong; only from a driver that packs lists densely.
Possible causes
List pointer near page end requires a chain; host omits it (Chapter 38 Case 3) or controller firmware mishandles a legal chain (Trace M34-N layout).
Evidence
List pointer offset, presence of a chain entry, the controller's second list read address.
First check
Compute S from the list pointer.
Second check
Is the slot at the page end a valid chain pointer in host memory?
Disambiguating experiment
Force list pointers to page-aligned addresses; if failures vanish while the host chain was correct, the firmware is at fault.
Likely conclusion
Either side; the capture decides.
Confidence
High after the experiment.

Admin command corrupts memory after a kernel change

Symptom
Get Log Page or Identify (4 KiB) corrupts an adjacent allocation on some boots.
Possible causes
Buffer allocated at an offset, so 4 KiB spans two pages, but PRP2 left zero.
Evidence
Buffer address offset; PRP2 in the admin SQE; IOMMU fault at address 0 or nearby.
First check
Is PRP1's offset non-zero?
Second check
Does the controller write the second part to PRP2 = 0?
Disambiguating experiment
Allocate the buffer page-aligned.
Likely conclusion
Admin path assumed "4 KiB fits one page".
Confidence
High.

Errors when lists are placed in the Controller Memory Buffer

Symptom
A driver feature that puts PRP lists in the CMB causes every large command to fail.
Possible causes
The CMB does not advertise support for lists (size register capability bit); wrong CMB address translation.
Evidence
CMB size and location registers; error status; absence of list MRds on the link (expected for CMB lists).
First check
Decode the CMB capability bits (confirm names and positions in the specification).
Second check
Is PRP2 inside the CMB's address range as seen by the controller?
Disambiguating experiment
Disable the feature; place lists in host memory.
Likely conclusion
Using an unadvertised CMB capability.
Confidence
Medium.

Interview

Beginner

  1. What decides whether PRP2 is used?

    Model answer

    The number of memory pages the transfer touches, from PRP1's offset, the length and the page size.

  2. Which PRP entries may have an offset?

    Model answer

    PRP1 (dword aligned) and a list pointer (quadword aligned); data entries in lists and PRP2-as-data must be page aligned.

  3. What sets the page size PRPs use?

    Model answer

    CC.MPS: 212+MPS bytes, within CAP.MPSMIN..MPSMAX.

  4. Is a PRP address a physical address?

    Model answer

    It is the bus address the device emits — an IOVA with an IOMMU in translated mode.

  5. Do admin commands use PRPs over PCIe?

    Model answer

    Yes; SGLs are optional for I/O only.

Intermediate

  1. A list pointer is at offset 0xF00. How many entries fit before a chain?

    Model answer

    32 slots; if more than 32 entries remain, 31 data entries and a chain pointer.

  2. Why can chains occur below MDTS?

    Model answer

    Slots depend on where the list starts; a list near a page end has few slots.

  3. How does a controller know an entry is a chain pointer?

    Model answer

    Only by position (last slot of a list page) and arithmetic (more than one entry remaining).

  4. Why does Linux use 256-byte list blocks?

    Model answer

    Most commands need short lists; a full page per command wastes memory. 256 bytes holds up to 32 entries, enough for 128 KiB.

  5. What changes with CC.MPS = 1?

    Model answer

    8 KiB pages: fewer entries, different PRP2 roles and alignment; the host builder must use the same size.

Advanced

  1. Describe three list-fetch strategies and their trace signatures.

    Model answer

    Eager: one list read sized 8×(N−1) (or per segment) early. Lazy: 8-byte reads spread through the command. Windowed: medium reads at regular intervals. Each shows different dependency gaps.

  2. How do you find host/controller disagreement in a trace before any error?

    Model answer

    Predict the first request at PRP2 from the SQE; compare with what the controller does.

  3. What happens if a non-checking controller receives Trace M34-F's command?

    Model answer

    It writes 8 KiB of read data to the list pool address, corrupting other commands' lists, and part of the data lands in unrelated memory after PRP1's 4 KiB.

  4. Why are PRPs friendly to out-of-order data movement?

    Model answer

    Fixed-size page entries allow direct computation of any byte's address.

  5. How do non-contiguous queues use PRPs?

    Model answer

    Create I/O SQ/CQ with PC clear passes a PRP list describing the queue pages; SQE fetch addresses jump between pages.

Senior

  1. Specify a PRP validation suite.

    Model answer

    Offsets (0, 4, 0x800, PS−4); lengths at, below and above page boundaries; N = 1, 2, 3, MDTS; list pointers at 0, 0x100, 0xF00, 0xF80, 0xFF8; page sizes from MPSMIN to MPSMAX; admin buffers with offsets; non-contiguous queues; CMB placement; IOMMU on/off; oracle checking every byte's destination; latency under host memory load.

  2. Which invariants would you put in a driver's PRP builder?

    Model answer

    Page size from CC.MPS only; length from current Identify data and NLB; slots from the list pointer's offset; chain when needed; lists and data mapped until CQE consumed; assertion that the controller's predicted N equals the builder's.

  3. When would you prefer SGLs to PRPs on PCIe?

    Model answer

    Large contiguous IOVA ranges (one descriptor, no list), byte-granular fragments, bit buckets, or controllers with slow list fetch — balanced against controller SGL performance and support.

  4. A vendor says lazy list fetching is "within spec". Response?

    Model answer

    True, but it is a performance defect against realistic host latency; provide the model and traces under load and request a prefetch window covering the round trip.

  5. How do you design for 64 KiB host pages?

    Model answer

    Either split host pages into controller pages or, if CAP allows, set CC.MPS to 64 KiB and accept larger PRP granularity; IOMMU granularity and buffer alignment must agree.

Quiz

  1. PRP2 is a list pointer at 0x1_5000_0FF0 for a 64 KiB transfer starting page-aligned (PS 4 KiB). How many data entries are in the first list page?

    • 1
    • 2
    • 15
    • 16
    Answer and reasoning

    S = 2 slots; 15 entries remain (> 2), so slot 0 is data and slot 1 is a chain pointer.

  2. CC = 0x0046_00E1. The memory page size is

    • 4 KiB
    • 8 KiB
    • 16 KiB
    • 64 KiB
    Answer and reasoning

    MPS field (bits 10:7) = 1 → 213 = 8 KiB.

  3. The first request after a 16 KiB Read's SQE is a data write to PRP2. What N did the controller compute?

    • 1
    • 2
    • 4
    • Cannot tell
    Answer and reasoning

    Using PRP2 as data means N = 2 — with 4 KiB pages that contradicts 16 KiB, revealing a page-size or length disagreement.

  4. Which is legal?

    • A data entry in a list at offset 0x200
    • PRP2 as a data page at offset 0x10
    • A list pointer at offset 0x108
    • PRP1 at offset 0x102
    Answer and reasoning

    List pointers need quadword alignment with offset allowed; PRP1 needs dword alignment (0x102 is not).

  5. A controller reads the PRP list 8 bytes at a time. The defect appears mostly when

    • Transfers are 4 KiB
    • The IOMMU is off
    • Reads dominate
    • Host round-trip time is high and writes are large
    Answer and reasoning

    Each entry costs a dependent round trip on the write pull.

  6. Linux's NVMe driver uses a 4 KiB controller page on a 64 KiB-page kernel. A 64 KiB host page in a request becomes

    • One PRP entry
    • Sixteen PRP entries
    • An SGL
    • An error
    Answer and reasoning

    Each host page is split into controller pages.

  7. Why is "first request at PRP2" the most useful prediction in PRP debugging?

    Model answer

    It reveals the controller's page count and PRP2 interpretation before any data moves.

  8. Give two causes of host/controller length disagreement.

    Model answer

    Using NLB as a count instead of 0's based; a stale LBA size after Format; forgetting interleaved metadata.

  9. Why is the reread in Trace M34-A not a violation?

    Model answer

    The buffer belongs to the controller until the CQE; it may read it any number of times.

Teach-back

  1. To a child: why the treasure hunter and card-writer must count the same pages.

    Model explanation

    The second line of the card means "next page" if there are two pages but "clue list" if there are more. If you count three pages and she counts two, she treats your clue list as treasure and goes to the wrong places.

  2. To a junior engineer: how to check a PRP set from a capture.

    Model explanation

    Decode PRP1, PRP2, NLB and the LBA size from the SQE; compute L and N with the CC.MPS page size; predict PRP2's role and the list read size (using S if it is a list); compare with the controller's next request; then check that every data request falls in a listed page. The first mismatch is your first abnormal event.

  3. To a senior engineer: why PRP bugs are agreement bugs, and how to prevent them.

    Model explanation

    The format carries no lengths, types or checks; correctness depends on two independent computations of N from inputs held in different places. Prevent disagreement by deriving page size only from CC.MPS, length only from current Identify data, slot counts from the list pointer, and by validating with a byte-destination oracle across page sizes, list offsets and host page sizes — plus performance tests under realistic host latency to catch weak list prefetch.
