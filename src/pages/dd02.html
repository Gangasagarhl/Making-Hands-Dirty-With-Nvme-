Every address an NVMe controller puts on the PCIe link — the queue it fetches from, the Physical Region Page (PRP) entries it follows, the buffer it writes — is a device-visible address. This module follows that address from the driver's mapping call, through the I/O memory-management unit (IOMMU) and its caches, to DRAM, and shows how Address Translation Services (ATS), the Page Request Interface (PRI) and Process Address Space IDs (PASIDs) change the picture.

Orientation

Chapter 20 taught why Direct Memory Access (DMA) exists and how a controller's Memory Read becomes a Completion with Data. Here we go one layer down: who chooses the number the device puts on the wire, who translates it, what is cached where, what happens on a miss, and what happens when a mapping disappears while the device is still using it. These questions decide whether an IOMMU fault in the kernel log is a driver bug, a device bug, a firmware bug or a harmless race.

You need Chapter 20 — DMA, the address-space picture from Chapter 1 and the CPU-side rules in Module 01. PRPs are in Chapter 36; TLP header fields in Chapter 11.

Next: Module 03 shows how topology and Access Control Services decide which DMA even reaches the IOMMU; Module 36 — DMA with NVMe applies all of this to PRP and SGL traffic; Module 52 — SR-IOV uses it for virtual functions.

Kid story

A town has a parcel company whose vans may deliver only to post-box numbers, never to street addresses. When your family wants a parcel, your parent goes to the post office and says: "Please let box 4017 mean our kitchen table, just for this week." The clerk writes that line in a big book. The van driver arrives at the post office gate with "box 4017"; the gatekeeper looks it up, sees "kitchen table, may deliver, may not take anything away", and lets the van through to the right house.

Some drivers keep a little notebook in the van with the boxes they visited recently, so they can go straight to the house. When your parent tells the post office "box 4017 is cancelled", the post office must phone every driver with a notebook and say "cross out 4017" — and wait until each says "done" — before it can give box 4017 to another family.

Analogy boundary

Represents. Post-box number = I/O virtual address (IOVA); the book = IOMMU page tables; the gatekeeper = IOMMU translation and permission check; the gatekeeper's memory of recent lookups = IOTLB; the driver's notebook = the device's Address Translation Cache under ATS; "cross out 4017" = ATS invalidation; "this week" = the lifetime of a DMA mapping.

Hides. Translation works on whole pages (4 KiB, 2 MiB, 1 GiB), not boxes; one van can carry many families' parcels under different PASIDs; a rejected van does not go home quietly — reads get an error completion and writes are dropped and logged; and the book lives in the same DRAM the parcels go to.

Misleads. The story implies the post office always exists. Many systems run with the IOMMU off or in passthrough (identity) mode, where box number equals street address. It also suggests drivers always use the gate; with ATS, a van carrying a translated address may be waved through with a lighter check, which is why ATS is a trust decision.

With ATS: the device holds translations

Why ATS exists: devices that touch many pages (accelerators, virtual functions in VMs) suffer IOTLB contention in a shared IOMMU; caching translations in the device spreads that load. The cost: each unmap must wait for every ATC holder to confirm invalidation, a slow or buggy device can stall the host, and the platform must trust translated requests. PRI extends ATS: if the translation completion says a page is not present, a PRI-capable device sends a Page Request, the host faults the page in, and answers with a PRG (Page Request Group) Response. PASID lets one function work in several address spaces, which shared virtual addressing needs.

Most NVMe SSDs on bare metal run without ATS: their DMA pattern (pinned buffers, sequential PRP walks) is IOTLB-friendly, and enabling ATS adds a trust and invalidation burden for little gain. Expect ATS mostly with virtualization and accelerators. Whether a given SSD implements ATS is Implementation-dependent; lspci -vvv shows the capability.

The ladder for "a translated DMA address"

The van may deliver only to post-box numbers; the gatekeeper turns the box into a house, and refuses boxes not in the book.

The driver maps a buffer and gives the device an IOVA. The IOMMU translates every device access and blocks anything unmapped.

Page tables in DRAM, an IOTLB in the IOMMU, an optional ATC in the device, a context table indexed by Requester ID, an invalidation queue.

PCIe defines the AT field, ATS translation requests and completions, invalidation messages, PRI and PASID. The IOMMU itself is defined by platform architecture specifications (VT-d, AMD IOMMU, Arm SMMU), not by PCIe or NVMe. NVMe only says PRPs and SGLs hold host memory addresses.

Untranslated MRd/MWr carry IOVAs (AT=00b); with ATS, translation requests (AT=01b), translated requests (AT=10b), and invalidation request/completion messages appear.

The analyzer shows IOVAs and Requester IDs, never physical addresses (unless ATS is in use). A blocked read shows an error completion; a blocked write shows nothing after it.

An IOMMU fault names the device, address and direction. Match it to the TLP, then to the PRP or queue that contained the address, then ask why that address was not mapped at that time.

Stated plainly: the 2-bit AT field distinguishes untranslated (00b), translation request (01b) and translated (10b) requests, with 11b reserved; PASID values are 20 bits wide; ATS invalidation uses an Invalidate Request message answered by Invalidate Completion messages.

Derived: because NVMe does not know about the IOMMU, the same controller firmware must work whether PRPs hold physical addresses or IOVAs; any fault is therefore a host mapping fact, not an NVMe protocol fact, unless the controller used an address the host never gave it.

Implementation-dependent: what completion status a blocked read receives (Unsupported Request or Completer Abort are common), whether blocked writes are reported per-write, IOTLB size, page-walk cost, fault-log capacity, whether ATS is supported or enabled by the OS.

Version-dependent: ATS was originally a separate PCI-SIG specification and was folded into the Base specification in a later revision; in Flit Mode (PCIe 6.0 and later) PASID and similar information travel in Orthogonal Header Content rather than in a TLP prefix — confirm encodings for your revision Uncertain on exact field placement.

Not said by PCIe or NVMe: how long a mapping must live, the IOVA allocation policy, the fault message format, or whether an IOMMU exists at all. Check platform IOMMU documentation and kernel source for those.

Never assume a fault address is a physical address, that an address in a trace is physical, or that "IOMMU on" means "strict".

Intermediate lab — Build a toy IOMMU

Safe lab Simulation.

Objective
Implement map, translate and unmap with a two-level table and an IOTLB, and watch faults and stale-IOTLB hazards.
Prerequisites
Mechanism section; Python 3.
Setup
Save as toy_iommu.py and run it.
#!/usr/bin/env python3
"""Toy IOMMU: 4 KiB pages, two-level table, small LRU IOTLB, strict or lazy unmap."""
from collections import OrderedDict

PAGE = 4096

class ToyIOMMU:
    def __init__(self, tlb_entries=4, strict=True):
        self.l1 = {}                       # L1 index -> {L2 index: (pa_page, perms)}
        self.tlb = OrderedDict()
        self.tlb_entries, self.strict = tlb_entries, strict
        self.walks = self.hits = 0
        self.pending_inval = []

    @staticmethod
    def split(iova):
        pfn = iova // PAGE
        return pfn >> 9, pfn & 0x1FF, iova % PAGE

    def map(self, iova, pa, perms):
        i1, i2, _ = self.split(iova)
        self.l1.setdefault(i1, {})[i2] = (pa // PAGE, perms)

    def unmap(self, iova):
        i1, i2, _ = self.split(iova)
        self.l1.get(i1, {}).pop(i2, None)
        if self.strict:
            self.tlb.pop(iova // PAGE, None)          # invalidate now
        else:
            self.pending_inval.append(iova // PAGE)   # flush later

    def flush(self):
        for pfn in self.pending_inval:
            self.tlb.pop(pfn, None)
        self.pending_inval.clear()

    def translate(self, iova, op):
        pfn = iova // PAGE
        if pfn in self.tlb:
            self.hits += 1
            self.tlb.move_to_end(pfn)
            entry = self.tlb[pfn]
        else:
            self.walks += 1
            i1, i2, _ = self.split(iova)
            entry = self.l1.get(i1, {}).get(i2)
            if entry is None:
                return f"FAULT  {op} iova={iova:#x} (not mapped)"
            self.tlb[pfn] = entry
            if len(self.tlb) > self.tlb_entries:
                self.tlb.popitem(last=False)
        pa_page, perms = entry
        if op not in perms:
            return f"FAULT  {op} iova={iova:#x} (permission {perms})"
        return f"OK     {op} iova={iova:#x} -> pa={pa_page * PAGE + iova % PAGE:#x}"

def demo(strict):
    print(f"--- strict={strict}")
    m = ToyIOMMU(strict=strict)
    m.map(0x2_0000_0000, 0x8_7A31_2000, "W")    # Read command buffer: device writes
    m.map(0x1_5000_0000, 0x8_1000_0000, "R")    # PRP list: device reads
    print(m.translate(0x1_5000_0008, "R"))
    print(m.translate(0x2_0000_0100, "W"))
    print(m.translate(0x2_0000_0100, "R"))      # wrong direction
    m.unmap(0x2_0000_0000)
    print(m.translate(0x2_0000_0200, "W"))      # late DMA after unmap
    m.flush()
    print(m.translate(0x2_0000_0300, "W"))
    print(f"walks={m.walks} hits={m.hits}")

demo(strict=True)
demo(strict=False)
Observations
Strict: the late write after unmap faults. Lazy: the late write still translates through the stale IOTLB entry until flush(), then faults.
Questions
(1) Why does the wrong-direction access fault? (2) What could the lazy-mode late write corrupt in a real system? (3) Why must the IOVA not be reused before the flush?
Expected reasoning
A Read command's buffer is mapped write-only for the device (DMA_FROM_DEVICE). The stale entry points at a page that may now belong to someone else. Reusing the IOVA before the flush could let a stale translation and a new mapping coexist.
Solution

Expected output: strict run shows OK, OK, FAULT (permission W), FAULT (not mapped), FAULT; lazy run shows OK, OK, FAULT (permission), OK (stale!), FAULT. (2) In a real system the physical page may already have been freed and reused, so the device writes into unrelated data. (3) That is exactly why Linux's deferred flush keeps IOVAs on a queue until the batched invalidation completes.

Extension: add an ATC on the "device" side and an invalidation that must be acknowledged before unmap() returns.

Advanced lab — IOTLB reach versus workload

Safe lab Simulation.

Objective
Measure hit rate for sequential and random buffer access with 4 KiB and 2 MiB mappings.
Prerequisites
The toy IOMMU above; the reach formula.
Setup
Add this function to toy_iommu.py (replacing the two demo calls).
import random

def hit_rate(page, pattern, entries=64, pool=1 << 30, ios=20000, io=4096):
    tlb, hits = OrderedDict(), 0
    rng = random.Random(7)
    for n in range(ios):
        off = (n * io) % pool if pattern == "seq" else rng.randrange(pool // io) * io
        key = off // page
        if key in tlb:
            hits += 1
            tlb.move_to_end(key)
        else:
            tlb[key] = True
            if len(tlb) > entries:
                tlb.popitem(last=False)
    return hits / ios

for page in (4096, 2 << 20):
    for pattern in ("seq", "rand"):
        print(f"page={page:>8} {pattern:4}: hit rate {hit_rate(page, pattern):.2f}")
Procedure
Run; then vary entries and pool.
Observations
Sequential 4 KiB I/O misses once per page (hit rate near 0 with 4 KiB pages because each I/O is a new page); random over 1 GiB with 4 KiB pages: almost always miss; 2 MiB pages: sequential near 1, random improves greatly because 64 × 2 MiB = 128 MiB of a 1 GiB pool is covered.
Questions
Why does even sequential I/O miss with 4 KiB pages? What does that tell you about the value of the IOTLB for streaming NVMe traffic?
Expected reasoning
Every 4 KiB I/O touches a new page exactly once; the IOTLB helps only when multiple TLPs hit the same page (16 MWr of 256 B per page) — the first misses, the next fifteen hit. Real hit rates are per TLP, not per I/O.
Solution

Per-I/O hit rates: 4 KiB seq ≈ 0.00, 4 KiB rand ≈ 0.00, 2 MiB seq ≈ 1.00, 2 MiB rand ≈ 0.12 (64 of the pool's 512 two-MiB pages are covered: 0.125). Counting per TLP instead, each 4 KiB page costs one walk then fifteen hits. Conclusion: huge-page-backed buffers (or ATS for devices that revisit pages) are the lever; for bare-metal NVMe the per-page walk is usually hidden behind media latency.

Extension: model per-TLP lookups (16 per 4 KiB) and plug the hit rate into the tavg formula.

Senior forensic lab — Faults that appear only during error recovery

Safe lab Paper exercise.

Objective
Decide whether recurring IOMMU write faults are a host lifecycle bug, a controller bug, or both.
Prerequisites
Trace 3; Chapter 48 — NVMe Reset.
Setup
Synthetic evidence: in a fleet, 0.1% of machines log IOMMU write faults from NVMe devices, always within 5 ms after a "resetting controller" message, always at IOVAs belonging to requests that timed out. A capture on one machine shows: CC.EN=0 written at t; host-side log shows buffers unmapped at t + 0.2 ms; CSTS read at t + 0.5 ms returns RDY=1; MWr to the timed-out request's IOVA at t + 1.1 ms; CSTS read at t + 4 ms returns RDY=0.
Procedure
Establish the first abnormal event; list hypotheses; state what each predicts; choose a fix.
Solution

Two facts are abnormal and their order matters. First: the host unmapped at t + 0.2 ms while RDY still read 1 — the controller had not completed shutdown of its DMA, so the host released buffers too early (host bug). Second: the controller wrote at t + 1.1 ms — permitted, because RDY=1 means it had not yet finished disabling. So the controller behaved within its contract; the host did not wait for RDY=0 (or a reset completion) before tearing down mappings. Fix: in the driver, unmap timed-out requests only after the controller is disabled (RDY=0) or after a reset that guarantees DMA has stopped; add a regression test that injects a slow-to-disable controller. Confidence high. The IOMMU's faults are the evidence that prevented corruption — on a system in identity mode this would have been silent memory corruption.

Extension: write the regression test plan and the oracle (no faults, no data corruption) using Validation Engineering.

Interview

Beginner

  1. What is an IOVA?

    Model answer

    The address a device uses for DMA when an IOMMU translates it into a physical address.

  2. Why do devices not use the CPU's virtual addresses?

    Model answer

    They are per-process and change; the device needs addresses fixed for the DMA's lifetime that the platform can translate or that are physical.

  3. What does an IOMMU protect against?

    Model answer

    Devices reaching memory not mapped for them: buggy drivers or firmware, malicious devices, other VMs' memory.

  4. What is a DMA mask?

    Model answer

    The number of address bits a device can generate; it bounds which addresses the DMA layer may hand it.

  5. Does a protocol analyzer show physical addresses for NVMe DMA?

    Model answer

    Only when no translation is in use or with ATS translated requests; otherwise it shows IOVAs.

Intermediate

  1. Coherent versus streaming mappings?

    Model answer

    Coherent: long-lived, shared by CPU and device without syncs (queues). Streaming: per-I/O, with a direction and explicit sync/unmap points (data buffers).

  2. What happens when the IOMMU blocks a DMA read? A write?

    Model answer

    Read: an error completion (commonly UR or CA, platform-dependent) and a fault record. Write: dropped and recorded.

  3. What is an IOMMU group and why does it matter for VFIO?

    Model answer

    The smallest set of functions the platform can isolate; VFIO assigns whole groups.

  4. Strict versus deferred invalidation?

    Model answer

    Strict invalidates the IOTLB at each unmap; deferred batches invalidations for speed, leaving a short window where stale translations may work.

  5. Why must the PRP-list page be mapped?

    Model answer

    The controller reads it by DMA like any other memory.

Advanced

  1. Describe an ATS translation and its invalidation.

    Model answer

    Device sends a translation request (AT=01b), receives the translated address and permissions, caches them in its ATC, issues translated requests (AT=10b). On unmap the host sends Invalidate Request; the device drops the entry and returns Invalidate Completion.

  2. What do PRI and PASID add?

    Model answer

    PRI lets the device ask the host to make pages present; PASID tags requests with an address-space ID so one function can serve several processes or guests.

  3. Why is ATS a trust decision?

    Model answer

    Translated requests may bypass full checks; a faulty device ATC could reach memory after it should have lost access.

  4. Compute IOTLB reach for 128 entries with 2 MiB pages.

    Model answer

    128 × 2 MiB = 256 MiB.

  5. How would Requester ID aliasing appear in fault logs?

    Model answer

    Faults naming a RID different from the device's BDF, typically the bridge's, on every access.

Senior

  1. Passthrough (identity) mode for performance: what would you ask?

    Model answer

    What threat model the system has (untrusted devices, hot-plug ports, Thunderbolt-like exposure), how much the measured gain is, and what evidence will exist after a DMA bug without faults.

  2. A fault names an IOVA. How do you get to the NVMe command?

    Model answer

    Correlate the IOVA with DMA-mapping traces or request logs, then with SQE PRP fields in a capture; use timestamps around the fault.

  3. Who is at fault when DMA follows a controller disable?

    Model answer

    Depends on timing: before CSTS.RDY = 0 the controller may still DMA, so early unmap is a host bug; after RDY = 0, continued DMA is a controller bug.

  4. How do you validate an ATS implementation?

    Model answer

    Invalidation latency under load, invalidation during outstanding DMA, ITag handling, behaviour with translations denied, interaction with function reset and power states.

  5. Why can identity mode turn a loud bug into a silent one?

    Model answer

    Without translation, a late or wild DMA lands in real memory with no fault record.

Quiz

  1. AT = 10b on a memory request means:

    • Untranslated
    • Translation request
    • Translated
    • Reserved
    Answer and reasoning

    10b marks a translated address obtained through ATS.

  2. Where are IOMMU page tables stored?

    • In the device
    • In host DRAM
    • In the Root Port's configuration space
    • In the NVMe controller registers
    Answer and reasoning

    Tables live in DRAM; the IOMMU caches them in its IOTLB.

  3. Which NVMe structure must be mapped in addition to data buffers for a large Read?

    • The PRP list page
    • The doorbell
    • The MSI-X table
    • CAP
    Answer and reasoning

    The controller fetches the PRP list by DMA.

  4. Why is a blocked write invisible in a trace?

    Model answer

    Writes are posted; there is no completion to carry an error. The IOMMU drops it and logs a fault on the host.

  5. What sysfs file tells you whether a group uses deferred invalidation?

    Model answer

    /sys/kernel/iommu_groups/<n>/type — "DMA-FQ" indicates the flush-queue (deferred) mode.

  6. Compute tavg for h = 0.9, thit = 20 ns, twalk = 400 ns.

    Model answer

    0.9 × 20 + 0.1 × 400 = 18 + 40 = 58 ns.

  7. Which specification defines IOMMU page-table formats?

    • NVMe Base
    • PCIe Base
    • NVMe over PCIe Transport
    • The platform's IOMMU architecture specification
    Answer and reasoning

    VT-d, AMD IOMMU or Arm SMMU documents; PCIe defines only ATS-related interfaces.

  8. In Trace 3, what single change prevents the fault?

    Model answer

    Waiting for CSTS.RDY = 0 (controller disabled) before unmapping the timed-out request's buffers.

  9. True or false: with ATS enabled, the IOMMU is no longer involved.

    • True
    • False
    Answer and reasoning

    False: the IOMMU still produces translations and invalidations; ATS only caches results in the device.

Teach-back

To a child

Model explanation

"The SSD's van is only allowed to use post-box numbers. A gatekeeper turns each number into a real house and stops the van if the number isn't in the book. When we're done, we cross the number out — and we must wait until it's really crossed out before giving it to someone else."

To a junior engineer

Model explanation

"Your driver never gives the SSD a pointer; it gives it a dma_addr_t from the DMA API. With the IOMMU on, that is an IOVA, translated per page and permission-checked. Map everything the device touches — queues, PRP lists, buffers — and do not unmap until the device can no longer access it. Faults in dmesg name the device, direction and IOVA."

To a senior engineer

Model explanation

"Translation is a platform service outside both NVMe and PCIe, except for ATS/PRI/PASID interfaces. The trade-offs are isolation versus invalidation cost and IOTLB reach; for NVMe the dangerous cases are lifecycle races during recovery and identity mode hiding them. Every fault is evidence of a mapping-time fact — correlate IOVA, RID and timing before blaming the device."
