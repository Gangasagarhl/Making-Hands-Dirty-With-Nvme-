How to turn a raw protocol capture into a defensible engineering finding automatically: ingestion, normalization, Transaction Layer Packet (TLP) decoding, NVM Express (NVMe) command correlation, timeline construction, anomaly detection, a rule engine, specification knowledge, root-cause hypotheses and an HTML report. Every stage is deterministic, and the page ends with an executable Python reference implementation that runs the whole pipeline on a synthetic CSV trace.

Why automate trace analysis

A single PCI Express (PCIe) capture of a few seconds of NVMe traffic can hold millions of TLPs. A human can read a few hundred carefully. Validation teams run thousands of tests overnight; every failing test produces a capture nobody has time to read. Automation is not about replacing the engineer's judgement: it is about getting the engineer to the first abnormal event quickly, with the evidence already gathered, and about applying the same checks to every capture so nothing is missed because someone was tired.

The danger is equal and opposite: an automated pipeline that silently mis-decodes one field, or that reports a conclusion without the evidence behind it, produces confident nonsense at scale. This page designs the pipeline so that every output is traceable to input events, every rule is cited, and every unknown is labelled.

Learning objectives

  • Describe each stage of a trace-analysis pipeline, its input, output and failure modes.
  • Design a normalized event schema and justify each field.
  • Explain the correlation identifiers that link PCIe events to NVMe commands: (Requester ID, Tag), queue slot, (SQ Identifier, Command Identifier), data address ranges, interrupt vectors.
  • Handle timestamps correctly: clock domains, resolution, direction, absence events and capture boundaries.
  • Write rule-based detectors and order findings to find the first abnormal event.
  • Explain where a large language model (LLM) may assist and why it must sit on top of deterministic decoding, never in place of it.
  • Run, read and extend the reference implementation.

The story

Imagine a huge pile of receipts from a whole day at a busy shop, all mixed up. A careful helper first sorts every receipt into the same shape — time, who paid, what was bought. Then they staple together receipts that belong to the same customer's visit, using the ticket number printed on each. Then they line every visit up in time order. Finally they look for the strange ones: a customer who came in but never paid, a payment with no customer, a receipt printed twice. They do not guess what happened — they point at the receipts.

An automated trace pipeline is like an airline's flight-data monitoring program. Every flight's recorder data is decoded by a fixed parameter map (deterministic), converted to engineering units (normalization), split into phases of flight (correlation and timeline), and checked against threshold rules ("descent rate above X below 1000 ft"). The output is a list of exceedances with the exact data behind each, reviewed by a safety analyst who decides what it means.

Flight recorders sample continuously at a fixed rate; a PCIe analyzer records discrete packets, and may miss some (one direction not probed, buffer overflow, filter settings). A flight has one aircraft; an NVMe trace interleaves thousands of commands whose events overlap in time, so correlation is much harder than phase splitting. And flight thresholds are set from operating limits; many "abnormal" conditions in PCIe/NVMe are not thresholds but broken relationships — a completion without a request, a CQE without a command — so the rules must reason about structure, not just values.

The pipeline's most valuable output is not the root cause. It is the timeline with the first abnormal event marked and the evidence attached. A senior engineer can usually finish the reasoning in minutes from there.

Trace ingestion

Ingestion reads whatever the capture tool produced and records provenance: what tool, which version, which settings, which link, which direction, which time range, and whether anything was lost. Analyzer native formats are proprietary; the usual practice is to export to CSV or text from the vendor software (see Teledyne LeCroy Analyzer Training and PEX / Capture File Training) and ingest the export.

The normalized event schema

Normalization converts every source — analyzer exports, simulator output, kernel logs — into one event model. A single schema is what makes correlation, rules and reports independent of the capture tool.

Design principles

  • Stable identifiers: every event has an event_id that never changes for a given input. Reports cite these.
  • Raw preserved: the original row or bytes are kept for audit.
  • Units explicit: time in nanoseconds (or picoseconds, but say so), lengths in bytes with the raw DW count preserved.
  • Layer explicit: physical, data link, transaction, NVMe, OS.
  • Derived vs observed: an event inferred by the pipeline (an absence, a deadline) is marked derived.
  • Correlation as data: links between events are fields, not program state.

No specification defines this event model. It is an engineering construction (Derived) built on the PCIe Base Specification (TLP semantics), the NVMe over PCIe Transport Specification (register and doorbell mapping) and the NVMe Base Specification (queue and command semantics).

Deterministic parsers

A deterministic parser is a pure function from bytes (or exported text) plus context to typed events: the same input always gives the same output, and every output field can be explained by pointing at input bits and a table in a specification. This is the foundation everything else stands on.

Rules for parsers

  1. Table-driven. Fmt/Type encodings, opcode tables and status tables are data, versioned by specification revision.
  2. Total. Every input produces an output; unknown values produce "unknown (raw=…)", never a guess.
  3. Context explicit. Anything not in the bits (BAR0, CAP.DSTRD, queue bases, LBA size, which queue is Admin) is a named input with a recorded source.
  4. Byte order explicit. TLP headers are drawn big-endian; NVMe structures in payloads are little-endian.
  5. Cross-checked. Decode a sample of events by hand and compare with the analyzer's own decode; differences are bugs in one of the two.

The TLP and SQE decoders from Project 3 and Project 4 are exactly such parsers.

Analyzer software can decode NVMe commands for you, but it must guess or be told where the queues are. If it assumed the wrong queue base, its "NVMe Read" may be your PRP list. Treat analyzer-level NVMe decode as an input to verify, not as ground truth.

Timestamps

  • One clock per capture. Analyzer timestamps are consistent within a capture. Kernel log timestamps are a different clock with different resolution; align them only by shared events, and state the uncertainty.
  • Direction and probe position. The analyzer sees a packet when it crosses the probe point, not when it was generated or consumed.
  • Resolution. State it. Two events with equal timestamps have unknown relative order unless the tool records sequence.
  • Absence events are dated at their deadline. "No completion" becomes observable only when the waiting time exceeds a threshold. Dating it at the request time would wrongly make it the first abnormal event.
  • Capture boundaries. An expectation whose deadline falls after the capture end is unknown, not violated.

Correlation links low-level events into higher-level transactions using identifiers they share.

The hardware creates the identifiers: the controller's DMA engine allocates tags; the driver chooses CIDs; the queue memory layout defines slots.

PCIe Base defines Requester ID and Tag uniqueness for outstanding non-posted requests and completion rules; NVMe Base defines CID uniqueness per SQ for outstanding commands; the PCIe Transport defines doorbell addresses.

On the wire, each identifier appears in a specific field: Tag in DW1 of a request and DW2 of a completion; CID inside the SQE payload and in CQE DW3.

In a capture, you follow tag 0x13 from the MRd at 3300 ns to the Cpl UR at 3950 ns, and the address 0x2_0000_1000 to the Write command whose PRP1 covers it.

When correlation breaks — a completion with no request, a CQE with no command — the break itself is a finding, and often the first abnormal event.

Anomaly detectors and the rule engine

Detectors look for four kinds of abnormality:

  • Structural — broken relationships: completion without request, CQE without command, data outside any command's buffer.
  • Value — fields with error meanings: completion status UR/CA, CQE status non-zero, poisoned TLP, doorbell value out of range.
  • Timing — absence by deadline, latency outliers, gaps.
  • Statistical — distribution shifts against a baseline (golden) capture.

Finding the first abnormal event

  1. Collect all findings, each with t_detect_ns: the time it became observable (the event time for observed anomalies, the deadline for absences).
  2. Discard or downgrade findings that depend on data lost to capture gaps.
  3. Sort by t_detect_ns. The earliest is the first abnormal event candidate.
  4. Check whether earlier "normal-looking" events are actually abnormal in context (for example, a request to an address no command owns). Rules may miss these; a human reviews the window before the candidate.

The first abnormal event is not necessarily the root cause; it is the earliest point where evidence departs from expectation. The cause may be earlier and invisible (a driver bug that mapped the wrong buffer). But the first abnormal event is where reasoning starts — see Senior Engineer Thinking.

Specification knowledge and hypotheses

Rules need knowledge: status code names, field layouts, which completion statuses exist, what the Phase Tag means. From findings to hypotheses

A hypothesis is a claim about cause that links findings. The pipeline produces hypotheses with four parts: the claim, the evidence (event IDs), a confidence level, and a falsification test — what observation would prove it wrong — plus a suggested next action. The confidence scale (CONFIRMED, HIGH, MEDIUM, LOW, UNKNOWN) is defined in AI + NVMe Protocol Analysis.

Causal-link rules are conservative: link two findings only when they share an identifier (the same command, the same tag, the same address range) and the cause precedes the effect. Time order alone is coincidence, not causation.

It is a teaching reference, not a production tool: one I/O queue, PRP1-only buffers, and a simplified CSV.

def ingest(text):

    for r in rows:
        r["idx"] = int(r["idx"]); r["time_ns"] = int(r["time_ns"])

def kv(s):
    return dict(p.split("=", 1) for p in s.split()) if s and "=" in s else {}

    """Return (layer, kind, attrs): a schema-shaped normalized event."""
    a, bar0 = r["addr"], sysc["bar0"]
    stride = 4 << sysc["dstrd"]
    if r["type"] == "MWr" and r["dir"] == "down" and a is not None and bar0 + 0x1000 <= a < bar0 + 0x2000:
        off = (a - bar0 - 0x1000) // stride
        qid, is_cq = off // 2, off % 2 == 1
        return ("nvme", "cq_head_doorbell" if is_cq else "sq_tail_doorbell",
                {"qid": qid, "value": int(r["data"], 16)})
    if r["type"] == "MWr" and r["dir"] == "up" and a is not None:
        lo, hi = sysc["msix_window"]
        if lo <= a <= hi:
            return ("pcie", "msix", kv(r["data"]))
        for qid, (sqb, sqn, cqb, cqn) in sysc["queues"].items():
            if cqb <= a < cqb + 16 * cqn:
                f = kv(r["data"])
                return ("nvme", "cqe_write", {"qid": qid, "slot": (a - cqb) // 16,
                        "cid": int(f["cid"], 16), "sqid": int(f["sqid"]), "sqhd": int(f["sqhd"]),
                        "sct": int(f["sct"]), "sc": int(f["sc"], 16), "p": int(f["p"])})
        return ("pcie", "dma_write", {"addr": a, "bytes": 4 * r["len"]})
    if r["type"] == "MRd" and r["dir"] == "up":
        for qid, (sqb, sqn, cqb, cqn) in sysc["queues"].items():
            if sqb <= a < sqb + 64 * sqn:
                return ("pcie", "sqe_fetch", {"qid": qid, "slot": (a - sqb) // 64,
                        "count": max(1, 4 * r["len"] // 64), "tag": r["tag"]})
        return ("pcie", "dma_read", {"addr": a, "bytes": 4 * r["len"], "tag": r["tag"]})
    if r["type"] in ("Cpl", "CplD"):
        return ("pcie", "completion", {"tag": r["tag"], "status": r["status"], "data": r["data"]})
    return ("pcie", "other", {})

def normalize(rows, sysc):
    ev = []
    for r in rows:
        layer, kind, attrs = classify(r, sysc)
        ev.append({"event_id": f"E{r['idx']:04d}", "t_ns": r["time_ns"], "dir": r["dir"],
                   "tlp": r["type"], "requester": r["req_id"], "layer": layer,
                   "kind": kind, "attrs": attrs, "corr": {}})
    return ev

# ---------------------------------------------------------------- 3. correlate
def correlate(ev, sysc):
    cmds = {}          # (sqid, cid) -> command record
    open_np = {}       # (requester, tag) -> outstanding non-posted event
    sq_tail = {q: 0 for q in sysc["queues"]}
    findings, notes = [], []
    for e in ev:
        k, a = e["kind"], e["attrs"]
        if k == "sq_tail_doorbell":
            q, n = a["qid"], a["value"]
            qsize = sysc["queues"][q][1]
            if n >= qsize:
                findings.append(("R6", e, f"SQ{q} tail doorbell {n} >= queue size {qsize}"))
            old = sq_tail[q]           # slots published by this write (handles wraparound)
            e["corr"]["new_slots"] = (list(range(old, n)) if n >= old
                                      else list(range(old, qsize)) + list(range(0, n)))
            sq_tail[q] = n
        elif k in ("sqe_fetch", "dma_read"):
            open_np[(e["requester"], a["tag"])] = e
        elif k == "completion":
            req = open_np.pop((e["requester"], a["tag"]), None)
            if req is None:
                findings.append(("R7", e, f"completion tag {a['tag']} matches no outstanding request"))
                continue
            e["corr"]["request"] = req["event_id"]
            if a["status"] != "SC":
                findings.append(("R2", e, f"completion status {a['status']} for {req['event_id']} "
                                          f"({req['kind']} addr=0x{req['attrs'].get('addr', 0):X})"))
            if req["kind"] == "sqe_fetch" and a["status"] == "SC":
                f = kv(a["data"])
                cid = int(f["cid"], 16); q = req["attrs"]["qid"]
                rec = {"sqid": q, "cid": cid, "opc": int(f["opc"], 16), "slot": req["attrs"]["slot"],
                       "prp1": int(f["prp1"], 16), "bytes": (int(f["nlb"]) + 1) * sysc["lba_bytes"],
                       "fetch": req["event_id"], "t_submit": None, "events": [req["event_id"], e["event_id"]],
                       "cqe": None, "t_done": None, "status": None}
                cmds[(q, cid)] = rec
                # earliest doorbell that published this slot = submit time
                for d in ev:
                    if d["kind"] == "sq_tail_doorbell" and rec["slot"] in d["corr"].get("new_slots", []):
                        rec["t_submit"] = d["t_ns"]; rec["events"].insert(0, d["event_id"]); break
                else:  # doorbell not in capture: fall back to fetch time and say so
                    rec["t_submit"] = req["t_ns"]; rec["submit_inferred"] = True
        elif k == "cqe_write":
            key = (a["sqid"], a["cid"])
            rec = cmds.get(key)
            if rec is None:
                findings.append(("R7", e, f"CQE for unknown command sqid={a['sqid']} cid=0x{a['cid']:04X}"))
                continue
            rec.update(cqe=e["event_id"], t_done=e["t_ns"], status=(a["sct"], a["sc"]))
            rec["events"].append(e["event_id"])
            if a["sct"] or a["sc"]:
                findings.append(("R3", e, f"CQE status SCT={a['sct']} SC=0x{a['sc']:02X} "
                                          f"for cid=0x{a['cid']:04X} (opc=0x{rec['opc']:02X})"))
        if k in ("dma_write", "dma_read"):
            for rec in cmds.values():
                if rec["prp1"] <= a["addr"] < rec["prp1"] + rec["bytes"]:
                    e["corr"]["cmd"] = (rec["sqid"], rec["cid"]); rec["events"].append(e["event_id"]); break
            else:
                if k == "dma_write":
                    findings.append(("R7", e, f"DMA write 0x{a['addr']:X} not attributable to a command"))
    # Absence findings: something expected did NOT happen. They are dated at the
    # moment the expectation expired (deadline), not at the request itself.
    end = ev[-1]["t_ns"]
    for (rq, tag), req in open_np.items():
        if end - req["t_ns"] > sysc["cpl_timeout_ns"]:
            findings.append(("R1", absence(req, req["t_ns"] + sysc["cpl_timeout_ns"]),
                             f"non-posted {req['tlp']} tag {tag} never completed"))
    fetched = {(r["sqid"], r["slot"]) for r in cmds.values()}
    for d in ev:
        if d["kind"] != "sq_tail_doorbell":
            continue
        for s in d["corr"]["new_slots"]:
            if (d["attrs"]["qid"], s) not in fetched:
                notes.append(f"SQ{d['attrs']['qid']} slot {s} published by {d['event_id']} "
                             f"{end - d['t_ns']} ns before capture end; fetch not seen -> UNKNOWN")
    for rec in cmds.values():
        if rec["cqe"] is None and end - rec["t_submit"] > sysc["cmd_timeout_ns"]:
            first = next(x for x in ev if x["event_id"] == rec["fetch"])
            findings.append(("R4", absence(first, rec["t_submit"] + sysc["cmd_timeout_ns"]),
                             f"cid=0x{rec['cid']:04X} (opc=0x{rec['opc']:02X}) no CQE within "
                             f"{sysc['cmd_timeout_ns']} ns of submission (anchor {first['event_id']})"))
    return cmds, findings, notes

def absence(anchor, deadline):
    """A pseudo-event standing for 'expected event missing by deadline'."""
    return {"event_id": anchor["event_id"], "t_ns": deadline, "absence": True,
            "attrs": anchor["attrs"], "corr": anchor["corr"]}

# ---------------------------------------------------------------- 4. detectors
def latency_outliers(cmds, factor=5.0):
    lat = {k: r["t_done"] - r["t_submit"] for k, r in cmds.items() if r["t_done"] and r["t_submit"] is not None}
    if len(lat) < 3:
        return []
    med = statistics.median(lat.values())
    return [("R8", k, v) for k, v in lat.items() if v > factor * med]

RULES = {
    "R1": ("PCIe", "Completion timeout candidate"),
    "R2": ("PCIe", "Unsuccessful completion (UR/CA/CRS)"),
    "R3": ("NVMe", "Command completed with error status"),
    "R4": ("NVMe", "Command never completed in capture"),
    "R6": ("NVMe", "Doorbell value out of range"),
    "R7": ("Correlation", "Event not attributable"),
    "R8": ("Performance", "Latency outlier"),
}

# ---------------------------------------------------------------- 5. hypotheses
def hypotheses(findings, cmds):
    hyp = []
    ur = [f for f in findings if f[0] == "R2"]
    err = [f for f in findings if f[0] == "R3"]
    for rid, e, msg in ur:
        req_id = e["corr"]["request"]
        for rid2, e2, msg2 in err:
            rec = cmds[(e2["attrs"]["sqid"], e2["attrs"]["cid"])]
            if req_id in rec["events"] and e["t_ns"] < e2["t_ns"]:
                hyp.append({"claim": f"The CQE error on cid=0x{rec['cid']:04X} is a consequence of the "
                                     f"UR completion to its data read {req_id}",
                            "evidence": [req_id, e["event_id"], e2["event_id"]],
                            "confidence": "HIGH",
                            "falsify": "Show the same CQE error without any unsuccessful completion, "
                                       "or show the UR read belongs to a different command",
                            "next": "Check IOMMU fault log / dmesg for the IOVA; check buffer mapping"})
    for rid, e, msg in findings:
        if rid == "R4":
            hyp.append({"claim": "Command was fetched but never completed; controller stall or lost CQE",
                        "evidence": [e["event_id"]], "confidence": "MEDIUM",
                        "falsify": "Extend the capture: a late CQE disproves 'lost'; a CQE in another CQ "
                                   "disproves 'stall'", "next": "Capture longer; read controller status/logs"})
    return hyp

# ---------------------------------------------------------------- 6. report
def report(ev, cmds, findings, notes, hyps):
    findings.sort(key=lambda f: f[1]["t_ns"])
    print("== Capture scope ==")
    print(f"events={len(ev)}  span={ev[0]['t_ns']}..{ev[-1]['t_ns']} ns  commands={len(cmds)}")
    print("\n== Commands ==")
    for (q, cid), r in sorted(cmds.items()):
        lat = (r["t_done"] - r["t_submit"]) if r["t_done"] else None
        st = "pending" if r["status"] is None else f"SCT={r['status'][0]} SC=0x{r['status'][1]:02X}"
        print(f"SQ{q} cid=0x{cid:04X} opc=0x{r['opc']:02X} slot={r['slot']} "
              f"latency={lat if lat is not None else '-'} ns  {st}  events={','.join(r['events'])}")
    print("\n== Findings (time order) ==")
    for rid, e, msg in findings:
        layer, name = RULES[rid]
        tag = " (deadline)" if e.get("absence") else ""
        print(f"{e['event_id']}{tag} t={e['t_ns']:>8} {rid} [{layer}] {name}: {msg}")
    if findings:
        f0 = findings[0]
        print(f"\nFIRST ABNORMAL EVENT: {f0[1]['event_id']} at t={f0[1]['t_ns']} ns ({RULES[f0[0]][1]})")
    for o in latency_outliers(cmds):
        print(f"R8 latency outlier: {o}")
    print("\n== Capture-boundary notes ==")
    for n in notes:
        print(n)
    print("\n== Hypotheses (evidence -> claim) ==")
    print(json.dumps(hyps, indent=2))

if __name__ == "__main__":
    rows = ingest(TRACE_CSV)
    events = normalize(rows, SYSTEM)
    cmds, findings, notes = correlate(events, SYSTEM)
    report(events, cmds, findings, notes, hypotheses(findings, cmds))

Walking through the result

  1. Correlation. The doorbell E0001 published slots 0–2. The three fetches E0002/E0004/E0006 map to slots 0, 1, 2 by address; their completions carry CIDs 0x40, 0x41, 0x42. Data TLPs E0010–E0011 fall in cid 0x40's buffer; the MRd E0008 falls in cid 0x41's buffer. The CQEs E0012 and E0015 match by (SQID, CID).
  2. Findings. R2 fires on E0009 (UR), R3 on E0015 (Data Transfer Error), R4 on cid 0x42 — but R4 is dated at its 2 ms deadline, not at the fetch.
  3. First abnormal event. E0009 at 3950 ns. If R4 had been dated at the fetch (2150 ns), the pipeline would have named the stuck Read as first, sending the investigation the wrong way.
  4. Hypotheses. The UR and the CQE error share a command (the MRd's address is inside cid 0x41's buffer) and are in causal order: HIGH. The stuck Read is MEDIUM: we know it was fetched and not completed within the window, but not why. Whether it is a consequence of the earlier error is a question, not a finding.
  5. Capture boundary. Slot 3 was published 0 ns before the end; the pipeline says UNKNOWN instead of "never fetched".

The interpretation "UR to a device DMA read usually means the host could not translate or route the address (for example an IOMMU fault)" is engineering reasoning, not a specification statement. The specification tells you what UR means at the Transaction Layer; the host-side reason must be confirmed from host evidence such as IOMMU fault logs.

Where an LLM fits

Everything above is deterministic. An LLM can add value at the top of the pipeline: explaining findings in prose, suggesting hypotheses a rule author did not anticipate, retrieving relevant specification passages from your notes, drafting the report. It must not parse packets, compute correlations, or invent fields. The rule is:

deterministic parser
normalized events
LLM reasoning (cites event IDs; checked by validators)

Failure patterns of analysis pipelines

These are failures of the tool, which look like failures of the device. Each has fooled real teams.

Phantom missing completions

Symptom: many R1 findings in one capture. Possible causes: one direction not captured; analyzer buffer overflow; filter dropped completions; tag field mis-parsed (10-bit tags). Evidence: capture metadata; whether any completions exist at all. First check: provenance — directions and gap markers. Second check: decode one request/completion pair by hand. Disambiguating experiment: recapture a short window with no filters. Likely conclusion: capture artifact. Confidence: HIGH once gaps are found.

Data attributed to the wrong command

Symptom: a command shows twice the expected data. Causes: buffer reuse across commands in the window; PRP list ignored. First check: overlapping ranges in the command table. Second check: times — was the earlier command already complete? Experiment: attribute only within each command's active interval. Confidence: MEDIUM until intervals are enforced.

Wrong first abnormal event

Symptom: the report's first event is an absence anchored at a request time. Cause: absence events not dated at deadline. Fix: date by deadline; show anchor separately. Confidence: CONFIRMED by inspection of the code.

Misnamed NVMe errors

Symptom: an SCT=1h error named as something unrelated to the command. Cause: status table lookup without opcode. Fix: key command-specific statuses by opcode and queue type.

Doorbells decoded with the wrong stride

Symptom: commands appear on the wrong queues; SQ2 shows CQ1 activity. Cause: CAP.DSTRD assumed 0. First check: read CAP from the register dump. Confidence: CONFIRMED once CAP is read.

Lab: extend the reference pipeline

Objective

Add two detectors and one correlation step to trace_forensics.py, then prove them with fault-injected traces.

Skills

Event modelling, correlation, rule writing, test design.

Safety

Safe lab Offline code and synthetic data only.

Hardware required

None.

Software required

Python 3.8 or later.

Input

The reference program and its embedded CSV.

Expected output

New findings fire on injected faults and stay silent on the original trace (except as noted).

Background

See the rule catalog above. The Phase Tag rules are in Queue Architecture; interrupt behaviour in MSI-X.

Step 1 — Phase tag detector

Track the expected phase per CQ (start at 1, invert when the CQE slot wraps to 0). Flag a CQE whose P differs. Inject a fault: change row 15's p=1 to p=0.

Step 2 — Interrupt correlation

Attribute each MSI-X write to the most recent unattributed CQE(s) on a CQ mapped to that vector; flag an MSI-X with no new CQE. Inject a fault: duplicate row 16 at 54000 ns.

Step 3 — CID reuse

Add a generation counter so that a CID reused after its CQE starts a new command record. Inject: add a fourth SQE fetch with cid 0x0040 after row 12.

Observation

Record which findings fire for each injected fault, and whether the first abnormal event changes.

Questions

  1. With the phase fault injected, which finding is first, and is it the right one to start from?
  2. Why could a duplicated MSI-X be harmless?
  3. What breaks in the original program if a CID is reused?

Challenge

Add a gap marker row type (type=GAP) and make every absence finding whose window spans a gap downgrade to UNKNOWN.

Hints

Phase: compute slot from the CQE address, keep expected[cq], and flip when you see slot 0 after a higher slot. MSI-X: keep a per-vector list of CQEs since the last MSI-X. CID reuse: key commands by (sqid, cid, gen) and bump gen when a fetch decodes a CID whose current record is completed.

Solution

1. The phase-mismatch finding on E0015 (53000 ns) is after E0009 (3950 ns), so E0009 remains first. The phase fault would also stop R3 from being meaningful — a host would not consume that CQE at all — so the narrative becomes: data read rejected, then the controller posts its error CQE with the wrong phase, so the host never sees the error and eventually times out. Both are real defect candidates; the UR is still where reasoning starts.

2. Interrupts may be spurious or shared without harm: the host's handler checks the CQ phase and finds nothing new. It matters only if it indicates an interrupt-to-queue mapping error or if it is excessive.

3. The original keys commands by (sqid, cid), so the second command with cid 0x40 overwrites the first record; its CQE would be attributed correctly only by luck, and the first command's events would be lost. The generation counter fixes it.

Challenge: store gap intervals during ingestion; in the absence pass, if [anchor_time, deadline] intersects a gap, emit the finding with confidence UNKNOWN and a note naming the gap row.

That every new rule needs a fault-injected test and a "silent on golden traces" test, and that the order of findings — not their count — is what drives the investigation.

Quiz

  1. Why is an absence finding dated at its deadline rather than at the request?

    • Because deadlines are defined by the specification
    • To make reports shorter
    • Because the abnormality becomes observable only when the deadline passes; dating it earlier distorts the first-abnormal-event ordering
    • Because the analyzer timestamps requests incorrectly
    Answer and reasoning

    At the request time nothing is wrong yet. The analysis threshold is an engineering choice, not a specification value.

  2. Which key matches a non-posted request to its completion?

    • Address
    • (Requester ID, Tag) among outstanding requests
    • (SQID, CID)
    • Timestamp proximity
    Answer and reasoning

    PCIe completions carry the Requester ID and Tag of the request. Tags are reused, so match only outstanding requests.

  3. An analyzer captured only the upstream direction. The pipeline reports "SQE fetch never completed" for every fetch. What is the right classification?

    • Device bug
    • Host bug
    • Link failure
    • Capture artifact: completions travel downstream and were not captured
    Answer and reasoning

    Completions to device reads travel host→device. Missing direction makes absences unknown.

  4. What context does the pipeline need that the TLPs do not carry?

    Model answer

    BAR0 address and CAP.DSTRD (to decode doorbells), queue base addresses and sizes, which queue is Admin, the command set per queue, LBA size per namespace, the MSI-X address/data per vector, MPS/MRRS, and the IOMMU setting — each with its source.

  5. Why must the schema keep raw input alongside decoded fields?

    Model answer

    For audit: a reviewer can check the decode, and when a decoder bug is found, past analyses can be re-run and corrected.

  6. Two findings: a UR at t=4 µs on a data read, and a CQE error at t=53 µs on some command. When may the pipeline link them causally?

    Model answer

    Only when they share an identifier — the UR's request address falls inside that command's data range (or the command's events include the request) — and the UR precedes the CQE. Time order alone is not enough.

  7. Name the four categories of anomaly detector.

    Model answer

    Structural (broken relationships), value (error fields), timing (absences, outliers), statistical (deviation from a baseline).

  8. What is a metamorphic test, applied to a trace pipeline?

    Model answer

    A test that transforms the input in a way that should not change the conclusions (for example, shifting all timestamps, or consistently renaming tags) and checks the output is equivalent.

  9. Why should an LLM not be used as the TLP parser?

    Model answer

    Parsing must be exact, reproducible and auditable; an LLM can mis-read bits, invent fields and give different answers to the same input. A deterministic parser has none of these failure modes and can be tested exhaustively.

Interview questions

  1. Intermediate: Design an event schema for NVMe-over-PCIe traces. What fields are mandatory and why?
    Model answer

    Stable event ID, source reference and raw text, timestamp with clock and unit, direction, layer, kind, observed vs derived flag, TLP fields, NVMe interpretation, correlation links. Mandatory: ID, source, time, layer, kind, observed — the minimum for citation, ordering and audit.

  2. Advanced: How do you avoid false "missing completion" reports?
    Model answer

    Record capture provenance (directions, filters, gaps); date absences at deadlines; ignore expectations whose deadlines fall beyond the capture end or inside a gap; handle split completions by Byte Count; test with golden traces.

  3. Advanced: How do you attribute DMA data to commands when buffers are reused?
    Model answer

    Use each command's active interval (from fetch to CQE), PRP/SGL ranges including fetched lists, and report ambiguity explicitly when two active commands overlap.

  4. Senior: Your team wants an LLM to "read the trace and tell us the root cause". What do you propose?
    Model answer

    A deterministic pipeline up to findings and hypotheses with evidence; the LLM operates only on normalized events and retrieved specification notes, must cite event IDs, and passes through a validator that rejects unsupported claims; confidence uses evidence-defined levels; humans approve root causes. Measure it on a labelled corpus before trusting it.

  5. Senior: How do you keep the pipeline correct across specification revisions?
    Model answer

    Version the knowledge tables by revision with citations; decode reserved bits as "reserved in revision X"; rerun the regression corpus on every table change and diff reports; review each revision's change list for decoder impact.
