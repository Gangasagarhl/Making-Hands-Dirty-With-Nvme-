Why this chapter exists

So far you have studied the pieces one at a time: Peripheral Component Interconnect Express (PCIe) packets in TLPs, base address registers (BARs) and memory-mapped I/O (MMIO) in BARs and MMIO, Direct Memory Access (DMA) in DMA, NVM Express (NVMe) queues in Queue Architecture, doorbells in Doorbells, the command layout in NVMe Command Structure, the READ command in READ and data pointers in Physical Region Pages. Each piece made sense on its own. What engineers struggle with in real work is the joins: the moment a block-layer request becomes a 64-byte command, the moment a doorbell write becomes a packet, the moment a completion entry becomes a woken-up thread.

Almost every serious NVMe-over-PCIe bug lives at one of those joins. A driver that writes the doorbell before the command is visible in memory. A controller that writes the completion before the data has landed. An interrupt that fires but nobody is listening. A data write that goes to an address the Input/Output Memory Management Unit (IOMMU) never mapped. You cannot debug any of these unless you can hold the entire path in your head and say, for each step, who acts, what changes, where it changes, what evidence it leaves, and what goes wrong.

That is what this chapter gives you. When you can narrate it from memory, with addresses, you have the mental model that a senior protocol engineer uses every day. Everything later in the course (interrupts, errors, resets, performance, trace analysis) is a variation on this one journey.

The story

Mia's class has a deal with a gigantic library across town. Mia wants page 40 of a book. Her teacher writes a request slip ("book shelf 1, page 40, please put the copy on table 3") and drops it into the class's request box, which sits on a shelf in the classroom. Then the teacher presses a buzzer that rings in the library.

The buzzer only says "there is new stuff in your box." So a library runner drives over on the fast road, picks up the slip, and drives back. The librarian looks up "shelf 1, page 40" in the big catalog card drawer to find where that page really lives in the basement stacks. A helper goes down, finds it, checks it for smudges, and copies it.

Now the clever bit: the runner does not hand the copy to the teacher. The runner walks into the classroom and lays the pages straight onto table 3, then drops a small "done!" card into the class's answer box, and flicks the classroom lights once. The teacher sees the lights flicker, reads the "done!" card, tells Mia her page is on table 3, and moves a marker to say "I have read that card."

A hospital ward orders a blood test. The doctor fills in a requisition form (the command) and places it in the ward's outbox tray (the submission queue in host memory). The doctor presses a call button at the nurses' station that lights up in the laboratory (the doorbell). A courier from the lab comes to the ward and collects the form (the controller's command fetch). The lab looks up where the sample is stored (the flash translation layer), runs the analysis (the NAND read), and a lab assistant writes the result directly into the patient's chart at the page the form specified (the DMA write into the host buffer). The assistant then drops a completion slip into the ward's results tray (the CQE in the completion queue) and sends a pager message to the doctor (MSI-X, Message Signaled Interrupts eXtended). The doctor reads the results tray, initials the slip so the lab knows the tray space can be reused (the completion queue head doorbell), and tells the patient.

  • Many forms at once. A real drive has thousands of commands in flight across many queues; the courier collects several forms per trip and finishes them in any order. The analogy suggests one at a time.
  • The courier does not walk. Every "trip" is a set of PCIe packets with addresses, lengths and tags, governed by credits and ordering rules. Nothing in the hospital models flow control or the fact that a write is fire-and-forget while a read needs an answer.
  • The chart pages are not where the doctor thinks. The address in the form is an I/O virtual address that the IOMMU translates; the lab could write to the wrong patient's chart if the translation is wrong, and the hospital story has no IOMMU.
  • The pager is a memory write. MSI-X is not a separate wire or radio: it is one more posted write packet to a special address, and it travels the same road, in order, behind the data and the completion slip.
  • The doctor never acknowledges the pager. There is no interrupt acknowledgement on the link. The only feedback to the lab is the head doorbell, and it may come much later and cover many slips at once.

Beginner explanation

A computer program cannot read from a solid-state drive (SSD) directly. It asks the operating system kernel, which asks a storage driver, which talks to the drive. The drive is a separate computer of its own (a controller with a processor, memory and flash chips) connected to the host by a PCIe link.

The driver and the drive do not talk by sending messages to each other in the usual sense. They share a few areas of the host's main memory, called submission queues and completion queues. To ask for something, the driver writes a 64-byte form, the command, into the next free slot of a submission queue. Then it writes a single number, the new tail position, into a special register on the drive called a doorbell.

Ringing the doorbell is the only thing the host sends to the drive for a normal read. Everything else, the drive does by itself, reaching into host memory: it reads the command out of the queue, finds the data in its flash, writes the data into the buffer the command pointed to, writes a 16-byte answer into the completion queue, and then sends an interrupt so the central processing unit (CPU) notices. The driver reads the answer, tells the drive "I consumed it" with another doorbell write, and hands the data back to the program.

So a read is not "host asks, drive answers" over a wire. It is "host writes a note in shared memory, pokes the drive, and the drive does all the moving." That idea, that the device masters the memory traffic, is the single most important thing to understand about NVMe over PCIe.

The central concept on the ladder

The central concept of this chapter is the end-to-end command transaction: one host request carried across three different contracts (Linux internal interfaces, the NVMe queue protocol, and PCIe transactions) and back.

The teacher drops a slip in the request box and rings a buzzer. The library's runner comes, takes the slip, finds the page, lays the copy right on the class table, drops a "done" card in the answer box and flicks the lights. The teacher reads the card and moves a marker.

The driver writes a 64-byte command into a submission queue in host memory and writes the new tail index to the controller's doorbell register. The controller fetches the command, reads the flash, copies data into the host buffer by DMA, writes a 16-byte completion into the completion queue and raises an MSI-X interrupt. The driver consumes the completion, updates the completion queue head doorbell and completes the request upward.

The CPU's store to 0xFE60_1008 is an uncached memory-mapped I/O write that the root complex turns into a packet. The controller's command-fetch engine and DMA engines are bus masters: they generate Memory Read and Memory Write requests to host memory, which the root complex forwards through the IOMMU to the memory controller. The flash translation layer (FTL), the NAND channel controller and the error-correction engine all live inside the SSD and never appear on the link.

The NVMe Base Specification defines queues, the SQE and CQE formats, doorbell semantics, the phase tag and status; the NVM Command Set Specification defines the READ command fields (SLBA, NLB, Force Unit Access (FUA), Limited Retry (LR)); the NVMe over PCIe Transport Specification defines how those map onto PCIe memory space, PRPs and MSI-X; the PCI Express Base Specification defines the TLPs, the ordering rules, MPS, MRRS and RCB.

On the wire: one posted MWr (doorbell), one non-posted MRd for the SQE and its CplD, sixteen posted MWr TLPs for data, one posted MWr for the CQE, one posted MWr for MSI-X, one posted MWr for the CQ head doorbell. Plus Data Link Layer Packets (DLLPs) for acknowledgement and flow-control credit updates in both directions.

An analyzer between root port and SSD shows 22 TLPs: a doorbell at t = 0, an SQE fetch and its completion about 1.35 µs later, then about 56 µs of silence while the NAND works, then a dense burst of 16 data writes, one CQE write and one MSI-X write within about 0.75 µs, then a CQ head doorbell about 2.5 µs after that.

To debug, find the first expected TLP that is missing or wrong. No SQE fetch after the doorbell: the controller did not see or did not accept the doorbell. A fetch completed with Unsupported Request: the IOMMU or address is wrong. Data but no CQE: controller stuck after transfer. CQE but no MSI-X: interrupt configuration. MSI-X but no head doorbell: the host did not process the completion.

The sixteen questions, applied to the end-to-end transaction

The end-to-end command transaction through the course's sixteen questions
QuestionAnswer for a 4 KiB NVMe READ over PCIe
What is it?The complete chain of software calls, memory updates and PCIe transactions that turns one read request into data in a host buffer and a completed system call.
Why was it created?NVMe was designed so that a command costs the host very little: one memory write of 64 bytes and one uncached register write, with no register reads on the submission path.
What problem does it solve?Earlier host interfaces needed several register accesses per command and serialized commands through few queues; with flash latencies of tens of microseconds and millions of I/O operations per second (IOPS), those costs dominated.
What existed before?Advanced Host Controller Interface (AHCI) for SATA: one command list of 32 slots per port, more uncached register traffic, a single interrupt path. See From SATA/SAS to NVMe.
Why is the current design better?Per-CPU queue pairs with no locking between CPUs, deep queues, device-mastered fetch and data movement, one MSI-X vector per queue, and a submission path with no MMIO reads.
Who creates it?The application starts it; the kernel builds the request; the NVMe driver builds the command and rings the doorbell; the controller carries out every transfer after that.
Who consumes it?The controller consumes the SQE; the host consumes the CQE and the data; the application consumes the return value and buffer.
Where does it live?In host memory (SQ, CQ, buffer), in controller registers (doorbells), in controller internal memory (command context, FTL map, data buffer) and as packets on the link.
What memory/registers are involved?SQ1 slot at 0x1_2340_0140, buffer at 0x2_0000_3000, CQ1 slot at 0x1_2341_00B0, doorbells at 0xFE60_1008 and 0xFE60_100C, MSI-X table entry 1 at BAR0 + 0x2010, the IOMMU page tables.
What happens before it?Controller initialization and queue creation (Admin Queue, I/O Queues); the file was opened; the buffer was allocated and aligned.
What happens after it?The application uses the data; the blk-mq tag and SQ slot are reused for later commands; the CQ head moves on.
What happens if it is wrong?Depending on the stage: data corruption, wrong data in the wrong buffer, IOMMU faults, controller fatal status, a timed-out command, or a reset of the controller.
What does the protocol analyzer show?The TLPs and DLLPs on one link, with timestamps. It does not show anything that happens inside the CPU, the IOMMU or the SSD.
What does Linux show?Block and NVMe tracepoints with CIDs, queue IDs, opcodes, LBAs and timestamps; interrupt counts; error and timeout messages; lspci link and capability state.
What would a validation engineer test?Every stage boundary: doorbell values at wrap, fetch of multiple SQEs, data integrity, phase-tag flips, interrupt delivery per vector, completion ordering with relaxed ordering on and off, behaviour under IOMMU faults and timeouts.
What would a senior engineer suspect when it fails?The join between stages: memory visibility before the doorbell, address translation, MSI-X masking and vector assignment, the phase tag at wrap, and controller firmware stalls between fetch and data.

The library story from The story supplies the analogies. Application request

Who acts / when
The application thread, then the system-call entry code. t = 0.00 µs.
What changes, where
The CPU switches from user to kernel mode; the kernel records the request (file, offset 0x40000, length 4096, user buffer address) in an I/O control block on the thread's kernel stack.
Analogy
Mia tells the teacher: "I need page 40 of the blue book, please put it on my table."
Technical
pread() enters vfs_read(), which calls the file system's read_iter method. Because the file was opened with O_DIRECT, the file system takes the direct-I/O path (on ext4 and XFS this is the iomap direct-I/O code, iomap_dio_rw()). Direct I/O requires the buffer address, file offset and length to be aligned to the device's logical block size or a value the file system reports (recent kernels expose it through statx() as the direct-I/O alignment). Our buffer is page aligned, so it qualifies. The kernel pins the user page so it cannot be swapped out or moved while the device writes into it.
Hardware
Only the CPU core is involved: a system-call instruction, a privilege change, kernel code running out of the caches. No device sees anything yet.
Protocol
None. This stage is pure software; no NVMe or PCIe contract is involved.
Trace appearance
Nothing on the PCIe link. On the host, syscalls:sys_enter_pread64 fires if enabled.
Evidence
strace or the syscall tracepoints show the call, file descriptor, length and offset.
What goes wrong
A misaligned buffer or offset makes direct I/O fail with EINVAL (or, on some file systems, silently fall back to buffered I/O); a buffered read would instead be served from the page cache or trigger read-ahead, so the drive sees a different, larger read. If you trace without knowing which path was taken, you will look for a 4 KiB READ that never exists.

Without O_DIRECT a 4 KiB read() on a cold file usually becomes one or more larger READ commands (read-ahead window), and a warm file produces no NVMe command at all. When someone says "my 4 KiB read is slow", the first question is: was it buffered? The trace you expect depends on the answer.

Block request

Who acts / when
The file system, then the block layer, multi-queue design (blk-mq). t ≈ 0.35 to 0.90 µs.
What changes, where
The file system looks up its extent map: file offset 0x40000 lives at device sector 0x0010_2000. A bio is allocated with one segment pointing at the pinned user page. blk-mq turns the bio into a struct request, allocates tag 0x2A from the tag set of hardware context 1 (the one mapped to the submitting CPU), and records the start time.
Analogy
The teacher looks up which shelf the blue book is on and fills in the catalog number on a request slip.
Technical
submit_bio() → blk_mq_submit_bio(). The request may be held briefly in a per-task plug list and merged with adjacent requests; with a single 4 KiB direct read there is nothing to merge. NVMe devices usually run with the none I/O scheduler, so the request is issued directly to the driver's queue_rq callback. The tag is important: it is the request's index in the hardware context, and the NVMe driver derives the CID from it.
Hardware
Still only CPU and memory. The extent lookup may hit the file system's in-memory cache; if the extent is not cached, the file system issues its own metadata READ first, which would appear as an earlier, separate NVMe command.
Protocol
None on the link. Inside Linux the contract is the block layer's request interface: a sector, a size in bytes, an operation (REQ_OP_READ) and flags.
Trace appearance
block:block_bio_queue, block:block_rq_insert (if a scheduler queues it) and block:block_rq_issue show device, sector 1056768 (0x102000), 8 sectors, operation R.
Evidence
filefrag -v on the file confirms the extent mapping; block tracepoints confirm the sector and size the drive will be asked for.
What goes wrong
Tag exhaustion (all tags in use) makes the submitter sleep: latency appears before the driver, and the NVMe trace is innocent. A wrong extent map (file-system corruption) produces a perfectly healthy NVMe READ of the wrong LBA, so the "bad data" bug is invisible at the protocol level.

Driver command creation

Who acts / when
The NVMe PCI driver's nvme_queue_rq() on the submitting CPU. t ≈ 0.90 to 1.10 µs.
What changes, where
The driver fills a 64-byte command structure in its per-request area (not yet in the queue): opcode, CID, NSID, data pointer, SLBA, NLB. It maps the data buffer for DMA, which makes the IOMMU create a translation from I/O virtual address (IOVA) 0x2_0000_3000 to the user page's physical address.
Analogy
The teacher writes the slip: "Shelf 1, starting page 40, 8 small pages, copy onto table 3, slip number 0x102A."
Technical
nvme_setup_cmd() → nvme_setup_rw() sets opcode 02h (Read), NSID 1, SLBA = request sector converted to LBAs (here the LBA size equals the 512-byte sector, so SLBA = 0x0010_2000), NLB = 8 − 1 = 7 because the field is zero-based. The CID comes from the blk-mq tag; recent kernels also store a small generation counter in the top bits of the CID (here generation 1, giving 0x102A) to catch completions for stale commands Implementation-dependent. nvme_map_data() maps the segment; for a single segment that fits in one or two memory pages the driver uses a fast path that sets PRP1 (and PRP2 if needed) directly without a PRP list.
Hardware
The IOMMU's page tables in host memory are updated (and, depending on the IOMMU mode, an I/O translation lookaside buffer (IOTLB) invalidation may be queued later at unmap time). The CPU writes these structures through its caches.
Protocol
The NVMe contract begins here: the driver must produce a command that follows the common command format of the NVMe Base Specification and the Read command format of the NVM Command Set Specification, with PRP entries that follow the PRP rules (PRP1 may have an offset; with the Controller Configuration field CC.MPS = 0 the memory page size is 4 KiB).
Trace appearance
nvme:nvme_setup_cmd shows qid=1, cmdid=4138 (0x102A), nsid=1, opcode Read, slba=1056768, len=7. Nothing on the link.
Evidence
The tracepoint is the best host-side record of exactly which command the driver built. It does not show PRP values or the queue slot.
What goes wrong
An off-by-one in NLB (the zero-based trap) reads one block too many or too few; a DMA-mapping failure (IOVA space exhausted) returns a resource error and the request is requeued; a wrong LBA conversion on a 4 KiB-LBA namespace reads eight times the intended range. All of these produce syntactically valid commands, so the controller will not complain.

Submission queue

Who acts / when
The driver, with the submission-queue lock for SQ1 held. t ≈ 1.10 to 1.20 µs.
What changes, where
The 64 bytes are copied into SQ1 slot 5 at IOVA 0x1_2340_0140. The driver's private copy of the tail moves from 5 to 6. The controller's view of the tail is still 5.
Analogy
The slip goes into the request box on the shelf, in the next free compartment.
Technical
nvme_sq_copy_cmd() does a memcpy into sq_cmds + (sq_tail << 6) and increments the tail, wrapping to 0 at 1024. The queue is a ring: the slot address is always base + index × 64. The ring is full when advancing the tail would make it equal to the head, so at most 1023 commands can be outstanding in SQ1; blk-mq's tag depth is set accordingly, which is why the Linux driver never has to read the SQ head before writing.
Hardware
Plain cached stores to ordinary DRAM-backed memory that was allocated as coherent DMA memory when the queue was created.
Protocol
NVMe Base Specification queue rules: the host is the producer of SQ entries and owns the tail; the controller is the consumer and owns the head. An entry belongs to the controller only after the tail doorbell moves past it.
Trace appearance
Nothing on the link. nvme:nvme_sq is a completion-time tracepoint, not this one; there is no standard tracepoint for the copy itself.
Evidence
Only indirect: the slot index is recovered later from the SQE fetch address on the analyzer: (0x1_2340_0140 − 0x1_2340_0000) / 64 = 5.
What goes wrong
Two CPUs writing the same SQ without a lock corrupt each other's entries; a driver that computes the slot with the wrong entry size (for example 16 instead of 64) writes commands into the middle of other entries; a queue full condition that the driver ignores overwrites a command the controller has not fetched yet.

Doorbell

Who acts / when
The driver: a memory barrier, then one 32-bit store. t ≈ 1.25 µs.
What changes, where
The CPU issues an uncached store of 0x0000_0006 to physical address 0xFE60_1008, the SQ1 Tail Doorbell register in BAR0. Once the controller receives it, its internal tail for SQ1 becomes 6, meaning slot 5 is now valid.
Analogy
The teacher presses the buzzer. The buzzer carries one number: "the box now has items up to compartment 6."
Technical
nvme_write_sq_db() uses writel(), which on Linux is ordered after the preceding normal memory stores, so the SQE is globally visible before the doorbell can arrive. The register address is 0x1000 + (2 × 1) × (4 << CAP.DSTRD) = 0x1008. The driver may skip the doorbell for a request when it knows more requests are coming in the same batch and ring once at the end (blk-mq's "last request" hint), so one doorbell can cover many commands. In virtualized setups the shadow doorbell feature (Doorbell Buffer Config) can replace most doorbell MMIO with memory updates Optional.
Hardware
The store goes from the core to the uncore and is routed by address decoding to the root port 00:01.1, whose memory window includes 0xFE60_0000. Because MMIO stores are posted, the CPU does not wait: writel() returns long before the device receives it.
Protocol
NVMe: the value written is the new tail index, not a count and not a byte offset. Writing a value that is not a valid slot index, or that would make the queue appear to hold more entries than its size minus one, is an invalid doorbell write; the controller may report an asynchronous error event for it Uncertain (confirm the exact Asynchronous Event information value for "invalid doorbell write value" in the NVMe Base Specification).
Trace appearance
The next stage: the store becomes one TLP.
Evidence
perf can see time spent in the submit path; nothing on the host records the store itself.
What goes wrong
Missing barrier on a weakly ordered CPU: the doorbell arrives before the SQE is visible, the controller fetches the old contents of slot 5 and executes garbage (classic intermittent corruption). Wrong register (SQ2 instead of SQ1): the command sits unfetched until it times out. Wrong value (byte offset 0x180 instead of index 6): the controller sees an invalid tail.

Who acts / when
The root port transmits; the SSD's PCIe core receives. On the link at t = 1.70 µs (analyzer t = 0 ns).
What changes, where
A posted Memory Write request TLP crosses the link downstream. The controller's PCIe core decodes the address against BAR0 (0xFE60_0000 to 0xFE60_3FFF), finds offset 0x1008, and hands the value to the NVMe register logic.
Analogy
The buzzer signal travels along the fast road to the library.
Technical
Because the address is below 4 GiB, the TLP uses a 3-DW header (32-bit address format) even though BAR0 is a 64-bit BAR. One data DW.

Controller command fetch

Who acts / when
The controller's front end (queue manager and arbiter). Analyzer t ≈ 0 to 700 ns.
What changes, where
The controller's SQ1 tail register becomes 6. The arbiter computes available entries = (tail − head) mod 1024 = 1 and schedules a fetch of slot 5 when SQ1 wins arbitration.
Analogy
The librarian hears the buzzer, checks the clipboard ("class 1 has one new slip") and sends a runner.
Technical
The NVMe Base Specification defines arbitration mechanisms (round robin is mandatory; weighted round robin with urgent priority class is optional). The controller may fetch several entries in one request when several are available; how many it fetches, and how soon after the doorbell, is up to the implementation.
Hardware
Doorbell writes typically land in a small register file; firmware or a hardware queue engine notices the change, often by an internal interrupt or polling loop. This internal reaction time is a large share of the 700 ns between doorbell and fetch.
Protocol
NVMe only: the controller may fetch entries from head up to (but not including) tail. It must not fetch beyond the tail.
Trace appearance
A gap on the link between the doorbell MWr and the next upstream MRd.
Evidence
Doorbell-to-fetch latency on the analyzer is a direct measure of controller front-end responsiveness.
What goes wrong
Controller firmware hung (no fetch ever; later the host times out and reads the Controller Status register, CSTS); controller in a reset or shutdown state (CC.EN = 0, CSTS.RDY = 0) so doorbells are ignored; queue not actually created (Create I/O SQ failed earlier but the driver ignored it).

DMA request

Who acts / when
The controller's DMA (command-fetch) engine. Analyzer t ≈ 690 ns.
What changes, where
The engine allocates a PCIe tag (0x21) from its pool of outstanding non-posted requests, reserves 64 bytes of receive buffer for the completion, and queues a read request for IOVA 0x1_2340_0140, length 64 bytes.
Analogy
The runner writes a numbered ticket (number 0x21) so that when the slip comes back, the library knows which errand it belongs to.
Technical
The engine must split any read into requests no larger than MRRS (512 B here) and must not cross a 4 KiB address boundary in one request. A 64-byte SQE fetch needs one request. For a larger transfer described by a PRP list (more than two memory pages), the controller would also issue reads for the PRP list itself at this point, and those reads would appear as additional MRd TLPs to 0x1_5000_xxxx; our 4 KiB read needs none. See Physical Region Pages.
Hardware
Endpoints must advertise infinite completion credits, so the device itself must make sure it has room for every completion it asks for; that is why the number of outstanding reads is limited by the device's internal buffer and its tag space, not by link credits.
Protocol
PCIe: the tag together with the Requester ID uniquely identifies the outstanding request. The tag is chosen by the device and has no relationship to the NVMe CID.
Trace appearance
Not yet visible; the request is about to become a TLP.
Evidence
None directly. Indirectly, the number of distinct tags in flight on the analyzer shows how deep the device's read pipeline is.
What goes wrong
Tag exhaustion inside the device stalls fetches (shows as long doorbell-to-fetch gaps under load); a firmware bug that reuses a tag before its completion arrives causes the device to match the wrong completion (a malformed or unexpected completion error).

Completion with Data

Who acts / when
The root complex transmits; the device receives and matches. Analyzer t = 1,350 ns.
What changes, where
A CplD with 64 bytes of payload goes downstream. The device matches it to tag 0x21, frees the tag, and places the SQE in its internal command buffer.
Analogy
The runner comes back with the slip, stamped "ticket 0x21," and hands it to the librarian.
Technical
Header fields: Completer ID (root complex), Completion Status = Successful Completion, Byte Count = 64 (bytes remaining including this completion), Requester ID 0x0100, Tag 0x21, Lower Address = 0x40 (the low seven bits of the request address 0x140). With RCB = 64 B and a 64-byte aligned request, a single completion is natural; a larger read could legally arrive as several completions split at RCB-aligned boundaries.
Hardware
Lands in the device's completion buffer (for which it advertised infinite credits). The device's command parser then reads CDW0 to find opcode 02h and CID 0x102A.
Protocol
PCIe completion matched by (Requester ID, Tag). It is the first time the NVMe command exists inside the controller.
Trace appearance
CplD Host→Dev Len=16 Tag=0x21 ReqID=0x0100 BC=64 LowAddr=0x40 Status=SC, payload starting 02 00 2A 10 01 00 00 00 (bytes of CDW0 and CDW1, little-endian).
Evidence
Decode the payload with the SQE layout: opcode, CID, NSID, PRP1, SLBA and NLB are all visible. This is the anchor for every later correlation step (see Command-to-TLP Correlation).
What goes wrong
Completion status Unsupported Request (UR) or Completer Abort (CA): the device cannot run the command; NVMe gives it no way to post a CQE for a command it could not read, so the result is usually a host timeout, and some controllers set Controller Fatal Status Implementation-dependent. Poisoned completion (EP bit set): memory error on the host. Completion never arrives: Completion Timeout in the device, logged through Advanced Error Reporting (AER) if enabled.

Flash operation

Who acts / when
Controller firmware, the flash translation layer (FTL), the NAND channel controller, the NAND die, and the error-correction engine. Analyzer t ≈ 1.4 µs to 57.6 µs (host t ≈ 3.05 to 59.3 µs).
What changes, where
Entirely inside the SSD: the command is validated, the LBA range is translated to physical flash locations, a read is issued to a die, the die senses the cells into its page register, the data is clocked out over the channel, decoded and placed in the controller's data buffer.
Analogy
The librarian looks up "shelf 1, page 40" in the card catalog, which says "basement, aisle 3, rack 1, box 418, sheet 87." A helper goes down, pulls the sheet, checks it for smudges and fixes small ones, and brings a clean copy upstairs.
Technical
Validation: opcode supported, NSID 1 active, SLBA + NLB within the namespace size (0x7470_6DB0 blocks), PRP1 offset valid for the memory page size. Translation: with a typical 4 KiB mapping unit, LBAs 0x0010_2000 to 0x0010_2007 are one mapping unit, logical page 0x2_0400; the map entry gives (for example) channel 3, die 1, plane 0, block 0x1A2, page 0x57, 4 KiB slot 2 of a 16 KiB physical page Implementation-dependent. The die performs the array read (tR, about 50 µs for this synthetic triple-level-cell (TLC) part), the channel transfers the 4 KiB plus its error-correction parity, and the error-correcting code (ECC) engine, here a low-density parity-check (LDPC) decoder, corrects bit errors.
Hardware
The mapping table usually lives in the SSD's DRAM. A DRAM-less SSD may keep part of it in the Host Memory Buffer (HMB), host DRAM lent to the controller; a map miss would then appear on the link as extra device MRd TLPs to the HMB region in the middle of this "silent" period, which is a useful trace signature. If decoding fails, the controller retries with shifted read voltages (read retry) or stronger soft-decision decoding, which can multiply the latency.
Protocol
None of this is defined by NVMe or PCIe; the specifications define only the command's observable result. That is why the timing of this stage is the least predictable part of the trace.
Trace appearance
About 56 µs of no TLP traffic for this command on the link, possibly with periodic DLLPs (UpdateFC) and, if Active State Power Management (ASPM) L0s or L1 were enabled, low-power entry and exit. On a busy drive, other commands' traffic fills the gap.
Evidence
Indirect only: the gap between SQE fetch completion and the first data write. Comparing that gap across many reads gives a latency distribution; long-tail outliers suggest read retry, die contention or garbage collection. Self-Monitoring, Analysis and Reporting Technology (SMART) / Health and vendor logs (SMART / Health) can confirm media trouble.
What goes wrong
Uncorrectable read: the controller completes the command with an Unrecovered Read Error status (Media and Data Integrity Errors status type) and transfers no valid data; LBA out of range: LBA Out of Range status without touching flash; namespace not ready; die busy with a program or erase, adding hundreds of microseconds (program/erase suspend support is implementation-dependent).

Data transfer

Who acts / when
The controller's data DMA engine transmits; the root complex and IOMMU receive and write memory. Analyzer t = 57,600 to 58,200 ns.
What changes, where
4096 bytes move from the SSD's buffer into host memory at IOVA 0x2_0000_3000 to 0x2_0000_3FFF, which the IOMMU translates to the pinned user page.
Analogy
The runner walks into the classroom and lays the copy onto table 3, one sheet at a time, without asking the teacher.
Technical
For a READ, data flows from device to host as Memory Write requests issued by the device, not as completions. Each write may carry at most MPS = 256 bytes and must not cross a 4 KiB boundary, so 4096 bytes become 16 TLPs of 64 DW each, at 0x2_0000_3000, 0x2_0000_3100, … 0x2_0000_3F00. A device is allowed to use smaller payloads; 16 is the minimum count, not a requirement Derived.

Hardware
Each TLP needs one posted header credit and 16 posted data credits (one data credit is 16 bytes) at the root port's receiver. On Intel platforms with Data Direct I/O, inbound writes may be allocated directly into the last-level cache Implementation-dependent. The IOMMU translates each TLP's address (one IOTLB entry covers the whole 4 KiB page).
Protocol
Posted writes: no completions. PCIe ordering keeps posted writes in order unless the Relaxed Ordering attribute is set; if the device sets Relaxed Ordering on data writes (and the host enabled it in Device Control), they may be reordered relative to each other, but a later write without Relaxed Ordering (the CQE) still may not pass them. See PCIe Ordering.
Trace appearance
Sixteen MWr(64) Dev→Host Len=64 TLPs, addresses stepping by 0x100, about 40 ns apart, Requester ID 0x0100. Posted TLPs carry a tag field, but its value means nothing for matching.
Evidence
Address range equals PRP1 through PRP1 + 4095: proof that the data went where the command said. The payload of the TLPs is the data itself, which you can compare with known file content.
What goes wrong
Data written outside the PRP range (a controller PRP-walking bug) corrupts other memory or, with an IOMMU, causes a DMA write fault and the write is dropped; payload larger than MPS is a Malformed TLP and the root port reports it through AER; poisoned data (EP set) when the SSD had an internal memory error.

Completion entry

Who acts / when
The controller's completion engine. Analyzer t = 58,280 ns.
What changes, where
A 16-byte CQE is written into CQ1 slot 0x0B at IOVA 0x1_2341_00B0. The controller's CQ1 tail moves to 0x0C.
Analogy
The runner drops a "done, slip 0x102A, everything fine" card into the class's answer box, in the next compartment, with today's coloured ink.
Technical
CQE contents: DW0 = 0 and DW1 = 0 (command-specific, unused by Read), DW2 = 0x0001_0006 (SQ Identifier 1 in bits 31:16, SQ Head Pointer 6 in bits 15:0), DW3 = 0x0001_102A (Status Field 0 in bits 31:17, Phase Tag 1 in bit 16, CID 0x102A in bits 15:0). The phase tag is the "coloured ink": the controller inverts it each time it wraps the CQ, so the host can tell a new entry from an old one without a separate valid bit.

One more posted write from the same DMA engine. Controllers usually serialize "data writes, then CQE" in the same internal queue so that link ordering does the rest.
Protocol
NVMe requires that the data for a command be transferred before its completion is posted, from the host's point of view; on PCIe this relies on posted-write ordering, so the CQE write must not carry the Relaxed Ordering attribute Derived from the PCIe ordering rules.

What goes wrong
Wrong phase bit (controller bug, or host and controller disagree after a wrap): the host never sees the entry and the command times out although the CQE is in memory. Wrong CID: Linux reports an invalid command identifier completed on the queue and the real request later times out. CQE written before the data (ordering violation): the application reads stale data, a silent corruption that only a trace can prove.

MSI-X

Who acts / when
The controller's interrupt logic, then the root complex's interrupt path (interrupt remapping, the local Advanced Programmable Interrupt Controller or APIC). Analyzer t = 58,340 ns; handler entry at host t ≈ 61.6 µs.
What changes, where
The controller notes that CQ1 has a new entry, CQ1 was created with interrupts enabled on vector 1, and vector 1 is not masked. It reads MSI-X table entry 1 (Message Address 0xFEE0_1000, Message Data 0x0000_0041, both programmed by the operating system) and sends a write with those values. The root complex recognizes the address window as an interrupt message rather than memory and delivers interrupt vector 0x41 to the CPU core the address targets.
Analogy
The runner flicks the classroom lights once.
Technical
The interrupt vector for a completion queue is chosen when the queue is created (the Interrupt Vector field of Create I/O Completion Queue). If the vector is masked (per-vector Mask bit in the table, or Function Mask in the MSI-X capability), the controller sets the vector's bit in the Pending Bit Array (PBA) at BAR0 + 0x3000 instead and sends the message when it is unmasked. Interrupt coalescing (an NVMe feature, off by default in Linux) can delay the message until several completions or a timer expire. See MSI-X.
Hardware
With IOMMU interrupt remapping enabled, the address and data are in a "remappable" format and are looked up in the interrupt remapping table; the values above are the classic compatibility format and are illustrative.
Protocol
On the link, MSI-X is simply a posted Memory Write of one DW. Because it is posted and from the same requester, it cannot pass the earlier data and CQE writes (unless they used Relaxed Ordering, which the CQE did not), so by the time the CPU takes the interrupt, the CQE and data are visible.
Trace appearance
MWr(32) Dev→Host Addr=0xFEE01000 Len=1 Data=0x00000041, 60 ns after the CQE write.
Evidence
On the host: the per-CPU counter for the queue's interrupt line in /proc/interrupts increments; irq:irq_handler_entry fires with the NVMe queue's handler name.
What goes wrong
Vector masked or wrong vector assigned at CQ creation: CQE is in memory but no interrupt (the abnormal trace in Trace view). Interrupt remapping fault: the message is blocked and logged by the IOMMU. Interrupt affinity on an offline or overloaded CPU: the handler runs late.

Driver

Who acts / when
The NVMe driver's interrupt handler and the blk-mq completion path. Host t ≈ 61.6 to 62.4 µs; CQ head doorbell on the link at host t ≈ 62.55 µs (analyzer t = 60,850 ns).
What changes, where
The driver reads the CQE at its CQ1 head (slot 0x0B), sees phase 1 equal to its expected phase, looks up the request by CID, completes it, advances its head to 0x0C and writes 0x0000_000C to the CQ1 Head Doorbell at 0xFE60_100C. The DMA mapping of the buffer is torn down.
Analogy
The teacher sees the lights flicker, reads the card in the answer box, and slides a marker to show "I have read up to here," so the runner knows that compartment can be reused.
Technical
nvme_irq() → nvme_poll_cq() loops while the entry at the head has the expected phase; a read barrier (dma_rmb()) ensures the rest of the CQE is read after the phase bit. nvme_handle_cqe() extracts the CID, splits it into generation and tag, finds the request and checks the generation; it then completes the request (possibly in a batch, possibly by sending it to the submitting CPU). After the loop, nvme_ring_cq_doorbell() writes the new head once for all entries processed. When the head wraps to 0 the expected phase inverts. The SQ Head Pointer in the CQE tells the host how far the controller has consumed SQ1; Linux sizes its tags so it never needs it for flow control.
Hardware
The CPU reads the CQE from cache or memory, then performs another posted MMIO store, which becomes one more downstream MWr TLP.
Protocol
NVMe: the host is the consumer of the CQ and owns its head; the head doorbell tells the controller which CQ slots are free again. Not updating it eventually fills the CQ; a controller that has no free CQ slot cannot post completions.
Trace appearance
MWr(32) Host→Dev Addr=0xFE60100C Len=1 Data=0x0000000C. On the host: nvme:nvme_complete_rq with cmdid=4138, status=0x0; nvme:nvme_sq showing SQ head 6.
Evidence
Head doorbell value − previous value = number of CQEs consumed in that pass. A head doorbell that jumps by many entries at once means the driver processed a batch.
What goes wrong
Head doorbell never written: the CQ fills and the controller stalls all completions on that queue. Head doorbell written with a value beyond the controller's tail: an invalid doorbell write. Missing read barrier on a weakly ordered CPU: the driver reads a stale CID from a CQE whose phase bit it already saw as new.

Application completion

Who acts / when
The block layer, the direct-I/O completion code, the scheduler, and finally the application thread. Host t ≈ 62.4 to 64.6 µs.
What changes, where
The request's tag 0x2A returns to the free pool; the bio completes; the waiting thread is woken, scheduled, unpins its page and returns 4096 from pread(). The buffer holds the file's bytes.
Analogy
The teacher tells Mia, "Your page is on table 3." Mia reads it.
Technical
blk_mq_end_request() → bio_endio() → the iomap direct-I/O end-io handler, which wakes the submitter. Block-layer statistics (/sys/block/nvme0n1/stat) are updated. If the CQE status had been non-zero, nvme_complete_rq() would have mapped it to a block status (for example an I/O error), and the application would see a negative return value with errno set to EIO, possibly after retries the driver decided to make based on the Do Not Retry bit.
Hardware
Only CPU work: the wake-up may involve an inter-processor interrupt if the completion ran on a different CPU from the waiting thread.
Protocol
None on the link. Inside Linux, the block-layer completion contract.
Trace appearance
block:block_rq_complete with sector 1056768, 8 sectors, error 0; syscalls:sys_exit_pread64 with return value 4096.
Evidence
Issue-to-complete time from the block tracepoints (here about 61.5 µs) versus the system-call duration (64.6 µs) separates device time from software overhead.
What goes wrong
Wake-up latency on a busy system (the thread is not scheduled for milliseconds) makes a healthy drive look slow; a timeout that already fired and aborted the command means the late CQE is ignored as stale (the generation counter catches this).

  • "The CQE cannot overtake the data, and MSI-X cannot overtake the CQE," from posted-write ordering when Relaxed Ordering is not set on the later write.
  • The wire-time estimate of about 569 ns.
  • How quickly and in what batch size the controller fetches SQEs; whether it splits data into MPS-sized or smaller TLPs; whether it sets Relaxed Ordering.
  • FTL mapping granularity, NAND timings, ECC and read-retry behaviour, internal buffering.
  • Linux CID encoding (generation counter), doorbell batching, completion batching, IOMMU strict or lazy invalidation.
  • Platform coherency (snooping, Data Direct I/O), MSI-X address/data format and interrupt remapping.

NVMe document organization (Base versus transport) is version-dependent, as are Linux function and tracepoint field names. The TLP header layouts used here are the non-Flit-mode formats; PCIe 6.0 and later also define Flit Mode, in which header encoding and framing differ. A Gen4 x4 link like ours runs in non-Flit mode.

  • NVMe does not say how long any stage takes, nor that the controller must fetch an SQE promptly after a doorbell.
  • NVMe does not require one MSI-X message per CQE; with coalescing, or while a vector is masked, several CQEs can share one interrupt.
  • PCIe does not know about commands: no TLP field identifies an NVMe command. The PCIe tag is not the CID.
  • Neither specification says what the host's driver must do between interrupt and head doorbell, or how often it must ring the head doorbell.
  • Check in the NVMe Base Specification: the exact rules for invalid doorbell values and the associated asynchronous event; the conditions under which the controller may post a completion relative to data transfer.
  • Never assume data TLPs arrive in ascending address order (Relaxed Ordering, multiple DMA engines).
  • Never assume the analyzer timestamp of a TLP is the moment the host or device "did" something; it is the moment the packet crossed that link.
  • Never assume one doorbell equals one command, or one MSI-X equals one completion.
  • Never assume the addresses on the link are physical addresses: with an IOMMU they are IOVAs.

The host learns that data is ready by seeing a CQE; it sees the CQE because an interrupt arrived. NVMe does not add any handshakes of its own for these; it relies on memory ordering on the host side and PCIe ordering on the link.

Reasoning. Walk forward and stop at the first missing or wrong event. Rows 1–3 prove the doorbell and fetch worked. Rows 4–19 prove the data reached the correct addresses. Row 20 proves the CQE was written with the right SQID, CID and phase. The expected next event, a posted write to the MSI-X address for vector 1, never appears; that is the first abnormal event, and everything after it (the 30-second wait, the CSTS read, the late head doorbell) is a consequence, not a cause.

The CSTS read returning RDY = 1 and CFS = 0 confirms the controller is alive, and the driver's polling finding a valid CQE confirms the completion path through memory is fine. The fault is confined to interrupt generation or delivery. Candidates, in order of likelihood: (1) the vector is masked (per-vector Mask bit in MSI-X table entry 1, or Function Mask); (2) CQ1 was created with Interrupts Enabled cleared or a different Interrupt Vector than the host expects; (3) interrupt coalescing set to an extreme value; (4) controller firmware bug in interrupt generation. If the MSI-X write had appeared on the link and the handler still did not run, the suspects would move to the host: interrupt remapping, the interrupt request (IRQ) affinity, or a handler registered on the wrong vector.

Code / pseudocode

A runnable model of the whole read

This script builds the SQE and CQE byte for byte, derives every address from the lab-system constants and prints the analyzer-style timeline from Trace view. Change MPS to 128 or 512, or the buffer address to one that is not page aligned, and watch the TLP list change.

#!/usr/bin/env python3
"""Synthetic end-to-end 4 KiB NVMe READ on the course's lab system.
Builds the SQE and CQE bytes, derives every address, splits the data
into MPS-sized Memory Write TLPs and prints an analyzer-style timeline.
Standard library only. Latencies are illustrative, not measured."""
import struct

BAR0, DSTRD = 0xFE60_0000, 0          # BAR0 address, CAP.DSTRD
SQ1_BASE, CQ1_BASE = 0x1_2340_0000, 0x1_2341_0000
QSIZE, MPS, LBA_SIZE = 1024, 256, 512
MSIX_ADDR, MSIX_DATA = 0xFEE0_1000, 0x41   # illustrative vector 1 values

def sq_tail_db(qid): return BAR0 + 0x1000 + (2 * qid) * (4 << DSTRD)
def cq_head_db(qid): return BAR0 + 0x1000 + (2 * qid + 1) * (4 << DSTRD)

def read_sqe(cid, nsid, prp1, prp2, slba, nlb0):
    cdw0 = 0x02 | (cid << 16)            # opcode 02h, FUSE=0, PSDT=0 (PRP)
    return struct.pack("<IIQQQQIIIIII", cdw0, nsid, 0, 0, prp1, prp2,
                       slba & 0xFFFFFFFF, slba >> 32, nlb0, 0, 0, 0)

def cqe(sqhd, sqid, cid, phase, status=0):
    return struct.pack("<IIII", 0, 0, sqhd | sqid << 16,
                       cid | phase << 16 | status << 17)

def split_writes(addr, length, mps=MPS):
    """Device-to-host writes: never exceed MPS, never cross a 4 KiB boundary."""
    while length:
        n = min(mps, length, 0x1000 - (addr & 0xFFF))
        yield addr, n
        addr, length = addr + n, length - n

def wire_ns(payload, hdr=16, gts=16.0, lanes=4):
    """STP token (4) + header + payload + LCRC (4), 128b/130b encoding."""
    return (4 + hdr + payload + 4) / (gts * lanes * 128 / 130 / 8)

def dws(b): return " ".join(f"{d:08X}" for d in struct.unpack(f"<{len(b)//4}I", b))

def main():
    sq_slot, cq_slot, phase = 5, 0x0B, 1
    cid = (1 << 12) | 0x2A               # Linux-style: generation 1, tag 0x2A
    buf, slba, length = 0x2_0000_3000, 0x0010_2000, 4096
    sqe = read_sqe(cid, 1, buf, 0, slba, length // LBA_SIZE - 1)
    new_tail = (sq_slot + 1) % QSIZE
    rows = [(0, "H>D", "MWr32", f"addr={sq_tail_db(1):#x} data={new_tail:#x}", "SQ1 tail doorbell")]
    rows.append((700, "D>H", "MRd64", f"addr={SQ1_BASE + sq_slot * 64:#x} len=16 tag=0x21", f"fetch SQ1 slot {sq_slot}"))
    rows.append((1350, "H>D", "CplD", f"tag=0x21 BC=64 payload={dws(sqe[:8])} ...", "SQE delivered"))
    t = 57_600
    for a, n in split_writes(buf, length):
        rows.append((t, "D>H", "MWr64", f"addr={a:#x} len={n // 4}", "read data"))
        t += 40
    entry = cqe(new_tail, 1, cid, phase)
    rows.append((t + 40, "D>H", "MWr64", f"addr={CQ1_BASE + cq_slot * 16:#x} len=4 payload={dws(entry)}", "CQE"))
    rows.append((t + 100, "D>H", "MWr32", f"addr={MSIX_ADDR:#x} data={MSIX_DATA:#x}", "MSI-X vector 1"))
    rows.append((60_850, "H>D", "MWr32", f"addr={cq_head_db(1):#x} data={(cq_slot + 1) % QSIZE:#x}", "CQ1 head doorbell"))
    for i, (ts, d, typ, fields, meaning) in enumerate(rows, 1):
        print(f"{i:2d} {ts:>7,} ns {d} {typ:6s} {fields:60s} {meaning}")
    n = len(list(split_writes(buf, length)))
    total = sum(wire_ns(p) for _, p in split_writes(buf, length))
    print(f"\n{n} data TLPs; minimum serialization time {total:.0f} ns at Gen4 x4")

if __name__ == "__main__":
    main()

The driver's two hot paths, simplified

/* Submission: called by blk-mq for one request (cf. nvme_queue_rq) */
int submit(struct queue *q, struct request *rq)
{
    struct nvme_command c = {0};
    c.opcode  = 0x02;                          /* Read */
    c.cid     = (rq->genctr << 12) | rq->tag;   /* 0x102A in this chapter */
    c.nsid    = 1;
    c.slba    = rq->sector;                      /* 512-byte LBAs: no shift */
    c.nlb     = rq->bytes / 512 - 1;             /* zero-based: 7 */
    c.prp1    = dma_map(rq->page, rq->offset);   /* IOVA 0x2_0000_3000 */
    c.prp2    = 0;                               /* fits in one memory page */

    spin_lock(&q->sq_lock);
    memcpy(q->sq + q->sq_tail * 64, &c, 64);    /* slot 5 → 0x1_2340_0140 */
    q->sq_tail = (q->sq_tail + 1) % q->depth;    /* 6 */
    if (rq->is_last_in_batch)
        writel(q->sq_tail, q->sq_doorbell);       /* writel orders after the memcpy */
    spin_unlock(&q->sq_lock);
    return OK;
}

/* Completion: MSI-X handler for the queue's vector (cf. nvme_irq / nvme_poll_cq) */
irqreturn_t irq(struct queue *q)
{
    int found = 0;
    while ((q->cq[q->cq_head].status & 1) == q->cq_phase) {   /* phase bit is bit 0 of the 16-bit status word */
        dma_rmb();                                 /* read the rest after the phase */
        struct cqe *e = &q->cq[q->cq_head];
        struct request *rq = lookup(q, e->cid & 0xFFF);
        if (!rq || genctr(e->cid) != rq->genctr)
            warn("invalid id completed on queue");
        else
            complete(rq, e->status >> 1);           /* drop phase, keep status */
        if (++q->cq_head == q->depth) {           /* wrap: flip expected phase */
            q->cq_head = 0;
            q->cq_phase ^= 1;
        }
        found++;
    }
    if (found)
        writel(q->cq_head, q->cq_doorbell);        /* one head doorbell for the batch */
    return found ? IRQ_HANDLED : IRQ_NONE;
}

/* Reads one 4 KiB block with O_DIRECT. Needs a real file or block device.
   Read-only: it never writes to the device. Build: cc -O2 -o direct_read direct_read.c */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <time.h>
#include <unistd.h>

int main(int argc, char **argv)
{
    if (argc != 3) { fprintf(stderr, "usage: %s FILE BYTE_OFFSET\n", argv[0]); return 2; }
    int fd = open(argv[1], O_RDONLY | O_DIRECT);
    if (fd < 0) { perror("open"); return 1; }
    void *buf;
    if (posix_memalign(&buf, 4096, 4096)) return 1;   /* page-aligned: one PRP entry */
    struct timespec a, b;
    clock_gettime(CLOCK_MONOTONIC, &a);
    ssize_t n = pread(fd, buf, 4096, strtoll(argv[2], NULL, 0));
    clock_gettime(CLOCK_MONOTONIC, &b);
    printf("pread returned %zd in %.1f us\n", n,
           (b.tv_sec - a.tv_sec) * 1e6 + (b.tv_nsec - a.tv_nsec) / 1e3);
    free(buf);
    close(fd);
    return n == 4096 ? 0 : 1;
}

Three lessons fall out of the budget.

  1. The media dominates. About 84% of the time (54.3 µs) is inside the flash back end. On a drive with faster media (low-latency single-level-cell (SLC) NAND or other storage-class memory), the same software and link overheads become a much larger share, which is why polled I/O and interrupt tuning matter more on those drives.
  2. PCIe is almost free for a single 4 KiB read. All link activity for this command, summed, is about 2.5 µs (doorbell transit, fetch round trip, data/CQE/MSI-X), and most of that is waiting, not serialization: the data itself occupies the wire for only about 0.57 µs.
  3. Host software is about 9%. Submission, interrupt delivery, completion and wake-up add up to about 5.8 µs. At queue depth 1 this caps the system at 1 / 64.6 µs ≈ 15,500 IOPS no matter how fast the link is; Little's Law (Calculators) says you need about 64.6 µs × target IOPS commands in flight to go faster.

Common mistakes

  • Expecting data in Completions. For an NVMe READ, data reaches the host as device-initiated Memory Writes. Completions with Data appear only for things the device reads: SQEs, PRP lists, and WRITE data (see End-to-End Write).
  • Matching by tag across the command. The tag on the SQE fetch is reused for unrelated reads microseconds later. It identifies one PCIe request, not the NVMe command.
  • Treating NLB as a count. NLB 7 means 8 blocks.
  • Computing the doorbell from a guessed stride. Always read CAP.DSTRD; on our system it is 0, but some controllers (and many emulated ones) use larger strides.
  • Assuming addresses on the link are physical. With an IOMMU they are IOVAs; comparing them with physical addresses from a kernel crash dump will not match.
  • Forgetting buffered I/O. Tracing a buffered 4 KiB read and looking for a 4 KiB command.
  • Reading the gap as link idleness. The 56 µs gap is the media working; a longer gap is a media or firmware question, not a PCIe one.
  • Blaming the last visible event. In the missing-interrupt trace, the CSTS read and late doorbell are host recovery, not the fault.
  • Assuming one interrupt per command. Under load, one MSI-X typically covers several CQEs, and one head doorbell acknowledges a batch.

Senior engineer insight

  • Think in ownership transfers. The SQ slot belongs to the host until the tail doorbell passes it, then to the controller until a CQE's SQ Head Pointer passes it. The buffer belongs to the controller from doorbell to CQE. The CQ slot belongs to the controller until the head doorbell passes it. Most corruption bugs are someone touching a thing they do not own at that moment.
  • The protocol has exactly two synchronization points per direction. Host to device: memory ordering before the doorbell. Device to host: posted-write ordering before the CQE and MSI-X. When a bug is intermittent and data-dependent, look at those two points first.
  • The silent gap is information. A distribution of fetch-to-first-data gaps across thousands of reads is a picture of the media and firmware. Bimodal distributions usually mean two different internal paths (cache hit versus NAND, or read retry).
  • Count TLPs before you read them. 1 + 1 + 1 + 16 + 1 + 1 + 1 for a 4 KiB read on this system. If a capture has 32 data writes, MPS is 128 or the buffer is not aligned. If it has an extra MRd, a PRP list or HMB access is involved. Counting is the fastest sanity check there is.
  • Doorbells are the only host speech. If you want to know what the host believed, read the doorbell values: SQ tail tells you how many commands it thought it submitted; CQ head tells you how many completions it thought it consumed.

Lab

Lab 39 — Follow one direct read end to end

Objective

Predict every address, identifier and TLP of a single 4 KiB direct read on your own system, then capture the host-side evidence and reconcile it with your prediction.

Skills

Address arithmetic for queues and doorbells; reading tracepoints; separating host and device time; building a latency budget.

Safety

Safe lab Read-only. The only device access is a single 4 KiB read with iflag=direct. Use if= (input), never of=, on the NVMe device. Tracing needs root but changes nothing persistent.

Hardware required

Any Linux machine with an NVMe SSD. No analyzer needed (an optional extension uses one).

Software required

Linux with tracefs, trace-cmd, nvme-cli, pciutils, Python 3.

Input

Your device name (for example nvme0n1), its logical block size, and a chosen 4 KiB-aligned byte offset within the namespace.

Expected output

A filled-in table: SLBA, NLB, opcode, queue ID, CID, interrupt name, and five timestamps (issue, setup_cmd, irq entry, complete_rq, rq_complete), plus a predicted TLP list for the lab system.

Background

Stages 1–17 of this chapter. The key formula: SLBA = byte offset ÷ LBA size; NLB = 4096 ÷ LBA size − 1.

Step 1 — Predict

Run e2e_read_sim.py. Then change the offset so the read targets SLBA 0x0010_2008 and the SQ slot to 6, and predict the new SQE address, doorbell value and CQE contents by hand before running it.

Step 2 — Inspect your system

Run the read-only commands in Linux view: record LBA size, MPS, MRRS, MSI-X vector count and which nvme0qN interrupt belongs to the CPU you will run on (use taskset -c 3 to pin the read).

Step 3 — Capture

Run the trace-cmd record command with your offset, pinned with taskset. Extract the five timestamps and the nvme_setup_cmd line.

Observation

Note the cmdid value (decimal); convert it to hex and split it into generation and tag. Note the gap between nvme_setup_cmd and irq_handler_entry.

Questions

  1. Does slba in the tracepoint equal your offset ÷ LBA size? Does len equal 4096 ÷ LBA size − 1?
  2. Which interrupt name fired, and does it match the queue ID in the tracepoint?
  3. Run it ten times. Which segment of the latency varies most?
  4. On the lab system, how many TLPs would your read produce if MPS were 128?

Challenge

Repeat without iflag=direct (drop caches first with care, or use a fresh offset) and explain the different NVMe commands you see.

Hints

If you see no nvme events, check that the tracepoints exist: ls /sys/kernel/tracing/events/nvme/. If qid differs from what you expected, remember that queue mapping depends on the CPU and on how many I/O queues the driver created. A 4 KiB-LBA namespace makes len=0.

Solution

Step 1: slot 6 → SQE at 0x1_2340_0000 + 6 × 64 = 0x1_2340_0180; doorbell value 7 to 0xFE60_1008; CQE DW2 = 0x0001_0007 (SQHD 7), DW3 = CID | phase. SLBA 0x0010_2008 in CDW10.

Q1: yes if LBA size is 512 (len=7) or 4096 (len=0). Q2: the interrupt is nvme0qN where N is the queue ID; they should match. Q3: usually the setup-to-irq segment (device time) varies most; if the irq-to-complete or complete-to-return segment varies, suspect host scheduling. Q4: MPS 128 → 32 data MWr TLPs, so 1 + 1 + 1 + 32 + 1 + 1 + 1 = 38 TLPs.

Challenge: buffered I/O on a cold page produces a read-ahead READ (often 128 KiB or more, many NLB) and possibly several commands; on a warm page it produces none.

What a senior engineer notices

That the trace timestamps from different CPUs need the same clock source; that the first read after idle is slower (power-state exit, cold caches); that cmdid generation bits change across reuse; that the irq fired on the same CPU because the queue is per-CPU.

Failure variants

  • dd fails with "Invalid argument": offset or size not aligned for direct I/O.
  • No irq_handler_entry: the driver is using polled queues for this I/O or interrupts are threaded under a different name.
  • Latency in milliseconds for the first read: the drive was in a non-operational power state (Power Management).

Extension

With a PCIe analyzer or an interposer: capture the same read and fill in the link column of the timeline. Align host and link clocks using the doorbell (setup_cmd + a few hundred ns) and the MSI-X (irq entry − 1 to 3 µs).

Exercises

  1. The same 4 KiB read is issued to a buffer at IOVA 0x2_0000_3800 (not page aligned). List PRP1, PRP2 and the data TLPs on the lab system.

    Answer

    PRP1 = 0x2_0000_3800 (offset 0x800 in its page, allowed for PRP1). The transfer spans two pages, so PRP2 = 0x2_0000_4000 (a direct pointer to the second page, no list). Data: 0x800 bytes in the first page → 8 TLPs of 256 B at 0x3800…0x3F00; then 8 TLPs at 0x4000…0x4700. Still 16 TLPs, because 0x800 is a multiple of 256; the TLP that would cross 0x4000 does not exist since the split happens exactly at the boundary.

  2. SQ1 tail is 1023 before submission. What doorbell value is written, and at which address is the SQE stored?

    Answer

    SQE at 0x1_2340_0000 + 1023 × 64 = 0x1_2340_FFC0. New tail wraps to 0, so the driver writes 0x0000_0000 to 0xFE60_1008. A tail value of 0 after a wrap is normal and must not be read as "nothing submitted."

  3. The CQE for our read lands in CQ1 slot 1023 with phase 1. What are the CQ head doorbell value and the driver's expected phase afterwards?

    Answer

    Head wraps to 0; the driver writes 0 to 0xFE60_100C; its expected phase flips to 0 for the next pass through the ring.

  4. Namespace 2 uses 4 KiB LBAs. Rewrite CDW10 and CDW12 for a 4 KiB read at byte offset 0x2040_0000.

    Answer

    SLBA = 0x2040_0000 ÷ 4096 = 0x2_0400 → CDW10 = 0x0002_0400; NLB = 1 − 1 = 0 → CDW12 = 0x0000_0000; NSID = 2 in CDW1.

  5. Repeat the wire-time estimate for a Gen5 x4 link (32 GT/s) with MPS 512.

    Answer

    B = 32 × 4 × 128/130 ÷ 8 ≈ 15.75 GB/s. N = 4096/512 = 8 TLPs of 4 + 16 + 512 + 4 = 536 bytes → 4288 bytes ÷ 15.75 GB/s ≈ 272 ns. Still negligible against tens of microseconds of NAND time.

  6. A capture shows the SQE fetch as an MRd with Length = 64 DW at 0x1_2340_0100. What does that tell you?

    Answer

    Slot (0x100 ÷ 64) = 4, and 64 DW = 256 bytes = 4 SQEs: the controller fetched slots 4, 5, 6 and 7 in one request, so the host must have submitted at least 4 commands before the doorbell (tail ≥ 8). The completion may come back as one or several CplDs (each ≤ MPS, split at RCB boundaries).

Quiz

  1. Which TLP carries the read data from the SSD into host memory?

    • Completion with Data returned by the root complex
    • Memory Write requests issued by the SSD
    • Memory Read requests issued by the root complex
    • Completion with Data returned by the SSD
    Answer and reasoning

    The controller is a bus master and pushes read data into host memory with posted Memory Writes to the PRP addresses. Completions carry data only for reads someone issued; the host issues no reads in the data path.

  2. On the lab system, what address does the doorbell for this read go to?

    • 0x1_2340_0140
    • 0xFE60_1000
    • 0xFE60_1008
    • 0xFE60_100C
    Answer and reasoning

    SQ1 tail doorbell = BAR0 + 0x1000 + 2 × 1 × 4 = 0xFE60_1008. 0xFE60_1000 is the admin SQ tail; 0xFE60_100C is the CQ1 head; 0x1_2340_0140 is the SQE in host memory.

  3. Why does the SQE fetch MRd use a 4-DW header but the doorbell MWr a 3-DW header?

    Answer

    The header format depends on the address, not the BAR type. The SQE is at 0x1_2340_0140, above 4 GiB, so a 64-bit address (4-DW header) is required; the doorbell is at 0xFE60_1008, below 4 GiB, which must use the 32-bit (3-DW) format.

  4. How many data TLPs, at minimum, does a page-aligned 4 KiB read produce with MPS = 256?

    • 1
    • 8
    • 16
    • 32
    Answer and reasoning

    4096 ÷ 256 = 16. The device may use smaller payloads (more TLPs) but never larger ones.

  5. What in the CQE tells the driver that the entry is new?

    Answer

    The Phase Tag (DW3 bit 16) matching the driver's expected phase for the current pass of the ring. There is no "valid" bit; the controller inverts the phase each time it wraps the CQ.

  6. Which value identifies the command in the CQE?

    • The PCIe tag of the SQE fetch
    • The pair (SQ Identifier, Command Identifier)
    • The CQ slot index
    • The MSI-X vector
    Answer and reasoning

    CIDs are unique only within a submission queue, so the pair (SQID, CID) is the key. The PCIe tag belongs to a different layer and is reused; the CQ slot and vector are shared by many commands.

  7. Why can the host trust that the data is in memory when it sees the CQE?

    Answer

    Data and CQE are posted writes from the same requester; PCIe ordering does not allow a posted write without Relaxed Ordering (the CQE) to pass earlier posted writes, and the controller writes the CQE only after transferring the data. The MSI-X write likewise cannot pass the CQE.

  8. In the latency budget, which segment would shrink most if the NAND were replaced with a much faster medium, and which would then dominate?

    Answer

    The NAND array read (50 µs) would shrink most. Host software (submission, interrupt delivery, completion, wake-up: about 5.8 µs) and the controller front end would then dominate, which motivates polled completions and lighter submission paths.

  9. A trace shows the doorbell and nothing else for this command. List the first three things to check.

    Answer

    (1) Controller state: CSTS.RDY and CFS. (2) That SQ1 exists and its tail doorbell is the one written (the doorbell address and value against the queue's size). (3) Bus Master Enable in the device's Command register; without it the device cannot fetch. Then firmware state via logs.

  10. True or false: one MSI-X message is always sent per CQE.

    • True
    • False
    Answer and reasoning

    False. Interrupt coalescing, masking (pending bits), and implementation choices mean one message may cover several CQEs; the driver processes every new CQE it finds in one handler run.

Interview questions

  1. (Beginner) What does the host send to the SSD to start a read?

    Model answer

    Only a doorbell write: the new SQ tail index written to the SQ tail doorbell register in BAR0. The command itself is placed in host memory, and the controller fetches it.

  2. (Beginner) What is the difference between the SQ tail doorbell and the CQ head doorbell?

    Model answer

    The SQ tail doorbell tells the controller new commands are available up to that index (host is producer). The CQ head doorbell tells it the host has consumed completions up to that index, freeing those CQ slots (host is consumer).

  3. (Intermediate) Walk me through all TLPs of a 4 KiB read on a system with MPS 256.

    Model answer

    MWr doorbell down; MRd SQE fetch up (non-posted, tag); CplD with 64 bytes down; 16 MWr data up to the PRP address; MWr CQE up; MWr MSI-X up; later MWr CQ head doorbell down. Plus Ack and UpdateFC DLLPs.

  4. (Intermediate) Why is the CID not visible in any TLP header?

    Model answer

    Because PCIe is unaware of NVMe. The CID lives inside the payload of the SQE fetch completion and the CQE write. To correlate on the link you decode payloads and use addresses; TLP tags only match requests to completions.

  5. (Advanced) A customer reports occasional stale data on reads. The drive's logs are clean. What could cause this and how would you prove it?

    Model answer

    Candidates: CQE overtaking data (controller using Relaxed Ordering on the CQE or a platform ordering bug), driver reading CQE fields before the phase without a barrier, IOMMU unmapping too early, file-system or application races. Prove with an analyzer: check every CQE is after the last data MWr for that command and without RO; then check host-side ordering (barriers) and buffer ownership.

  6. (Advanced) Your QD1 4 KiB read latency is 80 µs; the vendor says the media read is 50 µs. Where do you look?

    Model answer

    Build a latency budget. Use block and nvme tracepoints to split host submission, device time and host completion. Check power states (APST exit latency), interrupt delivery (affinity, CPU idle states), IOMMU mode, and whether the I/O is really direct. An analyzer gives fetch-to-data time to separate controller from host.

  7. (Senior) Design a validation test that proves a controller never posts a CQE before its data.

    Model answer

    Run mixed-size reads with Relaxed Ordering enabled and disabled, many queues and high depth; capture on the link; for every CQE find all data MWr whose address lies in that command's PRP ranges and assert all precede the CQE and the CQE has RO clear. Add host-side data verification with known patterns and an injector that delays some data writes (exerciser) to provoke reordering.

  8. (Senior) What would you change in this flow for a storage-class-memory device with 5 µs media latency?

    Model answer

    Host software becomes the bottleneck: use polled completions (no MSI-X, fewer context switches), io_uring with registered buffers to avoid pinning costs, avoid IOMMU strict mode costs, keep queues per-CPU, consider interrupt coalescing only at high depth, and minimize doorbell writes via batching. On the device, faster fetch and shorter front-end paths matter more than link bandwidth.

Model answer for the junior-engineer version

The application calls pread with O_DIRECT; the file system maps the offset to an LBA; blk-mq creates a request with a tag; the NVMe driver builds a 64-byte Read command whose CID comes from the tag, maps the buffer through the IOMMU, copies the command into the next SQ slot and writes the new tail to the SQ tail doorbell. That store becomes a posted MWr TLP. The controller sees the new tail, issues an MRd for the SQE, gets it back in a CplD, translates the LBA, reads NAND, then writes the data to the PRP address in MPS-sized MWr TLPs, writes the 16-byte CQE to the next CQ slot with the current phase, and sends an MSI-X MWr. The CPU takes the interrupt, the driver finds the CQE by phase, completes the request by CID, writes the CQ head doorbell, and the block layer wakes the application.

Chapter summary

A 4 KiB NVMe READ is seventeen stages and, on our lab system, 22 TLPs. The host contributes a 64-byte command in memory and two 4-byte doorbell writes; the controller does all other link traffic as a bus master: one SQE fetch (the only non-posted request), sixteen data writes, one CQE write and one MSI-X write. Correctness rests on two ordering guarantees: the SQE is visible before the doorbell, and data is visible before the CQE (and the CQE before the MSI-X). The latency is dominated by the NAND read; the link's share is small; host software is under a tenth at these media speeds. Every failure shows up as the first stage whose expected evidence is missing, which makes this chapter your template for every debug session that follows.
