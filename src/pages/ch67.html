NVMe over RDMA (NVMe/RDMA) carries NVMe capsules over Remote Direct Memory Access networks: RDMA over Converged Ethernet (RoCE), the Internet Wide Area RDMA Protocol (iWARP) and InfiniBand. The target's network adapter moves data directly into and out of host memory that the host has registered and named with a key. This chapter builds the RDMA concepts from the ground up (queue pairs, memory registration, SEND, RDMA READ and RDMA WRITE) and shows how NVMe maps onto them, with keyed SGL descriptors as the bridge.

Why this chapter exists

RDMA was the first NVMe-oF transport. NVMe over Fabrics 1.0 in 2016 defined RDMA and Fibre Channel bindings, and RDMA is still the choice when the lowest latency and lowest CPU cost per I/O matter. It is also the transport that most confuses engineers coming from PCIe, because it almost looks like PCIe. A device on one side writes directly into memory on the other side, without the remote CPU touching the data.

That "almost" is where bugs live. Over PCIe, an NVMe controller can DMA to any address the IOMMU allows. Over RDMA, the target's NIC can touch only memory regions the host explicitly registered, only within their bounds, and only while the key that names them is valid. Over PCIe, a bad address yields an Unsupported Request or an IOMMU fault. Over RDMA, a bad key yields a remote access error that kills the whole queue pair and every command on it.

The master prompt asks for this topic to be taught conceptually. You will not program verbs here. You will learn the objects and operations well enough to read an NVMe/RDMA capture, reason about a failure and hold a design discussion.

The story

Remember the library across town? With RDMA, the library has a robot arm that can reach through a special window into the teacher's classroom. But the teacher is careful. She puts the books she wants filled on one particular shelf, locks the shelf, and writes the shelf's number and a secret code on her request slip. The librarian's robot can open only that shelf, only with that code, and only until the teacher changes the lock.

When the teacher asks for books, the robot reaches in and puts them on the shelf. When the teacher wants to send books to the library, the robot reaches in and takes them from the shelf. Either way, the teacher does not carry anything. When the job is done, the librarian sends back a note that says "done, and please change the lock now", so the code can never be used again.

Think of a bank's safe-deposit service. You rent a box (register memory) and receive a box number and a one-time access code (address and remote key). You hand a courier a work order containing the box number and code (the command capsule with a keyed SGL). The courier can open that box, and only that box, to deposit or withdraw items without you being present (RDMA WRITE or READ). When the job finishes, the bank voids the code (invalidation). If the courier shows up with a voided code, the guard refuses entry and also closes the whole branch counter you were using until someone resets it (the queue pair enters the error state).

What it hides. Registration is not free. It pins memory so the operating system cannot move it, and loads translations into the NIC. Doing it per I/O costs work requests and NIC cache space. The analogy also hides that the command and completion still travel as messages (SEND). Only the bulk data uses the "reach into the box" path.

Where it misleads. A real safe-deposit box can be opened by its owner at any time. In RDMA, the host CPU must not reuse or free a buffer while the remote side may still access it. That is why invalidation must be complete before the I/O completes to the application. The analogy also suggests one courier per box. In fact many commands share one queue pair, each with its own key.

Beginner explanation

RDMA lets a network adapter read or write memory on a remote machine without involving the remote machine's CPU in moving the data. The remote side must first register that memory. Registration tells its network adapter "this range is allowed", and produces a remote key (rkey) that the peer must present.

RDMA-capable network adapters (RNICs) communicate through queue pairs (QPs). Each QP has a send queue and a receive queue. Software posts work requests to them: "send this message", "write these bytes to that remote address with this key", "read those remote bytes into this local buffer". The RNIC reports finished work on a completion queue. Yes, RDMA has its own queues and completions, completely separate from NVMe's. Keep the two vocabularies apart.

NVMe/RDMA maps each NVMe queue pair onto one RDMA queue pair:

  • Command: the host posts a SEND carrying the command capsule. The target's RNIC places it in a receive buffer the target posted earlier.
  • Read data: the target posts an RDMA WRITE that puts the data straight into the host's registered buffer, using the address and key from the command's Keyed SGL Data Block descriptor.
  • Write data: small writes travel in-capsule. Large writes are fetched by the target with an RDMA READ from the host's registered buffer.
  • Completion: the target posts a SEND (often SEND with Invalidate) carrying the response capsule.

Three network technologies provide RDMA:

  • InfiniBand: its own link layer, switches and subnet manager. It was designed for RDMA from the start.
  • RoCE (RDMA over Converged Ethernet): InfiniBand transport packets carried on Ethernet. RoCE v2 encapsulates them in UDP/IP (UDP destination port 4791), so they are routable.
  • iWARP: RDMA semantics layered on TCP, defined by the IETF.

RDMA has queue pairs, completion queues and work requests. NVMe has submission queues, completion queues and commands. In NVMe/RDMA, one NVMe SQ/CQ pair rides on one RDMA QP, and every NVMe command produces several RDMA work requests. When someone says "the CQ", ask "which one?"

What a RoCE v2 packet looks like

The Packet Sequence Number (PSN) in the BTH is how the RNICs detect loss and order. A NAK carrying "PSN sequence error" triggers go-back-N retransmission. A NAK carrying "Remote Access Error" or "Remote Operational Error" is fatal to the QP. A NAK carrying "RNR" (Receiver Not Ready) means "no receive buffer posted, try again later".

Memory registration

Memory registration does three things: it pins the pages so they cannot be swapped or migrated, it loads the virtual-to-physical (or IOVA) translations into the RNIC's tables, and it assigns access rights (local write, remote read, remote write) and keys.

NVMe hosts handle I/O buffers in one of two broad ways:

  • Per-I/O fast registration, the default for Linux nvme-rdma. For each I/O, the host posts a registration work request that maps the request's scatterlist into an MR with a fresh key, then sends the command. After completion, the key is invalidated, either remotely by the target's SEND with Invalidate or locally by a Local Invalidate WR. The buffer is exposed only for the lifetime of one command.
  • Pre-registered or global keys. Registering all memory once with a single rkey avoids per-I/O work but exposes everything to the remote side for as long as the key lives. Linux treats this as unsafe and offers it only as a non-default option (the register_always module parameter). Implementation-dependent

Memory registration interacts with the IOMMU: the RNIC's DMA uses IOVAs, exactly as the Lab SSD's does in DMA. An RNIC remote access error and an IOMMU fault on the RNIC are different failures with similar symptoms. The first is a key/bounds check in the RNIC. The second is the platform blocking a translation. Check both logs.

Connection establishment: the RDMA Connection Manager

NVMe/RDMA uses the RDMA Connection Manager (RDMA_CM) to create each RC QP connection. RDMA_CM resolves an IP address to an RDMA device and path, then runs the InfiniBand CM exchange: REQ (request), REP (reply), RTU (ready to use), or REJ (reject). On RoCE, these are management datagrams to the special QP1. On iWARP, the equivalent is the MPA exchange over TCP.

NVMe/RDMA puts its own private data into these messages, as defined by the RDMA Transport specification:

After the RDMA connection is up, the NVMe Connect command still follows as a SEND. The RDMA_CM exchange sets up the pipe, and Connect sets up the NVMe queue and association, exactly as ICReq/Connect do on TCP.

NVMe/RDMA has no equivalent of TCP's ICReq/ICResp PDU. RDMA_CM private data plays that role. There are no header or data digests, because the RDMA transport's ICRC (RoCE/IB) or MPA CRC (iWARP) already protects every packet end to end between RNICs.

Receive buffers, credits and RNR

SEND only works if the receiver has posted a receive work request with a buffer large enough for the incoming capsule. The target posts receives on each QP or on an SRQ, each sized for a command capsule including in-capsule data. The host posts receives sized for response capsules. If a SEND arrives with no receive posted, the receiving RNIC answers with an RNR NAK, and the sender retries after a timer. With RNR retries exhausted, the QP fails. NVMe's queue sizes keep this from happening in a correct implementation: the host never has more commands outstanding than the target has receive buffers (CRQSIZE). An RNR in a trace is therefore a strong sign of a sizing or reposting bug, or of severe CPU starvation on the receiver.

In-capsule data on RDMA

Exactly as on TCP, small writes can ride inside the command capsule (the SEND payload), bounded by IOCCSZ. The SGL is then a Data Block/Offset descriptor (identifier 01h), not a keyed descriptor. This saves an RDMA READ round trip. Linux nvmet-rdma exposes the in-capsule size as a per-port configuration attribute. Implementation-dependent

The central concept on the ladder: data movement with registered memory

A locked shelf in the classroom, a secret code on the request slip, a robot arm from the library that can open only that shelf, and a "change the lock" note at the end.

The host registers the I/O buffer, getting an rkey, and puts address + length + rkey in a Keyed SGL descriptor in the SQE. The target RDMA WRITEs read data into it or RDMA READs write data from it, then sends the response capsule, invalidating the key.

The host RNIC holds translation and protection tables for the MR. The target's RDMA WRITE arrives as packets. The host RNIC checks the key, bounds and access rights, translates to IOVA and emits PCIe Memory Writes into host memory. No host CPU involvement until the final SEND completes.

The NVMe over RDMA Transport Specification, Revision 1.3 defines the binding: RC QPs, capsules via SEND, keyed SGLs, RDMA_CM private data. The Base 2.4 specification defines Keyed SGL Data Block descriptors and capsules. RDMA semantics come from the InfiniBand Architecture Specification (IBTA) and the IETF iWARP RFCs.

Read: SEND(capsule) → RDMA WRITE(data) → SEND with Invalidate(response). Write: SEND(capsule) → RDMA READ request → RDMA READ response(data) → SEND with Invalidate(response). RNIC ACKs and NAKs flow underneath.

A RoCE v2 capture shows UDP/4791 packets decoded as InfiniBand: "RC Send Only" with an NVMe-oF capsule inside, "RC RDMA Write Only" with RETH (VA, R_key, length), "RC Acknowledge", and "RC Send Only with Invalidate". On the host's PCIe link, the RDMA WRITE appears as RNIC MWr TLPs into the buffer.

A NAK with Remote Access Error points to a key, bounds or permission mismatch: stale key, wrong PD, buffer too small. RNR NAKs point to receive-buffer starvation. Retry-exceeded errors point to network loss or a dead peer. Each kills the QP, so check whether all commands on that queue failed together.

Hardware view

In NVMe/RDMA, the RNIC does much of the work that host and target CPUs do in NVMe/TCP. It segments and reassembles messages, acknowledges and retransmits, checks keys and bounds, and DMAs payloads directly to their final buffers.

The PCIe side of an RDMA WRITE

This is the part PCIe engineers find satisfying. When the target RDMA WRITEs 4 KiB into a host buffer, the host RNIC turns it into PCIe Memory Write TLPs, just as the Lab SSD does for a local read. The requester is now the RNIC, and the completion signal is a verbs completion entry plus an MSI-X interrupt, not an NVMe CQE. The NVMe completion arrives later, as a SEND payload written into a receive buffer.

Specification view

The binding is normative in the NVMe over RDMA Transport Specification, Revision 1.3. Capsules, Fabrics commands and SGL descriptor formats, including the Keyed SGL Data Block, are in the NVM Express Base Specification, Revision 2.4. RDMA semantics come from outside NVM Express: the InfiniBand Architecture Specification (IBTA), including the RoCE and RoCE v2 annexes, and the IETF iWARP RFCs (RFC 5040 RDMAP, RFC 5041 DDP, RFC 5044 MPA).

  • NVMe/RDMA uses Reliable Connected QPs, one per NVMe queue pair.
  • Command and response capsules are carried by RDMA SEND (the response optionally by SEND with Invalidate).
  • Host data buffers are described with Keyed SGL Data Block descriptors (type 4h) carrying address, length and key. Subtype Fh requests remote invalidation.
  • Connection setup uses RDMA_CM with NVMe-specific private data (record format, QID, host receive/send queue sizes in REQ, controller receive queue size in REP).
  • NVMe/RDMA uses port 4420 by convention, in the RDMA_CM port space.
  • Because RC delivers in order and the RNIC ACKs the RDMA WRITE before the following SEND is delivered, the host can safely consume read data when it sees the response capsule. No extra fence is needed.
  • Because the target initiates all data operations, the host's exposure is limited to the buffers named in outstanding commands, provided keys are invalidated on completion.
  • Because any fatal QP error flushes the QP, a single bad key fails every outstanding command on that NVMe queue, not just one.
  • Per-I/O fast registration versus pre-registered memory, and whether remote invalidation is requested.
  • SRQ use, receive buffer counts and in-capsule data size on the target.
  • RDMA READ depth (initiator depth and responder resources negotiated by RDMA_CM).
  • RoCE congestion control (DCQCN or vendor equivalents), PFC priorities, DSCP marking.
  • RNR and transport retry counts and timeouts.
  • NVMe/RDMA was defined in NVMe over Fabrics 1.0 (2016) and became a standalone transport specification in the 2.0 restructuring. The 2.4 set includes RDMA Transport 1.3.
  • Later revisions added fields to the CM private data (for example a controller ID in REQ). Older targets ignore them. Confirm in spec
  • RoCE v2 is an IBTA annex, revised independently of NVMe.
  • The NVMe specifications do not define RDMA packet formats, ACK/NAK codes or RNR timer encodings. Those belong to IBTA and the IETF.
  • They do not require a lossless network, nor specify PFC/ECN configuration.
  • They do not say how a host should register memory, only what the keyed descriptor carries.
  • Numeric REJ status values and exact private-data offsets must be read from RDMA Transport 1.3.
  • Never assume an rkey is valid after the command completes.
  • Never assume a missing response capsule means the target did not run the command. A QP error can flush the response after the data was written.
  • Never assume RoCE "works" on a network just because ping works. Lossless or congestion configuration is invisible to ping.

Ordering

  • Within one RC QP, operations execute in order. An RDMA WRITE posted before a SEND is placed in host memory before the SEND's receive completes. This is why the response capsule can safely follow the data without an extra handshake.
  • RDMA READ is the exception that needs care. A later SEND may overtake an earlier RDMA READ's completion unless the target waits for the READ to complete (or uses a fence) before posting dependent work. Targets always wait for the READ completion before executing the write, so this is natural in NVMe.
  • Across QPs (NVMe queues), there is no ordering, as on PCIe and TCP.

Reasoning

  1. Layer. No PSN gaps or retransmissions occurred, so the network is fine. The NAK type, Remote Access Error, is a protection check: key, bounds or rights.
  2. Which check failed? The rkey 0x0001C3D4 in the RETH matches the one in the SQE, so the target used the key it was given. The VA matches. The NAK PSN is 0x5C3500, the start of the WRITE message. The responder rejects the whole message, so the PSN alone does not show which part was out of bounds.
  3. Hypotheses. (a) The host registered fewer bytes than it advertised (MR 4 KiB, SGL 8 KiB). (b) The key was invalidated before use, for example by a host-side timeout path. (c) The MR lacked remote-write permission.
  4. Evidence. Host-side driver tracing of the registration WR for this request (mapped length), and rdma resource show mr during a reproduction. A host-side abort or timeout for CID 0x0090 before frame 3 would support (b). Nothing like that appears here.
  5. Likely conclusion (synthetic case): the host built the keyed SGL from the request length but mapped only the first scatterlist segment into the MR. This is a host driver bug in partial-mapping handling. Fix: fail or split the request when the MR mapping returns fewer bytes than requested. Regression test: I/O with highly fragmented buffers that exceed the MR's page-list capacity.

The collateral damage is the lesson. CID 0x0091 was innocent, but it failed too because it shared the QP. On PCIe, one bad PRP fails one command. On RDMA, one bad key fails a whole NVMe queue and triggers a controller-wide reconnect. Correlated failures across all commands on one queue are an RDMA signature.

Code / pseudocode

The simulation below models what matters for reasoning about NVMe/RDMA without real verbs. A host has memory and a table of registered regions keyed by rkey. A target can only RDMA READ or WRITE through those keys. Keyed SGL descriptors are encoded byte-exactly, and SEND with Invalidate revokes keys. Case 3 reproduces the stale-key failure. Standard library only, runs as written.

#!/usr/bin/env python3
"""nvme_rdma_sim.py - a toy model of NVMe/RDMA data movement (simulation, not real verbs).
Shows keyed SGL descriptors, memory registration, RDMA READ/WRITE against registered
regions, SEND with Invalidate, and what a stale remote key does."""
import struct, itertools

def keyed_sgl(addr, length, key, invalidate):
    """Keyed SGL Data Block descriptor: type 4h, subtype 0h (address) or Fh (invalidate key)."""
    ident = (0x4 << 4) | (0xF if invalidate else 0x0)
    return struct.pack("<Q", addr) + length.to_bytes(3, "little") + struct.pack("<I", key) + bytes([ident])

def parse_keyed_sgl(d):
    addr, = struct.unpack_from("<Q", d, 0)
    length = int.from_bytes(d[8:11], "little")
    key, = struct.unpack_from("<I", d, 11)
    return addr, length, key, d[15]

class RemoteAccessError(Exception):
    pass

class HostMemory:
    """Host side: buffers and the RNIC's table of registered regions (rkey -> window)."""
    def __init__(self):
        self.mem = bytearray(1 << 20)
        self.regions = {}
        self._keys = itertools.count(0x1A2B00)

    def register(self, addr, length):              # like a fast-registration work request
        key = next(self._keys)
        self.regions[key] = (addr, length)
        return key

    def invalidate(self, key):                     # local invalidate or remote SEND w/ Invalidate
        self.regions.pop(key, None)

    def check(self, key, addr, length):
        win = self.regions.get(key)
        if not win or addr < win[0] or addr + length > win[0] + win[1]:
            raise RemoteAccessError(f"NAK Remote Access Error (rkey 0x{key:06X}, addr 0x{addr:X}, len {length})")

    # what the target's RNIC can do to host memory, and nothing else:
    def rdma_write(self, key, addr, data):
        self.check(key, addr, len(data)); self.mem[addr:addr + len(data)] = data

    def rdma_read(self, key, addr, length):
        self.check(key, addr, length); return bytes(self.mem[addr:addr + length])

class Target:
    def __init__(self, host):
        self.host, self.media = host, bytearray(1 << 20)

    def on_send(self, capsule):                    # a SEND carrying a command capsule arrived
        opc, cid = capsule[0], struct.unpack_from("<H", capsule, 2)[0]
        addr, length, key, ident = parse_keyed_sgl(capsule[24:40])
        slba, = struct.unpack_from("<Q", capsule, 40)
        off = slba * 512
        log = [f"  target: SEND received, opcode {opc:02X}h CID 0x{cid:04X}, keyed SGL id {ident:02X}h addr 0x{addr:X} len {length} key 0x{key:06X}"]
        try:
            if opc == 0x02:                         # Read: media -> RDMA WRITE into host buffer
                self.host.rdma_write(key, addr, self.media[off:off + length])
                log.append(f"  target: RDMA WRITE {length} B -> host 0x{addr:X}")
            elif opc == 0x01:                       # Write: RDMA READ from host buffer -> media
                self.media[off:off + length] = self.host.rdma_read(key, addr, length)
                log.append(f"  target: RDMA READ {length} B <- host 0x{addr:X}")
            status = 0
        except RemoteAccessError as e:
            log.append(f"  host RNIC rejects the access: {e}; the QP moves to Error, outstanding work is flushed")
            return log, None
        if ident & 0xF == 0xF:
            self.host.invalidate(key)
            log.append(f"  target: SEND with Invalidate (rkey 0x{key:06X}) carrying response capsule")
        else:
            log.append("  target: SEND carrying response capsule")
        return log, status

def sqe(opc, cid, slba, sgl):
    s = bytearray(64)
    struct.pack_into("<BBHI", s, 0, opc, 0x40, cid, 1)     # PSDT=SGL, NSID 1
    s[24:40] = sgl
    struct.pack_into("<Q", s, 40, slba)
    return bytes(s)

if __name__ == "__main__":

What to notice

  • The SGL identifier is 4Fh: Keyed Data Block (4h) with the Invalidate Key subtype (Fh). The key bytes 00 2b 1a 00 are little-endian for 0x001A2B00.
  • For the write, the target pulls the data. The host does nothing between sending the capsule and receiving the response.
  • After SEND with Invalidate, the key is gone. Case 3 shows that reuse is caught by the host-side check, and that the failure is a connection-level event with no response capsule, not an NVMe status.

Worked example

Problem. Compare a 128 KiB write over NVMe/RDMA (RoCE v2, path MTU 4096, 25 Gb/s) and over NVMe/TCP (MTU 9000) on the same network, where the one-way propagation and switching delay is 5 µs. Count round trips and estimate the wire time for the data phase.

Round trips

  • RDMA: SEND(capsule) → target posts RDMA READ request → host RNIC streams READ responses → target writes to media → SEND(response). Network legs: capsule (1), READ request (2), READ response (3), response capsule (4). That is two round trips.
  • TCP: CapsuleCmd → R2T → H2CData → CapsuleResp. Also four legs, two round trips.

Same round-trip count. RDMA's advantage is not fewer round trips. It is that the host CPU does no copying and no per-packet processing, and that each leg is processed by hardware with less latency jitter.

Wire time for 128 KiB of data at 25 Gb/s

T = 8 × (D + N × H) / R
T
serialization time of the data phase, in seconds
D
data bytes (131,072)
N
number of packets carrying the data
H
per-packet overhead in bytes, including Ethernet preamble, start delimiter, FCS and inter-frame gap (24 bytes)
R
link rate in bits per second (25 × 109)

RoCE v2: 32 READ response packets of 4096 bytes. H = 58 (headers incl. ICRC) + 4 (AETH on first/last/only responses; ignore for middle packets) + 24 ≈ 84. T ≈ 8 × (131,072 + 32 × 84) / 25e9 ≈ 8 × 133,760 / 25e9 ≈ 42.8 µs.

NVMe/TCP, jumbo frames: one H2CData PDU of 131,096 bytes (no digests) in ⌈131,096 / 8,948⌉ = 15 segments. H = 66 + 24 = 90. T ≈ 8 × (131,096 + 15 × 90) / 25e9 ≈ 8 × 132,446 / 25e9 ≈ 42.4 µs.

On the wire they are essentially equal. The difference between transports is end-host processing: CPU cycles, copies, interrupt handling and scheduling jitter. RDMA wins those by a wide margin, and that is where its latency and efficiency advantage comes from. Derived

When someone claims "RDMA is faster because it is RDMA", ask "faster at what?" On the wire, no. In host CPU per I/O and tail latency under load, usually yes. In tolerance of lossy networks, no: RoCE suffers badly from loss, while TCP and iWARP cope.

Senior engineer insight

Because a protection error or retry exhaustion takes down the whole QP, and NVMe recovery resets the whole controller association, a single malformed I/O can stall every application using that path for the reconnect time. With native NVMe multipathing (see Fabric Architecture) I/O fails over, but the root cause is often hidden behind "path flapped". Senior engineers keep the first QP error event with its WC status, because that is the evidence that survives the reconnect.

RoCE deployments succeed or fail on network engineering: priority mapping, PFC on exactly one priority, ECN thresholds, congestion control tuning, and buffer headroom. Storage teams that treat the network as "someone else's problem" see unexplained latency tails. Bring network counters into every storage incident review.

Per-I/O keys with remote invalidation give each command a capability that dies with it. Design reviews of NVMe/RDMA hosts should ask: what memory is exposed, to whom, for how long, and what happens on timeout paths where the host gives up on a command but the target may still write?

The ACKs. In RoCE they are generated by the RNIC (here, rxe in software) and coalesced. Their timing tells you about the receiver's transport layer, not about NVMe processing. Answers
  1. Address 0x0000_0002_0001_0000. Length 0x020000 = 131,072 (128 KiB). Key 0x00556677. Identifier 40h: Keyed Data Block, Address subtype (no remote invalidation requested).
  2. 16 KiB > 4 KiB, so not in-capsule. Host: [REG_MR] + SEND(capsule, keyed SGL). Target: RDMA READ request → READ responses (4 at PMTU 4096). Target writes to media → SEND with Invalidate (response). Plus RNIC ACKs.
  3. The RDMA transport protects every packet end to end between RNICs with the ICRC (RoCE/IB) or MPA CRC (iWARP), and the RC service guarantees delivery. Corruption inside the endpoints is still possible, but the network path is already covered.
  4. Over PCIe, a receiver that cannot accept a posted write withholds flow-control credits, and the sender simply waits. RNR is similar in spirit: "no receive buffer, try later". But it is a NAK followed by a timer-based retry, and it consumes a retry budget. Exhaust it and the QP fails, which never happens to PCIe credit waits.
  5. Under load, more response capsules than posted receives can arrive. Expect RNR NAKs on the host side, latency spikes in multiples of the RNR timer, and possibly QP failure when RNR retries are exhausted. A correct host never allows more outstanding commands than it has receives.

Quiz

  1. Which RDMA operation carries a command capsule?

    • SEND
    • RDMA WRITE
    • RDMA READ
    • Atomic Compare-and-Swap
    Answer and reasoning

    Capsules are messages delivered into posted receive buffers via SEND.

  2. Who issues the RDMA READ that fetches write data?

    • The host
    • The target
    • The switch
    • The subnet manager
    Answer and reasoning

    The target initiates all data operations, mirroring the PCIe controller's role as DMA master.

  3. SGL identifier 4Fh means:

    • Data Block, Offset
    • Transport Data Block
    • Keyed Data Block, Invalidate Key
    • Last Segment
    Answer and reasoning

    Type 4h (Keyed SGL Data Block), subtype Fh (Invalidate Key).

  4. Which RDMA transport service does NVMe/RDMA use?

    • Unreliable Datagram
    • Unreliable Connected
    • Reliable Datagram
    • Reliable Connected
    Answer and reasoning

    RC: connected, reliable, in order. One QP per NVMe queue pair.

  5. RoCE v2 packets are identified on the wire by:

    • TCP port 4420
    • UDP destination port 4791
    • EtherType 0x8915 only
    • TCP port 8009
    Answer and reasoning

    RoCE v2 uses UDP/IP with destination port 4791. EtherType 0x8915 is RoCE v1. 4420 is the NVMe-oF service port in the RDMA_CM port space and for TCP.

  6. A NAK with Remote Access Error causes:

    • A retry of the same packet
    • An NVMe status in the response capsule
    • The QP to enter the error state, flushing outstanding work
    • Nothing: it is informational
    Answer and reasoning

    Protection errors are fatal to the QP. The NVMe host must recover the queue (usually the whole controller).

  7. What carries the NVMe queue ID during NVMe/RDMA connection setup, before the Connect command?

    • RDMA_CM REQ private data
    • ICReq PDU
    • The BTH
    • The Discovery Log Page
    Answer and reasoning

    NVMe/RDMA defines CM private data (RECFMT, QID, HRQSIZE, HSQSIZE). ICReq is NVMe/TCP.

  8. Why can't tcpdump normally see NVMe/RDMA traffic on a hardware RNIC?

    • It is encrypted
    • It uses a different MAC address
    • It uses IPv6 only
    • The RNIC sends and receives it without the kernel network stack
    Answer and reasoning

    Kernel bypass is the point of RDMA. Use taps or mirror ports, vendor sniffer features, or Soft-RoCE.

  9. Open: why does NVMe/RDMA's write path have the same round-trip count as NVMe/TCP's R2T path, and where is the advantage?

    Model answer

    Both require the target to solicit data (RDMA READ request vs R2T) and the host side to deliver it, then a response: two round trips. RDMA's advantage is that the host RNIC serves the READ without host CPU involvement or copies, giving lower CPU cost and less latency variance.

  10. Open: what is the risk of a host completing an I/O to the application before the rkey is invalidated?

    Model answer

    The buffer may be reused for other data while the remote target still holds a valid key. A delayed or buggy RDMA WRITE could then corrupt unrelated data, or a READ could leak it. The host must ensure invalidation, remote or local, completes first.

Interview questions

  1. Beginner: What is RDMA in one paragraph?

    Model answer

    A networking model in which an adapter reads and writes memory on a remote machine, within regions the remote side registered and named with keys, without the remote CPU copying data. It relies on queue pairs, work requests and completion queues managed by RDMA-capable NICs, over InfiniBand, RoCE or iWARP.

  2. Beginner: How does NVMe map onto RDMA?

    Model answer

    One RC QP per NVMe queue pair. Command and response capsules travel by SEND. Read data goes by target RDMA WRITE, and write data by target RDMA READ (or in-capsule). Host buffers are described by Keyed SGL descriptors with address, length and rkey.

  3. Intermediate: Explain memory registration and why per-I/O registration is preferred.

    Model answer

    Registration pins pages, loads translations into the RNIC and creates keys with access rights. Per-I/O fast registration limits exposure to the buffers of in-flight commands and invalidates keys at completion. Global registration exposes all memory permanently, which is a security and fault-containment risk.

  4. Intermediate: Compare RoCE v2 and iWARP for NVMe/RDMA.

    Model answer

    RoCE v2 runs IB transport over UDP/IP, needs well-engineered (often lossless or ECN-managed) Ethernet, and offers low latency with go-back-N loss recovery. iWARP runs RDMA over TCP, tolerates lossy and routed networks, and has historically had less vendor adoption. NVMe-level behaviour is identical.

  5. Advanced: All commands on one I/O queue failed at once, followed by a reconnect. What do you suspect and how do you prove it?

    Model answer

    A QP-fatal event: remote access error, retry exceeded, RNR retries exceeded, or local protection error. Get the first verbs WC error status from host and target logs, capture the NAK type if possible, and compare the keyed SGL with the RETH. Check network counters for loss. The first WC error identifies the class.

  6. Advanced: Why does SEND with Invalidate exist, and what does it save?

    Model answer

    It combines delivering the response capsule with invalidating the host's rkey, saving the host a Local Invalidate work request and its completion per I/O. This reduces latency and CPU, and closes the exposure window at the moment the target declares completion.

  7. Senior: Design the network requirements for a RoCE v2 NVMe/RDMA deployment.

    Model answer

    A dedicated traffic class for RoCE with consistent DSCP/PCP mapping. PFC enabled only on that priority with sufficient headroom, or ECN-based congestion control (DCQCN-like) with correctly tuned marking thresholds. Consistent MTU, pause-storm protection (watchdogs), monitoring of CNPs, pauses and drops, and failure-domain separation with multipathing across two fabrics.

  8. Senior: What would you validate in an NVMe/RDMA target before shipping?

    Model answer

    Correct use of keys (never beyond SGL length, never after completion), handling of multiple keyed descriptors up to MSDBD, in-capsule boundaries, CM private-data validation and REJ reasons, behaviour on QP errors (cleanup, no leaks), RNR avoidance under maximum queue depth, interoperability across RoCE v2, iWARP and IB, and recovery during network loss and congestion.

Chapter summary

  • RDMA lets RNICs move data directly between registered memory regions, protected by keys, without CPU copies.
  • NVMe/RDMA maps each NVMe queue pair to one Reliable Connected QP. Capsules travel by SEND. The target moves data with RDMA WRITE (reads) and RDMA READ (writes).
  • Keyed SGL Data Block descriptors (40h, or 4Fh with Invalidate Key) carry address, length and rkey inside the SQE.
  • RDMA_CM, with NVMe private data (QID, queue sizes), establishes each QP before the NVMe Connect.
  • InfiniBand, RoCE v2 and iWARP differ in layering and loss handling, not in NVMe behaviour.
  • QP-fatal errors (remote access, retry exceeded, RNR exhausted) fail all commands on the queue and trigger reconnect.
