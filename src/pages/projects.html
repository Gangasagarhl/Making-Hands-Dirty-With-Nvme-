Twelve projects that turn reading into building. Each one produces something you keep — a diagram, a decoder, a simulator, an analysis pipeline — and each has a goal, requirements, an architecture, deliverables, milestones, a starter code sketch, expected output, acceptance tests, failure cases and stretch goals. Together they add up to the tools a senior NVMe and PCI Express (PCIe) protocol engineer carries around.

Why projects

You can read about Phase Tags for a week and still be surprised the first time a simulated Completion Queue (CQ) wraps. Building forces every vague idea to become a decision: which bit, which byte order, which side owns which pointer, what happens on the edge. When your code disagrees with the specification, you learn something; when your code disagrees with a trace, you learn something more.

The projects are ordered. Projects 1–4 build decoders and mental models; 5–7 build simulators of the NVM Express (NVMe) queue and Direct Memory Access (DMA) machinery; 8–10 connect NVMe commands to PCIe Transaction Layer Packets (TLPs) and automate analysis; 11–12 build classifiers and a debugging assistant. Later projects reuse earlier ones, so keep everything in one repository.

Learning objectives

  • Turn specification tables into tested decoders with revision-aware field handling.
  • Simulate queue, doorbell and DMA behaviour well enough to predict real traces.
  • Correlate NVMe commands with the PCIe transactions that carry them.
  • Build automated summaries, classifiers and evidence-based reports on top of deterministic parsing.
  • Write acceptance tests that encode protocol knowledge, including failure cases.

Prerequisites

Python 3 and basic Git. The concepts come from TLP Header Anatomy, Configuration Space, Queue Architecture, Doorbells, NVMe Command Structure, Physical Region Pages and Command-to-TLP Correlation. The Specification Reading School notebook (field dictionary, command matrix, trace mapping) is the raw material for Projects 2–4.

Shared conventions

  • One repository, one Python package per project (p01_model/ … p12_assistant/), standard library only unless a stretch goal says otherwise.
  • The course lab system (Gen4 x4, BAR0 at 0xFE60_0000, Requester ID 0x0100, MPS 256 B, MRRS 512 B, I/O SQ1 at IOVA 0x1_2340_0000, CQ1 at 0x1_2341_0000) is the default input. All inputs you create are synthetic; label them so.
  • Every decoder output field carries its source: the document and section name it came from, and the revision.
  • Tests first for edge cases: 0's based fields, wraparound, reserved bits, the 4 KiB boundary.
  • No device writes. All projects run on files and simulations. Where a project touches a real system, it is read-only inspection.

All twelve projects are Safe lab work: offline files, simulations and read-only inspection. Project 9 uses a real capture file but never drives hardware.

Project 1 — Build an NVMe mental model

Goal

Produce a single diagram and a written walk-through that trace one 4 KiB Read from the application's read() call to the moment the application has the data — through driver, memory, Submission Queue Entry (SQE), doorbell, TLPs, controller, NAND, data DMA, Completion Queue Entry (CQE), interrupt and back. This is the scaffold every other project hangs on.

Requirements

  • Every step names the actor, the location of state it changes (host memory, controller register, controller internal), the direction of any PCIe traffic, and the evidence an engineer could observe.
  • Every PCIe transaction is labelled posted or non-posted.
  • Every value uses the course lab system's addresses.
  • Each step is tagged with the owning specification (NVMe Base, NVM Command Set, NVMe over PCIe Transport, PCIe Base, or Linux implementation).

Architecture

Applicationread(fd, buf, 4096)
Block layer + NVMe driverbuild SQE, choose CID, map buffer (IOVA)
Host memorySQ1 slot, data buffer, CQ1 slot
PCIe linkMWr doorbell → MRd SQE → CplD → MWr data ×16 → MWr CQE → MWr MSI-X
NVMe controllerfetch, parse, schedule, NAND read, DMA, complete

Deliverables

  1. A sequence diagram (hand-drawn or SVG) with all actors.
  2. A step table: step · actor · state changed · location · PCIe transaction · direction · posted? · evidence · owning spec.
  3. A one-page narrative explaining the flow to a junior engineer.
  4. A "what if it breaks here" column with one failure per step.

Milestones

  1. Draft from memory (no references). Keep it; you will compare later.
  2. Correct it using The Most Important Chapter and the reading notes.
  3. Add evidence and failure columns.
  4. Review with a peer; explain it without notes in ten minutes.

Starter sketch

step | actor      | state changed        | location     | PCIe txn          | dir      | posted | evidence                  | spec
1    | driver     | SQE written slot 5   | host memory  | none              | -        | -      | (memory only)             | Base
2    | driver     | SQ1 tail = 6         | ctrl reg     | MWr BAR0+0x1008   | host→dev | yes    | analyzer MWr, 1 DW        | PCIe Transport + PCIe
3    | controller | fetch SQE            | ctrl internal| MRd 0x1_2340_0140 | dev→host | no     | MRd + CplD (tag match)    | PCIe
...
n    | driver     | CQ1 head = k         | ctrl reg     | MWr BAR0+0x100C   | host→dev | yes    | analyzer MWr              | PCIe Transport

Expected output

Around fifteen steps. The data movement step should state sixteen 256-byte Memory Writes (MPS limited) for an aligned 4 KiB buffer, and the CQE write must come after the data writes.

Acceptance tests

  • Every PCIe transaction has a direction and posted/non-posted label.
  • The doorbell write is shown as host→device and posted.
  • The SQE fetch is a non-posted read with a completion carrying 64 bytes.
  • The diagram explains why the CQE is not overtaken by the data writes (PCIe ordering for posted writes).
  • The interrupt is identified as an MSI-X Memory Write, not a wire.
  • At least one step is marked "not observable on PCIe" (for example, NAND read inside the controller).

Failure cases to include

  • Doorbell written before the SQE is visible in memory (missing write barrier) → controller fetches stale SQE.
  • IOMMU mapping missing → data writes rejected; controller reports a data transfer error.
  • MSI-X masked → CQE present, no interrupt, completion found only by polling.

Stretch goals

Repeat for a Write (device reads data: MRd + CplD) and for a Write with a PRP list. Repeat for NVMe/TCP and mark which steps disappear and which appear.

Project 2 — Decode PCIe configuration space

Goal

A decoder that takes a configuration-space hex dump (the format lspci -xxx or -xxxx prints) and produces a human-readable, cited report of the Type 0 header and the capability lists, including the fields NVMe engineers care about: class code, BAR0, MSI-X table location and size, Max Payload Size (MPS), Max Read Request Size (MRRS), link speed and width, and AER status.

Requirements

  • Little-endian field assembly; register attribute (RO/RW/RW1C…) shown for each decoded field.
  • Walk the standard capability list from the Capabilities Pointer and the extended list from offset 100h.
  • Loop protection: stop on revisits or pointers outside range.
  • Unknown capability IDs are printed raw, never guessed.
  • Every field cites the PCI Express Base Specification by section name, and the revision family you used.

Architecture

Parser (hex dump → 4096-byte array) → header decoder → capability walker → per-capability decoders (registry keyed by ID) → report renderer (text and JSON).

Deliverables

cfgdecode.py, a test suite with at least six synthetic dumps (including malformed ones), and a JSON output schema.

Milestones

  1. Header only.
  2. Standard capability walk.
  3. MSI-X and PCI Express capability decode.
  4. Extended capabilities including AER.
  5. JSON output + tests.

Starter code

A runnable first milestone, working on a synthetic dump of the course lab SSD (vendor and device IDs are the ones QEMU's emulated NVMe controller uses, so you can compare against a QEMU guest).

# cfgdecode.py - decode a Type 0 configuration header and walk the capability list.
# Input: synthetic dump of the course lab SSD (IDs as QEMU's emulated NVMe uses).
DUMP = """
00: 36 1b 10 00 06 04 10 00 02 02 08 01 00 00 00 00
10: 04 00 60 fe 00 00 00 00 00 00 00 00 00 00 00 00
20: 00 00 00 00 00 00 00 00 00 00 00 00 36 1b 00 11
30: 00 00 00 00 40 00 00 00 00 00 00 00 0b 01 00 00
40: 01 50 03 00 08 00 00 00 00 00 00 00 00 00 00 00
50: 11 60 20 80 00 20 00 00 00 30 00 00 00 00 00 00
60: 10 00 02 00 00 80 00 10 30 28 10 00 44 7c 41 00
70: 00 00 44 10 00 00 00 00 00 00 00 00 00 00 00 00
"""
cfg = bytearray(256)
for line in DUMP.strip().splitlines():
    off, data = line.split(":")
    for i, b in enumerate(data.split()):
        cfg[int(off, 16) + i] = int(b, 16)

def r8(o):  return cfg[o]
def r16(o): return cfg[o] | cfg[o + 1] << 8          # little-endian
def r32(o): return r16(o) | r16(o + 2) << 16

print(f"Vendor ID 0x{r16(0x00):04X}  Device ID 0x{r16(0x02):04X}")
print(f"Command 0x{r16(0x04):04X}: MemSpace={r16(4)>>1&1} BusMaster={r16(4)>>2&1}")
print(f"Status  0x{r16(0x06):04X}: CapList={r16(6)>>4&1}")
cc = (r8(0x0B), r8(0x0A), r8(0x09))
print(f"Class code {cc[0]:02X}h/{cc[1]:02X}h/{cc[2]:02X}h  (01/08/02 = mass storage / NVM / NVMe)")
print(f"Header type 0x{r8(0x0E):02X}")
bar0 = r32(0x10)
if bar0 & 1 == 0:
    typ = (bar0 >> 1) & 3
    base = bar0 & ~0xF
    if typ == 2:
        base |= r32(0x14) << 32
    print(f"BAR0 memory, {'64' if typ == 2 else '32'}-bit, prefetchable={bar0>>3&1}, base=0x{base:X}")
ptr = r8(0x34) & 0xFC
names = {0x01: "Power Management", 0x05: "MSI", 0x10: "PCI Express", 0x11: "MSI-X"}
while ptr:
    cid, nxt = r8(ptr), r8(ptr + 1) & 0xFC
    print(f"cap @0x{ptr:02X}: ID 0x{cid:02X} {names.get(cid, '?')}  next=0x{nxt:02X}")
    if cid == 0x11:
        mc = r16(ptr + 2)
        t, p = r32(ptr + 4), r32(ptr + 8)
        print(f"   MSI-X enable={mc>>15&1} table size={(mc & 0x7FF) + 1} (field is N-1)")
        print(f"   table BIR={t&7} offset=0x{t&~7:X};  PBA BIR={p&7} offset=0x{p&~7:X}")
    if cid == 0x10:
        devctl = r16(ptr + 8)
        lnksta = r16(ptr + 0x12)
        print(f"   DevCtl MPS={128 << (devctl>>5 & 7)} B  MRRS={128 << (devctl>>12 & 7)} B")
        print(f"   LnkSta speed code={lnksta & 0xF} width=x{lnksta>>4 & 0x3F}")
    ptr = nxt

Acceptance tests

  • Class code decodes to 01h/08h/02h for an NVMe I/O controller.
  • A 64-bit BAR combines BAR0 and BAR1; type bits are reported.
  • MSI-X table size is reported as field + 1.
  • MPS/MRRS encodings 000b–101b map to 128–4096 bytes.
  • A capability list that loops back to itself terminates with an error, not a hang.
  • A dump with only 64 bytes (non-root lspci -x) reports "capabilities not available" rather than decoding zeros.

Failure cases

  • Reading the dump as big-endian: vendor ID 0x361B instead of 0x1B36.
  • Forgetting to mask the low two bits of capability pointers.
  • Reporting negotiated speed from Link Capabilities instead of Link Status.

Project 3 — Build a TLP decoder

Goal

A decoder for non-Flit-mode TLP headers (the 3DW and 4DW formats used up to and including 32 GT/s): memory requests, completions, configuration requests and messages, with field-level output and validation warnings.

Requirements

  • Input: header DWORDs as analyzers usually print them (big-endian byte order within each DWORD as drawn in the PCIe Base Specification).
  • Decode Fmt/Type, TC, Attr (RO, NS, IDO), TD, EP, Length (0 means 1024 DW), Requester ID, Tag, byte enables, address; for completions Completer ID, status, BCM, Byte Count, Lower Address.
  • Validate: 4DW header with address below 4 GiB (should use 3DW), Length 1 with Last DW BE non-zero, request crossing a 4 KiB boundary, payload above MPS.
  • Flit-mode headers (64 GT/s and above) are out of scope; detect and refuse them rather than misdecode.

Architecture

Header reader → DW0 dispatcher by Fmt/Type → per-type decoder → validator → formatter. Keep the Fmt/Type table as data so it can be updated per revision.

Starter code

# tlpdecode.py - decode non-Flit TLP headers given as big-endian DWORDs (as analyzers print them).
FMT = {0: "3DW, no data", 1: "4DW, no data", 2: "3DW, with data", 3: "4DW, with data"}
CPL_STATUS = {0: "SC", 1: "UR", 2: "CRS", 4: "CA"}

def tlp_name(fmt, typ):
    if typ == 0x00: return {0: "MRd32", 1: "MRd64", 2: "MWr32", 3: "MWr64"}[fmt]
    if typ == 0x0A: return "CplD" if fmt & 2 else "Cpl"
    if typ == 0x04: return "CfgWr0" if fmt & 2 else "CfgRd0"
    if typ & 0x18 == 0x10: return "MsgD" if fmt & 2 else "Msg"
    return f"type 0x{typ:02X} (not decoded here)"

def decode(dws):
    d0 = dws[0]
    fmt, typ = d0 >> 29 & 7, d0 >> 24 & 0x1F
    out = {"name": tlp_name(fmt, typ), "fmt": FMT.get(fmt, "prefix/other"),
           "tc": d0 >> 20 & 7, "td": d0 >> 15 & 1, "ep": d0 >> 14 & 1,
           "ro": d0 >> 13 & 1, "ns": d0 >> 12 & 1}      # Attr[1:0] = bits 13:12
    if fmt & 2 or typ == 0x00:                          # Length is meaningful here
        out["len_dw"] = d0 & 0x3FF or 1024              # 0 encodes 1024 DW
    if typ == 0x00:
        d1 = dws[1]
        out.update(req_id=f"{d1>>16:04X}", tag=f"0x{d1>>8 & 0xFF:02X}",
                   last_be=f"{d1>>4 & 0xF:04b}", first_be=f"{d1 & 0xF:04b}")
        addr = (dws[2] << 32 | dws[3]) if fmt & 1 else dws[2]
        out["addr"] = f"0x{addr & ~3:X}"
    elif typ == 0x0A:
        d1, d2 = dws[1], dws[2]
        out.update(cpl_id=f"{d1>>16:04X}", status=CPL_STATUS.get(d1 >> 13 & 7, "reserved"),
                   byte_count=d1 & 0xFFF or 4096, req_id=f"{d2>>16:04X}",
                   tag=f"0x{d2>>8 & 0xFF:02X}", lower_addr=f"0x{d2 & 0x7F:02X}")
    return out

samples = {
    "doorbell (RC->dev)":  [0x40000001, 0x0009000F, 0xFE601008],
    "SQE fetch (dev->RC)": [0x20000010, 0x01001AFF, 0x00000001, 0x23400000],
    "data for SQE":        [0x4A000010, 0x00090040, 0x01001A00],
    "UR completion":       [0x0A000000, 0x00092200, 0x01001300],
}
for k, v in samples.items():
    print(f"{k:22s}", decode(v))

Notice what the decoder has to know that the bits alone do not tell it: that 0xFE60_1008 is the SQ1 tail doorbell, or that 0x1_2340_0000 is the SQ1 base. That context comes from the configuration (Project 2) and from the driver's queue setup — which is the whole point of Project 8.

Acceptance tests

  • All four Fmt values for memory requests decode to the right name.
  • Length 0 decodes as 1024 DW.
  • Completion status 001b decodes as UR, 100b as CA, 010b as CRS.
  • A completion with Byte Count equal to its payload is flagged as the last completion of its request.
  • A 4DW MRd with an address below 4 GiB raises a warning.
  • An unknown Type value is printed raw, not guessed.

Failure cases

  • Reading the address's low two bits as address (they are reserved / used differently).
  • Treating the tag of a posted MWr as meaningful for matching.
  • Ignoring 10-bit tag bits when 10-bit tags are enabled.

Stretch goals

10-bit tag support; decode Msg routing and common message codes (ERR_COR, ERR_NONFATAL, ERR_FATAL); a Flit-mode decoder written from the PCIe 6.x text.

Project 4 — Build an NVMe command decoder

Goal

Decode 64-byte SQEs and 16-byte CQEs for Admin and NVM I/O commands, using your field dictionary and command matrix as data.

Requirements

  • Input as 16 little-endian Dwords (SQE) or 4 Dwords (CQE), or raw bytes from a TLP payload.
  • Admin vs I/O must be explicit (the same opcode means different commands). The command set must be explicit for I/O.
  • 0's based fields printed both raw and as quantities.
  • Command-specific status decoded only with the opcode.
  • Unknown opcodes and reserved non-zero bits are reported, not hidden.

Architecture

Byte reader → common-field decoder (CDW0, NSID, MPTR, DPTR) → command registry keyed by (queue type, command set, opcode) → command-specific decoder → status decoder keyed by (SCT, SC, opcode).

Starter code

# sqedecode.py - decode a 64-byte NVMe Submission Queue Entry given as 16 little-endian Dwords.
ADMIN = {0x01: "Create I/O SQ", 0x02: "Get Log Page", 0x05: "Create I/O CQ", 0x06: "Identify"}
NVM_IO = {0x00: "Flush", 0x01: "Write", 0x02: "Read", 0x09: "Dataset Management"}

def decode_sqe(dw, admin=False):
    opc = dw[0] & 0xFF
    out = {"opc": f"0x{opc:02X}",
           "name": (ADMIN if admin else NVM_IO).get(opc, "unknown to this decoder"),
           "fuse": dw[0] >> 8 & 3, "psdt": dw[0] >> 14 & 3, "cid": f"0x{dw[0] >> 16:04X}",
           "nsid": dw[1], "mptr": f"0x{dw[5] << 32 | dw[4]:X}",
           "prp1": f"0x{dw[7] << 32 | dw[6]:X}", "prp2": f"0x{dw[9] << 32 | dw[8]:X}"}
    if not admin and opc in (0x01, 0x02):
        nlb0 = dw[12] & 0xFFFF
        out.update(slba=f"0x{dw[11] << 32 | dw[10]:X}", nlb_field=nlb0,
                   blocks=nlb0 + 1,                       # NLB is 0's based
                   fua=dw[12] >> 30 & 1, lr=dw[12] >> 31 & 1)
    if admin and opc == 0x05:
        out.update(qid=dw[10] & 0xFFFF, qsize_entries=(dw[10] >> 16) + 1,
                   iv=dw[11] >> 16, ien=dw[11] >> 1 & 1, pc=dw[11] & 1)
    if admin and opc == 0x06:
        out.update(cns=dw[10] & 0xFF)
    return out

read_sqe = [0x00400002, 1, 0, 0, 0, 0, 0x00000000, 0x2, 0, 0, 0x1000, 0, 7, 0, 0, 0]
ccq_sqe  = [0x00030005, 0, 0, 0, 0, 0, 0x23410000, 0x1, 0, 0, 0x03FF0001, 0x00010003, 0, 0, 0, 0]
print(decode_sqe(read_sqe))
print(decode_sqe(ccq_sqe, admin=True))

Acceptance tests

  • Read with NLB=7 reports 8 blocks.
  • Opcode 02h decodes as Read on an I/O queue and as Get Log Page on the Admin queue.
  • Create I/O CQ with QSIZE field 3FFh reports 1024 entries.
  • PSDT ≠ 0 switches DPTR decoding to SGL (or reports "SGL decoding not implemented").
  • CQE with SCT=1h and no opcode context prints "command-specific; opcode required".
  • Bytes taken from a CplD payload produce the same decode as the Dword form.

Failure cases

  • Decoding Admin opcodes with the I/O table.
  • Forgetting that SLBA spans CDW10 (low) and CDW11 (high).
  • Mis-assembling Dwords from payload bytes (byte order).

Stretch goals

Generate the decoder tables from your field dictionary (CSV → Python); add Identify data structure decoding; add SGL descriptor decoding.

Project 5 — Simulate Submission and Completion Queues

Goal

A simulator of one or more SQ/CQ pairs that models head and tail ownership, full and empty conditions, wraparound and the Phase Tag, and prints the PCIe-visible events each step would cause.

Requirements

  • The host owns the SQ tail and CQ head; the controller owns the SQ head and CQ tail.
  • A queue is full when advancing the tail would make it equal to the head (one slot is always empty); empty when head equals tail.
  • The controller writes P=1 on the first pass and inverts on each wrap; the host consumes an entry only if its phase matches the expected phase.
  • The host learns the SQ head only from CQE SQHD values (model this in the stretch goal).
  • Out-of-order completion must be possible.

Architecture

Two cooperating agents (host, controller) sharing a memory model, with an event log that records each PCIe-visible action (doorbell MWr, SQE MRd, CQE MWr).

Starter code

# queuesim.py - one SQ/CQ pair with doorbells and phase tags. Simulation, not a driver.
class QueuePair:
    def __init__(self, entries):
        self.n = entries
        self.sq = [None] * entries; self.cq = [None] * entries
        self.sq_tail = 0          # host-owned, published via SQ tail doorbell
        self.sq_head = 0          # controller-owned, reported in CQE.SQHD
        self.cq_tail = 0          # controller-owned
        self.cq_head = 0          # host-owned, published via CQ head doorbell
        self.ctrl_phase = 1       # controller writes P=1 on the first pass
        self.host_phase = 1       # host expects P=1 on the first pass
        self.db_sq = 0; self.db_cq = 0   # what the controller has been told
        self.log = []

    # ---- host side
    def submit(self, cid):
        if (self.sq_tail + 1) % self.n == self.sq_head:
            raise RuntimeError("SQ full: tail+1 == head (one slot always stays empty)")
        self.sq[self.sq_tail] = cid
        self.sq_tail = (self.sq_tail + 1) % self.n
    def ring_sq(self):
        self.db_sq = self.sq_tail; self.log.append(f"MWr SQ tail doorbell = {self.db_sq}")
    def reap(self):
        done = []
        while self.cq[self.cq_head] and self.cq[self.cq_head][1] == self.host_phase:
            done.append(self.cq[self.cq_head][0])
            self.cq_head = (self.cq_head + 1) % self.n
            if self.cq_head == 0:
                self.host_phase ^= 1          # wrapped: expect inverted phase
        if done:
            self.db_cq = self.cq_head; self.log.append(f"MWr CQ head doorbell = {self.db_cq}")
        return done

    # ---- controller side
    def controller_step(self):
        while self.sq_head != self.db_sq:     # fetch everything published
            cid = self.sq[self.sq_head]
            self.log.append(f"MRd SQE slot {self.sq_head} (cid {cid})")
            self.sq_head = (self.sq_head + 1) % self.n
            if (self.cq_tail + 1) % self.n == self.db_cq:
                raise RuntimeError("CQ full: controller must not overwrite unconsumed entries")
            self.cq[self.cq_tail] = (cid, self.ctrl_phase)
            self.log.append(f"MWr CQE slot {self.cq_tail} cid {cid} P={self.ctrl_phase} SQHD={self.sq_head}")
            self.cq_tail = (self.cq_tail + 1) % self.n
            if self.cq_tail == 0:
                self.ctrl_phase ^= 1

qp = QueuePair(4)
for rnd in range(3):
    for k in range(2):
        qp.submit(0x40 + 2 * rnd + k)
    qp.ring_sq(); qp.controller_step()
    print(f"round {rnd}: reaped", [hex(c) for c in qp.reap()],
          f"host_phase={qp.host_phase} ctrl_phase={qp.ctrl_phase}")
print("\n".join(qp.log))

Acceptance tests

  • Submitting N entries into an N-entry queue raises "full" on the Nth.
  • After exactly one wrap, the host expects P=0 and consumes only P=0 entries.
  • A CQE written with the wrong phase is not consumed (inject this fault).
  • SQHD in each CQE equals the controller's SQ head at the time of writing.
  • Out-of-order completion: completing CIDs 0x41 before 0x40 still reaps both, in CQ order.

Failure cases

  • Host forgets to flip phase on wrap → hangs after the first lap.
  • Controller overwrites an unconsumed CQE because the CQ head doorbell was never written.
  • Host uses N entries in an N-entry queue → full and empty become indistinguishable.

Project 6 — Simulate doorbells

Goal

Extend Project 5 with a register-level doorbell model: addresses from CAP.DSTRD, invalid doorbell writes, batching, and the analyzer view of each write.

Requirements

  • SQ y tail doorbell at 1000h + (2y × (4 << CAP.DSTRD)); CQ y head doorbell at 1000h + ((2y + 1) × (4 << CAP.DSTRD)).
  • Writes to a doorbell of a non-existent queue, or a value ≥ queue size, are flagged as invalid doorbell writes. (How the controller reports them — for example through an asynchronous event — must be read from the Base Specification; model it as a configurable reaction, not a hard-coded assumption.)
  • Model batching: the host may submit several SQEs and ring once; the controller may fetch several SQEs with one read (implementation-dependent).
  • Emit the MWr TLP that would carry each doorbell (address, 1 DW, data).

Architecture

Address decoder (offset → queue, SQ/CQ) → validator → queue model from Project 5 → TLP emitter (uses Project 3's formatter).

Starter sketch

def doorbell_offset(qid, is_cq, dstrd):
    stride = 4 << dstrd
    return 0x1000 + (2 * qid + (1 if is_cq else 0)) * stride

def decode_doorbell(addr, bar0, dstrd):
    off = addr - bar0 - 0x1000
    stride = 4 << dstrd
    if off < 0 or off % stride:
        return None                      # not a doorbell (or misaligned)
    idx = off // stride
    return {"qid": idx // 2, "kind": "CQ head" if idx % 2 else "SQ tail"}

def on_doorbell_write(state, qid, kind, value):
    q = state.queues.get(qid)
    if q is None or value >= q.size:
        state.report_invalid_doorbell(qid, kind, value)   # reaction is configurable
        return
    ...

Expected output

For the lab system with DSTRD=0: SQ0 tail at BAR0+1000h, CQ0 head at +1004h, SQ1 tail at +1008h, CQ1 head at +100Ch, SQ2 tail at +1010h. With DSTRD=1 (8-byte stride) SQ1 tail moves to +1010h.

Acceptance tests

  • Offsets match the formula for DSTRD 0, 1 and 2.
  • A write of 1024 to a 1024-entry queue's tail is flagged invalid.
  • A write to the doorbell of a deleted queue is flagged.
  • Ringing once after three submissions leads to fetches of exactly three slots.
  • Ringing with the same tail value twice causes no new fetches.

Failure cases

  • Assuming a 4-byte stride when CAP.DSTRD ≠ 0 → doorbells written to the wrong queue.
  • Writing a tail that "goes backwards" by more than the outstanding count — the controller sees it as many new commands.

Stretch goals

Model the shadow doorbell buffer feature by reading its description in the Base Specification (do not guess its layout); measure how many doorbell MWr TLPs it saves in your simulation.

Project 7 — Simulate DMA

Goal

From a command's data pointer and length, produce the PRP entries (and PRP list) the driver would build, then the stream of TLPs the controller would emit to move the data, respecting MPS, MRRS, the Read Completion Boundary (RCB) and the 4 KiB boundary rule.

Requirements

  • PRP rules: only the first entry may have a non-zero page offset; two pages → PRP2 is a page address; more → PRP2 points to a PRP list; chaining when a list page is full.
  • Read command: device→host MWr TLPs no larger than MPS and never crossing a 4 KiB boundary.
  • Write command: device→host MRd requests no larger than MRRS; host→device CplD completions no larger than MPS, split on RCB boundaries.
  • If a PRP list is used, the controller's MRd of the list appears before the data that depends on it.
  • Splitting strategy within the rules is implementation-dependent; make it configurable.

Architecture

PRP builder → address-range iterator (one range per PRP entry) → TLP segmenter (per direction) → event stream compatible with Project 8's input.

Starter code

# prpsim.py - build PRP1/PRP2 (and a PRP list) for a buffer, then simulate the controller's DMA
# as PCIe TLPs limited by Max Payload Size. Simulation of the course lab system.
PAGE, MPS = 4096, 256
PRP_LIST_BASE = 0x1_5000_0000

def build_prps(addr, length):
    pages, a, end = [], addr, addr + length
    while a < end:
        pages.append(a)
        a = (a // PAGE + 1) * PAGE                 # only the first entry may have an offset
    prp1 = pages[0]
    if len(pages) == 1:
        return prp1, 0, []
    if len(pages) == 2:
        return prp1, pages[1], []
    assert len(pages) - 1 <= PAGE // 8, "would need a chained PRP list (not simulated)"
    return prp1, PRP_LIST_BASE, pages[1:]          # PRP2 points to the list

def dma_writes(addr, length):
    """Device->host MWr TLPs for a Read: split at MPS and never cross a 4 KiB boundary."""
    out, a, end = [], addr, addr + length
    while a < end:
        n = min(MPS - (a % MPS) if a % MPS else MPS, end - a, PAGE - a % PAGE)
        out.append((a, n)); a += n
    return out

for addr, length in [(0x2_0000_0000, 4096), (0x2_0000_0200, 8192), (0x2_0000_0F00, 1024)]:
    p1, p2, lst = build_prps(addr, length)
    tlps = dma_writes(addr, length)
    print(f"buf=0x{addr:X} len={length}: PRP1=0x{p1:X} PRP2=0x{p2:X} list={[hex(x) for x in lst]}")
    print(f"   {len(tlps)} MWr TLPs; first={hex(tlps[0][0])}/{tlps[0][1]}B last={hex(tlps[-1][0])}/{tlps[-1][1]}B"
          + ("; controller must first MRd the PRP list (%d bytes)" % (8 * len(lst)) if lst else ""))

Expected output

buf=0x200000000 len=4096: PRP1=0x200000000 PRP2=0x0 list=[]
   16 MWr TLPs; first=0x200000000/256B last=0x200000f00/256B
buf=0x200000200 len=8192: PRP1=0x200000200 PRP2=0x150000000 list=['0x200001000', '0x200002000']
   32 MWr TLPs; first=0x200000200/256B last=0x200002100/256B; controller must first MRd the PRP list (16 bytes)
buf=0x200000F00 len=1024: PRP1=0x200000F00 PRP2=0x200001000 list=[]
   4 MWr TLPs; first=0x200000f00/256B last=0x200001200/256B

The third case is the interesting one: a 1 KiB buffer that straddles a page boundary needs two PRP entries even though it is smaller than one page. The simulation treats the IOVA range as contiguous for simplicity; in a real system the second page's PRP entry may point anywhere.

Acceptance tests

  • Aligned 4 KiB Read → PRP2 = 0 (unused), 16 MWr TLPs of 256 bytes.
  • 8 KiB at offset 200h → three pages, PRP list with two entries, 32 TLPs.
  • No generated TLP crosses a 4 KiB boundary.
  • Write of 4 KiB with MRRS 512 → eight MRd requests; each completed by CplDs no larger than 256 bytes.
  • A buffer needing more than 512 list entries triggers chaining (or a clear "not implemented").

Failure cases

  • Non-zero offset in a non-first PRP entry → the specification calls this invalid; your simulator must flag it.
  • PRP list itself crossing a page without chaining.
  • Payload larger than MPS → would be a Malformed TLP at the receiver.

Stretch goals

SGL support (data block and segment descriptors); add an IOMMU model where unmapped pages produce UR completions — then feed the result to Project 8 and watch the correlation catch it.

Project 8 — Correlate NVMe commands with PCIe TLPs

Goal

Given a TLP-level trace (CSV exported from an analyzer, or produced by Project 7) and the system context (BAR0, queue bases and sizes, MSI-X addresses), reconstruct each NVMe command's lifecycle: doorbell → SQE fetch → data movement → CQE → interrupt → CQ head doorbell.

Requirements

  • Classify each TLP by address region: doorbell, SQ fetch, CQ write, MSI-X, data, PRP list, other.
  • Match non-posted requests to completions by (Requester ID, Tag), handling split completions.
  • Map SQE fetch addresses to slots ((addr − SQ base) / 64), then to the CID inside the fetched data.
  • Attribute data TLPs to commands via PRP ranges; flag unattributable data.
  • Match CQEs to commands by (SQID, CID).
  • Record for each command the list of event IDs that support each lifecycle step.

Architecture

This is exactly the "correlation engine" of Automated Trace Analysis, whose executable reference implementation is your starting point. Copy it, then extend it.

Deliverables

A correlator module, a command lifecycle table (CSV/JSON), and a test corpus of at least five synthetic traces: normal read, normal write, out-of-order completions, a missing CQE, and a UR on data.

Milestones

  1. Region classification.
  2. Tag matching with split completions.
  3. SQE slot → CID.
  4. Data attribution.
  5. CQE matching and lifecycle table.
  6. Unattributed-event report.

Expected output

One row per command: SQID, CID, opcode, submit time, fetch event, data event count, CQE event, status, latency, and the supporting event IDs.

Acceptance tests

  • A CID reused after completion is treated as a new command, not merged with the old one.
  • Two commands with overlapping buffers produce an "ambiguous attribution" warning, not a silent guess.
  • A CplD arriving for an unknown tag is reported as an unexpected completion candidate.
  • Completions arriving out of submission order are attributed correctly.
  • If the capture starts mid-stream, commands without a visible doorbell are marked "submit time unknown".

Failure cases

  • Matching completions by tag alone across different requesters.
  • Using IOVA from the trace and physical addresses from somewhere else.
  • Assuming one SQE per fetch read.

Stretch goals

Multiple queues and MSI-X vector mapping per CQ; SGL; a timeline view.

Project 10 — Build an automated trace summarizer

Goal

Generate a readable HTML summary of a trace automatically: capture scope, link facts, traffic mix, per-command latency statistics, error events, and the first abnormal event candidate — with every statement linked to event IDs.

Requirements

  • Deterministic: the same input produces byte-identical output.
  • Statistics with definitions (median, p99, maximum; per opcode and per queue).
  • Explicit "unknown" where data is missing (for example, no doorbell seen for the first commands).
  • No interpretation beyond what rules support; hypotheses come in Project 11.

Architecture

Project 8 output → aggregators (counts, latency distributions, error lists) → template renderer (standard library string.Template or plain f-strings) → static HTML.

Starter sketch

def summarize(events, commands, context):
    s = {}
    s["scope"] = {"first_ns": events[0].t, "last_ns": events[-1].t,
                  "n_events": len(events), "truncated": context.buffer_overflow}
    s["mix"] = Counter(e.kind for e in events)
    lat = defaultdict(list)
    for c in commands:
        if c.t_done is not None and c.t_submit is not None:
            lat[(c.sqid, c.opc)].append(c.t_done - c.t_submit)
    s["latency"] = {k: {"n": len(v), "median": median(v), "p99": percentile(v, 99),
                        "max": max(v)} for k, v in lat.items()}
    s["errors"] = [e for e in events if e.is_error()]       # each with event_id
    s["first_abnormal"] = min(findings, key=lambda f: f.t_detect, default=None)
    return render_html(s)        # every number links to the events behind it

Expected output

An HTML page with sections matching the automated report format in AI + NVMe Protocol Analysis: Executive Summary, System Configuration, Capture Scope, Timeline, Key Transactions, First Abnormal Event, Errors, Evidence, and an Appendix with the raw lifecycle table.

Acceptance tests

  • Running twice gives identical output.
  • A trace with no errors produces "no abnormal events detected in the capture window" — not silence.
  • Latency percentiles match a hand calculation on a ten-command fixture.
  • Every number in the summary is traceable to event IDs.

Failure cases

  • Averages hiding a bimodal latency distribution — always show the distribution.
  • Reporting "0 errors" when error detection was disabled for a layer.

Stretch goals

Inline SVG histograms; a diff mode comparing two captures (see Synthetic vs Real Traces, Diffing and Golden Traces).

Project 11 — Build a failure classifier

Goal

Classify findings into failure classes (link, transaction, NVMe command, queue protocol, DMA/IOMMU, interrupt, performance, capture artifact) with a confidence level and the evidence that supports and could falsify each classification.

Requirements

  • Rule-based first; every rule documented with its source (specification section name or engineering heuristic, labelled as such).
  • Confidence on the course scale: CONFIRMED, HIGH, MEDIUM, LOW, UNKNOWN — defined by evidence criteria, not by a percentage.
  • Distinguish symptom from cause: a CQE error caused by a UR completion is classified under DMA/IOMMU with the CQE as a symptom.
  • Each classification lists a falsification test.

Architecture

Findings from Projects 8/10 → rule engine (ordered rules, each producing a classification with evidence) → causal linker (time order + shared identifiers) → classifier output.

Starter sketch

RULES = [
  Rule("dma-ur-causes-cqe-error",
       when=lambda f: f.kind == "cpl_ur" and f.request.kind == "dma_read",

]

Expected output

For the reference trace of Automated Trace Analysis: one HIGH DMA/IOMMU classification linking the UR completion to the Write command's Data Transfer Error, and one MEDIUM "command never completed" classification for the stuck Read, with the note that the stall may be a consequence of the earlier error (unproven).

Acceptance tests

  • Each classification lists at least one event ID and one falsification test.
  • A CQE error without any PCIe error is not classified as DMA/IOMMU.

  • Classifying by the most visible symptom (the kernel log timeout) instead of the earliest abnormal event.

Goal

An assistant that takes a trace and context, runs Projects 3–11 deterministically, and then helps an engineer reason: it asks the senior questions, proposes hypotheses with evidence and falsification tests, and drafts the report. Requirements

  • The assistant never invents packets, timestamps, fields, register values, specification requirements or root causes; every claim cites event IDs or a specification passage retrieved from your notes.

Raw capture + context

Quiz

  1. In Project 5, why is one queue slot always left empty?

    • To store the phase tag
    • So that head == tail unambiguously means empty, and tail + 1 == head means full
    • Because the specification reserves slot 0
    • For the doorbell
    Answer and reasoning

    With N slots and N entries used, head would equal tail just as when empty. Leaving one slot free removes the ambiguity.

  2. In Project 7, a 1 KiB buffer at IOVA 0x2_0000_0F00. How many PRP entries?

    • 1
    • 2
    • 3
    • A PRP list is required
    Answer and reasoning

    It touches two pages (0x…0F00–0x…0FFF and 0x…1000–0x…12FF), so PRP1 and PRP2 (a page address). No list is needed.

  3. Project 3 decodes a completion with status field 001b. What is it?

    • Successful Completion
    • Completer Abort
    • Unsupported Request
    • Configuration Request Retry Status
    Answer and reasoning

    000b SC, 001b UR, 010b CRS, 100b CA.

  4. Why must Project 4 know whether an SQE came from the Admin queue?

    Model answer

    Admin and I/O opcodes overlap: 02h is Get Log Page on the Admin queue and Read on an NVM I/O queue; 01h is Create I/O SQ versus Write. The queue identifies the opcode table.

  5. Why does Project 8 need system context that is not in the trace?

    Model answer

    A TLP carries addresses, not meanings. Knowing that an address is a doorbell, an SQ slot or a CQ slot requires BAR0, CAP.DSTRD and the queue bases the driver programmed. Without them, correlation is guesswork.

  6. In Project 10, why must the summarizer be deterministic?

    Model answer

    So results are reproducible, diffable and testable; so a reviewer can rerun and get the same evidence; and so any non-deterministic reasoning layer added later can be checked against a fixed base.

  7. What is a falsification test, and why does Project 11 require one per classification?

    Model answer

    An observation that, if found, would show the classification is wrong. It forces the classifier (and the engineer) to state what evidence would change the conclusion, which prevents confirmation bias and guides the next experiment.

  8. In Project 12, what is the role of the claim validator?

    Model answer

    To check mechanically that every claim cites existing event IDs and that cited field values match the decoded data, rejecting fabricated or contradicted claims before they reach the report.
