This chapter turns your Linux machine into a careful PCIe witness. You will learn exactly what lspci, setpci and the /sys/bus/pci tree reveal about an NVMe SSD's PCI Express function, which hardware access produces each line of output, and, just as important, what that output can never prove.

Why this chapter exists

Every NVMe-over-PCIe investigation starts with the same three questions: Is the device there? Is the link what we think it is? Has anything already gone wrong? A protocol analyzer answers those questions with certainty, but most of the time you do not have an analyzer attached. What you always have is a Linux shell, and Linux exposes a great deal of the PCI Express (PCIe) view of a device through a small set of tools.

Junior engineers often treat lspci -vvv as a wall of noise, or worse, as an oracle. Senior engineers read it the way a doctor reads a blood test: each line is a measurement taken at a specific moment, by a specific mechanism, with known blind spots. This chapter teaches that reading.

Earlier chapters taught the concepts: enumeration in Chapter 17, configuration space in Chapter 18, Base Address Registers (BARs) in Chapter 19, link training in Chapter 9 and Advanced Error Reporting (AER) in Chapter 46. Here you meet the same concepts as they appear on a real Linux system, so that you can check them in seconds on any machine you touch.

Learning objectives

  • Find an NVMe SSD's Bus:Device.Function (BDF) address, its place in the topology and its upstream root port, using lspci -tv, lspci -nn and lspci -D.
  • Read lspci -vv / -vvv output section by section: header, Command/Status, BARs, capability list, PCI Express capability (DevCap/DevCtl/DevSta, LnkCap/LnkCtl/LnkSta), MSI-X and AER.

  • Navigate /sys/bus/pci/devices/<BDF>/: config, resource, current_link_speed/_width, max_link_speed/_width, aer_dev_* counters, driver, iommu_group, msi_irqs.
  • State, for each tool, what it proves, what it suggests, and what it cannot prove.
  • Know which TLPs (Transaction Layer Packets) your inspection itself puts on the wire.

The story

Imagine the giant library (the SSD) has a little name card stuck on its front door. The card says who built the library, what kind of library it is, which road it sits on, how wide that road is, and has a small notebook where the library writes down every time a delivery truck arrived damaged. You are not allowed inside the library, but you are allowed to walk up to the door and read the card and the notebook. You can read them as many times as you like. You must never scribble on them, because the librarian uses that card to know how to behave.

lspci is you reading the card aloud. setpci is a pen: you will only use its "read" end. The /sys folder is a photocopy of the card that the school office (the Linux kernel) keeps, with a few notes of its own added.

An adult version: configuration space is a building's electrical inspection panel. The panel has a nameplate (vendor, device, class), breaker settings (Command register, Device Control), a rating plate (Link Capabilities: "rated for 16 GT/s ×4"), live meters (Link Status: "running at 16 GT/s ×4 right now") and a fault log (AER status bits). An inspector with a flashlight can read all of it without touching a breaker. Flipping a breaker (writing config space) is a licensed electrician's job.

Where the analogy breaks. (1) A meter on a panel is continuous; Link Status is a register you sample, so a link that flapped down and back up between two reads looks perfectly healthy. (2) Reading a real panel never changes it, but some PCIe status bits are "write 1 to clear" and some reads have side effects in the kernel (for example waking a runtime-suspended device so its config space can be read). (3) The panel's nameplate is fixed; much of config space is programmed by software (BAR addresses, MPS, MRRS, ASPM), so what you read reflects firmware and kernel decisions, not only the device. (4) The fault log on a panel is complete; AER bits record that an error class happened at least once, not how many times or when, unless the kernel counted them for you.

Beginner explanation

Every PCIe function has a small block of memory-like storage called configuration space: 256 bytes for the classic PCI-compatible part and up to 4 KiB in total with the PCIe extended region. The kernel's PCI subsystem reads it during enumeration and keeps reading it whenever a driver or a tool asks.

lspci, from the pciutils package, is a decoder. It asks the kernel for each function's configuration space (through files under /sys/bus/pci/devices/), adds human names from a vendor/device ID database (pci.ids), and prints the result. Most of what it shows is a translation of bytes you could read yourself.

Linux also publishes a pre-digested view in sysfs: one directory per function, with small text files such as current_link_speed or vendor. Those files are produced by kernel code that read the same registers, sometimes adding information only the kernel knows (which driver is bound, which IOMMU group the device is in, how many AER errors it has counted).

Three commands cover 90% of daily use:

lspci -nn | grep -i 'non-volatile'      # find NVMe controllers (class 0108)
lspci -tv                               # where is it in the tree?
sudo lspci -vvv -s 01:00.0              # full decode of one function (root needed for capabilities)

Everything in this chapter is a Safe lab operation unless a block says otherwise: you are only reading.

Engineering explanation

Where lspci gets its bytes

On Linux, lspci uses the linux-sysfs access method by default: it opens /sys/bus/pci/devices/<domain:bus:dev.fn>/config and reads it. The kernel services that read with its own configuration accessors, which on a modern x86 or Arm server use the Enhanced Configuration Access Mechanism (ECAM): a memory-mapped window in which each function's 4 KiB config space has an address. A CPU load from that window is turned by the root complex into a Configuration Read Request TLP (CfgRd0 for a device directly below a root port, CfgRd1 when it must be forwarded through a bridge). The function answers with a Completion with Data (CplD).

Two consequences follow:

  • Most lspci fields are live reads from the device at the moment you ran the command. They are not a cached copy from boot. Implementation-dependent exceptions exist: a few header fields can be served from kernel-saved state, and sysfs may resume a runtime-suspended device so it can be read.
  • An unprivileged user only receives the first 64 bytes of config (the standard header). That is why lspci -vv as a normal user prints Capabilities: <access denied>. Use sudo for capability decoding.

Identity line

Non-Volatile memory controller is the name of class code 01h (mass storage), subclass 08h (non-volatile memory). prog-if 02 [NVM Express] is the programming interface byte that says "this function speaks the NVMe register interface". Together, class code 01 08 02 is how the Linux nvme driver matches a device even when it has never heard of the vendor. If the prog-if were 01h, the function would advertise the older NVMHCI interface; the nvme driver would not claim it by class.

Control and Status (Command and Status registers, offsets 04h and 06h)

  • Mem+: Memory Space Enable. Without it, MMIO to BAR0 (every NVMe register access and every doorbell) is not decoded by the function. A function with Mem- while the driver is bound is a red flag.
  • BusMaster+: Bus Master Enable. Without it the controller may not issue memory requests, so it cannot fetch SQEs, move data or post completions and MSI-X writes. After a failed reset or a device removal path, this is often what you find cleared.
  • DisINTx+: legacy INTx is disabled, consistent with MSI-X in use.
  • SERR+: the function may report system errors. >SERR- and <PERR- in Status say none were signalled or detected through the legacy bits.
  • <MAbort- / >TAbort-: "received master abort" and "signalled target abort". On PCIe these map to Unsupported Request and Completer Abort handling on the conventional-PCI side of the bits. A set bit here is a historical fact, not a timestamp.

Region 0 (BAR0/BAR1)

Memory at fe600000 (64-bit, non-prefetchable) [size=16K] is BAR0 and BAR1 combined into one 64-bit BAR. The address is the CPU physical address the kernel assigned; the size was discovered by the BAR sizing procedure from Chapter 19. The NVMe controller registers (CAP at offset 00h, VS at 08h, CC at 14h, CSTS at 1Ch, AQA at 24h, ASQ at 28h, ACQ at 30h, doorbells from 1000h) live at fe600000 + offset. If lspci prints [virtual] or [disabled] next to a region, the BAR is not enabled or the address is not live.

Capabilities: the linked list

The number in brackets ([40], [70], [b0]) is the capability's offset in config space. Offsets below 100h are in the PCI-compatible region, reached from the Capabilities Pointer at 34h. Offsets from 100h upward are PCIe extended capabilities, a separate linked list starting at 100h. v2 after an extended capability is its version field.

MSI-X capability

Enable+ Count=33 Masked- says MSI-X is in use with 33 vectors (the reference SSD: vector 0 for the admin queue, 1–32 for I/O queues), none function-masked. The table and Pending Bit Array (PBA) are in BAR0 at offsets 2000h and 3000h. Plain MSI (Enable-) is present but unused. More in Chapter 43.

Advanced Error Reporting

  • UESta: Uncorrectable Error Status. A + is a sticky record that an uncorrectable error of that type was detected. CmpltTO+, UnsupReq+, MalfTLP+ are the ones NVMe engineers see most.
  • UEMsk: masked types are still recorded in status on many implementations but do not generate error messages. Version-dependent detail; check the AER chapter of the PCIe Base Specification.
  • UESvrt: which uncorrectable types are treated as Fatal (+) versus Non-Fatal.
  • CESta/CEMsk: correctable errors such as RxErr (receiver error at the Physical Layer), BadTLP, BadDLLP, Rollover (replay number rollover), Timeout (replay timer timeout). These are the early warnings of a marginal link.
  • HeaderLog: the header of the TLP associated with the first recorded uncorrectable error, when one is logged. With an all-zero log there is nothing to decode.

The Linux AER driver normally clears status bits after it handles and logs an error. A clean UESta/CESta therefore does not mean "no error ever happened"; it may mean "the kernel already reported and cleared it". Check the kernel log (Chapter 71) and the aer_dev_* counters before declaring a device clean. Conversely, if firmware handles errors (firmware-first), the OS may never see or clear them. setpci: reading named registers (and why you will not write)

setpci addresses one register at a time. Its syntax is setpci -s <BDF> <register>[.b|.w|.l][=value]. Without =value it reads. With =value it writes. That single character is the difference between a safe lab and an expert one.

sudo setpci -s 01:00.0 VENDOR_ID           # 16-bit read at 00h
sudo setpci -s 01:00.0 COMMAND             # 16-bit Command register at 04h
sudo setpci -s 01:00.0 CAP_EXP+0x12.w      # Link Status: Express capability + 12h
sudo setpci -s 01:00.0 CAP_EXP+0x08.w      # Device Control (MPS bits 7:5, MRRS bits 14:12)
sudo setpci -s 01:00.0 ECAP_AER+0x04.l     # AER Uncorrectable Error Status
sudo setpci -s 01:00.0 ECAP_AER+0x10.l     # AER Correctable Error Status
sudo setpci -s 00:01.1 CAP_EXP+0x12.w      # same Link Status, seen from the root port

CAP_EXP and ECAP_AER are names pciutils resolves by walking the capability lists, so you do not need to know the offsets 70h and 100h for this particular device. Names supported depend on the pciutils version (setpci --dumpregs lists them). A Link Status read of 1044 decodes as: bits 3:0 = 4 (current speed is the fourth entry in the Supported Link Speeds Vector, 16.0 GT/s on a Gen4-capable port), bits 9:4 = 4 (×4), bit 12 = 1 (Slot Clock Configuration). The Python decoder in the code section does this for you.

Expert lab setpci writes. Writing config space bypasses the driver's understanding of the device. Examples of what a single write can do: clear Bus Master Enable (the controller can no longer DMA; in-flight commands time out and the driver resets the controller); disable Memory Space (every MMIO read returns all-ones, the driver believes the device is dead); change MPS so it no longer matches the link partner (Malformed TLP, fatal errors, possible machine check on some platforms); set Link Disable or Retrain on a root port (the drive drops off the bus; data in flight is lost); clear RW1C error status before anyone logged it (destroys evidence). Writes belong only on a spare drive in a lab machine, with the filesystem unmounted, with a written plan and a recovery path (see Lab Environment). This chapter never asks you to write.

The central concept on the ladder: a config-space snapshot as evidence

You read the name card and the damage notebook on the library's door. You only see what is written right now.

lspci and sysfs read the function's configuration space and translate bytes into names: identity, enables, BARs, link speed and width, error status.

The registers are flip-flops inside the SSD controller's PCIe core (and inside the root port for the upstream view). Some are hard-wired (capabilities), some are programmed by firmware/kernel (BARs, MPS), some are set by hardware events (Link Status, error status).

The PCI Express Base Specification defines the Type 0 header, the PCI Express Capability structure, and the AER extended capability, including which bits are read-only, read-write and RW1C (write 1 to clear) and which are sticky across resets.

Each read is a non-posted Configuration Read Request (CfgRd0) from the root complex to the function, answered by a CplD. A function that is gone yields an Unsupported Request completion or a timeout, which the root complex turns into all-ones data.

On an analyzer, running lspci -vvv appears as a burst of a few hundred CfgRd0/CplD pairs, 1 DW each, between the root port and the SSD. You can correlate the timestamp of that burst with the moment you typed the command.

A senior engineer uses snapshots differentially: before and after a workload, both ends of the link, live and from a saved dump. A value of ffff for Vendor ID or a whole dump of ff means "nobody answered", which reframes the problem from NVMe to link or power.

The sixteen questions for "inspecting a PCIe function from Linux"

1. What is it?
A read-only sampling of a function's configuration space and the kernel's bookkeeping about it, via lspci, setpci (read form) and sysfs.
2. Why was it created?
Software needs to discover, configure and diagnose devices without device-specific tools; config space is the standard, vendor-neutral window.
3. What problem does it solve?
Answers "what is present, how is it configured, how is the link running, has it reported errors" without an analyzer.
4. What existed before?
Conventional PCI config mechanism #1 (I/O ports CF8h/CFCh) limited to 256 bytes; ISA-era jumpers and vendor utilities.
5. Why is the current design better?
ECAM gives 4 KiB per function, memory-mapped; extended capabilities (AER, DSN, Physical Layer 16.0 GT/s, etc.) are discoverable by a generic walker.
6. Who creates it?
The device designer (read-only fields), platform firmware and the Linux PCI core (programmed fields), hardware events (status fields).
7. Who consumes it?
The PCI core, drivers (nvme reads MSI-X and BAR info), the AER/DPC/hotplug services, and you.
8. Where does it live?
In the device's PCIe core logic; mirrored in the kernel's struct pci_dev and in sysfs.
9. What memory/registers are involved?
Type 0 header (00h–3Fh), capability list (from 34h), extended capabilities (from 100h), the ECAM window.
10. What happens before?
Link training, enumeration, BAR assignment, driver binding.
11. What happens after?
You form hypotheses and choose the next probe: kernel log, nvme-cli (Chapter 70), tracing, an analyzer.
12. What happens if it is wrong?
Misread fields lead to false conclusions (blaming the SSD for a root-port speed cap); writes can break a live device.
13. What does the analyzer show?
CfgRd0/CplD pairs; on failure, UR completions or no completion.
14. What does Linux show?
The decoded lspci output, sysfs files, and kernel messages from enumeration and AER.
15. What would a validation engineer test?
That reported capabilities match the datasheet, that link trains to max on every supported platform, that AER status is clean after stress, that config values persist correctly across FLR and resets.
16. What would a senior engineer suspect when it fails?
All-ones reads → link down/surprise removal/power. Downgraded LnkSta → SI, slot wiring, firmware target speed, bifurcation. Clean AER but errors in logs → OS already cleared them. BusMaster- after reset → incomplete recovery.

Hardware view

Inside an NVMe SSD controller application-specific integrated circuit (ASIC), the PCIe core (usually licensed intellectual property) implements the configuration space as a set of registers next to the Transaction Layer. Read-only capability fields are often strapped at reset from controller firmware or from an internal ROM, which is why a firmware update can change, for example, the reported Max Payload Supported or the presence of a capability.

Link Status fields are driven by the Physical and Data Link Layer logic. Current Link Speed and Negotiated Link Width are updated when the Link Training and Status State Machine (LTSSM) completes training and re-enters L0 (see Chapter 8). The error status bits are set by the logic that detects each condition: the receiver sets Receiver Error, the Data Link Layer sets Bad TLP/Bad DLLP, the Transaction Layer sets Unsupported Request or Completion Timeout.

Some status bits are sticky: they survive a conventional (hot/warm) reset so that post-mortem software can still read them. That is a hardware design choice requested by the specification exactly for debugging. It also means that after a reset you may read errors from before the reset.

The root port is a separate piece of hardware with its own copy of the same structures, plus extras an endpoint does not have: Slot Capabilities/Status (presence detect, hot-plug), Root Control/Status, the root's AER Root Error Status, and often a Downstream Port Containment (DPC) capability. For link problems the root port's view is usually more informative than the endpoint's.

A read of a device that has lost its link never reaches the device. The root port either completes the request locally with an error status, or the request times out in the root complex. Either way, the CPU's load instruction receives all-ones data (0xFFFFFFFF) on typical x86 platforms. That is why ffff for vendor ID, CSTS=0xffffffff in an NVMe message and a dump full of ff are the classic signatures of "device not reachable". Platform-dependent handling; some platforms raise an error instead.

Specification view

The structures lspci decodes are defined by the PCI Express Base Specification, Revision 6.x/7.0 — Configuration Space; PCI Express Capability Structure; Advanced Error Reporting Capability (a PCI-SIG members' document; earlier revisions define the same core registers). The class code 01 08 02 is assigned in the PCI Code and ID Assignment Specification. The NVMe interface behind the BAR is defined by the NVM Express Base Specification 2.4 — Controller Registers and the NVMe over PCIe Transport Specification 1.4. Linux behaviour is defined by the kernel source and its documentation (Linux kernel documentation — PCI Express AER driver guide; sysfs-bus-pci ABI), which are informative for the PCIe protocol but normative for what Linux prints.

Verified, well-established: the Type 0 header layout (Vendor ID 00h, Device ID 02h, Command 04h, Status 06h, Class Code 09h–0Bh, Header Type 0Eh, BAR0 10h, Capabilities Pointer 34h); extended capabilities start at 100h; within the PCI Express Capability, Device Capabilities 04h, Device Control 08h, Device Status 0Ah, Link Capabilities 0Ch, Link Control 10h, Link Status 12h; Link Status bits 3:0 current speed and 9:4 negotiated width; Device Control MPS in bits 7:5 and MRRS in bits 14:12 with encoding 000b = 128 bytes doubling to 101b = 4096 bytes; within AER, Uncorrectable Status 04h, Mask 08h, Severity 0Ch, Correctable Status 10h, Correctable Mask 14h, Capabilities and Control 18h, Header Log from 1Ch.

Derived: because each lspci field is a live read, two lspci runs bracket a time window; any difference between them happened inside that window. Because AER status is RW1C and Linux clears it after handling, the absence of a set bit is weak evidence; the presence of one is strong evidence that the OS has not (yet) handled it or that the error is masked from signalling.

Implementation-dependent: which optional capabilities exist; Max Payload Supported; Completion Timeout ranges; whether masked errors still set status bits; how the root complex responds to a config read to an absent device; whether the platform uses firmware-first error handling; whether sysfs resumes a suspended device for a config read.

Version-dependent: pciutils' decoding and naming; sysfs file names and formats across kernel releases; the Link Status encoding of speeds beyond 32.0 GT/s (Gen6 64.0 GT/s, Gen7 128.0 GT/s) depends on the Supported Link Speeds Vector and on newer capability structures; Flit-mode-related fields only exist in PCIe 6.0 and later.

The specification does not say what an operating system must print, how often it must poll status, whether it must clear AER bits, or what a "healthy" number of correctable errors is. Confirm in the specification: the exact RW1C/sticky attributes of each AER bit, the meaning of Supported Link Speeds Vector values for your generation, and the Completion Timeout range encodings in Device Control 2.

Never assume: that LnkCap is what the link runs at; that a clean AER status means no errors happened; that the kernel's IRQ number in Interrupt: is used (with MSI-X it is not); that lspci output from a different pciutils version will be laid out identically; that -xxxx is harmless on every device in a production fleet.

Protocol view

Inspection is not free on the wire. Each 4-byte register read becomes one non-posted request and one completion:

  • Direction: configuration requests always flow downstream from the root complex; endpoints never send configuration requests.
  • Ordering: configuration requests are non-posted, and Linux serializes them per access, so a config read cannot overtake a preceding posted MMIO write the way you might fear; the kernel's accessors also take a lock.
  • Size: config TLPs carry exactly 1 DW of data. A 4 KiB -xxxx dump is about 1024 request/completion pairs.
  • Addressing: config TLPs are routed by ID (bus/device/function), not by address. The register number travels in the header.
  • Failure: a function that does not exist answers with Unsupported Request (UR) status; a function still initializing after reset may answer Configuration Request Retry Status (CRS), which the root complex may retry or surface depending on CRS Software Visibility; a dead link produces no completion at all.

Contrast with the NVMe traffic you will inspect in Chapter 70: NVMe register reads and doorbell writes are memory requests (MRd/MWr) to BAR0, routed by address. lspci never touches BAR0; nvme show-regs does.

Code / pseudocode

The decoder below reads a function's config space from sysfs (read-only) and prints the fields this chapter taught. It walks both capability lists with loop guards, so a corrupted or all-ones image cannot hang it. Run --selftest on any machine (no hardware needed): it decodes a built-in synthetic image of the Lab SSD in which one correctable error bit has been set on purpose so you can see the AER decode.

#!/usr/bin/env python3
"""Read-only PCI config space decoder for teaching.

  python3 pcicfg_decode.py --selftest          # synthetic Lab SSD image, no hardware
  sudo python3 pcicfg_decode.py 0000:01:00.0   # live device via sysfs (read-only)
  python3 pcicfg_decode.py --file config.bin   # a saved binary copy of 'config'
"""
import struct
import sys

# Link Status 'current speed' is an index into the Supported Link Speeds Vector.
# On ports that support every lower speed, index n is generation n.
SPEED = {1: "2.5 GT/s", 2: "5.0 GT/s", 3: "8.0 GT/s", 4: "16.0 GT/s",
         5: "32.0 GT/s", 6: "64.0 GT/s"}
UE = {4: "DLP", 5: "SDES", 12: "PoisonedTLP", 13: "FCP", 14: "CmpltTO",
      15: "CmpltAbrt", 16: "UnxCmplt", 17: "RxOF", 18: "MalfTLP",
      19: "ECRC", 20: "UnsupReq", 21: "ACSViol"}
CE = {0: "RxErr", 6: "BadTLP", 7: "BadDLLP", 8: "Rollover", 12: "Timeout",
      13: "AdvNonFatalErr", 14: "CorrIntErr", 15: "HeaderOF"}
CAP_NAMES = {0x01: "Power Management", 0x05: "MSI", 0x10: "PCI Express",
             0x11: "MSI-X"}
ECAP_NAMES = {0x0001: "Advanced Error Reporting", 0x0003: "Device Serial Number",
              0x0019: "Secondary PCI Express"}


def u8(b, o):
    return b[o]


def u16(b, o):
    return struct.unpack_from("<H", b, o)[0]


def u32(b, o):
    return struct.unpack_from("<I", b, o)[0]


def bits(value, names):
    on = [n for bit, n in sorted(names.items()) if value >> bit & 1]
    return ", ".join(on) if on else "none"


def synthetic_lab_ssd():
    """Synthetic example for teaching: the course's Lab SSD (placeholder IDs)."""
    b = bytearray(4096)
    struct.pack_into("<HHHH", b, 0x00, 0x10AB, 0xC0DE, 0x0406, 0x0010)
    b[0x09:0x0C] = bytes([0x02, 0x08, 0x01])           # prog-if, subclass, class
    struct.pack_into("<I", b, 0x10, 0xFE600004)        # 64-bit non-prefetchable BAR0
    b[0x34] = 0x40
    b[0x3C], b[0x3D] = 0xFF, 0x01
    b[0x40:0x42] = bytes([0x01, 0x50])                  # PM -> 0x50
    b[0x50:0x52] = bytes([0x05, 0x70])                  # MSI -> 0x70
    b[0x70:0x72] = bytes([0x10, 0xB0])                  # Express -> 0xB0
    struct.pack_into("<H", b, 0x72, 0x0002)            # version 2, endpoint
    struct.pack_into("<I", b, 0x74, 0x00008022)        # DevCap: MPS supported 512
    struct.pack_into("<H", b, 0x78, 0x293F)            # DevCtl: MPS 256, MRRS 512
    struct.pack_into("<I", b, 0x7C, 0x00000844)        # LnkCap: 16 GT/s x4, ASPM L1
    struct.pack_into("<H", b, 0x80, 0x0040)            # LnkCtl: CommClk
    struct.pack_into("<H", b, 0x82, 0x1044)            # LnkSta: 16 GT/s x4, SlotClk
    b[0xB0:0xB2] = bytes([0x11, 0x00])                  # MSI-X, end of list
    struct.pack_into("<HII", b, 0xB2, 0x8020, 0x00002000, 0x00003000)
    struct.pack_into("<I", b, 0x100, 0x0001 | (2 << 16) | (0x148 << 20))
    struct.pack_into("<I", b, 0x110, 0x00000001)       # CESta: RxErr set (on purpose)
    struct.pack_into("<I", b, 0x114, 0x00002000)       # CEMsk: AdvNonFatalErr
    struct.pack_into("<I", b, 0x148, 0x0003 | (1 << 16))
    return bytes(b)


def walk_caps(b):
    seen, ptr, out = set(), u8(b, 0x34) & 0xFC, {}
    while ptr and ptr not in seen and ptr + 1 < min(len(b), 256):
        seen.add(ptr)
        out[u8(b, ptr)] = ptr
        ptr = u8(b, ptr + 1) & 0xFC
    return out


def walk_ecaps(b):
    out, off, seen = {}, 0x100, set()
    while len(b) >= off + 4 and off not in seen:
        seen.add(off)
        hdr = u32(b, off)
        if hdr in (0, 0xFFFFFFFF):
            break
        out[hdr & 0xFFFF] = off
        off = (hdr >> 20) & 0xFFC
        if off < 0x100:
            break
    return out


def decode(b):
    if len(b) < 64:
        sys.exit("config image shorter than 64 bytes")
    vid, did = u16(b, 0), u16(b, 2)
    if vid == 0xFFFF:
        print("Vendor ID reads 0xFFFF: nobody answered (link down, removed, or in reset).")
        return
    cmd, sts = u16(b, 4), u16(b, 6)
    cls = (b[0x0B], b[0x0A], b[0x09])
    print(f"ID {vid:04x}:{did:04x}  class {cls[0]:02x}{cls[1]:02x}{cls[2]:02x}"
          + ("  (NVM Express)" if cls == (1, 8, 2) else ""))
    print(f"Command 0x{cmd:04x}: Mem{'+' if cmd & 2 else '-'} "
          f"BusMaster{'+' if cmd & 4 else '-'} DisINTx{'+' if cmd & 0x400 else '-'}")
    bar0 = u32(b, 0x10)
    if not bar0 & 1:
        addr = bar0 & ~0xF
        if (bar0 >> 1) & 3 == 2:
            addr |= u32(b, 0x14) << 32
        print(f"BAR0 0x{addr:x} ({'64' if (bar0 >> 1) & 3 == 2 else '32'}-bit, "
              f"{'prefetchable' if bar0 & 8 else 'non-prefetchable'})")
    if not sts & 0x10:
        print("No capability list.")
        return
    if len(b) <= 64:
        print("Only 64 bytes readable: run as root to decode capabilities.")
        return
    caps = walk_caps(b)
    print("Capabilities:", ", ".join(f"[{o:02x}] {CAP_NAMES.get(i, hex(i))}"
                                     for i, o in sorted(caps.items(), key=lambda x: x[1])))
    e = caps.get(0x10)
    if e is not None:
        devctl, devsta = u16(b, e + 8), u16(b, e + 0x0A)
        lnkcap, lnksta = u32(b, e + 0x0C), u16(b, e + 0x12)
        mps = 128 << ((devctl >> 5) & 7)
        mrrs = 128 << ((devctl >> 12) & 7)
        print(f"DevCtl: MPS {mps} B, MRRS {mrrs} B; DevSta errors: "
              + (bits(devsta & 0xF, {0: "CorrErr", 1: "NonFatal", 2: "Fatal", 3: "UnsupReq"})))
        cap_s, cap_w = lnkcap & 0xF, (lnkcap >> 4) & 0x3F
        sta_s, sta_w = lnksta & 0xF, (lnksta >> 4) & 0x3F
        flag = "" if (sta_s, sta_w) == (cap_s, cap_w) else "   <-- below this port's capability"
        print(f"LnkCap: {SPEED.get(cap_s, cap_s)} x{cap_w}")
        print(f"LnkSta: {SPEED.get(sta_s, sta_s)} x{sta_w}{flag}")
    x = caps.get(0x11)
    if x is not None:
        mc = u16(b, x + 2)
        print(f"MSI-X: {'enabled' if mc >> 15 else 'disabled'}, {(mc & 0x7FF) + 1} vectors, "
              f"table BIR {u32(b, x + 4) & 7} off 0x{u32(b, x + 4) & ~7:x}")
    ecaps = walk_ecaps(b)
    for i, o in sorted(ecaps.items(), key=lambda x: x[1]):
        print(f"Extended [{o:03x}] {ECAP_NAMES.get(i, hex(i))}")
    a = ecaps.get(0x0001)
    if a is not None:
        print("  UESta:", bits(u32(b, a + 0x04), UE), "  UESvrt=0x%08x" % u32(b, a + 0x0C))
        print("  CESta:", bits(u32(b, a + 0x10), CE))
        print("  HeaderLog:", " ".join(f"{u32(b, a + 0x1C + 4 * k):08x}" for k in range(4)))


def main(argv):
    if len(argv) > 1 and argv[1] == "--selftest":
        print("Synthetic example for teaching (Lab SSD, placeholder IDs):")
        decode(synthetic_lab_ssd())
    elif len(argv) > 2 and argv[1] == "--file":
        with open(argv[2], "rb") as f:
            decode(f.read())
    elif len(argv) > 1:
        with open(f"/sys/bus/pci/devices/{argv[1]}/config", "rb") as f:
            decode(f.read())
    else:
        print(__doc__)


if __name__ == "__main__":
    main(sys.argv)

Worked example

Symptom

A Gen4 ×4 NVMe SSD in a new server reads sequentially at about 3.4 GB/s. The same model reaches about 7 GB/s in another chassis.

Step 1: the arithmetic of the expectation

BWraw = R × N × E ÷ 8
BWraw
raw one-direction link bandwidth in bytes per second, before TLP/DLLP overhead
R
signalling rate per lane in transfers per second (16 × 10⁹ for Gen4, 8 × 10⁹ for Gen3)
N
negotiated lane count
E
line-encoding efficiency: 128/130 for Gen3 to Gen5

Gen4 ×4: 16e9 × 4 × 128/130 ÷ 8 ≈ 7.88 GB/s. Gen3 ×4: ≈ 3.94 GB/s. After packet overhead, a Gen3 ×4 link delivers roughly 3.4–3.6 GB/s of read payload. Derived The symptom is suspiciously close to a Gen3 ×4 ceiling.

Step 2: endpoint view

Synthetic example for teaching: sudo lspci -vv -s 01:00.0 | grep -E 'LnkCap:|LnkSta:' shows LnkCap: Port #0, Speed 16GT/s, Width x4 and LnkSta: Speed 8GT/s (downgraded), Width x4.

Step 3: upstream view

The root port shows LnkCap: Speed 16GT/s, Width x4, LnkSta: Speed 8GT/s, Width x4, and LnkCtl2: Target Link Speed: 16GT/s. So both ends can do 16 GT/s, and software asked for 16 GT/s. The link chose 8 GT/s.

Step 4: kernel corroboration

The enumeration message (synthetic, see Chapter 71): pci 0000:01:00.0: 31.508 Gb/s available PCIe bandwidth, limited by 8.0 GT/s PCIe x4 link at 0000:00:01.1 (capable of 63.016 Gb/s with 16.0 GT/s PCIe x4 link). And aer_dev_correctable shows hundreds of RxErr since boot.

Step 5: reasoning

Both ends capable, target 16 GT/s, link at 8 GT/s, many receiver errors: the 16 GT/s equalization probably failed and the link fell back. LnkSta2 on the root port showing an equalization phase incomplete would strengthen this. The hypothesis is a signal-integrity issue in this chassis's path (riser, retimer setting, cable for a U.2/E3.S backplane). The disambiguating experiment: move the drive to a slot without the riser, or move a known-good drive into this slot. If the speed follows the slot, the problem is the platform path; if it follows the drive, the drive.

Conclusion and confidence

Likely platform signal-integrity fallback to Gen3; confidence medium until the swap experiment is done. Notice that no NVMe tool was needed, and that the NVMe controller is behaving perfectly: it is simply on a slower road.

Common mistakes

  • Running lspci -vv without sudo and concluding "the device has no capabilities". Look for <access denied>.
  • Reading LnkCap as the current speed. LnkCap is the capability; LnkSta is now.
  • Checking only the endpoint. The root port's LnkCap, LnkCtl2 and DLActive tell the other half.
  • Treating DLActive- on an endpoint as a dead link. Endpoints usually do not report it.
  • Declaring "no errors" from a clean UESta/CESta after the kernel already logged and cleared them.
  • Trusting names over numbers. An outdated pci.ids can name the wrong product; IDs from -nn are the truth.
  • Using setpci with "=" to "just test something" on a mounted, live drive.
  • Assuming the IRQ in "Interrupt: pin A routed to IRQ 40" is the NVMe interrupt. With MSI-X enabled it is the unused legacy line.
  • Comparing lspci text across pciutils versions and seeing "changes" that are only decoder differences.
  • Running -xxxx across an entire production fleet without knowing whether any device there has read side effects.

Senior engineer insight

A single lspci capture is a photograph. Seniors take three: before the workload, during it, after the failure, always on both ends of the link, and always keep the raw -xxxx dump so a better decoder can re-read it next year. They also note the time and the pciutils and kernel versions, because "the link said 8GT/s" means little without "at 14:02:11, before the reset, pciutils 3.x".

For every field, ask: did the device hard-wire it, did firmware/kernel program it, or did hardware set it in response to an event? A wrong hard-wired value is a device bug; a wrong programmed value is a platform or driver decision; an unexpected event bit is a symptom. Mixing these up sends bug reports to the wrong team.

On power-managed laptops, reading config space can resume a sleeping device; on fragile devices, reading certain registers has side effects; on a busy server, a fleet-wide -xxxx generates thousands of TLPs. A senior engineer chooses the least intrusive probe that answers the question.

Lab: PCIe inspection of an NVMe SSD from Linux

Objective

Produce a complete, evidence-backed PCIe profile of one NVMe SSD and its upstream port, and state for each finding what it proves and what it does not.

Skills

lspci option family; hand-decoding a config header; setpci reads; sysfs PCI attributes; link and error assessment.

Safety

Safe lab Read-only. No setpci command in this lab contains =. Do not write to any file under /sys/bus/pci. On unfamiliar production hardware, skip step 4's -xxxx and use -vv only. Ideal environment: a QEMU VM with an emulated NVMe controller (see Lab Environment), or your own lab machine.

Hardware required

Any Linux system with an NVMe SSD, or a QEMU VM started with -device nvme.

Software required

pciutils (lspci, setpci), Python 3, sudo.

Input

The machine. Optionally the synthetic image from pcicfg_decode.py --selftest.

Expected output

A one-page profile: BDF, IDs, class, driver, upstream port, BAR0 address and size, MPS/MRRS on both ends, link capability and status on both ends, MSI-X vector count, AER status and counters, IOMMU group, NUMA node, and a verdict line with confidence.

Background

Sections "Engineering explanation" and "Linux view" of this chapter; Chapter 18 for config space.

Step 1: find the device

lspci -nn -D | grep -i '\[0108\]'
lspci -tv

Record the BDF and the upstream root port. On QEMU, the emulated controller appears with Red Hat/QEMU IDs and class 0108.

Step 2: decode the header by hand

lspci -x -s 01:00.0

Fill in the header table from this chapter with your own bytes. Then confirm with lspci -nn -v -s 01:00.0.

Step 3: capabilities and link, both ends

sudo lspci -vv -s 01:00.0 | grep -E 'DevCtl:|MaxPayload|LnkCap:|LnkSta:|LnkCtl2|MSI-X'
sudo lspci -vv -s 00:01.1 | grep -E 'MaxPayload|LnkCap:|LnkSta:|LnkCtl2|SltSta'
sudo setpci -s 01:00.0 CAP_EXP+0x12.w
sudo setpci -s 00:01.1 CAP_EXP+0x12.w

Step 4: raw dump and offline decode

sudo lspci -xxxx -s 01:00.0 > dump.txt
lspci -F dump.txt -vv          # decode the saved dump, no hardware access
sudo cat /sys/bus/pci/devices/0000:01:00.0/config > config.bin
python3 pcicfg_decode.py --file config.bin

Step 5: sysfs and counters

Run the pcie-inspect.sh block from the Linux view and record every value.

Observation

Note any field where the two ends disagree, any status bit set, any counter not zero, and any capability printed with <?>.

Questions

  1. Is the link at the lower of the two capabilities? If not, what are the candidate reasons?
  2. Do MPS values match across the link? Does MRRS have to?
  3. How many MSI-X vectors does the function support, and how many did the driver allocate (msi_irqs)? Why might they differ?
  4. Are the AER status bits all clear? What would you need to check before calling the device error-free?
  5. Which of your findings came from a live register read, and which from kernel bookkeeping?

Challenge

Without using lspci's decoding, compute the current link speed, width, MPS and MRRS from the four bytes returned by two setpci reads, and the BAR0 address from the -x dump.

Hints

Link Status is CAP_EXP+0x12: speed is bits 3:0, width bits 9:4. Device Control is CAP_EXP+0x08: MPS is 128 << bits 7:5, MRRS is 128 << bits 14:12. BAR0 is little-endian at 10h; clear the low 4 bits; if bits 2:1 are 10b, the next DW is the upper half.

Solution

For the reference Lab SSD: Link Status 0x1044 → speed index 4 (16.0 GT/s), width 4; Device Control 0x293F → bits 7:5 = 001b → 256 bytes, bits 14:12 = 010b → 512 bytes; BAR0 bytes 04 00 60 fe + 00 00 00 00 → 0x00000000FE600000, 64-bit, non-prefetchable. MPS must match what both ends are programmed to accept (software programs the same value or the minimum across the path); MRRS is a per-requester limit and need not match. MSI-X supported (33) can exceed allocated vectors when the driver creates fewer I/O queues than vectors (for example, fewer CPUs). A clear AER status requires a check of the kernel log and aer_dev_* counters before claiming no errors occurred. Live reads: everything from config, current_link_*, max_link_*; kernel bookkeeping: driver, IOMMU group, NUMA node, aer_dev_*, msi_irqs.

What a senior engineer notices

Whether the root port reports Slot capabilities (hot-plug capable bay or soldered-down M.2), whether DPC is present on the root port (it changes how a link failure will look in the log), whether ASPM is enabled (latency outliers), whether Completion Timeout is at a short range (spurious CmpltTO under heavy load), and whether the drive sits on the NUMA node of the CPUs that issue its I/O.

Failure variants

  • Link at ×2 instead of ×4: lane fault, bifurcation setting, adapter wiring.
  • Capabilities: <access denied>: you forgot sudo.
  • Device present, no driver: the nvme module not loaded, or the device bound to vfio-pci for passthrough.
  • All-ones dump: the device fell off; go to Chapter 71.

Extension

Exercises

  1. Write the lspci command that prints only the NVMe controllers with numeric IDs and domain, and explain each flag.
  2. From lspci -tv output of a system with a PCIe switch, identify the switch upstream port, its downstream ports, and the SSDs behind each.
  3. Given a Device Control value of 0x5937, compute MPS and MRRS and list the enabled error-reporting bits.
  4. Explain why current_link_speed can be correct and the drive still slow. Name three non-link causes.
  5. Write a setpci read that returns the AER Correctable Error Status of the root port, and say what each set bit would mean.
  6. Design a cron-free method to detect a link that occasionally drops to Gen3 for a few seconds and returns. (Hint: what in sysfs counts, and what in the log records?)
Answers

1: lspci -nn -D -d ::0108 (class filter form -d [vendor]:[device][:class]) or lspci -nn -D | grep '\[0108\]'. 2: the switch upstream port is the bridge directly under the root port; its secondary bus contains the downstream-port bridges; each downstream port's secondary bus holds one SSD. 3: 0x5937 → bits 7:5 = 001b → 256 B; bits 14:12 = 101b → 4096 B; bits 3:0 = 0111b → Correctable, Non-Fatal and Fatal reporting enabled, UR reporting disabled. 4: queue depth too low, CPU/NUMA placement, small block size, filesystem or device-side throttling (thermal), interrupt coalescing. 5: sudo setpci -s 00:01.1 ECAP_AER+0x10.l; bits 0 RxErr, 6 BadTLP, 7 BadDLLP, 8 Rollover, 12 Timeout, 13 Advisory Non-Fatal. 6: a link speed change sets Link Bandwidth Management Status in the root port's Link Status and, when the kernel's bandwidth notification support is active, can be logged; correlating with aer_dev_correctable increments and journalctl timestamps finds the episodes. Sampling current_link_speed alone would miss short dips.

Quiz

  1. Which lspci option prints the full 4096-byte extended configuration space in hex?

    • -x
    • -xxx
    • -xxxx
    • -vvv
    Answer and reasoning

    -x is 64 bytes, -xxx 256 bytes, -xxxx 4096 bytes. -vvv decodes but does not dump.

  2. A normal user runs lspci -vv and sees Capabilities: <access denied>. Why?

    • The device has no capabilities
    • sysfs only returns the first 64 bytes of config space to unprivileged users
    • The driver locked config space
    • ECAM is disabled
    Answer and reasoning

    The kernel restricts reads beyond the standard header to privileged users; capabilities live beyond 40h.

  3. An endpoint shows LnkSta: ... DLActive- while I/O is working. What is the best interpretation?

    • Normal: DL Link Active is meaningful mainly on downstream ports that report it
    • The link is down
    • The Data Link Layer is in replay
    • The device is in L1
    Answer and reasoning

    Check the bit on the root port, where LLActRep+ indicates it is reported. An endpoint commonly shows DLActive-.

  4. Which command is a write?

    • setpci -s 01:00.0 COMMAND
    • setpci -s 01:00.0 CAP_EXP+0x12.w
    • lspci -xxxx -s 01:00.0
    • setpci -s 01:00.0 COMMAND=0x0402
    Answer and reasoning

    The =value form writes. 0x0402 would clear Bus Master Enable, stopping all DMA: an expert-only, disruptive action.

  5. The AER status on a device is all clear, yet the kernel log contains corrected AER messages from it. Which statement is most accurate?

    • The log is wrong
    • The Linux AER driver handled and cleared the status bits after logging
    • The errors were masked
    • The device reset cleared sticky bits
    Answer and reasoning

    OS-native AER handling clears RW1C status after reporting. The aer_dev_* counters preserve the count.

  6. lspci shows Vendor ID ffff for a function that was working. What does this prove?

    • The SSD firmware returned 0xFFFF
    • The vendor ID was reprogrammed
    • Config reads are not completing successfully from a responsive function; the host synthesized all-ones
    • The NVMe controller is in shutdown
    Answer and reasoning

    0xFFFF is not a valid vendor ID; it is what the CPU receives when no successful completion arrives.

  7. Does current_link_speed = 16.0 GT/s prove that the link has been at 16 GT/s since boot? Explain.

    Model answer

    No. It is a sample of Link Status at read time. The link may have retrained down and back up (or been recovered by DPC/reset) in between. Evidence of history comes from kernel logs, AER counters, Link Bandwidth Management Status, or an analyzer.

  8. Why should you capture lspci from the root port as well as the SSD when investigating a slow link?

    Model answer

    The link speed is the outcome of both ends' capabilities and the downstream port's Target Link Speed. The root port also reports DLActive, Slot Status, LnkSta2 equalization progress and may have DPC. Without its view you cannot distinguish a capped platform from a failing link.

  9. Which sysfs file would you read to confirm that the NVMe function is owned by the kernel nvme driver rather than vfio-pci?

    • driver (symlink)
    • resource
    • class
    • msi_irqs
    Answer and reasoning

    The driver symlink names the bound driver; lspci -k prints the same.

  10. How many configuration TLP request/completion pairs does a full -xxxx dump of one function generate, approximately, and why?

    Model answer

    About 1024: config requests carry 1 DW, and 4096 bytes / 4 bytes = 1024 reads (implementations may read in other sizes in software, but on the wire each config TLP is 1 DW).

Interview questions

  1. (Beginner) How do you find which PCIe slot and root port an NVMe drive is attached to?

    Model answer

    lspci -nn -D to find the BDF (class 0108), lspci -tv to see the bridge above it, or readlink -f /sys/bus/pci/devices/<BDF> whose path lists every upstream port. Physical slot names come from lspci -vv "Physical Slot" on the bridge or /sys/bus/pci/slots/.

  2. (Beginner) What is the difference between LnkCap and LnkSta?

    Model answer

    LnkCap is a read-only description of what the port supports; LnkSta reports the speed and width negotiated now. The link runs at the best mutually supported setting that training achieved, possibly capped by Target Link Speed.

  3. (Intermediate) A drive shows MaxPayload 512 in DevCap but 256 in DevCtl. Is that a problem?

    Model answer

    No. DevCap is the maximum supported; software programs DevCtl to a value all components on the path support, often the minimum. 256 bytes is common. A problem would be DevCtl MPS larger than what the partner accepts.

  4. (Intermediate) When would you use setpci instead of lspci?

    Model answer

    To read one register quickly and repeatedly in a script (polling Link Status during a stress run), to read a field lspci does not decode, or to get the raw value for a bug report. Never to write on a live system unless it is an expert lab with a recovery plan.

  5. (Advanced) lspci shows the device fine, but nvme list shows nothing. Where do you look?

    Model answer

    Config space works, so the link is up. Check lspci -k for the bound driver, then the kernel log for nvme probe errors (controller not ready, CSTS.CFS, timeouts on Identify), then Mem+/BusMaster+, and BAR assignment (resource). This is the boundary between PCIe health and NVMe controller health.

  6. (Advanced) What are the risks of running lspci -xxxx across a fleet?

    Model answer

    Some devices have registers with read side effects; reading them can confuse or hang the device. Reads may resume suspended devices. It generates traffic. Prefer -vv and targeted reads in production; full dumps in the lab.

  7. (Senior) How would you prove that an intermittent Gen4-to-Gen3 downgrade is caused by the platform rather than the SSD?

    Model answer

    Swap experiments: known-good SSD in the suspect slot and suspect SSD in a known-good slot, with identical workloads, recording both ends' LnkSta, LnkSta2, AER correctable counters and kernel bandwidth messages. If the behaviour follows the slot, the platform path is implicated. Then use margining (Lane Margining at the Receiver, where supported) or an analyzer on the suspect path. State confidence explicitly.

  8. (Senior) Why do sticky error bits matter for post-mortem analysis?

    Model answer

    They survive conventional resets, so after a recovery the error that triggered it may still be readable, provided the OS did not clear it. Seniors capture config space immediately after an incident, before any manual reset, and know which handling mode (OS-native or firmware-first) the platform uses.

Chapter summary

lspci decodes configuration space read live through sysfs and ECAM; its options range from a one-line inventory to a 4 KiB hex dump, and decoding beyond the 64-byte header needs root. setpci reads named registers precisely; its write form is an expert-only operation that can stop DMA, break the link or erase evidence. sysfs adds the kernel's knowledge: driver binding, link speed/width summaries, AER counters, IOMMU group, MSI vectors. Every observation is a sample in time from one end of a link. Always compare capability with status, endpoint with root port, and live values with logs.

Do not move on until you can:

  • find an NVMe function's BDF, IDs, class, driver and upstream root port in under a minute
  • hand-decode the 64-byte header, including a 64-bit BAR
  • read MPS, MRRS, link speed and width from lspci and from raw setpci values
  • explain why a clean AER status does not prove that no error occurred
  • say which TLPs an lspci run produces and what all-ones means on the wire
  • list the sysfs PCI attributes you would capture for a bug report, and which are live reads
  • explain why setpci ...=value is an expert lab operation
