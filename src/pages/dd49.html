This module follows the drive through the minutes when no operating system exists. It covers the firmware driver's timing contract with the controller, Boot Partition reads at Transaction Layer Packet (TLP) level, the internal structure of the NVMe Boot Firmware Table (NBFT), the firmware-to-OS handoff for NVMe over TCP (NVMe/TCP) boot, and the failures that only show up at the seams: a timeout chosen too short, an identity that changes between firmware and OS, and Direct Memory Access (DMA) that outlives the code that started it.

Orientation

Chapter 64 walked through the pre-OS journey: Unified Extensible Firmware Interface (UEFI) enumeration, option ROMs, a local boot from a namespace with firmware queues at 0x7F00_0000, Boot Partitions, and NVMe over Fabrics (NVMe-oF) boot with the NBFT. This module assumes all of that. It works on three seams the chapter only named. The first is the timing seam: the Capability Timeout (CAP.TO) and how firmware should honour it. The second is the data seam: how the NBFT carries host identity, interfaces and namespaces across the handoff, byte by byte. The third is the ownership seam: who owns the controller, the queues and the network sessions at each moment between power-on and the root file system mounting.

Read NVMe Boot first. You also need Controller Initialization (CC/CSTS sequence), NVMe over Fabrics (Connect, NQNs, discovery), NVMe/TCP (Protocol Data Units (PDUs)), and PCIe Reset. Related modules: Reset, NVMe/TCP.

Kid story

A big ship arrives at a harbour at night. The captain does not know the harbour, so a small boat brings out a pilot. The pilot steers the ship through the narrow entrance and ties it to the dock. Then the pilot climbs down, and the captain takes over for the rest of the journey.

Before leaving, the pilot writes a card: "Your ship's name, which dock, which rope is tied to which post, and the harbour master's radio channel." The captain must use the card. If the captain forgets it and calls the harbour master using a different ship's name, the harbour master says "I don't know you" and the ship cannot unload.

Two more rules. The pilot must wait as long as the harbour's rule book says before deciding the dock is closed, not give up after one minute. And the pilot must untie every rope it was holding before leaving. A rope still pulling on the ship after the captain takes over causes accidents nobody can explain.

The central concept on the ladder: a handoff of ownership

A pilot brings the ship in, writes a card, unties the ropes and leaves; the captain uses the card to carry on.

Firmware brings up the storage path, reads the loader, records how it did so, and must leave the device quiet; the OS reconstructs the path from that record.

UEFI drivers with polling queues in low memory; a NIC and TCP/IP stack in firmware; an ACPI table in reserved memory; an OS driver that resets the controller.

Base 2.4 (initialisation, CAP.TO, Boot Partitions), NVMe Boot 1.4 (pre-OS NVMe-oF, NBFT), UEFI (driver model, ExitBootServices, Pass Thru), ACPI (table header and checksum).

Local: CC.EN → CSTS.RDY within CAP.TO → admin commands → reads. Fabric: discovery → Connect → reads → NBFT → disconnect by abandonment → OS Connect.

PCIe: MWr32/MRd32 to BAR0 0xFE60_xxxx and DMA to 0x7F00_xxxx, then the OS reset. Network: two Connects with the same host NQN, minutes apart.

Ask who owned the device at the failing moment, which identity it used, and what timing contract it honoured.

From libnvme 1.16.2 nbft.h: signature 4E424654h ("NBFT"); the entire table including the checksum field shall sum to 0; descriptor type values 0 Header, 1 Control, 2 Host, 3 HFI, 4 SSNS, 5 Security, 6 Discovery, 7 HFI Transport Info, 9 SSNS Extended Info; heap objects as 32-bit offset from table start plus 16-bit length; TCP transport type 3. The ACPI header layout (36 bytes, checksum at byte 9) is ACPI-standard. The example system's CAP = 0x0040_0830_1401_0FFF has TO = 14h = 20 × 500 ms = 10 s (Chapter 64's firmware trace used an illustrative 30 s).

The specifications do not say how long a firmware driver should keep retrying a discovery controller, how firmware should order multiple boot paths, or that the OS must reconnect within a time limit (the target's keep-alive and controller-loss timers decide what survives). The Base specification does not require firmware to disable the controller before handoff; good firmware does, and good OS drivers reset regardless. This module does not give Boot Partition register bit positions.

Never assume: that a slow CSTS.RDY is a fault; that firmware cleaned up; that the OS will find the same interface name; that the host NQN in the OS image equals the one in firmware setup; that a corrupted NBFT is reported loudly.

Labs

Safe lab Labs are simulation and analysis. Booting real systems over the network or reading Boot Partitions on test hardware is Expert lab work on lab machines only; never write Boot Partitions on drives you depend on.

Beginner lab — map the seams

Objective: list ownership and identity at each boot stage. Prerequisites: mechanism table. Setup: paper. Procedure: for local boot and fabric boot, fill a table with columns: stage, owner of the controller (or session), queues or connection used, identity presented, artefact handed on. Observations: note where two owners overlap. Questions: at which stage can a late DMA occur? At which stage does the host NQN matter twice?

Solution

Local: firmware (queues at 0x7F00_xxxx) → loader (same driver) → gap after ExitBootServices (no owner, device maybe still enabled) → OS driver after reset. Fabric: firmware sessions (host NQN from setup) → loader → gap (target still has controller 1 until keep-alive expiry) → initramfs (host NQN from NBFT). Late DMA belongs to the local gap; the host NQN matters at the firmware Connect and the OS Connect.

Extension: add a Boot Partition stage before full initialisation.

Intermediate lab — build and break an NBFT model

Objective: understand header, heap objects and checksum. Prerequisites: architecture section. Setup: save as nbft_toy.py; run it. Descriptor bodies are a teaching format, not the real layout.

#!/usr/bin/env python3
"""nbft_toy.py - build and check a TEACHING model of an NBFT.

Real parts: the 36-byte ACPI table header (signature, length, revision,
checksum, OEM fields, creator fields) and the rule that all bytes of the
table sum to 0 modulo 256. Header extension (heap offset/length) and the
6-byte heap object (le32 offset, le16 length) follow libnvme's nbft.h.
Toy parts: the descriptor bodies below are a simplified record format,
NOT the NVMe Boot 1.4 byte layout. Read the specification for that.
"""
import struct

HOSTNQN = b"nqn.2014-08.org.nvmexpress:uuid:5e1f0000-0000-4000-8000-000000000010"
SUBNQN = b"nqn.2026-10.org.example:lab-ssd"

def heap_obj(off, ln):
    return struct.pack("<IH", off, ln)

def build(trsvcid=b"4420", traddr=b"192.0.2.20", nsid=1, corrupt=False):
    heap = bytearray()
    def put(b):
        off = len(heap)
        heap.extend(b + b"\0")          # NUL-terminate for readability
        return off, len(b)
    s_nqn, s_traddr, s_svc, h_nqn = put(SUBNQN), put(traddr), put(trsvcid), put(HOSTNQN)
    # toy descriptors: (type, index, flags, fields...)
    host = struct.pack("<BBH", 2, 0, 0x0007) + b"\x5e\x1f" + b"\0" * 14
    hfi = struct.pack("<BBHB4sB4s", 3, 1, 0x0001, 3, bytes([192, 0, 2, 10]), 24,
                      bytes([192, 0, 2, 1]))
    ssns = struct.pack("<BBHBI", 4, 1, 0x0001 | 0x0080, 3, nsid)
    hdr_len = 36 + 4 + 4 + 6 + 1 + 3          # ACPI hdr + heap off/len + sig obj + minor + pad
    body = host + hfi + ssns
    heap_off = hdr_len + len(body) + 4 * 6     # four heap objects follow the body
    # heap objects hold offsets from byte 0 of the table, not from the heap
    refs = [heap_obj(heap_off + o, l) for o, l in (h_nqn, s_nqn, s_traddr, s_svc)]
    body += b"".join(refs)
    total = hdr_len + len(body) + len(heap)
    acpi = struct.pack("<4sIBB6s8sI4sI", b"NBFT", total, 1, 0, b"LABOEM",
                       b"LABNBFT ", 1, b"LABF", 1)
    ext = struct.pack("<II", heap_off, len(heap)) + heap_obj(0, 0) + b"\x00" + b"\0" * 3
    t = bytearray(acpi + ext + body + heap)
    t[9] = (-sum(t)) & 0xFF                    # checksum at byte offset 9
    if corrupt:
        t[heap_off + 5] ^= 0x01                 # flip one bit in the subsystem NQN
    return bytes(t)

def check(t):
    sig, length, rev, csum = struct.unpack_from("<4sIBB", t, 0)
    problems = []
    if sig != b"NBFT": problems.append("bad signature")
    if length != len(t): problems.append("length %d != %d" % (length, len(t)))
    if sum(t) & 0xFF: problems.append("checksum: table sums to %02Xh, not 00h" % (sum(t) & 0xFF))
    heap_off, heap_len = struct.unpack_from("<II", t, 36)
    if heap_off + heap_len > length: problems.append("heap outside table")
    return problems, heap_off, heap_len

def strings(t):
    _, heap_off, _ = check(t)
    out = []
    p = heap_off - 4 * 6
    for name in ("host NQN", "subsystem NQN", "traddr", "trsvcid"):
        off, ln = struct.unpack_from("<IH", t, p); p += 6
        out.append("%-13s @%3d len %2d: %s" % (name, off, ln, t[off:off + ln].decode(errors="replace")))
    return out

if __name__ == "__main__":
    for label, kw in (("good", {}), ("corrupted", {"corrupt": True})):
        t = build(**kw)
        problems, ho, hl = check(t)
        print("%-9s table %d bytes, heap at %d (%d bytes): %s" %
              (label, len(t), ho, hl, "; ".join(problems) or "OK"))
    for line in strings(build()):
        print("   ", line)

Procedure: (1) change the target port to 4421 and confirm the checksum is recomputed; (2) flip two bits that cancel in the byte sum (add 1 to one byte, subtract 1 from another) and run check(); (3) make a heap object point beyond the table. Questions: what does a byte-sum checksum fail to catch? Why must parsers bound-check heap objects? Expected reasoning: the checksum detects accidental single changes, not compensating ones; heap offsets come from firmware and must be distrusted.

Solution

(2) passes the checksum: an 8-bit sum misses compensating errors and any reordering of bytes. (3) a parser that trusts the offset reads outside the table — at best garbage, at worst a crash in early boot. Real parsers (libnvme) check offsets against the table length. A senior lesson: the ACPI checksum is integrity against accidents, not validation; parse defensively.

Advanced lab — timeout and retry policy by simulation

Objective: quantify firmware timeout and discovery retry choices. Prerequisites: Controller Initialization. Setup: save as boot_budget.py; run it.

#!/usr/bin/env python3
"""boot_budget.py - Monte Carlo model of two pre-OS timing contracts.

1. Local boot: firmware waits for CSTS.RDY with its own timeout. CAP.TO is
   the device's promise (here 10 s). Ready-time distribution is invented
   for teaching: most boots are fast, boots after an unsafe shutdown are slow.
2. Fabric boot: discovery controller retries before falling back to the
   subsystem address stored in firmware settings.
All numbers are synthetic; the shape of the result is the lesson.
"""
import random

CAP_TO_S = 10.0
N = 200_000

def ready_time(rng):
    if rng.random() < 0.97:                       # clean shutdown last time
        return rng.uniform(0.3, 0.7)
    t = rng.lognormvariate(1.0, 0.6)              # recovery after power loss
    return min(t, CAP_TO_S * 0.98)                # device honours its CAP.TO

def local(timeout_s, rng):
    fails = sum(ready_time(rng) > timeout_s for _ in range(N))
    return fails / N

def fabric(discovery_up, tries, per_try_s, rng):
    t = rng.uniform(1.5, 3.0)                     # link up + DHCP
    if discovery_up:
        t += rng.uniform(0.05, 0.2)               # discovery connect + log page
    else:
        t += tries * per_try_s                    # every try times out
    t += rng.uniform(0.1, 0.4)                    # connect admin/I/O, Identify
    t += rng.uniform(0.8, 2.0)                    # read GPT, ESP, loader over TCP
    return t

if __name__ == "__main__":
    rng = random.Random(64)
    print("Local boot, CAP.TO = %.0f s, %d simulated boots" % (CAP_TO_S, N))
    for timeout in (2.0, 5.0, 10.0, 15.0):
        print("  firmware timeout %4.1f s -> 'no bootable device' rate %.4f%%"
              % (timeout, 100 * local(timeout, rng)))
    print("Fabric boot, p50 / p99 time to loader (s)")
    for label, up, tries, per in (("discovery up", True, 0, 0),
                                  ("down, 3 x 5 s", False, 3, 5.0),
                                  ("down, 1 x 2 s", False, 1, 2.0)):
        ts = sorted(fabric(up, tries, per, rng) for _ in range(20_000))
        print("  %-14s %5.1f / %5.1f" % (label, ts[len(ts) // 2], ts[int(len(ts) * 0.99)]))

Expected output (deterministic with seed 64):

  firmware timeout  2.0 s -> 'no bootable device' rate 2.1235%
  firmware timeout  5.0 s -> 'no bootable device' rate 0.4835%
  firmware timeout 10.0 s -> 'no bootable device' rate 0.0000%
  firmware timeout 15.0 s -> 'no bootable device' rate 0.0000%
Fabric boot, p50 / p99 time to loader (s)
  discovery up     4.0 /   5.2
  down, 3 x 5 s   18.9 /  20.1
  down, 1 x 2 s    5.9 /   7.1

Procedure: (1) set the unsafe-shutdown share to 10% and rerun; (2) remove the min() cap so the device sometimes exceeds CAP.TO, and see which timeout catches it; (3) find the shortest discovery policy that keeps p99 under 8 s with discovery down. Questions: who is at fault in each failure case? What should firmware log when it gives up?

Solution

With timeout below CAP.TO, failures are the firmware's fault: the device kept its promise. Removing the cap creates device faults that even a CAP.TO-length wait cannot fix; firmware should then log "CSTS.RDY not set within CAP.TO (10 s)" with CSTS (including CFS) so the failure is attributable. One 2 s discovery try keeps p99 near 7 s. A fleet with 2% "no bootable device" after power events is the classic signature of a firmware timeout shorter than CAP.TO.

Extension: model CRTO: a smaller ready-without-media time and a larger ready-with-media time, and decide which one gates the firmware's first admin command.

Senior forensic lab — the reboot that loses one server in 300

Objective: reason from fleet evidence across firmware, OS and target. Prerequisites: all traces. Setup (synthetic evidence): 6,000 diskless servers boot over NVMe/TCP; after a scheduled reboot wave, 21 hang at "waiting for root device". All 21 booted firmware successfully. Target logs show their OS Connects succeeded, then I/O queue Connects failed with Connect Invalid Parameters. Each of the 21 reconnected within 3 s of the firmware's Connect. Controller limit per host on the target: 2.

Solution

Identity is fine (admin Connect succeeded). The firmware's abandoned controller still counts until keep-alive expiry, so a fast OS reconnect creates a second controller for the same host; I/O queue Connects then hit the target's resource limit (shown as Invalid Parameters on this target — check what your target returns). Servers that reconnect after the old controller expired are unaffected, which explains the small fraction. Decisive experiment: delay initramfs connection by keep-alive time + 1 s on a test group, or raise the per-host limit; capture target logs. Fixes: firmware sends a disconnect (or a short keep-alive timeout in its Connect) before handoff; target limits account for boot overlap. Confidence before experiment: medium-high.

Extension: write the post-incident report section "why this did not appear in lab testing".

Interview

Beginner

  1. What does firmware need to boot from a local NVMe SSD?

    Model answer

    Enumeration, an NVMe driver, controller enable, Identify, an I/O queue, and reads of GPT, ESP and the loader.

  2. What is the NBFT for?

    Model answer

    Telling the OS how firmware reached the fabric boot namespace so it can reconnect the same way.

  3. Why does the OS reset the controller?

    Model answer

    To start from a known state, regardless of what firmware left.

  4. What is a Boot Partition?

    Model answer

    A small optional storage area read through registers before full initialisation, with two IDs for A/B updates.

  5. What does CAP.TO mean?

    Model answer

    Worst-case time for CSTS.RDY to follow CC.EN, in 500 ms units.

Intermediate

  1. Why are firmware TLPs 32-bit?

    Model answer

    Firmware typically allocates buffers below 4 GiB (0x7F00_0000 here), and MMIO BAR0 is below 4 GiB.

  2. How does firmware know a Boot Partition read finished?

    Model answer

    BPINFO read status shows completed; ordering ensures earlier posted data writes are visible first.

  3. What is a heap object?

    Model answer

    An offset-from-table-start and length pair locating variable data in the NBFT heap.

  4. Connect Invalid Host after fabric boot: first suspect?

    Model answer

    OS host NQN differs from the firmware's; initramfs did not use the NBFT.

  5. Why do two controllers exist briefly for one host?

    Model answer

    Firmware sessions are abandoned; the target removes them only at keep-alive expiry.

Advanced

  1. How should firmware pick its ready timeout?

    Model answer

    At least CAP.TO (or the applicable CRTO value), logging CSTS on failure; never a fixed short value.

  2. What must firmware do at ExitBootServices?

    Model answer

    Wait for or abort outstanding commands, disable the controller (and ideally bus mastering), and disconnect fabric sessions where practical.

  3. How would you validate NBFT generation?

    Model answer

    Parse with independent parsers, compare to setup, cover static/DHCP, VLAN, multipath, security, and corrupt-table handling in the OS.

  4. What does A/B mean for Boot Partitions?

    Model answer

    Write the inactive partition, verify it, then switch the active ID; a failed write never removes the working copy.

  5. Why is discovery retry policy an SLA decision?

    Model answer

    Retries trade boot time against resilience; at fleet scale each second multiplies across reboots.

Senior

  1. Design identity management for diskless servers.

    Model answer

    Per-server host NQN/ID provisioned in firmware, published in NBFT, consumed by initramfs, never baked into images; allow lists managed centrally.

  2. 2% boot failures after a data-centre power event. Approach?

    Model answer

    Check firmware ready timeout versus CAP.TO; group by firmware version and drive model; capture CSTS; lab-reproduce with power cuts.

  3. Who owns the handoff gap?

    Model answer

    Both: firmware quiesces, OS resets early with IOMMU on; tests must cover the gap explicitly.

  4. When would you use Boot Partitions in a product?

    Model answer

    Embedded or appliance designs needing a first stage before a full driver; not on general servers using UEFI and an ESP.

  5. How do you keep boot behaviour stable across firmware updates?

    Model answer

    Boot regression suite with timing budgets, NBFT diffs, identity checks, and slow-ready injection on each release.

    • The start of the heap
    • The descriptor
    • The end of the header
    Answer and reasoning

    Per libnvme's description of the heap object.

  4. A 128 KiB Boot Partition read at MPS 256 produces how many device writes at minimum?

    • 32
    • 128
    • 256
    • 512
    Answer and reasoning

    131,072 / 256 = 512.

  5. Connect Invalid Host is:

    • SCT 0h SC 84h
    • SCT 1h SC 84h
    • SCT 1h SC 82h
    • A TCP reset
    Answer and reasoning

    Command-specific status 84h (82h is Invalid Parameters), per libnvme and Linux; confirm in Base 2.4.

  6. Which artefact passes a local boot path to the OS?

    • NBFT
    • BPINFO
    • UEFI boot variables and device paths
    • CAP
    Answer and reasoning

    NBFT is for fabric boot.

  7. Why does an 8-bit byte-sum checksum not prove an NBFT is correct?

    Model answer

    Compensating changes and wrong-but-consistent content pass; it detects accidents only.

  8. Why might a late DMA corrupt OS memory only on some boots?

    Model answer

    It depends on whether the page was already reused and on command latency, both variable.

Teach-back

To a child — model

"A pilot steers a ship into harbour, writes a card saying the ship's name and dock, lets go of every rope, and leaves. The captain uses the same name from the card. If the captain uses a different name, the harbour won't let the ship unload."

To a junior engineer — model

"Firmware brings the controller up, waiting at least CAP.TO, reads the loader, and for fabric boot writes an NBFT with host identity, interfaces and namespaces. The OS resets the controller or reconnects using the NBFT. Most boot bugs are short timeouts, identity mismatches, or firmware leaving the device running."

To a senior engineer — model

"Boot is a chain of ownership transfers with gaps. Contracts at each seam: timing (CAP.TO/CRTO), identity (host NQN/ID via NBFT), and quiescence (no DMA or live sessions across handoff). Instrument each seam, test with slow-ready and unreachable-discovery injection, and treat images that carry identity as defects."
