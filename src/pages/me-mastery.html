Reading a chapter is not mastery. This page gives you the loop that turns a concept into something you can explain, find in a trace, break on purpose and debug, plus the reasoning tools senior engineers use on every capture: a universal event model, a timeline reconstruction method, the first-abnormal-event rule, and the discipline of negative evidence and trace coverage.

Why this part exists

Most learners stop at "I understood it when I read it". Two weeks later they cannot draw the sequence; two months later, faced with a real capture, they recognise the words but not the events. The difference between recognition and mastery is that mastery survives a new situation: an unfamiliar trace, a failure nobody has seen, a question from a skeptical senior.

The second half of this page is about reasoning on traces. Every NVM Express (NVMe) over PCI Express (PCIe) investigation reduces to the same moves: turn raw rows into events, arrange events into a timeline, compare it with the expected timeline, find the first point where they differ, walk backward to its cause, and be honest about what the capture could and could not have seen. These moves are learnable, and this page drills them.

Learning objectives

  • Run the twelve-stage mastery loop on any concept and produce evidence for each stage.
  • Explain one concept at child, junior and senior level so that the three versions are recognisably the same mechanism.
  • Answer the five-question depth test (what, why, how, failure, proof) and know when an answer is not good enough to move on.
  • Identify start, trigger, request, response, completion, side effect, expected next event, actual next event and anomaly in a trace.
  • Produce counterexamples that break naive interpretations, and separate nine commonly confused pairs of concepts.
  • Express any trace row in the seventeen-field event model.
  • Reconstruct a T0–T7 timeline and compare expected with observed.
  • Walk backward from symptom to first deviation to preceding cause.
  • Use absence of events as evidence only when coverage supports it, and write a coverage statement for any capture.

The story

Mia read a whole book about riding a bicycle. She could tell you about pedals, balance and brakes. Then she sat on a bicycle and fell over. Her uncle did not give her another book. He held the saddle while she pedalled (doing it), let go for three metres (trying it alone), made her stop on purpose (practising what happens when it goes wrong), took her onto gravel (a new situation), and finally asked her to teach her little brother. Only then did he say she could ride.

When something went wrong, like the chain falling off, her uncle did not look only at where the bike stopped. He walked back along the path to find the exact bump where the chain first slipped.

Airline pilots are not certified by reading manuals. They learn a system, fly it in a simulator, are given failures on purpose (an engine out on take-off), must explain their decisions, and pass a check ride. Accident investigators then use the flight data recorder the same way you will use a trace: rebuild a timeline, compare it to what should have happened, find the first deviation, and refuse to conclude anything the recorder was not wired to capture.

What maps well: mastery by doing, failure on purpose, teaching as a test, investigation by timeline and first deviation.

What does not map: a flight recorder records a fixed list of channels continuously; a protocol analyzer records only what its probe sees, often filtered, with a finite buffer, on one link. A crashed plane is one event; a storage failure can be a slow drift over millions of commands.

What it hides: in NVMe over PCIe, half the system state (host memory writes, controller internals) is never on the wire at all. The analogy makes recordings sound complete; yours never are.

The loop run once: the Phase Tag

  1. Intuition. A hotel guest checks a mailbox whose slots are never emptied, only overwritten. To know which letters are new, the hotel uses blue envelopes on odd rounds and red on even rounds. The guest knows which colour to expect this round.
  2. Terminology. Phase Tag (P): a bit in each Completion Queue Entry (CQE). Written by the controller, read by the host. Expected phase: host-side state. Wrap: when an index returns to 0.
  3. Structure. The CQE is 16 bytes; the phase bit sits in the DWORD that also carries the status field and Command Identifier (confirm the bit position in the Base Specification's CQE figure).
  4. Mechanism. The host zero-fills the CQ, expects phase 1. The controller writes entries with P = 1 until its tail wraps, then with P = 0. The host consumes entries while P equals its expected phase, flips its expectation when its head wraps, and writes the CQ head doorbell.
  5. Example. CQ1 has 1024 entries. Entry 1023 is written with P = 1; entry 0 on the second pass is written with P = 0. The host at head 1023 consumes it, wraps head to 0, flips expected phase to 0, and consumes entry 0.
  6. Counterexample. "A non-zero CID means a new entry." False: on the second pass, every slot already contains an old, non-zero entry. Only the phase distinguishes old from new.
  7. Trace. The phase bit is inside the CQE payload of an upstream Memory Write to the CQ region. If payload is not captured, the phase is not visible.
  8. Lab. Run queue_sim.py from Lab Progressions and watch P flip on the wrap.
  9. Failure. The "stale phase" scenario: the host flips its expected phase at the wrong time and reaps nothing while CQEs sit in memory. Symptom: an interrupt arrives but no completion is processed; eventually an I/O timeout.
  10. Recovery. The host's timeout handling aborts commands and, if needed, resets the controller, which reinitialises the queues and phase state.
  11. Explanation. The three levels below.
  12. Assessment. The five-question test below and the trace test in the next section.

Three-level explanation

Every major concept must be explainable to a child, a junior engineer and a senior engineer, and the three must be recognisably the same mechanism. If your child version and your senior version could describe different things, one of them is wrong.

Three levels for three concepts
ConceptChildJunior engineerSenior engineer
SQ tail doorbell"You put your request slip in the box, then tap the librarian's bell with a number on it: 'there are slips up to number 6'.""The driver writes the SQE into the SQ in host memory, then writes the new tail index to the queue's doorbell register in BAR0. The controller then fetches entries from its head up to the new tail.""A posted 4-byte MMIO write to BAR0 + 0x1000 + 2y·(4 << DSTRD). The SQE stores must be visible to the device before the doorbell write is observed; the driver's write barrier provides this. Batching amortises the MMIO cost; shadow doorbells in virtualised controllers reduce exits."
PCIe tag"Every parcel request gets a ticket number, and the parcel that comes back has the same number, so you know which request it answers.""A non-posted request carries a tag; its completions carry the same tag and the requester's ID, so the requester matches them. Tags are reused after completion.""Transaction ID = Requester ID + Tag. MSI-X"When the librarian finishes, she rings a particular phone so the right teacher answers.""The device writes a message (data value) to a message address the host programmed into the MSI-X table; the CPU's interrupt hardware turns that write into an interrupt for the right handler.""An upstream posted MWr whose address/data come from the table entry; per-vector and function masks hold messages pending in the PBA; ordering with the preceding CQE write follows PCIe ordering for posted writes (relaxed ordering attributes matter); coalescing trades latency for interrupt rate."

Counterexample: three levels that do not match

Child: "The bell carries the request to the librarian." Junior: "The doorbell write tells the controller where to fetch." The child version says the bell carries the request; the junior says the controller fetches it. One of them is wrong (the child version). A child version can simplify, but it must not invert who moves what. A corrected child version: "the bell says go and look in the box; the librarian walks over and takes the slips herself."

The five-question depth test

After every major concept, answer five questions. Do not proceed if you cannot.

  1. What? Define it precisely, with its owner.
  2. Why? What problem does it solve; what would happen without it?
  3. How? The mechanism, step by step.
  4. What happens if it fails? Name at least two failure modes and their symptoms.
  5. How would you prove what happened? Name the evidence: which trace rows, registers, logs, counters.

Applied: the CQ head doorbell

Weak versus strong answers
QuestionWeak answerStrong answer
What?"It tells the SSD we read the completion.""A controller register (on the lab system BAR0 + 0x100C for CQ1) to which the host writes its new CQ head index after consuming entries."
Why?"So it knows.""The controller must not overwrite unconsumed entries. Without the head index it cannot know which slots are free, so the CQ would either overflow or stall."
How?"The driver rings it.""After processing CQEs with the expected phase, the host advances its head (wrapping and flipping phase at the end) and writes the head value with a posted MMIO write. Hosts often batch: one head write per interrupt, not per CQE."
Failure?"It breaks.""(a) Never written: CQ fills; the controller stops posting; commands appear hung though the device has finished them. (b) Written with a value beyond the CQ's tail: invalid doorbell value (the specification defines how the controller reports this; check the asynchronous event definitions). (c) Written to the wrong offset (wrong DSTRD assumption): another queue's doorbell is corrupted."
Proof?"Look at the logs.""Analyzer: downstream MWr to BAR0 + 0x100C and their payloads, against upstream CQE writes to CQ1; host: driver state of CQ head and /proc/interrupts counts; device: asynchronous events and error log. Coverage statement for any 'no write seen' claim."

The fifth question is the one that separates engineers from readers. If you cannot say what evidence would distinguish "it happened" from "it did not", you do not yet understand the mechanism well enough to debug it.

Counterexample training

For every important concept there is a naive interpretation that sounds right and is wrong. Collect them. Each one below is a real category of mistake seen in investigations.

Naive interpretations and why they fail
Naive interpretationWhy it is false
"Every Memory Read Completion means the NVMe command completed."A PCIe Completion with Data answers a lower-level PCIe Memory Read (an SQE fetch, a PRP list fetch, write data). It is not an NVMe Completion Queue Entry. The NVMe completion is a Memory Write of a CQE into the CQ.
"One NVMe command produces one TLP."A 4 KiB Read on the lab system produces at least a doorbell, an SQE fetch and its completion, sixteen data writes, a CQE write, an MSI-X write and a head doorbell: about twenty-one TLPs.
"Completions arrive in submission order."The controller may complete commands in any order. Match by SQ identifier and CID.
"An interrupt means one new completion."One interrupt can cover many CQEs (coalescing, batching); a polled CQE can be consumed with no interrupt.
"Status SC in a PCIe completion means the NVMe command succeeded."PCIe success says the memory read worked. NVMe status lives in the CQE.
"The SQE fetch length is always 64 bytes."A controller may fetch several SQEs in one read (implementation-dependent), bounded by MRRS.
"A link-down error caused the timeout."Maybe the timeout handling reset the controller and the reset took the link down. Order matters; check timestamps.
"Gen5 means the drive is twice as fast as Gen4."Link rate bounds bandwidth; the device's media and controller usually limit first, and latency barely changes.
"The PRP address in the trace is the physical address of the buffer."With an IOMMU it is an IOVA.
"No UR seen, so the address was valid."Writes are posted; an IOMMU fault on a write produces no completion to the device. Look in the platform's IOMMU fault log.

Exercise

Write a counterexample for: "If the SQ tail doorbell was written, the controller received the command."

Model answer

The doorbell only tells the controller where the tail is. The controller must still fetch the SQE (an MRd, which can fail with UR/CA or a completion timeout), and the SQE contents may be invalid. Also, a doorbell write to a non-existent queue or with an invalid value is reported as an error, not accepted. "Received" requires at least a successful fetch (MRd with completed CplD carrying the SQE), and "accepted" requires a CQE status.

Layer-confusion training

Nine pairs cause most layer confusion. For each pair, learn one sentence and one test that distinguishes them.

Commonly confused pairs
PairDistinctionTest that tells them apart
NVMe command vs PCIe TLPA command is a 64-byte data structure in host memory; a TLP is a packet on a link.Is it in a queue slot (command) or in a packet header (TLP)?
NVMe CQE vs PCIe Completion TLPA CQE is a 16-byte record written into a CQ by a Memory Write; a Completion TLP answers a non-posted request.CQE: upstream MWr to the CQ region. Completion TLP: Type = Cpl/CplD, matched by tag.
Doorbell vs commandA doorbell carries only an index; the command is fetched separately.Doorbell payload is one DWORD; the command appears in a CplD after an MRd.
Controller vs namespaceA controller processes commands; a namespace is a quantity of storage addressed by commands.Controller: PCIe function, registers, queues. Namespace: NSID in the SQE.
Queue entry vs packetEntries live in memory; packets move entries (or parts of them).One MRd may carry several SQEs; one SQE may be split over completions.

Interrupt vs completionA completion is a CQE in memory; an interrupt tells the host to look.CQE without interrupt (polling, coalescing); interrupt with nothing new.
PCIe reset vs NVMe controller resetPCIe resets (conventional, function-level, hot) act on the link or function; an NVMe controller reset (CC.EN 1→0, or NVM Subsystem Reset) acts on the controller state.Did configuration space and link state change (PCIe reset) or only NVMe registers and queues (controller reset)?

Exercise: which layer?

  1. "The completion had status UR."

    Model answer

    PCIe completion TLP (Unsupported Request is a PCIe completion status). Not an NVMe status.

  2. "The completion had status Invalid Field in Command."

    Model answer

    NVMe CQE status (generic command status).

  3. "We reset the drive and it renegotiated at Gen3."

    Model answer

    A PCIe-level reset or retrain (link renegotiation). An NVMe controller reset alone does not retrain the link.

  4. "The drive supports NVMe 2.0, so it runs at Gen5."

    Model answer

    Mixes NVMe revision with PCIe generation; they are independent.

  5. "Namespace 2 timed out, so the controller is broken."

    Model answer

    Commands to namespace 2 timed out. Check whether commands to namespace 1 on the same controller still complete before blaming the controller.

Everyone in a story writes what they saw on a card of the same shape: when, who, to whom, what, and how sure. Then you can lay all the cards on one table in time order.

An event is a normalised record of one observation with fixed fields, including what was expected next and how confident we are.

Events come from different hardware vantage points: the analyzer probe on the link, the CPU (kernel log), the controller (log pages). Each has its own clock and blind spots.

Field meanings come from the specifications (tag, CID, status) and must be decoded per the cited revision before being written into the event.

Protocol events become groups: one NVMe command's doorbell, fetch, data, CQE and interrupt share a CORRELATION_ID.

A trace becomes a list of events; a timeline becomes a sorted list; an anomaly becomes an event whose ACTUAL_NEXT differs from EXPECTED_NEXT.

Debugging becomes a search for the earliest event with a mismatch, then backward reasoning over preceding events that share resources (queue, vector, address range).

The event model is used again in trace normalization and at scale in Automated Trace Analysis.

Timeline reconstruction

A timeline is the backbone of every investigation. Build it in eight slots, first for what should happen, then for what did.

Tool: the same reconstruction in code

The program below performs the expected-vs-observed match on normalised events, checks the coverage statement before treating absence as evidence, and searches backward for a preceding cause touching the MSI-X table.

#!/usr/bin/env python3
"""timeline.py - build an expected-vs-observed T0..T7 timeline from normalized events.

SYNTHETIC TEACHING EVENTS - NOT REAL DEVICE CAPTURES. Standard library only.
"""

# Capture coverage statement (the trace-coverage rule): without it, absence proves nothing.
COVERAGE = {
    "start_ns": -5_000_000, "end_ns": 30_000_000_000,
    "both_directions": True, "filters": "none", "timestamps_complete": True,
}

# Normalized events (a subset of the complete event model fields).
EVENTS = [
    {"id": "E1", "t": -2_400_000, "src": "RC", "dst": "Lab SSD", "layer": "TL", "type": "MWr",
     "addr": "BAR0+0x201C", "payload": "0x00000001", "meaning": "MSI-X table entry 1 Vector Control"},
    {"id": "E2", "t": 0, "src": "RC", "dst": "Lab SSD", "layer": "TL", "type": "MWr",
     "addr": "BAR0+0x1008", "payload": "0x00000006", "meaning": "SQ1 tail doorbell = 6"},
    {"id": "E3", "t": 910, "src": "Lab SSD", "dst": "RC", "layer": "TL", "type": "MRd",
     "addr": "SQ1+0x140", "tag": "0x21", "meaning": "SQE fetch, slot 5"},
    {"id": "E4", "t": 1650, "src": "RC", "dst": "Lab SSD", "layer": "TL", "type": "CplD",
     "tag": "0x21", "status": "SC", "meaning": "SQE bytes: Read, CID 0x0005"},
    {"id": "E5", "t": 48200, "src": "Lab SSD", "dst": "RC", "layer": "TL", "type": "MWr",
     "addr": "DATA+0x0", "meaning": "first data MWr (16 x 256 B follow)"},
    {"id": "E6", "t": 52100, "src": "Lab SSD", "dst": "RC", "layer": "TL", "type": "MWr",
     "addr": "CQ1+0x50", "meaning": "CQE, CID 0x0005, SC=0, phase 1"},
    {"id": "E7", "t": 30_000_100_000, "src": "RC", "dst": "Lab SSD", "layer": "TL", "type": "MWr",
     "addr": "SQ0+...", "meaning": "admin SQ tail doorbell (Abort after timeout)"},
]

# Expected phases for one interrupt-driven I/O, with a predicate that recognizes each.
EXPECTED = [
    ("T1 first event (doorbell)",       lambda e: e.get("addr") == "BAR0+0x1008"),
    ("T2 request (SQE fetch MRd)",      lambda e: e["type"] == "MRd" and e.get("addr", "").startswith("SQ1")),
    ("T3 transport (SQE CplD)",         lambda e: e["type"] == "CplD" and e.get("tag") == "0x21"),
    ("T4 device action (data MWr)",     lambda e: e.get("addr", "").startswith("DATA")),
    ("T5/T6 response+completion (CQE)", lambda e: e.get("addr", "").startswith("CQ1")),
    ("T7 notification (MSI-X MWr)",     lambda e: e.get("addr", "").startswith("MSIX")),
]


def reconstruct():
    print("T0 system state: MSI-X enabled, vector 1 -> CQ1 (from config/Identify, not shown)")
    cursor, missing_at, first_seen = 0, None, None
    for name, match in EXPECTED:
        hit = next((e for e in EVENTS[cursor:] if match(e)), None)
        if hit:
            cursor = EVENTS.index(hit) + 1
            first_seen = first_seen or hit
            print(f"{name:34s} OBSERVED  {hit['id']} t={hit['t']} ns  {hit['meaning']}")
        else:
            print(f"{name:34s} NOT SEEN in captured interval")
            missing_at = missing_at or name
    if not missing_at:
        print("timeline complete")
        return
    cov = COVERAGE
    print()
    print(f"deviation: {missing_at}")

Because masking a vector is not automatically a bug: a host may mask a vector while it migrates interrupt affinity, and then must unmask it. The abnormal part is that no unmask follows. Change COVERAGE["filters"] to "NVMe only" and run again: the program refuses to state the absence as evidence.

The first-abnormal-event rule

The first visible failure is not necessarily the root cause. The cause may be earlier, sometimes much earlier, and is often quiet. Always investigate backward:

Three disciplines make this work:

  • Do not start at the loudest event. The Abort, the controller reset, the AER message and the kernel error are all after the first deviation. They are consequences until proven otherwise.
  • Search backward by shared resource. Ask what resources the deviating step depends on (here: vector 1's table entry, the function mask, the MSI-X enable bit, the CPU's interrupt routing) and look for earlier events that touched them.
  • Keep the cause as a hypothesis until a test confirms it. Here: read the MSI-X table entry and PBA after the stall (Pending bit set would show the message was held), or reproduce with the masking code path disabled.

The negative-evidence rule

The absence of an event is evidence only if two conditions hold:

  1. the event was expected (you can say what should have appeared, where and roughly when), and
  2. the capture is known to be complete enough to have observed it.

Never write "the packet did not happen" unless coverage supports it. Prefer: "No corresponding packet is visible in the captured interval."

Exercise

The capture filter was set to "TLPs from Requester ID 0x0100 only". Which absences in the full-CQ example above can you still claim?

Model answer

Only absences of device-originated TLPs (SQE fetches, data writes, CQE writes, MSI-X writes) — those have Requester ID 0x0100. The CQ head doorbell writes come from the root complex with its own Requester ID and would be filtered out, so "no head doorbell since row 1" becomes unsupported. The investigation would need a new capture or host-side evidence of the head value.

The trace-coverage rule

Every trace in a lab, a report or a bug ticket states its coverage. Six items:

Coverage statement

Ways coverage silently fails

  • The probe is on the SSD's link, but the root cause is on another link (a switch upstream port).
  • The capture buffer wrapped; the earliest part of the window is gone.
  • The analyzer lost lock during a speed change and resumed later.
  • A "smart" filter keeps only TLPs that its NVMe overlay recognises.
  • Peer-to-peer traffic or traffic behind a switch never crosses the probed link.
  • Host memory writes (SQE writes) never cross any PCIe link.

Solution (for "PCIe completion splitting")

Intuition: a big order delivered in several boxes, each labelled with the order number and "N items still to come". Terminology: Read Completion Boundary (RCB), Byte Count, Lower Address, Completer ID, Tag. Structure: CplD header fields Byte Count (remaining bytes including this completion) and Lower Address (low bits of the first byte's address). Mechanism: a completer may split a read into several completions at naturally aligned RCB boundaries; they return in address order for one request. Example: a 512-byte MRd to a 64-byte-aligned address with RCB 64 can return as eight 64-byte CplDs with Byte Count 512, 448, …, 64. Lab: decode synthetic CplD headers with the TLP decoder. Failure: one completion missing → the requester's completion timeout for that request. Recovery: error reporting (AER completion timeout) and the device's own recovery; the NVMe command typically fails or times out. Five questions — proof: the sequence of Byte Count values with a gap shows exactly which piece is missing.

Quiz

  1. Which stage of the mastery loop produces "a case where the naive reading is wrong"?

    • Example
    • Failure
    • Counterexample
    • Assessment
    Answer and reasoning

    Counterexample. A failure is the mechanism breaking; a counterexample is your interpretation breaking.

  2. A PCIe CplD with status SC arrives for an SQE fetch. What does it tell you about the NVMe command's outcome?

    • The command succeeded
    • The command failed
    • The command was aborted
    • Nothing yet; the outcome is in the CQE
    Answer and reasoning

    The CplD only completes the PCIe read of the SQE. The NVMe outcome is in the CQE written later.

  3. When is the absence of an event evidence?

    • Whenever the analyzer shows nothing
    • When it was expected and the capture could have observed it
    • When the kernel log is also empty
    • Never
    Answer and reasoning

    Both conditions are required: an expectation and adequate coverage.

  4. Which event-model field links a PCIe CplD to a kernel timeout message?

    • EVENT_ID
    • TAG/CID
    • CORRELATION_ID
    • EVIDENCE
    Answer and reasoning

    CORRELATION_ID groups events belonging to one operation across sources. TAG/CID alone is ambiguous (PCIe tags and NVMe CIDs are different namespaces).

  5. Name the nine items of the trace-based mastery test.

    Model answer

    Start, trigger, request, response, completion, side effect, expected next event, actual next event, anomaly.

  6. Why is the first visible failure often not the root cause?

    Model answer

    Systems absorb deviations until something breaks loudly: timeouts fire seconds later, resets cascade, error handlers produce more messages. The deviation that started it is usually quieter and earlier; you find it by comparing expected and observed timelines and walking backward by shared resource.

  7. Distinguish a PCIe reset from an NVMe controller reset in one test.

    Model answer

    After a PCIe reset, configuration space is reset and the link retrains (visible as LTSSM activity and re-enumeration or config restore); after an NVMe controller reset (CC.EN 1→0→1), the link and configuration space stay, and only controller state and queues are reinitialised.

  8. Write the six items of a coverage statement.

    Model answer

    Capture start; capture end; whether timestamps are complete; whether packets may be filtered; whether analyzer decoding may omit events; whether both directions were captured.

  9. A three-level explanation's child version says "the SSD sends the request to the computer". What is wrong?

    Model answer

    It inverts the direction: the host creates the request, and the SSD fetches it. A child version may simplify, but must preserve who acts and in which direction, or it will contradict the senior version.

Interview questions

  1. (Beginner) What is the difference between an NVMe completion and an interrupt?

    Model answer

    The completion is a CQE the controller writes into the Completion Queue in host memory. The interrupt (MSI-X write) tells the host there may be new CQEs. They can be decoupled: polling uses no interrupts; one interrupt can cover many CQEs.

  2. (Beginner) How do you explain a concept to check you understand it?

    Model answer

    At three levels (child, junior, senior) that describe the same mechanism, plus answers to what, why, how, how it fails, and how I would prove what happened.

  3. (Intermediate) Walk me through reconstructing a timeline for a hung I/O.

    Model answer

    Write T0 state (link, controller ready, queues, vectors, IOMMU). Write the expected T1–T7 for the command. Normalise trace rows and log lines into events with a correlation ID. Align clocks. Fill observed slots; mark the first slot that differs; check coverage before treating any missing slot as absence; search backward by shared resource for the preceding cause; state confidence and the next test.

  4. (Intermediate) The analyzer shows no completion for a read. What do you say in the report?

    Model answer

    "No completion for Requester 0x0100 tag 0x1A is visible in the captured interval", with the interval, direction coverage, filters and buffer state. If coverage is complete, I add whether a completion timeout was reported (AER) to corroborate.

  5. (Advanced) How do you avoid confusing PCIe tags and NVMe CIDs in automated analysis?

    Model answer

    Keep them in separate namespaces: tags are scoped by Requester ID and outstanding window; CIDs are scoped by SQ identifier. Correlation from one to the other happens only through payload (the SQE bytes in a CplD) and addresses (CQ slot), producing a correlation ID like SQ1:CID0x0005.

  6. (Advanced) Give an example where the device is correct and the loudest error is a PCIe error.

    Model answer

    A host builds a PRP list with a zero entry; the device faithfully reads address 0; the platform returns UR and logs AER; the NVMe command fails with a data transfer error. The PCIe error is a consequence; the root cause is host software.

  7. (Senior) How do you train a team to stop starting at the loudest error?

    Model answer

    Make the expected timeline a required section of every bug report, require "first deviation" and "preceding cause" as separate fields, require a coverage statement, and run review drills on synthetic traces where the loud event is a consequence. Reward reports that say "insufficient evidence" with a capture plan.

  8. (Senior) Why model events with EXPECTED_NEXT and ACTUAL_NEXT instead of just a timeline?

    Model answer

    Because anomalies are differences between expectation and observation. Writing the expectation on each event makes the reasoning auditable, lets tools find mismatches deterministically, and exposes the cases where nobody knew what to expect, which is itself a finding.

Summary and mastery gate

Mastery is shown, not felt: twelve stages with artefacts, three levels that agree, five questions answered with evidence, nine trace items identified. On traces, normalise rows into events, rebuild expected and observed timelines, start from the first deviation, walk back to the preceding cause, and treat absence as evidence only when you can prove the capture could have seen it.

  • write any trace row or log line as a seventeen-field event

  • find the first abnormal event when it precedes the symptom
