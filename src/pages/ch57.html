An NVMe SSD keeps a running account of its own health: how hot it is, how much spare flash it has left, how much of its rated life it has used, how much data it has moved, how often it lost power without warning, and how many errors it has seen. This chapter teaches every field of the SMART / Health Information log page, the logs around it (error information, endurance group, telemetry, persistent events), how the host is alerted, and how to read the numbers without fooling yourself.

Why this chapter exists

Every fleet operator, every validation engineer and every support engineer reads SMART data. It decides when drives are replaced, whether a warranty claim is accepted, whether a field failure was caused by heat or by wear, and whether a platform shut drives down cleanly. Yet SMART fields are among the most misread numbers in storage: data units that are not bytes, a "percentage" that can exceed 100, a power-on-hours counter that may not count every hour, and an "unsafe shutdowns" counter that blames the drive for a platform's mistakes.

Part XVIII moves from the PCIe transport to NVMe features above it. Health reporting is the natural first stop: it uses only commands you already know (Get Log Page, Asynchronous Event Request, Get/Set Features), and it connects directly to the errors, resets and power topics of Parts XV and XVI.

Learning objectives

  • Explain available spare, its threshold, and percentage used, and why percentage used is an estimate.

  • Interpret power cycles, power-on hours, unsafe shutdowns, media and data integrity errors, and error log entry counts, including their common misreadings.
  • Use the Error Information log, Endurance Group Information log, Persistent Event log and Telemetry logs alongside SMART.

The story

Think of a bicycle with a little notebook tied to it. Every day the bicycle writes in its notebook: how hot its tyres got, how many kilometres it rode, how many times somebody fell off it, how worn its brake pads are, and how many spare inner tubes are left in the saddlebag. If the bicycle notices something really bad — the last spare tube is nearly used, or the brakes are hot — it rings its bell to tell you right away.

When you want to know if the bicycle is healthy, you read the notebook. But you have to know how it counts: it writes kilometres in "thousands of half-metres," and when it says "worn 80%," that is its own guess, not a measurement.

A car's dashboard and service record: an odometer (data written), an engine hours meter (power-on hours), a temperature gauge and warning lights (critical warnings), a log of engine starts (power cycles), a record of "ignition cut while engine running" events (unsafe shutdowns), and a manufacturer's estimate of remaining tyre life (percentage used). The dashboard is standardized; the mechanic's diagnostic dump (telemetry) is in the manufacturer's own format.

What it hides: an SSD's "odometer" counts only host data, not the extra writes the drive makes internally (garbage collection, wear levelling). Real flash wear depends on those internal writes. And there is no single "engine": a drive may have several temperature sensors and an internal composite figure that is a weighted judgement, not one reading.

Where it misleads: a car's warning light usually means "a part is failing." Several NVMe critical warnings mean "the drive has protected itself" — for example, going read-only to preserve data — which is a designed safe state, not a malfunction. And "unsafe shutdown" is often the platform's fault, not the drive's.

Beginner explanation

"SMART" originally meant Self-Monitoring, Analysis and Reporting Technology, a scheme from ATA hard drives with vendor-defined attributes. NVMe standardized the idea into one fixed-format, 512-byte SMART / Health Information log page, log identifier 02h. Every NVMe controller must support it, and every field has a defined meaning and unit.

The host reads it with the admin command Get Log Page (opcode 02h), asking for log identifier 02h. The controller copies the 512 bytes into host memory by DMA and posts a completion. Tools such as nvme smart-log and smartctl do exactly this and print the fields.

The fields fall into five groups:

Besides being polled, the controller can tell the host when something becomes critical, through an Asynchronous Event Request (AER in NVMe terminology — not to be confused with PCIe Advanced Error Reporting) that completes with a SMART/Health event type.

Two different "AER"s meet in this course. PCIe AER is Advanced Error Reporting (Chapter 46). NVMe's Asynchronous Event Request is an admin command (opcode 0Ch) that the host leaves outstanding so the controller can complete it when an event occurs. Always say which one you mean.

Engineering explanation

Retrieving the log

Get Log Page carries the log identifier in Command Dword 10 bits 07:00 (LID), a Log Specific Parameter, a Retain Asynchronous Event (RAE) bit, and the number of dwords to return (0's based, split into NUMDL in CDW10 bits 31:16 and NUMDU in CDW11). For the full 512-byte SMART log, NUMD = 128 dwords → NUMDL = 127 (7Fh), so CDW10 = 007F0002h when RAE = 0. The data pointer (PRP1, or an SGL) gives the destination buffer.

The Namespace Identifier (NSID) selects scope:

  • NSID = FFFFFFFFh (or 0 on many controllers; check the rules for your revision): controller-wide or NVM-subsystem-wide information.
  • A specific NSID: per-namespace information, only if the controller reports support in the Log Page Attributes (LPA) field of Identify Controller. Many fields are not meaningful per namespace; the specification says which.

Version-dependent: the scope rules for SMART (controller vs NVM subsystem vs namespace, and the meaning of NSID 0 vs FFFFFFFFh) have been refined across NVMe 1.x and 2.x. Check the "SMART / Health Information" section of the NVMe Base Specification 2.4 — Log Page Identifiers.

The Asynchronous Event Configuration feature (Feature Identifier 0Bh) has matching enable bits: the host chooses which critical warnings generate an asynchronous event. A bit can be set in the log even if its event is disabled.

Critical Warning bits reflect current conditions (temperature) or latched conditions (read-only, reliability degraded). A temperature warning clears when the drive cools; a read-only warning does not go away. Monitoring should store the history of the byte, not just alert on the present value.

Temperature

Composite Temperature is a single value in Kelvin that the controller derives from its sensors to represent the device's thermal state — the value the host should compare with the thresholds. Its derivation is Implementation-dependent. Up to eight raw Temperature Sensor values are reported separately (0 means not implemented). Subtract 273 (more precisely 273.15) for degrees Celsius.

Thresholds come from two places:

  • Identify Controller reports WCTEMP (Warning Composite Temperature Threshold) and CCTEMP (Critical Composite Temperature Threshold), in Kelvin. The SMART fields "Warning/Critical Composite Temperature Time" count minutes spent at or above these.
  • Temperature Threshold feature (Feature Identifier 04h) lets the host read and set over- and under-temperature thresholds for the composite temperature and for each sensor. Crossing them sets Critical Warning bit 1.

The Host Controlled Thermal Management feature lets the host set two thermal management temperatures (TMT1 for light throttling, TMT2 for heavy throttling); the SMART log counts transitions into each and the time spent in each. Throttling is the drive reducing performance to cool down — a common, silent cause of "the SSD got slow."

Available spare and percentage used

Flash blocks wear out. SSDs keep spare blocks to replace blocks that fail. Available Spare is the remaining spare capacity as a normalized percentage (100 = all spare left). The vendor sets the Available Spare Threshold; when spare falls below it, Critical Warning bit 0 sets. Spare usually stays at 100% for most of a drive's life and then falls quickly near the end — or after a cluster of block failures.

Percentage Used is the vendor's estimate of how much of the device's rated life has been consumed, based on actual usage and the manufacturer's prediction of life. 100 means the rated endurance is reached, not that the drive fails at once; values above 100 are allowed, saturating at 255. The specification asks for it to be updated about once per power-on hour. It is the field closest to "wear," but its formula is the vendor's.

Percentage Used, the composite temperature algorithm, the spare threshold, which events count as media errors, and how Controller Busy Time is measured are all vendor decisions inside the specification's definitions. Compare these fields across drives of the same model and firmware, not across vendors.

Data units, commands and busy time

Bytes ≈ DU × 1000 × 512
Bytes
approximate host bytes read (or written)
DU
Data Units Read (or Written) from the SMART log; one unit is 1000 × 512 = 512,000 bytes, and the controller rounds up

The unit is always 512 bytes, even for namespaces formatted with 4 KiB logical blocks: a 4 KiB write counts 8 units of 512 bytes toward the "thousands." Metadata is not counted. Data units count host data transferred by I/O commands (for example Read, Write, Compare for the NVM command set); the specification defines which commands contribute.

Host Read Commands and Host Write Commands count completed commands. Dividing data by commands gives the average transfer size — a quick check of the workload's shape. Controller Busy Time counts minutes during which the controller had I/O outstanding; on a lightly loaded system it is far smaller than power-on time.

Write amplification

Data Units Written counts only host writes. The flash also absorbs internal writes (garbage collection, wear levelling, metadata). The ratio is the write amplification factor (WAF):

WAF = MediaUnitsWritten ÷ DataUnitsWritten
WAF
write amplification factor (≥ 1 in normal operation)
MediaUnitsWritten
units written to the media, reported in the Endurance Group Information log (where supported)
DataUnitsWritten

The SMART log alone cannot give WAF; the Endurance Group Information log can (see below), and some vendors report it in vendor-specific logs.

History counters

  • Power Cycles: number of power cycles. Compare with the platform's boot count: a drive with far more cycles than the server has boots is being power-cycled by something else (hot-plug, backplane faults, power capping).
  • Power On Hours: hours powered on. Whether time in non-operational power states counts can differ (the specification has notes on this; check your revision). Not a wall clock.
  • Unsafe Shutdowns: incremented when power is lost without a shutdown notification having been completed (CC.SHN written and CSTS.SHST reporting completion; see Chapter 48). Often a platform or driver problem: the OS powered off before the drive finished, the BMC cut slot power, or a hot-unplug occurred.
  • Media and Data Integrity Errors: unrecovered data integrity errors the controller detected — uncorrectable ECC, CRC or end-to-end protection (Protection Information) check failures, LBA tag mismatch. Each normally caused a command to fail. Non-zero values deserve attention; a rising count is serious.
  • Number of Error Information Log Entries: lifetime count of entries created in the Error Information log (01h). Many are harmless (an invalid field in a vendor tool's command, for example). The count says "something was logged," the Error Information log says what.

Endurance groups

An endurance group is a collection of NVM sets (and their namespaces) whose wear is managed together. Drives with one endurance group report the same wear in SMART and in the Endurance Group Information log; drives with several (for example, separate groups for different media regions or tenants) report each separately, and the SMART log's Endurance Group Critical Warning Summary tells the host that at least one group needs attention. The Endurance Group Information log also reports Endurance Estimate (an estimate of total data units writable over the group's life) and Media Units Written, which gives write amplification.

Telemetry

Telemetry logs carry vendor-defined diagnostic data inside a standardized container: a header (with identifiers, reason information and generation numbers) and data areas of increasing size (Data Area 1, 2, 3 and, with extended telemetry, Data Area 4). The host requests a host-initiated capture by setting the Create Telemetry Host-Initiated Data flag in the Log Specific Parameter on Get Log Page; the controller may capture controller-initiated data on its own and signal it with an asynchronous event. The content is opaque to the host — it is for the vendor's tools — but collecting it at the right moment is the host's job.

Collect telemetry before resetting, power-cycling or updating firmware on a misbehaving drive. Resets can discard the volatile state the vendor needs. A controller-initiated telemetry generation number that changed since the last check means the drive captured something on its own.

Asynchronous events for health

The host keeps one or more Asynchronous Event Request commands (admin opcode 0Ch) outstanding. When an enabled health condition occurs, the controller completes one with an event type of SMART / Health Status and event information (for example reliability, temperature threshold, or spare below threshold) and identifies the associated log page (02h). The host must then read that log page (with RAE = 0) to clear the condition and re-arm the event; until it does, the controller does not report the same event type again. A new Asynchronous Event Request must also be submitted to replace the one that completed.

The central concept on the ladder

The bicycle's notebook records heat, kilometres, falls and worn brakes, and the bicycle rings its bell when something is really wrong.

The SSD keeps standardized counters and warnings in a 512-byte log; the host reads it, and the SSD can raise an event when a critical condition starts.

Controller firmware maintains counters in its RAM and persists them to flash periodically; temperature sensors feed a composite value; the flash translation layer tracks spare blocks and erase counts.

Get Log Page (02h) with LID 02h and NUMD 128 dwords; the controller DMAs 512 bytes; CQE; Asynchronous Event Request completions for health events.

On PCIe: doorbell MWr, SQE fetch MRd, two 256-byte MWr (MPS 256) carrying the log, CQE MWr, MSI-X MWr. The analyzer's NVMe decode shows LID and field values.

Compare snapshots over time; correlate unsafe shutdowns with platform power events, media errors with the error log, throttling counts with performance drops; collect telemetry before resetting.

The 16 questions, for the SMART / Health log

1. What is it?
A mandatory, standardized 512-byte log of device health and lifetime counters.
2. Why was it created?
To give hosts a vendor-independent way to monitor wear, temperature, errors and usage.
3. What problem does it solve?
Predicting failure and end of life, diagnosing environment and platform issues, fleet management.
4. What existed before?
ATA SMART with vendor-specific attribute IDs, thresholds and raw-value formats.
5. Why is it better?
Fixed fields, fixed units and standardized warnings; one decoder works for every NVMe device.
6. Who creates it?
The controller's firmware.
7. Who consumes it?
Host drivers (for events), monitoring tools, fleet management, validation and support engineers, NVMe-MI management controllers.
8. Where does it live?
Inside the controller, persisted to non-volatile storage; delivered into host memory on request.
9. Memory/registers?
No registers; a host buffer described by PRP/SGL; Identify Controller fields (LPA, WCTEMP, CCTEMP, ELPE); features 04h and 0Bh.
10. Before it?
Controller ready, admin queue running; for events, Asynchronous Event Requests outstanding and Asynchronous Event Configuration set.
11. After it?
Host decides: alert, throttle, migrate data, replace drive, or collect telemetry.
12. If wrong?
Misread units cause wrong endurance planning; unhandled warnings lead to data loss; misattributed unsafe shutdowns blame the wrong party.
13. Analyzer shows?
Get Log Page SQE (CDW10 = 007F0002h for the full log), 512 bytes of data MWr, CQE.
14. Linux shows?
nvme smart-log, smartctl -a, hwmon temperature for NVMe, kernel messages for AER-driven events.
15. Validation tests?
Field units and rounding, counter persistence across power cycles, thresholds and events, unsafe shutdown detection, per-namespace support, telemetry capture.
16. Senior suspects?
Platform power sequencing (unsafe shutdowns), cooling (throttling), workload shape (WAF), firmware version changes in counter behaviour.

Hardware view

  • Counters are persisted periodically. After an unsafe power loss, the last few minutes of counting may be lost (an implementation choice); expect small inconsistencies after power failures.
  • Spare and wear are tracked by the flash translation layer (FTL) per block; the SMART values are summaries.
  • Power-loss detection uses supply monitoring; drives with power-loss protection capacitors can finish in-flight work after power loss, but still count an unsafe shutdown if no shutdown notification was completed.
  • Thermal throttling is enforced by firmware reducing NAND parallelism, clock rates or link activity.
