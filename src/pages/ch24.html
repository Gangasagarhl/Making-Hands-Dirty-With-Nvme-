Every Non-Volatile Memory Express (NVMe) conversation over PCI Express (PCIe) begins with a handful of registers at the start of BAR0. This chapter teaches each of them in depth — address, width, fields, purpose, reset behaviour, what the host does with it, what the controller does with it, and what it looks like in a trace — then assembles them into the controller enable sequence, the doorbell stride formula, and a full decode of the course's synthetic Lab SSD register dump.

Why this chapter exists

Registers are the controller's only interface before any queue exists. Every bring-up problem — "the controller never becomes ready", "the first Identify times out", "the device works in one machine but not another" — is solved by reading registers correctly. They are also the only part of NVMe a host can read while the controller is broken, which makes them the first evidence in any serious investigation.

Registers are also where learners most often guess. A guessed bit position in a decoder silently mislabels every trace it touches. This chapter states the fields that are well established, marks the ones you must confirm, and shows you how to check a value against the specification rather than against memory.

Learning objectives

  • Recite the controller register map from 00h to 3Fh and the start of the doorbell array at 1000h, with widths.

  • Explain INTMS/INTMC and when they must not be used.
  • Explain NSSR and its consequences on PCIe.
  • Compute any doorbell address from CAP.DSTRD.
  • Perform and explain the controller enable sequence, and recognise it in a trace.
  • Decode a full register dump and spot inconsistent or illegal configurations.

The story

Picture the control panel on the side of a big factory machine. A small metal nameplate tells you what the machine can do: the biggest box it can handle, how long it takes to warm up, how far apart its buttons are. Another plate shows its model year. There is a switch panel where you set the speed and the box size and flip the big ON switch. There are status lights: green for ready, red for broken, yellow for "shutting down". There is a mailbox address where you tell it where the first job list is kept. And along the bottom there is a long row of bells, one per conveyor belt, that you press to say "new boxes are waiting".

The nameplate is CAP, the model year is VS, the switch panel is CC, the lights are CSTS, the mailbox address is AQA/ASQ/ACQ, and the row of bells is the doorbells.

For adults: the registers are like a network device's management interface before it has an IP address — you configure it through a console port with a few fixed settings, and only after it is "up" can you send it real traffic. CAP is the datasheet, CC is the configuration you commit, CSTS is the link LED, and the admin queue registers are the first static route.

  • The bells are not all the same distance apart on every machine. The spacing (doorbell stride) is chosen by the device and reported in CAP.DSTRD; the analogy's fixed row hides that.
  • Some switches only work when the machine is off. Several CC fields may only be changed while CC.EN = 0. A physical switch panel rarely enforces that.
  • Lights can lie by omission. CSTS.RDY = 1 says the controller can accept commands, not that every namespace or the media is healthy.
  • Reading a register is not free. On PCIe a register read stalls the CPU for a full round trip. Glancing at a light costs nothing; glancing at CSTS costs about a microsecond.

Beginner explanation

When the computer finds an NVMe SSD on PCIe, it gives the SSD a range of memory addresses called BAR0. Reading or writing those addresses does not touch RAM; it reaches small storage cells inside the SSD's controller called registers. The first few dozen bytes hold the controller's settings and status. Starting at offset 1000h (4096) are the doorbells.

Before the SSD can do anything, the driver:

  1. reads CAP to learn the controller's limits;
  2. makes sure the controller is off (CC.EN = 0, CSTS.RDY = 0);
  3. tells it where the admin command queue and admin completion queue are, and how big they are (AQA, ASQ, ACQ);
  4. writes its configuration and turns it on (CC, with EN = 1);
  5. waits for the ready light (CSTS.RDY = 1);
  6. then rings the admin doorbell to send its first command.

After that, almost all communication happens through queues in memory and doorbell writes. Registers come back into play only for resets, shutdown and error handling.

Engineering explanation

Properties, registers and the memory map

The Base Specification defines controller properties: named values with fields, sizes and behaviours. The NVMe over PCIe Transport Specification maps them into the memory space described by BAR0 — at which point we call them registers — and adds PCIe-only structures such as the doorbell array. On NVMe over Fabrics the same properties are read and written with Property Get and Property Set commands, and there are no doorbells. When this chapter says "register", it means the PCIe memory-mapped form.

Why reads and writes cost differently

A register write becomes a PCIe Memory Write, which is posted: the CPU hands it to the root complex and carries on. A register read becomes a Memory Read, which is non-posted: the CPU core waits for the Completion with Data to travel back, typically on the order of a microsecond or more depending on the platform. That is why NVMe's design keeps register reads out of the I/O path entirely and why the only register touched per I/O is a doorbell write.

Posted writes also explain a classic ordering subtlety: a write to CC followed immediately by a read of CSTS is safe because PCIe ordering rules do not let the read pass the earlier posted write in the same direction. But two writes from different CPU cores to two different doorbells have no defined order relative to each other. See PCIe Ordering.

0's based values

Several register fields are 0's based: the stored value is one less than the quantity. MQES, ASQS and ACQS are examples. A value of 0x1F means 32 entries. This saves a bit (a 12-bit field can express 4096) and is a common source of off-by-one bugs in hand-written decoders.

The teaching ladder for the controller registers

A machine's control panel: nameplate (CAP), model year (VS), switches (CC), lights (CSTS), the address of the first job list (AQA/ASQ/ACQ), and a row of bells (doorbells).

The registers are the controller properties as memory-mapped on PCIe: capability, version, configuration, status, admin queue attributes and base addresses, optional groups, and per-queue doorbells.

They sit at BAR0 + 0 in the controller's front end; CC.EN and CC.SHN trigger firmware actions; doorbells feed hardware fetch engines; CSTS is updated by firmware.

Base Specification 2.4 defines the properties and initialisation rules; PCIe Transport 1.4 defines the offsets and doorbell layout. Field widths, 0's based encodings and "only when EN = 0" rules are normative.

Register access is host-initiated MMIO: posted MWr for configuration and doorbells, non-posted MRd/CplD for CAP, VS and CSTS.

In a trace: an enable shows CAP/VS reads, AQA/ASQ/ACQ/CC writes and CSTS polling; operation shows only doorbell writes to BAR0 + 1000h and up.

Debug with registers first: CSTS tells you ready/fatal/shutdown or a dead link (all-ones); CAP tells you stride and timeouts; CC tells you what the host actually configured.

The sixteen questions, answered for the controller registers

1. What are they?
The memory-mapped form of the NVMe controller properties plus the doorbell array, in BAR0.
2. Why were they created?
The host needs a way to discover, configure, enable, reset and observe the controller before any queue exists.
3. What problem do they solve?
Bootstrapping: they let the host describe the admin queue so that everything else can happen through commands.
4. What existed before?
AHCI's register-heavy port interface, where command issue itself needed register accesses per command.
5. Why is the current design better?
A minimal register set; after enable, only doorbell writes in the fast path.
6. Who creates them?
The device designer (layout per spec); values come from silicon, firmware and the host.
7. Who consumes them?
The host driver (CAP, VS, CSTS) and the controller (CC, AQA, ASQ, ACQ, doorbells).
8. Where do they live?
In the controller, at BAR0 + 0 (registers) and BAR0 + 1000h (doorbells).
9. What memory/registers are involved?
CAP, VS, INTMS, INTMC, CC, CSTS, NSSR, AQA, ASQ, ACQ, optional groups, doorbells; plus host memory for the admin queues they point to.
10. What happens before?
PCIe enumeration assigns BAR0; the OS enables memory space and bus mastering.
11. What happens after?
Admin commands build I/O queues; registers go quiet except doorbells.
12. What happens if they are wrong?
Enable fails, the controller fetches from the wrong address, doorbells hit the wrong queue, or the host misses fatal status.
13. What does the analyzer show?
MRd/MWr TLPs to BAR0 offsets, which you decode with this chapter's map.
14. What does Linux show?
nvme show-regs; CSTS in kernel reset messages; BAR addresses in lspci.
15. What would a validation engineer test?
Reset values, read-only enforcement, EN/RDY timing against CAP.TO, illegal CC combinations, shutdown timing, NSSR behaviour, doorbell error handling, 32/64-bit access forms.
16. What would a senior engineer suspect when it fails?
Mismatched DSTRD or MPS assumptions, enabling before RDY = 0, missing Bus Master Enable, IOVA/IOMMU mapping of ASQ/ACQ, and the all-ones read that signals a dead link rather than a register value.

MQES applies to I/O queues. The admin queue size is set by AQA and is limited to 4096 entries regardless of MQES. And MQES is 0's based: MQES = 0x0FFF means 4096 entries.

Host and controller interaction

The controller sets CAP at power-on from silicon straps and firmware; it never changes while the controller is running. The host reads it once during probe (Linux reads it as a 64-bit value) and caches it. Rereading CAP in the I/O path would be a pointless non-posted read.

Trace consequences

CAP shows up as one 64-bit MRd (Len = 2) or two 32-bit MRd TLPs to BAR0 + 00h and + 04h right after the driver maps BAR0, before any CC write. Its value determines the addresses of every doorbell you will see later, so capture it (or reconstruct DSTRD from the doorbell pattern) before decoding I/O.

VS — Version

Address 08h · Width 32 bits · Access read-only · Reset constant.

DW31…2423…1615…87…0
08hMJR (major)MNR (minor)TER (tertiary)

VS reports the Base Specification revision the controller claims to comply with. Examples of encoding: 1.4.0 → 0x0001_0400; 2.0.0 → 0x0002_0000; following the same encoding, 2.4.0 would be 0x0002_0400 Derived. Identify Controller's VER field uses the same encoding and should match.

Host interaction: read once; used to decide which optional fields and behaviours may be relied on (together with capability bits). Controller interaction: none at run time. Trace consequence: one 32-bit MRd at probe. A VS older than 1.2 (where some register fields did not exist) changes how you interpret reserved bits elsewhere.

VS is a claim, not a proof. Validation engineers test whether the device behaves according to the revision it claims; field engineers must not assume features from it.

INTMS and INTMC — Interrupt Mask Set and Clear

Addresses 0Ch (INTMS) and 10h (INTMC) · Width 32 bits each · Reset 0 (no vectors masked).

DW31…2423…1615…87…0
0ChIVMS — Interrupt Vector Mask Set (one bit per vector)
10hIVMC — Interrupt Vector Mask Clear (one bit per vector)

Purpose. With pin-based (INTx) or MSI interrupts there is no per-vector mask in a table the host can write cheaply, so NVMe provides one: writing 1 to a bit of INTMS masks that vector; writing 1 to the same bit of INTMC unmasks it. Writing 0 has no effect. Reading either register returns the current mask.

Rule. When MSI-X is in use, the host does not use INTMS/INTMC; MSI-X has its own per-vector mask bits in the MSI-X table, and accessing INTMS/INTMC while MSI-X is configured results in undefined behaviour. Modern Linux uses MSI-X and never touches these registers in normal operation.

Controller interaction: a masked vector does not generate interrupt messages; the controller remembers that an interrupt is pending and sends it when unmasked (if completions are still outstanding). Trace consequence: on MSI-X systems, any access to 0Ch/10h is itself suspicious; on INTx/MSI systems, you may see INTMS writes at the start of an interrupt handler and INTMC writes at the end, bracketing CQ processing.

NSSR — NVM Subsystem Reset

Address 20h · Width 32 bits · Optional (present when CAP.NSSRS = 1).

DW31…2423…1615…87…0
20hNSSRC — NVM Subsystem Reset Control (write 4E56_4D65h = "NVMe" to reset)

Purpose. Writing the value 4E56_4D65h (ASCII "NVMe") initiates an NVM Subsystem Reset, which resets the entire subsystem — every controller, on every port — not just this controller. The magic value prevents accidental resets from stray writes. Other values have no effect.

Consequences. All controllers undergo a Controller Level Reset; afterwards CSTS.NSSRO = 1 on the controllers so hosts can tell what happened. On PCIe, a subsystem reset also resets the subsystem's PCIe ports, so the link goes down and must retrain; the host sees something close to a surprise removal and re-insertion Derived (confirm the PCIe-specific behaviour in the PCIe Transport Specification's NVM Subsystem Reset text). In a dual-host system, one host's NSSR write disrupts the other host.

Read behaviour: Uncertain confirm what reads return. Trace consequence: one MWr32 to BAR0 + 20h with data 0x4E56_4D65, followed by the link leaving L0 (recovery or detect in the Link Training and Status State Machine), then a fresh enumeration and enable. Linux exposes it as nvme subsystem-reset — never run it on a production system.

AQA, ASQ and ACQ — the admin queue registers

AQA — Admin Queue Attributes

Address 24h · Width 32 bits · Reset 0.

DW31…2423…1615…87…0
24hrsvdACQS (0's based)rsvdASQS (0's based)

ASQS (bits 11:0) is the admin SQ size and ACQS (bits 27:16) the admin CQ size, both 0's based. Valid sizes are 2 to 4096 entries (values 1 to 4095). The Lab SSD uses 32 entries each: AQA = 0x001F_001F.

ASQ — Admin Submission Queue Base Address

Address 28h · Width 64 bits. Bits 63:12 hold the base address (ASQB); bits 11:0 are reserved, so the admin SQ is at least 4 KiB aligned (and must respect the memory page alignment the specification requires for the configured CC.MPS — confirm). The admin SQ is always physically contiguous. Lab SSD: 0x0000_0001_0000_0000.

ACQ — Admin Completion Queue Base Address

Address 30h · Width 64 bits. Same layout (ACQB in bits 63:12). Lab SSD: 0x0000_0001_0000_1000.

Host interaction: written only while CC.EN = 0, before enabling. Controller interaction: latched when CC.EN goes to 1; the controller then fetches admin commands from ASQ and posts admin completions to ACQ. Reset behaviour: not cleared by a CC.EN-initiated Controller Reset in the revisions the course checked, which is why some drivers skip rewriting them — a fragile shortcut confirm per reset type.

Trace consequence: these values are the key to decoding admin traffic. Every device MRd that hits ASQB + n × 64 is an admin SQE fetch; every device MWr to ACQB + n × 16 is an admin completion. Note that the addresses are those the device uses — with an IOMMU, they are I/O virtual addresses (IOVAs), not physical addresses.

Optional register groups: CMB, boot partitions, PMR, ready timeouts

Controller Memory Buffer — CMBLOC (38h) and CMBSZ (3Ch)

A Controller Memory Buffer is a region of device memory, exposed through a BAR, that the host may use for queues and data instead of host memory, reducing round trips for some workloads.

  • CMBLOC: BIR (bits 2:0) names the BAR holding the CMB; OFST (bits 31:12) is the offset within that BAR, in units of CMBSZ.SZU. Bits 3–8 carry several capability/restriction flags added in 1.4 confirm.
  • CMBSZ: SQS (bit 0) submission queues supported in CMB; CQS (bit 1) completion queues; LISTS (bit 2) PRP/SGL lists; RDS (bit 3) read data; WDS (bit 4) write data; SZU (bits 11:8) size units (4 KiB × 16SZU); SZ (bits 31:12) size in SZU units.
  • CMBMSC / CMBSTS (1.4+): the host must enable the CMB's memory space and register its controller-side address before use confirm offsets and fields.

Trace consequence: queue traffic that lives in a CMB becomes host writes to the device (SQEs written by the CPU into device memory) instead of device reads from host memory — the rhythm of the trace changes completely.

Boot partitions — BPINFO (40h), BPRSEL (44h), BPMBL (48h)

Boot partitions are small areas readable without enabling the controller, so platform firmware can load a boot image early. BPINFO reports size and status; BPRSEL selects which partition and range to read; BPMBL gives the host memory buffer the controller writes into. Present when CAP.BPS = 1. Uncertain confirm the field positions within these registers before decoding.

Persistent Memory Region — PMR registers (from E00h)

A PMR is persistent, byte-addressable device memory exposed through a BAR (1.4+). PMRCAP describes it; PMRCTL enables it; PMRSTS reports status; the remaining registers describe elasticity, throughput and the memory space control. Present when CAP.PMRS = 1. Offsets beyond PMRCAP should be confirmed.

NVM Subsystem Shutdown (NSSD) and Controller Ready Timeouts (CRTO)

NVMe 2.0 added a property to request shutdown of the whole subsystem (NSSD, when CAP.NSSS = 1) and a property reporting separate ready timeouts for the two ready modes (CRTO: a timeout for ready-with-media and one for ready-independent-of-media, in 500 ms units). When CRTO is present, hosts should use it rather than CAP.TO for the selected mode. Version-dependent Confirm offsets 64h/68h and field layout

Doorbells and the doorbell stride

Each queue has one doorbell: submission queues a tail doorbell (SQyTDBL), completion queues a head doorbell (CQyHDBL). Each is a 32-bit register whose low 16 bits hold the new index (SQT or CQH); bits 31:16 are reserved. The host writes; reading a doorbell is not meaningful.

SQyTDBL = 1000h + (2y) × (4 << CAP.DSTRD)

Why a stride at all? A larger stride lets each doorbell sit in its own cache line or page, which helps devices that implement doorbells in separate hardware blocks and helps virtualization (mapping individual doorbells into guests). Most physical SSDs report DSTRD = 0.

BAR size check. BAR0 must be large enough for every doorbell of every queue the controller supports: the Lab SSD's 33 queue pairs with stride 4 end at 1104h + 4, comfortably inside 16 KiB.

Invalid writes. A write to a doorbell of a queue that does not exist, or of a value that is not a valid index (for example a tail beyond the queue size, or a CQ head that releases entries the controller has not posted), is an error the controller may report through an Asynchronous Event of type Error Status ("Write to Invalid Doorbell Register" or "Invalid Doorbell Write Value") confirm event information values. Some controllers instead stop processing or set CFS.

Doorbell mechanics, batching and the shadow-doorbell (Doorbell Buffer Config) optimisation for virtual machines are treated in Doorbells.
