The practical core of senior work, drilled until it is reflex: exact capacity and unit arithmetic, completion status decoding, reading Identify and log pages, discovering capabilities before using them, interoperability, debugging by layer, a cross-layer lab — and then the final rubric, the seven-stage journey from kid to principal, the five teach-backs that prove it, and the rule the whole course is built on.

Why this part exists

Most real mistakes in NVM Express (NVMe) work are not deep protocol misunderstandings. They are unit errors (a "1 TB" drive that shows 931 "GB"), off-by-one errors (zero-based counts), unverified assumptions (an optional log that this drive does not support), and decoding slips (a status code read in the wrong status code type). This part drills those basics with labs that use the course's lab system, then closes the Mastery Engine with the rubric and the teach-backs that show whether the whole journey worked.

Learning objectives

  • Compute namespace capacity exactly in bytes, KB/MB/GB and KiB/MiB/GiB, from Identify Namespace fields.
  • Interpret every counter by its defined unit, never by its display.
  • Decode a Completion Queue Entry (CQE) status and decide whether to retry, abort or recover.
  • Approach Identify data by structure (controller, namespace, command-set-specific) with source, revision, width, interpretation and use for every field.
  • Request and interpret log pages, without assuming optional logs exist.
  • Discover capabilities before using optional features.
  • Localise a symptom by layer and own a cross-layer investigation.
  • Assess yourself against the final rubric and complete the five teach-backs.

Prerequisites

Namespaces, SMART / Health, NVMe Errors, Admin Commands, Mathematics for Storage and Links, and the reading procedures of Reading Commands, Registers and State Machines.

The story

A shopkeeper says the bag holds "a thousand sweets". Another shop says "a thousand and twenty-four". A third counts in "packs of a thousand". If you mix them up, you think you were cheated — or you promise your friends sweets you do not have. Engineers have to know exactly which kind of "thousand" every number uses.

A pharmacist checks every prescription for units: milligrams versus micrograms, per dose versus per day. The chemistry is not hard; the discipline is. A thousand-fold error from a unit is as fatal as any exotic mistake.

Pharmacy units are standardised by law and printed on every label. Storage counters are defined in specification text that the display may not repeat: a tool can print "Data Units Read: 9,765,625" without saying that one unit is 512,000 bytes. You must bring the definition yourself.

Capacity and LBA lab

Safe lab Arithmetic and a read-only extension.

Objective

Compute namespace capacity from Identify Namespace fields with exact unit handling, and explain why the same namespace is "1 TB" and "931 GiB".

Skills

  • Decimal versus binary prefixes.
  • LBA formats and zero-based counts.

Hardware and software required

Python 3. Optional: a Linux machine with an NVMe drive (read-only commands).

Input

Lab system: namespace 1 has NSZE = 0x0000_0000_7470_6DB0 with 512-byte LBAs (LBADS = 9); namespace 2 uses 4 KiB LBAs (LBADS = 12) and, for this lab, NSZE = 0x0E8E_0DB6.

"""units.py - capacity and unit conversions for a namespace (Executable, standard library)."""

DEC = [("B", 1), ("KB", 10**3), ("MB", 10**6), ("GB", 10**9), ("TB", 10**12)]
BIN = [("B", 1), ("KiB", 2**10), ("MiB", 2**20), ("GiB", 2**30), ("TiB", 2**40)]

def human(n, table):
    name, size = table[0]
    for nm, sz in table:
        if n >= sz:
            name, size = nm, sz
    return f"{n / size:,.3f} {name}"

def namespace(nsze, lbads, ms=0, label=""):
    lba_bytes = 1 << lbads                      # LBA data size = 2^LBADS bytes
    total = nsze * lba_bytes                    # user data only; metadata is extra
    print(f"{label}: NSZE={nsze:#x} ({nsze:,} LBAs) x {lba_bytes} B")
    print(f"   = {total:,} bytes = {human(total, DEC)} = {human(total, BIN)}")
    if ms:
        print(f"   + metadata {ms} B per LBA = {nsze * ms:,} bytes not counted in capacity")
    print(f"   last valid LBA = {nsze - 1:#x}")

namespace(0x7470_6DB0, 9, label="NS1 (512 B LBAs)")
namespace(0x0E8E_0DB6, 12, label="NS2 (4 KiB LBAs)")
# NLB is zero-based: a Read with NLB=7 on NS1 moves (7+1) * 512 bytes
print("Read NLB=7 on NS1 moves", (7 + 1) * 512, "bytes; on NS2 moves", (7 + 1) * 4096, "bytes")

Expected output

Both namespaces hold 1,000,204,886,016 bytes = 1.000 TB = 931.513 GiB. NS1's last valid LBA is 0x7470_6DAF.

Step 1

By hand, convert 1,953,525,168 × 512 bytes to GB and to GiB.

Step 2

Run the script and check your arithmetic.

Step 3

Compute the byte count of a Read with NLB = 255 on each namespace.

Observation

The same bytes are "1 TB" and "931 GiB" — a 7 % difference that has generated countless "my drive is smaller than advertised" tickets.

Questions

  1. What is the highest SLBA a one-block Read on NS1 may use?
  2. A Read on NS1 with SLBA = 0x7470_6DA8 and NLB = 7: valid?
  3. A Read on NS1 with SLBA = 0x7470_6DA8 and NLB = 8: valid?
  4. If NS1 were reformatted to LBA format 1 (4 KiB), what would NSZE become, assuming the same byte capacity?
  5. Why might a namespace with protection information report the same NSZE but transfer more bytes per LBA?

Challenge

lsblk shows the namespace as "931.5G" and the vendor's label says "1 TB". A colleague files a bug that 68 GB are missing. Write the reply in three sentences.

Hint

NLB is zero-based: NLB = 7 means eight blocks. The last block touched is SLBA + NLB.

Solution

Step 1. 1,953,525,168 × 512 = 1,000,204,886,016 bytes. ÷ 109 = 1,000.2 GB. ÷ 230 = 931.51 GiB.

Step 3. NLB = 255 → 256 blocks: 131,072 bytes (128 KiB) on NS1; 1,048,576 bytes (1 MiB) on NS2. Check that this is within MDTS (see Identify).

Q1. 0x7470_6DAF (NSZE − 1). Q2. Last block = 0x7470_6DA8 + 7 = 0x7470_6DAF: valid. Q3. Last block = 0x7470_6DB0 = NSZE: out of range (LBA Out of Range). Q4. 1,000,204,886,016 ÷ 4,096 = 244,190,646 (0x0E8E_0DB6). Q5. Protection information lives in metadata: with extended LBAs, each transferred block is LBA data plus metadata (e.g. 512 + 8 bytes), while NSZE counts blocks and capacity counts only user data.

Challenge. "No capacity is missing: the drive holds 1,000,204,886,016 bytes. The label uses decimal terabytes (1012 bytes) and lsblk uses binary gibibytes (230 bytes), so the same bytes show as 1.0 TB and 931.5 GiB. Closing as not a bug; see the unit table in our runbook."

What a senior engineer notices

  • Every capacity number in a report gets a unit with its prefix family. "GB" in a kernel tool's output is often GiB in disguise — check the tool's documentation.
  • Off-by-one at the end of a namespace is the classic boundary test: SLBA + NLB = NSZE − 1 must pass; = NSZE must fail.

Failure variants

  • A tool computes capacity as NCAP × LBA size on a thin-provisioned namespace and reports the wrong figure: NCAP is not NSZE.
  • A driver uses LBA format 0's size after the namespace was reformatted to format 1: every offset is wrong by a factor of 8.

Extension

Safe lab On a Linux machine, read (only) nvme id-ns /dev/nvme0n1 -H and cat /sys/block/nvme0n1/size (in 512-byte sectors, regardless of LBA size). Reconcile them.

Data unit lab

Safe lab

Objective

Interpret storage statistics by their defined units, and build a personal table of NVMe fields whose units are not what they appear.

Skills

  • Reading a field's unit from its definition.
  • Distrusting displayed units.

Hardware and software required

Python 3.

Background

The SMART / Health Information log reports Data Units Read and Data Units Written in units of one thousand 512-byte units, rounded up: a value of 1 means 512,000 bytes. It reports temperature in kelvin. Tools convert these for you — sometimes into decimal units, sometimes binary, sometimes not at all. The rule: do not assume a displayed counter's unit without checking its specification definition.

Input

"""smart.py - decode selected fields of the SMART / Health Information log (Executable).
Byte offsets are the course's reading of the log layout; confirm them in your revision."""
import struct

log = bytearray(512)                                  # synthetic log page for the Lab SSD
log[0] = 0x00                                         # Critical Warning
struct.pack_into("<H", log, 1, 318)                   # Composite Temperature, kelvin
log[3], log[4], log[5] = 100, 10, 3                   # Available Spare, threshold, Percentage Used
def put128(off, v): log[off:off + 16] = v.to_bytes(16, "little")
put128(32, 9_765_625)       # Data Units Read
put128(48, 19_531_250)      # Data Units Written
put128(64, 812_004_117)     # Host Read Commands
put128(80, 1_502_331_900)   # Host Write Commands
put128(112, 214)            # Power Cycles
put128(128, 8_760)          # Power On Hours
put128(144, 3)              # Unsafe Shutdowns
put128(160, 0)              # Media and Data Integrity Errors

def get128(off): return int.from_bytes(log[off:off + 16], "little")

DATA_UNIT = 1000 * 512      # one reported unit = 1,000 units of 512 bytes (value is rounded up)
temp_k = struct.unpack_from("<H", log, 1)[0]
print(f"Critical Warning = {log[0]:#04x}; temperature = {temp_k} K = {temp_k - 273} degC (approx.)")
print(f"Available Spare = {log[3]} % (threshold {log[4]} %); Percentage Used = {log[5]} %")
for name, off in (("Data Units Read", 32), ("Data Units Written", 48)):
    v = get128(off)
    print(f"{name} = {v:,} units -> about {v * DATA_UNIT / 1e12:.2f} TB "
          f"({v * DATA_UNIT / 2**40:.2f} TiB), resolution 512,000 bytes")
for name, off in (("Host Read Commands", 64), ("Host Write Commands", 80), ("Power Cycles", 112),
                  ("Power On Hours", 128), ("Unsafe Shutdowns", 144), ("Media Errors", 160)):
    print(f"{name} = {get128(off):,}")

Expected output

Data Units Written 19,531,250 → about 10.00 TB (9.09 TiB); temperature 318 K ≈ 45 °C.

Steps

  1. Run the script and verify one conversion by hand.
  2. Compute the drive's average write rate over its power-on time.
  3. Compute host writes per Host Write Command, and say what it tells you about the workload.

Questions

  1. Why can Data Units Written not tell you the exact number of bytes written?
  2. Does Data Units Written include metadata?
  3. Data Units Written rises by 1 after writing a single 4 KiB block to a fresh drive. Is that consistent?

Challenge

Compute an approximate write amplification if a vendor log reports 25 TB of NAND writes. What can and cannot be concluded?

Solution

Step 2. 10.00 TB over 8,760 hours ≈ 1.14 GB/hour ≈ 317 kB/s average. Step 3. 10.00 × 1012 bytes ÷ 1,502,331,900 commands ≈ 6.66 KB per write command: a small-block-dominated workload. Q1. The resolution is 512,000 bytes and the value is rounded up. Q2. No — the definition excludes metadata (confirm wording). Q3. Yes: rounding up means any partial thousand counts as one unit. Challenge. 25 / 10.00 ≈ 2.5. You can conclude the device wrote about 2.5× the host data internally over its life. You cannot conclude why (garbage collection, workload pattern, over-provisioning, firmware) or whether it will continue; and the vendor log's unit and scope must be checked just as carefully.

What a senior engineer notices

  • The commonest wrong number in a report is a counter read in the wrong unit. Write the unit next to every value you copy.

Failure variants

  • A monitoring system graphs Data Units Written as bytes: the graph shows 19 MB written per year.

Extension

Compare nvme smart-log /dev/nvme0 output with the raw log (nvme get-log /dev/nvme0 --log-id=2 --log-len=512 -b | xxd, read-only) and check every conversion the tool performs.

Command status lab

Safe lab

Objective

Decode synthetic CQEs — status, phase, command identifier and status fields — and reason about retry, abort and recovery for each.

Skills

  • CQE Dword 2 and Dword 3 layout.
  • Status Code Type versus Status Code.
  • DNR, More and Command Retry Delay.

Hardware and software required

Python 3.

Background

CQE Dwords 2 and 3 (course's reading of the 1.4-and-later layout; confirm in Base 2.4 — Completion Queue Entry)
DW31…2423…1615…87…0
DW2SQ IdentifierSQ Head Pointer
DW3DNRMCRDSCTSCPCommand Identifier

A Status Code (SC) is meaningless without its Status Code Type (SCT). SC 81h with SCT 0h is a Generic status (in the NVM command set's range); SC 81h with SCT 2h is a Media and Data Integrity error. Always decode the pair. Exact bit meanings and code values must be verified against the applicable specification revision before you publish a decoder.

Input

"""cqe_status.py - decode CQE Dword 2 and Dword 3 (Executable, standard library).
Field positions and the few status names below follow the course's reading of the NVMe Base
Specification (1.4 and later layout). Confirm them against the revision you work with."""

SCT = {0: "Generic Command Status", 1: "Command Specific Status",
       2: "Media and Data Integrity Errors", 3: "Path Related Status", 7: "Vendor Specific"}
GENERIC = {0x00: "Successful Completion", 0x01: "Invalid Command Opcode",
           0x02: "Invalid Field in Command", 0x04: "Data Transfer Error",
           0x06: "Internal Error", 0x07: "Command Abort Requested",
           0x08: "Command Aborted due to SQ Deletion", 0x0B: "Invalid Namespace or Format",
           0x80: "LBA Out of Range", 0x82: "Namespace Not Ready"}
MEDIA = {0x81: "Unrecovered Read Error"}

def decode(dw2, dw3):
    sqhd, sqid = dw2 & 0xFFFF, dw2 >> 16
    cid, phase = dw3 & 0xFFFF, (dw3 >> 16) & 1
    sc, sct = (dw3 >> 17) & 0xFF, (dw3 >> 25) & 0x7
    crd, more, dnr = (dw3 >> 28) & 0x3, (dw3 >> 30) & 1, (dw3 >> 31) & 1
    names = GENERIC if sct == 0 else MEDIA if sct == 2 else {}
    name = names.get(sc, "(look up in the specification)")
    return (f"SQID={sqid} SQHD={sqhd:#x} CID={cid:#06x} P={phase} "
            f"SCT={sct:x}h ({SCT.get(sct, 'reserved')}) SC={sc:02X}h {name} CRD={crd} M={more} DNR={dnr}")

EXAMPLES = [  # (DW2, DW3) - synthetic CQEs from the lab system's I/O queue 1
    (0x0001_0006, 0x0001_000C),
    (0x0001_0007, 0x0009_0031),
    (0x0001_0008, 0x8005_0032),
    (0x0001_0009, 0x8101_0033),
    (0x0001_000A, 0x0503_0034),
    (0x0001_000B, 0x0010_0035),
    (0x0001_000C, 0x500D_0036),
]
for dw2, dw3 in EXAMPLES:
    print(f"DW2={dw2:#010x} DW3={dw3:#010x} -> {decode(dw2, dw3)}")

Expected output

Seven decoded CQEs, one per line, from CID 0x000C to 0x0036.

Step 1

Decode each by hand first, then run the script.

Step 2

For each, decide: retry, do not retry, recover (reset or re-initialise something), or investigate.

Questions

  1. CID 0x0031: Data Transfer Error, DNR = 0. Retry?
  2. CID 0x0032: Invalid Field in Command, DNR = 1. Retry?
  3. CID 0x0033: LBA Out of Range. Whose bug?
  4. CID 0x0034: Unrecovered Read Error, DNR = 0. Retry, and what else?
  5. CID 0x0035 has P = 0. Is it a new entry?
  6. CID 0x0036: Internal Error with CRD = 1 and M = 1. What do CRD and M ask of the host?
  7. What does SQ Head Pointer = 0xB in CID 0x0035's entry tell the host?

Challenge

Write a retry policy table (status class × DNR × CRD → action) for a driver, and name one case where retrying is harmful even though DNR = 0.

Hint

Phase alternates each pass through the CQ. Whether P = 0 is "new" depends on which pass the host expects.

Solution

Q1. DNR = 0 permits a retry, and a Data Transfer Error can be transient — but first find out why: check AER and IOMMU logs for that command's buffers (see Case B). Blind retry hides a host-side mapping bug. Q2. No: DNR = 1 means the same command will fail again; fix the command (which field? read the command's field rules and the Error Information log entry, which can point to the offending parameter). Q3. The submitter's: the command addressed blocks beyond NSZE; check the host's capacity calculation (often a unit or off-by-one error from the capacity lab). Q4. A retry may succeed (some devices recover data on retry) but the data at that LBA is at risk: report it upward, read the Error Information log for the LBA, check SMART media error counters, and recover the data from redundancy. Q5. Only if the host is on a pass where it expects P = 0 (every second pass through the CQ). If the host expects P = 1, this is a stale entry and must not be consumed — a classic after-reset bug when CQ memory was not cleared. Q6. CRD selects one of the Command Retry Delay times reported in Identify Controller (only meaningful if the host enabled the behaviour); M = 1 means more status information is available in the Error Information log page. Q7. The controller has consumed SQ entries up to (but not including) slot 0xB; the host may reuse slots before it.

A starting retry policy (Derived; adapt to command semantics)
StatusDNRAction
Success—Complete
Any1Fail to caller; log; do not retry
Generic transport-type (Data Transfer Error, Internal Error)0Retry after CRD delay (if enabled), bounded count; log
Media (Unrecovered Read Error)0Limited retry; then fail and report the LBA
Path-related0Retry on another path (multipath), per ANA state
Aborted (SQ deletion, abort requested)0Requeue if the host initiated deletion as part of recovery

Harmful retry with DNR = 0: non-idempotent commands, e.g. retrying a Zone Append whose first attempt actually wrote data but whose completion reported an error after the write — a second append writes the data twice at a different LBA.

What a senior engineer notices

  • Retry policy is where drivers hide bugs. Count retries per status in production; a non-zero Data Transfer Error retry rate is a signal, not noise.

Failure variants

  • A decoder written for 1.3 masks bits 29:28 as reserved and reports CRD statuses as "unknown".
  • A tool prints "SC=81h" without SCT; two teams argue about whether it is a media error.

Extension

Extend the decoder with the Error Information log entry structure, joined by SQID and CID.

Identify lab

Safe lab

Objective

Approach Identify data by structure, and for every field you use record source, revision, width, interpretation and practical use — never inventing a field meaning.

Skills

  • Choosing the right Identify structure (CNS).
  • Little-endian multi-byte fields.
  • Field records with provenance.

Hardware and software required

Python 3; optionally a Linux machine for read-only extension.

Background

Identify (admin opcode 06h) returns a 4,096-byte data structure selected by the Controller or Namespace Structure (CNS) value. Three families matter:

Identify structure families
FamilyExamples (by name)CNSDefined in
ControllerIdentify Controller data structure01hBase specification
Namespace (command-set-common or NVM)Identify Namespace data structure; active namespace ID list (CNS 02h); namespace identification descriptor list00h for Identify NamespaceBase / NVM Command Set
Command-set-dependentI/O Command Set specific Identify Controller and Identify Namespace (e.g. ZNS's zone sizes, NVM's extended formats)Other values — read the CNS tableThe command set's specification

Since NVMe 2.0, which fields live in which structure has shifted as command sets were separated. A field you remember from a 1.4 Identify Namespace may now be described in the NVM Command Set specification, or in a command-set-specific structure. Record the document and revision for every field.

Input

"""idns.py - decode the first fields of an Identify Namespace data structure (Executable).
Offsets: NSZE 7:0, NCAP 15:8, NUSE 23:16, NLBAF 25, FLBAS 26, LBA Format 0 at 131:128.
Confirm every offset in your revision's Identify Namespace table before reusing this."""
import struct

# Synthetic 4096-byte buffer for the lab system's namespace 1 (only the fields used are filled).
buf = bytearray(4096)
struct.pack_into("<QQQ", buf, 0, 0x7470_6DB0, 0x7470_6DB0, 0x2E8C_1A00)   # NSZE NCAP NUSE
buf[25] = 1                       # NLBAF: zero-based -> 2 formats
buf[26] = 0x00                    # FLBAS: format 0 in use, metadata not extended
struct.pack_into("<I", buf, 128, (2 << 24) | (9 << 16) | 0)    # LBAF0: RP=2, LBADS=9, MS=0
struct.pack_into("<I", buf, 132, (0 << 24) | (12 << 16) | 0)   # LBAF1: RP=0, LBADS=12, MS=0

def le(b, lo, hi):                # inclusive byte range, little-endian
    return int.from_bytes(b[lo:hi + 1], "little")

nsze, ncap, nuse = le(buf, 0, 7), le(buf, 8, 15), le(buf, 16, 23)
nlbaf, flbas = buf[25], buf[26]
fmt = flbas & 0xF                 # low bits select the format (more bits exist for >16 formats)
print(f"NSZE={nsze:,} NCAP={ncap:,} NUSE={nuse:,}  ({nuse / nsze:.1%} of LBAs allocated)")
print(f"NLBAF={nlbaf} -> {nlbaf + 1} LBA formats; FLBAS selects format {fmt}; "
      f"extended metadata={'yes' if flbas & 0x10 else 'no'}")
for i in range(nlbaf + 1):
    d = le(buf, 128 + 4 * i, 131 + 4 * i)
    ms, lbads, rp = d & 0xFFFF, (d >> 16) & 0xFF, (d >> 24) & 0x3
    mark = "  <- in use" if i == fmt else ""
    print(f"LBAF{i}: data size {1 << lbads} B, metadata {ms} B, relative performance {rp}{mark}")
lbads = (le(buf, 128 + 4 * fmt, 131 + 4 * fmt) >> 16) & 0xFF
print(f"Capacity = NSZE x 2^LBADS = {nsze * (1 << lbads):,} bytes")

Step 1 — Field records

For each field the script decodes, complete a record like this:

Field record template, filled for MDTS
ItemMDTS — Maximum Data Transfer Size
SourceIdentify Controller data structure, NVMe Base Specification
Revision2.4 (field present since early revisions)
Width / location1 byte, byte 77
InterpretationMaximum transfer = 2MDTS × minimum memory page size (CAP.MPSMIN); 0 = no limit reported. Applies to commands that transfer data (with some exceptions defined in the spec)
Practical useDriver splits I/O larger than this; test MDTS and MDTS + 1 page as a boundary pair. Example: MDTS = 5, MPSMIN 4 KiB → 128 KiB

Step 2 — Controller fields to record

Do the same for: VID (bytes 1:0), Serial Number (23:4, ASCII), Model Number (63:24, ASCII), Firmware Revision (71:64, ASCII), Number of Namespaces (519:516). For any further field — for example the optional admin and NVM command support fields — write "source: Identify Controller, Base 2.4, field named …" and look up its location; the course does not list offsets it has not verified.

Questions

  1. The script shows NUSE at 40 % of NSZE. What does that mean for a drive with no thin provisioning?
  2. LBAF1 has Relative Performance 0 and LBAF0 has 2. What should an administrator conclude?
  3. Why are SN and MN padded with spaces rather than null bytes?
  4. Which structure would you read to learn a ZNS namespace's zone size?

Challenge

Find one Identify field whose meaning you were taught and could not locate in the 2.4 documents. What happened to it?

Solution

Q1. 40 % of LBAs are allocated (written and not deallocated). On a drive that supports deallocation reporting, NUSE drops after Deallocate; it is not "space used by the file system". Q2. RP is a hint: 0 means "best performance" relative to other formats on this namespace. The 4 KiB format may perform better; reformatting destroys data and changes NSZE — a decision, not a tweak. Q3. They are defined as ASCII strings padded with spaces (confirm wording); tools must trim. Q4. The ZNS command-set-specific Identify Namespace structure (ZNS Command Set specification). Challenge. Typical outcomes: the field moved to a command-set specification; it became obsolete; or it was never in the specification (it was a tool's derived value). Each outcome is a lesson in provenance.

What a senior engineer notices

  • "Never invent a field meaning" includes vendor-specific areas: bytes in the vendor-specific region mean whatever the vendor says, and nothing without their document.

Failure variants

  • A tool reads FLBAS bits 3:0 only and mis-selects the format on a namespace with more than 16 formats.

Extension

Safe lab nvme id-ctrl /dev/nvme0 -H and nvme id-ns /dev/nvme0n1 -H (read-only): fill five field records from your own drive.

Background

A log page is a data structure the controller maintains and returns on request with Get Log Page (admin opcode 02h). Logs exist because some information is cumulative (health, errors), event-driven (changed namespaces, persistent events), or large (telemetry), and does not fit a register or a completion entry.

  2. For each, determine support: is it mandatory in the revision, reported in Identify Controller's log page attributes, or listed in the Supported Log Pages log (where implemented)?

Interoperability

A system is a chain: host ↔ driver ↔ PCIe platform ↔ NVMe controller ↔ firmware ↔ storage media. A standard interface defines each seam; it does not eliminate implementation bugs on either side of it.

The Linux NVMe driver carries a table of device-specific quirks — workarounds keyed by PCI vendor and device ID for drives that misbehave in known ways. Each quirk is a recorded interoperability bug. Reading the quirk list in the kernel source (drivers/nvme/host/pci.c) is an education in how standard interfaces fail in practice.

Cross-layer lab: "Read occasionally takes 10 seconds"

Safe lab Synthetic evidence.

Objective

From OS logs, NVMe logs, a PCIe trace and performance counters, determine which layer owns an intermittent 10-second Read.

Skills

  • Cross-layer elimination.
  • Recognising red herrings.
  • Designing the confirming experiment.

Hardware and software required

None.

Input

OS log (illustrative)

No NVMe timeouts, resets or errors in the window (the driver timeout is 30 s). One unrelated line: "pcieport 0000:00:01.1: AER: Corrected error received: 0000:01:00.0" with Receiver Error, at 03:12:44 — the slow reads happened at 03:41:05, 05:18:30 and 09:02:17.

NVMe logs

SMART / Health: Media and Data Integrity Errors unchanged across the day (0); Composite Temperature between 309 K and 316 K; Percentage Used 61 %. Error Information log: no new entries.

Performance counters (host)

CPU idle normal during the slow reads. On the same SQ and on other SQs, other reads issued during each slow read complete in under 200 µs. All three slow reads target LBAs between 0x3A00_0000 and 0x3A0F_FFFF. The application log shows this range holds an archive written 14 months ago and not rewritten since.

Challenge

Write the 30-second manager summary and the firmware-engineer summary (see Communication skill).

Hint

Where in the command lifecycle is the gap? Which agent owns that stage? What is special about the LBAs?

Solution

Layer walk. Application: issues ordinary reads — not the owner (the request is well-formed and in range). File system / block layer / driver: the request reached the device within microseconds (doorbell, fetch) and completed when the device answered — eliminated. Transport and PCIe transaction: fetch normal, data and CQE normal, 41,882 other commands flowed — eliminated. PCIe data link and physical: no NAKs, no Recovery, L0 throughout — eliminated. Firmware / media: the 9.96 s gap sits between FETCHED and DATA TRANSFER, i.e. in EXECUTING / MEDIA OPERATION, which the device alone owns. Owner: the device's media-read path (firmware read-recovery on aged data is the leading mechanism).

Red herring. The Receiver Error was corrected by the link, occurred 29 minutes before the first slow read, and did not recur at the slow reads: time course and magnitude both weaken it (see performance causality).

Why no logs. The read eventually succeeded. A device that recovers data after extended internal retries (read retry, stronger error correction) may log nothing in standard logs, because no error was returned. The standard interface does not expose internal retry activity (see storage media reality).

Confidence. Layer ownership: HIGH (elimination of all host and link layers with direct evidence). Mechanism (read recovery on data retained for 14 months): MEDIUM — consistent with the LBA clustering and age, but not observed directly.

Confirming experiments. (1) Re-read the range in a loop: if the same LBAs are consistently slow, the cause is data-location-specific. (2) Rewrite (refresh) a copy of a slow region elsewhere and read it: fast reads support the retention mechanism. (3) Issue the Read with Limited Retry set: if the device honours it, a fast error instead of a slow success supports "extended retry". (4) Ask the vendor for telemetry on read-retry levels. Any one of (2)–(4) can move mechanism confidence to HIGH; vendor confirmation to CONFIRMED.

Manager summary. "Three reads a day from a 14-month-old archive take ten seconds because the drive works hard to recover old data. Nothing is lost and nothing else is affected. We're confirming with the vendor; a background refresh of that archive should remove it."

What a senior engineer notices

  • The decisive observation is the location of the gap in the command lifecycle: between fetch and data. That single fact eliminates half the stack.
  • "Other commands complete normally during the gap" eliminates a global stall and points to something specific to this command.

Failure variants

  • The gap is between CQE and interrupt instead: a completely different owner (interrupt path).
  • The gap is before the fetch: the controller did not fetch for 10 s — arbitration starvation or a controller-wide stall; check other queues' fetches.

Teach-back 1 — "Explain an NVMe Read from application to NAND and back"

You must cover: software, queue, command, doorbell, PCIe, TLP, DMA, controller, media, completion, interrupt. Each layer is graded.

Layer-by-layer grading (0 = missing, 1 = vague, 2 = correct, 3 = correct with evidence/trace view)
LayerA score-3 answer mentions…
SoftwareSystem call, block layer request, driver building the command, buffer pinned and mapped (IOVA)
QueuePer-CPU SQ/CQ pair; tail advanced; slot index
Command64-byte SQE: opcode 02h, CID, NSID, SLBA, zero-based NLB, PRP1/PRP2
DoorbellMMIO write of the new tail to BAR0 + 1000h + offset (stride)
PCIePosted MWr for the doorbell; non-posted MRd and CplD for the fetch
TLPHeader fields that link request and completion (Requester ID, Tag); MPS-limited data TLPs
DMAController writes data to PRP addresses; IOMMU translation
ControllerParses, validates, schedules, maps LBA to media via FTL
MediaNAND read latency (tens of µs), ECC, possible retries — internal and not specified
Completion16-byte CQE: CID, SQ head, phase, status; posted by MWr
InterruptMSI-X MWr; handler checks phase; CQ head doorbell; request completed upward
Model answer

The application calls read() on a file opened for direct I/O. The block layer builds a request; the NVMe driver picks the submission queue of the current CPU, maps the user buffer for DMA (getting an I/O virtual address through the IOMMU), and fills a 64-byte SQE in the next slot: opcode 02h, a free CID, NSID 1, the starting LBA, NLB = blocks − 1, and PRP1 (plus PRP2 or a PRP list for larger buffers). It advances its tail and writes the new tail to the SQ's doorbell in BAR0 — a posted PCIe Memory Write. The controller sees the doorbell and issues a Memory Read for the SQE; the root complex returns a Completion with Data carrying the 64 bytes, matched by Requester ID and Tag. The controller validates the command, translates the LBAs through its flash translation layer, and reads NAND — tens of microseconds, with error correction and possibly retries, none of it visible on the link. It then writes the data to the host buffer with Memory Write TLPs no larger than Max Payload Size, through the IOMMU. It posts a 16-byte CQE (CID, SQ head, phase bit, status) with another Memory Write, then sends the MSI-X message — a Memory Write to the interrupt address — for the CQ's vector. The interrupt handler reads CQEs while the phase bit matches, completes the request, writes the CQ head doorbell, and the block layer wakes the application. Trace view: MWr, MRd, CplD, a gap, MWr × n, MWr, MWr, MWr.

Teach-back 2 — "Why a PCIe Completion TLP is not the same as an NVMe CQE"

Model answer

They live in different layers and answer different questions. A PCIe Completion is a transaction-layer packet that answers one non-posted PCIe request — for example the controller's Memory Read of an SQE — and is matched to it by Requester ID and Tag; it is created by the completer (often the root complex) and consumed by the requester's PCIe logic, within nanoseconds to microseconds, and it knows nothing about NVMe commands. An NVMe CQE is a 16-byte data structure that reports the outcome of an NVMe command, matched by CID and SQ identifier; it is created by the NVMe controller and written into host memory — and on PCIe it travels as the payload of a posted Memory Write, which has no PCIe Completion at all. A single NVMe Read involves several PCIe Completions (for the SQE fetch and any PRP list) and exactly one CQE. A PCIe Completion with Successful status says a memory access worked; a CQE with Success says a command worked. Confusing them leads to errors like "the completion arrived, so the command finished".

Teach-back 3 — "How would you debug a missing NVMe completion?"

Required: queue inspection, command tracking, doorbell, controller, DMA, completion, interrupt, PCIe evidence, logs, hypothesis elimination.

Model answer

First, track the command: its CID and SQ, when it was submitted, and that no CQE was consumed for it. Inspect the queues: the SQ slot contents (is the SQE well-formed?), the host's tail and the controller-reported SQ head from recent CQEs (was it fetched?), and the CQ memory itself — if a CQE for the CID is sitting there, the problem is notification (interrupt) or host consumption, not the controller. Check the doorbell: did the MWr with the right tail value go to the right address (analyzer, or driver tracing)? Check the controller: CSTS (RDY, CFS), whether other commands on the same and other queues complete (global versus local stall). Check DMA: in the analyzer, did the fetch occur, did data transfers start, did any request get UR, CA or time out (AER)? Check completion and interrupt: was a CQE MWr sent; was the MSI-X MWr sent; is the vector masked (MSI-X table, pending bits)? Read logs: kernel log (timeouts, AER, IOMMU faults), Error Information and SMART logs, vendor telemetry. Then eliminate: CQE present → interrupt path; fetched but no data → controller or DMA; DMA error → PCIe/IOMMU; not fetched → doorbell or controller; doorbell absent → driver. State the surviving hypothesis with confidence and the experiment that would confirm it.

Teach-back 4 — "What you would look for first in a LeCroy trace when a system reports an NVMe timeout"

Generic answers ("look for errors") score zero. Give a concrete investigative sequence.

Model answer

(1) Confirm capture scope: both directions, the right link, no filters, the time window covers the command's submission (timeouts are reported 30 s later by default on Linux, so the trigger must be placed to catch the submission, not the timeout). (2) Check link health over the window: LTSSM state, Recovery events, speed/width changes, NAK and replay counts — a link that left L0 changes everything. (3) Find the command: locate the CID from the kernel log and the SQ ID; find the doorbell MWr to that SQ's tail register whose value covers the command's slot. (4) Find the SQE fetch: an MRd to the SQ base + slot × 64, its CplD, and decode the SQE to confirm CID and fields. (5) Follow the data: MRd/CplD (write) or MWr (read) to the PRP addresses — look for completions with UR/CA status, missing completions (outstanding tags), poisoned TLPs. (6) Look for the CQE MWr to the CQ with that CID, and then the MSI-X MWr. (7) Mark the last stage that happened and the first that did not: that is the first abnormal event. (8) Compare with a neighbouring successful command in the same trace as the golden reference. (9) Note analyzer limitations (overflow, decoder version) before concluding.

Teach-back 5 — "Explain NVMe 2.4 to a senior engineer who knows NVMe 1.4"

Model answer

"The core you know is unchanged: registers, queues, doorbells, 64-byte SQE and 16-byte CQE, PRP/SGL, Identify, Get Log Page, Read/Write. What changed is the shape of the specification and the scope of the device. Since 2.0 the specification is a set: a Base specification, separate command set specifications (NVM, Zoned Namespaces, Key Value, and later Computational Programs and Subsystem Local Memory), separate transport specifications (PCIe, RDMA, TCP), plus NVMe-MI and Boot. Namespaces carry a command set identifier, so 'every namespace is block storage' is no longer safe; Identify has command-set-specific structures. Fabrics moved into the Base architecture. Then each revision added features; 2.4, released in August 2026 with all eleven documents revised together, focuses on security, virtualization, management and sustainability: post-quantum-ready key exchange for authentication, live migration of exported NVM subsystems between hosts (configuration templates identified by UUID), TDISP-related state reporting, persistent lockdown, per-controller rate limiting, voltage monitoring, idle exit-latency limits and a manufacturing-default reset. Most of that is management-plane: your trace analysis is the same, but more settings can explain a behaviour, and capability discovery is mandatory because none of it can be assumed. Read the Revision Changes document for the exact list, and verify field-level details in Base 2.4 — I have not quoted identifiers I haven't checked."
