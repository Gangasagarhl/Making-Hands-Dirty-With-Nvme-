This page is the course's practical spine: a ten-step hardware lab progression on a real Linux machine (read-only and safe), a twelve-step software progression in which you build your own parsers, decoders, simulators and report generator, precise requirements for the four teaching tools (queue simulator, TLP decoder, NVMe command decoder, PRP visualizer), and four full performance labs on percentiles, Little's law, link bandwidth and latency budgets.

Why this part exists

You cannot become a protocol engineer by reading about protocol engineering. You need to touch a real device (carefully), and you need to build the tools that make the protocol visible: when you have written a TLP decoder yourself, you never again confuse Fmt with Type; when you have simulated a phase-tag wrap, you recognise a stale-phase bug in a trace within seconds.

The progressions are ordered so that every lab uses only skills from earlier labs. The hardware track ends with correlating Linux logs with a trace; the software track ends with an automated forensic report. Together they rehearse the whole job.

Learning objectives

  • Identify and inspect an NVM Express (NVMe) SSD on Linux from PCI Express (PCIe) enumeration through namespaces, health and error logs, without risking data.
  • Explain what each inspection command proves and what it cannot prove.
  • Build, in Python with the standard library, a hex parser, bitfield parser, configuration-space parser, TLP header decoder, NVMe command and Completion Queue Entry (CQE) decoders, Physical Region Page (PRP) planner, queue simulator, timeline builder, anomaly detector, correlation engine and HTML report generator.
  • State the requirements of the course's four interactive tools and verify them against worked examples.
  • Compute and interpret mean, median, p95, p99 and p99.9 latency, throughput, IOPS and queue depth; identify bottleneck, saturation, bandwidth limit and latency limit.
  • Apply Little's law (L = λW) to storage, compute link bandwidth from signalling rate to payload rate, and build and modify an end-to-end latency budget.

The story

Learning to cook goes in steps. First you learn the names of things in the kitchen and where they live. Then you look inside the fridge without moving anything. Then you follow one simple recipe exactly. Only much later do you make your own recipe, and later still you can taste a dish and say "too much salt, added too early". A good teacher never lets you use the big knife on the first day.

An aircraft maintenance apprentice follows a structured progression: identify components, read the logbook, inspect without disassembly, run a ground test, observe instruments under load, and finally correlate a pilot's report with the flight-data record. Separately, the apprentice builds skill with tools: first reading gauges, then calibrating instruments, then writing inspection reports others rely on.

What maps well: a safe-to-dangerous ordering; looking before touching; tools before judgement.

What does not map: in storage, "looking" commands are not all harmless (some admin commands change state, some tools write by default), and the dangerous step is often a single mistyped device name.

What it hides: the software track has no physical risk but is where most of the understanding is built; both tracks are needed.

Safety rules for every hardware lab

  • Use a test machine and a scratch SSD that holds no data you need. Even read-only labs are done on a scratch device so that a mistyped command cannot cost you data.
  • Every command in H1–H9 is read-only. Never run format, sanitize, firmware download/commit, namespace create/delete/attach, or setpci with an = (a write) as part of these labs.
  • Workload tools must be explicitly read-only: fio --readonly. A write workload on the wrong device destroys data.
  • Identify the device by PCI address and serial number before every session; device names such as /dev/nvme0 can change between boots.
  • Do not unbind drivers, reset links or change power settings in these labs.

Hardware lab progression

Ten labs, H1–H10. Common to all of them unless stated: hardware — a Linux test machine with an NVMe SSD (the course's examples use the lab system: SSD at 0000:01:00.0, Gen4 x4); software — pciutils (lspci, setpci), nvme-cli, fio, sysstat (iostat); safety — Safe lab unless marked. H1 — Identify the PCIe device

Objective

Find every NVMe controller on the system and record its PCI address, IDs and class.

Skills

Bus/Device/Function addressing, class codes, topology.

Input

A running system.

Steps

lspci -D -nn | grep -i 'non-volatile'      # class 0108: NVM controller
lspci -tv                                   # where it sits in the tree
ls -l /sys/class/nvme/                      # nvme0 -> ../../devices/pci0000:00/0000:00:01.1/0000:01:00.0/nvme/nvme0

Expected output

One line per NVMe function with domain:bus:device.function, a class shown as [0108], vendor and device IDs in brackets, and the sysfs link from nvme0 to its PCI address.

Background

Class code 01h (mass storage), subclass 08h (non-volatile memory controller), programming interface 02h identifies an NVMe controller. See Chapter 17 — PCIe Enumeration.

Observation

Record: PCI address, upstream root port, vendor:device IDs, which nvmeX name maps to which address.

Questions

  1. What does lspci prove about the device's NVMe compliance?
  2. Why is the PCI address a better identifier than nvme0?

Challenge

Draw the path from the root complex to the SSD, including any switch.

Hint

lspci -tv nests downstream devices under their bridges.

Solution

(1) Nothing about compliance: it proves the function enumerated and reports a class code saying it is an NVMe controller. (2) Kernel names are assigned in probe order and can change; the PCI address is tied to the slot topology (it too can change if the hardware changes, so record the serial number as well). Challenge: on the lab system, root port 00:01.1 → 01:00.0 directly, no switch.

What a senior engineer notices

Whether the SSD sits behind a switch or a retimer: it changes where errors are reported and where an analyzer must be placed.

Failure variants

  • Device absent from lspci: link not trained or device not powered; go to dmesg and the root port's link status.
  • Present with no nvme driver bound: check lspci -k.

Extension

Repeat on a system with two SSDs and a switch; record the topology.

H2 — Read configuration space

Objective

Read the configuration header and capability list without writing anything.

Skills

Header layout, capability walking, link status.

Input

The PCI address from H1.

Steps

sudo lspci -vvv -s 01:00.0                 # decoded view; root needed for capabilities
sudo lspci -xxx -s 01:00.0                 # first 256 bytes as hex
sudo lspci -xxxx -s 01:00.0                # full 4 KiB including extended capabilities
sudo setpci -s 01:00.0 CAP_EXP+0x12.w      # read Link Status (no '=' means read)

Expected output

Decoded capabilities (Power Management, MSI, MSI-X, PCI Express), Link Capabilities vs Link Status (on the lab system: capable 16 GT/s x4, status 16 GT/s x4), and extended capabilities such as Advanced Error Reporting.

Background

Chapter 18 — Configuration Space.

Observation

Record capability offsets, negotiated speed/width, MPS and MRRS from Device Control.

Questions

  1. Why can lspci -xxx without root show fewer bytes?
  2. Which register says what the link can do and which says what it is doing?

Challenge

Walk the capability list by hand from the 0x34 pointer in the hex dump and confirm each capability ID and next pointer.

Hint

Each capability starts with an ID byte and a next-pointer byte.

Solution

(1) The kernel restricts reading beyond the first 64 bytes of configuration space to privileged users. (2) Link Capabilities (maximum supported speed and width) vs Link Status (current negotiated speed and width). A gap (for example capable Gen4, running Gen3) is a classic finding to investigate (slot, riser, signal integrity, platform limit).

What a senior engineer notices

MPS and MRRS values, because they shape every trace and throughput number, and whether AER is present and enabled.

Failure variants

  • All bytes read as FF: the device has dropped off the bus.
  • Link width lower than expected: lane failure or slot wiring.

Extension

Decode the same dump with your own parser from Lab S3.

H3 — Identify BARs

Objective

Find the controller's register BAR, its address, size and type.

Skills

BAR decoding, MMIO, sysfs resources.

Input

The PCI address.

Steps

sudo lspci -vv -s 01:00.0 | grep -i region
cat /sys/bus/pci/devices/0000:01:00.0/resource   # start end flags, one line per resource

Expected output

Illustrative shape for the lab system: "Region 0: Memory at fe600000 (64-bit, non-prefetchable) [size=16K]".

Background

Chapter 19 — BARs and MMIO.

Observation

Record BAR0 address and size. Compute where SQ1's tail doorbell is (BAR0 + 0x1008 if DSTRD = 0).

Questions

  1. Why is BAR0 64-bit but only one "Region" line shown?
  2. Is the BAR address the address the device uses for DMA?

Challenge

Find the MSI-X table's BAR and offset from the MSI-X capability and check it falls inside BAR0.

Hint

The MSI-X capability reports a BAR Indicator Register (BIR) and an offset for both the table and the Pending Bit Array.

Solution

(1) A 64-bit BAR uses two consecutive BAR registers (BAR0 and BAR1) that together form one region. (2) No: the BAR address is where the host reaches the device's registers (host → device MMIO). DMA addresses are host memory addresses (IOVAs) the device targets. Challenge: on the lab system the table is at BAR0 + 0x2000 and the PBA at BAR0 + 0x3000 (an implementation choice).

What a senior engineer notices

Whether the BAR is large enough for all doorbells at the reported stride and queue count.

Failure variants

  • BAR unassigned ("[disabled]" or "[virtual]"): resource allocation failure at boot.

Extension

Compute the highest doorbell offset for 65 queue pairs at DSTRD 0 and check it fits in 16 KiB.

H4 — Inspect the NVMe controller

Objective

Read controller identity and capability information.

Skills

Identify Controller, controller registers, sysfs attributes.

Input

/dev/nvme0 (confirmed against the PCI address).

Steps

cat /sys/class/nvme/nvme0/{model,serial,firmware_rev,transport}
sudo nvme id-ctrl /dev/nvme0               # Identify Controller (admin opcode 06h, read-only)
sudo nvme id-ctrl /dev/nvme0 -H | less     # human-readable bit fields
sudo nvme show-regs /dev/nvme0 -H          # CAP, VS, CC, CSTS, AQA ... (reads BAR0)

Expected output

Model, serial, firmware revision; MDTS, number of namespaces, optional command support (ONCS), volatile write cache; CAP.MQES, CAP.DSTRD, CAP.TO; VS; CC.EN = 1 and CSTS.RDY = 1.

Background

Chapter 24 — NVMe Registers, Chapter 30 — Admin Commands.

Observation

Record VS (NVMe version the controller reports), MDTS, MQES, DSTRD, and the volatile write cache field.

Questions

  1. Does VS = 2.0 mean the device implements every 2.0 feature?
  2. Why is show-regs sometimes unavailable?

Challenge

Convert MDTS into bytes using CAP.MPSMIN.

Hint

MDTS is a power-of-two multiple of the minimum memory page size; 0 means no limit reported.

Solution

(1) No: VS states the specification version the controller complies with; many features are optional and advertised separately in capability fields. (2) It maps the BAR from user space; some kernels or security settings (lockdown) prevent it. Challenge: bytes = 2^MDTS × 2^(12 + CAP.MPSMIN); for MPSMIN = 0 and MDTS = 5, 32 × 4 KiB = 128 KiB.

What a senior engineer notices

The firmware revision and the volatile write cache flag, because they decide whether a Flush does real work and which known issues apply.

Failure variants

  • id-ctrl times out: the admin queue is unhealthy; check CSTS.CFS (controller fatal status).

Extension

Decode the Identify Controller bytes yourself from nvme id-ctrl -b (binary) output.

H5 — Identify namespaces

Objective

List namespaces and their formats.

Skills

Namespace vs controller, LBA formats.

Input

The controller from H4.

Steps

sudo nvme list
sudo nvme list-ns /dev/nvme0               # active namespace IDs
sudo nvme id-ns /dev/nvme0n1 -H            # NSZE, NCAP, NUSE, LBA formats, in-use format
lsblk -o NAME,SIZE,LOG-SEC,PHY-SEC /dev/nvme0n1

Expected output

For the lab system: namespace 1, 512-byte LBAs (LBADS 9), NSZE 1,953,525,168 blocks (≈1 TB).

Background

Chapter 58 — Namespaces.

Observation

Record NSID, LBA size, metadata size, capacity.

Questions

  1. Why can NUSE be smaller than NSZE?
  2. What does the "n1" in nvme0n1 correspond to?

Challenge

Compute capacity in bytes from NSZE and LBADS and compare with lsblk.

Hint

LBA size = 2^LBADS.

Solution

(1) NUSE counts allocated blocks (thin provisioning or deallocated blocks can make it smaller); its meaning depends on features the namespace reports. (2) In Linux naming it is usually the namespace's instance, commonly NSID 1, but naming can differ with multipath; confirm with nvme id-ns. Challenge: 1,953,525,168 × 512 = 1,000,204,886,016 bytes.

What a senior engineer notices

Whether the in-use LBA format has metadata or protection information, which changes every I/O's data layout.

Failure variants

  • No namespaces listed: none attached to this controller.

Extension

Compare LBA formats offered with the one in use, and note the relative performance hints if reported.

H6 — Inspect SMART / health

Objective

Read health information and interpret it cautiously.

Skills

Get Log Page, units, critical warnings.

Input

The controller.

Steps

sudo nvme smart-log /dev/nvme0
sudo nvme smart-log /dev/nvme0 -o json     # machine-readable, for your own scripts

Expected output

Critical warning, composite temperature, available spare and threshold, percentage used, data units read/written, power cycles, power-on hours, unsafe shutdowns, media and data integrity errors, error log entries.

Background

Chapter 57 — SMART / Health.

Observation

Record data units read before and after H8, and unsafe shutdowns.

Questions

  1. What unit is "data units read"?
  2. Does "percentage used = 3%" mean 97% of life remains?

Challenge

Predict how much "data units read" should increase after H8's workload and verify.

Hint

Check the specification's definition of the data unit and its rounding.

Solution

(1) The specification defines a data unit as thousands of 512-byte units, rounded up (confirm wording in the Base Specification's SMART / Health Information log). (2) It is a vendor estimate of life used based on its own model; it can exceed 100 and is not a guarantee. Challenge: bytes read ÷ 512,000 ≈ expected increase.

What a senior engineer notices

Unsafe shutdown and media error counters, and any non-zero critical warning bit, before doing anything else with the device.

Failure variants

  • Temperature very high at idle: cooling problem that will distort performance labs.

Extension

Log SMART every minute during H8 and plot temperature.

H7 — Inspect the error log

Objective

Read the Error Information log and relate entries to commands.

Skills

Error log fields: error count, SQ ID, CID, status, LBA, namespace.

Input

The controller.

Steps

sudo nvme error-log /dev/nvme0
sudo nvme error-log /dev/nvme0 -o json

Expected output

Entries (possibly all empty) with error count, submission queue ID, command ID, status field, parameter error location, LBA, namespace.

Background

Chapter 44 — NVMe Errors.

Observation

Record the highest error count and whether entries are empty.

Questions

  1. Can an error log entry be matched to a kernel log line by time?
  2. Are entries guaranteed for every failed command?

Challenge

Explain how you would correlate an entry with an analyzer trace.

Hint

Look at which identifying fields the entry carries.

Solution

(1) Not directly: the entry identifies the command by SQ ID and CID (and an increasing error count) rather than by time; correlate via the CID/SQ and the order of events. (2) No: which errors are logged is defined partly by the specification and partly left to the controller; an empty log does not prove no errors occurred. Challenge: find the CQE in the trace with matching SQ ID, CID and status; then the CID's SQE fetch; CIDs are reused, so use the error count order and approximate time window to pick the right occurrence.

What a senior engineer notices

The parameter error location field, which points at the byte and bit of the command the controller objected to.

Failure variants

  • Log full of old entries from manufacturing tests: check error count increments rather than presence.

Extension

Write a script that saves the error log as JSON before and after a test and prints only new entries.

H8 — Run a safe read workload

Caution lab Read-only, but generates load. Use --readonly, double-check the device path, and do not run on a production machine.

Objective

Generate a controlled read workload and capture latency statistics.

Skills

fio parameters, direct I/O, read-only safety.

Input

The namespace block device.

Steps

sudo fio --name=rr4k --filename=/dev/nvme0n1 --readonly \
  --rw=randread --bs=4k --iodepth=32 --numjobs=1 \
  --ioengine=io_uring --direct=1 --time_based --runtime=30 \
  --percentile_list=50:95:99:99.9 --output-format=normal

Expected output

IOPS, bandwidth, completion latency mean and percentiles (values depend entirely on the device and system).

Background

Performance Engineering.

Observation

Record IOPS, mean, p50, p99, p99.9; compute Little's law L = IOPS × mean latency and compare with iodepth.

Questions

  1. Why --direct=1?
  2. Why might L come out below 32?

Challenge

Repeat at iodepth 1, 4, 16, 64, 256 and build a queue-depth curve.

Hint

L is what was actually outstanding on average, not what was allowed.

Solution

(1) To bypass the page cache so reads reach the device. (2) Submission overhead, completion batching, or a CPU-bound single job can keep fewer commands in flight than the configured depth; L measures the achieved in-flight depth. Challenge: expect IOPS to grow almost linearly at low depth, then flatten while latency grows (see the performance lab below).

What a senior engineer notices

Whether the drive was preconditioned and its temperature; random-read results on a fresh, empty drive can be unrepresentative (reads of never-written LBAs may be served without media access on some devices).

Failure variants

  • Forgetting --readonly with a write pattern: data loss.
  • Running on a partition that is mounted: interference from the filesystem.

Extension

Add --ioengine=libaio and compare.

H9 — Observe performance from the system's side

Caution lab Read-only observation during H8's workload.

Objective

Observe the same workload through kernel statistics and interrupts.

Skills

iostat, interrupt counters, queue-to-CPU mapping.

Input

H8 running in another terminal.

Steps

iostat -x 1 /dev/nvme0n1                    # r/s, rkB/s, r_await, aqu-sz, %util
grep nvme0 /proc/interrupts                 # per-queue vectors and per-CPU counts
cat /sys/block/nvme0n1/queue/nr_requests
ls /sys/block/nvme0n1/mq/                   # hardware queues as seen by blk-mq

Expected output

Reads per second close to fio's IOPS; average queue size (aqu-sz) close to Little's L; interrupt counts rising on the vectors for the CPUs running fio.

Background

Chapter 42 — Interrupt Architecture.

Observation

Which I/O queues and vectors carry the load? Does aqu-sz match L from H8?

Questions

  1. Why is %util not a good saturation metric for NVMe?
  2. Why do interrupts rise on only some CPUs?

Challenge

Pin fio to a different CPU and observe which vector's count rises.

Hint

Linux usually maps I/O queues to CPUs.

Solution

(1) %util measures the fraction of time at least one request was outstanding; a device serving many requests in parallel can be at 100% util with lots of headroom. (2) Each CPU submits on its mapped queue and the queue's completion vector is affined to that CPU set. Challenge: with taskset -c 3, the vector for the queue mapped to CPU 3 rises (mapping is kernel-version-dependent).

What a senior engineer notices

Interrupt rate vs IOPS: their ratio shows how many completions each interrupt covers (coalescing, batching).

Failure variants

  • All interrupts on one CPU: affinity misconfiguration, a CPU bottleneck hiding as device latency.

Extension

Repeat with polled I/O (--hipri with io_uring and poll queues configured) and compare interrupt counts.

  2. Which component's behaviour is now the focus?

S1 and S2 — Hex parser and bitfield parser

Objective

Turn hex text (bytes or DWORDs, with or without 0x, underscores, commas) into bytes, then extract any bit range from a DWORD.

Skills

Endianness, masks and shifts, field tables.

Input

The synthetic header of the SSD's SQE fetch: 0x20000010 0x010021FF 0x00000001 0x23400140.

Expected output

A field table with binary, hex, decimal and meaning for Fmt, Type, TC, Length, Requester ID, Tag, byte enables and address.

Background

TLP headers are drawn and transmitted with byte 0 holding bits 31:24 of DW0 (big-endian within each DWORD as drawn), whereas configuration space and NVMe data structures are little-endian in memory. Mixing the two conventions is the most common parser bug.

Steps

  1. Write parse_hex that accepts both DWORD tokens and byte tokens.
  2. Write field(value, hi, lo).
  3. Describe the header layout as a table of (DW, hi, lo, name, meaning) and loop over it.
#!/usr/bin/env python3
"""bitfields.py - Labs S1/S2: parse hex text into DWORDs, then slice bit fields.

Decodes a SYNTHETIC 4DW Memory Read request header (non-Flit format) and prints
each field as binary, hex, decimal and meaning. Standard library only.
"""


def parse_hex(text):
    """S1: accept '20 00 00 10 01 00 21 ff ...' or '0x20000010 0x010021FF', return bytes."""
    cleaned = text.replace("0x", " ").replace(",", " ").replace("_", "")
    tokens = cleaned.split()
    if all(len(t) == 8 for t in tokens):          # DWORD tokens, big-endian as written
        return b"".join(int(t, 16).to_bytes(4, "big") for t in tokens)
    return bytes(int(t, 16) for t in tokens)      # byte tokens


def dword(buf, n):
    """TLP headers are transmitted byte 0 first; byte 0 holds bits 31:24 of DW0 as drawn."""
    return int.from_bytes(buf[4 * n:4 * n + 4], "big")


def field(value, hi, lo):
    """S2: extract bits hi..lo (inclusive) of a 32-bit value."""
    return (value >> lo) & ((1 << (hi - lo + 1)) - 1)


FMT = {0b000: "3DW header, no data", 0b001: "4DW header, no data",
       0b010: "3DW header, with data", 0b011: "4DW header, with data"}

LAYOUT = [  # (DW, hi, lo, name, meaning function)
    (0, 31, 29, "Fmt", lambda v: FMT.get(v, "other/reserved - check spec")),
    (0, 28, 24, "Type", lambda v: "memory request (with Fmt 000/001 = MRd)" if v == 0 else "see Type table"),
    (0, 22, 20, "TC", lambda v: f"traffic class {v}"),
    (0, 9, 0, "Length", lambda v: f"{v or 1024} DW = {(v or 1024) * 4} bytes"),
    (1, 31, 16, "Requester ID", lambda v: f"Bus {v >> 8:02x} Dev {(v >> 3) & 0x1f:02x} Fn {v & 7}"),
    (1, 15, 8, "Tag", lambda v: f"tag {v} (8-bit tag field)"),
    (1, 7, 4, "Last DW BE", lambda v: f"bytes enabled mask {v:04b}"),
    (1, 3, 0, "First DW BE", lambda v: f"bytes enabled mask {v:04b}"),
    (2, 31, 0, "Address[63:32]", lambda v: "upper address DW"),
    (3, 31, 2, "Address[31:2]", lambda v: "lower address, DW aligned"),
]


def decode(text):
    buf = parse_hex(text)
    print(f"{'field':16s} {'binary':>34s} {'hex':>11s} {'dec':>11s}  meaning")
    for dw, hi, lo, name, meaning in LAYOUT:
        v = field(dword(buf, dw), hi, lo)
        width = hi - lo + 1
        print(f"{name:16s} {format(v, f'0{width}b'):>34s} {hex(v):>11s} {v:>11d}  {meaning(v)}")
    addr = (dword(buf, 2) << 32) | (dword(buf, 3) & ~0x3)
    print(f"\nfull address = 0x{addr:016X}")


if __name__ == "__main__":
    # SYNTHETIC: Lab SSD (RID 0x0100) fetches a 64-byte SQE from SQ1 slot 5.
    decode("0x20000010 0x010021FF 0x00000001 0x23400140")

Observation

The program prints Fmt 001 (4DW header, no data), Type 00000 (memory request), Length 16 DW = 64 bytes, Requester ID 0x0100 (bus 01 device 00 function 0), Tag 0x21, byte enables 1111/1111, and the full address 0x0000000123400140.

Questions

  1. Why does Length 0 mean 1024 DWORDs?
  2. Why are address bits 1:0 not part of the address field?

Challenge

Add a byte-token test: feed the same header as 16 space-separated bytes and confirm identical output.

Hint

parse_hex already handles byte tokens; check the 8-character rule.

Solution

(1) The 10-bit Length field encodes 1–1024 DWORDs; the value 0 is defined as 1024 (the maximum). (2) Memory request addresses are DWORD-aligned; byte granularity comes from the byte enables. Challenge: decode("20 00 00 10 01 00 21 ff 00 00 00 01 23 40 01 40") produces the same table.

What a senior engineer notices

Whether the parser rejects malformed input (odd number of hex digits, wrong length) instead of silently decoding garbage.

Failure variants

  • Treating a little-endian memory dump of a TLP as big-endian.
  • Off-by-one in hi - lo + 1.

Extension

Add 10-bit tag handling: the extra tag bits live in other header fields; find them in the PCI Express Base Specification and mark the decoder's assumption.

"""cfg_cqe.py - Labs S3 and S6: decode a PCI configuration header and an NVMe CQE.

Both inputs are SYNTHETIC teaching data for the course's lab system.

import struct

# 64-byte Type 0 configuration header, little-endian as read from config space.
# Vendor/Device IDs are placeholders, not a real product.
CFG_HEX = (
    "cdab3412 06041000 00020801 00000000"   # 00h: VID DID | CMD STS | REV PI SUB CLASS | CLS LAT HDR BIST
    "0400 60fe 00000000 00000000 00000000"  # 10h: BAR0 BAR1 BAR2 BAR3
    "00000000 00000000 00000000 cdab0100"   # 20h: BAR4 BAR5 CardBus SSVID SSID
    "00000000 40000000 00000000 ff010000"   # 30h: ROM CapPtr rsvd INTLINE INTPIN ...
)


def decode_cfg(raw):
    vid, did, cmd, sts = struct.unpack_from("<HHHH", raw, 0x00)
    rev, progif, sub, cls = struct.unpack_from("<BBBB", raw, 0x08)
    hdr = raw[0x0E]
    bars = struct.unpack_from("<6I", raw, 0x10)
    cap = raw[0x34]
    print(f"Vendor ID 0x{vid:04X}  Device ID 0x{did:04X}  (synthetic placeholders)")
    print(f"Command 0x{cmd:04X}: memory space {'on' if cmd & 2 else 'off'}, bus master {'on' if cmd & 4 else 'off'}")
    print(f"Status  0x{sts:04X}: capabilities list {'present' if sts & 0x10 else 'absent'}")
    print(f"Class {cls:02X}h / subclass {sub:02X}h / prog-if {progif:02X}h"
          + ("  -> NVM Express controller" if (cls, sub, progif) == (1, 8, 2) else ""))
    print(f"Header type {hdr & 0x7F} ({'multi' if hdr & 0x80 else 'single'}-function)  revision {rev:02X}h")
    i = 0
    while i < 6:
        b = bars[i]
        if b & 1:
            print(f"BAR{i}: I/O space 0x{b & ~3:X}")
            i += 1
            continue
        kind = (b >> 1) & 3
        pref = "prefetchable" if b & 8 else "non-prefetchable"
        if kind == 2:
            addr = (bars[i + 1] << 32) | (b & ~0xF)
            if addr:
                print(f"BAR{i}/{i + 1}: 64-bit memory, {pref}, address 0x{addr:X}")
            i += 2
        else:
            if b & ~0xF:
                print(f"BAR{i}: 32-bit memory, {pref}, address 0x{b & ~0xF:X}")
            i += 1
    print(f"Capabilities pointer 0x{cap:02X}  (walk the list from here)")
    print("Note: BAR size needs the write-ones sizing procedure - never do that on a live device.")


def decode_cqe(dw):
    """dw: four 32-bit DWORDs of a 16-byte CQE (DW0..DW3)."""
    sqhd, sqid = dw[2] & 0xFFFF, dw[2] >> 16
    cid, phase = dw[3] & 0xFFFF, (dw[3] >> 16) & 1
    status = dw[3] >> 17                     # 15-bit Status field
    sc, sct = status & 0xFF, (status >> 8) & 0x7
    more, dnr = (status >> 13) & 1, (status >> 14) & 1
    print(f"DW0 command-specific 0x{dw[0]:08X}")
    print(f"SQ Head Pointer {sqhd}  SQ Identifier {sqid}  CID 0x{cid:04X}  Phase {phase}")
    print(f"Status: SCT {sct}  SC 0x{sc:02X}  More {more}  DNR {dnr}"
          + ("  -> success" if sct == 0 and sc == 0 else "  -> look up SCT/SC in the spec tables"))


if __name__ == "__main__":
    decode_cfg(bytes.fromhex(CFG_HEX.replace(" ", "")))
    print()
    decode_cqe([0x00000000, 0x00000000, 0x00010006, 0x00010005])   # success, CID 5
    print()
    decode_cqe([0x00000000, 0x00000000, 0x00010007, 0x80050006])   # SCT 0 SC 02h, DNR 1

Background

Chapter 18 (configuration header), Chapter 29 and Chapter 44 (CQE and status). The CQE layout used: DW2 = SQ Identifier (31:16) and SQ Head Pointer (15:0); DW3 = Status (31:17), Phase Tag (16), CID (15:0); within the 15-bit Status field, SC is bits 7:0, SCT bits 10:8, More bit 13 and DNR bit 14 (bits 12:11 carry the Command Retry Delay field in newer revisions; confirm in the Base Specification's CQE figure).

Steps

  1. Run the program and check every line against the expected output.
  2. Hand-decode DW3 = 0x80050006 on paper.
  3. Add a third CQE with a non-zero SCT.

Observation

Generic status 02h is Invalid Field in Command; DNR = 1 tells the host that retrying the same command will not help.

Questions

  1. Why does the parser never compute BAR sizes?
  2. Why does the CQE carry the SQ identifier?

Challenge

Walk the capability list from 0x40 in a full 256-byte synthetic dump that you construct (PM at 0x40 → MSI-X at 0x50 → PCIe at 0x70).

Hint

Each capability: ID at offset 0, next pointer at offset 1; 0x00 ends the list.

Solution

(1) Sizing requires writing all ones to the BAR and reading back, which changes device state; a parser of dumps cannot and must not do it. Size comes from the OS (lspci's [size=…]). (2) Several SQs can share one CQ; the SQ identifier plus CID identify the command. Paper decode: 0x80050006 → CID = 0x0006; bit 16 = 1 (phase); status = 0x4002 → SC 0x02, SCT 0, More 0, DNR 1.

What a senior engineer notices

Whether the decoder distinguishes "unknown status" from "success" and prints raw values so nothing is lost in translation.

Failure variants

  • Reading DW3 as big-endian from a memory dump.
  • Treating a 64-bit BAR's upper half as a separate 32-bit BAR.

Extension

Feed it the hex dump from hardware lab H2.

S11 — NVMe command / TLP correlation engine

Objective

Assign every TLP to an NVMe command (or to "not command-related": configuration, link management, other devices).

Method

  1. Learn the queue map from admin commands (Create I/O SQ/CQ: base addresses, sizes, vectors) or from configuration input.
  2. Doorbell writes → queue and new tail.
  3. MRd to an SQ region → slots fetched; their CplD payload → SQEs (opcode, CID, PRPs).

#!/usr/bin/env python3
"""queue_sim.py - conceptual NVMe SQ/CQ simulator with fault injection (SIMULATION).

Models ring indices, doorbells, phase tags and interrupts only. It is not a
device model: no PCIe, no timing, no real register access. Standard library only.
Run: python3 queue_sim.py            (all scenarios)
"""


class Pair:
    def __init__(self, qid, sq_size, cq_size):
        self.qid, self.sqs, self.cqs = qid, sq_size, cq_size
        self.sq = [None] * sq_size          # host memory: SQ entries
        self.cq = [None] * cq_size          # host memory: CQ entries (cid, sqhd, phase)
        self.sq_tail = 0                    # host-owned producer index
        self.sq_head = 0                    # controller-owned consumer index
        self.db_sq_tail = 0                 # last value written to SQ tail doorbell
        self.cq_tail, self.cq_phase = 0, 1  # controller-owned producer index and phase
        self.cq_head, self.host_phase = 0, 1  # host-owned consumer index and expected phase
        self.db_cq_head = 0                 # last value written to CQ head doorbell
        self.log = []

    # ---- host side
    def submit(self, cid):
        if (self.sq_tail + 1) % self.sqs == self.sq_head:
            self.log.append(f"host: SQ{self.qid} full, cannot submit CID {cid}")
            return
        self.sq[self.sq_tail] = {"cid": cid}
        self.sq_tail = (self.sq_tail + 1) % self.sqs

    def ring_sq(self, value=None):
        self.db_sq_tail = self.sq_tail if value is None else value
        self.log.append(f"host: SQ{self.qid} tail doorbell <- {self.db_sq_tail}")

    def reap(self):
        done = []
        while True:
            e = self.cq[self.cq_head]
            if e is None or e["phase"] != self.host_phase:
                break
            done.append(e["cid"])
            self.cq_head = (self.cq_head + 1) % self.cqs
            if self.cq_head == 0:
                self.host_phase ^= 1
        if done:
            self.db_cq_head = self.cq_head
            self.log.append(f"host: reaped CIDs {done}; CQ{self.qid} head doorbell <- {self.cq_head}")
        return done

    # ---- controller side
    def controller_run(self, drop_cid=None, ignore_cq_head=False):
        seen, posted = set(), 0
        while self.sq_head != self.db_sq_tail:
            sqe = self.sq[self.sq_head]
            self.sq_head = (self.sq_head + 1) % self.sqs
            cid = sqe["cid"] if sqe else None
            if cid in seen:
                self.log.append(f"sim: CID {cid} is already outstanding on SQ{self.qid} - host bug; "
                                "a real controller is not guaranteed to detect it")
            seen.add(cid)
            if cid == drop_cid:
                self.log.append(f"ctrl: (fault) no completion posted for CID {cid}")
                continue
            nxt = (self.cq_tail + 1) % self.cqs
            head = self.cq_head if ignore_cq_head else self.db_cq_head
            if nxt == head:
                self.log.append(f"ctrl: CQ{self.qid} full (head doorbell={head}); completion for CID {cid} must wait")
                break
            self.cq[self.cq_tail] = {"cid": cid, "sqhd": self.sq_head, "phase": self.cq_phase}
            self.cq_tail = nxt
            posted += 1
            if self.cq_tail == 0:
                self.cq_phase ^= 1
            self.log.append(f"ctrl: CQE CID {cid} SQHD={self.sq_head} P={self.cq[(self.cq_tail - 1) % self.cqs]['phase']}")
        if posted:
            self.log.append(f"ctrl: interrupt for CQ{self.qid} ({posted} new CQEs)")


def scenario(name, fn):
    q = Pair(1, 8, 8)
    fn(q)
    print(f"--- {name}")
    for line in q.log:
        print("   ", line)


def normal(q):
    for cid in (1, 2, 3):
        q.submit(cid)
    q.ring_sq()
    q.controller_run()
    q.reap()


def wrong_tail(q):
    for cid in (1, 2, 3):
        q.submit(cid)
    q.ring_sq(2)            # host forgets the third command
    q.controller_run()
    q.reap()
    q.log.append(f"note: CID 3 sits in SQ slot 2 but the controller was told tail=2")


def wrong_qid(q):
    q.submit(1)
    q.log.append("host: (fault) writes tail=1 to SQ2's doorbell (BAR0+0x1010) instead of SQ1's (BAR0+0x1008)")
    q.controller_run()              # SQ1 doorbell never changed, so SQ1 looks empty
    q.log.append("note: SQ1 still holds CID 1; SQ2 does not exist, so the write targets an invalid doorbell")
    q.log.append("note: how the controller reports that is defined by the spec - look up doorbell error reporting")


def duplicate_cid(q):
    for cid in (7, 7):
        q.submit(cid)
    q.ring_sq()
    q.controller_run()
    q.reap()


def missing_completion(q):
    for cid in (1, 2):
        q.submit(cid)
    q.ring_sq()
    q.controller_run(drop_cid=2)
    q.reap()
    q.log.append("note: host timeout logic must notice CID 2; nothing else will")


def cq_overflow(q):
    for cid in range(1, 8):         # 7 commands, CQ of 8 holds at most 7 unreaped
        q.submit(cid)
    q.ring_sq()
    q.controller_run()              # host never reaps / never rings CQ head
    for cid in range(8, 10):
        q.submit(cid)
    q.ring_sq()
    q.controller_run()


def stale_phase(q):
    for cid in range(1, 8):
        q.submit(cid)
    q.ring_sq()
    q.controller_run()
    q.reap()
    q.host_phase ^= 1               # (fault) host driver flips its phase at the wrong time
    for cid in (8, 9):
        q.submit(cid)
    q.ring_sq()
    q.controller_run()
    got = q.reap()
    q.log.append(f"note: host reaped {got or 'nothing'} although CQEs for 8 and 9 were posted")


if __name__ == "__main__":
    scenario("normal", normal)
    scenario("wrong tail", wrong_tail)
    scenario("wrong queue ID", wrong_qid)
    scenario("duplicate CID", duplicate_cid)
    scenario("missing completion", missing_completion)
    scenario("CQ overflow (host never updates CQ head)", cq_overflow)
    scenario("stale phase", stale_phase)

Run with python3 queue_sim.py. Each scenario prints a log from the host's and controller's points of view. In "CQ overflow" the controller reports the CQ full after seven entries because a ring of eight slots can hold at most seven unconsumed entries (one slot stays empty to distinguish full from empty). In "stale phase", CQEs for CIDs 8 and 9 are in memory but the host, expecting the wrong phase, reaps nothing.

This is a simulation of index arithmetic, not of a device. It has no timing, no PCIe, and its error messages are not controller behaviour. Real controller responses to invalid doorbell writes, duplicate CIDs or full queues are defined (or left open) by the specification; check the Base Specification before predicting them.

PRP visualizer requirements

The visualizer (Lab S7 and the PRP Visualizer) takes page size, buffer address and buffer length and shows PRP1, PRP2, the PRP list if required, and the pages covered. It must clearly state its assumptions.

Rules it encodes

  • PRP1 points to the first byte; it may have a non-zero offset within its page.
  • If the transfer fits in PRP1's page, PRP2 is not used.
  • If it needs exactly two pages, PRP2 is the second page's address (offset 0).
  • If it needs more than two pages, PRP2 points to a PRP list whose entries are the remaining page addresses (offset 0).
  • A list longer than one page is chained: the last entry of a full list page points to the next list page (confirm the exact chaining and alignment rules for list pointers in the Base Specification).
#!/usr/bin/env python3
"""prp_plan.py - which PRP entries describe a buffer? (conceptual, SIMULATION)

Assumptions (state them, always):
  * host memory page size = 4 KiB (CC.MPS = 0 in the course's lab system)
  * buffer is physically contiguous in IOVA space (a real buffer may not be)
  * one PRP list page holds page_size / 8 entries; list chaining is shown but
    the last-entry-points-to-next-list rule must be confirmed in the spec
Standard library only.
"""

LIST_BASE = 0x1_5000_0000          # PRP list pages (lab system)


def plan(addr, length, page=4096):
    first_off = addr % page
    pages, a = [], addr
    end = addr + length
    while a < end:
        pages.append(a)
        a = (a // page + 1) * page   # next page boundary
    print(f"buffer 0x{addr:X}, {length} bytes, page {page} -> touches {len(pages)} page(s)")
    print(f"  PRP1 = 0x{pages[0]:X}  (offset 0x{first_off:X} into its page)")
    if len(pages) == 1:
        print("  PRP2 = not used (whole transfer fits in PRP1's page)")
    elif len(pages) == 2:
        print(f"  PRP2 = 0x{pages[1]:X}  (second page, offset 0)")
    else:
        per_list = page // 8
        print(f"  PRP2 = 0x{LIST_BASE:X}  (pointer to a PRP list, {len(pages) - 1} entries)")
        for i, p in enumerate(pages[1:]):
            print(f"    list[{i}] = 0x{p:X}")
        if len(pages) - 1 > per_list:
            print(f"  NOTE: more than {per_list} entries -> list chaining needed (check spec rules)")
    print()


if __name__ == "__main__":
    plan(0x2_0000_0000, 4096)        # aligned 4 KiB: PRP1 only
    plan(0x2_0000_0E00, 1024)        # 1 KiB crossing a page: PRP1 + PRP2
    plan(0x2_0000_0200, 8192)        # 8 KiB, unaligned: three pages -> list
    plan(0x2_0001_0000, 16384)       # 16 KiB aligned: four pages -> list

Output (from running it): aligned 4 KiB uses PRP1 only; 1 KiB at offset 0xE00 uses PRP1 and PRP2 = 0x200001000; 8 KiB at offset 0x200 touches three pages, so PRP2 points to a list with two entries; 16 KiB aligned touches four pages and needs a three-entry list.

Assumptions to display

  • Memory page size is the host-configured CC.MPS (4 KiB on the lab system), not necessarily the CPU page size.
  • The buffer is contiguous in the device's address space (IOVA); real buffers can be scattered, giving arbitrary list entries.
  • The list location is a placeholder (the lab system's PRP list region).
  • SGLs are not modelled.

Exercise

A 12 KiB transfer starts at 0x2_0000_0F00. How many pages, and what are PRP1, PRP2 and the list?

Model answer

It spans 0x2_0000_0F00 to 0x2_0000_3EFF: pages at 0x0000, 0x1000, 0x2000, 0x3000 → four pages. PRP1 = 0x2_0000_0F00; PRP2 = list pointer; list = 0x2_0000_1000, 0x2_0000_2000, 0x2_0000_3000. An unaligned start always costs an extra page.
