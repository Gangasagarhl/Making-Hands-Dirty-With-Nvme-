One page that maps every major concept of the course to the layer it lives in, the specification that defines it, the Linux evidence that shows it, the trace evidence that proves it, and the chapter that teaches it. Use it as an index when you study, a checklist when you debug, and a map when you review a design.

How to read the matrix

The course keeps three technologies apart: NVM Express (NVMe), the storage interface and its command sets; PCI Express (PCIe), the interconnect; and the NVMe over PCIe Transport specification that joins them. Most confusion in debugging comes from asking one of them a question only another can answer. The matrix makes the division explicit: every row says which document owns the concept, and every row says what evidence you can actually collect.

Column meanings
ColumnWhat it tells you
NVMe BaseWhat the NVM Express Base Specification (Revision 2.4 in the August 2026 set) defines about the concept: architecture, controller properties, admin commands, status, logs, features, reset and power behaviour
NVM Cmd SetWhat the NVM Command Set Specification (1.3) adds: logical-block I/O commands and namespace formats. For other command sets (ZNS 1.5, KV 1.4, SLM 1.3, Computational Programs 1.3) the row names that document instead
PCIe TransportWhat the NVMe over PCIe Transport Specification (1.4) defines: the register map in a BAR, doorbells, memory-resident queues, PRPs, interrupts, PCIe-specific reset interaction
PCIe SpecWhat the PCI Express Base Specification (revision families 5.0, 6.x, 7.0) defines: physical, data link and transaction layers, configuration space, error handling, power management, virtualization capabilities
LinuxSafe, read-only evidence on a Linux host: lspci, sysfs, nvme-cli, kernel log, tracepoints
TraceWhat a PCIe protocol analyzer (or, for fabrics, a network capture) shows when the concept is in action
ChaptersWhere the concept is taught: chapters (Ch) and deep-dive modules (M)

Specification cells name topics and document names, never section numbers, because section numbering changes between revisions. Linux cells describe commands and sysfs files whose exact output varies by kernel and tool version. Trace cells describe what a correctly configured analyzer would show; some analyzers need BAR and queue addresses before they can decode NVMe from TLPs. Rows about features new in NVMe 2.4 describe purpose only — field-level details must be checked in the specification. Version-dependent

Evidence strength legend used in the evidence columns: proves (direct observation of the mechanism), suggests (consistent with but not unique to it), cannot show (outside what that source can see).

Two rules fall out of this table. First, an identifier is only meaningful in the layer that owns it: a PCIe tag says nothing about which NVMe command a TLP serves, and a CID never appears in a TLP header. Second, correlation across layers always needs a bridge — an address (SQ slot, buffer IOVA), a time window, or a decoded payload (the SQE inside a CplD). Using the matrix

As a study plan

Pick one row a day. For that concept, read the owning specification topic, run the Linux command (on a safe system), find the trace evidence in a synthetic trace on Example Data Sets or the Trace Lab, and explain to yourself why the empty cells are empty. A row is mastered when you can fill every cell from memory and cite the source for the specification cells.

As a debugging checklist

When a symptom appears, find its row in the symptom table, then walk the corresponding concept rows across the evidence columns from cheapest (Linux, read-only) to most expensive (analyzer capture). Record which cells you have evidence for and which you are assuming; an investigation whose conclusion rests on cells marked "suggests" needs a disambiguating experiment before it is a root cause (Debugging Methodology, Evidence-Based Debugging).

As a design-review map

For a new feature, add a row: which document owns it, what new fields it adds, what Linux evidence will exist, what a trace will show, and what a validation engineer will test. If any cell is blank because nobody has thought about it — not because it is genuinely not applicable — the design review has found work to do (Senior Engineer Thinking).

Exercises

  1. Fill in a matrix row for "interrupt coalescing" across all core columns.
    Model answer

    NVMe Base: Interrupt Coalescing feature (aggregation threshold and time) and per-vector configuration. NVM Cmd Set: none. PCIe Transport: applies to MSI/MSI-X vectors for completion queues. PCIe Spec: nothing specific; the interrupt is an MWr. Linux: nvme get-feature -f 8; interrupt counts in /proc/interrupts per CQ. Trace: fewer MSI-X MWrs than CQE MWrs; MSI-X following the Nth CQE or a time gap. Chapters: Ch 43, Performance.

  2. Explain why "Namespaces" has empty PCIe columns but "Interrupts" does not.
    Model answer

    A namespace is an NVMe concept that exists only in command fields (NSID) and data structures; PCIe carries it as opaque payload. Interrupts over PCIe are themselves PCIe transactions (MSI/MSI-X writes) configured through PCIe capabilities, so the PCIe specification defines the mechanism while NVMe defines when it is used.

  3. For the "Write data path" row, which evidence would distinguish a host DMA-mapping bug from a controller bug?
    Model answer

    The analyzer shows the device's MRd addresses: if they equal the PRP entries and the completions are UR with an IOMMU fault logged for that IOVA, the host mapping is at fault. If the MRd addresses differ from the PRP entries the host wrote (visible in the fetched SQE or PRP list), the controller computed them wrongly.
