This module builds on Chapter 60 — Key Value, which introduced the KV namespace (CSI 01h), the Store, Retrieve, Delete, Exist and List commands, the SIKE/SINKE options, the key and value limits and the KV statuses. Here the subject is building systems on KV namespaces: how a host library maps real names onto short keys, how byte-exact keys break between tools, how to iterate safely, what the device's index costs as it grows, how KV traffic uses the PCIe link compared with block storage, and what "stored" means when the power fails.

Orientation

Chapter 60 traced single KV commands: a Store, a Retrieve, a Delete racing a Retrieve (87h), and an oversized key (86h). Real KV deployments fail in ways a single command cannot show — two libraries that disagree on what a key is, a List loop that sees a key twice, latency that rises with the number of keys, and data that disappears after power loss even though every Store succeeded. This module covers those, and gives you tools to quantify when KV is worth using.

Kid story

A school has a lost-property cupboard with tiny labels — each label fits only a few letters. "Alexandra Montgomery's blue raincoat" will not fit, so the caretaker writes a short code like "AM7" and pins a full note inside the pocket saying whose coat it really is.

One day a teacher asks for "AM7 " with a space at the end. The caretaker looks at the label — "AM7", no space — and says "not here". The coat is right there, but the label is not exactly the same.

Another day the caretaker writes a new label but has not pinned it yet when the lights go out. In the morning, the old label is still there.

Analogy boundary

What it represents. The tiny label is the key with its maximum length; the short code is a hash of the real name; the note inside the pocket is the full name stored inside the value to detect collisions; "AM7 " versus "AM7" is the byte-exact key comparison (a NUL-padded key is a different key); the unpinned label is a completed Store that was still in a volatile write cache when power was lost.

What it hides. The caretaker's own index — how the device finds a key among millions — and that it may not fit in the device's fast memory. The fact that asking "what is in the cupboard?" (List) while children are adding and removing coats may show some coats twice or not at all.

Where it misleads. The caretaker could guess that "AM7 " meant "AM7". The device must not: keys are byte strings, not text. And losing an unpinned label is not carelessness — if the drive advertises a volatile write cache, it is allowed until the host sends Flush.

Mechanism

The mechanism followed here is a host library "put" of a long name, with collision handling and durability. Synthetic example for teaching on namespace 3 of the Lab SSD; key and length fields are named, not positioned, as in Chapter 60.

  1. Map. Who: library. What: hash the name to a key no longer than the maximum key length read from the KV format descriptor (16 bytes assumed here, uncertain per Chapter 60). Where: host CPU. Evidence: library logs only.
  2. Wrap. Who: library. What: build the value envelope: name length, name, payload. Evidence: the value bytes the device fetches.
  3. Create-only Store. Who: library. What: Store (01h) with SINKE. Where: SQ1. Evidence: SQE with key bytes, key length, value size, Store option; device MRds pulling exactly the value size.
  4. Resolve. Who: library. What: on 89h Key Exists, Retrieve (02h) the key and compare the stored name: same name → update with a plain Store (or SIKE); different name → collision, probe the next key. Evidence: the 89h CQE then a Retrieve SQE with the same key.
  5. Complete. Who: controller. What: index updated; value possibly in the volatile cache. Evidence: success CQE.
  6. Make durable. Who: library. What: Flush (00h) when the application requires durability, or batch Flushes. Evidence: a Flush SQE and its CQE after the Stores.
  7. Acknowledge. Who: library. What: report success to the application only after the step its contract requires (Store or Flush). Evidence: application logs.

The ladder for key mapping

Long names get short codes on the label and the full name is pinned inside, so mix-ups can be caught.

The host turns names into keys within the device limit and stores the name with the value to detect collisions.

A hash function in the library, SINKE for atomic create, Retrieve to check ownership, probing to resolve, Flush for durability.

NVMe Key Value Command Set 1.4: key and key length in the command, Store options, KV statuses; NVMe Base 2.4: Flush and the volatile write cache.

Each Store is one SQE (key inside) plus value MRds; each collision adds a Store and a Retrieve.

In a capture: 01h SQE → 89h CQE → 02h SQE with the same key bytes → 01h SQE with a different key → success → 00h.

Missing data: compare key bytes and lengths byte for byte between writer and reader; then check probe chains; then check Flush.

Link efficiency

η = v / ( v + Bfixed + NTLP × O )

η
link efficiency of one Store: payload bytes over all bytes on the link
v
value size in bytes
Bfixed
payload of the fixed parts: 4-byte doorbell, 64-byte SQE, 16-byte CQE, 4-byte MSI-X data
NTLP
number of TLPs in the command (doorbell, MRd requests, CplDs, MWrs)
O
per-TLP overhead in bytes (header, framing, sequence number, LCRC); an assumption of 24 bytes in this module

Worked example: a 16-byte value takes 7 TLPs and 272 bytes on the link (η ≈ 6%); a 4,000-byte value takes 29 TLPs and about 4,784 bytes (η ≈ 84%). The advanced lab derives these numbers and compares them with block approaches.

Specification discipline

  • NVM Express Key Value Command Set Specification, Revision 1.4 — Store, Retrieve, Delete, Exist and List commands; Store options; KV Identify Namespace data structure and KV format descriptors; command-specific status values
  • NVM Express Base Specification, Revision 2.4 — Flush command; Volatile Write Cache feature; Identify Controller (volatile write cache presence); I/O Command Set selection

Normative As recorded in Chapter 60 (libnvme encodings): CSI 01h; Store 01h, Retrieve 02h, List 06h, Delete 10h, Exist 14h; Flush 00h; statuses 85h Invalid Value Size, 86h Invalid Key Size, 87h KV Key Does Not Exist, 88h Unrecovered Error, 89h Key Exists under SCT 0h; SIKE and SINKE.

Informative The KV specification's discussion of use cases. Optional Volatile write cache presence; multiple KV formats; List support details. Host API conventions (for example the SNIA Key Value Storage API) are outside NVMe.

Index structure and DRAM residency; latency against key count; List order; GC of the value log; actual maximum key and value lengths up to the specification maximum.

KV was published as a separate command set with the NVMe 2.0 restructuring; revision 1.4 is current with the 2026 set. Linux pass-through for non-block command sets (generic character devices, io_uring passthrough) arrived in kernel stages Version-dependent.

The specification does not define host key mapping, collision handling or value envelopes. Uncertain and to check in KV 1.4: the maximum key length and where key bytes sit in the SQE; the List data format, ordering and whether the start key is included; whether Retrieve with a small buffer truncates or fails, and which completion dword carries the value length; Store atomicity on power loss.

Never assume two tools encode keys identically, that List is a snapshot, that 87h means data loss, or that a successful Store is durable when a volatile write cache is present and enabled.

The device needs some bytes of index per key. While the index fits in DRAM, every lookup is a memory probe; once it outgrows DRAM, a lookup may need a flash read for the index page before the flash read for the value. Exist and Delete, which move no data, become slow too — which is how to tell index misses from value-read slowness Derived. Index sizes and cache policies are Implementation-dependent.

Analysis. Two explanations fit. Version 1 being returned intact (not a torn mixture) is consistent with an atomic Store, but atomicity on power loss is itself something to confirm in KV 1.4.

Labs

Beginner lab — keys and statuses on paper

Safe lab Objective: encode keys byte-exactly and decode KV completions. Prerequisites: Chapter 60. Setup: names "user:1001", "user:1001\0", "USER:1001", the 64-bit integer 1001 as an 8-byte little-endian and big-endian key; CQE DW3 values 0x010F_0400, 0x0113_0401, 0x010D_0402, 0x0001_0403.

Procedure: write each key's bytes and length; decide which are the same key; decode each DW3. Questions: which pairs collide? Which status is not an error for Exist? Why would big-endian integer keys be preferable for a sorted List? Expected reasoning: keys are bytes; status = DW3 bits 31:17.

Solution

"user:1001" = 75 73 65 72 3A 31 30 30 31 (9 bytes); with "\0" it is 10 bytes — a different key; "USER:1001" differs in four bytes. 1001 = 0x3E9: little-endian E9 03 00 00 00 00 00 00, big-endian 00 00 00 00 00 00 03 E9 — different keys for the same number; big-endian keys sort numerically if the device sorts bytewise. DW3: 0x010F → SC 87h (key absent; "no" for Exist); 0x0113 → SC 89h Key Exists; 0x010D → SC 86h Invalid Key Size; 0x0001 → success (P = 1). Status field = DW3 bits 31:17: (0x010F >> 1) = 0x87.

Extension: design a 16-byte structured key (table, row, version) and state its sort behaviour.

Intermediate lab — a collision-safe key library

Safe lab Simulation. Objective: exercise hashing, probing and the padding bug. Prerequisites: beginner lab. Setup: save as kv_key_wrapper.py.

#!/usr/bin/env python3
"""Simulation for learning: a host library that maps long names onto short
NVMe KV keys, on top of a model device.

Device model: keys are exact byte strings (length matters), statuses use the
libnvme encodings for the KV command set (SCT 0h): 86h Invalid Key Size,
87h KV Key Does Not Exist, 89h Key Exists. MAX_KEY is a parameter: read the
real limit from your namespace's KV format descriptor.
"""
import hashlib

MAX_KEY = 16
OK, INVALID_KEY_SIZE, NO_KEY, KEY_EXISTS = 0x00, 0x86, 0x87, 0x89

class Device:
    def __init__(self):
        self.pairs = {}
    def store(self, key, value, sinke=False):
        if not 1 <= len(key) <= MAX_KEY:
            return INVALID_KEY_SIZE
        if sinke and key in self.pairs:
            return KEY_EXISTS
        self.pairs[key] = value
        return OK
    def retrieve(self, key):
        if not 1 <= len(key) <= MAX_KEY:
            return INVALID_KEY_SIZE, None
        if key not in self.pairs:
            return NO_KEY, None
        return OK, self.pairs[key]

class Library:
    """Hashes names to hash_bytes-long keys; stores the full name in the
    value envelope; resolves collisions by probing with a counter."""
    def __init__(self, dev, hash_bytes=MAX_KEY, pad=False):
        self.dev, self.n, self.pad = dev, hash_bytes, pad
        self.collisions = 0
    def _key(self, name, probe):
        k = hashlib.sha256(name.encode() + bytes([probe])).digest()[: self.n]
        return k.ljust(MAX_KEY, b"\0") if self.pad else k
    @staticmethod
    def _wrap(name, data):
        nb = name.encode()
        return len(nb).to_bytes(2, "little") + nb + data
    @staticmethod
    def _unwrap(value):
        ln = int.from_bytes(value[:2], "little")
        return value[2:2 + ln].decode(), value[2 + ln:]
    def put(self, name, data):
        for probe in range(8):
            k = self._key(name, probe)
            st = self.dev.store(k, self._wrap(name, data), sinke=True)
            if st == OK:
                return OK
            if st != KEY_EXISTS:
                return st
            # key taken: ours (an update) or someone else's (a collision)?
            _, v = self.dev.retrieve(k)
            if self._unwrap(v)[0] == name:
                return self.dev.store(k, self._wrap(name, data))
            self.collisions += 1
        return KEY_EXISTS
    def get(self, name):
        for probe in range(8):
            st, v = self.dev.retrieve(self._key(name, probe))
            if st != OK:
                return st, None
            stored, data = self._unwrap(v)
            if stored == name:
                return OK, data
        return NO_KEY, None


if __name__ == "__main__":
    names = [f"https://example.test/objects/{i:06d}" for i in range(20000)]
    for hb in (16, 3, 2):
        dev = Device()
        lib = Library(dev, hash_bytes=hb)
        for nm in names:
            assert lib.put(nm, nm[-6:].encode()) == OK
        bad = sum(1 for nm in names if lib.get(nm) != (OK, nm[-6:].encode()))
        print(f"hash {hb:2d} bytes: stored={len(dev.pairs)} "
              f"collisions resolved={lib.collisions} wrong reads={bad}")
    # Two libraries, one device: one pads keys to 16 bytes, one does not.
    dev = Device()
    writer = Library(dev, hash_bytes=9, pad=False)
    reader = Library(dev, hash_bytes=9, pad=True)
    writer.put("user:1001", b'{"name":"Ada"}')
    st, _ = reader.get("user:1001")
    print(f"writer 9-byte keys, reader NUL-padded 16-byte keys: status {st:02X}h")

Procedure: run it; then add delete(name) that simply deletes the key, store three colliding names with a 2-byte hash, delete the first, and get the second. Observations: collision counts per hash size; status of the padded read. Questions: why are wrong reads zero even with a 2-byte hash? Why does naive delete break the probe chain? What does probing cost in commands? Expected reasoning: the envelope detects collisions; open addressing needs tombstones.

Solution

Output: 16-byte hash — 0 collisions; 3-byte — 19 resolved; 2-byte — 3,840 resolved; wrong reads 0 in all cases because every get compares the stored name. The padded reader gets 87h, matching Trace 3. Naive delete leaves a hole: get() stops at the first absent probe key and returns 87h for names further down the chain. Fix: tombstones (store a marker envelope) or re-insert the chain. Each collision costs an extra Store (89h) and a Retrieve on put, and an extra Retrieve on get — with a real 16-byte hash these are vanishingly rare, but the code path must exist and be tested with a weakened hash.

Extension: add a mapping version byte to the envelope and write a migration that re-keys values when the hash function changes.

Advanced lab — link cost of KV versus block

Safe lab Simulation. Objective: quantify where KV saves link bandwidth and where it does not. Prerequisites: Completion Rules. Setup: save as kv_link_model.py.

#!/usr/bin/env python3
"""Simulation for learning: PCIe link bytes per stored value, KV versus block.

Lab system parameters: MPS 256, MRRS 512, 4 KiB LBAs for the block paths.
Per-TLP overhead is an assumption (header 16 B for 64-bit addressing, plus
about 8 B framing, sequence number and LCRC): 24 B. DLLPs are ignored.
Paths:
  kv        one Store per value: SQE fetch, value fetch, CQE
  block-1   one 4 KiB WRITE per value (value padded to a block)
  block-log host packs values into a log; one 128 KiB WRITE per log segment,
            plus host compaction rewriting each value WA_HOST more times
"""
import math

MPS, MRRS, OVH, LBA = 256, 512, 24, 4096
WA_HOST = 6           # assumed host LSM compaction rewrites per value

def device_reads(nbytes):
    """Device fetches nbytes from host memory: MRd requests + CplD data."""
    if nbytes == 0:
        return 0, 0
    mrd = math.ceil(nbytes / MRRS)
    cpl = sum(math.ceil(min(MRRS, nbytes - i * MRRS) / MPS) for i in range(mrd))
    return mrd + cpl, nbytes + (mrd + cpl) * OVH

def device_writes(nbytes):
    """Device writes nbytes into host memory: MWr TLPs of at most MPS."""
    n = math.ceil(nbytes / MPS)
    return n, nbytes + n * OVH

def command(read_bytes=0, write_bytes=0):
    """One NVMe command: doorbell, SQE fetch, data, CQE, MSI-X."""
    t, b = 1, 4 + OVH                         # SQ tail doorbell MWr
    tt, bb = device_reads(64); t += tt; b += bb   # SQE fetch
    tt, bb = device_reads(read_bytes); t += tt; b += bb
    tt, bb = device_writes(write_bytes); t += tt; b += bb
    tt, bb = device_writes(16); t += tt; b += bb  # CQE
    return t + 1, b + 4 + OVH                 # MSI-X MWr

def per_value(v):
    kv = command(read_bytes=v)
    blk = command(read_bytes=math.ceil(v / LBA) * LBA)
    seg = 128 * 1024
    per_seg = seg / (v + 32)                  # values per segment (32 B index each)
    t, b = command(read_bytes=seg)
    log = (t / per_seg, b / per_seg)
    # compaction: read and write the value WA_HOST more times
    rt, rb = command(write_bytes=seg)
    log_c = (log[0] + WA_HOST * (t + rt) / per_seg,
             log[1] + WA_HOST * (b + rb) / per_seg)
    return kv, blk, log, log_c

if __name__ == "__main__":
    print(f"{'value':>7} | {'kv B':>8} {'TLPs':>5} | {'block-1 B':>9} | "
          f"{'block-log B':>11} | {'log+compact B':>13} | kv efficiency")
    for v in (16, 100, 512, 4000, 16384, 65536):
        kv, blk, log, logc = per_value(v)
        print(f"{v:7d} | {kv[1]:8.0f} {kv[0]:5d} | {blk[1]:9.0f} | "
              f"{log[1]:11.0f} | {logc[1]:13.0f} | {v / kv[1]:6.1%}")

Procedure: run it; vary OVH (20–30), MRRS (256, 1024) and WA_HOST (2, 10). Questions: for which value sizes does KV beat one-write-per-value block storage? Where does a packed log beat KV, and what does compaction change? What does the model leave out? Expected reasoning: fixed per-command costs dominate small values; host compaction multiplies link traffic; device-internal GC is invisible on the link.

Solution

Output: 16-byte value — KV 272 B (7 TLPs, η 5.9%), one block per value 4,880 B, packed log 55 B, packed log with compaction 699 B; at 4,000 B — KV 4,784 B, block 4,880 B, log 4,605 B, log+compaction 58,736 B; at 64 KiB — KV and block equal (74,960 B). KV beats per-value block writes up to about 4 KiB and always beats a log that compacts on the host; a packed log without compaction is cheaper on the link for small values. The model omits retrieval traffic, device-internal write amplification (not on the link but on the media), CPU cost of host indexing and compaction, and DLLP overhead — so link bytes alone never decide; they bound one dimension.

Extension: add Retrieve traffic for a 90:10 read/write mix and Bloom-filter hits that avoid Exist.

Senior forensic lab — stale configuration after a power event

Safe lab Paper forensic. Objective: separate host durability bugs from device bugs. Prerequisites: Trace 4; Root Cause, Ambiguity and Forensic Reporting.

Setup: after a building power event, 6 of 40 servers returned old values for keys updated in the last second before the outage. Evidence: (1) all 40 use the same Lab SSD model and firmware; (2) Identify Controller reports a volatile write cache on all; (3) the 6 affected ran library version 3.2, which batches Flush every 1 s; the other 34 ran 3.1, which Flushes after each Store; (4) Unsafe Shutdowns +1 on all 40; (5) on the 34 unaffected servers, updates acknowledged within the last second exist; (6) the vendor datasheet does not claim power-loss protection.

Procedure: evaluate both explanations against each item; state root cause, confidence and a test. Questions: which item best separates the stories? Is the device at fault? What should library 3.2 have documented? Expected reasoning: a controlled difference (library version) within one device population.

Solution

Item 3 with item 5 is the control: same drive and firmware, same power event, staleness only where Flush was deferred. With a volatile cache present and no PLP claim, losing un-flushed Stores is permitted. Root cause, high confidence: library 3.2 acknowledged updates before the batched Flush, changing the durability contract silently. The device is not at fault. Test: in the lab, cut power 200 ms after a Store under 3.1 and 3.2; expect loss only with 3.2. 3.2 should document "acknowledged ≠ durable for up to 1 s" or offer a durable-write call that waits for Flush.

Extension: design a power-cut test matrix (cache on/off, Flush policy, value sizes) that would detect a real device durability bug.

Pattern 1 — 87h for keys that "exist"
SymptomOne client cannot find data another stored.
Possible causesPadding or terminator differences; case or encoding differences; endianness of integer keys; different hash or probe rules; wrong NSID.
EvidenceKey bytes and lengths in both clients' SQEs (trace or library debug logs).
First checkKey length field in both commands.
Second checkByte-for-byte comparison of key bytes.
Disambiguating experimentStore with client A, Exist with client B, on a lab namespace.
Likely conclusion / confidenceKey-encoding mismatch — high once bytes differ.
Pattern 2 — List skips or repeats keys
SymptomIteration counts vary between runs; some keys appear twice.
Possible causesStart key included and not de-duplicated; concurrent Store/Delete during iteration; truncated last entry in the buffer parsed as a key.
EvidenceBuffer contents of consecutive Lists; concurrent writes in the same period.
First checkDoes the second List's first key equal the first List's last?
Second checkWas the buffer full at the last entry?
Disambiguating experimentIterate a quiescent namespace twice; differences then are parser bugs.
Likely conclusion / confidenceIteration parser — high if a quiescent run differs; otherwise concurrency, by design.
Pattern 3 — large values fail
SymptomStores above some size fail while the KV format allows larger values.
Possible causesValue above MDTS (128 KiB on the Lab SSD); envelope overhead pushes the value over the maximum (85h); PRP list built wrongly for multi-page buffers.
EvidenceStatus (85h versus Invalid Field or a data transfer error); exact value size including envelope.
First checkValue size versus MDTS and the KV maximum.
Second checkThe failing size boundary: page multiple, MDTS, or the KV maximum?
Disambiguating experimentBinary search on value size in the lab.
Likely conclusion / confidenceSize-limit handling in the library — high at an exact boundary.
Pattern 4 — latency rises as the namespace fills
Symptomp50 and p99 grow with key count; no errors.
Possible causesIndex outgrowing device DRAM; value-log GC; media read retries.
EvidenceExist latency (index only) versus Retrieve latency; Store rate during spikes; SMART media errors.
First checkDid Exist latency rise?
Second checkDo spikes align with Store bursts?
Disambiguating experimentMeasure latency at several fill levels with a fixed workload.
Likely conclusion / confidenceIndex residency if Exist rises — medium to high.
Pattern 5 — data older than acknowledged after power loss
SymptomRecent updates missing after an outage.
Possible causesVolatile write cache without Flush; acknowledgement before Flush in batched designs; a device durability bug.

Second checkWas Flush completed before acknowledgement?
Disambiguating experimentPower-cut test with Flush after every Store.
Likely conclusion / confidenceHost contract — high when losses vanish with Flush.

Interview

Beginner

  1. Is "abc" the same KV key as "abc\0"?

    Model answer

    No: keys are byte strings with a length; 3 bytes and 4 bytes are different keys.

  2. Why are KV keys short?

    Model answer

    They ride inside the 64-byte SQE, so no extra DMA is needed.

  3. What does 87h mean on Exist?

    Model answer

    The key is absent — an answer, not a failure.

  4. How do you store data under a 60-byte name?

    Model answer

    Hash it to a key within the limit and store the full name in the value to detect collisions.

  5. Which command makes Stores durable when a volatile cache is present?

    Model answer

    Flush.

Intermediate

  1. How do you handle a hash collision?

    Model answer

    Detect it via the name in the envelope after 89h, then probe a deterministic next key; all clients must probe identically.

  2. Why does naive Delete break probing?

    Model answer

    Lookups stop at the first missing key in the chain; tombstones are needed.

  3. How do you iterate all keys safely?

    Model answer

    Repeated List from the last key, de-duplicate the start key, handle partial buffers, and accept that concurrent changes may appear or not.

  4. Why prefer SINKE over Exist then Store?

    Model answer

    The check and store are atomic in the device; Exist then Store races.

  5. What limits a single Store's value size?

    Model answer

    The KV format's maximum value length and the controller's MDTS.

Advanced

  1. Retrieve latency doubled as the namespace filled. What do you measure next?

    Model answer

    Exist latency: if it rose too, the index left DRAM.

  2. Why is link efficiency poor for tiny values?

    Model answer

    Fixed costs (doorbell, SQE fetch, CQE, MSI-X) and per-TLP overhead dwarf a few bytes of payload.

  3. When does KV reduce total link traffic versus a host LSM?

    Model answer

    When host compaction would rewrite data several times; the device's internal GC stays off the link.

  4. A Store succeeded but the value was gone after power loss. Is the device broken?

    Model answer

    Not if a volatile cache was enabled and no Flush completed; check VWC and Flush first.

  5. Why are big-endian integer keys useful?

    Model answer

    They sort numerically under bytewise ordering, if the device's List order is bytewise.

Senior

  1. When would you choose a KV namespace over a block namespace with RocksDB?

    Model answer

    When host CPU and DRAM for indexing and compaction dominate cost, values are moderate in size, prefix scans are rare, and the KV device's latency curve fits the key count.

  2. What must a KV library document?

    Model answer

    Key encoding and mapping version, collision handling, durability point (Store or Flush), iteration semantics, size limits.

  3. How would you qualify a KV device?

    Model answer

    Limits at max and max+1, latency against fill level, List behaviour under churn, power-cut durability with and without Flush, cross-client key compatibility.

  4. How do you migrate keys when the hash changes?

    Model answer

    Version the mapping in the envelope, dual-read during migration, re-key with SINKE, delete old keys with tombstone awareness.

  5. What is the biggest operational risk of KV namespaces?

    Model answer

    Tooling: Linux and most tools do not understand them, so diagnosis depends on the library's own logging and on traces.

Quiz

  1. CQE DW3 = 0x0113_0042 on a KV namespace means…

    • Invalid Key Size
    • KV Key Does Not Exist
    • Success
    • Key Exists
    Answer and reasoning

    0x0113 >> 1 = 0x89, SCT 0h.

  2. In Trace 3, what proves a host bug?

    • The 87h status
    • Key length 16 versus 9 in the SQEs
    • No data phase
    • The 5 s delay
    Answer and reasoning

    Different key lengths for the same name are different keys.

  3. Which measurement separates index misses from value-read slowness?

    • Store latency
    • List latency
    • Exist latency
    • Flush latency
    Answer and reasoning

    Exist touches only the index.

  4. A 16-byte value Store on the lab system uses about how many link bytes in the model?

    • 272
    • 64
    • 4,880
    • 16
    Answer and reasoning

    Fixed command costs dominate: 7 TLPs, 272 bytes.

  5. Which is required for a Store to survive power loss on a drive with an enabled volatile cache?

    • SINKE
    • A completed Flush
    • An Exist
    • A List
    Answer and reasoning

    Flush makes cached data durable.

  6. Why are wrong reads zero in the 2-byte-hash simulation?

    Model answer

    Every get compares the full name stored in the envelope and probes past collisions.

  7. Give two reasons a List loop might repeat a key.

    Model answer

    The start key is included in the next call; the key was deleted and re-stored during iteration (depending on order).

  8. In the senior forensic lab, what is the control group and what does it show?

    Model answer

    The 34 servers with per-Store Flush on the same drives: no loss, so the deferred Flush is the cause.

Teach-back

  1. To a child: why did the caretaker say the coat was not there?

    Model explanation

    "The label had to match exactly. 'AM7 with a space' is a different label from 'AM7', so she could not find it, even though the coat was right there."

  2. To a junior engineer: how does a KV library store an object with a long name?

    Model explanation

    "Hash the name to a key within the device limit, put the name inside the value, Store with create-only, and if the key exists check whose it is and probe on a collision. Flush when you promise durability."

  3. To a senior engineer: what decides whether KV is a good fit?

    Model explanation

    "Host cost saved (index, compaction, CPU, DRAM) against what you lose: prefix scans, tooling, long keys and link efficiency for tiny values. Qualify the device's latency against key count, define durability with Flush explicitly, and make key encoding a shared, versioned contract."
