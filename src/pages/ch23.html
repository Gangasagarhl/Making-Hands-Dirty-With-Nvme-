The controller is the part of a Non-Volatile Memory Express (NVMe) subsystem that a host actually talks to: it owns the queues, the registers (properties), the state machine and the command processing. The namespace is the storage those commands act on. This chapter makes the difference between the two impossible to forget, and teaches the host, subsystem, controller properties and controller states that every later chapter depends on.

Why this chapter exists

"The drive reset" and "the namespace disappeared" sound like the same complaint. They are not. A controller reset tears down every queue and outstanding command on that controller but leaves the data in every namespace untouched. A namespace detach leaves the controller healthy and its queues running but makes one NSID invalid on that controller. Confusing the two produces wrong root causes, wrong fixes and, in production, wrong recovery actions that can lose data.

The controller is also where nearly every bring-up failure lives: a controller that never becomes ready, a controller that reports fatal status, a controller that will not shut down cleanly before power loss. To debug those you need a clear model of what the controller holds and what states it moves through.

Learning objectives

  • Define host, NVM subsystem, controller and namespace precisely, with the identifier and scope of each.
  • List what state belongs to a controller and what belongs to a namespace, and predict what survives each kind of reset.
  • Explain the four controller–namespace topologies (private, multiple namespaces, shared, many-to-many).
  • Explain namespace states: allocated, attached (active), inactive, invalid NSID.
  • Describe controller properties and the key Identify Controller fields (MDTS, SQES, CQES, NN, CMIC, OACS, ONCS, SUBNQN).
  • Draw the controller state machine: disabled, enabling, ready, shutdown processing, shutdown complete, fatal, and the resets that move between them.
  • Distinguish, in a trace and in Linux, a controller-level failure from a namespace-level failure and from a PCIe-level failure.

The story

Think of a bank. The vault holds everyone's money in separate numbered safe-deposit boxes. You never walk into the vault. You go to a teller window. The teller has a tray for your request slips, a tray for answers, a little sign that says "OPEN" or "CLOSED", and a list of which boxes this window is allowed to open.

The bank (the whole building) is the NVM subsystem. Each teller window is a controller. Each safe-deposit box is a namespace. You are the host. If a teller window closes for a moment and reopens (a controller reset), your requests in the tray are thrown away and you must hand them in again, but the money in the boxes does not move. If the bank removes box 3 from window 1's list (namespace detach), window 1 stays open but now says "I can't open that box". Two windows can both be allowed to open the same box (a shared namespace), which is useful, but then the two customers had better agree about who is touching it.

An operating-systems analogy for adults: the controller is like a file descriptor table plus a device driver instance — per-client state (open requests, queues, configuration) through which you reach shared objects. The namespace is like a file on disk: it exists independently of who has it open, it can be opened by several clients at once, and closing or crashing a client does not delete it.

  • Teller windows are not stateless. A controller holds a lot of configuration (features, interrupt settings, queue layout, arbitration). A reset discards much of it; the host must rebuild it.
  • A "window" can be created on demand. On fabrics with the dynamic controller model, a controller is created when a host connects, which no bank window does.
  • Some settings belong to neither window nor box. Some features and logs are scoped to the NVM subsystem, an endurance group or a domain, and firmware is a subsystem-wide object. The two-level picture is a simplification.
  • The file-descriptor analogy hides attachment. Any process can open any file it has permission for; a controller can only reach namespaces explicitly attached to it.

Beginner explanation

When your computer uses an NVMe SSD, four things are involved:

  • The host is your computer: the processor, memory and operating system that send commands.
  • The NVM subsystem is the SSD as a whole, seen as an NVMe object.
  • The controller is the "front desk" inside the SSD. It has registers the host can read and write, it reads the commands the host queued, it does the work and it writes back the answers. A controller has its own on/off switch, its own "I'm ready" light and its own queues.
  • The namespace is a slice of the SSD's storage, numbered 1, 2, 3… A command such as Read says "namespace 1, blocks 1000 to 1007". Your operating system shows each namespace as a disk, like /dev/nvme0n1.

The simplest SSD has one controller and one namespace, so people use "the drive" for both. Bigger SSDs can have several controllers (so two servers can connect at once) and many namespaces (so one SSD can be carved into separate disks). Once that happens, the difference matters a lot: you reset a controller, you format a namespace.

Engineering explanation

The host

In NVMe the host is the entity that creates queues, submits commands and consumes completions. On PCIe the host is implicit: whoever owns the root complex and maps BAR0 is the host. On fabrics the host is explicit and identified: it presents a Host Identifier (Host ID) and a host NVMe Qualified Name (host NQN) when it connects, and the subsystem uses them for access control and reservations.

Even on PCIe the Host ID matters for one feature: reservations, which coordinate access to shared namespaces between hosts. A host sets its Host Identifier with Set Features before registering reservations. Uncertain Confirm the Host Identifier feature identifier and its 64-bit/128-bit variants in the Base Specification's Features clause.

The NVM subsystem

Recall from NVMe 2.x Architecture: an NVM subsystem contains one or more controllers, zero or more namespaces, one or more ports, the media, and the interface between controllers and media. It is named by its subsystem NQN (SUBNQN), reported in Identify Controller. Things that are subsystem-scoped include the set of namespaces and NSIDs, firmware images (and, depending on the device, their activation), sanitize operations and NVM Subsystem Reset.

The controller

A controller is the interface between a host and an NVM subsystem. It is identified by a Controller Identifier (CNTLID), unique within the subsystem and reported in Identify Controller. Everything a host does goes through exactly one controller at a time.

Four topologies

The Identify Controller field Controller Multi-Path I/O and Namespace Sharing Capabilities (CMIC) says whether the subsystem may have more than one port, more than one controller, or is associated with an SR-IOV virtual function. The Identify Namespace field Namespace Multi-path I/O and Namespace Sharing Capabilities (NMIC) says whether a namespace may be attached to more than one controller.

Identify Controller's NN field (Number of Namespaces) is the maximum valid NSID, not the number of namespaces that exist. Static and dynamic controllers

On PCIe, controllers are static: a PCIe function is a controller, it exists from power-on, and its CNTLID is fixed. On fabrics, subsystems may use the static controller model (a host connects to a specific CNTLID) or the dynamic controller model (the host asks for "any controller" and the subsystem allocates one on Connect). Discovery controllers are typically dynamic. This is why fabrics bring-up logs show CNTLIDs that change between connections.

Controller state

The controller's lifecycle is driven by the host writing CC and the controller reporting through CSTS:

Disabled

CC.EN = 0 and CSTS.RDY = 0. The host may program AQA, ASQ, ACQ and CC fields. No commands are processed; doorbells must not be written.

Enabling and ready

When the host sets CC.EN to 1, the controller reads the admin queue configuration and prepares to process commands. When it is ready, it sets CSTS.RDY to 1. The host waits up to CAP.TO (in 500 ms units) for that. Only then may the host ring the admin doorbell. From NVMe 2.0, a controller may support two ready modes: ready with media and ready independent of media, selected through CC.CRIME, with separate timeouts reported in the Controller Ready Timeouts (CRTO) property. Version-dependent

Controller reset

Writing CC.EN from 1 to 0 performs a Controller Reset: the controller stops processing, deletes all I/O queues, aborts outstanding commands without posting completions, resets most properties, and clears CSTS.RDY to 0 when done (again bounded by CAP.TO). This is one form of Controller Level Reset. Others are an NVM Subsystem Reset, a PCIe Conventional Reset (hot, warm or cold), and a PCIe Function Level Reset (FLR). See NVMe Reset and PCIe Reset.

Shutdown

Before removing power, the host writes CC.SHN = 01b (normal shutdown) or 10b (abrupt shutdown). The controller flushes volatile state to media, reporting CSTS.SHST = 01b while processing and 10b when complete. The host should wait for 10b; the RTD3E field estimates how long that may take. Skipping this step is how "unsafe shutdowns" (counted in the SMART / Health log) happen.

Fatal

If the controller hits an error it cannot report through a completion (internal firmware fault, for example), it sets CSTS.CFS = 1. It may stop processing commands entirely. The host's only recovery is a reset. Linux reports this as "controller is down; will reset" with the CSTS value.

Processing paused

CSTS.PP indicates the controller has temporarily paused command processing, for example while activating new firmware without a reset. The host should expect delayed completions, not treat it as a failure.

Admin versus I/O addressing of commands

  • Controller-addressed: most admin commands (Create I/O SQ, Identify Controller, Set Features for controller-scoped features, Get Log Page for controller-scoped logs) leave NSID unused or 0.
  • Namespace-addressed: every I/O command and some admin commands (Identify Namespace, Format NVM, Namespace Attachment, namespace-scoped Get Log Page or features) carry an NSID.
  • Broadcast: NSID FFFFFFFFh applies to all namespaces where a command permits it (e.g. a subsystem-wide SMART / Health log, or Format NVM of all namespaces when supported).

The teaching ladder for the controller

A bank teller window: trays for requests and answers, an OPEN/CLOSED sign, and a list of boxes it may open.

An NVMe controller is the interface between a host and an NVM subsystem: it owns properties, an admin queue, I/O queues, doorbells, features and a ready/fatal/shutdown state, and accesses attached namespaces.

On a PCIe SSD the controller is a PCIe function whose BAR0 exposes registers and doorbells, plus DMA engines and firmware that process commands and map namespaces to media.

The Base Specification defines the controller's properties (CAP, VS, CC, CSTS, AQA, ASQ, ACQ…), initialisation, Controller Level Reset, shutdown, Identify Controller and controller types; the PCIe Transport Specification maps them to BAR0.

Host↔controller interaction: property writes (CC), property reads (CSTS polling during enable/reset/shutdown), doorbells, then SQE fetches and CQE posts. Namespaces appear only as NSIDs inside commands.

In a trace: CC writes and repeated CSTS reads at bring-up; after enable, admin doorbells and fetches; a controller failure shows as doorbells with no fetches, or CSTS reads returning CFS = 1; a namespace failure shows as error CQEs for one NSID.

Localise: all namespaces failing on one controller → controller or PCIe; one namespace failing everywhere → namespace (format, media, protection); one namespace on one controller → attachment or ANA path state.

The sixteen questions, answered for "controller vs namespace"

1. What is it?
The controller is the command-processing interface; the namespace is the addressed storage.
2. Why was the separation created?
To allow many hosts and paths (controllers) to reach the same storage, and one interface to reach many independent storage units.
3. What problem does it solve?
Multi-host access, multipath, virtualisation and storage partitioning, without changing the command model.
4. What existed before?
In SCSI, the analogous split is target/port vs logical unit (LUN); in AHCI/SATA a port was effectively one device with one storage unit.
5. Why is the design better?
Clean scoping: queues and state per controller, data and format per namespace, explicit attachment between them.
6. Who creates them?
Controllers: the device (or the subsystem on Connect). Namespaces: the factory, or the host with Namespace Management.
7. Who consumes them?
Hosts use controllers to issue commands that consume namespaces.
8. Where do they live?
Controller: PCIe function, BAR0 registers, firmware state. Namespace: media plus FTL metadata.
9. What memory/registers are involved?
CAP, CC, CSTS, AQA, ASQ, ACQ, doorbells; Identify Controller and Identify Namespace; attachment lists.
10. What happens before?
PCIe enumeration (controller as PCIe function); namespace creation and attachment.
11. What happens after?
Queue creation, namespace discovery, block device creation.
12. What happens if it is wrong?
Reset the wrong object, lose outstanding I/O, detach a namespace in use, or write to a shared namespace from two hosts without reservations.
13. What does the analyzer show?
Controller activity as register and doorbell traffic; namespaces only as NSID fields inside fetched SQEs.
14. What does Linux show?
/dev/nvme0 and /sys/class/nvme/nvme0/state for the controller; /dev/nvme0n1 and its sysfs for the namespace.
15. What would a validation engineer test?
Reset survival (namespaces intact, queues gone), attach/detach with I/O in flight, NN boundary NSIDs, shared namespace behaviour, shutdown timing against RTD3E, CFS recovery.
16. What would a senior engineer suspect?
Scope errors: per-controller failure blamed on media, or per-namespace attachment changes blamed on the controller; host caching stale namespace lists after attachment changes.

The table explains reset behaviour without memorisation: anything in the "volatile" rows is lost by a Controller Level Reset; anything in the "non-volatile" rows is not. A multi-controller device duplicates the volatile rows per controller and shares the non-volatile rows.

On most controllers CSTS.RDY is set by firmware after it has initialised queues and, in "ready with media" mode, loaded enough of the mapping table to serve commands. That is why ready time can vary from milliseconds to many seconds (for example after an unsafe shutdown, when the map must be rebuilt) and why CAP.TO exists.

Specification view

Primary source: NVM Express Base Specification, Revision 2.4 — NVM Subsystem Entities; Controller Architecture; Controller Properties; Controller Initialization; Resets; Shutdown; Identify Controller and Identify Namespace data structures. Memory mapping of properties: NVMe over PCIe Transport Specification, Revision 1.4 — Controller Registers. Normative: field definitions and "shall" statements on initialisation, reset and shutdown. Informative: the theory-of-operation descriptions and example topologies.

  • CNTLID is unique within the NVM subsystem; NSIDs are unique within the NVM subsystem.
  • CC.EN 1→0 causes a Controller Reset; the host waits for CSTS.RDY = 0 before re-enabling. CAP.TO gives the worst-case time, in 500 ms units, for CSTS.RDY to change after CC.EN changes (in the default ready mode).
  • CC.SHN requests normal (01b) or abrupt (10b) shutdown; CSTS.SHST reports processing (01b) and complete (10b).
  • CSTS.CFS indicates a controller fatal condition.
  • Identify Controller (CNS 01h) and Identify Namespace (CNS 00h) report controller and namespace properties respectively; NN is the maximum valid NSID.
  • On PCIe, Controller Level Resets include Controller Reset, NVM Subsystem Reset, Conventional Reset and Function Level Reset.
  • Because I/O queues are controller state, every I/O path must be rebuilt after any Controller Level Reset; because namespaces are subsystem state, their data and format survive it.
  • A symptom that affects all NSIDs on one controller but none through another controller of the same subsystem points away from media.
  • Actual ready time (anything up to CAP.TO), shutdown time (RTD3E is an estimate), and how long a controller reset takes.
  • Which conditions cause CSTS.CFS.
  • How many controllers and namespaces a subsystem supports (NN, and namespace management capacity).
  • Which features are saveable.
  • Controller ready modes (CC.CRIME, CRTO) appeared in NVMe 2.0.
  • Administrative and discovery controller types as named types, and CNTRLTYPE in Identify Controller, are 1.4/2.x-era; older devices report 0 (not reported).
  • NVM Subsystem Shutdown (a subsystem-wide shutdown property) appeared in 2.0; check whether the device supports it via CAP.
  • Exported NVM Subsystems (2.4) add controllers and namespaces that live inside virtual subsystems; see 2026 NVMe 2.4 Updates.
  • The specification does not define a named state machine diagram for the controller; the states above are a teaching model built from CC/CSTS rules.
  • It does not specify how fast a controller must become ready, only the maximum it may report.
  • It does not say how a host should react to CFS beyond resetting; recovery policy is host software.

Check in the specification: exactly which properties are and are not reset by each kind of Controller Level Reset; the status returned for I/O to an inactive NSID; the Host Identifier feature format.

  • Never assume a controller reset preserves I/O queues or outstanding commands.
  • Never assume namespace changes are visible to a host without it re-reading Identify (watch for Namespace Attribute Changed asynchronous events).
  • Never assume a shared namespace is safe to write from two hosts without coordination (reservations or a cluster filesystem).
  • Never treat NN as the number of existing namespaces.

Walking the reasoning

  1. Is it PCIe? The CSTS read in row 6 completed successfully with real data. If the link or the function were gone, the root complex would typically synthesise all-ones (0xFFFF_FFFF) for the read, and AER or a link-down event would usually be logged. Here the device answered, so the PCIe path is alive.
  2. Is it a namespace? Commands on two different queues stopped, and no CQE with an error status ever arrived. A namespace problem produces error CQEs, not silence.
  3. Is it the controller? CSTS = 0x0000_0003 decodes to RDY = 1 and CFS = 1. The controller itself declared a fatal condition. The first abnormal event is the missing fetch after row 4, about 20 µs into the trace, roughly 30 seconds before the host noticed.
  4. What next? The reset in row 8 will recover service if the fault was transient. Root cause needs device-side evidence: the Telemetry Controller-Initiated log, the Error Information log after recovery, vendor logs. The trace's job was to prove where the failure lives and when it started.

Three CSTS read results tell three different stories: 0x0000_0003 (controller alive enough to report its own fatal state), 0xFFFF_FFFF (no valid answer — the function or link is gone, or the read failed), and 0x0000_0001 with commands still stuck (controller claims to be fine — look at the host: interrupts, CQ head doorbells, IOMMU faults). Linux prints CSTS in its "controller is down; will reset" message precisely so you can tell these apart.

Code / pseudocode

A small simulator of the controller's CC/CSTS behaviour, so you can explore enable, reset, shutdown and fatal transitions without hardware. Executable with Python 3, standard library only. Times are simulated, not real.

"""Simulated NVMe controller CC/CSTS state machine (teaching model, not the spec's text)."""

class Controller:
    def __init__(self, cap_to=20, ready_ms=200, reset_ms=5):
        self.cap_to = cap_to          # CAP.TO in 500 ms units (20 -> 10 s)
        self.ready_ms, self.reset_ms = ready_ms, reset_ms
        self.cc = 0
        self.rdy = self.cfs = 0
        self.shst = 0
        self.io_queues = set()
        self.outstanding = []
        self.t = 0                    # simulated time in ms
        self._pending = None          # (time, action)

    def write_cc(self, value):
        old_en, new_en = self.cc & 1, value & 1
        shn = (value >> 14) & 3
        self.cc = value
        if old_en == 0 and new_en == 1:
            self._pending = (self.t + self.ready_ms, "ready")
        elif old_en == 1 and new_en == 0:
            self.io_queues.clear(); self.outstanding.clear()  # aborted, no CQEs
            self.cfs = 0
            self._pending = (self.t + self.reset_ms, "disabled")
        if shn in (1, 2) and new_en == 1:
            self.shst = 1
            self._pending = (self.t + 50, "shutdown_done")

    def read_csts(self):
        if self._pending and self.t >= self._pending[0]:
            what = self._pending[1]; self._pending = None
            if what == "ready": self.rdy = 1
            elif what == "disabled": self.rdy = 0; self.shst = 0
            elif what == "shutdown_done": self.shst = 2
        return self.rdy | (self.cfs << 1) | (self.shst << 2)

    def fatal(self):
        self.cfs = 1

def wait_for(ctrl, mask, want, label):
    limit = ctrl.cap_to * 500
    while ctrl.t <= limit:
        if ctrl.read_csts() & mask == want:
            print(f"  {label}: after {ctrl.t} ms, CSTS=0x{ctrl.read_csts():08x}")
            return True
        ctrl.t += 10
    print(f"  {label}: TIMEOUT after CAP.TO ({limit} ms)")
    return False

if __name__ == "__main__":
    c = Controller()
    print("Enable:")
    c.write_cc(0x0046_0061); wait_for(c, 1, 1, "RDY=1")
    c.io_queues.update({1, 2}); c.outstanding.append(("SQ1", 0x41))
    print("Fatal error, host reads CSTS:")
    c.fatal(); print(f"  CSTS=0x{c.read_csts():08x}  (RDY=1, CFS=1)")
    print("Controller reset (CC.EN=0):")
    c.t = 0; c.write_cc(0x0046_0060); wait_for(c, 1, 0, "RDY=0")
    print(f"  I/O queues after reset: {sorted(c.io_queues)}; outstanding: {c.outstanding}")
    print("Re-enable, then normal shutdown (CC.SHN=01b):")
    c.t = 0; c.write_cc(0x0046_0061); wait_for(c, 1, 1, "RDY=1")
    c.t = 0; c.write_cc(0x0046_4061); wait_for(c, 0xC, 0x8, "SHST=10b")

Expected output: ready after about 200 simulated ms; CSTS 0x00000003 after the fatal error; RDY = 0 shortly after the reset with no I/O queues or outstanding commands left; ready again; shutdown complete with SHST = 10b (CSTS bits 3:2), CSTS = 0x00000009.

Worked example

Scenario. A two-node cluster shares a dual-port enterprise SSD. Node A reaches it through controller CNTLID 1, node B through CNTLID 2. Namespace 1 is private to A, namespace 2 is private to B, and namespace 3 is shared (NMIC indicates sharing) for a cluster filesystem. At 14:02 node A logs "controller is down; will reset: CSTS=0x3" and recovers after 2 seconds. Node B logs nothing. Questions: what was affected, what was not, and what should be checked?

  1. Scope of the event. CSTS = 0x3 means controller 1 reported fatal status. A reset of controller 1 deleted A's I/O queues and aborted A's outstanding commands; Linux retried them after recovery.
  2. Unaffected: controller 2 and all I/O from node B, including B's I/O to shared namespace 3. Namespace data is subsystem state and was not touched by A's controller reset.
  3. Subtle risk: A's in-flight writes to namespace 3 were aborted and retried. If the cluster filesystem relies on write ordering between nodes, the retries arrive later than originally intended. That is a host/cluster correctness question, not an NVMe one, but the NVMe event triggered it.
  4. Reservations: a controller reset does not release reservations held for a host on a namespace (reservations are tied to the host, not the controller's queues). Confirm the exact reservation persistence rules for each reset type in the Base Specification's Reservations clause.
  5. Checks: on node A read the Error Information log and SMART / Health log (critical warnings), and the telemetry log if supported; on both nodes check firmware revision equality (FR in Identify Controller should match across controllers of one subsystem); check whether the event correlates with a firmware activation (CSTS.PP) or a thermal event.

Also from Identify Controller on this drive: MDTS = 5 and CAP.MPSMIN = 0 → maximum transfer 128 KiB; NN = 32 → NSIDs 1–32 are valid, of which 1, 2 and 3 are allocated. Node A's nvme list-ns shows 1 and 3; node B's shows 2 and 3; both --all listings show 1, 2, 3.

Debugging connection

Use the controller/namespace split as the first branch of every NVMe investigation:

During triage, read CSTS through MMIO (or nvme show-regs), never through an admin command: if the controller is fatal, admin commands will also hang and you will learn nothing except another timeout.

Senior engineer insight

Seniors think of the controller as a session and the namespace as data. Sessions are cheap to tear down and rebuild; data is precious. Every recovery action is classified that way: "this resets a session" (safe, costs outstanding I/O) versus "this changes data or its accessibility" (format, sanitize, detach, delete — requires explicit approval).

They also watch for the scope of firmware actions: firmware images and activation are subsystem-level, so activating new firmware through one controller can pause or reset every controller in the subsystem. In a dual-host cluster that turns a "single-node maintenance" into an outage on the other node. Checking the Firmware Commit action and the device's activation behaviour (with or without reset, CSTS.PP) is part of change review.

And they never trust the host's namespace view after a topology change. Asynchronous Event Requests carry "namespace attribute changed" notices; a host that missed one (because its AERs were not re-armed after a reset, for example) keeps using stale NSIDs. When namespace errors appear after maintenance, verify that the host re-read the active namespace list.

Lab — Controller or namespace? Scope triage with real and simulated evidence

Objective

Skills

  • Decoding CSTS values.

Safety

Safe lab All commands are read-only. Do not trigger resets on a system disk. An optional extension marked Caution lab resets a controller and must only be done on a scratch, unmounted test drive.

Hardware required

Software required

Input

  6. CSTS = 0x0000_0003.

For each report: scope (PCIe, controller, namespace, attachment, host), reasoning, first check.

  1. Classify reports (a)–(f).
  2. Which of your system's settings would survive a controller reset?
  3. Why is reading CSTS via MMIO preferable to an admin command during triage?

Challenge

Extend the simulator with two controllers sharing one namespace object, and show that a reset of one controller leaves the other's queues and the namespace untouched.

Hints

Make the namespace a separate object held by a Subsystem; give each Controller its own queues and a reference to the shared namespace. Reset should only touch self.

Solution

(a) PCIe/function: all-ones read plus completion timeout means MMIO is not answered; check link status and AER (PCIe Errors). (b) Namespace: LBA Out of Range on one namespace; check NSZE of nvme0n2 versus the LBAs used — likely a partition table or tool assuming a larger namespace (or 512-byte vs 4 KiB LBA confusion). (c) Host side: controller claims ready and not fatal, but interrupts stopped; check MSI-X configuration, IOMMU faults, and whether CQEs are being posted (trace) — classic interrupt-path failure (Interrupt Architecture). (d) Attachment: NSID 3 is attached to controller of nvme1 only; check list-ns --all and the namespace's controller list. (e) Controller, but compliant: 9 s < CAP.TO 0x14 × 500 ms = 10 s; long ready after power cut is expected map rebuilding; product concern at most. (f) Controller fatal: reset and collect telemetry.

(2) Namespace data, format, attachment, saved features; not I/O queues, unsaved features or outstanding commands. (3) Admin commands need a working controller; MMIO reads of CSTS work even when command processing has stopped, and their result (real value vs all-ones) itself discriminates controller vs PCIe failure.

What a senior engineer notices

  • Whether RTD3E is large enough that the OS's shutdown timeout could cut the controller off before SHST = 10b.
  • Whether max_hw_sectors_kb is smaller than MDTS implies (the driver may cap it further).
  • Whether the device reports CMIC multi-controller on a client drive (some do, for SR-IOV or future use).

Failure variants

  • list-ns --all returns an error: the controller does not support Namespace Management; only active namespaces are visible.
  • state shows connecting: a fabrics controller; the PCIe-specific parts of this lab do not apply.

Solutions
  1. Controller: CC.MPS, I/O SQ 3, Interrupt Coalescing, CAP.TO, outstanding command. Namespace: LBA format, NSZE, reservation holder (per namespace, for a host), NMIC.
  2. See the figure: host on controller 1 reads NS1 and NS3; host on controller 2 reads NS2 and NS3.
  3. 0x1: ready. 0x5: ready, SHST = 01b (shutdown processing). 0x9: ready, SHST = 10b (shutdown complete). 0x3: ready, CFS = 1. 0x21: ready, PP = 1 (processing paused). 0xFFFF_FFFF: not a valid CSTS; the read failed (device or link gone).
  4. 26 × 4 KiB = 256 KiB; with MPSMIN = 1 (8 KiB minimum page) 26 × 8 KiB = 512 KiB.
  5. The queues those completions would go to are being deleted as part of the reset, so there is nowhere to post them. The host must treat all outstanding commands on that controller as not completed and retry or fail them after re-initialisation.

Quiz

  1. Which identifier is unique within an NVM subsystem and names a controller?

    • NSID
    • CNTLID
    • QID
    • CID
    Answer and reasoning

    CNTLID. NSID names namespaces; QID names queues within a controller; CID names commands within an SQ.

  2. What survives a controller reset (CC.EN 1→0)?

    • I/O submission queues
    • Outstanding commands
    • Namespace data and attachment
    • CSTS.RDY = 1
    Answer and reasoning

    Namespaces are subsystem state. Queues and outstanding commands are controller state and are discarded; RDY goes to 0.

  3. Identify Controller reports NN = 32. What does that mean?

    • Valid NSIDs are 1–32; some may be inactive
    • There are 32 namespaces
    • 32 controllers exist
    • The namespace has 32 LBA formats
    Answer and reasoning

    NN is the maximum valid NSID, not a count of existing namespaces.

  4. A CSTS read returns 0x0000_0003. Interpret it.

    Model answer

    RDY = 1 and CFS = 1: the controller is reporting a fatal condition. The PCIe path is working (the read returned real data). The host must reset the controller.

  5. Which field tells you whether a namespace may be attached to more than one controller?

    • CMIC
    • OACS
    • MDTS
    • NMIC
    Answer and reasoning

    NMIC in Identify Namespace. CMIC (Identify Controller) is the subsystem/controller-level capability.

  6. What is the correct host action before cutting power to an NVMe SSD?

    Model answer

    Write CC.SHN = 01b (normal shutdown) and wait until CSTS.SHST = 10b (or until a timeout informed by RTD3E). This lets the controller persist volatile state and avoids an unsafe shutdown.

  7. On PCIe, which is not a Controller Level Reset?

    • Function Level Reset
    • CC.EN 1→0
    • Namespace detach
    • NVM Subsystem Reset
    Answer and reasoning

    Namespace detach changes attachment, not controller state.

  8. All I/O to nvme0n1 and nvme0n2 times out, but I/O to the same shared namespace through nvme1 works. Where do you look first?

    Model answer

    Controller nvme0 (or its PCIe path/host interrupt path): the namespace itself is healthy because another controller can use it. Read nvme0's CSTS via MMIO and check its PCIe status and interrupts.

  9. What does MDTS = 0 mean?

    Answer

    No limit on data transfer size is reported by the controller (the host may still impose its own).

Interview questions

  1. Beginner: What is the difference between an NVMe controller and a namespace?

    Model answer

    The controller is the interface that processes commands: registers, queues, state. The namespace is storage addressed by those commands via an NSID. One controller can access many namespaces; a namespace can be attached to many controllers.

  2. Beginner: What do CSTS.RDY and CSTS.CFS mean?

    Model answer

    RDY = 1: the controller is ready to process commands after enable. CFS = 1: the controller has hit a fatal condition and needs a reset.

  3. Intermediate: Walk through a controller reset and re-initialisation.

    Model answer

    Write CC.EN = 0; poll CSTS until RDY = 0 (bounded by CAP.TO); program AQA/ASQ/ACQ; write CC with CSS, MPS, AMS, IOSQES/IOCQES and EN = 1; poll until RDY = 1; then Identify, Set Features Number of Queues, Create I/O CQs and SQs, re-arm Asynchronous Event Requests, and resubmit or fail aborted I/O.

  4. Advanced: How do you tell a controller failure from a PCIe failure using one register read?

    Model answer

    Read CSTS via MMIO. All-ones indicates the read was not completed by the device (link/function failure). A real value with CFS = 1 indicates a controller fatal condition. A real value with RDY = 1 and no CFS indicates the controller believes it is healthy; look at the host path.

  5. Senior: A firmware activation on a dual-port drive caused I/O errors on the passive node. Explain and propose mitigations.

    Model answer

    Firmware is subsystem-scoped; activation (depending on the commit action and device capability) may require or cause a reset of all controllers, or pause processing (CSTS.PP) on all of them. The passive node saw its controller reset or paused. Mitigations: choose a commit action that activates on next reset and schedule a coordinated reset; verify the device supports activation without reset and its maximum time; ensure host timeouts exceed the documented activation time; quiesce I/O on both nodes; test the procedure in validation with I/O in flight.

  6. Senior: Design a validation test for "namespace data survives every Controller Level Reset".

    Model answer

    Write known patterns with Flush (or FUA) across namespaces, record checksums; for each reset type (CC.EN, NSSR if supported, FLR, hot reset, link disable) with and without I/O in flight, re-initialise and verify checksums of flushed data; verify that unflushed data obeys the device's volatile write cache rules; verify namespace attachment, format and identifiers are unchanged; record ready time against CAP.TO. Repeat with power-loss injection for completeness.

Chapter summary

  • Host issues commands; the NVM subsystem contains controllers, namespaces and ports; the controller is the command-processing interface; the namespace is the storage.
  • Controller state (properties, queues, doorbells, outstanding commands, most features) is volatile and per controller; namespace state (data, format, size, sharing, identifiers) is persistent and subsystem-wide.
  • Topologies range from 1:1 to many-to-many; CMIC and NMIC describe sharing; attachment controls which controller sees which namespace; NN is the maximum NSID, not a count.
  • Controller states: disabled, enabling, ready, shutdown processing/complete, fatal, paused — driven by CC, reported by CSTS, bounded by CAP.TO.
  • Triage by scope: all NSIDs on one controller → controller or PCIe; one NSID everywhere → namespace; one NSID on one controller → attachment or path.

Do not move on until you can:

  • explain controller vs namespace with the comparison table from memory
  • predict what survives a controller reset and why
  • draw the controller state diagram with CC and CSTS fields on the transitions
  • decode CSTS values including CFS, SHST and PP
  • compute maximum transfer size from MDTS and CAP.MPSMIN
  • triage a failure by scope using the debugging tree
  • read the abnormal trace and find the first abnormal event as an absence
