The central skill: the first abnormal event

Every lab asks for the first abnormal event. It is the earliest observation that departs from what a correct system would do, and it is rarely the loudest row. The ladder below is worth climbing before you start.

A row of dominoes fell over. The last domino is the one everyone points at. The interesting one is the first that tipped, and sometimes it is a domino that was missing from the row.

The first abnormal event is the earliest point in time where observed behaviour diverges from the behaviour the protocol and the configuration predict. Everything after it may be consequence.

In hardware, a divergence starts in one agent: a register value, a DMA engine, a queue pointer, a receiver that mis-sampled a symbol. The analyzer only sees it when it reaches the wire.

"Abnormal" is defined against the specifications (what must and must not happen) and against configuration (what this system was set up to do). Something legal but unexpected (a completion that is late but within limits) is a different category from something illegal.

On the link, divergence appears as a wrong field value, a wrong order, a missing response, an unexpected retry, or an error message.

In a trace it may be a row, or the absence of an expected row. Absences need the capture's scope to be known: no filter, no gap, no buffer wrap.

A senior engineer finds the last known-good point, then the first deviation after it, then asks what could have produced that deviation, and keeps the rest of the trace as tests for the hypotheses.

A procedure you can follow every time

  1. Scope the evidence. Which link? Which direction(s)? Which filters, triggers and time window? (See analyzer limitations.)
  2. Find the skeleton. Mark doorbells, SQE fetches, data, CQEs, interrupts, head doorbells. Most traces are 95% healthy skeleton.
  3. Find the last known-good point. The last command that completed normally before the symptom.
  4. Find the first deviation after it. A field, an order, a time, or an absence.
  5. Write hypotheses that would each produce that deviation, and the evidence each predicts.
  6. Test against the rest of the trace and outside evidence (registers, logs, configuration).
  7. State the root cause with mechanism, owner and confidence; propose the fix and the regression test.

First abnormal event

None in the captured window. Doorbell to SQE arrival: 1.4 µs. SQE arrival to first data: about 69.8 µs (media). Data transfer: about 1.6 µs. CQE to interrupt: 0.15 µs. Root cause

No defect. Expected behaviour: QD1 random-read latency is dominated by NAND read time; the 80 µs at the application includes host software overhead. Datasheet IOPS figures typically come from high queue depth, where many reads overlap. Confidence: high for this capture.

Corrective action

Re-baseline expectations: measure QD1 completion-latency percentiles (not averages) with a tool such as fio, and compare like with like against the datasheet's stated test conditions. See Performance Engineering.

Regression test

A latency baseline test: QD1 4 KiB random read, fixed preconditioning, report p50/p99/p99.9, fail if the device-side p99 (from a capture or host tracepoints) exceeds the agreed threshold.

Senior-engineer insight

"Nothing is wrong" is a finding, and it needs the same evidence as any other finding. The skill is decomposing latency into owners: link, controller, media, host. Once you can show where the 80 µs goes, the conversation changes from blame to engineering.

Follow-up challenge

Trace Lab 2 — Commands never start: a doorbell written to the wrong register

Beginner Skills: doorbell address arithmetic, recognising absence, reading asynchronous events.

Scenario

A team is bringing up a user-space test driver on a dedicated lab machine. Admin commands work: the I/O queues were created successfully. But the first I/O Read never completes and the tool times out.

System configuration

PCIe generation
PCIe 4.0
Link width
×4
NVMe device
Lab SSD, CAP.DSTRD = 0
Other
Kernel driver unbound; test driver owns the controller; one Asynchronous Event Request outstanding (CID 0x0FFF on the admin queue)

Expected operation

The tool writes a Read SQE into SQ1 slot 0 and rings the SQ1 tail doorbell with value 1.

Background

Doorbell registers start at BAR0 + 1000h. With stride 4 << CAP.DSTRD bytes, SQ y's tail doorbell is at 1000h + (2y) × stride and CQ y's head doorbell at 1000h + (2y + 1) × stride. Tail and head doorbells for the same queue pair are interleaved.

Row 1 is the first abnormal event. Offset 0x1004 is doorbell index 1: CQ 0's head doorbell. The host told the controller "I have consumed admin CQ entries up to slot 0", which moves the admin CQ head backwards (from 3 to 1) and is not a valid value.

Hypotheses

  • H1: doorbell offset computed without the ×2 interleave (1000h + y × 4 instead of 1000h + 2y × 4).
  • H2: the tool used the correct formula with a wrong DSTRD (it would then write a larger offset, not a smaller one).
  • H3: the controller ignores valid doorbells (predicts a write to 0x1008 in the trace with no fetch).

Evidence

Only one doorbell write occurs, at 0x1004: H3 is ruled out (no write to 0x1008 exists). A wrong DSTRD would produce 0x1010 or larger for SQ1: H2 is ruled out. The tool's source computes 0x1000 + qid * 4: H1 confirmed. Row 3 is consistent: the controller reported an invalid doorbell write through the outstanding Asynchronous Event Request.

Root cause

Doorbell address formula in the test driver omitted the SQ/CQ interleave. Owner: host software (test driver). Confidence: high.

Corrective action

Use 1000h + (2y + isCQ) × (4 << CAP.DSTRD). Add an assertion that SQ tail doorbells are even indices and CQ head doorbells odd.

Regression test

Unit test the doorbell helper for queues 0–3 with DSTRD 0 and 1 against hand-computed offsets; integration test that the first I/O on each queue produces an SQE fetch from that queue's base within a fixed time.

Senior-engineer insight

When a command "never starts", the absence of the SQE fetch moves suspicion to the host side of the doorbell. Asynchronous event reporting of doorbell errors is helpful when it happens, but whether and how a controller detects invalid doorbell writes, and whether an Asynchronous Event Request is outstanding to carry the report, varies. Do not use the absence of such an event as proof the doorbells were correct. Check the event's exact encoding in the Base specification's Asynchronous Event Request section rather than trusting the decode in this table.

Trace Lab 3 — SQE fetch answered with Unsupported Request

Intermediate Skills: completion status, IOVA lifetime, linking link-level failure to controller state.

Scenario

During a driver unload/reload stress test, the host log shows an IOMMU fault for 0000:01:00.0 and, 30 seconds later, an I/O timeout followed by a controller reset. The analyzer was triggered on the first non-successful completion.

System configuration

PCIe generation
PCIe 4.0
Link width
×4
NVMe device
Lab SSD
Other
IOMMU in translated mode; on this platform, DMA requests blocked by the IOMMU are completed with Unsupported Request (platform-dependent behaviour)

Expected operation

The stress test unloads the driver (which should delete the I/O queues and disable the controller) and reloads it (which re-creates them with new memory).

Background

The controller keeps each I/O SQ's base address from the Create I/O SQ command until the queue is deleted or the controller is reset. If host software frees and unmaps the queue memory while the controller still believes the queue exists, any later fetch from that queue targets an IOVA with no mapping. What the Root Complex does with such a request is platform-specific: return UR or CA, or drop it.

Initial state

The analyzer's pre-trigger buffer shows the unload path's last admin commands: Delete I/O SQ for queues 2–8 completed; no Delete I/O SQ for queue 1 appears in the buffer. CC.EN is still 1.

The analyzer triggered on row 3, but row 3 is a correct response to a request for an unmapped address. Row 2 is a correct fetch from the queue the controller was told exists. The first abnormal event is row 1: a doorbell for SQ1 while the host was tearing SQ1 down, after its memory had been unmapped (inferred from the IOMMU fault and the missing Delete I/O SQ for queue 1).

Hypotheses

  • H1: teardown race: the unload path freed SQ1's memory before deleting SQ1 (or disabling the controller), and a submitter thread still rang SQ1.
  • H2: the controller used a corrupted SQ base address (predicts an address that does not match the Create I/O SQ command's PRP1).
  • H3: the IOMMU mapping was torn down by an unrelated component.

Evidence

Row 2's address, 0x1_2340_0300, is exactly SQ1 base + slot 12 × 64: H2 is ruled out. The pre-trigger buffer shows Delete I/O SQ for queues 2–8 but not 1, and the IOMMU fault names the same IOVA. The driver's unload path (code review) frees the queue memory for queue 1 before issuing its Delete I/O SQ, and a submission path checks a "queue live" flag without locking. H1 is supported; H3 has no evidence. Rows 5–6: the controller treated the failed fetch as fatal (CSTS = 0x3: RDY = 1, CFS = 1) and the host's timeout handler reset it (CC write with EN = 0). How a controller reacts to a failed SQE fetch is implementation-dependent. Note also who logs what: the Root Complex, as completer, detected the Unsupported Request and the IOMMU logged the fault; the SSD, as requester, merely received a UR completion, which typically sets a received-abort indication in its Status register rather than producing its own AER report (confirm the exact bits in the PCI Express Base Specification's error-logging rules).

Root cause

Driver teardown ordering bug: SQ1's memory was unmapped while SQ1 was still live in the controller and still reachable by a submitter. Owner: host driver. Confidence: high (address match, missing delete, code inspection).

Corrective action

Quiesce submitters, delete I/O SQs (or disable the controller and wait for CSTS.RDY = 0), and only then unmap and free queue memory. Make the "queue live" check and the doorbell write atomic with respect to teardown.

Regression test

Unload/reload loop under concurrent I/O with an IOMMU in strict mode; pass criteria: no IOMMU faults, no UR completions on the link, no CFS. Add a fault-injection hook that delays the delete path to widen the race window.

Senior-engineer insight

Analyzers trigger on what is easy to detect (an error status), which is usually downstream of the cause. Treat the trigger point as the end of the story and read backwards. And remember the platform dependency: on another machine the same bug would show up as a completion timeout instead of a UR, which is Trace Lab 7.

Identical PRP2 in two concurrent SQEs supports H1; code review finds the list pool's free-list pop is not protected against two CPUs.

Root cause

Host driver concurrency bug: PRP list page double-allocation. CID 0x21's pages 2–3 were written into CID 0x22's buffer, and CID 0x21's real pages B000 and C000 were never written, so they kept stale data. Owner: host driver. Confidence: high.

Corrective action

Protect the pool (per-CPU pools or a lock), and add a debug check that no two outstanding commands share a PRP list page.

Regression test

Multi-threaded random-read test with buffers filled with a known pattern and verified after each read; in a validation build, assert list-page uniqueness at submission. On the analyzer side, a rule that flags identical PRP2 values among outstanding commands.

Senior-engineer insight

Data corruption investigations often end on the host side, because the controller is a very literal machine: it writes where the PRPs say. Before blaming the SSD, prove the PRPs it fetched were the PRPs you intended. The analyzer's payload view of the list fetch is the single most important piece of evidence here.

Follow-up challenge

Writing your own trace labs

Building traces is the fastest way to learn to read them. A good synthetic trace lab follows these rules:

  • Start from a mechanism, not a symptom. Decide the root cause first, then derive every row the mechanism would produce, then decide what the reporter would have noticed.
  • Keep it consistent. Addresses must match queue bases and slots; tags must pair; Byte Counts must add up; times must be ordered and plausible. Run it through Programming Labs 6, 7 and 9.
  • Put the first abnormal event where it really is, which is usually not where the analyzer would trigger.
  • Include at least one red herring (a legal reordering, a batched doorbell) so solvers practise not over-reacting.
  • Label provenance. Everything you write is synthetic; say so on the trace.
  • State what the trace cannot show. Internal controller state, host memory contents, events off the probed link.

Teams that keep a library of "golden" healthy traces for their own platforms debug faster: the first abnormal event is easiest to see by diffing against a known-good trace of the same operation. See Synthetic vs Real Traces, Diffing and Golden Traces.

Quiz

  1. An analyzer triggers on a completion with UR status for the SSD's SQE fetch. Where is the first abnormal event most likely to be?

    • At the trigger row
    • In the completion's header fields
    • Earlier: in why the SSD fetched from that address (queue lifetime, doorbell)
    • After the trigger, in the recovery
    Answer and reasoning

    The UR is a correct response to a bad address. The cause lies in why the address was invalid or why the fetch happened (Trace Lab 3).

  2. A Nak DLLP carries sequence number 0x11F. Which TLPs are replayed?

    • 0x11F only
    • All unacknowledged TLPs from 0x120 onward
    • 0x11F and earlier
    • None; Nak only reports an error
    Answer and reasoning

    The sequence number in a Nak acknowledges everything up to and including it; the transmitter replays all TLPs after it that are still in its replay buffer.

  3. A CQE is written but no MSI-X follows. Which is the least likely cause?

    • Vector masked
    • CQ created with interrupts disabled
    • Interrupt coalescing
    • The CQE's phase tag was wrong
    Answer and reasoning

    The phase tag affects whether the host recognises the entry, not whether the device sends an interrupt.

  4. The analyzer reports "posted data credits = 0" on a capture that started after link training. How much should you trust the absolute value?

    • Little: the analyzer did not see the initial credit advertisement
    • Fully: credits are fields in every TLP
    • Fully, if the analyzer is calibrated
    • Not at all: credits are not visible on the link
    Answer and reasoning

    Credits are reconstructed from InitFC and UpdateFC DLLPs; without the initial values, absolute counts are guesses (Trace Lab 9).

  5. A configuration write that completes successfully can still be a first abnormal event. Give the example from this page and explain.

    Model answer

    Trace Lab 6: the CfgWr raising the SSD's MPS to 512 bytes. It is a legal TLP with SC status, but it breaks a system rule (MPS consistency on the path), so it is abnormal against configuration, not against packet formation.

  6. Why can a trace show a successful write CQE together with data reads that have no completions, and what does that combination prove?

    Model answer

    The SSD cannot complete a write successfully without its data, so the completions must have existed. The combination proves the capture is incomplete (filter, gap), not that completions were lost (Trace Lab 11).

  7. In Trace Lab 7, why is the injected 1.5-second stall not the first abnormal event?

    Model answer

    NVMe does not bound how long a controller may take; a long-running command is legal (the host's timeout is a host policy). The first rule broken is the host releasing memory for a command it no longer owned.

  8. In Trace Lab 8, the analyzer saw no corrupted TLPs but the Root Port sent Naks. Reconcile the two.

    Model answer

    The analyzer observes the signal at its probe point. Corruption added on the channel between the probe and the Root Port's receiver (including by the interposer itself) is invisible to it.

  9. State the seven-step procedure from the top of this page in one sentence each.

    Model answer

    Scope the evidence; find the healthy skeleton; find the last known-good point; find the first deviation after it; write hypotheses that would produce it; test them against the rest of the trace and outside evidence; state root cause with owner and confidence and propose fix and regression test.

Interview questions

  1. Intermediate. You have a trace of a command that never completed. Walk me through your first five minutes.

    Model answer

    Confirm capture scope (link, direction, filters, time window). Find the command's SQE fetch by queue address and CID. Check the doorbell that preceded it. Look for its data movement and CQE. Identify the first missing stage, then check the configuration that stage depends on (interrupt vector, queue state, controller status) before blaming the device.

  2. Advanced. How do you tell a device bug from a host bug using only a PCIe trace?

    Model answer

    Check whether each agent did what its inputs told it. If the device acted exactly on what it fetched (PRPs, SQEs, doorbells), the inputs are suspect, which points at the host. If the device deviated from its inputs or the protocol, it is the device. Where inputs live off the link (host memory, internal state), say what extra evidence is needed.

  3. Senior. A customer sends you a capture and a conclusion. How do you review it?

    Model answer

    Review the evidence before the conclusion: settings, filters, probe point, buffer mode, analyzer and software versions, link state at capture. Run cross-layer consistency checks. Then verify that the claimed first abnormal event is first, that alternatives were considered, and that confidence matches evidence.

  4. Senior. When is "no defect found" the right answer?

    Model answer

    When the evidence covers the failure window, every stage behaves within specification and configuration, and the symptom is explained by something else (expectations, host overhead, topology). It must be written with the same evidence standard as a defect, including what was not covered.
