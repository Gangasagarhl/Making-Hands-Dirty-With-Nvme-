This module treats NVMe over TCP (NVMe/TCP) as a set of state machines on one byte stream. It covers how a receiver frames Protocol Data Units (PDUs) and when it must give up, how Ready to Transfer (R2T) pacing limits write throughput, why one TCP connection per queue creates head-of-line blocking, how digests split errors into "this command" and "this connection", and what changes once Transport Layer Security (TLS) hides every byte. The traces are new: interleaved reads, R2T starvation, a header digest failure with reconnect, and an encrypted capture you have to reason about without seeing a single PDU.

Orientation

Chapter 66 decoded every PDU type byte by byte, walked through reads, writes, digests and TLS 1.3, and built a stream parser. Chapter 65 placed NVMe/TCP inside NVMe over Fabrics (NVMe-oF): capsules, Connect, discovery and associations. This module assumes both. It adds the receiver's view (what a correct implementation must check, in what order), the performance view (what bounds a command's latency and a connection's throughput), and the operations view (how to debug when captures are incomplete or encrypted).

Read NVMe/TCP and NVMe over Fabrics first. Also useful: I/O Commands and Latency. Related modules: NVMe Boot (fabric boot and NBFT), Performance Engineering.

Kid story

Imagine a long paper tape coming out of a ticker machine, with no gaps between messages. Every message starts with a small stamp: "message kind, how long the stamp is, where the words begin, total length." The reader cuts the tape after exactly that many letters, then reads the next stamp.

If one stamp gets smudged, the reader can no longer find where the next message starts — everything after is gibberish. So the reader stops the tape and asks for a fresh roll. But if only the words inside a message are smudged, the reader can still find the next stamp and just asks for that one message again.

When the writer wants to send a big parcel of words, the reader first says "I have space for this much, send it now." The writer waits for that note before sending. And because there is only one tape, a very long message holds up all the short ones behind it.

The central concept on the ladder: framing and pacing on one stream

Messages on a tape are cut by their stamps; big parcels wait for a "send now" note; one long message delays the rest.

Each queue is a TCP stream of self-describing PDUs. Reads are pushed, writes are pulled by R2T. Header errors kill the stream; data errors kill one command.

Socket workers on both ends; CPU (or NIC offload) for CRC32C and TLS; target buffer pools for R2T; NIC segmentation and receive offloads.

TCP Transport 1.3 (PDUs, ICReq/ICResp, digests, R2T rules, TermReq, TLS use); Base 2.4 (capsules, transport error status, Connect); RFC 8446 (TLS 1.3); TCP RFCs.

ICReq/ICResp → Connect → Capsules. Read: CapsuleCmd → C2HData… → CapsuleResp (or SUCCESS). Write: CapsuleCmd → (R2T → H2CData…)… → CapsuleResp.

Wireshark NVMe/TCP dissector with reassembly: per-PDU type, CCCID, DATAO/DATAL, R2T fields; TCP retransmissions and window; with TLS, only record sizes and times.

Find the first PDU or gap that deviates; decide layer (TCP, framing, R2T pacing, target backing, NVMe status); then check whether other queues show it.

The sixteen questions, answered for the header digest

Sixteen questions
1–3. What, why, problemA CRC32C over a PDU's header (common + specific) that protects framing against corruption TCP's 16-bit checksum and offloads may miss.
4–5. Before, betteriSCSI also had optional header digests; without them, a corrupted length silently misframes the stream. With them, the receiver detects and terminates cleanly.
6–8. Creator, consumer, locationSender computes, receiver checks; 4 bytes right after the header, not counted in HLEN.
9. Memory/registersSocket buffers; NIC offload engines if CRC32C offload exists.
10–11. Before, afterNegotiated in ICReq/ICResp; checked on every PDU thereafter.
12. If wrongTermReq with a header-digest FES, close; all commands on that queue are retried after reconnect.
13–14. Analyzer, LinuxWireshark can validate digests when enabled; Linux logs a header digest error and reconnects the controller.
15. ValidationInject corruption in each header field of each PDU type; verify TermReq, close, and recovery without data corruption.
16. Senior suspicionA NIC or middlebox that corrupts at segment boundaries; memory errors on one host.

Consistent with Chapter 66: PDU types 00h–07h and 09h; HLEN 128 (ICReq/ICResp), 24 (TermReq, CapsuleResp, data PDUs, R2T), 72 (CapsuleCmd); digests are CRC32C; ports 4420 and 8009; TLS 1.3 with PSKs. TLS record overhead from RFC 8446: 5-byte record header, 1-byte inner content type and a 16-byte tag for the AEAD ciphers used with TLS 1.3, at most 214 plaintext bytes per record.

This module names FES values (Invalid PDU Header Field, PDU Sequence Error, Header Digest Error, Data Transfer Out of Range, Data Transfer Limit Exceeded, Unsupported Parameter) but does not give their numbers; read them from the TermReq figures. It does not state the exact conditions for using the SUCCESS flag (they involve SQ flow control). The specification does not say how large C2HData PDUs should be, how a target should schedule R2Ts across commands, or how many connections a host should open.

Never assume: that PDU boundaries align with segments; that a CapsuleResp always follows C2HData; that MAXR2T > 0; that a capture with TLS can be decoded later; that TCP retransmission hides corruption (it hides loss, not corruption the checksum missed).

Ordering: within a connection, PDUs arrive in send order. Across commands, the target may interleave C2HData PDUs of different CCCIDs; within one command, DATAO increases. Why it is ambiguous. The PDUs are invisible. Record sizes allow inference: each record adds 22 bytes (5 header + 1 content type + 16 tag), so a 50-byte record holds 28 bytes — a CapsuleResp with header digest; 98 − 22 = 76 bytes is a CapsuleCmd with header digest; 16,406 − 22 = 16,384 bytes is a full record of C2HData bytes. These are inferences: records and PDUs are independent, just as segments and PDUs are, and one record could hold parts of two PDUs. The 8.4 ms delay has at least three explanations: (a) the target's backing read was slow; (b) the target's TLS send path (kTLS, or a stalled offload) delayed the data; (c) the host's capture point is above kTLS and the delay is in the host's receive path. The capture cannot tell them apart. Resolve with target-side NVMe tracing (backing I/O latency at the same time), TLS key logging in the lab to decrypt, or host nvme-tcp tracepoints. Lesson for production: plan observability before enabling TLS — per-command latency on both ends, exported as metrics.

Labs

Safe lab Labs are simulation and paper analysis. Live captures on lab hosts are optional and read-only.

Beginner lab — length arithmetic

Objective: compute PDO and PLEN. Prerequisites: the length table. Setup: paper. Procedure: compute PDO and PLEN for (i) CapsuleCmd with 4 KiB in-capsule data, both digests, CPDA 0; (ii) C2HData 4 KiB, both digests, HPDA 7 (32-byte alignment); (iii) R2T with header digest. Questions: which PDUs never carry a data digest? Why does HLEN not include digests?

Solution

(i) PDO 76, PLEN 76 + 4096 + 4 = 4176. (ii) header + HDGST = 28; next 32-byte boundary 32 → PDO 32, PLEN 32 + 4096 + 4 = 4132. (iii) PLEN 28, PDO 0. CapsuleResp, R2T, ICReq/ICResp and TermReq carry no data digest. HLEN is fixed per type so a receiver can validate it before knowing negotiated options.

Extension: compute the frames for (ii) at MTU 1500.

Intermediate lab — a PDU stream checker

Objective: implement the receiver checks for writes. Prerequisites: Chapter 66 stream parser. Setup: save as pdu_check.py; run it. It walks a merged view of both directions of one connection.

#!/usr/bin/env python3
"""pdu_check.py - frame an NVMe/TCP byte stream into PDUs and check the
write data rules (R2T -> H2CData) for one connection, host-side view.

Common header (8 bytes): type, flags, HLEN, PDO, PLEN (le32).
Flag bits as in Linux nvme-tcp.h: 01h HDGSTF, 02h DDGSTF, 04h LAST_PDU,
08h SUCCESS. PDU-specific fields from the TCP Transport chapter.
Digests are CRC32C. Teaching tool: confirm every rule in TCP Transport 1.3.
"""
import struct

HLEN = {0: 128, 1: 128, 2: 24, 3: 24, 4: 72, 5: 24, 6: 24, 7: 24, 9: 24}
NAME = {0: "ICReq", 1: "ICResp", 2: "H2CTermReq", 3: "C2HTermReq", 4: "CapsuleCmd",
        5: "CapsuleResp", 6: "H2CData", 7: "C2HData", 9: "R2T"}

def crc32c(data, crc=0xFFFFFFFF):
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ (0x82F63B78 if crc & 1 else 0)
    return crc ^ 0xFFFFFFFF

def pdu(ptype, psh=b"", data=b"", flags=0, hdgst=True):
    hlen = HLEN[ptype]
    flags |= 0x01 if hdgst else 0
    pdo = (hlen + (4 if hdgst else 0)) if data else 0
    plen = hlen + (4 if hdgst else 0) + len(data)
    ch = struct.pack("<BBBBI", ptype, flags, hlen, pdo, plen)
    hdr = ch + psh.ljust(hlen - 8, b"\0")
    return hdr + (struct.pack("<I", crc32c(hdr)) if hdgst else b"") + data

def r2t(cccid, ttag, off, ln):
    return pdu(9, struct.pack("<HHII", cccid, ttag, off, ln))

def h2c(cccid, ttag, off, data, last):
    return pdu(6, struct.pack("<HHII", cccid, ttag, off, len(data)), data, 0x04 if last else 0)

def check(stream, write_len, maxr2t=0, maxh2cdata=65536):
    """Walk a mixed stream; return list of findings (first is first abnormal)."""
    out, pos, open_r2t = [], 0, {}
    while pos + 8 <= len(stream):
        t, flags, hlen, pdo, plen = struct.unpack_from("<BBBBI", stream, pos)
        name = NAME.get(t, "type %02Xh" % t)
        if t not in HLEN or hlen != HLEN[t]:
            return out + ["@%d %s: invalid header field (HLEN %d) -> TermReq" % (pos, name, hlen)]
        if flags & 1:
            want = struct.unpack_from("<I", stream, pos + hlen)[0]
            if crc32c(stream[pos:pos + hlen]) != want:
                return out + ["@%d %s: header digest error -> H2CTermReq, close" % (pos, name)]
        cccid, ttag, off, ln = struct.unpack_from("<HHII", stream, pos + 8)
        if t == 9:
            if off + ln > write_len:
                return out + ["@%d R2T beyond command length -> fatal" % pos]
            open_r2t[ttag] = [off, off + ln]
            if len(open_r2t) > maxr2t + 1:
                return out + ["@%d R2T: %d outstanding > MAXR2T+1 -> fatal" % (pos, len(open_r2t))]
            out.append("@%d R2T ttag %d [%d, %d)" % (pos, ttag, off, off + ln))
        elif t == 6:
            if ttag not in open_r2t:
                return out + ["@%d H2CData for unknown TTAG %d -> fatal" % (pos, ttag)]
            exp, end = open_r2t[ttag]
            if off != exp or off + ln > end or ln > maxh2cdata:
                return out + ["@%d H2CData [%d, %d) outside expected [%d, %d) or > MAXH2CDATA"
                              % (pos, off, off + ln, exp, end)]
            open_r2t[ttag][0] = off + ln
            if flags & 0x04:
                status = "complete" if off + ln == end else "LAST_PDU early!"
                out.append("@%d H2CData ttag %d LAST_PDU, R2T %s" % (pos, ttag, status))
                del open_r2t[ttag]
        pos += plen
    return out + ["end of stream, %d R2T(s) still open" % len(open_r2t)]

            + h2c(0x21, 1, 32768, D[32768:65536], True)
            + r2t(0x21, 2, 65536, 65536) + h2c(0x21, 2, 65536, D[65536:], True))
    print("good stream:"); [print("  ", s) for s in check(good, len(D))]
    bad = bytearray(good)
    bad[len(r2t(0x21, 1, 0, 65536)) + 13] ^= 0x10     # flip a bit in DATAO of PDU 2
    print("corrupted header:"); [print("  ", s) for s in check(bytes(bad), len(D))]
    eager = r2t(0x21, 1, 0, 65536) + r2t(0x21, 2, 65536, 65536)
    print("two R2Ts, MAXR2T=0:"); [print("  ", s) for s in check(eager, len(D))]

Solution

(1) The checker reports "LAST_PDU early!": the R2T range is not covered, so the controller cannot complete the transfer — a fatal sequence error in a real target. (2) DDGST covers data only; on mismatch, report a per-command failure and continue framing. (3) Keep a dictionary CCCID → next expected DATAO; reject gaps, overlaps and data beyond the command length. Fatal: anything that breaks framing or references unknown state; per-command: data digest.

Advanced lab — what bounds latency and throughput

Objective: quantify R2T pacing, head-of-line blocking and TLS overhead. Prerequisites: Latency. Setup: save as tcp_model.py; run it.

#!/usr/bin/env python3
"""tcp_model.py - first-order NVMe/TCP timing model (teaching numbers).

1. Large write: time vs MAXR2T for R2T-paced data.
2. Head-of-line blocking: a 4 KiB read queued behind a 1 MiB read on the
   same connection, for different C2HData PDU sizes, plus one TCP loss.
3. TLS 1.3 record overhead (RFC 8446: 5-byte header, 16-byte AEAD tag,
   1-byte inner content type, at most 16 KiB plaintext per record).
"""
LINK_GBPS = 25.0
RTT_US = 60.0            # host <-> target round trip incl. stack processing
R2T_PREP_US = 20.0       # target time to allocate a buffer and send an R2T
BYTES_PER_US = LINK_GBPS * 1000 / 8   # 3125 bytes per microsecond

def write_time(total, r2tl, maxr2t):
    """CapsuleCmd, then R2T rounds; up to maxr2t+1 R2Ts outstanding."""
    n = -(-total // r2tl)
    window = maxr2t + 1
    rounds = -(-n // window)
    # each round: R2T(s) reach host, data flows; pipelining hides RTT only inside a round
    return RTT_US / 2 + rounds * (R2T_PREP_US + RTT_US) + total / BYTES_PER_US

def hol_wait(big, pdu, loss=False, rto_us=0.0):
    """Extra wait of a small read whose data the target interleaves at PDU granularity."""
    wait = min(big, pdu) / BYTES_PER_US          # finish the PDU in flight
    if loss:
        wait += rto_us                           # TCP delivers in order: all streams wait
    return wait

if __name__ == "__main__":
    print("1 MiB write, R2TL 128 KiB, %.0f Gb/s, RTT %.0f us" % (LINK_GBPS, RTT_US))
    for m in (0, 1, 3, 7):
        t = write_time(1 << 20, 128 << 10, m)
        print("  MAXR2T %d (%d outstanding): %6.1f us  -> %5.2f GB/s per command"
              % (m, m + 1, t, (1 << 20) / t / 1000))
    print("4 KiB read behind a 1 MiB read on the same connection")
    for p in (8 << 10, 32 << 10, 128 << 10, 1 << 20):
        print("  C2HData PDU %7d B: extra wait %6.1f us" % (p, hol_wait(1 << 20, p)))
    print("  ... plus one lost segment, fast retransmit after ~3 RTT: %6.1f us"
          % hol_wait(1 << 20, 32 << 10, True, 3 * RTT_US))
    print("  ... plus one lost tail segment, RTO 200 ms:            %8.1f us"
          % hol_wait(1 << 20, 32 << 10, True, 200_000))
    rec = 16384
    over = 5 + 16 + 1
    print("TLS 1.3: %d B overhead per %d B record = %.3f%%; 1 MiB = %d records"
          % (over, rec, 100 * over / rec, (1 << 20) // rec))

  C2HData PDU   32768 B: extra wait   10.5 us
  C2HData PDU  131072 B: extra wait   41.9 us
  C2HData PDU 1048576 B: extra wait  335.5 us
  ... plus one lost segment, fast retransmit after ~3 RTT:  190.5 us
  ... plus one lost tail segment, RTO 200 ms:            200010.5 us
TLS 1.3: 22 B overhead per 16384 B record = 0.134%; 1 MiB = 64 records

Procedure: (1) change RTT to 500 µs (cross-site) and compare MAXR2T values; (2) find R2TL that gives 2 GB/s with MAXR2T 0; (3) explain why throughput per connection can exceed per-command throughput. Questions: what does the tail-loss line mean for p99.99 latency? Is TLS's byte overhead the real cost?

Solution

(1) With long RTT, MAXR2T 0 collapses (≈ 8 RTTs per 1 MiB); pipelining matters more. (2) With one R2T for the whole MiB (R2TL 1 MiB) the model gives 30 + (20 + 60) + 335.5 ≈ 446 µs, about 2.35 GB/s — at the cost of 1 MiB target buffer per write. (3) Many commands run concurrently on one connection, each with its own R2Ts, so the link fills even when each command is paced. A single tail loss stalls every command on that connection for an RTO — the p99.99 driver in many deployments; tail loss probes and more connections reduce the blast radius. TLS byte overhead is 0.13%; its real cost is CPU per record unless offloaded.

Extension: add data digest CPU cost (bytes / CRC throughput per core) and find where CPU, not the link, becomes the limit.

Senior forensic lab — periodic reconnects on 3% of hosts

Objective: localise corruption from digest evidence. Setup (synthetic evidence): 3% of hosts log header digest errors and reconnects every 2–6 hours; data digest errors are never logged; all affected hosts use NIC firmware F2 with TSO enabled; no affected host with TSO disabled; target-side captures (wire mirror) of the bad PDUs show the corrupted header bytes always start exactly at a TCP segment boundary; switch error counters are clean.

Procedure: list hypotheses (switch, cable, host memory, NIC offload, target bug); test each against the evidence; choose a decisive experiment.

Solution

Clean switch counters and correlation with NIC firmware and TSO point at the sending NIC's segmentation offload. Corruption only at segment boundaries fits a segmentation bug. If ordinary data bytes at boundaries were hit, data digest errors would appear; none do, so the corruption is specific to PDU headers that happen to start at a segment boundary. That is consistent with a NIC that inspects or rewrites bytes it believes are a header at the start of each segment (for example, an offload that partly parses upper-layer protocols). Decisive experiment: on one affected host, toggle TSO off, then F2 → F1, each for 48 h, with digest error counts. Fix: firmware update or disable the offload; keep digests on — they turned silent corruption into a recoverable event. Confidence: medium-high before the experiment.

Extension: estimate how many commands per day were retried because of these reconnects.

Interview

Beginner

  1. Why does NVMe/TCP need PDUs?

    Model answer

    TCP is a byte stream without message boundaries; PDUs carry their own lengths.

  2. Which PDUs make a read?

    Model answer

    CapsuleCmd, one or more C2HData, CapsuleResp (unless SUCCESS is used).

  3. What is R2T for?

    Model answer

    The controller requests write data when it has buffer space.

  4. What ports are used?

    Model answer

    4420 for I/O controllers, 8009 for discovery (both registered; targets may choose others).

  5. What does a data digest protect?

    Model answer

    The PDU's data bytes, with CRC32C.

Intermediate

  1. Why is a header digest error fatal but a data digest error not?

    Model answer

    A bad header means framing is lost; a bad data digest leaves framing intact.

  2. Compute PLEN of a 32 KiB C2HData with both digests, HPDA 0.

    Model answer

    28 + 32,768 + 4 = 32,800.

  3. What does MAXR2T 0 mean?

    Model answer

    One outstanding R2T per command.

  4. Why can a host capture show 64 KiB frames?

    Model answer

    Captured above TSO/GRO.

  5. What happens to other commands after a TermReq?

    Model answer

    They fail at transport level and are retried after reconnect.

Advanced

  1. Model write time per command.

    Model answer

    Capsule half-RTT + rounds × (R2T preparation + RTT) + bytes/bandwidth, with rounds = ceil(ranges / (MAXR2T+1)).

  2. How does a target reduce head-of-line blocking?

    Model answer

    Interleave C2HData of different commands at moderate PDU sizes; hosts use more connections.

  3. How do you debug inside TLS?

    Model answer

    Record sizes and timing, endpoint tracing and metrics, lab key logging.

  4. Validate digest handling.

    Model answer

    Inject corruption in each field and data region; verify fatal vs per-command outcomes and clean recovery.

  5. When is in-capsule data better?

    Model answer

    Small writes: saves an R2T round trip, costs target buffer per capsule.

Senior

  1. Digests on or off in production?

    Model answer

    On, unless TLS already provides integrity and CPU cost is proven prohibitive; measure.

  2. How many connections per host?

    Model answer

    Enough to spread CPU and limit loss blast radius; bounded by target resources.

  3. Plan TLS rollout.

    Model answer

    Key provisioning, tlshd health, offload capacity, observability first, staged rollout with rollback.

  4. Cross-site NVMe/TCP: risks?

    Model answer

    RTT amplifies R2T pacing and loss recovery; tune MAXR2T, R2TL, in-capsule size and timeouts.

  5. How do you report a "network is slow" complaint?

    Model answer

    Split latency into host, network (RTT/retransmits), target transport (R2T gaps) and backing device, with evidence for each.

Quiz

  1. HLEN of an R2T PDU is:

    • 8
    • 24
    • 72
    • 128

  2. FLAGS 07h on C2HData means:

    • Header digest only
    • SUCCESS
    • Both digests and LAST_PDU
    • Error

    01h + 02h + 04h.

  3. A data digest mismatch leads to:

    • That command failing with a transport error status
    • TermReq and close
    • TCP retransmission
    • Nothing
    Answer and reasoning

    Framing is intact.

  4. Which shows target buffer pressure?

    • Retransmissions
    • Bad digests
    • Large frames
    • Long CapsuleCmd→R2T or R2T→R2T gaps
    Answer and reasoning

    The target delays R2Ts until it has space.

  5. TLS 1.3 adds per record:

    • 5 bytes
    • 22 bytes
    • 64 bytes
    • 16 bytes
    Answer and reasoning

    5 header + 1 content type + 16 tag.

  6. A single lost tail segment affects:

    • One command
    • All connections of the host
    • All commands on that connection
    • Only writes
    Answer and reasoning

    In-order delivery per connection.

    Model answer

    The connection terminated; all outstanding commands on it failed.

  8. In Trace D, what does a 50-byte TLS record most likely contain?

    Model answer

    A 28-byte CapsuleResp with header digest (50 − 22).

Teach-back

To a child — model

"Messages on one long tape, each with a stamp saying how long it is. A smudged stamp means start a new tape; smudged words mean ask for that message again. Big parcels wait for a 'send now' note, and long messages slow down the short ones behind them."

To a junior engineer — model

"Each queue is a TCP connection carrying PDUs: 8-byte common header, fixed HLEN, optional digests and padding. Reads come back as C2HData plus CapsuleResp; writes use R2T and H2CData unless small enough for in-capsule. Header digest errors kill the connection; data digest errors fail one command."

To a senior engineer — model

"NVMe/TCP latency is host stack + RTT × R2T rounds + target buffering + backing device, and the tail is TCP loss on a shared connection. Tune MAXR2T, R2TL, in-capsule size and connection count; keep digests on; plan observability before TLS, because captures stop working."
