This module builds on Chapter 59 — ZNS, which taught zone geometry, the state machine, the write-pointer rule, Zone Append, Zone Management Send and Receive, the open and active limits and the ZNS status codes. Here the subject is the host system built on zones: garbage collection, resource accounting over days, recovery after resets, the cost of implicit closes, shrinking zone capacity, and the device asking for help through zone attributes and events.

Orientation

Chapter 59 ended where most real ZNS bugs begin. Its traces showed single commands failing for clear reasons: a reordered WRITE (BCh), a fourth active zone (BDh). In production, failures come from host software that keeps a model of the device — a write-pointer cache, an active-zone count, a capacity table — and lets that model drift from the device's truth. This module follows that drift: through a host garbage-collection (GC) cycle, through an open-resource thrash that costs throughput without any error, through a controller reset that leaves the host's write pointers wrong, and through zone capacity that changes under the host's feet.

From Chapter 59: ZS encodings, ZSA and filter values, the descriptor layout, statuses B8h–BFh, MOR/MAR as 0's-based values. From Module 41: what a controller reset does to outstanding commands. From Module 43: asynchronous events and RAE. From Namespaces: CSI and command-set-specific Identify.

Kid story

A class keeps its drawings in notebooks. The rule: you always draw on the next empty page, and you can never rub out one page — to reuse a notebook you must wipe the whole thing. When most drawings in an old notebook are no longer wanted, a helper copies the good ones into a fresh notebook and wipes the old one.

The teacher has a list of where each child's next empty page is. One day the lights go out in the middle of drawing time. When they come back on, the teacher's list says Mia's next page is page 12 — but Mia had already finished page 12 before the lights went out. If the teacher sends her to page 12, the rule is broken. The teacher must look in every open notebook again before anyone draws.

And there are only so many desks: each notebook still being filled takes a desk, even if nobody is drawing in it right now.

Analogy boundary

What it represents. Notebooks are zones; "next empty page" is the write pointer; wiping a whole notebook is Reset Zone; the helper is host GC; the teacher's list is the host's write-pointer cache; looking in every notebook is a zone report; desks are active resources (MAR+1), and the children drawing right now are open resources (MOR+1).

What it hides. A notebook's usable page count can shrink when it is wiped (zone capacity may change on reset). The device can also ask the class to close a notebook early (Finish Zone Recommended). Copying drawings costs time the class could have spent drawing — write amplification moves from the device to the host but does not vanish.

Where it misleads. The lights going out is a controller reset, not power loss; with a volatile write cache, power loss can also lose recently completed writes, which is a different and worse problem. And unlike the teacher, the host may have many writes in flight to a zone with Zone Append, so "the next page" is the device's decision, not the host's.

Mechanism

The mechanism followed here is a host GC cycle on namespace 2 of the Lab SSD (synthetic example for teaching: 4 KiB LBAs, ZSZE = 0x1_0000, ZCAP = 0xD800 as in Chapter 59; MOR = 11 and MAR = 13, so 12 open and 14 active zones).

  1. Trigger. Who: host GC. What: the count of Empty zones falls below a threshold. Where: host free-zone list. Evidence: host metrics only.
  2. Choose a victim. Who: host. What: among Full zones, pick the lowest live fraction. Where: host live-data map; optionally confirmed with Zone Management Receive filtered to Full (filter 5h). Evidence: a 7Ah SQE with ZRASF = 5h.
  3. Reserve a destination. Who: host. What: pick an open GC zone, counting it against the active budget. Evidence: none until the first write.
  4. Copy. Who: host. What: Read live extents of the victim, Zone Append them to the GC zone, record returned LBAs. Where: I/O queues. Evidence: reads to the victim's range; appends with CDW10–11 = GC zone's ZSLBA; CQE DW0–DW1 with new LBAs.
  5. Commit metadata. Who: host. What: durably update the mapping from the old to the new LBAs (often with a Flush first). Evidence: writes to the host's metadata zone, Flush.
  6. Reset. Who: host. What: Zone Management Send ZSA 4h on the victim. Where: device zone state. Evidence: 79h SQE, CQE success; a report now shows ZS = 1h, WP = ZSLBA and possibly a new ZCAP.
  7. Return. Who: host. What: put the victim on the free list with the ZCAP from the report. Evidence: host state.

GC cost and capacity formulas

WAhost = 1 / (1 − u) , usable fraction = ZCAP / ZSZE

WAhost
host write amplification: blocks written to the device per block of new data, in steady state with greedy GC
u
live fraction of the victim zone when it is collected (0 to 1)
ZCAP
zone capacity in blocks, from the zone descriptor
ZSZE
zone size in blocks, from the LBA Format Extension

Worked example: with victims at u = 0.25, WA = 1.33 — every 3 blocks of new data cost 1 extra block of copying. At u = 0.75, WA = 4. Separating short-lived from long-lived data drives victims' u toward 0, which is the entire point of host placement. For the Lab SSD, ZCAP/ZSZE = 0xD800/0x1_0000 = 55,296/65,536 = 84.4%: LBA space is not capacity, and a host that sizes its allocator by ZSZE will try to write 10,240 non-writable blocks per zone.

What a reset does to zones

As Chapter 59 notes, zones in the opened states become Closed across a controller reset or power cycle. Writes that were in flight when the reset hit may or may not have been executed: the host saw no completion, but the device may have advanced the write pointer. So after any reset the host's WP cache is unreliable exactly for the zones it was writing — which is why recovery begins with a report, not with a retry Derived.

  • NVM Express Base Specification, Revision 2.4 — Asynchronous Event Request; Get Log Page; Asynchronous Event Configuration; Controller Reset

Normative As recorded in Chapter 59 (values agreeing with libnvme): opcodes 79h, 7Ah, 7Dh; ZSA 1h–5h; report filter 5h = Full; ZS 1h Empty and 4h Closed; statuses B8h–BFh under SCT 1h. Zone capacity may vary between zones; writes must start at the write pointer; Close does not release an active resource.

Informative The specification's explanation of why ZNS exists and how hosts may use it. Optional Zone Descriptor Extensions, ZRWA, Read Across Zone Boundaries, the Zone Descriptor Changed event and its enable bit, FRL/RRL-driven attributes.

Which implicitly opened zone the controller closes; how long Reset and Finish take; whether and how ZCAP shrinks; when Finish/Reset Recommended are set within FRL/RRL; the internal cost of an implicit close.

ZRWA, extra report filters and zone attributes arrived after ZNS 1.0 Version-dependent. Linux added max_active_zones and zone append support in stages; older kernels expose only some limits.

The specification does not say how to choose victims, how many streams to map to a zone, or how to recover host metadata. Check in the text: which status a write that exceeds remaining zone capacity (but not the zone size) returns; the Asynchronous Event Information value for Zone Descriptor Changed; the Feature 0Bh bit that enables it; the exact Changed Zone List layout and its overflow behaviour; what happens to the write pointer of an opened zone across a controller reset when writes were in flight.

Never assume the host's WP cache is right after a reset, that ZCAP is constant, that Close frees an active resource, that an implicit close is free, or that Reset may precede durable metadata.

Hardware view

Hardware participation
CategoryHardware
Must participateNAND erase blocks grouped into zone stripes; controller zone state table; write buffers for each open zone.
May participatePower-loss capacitors sized for MOR+1 open zones; parity engines per open stripe; bad-block retirement shrinking ZCAP.
ObservableZone states, WP, ZCAP, attributes in reports; latency of writes after implicit closes; Reset latency.
InternalWhich dies a zone spans, when erase happens, parity layout, why capacity changed.

An open zone owns a partially programmed stripe: data sitting in buffers, parity accumulating, perhaps a NAND page that needs multi-pass programming. Closing it means padding or flushing that state so it is safe without a buffer. Reopening it means rebuilding the context. When a host writes round-robin across more zones than MOR+1, every write may force a close and a reopen — no error, just lower throughput and higher latency Implementation-dependent in magnitude.

ZCAP usually covers whole erase-block stripes across dies. When a block in the stripe is retired, the device can either borrow a spare or offer a smaller zone after the next reset. A drive with few spares left will show shrinking capacities — a health signal that belongs next to the SMART spare counter of Module 43.

Analysis. With least-recently-used closing and round-robin access, the zone written next is always the one just closed: the worst case for any cache. The first abnormal event is row 3 — the first write whose latency jumps — and its cause is resource pressure, not media. Evidence: latency correlated with "zone was Closed before the write" in successive reports; zero errors. Fixes: map 14 streams onto at most 12 zones (merge streams of similar lifetime), or explicitly open the hottest 12 and serialise the rest. Which zone the controller closes is implementation-dependent; another device may degrade differently but will still pay for closes.

Analysis. The device executed the write before the reset; only the completion was lost. The host requeued the command from its unacknowledged list — the right thing for a block device, the wrong thing for a zone. The correct recovery: after any reset, report every zone the host was writing; if WP moved past the in-flight range, treat the write as done (verify by reading back if the data matters); if WP did not move, resubmit at the new WP. Zone Append avoids part of the problem — a requeued append never fails with BCh — but creates the opposite one: the data may now be written twice, and only the host's metadata knows which copy is current. Regression test: inject a reset with writes in flight and assert that no retry precedes a report.

Labs

Beginner lab — zone arithmetic for a host allocator

Safe lab Paper. Objective: derive the numbers an allocator needs. Prerequisites: Chapter 59. Setup: Lab SSD namespace 2: 4 KiB LBAs, ZSZE 0x1_0000, ZCAP 0xD800, 1,024 zones, MOR 11, MAR 13, ZASL 3 (with MPSMIN 4 KiB), MDTS 128 KiB.

Procedure: compute (a) usable capacity in GiB; (b) zone and last writable LBA for LBA 0x2A_7F00; (c) open and active zone limits; (d) maximum append size; (e) the report buffer for all zones with Partial = 1. Observations: which numbers differ from the "obvious" ones. Questions: what goes wrong if the allocator uses ZSZE? If it treats MOR as 1's based? Expected reasoning: careful units and 0's-based fields.

Solution

(a) 1,024 × 55,296 × 4 KiB = 216 GiB (LBA space is 256 GiB). (b) 0x2A_7F00 / 0x1_0000 = zone 0x2A (42); last writable LBA 0x2A_D7FF; 0x2A_7F00 is writable. (c) 12 open, 14 active. (d) ZASL 3 → 23 × 4 KiB = 32 KiB, smaller than MDTS (confirm ZASL units in ZNS 1.5). (e) 64 + 1,024 × 64 = 65,600 bytes, which fits in one 128 KiB transfer; larger namespaces need a loop. Using ZSZE tries to write 10,240 non-writable blocks per zone. Reading MOR as 1's based plans for one zone fewer than allowed, which is harmless; the dangerous error is the opposite (adding 2 instead of 1), which ends in BDh.

Extension: compute WA at victim live fractions 0.1, 0.5 and 0.9, and the GC read bandwidth needed to sustain 1 GB/s of new writes at u = 0.5.

Intermediate lab — controller reset with zones open

Caution lab QEMU VM with an emulated zoned namespace, as in Chapter 59's lab (options such as zoned.max_open=4,zoned.max_active=6; names version-dependent). Objective: see what a reset does to zone states and write pointers. Setup: guest with nvme-cli and blkzone; scratch image only.

Procedure:

  1. Write 64 KiB to zones 0, 1 and 2 with nvme write at each zone's WP; explicitly open zone 3 with nvme zns open-zone.
  2. Report zones 0–4; note states and WPs.
  3. Reset the controller: nvme reset /dev/nvme0.
  4. Report again; compare states and WPs.
  5. Repeat step 1's write to zone 0 at the old WP; observe the status.

Observations: state changes across the reset; whether WPs moved. Questions: which zones changed state? Did explicitly opened zone 3 behave differently? What status did step 5 return, and why? Expected reasoning: opened zones become Closed; completed writes keep their WP; a write at a stale WP is invalid.

Solution

Zones 0–2 (Implicitly Opened) and zone 3 (Explicitly Opened) report Closed after the reset (QEMU's emulation follows the specification here in recent versions; confirm on yours), with WPs unchanged because their writes completed. Step 5 writes at the old WP, which is now below the device's WP: SCT 1h / SC BCh Zone Invalid Write. In this lab no writes were in flight, so the WP is predictable; the dangerous case (Trace 3) is a reset with writes in flight, which you can approximate by issuing a large write in the background and resetting immediately.

Extension: fill five zones to make them active and reset; check that Closed zones still count against max_active and that a write to a seventh zone still fails with BDh.

Advanced lab — allocation policy versus active-zone leaks

Safe lab Simulation. Objective: quantify how stream count and the "end of stream" policy affect resource exhaustion and wasted capacity. Setup: save as zone_alloc_sim.py.

#!/usr/bin/env python3
"""Simulation for learning: host zone allocation against open/active limits.

Synthetic model of namespace 2 of the course Lab SSD (ZNS):
ZCAP = 0xD800 blocks per zone, MOR = 11 (12 open), MAR = 13 (14 active),
both 0's based as Identify reports them. The controller here implicitly
closes the least recently written implicitly opened zone when it needs an
open resource (one simple choice; real controllers choose for themselves).
"""
import random

ZCAP = 0xD800          # writable blocks per zone
MOR, MAR = 11, 13      # 0's based limits from Identify
NZONES = 512

class Device:
    def __init__(self):
        self.state = ["E"] * NZONES      # E, IO (impl. open), C, F
        self.wp = [0] * NZONES
        self.last = [0] * NZONES
        self.implicit_closes = 0
        self.clock = 0
        self.wasted = 0          # blocks skipped by Finish

    def count(self, *states):
        return sum(1 for s in self.state if s in states)

    def write(self, z, nblocks):
        """Write at the write pointer. Returns status name."""
        self.clock += 1
        s = self.state[z]
        if s == "F":
            return "ZONE_IS_FULL"
        if s == "E" and self.count("IO", "C") >= MAR + 1:
            return "TOO_MANY_ACTIVE_ZONES"
        if s in ("E", "C") and self.count("IO") >= MOR + 1:
            # need an open resource: implicitly close the LRU open zone
            lru = min((i for i, x in enumerate(self.state) if x == "IO"),
                      key=lambda i: self.last[i])
            self.state[lru] = "C"
            self.implicit_closes += 1
        n = min(nblocks, ZCAP - self.wp[z])
        self.wp[z] += n
        self.state[z] = "F" if self.wp[z] == ZCAP else "IO"
        self.last[z] = self.clock
        return "OK"

    def finish(self, z):
        if self.state[z] in ("IO", "C", "E"):
            self.wasted += ZCAP - self.wp[z]
            self.state[z] = "F"

    def reset(self, z):
        self.state[z], self.wp[z] = "E", 0


def run(policy, streams, days=30, seed=7):
    """policy: 'leaky' leaves a stream's partial zone active when the stream
    ends; 'finish' finishes it; 'share' lets a new stream reuse it."""
    rnd = random.Random(seed)
    dev = Device()
    zone_of = {}            # stream -> current zone
    free = list(range(NZONES))
    orphans = []            # partial zones whose stream ended
    for day in range(1, days + 1):
        for tick in range(200):
            sid = rnd.randrange(streams)
            if sid not in zone_of:
                if policy == "share" and orphans:
                    zone_of[sid] = orphans.pop()
                else:
                    zone_of[sid] = free.pop(0)
            z = zone_of[sid]
            st = dev.write(z, rnd.randint(64, 2048))
            if st != "OK" and st != "ZONE_IS_FULL":
                return day, st, dev
            if dev.state[z] == "F":
                del zone_of[sid]
            # a stream occasionally ends (file closed, compaction done)
            if rnd.random() < 0.004 and sid in zone_of:
                z = zone_of.pop(sid)
                if policy == "finish":
                    dev.finish(z)
                elif policy == "share":
                    orphans.append(z)
                # leaky: nothing; the zone stays active forever
        # host GC: reset full zones whose data is dead (simplified: oldest half)
        full = [i for i, s in enumerate(dev.state) if s == "F"]
        for z in full[: len(full) // 2]:
            dev.reset(z)
            free.append(z)
    return None, "OK", dev


if __name__ == "__main__":
    for streams in (8, 12, 16):
        for policy in ("leaky", "finish", "share"):
            day, st, dev = run(policy, streams)
            when = f"failed day {day} with {st}" if day else "30 days clean"
            print(f"streams={streams:2d} {policy:6s}: {when:42s} "
                  f"active={dev.count('IO', 'C'):2d} "
                  f"implicit_closes={dev.implicit_closes:2d} "
                  f"finished_unwritten={dev.wasted * 4 // 1024} MiB")

Procedure: run it; change the stream-end probability from 0.004 to 0.001 and 0.02; give "finish" a rule that finishes only zones more than 90% full and shares the rest. Questions: why does "leaky" fail sooner with more streams? Why does every policy fail at 16 streams? What does "finish" cost? Expected reasoning: active zones are a budget; leaks consume it; Finish trades capacity for budget.

Solution

Output: with 8 streams, leaky fails on day 8 with Too Many Active Zones, finish and share run 30 days clean; with 12 streams leaky fails on day 2; at 16 streams every policy fails on day 1 because 16 concurrent streams need 16 active zones and only 14 exist — no end-of-stream policy fixes an over-subscribed design. Finish costs capacity: about 3.3 GiB of finished-but-unwritten space over 30 days at 8 streams, which is lost until GC resets those zones. Share wastes nothing but mixes lifetimes in a zone, raising future GC cost. Implicit closes appear whenever more than 12 zones are written concurrently.

Extension: add a GC model that tracks live fraction per zone and compare host WA for "share" versus "finish".

Senior forensic lab — Too Many Active Zones after nine days

Safe lab Paper forensic. Objective: find a leak from evidence, not code. Prerequisites: all labs above; Root Cause, Ambiguity and Forensic Reporting.

Setup: an object store on Lab SSDs (MAR 13) starts failing writes with SCT 1h / SC BDh nine days after deployment. Evidence: (1) daily zone-state histograms: active zones 4, 5, 6, 7, 8, 9, 11, 12, 14 on days 1–9; (2) the store's logs: 3–5 "compaction aborted" events per day, on lock timeout; (3) the store's code review notes: compaction writes to a dedicated zone, and on success it finishes that zone; (4) no controller resets; (5) SMART normal; (6) a sister cluster running the same build with compaction disabled shows a steady 4 active zones.

Procedure: build a timeline; estimate leak rate; propose root cause, confirming experiment and fix. Questions: which evidence rules out the device? What leaks? Why did the store not see Too Many Open Zones first? What is the correct immediate mitigation? Expected reasoning: a monotonic active count with abort events and a control group points to an error path.

Solution

Active zones rise about one per day, close to the number of compaction aborts that left a partially written zone (not every abort had written data yet). The sister cluster with compaction disabled is the control: no growth. The device is behaving correctly (BDh only at 14 active, no resets, normal SMART). Root cause, high confidence: the abort path abandons its compaction zone without Finish or Reset, so each abort leaks one active resource. Open-resource pressure never surfaced because the controller implicitly closes abandoned zones — they move to Closed, which still counts as active. Confirming experiment: force an abort in staging and watch the active count rise by one. Mitigation: Finish (or Reset, if the data is not referenced) every Closed zone that no live stream owns; fix: release the zone in the abort path and add an invariant check comparing the host's active set with a daily report.

Extension: write the invariant check as pseudocode that runs after every reset and once a day.

Debugging

Pattern 1 — intermittent Zone Invalid Write after errors or resets
SymptomBCh appears only after timeouts, resets or path failover.
Possible causesRequeued writes at a stale cached WP; two paths writing one zone; WP cache updated at submission.
EvidenceReset and requeue events in dmesg; report WP versus the failing SLBA.
First checkWas there a report between the reset and the retry?
Second checkDevice WP minus failing SLBA equals the in-flight length?
Disambiguating experimentInject a reset with one large write in flight in a VM.
Likely conclusion / confidenceStale host WP — high when the difference equals the in-flight write.
Pattern 2 — Too Many Active Zones after days
SymptomBDh after long uptime; restart of the application "fixes" it only if it finishes zones on startup.
Possible causesError paths abandoning zones; Close used to release resources; stream count above MAR+1.
EvidenceDaily state histograms; application error-path events.
First checkCount Closed zones that no host component owns.
Second checkCorrelate growth with specific application events.
Disambiguating experimentTrigger the suspect path in staging; watch the count.
Likely conclusion / confidenceHost leak — high when the count is monotonic and a control group is flat.
Pattern 3 — throughput collapse with no errors
SymptomWrite latency rises tenfold; no error statuses.
Possible causesImplicit-close thrash; GC competing with foreground; device-internal erase backlog after mass resets.
EvidenceNumber of distinct zones written per second versus MOR+1; GC activity; reset rate.
First checkSuccessive reports: do Closed zones rotate?
Second checkLatency of writes to previously Closed zones versus open ones.
Disambiguating experimentReduce concurrent zones to MOR+1 and re-measure.
Likely conclusion / confidenceOpen-resource thrash — high if latency recovers.
Pattern 4 — data read from the wrong place after appends
SymptomRecords come back out of order or swapped, no I/O errors.
Possible causesHost recorded LBAs by submission order instead of from CQE DW0–DW1; driver path discards DW0–DW1; requeued append written twice.
EvidenceCQE DW0–DW1 in a trace compared with the host's map.
First checkDoes the map match completion LBAs?
Second checkAny appends requeued after resets?
Disambiguating experimentRun appends at queue depth 1; if the bug disappears, the ordering assumption is wrong.
Likely conclusion / confidenceHost mapping bug — high.
Pattern 5 — writes fail near the end of some zones
SymptomZone Is Full or boundary errors on a few zones, older drives more often.
Possible causesAllocator caches ZCAP or uses ZSZE; capacity shrank on reset.
EvidenceDistinct ZCAP values in reports; host capacity table.
First checkZCAP of the failing zone now versus host's value.
Second checkNumber of reduced-capacity zones over time; SMART spare.
Disambiguating experimentRe-read ZCAP after each reset in a long test.
Likely conclusion / confidenceHost ignores ZCAP — high; whether wear is behind it — medium, from trends.

Interview

Beginner

  1. Who does garbage collection on a ZNS drive?

    Model answer

    The host: it copies live data out of zones and resets them.

  2. Why is ZCAP not equal to ZSZE?

    Model answer

    Zone size is a power-of-two LBA span; capacity matches whole erase stripes and can be smaller.

  3. Does Close Zone free an active resource?

    Model answer

    No. Only Finish or Reset does.

  4. Where does Zone Append report the LBA written?

    Model answer

    Completion Dwords 0–1.

  5. What must the host do after a controller reset?

    Model answer

    Report the zones it was writing and rebuild its write-pointer cache before writing.

Intermediate

  1. Give the GC cost formula.

    Model answer

    WA = 1/(1−u), with u the victim's live fraction.

  2. Why must metadata be durable before Reset Zone?

    Model answer

    After Reset the old copy is gone; a crash before the new mapping is durable loses the data.

  3. What is an implicit close and why does it cost time?

    Model answer

    The controller closes an implicitly opened zone to free an open resource, flushing that zone's buffers and parity.

  4. How do you find Full zones efficiently?

    Model answer

    Zone Management Receive with the Full filter (5h), paging with Partial = 1.

  5. Why can a requeued append be worse than a requeued write?

    Model answer

    It silently succeeds and duplicates data; only host metadata can tell which copy is valid.

Advanced

  1. A write fails with BCh right after a reset. What do you compare?

    Model answer

    The device WP from a report with the failing SLBA; a difference equal to an in-flight write proves it executed.

  2. How do you handle a Zone Descriptor Changed event?

    Model answer

    Read the Changed Zone List with RAE = 0, report the listed zones, act on Finish/Reset Recommended and capacity changes.

  3. Fourteen streams, twelve open resources: what happens?

    Model answer

    No errors, but implicit-close thrash; merge streams or explicitly manage open zones.

  4. Why might ZCAP shrink over a drive's life?

    Model answer

    Retired erase blocks in the zone's stripe without spares to replace them.

  5. What invariant should a host check daily?

    Model answer

    Device active zones equal the host's owned active set; any surplus is a leak.

Senior

  1. Design stream-to-zone mapping for a key-value store.

    Model answer

    Group data by expected lifetime (per compaction level), keep concurrent zones under MOR+1, reserve active budget for GC and metadata, and use appends for parallel writers.

  2. When would you choose Finish over sharing a partial zone?

    Model answer

    When active budget is scarce or the partial zone's lifetime differs from the next stream's; accept lost capacity until GC.

  3. How would you validate reset recovery?

    Model answer

    Fault-inject resets and power loss with writes and appends in flight; assert no write before a report and no duplicate or lost records.

  4. What would make you suspect the device rather than the host in a ZNS incident?

    Model answer

    A status that contradicts a fresh report (BCh at the reported WP, BDh below MAR+1 active) reproduced with a minimal host.

  5. How does ZNS change drive-health monitoring?

    Model answer

    Add zone-level signals — shrinking capacities, Read Only or Offline zones, recommendation rates — beside SMART spare and wear.

Teach-back

    Model explanation

    "Pick a Full zone with little live data, copy the live data into a GC zone with appends, save the new locations durably, then reset the old zone and read its new capacity from a report."

  3. To a senior engineer: what are the system risks of host-managed zones?

    Model explanation

    "Drift between the host's model and the device: stale write pointers after resets, leaked active zones in error paths, cached capacities, ignored recommendations.
