A guided route through the real documents: the NVM Express (NVMe) 2.4 specification family and the PCI Express (PCIe) Base Specification. Four reading tracks — Base, Commands, Transport, Advanced — each broken into reading units that tell you what to read first, what to skip, what to highlight, which tables to memorize, which diagrams to redraw, which safe commands to run, which trace patterns to look for, and how to check yourself.

Why a reading plan

The NVMe 2.4 family is eleven documents and well over a thousand pages, and the PCIe Base Specification on its own is larger still. Nobody reads them cover to cover on a first pass, and nobody should. Read in the wrong order and you drown in detail you have no hooks for; read only summaries and you will never be able to settle an argument with the text. This plan is the middle path: purposeful passes through the official documents, each tied to chapters of this course and to things you can observe on a real system or in a trace.

The plan assumes you have read Specification Reading School and keep the six notebook artifacts it describes. Every unit below ends with self-check questions: answer them from the document, with a citation, before ticking the unit off.

Learning objectives

  • Know which NVMe document, and which part of the PCIe Base Specification, owns each major topic.
  • Read each document in a deliberate order of passes: structure, core, detail, edge cases.
  • Build field dictionary and command matrix entries while reading, not afterwards.
  • Connect every reading unit to a safe Linux observation and to a trace pattern.
  • Answer source-lookup questions from the text with a citation by document, revision and section name.

Prerequisites

Track A assumes Parts IX–XI (What Is NVMe? through Dataset Management). Track C assumes Parts IV–VIII (PCIe Mental Model through DMA). Track D assumes Tracks A–C and the corresponding chapters in Parts XVIII–XX. You can start Track A in parallel with the PCIe chapters.

This plan refers to parts of each document by name — for example "Controller Initialization", "Submission Queue Entry", "Status Field definition" — because section numbers change between revisions. Headings in your copy may be worded slightly differently; treat the names below as search terms and use the table of contents and figure list to locate them. Where this course is not certain a heading exists under that exact name, the unit says so.

How to work through a reading unit

Each unit is read in up to four passes. Do not try to absorb everything in one.

  1. Structure pass (15–30 minutes). Read the table of contents for the unit, every figure and table title, and the first paragraph of each subsection. Write a one-page outline.
  2. Core pass. Read the parts marked "highlight" below in full. Fill field dictionary and command matrix rows as you go.
  3. Detail pass. Read the parts marked "skip initially". Add exceptions, conditional requirements and footnotes to your notes.
  4. Edge pass (later, driven by real problems). Reread a section when a bug, a trace or an interview question sends you there.

Reading Track A — NVM Express Base Specification

The Base Specification is the centre of the family. It defines what an NVM subsystem, controller and namespace are; how queues work; the common command and completion formats; the Admin command set; log pages and features; error reporting; reset and shutdown; and the extended capabilities that span command sets. The NVMe 2.4 Base Specification was ratified on 2026-07-31.

A1 — Introduction, conventions and definitions

Prerequisite chapters
What Is NVMe?, Specification Reading School.
Purpose
Learn the dialect: keywords, number notation, 0's based values, reserved-field rules, defined terms. Everything later depends on it.
Skip initially
Legal notices, the full acronym list (consult as needed).
Highlight
Requirement keywords; numerical notation; bit and byte ordering; the definition of reserved; the definitions of NVM subsystem, controller, namespace, host, NVM set and endurance group; the description of the document family.
Tables to memorize
None verbatim; memorize the notation rules.
Diagrams to redraw
The specification family diagram (Base, command sets, transports).
Commands to test
nvme version; nvme list; nvme list-subsys — map subsystem, controller and namespace names in Linux to the defined terms.
Trace patterns
None yet; note that "NVM subsystem" is not visible on PCIe at all — only Functions are.

Self-check

  1. What is the difference between an NVM subsystem and a controller?
    Answer

    An NVM subsystem is the whole entity containing one or more controllers, namespaces, ports and storage media. A controller is the interface between a host and the subsystem; on PCIe a controller is presented through a PCIe Function. One subsystem can contain several controllers.

  2. What does "0's based" mean, and where do the conventions define it?
    Answer

    A value one less than the quantity represented. It is defined in the Base Specification's conventions material near the start of the document.

  3. Where would you look to find whether a reserved field may be non-zero in a command a host submits?
    Answer

    The conventions clause (reserved definition) first, then the specific command's table and footnotes.

A2 — Theory of operation and architecture

Prerequisite chapters
NVMe 2.x Architecture, NVMe Controller, Namespaces.
Purpose
Build the official mental model: controller types (I/O, administrative, discovery), namespaces and namespace identifiers, command sets and how a controller reports which it supports, the queue model.
Skip initially
Multi-path, NVM sets, endurance groups, domains, reservations, virtualization architecture.
Highlight
Controller types; the queue model (paired SQ and CQ, Admin queue pair, many-to-one SQ to CQ mapping); namespace types and Command Set Identifier (CSI); the command execution model, including that commands in one SQ may complete out of order.
Tables to memorize
Controller types and which command sets each supports.
Diagrams to redraw
Host–controller–namespace relationship; queue pair diagram; NVM subsystem with two controllers sharing a namespace.
Commands to test
nvme id-ctrl /dev/nvme0 -H (look at controller type, number of namespaces); nvme list-ns /dev/nvme0; nvme id-ns /dev/nvme0n1.
Trace patterns
Admin queue traffic during initialization (Identify commands) versus I/O queue traffic; distinct SQ doorbells per queue.

Self-check

  1. Does the Base Specification require commands in one Submission Queue to complete in order?
    Answer

    No. Commands may complete in any order; the host matches completions by SQ identifier and Command Identifier. Ordering requirements exist only for specific cases such as fused operations.

  2. Can two Submission Queues share one Completion Queue?
    Answer

    Yes; several I/O SQs may map to one CQ. The Admin SQ always uses the Admin CQ.

A3 — Data structures: SQE, CQE, data pointers, status

Prerequisite chapters
NVMe Command Structure, Physical Region Pages, Scatter Gather Lists, NVMe Errors.
Purpose
These are the structures you decode in every trace.
Skip initially
Less common SGL descriptor types; keyed SGL; metadata pointer subtleties.
Highlight
Submission Queue Entry common format; Completion Queue Entry; Physical Region Page entries and lists (offset rules, list chaining); SGL descriptor basics; the Status Field definition (SC, SCT, CRD, M, DNR); the Generic Command Status table.
Tables to memorize
SQE Dword map (CDW0, NSID, MPTR, DPTR, CDW10–15); CQE Dword map (DW2 SQHD/SQID, DW3 CID/P/Status); Status Code Types (0h generic, 1h command specific, 2h media and data integrity, 3h path related, 7h vendor specific); the first entries of Generic Command Status (Successful Completion, Invalid Command Opcode, Invalid Field in Command, Command ID Conflict, Data Transfer Error).
Diagrams to redraw
CDW0 bit layout; PRP1/PRP2 for a transfer spanning three pages; a PRP list chain.
Commands to test
nvme error-log /dev/nvme0 — read the status fields of recorded errors; compare with the Status Field definition.
Trace patterns
SQE fetch: device Memory Read (MRd) of 64 bytes (or a multiple) from the SQ base; CQE post: device Memory Write (MWr) of 16 bytes to the CQ; PRP list fetch: device MRd from a PRP list page before data movement.

Self-check

  1. Which bit of CQE Dword 3 is the Phase Tag, and why does it exist?
    Answer

    Bit 16. It lets the host detect new entries without reading a controller register: the controller inverts the phase value it writes each time it wraps the queue.

  2. A transfer of 8 KiB starts at a page offset of 512 bytes with 4 KiB pages. How many PRP entries describe it and is a PRP list needed?
    Answer

    It touches three pages (3.5 KiB + 4 KiB + 0.5 KiB), so three entries. PRP1 covers the first page; because more than two entries are needed, PRP2 points to a PRP list holding the remaining entries.

  3. What does DNR mean?
    Answer

    Do Not Retry: if set, the controller indicates the same command is expected to fail again if resubmitted.

A4 — Controller properties, initialization, shutdown and reset

Prerequisite chapters
NVMe Registers, NVMe Reset, Admin Queue.
Purpose
Understand bring-up, which is where many field failures and nearly all "device not found" or "controller not ready" bugs live.
Skip initially
Controller memory buffer, persistent memory region, boot partitions, NVM subsystem reset details.
Highlight
Controller properties: CAP, VS, CC, CSTS, AQA, ASQ, ACQ (offsets 00h, 08h, 14h, 1Ch, 24h, 28h, 30h); the Controller Initialization sequence; controller shutdown (CC.SHN and CSTS.SHST); controller-level reset and what it does to queues; CAP.TO, CAP.MQES, CAP.DSTRD, CAP.CSS.
Tables to memorize
The register/property offset map above; the CC.EN / CSTS.RDY handshake.
Diagrams to redraw
Initialization sequence as a sequence diagram; shutdown handshake.
Commands to test
sudo nvme show-regs /dev/nvme0 -H (reads controller registers through the driver; read-only, but run on a lab machine); sudo dmesg | grep -i nvme after boot to see initialization messages.
Trace patterns
Host MRd of CAP (BAR0+00h), MWr to AQA/ASQ/ACQ, MWr to CC with EN=1, a sequence of MRd polls of CSTS until RDY=1, then the first Admin doorbell write at BAR0+1000h.

The Base Specification defines these as controller properties. How they are mapped into memory and accessed on PCIe — as registers in BAR0 — is defined by the NVMe over PCIe Transport Specification (Track C).

Self-check

  1. What must the host program before setting CC.EN to 1?
    Answer

    At minimum the Admin Queue Attributes (AQA) and the Admin SQ and CQ base addresses (ASQ, ACQ), plus the CC fields such as the I/O command set selection, memory page size and arbitration mechanism. Confirm the full list in the Controller Initialization material.

  2. What does CAP.TO bound?
    Answer

    The worst-case time the host should wait for CSTS.RDY to transition after changing CC.EN, in units of 500 ms.

A5 — Admin command set

Prerequisite chapters
Admin Commands, Admin Queue, I/O Queues.
Purpose
Admin commands configure, discover and manage the controller. Initialization traces are Admin traces.
Skip initially
Security Send/Receive, Sanitize details, Virtualization Management, Directive Send/Receive, Namespace Management internals, migration-related commands added in 2.4.
Highlight
Identify (opcode 06h) and its Controller or Namespace Structure (CNS) values; Create I/O Completion Queue (05h) and Create I/O Submission Queue (01h); Delete I/O SQ/CQ; Get Log Page (02h); Set Features and Get Features; Asynchronous Event Request; Abort; Firmware Image Download and Firmware Commit (read, do not run).
Tables to memorize
Opcodes of Identify, Create/Delete queues and Get Log Page; the CDW10/CDW11 layout of the two Create commands; the main CNS values you use (controller and namespace data).
Diagrams to redraw
The order of Admin commands a driver issues during initialization; the dependency "create CQ before the SQ that uses it".
Commands to test
nvme id-ctrl /dev/nvme0; nvme id-ns /dev/nvme0n1; nvme get-feature /dev/nvme0 -f 0x07 -H (Number of Queues); nvme get-feature /dev/nvme0 -f 0x08 -H (Interrupt Coalescing).
Trace patterns
Admin SQ doorbell (BAR0+1000h) → SQE fetch from the Admin SQ base → for Identify, a 4 KiB data MWr into host memory → CQE MWr into the Admin CQ → MSI-X vector 0.

Self-check

  1. Why must an I/O Completion Queue be created before the Submission Queue that posts to it?
    Answer

    Create I/O Submission Queue names the CQ identifier its completions go to; the controller rejects an SQ whose CQ does not exist (a command-specific status for an invalid completion queue).

  2. Which Admin command tells you how many I/O queues the controller granted?
    Answer

    Set Features (or Get Features) with the Number of Queues feature; completion Dword 0 returns the numbers allocated (0's based).

A6 — Log pages and features

Prerequisite chapters
SMART / Health, Power Management.
Purpose
Logs and features are the controller's self-report and its tunables. They are what you read when there is no analyzer.
Skip initially
Telemetry, persistent event log, endurance group logs, vendor-specific log ranges.
Highlight
Error Information log (01h), SMART / Health Information log (02h), Firmware Slot Information log (03h), Changed Namespace List log (04h), Commands Supported and Effects log (05h); Arbitration, Power Management, Temperature Threshold, Number of Queues, Interrupt Coalescing, Interrupt Vector Configuration and Asynchronous Event Configuration features.
Tables to memorize
The log identifiers above; the SMART critical-warning bits; the units of Data Units Read/Written (thousands of 512-byte units — confirm in the text).
Diagrams to redraw
The Asynchronous Event flow: outstanding AER command → event → completion → host reads the log page that clears the event.
Commands to test
nvme smart-log /dev/nvme0; nvme error-log /dev/nvme0; nvme fw-log /dev/nvme0; nvme get-log /dev/nvme0 --log-id=5 --log-len=4096 (Commands Supported and Effects; check your nvme-cli syntax).
Trace patterns
Get Log Page traffic is identical in shape to Identify: SQE fetch, data MWr to host, CQE. The log identifier is visible only by decoding CDW10 inside the SQE fetch completion.

Self-check

  1. Why can't a PCIe analyzer show you which log page was read without decoding the SQE?
    Answer

    On the wire the log identifier exists only as bits in CDW10 of the 64-byte SQE, carried in the payload of the completion to the controller's SQE fetch. The data MWr that returns the log carries only bytes.

  2. What does the host have to do so the controller can report further asynchronous events of the same type?
    Answer

    Read the associated log page (with the option that retains or clears the event as described), and keep Asynchronous Event Request commands outstanding.

A7 — Error handling, asynchronous events and reset types

Prerequisite chapters
NVMe Errors, Error Correlation, NVMe Reset.
Purpose
Learn how failures are signalled at the NVMe level and how recovery works.
Skip initially
Command retry delay mechanics, multipath error handling.
Highlight
Command and queue-level error reporting; controller fatal status (CSTS.CFS); the reset types (controller reset, NVM subsystem reset, and transport-level resets that the PCIe Transport defines); what happens to outstanding commands on reset; Abort semantics.
Tables to memorize
Reset types and their scope (what is reset, what persists).
Diagrams to redraw

Commands to test

Self-check

  1. Is an Abort guaranteed to abort the target command?
    Answer

    No. Abort is best effort; the target command may complete normally, and the Abort completion reports whether it was aborted. Check the Abort command description.

Reading Track B — NVM Command Set Specification

The NVM Command Set Specification 1.3 defines the I/O commands, data structures and behaviour for namespaces that store logical blocks — the "normal" SSD namespace. It relies on the Base Specification for everything common.

B1 — Introduction and the NVM namespace model

Prerequisite chapters
NVM Command Set, Namespaces, What Is Storage?.
Purpose
Understand logical blocks, LBA formats, metadata and how the command set extends Base structures.
Skip initially
Endurance group and NVM set interactions.
Highlight
Logical block and LBA format definitions (LBA Data Size as a power of two, metadata size); the command-set-specific Identify Namespace data structure: NSZE, NCAP, NUSE, FLBAS, the LBA Format list; namespace size versus capacity versus utilization.
Tables to memorize
NSZE/NCAP/NUSE meanings; LBA Format entry fields (metadata size, LBA data size, relative performance).
Diagrams to redraw
A namespace as an array of logical blocks with optional metadata, both interleaved (extended LBA) and separate.
Commands to test

Trace patterns
Identify Namespace data returned in a 4 KiB data MWr after an Admin SQE with NSID set.

Self-check

  1. The lab system's namespace 1 has NSZE = 1,953,525,168 with 512-byte LBAs. What is its size in bytes?
    Answer

    1,953,525,168 × 512 = 1,000,204,886,016 bytes ≈ 1.0 TB.

B2 — The I/O commands

Prerequisite chapters
READ, WRITE, FLUSH, Dataset Management.
Purpose
These are the commands in almost every trace you will ever analyze.
Skip initially
Copy command formats, Write Uncorrectable, Verify, Compare and fused Compare-and-Write details.
Highlight
Read (02h) and Write (01h): SLBA (CDW10–11), NLB (CDW12 bits 15:0, 0's based), Force Unit Access, the protection information fields; Dataset Management (09h) and its range list; Write Zeroes; Flush (00h) — confirm whether your revision defines Flush in the Base Specification's I/O command material or in the command set.
Tables to memorize
Read/Write CDW10–CDW15 layout; the four opcodes 00h, 01h, 02h, 09h.
Diagrams to redraw
Read: device writes data into host memory (MWr). Write: device reads data from host memory (MRd + CplD). Draw both as sequence diagrams.
Commands to test
cat /sys/block/nvme0n1/queue/max_hw_sectors_kb and nvme id-ctrl /dev/nvme0 | grep -i mdts — relate Maximum Data Transfer Size to command sizes you will see. Avoid issuing raw I/O commands outside a lab.
Trace patterns
Read 4 KiB on the lab system (MPS 256 B): SQE fetch, then sixteen 256-byte MWr data TLPs device→host, then CQE MWr, then MSI-X MWr. Write 4 KiB (MRRS 512 B): eight 512-byte MRd requests, each satisfied by completions no larger than MPS and split at the Read Completion Boundary where applicable.

Self-check

  1. Why does a Write command cause the device to issue Memory Reads?
    Answer

    The data is in host memory; the controller pulls it with DMA reads (non-posted MRd), and the host's completer returns CplD TLPs carrying the data.

  2. On the lab system, how many data TLPs does a 4 KiB Read produce at minimum, and why?
    Answer

    Sixteen, because the Max Payload Size of 256 bytes limits each MWr payload: 4096 / 256 = 16 (assuming an aligned buffer).

  1. A Read fails with a media error after data TLPs were already sent. What can you say about the data in the host buffer?

Reading Track C — Transport: NVMe over PCIe and the PCIe Base Specification

This track joins two separate standards. The NVMe over PCIe Transport Specification 1.4 explains how NVMe uses PCIe: how the controller appears as a PCIe Function, where registers and doorbells sit, how interrupts work, and how queues and data live in host memory. The PCI Express Base Specification defines PCIe itself. Keep them separate in your notes; the transport document is the bridge, not a replacement for either side.

C1 — NVMe over PCIe Transport: the PCIe mapping

Prerequisite chapters
BARs and MMIO, Doorbells, MSI-X, NVMe over PCIe deep dive.
Purpose
Know exactly what an NVMe controller looks like to a PCIe host.
Skip initially
Legacy pin-based and multi-message MSI details; controller memory buffer mapping specifics.
Highlight
The PCI header and capability requirements (class code for NVMe, BAR0/BAR1 as the register space); the mapping of controller properties to memory-mapped registers; the doorbell registers and the stride formula (SQ y tail at 1000h + (2y × (4 << CAP.DSTRD)), CQ y head at that plus (4 << CAP.DSTRD)); interrupt mechanisms (MSI-X, MSI, pin-based) and their use; queue memory requirements (physically contiguous or PRP list); PCIe-specific resets (for example Function Level Reset) and their effect on the controller.
Tables to memorize
Doorbell layout and stride formula; which capability structures an NVMe Function must or may implement.
Diagrams to redraw
BAR0 map: registers at 0h–FFFh, doorbells from 1000h, and (on the lab system) MSI-X table at 2000h and PBA at 3000h — the latter two are an implementation choice found through the MSI-X capability.
Commands to test
lspci -nn -d ::0108 (find NVMe class devices); sudo lspci -vvv -s 01:00.0 (capabilities, BAR, MSI-X table size); cat /sys/bus/pci/devices/0000:01:00.0/resource.
Trace patterns
All MWr from the root complex into BAR0+1000h–1FFFh are doorbells; decode queue number and head/tail from the offset.

Section headings of the PCIe Transport document are not quoted here because this course has not confirmed their exact wording in revision 1.4. Use the table of contents; the topics above are all there.

Self-check

  1. With CAP.DSTRD = 0, what is the address of the CQ1 head doorbell on the lab system?
    Answer

    BAR0 + 1000h + (2×1 + 1) × 4 = BAR0 + 100Ch = 0xFE60_100C.

  2. Which document defines the MSI-X table format: NVMe Base, NVMe over PCIe Transport, or PCIe Base?
    Answer

    PCIe Base. The transport document says how NVMe uses MSI-X; the Base Specification of NVMe deals with interrupt vectors only abstractly (in Create I/O CQ, for example).

C2 — PCIe Base: Transaction Layer Specification

Prerequisite chapters
TLPs, TLP Header Anatomy, Posted vs Non-Posted Transactions, PCIe Tags, PCIe Ordering.
Purpose
Every NVMe action on PCIe becomes TLPs. This chapter is the grammar of your traces.
Skip initially
Atomic operations, TLP prefixes, deferrable memory writes, Integrity and Data Encryption (IDE), and Flit-mode header details unless you work at 64 GT/s or above.
Highlight
Transaction types and TLP formats (Fmt/Type); memory request headers (address, length, first/last byte enables, tag, requester ID); completion headers (completion status, byte count, lower address, completer ID); completion rules (splitting at the Read Completion Boundary, ordering of completions for one request); ordering rules table; flow control credit types; completion timeout mechanism.
Tables to memorize
Fmt/Type encodings for MRd, MWr, CplD, Cpl, CfgRd, CfgWr, Msg; completion status values (SC, UR, CRS, CA); the ordering table's main rules (posted may pass non-posted; completions may pass non-posted; posted writes do not pass posted writes unless relaxed ordering applies).
Diagrams to redraw
3DW and 4DW memory request headers; the completion header; a 512-byte read completed in multiple completions.
Commands to test
sudo lspci -vvv -s 01:00.0 | grep -E "MaxPayload|MaxReadReq|ExtTag|RlxdOrd".
Trace patterns
Tag reuse after completion; byte count decreasing across split completions; UR completions to DMA reads after an IOMMU fault.

Self-check

  1. What tells you that the last completion for a split read has arrived?
    Answer

    The Byte Count field equals the payload length of that completion (the remaining bytes reach zero after it).

  2. Can a CQE Memory Write overtake the data Memory Writes of the same Read command?
    Answer

    Not under default ordering: posted writes from the same requester stay in order unless Relaxed Ordering is set on them. This is why a controller can safely write data before the CQE. Check the ordering rules and the Relaxed Ordering attribute.

Final self-check across tracks

  1. Which document defines the location of the SQ tail doorbell registers?

    • NVM Express Base Specification
    • NVM Command Set Specification
    • NVMe over PCIe Transport Specification
    • PCI Express Base Specification
    Answer and reasoning

    The transport specification maps the abstract tail pointer onto a memory-mapped register; the Base Specification defines what a tail is; PCIe defines the Memory Write that carries it.

  2. Where do you read the format of a completion TLP's Byte Count field?

    • NVMe Base
    • NVMe over PCIe Transport
    • NVM Command Set
    • PCI Express Base Specification, Transaction Layer Specification
    Answer and reasoning

    Completions are PCIe Transaction Layer constructs.

  3. Which NVMe document defines the Read command's CDW12 NLB field?

    • NVMe Base
    • NVM Command Set
    • NVMe over PCIe Transport
    • NVMe-MI
    Answer and reasoning

    Read is an NVM Command Set I/O command.

  4. You see Msg TLPs carrying vendor-defined payloads to the SSD while no I/O is running. Which Track D document should you read?

    Model answer

    NVMe-MI 2.2: management traffic can use MCTP over PCIe Vendor Defined Messages. Confirm by decoding the message header.

  5. Why is the PCIe Base Specification on this reading plan at all, if the course is about NVMe?

    Model answer

    Every NVMe-over-PCIe action is carried by PCIe transactions; ordering, completion rules, errors and link behaviour are PCIe-defined. Without it you cannot interpret a trace or attribute errors to the right layer.

  6. Name three things you should "skip initially" in the Base Specification and why.

    Model answer

    For example: virtualization management, reservations, and telemetry logs. They are important but rely on the core model; reading them first produces detail without hooks. Read them when a project needs them.

  7. What must every reading unit produce besides understanding?

    Model answer

    Notebook entries: field dictionary rows, command matrix rows, state-machine notes and trace mapping rows, each with revision and citation by section name.

  8. Where are the opcodes for 2.4 features such as rate limiting documented?

    Model answer

    In the NVM Express Base Specification 2.4 (and related documents) and summarized in the Revision Changes document dated 2026-07-30. This course deliberately does not state them.
