PCI Express is built in three layers: the Transaction Layer says what to do, the Data Link Layer makes sure it arrives intact and in order across one link, and the Physical Layer turns it into signals. Knowing exactly which layer owns which job, which packet and which error is the single most useful skill in reading PCIe traces and error logs.

Why this chapter exists

When an NVMe SSD reports a problem, the evidence arrives labelled by layer even if nobody says so. "Receiver Error" is a Physical Layer complaint. "Bad TLP" and "Replay Timer Timeout" are Data Link Layer complaints. "Unsupported Request" and "Completion Timeout" are Transaction Layer complaints. Each points to different causes and different owners. Engineers who do not know the layer model chase signal integrity when the bug is a driver writing to an unmapped address, or chase driver bugs when a connector is dirty.

This chapter is the map. Part V then dives into the Transaction Layer, Part VI into the Data Link Layer, and Chapters 8–9 into the Physical Layer's state machine.

Learning objectives

  • Name the three PCIe layers and state each layer's purpose and main responsibilities.
  • Follow one NVMe doorbell write down the transmitter's layers and up the receiver's, naming what each layer adds and checks.
  • Recognise the basic structures: TLP header DW0, DLLP format, physical framing and ordered sets.
  • Classify a PCIe error by layer and by severity (correctable, non-fatal, fatal).
  • Say what each layer's activity looks like in an analyzer trace and what (little) Linux can see of it.
  • Explain hop-by-hop (link-local) versus end-to-end mechanisms.

The story

Think of sending a parcel through a chain of post offices.

  • You write the letter and the address: "Please put these 4 numbers in drawer 1008 at the SSD's house." That is the Transaction Layer. It decides what the message means and where it goes.
  • At each post office counter, a clerk puts the letter in an envelope, writes a ticket number on it, and seals it with a special sticker that shows if anyone tore it. The clerk keeps a photocopy until the next counter says "got ticket 26, all fine". If the next counter says "ticket 26 was torn", the clerk sends the photocopy again. That is the Data Link Layer. It only cares about getting from this counter to the next one.
  • The delivery van drives the envelope along the road, at whatever speed the road allows, in whatever lanes are open. That is the Physical Layer.

Network engineers will recognise the shape from TCP/IP over Ethernet: an application request (Transaction Layer), a reliable delivery mechanism with sequence numbers and acknowledgements (Data Link Layer), and framing plus signalling on a cable (Physical Layer). The PCIe layers are a compressed, hardware-implemented version of that stack.

  • Reliability is per hop, not end to end. TCP's acknowledgements are end to end. PCIe's Ack/Nak works only between the two ports of one link. Across a Switch, each link has its own sequence numbers and its own retries; the Switch could, in principle, corrupt a packet internally after a successful link-level check. End-to-end protection exists only as the optional End-to-end CRC (ECRC) and data poisoning.
  • No routing at the link layer. In networking, layer 2 has addresses. The PCIe Data Link Layer has none; it talks only to its single neighbour. Routing information lives in the TLP header.
  • Everything is hardware and fast. Retries complete in hundreds of nanoseconds to microseconds, without software.
  • The post office never loses envelopes silently. A PCIe link that cannot deliver retrains and, if that fails, goes down; software is told.

Beginner explanation

Each PCIe port contains the same three layers, stacked:

Device core / softwareNVMe controller logic; CPU and driver on the host side
Transaction Layerbuilds and checks TLPs: reads, writes, completions, messages; flow-control credits; ordering
Data Link Layersequence numbers, LCRC, Ack/Nak, replay; DLLPs
Physical Layerframing, scrambling/encoding, lanes, LTSSM, SerDes
The linkcopper, connectors, retimers

When the CPU writes an NVMe doorbell, the Root Port's Transaction Layer builds a Transaction Layer Packet (TLP) that says "memory write, address 0xFE60_1008, 4 bytes, value 6". The Data Link Layer gives it a sequence number and a checksum (the Link CRC, LCRC). The Physical Layer frames it and sends it across the lanes.

At the SSD, the layers run in reverse. The Physical Layer recovers the bytes. The Data Link Layer checks the LCRC and sequence number, sends back a small acknowledgement (a Data Link Layer Packet, DLLP, of type Ack), and passes the TLP up. The Transaction Layer reads the header and delivers the write to the NVMe controller's doorbell register.

Three kinds of things therefore travel on a link: TLPs (meaningful work), DLLPs (link housekeeping), and ordered sets (physical housekeeping).

Engineering explanation

First the whole journey, then each layer in depth.

Physical Layer

The Physical Layer is the delivery van and the road. It does not read the letter. It just makes sure envelopes get onto the road, in the right lanes, at a speed the road can handle, and that the van at the other end knows where each envelope starts and stops.

Purpose

Move bytes between two ports reliably enough for the Data Link Layer to do the rest, and manage the link itself.

Responsibilities

The specification divides it into a logical sub-block and an electrical sub-block.

  • Framing: marking the start and end of each TLP and DLLP (K-code symbols at 8b/10b; tokens at 128b/130b; flit structure in Flit Mode).
  • Byte striping across lanes and deskew at the receiver.
  • Scrambling and encoding (8b/10b; 128b/130b with sync headers; PAM4 and FEC in Flit Mode).
  • Ordered sets: TS1/TS2 (training), SKP (clock compensation), EIOS/EIEOS (electrical idle entry/exit), FTS (L0s exit), SDS (start of data stream).
  • The Link Training and Status State Machine (LTSSM): detect, train, set width and speed, equalise, recover, enter and leave low-power states (Chapter 8).
  • Electrical: transmitters, receivers, equalisation, clock recovery, receiver detection, electrical idle (Chapter 5).

Errors

  • Receiver Error (correctable): an umbrella for physical problems such as 8b/10b invalid symbols or disparity errors, 128b/130b sync header errors, framing errors, elastic buffer over/underflow, and lock loss. Precisely which events are counted is defined in the specification and partly implementation-dependent.
  • Training failures: not an AER error class; visible as a link that never reaches L0, reduced width/speed, or repeated Recovery.
  • Surprise Down: the link went down without software asking; reported by the Data Link Layer of a downstream port that supports it.

Trace visibility

Fully visible to a protocol analyzer: ordered sets, LTSSM state transitions (analyzers infer them), per-lane symbol errors, electrical idle periods, data rate changes. An oscilloscope or the receiver's margining capability sees the analog layer. Linux sees only the results: Link Status, correctable Receiver Error counts, link-bandwidth notifications.

Data Link Layer

The Data Link Layer is the counter clerk who numbers every envelope, seals it with a tamper sticker, keeps a photocopy, and resends it if the next counter says it arrived torn. The clerk only ever talks to the next counter, never to the final address.

Purpose

Provide a reliable, ordered TLP delivery service across one link, and exchange link-management information.

Responsibilities

  • Link initialisation: after the Physical Layer reports link up, the Data Link Layer moves from DL_Inactive through DL_Init (exchanging InitFC1 and InitFC2 DLLPs to advertise initial flow-control credits) to DL_Active. Only then can TLPs flow.
  • Sequence numbers: a 12-bit sequence number on every TLP, incremented per TLP, wrapping at 4096.
  • LCRC: a 32-bit Link CRC over the sequence number and TLP, checked by the receiver.
  • Ack/Nak protocol: the receiver acknowledges good TLPs (Ack DLLP with the latest good sequence number, cumulative) or requests replay (Nak). The transmitter keeps every TLP in a replay buffer until acknowledged.
  • Replay timer and REPLAY_NUM: if no Ack arrives in time, the transmitter replays. A small counter tracks consecutive replays; when it rolls over, the Data Link Layer asks the Physical Layer to retrain the link (enter Recovery).
  • Flow-control credit exchange: carries the Transaction Layer's credit information in InitFC and UpdateFC DLLPs.
  • Power management handshakes: PM DLLPs for entering L1 and L2/L3 Ready.
  • Data Link Features exchange (Revision 4.0 and later): optional capabilities such as scaled flow control are negotiated with a Data Link Feature DLLP. Version-dependent

Trace visibility

Analyzers show sequence numbers on TLPs, Ack/Nak DLLPs, replays (a TLP with a sequence number already seen), UpdateFC DLLPs and credit values, and PM DLLPs. Many analyzers can compute "Ack latency" and flag replays automatically. Linux sees AER correctable counts (Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover) and, for uncorrectable errors, AER logs.

Transaction Layer

The Transaction Layer is the letter writer. It decides what the message says ("write these numbers into drawer 1008", "please send me the 64 bytes at shelf 0x1_2340_0140", "here are the bytes you asked for"), who it is from, and where it goes. It also keeps track of how much space the other side has left in its mailbox, so it never sends more letters than fit.

Purpose

Carry requests and completions between requesters and completers anywhere in the hierarchy, with routing, ordering, flow control and quality-of-service information.

Responsibilities

  • Building and decoding TLPs: memory, I/O and configuration requests; completions; messages (interrupts INTx emulation, error messages, power management, vendor-defined); atomic operations.
  • Routing information: address, ID or implicit routing (Chapter 4).
  • Split transactions: non-posted requests carry a Requester ID and Tag; completions return them (Chapter 13).
  • Flow control: credit-based, per type (Posted, Non-Posted, Completion), separately for headers and data (data credits in units of 16 bytes). A transmitter must not send a TLP unless the receiver has advertised enough credits (Chapter 16).
  • Ordering rules (Chapter 14), traffic classes and virtual channels.
  • End-to-end integrity: optional ECRC; data poisoning (the EP bit).
  • Completion timeout tracking for non-posted requests.

The central concept on the ladder: layered responsibility

The letter writer decides what to say, the counter clerk numbers and seals envelopes and resends torn ones, the van drives them.

Transaction Layer = what and where; Data Link Layer = reliable delivery across one link; Physical Layer = framing and signalling.

In a port, the Transaction Layer has request/completion queues and credit counters; the Data Link Layer has a replay buffer, sequence counters, LCRC generators/checkers and timers; the Physical Layer has the LTSSM, scramblers, encoders, and SerDes.

The Base Specification has separate chapters for each layer, and AER classifies errors by the layer that detects them.

TLPs carry work end to end (hop by hop through Switches); DLLPs and ordered sets are link-local.

An analyzer view groups these: ordered sets and LTSSM in one pane, DLLPs (Ack/Nak/FC) in another, TLPs and transactions in a third. A replay shows as a repeated sequence number after a Nak.

Classify the first error by layer: physical errors point to the channel, Data Link errors to link integrity or retry tuning, Transaction errors to addressing, software, device state or timeouts.

The sixteen questions for "the Data Link Layer's Ack/Nak protocol"

1. What is it?
A link-level retransmission protocol using 12-bit sequence numbers, LCRC, Ack/Nak DLLPs and a replay buffer.
2. Why was it created?
So that bit errors on a high-speed serial link are corrected in hardware without involving software.
3. What problem does it solve?
Makes the link appear lossless to the Transaction Layer despite occasional corruption.
4. What existed before it?
Parallel PCI had parity, reported to software, but no automatic link-level retry.
5. Why is the current design better?
Errors are corrected in microseconds, invisibly, and counted for diagnosis.
6. Who creates it?
The transmitting port's Data Link Layer assigns sequence numbers and LCRC; the receiving port's Data Link Layer generates Ack/Nak.
7. Who consumes it?
The transmitting Data Link Layer consumes Ack/Nak to purge or replay its buffer.
8. Where does it live?
In each port's Data Link Layer hardware; per link.
9. What memory/registers are involved?
The replay buffer (internal memory), NEXT_TRANSMIT_SEQ, ACKD_SEQ, NEXT_RCV_SEQ counters, REPLAY_TIMER, REPLAY_NUM (internal); AER correctable status/mask registers expose the outcomes.
10. What happens before it?
Link reaches L0 and Data Link initialisation (InitFC) completes: DL_Active.
11. What happens after it?
Good TLPs pass to the Transaction Layer in order; credits are returned with UpdateFC.
12. What happens if it is wrong?
Replays, Replay Timer Timeouts, REPLAY_NUM rollover leading to Recovery; protocol errors (fatal) if sequence numbers are inconsistent.
13. What does the protocol analyzer show?
Sequence numbers, Ack/Nak DLLPs, replayed TLPs, Ack latency.
14. What does Linux show?
AER correctable counters in sysfs and kernel log lines naming Bad TLP, Bad DLLP, Replay Timer Timeout, REPLAY_NUM Rollover.
15. What would a validation engineer test?
Error injection (corrupt LCRC, drop Acks), replay timer behaviour, sequence wrap, rollover-triggered retraining.
16. What would a senior engineer suspect when it fails?
Marginal signal integrity (most common), a receiver buffer or Ack scheduling bug, or retimer misbehaviour.

Hardware view

Inside an NVMe SSD controller ASIC, the three layers map onto distinct hardware blocks, often from different design teams or IP vendors:

Where each layer lives in a typical NVMe SSD controller (implementation-dependent)

Replay buffer sizing is a real design constraint: the buffer must hold every TLP sent but not yet acknowledged, which is roughly link bandwidth × Ack round-trip time. Doubling the generation doubles the bytes in flight for the same round-trip time. Receive buffer (credit) sizing similarly determines whether a port can sustain line rate: too few advertised credits and the transmitter stalls waiting for UpdateFC.

On the host side the same blocks exist in the Root Port. In a Switch, each port has its own Physical and Data Link Layers, and the Switch core routes TLPs between ports' Transaction Layer buffers.

Specification view

The PCI Express Base Specification, Revision 6.x/7.0 devotes separate chapters to the Transaction Layer Specification, the Data Link Layer Specification and the Physical Layer Logical Block / Electrical Sub-Block, plus Error Signalling and Logging and Advanced Error Reporting Capability for the error model. Layering is normative in the sense that each layer's required behaviour is specified; how a design partitions logic internally is not.

  • Three layers: Transaction, Data Link, Physical (with logical and electrical sub-blocks).
  • TLP sequence numbers are 12 bits; LCRC is 32 bits; DLLPs carry a 16-bit CRC.
  • DLLP type encodings: Ack 00h, Nak 10h, PM_Enter_L1 20h, PM_Enter_L23 21h, PM_Active_State_Request_L1 23h, PM_Request_Ack 24h, InitFC1/InitFC2/UpdateFC for P, NP, Cpl as tabulated.
  • Flow control uses header and data credits per type; one data credit is 16 bytes (4 DW).
  • Errors are classed as correctable or uncorrectable; uncorrectable as non-fatal or fatal, with severity programmable in AER.

Because Ack/Nak is per link, a TLP crossing a Switch is protected by two independent LCRCs, and nothing at the Data Link Layer protects it while inside the Switch. That is the reason ECRC exists and why it matters more in multi-hop topologies.

Replay buffer and receive buffer sizes; Ack coalescing policy (how many TLPs per Ack); UpdateFC frequency; exactly which physical events a port counts as Receiver Errors beyond those required; whether ECRC is supported.

Flit Mode (Revision 6.0+) reorganises the Data Link Layer: per-TLP sequence numbers and LCRC give way to flit-level sequence, CRC and FEC, and a new TLP header format is used. 10-bit tags, Data Link Features, scaled flow control and some DLLP types were added in later revisions (4.0+). This chapter's packet layouts are non-flit unless stated.

  • The specification does not say how long a replay or Recovery takes in a given product.
  • It does not say that a correctable error rate of N per hour is acceptable; that is a platform or customer policy.
  • Confirm in the specification: the replay timer formula and its dependence on width, MPS and rate; the precise events counted as Receiver Errors; the Flit Mode TLP header layout.

Never assume that a correctable error is harmless (each replay costs bandwidth and latency, and a rising rate predicts failure); never assume an Ack means the data reached its final destination (it means the next port received it); never decode a Flit Mode trace with non-flit header layouts.

Reasoning

  1. Two unrelated problems at two layers. Treat them separately.
  2. Rows 2–5: a physical error on lane 2 produced a Data Link replay. The fix belongs to signal integrity if it repeats. One isolated event is within normal life; a rising rate is not.
  3. Rows 6–8: a perfectly delivered request for an address the device does not implement. The Data Link Layer Acked it (row 7): delivery was fine. The Transaction Layer answered UR (row 8). Look for a driver or tool reading beyond the BAR (for example, a debug script), not at the link.
  4. Layer classification turned one confusing trace into two clear investigations with different owners.

In lspci -vvv, the AER section shows UESta (uncorrectable status), UEMsk, UESvrt (severity), CESta (correctable status) and CEMsk, each as a list of named bits with + or -, for example CESta: RxErr- BadTLP+ BadDLLP- Rollover- Timeout- AdvNonFatalErr-. The names map directly to the layer tables above: RxErr (Physical), BadTLP/BadDLLP/Rollover/Timeout (Data Link), UnsupReq/CmpltTO/UnxCmplt/MalfTLP (Transaction).

Kernel AER log lines have the shape "PCIe Bus Error: severity=Corrected, type=Physical Layer, (Receiver ID)" or "type=Data Link Layer" or "type=Transaction Layer", followed by the device and the error bits. The kernel itself classifies by layer. Version-dependent wording varies across kernel versions.

What Linux cannot show: individual TLPs, DLLPs, sequence numbers, the time of each replay, or the LTSSM path. Status bits are sticky flags, not event logs; counters in sysfs are totals since boot. AER may be owned by platform firmware (firmware-first error handling) rather than the OS, in which case Linux sees fewer details.

Code / pseudocode

The following simulation implements the Data Link Layer's Ack/Nak and replay logic for one direction of one link, with a channel that corrupts TLPs at a chosen probability. It is a teaching model, not a conformant implementation: a burst that makes no progress stands in for the replay timer, every good TLP is acknowledged individually (no Ack coalescing), and sequence wrap edge cases are simplified. It uses zlib.crc32 as a stand-in for LCRC; the real LCRC uses the same CRC-32 polynomial but specific bit ordering and coverage rules you must take from the specification.

#!/usr/bin/env python3
"""Toy model of PCIe Data Link Layer Ack/Nak replay (one direction, one link)."""
import random, zlib

SEQ_MOD = 4096                     # 12-bit sequence numbers

class Transmitter:
    def __init__(self):
        self.next_seq = 0
        self.replay = []               # list of (seq, payload, lcrc) awaiting Ack
    def send(self, payload: bytes):
        seq = self.next_seq
        self.next_seq = (self.next_seq + 1) % SEQ_MOD
        frame = (seq, payload, zlib.crc32(seq.to_bytes(2, "big") + payload))
        self.replay.append(frame)
        return frame
    def on_ack(self, seq):
        self.replay = [f for f in self.replay if (seq - f[0]) % SEQ_MOD >= SEQ_MOD // 2]
    def on_nak(self, seq):
        self.on_ack(seq)               # everything up to seq is acknowledged
        return list(self.replay)       # replay the rest, in order

class Receiver:
    def __init__(self):
        self.next_rcv = 0
        self.delivered, self.bad = [], 0
        self.nak_pending = False
    def receive(self, frame):
        seq, payload, lcrc = frame
        if zlib.crc32(seq.to_bytes(2, "big") + payload) != lcrc:
            self.bad += 1              # "Bad TLP": discard, schedule Nak once
            if not self.nak_pending:
                self.nak_pending = True
                return ("NAK", (self.next_rcv - 1) % SEQ_MOD)
            return None
        if seq != self.next_rcv:       # out of sequence after a lost TLP: discard
            return None
        self.delivered.append(payload)
        self.next_rcv = (self.next_rcv + 1) % SEQ_MOD
        self.nak_pending = False
        return ("ACK", seq)

def channel(frame, p_err, rng):
    seq, payload, lcrc = frame
    if rng.random() < p_err:
        payload = bytes([payload[0] ^ 0x01]) + payload[1:]    # flip one bit
    return (seq, payload, lcrc)

def run(n=2000, p_err=0.01, window=8, seed=1):
    """Send n TLPs with at most 'window' unacknowledged. A Nak, or a burst that makes no
    progress (standing in for the replay timer), replays every unacknowledged TLP in order."""
    rng, tx, rx = random.Random(seed), Transmitter(), Receiver()
    next_new, transmissions, replayed, naks, timeouts = 0, 0, 0, 0, 0
    resend = []
    while len(rx.delivered) < n:
        burst, resend = resend, []
        while len(tx.replay) < window and next_new < n:
            burst.append(tx.send(next_new.to_bytes(4, "big")))
            next_new += 1
        progress, nak_seen = False, False
        for frame in burst:
            transmissions += 1
            reply = rx.receive(channel(frame, p_err, rng))
            if reply and reply[0] == "ACK":
                tx.on_ack(reply[1])
                progress = True
            elif reply and reply[0] == "NAK":
                tx.on_ack(reply[1])        # a Nak also acknowledges up to its sequence number
                nak_seen = True
        if nak_seen or (not progress and tx.replay):
            naks += nak_seen
            timeouts += not nak_seen
            resend = list(tx.replay)
            replayed += len(resend)
    ok = rx.delivered == [i.to_bytes(4, "big") for i in range(n)]
    print(f"p_err={p_err:<6} TLPs={n} transmissions={transmissions} "
          f"overhead={transmissions / n - 1:6.1%} replayed={replayed} naks={naks} "
          f"timeouts={timeouts} bad_tlp={rx.bad} in-order-and-complete={ok}")

if __name__ == "__main__":
    for p in (0.0, 0.001, 0.01, 0.05):
        run(p_err=p)

Run it and watch the cost of errors: transmissions grow faster than the error rate because every Nak replays all unacknowledged TLPs after the bad one. Delivery stays complete and in order. That is the Data Link Layer's promise.

Worked example

Scenario. A validation engineer reports: "Under heavy write load, the lab SSD occasionally logs AER correctable errors: BadTLP and Rollover, at the SSD; RxErr at the SSD. Throughput dips by 30 % for a few milliseconds each time. No NVMe errors."

  1. Classify by layer. RxErr: Physical. BadTLP and Rollover: Data Link. Detected at the SSD: the SSD's receiver saw bad data, so the problem is on the host→device direction of the link.
  2. Interpret Rollover. Several consecutive replays failed, so the Root Port's Data Link Layer forced the link into Recovery: that explains milliseconds of reduced throughput.
  3. Why heavy write load? Writes mean the SSD fetches lots of data from host memory: the host→device direction carries large completions (CplD), saturating that direction. More bits on the marginal direction, more chances for error, and possibly more crosstalk or supply noise.
  4. Where next? Physical evidence for the downstream direction: which lane (Lane Error Status if implemented, or an analyzer with per-lane error reporting), lane margining from the SSD's receiver, Root Port transmitter equalisation settings, the connector.
  5. What not to do. Do not open an NVMe firmware bug: NVMe never saw an error; the link layer did its job.

Common mistakes

  • Calling DLLPs "small TLPs". They are a different layer's packets and never leave the link.
  • Believing an Ack confirms end-to-end delivery. It confirms delivery to the neighbour port.
  • Assuming Unsupported Request is a link problem. It is a Transaction Layer response to an address or request type.
  • Ignoring which side detected an error. The detecting receiver identifies the bad direction.
  • Mixing sequence numbers of the two directions in trace analysis.
  • Thinking credits are end to end. They are per link (a Switch has its own credits on each port).
  • Decoding a Flit Mode capture with non-flit framing expectations.

Errors cascade upward: physical corruption creates Data Link replays; persistent replays create Recovery; a long Recovery or link-down creates Transaction Layer Completion Timeouts; those create NVMe command timeouts and driver resets. The first error in time is usually the lowest layer. Find it before reasoning about the rest (Chapter 47).

Senior engineer insight

A senior engineer reads an error report and immediately annotates each line with a layer and a direction. "BadTLP at the Root Port" means the device→host direction is corrupting; "BadTLP at the SSD" means host→device. Two reports that look identical can point in opposite directions.

They also treat correctable errors as early warnings, not noise. Each replay costs bandwidth and adds latency jitter to NVMe commands; a slowly rising rate on a fleet is how connectors, retimers and boards fail months before they fail outright. Good fleets trend AER correctable counters per link.

Finally, they remember that the layers are a model. Some failures straddle them: an elastic buffer overflow due to clocking mismatch is physical but surfaces as Bad TLPs; a credit leak is Transaction Layer but looks like a link stall. The model tells you where to start, not where to stop.

Questions

  1. In the simulation, why does overhead grow faster than the error probability?
  2. If RxErr is non-zero but BadTLP is zero on a port, what could that mean?

Challenge

Modify the simulator so the receiver sends one Ack per 4 good TLPs (Ack coalescing). How does the replay count change at 1 % errors? Why do real implementations coalesce Acks anyway?

Hint

A Nak replays everything not yet acknowledged; with coalescing, more TLPs are unacknowledged at any moment.

Solution

1: Each Nak replays every TLP after the last good one, so one corruption costs several transmissions; and replays can themselves be corrupted. 2: Physical errors occurred outside TLPs (for example during DLLPs, idle, or ordered sets), or were corrected before affecting a TLP; or the port counts additional events as Receiver Errors (implementation-dependent). 3: The Root Port receives device→host traffic, so its RxErr and BadTLP counters rise; the SSD would see Replay Timer Timeouts only if Acks were lost, which is the other direction. Challenge: replays per error rise with coalescing; implementations coalesce because Acks consume bandwidth in the opposite direction and the specification lets a receiver acknowledge cumulatively within timing limits.

What a senior engineer notices

  • Whether correctable errors are masked (CEMsk) so that counters stay at zero even though errors occur.
  • Whether firmware-first error handling hides details from the OS.
  • Whether counts correlate with a particular boot, workload or time of day.

Failure variants

  • No AER capability on a device: older or simple devices; rely on the parent port.
  • Counters always zero although the kernel log shows AER messages: counters exist only on newer kernels or for certain ports.
  • Fatal errors present: the device may have been reset; correlate with the kernel log before drawing conclusions.

Extension

Extend the simulator with a second link and a Switch that forwards TLPs, each link with its own sequence numbers, and show that a corruption on link 2 never causes a replay on link 1.

  3. Why does the Nak carry the sequence number of the last good TLP rather than the bad one?

Answers

1: MWr – Transaction/Transaction; Ack – Data Link/Data Link; UpdateFC – Data Link (with Transaction Layer credit information)/Data Link → Transaction credit counters; TS1 – Physical/Physical; SKP – Physical/Physical; CplD – Transaction/Transaction; PM_Enter_L1 – Data Link (on behalf of power management)/Data Link. 2: Two links, so two LCRC generations and two checks; one ECRC generation at the requester and one check at the final completer. 3: The bad TLP's sequence number might itself be corrupted, and the cumulative "last good" number tells the transmitter exactly where to restart. 4: Transaction; Physical; Transaction; Data Link (link down); Transaction. 5: Acks and UpdateFCs for the data travel host→device, and the device's read requests' completions do not, but doorbells, command fetch completions and those DLLPs do; a marginal host→device direction causes lost Acks (Replay Timer Timeouts at the SSD) and replays of host TLPs.

    • A fatal error and link-down
    • A software interrupt to the NVMe driver
    • Dropping the TLP
    • The link to be retrained (Recovery), reported as a correctable error
    Answer and reasoning

    The Data Link Layer requests retraining; AER reports REPLAY_NUM Rollover as correctable.

  6. What does the Fmt/Type pair 011b / 0 0000b denote in non-flit mode?

    • MWr with 4 DW header (64-bit address)
    • MRd with 3 DW header

    • CfgWr0
    Answer and reasoning

    Fmt 011b = 4 DW header with data; Type 0 0000b = memory request: MWr64.

  7. Why is ECRC more important in a topology with Switches?

    Model answer

    LCRC protects each link separately; inside a Switch the TLP is unprotected by the link layer. ECRC covers the TLP from requester to completer across all hops.

  8. BadTLP is logged at the Root Port. Which direction of the link is suspect?

    Model answer

    Device→host (upstream): the Root Port's receiver detected the corruption.

  9. Name the three main jobs of the Physical Layer's logical sub-block.

    Model answer

    Any three of: framing, byte striping and deskew, scrambling/encoding, ordered sets, the LTSSM (training, speed/width, power states).

Interview questions

  1. (Beginner) Name the three PCIe layers and one job of each.

    Model answer

    Transaction: build/route TLPs and manage credits. Data Link: sequence numbers, LCRC and Ack/Nak replay. Physical: framing, encoding and link training.

  2. (Beginner) What is the difference between a TLP and a DLLP?

    Model answer

    A TLP carries a transaction (request, completion, message) and can be routed across many links; a DLLP carries link management (Ack/Nak, credits, PM) and is consumed by the neighbour port.

  3. (Intermediate) Walk through what happens when a TLP is corrupted on the wire.

    Model answer

    Receiver's LCRC check fails → Bad TLP, discard, Nak with last good sequence; transmitter replays from its buffer all TLPs after that number; receiver accepts and Acks. If no Ack/Nak arrives, the replay timer forces a replay. After repeated replays, REPLAY_NUM rolls over and the link retrains.

  4. (Intermediate) Why must credits be advertised before TLPs flow?

    Model answer

    PCIe is lossless: a receiver must never be sent a TLP it cannot buffer. InitFC exchange tells each transmitter how much buffer space exists per type; UpdateFC replenishes as buffers drain. Without credits, sending would risk Receiver Overflow, a fatal error.

  5. (Senior) Completion Timeouts appear on the Root Port for an SSD, with no correctable errors anywhere. What do you consider?

    Model answer

    The link delivered requests (no link-layer errors), so the completer did not respond in time: device firmware hang, device internally reset, a function-level reset in progress, a Switch internal drop, power-state exit delays exceeding the timeout, or a completion timeout value set too short. Check device state (NVMe CSTS, whether config reads succeed), link state at the time, completion timeout configuration (Device Control 2), and capture to see whether completions arrive late (then Unexpected Completion) or never.

  6. (Senior) How does Flit Mode change your trace analysis habits?

    Model answer

    Retry is per flit, not per TLP, so a single error may replay several small TLPs at once; there are no per-TLP LCRC or framing tokens; TLP headers use a different format; Ack/credit information is embedded in flits; FEC corrections occur silently and may only appear in counters. Analyzer decoding must be set for Flit Mode, and error accounting should consider FEC-corrected versus CRC-failed flits.
