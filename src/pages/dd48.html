This module opens the NVMe Management Interface (NVMe-MI) message itself: the bytes of a request and a response, command slots, More Processing Required, the integrity check, tunnelled admin commands without Physical Region Pages, lockdown on the management path, and the scheduling problem of a slow shared bus. It ends with a cross-path ambiguity where the host and the Baseboard Management Controller (BMC) quietly steal each other's health events.

Orientation

Chapter 63 separated the three management paths — Management Component Transport Protocol (MCTP) over System Management Bus (SMBus) / Inter-Integrated Circuit (I2C), MCTP over PCI Express (PCIe) Vendor Defined Messages (VDMs), and in-band NVMe-MI Send/Receive — and walked through discovery, health polling, Vital Product Data (VPD), firmware update and enclosure management, with a simplified packetiser. This module goes one layer down into the NVMe-MI message format and one layer up into fleet behaviour: how a management controller schedules a shared bus, how long operations report progress, how lockdown appears on the management path, and how concurrent requesters interfere.

Read NVMe-MI first. You also need SMART / Health (the data health polls summarise), TLP Header Anatomy (Message TLPs), Admin Commands (what gets tunnelled), and PCIe Reset (why VDM paths disappear). Related modules: SMART and Health, Reset. Next: NVMe Boot.

Kid story

In a hospital, every patient's bed has a little monitor. Doctors come to the bed to treat the patient — that is the main job. But the nurses at the central station watch every monitor through a separate cable, all day and all night, even when no doctor is around.

The nurse can ask a monitor short questions: "Temperature? Anything changed since I last asked?" The monitor answers in a tiny note with a seal on it, so the nurse knows the note was not smudged on the way. If the nurse asks for something that takes a while, the monitor first says "Busy — ask me again in two seconds," and then sends the real answer.

There is one tricky rule. When anyone asks "anything changed?", the monitor forgets the change after answering. If a doctor at the bed asks first, the nurse at the station hears "nothing changed" — even though something did.

A patient monitor only observes. NVMe-MI can also act: it can tunnel admin commands that format, sanitize or update firmware. That is why management access is a security boundary and why lockdown applies per interface.

The central concept on the ladder: a sealed, slotted management exchange

The nurse asks the bedside monitor a question on a separate cable; the answer comes back sealed; if it takes time, the monitor says "busy" first.

A requester sends an NVMe-MI request into one of two command slots; the endpoint answers once (or with MPR, then once more); a CRC-32C MIC protects the message.

Drive firmware runs an MCTP stack and an NVMe-MI processor sharing sensors, SMART counters and firmware slots with the controller; the BMC drives SMBus wires or PCIe VDMs.

NVMe-MI 2.2 defines messages, slots, statuses and data structures; DMTF DSP0236/0237/0238 define MCTP and its bindings; Base 2.4 defines in-band carriers, tunnelled commands and lockdown.

Request → (MPR →) response, matched by MCTP tag and NVMe-MI slot; no ordering against host I/O; Control Primitives bypass busy slots.

PCIe analyzer: small MsgD TLPs from Requester 0x0009 and 0x0100 interleaved with I/O; payload starts 84h; SMBus needs a two-wire analyzer.

Check path first (link up? bus hung?), then integrity (MIC), then slot and MPR handling in the requester, then policy (Access Denied), then concurrency (who cleared the flags?).

These are consistent with each other and with the course's earlier uncertainty notes; still read them in NVMe-MI 2.2 and DSP0239 before shipping a decoder.

This module does not give: opcodes for Controller Health Status Poll, VPD Read/Write, SES Send/Receive and Reset; field encodings of composite temperature and the change-flag bits; MCTP header bit positions; VDM header values (vendor ID, routing); SMBus addresses; the maximum NVMe-MI message size; reset behaviour of in-flight management messages. The specifications also do not define how a BMC schedules polls or exposes data to operators (Redfish and IPMI are above NVMe-MI).

Never assume: one requester; a side-effect-free poll; that MPR means failure; that out-of-band and in-band lockdown policies match; that a tunnelled command's data appears in host memory; that EIDs survive hot-plug.

SMBus is open-drain and shared: a device holding the data line low hangs the segment for every drive behind that multiplexer channel, and bus recovery is a platform function. Bus time is the scarce resource: at 100 kHz one byte with acknowledge costs about 90 µs, so a 64-byte packet is several milliseconds and a 4 MiB firmware image is minutes.

Internal and unobservable: how the drive prioritises management firmware against I/O firmware (a long management task can add I/O latency on some designs), whether the management endpoint shares a processor core with the flash translation layer, and how it buffers multi-packet messages.

  • Matching: MCTP tag + Tag Owner + EID pair for packets; slot bit for NVMe-MI commands.
  • Ordering: none between management commands and host I/O; none between two slots.
  • Completion: exactly one final response per request; MPR is interim.
  • Errors: MIC failure → message discarded, requester times out; NVMe-MI status for message-level errors (Invalid Parameter, Access Denied …); for tunnelled admin commands, the NVMe completion status is inside the response.
  • Tunnelled data: the admin header carries a data offset and data length instead of PRPs; large data is read in pieces by offset. Derived from the libnvme admin header layout.

Why it is ambiguous. From the BMC's side alone, row 6 has two explanations: (a) the change flag was set and consumed by another requester; (b) the device never set a change flag for this crossing (for example, the flag covers a different threshold, or the drive's firmware does not report it). Labs

Safe lab All four labs are paper, simulation or analysis. Optional hardware steps are read-only.

Beginner lab — decode messages by hand

Objective: decode the NVMe-MI bytes in Trace A–C. Prerequisites: the byte layout table. Setup: paper.

Procedure: for payloads (i) 84 08 00 00 01 …, (ii) 84 91 00 00 01 00 19 00, (iii) 84 90 00 00 07 00 00 00, give request/response, message type, slot, opcode or status, and meaning. Questions: why does 84h appear in every message? What would 04h in byte 0 mean? Expected reasoning: split NMP into bit 7, bits 6:3 and bit 0.

Solution

(i) 08h = 0 · 0001 · 0: request, MI Command, slot 0; opcode 01h = subsystem health status poll. (ii) 91h = 1 · 0010 · 1: response, admin message, slot 1; status 01h MPR with MPRT 0019h = 2.5 s. (iii) 90h: response, admin, slot 0; status 07h Access Denied. 84h = MCTP message type 04h (NVMe) with the Integrity Check bit set, meaning a MIC follows; 04h alone would mean no MIC — check whether NVMe-MI permits that.

Extension: write the request bytes for Configuration Get of the SMBus frequency (identifier 01h) on port 0, leaving the NMD0 field layout to be confirmed in NVMe-MI 2.2.

Intermediate lab — build and verify NVMe-MI messages

Objective: generate requests, check MICs and decode responses including MPR. Prerequisites: beginner lab; the CRC-32C code of Chapter 63. Setup: save as mi_msg.py; run python3 mi_msg.py.

#!/usr/bin/env python3
"""mi_msg.py - build and check NVMe-MI messages (the payload of MCTP).
Byte layout follows the libnvme 1.16.2 structures (nvme/mi.h): byte 0 = MCTP
message type 04h with the Integrity Check bit (80h) set; byte 1 = NMP
(bit 7 ROR, bits 6:3 NVMe-MI message type, bit 0 command slot); then the
command header; MIC = CRC-32C over everything before it, little-endian.
Confirm every field against NVMe-MI 2.2 before using this for real devices."""
import struct

def crc32c(data):
    crc = 0xFFFFFFFF
    for b in data:
        crc ^= b
        for _ in range(8):
            crc = (crc >> 1) ^ (0x82F63B78 if crc & 1 else 0)
    return crc ^ 0xFFFFFFFF

MT = {0: "Control Primitive", 1: "MI Command", 2: "NVMe Admin Command", 4: "PCIe Command", 5: "Async Event"}
STATUS = {0x00: "Success", 0x01: "More Processing Required", 0x02: "Internal Error",
          0x03: "Invalid Command Opcode", 0x04: "Invalid Parameter", 0x05: "Invalid Command Size",
          0x06: "Invalid Command Input Data Size", 0x07: "Access Denied"}

def nmp(ror, mtype, slot):
    return (ror << 7) | (mtype << 3) | (slot & 1)

def with_mic(body):
    return body + struct.pack("<I", crc32c(body))

def mi_request(opcode, nmd0, nmd1, slot=0, data=b""):
    body = bytes([0x84, nmp(0, 1, slot), 0, 0, opcode, 0, 0, 0]) + struct.pack("<II", nmd0, nmd1) + data
    return with_mic(body)

def decode_response(msg, expect_slot):
    body, (mic,) = msg[:-4], struct.unpack("<I", msg[-4:])
    if crc32c(body) != mic:
        return "MIC mismatch: discard the message"
    if body[0] != 0x84:
        return f"not an NVMe-MI message with IC set (type byte {body[0]:02X}h)"
    ror, mtype, slot = body[1] >> 7, (body[1] >> 3) & 0xF, body[1] & 1
    if ror != 1 or slot != expect_slot:
        return f"unexpected ROR={ror} or slot={slot}"
    status = body[4]
    text = f"{MT.get(mtype, '?')} response, slot {slot}, status {status:02X}h {STATUS.get(status, '(see spec)')}"
    if status == 0x01:
        (mprt,) = struct.unpack_from("<H", body, 6)
        text += f", device asks for up to {mprt * 100} ms more"
    elif status == 0x00 and len(body) >= 16:
        nss, sw, ctemp, pdlu, ccs = struct.unpack_from("<BBBBH", body, 8)
        text += f"; NSS={nss:02X}h SW={sw:02X}h CTEMP raw={ctemp} PDLU={pdlu}% CCS={ccs:04X}h"
    return text

def hexs(b):
    return " ".join(f"{x:02X}" for x in b)

if __name__ == "__main__":
    # NVM Subsystem Health Status Poll (opcode 01h per libnvme), clear-status bit 31 of NMD1 set

Procedure: (1) confirm the request bytes match Trace A; (2) build a Control Primitive Get State (type 0, opcode 03h) for slot 1; (3) corrupt one byte of each request and confirm the MIC catches it. Questions: why does the MIC cover the 84h byte? Which corruption would the MIC not catch? Expected reasoning: integrity covers the whole message as delivered to NVMe-MI.

Solution

(2) bytes([0x84, nmp(0, 0, 1), 0, 0, 0x03, …]) plus MIC; the remaining Control Primitive fields must come from the specification. The MIC covers the type byte so a corrupted IC bit or message type is detected. CRC-32C detects all burst errors up to 32 bits and most others, but not deliberate modification with a recomputed CRC (tampering), nor a well-formed message sent to the wrong slot or controller — semantic checks belong to the requester.

Advanced lab — budget a shared SMBus segment

Objective: quantify the trade-off between firmware-update speed and health-poll latency on a slow bus. Prerequisites: Chapter 63 worked example. Setup: save as smbus_budget.py; run it.

#!/usr/bin/env python3
"""smbus_budget.py - one SMBus segment shared by health polls of 24 drives and an
out-of-band firmware download to one of them. The bus serves one message at a
time (no pre-emption inside a message). Bus timing: about 90 us per byte at
100 kHz (9 clocks per byte incl. ACK); MCTP packets carry up to 64 payload bytes
plus about 8 bytes of SMBus/MCTP framing and PEC. All numbers illustrative."""
import math

BYTE_US = 90.0

def bus_us(payload):                          # one MCTP message on SMBus
    packets = max(1, math.ceil(payload / 64))
    return (payload + 8 * packets) * BYTE_US

def simulate(chunk, image=4 << 20, drives=24, period_s=5.0, horizon_s=600.0, fw_dev_ms=15.0):
    poll_bus = bus_us(20) + bus_us(32)         # request + response
    # each drive polled every period, staggered evenly
    polls = sorted((d * period_s / drives + k * period_s, d)
                   for d in range(drives) for k in range(int(horizon_s / period_s)))
    t, pi, sent, worst, fw_next, fw_done = 0.0, 0, 0, 0.0, 0.0, None
    while pi < len(polls) or sent < image:
        start_poll = max(t, polls[pi][0]) if pi < len(polls) else math.inf
        start_fw = max(t, fw_next) if sent < image else math.inf
        if start_fw < start_poll:                         # ties go to the poll
            n = min(chunk, image - sent)
            t = start_fw + (bus_us(n + 64) + bus_us(24)) / 1e6   # FW Image Download + response
            sent += n
            fw_next = t + fw_dev_ms / 1e3                 # drive writes the chunk; bus is free
            if sent >= image:
                fw_done = t
        else:
            t = start_poll + poll_bus / 1e6
            worst = max(worst, t - polls[pi][0])
            pi += 1
    return fw_done, worst

if __name__ == "__main__":
    print("24 drives polled every 5 s on one 100 kHz segment; 4 MiB image to one drive")
    for chunk in (512, 4096, 32768, 262144):
        done, worst = simulate(chunk)
        print(f"  chunk {chunk:6d} B: firmware transfer {done/60:5.1f} min, worst poll delay {worst*1000:8.1f} ms")

Expected output (deterministic):

24 drives polled every 5 s on one 100 kHz segment; 4 MiB image to one drive
  chunk    512 B: firmware transfer  10.4 min, worst poll delay     62.9 ms
  chunk   4096 B: firmware transfer   7.5 min, worst poll delay    429.7 ms
  chunk  32768 B: firmware transfer   7.3 min, worst poll delay   3331.4 ms
  chunk 262144 B: firmware transfer   7.3 min, worst poll delay  26548.1 ms

Procedure: explain the trend; change the bus to 400 kHz (BYTE_US = 22.5); find the largest chunk keeping worst poll delay under 1 s at each speed. Questions: why do large chunks barely shorten the transfer? Why is a 26 s poll delay dangerous? Expected reasoning: a message is not pre-emptible; per-chunk overhead is small once the device's write time is amortised.

Solution

Small chunks pay the device's 15 ms write time per chunk (8,192 × 15 ms ≈ 2 min of idle bus with 512-byte chunks); beyond about 4 KiB the bytes dominate and the transfer approaches the raw ≈ 7 min. A poll stuck behind a 256 KiB message waits up to 26 s — five poll periods — so a failing drive's alarm is delayed and the BMC may declare other drives unresponsive. At 400 kHz delays shrink four-fold. Practical policy: chunk around 4 KiB on SMBus (also check the endpoint's maximum message size in NVMe-MI 2.2), prefer VDM or in-band for images, and give polls priority between chunks.

Extension: add a second segment and a per-segment scheduler; update two drives in parallel on different segments.

Senior forensic lab — 0.3% of drives "missing" from the BMC

Objective: localise a fleet symptom using grouping and path separation. Prerequisites: Chapter 63 debugging; Root Cause, Ambiguity and Forensic Reporting.

Setup (synthetic evidence): 40,000 servers, 24 drives each; 2,880 drive-days of "not present" in the BMC, all healthy in the OS. Grouping: 96% on platform P2; on P2, 91% in slots 16–23; drive firmware spread evenly; BMC build B7 only (B6 had none). On affected drives, FRU reads directly over SMBus succeed; MCTP Get Endpoint ID fails. Events start within 2 s of host warm resets 70% of the time.

Procedure: state hypotheses per layer (wiring, SMBus mux, MCTP EID assignment, NVMe-MI endpoint, BMC software); use the evidence to accept or reject each; propose the decisive experiment. Questions: what does "FRU read works, MCTP fails" eliminate? Why does the reset correlation matter?

Solution

FRU reads succeeding over the same SMBus segment eliminate wiring, multiplexer and bus-hang causes. Even firmware distribution makes a drive defect unlikely. Concentration on B7, P2 and slots 16–23 (one multiplexer channel on P2) plus reset correlation points at BMC software: B7 likely re-runs MCTP discovery on host reset and loses or duplicates EID assignments on that channel (for example a race with the drive's endpoint re-initialising after a reset). Decisive experiment: on a P2 lab system, run B6 and B7 alternately with scripted warm resets and an SMBus analyzer on channel 3; capture Set Endpoint ID exchanges. Confidence before the experiment: medium; the fix and regression test follow the capture.

Extension: write the operator-facing note explaining why the drives are healthy despite the dashboard.

Interview

Beginner

  1. What is a management endpoint?

    Model answer

    The MCTP endpoint in the subsystem that processes NVMe-MI messages and forwards tunnelled admin commands to a controller.

  2. Name the three management paths.

    Model answer

    MCTP over SMBus/I2C, MCTP over PCIe VDM, and in-band NVMe-MI Send/Receive.

  3. What does the MIC protect?

    Model answer

    The whole NVMe-MI message, end to end, with CRC-32C.

  4. Where does a tunnelled Get Log Page's data go?

    Model answer

    Into the response message to the requester; not into host memory.

  5. Why is out-of-band management needed at all?

    Model answer

    To monitor and manage drives when the host OS is absent, crashed or not trusted.

Intermediate

  1. Decode NMP 89h.

    Model answer

    Response, MI Command message type, slot 1.

  2. Why two command slots?

    Model answer

    So two requests (or a requester and a Control Primitive) can coexist while one command is busy.

  3. How should a requester handle MPR?

    Model answer

    Keep the tag and slot, wait up to the stated time, accept the final response; never resend.

  4. Why can two pollers interfere?

    Model answer

    Polls with clear consume change indications for everyone.

  5. What does 84h in byte 0 mean?

    Model answer

    MCTP message type 04h (NVMe) with the Integrity Check bit: a MIC follows.

Advanced

  1. Design a BMC polling policy for 24 drives on one 100 kHz segment.

    Model answer

    Staggered polls, one clearing owner, priority over bulk transfers, chunked updates around 4 KiB, VDM or in-band for images, threshold-based alerts.

  2. How would you validate reset interaction?

    Model answer

    Continuous polls and MPR operations on each path while injecting controller reset, FLR, subsystem reset, hot reset and link disable; check recovery, no false alerts and specification-conformant handling of in-flight messages.

  3. Status 07h on the BMC, success in-band. Bug?

    Model answer

    Probably intended per-interface lockdown; confirm configuration before filing.

  4. How is tunnelled data sized without PRPs?

    Model answer

    The admin message carries data offset and length; large data is read in offset pieces within the endpoint's message limits.

  5. When is MIC not enough?

    Model answer

    Against tampering and against well-formed but wrong requests; requesters must validate lengths and identities, and use authentication where supported.

Senior

  1. What management security policy would you set for a cloud fleet?

    Model answer

    Lock destructive admin commands out-of-band, restrict in-band NVMe-MI to privileged agents, authenticate the BMC path where supported, audit tunnelled commands, keep VPD read-only in the field.

  2. A dashboard shows wrong temperatures. Debug chain?

    Model answer

    Dashboard → Redfish/BMC software → NVMe-MI decode (encoding) → endpoint → sensor; compare with in-band SMART at aligned times.

  3. Should out-of-band firmware update be the default?

    Model answer

    Only via VDM or with host coordination; SMBus is recovery-only because of time and poll starvation.

  4. How do you keep host and BMC from fighting?

    Model answer

    Single owner per function (polling, updates), documented clear semantics, lockdown per interface, and correlated logs with synchronised clocks.

  5. What 2026 changes might affect NVMe-MI tooling?

    Model answer

    Manageability features in the 2.4 set such as voltage monitoring and lockdown persistence; read the Revision Changes document before updating decoders.

Quiz

  1. Byte 1 = 11h in a request means:

    • MI Command, slot 1
    • Control Primitive, slot 0
    • NVMe Admin Command, slot 1
    • Response, slot 1
    Answer and reasoning

    11h = 0 · 0010 · 1: request, type 2 (admin), slot 1.

  2. A response with status 01h means:

    • Internal error
    • More Processing Required; the final response follows
    • Invalid opcode
    • Resend the request
    Answer and reasoning

    MPR is interim, with a time estimate.

  3. Which check is end-to-end for an NVMe-MI message?

    • SMBus PEC
    • PCIe LCRC
    • MCTP sequence number
    • MIC
    Answer and reasoning

    PEC and LCRC are per hop; sequence numbers detect some losses.

  4. Status 07h on a tunnelled Format NVM most likely indicates:

    • Lockdown prohibits it on this interface
    • Bad MIC
    • Slot busy
    • Link down
    Answer and reasoning

    Access Denied relates to Command and Feature Lockdown per libnvme's description.

  5. On SMBus, why can a large firmware chunk hurt health monitoring?

    • It changes EIDs
    • Messages are not pre-emptible, so polls wait behind it
    • It disables PEC
    • It resets the endpoint
    Answer and reasoning

    The bus serves one message at a time.

  6. Which data structure type does NMD0 = 02000000h request?

    • Subsystem information
    • Port information
    • Controller list
    • Controller information
    Answer and reasoning

    Type 02h in bits 31:24 (libnvme).

  7. Why did the BMC in Trace D miss the event?

    Model answer

    An in-band agent polled with clear first and consumed the change flag; the BMC alerted only on flags.

  8. Why is FRU-read success evidence in a "missing drive" case?

    Model answer

    It proves the segment, multiplexer and drive's two-wire interface work, moving suspicion to MCTP/NVMe-MI software.

Teach-back

Explain to three audiences, then compare with the models.

To a child — model

"Nurses watch every bed's monitor through a separate cable. They ask short questions and get sealed answers. If a question takes long, the monitor says 'busy, wait'. If someone else asks 'anything changed?' first, the nurse may hear 'no' — so only one person should ask that question."

To a junior engineer — model

"Every NVMe-MI message starts 84h, then the NMP byte: request/response, message type, slot. MI commands read data structures and poll health; admin messages tunnel admin commands with offset and length instead of PRPs. A CRC-32C MIC ends the message. MPR means wait, not fail. Over SMBus everything is slow, so schedule it."

To a senior engineer — model

"NVMe-MI is a second control plane with its own concurrency (slots, multiple requesters, clear-on-read), its own timing contract (MPR) and its own policy surface (per-interface lockdown). Fleet incidents come from requester logic and ownership, not the drive: who clears, who retries, who updates over which bus. Design ownership and correlation first."
