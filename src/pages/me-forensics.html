How a senior engineer turns a failure into a defensible root cause: the root-cause template, the language of evidence, cases built to be ambiguous, failures that cross layers, deciding what to capture, test-matrix design, reproduction and regression engineering, the confidence model and the forensic report — finished with a graded report lab on a broken trace.

Why this part exists

Finding a cause is easy. Every failing system offers a dozen things that look wrong. Finding the cause — the mechanism whose removal prevents the failure — and proving it to a sceptical reviewer is the skill that separates a senior engineer from a capable one. This part teaches that skill as a set of disciplines you can practise.

It builds directly on Debugging Methodology (the debugging chain and the first abnormal event) and on Senior Engineer Thinking (falsification). Where AI + NVMe Protocol Analysis already teaches the large language model (LLM) guardrails, the confidence levels and the report format in depth, this page summarises them and goes further into the forensic side: how humans apply the same rules, how confidence moves as evidence arrives, and how a report is graded.

Learning objectives

  • Fill every heading of the senior root-cause template for a real investigation.
  • Write conclusions as "evidence A supports X; evidence B weakens Y; evidence C is insufficient".
  • Separate two or more initially plausible root causes with discriminating evidence.
  • Localise multi-layer failures: PCIe healthy but NVMe failing, NVMe healthy but PCIe failing, and both healthy with software misuse.
  • Plan evidence escalation from OS logs to hardware signals, knowing what each step makes possible.
  • Design a test matrix that survives combinatorial explosion.
  • Choose a reproduction method and compute how many clean runs justify claiming a fix.
  • Run the eight-step regression procedure.
  • Assign and defend confidence levels, and produce a forensic report in the standard section order.

The story

A cake is missing from the kitchen. Your little brother has chocolate on his face. Case closed? A good detective says: "The chocolate supports the idea that he ate something chocolate. But the cake was lemon. And the dog's bowl has lemon crumbs in it." The detective does not shout the answer. They line up the clues, say which ones point where, and only then decide — and they say how sure they are.

An air-accident investigation board does not publish "pilot error" the day after a crash. It recovers the recorders, builds a timeline, lists every factor that could have contributed, tests each against the evidence, states findings with their degree of certainty, and issues recommendations designed to prevent recurrence — not to assign blame. A storage forensic report has the same skeleton.

Accident boards have months and full wreckage; you often have hours, a partial capture, and a system that has since rebooted and destroyed volatile state. And unlike an aircraft, a storage system can usually be made to fail again on purpose — reproduction is a tool investigators of crashes rarely have, and it is your strongest one.

The filled template

Observed symptom
One Read per day times out after 30 s; it then succeeds without retry ("completion polled").
Evidence
E1–E8 analyzer capture (unfiltered, both directions, 60 s window around the event); E9 host log; E10 PBA snapshot; driver version and kernel version recorded.
First abnormal event
E6: no MSI-X write for vector 3 after a successful CQE at E5.
Expected behaviour
After posting a CQE to a CQ with interrupts enabled, the controller signals the CQ's vector (subject to interrupt coalescing settings, which are off here), unless the vector is masked — in which case the PCIe MSI-X rules say the function sets the pending bit and sends the message when the vector is unmasked. PCI Express Base Specification — MSI-X capability and table
Actual behaviour
CQE written; no interrupt; pending bit set; nothing sent for 30 s.
Affected layer
Interrupt delivery between the PCIe function's MSI-X logic and host interrupt management — not NVMe command processing, which completed in 73 µs.
Candidate causes
(a) device failed to send the MSI-X write (device bug); (b) vector was masked by the host and never unmasked, or unmasked without the device noticing; (c) the write was sent but lost or misrouted (interrupt remapping); (d) the driver missed a delivered interrupt.
Eliminated causes
(c) eliminated: the analyzer sees every TLP on the link and no MSI-X write exists for vector 3 (a write lost after the link would still appear in the capture). (d) eliminated: no interrupt was delivered to miss. (a) weakened: the pending bit is set, which is what a correct device does when the vector is masked.
Most likely cause
(b): the host masked vector 3 during the affinity change (E9) and the unmask path did not result in delivery of the pending message.
Confidence
HIGH. Three independent sources agree (absence on the wire, pending bit, time-coincident affinity change). Not CONFIRMED until a reproduction isolates it.
Additional evidence needed
Capture of the MSI-X table writes during an induced CPU offline (does the host write Mask=1 then Mask=0? does the device send the pending message on unmask?). That single experiment separates "host never unmasked" from "device did not send on unmask".
Fix / workaround
Workaround: disable the daemon's CPU offlining. Fix depends on the experiment: host interrupt-migration code or device unmask handling.
Regression test
Loop: run I/O on every queue while repeatedly offlining and onlining the CPUs that own vectors; assert no completion is found by the timeout handler's poll (count "completion polled" events = 0) over at least 3× the original mean time to failure scaled to the loop rate.

No magic answers: the language of evidence

"The answer is X" teaches nothing and invites nothing. Senior engineers write conclusions in a form that shows the reasoning and can be attacked:

  • Evidence A supports X.
  • Evidence B weakens Y.
  • Evidence C is insufficient (to decide between X and Z).
  • Therefore X, at confidence level L, and here is what would change my mind.

This is not hedging. It is precise: it tells the reader exactly which evidence to re-examine if they disagree.

Rewriting magic answers
Magic answerEvidence-based rewrite
"The SSD is broken.""The SSD fetched the command (E2–E3) and posted a successful CQE (E5), which weakens 'SSD failed to process'. No interrupt followed (E6), and the pending bit is set (E10), which supports 'vector masked'. The SSD's role is insufficiently determined until the unmask experiment."
"It's a PCIe problem.""Correctable error counters on both ports are zero across the window and no Recovery occurs, which weakens a link-quality cause. The UR completion at E9 supports a transaction-layer address problem."
"Firmware bug.""The failure occurs only on firmware 3.1 in 40 of 40 runs and never on 3.0 in 40 runs with identical hardware, which supports a firmware-version cause. Which change in 3.1 is insufficiently determined."
"The analyzer shows the packet was dropped.""The analyzer shows no TLP in the window. Its capture buffer overflowed at 12.4 ms (capture-scope note), so the absence is insufficient evidence of a drop."

Rewrite these three statements in evidence form, inventing nothing beyond what is given: (1) "The driver is wrong — the doorbell value is 1024." (2) "The link is bad because we saw a Recovery." (3) "The namespace is full."

Model answer

(1) "The doorbell write at E4 carries 1024 for a queue created with 1024 entries (Create I/O SQ, E1), which supports an invalid tail value written by the host; whether the driver computed it or a buffer was corrupted is insufficiently determined." (2) "One Recovery occurred at E7 and returned to L0 in 3 µs; no errors are associated and all commands completed. This is insufficient to conclude the link is faulty." (3) "The Write failed with a capacity-related status at E5. Identify Namespace NUSE versus NCAP was not captured, so 'namespace full' is plausible but insufficiently supported; capture Identify Namespace."

Ambiguity training

Real failures rarely point at one cause. The skill is not guessing well; it is knowing what evidence separates the candidates. Build a discrimination table: candidates as rows, observations as columns, and for each cell what that candidate predicts.

Model answer

Lost interrupt vs everything else: read the CQ memory (or note the "completion polled" message) — a CQE present means the controller finished. Completion timeout vs controller failure/deadlock: device AER Uncorrectable Error Status (Completion Timeout bit), readable with lspci -vvv. Queue corruption vs deadlock: the SQE contents and doorbell values in a capture, or a dump of the SQ memory compared with the driver's intended command. Hardest: controller failure vs firmware deadlock. Both look like "fetched, then nothing"; CFS may not be set in either. Separating them needs vendor telemetry, firmware logs or a debug port — which is why evidence escalation exists.

Case B — Data Transfer Error: host or device?

A Write completes with Data Transfer Error. Candidate 1: the host gave a bad buffer address (IOMMU blocks it). Candidate 2: the device generated a bad address from a good PRP (device bug). Both produce an Unsupported Request completion to the device's MRd.

Discriminating evidence

Compare the MRd address in the trace with the PRP entries in the fetched SQE (and PRP list). If the MRd address equals a PRP entry, the device faithfully used what the host provided: candidate 1 is supported; check the host's IOMMU mapping for that IOVA at that time (IOMMU fault log). If the MRd address differs from every PRP-derived address, candidate 2 is supported. This is decisive because the SQE and PRP list are themselves in the capture as CplD payloads — evidence from both sides on the same wire.

Multi-layer failure

Three patterns recur. Learn their fingerprints.

Pattern 1 — PCIe healthy, NVMe fails

#DirTimeTypeFieldsMeaning
1Host→Dev0MWr32SQ1 tail doorbell

Pattern 3 — both healthy, software misuses the interface

No layer violated its specification: NVMe does not order execution of commands, so two overlapping writes in flight have no defined winner. The first abnormal event is in the application's design (issuing overlapping writes without ordering), and the marked row is merely where the consequence becomes visible. Fix in software.

How to separate layers

  1. For each layer, ask "did this layer do what its specification requires, given what it received?"
  2. Walk down from the symptom until a layer's input was correct but its output was not. That layer owns the deviation.
  3. If every layer's output is correct for its input, the defect is in how the layers are used — the contract between them (pattern 3).

The complete layer table is in Debugging by layer.

"What would you capture?" — evidence escalation

A server reboots and the NVMe boot drive is "missing" one boot in fifty. Walk the ladder: what does each level tell you, and where would you stop?

Model answer

OS logs: whether the root port saw a link at all (link-up messages, enumeration logs), whether the device enumerated but the driver failed. If the device never enumerated, NVMe logs are irrelevant (the driver never talked to it). NVMe logs (on good boots): Persistent Event Log may record power cycles or resets; SMART unexpected power-loss count. Analyzer: trigger on PERST# deassertion and capture LTSSM: does Detect find receivers? Does training stall in Polling or Configuration? Hardware signals: PERST# timing relative to power-good and reference clock stability — a too-early PERST# deassert is a classic platform cause. Stop at the level whose evidence identifies the first abnormal event; here it is likely the analyzer or the scope, because the failure precedes any NVMe activity.

At even ten minutes per run (most runs are much longer, and the 24-hour ones dominate), 437,400 runs is over eight years of one machine. This is combinatorial explosion, and it is why nobody runs the full matrix.

How senior engineers choose high-value tests

  • Pairwise (all-pairs) coverage. Most interaction bugs involve two factors. Pairwise selection covers every pair of values with a few dozen configurations instead of hundreds of thousands. (The pairwise generator in Validation Engineering builds such a set.) Pairs are not a guarantee: three-way interactions exist.
  • Risk weighting. Spend runs where failure is likely or costly: the newest firmware, the fastest link, the deepest queues, temperature extremes.
  • Boundaries. MDTS and MDTS + 1, queue full, last LBA, first and last zone. Boundaries find off-by-one bugs that interior values never will.
  • Change-driven selection. A firmware change in the power-management code earns power-state × duration coverage; it does not earn twelve-dimension coverage.
  • Field-failure feedback. Every customer failure adds its configuration to the permanent set.
  • Long-duration on few configurations. Run the 24-hour tests on a handful of risk-ranked configurations, not across the matrix.
  • Separate dimensions that do not interact. If OS and temperature have no plausible interaction for this feature, they need not be crossed.

A firmware fix changes how the controller splits large transfers into internal operations. Choose at most 20 configurations from the matrix above and justify each choice.

Model answer (outline)

Transfer size is the primary dimension: all five values. Cross it with queue depth (1 and 1024: idle and saturated), read/write mix (100/0 and 0/100), and namespace LBA size (512 B and 4 KiB, because splitting is in LBAs). That is 5 × 2 × 2 × 2 = 40; reduce to 20 by pairwise over the last three dimensions (4 combinations instead of 8) per transfer size. Fix the link at the fastest generation and width (most concurrency), power at PS0, firmware at the new version (plus 5 configurations on the previous one as a baseline), one OS/driver. Add one 24-hour run at MDTS, QD 128, 70/30.

How many clean runs justify "fixed"?

If a failure happens with probability p per run, the chance of not seeing it in n independent runs is (1 − p)n. To claim with confidence c that the failure rate has dropped below p:

n ≥ ln(1 − c) / ln(1 − p) ≈ 3 / p for c = 0.95 (the rule of three)
n
number of consecutive clean runs after the fix
p
failure probability per run before the fix (estimated from the reproduction rate)
c
desired confidence that the true failure rate is now below p (0.95 gives the "rule of three")
"""repro_runs.py - how many clean runs before you may claim a fix (Executable, standard library)."""
import math

def runs_needed(p_fail, confidence=0.95):
    """Smallest n with (1 - p_fail)**n <= 1 - confidence."""
    return math.ceil(math.log(1 - confidence) / math.log(1 - p_fail))

def p_seen_at_least_once(p_fail, n):
    return 1 - (1 - p_fail) ** n

for mtbf_runs in (5, 20, 100, 1000):
    p = 1 / mtbf_runs
    print(f"fails 1 in {mtbf_runs:5d} runs: need {runs_needed(p):5d} clean runs for 95 %, "
          f"{runs_needed(p, 0.99):5d} for 99 %   (rule of three: ~{3 * mtbf_runs})")
print("chance a 10-run smoke test sees a 1-in-100 bug:", round(p_seen_at_least_once(0.01, 10), 3))

Running it shows that a 1-in-100 failure needs about 300 clean runs for 95 % confidence, and that a 10-run smoke test has under a 10 % chance of seeing such a bug at all. This calculation assumes runs are independent and the failure rate is stable — state that assumption in your report.

Regression engineering

After every fixed failure, eight steps. Each one guards against a specific way that "fixed" turns out to be false.

  1. Reproduce the original failure — on the unfixed build, so you know your test can see it. A test that never failed proves nothing.
  2. Capture a baseline — trace, logs, metrics of the failing run; this is your "before".
  3. Apply the fix — one change, recorded by version.
  4. Rerun the original test — for enough runs (see the formula above).
  5. Run neighbouring cases — the configurations adjacent in the test matrix (other transfer sizes, other queue depths, other firmware paths touched by the change).
  6. Run stress — fixes often change timing; timing changes uncover other races.
  7. Compare traces — the first abnormal event must be gone, not merely followed by faster recovery; and no new first abnormal event may have appeared elsewhere (see golden-trace diffing).
  8. Record evidence — versions, run counts, captures, and the regression test added to the permanent suite.

Step 7 catches the commonest false fix: a driver change that makes the timeout handler recover faster. The symptom disappears from user view; the first abnormal event is still there in the trace.

Apply the eight steps to the lost-interrupt case in the template section. What is the "neighbouring case" for a fix in interrupt migration?

Model answer

Neighbours: CPU onlining (not just offlining), affinity changes without offlining, vectors shared by several queues, interrupt coalescing enabled, polled queues, and the admin queue's vector 0. Stress: high-rate I/O during continuous affinity churn. Trace comparison: every CQE followed by an MSI-X write or a documented coalescing delay; no "completion polled" events.

LLM guardrails, applied to forensics

The full treatment — failure modes of LLMs on protocol data, architecture, retrieval, grounding, the claim validator — is in AI + NVMe Protocol Analysis. This section summarises the rule and applies it to human investigators too.

An LLM assisting an investigation must never invent packets, timestamps, fields, register values, specification requirements or root causes. Every conclusion links to evidence: EVIDENCE → CLAIM, never CLAIM → imagined evidence.

The uncomfortable truth is that humans break this rule too. "Confirmation capture" — re-running the analyzer until a capture shows what you expected — is CLAIM → evidence. So is reading a log for lines that support your theory and skimming the rest. The forensic discipline is the same for both:

The confidence model in practice

The five confidence levels — CONFIRMED, HIGH, MEDIUM, LOW, UNKNOWN — are defined by evidence criteria in AI + NVMe Protocol Analysis. In brief: CONFIRMED is directly observed or demonstrated by an isolating experiment; HIGH is several independent, causally ordered pieces of evidence with no contradiction; MEDIUM is consistent evidence with alternatives still open; LOW is plausible by mechanism with weak evidence; UNKNOWN is evidence absent.

Why a confidence level is not a probability

A probability ("85 % likely") claims calibration: that over many similar cases, such claims are right 85 % of the time. Unless your organisation has measured that — a labelled history of past investigations — the number is invented precision, and people will multiply it, average it and compare it as if it were real. An ordinal level, defined by evidence, says what kind of support exists and what would move it. Use numbers only when you have formally calculated them (as in the reproduction formula above, which is a real probability under stated assumptions).

In the Case B discrimination above, the MRd address equals PRP1 exactly, and the host IOMMU log shows a fault for that IOVA 4 µs later. What confidence does "the host supplied an unmapped buffer" deserve, and what would make it CONFIRMED?

Model answer

HIGH: two independent sources (wire and host IOMMU log) share the address and are causally ordered. CONFIRMED requires an experiment: for example reproducing with IOMMU tracing that shows the unmap of that IOVA before the command was submitted, or a fix in the buffer lifetime code that removes the failure across the computed number of runs.

The forensic report format

Every report follows the same order so readers always know where to look. The automated generator in AI + NVMe Protocol Analysis produces exactly this structure; the hand-written forensic report does too.

Forensic report lab: the split completion

Safe lab Synthetic trace; written analysis only.

Objective

Given a broken synthetic trace, produce a complete forensic report in the standard section order. Your report is graded on factual accuracy, evidence, reasoning, uncertainty, root cause and recommendations.

Skills

  • Completion rules (Byte Count, Lower Address, Read Completion Boundary).
  • Distinguishing a legal-but-unusual event from an abnormal one.
  • Writing the report.

Hardware and software required

None. Optional: TLP Header Decoder.

Background

Read Completion Rules and PCIe Completions. Key facts: a completer may split a read completion into several Completion TLPs; splits other than at the end must end on a Read Completion Boundary (RCB, 64 bytes on the lab system's root complex); each Completion carries the remaining Byte Count and the Lower Address of its first byte; the requester reassembles by Tag and must accept legal splits.

Input

System configuration (Synthetic example for teaching)

Lab system: Gen4 x4, MPS 256 B, MRRS 512 B, RCB 64 B, IOMMU on. Lab SSD firmware "2.7"; Linux kernel inbox NVMe driver. SQ2 base 0x1_2342_0000, CQ2 base 0x1_2343_0000 (I/O queue pair 2, 1024 entries, MSI-X vector 2). Capture: analyzer, both directions, no filter, 2 s window, no overflow.

Device AER snapshot after the event (Synthetic)

Endpoint 01:00.0 Uncorrectable Error Status: Unexpected Completion = 1. Header Log: a Completion with data, Completer ID = root complex, Requester ID = 0x0100, Tag = 0x33, Byte Count = 224, Lower Address = 0x40.

Further evidence

Over a 1-hour fio run with randomly offset 512-byte buffers, 7,912 of 7,912 Writes whose PRP1 offset is not a multiple of 64 fail with Data Transfer Error; 0 of 39,840 Writes with 64-byte-aligned PRP1 fail. Firmware 2.6 on the same platform: 0 failures in both groups.

Step 1

Build the timeline and mark the first abnormal event. Beware: one row is out of time order.

Step 2

Check every completion for Tag 0x33 against the completion rules: does each Byte Count and Lower Address make sense? Is the split legal?

Step 3

List at least three hypotheses, with supporting and weakening evidence.

Step 4

Write the report in the thirteen-section format.

Questions

  1. Was the root complex's split of the read for Tag 0x33 legal?
  2. Which completion did the device consider unexpected, and why might it?
  3. Is the Data Transfer Error a cause or a consequence?
  4. Why does firmware 2.6 matter?
  5. What would make your root cause CONFIRMED?

Challenge

The device's MRd at row 12 is itself legal? Check: the request starts at offset 0x20 within its page and asks for 512 bytes. Does it cross a 4 KiB boundary? Does it respect MRRS?

Hint

Sum the lengths of rows 13, 14 and 16 (in bytes) and compare with 512. Then follow Byte Count down: 512 → 480 → 224. A requester whose tracker retires a tag when "this completion's length equals what I expected for the first completion", or that mis-handles a first completion shorter than the RCB-aligned size, would see row 16 as belonging to no outstanding request.

Model report

Executive Summary. On firmware 2.7, Write commands whose data buffer is not 64-byte aligned fail with Data Transfer Error. The first abnormal event is the device's error message at 42,520 ns (row 15), which its AER registers record as an Unexpected Completion for a legal third Completion of a split read (row 16). Best-supported cause (HIGH): firmware 2.7 mis-tracks split completions whose first fragment is shorter than the Read Completion Boundary. Recommended: escalate to the SSD vendor with this report; workaround: align host buffers to 64 bytes; do not deploy 2.7.

System Configuration. As given (Gen4 x4, MPS 256, MRRS 512, RCB 64, IOMMU on, firmware 2.7, inbox driver). Sources: lab configuration record (synthetic).

Capture Scope. Analyzer, both directions, unfiltered, 2 s, no overflow. Absence claims are valid within the window.

Timeline. Rows 1–8: CID 0x0030 (aligned buffer) completes successfully, read split as 256 + 256 at RCB-aligned points. Rows 9–18: CID 0x0031 (buffer at offset 0x20). Row 15 is listed before row 16 but timestamped after it (42,520 > 42,470): in time order, the third completion (row 16, 42,470 ns) precedes the error message (row 15, 42,520 ns). The analyzer's display order is not time order — noted as a capture-presentation caveat.

Key Transactions. CID 0x0031: SQE fetch (rows 10–11) → data MRd Tag 0x33 for 512 B at 0x2_0000_4020 (row 12) → three completions: 32 B (BC 512, LA 0x20), 256 B (BC 480, LA 0x40), 224 B (BC 224, LA 0x40) → error message → CQE Data Transfer Error.

First Abnormal Event. Row 15, the device's error message at 42,520 ns, 50 ns after the third completion. Expected: the requester accepts all three completions (32 + 256 + 224 = 512 bytes; Byte Count decrements consistently 512 → 480 → 224; the first split ends at the 64-byte boundary 0x…4040, as RCB rules require). Observed: the device flags one as unexpected. Layer: PCIe transaction layer, within the device's requester logic. PCI Express Base Specification — completion rules, Read Completion Boundary

Errors. PCIe: Unexpected Completion at the endpoint (AER), Tag 0x33, BC 224. NVMe: Data Transfer Error on CID 0x0031. No errors on CID 0x0030; no correctable errors; no link events.

Evidence. E1 trace rows 1–18; E2 endpoint AER snapshot; E3 1-hour alignment statistics (7,912/7,912 vs 0/39,840); E4 firmware 2.6 comparison (0 failures).

Hypotheses. H1 — device firmware 2.7 mishandles a three-way split whose first fragment is shorter than RCB: supported by E2 (the unexpected completion is the third one), E3 (perfect correlation with misalignment, which is exactly what produces a short first fragment) and E4 (2.6 does not fail); not contradicted. H2 — root complex produced an illegal split: weakened by the arithmetic — all fields are consistent and the split points are RCB-aligned; the same root complex works with 2.6. H3 — host buffer unmapped (IOMMU): eliminated — completions carry data with Successful status; no UR. H4 — link corruption: eliminated — no LCRC/replay evidence, deterministic correlation with alignment.

Root Cause. H1, confidence HIGH. Not CONFIRMED: the device's internal mechanism is not visible; confirmation requires the vendor to identify the defect, or a decisive experiment (below).

Recommendations. Fix: vendor firmware correction. Workaround: 64-byte-aligned buffers in the host (or remain on 2.6). Experiment to confirm: force the root complex (or an exerciser) to send the same read as two completions with the first fragment ≥ 64 B, versus a short first fragment; failures only in the second case isolate the mechanism.

Regression Tests. Write and Read (Reads exercise the device as completer, not requester — include for coverage of other paths) with every PRP1 offset from 0 to 4092 in steps of 4, for transfer sizes that straddle RCB and MRRS boundaries; expected zero Unexpected Completions and zero Data Transfer Errors; run on every firmware release.

Appendix. Trace excerpt; AER snapshot; fio job file; firmware versions; analyzer software version.

Challenge answer. The MRd at row 12 is legal: 512 bytes ≤ MRRS 512; it spans 0x2_0000_4020 to 0x2_0000_421F, which does not cross a 4 KiB boundary. The request is fine; only the device's handling of the completions is not.

What a senior engineer notices

  • The trace contained a presentation trap (rows out of time order). Analyzers can display by capture order, by transaction grouping or by time; always sort by time before reasoning about "first".
  • A perfect correlation (7,912 of 7,912) with a mechanism is much stronger evidence than a statistical one, but it is still not CONFIRMED until the mechanism is isolated.
  • The aligned command in the same capture is the golden run. Always look for the success case next to the failure.

Failure variants

  • Same bug on Reads with metadata buffers at odd offsets.
  • A root complex with RCB 128 B: the failure rate changes, which is itself a test of H1.

Quiz

  1. Which template heading most often contains the reporting layer by mistake?

    • Observed symptom
    • Evidence
    • Affected layer
    • Regression test
    Answer and reasoning

    "Affected layer" should be the layer where the deviation occurred. Writing "NVMe" because the error appeared as an NVMe status is the classic slip.

  2. A Read times out; the timeout handler finds the CQE already in the CQ. Which candidate does this support most?

    • Firmware deadlock
    • Lost or undelivered interrupt
    • Completion timeout on DMA
    • Queue corruption
    Answer

    The controller finished; the notification path failed.

  3. Why is "85 % likely" usually inappropriate in a root-cause report?

    Answer

    It implies calibration that has not been measured. Use evidence-defined levels unless the probability was formally calculated.

  4. A failure occurs 1 in 50 runs. Roughly how many clean runs give 95 % confidence the rate is now below 1 in 50?

    • 10
    • 50
    • About 150
    • 1,000
    Answer

    Rule of three: ≈ 3/p = 150 (exactly 149 by the formula).

  5. Which regression step catches a fix that only made recovery faster?

    Answer

    Compare traces: the first abnormal event must be gone.

  6. With OS logs only, can you determine whether the doorbell write reached the device?

    Answer

    No. That requires an analyzer (or device-side logs). OS logs show what the driver did, not what crossed the link.

  7. In pattern 3 (both layers healthy, software misuse), which statement is true?

    • Every layer behaved correctly for its input; the contract between layers was misused
    • The device reordered illegally
    • The link dropped a write
    • The CQE was corrupted
    Answer

    NVMe permits completion in any order; overlapping writes have no defined winner.

  8. Was the three-way split of the 512-byte read in the report lab legal? Show the arithmetic.

    Answer

    Yes: 32 + 256 + 224 = 512; first fragment ends at the 64-byte boundary (0x…4040); Byte Count decrements 512 → 480 → 224; Lower Address consistent.

  9. Why is pairwise testing not a guarantee?

    Answer

    It covers all two-way value interactions, not three-way or higher; bugs needing three specific values together can be missed.

Interview questions

  1. (Intermediate) What is the difference between a root cause and a contributing factor?

    Model answer

    The root cause is the mechanism whose removal prevents the failure; contributing factors make it more likely or worse (high queue depth, short timeouts). Fix the root cause; consider hardening against contributors.

  2. (Advanced) Your analyzer shows no completion for a request. How confident can you be that none was sent?

    Model answer

    Only as confident as the capture scope: filters, overflow, direction coverage, lane/link probing, and whether the analyzer was in the path at the right time. Within an unfiltered, gap-free window, the absence is an observation; otherwise it is UNKNOWN.

  3. (Senior) A customer wants a root cause by tomorrow; you have MEDIUM confidence. What do you send?

    Model answer

    The current best hypothesis labelled MEDIUM, the alternatives still open, the experiment that will decide and when, and a safe workaround if one exists. Never upgrade confidence to meet a deadline.

  4. (Senior) How do you choose 50 tests out of a 400,000-configuration matrix?

    Model answer

    Pairwise coverage for breadth, risk-weighted additions (new code, extremes), boundaries, change-driven focus on dimensions the change touches, field-failure configurations, and a few long-duration runs on top-risk configurations. Document what is not covered.

  5. (Principal) How would you design an experiment that proves a root cause rather than correlates with it?

    Model answer

    Manipulate the suspected cause directly while holding other factors fixed: induce it and observe the failure, remove it and observe its absence across enough runs; ideally use a minimal reproduction and a mechanism-level observation (the first abnormal event appears and disappears with the manipulation).
