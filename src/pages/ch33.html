A WRITE looks like a READ run backwards, and that is exactly where people go wrong. In a WRITE the controller pulls the data out of host memory with read requests, holds it somewhere you cannot see, and may tell you it is finished long before the data is safe from a power cut. This chapter follows one 4 KiB write from the application to the flash cell and back, and teaches you what "completion" really promises.

Why this chapter exists

Writes are where storage systems keep their promises or break them. A database commit, a filesystem journal, a log line in a payment system: each is a write that someone, somewhere, is relying on. If you misunderstand what a Non-Volatile Memory Express (NVMe) Write command guarantees, you will design software that loses data on power failure, or you will add so many safety barriers that performance collapses.

Writes are also where Peripheral Component Interconnect Express (PCIe) traces surprise beginners. In Chapter 32 (READ) the controller pushed data to the host with posted Memory Write requests. In a WRITE the same controller has to ask for the data with non-posted Memory Read requests and wait for Completions with Data. The direction of the data is host-to-device, but the direction of the requests is device-to-host. If you look for "writes" on the analyzer during an NVMe WRITE, you will find almost none.

Finally, writes reveal the gap between the protocol and the medium. Programming a NAND flash page takes hundreds of microseconds to milliseconds; a well-behaved SSD completes a 4 KiB write in tens of microseconds. That gap is filled by a write cache, and the write cache is the subject of half the arguments you will ever have about durability.

Learning objectives

  • Trace a single NVMe Write command through every layer: application, filesystem, block layer, driver, Submission Queue Entry (SQE), doorbell, controller, Direct Memory Access (DMA), controller buffer, NAND program, Completion Queue Entry (CQE), interrupt.
  • Decode the Write command fields that matter: opcode 01h, Namespace Identifier (NSID), Starting LBA (SLBA), Number of Logical Blocks (NLB, 0's based), Force Unit Access (FUA), Limited Retry (LR), and the data pointer (PRP or SGL).
  • Predict the PCIe footprint of a write: how many Memory Read (MRd) requests and Completions with Data (CplD) a given size produces, given Max Read Request Size (MRRS), Max Payload Size (MPS) and the root complex's completion behavior.
  • Explain precisely what a successful completion means for durability with and without a volatile write cache, and what FUA changes.
  • Read a normal, a slow and a failed synthetic WRITE trace, find the first abnormal event, and reason to a root cause.
  • Inspect write-path behavior safely on Linux and know what that output can and cannot prove.

The story

Imagine a bakery that takes cake orders. You (the teacher) write an order slip — "please store this recipe in the vault, shelf 4096" — and drop it in the order box. You ring the bell. The baker's helper (the librarian from our earlier chapters) comes to your desk, reads the slip, and then walks over to your kitchen table to copy the recipe page by page. When the helper has every page in their apron pocket, they shout "Got it!" and put a ticket in your answer box.

But here is the secret: the recipe is still in the helper's apron, not in the vault. Getting into the vault takes a long time, so the helper waits and carries many recipes in together. If the helper trips and the apron catches fire before reaching the vault, the recipe is gone — even though you heard "Got it!". If you really need to know it is in the vault, you must either say "put it straight in the vault before you shout" (that is FUA) or later say "empty your apron into the vault now" (that is FLUSH, the next chapter).

A moving company that offers "we've collected your boxes" receipts. You book a job (the command), point to where the boxes are in your house (the data pointer), and the movers come and load them into their truck (DMA reads from host memory). They hand you a receipt as soon as the truck is loaded (the completion). The boxes reach the warehouse later (NAND program). The receipt is real, and the movers will deliver if nothing goes wrong, but if the truck crashes before the warehouse, the receipt does not bring your furniture back. A premium "warehouse-signed receipt" (FUA) costs you a longer wait.

What it hides. Movers carry everything in one trip; a controller asks for data in many small read requests (often 512 bytes each in our lab system), each with its own tag, and receives the data in even smaller completion packets. The analogy hides that pipelining entirely, and pipelining is what decides write throughput.

Where it misleads. A moving truck is a physical place; a controller's write cache may be DRAM, SRAM, or a region of host memory, and some SSDs protect it with capacitors (power-loss protection) so that "in the truck" is effectively "in the warehouse". The analogy also suggests boxes arrive in order; NVMe imposes no ordering between separate commands, so two overlapping writes in flight at the same time can land in either order.

What it gets right. The receipt (completion) and the warehouse (non-volatile media) are different events, and you can buy a stronger receipt at the cost of time.

Beginner explanation

When a program saves data, the bytes start in the computer's main memory (RAM). The SSD cannot see the program; it only sees memory addresses. So the operating system does three things:

  1. It makes sure the bytes sit in memory pages that the SSD is allowed to reach.
  2. It writes a 64-byte instruction — a Submission Queue Entry — saying "write these logical blocks of namespace 1, starting at block number X, and the data is at memory address Y".
  3. It rings the SSD's doorbell by writing a number into a register on the SSD.

The SSD then does the work: it fetches the instruction, copies the data out of memory by itself (this is Direct Memory Access, DMA), stores it, and writes a 16-byte Completion Queue Entry back into memory saying "done, success". It usually also sends an interrupt so the CPU notices.

Two ideas make WRITE different from READ:

  • The SSD reads to write. To get the data, the SSD must read host memory. On the PCIe link you see the SSD sending read requests and the host answering with data.
  • "Done" is not "permanent". Many SSDs keep recently written data in a fast but volatile buffer and copy it to flash later. A successful completion means the SSD has accepted the data and will return it on a later read; it does not by itself mean the data would survive a power cut. Whether it would depends on the write cache, the FUA bit, Flush commands and the drive's power-loss protection.

Engineering explanation

Application, filesystem and block layer

An application calls write() or pwrite(). With buffered I/O the kernel copies the bytes into the page cache and returns immediately; nothing has reached the SSD yet. Later, writeback (or an explicit fsync()) turns dirty pages into block I/O requests. With O_DIRECT the user buffer itself (after pinning) becomes the DMA source and the write is issued synchronously or asynchronously from the application's own memory.

The filesystem translates a file offset into logical block addresses (LBAs) on the namespace and, for journaling filesystems, emits metadata writes too. When it needs ordering or durability — a journal commit, for example — it marks requests with REQ_PREFLUSH (flush the cache before this write) and/or REQ_FUA (this write must be on stable media before completing). The block layer (blk-mq) merges and splits requests to respect the device's limits (maximum transfer size, segment limits) and hands each request to a hardware queue context that maps to an NVMe I/O Submission Queue.

The flag names above are Linux kernel names. If the device reports no volatile write cache, the Linux block layer drops REQ_PREFLUSH and REQ_FUA because they would be meaningless. If it reports a cache, the NVMe driver translates REQ_FUA into the Write command's FUA bit and REQ_PREFLUSH into a separate Flush command. This translation is Implementation-dependent and has changed across kernel versions; read the driver source for the kernel you run.

The driver builds the command

The NVMe driver allocates a Command Identifier (CID) unique among the commands outstanding on that Submission Queue, fills a 64-byte SQE in the next free slot of the ring, and describes the data buffer. For a 4 KiB write whose buffer starts on a page boundary, a single PRP entry (PRP1) is enough. For two pages, PRP1 and PRP2 both hold page addresses. For more, PRP2 points to a PRP list (Chapter 36). If the controller supports Scatter Gather Lists and the driver chooses them, the data pointer holds an SGL descriptor instead (Chapter 37).

Opcode bits tell you the direction

For NVMe I/O commands the two low bits of the opcode encode the data transfer direction: 00b no data, 01b host-to-controller, 10b controller-to-host, 11b bidirectional. Write is 01h → 01b, host-to-controller. Read is 02h → 10b. Flush is 00h → no data. Dataset Management is 09h → 01b, because the controller reads a list of ranges from host memory. This is a quick sanity check when decoding an unfamiliar trace: if a 01b-class command is followed by the controller writing large amounts of data to the host, something is wrong with your decoding or with the device.

Submission and the doorbell

After writing the SQE into host memory, the driver issues a memory barrier and writes the new tail index into the SQ tail doorbell. On our lab system I/O SQ 1's tail doorbell is BAR0 + 0x1008 = 0xFE60_1008. That single 4-byte posted Memory Write (MWr) is the only thing the host sends to the device for the whole command. Everything else is the device's initiative.

The controller fetches and parses the command

The controller sees the tail move, issues an MRd for the 64 bytes at SQ base + slot × 64, and receives a CplD carrying the SQE. It checks opcode, NSID, LBA range against the namespace size (NSZE), the data pointer format, and whether the namespace is write-protected or reserved by someone else. Errors found here complete the command immediately without any data transfer — a useful clue in traces: an error CQE with no data MRd before it points at a parameter problem, not a media problem.

DMA: the controller reads the data

For a WRITE, DMA means the controller issues Memory Read requests to the host addresses given by PRP or SGL. Each MRd is non-posted: it consumes a tag (Chapter 13) and waits for completions. Three PCIe limits shape the stream:

  • MRRS (Max Read Request Size, 512 bytes on our lab system) caps how much one MRd may ask for. A 4 KiB write therefore needs at least 8 MRds.
  • 4 KiB address boundary. A PCIe memory request must not cross a 4 KiB address boundary. With page-aligned PRPs this never bites; with an SGL pointing at an odd offset, it adds requests.
  • MPS and Read Completion Boundary (RCB). The root complex returns the data in one or more CplDs, each no larger than MPS (256 bytes here); it may split a completion at RCB-aligned addresses (64 bytes here). Many root complexes return 64-byte or 128-byte completions regardless of MPS — Implementation-dependent. One 512-byte MRd can come back as two, four or eight CplDs.

Because each MRd has a round trip of roughly a microsecond on a typical server, the controller must keep many reads outstanding to fill the link. This is the single most important performance difference between WRITE and READ: READ data leaves the device as posted writes, so the device only needs flow-control credits; WRITE data must be requested, so the device needs tags, completion buffer space, and a host that answers quickly.

The controller stores the data

Once all CplDs have arrived the controller has the data in an internal buffer. What happens next is entirely inside the device and invisible on the PCIe link:

  • The flash translation layer (FTL) picks a free physical page — never the page that held the old version, because flash cannot be overwritten in place — and records the new logical-to-physical mapping.
  • If a volatile write cache is enabled, the controller may complete the command now and program the NAND later, typically after accumulating enough data to fill a multi-plane program unit.
  • If FUA is set, or there is no volatile write cache, the controller must not report completion until the data and its metadata are on non-volatile media. "Non-volatile media" may include capacitor-protected DRAM on drives with power-loss protection; the specification does not say how durability is achieved, only what the host can rely on.

Flash programming

NAND is programmed in pages (commonly 16 KiB per plane on modern TLC, implementation-dependent) and erased in much larger blocks. A program operation on TLC NAND takes on the order of hundreds of microseconds up to a few milliseconds depending on the technology and mode (SLC-cache programs are faster). A controller hides this by striping across many dies and planes and by caching. The consequences for the host:

  • Small writes are absorbed by the cache; their latency is the PCIe and firmware path, not the NAND.
  • Sustained writes eventually exceed what the cache and the dies can absorb. Latency then rises to the NAND's real rate, and when free blocks run low, garbage collection competes for the same dies (Chapter 35).
  • A write that is smaller than the flash page, or not aligned to it, may require read-modify-write inside the device, increasing write amplification.

Completion

The controller posts a 16-byte CQE to the Completion Queue with a posted MWr: Dword 2 carries the SQ Head Pointer (SQHD) and SQ Identifier, Dword 3 carries the CID, the Phase tag and the Status field. If interrupts are enabled for that CQ, the controller then sends an MSI-X message — another posted MWr to the address in its MSI-X table — subject to interrupt coalescing. The driver reads the CQE, matches the CID, completes the block request, and eventually writes the CQ head doorbell (0xFE60_100C for CQ 1 on our lab system) to release the slots.

The host must not modify or free the data buffer until the completion arrives. The controller is allowed to read the buffer at any time between the doorbell and the completion, and some controllers re-read data (for example on an internal retry). An application that reuses its buffer early has a race that may pass every test on one SSD and corrupt data on another.

FUA covers only the data of the command that carries it. It does not flush other cached writes. A journal commit block written with FUA is only safe if the journal blocks it refers to were made durable first — which is why Linux pairs REQ_PREFLUSH with REQ_FUA on commit records.

Atomicity and ordering

Two further guarantees are easy to assume and often absent:

  • Ordering. NVMe does not order the execution or completion of separate commands, even in the same Submission Queue. If a host submits two overlapping writes without waiting, the final content of the overlap is undefined from the host's point of view. Software that needs order waits for the first completion before submitting the second.
  • Atomicity. Identify Controller reports Atomic Write Unit Normal (AWUN) and Atomic Write Unit Power Fail (AWUPF); namespaces may report their own values (NAWUN, NAWUPF). A write no larger than the power-fail atomic unit, and not crossing an atomic boundary if one is reported, is either entirely old or entirely new after a power failure. Larger writes may be torn. These fields are 0's based counts of logical blocks; confirm the exact boundary rules (for example NABSPF and NABO) in the NVM Command Set specification for your revision. Version-dependent

The central concept on the ladder: the WRITE data path

You leave a note saying "copy the recipe on my table into the vault". The helper comes and copies it, says "got it", and takes it to the vault later.

The driver writes a Write SQE pointing at a host buffer and rings the doorbell. The controller DMA-reads the buffer, acknowledges with a CQE, and commits the data to flash at its own pace unless told otherwise (FUA or Flush).

Host memory holds the SQ ring and the data pages; the SSD's BAR0 holds the doorbell register; the controller's DMA engine issues read requests; its DRAM/SRAM buffers data; the FTL maps LBA to NAND page; NAND dies program the page.

NVM Command Set: Write (01h) with SLBA, NLB (0's based), FUA, LR, PRINFO, DSM and directive fields. NVMe Base: SQE/CQE formats, PRP/SGL rules, Volatile Write Cache feature and the VWC field of Identify Controller. NVMe over PCIe Transport: doorbells, memory-based queues, MSI-X.

Host→device: one MWr (doorbell). Device→host: MRd (SQE), MRds (data), MWr (CQE), MWr (MSI-X). Host→device: CplDs (SQE and data), MWr (CQ head doorbell). Data flows downstream; requests flow upstream.

In an analyzer: a doorbell write, a 64-byte read, then a burst of 512-byte MRds with consecutive tags, a storm of CplDs on the downstream side, a 16-byte MWr to the CQ address, a 4-byte MWr to 0xFEE…, and later a CQ head doorbell write.

A slow write with an idle link points inside the device (cache full, garbage collection, FUA). A CplD with Unsupported Request status points at a bad address or IOMMU mapping. A completion with success after data that never reached the media points at an unflushed cache, not at a protocol fault.

On the host side, the participants are the CPU (writes the SQE and doorbell), the memory controller (serves the device's reads), the IOMMU (translates device-visible I/O virtual addresses to physical addresses) and the root complex (turns MRds into memory reads and returns CplDs). A slow IOMMU translation or a congested memory controller shows up on the trace as long MRd→CplD gaps — a host problem that looks like a device problem if you only measure command latency.

Without a buffer, every 4 KiB write would wait for a NAND program and each die could only service one program at a time. With a buffer, the controller gathers writes into full program units, stripes them across dies, and returns completions in microseconds. The price is the durability window, which the controller closes either with capacitors or by honoring FUA and Flush.

Specification view

Three NVMe documents meet in a WRITE. In the 2026 baseline these are the NVM Express Base Specification, Revision 2.4, the NVM Express NVM Command Set Specification, Revision 1.3, and the NVM Express NVMe over PCIe Transport Specification, Revision 1.4. The PCIe side is governed by the PCI Express Base Specification, Revision 6.x/7.0 (a PCI-SIG members' document).

  • The NVM Command Set specification defines the Write command itself: its fields, the FUA semantics, protection information handling, and the command-specific status values. Look for the section named for the Write command and the figures describing its command Dwords.
  • The Base specification defines the common command format, the CQE, PRP and SGL rules, generic status codes, the Volatile Write Cache feature, Identify Controller (including VWC, AWUN, AWUPF, MDTS) and the Flush command.
  • The PCIe Transport specification defines how queues live in memory, doorbell registers and interrupts over PCIe.

The specification text that matters most here is Normative: FUA requires data and metadata to be committed to non-volatile media before the command completes; the controller indicates presence of a volatile write cache in Identify Controller; and with the cache enabled, the host uses Flush (or FUA) to get durability.

Write is NVM Command Set opcode 01h; its data direction is host-to-controller. SLBA occupies CDW10–11; NLB is a 0's based value in CDW12 bits 15:0; FUA is CDW12 bit 30 and Limited Retry bit 31. The data pointer is in CDW6–9 and its format is selected by PSDT in CDW0 bits 15:14. A CQE is 16 bytes and carries SQHD, SQID, CID, Phase tag and Status.

The number of MRds and CplDs for a write, the outstanding-request requirement from Little's Law, and the claim that WRITE throughput is more sensitive to host read latency than READ throughput are reasoned from PCIe rules, not stated by any NVMe document.

Cache size, destage policy, whether the cache is power-loss-protected, the NAND program unit, how the controller paces its MRds, whether it fetches data before or after reserving buffer space, and how the root complex splits completions are all implementation-dependent.

CDW12 and CDW13 have gained fields over revisions (directives in 1.3, storage tags and extended protection formats later, further placement-related use of the directive fields in 2.x). Status codes have been added over time. The split of the specification into Base, command sets and transports happened with NVMe 2.0; in 1.x everything lived in one document. When reading a device's behavior, match it to the revision it reports in the Version (VS) register and Identify data.

The specification does not say how fast a write must complete, how long data may stay in a volatile cache before destaging, what technology "non-volatile media" is, or whether data that completed without FUA will in practice survive a power cut on a particular product. It does not define ordering between separate commands. Check in the specification: the exact layout of CDW12 bits 25:16 and CDW13 for your revision; the AWUPF/NAWUPF boundary rules; the command-specific status codes for Write.

Never assume: that completion means durable; that commands complete in submission order; that the controller reads the data buffer exactly once; that an SSD with "power-loss protection" in its datasheet reports VWC as absent (some do, some report a cache and treat Flush as cheap); that a write smaller than a sector is possible (it is not; the unit is the LBA).

Ordering on the wire

PCIe ordering rules (Chapter 14) matter at two points. First, the CQE MWr must not be observed by the host before the data it describes; for a WRITE this is trivially true because the data flowed the other way. (For a READ it is the key rule: posted data MWrs must not be passed by the posted CQE MWr.) Second, the MSI-X MWr is posted after the CQE MWr in the same direction, so by the time the interrupt handler runs the CQE is visible — provided nobody set Relaxed Ordering on the CQE write in a way the platform honors. Controllers generally do not use Relaxed Ordering for CQE and MSI-X writes. Implementation-dependent

No ordering between commands

If the driver submits Write A (LBA 100) and Write B (LBA 100) back to back, the controller may fetch both, read both data buffers, and commit them in either order. NVMe offers fused operations only for the specific Compare-and-Write case, and no general "barrier" command. Ordering is the host's job.

Code / pseudocode

First, the driver-side logic of a write, as pseudocode modelled loosely on what Linux's NVMe driver does (function names in comments are real Linux names; the body is simplified and is not the kernel code).

/* nvme_setup_rw(): fill a Write SQE from a block request */
sqe.opcode    = 0x01;                       /* Write */
sqe.cid       = alloc_cid(sq);              /* unique among outstanding on this SQ */
sqe.nsid      = ns->nsid;
sqe.slba      = sector_to_lba(rq->sector);  /* 512-byte sectors to namespace LBAs */
sqe.cdw12     = (nr_lbas - 1) & 0xFFFF;     /* NLB is 0's based */
if (rq->flags & REQ_FUA)
    sqe.cdw12 |= 1u << 30;                  /* FUA */
map_data(rq, &sqe.dptr);                    /* dma_map_*, build PRP1/PRP2 or PRP list or SGL */

/* nvme_submit_cmd(): copy into ring, then ring the doorbell */
memcpy(&sq->ring[sq->tail], &sqe, 64);
sq->tail = (sq->tail + 1) % sq->depth;
wmb();                                      /* SQE visible before the doorbell */
writel(sq->tail, sq->db_tail);              /* MWr on PCIe */

/* nvme_irq() / nvme_poll_cq(): later */
while (cqe_phase(&cq->ring[cq->head]) == cq->phase) {
    cqe = cq->ring[cq->head];
    req = lookup(sq, cqe.cid);
    unmap_data(req);                        /* only now may the buffer be reused */
    complete(req, cqe.status);
    advance(cq);
}

Second, a runnable model that builds a Write SQE byte by byte, decodes it, and predicts the PCIe footprint for different root-complex completion sizes. It is the basis of the lab below.

#!/usr/bin/env python3
"""write_footprint.py - build an NVMe Write SQE and predict its PCIe footprint.

Synthetic teaching model (standard library only). It is NOT a driver and touches no hardware.
Assumptions come from the course lab system: MPS 256 B, MRRS 512 B, 4 KiB host pages.
"""
import struct

MPS, MRRS, PAGE = 256, 512, 4096


def build_write_sqe(cid, nsid, prp1, prp2, slba, nlb0, fua=False, lr=False):
    """Return the 64-byte SQE for NVM Write (opcode 01h), PRP data pointer (PSDT=00b)."""
    cdw0 = 0x01 | (0 << 8) | (0 << 14) | (cid << 16)      # opcode, FUSE=0, PSDT=0, CID
    cdw12 = (nlb0 & 0xFFFF) | (int(fua) << 30) | (int(lr) << 31)
    return struct.pack("<IIIIQQQQIIII",
                       cdw0, nsid, 0, 0,          # CDW0, NSID, CDW2, CDW3
                       0,                         # MPTR (CDW4-5)
                       prp1, prp2,                # DPTR (CDW6-9)
                       slba,                      # SLBA (CDW10-11)
                       cdw12, 0, 0, 0)            # CDW12..CDW15


def decode_sqe(sqe):
    (cdw0, nsid, _c2, _c3, _mptr, prp1, prp2, slba,
     cdw12, cdw13, cdw14, cdw15) = struct.unpack("<IIIIQQQQIIII", sqe)
    return {
        "opcode": cdw0 & 0xFF, "fuse": (cdw0 >> 8) & 3, "psdt": (cdw0 >> 14) & 3,
        "cid": cdw0 >> 16, "nsid": nsid, "prp1": prp1, "prp2": prp2, "slba": slba,
        "nlb": (cdw12 & 0xFFFF) + 1,            # NLB is 0's based
        "fua": (cdw12 >> 30) & 1, "lr": (cdw12 >> 31) & 1,
    }


def prp_segments(prp1, length):
    """Split a transfer into host-page segments, as PRP entries describe it (PRP list fetch ignored)."""
    segs, addr, left = [], prp1, length
    while left:
        room = PAGE - (addr % PAGE)
        n = min(room, left)
        segs.append((addr, n))
        left -= n
        addr += n          # model: contiguous IOVA; real PRP entries may point anywhere
    return segs


def mrd_requests(segs):
    """Memory Read requests the controller could issue: <= MRRS, never crossing a 4 KiB boundary."""
    reqs = []
    for addr, n in segs:
        while n:
            room = PAGE - (addr % PAGE)
            size = min(MRRS, n, room)
            reqs.append((addr, size))
            addr += size
            n -= size
    return reqs


def completions(addr, size, chunk):
    """Completions with data (CplD) the root complex might return for one MRd.
    chunk = how the root complex splits (implementation-dependent: 64, 128, 256...)."""
    out, byte_count = [], size
    while byte_count:
        n = min(chunk, MPS, byte_count)
        out.append((addr, n, byte_count))   # Byte Count = bytes remaining including this one
        addr += n
        byte_count -= n
    return out


def footprint(length, prp1, rc_chunk):
    segs = prp_segments(prp1, length)
    reqs = mrd_requests(segs)
    cpls = [c for a, s in reqs for c in completions(a, s, rc_chunk)]
    return segs, reqs, cpls


if __name__ == "__main__":

    print("SQE bytes :", sqe.hex(" ", 4))
    d = decode_sqe(sqe)
    print("Decoded   : opcode=%02Xh cid=%04Xh nsid=%d slba=%#x nlb=%d fua=%d psdt=%d"
          % (d["opcode"], d["cid"], d["nsid"], d["slba"], d["nlb"], d["fua"], d["psdt"]))

    for chunk in (256, 64):

Worked example

Scenario (synthetic). A database on the lab system writes a 16 KiB page with O_DIRECT to file offset 1 MiB, which the filesystem maps to LBA 0x0040_0000 of namespace 1 (512-byte LBAs). The buffer is 4 KiB-aligned at IOVA 0x2_0010_0000 and physically spans four pages at 0x2_0010_0000, 0x2_0010_1000, 0x2_0010_2000 and 0x2_0010_3000 (contiguous for simplicity). The volatile write cache is enabled. The database then commits.

Step 1 — Build the command

  • 16 KiB ÷ 512 B = 32 LBAs → NLB = 31 = 0x1F (0's based). CDW12 = 0x0000001F.
  • SLBA = 0x0040_0000 → CDW10 = 0x00400000, CDW11 = 0x00000000.
  • Four pages → PRP1 = 0x2_0010_0000 and PRP2 points to a PRP list in memory at 0x1_5000_0000 holding three entries: 0x2_0010_1000, 0x2_0010_2000, 0x2_0010_3000.

Step 2 — Predict the link traffic

  • 1 doorbell MWr down; 1 SQE MRd up and 1 CplD down.
  • PRP list: 3 × 8 = 24 bytes → 1 MRd up (6 DW) and 1 CplD down. Controllers may prefetch more of the list; that is allowed.
  • Data: 16 KiB ÷ 512 B MRRS = 32 MRds up; with a root complex returning 256-byte completions, 64 CplDs down.
  • CQE MWr (16 B) up, MSI-X MWr up, CQ head doorbell down.

Step 3 — Estimate time on the downstream link

Gen4 x4 carries 16 GT/s × 4 lanes × 128/130 ≈ 63.0 Gbit/s ≈ 7.88 GB/s of raw symbols per direction. Each 256-byte CplD carries roughly 20–28 bytes of framing, sequence number, header and LCRC overhead (exact amount depends on header size and ECRC). Taking ~24 bytes: 64 × 280 B = 17,920 B → ≈ 2.3 µs of downstream wire time. Compared to a NAND program of hundreds of microseconds, the link is not where the time goes for a cached write. Derived

Step 4 — The commit

For the commit record, the database calls fdatasync(). The filesystem issues its log/commit write with REQ_PREFLUSH | REQ_FUA. On the wire you will see a Flush command (opcode 00h, no data) complete before the commit write is submitted, then the commit Write with CDW12 bit 30 set. Its CQE will typically arrive later than an ordinary cached write — how much later is implementation-dependent and can range from barely measurable (power-loss-protected drives) to milliseconds.

Step 5 — What the host may now rely on

After the Flush completed, every write that completed before the Flush was submitted is on non-volatile media. After the FUA write completed, the commit record is on non-volatile media. The 16 KiB page write is durable only if it completed before the Flush was submitted — which is precisely why the database waits for it before calling fdatasync().

Senior engineer insight

1. Whose time is it? Split write latency into host submission, SQE fetch, data fetch (MRd→last CplD), firmware (last CplD→CQE) and host completion (CQE→doorbell). Only the firmware segment belongs to the SSD alone. Most "slow SSD" write reports I have seen were split between IOMMU and memory latency, interrupt coalescing, and real device stalls — and the trace tells you which in minutes.

2. What did the application ask for? Before blaming durability on a drive, prove the stack issued Flush or FUA. A surprising number of "the SSD lost data" incidents are applications that never called fsync, filesystems mounted with barriers disabled, or virtualization layers that acknowledged flushes without passing them down.

3. Is this a burst or a steady state? SSD write performance has at least two regimes. Fresh-out-of-box and burst numbers measure the cache; sustained numbers after the drive has been filled and overwritten measure the NAND and garbage collection. Validation that only measures the first regime ships products that disappoint in production.

A further point that separates senior engineers: the asymmetry between READ and WRITE on PCIe means mixed workloads can exceed the one-direction bandwidth of the link, because read data uses the upstream direction and write data the downstream direction. A 50/50 mix on Gen4 x4 can move noticeably more than 7 GB/s in total if the device back end keeps up. Conversely, a write-heavy workload stresses the host's ability to answer reads from the device — root complex completion latency becomes a first-class performance parameter.

With rc_chunk 64, every CplD count multiplies by four relative to 256.

Question 1. Not for 0x800 (a 512-multiple, so the page boundary falls on a request boundary); it does for offsets that are not 512-aligned because requests are cut at the 4 KiB boundary, leaving a partial request on each side. Question 2. 7 × 109 × 10-6 ÷ 512 ≈ 14 outstanding MRds. Question 3. With dsync the filesystem must make the data durable; with a volatile cache it issues a flush (or FUA), without one the block layer suppresses flushes as unnecessary. Question 4. Kernel versions differ in whether the tracepoint prints the raw 0's based field; the honest answer is "verify against the request size in bytes" — 16 KiB = 32 LBAs.

What a senior engineer notices

Whether the flush appears before or after the data write in the tracepoint stream, and whether the data write completes before the flush is submitted. If the stack submitted a flush while the data write was still outstanding, the flush does not cover it — a classic ordering bug in custom storage stacks.

Failure variants

  • No nvme_cmd_write lines: the file is on a different device, or the write was satisfied from the page cache because oflag=direct was dropped.
  • Write split into several commands: the request exceeded max_sectors_kb or segment limits.
  • Tracepoint directory missing: kernel built without NVMe tracepoints or tracefs mounted elsewhere (/sys/kernel/debug/tracing).

Answers

1. 64 KiB ÷ 4 KiB = 16 LBAs → NLB = 15 = 0x0F. CDW10 = 0x00000000, CDW11 = 0x00000001, CDW12 = 0x4000000F (bit 30 FUA).

2. (a) The analyzer missed packets (filter, trigger window, or a second link in the path); check sequence numbers and capture settings. (b) The data came from a Controller Memory Buffer on the device (PRP pointed into the device's own BAR), so no host read was needed; check the PRP address against BAR ranges. (c) You misdecoded the command: it is actually a Write Zeroes (08h) or another command that carries no data; re-check the opcode byte in the SQE CplD. A firmware bug that completes without reading is the last explanation, not the first.

3. READ data travels as posted MWrs; the device needs only credits. WRITE data must be requested with non-posted MRds; each waits a round trip. If the device cannot keep enough reads outstanding to cover that round trip, throughput drops in proportion.

4. Write latency rises toward NAND program time and throughput for small writes collapses; endurance may also suffer from smaller program units. Better: keep the cache enabled and make software issue Flush/FUA where durability is needed; or choose a drive with power-loss protection.

5. Same as the normal diagram, but the CQE MWr is delayed until after the internal NAND program (hundreds of µs to ms). The PCIe portion is unchanged; the gap between the last CplD and the CQE grows.

Quiz

  1. During an NVMe WRITE over PCIe, how does the data travel from host memory to the controller?

    • The host sends posted MWr TLPs containing the data to the device's BAR
    • The controller sends MWr TLPs that pull the data
    • The controller sends MRd TLPs and the root complex returns CplD TLPs carrying the data
    • The CPU copies the data into the doorbell register
    Answer and reasoning

    The controller is the DMA master; it requests the data with non-posted reads and receives completions with data. Host MWrs carry only doorbell values.

  2. A Write command has CDW12 = 0x4000_0003 on a namespace with 512-byte LBAs. What does it do?

    • Writes 3 LBAs (1,536 bytes) with FUA
    • Writes 4 LBAs (2,048 bytes) with FUA
    • Writes 4 LBAs with Limited Retry
    • Writes 3 LBAs with Limited Retry
    Answer and reasoning

    NLB = 3 is 0's based → 4 LBAs. Bit 30 (0x4000_0000) is FUA; Limited Retry is bit 31.

  3. The volatile write cache is enabled and FUA is clear. The CQE reports success. Which statement is guaranteed?

    • A subsequent Read of those LBAs returns the new data
    • The data will survive a sudden power loss
    • The data has been programmed to NAND
    • All earlier writes are also durable
    Answer and reasoning

    Completion guarantees the command took effect for subsequent commands; durability against power loss requires Flush or FUA (or no volatile cache).

  4. Which PCIe parameter limits the size of each Memory Read request the controller issues for write data?

    • Max Payload Size
    • Max Read Request Size
    • Read Completion Boundary
    • The NVMe MDTS field
    Answer and reasoning

    MRRS bounds read requests. MPS bounds each completion's payload; RCB governs where completions may be split; MDTS bounds the whole NVMe command's transfer.

  5. Two writes to LBA 500 are submitted back to back on the same SQ without waiting. What final content can the host assume?

    • The second write's data, because SQs are FIFO
    • The first write's data, because it was fetched first
    • A mix of both at sector granularity
    • Nothing specific; NVMe does not order separate commands
    Answer and reasoning

    Fetch order is not execution or commit order. The host must serialize dependent writes.

  6. In a WRITE trace, a device MRd to host data receives a completion with status UR. What is the first suspect on an IOMMU-enabled host?

    • The IOVA is not mapped for the device (DMA mapping lifetime or wrong PRP)
    • NAND program failure
    • Wrong CQ head doorbell
    • MSI-X table misconfiguration
    Answer and reasoning

    Unsupported Request for a memory read from the device indicates the host side refused that address; with an IOMMU, an unmapped or revoked mapping is the most common cause. Confirm with the kernel's IOMMU fault log.

  7. Why does the opcode value 01h tell you Write transfers data host-to-controller?

    Model answer

    For NVMe I/O command opcodes the two least significant bits encode data direction; 01b means host-to-controller, 10b controller-to-host, 00b no data, 11b bidirectional. 01h ends in 01b.

  8. Explain why FUA on a journal commit record is not enough on its own, and what Linux adds.

    Model answer

    FUA makes only the commit record durable. The journal blocks it refers to may still sit in the volatile cache. The filesystem therefore issues a preflush (an NVMe Flush) before the commit write, after the journal writes have completed, so that the earlier blocks are durable before the record that declares them valid.

  9. A sustained random-write test shows occasional 4 ms completions. The trace shows the SQE fetched promptly and the data MRds delayed by 4 ms. Where is the problem, and what is your next experiment?

    Model answer

    Inside the device: it accepted the command but had no buffer to receive data, typically because the cache is full and destage is limited by NAND/GC. Next: vary write rate and free space (or deallocate unused space), compare fresh vs steady state, check temperature/throttling data in SMART. The host and link are exonerated by the prompt fetches and line-rate data transfer.

  10. When may the host safely reuse the data buffer of a Write command?

    Model answer

    Only after it has consumed the command's CQE. Until then the controller may read (or re-read) the buffer at any time.

Interview questions

  1. Beginner. Walk me through what happens when Linux writes 4 KiB to an NVMe SSD.

    Model answer

    The block layer hands a write request to the NVMe driver, which writes a 64-byte Write SQE (opcode 01h, NSID, SLBA, NLB=7 for 512-byte LBAs, PRP1 = buffer address) into an I/O SQ and writes the new tail to the SQ doorbell. The controller fetches the SQE with a PCIe memory read, reads the data from host memory with more memory reads, stores it (in cache or media), writes a 16-byte CQE into the CQ and sends an MSI-X interrupt. The driver processes the CQE, completes the request and updates the CQ head doorbell.

  2. Beginner. What is FUA?

    Model answer

    Force Unit Access, CDW12 bit 30 of Write: the controller must commit this command's data and metadata to non-volatile media before completing it, bypassing the durability window of a volatile write cache.

  3. Intermediate. Why does an NVMe WRITE generate non-posted traffic from the device, and why does that matter for performance?

    Model answer

    The device is the DMA master and must read host memory; PCIe reads are non-posted and require completions. Each read occupies a tag and completion buffer until answered, so throughput depends on how many reads the device keeps in flight versus the read round-trip latency (Little's Law). READ data, by contrast, is pushed with posted writes limited only by flow-control credits.

  4. Intermediate. How would you determine whether a given SSD's write cache is volatile and enabled?

    Model answer

    Identify Controller's VWC field reports presence; Get Features for the Volatile Write Cache feature (FID 06h) reports whether it is enabled. On Linux, nvme id-ctrl -H, nvme get-feature -f 6 -H and /sys/block/…/queue/write_cache. Whether the cache is power-loss protected is not reported by these; a drive with full protection typically reports no volatile cache, but confirm with vendor documentation and power-cut testing.

  5. Advanced. A customer reports corrupted data after power failure even though their application uses O_DIRECT. Investigate.

    Model answer

    O_DIRECT bypasses the page cache but not the device's volatile write cache. Check whether the application calls fsync/fdatasync or uses O_DSYNC; whether the filesystem or virtualization layer passes flushes down (tracepoints showing Flush commands); VWC state; and whether the drive honors Flush (power-cut tests). Also check atomicity: torn writes larger than AWUPF can corrupt structures even with flushes if the application assumes atomic multi-block writes.

  6. Advanced. Two consecutive writes to the same LBA came back in the opposite order. Bug?

    Model answer

    Not a device bug by itself. NVMe imposes no ordering on completions or execution between commands. If the final data on media is the first write's, the host violated its own ordering requirement by not waiting. The host stack must serialize overlapping writes.

  7. Senior. Design a validation plan for write durability on a new SSD.

    Model answer

    Matrix over cache enabled/disabled, FUA on/off, Flush before cut or not, write sizes around AWUPF and the atomic boundary, sequential and random, burst and steady state. Use a host that writes unique, verifiable signatures (LBA, write generation, checksum) and records which completions and Flush completions it observed before a controlled power cut (programmable PSU, at random points including during Flush). After power-up, verify: every write completed before a completed Flush, and every FUA write, must be present; no write may be torn within AWUPF; data not covered may be old or new but never garbage. Repeat thousands of times, include temperature extremes and nearly-full drives, and correlate failures with time-since-last-flush.

  8. Senior. Write throughput is 20% below READ throughput on the same Gen4 x4 link. Where do you look?

    Model answer

    First confirm whether it is a back-end (NAND/GC) limit by checking if the link has idle periods. If the link is the limit: count outstanding MRds and measure MRd→CplD latency; check MRRS (a 128-byte MRRS multiplies request overhead), root complex completion size (64-byte completions cost more framing), IOMMU translation latency (IOTLB misses for scattered buffers), and whether the device uses enough tags (10-bit tags on Gen5). Compare with IOMMU passthrough on a test system and with larger, page-contiguous buffers.

Chapter summary

An NVMe Write (01h) is built by the driver, announced with one doorbell write, and then executed entirely on the controller's initiative: it fetches the SQE, pulls the data with PCIe Memory Read requests answered by Completions with Data, stores the data, posts a CQE and raises an interrupt. The request traffic flows upstream and the data flows downstream — the mirror image of READ — which makes write throughput sensitive to read-request pipelining and host read latency. A successful completion guarantees that later commands see the data; it guarantees durability against power loss only when the volatile write cache is absent or disabled, or when FUA was set, or after a subsequent Flush. NAND programming is slow and invisible on the link; the write cache hides it until sustained load exposes it.
