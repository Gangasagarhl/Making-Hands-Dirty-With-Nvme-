This module takes NVMe over Remote Direct Memory Access (NVMe/RDMA) past the happy path. Chapter 67 taught the objects (queue pairs, memory regions, keys) and the basic read and write flows. Here you study the queue pair as a failure domain: its state machine, the limits that throttle it (receive credits, RDMA READ depth, memory-region pools), the network behaviour that starves it, and the races between host timeouts and late remote access. Every trace on this page is new, and every lab is harder than the chapter's.

Orientation

Chapter 67 answered "how does an NVMe command travel over RDMA?" This module answers "why did a perfectly correct NVMe/RDMA setup stall, slow down or reconnect, and how do you prove which layer did it?" You will follow one Reliable Connected (RC) queue pair (QP) through its whole life, from Connection Manager exchange to error state and back; quantify how RDMA READ depth caps write throughput; read congestion signals (Explicit Congestion Notification (ECN), Congestion Notification Packets (CNPs) and Priority Flow Control (PFC) pauses) as performance evidence; and untangle the most dangerous ambiguity in the transport: a host that gave up on a command while the target was still about to touch its buffer.

  • NVMe/RDMA: queue pairs, memory registration, keyed SGL descriptors (40h and 4Fh), SEND with Invalidate, RDMA_CM private data, the Soft-RoCE lab. This module assumes all of it.
  • NVMe-oF Mental Model: capsules, the Connect command, association.
  • Scatter Gather Lists: Segment and Last Segment descriptors, which you will decode inside a capsule.
  • NVMe/TCP module: the companion transport module; we contrast loss recovery and flow control with it.
  • PCIe Flow Control: credit-based flow control, the comparison point for RDMA receive credits.

Where it goes next: Fabric Architecture zooms out to discovery, multipathing and keep alive, which decide what the host does after the QP failures you learn to diagnose here. Performance Engineering generalises the bandwidth-delay arithmetic you apply to RDMA READ.

Kid story

Two castles stand on opposite hills, joined by a zip line. Each castle has a signal tower. When the left castle wants something, a messenger writes a note and clips it to the zip line. The right castle has a row of baskets ready to catch notes; each basket catches one note. If no basket is ready, the note bounces back and the messenger must wait and try again.

Every note gets a number: 1, 2, 3. The catcher shouts back "got up to 5!" If the catcher sees note 7 arrive after note 5, she shouts "I missed 6!" and the sender re-sends everything from 6, even notes that arrived fine.

Some notes are special: "Bring me the treasure from chest 12, here is the chest's secret word." The right castle's crane swings over and lifts the treasure out of chest 12 itself. But the crane can only carry four loads at once, so a huge treasure takes many trips.

And if anyone ever sends a wrong secret word, the zip line is cut. Every note on it is lost, and the castles must build a new line before they can talk again.

Analogy boundary

What it represents. The zip line is one RC queue pair. The catching baskets are posted receive buffers; a bounced note is a Receiver Not Ready (RNR) NAK. Numbered notes and "I missed 6" are PSNs and go-back-N retransmission. The crane is the target's RDMA READ engine, limited in how many reads it may have outstanding. The secret word is the remote key (rkey). Cutting the line is the QP entering the Error state, flushing all outstanding work.

What it hides. The two castles each have their own crane limits, negotiated when the line is built (initiator depth on one side must fit responder resources on the other). Notes are not just messages: the NVMe completion rides inside one. The castle's guards (the host RNIC) check every crane load against the secret word, its bounds and its permissions, not just the word. And the hills are not alone: many zip lines share the same valley wind (switch buffers), so one castle's traffic can slow another's.

Where it misleads. Cutting the line sounds like a dramatic, rare event. In practice a QP error is the transport's normal way of reporting any fatal problem, including a host bug that has nothing to do with the network. The story also suggests that a lost note is noticed immediately; in RoCE v2 a lost final packet is only noticed when a timer expires, which is where long latency spikes come from. Finally, a cut line in the story loses notes; in RDMA the data the crane already delivered stays delivered, even if no completion ever arrives. That last point is the root of the hardest ambiguity in this module.

Six resources decide most NVMe/RDMA incidents: target receive buffers (CRQSIZE), host response receives (HRQSIZE), the host MR pool, RDMA READ depth, the transport retry budget, and switch buffer per priority. The first two produce RNR NAKs when exhausted; the MR pool and READ depth produce silent stalls with no error on the wire; the retry budget and switch buffers produce retransmissions and, eventually, QP errors.

SEND with Invalidate carries one key in its Invalidate Extended Transport Header (IETH). The QP state machine as NVMe sees it

A verbs QP moves Reset → Init → Ready to Receive (RTR) → Ready to Send (RTS) during connection setup; RDMA_CM drives these transitions, and the target posts its capsule receives while the QP is in Init, before sending the CM REP. Only RTS carries NVMe I/O. Any fatal transport or protection error moves the QP to Error, where nothing is sent or received and every outstanding work request completes with a flush status. Send Queue Drained (SQD) and Send Queue Error (SQE) also exist; the latter is a QP state, not an NVMe Submission Queue Entry. Informative: transition rules belong to the InfiniBand Architecture Specification and the verbs API.

The central concept on the ladder: the queue pair as a failure domain

One zip line between two castles. If anyone sends a wrong secret word, the line is cut and every note on it is lost until a new line is built.

An RC QP carries one NVMe queue pair's commands, data operations and responses. Any fatal event on that QP (protection error, retries exhausted) moves it to Error, and every work request still outstanding on it completes with a flush status.

The QP is a hardware context in each RNIC: PSNs, retry counters, timers, the remote QPN. Errors are detected by the responder's checks (key, bounds, rights, sequence) or by the requester's timers, and the context is marked Error in RNIC memory.

NVMe over RDMA Transport 1.3 binds each NVMe queue to one RC QP. Recovery from a QP failure is not defined as a per-command retry by the transport; hosts recover by re-establishing queues (and usually the association), as Base 2.4's fabrics model allows. Derived: confirm the transport specification's wording about queue failure.

On the wire: a NAK (Remote Access Error, Remote Operational Error, Invalid Request) or the silence that triggers retry exhaustion; then CM DREQ/DREP or simply no further traffic on that QP; then a fresh CM REQ/REP/RTU and NVMe Connect.

In a capture: the last ACKed PSN, the first NAK or the first retransmission burst, and then the absence of response capsules for every CID that was outstanding. In host logs: one real error status followed by many flush statuses.

Count the CIDs that failed together. If they span exactly one queue, the cause is per-QP; if they span every queue to one target, suspect the network path or the target; if one CID failed alone with an NVMe status, it was not a transport failure at all.

Context caches: a hidden performance cliff

RNICs keep QP and MR contexts in host memory and cache active ones on chip. When the working set (hosts × queues, plus MRs) exceeds the cache, packets trigger extra RNIC PCIe reads for context: MRd TLPs that are not data. Cache sizes are Implementation-dependent; count QPs in design reviews and watch RNIC read traffic in captures.

The host PCIe link during an RDMA READ

When the target issues an RDMA READ for 16 KiB of write data, the host RNIC issues PCIe Memory Read requests into host memory and receives Completions with Data, just as the Lab SSD does for a local write in End-to-End Write. Every limit you learned there applies to the RNIC too: Max Read Request Size (MRRS), Read Completion Boundary (RCB), tags and completion buffer space. An RNIC in a slot with MRRS = 512 bytes needs 32 MRd TLPs per 16 KiB READ response. Two flow-control systems are therefore stacked: RDMA READ depth across the network, and PCIe outstanding reads inside the host.

Protocol view

Beyond Chapter 67's flows, three relationships matter for diagnosis. A transport ACK of a command SEND proves delivery into a target receive buffer, not execution. RDMA READ responses act as the READ's acknowledgement and consume PSN space, so a READ for 16 KiB at path MTU 4096 reserves four PSNs. An ECN mark produces a CNP from receiver to sender and a rate decrease, never a retransmission.

Ordering rules that matter for diagnosis

  • Within an RC QP, the responder executes requests in PSN order. An RDMA WRITE ACKed before a SEND is visible in host memory before that SEND's receive completion. Informative for NVMe, normative in IBTA.
  • RDMA READ responses can be outstanding while later SENDs are transmitted; the target must wait for its READ completions before using the data and before sending the response capsule.
  • A NAK names the PSN where the problem was detected. For go-back-N, every packet from that PSN onwards is retransmitted, including packets the responder had already received out of order and discarded.
  • Across QPs there is no ordering, as across NVMe queues on PCIe.

Go-back-N plus timer-driven tail recovery turns a small drop rate into timeout-length spikes and finally retry exhaustion. Likely conclusion (high confidence once counters confirm): DSCP-to-priority mismatch. Fix the mapping or add ECN-based congestion control; validate with an N-host incast test asserting zero drops on the priority.

Beginner lab: decode a multi-descriptor capsule

Objective. Decode a Write capsule whose SGL1 is a Last Segment descriptor pointing to keyed descriptors, and decide whether it describes the right number of bytes. Safe lab

Prerequisites. SGL descriptor types (Chapter 37), the keyed descriptor (Chapter 67), Python 3.8+.

Setup. Save and run the program; it builds two synthetic capsules (standard library only).

#!/usr/bin/env python3
"""capsule_sgl.py - check the SGL of a synthetic NVMe/RDMA Write capsule (simulation)."""
import struct

def keyed(addr, length, key, inval=False):          # Keyed SGL Data Block, 40h or 4Fh
    return (struct.pack("<Q", addr) + length.to_bytes(3, "little")
            + struct.pack("<I", key) + bytes([0x4F if inval else 0x40]))

def build_write(cid, nlb, descs):
    seg = b"".join(descs)
    sqe = bytearray(64)
    struct.pack_into("<BBHI", sqe, 0, 0x01, 0x40, cid, 1)        # Write, PSDT=01b, NSID 1
    sqe[24:40] = struct.pack("<QI", 0, len(seg)) + bytes(3) + b"\x31"  # Last Segment, offset 0
    struct.pack_into("<H", sqe, 48, nlb - 1)                      # NLB is zero-based
    return bytes(sqe) + seg

def check(cap, lba=512, msdbd=16):
    cid = struct.unpack_from("<H", cap, 2)[0]
    want = (struct.unpack_from("<H", cap, 48)[0] + 1) * lba
    ident = cap[39]
    off, seglen = struct.unpack_from("<QI", cap, 24)
    print(f"CID 0x{cid:04X}: SGL1 id {ident:02X}h, list at offset {off}, {seglen} bytes; need {want} bytes")
    seg = cap[64 + off:64 + off + seglen]
    total, problems = 0, []
    for n in range(0, len(seg), 16):
        d = seg[n:n + 16]
        addr, length, key = struct.unpack_from("<Q", d)[0], int.from_bytes(d[8:11], "little"), struct.unpack_from("<I", d, 11)[0]
        print(f"  desc {n // 16 + 1}: id {d[15]:02X}h VA 0x{addr:X} len {length} key 0x{key:08X}")
        total += length
    if len(seg) // 16 > msdbd:
        problems.append(f"{len(seg) // 16} descriptors exceed MSDBD {msdbd}")
    if total != want:
        problems.append(f"SGL describes {total} bytes, command needs {want}")
    print("  RESULT:", "; ".join(problems) or "OK")

if __name__ == "__main__":
    check(build_write(0x0101, 512, [keyed(0x2_0010_0000, 0x20000, 0x0002A100, True),
                                    keyed(0x2_0030_0000, 0x20000, 0x0002A201)]))
    check(build_write(0x0102, 512, [keyed(0x2_0050_0000, 0x20000, 0x0002A302, True),
                                    keyed(0x2_0070_0000, 0x10000, 0x0002A403)]))

Advanced lab: model RDMA READ depth

Objective. Predict write throughput from READ depth, chunk size and round-trip time, and compare with a simulation. Safe lab

Prerequisites. Bandwidth-delay product (Performance Engineering); the slow trace above. Setup. Python 3.8+.

#!/usr/bin/env python3
"""read_depth.py - simulate how RDMA READ depth and round-trip time cap NVMe/RDMA write throughput.
Simulation: one QP, one 1 MiB write fetched in 16 KiB RDMA READs, 100 Gb/s link, path MTU 4096."""

LINK_BYTES_PER_US = 100e9 / 8 / 1e6          # 12 500 bytes per microsecond
EFF = 4096 / 4158                             # payload share of a full RoCE v2 packet (headers + ICRC)

def simulate(total, chunk, depth, rtt_us):
    serialize = chunk / (LINK_BYTES_PER_US * EFF)   # time one READ response occupies the link
    link_free, t_done, issued, inflight = 0.0, 0.0, 0, []
    while issued < total // chunk and len(inflight) < depth:   # initial burst of requests
        inflight.append(0.0); issued += 1
    finished = 0
    while inflight:
        t_issue = inflight.pop(0)
        start = max(t_issue + rtt_us, link_free)
        link_free = start + serialize
        t_done = link_free
        finished += 1
        if issued < total // chunk:                  # completion frees a slot: issue the next READ
            inflight.append(t_done); issued += 1
            inflight.sort()
    return total / t_done / 1e3                      # bytes per us -> GB/s

def model(chunk, depth, rtt_us):
    serialize = chunk / (LINK_BYTES_PER_US * EFF)
    return min(LINK_BYTES_PER_US * EFF, depth * chunk / (rtt_us + serialize)) / 1e3

if __name__ == "__main__":
    total, chunk = 1 << 20, 16 << 10
    print(f"{'depth':>5} {'RTT us':>7} {'sim GB/s':>9} {'model GB/s':>11}")
    for rtt in (6, 30):
        for depth in (1, 2, 4, 8, 16):
            print(f"{depth:>5} {rtt:>7} {simulate(total, chunk, depth, rtt):>9.2f} {model(chunk, depth, rtt):>11.2f}")
B = min( R, D × C / (Trt + C/R) )

Interview

Beginner

  1. Why does one bad rkey fail many NVMe commands?

    Model answer

    Because all commands on an NVMe queue share one RC QP, and a remote access error moves that QP to the Error state, flushing every outstanding work request. The host must rebuild the queue (usually the whole association).

  2. What is a PSN?

    Model answer

    The 24-bit Packet Sequence Number in each BTH, per QP and direction. Receivers use it to detect gaps and duplicates; ACKs and NAKs refer to it.

  3. Who issues RDMA READ in NVMe/RDMA, and for what?

    Model answer

    The target, to fetch write data from the host's registered buffer described by a keyed SGL descriptor.

  4. What is a flush error?

    Model answer

    The status given to work requests that were outstanding when their QP entered Error. It reports collateral damage, not a root cause.

  5. Is a CNP an error?

    Model answer

    No. A Congestion Notification Packet tells a sender that ECN-marked packets arrived, so it should reduce its rate. It is a performance signal.

Intermediate

  1. How can a command use more than one keyed descriptor?

    Model answer

    SGL1 is a Last Segment descriptor that points to a list of keyed descriptors carried in the capsule after the SQE; the count is limited by MSDBD in Identify Controller and the capsule size by IOCCSZ.

  2. Why does a multi-key command always need local invalidation?

    Model answer

    SEND with Invalidate names one rkey in its IETH. Any additional keys must be invalidated by the host with Local Invalidate before it completes the request.

  3. Explain initiator depth and responder resources.

    Model answer

    Initiator depth is how many RDMA READs a requester may have outstanding; responder resources is how many the responder can serve at once. They are negotiated in the CM exchange; the effective depth is bounded by both.

  4. Why is tail loss worse than mid-message loss on RoCE?

    Model answer

    Mid-message loss is revealed by the next packet's PSN gap and answered quickly by a NAK. Loss of the final packet (or its ACK) is only detected when the local ACK timer expires, adding a timeout-length delay.

  5. What does an RNR NAK from the target indicate?

    Model answer

    The target had no receive buffer posted for an incoming SEND: a host exceeding CRQSIZE, a target SRQ over-subscribed, or slow receive reposting on the target.

Advanced

  1. Write throughput is 1 GB/s on a 100 GbE path with a 30 µs round trip. How do you prove READ depth is the cause?

    Model answer

    Capture: count outstanding READ requests over time (never above D) and check that new requests follow completions by one RTT. Compute D × C / RTT and compare. Change RTT (short path) and see throughput scale inversely. Read the CM REQ/REP depth fields.

  2. How do you tell a host registration bug from a target bounds bug after a remote access error?

    Model answer

    Compare the RETH (VA, key, length) with the SQE's keyed descriptors. If the target stayed within the advertised range and key, the host's MR did not cover what it advertised (host bug). If the target exceeded the advertised range or used another key, the target is wrong.

  3. Why can RDMA READ throughput depend on the host's PCIe settings?

    Model answer

    The host RNIC serves READs by issuing PCIe memory reads; MRRS, completion sizes, tags and completion buffering limit how fast it can fetch, adding a second bandwidth-delay limit inside the host.

  4. What makes the timeout/invalidation race dangerous, and what makes it safe?

    Model answer

    Danger: completing a timed-out request and reusing its buffer while the target still holds a valid key. Safety: ensure the key is invalidated (or the QP is in Error, which stops all remote access) before releasing the buffer or completing the request.

  5. Why does an MR-context cache miss show up on the host's PCIe link?

    Model answer

    The RNIC must fetch the missing context from host memory with PCIe reads before processing the packet, adding RNIC-originated MRd traffic and latency.

Senior

  1. Design a validation plan for QP error containment.

    Model answer

    Inject faults per QP (bad key, induced retry exhaustion, RNR exhaustion) under load on multiple queues. Pass criteria: only the affected queue's commands fail or are retried, exactly once; no data corruption (pattern verification); recovery time bounded; no leaked MRs or QPs after 1 000 cycles; other hosts unaffected. Record first-error WC statuses.

  2. A customer says "RDMA is unstable, switch to TCP." How do you respond?

    Model answer

    Ask for the first-error evidence: WC statuses, NAK types, switch counters. If the failures are retry-exceeded with drops on the RoCE priority, the network is lossy for RoCE; fix QoS or choose TCP/iWARP knowingly. If they are remote access errors, switching transport hides a host or target bug. Decide on evidence.

  3. How would you size target receive buffers with an SRQ for 200 hosts?

    Model answer

    The target promised CRQSIZE per QP; worst case is the sum of promises. An SRQ smaller than that is a bet on statistical multiplexing; quantify it with measured concurrency, add headroom, monitor RNR NAKs from the target, and bound promises if memory is limited.

  4. What evidence survives a reconnect, and how do you preserve it?

    Model answer

    Kernel logs with the first WC error, RNIC and switch counters (if snapshotted), and analyzer captures with triggers on NAKs or DREQ. Configure triggers and periodic counter snapshots before the incident; QP state itself is destroyed by recovery.

  5. When is per-command remote invalidation not worth it?

    Model answer

    When the target does not support it reliably or when a host registers long-lived buffers deliberately (with a security review). Otherwise it is cheap: it saves a local work request and closes the exposure window at completion.

Quiz

  1. Which QP state is required for NVMe I/O?

    • Init
    • RTR
    • RTS
    • SQD
    Answer and reasoning

    Ready to Send: both send and receive work are processed. RTR can receive only.

  2. SGL1 identifier 31h in a capsule means:

    • Keyed Data Block, address
    • Last Segment, offset (list in capsule)
    • Data Block, offset
    • Segment, address
    Answer and reasoning

    Type 3h (Last Segment), subtype 1h (Offset): the descriptor list is inside the capsule.

  3. Two keyed descriptors, response is SEND with Invalidate naming the first. The host must:

    • Locally invalidate the second key before completing
    • Complete immediately
    • Ask the target to resend
    • Reset the QP
    Answer and reasoning

    Only one key per IETH; the other needs Local Invalidate, and completion must wait for it.

  4. Write throughput scales inversely with round-trip time and shows no errors. Most likely limit:

    • MDTS
    • PFC
    • NVMe queue depth
    • RDMA READ depth
    Answer and reasoning

    A fixed number of outstanding READs over a round trip gives D × C / RTT.

  5. Drops on the RoCE priority with zero PFC pauses sent suggest:

    • A host driver bug
    • RoCE traffic not mapped to the lossless priority, or PFC off
    • Remote access errors
    • Normal operation
    Answer and reasoning

    PFC would pause rather than drop on a correctly configured lossless priority.

  6. Which status is collateral damage rather than a root cause?

    • Remote access error
    • Retry exceeded
    • Work request flush error
    • Local protection error
    Answer and reasoning

    Flush errors are assigned to work outstanding when the QP entered Error.

  7. Which loss is detected by timer rather than by NAK?

    • The last packet of a message
    • A middle packet
    • The first packet when more follow
    • None; all loss is NAKed
    Answer and reasoning

    No later packet reveals the gap, so the requester's local ACK timeout must expire.

  8. Open: why does the ambiguous trace need an unfiltered capture?

    Model answer

    The evidence of who acted first (an admin-queue Abort, a property read, host-initiated teardown on other queues) travels on other QPs, which the capture filter removed.

  9. Open: name two finite resources on the host and one on the target that can each stall NVMe/RDMA without any error on the wire.

    Model answer

    Host: MR pool, response receives (if reposting lags it produces RNR, which is visible but not an error), responder resources. Target: RDMA READ depth or staging memory. Each shows as gaps in time rather than error packets.

  10. Open: a host's I/O timeout is 30 s and the target's back end sometimes takes 35 s. Describe what a safe host does and what the wire shows.

    Model answer

    At 30 s the host stops trusting the command: it moves the QP to Error or invalidates the key before releasing the buffer, then recovers. At 35 s the target's RDMA WRITE (or READ) meets an invalid key and is NAKed with Remote Access Error, killing the target's QP if it still exists. No late data reaches application memory.

Teach-back

  1. To a child: explain why sending one wrong secret word cuts the whole zip line, and why that is safer than letting the crane open the wrong chest.

    Model explanation

    "If someone sends a wrong secret word, maybe something has gone wrong in the castle. The safest thing is to stop everything on that line straight away, so no treasure goes into the wrong chest. Then the castles build a fresh line and start again carefully."

  2. To a junior engineer: walk through a 256 KiB write with two keys and READ depth 16, naming who issues each operation and when the host may complete the request.

    Model explanation

    "The host fast-registers two MRs, builds an SQE whose SGL1 is a Last Segment pointing at two keyed descriptors in the capsule, and SENDs it. The target RNIC ACKs, the target issues sixteen 16 KiB RDMA READs using those keys, the host RNIC serves them from memory. The target writes to its SSD, then SENDs the CQE with Invalidate for one key. The host locally invalidates the other key and only then completes the request."

  3. To a senior engineer: argue which evidence you would collect, before an incident, to make the next NVMe/RDMA reconnect diagnosable within an hour.

    Model explanation

    "Persistent kernel logs with WC statuses; periodic snapshots of RNIC counters (retransmits, out-of-sequence, RNR, CNPs) and switch per-priority drops and pauses; an analyzer or mirror-port capture armed with a trigger on NAKs and DREQ with a large pre-trigger window and no QP filter; clock alignment via marker I/O; and a record of CM parameters per connection (depths, queue sizes). With that, the first error and its layer are visible immediately."

Mastery gate

Do not consider this module mastered until you can:

  • explain the QP as a failure domain and why flush errors follow one real error
  • diagram a multi-key NVMe/RDMA write including READ depth and local invalidation
  • identify in a trace: a PSN gap, a NAK type, READ-depth throttling and timer-driven retransmission
  • debug the six patterns on this page, naming first and second checks for each
  • distinguish NVMe/RDMA from neighbouring concepts: NVMe/TCP (software loss recovery, R2T), PCIe flow control (credits, no NAK-driven retries at the transaction layer), SGLs over PCIe (no keys), and fabric multipathing (what happens after the QP dies)
  • cite the applicable sources: NVMe over RDMA Transport 1.3, NVMe Base 2.4 (SGL, Identify Controller), IBTA Volume 1 with the RoCE v2 annex, IETF RFC 5040/5041/5044, IEEE 802.1Qbb
