How to study a new feature: the twelve questions

Every feature section below answers the same twelve questions. Learn the questions as a method you can reuse for every future release, not just as a way to read this page.

  1. What existed before?
  2. What changed?
  3. Why was it needed?
  4. What problem does it solve?
  5. Which specification contains it?
  6. Which revision introduced or updated it?
  7. Is it mandatory or optional?
  8. What hardware/software is affected?
  9. How could it appear in traces?
  10. How would a validation engineer test it?
  11. What could go wrong?
  12. Why should a senior engineer care?

Almost every feature added to NVMe in the 2.x era is Optional for a controller to implement and is discovered by the host through Identify Controller fields, supported-feature logs or capability bits. Some become required within a particular profile or by an industry specification that builds on NVMe (for example an Open Compute Project datacentre solid-state drive (SSD) specification). Unless you have read the requirement statement in Base 2.4, the honest answer is "probably optional — confirm in spec".

Most new features in this release live in admin commands, features, log pages and data structures. On NVMe over PCIe, an admin command looks the same on the link whatever it does: a doorbell write, a submission queue entry (SQE) fetch, possibly data, a completion queue entry (CQE), an interrupt. The meaning is inside the SQE and the data. A protocol analyzer with an NVMe decoder that knows the 2.4 definitions can name them; an older decoder will show "vendor-specific or unknown opcode". The visible effects of rate limiting and idle-latency limits are timing effects, not new packet types.

Post-quantum cryptography

Today's locks are very good against today's burglars. But a new kind of burglar is being trained who could open some of these locks quickly. Thieves could even steal locked boxes now and wait until that burglar is ready. So the library is adding new lock designs that the new burglar cannot open — before that burglar arrives.

Not all locks are at risk: the analogy hides that quantum attacks mainly threaten asymmetric (public-key) cryptography used for key exchange and signatures, while symmetric encryption such as the Advanced Encryption Standard (AES) with large keys is far less affected. It also hides that the change is in negotiation and authentication protocols, not in how data is stored on flash.

Twelve questions — post-quantum cryptography
#QuestionAnswer
1What existed before?NVMe 2.x already uses public-key cryptography in several places: in-band authentication for fabrics (DH-HMAC-CHAP: Diffie-Hellman Hashed Message Authentication Code Challenge Handshake Authentication Protocol, which uses finite-field Diffie-Hellman groups), Transport Layer Security (TLS) 1.3 for NVMe/TCP, and security protocols carried by Security Send/Receive. These rely on classical algorithms (Diffie-Hellman, elliptic-curve and RSA-family algorithms) whose security depends on problems a large quantum computer could solve.
2What changed?Asymmetric key-exchange algorithms were updated to prepare for post-quantum cryptography (PQC). Coverage names the US National Institute of Standards and Technology (NIST) Federal Information Processing Standards (FIPS) 203 (ML-KEM, a key-encapsulation mechanism), FIPS 204 (ML-DSA, signatures) and FIPS 205 (SLH-DSA, hash-based signatures), finalised by NIST in August 2024. Which NVMe protocols gained which algorithms, and how they are negotiated: confirm in spec (Base 2.4 security and authentication sections; TCP Transport 1.3 for TLS-related changes).
3Why was it needed?"Harvest now, decrypt later": recorded key exchanges can be broken later, exposing session keys. Drives deployed in 2026 may stay in service for many years.
4What problem does it solve?Keeps NVMe authentication and key establishment secure against future quantum attacks, and aligns with government and industry migration timelines toward PQC.
5Which specification?Base 2.4 (reported). Transport documents may be affected. Confirm in the Revision Changes document which documents changed.
6Which revision?Introduced in the 2.4 set (August 2026), as reported.
7Mandatory or optional?Confirm in spec. Expect algorithm support to be optional and negotiated.
8Hardware/software affectedController firmware and crypto engines (ML-KEM and ML-DSA keys and ciphertexts are much larger than elliptic-curve equivalents: kilobytes rather than tens of bytes); host authentication code (Linux nvme-auth, TLS libraries); key management systems; possibly NVMe-MI-based authentication paths.
9How could it appear in traces?On fabrics: larger authentication or handshake messages, more round trips, longer connect times. On PCIe: Security Send/Receive or authentication-related admin commands with larger data transfers. No new PCIe packet types.
10How would validation test it?Interoperability matrix (classical-only host vs PQC-capable controller and vice versa), negotiation downgrade attempts, large-message handling and fragmentation, connect-time budget under scale, negative tests with corrupted ciphertexts and signatures, known-answer tests against NIST vectors.
11What could go wrong?Silent downgrade to classical algorithms; buffer limits too small for PQC key sizes; timeouts during connect storms; interoperability gaps between implementations of different spec revisions; side-channel weaknesses in firmware implementations.
12Why should a senior engineer care?Crypto-agility is now an architectural requirement. Product lifetimes outlast algorithm lifetimes; security reviews will ask which NVMe paths are quantum-resistant.

Not established here: which NVMe protocols (DH-HMAC-CHAP, TLS, Security Protocol and Data Model (SPDM)-based or other) changed; whether hybrid (classical + PQC) modes are defined; identifiers for new algorithms or groups; whether signatures (ML-DSA, SLH-DSA) are used inside NVMe-defined protocols or only referenced. Read Base 2.4's authentication and security sections and the Revision Changes document.

PCIe Exported NVM Subsystem Migration

One big library building is divided into many small "pretend libraries", one for each class. Each class thinks it has its own library. Now a class must move to a different building without stopping lessons. The new building sets up a pretend library with exactly the same name plates and shelf numbers, using the same blueprint. Then the librarians copy over the "what is happening right now" notes, the class walks across, and the old pretend library is taken down.

The analogy hides that user data is not necessarily copied by this mechanism (storage may be shared or migrated separately — confirm in spec), that "what is happening right now" includes in-flight commands and queue state that must be quiesced and captured precisely, and that the virtual machine (VM)'s own memory migration is a hypervisor job outside NVMe.

The reported flow

  1. create Exported NVM Subsystem
  2. recreate controller + namespace, same IDs
  3. apply same configuration template (UUID)
  4. capture runtime state
  5. runtime state
  6. transfer + apply runtime state
  7. migrate the VM
  8. clean up source

Conceptual sequence of the reported steps. Command names, ordering constraints (for example when the source is paused) and state formats: confirm in Base 2.4.

The central concept on the ladder

Pretend libraries inside one building; a class moves to a new building using the same blueprint and a copy of "what is happening now".

An Exported NVM Subsystem is a virtual SSD presented from within a physical SSD to a VM. Migration recreates it on a destination SSD with identical identifiers and the same configuration template, then transfers runtime state.

Each physical SSD holds controller state, namespace mappings and queue state for each exported subsystem; it must be able to export that state in a portable form and import it.

Base 2.4 (reported) defines Exported NVM Subsystems, configuration templates identified by a 128-bit universally unique identifier (UUID), and the migration mechanisms. Field-level definitions: confirm in spec.

Management/admin commands from an orchestrator to source and destination; the VM's own I/O pauses and resumes around the switch.

On PCIe: admin commands with data transfers carrying state; a gap in the VM's I/O; then the VM's I/O resuming on the destination function. Distinctive packet types: none.

After migration, the VM sees errors or different behaviour: compare identifiers and configuration template UUIDs on both sides; check that all in-flight commands were completed or captured; check feature settings that the template may not cover.

TDISP information package

The TEE Device Interface Security Protocol (TDISP) is a PCI-SIG mechanism for confidential computing: it lets a trusted execution environment (TEE), such as a confidential VM, establish trust in a device interface, lock its configuration, and bring it into a secure running state, working with the Security Protocol and Data Model (SPDM) and PCIe Integrity and Data Encryption (IDE). Verified as a description of TDISP's purpose; read the PCIe specification family for detail.

Twelve questions — TDISP information package
#QuestionAnswer
1What existed before?TDISP at the PCIe level; NVMe-specific state was not reported in a standard package for the TEE to check.
2What changed?Controllers can report detailed state information as a "TDISP information package", used when validating controller state (for example during migration).
3Why was it needed?A confidential VM must verify that the NVMe controller assigned to it is configured as expected before trusting it, and must re-verify after events such as migration.
4What problem does it solve?Gives the TEE NVMe-level evidence, beyond PCIe-level device identity, about the controller's configuration.
5Which specification?Base 2.4 (reported); depends on PCI-SIG TDISP.
6Which revision?2.4 set (reported).
7Mandatory or optional?Confirm in spec.
8AffectedController firmware; TEE software (guest drivers, attestation verifiers); hypervisor; platforms with TDISP/IDE support.
9TracesDepends on how the package is retrieved — confirm in spec. TDISP/SPDM messages themselves are carried by PCIe mechanisms (e.g. Data Object Exchange) that an analyzer can show; encrypted IDE traffic hides payloads.
10ValidationPackage content matches actual configuration; package changes when configuration changes; consistent across migration; rejected/handled correctly in the locked states.
11What could go wrong?Package omits a security-relevant setting; stale package after reconfiguration; verifier accepts a package from the wrong device.
12Why care?Confidential computing is moving storage devices inside the trust boundary; debugging with encrypted links and locked configurations demands new methods.

Not established: package format, retrieval command or log, which fields are included, and how it binds to TDISP states. Confirm in Base 2.4 and the PCIe TDISP definitions.

Lockdown improvements

Twelve questions — lockdown improvements
#QuestionAnswer
1What existed before?A Command and Feature Lockdown mechanism in the Base specification lets a host prohibit specific commands or Set Features on specific interfaces (for example the admin queue vs management endpoints). Revision in which it was introduced: confirm in spec revision history.
2What changed?Lockdown settings can persist across reboots; separate lockdown controls exist for virtualized environments (reported).
3Why was it needed?Non-persistent lockdown must be re-applied by trusted software at each boot, leaving windows; in virtualized hosts, the host and the guests need different restrictions.
4What problem does it solve?Closes the boot-time window and lets cloud operators restrict guests without restricting themselves.
5Which specification?Base 2.4 (reported); NVMe-MI 2.2 possibly for management-interface scope — confirm.
6Which revision?2.4 set (reported).
7Mandatory or optional?Confirm in spec.
8AffectedController firmware; platform security software; hypervisors; Baseboard Management Controller (BMC) management policy (Chapter 63).
9TracesProhibited commands complete with an error status rather than executing; no new packet types.
10ValidationLockdown survives each kind of reset and power cycle as specified; correct scope (which interfaces, which controllers); how lockdown is cleared (and by whom); interaction with manufacturing reset.
11What could go wrong?Persistent lockdown that cannot be cleared — a drive bricked for a needed operation (e.g. firmware update); scope leaks between host and guests.
12Why care?Persistent state that changes what commands do is a debugging trap: "Invalid command" on one machine and success on another may be configuration, not a bug.

Rate limiting

Twelve questions — rate limiting
#QuestionAnswer
1What existed before?SR-IOV resource allocation (queues, interrupt vectors) per secondary controller, but no standard cap on bandwidth or I/O operations per second (IOPS); NVM Sets / Endurance Groups and Predictable Latency features for isolation; host-side throttling (e.g. Linux cgroup io.max); vendor-specific QoS.
2What changed?Controls to allocate PCIe bandwidth and IOPS among multiple controllers, with controller-enforced caps (reported).
3Why was it needed?Multi-tenant drives suffer "noisy neighbours"; host throttling cannot police guests that own a virtual function directly.
4What problem does it solve?Enforceable per-controller service levels inside the device.
5Which specification?Base 2.4 (reported).
6Which revision?2.4 set (reported).
7Mandatory or optional?Confirm in spec.
8AffectedController firmware schedulers; hypervisor/orchestrator; tenants' performance expectations; benchmarking tools.
9TracesTiming, not new packets: a capped controller's data Transaction Layer Packets (TLPs) and completions are spaced out; IOPS plateau while queue depth rises; latency grows by queueing. Units, burst behaviour and enforcement granularity: confirm in spec.
10ValidationMeasure achieved rate vs configured cap for several I/O sizes and mixes; isolation (one controller saturating cannot exceed its cap nor starve others); cap changes at runtime; behaviour at the boundaries (cap = 0, cap above physical capability); interaction with SR-IOV resource allocation.
11What could go wrong?Caps enforced at too coarse a time granularity (bursty latency); bandwidth counted differently than users expect (payload vs TLP bytes; read vs write); misconfiguration mistaken for a slow drive.
12Why care?Performance investigations must now ask "is a cap configured?" before blaming firmware, link or media.

Voltage monitoring

Twelve questions — voltage monitoring
#QuestionAnswer
1What existed before?Temperature sensors and thresholds, SMART critical warnings, power-state reporting; no standard reporting of supply voltage as seen by the device. Platforms used their own voltage sensors.
2What changed?Detection of discrepancies between the voltage the platform supplies and what the device receives; over/undervoltage thresholds with alerts and historical logs (reported).
3Why was it needed?Marginal power (connectors, backplanes, cables, regulator ageing) causes intermittent resets, link errors and data-integrity scares that are hard to attribute.
4What problem does it solve?Gives evidence at the device side, with history, so power problems can be separated from device faults.
5Which specification?Base 2.4 (reported); likely visible via NVMe-MI 2.2 for BMCs — confirm.
6Which revision?2.4 set (reported).
7Mandatory or optional?Confirm in spec.
8AffectedDevice hardware (sense circuits), firmware, host monitoring agents, BMC firmware, fleet analytics.
9TracesAlerts may surface as asynchronous events and log reads (mechanism: confirm in spec). Correlated PCIe symptoms of a real undervoltage may include link retraining or surprise link down — but those are effects, not the feature.
10ValidationProgrammable bench supply: sweep voltage, verify threshold crossing produces alerts with correct hysteresis; verify logs record events across resets; accuracy against a reference meter; no false alerts during normal transients (hot-plug inrush).
11What could go wrong?Inaccurate sensing; thresholds set too tight (alert storms) or too loose; history lost on power loss — exactly when it matters.
12Why care?"Unexplained resets" are among the costliest fleet issues; device-side voltage history turns arguments between platform and drive vendors into evidence.

Voltage-sweep validation is an Expert lab: driving a device outside its rated supply range can damage it and corrupt data. Use sacrificial units and follow the form-factor's electrical limits.

Idle I/O exit latency limits

Twelve questions — idle I/O exit latency limits
#QuestionAnswer
1What existed before?Power state descriptors with entry and exit latencies; Autonomous Power State Transition (APST), where the host gives the controller idle-time thresholds for entering non-operational states; PCIe Active State Power Management (ASPM) and L1 substates with Latency Tolerance Reporting (LTR) at the link level (Chapter 50).
2What changed?Hosts can specify latency thresholds that must be maintained when exiting idle to service I/O (reported).
3Why was it needed?APST expresses when to enter states; hosts also need to bound how long the first I/O after idle takes, which depends on the device's internal choices.
4What problem does it solve?Lets platforms save power aggressively without unbounded wake-up latency spikes.
5Which specification?Base 2.4 (reported); PCIe transport aspects possibly in PCIe Transport 1.4 — confirm.
6Which revision?2.4 set (reported).
7Mandatory or optional?Confirm in spec.
8AffectedController power management firmware; OS power policy (Linux nvme_core APST parameters, platform power daemons); laptop and datacentre power tuning.
9TracesTiming: the gap between the first doorbell after idle and the SQE fetch (plus any link exit from L1.x seen as electrical idle exit and retraining activity). Measure against the configured limit.
10ValidationIdle for varying periods, then issue a single I/O; histogram first-I/O latency; verify it stays within the configured threshold across temperatures and states; verify the setting persists or resets as specified.
11What could go wrong?Link-level exit latency (ASPM) not accounted for in the device's promise; host misconfigures thresholds and loses power savings; interaction with APST tables.
12Why care?Tail latency after idle is a common client complaint and a datacentre power-cost lever; this feature makes it negotiable instead of anecdotal.

What changed from NVMe 2.3 to 2.4? A guided reading exercise

This section does not give you a list of differences, because a list from this course would be second-hand. It teaches you to produce your own, from the primary sources, in a form you can defend in a design review.

Materials

  • NVM Express Revision Changes 2026.07.30 — the authoritative change list, linked from the Revision Changes page on nvmexpress.org.
  • NVM Express Base Specification, Revision 2.4 and the previous revision you already use (the 2.3 set).
  • The other ten documents of the 2.4 set, as needed.

Step 1 — Inventory

Open the Revision Changes document. For each entry, record: document affected, short title, type (new feature, clarification, errata incorporation, editorial), and the technical proposal or errata identifier if one is cited. Do not interpret yet.

Step 2 — Classify impact

For each entry, mark whether it changes: (a) host-visible commands or data structures; (b) required behaviour of existing features; (c) only text. Entries in (b) are the dangerous ones — existing implementations may become non-compliant without anyone adding a feature.

Step 3 — Map the reported features

Find each of the eight features covered on this page in the change list and in Base 2.4. Fill in the "Confirm in spec" cells: opcode or mechanism, data structures, optional/mandatory, discovery bit.

Step 4 — Check backward compatibility

For each new field, find what a 2.3-era host does when it sees it (ignores reserved bits?) and what a 2.4 host does with a 2.3-era controller (capability absent). Write one sentence per feature.

Step 5 — Decide trace and decoder impact

For each change, decide whether your protocol analyzer's NVMe decoder, your nvme-cli version and your test suites need updating. Most 2.4 features will appear as admin commands, features or logs that old decoders show as unknown.

Step 6 — Write the delta memo

One page: top five changes that matter to your product, with citations by document and section name, the compatibility sentence, and the validation work needed.

What a good delta memo looks like (template, not answers)

Feature: [name] — Document: [Base 2.4, section name] — Type: new optional feature / behaviour change — Discovery: [field name in Identify or log] — Compatibility: [one sentence] — Our impact: firmware / driver / tests / decoder — Validation: [three test ideas] — Open questions: [what the text leaves implementation-dependent].

2026 features lab

One lab card per feature. Each card has the six elements: reading task, source, concept map, "what changed" exercise, "what is not specified here" exercise, and a validation thought experiment. No card asks you to produce a packet trace, because none of these features necessarily has a direct PCIe trace signature.

Safe lab — reading and reasoning only. Hardware extensions are marked separately.

Card 1 — Post-quantum cryptography

Reading task
Find every place Base 2.4 defines or references asymmetric key exchange or signatures. List the algorithms and how they are negotiated.
Source
Base 2.4 (authentication, security sections); TCP Transport 1.3 (TLS); Revision Changes 2026.07.30; NIST FIPS 203/204/205.
Concept map
Threat (quantum attack on public-key crypto) → affected NVMe protocols → algorithm negotiation → key sizes → buffer/transport limits → interoperability.
What changed
Write the before/after algorithm list for each protocol.
Not specified here
List what the spec leaves to implementations (e.g. side-channel protections, performance) and what it delegates to external standards.
Validation thought experiment
A classical-only host connects to a PQC-capable target that prefers PQC. What should happen, and how would you prove no silent downgrade occurred?

Card 2 — PCIe Exported NVM Subsystem Migration

Reading task
Locate the definitions of Exported NVM Subsystem and configuration template; trace the commands that implement each of the reported eight steps.
Source
Base 2.4; PCIe Transport 1.4; Revision Changes 2026.07.30.
Concept map
Physical subsystem → exported subsystem → exported controller + namespace → identifiers → configuration template (UUID) → runtime state → transfer → VM switch → cleanup.
What changed
Compare with SR-IOV-only virtualization (Chapter 56): what can now move that could not before?
Not specified here
What about user data, hypervisor memory migration, orchestrator protocols, and transfer security? Which are outside NVMe?
Validation thought experiment
Migrate while a 1 MiB write is half transferred. Define the pass criteria from the specification's rules on quiescence.

Card 3 — TDISP information package

Reading task
Find how the package is obtained and what it contains; relate it to TDISP states.
Source
Base 2.4; PCI-SIG TDISP and IDE definitions; Distributed Management Task Force (DMTF) SPDM.
Concept map
TEE → TDISP lock → NVMe state package → verifier policy → RUN state → migration → re-verify.
What changed
What NVMe-level evidence is available now that was not before?
Not specified here
Verifier policy (what values are acceptable) is not an NVMe matter — confirm.
Validation thought experiment
Change one feature setting after the package is read. How does the TEE detect it?

Card 4 — Lockdown improvements

Reading task
Find the persistence rules and the virtualization-specific scopes.
Source
Base 2.4 (Command and Feature Lockdown); NVMe-MI 2.2.
Concept map
Command/feature → interface scope → persistence → reset types → clearing authority.
What changed
Table: setting × reset type × persists before/after 2.4.
Not specified here
Who in your organisation is authorised to set persistent lockdown — a policy, not a spec, question.
Validation thought experiment
A persistent lockdown blocks Firmware Commit; a critical firmware fix must ship. Design the recovery path.

Card 5 — Rate limiting

Reading task
Find units, granularity, scope (per controller? per function?) and burst rules.
Source
Base 2.4.
Concept map
Tenant → controller → cap (bandwidth, IOPS) → scheduler → achieved rate → latency (Little's law).
What changed
Compare with SR-IOV resource allocation: resources vs rates.
Not specified here
Scheduler algorithm and fairness between uncapped controllers — likely implementation-dependent; confirm.
Validation thought experiment
Cap = 100k IOPS; a tenant issues 128 KiB reads. Which limit applies first — IOPS or bandwidth — and how do you measure each?

Card 6 — Voltage monitoring

Reading task
Find thresholds, alert mechanism, and history log definitions.
Source
Base 2.4; NVMe-MI 2.2.
Concept map
Platform supply → connector/backplane drop → device sense → threshold → alert → log → BMC/host.
What changed
Compare to temperature thresholds and SMART warnings (Chapter 57).
Not specified here
Sensor accuracy and sampling rate — likely implementation-dependent; confirm.
Validation thought experiment
A 2 ms undervoltage dip during hot-plug of a neighbour drive: should it alert? Defend your answer from the text.

Card 7 — Idle I/O exit latency limits

Reading task
Find how the host sets the threshold and how it relates to power-state descriptors and APST.
Source
Base 2.4; PCIe Transport 1.4; PCIe Base (ASPM, LTR).
Concept map
Idle time → power state → link state → exit latency (device + link) → host threshold.
What changed
Before: host chose states by tables; after: host states a latency bound (reported).
Not specified here
Whether link-level exit latency is included — confirm.
Validation thought experiment
Threshold 100 µs; ASPM L1.2 exit alone takes longer on the platform. Whose problem is it?

Card 8 — Restore manufacturing default settings

Reading task
Find exactly what is restored, what is erased, what is preserved, and who may invoke it.
Source
Base 2.4; NVMe-MI 2.2.
Concept map
Configuration state (namespaces, features, lockdown, security) → reset → as-shipped state; relation to Format/Sanitize.
What changed
Compare with Sanitize: data vs configuration.
Not specified here
Your decommissioning policy (is a sanitize also required?).
Validation thought experiment
Power is lost halfway through. What must the device look like on the next power-on?

Lab — Build a 2.4 delta memo and a validation plan

Objective

Produce a verified delta memo for two 2.4 features and a validation plan for one of them.

Skills

Specification reading, change classification, test design, honest uncertainty labelling.

Safety

Safe lab (reading). The optional hardware step is Caution lab.

Hardware required

None. Optional: a drive whose firmware claims 2.4 features.

Software required

PDF reader; optionally nvme-cli (a version that decodes 2.4 structures).

Input

Revision Changes 2026.07.30; Base 2.4.

Expected output

Two delta memo entries (template in the reading section) and a ten-test validation plan.

Background

The twelve-questions method; the reading pipeline.

Step 1

Choose rate limiting and manufacturing reset. Complete Steps 1–4 of the reading exercise for both.

Step 2

For rate limiting, write ten test cases: each with configuration, stimulus, measurement, pass criterion, and the specification statement it derives from.

Step 3

Mark every pass criterion as normative (from a "shall"), derived, or implementation-dependent.

Observation

Count how many of your criteria are normative. If fewer than half, ask what the vendor must document for the rest.

Questions

  1. Which of your tests would detect a cap enforced only on average over one second?
  2. Which features on this page could interact with manufacturing reset?

Challenge

Add a test that distinguishes "rate limited by cap" from "rate limited by thermal throttling".

Hints

Thermal throttling correlates with temperature and with SMART thermal-management counters; a cap does not, and its plateau is flat at the configured value regardless of temperature.

Solution outline

A good plan includes: steady-state accuracy at several I/O sizes; read/write/mixed; burst behaviour measured in 1 ms windows (answers Q1: averaging windows hide bursts); isolation between two capped and one uncapped controller; runtime cap changes; cap persistence across reset per spec; boundary values; interaction with SR-IOV resource limits; correct error/status for invalid configuration; and the thermal discriminator (log temperature and throttling counters during the plateau). Q2: lockdown (can persistent lockdown block or survive the reset?), rate-limit and other saved configuration, voltage-monitoring thresholds and history, security/PQC credentials — each is a "what is restored" question for the specification.

What a senior engineer notices

Whether each test cites the specification, and whether the plan has a clear list of questions for the vendor where the specification is silent.

Failure variants

  • Cap applies per function but test assumes per controller.
  • Tooling reports TLP bytes; the cap counts payload bytes.
  • Manufacturing reset preserves a setting the plan assumed restored.

Extension

On a drive that supports a 2.4 feature, capture an analyzer trace while configuring it, and annotate which commands your decoder names correctly and which it shows as unknown.

Why this release matters to a senior engineer

  • NVMe is now a platform protocol. Security (PQC, TDISP, lockdown), virtualization (exported subsystems, migration, rate caps) and operations (voltage, manufacturing reset, power latency) are converging into one specification family. Architecture reviews must include NVMe experts early.
  • State outlives sessions. Persistent lockdown, migrated runtime state and configuration templates mean a drive's behaviour depends on history. Debugging must start with a configuration snapshot.
  • Tooling lags specifications. Analyzer decoders, nvme-cli and kernels need time to learn 2.4 structures. Until then, "unknown opcode" in a trace is a tooling fact, not a device fact.
  • Evidence discipline is the skill. Most of this page says "confirm in spec". Engineers who can turn those cells into cited facts quickly are the ones teams rely on after every release.

Quiz

  1. When was the NVMe 2.4 specification set released?

    • 31 July 2026
    • 30 July 2026
    • 4 August 2026
    • August 2024
    Answer and reasoning

    Released 4 August 2026. Base 2.4 was ratified 31 July 2026; the Revision Changes document is dated 2026-07-30; August 2024 is when NIST finalised FIPS 203/204/205.

  2. Which document is the authoritative list of what changed?

    • Press coverage of the release
    • NVM Express Revision Changes 2026.07.30
    • The NVMe-MI 2.2 specification
    • This course
    Answer and reasoning

    The Revision Changes document, linked from nvmexpress.org, is authoritative; press coverage is secondary.

  3. What identifies a configuration template ("blueprint") in Exported NVM Subsystem Migration, as reported?

    • A 128-bit UUID
    • An NVMe Qualified Name (NQN)
    • A PCIe Requester ID
    • A namespace ID
    Answer and reasoning

    Reported as a 128-bit UUID.

  4. Which NIST standard defines ML-KEM?

    • FIPS 197
    • FIPS 203
    • FIPS 204
    • FIPS 205
    Answer and reasoning

    FIPS 203 is ML-KEM; 204 is ML-DSA; 205 is SLH-DSA; 197 is AES.

  5. Why does this page refuse to show packet traces for most 2.4 features?

    Model answer

    They live in admin commands, features and logs that look like any other admin traffic on PCIe, or they show only as timing effects; inventing distinctive packets would teach false signatures.

  6. A capped controller at queue depth 64 and cap 200,000 IOPS: expected mean latency?

    Model answer

    Little's law: W = L/λ = 64 / 200,000 s = 320 µs (if the cap is the bottleneck).

  7. Name two features from this release that create persistent state affecting later debugging.

    Model answer

    Persistent lockdown; rate-limit configuration; migrated runtime state and templates; voltage history (as evidence).

  8. Is rate limiting mandatory in NVMe 2.4?

    Model answer

    Not established from verified sources — expected optional, confirm in Base 2.4's requirement statements.

  9. What is the difference between manufacturing reset and Sanitize, as far as this course can verify?

    Model answer

    Sanitize erases user data; manufacturing reset returns the subsystem to as-shipped state. Whether manufacturing reset also erases data is not verified here — read Base 2.4.

  10. Why does every document get a new revision number even if a command set gained no feature?

    Model answer

    The documents cross-reference each other and were revised together; a revision may reflect alignment, clarifications or errata, not necessarily new features. The Revision Changes document tells you which.

Interview questions

  1. Beginner: What is the current NVMe baseline and how do you verify it?

    Model answer

    The August 2026 NVMe 2.4 set (Base 2.4 and ten companion documents). Verify on nvmexpress.org's specifications page and the Revision Changes page.

  2. Intermediate: Why does NVMe need post-quantum cryptography if data on flash is encrypted with AES?

    Model answer

    The risk is in public-key key exchange and authentication (fabrics, security protocols), which a quantum computer could break; recorded sessions could be decrypted later. AES with large keys is much less affected.

  3. Advanced: Outline the reported Exported NVM Subsystem migration flow and the riskiest step.

    Model answer

    Create on destination; recreate controller/namespace with matching identifiers; apply the same template; capture runtime state; transfer and apply; migrate VM; clean source. Riskiest: capturing and applying runtime state consistently with in-flight commands.

  4. Senior: How do you brief a team on a new NVMe release when only press coverage is available?

    Model answer

    Teach purpose and architectural impact, label everything as secondary, list concrete reading tasks in the primary documents with owners, and gate implementation decisions on verified delta memos.

  5. Senior: What should a validation strategy for 2.4 prioritise?

    Model answer

    Behaviour changes to existing features first (they can break compliance silently), then security features (downgrade, persistence), then multi-tenant features (isolation, migration), with tooling (decoders, nvme-cli) updated in parallel.
