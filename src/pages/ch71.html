When an NVMe SSD or its PCIe link misbehaves, the Linux kernel is usually the first witness to write anything down. This chapter teaches you to read that testimony: dmesg and journalctl patterns for link errors, Advanced Error Reporting, Downstream Port Containment, hot-plug link down/up, IOMMU faults, NVMe timeouts, aborts, resets and controller failure, and how to turn a wall of messages into an ordered timeline that you can correlate with traces.

Why this chapter exists

Most real NVMe incidents are investigated after the fact. Nobody had an analyzer attached; nobody was tracing. What remains is the kernel log: a few dozen lines from the PCI core, the port services (AER, DPC, hot-plug), the IOMMU driver, the NVMe driver, the block layer and the filesystem, each printed by a different piece of code with its own vocabulary and its own idea of time.

Read naively, the log misleads. The loudest line is rarely the first event. "I/O error" is a consequence, not a cause. A controller reset message tells you what the driver did, not what the device did. Read carefully, the same log lets you rebuild the sequence of events, identify the layer where the first abnormal event happened, and choose the next experiment.

This chapter is the Linux-side companion to error correlation in Chapter 47: there you learned to reason across layers; here you learn the exact form in which Linux reports each layer.

Learning objectives

  • Use dmesg and journalctl effectively: boots, time formats, priority filters, pattern searches, following live, and the limits of each.
  • Recognize the message prefixes (pci, pcieport, nvme nvme0, nvme 0000:01:00.0, nvme0n1, DMAR, AMD-Vi, block and filesystem) and the code that prints each.
  • Read AER messages field by field: severity, type, agent ID, status/mask, bit names, TLP Header log.
  • Recognize the patterns of: correctable link errors, uncorrectable errors, DPC containment, hot-plug link down/up, NVMe command timeout → abort → reset, controller-fatal status, device-gone (all-ones), I/O errors with NVMe status, and IOMMU translation faults.
  • Build a timeline, find the first abnormal event, state what each line proves and does not prove, and correlate with tracepoints, nvme-cli logs and analyzer traces.

NVMe status codes and error reporting (Chapter 44), PCIe error classes (Chapter 45), AER (Chapter 46), error correlation (Chapter 47), NVMe and PCIe resets (Chapter 48, Chapter 49), advanced error handling including DPC (Chapter 55), DMA and address translation (Chapter 20), and the Linux inspection tools of Chapter 69 and Chapter 70.

The story

The school office keeps a diary. Whenever something happens, whoever noticed it writes one line: the road guard writes "a truck arrived with a scratched box", the gate keeper writes "the road to the library closed", the teacher writes "I asked the librarian for a book half a minute ago and got no answer, so I am ringing the bell again". Later, when the headmaster wants to know what went wrong, she reads the diary. But she has to be careful: the teacher's line about "no answer" was written thirty seconds after the road guard's line about the road closing, and the road closing is the real reason.

Adult version: the kernel log is like the combined radio log of an airport, where the tower, ground control, the fire service and each airline write into one shared logbook. Every entry is true from its writer's point of view, entries carry the time of writing (not of the event), some writers only write when they notice a problem long after it began, and some suppress repeated entries ("and 40 similar messages") when things get busy.

Where the analogy breaks. (1) An airport log is kept by people who can describe what they saw; kernel code prints fixed templates with numbers that need decoding. (2) A logbook persists; the kernel ring buffer has a fixed size and old messages are overwritten, and messages from the boot that crashed may be lost unless the journal is persistent or pstore captured them. (3) In the airport, the fire service knows about the tower; in the kernel, the AER driver and the NVMe driver often report the same incident independently without referring to each other, so you must do the joining. (4) Some events are never logged at all: errors that firmware handled (firmware-first), masked errors, and a link that recovered silently.

Beginner explanation

The kernel writes messages into a ring buffer in memory. dmesg prints that buffer. On systems with systemd, the journal daemon copies kernel messages into the journal, and journalctl -k shows them, including from earlier boots if the journal is stored persistently.

sudo dmesg -T | grep -iE 'nvme|aer|dpc|pciehp|dmar|amd-vi'   # this boot, human time
journalctl -k -b -1 | grep -iE 'nvme|aer'                    # previous boot (needs persistent journal)
sudo dmesg -w                                                # follow new messages live

Each line starts with a timestamp. By default dmesg shows seconds since boot ([ 5012.000431]), a monotonic clock that is the best clock for ordering kernel events. dmesg -T converts to wall-clock time but can be wrong after the system has been suspended. journalctl shows wall-clock time by default and can show the monotonic value with -o short-monotonic.

Then comes a prefix that tells you which code printed the line and about which device. Learning those prefixes is half of reading the log.

Safe lab Reading logs never touches a device. Some distributions restrict dmesg to root (kernel.dmesg_restrict). Do not clear the ring buffer (dmesg -c / -C) on a system under investigation: you would destroy evidence other people may need.

Pattern 1: enumeration and link bandwidth (the baseline you need)

Before you read failure messages, know what a healthy boot says. Synthetic example for teaching:

[    1.204118] pci 0000:01:00.0: [10ab:c0de] type 00 class 0x010802 PCIe Endpoint
[    1.204190] pci 0000:01:00.0: BAR 0 [mem 0xfe600000-0xfe603fff 64bit]
[    1.204551] pci 0000:01:00.0: 63.016 Gb/s available PCIe bandwidth, limited by 16.0 GT/s PCIe x4 link at 0000:00:01.1 (capable of 63.016 Gb/s with 16.0 GT/s PCIe x4 link)
[    2.811034] nvme nvme0: pci function 0000:01:00.0
[    2.835520] nvme nvme0: 32/0/0 default/read/poll queues
[    2.840911]  nvme0n1: p1 p2

The bandwidth line is printed at enumeration; when the "available" figure is lower than the "capable" figure, the line names the link that limits it. It is the kernel's own version of the LnkCap/LnkSta comparison. 32/0/0 default/read/poll queues says the driver created 32 I/O queues of the default type and none dedicated to reads or polling. Save a healthy boot log from every lab machine: it is the "golden" reference against which you diff a bad one.

Pattern 2: correctable link errors (AER, Physical/Data Link Layer)

[ 4012.517802] pcieport 0000:00:01.1: AER: Correctable error message received from 0000:01:00.0
[ 4012.517826] nvme 0000:01:00.0: PCIe Bus Error: severity=Correctable, type=Physical Layer, (Receiver ID)
[ 4012.517830] nvme 0000:01:00.0:   device [10ab:c0de] error status/mask=00000001/0000e000
[ 4012.517834] nvme 0000:01:00.0:    [ 0] RxErr                  (First)
  • Line 1: the root port received an ERR_COR Message whose requester was 01:00.0. The root port is the reporter; the SSD is the source.
  • Line 2: severity Correctable; type=Physical Layer is the layer the kernel associates with the set bit; (Receiver ID) says the ID logged is the receiver that detected the error, i.e. the error was on traffic arriving at the SSD (downstream direction).
  • Line 3: the raw Correctable Error Status register (bit 0 set) and Mask register (bits 13–15 masked).
  • Line 4: decoded bit 0, Receiver Error.

What it proves: the SSD's receiver detected at least one physical-layer error, which the link corrected (by replay or by the error being benign). What it does not prove: data corruption (none, by definition of correctable), or the cause (signal integrity, reference clock, power noise, equalization). A handful per day can be normal on some platforms; a rising rate or a burst before an uncorrectable error is a warning. Other correctable bits: BadTLP (LCRC or sequence error at the Data Link Layer), BadDLLP, Rollover (replay number rollover), Timeout (replay timer timeout) — all Data Link Layer recovery signals (see Chapter 15).

Pattern 3: uncorrectable non-fatal errors (Transaction Layer)

[ 5102.330114] pcieport 0000:00:01.1: AER: Uncorrected (Non-Fatal) error message received from 0000:01:00.0
[ 5102.330139] nvme 0000:01:00.0: PCIe Bus Error: severity=Uncorrected (Non-Fatal), type=Transaction Layer, (Requester ID)
[ 5102.330143] nvme 0000:01:00.0:   device [10ab:c0de] error status/mask=00004000/00400000
[ 5102.330147] nvme 0000:01:00.0:    [14] CmpltTO                (First)
[ 5102.330160] nvme 0000:01:00.0: AER:   TLP Header: 00000000 00000000 00000000 00000000
[ 5102.330198] nvme 0000:01:00.0: AER: device recovery successful

Bit 14 is Completion Timeout: the SSD, as a requester, issued a non-posted request (most likely a memory read: an SQE fetch, a PRP list fetch or write data being fetched from host memory) and no completion arrived within its Completion Timeout window. (Requester ID) marks the SSD as the requester. For Completion Timeout the header log is typically empty because the device does not have a received TLP to log; for Malformed TLP or Unsupported Request the header log holds the offending TLP's header, which you decode with the tools of Chapter 11.

Consequences to look for next: an NVMe command whose data or SQE fetch failed. The controller will typically complete that command with an error status (for example a Data Transfer Error) or may stall it, which leads to a timeout message from the NVMe driver later. Causes to consider: host memory read latency beyond the device's timeout setting (DevCtl2 range too short), IOMMU blocking the read (look for an IOMMU fault line at the same moment), a root complex problem, or a link retraining event that delayed completions.

AER: device recovery successful means the kernel ran the error recovery callbacks of the bound driver (for non-fatal errors, usually without resetting the link) and they reported recovered. It does not mean the NVMe command that suffered was retried successfully: check the NVMe lines.

Pattern 4: fatal errors, Surprise Down and Downstream Port Containment

When the root port supports Downstream Port Containment (DPC) and Linux has it enabled, an uncorrectable error (per its configuration) makes the port immediately disable the link to contain the error. Linux then runs recovery: the driver's error callbacks, waiting for the link to come back, a slot reset, and resume.

[ 7301.004410] pcieport 0000:00:01.1: DPC: containment event, status:0x1f01 source:0x0000
[ 7301.004418] pcieport 0000:00:01.1: DPC: unmasked uncorrectable error detected
[ 7301.004431] pcieport 0000:00:01.1: PCIe Bus Error: severity=Uncorrected (Fatal), type=Transaction Layer, (Receiver ID)
[ 7301.004435] pcieport 0000:00:01.1:   device [1022:1483] error status/mask=00000020/00000000
[ 7301.004439] pcieport 0000:00:01.1:    [ 5] SDES                   (First)
[ 7301.004511] nvme nvme0: frozen state error detected, reset controller
[ 7301.452109] pcieport 0000:00:01.1: pciehp: Slot(1): Link Down
[ 7301.903377] pcieport 0000:00:01.1: pciehp: Slot(1): Link Up
[ 7302.118004] nvme nvme0: restart after slot reset
[ 7302.402331] nvme nvme0: 32/0/0 default/read/poll queues
[ 7302.410822] pcieport 0000:00:01.1: AER: device recovery successful

How to read it: the root port (vendor ID shown is the root port's, here a placeholder) triggered containment; the reported error was Surprise Down Error (SDES, bit 5), meaning the link went down unexpectedly from the port's point of view. The NVMe driver was told the channel is frozen and prepared for a reset; hot-plug saw the link go down and up (with DPC, these lines may or may not appear, depending on configuration); the driver re-initialized the controller and recreated 32 I/O queues. In-flight commands were failed back to the block layer or requeued.

What it proves: the link went down unexpectedly, the platform contained it, and recovery succeeded. What it does not prove: why the link went down (device firmware crash and PHY reset, power glitch, connector, retimer). The DPC status and source registers encode the trigger reason and source; decode them with the DPC capability layout in the PCIe Base Specification. Do not guess bit meanings from memory

Platform-dependent: with firmware-first error handling (common on servers, signalled through ACPI APEI/GHES), the kernel may print {1}[Hardware Error]: … records from GHES instead of the native AER lines, or may not see some errors at all. DPC may be owned by firmware (EDR, Error Disconnect Recover) rather than the OS. Always establish which mode the platform uses before concluding "the OS never saw an error".

Pattern 5: hot-plug link down/up without DPC

[ 8120.771203] pcieport 0000:00:01.1: pciehp: Slot(1): Link Down
[ 8120.771240] pcieport 0000:00:01.1: pciehp: Slot(1): Card not present
[ 8120.790115] nvme nvme0: controller is down; will reset: CSTS=0xffffffff, PCI_STATUS=0xffff
[ 8120.812554] nvme0n1: detected capacity change from 1953525168 to 0
[ 8120.812990] I/O error, dev nvme0n1, sector 18800640 op 0x1:(WRITE) flags 0x8800 phys_seg 1 prio class 0
[ 8120.861732] nvme nvme0: Removing after probe failure status: -19

Card not present comes from the slot's Presence Detect: the device is physically gone or lost power. CSTS=0xffffffff, PCI_STATUS=0xffff is the all-ones signature from Chapter 69: the driver read the CSTS register and the PCI Status register and both came back as all ones, so the device is not reachable. Error -19 is ENODEV. The I/O error is a consequence. If instead the log shows Link Down without Card not present and then Link Up, the device stayed present but the link dropped: a device reset, firmware crash, power-state problem or signal issue.

Pattern 6: NVMe command timeout → abort → reset

The NVMe driver arms a timer for each request (nvme_core.io_timeout, default 30 s; admin commands use admin_timeout, default 60 s). When it fires, the PCIe driver's timeout handler first checks whether the controller is alive (reads CSTS), checks whether the completion is actually sitting in the CQ (a missed interrupt), and then escalates: Abort command first, controller reset if the abort fails or times out.

[ 9030.118702] nvme nvme0: I/O tag 419 (01a3) opcode 0x2 (I/O Cmd) QID 2 timeout, aborting req_op:READ(0) size:131072
[ 9030.118950] nvme nvme0: Abort status: 0x0
[ 9060.230113] nvme nvme0: I/O tag 419 (01a3) opcode 0x2 (I/O Cmd) QID 2 timeout, reset controller
[ 9060.611087] nvme nvme0: 32/0/0 default/read/poll queues
[ 9060.611540] nvme0n1: I/O Cmd(0x2) @ LBA 3813120, 256 blocks, I/O Error (sct 0x3 / sc 0x71)
[ 9060.611566] I/O error, dev nvme0n1, sector 3813120 op 0x0:(READ) flags 0x80700 phys_seg 32 prio class 0
  • tag 419 (01a3): the block-layer tag and the NVMe command identifier in hex. On recent kernels the CID may include generation bits, so it can differ from the tag. This CID is your join key with tracepoints (Chapter 70) and with the SQE on an analyzer.
  • opcode 0x2 on an I/O queue is Read (NVM command set). QID 2 is the I/O queue.
  • Abort status: 0x0: the Abort command itself completed successfully. That only means the controller accepted the abort request; the timed-out command was still not completed, so 30 seconds later the driver escalated to a controller reset.
  • After the reset, the driver recreated the queues; the stuck request was completed with a host-synthesized status. sct 0x3 / sc 0x71 is shown here as an example of a path-related status code that Linux uses for host-aborted commands; confirm the exact SCT/SC your kernel assigns and its name in the Path Related Status table of the NVMe Base Specification 2.4. Crucially, this status was not sent by the device.

A timeout message is printed io_timeout after the command was submitted. The real first abnormal event happened up to 30 seconds earlier. Always look backwards from a timeout line for AER, DPC, IOMMU or link messages in that window.

[    3.912003] nvme nvme0: pci function 0000:01:00.0

[   64.121022] nvme nvme0: Removing after probe failure status: -19

The controller was enabled (CC.EN = 1) but CSTS.RDY never became 1 within the CAP.TO timeout (60 s here). PCIe works (config space read, BAR mapped); the controller's firmware did not finish starting. Look at firmware revision, a recent firmware update, or a drive in a vendor "safe mode".

Pattern 8: I/O errors carrying a device status

[10433.517220] nvme0n1: I/O Cmd(0x2) @ LBA 774016, 8 blocks, I/O Error (sct 0x2 / sc 0x81) DNR
[10433.517301] critical medium error, dev nvme0n1, sector 774016 op 0x0:(READ) flags 0x0 phys_seg 1 prio class 0

Here the device completed the command with status SCT 2h (Media and Data Integrity Errors), SC 81h (Unrecovered Read Error), with Do Not Retry set. The block layer maps it to a "critical medium error". No timeout, no reset, no AER: the transport worked perfectly and delivered bad news. Correlate with nvme error-log (an entry with the same LBA is likely) and media_errors in smart-log. The verbose NVMe decode line appears only on kernels with verbose error reporting enabled (kernel-configuration-dependent); otherwise you see only the block-layer line.

Pattern 9: IOMMU translation faults

With an IOMMU enabled (the reference system), every DMA address the SSD emits is an I/O virtual address (IOVA). If the address is not mapped, or mapped without the needed permission, the IOMMU blocks the access and logs a fault.

[11210.004418] DMAR: DRHD: handling fault status reg 2
[11210.004431] DMAR: [DMA Write NO_PASID] Request device [01:00.0] fault addr 0x1fff00000 [fault reason 0x05] PTE Write access is not set

[11210.004502] nvme 0000:01:00.0: AMD-Vi: Event logged [IO_PAGE_FAULT domain=0x000e address=0x1fff00000 flags=0x0020]

Read: the requester (01:00.0, the SSD), the direction (a DMA write: the device writing to host memory, as for read data or a CQE), the IOVA (0x1fff00000), and the reason (no write permission or no mapping). On the wire the SSD sent a perfectly valid MWr TLP; the platform refused it. The device may receive an error completion for reads, and for writes the data is silently dropped; the NVMe command will then fail, hang or complete with corrupted host-side data. Platform-dependent The reason codes and flag bits are IOMMU-architecture-specific: decode them with the Intel VT-d or AMD IOMMU specification, not from memory.

Typical causes: a driver bug (buffer unmapped before the device finished, use-after-free of a DMA buffer), a device bug (DMA to a stale PRP from a previous command, or to an address beyond the PRP list), or a passthrough misconfiguration. The faulting address is the key: compare it with the PRP entries in the command's SQE (from a trace) and with the queue base addresses.

The central concept on the ladder: a log line as evidence

Different helpers write in one diary when they notice trouble. Each line is true for its writer, but the writer may notice late, and the loudest line is not always the first problem.

Kernel subsystems (PCI core, AER, DPC, hot-plug, IOMMU, NVMe driver, block layer, filesystems) print templated messages with a monotonic timestamp and a device name. You order them, classify them by layer and find the earliest abnormal one.

Behind each message is a hardware event the kernel noticed: an error Message TLP arriving at the root port and raising an interrupt, a slot status change, an IOMMU fault record, a register read returning all ones, a CQE with a non-zero status, or a timer expiring because nothing happened.

The PCIe Base Specification defines the error types, their severities, the AER and DPC registers and the error Messages; the NVMe Base Specification 2.4 defines CSTS, status codes and Abort; IOMMU specifications define fault records. The log text itself is defined by nobody but the kernel source.

Error signalling travels as Message TLPs (ERR_COR, ERR_NONFATAL, ERR_FATAL) from the detecting function to the root complex; NVMe status travels inside CQEs; timeouts are the absence of a CQE.

On an analyzer, an AER line corresponds to an error Message TLP preceded by the actual problem (an LCRC failure and NAK, a malformed TLP, a missing completion, an LTSSM drop). Kernel timestamps lag the wire by the interrupt and handler latency, and timeouts lag by up to io_timeout.

A senior engineer builds a timeline, groups lines by device and layer, marks consequences (I/O errors, filesystem errors) separately from causes, finds the first abnormal event, and names the experiment that would distinguish the remaining hypotheses.

The sixteen questions for "the kernel log in an NVMe/PCIe incident"

1. What is it?
The kernel's ring buffer of messages, persisted by the journal, written by every subsystem that touches the device.
2. Why was it created?
To give administrators and developers a durable, low-cost record of significant kernel events.
3. What problem does it solve?
Post-incident visibility without prior instrumentation.
4. What existed before?
Console output and syslog; vendor-specific hardware event logs; for PCI, almost nothing (parity errors and system errors with no detail before AER).
5. Why is the current design better?
AER gives typed, attributed errors with header logs; DPC adds containment; structured journal storage survives reboots and supports searching by time and pattern.
6. Who creates it?
Kernel code: drivers and core subsystems, triggered by hardware events or timers.
7. Who consumes it?
Engineers, monitoring (log shippers, rasdaemon), automated triage.
8. Where does it live?
Kernel memory (ring buffer), the systemd journal on disk (if persistent), remote log collectors, pstore after crashes.
9. What memory/registers are involved?
AER status/mask/severity/header log, Root Error Status, DPC status/source, Slot Status, CSTS, PCI Status, IOMMU fault recording registers.
10. What happens before?
The hardware event, its detection, signalling, and the handler or timer that notices it.
11. What happens after?
Recovery actions (driver callbacks, resets, retries), more messages describing them, and consequences up the stack.
12. What happens if it is wrong?
Misordered or misattributed reading leads to the wrong team chasing the wrong layer; lost logs (no persistent journal) leave an incident unexplained.
13. What does the analyzer show?
The actual first abnormal event, often earlier and lower in the stack than the first log line.
14. What does Linux show?
The messages in this chapter, plus counters in sysfs and tracepoints if enabled.
15. What would a validation engineer test?
That each injected error (link down, poisoned TLP, completion timeout, CFS, media error) produces the expected log signature and successful recovery, and that no error goes unreported.
16. What would a senior engineer suspect when it fails?
That the first visible line is a consequence; that firmware-first handling hid the cause; that rate limiting hid the volume; that wall-clock conversion misordered events; that the "hint" lines are being mistaken for diagnoses.

Two physical facts shape the log. First, a link-level problem is detected by the receiver, so errors on data flowing to the SSD are logged by the SSD and errors on data flowing to the host by the root port; the "(Receiver ID)" annotation tells you which. Second, when the link is down, the SSD cannot send an error Message at all, so the root port (via Surprise Down, DPC or hot-plug) becomes the only reporter. A log that contains only root-port lines is itself evidence that the endpoint could not speak.

Specification view

Sources: PCI Express Base Specification, Revision 6.x/7.0 — Error Signaling and Logging; Advanced Error Reporting Capability; Downstream Port Containment; Hot-Plug; NVM Express Base Specification 2.4 — Controller Status (CSTS); Status Field definition and status code tables; Abort command; Controller Reset; the Intel Virtualization Technology for Directed I/O and AMD I/O Virtualization Technology specifications for IOMMU fault records; the ACPI specification's APEI section for firmware-first reporting. The Linux messages are informative artefacts of the kernel source, which is the only authority on their wording.

Verified, well-established: AER correctable status bits 0 Receiver Error, 6 Bad TLP, 7 Bad DLLP, 8 REPLAY_NUM Rollover, 12 Replay Timer Timeout, 13 Advisory Non-Fatal Error; uncorrectable bits 4 Data Link Protocol Error, 5 Surprise Down Error, 12 Poisoned TLP, 13 Flow Control Protocol Error, 14 Completion Timeout, 15 Completer Abort, 16 Unexpected Completion, 17 Receiver Overflow, 18 Malformed TLP, 19 ECRC Error, 20 Unsupported Request, 21 ACS Violation; error Message codes ERR_COR 30h, ERR_NONFATAL 31h, ERR_FATAL 33h; CSTS.RDY is bit 0 and CSTS.CFS is bit 1; generic status 00h Successful Completion, 07h Command Abort Requested, 80h LBA Out of Range; media status (SCT 2h) 81h Unrecovered Read Error.

Derived: a timeout line printed at time T implies the command was submitted at about T − io_timeout; a DPC event with no preceding endpoint AER line implies the endpoint could not or did not signal; CSTS = 0xFFFFFFFF together with PCI_STATUS = 0xFFFF implies that both a memory read and a configuration read failed, which places the fault at or below the link.

Implementation-dependent: which errors a device detects and reports; Completion Timeout values; whether DPC is present, enabled and OS-owned; firmware-first versus OS-native handling; the NVMe driver's escalation policy and timeouts; the status Linux assigns to host-aborted commands; IOMMU fault formats.

Version-dependent: message wording across kernel versions; availability of verbose NVMe error decoding; AER's "(First)" annotation and rate limiting; DPC and EDR support; status code tables (Path Related status codes were added in NVMe 1.4 and extended later).

No specification says what Linux must log, or that an error must be logged at all. The PCIe specification does not say how software must recover from DPC; the NVMe specification does not define host timeouts. Check in the specifications: DPC Status and Error Source ID layouts, the exact AER bit names for your revision (including newer bits such as those for flit mode), the Abort command's completion DW0 semantics, and the Path Related status code table.

Never assume: that the first line in the log is the first event; that "device recovery successful" means no data was lost; that an empty log means no errors (firmware-first, masking, rate limits, ring overflow); that a status printed in an I/O error came from the device; that the kernel's hint about power saving is the root cause.

Protocol view

Key protocol facts for reading logs: error Messages are posted, routed to the root complex, and carry the requester ID of the reporting function, which is why the log can say "received from 0000:01:00.0"; a function sends at most one Message per error occurrence subject to masking; the root port aggregates and may record "multiple errors" when more than one arrives before software services the first; the AER driver's config writes that clear status are themselves visible on an analyzer as CfgWr0 TLPs, which gives you a marker to align kernel time with wire time.

Code / pseudocode

A triage script that classifies kernel log lines by layer, builds an ordered timeline, marks the first abnormal event and the likely consequences, and computes the implied submission time of timed-out commands. It reads dmesg text (with [seconds] timestamps) or journalctl -o short-monotonic output from standard input, or uses an embedded synthetic log with --selftest. Standard library only.

#!/usr/bin/env python3
"""Classify NVMe/PCIe kernel log lines and find the first abnormal event.

  python3 klog_triage.py --selftest
  sudo dmesg | python3 klog_triage.py
  journalctl -k -o short-monotonic | python3 klog_triage.py
"""
import re
import sys

IO_TIMEOUT_S = 30.0   # nvme_core.io_timeout default; read yours from sysfs

# (category, layer, is_cause_candidate, regex). Order matters: first match wins.
RULES = [
    ("iommu-fault",    "platform/IOMMU", True,  r"DMAR: \[DMA|AMD-Vi: Event logged|IO_PAGE_FAULT|smmu.*event"),
    ("dpc",            "PCIe link",      True,  r"DPC: containment|DPC: .*error detected"),
    ("surprise-down",  "PCIe link",      True,  r"\]\s*SDES|Surprise Down"),
    ("link-down",      "PCIe link",      True,  r"pciehp: .*Link Down|Card not present"),
    ("link-up",        "PCIe link",      False, r"pciehp: .*Link Up|Card present"),
    ("aer-uncorr",     "PCIe",           True,  r"severity=Uncorrect|Uncorrected \((Non-)?Fatal\) error"),
    ("aer-corr",       "PCIe",           True,  r"severity=Correctable|Correctable error message"),
    ("aer-detail",     "PCIe",           False, r"error status/mask=|TLP Header:|\]\s+[A-Za-z]+\s+\(First\)|\[\s*\d+\]\s+\w+"),
    ("nvme-ctrl-down", "NVMe controller",True,  r"controller is down|Device not ready|frozen state error"),
    ("nvme-timeout",   "NVMe command",   True,  r"timeout, (aborting|reset controller)|I/O \d+ QID \d+ timeout"),
    ("nvme-abort",     "NVMe command",   False, r"Abort status"),
    ("nvme-reset",     "NVMe controller",False, r"default/read/poll queues|restart after slot reset"),
    ("nvme-status",    "NVMe command",   True,  r"I/O Error \(sct|I/O Cmd\(0x"),
    ("recovered",      "recovery",       False, r"recovery successful"),
    ("io-error",       "consequence",    False, r"I/O error, dev|medium error|Buffer I/O error"),
    ("fs-error",       "consequence",    False, r"EXT4-fs error|XFS \(.*\):.*error|BTRFS error"),
    ("removed",        "consequence",    False, r"Removing after|capacity change from \d+ to 0"),
]
RULES = [(c, l, k, re.compile(r)) for c, l, k, r in RULES]
TS = re.compile(r"^\s*\[\s*(\d+\.\d+)\]\s*(.*)$")
TOUT = re.compile(r"(?:tag|I/O) (\d+).*?QID (\d+) timeout")

SAMPLE = """\
[ 7300.912001] pcieport 0000:00:01.1: AER: Correctable error message received from 0000:01:00.0
[ 7300.912020] nvme 0000:01:00.0: PCIe Bus Error: severity=Correctable, type=Physical Layer, (Receiver ID)
[ 7300.912024] nvme 0000:01:00.0:   device [10ab:c0de] error status/mask=00000001/0000e000
[ 7300.912027] nvme 0000:01:00.0:    [ 0] RxErr                  (First)
[ 7301.004410] pcieport 0000:00:01.1: DPC: containment event, status:0x1f01 source:0x0000
[ 7301.004418] pcieport 0000:00:01.1: DPC: unmasked uncorrectable error detected
[ 7301.004431] pcieport 0000:00:01.1: PCIe Bus Error: severity=Uncorrected (Fatal), type=Transaction Layer, (Receiver ID)
[ 7301.004439] pcieport 0000:00:01.1:    [ 5] SDES                   (First)
[ 7301.004511] nvme nvme0: frozen state error detected, reset controller
[ 7301.452109] pcieport 0000:00:01.1: pciehp: Slot(1): Link Down
[ 7301.903377] pcieport 0000:00:01.1: pciehp: Slot(1): Link Up
[ 7302.118004] nvme nvme0: restart after slot reset
[ 7302.402331] nvme nvme0: 32/0/0 default/read/poll queues
[ 7302.410822] pcieport 0000:00:01.1: AER: device recovery successful
[ 7302.412100] I/O error, dev nvme0n1, sector 18800640 op 0x1:(WRITE) flags 0x8800 phys_seg 1 prio class 0
[ 7302.412377] XFS (nvme0n1p1): metadata I/O error in "xfs_buf_ioend" at daddr 0x11ee000 len 8 error 5
[ 7340.118702] nvme nvme0: I/O tag 419 (01a3) opcode 0x2 (I/O Cmd) QID 2 timeout, aborting req_op:READ(0) size:131072
[ 7340.118950] nvme nvme0: Abort status: 0x0
"""


def parse(lines):
    events = []
    for raw in lines:
        m = TS.match(raw)
        if not m:   # journalctl short-monotonic also uses [seconds]; others are skipped
            continue
        t, text = float(m.group(1)), m.group(2)
        for cat, layer, cause, rx in RULES:
            if rx.search(text):
                events.append((t, cat, layer, cause, text))
                break
    return events


def report(events):
    if not events:
        print("No NVMe/PCIe-related lines recognized.")
        return
    print(f"{'time(s)':>12}  {'category':<15} {'layer':<16} message")
    for t, cat, layer, cause, text in events:
        mark = "*" if cause else " "
        print(f"{t:12.6f} {mark}{cat:<15} {layer:<16} {text[:96]}")
    first = next((e for e in events if e[3]), None)
    if first:
        print(f"\nFirst abnormal (cause-candidate) line: t={first[0]:.6f} [{first[1]}] {first[4][:100]}")
    for t, cat, _, _, text in events:
        m = TOUT.search(text)
        if cat == "nvme-timeout" and m:
            t0 = t - IO_TIMEOUT_S
            print(f"Timeout tag {m.group(1)} QID {m.group(2)} at t={t:.3f}: submitted around "
                  f"t={t0:.3f}. Look for causes in [{t0:.3f}, {t:.3f}].")
            near = [e for e in events if t0 - 1 <= e[0] < t and e[3] and e[1] != "nvme-timeout"]
            for e in near:
                print(f"    candidate in window: t={e[0]:.6f} [{e[1]}]")
            if not near:
                print("    no cause candidate in the window: investigate separately")
    cons = [e for e in events if e[2] == "consequence"]
    if cons:
        print(f"\n{len(cons)} consequence line(s) (I/O, filesystem, removal): "
              "do not treat these as the root cause.")


if __name__ == "__main__":
    if len(sys.argv) > 1 and sys.argv[1] == "--selftest":
        print("Synthetic example for teaching (embedded kernel log):\n")
        report(parse(SAMPLE.splitlines()))
    else:
        report(parse(sys.stdin))

Expected --selftest result: the first cause-candidate line is the correctable error at 7300.912001 (not the DPC line and not the XFS line); the timeout at 7340.12 is traced back to a submission around 7310.12, with no cause candidate in that window (so this later timeout is a separate event worth its own investigation: perhaps a command issued after recovery hit a different problem); two consequence lines are flagged. The rule list is deliberately simple; extend it with the exact strings of your kernel.

Worked example

Scenario

A database host logs, over one minute (synthetic example for teaching):

[20110.402871] nvme 0000:01:00.0: AMD-Vi: Event logged [IO_PAGE_FAULT domain=0x000e address=0x2000a3000 flags=0x0020]
[20110.402913] nvme 0000:01:00.0: AMD-Vi: Event logged [IO_PAGE_FAULT domain=0x000e address=0x2000a3040 flags=0x0020]
[20140.511020] nvme nvme0: I/O tag 77 (004d) opcode 0x2 (I/O Cmd) QID 5 timeout, aborting req_op:READ(0) size:16384
[20140.511214] nvme nvme0: Abort status: 0x0
[20170.622304] nvme nvme0: I/O tag 77 (004d) opcode 0x2 (I/O Cmd) QID 5 timeout, reset controller
[20171.004112] nvme nvme0: 32/0/0 default/read/poll queues
[20171.004530] I/O error, dev nvme0n1, sector 99112960 op 0x0:(READ) flags 0x80700 phys_seg 4 prio class 0

Step 1: order and classify

Two IOMMU faults (platform layer, cause candidates), then a timeout 30.1 s later, an abort, a second timeout 30 s after that, a reset, and a consequence.

Step 2: the 30-second shadow

The first timeout at 20140.51 implies submission around 20110.51. The IOMMU faults at 20110.40 fall inside the window, about 0.1 s before. Derived Strong temporal correlation.

Step 3: what the faults say

The SSD tried a DMA (flags indicate the access type; decode with the AMD IOMMU specification) to IOVA 0x2_000A_3000 and 0x2_000A_3040, inside the data buffer region of the reference system (buffers start at 0x2_0000_0000). The command was a 16 KiB read, so the SSD was writing read data to host memory. The IOMMU refused because no valid mapping existed for that IOVA at that moment.

Step 4: hypotheses

  1. Host driver or upper layer unmapped the buffer early (a use-after-unmap bug), e.g. a previous command for the same buffer was completed/aborted and its mapping torn down while the device still had it.
  2. The device used a stale or wrong PRP (a firmware bug: data for command A written with command B's addresses).
  3. IOMMU mapping race in a passthrough or virtualization setup.

Step 5: evidence that discriminates

Enable the NVMe tracepoints and capture the PRP1/PRP2 of each command (nvme_setup_cmd prints command dwords on many kernels; otherwise use bpftrace on the SQE). On the next occurrence, check whether the faulting IOVA belongs to the timed-out command's PRPs (hypothesis 1 or 3) or to a different, already-completed command (hypothesis 2). An analyzer capture would show the MWr TLP with the bad address and the SQE that supplied it.

Conclusion

The timeouts and reset are consequences; the first abnormal event is the IOMMU fault. Confidence that the fault is the trigger: high (timing, device, direction all match). Confidence about which side is wrong: low until the PRP correlation is done. A good bug report states exactly that.

Common mistakes

  • Starting from the bottom of the log (the I/O and filesystem errors) and opening the wrong bug.
  • Ignoring the 30-second shadow of timeouts.
  • Using dmesg -T across a suspend and misordering events against other logs.
  • Filtering with -l err and losing the info/warn-level AER and pciehp lines.
  • Counting errors from the log instead of from aer_dev_* counters (rate limiting).
  • Reading "Abort status: 0x0" as "the command was aborted successfully". It means the Abort command completed; check what happened next.
  • Treating kernel hints ("faulty power saving mode?") as diagnoses.
  • Attributing host-synthesized statuses to the device.
  • Clearing the ring buffer (dmesg -C) during an investigation.
  • Disabling AER (pci=noaer) to "fix" log noise: it hides evidence and the underlying problem.

Senior engineer insight

Every incident log contains three kinds of lines: the cause (or the earliest symptom of it), the mechanism lines (recovery, resets, retries), and the consequence lines (I/O errors, filesystem complaints, application failures). Seniors annotate each line with one of these three words before they form a hypothesis.

No endpoint AER before a DPC event, no CQE before a timeout, no "Card not present" with a link down: what was not logged narrows the hypotheses as much as what was. Knowing which messages a healthy recovery prints (from a golden log) lets you see what is missing.

OS-native AER, firmware-first (GHES), DPC owned by the OS or by firmware (EDR), ASPM and APST policies, IOMMU mode: these change what appears in the log. The first thing a senior engineer records about an unfamiliar platform is its error-handling policy, because it defines what silence means.

Lab: building an incident timeline from kernel logs

Objective

From a kernel log, produce an ordered, classified timeline, identify the first abnormal event, separate cause from consequence, and propose the next experiment, using your own system's logs, a synthetic incident, and a safe reset in an emulated environment.

Skills

dmesg/journalctl filtering and time handling; reading AER, DPC, pciehp, NVMe and IOMMU messages; correlation with tracepoints.

Safety

Steps 1–3: Safe lab (reading logs). Step 4 resets an emulated NVMe controller inside a QEMU guest: Caution lab procedure, zero risk to real hardware. Never run nvme reset against a real drive with mounted filesystems.

Hardware required

Any Linux system; for step 4, a QEMU guest with an emulated NVMe controller (Lab Environment).

Software required

systemd journal or dmesg, Python 3, klog_triage.py, nvme-cli and trace-cmd in the guest.

Input

Your system's kernel log; the synthetic incident in the worked example; the guest's log after step 4.

Expected output

Three timelines with every relevant line labelled cause / mechanism / consequence, the first abnormal event, and a one-paragraph conclusion with confidence.

Background

The patterns in this chapter; Chapter 47 on correlation.

Step 1: your own baseline

journalctl -k -b 0 -o short-monotonic | grep -E 'pci .*01:00.0|nvme|bandwidth' > golden.txt
journalctl -k -b 0 -o short-monotonic | python3 klog_triage.py

Record the enumeration, bandwidth and queue lines of a healthy boot. Note any correctable errors already present.

Step 2: previous boots

journalctl --list-boots
journalctl -k -b -1 -g 'nvme|AER|DPC|pciehp|DMAR|AMD-Vi' -o short-monotonic

If this prints nothing for earlier boots, your journal is probably volatile: note it as a gap in your evidence chain.

Step 3: the synthetic incident

Save the worked example's log to a file, run python3 klog_triage.py < incident.txt, and compare the script's view with your manual timeline.

Step 4: a reset you caused (emulated controller)

# inside the QEMU guest, emulated NVMe only, nothing mounted from it
sudo trace-cmd record -e nvme -- sh -c 'sleep 1; nvme reset /dev/nvme0; sleep 2'
sudo dmesg | tail -20
trace-cmd report | grep -E 'qid=0' | head -40

Observe which kernel lines a controller reset prints on your kernel, and the admin commands (Identify, Set Features Number of Queues, Create I/O CQ/SQ) the driver issues to bring the controller back, visible as qid=0 tracepoints.

Observation

For each timeline, mark the first abnormal event and the consequence lines. In step 4, note that no AER or link line appears: a controller reset is an NVMe-level event (CC.EN cleared and set), not a PCIe reset.

Questions

  1. In step 1, what link speed and width did the kernel report, and does it match LnkSta?
  2. In step 3, why is the IOMMU fault, not the timeout, the first abnormal event?
  3. In step 4, list the admin opcodes you saw after the reset and explain each.
  4. What would be different in the log if the reset had been a PCIe Function Level Reset instead of an NVMe controller reset?
  5. What evidence would you lose if the journal were volatile and the machine rebooted?

Challenge

Extend klog_triage.py with a rule for your kernel's exact NVMe timeout string and a correlation that, for each timeout, prints matching tracepoint events (same QID and CID) from a trace-cmd report file.

Hints

The CID in the timeout line is the hexadecimal value in parentheses; tracepoints print it in decimal as cmdid=. Convert before joining. Monotonic timestamps in both sources make the time window check straightforward.

Solution

1: the bandwidth line names speed and width; it should equal current_link_speed/width unless the link retrained since boot. 2: by timing (inside the timeout's 30-second window, just after the submission) and by mechanism (a refused DMA explains a command that never completes), the fault precedes and explains the timeout; the timeout is the host noticing the absence. 3: typically Identify (06h, controller and namespaces), Set Features (09h, Number of Queues 07h and others such as Asynchronous Event Configuration), Create I/O Completion Queue (05h) and Create I/O Submission Queue (01h) for each queue pair, Asynchronous Event Request (0Ch); exact set and order depend on the kernel. 4: an FLR is a PCIe function reset: config space is reset and restored by the kernel, the PCI core may log the reset; the NVMe driver goes through a full re-probe-like path; AER is not necessarily involved either. 5: everything before the reboot, including the first abnormal event; only rasdaemon records, BMC logs or remote log collectors would remain.

What a senior engineer notices

Whether the platform logs via native AER or GHES; whether DPC is present on the root port; the configured io_timeout; whether timestamps are monotonic; whether rate-limiting lines appear; and whether the golden log's queue count matches the post-reset count (a lower count after reset is a subtle sign of a degraded recovery).

Failure variants

  • nvme reset fails with "Resource busy" or similar: the device is in use or the kernel refuses; do not force it on a real drive.
  • No nvme events in trace-cmd: check that the nvme event group exists on your kernel.
  • The log contains GHES "Hardware Error" records instead of AER lines: the platform is firmware-first; decode the CPER records with the ACPI/UEFI definitions.

Extension

In QEMU, hot-unplug the emulated NVMe device from the monitor (device_del) while a read loop runs in the guest, and compare the resulting log with Pattern 5. Emulated hot-unplug is a safe way to see removal and I/O-error consequences without touching hardware.

Exercises

  1. Decode error status/mask=00000040/00002000 for a correctable error.
  2. Decode error status/mask=00100000/00000000 for an uncorrectable error. What would the TLP Header contain?
  3. A timeout appears at 1234.5 s with io_timeout = 30. A pciehp Link Down appears at 1205.0 s. Is it a plausible cause? Why?
  4. Which two values in a "controller is down" message distinguish "device unreachable" from "controller fatal"?
  5. Write a journalctl command that shows only kernel messages from the previous boot between two wall-clock times, with monotonic timestamps.
  6. List three reasons an error might never appear in the kernel log.
Answers

1: status bit 6 = Bad TLP; mask bit 13 = Advisory Non-Fatal masked. 2: bit 20 = Unsupported Request; the header log holds the header of the request that received UR (for example an MRd to an address no function claimed, or an MWr with a bad address), which you decode field by field. 3: plausible: the command was submitted around 1204.5 s, 0.5 s before the link went down, so it was in flight when the link dropped. 4: CSTS (0xFFFFFFFF vs 0x3 with CFS) and PCI_STATUS (0xFFFF vs a normal value). 5: journalctl -k -b -1 --since "…" --until "…" -o short-monotonic. 6: firmware-first handling not passed to the OS; error type masked; AER disabled (pci=noaer) or not supported; rate limiting; ring buffer overwritten; volatile journal lost on reboot; the device could not signal (link down) and the port had no reporting capability.

Quiz

  1. Which timestamp is best for ordering kernel events within one boot?

    • dmesg -T wall clock
    • Monotonic seconds since boot
    • The journal's receive time
    • The filesystem's mtime
    Answer and reasoning

    The monotonic clock is what the kernel stamps; wall-clock conversion can be wrong after suspend.

  2. "pcieport 0000:00:01.1: AER: Correctable error message received from 0000:01:00.0" — which device detected the error?

    • The root port
    • The CPU
    • 01:00.0, the SSD
    • The IOMMU
    Answer and reasoning

    The root port received the ERR_COR Message; the requester ID in the Message, 01:00.0, is the detecting function.

  3. CSTS=0xffffffff, PCI_STATUS=0xffff most likely means:

    • The device is unreachable (link down, removed, powered off, in reset)
    • The controller set CFS
    • A shutdown completed
    • The admin queue is full
    Answer and reasoning

    Both a memory read and a config read returned all ones, the host-synthesized value for a failed read.

  4. An NVMe timeout line appears at T. When was the command submitted, approximately, with default settings?

    • At T
    • T − 60 s
    • T − 1 s
    • T − 30 s
    Answer and reasoning

    nvme_core.io_timeout defaults to 30 s for I/O; admin commands default to 60 s.

  5. "nvme nvme0: Abort status: 0x0" followed by "timeout, reset controller" 30 s later means:

    • The command was aborted and then succeeded
    • The Abort command completed, but the original command still did not complete, so the driver escalated
    • The Abort failed
    • The controller reset itself
    Answer and reasoning

    Abort completion status 0 says the Abort command was processed; it does not guarantee the target command completed.

  6. Which AER line shows that a link-level problem was detected on data flowing to the SSD?

    Model answer

    A correctable or uncorrectable error from the SSD with "(Receiver ID)", e.g. RxErr or BadTLP reported by 01:00.0: the SSD was the receiver of the corrupted traffic.

  7. An IOMMU fault line names the SSD and a DMA write. On the PCIe link, what did the SSD send?

    • A malformed TLP
    • An ERR_FATAL Message
    • A valid MWr TLP whose address the IOMMU refused to translate
    • Nothing
    Answer and reasoning

    The transaction was well-formed; the platform's address translation rejected it.

  8. Why can the XFS and block I/O error lines be the most numerous yet least informative lines in an incident?

    Model answer

    They are consequences: every in-flight or subsequent I/O that failed produces one, after the causal event. They identify impact, not cause.

  9. Which source gives the true number of correctable errors since boot when the log shows "callbacks suppressed"?

    • aer_dev_correctable in sysfs
    • dmesg | wc -l
    • nvme error-log
    • smart-log
    Answer and reasoning

    The kernel counts every handled AER error in sysfs regardless of log rate limiting.

  10. Describe the difference in the log between an NVMe controller reset and a DPC event.

    Model answer

    A controller reset is NVMe-level (CC.EN toggled): NVMe driver lines (timeout/reset, queue recreation), no AER/DPC/pciehp lines. A DPC event is PCIe-level: pcieport DPC lines, AER details for the trigger, possible link down/up lines, the driver's error callbacks (frozen state, slot reset), then NVMe re-initialization.

Interview questions

  1. (Beginner) How do you see kernel messages from before the last reboot?

    Model answer

    journalctl -k -b -1, if the journal is persistent; otherwise from a remote log collector, pstore, or a BMC log. dmesg only holds the current boot.

  2. (Beginner) What does "I/O error, dev nvme0n1, sector …" tell you?

    Model answer

    That a block request to that namespace and sector failed. It is a consequence; find the NVMe or PCIe line that explains why.

  3. (Intermediate) Walk through the fields of an AER correctable error message.

    Model answer

    Reporter (root port) and source BDF; severity; type (layer); which ID (Receiver/Requester/Completer) was logged; raw status and mask registers; decoded bits with "(First)" marking the first error pointer; for uncorrectable, the TLP header log.

  4. (Intermediate) A drive logs "controller is down; will reset: CSTS=0x3". What next?

    Model answer

    CFS is set: the controller declared a fatal internal error while PCIe is fine. Capture firmware revision, SMART and error logs, vendor telemetry if possible (caution), the workload at the time, and check for known firmware issues; try to reproduce on a spare; test APST/ASPM hypotheses only as controlled experiments.

  5. (Advanced) How do you correlate a kernel NVMe timeout with an analyzer capture?

    Model answer

    Take QID and CID from the log line; find the doorbell write and SQE fetch whose SQE has that CID on that queue in the analyzer, around T − io_timeout; check for data, CQE and MSI-X; align clocks using a marker (e.g. the Abort command, AER CfgWr, or a known admin command).

  6. (Advanced) Why might a platform show no AER lines at all even though the drive is clearly suffering link errors?

    Model answer

    Firmware-first handling (errors go to firmware/BMC, maybe reported via GHES); AER disabled or not granted to the OS (_OSC); errors masked; the AER service not bound to the port; or errors only on a switch not covered by reporting.

  7. (Senior) A customer says "the filesystem corrupted itself". The log shows a DPC event 2 seconds before. How do you frame the investigation?

    Model answer

    As a link-level containment event whose consequence was failed in-flight writes; the filesystem reacted correctly. Questions: why did the link drop (power, SI, firmware), was write data acknowledged before loss (volatile cache, flush semantics, power-loss protection), and did the recovery path behave correctly. Present a timeline with cause/mechanism/consequence and confidence per claim.

  8. (Senior) What do you change on a lab fleet so that the next incident leaves better evidence?

    Model answer

    Persistent journals and remote logging; rasdaemon; golden boot logs per platform; continuous low-overhead counters (AER, SMART deltas); optional always-on BPF latency histograms; known error-handling policy per platform; and analyzer-ready slots for reproduction.

Teach-back challenge

  • To a child: explain why the teacher's "no answer" note in the diary was not the real problem.
  • To a junior engineer: explain how to read an AER correctable error message and what to do about one.
  • To a senior engineer: present the DPC incident timeline from the trace view in two minutes, with cause, mechanism, consequence and confidence.
Model explanation for the junior engineer

"The first line says the root port received a correctable error message from our SSD. The second gives severity and layer: Physical Layer, Receiver ID, so the SSD's receiver saw a bad symbol. The third is the raw status and mask, the fourth the decoded bit, RxErr. It was corrected, so no data was lost. One is not an incident; check the rate in aer_dev_correctable over time and under load, and compare with other slots. A rising rate or errors before a link drop make it an incident."

Chapter summary

dmesg and journalctl expose the kernel's testimony; monotonic timestamps order it; prefixes tell you which code and which device speak. AER lines report typed errors with the detecting function, the logged ID, status bits and header logs; DPC and pciehp lines report containment and link/presence changes; IOMMU lines report refused DMA with addresses; NVMe lines report timeouts, aborts, resets and CSTS values that distinguish unreachable from fatal controllers; block and filesystem lines report consequences. Build a timeline, look back across the timeout window, separate cause from mechanism from consequence, count with sysfs not with the log, and correlate with tracepoints and traces using QID/CID and time.

Do not move on until you can:

  • retrieve kernel messages from this and previous boots with the right time base
  • name the code behind each message prefix
  • decode an AER message, including status/mask bits and the ID annotation
  • recognize timeout/abort/reset, DPC, link down/up, IOMMU fault and controller-fatal patterns
  • interpret CSTS and PCI_STATUS values in "controller is down" lines
  • find the first abnormal event and label consequences in a synthetic incident
  • join a kernel timeout line to tracepoints and to an analyzer trace by QID/CID and time
