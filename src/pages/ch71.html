When an NVMe SSD or its PCIe link misbehaves, the Linux kernel is usually the first witness to write anything down. This chapter teaches you to read that testimony: dmesg and journalctl patterns for link errors, Advanced Error Reporting, Downstream Port Containment, hot-plug link down/up, IOMMU faults, NVMe timeouts, aborts, resets and controller failure, and how to turn a wall of messages into an ordered timeline that you can correlate with traces.

Why this chapter exists

Most real NVMe incidents are investigated after the fact. Nobody had an analyzer attached; nobody was tracing. What remains is the kernel log: a few dozen lines from the PCI core, the port services (AER, DPC, hot-plug), the IOMMU driver, the NVMe driver, the block layer and the filesystem, each printed by a different piece of code with its own vocabulary and its own idea of time.

Read naively, the log misleads. The loudest line is rarely the first event. "I/O error" is a consequence, not a cause. A controller reset message tells you what the driver did, not what the device did. Read carefully, the same log lets you rebuild the sequence of events, identify the layer where the first abnormal event happened, and choose the next experiment.

This chapter is the Linux-side companion to error correlation in Chapter 47: there you learned to reason across layers; here you learn the exact form in which Linux reports each layer.

Learning objectives

  • Use dmesg and journalctl effectively: boots, time formats, priority filters, pattern searches, following live, and the limits of each.
  • Recognize the message prefixes (pci, pcieport, nvme nvme0, nvme 0000:01:00.0, nvme0n1, DMAR, AMD-Vi, block and filesystem) and the code that prints each.
  • Read AER messages field by field: severity, type, agent ID, status/mask, bit names, TLP Header log.
  • Recognize the patterns of: correctable link errors, uncorrectable errors, DPC containment, hot-plug link down/up, NVMe command timeout → abort → reset, controller-fatal status, device-gone (all-ones), I/O errors with NVMe status, and IOMMU translation faults.
  • Build a timeline, find the first abnormal event, state what each line proves and does not prove, and correlate with tracepoints, nvme-cli logs and analyzer traces.

The story

The school office keeps a diary. Whenever something happens, whoever noticed it writes one line: the road guard writes "a truck arrived with a scratched box", the gate keeper writes "the road to the library closed", the teacher writes "I asked the librarian for a book half a minute ago and got no answer, so I am ringing the bell again". Later, when the headmaster wants to know what went wrong, she reads the diary. But she has to be careful: the teacher's line about "no answer" was written thirty seconds after the road guard's line about the road closing, and the road closing is the real reason.

Adult version: the kernel log is like the combined radio log of an airport, where the tower, ground control, the fire service and each airline write into one shared logbook. Every entry is true from its writer's point of view, entries carry the time of writing (not of the event), some writers only write when they notice a problem long after it began, and some suppress repeated entries ("and 40 similar messages") when things get busy.

Where the analogy breaks. (1) An airport log is kept by people who can describe what they saw; kernel code prints fixed templates with numbers that need decoding. (2) A logbook persists; the kernel ring buffer has a fixed size and old messages are overwritten, and messages from the boot that crashed may be lost unless the journal is persistent or pstore captured them. (3) In the airport, the fire service knows about the tower; in the kernel, the AER driver and the NVMe driver often report the same incident independently without referring to each other, so you must do the joining. (4) Some events are never logged at all: errors that firmware handled (firmware-first), masked errors, and a link that recovered silently.

Beginner explanation

The kernel writes messages into a ring buffer in memory. dmesg prints that buffer. On systems with systemd, the journal daemon copies kernel messages into the journal, and journalctl -k shows them, including from earlier boots if the journal is stored persistently.

sudo dmesg -T | grep -iE 'nvme|aer|dpc|pciehp|dmar|amd-vi'   # this boot, human time
journalctl -k -b -1 | grep -iE 'nvme|aer'                    # previous boot (needs persistent journal)
sudo dmesg -w                                                # follow new messages live

Each line starts with a timestamp. By default dmesg shows seconds since boot ([ 5012.000431]), a monotonic clock that is the best clock for ordering kernel events. dmesg -T converts to wall-clock time but can be wrong after the system has been suspended. journalctl shows wall-clock time by default and can show the monotonic value with -o short-monotonic.

Then comes a prefix that tells you which code printed the line and about which device. Learning those prefixes is half of reading the log.

Safe lab Reading logs never touches a device. Some distributions restrict dmesg to root (kernel.dmesg_restrict). Do not clear the ring buffer (dmesg -c / -C) on a system under investigation: you would destroy evidence other people may need.

Pattern 1: enumeration and link bandwidth (the baseline you need)

Before you read failure messages, know what a healthy boot says. Synthetic example for teaching:

[    1.204118] pci 0000:01:00.0: [10ab:c0de] type 00 class 0x010802 PCIe Endpoint
[    1.204190] pci 0000:01:00.0: BAR 0 [mem 0xfe600000-0xfe603fff 64bit]
[    1.204551] pci 0000:01:00.0: 63.016 Gb/s available PCIe bandwidth, limited by 16.0 GT/s PCIe x4 link at 0000:00:01.1 (capable of 63.016 Gb/s with 16.0 GT/s PCIe x4 link)
[    2.811034] nvme nvme0: pci function 0000:01:00.0
[    2.835520] nvme nvme0: 32/0/0 default/read/poll queues
[    2.840911]  nvme0n1: p1 p2

The bandwidth line is printed at enumeration; when the "available" figure is lower than the "capable" figure, the line names the link that limits it. It is the kernel's own version of the LnkCap/LnkSta comparison. 32/0/0 default/read/poll queues says the driver created 32 I/O queues of the default type and none dedicated to reads or polling. Save a healthy boot log from every lab machine: it is the "golden" reference against which you diff a bad one.

Pattern 2: correctable link errors (AER, Physical/Data Link Layer)

[ 4012.517802] pcieport 0000:00:01.1: AER: Correctable error message received from 0000:01:00.0
[ 4012.517826] nvme 0000:01:00.0: PCIe Bus Error: severity=Correctable, type=Physical Layer, (Receiver ID)
[ 4012.517830] nvme 0000:01:00.0:   device [10ab:c0de] error status/mask=00000001/0000e000
[ 4012.517834] nvme 0000:01:00.0:    [ 0] RxErr                  (First)
  • Line 1: the root port received an ERR_COR Message whose requester was 01:00.0. The root port is the reporter; the SSD is the source.
  • Line 2: severity Correctable; type=Physical Layer is the layer the kernel associates with the set bit; (Receiver ID) says the ID logged is the receiver that detected the error, i.e. the error was on traffic arriving at the SSD (downstream direction).
  • Line 3: the raw Correctable Error Status register (bit 0 set) and Mask register (bits 13–15 masked).
  • Line 4: decoded bit 0, Receiver Error.

What it proves: the SSD's receiver detected at least one physical-layer error, which the link corrected (by replay or by the error being benign). What it does not prove: data corruption (none, by definition of correctable), or the cause (signal integrity, reference clock, power noise, equalization). A handful per day can be normal on some platforms; a rising rate or a burst before an uncorrectable error is a warning. Other correctable bits: BadTLP (LCRC or sequence error at the Data Link Layer), BadDLLP, Rollover (replay number rollover), Timeout (replay timer timeout) — all Data Link Layer recovery signals (see Chapter 15).

Pattern 3: uncorrectable non-fatal errors (Transaction Layer)

[ 5102.330114] pcieport 0000:00:01.1: AER: Uncorrected (Non-Fatal) error message received from 0000:01:00.0
[ 5102.330139] nvme 0000:01:00.0: PCIe Bus Error: severity=Uncorrected (Non-Fatal), type=Transaction Layer, (Requester ID)
[ 5102.330143] nvme 0000:01:00.0:   device [10ab:c0de] error status/mask=00004000/00400000
[ 5102.330147] nvme 0000:01:00.0:    [14] CmpltTO                (First)
[ 5102.330160] nvme 0000:01:00.0: AER:   TLP Header: 00000000 00000000 00000000 00000000
[ 5102.330198] nvme 0000:01:00.0: AER: device recovery successful

Bit 14 is Completion Timeout: the SSD, as a requester, issued a non-posted request (most likely a memory read: an SQE fetch, a PRP list fetch or write data being fetched from host memory) and no completion arrived within its Completion Timeout window. (Requester ID) marks the SSD as the requester. For Completion Timeout the header log is typically empty because the device does not have a received TLP to log; for Malformed TLP or Unsupported Request the header log holds the offending TLP's header, which you decode with the tools of Chapter 11.

Consequences to look for next: an NVMe command whose data or SQE fetch failed. The controller will typically complete that command with an error status (for example a Data Transfer Error) or may stall it, which leads to a timeout message from the NVMe driver later. Causes to consider: host memory read latency beyond the device's timeout setting (DevCtl2 range too short), IOMMU blocking the read (look for an IOMMU fault line at the same moment), a root complex problem, or a link retraining event that delayed completions.

AER: device recovery successful means the kernel ran the error recovery callbacks of the bound driver (for non-fatal errors, usually without resetting the link) and they reported recovered. It does not mean the NVMe command that suffered was retried successfully: check the NVMe lines.

Pattern 4: fatal errors, Surprise Down and Downstream Port Containment

When the root port supports Downstream Port Containment (DPC) and Linux has it enabled, an uncorrectable error (per its configuration) makes the port immediately disable the link to contain the error. Linux then runs recovery: the driver's error callbacks, waiting for the link to come back, a slot reset, and resume.

[ 7301.004410] pcieport 0000:00:01.1: DPC: containment event, status:0x1f01 source:0x0000
[ 7301.004418] pcieport 0000:00:01.1: DPC: unmasked uncorrectable error detected
[ 7301.004431] pcieport 0000:00:01.1: PCIe Bus Error: severity=Uncorrected (Fatal), type=Transaction Layer, (Receiver ID)
[ 7301.004435] pcieport 0000:00:01.1:   device [1022:1483] error status/mask=00000020/00000000
[ 7301.004439] pcieport 0000:00:01.1:    [ 5] SDES                   (First)
[ 7301.004511] nvme nvme0: frozen state error detected, reset controller
[ 7301.452109] pcieport 0000:00:01.1: pciehp: Slot(1): Link Down
[ 7301.903377] pcieport 0000:00:01.1: pciehp: Slot(1): Link Up
[ 7302.118004] nvme nvme0: restart after slot reset
[ 7302.402331] nvme nvme0: 32/0/0 default/read/poll queues
[ 7302.410822] pcieport 0000:00:01.1: AER: device recovery successful

How to read it: the root port (vendor ID shown is the root port's, here a placeholder) triggered containment; the reported error was Surprise Down Error (SDES, bit 5), meaning the link went down unexpectedly from the port's point of view. The NVMe driver was told the channel is frozen and prepared for a reset; hot-plug saw the link go down and up (with DPC, these lines may or may not appear, depending on configuration); the driver re-initialized the controller and recreated 32 I/O queues. In-flight commands were failed back to the block layer or requeued.

What it proves: the link went down unexpectedly, the platform contained it, and recovery succeeded. What it does not prove: why the link went down (device firmware crash and PHY reset, power glitch, connector, retimer). The DPC status and source registers encode the trigger reason and source; decode them with the DPC capability layout in the PCIe Base Specification. Do not guess bit meanings from memory

Platform-dependent: with firmware-first error handling (common on servers, signalled through ACPI APEI/GHES), the kernel may print {1}[Hardware Error]: … records from GHES instead of the native AER lines, or may not see some errors at all. DPC may be owned by firmware (EDR, Error Disconnect Recover) rather than the OS. Always establish which mode the platform uses before concluding "the OS never saw an error".

Pattern 5: hot-plug link down/up without DPC

[ 8120.771203] pcieport 0000:00:01.1: pciehp: Slot(1): Link Down
[ 8120.771240] pcieport 0000:00:01.1: pciehp: Slot(1): Card not present
[ 8120.790115] nvme nvme0: controller is down; will reset: CSTS=0xffffffff, PCI_STATUS=0xffff
[ 8120.812554] nvme0n1: detected capacity change from 1953525168 to 0
[ 8120.812990] I/O error, dev nvme0n1, sector 18800640 op 0x1:(WRITE) flags 0x8800 phys_seg 1 prio class 0
[ 8120.861732] nvme nvme0: Removing after probe failure status: -19

Card not present comes from the slot's Presence Detect: the device is physically gone or lost power. CSTS=0xffffffff, PCI_STATUS=0xffff is the all-ones signature from Chapter 69: the driver read the CSTS register and the PCI Status register and both came back as all ones, so the device is not reachable. Error -19 is ENODEV. The I/O error is a consequence. If instead the log shows Link Down without Card not present and then Link Up, the device stayed present but the link dropped: a device reset, firmware crash, power-state problem or signal issue.

Pattern 6: NVMe command timeout → abort → reset

The NVMe driver arms a timer for each request (nvme_core.io_timeout, default 30 s; admin commands use admin_timeout, default 60 s). When it fires, the PCIe driver's timeout handler first checks whether the controller is alive (reads CSTS), checks whether the completion is actually sitting in the CQ (a missed interrupt), and then escalates: Abort command first, controller reset if the abort fails or times out.

[ 9030.118702] nvme nvme0: I/O tag 419 (01a3) opcode 0x2 (I/O Cmd) QID 2 timeout, aborting req_op:READ(0) size:131072
[ 9030.118950] nvme nvme0: Abort status: 0x0
[ 9060.230113] nvme nvme0: I/O tag 419 (01a3) opcode 0x2 (I/O Cmd) QID 2 timeout, reset controller
[ 9060.611087] nvme nvme0: 32/0/0 default/read/poll queues
[ 9060.611540] nvme0n1: I/O Cmd(0x2) @ LBA 3813120, 256 blocks, I/O Error (sct 0x3 / sc 0x71)
[ 9060.611566] I/O error, dev nvme0n1, sector 3813120 op 0x0:(READ) flags 0x80700 phys_seg 32 prio class 0
  • tag 419 (01a3): the block-layer tag and the NVMe command identifier in hex. On recent kernels the CID may include generation bits, so it can differ from the tag. This CID is your join key with tracepoints (Chapter 70) and with the SQE on an analyzer.
  • opcode 0x2 on an I/O queue is Read (NVM command set). QID 2 is the I/O queue.
  • Abort status: 0x0: the Abort command itself completed successfully. That only means the controller accepted the abort request; the timed-out command was still not completed, so 30 seconds later the driver escalated to a controller reset.
  • After the reset, the driver recreated the queues; the stuck request was completed with a host-synthesized status. sct 0x3 / sc 0x71 is shown here as an example of a path-related status code that Linux uses for host-aborted commands; confirm the exact SCT/SC your kernel assigns and its name in the Path Related Status table of the NVMe Base Specification 2.4. Crucially, this status was not sent by the device.

A timeout message is printed io_timeout after the command was submitted. The real first abnormal event happened up to 30 seconds earlier. Always look backwards from a timeout line for AER, DPC, IOMMU or link messages in that window.

Some kernels print the "faulty power saving mode" hint whenever a controller goes down. It is a suggestion for one common cause (problems leaving deep APST power states or ASPM), not a diagnosis. Disabling APST and ASPM is a valid experiment (Caution lab: it changes power behaviour for the whole machine), and its result is evidence; the message itself is not.

[    3.912003] nvme nvme0: pci function 0000:01:00.0
[   64.120771] nvme nvme0: Device not ready; aborting initialisation, CSTS=0x0
[   64.121022] nvme nvme0: Removing after probe failure status: -19

The controller was enabled (CC.EN = 1) but CSTS.RDY never became 1 within the CAP.TO timeout (60 s here). PCIe works (config space read, BAR mapped); the controller's firmware did not finish starting. Look at firmware revision, a recent firmware update, or a drive in a vendor "safe mode".

Pattern 8: I/O errors carrying a device status

[10433.517220] nvme0n1: I/O Cmd(0x2) @ LBA 774016, 8 blocks, I/O Error (sct 0x2 / sc 0x81) DNR
[10433.517301] critical medium error, dev nvme0n1, sector 774016 op 0x0:(READ) flags 0x0 phys_seg 1 prio class 0

Here the device completed the command with status SCT 2h (Media and Data Integrity Errors), SC 81h (Unrecovered Read Error), with Do Not Retry set. The block layer maps it to a "critical medium error". No timeout, no reset, no AER: the transport worked perfectly and delivered bad news. Correlate with nvme error-log (an entry with the same LBA is likely) and media_errors in smart-log. The verbose NVMe decode line appears only on kernels with verbose error reporting enabled (kernel-configuration-dependent); otherwise you see only the block-layer line.

Pattern 9: IOMMU translation faults

With an IOMMU enabled (the reference system), every DMA address the SSD emits is an I/O virtual address (IOVA). If the address is not mapped, or mapped without the needed permission, the IOMMU blocks the access and logs a fault.

[11210.004418] DMAR: DRHD: handling fault status reg 2
[11210.004431] DMAR: [DMA Write NO_PASID] Request device [01:00.0] fault addr 0x1fff00000 [fault reason 0x05] PTE Write access is not set

[11210.004502] nvme 0000:01:00.0: AMD-Vi: Event logged [IO_PAGE_FAULT domain=0x000e address=0x1fff00000 flags=0x0020]

Read: the requester (01:00.0, the SSD), the direction (a DMA write: the device writing to host memory, as for read data or a CQE), the IOVA (0x1fff00000), and the reason (no write permission or no mapping). On the wire the SSD sent a perfectly valid MWr TLP; the platform refused it. The device may receive an error completion for reads, and for writes the data is silently dropped; the NVMe command will then fail, hang or complete with corrupted host-side data. Platform-dependent The reason codes and flag bits are IOMMU-architecture-specific: decode them with the Intel VT-d or AMD IOMMU specification, not from memory.

Typical causes: a driver bug (buffer unmapped before the device finished, use-after-free of a DMA buffer), a device bug (DMA to a stale PRP from a previous command, or to an address beyond the PRP list), or a passthrough misconfiguration. The faulting address is the key: compare it with the PRP entries in the command's SQE (from a trace) and with the queue base addresses.
