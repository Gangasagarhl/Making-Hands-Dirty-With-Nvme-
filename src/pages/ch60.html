The Key Value (KV) Command Set lets a host store and fetch variable-sized values by key, with no logical block addresses at all. This chapter explains why such a command set exists, how Store, Retrieve, Delete, Exist and List work, what limits apply to keys and values, how KV compares with block storage, and how KV traffic looks in a trace.

Why this chapter exists

A great deal of the world's data is accessed by name, not by address: user records by ID, images by hash, cache entries by URL. Today that is usually built in layers: an application asks a key-value store (RocksDB, a hash table, an object store), which keeps its own index and log in a file system, which maps files to blocks, which an SSD's Flash Translation Layer (FTL) maps again to flash pages. Every layer has its own index, its own garbage collection and its own write amplification.

The NVM Express (NVMe) Key Value Command Set asks a simple question: the SSD already runs a translation layer that maps names (LBAs) to flash locations — why not let the name be the application's key? The host then sends "store this value under this key" directly, and the device does the indexing it was doing anyway. Whether that is a good trade depends on workload, key size limits, ecosystem and failure handling, and an engineer needs to be able to argue both sides.

The KV command set is also the clearest demonstration of a point made in Namespaces: the NVMe Base architecture — queues, doorbells, PCI Express (PCIe) transport, admin commands — is independent of what a namespace contains. A KV namespace uses exactly the same Submission and Completion Queues as a block namespace. Only the meaning of the 64-byte command changes.

The story

In the block-storage library, you ask for books by shelf number: "bring me whatever is on shelf 4,812." You must remember yourself which shelf holds your dinosaur book, so you keep a notebook: "dinosaur book → shelf 4,812."

The key-value library works differently. You hand the librarian a label — "DINOSAURS" — and a box, and say "keep this under DINOSAURS." Later you say "give me DINOSAURS" and she brings the box. You don't need a notebook; the librarian keeps it. You can ask "do you have anything called DINOSAURS?", "throw away DINOSAURS", or "list the labels starting from D".

The rule is that labels must be short — they have to fit on the request slip itself.

A coat check at a theatre. You hand over a coat (the value) and receive a ticket number (the key) — except in KV storage you choose the ticket number yourself. The attendant decides which rail and hanger to use; you never know or care. To retrieve, you present the ticket. "Is ticket 1001 here?" is a quick question with no coat moved. "Put this coat on 1001 only if 1001 is free" prevents two guests overwriting each other. Block storage, by contrast, is a rail of numbered hangers that you must manage yourself: you decide that coat A goes on hanger 7 and you keep the list.

What it hides. The attendant is not free: the device runs a hash table or index in its own memory and flash, has a maximum number of keys, and must garbage-collect values of many different sizes. Values are moved by DMA through host memory buffers exactly like block data.

Where it misleads. A coat check returns coats in any order and has no notion of "the next ticket". KV List does exist, but its ordering and completeness under concurrent updates are defined by the specification and the implementation, not by intuition. And the "short label" limit is severe — a few bytes, not a URL — so real applications usually hash long names into fixed-size keys, which brings back a host-side mapping for collisions.

Where it breaks. A coat check never loses half a coat. A KV Store of a large value interrupted by power loss must be atomic (old value or new value, never a mix) — whether and how a device guarantees that is a specification and implementation question you must check, not assume.

Beginner explanation

A KV namespace is a namespace whose command set is Key Value (Command Set Identifier 01h). Instead of blocks numbered from 0, it holds pairs: a key (a short byte string) and a value (a byte string that can be much larger). The device stores, finds and deletes pairs by key.

The five core commands are:

  • Store — write a value under a key (create or replace).
  • Retrieve — read the value for a key into a host buffer.
  • Delete — remove a key and its value.
  • Exist — ask whether a key exists; no data moves.
  • List — get a list of keys present, starting from a given key.

The key is short enough to travel inside the 64-byte command itself, so the device does not need to fetch it separately. The value travels like block data: the command carries a data pointer to a host buffer, and the device reads it (Store) or writes it (Retrieve) by DMA.

Errors are new but simple: a key that is empty or too long is rejected (Invalid Key Size); a value too large is rejected (Invalid Value Size); Retrieve, Delete or Exist of a key that is not there returns "KV Key Does Not Exist"; a Store with "only if absent" on a key that is present returns "Key Exists".

Linux does not turn a KV namespace into a disk. Applications reach it through the NVMe generic character device and pass-through commands, or through a user-space library.

Engineering explanation

The key/value model

A KV namespace is defined by the NVM Express Key Value Command Set Specification, Revision 1.4, which is current in the 2026 release. Each pair is a key — a byte string with a length between 1 and the namespace's maximum key length — and a value — a byte string from 0 to the namespace's maximum value length. Keys are compared as byte strings; there is no hierarchy, no type and no character set. A namespace holds at most a reported maximum number of keys and a reported capacity in bytes.

The KV-specific Identify Namespace data structure (Identify CNS 05h with CSI 01h) reports these limits through one or more KV format descriptors. The descriptor fields include a maximum key length, a maximum value length and a maximum number of keys; namespace size and utilization are reported in bytes rather than in logical blocks. Uncertain on exact field names, offsets and units — read them from the KV Identify Namespace definition in KV 1.4 before writing code.

Key size limits

The defining design choice of NVMe KV is that the key is carried in the Submission Queue Entry. A 64-byte command has room for the common fields (opcode, Command Identifier, NSID, data pointer) and a handful of command-specific dwords; the KV command set uses some of those dwords to hold the key bytes and a key length field. The widely documented consequence is a maximum key length of 16 bytes. Uncertain — the brief for this course asked us to check the specification for this value, and we could not consult the KV 1.4 text directly while writing; confirm the maximum key length (and whether any revision allows longer keys through a separate key buffer) in the KV Identify Namespace and command definitions. Your device's KV format descriptor reports the actual limit, which may be smaller than the specification maximum.

Why so small? Because a key inside the command costs no extra DMA: when the controller fetches the 64-byte SQE (one PCIe Memory Read), it already has the key and can start the index lookup. A longer key would need a second DMA to fetch a key buffer, adding latency to every operation, including Exist and Delete which otherwise move no data at all.

What applications do about it: hash long names (for example, a 128-bit hash of a URL → 16 bytes) and handle collisions by storing the full name inside the value and checking it on Retrieve; or use structured binary keys (8-byte table ID + 8-byte row ID). Neither is free — collisions, ordering and prefix listing all change.

Never hard-code 16. Read the maximum key length from the namespace's KV format descriptor and reject longer keys in the host, so that "Invalid Key Size" in the field means a bug, not normal operation.

Value size limits

The maximum value length is reported per KV format. Values are moved through the data pointer (PRP or SGL), so a single command's transfer is also bounded by the controller's Maximum Data Transfer Size (MDTS) — a value larger than MDTS cannot be moved in one command, whatever the KV limit says. Uncertain whether KV 1.4 defines a mechanism for storing a value in multiple commands; check the Store command's options. A Store with a value length above the namespace maximum fails with Invalid Value Size.

Store

The host places the value in a buffer, builds an SQE with the key, the key length, the value length and the data pointer, and submits. The controller fetches the SQE, reads the value by DMA, updates its index, writes the value to media (possibly buffered), and completes. The Store Option field selects conditional behaviour:

  • Store If Key Exists (SIKE) — update only: if the key does not exist, fail with KV Key Does Not Exist.
  • Store If No Key Exists (SINKE) — create only: if the key exists, fail with Key Exists.
  • Neither — upsert: create or replace.

These conditionals are atomic in the device: check and store happen as one operation, which a host cannot achieve with Exist followed by Store when several hosts or threads are racing. That is a real reason to prefer device KV for some coordination patterns.

Retrieve

The host supplies the key and a buffer with its size. The controller looks up the key, DMA-writes the value (up to the buffer size) to host memory and completes. The completion reports the value's length, so a host that supplied a too-small buffer can learn how much it needs and retry. Uncertain on whether a too-small buffer yields success with truncation or an error, and on which completion dword carries the length — confirm in the Retrieve command's completion definition.

Delete and Exist

Both carry only the key; no data is transferred. Exist is the cheapest possible KV operation — one SQE fetch, one index probe, one CQE — and is ideal for Bloom-filter-like checks. Note that Exist reports "no" as an error status (KV Key Does Not Exist). Host software must not log it as a failure or count it in error statistics.

List

List returns keys present in the namespace, beginning at (or after) a key the host supplies, into a host buffer. The returned data begins with the number of keys returned and then the keys themselves, each with its length. Hosts iterate by calling List again starting after the last key received. Uncertain on the exact list format (length field widths, padding), on whether the start key itself is included, and on the order of keys — read the List command's data structure in KV 1.4. Implementation-dependent whether the order is sorted at all; a hash-based device may return keys in hash order, which makes prefix listing impossible without scanning everything.

Why a KV command set exists

  1. Remove a translation layer. Host KV stores maintain an index from key to file offset; the file system maps offsets to LBAs; the FTL maps LBAs to flash. KV collapses the last two into the device's index.
  2. Reduce write amplification. Log-structured merge (LSM) tree stores rewrite data repeatedly during compaction (application-level write amplification of 10× or more is common), on top of device GC. A device KV index can update in place in its own structures and avoid compaction traffic across PCIe.
  3. Save host CPU and DRAM. Indexing, compaction and caching consume host cores and memory; offloading them frees both.
  4. Atomic conditional operations. SIKE/SINKE give per-key atomic create/update semantics at the device.
  5. Variable-size values without padding. A 100-byte value does not occupy a 4 KiB block on the host side.

KV wins when the application's natural interface is already get/put by short keys, values are small to medium, and host CPU or write amplification is the bottleneck. It loses when the application needs ordered scans, long keys, transactions across keys, or portability — which is why KV SSDs have remained a niche compared with ZNS and FDP. A senior engineer frames the decision in terms of who owns the index and who pays for garbage collection.

The central concept on the ladder

A coat check: hand over a coat with your own ticket number; get it back by the number; ask if a number is in use; throw a coat away.

A KV namespace stores variable-size values under short byte-string keys. Store, Retrieve, Delete, Exist and List replace READ and WRITE; the device maintains the key index.

Inside the controller, a hash or tree index maps keys to flash locations, stored in DRAM and journaled to flash; values are packed into flash pages; a GC process reclaims space from deleted or replaced values of varying sizes.

The KV Command Set 1.4 defines the commands, Store options SIKE/SINKE, KV formats with key and value limits, KV Identify structures and statuses 85h–89h. The Base 2.4 specification supplies queues, admin commands and CSI 01h.

Each command is one 64-byte SQE with the key inside; Store pulls the value with device MRds; Retrieve and List push data with device MWrs; Exist and Delete move no data. Completions carry status and, for Retrieve, the value length.

In a trace: SQE fetch, then either a value-sized DMA (often a non-multiple of 4 bytes, visible as partial byte enables) or nothing, then a CQE. A "does not exist" completion arrives with no data phase.

Debugging: distinguish "no" (87h on Exist) from failure; check key length handling in the host; check value length against MDTS and the KV maximum; check buffer sizes on Retrieve; check List iteration for skipped or repeated keys under concurrent Store/Delete.

The sixteen questions, answered for "KV Store"

1. What is it?
An I/O command that writes a value under a key in a KV namespace.
2. Why was it created?
To let applications that think in keys skip host-side indexing and block mapping.
3. What problem does it solve?
Duplicate indexing, compaction write amplification, host CPU/DRAM cost, and racy create/update semantics.
4. What existed before it?
Host key-value stores over file systems over block devices; proprietary KV SSD interfaces; the SNIA Key Value Storage API as a host-side API standard.
5. Why is the current design better?
It standardizes KV on the same NVMe queues, transports and management as block storage, so one controller can offer both.
6. Who creates it?
The host driver or user-space library builds the SQE on behalf of the application.
7. Who consumes it?
The controller's KV engine.
8. Where does it live?
The SQE in an I/O Submission Queue in host memory; the value in a host data buffer; the stored pair in device media.
9. What memory/registers are involved?
SQ tail doorbell; SQE (key, key length, value length, options, data pointer); host value buffer; CQ entry; device DRAM index.
10. What happens before it?
KV namespace created (CSI 01h) and attached; KV command set enabled; KV Identify read for limits.
11. What happens after it?
Completion; the pair may be in a volatile write cache until Flush if a volatile cache is present.
12. What happens if it is wrong?
Invalid Key/Value Size, Key Exists or KV Key Does Not Exist; or silent overwrite of another application's key if keys collide.
13. What does the protocol analyzer show?
SQE with opcode 01h, device MRds pulling exactly the value length, a CQE.
14. What does Linux show?
A /dev/ngXnY generic device; nvme list may show the namespace; no block device; pass-through command results in the tool you use.
15. What would a validation engineer test?
Key lengths 0, 1, max, max+1; value lengths 0, 1, odd sizes, max, max+1, above MDTS; SIKE/SINKE on present/absent keys; concurrent Store/Delete/List; power loss during Store (atomicity); max number of keys.
16. What would a senior engineer suspect when it fails?
Host key truncation or padding differences (is "abc" the same key as "abc\0"?), buffer-size and value-length confusion, treating 87h as an error, and List iteration bugs.

Hardware view

On the PCIe side nothing changes: the same Base Address Register (BAR), doorbells, queues and MSI-X interrupts. The difference is in the controller's back end.

Inside a KV-capable SSD controller (implementation-dependent)
BlockRole in KV
Command front endDecodes the SQE, extracts key and key length without any extra DMA
Hash/index engine (often hardware-assisted)Maps key → value location; must handle collisions and the maximum key count
DRAMHolds the hot index; size bounds the number of keys or forces index paging from flash
Packing logicPacks variable-size values into flash pages; small values share pages
Garbage collectorReclaims space from replaced and deleted values; must move values and update the index
Power-loss protectionMakes index updates and value writes atomic per Store

DMA of values is byte-granular from the host's perspective: a 14-byte value is fetched with a 4-DWORD Memory Read with a Last DW Byte Enable of 0011b. Small-value workloads therefore generate many small TLPs — the PCIe efficiency of KV for tiny values is poor, which the device compensates for by saving whole round trips of host indexing.

A KV device's maximum number of keys is often a DRAM budget in disguise. An index entry of tens of bytes per key times billions of keys is many gigabytes; a device either carries that DRAM or pages its index from flash and accepts slower lookups.

That the key travels in the SQE to avoid a second DMA, the PCIe efficiency of small values, the DRAM cost of the index and the comparison with block storage are reasoned, not quoted.

KV was among the first separate I/O command set specifications published with the NVMe 2.0 restructuring (2021). Revision 1.4 is current with the 2026 set; changes since 1.0 are listed in the specification's revision history and in the Revision Changes document. See 2026 NVMe 2.4 Updates.

Check in KV 1.4 before relying on:

  • the maximum key length the specification permits and where key bytes sit in the SQE;
  • the exact field positions of key length, value length, Store options and Retrieve options;
  • where the value length is returned on Retrieve and what happens with a too-small buffer;
  • the List data format and ordering rules;
  • atomicity guarantees for Store and behaviour on power loss;
  • units of namespace size and utilization in KV Identify.

Never assume keys are NUL-terminated strings, that List is sorted, that 87h is an error, that a value can be larger than MDTS in one command, or that every NVMe tool understands KV namespaces.

Protocol view

Direction. Store moves data host → controller (device-issued reads). Retrieve and List move data controller → host (device-issued writes). Exist and Delete move no data. In every case the key arrives with the SQE fetch.

Ordering. As in all NVMe command sets, commands are not ordered with respect to each other. A Store and a Retrieve of the same key submitted together may execute in either order; a Delete and a Store of the same key likewise. If the application needs read-your-writes, it must wait for the Store's completion before submitting the Retrieve. Conditional Stores (SIKE/SINKE) are atomic per command, not per sequence of commands.

Errors and layer. All KV outcomes, including "does not exist", are NVMe completion statuses. PCIe errors (for example a completion timeout while fetching a value) are transport faults and leave the pair's state for the controller to resolve: the specification decides whether a failed Store leaves the old value intact.

Linux view

The Linux NVMe driver creates block devices only for command sets it can drive as block storage (NVM, and ZNS as zoned block devices). Since kernel 5.13 it also creates a generic character device per namespace, /dev/ng<ctrl>n<ns>, including for namespaces whose command set it does not otherwise support. KV namespaces are reached through that node with pass-through ioctls or io_uring pass-through. Version-dependent

# Does the controller support the KV command set? (Identify Controller, I/O command set data)
sudo nvme id-ctrl /dev/nvme0 -H | grep -iE 'command set|cmic|oncs'
sudo nvme id-iocs /dev/nvme0                 # I/O Command Set data structure (CNS 1Ch), if your nvme-cli supports it

# Which command set is each namespace? Look at the CSI descriptor.
sudo nvme ns-descs /dev/ng0n3                # "csi : 1" means Key Value
ls -l /dev/ng* /dev/nvme*n*                  # a KV namespace has /dev/ng0n3 but no /dev/nvme0n3

# Raw KV-specific Identify Namespace (CNS 05h, CSI 01h) via admin pass-through, read-only
sudo nvme admin-passthru /dev/nvme0 --opcode=0x06 --namespace-id=3 \

Code / pseudocode

The simulation below models the KV command semantics — key and value limits, conditional Store, Retrieve with a host buffer, Exist, List, Delete — and prints statuses with the libnvme encodings. The limits are parameters because a real device reports them; 16 bytes is used as the default key maximum, subject to the caveat above.

#!/usr/bin/env python3
"""Key Value namespace behaviour model (teaching simulation).
Command names follow the NVMe KV Command Set; opcodes and status values are the
libnvme encodings. KEY_MAX and VALUE_MAX stand in for the limits a real device
reports in its KV Identify Namespace data -- read those from your device."""

OPC = {"Store": 0x01, "Retrieve": 0x02, "List": 0x06, "Delete": 0x10, "Exist": 0x14}
SC = {"SUCCESS": (0x0, 0x00, "Successful Completion"),
      "INVALID_VALUE_SIZE": (0x0, 0x85, "Invalid Value Size"),
      "INVALID_KEY_SIZE": (0x0, 0x86, "Invalid Key Size"),
      "KEY_NOT_EXIST": (0x0, 0x87, "KV Key Does Not Exist"),
      "KEY_EXISTS": (0x0, 0x89, "Key Exists")}

class KVNamespace:
    def __init__(self, key_max=16, value_max=1 << 20):
        self.key_max, self.value_max = key_max, value_max
        self.store_ = {}
        self.used = 0

    def _check_key(self, key):
        return 1 <= len(key) <= self.key_max

    def store(self, key, value, sike=False, sinke=False):
        """sike: store only if key exists; sinke: store only if key does not exist."""
        if not self._check_key(key):      return SC["INVALID_KEY_SIZE"], None
        if len(value) > self.value_max:   return SC["INVALID_VALUE_SIZE"], None
        exists = key in self.store_
        if sike and not exists:           return SC["KEY_NOT_EXIST"], None
        if sinke and exists:              return SC["KEY_EXISTS"], None
        delta = len(value) - (len(self.store_[key]) if exists else 0)
        self.store_[key] = bytes(value)
        self.used += delta
        return SC["SUCCESS"], None

    def retrieve(self, key, host_buf_len):
        """Returns (status, (bytes copied, full value length))."""
        if not self._check_key(key):      return SC["INVALID_KEY_SIZE"], None
        if key not in self.store_:        return SC["KEY_NOT_EXIST"], None
        v = self.store_[key]
        return SC["SUCCESS"], (v[:host_buf_len], len(v))

    def delete(self, key):
        if not self._check_key(key):      return SC["INVALID_KEY_SIZE"], None
        if key not in self.store_:        return SC["KEY_NOT_EXIST"], None
        self.used -= len(self.store_.pop(key))
        return SC["SUCCESS"], None

    def exist(self, key):
        if not self._check_key(key):      return SC["INVALID_KEY_SIZE"], None
        return (SC["SUCCESS"] if key in self.store_ else SC["KEY_NOT_EXIST"]), None

    def list(self, start_key, max_keys):
        """Keys at or after start_key. Ordering is implementation-dependent;
        this model returns byte-wise sorted order."""
        if not self._check_key(start_key): return SC["INVALID_KEY_SIZE"], None
        keys = sorted(k for k in self.store_ if k >= start_key)
        return SC["SUCCESS"], keys[:max_keys]

def show(cmd, key, result):
    (sct, sc, name), data = result
    k = key if isinstance(key, str) else key.decode(errors="replace")
    extra = "" if data is None else f"  data={data!r}"
    print(f"{cmd:9s} (opc {OPC[cmd]:02X}h) key={k!r:24s} -> SCT={sct}h SC={sc:02X}h {name}{extra}")

if __name__ == "__main__":
    ns = KVNamespace()
    show("Store",    b"user:1001",  ns.store(b"user:1001", b'{"name":"Ada"}'))
    show("Store",    b"user:1001",  ns.store(b"user:1001", b'{"name":"Bob"}', sinke=True))
    show("Store",    b"user:1002",  ns.store(b"user:1002", b'{"name":"Cy"}', sike=True))
    show("Store",    b"user:1002",  ns.store(b"user:1002", b'{"name":"Cy"}'))
    show("Retrieve", b"user:1001",  ns.retrieve(b"user:1001", 4096))
    show("Retrieve", b"user:1001",  ns.retrieve(b"user:1001", 8))
    show("Exist",    b"user:9999",  ns.exist(b"user:9999"))
    show("Store",    b"x" * 17,     ns.store(b"x" * 17, b"too long key"))
    show("Store",    b"",           ns.store(b"", b"empty key"))
    show("List",     b"user:",      ns.list(b"user:", 10))
    show("Delete",   b"user:1001",  ns.delete(b"user:1001"))
    show("Delete",   b"user:1001",  ns.delete(b"user:1001"))
    print(f"bytes in use: {ns.used}")

The second listing is pseudocode for a host-side KV library call built on pass-through. It shows the checks that belong in the host.

int kv_put(int ng_fd, uint32_t nsid, const void *key, size_t klen,
           const void *val, size_t vlen, enum put_mode mode)
{
    if (klen == 0 || klen > ns_limits.max_key_len)   return -EINVAL;  /* never let 86h happen */
    if (vlen > ns_limits.max_value_len)              return -EFBIG;   /* never let 85h happen */
    if (vlen > ctrl_limits.mdts_bytes)               return -E2BIG;   /* cannot move in one command */

    void *buf = dma_buffer_copy(val, vlen);          /* pinned, page-aligned */
    struct kv_sqe sqe = { .opcode = KV_STORE /*01h*/, .nsid = nsid };
    kv_sqe_set_key(&sqe, key, klen);                 /* positions per KV 1.4 */
    kv_sqe_set_value_size(&sqe, vlen);
    kv_sqe_set_store_option(&sqe, mode == PUT_CREATE ? SINKE : mode == PUT_UPDATE ? SIKE : 0);
    sqe_set_prp(&sqe, buf, vlen);

    status = passthru_io(ng_fd, &sqe, /*result*/ NULL);
    switch (status) {
    case 0:                return 0;
    case SC_KEY_EXISTS:    return -EEXIST;            /* 89h: expected for PUT_CREATE races */
    case SC_KEY_NOT_EXIST: return -ENOENT;            /* 87h: expected for PUT_UPDATE races */
    default:               return log_and_map(status); /* real errors */
    }
}

Worked example

Problem. A session cache stores 300 million entries, keys are 36-character UUID strings, values average 600 bytes. Evaluate storing it in a KV namespace with a 16-byte key limit, versus a host hash table on a block namespace with 4 KiB blocks. Synthetic example for teaching.

  1. Key fit. A 36-character UUID string is 36 bytes; its binary form is 16 bytes. Converting text UUIDs to binary gives exactly 16 bytes — fits, no hashing needed.
  2. Capacity. 300 M × 600 B = 180 GB of values. KV namespace stores values without block padding (device-internal packing overhead aside). A naive block design with one 4 KiB block per entry would need 300 M × 4 KiB = 1.2 TB; packing several entries per block needs a host index and compaction.
  3. Host DRAM. A host hash table at ~32 bytes per entry (key 16 + location 8 + overhead) = 9.6 GB of host DRAM. With KV, the host needs none; the device needs its own index memory, so check the device's maximum number of keys ≥ 300 M.
  4. Operations. A lookup with KV: one Retrieve; PCIe moves 64 B SQE + ~600 B value + 16 B CQE. With a block design and host index in DRAM: one READ of 4 KiB; PCIe moves 64 B + 4096 B + 16 B. KV moves about 6× less data per lookup (680 B versus 4,176 B).
  5. Writes. KV: one Store per update. Block with packed blocks: read-modify-write of a 4 KiB block, or log-append plus compaction later.
  6. Risks. Device maximum keys, List semantics (needed for expiry scans?), single-vendor availability, Linux tooling, and portability of backups (you cannot dd a KV namespace).

Conclusion: technically attractive for this workload; operationally contingent on device limits and ecosystem. That is the typical KV verdict.

Common mistakes

  • Treating "KV Key Does Not Exist" from Exist as an error and alarming on it.
  • String keys with and without a terminating NUL, or with padding: "abc" and "abc\0" are different keys.
  • Hard-coding the key limit instead of reading the KV format descriptor.
  • Assuming List is sorted and building prefix scans on it.
  • Submitting Store then Retrieve without waiting and expecting the new value.
  • Exist-then-Store for create-only semantics instead of SINKE — a race between hosts.
  • Values larger than MDTS in a single command.
  • Expecting a block device to appear for a KV namespace.
  • Confusing 87h across command sets: in a non-KV namespace the generic 80h–BFh range means something else.

Senior engineer insight

Every storage design has an index from names to bytes. Block storage puts most of it in the host and a second copy (the FTL) in the device. KV puts it in the device. ZNS puts it in the host and strips it from the device. FDP shares it. When someone proposes a KV SSD, the senior questions are: can the device's index hold our key count with our access pattern; what happens to latency when it cannot; how do we back up, migrate and inspect data when no standard tool can read the namespace; and is the saving in host CPU worth a single-purpose device?

A second insight: KV statuses turn data-plane outcomes into status codes. Monitoring systems that count every non-zero status as an error will report a healthy KV cache as failing. Instrumentation must be command-set aware.

Hints

Hint

For Step 3: 4,000 bytes at MRRS 512 is eight reads (seven of 512 bytes and one of 416 bytes, assuming a page-aligned buffer); each 512-byte read completes as two 256-byte CplDs (MPS). The 416-byte read completes as 256 + 160.

Solution

Solution

Step 1: outputs as printed by the simulator (success; Key Exists; KV Key Does Not Exist; success; success with 14-byte value; success with 8-byte truncated copy and full length 14 — a modelling choice; KV Key Does Not Exist; Invalid Key Size twice; List of two keys; success; KV Key Does Not Exist).

Step 2: with SINKE, the second Store returns Key Exists. With Exist-then-Store, both clients can receive "does not exist" before either Store executes, and both Stores then succeed — last writer wins silently.

Step 3: Store 4,000 B: SQE fetch (MRd Len=16 + CplD), eight value MRds (Len=128 ×7, Len=104 ×1), sixteen CplDs, CQE MWr (Len=4), MSI-X MWr. Retrieve 1 B: SQE fetch, one MWr Len=1 FirstBE=0001 (LastBE=0000 for a single-DW request), CQE, MSI-X. The SQE and CQE are fixed-size regardless of payload — the per-command overhead that makes tiny values inefficient on the link.

Step 4: on most systems, no KV support; the controller's I/O command set data shows only NVM (and maybe ZNS).

Questions: 1 — status codes are how NVMe reports per-command outcomes without a data phase; Exist avoids DMA entirely. 2 — the command and completion formats are fixed by the Base specification. 3 — whether key byte encoding changed (host or device), whether the namespace was reformatted, and whether the right NSID/CSI is in use.

What a senior engineer notices

That the simulator's truncation behaviour is a modelling choice, not a fact — and that the real behaviour must be read from the specification before any library depends on it.

  3. Why is generic status 81h ambiguous unless you know the namespace's CSI?

Answers

1. Doorbell MWr; SQE MRd + CplD; CQE MWr (status 87h); MSI-X MWr. Zero data TLPs.

2. Phase 1; SC = 0x89; SCT = 0; DNR = 0; CID 0x0203 → Key Exists: the Store had SINKE set and the key was present.

3. The generic 80h–BFh range is I/O command set specific: 81h is Capacity Exceeded for the NVM command set, while KV's assignments are different; the opcode and CSI give the context.

4. Example: 4 bytes tenant (20 bits used, 12 reserved) + 8 bytes object ID + 2 bytes version + 2 bytes reserved/flags = 16 bytes, big-endian so byte-wise order groups tenants (useful only if List is ordered).

5. Ordered scans and arbitrary-length names stay in host software they already have; ZNS has broader industry support and Linux integration; the host controls placement and GC policy; values far larger than KV limits are natural in zones.

Quiz

  1. What is the Command Set Identifier of a KV namespace?

    • 00h
    • 01h
    • 02h
    • 04h
    Answer and reasoning

    NVM is 00h, KV 01h, ZNS 02h, SLM 03h, Computational Programs 04h.

  2. Where does the key of a KV command travel?

    • Inside the Submission Queue Entry
    • In a separate key buffer fetched by DMA
    • In the doorbell write
    • In the completion
    Answer and reasoning

    The KV design places the key in command dwords of the 64-byte SQE so no extra DMA is needed. That is why keys are short.

  3. Which command moves no data in either direction?

    • Store
    • Retrieve
    • List
    • Exist
    Answer and reasoning

    Exist (and Delete) carry only the key; the answer is the completion status.

  4. A Store with "Store If No Key Exists" targets an existing key. Status?

    • KV Key Does Not Exist
    • Invalid Key Size
    • Key Exists
    • Success, value replaced
    Answer and reasoning

    SINKE is create-only; an existing key yields Key Exists (89h in libnvme).

  5. Which statement about KV List is safe to assume without reading your device's documentation?

    • Keys are returned sorted
    • A host may need several List commands to enumerate all keys
    • List returns values as well as keys
    • List is atomic with respect to concurrent Stores
    Answer and reasoning

    A host buffer has finite size, so iteration over multiple commands is inherent. Ordering, atomicity and contents beyond keys must be checked.

  6. In a trace, how can you tell a KV Store's value fetch from a block WRITE's data fetch?

    • Its length need not be a multiple of the block size and may end with partial byte enables
    • It uses Configuration Write TLPs
    • It carries a different Requester ID
    • It is always a single TLP
    Answer and reasoning

    Block transfers are multiples of the LBA size; KV values are any byte length, visible as odd lengths and partial Last DW BE.

  7. Why is it dangerous to implement create-only semantics with Exist followed by Store?

    Model answer

    Because the two commands are separate and NVMe does not order or lock across commands; two clients can both observe "does not exist" and both Store, with the last one silently winning. Store with SINKE performs the check and the store atomically in the device.

  8. Why does Linux not create /dev/nvme0n3 for a KV namespace, and how do applications reach it?

    Model answer

    The block layer needs LBA-addressed fixed-size blocks; KV has neither. The driver exposes a generic character device /dev/ng0n3 (kernel 5.13+), through which user space sends pass-through KV commands via ioctl or io_uring.

  9. Give two reasons KV might reduce total write amplification compared with an LSM-tree store on a block SSD.

    Model answer

    The host no longer performs compaction rewrites across PCIe, and the device maintains one index instead of host index + file system + FTL, so data is relocated by one garbage collector instead of several stacked ones.

Interview questions

  1. Beginner. What are the main KV commands?

    Model answer

    Store, Retrieve, Delete, Exist and List (plus Flush and reservation commands).

  2. Beginner. How does a KV namespace differ from a block namespace?

    Model answer

    It is addressed by keys instead of LBAs, holds variable-size values instead of fixed-size blocks, and the device maintains the key index.

  3. Intermediate. Why are KV keys limited to a small size?

    Model answer

    To fit inside the 64-byte SQE, so the controller has the key as soon as it fetches the command, with no extra DMA. The limit is reported per KV format and must be read from Identify.

  4. Intermediate. How would you recognise KV traffic in an unlabelled PCIe capture?

    Model answer

    Decode SQEs: NSID of a KV namespace and opcodes 01h/02h/06h/10h/14h with non-LBA fields; data transfers of arbitrary byte lengths with partial byte enables; commands with no data phase (Exist/Delete); statuses in 85h–89h.

  5. Advanced. A team reports 3% of Retrieves fail with 87h under load but never in single-threaded tests. Diagnose.

    Model answer

    Ordering: Retrieves submitted before the corresponding Store completes, or Delete/Store races, across queues or within a doorbell batch. Evidence: trace with CIDs and completion times; check whether the failing Retrieve's SQE fetch precedes the Store's CQE. Fix: enforce completion-before-dependent-submission in the host.

  6. Senior. Make the case for and against adopting KV SSDs for a metadata service.

    Model answer

    For: fewer layers, lower host CPU and DRAM, lower write amplification, atomic conditional puts, byte-granular values. Against: small key limit, unclear List ordering, limited vendor support, weak Linux tooling, harder backup/migration/forensics, device index limits under growth, lock-in. Decide by measuring key-count scaling, tail latency and operational tooling cost, not only throughput.

Model explanation for the senior engineer

Every design maps names to bytes. Block storage keeps that map twice — host and FTL. KV keeps it once, in the device, at the cost of a fixed key format and device-bounded scale. ZNS moves it to the host and slims the device. FDP keeps block semantics but lets the host hint placement. KV's technical benefits are real for short-key get/put workloads; its risks are operational: tooling, backups, portability, and monitoring that understands that 87h is an answer, not an error.

Chapter summary

The Key Value Command Set (KV 1.4, CSI 01h) addresses data by short byte-string keys and stores variable-size values. Store (01h), Retrieve (02h), List (06h), Delete (10h) and Exist (14h) replace LBA reads and writes; the key travels inside the SQE, which is why keys are short (a 16-byte maximum is widely documented — confirm in KV 1.4 and read your device's limit); values move by DMA like block data. Store options SIKE and SINKE give atomic update-only and create-only semantics. Statuses 85h–89h report key/value size problems, absence and presence. KV removes host indexing layers and can reduce write amplification, but it trades away ordered scans, long keys, ecosystem and tooling.
