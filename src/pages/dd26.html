Chapter 27 taught you how to create an I/O queue pair. This module treats I/O queues as a living system: many Submission Queues feeding fewer Completion Queues, sharing interrupt vectors, competing for the controller's attention under an arbitration policy, surviving resets, and failing in ways that only show up when you look at more than one queue at a time.

Orientation

An NVM Express (NVMe) controller on PCI Express (PCIe) can carry tens of I/O queue pairs at once. Chapter 27 showed one pair being born: Create I/O Completion Queue, Create I/O Submission Queue, first doorbell, first fetch. This module goes deeper in four directions that the chapter only touched. First, topology: how Submission Queues (SQs) map onto Completion Queues (CQs) and interrupt vectors, and how to size a shared CQ so it can never overflow. Second, competition: what arbitration does to latency when queues of different priority are busy at the same time. Third, lifecycle: what happens to queues across deletion, controller reset, suspend and resume, and why stale queue state is a classic source of silent failure. Fourth, evidence: the per-queue invariants a trace must satisfy, so that you can check a multi-queue capture mechanically instead of by eye.

This module assumes you can already encode Create I/O CQ (opcode 05h) and Create I/O SQ (opcode 01h) from memory, explain the creation and deletion order, and compute queue slot and doorbell addresses. If not, read Chapter 27 — I/O Queues first. The ring arithmetic (head, tail, full, empty, the phase tag) is in Chapter 25 — Queue Architecture; the Admin queue that carries the create commands is in Chapter 26 — Admin Queue.

Where it goes next: Module 27 — Doorbells studies the 4-byte writes that move each queue, and Module 28 — NVMe Command Structure studies what sits in each slot. Interrupt delivery for each CQ is treated in depth in Module 19 — MSI and MSI-X, and queue behaviour across resets in Module 41 — Reset.

Kid story

Imagine a big airport. Every check-in desk has its own conveyor belt that carries suitcases into the baggage room. That is a Submission Queue: each desk puts suitcases on its own belt, and nobody else touches that belt.

Inside, the baggage handlers take suitcases off the belts. They cannot take from all belts at once, so a supervisor says which belt to take from next: "two from belt 1, then two from belt 2…". Some belts are marked urgent (connecting flights) and get served first.

When a suitcase has been checked, a small ticket comes back out on a return carousel — that is the Completion Queue. Several desks can share one return carousel, as long as each ticket says which desk it came from. Each carousel has a light that flashes in one office when a ticket arrives — that is the interrupt.

The airport has rules: you must build the return carousel before you open a desk that sends tickets to it; you must close every desk using a carousel before you take the carousel away; and if a carousel is too small for all the desks sharing it, tickets pile up and the handlers have to stop.

Analogy boundary

What it represents. Belts are SQs, owned by one producer (a desk, i.e. a CPU or a group of CPUs). The supervisor is the controller's arbiter. The return carousel is a CQ, possibly shared by several SQs, and each ticket carries the desk number (SQ Identifier) and a ticket number (Command Identifier). The flashing light is the Message Signaled Interrupt eXtended (MSI-X) vector bound to the CQ. Building order and closing order mirror the creation and deletion rules.

What it hides. In NVMe the belts and carousels are not inside the airport (the controller); they are memory in the host, and the controller reaches them across the PCIe link with Direct Memory Access (DMA). The handlers do not watch the belts; a desk must press a doorbell with the new belt position. Tickets do not come back in the order suitcases went in. And the airport cannot see whether a desk is staffed: the controller has no idea which CPU uses which queue.

Where it misleads. A real carousel overflows physically; an NVMe CQ never overwrites — the controller simply stops posting when the CQ is full, which looks like a hang rather than a mess. "Urgent" belts in an airport finish urgent work first; NVMe arbitration only decides which SQ is fetched next, not which command finishes first inside the device. And an airport can re-route a desk to another carousel while open; an SQ's CQ is fixed at creation.

Mechanism

The life of two SQs sharing one CQ, from negotiation to teardown. Synthetic, reference lab system.

  1. Negotiate. Who: driver. What: Set Features FID 07h asks for 32 SQs and 32 CQs. Where: controller's queue-resource allocator. Evidence: Admin CQE Dword 0 (NSQA bits 15:00, NCQA bits 31:16, 0's based).
  2. Allocate interrupts. Who: operating system. What: MSI-X table entries 0…N programmed with address/data, affinity chosen. Where: MSI-X table in BAR0 + 0x2000 (reference system). Evidence: BAR writes during probe; /proc/interrupts.
  3. Allocate and map queue memory. Who: driver and IOMMU. What: SQ1 and SQ2 (64 KiB each), CQ1 (32 KiB for 2048 entries), zeroed. Where: host DRAM, IOMMU page tables. Evidence: none on the link.
  4. Create CQ1. Who: driver, then controller. What: CQ context 1 created: base 0x1_2341_0000, QSIZE 7FFh (2048 entries), IV 1, IEN 1, PC 1. Where: controller queue-context table. Evidence: SQE payload; successful Admin CQE.
  5. Create SQ1 → CQ1 and SQ2 → CQ1. Who: driver, waiting for each completion. What: two SQ contexts both naming CQID 1. Where: controller. Evidence: two SQE payloads with CDW11 bits 31:16 = 0001h; two successful Admin CQEs.
  6. Submit on both. Who: CPU 0 on SQ1, CPU 5 on SQ2. What: SQ tails advance independently. Where: host SQ memory and the controller's latched tails. Evidence: MWr32 to 0xFE60_1008 and 0xFE60_1010.
  7. Arbitrate and fetch. Who: controller arbiter. What: chooses SQ1 or SQ2 by round robin, takes up to Arbitration Burst commands, advances that SQ's head. Where: controller. Evidence: interleaving of MRd64 to the SQ1 and SQ2 ranges.
  8. Complete into the shared CQ. Who: controller completion engine. What: CQEs for both SQs written into CQ1 in completion order, each with SQID and SQHD of its own SQ. Where: CQ1 memory. Evidence: MWr64 into 0x1_2341_xxxx with DW2 = SQID/SQHD.
  9. Interrupt. Who: controller. What: vector 1 signalled (subject to coalescing). Where: MSI-X address 0xFEE0_1000. Evidence: MWr32 with data 0x41.
  10. Reap and demultiplex. Who: interrupt handler on the CPU targeted by vector 1. What: reads CQEs by phase; routes by (SQID, CID). Evidence: CQ1HDBL MWr32 to 0xFE60_100C.
  11. Tear down. Who: driver. What: Delete I/O SQ 1 and 2 (opcode 00h), then Delete I/O CQ 1 (04h); or a controller reset (CC.EN = 0) which deletes everything. Evidence: Admin CQEs; possibly I/O CQEs with Command Aborted due to SQ Deletion.

With a shared CQ, the CPU that reaps a completion may not be the one that submitted it — a cache-locality cost, and one reason Linux prefers one CQ per SQ when enough CQs and vectors are granted.

The central concept on the ladder: a multi-queue topology

Every check-in desk has its own belt in; desks can share a return carousel; each carousel has a light in one office; urgent belts are served first.

Each SQ has one producer and one CQ. Several SQs may name the same CQ. Each CQ has at most one interrupt vector or none. The controller picks which SQ to fetch from with the selected arbitration mechanism.

The controller holds a context per queue and a doorbell register per queue side. Its arbiter scans SQ contexts whose latched tail differs from head; its completion engine writes into the CQ named by the command's SQ context and drives the vector named by that CQ context.

NVMe Base Specification 2.4: queueing model (many-to-one SQ→CQ, full/empty), Create/Delete I/O SQ/CQ, Number of Queues, Arbitration feature, CAP.AMS/CC.AMS. NVMe over PCIe Transport 1.4: queue memory and interrupts on PCIe.

Per SQ: host MWr doorbells and device MRd fetches in that SQ's address range. Per CQ: device MWr CQEs in that CQ's range, then MWr to that CQ's MSI-X address. CQE Dword 2 ties each completion to its SQ.

Group trace rows by address range: each SQ range sees only fetches, each CQ range only CQE writes. Interleaving of fetch ranges shows arbitration; SQIDs in one CQ range reveal sharing.

When "only some queues" misbehave, build the per-queue fact table (QID, base, size, CQID, IV, IEN, CPU set) from the create payloads and compare columns; when latency differs between CPUs, look at fetch interleaving and the Arbitration settings before blaming media.

On the host, NUMA (Non-Uniform Memory Access) placement of queue memory and MSI-X affinity decide whether a CQE write and the handler that reads it are on the same socket. A queue whose ring sits on socket 0 but whose vector targets a CPU on socket 1 pays a cross-socket cache miss on every completion. This is host policy, invisible on the PCIe link, and shows up only as a latency difference between queues that are otherwise identical.

Ordering across queues

Within one direction on one path, PCIe keeps posted writes in order (absent Relaxed Ordering), so data, CQE and MSI-X for one command arrive in that order. Across queues there is no NVMe ordering at all. Two commands on different SQs, even to the same Logical Block Address (LBA), may execute and complete in either order. A host that needs ordering between two I/Os must wait for the first completion before submitting the second — regardless of whether they are on the same queue or not. Shared CQs do not create ordering either: the order of CQEs in a shared CQ is completion order, not submission order.

Completion and errors

Queue-management errors surface as Admin CQE status values (command specific, Status Code Type 1h, with names such as Completion Queue Invalid, Invalid Queue Identifier, Invalid Queue Size, Invalid Interrupt Vector, Invalid Queue Deletion — numeric codes to be read in the specification). Queue use errors surface differently: invalid doorbell writes through Asynchronous Event Requests (Chapter 28), DMA faults on queue memory as PCIe completion status (Unsupported Request on an SQE fetch) or as nothing at all (a dropped CQE write to an unmapped IOVA), and lost interrupts as nothing at all. The asymmetry is the theme of the debugging section: the controller can tell you about bad commands; it often cannot tell you about bad queues.

Intermediate lab — Size a shared CQ, then break it

Safe lab Pure simulation.

Objective

Show experimentally that a shared CQ smaller than the sum of its SQs' outstanding limits can block the controller, and that fast host reaping only hides the problem.

Prerequisites

Full/empty rules from Chapter 25; Python 3.8+.

Setup

#!/usr/bin/env python3
"""Shared-CQ sizing simulator (synthetic teaching model, standard library only).
Several SQs complete into one CQ. The controller may post a CQE only when the
CQ is not full ((tail + 1) % size != head). The host reaps the CQ every
REAP_EVERY microseconds, frees those commands, and refills its SQs.
"""
import random

def simulate(cq_entries, sq_depths, reap_every, run_us=20000, seed=7):
    rng = random.Random(seed)
    head = tail = 0                     # CQ indices: controller owns tail, host owns head
    outstanding = {q: 0 for q in sq_depths}
    executing = []                      # (finish_time, sqid) inside the controller
    in_cq = []                          # sqids of CQEs posted but not yet reaped
    blocked_us, worst_wait = 0, 0
    for t in range(run_us):
        for q, depth in sq_depths.items():          # host keeps each SQ full
            while outstanding[q] < depth:
                outstanding[q] += 1
                executing.append((t + rng.randint(60, 140), q))  # media 60-140 us
        executing.sort()
        ready = [e for e in executing if e[0] <= t]
        posted = 0
        for e in ready:
            if (tail + 1) % cq_entries == head:     # CQ full: controller must wait
                break
            tail = (tail + 1) % cq_entries
            in_cq.append(e[1])
            executing.remove(e)
            posted += 1
        waiting = len(ready) - posted
        blocked_us += waiting > 0
        worst_wait = max(worst_wait, waiting)
        if t % reap_every == 0:                     # host reaps, then CQ head doorbell
            for q in in_cq:
                outstanding[q] -= 1
            in_cq.clear()
            head = tail
    return blocked_us, worst_wait

if __name__ == "__main__":
    sqs = {1: 255, 2: 255}                  # each SQ may hold 255 outstanding commands
    need = sum(sqs.values()) + 1
    print(f"SQ limits {sqs}: a CQ needs at least {need} entries to be unable to fill")
    for entries, reap in [(256, 200), (256, 20), (511, 200), (1024, 200)]:
        blocked, worst = simulate(entries, sqs, reap)
        verdict = "never blocked" if blocked == 0 else f"blocked {blocked} us"
        print(f"CQ {entries:5d} entries, reap every {reap:3d} us: {verdict:>16}, "
              f"worst results waiting for a CQ slot = {worst}")

Questions

  1. Why does the 256-entry CQ never block when the host reaps every 20 µs?
  2. What host events could stretch the reap interval in a real system?
  3. Why is 511 the threshold rather than 510?

Expected reasoning

Blocking needs both a CQ smaller than the worst-case outstanding sum and a host that leaves completions unreaped long enough. Design must remove the first condition; the second is not under the driver's full control.

Solution

(1) With media time ≥ 60 µs and reaping every 20 µs, at most a few dozen completions can accumulate between reaps, far below 255 free slots: the CQ never fills, by luck of timing rather than by design. (2) Interrupt coalescing with a long aggregation time, a CPU busy with higher-priority work, a long interrupt-disabled section, a virtual machine descheduled by the hypervisor, or a debugger breakpoint. (3) A CQ of N entries holds at most N − 1 entries; 510 outstanding commands need N − 1 ≥ 510, so N ≥ 511. Step 3: three SQs of 255 need 766 entries.

#!/usr/bin/env python3
"""Per-queue invariant checker for synthetic NVMe-over-PCIe traces.
Standard library only. Events are decoded analyzer rows:
  ("CQ", qid, base, entries, iv, ien)      Create I/O CQ payload (success assumed)
  ("SQ", qid, base, entries, cqid)         Create I/O SQ payload (success assumed)
  ("SQDB", qid, value)                     host MWr to SQ tail doorbell
  ("FETCH", addr, nbytes)                  device MRd of SQEs
  ("CQE", addr, sqid, sqhd, cid, phase)    device MWr of one CQE
  ("CQDB", qid, value)                     host MWr to CQ head doorbell
"""
class SQ:
    def __init__(s, base, n, cqid):
        s.base, s.n, s.cqid, s.tail, s.head, s.last_sqhd = base, n, cqid, 0, 0, 0
class CQ:
    def __init__(c, base, n):
        c.base, c.n, c.tail, c.head, c.phase = base, n, 0, 0, 1

def check(events):
    sqs, cqs, out = {}, {}, []
    def flag(i, msg): out.append(f"#{i:<3} VIOLATION {msg}")
    for i, ev in enumerate(events, 1):
        kind = ev[0]
        if kind == "CQ":
            _, q, base, n, iv, ien = ev
            cqs[q] = CQ(base, n)
        elif kind == "SQ":
            _, q, base, n, cqid = ev
            if cqid not in cqs:
                flag(i, f"SQ{q} names CQ{cqid}, which does not exist")
            sqs[q] = SQ(base, n, cqid)
        elif kind == "SQDB":
            _, q, v = ev
            sqs[q].tail = v
        elif kind == "FETCH":
            _, addr, nbytes = ev
            hit = [(q, s) for q, s in sqs.items() if s.base <= addr < s.base + s.n * 64]
            if not hit:
                flag(i, f"fetch at 0x{addr:X} is outside every SQ (I1)")
                continue
            q, s = hit[0]
            slot = (addr - s.base) // 64
            count = nbytes // 64
            published = (s.tail - s.head) % s.n
            if slot != s.head:
                flag(i, f"SQ{q} fetch starts at slot {slot}, expected head {s.head} (I1)")
            if count > published:
                flag(i, f"SQ{q} fetch of {count} SQEs but only {published} published (I1)")
            s.head = (slot + count) % s.n
        elif kind == "CQE":
            _, addr, sqid, sqhd, cid, p = ev
            hit = [(q, c) for q, c in cqs.items() if c.base <= addr < c.base + c.n * 16]
            if not hit:
                flag(i, f"CQE at 0x{addr:X} is outside every CQ (I2)")
                continue
            q, c = hit[0]
            slot = (addr - c.base) // 16
            if slot != c.tail:
                flag(i, f"CQ{q} CQE in slot {slot}, expected tail {c.tail} (I2)")
                c.tail = slot                    # resynchronise and keep checking
            if (c.tail + 1) % c.n == c.head:
                flag(i, f"CQ{q} posted while full (head {c.head}) (I3)")
            if sqid not in sqs or sqs[sqid].cqid != q:
                flag(i, f"CQE on CQ{q} carries SQID {sqid}, which is not mapped to CQ{q} (I2)")
            elif (sqhd - sqs[sqid].last_sqhd) % sqs[sqid].n > (sqs[sqid].head - sqs[sqid].last_sqhd) % sqs[sqid].n:
                flag(i, f"SQ{sqid} SQHD {sqhd} is beyond what was fetched (I4)")
            else:
                sqs[sqid].last_sqhd = sqhd
            if p != c.phase:
                flag(i, f"CQ{q} slot {slot} written with P={p}, expected {c.phase} (I5)")
            c.tail = (c.tail + 1) % c.n
            if c.tail == 0:
                c.phase ^= 1
        elif kind == "CQDB":
            _, q, v = ev
            c = cqs[q]
            if (v - c.head) % c.n > (c.tail - c.head) % c.n:
                flag(i, f"CQ{q} head doorbell {v} passes the posted tail {c.tail} (I3)")
            c.head = v
    return out

Number of Queues grant; Admin CQE status for each create; doorbell addresses in the trace.
First check
Compare NSQA/NCQA with the highest QID created.
Second check
Recompute every doorbell address with the real CAP.DSTRD and check it lies inside BAR0's size.
Disambiguating experiment
Limit the driver to 8 queues; then create queue 9 alone with a hand-built command and watch its first use.
Likely conclusion
A boundary almost always means arithmetic or a resource limit, not media.
Confidence
High.

Pattern 3 — Latency unfairness between CPUs

Symptom
p99 read latency on CPUs 0–3 is ten times worse than on CPUs 8–15 for the same workload.
Possible causes
Weighted round robin with an urgent or high-weight queue hogging fetches; several CPUs sharing one queue (fewer queues than CPUs) and contending on its lock; shared CQ whose vector targets a remote CPU; NUMA-remote queue memory.
Evidence
Doorbell-to-fetch latency per SQ; the CPU→hctx map; vector affinity; numa_node.
First check
Measure doorbell-to-fetch for the slow CPUs' SQ. If it is large, arbitration is the cause.
Second check
If fetch latency is normal, compare CQE-to-handler time (MSI-X MWr to CQ head doorbell) across queues.
Disambiguating experiment
Switch to round robin (driver/controller configuration on a test system) or move the background job to a Low-class SQ, and remeasure.
Likely conclusion
Fetch delay → arbitration policy; handler delay → host interrupt placement.
Confidence
Medium until per-segment timing is measured; high after.

Pattern 4 — Controller stalls under heavy load with a shared CQ

Symptom
At high queue depth, all SQs mapped to one CQ stop completing for milliseconds; fetches continue until the device's internal slots fill.
Possible causes
CQ smaller than the sum of its SQs' outstanding limits combined with delayed reaping (coalescing, CPU busy); CQ head doorbell written too rarely.
Evidence
Gap in CQE writes to that CQ while (tail + 1) mod size equals the last head doorbell value.
First check
Sum the outstanding limits of the SQs on that CQ and compare with its size − 1.
Second check
Track the CQ head doorbell values and timing around the stall.
Disambiguating experiment
Double the CQ size; if stalls vanish, the sizing was the cause.
Likely conclusion
Host design error (CQ sizing) exposed by host timing.
Confidence
High.

Pattern 5 — Stalls only after reset, resume or driver rebind

Symptom
Fresh boot is fine; after a controller reset or resume, some queues time out.
Possible causes
Stale queue base addresses; host indices or phase not reset (host expects phase 0 on a fresh CQ, or SQ tail not zeroed while the controller's head restarted at 0); CQ memory not re-zeroed so old entries with P = 1 look new; queue count changed by the new grant.
Evidence
Create payloads after reset vs host allocation; first doorbell value after reset (should be small: tail restarts at 0); first CQE phase.
First check
Is the first SQ tail doorbell after reset a value consistent with a freshly zeroed tail?
Second check
Is CQ memory zeroed before Create I/O CQ, and does the host reset its expected phase to 1?
Disambiguating experiment
Fill CQ memory with a pattern having P = 1 before recreation; phantom completions appear immediately if the host does not re-zero.
Likely conclusion
Host lifecycle bug; the controller starts every queue fresh after CC.EN = 0 → 1.
Confidence
High when the first-use evidence after reset is captured.

Interview

Beginner

  1. Why does NVMe have many I/O queues instead of one?

    Model answer

    So cores submit and complete in parallel without a shared lock, each with its own interrupt, and the device sees enough work to stay busy.

  2. What must exist before you create an I/O SQ?

    Model answer

    The I/O CQ it names (and, before that, the Admin queue and the Number of Queues grant).

  3. Can two SQs share a CQ?

    Model answer

    Yes; each CQE carries the SQID. One SQ cannot spread over several CQs.

  4. What is a polled queue?

    Model answer

    A CQ created with interrupts disabled (IEN = 0); the host checks phase tags itself instead of waiting for an interrupt.

  5. Who decides how many I/O queues exist?

    Model answer

    The controller grants a maximum through Number of Queues; the driver decides how many of those to create.

Intermediate

  1. How big must a CQ shared by two 1024-entry SQs be to never fill?

    Model answer

    2 × 1023 pending CQEs need at least 2047 entries; 2048 is natural.

  2. What does QPRIO do under round robin?

    Model answer

    Nothing. It is only used when weighted round robin with urgent priority class is selected in CC.AMS.

  3. Why can a Create I/O CQ succeed with a bad base address?

    Model answer

    Creation records the address without accessing it; the first CQE post is the first access, and a posted write returns no error.

  4. How does Linux map CPUs to NVMe queues?

    Model answer

    blk-mq creates one hardware context per I/O queue and assigns CPU sets aligned with vector affinity; with fewer queues than CPUs, CPUs share.

  5. What happens to outstanding commands when an SQ is deleted?

    Model answer

    They complete or are aborted with Command Aborted due to SQ Deletion, posted to the CQ before the Delete completes — so the CQ must outlive the SQ.

Advanced

  1. Explain how weighted round robin with urgent priority class can starve a queue.

    Model answer

    Urgent is strict priority above the weighted classes; while any Urgent SQ is non-empty, weighted SQs are not fetched — without bound, and legally.

  2. Does arbitration order equal completion order?

    Model answer

    No. Arbitration orders fetches; execution is parallel and completes in any order.

  3. Why might a controller support more SQs than CQs?

    Model answer

    CQs carry interrupt state and are bounded by vectors; SQs are cheaper and useful for priority separation.

  4. How would you prove a queue is healthy after creation?

    Model answer

    First use: doorbell at the right offset, fetch at base + head × 64, CQE at the CQ base with the right SQID and P = 1, and its MSI-X write.

  5. What is the risk of putting SQs in a Controller Memory Buffer?

    Model answer

    SQE writes become posted writes to the device that must precede the doorbell; write-combining mappings can break that. It is optional, scarce, and removes SQE fetches from traces.

Senior

  1. Design a queue-management validation matrix.

    Model answer

    Limits (every QID, sizes 2 and MQES + 1); topologies (1:1, many:1, mixed IEN, shared vectors); arbitration (RR fairness, WRR weights, urgent starvation); lifecycle (delete with outstanding commands, wrong delete order, reset during creation, churn, suspend/resume with IOVA randomisation); every queue error status; first-use proof after every event.

  2. A customer's custom driver uses one SQ per thread (200 SQs) and one shared CQ. What do you review?

    Model answer

    The grant; CQ size versus the sum of outstanding limits (likely beyond MQES); the single reaping CPU as a bottleneck; demultiplexing by SQID; fairness across 200 SQs.

  3. How do you decide between interrupts and polling per queue?

    Model answer

    Polling saves interrupt delivery at the cost of spinning CPU; it pays at low depth with tight latency targets. Keep polled queues separate.

  4. A firmware engineer says "queue creation succeeded, so the host is to blame". How do you respond?

    Model answer

    Creation success proves only that fields passed validation. The create payload and first-use evidence decide.

  5. What queue-related state must survive, and what must not survive, a controller reset?

    Model answer

    No I/O queue context survives CC.EN = 0. The host recreates queues, re-zeroes CQs, resets pointers and phases, renegotiates, and reuses DMA addresses only if still mapped.

Quiz

  1. Two SQs, each 256 entries, share one CQ. Minimum CQ entries for no possible overflow?

    • 256
    • 510
    • 511
    • 512
    Answer and reasoning

    Each SQ can hold 255 outstanding: 510 CQEs; a CQ of N holds N − 1, so N ≥ 511.

  2. Under weighted round robin with urgent priority class, which is served first?

    • Admin SQ
    • Urgent SQs
    • High-class SQs
    • The SQ with the largest weight
    Answer and reasoning

    The Admin SQ is the highest strict priority, then Urgent, then weighted High/Medium/Low.

  3. Create I/O SQ CDW11 = 0x0001_0007. What is QPRIO?

    • Urgent
    • High
    • Medium
    • Low
    Answer and reasoning

    Bits 2:1 of 0x7 = 11b = Low. CQID = 1, PC = 1.

  4. A CQE written into CQ1 carries SQID 4. Which statement is certainly true?

    • The controller has a bug
    • Either SQ4 maps to CQ1 or host and controller disagree about the mapping
    • SQ4 does not exist
    • The host must discard it
    Answer and reasoning

    Many-to-one is legal; only the Create I/O SQ 4 payload can say which story is true.

  5. Which evidence clears the media in a "slow read" complaint?

    • The CQE status is 0
    • The MSI-X arrived
    • Fetch-to-CQE time is normal while doorbell-to-fetch is large
    • The data TLPs are 256 bytes
    Answer and reasoning

    If the excess latency is before the fetch, the command was waiting for arbitration, not for NAND.

  6. What happens when a controller's CQ is full and it has a completion to post?

    • It overwrites the oldest entry
    • It waits until the host frees slots with the CQ head doorbell
    • It posts to another CQ
    • It returns a PCIe error
    Answer and reasoning

    The controller never overwrites unconsumed entries; it stops posting into that CQ until the head moves.

  7. Why can an analyzer not show you a queue being "created"?

    Model answer

    Creation is an Admin command exchange; the queue itself is only an address range plus controller-internal context. The analyzer shows the create SQE inside a CplD payload and its Admin CQE; the queue's existence becomes visible only when its doorbells, fetches and CQE writes appear.

  8. Give two host events that can turn an undersized shared CQ from harmless to harmful.

    Model answer

    Longer interrupt coalescing; the reaping CPU busy or descheduled (virtual machine, real-time task, long interrupt-off section); debugger stops. Each lengthens the interval between CQ head doorbells.

Teach-back

  1. To a child: explain the airport: desks with their own belts, shared return carousels, the light in the office, urgent belts, and why you build a carousel before opening a desk.

    Model explanation

    "Each desk puts suitcases on its own belt so desks never bump into each other. Workers inside take suitcases from the belts one after another, but urgent belts first. When a suitcase is checked, a ticket comes back on a return carousel — several desks can share one carousel because each ticket says which desk it belongs to. A light flashes in an office when tickets arrive. You build the carousel first, because a desk with nowhere to send tickets would be stuck. And if the carousel is too small for all its desks, the workers have to stop and wait."

  2. To a junior engineer: explain topology design for a host with 16 CPUs, a grant of 8 SQs and 4 CQs, and 5 MSI-X vectors.

    Model explanation

    "We can create at most 8 SQs and 4 CQs. With 4 CQs and 4 I/O vectors (vector 0 is Admin), give each CQ its own vector targeting a group of 4 CPUs. Map 2 SQs to each CQ, one SQ per pair of CPUs, so each CQ is shared by 2 SQs — size each CQ at 2 × (SQ entries − 1) + 1 or more. CQEs carry SQID so the handler can route completions. Create every CQ before its SQs and wait for each completion. Prove each queue by its first use."

  3. To a senior engineer: argue which queue facts you can and cannot recover from a mid-stream capture, and what that implies for capture practice.

    Model explanation

    "From mid-stream I can infer address ranges, doorbell-to-queue mapping and, from CQE SQIDs, which SQs complete into which CQ ranges — but not QSIZE exactly, not QPRIO, not IEN for silent queues, and not whether an SQID-on-CQ pairing was intended. NVMe offers no read-back of queue contexts. So for any queue-topology question I capture from controller enable, or I correlate with the driver's own creation tracing; otherwise ambiguous traces like an unexpected SQID can only be reported with both hypotheses."
