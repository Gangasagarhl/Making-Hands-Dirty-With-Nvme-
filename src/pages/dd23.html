Chapter 58 taught what a namespace is: NSID, size, capacity, utilization, LBA formats, attachment and identifiers. This module follows a namespace through its whole life — create, attach, format, not-ready, detach, delete, reuse — and studies the places where the host's picture and the device's picture of a namespace disagree, because that is where namespace bugs live.

Orientation

A namespace in Non-Volatile Memory Express (NVMe) is stored state in the subsystem, but every host keeps its own cached copy of it: the list of active NSIDs, each one's block size and capacity, its identifiers, and a block device built on top. Almost every namespace failure is a disagreement between those two copies at some moment: the device changed the format but the host still uses the old block size; the device deleted and reused an NSID but the host still believes it is the old namespace; the device is not ready yet but the host gives up. This module teaches the life cycle precisely enough to predict each disagreement, and shows the trace and log evidence for each.

  • Namespaces — NSID value space, allocated/active/inactive, NSZE/NCAP/NUSE, FLBAS and LBA formats, Namespace Management (0Dh) and Attachment (15h), identifiers, ANA. Not repeated here.
  • NVMe Controller — controller vs namespace and scope triage.
  • NVMe Subsystem — namespaces as subsystem objects reached through several controllers.
  • NVMe Command Structure — CQE status field layout (SC, SCT, CRD, M, DNR).

Where it goes next: NVM Command Set (how Read/Write use the format), Dataset Management (deallocation and NUSE), ZNS and Key Value (namespaces of other command sets), NVMe Errors.

Kid story

Picture a hotel. Rooms are numbered 1 to 32, but only some numbers have a room built behind the door. The manager can build a room (it exists, but no reception desk has a key yet), give a key to one or more reception desks, take a key back, or knock a room down. When a room is knocked down, its number goes back on the list, and the next room built may get the same number.

Each room also has a brass plaque with a long serial code that is never reused. If you come back to "room 5" after a while, the smart guest checks the plaque, not just the number on the door. Sometimes a room is renovated: the shelves are rebuilt to a new size and everything inside is thrown away. While it is being renovated, an "Not ready — try again in half an hour" sign hangs on the door.

Rooms are namespaces; numbers are NSIDs; building and knocking down are Namespace Management create and delete; keys are attachments to controllers; the plaque is the NGUID, EUI-64 or UUID; renovation is Format NVM; the sign is the Namespace Not Ready status with a Command Retry Delay.

Analogy boundary

  • Represents. Numbers that can be reused, identities that cannot, keys per desk, destructive renovation, and "try later" signs.
  • Hides. Every guest keeps a private notebook of which rooms exist and what size their shelves are — the host's cached namespace list and block device. The hotel tells guests about changes only by leaving a note at their desk (an asynchronous event), and only if the guest left an empty envelope there in advance (an outstanding Asynchronous Event Request).
  • Misleads. A hotel room has a physical location. A namespace has none: its blocks are spread across all the flash by the flash translation layer (FTL), and "knocking it down" usually means discarding mapping tables or encryption keys, not moving anything. Also, renovation (format) can, depending on the device, apply to every room at once.

The I/O hot path for an NSID

For each I/O SQE, the controller checks the NSID against the controller's active set (inactive or invalid: Invalid Namespace or Format, 0Bh, typically with DNR = 1), checks readiness (Namespace Not Ready, 82h, or Format In Progress, 84h Uncertain on which is returned when), converts SLBA and NLB using the format's LBADS, checks SLBA + NLB + 1 against NSZE (LBA Out of Range, 80h), checks capacity for writes to unallocated blocks on thin namespaces (Capacity Exceeded, 81h), checks reservations (Reservation Conflict, 83h), and only then reaches the FTL. Every one of these checks uses device state; every one can fail because the host used stale state.

Command Retry Delay

The 15-bit status field in CQE Dword 3 (bits 31:17) holds, from the bottom: Status Code (8 bits, DW3 24:17), Status Code Type (3 bits, 27:25), Command Retry Delay (2 bits, 29:28), More (bit 30) and Do Not Retry (bit 31). CRD = 0 means retry at will; CRD = 1, 2 or 3 asks the host to wait CRDT1, CRDT2 or CRDT3 from Identify Controller, each in units of 100 ms. A namespace that is not ready after power-on is the classic user. The host must enable this behaviour (Advanced Command Retry Enable in the Host Behavior Support feature) Uncertain — confirm the feature identifier and field in Base 2.4; otherwise CRD is reported as 0.

NSID reuse and identity

NSIDs are numbers, not names. Delete NSID 5, create a new namespace, and the device may return NSID 5 again. A host that missed the change (for example because no Asynchronous Event Request was outstanding during a reset) still holds a cached "NSID 5" with the old identifiers and may issue I/O that lands in a different tenant's namespace. The defence is identity revalidation: compare NGUID, EUI-64 or UUID whenever the namespace list may have changed. Linux revalidates identifiers on rescan and removes a namespace whose identifiers changed Implementation-dependent (kernel behaviour; version-dependent details).

The ladder for the central concept: namespace life cycle and cache coherence

Hotel rooms that are built, keyed, renovated, unkeyed and knocked down, with guests who keep their own notebooks.

A namespace moves through allocated, active, formatting/not-ready, inactive and deleted; hosts cache its NSID, format and identifiers and must refresh the cache after every change.

Device: persistent namespace table and attachment matrix, a per-controller hot-path cache, per-namespace FTL tables; host: kernel namespace list and block devices.

Base 2.4 defines management, attachment, notices, the Changed Namespace List, CRD and Commands Supported and Effects; NVM Command Set 1.3 defines format fields and statuses such as LBA Out of Range and Namespace Not Ready.

Admin commands with data in the right direction, completion Dword 0 carrying new NSIDs, AER completions carrying notices, and I/O CQEs whose status reveals stale host state.

In a capture: opcode 0Dh/15h/80h SQEs, long gaps for format, AER completions on every affected controller, then Identify refreshes; failures show as error CQEs with no data phase.

For every namespace error, ask which copy of state was stale, when it last changed on the device, and whether the host was told.

The sixteen questions for the namespace life cycle

1. What is it?
The sequence of states a namespace passes through from creation to deletion, and the host's mirror of it.
2. Why was it created?
To let hosts carve, reshape and reassign storage at run time without hardware changes.
3. What problem does it solve?
Multi-tenancy, reprovisioning and format changes on a single device.
4. What existed before?
Fixed logical units configured by array tools; host partitioning only.
5. Why is it better?
The device enforces boundaries, formats and access; hosts are notified of changes.
6. Who creates the transitions?
Management software via admin commands; the device for readiness changes.
7. Who consumes them?
Every host attached to the namespace.
8. Where does the state live?
Persistently in the device; cached in hosts and in the controller's hot path.
9. What memory/registers are involved?
No registers; Identify structures, create structures, controller lists, log pages 04h and 05h.
10. What happens before?
Capacity must be available (UNVMCAP); controllers must exist; Asynchronous Event Requests should be outstanding.
11. What happens after?
Hosts refresh caches and rebuild block devices.
12. What happens if it is wrong?
Wrong block size, I/O to the wrong namespace, data loss through format scope, retry storms.
13. What does the analyzer show?
Admin commands and their data, notices, and I/O statuses — never "a namespace" as such.
14. What does Linux show?
Block devices appearing, resizing or disappearing; uevents; nvme list-ns; kernel messages about identifier changes.
15. What would a validation engineer test?
Every transition with I/O in flight, through every controller, with and without outstanding event requests, across resets.
16. What would a senior engineer suspect?
A stale cache: which copy, and why it was not refreshed.

The "three copies" model, the stale-cache classification of namespace failures and the NSID-reuse hazard are reasoning built on the definitions; the specification does not use those words.

  • The specification does not require a device to avoid reusing a deleted NSID, nor to delay reuse.
  • It does not say how long a format or a not-ready period may last, beyond what CRDT values and timeouts imply.
  • It does not require NUSE to change at any particular time after deallocation.
  • Check in the specification: the exact Format NVM field positions above bit 8 (SES, upper LBAF bits); the FNA rules for which NSID values are accepted; whether Format In Progress or Namespace Not Ready applies during a format; the Host Behavior Support feature identifier and its retry-enable field.

Never cache a namespace's block size across a format, never treat an NSID as an identity across delete/create, never read the Changed Namespace List from a tool without retaining the event if a driver depends on it, and never format a multi-namespace device without reading FNA.

Hardware view

Hardware participation
CategoryHardware and firmware
Must participateController front end (NSID check on every SQE), firmware namespace table, persistent metadata store, FTL, media
May participatePer-namespace encryption keys in a security engine (cryptographic erase rotates the key instead of erasing NAND); hardware LBA-range checkers; protection-information engines per namespace format
ObservableAdmin commands and data structures; notices; I/O statuses; time gaps during format
Internal, unobservableHow a namespace's blocks map to dies; when NUSE accounting runs; whether format erases NAND, discards maps or rotates keys; hot-path cache refresh

The time a format takes is a fingerprint of the method: seconds for a map discard or key rotation, minutes to hours for a user-data erase that physically erases blocks. If a "secure erase" format completes in under a second, it almost certainly used a cryptographic erase — which is legitimate only if the device supports it (FNA bit 2) and the key handling is trustworthy.

Real controllers keep a small per-controller structure indexed by NSID so that the active/format/range check costs nanoseconds. Firmware must update it atomically with the persistent table on attach, detach, format and delete. A window where the two disagree is how "I/O succeeded briefly after detach" bugs occur; validation should hammer I/O while attachment changes.

Ordering: the device orders nothing between a management command on one controller and I/O on another. The only ordering a host can rely on is its own: wait for the management completion, then for the notice or a re-read of Identify, before using the changed namespace. Errors stay in their layer: namespace problems surface as NVMe statuses, never as PCIe errors — unless the host's stale state makes the data pointer wrong, as in the failed trace below, where a PCIe Unsupported Request is a downstream consequence of a namespace mistake.

Analysis. Row 5 is the loudest event — a PCIe error, probably logged by the IOMMU and possibly by Advanced Error Reporting — but it is a consequence. The first abnormal event is the SQE in row 3: NLB = 7 means eight blocks; the tool computed it as 4096 / 512 − 1, and SLBA 0x4000 as 8 MiB / 512. Why it is ambiguous. The command was well-formed and succeeded. Three explanations fit: (a) the device does not track utilisation by deallocation — with thin provisioning unsupported, NUSE may simply equal NCAP or track only writes; (b) the device accepted the deallocation as a hint and has not acted on it yet (deallocation is advisory for many devices); (c) the device updates NUSE lazily in the background and 300 s is not long enough. The trace proves the host did its part. It cannot prove which device behaviour applies.

Disambiguating evidence. Check NSFEAT and the Deallocate Logical Block Features (DLFEAT) field: if DLFEAT says deallocated blocks read as zeros, read a few LBAs in the range — zeros confirm deallocation happened (so NUSE accounting is the issue, a or c); old data means the hint was not acted on (b). Repeat after an idle hour for (c). Confidence before checks: low.

Intermediate lab — Decode namespace statuses and retry policy

Objective

Decode CQE Dword 3 values into status, retry permission and retry delay, and connect each status to the stale state that typically causes it.

Prerequisites

The Command Retry Delay section; NVMe Command Structure.

Setup

#!/usr/bin/env python3
"""Decode CQE Dword 3 and explain namespace-related statuses.
Status names below are the ones this course treats as established; confirm
any value you rely on in the Base and NVM Command Set specifications."""

GENERIC = {0x00: "Successful Completion", 0x02: "Invalid Field in Command",
           0x04: "Data Transfer Error", 0x0B: "Invalid Namespace or Format",
           0x80: "LBA Out of Range", 0x81: "Capacity Exceeded",
           0x82: "Namespace Not Ready", 0x83: "Reservation Conflict"}
HINT = {0x0B: "host used an inactive/invalid NSID or a format it does not have: stale namespace list?",
        0x80: "SLBA+NLB beyond NSZE: wrong block size or stale size?",
        0x81: "thin pool exhausted: compare NUSE with NCAP",
        0x82: "wait (honour CRD) and retry; check CRIME / format in progress",
        0x83: "another host holds a reservation on this namespace"}

def decode_dw3(dw3, crdt=(0, 0, 0)):
    status = dw3 >> 17
    d = {"cid": dw3 & 0xFFFF, "phase": (dw3 >> 16) & 1,
         "sc": status & 0xFF, "sct": (status >> 8) & 0x7,
         "crd": (status >> 11) & 0x3, "more": (status >> 13) & 1, "dnr": (status >> 14) & 1}
    name = GENERIC.get(d["sc"], "see status tables") if d["sct"] == 0 else f"SCT {d['sct']} table"
    d["name"] = name
    d["retry_after_ms"] = None if d["dnr"] else (crdt[d["crd"] - 1] * 100 if d["crd"] else 0)
    d["hint"] = HINT.get(d["sc"], "") if d["sct"] == 0 else ""
    return d

if __name__ == "__main__":
    CRDT = (5, 20, 100)                     # synthetic Identify Controller CRDT1..3
    for dw3 in (0x0001_0042, 0x1105_0040, 0x0009_0150, 0x8017_0007,
                0x8101_0011, 0x0103_0022, 0x8107_0033):
        d = decode_dw3(dw3, CRDT)
        retry = "never (DNR)" if d["retry_after_ms"] is None else f"after {d['retry_after_ms']} ms"
        print(f"DW3=0x{dw3:08X} CID=0x{d['cid']:04X} P={d['phase']} SCT={d['sct']} SC=0x{d['sc']:02X} "
              f"CRD={d['crd']} DNR={d['dnr']} -> {d['name']}; retry {retry}"
              + (f"\n    hint: {d['hint']}" if d["hint"] else ""))

Procedure

  1. Run it. Expected: seven decoded lines — success; Namespace Not Ready with CRD 1 → retry after 500 ms; Data Transfer Error; Invalid Namespace or Format (DNR); LBA Out of Range (DNR); Capacity Exceeded (retry permitted); Reservation Conflict (DNR).
  2. Decode by hand first: 0x1105_0040 and 0x8101_0011.
  3. Construct the DW3 for "Namespace Not Ready, CRD 2, CID 0x0099" and check it with the program.

Observations

Note which statuses forbid retry and which ask for a delay.

Questions

  1. Why is Capacity Exceeded retryable while LBA Out of Range is not?
  2. What does a host do with CRD = 2 if it did not enable advanced command retry?
  3. Why can the More (M) bit matter for namespace errors?

Expected reasoning

DNR expresses whether the same command can ever succeed; CRD expresses when.

Solution

Hand decode: 0x1105_0040 → status 0x0882 → SC 82h, SCT 0, CRD 1, DNR 0, CID 0x0040. 0x8101_0011 → status 0x4080 → SC 80h, DNR 1, CID 0x0011. Constructed value: status = 0x82 | (2 << 11) = 0x1082; DW3 = (0x1082 << 17) | (1 << 16) | 0x0099 = 0x2105_0099.

(1) Capacity may be freed (deallocation elsewhere) so the same write can later succeed; an LBA beyond NSZE will never be valid. (2) A device should not report a non-zero CRD unless the host enabled it; if it does, treating CRD as 0 (immediate retry) is safe but may waste retries. (3) M = 1 says more information is in the Error Information log; for namespace errors it can name the LBA or parameter that failed.

Extension

Add Status Code Type 1h (command specific) decoding for Namespace Management and Attachment statuses after confirming values in the Base Specification.

Advanced lab — Model stale caches and NSID reuse

Objective

Show with a simulation how a missed notice or the absence of identity checks turns ordinary orchestration into wrong-unit I/O and cross-tenant writes.

Prerequisites

The NSID reuse section; Python 3.

Setup

#!/usr/bin/env python3
"""Namespace life cycle with a device table and a host cache.
Shows how missed notices and NSID reuse create stale host state.
Teaching simulation; identifiers and NSIDs are synthetic."""
import itertools

class Device:
    def __init__(self, nn=8):
        self.nn, self.table, self.serial = nn, {}, itertools.count(0xA000)
        self.pending_notice = set()          # NSIDs changed, for the host's controller

    def create(self, size, lbads):
        nsid = next(n for n in range(1, self.nn + 1) if n not in self.table)  # lowest free: reuse!
        self.table[nsid] = {"size": size, "lbads": lbads, "nguid": next(self.serial), "attached": False}
        return nsid

    def attach(self, nsid):  self.table[nsid]["attached"] = True;  self.pending_notice.add(nsid)
    def detach(self, nsid):  self.table[nsid]["attached"] = False; self.pending_notice.add(nsid)
    def delete(self, nsid):
        if self.table.pop(nsid)["attached"]:
            self.pending_notice.add(nsid)
    def format(self, nsid, lbads):
        ns = self.table[nsid]
        ns["size"] = ns["size"] * (1 << ns["lbads"]) // (1 << lbads)
        ns["lbads"] = lbads
        self.pending_notice.add(nsid)

    def io(self, nsid, nguid_expected, lbads_used):
        ns = self.table.get(nsid)
        if ns is None or not ns["attached"]:
            return "0Bh Invalid Namespace or Format"
        if ns["nguid"] != nguid_expected:
            return f"SUCCESS - but into namespace NGUID {ns['nguid']:#x}, not {nguid_expected:#x}!"
        if ns["lbads"] != lbads_used:
            return f"accepted with wrong units ({1 << lbads_used} B assumed, {1 << ns['lbads']} B real)"
        return "success"

class Host:
    def __init__(self, dev, aer_outstanding=True, check_ids=False):
        self.dev, self.aer, self.check_ids, self.cache = dev, aer_outstanding, check_ids, {}

    def rescan(self):
        new = {n: dict(v) for n, v in self.dev.table.items() if v["attached"]}
        if self.check_ids:
            for n, old in self.cache.items():
                if n in new and new[n]["nguid"] != old["nguid"]:
                    print(f"    host: NSID {n} identifiers changed -> drop old device, add new")
        self.cache = new

    def poll_events(self):
        if self.aer and self.dev.pending_notice:
            print(f"    host: notice for NSIDs {sorted(self.dev.pending_notice)} -> rescan")
            self.dev.pending_notice.clear()
            self.rescan()

    def open(self, nsid):                    # an application's handle
        return (nsid, self.cache[nsid]["nguid"])

    def write(self, handle):
        nsid, nguid = handle
        ns = self.cache.get(nsid)
        if ns is None or (self.check_ids and ns["nguid"] != nguid):
            return "host refuses: the namespace behind this handle is gone (EIO, no command sent)"
        return self.dev.io(nsid, nguid, ns["lbads"])

def run(aer, check_ids):
    print(f"--- AER outstanding={aer}, identity check={check_ids}")
    d = Device(); h = Host(d, aer, check_ids)
    a = d.create(1000, 9); d.attach(a); h.poll_events()
    if not aer: h.rescan()                   # initial scan at probe
    hx = h.open(a)                           # tenant X's application opens NSID a
    print("  write NSID", a, "->", h.write(hx))
    d.format(a, 12); h.poll_events()
    print("  after format ->", h.write(hx))
    d.detach(a); d.delete(a)                 # tenant X removed by orchestration
    b = d.create(500, 12); d.attach(b)        # tenant Y gets the lowest free NSID
    h.poll_events()
    print(f"  tenant Y got NSID {b}; tenant X's old handle writes ->", h.write(hx))

if __name__ == "__main__":
    run(aer=True, check_ids=True)
    run(aer=False, check_ids=False)

Procedure

  1. Run it. Expected: with notices and identity checks, the format is absorbed and the old handle is refused after reuse; without them, I/O after the format uses wrong units and the old handle writes successfully into tenant Y's namespace.
  2. Run with notices but without identity checks. What happens, and why?
  3. Change create to allocate the highest free NSID. Does reuse disappear? Does the hazard?

Observations

Record which defence prevents which failure.

Questions

  1. Which single host-side check prevents the cross-tenant write even when notices are missed?
  2. Why does the device happily accept the cross-tenant write?
  3. What orchestration rule removes most of the risk?

Expected reasoning

The device checks NSIDs, not intentions; only identifiers bind a handle to a namespace.

Solution

Step 2: notices refresh the cache, so the format is absorbed, but without identity checks the host silently re-binds the old handle to the new namespace at NSID 1 — the write lands in tenant Y's namespace. (1) Revalidating NGUID/EUI-64/UUID before using a cached NSID. (2) The NSID is active and attached; the device has no notion of which application or tenant sent the command. (3) Never reattach a reused NSID to a controller whose host held the old one without a confirmed rescan; or quarantine NSIDs for a period after delete; and key all orchestration on global identifiers. Step 3: allocating the highest free NSID delays reuse but does not prevent it once the space wraps.

Extension

Add a second controller and host; detach on one controller while the other host has I/O in flight, and model the device's per-controller active cache updating late.

Senior forensic lab — The tenant who saw someone else's data

Objective

Reconstruct how a virtual machine read another tenant's data on a multi-tenant host, assign root cause across layers, and propose controls.

Prerequisites

Everything above; NVMe Subsystem; Admin Queues (asynchronous events).

Setup — evidence (synthetic)

  • Orchestrator log: 10:00:00 detach + delete NSID 7 (tenant X, VM retired); 10:00:02 create → NSID 7 (tenant Y), attach to CNTLID 1; 10:00:03 tenant Y's VM starts and writes a file system.
  • Host kernel log: 09:58:40 controller reset after an I/O timeout; 09:58:42 controller live. No namespace rescan messages between 09:58:42 and 10:05.
  • Capture of admin traffic after 09:58:42: Identify, Set Features, Create I/O CQ/SQ… but no Asynchronous Event Request command (opcode 0Ch) is ever submitted.
  • 10:04: a forgotten backup agent on the host, still holding tenant X's old block device handle for NSID 7, reads it and uploads the content to tenant X's backup store. Tenant X later reports "strange files" in the backup.

Procedure

  1. Timeline everything.
  2. Identify the first abnormal event.
  3. Explain why the host never learned about the change.
  4. Assign contributing causes to driver, orchestration and agent; propose controls.

Observations

Look for absences in the admin traffic after the reset.

Questions

  1. What is the first abnormal event?
  2. Did the device misbehave?
  3. Which three controls would each have prevented the exposure?

Expected reasoning

Notices are only delivered into outstanding requests; reuse plus a stale cache equals wrong binding; identity checks are the last line of defence.

Solution

(1) The first abnormal event is an absence: after the 09:58:42 re-initialisation, the driver never re-armed Asynchronous Event Requests. Every later namespace change was therefore silent for this host. (2) No: the device reported changes the only way it can — by completing an outstanding Asynchronous Event Request — and there was none; it accepted reads to an active NSID. (3) Controls: (a) driver — re-arm AERs on every re-initialisation, and periodically rescan and revalidate identifiers; (b) orchestration — revoke host handles before deleting, and never reattach a just-deleted NSID to a controller whose host held the old one without confirming that host rescanned (what leaked was tenant Y's new data, so erasing the old namespace would not have helped); (c) host — the backup agent should bind to namespace identifiers (wwid), not device names, and fail closed if the identifier changes. Confidence: high on mechanism.

Extension

Write a validation test for the driver: reset the controller, change the namespace inventory from another controller, and assert the host notices within a bound.

Debugging

Pattern 1 — Wrong block size after a format

Symptom
After formatting, I/O fails with LBA Out of Range, Data Transfer Error or IOMMU faults; or a file system will not mount.
Possible causes
Application or tool cached the old logical block size; host missed the notice; kernel rescanned but a user-space driver (SPDK, passthrough) did not.
Evidence
SQE NLB/SLBA values versus LBADS; logical_block_size versus id-ns.
First check
Compare sysfs logical_block_size with the LBA format in use.
Second check
Decode one failing SQE: does NLB × block size equal the buffer size?
Disambiguating experiment
Restart the tool (forcing it to re-read the size) and repeat.
Likely conclusion
Stale host cache.
Confidence
High once the SQE arithmetic is shown.

Pattern 2 — Retry storm at power-on

Symptom
Boot logs show many I/O errors, then success; analyzer shows thousands of fetch/CQE pairs in the first second.
Possible causes
Namespace Not Ready returned while the host ignores CRD; CRIME enabled without host support for retry delays; slow media initialisation after an unsafe shutdown.
Evidence
CQE status 82h with CRD values; CRDT1–3; CC.CRIME.
First check
Decode the first error CQE: SC 82h? CRD non-zero?
Second check
Did the host enable advanced command retry, and does it wait?
Disambiguating experiment
Boot with CRIME disabled (wait for media-ready RDY) and compare the error count and boot time.
Likely conclusion
Host retry policy mismatch with an early-ready device.
Confidence
Medium-high.

Pattern 3 — NSID reused under a stale host

Symptom
Unexpected data, file system corruption or "wrong disk" symptoms after orchestration changes; no NVMe errors.
Possible causes
Delete/create reused an NSID; the host missed notices; no identity revalidation.
Evidence
NGUID/EUI-64/UUID before and after; orchestration timeline; presence of outstanding AERs.
First check
Compare the identifiers of the namespace now at that NSID with what the host recorded.
Second check
Was an Asynchronous Event Request outstanding when the change happened?
Disambiguating experiment
Replay delete/create in a lab with and without AERs outstanding.
Likely conclusion
Host cache and orchestration failure; the device behaved legally.
Confidence
High if identifiers differ.

Pattern 4 — A format wiped more than one namespace

Symptom
After formatting one namespace, data on others is gone.
Possible causes
FNA bit 0 (format applies to all namespaces) or bit 1 (secure erase applies to all) set; tool used NSID FFFFFFFFh; a sanitize was issued instead.
Evidence
FNA; the Format SQE's NSID and SES; admin history.
First check
Read FNA in Identify Controller.
Second check
Decode the Format SQE that was sent (tool logs or capture).

In a lab, format one namespace on the same model with two namespaces holding marker data.

High.

Symptom

Interview

Beginner

  1. What is the difference between an allocated and an active namespace?

    Model answer

    Allocated: exists in the subsystem. Active: allocated and attached to the controller you are asking; only then can it receive I/O through that controller.

  2. What does Format NVM do?

    Model answer

    Changes a namespace's LBA format, metadata and protection settings, optionally with secure erase, destroying its user data.

  3. How does a host learn that a namespace was attached?

    Model answer

    Through a Namespace Attribute Changed notice delivered by completing an outstanding Asynchronous Event Request, then reading the Changed Namespace List and Identify.

  4. Why is an NSID not a good long-term identifier?

    Model answer

    It can be reused after a delete. NGUID, EUI-64 and UUID are the stable identities.

  5. What does Namespace Not Ready mean?

    Model answer

    The namespace exists but cannot process I/O yet (for example during start-up); retry later, ideally after the delay CRD indicates.

Intermediate

  1. Decode DW3 = 0x8017_0007.

    Model answer

    CID 0x0007, phase 1, SC 0Bh (Invalid Namespace or Format), SCT 0, DNR 1.

  2. What is FNA and why read it?

    Model answer

    Format NVM Attributes in Identify Controller: whether format and secure erase apply to all namespaces, and whether cryptographic erase is supported. It decides the blast radius of a format.

  3. Why does the Commands Supported and Effects log matter for namespaces?

    Model answer

    It tells the host which opcodes change namespace content, capabilities or inventory, so the driver can quiesce and rescan around passthrough commands like Format.

  4. How is CRD turned into a delay?

    Model answer

    CRD 1–3 selects CRDT1–3 from Identify Controller, each in 100 ms units; the host must have enabled the behaviour.

  5. What changes for the host after formatting 512 B → 4 KiB?

    Model answer

    Logical block size, NSZE in blocks, every LBA's meaning, I/O size alignment; byte capacity may be unchanged. All caches must refresh.

Advanced

  1. In the failed trace, why is the PCIe Unsupported Request not the first abnormal event?

    Model answer

    It is the device faithfully following a bad command: the SQE with NLB and SLBA in the wrong units and a missing PRP list. The first abnormal event is that SQE.

  2. How can a namespace detach race with I/O on another controller?

    Model answer

    Attachment changes and I/O on different controllers are unordered; commands already fetched may complete, later ones fail with Invalid Namespace or Format; the device must update its per-controller active cache atomically. Hosts must quiesce before detaching.

  3. What is the risk of reading the Changed Namespace List from a monitoring tool?

    Model answer

    Reading it without Retain Asynchronous Event clears the list and re-arms the event, so the driver may never see which namespaces changed.

  4. How would you tell whether a secure-erase format was cryptographic?

    Model answer

    FNA bit 2 support, the SES value used, and the duration (seconds versus long erase times); confirm with the vendor's documentation.

  5. Why can NUSE stay unchanged after a successful deallocate?

    Model answer

    Deallocation may be advisory, applied lazily, or not reflected in NUSE when thin provisioning is not supported; check NSFEAT and DLFEAT and read back deallocated LBAs.

Senior

  1. Design safe namespace recycling for a multi-tenant platform.

    Model answer

    Revoke host handles; detach and confirm every host rescanned (or reset its controller association); erase (cryptographic where supported); delete; quarantine the NSID; create with new identifiers; attach only to the new tenant's controller; verify identifiers end to end; audit by identifier, not NSID.

  2. What would you validate about format on a new SSD?

    Model answer

    Each LBA format with and without metadata and protection; FNA scope; behaviour of I/O to the formatting namespace and to others; notices generated; duration; power loss during format; identifiers unchanged; Identify consistency afterwards.

  3. How should a driver behave after any controller reset with respect to namespaces?

    Model answer

    Re-arm Asynchronous Event Requests immediately, re-read the active list and identifiers, compare with its cache, and remove or update namespaces whose identity or format changed — because events during the reset window are lost.

  4. A cloud team wants CRIME on for faster boot. Your advice?

    Model answer

    Only if every host stack supports retry delays and treats Namespace Not Ready as transient; measure first-I/O latency, verify retry budgets, and test after unsafe shutdowns where media-ready can take much longer.

  5. Where do namespace bugs hide in a host stack?

    Model answer

    In every layer that caches namespace state: kernel namespace list, block device geometry, multipath identity, user-space drivers, file systems, backup and inventory agents — each must refresh or revalidate on change.

Quiz

  1. After delete and create, the device returns the same NSID. Which field tells the host it is a different namespace?

    • NSZE
    • FLBAS
    • NGUID / EUI-64 / UUID
    • NN
    Answer and reasoning

    Global identifiers are assigned at creation and differ for a new namespace.

  2. DW3 = 0x1105_0040. What should the host do (CRDT1 = 5)?

    • Fail the I/O permanently
    • Retry after 500 ms
    • Reset the controller
    • Reformat the namespace
    Answer and reasoning

    SC 82h Namespace Not Ready, CRD 1, DNR 0 → wait CRDT1 × 100 ms.

  3. Which Identify Controller field says a format may affect every namespace?

    • FNA
    • OACS
    • NMIC
    • CMIC
    Answer and reasoning

    FNA bit 0 (and bit 1 for secure erase).

  4. A Read on a 4 KiB namespace has NLB = 7. How much data does it transfer?

    • 3.5 KiB
    • 4 KiB
    • 28 KiB
    • 32 KiB
    Answer and reasoning

    NLB is 0's based: 8 blocks × 4 KiB.

  5. Why did the host in the forensic lab never learn about the new NSID 7?

    Model answer

    No Asynchronous Event Request was outstanding after the controller reset, so the notice could not be delivered, and the host did not rescan otherwise.

  6. Which log page lists the NSIDs that changed?

    • 02h
    • 04h
    • 05h
    • 0Ch
    Answer and reasoning

    Changed Namespace List, 04h. 05h is Commands Supported and Effects; 0Ch is ANA.

  7. What does Identify CNS 00h return for a valid but inactive NSID?

    Model answer

    A zero-filled data structure, not an error.

  8. Name the first abnormal event in the failed trace and explain why.

    Model answer

    The SQE with NLB 7 and SLBA 0x4000 on a 4 KiB namespace: it encodes 512-byte assumptions; the PRP list read from address 0 and the UR follow from it.

  9. Is Capacity Exceeded retryable?

    Model answer

    Typically yes (DNR = 0): freeing capacity can make the same write succeed. It is a provisioning problem, not a malformed command.

To a junior engineer

Model explanation

"A namespace is created (allocated), attached (active on a controller), maybe formatted (new block size, data gone, not ready meanwhile), detached and deleted — and its NSID can come back for a new namespace. The host caches NSIDs, block size and identifiers, and learns about changes only from notices delivered into outstanding Asynchronous Event Requests. After any change, re-read Identify; after any reset, re-arm events and rescan; always check identifiers, not just NSIDs. Decode status codes: 0Bh, 80h, 81h, 82h with CRD tell you which cached fact was wrong."

To a senior engineer

Model explanation

"Namespace failures are cache-coherence failures across three copies: the device table, the controller hot path and every host stack. The device is usually legal; the host or orchestration is stale. The dangerous cases produce no errors — NSID reuse with a stale handle, double binding — so defences must be identity-based and orchestration must sequence revoke, rescan, erase, delete, quarantine and recreate. Format scope (FNA), early-ready devices (CRIME with CRD) and advisory deallocation are the product-specific traps to validate."

Mastery gate

Do not consider this module mastered until you can:

  • explain the namespace life cycle and the three copies of namespace state;
  • diagram the life cycle with commands, notices and statuses on the transitions;
  • identify in traces a format with refresh, a not-ready retry sequence, a stale-block-size failure and an advisory deallocation;
  • debug the six failure patterns and decode CQE status including CRD and DNR by hand;
  • distinguish a namespace from neighbouring concepts: the controller (NVMe Controller), the subsystem (NVMe Subsystem), endurance groups and NVM Sets (Namespaces), zones (ZNS) and host partitions;
  • cite NVM Express Base Specification, Revision 2.4 (Namespace Management and Attachment, Asynchronous Events, Changed Namespace List, Commands Supported and Effects, Format NVM) and NVM Command Set Specification, Revision 1.3 (Identify Namespace, status values).
