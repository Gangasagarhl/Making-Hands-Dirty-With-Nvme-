Chapter 58 taught what a namespace is: NSID, size, capacity, utilization, LBA formats, attachment and identifiers. This module follows a namespace through its whole life — create, attach, format, not-ready, detach, delete, reuse — and studies the places where the host's picture and the device's picture of a namespace disagree, because that is where namespace bugs live.

Orientation

A namespace in Non-Volatile Memory Express (NVMe) is stored state in the subsystem, but every host keeps its own cached copy of it: the list of active NSIDs, each one's block size and capacity, its identifiers, and a block device built on top. Almost every namespace failure is a disagreement between those two copies at some moment: the device changed the format but the host still uses the old block size; the device deleted and reused an NSID but the host still believes it is the old namespace; the device is not ready yet but the host gives up. This module teaches the life cycle precisely enough to predict each disagreement, and shows the trace and log evidence for each.

  • Namespaces — NSID value space, allocated/active/inactive, NSZE/NCAP/NUSE, FLBAS and LBA formats, Namespace Management (0Dh) and Attachment (15h), identifiers, ANA. Not repeated here.
  • NVMe Controller — controller vs namespace and scope triage.
  • NVMe Subsystem — namespaces as subsystem objects reached through several controllers.
  • NVMe Command Structure — CQE status field layout (SC, SCT, CRD, M, DNR).

Where it goes next: NVM Command Set (how Read/Write use the format), Dataset Management (deallocation and NUSE), ZNS and Key Value (namespaces of other command sets), NVMe Errors.

Kid story

Picture a hotel. Rooms are numbered 1 to 32, but only some numbers have a room built behind the door. The manager can build a room (it exists, but no reception desk has a key yet), give a key to one or more reception desks, take a key back, or knock a room down. When a room is knocked down, its number goes back on the list, and the next room built may get the same number.

Each room also has a brass plaque with a long serial code that is never reused. If you come back to "room 5" after a while, the smart guest checks the plaque, not just the number on the door. Sometimes a room is renovated: the shelves are rebuilt to a new size and everything inside is thrown away. While it is being renovated, an "Not ready — try again in half an hour" sign hangs on the door.

Rooms are namespaces; numbers are NSIDs; building and knocking down are Namespace Management create and delete; keys are attachments to controllers; the plaque is the NGUID, EUI-64 or UUID; renovation is Format NVM; the sign is the Namespace Not Ready status with a Command Retry Delay.

Analogy boundary

  • Represents. Numbers that can be reused, identities that cannot, keys per desk, destructive renovation, and "try later" signs.
  • Hides. Every guest keeps a private notebook of which rooms exist and what size their shelves are — the host's cached namespace list and block device. The hotel tells guests about changes only by leaving a note at their desk (an asynchronous event), and only if the guest left an empty envelope there in advance (an outstanding Asynchronous Event Request).
  • Misleads. A hotel room has a physical location. A namespace has none: its blocks are spread across all the flash by the flash translation layer (FTL), and "knocking it down" usually means discarding mapping tables or encryption keys, not moving anything. Also, renovation (format) can, depending on the device, apply to every room at once.

The I/O hot path for an NSID

For each I/O SQE, the controller checks the NSID against the controller's active set (inactive or invalid: Invalid Namespace or Format, 0Bh, typically with DNR = 1), checks readiness (Namespace Not Ready, 82h, or Format In Progress, 84h Uncertain on which is returned when), converts SLBA and NLB using the format's LBADS, checks SLBA + NLB + 1 against NSZE (LBA Out of Range, 80h), checks capacity for writes to unallocated blocks on thin namespaces (Capacity Exceeded, 81h), checks reservations (Reservation Conflict, 83h), and only then reaches the FTL. Every one of these checks uses device state; every one can fail because the host used stale state.

Command Retry Delay

The 15-bit status field in CQE Dword 3 (bits 31:17) holds, from the bottom: Status Code (8 bits, DW3 24:17), Status Code Type (3 bits, 27:25), Command Retry Delay (2 bits, 29:28), More (bit 30) and Do Not Retry (bit 31). CRD = 0 means retry at will; CRD = 1, 2 or 3 asks the host to wait CRDT1, CRDT2 or CRDT3 from Identify Controller, each in units of 100 ms. A namespace that is not ready after power-on is the classic user. The host must enable this behaviour (Advanced Command Retry Enable in the Host Behavior Support feature) Uncertain — confirm the feature identifier and field in Base 2.4; otherwise CRD is reported as 0.

NSID reuse and identity

NSIDs are numbers, not names. Delete NSID 5, create a new namespace, and the device may return NSID 5 again. A host that missed the change (for example because no Asynchronous Event Request was outstanding during a reset) still holds a cached "NSID 5" with the old identifiers and may issue I/O that lands in a different tenant's namespace. The defence is identity revalidation: compare NGUID, EUI-64 or UUID whenever the namespace list may have changed. Linux revalidates identifiers on rescan and removes a namespace whose identifiers changed Implementation-dependent (kernel behaviour; version-dependent details).

The ladder for the central concept: namespace life cycle and cache coherence

Hotel rooms that are built, keyed, renovated, unkeyed and knocked down, with guests who keep their own notebooks.

A namespace moves through allocated, active, formatting/not-ready, inactive and deleted; hosts cache its NSID, format and identifiers and must refresh the cache after every change.

Device: persistent namespace table and attachment matrix, a per-controller hot-path cache, per-namespace FTL tables; host: kernel namespace list and block devices.

Base 2.4 defines management, attachment, notices, the Changed Namespace List, CRD and Commands Supported and Effects; NVM Command Set 1.3 defines format fields and statuses such as LBA Out of Range and Namespace Not Ready.

Admin commands with data in the right direction, completion Dword 0 carrying new NSIDs, AER completions carrying notices, and I/O CQEs whose status reveals stale host state.

In a capture: opcode 0Dh/15h/80h SQEs, long gaps for format, AER completions on every affected controller, then Identify refreshes; failures show as error CQEs with no data phase.

For every namespace error, ask which copy of state was stale, when it last changed on the device, and whether the host was told.

The sixteen questions for the namespace life cycle

1. What is it?
The sequence of states a namespace passes through from creation to deletion, and the host's mirror of it.
2. Why was it created?
To let hosts carve, reshape and reassign storage at run time without hardware changes.
3. What problem does it solve?
Multi-tenancy, reprovisioning and format changes on a single device.
4. What existed before?
Fixed logical units configured by array tools; host partitioning only.
5. Why is it better?
The device enforces boundaries, formats and access; hosts are notified of changes.
6. Who creates the transitions?
Management software via admin commands; the device for readiness changes.
7. Who consumes them?
Every host attached to the namespace.
8. Where does the state live?
Persistently in the device; cached in hosts and in the controller's hot path.
9. What memory/registers are involved?
No registers; Identify structures, create structures, controller lists, log pages 04h and 05h.
10. What happens before?
Capacity must be available (UNVMCAP); controllers must exist; Asynchronous Event Requests should be outstanding.
11. What happens after?
Hosts refresh caches and rebuild block devices.
12. What happens if it is wrong?
Wrong block size, I/O to the wrong namespace, data loss through format scope, retry storms.
13. What does the analyzer show?
Admin commands and their data, notices, and I/O statuses — never "a namespace" as such.
14. What does Linux show?
Block devices appearing, resizing or disappearing; uevents; nvme list-ns; kernel messages about identifier changes.
15. What would a validation engineer test?
Every transition with I/O in flight, through every controller, with and without outstanding event requests, across resets.
16. What would a senior engineer suspect?
A stale cache: which copy, and why it was not refreshed.
