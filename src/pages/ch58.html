A namespace is the thing the host actually reads and writes: a numbered, formatted, independently sized slice of the storage behind an NVMe controller. This chapter teaches you how namespaces are identified, sized, formatted, created, attached, shared and grouped, and how to see every one of those facts in Identify data, in a PCIe trace and in Linux.

Why this chapter exists

Up to now most examples in this course have quietly used "namespace 1" as if it were the drive. That shortcut is fine for learning READ and WRITE, but it hides an entire layer of the architecture. A modern NVM Express (NVMe) subsystem can hold many namespaces, of different sizes, block sizes and even different command sets; it can attach some of them to one controller and others to several; it can report that a namespace is reachable at full speed on one path and not at all on another; and it can group namespaces by wear budget and by latency isolation.

Every one of those facts changes what a correct command looks like. A WRITE that is perfect for a 512-byte-block namespace is wrong for a 4 KiB-block namespace. A READ to Namespace Identifier (NSID) 3 is valid on controller 0 and fails on controller 1 if namespace 3 is only attached to controller 0. A firmware engineer who gets the Identify data wrong will make Linux create a block device of the wrong size. A validation engineer who never tests detach-while-I/O will ship a race. This chapter is where the word "namespace" stops being a synonym for "disk" and becomes a precise engineering object.

It is also the doorway to the rest of Part XVIII. Zoned Namespaces (ZNS), Key Value, Computational Programs and Subsystem Local Memory are all, at bottom, kinds of namespace, selected by a Command Set Identifier. You cannot understand them until you understand the container they live in.

The story

Think about a huge school library building. The building is the subsystem. Inside it there are separate rooms: a picture-book room, a science room, a room of old newspapers. Each room has a number painted on the door: room 1, room 2, room 3. Those rooms are namespaces, and the door number is the NSID.

Each room decides how big its shelf slots are. The picture-book room has small slots that hold thin books; the newspaper room has big slots that hold heavy bundles. You must ask for things in the room's own slot size — you cannot ask the newspaper room for "half a slot".

The building has several help desks, one for each class. That is the controller. The head librarian decides which rooms each help desk is allowed to open: maybe desk A can open rooms 1 and 2, and desk B can open rooms 2 and 3. Room 2 is shared — both desks can open it. Room 1 is private to desk A. Building a new room, knocking one down, or giving a desk the key to a room are special jobs only the head librarian does, using special forms.

A self-storage facility. The facility (subsystem) has one perimeter fence, one manager's office and several gates (controllers). Inside, the manager carves out lockers (namespaces) of whatever size customers rent. Each locker has a unit number (NSID) unique within this facility, plus a serial number stamped by the manufacturer that is unique in the whole world (NGUID/EUI-64/UUID). A customer's gate card (attachment) lists which lockers it opens; a locker rented by a company may be opened from two gates (shared), one rented by an individual from just one (private). Some lockers are "rented at 10 m³" but the facility only has 2 m³ of boxes in them so far — the manager oversold, betting not every customer fills their space at once (thin provisioning). And lockers in the cheap wing share a single climate-control unit that wears out together (endurance group).

What it hides. A namespace is not a physical region of flash. The controller's flash translation layer spreads every namespace's data across all the dies it chooses; "locker 2" has no walls. Two namespaces can share the same NAND blocks over time. What is isolated is the address space and the format, not the silicon — unless the device uses NVM Sets or endurance groups to make a stronger promise.

Where it misleads. In the storage facility, the gate card is held by the customer. In NVMe the attachment is held by the subsystem and changed only by an admin command, usually from a privileged host. A host does not "log in" to a namespace; it either sees it in its controller's active namespace list or it does not. And the unit number is not globally unique: NSID 1 on drive A and NSID 1 on drive B are unrelated. That is exactly why the separate global identifiers exist.

Where it breaks completely. Thin provisioning in a storage facility ends with an angry customer; in NVMe it ends with a WRITE failing with a capacity status when the pool runs dry, which is a data-path failure the host must handle.

Beginner explanation

When you plug in an NVMe SSD, the operating system does not see "the SSD" as one block device. It first talks to the controller through the admin queue, asks it "how many namespaces can you have, and which ones are active for me?", and then creates one block device per active namespace. On Linux those are the familiar /dev/nvme0n1, /dev/nvme0n2 and so on.

Each namespace is a list of numbered blocks, starting at LBA 0. The namespace says how big each block is (commonly 512 bytes or 4096 bytes), how many blocks it has, and whether each block carries some extra metadata bytes. Every READ and WRITE command carries an NSID that says which namespace it targets, and an LBA range inside it.

Most consumer SSDs ship with a single namespace that covers the whole drive. Data-center and enterprise SSDs often support namespace management: an administrator can delete that namespace and create several smaller ones, each with its own block size, then attach them to particular controllers. That is how a single SSD is sliced between tenants, virtual machines or applications.

Three numbers describe a namespace's space:

  • Size (NSZE) — how many blocks the host can address: LBA 0 to NSZE−1.
  • Capacity (NCAP) — how many blocks may actually be allocated (hold data) at once.
  • Utilization (NUSE) — how many blocks are allocated right now.

For an ordinary "fully provisioned" namespace, size and capacity are equal. For a thin-provisioned namespace, the size can be larger than the capacity the device has really set aside, and utilization tells you how much is in use.

Finally, every namespace has a globally unique name — a 128-bit Namespace Globally Unique Identifier (NGUID), a 64-bit IEEE Extended Unique Identifier (EUI-64), a 128-bit Universally Unique Identifier (UUID), or several of them — so that a host which sees the same namespace through two different controllers can tell it is the same namespace.

Engineering explanation

The namespace as an object in the subsystem

The NVM Express Base Specification 2.4 — Theory of Operation (NVM subsystem entities) describes an NVM subsystem as containing one or more controllers, zero or more namespaces, and the non-volatile storage media behind them. A namespace is a quantity of non-volatile storage that may be formatted into logical blocks (for the NVM and ZNS command sets) or into other units (key-value pairs for KV, bytes of memory for SLM, programs for a compute namespace). It is the unit of:

  • addressing — every I/O command names it with an NSID;
  • formatting — block size and metadata are chosen per namespace;
  • command set — since NVMe 2.0, each namespace is associated with one I/O command set, identified by a Command Set Identifier (CSI);
  • access control — attachment, reservations and write protection apply per namespace;
  • path state — Asymmetric Namespace Access (ANA) reports reachability per group of namespaces per controller.

An NSID is unique only within one NVM subsystem. The same number on another subsystem means nothing. The Linux name nvme0n2 is a kernel instance number and is not guaranteed to equal NSID 2 — read /sys/block/nvme0n2/nsid when it matters.

Allocated, active, inactive

A namespace has two independent relationships that beginners blur together:

  • Allocated — the namespace exists in the subsystem (it was created and not deleted). Storage has been set aside for it according to its capacity.
  • Active (with respect to a controller) — the namespace is allocated and attached to that controller. Only active namespaces can be the target of I/O commands sent through that controller.

An allocated but unattached namespace is inactive on every controller: it holds data, but no controller will accept I/O to it. An NSID that is not allocated at all is unallocated. The Identify command has separate views for each population:

Private and shared namespaces

A private namespace may be attached to only one controller at a time. A shared namespace may be attached to two or more controllers simultaneously. The capability is reported per namespace in the Namespace Multi-path I/O and Namespace Sharing Capabilities (NMIC) field, bit 0 ("may be attached to two or more controllers"), and set at creation time in the Namespace Management host data. At the controller level, the Controller Multi-Path I/O and Namespace Sharing Capabilities (CMIC) field reports whether the subsystem may contain more than one port, more than one controller, whether the controller is associated with an SR-IOV virtual function, and whether ANA reporting is supported.

Sharing is what makes multipath possible: two controllers (perhaps on two PCI Express (PCIe) ports of a dual-port SSD, or two fabric controllers) present the same namespace, and the host multipath layer merges them into one block device. Sharing is also what makes reservations necessary, because two hosts can now write the same LBAs.

Size, capacity and utilization

These three fields sit at the very start of the NVM Command Set Identify Namespace data structure, each 8 bytes, little-endian, in units of logical blocks:

A block becomes "allocated" when written and may become unallocated after Dataset Management deallocate (Dataset Management), Write Zeroes with deallocate, or a Format/Sanitize — the exact accounting is Implementation-dependent within the rules the specification sets.

A related controller-level pair, Total NVM Capacity (TNVMCAP) and Unallocated NVM Capacity (UNVMCAP) in Identify Controller, reports bytes in the whole subsystem and bytes not yet given to any namespace. A per-namespace NVM Capacity (NVMCAP) field reports the bytes a namespace consumes. When you plan namespace creation, UNVMCAP is the number you have to work with.

Thin provisioning

Thin provisioning lets NSZE exceed NCAP — or, at the subsystem level, lets the sum of namespace sizes exceed the physical capacity — on the bet that not every namespace will be full at once. The Namespace Features (NSFEAT) field bit 0 ("THINP") reports that the namespace supports thin provisioning and that NCAP may be less than NSZE. If a host requests NCAP < NSZE in Namespace Management on a device that does not support it, the create fails with the command-specific status Thin Provisioning Not Supported.

Thin provisioning moves a failure from creation time to write time. When the pool is exhausted, a WRITE to a never-written LBA fails with the generic status Capacity Exceeded, even though the LBA is inside NSZE. A host that never tested that status will treat it as a device failure. Note that on many devices "NUSE" is only meaningful when the host deallocates (trims): without trim, every LBA ever written stays allocated.

LBA formats and FLBAS

A namespace that uses logical blocks offers a menu of formats. The Identify Namespace structure lists up to 64 LBA Format descriptors (LBAF0, LBAF1, …), and the Number of LBA Formats (NLBAF) field says how many are valid (it is a 0's based value: NLBAF = 1 means two formats). Each descriptor is one dword:

DW31…2625…2423…1615…0

  • LBADS — LBA Data Size: the block size as a power of two. LBADS = 9 → 512 bytes, LBADS = 12 → 4096 bytes. A value below 9 means the format is not supported.
  • RP — Relative Performance: 0 best, 1 better, 2 good, 3 degraded. A hint, not a guarantee.

The Formatted LBA Size (FLBAS) field selects which descriptor is in use. Its low bits 3:0 give the lower part of the index and, because 64 formats need 6 bits, bits 6:5 give the upper two bits. Bit 4 says whether metadata is transferred at the end of each data block in one buffer ("extended LBA") or in a separate metadata buffer pointed to by the Metadata Pointer. Namespace Management: create and delete

Namespace Management is admin opcode 0Dh. Support is reported in the Optional Admin Command Support (OACS) field of Identify Controller, bit 3 (Namespace Management and Attachment). The Select (SEL) field in Command Dword 10 bits 3:0 chooses the operation: 0h create, 1h delete.

  • Create. NSID in the command is reserved (zero). The host sends a 4 KiB data structure (host software specified fields) through the data pointer: NSZE, NCAP, FLBAS, Data Protection Settings (DPS), NMIC (private or shared), ANA Group Identifier, NVM Set Identifier, Endurance Group Identifier, and in newer revisions other fields. The CSI for the new namespace is given in Command Dword 11. On success, the controller returns the new NSID in Dword 0 of the completion. The new namespace is allocated but not attached to any controller.
  • Delete. The NSID field names the namespace; FFFFFFFFh deletes all namespaces. The namespace is detached from every controller and its storage is returned to the unallocated pool. Data is gone.

Failure statuses worth knowing by name (all command-specific, Status Code Type 1h): Namespace Insufficient Capacity (requested capacity exceeds UNVMCAP), Namespace Identifier Unavailable (no free NSID — MNAN or NN reached), Thin Provisioning Not Supported, and, if the ANA Group ID is bad, ANA Group Identifier Invalid. The libnvme library encodes them as 15h, 16h, 1Bh and 24h respectively; confirm against the status code table in the Base specification before relying on a value.

Namespace Attachment: attach and detach

Namespace Attachment is admin opcode 15h. The NSID field names the namespace; SEL in Command Dword 10 bits 3:0 is 0h attach or 1h detach. The data buffer is a Controller List: a 16-bit count of identifiers followed by up to 2047 16-bit Controller Identifiers (CNTLID). One command can attach or detach a namespace to or from several controllers.

When attachment changes, each affected controller reports it to its host with a Namespace Attribute Notices asynchronous event and records the NSID in the Changed Namespace List log page (log identifier 04h). The host reads that log and rescans. Linux does this automatically; a custom driver must implement it, or newly attached namespaces will simply never appear.

Typical failures (command-specific): Namespace Already Attached (18h in libnvme), Namespace Is Private (19h — trying to attach a private namespace to a second controller), Namespace Not Attached (1Ah — detaching from a controller it is not attached to), Controller List Invalid (1Ch — a CNTLID that does not exist or a malformed list), and ANA Attach Failed (25h).

Attachment is per controller, not per host and not per port. On an SR-IOV device each virtual function is its own controller with its own CNTLID; "attach namespace 3 to the VM" really means "attach it to secondary controller 5". Get the CNTLID from Identify (CNS 13h or the secondary controller list) on the subsystem you are actually talking to, never from a document about a different SKU.

The Base specification requires a controller to report at least one globally unique identifier for each namespace, and requires that identifier to remain unchanged across power cycles, resets and firmware activation for the life of the namespace; it is assigned at creation. A value of all zeros in NGUID or EUI-64 means "not reported". Linux builds the /dev/disk/by-id/nvme-eui.* links and the wwid sysfs attribute from these values, and the multipath layer uses them to decide that two paths reach one namespace. Two different namespaces reporting the same NGUID — a real firmware bug class, often after a manufacturing clone step — will make the host merge them into one multipath device and corrupt data.

The identifiers arrived over time: EUI-64 in the 1.1 era, NGUID with namespace management in the 1.2 era, the Namespace Identification Descriptor list and UUID in the 1.3 era, and the CSI descriptor with the 2.0 command-set split. Uncertain on the exact revision for each — confirm in the "Revision History" of the Base specification if it matters to you.

Command sets and namespace types

NVMe 2.0 split the monolithic specification into a Base specification, transport specifications and I/O command set specifications. A namespace is associated with exactly one I/O command set. The Command Set Identifier values defined so far (as encoded in the libnvme library, which follows the Base specification) are: 00h NVM, 01h Key Value, 02h Zoned Namespace, 03h Subsystem Local Memory, 04h Computational Programs. Confirm the list in the Base 2.4 "Command Set Identifier" definition.

Which command sets a controller may use is negotiated: CAP.CSS reports support, CC.CSS selects, and the I/O Command Set Profile feature chooses a combination. A host that only enables the NVM command set will see ZNS or KV namespaces either as inactive or as namespaces it cannot use, depending on configuration. The rest of Part XVIII treats each non-NVM type in turn: ZNS, KV, compute namespaces and memory namespaces.

Asymmetric Namespace Access (ANA) groups

When the same shared namespace is reachable through several controllers, those paths may not be equal. In a dual-controller storage array, the controller that "owns" a volume serves it quickly; the partner serves it through an internal link, or not at all during failover. Asymmetric Namespace Access (ANA) lets each controller report, per group of namespaces, the state of its path:

Each namespace carries an ANA Group Identifier (ANAGRPID, Identify Namespace bytes 95:92); all namespaces in a group share a state on a given controller. The host reads the ANA log page (log identifier 0Ch) after an ANA Change asynchronous event, and I/O failed for path reasons returns Status Code Type 3h (Path Related Status), for example Asymmetric Access Inaccessible or Asymmetric Access Transition. ANA matters little for a single-port PCIe SSD — it is almost always reported, if at all, as one optimized group — and enormously for NVMe over Fabrics (NVMe-oF) arrays. It is taught in full with fabrics in NVMe-oF Mental Model and Fabric Architecture.

Endurance groups and NVM Sets

Namespaces describe addressing. Two further groupings describe the media behind them:

  • An endurance group is a collection of media whose wear is managed together. Endurance (percentage used, data units written, available spare) is reported per group in the Endurance Group Information log page (log identifier 09h). On a simple SSD there is one implicit group; on a device that splits, for example, a high-endurance region from a dense region, each region is a group with its own wear budget. Identify Controller field ENDGIDMAX gives the highest group identifier, and the Identify Namespace ENDGID field says which group a namespace draws from.
  • An NVM Set is a subset of an endurance group's media that is isolated for performance: I/O to one set should not interfere with the latency of another. NVM Sets are the foundation of Predictable Latency Mode, which reports per-set deterministic and non-deterministic windows. Identify with CNS 04h returns the NVM Set List, and NVMSETID in Identify Namespace binds a namespace to a set.

The hierarchy is: NVM subsystem → (domains, in large multi-domain subsystems) → endurance groups → NVM Sets → namespaces. A namespace belongs to exactly one set when sets are supported. Support for both is reported in the Controller Attributes (CTRATT) field of Identify Controller. Since NVMe 2.0 the related Capacity Management command lets the host create and delete endurance groups and NVM Sets on devices that support it — see NVM Express Base Specification 2.4 — Capacity Management.

Version-dependent NVM Sets, endurance groups and ANA were introduced in the NVMe 1.4 generation; Capacity Management and domains in 2.0. Flexible Data Placement (FDP, ratified as a technical proposal in 2022 and folded into the Base specification in the 2.1 generation) adds reclaim units inside endurance groups — a different, more widely deployed way to steer placement, covered in the deep-dive Namespaces module.

Namespace write protection and other per-namespace attributes

The Namespace Write Protection Config feature can put a namespace into write-protected or write-protect-until-power-cycle states; writes then fail with Namespace is Write Protected. The Namespace Attributes (NSATTR) field reports it. Reservations (Reservation Register/Acquire/Release/Report) coordinate shared namespaces between hosts. Namespace Optimal I/O Boundary (NOIOB), the Namespace Preferred Write Granularity/Alignment (NPWG/NPWA) and atomic-write fields (NAWUN, NAWUPF) are per-namespace performance and atomicity hints Linux exposes in /sys/block/*/queue/. None of these change addressing, but all of them are namespace properties that a mis-configured device reports wrongly.

The central concept on the ladder

A namespace is a numbered room in the library building. Each room chooses its shelf-slot size. A help desk can open only the rooms the head librarian gave it keys to.

A namespace is an independently formatted logical address space of NSZE blocks, identified by a 32-bit NSID inside one NVM subsystem, attached to zero or more controllers. I/O commands carry the NSID and an LBA range within it.

Inside the controller, the NSID indexes a namespace table: format, size, FTL mapping root, protection settings, attachment bitmap per controller, ANA group, set and endurance group. Every I/O command's NSID is looked up there before any media access. The flash itself is shared; the mapping tables are per namespace.

The Base specification defines NSID semantics, allocated/active, Namespace Management (opcode 0Dh), Namespace Attachment (15h), identifiers, ANA, endurance groups and NVM Sets. The NVM Command Set specification defines NSZE/NCAP/NUSE, LBA formats and FLBAS for block namespaces. Other command set specifications define their own namespace contents.

On the wire: admin SQEs with opcode 06h/0Dh/15h, 4 KiB data structures moving by DMA (Identify data to host; create data and controller lists from host), a completion with the new NSID in Dword 0, then an asynchronous event and a Changed Namespace List read.

In a PCIe trace: an admin SQ tail doorbell MWr, a 64-byte MRd for the SQE, sixteen 256-byte MWr TLPs carrying an Identify page (MPS 256), or MRd/CplD pulling a create structure, then a 16-byte CQE MWr and an MSI-X MWr. Later, an unsolicited AER completion and a Get Log Page for log 04h.

Debugging: "the new namespace never appeared" splits into: create failed (check CQE status), create succeeded but attach not sent, attach sent to the wrong CNTLID, attach succeeded but no Namespace Attribute Notice, or the host ignored the notice. Each leaves a different trace signature.

The sixteen questions, answered for "namespace"

1. What is it?
A formatted, independently addressed quantity of storage in an NVM subsystem, identified by an NSID.
2. Why was it created?
To let one controller expose multiple independent logical devices with different formats and owners, without separate hardware.
3. What problem does it solve?
Partitioning and sharing of a device at the protocol level: tenants, formats, multipath, wear and latency isolation — things a host partition table cannot express to the device.
4. What existed before it?
SCSI Logical Units (LUNs) on SAS/Fibre Channel arrays; on SATA, one device was one address space and partitioning lived only in host software.
5. Why is the current design better?
The device knows the boundaries, so it can format, sanitize, protect, report capacity, report path state and isolate media per namespace; hosts get globally unique IDs for multipath.
6. Who creates it?
The controller, on a host's Namespace Management create (or at manufacturing for a fixed namespace).
7. Who consumes it?
Hosts, via I/O commands through attached controllers; the operating system turns each active namespace into a block or character device.
8. Where does it live?
Its metadata lives in controller firmware tables persisted in media; its data is spread across the media by the FTL.
9. What memory/registers are involved?
No controller registers; it is described by Identify data structures (Controller: NN, MNAN, OACS, CMIC, TNVMCAP/UNVMCAP; Namespace: NSZE, NCAP, NUSE, NSFEAT, NLBAF, FLBAS, NMIC, ANAGRPID, NVMSETID, ENDGID, NGUID, EUI64, LBAF) transferred to host memory by DMA.
10. What happens before it?
Controller enable, admin queue setup, Identify Controller, I/O command set selection.
11. What happens after it?
Attachment, host rescan, Identify Namespace, block device creation, I/O queue use with that NSID.
12. What happens if it is wrong?
Wrong size or block size in the host, Invalid Namespace or Format errors, merged multipath devices on duplicate IDs, capacity-exceeded write failures on oversubscribed thin pools.
13. What does the protocol analyzer show?
Admin command SQEs and their data payloads; the NSID in CDW1 of every I/O SQE; status fields in CQEs.
14. What does Linux show?
nvme list, nvme list-ns, nvme id-ns, nvme ns-descs, sysfs attributes nsid, size, wwid, logical_block_size.
15. What would a validation engineer test?
Create/delete to limits (NN, MNAN, UNVMCAP), every LBA format, attach/detach to every controller including during I/O, persistence of identifiers across power cycle and firmware update, AEN and log 04h behaviour, thin-pool exhaustion, inactive-NSID Identify returning zeros.
16. What would a senior engineer suspect when it fails?
Attachment and CNTLID confusion, stale host view (no rescan after AEN), identifier collisions, FLBAS index decoding bugs above 16 formats, NSID ≠ Linux instance assumptions, and race conditions between detach and in-flight I/O.

Hardware view

Nothing in the PCIe hardware knows about namespaces. There is no namespace register, no namespace BAR, no namespace function. The PCIe link carries Transaction Layer Packets (TLPs) whose payloads happen to contain NSIDs. Everything namespace-shaped lives in controller firmware and the media it manages.

On every I/O command, the controller front end decodes the SQE, takes the NSID from CDW1, checks it against the controller's active set, looks up the LBA format to convert NLB and SLBA into bytes, checks the range against NSZE, and only then hands the command to the FTL. That lookup is on the hot path, so real controllers keep a small per-controller array indexed by NSID. A firmware bug that updates the persistent table but not that cached array is how "the namespace was detached but I/O still worked for a few seconds" happens.

Formatting and namespace creation can be slow. A create on a fully provisioned namespace may need to reserve and erase blocks; Format NVM with a secure erase setting must touch all media. These commands can take seconds to minutes, which matters for host command timeouts (see NVMe Errors).

Dual-port U.2/E3 SSDs expose two PCIe ports, each with its own controller(s). A shared namespace is then reachable over two physical links to two different root ports, possibly in two different servers. The namespace is the shared object; the links, controllers, queues and interrupts are all separate.

  • NVM Command Set Specification, Revision 1.3 — the NVM-specific Identify Namespace data structure (NSZE, NCAP, NUSE, NSFEAT, NLBAF, FLBAS, LBA Format descriptors), protection information, and how LBAs and blocks are used by READ/WRITE. Normative

Both are current as of the August 2026 release. The explanatory text and the diagrams in the specifications are Informative; the "shall" statements and field definitions are normative.

These agree with the open-source libnvme definitions, which track the specification.

That NSID ≠ Linux instance number, that sharing implies reservations are needed for safety, that thin provisioning moves failures to write time, and that the per-NSID cache is a hot-path structure are reasoned from the specification and from how drivers and controllers are built — not quoted.

How many namespaces are supported, which LBA formats are offered, the namespace granularity, how long create/format take, whether thin provisioning or sharing is supported, how NUSE is computed, and whether a device ships with one namespace or none are all Implementation-dependent.

Namespace Management and Attachment date from the NVMe 1.2 generation; ANA, NVM Sets and endurance groups from 1.4; the CSI and the separate NVM Command Set document from 2.0; the "I/O Command Set Independent Identify Namespace" (CNS 08h) from 2.0. Field positions above 4 KiB-structure offset 384 and the newer host-specified create fields have grown in 2.x revisions. 2026 changes exist in Base 2.4 and NVM Command Set 1.3 — see 2026 NVMe 2.4 Updates.

Check in the specification before relying on:

  • the exact layout of the Namespace Management host-specified data structure in Base 2.4 (it gained fields in 2.x);
  • which commands accept NSID FFFFFFFFh and with what meaning;
  • status code values beyond the names given here (this page quotes the libnvme encodings and names; the specification's status code table is authoritative);
  • the rules for what a controller returns for an inactive or unallocated NSID with each CNS value;
  • namespace granularity reporting (Identify CNS 16h in libnvme) and how it rounds create sizes.

The specification does not say how a controller lays a namespace out on NAND, how fast create must be, or how NUSE accounting interacts with internal garbage collection.

Never assume that NSID 1 exists, that NSIDs are contiguous, that every namespace uses the same block size, that a namespace is private, that the NGUID is non-zero, or that nvme0nX means NSID X.

Protocol view

All namespace administration is admin-queue traffic. Every exchange has the same shape: host writes an SQE into the admin SQ, rings the admin SQ tail doorbell (a posted Memory Write), the controller fetches the SQE (non-posted Memory Read), moves the data structure by DMA in the direction the command requires, writes a CQE, and signals MSI-X vector 0.

Ordering. The specification does not order admin commands against each other beyond submission; a host must wait for the create completion (to learn the NSID) before attaching. Attachment and I/O on other controllers are not ordered with respect to each other; a detach on controller 0 while controller 1 has I/O in flight to the same shared namespace is a legitimate case the device must handle. A detach on the same controller with I/O in flight is resolved by the controller: in-flight commands may complete normally or be aborted; new commands with that NSID fail with Invalid Namespace or Format (generic status 0Bh).

Errors and their layer. Namespace administration errors are NVMe command-level statuses in the CQE. They never produce PCIe errors. If you see an Unsupported Request completion or an AER (PCIe Advanced Error Reporting) event during namespace work, the problem is in the transport, not the namespace logic — keep the two "AER" acronyms apart: NVMe Asynchronous Event Request versus PCIe Advanced Error Reporting.

How to find namespace work in a large capture: filter device-issued MRd/MWr to the admin SQ/CQ address ranges, decode CDW0 opcode of each fetched SQE, and look for 06h, 0Dh, 15h, 80h and 02h with LID 04h. Code / pseudocode

The first program builds a synthetic Identify Namespace buffer and a descriptor list for the lab's namespace 1, then decodes them exactly the way a driver does. It uses only the Python standard library.

#!/usr/bin/env python3
"""Decode an NVM Command Set Identify Namespace structure and a Namespace
Identification Descriptor list. The buffers are synthetic (course lab system)."""
import struct, uuid

def build_synthetic_idns():
    b = bytearray(4096)
    nsze = 0x7470_6DB0
    struct.pack_into("<QQQ", b, 0, nsze, nsze, 0x1F00_0000)  # NSZE, NCAP, NUSE
    b[24] = 0x01           # NSFEAT bit0: thin provisioning supported
    b[25] = 1              # NLBAF (0's based): two formats
    b[26] = 0x00           # FLBAS: format index 0, metadata in separate buffer
    b[30] = 0x00           # NMIC bit0 = 0: private namespace
    struct.pack_into("<I", b, 92, 1)          # ANAGRPID
    struct.pack_into("<HH", b, 100, 1, 1)     # NVMSETID, ENDGID
    b[104:120] = bytes.fromhex("acde4800c0ffee010000000000000001")  # NGUID
    b[120:128] = bytes.fromhex("acde4800c0ffee01")                  # EUI64
    # LBAF0: 512 B, no metadata, RP=2 ; LBAF1: 4096 B, no metadata, RP=0
    struct.pack_into("<I", b, 128, (2 << 24) | (9 << 16) | 0)
    struct.pack_into("<I", b, 132, (0 << 24) | (12 << 16) | 0)
    return bytes(b)

def decode_idns(b):
    nsze, ncap, nuse = struct.unpack_from("<QQQ", b, 0)
    nsfeat, nlbaf, flbas, nmic = b[24], b[25], b[26], b[30]
    idx = (flbas & 0x0F) | (((flbas >> 5) & 0x3) << 4)   # 6-bit index
    lbafs = []
    for i in range(nlbaf + 1):
        (d,) = struct.unpack_from("<I", b, 128 + 4 * i)
        lbafs.append({"ms": d & 0xFFFF, "lbads": (d >> 16) & 0xFF, "rp": (d >> 24) & 0x3})
    cur = lbafs[idx]
    if cur["lbads"] < 9:
        raise ValueError("selected LBA format is not supported (LBADS < 9)")
    bs = 1 << cur["lbads"]
    (anagrpid,) = struct.unpack_from("<I", b, 92)
    nvmsetid, endgid = struct.unpack_from("<HH", b, 100)
    print(f"NSZE={nsze:#x} ({nsze:,} blocks)  NCAP={ncap:#x}  NUSE={nuse:#x}")
    print(f"thin provisioning: {'yes' if nsfeat & 1 else 'no'}   shared: {'yes' if nmic & 1 else 'no (private)'}")
    print(f"LBA format in use: index {idx}, {bs} B data + {cur['ms']} B metadata, RP={cur['rp']}")
    print(f"extended LBA (metadata inline): {'yes' if flbas & 0x10 else 'no'}")
    print(f"size  = {nsze * bs:,} bytes   used = {nuse * bs:,} bytes ({100*nuse/nsze:.1f} %)")
    print(f"ANAGRPID={anagrpid} NVMSETID={nvmsetid} ENDGID={endgid}")
    print(f"NGUID={b[104:120].hex()}  EUI64={b[120:128].hex()}")
    for i, f in enumerate(lbafs):
        print(f"  LBAF{i}: ms={f['ms']} lbads={f['lbads']} ({1 << f['lbads']} B) rp={f['rp']}{'  <-- in use' if i == idx else ''}")

NIDT = {1: ("EUI64", 8), 2: ("NGUID", 16), 3: ("UUID", 16), 4: ("CSI", 1)}

def decode_descs(b):
    off = 0
    while off + 4 <= len(b):
        nidt, nidl = b[off], b[off + 1]
        if nidt == 0:                    # end of list
            break
        name, expect = NIDT.get(nidt, (f"unknown({nidt})", nidl))
        nid = b[off + 4: off + 4 + nidl]
        if nidl != expect:
            print(f"  WARNING: {name} length {nidl}, expected {expect}")
        val = str(uuid.UUID(bytes=bytes(nid))) if nidt == 3 else nid.hex()
        print(f"  {name}: {val}")
        off += 4 + nidl

if __name__ == "__main__":
    decode_idns(build_synthetic_idns())
    d = bytearray(4096)
    d[0:4] = bytes([2, 16, 0, 0]); d[4:20] = bytes.fromhex("acde4800c0ffee010000000000000001")
    d[20:24] = bytes([3, 16, 0, 0]); d[24:40] = uuid.UUID("6f1c2a5e-0d7b-4c39-9a51-3e2b8f40c001").bytes
    d[40:44] = bytes([4, 1, 0, 0]); d[44] = 0x00
    print("Descriptors:"); decode_descs(bytes(d))

Worked example

Problem. On the lab SSD (TNVMCAP = 1,000,204,886,016 bytes; one 512-byte-block namespace covering everything), the team wants: a 100 GiB 4 KiB-block namespace for a database, private to the host; a 400 GiB 4 KiB-block thin-provisioned namespace for a VM image store, actual capacity 200 GiB; and to keep the rest unallocated for later. The device supports thin provisioning and 4 KiB format (LBAF1). Synthetic example for teaching.

  1. Free the capacity. NSID 1 owns everything, so UNVMCAP = 0. Back up, then detach NSID 1 and delete it. UNVMCAP returns to 1,000,204,886,016 (implementation-dependent rounding aside).
  2. Database namespace. NSZE = NCAP = 100 GiB / 4096 = 107,374,182,400 / 4096 = 26,214,400 = 0x0190_0000 blocks. FLBAS = 0x01. NMIC = 0. Create → completion DW0 says NSID 1 (controllers often reuse the lowest free NSID; do not assume). Attach to CNTLID 0.
  3. Thin namespace. NSZE = 400 GiB / 4096 = 104,857,600 = 0x0640_0000 blocks; NCAP = 200 GiB / 4096 = 52,428,800 = 0x0320_0000 blocks. FLBAS = 0x01. Create → NSID 2. Attach.
  4. Remaining capacity. Consumed: 100 GiB + 200 GiB (NCAP, not NSZE) = 300 GiB = 322,122,547,200 bytes. UNVMCAP ≈ 1,000,204,886,016 − 322,122,547,200 = 678,082,338,816 bytes ≈ 631.5 GiB, subject to the device's namespace granularity.
  5. Host view. Linux shows two block devices: one of 26,214,400 × 8 = 209,715,200 sectors (512-byte sector units in sysfs) and one of 104,857,600 × 8 = 838,860,800 sectors, both with logical_block_size 4096.
  6. Risk. The VM store believes it has 400 GiB. When NUSE on NSID 2 reaches NCAP (52,428,800 blocks), further writes to unallocated LBAs fail with Capacity Exceeded. Monitoring must alarm on NUSE/NCAP, not on file system free space.

Check of units: Identify fields are in logical blocks of the namespace's own format; sysfs size is always in 512-byte units; UNVMCAP/TNVMCAP are in bytes. Mixing these three units is the most common arithmetic error in namespace planning.

Common mistakes

  • Treating nvme0n1 as NSID 1. Read the nsid sysfs attribute or nvme list.
  • Forgetting to attach. A created namespace is allocated but inactive everywhere. "I created it and it's not there" is nearly always this.
  • Attaching to the wrong CNTLID, especially on SR-IOV or dual-port devices where CNTLIDs are not 0 and 1.
  • Decoding FLBAS with only bits 3:0. Works until a device offers more than 16 formats; then the host picks the wrong block size.
  • Mixing units — blocks, 512-byte sectors and bytes — in capacity math.
  • Reading CNS 00h for an inactive NSID and trusting the zeros as "size 0 namespace".
  • Ignoring NCAP < NSZE and getting surprised by Capacity Exceeded under load.
  • Assuming detach flushes or quiesces I/O on the host. It does not; the host must quiesce.
  • Using NSID for identity across drives. Use NGUID/EUI-64/UUID, and validate they are non-zero and unique.
  • Formatting the wrong namespace by passing NSID FFFFFFFFh where the device applies format to all namespaces. Check the Format NVM Attributes (FNA) field in Identify Controller first.

Senior engineer insight

Junior engineers think of namespaces as partitions the drive knows about. Senior engineers think of them as a contract with five clauses: an address space (NSZE), a format (FLBAS/LBAF), an identity (NGUID/EUI-64/UUID), an access set (attachment, sharing, reservations, write protection) and a media binding (endurance group, NVM Set, ANA group). Every bug in this area is a clause being violated or two parties disagreeing about a clause.

Three habits follow. First, always read Identify fresh after any management operation — caches are where disagreements live. Second, when two hosts or two controllers are involved, draw the attachment matrix before reading a single trace. Third, test the boundaries the specification leaves to implementation: the last namespace (MNAN), the smallest create (granularity), the largest LBA format, detach under load, and power loss in the middle of create. Those are where firmware has the least test coverage and where field escalations come from.

For thin provisioning, the most senior advice is organisational: decide who owns the alarm on NUSE/NCAP before deploying it. The device will tell you the truth; nobody will be watching.

Lab

Lab 58 — Map the namespaces of an NVMe subsystem

Objective

Produce a complete, verified namespace map — allocated, active, attached controllers, formats, sizes, identifiers and groups — for one NVMe subsystem, and reconcile it with the kernel's view.

Skills

Reading Identify Controller and Identify Namespace; decoding FLBAS/LBAF; computing capacity in three units; validating identifiers; recognising allocated vs active.

Safety

Safe lab for Steps 1–3: read-only commands only. Step 4 (optional) is an Expert lab and must only be run in a QEMU virtual machine or on a scratch SSD whose data you are willing to lose: it creates, attaches, detaches and deletes namespaces.

Hardware required

Any Linux machine with an NVMe SSD, or a QEMU virtual machine with an emulated NVMe controller (preferred for Step 4).

Software required

nvme-cli, Python 3, and for Step 4 QEMU with its NVMe emulation (the nvme, nvme-ns and nvme-subsys devices; option names are version-dependent — check your QEMU's NVMe documentation).

Input

The device node /dev/nvme0 and its namespace block devices.

Expected output

A table with one row per allocated NSID: active here (y/n), attached CNTLIDs, NSZE/NCAP/NUSE, block size, metadata size, bytes, thin (y/n), shared (y/n), NGUID/EUI-64/UUID, ANAGRPID, NVMSETID, ENDGID, Linux block device name. Plus a statement reconciling UNVMCAP + Σ(namespace capacity) with TNVMCAP.

Background

This chapter's Engineering explanation and the code listing idns_decode.py. Consumer SSDs often do not support namespace management; then the allocated list may be unsupported and you will have a single namespace — that is a valid result.

Step 1 — controller facts

Run sudo nvme id-ctrl /dev/nvme0 -H and record NN, MNAN, OACS bit 3, CMIC, TNVMCAP, UNVMCAP, CNTLID, CTRATT (NVM Sets, endurance groups), ANACAP. Decide in advance which later commands will be unsupported.

Step 2 — namespace populations

Run sudo nvme list-ns /dev/nvme0 and sudo nvme list-ns /dev/nvme0 --all. For each allocated NSID, run sudo nvme list-ctrl /dev/nvme0 --namespace-id=N. Mark which are active here.

Step 3 — per-namespace detail

For each active NSID: sudo nvme id-ns /dev/nvme0 -n N -b > idns_N.bin, decode it with idns_decode.py's decode_idns, then run sudo nvme ns-descs /dev/nvme0 -n N. Compare with cat /sys/block/nvme0nX/{nsid,size,wwid} for the matching block device.

Step 4 (optional, expert) — create, attach, observe, delete

In a QEMU VM with an emulated NVMe subsystem that supports namespace management: record UNVMCAP; create a small namespace (nvme create-ns with explicit --nsze, --ncap, --flbas); note the NSID printed from completion Dword 0; confirm it appears in --all but not in the active list; attach it to your CNTLID (nvme attach-ns --controllers=); watch dmesg -w for the rescan; check the new block device; then detach and delete, and verify UNVMCAP returns to its original value.

Observation

Record any field that surprised you: NUSE equal to NSZE on a mostly empty drive (no deallocation tracking), an all-zero EUI-64, RP values, the Linux instance number not matching the NSID.

Questions

  1. Does UNVMCAP + Σ NVMCAP equal TNVMCAP on your device? If not, why might that be?
  2. Is any namespace shared? What does CMIC say about whether sharing is even possible?
  3. Which LBA formats are offered, and which has the best Relative Performance?
  4. In Step 4, how long did create take, and did the kernel react before or after you ran attach?

Challenge

Extend idns_decode.py to read every idns_N.bin and the descriptor lists, and print the map automatically, flagging: zero identifiers, duplicate identifiers across namespaces, NCAP < NSZE, and an LBAF with LBADS < 9.

Hints

Hint

nvme ns-descs -b writes the raw 4096-byte descriptor list; parse it with decode_descs. If --all fails with Invalid Field, the controller does not support the allocated-list CNS value — that tells you namespace management is unsupported.

Solution

Solution

A typical client SSD gives: NN = 1, MNAN = 0, OACS bit 3 = 0, one active NSID 1, --all unsupported, NSZE = NCAP, NUSE either equal to NSZE or tracking written data, EUI-64 and/or NGUID non-zero, one or two LBA formats (512 B and 4 KiB). UNVMCAP may be reported as 0 and TNVMCAP as 0 on devices without namespace management — the specification makes these fields meaningful only when namespace management is supported, so "does not reconcile" is the expected answer there.

A data-center SSD typically shows NN of 32–128 or more, OACS bit 3 = 1, CMIC with multi-controller set on dual-port parts, and a reconciliation where TNVMCAP − UNVMCAP equals the sum of namespace capacities rounded up to the device's namespace granularity.

In Step 4 the kernel only reacts after attach: creating a namespace generates no Namespace Attribute Notice for a controller to which it is not attached. Create is usually tens of milliseconds to a few seconds in QEMU; real devices vary widely.

What a senior engineer notices

Whether identifiers are consistent between the Identify Namespace fields and the descriptor list; whether NUSE moves after a trim (deallocation tracking); whether the attachment matrix matches what the orchestration system believes; and whether the namespace granularity rounding silently made a namespace larger than requested.

Failure variants

  • Attach to a non-existent CNTLID → Controller List Invalid.
  • Create larger than UNVMCAP → Namespace Insufficient Capacity.
  • Create with NCAP < NSZE on a non-thin device → Thin Provisioning Not Supported.
  • Delete while attached and in use → the block device disappears; in-flight I/O fails; check how your host reports it.

Extension

In QEMU, build a subsystem with two controllers and one shared namespace, enable native multipath, and observe nvme list-subsys showing two paths to one namespace. Then detach the namespace from one controller and watch the path count drop.

Exercises

  1. A namespace has NSZE = 0x0000_0000_0E8E_0DB6 and uses LBAF with LBADS = 12. Compute its size in bytes and in GiB.
  2. FLBAS = 0x31. Which LBA format index is in use, and is metadata transferred inline?
  3. Write the Controller List bytes (little-endian) to attach a namespace to CNTLIDs 0x0002 and 0x0007.
  4. Draw the attachment matrix for: NSID 1 private on ctrl 0; NSID 2 shared on ctrl 0 and 1; NSID 3 allocated, unattached. Which Identify CNS values on each controller list which NSIDs?
  5. Decode completion DW3 = 0x82350013, given that CID 0x0013 was a Namespace Attachment detach. Which status is it and what likely caused it?
  6. Explain in three sentences why thin provisioning makes Capacity Exceeded a data-path error that file systems must handle.
Answers

1. 0x0E8E_0DB6 = 244,190,646 blocks × 4096 = 1,000,204,886,016 bytes ≈ 931.5 GiB (the same 1 TB drive, formatted 4 KiB).

2. Bits 3:0 = 1, bit 4 = 1, bits 6:5 = 01b → index = 1 | (1 << 4) = 17; bit 4 set → metadata inline (extended LBA).

3. 02 00 02 00 07 00 followed by zeros to 4096 bytes: count = 2 (16-bit LE), then 0x0002, 0x0007.

4. Controller 0: active list (CNS 02h) = {1, 2}; controller 1: {2}; allocated list (CNS 10h) on either = {1, 2, 3}. CNS 12h for NSID 2 = {0, 1}; for NSID 3 = {}.

5. Bit 31 DNR = 1; bits 27:25 = 001b → SCT 1h (command specific); bits 24:17 = 0x1A; phase = 1; CID = 0x0013. If CID 0x0013 was a Namespace Attachment with SEL = detach, SC 1Ah is Namespace Not Attached (libnvme encoding): the host tried to detach a namespace from a controller it is not attached to — usually a stale attachment view or the wrong CNTLID in the list. Command-specific codes are meaningless until you know the opcode, so always find the SQE with the matching CID first.

6. The host was promised NSZE blocks, so the file system allocates freely within that space. The device can only back NCAP blocks (or the pool's real capacity), so a write to a new LBA may fail even though the LBA is in range. The failure appears on a write path, often long after deployment, and must be handled like a full disk rather than a media error.

Quiz

  1. Which NSID value means "all namespaces" for commands that allow it?

    • 0h
    • 1h
    • FFFFFFFFh
    • The value of NN
    Answer and reasoning

    FFFFFFFFh is the broadcast NSID. 0h means "no namespace" and is invalid for namespace-scoped commands; NN is the largest valid individual NSID.

  2. A namespace was created successfully but does not appear in the Active Namespace ID list of any controller. What state is it in?

    • Unallocated
    • Allocated and inactive
    • Active but hidden
    • Deleted
    Answer and reasoning

    Creation allocates; only attachment makes it active on a controller. It appears in the allocated list (CNS 10h) but not in any active list (CNS 02h).

  3. Which relationship always holds?

    • NUSE ≤ NCAP ≤ NSZE
    • NSZE ≤ NCAP ≤ NUSE
    • NCAP ≤ NUSE ≤ NSZE
    • NSZE = NCAP = NUSE
    Answer and reasoning

    Size bounds the address space; capacity bounds what can be allocated; utilization is what is allocated now.

  4. Where does the host learn the NSID of a namespace it has just created?

    • From the Identify Controller NN field
    • From a Namespace Attribute Notice
    • From the SQE it submitted
    • From Dword 0 of the Namespace Management completion
    Answer and reasoning

    The controller chooses the NSID and returns it in completion Dword 0. No notice is sent for a namespace that is not attached to the controller.

  5. LBAF2 = 0x020C0008. What are the block size, metadata size and relative performance?

    • 512 B, 8 B, best
    • 4096 B, 8 B, good
    • 4096 B, 12 B, good
    • 8 B, 4096 B, degraded
    Answer and reasoning

    MS = bits 15:0 = 0x0008 = 8 bytes; LBADS = bits 23:16 = 0x0C = 12 → 4096 bytes; RP = bits 25:24 = 2 = good.

  6. Which identifier is reported only through the Namespace Identification Descriptor list, not in a fixed Identify Namespace field?

    • EUI-64
    • NGUID
    • UUID
    • NSID
    Answer and reasoning

    NGUID and EUI-64 have fixed fields (bytes 119:104 and 127:120) and also appear in the descriptor list; the UUID appears only as a descriptor (NIDT 3h).

  7. An I/O fails with Status Code Type 3h. Which namespace concept should you investigate first?

    • ANA group state on that controller
    • LBA format
    • Thin-provisioning pool
    • Endurance group wear
    Answer and reasoning

    SCT 3h is Path Related Status; Asymmetric Access statuses live there. Read the ANA log page (0Ch) for that controller.

  8. Why does a validation plan include "Identify CNS 00h for an inactive NSID"?

    Model answer

    Because the specification requires a zero-filled structure rather than an error for an inactive but valid NSID, and host software commonly mishandles it. Testing confirms the firmware returns zeros (not stale data from a previously attached namespace, which would be an information leak) and that the host does not create a zero-size device.

  9. Explain the difference between an endurance group and an NVM Set in one sentence each.

    Model answer

    An endurance group is a pool of media whose wear is managed and reported together. An NVM Set is a performance-isolated subset of an endurance group's media, intended so that I/O to one set does not disturb latency in another.

  10. A detach on controller 0 completes successfully while controller 1 is mid-way through writes to the same shared namespace. What should happen to controller 1's I/O?

    Model answer

    Nothing: attachment is per controller. Controller 1 remains attached and its I/O continues normally. Only controller 0 loses access, and its host receives a Namespace Attribute Notice. If controller 1's I/O fails, that is a firmware bug — a good validation test.

Interview questions

  1. Beginner. What is a namespace, and how is it different from a partition?

    Model answer

    A namespace is an independently formatted logical address space defined and enforced by the NVMe controller, addressed by an NSID in every command. A partition is a host-side convention written in a partition table on a block device; the device does not know it exists. The device can format, sanitize, attach, share, protect and report capacity per namespace, but not per partition.

  2. Beginner. What do NSZE, NCAP and NUSE mean?

    Model answer

    Size: addressable blocks. Capacity: blocks that may be allocated at once. Utilization: blocks allocated now. NUSE ≤ NCAP ≤ NSZE; NCAP < NSZE means thin provisioning.

  3. Intermediate. Walk me through creating a namespace and making it usable in Linux.

    Model answer

    Check OACS bit 3 and UNVMCAP. Send Namespace Management (0Dh) SEL create with a host data structure giving NSZE, NCAP, FLBAS, NMIC and optionally group IDs, with the CSI. Read the new NSID from completion DW0. Send Namespace Attachment (15h) SEL attach with a controller list containing the controller's CNTLID. The controller raises a Namespace Attribute Notice; the host reads the Changed Namespace List (log 04h), issues Identify for the NSID and creates a block device. Verify with nvme list.

  4. Intermediate. How does a host know that two block devices are the same namespace?

    Model answer

    By the namespace's globally unique identifier — NGUID, EUI-64 or UUID — reported in Identify Namespace and the descriptor list, together with the subsystem NQN. NSIDs are only unique within a subsystem. Linux multipath groups paths by subsystem and namespace identifiers.

  5. Advanced. A customer says writes intermittently fail with Capacity Exceeded although df shows 40% free. Diagnose.

    Model answer

    The namespace is thin-provisioned (NSFEAT bit 0, NCAP < NSZE) or the subsystem pool is oversubscribed. The file system's free space is computed against NSZE, but the device can only back NCAP. Without trim, every block the file system ever wrote stays allocated, so NUSE reaches NCAP long before the file system is full. Evidence: id-ns NUSE vs NCAP, whether discard is enabled, pool UNVMCAP. Fix: enable discard/fstrim, raise NCAP, or stop oversubscribing.

  6. Advanced. Why is FLBAS decoding a classic bug?

    Model answer

    Originally the format index was bits 3:0 (16 formats). When 64 formats were allowed, bits 6:5 were added as the upper index bits, with bit 4 (metadata inline) between them. Code that masks only 0x0F silently picks the wrong LBAF once the device uses index 16 or higher, producing a wrong block size and data corruption.

  7. Senior. Design a validation matrix for namespace management on a dual-port SSD.

    Model answer

    Axes: operation (create, delete, attach, detach, format), sharing (private, shared), controller (port A, port B, both), LBA format (each offered), provisioning (full, thin), state (idle, under I/O from the same controller, under I/O from the other controller, during reset, across power loss), limits (NN, MNAN, UNVMCAP, granularity). Checks: completion status and DW0, Identify consistency on both controllers, identifier stability across power cycle and firmware activation, AEN and log 04h on exactly the affected controllers, no data from deleted namespaces leaking into new ones, reservations behaviour on shared namespaces.

  8. Senior. When would you use NVM Sets versus FDP versus separate namespaces to isolate tenants?

    Model answer

    Separate namespaces isolate address space, format and access but not media or latency. NVM Sets add media-level performance isolation with predictable-latency reporting, at the cost of fixed capacity partitioning and limited device support. FDP lets the host steer writes into reclaim units to reduce write amplification and interference while keeping one shared pool; it is more flexible and more widely deployed in hyperscale. The choice depends on whether the requirement is security/ownership (namespaces), latency guarantees (sets) or write-amplification and endurance (FDP).

Model explanation for the junior engineer

Creating a namespace is like building a room: storage is set aside and it gets a number, but no desk has a key yet. Attaching gives one or more controllers the key. Linux only talks through a controller, and the controller only lists namespaces it holds a key for, so until you attach, Linux is not even told the room exists. Attach, the controller rings the "something changed" bell (an asynchronous event), Linux reads which NSIDs changed, asks Identify about them, and creates the block device.

Chapter summary

A namespace is the formatted logical storage object that I/O addresses. It is identified locally by a 32-bit NSID and globally by NGUID, EUI-64 or UUID; it is sized by NSZE, NCAP and NUSE; it is formatted by an LBA Format chosen through FLBAS; it is created and deleted with Namespace Management (0Dh) and made usable on a controller with Namespace Attachment (15h); it is private or shared; and it belongs to an ANA group, an NVM Set and an endurance group. Since NVMe 2.0, each namespace also belongs to one I/O command set, which is why ZNS, KV, compute and memory namespaces can coexist with ordinary block namespaces. Namespace problems are almost always NVMe-level statuses or host-state races, rarely PCIe problems.
