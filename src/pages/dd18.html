Chapter 46 taught you to read an Advanced Error Reporting (AER) log; Chapter 55 taught you how a platform contains and recovers from what it reports. This module is about the gap between the two: who detects which error, what reaches the Root Port and what is lost on the way, how severity, masks and roles change the message, and how to build a causal story from registers that each hold only a fragment of it.

Orientation

AER is an optional PCI Express (PCIe) Extended Capability (ID 0001h) that gives each function status, mask and severity registers, a First Error Pointer and a Header Log, and gives Root Ports a collection point for error messages. It is a reporting system, not a recovery system: it tells software that something went wrong and leaves a few clues. Deep mastery means knowing exactly which clues exist, where, for how long, and which are missing.

You need Chapter 46 — PCIe AER (register map, bit names, severity, masks, Header Log decoding, Linux log format) and Chapter 55 — PCIe Advanced Error Handling (Downstream Port Containment, Access Control Services, firmware-first versus OS-first, Linux recovery callbacks). Completion rules come from Chapter 12; link-layer errors from Module 16 — DLLP and Replay.

Next: the NVMe side of the same failures is Module 39 — NVMe Errors; the broader PCIe error taxonomy is Module 40 — PCIe Errors; resets that follow fatal errors are Module 41 — Reset.

Kid story

In Grandma Rosa's apartment building, every flat has a little notebook by the door. When something goes wrong — a dripping tap, a broken window — the person who notices writes it in their own notebook, and for the first serious problem they also copy down exactly what they saw.

Then they send a coloured postcard down to the caretaker, Mr Okafor: green for "fixed it myself", yellow for "needs help but not urgent", red for "emergency". The postcard says only the flat number and the colour. Mr Okafor has a board showing which colours arrived and the flat number of the first green and the first red-or-yellow postcard. To learn what actually happened he must climb the stairs and read that flat's notebook.

Some flats have taped over certain lines of their notebook ("don't bother me about squeaky doors"). And if the stairway itself collapses, Mr Okafor can no longer go up to read anything.

Analogy boundary

What it represents. Flats are PCIe functions; notebooks are each function's AER status registers; the copied description is the Header Log; the postcards are ERR_COR, ERR_NONFATAL and ERR_FATAL messages; Mr Okafor's board is Root Error Status and Error Source Identification; taped lines are mask bits; climbing the stairs is software reading configuration space; the collapsed stairway is a link-down or contained port.

What it hides. Flats can also be told to treat an error as yellow or red (severity); a postcard can be suppressed by Device Control enables, not only masks; the caretaker's board keeps only the first sender of each kind plus a "more arrived" flag; and some errors are detected by the caretaker's own flat (the Root Port).

Where it misleads. It suggests the notebook-writer caused the problem. In PCIe the logging function is usually the detector: a Root Port logging Unsupported Request may be complaining about a request the SSD sent, and an SSD logging Poisoned TLP is reporting bad data the host sent it. It also suggests a postcard always goes out; in a firmware-first platform, firmware may read and clear the notebook before the OS sees anything.

Architecture

AER is distributed: every function that implements it detects and logs locally; only a one-line message travels upstream; the Root Port collects messages and interrupts software; software then walks the hierarchy reading each suspect's registers. Everything a function logs is in configuration space, so it is reachable only while the path to it works.

Mechanism

Follow one uncorrectable error: the Lab SSD receives a poisoned Completion with Data (CplD) for a read of write data.

  1. Detect. Who: SSD Transaction Layer, as the ultimate receiver (and requester). What changes: Uncorrectable Error Status bit 12 sets. Where: SSD AER at 04h. Evidence: on the wire, the CplD with the poisoned (EP) bit set.
  2. Decide logging. Who: SSD AER logic. What changes: if bit 12 is not masked and no other unmasked uncorrectable status is already pointed at, the First Error Pointer becomes 12 and the CplD header is copied into the Header Log. Where: 18h, 1Ch–28h. Evidence: readable later by configuration reads.
  3. Decide signalling. Who: SSD. What changes: severity bit 12 (default 0 = non-fatal) selects ERR_NONFATAL — unless the case is one the specification treats as Advisory Non-Fatal for this role, in which case it may set correctable bit 13 and signal ERR_COR instead (or nothing, since bit 13 is masked by default). Device Control enables (Non-Fatal Error Reporting Enable, bit 1) must permit the message. Device Status bit 1 sets regardless. Evidence: a Msg TLP or its absence.
  4. Act locally. Who: SSD firmware. What changes: the NVMe command that needed the data cannot complete successfully; the controller posts a Completion Queue Entry (CQE) with an error status. Evidence: the CQE MWr64 and its status field.
  5. Collect. Who: Root Port. What changes: Root Error Status records an ERR_FATAL/NONFATAL received (and "Non-Fatal Error Messages Received"); Error Source Identification bits 31:16 = 0x0100 if this is the first; an interrupt fires if Root Error Command enables it. Evidence: none on the link after the Msg.
  6. Read. Who: OS AER driver (or firmware). What changes: it reads Root Error Status, then the SSD's AER registers through configuration reads, prints the record, and clears RW1C status bits. Evidence: CfgRd0/CfgWr0 TLPs to the SSD; kernel log lines.
  7. Recover. Who: OS, driver. What changes: for non-fatal errors, the NVMe driver's error handlers may be invoked; for fatal ones, a link reset or DPC precedes recovery. Evidence: driver log lines; possibly a Secondary Bus Reset or DPC trigger.

Ownership: firmware-first or OS-first

At boot, the OS asks platform firmware through ACPI _OSC for control of AER (and DPC). If granted, the OS AER driver services the Root Port interrupt (OS-first). If not, firmware handles errors — often through a System Management Interrupt — reads and clears the registers, and reports a Common Platform Error Record to the OS through APEI/GHES (firmware-first). A third path, Error Disconnect Recover (EDR), lets firmware hand DPC events back to the OS. The same device fault therefore produces different kernel log lines on different platforms, and sometimes none. Implementation-dependent

The ladder

Every flat writes its own notebook and sends a coloured postcard; the caretaker must climb the stairs to read the details.

Each function logs which error it detected and the first offending header; it sends a one-line message to the Root Port, which interrupts software; software reads the details from the function.

Detection logic in each layer, sticky status registers, a header capture latch frozen by the First Error Pointer, message generation gated by masks, severity and Device Control enables, and a Root Port collector with an interrupt.

PCI Express Base Specification: Error Signaling and Logging (classification, roles, Advisory Non-Fatal, message rules), AER Extended Capability registers, Root Complex Event Collector; ACPI for _OSC and APEI; DPC Extended Capability.

Msg TLPs ERR_COR 30h, ERR_NONFATAL 31h, ERR_FATAL 33h routed to the Root Complex; configuration reads and RW1C writes by software; often the offending TLP itself is in the capture.

An error message a few hundred nanoseconds to microseconds after an abnormal TLP or link event; a burst of configuration accesses afterwards; for poison, the EP bit; for timeouts, a missing completion.

Reading a kernel AER record: identify the detector and its role, find the first error, decode the header, correlate with NVMe status and platform logs, and ask what was lost.

Specification discipline

Applicable specifications. PCI Express Base Specification, Revision 6.x/7.0 — Error Signaling and Logging; PCI Express Base Specification — Advanced Error Reporting Extended Capability; PCI Express Base Specification — Downstream Port Containment Extended Capability; ACPI Specification — _OSC and APEI; on the NVMe side, NVM Express Base Specification, Revision 2.x — Status Code definitions.

Normative Three classes; three error messages routed to the Root Complex; the AER register map in Chapter 46; per-bit severity for uncorrectable errors; masks for both classes; First Error Pointer and Header Log semantics; RW1C clearing; Root Error Status and Error Source Identification at Root Ports and RCECs; Advisory Non-Fatal as a defined signalling path for certain role-dependent cases.

Informative The specification's error-flow figure is informative guidance on the decision chain. The role table, timelines and causal chains in this module are derived.

Optional / Implementation-dependent AER itself for Endpoints; which bits are implemented; ECRC generation and checking; Completion Timeout header logging; Multiple Header Recording and its depth; the TLP Prefix Log; Root Port interrupt vector choice; which platform owns AER; how quickly firmware clears records.

Version-dependent Newer revisions add uncorrectable bits beyond 22 (egress-blocked and prefix errors, as listed in Chapter 46), Flit Mode changes to how some link errors are detected and counted, and larger header logs for Flit Mode TLP headers. Uncertain Confirm the Flit Mode Header Log layout in your revision before decoding.

The specification does not say how software should prioritise or recover, what correctable error rate is acceptable, how long a platform may wait before reading logs, or which NVMe status code a controller must return for a poisoned completion. Data Transfer Error (04h) is the generic NVMe status commonly used; check your controller's documentation. Check in your revision: the exact Advisory Non-Fatal cases per role, sticky attributes per field, and whether a given error has a meaningful header.

Never conclude that the function which logged an error caused it, that an empty AER log means no errors (masks, firmware-first, cleared status), that the First Error Pointer shows the most recent error, or that a Header Log belongs to the current incident without checking that status was cleared after the previous one.

Labs

Lab 1 (beginner) — Map your own AER

Safe lab Read-only commands.

Objective. Record, for your NVMe SSD and its Root Port, which AER features exist and how they are configured. Prerequisites. Chapter 46. Setup. A Linux machine with an NVMe SSD; root for lspci -vvv.

Procedure. Run the Linux view commands. Fill a table: AER present (both functions)? Uncorrectable mask and severity values; correctable mask; DevCtl reporting enables; ECRC capable/enabled; who owns AER; current non-zero status bits.

Observations. Typical: correctable mask with bits 13–15 set (0xE000), Surprise Down and Data Link Protocol Error fatal by default, ECRC capable but disabled. Some platforms show "AER: firmware first".

Questions. Which errors from your SSD would reach the OS as messages? Which would be logged but silent?

Expected reasoning. An error is signalled only if unmasked, enabled in Device Control, and the platform's handler is the OS.

Solution

No single answer: compare against defaults in Chapter 46. Advisory Non-Fatal, Corrected Internal Error and Header Log Overflow are typically silent (masked); everything else unmasked by default would be signalled if DevCtl enables are set. Non-zero sticky status bits from earlier boots may be present and are history, not current events.

Extension. Repeat for a switch on another machine and compare its Root Port and downstream port settings.

Lab 2 (intermediate) — Predict the log and the message

Safe lab Paper exercise.

Objective. Apply masks, severity and enables. Prerequisites. Mechanism above. Setup. SSD with UE mask 0x0000_0000, UE severity 0x0006_2030 (Data Link Protocol Error, Surprise Down, Flow Control Protocol Error, Receiver Overflow, Malformed TLP fatal), CE mask 0x0000_E000, DevCtl bits 0–3 set.

Procedure. For each event, give status bits, FEP, header logged?, and message: (1) Malformed TLP received; (2) a correctable Bad DLLP; (3) Poisoned CplD, then a Completion Timeout before software clears anything; (4) same as 1 but with UE mask bit 18 set; (5) same as 2 but DevCtl bit 0 clear.

Questions. In (3), which header is in the log?

Expected reasoning. Masks suppress logging and messages; severity selects fatal or non-fatal; the FEP and header freeze on the first unmasked error.

Solution

(1) UE bit 18, FEP=18, header logged, ERR_FATAL. (2) CE bit 7, ERR_COR. (3) Bits 12 and 14 set; FEP=12; header is the poisoned CplD's; ERR_NONFATAL (whether a second message is sent for the timeout is implementation-specific in detail — expect at least one). (4) Status bit 18 may set but no FEP, header or message — the error is invisible to the OS. (5) CE bit 7 sets; no ERR_COR is sent. Check the severity value against your revision's defaults; it is chosen here to make bit 18 fatal.

Extension. Add Multiple Header Recording enabled with a depth of two, and predict (3) again.

Lab 3 (advanced) — Decode AER records with a script

Safe lab Pure computation.

Objective. Decode status, masks, the First Error Pointer and the Header Log, and match the header to the trace. Prerequisites. Traces 3 and 4. Setup. Python 3.

"""Decode AER status words and a 4-DW Header Log (teaching tool, synthetic inputs)."""
COR = {0: "RxErr", 6: "BadTLP", 7: "BadDLLP", 8: "Rollover", 12: "Timeout",
       13: "AdvNonFatal", 14: "CorrIntErr", 15: "HdrLogOverflow"}
UNC = {4: "DLP", 5: "SurpriseDown", 12: "PoisonedTLP", 13: "FCP",
       14: "CmpltTO", 15: "CmpltAbrt", 16: "UnxCmplt", 17: "RxOF",
       18: "MalfTLP", 19: "ECRC", 20: "UR", 21: "ACSViol", 22: "UncorrIntErr"}

def bits(value, names):
    return [names.get(b, "bit%d" % b) for b in range(32) if value >> b & 1]

def unmasked(status, mask):
    return status & ~mask & 0xFFFFFFFF

def header(dw):
    fmt, typ = dw[0] >> 29, (dw[0] >> 24) & 0x1F
    length = dw[0] & 0x3FF or 1024
    out = {"fmt": fmt, "type": typ, "len_dw": length,
           "TD": dw[0] >> 15 & 1, "EP": dw[0] >> 14 & 1}
    if typ in (0x00, 0x01):                      # memory request
        out["kind"] = ("MWr" if fmt & 2 else "MRd") + ("64" if fmt & 1 else "32")
        out["req_id"] = "%04X" % (dw[1] >> 16)
        out["tag"] = "%02X" % (dw[1] >> 8 & 0xFF)
        addr = (dw[2] << 32 | dw[3]) if fmt & 1 else dw[2]
        out["addr"] = hex(addr & ~3)
    elif typ == 0x0A:                            # completion
        out["kind"] = "CplD" if fmt & 2 else "Cpl"
        out["cpl_id"] = "%04X" % (dw[1] >> 16)
        out["status"] = dw[1] >> 13 & 7
        out["req_id"] = "%04X" % (dw[2] >> 16)
        out["tag"] = "%02X" % (dw[2] >> 8 & 0xFF)
    return out

def report(name, unc, umask, cor, cmask, cap_ctl, hdr):
    print("==", name)
    print(" uncorrectable:", bits(unc, UNC), "unmasked:", bits(unmasked(unc, umask), UNC))
    print(" correctable:  ", bits(cor, COR), "unmasked:", bits(unmasked(cor, cmask), COR))
    fep = cap_ctl & 0x1F
    print(" first error pointer:", fep, UNC.get(fep, "?"))
    print(" header:", header(hdr))

if __name__ == "__main__":
    report("Root Port, ch46 UR example", 0x0010_0000, 0, 0, 0xE000, 20,
           [0x20000020, 0x010032FF, 0x00000001, 0x50000000])
    report("SSD, poisoned CplD (Trace 3)", 0x0000_1000, 0, 0, 0xE000, 12,
           [0x4A004010, 0x00090040, 0x01002100, 0x00000000])
    report("SSD, timeout then late completion (Trace 4)", 0x0001_4000, 0, 0, 0xE000, 14,
           [0x20000080, 0x01002AFF, 0x00000002, 0x00003000])

Procedure. Run it. For each record, name the detector's role and the culprit candidate. Then add a record for the Malformed TLP header from Chapter 46 (60000080 010000ff 00000002 00000100) at the Root Port.

Observations. The UR header is an MRd64 from the SSD to 0x1_5000_0000 (the PRP list region); the poisoned header names completer 0x0009; the timeout header is the request, not a completion.

Questions. Why does the Malformed record name the SSD's TLP although the Root Port logged it? Why is a Completion Timeout header (if logged) a request header?

Expected reasoning. The detector logs the TLP it received or the request whose completion failed to arrive.

Solution

The Malformed record decodes to MWr64, length 128 DW (512 bytes), requester 0x0100, address 0x2_0000_0100 — over MPS 256, so the SSD sent an illegal TLP and the Root Port detected it. A timeout has no received TLP, so a capable function logs the request that timed out.

Lab 4 (senior forensic) — "Random write failures on one server"

Safe lab Synthetic evidence.

Objective. Build a cross-log timeline and decide cause, consequence and coincidence. Prerequisites. This module; Module 39.

Setup (synthetic). Over a week: 11 NVMe WRITE failures with status 04h on 01:00.0; kernel AER records for 01:00.0 "Poisoned TLP" (4 of them) and "Completion Timeout" (7); EDAC reports 4 uncorrectable memory errors on DIMM B2, at the same seconds as the poisoned records; 312 correctable Receiver Errors from the Root Port, spread evenly; the 7 timeouts coincide with a nightly backup that drives the system's memory bandwidth to its limit.

Procedure. Write the timeline, assign each NVMe failure a cause, decide what the correctable errors mean, and propose actions.

Questions. Is the SSD faulty? Which evidence is a coincidence?

Solution

Poisoned (4): DIMM B2 uncorrectable errors poisoned write data; the SSD correctly refused it. Action: replace B2, retire pages. Timeouts (7): host memory latency under the backup exceeds the SSD's completion timeout range; action: check DevCtl2, raise the range via platform policy, and investigate memory/IOMMU latency. Correctables (312): evenly spread, not correlated with failures — a separate, low-priority link-quality question (Module 7). SSD: not faulty on this evidence. Confidence: high for the poison chain (time-aligned independent logs), medium for the timeouts (correlation with load but no direct latency measurement).

Extension. Design the monitoring rule that would have raised this in a fleet.

Interview

Beginner

  1. What are the three error classes?

    Model answer

    Correctable, uncorrectable non-fatal, uncorrectable fatal.

  2. What does ERR_COR carry?

    Model answer

    Only the sender's Requester ID; details stay in the sender's registers.

  3. How are AER status bits cleared?

    Model answer

    Write 1 to clear (RW1C).

  4. What does a mask do?

    Model answer

    Prevents header/pointer logging and signalling for that error; status may still set.

  5. Where does the Root Port record who sent an error?

    Model answer

    Error Source Identification at offset 34h.

Intermediate

  1. Linux reports a UR at the Root Port with a header from 0x0100. Who is at fault?

    Model answer

    Not necessarily anyone: the Root Port detected a request from the SSD it could not support; the address came from software. Decode and check mappings.

  2. Why can the Header Log describe an old error?

    Model answer

    It freezes until the status bit named by the FEP is cleared.

  3. What is Advisory Non-Fatal?

    Model answer

    A role-dependent path where a non-fatal error is signalled as correctable (bit 13), because another agent will handle it.

  4. What does severity change?

    Model answer

    Whether an uncorrectable error is signalled as fatal or non-fatal.

  5. Why might an NVMe error appear before the AER record?

    Model answer

    The CQE and its interrupt are serviced quickly; the AER handler reads registers later.

Advanced

  1. Explain the multiple-error loss problem.

    Model answer

    Root Ports keep one source per message kind plus "multiple" flags; functions keep one header unless Multiple Header Recording exists. Later errors are counted but not described.

  2. How does firmware-first change debugging?

    Model answer

    Firmware reads and clears registers; the OS receives records via APEI/GHES or nothing; you need firmware or BMC logs.

  3. What should an SSD do on a poisoned completion for write data?

    Model answer

    Report it and fail the command (for example Data Transfer Error), never commit the data.

  4. Why can a completion timeout produce an Unexpected Completion later?

    Model answer

    The requester retired the tag; a late completion matches nothing.

  5. How does DPC change what AER shows?

    Model answer

    The Downstream Port contains the error and takes the link down; the device's registers become unreachable until recovery, so the port's DPC and AER logs carry the evidence.

Senior

  1. Design an AER validation suite for an SSD.

    Model answer

    For each implemented bit: inject the cause with an exerciser, verify status, FEP, header, mask, severity, enables and message; sticky behaviour across resets; correct NVMe status; no data corruption.

  2. How do you decide whether correctable errors matter?

    Model answer

    By rate, trend and correlation with performance and with uncorrectables; a fleet baseline sets the threshold.

  3. What is your first action when a customer reports NVMe errors and "no AER"?

    Model answer

    Establish ownership and masks; obtain firmware/BMC logs; only then conclude there were no PCIe errors.

  4. A platform team wants to mask Completion Timeout to stop alarms. Response?

    Model answer

    Masking hides symptoms of real latency; fix the latency or set the range deliberately, and keep reporting.

  5. How do you correlate AER with NVMe events across clocks?

    Model answer

    Kernel timestamps for both, analyzer triggers on error Msgs, and anchor events (e.g. a CQE with error status) to align captures.

Teach-back

To a child: the notebooks, the postcards and why the caretaker must climb the stairs.

Model explanation

"Each flat writes what went wrong in its own notebook and sends a coloured card downstairs. The card only says which flat. To know what happened, the caretaker has to go up and read — and if the stairs are broken, he can't."

To a junior engineer: how to read an AER record without blaming the wrong device.

Model explanation

"The named device is who detected it. Look at the first error and decode the header: requester, tag, address. Ask who produced that TLP. Then look for matching logs elsewhere — memory errors, IOMMU faults, NVMe status."

To a senior engineer: why AER is evidence, not truth.

Model explanation

"It shows one header per function, one source per message kind, only unmasked errors and only what the owner chose to print. Treat each record as a witness statement from a detector, and build the case from several witnesses aligned in time."
