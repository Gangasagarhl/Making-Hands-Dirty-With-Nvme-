How to use a PCI Express (PCIe) protocol analyzer as an engineer rather than as a screen-reader: how it attaches to a link, how capture, triggers and filters decide what evidence exists, how its packet, transaction and NVM Express (NVMe) views are built, and the four-step workflow from a symptom to a root-cause hypothesis. Teledyne LeCroy's tools are the running example, described at the level of concepts; product menus and feature names are left to the vendor's documentation for your version.

Why this part exists

Every trace in this course so far was synthetic: tidy rows, chosen to teach. A real capture is millions of events from a probe on a physical link, shaped by settings someone chose, decoded by software with its own version and assumptions. Engineers who can read synthetic traces but cannot judge a real capture make two expensive mistakes: they trust evidence that was never complete, and they waste hours scrolling instead of navigating.

This part teaches the analyzer as an instrument: what it physically sees, what it chooses to keep, how it turns bits into rows, and how to drive it to the one region that matters. Teledyne LeCroy is used as the concrete example because its PCIe analyzers are widely used in NVMe and PCIe validation labs, and because the master plan for this course names it. Everything taught here transfers to other vendors' analyzers, because the underlying protocol is the same.

It does not reproduce menu names, button labels, file-format internals or feature names of any product. Those change between software releases, and inventing them would teach you things that are not true. Where a capability is mentioned, it is described generically ("a capture filter", "a split-transaction view"); look up what your analyzer calls it in the documentation for your hardware model and software version.

Learning objectives

  • Explain the four layers between a wire and a conclusion: raw event, protocol decoding, analyzer presentation, engineer interpretation.
  • Choose a probing method and explain how it can change the link it observes.
  • Configure capture depth, trigger position, triggers and filters for a stated question, and say what each setting makes impossible to see.
  • Use packet, link-transaction, split-transaction and NVMe-level views, and know what each hides.
  • Navigate from a symptom to a trace region, find the first abnormal event, reconstruct the transaction and state a falsifiable hypothesis.
  • List the limitations of any capture and record the metadata that lets someone else trust it.

Prerequisites

You need the PCIe layer model (PCIe Layer Model), the Link Training and Status State Machine (LTSSM) (PCIe LTSSM), TLPs and DLLPs (TLPs, DLLP), flow control (PCIe Flow Control) and the end-to-end NVMe READ (The Most Important Chapter). The Trace Analysis Laboratory is the companion practice page; Teledyne LeCroy Trace Analysis goes deeper.

Acronyms used throughout: Transaction Layer Packet (TLP), Data Link Layer Packet (DLLP), Submission Queue (SQ) and Submission Queue Entry (SQE), Completion Queue (CQ) and Completion Queue Entry (CQE), Message Signaled Interrupts eXtended (MSI-X), Advanced Error Reporting (AER), Device Under Test (DUT), Solid-State Drive (SSD), Base Address Register (BAR), Requester ID (RID).

The story

Imagine a very long, very busy road between a town and a warehouse. You want to know why some parcels arrive late. You cannot stand everywhere, so you put one camera at one spot on the road. The camera can only remember the last hour of pictures, so you tell it: "start keeping pictures when you see a red truck, and keep a few minutes from before." Later you watch the film. You see every vehicle that passed that spot, in order. You do not see what happened inside the warehouse, or on other roads, or anything that happened before the hour you kept.

A protocol analyzer is a flight data recorder fitted to one link of an aircraft's wiring. It records every message on that wire with a precise clock, can be told to preserve the minutes around an alarm, and comes with ground software that turns raw recordings into readable timelines. Accident investigators trust it, but they always ask where the recorder was fitted, what it was configured to record, and whether any channel dropped out.

A flight recorder is passive; an interposer is not entirely passive: it is part of the electrical channel and can change the link it observes (Trace Lab 8). The camera story suggests the analyzer "sees what happened"; in fact it sees signals at one point, which can differ from what the receiver at the far end decoded. And the "readable timeline" is itself a product of decoding software with its own version and assumptions, which the analogy hides entirely.

Analyzer presentation versus protocol truth

A protocol analyzer displays decoded events in a convenient, often proprietary representation. That display is not automatically the normative wire-level definition. Keep four layers separate in your head and in your reports:

Raw eventsymbols, ordered sets and packets as sampled at the probe point, with a timestamp
Protocol decodingthe analyzer software applies the PCIe (and NVMe) rules to raw bytes: fields, types, pairings
Analyzer UIrows, colours, grouping, summaries, warnings, names chosen by the vendor
Engineer interpretation"this completion answers that read", "this is the first abnormal event"

Each step can add errors. The probe may mis-sample a marginal signal (raw). The decoder may assume the wrong revision, the wrong BAR or queue address, or non-flit format on a flit-mode link (decoding). The UI may merge, hide or rename things (presentation). And the engineer may read causation into proximity (interpretation).

In a bug report, quote raw fields (header DWORDs, addresses, tags, timestamps) and say which decoding you relied on. "The analyzer said error" is not evidence; "the Root Port sent a Nak DLLP with sequence number 0x11F at 0.310 µs, analyzer software version X" is.

The camera photographs cars; a helper writes "red truck, late" under each photo. The photo is evidence; the caption is the helper's opinion.

An analyzer row is captured bytes plus a decode plus a presentation. Only the bytes and timestamp were measured.

The analyzer's front end recovers the serial bit stream per lane at the probe point, deskews lanes, descrambles or decodes the line coding, and frames symbols into packets. Marginal signals can make this step fail independently of the link's own receivers.

The PCI Express Base Specification defines the wire format; NVMe specifications define the queue structures. The analyzer's decode is an implementation of those definitions, not a definition itself.

On the wire: ordered sets, DLLPs and TLPs per direction, each with sequence numbers, CRCs and headers.

In the software: rows, transactions, commands, warnings, statistics. All derived.

When the decode says something impossible, check the raw bytes and the decoder's configuration before believing the device misbehaved.

The instrument and how it attaches

What a PCIe protocol analyzer is

A protocol analyzer is a passive (as far as the protocol is concerned) recorder that sits on a link and captures traffic in both directions. It has a probing front end that receives the link's signals, recovery and decoding hardware per lane, a large capture memory, trigger and filter logic that runs at line rate, and host software that configures captures and analyses the stored trace. It does not take part in the protocol: it sends no Acks, holds no credits, and is not enumerated by the host.

Related instruments are often confused with it. An exerciser generates traffic (it can act as a root complex or an endpoint and send deliberately unusual packets). A jammer or error injector sits in the link and modifies traffic to provoke error handling. Test equipment vendors, including Teledyne LeCroy, offer these as separate products or functions; they are active and change what the DUT experiences.

Teledyne LeCroy in brief

Teledyne LeCroy makes protocol analysis tools for several interfaces. For PCIe, its analyzers are sold under the Summit name, and captures are configured and analysed with its PCIe Protocol Suite software (earlier generations of the software were known by other names). Supported PCIe generations, link widths, buffer sizes, probe options and decode features differ by model and software release.

Product line-ups, model capabilities and software feature names change frequently. Before planning a capture, confirm in the vendor's current documentation: which PCIe generations and widths your model captures, which form-factor interposers and probes it supports, whether it supports flit mode and Integrity and Data Encryption (IDE) visibility, and what NVMe decoding your software version provides. Signal, clocks and training

  • Every probe is part of the channel. At 16.0 GT/s and above, the added loss of an interposer can push a marginal channel into errors or a lower speed (Trace Lab 8). Always compare link speed, width and correctable error counters with and without the probe.
  • Lock and training. To decode, the analyzer must recover each lane's data, deskew lanes and follow speed changes. At higher generations it may need to observe link training and equalization to follow the link reliably; some setups capture best when the analyzer is ready before the link trains. Check your product's guidance.
  • Clocking. Platforms use various reference-clock arrangements, including spread-spectrum clocking. The analyzer must cope with the platform's choice; mismatches show up as lock problems, not as protocol errors.
  • Flit mode. PCIe 6.x introduced flit-based encoding with a different packet framing and TLP header format. An analyzer and software that support it are needed to decode such links.
  • Encryption. When IDE is in use, TLP contents are encrypted on the link. An analyzer without access to keys can see framing and some header information, but not payloads such as SQEs. Whether and how keys can be supplied is product- and policy-dependent.

Capture

A capture is a recording of a time window on one link, stored in the analyzer's memory and later saved as a trace file. Its usefulness is decided before it starts, by four choices.

Its lesson is robust: at full load a capture covers milliseconds to seconds, not minutes. A thirty-second NVMe timeout cannot be captured end to end at full load; you capture its start (trigger on the command) or its end (trigger on the abort or reset) and reason across the gap.

Before you press record

  • Write down the question this capture answers.
  • Confirm link speed and width with the probe installed, and compare with the unprobed system.
  • Decide whether you need link training in the capture (for LTSSM questions, for NVMe decode that learns from initialization, for flow-control credit tracking).
  • Clear inherited filters and triggers; then add only what the question needs.
  • Choose trigger position from where the cause probably is relative to the symptom.
  • Record the probe type, the slot, the analyzer model, firmware and software versions, and the DUT configuration.

Triggers

A trigger is a condition evaluated in real time that marks a point in the capture and, depending on settings, stops recording after a chosen amount of post-trigger traffic. Good triggers turn "capture everything and search" into "capture the right second".

Trigger types (generic capabilities; availability is product-dependent)

Packet type and header fieldsAny completion with status other than Successful Completion; any MWr to BAR0 + 0x1000…0x1FFFYou know which packet marks the event
Address or data patternsMWr to the CQ1 address range with a specific CID in the payloadYou want one command's completion

When the symptom is visible in software but not on the link, make software produce a recognisable link event at the moment it notices the problem: for example, a read of a dedicated, otherwise unused LBA range, whose SQE (or data address) the analyzer can trigger on. Use a side effect that cannot change the behaviour under test. This is safer than any register write and works through the normal I/O path.

A missing response cannot be triggered on directly, but it can be triggered on as a sequence: "request with tag T not followed by a completion with tag T within time W". If your analyzer cannot express that, trigger on the consequence (the abort, the reset, the AER message) with a large pre-trigger portion.

Filters

Filters come in two kinds, and confusing them is one of the most consequential mistakes in trace analysis.

Capture filters versus display filters
Capture (hardware) filterDisplay (software) filter
When appliedBefore storage, in real timeAfter capture, when viewing
EffectFiltered events are not in the trace file at allEvents are hidden but still present
BenefitLonger capture windows for the traffic you keepClarity without losing evidence
RiskCreates false "missing" events; breaks decoders that need the removed trafficYou forget a filter is on and miss rows
Record in the reportAlways, verbatimWhen it affected what you looked at

Some traffic is commonly not stored by default to save memory (for example, idle symbols or certain repeating ordered sets); check what your configuration keeps. Payload truncation (storing only the first bytes of each payload) is another form of capture filtering: it saves memory but can make SQE decoding or data checks impossible.

Filtering out DLLPs breaks credit tracking and replay analysis. Filtering out completions breaks request pairing and the NVMe decode of fetched SQEs. Filtering out configuration traffic or the start of the link's life can prevent the NVMe decoder from learning queue addresses. Filter with the decoder's needs in mind.

Link-transaction view

Groups a TLP with the Data Link Layer response that acknowledged it (rows 1 + 2, 4 + 5, 6 + 7 above). Useful for replay and Ack-latency questions: how long did the receiver take to acknowledge, which TLPs were replayed, how often.

Split-transaction view

Groups a non-posted request with its completion(s) by Requester ID and Tag (rows 4 + 6). This is where completion latency, split completions, missing completions and unexpected completions become visible. Posted writes appear alone, because nothing answers them.

Higher-level (NVMe) view

Groups split transactions and posted writes into NVMe operations: "SQ1 doorbell, fetch of CID 0x0019, data, CQE, interrupt". This view needs configuration knowledge (see Decoding NVMe over PCIe). It is the most convenient view and the most assumption-laden.

Hierarchy

Move up the hierarchy to navigate; move down to verify. Any conclusion you report should be checkable at the packet level.

TLP view and DLLP view

Most software can show only TLPs or only DLLPs, or expand one packet into its fields and raw bytes. In the TLP field view, check Fmt/Type, Requester ID, Tag, Length, byte enables, address, the TD and EP bits and the attribute bits; compare them with your own decode (Programming Lab 2). In the DLLP view, look at Ack/Nak sequence numbers, the flow-control update types and values, and power-management DLLPs.

Timestamps

Timestamps are the analyzer's own clock attached to each captured event. They are among the most trusted fields in a trace, and still have limits:

  • Resolution and reference point. Know whether a timestamp marks the start or end of a packet and the resolution of the clock. Sub-microsecond comparisons near the resolution are meaningless.
  • One clock, two directions. Within one analyzer, both directions are normally timestamped on the same clock, which makes request-to-completion intervals reliable. Comparing two analyzers (for example on both sides of a switch) needs synchronisation or shared anchor events.
  • Not the host's clock. Kernel log timestamps and analyzer timestamps are different clocks with different offsets and drift. Align them with events visible in both (a marker I/O, a reset, an AER message).
  • Gaps. Segmented buffers, capture pauses and filtered periods create jumps. A large delta between consecutive rows can mean "the link was idle" or "nothing was stored". The settings tell you which.
  • Probe point latency. The analyzer timestamps events where it sees them, not when the device's logic produced or consumed them. Device-internal latency is inferred, not measured.

Link state

Link-state information comes from ordered sets and electrical conditions rather than from TLPs: training sequences (TS1/TS2), electrical idle and its exit, speed changes and equalization, Recovery, low-power states, and in flit mode the corresponding mechanisms of that encoding. The analyzer usually presents this as a state timeline or as decoded ordered-set rows.

Error view

Analyzers flag errors they detect themselves at the probe point: symbol or disparity errors, framing errors, LCRC (Link Cyclic Redundancy Check) failures, malformed packets, sequence-number anomalies, unexpected completions, and protocol-rule checks implemented in the software. This is valuable, and it is a different thing from the errors the link partners detect and report through AER.

When all three agree, confidence is high. When the analyzer flags an error that no device reported, suspect the probe or a decoder rule first. When a device reports an error that the analyzer did not flag, suspect the channel beyond the probe point, or a device-internal problem.

Decoding NVMe over PCIe

NVMe is not a packet protocol on PCIe; it is memory structures and register writes carried by ordinary TLPs (What Is NVMe?). To turn TLPs into NVMe commands, decoding software must know:

  1. Which device is the NVMe controller and where its BAR0 is (to recognise doorbell writes and register accesses).
  2. The doorbell stride (CAP.DSTRD), to map doorbell offsets to queues.
  3. The base addresses and sizes of the admin queues (from AQA, ASQ, ACQ writes) and of each I/O queue (from Create I/O SQ and Create I/O CQ commands), to recognise SQE fetches and CQE writes.
  4. The MSI-X table contents, to recognise interrupt messages.
  5. The queue-to-command-set context, because opcodes mean different commands on admin and I/O queues.

Software can learn all of this by watching initialization from the start, which is why capturing from link-up or controller enable matters. If the capture starts later, the decoder may show SQE fetches as plain memory reads, or need you to enter the BAR and queue addresses manually (how is product-specific; check your documentation). Programming Lab 6 in Programming Labs implements exactly this classification and shows how fragile it is.

NVMe decoding can be wrong without looking wrong: if the configured queue base is stale (queues re-created at new addresses after a reset), SQE fetches from the new queue will be decoded as data reads, or data reads that happen to fall in an old queue range will be decoded as SQE fetches. After any reset or queue re-creation in a capture, verify that the decoder followed it.

Which NVMe revisions, command sets, SGL forms and newer features (for example those introduced in NVMe 2.4) a decoder understands depends on its software version. An unknown opcode or field shown as "reserved" may simply be newer than the decoder.

Traffic analysis

Beyond individual events, analyzer software usually offers statistics computed over the capture: throughput per direction and per packet type, latency distributions for split transactions, counts of outstanding requests over time, flow-control credit levels, link utilisation, and (with NVMe decoding) per-queue and per-command latency. These turn "it feels slow" into numbers.

  • Throughput: separate payload bytes from overhead; compare with the link's theoretical capacity (Calculators).
  • Outstanding requests: if the device's non-posted requests plateau at a fixed number, look at tag limits and its internal queue depth.
  • Latency histograms: look at the tail, not the mean; then jump from the worst sample to its location in the trace.
  • Credits: long periods at zero credits show where back-pressure starts (Trace Lab 9), as long as the capture saw the initial credit advertisement.

Statistics inherit every capture limitation: filters, gaps and decoder assumptions all bias them silently.

Exporting

Vendor software is the authoritative decoder of its own trace files. To process a capture with your own tools (scripts, the programs from Programming Labs, a team database), export a decoded representation: typically text, CSV or another structured format, at a chosen view level, with chosen fields. What export formats and field selections are available depends on the product and version.

  • Export the packet level when you need to re-derive pairing yourself; export a transaction level when you only need latencies.
  • Always include timestamps, direction, type, Requester ID, Tag, address, length, status, and the raw header if offered.
  • Export the capture settings alongside the data.
  • Keep the original trace file unmodified and record its hash.

The whole topic, including normalising exports into a portable format, is covered in PEX / Capture File Training.

The four-step workflow

The master plan asks for four specific skills. Together they form the analyzer workflow used throughout this course.

Step 1 — From a symptom to a trace region

A symptom is reported in host terms ("I/O timeout on nvme0, QID 2, command 0x33 at 14:02:31"). A trace is in link terms. Bridge them:

  1. Translate the symptom into link events. QID 2 → SQ2 tail doorbell at BAR0 + 0x1010, CQ2 head doorbell at BAR0 + 0x1014, SQ2 and CQ2 base addresses. Command 0x33 → CID 0x0033 in an SQE fetched from SQ2.
  2. Anchor time. Find an event visible in both clocks (a marker I/O, a reset, an AER message, an abort command) and compute the offset; account for drift on long captures.
  3. Search, do not scroll. Use the software's search or a display filter for the SQ2 doorbell writes and for the CID inside SQE payloads; for timeouts, also search for the abort or reset that the host issued.
  4. Bound the region. From the doorbell that submitted the command to the event that ended the story (CQE, abort, reset). That is your region.

Step 2 — Identifying the first abnormal event

  1. Confirm coverage of the region. No segment boundary, no filter that removes needed traffic, analyzer locked throughout.
  2. Find the last known-good point: the last stage of this command (or of the last healthy command) that matches expectation.
  3. Walk forward stage by stage (doorbell, fetch, PRP/SGL fetch, data, CQE, interrupt, head doorbell; plus DLLPs and link state for lower layers), checking fields, order and timing.
  4. Mark the first departure, including an absence; then check whether an earlier, quieter event explains it (a configuration write, a mask, a reset).

Step 3 — Reconstructing the transaction

Step 4 — Formulating a root-cause hypothesis

A useful hypothesis names a mechanism, an owner, and a prediction you can test:

Template: "Because [mechanism] in [agent], [first abnormal event] occurred, which led to [symptom]. If this is right, then [observable prediction]; if it is wrong, then [alternative observation]. Confidence: [low/medium/high], because [evidence]."

Always write at least one competing hypothesis and the evidence that separates them. The Trace Analysis Laboratory gives twelve worked examples; Debugging Methodology generalises the method.

Worked example

Symptom: "nvme0: I/O timeout, QID 1, command 0x57" (host log, synthetic). The capture used a sequence trigger: "completion MWr to the CQ1 range not followed by an MWr to the MSI-X window within 50 µs", with 80% of the buffer before the trigger.

  1. Region: search for CID 0x0057 in SQE payloads on SQ1: one fetch at 1,201.4 µs; its CQE at 1,270.5 µs (the trigger). Region: from the SQ1 doorbell at 1,200.0 µs to the trigger.
  2. First abnormal event: fetch, data and CQE are normal; the interrupt is missing. Searching backwards for writes to the MSI-X table (BAR0 + 0x2000…0x2FFF) finds a mask write for vector 1 at 0 µs and no unmask.
  3. Reconstruction: every stage up to the CQE checks out at packet level; vector 1's table entry was rewritten but left masked.
  4. Hypothesis: "Because the host's interrupt-retargeting path left vector 1 masked, the CQE for CID 0x57 produced no interrupt, so the I/O sat until the 30 s timeout. Prediction: unmasking vector 1 will immediately produce the pending interrupt message." This is Trace Lab 5, where the prediction is confirmed.

No specification defines what an analyzer must display or how it must decode. The PCI Express and NVMe specifications define the protocol; analyzer behaviour is a vendor implementation. Any analyzer statement that cannot be traced back to raw fields and a specification rule is an annotation, not a fact about the protocol.

Specification view

The relevant documents are the PCI Express Base Specification (a PCI-SIG members' document; revision family 6.x/7.0 for current links, with older revisions for older devices), the NVM Express Base Specification 2.4, the NVM Command Set Specification 1.3 and the NVMe over PCIe Transport Specification 1.4. Analyzer documentation is vendor material: informative about the tool, never normative about the protocol.

What is verified? Wire formats (TLP and DLLP fields, ordered sets), ordering and flow-control rules, error types, and the NVMe register map and queue structures are defined by the specifications above. A packet-level decode can be checked against them.

What is derived? Transaction pairing, NVMe command grouping, latencies, inferred LTSSM states and credit levels are computed by software from captured events. They are as good as the capture and the decoder's assumptions.

What is implementation-dependent? Every product's probe, buffer, trigger and filter capabilities, views, names, file formats and export formats; how a device reacts to errors; platform behaviour for blocked DMA.

What is version-dependent? The decoder's knowledge of PCIe revisions (including flit mode) and NVMe revisions and features; the UI; default settings.

What must be checked in the specification? Any field, encoding or rule that a decoded view relies on and your conclusion depends on: check it in the specification revision the link and device actually implement.

What should never be assumed? That the capture is complete; that the analyzer's "error" is the device's error; that the NVMe decode used current queue addresses; that the probe did not affect the link; that a product feature exists under the name someone remembers.

The sixteen questions, for a protocol-analyzer capture

A capture, examined like any other engineering concept
QuestionAnswer
What is it?A time-stamped recording of the traffic on one PCIe link, as seen at one probe point, plus the settings that shaped it.
Why was it created?Because device and host software can only report what they noticed; the link carries what actually happened between them.
What problem does it solve?Attributing behaviour to an agent and a moment, with evidence independent of either party's logs.
What existed before it?Logic analyzers on parallel buses, debug prints, register dumps, oscilloscopes.
Why is the current design better?Line-rate decoding of serial links with triggers and multi-level views; parallel-bus tools cannot follow multi-gigatransfer serial links.
Who creates it?The analyzer hardware (raw events) and the engineer (settings).
Who consumes it?Validation, firmware, driver and platform engineers; sometimes customers and vendors in joint debugging.
Where does it live?In analyzer memory during capture, then in a trace file, often in a proprietary format (PEX / Capture File Training).
What memory/registers are involved?None in the DUT; the analyzer's own capture memory and configuration.
What happens before it?A question, a probe installation, settings, a reproduction plan.
What happens after it?Navigation, reconstruction, hypothesis testing, export, a report.
What happens if it is wrong?Wrong root causes, wasted weeks, bugs filed against the wrong party (Trace Lab 11).
What does the protocol analyzer show?Packets, transactions, link states, statistics and its own error flags, all subject to the four truth layers.
What does Linux show?Not the capture; but AER messages, NVMe errors, tracepoints and register dumps that corroborate or contradict it.
What would a validation engineer test?That the probe does not change link behaviour; that triggers fire when expected; that decoding matches hand-decoded samples.

Lab A — Install a probe and prove it does not change the link

Objective

Establish a trustworthy capture setup by measuring the link with and without the probe.

Skills

  • Probe installation
  • Read-only link verification
  • Recording capture metadata

Safety

Caution lab Power down before installing hardware; use electrostatic-discharge protection; test system and disposable data only.

Hardware required

A PCIe protocol analyzer with an interposer for the SSD's form factor; a test server; an NVMe SSD.

Software required

The analyzer's software (for example, Teledyne LeCroy PCIe Protocol Suite for a Summit analyzer), Linux with lspci, nvme (nvme-cli) and fio.

Input

The unprobed system.

Expected output

A one-page setup record: link speed and width with and without probe, correctable error counts after an identical workload, analyzer and software versions, probe type.

Background

See The instrument and how it attaches.

Step 1

Without the probe, record link status and error state read-only, then run a fixed workload:

sudo lspci -vvv -s 01:00.0 | grep -E "LnkCap:|LnkSta:"
sudo lspci -vvv -s 01:00.0 | grep -A3 "Advanced Error Reporting"
# the workload reads only; use a test drive anyway
sudo fio --name=seqread --filename=/dev/nvme0n1 --readonly --rw=read --bs=128k --iodepth=32 --direct=1 --runtime=60 --time_based

Step 2

Power down, install the interposer following the vendor's guide, power up, repeat Step 1 exactly. Then start a capture with no filters and capture link training.

Step 3

Compare: speed, width, correctable error status, throughput. Record the analyzer model, firmware and software versions, probe type and slot.

Observation

Any difference in link speed, width, error counts or throughput is an effect of the probe or of the reseating, and must be resolved before the setup is trusted.

Questions

  1. Throughput is identical but the Root Port shows new Bad TLP correctable errors with the probe. Is the setup acceptable?

    Answer

    Not for questions about errors, retries or latency: the probe is causing replays. It may be acceptable for a purely functional question, if documented. Prefer fixing the setup.

  2. Why capture link training even if the bug is about NVMe commands?

    Answer

    It lets the analyzer lock reliably at higher generations, captures initial flow-control credits, and (with initialization also captured) lets the NVMe decoder learn BAR and queue addresses.

Challenge

Repeat with a second probe type or slot, and quantify which setup is least intrusive.

Hint

Use the same workload, the same duration and fresh error counters each time; reboot between runs if you cannot clear counters without writing registers.

Solution

A good record is a small table: setup × (speed, width, correctable errors per minute, throughput). The least intrusive setup has unchanged speed and width, zero new correctable errors and unchanged throughput. If none qualifies, state the residual effect in every report made with that setup.

What a senior engineer notices

Reseating the drive is itself a variable. A good engineer reseats without the probe once to separate "the probe" from "the reseat".

Failure variants

  • Link trains at a lower speed only with the probe.
  • Analyzer never locks at the top speed although the link does.
  • The system fails to boot because the probe changes reset or presence timing.

Extension

Write the setup record as a template your team fills in for every capture (see capture metadata).

Lab B — Trigger on a missing interrupt

Objective

Design and test a trigger that catches a CQE not followed by its MSI-X message.

Skills

  • Sequence triggers
  • Address-range conditions
  • Trigger position

Safety

Caution lab with hardware (probe installed as in Lab A); Safe lab as a paper exercise.

Hardware required

As Lab A, or none for the paper version.

Software required

Analyzer software; for the paper version, the trace of Trace Lab 5.

Input

CQ1 address range (0x1_2341_0000–0x1_2341_3FFF), MSI-X window (0xFEE0_0000–0xFEEF_FFFF), device Requester ID 0x0100.

Expected output

A written trigger specification and, with hardware, a capture that triggers only when an interrupt is missing.

Background

See Triggers.

Step 1

Write the condition in words: "MWr from 0x0100, 16 bytes, to the CQ1 range, NOT followed within W µs by an MWr from 0x0100 to the MSI-X window".

Step 2

Choose W from healthy traffic: measure CQE-to-MSI-X intervals in a capture without the fault and pick a value well above the maximum (and above any interrupt coalescing time configured).

Step 3

Choose trigger position (mostly pre-trigger, because the cause precedes the CQE), express the condition in your analyzer's trigger language, and test it on healthy traffic first: it must not fire.

Observation

A trigger that fires on healthy traffic is measuring your assumptions, not the bug.

Questions

  1. Why must W exceed the interrupt coalescing time?

    Answer

    With coalescing, a CQE may legitimately not be followed by an interrupt until a time or count threshold is reached. Without accounting for it, the trigger fires on correct behaviour.

  2. Why "from 0x0100" in both conditions?

    Answer

    Other devices on other links will not appear on this link, but on a shared or switched link, other functions could write to the MSI window. Restricting the requester avoids false negatives.

Challenge

Extend the condition so that it ignores CQEs on queues created with interrupts disabled.

Hint

Restrict the CQE address range to the CQs created with IEN = 1 (from the Create I/O CQ commands).

Solution

Build one address range per interrupt-enabled CQ from the Create I/O CQ commands (base PRP1, size QSIZE + 1 entries × 16 bytes) and use their union in the first condition. If the analyzer cannot express unions, run one capture per queue of interest.

What a senior engineer notices

The trigger encodes a theory. If it never fires during a reproduction, either the theory is wrong or the trigger is; test the trigger on a synthetic fault (for example, a test build that masks a vector) before trusting a negative result.

Failure variants

  • Trigger never fires: the bug is elsewhere, or W is too large.
  • Trigger fires constantly: coalescing, wrong address ranges, or polling-mode queues.

Extension

Design a trigger for "SQ doorbell not followed by an SQE fetch from that queue within W".

Lab C — Climb the decode hierarchy by hand

Objective

Rebuild link transactions, split transactions and one NVMe command from the packet view at the top of this page.

Skills

  • Ack pairing by sequence number
  • Completion pairing by Requester ID and Tag
  • NVMe stage identification

Safety

Safe lab Paper exercise.

Hardware required

None.

Software required

None (optionally Programming Labs 2 and 6).

Input

The packet view in Views.

Expected output

Three tables: link transactions, split transactions, NVMe stages.

Background

See Views.

Step 1

Pair every TLP with its Ack by sequence number.

Step 2

Pair every non-posted request with its completion by Requester ID and Tag; list posted writes alone.

Step 3

Label the NVMe stage of each split transaction or posted write.

Observation

Some packets (the UpdateFC DLLPs) belong to no transaction at all; they are link housekeeping that only the packet view shows.

Questions

  1. Which rows form the split transaction, and what is its latency?

    Answer

    Rows 4 (MRd64, tag 0x30) and 6 (CplD, tag 0x30): 1.410 − 0.620 = 0.790 µs at the probe point.

  2. Why does row 1 have no split transaction?

    Answer

    It is a posted write (a doorbell). It has a link transaction (row 2's Ack) but no completion.

Challenge

If row 5 were a Nak with sequence number 0x1A6, what rows would follow?

Hint

The Nak names the last good sequence number.

Solution

The SSD would replay sequence 0x1A7 (the MRd64, same tag 0x30) and anything after it still unacknowledged; then the Root Port would Ack 0x1A7. The split transaction is unchanged (same tag, one completion); its latency grows by the replay time. The Root Port would log a Bad TLP (or similar receiver error) as a correctable error.

What a senior engineer notices

Replays are invisible at the split-transaction and NVMe levels except as extra latency. If you only read the top view, you will call a link problem "slow firmware".

Failure variants

  • Ack for a sequence number never seen (capture started mid-stream).
  • Completion before its request (clock or capture problem, or misread direction).

Extension

Repeat for the full trace of Trace Lab 1.

Lab D — Audit a capture before analysing it

Objective

Decide whether a capture is fit for a stated question, using only its settings and a few rows.

Skills

  • Capture scope reasoning
  • Writing an evidence-validity statement

Safety

Safe lab Paper exercise.

Hardware required

None.

Software required

None.

Input

Question: "Did the SSD ever issue a memory read that was not completed?" Capture settings (paraphrased): link Gen4 ×4; capture started 40 s after boot; capture filter excludes ordered sets and DLLPs; payloads truncated to 16 bytes; buffer mode wrap; trigger on Completion Timeout message from the SSD; trigger position 90%.

Expected output

A verdict per setting: helps, harmless, or invalidates the question; and a recommended configuration.

Background

See Capture, Filters and Limitations.

Step 1

For each setting, ask what it removes.

Step 2

Ask what the question needs: every non-posted request and every completion in the window.

Step 3

Write the verdict and the recommended settings.

Observation

Several settings that look harmless for this question are harmful for others, and vice versa.

Questions

  1. Does payload truncation to 16 bytes harm this question?

    Answer

    Not directly: request/completion pairing needs headers, not payloads. It would harm NVMe decoding of SQEs (64 bytes) and any data check.

  2. Is the trigger a good one?

    Answer

    Yes for the stated question: an error message reporting a Completion Timeout is sent after the timeout expires, so the request that timed out is well before the trigger. A 90% pre-trigger position keeps it, provided the buffer covers the timeout duration at the traffic rate. Otherwise trigger on the request pattern instead.

Challenge

Rewrite the settings for the different question "Why did the link enter Recovery?"

Hint

Recovery is a link-state question: which filtered items does it need back?

Solution

Keep ordered sets and DLLPs (training sets and Naks are the evidence), keep payload truncation (payloads are irrelevant), trigger on entry to Recovery with most of the buffer before the trigger, and record probe configuration because signal integrity is a likely cause.

What a senior engineer notices

Capture settings are part of the evidence chain. A finding without them cannot be reviewed.

Failure variants

  • Settings not exported with the trace.
  • Settings changed between two captures being compared.

Extension

Turn your verdicts into a checklist and apply it to Trace Lab 11.

Common mistakes

  • Treating the analyzer's view as the protocol truth instead of a decoded, presented interpretation.
  • Starting analysis at the trigger point and reading forward.
  • Inheriting capture filters from a previous project.
  • Reading NVMe-level views without checking that the decoder knew the current queue addresses.
  • Ignoring the probe's effect on a high-speed link.
  • Comparing analyzer timestamps directly with kernel log timestamps.
  • Reporting button names instead of describing settings, so nobody on another software version can reproduce the capture.

Senior engineer insight

The best analyzer users spend more time before the capture than after it. They write the question down, decide what evidence would answer it, set up the narrowest capture that still contains that evidence, prove the setup does not disturb the system, and only then reproduce. After the capture, they navigate by search and triggers, verify every important claim at the packet level, and write reports that someone with a different software version can check.

They are also generous with doubt. "The analyzer shows no completion" becomes "no completion was stored in this capture; filters: none; buffer: continuous; analyzer status: locked throughout". That sentence takes ten seconds longer to write and saves weeks.

Quiz

  1. Which layer of the "truth stack" does an NVMe command grouping belong to?

    • Raw event
    • Protocol decoding (using configuration knowledge)
    • Engineer interpretation only
    • None; it is on the wire
    Answer and reasoning

    NVMe commands are not packets; the software groups TLPs into commands by decoding them with knowledge of BAR and queue addresses.

  2. A capture filter excluded completions. What happens to those completions?

    • Hidden, but restorable by clearing the filter
    • Stored with a "filtered" mark
    • Never stored; they are not in the trace file
    • Stored in a separate file
    Answer and reasoning

    Capture filters act before storage. Only display filters can be undone.

  3. The analyzer flags no errors, but the Root Port logs Bad TLP errors. The most likely location of the problem is:

    • The channel between the probe point and the Root Port's receiver
    • The SSD's transmitter before the probe
    • The NVMe driver
    • The analyzer's software
    Answer and reasoning

    The signal was good at the probe and bad at the receiver, so it degraded in between (Trace Lab 8).

  4. Why does capturing initialization help NVMe decoding?

    • It makes the capture smaller
    • It enables encryption
    • It sets the trigger automatically
    • The decoder learns BAR, doorbell stride and queue addresses from it
    Answer and reasoning

    Without that knowledge, doorbells and SQE fetches look like ordinary memory traffic.

  5. Which view shows replays most directly?

    • Packet or link-transaction view
    • Split-transaction view
    • NVMe command view
    • Traffic statistics only
    Answer and reasoning

    Replays are Data Link Layer behaviour: Naks and repeated sequence numbers appear at the packet and link-transaction levels; higher views only show extra latency.

  6. Explain why an analyzer's inferred LTSSM state is an interpretation.

    Model answer

    The LTSSM runs inside each port; the analyzer only sees the ordered sets and electrical conditions on the wire and infers which state the ports are probably in. The ports' internal transitions and timers are invisible.

  7. Your capture window is shorter than the 30-second NVMe timeout. How do you still capture the cause of a timeout?

    Model answer

    Trigger on the command's start (its doorbell or SQE, if identifiable) with mostly post-trigger buffer, or on the event that ends it (abort, reset) with mostly pre-trigger buffer; or use a sequence trigger on the missing response. Use capture filters only if they do not remove the needed evidence. Reason across any gap with corroborating logs.

  8. Name four limitations of analyzer evidence and one mitigation for each.

    Model answer

    Filtering (export and read settings); capture gaps (check timestamp continuity and buffer mode); dropped packets (check analyzer status and sequence numbers); decoder limitations (verify at packet level, record software version). Others: timestamps, version-dependent UI, proprietary annotations, single probe point, observer effect.

  9. Why should reports describe settings rather than name UI buttons?

    Model answer

    UI names change between software versions and vendors. A description of what was captured, filtered and triggered can be reproduced on any version and reviewed by someone with a different tool.

Interview questions

  1. Beginner. What is the difference between a protocol analyzer and an exerciser?

    Model answer

    An analyzer observes and records a link without taking part in the protocol. An exerciser generates traffic and acts as a protocol participant (for example emulating a host or a device), so it changes what the DUT experiences.

  2. Intermediate. How do you pair a completion with its request in a capture, and what can break the pairing?

    Model answer

    By Requester ID and Tag (10-bit tags if enabled). Pairing breaks if either side was not captured (filters, gaps, capture start), if tags are reused after a timeout (late completions), or if the decoder mis-handles extended tags or flit-mode headers.

  3. Advanced. A customer's capture shows the SSD sending a Malformed TLP. How do you verify the claim?

    Model answer

    Inspect the raw header bytes and decode by hand; check which rule is violated and against which configuration (for example MPS on both ends); confirm the receiver reported it (AER at the receiver); check the analyzer's own lock and error status at that moment; and check the decoder version supports the link's mode.

  4. Senior. Describe how you would set up a capture to investigate a once-a-day I/O timeout in a production-like lab.

    Model answer

    Prove the probe is non-intrusive; capture with a sequence trigger on the missing response (or on the host's abort/reset, made visible on the link), mostly pre-trigger buffer, minimal filters chosen not to break decoding; add a host-side marker I/O when the driver detects the timeout; collect host logs and register snapshots; and keep the setup unchanged across days so captures are comparable.
