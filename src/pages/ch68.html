This chapter zooms out from a single connection to the whole NVMe over Fabrics (NVMe-oF) system: host → fabric → target → subsystem → controller → namespace. You will learn how each layer is named (NVMe Qualified Names, or NQNs, host identifiers, ports, controller IDs, namespace IDs), how a host finds storage (discovery controllers, the Discovery Log Page, centralized discovery), how it stays connected (keep alive and reconnection), and how it survives path failures (Asymmetric Namespace Access and multipathing).

Why this chapter exists

On PCIe, the architecture is given to you by the hardware. Enumeration finds a function, its BAR holds one controller, and the controller exposes namespaces. There is one path, discovered automatically, and it is trusted by physical presence.

On a fabric, none of that is automatic. A host must be told, or must discover, which subsystems exist and at which addresses. A subsystem must decide which hosts it accepts. One namespace may be reachable through several controllers on several ports over several networks, and those paths may differ in performance or fail independently. A connection may silently die. A senior engineer working on NVMe-oF spends far more time on this architectural layer than on PDU formats.

Chapter 65 gave the per-command model. Chapter 66 and Chapter 67 gave the transports. This chapter gives the system.

The story

Imagine a city full of libraries. Before you can borrow a book, you need to know which libraries exist and where they are. So the city has an information desk. You walk in, say your name, and the desk gives you a printed list: "The Science Library is at 12 Oak Street, door 4420. It also has a back door at 5 Elm Street." Every library has a long, unique name so there is never confusion, and you have a long, unique name too, so libraries know who you are.

At the library you talk to a librarian at a counter. Some libraries have two counters for the same shelves. If one counter closes, you walk to the other one, and you still reach the same books. Sometimes the librarian says "this counter is slow today, use the other one". And if you stop waving at the librarian every few seconds, she assumes you left, closes your account and puts your requests away.

Think of an airport. The host is a traveller. The fabric is the road and rail network. The target is the airport building. The subsystem is one airline inside it. The controllers are that airline's check-in desks, possibly in two terminals. The namespaces are the flights. The discovery controller is the departures board at the entrance, listing which airlines operate from which terminal and gate. A Centralized Discovery Controller is a city-wide travel information service covering every airport. ANA is the desk sign: "open", "open but slow, other terminal preferred", "closed", "closed permanently", "changing over". Keep alive is the boarding agent checking every few minutes that you are still in the queue.

What it hides. Departure boards are global and public. A discovery controller can return different lists to different hosts (per-host filtering, zoning in CDCs), and it is a controller that you connect to with the same Connect command as any other. Airline desks also do not "share" a flight in the way two NVMe controllers share a namespace. Shared namespaces need reservations and ANA to stay consistent.

Where it misleads. A traveller with a closed desk walks to another terminal immediately. NVMe hosts may queue I/O during ANA transitions and wait (bounded by timers) instead of failing over at once. The analogy also suggests one traveller per queue. Each host opens many queues (connections) to each controller.

Beginner explanation

Read the hierarchy from the host outward:

  • An NQN is a globally unique text name, such as nqn.2026-10.org.example:lab-ssd. Every subsystem has one. Every host has a host NQN.
  • A port on the target is a transport address where controllers can be reached, such as TCP 192.0.2.20:4420.
  • To learn which subsystems exist, a host connects to a discovery controller and reads the Discovery Log Page, a list of entries saying "subsystem X is reachable over transport T at address A, port P".
  • The host then connects to each entry. Each connection to a subsystem creates a controller. Two connections through two ports create two controllers, so the host has two paths to the same namespaces.
  • Asymmetric Namespace Access (ANA) tells the host, per path and per group of namespaces, whether that path is optimized, non-optimized or unusable. The host's multipathing logic uses this to choose paths.
  • Keep alive lets each side detect that the other has disappeared, and tear down and reconnect.

NVMe Qualified Names

An NQN is a UTF-8 string of at most 223 bytes that identifies a host or an NVM subsystem. Two formats are defined in the Base specification: Verified

Two NQNs are reserved and well known: nqn.2014-08.org.nvmexpress.discovery, the well-known discovery subsystem NQN that any host may use to reach a discovery controller, and the UUID prefix above. A subsystem's NQN is reported in Identify Controller (SUBNQN). A host's NQN is presented in every Connect.

The Host Identifier (HOSTID) is a separate 128-bit value, also sent in Connect. It identifies the host for features that span controllers, most importantly reservations. A subsystem uses it to recognise that two controllers belong to the same host. On Linux, the host NQN is in /etc/nvme/hostnqn and the Host Identifier in /etc/nvme/hostid. Both are generated once per installation. Implementation-dependent

VM templates and disk images often carry /etc/nvme/hostnqn and hostid with them. Two hosts with the same identity confuse allow lists, reservations and target-side accounting. One host can even cause the target to tear down the other's association. Regenerate both on first boot (nvme gen-hostnqn).

Subsystem, controller, namespace over fabrics

  • An NVM subsystem is the unit of naming and access control. It contains namespaces, one or more ports and controllers.
  • A controller over fabrics exists per association. With the dynamic model, each admin Connect (CNTLID FFFFh) causes the subsystem to allocate a new controller, with its own CNTLID, feature state and keep alive timer. Disconnecting destroys it.
  • A namespace belongs to the subsystem. When several controllers can access it, it is a shared namespace, identified consistently by NSID and by globally unique identifiers (NGUID, EUI-64, UUID). This is how a host recognises that nvme1n1 and nvme2n1 are the same storage.
  • A port is where controllers are reachable. One subsystem may be exposed on several ports and transports at once. The Discovery Log Page entry has a PORTID field.

Discovery controllers

A discovery controller is a special controller in a discovery subsystem. It has no namespaces and no I/O queues. It exists only to serve the Discovery Log Page. A host reaches it like any other controller: transport connection, then admin Connect with SUBNQN set to the well-known discovery NQN (or to a discovery subsystem's unique NQN), then Property Get/Set to enable it, then Identify Controller and Get Log Page.

Two flavours matter:

  • Non-persistent (traditional): the host connects, reads the log page and disconnects. KATO is typically zero, since there is no long-lived association.
  • Persistent discovery controller: the host keeps the association open with keep alive and arms an Asynchronous Event Request. When the discovery information changes, the controller sends a Discovery Log Page Change asynchronous event, and the host re-reads the log page and connects to new entries. This is how hosts learn about new subsystems without polling.

Centralized Discovery Controllers (CDC)

In a large Ethernet fabric with hundreds of hosts and dozens of storage arrays, configuring every host with every array's discovery address does not scale. The NVMe-oF ecosystem added (through ratified Technical Proposals for centralized discovery and automated discovery) the concept of a Centralized Discovery Controller (CDC). A CDC is a discovery service, often running in a fabric switch or a dedicated service, that:

  • accepts registrations: hosts and storage subsystems register their discovery information with the CDC (explicitly, or the CDC pulls it from subsystem discovery controllers);
  • applies zoning: administrators define which hosts may see which subsystems, so each host's Discovery Log Page contains only what it is allowed to reach;
  • uses persistent connections and change notices to tell hosts when their zone's content changes;
  • can itself be found automatically on the local network using DNS-based service discovery (mDNS/DNS-SD).

The commands and log pages involved are defined in the Base specification (Discovery Information Management and related structures). Their opcodes and formats are not reproduced here. Confirm in spec Read them in the Base 2.4 sections on discovery and centralized discovery before implementing.

Keep Alive and association lifetime

Over PCIe, a controller cannot vanish without the platform noticing (link down, surprise removal, AER). Over a fabric, a peer can vanish silently: power loss, a crashed target, a partitioned network. The Keep Alive mechanism defines a timeout for the association:

  • The host sets KATO (Keep Alive Timeout) in the admin Connect, in milliseconds. Identify Controller's KAS (Keep Alive Support) field gives the controller's timer granularity.
  • The host sends the Keep Alive admin command (opcode 18h) often enough that the controller always sees one within KATO. Linux sends it at a fraction of KATO. Implementation-dependent
  • With Traffic Based Keep Alive (when supported), any command processed within the interval counts, which reduces explicit Keep Alive traffic on busy controllers.
  • If the controller's timer expires, it treats the host as gone: it tears down the association, aborts outstanding commands, and releases the controller (dynamic model). The host learns this when its next command or Keep Alive fails, or its connection is closed.
  • If the host's Keep Alive command does not complete in time, the host assumes the controller is gone and starts error recovery: tear down all queues, then reconnect.

KATO protects against dead peers, but it also turns slowness into failure. A target whose admin path is starved for longer than KATO, or a host whose Keep Alive work is delayed by CPU saturation, causes association teardown and reconnect even though nothing is broken. Choose KATO with the worst-case admin path latency in mind.

Asymmetric Namespace Access (ANA)

In a dual-controller storage array, a namespace is usually "owned" by one controller. Accessing it through the other controller works, but may be slower (the I/O crosses an internal link) or impossible during failover. ANA lets the subsystem describe this per path, so hosts route I/O sensibly.

  • Namespaces are grouped into ANA groups, identified by an ANA Group ID (ANAGRPID) reported in Identify Namespace. All namespaces in a group share an access state per controller.
  • Each controller reports, for each ANA group, one of five ANA states:

Commands sent on a path in a non-usable state complete with path-related status values (Status Code Type 3h), such as Asymmetric Access Inaccessible, Asymmetric Access Persistent Loss and Asymmetric Access Transition. Multipathing on the host

Linux has a native NVMe multipath implementation in nvme-core, enabled by default in most distributions (/sys/module/nvme_core/parameters/multipath). Each shared namespace appears once, as /dev/nvmeXnY, the multipath "head". Per-path devices (named like nvmeXcYnZ) are hidden. The kernel picks a path per I/O using the ANA state and an I/O policy, set per subsystem in /sys/class/nvme-subsystem/nvme-subsysX/iopolicy: Implementation-dependent

  • numa (default): prefer the optimized path closest to the submitting CPU's NUMA node.
  • round-robin: rotate among the best-state paths.
  • queue-depth: choose the best-state path with the fewest outstanding commands (newer kernels). Version-dependent

Device-mapper multipath (dm-multipath) is an alternative some distributions and vendors prefer. Use one or the other for a given subsystem, never both.

The central concept on the ladder: a path

Two counters in the same library, serving the same shelves. A sign on each counter says "open", "slow", "closed" or "changing".

A path is one controller (one association, over one port and transport address) through which a host reaches a shared namespace. Multiple paths give redundancy and bandwidth. ANA states tell the host which to use.

Each path is a set of transport connections (one per queue) from a host NIC through switches to a target port. The paths may cross different NICs, switches and target controllers, which is the whole point. Their failure domains should be independent.

The Base 2.4 specification defines controllers, shared namespaces, NGUID/EUI-64/UUID identification, ANA groups and states, the ANA log page (0Ch), ANA change events, path-related status values and the Discovery Log Page (70h). Host path selection is not specified.

Per path: transport connect → Connect (admin, then I/O queues) → Identify (namespace IDs match across paths) → Get Log Page 0Ch (ANA states) → AER armed. I/O flows on the selected path. Path errors return path-related status, then the host retries elsewhere.

Captures on two host interfaces show I/O shifting from one to the other after an AEN and an ANA log read, or after a keep alive failure and connection reset. The CIDs are independent per path.

Was failover triggered by ANA (orderly: AEN, log read, state change), by transport loss (disorderly: connection reset, keep alive failure), or by error status? Did I/O pause for ANATT or fast_io_fail_tmo? Were both paths really independent, or did they share a switch?

Specification view

The architecture in this chapter is normative in the NVM Express Base Specification, Revision 2.4 — NVM subsystem and controller architecture, NVMe over Fabrics, discovery, Discovery Log Page, Asymmetric Namespace Access, Keep Alive, authentication. Transport-specific discovery fields (TSAS) and TLS requirements come from the NVMe over TCP Transport Specification, Revision 1.3 and the NVMe over RDMA Transport Specification, Revision 1.3.

  • NQNs are at most 223 bytes, in domain-based or UUID-based format. nqn.2014-08.org.nvmexpress.discovery is the well-known discovery NQN.
  • The Discovery Log Page is log identifier 70h: a 1024-byte header (GENCTR, NUMREC, RECFMT) plus 1024-byte entries (TRTYPE, ADRFAM, SUBTYPE, TREQ, PORTID, CNTLID, ASQSZ, TRSVCID, SUBNQN, TRADDR, TSAS).
  • The ANA log page is log identifier 0Ch. ANA states are Optimized, Non-Optimized, Inaccessible, Persistent Loss and Change.
  • Keep Alive is admin opcode 18h. KATO is set in the admin Connect for fabrics.
  • Authentication Send/Receive are Fabrics commands (opcode 7Fh) carrying authentication protocols such as DH-HMAC-CHAP.
  • Because controllers are per association, ANA state is a property of (controller, ANA group), and therefore of a path. The same namespace can be Optimized on one path and Inaccessible on another at the same moment.
  • Because Discovery Log contents can be host-specific, two hosts running nvme discover against the same address may legitimately get different answers.
  • Because keep alive expiry destroys the association, any host retry after expiry happens on a new controller with fresh feature state.
  • Host path selection policy (numa, round-robin, queue-depth), reconnect timers and whether native multipath is used.
  • Target ANA group layout and state transitions (ownership, failover behaviour).
  • Discovery filtering per host, CDC zoning features, and how targets register with a CDC.
  • Default KATO values and Keep Alive send intervals.
  • ANA was introduced in the NVMe 1.4 timeframe (via Technical Proposal) and is part of the Base specification today.
  • Persistent discovery controllers, Discovery Log Change notices, explicit registration, CDC and automated discovery arrived through later Technical Proposals and were integrated into Base 2.x.
  • Discovery Log entry EFLAGS bits and some TSAS definitions were added after the original Fabrics 1.0 layout.
  • Authentication algorithm options were updated in the 2.4 set (PQC preparation).
  • The specification does not define how hosts choose among optimized paths, or how quickly they must fail over.
  • It does not mandate a CDC, nor any particular discovery address for a host to use.
  • It does not define allowed-host list configuration. That is target configuration, though Connect status values report the result.
  • Opcodes and structures for CDC registration and zoning, and the numeric path-related status values, must be read from the Base 2.4 document. They are named here, not numbered.
  • Never assume two paths are independent because they have different IP addresses. Check the physical topology.
  • Never assume a namespace seen through two controllers is the same storage unless its NGUID/EUI-64/UUID match.
  • Never assume Discovery Log entries are reachable from the host. Discovery reports addresses, not routability.
  • Never assume a reconnected controller has the same CNTLID or retains Set Features state.

Building and parsing a Discovery Log Page

This program builds the synthetic three-entry Discovery Log Page from the trace above, byte-exact at the offsets listed in the Engineering section, and parses it back. Standard library only, runs as written.

#!/usr/bin/env python3
"""disclog.py - build and parse a Discovery Log Page (Log Identifier 70h).
Synthetic teaching tool: the layout follows the Base specification's Discovery Log
Page (1024-byte header, 1024-byte entries); confirm offsets there before reuse."""
import struct

TRTYPE = {1: "rdma", 2: "fc", 3: "tcp", 0xFE: "loop"}
ADRFAM = {1: "ipv4", 2: "ipv6", 3: "ib", 4: "fc", 0xFE: "loop"}
SUBTYPE = {1: "referral (discovery)", 2: "nvm subsystem", 3: "current discovery subsystem"}
TREQ_SECURE = {0: "not specified", 1: "required", 2: "not required"}

def entry(trtype, adrfam, subtype, treq, portid, trsvcid, subnqn, traddr, cntlid=0xFFFF, asqsz=32):
    e = bytearray(1024)
    struct.pack_into("<BBBBHHH", e, 0, trtype, adrfam, subtype, treq, portid, cntlid, asqsz)
    e[32:32 + len(trsvcid)] = trsvcid.encode()         # TRSVCID, 32 bytes, ASCII
    e[256:256 + len(subnqn)] = subnqn.encode()          # SUBNQN, 256 bytes
    e[512:512 + len(traddr)] = traddr.encode()          # TRADDR, 256 bytes
    return bytes(e)                                    # TSAS (768-1023) left zero here

def log_page(genctr, entries):
    hdr = bytearray(1024)
    struct.pack_into("<QQH", hdr, 0, genctr, len(entries), 0)   # GENCTR, NUMREC, RECFMT
    return bytes(hdr) + b"".join(entries)

def cstr(b):
    return b.split(b"\0", 1)[0].decode()

def parse(page):
    genctr, numrec, recfmt = struct.unpack_from("<QQH", page, 0)
    print(f"Discovery Log Page: GENCTR={genctr} NUMREC={numrec} RECFMT={recfmt}")
    for i in range(numrec):
        e = page[1024 * (i + 1):1024 * (i + 2)]
        trtype, adrfam, subtype, treq, portid, cntlid, asqsz = struct.unpack_from("<BBBBHHH", e, 0)
        print(f"=====Discovery Log Entry {i}======")
        print(f"trtype:  {TRTYPE.get(trtype, hex(trtype))}")
        print(f"adrfam:  {ADRFAM.get(adrfam, hex(adrfam))}")
        print(f"subtype: {SUBTYPE.get(subtype, hex(subtype))}")
        print(f"treq:    secure channel {TREQ_SECURE.get(treq & 3, 'reserved')}"
              f"{', sq flow control disable supported' if treq & 4 else ''}")
        print(f"portid:  {portid}")
        print(f"trsvcid: {cstr(e[32:64])}")
        print(f"subnqn:  {cstr(e[256:512])}")
        print(f"traddr:  {cstr(e[512:768])}")
        print(f"cntlid:  0x{cntlid:04x}   asqsz: {asqsz}")

Path selection over ANA states

A simulation of the idea behind native multipath I/O policies: use the best ANA state available, then apply the policy. It is not Linux's exact algorithm.

#!/usr/bin/env python3
"""ana_paths.py - simulate host path selection over ANA states (simulation only).
Models the idea behind native NVMe multipath I/O policies; not Linux's exact algorithm."""
import itertools

USABLE = {"optimized": 0, "non-optimized": 1}          # lower is better; others unusable

class Path:
    def __init__(self, name, numa_node, ana_state):
        self.name, self.numa_node, self.ana_state, self.inflight = name, numa_node, ana_state, 0

def candidates(paths):
    usable = [p for p in paths if p.ana_state in USABLE]
    if not usable:
        return []
    best = min(USABLE[p.ana_state] for p in usable)    # use optimized paths if any exist
    return [p for p in usable if USABLE[p.ana_state] == best]

def choose(paths, policy, cpu_node, rr=itertools.count()):
    c = candidates(paths)
    if not c:
        return None                                    # queue I/O; wait for ANA change or timeout
    if policy == "numa":
        local = [p for p in c if p.numa_node == cpu_node]
        return (local or c)[0]
    if policy == "round-robin":
        return c[next(rr) % len(c)]
    if policy == "queue-depth":
        return min(c, key=lambda p: p.inflight)

def run(title, paths, policy, ios=6, cpu_node=0):
    picks = []
    for _ in range(ios):
        p = choose(paths, policy, cpu_node)
        picks.append(p.name if p else "QUEUED")
        if p:
            p.inflight += 1
    states = ", ".join(f"{p.name}={p.ana_state}" for p in paths)
    print(f"{title:<46} [{states}] policy={policy}\n   -> {' '.join(picks)}")

if __name__ == "__main__":
    mk = lambda a, b: [Path("A(192.0.2.20)", 0, a), Path("B(198.51.100.20)", 1, b)]
    run("1 both optimized, CPU on node 0", mk("optimized", "optimized"), "numa")
    run("2 both optimized", mk("optimized", "optimized"), "round-robin")
    run("3 A optimized, B non-optimized", mk("optimized", "non-optimized"), "round-robin")
    run("4 A inaccessible (controller failover)", mk("inaccessible", "non-optimized"), "round-robin")
    run("5 A in change, B persistent-loss", mk("change", "persistent-loss"), "numa")
    run("6 queue-depth balancing", mk("optimized", "optimized"), "queue-depth")

Worked example

Problem. An application issues 4 KiB random reads at 200,000 IOPS to NSID 1 through the two-path layout. Path A fails silently at t = 0 (a target node hangs, as in the abnormal trace). KATO = 5 s, Keep Alive is sent every 2.5 s, fast_io_fail_tmo = 5 s, and native multipath is on. Roughly how much I/O is delayed, and for how long, before path B absorbs it? What if KATO were 15 s?

Step 1: when does the host notice?

The worst case is a failure just after a successful Keep Alive. The next Keep Alive is sent at about 2.5 s and must complete within the keep alive timeout. Linux treats a Keep Alive not completed within KATO as failure. Implementation-dependent Detection is therefore between roughly KATO and KATO + the send interval: 5–7.5 s. I/O timeouts (default 30 s on Linux) are longer, so keep alive detects the failure first.

Step 2: how much I/O is caught?

With the numa policy and both paths optimized, I/O submitted from CPUs on node 0 goes to path A, about half of it.

Q = λ × f × Tdetect
Q
number of I/Os submitted to the failed path before detection, bounded by queue depth (see below)
λ
total I/O rate (200,000 per second)
f
fraction of I/O routed to path A (0.5)
Tdetect
time until the host declares path A failed (5–7.5 s)

Unbounded, Q would be 500,000–750,000, but this is not what happens. Once path A's queues fill, at queue depth × number of queues, say 4 queues × 128 = 512 commands, submissions to path A block. Applications on node-0 CPUs stall while their outstanding I/O waits. So the real impact is: about 512 I/Os stuck for 5–7.5 s, and all node-0 submitters stalled for that time. After detection, multipath requeues the 512 commands to path B and node-0 traffic flows there. Derived

Step 3: KATO = 15 s

Detection becomes 15–22.5 s. Same stuck count, three times longer stall. That is the cost of a KATO chosen to avoid spurious resets on a slow admin path.

Step 4: what would help?

  • A shorter KATO, if the target's admin path latency is reliably low.
  • The round-robin or queue-depth policy, so both nodes' CPUs use both paths. Then only part of every CPU's I/O stalls, and no CPU stalls completely, because queue-depth steers new I/O away from the stuck path as its queue fills.
  • Target-side health monitoring that sets the ANA state to Inaccessible on the surviving node's behalf, which some arrays do. That turns a silent hang into an orderly ANA event.

Senior engineer insight

Every NVMe-oF architecture review should walk through four scenarios with timings: a link failure on path A, a silent target-node hang, a switch reboot, and a planned controller failover. For each, write down who detects it (transport, keep alive, ANA, I/O timeout), when (with the configured timers), what the application sees (pause or error, and for how long), and how recovery happens. Most production surprises come from scenarios nobody walked through.

Host NQNs, allow lists, zoning, discovery entries and ANA group assignments are all configuration on different systems owned by different teams. Treat them like code: source of truth, review, automated validation (can every host reach every allowed subsystem on every expected path?), and alarms on drift.

Hosts trust ANA states. An array that reports Optimized on a path that actually forwards I/O internally, or that hangs instead of reporting Inaccessible, breaks multipath behaviour in ways no host setting can fix. Validate the array's ANA behaviour during failover tests with captures, not just with "I/O kept running".

What a senior engineer notices

Both "paths" here share one host, one loopback interface and one target kernel. The lab demonstrates protocol behaviour, not redundancy. A real redundancy test requires independent NICs, switches and target nodes, and a fault injected at each.

Failure variants

  • Two separate block devices instead of one: native multipath is off (nvme_core.multipath=N), so the two paths are not merged.
  • echo inaccessible fails: the port has no group with that ID. Use group 1, or create the group with mkdir and set the namespace's ana_grpid.
  • The real host is rejected too: /etc/nvme/hostnqn differs from what nvme-cli uses (for example, a config file override). Check with nvme show-hostnqn.

    • Change
    • Non-Optimized
    • Persistent Loss

    Persistent Loss is permanent. Inaccessible is temporary.

    • An NVM subsystem
    • The current discovery subsystem
    • A CDC registration

    1 = referral, 2 = NVM subsystem, 3 = current discovery subsystem.

    • In the Discovery Log entry
    • In ICReq

  6. What tells a host that two controllers expose the same namespace?

    • Same TRADDR

    NSIDs are per subsystem, and globally unique namespace identifiers confirm identity. CNTLIDs differ per controller by definition.

  7. Which mechanism answers "is this host really who it claims to be"?

    • Allowed-host list
    • DH-HMAC-CHAP in-band authentication
    • ANA
    • The Discovery Log Page
    Answer and reasoning

    Allow lists check the claimed NQN. Authentication proves it.

  8. With iopolicy numa and both paths optimized, a workload running only on node-0 CPUs will:

    • Mostly use the path associated with node 0
    • Split I/O evenly
    • Use the non-optimized path
    • Fail over continuously
    Answer and reasoning

    The numa policy prefers the path closest to the submitting CPU's node.

  9. Open: why can keep alive turn a slow target into a "failed" one, and how do you tell the difference in a capture?

    Model answer

    If the controller does not complete Keep Alive within KATO, the host tears down the association even though the target might have recovered. In a capture, a slow target eventually completes the Keep Alive (late) or completes other commands. A hung target shows TCP ACKs with no NVMe responses at all, and often no ICResp on reconnect.

  10. Open: what does a CDC add over per-array discovery controllers?

    Model answer

    One discovery address for the whole fabric, registration of hosts and subsystems, centralized zoning (which hosts see which subsystems), persistent connections with change notifications, and automated discovery of the CDC itself. That removes per-host configuration of every array.

Interview questions

  1. Beginner: What is an NQN and who has one?

    Model answer

    An NVMe Qualified Name: a globally unique string identifying an NVM subsystem or a host, in domain-based or UUID-based format, at most 223 bytes. Subsystems, hosts and discovery subsystems have NQNs.

  2. Beginner: How does a host find NVMe-oF storage?

    Model answer

    It connects to a discovery controller (often TCP port 8009) using the well-known discovery NQN, reads the Discovery Log Page (70h), and connects to the listed subsystems at their transport addresses.

  3. Intermediate: Explain ANA states and how a host uses them.

    Model answer

    Per controller and ANA group: Optimized, Non-Optimized, Inaccessible, Persistent Loss, Change. Hosts read them from log page 0Ch, update them on ANA change AENs, send I/O to optimized paths, fall back to non-optimized, avoid inaccessible or lost paths, and wait during Change up to ANATT.

  4. Intermediate: Compare persistent and non-persistent discovery.

    Model answer

    Non-persistent: connect, read, disconnect, with KATO 0. The host must re-run discovery to see changes. Persistent: keep the association with keep alive, arm an AER, and receive Discovery Log Change notices to re-read. Changes are learned promptly, at the cost of a long-lived connection.

  5. Advanced: A customer's I/O stalls for ~7 s whenever one array node reboots. Explain and propose fixes.

    Model answer

    The node hangs or disappears without ANA notification, so the host detects it via keep alive (KATO 5 s plus send interval). With the numa policy, CPUs bound to that path stall. Fixes: array-side ANA notification before planned reboots, round-robin or queue-depth policy, tuned KATO and fast_io_fail_tmo, and confirmed independent paths.

  6. Advanced: How do authorization, authentication and TLS differ, and which failures does each produce?

    Model answer

    Authorization (allow list by host NQN): Connect Invalid Host. Authentication (DH-HMAC-CHAP via Authentication Send/Receive after Connect): failed authentication transaction, and commands refused. TLS (NVMe/TCP): handshake failure before ICReq. They answer "allowed?", "really you?" and "private and untampered?" respectively.

  7. Senior: Design discovery and multipathing for 500 hosts and 20 arrays on a dual-fabric Ethernet network.

    Model answer

    A CDC per fabric (or a redundant CDC pair), with arrays registering their subsystems and hosts registering. Zoning managed as code. Hosts use persistent discovery to both CDCs, with change notifications. Each array exposes every subsystem on both fabrics with correct ANA groups. Hosts use native multipath with queue-depth or round-robin. Reconnect delays are staggered to avoid storms. Monitor path counts per host and alarm when below two. Use authentication (DH-HMAC-CHAP) and TLS according to the threat model.

  8. Senior: What would you put in an NVMe-oF failover test plan?

    Model answer

    Faults: host NIC down, cable pull, switch reboot, target port down, target node hang (not crash), planned ownership move, discovery service loss, CDC failover. For each: expected detector, expected time, ANA states observed, path-related statuses, application-visible pause or error, recovery time, and captures on both fabrics. Repeat under load and at scale, with timer variants.

  • To a junior engineer: explain discovery and connection from nvme discover to a multipath block device.

Model explanations

Child: "The information desk gives you a list of libraries and their doors. Every library and every reader has a long special name. Some libraries have two counters for the same books, and a sign says which counter is best. If you go quiet for too long, the librarian assumes you left."

Junior: "nvme discover connects to the discovery controller and reads log page 70h, which lists each subsystem's NQN, transport, address and port. nvme connect (or connect-all) makes one controller per entry, with admin and I/O queues each on its own connection. Because both controllers report the same namespace identifiers, the kernel merges them into one /dev/nvmeXnY with two paths, and chooses between them using ANA states and the iopolicy."

Senior: "The most graceful detection is ANA: the array announces a change, hosts reroute, and I/O barely pauses. Next is path-related status on individual commands, which gives immediate per-command retry. Then keep alive, which costs up to KATO plus the send interval of stall on silent failures. Worst is I/O timeout, at tens of seconds. Architecture work is about pushing every fault class up this list."

Chapter summary

  • Host → fabric → target → subsystem → controller → namespace. Each layer has its own identifier: host NQN and HOSTID, transport address, port, subsystem NQN, CNTLID, NSID plus NGUID/EUI-64/UUID.
  • Discovery controllers serve the Discovery Log Page (70h). Entries give TRTYPE, ADRFAM, SUBTYPE, TREQ, PORTID, TRSVCID, SUBNQN and TRADDR. GENCTR protects consistency. Referrals chain discovery.
  • Persistent discovery and CDCs add change notification, registration and zoning for large fabrics.
  • Keep alive (KATO in Connect, Keep Alive 18h) bounds association lifetime. Host reconnect policy is implementation-defined.
  • ANA (log 0Ch, five states, groups, AENs, path-related status) lets hosts route I/O across asymmetric paths. Native multipath applies an I/O policy on top.
  • Authorization, authentication (DH-HMAC-CHAP) and transport security (TLS) are separate layers with distinct failure signatures.
