A storage failure is almost never reported by the layer that caused it. An application times out, a filesystem remounts read-only, the NVMe driver resets the controller, an Advanced Error Reporting (AER) message scrolls past — and the real cause sits in one of seven places: software, driver, NVMe, PCIe transaction, link, firmware or media. This chapter teaches the discipline that tells them apart: one timeline, the first abnormal event, evidence per layer, and decision trees — practised on six complete worked cases.

Why this chapter exists

Chapters 42–46 each taught one source of evidence: interrupts, MSI-X tables, NVMe status, PCIe errors, AER registers. Real incidents arrive as a pile of all of them at once, out of order, with different clocks, plus noise from recovery actions. A junior engineer reads the loudest line in the log and files a bug against whoever printed it. A senior engineer builds a timeline, finds the first thing that went wrong, and asks which layer could have produced it.

The difference is not knowledge of more registers. It is method. This chapter is that method.

Learning objectives

  • Name the seven failure domains (software, driver, NVMe protocol, PCIe transaction, link, firmware, media) and the evidence signature of each.
  • Build a unified timeline from kernel log, NVMe tracepoints, AER registers, NVMe logs and a protocol-analyzer capture, including clock alignment.
  • Apply first-abnormal-event discipline: separate cause from cascade, and absence from presence.
  • Use decision trees to move from symptom to layer to root cause, and know which experiment disambiguates two candidate layers.
  • Read the common Linux cascade: AER event → NVMe I/O timeout → abort → controller reset → recovery or removal.
  • Write a root-cause statement with evidence, confidence and a regression test.

The story

One morning the class goldfish is found on the floor. Everybody has a story. The cleaner says the window was open. The teacher says the tank was knocked. A child says the cat came in. Someone noticed the water was low yesterday.

A good detective does not believe the loudest person. She makes a list of everything that happened, in order, with times. Then she asks: what was the very first strange thing? Water low yesterday afternoon — that came before the open window, the cat, and the knocked tank. A fish with little water jumps. Everything else happened after.

She also checks things that didn't happen: the fish food was untouched, so nobody fed it. "Nothing happened" can be a clue too.

Error correlation is accident investigation in aviation. Investigators gather the flight data recorder (analyzer trace), the cockpit voice recorder (kernel log), maintenance logs (SMART, error logs), air traffic control tapes (AER at the root port) and wreckage (register dumps after the fact). They synchronise every source to one clock, find the first deviation from normal operation, and then build the causal chain forward from it — refusing to stop at the dramatic final events, which are consequences.

Hides: unlike an aircraft, most systems have no flight data recorder running; you usually have only the logs that happened to be enabled, and recovery actions (resets) actively destroy evidence. Misleads: "first abnormal event" means the first one you can observe. The true first cause may predate every log (a firmware bug latent since boot, a cracked solder joint). The first observed event narrows the search; it does not always end it.

Each domain leaves its own kind of fingerprints. The method is always the same:

  1. Collect everything before anyone resets or reboots.
  2. Line it up on one timeline.
  3. Find the first abnormal event — the earliest thing that differs from normal.
  4. Ask which domain could produce that event, using the fingerprints.
  5. Test the hypothesis with an experiment that would come out differently if you were wrong.

Building one timeline

Every source has its own clock. Before any reasoning, convert all events to one timebase.

  • Kernel sources (dmesg, tracepoints) share the monotonic clock. Use raw dmesg seconds-since-boot, not dmesg -T, whose wall-clock conversion drifts after suspend.
  • Analyzer: align using an event visible in both. A practical marker: write a string to /sys/kernel/tracing/trace_marker, then immediately issue a distinctive admin command (for example Get Features for an unusual Feature Identifier); trigger the analyzer on that command's SQE fetch; the offset between the two timestamps is your alignment, accurate to a few microseconds.
  • Controller time: NVMe logs that carry timestamps (if the host has set the Timestamp feature) use the controller's clock; align via a known event such as the last controller reset.
  • Platform logs: BMC clocks can be minutes off; align on a shared event (a reboot, a link-down that the BMC also logs).
tcommon = tsource + Δsource ± εsource
tcommon
time of the event on the chosen common timebase (usually kernel monotonic seconds)
tsource
timestamp as recorded by the source (analyzer, BMC, controller)
Δsource
offset measured from a marker event seen by both the source and the common timebase
εsource
alignment uncertainty: the jitter of the marker method (µs for trace_marker + analyzer trigger; seconds for BMC logs)

Never order two events from different sources whose difference is smaller than the combined alignment uncertainty. If ε says "±2 s", an AER message and an NVMe timeout one second apart are simultaneous for reasoning purposes.

First-abnormal-event discipline

Rules:

  1. Write down the expected sequence first (from Chapter 39): doorbell → SQE fetch → PRP fetch → data → CQE → interrupt → head doorbell. Deviations are only visible against expectations.
  2. Absence is an event. A missing SQE fetch, completion, interrupt or ACK is timestamped by when it should have occurred.
  3. Walk forward in time, not backward from the loudest symptom. Mark the first event that deviates. Everything after it is suspect as consequence.
  4. Distinguish cascade from coincidence. Ask: could event A cause event B through a known mechanism? If not, they may be independent, and you may have two problems.
  5. Exclude recovery noise. After a reset begins, you will see all-ones reads, Completion Timeouts, link down/up, aborted commands, configuration reads. These are expected effects of recovery.
  6. Record confidence. "First abnormal event observed" is not "root cause". Say what could precede it unobserved.

The central concept on the ladder

Find the first strange thing that happened, not the loudest one.

Merge all evidence onto one timeline; the earliest deviation from the expected command life cycle points to the failing domain; later events are usually cascade.

Each hardware block leaves specific evidence: PHY/DLL in correctable counters and LTSSM; transaction layer in AER uncorrectable bits and header logs; controller in CSTS, CQE status and NVMe logs; host in IOMMU faults and interrupt counters.

Specifications define the meaning of each piece of evidence (status codes, AER bits, CSTS fields) — not causality. Causal reasoning is derived and must be labelled as such.

Protocol order is the backbone of the timeline: doorbell, fetch, data, CQE, interrupt, head doorbell; non-posted requests and their completions; ACK/NAK.

In a capture, mark the expected sequence per command and diff; the first missing or wrong packet is the anchor. Align with kernel events via a marker.

Root-cause statement: first abnormal event, mechanism to symptom, evidence for, evidence against, confidence, fix, regression test.

The 16 questions for "the first abnormal event"

1. What is it?
The earliest observed event that deviates from the expected behaviour of the system.
2. Why was it created (as a practice)?
Because failure cascades bury causes under consequences; the earliest deviation is closest to the cause.
3. What problem does it solve?
Misattribution to the loudest or last component.
4. What existed before it?
Symptom-driven debugging: start at the error message and guess.
5. Why is it better?
It is falsifiable and repeatable: two engineers with the same timeline reach the same anchor.
6. Who creates it?
The engineer, from merged evidence.
7. Who consumes it?
Root-cause analysis, bug reports, the owning team (vendor, driver, platform).
8. Where does it live?
In the incident timeline document.
9. What memory/registers are involved?
All evidence sources: logs, AER, CSTS, NVMe logs, capture buffers.
10. What happens before it?
Normal operation (or unobserved latent faults).
11. What happens after it?
The cascade: timeouts, resets, errors in other layers.
12. What happens if it is wrong?
You fix a symptom; the failure recurs; the wrong team owns the bug.
13. What does the protocol analyzer show?
The first missing or malformed packet relative to the expected sequence.
14. What does Linux show?
The earliest relevant kernel message — often an AER or IOMMU line, minutes or seconds before the timeouts.
15. What would a validation engineer test?
That injecting the identified first event reproduces the full cascade; that the fix prevents it.
16. What would a senior engineer suspect when it fails?
Missing evidence (logs not enabled, clocks misaligned, rate-limited messages), a latent earlier fault, or two independent problems.
