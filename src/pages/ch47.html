A storage failure is almost never reported by the layer that caused it. An application times out, a filesystem remounts read-only, the NVMe driver resets the controller, an Advanced Error Reporting (AER) message scrolls past — and the real cause sits in one of seven places: software, driver, NVMe, PCIe transaction, link, firmware or media. This chapter teaches the discipline that tells them apart: one timeline, the first abnormal event, evidence per layer, and decision trees — practised on six complete worked cases.

Why this chapter exists

Chapters 42–46 each taught one source of evidence: interrupts, MSI-X tables, NVMe status, PCIe errors, AER registers. Real incidents arrive as a pile of all of them at once, out of order, with different clocks, plus noise from recovery actions. A junior engineer reads the loudest line in the log and files a bug against whoever printed it. A senior engineer builds a timeline, finds the first thing that went wrong, and asks which layer could have produced it.

The difference is not knowledge of more registers. It is method. This chapter is that method.

Learning objectives

  • Name the seven failure domains (software, driver, NVMe protocol, PCIe transaction, link, firmware, media) and the evidence signature of each.
  • Build a unified timeline from kernel log, NVMe tracepoints, AER registers, NVMe logs and a protocol-analyzer capture, including clock alignment.
  • Apply first-abnormal-event discipline: separate cause from cascade, and absence from presence.
  • Use decision trees to move from symptom to layer to root cause, and know which experiment disambiguates two candidate layers.
  • Read the common Linux cascade: AER event → NVMe I/O timeout → abort → controller reset → recovery or removal.
  • Write a root-cause statement with evidence, confidence and a regression test.

The story

One morning the class goldfish is found on the floor. Everybody has a story. The cleaner says the window was open. The teacher says the tank was knocked. A child says the cat came in. Someone noticed the water was low yesterday.

A good detective does not believe the loudest person. She makes a list of everything that happened, in order, with times. Then she asks: what was the very first strange thing? Water low yesterday afternoon — that came before the open window, the cat, and the knocked tank. A fish with little water jumps. Everything else happened after.

She also checks things that didn't happen: the fish food was untouched, so nobody fed it. "Nothing happened" can be a clue too.

Error correlation is accident investigation in aviation. Investigators gather the flight data recorder (analyzer trace), the cockpit voice recorder (kernel log), maintenance logs (SMART, error logs), air traffic control tapes (AER at the root port) and wreckage (register dumps after the fact). They synchronise every source to one clock, find the first deviation from normal operation, and then build the causal chain forward from it — refusing to stop at the dramatic final events, which are consequences.

Hides: unlike an aircraft, most systems have no flight data recorder running; you usually have only the logs that happened to be enabled, and recovery actions (resets) actively destroy evidence. Misleads: "first abnormal event" means the first one you can observe. The true first cause may predate every log (a firmware bug latent since boot, a cracked solder joint). The first observed event narrows the search; it does not always end it.

  2. Line it up on one timeline.
  3. Find the first abnormal event — the earliest thing that differs from normal.

  5. Test the hypothesis with an experiment that would come out differently if you were wrong.

Building one timeline

Every source has its own clock. Before any reasoning, convert all events to one timebase.

  • Kernel sources (dmesg, tracepoints) share the monotonic clock. Use raw dmesg seconds-since-boot, not dmesg -T, whose wall-clock conversion drifts after suspend.
  • Analyzer: align using an event visible in both. A practical marker: write a string to /sys/kernel/tracing/trace_marker, then immediately issue a distinctive admin command (for example Get Features for an unusual Feature Identifier); trigger the analyzer on that command's SQE fetch; the offset between the two timestamps is your alignment, accurate to a few microseconds.
  • Controller time: NVMe logs that carry timestamps (if the host has set the Timestamp feature) use the controller's clock; align via a known event such as the last controller reset.
  • Platform logs: BMC clocks can be minutes off; align on a shared event (a reboot, a link-down that the BMC also logs).
tcommon = tsource + Δsource ± εsource
tcommon
time of the event on the chosen common timebase (usually kernel monotonic seconds)
tsource
timestamp as recorded by the source (analyzer, BMC, controller)
Δsource
offset measured from a marker event seen by both the source and the common timebase
εsource
alignment uncertainty: the jitter of the marker method (µs for trace_marker + analyzer trigger; seconds for BMC logs)

Never order two events from different sources whose difference is smaller than the combined alignment uncertainty. If ε says "±2 s", an AER message and an NVMe timeout one second apart are simultaneous for reasoning purposes.

First-abnormal-event discipline

Rules:

  1. Write down the expected sequence first (from Chapter 39): doorbell → SQE fetch → PRP fetch → data → CQE → interrupt → head doorbell. Deviations are only visible against expectations.
  2. Absence is an event. A missing SQE fetch, completion, interrupt or ACK is timestamped by when it should have occurred.
  3. Walk forward in time, not backward from the loudest symptom. Mark the first event that deviates. Everything after it is suspect as consequence.
  4. Distinguish cascade from coincidence. Ask: could event A cause event B through a known mechanism? If not, they may be independent, and you may have two problems.
  5. Exclude recovery noise. After a reset begins, you will see all-ones reads, Completion Timeouts, link down/up, aborted commands, configuration reads. These are expected effects of recovery.
  6. Record confidence. "First abnormal event observed" is not "root cause". Say what could precede it unobserved.

The central concept on the ladder

Find the first strange thing that happened, not the loudest one.

Merge all evidence onto one timeline; the earliest deviation from the expected command life cycle points to the failing domain; later events are usually cascade.

Each hardware block leaves specific evidence: PHY/DLL in correctable counters and LTSSM; transaction layer in AER uncorrectable bits and header logs; controller in CSTS, CQE status and NVMe logs; host in IOMMU faults and interrupt counters.

Specifications define the meaning of each piece of evidence (status codes, AER bits, CSTS fields) — not causality. Causal reasoning is derived and must be labelled as such.

Protocol order is the backbone of the timeline: doorbell, fetch, data, CQE, interrupt, head doorbell; non-posted requests and their completions; ACK/NAK.

In a capture, mark the expected sequence per command and diff; the first missing or wrong packet is the anchor. Align with kernel events via a marker.

Root-cause statement: first abnormal event, mechanism to symptom, evidence for, evidence against, confidence, fix, regression test.

The 16 questions for "the first abnormal event"

1. What is it?
The earliest observed event that deviates from the expected behaviour of the system.
2. Why was it created (as a practice)?
Because failure cascades bury causes under consequences; the earliest deviation is closest to the cause.
3. What problem does it solve?
Misattribution to the loudest or last component.
4. What existed before it?
Symptom-driven debugging: start at the error message and guess.
5. Why is it better?
It is falsifiable and repeatable: two engineers with the same timeline reach the same anchor.
6. Who creates it?
The engineer, from merged evidence.
7. Who consumes it?
Root-cause analysis, bug reports, the owning team (vendor, driver, platform).
8. Where does it live?
In the incident timeline document.
9. What memory/registers are involved?
All evidence sources: logs, AER, CSTS, NVMe logs, capture buffers.
10. What happens before it?
Normal operation (or unobserved latent faults).
11. What happens after it?
The cascade: timeouts, resets, errors in other layers.
12. What happens if it is wrong?
You fix a symptom; the failure recurs; the wrong team owns the bug.
13. What does the protocol analyzer show?
The first missing or malformed packet relative to the expected sequence.
14. What does Linux show?
The earliest relevant kernel message — often an AER or IOMMU line, minutes or seconds before the timeouts.
15. What would a validation engineer test?
That injecting the identified first event reproduces the full cascade; that the fix prevents it.
16. What would a senior engineer suspect when it fails?
Missing evidence (logs not enabled, clocks misaligned, rate-limited messages), a latent earlier fault, or two independent problems.

Hardware view

Correlation is easier when you know which hardware block could have produced each piece of evidence, and which blocks are blind spots.

  • Blind spots: inside the root complex (between root port and memory controller), inside the controller (between front end and media), and any link not covered by the analyzer. Errors there are inferred from the edges.
  • Evidence destroyers: controller reset (CSTS, queues, volatile logs), link reset (in-flight TLPs), reboot (dmesg ring unless persisted), firmware-first handlers (clear AER), power cycles (controller volatile state, sometimes telemetry).

Specification view

No specification defines "error correlation". It draws on all of them:

  • NVM Express Base Specification, Revision 2.4 — status values, Error Information log, Asynchronous Events, Controller Status, Telemetry log, Timestamp feature
  • NVMe over PCIe Transport Specification, Revision 1.4 — queue and doorbell mechanics on PCIe, interrupts
  • PCI Express Base Specification, Revision 6.x/7.0 — Error Signaling and Logging; AER; Data Link Layer retry; Completion Timeout

Each piece of evidence used in this chapter has a defined meaning in its specification: NVMe status codes, CSTS.CFS, Error Information log; PCIe error classes, AER status bits, header log, completion status. Those meanings are normative.

Every causal link in this chapter — "this Completion Timeout caused that NVMe timeout" — is derived reasoning. Label it as such in bug reports, with the mechanism stated.

Linux timeout values, retry policies, message formats and recovery sequences; controller logging depth; platform error handling (OS-first vs firmware-first) are implementation-dependent and change the evidence you get.

Kernel message formats (e.g. NVMe timeout lines that now include opcode names and request ops), tracepoint fields, and nvme-cli output change across versions; NVMe log pages (telemetry, persistent event log) vary by revision and by what the controller supports.

The specifications do not say how long a host should wait before declaring a command lost, which layer to blame, or how errors in one specification map to errors in another — except where the NVMe over PCIe Transport describes NVMe reporting of transport errors. Check that document for your controller's revision.

Never write "root cause: PCIe error" or "root cause: NVMe timeout". Those are evidence categories. A root cause names a mechanism and a component: "riser connector on lane 2 marginal at Gen4 causing replay storms".

Linux view

Collect before you touch. A minimal incident-capture script (read-only; run as root; writes only to a local directory):

#!/bin/sh
# Capture NVMe/PCIe evidence for one SSD and its upstream port. Read-only.
D=${1:-0000:01:00.0}; OUT=incident-$(date +%s); mkdir -p "$OUT"
RP=$(basename "$(dirname "$(readlink -f /sys/bus/pci/devices/$D)")")
cat /proc/uptime                                   > "$OUT/uptime"
dmesg                                              > "$OUT/dmesg.txt"        # raw monotonic stamps
lspci -vvv -s "$D"                                 > "$OUT/lspci_dev.txt"
lspci -vvv -s "$RP"                                > "$OUT/lspci_rp.txt"
grep . /sys/bus/pci/devices/$D/aer_dev_* 2>/dev/null > "$OUT/aer_counters.txt"
grep -E 'nvme' /proc/interrupts                    > "$OUT/interrupts.txt"
CTRL=$(ls /sys/bus/pci/devices/$D/nvme 2>/dev/null | head -1)
if [ -n "$CTRL" ]; then
  nvme show-regs /dev/$CTRL -H                     > "$OUT/regs.txt" 2>&1
  nvme error-log /dev/$CTRL -e 64                  > "$OUT/error_log.txt" 2>&1
  nvme smart-log /dev/$CTRL                        > "$OUT/smart.txt" 2>&1
fi
echo "saved to $OUT"

Code / pseudocode

Timeline merger and first-abnormal-event finder

Standard-library Python. It merges events from several sources (each with its own clock offset and uncertainty), sorts them, flags the first abnormal event using simple rules, and applies a miniature version of the master decision tree. The embedded data is a synthetic incident. Run as written.

#!/usr/bin/env python3
"""Merge multi-source NVMe/PCIe evidence onto one timeline and find the
first abnormal event. Synthetic data; rules are deliberately simple."""
from dataclasses import dataclass

@dataclass
class Ev:
    t: float      # seconds on the source's clock
    src: str      # K=kernel log, T=tracepoint, A=analyzer, B=BMC
    kind: str
    text: str

# source -> (offset to kernel-monotonic seconds, uncertainty seconds)
CLOCKS = {"K": (0.0, 0.0), "T": (0.0, 0.0), "A": (8806.976800, 5e-6), "B": (-3.2, 2.0)}

EVENTS = [
    Ev(8812.079500, "T", "setup",   "qid=3 cid=0x20b opcode=0x01"),
    Ev(5.103200, "A", "link",    "root port NAK x40, replay; RxErr lane 2"),
    Ev(5.103900, "A", "link",    "LTSSM Recovery entered (REPLAY_NUM rollover)"),
    Ev(5.104100, "A", "missing", "SSD MRd tag 0x31 (PRP list): no completion"),
    Ev(8812.104311, "K", "aer",  "Non-Fatal from 01:00.0: CmpltTO (First)"),
    Ev(8817.0, "B",  "sel",      "PCIe correctable threshold exceeded, slot 3"),
    Ev(8842.497120, "K", "nvme", "I/O tag 523 QID 3 timeout, aborting"),
    Ev(8872.705002, "K", "nvme", "I/O tag 523 QID 3 timeout, reset controller"),
    Ev(8873.011020, "K", "blk",  "I/O error, dev nvme0n1, op WRITE"),
]

ABNORMAL = {"link", "missing", "aer", "sel", "nvme", "blk", "iommu", "cfs", "status"}
DOMAIN_RULES = [  # (kind, keyword, domain)  first match wins, applied to first abnormal
    ("link", "",          "LINK (signal integrity / training)"),
    ("missing", "MRd",    "PCIe transaction: completer/path did not answer"),
    ("iommu", "",         "DRIVER (DMA mapping)"),
    ("cfs", "",           "FIRMWARE"),
    ("status", "sct 0x2", "MEDIA"),
    ("aer", "UnsupReq",   "PCIe transaction (check header: often DRIVER mapping)"),
    ("aer", "CmpltTO",    "PCIe transaction (victim); look at completer/link"),
    ("nvme", "polled",    "DRIVER / interrupt path"),
    ("nvme", "timeout",   "UNKNOWN: a timeout is a symptom; look earlier"),
]

def merged():
    out = []
    for e in EVENTS:
        off, eps = CLOCKS[e.src]
        out.append((e.t + off, eps, e))
    return sorted(out, key=lambda x: x[0])

def classify(e):
    for kind, kw, dom in DOMAIN_RULES:
        if e.kind == kind and kw.lower() in e.text.lower():
            return dom
    return "UNCLASSIFIED"

def main():
    tl = merged()
    first = None
    print(f"{'time (kernel s)':>16}  {'±':>8}  src  event")
    for t, eps, e in tl:
        flag = ""
        if e.kind in ABNORMAL and first is None:
            first, flag = (t, eps, e), "  <== FIRST ABNORMAL"
        print(f"{t:16.6f}  {eps:8.0e}  {e.src:3s}  {e.kind:7s} {e.text}{flag}")
    if first:
        t, eps, e = first
        print("\nfirst abnormal event:", e.text)
        print("suggested domain   :", classify(e))
        close = [x for x in tl if x[2] is not e and abs(x[0] - t) <= eps + x[1]]
        if close:
            print("warning: events within alignment uncertainty of the anchor:")
            for x in close:
                print("   ", x[2].src, x[2].text)

if __name__ == "__main__":
    main()

The BMC event (±2 s) cannot be ordered against kernel events closer than 2 s; the tool warns rather than pretends. Replace EVENTS with parsed real data to use it on your own incidents.

7RafterLnkSta8GT/s x4 (downgraded)Link retrained at a lower speed

First abnormal event. Row 3 for the incident; row 2 shows the condition existed long before. Hypotheses. (a) Link signal integrity (riser, connector, retimer); (b) SSD firmware stalling the link; (c) host-side root port defect. Evidence for (a): correctable errors logged by the root port's receiver (device→host direction corrupted), rollover, speed downgrade; errors accelerate with temperature in SEL. Against (b): CSTS valid after reset, no CFS, SMART clean; NVMe errors only after the link failure. Against (c): moving the same drive to a direct-attached slot makes errors stop; a different drive in the riser shows the same errors (fault follows the riser).

Root cause. Marginal signal integrity on the riser at 16 GT/s, worsening with temperature, causing replay storms and rollovers; during repeated Recovery, an upstream completion for the SSD's PRP-list read was lost, producing a Completion Timeout, a stuck WRITE, an NVMe I/O timeout and a controller reset. Domain: link.

Corrective action. Replace the riser with a qualified part; monitor correctable error rates per root port with an alert threshold. Regression test. 48-hour soak at elevated inlet temperature with fio mixed load; pass criterion: zero rollovers, correctable rate below the platform's baseline, link remains at 16 GT/s x4. Confidence. High (fault follows the riser; mechanism explains every row).

Case 4 — Media: unrecoverable reads on a cluster of LBAs

Symptom. A nightly backup fails reading one file; dmesg shows NVMe errors with "Unrecovered Read Error"; the operations team suspects "PCIe problems" because the server recently had a riser replaced.

Case 5 — Driver, with evidence in the PCIe transaction layer: PRP list use-after-free

Symptom. Under a new out-of-tree storage module, rare WRITE failures with "Data Transfer Error"; IOMMU fault messages; one AER UR at the root port.

Timeline. As in the abnormal merged timeline in the Trace view above: the SSD's MRd for a PRP list at IOVA 0x1_5000_2000 gets a UR completion (first abnormal event), the IOMMU logs a read fault for that IOVA, the root port logs UR with a header naming the SSD's MRd, the SSD completes the WRITE with SCT 0h SC 04h.

Hypotheses. (a) Host freed/unmapped the PRP-list page before the device fetched it; (b) the SSD computed a wrong PRP-list address; (c) IOMMU hardware fault. Evidence. The nvme_setup_cmd tracepoint shows PRP2 = 0x1_5000_2000 for that CID — the SSD used exactly what the host gave it, refuting (b). Kernel debug (DMA API debugging) shows the module unmapped that page on a completion path for a different command that shared the PRP-list pool — supports (a). (c) has no supporting evidence and the fault reproduces on two platforms. Root cause. Module returned PRP-list pages to its pool on submission failure of a sibling command, while the original command was still in flight. Domain: driver (the PCIe layer is where the symptom appeared). Corrective action. Fix reference counting of PRP-list pages; enable DMA-API debugging in CI. Regression test. Fault-injection test that forces sibling submission failures under load with IOMMU strict mode; zero IOMMU faults and zero Data Transfer Errors. Confidence. High.

Symptom. p99 latency for a service's 4 KiB reads jumped from 0.2 ms to 25 ms after a platform rollout. The team opened a ticket against the SSD vendor.

Case 7 — NVMe protocol implementation: phase tag not inverted after wrap

Symptom. On a pre-production drive, exactly after 1024 completions on a freshly created queue (QSIZE 1024), that queue's next command times out; "completion polled" does not appear.

#SrcTimeEventFieldsMeaning
1At0MWr64CQ1 slot 1023, P=1Last entry of the first pass
2At0+80 µsMWr64CQ1 slot 0, P=1, CID 0x0400, status 0First abnormal event: second pass must use P=0
3At0+80 µsMWr32MSI-X vector 1Interrupt correctly sent
4K+30 snvmeI/O … QID 1 timeout, abortingDriver saw slot 0 with stale-looking phase, ignored it

Hypotheses. (a) Controller failed to invert the Phase Tag on wrap; (b) host initialised the CQ memory wrongly; (c) interrupt problem. Evidence. The interrupt arrived (row 3) — refutes (c). The host zeroes CQ memory at creation (P=0 everywhere), so the first pass must use P=1 and the second P=0; row 2 shows P=1 on the second pass — the controller's phase logic is wrong. The driver's polling on timeout also sees P=1 at slot 0 and treats it as old, so no "completion polled". Root cause. Firmware failed to toggle its CQ phase on wrap-around for queues whose size equals 1024 (an off-by-one in the wrap check). Domain: NVMe protocol implementation in the controller (firmware). Corrective action. Firmware fix. Regression test. For every supported queue size, run ≥ 3 full wraps of each CQ and check phase alternation in a capture or with a user-space driver. Confidence. High. See Queue Architecture for phase-tag rules.

In every case the loudest message (timeout, reset, I/O error) was a consequence. In four of seven, the domain where the evidence appeared (PCIe, NVMe) was not the domain of the root cause (link, driver, firmware, software). And in three, the first abnormal event was an absence.

Common mistakes

  • Starting from the last, loudest error message.
  • Treating "NVMe timeout" as a root cause.
  • Using dmesg -T wall-clock times to order events against other sources.
  • Ordering events closer together than the alignment uncertainty.
  • Rebooting before capturing AER, NVMe logs and registers.
  • Assuming the component that logged an error caused it.
  • Ignoring absences: missing fetches, completions, interrupts, unmasks.
  • Stopping at the first plausible cause without evidence against the alternatives.
  • Missing a second, independent problem hidden in the cascade.
  • Not writing a regression test: without it, the fix is a hope.

Senior engineer insight

  • Evidence first, opinions later. In an incident call, the first deliverable is the merged timeline, not a theory.
  • Every claim gets a source. "Link is fine" needs: AER confirmed operating, counters zero, LnkSta at capability, no Recovery in the capture.
  • Name the mechanism. A root cause that does not explain every row of the timeline is incomplete.
  • Seek disconfirming evidence. Design the experiment that would prove you wrong. If it doesn't, your confidence goes up honestly.
  • Make evidence automatic. Tracepoints, persistent journals, incident-capture hooks, correctable-error rate monitoring. The next incident should arrive with its own timeline.
  • Ownership follows root cause, not evidence. Route the bug to the team that owns the mechanism, with the timeline attached.

Lab

Trace Lab 47 — The poisoned write

Safe lab Paper/simulation lab: all evidence is provided below as synthetic data. No hardware access needed. Optional: run correlate.py with this data.

Scenario

A storage node reports sporadic WRITE failures on nvme0 at night. The application retries succeed. The SSD vendor is blamed.

System configuration

Lab system: x86-64, Linux, IOMMU on, OS-first AER. Root port 00:01.1, SSD 01:00.0.

PCIe generation

Gen4 (16 GT/s).

Link width

x4.

NVMe device

Lab SSD, MSI-X 33 vectors, namespace 1 with 512-byte LBAs.

Expected operation

WRITE: doorbell → SQE fetch → PRP/data MRd by the SSD → CplD from host with data → CQE status 0 → MSI-X.

  2. Decode the AER header in row 5 as far as you can. What kind of TLP is it?
  3. Why did the retry succeed?

First abnormal event, hypotheses, evidence, root cause, corrective action, regression test

First abnormal event. Row 1 — the EDAC uncorrectable memory error — precedes and explains row 4 (CplD with EP=1). If you only had the analyzer, row 4 would be your first abnormal event.

Header decode. 0x4A00_4040 → Fmt 010, Type 01010 → CplD; EP bit (DW0 bit 14) = 1 → poisoned; Length 0x040 = 64 DW (256 B). DW1 0x0009_0100 → Completer ID 0x0009 (root port/RC), status SC, byte count 0x100. DW2 0x0100_1200 → Requester 0x0100, Tag 0x12. It is exactly row 4.

Hypotheses. (a) Host memory uncorrectable error; (b) SSD fault; (c) link corruption. Evidence. Poisoning is applied by the sender who knew the data was bad — the root complex — not by link corruption (that would be a Bad TLP, LCRC). EDAC names a DIMM at the same time. The SSD behaved correctly: logged Poisoned TLP Received, did not commit the data, returned Data Transfer Error. The retry succeeded because the application rewrote the buffer (or the memory controller corrected/retired the location).

Root cause. Uncorrectable error in host DIMM B2; domain: platform memory — outside the seven domains, which is why the method says "look one hop away" rather than "pick from a list". Corrective action. Replace DIMM B2; close the SSD vendor ticket. Regression test. Memory stress test with EDAC monitoring; 7 days with zero UE events and zero Poisoned TLP at the SSD.

Hints

Hint

Who sets the EP bit, and why? What is the difference between poisoned and corrupted-on-the-wire?

What a senior engineer notices

That the vendor was blamed only because the NVMe error appeared in the SSD's log lines; that EDAC and AER timestamps are in the same clock domain and therefore orderable; that the SSD's handling of poison was correct and worth noting in the report.

Failure variants

  • If row 1 were absent (EDAC not loaded), you would conclude "RC sent poisoned data" and ask the platform team for memory logs.
  • If the SSD had committed the poisoned data and returned success, that would be a second, serious device bug.

Exercises

  2. An analyzer timestamp and a kernel timestamp differ by 3 µs with ε = ±5 µs. Can you say which came first?

  4. A timeout shows "completion polled" but the analyzer shows an MSI-X write. Where do you look?

Model answers

1. See the master tree: CQE? reachable? CFS? CQE in memory? interrupt on link? SQE fetched? data-phase errors? — tracepoints, CSTS read, analyzer, PBA/table, AER.

2. No: the difference is within the uncertainty; treat them as simultaneous.

3. PCIe UR evidence, driver cause (Case 5); NVMe timeout evidence, link cause (Case 1); NVMe Data Transfer Error evidence, platform memory cause (Trace Lab 47).

4. Host side after the write: IOMMU interrupt remapping, the target CPU's state, the IRQ handler mapping (wrong vector/handler), interrupt affinity changes.

5. "A marginal riser corrupted device-to-host traffic at 16 GT/s, causing replay storms and repeated link recovery. Quiz

  1. The first abnormal event is

    • The first error message in dmesg
    • The earliest observed deviation from expected behaviour, including absences
    • The most severe error
    • The last event before reboot
    Answer and reasoning

    It is defined against expected behaviour and includes missing events.

  2. Linux logs "I/O 77 QID 7 timeout, completion polled". Most likely domain?

    • Media
    • Link
    • Interrupt delivery (driver/platform or device not firing)
    • NVMe status error
    Answer and reasoning

    The CQE was there; notification failed.

  3. CSTS read = 0xFFFF_FFFF during timeout handling suggests

    • PCIe/link: device unreachable
    • Firmware fatal
    • Media error
    • Software throttling
    Answer and reasoning

    All ones is a failed read, not a CSTS value.

  4. Which timestamp source should you use to order kernel events against each other?

    • dmesg -T wall clock
    • Raw monotonic seconds (dmesg default / tracepoints)
    • BMC SEL
    • Application logs
    Answer and reasoning

    -T conversion can drift; BMC is a different clock.

  5. blktrace shows Q→D = 20 ms, D→C = 90 µs. Domain?

    • Media
    • Firmware
    • Link
    • Software (host-side queuing/throttling)
    Answer and reasoning

    Device time is normal; delay is before dispatch.

  6. Which is evidence against a media root cause for a read failure?

    • SMART media errors rising
    • Same LBA fails repeatedly
    • Status is Data Transfer Error with an AER Completion Timeout at the SSD
    • Long latency before the error
    Answer and reasoning

    Data Transfer Error + PCIe evidence points to transport, not media.

  7. Why must you capture AER and NVMe logs before resetting?

    Model answer

    Resets and recovery clear volatile controller state, logs can wrap, firmware-first handlers clear AER, and the link reset loses in-flight evidence. Some AER bits are sticky, but not everything survives.

  8. Explain "evidence domain ≠ cause domain" with an example.

    Model answer

    A UR at the root port (PCIe transaction evidence) caused by the driver freeing a PRP list early (driver cause).

  9. What makes a root-cause statement complete?

    Model answer

    It names the first abnormal event, the mechanism linking it to every observed symptom, evidence for and against alternatives, confidence, corrective action and a regression test.

Interview questions

  1. Beginner: Name the seven failure domains for NVMe on PCIe.

    Model answer

    Software, driver, NVMe protocol, PCIe transaction, link, firmware, media.

  2. Beginner: Why is "NVMe timeout" not a root cause?

    Model answer

    It is a host-side symptom that a command did not complete in time; many mechanisms in any domain can cause it.

  3. Intermediate: How do you align an analyzer capture with dmesg?

    Model answer

    Write a trace_marker and issue a distinctive command at the same moment; trigger the analyzer on it; compute the offset; carry the uncertainty.

  4. Intermediate: A drive "disappears" and comes back. What three readings decide between firmware and link?

    Model answer

    CSTS during the event (CFS vs all ones), AER at root port (Surprise Down / correctable storm vs nothing), link status before/after (downgrade/retrain).

  5. Advanced: Walk through a case where three layers report errors for one event.

    Model answer

    PRP use-after-free: IOMMU fault (platform), AER UR at root port (PCIe), Data Transfer Error (NVMe), block I/O error (software). Cause: driver; the first abnormal event is the MRd to the unmapped IOVA.

  6. Senior: You are given only "nvme timeout, reset controller" lines from a fleet of 10,000 servers. Design the investigation.

    Model answer

    Group by platform, slot, drive model, firmware, kernel; compute rates; check co-occurrence with AER, EDAC, thermal; for top clusters deploy incident-capture hooks and tracepoints; pick representative machines for analyzer capture; build timelines; validate hypotheses with A/B (firmware, riser, kernel). Report by root cause, not by symptom.

  7. Senior: How do you communicate a medium-confidence root cause to a vendor?

    Model answer

    Provide the merged timeline, the first abnormal event, the evidence for and against each hypothesis, the experiments run, the explicit confidence and what would raise it, and the specific data you need from them (telemetry, vendor logs).

Chapter summary

Error correlation turns a pile of messages into a root cause. Know the seven domains and their fingerprints; collect evidence before recovery destroys it; align every source onto one timeline with explicit uncertainty; mark the first abnormal event, including absences; treat later events as cascade; walk the decision trees to a domain; run the experiment that would prove you wrong; and write a root-cause statement with mechanism, confidence, fix and regression test. The domain where evidence appears is often not the domain that owns the cause.

Do not move on until you can:

  • list the seven failure domains with one fingerprint each
  • build a merged timeline from dmesg, tracepoints, AER and a capture, with clock alignment
  • identify the first abnormal event, including an absence
  • recognise the Linux AER → timeout → abort → reset cascade and skip to its start
  • apply the master tree and trees A–C to a new incident
  • choose a disambiguating experiment for any two candidate domains
  • write a complete root-cause statement for one of the seven cases from memory
