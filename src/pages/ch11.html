This chapter takes the Transaction Layer Packet (TLP) header apart bit by bit: every field of the request header, the configuration header and the completion header in non-Flit mode, with its position, size, purpose, an example, how it looks in a trace and what breaks when it is wrong. It ends with full hexadecimal decodes of three TLPs from the course's example system.

Why this chapter exists

In Chapter 10 you learned what kinds of TLP exist. That is enough to read an analyzer's summary column. It is not enough to debug. Real failures hide in single bits: a byte-enable nibble that is zero where it must not be, a Relaxed Ordering attribute that lets a write overtake another, a poisoned bit set by a switch, a Lower Address that puts data 64 bytes off, a Tag that collides with one already outstanding. Analyzers decode these for you — until the analyzer's decode is wrong for your revision, or until all you have is a raw header logged by Advanced Error Reporting (AER) in a kernel message. Then you must decode by hand.

This chapter makes the header a familiar object. By the end you should be able to take four hexadecimal doublewords from a kernel log and say exactly what the packet was, who sent it, where it was going, and why it was rejected.

Learning objectives

  • Number bits and bytes in a TLP header the way the PCI Express (PCIe) Base Specification does, and convert between DW hex, byte order on the wire and field values.
  • Locate and explain every field of DW0: Fmt, Type, TC, the 10-bit tag bits, Attr (Relaxed Ordering, No Snoop, ID-Based Ordering), TH, TD, EP, AT and Length.
  • Decode 3DW and 4DW memory request headers: Requester ID, Tag, Last DW BE, First DW BE, Address and Processing Hint.
  • Decode configuration request headers (Bus/Device/Function, Register Number) and completion headers (Completer ID, Completion Status, BCM, Byte Count, Requester ID, Tag, Lower Address).
  • Apply the byte-enable rules and compute the exact bytes a request touches.
  • Decode, by hand and with a program, a doorbell MWr32, an SQE-fetch MRd64 and its CplD from the example system.
  • State what changes in PCIe 6.x Flit Mode and what does not, at the level that can be supported.

The story

Remember the delivery trucks? Let us look closely at the label on the front. It is not a scribble: it is a form with boxes, and every box has a fixed place. The first box says how big the label is and whether the truck has boxes in the back. The next box says what kind of trip it is. There are little tick-boxes: "please hurry with the others" (traffic class), "you may let this truck go ahead of earlier ones" (relaxed ordering), "the boxes inside are broken, do not use them" (poisoned). There is a box for how many boxes are in the back, a box for who sent it, a box for the tracking number, two small boxes that say which items in the first and last box really count, and a big box for the street address.

Answer trucks have a different form: who is answering, did it go well, how many items are still to come, who asked, the tracking number, and exactly where in the first box the answer starts.

If even one tick-box is filled in wrong, the truck may be turned away at the gate, or worse, delivered to the wrong house.

A TLP header is like an airline boarding pass's barcode: a fixed-layout, densely packed record where every few bits mean something specific (flight, seat, class, sequence number, frequent-flyer status). Gate readers do not read the printed text; they decode bit fields. A single wrong field (the date) makes the pass invalid even though everything else is right, and a gate agent who can decode the barcode by hand can explain rejections the scanner only reports as "invalid".

  • A boarding pass is read once at a gate; a TLP header is parsed at every hop by switches (for routing) and fully by the final receiver (for meaning). Some fields matter only to one of them.
  • A boarding pass layout does not depend on what kind of trip it is. A TLP header's layout from DW1 onwards depends on Fmt/Type: requests, configuration requests, completions and messages lay out DW1–DW3 differently.
  • Barcodes carry no data. A TLP header announces a payload whose size (Length) must agree with what physically follows, and a mismatch is itself an error (Malformed TLP).
  • Kid-story "tick-boxes" sound optional; several of these bits are only permitted when software has enabled the feature (Relaxed Ordering, No Snoop, 10-bit tags, ID-Based Ordering). Setting a bit you are not enabled to set is a bug even if receivers tolerate it.

Beginner explanation

A TLP header is 12 or 16 bytes, organised as three or four 32-bit doublewords (DWs), DW0 to DW3. Think of each DW as a row of 32 boxes, numbered 31 on the left down to 0 on the right. Fields are runs of boxes inside a row.

  • DW0 is the same for every TLP kind. It says what the TLP is (Fmt and Type), a few handling hints, and how long the payload is.
  • DW1 for a request says who sent it (Requester ID) and its tracking number (Tag), plus byte enables. For a completion it says who is answering (Completer ID), whether it worked (status) and how many bytes remain.
  • DW2 and DW3 for a memory request carry the address (one DW for a 32-bit address, two DWs for a 64-bit address). For a completion, DW2 carries the original requester's ID and Tag, and the low bits of the address the data belongs to. For a configuration request, DW2 carries the target's Bus/Device/Function and register number.

When you see a header written as 40000001 0009000F FE601008, each group of eight hex digits is one DW, and inside each DW the leftmost hex digit holds bits 31–28. Decoding is just a matter of cutting each DW into its fields.

Header byte 0 = DW0 bits 31:24 = Fmt and Type. If you remember only one thing: 0x40 MWr32, 0x60 MWr64, 0x00 MRd32, 0x20 MRd64, 0x4A CplD, 0x0A Cpl, 0x04/0x44 CfgRd0/CfgWr0.

Engineering explanation

Numbering conventions: bits, bytes and the wire

The PCIe specification draws the header as rows of 4 bytes, labelled Byte 0 … Byte 3 left to right, with bit 7 on the left of each byte. Equivalently, if you read each row as a 32-bit big-endian number, header byte 0 is DW bits 31:24, byte 1 is 23:16, byte 2 is 15:8 and byte 3 is 7:0. This course writes bit positions as DW bit numbers (31…0), which is how analyzers and Linux's AER header log print the header.

  • Header byte order on the wire: byte 0 first. So the DW 40000001 is transmitted as bytes 40 00 00 01. Printing headers as big-endian DWs is therefore natural.
  • Payload byte order: payload byte 0 is the byte at the lowest address. A 32-bit value 0x00000005 written by a little-endian CPU to a doorbell travels as payload bytes 05 00 00 00. Analyzers differ in whether they show that DW as 05000000 (wire order) or 00000005 (as a little-endian integer). Always check which convention a tool uses before you conclude "the data is byte-swapped". Implementation-dependent display.

The single most common hand-decoding error is mixing these two conventions: treating header DWs as little-endian (wrong) or treating payload DWs as big-endian integers (often wrong). Headers: big-endian DW view. Payload: address-ordered bytes.

TC — Traffic Class (3 bits, DW0 [22:20])

Purpose: a label (TC0–TC7) used to map TLPs onto Virtual Channels (VCs) for differentiated service. Ordering rules apply only within the same TC. Example: virtually all NVMe traffic is TC0; configuration, I/O and many message requests must use TC0. Trace interpretation: any non-zero TC in NVMe traffic means someone configured TC/VC mapping deliberately — confirm it in the VC capability. Failure mode: a TC that is not mapped to an enabled VC at a port is a Malformed TLP at that port; differing TCs on related TLPs break ordering assumptions (Chapter 14).

T9 and T8 — high Tag bits (1 bit each, DW0 [23] and [19])

Purpose: extend the 8-bit Tag in DW1 to 10 bits when 10-Bit Tag Requester is enabled (Revision 4.0 onward Version-dependent). Tag[9] = T9, Tag[8] = T8. Example: in our example system 10-bit tags are disabled, so both are 0. Failure mode: a requester that uses 10-bit tags towards a completer (or through a path) that does not support them gets completions with the high bits lost, which shows up as unexpected completions or timeouts — Chapter 13.

TH — TLP Processing Hints present (1 bit, DW0 [16])

Purpose: when 1, the TLP carries TLP Processing Hints (TPH): a 2-bit Processing Hint (PH) occupies the low two address bits of a memory request, and a Steering Tag value is carried in a header field that otherwise has another use. The exact placement of the Steering Tag differs between reads and writes and when the extended TPH prefix is used — check the TPH section of your revision Uncertain on placement details. Example: 0 in all our NVMe examples. Failure mode: TH=1 from a function whose TPH Requester capability is not enabled is a configuration/implementation bug; hints are advisory, so wrong hints usually cost performance rather than correctness.

TD — TLP Digest present (1 bit, DW0 [15])

Purpose: 1 means a 1-DW End-to-end CRC (ECRC) follows the payload (or the header, if no payload). Trace interpretation: header byte 2 ≥ 0x80. Failure mode: TD=1 with no digest, or a digest with TD=0, is malformed; an ECRC mismatch at a receiver that checks ECRC is an ECRC Error in AER.

EP — Error Poisoned (1 bit, DW0 [14])

Purpose: the payload is known to be bad (for example, an uncorrectable memory error at the Root Complex while servicing a read). Data is forwarded but must not be used as good. Trace interpretation: header byte 2 has 0x40 set. Failure mode: the receiver reports a Poisoned TLP Received error (AER) and, for an NVMe controller, the affected command should fail with a data-transfer-related error rather than complete successfully. An EP bit appearing at a switch egress but not at its ingress means the switch poisoned it.

AT — Address Type (2 bits, DW0 [11:10])

Purpose: for memory requests, whether the address is untranslated (00b, the normal case), a translation request (01b) or already translated (10b) under Address Translation Services (ATS); 11b is reserved. Example: 00b for all NVMe traffic in our system (the IOMMU translates in the Root Complex; the device does not use ATS). Failure mode: AT=10b from a device not enabled for ATS is a serious isolation problem and is blocked by Access Control Services where configured; non-memory TLPs must carry 00b.

Length (10 bits, DW0 [9:0])

Purpose: payload length in DWs for TLPs with data; requested length in DWs for reads. Value 0 means 1024 DW (4 KiB). For TLPs without data (other than reads and some messages), it is reserved. Example: doorbell = 1 (0x001); SQE fetch = 16 (0x010); 256-byte data write = 64 (0x040). Failure mode: Length greater than MPS on a TLP with data, or a read Length greater than MRRS, or a payload that does not match Length — Malformed TLP (MPS violations are checked by receivers; MRRS is a requester-side rule). A request crossing a 4 KiB address boundary is also invalid.

Requester ID (16 bits, DW1 [31:16])

Purpose: identifies the requester as Bus[15:8], Device[7:3], Function[2:0] (or, with Alternative Routing-ID Interpretation (ARI), Bus[15:8] and an 8-bit Function number). It is where completions are routed back to, and it is the identity the IOMMU uses to choose a translation context. Example: Lab SSD 01:00.0 → 0000 0001 0000 0 000 = 0x0100. Root Port 00:01.1 → 0x0009. Trace interpretation: group traffic by Requester ID to separate functions (e.g. SR-IOV virtual functions each have their own). Failure mode: a device that captured the wrong bus number (for example, before enumeration finished, or after a hot-reset renumbering) sends requests with a stale ID; completions then route to the wrong place or IOMMU lookups fail.

Tag (8 bits in DW1 [15:8]; up to 10 bits with T9/T8)

Purpose: distinguishes a requester's outstanding non-posted requests. Requester ID + Tag = Transaction ID. For posted requests the Tag has no matching role; with TPH it may carry a Steering Tag instead. Example: SQE fetch Tag 0x21. Trace interpretation: follow a Tag from request to its completion(s); a Tag reused before all its completions arrived is a requester bug. Failure mode: duplicate outstanding Tags → completions mis-associated (data delivered into the wrong buffer); Tag values beyond the enabled width → Unexpected Completion or Malformed TLP depending on where detected. Details in Chapter 13.

Last DW BE and First DW BE (4 bits each, DW1 [7:4] and [3:0])

Purpose: byte enables for the first and last DW of the request. Bit n of a BE nibble enables byte n of that DW (bit 0 = lowest-addressed byte). Rules (non-Flit, memory requests):

  • Length = 1 DW: Last DW BE must be 0000b; First DW BE says which bytes of the single DW are accessed (any pattern, including non-contiguous, is permitted for a single DW).
  • Length > 1 DW: First DW BE and Last DW BE must both be non-zero.
  • For longer requests, the enabled bytes must be contiguous: First DW BE may only clear low-order bits (e.g. 1100b) and Last DW BE may only clear high-order bits (e.g. 0011b). Non-contiguous patterns are also allowed for some two-DW quadword-aligned cases — confirm the exact exception in your revision's byte-enable rules.
  • A read with Length = 1 and both BE fields 0000b is a zero-length read: it returns one DW of unspecified content and is used to "flush" earlier posted writes (Chapter 14).

Trace interpretation: NVMe doorbells are always full-DW writes (First DW BE = 1111b, Last = 0000b). Partial byte enables in NVMe traffic usually come from unaligned host buffers (with SGLs, which allow byte-granular addresses) or from CPU sub-DW register accesses. Failure mode: Last DW BE = 0000b with Length > 1, or non-contiguous enables where not allowed, is a Malformed TLP. A driver accessing a 64-bit register with two 32-bit accesses in the wrong order (or with 8-bit accesses) shows up as unexpected BE patterns and may hit registers that require full-DW access.

Address (30 or 62 bits) and PH (2 bits)

Purpose: the DW-aligned target address. 3DW: Address[31:2] in DW2[31:2]. 4DW: Address[63:32] in DW2, Address[31:2] in DW3[31:2]. Bits [1:0] of the last address DW are not address bits: they are the Processing Hint (PH) when TH=1, otherwise reserved (0). Rule: requests to addresses below 4 GiB must use the 3DW format. Example: SQ1 tail doorbell 0xFE60_1008 → 3DW DW2 = 0xFE601008. SQE at IOVA 0x1_2340_0100 → 4DW DW2 = 0x00000001, DW3 = 0x23400100. Trace interpretation: addresses from the device are IOVAs when an IOMMU is in use — never compare them directly with kernel physical addresses. Failure mode: address not claimed by any BAR/window → Unsupported Request; IOMMU has no mapping → the Root Complex fails the request (UR or CA, platform-dependent) and logs a fault; request crossing a 4 KiB boundary → Malformed TLP.

Configuration requests always use a 3DW header, TC0, Length 1, Last DW BE 0000b. The target's Bus/Device/Function (the "Completer ID" to be) sits in DW2 [31:16]; the register's DW offset is Extended Register Number (DW2 [11:8], the high 4 bits) concatenated with Register Number (DW2 [7:2]), giving a 10-bit DW index into the 4 KiB configuration space. Byte offset = (Ext Reg Num × 256) + (Register Number × 4). Example: read Vendor ID/Device ID (offset 0x000) of 01:00.0 → DW2 = 0x01000000. Read DW at offset 0x104 → Ext Reg Num = 1, Register Number = 1 → DW2 = 0x01000104. Failure mode: CfgRd0 to a non-existent function → Unsupported Request completion (software sees all-ones data for a failed config read on most platforms); a function not yet ready after reset may answer with Configuration Request Retry Status (CRS).

Completions always use a 3DW header. They carry the TC and the RO/NS attributes of the request they answer, and T9/T8 when the request used a 10-bit tag.

Completer ID (16 bits, DW1 [31:16])

Purpose: Bus/Device/Function of the function that completed the request. Example: CplD from the Root Complex to the SSD's SQE fetch — Completer ID is the Root Complex/Root Port identity (0x0009 in our example system; which ID the Root Complex uses is implementation-dependent). CplD from the SSD to a CPU MMIO read — 0x0100. Trace interpretation: a completion from an unexpected Completer ID (for example a switch port) usually means that port generated an error completion (UR) itself because nothing claimed the request. Failure mode: rarely wrong, but a stale captured bus number in an endpoint will show here too.

BCM — Byte Count Modified (1 bit, DW1 [12])

Purpose: set only by PCI-X completers to indicate that Byte Count reports only the bytes in this completion. PCIe completers must not set it. Trace interpretation: BCM=1 in a pure PCIe system is a red flag (or a PCI-X bridge in the path). Failure mode: a requester that ignores BCM when a bridge sets it will miscount remaining bytes.

Byte Count (12 bits, DW1 [11:0])

Purpose: for memory read completions, the number of bytes remaining to complete the request, including the bytes in this completion. A value of 0 means 4096 bytes. For a single-completion read, Byte Count = total bytes requested (counting only enabled bytes in the first/last DW). For configuration and I/O completions, Byte Count is 4 for a successful 1-DW access (precisely: it reflects the enabled bytes per the rules for those completions — confirm in your revision). Example: SQE fetch CplD → Byte Count 64 (0x040). A 512-byte read split into two 256-byte CplDs → 512 then 256. Trace interpretation: when Byte Count equals the bytes carried, this is the last completion for the request. Failure mode: Byte Count inconsistent with Length and Lower Address → the requester may flag a Malformed TLP or mis-assemble data; for unsuccessful completions the Byte Count and Lower Address follow specific rules that you should check in the specification before drawing conclusions from them.

Requester ID and Tag (DW2 [31:16], [15:8])

Purpose: copied from the request; the completion is ID-routed to Requester ID and matched by Requester ID + Tag. Failure mode: a completion whose Transaction ID matches no outstanding request at the requester is an Unexpected Completion (AER); if a completer corrupts the Tag, the real request later times out.

Lower Address (7 bits, DW2 [6:0])

Purpose: for memory read completions, the low 7 bits of the byte address of the first enabled byte of data in this completion. With Byte Count it lets the requester place the data exactly, and it reveals where a split occurred relative to the Read Completion Boundary. For other completions it is defined differently (zero, or reserved for AtomicOp completions) — confirm in your revision. Example: read starting at byte 0x…0106 → first CplD Lower Address = 0x06. Read of 0x1_2340_0100 → 0x00. Trace interpretation: the second and later completions of a split read have Lower Address aligned to the Read Completion Boundary (RCB) or to the previous completion's end — Chapter 13. Failure mode: wrong Lower Address → data placed at the wrong offset in the requester's buffer; requesters may check it against their expectation and flag Malformed TLP.

The central concept on the ladder: reading a header

The truck's label is a form with boxes in fixed places. Read the boxes in order and you know everything about the trip.

A header is 3–4 DWs. DW0 = kind, handling bits, Length. DW1 = who and which (request) or who answered and how it went (completion). DW2/DW3 = where (request) or for whom and at what offset (completion).

Header-building hardware fills these fields from DMA descriptors and configuration registers (Requester ID from captured bus number, Tag from a free-tag pool, attributes gated by Device Control enables). Receive logic checks them in a fixed order (format, type, length vs MPS, byte-enable rules, address range) before acting.

The Transaction Layer chapter of the PCIe Base Specification defines each field, its encodings and its rules, and lists which violations are Malformed TLPs and which are Unsupported Requests.

Fields drive protocol behaviour: Fmt/Type → routing and obligation; Attr → ordering permissions; Requester ID + Tag → completion routing and matching; Byte Count/Lower Address → reassembly.

An analyzer shows decoded fields; AER logs show four raw DWs. Both are the same bits: 20000010 010021ff 00000001 23400100 is an MRd64 of 16 DW at 0x1_2340_0100, Requester 01:00.0, Tag 0x21.

Header-level debugging asks: is any field illegal (malformed), unexpected (wrong address/ID/Tag), or inconsistent with configuration (MPS, MRRS, attributes not enabled)? The first header that fails such a check is usually the cause.

Flit Mode (PCIe 6.x): what changes

Everything above is the non-Flit header format. PCIe Revision 6.0 introduced Flit Mode, which is required at 64 GT/s and may also be used at lower speeds when both ends support it. In Flit Mode the link carries fixed-size flits protected by forward error correction and a flit-level CRC, and the TLP header encoding is different.

What can be stated with reasonable confidence Version-dependent:

  • The Fmt + Type pair of DW0 is replaced by a single 8-bit Type field in the first header byte; header size is described differently.
  • Several fields that non-Flit headers always carry become optional and are carried in Orthogonal Header Content (OHC) DWs appended to a base header only when needed (byte enables beyond simple cases and PASID are examples).
  • Tag space grows (14-bit tags are supported in Flit Mode).
  • Per-TLP framing tokens, per-TLP sequence numbers and per-TLP LCRC of non-Flit mode are replaced by flit-level mechanisms (see Chapter 15).
  • The transaction model — posted/non-posted, completions, Transaction IDs, ordering — is unchanged in concept.

This course does not give Flit Mode bit positions, Type encodings or OHC layouts. They are defined in the PCI Express Base Specification, Revision 6.x/7.0 — Flit Mode TLP header formats; read them there, and check which header format your analyzer decodes before trusting a field. Do not decode a Flit Mode header with the tables in this chapter.

Specification view

The header formats are defined in the PCI Express Base Specification, Revision 6.x/7.0 — Transaction Layer Specification (TLP formats and field rules). Error classifications for violations (Malformed TLP, Unsupported Request, Unexpected Completion, Poisoned TLP Received, ECRC Error) are defined in its error-signalling chapter and logged through the Advanced Error Reporting capability. The NVMe over PCIe Transport Specification 1.4 and the NVM Express Base Specification 2.4 define the meaning of the addresses and data (doorbells, queue entries), not the header.

  • Non-Flit DW0 layout: Fmt [31:29], Type [28:24], TC [22:20], Attr[2] [18], TH [16], TD [15], EP [14], Attr[1:0] [13:12], AT [11:10], Length [9:0]; T9/T8 at [23]/[19] for 10-bit tags.
  • Memory request DW1: Requester ID, Tag, Last DW BE, First DW BE. 64-bit addresses: upper DW first.
  • Completion DW1: Completer ID, Completion Status, BCM, Byte Count; DW2: Requester ID, Tag, Lower Address.
  • Status encodings SC 000b, UR 001b, CRS 010b, CA 100b.
  • Requests below 4 GiB use the 32-bit (3DW) format; Length 0 means 1024 DW; Byte Count 0 means 4096 bytes.
  • The byte-0 "cheat values" (0x40, 0x60, 0x4A…) are computed from the Fmt/Type encodings.
  • The configuration-offset formula (Ext Reg Num × 256 + Register Number × 4) is arithmetic on the field definitions.
  • All hex decodes in this chapter are worked by hand from the layouts above, for synthetic packets.
  • The Requester/Completer ID the Root Complex uses for CPU-originated requests and for completions to device reads.
  • Which attributes a device sets on which transfers, when enabled.
  • How analyzers print payload DWs (wire byte order vs integer).
  • T9/T8 (10-bit tags) from Revision 4.0; earlier revisions mark them reserved.
  • Bit 17 (LN) and its later status; CRS vs RRS naming; new Type encodings.
  • Flit Mode header formats (Revision 6.0 onward) — completely different encoding.

Check in the specification: the exact non-contiguous byte-enable exceptions; Byte Count and Lower Address rules for unsuccessful completions, I/O/configuration completions and AtomicOp completions; Steering Tag placement with TPH; the full Message Code table; which header fields a switch may legally modify (for example, EP).

  • Never decode a header without first establishing non-Flit vs Flit Mode.
  • Never assume a reserved bit is zero in a capture from a newer-revision device: it may be defined there.
  • Never assume Lower Address alone gives you the request address — it is 7 bits.

Code / pseudocode

A complete non-Flit header decoder in standard-library Python. It accepts header DWs as hex strings (as printed by AER or an analyzer), decodes every field covered in this chapter, and flags rule violations it can detect from the header alone.

#!/usr/bin/env python3
"""Decode non-Flit PCIe TLP headers given as hex DWs (big-endian DW view).
Usage: python3 tlp_decode.py 40000001 0009000f fe601008
       python3 tlp_decode.py            (runs the built-in examples)"""
import sys

STATUS = {0: "SC", 1: "UR", 2: "CRS/RRS", 4: "CA"}
MSG_ROUTE = ["to RC", "by address", "by ID", "broadcast from RC", "local", "gathered to RC", "rsvd", "rsvd"]

def bdf(v):
    return f"{v >> 8:02x}:{(v >> 3) & 0x1f:02x}.{v & 7} (0x{v:04x})"

def decode(dws):
    d0 = dws[0]
    fmt, typ = d0 >> 29, (d0 >> 24) & 0x1f
    f = dict(Fmt=f"{fmt:03b}", Type=f"{typ:05b}",
             TC=(d0 >> 20) & 7, T9=(d0 >> 23) & 1, T8=(d0 >> 19) & 1,
             IDO=(d0 >> 18) & 1, LN=(d0 >> 17) & 1, TH=(d0 >> 16) & 1,
             TD=(d0 >> 15) & 1, EP=(d0 >> 14) & 1, RO=(d0 >> 13) & 1,
             NS=(d0 >> 12) & 1, AT=(d0 >> 10) & 3)
    length = d0 & 0x3ff or 1024
    hdr4 = bool(fmt & 1)
    data = bool(fmt & 2)
    warn = []
    if fmt == 0b100:
        return "TLP Prefix DW (decode the following header separately)", f, warn
    if fmt > 0b011:
        return "reserved Fmt", f, ["reserved Fmt"]
    need = 4 if hdr4 else 3
    if len(dws) < need:
        return f"need {need} DWs", f, warn
    tag_hi = (f["T9"] << 9) | (f["T8"] << 8)

    if typ in (0b00000, 0b00001):                    # memory request
        name = ("MWr" if data else ("MRdLk" if typ else "MRd")) + ("64" if hdr4 else "32")
        d1 = dws[1]
        rid, tag, lbe, fbe = d1 >> 16, ((d1 >> 8) & 0xff) | tag_hi, (d1 >> 4) & 0xf, d1 & 0xf
        addr = ((dws[2] << 32) | (dws[3] & ~3)) if hdr4 else (dws[2] & ~3)
        ph = (dws[3] if hdr4 else dws[2]) & 3
        f.update(Length_DW=length, RequesterID=bdf(rid), Tag=hex(tag),
                 LastBE=f"{lbe:04b}", FirstBE=f"{fbe:04b}", Address=f"0x{addr:x}", PH=ph)
        if length == 1 and lbe:
            warn.append("Length=1 requires Last DW BE = 0000b")
        if length > 1 and (lbe == 0 or fbe == 0):
            warn.append("Length>1 requires non-zero First and Last DW BE")
        if hdr4 and addr < 1 << 32:
            warn.append("4DW header used for an address below 4 GiB")
        if (addr & 0xfff) + 4 * length > 4096:
            warn.append("request crosses a 4 KiB boundary")
        if length == 1 and lbe == 0 and fbe == 0 and not data:
            warn.append("zero-length read (flush semantics)")
        nbytes = 4 * length
        if length == 1:
            nbytes = bin(fbe).count("1")
        else:
            nbytes -= (4 - bin(fbe).count("1")) + (4 - bin(lbe).count("1"))
        f["EnabledBytes"] = nbytes
        return name, f, warn

    if typ in (0b00100, 0b00101):                    # configuration
        name = ("CfgWr" if data else "CfgRd") + str(typ & 1)
        d1, d2 = dws[1], dws[2]
        target = d2 >> 16
        off = (((d2 >> 8) & 0xf) << 8) | (d2 & 0xfc)
        f.update(RequesterID=bdf(d1 >> 16), Tag=hex(((d1 >> 8) & 0xff) | tag_hi),
                 FirstBE=f"{d1 & 0xf:04b}", Target=bdf(target), RegOffset=f"0x{off:03x}")
        if length != 1 or (d1 >> 4) & 0xf:
            warn.append("config requests must have Length=1 and Last DW BE=0000b")
        return name, f, warn

    if typ in (0b01010, 0b01011):                    # completion
        name = ("CplD" if data else "Cpl") + ("Lk" if typ & 1 else "")
        d1, d2 = dws[1], dws[2]
        st, bcm, bc = (d1 >> 13) & 7, (d1 >> 12) & 1, (d1 & 0xfff) or 4096
        f.update(Length_DW=length if data else "n/a", CompleterID=bdf(d1 >> 16),
                 Status=STATUS.get(st, f"reserved {st:03b} (treat as UR)"), BCM=bcm,
                 ByteCount=bc, RequesterID=bdf(d2 >> 16),
                 Tag=hex(((d2 >> 8) & 0xff) | tag_hi), LowerAddress=hex(d2 & 0x7f))
        if data and st != 0:
            warn.append("completion with data but non-SC status")
        if bcm:
            warn.append("BCM set: only PCI-X completers may set it")
        if data:
            carried = 4 * length - (d2 & 3)
            f["LastCompletion?"] = "yes" if bc <= carried else f"no ({bc - carried} bytes still to come, approx.)"
        return name, f, warn

    if typ >> 3 == 0b10:                             # message
        name = ("MsgD" if data else "Msg") + f" routed {MSG_ROUTE[typ & 7]}"
        d1 = dws[1]
        f.update(RequesterID=bdf(d1 >> 16), MessageCode=hex(d1 & 0xff))
        return name, f, warn

    if typ in (0b01100, 0b01101, 0b01110) and data:
        name = {0b01100: "FetchAdd", 0b01101: "Swap", 0b01110: "CAS"}[typ] + ("64" if hdr4 else "32")
        return name, f, warn
    return "unknown/reserved Type", f, ["unrecognised Fmt/Type"]

def show(words):
    dws = [int(w, 16) for w in words]
    name, fields, warns = decode(dws)
    print(" ".join(f"{w:08x}" for w in dws), "=>", name)
    for k, v in fields.items():
        print(f"    {k:15s} {v}")
    for w in warns:
        print("    !!", w)

if __name__ == "__main__":
    if len(sys.argv) > 1:
        show(sys.argv[1:])
    else:
        for ex in ("40000001 0009000f fe601008",
                   "20000010 010021ff 00000001 23400100",
                   "4a000010 00090040 01002100",
                   "4a004010 00090040 01002100",
                   "60000040 0100000f 00000002 00000100",
                   "04000001 0009050f 01000000",
                   "30000000 01000031 00000000 00000000"):
            show(ex.split())
            print()

Worked example

Three TLPs from the course's example system, decoded field by field in binary and hexadecimal. Synthetic examples for teaching.

Decode 1: MWr32 — SQ1 tail doorbell write

Header 40000001 0009000F FE601008, payload bytes on the wire 05 00 00 00.

Interpretation. BAR0 + 0x1008 = 0x1000 + (2 × 1) × (4 << CAP.DSTRD) with DSTRD = 0 → the Submission Queue 1 Tail Doorbell. The new tail is 5, so (if the previous tail was 4) the driver placed one new SQE at slot 4. The address is below 4 GiB, so the 3DW format is mandatory. The Tag value is irrelevant for a posted write (it matches nothing). The Requester ID is the Root Complex side's (implementation-dependent).

Decode 2: MRd64 — the controller fetches the SQE

Header 20000010 010021FF 00000001 23400100.

Interpretation. SQ1 base is 0x1_2340_0000; offset 0x100 ÷ 64 bytes per SQE = slot 4 — exactly the entry announced by the doorbell. 64 bytes = one SQE, all bytes enabled. The address is above 4 GiB, so 4DW is mandatory. The read does not cross a 4 KiB boundary (0x100 + 64 ≤ 0x1000) and is within MRRS (512).

Decode 3: CplD — the Root Complex returns the SQE

Header 4A000010 00090040 01002100, then 16 DW of payload starting 02 00 11 00 01 00 00 00.

Interpretation. Requester ID 0x0100 and Tag 0x21 match Decode 2 → this answers the SQE fetch. Byte Count 64 equals the 16 DW carried → it is the only (last) completion. Lower Address 0x00 = 0x1_2340_0100 & 0x7F. Status SC. The payload is now NVMe territory: CDW0's opcode 02h is the NVM Read command (Chapter 32). Notice how cleanly the layers separate: PCIe fields say "64 bytes for 01:00.0's request 0x21"; only the NVMe controller knows those bytes are a Submission Queue Entry.

Bonus: a configuration read and its completion

Request 04000001 0009050F 01000000: Fmt 000 Type 00100 → CfgRd0; Requester 0x0009, Tag 0x05, First BE 1111; target bus 01 device 00 function 0, Ext Reg 0, Register 0 → offset 0x000 (Vendor ID and Device ID). Its completion would be 4A000001 01000004 00090500 + 1 DW: CplD, Length 1, Completer 0x0100, SC, Byte Count 4, Requester 0x0009, Tag 0x05, Lower Address 0x00; payload bytes = Vendor ID (low two bytes) then Device ID.

Common mistakes

  • Reading the Requester ID as a bus number only. 0x0100 is bus 1, device 0, function 0 — not "device 256".
  • Treating Address bits [1:0] as address. They are PH (or reserved). Address is always DW-aligned; byte precision comes from BEs.
  • Forgetting that Length 0 means 1024 and Byte Count 0 means 4096.
  • Swapping First and Last BE. First DW BE is the low nibble (bits 3:0).
  • Assuming Byte Count is the size of this completion. It is what remains, including this one.
  • Reading the 4DW address in the wrong order. Upper 32 bits come first (DW2), lower second (DW3).
  • Applying non-Flit layouts to a Gen6 Flit Mode capture.
  • Byte-swapping payload when the tool already did. Check the convention on a known value (a doorbell write of a small tail number is ideal).

Debugging connection

A header-level checklist that finds most header bugs:

  1. Format sanity: Fmt/Type defined? 3DW for <4 GiB, 4DW otherwise? Payload size equals Length?
  2. Limits: Length ≤ MPS (writes, completions), ≤ MRRS (reads); no 4 KiB crossing.
  3. Byte enables: Length 1 → LBE 0000; Length > 1 → both non-zero and contiguous.
  4. Identity: Requester ID matches the function's current BDF; Tag within enabled width and not already outstanding.
  5. Attributes: RO/NS/IDO only if enabled; AT 00 unless ATS is in use.
  6. Completions: Transaction ID matches an outstanding request; status; Byte Count and Lower Address consistent with request and previous completions.
  7. Poison and digest: EP set where? TD consistent with ECRC presence?

When AER logs a Malformed TLP at the Root Port with the device's Requester ID, the device is almost always the author (the Root Port merely detected it). When it logs Unsupported Request at the device with the Root Complex's Requester ID, a CPU access (driver or a tool like setpci) hit an address or register the device does not support.

Senior engineer insight

Seniors decode the difference, not the header. Line up a failing TLP with a good one of the same kind from the same device and XOR them mentally: the bits that differ are the story. In the abnormal trace above, one nibble differs. That points to the code path that computes the last byte enable — far more precise than "the device sends bad writes".

RO, NS, IDO and TC are where system policy leaks into packets. If a platform starts misbehaving after a firmware or BIOS update, compare attribute bits in traces before and after: a changed Device Control enable can silently change every data TLP's attributes without any change in the NVMe driver.

The SSD had no outstanding request with Tag 0x27 — either the tag was already retired (a previous completion for it was taken as final, e.g. the device mis-counted Byte Count) or the request had already timed out and the tag was freed before this late completion arrived. Check for a Completion Timeout on Tag 0x27 shortly before.
  • E: MWr64, Length 0x081 = 129 DW = 516 bytes > MPS 256 → malformed (MPS violation). Also 129 DW from 0x2_0000_0000 is within 4 KiB, so that rule is not the issue. Owner: SSD — it ignored the programmed MPS (or MPS was changed under it without a reset of its DMA configuration).

What a senior engineer notices

A and E are both device-authored malformed writes but of different kinds (BE rule vs MPS rule); they suggest different code paths. B is a detection, not a cause. D's "Unexpected Completion" is very often the second half of a Completion Timeout story — look for the timeout first.

Failure variants

  • Change A's DW0 to 0x40000040 with the same 64-bit address split across DW2: the format no longer matches the address width.
  • Change B's EP to 0 but set TD=1 with no digest present.
  • Change D's Lower Address to 0x00 and Byte Count to 0x200: now it looks like a first completion of a 512-byte read.

Quiz

  1. Header byte 0 = 0x60. What is the TLP?

    • MRd64
    • MWr32
    • MWr64
    • CplD
    Answer and reasoning

    0x60 = 011 00000: Fmt 4DW with data, Type memory → MWr64.

  2. Which DW0 bit is EP?

    • 15
    • 14
    • 13
    • 12
    Answer and reasoning

    TD is 15, EP 14, RO (Attr[1]) 13, NS (Attr[0]) 12.

  3. A MRd has Length = 1, First DW BE = 0000b, Last DW BE = 0000b. What is it?

    • A zero-length read, legal, often used as a flush
    • A malformed TLP
    • A read of 1024 DW
    • A read with all four bytes enabled
    Answer and reasoning

    Zero-length reads are legal for Length 1 with both BEs zero; they force ordering of earlier posted writes before the completion returns.

  4. Completion DW1 = 0x00094000. What is the status?

    • SC
    • UR
    • CRS
    • CA
    Answer and reasoning

    The low 16 bits are 0x4000 = 0100 0000 0000 0000b. Bits 15:13 are 010b = CRS (Configuration Request Retry Status). Reading the hex digit "4" as status 100b (CA) is the classic trap: the status field starts at bit 15, not at bit 14. Always convert to binary before naming a status.

  5. In a 4DW memory request, which DW holds Address[63:32]?

    • DW1
    • DW2
    • DW3
    Answer and reasoning

    DW2 holds the upper half; DW3 the lower half and PH.

  6. A CplD has Byte Count 512 and carries 256 bytes. What follows?

    • Nothing; the request is complete
    • At least one more completion with 256 bytes remaining
    • A Completion Timeout
    Answer and reasoning

    Byte Count counts remaining bytes including this completion: 512 − 256 = 256 bytes still to come.

  7. Why must the Lab SSD's doorbell writes from the CPU use a 3DW header?

    Model answer

    BAR0 is at 0xFE60_0000, below 4 GiB. The specification requires the 32-bit format for addresses below 4 GiB even when the BAR is 64-bit capable.

  8. What does Lower Address tell you that Byte Count does not?

    Model answer

    Where, in the low 7 address bits, the first byte of this completion's data belongs. Byte Count says how much remains; Lower Address says where this piece starts. Together they let the requester place partial completions.

  9. Name two header fields a device may only set when software has enabled the feature.

    Model answer

    Any two of: Relaxed Ordering (Attr[1]), No Snoop (Attr[0]), IDO (Attr[2]), 10-bit tag bits (T9/T8), TH (TPH), AT ≠ 00 (ATS), TD (ECRC generation).

Interview questions

  1. (Beginner) What do Fmt and Type encode?

    Model answer

    Fmt: header size (3DW/4DW) and whether data follows (or that the DW is a TLP prefix). Type: the transaction kind (memory, I/O, config type 0/1, message with routing, completion, AtomicOp). Together they name the TLP.

  2. (Beginner) How is a Requester ID composed?

    Model answer

    Bus number (8 bits), Device (5 bits), Function (3 bits); with ARI, Bus (8) and Function (8).

  3. (Intermediate) Explain First/Last DW BE rules and give an illegal example.

    Model answer

    BE bits enable bytes of the first and last DW. Length 1 → Last BE 0000. Length > 1 → both non-zero and enabled bytes contiguous across the request. Illegal: Length 64 with Last BE 0000.

  4. (Intermediate) What are Byte Count and Lower Address for?

    Model answer

    They let a requester reassemble a read answered by multiple completions: Byte Count = bytes remaining including this completion; Lower Address = low 7 bits of the address of this completion's first byte.

  5. (Advanced) A Root Port logs Malformed TLP with the device's Requester ID; the device vendor says their device is compliant. How do you settle it?

    Model answer

    Decode the logged header and identify the specific rule (MPS, BE, 4 KiB, Fmt/address mismatch, TD/digest). Capture the link with an analyzer to confirm the TLP on the wire matches the log (ruling out a Root Port detection bug). Check the configured MPS on both ends. Reproduce with a transfer pattern that exercises the path. Evidence on the wire is decisive.

  6. (Advanced) Why do completions copy RO and NS from the request?

    Model answer

    So that the completion is treated under the same ordering and coherency assumptions the requester chose: RO on a read lets its completion data pass earlier posted writes where permitted; NS tells paths that snooping is not required.

  7. (Senior) How would you design a header-level regression test for a new SSD controller's DMA engine?

    Model answer

    Drive transfers with every alignment (byte offsets 0–3 within DW, offsets relative to RCB and 4 KiB), sizes around MPS/MRRS multiples, both address widths (below/above 4 GiB), all MPS/MRRS settings, RO/NS enabled and disabled; capture all TLPs and check every header rule automatically, plus completion reassembly with injected split patterns and error completions.

  8. (Senior) What do you tell a team migrating their trace tooling to Gen6?

    Model answer

    Header decoding must branch on Flit vs non-Flit; Flit Mode uses a different Type encoding and optional OHC, wider tags, and different link framing. Re-validate every decoder rule against the 6.x specification and keep transaction-level checks (matching, ordering) separate from encoding so they survive.

Chapter summary

A non-Flit TLP header is three or four DWs. DW0 is common: Fmt [31:29], Type [28:24], T9 [23], TC [22:20], T8 [19], Attr[2] [18], TH [16], TD [15], EP [14], Attr[1:0] [13:12], AT [11:10], Length [9:0]. Memory requests add Requester ID, Tag and byte enables in DW1 and a DW-aligned 32- or 64-bit address. Configuration requests carry the target Bus/Device/Function and register number. Completions carry Completer ID, status, BCM and Byte Count in DW1 and Requester ID, Tag and Lower Address in DW2. You decoded a doorbell write, an SQE fetch and its completion by hand, and you know that Flit Mode changes the encoding and must be decoded with the 6.x specification.

Do not move on until you can:

  • draw DW0 from memory with bit positions
  • decode a 3DW and a 4DW memory request header from hex
  • decode a completion header and say whether more completions follow
  • state the byte-enable rules and spot a violation
  • decode an AER "TLP Header" line and name the likely owner
  • say what you would not decode with these tables (Flit Mode)
