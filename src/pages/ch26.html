Before any data can move, the host must build one queue pair from nothing but three registers — AQA, ASQ and ACQ — and then use it to discover the controller and create every other queue. This chapter follows that bootstrap step by step, register by register and packet by packet, and introduces the Admin commands you will meet in every trace: Identify, Get Log Page, Get Features, Set Features, and the queue-creation commands.

Why this chapter exists

The Admin queue is the controller's control plane. Every NVM Express (NVMe) controller has exactly one, it is the first queue to exist after reset, and it is the only way to create I/O queues, read health and error logs, update firmware, manage namespaces or change features. When a system fails to boot from an SSD, or an SSD "disappears" after a reset, the evidence is almost always in the first few Admin commands.

The Admin queue is also special: it is not created by a command. It cannot be — there is no queue yet to send a command on. The host describes it directly through controller registers and then enables the controller. Understanding that chicken-and-egg bootstrap, and the precise rules about when those registers may be written, is what lets you read a bring-up trace and spot the first wrong step.

Learning objectives

  • Explain why the Admin queue pair is configured by registers (AQA, ASQ, ACQ) rather than by a command.
  • Decode the Admin Queue Attributes (AQA), Admin Submission Queue Base Address (ASQ) and Admin Completion Queue Base Address (ACQ) registers, including 0's based sizes and alignment.
  • Walk through controller initialisation in the order the NVMe Base Specification describes, including CC.EN, CSTS.RDY and the CAP.TO timeout.
  • Describe the common 64-byte Submission Queue Entry (SQE) layout used by every Admin command.
  • Use Identify, Get Log Page, Get Features and Set Features correctly, including the Number of Queues feature that gates I/O queue creation.
  • Recognise an Admin queue bring-up in a synthetic PCI Express (PCIe) trace and find the first abnormal event in a failed one.

The story

A new librarian arrives at an empty library. Before anyone can ask for books, someone has to tell her where the "questions" tray and the "answers" tray are. The head teacher writes three things on a whiteboard by the librarian's desk: "the questions tray is on table 4, the answers tray is on table 5, and each tray has 32 slots". Then the head teacher flips the "OPEN" sign. The librarian checks her whiteboard, gets ready, and turns on a green light that says "I'm ready".

The very first question the head teacher puts in the tray is "who are you, and what can you do?" The librarian writes a long answer on a sheet and puts it on the teacher's desk. Only after that does the teacher ask her to set up the other trays — one for each class in the school.

A ship's radio room has one emergency channel that is hard-wired: its frequency is printed on a plate bolted to the bulkhead. You don't negotiate the emergency channel over the radio, because without it you have no radio link to negotiate on. Once the emergency channel is up, the operator uses it to ask the shore station for working channels, set them up, and from then on routine traffic goes over the working channels, while the emergency channel carries control traffic — reports, configuration, alarms.

The Admin queue is the emergency channel; its "plate" is the AQA, ASQ and ACQ registers. Working channels are I/O queues, set up with Create I/O Completion Queue and Create I/O Submission Queue sent over the Admin queue.

What it hides. The radio channel is a single wire both ways; the Admin queue is two separate rings in host memory plus two doorbells. The "plate" can only be rewritten while the controller is disabled (CC.EN = 0); a ship could change its plate any time.

Where it misleads. The Admin queue is not reserved for emergencies or low-volume traffic only — it can carry many commands (up to 4096 entries), and things like firmware download and Get Log Page can move megabytes. Also, alarms (Asynchronous Event Requests) work in reverse of what the analogy suggests: the host must post a request in advance and the controller completes it when something happens; the controller cannot start a conversation.

Beginner explanation

The Admin queue pair is queue identifier 0. It has an Admin Submission Queue (ASQ, the same letters as the register that holds its address) and an Admin Completion Queue (ACQ). Like every NVMe queue, both live in host memory; the controller learns where they are from three registers in its BAR0 (Base Address Register 0) space:

The three Admin queue registers

The host writes these while the controller is disabled, then sets CC.EN (Controller Configuration, Enable bit) to 1 and waits for CSTS.RDY (Controller Status, Ready bit) to become 1. From that moment, the Admin queue exists, and the host can put commands in it and ring the Admin SQ tail doorbell (at offset 1000h).

Then the host asks questions. The first is nearly always Identify Controller: "tell me your model, firmware, limits and optional features". Next come Identify commands for namespaces, a Set Features asking for a number of I/O queues, and the commands that create those I/O queues. Throughout the controller's life, the Admin queue also carries Get Log Page (health and error logs), Get Features/Set Features (settings), firmware updates, and namespace management.

Key properties:

  • Sizes are 0's based and 12 bits wide. ASQS = 01Fh means 32 entries. The largest Admin queue is therefore 4096 entries, and the smallest legal value is 1h (2 entries). Whether the Admin queue size must also respect CAP.MQES is something to check for your revision Uncertain.
  • Base addresses are 4 KiB aligned. Bits 11:00 are reserved, so the queue starts on a 4 KiB boundary. (Many controllers ignore low bits rather than reject them — which turns an alignment bug into a silent "fetch from the wrong place" bug.)
  • Admin queues are always physically contiguous. There is a single base address; no Physical Region Page (PRP) list form exists for the Admin queue.
  • The Admin SQ and CQ are a fixed pair. The Admin SQ always completes into the Admin CQ. The Admin CQ uses interrupt vector 0.
  • They can be different sizes. ASQS and ACQS are independent; most drivers use the same value for both.

The host may change AQA, ASQ and ACQ only while CC.EN = 0. Writing them while the controller is enabled has no defined effect on the running Admin queue — a driver that "moves" its Admin queue without a reset will see the controller keep using the old addresses.

Controller initialisation, step by step

The NVMe Base Specification describes the initialisation sequence for a memory-based (PCIe) controller. In outline Normative order, with the information each step needs:

  1. Wait for the controller to be disabled. If CC.EN was 1, write CC.EN = 0 and wait for CSTS.RDY = 0. The wait is bounded by CAP.TO (Timeout, bits 31:24, in units of 500 ms).
  2. Configure the Admin queue. Write AQA, ASQ and ACQ. The host must have allocated and zeroed the queue memory (zeroing the ACQ gives every entry phase tag 0).
  3. Configure the controller. Write CC with: CSS (I/O Command Set Selected), MPS (Memory Page Size, 2(12+MPS) bytes; must lie within CAP.MPSMIN and CAP.MPSMAX), AMS (Arbitration Mechanism Selected; round robin unless CAP.AMS shows another is supported). IOSQES and IOCQES (I/O SQ/CQ Entry Size, 6 and 4 for 64- and 16-byte entries) must be valid before I/O queues are created; most drivers write them now.
  4. Enable. Write CC.EN = 1.
  5. Wait for ready. Poll CSTS.RDY until it reads 1, for up to CAP.TO. If CSTS.CFS (Controller Fatal Status) becomes 1 instead, the controller has failed.
  6. Identify. Send Identify Controller (and, on controllers supporting multiple I/O command sets, the command-set-specific Identify data). Read the limits: Maximum Data Transfer Size, SQ/CQ entry sizes, number of namespaces, optional admin command support (OACS), and more.
  7. Discover namespaces. Identify Active Namespace ID list, then Identify Namespace for each.
  8. Negotiate I/O queues. Set Features — Number of Queues. The completion reports how many the controller allocated.
  9. Configure interrupts. Allocate and program MSI-X (Message Signaled Interrupts eXtended) vectors (this is PCIe configuration and MSI-X table work, done by the operating system).
  10. Create I/O queues. Create I/O Completion Queue for each CQ first, then Create I/O Submission Queue for each SQ that maps to it (Chapter 27).
  11. Arm asynchronous events. Optionally configure the Asynchronous Event Configuration feature and submit one or more Asynchronous Event Request commands, which stay outstanding until the controller has something to report.

NVMe 2.0 introduced multiple I/O command sets as first-class citizens (NVM, Zoned Namespaces, Key Value, and later others). With that came new CC.CSS encodings (one selecting "all supported I/O command sets", one selecting "Admin command set only") and new Identify CNS values for command-set-specific data. The exact encodings are in the NVMe Base Specification, Revision 2.4 — Controller Registers and Identify command; check them there rather than relying on 1.x-era drivers Version-dependent.

Identify

Identify (06h) returns a 4096-byte data structure into the buffer described by PRP Entry 1/2. Command Dword 10 holds the CNS (Controller or Namespace Structure) value in bits 07:00, which selects what to return, and a Controller Identifier in bits 31:16 for some CNS values. The three you will see constantly:

Two Identify Controller fields matter directly for queues: SQES and CQES report the required (minimum) and maximum SQ/CQ entry sizes as powers of two, which the host uses to program CC.IOSQES/IOCQES. OACS (Optional Admin Command Support) reports which optional Admin commands exist — including whether Doorbell Buffer Config is supported.

Get Log Page

Get Log Page (02h) reads a log identified by its Log Page Identifier (LID) in CDW10 bits 07:00. The amount to read is the Number of Dwords (NUMD), a 0's based count split across NUMDL (CDW10 bits 31:16) and NUMDU (CDW11 bits 15:00), so very large logs can be read. CDW12/13 carry a 64-bit Log Page Offset for reading in pieces. Common logs: Error Information (01h), SMART / Health Information (02h), Firmware Slot Information (03h), Commands Supported and Effects (05h). The Retain Asynchronous Event (RAE) bit controls whether reading a log clears a pending asynchronous event of the matching type.

Get Features and Set Features

Features are named settings identified by a Feature Identifier (FID) in CDW10 bits 07:00. Set Features (09h) changes one; Get Features (0Ah) reads one, with a Select field (CDW10 bits 10:08) to read the current, default, saved value or the supported capabilities. Most feature values travel in CDW11 and come back in completion Dword 0, so many features need no data buffer at all.

The Number of Queues feature

This is the negotiation that bounds how many I/O queues the host can create. The host asks for NSQR + 1 submission queues and NCQR + 1 completion queues; the controller answers with how many it allocated, which may be more or fewer than requested. The rules to remember:

  • Both requested and allocated values are 0's based and exclude the Admin queue.
  • A request value of FFFFh is invalid (65,536 I/O queues would exceed queue identifier space with the Admin queue).
  • The host should issue it during initialisation, before creating any I/O queue; the allocation is not expected to change until the next controller reset.
  • Creating a queue with an identifier above the allocated count fails with Invalid Queue Identifier.

Asynchronous Event Request: the controller's only way to "call"

The controller cannot send an unsolicited message. Instead, the host submits Asynchronous Event Request (0Ch) commands that stay outstanding indefinitely. When something noteworthy happens — a SMART threshold, a namespace change, a firmware activation, or an error such as an invalid doorbell write — the controller completes one of them; completion Dword 0 says the event type and which log page to read. The host then reads that log (Get Log Page) and re-submits a new Asynchronous Event Request. The number that may be outstanding is reported in Identify Controller (Asynchronous Event Request Limit, 0's based).

Outstanding Asynchronous Event Requests occupy Admin SQ slots' worth of commands forever. If a driver sizes its Admin queue at 32 and keeps several AERs outstanding, it has fewer slots for real Admin work. That is why drivers keep only a few outstanding, and why "Admin command timeout" analysis must exclude AERs, which legitimately never complete during a healthy run.

The ladder for the central concept: Admin queue bootstrap

The head teacher writes the location of two trays on the librarian's whiteboard, flips the OPEN sign, waits for the green light, then asks "who are you?".

The host allocates two queues in memory, writes their addresses and sizes into AQA/ASQ/ACQ, sets CC.EN = 1, waits for CSTS.RDY = 1, and sends Identify on the new Admin queue.

Those registers latch into the controller's queue context for queue 0 when it transitions to enabled. The fetch engine will read from ASQB + head × 64; the posting engine writes to ACQB + tail × 16; MSI-X vector 0 is associated with the Admin CQ.

MWr TLPs (Transaction Layer Packets) from the root complex to BAR0+0x24/0x28/0x30/0x14; MRd from the root complex to BAR0+0x1C answered by the device's CplD (polling CSTS); then the device's first MRd to the ASQ base.

In a capture: a burst of host-to-device register writes, a run of CSTS reads returning RDY = 0 then RDY = 1, MWr SQ0TDBL = 1, device MRd 64 bytes at 0x1_0000_0000, sixteen 256-byte MWr into the Identify buffer, a 16-byte MWr to 0x1_0000_1000 with P = 1, the MSI-X write for vector 0, MWr CQ0HDBL = 1.

"Controller timeout during probe": did CSTS.RDY ever become 1? Did the device ever fetch from the ASQ base, and did that fetch complete successfully? Is ASQ 4 KiB aligned? Was Bus Master Enable set so the device may issue reads at all?

The sixteen questions: the Admin queue

1. What is it?
The single queue pair (identifier 0) through which the host manages an NVMe controller.
2. Why was it created?
To separate control from data and give management commands a channel that exists before any I/O queue does.
3. What problem does it solve?
The bootstrap problem: queues are created by commands, so the first queue must be created another way.
4. What existed before it?
In AHCI, management (IDENTIFY DEVICE, SET FEATURES) shared the same command slots as data; in SCSI, management commands share the data path too.
5. Why is the current design better?
Management traffic cannot be starved by or reorder with data in the same queue; the Admin queue is the highest priority under weighted round robin; and I/O queues can be created, deleted and resized dynamically.
6. Who creates it?
The host driver, by writing AQA/ASQ/ACQ and enabling the controller.
7. Who consumes it?
The controller consumes Admin SQEs; the host consumes Admin CQEs.
8. Where does it live?
Host memory, contiguous, 4 KiB aligned; its doorbells are the first two doorbell registers at BAR0 + 1000h.
9. What memory/registers are involved?
AQA, ASQ, ACQ, CC, CSTS, CAP (TO, DSTRD, MPSMIN/MAX, AMS, CSS), SQ0TDBL, CQ0HDBL, MSI-X table entry 0.
10. What happens before it?
PCIe enumeration, BAR assignment, Memory Space Enable and Bus Master Enable in the Command register, controller reset.
11. What happens after it?
Identify, Number of Queues, I/O queue creation, Asynchronous Event Requests, then normal I/O.
12. What happens if it is wrong?
The controller never becomes ready (CFS set), never fetches, fetches from the wrong address, or posts completions where the host is not looking — the device fails to probe.
13. What does the protocol analyzer show?
Host MMIO writes to the Admin registers, CSTS polling reads and their completions, and then the first doorbell/fetch/post/interrupt cycle on queue 0.
14. What does Linux show?
Probe messages in the kernel log, the nvme0q0 interrupt line, and register values via nvme show-regs.
15. What would a validation engineer test?
Minimum and maximum AQA sizes; asymmetric ASQS/ACQS; misaligned bases; register writes while enabled; repeated enable/disable cycles; timeout behaviour against CAP.TO; Admin queue wrap; AER handling.
16. What would a senior engineer suspect when it fails?
Ordering of register writes versus CC.EN, IOMMU mapping of the queue memory, Bus Master Enable, CAP.TO too short in the driver, non-zeroed ACQ, and a controller that needs more time after a function-level reset.

Hardware view

From the controller's perspective, CC.EN is the master switch for the queue machinery. While EN = 0 the controller is in reset: queues do not exist, doorbell writes are not acted on, and AQA/ASQ/ACQ are ordinary writable registers. On the 0→1 transition the controller (firmware or hardware) typically latches the Admin queue configuration into its queue-context table, resets the Admin SQ head and CQ tail to 0 and the CQ phase to 1, and then sets CSTS.RDY = 1 once it can accept commands.

How long that takes is Implementation-dependent: some controllers are ready within milliseconds, while others must load firmware, rebuild mapping tables or recover from an unsafe shutdown first. CAP.TO is the controller's promise of the worst case, in 500 ms units; a driver that gives up earlier than CAP.TO is wrong.

Before the controller can fetch even one Admin SQE, three PCIe-level conditions must hold: the BAR is assigned and Memory Space Enable is set (so the host's register writes reach the device), Bus Master Enable is set (so the device may issue Memory Read requests), and, with an IOMMU (Input/Output Memory Management Unit), the queue memory is mapped for the device. None of these is visible in NVMe registers; all of them break the Admin queue.

On the host side, the Admin queues are ordinary DMA-coherent allocations. Linux allocates them with the DMA API, which returns both a CPU virtual address and the device-visible DMA address — the latter is what goes into ASQ/ACQ.

Protocol view

The bootstrap mixes two kinds of PCIe traffic: host MMIO (Memory Write and Memory Read requests from the root complex to the device's BAR) and device DMA (requests from the device to host memory). Register reads are non-posted: the root complex sends an MRd and the device returns a Completion with Data. That completion is a PCIe completion, not an NVMe completion — a distinction treated in detail in Command vs Packet vs Completion.

Ordering points: (1) the register writes are posted and arrive in order, so CC.EN = 1 reaches the controller after AQA/ASQ/ACQ; (2) the CSTS read is non-posted and cannot pass the earlier posted writes, so reading CSTS also "flushes" them; (3) the Identify data writes and the CQE write are posted writes from the same requester and arrive in order, so when the host sees the CQE the data is already in memory.

Code / pseudocode

A driver's Admin bring-up reduced to its skeleton. Register helpers write and read 32/64-bit values in BAR0.

int nvme_admin_init(struct ctrl *c) {
    uint64_t cap = readq(c->bar + 0x00);
    unsigned to_ms = ((cap >> 24) & 0xFF) * 500;      /* CAP.TO */
    unsigned dstrd = 4u << ((cap >> 32) & 0xF);       /* doorbell stride */

    /* 1. disable and wait for RDY = 0 */
    writel(readl(c->bar + 0x14) & ~1u, c->bar + 0x14);
    if (wait_csts_rdy(c, 0, to_ms)) return -ETIMEDOUT;

    /* 2. Admin queues: 32 entries, zeroed, 4 KiB aligned DMA memory */
    c->asq = dma_alloc_zeroed(32 * 64, &c->asq_dma);
    c->acq = dma_alloc_zeroed(32 * 16, &c->acq_dma);
    writel((31u << 16) | 31u, c->bar + 0x24);          /* AQA, 0's based */
    writeq(c->asq_dma, c->bar + 0x28);                  /* ASQ */
    writeq(c->acq_dma, c->bar + 0x30);                  /* ACQ */

    /* 3-4. CC: IOCQES=4, IOSQES=6, AMS=RR, MPS=0 (4 KiB), CSS=NVM, EN=1 */
    writel((4u << 20) | (6u << 16) | 1u, c->bar + 0x14);

    /* 5. wait for RDY = 1, watch CFS */
    if (wait_csts_rdy(c, 1, to_ms)) return -ENODEV;

    c->sq0_db = c->bar + 0x1000;
    c->cq0_db = c->bar + 0x1000 + dstrd;
    c->sq_tail = c->cq_head = 0; c->phase = 1;

    /* 6-8. Identify Controller, then Number of Queues */
    if (admin_identify(c, 0x01, 0, c->id_buf_dma)) return -EIO;
    uint32_t dw0;
    uint32_t want = c->nr_cpus - 1;                     /* 0's based */
    if (admin_set_features(c, 0x07, (want << 16) | want, &dw0)) return -EIO;
    c->nr_io_sq = (dw0 & 0xFFFF) + 1;
    c->nr_io_cq = (dw0 >> 16) + 1;
    return 0;
}

Note the two uses of 0's based arithmetic (AQA and Number of Queues) and the doorbell stride derived from CAP rather than assumed.

Worked example

Problem. On a new board, the Lab SSD reports CAP = 0x0000_0020_2803_03FF. The driver writes AQA = 0x003F_000F, ASQ = 0x1_0000_0000, ACQ = 0x1_0000_1000, CC = 0x0046_0001. Then it sends Set Features with FID 07h and CDW11 = 0x001F_001F, and receives completion Dword 0 = 0x000F_000F. (a) What are the Admin queue sizes and how many Admin commands can be outstanding? (b) How long may the driver wait for ready? (c) Where is the Admin CQ head doorbell? (d) How many I/O queues may the driver create? (e) Is anything suspicious?

(a) AQA = 0x003F_000F: ASQS = 00Fh → 16-entry Admin SQ, holding at most 15 commands; ACQS = 03Fh → 64-entry Admin CQ. Legal: sizes are independent. (Unusual, but a larger CQ than SQ wastes nothing but memory.)

(b) CAP.TO = 28h = 40 × 500 ms = 20 seconds.

(c) CAP.DSTRD (bits 35:32) = 0 → stride 4 bytes. CQ0HDBL = 1000h + (2 × 0 + 1) × 4 = 1004h → 0xFE60_1004.

(d) Requested 1Fh + 1 = 32 SQs and 32 CQs; allocated NSQA = 0Fh → 16 SQs, NCQA = 0Fh → 16 CQs. The driver may create I/O queues 1–16; creating queue 17 would fail with Invalid Queue Identifier.

(e) Two things to note. The ACQ base at 0x1_0000_1000 lies directly after a 16-entry ASQ (16 × 64 = 1 KiB, so the ASQ occupies 0x1_0000_0000–0x1_0000_03FF) — fine. If the driver had kept the ASQ at 64 entries (4 KiB) and the ACQ at the same address, they would be adjacent, still fine. The real suspicion: the driver asked for 32 queues and got 16. If it maps 32 CPUs to queues as if it had 32, CPUs 16–31 will try to use queues that do not exist. A correct driver shares the 16 queues among the 32 CPUs.

Debugging connection

Bring-up failures follow a fixed decision tree. Walk it in order; each step's evidence is in a different place.

  1. Did the host reach the registers? Look for host MWr to BAR0 offsets 24h/28h/30h/14h. If absent: BAR assignment or Memory Space Enable problem (Chapter 19).
  2. Did the controller become ready? CSTS reads: RDY 0 → 1? If CFS = 1, the controller failed internally — vendor logs needed. If RDY never changes, compare the wait time with CAP.TO.
  3. Did the controller fetch the first SQE? Device MRd to ASQ base after the SQ0 doorbell. If absent: Bus Master Enable, doorbell address (stride), or doorbell value.
  4. Did the fetch succeed? The root complex's completion status. UR or CA (Completer Abort): IOMMU mapping or address problem.
  5. Was the CQE posted where the host looks? Device MWr address versus the driver's ACQ; phase tag value.
  6. Did the interrupt arrive? MSI-X MWr for vector 0; MSI-X table programming; host interrupt counters.

If step 6 fails but steps 1–5 succeed, the driver will time out even though the CQE is sitting in memory. Linux's timeout handler often polls the CQ before giving up and may log that the completion was found by polling — strong evidence of an interrupt-path problem rather than a controller problem.

Senior engineer insight

  • The first fetch is the first time the device masters the bus. Many "NVMe" bring-up failures are platform DMA failures: IOMMU, address translation, Access Control Services, or a root port that blocks requests. Treat the first SQE fetch's completion status as a platform health check.
  • CAP.TO is a promise, not a typical value. Read it, honour it, and log how long ready actually took. A device whose ready time drifts towards CAP.TO over its life is telling you something about its internal recovery work.
  • Admin traffic is a performance factor in fleets. Monitoring agents polling SMART logs every second create Admin traffic that, on some controllers, competes with I/O for firmware attention. Weighted round robin gives the Admin queue strict priority for fetch — which is not always what you want.
  • The Admin queue is the right place to look after an error. Asynchronous events and the Error Information log carry the controller's own explanation. Correlate AER (PCIe Advanced Error Reporting) on one side with the NVMe asynchronous event and error log on the other.

Step 1 — Run the checker

#!/usr/bin/env python3
"""Admin-queue bring-up checker (synthetic teaching model, not a driver).

Decodes CAP, then replays a list of register writes and checks them
against the controller-initialisation rules taught in Chapter 26.
"""
import struct

CAP = 0x0000_0020_2803_03FF          # Lab SSD (synthetic)

def decode_cap(cap):
    return {
        "MQES (entries)": (cap & 0xFFFF) + 1,
        "CQR": (cap >> 16) & 1,
        "AMS": (cap >> 17) & 0x3,
        "TO (ms)": ((cap >> 24) & 0xFF) * 500,
        "DSTRD (bytes)": 4 << ((cap >> 32) & 0xF),
        "CSS": (cap >> 37) & 0xFF,
        "MPSMIN (bytes)": 4096 << ((cap >> 48) & 0xF),
        "MPSMAX (bytes)": 4096 << ((cap >> 52) & 0xF),
    }

def check_sequence(writes, cap):
    """writes: list of (register_name, value). Returns list of problems."""
    problems, regs, enabled = [], {}, False
    for i, (reg, val) in enumerate(writes, 1):
        if reg in ("AQA", "ASQ", "ACQ") and enabled:
            problems.append(f"write {i}: {reg} changed while CC.EN=1")
        if reg == "AQA":
            asqs, acqs = (val & 0xFFF) + 1, ((val >> 16) & 0xFFF) + 1
            if asqs < 2 or acqs < 2:
                problems.append(f"write {i}: admin queue smaller than 2 entries")
            if val & 0xF000F000:
                problems.append(f"write {i}: reserved AQA bits set")
        if reg in ("ASQ", "ACQ") and val & 0xFFF:
            problems.append(f"write {i}: {reg} not 4 KiB aligned (bits 11:0 must be 0)")
        if reg == "CC":
            en = val & 1
            if en and not enabled:
                for need in ("AQA", "ASQ", "ACQ"):
                    if need not in regs:
                        problems.append(f"write {i}: CC.EN=1 before {need} was programmed")
                mps = 4096 << ((val >> 7) & 0xF)
                c = decode_cap(cap)
                if not c["MPSMIN (bytes)"] <= mps <= c["MPSMAX (bytes)"]:
                    problems.append(f"write {i}: CC.MPS selects {mps} bytes, outside CAP range")
                ams = (val >> 11) & 0x7
                if ams == 1 and not (cap >> 17) & 1:
                    problems.append(f"write {i}: WRR selected but not supported")
            enabled = bool(en)
        regs[reg] = val
    return problems

def identify_controller_sqe(cid, prp1):
    """64-byte Identify (opcode 06h) with CNS=01h (Identify Controller)."""
    cdw0 = 0x06 | (cid << 16)              # opcode, FUSE=0, PSDT=0 (PRP), CID
    dwords = [cdw0, 0, 0, 0, 0, 0,          # CDW0, NSID=0, CDW2-3, MPTR
              prp1 & 0xFFFFFFFF, prp1 >> 32,  # PRP1
              0, 0,                         # PRP2 (4 KiB page-aligned buffer needs none)
              0x01, 0, 0, 0, 0, 0]          # CDW10: CNS=01h
    return struct.pack("<16I", *dwords)

if __name__ == "__main__":
    for k, v in decode_cap(CAP).items():
        print(f"{k:16} {v}")
    good = [("CC", 0x0000_0000), ("AQA", 0x001F_001F),
            ("ASQ", 0x1_0000_0000), ("ACQ", 0x1_0000_1000),
            ("CC", 0x0046_0001)]
    bad = [("AQA", 0x001F_0020), ("ASQ", 0x1_0000_0040),
           ("CC", 0x0046_0001), ("ACQ", 0x1_0000_1000)]
    print("good sequence problems:", check_sequence(good, CAP) or "none")
    print("bad sequence problems:")
    for p in check_sequence(bad, CAP):
        print("  -", p)
    sqe = identify_controller_sqe(cid=0x0001, prp1=0x2_0000_0000)
    for row in range(4):
        chunk = sqe[row * 16:(row + 1) * 16]
        print(f"SQE bytes {row*16:02X}-{row*16+15:02X}: " + " ".join(f"{b:02X}" for b in chunk))

Questions

  1. In the bad sequence, AQA = 0x001F_0020. Is mismatched ASQS/ACQS itself an error?
  2. Where in the SQE dump is PRP Entry 1, and why do bytes 0x18–0x1F read 00 00 00 00 02 00 00 00?
  3. Why does the Identify SQE not need PRP Entry 2?
  4. What would a controller that ignores reserved bits do with ASQ = 0x1_0000_0040?

Challenge

Extend check_sequence() to flag a CC write that sets EN = 1 with IOSQES ≠ 6 or IOCQES ≠ 4 (for an NVM Command Set controller whose Identify SQES/CQES require 64/16 bytes), and a write of CC.EN = 0 that is not followed by a wait for RDY = 0 before AQA is changed (add a ("WAIT_RDY", 0) pseudo-write).

Hints

PRP Entry 1 occupies SQE bytes 24–31 (Dwords 6–7). 0x2_0000_0000 is 0x00000000 in the low Dword and 0x00000002 in the high Dword.

Solution

Q1. No. ASQS = 20h (33 entries) and ACQS = 1Fh (32 entries) are both legal. The checker does not flag it. The bad sequence's errors are the misaligned ASQ, enabling before ACQ was programmed, and programming ACQ while enabled.

Q2. Bytes 0x18–0x1F are Dwords 6 and 7: low Dword 0x00000000, high Dword 0x00000002, little-endian — PRP Entry 1 = 0x2_0000_0000. Bytes 0x28–0x2B (01 00 00 00) are CDW10 = 1 → CNS 01h.

Q3. The 4096-byte buffer starts at a 4 KiB page boundary and the memory page size is 4 KiB, so the whole transfer fits in the page PRP Entry 1 points to; PRP Entry 2 is only needed when the transfer crosses into a second page.

Q4. Fetch from 0x1_0000_0000 — the aligned address. If the driver put its SQE at 0x1_0000_0040, the controller would read 64 bytes of whatever lies before it (probably zeros: opcode 00h, which on the Admin queue is Delete I/O SQ with queue ID 0 — an invalid command that completes with an error rather than the Identify the driver expected).

Challenge sketch. In the CC branch, when en is newly 1, extract (val >> 16) & 0xF and (val >> 20) & 0xF and compare with 6 and 4. Track a disabled_confirmed flag set by ("WAIT_RDY", 0) and cleared by a CC write with EN = 0; require it before AQA/ASQ/ACQ writes.

What a senior engineer notices

The most dangerous error in the bad sequence is not the one that fails loudly but the misalignment, which a lenient controller silently "fixes" by fetching from somewhere else. Validation should test that the controller's behaviour with reserved bits is at least consistent and documented.

Failure variants

  • ACQ and ASQ pointing at the same page: the controller's first CQE overwrites the SQ. On the Admin queue this produces corrupted subsequent commands.
  • CC.MPS outside CAP.MPSMIN/MPSMAX: controller may fail to become ready, or set CFS.
  • CC.AMS selecting weighted round robin on a controller whose CAP.AMS does not advertise it: enable fails or behaviour is undefined.

Exercises

  1. Write the AQA value for a 64-entry Admin SQ and a 128-entry Admin CQ.
    Answer

    ASQS = 03Fh, ACQS = 07Fh → AQA = 0x007F_003F.

  2. CAP.TO = 0Ah. The driver waits 2 seconds for CSTS.RDY. Is that enough?
    Answer

    No. 0Ah × 500 ms = 5 seconds; the driver must wait up to 5 seconds before declaring failure.

  3. Get Log Page for the Error Information log, 64 entries of 64 bytes each. What are LID and NUMD?
    Answer

    LID = 01h. 64 × 64 = 4096 bytes = 1024 Dwords → NUMD = 1023 (3FFh, 0's based), so NUMDL = 03FFh and NUMDU = 0.

  4. Explain why Asynchronous Event Request commands are submitted by the host even though they report device-initiated events.
    Answer

    The controller has no way to originate a message on the queue interface — it can only complete commands the host submitted. A pending AER is a "slot" the controller fills when an event happens.

  5. A driver requests 64 I/O queues and gets NSQA = 1Fh, NCQA = 0Fh. How many SQs and CQs may it create, and what mapping does that force?
    Answer

    32 SQs and 16 CQs. At least some CQs must be shared by two SQs (many-to-one), e.g. SQ1 and SQ2 into CQ1.

Quiz

  1. Why is the Admin queue configured through registers rather than a command?

    • Registers are faster
    • There is no queue to send a command on until the Admin queue exists
    • The Admin queue is in device memory
    • Commands cannot carry addresses
    Answer and reasoning

    The bootstrap problem: commands travel on queues, so the first queue must be defined some other way.

  2. AQA = 0x001F_001F means:

    • 31-entry Admin queues
    • 16-entry Admin queues
    • 32-entry Admin SQ and CQ
    • An Admin SQ of 0x1F001F entries
    Answer and reasoning

    ASQS (bits 11:00) = 1Fh and ACQS (bits 27:16) = 1Fh, both 0's based → 32 each.

  3. Which bits of ASQ are reserved?

    • 11:00
    • 63:32
    • 15:00
    • None
    Answer and reasoning

    The Admin SQ base is 4 KiB aligned; bits 11:00 are reserved.

  4. Which Admin opcode is Identify?

    • 02h
    • 05h
    • 09h
    • 06h
    Answer and reasoning

    Identify is 06h. 02h is Get Log Page, 05h Create I/O CQ, 09h Set Features.

  5. In Set Features — Number of Queues, completion Dword 0 = 0x0007_000F. The controller allocated:

    • 7 SQs and 15 CQs
    • 16 SQs and 8 CQs
    • 8 SQs and 16 CQs
    • 15 SQs and 7 CQs
    Answer and reasoning

    NSQA bits 15:00 = 0Fh → 16 SQs; NCQA bits 31:16 = 07h → 8 CQs.

  6. The host polls CSTS and gets a value through a PCIe Completion with Data. Which agent sent that completion?

    • The root complex
    • The NVMe device
    • The IOMMU
    • It is an NVMe CQE
    Answer and reasoning

    The register read is a root complex MRd targeting the device's BAR; the device, as completer, returns the CplD. It is a PCIe completion, unrelated to NVMe CQEs.

  7. Which interrupt vector does the Admin CQ use?

    • Vector 0
    • Vector 1
    • Chosen in Create I/O CQ
    • None — the Admin queue is always polled
    Answer and reasoning

    The Admin CQ is associated with interrupt vector 0. Whether the driver uses the interrupt or polls is its choice.

  8. Why can't the controller post a CQE for an Admin command whose SQE fetch failed with an Unsupported Request completion?

    Model answer

    It never received the SQE, so it does not know the Command Identifier (or even the opcode). A CQE without the CID cannot be matched by the host. The controller must report the problem another way (implementation-dependent: fatal status, error log) and the host will time out.

  9. List four things that must be true at the PCIe level before the first Admin SQE can be fetched.

    Model answer

    BAR assigned and Memory Space Enable set; Bus Master Enable set; the queue memory mapped for the device in the IOMMU (if any); the link up and the device not in a low-power state that blocks requests. Also: the doorbell write reached the right register.

Interview questions

  1. Beginner: What are AQA, ASQ and ACQ?
    Model answer

    Controller registers at 24h, 28h and 30h that give the sizes (0's based) and 4 KiB-aligned base addresses of the Admin SQ and CQ in host memory. Written while the controller is disabled.

  2. Beginner: What is the first command a driver usually sends?
    Model answer

    Identify Controller (opcode 06h, CNS 01h), to learn the controller's capabilities and limits.

  3. Intermediate: Describe the initialisation sequence.
    Model answer

    Disable and wait RDY = 0; program AQA/ASQ/ACQ; program CC (CSS, MPS, AMS, entry sizes); set EN; wait RDY = 1 within CAP.TO; Identify; Number of Queues; configure interrupts; create I/O CQs then SQs; post AERs.

  4. Intermediate: How does the host find out how many I/O queues it may create?
    Model answer

    Set Features with FID 07h requesting a number; the controller returns NSQA/NCQA in completion Dword 0 (0's based).

  5. Advanced: Probe fails with "controller is down; will reset" after an Admin timeout. Where do you start?
    Model answer

    Read CSTS (CFS?), check the kernel log for IOMMU faults and AER errors, then capture the bring-up: register writes, RDY transition, first SQE fetch and its completion status, CQE post address, MSI-X write. The first missing or abnormal item localises the layer.

  6. Advanced: Why do AERs complicate timeout handling?
    Model answer

    They are designed to remain outstanding indefinitely, so they must be excluded from timeout logic; they also consume Admin queue capacity and CIDs, and their completion triggers further Admin traffic (Get Log Page).

  7. Senior: How would you validate a controller's handling of the Admin queue registers?
    Model answer

    Matrix of sizes (2, odd, 4096), asymmetric sizes, aligned and misaligned bases, reserved bits set, writes while enabled, enable/disable loops, ready-time measurement against CAP.TO under various shutdown histories, Admin queue wrap with AERs outstanding, and checking every behaviour against the specification's requirements and the vendor's documented choices for reserved fields.

  8. Senior: A fleet shows occasional multi-second I/O latency spikes correlated with a monitoring agent. Hypothesis?
    Model answer

    Admin commands (SMART/log reads, telemetry) handled by firmware paths that stall or compete with I/O processing; with WRR, Admin fetch has strict priority. Confirm by correlating Admin command timestamps with I/O latency, and by changing the polling interval.

Model explanation for the junior engineer

"The Admin queue is queue 0. You can't create it with a command, so you put its addresses and sizes in three registers — AQA for sizes, ASQ and ACQ for the 4 KiB-aligned bases — while the controller is off. Then you turn it on with CC.EN and wait for CSTS.RDY, up to CAP.TO times half a second. Now the Admin queue works: send Identify Controller to learn limits, Identify the namespaces, then Set Features Number of Queues to find out how many I/O queues you're allowed. Then create each I/O CQ before the SQs that point at it, and leave a few Asynchronous Event Requests outstanding so the controller can tell you about events."

Chapter summary

The Admin queue pair (queue 0) is defined by registers — AQA for 0's based sizes, ASQ and ACQ for 4 KiB-aligned, contiguous base addresses — written while CC.EN = 0. Enabling the controller and waiting for CSTS.RDY (bounded by CAP.TO) brings it to life. Admin commands share the common 64-byte SQE format; the essential ones are Identify (06h), Get Log Page (02h), Get Features (0Ah), Set Features (09h), Asynchronous Event Request (0Ch) and the queue creation and deletion commands. The Number of Queues feature (FID 07h) bounds I/O queue creation. A bring-up trace shows register writes, CSTS polling with PCIe completions from the device, then the first doorbell/fetch/data/CQE/interrupt cycle.

  • explain the difference between the CSTS read's PCIe completion and an NVMe CQE
