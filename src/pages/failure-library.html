A troubleshooting encyclopedia of thirty failure classes seen in NVMe over PCI Express (PCIe) systems, from links that never train to resume failures. Every case is written the same way: symptoms, likely layers, Linux, NVMe and PCIe evidence, a synthetic trace with its first abnormal event, root-cause candidates, the experiment that isolates them, remediation and a regression test. Use it after you have learned the method in Debugging Methodology; it is a reference to reason with, not a lookup table to trust blindly.

How to use this library

Real failures do not arrive labelled. A "missing completion" may be caused by a "replay" problem, which may be caused by "receiver errors", which may be caused by a "power-management issue". The cases below are organised by the layer where the first abnormal event usually appears, and they cross-reference each other so you can follow a cascade back to its start.

Learning objectives

  • Recognise the trace signature of each of thirty failure classes and name the layer it belongs to.
  • Know which Linux, NVMe and PCIe evidence to collect for each, and what each piece can and cannot prove.
  • For each class, propose root-cause candidates and an experiment that discriminates between them.
  • Write a remediation and a regression test that targets the mechanism, not only the symptom.
  • Follow cascades across classes (for example receiver errors → replay → completion timeout → missing NVMe completion → reset loop).

Physical layer failures

Link never reaches L0

Symptoms: the SSD does not appear in lspci or nvme list; firmware setup does not show it; sometimes it appears only after a cold boot, or only in one slot.

Likely layers: physical (Link Training and Status State Machine, LTSSM), power, reset and reference clock; occasionally platform firmware (bifurcation settings).

Regression test: automated power-cycle loop (hundreds of cycles, cold and warm), asserting after each cycle that the device enumerates with the expected Vendor ID, link speed and width within the platform's boot budget.

Intermittent link recovery

Symptoms: occasional latency spikes of microseconds to milliseconds; bursts of correctable AER messages; sometimes nothing visible at all except in an analyzer.

Likely layers: physical (signal integrity, equalization, clocking); sometimes power management (exits from low-power link states trigger Recovery by design).

Width downgrade

Symptoms: sequential throughput capped at roughly half or a quarter of expected; lspci shows a narrower width than capability.

Likely layers: physical (one or more lanes fail detection or training), platform configuration (bifurcation, lane mapping), mechanical (connector, adapter).

Remediation: replace or clean the faulty component; correct platform lane configuration.

Regression test: a boot-time health check that compares negotiated width with the minimum of both ends' Maximum Link Width and fails loudly; include it in manufacturing tests for every slot.

Speed downgrade

Symptoms: throughput capped near the previous generation's ceiling; lspci shows, for example, 8 GT/s on a 16 GT/s-capable link.

Likely layers: physical (equalization failure, signal integrity), configuration (Target Link Speed limited), platform firmware policy.

Root-cause candidates: Target Link Speed set low by platform firmware or software; channel loss too high for 16 GT/s; equalization preset tables wrong in platform firmware; retimer not configured for the higher rate; device firmware equalization defect.

Regression test: the same boot-time speed-and-width assertion as for width downgrade, plus a retrain-loop test (thousands of retrains with a capture of the resulting speed) for platform qualification.

Receiver errors

Symptoms: a steady trickle or bursts of correctable "Receiver Error" AER reports; possibly slightly lower throughput; usually no user-visible failure.

Likely layers: physical. The receiving port detects symbol, framing or block-encoding errors; the data link layer recovers via replay.

Root-cause candidates: signal-integrity margin (channel, connector, crosstalk); power-supply noise correlated with load; temperature; a specific lane defect; electromagnetic interference from adjacent hardware.

Test to isolate: correlate error rate with load, temperature and lane; lower the speed (Caution lab); swap components; check whether errors appear in only one direction (device transmitter/host receiver path versus the reverse).

Remediation: hardware fix or platform equalization tuning; define an acceptable error-rate threshold if the system recovers transparently.

Regression test: soak test with an explicit threshold (for example "fewer than N correctable errors per hour at full load", N set from a validated platform baseline), plus an alert in production monitoring when counters exceed it.

A correctable error is still evidence. Rare receiver errors are normal on long channels; a change in rate is a signal. Track rates over time, not just presence.

Data link and transaction layer failures

Malformed TLP

Symptoms: an uncorrectable AER report "Malformed TLP", often followed by link reset or device removal (its default severity is fatal); sometimes appears only for large transfers.

Likely layers: transaction layer at the sender (bad header construction) or configuration (Max Payload Size mismatch). Detected by the receiver.

Root-cause candidates: device MPS programmed larger than its link partner's (software misconfiguration, or a hot-plugged device configured differently); device firmware bug in TLP construction; data-path corruption that preserved LCRC because it happened before LCRC was computed.

Test to isolate: compare MPS at both ends; decode the logged header field by field against the formation rules (see Chapter 11 — TLP Header Anatomy); reproduce with MPS set equal on both ends.

Remediation: configure MPS consistently along the path (Linux has a boot parameter family pcie_bus_* controlling the policy; check your kernel's documentation); fix firmware if the TLP violates rules independent of MPS.

Regression test: enumerate with every MPS combination the platform supports and run large sequential reads and writes; assert no Malformed TLP and that MPS matches at both ends after every hot-plug and reset.

Completion timeout

Symptoms: uncorrectable non-fatal AER "Completion Timeout" reported by the device (or the root port); NVMe commands time out; sometimes Linux shows reads of device registers returning all ones afterwards.

Likely layers: anywhere on the request path; detected by the requester. If the SSD reports it, the SSD issued a non-posted request (SQE fetch, PRP list fetch, data fetch for a Write) and got no completion.

Root-cause candidates: IOMMU blocked the address (buffer unmapped too early: a host driver lifetime bug); the request was lost during a link Recovery or replay; the completer (root complex, memory controller) stalled; a switch or Access Control Services (ACS) policy redirected or blocked the request; the completion was returned with a wrong Tag or Requester ID (seen as Unexpected Completion elsewhere).

Regression test: abort- and timeout-path stress (commands aborted or timed out while their data is in flight), with IOMMU in strict mode, asserting no IOMMU faults and no Completion Timeouts.

Unsupported Request

Symptoms: register reads return 0xFFFFFFFF (all ones); nvme show-regs shows all-ones; AER "Unsupported Request" reported; NVMe driver logs that the controller is unreachable.

Likely layers: configuration and addressing. A completer that does not claim or cannot service a request answers a non-posted request with Unsupported Request (UR) status; for posted requests there is no completion, only an error report.

Regression test: for every reset type the product supports, verify Command register, BARs, MSI-X state and capabilities are restored and that MMIO works before I/O resumes.

Poisoned transaction

Symptoms: AER "Poisoned TLP Received"; an NVMe Write (or Read) fails; sometimes accompanied by host memory error reports (machine check, EDAC).

Likely layers: data path. A TLP with the Error Poisoned (EP) bit set carries data known to be bad; the sender propagates poison instead of silently sending corrupt data.

Regression test: where the platform supports error injection into memory (for example through ACPI Platform Error Interfaces in a lab), inject poison into a Write buffer and verify the command fails cleanly and no bad data reaches media (Expert lab).

Symptoms: either thousands of correctable AER messages per minute (system slows, logs fill, Linux rate-limits the messages), or the opposite: obvious link problems with no AER messages at all.

Likely layers: the reporting path: device and port AER configuration, root port interrupt, platform firmware ownership of AER ("firmware-first"), OS policy.

Challenge

Explain how a Receiver Error on the device→host direction could lead to the device's request never being completed, given that the data link layer replays corrupted TLPs.

Hint

The root port's receiver sees device→host traffic. If the root port keeps rejecting the device's TLPs, the device's replay timer expires (row 3). If replays fail repeatedly, the link may enter Recovery; a request may be delayed long enough for its completion to time out, or lost if the link fails.

Solution

1. Receiver Errors are detected by the receiving port: the root port (00:01.1) received corrupted device→host TLPs. The device (01:00.0) transmitted those TLPs, so when Acks did not come back in time, its replay timer expired and it reported Replay Timer Timeout.

2. 0x1_2342_C3C0 − 0x1_2342_0000 = 0xC3C0 = 50 112 bytes = slot 783 (50 112 / 64). Length 16 DW = 64 bytes: the device was fetching SQE 783 of SQ3.

3. The device never received that SQE, so the command never executed; the host's 30 s I/O timer for the command expired at about 842.6 s.

4. A temperature change is a candidate trigger for reduced signal margin (hypothesis, not conclusion).

Cascade: receiver errors (device→host) → replays and replay timer timeouts → the SQE fetch request delayed or lost (exact mechanism needs analyzer evidence) → Completion Timeout at the device → command never executed → host I/O timeout → controller reset. First abnormal event: row 1 (or earlier, if an analyzer shows marginal behaviour before the first logged error).

Experiments: restore the previous fan profile and run the same workload for the same duration (does the error rate change?); force 8 GT/s (Caution lab) and repeat with the quiet profile; arm an analyzer on Receiver Error to capture the first event and the following Recovery or replay sequence.

What a senior engineer notices

That row 4 is the device reporting a timeout for a request the device made, so the "SSD error" is the SSD complaining about the host side of the link. And that the ops note is the only clue to why now.

Quiz

  1. A Completion Timeout is reported with source 01:00.0 (the SSD). Who failed to receive a completion?

    • The root port
    • The SSD
    • The NVMe driver
    • The IOMMU
    Answer and reasoning

    The requester detects Completion Timeout. The SSD issued a non-posted request (SQE fetch, PRP list fetch, or Write data fetch) and no completion arrived.

  2. Register reads return 0xFFFFFFFF and configuration reads also return all ones. The best first hypothesis is:

    • Memory Space Enable was cleared
    • MSI-X is masked
    • The device is not responding at all (link down or device dead)
    • A media error
    Answer and reasoning

    If config space still read valid values, a cleared Memory Space Enable would be likely. All-ones config reads point to the link or device being gone.

  3. Which correctable error is reported by the transmitter rather than the receiver?

    • Receiver Error
    • Bad TLP
    • Bad DLLP
    • Replay Timer Timeout
    Answer and reasoning

    The replay timer runs at the transmitter waiting for Acks; the other three are detected by the receiver of corrupted data.

  4. A device sends a 512-byte MWr to a root port configured with MPS 256. What does the root port detect?

    • Malformed TLP
    • Unsupported Request
    • Poisoned TLP
    • Completion Timeout
    Answer and reasoning

    A TLP payload exceeding the receiver's Max Payload Size violates formation rules and is treated as Malformed.

  5. The CQE is in host memory, the MSI-X message is on the wire, but the host times out. Which case?

    Model answer

    Interrupt loss (host-side). An MSI-X problem would show no message or a mis-addressed one. Next: check CPU hotplug, affinity, handler races and remapping.

  6. Why can a host that stops writing CQ head doorbells cause "missing completions" for commands that executed successfully?

    Model answer

    The controller must not overwrite unconsumed CQ entries. When the CQ is full (N − 1 entries unconsumed), completed commands cannot be posted, so the host sees no completion even though the work was done.

  7. A read fails with Unrecovered Read Error after 48 ms. What does the 48 ms suggest?

    Model answer

    The controller retried internally (read retry, stronger error correction) before giving up. Rising read latency on a region is an early warning of media trouble.

  8. Disabling ASPM removes latency spikes; disabling APST does not. Which component's power behaviour is implicated?

    • The NVMe controller's power states
    • The PCIe link's power states
    • The CPU's power states
    • NAND
    Answer and reasoning

    ASPM controls link power states (L0s, L1); APST controls NVMe controller power states. The experiment isolates the link.

  9. In a reset loop, why focus on the first iteration?

    Model answer

    Each failed iteration can degrade state further, so later iterations may fail for different reasons; the first iteration's failing step is closest to the original cause.

  10. A PRP list entry is 0x2_0000_3080. Why is that a problem when it is not the first entry?

    Model answer

    Only PRP1 may carry a non-zero offset into its page; later entries must be page-aligned (4 KiB with CC.MPS = 0). 0x...080 has an offset of 0x80.

Interview questions

  1. Beginner: Name three things that can make an NVMe command never complete.

    Model answer

    The SQE was never fetched (wrong doorbell, lost fetch), the controller is stuck on it (firmware), or its CQE could not be posted or was not noticed (CQ full, wrong CQ address, missing interrupt).

  2. Intermediate: How do you tell "MSI-X problem" from "interrupt loss"?

    Model answer

    Look on the wire after the CQE write. No interrupt message, or one to a wrong address/data: MSI-X configuration. A correct message with no host reaction: host interrupt path.

  3. Intermediate: Your link shows x2 instead of x4. List the first three checks.

    Model answer

    Both ends' Maximum Link Width (is x4 possible?), platform bifurcation and adapter wiring, and a swap test of the SSD and slot. Then a per-lane training capture.

  4. Advanced: A fleet shows rising correctable Receiver Errors on one platform after a BIOS update. How do you investigate?

    Model answer

    Confirm correlation by comparing updated and non-updated machines under the same workload; bisect BIOS versions; diff equalization and link settings between versions; use lane margining to compare margin before and after; check whether the errors are in one direction and which lanes.

  5. Senior: How would you build a regression suite from this library?

    Model answer

    One test per case targeting the mechanism (for example queue-wrap with doorbell range checks; MPS consistency after every reset; per-queue interrupt test; reset storms; suspend/resume loops), plus monitors on counters (AER, SMART) with thresholds, plus performance and latency tests with preconditioning. Each test is tied to a requirement and to the failure classes it guards against.

Summary

Thirty failure classes, one template. The first abnormal event is usually at the top of a cascade: physical errors drive replays, replays and lost requests drive completion timeouts, missing data drives NVMe timeouts, and timeouts drive resets. Detection is often far from the cause: requesters detect timeouts, receivers detect corruption, hosts detect missing completions only by their own timers. Every case ends in a mechanism-level regression test.
