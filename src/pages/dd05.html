Chapter 18 taught you to decode an Endpoint's configuration space by hand. This module teaches you to change it safely and to trust what you read: register attribute types (read-only, read-write, write-one-to-clear, sticky, reserved), byte-enable-sized writes, the read-modify-write hazards that erase evidence, the Root Port's Type 1 header and Root-specific registers, the extended capability rules, and how resets and virtualization alter what configuration space shows.

Orientation

Reading configuration space is safe; writing it is where engineers erase the very error bits they were investigating, change a bridge window under a running device, or "fix" a register that the next Function Level Reset silently reverts. And reading has subtleties of its own: an all-zeros extended space, an all-ones DWORD, a capability chain that loops. This module builds the habits that separate an engineer who can decode a dump from one who can change a register on a live system and explain afterward exactly what changed.

Know Chapter 18 — Configuration Space (Type 0 header, Command/Status, capability lists, the Lab SSD dump). Configuration requests and ECAM are in Chapter 17; the Type 1 bridge model in Module 03; allocation in Module 04; AER in Chapter 46.

Next: Module 06 — BAR and MMIO moves from configuration space to the memory space the BARs open; Module 18 — AER uses the sticky and RW1C rules from here.

Kid story

Every machine in a factory has a small panel of switches and lights on its side. Some lights you can only look at. Some switches you can flip either way. Some lights are "alarm lights": once lit, they stay lit until you press that exact light to say "I've seen it" — and pressing a light that is off does nothing. A few alarm lights even stay lit when the machine is switched off and on again, so the night shift can see what happened in the day.

The panel has one dangerous habit: the buttons are arranged in rows of four, and if you press a whole row at once to flip one switch, you also press any alarm lights in that row — and they go dark before anyone wrote them down.

Analogy boundary

Represents. Lights you only look at = read-only (RO) fields; switches = read-write (RW); alarm lights = write-1-to-clear (RW1C) status bits; lights that survive power cycling = sticky bits (ROS, RWS, RW1CS); a row of four buttons = one 32-bit DWORD written with all byte enables set.

Hides. Some switches only take effect later (a new Max Payload Size matters only for the next TLPs); some fields are set once by firmware and then frozen (HwInit); reserved positions must be written back exactly as read (RsvdP) or as zero (RsvdZ); the panel is reached through a network (configuration TLPs) that may itself be down — in which case every light appears lit (all ones).

Misleads. "Sticky" does not mean "survives everything": which resets preserve sticky bits is defined per reset type and depends on auxiliary power. And a hypervisor may show a guest a painted copy of the panel, not the real one.

Mechanism

One safe read-modify-write: setting MPS on the Lab SSD

Device Control lives at PCI Express Capability + 08h; for the Lab SSD that is 78h (capability at 70h, Chapter 18). It is a 16-bit register sharing DWORD 1Eh (offset 78h/4) with Device Status at 7Ah — and Device Status contains RW1C error bits.

The same change done as a 32-bit read of 78h and a 32-bit write of the modified DWORD would also write Device Status. Any error bits that were 1 when read would be written back as 1 — and RW1C clears them. The device's evidence is gone and nobody logged it.

The ladder for "writing a configuration register safely"

Press only the button you mean; never press a whole row that contains alarm lights.

Read, change only your field, write back with the narrowest width; never write a status register with a value you just read.

Each bit has hardware attribute logic: RO ignores writes, RW1C clears on 1, sticky bits live in an auxiliary-powered domain.

The PCI Express Base Specification assigns an attribute to every field and defines RsvdP/RsvdZ obligations and reset behaviour per attribute.

A CfgWr carries one DWORD and First DW Byte Enables; only enabled bytes are written; the completion confirms acceptance, not effect.

In a trace, a CfgWr to Register 01h with BE=1111b or to a DevCtl/DevSta DWORD with BE=1111b deserves a second look.

Missing error bits after "nothing happened" → check who wrote the status DWORD; errors at boot with no traffic → sticky leftovers.

Well established: configuration requests are non-posted, carry one DWORD with First DW Byte Enables, and use TC0; extended capabilities start at 100h with ID, version and next-offset fields; an extended capability header of all zeros at 100h means "no extended capabilities"; RW1C bits clear on writing 1.

Derived: because Command and Status share a DWORD, any 32-bit write to offset 04h is also a write to Status, so tools must use 16-bit writes for Command. The same reasoning applies to Device Control / Device Status, Link Control / Link Status, and Slot Control / Slot Status.

Implementation-dependent: which optional capabilities exist; vendor-specific capability contents; timing for a write's effect (e.g. retrain after Retrain Link); whether auxiliary power is present to preserve sticky bits; how a hypervisor virtualizes fields.

Version-dependent: newer revisions add capabilities (for example for Flit Mode and integrity and data encryption) and redefine formerly reserved bits — which is exactly why RsvdP must be preserved. Field names also change (CRS → RRS).

The specification does not say what software should do with an all-ones read, how tools should format dumps, or how operating systems should lock access. It does not define DVSEC contents — the designating vendor or consortium does.

Never write configuration space on a production system to "try something"; never write back a status DWORD; never assume a write took effect without reading back; never decode a VSEC/DVSEC without its defining document.

Beginner lab — Attribute safari

Safe lab

Objective
Classify configuration fields by attribute and predict write effects.
Prerequisites
Chapter 18.
Setup
The Root Port dump above; optionally your own lspci -vvv.
Procedure
For each field — Vendor ID, Command, Status bit 4, Status bit 13, Secondary Bus Number, Bridge Control bit 6, LnkSta, LnkCtl bit 5, SltCap Physical Slot Number, AER Uncorrectable Status — write the attribute and what happens if software writes 1, and if it writes 0.
Observations
A table of ten rows.
Questions
Which writes are dangerous on a live system? Which are no-ops?
Expected reasoning
Attributes from the specification; side effects from the field's meaning.
Solution

Vendor ID RO (no-op). Command RW (changes decode/bus mastering — dangerous). Status bit 4 Capabilities List RO (no-op). Status bit 13 Received Master Abort RW1C (1 clears, 0 no-op — erases evidence). Secondary Bus Number RW (re-routes configuration and completions — dangerous). Bridge Control bit 6 Secondary Bus Reset RW (1 resets the subtree — very dangerous). LnkSta mostly RO with some RW1C bits (Link Bandwidth Management Status, Link Autonomous Bandwidth Status). LnkCtl bit 5 Retrain Link (writing 1 retrains the link — traffic pauses; reads as 0). SltCap Physical Slot Number HwInit (no-op). AER Uncorrectable Status RW1CS (clears; sticky across some resets).

Extension: find two fields in your system's lspci -vvv whose attribute you are unsure of and look them up in the specification.

# --- RW1C emulation of the Command/Status DWORD at 04h ---
RW_CMD, RW1C_STS = 0x0507, 0xF900          # writable Command bits; RW1C Status bits (illustrative masks)
def cfg_write(off, value, be):
    old = rd(off, 4)
    new = old
    for byte in range(4):
        if be & (1 << byte):
            shift = 8 * byte
            mask_rw = ((RW_CMD | 0) >> shift) & 0xFF if byte < 2 else 0
            mask_1c = (RW1C_STS >> (shift - 16)) & 0xFF if byte >= 2 else 0
            vb, ob = (value >> shift) & 0xFF, (old >> shift) & 0xFF
            nb = (ob & ~mask_rw) | (vb & mask_rw)            # RW bits take the new value
            nb &= ~(vb & mask_1c)                              # RW1C bits clear where 1 written
            new = (new & ~(0xFF << shift)) | ((nb & 0xFF) << shift)
    cfg[off:off + 4] = new.to_bytes(4, "little")

cfg[0x06:0x08] = (0x1010).to_bytes(2, "little")   # pretend bit 12 got set by an error

Observations
Header type 0x01, buses 00/01/01, window 0xfe600000–0xfe6fffff; capabilities PCI Express (port type 0x4 = Root Port) and MSI; extended AER v2 and ACS v1; Status stays 0x1010 after the 16-bit write and drops to 0x0010 after the 32-bit write. With the corrupted pointer, the walker reports a loop instead of hanging.
Questions
(1) Why does the walker mask pointers with 0xFC? (2) Why is loop detection mandatory in production tools? (3) Which Status bits are RW1C in the real specification?
Expected reasoning
Low two bits of capability pointers are reserved; a corrupted or malicious device must not hang the host; the RW1C set comes from the Status register definition (error bits 8 and 11–15), not from this script's illustrative mask.
Solution

(1) Capability structures are DWORD aligned; software must ignore the low two bits. (2) Configuration space comes from hardware you may not trust (a malfunctioning device, a hostile one under VFIO); Linux limits capability walks for the same reason. (3) In the Status register, Master Data Parity Error (bit 8), Signaled Target Abort (11), Received Target Abort (12), Received Master Abort (13), Signaled System Error (14) and Detected Parity Error (15) are RW1C; the script's mask approximates them. The extended loop detector does not handle a next pointer below 100h — adding that check is the extension.

Advanced lab — Measure what a reset forgets

Caution lab Test machine only; the device is reset. Do not use a disk holding data you need, and unmount it first.

Objective
Observe which configuration fields a Function Level Reset changes, and that the OS restores them.
Prerequisites
Linux, an NVMe device advertising FLR ("FLReset+" in DevCap), root.
Setup
Unbind the nvme driver from the test device (echo 0000:01:00.0 | sudo tee /sys/bus/pci/drivers/nvme/unbind).
Procedure
  1. Save lspci -xxxx.
  2. Trigger a reset through the kernel (which saves and restores state): echo 1 | sudo tee /sys/bus/pci/devices/0000:01:00.0/reset.
  3. Save again and diff.
  4. Read AER status registers before and after.
  5. Rebind the driver.
Observations
Differences (if any) between before and after.
Questions
(1) Why might the diff be nearly empty even though FLR resets most fields? (2) Which differences would you expect if the kernel did not restore state? (3) Did AER status bits survive?
Expected reasoning
The kernel saves configuration state before the reset and restores it after; without restore, Command, DevCtl (MPS/MRRS), MSI-X enable and BARs would return to defaults; sticky AER bits survive FLR.
Solution

Typical result: almost identical dumps because of save/restore; status bits that were set may differ (non-sticky ones cleared by the reset; sticky ones preserved). Which reset method the kernel uses (FLR, Secondary Bus Reset, power-management reset) depends on capabilities and kernel version; /sys/bus/pci/devices/…/reset_method shows the choice on recent kernels. To see raw post-FLR defaults you would need to trigger FLR without restore — a deliberate experiment better done on a dedicated validation setup.

Senior forensic lab — Errors that predate the boot

Safe lab Paper exercise.

Objective
Decide whether AER errors seen right after boot belong to this boot.
Prerequisites
Chapter 46.
Setup
Synthetic evidence: after a firmware upgrade of the SSD, monitoring reports "Uncorrectable Error Status: Completion Timeout" on 01:00.0 within 2 seconds of boot, on 30% of servers. The kernel AER handler logged nothing during this boot. The AER Header Log is all zeros (Completion Timeout logs no header). Systems were warm-rebooted (no power loss) after the upgrade, during which the SSD reset itself while the host was reading its registers. Cold-booted systems never show it.
Procedure
First abnormal event, hypotheses, evidence, experiment, conclusion.
Solution

The status bit is sticky (RW1CS) and survives warm reset with auxiliary power. The first abnormal event happened before this boot: during the firmware activation reset, a host read went unanswered and the SSD logged a Completion Timeout for one of its own outstanding requests (or the requester was the SSD reading host memory as the host reset). Hypotheses: (a) stale sticky bit from the upgrade window; (b) a real error early in this boot that the kernel missed. Evidence: no kernel log (with AER enabled, a real error would interrupt), cold boots clean — supports (a). Experiment: clear the bit (RW1C) once, warm reboot without upgrade: it does not reappear → (a) confirmed. Conclusion: no defect in current operation; monitoring should clear and record sticky AER status at boot (with timestamp "inherited") instead of alarming. Confidence: high.

Extension: write the monitoring rule: record, classify as "pre-boot", clear, and alarm only on recurrence.

Interview

Beginner

  1. Where does configuration space live?

    Model answer

    In each function; software reaches it through ECAM or the legacy mechanism, which become configuration TLPs.

  2. What does RW1C mean?

    Model answer

    Read, write 1 to clear; writing 0 has no effect.

  3. How large is a function's configuration space?

    Model answer

    4 KiB: 256 PCI-compatible bytes plus extended space from 100h.

  4. What does a configuration read of all ones usually mean?

    Model answer

    The request was not completed successfully (no function, link down); the Root Complex returns all ones.

  5. Is the NVMe CC register in configuration space?

    Model answer

    No, it is at BAR0 + 14h in memory space.

Intermediate

  1. Why must Command be written with a 16-bit access?

    Model answer

    A 32-bit write at 04h also writes Status, clearing any RW1C bits written back as 1.

  2. RsvdP versus RsvdZ?

    Model answer

    RsvdP: write back what you read; RsvdZ: write zero.

  3. What is a sticky bit?

    Model answer

    A bit not reinitialized by certain resets (with auxiliary power), so it can record events across them.

  4. How do byte enables map to offsets?

    Model answer

    Register Number is the DWORD index; each BE bit enables one byte within it: offset = 4 × index + byte.

  5. What does an extended header of all zeros at 100h mean?

    Model answer

    The function has no extended capabilities.

Advanced

  1. Which Root Port registers would you read first after a link problem?

    Model answer

    LnkSta (speed, width, DLLLA, training), LnkCtl, SltSta, AER status and Root Error Status/Source ID.

  2. What does Bridge Control bit 6 do?

    Model answer

    Secondary Bus Reset: resets the hierarchy below the bridge.

  3. How does CRS Software Visibility appear in configuration space?

    Model answer

    Root Capabilities reports support; Root Control bit 4 enables it.

  4. VSEC versus DVSEC?

    Model answer

    VSEC content is defined by the function's own vendor; DVSEC carries a designating vendor ID and DVSEC ID, so any organization can define it.

  5. Why does a capability walker need loop detection?

    Model answer

    Pointers come from hardware that may be faulty or hostile; a loop would hang the host.

Senior

  1. Review a script that "fixes" MPS with setpci … CAP_EXP+8.l=….

    Model answer

    It writes Device Status too (clears RW1C), it bypasses the kernel's MPS policy for the hierarchy, and it will be lost on reset; use the narrow width, coordinate the whole path, and prefer kernel parameters.

  2. How do you preserve evidence during a PCIe incident?

    Model answer

    Dump full configuration space of the device and every port above before any write, reset or driver action; capture kernel logs; only then act.

  3. What do resets do to configuration state, in principle?

    Model answer

    Non-sticky fields return to defaults; sticky ones persist per reset type and auxiliary power; software restores saved state afterwards.

  4. How would you validate a device's configuration space implementation?

    Model answer

    Attribute conformance per field (write 0/1 patterns), reset defaults, sticky behaviour across reset types, capability chain integrity, behaviour of reserved bits, compliance tools.

  5. A guest reports odd capability values. How do you reason?

    Model answer

    Compare host and guest views; identify fields the hypervisor emulates (e.g. MSI/MSI-X, BARs); only treat passthrough fields as device evidence.

Quiz

  1. A 16-bit write to offset 06h uses which First DW BE on which register number?

    • 0011b, 01h
    • 1100b, 01h
    • 1111b, 06h
    • 0011b, 06h
    Answer and reasoning

    Offset 06h is bytes 2–3 of DWORD 1.

  2. Writing 0 to an RW1C bit that is 1:

    • Clears it
    • Sets it
    • Has no effect
    • Is an error
    Answer and reasoning

    Only 1 clears.

  3. In the Root Port dump, what is the memory window?

    Model answer

    Base FE60h, limit FE60h → FE60_0000–FE6F_FFFF (1 MiB).

  4. What Device/Port Type does PCIe Capabilities 0142h indicate?

    • Root Port
    • Endpoint
    • Switch upstream port
    • RCiEP
    Answer and reasoning

    Bits 7:4 = 0100b = Root Port.

  5. Why did Trace 3's investigation reach a wrong conclusion?

    Model answer

    A 32-bit write at 04h cleared Status bit 12 before anyone recorded it.

  6. The extended header 0x1402_0001 means:

    Model answer

    ID 0001h (AER), version 2, next capability at 140h.

  7. Which attribute must software preserve when writing?

    • RO
    • RW1C
    • RsvdZ
    • RsvdP
    Answer and reasoning

    RsvdP must be written back as read.

  8. Why can polling configuration space hurt power and latency?

    Model answer

    Each read is a non-posted TLP that forces the link out of low-power states and stalls the CPU until completion.

  9. True or false: a configuration write's completion proves the new value is in effect.

    • True
    • False
    Answer and reasoning

    It proves acceptance; RO bits ignore writes, and some effects are delayed. Read back.

Teach-back

To a child

Model explanation

"Each machine has a panel. Some lights are look-only, some are switches, and alarm lights go off only when you press them. Press one button at a time, or you'll switch off alarms before anyone sees them."

To a junior engineer

Model explanation

"Every field has an attribute. Write with the narrowest width, read-modify-write to preserve reserved bits, and never write back a status register. Save a full dump before any change, read back after. Sticky bits may be from an earlier boot; all ones means the path failed."

To a senior engineer

Model explanation

"Configuration space is a contract of per-bit attributes plus reset semantics. Evidence preservation requires capturing state before tooling or recovery touches it; sticky status needs boot-time classification; and the view may be virtualized. Review every write path — kernel, firmware-first handlers, scripts — for width and RW1C safety."
