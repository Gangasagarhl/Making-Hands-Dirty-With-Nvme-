Chapter 24 decoded every Non-Volatile Memory Express (NVMe) controller register field by field. This module studies registers as a live interface: how accesses look on the wire, which writes are legal when, what each reset does to each register, how analyzers find registers in a capture, and how register evidence goes wrong.

Orientation

Knowing that CSTS is at 1Ch and that bit 0 is RDY is the start. The engineering questions are harder: Is this CC write a shutdown or a reset? Did the host wait long enough? Is this 0xFFFF_FFFF a value or a failure? Is the analyzer decoding offsets from the right BAR? Which register values survived the Function Level Reset the hypervisor just issued? This module answers those questions with traces of register sequences, an audit tool for write sequences, an analyzer-style decoder that learns BAR0 from configuration writes, and failure patterns where register evidence is misleading.

Kid story

Imagine the control box of a big ferris wheel. On the side is a metal plate that never changes: "carries 40 cars, takes up to 10 minutes to start". Inside the box are switches the operator sets, and lamps the wheel lights by itself: green for running, amber for "stopping safely", red for "broken". Some switches only work when the wheel is stopped — try to change the speed setting while it is running and nothing happens.

One switch is special. To stop the wheel safely, the operator must flip only the "stop safely" switch and leave the main power switch on, then wait for the amber lamp to say "all cars at the bottom". If she flips the main power off instead, the wheel jerks to a halt with people still at the top. Looking at the lamps is cheap for the operator but, in the computer version, every look costs a little trip down a long corridor.

The plate is CAP and VS; the switches are CC; the lamps are CSTS; "only when stopped" is the EN = 0 rule for CSS, MPS and AMS; the safe-stop switch is CC.SHN; flipping the main switch is clearing CC.EN; the corridor is the PCI Express (PCIe) round trip of a non-posted read.

Analogy boundary

  • Represents. Constant capability plates, host-owned switches, device-owned lamps, rules about when switches may change, and the difference between a safe stop and a hard stop.
  • Hides. The operator never touches switches one at a time: CC is one 32-bit word written all at once, so changing one field means rewriting all the others — the root of read-modify-write bugs. And the lamps can lie by omission: if the corridor is blocked (link down), the operator gets "all lamps on" (all-ones), which is not a state the wheel can be in.
  • Misleads. A real wheel's lamps change continuously; a register's value is only sampled when read. Between two CSTS reads, RDY may have gone 1 → 0 → 1 and the host would never know.

Access rules that matter on the wire

  • Width. 4-byte registers are accessed with 32-bit accesses; CAP, ASQ and ACQ may be accessed as one 64-bit access or as two 32-bit halves, low then high (Uncertain — confirm the exact ordering rule in the PCIe Transport Specification). In a trace, a 64-bit register written as two halves shows as either one MWr32 with Len = 2 or two MWr32 with Len = 1.
  • When. CSS, MPS, AMS and CRIME change only while EN = 0; AQA/ASQ/ACQ are latched at the 0→1 transition of EN; SHN is written while enabled.
  • How. CC changes are read-modify-write; NSSRO is cleared by writing 1; reserved bits are written as 0; NSSR acts only on its magic value.
  • Flush. After a sequence of posted writes, a register read guarantees they have arrived. Drivers rely on this before starting a timeout.
  • Cost. Each read stalls the issuing core for a full round trip (about a microsecond on the reference system, far more if the device is slow to complete). Polling loops must sleep; monitoring must not poll CSTS at high frequency.

Ready timeouts in 2.x

On a device that reports no controller ready modes (CAP.CRMS = 00b, like the Lab SSD), CAP.TO bounds every RDY transition. A device that supports ready modes reports two timeouts in CRTO — one for ready with media, one for ready independent of media — and the host uses the one matching the mode it selected with CC.CRIME. CAP.TO then still exists for compatibility. Version-dependent Confirm the CRTO field layout and the rule for which timeout applies in Base 2.4.

The ladder for the central concept: registers as a live interface

A ferris wheel's control box: fixed plate, switches that only work when stopped, lamps the wheel lights, a safe-stop switch distinct from the power switch.

CAP/VS are constants, CC is written whole by the host under timing rules, CSTS is reported by the controller and must be polled, NSSR and NSSRO are special-purpose.

A register file in the controller front end; firmware reacts to CC edges and maintains CSTS; the BAR decoder only responds when configuration space enables it.

Base 2.4 defines properties, their reset values and modification rules; PCIe Transport 1.4 defines offsets, access widths and PCIe-specific behaviour.

Posted MWr32 for writes, non-posted MRd32 + CplD for reads (BAR0 below 4 GiB); failed reads become UR or timeouts and all-ones.

In a capture, register traffic clusters around life-cycle events: CAP/VS reads at probe, CC write + CSTS polling at enable, reset and shutdown, single CSTS reads in error handlers.

Decode every CC value against the previous one; check timing against CAP.TO/CRTO/RTD3E; distrust all-ones; confirm the BAR base before believing any offset.

The sixteen questions for registers as a live interface

1. What is it?
The rules and timing by which host and controller use the register file over PCIe.
2. Why was it created?
To bootstrap, reconfigure, reset and shut down the controller without queues.
3. What problem does it solve?
Safe life-cycle control with minimal register traffic.
4. What existed before?
AHCI's per-port register interface, used per command.
5. Why is it better?
Registers only at life-cycle edges; the I/O path uses only doorbell writes.
6. Who creates the accesses?
The host driver (and, dangerously, any other software that maps the BAR).
7. Who consumes them?
Controller hardware and firmware.
8. Where does it live?
BAR0 of the PCIe function.
9. What memory/registers are involved?
CAP, VS, CC, CSTS, AQA, ASQ, ACQ, NSSR, INTMS/INTMC, CRTO; config-space BARs and Command register.
10. What happens before?
Enumeration and BAR assignment; Memory Space Enable.
11. What happens after?
Queues take over; registers return at the next life-cycle event.
12. What happens if it is wrong?
Lost enables, accidental resets instead of shutdowns, unsafe shutdowns, undefined behaviour.
13. What does the analyzer show?
MWr32/MRd32 to BAR0 offsets, interpretable only with the right BAR base and DSTRD.
14. What does Linux show?
nvme show-regs, CSTS values in kernel messages, shutdown timeout messages.
15. What would a validation engineer test?
Reset values per reset type, illegal writes, access widths, timing bounds, RW1C behaviour.
16. What would a senior engineer suspect?
A CC write that is not what the author intended, or a register value that is not a value at all.

The register offsets used in this module (CAP 00h, VS 08h, INTMS 0Ch, INTMC 10h, CC 14h, CSTS 1Ch, NSSR 20h, AQA 24h, ASQ 28h, ACQ 30h, doorbells from 1000h), the CC fields EN/CSS/MPS/AMS/SHN/IOSQES/IOCQES, the CSTS fields RDY/CFS/SHST/NSSRO/PP and the NSSR value 4E56_4D65h.

The reset matrix entries marked derived follow from "Conventional and Function Level Reset return the function to its initial state"; the posted-write flush follows from PCIe ordering rules; "all-ones means failed read" follows from root complex behaviour, which is platform-dependent but nearly universal.

  • The specification does not define what a controller does with CSS/MPS/AMS writes while enabled — only that the host shall not make them.
  • It does not define how often a host polls CSTS, nor how a host chooses its shutdown timeout (RTD3E is an estimate).
  • It does not guarantee that a CC readback shows fields the controller rejected.
  • Check in the specification: the 64-bit access ordering rule; exactly which properties a Controller Reset preserves; CRTO layout; whether NSSRO survives a Controller Reset.

Never write CC without reading it first; never decode all-ones; never trust an offset until you have the BAR base from the same capture or system state; never let two pieces of software own the register file.

Hardware view

Hardware participation
CategoryHardware

May participateIOMMU interrupt and DMA remapping (not for MMIO itself); a hypervisor trapping BAR accesses for emulation; PCIe switches routing by address

Internal, unobservableWhen firmware noticed a CC edge; how long it took to update CSTS; whether a write was accepted or silently ignored

Register reads are the one place where the CPU waits on the device. A device whose firmware is busy may complete register reads slowly; a device in a deep power state may not complete them at all until it wakes; a function in reset returns Unsupported Request or nothing. That makes MMIO read latency itself a health signal — and makes high-frequency CSTS polling a performance bug.

Any software that can map the BAR (a user-space tool through sysfs, a debugger, a hypervisor, a management agent) can write CC. A stray EN = 0 from a second owner looks exactly like a controller-initiated reset from the driver's point of view. Kernel lockdown and IOMMU-based device assignment exist partly to keep one owner per register file.

Ordering: a CSTS read issued after a CC write from the same CPU cannot overtake it, so polling immediately after a write is safe. Writes from two CPUs to two registers have no order guarantee. A failed posted write produces no completion; the host learns nothing unless the device logs an error (Advanced Error Reporting) — which is why read-back is the only proof a write landed.

Why it is ambiguous. At least four stories fit: (a) the request or its completion was lost during link recovery and the root port's completion timeout fired (the timeout value is platform-configured and may be much shorter or longer than the 50 ms shown); (b) the device was briefly unable to complete MMIO (for example a firmware stall) and the read timed out; (c) another agent issued an FLR or hot reset between reads (but then row 4 would show RDY = 0 and queues would be gone — they were not, which weakens this story); (d) the monitoring agent read through a stale mapping (but then later reads would fail too).

Disambiguating evidence. The root port's AER status (Completion Timeout logged? correctable Receiver or Replay errors at the same time?), the analyzer's link-state record, and the device's error log. Recovery plus a Completion Timeout entry makes (a) strong. Confidence before checking: low. Lesson: one all-ones read is a PCIe event to correlate, not a controller state to decode — and an agent that resets the controller on a single all-ones read turns a 2 ms hiccup into an outage.

Labs

All four labs are Safe lab: synthetic values and pure software. Never write CC, NSSR, AQA, ASQ or ACQ on a real device from user space — not even "just to test" — because the driver owns the register file and a stray write is a controller reset or a subsystem reset.

Beginner lab — Decode a shutdown by hand

Objective

Decode CC and CSTS values field by field and decide whether a shutdown sequence was correct.

Prerequisites

NVMe Registers (CC and CSTS layouts); the mechanism section above.

Setup (two synthetic register logs)

  • Log A: read CC = 0x0046_0061; write CC = 0x0046_4061; CSTS reads 0x1, 0x5, 0x5, 0x9.
  • Log B: read CC = 0x0046_0061; write CC = 0x0046_8060; CSTS reads 0x0, 0x0, 0x0 …

Procedure

  1. For each CC value, write out EN, CSS, MPS, AMS, SHN, IOSQES and IOCQES.
  2. For each CSTS value, write out RDY, CFS, SHST, NSSRO and PP.
  3. Mark the first value in each log that departs from a correct normal shutdown.

Observations

Note which bits change between consecutive CC values, not just the values themselves.

Questions

  1. Is log A a correct normal shutdown? How long did it take if CSTS was polled every 10 ms?
  2. What did the host in log B ask for, and what did it actually do?
  3. Will the SMART / Health unsafe-shutdown count increase after log B if power is removed?

Expected reasoning

Shutdown changes only SHN with EN staying 1; SHST must reach 10b; any EN 1→0 is a reset.

Solution

0x0046_0061: EN 1, CSS 110b (bits 6:4), MPS 0 (4 KiB), AMS 000b, SHN 00b, IOSQES 6 (64 B), IOCQES 4 (16 B). 0x0046_4061 differs only in bits 15:14 = 01b: normal shutdown, correct. CSTS 0x1 → RDY; 0x5 → RDY + SHST 01b (processing); 0x9 → RDY + SHST 10b (complete). Log A is correct; with four polls 10 ms apart it took between 20 and 30 ms after the write (the first poll saw no reaction yet).

0x0046_8060: SHN = 10b (abrupt shutdown) and EN = 0. The host asked for an abrupt shutdown but also cleared EN, so the controller performs a Controller Reset; CSTS 0x0 confirms it (RDY 0, SHST 00b). Whether this controller also did any shutdown processing is unknown, so assume it did not: if power is removed now, the unsafe-shutdown count increases. The fix is the same as in the failed trace — read-modify-write and leave EN alone.

Extension

Write the CC value for "abrupt shutdown" done correctly, and the CSTS sequence you would expect.

Intermediate lab — Audit register sequences against life-cycle rules

Objective

Encode the register rules from this module as an automatic checker and run it on good and bad sequences.

Prerequisites

The access rules and reset matrix above; Python 3.

Setup

#!/usr/bin/env python3
"""Audit a sequence of NVMe register accesses against life-cycle rules.
Input: (op, register, value) with op 'W' (host write) or 'R' (host read result).
Teaching tool for the course's synthetic Lab SSD; confirm rules in the spec."""

CAP = 0x0040_0830_1401_0FFF          # Lab SSD: NSSRS=1, AMS RR only, CRMS=0
MSIX_ENABLED = True

def f(v, hi, lo):
    return (v >> lo) & ((1 << (hi - lo + 1)) - 1)

def audit(seq, cap=CAP, msix=MSIX_ENABLED):
    cc, rdy, findings = 0, 0, []
    for i, (op, reg, val) in enumerate(seq, 1):
        if op == "R":
            if val == 0xFFFF_FFFF:
                findings.append(f"{i}: {reg} read all-ones: not a register value (link/device/BAR)")
                continue
            if reg == "CC":
                cc = val                     # learn the current configuration
            if reg == "CSTS":
                rdy = val & 1
                if f(val, 3, 2) == 3:
                    findings.append(f"{i}: CSTS.SHST = 11b is reserved: suspicious value")
            continue
        if reg == "CC":
            old_en, new_en = cc & 1, val & 1
            if old_en and new_en:
                for name, hi, lo in (("CSS", 6, 4), ("MPS", 10, 7), ("AMS", 13, 11), ("CRIME", 24, 24)):
                    if f(cc, hi, lo) != f(val, hi, lo):
                        findings.append(f"{i}: CC.{name} changed while EN=1")
            if old_en and not new_en and f(val, 15, 14):
                findings.append(f"{i}: CC write sets SHN but clears EN: a reset, not a shutdown (no read-modify-write?)")
            if not old_en and new_en and rdy:
                findings.append(f"{i}: CC.EN=1 written while last observed CSTS.RDY=1 (wait for RDY=0)")
            if new_en and f(val, 13, 11) == 1 and not f(cap, 17, 17):
                findings.append(f"{i}: CC.AMS=WRR but CAP.AMS bit 17 = 0")
            if new_en and f(val, 24, 24) and not f(cap, 60, 59):
                findings.append(f"{i}: CC.CRIME=1 but CAP.CRMS reports no ready modes")
            cc = val
        elif reg in ("AQA", "ASQ", "ACQ") and cc & 1:
            findings.append(f"{i}: {reg} written while CC.EN=1 (no effect on the running admin queue)")
        elif reg == "NSSR":
            if not f(cap, 36, 36):
                findings.append(f"{i}: NSSR written but CAP.NSSRS = 0")
            elif val == 0x4E56_4D65:
                findings.append(f"{i}: NVM Subsystem Reset issued: every controller and port resets")
        elif reg in ("INTMS", "INTMC") and msix:
            findings.append(f"{i}: {reg} accessed while MSI-X is enabled (undefined behaviour)")
    return findings or ["no rule violations found"]

if __name__ == "__main__":
    good_shutdown = [("R", "CSTS", 0x1), ("R", "CC", 0x0046_0061),
                     ("W", "CC", 0x0046_4061), ("R", "CSTS", 0x5), ("R", "CSTS", 0x9)]
    bad_shutdown = [("R", "CSTS", 0x1), ("R", "CC", 0x0046_0061),
                    ("W", "CC", 0x0000_4000), ("R", "CSTS", 0x0)]
    messy = [("W", "CC", 0x0046_0060), ("R", "CSTS", 0x1), ("W", "AQA", 0x001F_001F),
             ("W", "CC", 0x0046_0861), ("W", "INTMS", 0x1), ("W", "CC", 0x0046_00E1),
             ("R", "CSTS", 0xFFFF_FFFF), ("W", "NSSR", 0x4E56_4D65)]
    for name, seq in (("good shutdown", good_shutdown), ("bad shutdown", bad_shutdown), ("messy", messy)):
        print(f"[{name}]")
        for line in audit(seq):
            print("  ", line)

Procedure

  1. Run it. Expected: the good shutdown has no violations; the bad shutdown is flagged at step 3; the messy sequence is flagged at steps 4 (twice), 5, 6 (twice), 7 and 8.
  2. Predict each finding in the messy sequence before reading the output.
  3. Add log B from the beginner lab and confirm the checker flags it.

Observations

Note which findings are protocol violations (host broke a "shall") and which are evidence warnings (a value you must not decode).

Questions

  1. Why does the checker need CC reads as well as writes?
  2. Step 3 of the messy sequence (AQA written) is not flagged. Why is that correct?
  3. What rule would catch a host that never waits for SHST = 10b?

Expected reasoning

Rules about "changed while enabled" need the current value; rules about timing need timestamps the input lacks.

Solution

(1) The checker compares each write against the current CC value. A capture that starts mid-run has never seen the enable write, so the read at step 2 teaches it the running value; without it, the bad shutdown's write would look like a write from a disabled state. (2) Step 1 cleared EN, so at step 3 the controller is disabled and AQA may be written — the messy sequence's first violation is step 4, which sets EN while the last observed RDY was still 1. (3) A rule that, after any write setting SHN, requires a CSTS read with SHST = 10b before the sequence ends (or before a power event marker); it needs a "power removed" event type in the input.

Extension

Add timestamps and two timing rules: RDY must follow an EN change within CAP.TO, and SHST = 10b must follow SHN within the host's shutdown timeout; then replay the slow trace.

Advanced lab — Decode MMIO traffic with a moving BAR

Objective

Build the decoding step an analyzer performs — address to register name — and see how it fails when the BAR moves.

Prerequisites

The protocol view; BARs and MMIO; doorbell stride from NVMe Registers.

Setup

#!/usr/bin/env python3
"""Decode host MMIO TLPs to NVMe register names, learning BAR0 from config
writes the way an analyzer must. Input is a simplified synthetic trace."""

REGS = {0x00: "CAP", 0x04: "CAP(hi)", 0x08: "VS", 0x0C: "INTMS", 0x10: "INTMC",
        0x14: "CC", 0x1C: "CSTS", 0x20: "NSSR", 0x24: "AQA", 0x28: "ASQ",
        0x2C: "ASQ(hi)", 0x30: "ACQ", 0x34: "ACQ(hi)"}

TRACE = """
CfgWr0 01:00.0 reg=0x10 data=0xFE600004
CfgWr0 01:00.0 reg=0x14 data=0x00000000
MRd32 addr=0xFE600000 len=2
MRd32 addr=0xFE60001C len=1
MWr32 addr=0xFE600014 len=1 data=0x00460061
MWr32 addr=0xFE601000 len=1 data=0x00000001
MWr32 addr=0xFE60100C len=1 data=0x00000012
MWr32 addr=0xFE601010 len=1 data=0x00000005
CfgWr0 01:00.0 reg=0x10 data=0xFE400004
MWr32 addr=0xFE601008 len=1 data=0x00000002
MWr32 addr=0xFE401008 len=1 data=0x00000002
"""

def parse(line):
    kind, *rest = line.split()
    fields = dict(x.split("=") for x in rest if "=" in x)
    return kind, {k: int(v, 16) if v.startswith("0x") else v for k, v in fields.items()}

def name_offset(off, dstrd):
    if off in REGS:
        return REGS[off]
    if off >= 0x1000:
        idx, rem = divmod(off - 0x1000, 4 << dstrd)
        if rem == 0:
            qid, is_cq = divmod(idx, 2)
            return f"{'CQ' if is_cq else 'SQ'}{qid}{'HDBL' if is_cq else 'TDBL'}"
        return "between doorbells (stride mismatch?)"
    return "reserved/optional register"

def decode(trace, dstrd=0, bar_size=16 * 1024):
    bar_lo = bar_hi = 0
    for line in trace.strip().splitlines():
        kind, f = parse(line)
        if kind == "CfgWr0" and f["reg"] in (0x10, 0x14):
            if f["reg"] == 0x10:
                bar_lo = f["data"] & ~0xF          # memory BAR: low 4 bits are attributes
            else:
                bar_hi = f["data"]
            print(f"{line:45} -> BAR0 now 0x{(bar_hi << 32) | bar_lo:X}")
            continue
        base, addr = (bar_hi << 32) | bar_lo, f.get("addr", 0)
        if not base <= addr < base + bar_size:
            print(f"{line:45} -> outside BAR0: not this controller (or stale BAR)")
            continue
        reg = name_offset(addr - base, dstrd)
        extra = f" value 0x{f['data']:X}" if "data" in f else ""
        print(f"{line:45} -> {reg}{extra}")

if __name__ == "__main__":
    decode(TRACE)

Procedure

  1. Run it. Expected: the first eight accesses decode to CAP, CSTS, CC, SQ0TDBL, CQ1HDBL and SQ2TDBL; after the configuration write moves BAR0 to 0xFE40_0000, the write to 0xFE60_1008 is reported as outside BAR0 and the write to 0xFE40_1008 decodes as SQ1TDBL.
  2. Change dstrd to 1 and rerun. Explain the new names.
  3. Delete the first two lines of the trace (a capture started late) and rerun.

Observations

Record which decodes changed with each edit.

Questions

  1. With DSTRD = 1, what is 0xFE60_100C?
  2. What does a capture that starts after enumeration need from the user before it can decode anything?
  3. Who could legitimately write 0xFE60_1008 after the BAR moved?

Expected reasoning

Stride = 4 << DSTRD; register names are offsets from a base that only configuration space defines.

Solution

(1) Stride 8: offset 0x00C − 0x000 = 12 is not a multiple of 8, so the tool reports "between doorbells" — on a DSTRD = 1 device the driver would never write there; 0x1008 would be CQ0HDBL. (2) The BAR base (from lspci or a configuration read captured earlier). Without it every access is "outside BAR0". Analyzers that guess a base produce confident nonsense. (3) Nobody associated with this function: a driver still using a mapping from before the move (a real bug, typically after a hot-plug or resource rebalance) or another device that now owns that range. Either way, it is not an SQ1 doorbell.

Extension

Teach the decoder 64-bit BARs (type field 10b) and a second function, then decode the dual-port trace from NVMe Subsystem.

Senior forensic lab — Slow boots after a "tuning" change

Objective

Find the root cause of a fleet-wide rise in boot time and probe failures using register, log and timing evidence only.

Prerequisites

All traces in this module; Power Management background.

Setup (synthetic incident record)

  • Week 0: a platform change rolled out a host tuning profile and, separately, a drive firmware update across the fleet.
  • Weeks 1–3: median NVMe ready time at boot rises from 0.4 s to 6.5 s; 0.3 % of boots log "Device not ready; aborting initialisation" from boot firmware, which waits only 5 s.
  • SMART / Health: unsafe shutdowns increase by one per reboot on 92 % of drives (before: about one per month).
  • Identify Controller after the firmware update: RTD3E = 0 (not reported). Before: 8,000,000 µs.
  • The tuning profile sets the host driver's shutdown timeout parameter to 2 s ("faster reboots").
  • Kernel logs at shutdown: "shutdown timeout, disable controller" on most hosts. Lab measurements of the drive: normal shutdown takes 3–7 s with a full write cache.
  • Drives in a test rack with the new firmware but without the tuning profile: no change in unsafe shutdowns.

Procedure

  1. Build a causal chain from reboot to slow ready.
  2. Separate the two changes and decide the role of each.
  3. Decide what evidence would prove the chain on a single host.
  4. Write remediation and prevention.

Observations

Note what the kernel message says the host did after the timeout.

Questions

  1. Why did neither change alone cause the problem?
  2. Why does an unsafe shutdown make the next ready time long?
  3. Which counter proves the hypothesis cheaply across the fleet?
  4. What test would have caught this before rollout?

Expected reasoning

Effective host wait = function of RTD3E and the parameter; if the device stops reporting RTD3E, the parameter decides. A wait shorter than real shutdown time turns every reboot into an unsafe shutdown.

Solution

Chain: on reboot the host writes SHN = 01b (correctly) and waits. With RTD3E = 0 the driver falls back to its parameter, now 2 s; real shutdown takes 3–7 s, so the driver times out, disables the controller (EN = 0) and the platform reboots before shutdown completes. The drive records an unsafe shutdown; at the next enable it rebuilds its mapping state, so RDY takes seconds (the slow trace); boot firmware with a 5 s budget gives up on the slowest drives.

(1) With the old firmware, RTD3E = 8 s let the driver wait long enough despite the low parameter — in drivers that use RTD3E as the bound and the parameter as a floor. (Check your kernel's driver: how it combines the two is implementation-specific.) Without the tuning profile, the default parameter was longer than real shutdown time. (2) Mapping tables and cache contents were not saved, so the drive must rebuild or replay them before declaring ready. (3) SMART / Health unsafe shutdowns per reboot. (4) A reboot loop on the new firmware with the production host profile, asserting SHST = 10b before power-off and unsafe-shutdown delta = 0.

Single-host proof: reboot with tracing of CC/CSTS (or kernel debug logs), observe the timeout before SHST = 10b and an unsafe-shutdown increment; repeat with the parameter at 10 s and observe SHST = 10b and no increment. Remediation: remove the override; ask the vendor to restore a realistic RTD3E (reporting 0 is legal but unhelpful); keep the boot firmware budget at least CAP.TO. Confidence: high after the A/B reboot.

Extension

Estimate data-at-risk: what does a drive with a volatile write cache lose when shutdown is cut short, and which feature (Volatile Write Cache, Flush) bounds it?

Debugging

Pattern 1 — Every register reads all-ones

Symptom
show-regs or the driver reports CAP, CC and CSTS as 0xFFFF_FFFF (or 0xFFFF_FFFF_FFFF_FFFF).
Possible causes
Link down or in recovery; device in D3cold or removed; Memory Space Enable cleared; BAR moved or unassigned; function in reset.
Evidence
lspci -vv (does configuration space respond? Region 0 address, Control: Mem+), link status, AER logs.
First check
Does configuration space read correctly? If not, it is the link or device presence.
Second check
Is Memory Space enabled and is BAR0 the address software uses?
Disambiguating experiment
Read the vendor ID through configuration space and CAP through MMIO back-to-back; one working and the other not isolates the BAR path.
Likely conclusion
A PCIe-level or power problem; never a controller state.
Confidence
High after the configuration read.

Pattern 2 — CC readback differs from what was written

Symptom
The driver writes a CC value and reads back something else, or enable fails with no CFS.
Possible causes
Writes to fields the controller does not support (AMS, CSS bits, CRIME) ignored; reserved bits written; write raced with another agent; write dropped (posted, not decoded).
Evidence
CAP fields (AMS, CSS, CRMS, MPSMIN/MPSMAX); the exact value written; analyzer capture.
First check
Bitwise XOR written ⊕ read: which fields differ?
Second check
Are those fields supported according to CAP?
Disambiguating experiment
Write with only supported fields set and compare.
Likely conclusion
Host requested an unsupported capability; fix the host's CAP checks.
Confidence
Medium-high; readback of rejected fields is implementation-dependent.

Pattern 3 — SHST stuck at 01b

Symptom
Shutdown never completes within the host timeout; CSTS stays 0x5.
Possible causes
Large cache flush on a slow or worn device; firmware hang during shutdown; I/O still outstanding (queues not deleted); thermal throttling.
Evidence
Time from SHN to timeout; RTD3E; whether I/O queues were deleted first; device temperature and error logs.
First check
Measure real shutdown time with a long timeout on a test host.
Second check
Compare with RTD3E and with the same device after a Flush.
Disambiguating experiment
Issue Flush, wait for completion, then shut down: if SHST reaches 10b quickly, cache flush time was the cause; if it still hangs, suspect firmware.
Likely conclusion
Usually real flush time exceeding the host wait; occasionally a firmware defect.
Confidence
Medium.

Pattern 4 — RDY drops to 0 with no host reset

Symptom
Driver sees CSTS = 0x0 during normal operation; all queues lost; kernel resets the controller.
Possible causes
Another agent wrote CC (user-space tool, management agent, debugger with the BAR mapped); an FLR from virtualization software; NSSR from another host (NVMe Subsystem); controller firmware reset itself.
Evidence
Which processes have the BAR mapped (/proc/*/maps for the resource file); hypervisor logs; NSSRO; analyzer capture of MWr to 14h.
First check
Was NSSRO set? (Points to a subsystem reset.)
Second check
Is anything else mapping the resource file?
Disambiguating experiment
Capture MMIO writes to offset 14h: a host-originated EN = 0 write proves another software owner.
Likely conclusion
Second owner of the register file, more often than device fault.
Confidence
High with a capture; low without.

Pattern 5 — Latency spikes correlated with a monitoring agent

Symptom
CPU stalls and tail latency spikes every few seconds; perf shows time in a register read.
Possible causes
An agent reads registers (show-regs, CSTS, CAP) at high frequency; each MMIO read stalls the core until the completion returns; a busy or low-power device completes slowly.
Evidence
Agent configuration; MRd count on the analyzer; spike period.
First check
Does stopping the agent remove the spikes?
Second check
Measure MMIO read latency (analyzer MRd→CplD).
Disambiguating experiment
Change the polling interval and watch the spike period follow it.
Likely conclusion
Monitoring by register polling; use logs and events instead.
Confidence
High when the period follows the setting.

Pattern 6 — Analyzer reports writes to "unknown registers"

Symptom
Decoded trace shows writes to reserved offsets or to "between doorbells", or doorbells for queues that do not exist.
Possible causes
Wrong BAR base in the analyzer; BAR moved during capture; DSTRD assumed 0; stale driver mapping; traffic belongs to another function.
Evidence
Configuration writes to BAR offsets in the capture; CAP.DSTRD; the requester and completer IDs.
First check
Confirm the base from lspci at the time of capture.
Second check
Confirm the stride from CAP.
Disambiguating experiment
Re-decode with the correct base and stride (the advanced lab's tool); if anomalies remain, they are real.
Likely conclusion
Decoder configuration, unless anomalies survive re-decoding — then a stale mapping bug.
Confidence
High after re-decoding.

Interview

Beginner

  1. What is the difference between CC and CSTS?

    Model answer

    CC is what the host asks for (enable, shutdown, sizes, arbitration); CSTS is what the controller reports (ready, fatal, shutdown status, subsystem reset occurred, processing paused).

  2. How does a host request a normal shutdown?

    Model answer

    Read CC, set SHN to 01b leaving EN at 1, write it, then poll CSTS until SHST = 10b.

  3. Why is a read of 0xFFFF_FFFF suspicious?

    Model answer

    It is what the root complex returns when a read fails; it is not a real register value.

  4. Where do the doorbells live?

    Model answer

    In BAR0 from offset 1000h, alternating SQ tail and CQ head per queue, spaced by 4 << CAP.DSTRD bytes.

  5. What does CAP.TO tell the host?

    Model answer

    The worst-case time, in 500 ms units, the host should wait for RDY to change after changing EN.

Intermediate

  1. Why must CC be written with read-modify-write?

    Model answer

    One write sets every field. Writing a constant changes fields the host did not mean to change — most dangerously EN, turning a shutdown into a reset.

  2. Which CC fields may only be changed while EN = 0?

    Model answer

    Those that define the running controller: CSS, MPS, AMS (and CRIME). IOSQES/IOCQES are set before creating I/O queues.

  3. What is NSSRO and how is it cleared?

    Model answer

    CSTS bit 4, set after an NVM Subsystem Reset; cleared by writing 1 to it (write-1-to-clear).

  4. Why should register writes be confirmed by reads?

    Model answer

    MWr is posted: no completion, no error to the host if it is dropped. Only a read proves the state.

  5. When is CRTO used instead of CAP.TO?

    Model answer

    When the controller supports ready modes (CAP.CRMS non-zero); CRTO gives separate bounds for ready-with-media and ready-independent-of-media. Check its layout in the specification.

Advanced

  1. A trace shows CC = 0x0000_4000 written during shutdown. Explain the consequences.

    Model answer

    EN goes 1→0: a Controller Reset. Queues are torn down; SHST will not reach 10b; if power is removed the drive records an unsafe shutdown and the next ready takes longer.

  2. Why can't you trust a single all-ones CSTS to mean the controller failed?

    Model answer

    It can be a completion timeout from link recovery, a transient device stall or a stale mapping; correlate with AER, link state and subsequent reads.

  3. How would you prove another process reset the controller?

    Model answer

    Capture MWr to CC with EN = 0 not issued by the driver (timing or analyzer); check which processes map the resource file; check hypervisor FLR logs and NSSRO.

  4. Why is high-frequency register polling harmful?

    Model answer

    Each MMIO read blocks the CPU until a completion returns; a slow device turns monitoring into latency spikes; it also contends with firmware.

  5. What does an analyzer need to decode MMIO correctly?

    Model answer

    The BAR base (and its changes), CAP.DSTRD, and which function owns the addresses.

Senior

  1. Unsafe shutdowns rise by one per reboot fleet-wide. Plan the investigation.

    Model answer

    Correlate with recent changes (host profiles, firmware); trace one reboot (CC/CSTS timing); compare host wait to actual shutdown time and RTD3E; A/B the suspected parameter; verify the next-boot ready time drops.

  2. Design a register-access policy for a storage driver.

    Model answer

    Single owner; read-modify-write; confirm writes by reads; bounded waits from CAP.TO/CRTO/RTD3E; treat all-ones as PCIe events; no polling on the I/O path; log every CC write with old and new values.

  3. How do you validate a device's CAP.TO claim?

    Model answer

    Measure ready time across clean and unsafe shutdowns, full and empty devices, temperature corners; compare the worst case to the bound and track margin over firmware releases.

  4. A vendor reports RTD3E = 0. What do you do?

    Model answer

    Treat it as "unknown"; measure shutdown time; set the host's wait above the worst measurement; ask the vendor for a real estimate.

  5. What register behaviour would you test in a qualification suite?

    Model answer

    Enable/disable timing versus CAP.TO; shutdown completion versus RTD3E; reserved-bit handling; unsupported-field writes; NSSR and NSSRO; FLR and register contents; behaviour under concurrent MMIO reads.

Quiz

  1. CC = 0x0046_4061. What is the controller doing?

    • Disabled
    • Enabled, normal shutdown requested
    • Enabled, abrupt shutdown requested
    • Resetting
    Answer and reasoning

    EN = 1, SHN = 01b.

  2. CSTS = 0x0000_0009 means:

    • Fatal status
    • Shutdown processing
    • Ready and shutdown complete
    • Subsystem reset occurred
    Answer and reasoning

    Bit 0 RDY = 1; bits 3:2 = 10b.

  3. CAP.TO = 0x14. Maximum RDY wait?

    • 20 ms
    • 2 s
    • 5 s
    • 10 s
    Answer and reasoning

    20 × 500 ms.

  4. With DSTRD = 0, what is offset 100Ch?

    • CQ1HDBL
    • SQ1TDBL
    • CQ3HDBL
    • SQ3TDBL
    Answer and reasoning

    1000h + (2·1 + 1)·4 = 100Ch.

  5. Which value starts an NVM Subsystem Reset?

    • 0x0000_0001
    • 0xFFFF_FFFF
    • 0x4E56_4D65 to NSSR
    • 0x0000_0010 to CSTS
    Answer and reasoning

    The ASCII "NVMe" value. Writing 10h to CSTS clears NSSRO.

  6. What is the first abnormal event in the failed trace?

    Model answer

    The CC write 0x0000_4000: it clears EN while requesting shutdown.

  7. Why are MWr failures invisible to the host?

    Model answer

    Memory writes are posted: no completion is returned.

  8. What can change between two healthy CSTS reads without trace in either?

    Model answer

    A reset and re-enable, a transient fatal state, a link recovery — reads are samples, not history.

  9. In the ambiguous trace, which evidence most strengthens the link-recovery story?

    Model answer

    A root port Completion Timeout logged at the same time as correctable link errors and the recorded Recovery state.

Teach-back

To a child

Model explanation

"The SSD has a little control panel with switches and lights. To turn the ride off safely you flip only the 'stop safely' switch and wait for the 'safe' light. If you slam every switch to off at once, the ride stops in a hurry and the next start takes much longer while it cleans up."

To a junior engineer

Model explanation

"Registers are memory-mapped at BAR0. CAP tells you limits, CC is your request, CSTS is the answer. Always read-modify-write CC; change one thing; poll CSTS until the terminal state with a bounded wait from CAP.TO or RTD3E. Never decode all-ones; never write CC from a second program."

To a senior engineer

Model explanation

"Register bugs are host bugs with delayed symptoms: a constant CC write turns shutdown into reset and shows up as unsafe-shutdown counts and slow next-boot ready times. Treat MMIO as PCIe transactions — posted writes are unconfirmed, failed reads are synthetic — keep one owner per register file, budget waits from CAP.TO/CRTO/RTD3E, and track ready and shutdown times in fleet telemetry."

Mastery gate

Do not consider this module mastered until you can:

  • explain each register's purpose and the access rules (read-modify-write, enabled-only fields, write-1-to-clear, reserved bits);
  • diagram enable, normal shutdown and reset as register sequences;
  • identify in traces a correct shutdown, a slow ready, a shutdown turned reset and a transient all-ones read;
  • debug the six failure patterns;
  • distinguish the register file from configuration space (BARs and MMIO), from the admin interface (Admin Queues), from controller behaviour (NVMe Controller), from doorbell flow (Doorbells) and from power states (Power Management);
  • cite the NVM Express Base Specification (Controller Properties, Initialization, Shutdown, Resets) and the NVMe over PCIe Transport Specification (Controller Registers) by section name.
