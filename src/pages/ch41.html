A real trace never contains one command. It contains hundreds, interleaved, completing out of order, on several queues, with PCIe tags being reused every few microseconds. This chapter teaches the method protocol analysts use to pull one command's thread out of that tangle: which key links each stage to the next, how long each key stays valid, and how to prove a match instead of guessing it.

Why this chapter exists

In The Most Important Chapter and End-to-End Write you followed single commands. The traces were easy to read because nothing else was happening. In practice an analyzer capture of a busy SSD shows thousands of TLPs per millisecond, and the question you are asked is never "what is a TLP?" but "which of these TLPs belong to the command that failed, and in what order did its stages happen?"

Answering that is the core skill of NVMe-over-PCIe protocol analysis. It is not hard once you see the structure: every stage of a command is linked to the next by a specific key (an address, an index, a tag, an identifier), and each key has a scope and a lifetime. Use the right key for each link, respect its lifetime, and the thread comes out cleanly. Use the wrong key, the tag to find the command, or the CID without its queue, and you will confidently connect TLPs that have nothing to do with each other.

This chapter trains that thinking until it is automatic. The method also underlies the automated tools in Automated Trace Analysis and the forensic process in Error Correlation.

Learning objectives

  • State the correlation chain: NVMe command ↔ queue location ↔ controller access ↔ PCIe requester/completer ↔ address ↔ tag ↔ completion ↔ interrupt, and the key that joins each pair.
  • Turn a doorbell write into (queue, new tail, number of new entries), and a fetch address into (queue, slot, number of entries).
  • Match non-posted requests to completions by Requester ID and tag, including split completions, and explain why tags must never be used to identify NVMe commands.
  • Identify a command by (SQ Identifier, Command Identifier) and explain why CID alone is ambiguous.
  • Attribute data TLPs to commands by address range from decoded PRP entries, for reads (device Memory Writes) and writes (device Memory Reads and Completions).
  • Link CQEs to commands and MSI-X messages to completion queues, handling many CQEs per interrupt and out-of-order completion.
  • Align host-side Linux tracepoints with analyzer time.
  • Untangle an interleaved trace of four concurrent commands on two queues by hand and with a script.

The story

At a busy airport, many families check in at once. Every suitcase gets a sticker with a number, but the stickers are reused every day, so a sticker number alone does not tell you whose suitcase it is today. To find your bag you need to know which flight (the queue), which seat (the slot), and your family name on the booking (the command identifier). The bag belt does not care whose bag is whose; it just carries bags. The person at the lost-and-found desk solves puzzles: "This bag came off flight 1, seat 17, the booking says Garcia family, so it is the Garcias' bag, even though the Garcias' friends on flight 2 also have a booking called Garcia."

A courier company's depot scanner log. Each line records "parcel scanned at door 3 at 10:02:17, route sticker 42." Route stickers are reused all day; customer orders are identified by account number plus order number; parcels for one order may come off several trucks and arrive in any order; and one "your delivery is ready" text message may announce several orders. To answer a customer complaint you work from the order (account plus order number) to the delivery addresses it lists, then to the scans at those addresses, using each sticker number only for the few minutes it was attached to one parcel.

  • Addresses carry more meaning in NVMe. In the depot story an address is just a destination; on PCIe the address of a fetch also tells you which queue and which slot the command came from, and the address of a data write tells you which command it belongs to.
  • Some events have no label at all. Posted writes (data for reads, CQEs, MSI-X, doorbells) have no tag that means anything. Every parcel in the analogy has a sticker.
  • The order number is inside the parcel. The CID is visible only in payloads (the SQE fetch completion and the CQE), never in TLP headers. The analogy suggests it is on the outside.
  • Some deliveries are invisible. An analyzer sees one link. Anything the IOMMU blocks, anything inside the SSD, and anything on another link is not in the log.

Beginner explanation

Each NVMe command leaves a trail of packets on the PCIe link: a doorbell, a fetch, data, a completion entry, an interrupt, another doorbell. When many commands run at once, their trails overlap. Correlation is the job of saying which packets belong to which command.

The trick is that you cannot use one label for the whole trail. Different parts of the trail carry different labels:

  • Doorbells and queue fetches are identified by addresses: which register was written, which slot in which queue was read.
  • A read request and its answer are tied together by a PCIe tag, but only until the answer arrives; then the tag is reused for something else.
  • The command itself is named by its Command Identifier (CID), which you find inside the fetched 64-byte command, and which is only unique within its submission queue.
  • Data packets carry no command label at all. You recognize them by their address: they fall inside the buffer addresses the command listed.
  • The completion entry carries the queue and the CID again, which closes the loop.
  • The interrupt carries only a vector, which tells you which completion queue to look at, not which command finished.

So correlation is a relay: address → slot → command (CID) → buffer addresses → data → completion (CID) → vector. Every hand-off uses the label that is valid at that point.

The method, as an algorithm

  1. Build the context. From the capture of controller initialization (or from Linux, see Linux view): BAR0, CAP.DSTRD, each queue's base, size, its CQ and its interrupt vector, and the MSI-X table entries. Without this table, addresses are just numbers.
  2. Classify every TLP by address and direction: doorbell (host MWr into BAR0 doorbell range), SQ fetch (device MRd in an SQ range), PRP list fetch (device MRd in a PRP-list range), data (device MWr or MRd elsewhere in memory), CQE (device MWr in a CQ range), MSI-X (device MWr in the interrupt window), completion (CplD/Cpl, matched by tag).
  3. Track doorbells per queue to know how many entries each doorbell published.
  4. Match fetches to completions by (Requester ID, Tag); reassemble split completions by Byte Count; decode each 64-byte SQE; create a command record keyed by (SQID, CID) with its slot, opcode, LBA range and PRP ranges.
  5. Attribute data to commands by address range; for writes, attribute the device's data MRds by address and their completions by tag.
  6. Close commands with CQEs keyed by (SQID, CID); record status, SQHD and phase; check that all of the command's data preceded its CQE.
  7. Attribute interrupts to CQs by vector, and head doorbells to the CQEs they acknowledge.
  8. Report orphans: completions with no matching request, data with no matching command, CQEs with no matching outstanding command, commands with no CQE. Orphans are where bugs live.

The central concept on the ladder

The central concept is the correlation key: the specific field that ties one stage of a command to the next, valid only within a scope and for a lifetime.

Bag stickers are reused every day; to find your bag you need the flight, the seat and the family name, used at the right moments.

Each link between stages uses one key: doorbell address, fetch address, PCIe tag, (SQID, CID), buffer address, CQ slot, MSI-X vector. Use each key only for the link it belongs to.

The controller's queue engine turns doorbells into fetches at computed addresses; its DMA engines allocate tags per outstanding read; its completion engine writes CQEs to computed addresses; its interrupt logic maps CQs to vectors. Each hardware block creates exactly one kind of key.

NVMe Base Specification: CIDs unique per SQ while outstanding; CQE carries SQID and CID; queue and doorbell layout. PCI Express Base Specification: tags unique per requester while outstanding; completions matched by Requester ID and tag; split-completion rules; MSI-X table.

Only non-posted requests carry a meaningful tag. Doorbells, data for reads, CQEs and MSI-X are posted writes and are identified only by address and payload.

In an analyzer, filter by address ranges (SQ, CQ, PRP pages, MSI-X window, doorbell block) rather than by tag; use tags only to pair each MRd with its CplDs; decode payloads to get CIDs.

Orphans and duplicates are the evidence: a CQE whose (SQID, CID) has no outstanding command, a data write outside every outstanding command's PRP range, a completion for a tag with no outstanding request, or two outstanding commands with the same (SQID, CID).

The sixteen questions, applied to the correlation key

The correlation key through the sixteen questions
QuestionAnswer
What is it?A field or derived value that links one stage of a command's trail to the next.
Why was it created?Each protocol layer needs its own way to match requests and responses: PCIe needs tags for split transactions; NVMe needs CIDs for out-of-order completion; queues need indices.
What problem does it solve?Allowing many outstanding operations at once without confusing their responses.
What existed before?Simpler interfaces with one outstanding operation per channel (or few, as in AHCI's 32 slots) where position alone identified the operation.
Why is the current design better?Deep parallelism and out-of-order completion at both layers; but it makes analysis harder, which is why this chapter exists.
Who creates it?Host: CID, queue placement, buffer addresses, vector assignment. Controller: PCIe tags for its requests, CQ slot choice (next tail). Root complex: tags for its own MMIO reads.
Who consumes it?The opposite party: the controller matches completions by tag; the host matches CQEs by (SQID, CID); the analyst uses all of them.
Where does it live?TLP headers (tag, Requester ID, address), payloads (CID, SQID, PRPs), configuration (queue bases, vectors).
What memory/registers are involved?SQ/CQ memory, doorbell registers, MSI-X table, IOMMU mappings.
What happens before it?Queue creation and MSI-X programming establish the static keys; submission assigns the dynamic ones.
What happens after it?Each key is released (tag on final completion, CID on consumed CQE, buffer on unmap) and reused.
What happens if it is wrong?Responses go to the wrong operation: wrong data placement, wrong command completed, stale completions, Unexpected Completion errors.
What does the protocol analyzer show?Tags, addresses and payloads; it can pair MRd/CplD automatically but cannot know NVMe meaning without queue context.
What does Linux show?qid and cmdid in NVMe tracepoints; queue and vector mapping in sysfs and /proc/interrupts; warnings for invalid CIDs.
What would a validation engineer test?CID reuse at high depth, tag reuse at maximum outstanding requests, completion reordering, shared vectors, queue wrap, duplicate-CID handling (Command ID Conflict).
What would a senior engineer suspect when it fails?Key reuse before release (tag or CID), stale state after reset or timeout, wrong queue context (BAR or base addresses changed), and analyzer visibility gaps.
