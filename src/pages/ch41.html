A real trace never contains one command. It contains hundreds, interleaved, completing out of order, on several queues, with Peripheral Component Interconnect Express (PCIe) tags being reused every few microseconds. This chapter teaches the method protocol analysts use to pull one command's thread out of that tangle: which key links each stage to the next, how long each key stays valid, and how to prove a match instead of guessing it.

Why this chapter exists

In The Most Important Chapter and End-to-End Write you followed single commands. The traces were easy to read because nothing else was happening. In practice an analyzer capture of a busy solid-state drive (SSD) shows thousands of Transaction Layer Packets (TLPs) per millisecond, and the question you are asked is never "what is a TLP?" but "which of these TLPs belong to the command that failed, and in what order did its stages happen?"

Answering that is the core skill of NVM Express (NVMe) over PCIe protocol analysis. It is not hard once you see the structure: every stage of a command is linked to the next by a specific key (an address, an index, a tag, an identifier), and each key has a scope and a lifetime. Use the right key for each link, respect its lifetime, and the thread comes out cleanly. Use the wrong key, the tag to find the command, or the Command Identifier (CID) without its queue, and you will confidently connect TLPs that have nothing to do with each other.

This chapter trains that thinking until it is automatic. The method also underlies the automated tools in Automated Trace Analysis and the forensic process in Error Correlation.

Learning objectives

  • State the correlation chain: NVMe command ↔ queue location ↔ controller access ↔ PCIe requester/completer ↔ address ↔ tag ↔ completion ↔ interrupt, and the key that joins each pair.

  • Identify a command by (SQ Identifier, Command Identifier) and explain why CID alone is ambiguous.

  • Untangle an interleaved trace of four concurrent commands on two queues by hand and with a script.

The story

At a busy airport, many families check in at once. Every suitcase gets a sticker with a number, but the stickers are reused every day, so a sticker number alone does not tell you whose suitcase it is today. To find your bag you need to know which flight (the queue), which seat (the slot), and your family name on the booking (the command identifier). The bag belt does not care whose bag is whose; it just carries bags. The person at the lost-and-found desk solves puzzles: "This bag came off flight 1, seat 17, the booking says Garcia family, so it is the Garcias' bag, even though the Garcias' friends on flight 2 also have a booking called Garcia."

A courier company's depot scanner log. Each line records "parcel scanned at door 3 at 10:02:17, route sticker 42." Route stickers are reused all day; customer orders are identified by account number plus order number; parcels for one order may come off several trucks and arrive in any order; and one "your delivery is ready" text message may announce several orders. To answer a customer complaint you work from the order (account plus order number) to the delivery addresses it lists, then to the scans at those addresses, using each sticker number only for the few minutes it was attached to one parcel.

  • Addresses carry more meaning in NVMe. In the depot story an address is just a destination; on PCIe the address of a fetch also tells you which queue and which slot the command came from, and the address of a data write tells you which command it belongs to.
  • Some events have no label at all. Posted writes (data for reads, CQEs, MSI-X, doorbells) have no tag that means anything. Every parcel in the analogy has a sticker.
  • The order number is inside the parcel. The CID is visible only in payloads (the SQE fetch completion and the CQE), never in TLP headers. The analogy suggests it is on the outside.
  • Some deliveries are invisible. An analyzer sees one link. Anything the I/O memory management unit (IOMMU) blocks, anything inside the SSD, and anything on another link is not in the log.

Beginner explanation

Each NVMe command leaves a trail of packets on the PCIe link: a doorbell, a fetch, data, a completion entry, an interrupt, another doorbell. When many commands run at once, their trails overlap. Correlation is the job of saying which packets belong to which command.

The trick is that you cannot use one label for the whole trail. Different parts of the trail carry different labels:

  • Doorbells and queue fetches are identified by addresses: which register was written, which slot in which queue was read.
  • A read request and its answer are tied together by a PCIe tag, but only until the answer arrives; then the tag is reused for something else.
  • The command itself is named by its Command Identifier (CID), which you find inside the fetched 64-byte command, and which is only unique within its submission queue.
  • Data packets carry no command label at all. You recognize them by their address: they fall inside the buffer addresses the command listed.
  • The completion entry carries the queue and the CID again, which closes the loop.
  • The interrupt carries only a vector, which tells you which completion queue to look at, not which command finished.

So correlation is a relay: address → slot → command (CID) → buffer addresses → data → completion (CID) → vector. Every hand-off uses the label that is valid at that point.

The method, as an algorithm

  1. Build the context. From the capture of controller initialization (or from Linux, see Linux view): BAR0, CAP.DSTRD, each queue's base, size, its CQ and its interrupt vector, and the MSI-X table entries. Without this table, addresses are just numbers.
  2. Classify every TLP by address and direction: doorbell (host MWr into BAR0 doorbell range), SQ fetch (device MRd in an SQ range), PRP list fetch (device MRd in a PRP-list range), data (device MWr or MRd elsewhere in memory), CQE (device MWr in a CQ range), MSI-X (device MWr in the interrupt window), completion (CplD/Cpl, matched by tag).
  3. Track doorbells per queue to know how many entries each doorbell published.
  4. Match fetches to completions by (Requester ID, Tag); reassemble split completions by Byte Count; decode each 64-byte SQE; create a command record keyed by (SQID, CID) with its slot, opcode, logical block address (LBA) range and PRP ranges.
  5. Attribute data to commands by address range; for writes, attribute the device's data MRds by address and their completions by tag.
  6. Close commands with CQEs keyed by (SQID, CID); record status, SQ Head Pointer (SQHD) and phase; check that all of the command's data preceded its CQE.
  7. Attribute interrupts to CQs by vector, and head doorbells to the CQEs they acknowledge.
  8. Report orphans: completions with no matching request, data with no matching command, CQEs with no matching outstanding command, commands with no CQE. Orphans are where bugs live.

The central concept on the ladder

The central concept is the correlation key: the specific field that ties one stage of a command to the next, valid only within a scope and for a lifetime.

Bag stickers are reused every day; to find your bag you need the flight, the seat and the family name, used at the right moments.

Each link between stages uses one key: doorbell address, fetch address, PCIe tag, (SQID, CID), buffer address, CQ slot, MSI-X vector. Use each key only for the link it belongs to.

The controller's queue engine turns doorbells into fetches at computed addresses; its direct memory access (DMA) engines allocate tags per outstanding read; its completion engine writes CQEs to computed addresses; its interrupt logic maps CQs to vectors. Each hardware block creates exactly one kind of key.

NVMe Base Specification: CIDs unique per SQ while outstanding; CQE carries SQID and CID; queue and doorbell layout. PCI Express Base Specification: tags unique per requester while outstanding; completions matched by Requester ID and tag; split-completion rules; MSI-X table.

Only non-posted requests carry a meaningful tag. Doorbells, data for reads, CQEs and MSI-X are posted writes and are identified only by address and payload.

In an analyzer, filter by address ranges (SQ, CQ, PRP pages, MSI-X window, doorbell block) rather than by tag; use tags only to pair each MRd with its CplDs; decode payloads to get CIDs.

Orphans and duplicates are the evidence: a CQE whose (SQID, CID) has no outstanding command, a data write outside every outstanding command's PRP range, a completion for a tag with no outstanding request, or two outstanding commands with the same (SQID, CID).

The sixteen questions, applied to the correlation key

What is it?A field or derived value that links one stage of a command's trail to the next.
Why was it created?Each protocol layer needs its own way to match requests and responses: PCIe needs tags for split transactions; NVMe needs CIDs for out-of-order completion; queues need indices.

Each correlation key is created by a specific hardware block: doorbell addresses by BAR decoding, fetch addresses by the controller's queue engine, tags by the controller's (or root complex's) request logic, CQ slot addresses by the completion engine, MSI-X address/data by the interrupt logic reading its table. Specification view

Correlation relies on a small number of normative uniqueness and ordering rules from two specification families: NVM Express Base Specification, Revision 2.4 (with the NVMe over PCIe Transport Specification, Revision 1.4 for the PCIe mapping) and the PCI Express Base Specification, Revision 6.x/7.0 family.

  • The Command Identifier, combined with the Submission Queue Identifier, uniquely identifies a command that is outstanding in the controller; the host must not reuse a CID on the same SQ while that command is outstanding (NVMe Base Specification, Submission Queue Entry and Completion Queue Entry definitions).
  • The CQE contains SQ Identifier, SQ Head Pointer, CID, Phase Tag and Status.
  • A requester's Transaction ID (Requester ID plus Tag) must be unique among its outstanding non-posted requests; completions are routed and matched by it (PCI Express Base Specification, Transaction Layer).
  • Completions for one request that is split are returned in increasing address order; completions for different requests may be returned in any order.
  • The interrupt vector used by an I/O completion queue is assigned by the host when the queue is created (Create I/O Completion Queue).
  • Data TLPs can be attributed only by address, because posted writes carry no command identity and no meaningful tag.
  • Using (SQID, CID) rather than CID as the command key; using the fetch address rather than the doorbell to locate each SQE.
  • The clock-alignment bracket method in Linux view.
  • How the controller chooses tags (sequential, recycled lowest-free, per-engine pools).
  • How many SQEs it fetches per request; whether it fetches from several queues in parallel.
  • How the host assigns CIDs (Linux derives them from blk-mq tags plus a generation counter), queue-to-CPU mapping, vector sharing.
  • Whether a controller detects a duplicate CID and reports Command ID Conflict.

Extended tags: 8-bit tags have been standard for a long time; 10-bit tags (and, in Flit Mode, 14-bit tags) extend the tag space. The Tag field's width and its header location depend on revision and mode. Our lab system has 10-bit tags disabled, so tags are 0x00–0xFF.

  • No specification ties PCIe tags to NVMe CIDs, or requires one fetch per doorbell, or one MSI-X per CQE.
  • NVMe does not require commands in one SQ to complete in submission order.
  • Neither specification says which CQ slot a given command will complete into; the CQ is filled in completion order.
  • Check in the NVMe Base Specification: the controller's obligations on detecting duplicate CIDs (the Command ID Conflict status exists; whether detection is required should be confirmed there).
  • Never identify a command by PCIe tag.
  • Never identify a command by CID without its SQ.
  • Never assume CQEs appear in submission order, or that a CQ slot number relates to an SQ slot number.
  • Never assume buffer addresses are unique across time: the same IOVA is reused by later commands.

Protocol view

Two layers of reordering

Out-of-order behaviour happens independently at both layers, and correlation has to survive both.

Interleaving patterns you will meet

  • Batched submission: one doorbell publishes several SQEs; one fetch of several entries; the commands then diverge.
  • Interleaved data: two reads finishing at the same time from different dies produce alternating data writes to two buffers; only addresses separate them.
  • Write pulls interleaved with read pushes: device MRd (upstream headers) and device MWr (upstream data) mixed, with CplDs flowing downstream.
  • Interrupt batching: one handler run consumes several CQEs and writes one head doorbell.
  • Spurious-looking interrupts: a second MSI-X arrives for a CQE the handler already consumed in the previous run, so the handler finds nothing new Implementation-dependent.

Linux view

Getting the context table

Correlation needs queue bases, sizes and vectors. Linux does not print queue base IOVAs in normal logs, so the most reliable source is the analyzer capture of controller initialization: the admin Create I/O Completion Queue (opcode 05h) and Create I/O Submission Queue (opcode 01h) commands carry each queue's base address in PRP1, its size and ID in CDW10, and (for the CQ) its interrupt vector in CDW11; the SQ's CDW11 names its CQ. If the capture started later, infer SQ bases from fetch addresses (they step by 64 and wrap) and CQ bases from CQE addresses. The rest comes from the host (IRQ below means interrupt request line):

# Queue-to-interrupt mapping: one IRQ per NVMe queue, named nvme0qN
grep -E 'nvme0q' /proc/interrupts
for i in $(grep -E 'nvme0q' /proc/interrupts | cut -d: -f1); do
  echo "IRQ $i -> CPUs $(cat /proc/irq/$i/smp_affinity_list)"; done

# Number of queues and which CPUs map to which hardware context
ls /sys/block/nvme0n1/mq/
cat /sys/block/nvme0n1/mq/*/cpu_list

# MSI-X capability: enabled, table size, table location (BIR/offset)
sudo lspci -vvv -s 01:00.0 | grep -A3 'MSI-X'

# BAR0 address and CAP.DSTRD (doorbell stride) as the driver sees them
sudo lspci -vvv -s 01:00.0 | grep 'Region 0'
sudo nvme show-regs /dev/nvme0 -H | grep -i -E 'stride|dstrd'

Host-side correlation by (qid, cmdid)

NVMe tracepoints print qid and cmdid, which are exactly the SQID and CID you decode from the link. That pair is the bridge between host and analyzer records:

Example with the ch39 READ (host times from pread() entry): setup at 1.00 µs, doorbell at link 0 ns gives Δ ≥ 1.00 µs; irq at 61.60 µs, MSI-X at link 58.34 µs gives Δ ≤ 3.26 µs. The true value (1.70 µs) lies in the bracket. Each additional command can only raise the lower bound or lower the upper bound; with a few hundred commands the bracket is usually well under a microsecond Derived.

What Linux evidence cannot do: it cannot tell you which TLPs belonged to a command, when the controller fetched it, or whether data writes went to the right addresses. It can tell you what the driver intended (setup), and what it concluded (complete), which is exactly what you compare the link against.

def num(s): return int(s, 0) if s.strip() else None

def classify_doorbell(addr):
    off = addr - BAR0 - 0x1000
    if 0 <= off < 0x1000 and off % (4 << DSTRD) == 0:
        idx = off // (4 << DSTRD)
        return idx // 2, "CQ head" if idx % 2 else "SQ tail"
    return None

def in_ring(addr, base, n, size):
    return base <= addr < base + n * size

def who(c):
    return f"SQ{c['qid']}/CID {c['cid']:#06x}" if c else "UNKNOWN command"

class Correlator:
    def __init__(self):
        self.pending = {}    # PCIe tag -> outstanding non-posted request
        self.cmds = []       # every command seen, in fetch order
        self.log = []

    def cmd_for_addr(self, addr):
        for c in reversed(self.cmds):
            if not c.get("done") and any(a <= addr < a + n for a, n in c["ranges"]):
                return c
        return None

    def add(self, t, d, typ, addr, ln, tag, bc, status, payload):
        if d == "H>D" and typ == "MWr":
            q = classify_doorbell(addr)
            self.log.append(f"{t:>9} ns  QID {q[0]} {q[1]} doorbell = {payload[0]:#x}")
        elif d == "D>H" and typ == "MRd":
            for qid, q in QUEUES.items():
                if in_ring(addr, q["sq"], q["sqn"], 64):
                    slot = (addr - q["sq"]) // 64
                    self.pending[tag] = dict(kind="sqe", qid=qid, slot=slot, size=ln * 4, buf=bytearray(ln * 4))
                    self.log.append(f"{t:>9} ns  tag {tag:#04x}: fetch SQ{qid} slots {slot:#x}..{slot + ln * 4 // 64 - 1:#x}")
                    return
            c = self.cmd_for_addr(addr)
            self.pending[tag] = dict(kind="data", cmd=c, addr=addr)
            self.log.append(f"{t:>9} ns  tag {tag:#04x}: data read {addr:#x} for {who(c)}")
        elif d == "H>D" and typ.startswith("Cpl"):
            p = self.pending.get(tag)
            if p is None:
                self.log.append(f"{t:>9} ns  tag {tag:#04x}: UNEXPECTED completion (no outstanding request)")
                return
            if status and status != "SC":
                self.log.append(f"{t:>9} ns  tag {tag:#04x}: completion status {status} ({who(p.get('cmd'))})")
            if p["kind"] == "sqe" and payload:
                off = p["size"] - bc                 # Byte Count = bytes still to come
                p["buf"][off:off + len(payload) * 4] = struct.pack(f"<{len(payload)}I", *payload)
                if bc == len(payload) * 4:
                    self.decode_sqes(t, p)
            if bc is not None and bc <= (ln or 0) * 4:
                self.pending.pop(tag, None)          # last completion: tag is free again
        elif d == "D>H" and typ == "MWr":
            for qid, q in QUEUES.items():
                if in_ring(addr, q["cq"], q["cqn"], 16):
                    dw2, dw3 = payload[2], payload[3]
                    sqid, cid, ph, st = dw2 >> 16, dw3 & 0xFFFF, dw3 >> 16 & 1, dw3 >> 17
                    match = [c for c in self.cmds if c["qid"] == sqid and c["cid"] == cid and not c.get("done")]
                    if match:
                        match[0]["done"], match[0]["status"] = t, st
                    self.log.append(f"{t:>9} ns  CQE CQ{qid} slot {(addr - q['cq']) // 16:#x}: SQ{sqid} CID {cid:#06x} "
                                    f"P={ph} status={st:#x} SQHD={dw2 & 0xFFFF:#x}" + ("" if match else "  <- NO MATCH"))
                    return
            if payload and (addr, payload[0]) in MSIX:
                v = MSIX[(addr, payload[0])]
                cqs = [qid for qid, q in QUEUES.items() if q["vec"] == v]
                self.log.append(f"{t:>9} ns  MSI-X vector {v} (CQ {cqs})")
                return
            self.log.append(f"{t:>9} ns  data write {addr:#x} for {who(self.cmd_for_addr(addr))}")

    def decode_sqes(self, t, p):
        for i in range(0, len(p["buf"]), 64):
            dw = struct.unpack_from("<16I", p["buf"], i)
            op, cid, nsid = dw[0] & 0xFF, dw[0] >> 16, dw[1]
            prp1, prp2 = dw[6] | dw[7] << 32, dw[8] | dw[9] << 32
            nbytes = ((dw[12] & 0xFFFF) + 1) * LBA if op in (1, 2) else 0
            first = min(nbytes, 4096 - prp1 % 4096)
            ranges = [(prp1, first)] + ([(prp2, nbytes - first)] if nbytes > first else [])
            c = dict(qid=p["qid"], slot=p["slot"] + i // 64, cid=cid, op=OPS.get(op, hex(op)),
                     slba=dw[10] | dw[11] << 32, nbytes=nbytes, ranges=ranges if nbytes else [], fetched=t)
            self.cmds.append(c)
            self.log.append(f"{t:>9} ns    SQ{c['qid']} slot {c['slot']:#x}: {c['op']} CID {cid:#06x} "
                            f"NSID {nsid} SLBA {c['slba']:#x} {nbytes} B PRP1 {prp1:#x} PRP2 {prp2:#x}")

def main():
    text = open(sys.argv[1]).read() if len(sys.argv) > 1 else DEMO
    k = Correlator()
    for row in csv.reader(io.StringIO(text)):
        if not row or row[0].startswith("#"):
            continue
        t, d, typ, addr, ln, tag, bc, status, payload = (row + [""] * 9)[:9]
        pl = [int(x, 0) for x in payload.split()] if payload.strip() else None
        k.add(int(t), d, typ, num(addr), num(ln), num(tag), num(bc), status.strip(), pl)
    print("\n".join(k.log))
    print("\nPer-command summary (fetch order):")
    for c in k.cmds:
        done = f"CQE at {c['done']} ns, status {c.get('status', 0):#x}" if c.get("done") else "NO COMPLETION SEEN"
        print(f"  SQ{c['qid']} slot {c['slot']:#x} CID {c['cid']:#06x} {c['op']:5s} -> {done}")

if __name__ == "__main__":
    main()

Common mistakes

  • Following a tag across stages. Tag 0x21 fetched the SQEs; three microseconds later, the controller may use 0x21 again for an unrelated data read.
  • Treating CID as globally unique. In the lab trace two different commands have CID 0x1041, on different SQs.
  • Assuming CQ slot = SQ slot. CQ slots are allocated in completion order and shared by every SQ that maps to the CQ.
  • Counting interrupts to count completions. One MSI-X can cover several CQEs; one CQE can be followed by a second, apparently useless, MSI-X.
  • Reading a fetch length as one command. Len = 48 DW is three SQEs.
  • Forgetting wrap. A tail doorbell value lower than the previous one means the ring wrapped, not that commands were withdrawn.
  • Attributing data by time. Data that arrives "near" a CQE is not necessarily that command's data; only address ranges prove it.
  • Ignoring the phase. A CQE with phase 0 is not an error; it means that CQ is on an odd pass through its ring.

Senior engineer insight

  • Build the context table first, always. Half of "impossible" correlations are wrong queue bases, a moved BAR after a reset, or an unknown previous doorbell value. Ten minutes on context saves a day.
  • Prefer address keys over everything. Addresses are carried by every TLP, are stable for the life of a command and cannot be reused while it is outstanding (if the host is correct). Tags and timing are secondary.
  • Hunt orphans, not matches. A correlator that reports only matches gives you a comforting picture; the bug is in the leftovers.
  • Correlate across resets carefully. After a controller reset, queues are recreated (often at the same IOVAs), CIDs restart and tags restart. Split the trace at the reset and correlate each segment separately.
  • Make the analyzer do the tag work. Let the tool pair MRd/CplD; spend your attention on the NVMe layer, where the tool has no semantics unless you give it the queue context.

What a senior engineer notices

The write completed in 3.6 µs while reads took 49–62 µs: a volatile write cache is enabled. The reads A and C finished together because they were probably served by the same die or channel batch. The interrupt pattern shows the driver handling batches, so interrupt counts underestimate completions.

Failure variants

  • Change row 51's DW3 to 0x00011041 (phase 1): the host, expecting phase 0 on CQ2, would not see the entry; D would time out although its CQE is in memory.
  • Change row 104's payload CID to 0x1041: the host would complete B a second time (or warn about an invalid CID), and A would time out.
  • Delete row 100: C's CQE would precede part of its data. On a read, that is a controller ordering violation and silent corruption risk.

Exercises

  1. An MRd from the device targets 0x1_2340_FFC0 with Len = 32 DW. What is wrong, or what is happening?

    Answer

    Slot (0xFFC0 / 64) = 1023, the last slot of SQ1. Len 32 DW = two SQEs, which would cover slots 1023 and 1024, but slot 1024 does not exist: the next entry after a wrap is slot 0 at the base. A correct controller splits the fetch at the wrap (one MRd for slot 1023, another at 0x1_2340_0000). This request would read 64 bytes beyond the queue: a controller bug.

  2. The previous SQ1 tail was 0x3FE and the new doorbell value is 0x003. How many commands were published, and in which slots?

    Answer

    (0x003 − 0x3FE) mod 1024 = 5 commands in slots 0x3FE, 0x3FF, 0x000, 0x001, 0x002.

  3. A CplD has Tag 0x40, Len 16 DW, BC 64, Lower Address 0x00. The request was an MRd of 48 DW at 0x1_2340_0400. Which bytes does this completion carry?

    Answer

    BC 64 means 64 bytes remain, including these 64: it is the last completion, carrying the last 64 bytes of the 192-byte request, i.e. address 0x1_2340_0480 (slot 0x12). Lower Address 0x00 agrees (0x480 & 0x7F = 0x00).

  4. Why can a CQE be safely attributed by (SQID, CID) even though the same CID appears on many commands over a capture?

    Answer

    Uniqueness holds among outstanding commands. At the moment of the CQE, only one outstanding command on that SQ can have that CID, so the match is to the most recent fetched-but-not-completed command with that pair. The correlator must therefore track outstanding state in time order.

  5. Two CQs share MSI-X vector 3. An MSI-X with vector 3 arrives. Which CQEs might it announce?

    Answer

    Any new CQE in either CQ since the handler last ran. The vector tells you which handler runs, not which queue or command finished; you must look at both CQs' CQE writes before the MSI-X.

  6. A data MWr lands at 0x2_0005_2300 and no outstanding command's PRP range contains it. Name three explanations and the evidence for each.

    Answer

    (1) A command that the host already timed out or aborted is still transferring: look for an earlier fetch of a command with that range and a timeout/abort sequence. (2) A PRP list entry you have not decoded (the command used a PRP list): find the MRd/CplD for its PRP list. (3) A controller PRP-walk bug: the address is close to but outside a real range (for example an off-by-one page); check for an IOMMU fault.

Quiz

  1. Which pair uniquely identifies an outstanding NVMe command in a controller?

    • (Requester ID, Tag)
    • (CQ ID, CQ slot)
    • (SQ ID, CID)
    • (MSI-X vector, CID)
    Answer and reasoning

    CIDs are unique per SQ while outstanding. (Requester ID, Tag) identifies a PCIe request; CQ slots and vectors are shared.

  2. Which TLPs of a READ carry a tag that is useful for matching?

    • Data Memory Writes
    • The SQE fetch MRd and its CplD
    • The CQE write
    • The MSI-X write
    Answer and reasoning

    Only non-posted requests and their completions use tags for matching. All other READ TLPs are posted writes.

  3. A fetch MRd at SQ base + 0x400 with Len 48 DW covers which slots?

    Answer

    0x400 / 64 = slot 0x10; 48 DW = 192 bytes = 3 entries: slots 0x10, 0x11, 0x12.

  4. How are READ data TLPs attributed to a command?

    Answer

    By address: the TLP address must fall in a memory page listed by that command's PRP entries (PRP1, PRP2 or PRP list), while the command is outstanding.

  5. True or false: CQEs for one SQ appear in the order the commands were submitted.

    • True
    • False
    Answer and reasoning

    False. Commands may complete in any order; CQ slots are filled in completion order.

  6. What does an MSI-X message tell you about which command completed?

    Answer

    Nothing directly. It identifies a vector, which maps to one or more CQs. You must read the CQEs written to those CQs before the message.

  7. How do you bracket the host/analyzer clock offset?

    Answer

    Lower bound from causality on submission (host setup must precede the doorbell on the link), upper bound from causality on completion (MSI-X on the link must precede handler entry). Combine over many commands, taking the largest lower bound and smallest upper bound.

  8. A CQE arrives with phase 0 on a CQ whose host expects phase 0. What does it mean?

    • A new, valid entry on an odd pass of the ring
    • An error status
    • A stale entry from the previous pass
    • An entry for an admin command
    Answer and reasoning

    The phase alternates per pass; a match with the host's expectation means new. A stale entry would carry the opposite phase.

  9. After a controller reset, why should you split the trace before correlating?

    Answer

    Queues are recreated (possibly at the same addresses), doorbells restart from 0, CIDs and tags are reused, and outstanding commands from before the reset are void. Correlating across the boundary will join unrelated events.

Interview questions

  1. (Beginner) What is the difference between a PCIe tag and an NVMe CID?

    Model answer

    A tag is chosen by a PCIe requester to match its non-posted requests to completions and lives only until the final completion. A CID is chosen by the host to identify an NVMe command within its SQ until the command completes. They are unrelated layers.

  2. (Beginner) How do you know which queue a doorbell write is for?

    Model answer

    From its address: offset 0x1000 + (2y) × (4 << CAP.DSTRD) is SQ y's tail doorbell, and + (4 << CAP.DSTRD) more is CQ y's head doorbell.

  3. (Intermediate) Walk me through correlating a single READ in a busy trace.

    Model answer

    Build queue context; find the SQ fetch whose CplD payload contains the CID of interest at the right SQ (the SQ from the fetch address); record its PRP pages; collect MWr in those pages after the fetch; find the CQE with that (SQID, CID); check all data preceded it; map the CQ's vector to the MSI-X that followed; find the head doorbell covering that CQ slot.

  4. (Intermediate) Why can one MSI-X correspond to several completions?

    Model answer

    The handler processes all new CQEs it finds; CQEs may arrive before the handler runs; coalescing may deliberately aggregate; masked vectors set a pending bit and send one message on unmask. Interrupts announce "look at this CQ," not "this command finished."

  5. (Advanced) Your capture starts in the middle of heavy I/O. How do you bootstrap correlation without the initialization sequence?

    Model answer

    Infer SQ bases from fetch addresses (cluster by 64-byte stride and wrap), CQ bases from CQE writes (16-byte stride), doorbell queues from BAR offsets; ignore commands whose fetch you did not see; start tracking tags only after their requests appear; infer the previous tail from the first fetch after each doorbell; use CQE SQIDs to map SQs to CQs; use MSI-X address/data clusters to map vectors to CQs by temporal proximity, and confirm with Linux /proc/interrupts counters.

  6. (Advanced) The host logs an invalid CID completion. What do you look for in the trace?

    Model answer

    Find the CQE with that (SQID, CID). Search backwards for fetches carrying that pair: zero (controller produced a CID never submitted: corruption), one already completed earlier (duplicate completion: controller bug), or two outstanding (host reused the CID). Also check for a timeout or abort of that command before the CQE, which would make a late CQE legitimate from the controller's view.

  7. (Senior) Design an automated correlator that a validation team can trust.

    Model answer

    Parse admin-queue traffic to build context; maintain per-queue state machines (tail, head, phase, outstanding CID table) and per-requester tag tables; decode PRP/SGL fully, including lists; attribute every TLP or emit an orphan; validate invariants (CID uniqueness, CQE after data, phase continuity, no fetch beyond tail, tag uniqueness, split-completion rules); segment on resets; produce a per-command timeline and an exceptions report; regression-test it on golden synthetic traces with injected faults.

  8. (Senior) An analyzer shows all data for a read written correctly and the CQE after it, yet the application sees stale data. What else could be wrong, given the trace is clean?

    Model answer

    The link is fine, so look beyond it: IOMMU translating the IOVA to a different physical page than the application's (mapping bug), CPU cache coherency on a non-coherent platform (missing invalidation), the host reading the CQE before the data became visible due to a missing read barrier (rare on x86), or the application reading another buffer. The correlation proved the device's part; the remaining suspects are on the host side of the root complex.

Model answer for the junior-engineer version

The doorbell's address tells you the queue and its value tells you how many new SQEs there are. The controller's fetch address tells you the slot and its length how many entries it read; its tag only pairs it with the CplD. Decoding the CplD payload gives each command's CID and PRPs; the SQ from the fetch address plus the CID is the command's name. Data is matched by address to the PRP pages; for writes, the controller's data reads are matched by address and their completions by tag. The CQE's SQID and CID close the command; the MSI-X vector tells you which CQ to look at; the head doorbell tells you the host consumed it.

Chapter summary

Correlating NVMe commands to TLPs is a relay of keys: doorbell address and value give queue and new entries; fetch address and length give slots; (Requester ID, Tag) pairs a request with its completions only while outstanding; (SQID, CID) from the SQE payload names the command; PRP pages attribute data by address; CQE slot and (SQID, CID) close the command; the MSI-X vector points to CQs, not commands; the head doorbell records host consumption. Commands complete out of order, completions for different tags arrive out of order, and interrupts batch. Build the context first, prefer address keys, track outstanding state in time order, and look for orphans: that is where faults show themselves.
